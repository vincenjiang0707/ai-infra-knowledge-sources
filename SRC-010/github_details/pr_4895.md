# [PR #4895] feat(pytorch): add piecewise CUDA graph prefill

## 正文

## Motivation

LMDeploy currently captures decode with a full CUDA graph, but prefill often cannot be captured as one graph because attention metadata, recurrent-state updates, sparse attention, and DeepEP collectives depend on live request or distributed state.

Running the entire prefill eagerly leaves graph-safe projections, normalization, tensor transformations, and local MoE work paying Python and kernel-launch overhead.

This PR adds an opt-in piecewise CUDA graph (PCG) path that captures graph-safe regions while executing graph-hostile operators eagerly in their original order:

```text
GraphPiece -> EagerCall -> GraphPiece -> ...
```

The implementation uses direct CUDA capture. It does not depend on `torch.compile`, Dynamo graph breaks, or FX partitioning.

## Modification

### Graph-runner architecture

- Refactor the CUDA graph runner into:
  - `runner.py`: eager/full-graph/piecewise dispatch;
  - `full_graph.py`: existing full decode CUDA graph behavior;
  - `piecewise.py`: generic tracing, stable bridges, ordered replay, streams, and plan ownership;
  - `standard.py`: standard-decoder token buckets, input padding, output slicing, and request selection.
- Keep the existing full CUDA graph decode path unchanged.
- Add a graph-runner README describing ownership, lifecycle, extension points, and unsupported cases.

### Piecewise capture and replay

- Capture contiguous graph-safe CUDA work around explicitly registered eager boundaries.
- Preserve eager calls and graph pieces in their original execution order.
- Bind request-local eager arguments by exact execution-frame identity.
- Use stable, runner-owned bridge storage for eager outputs consumed by later graph pieces.
- Share one ordered CUDA stream across mutually exclusive PCG plans while retaining independent CUDA graph-private pools.
- Add profiler ranges for complete PCG replay and individual graph/eager steps.

### Startup and configuration

- Capture every supported token bucket during startup warmup.
- Never capture or evict plans during serving.
- Add `PytorchEngineConfig.piecewise_cudagraph_max_tokens`.
  - `None` keeps PCG disabled.
  - A positive value enables PCG and sets its maximum prefill-token cutoff.
  - Requests above the cutoff remain eager.
- Expose the setting through `lmdeploy serve api_server` and `benchmark/profile_throughput.py`.
- Keep PCG policy independent of scheduler and paging capacity.

### Operator and model integration

CUDA implementations own their eager boundaries and output adapters; the generic graph runner contains no model- or operator-specific dispatch.

Initial integration covers:

- default and FA3 attention;
- MLA and NSA/DSA paths;
- causal convolution and gated-delta-rule state updates;
- local and DeepEP MoE implementations;
- Qwen3, Qwen3.5, and GLM MoE DSA model families;
- TP and supported DP/EP execution;
- Qwen3.5 MTP under TP2 and DP2/EP4.

Unsupported operator or topology combinations fail closed and use eager execution. `DP_TP` layer execution remains explicitly unsupported.

### Distributed failure handling

If Ray executor initialization fails while constructing distributed graph state, all worker actors are terminated and the original initialization exception is preserved.

## Usage

```bash
lmdeploy serve api_server Qwen/Qwen3-8B \
    --backend pytorch \
    --piecewise-cudagraph-max-tokens 512
```

The cutoff should be selected using measurements for the target model, backend, and hardware. Larger buckets can lose performance because of padded computation and eager-to-graph bridge copies.

## Validation

### Real-model validation

- Qwen3-8B showed about 27% lower p50 end-to-end latency for the tested 512-token H200 workload.
- Qwen3.5-35B-A3B-FP8 with MTP completed:
  - TP2 serving;
  - DP2/EP4 serving with DeepEP;
  - a 2,000-request mixed-prefill soak at concurrency 32;
  - 1,037,626 prompt tokens and 128,000 completion tokens without HTTP, CUDA, NCCL, DeepEP, or bridge-shape failures.
- Full `GPQA_diamond_repeat_4` completed all 792 generations under both TP2 and DP2/EP4 without serving or judge failures.

## Known limitations

- Token-bucket padding can change floating-point reduction shapes, so padded PCG output is not necessarily bitwise identical to raw-shape eager output. Mechanism comparisons use an equivalent bucket-shaped eager baseline.
- Captured plans remain resident for the runner lifetime and increase startup time and CUDA graph memory usage.
- Runtime capture, plan eviction, concurrent replay on one runner, `DP_TP`, and PCG on PyTorch 2.0 are not supported.
