## 正文


## Motivation

Support dflash in pt

## Use cases (Optional)

### pipeline

```python
from lmdeploy import PytorchEngineConfig, pipeline
from lmdeploy.messages import SpeculativeConfig

spec_cfg = SpeculativeConfig(
    method='dflash',
    model='z-lab/Qwen3.5-35B-A3B-DFlash',
    dflash_block_size=8,
)
pipe = pipeline(
    'Qwen/Qwen3.5-35B-A3B',
    backend_config=PytorchEngineConfig(tp=2),
    speculative_config=spec_cfg,
)
```

### serving

```shell
lmdeploy serve api_server \
Qwen/Qwen3.5-35B-A3B \
--backend pytorch \
--tp 2 \
--speculative-algorithm dflash \
--speculative-draft-model z-lab/Qwen3.5-35B-A3B-DFlash \
--speculative-dflash-block-size 8
```

When a DFlash block size is provided, it overrides
`--speculative-num-draft-tokens` by setting the number of newly proposed
tokens to `block_size - 1`.

### harshal-96 · 2026-09-01

Thanks for the invite to review, @RunningLeon. I recently implemented this same design independently (see #4530), and during bring-up I hit three subtle correctness traps, so I reviewed this PR specifically against those. All three check out:

1. **Aux-layer indexing.** The reference (`dflash/model.py`) consumes HF `hidden_states[layer_id + 1]`, i.e. the *output* of layer `layer_id`. This PR captures after `decoder_layer(idx)` runs (`qwen3.py` / `qwen3_5.py`) and uses checkpoint `target_layer_ids` unshifted, which is exactly equivalent. Worth noting for future readers: llama.py's eagle3 captures at layer *input*, so anyone copying that pattern needs a +1 shift; capturing after-layer as done here avoids the trap.
2. **Non-causal block attention.** Per-layer `Attention(causal=...)` resolved from `layer_types` with `(None, False)` for full-attention layers, validated up front in `_validate_dflash_v1_supported`. The draft is trained bidirectional-within-block, and a silently-causal query is the kind of bug that just shows up as mysteriously low acceptance. Handled correctly here.
3. **Rejected-row hygiene.** Writing the full verifier block into the draft KV and exposing only the committed prefix via `query_history` / `_query_start_positions` (gathering the last accepted target position, +1 for the bonus anchor) is the right sync-free design. I verified the position arithmetic including the rejection case: `context_lengths = seq - num_rejected`, and the anchor lands at the bonus position.

One question: for chunked long-context prefill, the ar_spec input preparation shifts/carries tokens across chunks (Case B/C/D in `_prepare_inputs_from_main`) while `materialize_context` stores rows at the draft inputs' `position_ids`. Is the cross-chunk row/position alignment covered in `test_dflash_utils.py`? That boundary is where I'd expect an off-by-one to hide.

Happy to validate this branch end-to-end on consumer hardware (RTX 4070 8 GB, WSL2) and report acceptance/throughput if useful. And per your suggestion, I'll rebase my Qwen3 (dense) enablement from #4530 on top of this PR's infrastructure as a follow-up PR once this lands; my standalone run confirms Qwen3-4B DFlash checkpoints work with this exact design (mean 5.48/15 drafts accepted, 3-4x wall-clock on the 4-bit target).


### RunningLeon · 2026-09-01

@harshal-96 
Hi, thanks for your review and testing.  As for your question, the B/C/D carry path is not upstream of DFlash materialization: `_prepare_inputs_from_main()` is used only by autoregressive proposers, while DFlash uses the diffusion proposal path and receives the original main-model rows and positions directly. Thus materialize_context() never consumes _prev_chunk_last or shifted draft inputs.

### harshal-96 · 2026-09-01

Following up on the Qwen3 side: I validated dense Qwen3 end to end on this branch (RTX 4070 8 GB, target `thewimo/Qwen3-4B-AWQ` fp16, draft `z-lab/Qwen3-4B-DFlash-b16` bf16, greedy, 256 new tokens): **33.6 to 36.8 tok/s vs 25.1 baseline, mean 4.19 of 15 drafts accepted per block**, coherent output. Two small gaps needed fixing to get there, packaged in [harshal-96/lmdeploy@feat/dflash-qwen3-dense](https://github.com/harshal-96/lmdeploy/tree/feat/dflash-qwen3-dense) (+28/-4 on top of this branch; `test_dflash_utils.py` passes 49/49 including a new regression case):

1. **Checkpoint layout.** `parse_dflash_config` requires `dflash_config['block_size']`, but the original z-lab Qwen3 checkpoints (`Qwen3-4B/8B-DFlash-b16`) store `block_size` at the top level of config.json and nest only `mask_token_id` and `target_layer_ids`. Added the reference implementation's fallback order (dflash_config first, then the top-level attribute), for `mask_token_id` as well.

2. **Mixed target/draft dtypes.** With an fp16 AWQ target and the bf16 draft, the draft forward fails with a dtype mismatch (shared target embedding output and target aux states flow into bf16 draft weights). Worth noting: loading everything as fp16 instead is not a workaround, acceptance collapses to 0.06 of 15 because Qwen3 hidden state outliers overflow fp16 during feature fusion (measured on both this branch and my standalone implementation). So the fix casts to the draft dtype at the two ingestion boundaries (`embed_input_ids`, `project_target_hidden`); the logits side is already covered by `get_logits`.

Happy to open this as a PR into your branch so it ships with this one, or as a follow-up PR to main after this merges, whichever you prefer.
