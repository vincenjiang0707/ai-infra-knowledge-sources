# [PR #4975] Remove cuBLAS grouped GEMM and give cuBLAS dense priority over native BF16/FP16 kernels

source: https://github.com/InternLM/lmdeploy/pull/4975
state: closed | updated: 2026-09-16T08:54:23Z
labels: Bug:P0

## 正文

## Summary

- Remove the cuBLAS grouped-GEMM backend (`cublasGemmGroupedBatchedEx`) and its two kernel families; grouped MoE GEMMs now always run on native TurboMind kernels.
- Promote the cuBLAS dense families above all native dense BF16/FP16 families so dense GEMMs route to cuBLAS at weight-plan time:
  - `dense_f16`: 210 → **260** (native FP16 kernels sit at 190)
  - `dense_bf16`: 220 → **260** (native BF16 kernels sit at 200 on SM80, 250 on SM90)

## Changes

`src/turbomind/kernels/gemm/cublas.cu`
- Delete `CublasGroupedKernel` (~330 lines), the `grouped_f16` (id 102) / `grouped_bf16` (id 103) families, and their registration.
- Drop the now-unused `moe_utils_v2.h` include and the dead `Grouped` template parameter on the `supports`/`pack` helpers.
- Add a comment documenting the dense-family priority rationale.

`src/turbomind/kernels/gemm/CMakeLists.txt`
- Remove the `ENABLE_CUBLAS_GROUPED` compile definition (CUDA ≥ 12.5 gate for `cublasGemmGroupedBatchedEx`).

Net: ~350 lines removed; the dense `CublasKernel` path is unchanged.

## Verification

**Correctness (BF16 MoE, Qwen3.5-35B-A3B, tp=1):** smoke test passes with a meaningful 256-token response. With `TM_GEMM_VERBOSE=1`, all 82k dispatch lines across the run follow the intended routing with zero exceptions:
- dense BF16 GEMMs → `family=101 backend=1` (cuBLAS), incl. the lm_head
- MoE router GEMMs (BF16→F32) → `family=105 backend=1` (cuBLAS)
- grouped expert GEMMs → `family=27 backend=0` (native SM90 kernels)

**Performance (dense BF16, Qwen3.5-27B, tp=1, 4096-token generation, batch 1):**

| | Before (native wins) | After (cuBLAS dense) |
|---|---|---|
| Decode throughput | 41.3 / 42.0 tok/s | **61.8 / 61.3 tok/s** |
| Inference time (4096 tok) | 99.1 / 97.5 s | 66.3 / 66.8 s |

≈ **1.48× faster decode** (~32% lower latency); pipeline load unchanged. The gain is largest at decode-style shapes (M=1), where vendor-tuned cuBLAS kernels beat the fixed-tile native GMMA path.

## Risk notes

- Grouped MoE workloads lose the cuBLAS grouped fallback entirely — they rely on the native grouped kernels, which the routing log confirms are selected.
- Weight-plan now pins the cuBLAS dense family for BF16/FP16 dense weights, so those weights keep the source-preserving (unpacked) layout; quantized families (w8a8/mxfp4/nvfp4/u4, priorities 250–301) are unaffected.
