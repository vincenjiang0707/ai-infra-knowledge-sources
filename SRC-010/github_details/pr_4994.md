# [PR #4994] fix(serve): tolerate messages without a content key in multimodal preprocessing

source: https://github.com/InternLM/lmdeploy/pull/4994
state: closed | updated: 2026-09-21T09:34:09Z
labels: Bug:P1

## 正文

## Motivation

`MultimodalProcessor._parse_multimodal_item` reads `in_messages[i]['content']` unconditionally. The OpenAI protocol allows assistant messages that only carry `tool_calls` to omit the `content` key entirely, and the Anthropic adapter emits exactly that shape when converting a pure `tool_use` turn (no text, no thinking blocks). Any such message crashes preprocessing with `KeyError: 'content'`, which surfaces to the client as a `400 "Request preprocessing failed"` before generation starts.

This hits every agentic workload that replays tool-call histories. Concretely, running Terminal-Bench 2 evaluations through the `/v1/messages` endpoint: turns with thinking/text blocks succeed, and the first pure tool-call turn fails.

## Modification

- Read the content field with `.get()` instead of indexing.
- Treat "not a list" (missing, `None`, string) uniformly as the existing pass-through branch.
- When the key is missing, normalize the message to `content: ''` so downstream chat-template assertions (`model.messages2prompt` requires `role` and `content` on every message) still hold. This matches what `merge_message_content` already does on the text-only path.

## BC-breaking (Optional)

None. Messages that already carry `content` behave exactly as before.

## Use cases (Optional)

```python
messages = [
    {"role": "user", "content": "check the repo"},
    # assistant turn with only a tool call -- no content key
    {"role": "assistant", "tool_calls": [{
        "id": "call_1", "type": "function",
        "function": {"name": "bash", "arguments": "{\"command\": \"ls\"}"},
    }]},
    {"role": "tool", "tool_call_id": "call_1", "content": "file_a\nfile_b"},
]
```

Previously raised `KeyError('content')`; now parses and renders through the chat template.
