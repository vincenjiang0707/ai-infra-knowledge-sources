Testing the disaggregated-serving worker-event lifecycle.

## Reproduction

`DisaggClusterManager.worker_event_loop` can permanently drop later events from a watch-event batch when an earlier event raises.

The issue is reproducible on commit `67a0328029` using the real `worker_event_loop` and `WatchEventQueue.drain()` implementation.

Minimal event sequence:

1. Queue a `DELETE` event for an unknown worker (`ghost-worker`).
2. Queue a valid `SET` event for worker `w1` in the same batch.
3. Allow `worker_event_loop` to process the batch.

The resulting behavior is:

```text
drain() -> [DELETE ghost-worker, SET w1]
DELETE ghost-worker -> ValueError("Worker ghost-worker is unknown")
batch-level exception handler runs
SET w1 -> never processed
queue -> empty
```

A control case containing two valid `SET` events, `[SET w1, SET w2]`, processes both events normally.

## Expected behavior

Each event in a drained watch-event batch should be processed independently.

If one event is stale, invalid, duplicated, or otherwise raises an exception, the remaining events in the same batch should still be processed.

In particular, a failing `DELETE` for an unknown worker should not cause an unrelated subsequent `SET` event to be lost.

## Actual behavior

`WatchEventQueue.drain()` destructively removes all currently queued events.

`worker_event_loop` wraps the entire drained batch in a single `try/except`. When processing one event raises, the loop exits the batch immediately.

As a result, any later events that were already returned by `drain()` are silently discarded and are not retried.

In the reproduction:

```text
[DELETE ghost-worker, SET w1]
        |
        v
DELETE raises ValueError
        |
        v
SET w1 is skipped
        |
        v
queue is empty
        |
        v
w1 remains absent from the manager state
```

## Additional Notes

The relevant code paths are:

* `tensorrt_llm/serve/disagg_auto_scaling.py`

  * `worker_event_loop`
  * `_parse_worker_info`
  * `_get_workers_by_id`

* `tensorrt_llm/serve/cluster_storage.py`

  * `WatchEventQueue.drain`

`WatchEventQueue.drain()` is destructive, so events skipped after an exception cannot be recovered by the next polling iteration.

The current `worker_event_loop` has one exception handler around the entire drained batch. This differs from the `get_worker_events` path in the same component, which isolates failures per event.

The runtime reproduction was performed against commit `67a0328029` using the real implementation. The exercised repository files were verified to be byte-identical to the pinned commit.

The bug case:

```text
[DELETE unknown-worker, SET w1]
```

resulted in no `on_event` calls and an empty queue afterward.

The control case:

```text
[SET w1, SET w2]
```

processed both events successfully.

A likely fix is to isolate exception handling per event so that one failing event does not abort the remainder of the drained batch. Unknown-worker `DELETE` events may also need to be treated as an idempotent no-op.

I can contribute a CPU-only regression test and fix if useful.
