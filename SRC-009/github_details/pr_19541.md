## Summary

Follow-up to #19469 (merged as f94eeb3738). Three commits:

1. **One parent reset for both locality-domain shards** (below).
2. **Static planner decision, shards as the only weight copy** (see below).
3. **[chore] Drop the cached-FC2 tactic from the split** so its tactic space equals the full-GPU op's and cannot be misled by warm profiling (concurrent partition tuning cannot use the cold-L2 mode). No measurable performance change (table at the end).

 The MXFP8 locality-domain split of the fused FC12 MoE launched each shard through the full fused op, so a split call paid two workspace resets, a standalone output memset (with its aux-stream event pair) and, because raw activations could not be handed to two concurrent shards, a standalone `mxfp8_quantize` launch. Those launches cost more than the split's kernel-level locality gain, which is why `enable_locality_domains` was neutral to slightly negative per MoE call.

This PR runs **one parent reset for both shards** on the caller's stream before the fork:

- `fused_fc12_workspace.py`: the reset kernel takes an optional second workspace (ready flags + two counters) and clears both partitions in one launch.
- `cute_dsl_custom_ops.py`: `Sm107Mxfp8FusedFc12MoeRunner` gains `skip_reset` (shard launches do no reset and require E4M3 input), class-level accessors for the cached sync workspace and input-quant scratch, and `launch_locality_domain_parent_reset` (both workspaces, whole-output clear under `zero_output`, BF16/FP16 -> MXFP8 quantization into the shared scratch, PDL against the preceding kernel). The composite op `cute_dsl_mxfp8_fused_fc12_moe_locality_domain_inplace_rubin` gains `zero_output`, registers the parent reset as the concurrent tuning runner's prologue and launches the skip-reset runner directly per partition (no nested custom op).
- `locality_domain/autotune.py`: `LocalityDomainConcurrentTunableRunner` / `tune_locality_domain_concurrent` accept an optional `prologue_fn` that runs before the fork on every forward, profiling included.
- `fused_moe_cute_dsl.py`: raw activations reach the split like the full-GPU op (the quant fusion no longer depends on the recorded per-token decision; `_mxfp8_full_gpu_path_selected` is removed) and the split path passes `zero_output` under the same dense-case rule instead of launching the separate memset.

Per split call: routing, one parent reset, two shard GEMMs (4 launches) instead of routing, quantize, memset, two resets, two shard GEMMs (6 launches + event pair). Locality domains stay **off by default**.

## Commit 2: static planner decision (as for NVFP4 / BF16), shards are the only copy

The MXFP8 split was a per-shape runtime choice: the autotuner profiled the full-GPU op and the split side by side, a per-token decision picked one (inside a 2048-row / 4096-route admission rule), and to keep that option open the module kept **both** the full expert weights and the shards resident, doubling the MoE weight memory whenever the flag was on. This commit follows the NVFP4 and BF16 paths: with `enable_locality_domains` the planner decides once, every shape of the layer runs the split (its tile / weight-streaming tactics stay autotuned), and `post_load_weights` releases the full parameters after sharding. The selector, its decision cache and the admission rule are removed. A refit after the release (RLHF) re-creates the full parameters transiently in `load_weights`; `post_load_weights` re-shards and releases them again.

**Bug fix (latent in #19469 and in the tekit MR):** the shard block scales were unswizzled and re-swizzled with the module's NVFP4 scale-vector size (16) instead of the MXFP8 block size (32), so the split computed with wrong scales whenever it ran. The op-level test did not catch it because it slices shards with its own helper; the flag is off by default, so the merged default path is unaffected.

**New test** `test_moe_module_mxfp8_locality_domain_static_split_rubin` (2 passed on Rubin): shards an MXFP8 layer, checks the full parameters and quant scales are released, checks the shards concatenate to exactly the base weights, compares the split against the full-GPU module at 16 and 4096 rows (0.5% RMS relative, cosine 0.99999: the shards' extra BF16 rounding of the partial FC2 sums at ~1e5 output magnitude; the MXFP8 quantization itself sits at 2.7% RMS from exact math) and repeats after a refit reload. All other sections re-pass (split op 2, CPU rules 18, kernel 39, planner 55, backend A/B 3).

## Same-node check of the cached-FC2 tactic removal (commit 3) and node sensitivity

Rubin, one node (a different one from the sweep above), same wheel, TEP8 worst rank, cold weights, us:

| tokens | off | split, cached-FC2 allowed | split, streaming only (commit 3) |
|---:|---:|---:|---:|
| 1 / 2 | 14.78 / 15.18 | 15.02 / 14.74 | 14.57 / 14.66 |
| 4 / 8 | 17.58 / 19.42 | 20.13 / 21.90 | 20.12 / 22.04 |
| 16 / 32 | 27.55 / 33.74 | 24.95 / 29.05 | 24.97 / 29.05 |
| 64 / 128 / 256 | 42.23 / 58.67 / 67.20 | 37.51 / 49.59 / 55.46 | 37.07 / 49.18 / 55.24 |
| 512 / 1024 / 2048 | 73.69 / 81.68 / 89.05 | 61.32 / 65.87 / 79.21 | 61.04 / 66.05 / 80.74 |
| 4096 / 8192 / 16384 | 116.78 / 155.95 / 226.67 | 105.95 / 186.30 / 281.00 | 106.12 / 186.74 / 281.56 |

The two split variants agree within 1-2% everywhere (3% at 1 token, within the run-to-run spread), so commit 3 is hygiene. Two observations from the traces at 1-16 tokens: (a) at 1-2 tokens (3-5 routes) each half-channel shard kernel is 0.5-0.8 us shorter than the full kernel because a few CTAs are limited by per-CTA weight streaming and each shard streams half the bytes; (b) at 4-8 tokens (9-17 routes) the full kernel is already close to the aggregate HBM limit, so the split cannot cut the bytes and each shard runs 1-1.5 us *longer* than the whole kernel (doubled input/metadata gathers, both shards' atomics on the same output rows, and the slower shard sets the pace), hence +13-15%. From 16 tokens per-CTA FC1 work is large enough for the half-channel split to win and the gain grows with routes. Note the split is more node-sensitive than the full-GPU op: flag-off agrees with the other node within 1-4%, while the split measured 9-19% under flag-off here against 4-8% there at the same token counts.
