# [Issue #19363] [Bug]: MegaMoE CuTe DSL is not rejected in can_implement on SM107, fails at launch

source: https://github.com/NVIDIA/TensorRT-LLM/issues/19363
state: closed | updated: 2026-09-17T19:24:51Z
labels: bug, Customized kernels

## 正文

## Summary
On SM107, MoE resolution can select the MegaMoE CuTe DSL backend because its `can_implement` does not turn SM107 down. The failure only surfaces at launch:

```
cute_dsl_megamoe_nvfp4_blackwell requires SM 100 (B200) or SM 103 (B300); got SM 107
```

## Impact
19 parametrized cases fail at launch instead of skipping/being rejected during resolution: `tests/unittest/_torch/moe/test_moe_backend.py` and `test_moe_module.py`, `backend=MEGAMOE_CUTEDSL-quant=NVFP4-*` (seen on 4x SM107 against `main`).

## Ask
Add the SM gate to `MegaMoECuteDsl.can_implement` (`tensorrt_llm/_torch/moe/fused_moe/mega_moe.py`) so resolution reports `sm_unsupported` on SM107, consistent with the other backends; or port the MegaMoE kernels to SM107 (#19183 territory).


## 评论 (1)

### farazkh80 · 2026-09-17

Superseded by #17956 (merged 2026-09-17, after this was filed): it ships Rubin MegaMoE kernels and `MegaMoECuteDsl.can_implement` now admits SM107 explicitly (`requires SM100, SM103 or SM107`), and the launch-time `requires SM 100 (B200) or SM 103 (B300)` path this issue describes no longer exists on `main`. Closing; the 19 `MEGAMOE_CUTEDSL-NVFP4` cases in `test_moe_backend.py`/`test_moe_module.py` will be re-checked on SM107 in the next QA sweep and a new issue opened if any bucket still fails.
