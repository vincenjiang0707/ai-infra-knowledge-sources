# [PR #18617] [#18616][fix] Continue a reasoning end tag the model began, do not restart it

## 正文

## Description

`ThinkingBudgetLogitsProcessor._forced_token` had two budget checks that disagreed. The first discounts the end tokens the model already emitted; the fallback below it counted those same tokens as reasoning content and forced `reasoning_end_token_ids[0]` again. In the band `budget - partial_end_len <= content < budget` the first branch correctly declined and the fallback fired anyway, restarting the end sequence at index 0.

With a two-token `</think>` the stream came out `</` `</` `think>`, so the reasoning parser never matched a clean end tag and reasoning text leaked into `message.content`. Same class of failure as #16785, which fixed the stale-token-view path and left the arithmetic alone.

The fix is one check that always discounts the partial end sequence and resumes at `reasoning_end_token_ids[partial_end_len]`. That value is 0 when no end sequence is in flight, so the old fallback behavior is unchanged.

Only multi-token end sequences are affected. On the Qwen2.5 tokenizer `</mm:think>` encodes to 5 ids and `<channel|>` to 4.

## Test Coverage

`tests/unittest/llmapi/test_sampling_params.py::test_thinking_budget_logits_processor_does_not_restart_partial_end_sequence`, added here. Greedy decode from `[1, 5, 6, 2]` with budget 3 gives `[1, 5, 6, 2, 2, 3, 7]` on main and `[1, 5, 6, 2, 3, 7, 7]` with this change. The file's other nine thinking-budget cases pass before and after.

Fixes #18616.

### Kayvan-Zahiri · 2026-09-03

You're right, and it's a regression from my previous commit rather than a pre-existing
gap. Fixed in f4f4a83.

I reproduced your case before changing anything. Driving the processor from
`token_ids=[1, 2, 3]` with start `[1, 2]`, end `[2, 3, 4]` and budget 0:

```
before:  forced [3, 4]      stream [1, 2, 3, 3, 4]      complete end tag: False
after:   forced [2, 3, 4]   stream [1, 2, 3, 2, 3, 4]   complete end tag: True
```

The raw match is 2 because `[2, 3]` is a genuine suffix-prefix of `[2, 3, 4]`, but it
straddles `reasoning_start`, and clamping to 1 keeps a length whose equality no longer
holds. Matching `token_ids[reasoning_start:]` restores the invariant and drops the `min`.

Added the overlapping case you asked for, with the same shape as your repro. It walks
three greedy steps and asserts the stream is `[1, 2, 3, 2, 3, 4]`, so it pins `end[0]`,
`end[1]`, `end[2]` in order. Simulated against both code paths, the assertion fails on the
previous commit with `[1, 2, 3, 3, 4, 0]` and passes after.

You were also right that the existing cases could not catch this: every one of them uses
disjoint start and end tokens, so `_longest_suffix_prefix_len` never had a way to match
across the boundary.

One limitation worth stating plainly. I could not run
`tests/unittest/llmapi/test_sampling_params.py` locally, because importing `tensorrt_llm`
needs the vendored triton kernels and a CUDA build that I do not have here. I verified the
logic by re-implementing `_find_last_sequence_index`, `_longest_suffix_prefix_len` and the
`_forced_token` decision path exactly as they appear on the branch, and driving both
variants through the same loop the new test uses. That is a faithful simulation, not an
execution of the test itself, so CI is the first real run of it. Please treat the numbers
