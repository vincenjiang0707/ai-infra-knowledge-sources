### Reproduction

When `enable_iter_req_stats` and `enable_iter_perf_stats` are both enabled, the queued-request stats
path treats every item on the request queue as a normal request. Shutdown and control sentinels are
not normal requests and do not carry the fields that path reads, so collection raises.

Stats collection is a prototype feature (both options default to `False`), so the blast radius is
limited to deployments that turn it on — but for those, the failure occurs on the executor's own
stats path rather than in a request, which makes it disproportionately disruptive relative to the
feature's value.

### Expected behavior

Sentinel items on the request queue are skipped when populating queued-request stats.

### actual behavior

They are treated as normal requests, so stats collection raises on fields they do not carry.

### additional notes

Skip sentinel items when populating queued-request stats, using the existing predicate that already
distinguishes them. No API change; for normal requests, allocation and reporting are unchanged apart
from evaluating that predicate.

We have the patch and unit tests, and are raising this Issue Request first per CONTRIBUTING.md.

### karljang · 2026-09-05

Thank you for reporting this.
This is already fixed on main, and along the lines you proposed. The queued-request stats loop at `tensorrt_llm/_torch/pyexecutor/py_executor.py:2214-2218` now skips items where `is_normal_request` is false before anything dereferences `item.request`, using the existing predicate rather than a new one, and adds a `None`-payload guard immediately after. The surrounding code also handles the unusual case where a normal request carries no readable `input_token_ids` by excluding it from the counters and logging, so a stats collection pass no longer raises on queue contents that are not ordinary requests. There is a test covering the sentinel case at `tests/unittest/_torch/executor/test_iter_stats_populate.py:380`.
