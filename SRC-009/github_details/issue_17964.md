## Config


## Start server

```bash
trtllm-serve serve /path/to/Qwen3.5-2B --host 0.0.0.0 --port 8000 --config qwen3.5-2b.yaml
```

## Send 20 concurrent identical requests

```bash
for i in $(seq 1 20); do
  curl -s http://localhost:8000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
      "model": "Qwen3.5-2B",
      "messages": [
        {"role": "system", "content": "Translate the following Chinese text to English."},
        {"role": "user", "content": "今天天气怎么样？你去哪里玩呢"}
      ],
      "max_tokens": 256,
      "temperature": 0
    }' &
done
wait
```

## Observation

- Single request: correct output (14 tokens)
- 20 concurrent requests: 19 out of 20 produce wrong output (22 tokens with hallucinated repetitions)
- The 1 request that was prefilled alone produces different (better) output than the 19 prefilled as a batch


### Expected behavior

All 20 concurrent requests should return the same correct translation:

> How is the weather today? Where are you going to play?

This is what a single request returns, and what vLLM (with --language-model-only) returns at any concurrency level.


### actual behavior

19 out of 20 requests return incorrect output with hallucinated repetitions:

> How's the weather today? Where are you going? Where are you from? Where are you from?

The first request (prefilled alone, batch=1) returns 17 tokens with slightly different content.
The remaining 19 (prefilled together, batch=19) all return identical wrong 22-token output.

Corruption scales with output length — short outputs (~7 tokens) appear correct even at high concurrency.


### additional notes

- Batch size <= 3: output is correct
- Batch size > 3: output becomes corrupted
- Disabling CUDA graph does not fix the issue
- The same model works correctly under vLLM with `--language-model-only` at any concurrency
- Verbose log confirms all requests are batched together for generation:
  `has 20 active_requests, scheduled 0 encoder requests, 0 context requests and 20 generation requests`
- Short outputs appear correct because corruption has not accumulated enough tokens to be visible

1. graph enabled with padding disabled / exact graph sizes around concurrency 4–10;
2. a fresh-server graph-off concurrency-20 control plus mapping 11–20;
3. direct `LLM.generate()` batching to bypass the OpenAI HTTP layer. This still uses TensorRT-LLM's `GenerationExecutor`, so a direct RED result would place the defect below the HTTP frontend but would not by itself distinguish scheduler/state metadata from the model/GDN kernels.

### Consolidated status through root-cause closure

This is the current master status for my reproduction/localization work on
current-main commit `f51e32335aefdc39c4118a0ab0ce5f5196623711` /
TensorRT-LLM `1.3.0rc25`, Qwen3.5-2B, TP1, single-process worker, RTX 4090 D.

#### Established output boundary

The reporter-provided prompt reproduces deterministically on current main:

- CUDA graph on: batch 4 passes; batch 5 fails.
- CUDA graph off: batch 14 passes; batch 15 fails.
- Graph padding on/off has the same 4/5 boundary.
- Block reuse had no detectable effect in the matched 2×2 matrix.
- Offline `LLM.generate()` and `trtllm-serve` have the same integer boundaries.
- Every failing case first changes generated token index 9 from `?` to ` and`.

#### Localization before the closure run

Request-bound metadata tracing found no inconsistency in the observed live
request-to-slot mapping, while retaining the limitation that full cache-manager
ownership was not visible.

At the aligned failing request:

```text
layer 2 linear output:          bitwise identical
layer 3 full-attention input:   bitwise identical
layer 3 attention-core output:  first differing boundary
```

QKV projection, position inputs, Q/K/V preprocessing, conversion, and the
selected visible length/block metadata matched before that boundary. This
placed the remaining fault inside the attention backend / KV-state boundary,
not in the downstream gate or output projection.

#### One-pass closure result

I ran a fresh graph-off/block-reuse-off closure matrix with b1, b14, b15, and a
second b15 instance in two rounds. All eight cases passed the runtime and trace
contract:

```text
b1:  PASS
b14: PASS
b15: FAIL
b15 target output stable across all repeats
```

Every case selected
`tensorrt_llm._torch.attention_backend.fmha.fallback.FallbackFmha`.

At generation steps 0 and 7, the exact common first-14 values of all bounded
Python-visible native-attention inputs had no observed differences. The only
incomplete call-pack paths were the global `kv_cache_block_offsets` table and
native `workspace_`, for which the Python boundary exposes summaries rather
than an exact per-request state. Physical Layer-3 KV pages and the C++ runner /
plan cache also cannot be cloned for a semantically valid same-input replay.

```text
FMHA dispatch:       CLEAN
exact call inputs:   no observed common-prefix difference
KV content:          not exposed safely
isolated replay:     not semantically available
overall:             CXX_PLAN_OPAQUE
```

This does not justify a production patch yet, and I do not want to guess at a
kernel or KV fix from pointer/layout summaries.

The minimum next step is one narrow C++ diagnostic hook around
`thop.attention` / `Runner::run` that emits, for the selected Layer-3 call:

- XQA/MMHA selection and concrete kernel name;
- multi-block setting and blocks per sequence;
- workspace partition sizes;
- runner/plan cache reuse decision;
- launch/grid parameters;
- the physical KV page mapping used by the selected request.

Could a maintainer point me to the preferred existing debug surface, or confirm
that a small diagnostic-only hook for those fields would be acceptable?
