# [Bug] /v1/responses does not populate /perf_metrics request entries

## Description

`trtllm-serve` exposes `/perf_metrics` for completed request-level performance metrics. In a current source checkout (`c2e0379fb3988b1b7f97fcf6441685f189b805ff`), static inspection shows the chat/completions and completions handlers call `_extract_metrics(...)` after generation, while the Responses API success paths return without an equivalent metrics extraction call.

On an A100 using the official TensorRT-LLM container `nvcr.io/nvidia/tensorrt-llm/release:1.3.0rc14`, successful `/v1/chat/completions` and `/v1/completions` requests produced `/perf_metrics` entries, but successful `/v1/responses` requests did not. The same gap reproduced across three non-streaming request orders, repeated `/v1/responses` requests, streaming `/v1/responses`, and postprocess-worker mode.

## Why this matters

The Responses API is an OpenAI-compatible serving endpoint. Operators using `/perf_metrics` for latency, KV-cache metrics, or per-request diagnostics may silently miss all `/v1/responses` traffic. In the same runtime pass, Prometheus request counters also did not advance for `/v1/responses` while they advanced for chat/completions and completions.

1. Start `trtllm-serve` with request perf metrics enabled using the command/config above.
2. Call `GET /perf_metrics` and save the baseline.
3. Send a successful `/v1/chat/completions` request.
4. Call `GET /perf_metrics` and observe a new request metric entry.
5. Send a successful `/v1/responses` request.

7. Repeat with request order changed and repeated `/v1/responses` requests.

- I found Responses API tests in `tests/unittest/llmapi/apps/_test_openai_responses.py:92-287`, but no `/perf_metrics` assertion for `/v1/responses`. Existing `/perf_metrics` unit coverage is completions-only in `tests/unittest/llmapi/apps/_test_openai_perf_metrics.py:54-101`.

## Controls

- Perf metrics disabled: with no perf metrics config, all three endpoints returned 200 and `/perf_metrics` remained empty. This confirms the positive-control entries require the metrics config.
- Buffer control: `perf_metrics_max_requests=50` with a nine-request matrix; no eviction should occur. Chat/completions and completions produced entries, Responses did not.
- Repeated chat positive control: three non-streaming chat requests returned 200 and produced request IDs `24`, `25`, and `26`.
- Repeated responses target control: three non-streaming Responses requests returned 200 with response IDs `resp_713cc4ede5c44320957ce61c50f86926`, `resp_ac29b23170bf4c50b931c2d2d16deabf`, and `resp_eb7f74ade1c74096890ec8e8d78feee5`; `/perf_metrics` returned zero entries after each.
- Request order controls: the gap reproduced in `chat -> completions -> responses`, `responses -> chat -> completions`, and `completions -> responses -> chat`.
- Streaming control: streaming chat and completions produced entries; streaming Responses returned 200 and produced no entry.
- Postprocess worker control: with `--num_postprocess_workers 2`, the non-streaming matrix reproduced the same result, so the gap was not caused by the default no-worker setting.

Update on the current state of this issue:

The missing metrics extraction on the Responses API paths was fixed as part of #16668 — `openai_responses` now calls `_extract_metrics` on both the non-streaming path (`create_response`) and the streaming path (`create_streaming_generator`):
https://github.com/NVIDIA/TensorRT-LLM/blob/40bee2a8/tensorrt_llm/serve/openai_server.py#L2804
https://github.com/NVIDIA/TensorRT-LLM/blob/40bee2a8/tensorrt_llm/serve/openai_server.py#L2821

What was still missing is test coverage: `tests/unittest/llmapi/apps/_test_openai_perf_metrics.py` only exercised `/v1/completions`, so a regression on `/v1/responses` would go unnoticed. I opened #18856 adding non-streaming and streaming `/v1/responses` perf-metrics tests to that file, which should close this issue once merged.
