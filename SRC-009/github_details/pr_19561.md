## Description

`RemoteMpiCommSessionClient.submit_sync` could return an exception object where
its callers expect `List[T]`.

When a worker task fails, the server forwards the failure as the response
payload itself:

```python
# RemoteMpiCommSessionServer.mpi_future_callback
if future.exception() is not None:
    self.queue.put(future.exception())
    return
```

The client returned that payload verbatim, so the caller received a bare
exception instead of a list. `CachedModelLoader._download_hf_model_if_needed`
then iterates it:

```python
model_dir = next((d for d in model_dirs if d is not None), None)
```

which raises `TypeError: '<SomeError>' object is not iterable` — far from the
real cause, and hiding whatever the worker actually raised.

The other two sessions do not have this problem: `MpiPoolSession.submit_sync`
and `MpiCommSession.submit_sync` both return `[future.result() for ...]`, and
`future.result()` re-raises. This change makes the remote session consistent
with them.

## Test Coverage

No new test. The change is a two-line guard on an error path that requires a
live remote MPI session with a failing worker to exercise; it has not been run
against such a session. It is derived from the two call sites quoted above.

Behaviour on the success path is unchanged: `res` is a list there, so
`isinstance(res, BaseException)` is false and the function returns as before.
