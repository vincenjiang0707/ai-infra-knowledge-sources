## Description

Adds `.claude/skills/trtllm-pr-checklist`, a review-time checklist skill for preparing, reviewing, and revising TensorRT-LLM pull requests, and fixes three documentation inconsistencies found while writing it and during review.

**Why.** The repo already has strong agent tooling for the *implementation* phase — `trtllm-codebase-exploration` (survey before coding) and `trtllm-code-contribution` (patterns and pitfalls while coding). Nothing covered the point where a change is handed to a human. The result is that recurring review feedback — unstated compatibility assumptions, over-parametrized tests, performance claims without a stated configuration — has to be raised by hand on every PR.

**What the skill covers.** Design fit and blast radius on core components; correctness across shared execution paths (parallelism modes, SM versions, quantization, aggregate/disaggregated, the Python/C++ nanobind boundary); the distinction between *validating* a change by running it and *testing* it with code that lands in the repo; CI registration (test-db lists for both integration and unit tests, `test_to_stage_mapping.py`, waives needing an NVBug link); code quality; and whether a PR's claims are actually backed by evidence. It supports three modes: author self-check, reviewing someone else's PR, and revising after reviewer or CodeRabbit feedback.

**Scope change to `trtllm-code-contribution`.** It now covers the implementation phase only. Its PR-specific sections move to the new skill, and its readiness list is rescoped to implementation invariants. This also fixes a stale path: it referenced `tests/api_stability`, but the suite lives under `tests/unittest/api_stability`.

**`AGENTS.md`** gains one rule — run the checklist before requesting review — and a fourth step in the Development Workflow. The rule cites the file path rather than only the Claude Code slash command, so non-Claude agents can follow it too.

### Documentation corrections

These are all cases where a checked-in document disagreed with what CI actually enforces, so following the document produced a failing or silently ineffective PR.

| Document | Was | Actually |
|---|---|---|
| `CONTRIBUTING.md` — PR title | Described Conventional Commits (`feat: description`) | `pr-check.yml` enforces `[ticket][type] Summary`; 299 of the last 300 commits on `main` use it. Every example previously listed would be rejected |
| `CONTRIBUTING.md` — `BREAKING` | "add BREAKING to the title", placement unstated | Only `[None][feat] BREAKING: Summary` passes both checks. `[BREAKING]` as a bracket tag fails the title regex; `[breaking]` fails the case-sensitive `api-breaking` check |
| `CONTRIBUTING.md` — protected APIs | Quoted a failure at `tests/api_stability/test_api_stability.py:241` | That path no longer exists; `api_stability_core.py` now raises two distinct messages |
| `docs/source/developer-guide/ci-overview.md` | Unit tests "run during the merge-request pipeline ... do not require mapping to specific hardware stages" | CI does not collect `tests/unittest/` directly. Unit tests run only through `unittest/...` bridge entries in the test-db lists |

The `ci-overview.md` fix is in this PR rather than a separate one because it is the same defect the checklist itself had, found from the same review comment — splitting them would leave the source of the error in place while fixing the copy.

## Test Coverage

No automated tests are added. This PR changes documentation and agent instructions only; it does not touch runtime code, build configuration, CI workflows, CI scripts, or the PR template, so no runtime test, model evaluation, or benchmark applies.

Validation performed:

- `pre-commit run --files <each changed file>` passes, including the repo's own `Check Claude Code skill naming convention` hook and `codespell`.
- The six PR-title examples newly written into `CONTRIBUTING.md` were checked against the exact regex from `.github/workflows/pr-check.yml`; all six match. The six they replace do not.
- The `BREAKING` placement table was reproduced against both regexes — `pr-check.yml`'s title format and `llm-api-compatibility.yml`'s `title.includes('BREAKING')`. Of the four plausible placements, only `[None][feat] BREAKING: Summary` passes both.
- The claim that the bracketed title form is the de facto convention was measured, not assumed: of the last 300 non-merge commits on `origin/main`, 299 match `[ticket][type]` and 0 match Conventional Commits. The one outlier carries two ticket tags.
- The unit-test collection claim was checked against the test-db lists directly: 853 entries carry the `unittest/` prefix and none is a bare `unittest/`, confirming there is no catch-all and that an unlisted unit test is never collected.
- The API-stability trigger set was read from `llm-api-compatibility.yml`: four prefixes, including `llmapi/llm_args.py` and `usage/llm_args_golden_manifest.json`. The earlier draft told authors to commit that manifest and then implied no label was needed, which fails the job.
- `.github/scripts/pr_checklist_check.py` was exercised directly to confirm the constraint documented in the skill's section 4.6: any unchecked checkbox anywhere in a PR body fails the job, and only a strikethrough spanning the entire item counts as resolved. The skill's summary checklist is therefore marked as being for local use or a review comment, not for pasting into a PR description.
- Every repository path referenced by the new skill was checked for existence against `main` (45 paths). This caught an earlier draft that pointed at `_torch/modules/attention.py` (now a compatibility shim), `_torch/modules/fused_moe/` (removed), and `_torch/attention_backend/` (now re-export only).

Not validated: the skill's effect on real review cycles. This PR makes no claim about reduced review rounds or review time — that can only be assessed after it has been used on actual PRs.

## PR Checklist

Please review the following before submitting your PR:
- PR description clearly explains what and why. If using CodeRabbit's summary, please make sure it makes sense.
- PR Follows [TRT-LLM CODING GUIDELINES](https://github.com/NVIDIA/TensorRT-LLM/blob/main/CODING_GUIDELINES.md) to the best of your knowledge.
- Test cases are provided for new code paths (see [test instructions](https://github.com/NVIDIA/TensorRT-LLM/tree/main/tests#1-how-does-the-ci-work))
- If PR introduces API changes, an appropriate PR label is added - either `api-compatible` or `api-breaking`. For `api-breaking`, include `BREAKING` in the PR title.
- Any new dependencies have been scanned for license and vulnerabilities
- [CODEOWNERS](https://github.com/NVIDIA/TensorRT-LLM/blob/main/.github/CODEOWNERS) updated if ownership changes
- Documentation updated as needed
- Update [tava architecture diagram](https://github.com/NVIDIA/TensorRT-LLM/blob/main/.github/tava_architecture_diagram.md) if there is a significant design change in PR.
- The reviewers assigned automatically/manually are appropriate for the PR.
