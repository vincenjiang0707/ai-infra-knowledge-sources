# [Issue #18083] Reasoning-parser auto-selection misclassifies reasoning-at-start templates, silently emptying reasoning_content

source: https://github.com/NVIDIA/TensorRT-LLM/issues/18083
state: open | updated: 2026-09-14T06:12:52Z
labels: LLM API

## 正文


### System Info

- TensorRT-LLM: 1.3.0rc23
- GPU: NVIDIA GeForce RTX 5090 (sm_120), driver 595.71.05
- Backend: PyTorch; single GPU, no TP/PP
- Model: `Qwen/Qwen3.8-27B` (also reproduced with the NVFP4 conversion of the same model)

### Who can help?

_No response_

### Reproduction

`_resolve_qwen3_reasoning_parser` (`tensorrt_llm/llmapi/reasoning_parser.py`) classifies a chat
template as "hybrid" when the template contains an `enable_thinking` toggle, and selects the
`qwen3` parser, which expects a matched `<think>...</think>` pair.

Qwen3.8's chat template injects `<think>\n` into the *generation prompt* whenever
`enable_thinking` is undefined — which is the default. The model's output therefore begins
already inside the reasoning span: it contains a closing `</think>` and **no opening `<think>`**.

Serve with automatic parser selection and send any prompt:

```bash
trtllm-serve <qwen3.8-27b> --backend pytorch     # no --reasoning_parser
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-27b","messages":[{"role":"user","content":"What is 17*23?"}]}'
```

The three-way classification has no case for "template has a toggle, but injects the opening
marker when that toggle is undefined".

### Expected behavior

Automatic selection picks a parser registered `reasoning_at_start=True`, so `reasoning_content` carries the chain of thought and `content` carries only the answer.

### actual behavior

The `qwen3` parser finds no opening marker, splits nothing, and returns `reasoning_content` empty while raw chain-of-thought is emitted into `content`. No warning is raised, so a caller that renders `content` shows the model's private reasoning to the end user.

### additional notes

Explicitly selecting `--reasoning_parser deepseek-r1`, which is registered
`reasoning_at_start=True`, produces correct separation on the same build and model. That is the
workaround we run in production, and it is also the evidence that the parser set is adequate and
only the selection is wrong.

This is a *selection* defect and is distinct from two nearby reports: #17916 concerns
`DeepSeekR1Parser` ignoring a per-request `enable_thinking=False`, and #17296 concerns streaming
and non-streaming parsers disagreeing. Both assume the correct parser was chosen.

**Questions for maintainers**

1. Should the classifier gain a fourth case, or should templates that inject an opening marker be
   detected directly (e.g. by rendering the generation prompt and inspecting it)?
2. Is a warning appropriate when a selected parser produces an empty `reasoning_content` for every
   response in a session? The silence is what makes this reach production.

### somtri · 2026-09-13

Reproduced on main (21dc97fb) with the published `Qwen/Qwen3.8-27B` config and `tokenizer_config.json`. I called the resolver and parsers in `reasoning_parser.py` directly, CPU only:

- `resolve_auto_reasoning_parser` returns `"qwen3"`, because the template mentions `enable_thinking`.
- The template's generation prompt ends in `<think>\n` unless `enable_thinking` is explicitly false, so the model output has `</think>` but no opening tag.
- With `qwen3`, everything including `</think>` ends up in `content` and `reasoning_content` is empty. `qwen3_5` and `deepseek-r1` split the same output correctly.

1. At selection time, render the template's generation prompt and check whether it ends in `<think>`, rather than searching the template source. A template that prefills it would get a reasoning-at-start parser that still respects a per-request `enable_thinking=false`.
2. Have the parser picked for Qwen3 hybrid templates set `resolves_thinking_from_prompt`, so `openai_server.py` reads the mode off each rendered prompt, the same path `poolside_v1` already uses.

For tests, I'd keep the existing `_HYBRID_TEMPLATE` case and add cases from the real Qwen3 and Qwen3.8 templates. The change would stay in `reasoning_parser.py` and its test file, and I'd rebase on #18074 if that merges first.

### zhaoyangwang-nvidia · 2026-09-14

Thanks @somtri for the repro, and @yenhao-huang for handing it over. Please go ahead — this is yours.

I'd go with approach 2 (`resolves_thinking_from_prompt`). My reasoning, and a few things that will save you a round of review:

**Approach 1 alone cannot be made correct.** The mode is per-request but the parser key is per-server, so the granularities don't match. `_HYBRID_TEMPLATE` in `tests/unittest/llmapi/test_reasoning_parser.py:829-834` already shows both renderings of the same template: `<think>\n` when the toggle is undefined or true, and `<think>\n\n</think>\n\n` when it is false. `DeepSeekR1Parser.parse()` branches on `reasoning_at_start` (reasoning_parser.py:244-253) and the flag is fixed at registration (199-211), so `qwen3` breaks the first case (this issue) and `qwen3_5` breaks the second (the answer lands entirely in `reasoning_content`). There is no correct static key for a hybrid template. That is also why only changing the selector is not enough: it only runs for `--reasoning_parser auto` (`commands/serve.py:1348`), so anyone passing `--reasoning_parser qwen3` explicitly stays broken.

**We already have a precedent for exactly this shape.** Families with a thinking toggle are handled by making the parser adaptive, never by making the selection smarter, and they fall into three tiers: structural parsing with no mode at all (`MiniMaxM3ReasoningParser` 390-434, `Gemma4ReasoningParser` 667+), mode read from `chat_template_kwargs` (`NemotronV3ReasoningParser` 557-568, `KimiK2ReasoningParser` 808-820, `DeepSeekV4ReasoningParser` 333-350), and mode read from the rendered prompt (`PoolsideV1ReasoningParser` 362-387). Qwen3 belongs in the third tier for the reason stated verbatim in the poolside docstring at 366-368: the family's templates disagree on the `enable_thinking` default. Kwargs cannot help in the failing case precisely because the toggle is undefined there.

The purely structural option is tempting but has a trap: "not thinking" and "thinking truncated by max_tokens" produce the same output shape, and Kimi K2 disambiguates them using the mode flag (844-857). So the mode is needed either way.

**On Qwen3 the existing mechanism works unchanged.** `resolve_prefilled_thinking` (93-132) rstrips the prompt tail and tests the suffix: `...<think>\n` resolves True, `...<think>\n\n</think>\n\n` resolves False. Both branches of the real template are covered, and the suffix-not-containment argument in the docstring (96-119) applies verbatim to Qwen3 multi-turn. The serving wiring is already in place: `openai_server.py:2182-2207` and the disagg relay in `postprocess_handlers.py:664-677`.

Four implementation notes:

1. You cannot put the flag on the existing `qwen3` key. `register_reasoning_parser` validates at import (51-60) that `reasoning_start`/`reasoning_end` are class attributes, and `DeepSeekR1Parser` assigns them in `__init__` (225-226). Subclassing `DeepSeekV4ReasoningParser` is the cheapest path since it declares them at 330-331.
2. For the fallback when the prompt cannot be resolved (`add_generation_prompt=false`, offline paths), I'd take `reasoning_at_start=False`, matching poolside at 384-387. That makes the fallback identical to today's `qwen3` behavior, so the change is non-regressive on every path while fixing the serving path. With that fallback you don't need to render the template at selection time at all, which avoids loading a tokenizer during CLI validation or rendering HF templates under a bare jinja2 env.
3. Don't touch the qwen3 entries in `MODEL_TYPE_TO_REASONING_PARSER` (437-442) — `resolve_auto_reasoning_parser` returns early for `_QWEN3_MODEL_TYPES` at 538-539, so they are unreachable and editing them has no effect.
4. `/v1/responses` builds its parser separately in `responses_utils.py:1237-1257` and never calls `resolve_prefilled_thinking`. Poolside left that gap too. Either close it or call it out explicitly in the PR.

For tests, please also update `test_auto_detect_qwen3_hybrid` (847-855): it currently asserts `== "qwen3"` on the very template that triggers this bug, so it is pinning the wrong behavior. Adding cases without changing that assertion won't be enough.

On the warning question from the original report: I'd rather not warn on "empty `reasoning_content` for a whole session" — a legitimately non-thinking deployment would trip it every time. But the underlying concern is right, and we already have the precise version of it in `_warn_unresolvable_thinking_once` (`openai_server.py:179-199`), which fires once at the moment the mode genuinely cannot be determined. Reusing that for Qwen3 covers the silent-failure case without the false positives.

Rebasing on #18074 if it lands first sounds right.
