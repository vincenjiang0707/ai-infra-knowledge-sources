## 正文

## Purpose

The DeepGEMM E8M0 accuracy guard added in #38083 (fixing #37804) is keyed on **model type** —
`should_auto_disable_deep_gemm()` tests `_DEEPGEMM_BLACKWELL_EXCLUDED_MODEL_TYPES`, currently
`{"qwen3_5_text", "qwen3_5_moe_text"}`.

The precision loss it guards against is a property of the **quantization path**, not of the
architecture. It occurs whenever a checkpoint's float32 block scales are requantized to UE8M0 at
load time — a *second* rounding on top of the one already baked into the checkpoint. A model is
therefore protected only once someone has measured a regression on it and added its `model_type`;
everything else is requantized silently, with no signal.

#48302 shows the failure mode in practice: a new model adding *itself* to the exclusion set, having
learned of the problem from `sgl-project/sglang#30275` rather than from vLLM.

A concrete uncovered case on hardware — Qwen3.8-Flash-Next (`model_type: qwen4_exp` /
`qwen4_exp_text`, ModelOpt `MIXED_PRECISION`: **157 `FP8_PB_WO` blockwise-FP8 layers** plus an NVFP4
MoE), DGX Spark GB10 (sm_121), vLLM `0.28.1rc1.dev524`. It is not in the exclusion set, and with
DeepGEMM enabled every blockwise linear selects the DeepGEMM kernel:

```
deep_gemm.py:136  DeepGEMM E8M0 enabled on current platform.
__init__.py:698   Selected DeepGemmFp8BlockScaledMMKernel for MergedColumnParallelLinear
__init__.py:698   Selected DeepGemmFp8BlockScaledMMKernel for QKVParallelLinear
__init__.py:698   Selected DeepGemmFp8BlockScaledMMKernel for RowParallelLinear
__init__.py:698   Selected DeepGemmFp8BlockScaledMMKernel for ParallelLMHead
```

— with nothing indicating the weights were requantized. #37804 measured **-12pp GSM8K** from this
path on Qwen3.5-FP8 across ~80 such layers; this checkpoint has 157. **I have not measured accuracy
for this model and this PR makes no claim about it.** The point is that nothing tells a user to look.

## What this changes

No policy, selection or kernel behaviour. One `logger.warning_once` at the point where the
requantization runs, in `deepgemm_post_process_fp8_weight_block`, plus a test.

## Why a warning rather than a scheme-keyed auto-disable

The precise predicate for "this checkpoint loses precision" is already available per tensor:
`ws.dtype == torch.float32 and use_e8m0`. Checkpoints shipping E8M0 scales (`float8_e8m0fnu` /
`uint8`) take the other branch, are not requantized, and lose nothing — so "DeepGEMM is enabled" on
its own is too coarse a condition to warn on.

Auto-*disabling* on that predicate would however be too broad: DeepSeek FP8 checkpoints ship float32
`weight_scale_inv` and are DeepGEMM's primary target, so it would turn DeepGEMM off for the workload
it was written for. A warning costs no throughput, cannot regress anyone, and addresses the actual
failure mode, which is silence. If maintainers want something stronger, this is the natural place to
hang a config-gated disable in a follow-up — I'm happy to write it.

## Test Plan

```
pytest tests/quantization/test_fp8.py -k ue8m0_requant_warns -q
```

`test_deepgemm_ue8m0_requant_warns_only_when_it_runs` calls
`deepgemm_post_process_fp8_weight_block` with `use_e8m0=True` under both scale formats and asserts
the warning appears **iff** the requantization actually runs:

- float32 block scales → requantized → warns
- `float8_e8m0fnu` scales → branch skipped → silent

`warning_once` dedupes through an `lru_cache`, so the test calls
`_print_warning_once.cache_clear()` first; without that the second parametrization passes vacuously.

## Test Result

Run on DGX Spark GB10 (sm_121, cc 12.1), CUDA 13.0, against a build carrying the patch:

```
$ pytest test_ue8m0_warn.py -q
..                                                                       [100%]
2 passed, 14 warnings in 3.89s
```

Both parametrizations pass, and the run emits no device-side assertions. (An earlier draft of the
test contrasted `use_e8m0=True/False` with float32 scales instead; that combination drives
non-power-of-two scales into the packed-UE8M0 layout kernel and trips
`smxx_layout.cuh:131 (values[j] & 0x807fffffu) == 0` when both cases run in one process. It is
unrelated to this change — which only adds a log line — but worth noting, as it is the same
float32-scales-on-SM12x hazard #57512 addresses.)

### jschmied · 2026-09-22

Measured what the requantization actually costs, on the checkpoint in the description
(Qwen3.8-Flash-Next, 157 `FP8_PB_WO` tensors, GB10 sm_121).

Baseline is what CUTLASS consumes — the checkpoint's FP8 weights with their float32 block scales.
DeepGEMM consumes the same weights after `requant_weight_ue8m0_inplace`. The table is the divergence
between the two *dequantized* tensors, 40 tensors sampled:

| metric | mean | min | max |
|---|---|---|---|
| relative Frobenius error | **0.02645** | 0.02575 | 0.02715 |
| `1 - cos` | 3.50e-04 | — | 3.69e-04 |

Flat across 7 layer families (`linear_attn.{in_proj_qkv,in_proj_z,out_proj}`,
`self_attn.{q,k,v,o}_proj`) and shapes from `(512, 2560)` to `(12288, 2560)`. That tightness is the
point: it is systematic to the format, not data- or shape-dependent. ~2.6% is roughly what one e4m3
rounding costs, so the requantization adds about a second full rounding on top of the one already in
the checkpoint, on every blockwise layer.

**This is weight divergence, not an accuracy measurement** — I am not claiming a task-level number
for this model. It is offered only as a size for what the warning warns about.

One aside for anyone who finds this while searching, unrelated to the change itself: on this model
enabling DeepGEMM is also **~8% slower** than the CUTLASS fallback (4 server starts, 2 per arm:
`[36.98, 37.26]` vs `[39.98, 40.41]` tok/s, disjoint), so it is not a speed-for-accuracy trade here.


### hclsys · 2026-09-23

Ran the new test on a GB10 (sm_121, CUDA 13.0) against a source build of your branch, since that's the same hardware your measurement came from:

```
tests/quantization/test_fp8.py -k deepgemm_ue8m0_requant_warns

```

Both parametrizations behave as asserted. I'd half expected the `caplog` half to be a problem, because `vllm/logger.py:67` sets `"propagate": False` and `caplog` attaches at the root — it isn't, the records land. Worth knowing since that pattern shows up in other tests.

The placement looks right to me for the reason you give: the warn sits under `if ws.dtype not in (float8_e8m0fnu, uint8)` *and* `if use_e8m0`, so checkpoints that already ship E8M0 scales skip the whole block and never warn. And `VLLM_USE_DEEP_GEMM=0` is the correct lever — it's read in `is_deep_gemm_supported()` at `deep_gemm.py:115`, so it takes out the selection, not just this path.

One interaction you may want to mention in the description, since both are in flight. I have #57512 open, which makes `deep_gemm_supports_scale_fmt()` decline DeepGEMM for `(device_capability_family(120), FLOAT32)` only. Zero file overlap with this PR, and the conditions are disjoint — yours fires when E8M0 is **on**, mine only gates when it's **off**.

But if both land, on SM12x the FLOAT32 path stops selecting DeepGEMM entirely, so the only remaining DeepGEMM linear route there is E8M0-on — which is exactly the route this warns about. Net effect on SM12x: every float32-scale checkpoint gets the warning, every run, with `VLLM_USE_DEEP_GEMM=0` as the only way to quiet it. That reads as intended to me given what #37804 cost, but it's a behaviour change worth being explicit about rather than letting a reviewer discover it.


### jschmied · 2026-09-23

Thanks for running it on a GB10. Having the test pass on the same hardware as the measurement is useful.

Agreed on the interaction with #57512. For the record, this is what happens on SM12x if both land. With the
defaults (`VLLM_USE_DEEP_GEMM=1`, `VLLM_USE_DEEP_GEMM_E8M0=1`), every float32-scale blockwise-FP8 checkpoint that is
not on the denylist takes the requantizing route. So it gets this warning once per worker process, at every start.
`VLLM_USE_DEEP_GEMM=0` is the only way to quiet it. That is the intended outcome. On this checkpoint the route
costs 2.6 % relative weight error and was 8 % slower than CUTLASS on our GB10, so a per-start warning seems proportionate.
The two PRs are independent and can land in either order.
