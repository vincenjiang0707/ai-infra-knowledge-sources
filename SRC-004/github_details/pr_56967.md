# [PR #56967] [Bugfix][KV Connector] Preserve PyTorch family during Docker dependency install

## Purpose

Fixes #56829.

The cu129 Docker image can end up with an inconsistent PyTorch package family after optional KV connector dependencies are installed, for example:

```text
torch       2.14.0+cu130
torchvision 0.28.0+cu129
torchaudio  2.11.0+cu129
```

This causes imports such as `torchvision.ops` to fail before `vllm serve` can start.

The latest `main` derives a temporary `/tmp/kv-constraints.txt` from the PyTorch family and CUDA-related packages selected in the image before installing optional KV connector dependencies. This preserves the dependency versions already present in the image while retaining the upstream CUDA-specific connector requirement selection.

The constraint is applied to:

- the normal KV connector installation path;
- the `--no-build-isolation` source-build fallback;
- the CUDA 13 Mooncake wheel replacement.

After installing the connectors, the Docker build verifies that:

- `torch`, `torchvision`, and `torchaudio` still match the versions selected during the build;
- `uv pip check --system` succeeds;
- `torch`, `torchvision`, `torchvision.ops`, `torchaudio`, and `vllm` can be imported.

A Dockerfile contract test keeps these safeguards in place.

This change does not modify the supported PyTorch/CUDA combinations or introduce a separate PyTorch pin for KV connectors. The existing build-time PyTorch package set remains the source of truth.

I checked for open PRs referencing #56829 and for PRs in the same Docker/KV connector dependency area; no competing PR was found.
