### 🐛 Describe the bug

Gemma 4 models (both `google/gemma-4-31B-it` and `google/gemma-4-26B-A4B-it`) fall into infinite repetition loops during generation. The issue occurs significantly more frequently when structured output (JSON schema / grammar constraints) is enabled, but has also been observed in unconstrained generation.

**Example output (with JSON schema):**
{"patient_information": "Patient reports a 2-week duration of a...",
"diagnosis_and_complaints": "General/Systemic-related symptoms: General/Systemic-related symptoms:
General/Systemic-related symptoms: General/System-related symptoms: General/Systemic-related symptoms:
General/System/related-related symptoms: General/Systemic-related symptoms: General/Systemic-related
symptoms: General/System-related symptoms: General/Systemic-related symptoms: ...

<img width="535" height="595" alt="Image" src="https://github.com/user-attachments/assets/389f31a3-f342-40d9-bafd-c0c8994631b7" />

The model generates a valid prefix, then enters a degenerate loop repeating a phrase with minor variations indefinitely until `max_tokens` is hit.

**Observations:**
- Occurs with both BF16 and quantized (FP8, NVFP4) weights
- Much higher frequency when grammar/JSON schema constraints are applied via xgrammar
- Not specific to tensor parallelism configuration
- Occurs on both vLLM v0.19.x and latest main
- **Not a vLLM-specific issue** — the same behavior has been reported across multiple deployment platforms (see related issues below)


### Related issues (cross-platform)

This appears to be a model-level issue affecting all serving platforms, not specific to vLLM:

- **google-deepmind/gemma#622** — Gemma 4 repetition issue (general)
- **google-deepmind/gemma#610** — Cloudflare Gemma-4-26B-A4B repetition
- **google/gemma-4-31B-it HF discussion#63** — Repetition reported on Google Vertex AI official deployment
- **vllm#39130** — Related: `--reasoning-parser gemma4` silently disables structured output when `enable_thinking=false`

### Analysis

The repetition pattern seems to be a model-level tendency that is amplified by grammar-constrained decoding. When xgrammar restricts the token space to valid JSON tokens, the model's slight repetition bias becomes a strong loop because the grammar prevents the model from generating an EOS or breaking out of the pattern.

Possible mitigations at the vLLM level:
- `repetition_penalty` / `frequency_penalty` sampling parameters partially help but do not fully prevent the issue
- The interaction between xgrammar bitmask and Gemma 4's attention pattern may deserve investigation

## Analysis & Proposed Mitigation

### What's broken?

Gemma 4 models (31B-it and 26B-A4B-it) produce infinite repetition loops when generating structured output via JSON schema. The model generates a valid prefix, then enters a degenerate loop repeating a phrase with minor variations until `max_tokens` is hit — consuming GPU resources for thousands of garbage tokens.

### Who is affected?

Any user serving Gemma 4 with `response_format=json_schema`. Other models with repetition tendencies (Gemma 3, some Llama variants) may also be affected. Unconstrained generation is less frequently impacted but not immune.

### When does it trigger?

Reproducibly when grammar-constrained decoding (xgrammar) restricts the token space. The grammar mask limits available tokens to valid JSON, and the model's logit distribution heavily favors the repeating phrase within that constrained space. Frequency increases with longer generation and complex schemas.

### Where is the bug?

This is a **model-level repetition tendency** confirmed across platforms (google-deepmind/gemma#622, google-deepmind/gemma#610, Vertex AI). At the vLLM level, the amplification happens in the sampling pipeline:

1. Grammar bitmask is applied **before** sampling penalties (`vllm/v1/worker/gpu/model_runner.py:841-848`)
2. Disallowed tokens get `-inf` logits — penalties cannot restore them
3. Inside a JSON string value, xgrammar allows thousands of tokens, but the model's distribution heavily favors the repeating phrase
4. Default `repetition_penalty=1.0` (no penalty) means nothing counteracts this bias
5. `RepetitionDetectionParams` (N-gram loop detection) exists but is **opt-in and disabled by default**

> Note: This is distinct from #39842 (BOS token fix for PT models by @lucianommartins), which addressed a different Gemma 4 repetition mode.

### Why does it happen?

The root cause is the model's repetition tendency. vLLM's grammar-constrained decoding amplifies it because:
- The grammar mask restricts the escape routes (EOS/break tokens may be masked at certain FSM states)
- The default sampling params include zero repetition mitigation
- The existing `RepetitionDetectionParams` feature is not discoverable — users don't know it exists

### How to fix it?

**Proposed mitigation**: Auto-enable `RepetitionDetectionParams` with generous thresholds when structured output is active and the user hasn't set explicit repetition detection. This follows the precedent of #38663 (defensive abort for stuck FSM requests).

Default thresholds: `max_pattern_size=20, min_pattern_size=3, min_count=4` — only triggers after ~60+ tokens of pure N-gram repetition. Legitimate JSON will not false-positive at these thresholds.

The user gets `finish_reason="repetition_detected"` instead of 2000 tokens of garbage JSON. The JSON was never going to be valid with a repetition loop — stopping early saves tokens/time/cost and gives the client a clear error signal for retry logic.

Users who want the old behavior can explicitly set `repetition_detection=None`.

### rnh0 · 2026-04-19

Adding cross-runtime evidence on the same bug. Running an identical prompt (1000-word beach-scene analysis) and identical `response_format` JSON schema with two string fields + a string array, 10 fixed seeds each:

| Runtime / config | Rep | Valid JSON | `finish_reason` |
|---|---|---|---|
| llama.cpp-server + Gemma 4 **MoE 26B** GGUF (unsloth UD-Q4_K_XL) | 0/10 | **10/10** | all `stop` |
| llama.cpp-server + Gemma 4 **Dense 31B** GGUF (unsloth UD-Q4_K_XL) | 0/10 | **10/10** | all `stop` |
| vLLM (nightly `cu130`) + Dense 31B AWQ-4bit (`cyankiwi`) + **default (`backend="auto"`)** | 0/10 word | **0/10** | all `length` — whitespace-pad loop fills `max_tokens` |
| vLLM same + **`backend="xgrammar", disable_any_whitespace=true`** | 0/10 | **9/10** | all `stop` |
| vLLM same + **`backend="outlines"`** | — | 0/10 | 7× 500 Internal Server Error, 3× `length` |
| vLLM same + **no `response_format`** (free generation) | 0/10 | N/A | all `stop` |

(Prior Ollama data for the same prompt+schema: 10/10 rep on 31B Dense GGUF, 5/10 on 26B MoE GGUF.)

Three things worth highlighting:

1. **AWQ is affected too** — not listed in the issue body, but reproducibly degenerates with the default structured-output config.

2. **Failure mode on AWQ is whitespace-loop rather than word-phrase.** Captured output for `seed=0`: valid JSON for the first ~6,400 chars, correctly closes the `analysis` string with `"`, then emits `"  \n"` (two-space-newline) ~3,450 times until the token budget runs out, never emitting `, "tags": [...] }`. Grammar permits arbitrary whitespace between JSON tokens, so the low-entropy trap is inside the grammar's allowed language.

3. **`disable_any_whitespace=true` is a working mitigation** (9/10 valid) — supports the hypothesis in the issue body that the problem is xgrammar's permissive whitespace, not the model alone. `backend=outlines` is not a workable alternative here — 7/10 seeds returned 500, the rest still degenerated.

The llama.cpp rows are notable: the exact same GGUF file (`unsloth/gemma-4-26B-A4B-it-GGUF` UD-Q4_K_XL) that fails on Ollama runs 10/10 clean under `llama.cpp:server-cuda`'s grammar path. So the bug isn't in the ggml weights or the GGUF tokenizer — it's how the structured-output constraint interacts with the model's logit distribution in a specific grammar implementation.

```
--override-generation-config '{"repetition_penalty": 1.3, "frequency_penalty": 0.3, "presence_penalty": 0.3, "temperature": 1.0}'
```

First pass tried `repetition_penalty: 1.1` matching the model's own `generation_config.json` and it was not enough. `1.3` plus the other penalties broke the loop on a tool-call stress test (8/8 unique tool args across 8 sequential requests, where without the override the same call reproduced identically every time). Some general mode collapse on simple prompts remains at this temperature but the structured-output loop is gone.

For anyone landing here trying the same thing: bumping only `repetition_penalty` is not enough. The frequency/presence pair together is what made the difference for us.
