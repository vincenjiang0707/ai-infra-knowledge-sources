# [PR #58260] [Bugfix][MLA] Fix SM90 sparse MLA IMA on >16k-row steps by chunking plan/run

state: open | updated: 2026-09-23T04:54:01Z

## 正文

## Purpose

Fixes a CUDA illegal-memory-access crash whenever a single scheduled step packs more than 16384 query rows on the SM90 sparse MLA backend (the GLM-5.3-Flash default), e.g. `--max-num-batched-tokens 32768` with a 28k-token prefill chunk, or 32k tokens scheduled across concurrent requests.

**Root cause (flashinfer 0.6.18.post1, the pinned version).** The SM90 batch-MLA plan hardcodes `max_total_num_works = 16384` and never checks it: the load-balancing schedule is `std::copy`'d into per-array regions sized for 16384 works, so a larger step silently overwrites neighboring schedule arrays, and the kernel then reads garbage `q_indptr`/`kv_indptr` (IMA in `BatchMLAPageAttentionHopper`). This backend feeds one varlen row per query token, so any step with more than 16384 scheduled tokens overflows. flashinfer 0.7.0 raised the limit to 65536 and added a hard error, but vLLM pins `flashinfer-python==0.6.18`. Small overflows (e.g. 16385 works) do not even fault — they run with a corrupted schedule.

**Fix.** When a step has more than `_MAX_PLAN_CHUNK_ROWS = 8192` query rows, plan and run the MQA as independent row chunks: the builder plans each chunk into its own `_SM90State` (a lazily grown pool), and `forward_mqa` runs each state's row range and concatenates. Each row is already an independent varlen query (causality is encoded in the top-k selection, `causal=False`), so chunking is exact. The bound is 8192 rather than 16384 so the work count stays provably under 16384 even with split-kv rows: works <= rows + total_kv_len / kv_len_limit, and `kv_len_limit` tracks total_kv_len / num_clusters. Steps at or under the limit keep the existing single-plan path unchanged, including CUDA-graph replay.

## Not a duplicate

- #56969 fixed a different OOB in this backend (mixed prefill/decode batches); it is in the tested tree and the crash still reproduces without this change.
- #55222 fixes the fp8 plan dtype and the indexer prefill workspace sizing; different call sites.
- #55626 reports a FlashInfer SM90 sparse-MLA IMA on H20 under TP+EP+MTP. Its stack is an async host sync point so it cannot be confirmed as the same bug, but a corrupted plan schedule is consistent with it.
- Searched open PRs for this backend, the plan work limit and schedule chunking; nothing else covers it.

## Testing

- Two new CPU wiring tests in `tests/v1/attention/test_flashinfer_mla_sparse_sm90.py` (chunked planning, chunked forward). The existing tests pass unchanged (`11 passed` total).
- Standalone flashinfer probe of this backend's exact plan/run call shape (rows x 1 token, kv_len=2048, heads=8, ckv=512, kpe=0, bf16) on H20: 16384 rows OK; 16385 rows runs but schedule corrupted; 20480 rows CUDA fault.
- Operator-level equivalence on H20 (real `BatchMLAPagedAttentionWrapper`, N=9000 rows, chunked 8192+808 vs single plan, per-row pseudo-random kv indices): **bit-identical outputs**, both for uniform kv_len=2048 and mixed kv_len in [512, 2176] (`max_abs_diff=0.0`). Chunking decomposes the plan/run only; per-row math is unchanged.
- Server A/B, GLM-5.3-Flash-FP8, TP=8 on 8xH20, MTP spec decode, 28201-token prompt:
  - without this fix, `--max-num-batched-tokens 16384`: OK (prefill chunks stay under the limit);
  - without this fix, `--max-num-batched-tokens 32768`: IMA in `BatchMLAPageAttentionHopper`, engine dead;
  - with this fix, `--max-num-batched-tokens 32768`: OK (28201-token prompt served in 1.71s; e2e requests pass).
  - The e2e tree is based on a Sep-17 main snapshot with the already-merged #57317 cherry-picked; upstream main has it. Note the FP8+MoE stack is not bit-stable across server restarts (greedy texts can flip between launches even on an unchanged tree), so equivalence is asserted at the operator level above, not via cross-launch text diffs.
- Upstream-main alignment (checked today): main still pins `flashinfer-python==0.6.18.post1`, and both touched files are byte-identical between main and the tested snapshot (last backend-file change is #56969 on Sep 15). The full test file, including the two new tests, passes on a checkout of today's main (`11 passed`; the engine e2e on that tree was not runnable in this image due to an unrelated `_moe_C` ABI bump in main, no nvcc available to rebuild).
- Backend-level repro on today's main tree (bypasses model loading): an unpatched-style single `plan` over N=20480 rows hits CUDA illegal address; the patched `build()` plans the same step as 3 chunks and all chunk runs complete with finite outputs.

## Notes

Each chunk state allocates its own 128 MiB workspace plus top-k index buffer, lazily on the first oversized step (~200 MiB each; two cover 32k tokens). Once the flashinfer pin moves to >= 0.7.0, the chunk limit can be revisited or removed.
