# [PR #58231] [Bugfix][Sampler] Fix split top-p masking every token for huge logits (thinking_token_budget + spec decode emits token 0)

state: open | updated: 2026-09-23T01:27:42Z

## 正文

## Purpose

This affects `thinking_token_budget` with speculative decoding (MTP, on both the V1 runner and Model Runner V2) and any `top_p < 1`, including a model's `generation_config` default. When the budget is reached, the request emits token id 0 (`<unk>` for NemotronH) until `max_tokens` instead of the forced `</think>`. Greedy requests and `top_p=1.0` are not affected.

**Root cause.** The bug is in the split-row top-p pipeline (#54651), not in the thinking-budget code. `_topp_sb_mask_kernel` in `vllm/v1/sample/ops/topk_topp_triton.py` runs on CUDA for batches of 64 rows or fewer, for rows with top-p and without an active top-k. It finds its pivot in probability space but masks in logit space:

```python
pivot_logit = tl.log(pivot) + logZ + M
keep = x > pivot_logit
```

Thinking-budget forcing writes `1e9` into the end-of-reasoning logit. The V1 `ThinkingBudgetStateHolder` and the MRV2 `_thinking_budget_kernel` both do this, so `M = 1e9`. fp32 spacing at 1e9 is 64. The term `log(pivot) + log(Z)` (about -7.7) is lost in the addition, so `pivot_logit == M`. No token passes the strict `>`, and the whole row becomes `-inf`. From there:
- In the V1 rejection sampler, `softmax` gives NaN, the draft is rejected, and `sample_recovered_tokens_kernel` falls back to `recovered_id = 0`.
- In the MRV2 verifier (`_resample_kernel`), argmax over an all `-inf` row returns index 0.

Token 0 is sampled, the budget is still exceeded, forcing runs again, and the loop never ends. Throughput also drops about 3x because every draft is rejected.

Spec decode exposes the bug because the forced verification rows go through `apply_top_k_top_p`: V1 via `apply_sampling_constraints`, MRV2 via `SamplingStates.apply_top_k_top_p`. Non-spec decoding is safe only in the default configuration, where the fused FlashInfer sampler is used. If processed-logprobs mode is on, or the FlashInfer sampler is unavailable, non-spec sampling goes through the same Triton path and hits the same bug.

The monolithic `_topk_topp_kernel` (batches over 64) is left alone on purpose. Its `max_sample` estimate (avg + 10·std of a sample block) is far below 1e9, so `sum_exp` overflows to inf and the pivot becomes NaN. Its `not (final_pivot < max_logit)` guard then disables top-p for that row. Sampling stays correct because the 1e9 logit dominates the softmax.

**Fix.** Mask with the same probability-space predicate the step kernels used to measure the mass: `exp(x - M) / Z > pivot`. This matches `pivot` and `dup` bitwise against the values the search produced. Tie handling reuses the same `prob`; it already compared in probability space for exactly this precision reason. The row max is also kept as a backstop. For ordinary logits the kept set does not change: 24 of 24 randomized rows were identical before and after under `TRITON_INTERPRET=1`.

This is not a duplicate of #54906 or #39573. Those were reported on v0.28.1 and v0.19, which predate the split pipeline (#54651, 2026-09-03), and they describe the budget being ignored rather than token-0 output. No open PR or issue covers split top-p masking with large logits. #55414 touches the same kernel, but only to precompile variants.

## Known related follow-ups (out of scope)

- The monolithic `_topk_topp_kernel` has the same logit-space round trip (`final_pivot = log(p_pivot * sum_exp) + max_*`, `duplicate_logit = ...`). Today it fails open through the guard described above, so it does not produce wrong tokens.
- Thinking-budget forcing uses a `1e9` sentinel logit. Masking every other token to `-inf` and keeping the forced logit ("mask-and-bump") would stop producing extreme values that downstream sampling ops must tolerate.
- The `nomask = pivot * Z >= 1` guard in `_topp_sb_combine` is stale: pivots are always strictly below `hi = 1/Z`.
- Duplicate matching uses inconsistent tolerances: `abs(a - b) < 1e-9` in the step/combine kernels versus exact equality in the mask kernel.

## Related issues

- Related to #54906, but a different bug. #54906 reports the budget being ignored (reasoning continues) on MRV2 only, with `top_k=20` set. Rows with an active top-k go through the monolithic `_topk_topp_kernel`, not the split top-p path fixed here, so this PR is not expected to fix #54906.
- Same symptom family as #39573 (closed), which was reported on v0.19, before the split top-p pipeline (#54651) existed.

## Test Result

- CPU kernel under `TRITON_INTERPRET=1` (vocab 131072, p=0.95):
  - Before the fix, `forced 1e9` gives `kept=0`: the whole row is `-inf`, and sampling returns token 0 via NaN.
  - After the fix, `kept=1` (the forced token), and the sampled token is 13 (`</think>`).
  - Normal rows: 24 of 24 are identical to the pre-fix kernel, and within 1 token of the PyTorch sort reference.
- End-to-end on unpatched v0.30.0 (V1 runner + MTP5):
  - `top_p=0.95`: the budget is reached, then every remaining token is `<unk>`.
  - `top_p=1.0` or `top_k=50`: `</think>` is forced at the budget and a normal answer follows.
  - Greedy: works.
- GPU pytest (1x A100-SXM4-80GB, v0.30.0 with this fix applied, `--noconftest`):
  - `pytest tests/v1/sample/test_topk_topp_sampler.py -k test_topp_keeps_forced_huge_logit -v`: 4 passed (`split` and `split-boundary`, each with `1e9` and `1e9_over_temp0.6`).
  - `pytest tests/v1/sample/test_topk_topp_sampler.py`: 135 passed, 2 skipped, 0 failed. This includes the existing Triton and FlashInfer distribution and reference tests; `scipy` is needed for the FlashInfer distribution tests.
- Patched end-to-end run (MRV2, Nemotron-3.5-Lightning-30B-A3B + MTP `num_speculative_tokens=5`, 1x A100, default sampling `top_p=0.95`):
  - Raw `/v1/completions`, `thinking_token_budget=300`, `skip_special_tokens=false`: 0 `<unk>` tokens. `</think>` is forced at the budget and a valid JSON answer follows (`finish_reason=stop`). Checked on BF16 weights and on FP8 weights.
  - Chat, `thinking_token_budget=1000`: 212 tok/s (the unpatched run collapsed to 65 tok/s), `finish_reason=stop`, valid answer.
  - Not re-run on the V1 runner with the patch applied. The fix is in the shared Triton kernel that both runners call.
