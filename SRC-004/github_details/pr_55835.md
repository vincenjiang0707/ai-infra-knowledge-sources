# [PR #55835] [Bugfix][Distributed] Keep cross-node MNNVL groups off CUDA IPC all-reduce

## 正文

## Purpose

Addresses #52778.

**Reporter-provided multi-node GPU validation is available below; same-node GPU controls and model-output evaluation remain pending.** Local validation uses CPU tests only; this PR does not claim submitter-run GPU tests.

Cross-node MNNVL-capable groups remain enabled for custom all-gather/reduce-scatter, but cannot exchange node-local CUDA IPC handles. `should_custom_ar()` currently admits TP=2 cross-node groups; CUDA-graph teardown can subsequently exchange their IPC handles and terminate the process inside `cudaIpcOpenMemHandle`.

This patch:

- declines node-local custom all-reduce when `mnnvl_only=True`, allowing the existing caller dispatch to try another backend;
- skips IPC graph registration for those groups, whose MNNVL collectives use pre-registered symmetric memory;
- preserves same-node custom all-reduce and the existing MNNVL all-gather/reduce-scatter eligibility;
- adds regression coverage in the existing custom-all-reduce test suite.

No CUDA kernels or arithmetic implementations are changed.

## Why this is not duplicate work

Before starting, #52778 had no assignee or visible work claim. Issue/timeline checks and open-PR searches for the issue number, cross-node IPC, MNNVL custom allreduce, `mnnvl_only`, and `register_graph_buffers` found no open implementation of this specific fix. The issue-number and `mnnvl_only` searches were repeated before opening this PR.

Related changes address different mechanisms:

- Merged #53253 prevents unsupported cross-node groups from reaching MNNVL rendezvous; its description explicitly distinguishes #52778. Supported Blackwell groups still reach the paths changed here.
- Open #53377 concerns FlashInfer fusion-workspace capability checks.
- Open #46515 concerns IPC-handle lifetime rather than cross-node eligibility.
- Open #50505 changes buffer sizing for batch invariance rather than node locality.

### janbernloehr · 2026-09-08

**TLDR; We have validated that this patch resolves the abort.**

### Setup

- 2 nodes, GB200 NVL72, MNNVL fabric, 1 GPU used per node, driver `580.178.04`, compute capability 10.0
- `vllm/vllm-openai:nightly` as the base, with vLLM pinned to `311b3513af33bc29b4acb2fde2e9313e5e9966a0` (reports itself as `0.27.2rc1.dev150+g311b3513a`)
- Model `nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-FP8`, served with `--quantization modelopt`, `--tensor-parallel-size 2`, max model length 4096, FP8 KV cache
- Ray-based multi-node serving, one rank per node, so **the TP=2 group spans two nodes**
- Custom all-reduce left at its default: `disable_custom_all_reduce=False`. Nothing was disabled to make the run pass.

```sh
vllm serve nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-FP8 \
  --quantization modelopt \
  --tensor-parallel-size 2 \
  --max-model-len 4096 \
  --kv-cache-dtype fp8_e4m3
```

The essential ingredient is that the two TP ranks land on **different** MNNVL-capable nodes. A same-node TP=2 run does not reproduce it.

### Unpatched behaviour

The server dies during startup inside the Ray workers. It gets through `torch.compile`, the warmup run, and

```
Profiling CUDA graph memory: PIECEWISE=83 (largest=1024), FULL=83 (largest=1024)
```

and then both ranks die with no capture progress and no `Graph capturing finished`:

```
Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:143 'invalid resource handle'
```

This matches your reading of the mechanism: `should_custom_ar()` admits the cross-node TP=2 group via the `world_size == 2` shortcut, and the CUDA-graph path then exchanges CUDA IPC handles for peers that are not on this node.

### With your patch

Same commit, same base image, patch applied as the only difference:

```
Capturing CUDA graphs (decode, FULL): 100%|██████████| 83/83
Graph capturing finished in 46 secs, took 2.10 GiB
Application startup complete.
```

Startup completes, CUDA-graph capture completes, and a four-point concurrency sweep (1 / 16 / 64 / 128) runs to completion and reports metrics. Zero occurrences of `custom_all_reduce.cuh:143` anywhere in the log, versus two in the unpatched control (one per rank).

### Controls

We pinned the exact aborting commit and ran candidate patches as sibling container layers over it, so every arm shares one base image and one vLLM wheel and the applied source patch is the only difference.

Two further data points on the same baseline:

1. Gating only the `world_size == 2` shortcut on `not self.mnnvl_only` is *also* sufficient to stop the abort. Your patch is a strict superset of that gate — it rejects `mnnvl_only` groups before that shortcut is reached, covers groups admitted via `fully_connected`, and independently guards the registration call. Both arms pass, and their throughput lands within about 4% of each other in both directions across all four concurrency levels, so there is no measurable cost to the broader gate.
2. Merged PR #53253 applied over the same aborting commit **does not fix this** — the workload aborts identically to the control. That is consistent with your "Why this is not duplicate work" section, and worth keeping in mind if anyone tries to close #52778 as already handled.

Worth stressing, because it speaks to the shape of the fix:

```
Initialized FlashInfer Allreduce norm fusion workspace with backend=mnnvl
```

appears on **both workers in both arms** — unpatched and patched alike, and in the unpatched arm it appears before the abort. Your patch leaves MNNVL allreduce setup completely untouched; it only stops the CUDA-IPC custom all-reduce from claiming a group it cannot serve. This is a correctness restoration, not a disablement.
