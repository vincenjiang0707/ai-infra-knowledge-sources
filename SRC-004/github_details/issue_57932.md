### hclsys · 2026-09-22

That rejection is correct — `--attention-backend FLASHINFER` is what's causing it.

GLM-5.3-Flash needs MLA *and* DeepSeek-style sparse attention. The check at `v1/attention/backend.py` is a strict equality on both, not a "supports at least" test:

```python
if use_mla != cls.is_mla():
    invalid_reasons.append("MLA not supported")
...
if use_sparse != cls.is_sparse():
    invalid_reasons.append("sparse not supported")
```

Plain `FLASHINFER` is neither MLA nor sparse, so both fire — which is exactly the two reasons in your error. The backend you want on SM120 is `FLASHINFER_MLA_SPARSE_SM120`, and it's selected automatically. Just drop the `--attention-backend` line:

```
vllm serve zai-org/GLM-5.3-Flash \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.95 \
  --kv-cache-dtype fp8 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":5}' \
  ...
```

Fair warning so you don't lose another cycle to it: on SM120 that is likely to move you to the next wall rather than to a running server. GLM-5.3-Flash is NoPE MLA (`qk_rope_head_dim = 0`), and the `fp8_ds_mla` cache kernel that the sparse backend uses hardcodes DeepSeek geometry, so it asserts `pe_dim must be 64 for fp8_ds_mla` during MLA warmup. That's tracked in #55773 (and #57578 is the same assert reported from GB10). If you hit it, you're in that thread, not this one.

### hclsys · 2026-09-22

Good — that's past the selection problem. The new message is a FlashInfer capability probe, not a vLLM config issue.

`has_flashinfer_sparse_mla_sm120()` (`vllm/utils/flashinfer.py`) is just three imports:

```python
from flashinfer.autotuner import autotune
from flashinfer.decode import (
    trtllm_batch_decode_sparse_mla_dsv4,
    trtllm_batch_decode_with_kv_cache_mla,
)
```

Any `ImportError` there and you get exactly the line you're seeing. So run this against the same interpreter vLLM uses and it'll tell you which piece is missing:

```
python -c "import flashinfer; print(flashinfer.__version__, flashinfer.__file__); \
from flashinfer.autotuner import autotune; \
from flashinfer.decode import trtllm_batch_decode_sparse_mla_dsv4, trtllm_batch_decode_with_kv_cache_mla; \
print('sparse MLA decode API present')"
```

`trtllm_batch_decode_sparse_mla_dsv4` is the one that's usually absent — it's newer than the rest of the sparse MLA surface.

One more gate to be aware of before you go version-hunting, because it bites after this one: right below that check there's `has_flashinfer_sparse_mla_sm120_config(num_q_heads, top_k)`, which looks your specific shape up in FlashInfer's `_DECODE_DSV4_DISPATCH` table. Its docstring is explicit that "the public sparse MLA API predates some DSV4 shapes", so having the symbol is necessary but not sufficient — the specialization for your head count and `top_k` has to be in that table too. Worth checking both at once:

```
python -c "from flashinfer.mla._sparse_mla_sm120 import _DECODE_DSV4_DISPATCH as d; print(sorted(d))"
```

That prints the `(num_q_heads, top_k)` pairs your build actually ships, which is a faster answer than trying releases one at a time. For reference, people running this path on sm120 in #46329 are on FlashInfer 0.6.15–0.6.18 built alongside the branch, rather than a stock wheel.
