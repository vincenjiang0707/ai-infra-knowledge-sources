# [PR #57586] [Perf] Use breakable CUDA graphs (no torch.compile) by default under VLLM_BATCH_INVARIANT so the tuned matmul configs see the runtime M

source: https://github.com/vllm-project/vllm/pull/57586
state: open | updated: 2026-09-23T01:00:07Z
labels: documentation, ready, torch.compile, nvidia

## 正文

## Purpose

`VLLM_BATCH_INVARIANT=1` routes every linear layer through the batch-invariant persistent Triton matmul, which picks its tile config from a per-architecture table keyed by `(N, K)` and an **M bucket** (#53247 Ada/Hopper, #53649 SM100, #57456 SM120). On the default `torch.compile` path that lookup (`_get_matmul_config`, called from `matmul_persistent`) runs while Dynamo traces the model with the compile-time dummy M, and the selected `BLOCK_M / BLOCK_N / num_warps / num_stages` are frozen in the graph. Every decode step therefore runs with the largest bucket's configs (#54243): on RTX PRO 6000 that is 3-6x slower per GEMM than the `M <= 8` configs the tables were tuned for, and it is where essentially all of the remaining batch-invariance overhead goes ([profile](https://github.com/vllm-project/vllm/issues/54243#issuecomment-5723774275)).

Without `torch.compile` the lookup executes at CUDA graph capture time with each capture size's real M, and the tables work as intended. This PR makes batch-invariant mode default to that path via the existing breakable CUDA graph mechanism (#42304, `VLLM_USE_BREAKABLE_CUDAGRAPH=1`), following the same opt-in pattern as `default_breakable_cudagraph_architectures`. It is in line with moving models off `torch.compile` (as suggested in #54503) and needs no change to the matmul or the tables.

## Changes

- `vllm/config/vllm.py`: `_maybe_enable_breakable_cudagraph` also auto-enables breakable CUDA graphs when `VLLM_BATCH_INVARIANT=1`, the platform is CUDA, the model is bf16 and unquantized, `enforce_eager` is off, sequence parallelism / async TP were not explicitly enabled (they are `torch.compile` passes), and at least one of the per-rank `(N, K)` shapes of the linear layers inside the compiled forward (qkv_proj / o_proj / gate_up_proj / down_proj, derived from `ModelConfig` + TP size; `lm_head` runs in `compute_logits()` outside the compiled graph and does not count) is a key of the device's tuned table. Only when the user did not set `VLLM_USE_BREAKABLE_CUDAGRAPH` themselves; `VLLM_USE_BREAKABLE_CUDAGRAPH=0` opts out (old behaviour). Logged once.
- `tests/test_config.py`: one parametrized config-level test (`test_batch_invariant_breakable_cudagraph`, 11 cases: on; BI off; explicit opt-out; eager; SP enabled; fp16; quantized; untuned shapes; TP=4 per-rank hit; list-valued `intermediate_size`; no table).
- `docs/features/batch_invariance.md`: one item under "Implementation Details".

No change for `VLLM_BATCH_INVARIANT=0`, ROCm/XPU, devices without a tuned table, or models whose shapes / dtype the table does not cover (those keep `torch.compile`, since `_get_matmul_config` would fall back to the default config anyway).

Kernel-level, the persistent matmul is at cuBLAS parity for decode on this path (370 ms vs 388 ms of GEMM time over 128 decode steps of Qwen3-1.7B, vs 1349 ms with the frozen bucket; same comment).
