# [PR #56926] [Perf][Engram] Serialize offloaded lookups and pack host tables into huge pages

## 正文

## Purpose

Two CPU-offloaded Engram lookups ran on separate streams and interfered with main-stream decoder work. Use one model-owned stream and a completion event per layer, so the lookups take turns instead of jointly starving decoder compute of SMs, and the first consumer waits only for its own lookup.

For private CPU-offloaded tables, `thp_packing` allocates weights and scales in one anonymous mapping that requests transparent huge pages (`MADV_HUGEPAGE`), prefaults it, and registers it with CUDA. Before prefaulting, the cached pages of the local checkpoint snapshot are released (`posix_fadvise(DONTNEED)`) so the kernel can find contiguous physical memory; after weight loading refills that cache, it is released again and one `MADV_COLLAPSE` is attempted. Huge pages are best effort: any failure falls back to ordinary Torch pinned memory or keeps the existing pages with a warning, and correctness never depends on them. Small tables, DP shared storage, the lookup kernel and the SM/2 background grid are unchanged.

Why the page-cache release and the post-load collapse are kept: measured on one GB200 NUMA node (441 GiB) with 250 GiB of small-page anonymous memory resident and the DeepSeek-V4.1-Flash checkpoint in the page cache, allocating a 25 GiB table:

| Step | Huge-page coverage |
|---|---|
| prefault, no fadvise | 12-22% |
| fadvise before prefault | 66% |
| + post-load fadvise + `MADV_COLLAPSE` | 100% |
| post-load collapse without fadvise | `ENOMEM`, unchanged |

`EngramConfig.thp_packing` defaults to `False`; set `--engram-config '{"thp_packing": true}'` to enable it. Page allocation follows the host's THP policy; the code does not change system settings.

Duplicate-work check (2026-09-15): [#56436](https://github.com/vllm-project/vllm/pull/56436) controls overlap eligibility; [#56757](https://github.com/vllm-project/vllm/pull/56757) uses file-backed tables. Neither serializes the offloaded lookups on a single model-owned stream nor implements this registered THP allocation path.

## Model evaluation

GSM8K with lm-eval 0.4.12 (all 1319 problems, five-shot chat, greedy, 1024 output tokens, seed 123) on 4xGB200, TP4, eager, checkpoint `deepseek-ai/DeepSeek-V4.1-Flash@dba1be0a`:

| `thp_packing` | Accuracy |
| --- | --- |
| OFF | 96.51% (1273/1319) |
| ON | 96.59% (1274/1319) |

The ON run had all 8 tables fully huge-page backed (192 GiB, 100% coverage, no fallback). The two-problem delta is within run-to-run noise; THP packing changes only how table memory is backed, not its contents.

## Performance

E2E average TTFT (ms, lower is better), same serving config for all three variants. A = independent lookup streams + pinned tables; B = one serialized model-owned stream + pinned tables; C = serialized stream + THP-packed tables (this PR).

| Input / concurrency | A | B | C | C vs A | C vs B |
|---|---|---|---|---|---|
| 8K / 1 | 230.88 | 237.16 | 229.53 | -0.58% | -3.22% |
| 8K / 32 | 1642.64 | 1617.62 | 1595.97 | -2.84% | -1.34% |
| 32K / 1 | 891.66 | 887.84 | 886.45 | -0.58% | -0.16% |
| 32K / 32 | 5160.91 | 5128.07 | 5104.18 | -1.10% | -0.47% |

C is fastest in every configuration; the gain grows with concurrency at 8K input (up to -2.84% vs A, -3.22% vs B at the opposite ends of the matrix).

Kernel-level comparison of the lookup itself (SM/2 background grid, one DeepSeek-V4.1-Flash TP4 shard: 96,002,653 rows x 256 fp8 + ue8m0 scales, ~24.8 GiB host table, CUPTI timing with CUDA graphs and cold L2, mean of 20 reps with rotated measurement order, THP coverage 97.4%):

| tokens / lookup | THP (us) | 4K pinned (us) | speedup |
|---:|---:|---:|---:|
| 1 | 2.68 | 2.69 | 1.00x |
| 32 | 3.28 | 3.35 | 1.02x |
| 512 | 8.56 | 11.24 | 1.31x |
| 2048 | 28.30 | 34.26 | 1.21x |
| 8192 | 102.32 | 264.58 | 2.59x |
| 32768 | 392.51 | 3947.99 | 10.06x |

THP is at parity for decode-sized lookups and increasingly faster beyond 512 tokens: the 64 KiB baseline collapses to ~13 GB/s at 32K tokens from GPU MMU TLB thrash (unstable across runs, 2.8-41x), while THP sustains ~134 GB/s of host read bandwidth. An ablation with mmap+cudaHostRegister but no huge pages matched cudaHostAlloc at every size, so the difference comes from the page size alone, not the allocation path.

AI assistance was used for implementation, testing, and this draft. Human review of every changed line and independent execution of relevant tests are required before submission.
