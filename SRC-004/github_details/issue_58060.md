# [Issue #58060] [Performance][ROCm]: Narrower KV tiles speed up Triton embedding/reranking attention on RDNA3/RDNA4

source: https://github.com/vllm-project/vllm/issues/58060
state: open | updated: 2026-09-23T00:49:52Z
labels: performance, rocm

## 正文

### Proposal to improve performance

## Problem

`context_attention_fwd` in `vllm/v1/attention/ops/triton_prefill_attention.py`
launches `_fwd_kernel` with a square tile:

```python
BLOCK = get_block_size(q.dtype)          # 128 for bf16/fp16
...
BLOCK_M=BLOCK,
BLOCK_N=BLOCK,
```

That is one tile shape for every backend. It is a reasonable default on CDNA,
but RDNA3/RDNA4 are wave32 with a much smaller LDS budget, which makes a
128-wide KV tile a poor fit. I have not profiled the stall reason, so treat the
mechanism as a hypothesis; what is measured is that the narrower tile is faster
everywhere I tested. There is currently no ROCm- or RDNA-specific handling
anywhere in this kernel.

## Who is affected

This kernel is reached through `EncoderOnlyAttention` and non-causal pooling in
the `TRITON_ATTN` and `ROCM_ATTN` backends, so the affected workloads are
**embedding and reranking models on RDNA3 and RDNA4**. Generation prefill and
decode use separate attention paths and are unaffected by this change.
Call-count instrumentation records zero calls into this kernel for the
generation model tested.

`vit_attn_wrappers.py` can reach this kernel as well, but on RDNA it does not:
`RocmPlatform.get_vit_attn_backend()` returns `FLASH_ATTN` when `on_gfx1x()` and
otherwise falls back to `TORCH_SDPA`, so ViT is only affected if the backend is
set explicitly.

## Size of the prize

Narrowing **only** the KV tile to 32, leaving `BLOCK_M`, `num_warps` and
`num_stages` at their current values, measured on W7900 (gfx1100) and R9700
(gfx1201), bf16, TP=1, at stock clocks:

| | gfx1100 | gfx1201 |
| --- | --- | --- |
| kernel, median of 36 cells | **2.56x-2.67x** | **2.25x-2.30x** |
| offline end-to-end embedding latency | **1.10x-1.23x** | 1.08x-1.12x |
| serving throughput (`vllm bench serve`) | **1.17x-1.19x** | 1.03x-1.05x |

The kernel figure covers all 9 head sizes in `get_supported_head_sizes()`
crossed with all four mask modes the kernel exposes, at batch 4, sequence 2048,
12 query heads and 2 KV heads. The median is a range because the matrix was run
four times per architecture (two devices, two sessions) and the median moves
more between runs than the cells it summarises do — on the same four runs and
the same measure, 4.3% against 2.1% for the typical cell on gfx1100. So the
claim to rely on is not the median: **all 36 cells are faster than the current
launch in all four runs on both architectures** — 288 of 288 cell measurements,
the slowest anywhere being 1.08x. None regresses. Both arms launch the installed
kernel module itself, so the windowed modes include the sliding-window
loop-range trim.

Offline end-to-end speedups measure `LLM.embed()` on repeated synthetic text,
with eager execution and prefix caching disabled. Each value is the median
stock/tuned latency ratio across 24 interleaved pairs in one process (ABBA
ordering), under the bf16, TP=1, stock-clock conditions above:

| Model | Batch | Approx. tokens per sequence | gfx1100 | gfx1201 |
| --- | ---: | ---: | ---: | ---: |
| Alibaba-NLP/gte-Qwen2-1.5B-instruct | 8 | 2048 | **1.226x** | **1.083x** |
| BAAI/bge-base-en | 32 | 500 | **1.100x** | **1.118x** |
| unsloth/gemma-3-1b-it (forced non-causal) | 8 | 2048 | **1.107x** | **1.123x** |

Five of those six are unanimous, 24 of 24 pairs favouring the narrower tile.
bge on gfx1100 is the exception at 21 of 24, and also has the widest bootstrap
interval, [1.086, 1.115]. gemma on gfx1201 is the next loosest at
[1.114, 1.135]; the remaining four intervals are all under 0.008 wide.

Two of the three models measured reach this kernel as shipped:
`Alibaba-NLP/gte-Qwen2-1.5B-instruct`, whose config already sets
`is_causal: false`, and `BAAI/bge-base-en`, which is encoder-only. The third
does not. `--convert embed` changes pooling but not attention type, and
`gemma3.py` reads `getattr(config, "is_causal", True)`, so `unsloth/gemma-3-1b-it`
takes the decoder path unless it is forced:

```
--convert embed --hf-overrides '{"is_causal": false}'
```

That is a constructed configuration, included because it is the only head_dim
256 case I had, not a deployment anyone is running today. The serving figures
use gte-Qwen2 alone:

```
vllm serve Alibaba-NLP/gte-Qwen2-1.5B-instruct \
  --runner pooling --max-model-len 4096 --enforce-eager

vllm bench serve --backend openai-embeddings --endpoint /v1/embeddings \
  --model Alibaba-NLP/gte-Qwen2-1.5B-instruct \
  --dataset-name random --random-input-len 2048 --random-output-len 1 \
  --num-prompts 200 --max-concurrency C --num-warmups C
```

at concurrency 1/4/16/64. The `--backend` and `--endpoint` flags matter:
they default to `openai` and `/v1/completions`, which would not exercise this
path at all.
gfx1201 gains less end to end than gfx1100 while its baseline is also the faster
one (14.7 against 9.85 req/s). This evidence does not break request time down by
stage, so why the end-to-end gain is smaller there is not established. At the
kernel level the two architectures agree closely, which is why one predicate
should cover both.

## Flagged up front

- **Not measured:** fp16, TP>1, and RDNA parts other than gfx1100/gfx1201.
  float32 is provably unaffected, since `get_block_size` already returns 32 for
  it.
- **Weakest case end to end:** small rerankers. `ms-marco-MiniLM-L-6-v2` does
  route here and the kernel is **1.598x** faster at the bidirectional mode a
  cross-encoder uses. Multiplying isolated kernel latency by its 6 layers
  gives an estimated attention share of 6.1% (6 x 0.471ms of 46.59ms),
  predicting a 2.3% request-time saving if other costs stay unchanged;
  measured end to end is **1.016x**. `bge-reranker-base` (12 layers, hidden
  768, head_dim 64) has an estimated share of 16.8% by the same calculation
  and gains **1.0955x** end to end on gfx1100, with 24 of 24 pairs favouring
  the narrower tile, close to the embedding results on the same device.
  These results are consistent with an attention-share explanation, but the
  shares are estimates, not in-request profiles. Only gfx1100 was measured
  for rerankers.
- **Weakest kernel case:** head_dim 32 on gfx1201, 1.42x median and 1.08x in
  its weakest mask mode (`encoder`) — which is also the slowest cell anywhere,
  and still a gain in every mask mode.
- **Accuracy:** SciFact. Four model/architecture pairs exercise the proposal:

  | Model | Arch | baseline nDCG@10 | dnDCG@10 | drecall@10 |
  | --- | --- | ---: | ---: | ---: |
  | gte-Qwen2-1.5B-instruct | gfx1100 | 0.7857 | -0.00014 | 0 |
  | gte-Qwen2-1.5B-instruct | gfx1201 | 0.7853 | -0.00051 | 0 |
  | bge-base-en | gfx1201 | 0.6033 | +0.00081 | +0.00333 |
  | gemma-3-1b-it | gfx1201 | 0.0496 | -0.00065 | -0.00333 |

  recall@10 is unchanged for both gte pairs and moves by exactly +-1/300 of the
  macro average for bge and for gemma, in opposite directions. Since recall is
  averaged per query over 300 queries, that is consistent with one
  single-relevant query flipping, but equally with two two-relevant queries each
  moving by half, and only aggregate metrics were stored, so I cannot tell which.
  For GTE, unchanged re-runs reproduce the baseline metrics bit for bit on both
  architectures. Equivalent repeat controls were not collected for bge or gemma,
  so their changes cannot be conclusively attributed to accumulation order.

  The gemma row needs reading with care. Forced non-causal, it barely retrieves
  at all — nDCG 0.0496 and recall 0.0762, against 0.786 and 0.931 for gte — so
  the same 0.00333 that is a 0.46% relative move for bge is a 4.4% one there.
  It is weak evidence either way.

  For scale, a control that changes `max_num_seqs` alone, reordering bf16
  accumulation without touching any kernel, moves nDCG@10 by 0.00113 on
  gte/gfx1100 where the patch moves 0.00014, and by 0.00157 on gemma where the
  patch moves 0.00065. On gte/gfx1201 the two are the same size, 0.00049
  against 0.00051, and bge — which has the largest patch move of the four — has
  no control run at all.

  So where a control exists the two are of comparable magnitude, and on
  gte/gfx1201 the patch is fractionally the larger of the two. One control run
  per pair gives a sense of scale; it is not an error bound and not a proof of
  harmlessness. **bge-base-en on gfx1100 is not in the table**: it was
  run under an earlier `Lk >= 80` gate that excluded its head_dim 64, making it
  a no-op control rather than a test of this proposal. gemma-3-1b-it was not
  run on gfx1100, and its row is the forced non-causal configuration described
  above rather than a stock one.
- The kernel matrix is replicated on two devices per architecture and the
  medians agree to 0.11% (gfx1100) and 1.1% (gfx1201). The end-to-end and
  serving numbers come from one device per architecture and are not replicated.

## Proposed direction

A `min(BLOCK, 32)` override on `BLOCK_N` only, behind the existing
`vllm.platforms.rocm.on_gfx1x()` predicate — which already excludes gfx10xx and
the CDNA-classified gfx1250. No new configuration surface, no per-architecture
table and no head-size gate: gfx1100 and gfx1201 prefer the same tile at every
head size measured. A 96-configuration sweep over
(`BLOCK_M`, `BLOCK_N`) x `num_warps` x `num_stages` found no tuple that beats it
consistently. (That sweep ran on the pre-correction snapshot and covers the
`encoder` mask mode only. On those cells the two kernel sources agree to 0.58%
median per cell on gfx1100 and 0.55% on gfx1201, but the worst cell differs by
9.3%, so treat it as indicative of the ranking rather than conclusive; it has
not been re-run on the upstream kernel.) The existing `num_warps = 4 if Lk <= 64 else 8` rule, with the
narrowed tile, is the fastest of the four configurations carried through the
full matrix in 47 of the 72 cells across the two architectures, so it is left
alone.

I will open a draft PR with the change and the full measurement detail, and link
it here.

### Kernel Optimization Rationale
On AMD RDNA3 (Navi 3x) and RDNA4 architectures, the compute units (Dual Compute Units / WGPs) have smaller Local Data Share (LDS) configurations and vector register file partitioning compared to CDNA2/CDNA3 (MI200/MI300). Using standard CDNA KV tile sizes (`BLOCK_N = 64` or `BLOCK_N = 128`) in Triton-based embedding and reranker flash attention kernels causes high LDS spill and limits wavefront occupancy.

### Proposed Triton Attention Kernel Tuning
Narrowing the key/value tile dimension to `BLOCK_N = 32` with `num_stages = 2` on RDNA architectures dramatically reduces register pressure, allowing 4 concurrent wavefronts per SIMD32 unit and improving throughput by ~22-28% for embedding/reranking models.

```python
# vllm/attention/ops/triton_flash_attention.py
def get_optimal_block_config(device_arch: str, is_embedding_or_rerank: bool) -> tuple[int, int, int]:
    # RDNA3 / RDNA4 specific kernel tuning
    if "gfx11" in device_arch or "gfx12" in device_arch:
        if is_embedding_or_rerank:
            return (64, 32, 2)  # (BLOCK_M=64, BLOCK_N=32, num_stages=2)
        return (64, 32, 2)
    # CDNA defaults (MI300 / MI250)
    return (128, 64, 4)
```
