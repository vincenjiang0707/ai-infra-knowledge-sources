### 🐛 Describe the bug

## Description

For a BERT-style cross encoder, `padding="max_length"` pads `input_ids` correctly but assigns every padding token the last real token's `token_type_id`. In a query/document pair that value is normally 1, so padding is incorrectly treated as part of the document segment instead of using the tokenizer's `pad_token_type_id` of 0.

BERT consumes token-type embeddings, so accepted `/score` and `/rerank` requests can run on different segment IDs from the tokenizer's intended input. This can change scores, rank order, and threshold decisions.

## Reproduction

Use the script [repro.py](https://github.com/user-attachments/files/32512913/repro_cross_encoder.py), run:

```bash
python repro.py 2>&1 | tee reproducer.log
```

The reproducer uses vLLM's released rerank request, tokenization parameters, post-tokenization logic, and worker-side token-type compression. An in-memory BERT tokenizer provides the Transformers reference result, so no model download or GPU is required. The script exits with status 1 when the bug is reproduced.

## Actual result

Both paths produce the same padded input IDs:

```text
[2, 5, 3, 6, 3, 0, 0, 0]
```

vLLM produces:

```text
token_type_ids = [0, 0, 0, 1, 1, 1, 1, 1]
```

## Expected result

Transformers uses the tokenizer's padding token type:

```text
token_type_ids = [0, 0, 0, 1, 1, 0, 0, 0]
```

Full log is here: [reproducer_cross_encoder.log](https://github.com/user-attachments/files/32512950/reproducer_cross_encoder.log).

## Root cause

`_apply_post_tokenization_to_token_type_ids()` pads with `token_type_ids[-1]` instead of `tokenizer.pad_token_type_id`. The following compression step stores only one zero-to-one boundary. That representation can encode `0*1*`, but not the correct right-padded shape `0*1*0*`, so the worker also reconstructs all padded positions as type 1.

## Related PR

[PR #47772](https://github.com/vllm-project/vllm/pull/47772) fixes a different boundary problem after truncation. It does not change max-length padding or the single-boundary representation, so this case remains reproducible in vLLM 0.29.0.
