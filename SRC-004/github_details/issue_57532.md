# [Issue #57532] [Bug]: GLM-5.3-Flash NVFP4 + MTP fails to load on main: NVFP4 weight_scale for 'parallel_lm_head' was never loaded (still NaN)

source: https://github.com/vllm-project/vllm/issues/57532
state: closed | updated: 2026-09-22T20:08:29Z
labels: quantization, glm

## 正文

### Summary

Since #52501 (merged 2026-09-13) GLM-5.3-Flash NVFP4 cannot be served with MTP on `main`.
The engine fails while loading the draft model:

```
RuntimeError: NVFP4 weight_scale for layer 'parallel_lm_head' was never loaded (still NaN).
The checkpoint likely stores this layer as BF16 (not FP4). Fix: pass quant_config=None when
constructing this layer, or add it to the quantization ignore list.
```

The layer it rejects is the MTP `shared_head.head` placeholder, which never takes part in
inference: `load_eagle_model()` replaces it with the target model's `lm_head` right after
loading. So this is a load-time false positive on a module that is discarded a moment later,
not a real precision problem.

### Environment

- 2x H200 NVL, driver R580, CUDA 13, TP2
- `vllm/vllm-openai:nightly`, digest `sha256:c4392d76e3eec8983fa152651365158cb062e348fd40398963f499d5867b9e28`, engine banner `v0.3.1.dev3+g0bfc7a15d`
- Checkpoint: `LibertAIDAI/GLM-5.3-Flash-NVFP4`

### Reproduce

```bash
vllm serve <GLM-5.3-Flash-NVFP4 checkpoint> \
  --tensor-parallel-size 2 \
  --kv-cache-dtype fp8 \
  --max-model-len 1048576 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
```

### Why it happens

1. `Glm5NextMultiTokenPredictorLayer` builds `SharedHead(config, prefix, quant_config)`, which
   creates a `ParallelLMHead` with the ModelOpt NVFP4 config. Note the prefix it is given is
   `maybe_prefix(<layer prefix>, "head")`, i.e. `model.layers.<mtp>.head`, not the HF-style
   `model.layers.<mtp>.shared_head.head` that the attribute path suggests.
2. The checkpoint's `ignore` list contains `lm_head` and nothing that matches that prefix, so
   `is_layer_excluded()` returns False and the head is built as an NVFP4 layer with a
   `weight_scale` parameter. Worth noting for the second remedy the error message suggests:
   an ignore entry cannot be spelled as the HF path for these heads, only a wildcard covering
   the whole MTP layer matches.
3. GLM-5.3 ties the MTP head to the target head. The checkpoint carries exactly one head
   tensor, `lm_head.weight` in BF16, and the MTP layer ships only
   `model.language_model.layers.45.shared_head.norm.weight`, no `shared_head.head.*` entry, so
   nothing is ever loaded into that `weight_scale`. Same in all three GLM-5.3-Flash checkpoints
   I checked: `zai-org/GLM-5.3-Flash`, `LibertAIDAI/GLM-5.3-Flash-NVFP4` and
   `amd/GLM-5.3-Flash-Quark-MXFP4`.
4. `load_eagle_model()` shares the target head with the draft and rewrites every per-layer
   copy (`del sh.head; sh.head = target_lm_head`). `has_own_lm_head` defaults to False for this
   model, so the share is unconditional and the placeholder is always discarded.
5. #52501 initializes `weight_scale` to NaN and raises in `KNvfp4Static.process()`, which runs
   inside `get_model()` during the draft load, i.e. before step 4 can replace anything.

Before #52501 the same placeholder existed with an uninitialized (`torch.empty`) scale and was
harmless because nothing ever read it. A build from 2026-09-12 main serves this checkpoint with
MTP k=3 in production here: 1,358,611 drafts, 3,207,271 of 4,075,779 draft tokens accepted
(78.7%, accept length 3.36), so the drafts go through the shared BF16 head as intended.

### Scope

The trigger is a ModelOpt NVFP4 checkpoint whose MTP head is tied to `lm_head` and is not
covered by the checkpoint's ignore list. `nvidia/DeepSeek-R1-0528-FP4` does not hit it because
its `hf_quant_config.json` excludes `model.layers.61*` wholesale, which covers that model's MTP
layer and its shared head. Models that build the same `SharedHead` placeholder and would fail
the same way on such a checkpoint: `deepseek_mtp`, `glm4_moe_mtp`, `glm4_moe_lite_mtp`,
`glm_ocr_mtp`, `step3p5_mtp`, `openpangu_mtp`, `dots3_note`, `kimi_k3`.

### Existing fix

#55442 (open since 2026-09-05) replaces the GLM placeholder with a parameter-free
`DeferredLMHead`. It was written to cut the loading peak, but since it removes the
`ParallelLMHead` entirely it also removes the layer this check rejects, so it fixes this
failure as a side effect. It currently conflicts with `main` after the glm5next file move in
#55358 and has no review yet. Landing it (or an equivalent) closes this issue; the reason for
filing is that the symptom is now a hard startup failure rather than a memory optimization.

Workarounds until then: serve without `--speculative-config`, or build from before #52501.
