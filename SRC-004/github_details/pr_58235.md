## 正文

## Purpose

Two fixes in `mimo_v2_omni.py`:

**1. ViT attention sink (`sinks_bias_key0=True` → `False`).** #49815 wired the learned vision sinks into the window-attention path. It chose the key-0 form to match the released HF `modeling_mimo_v2.py`, which adds `sinks[h]` to the logit of each sequence's first key. MiMo-V2.6's technical report (§2.2) describes *sink-augmented* SWA and cites a formulation where the sink is an extra logit that only enlarges the softmax denominator. Xiaomi's own SGLang integration runs the ViT on FA3 with `sinks=s_aux`, which is that denominator form.

The key-0 form is a no-op on uniform inputs, because every key and value is identical. So all patch tokens of a flat-colour image come out identical, and the image is misread. With MiMo-V2.6-Pro-RL, a solid green 448×448 PNG gives "a close-up of a person's eye" on current main, versus "a solid, uniform green square" from Xiaomi's hosted API. The denominator form is already supported by `context_attention_fwd` via `sinks_bias_key0=False`.

**2. `packed_modules_mapping` on `MiMoV2OmniForCausalLM`.** `SupportsQuant` sets up quantization on the omni wrapper, which declares no `packed_modules_mapping`. The inner `MiMoV2FlashForCausalLM` mapping is therefore never used when resolving `ignored_layers`. A checkpoint that dequantizes a dense MLP to BF16 and lists `gate_proj`/`up_proj` in `ignored_layers` still gets `Fp8LinearMethod` on the fused `gate_up_proj`. Its BF16 weights are then loaded without scales, and the model emits NaN on every request. Stock MiMo is unaffected, since its layer-0 MLP is FP8 and not ignored. The wrapper now carries the inner model's mapping.

## Not a duplicate

Searched open PRs and issues (`gh pr list --state open --search "mimo sink"`, `"mimo_v2_omni"`; `gh search issues "mimo sink"`). The only related open work is #57804/#57795/#57806, which route the *language-model* attention-sink bias in `mimo_v2.py` through `weight_loader` for RL weight reload. They do not touch the ViT sink semantics or the omni wrapper's `packed_modules_mapping`, and this PR does not touch `mimo_v2.py`.

## Test Plan

- `ruff check` and `ruff format --check` on the changed file: clean.
- Served MiMo-V2.6-Pro-RL (TP8) and MiMo-V2.6-Flash-RL (TP4) on the `vllm/vllm-openai:mimo-v26` image, with and without this change mounted over `mimo_v2_omni.py`. - Fix 2: served a MiMo-V2.6-Pro checkpoint with experts, `qkv_proj` and layer-0 MLP dequantized to BF16 (listed in `ignored_layers`), with and without this change; checked the load log for `Fp8LinearMethod` and requested logprobs.

## Test Results

Same weights, pixels and prompts, B300, TP8 for Pro and TP4 for Flash, `temperature=0`:

| input | main | this PR | Xiaomi API |
|---|---|---|---|
| solid green | "close-up of a person's eye" | "I see a solid, uniform green square." | "a solid, uniform green square" |
| solid white | "close-up of a person's face" | "The image is completely blank and white." | "completely blank and white" |
| left white / right black | "left: black, right: white" | "left: white, right: black" | same |
| photo, two cats on a pink couch | correct | correct, identical wording to API | — |

Also checked with no regressions and small gains: OCR ("Invoice #4827 Total: $1,309.55"), arrow direction, colour grids, and 8-colour stripes, where main drops cyan. The HF reference code reproduces main's outputs exactly with the key-0 sink, and the fixed outputs with the denominator sink.

Fix 2: a BF16-dequantized MiMo-V2.6-Pro hybrid returns NaN logits on main (`17*23` with logprobs → HTTP 400 "Out of range float values: nan"), and `DeepGemmFp8BlockScaledMMKernel` is selected despite no FP8 active weights. With this PR, no `Fp8LinearMethod` remains and it answers "391" with finite logprobs.

Related: #49815, which introduced the key-0 form.
