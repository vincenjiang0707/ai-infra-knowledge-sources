## 正文

## Summary

Cross-posting field data from a 3-day bring-up of **DeepSeek-V4.1-Flash** (769B total, MXFP4 experts, Engram memory) on **8x RTX PRO 6000 (SM120, consumer Blackwell)**, since SM120 users currently have to rediscover all of this from scratch. Related: #54929 (Triton sparse-MLA fallback — we left perf data there), #5135-tracked flashinfer instantiation gaps.

## What works (final configuration)

- vLLM `deepseekv41-flash-0909` image, TP=8, `--tokenizer-mode deepseek_v41 --tool-call-parser deepseek_v41 --reasoning-parser deepseek_v41`
- `--kv-cache-dtype fp8 --block-size 128`, `--gpu-memory-utilization 0.85`
- 1M context enabled: 950K-token double-needle retrieval **correct**, 4584 tok/s prefill throughput (pure-torch logits path, eager mode)
- VRAM: ~91GB/96GB per GPU (Engram tables dominate: 2 x ~100GB shards = 189GiB across the TP group)

## Pitfall map (in the order we hit them)

1. **DeepGEMM autotune hang on first long-context batch** — warmup deadlocks at 128K+; needs skip or eager for first bring-up.
2. **flashinfer sparse-MLA SM120 instantiation gaps** — several `(num_heads, topk)` combos (e.g. `(16, 512)`) missing from `_DECODE_DSV4_DISPATCH` / prefill dispatch (same family as flashinfer#3828). Vision path hits this too → we ran `--limit-mm-per-prompt {"image":0}` until resolved.
3. **FP8 KV-cache scale layout semantics** — the killer. Block layout is `[64tok x 128B fp8 | 64tok x 4B fp32 scale]` (block-appended), NOT per-token interleaved. Wrong interpretation passes short-prompt smoke tests and **only fails at ≥100K needle retrieval** — silent numerical corruption. Test with long needles, not perplexity.
4. **CUDA graph capture crash with flashinfer ops in graph** (>4K tokens) — resolved for us by replacing the ops with pure-torch; graphs now capture cleanly.
5. **MXFP4 expert path falls back to Marlin** on SM120 (known #30135) — works, perf hit acceptable.

## Verification methodology (cheap, catches #3)

Synthetic doc ~1M tokens with two inserted facts at 50% and 80% depth (e.g. meeting-room password + project codename/lead). Single prompt asking both. Catches numerical corruption that short-prompt tests miss. We publish numbers at 190K and 950K this way.

## Ask

- Would maintainers accept a PR adding the **pure-torch paged-MQA-logits fallback** (auto-selected on SM12x when flashinstantiation is missing)? It's ~90 lines, numerically exact, and would have saved us days. Can also serve as golden reference for #54929's Triton kernels.
- Long-needle (≥100K) test cases for SM12x CI would have caught pitfall 3 upstream.

Env: vLLM 0.1.dev20904 (deepseekv41-flash-0909), torch 2.13.0+cu130, CUDA 13.0, 8x RTX PRO 6000 96GB.

### Lei-010 · 2026-09-22

## DeepSeek-V4.1-Flash on 8× RTX PRO 6000 Blackwell (sm_120): SGLang TP8 — starts, serves, then crashes (with working config)

Following up on the excellent discussion in this thread and related issues (#56700, #56892), here is our experience running DeepSeek-V4.1-Flash on 8× RTX PRO 6000 Blackwell (96 GB each, sm_120, compute capability 12.0, NVIDIA driver 590.48.01).

### What worked (briefly)

We achieved a **successful startup** with SGLang (custom build `deepseek-v41-4x6000:local`, based on `lmsysorg/sglang:dev-dsv41` with TP=8). The server reached `"The server is fired up and ready to roll!"` and served requests briefly before crashing during runtime.

### Configuration that reached serving state

```bash
docker run --gpus all -d --name dsv41 \
  --shm-size=64g --ipc=host --network host \
  --restart unless-stopped \
  -v /ssd/DeepSeek-V4.1-Flash:/model \
  deepseek-v41-4x6000:local \
  python3 -m sglang.launch_server \
    --model-path /model \
    --tp 8 \
    --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.92 \
    --trust-remote-code
```

**Key server_args from the successful start:**

| Parameter | Value |
|-----------|-------|
| tp_size / ep_size | 8 / 8 |
| attention_backend | `dsv4` |
| kv_cache_dtype | `fp8_e4m3` |
| mem_fraction_static | 0.72 |
| max_running_requests | 8 |
| chunked_prefill_size | 2048 |
| page_size | 256 |
| c128_page_size | 16 |
| context_length | 1,048,576 |
| CUDA graph (decode) | full, max_bs=8 |
| CUDA graph (prefill) | disabled |
| speculative_algorithm | DSPARK (block_size=6, draft=same model) |
| moe_runner_backend | `flashinfer_mxfp4` |
| reasoning_parser | `deepseek-v4` |
| sampling_backend | `flashinfer` |
| mamba_backend / linear_attn_backend | `triton` |
| fp8/fp4 GEMM runner | `auto` |
| dsa_topk_backend | `sgl-kernel` |

### The failure mode

After reaching serving state, the process crashed at runtime (`Connection refused` on internal health-check port → `boot.py` timeout → container restart loop). The crash is **not** the `cache_compressor_weight` AssertionError seen during weight loading (which we also hit with an older SGLang build) — this is a **runtime serving crash**, likely related to one of the known SM120 gaps discussed above (MHC kernel, Lightning Indexer integration, or memory pressure under serving load).

### Key observations

1. **Weight loading succeeded** — all 48 shards (511 GB) loaded across 8 GPUs (mem_fraction 0.92 was briefly too high; 0.72 was used for the successful start).
2. **DSPARK speculative decoding initialized** with `dspark_block_size=6`, accepting the config without error at startup.
3. **Engram memory initialization** (the 183 GiB n-gram hash table) completed — the `Exact nvme Engram` setup ran through 14 layers × 4 TP ranks without issue.
4. The runtime crash after ~30 minutes of idle suggests either a **memory leak in serving**, a **race condition in the DSPARK path on SM120**, or a **kernel that only triggers under specific request patterns**.

### What we need to reproduce stably

- A SGLang build that resolves the runtime serving crash (we suspect the MHC or indexer path)
- Confirmation on whether `mem_fraction_static=0.72` is sufficient or if Engram CPU offload (`--engram-config '{"cpu_offload":true}'`) is required on 96 GB cards
- Whether the DSPARK speculative path is stable on sm_120 or should be disabled

### Comparison with GLM-5.3-Flash (same hardware)

For context, GLM-5.3-Flash (321B/18B MoE, NoPE MLA, FP8) runs **stably on the same hardware** with vLLM TP=8 via a community patch (`FLASHINFER_MLA_SPARSE_SM90=1` pinning): decode ~100 tok/s, prefill ~9K tok/s, 1M context needle-in-haystack all-pass. The contrast highlights that DSV4.1-Flash's architecture (Engram memory + causal encoder-decoder + DSPARK + dual-tier sparse attention) has significantly more SM120 integration surface than GLM's (KDA linear attention + NoPE MLA).
