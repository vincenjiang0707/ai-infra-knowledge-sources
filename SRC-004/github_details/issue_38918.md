# Summary

I'd like to share a compatibility finding for awareness: **Gemma4 models cannot currently run on Turing architecture GPUs (SM 7.5, e.g. RTX 2080 Ti) via any available attention backend in vLLM** by default. I understand this is likely an edge case given the age of the hardware, but wanted to document the situation in case it's useful for the project — either for improving error messaging or for considering potential kernel tuning.

## Environment

| Item | Value |
|---|---|
| **vLLM version** | `0.19.1rc1.dev4` |
| **Commit** | [`fa9e680`](https://github.com/vllm-project/vllm/commit/fa9e68022d29c5396dfbb96d13587b6bc1bdb933) |
| **GPU** | 2× NVIDIA GeForce RTX 2080 Ti (22 GB, CC 7.5, Turing) |
| **CUDA Driver** | 580.126.18, CUDA 13.0 |
| **Python** | 3.12 (Docker) |
| **Model** | Gemma4-31B AWQ 4-bit (`google/gemma-4-31b-it`), also reproduced with `cyankiwi/gemma-4-31B-it-AWQ-4bit` |

## What happens

Gemma4's `text_config` specifies `head_dim: 256` (sliding attention) and `global_head_dim: 512` (full attention). This large head dimension causes Triton-based attention kernels to require **96 KB shared memory**, but Turing GPUs have a hardware ceiling of **64 KB per SM**. Meanwhile, non-Triton backends are blocked by other constraints.

Here is the status of each backend I tested:

| Backend | Stage | Result |
|---|---|---|
| `FLASH_ATTN` | Startup (auto-excluded) | Requires SM ≥ 8.0; not available on Turing. |
| `FLASHINFER` | Startup | `Reason: ['head_size not supported']` — supports `[64, 128, 256]` only ([`flashinfer.py#L388-L390`](https://github.com/vllm-project/vllm/blob/fa9e68022d/vllm/v1/attention/backends/flashinfer.py#L388-L390)), Gemma4 full-attn layers need 512. |
| `TRITON_ATTN` | First inference | `OutOfResources: shared memory, Required: 98304, Hardware limit: 65536` — kernel at [`triton_unified_attention.py#L1124`](https://github.com/vllm-project/vllm/blob/fa9e68022d/vllm/v1/attention/ops/triton_unified_attention.py#L1124). |
| `FLEX_ATTENTION` | CUDA graph warmup | Same shared memory error via Inductor-generated Triton kernel (`triton_tem_fused_flex_attention_0`). |

## Reproduction

```bash
# With --attention-backend auto (default), TRITON_ATTN is selected;
# server starts but crashes on first request.
vllm serve /models \
  --tensor-parallel-size 2 --dtype float16 \
  --max-model-len 32768

# Explicitly trying each backend:
vllm serve /models ... --attention-backend FLASHINFER    # fails at startup
vllm serve /models ... --attention-backend TRITON_ATTN   # fails on first request
vllm serve /models ... --attention-backend FLEX_ATTENTION # fails during warmup
```

## Suggestions (non-blocking, just ideas)

1. **Better early detection**: When *all* backends are invalid for a model+GPU combination, the current behavior with `TRITON_ATTN` is to start successfully but crash on the first request. An early check correlating `head_dim` with the GPU's shared memory capacity could provide a clearer error at startup.

2. **Smaller tiles for large head_dim**: In `triton_unified_attention.py`, reducing `TILE_SIZE` (e.g., from 32 to 16) for large `head_dim` on shared-memory-constrained GPUs could potentially bring usage below 64 KB, though this may impact performance.

3. **Documentation note**: It might be helpful to note in the Gemma4 model card or vLLM docs that CC 7.5 GPUs are not supported for this model family due to the large head dimension.

> **解决步骤（必须操作，仅针对 v0.19.0 环境有效）：**
> 1. 使用 vim 等工具修改 `vllm` conda 环境下的核心文件：
>    `/root/miniconda3/envs/vllm/lib/python3.12/site-packages/vllm/v1/attention/ops/triton_unified_attention.py`
> 2. **修改 `TILE_SIZE`**（约第 875 行）：
>    将 `_get_tile_size` 函数中返回的 `32` 全局修改为 `16`：
>    ```python
>    if _is_gemma3_attention(head_size, sliding_window):
>        return 16 # 强制降级为 16
>    if is_prefill:
>        return 16 # 强制降级为 16
>    ```
> 3. **强行约束 `num_stages`**：
>    在 `kernel_unified_attention_2d` 与 `kernel_unified_attention_3d` 的启动参数末尾，追加 `num_stages=1`，打破 Triton 默认的 3 级流水线以停止超额申请双重缓冲区。
>    ```python
>    kernel_unified_attention_2d[ ... ](
>        ...
>        USE_FP8=output_scale is not None,
>        num_stages=1, # <--- 新增此行
>    )
>    ```
> 4. 修改完成后，删除编译器旧缓存以使其生效：
>    `rm -rf ~/.triton ~/.cache/vllm/torch_compile_cache

### DoradusResearch · 2026-05-19

Drive-by FYI for anyone subscribed here — just submitted [#43047](https://github.com/vllm-project/vllm/pull/43047) which adds a generic Triton autotune shmem-budget helper (`vllm/triton_utils/shmem_budget.py`) at the existing `prune_configs_by={"early_config_prune": ...}` hook layer.

It replaces per-kernel hand-rolls like the `BKV_LIST = [...] if check_shared_mem() else [...]` pattern with per-config + per-`num_stages` byte estimation against `torch.cuda.get_device_properties(device).shared_memory_per_block_optin` (T4 reports ~65 KiB, A100 ~163 KiB, SM_120 ~99 KiB, H100/H200 ~228 KiB).

The PR wires it into two reference FLA call sites (`chunk_delta_h`, `chunk_o`) — neither is the Gemma path you're hitting, but the helper is general. If the workaround you found ("simple patch... may not be optimal") is shape-equivalent (drop configs that overflow), wiring `make_shmem_pruner` into the Gemma kernel with a small estimator should give you the optimal solution without the per-bucket guesswork. ~1 import + 1 estimator function + 1 kwarg added to the kernel's existing `@triton.autotune` decorator.

Validated live on RTX PRO 6000 (SM_120) against Ling-Flash-FP8 + Qwen3-Next-80B; happy to write the Gemma-kernel estimator collaboratively if useful. Full writeup: https://doradusresearch.ai/blog/sleep-mode-on-blackwell-part-2/

### waqasm86 · 2026-09-10

Hello @lisp19 

I maintain kaggle-vllm, which targets upstream vLLM on Kaggle's 2× NVIDIA Tesla T4 GPUs (SM75):

https://github.com/kaggle-vllm/kaggle-vllm

This issue is directly relevant to the environment we validate.

In our Kaggle T4 runs, FA2 is correctly rejected on SM75 and upstream vLLM automatically selects TRITON_ATTN. For Gemma4, however, the problem here is deeper than backend selection: the large attention head sizes can make the Triton kernel exceed Turing's shared-memory budget.

The failure reported here is:

```
TRITON_ATTN
Required shared memory: 98304
Turing/T4 hardware limit: 65536
```

The Turing-safe workaround discussed in this issue also looks appropriate for a Kaggle T4 compatibility profile:

```python
from vllm.platforms import current_platform

def _get_turing_safe_tile_size(
    head_size: int,
    default_tile_size: int = 32,
) -> int:
    """
    Use a smaller Triton attention tile on pre-Ampere GPUs
    when large head dimensions would otherwise exceed the
    available shared-memory budget.
    """

    if (
        not current_platform.has_device_capability(80)
        and head_size > 128
    ):
        return 16

    return default_tile_size
```

Conceptually, the compatibility path on Kaggle T4 is:

```
Tesla T4 / SM75
     |
     +--> FLASH_ATTN: rejected (requires SM80+)
     |
     +--> TRITON_ATTN: auto-selected by upstream vLLM
                         |
                         +--> large head_dim detected
                         |
                         +--> use tile_size=16
                         |
                         +--> stay within Turing shared-memory limit
```

I would not describe this as forcing Triton from kaggle-vllm; rather, the validated Kaggle/T4 profile allows upstream vLLM to auto-select TRITON_ATTN, and the compatibility layer can apply or validate the Turing-safe kernel configuration where required.

I am planning to test this on Kaggle's full T4×2 + tensor-parallel/NCCL environment and record both the failing and patched runs. A useful validation would be:

    cc = torch.cuda.get_device_capability(i)

    )

def check_large_head_turing_risk(
    compute_capability: tuple[int, int],
    head_dim: int,
    global_head_dim: int | None = None,

        head_dim,
        global_head_dim or head_dim,

    pre_ampere = compute_capability[0] < 8

    return {
        "flash_attention_2_supported": not pre_ampere,
        "triton_large_head_shared_memory_risk":
            pre_ampere and largest_head > 128,
        "recommended_tile_size":
            16 if pre_ampere and largest_head > 128 else 32,
    }
