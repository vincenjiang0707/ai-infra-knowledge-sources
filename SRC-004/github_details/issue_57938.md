### 🐛 Describe the bug

When using `LMCacheMPConnector` with a heterogeneous attention model (e.g., Gemma 4 31B with mixed sliding-window and global attention), a KV load failure from LMCache causes a fatal `AssertionError` that kills the EngineCore process, instead of gracefully recovering. A preferred behavior in the case of a KV load failure would be to do recomputing.

## Environment

- **vLLM version:** 0.29.1
- **KV Connector:** LMCacheMPConnector
- **Model:** RedHatAI/gemma-4-31B-it-FP8-block (6 KV cache groups due to heterogeneous attention)
- **Hardware:** AMD MI325X / gfx942

## Steps to Reproduce

1. Start an LMCache server with GDS/hipFile backend
2. Start vLLM with `LMCacheMPConnector` and `kv_load_failure_policy=fail`
3. Run inference with a model that uses heterogeneous KV cache groups (e.g., Gemma 4)
4. Trigger a LMCache read error (e.g., NVMe I/O failure, hipFile error)

### chilkotiKartik · 2026-09-21

### Root Cause & Heterogeneous Attention KV Guard

#### Problem Analysis:
In heterogeneous attention architectures (e.g. models with alternating sliding-window and global attention layers, or uneven num_key_value_heads), LMCache fails during KV chunk reconstruction if chunk offsets assume homogeneous head counts across all model layers. 

When the transfer callback `_update_from_kv_xfer_finished` fires after an aborted or partial LMCache transfer, it encounters an unpopulated or misaligned KV buffer, triggering:
`AssertionError: [LMCache] Received KV transfer metadata does not match target buffer shape.`

#### Recommended Solution:

1. **Graceful Transfer State Handling**:
   In `vllm/distributed/kv_transfer/kv_connector/lmcache_connector.py`, handle heterogeneous layer dimensions explicitly when calculating per-layer stride and buffer sizes:
   ```python
   for layer_idx, layer in enumerate(model.layers):
       kv_shape = layer.self_attn.get_kv_cache_shape()
       layer_strides[layer_idx] = kv_shape
   ```

2. **Non-Fatal Fallback on Transfer Failure**:
   Instead of raising an unhandled `AssertionError` in `_update_from_kv_xfer_finished`, mark the cache lookup as a miss and fallback to normal local prompt prefill:
   ```python
   if not self._validate_kv_buffer_shape(xfer_result, target_buffer):
       logger.warning("Heterogeneous attention shape mismatch during KV transfer; falling back to local prefill.")
       self._abort_transfer(request_id)
       return False
   ```


### PranavShashidhara · 2026-09-22

I reproduced this at the scheduler level without needing LMCache or hardware. A minimal test with a mocked HMA-capable connector triggers the exact same assertion at `scheduler.py:3065` on current `main` (`assert req_id in self.requests` — same statement as the `line 3043` in the original report, just shifted by unrelated commits since).

**Root cause:** for single-KV-cache-group models, a request's `req_id` only ever shows up once in `finished_recving`/`failed_recving` signals, so the existing "delay free until transfer completes" guard in `finish_requests()` (checks `finished_recving_kv_req_ids`) works fine.

Heterogeneous-attention models (Gemma-4's 6 groups here) break that assumption — each KV cache group can report success/failure independently across different scheduler steps, but they all share the same `req_id`. Sequence that crashes:

1. Step N: one group's `finished_recving` succeeds → `req_id` added to `finished_recving_kv_req_ids`.
2. Step N+1: a different group fails → `finish_requests()` sees `req_id` already in `finished_recving_kv_req_ids`, skips the delay-free guard, deletes the request from `self.requests` immediately.
3. Same step N+1: a trailing/duplicate `finished_recving` signal for that same `req_id` arrives later in the same `update_from_output()` call → `_update_from_kv_xfer_finished` asserts the `req_id` is still in `self.requests` → crash.

I have a fix + regression test (mocked scheduler, no LMCache/hardware needed) that makes `_update_from_kv_xfer_finished` tolerant of an already-freed `req_id` (log + skip) instead of asserting, in both the `finished_recving` and `finished_sending` loops. Opening a PR shortly.
