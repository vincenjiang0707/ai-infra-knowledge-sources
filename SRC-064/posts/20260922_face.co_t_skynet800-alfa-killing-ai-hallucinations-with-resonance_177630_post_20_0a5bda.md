What “hallucination” may mean here

Factual hallucination |

Those may be useful points to foreground when describing what is specific to Code Factory.

ChatDev

**communicative dehallucination**.

That framing may be particularly close if “hallucination” here mainly includes:

Workflow versus autonomous agent pool

The current [ LangGraph workflow and agent documentation](https://docs.langchain.com/oss/python/langgraph/workflows-agents) distinguishes:

**workflows**, which follow predetermined code paths;**agents**, which dynamically choose their own processes and tools.

Code Factory could plausibly follow several routes:

| Route | Strength | Main trade-off |
|---|---|---|
| Mostly deterministic workflow | Reproducible, testable, auditable | Less flexible |
| Autonomous agent pool | Flexible for unknown tasks | Harder to constrain and trace |
| Hybrid workflow | Stable outer process with dynamic workers | More architectural work |

The sequence described in the legend—Product Owner decomposes a request, HR assigns it, Coder modifies the system, Tester verifies it, Memory Analyst compares versions—already resembles a hybrid orchestrator/worker workflow.

The system does not have to begin with maximum autonomy. A deterministic vertical slice could establish the contracts first.

Independent verification

[ Chain-of-Verification](https://aclanthology.org/2024.findings-acl.212/) comes from factual question answering rather than software development, but it illustrates a generally useful principle: verification is more valuable when the verifier does not simply repeat the assumptions of the original generator.

For a Coder/Tester pair, several modes are possible:

| Tester receives | What can be tested |
|---|---|
| Coder’s full explanation and code | Consistency with the proposed solution |
| Specification and code only | Behavior independent of the Coder’s explanation |
| Specification only | Independently generated tests |
| Code, specification, and official docs | Interface and dependency correctness |
| Executable artifact only | Black-box behavior |

These modes can be combined. The distinction matters because two agents agreeing is not automatically two independent pieces of evidence, especially when they use the same model, prompt history, memory, or source material.

Shared memory and Trust Graph

Persistent state is important. Frameworks such as [ LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) provide checkpoints and saved state for agent workflows.

However, memory storage and knowledge validity are separate problems. A shared database can preserve correct decisions, but it can also preserve an incorrect assumption and distribute it to every later agent.

A possible development path would distinguish record types:

| Record type | Example |
|---|---|
| Raw observation | Tool output, query result, test log |
| Source-backed fact | API behavior linked to official documentation |
| Agent inference | “This module probably owns calibration” |
| Approved decision | Accepted architecture choice |
| Test result | Pass/fail with environment and commit |
| Rejected path | Attempt that failed and why |
| Superseded record | Earlier information replaced by a newer version |

The Trust Graph could then include several dimensions:

- task-specific competence;
- test results;
- specification compliance;
- source and provenance quality;
- independence of evidence;
- correction and rollback behavior;
- performance by module or task class;
- validity for the current code version.

For example, an agent might be reliable for PyQt changes but unreliable for ClickHouse migrations. Task-specific trust would preserve that distinction better than a single global score.

## Why code structure matters for a future Code Factory

Agent roles create organizational boundaries, but the codebase also needs inspectable artifact boundaries.

If Architect, Coder, Tester, and Memory Analyst all receive the same large and semantically mixed context, each agent may independently have to reconstruct:

- which component owns the behavior;
- which functions and state are relevant;
- where side effects occur;
- what can be changed safely;
- which tests are sufficient;
- which version of a concept is current.

That increases more than token usage. It can also increase:

- repository-search calls;
- dependency reconstruction;
- disagreement between agents;
- unintended edit scope;
- regression scope;
- retries and review time.

Long context windows do not completely remove this problem. [ Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/) found that models may use relevant information less reliably depending on where it appears inside a long context.

Repository-level coding systems therefore often try to retrieve relevant structures instead of sending the entire repository indiscriminately. [ RepoCoder](https://arxiv.org/abs/2303.12570), for example, uses iterative retrieval and generation to bring in repository context relevant to the current code task.

The useful target is not merely “short context.” It is **task-specific context that preserves the necessary structure**.

Human readability and LLM readability

Human readability is not a perfect measure of LLM readability, but it is a useful proxy.

Both humans and current code models benefit from signals such as:

- meaningful names;
- local responsibility;
- explicit inputs and outputs;
- clear state ownership;
- stable interfaces;
- visible dependency direction;
- tests associated with the behavior they protect.

There are also differences:

- an AST or call graph may help an agent even when the source layout is not pleasant for a human;
- excessive abstraction can force both humans and retrieval systems to traverse too many files;
- comments can be harmful if they describe an older version;
- splitting code too aggressively can destroy useful local context.

So the useful principle is not:

More files are always better.


It is closer to:

Make semantic ownership, interfaces, dependencies, and tests visible; then choose file boundaries that preserve those relationships.

- a Tester scope;
- a Memory Analyst version unit;
- a Trust Graph task category.

In that sequence, the refactor is not separate from Code Factory. It establishes the structure Code Factory needs in order to operate efficiently.

A. DCM / forecasting track

A low-cost progression could be:

- one frozen worked example;
- a small prediction ledger;
- a chronological sequence of predictions;
- a simple baseline comparison;

The useful distinction is between:

- a pattern discovered while looking at the full history;
- a fixed rule applied to a separate historical period;
- a prediction saved before the future observation became available.

For repeated evaluation, [ time-series cross-validation](https://otexts.com/fpp3/tscv.html), also called rolling forecasting origin, is a standard reference. Each test prediction uses only observations available before that point.

A simple comparison does not replace DCM. It gives readers context:

- last observed value;
- persistence or random-walk forecast;
- drift forecast;
- ordinary periodic baseline;
- nearest-neighbor or analog forecast.

|---|---|

| Price | Absolute or percentage error |
| Event time | Absolute time error |
| Joint time-and-price hit | Predefined tolerance window |
| No-signal decision | Coverage and error conditional on emitting a prediction |

For example:

```
Time hit: within a predefined time window
Price hit: within a predefined percentage
Direction hit: correct sign
Joint hit: all selected conditions satisfied
```


The actual tolerances should reflect the intended use of the system.

A public prediction ledger may initially be more useful than a large benchmark. It would let later readers inspect both hits and misses without requiring prior agreement about the physical interpretation of resonance.

E. RNG / security track

The RNG branch becomes easier to evaluate when it identifies a specific threat model:

- RNG algorithm;
- implementation and version;
- entropy source;
- internal state size;
- attacker-visible outputs;
- observation count;
- recovery workload;
- success rate.

[ BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) defines how mnemonic sentences are produced from entropy and a checksum.

A concrete historical comparison is the [ Milk Sad](https://milksad.info/) vulnerability. In that case, recovery was possible because a specific wallet tool used an unsuitable generator and drastically reduced the effective search space.

That case does not establish that any RNG can be recovered by representing it as a time series. It shows how a recovery claim becomes testable once the exact implementation, entropy limitation, observations, and attacker model are specified.

This branch may therefore work best as a separate security experiment rather than as evidence for the forecasting application itself.
