## 正文

## Summary

This PR fixes pipeline parallelism support for Qwen3.8-Flash-Next, whose checkpoint is served through the Qwen4-Exp model implementation in SGLang. 

It addresses three PP-specific issues:
- Skip non-local PP layer weights before invoking Qwen4-Exp specialized PLE loaders.
- Expose `pp_proxy_tensors` in the Qwen4-Exp forward signatures.
- Pass only the flattened hyperconnection `hidden_states` across PP stages, matching the existing CUDA graph proxy tensor schema.

## Motivation

Qwen4-Exp currently fails under pipeline parallelism because remote PP layer PLE weights can be interpreted by local specialized loaders before the layer locality check. In addition, the model wrapper does not expose the PP proxy tensor argument required by the generic PP execution path.

For decode CUDA graph, Qwen4-Exp should not pass a separate `residual` tensor across PP stages because its graph schema only allocates the flattened hyperconnection hidden state.

## Performance sanity check: 
On the same 8x H20 node, `TP4/PP2/EP4` showed better high-concurrency throughput than `TP8/PP1/EP8` in our test. 
Workload: random input/output workload, concurrency 32. 
- `TP8/PP1/EP8` : 
- Request throughput: `8.79 req/s` 
- Input throughput: `3560.78 tok/s` 
- Output throughput: `281.83 tok/s` 
- Mean TTFT: `2616.95 ms` 
- Mean TPOT: `21.17 ms` 
- `TP4/PP2/EP4` : 
- Request throughput: `16.30 req/s` 
- Input throughput: `6604.12 tok/s` 
- Output throughput: `522.71 tok/s` 
- Mean TTFT: `982.98 ms` 
- Mean TPOT: `20.18 ms` 

Relative change: 
- Request/output throughput: about `+85.5%` 
- Mean TTFT: about `-62.4%` 
- Mean TPOT: about `-4.7%`

Low-concurrency note: 
- At concurrency 1, `TP4/PP2` is slower than `TP8/PP1` , which is expected due to PP bubble/communication overhead. 
- This PR is therefore positioned as a compatibility fix for the existing PP path, with high-concurrency validation showing that PP can also be useful for this model in throughput-oriented deployments.
