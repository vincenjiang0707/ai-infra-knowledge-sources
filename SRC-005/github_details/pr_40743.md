# [PR #40743] [Hisparse] fix: account for MiniMax HiSparse full-pool memory

## 正文

## Motivation

MiniMax HiSparse allocates dense KV and index caches at `size * host_to_device_ratio`, while sparse main KV stays at `size`. The memory estimator currently budgets all three at `size`, so automatic token capacity can exceed available GPU memory and fail during cache initialization. This fixes the capacity accounting introduced by #31446.

## Modifications

Apply the HiSparse ratio to dense layers and index-cache bytes when computing the MiniMax per-slot cost. Sparse main KV keeps its original cost; disabling HiSparse or using ratio 1 preserves the existing estimate.

For a 3-dense/57-sparse layout with one KV head per rank, 128-dimensional bf16 main/index caches and K-only index layers, ratio 2 changes the estimate from 45,312 to 61,440 bytes per slot.

## Validation

- All applicable pre-commit checks passed.
- Ran 648 local arithmetic/layout checks against the changed calculation, covering ratios 1/2/4, dense/sparse layer counts, KV heads, element sizes, and K-only/mixed/KV index layers. No test files added.
- Prior H200 A/B E2E on the original #31446 review head (`d0fb09af10ad36fc9b2458e6672f710bae387e9a`), with an equivalent formula fix: at `mem_fraction_static=0.80` and ratio 2, automatic capacity dropped from 2,629,667 to 1,939,380 slots. The original failed with CUDA OOM during index K allocation; the corrected budget completed startup, decode CUDA graph capture, and six HTTP generation requests (short, longer than the working set, and concurrent).
- That E2E used a small random-weight M3 fixture preserving the 60-layer KV layout, not the full pretrained model. GPU E2E has not been rerun on this main-based branch.

## Accuracy Tests

No model forward or kernel changes. The earlier E2E checked execution and output lengths, not numerical accuracy.

## Speed Tests and Profiling

Not run; the change only affects startup capacity estimation.
