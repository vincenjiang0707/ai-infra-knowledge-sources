## 正文

## Motivation

Multimodal padding runs **inside the scheduler process** while handling generation and embedding requests. Tokenizer ingress already produces native `array("q")` token buffers, but this scheduler-side padding still advertises lists and round-trips the full prompt through Python integers. In particular, `torch.as_tensor(array)` walks the sequence instead of viewing its buffer, adding per-token CPU work to the scheduler's request-handling path.

```text
Scheduler process (offset-based padding):
Before: array -> as_tensor (sequence walk) -> tolist -> array
After:  array -> bulk copy + frombuffer -> array -> ownership copy
```

Keep the model-padding boundary packed by default, with cheap assertion guardrails at representation-sensitive boundaries.

## Speed Tests and Profiling

Synthetic CPU microbenchmark of offset-based scheduler padding at **`70729c719c`** against baseline **`6e1338dd1eb1546518bdffe3b69d2ea0e011ef28`**. aarch64, Python 3.12.14, PyTorch 2.13.0+cu130, one CPU thread; median of 41 alternating trials after 5 warmups. Both sides include the scheduler's final ownership copy. Ten sparse MM spans, up to 32 tokens per span:

| Prompt tokens | Baseline (ms) | Optimized (ms) | Speedup |
| ---: | ---: | ---: | ---: |
| 4,096 | 0.6279 | 0.03021 | 20.8x |
| 16,384 | 2.3663 | 0.03552 | 66.6x |
| 131,072 | 18.8500 | 0.11690 | 161.3x |

These are offset-based padding CPU measurements, **not** end-to-end TTFT or serving-throughput improvements.

```bash
PYTHONPATH=python python benchmark/io/bench_mm_token_padding.py \
  --baseline-ref 6e1338dd1eb1546518bdffe3b69d2ea0e011ef28 \
  --tokens 128 4096 16384 131072 --items 0 1 10 \
  --threads 1 --trials 41 --warmups 5
```

The benchmark verifies token values, source immutability and a separate scheduler-owned result before timing. Add `--json` for machine-readable output. All inputs are generated; no request/trace data or benchmark-output files are added to the repository.

## Modifications

- Trust the existing packed input at the scheduler boundary. Assert eight-byte `array("q")` inputs in the shared padding helpers and each model callback's output once. No redundant wrapper input check or per-token coercion.
- Use `torch.frombuffer` on a bulk array copy for offset-based padding. Preserve modality grouping, inclusive offsets, int64 values, and the original unpadded input.
- Make token-pair padding construct arrays directly. Preserve marker scans, grouping and data offsets, including zero-length spans.
- Use `duplicate_pad_mm_input_ids` to validate model output and create a separate scheduler-owned copy, including when a model returns its input or retains the padded buffer in multimodal metadata.
- Update stale padding annotations/imports in 58 model files. All 68 model padding method bodies are unchanged.
- Let EVS consume either existing list metadata or packed model-padding metadata, while retaining its existing list-output contract.
- Add a synthetic benchmark that loads the exact baseline helper classes from a supplied local git ref.

Inputs were already arrays on normal scheduler paths; the input annotation changes reflect that existing contract. Padding outputs now remain packed too: out-of-tree `pad_input_ids` implementations must accept and return native `array("q")`. The assertions are internal guardrails and are disabled by `python -O`. The public request format and tokenizer/IPC wire format are unchanged.

## Accuracy Tests

Existing VLM E2E suites cover both padding strategies, multiple input formats and chunked prefill. Follow the PR's CI checks for GPU/E2E results.

Local pre-commit checks and all 12 offset-based benchmark cases pass: 128, 4,096, 16,384 and 131,072 tokens with 0, 1 and 10 MM items. A separate smoke run covers empty input and the text output format.

AST verification confirms all 68 model padding bodies are unchanged, all their input/output annotations are arrays, and both scheduler callbacks use the checked boundary.
