# [PR #39462] Add --padded-output-tokens to close the completion-length oracle

source: https://github.com/sgl-project/sglang/pull/39462
state: open | updated: 2026-09-23T03:23:11Z
labels: documentation

## 正文

## Motivation

Classifier-style deployments behind `/v1/completions` emit tiny, highly structured
completions — `safe`/`unsafe`, `false|...` / `true|NN|...` — whose token count
correlates with the answer. An observer who can only count tokens or SSE frames on
an otherwise encrypted stream recovers the verdict without decrypting anything.

This adds `--padded-output-tokens N`, which pads every `/v1/completions` response
out to exactly `N` output tokens on both the streaming and the non-streaming path,
by appending a run of the model's own terminal token after the real completion.
The run moves the counts, not the text: pad positions carry no text of their own,
so both paths hand back the completion the model actually generated, and a client
switching `stream` gets identical content. Using the model's EOS rather than a
configurable pad id keeps the feature to a single knob.

The flag defaults to unset, in which case responses are byte-for-byte unchanged.

**Equalized on both paths:** the emitted token count, the reported
`usage.completion_tokens`, the logprob positions, `token_ids`, and the finish
verdict — always `finish_reason: "length"` with no `matched_stop`, so a completion
that stopped on its own token is indistinguishable from one that filled the budget.
Streaming additionally equalizes the content-frame count and the terminal frame.
The single body additionally collapses `metadata.weight_versions`, whose spans are
output-token positions clamped to the real length.

**Not equalized, and documented as non-goals:** byte length — the completion's own
text is delivered verbatim, and token ids and logprobs are decimal text of varying
width — and timing. What the flag closes is every *count* a reader can take off the
response, not the size of the ciphertext.

**`N` is a hard limit on both paths.** A request whose `max_tokens` exceeds `N` is
rejected with HTTP 400 before generation starts, as are `echo=true` requests and
models exposing no `eos_token_id`. Truncating would corrupt a completion mid-answer,
and rounding the emitted length up to a multiple of `N` would only move the oracle
to a coarser scale. A budget of exactly `N` is admitted, since the emitted run is
clamped at `max_new_tokens` inclusively.

## Modifications

- `arg_groups/fields/serving.py` — new `padded_output_tokens: Optional[int] = None`
  on the `Serving` struct, deriving the `--padded-output-tokens` flag.
- `arg_groups/validation_hook.py` — `_validate_output_padding_config`, a startup
  range check wired into `check_server_args`.
- `entrypoints/openai/output_padding.py` *(new)* — `OutputPaddingPlan`, a frozen
  `msgspec.Struct` holding the pad arithmetic and logprob shaping. Pure logic, no I/O.
- `entrypoints/openai/serving_completions.py` — the budget/echo/EOS rejections in
  `_validate_request`; the pad run, per-token frame re-splitting and usage override
  in `_handle_streaming_request`; and `_padded_choice` plus the abort gate, usage
  override and metadata collapse in `_build_completion_response`.
- `entrypoints/openai/usage_processor.py` — `completion_tokens_override` on
  `calculate_response_usage`, so `total_tokens` stays consistent with the padded count.
- `docs/.../server_arguments.mdx` — flag row and a "Constant-length output padding"
  section covering both paths and the documented non-goals.

Implementation notes worth a reviewer's attention:

- The pad count comes from the tokens the response actually carries, not from
  `meta_info`'s `completion_tokens`, which mirrors the manager and can lead or lag.
  Streaming counts what it framed onto the wire; the single body counts the ids it returns.
- While padding is on, every token gets its own SSE frame, re-splitting the merged
  delta the manager produces when the consumer lags. Without that the frame count
  keeps tracking the real length even though the token count does not.
- Whether a payload carries logprobs is decided by the request-level flag, never by
  what the manager returned. Positions the manager omitted fall back to a finite
  filler; a non-finite one would serialize to `null` through pydantic, a shape no
  real position has.
- The non-streaming logprob block is built to an absolute length, never by appending
  a pad-count delta. With no top-k requested the manager supplies no top rows at all,
  so a delta would leave `top_logprobs` short by exactly the real count.
- Both paths share one overrun guard. It logs the counts and raises a number-free
  message, because the non-streaming handler returns `str(e)` to the client and a
  message naming them would hand back the length being hidden.
- Aborts are exempt on both paths. An abort is not content-correlated, and padding
  one would relabel a cancelled request as a normal length-capped completion.
