# [PR #34355] [XPU] Support decode context parallelism (DCP) on Intel XPU

## 正文

## Motivation

Decode context parallelism (DCP) shards the KV cache across TP ranks by token
position (`pos % dcp_size == dcp_rank`), so each rank attends over only its shard
and produces a partial attention output plus a softmax LSE; the partials are then
merged across ranks by log-sum-exp. This lets a group of ranks hold a context
`dcp_size` times longer than any one rank's KV pool could.

DCP already existed for CUDA. On Intel XPU nothing carried it: there was no
per-rank page table, no owner-rule-aware KV write, and no cross-rank LSE merge.
This PR implements DCP on XPU, on the `intel_xpu` attention backend.

## Review feedback addressed

Three rounds of review from @mingfeima, all addressed:

1. **"DCP on triton backend won't be useful. We prefer xpu backend over triton
   backend which is not performant on intel gpu."** — The real implementation now
   lives in `xpu_backend.py` (per-rank paged page table, masked KV write, partial
   + LSE merge). The Triton path is kept only as a portable reference leg, and the
   benchmark below quantifies why: `intel_xpu` is **2.8× faster on prefill** at the
   same DCP width.

2. **"Benchmarking with `Qwen2.5-1.5B-Instruct, batch 1, input 64, output 8` doesn't
   make any sense. Try some KPI models with at least 3500 input length."** — Replaced
   with GLM-4.1V-9B-Thinking at 4096-token input, batch 4, TP=4. A 64-token prompt
   measures model launch, not KV sharding.

3. **"Continue to develop on xpu backend. And provide reasonable benchmark
   results."** — Numbers below, plus a GSM8K accuracy gate.

## Benchmark

`GLM-4.1V-9B-Thinking`, TP=4, batch 4, input 4096, output 32,
`--mem-fraction-static 0.70`, `--disable-radix-cache`, 4× Intel Arc Pro B60.
Measured with `sglang.benchmark.one_batch`; the warm-up pass is excluded and only
the measured pass is reported.

| Attention backend | `--dcp-size` | Prefill (tok/s) | Decode (tok/s) | Decode latency (s) |
|---|---|---|---|---|
| `intel_xpu` | 1 | **8716.12** | **72.85** | 0.05491 |
| `intel_xpu` | 2 | **8508.58** | **31.77** | 0.12589 |
| `triton`    | 1 | 3164.72 | 59.50 | 0.06723 |
| `triton`    | 2 | 2954.69 | 28.21 | 0.14178 |

**`intel_xpu` vs `triton` at equal DCP width** — the result that motivates putting
DCP on this backend:

| | prefill | decode |
|---|---|---|
| dcp=1 | **2.75×** | **1.22×** |
| dcp=2 | **2.88×** | **1.13×** |

**Cost of turning DCP on** (dcp=2 ÷ dcp=1, same backend):

| | prefill | decode |
|---|---|---|
| `intel_xpu` | 0.98× | 0.44× |
| `triton`    | 0.93× | 0.47× |

Prefill is essentially unchanged; decode costs roughly 2× on both backends. That is
expected and worth stating plainly: at a *fixed* 4096-token context DCP adds a
per-step cross-rank merge and buys nothing back, because the context already fits in
one rank's pool. DCP's payoff is capacity — contexts that do not fit otherwise — not
throughput at a context that does. The decode cost being nearly identical on both
backends (0.44× vs 0.47×) indicates the toll is the collective, not this
implementation.

### DCP width scaling

A second experiment on a synthetic 16-query-head / 1-KV-head MQA model (345M — the
only shape the KV-head replication rule admits at dcp=4 on 4 GPUs), TP=4, same
request shape, **n=3, mean ± sd**:

| Attention backend | `--dcp-size` | Decode (tok/s) |
|---|---|---|
| `intel_xpu` | 1 | 469.71 ± 4.44 |
| `intel_xpu` | 2 | 249.09 ± 15.80 |
| `intel_xpu` | 4 | 255.73 ± 21.27 |
| `triton`    | 2 | 244.60 ± 0.49 |
| `triton`    | 4 | 244.66 ± 0.89 |

**Widening DCP from 2 to 4 is free** on both backends — the difference is inside
run-to-run noise. DCP's decode cost is a one-time toll for entering the sharded
regime, not a per-rank tax, which is the property that makes wide DCP worth having.

Two caveats on this table, stated rather than smoothed over:

* `triton` at dcp=1 on this model crashes with
  `RuntimeError: mat1 and mat2 shapes cannot be multiplied (1x524288 and 1024x1024)`
  (the attention output returns flattened). It is **not** a regression from this PR:
  it reproduces identically on the base commit with none of these commits applied,
  at tp=1, 2 and 4. Reported as a pre-existing upstream bug in the Triton MQA path
  rather than left as a blank cell.
* `intel_xpu` carries 10–17% run-to-run variance on a model this small (sd 4.4–21.3)
  where `triton` is very stable (sd 0.5–0.9). The dcp=4 ≥ dcp=2 ordering is noise,
  not a real speed-up.

`dcp=8` is not measured: it needs a 1-KV-head model **and** 8 GPUs, and this bench
box has 4.

## Accuracy

GSM8K on GLM-4.1V-9B-Thinking, TP=4, 200 questions, 5 shots:

| | accuracy | invalid |
|---|---|---|
| dcp=2 | 0.880 | 0.000 |
| no DCP | 0.880 | 0.000 |

DCP costs no accuracy here. The CI gate is set at 0.80 — deliberately loose, because
the failure it guards against (a broken LSE merge, or a KV write landing at the wrong
stride) collapses accuracy toward zero rather than shaving a point off it.

## Design

* **Owner rule.** Each rank stores KV only for positions where
  `pos % dcp_size == dcp_rank`. `layers/dcp/layout.py` owns the index math;
  `_set_kv_buffer_mha` writes only this rank's positions.
* **Read path.** A per-rank paged page table addresses the local shard; the
  gathered-Q decode attends the full query head set against it.
* **Merge.** Each rank's partial output is weighted by its softmax LSE and combined
  across the DCP group. On XPU the collectives run over xccl through
  `torch.distributed` (there is no pynccl); merge and index kernels are Triton.
* **Process group** comes from `get_parallel().dcp_group`, not `ParallelState` — the
  latter carries sizes and ranks only, never process groups.

## Refused at startup rather than left to fail late

Every one of these would produce *wrong output* rather than an error, so each is
rejected at argument-resolution time with a message naming the knob to change:

| Refused | Why |
|---|---|
| `intel_xpu` on a kernel build whose FMHA does not write `softmax_lse` | The merge weights partials by that LSE. Older builds accept `return_softmax_lse` and leave the buffer untouched, so the result is silently wrong. Probed via the op schema, so a new enough kernel is admitted. |
| MLA models | Triton's MLA KV write takes the combined-row `set_kv_buffer`, which has no owner-rule-aware kernel; `intel_xpu`'s MLA kernels return no LSE at all. |
| GQA with `total_num_kv_heads > tp_size / dcp_size` | Every rank of a DCP group must hold the *same* KV heads. Only `models/qwen3_5.py` shards its qkv projection that way; anything else builds fewer KV heads per rank than the pool was allocated for, and the masked KV write strides by the model's count — corrupting the cache silently. Measured on Llama-3.1-8B at tp=4/dcp=2: GSM8K 0.0, output like `apoculculculcul...`. |
| `--dcp-size` not dividing `--tp-size` | A DCP group is a subdivision of the TP group. |
| Gathered Q group > 16 query heads per KV head on `intel_xpu` | Its decode FMHA is not instantiated above 16. Reachable only by MQA shapes under DCP, since the gather is what multiplies the group size. |
| SWA, chunked local attention (iRoPE), encoder-decoder, speculative decoding, quantized KV cache, captured decode graphs | Each reaches the KV cache through indices the sharded page table no longer describes. |

`docs/docs/hardware-platforms/xpu.mdx` records what would lift each restriction.

The throughput gate is registered nightly (`nightly-xpu-4-gpu`) and skips on a runner
whose `sgl-kernel-xpu` does not emit `softmax_lse` — using the same probe the startup
guard uses, so the skip can never disagree with the rejection.

## Known limitations / follow-ups

* **No capacity measurement yet.** The index-space widening exists (allocator page is
  `page_size * attn_dcp_size`, reads translate through `widened_ids // dcp_size`), but
  `max_total_num_tokens` still reports only the physical per-rank pool and
  `one_batch`'s `max_batch_size` check has no `dcp_size` factor — so the bench harness
  cannot currently demonstrate the longer-context regime DCP exists for. This is the
  one axis DCP improves and it is not yet quantified. Left out of this PR because it
  means changing a shared cross-platform benchmark harness.
* `dcp=8` unverified — needs 8 GPUs and a 1-KV-head model.
* Varying DCP width on a real (non-synthetic) model needs a DCP-aware-qkv model
  (Qwen3.5), which needs GDN kernels `sgl-kernel-xpu` does not ship yet.
* The `triton` MQA `dcp=1` crash noted above is pre-existing upstream and not
  addressed here.
