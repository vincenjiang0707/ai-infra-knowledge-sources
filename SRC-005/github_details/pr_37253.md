## 正文

Add inference support for DeepSeek-V4-Flash-Vision-Exp.

## What

- ViT + aligner (`deepseek_v4_vit.py`) and an mm processor reproducing the reference image preprocessing and sentinel-block token layout.
- VL wrapper registered under the shared `DeepseekV4ForCausalLM` arch (MiMo-V2 style conditional vision); text-only checkpoints unaffected.
- Visible-window attention: image spans attend bidirectionally within the span during prefill (dsv4 backend, both flash_mla and sparse paths).
- MoE gate `bias_vl` routing for image tokens (hash and non-hash layers).
- Chat completions: updated vendored `encoding_dsv4` to the vision release with backward-compatible reasoning-effort profiles.

## Launch

```bash
python3 -m sglang.launch_server   --model-path deepseek-ai/DeepSeek-V4-Flash-Vision-Exp   --tp 8 --host 0.0.0.0 --port 30000 --mem-fraction-static 0.85
```

The engine auto-configures for this checkpoint: shared-experts fusion is auto-disabled with the flashinfer_mxfp4 MoE runner (HashTopK + fused scaling factor rejects fused shared experts).

Chunked prefill and radix cache both stay enabled, with span-safety handled by the scheduler:

- Chunked prefill truncation points are span-aligned (`image_span_aligned_extend_end`), so an image span is always prefilled within a single extend (the chunk budget may be overshot by at most one span, a few hundred tokens).
- A radix match ending deep inside an image span is re-issued capped to the span start (`image_span_cut_point`), fully re-prefilling the span — the span's early raw KV is not retained beyond the SWA window, so reusing it would read garbage. Shallow mid-span matches (within one window of the span start) are safe and reuse normally; the visible window then extends into the cached prefix.

## Known limitations

- A prefix match ending right at/inside a span start region hits an SWA tombstone and degrades to a full re-prefill (safe, no incorrect reuse). Retaining an extra SWA window around cached span starts is a possible follow-up.
- HIP/unified-KV falls back to causal windows inside image spans (the 128-slot SWA ring cannot hold a widened window).
- MTP/DSpark speculative decoding with image batches is unverified.

### jmeadlock · 2026-09-04

Thanks for the Vision-Exp work — we have been exercising this stack on a single DGX Station GB300 (TP=1, DSpark, 1M context) and found a reproducible tool-history regression in the preview artifact.

**Affected artifact / source**

- Preview image: `lmsysorg/sglang@sha256:7ac467a50508b7029a23e846c150998fdd26d95c1cfd377ea7e74e28374486a6`
- Current PR head checked: `1ca94a0c10ba7fb1bc20421acbe04d1f9ee30403`
- File: `python/sglang/srt/entrypoints/openai/encoding_dsv4.py`

`serving_chat.py` normalizes replayed OpenAI `assistant.tool_calls[].function.arguments` from a JSON string to a dict (the behavior added by #28035). The vendored Vision encoder still unconditionally calls `json.loads(tool_call["arguments"])`. Given a dict, that raises `TypeError`, falls through to:

```python
arguments = {"arguments": tool_call["arguments"]}
```

The prior call is therefore rendered as one DSML parameter named `arguments`. On subsequent tool turns the model imitates that representation, producing progressively deeper `{"arguments": {...}}` nesting. First-turn tool smokes pass; replayed agent sessions begin degrading after roughly two tool turns.

SGLang `main` already has the correct dict-aware implementation in `encoding_dsv4.py`, so this appears to be branch/image skew rather than a new design change. Could that implementation be carried into this PR and the preview image when it is rebuilt?

Reproducer, patch, and receipts:

- Fix commit: https://github.com/jmeadlock/dsf-vision-exp-gb300/commit/08b5d30
- Minimal replay reproducer: https://github.com/jmeadlock/dsf-vision-exp-gb300/blob/main/patches/toolcall_replay_repro.py
- Exact patch: https://github.com/jmeadlock/dsf-vision-exp-gb300/blob/main/patches/encoding_dsv4.diff

A one-file bind-mounted correction passed the minimal replay and an 8-hop Hermes tool-use replay, while retaining the full vision/tool-call smoke results.

### rwang5203 · 2026-09-01 · CHANGES_REQUESTED

## Top-level HiCache blocker

I reproduced this on the exact checkpoint with TP8, `--enable-hierarchical-cache`, `--hicache-ratio 4`, and `--hicache-write-policy write_through`. Every rank attached HiCache, but `/health` stayed at 503 with the default overlap scheduler and with `--disable-overlap-schedule`. Stack sampling split ranks between the HiCache count all-reduce and request broadcast, so neither launch reached a serving state.

This advertised composition needs either a serving path that reaches a healthy state or an explicit startup rejection with a clear compatibility error.

## Top-level PD rebootstrap blocker

In the true-rebootstrap reproducer, `Req.build_rebootstrap_payload` returned token IDs and request settings with no multimodal key. `Req.reset_for_retract` and a fresh `PREBUILT` control both retained the same image object and offsets. `pause_generation` can send unfinished multimodal decode requests through the token-only path, so resumed prefill can silently rebuild KV without the image.

One way to close this gap is to carry the original multimodal payload through rebootstrap. If that path cannot support images yet, rejecting those requests before rebootstrap would avoid silently dropping the data.

## Top-level DP attention blocker

With DP8 and TBO disabled, 16 identical image requests returned 200 but formed six token signatures, while 16 identical text requests formed four. Every response differed from the normal TP8 baseline. Enabling TBO produced ten image signatures across 16 requests, so TBO is not the source of the no-TBO corruption.
