## 正文

## Motivation

This PR fixes two correctness issues in the PD prefill early-send path.

`SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX` defaults to `True`, so both issues affect the default PD path rather than an opt-in configuration.

### 1. CUDA-specific event creation crashes the prefill scheduler on non-CUDA devices

`maybe_send_cached_prefix_chunk` creates the early-send wait event using `torch.cuda.Event()`. On builds without CUDA support, this raises:

```text
Tried to instantiate dummy base class Event
```

As a result, the prefill scheduler can crash when a request reuses a cached prefix under overlap scheduling.

This was reproduced on Intel XPU with PD (NIXL transfer) and hierarchical cache: when the second request in a group reuses the shared prefix, the scheduler hits the CUDA-only event creation.

### 2. NIXL and Mooncake did not propagate the early-send wait event

The scheduler records a completion event on `forward_stream` and passes it to the sender so the transfer worker waits for the preceding prefill writes before reading the cached prefix pages.

Mori already consumed this event, but NIXL and Mooncake `add_transfer_request` did not accept or propagate `wait_event`. The event was therefore effectively dropped for those backends.

Without the wait, the transfer worker can read the prefix pages before the preceding forward has completed writing them. The transfer can still report success because the data movement itself succeeds, while the transferred KV may contain stale or partially written data. Transfer failure counters and performance benchmarks would not necessarily detect this; an output-correctness check is needed to expose the issue.

### Why the fixes are kept together

The two fixes intentionally ship together.

Fixing only the first issue makes the early-send path usable on XPU while leaving the missing synchronization in NIXL/Mooncake. That would replace an immediate scheduler failure with a potential correctness issue.

The fixes are kept as separate commits so they can be independently reverted, backported, and bisected.

## Modifications

### `75c7cb3f13` — Use the scheduler device for the PD early-send event

* `prefill.py`: replace `torch.cuda.Event()` with `self.device_module.Event()`.
* `self.device_module` is initialized from `self.device` during `Scheduler.init_overlap()` and is also used to construct `forward_stream`. This ensures the event and stream use the same accelerator.
* Using `torch.get_device_module()` without an explicit device could select the process-default accelerator rather than the scheduler device.
* Add a CPU unit test covering event creation through the scheduler's device module.

### `68a6dfed75` — Propagate the early-send event through NIXL and Mooncake

* `nixl/conn.py` and `mooncake/conn.py`: add `wait_event` to `add_transfer_request` and propagate it to the queued `TransferKVChunk`.
* The sender obtains the event through `_take_early_send_wait_event()`.
* The transfer worker synchronizes the event before reading/staging the KV pages.
* The parameter is trailing and has a default value, so existing call sites retain their current behavior.
* The Ascend backend inherits the common sender/event propagation change through its existing subclassing.

### Ordering requirement

The event must be synchronized **before** `gather_all_layers_to_staging()`, not only before posting the RDMA operation.

`gather_all_layers_to_staging()` synchronizes its own gather stream, which provides ordering between the gather and the subsequent transfer. It does not, however, establish ordering between the gather and the previous forward's writes.

Therefore, waiting only before the RDMA post would still allow the staging gather to read KV pages before the preceding forward has finished writing them.

The worker-side wait is intentionally blocking rather than deferring the chunk back onto the queue. Deferring would require additional bounded waiting/polling to avoid repeatedly retrying the same chunk. The trade-off is that the worker thread can be blocked while the covered forward is still running. This preserves the required ordering while retaining the purpose of early-send: the transfer can begin as soon as the required pages are ready rather than waiting for the entire current forward step.

### Common sender cleanup

* `common/conn.py`: declare `_early_send_wait_event` in `CommonKVSender`.
* Consume it through `_take_early_send_wait_event()` instead of using `getattr()` on backend subclasses.
* The accessor is one-shot so a later chunk cannot consume a stale event.
* `mori/conn.py` switches to the shared accessor.
* `common/utils.py` removes the Mori-specific wording from the `TransferKVChunk.wait_event` comment.

## Unit tests

Eight CPU tests cover event creation, event propagation, one-shot consumption, and worker ordering. They run in `register_cpu_ci` using stubs/mocks, so no accelerator is required.

* `test_taking_the_early_send_wait_event_clears_it`

### Mooncake

* `test_worker_synchronizes_the_early_send_event_before_the_staging_gather`
* `test_worker_waits_on_the_early_send_event_with_staging_disabled`
* `test_add_transfer_request_forwards_the_wait_event_to_the_queued_chunk`

### Scheduler

`test/registered/unit/disaggregation/test_prefill_abort_result_cleanup.py`

* `test_early_send_wait_event_comes_from_the_scheduler_device_module`

This test injects a stub device module and verifies that the scheduler creates the event through that module rather than through `torch.cuda`.

All eight tests fail against the pre-fix implementation.

The worker tests verify ordering by stubbing the downstream read and checking the recorded operation order. Each test bounds the worker queue with `side_effect=[chunk, SystemExit()]`, so an implementation that stops matching the expected sequence terminates the worker instead of re-dequeuing indefinitely. `SystemExit` is used rather than `AssertionError` because the NIXL worker loop catches `Exception` and would otherwise swallow the assertion.
