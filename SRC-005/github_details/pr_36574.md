# MiniMax-M3: MXFP8 dense-only block convert + `torch._scaled_mm` Blockwise-1x32 path

Branch: `m3/mxfp8-dense-block-convert` · base: `main` · **base of the stack** (`m3/fused-norm-fp8-quant` sits on top of this)

MXFP8 checkpoints on gfx950 currently have two all-or-nothing options: keep every
weight on the native MX per-1x32 `dot_scaled` path, or convert every weight to
block-fp8 `[128, 128]` at load (`SGLANG_FORCE_MXFP8_BLOCK_CONVERT`) and run the
mature aiter block-scale kernels. Neither works for MiniMax-M3: the dense linears
want the block-scale kernels, but converting the fused-MoE weights too routes the
MoE to a block-scale kernel that has no SwiGLU-OAI activation. This PR adds a
dense-only conversion mode (`SGLANG_FORCE_MXFP8_BLOCK_CONVERT_DENSE`, default
off) so dense linears convert while fused-MoE weights stay on the native MX path.
Around it: MXFP8 dense dispatch gains a `torch._scaled_mm` Blockwise-1x32 route
behind a runtime availability probe, with the existing Triton `dot_scaled` kernel
as the fallback; a new `--fp8-gemm-backend bf16` choice dequantises MXFP8 weights
once and uses BF16 `F.linear` (gfx950 only, for A/B and for shapes with no
kernel); converted dense weights additionally cache a rowwise-fp8 (per-token x
per-channel) copy that `aiter_w8a8_block_fp8_linear` uses at or below
`MXFP8_DENSE_PTPC_DECODE_MAX_M = 128` tokens, where the ptpc GEMM beats the
block-fp8 GEMMs; and `dispatch_w8a8_mxfp8_linear` now handles every
`Mxfp8DenseGemmBackend` member explicitly instead of falling through to the ROCm
import for anything unrecognised.

Two behavioural notes a reviewer should have up front:

- **CUDA is unaffected.** Every new code path is gated on `_is_hip` /
  `_is_gfx95_supported` / `is_aiter()`, or on a new env var and a new
  `--fp8-gemm-backend` choice that both default off. The
  `dispatch_w8a8_mxfp8_linear` restructure is behaviour-identical: the enum has
  six members and all six are now matched explicitly.
- **The gfx950 `auto` default does move.** `_use_scaled_mm_mxfp8_gemm()` returns
  true for `auto` when the `torch._scaled_mm` Blockwise-1x32 probe succeeds, so on
  a build that supports it, `--fp8-gemm-backend auto` on gfx950 switches from the
  Triton `dot_scaled` kernel to `torch._scaled_mm`. `--fp8-gemm-backend aiter`
  raises rather than silently falling back if the probe fails, so the selection is
  never silent.

## Accuracy — this FAILS the gate I set, and I am filing it anyway with the number stated

gsm8k, 512 examples, `max_tokens 2048`, `temperature 0`, `seed 0`:

| | score | stop_rate | truncated_rate | error_rate |
|---|---|---|---|---|
| `upstream/main` | 97.07% | 98.44% | 1.56% | 0.00% |
| this PR | **95.90%** | 97.46% | **2.54%** | 0.00% |

**-1.17 pp.** My own bar was "no more than 1.0 pp below baseline", so by that rule this does not pass. It is filed because the throughput is the largest in this series (+13.7%..+27.0% output at low batch) and because the failure has a specific, checkable shape rather than being diffuse.

**The shape suggests truncation, not wrong reasoning.** `truncated_rate` rises 1.56% -> 2.54%, i.e. ~5 more of 512 completions hit the 2048-token cap, and the score falls by ~6 questions. Tiny numerical differences compounding through greedy decoding into longer generations would produce exactly this. I did **not** confirm it: a re-gate at a larger budget was cancelled, so this remains a hypothesis, not a finding.

**Caveat on the measurement itself.** This gate is a single run, and the eval is less deterministic than temperature 0 suggests -- SGLang batches dynamically, so accumulation order and therefore greedy token choices vary between runs. A different PR in this series read 96.88 / 96.68 / 96.29 across three runs of the same tree, a 0.59 pp spread. Against that, a -1.17 pp single-run delta is roughly two spreads and should not be treated as precisely located.

What I would want before merging: three gate runs reported as a range, and a run at `max_tokens 4096` on both sides to settle the truncation question.

## Behaviour change worth flagging

This is a strict no-op on CUDA -- both `fp8.py` MoE hunks sit behind `_is_hip and is_aiter()` or an early return, and the `dispatch_w8a8_mxfp8_linear` restructure is enum-exhaustive. But it **does move the gfx950 `auto` default** from the Triton `dot_scaled` path to `torch._scaled_mm`, so gfx950 users get a different kernel without asking for one.
## Reproduction

Server (identical on both sides):

```bash
SGLANG_USE_AITER=1 \
AITER_CONFIG_FMOE=/path/to/minimax_m3_mxfp8_tuned_fmoe.csv \
SGLANG_FORCE_MXFP8_BLOCK_CONVERT_DENSE=1 \
python3 -m sglang.launch_server \
  --model-path /path/to/MiniMax-M3-MXFP8 \
  --trust-remote-code --tp 8 --quantization mxfp8 \
  --moe-runner-backend aiter --fp8-gemm-backend auto \
  --enable-aiter-allreduce-fusion --attention-backend triton \
  --dtype bfloat16 --chunked-prefill-size 8192 --mem-fraction-static 0.80 \
  --host 0.0.0.0 --port 30000
```

Benchmark:

```bash
python3 -m sglang.benchmark.one_batch_server \
  --model None --base-url http://127.0.0.1:30000 \
  --output-len 600 --skip-warmup \
  --batch-size 1 2 4 8 16 32 \
  --input-len 80000 --show-report --cache-hit-rate 0.9
```

Accuracy gate:

```bash
sgl-eval run gsm8k --base-url http://127.0.0.1:30000/v1 \
  --num-examples 512 --num-threads 64 \
  --max-tokens 2048 --temperature 0 --seed 0
```

Two bench reps per boot, warm rep reported; noise floor +/-0.4%, established by a separate PR measuring flat under a config where its code cannot fire.
