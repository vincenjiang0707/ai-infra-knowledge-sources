# [PR #40508] [DSV4.1] Enable Engram WKV projection sharding for TP4/TP8

state: open | updated: 2026-09-23T04:03:33Z

## 正文

## Motivation

DeepSeek-V4.1 uses ReplicatedLinear for the Engram WKV projection. When token inputs are replicated across TP ranks, every rank stores the full projection weights and repeats the same computation during prefill and decode.

This PR partitions the projection's output dimension across TP4/TP8 ranks and gathers the projected activations before the existing Engram gate. This reduces per-rank projection weight storage and redundant computation while preserving the gate's full input layout. The optimization is enabled automatically for supported configurations in both PD-disaggregated and standalone serving, with ReplicatedLinear retained as the fallback.

## Modifications

- Automatically shard Engram WKV projections with ColumnParallelLinear and gather_output=True for TP4/TP8 with replicated token inputs.
- Support prefill and decode workers in PD deployments, plus standalone non-PD serving (disaggregation_mode="null"). No dedicated environment variable is required.
- Retain ReplicatedLinear for unsupported deployment roles, other TP sizes, DP attention, context parallelism, LayerNorm sequence parallelism, and scattered attention inputs.
- Fall back to ReplicatedLinear when output partitions do not align with weight quantization blocks. Reuse the existing linear weight loaders and leave Engram lookup and gating unchanged.
- Add unit coverage for full-weight reconstruction from rank-local slices for TP4 and TP8 in prefill, decode, and standalone modes, topology fallback, and partition alignment.

## Accuracy Tests

### TP4 prefill correctness

In a cross-node PD deployment on H20-3e GPUs, projection sharding was enabled only on prefill. All 72 paired synthetic benchmark outputs matched exactly. Both deployments passed 24 additional arithmetic, retrieval, and JSON correctness samples; two paired responses differed only in JSON whitespace and matched after parsing.

### TP8 decode validation

All 2,160 requests in the decode sharding comparison completed successfully. Generated outputs differed between sharding-on and sharding-off runs, and also between repeated sharding-on runs. These runs confirm request completion but do not establish accuracy equivalence; no logits-level comparison was performed.

These checks and the performance measurements below used earlier development builds. GPU validation of the current PR revision, TP4 decode and standalone serving validation, and broader model accuracy evaluation remain pending.

## Speed Tests and Profiling

### TP8 performance

Prefill and decode were measured with different workloads and cache settings. The decode experiment measures the incremental effect of enabling decode sharding while prefill sharding remains enabled. Results from the two experiments are not directly comparable and their gains cannot be added.

#### Prefill sharding

Cross-node 1P1D, 8×H20-3e GPUs per side, TP8/EP8, approximately 68K input tokens per request, and approximately 90% mean request-level prefix-cache hit rate. The table compares measurements before and after enabling prefill projection sharding. Input throughput counts uncached tokens only.

| Request rate | Input throughput change | Mean TTFT change |
|---|---:|---:|
| 40 RPM | Essentially unchanged | 18.1% lower |
| 50 RPM | 4.4% lower | 16.2% lower |
| 60 RPM | 8.4% higher | 3.2% higher |

#### Additional decode sharding

Cross-node 1P1D, 8×H20-3e GPUs per side, TP8/EP8, with DSpark and CUDA Graph enabled. HiCache and radix caching were disabled. Each request used approximately 43–51 input tokens and 512 output tokens. Prefill sharding remained enabled in both configurations; only decode sharding was toggled.

| Request rate | Output throughput change |
|---|---:|
| 60 RPM | 0.25% lower |
| 120 RPM | 1.40% higher |
| 180 RPM, two-run average | 1.81% higher |

Requests were launched for 120 seconds at each rate, then allowed to drain. Output throughput includes launch and drain time. At 180 RPM, the full-run completion rate was approximately 102–104 RPM, not sustained 180 RPM capacity. The small throughput changes and generation variability do not establish an isolated operator speedup.

### TP4 prefill performance

Cross-node 1P1D, 4×H20-3e GPUs per side, TP4/EP4, with DSpark enabled. HiCache and radix caching were disabled. Each rate used the same 24 synthetic requests in the same order: eight each at approximately 3K, 12K, and 52K input tokens, grouped by length, with up to 128 output tokens per request. Projection sharding was enabled only on prefill in the custom build.

The comparison is between the custom build and a compatible deployment of main at e332e1b84e643d02d6223542941030c03717f62c. Their code and kernel stacks differ, so the table reports overall deployment changes rather than the isolated effect of projection sharding.

| Request rate | Input throughput change | Mean TTFT change |
|---|---:|---:|
| 15 RPM | 12.6% higher | 39.7% lower |
| 30 RPM | 17.0% higher | 28.0% lower |
| 60 RPM | 25.2% higher | 32.0% lower |

RPM is the client request launch rate. Input throughput covers the full batch, including launch intervals and drain time, rather than peak prefill throughput. Each rate was measured once, and the synthetic outputs were favorable to speculative decoding.
