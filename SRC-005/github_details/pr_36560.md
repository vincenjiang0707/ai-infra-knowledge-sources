# kernels: wave64 histogram-select for the MiniMax-M3 decode top-k

The MiniMax-M3 decode block top-k (`minimax_decode_topk` / `minimax_decode_topk_page_table`) picks the `topk` highest-scoring KV blocks per (head, batch) row with one CTA per row. This PR adds a wave64 histogram-select implementation of that selection for ROCm, and raises `TopKTrait::kMaxNumBlocks` from 4096 to 16384. The ROCm path packs `(score, ~block_id)` into a `u64` total order, runs one coarse histogram round (256 bins for rows up to 1024, else 2048), refines with 11-bit rounds while more than 128 candidates remain, and finishes with a wave-0 bitonic sort over the survivors; bins above the threshold bin are emitted immediately, bins below die, and the threshold bin survives to the next round, so the row is still read from global memory exactly once. The block-id kernel's ascending-order emit now uses a single 64-lane ballot instead of two width-32 shuffle reductions, and `TopKTrait` becomes `TopKTraitImpl<kNumThreads>` so the ROCm launchers can select a 1024-thread instantiation when `max_seqblock > 1024` (CUDA still instantiates only the 512-thread trait). The `kMaxNumBlocks` bump is the part that matters beyond ROCm: under CUDA graph capture the sparse backend bounds `max_seqblock` by the model's **full** context length rather than by the batch's real sequence lengths (capture runs on tiny dummy `seq_lens`, so replay must not be able to exceed the captured bound), which means any context above `4096 * block_size` — 524288 tokens at `block_size = 128` — trips the `max_seqblock` `RuntimeCheck` at capture time and the kernel cannot be used under graphs at all. 16384 blocks lifts that to 2M tokens at `block_size = 128`. `_MAX_NUM_BLOCKS` in the Python wrapper mirrors the C++ constant and is asserted in both `minimax_decode_topk` and `minimax_decode_topk_page_table`.

Note for reviewers on the CUDA path: the selection code is untouched on CUDA, but `kIters = kMaxNumBlocks / kCTASize` is derived from the bumped constant, so the multi-element regime (`num_blocks > 512`) now caches up to 32 keys per thread in registers instead of 8. That is still exactly at the `static_assert(kIters <= 32)` liveness-bitmask limit and the per-slot `idx < num_blocks` guard makes the extra slots inert, but it does raise the register footprint of that regime on CUDA.

## Correctness

The top-k selection semantics are unchanged -- this is a different reduction strategy (wave64 histogram select) over the same scores, not a different selection rule. Verified by gate rather than asserted: gsm8k **97.27% against a 97.07% baseline (+0.20 pp, one question of 512)**, `truncated_rate` **1.17% vs 1.56%** (i.e. below baseline) and `error_rate` 0.00%. Read as "no measurable accuracy cost".

Caveat on precision: this is a **single gate run**. The eval is not as deterministic as `temperature 0, seed 0` suggests -- SGLang batches requests dynamically, so fp accumulation order (and therefore greedy token choices) varies between runs. Repeating the same gate on another PR in this series gave 96.88% and 96.29% on two independent, uncontaminated runs, i.e. a **~0.6 pp run-to-run spread**. So read +0.20 pp as "within run-to-run noise", not as a measured improvement, and treat any single number here as having roughly that uncertainty.

## What the kMaxNumBlocks bump actually unblocks

`kMaxNumBlocks` 4096 -> 16384 is the load-bearing half of this PR, and it is not cosmetic. `MiniMaxSparseAttnBackend` pins `_max_seqlen_k = self.max_context_len` during CUDA-graph capture (capture runs on tiny dummy `seq_lens`, so replay must not exceed the captured bound), which makes `max_seqblock = ceil(context_len / block_size)`. At 4096 that caps out at 524288 tokens with `block_size = 128`; anything longer trips the `max_seqblock` `RuntimeCheck` **at capture time**, which is why the kernel was unusable under graphs at long context. 16384 lifts the ceiling to ~2M. The existing registered tests already sweep `max_ctx` up to exactly 524288 at block 128 -- i.e. the old ceiling.

The evidence that matters for this half is therefore a **graph-capture-on** run (no `--disable-cuda-graph`), which is how every number above was measured, not a microbenchmark.

One consequence a reviewer will want flagged: the bump is **not** a no-op on the CUDA path. `kIters = kMaxNumBlocks / kCTASize` is derived from it, so the `num_blocks > 512` regime now caches 32 keys per thread in registers instead of 8. It remains correct -- exactly at `static_assert(kIters <= 32)`, the uint32 liveness-bitmask limit, with the per-slot `idx < num_blocks` guard making extra slots inert -- but the register footprint of that regime grows.

`_MAX_NUM_BLOCKS` in the Python wrapper must stay in sync with `TopKTrait::kMaxNumBlocks`; it is asserted in both entry points (`minimax_decode_topk` and `minimax_decode_topk_page_table`).
## Reproduction

Server (identical on both sides):

```bash
SGLANG_USE_AITER=1 \
AITER_CONFIG_FMOE=/path/to/minimax_m3_mxfp8_tuned_fmoe.csv \
SGLANG_FORCE_MXFP8_BLOCK_CONVERT_DENSE=1 \
python3 -m sglang.launch_server \
  --model-path /path/to/MiniMax-M3-MXFP8 \
  --trust-remote-code --tp 8 --quantization mxfp8 \
  --moe-runner-backend aiter --fp8-gemm-backend auto \
  --enable-aiter-allreduce-fusion --attention-backend triton \
  --dtype bfloat16 --chunked-prefill-size 8192 --mem-fraction-static 0.80 \
  --host 0.0.0.0 --port 30000
```

Benchmark:

```bash
python3 -m sglang.benchmark.one_batch_server \
  --model None --base-url http://127.0.0.1:30000 \
  --output-len 600 --skip-warmup \
  --batch-size 1 2 4 8 16 32 \
  --input-len 80000 --show-report --cache-hit-rate 0.9
```

Accuracy gate:

```bash
sgl-eval run gsm8k --base-url http://127.0.0.1:30000/v1 \
  --num-examples 512 --num-threads 64 \
  --max-tokens 2048 --temperature 0 --seed 0
```

Two bench reps per boot, warm rep reported; noise floor +/-0.4%, established by a separate PR measuring flat under a config where its code cannot fire.

## Note on the launch command

`--moe-runner-backend aiter` is **not honoured on current `main`** for mxfp8. Arg resolution logs:

```
mxfp8 quantization supports only cutlass, deep_gemm, flashinfer_trtllm,
flashinfer_trtllm_routed, triton backends. Overriding 'aiter'.
```

and falls back to **triton**. Both sides of this A/B therefore ran the Triton MoE runner, so the comparison is apples-to-apples and the deltas stand — but `AITER_CONFIG_FMOE` is inert under this configuration and the aiter MoE path is *not* what was measured. The flag is kept in the command above only because it matches the invocation actually used; anyone reproducing will get triton and should see the same numbers.
