### Describe the bug

### Describe the bug

SGLang hardcodes `params_dtype=torch.float32` for Kimi Delta Attention (KDA) short-convolution weights, regardless of the checkpoint's native data type. This silently up-casts native `bf16` checkpoints to `fp32`. Up-casting doubles the convolution weight bandwidth during decoding without adding any true precision to the weights.

#### Root cause
The hardcoded definitions exist in the following locations (as of commit `95521da18d`):
- `python/sglang/srt/models/kimi_linear.py:400` — `qkv_conv1d` uses `MergedColumnParallelLinear(..., params_dtype=torch.float32, ...)`.
- `python/sglang/srt/models/glm5_next.py:520-526` — `qkv_conv1d` is hardcoded to `torch.float32`.
- `python/sglang/srt/models/bailing_moe_v3.py:888-928` — `BailingKDA` subclasses `KimiDeltaAttention`, inheriting the `fp32` hardcode.
- `python/sglang/srt/models/kimi_k3.py:1726` — Kimi-K3 does not inherit from `kimi_linear.py` but has its own `MergedColumnParallelLinear(..., params_dtype=torch.float32)` for a third, separate KDA `qkv_conv1d`.

The type casting is silent because the loader uses in-place `param_data.copy_(loaded_weight)`. 

*History & Context:* The `fp32` cast was introduced in the original Kimi Linear PR. However, the original Kimi-Linear-48B checkpoint is natively `bf16`, meaning the engine's `fp32` allocation never matched the checkpoint. Contrast this with `python/sglang/srt/layers/attention/dsa/dsa_indexer_kpool.py:142`, which performs a similar up-cast but includes a clear, explicit comment justifying it: `# Keep weights_proj in FP32 because its accumulation/scale path requires FP32; checkpoint BF16 weights are cast on load.` The lack of any such justification for KDA strongly suggests an oversight rather than a deliberate choice. 

Note that vLLM has the exact same bug at `vllm/model_executor/models/bailing_moe_v3.py:697-716`.

#### Reference implementations
The original model implementations do not require `fp32`:
- `moonshotai/Kimi-Linear-48B-A3B-Instruct` (`modeling_kimi.py:471-483`): Instantiates `fla.modules.ShortConvolution(...)` using the model's default dtype.
- `moonshotai/Kimi-K3` (`modeling_kimi_linear.py:504-518`): Uses `ShortConvolution(...)` with no dtype override.

#### Kimi K3 Exception
`moonshotai/Kimi-K3` intentionally ships `fp32` convolutions. Within a single KDA block, small parameters (`A_log`, `dt_bias`, `q/k/v_conv1d.weight`) are `fp32`, while projections remain `bf16`. The checkpoint parser should respect this deliberate choice (when specified).

#### Up-casting to fp32 is pure waste
Up-casting a `bf16` weight to `fp32` adds no actual information to the weight itself because it was already rounded when saved. 

Note on numerics: Applying a fix to load `bf16` natively is not strictly bit-exact to the current `fp32` cast due to how the Triton kernel is written. In `causal_conv1d_triton.py:366`, the multiply-accumulate is:
`acc += matrix_x * matrix_w` (no explicit cast)
- **Today (x is bf16, w is fp32):** `matrix_x` promotes, the product is computed and kept in `fp32`, and added to the `fp32` accumulator.
- **After fix (x is bf16, w is bf16):** The product is computed in `bf16` and rounded *before* it reaches the `fp32` accumulator.

The observable difference comes entirely from the kernel's uncast multiply, not the weights. If need to keep exact bit-for-bit equivalence with the old behavior while saving weight bandwidth, it is a two-line change in the Triton kernel to cast `matrix_x` and `matrix_w` to `tl.float32` prior to the multiplication. 

#### Impact
At batch=1 decode, the convolution is weight-bandwidth bound. For GLM-5.3-Flash, the activation slice is ~48 KB per layer compared to ~393 KB for the current `fp32` weights.

Conv weight bytes streamed per decode token, unsharded:

| Model | KDA layers | conv_dim | fp32 (current waste) | bf16 (if fixed) |
| :--- | :--- | :--- | :--- | :--- |
| zai-org/GLM-5.3-Flash | 34 | 3 x 8192 = 24576 | 13.4 MB | 6.7 MB |
| inclusionAI/Ling-3.0-flash | 35 | 3 x 4096 = 12288 | 6.9 MB | 3.4 MB |
| moonshotai/Kimi-Linear-48B-A3B | 20 | 3 x 4096 = 12288 | 3.9 MB | 2.0 MB |
| moonshotai/Kimi-K3 | 69 | 3 x 12288 = 36864 | 40.7 MB | *(keeps fp32, correctly)* |

Removing `fp32` weights against `bf16` activations also eliminates a mixed-dtype promotion directly from the Triton inner loop.

#### Proposed fix
Probe the checkpoint's convolution weight dtype during configuration resolution and pass it dynamically as `params_dtype`. It should not need an override configuration to change the dtype; the engine should automatically respect the checkpoint. 

Precedent exists in-tree: `python/sglang/srt/model_loader/weight_utils.py:90-131` (`probe_routed_expert_weight_dtype`).

**Implementation hazard:** The dtype must be resolved before module construction. Currently, SGLang captures a view of the weights at `__init__` time (`conv_weights = self.qkv_conv1d.weight.squeeze(1)`). If `param.data` is swapped post-initialization, these views will point to uninitialized memory.

#### NVIDIA Quant
NVIDIA's repacks disagree with original authors: `zai-org/GLM-5.3-Flash` is BF16, but `nvidia/GLM-5.3-Flash-NVFP4` is F32. NVIDIA baked their engine-side up-cast directly into the file. The engine should simply respect the checkpoint provided. (But seems wrong).

```python
import json, struct, sys

with open(sys.argv[1], "rb") as f:
    n, = struct.unpack("<Q", f.read(8))
    hdr = json.loads(f.read(n))
    
for k, v in hdr.items():
    if "conv1d" in k or "sconv" in k:

```

1. Run the script on `moonshotai/Kimi-K3` shard 1: It prints `F32 [12288, 1, 4]` for `language_model.model.layers.0.self_attn.{q,k,v}_conv1d.weight`.

3. Load either model in SGLang and check the parameters: Every KDA `qkv_conv1d.weight` is forcibly allocated as `torch.float32`.
