# [PR #40149] [NPU][Perf] Run MiMo-V2.5 MoE router in bf16 and drop redundant topk_ids casts

state: open | updated: 2026-09-23T06:11:53Z

## 正文

## Motivation

The MiMo-V2.5 MoE router kept its gate weight in fp32: every MoE layer cast `hidden_states` bf16→fp32 for the router matmul, then `fused_topk_npu` cast the logits back to fp32 for `npu_moe_gating_top_k` — two Cast kernels plus a non-Cube fp32 matmul per layer (57 layers). Separately, the DeepEP low-latency dispatcher converted `topk_ids` to int64 while the NPU DeepEP runtime takes int32 — an int32→int64→int32 round trip costing 2–3 more Cast kernels per layer.

## Modifications

- Keep `MoEGate.weight` / `e_score_correction_bias` in bf16 **on NPU**: the router matmul runs natively on Cube units and `npu_moe_gating_top_k` consumes bf16 logits directly. GPU keeps the historical fp32 gate.
- `fused_topk_npu`: dtype-alignment guard instead of unconditional fp32 casts — nothing is cast when logits and bias share a dtype; an fp32 bias promotes the logits to fp32 (downcasting the bias to bf16 reorders top-k routing, see the GLM-5.2 note in `deepseek_v2.py`). No bias → historical fp32 scoring, so sigmoid / `num_token_non_padded` models are unaffected.
- Skip `topk_ids.to(torch.int64)` in the DeepEP LL dispatcher on NPU; GPU keeps int64 (its native requirement).
- `topk_weights` stay fp32: `MoeLowLatencyCombineV2` requires DT_FLOAT expert scales — a hard requirement, not a leftover. The modelopt_fp4 + flashinfer_trtllm bias branch also stays fp32.

Other models: Qwen3-MoE-style (softmax, no bias) takes a different branch — unaffected; DeepSeek-family ends up fp32 either way — identical numerics; GPU behavior unchanged everywhere.

## Speed Tests and Profiling

Profiling (per MoE layer, decode, DeepEP LL, EP6):

| Kernel | Before | After |
|---|---|---|
| Router MatMulV3 | 13.84 us | 9.12 us (**-34%**) |
| Pre-router Cast (bf16→fp32) | 2.63 us | eliminated |
| Topk-related Casts | 4 casts / 8.67 us | 1 cast / 2.50 us |

The single remaining cast is the hard-required bf16→fp32 `topk_weights` conversion (CombineV2 DT_FLOAT).

Benchmark (16k-input prefill-heavy workload, 128 prompts, request rate 0.4):

| Metric | Before | After |
|---|---|---|
| Mean TTFT | 2308.5 ms | 1866.78 ms (**-19.1%**) |
| P90 TTFT | 4274.1 ms | 3033.30 ms (**-29.0%**) |
| P99 TTFT | 7061.9 ms | 4062.82 ms (**-42.5%**) |

Decode-side gains are minor as expected — the router is a small share of the decode step.
