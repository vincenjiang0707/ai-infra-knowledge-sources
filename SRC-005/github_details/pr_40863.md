# [PR #40863] [AMD] Use packed AWQ GEMM for small batches

source: https://github.com/sgl-project/sglang/pull/40863
state: open | updated: 2026-09-23T06:51:25Z
labels: quant, jit-kernel

## 正文

## Motivation

The ROCm `AWQLinearKernel.apply` path expands the entire weight matrix with `awq_dequantize_triton`, then calls `torch.matmul` on every invocation. `awq_gemm_triton` already exists, but no runtime caller uses it.

This is expensive during decode. I encountered it while tracing the [official Ternary Bonsai AWQ checkpoint](https://huggingface.co/prism-ml/Ternary-Bonsai-27B-AWQ-4bit/tree/7f49f5d23a09087131cd50627366967f013b9f9e). Its sampled attention and MLP weights use only codes 7, 8 and 9 with zero point 8, but the generic AWQ path still materializes a full floating-point matrix.

## Modifications

- Route gfx1151 ROCm AWQ batches of 1 through 16 rows to the existing packed Triton GEMM with a 16x64x32 tile and split-K 8. Larger batches, other HIP architectures, and CUDA/Marlin routing stay unchanged. CDNA does not take the new path without CDNA measurements.
- Accumulate in FP32 and retain FP32 split-K partials. The existing helper used the output dtype for both, which could overflow on FP16 inputs even when the final answer was finite.
- Reduce split-K partials directly into the activation dtype. Avoid the initial zero-fill and skip reduction for split-K 1.
- Allow BF16 activations on the ROCm AWQ path. Keep checkpoint weights, zero points and scales unchanged. No activation quantization or ternary-specific repacking is introduced.
- Add kernel tests, runtime dispatch coverage for strided/empty/batched inputs and bias, and a paired benchmark. Defer unrelated Quark AITER imports until the operations that need them, so AWQ runtime imports do not require AITER.

## Accuracy tests

On Radeon 8060S, gfx1151, ROCm 7.2.53211, Torch 2.14.0+rocm7.2 and Triton 3.8.0:

```sh
python -m pytest test/registered/kernels/ops/quantization/test_awq_gemm.py -q
# 18 passed in 4.34s
```

Coverage includes FP16/BF16, group sizes 32/64/128/full-K, split-K 1/8, tail output columns, signed packed words, exact agreement between dequantization implementations, and a cancellation case that needs FP32 accumulation.

On the real Bonsai tensor panels below, relative squared error against FP32 matmul of the same dequantized operands was 2.64e-6 for the BF16 attention tensor, 2.75e-6 for the BF16 gate tensor, and 4.27e-8 for the FP16 gate tensor. The dequantize-plus-matmul reference has essentially the same output-rounding error. Reduction order changes, so outputs are not promised bit-identical.

The registered HIP `test_linear_dispatch` now passes on gfx1151, including packed rows 1/16, fallback rows 0/17, BF16/FP16, strided input and bias. A gfx942 architecture control checks that CDNA does not select packed GEMM. Sixteen more cases load both pinned Bonsai layer-0 matrix tensors and compare runtime outputs with FP32 decoded-weight matmul; relative squared errors are below 1e-4 with generated activations. These are layer-level checks, not a full Bonsai model forward. Quark AITER imports have been moved to their operation boundaries, without installing or stubbing AITER. This PR remains a draft pending complete-model or server accuracy acceptance. CDNA performance is unmeasured and CDNA retains the existing fallback, so no CDNA speedup is claimed.

## Speed tests and profiling

Paired GPU-graph timing, nine rounds with alternating arm order and 40 calls per graph, on the hardware above. Actual checkpoint weight tensors are pinned to revision `7f49f5d23a09087131cd50627366967f013b9f9e`; activation inputs are generated with seed 917, not captured model activations. Times include dequantization and matmul in the reference, and packed GEMM plus split reduction in the candidate.

| Weight tensor | M | dtype | K x N | Dequantize + matmul | Packed GEMM | Median paired ratio |
|---|---:|---|---|---:|---:|---:|
| Layer 0 linear attention `in_proj_qkv` | 1 | BF16 | 5120 x 10240 | 1222.43 us | 169.60 us | 7.22x |
| Layer 0 MLP `gate_proj` | 16 | BF16 | 5120 x 17408 | 2116.53 us | 321.31 us | 6.65x |
| Layer 0 MLP `gate_proj` | 1 | FP16 | 5120 x 17408 | 2089.41 us | 279.21 us | 7.48x |

A synthetic 512x1024 ternary AWQ matrix at M=1 took 18.56 vs 6.42 us, 2.89x paired. General random 4-bit weights at 5120x5120 took 564.05 vs 87.43 us at M=1, and 559.33 vs 93.99 us at M=16.

Clock and package-power telemetry was retained with the local panels. The machine had other CPU work, roughly 2 to 3 busy host cores during the real-tensor panels, so these are paired measurements under shared-package load rather than quiet or fixed-clock results. These are linear-operation timings, not end-to-end serving throughput or a comparison with CUDA Marlin.

The included benchmark reproduces the comparison using generated AWQ weights, including the same ternary codes:

```sh
python test/manual/bench_awq_gemm.py --m 1 --k 5120 --n 10240 --dtype bfloat16 --ternary
python test/manual/bench_awq_gemm.py --m 16 --k 5120 --n 17408 --dtype bfloat16 --ternary
```
