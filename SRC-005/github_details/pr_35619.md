## Summary
- add the packaged Aiter/FlyDSL MegaMoEv2 backend for DeepSeek-V4 with DP rank synchronization and graph-safe idle handling
- add prefill-only fused EPLB remap/recording to remove per-layer recorder overhead
- preserve stable SWA eviction cadence for the MegaMoE path under high DP concurrency and cover rank-sync, recorder, and mixed-slot behavior with regression tests

## Performance
Validated on 8×MI355X, DeepSeek-V4-Pro, ISL/OSL 8192/1024, concurrency 512, 5120 requests:
- no EPLB: 38,863.10 tok/s
- dynamic fused EPLB (interval 200): 42,382.44 tok/s

These match the source integration within +0.26% and +0.015%, respectively. The branch was subsequently rebased onto current `main`; full GPU e2e revalidation on the new base remains pending.

### Four settings that silently break it

1. **`MORI_SHMEM_HEAP_SIZE`.** The mori default (4 GiB) is not enough —
   MegaMoEV2's dispatch/combine buffers want ~3.1 GiB each, and it fails during
   **decode CUDA-graph capture** with `AssertionError: mori_shmem.shmem_malloc
   failed`. 16 GiB was sufficient here. Worth noting capture exercises MegaMoE
   unconditionally (`should_use_mega_moe` returns True in capture mode), so this
   fires regardless of load.
2. **`--enforce-shared-experts-fusion` is incompatible.** Use
   `--disable-shared-experts-fusion`. With fusion on, `forward_mega_moe` sizes
   MegaMoEV2 with `topk = num_experts_per_tok + num_fused_shared_experts` (7
   instead of 6) and the dispatch path dies with
   `HSA_STATUS_ERROR_EXCEPTION 0x1016`.
3. **The four DP-comm envs must be 0.** MoE comm is mori's; leaving the DP
   gatherv/reduce-scatter path enabled runs two schemes at once and also faults
   with 0x1016.
4. **EPLB without `--expert-distribution-recorder-mode stat` is a regression.**
   Measured **36,642.28 tok/s (-6.5% vs no-EPLB)** with 1040 rebalance events
   and no load statistics behind them. The recorder is what turns it into
   +8.4%. Also: leaving `--ep-num-redundant-experts` at its default 0 is
   correct — setting 32 costs KV pool for no gain.

Might be worth folding 1-4 into the PR description, since none of them produce
an error that points at the actual cause.

### One bug: `SGLANG_AITER_MEGA_RANK_SYNC` with DP attention

In `forward_batch_info.py`:

```python
if mega_moe_idle_materialize:      # RANK_SYNC and is_extend_in_batch and forward_mode.is_idle()
    global_num_tokens = [1]
```

`adjust_num_token_non_padded_for_attn_tp` then does
`self.global_num_tokens_cpu[dp_rank]`, and `attn_dp_rank` reaches 7 at
`dp_size 8`, so any rank above 0 raises `IndexError: list index out of range`
and takes the scheduler down on the first real forward. The server prints
`ready to roll` before this, so it presents as "died before /health became
ready".

The fixed-seq-len runs above did not hit it, including the EPLB arm with
`RANK_SYNC=1` — it needs an idle batch to coincide with an extend. I hit it
consistently on a long-context multi-turn agentic workload with
`--enable-prefill-delayer` on. `[1] * len(global_num_tokens)` would keep the
intent and fix the indexing.
