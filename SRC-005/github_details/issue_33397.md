### Describe the bug


## Summary

Serving `deepseek-ai/DeepSeek-V4-Flash-0731` with SGLang on 2× H200 produces
**corrupted output that scales with batch size**. It starts as subtly degraded
language, escalates to malformed/mis-channelled tool-call markup, and ends in
complete token soup. We reproduced it on **two configurations that share almost
nothing** except SGLang, the checkpoint, `--attention-backend dsv4` and DP
attention — including a self-built image carrying the #33098 patch — and we do
**not** see it with vLLM 0.26.0 on the same node, same checkpoint, same fp8 KV.

We suspect a KV/page-index issue in the DSA ("HiSparse") path under batching —
i.e. the same *class* of defect as #31482 / #31901, but on the non-PD code path.

## Symptoms — one defect, three severity tiers

**Tier 1 — degraded language.** Grammatically fluent but semantically wrong
words, drifting register, occasional wrong-language insertions (our traffic is
mixed German/English, and corrupted turns swap between the two mid-sentence). Easy to dismiss
as model quality until the harder tiers show up in the same session.

**Tier 2 — tool-call markup emitted in the wrong channel / malformed.** DSML
markup appears as visible text, or a complete, well-formed DSML block is streamed
as `reasoning_content` while `</think>` never arrives, so the tool parser never
sees it and the turn ends `finish_reason: stop` with empty content and no tool
calls. From a byte-level capture in front of the server (1203 upstream chunks,
one turn):

- `<｜DSML｜tool_calls>` / `<｜DSML｜invoke name="Bash">` / closers arrive
  **exclusively in `delta.reasoning_content`**
- **no `</think>` anywhere** in the stream (neither reasoning nor content)
- zero `delta.tool_calls`, `content` deltas empty, final chunk `finish_reason: "stop"`

We initially read this as a reasoning/tool parser classification bug. Given tier 3
below, a corrupted or dropped `</think>` token is at least as likely an
explanation — which is why we are filing it here rather than as a parser issue.

**Tier 3 — total corruption.** Verbatim examples from production (German/English
mixed input):

```
Allen Kolleginnen und Kollegen großzügig nuts. Hier die Rücksicht genommen.</think>
```

(Reads as grammatical German with semantically random words: "To all colleagues
generously nuts. Here the consideration taken." The English word "nuts" is spliced
into an otherwise German sentence, and `</think>` lands in the visible answer.)

```
:** Which better move me taped the Lightness, the flip script se ker @ Verb's 0.</think>
Wie einfach regarding to the{ csvDiscovery: { React was gebraten. Damit nun m who
meint that she is. User turned adjected slight. And then got the safety influence
and in man mit. Gu easily.
```

The second sample mixes German and English mid-sentence with no semantic
connection to the request ("React was gebraten" = "React was fried"), and again
carries `</think>` inside the visible answer. A third sample degenerated into a
heading repeated eight times with fragmentary table rows ("## Fixed Jira
Configuration" / "| Column | B" / "-(follows | |" …), ending in the model's own
line "... Content has drifted far from the instructions.".

The model sometimes notices and apologises for its own output in the next turn —
"das war Unsinn — meine letzte Antwort war fehlerhaftes Zeug" ("that was nonsense —
my last answer was broken stuff") — i.e. the corruption is in the generated tokens,
not in client-side rendering.

## Load correlation

The reports clustered exactly in a window where the server ran **up to 8–9
concurrent requests per DP rank** (`sglang:num_running_reqs` from the Prometheus
metrics endpoint, per `dp_rank`).
Single-request smoke tests are clean; we could not reproduce any tier with
sequential synthetic requests, including 14 attempts spanning complex nested
tool schemas, thinking on/off, multi-turn tool histories, and contexts of
30k / 120k / 155k / 770k tokens with `reasoning_effort: max`. Corruption only
showed up under real concurrent production traffic.

## What we ruled out

- **HiCache / L2+L3 offloading** — config B has no host or disk tier (verified
  against the deployed container spec: no `--enable-hierarchical-cache`, no
  `--hicache-*`, no NVMe mount, no `SGLANG_HICACHE_*` env) and still corrupts.
  **Not** ruled out: the device-level radix/prefix cache, which was active in both
  configs (`--disable-radix-cache` is not set anywhere). A page-ID mismatch between
  the radix cache and the DSA indexer tiers is in fact one of our hypotheses below.
- **Speculative decoding** — config A has none and still corrupts.
- **PD disaggregation / Mooncake** — not used in either config.
- **#33098 as a sufficient fix** — config B *includes* that patch and still
  corrupts, so whatever remains is not (only) the DSpark draft-batch metadata.
- **The checkpoint and the hardware** — same node, same checkpoint, same
  `--kv-cache-dtype fp8` served by **vLLM 0.26.0** (TP=2 + EP, block-size 256,
  prefix caching, no offloading): no corruption observed in production traffic
  after the switch. This is what we are running now.
- **Client-side / proxy** — the corruption is present in the raw upstream SSE
  chunks captured in front of the server.

## Relation to #33098

Config B runs a self-built `v0.5.16` image with the #33098 patch ("Fix DSpark and
DP/EP"), because without it DSpark + `--enable-dp-attention` cannot start at all:
first `ValueError: DSpark with dp attention requires --enable-dp-lm-head`, and
with that flag a warm-up crash loop in the draft forward
(`decode_cuda_graph_runner.can_run_graph` → `TypeError: 'NoneType' object is not
iterable`, both DP ranks, ~24 min boot/timeout cycle). With the patch it boots and
serves — and then shows the corruption described above. So #33098 fixes the
startup/graph-admission problem but does not address this.

## Suspected area

The remaining common factors are `--attention-backend dsv4` (DSA/HiSparse) with
fp8 KV **and DP attention**, under batching. DeepSeek-V4 keeps several KV tiers (full / swa / c4 / c128
indexer). If page or batch indices for the indexer tiers can be mismatched while
several sequences share a batch — or across DP ranks, where token counts and
padding differ per rank —  sparse attention would select the wrong tokens —
which produces exactly this signature: locally fluent, semantically wrong output
that gets worse as batch size grows, up to complete token soup, and occasionally
destroys single structural tokens such as `</think>`.

That is the same class of defect as:

- **#31482** — "DeepSeek-V4 PD HiSparse shows lower accuracy on GPQA and SWE-Bench",
  including malformed/mixed DSML in failed turns
- **#31901** — fix for the PD/Mooncake path: host KV page indices were used for
  both host and device destination buffers because "HiSparse allocates host pages
  and logical device pages independently, so their page IDs are not guaranteed to
  match"

Our setups do **not** use PD, so #31901 cannot be the fix for us — but the
described independent-page-ID hazard would explain everything we see if it also
exists on the plain (non-PD) dsv4 path, e.g. between the device pools of the
different indexer tiers, or between radix-cache page IDs and indexer page IDs.

## Questions

1. Is there a known batch-size-dependent page/index hazard in the non-PD dsv4
   HiSparse path (device-side only, no host/disk tiers involved), in particular
   under `--enable-dp-attention` where per-rank token counts/padding differ?
2. Is `--attention-backend dsv4` + `--kv-cache-dtype fp8_e4m3` on Hopper a tested
   combination for 0731, or is fp8 KV expected to be used only with specific
   indexer settings?
3. Anything we can enable to help localise this (per-tier page-ID assertions, a
   debug mode that validates indexer page mapping against the radix cache)?

### Reproduction


**Model:** `deepseek-ai/DeepSeek-V4-Flash-0731`, unmodified, from HF.

**How it manifests:** real production traffic only. Agentic coding clients
(Claude Code and OpenAI-compatible agents) with thinking enabled, 30–70 tools per

corrupted answers appear within minutes of taking real traffic, and cluster where
`sglang:num_running_reqs` reaches 8–9 per DP rank.

**We have no deterministic reproducer.** Synthetic *sequential* requests stayed

production had already been moved to vLLM to stop user impact, and we did not want
to put the corrupting configuration back in front of users. Reproducing under
synthetic concurrency is therefore still untested from our side.

## What I ruled out on our side

- **weights** — Both stacks runs the original FP4 checkpoint; both corrupt. FP8 custom checkpoint shows the same results
- **speculative decoding** — absent in both stacks at the time of the observations
- **hicache / CPU offload** — absent in Stack A, present only later in Stack B
- **sampling** — `top_p 1.0` vs `0.95` made no difference; 8 replays at each value, 0 loops either way (the failures are load-dependent, see below)
- **tool-call parser** — corrupted outputs contain no tool calls at all
- **prompt-side drift** — diffed two consecutive requests of one session byte-for-byte: identical prefix, only two messages appended

## Sequential vs concurrent — matches your observation

Replaying the exact failing request **serially** does not reproduce it: 0/11 on SGLang for one request, 0/17 on vLLM across variants, even with the already-corrupted assistant turn left in the history. The 20% figure above comes from 30 replays issued back-to-back against a node that was **also serving live traffic** at the time. This lines up with your "only under concurrent production traffic, not with sequential requests".

## Common factor

Given that both frameworks corrupt on the same node with different weight formats and no speculative decoding, the shared surface is: **DSA indexer + fp8 KV + data-parallel attention under batching** — i.e. exactly the page/batch-index mismatch across DP ranks you suspect, rather than anything framework-specific.

Next thing I plan to test is vLLM with **`tp` only, no data parallelism**, under the same concurrent load. If that comes back clean, DP is the trigger and the two frameworks are just two ways of hitting it. Happy to post the numbers either way, including if they disagree with the above.

### Wendy-Hamlet · 2026-09-22

A possibly relevant data point for the SM90 (H100/H200) + `--moe-runner-backend flashinfer_mxfp4` configurations in this thread.

We found a race in FlashInfer's SM90 W4A16 MXFP4 CUTLASS fused MoE that makes an occasional CTA tile of one expert use the **next expert's weight scales** for its last K-blocks. The affected rows come out wrong by roughly 10–30% (against a PyTorch reference), silently, and only on some calls. Details, a standalone repro and a one-line fix are in flashinfer-ai/flashinfer#5438.

Why it may matter here:

- **Affected FlashInfer releases are 0.6.10 – 0.6.15.post1.** SGLang v0.5.15.post1 pins 0.6.12 and v0.5.16 pins 0.6.14 (the versions used above); v0.5.17 pins 0.6.15.post1. v0.5.18 and later pin 0.6.17+, where the kernel was rewritten (flashinfer-ai/flashinfer#3738); we could not reproduce the error on 0.6.18.
- **It only shows up in prefill-sized MoE calls.** SGLang's FlashInfer autotune only covers decode batch sizes (M ≤ 256 in our cache), so prefill uses the default tactic, which hits the race. Decode-sized calls (M ≤ 256) were clean for every tactic we tried.
- **How often it hits depends on the tactic and the call size.** For the default tactic we measured roughly one bad call per 100–200 at 8,192–65,536 tokens per call; some other tactics that are clean at 8,192 tokens fail on most calls at 32,768–65,536. Under concurrent load there are more prefill-sized MoE calls (and with DP attention each call carries the tokens gathered across DP ranks), so more of them would be expected. That is compatible with "clean when replayed serially, corrupted under concurrent traffic", but we have **not** verified that this race explains the corruption reported here, and it cannot explain the Blackwell (B300) case, which uses a different MoE path.

On our side (DeepSeek-V4-Flash-0731, 8×H100, TP8 + DP-attention, FlashInfer 0.6.12) the observed effect in prefill was a sporadic group of ~16 tokens (one tile of one expert) whose MoE output differed by ~1e-3 – 4e-3 relative between two identical runs, which then propagates through later layers.

If someone here can still reproduce on SM90, it would be useful to know whether it goes away with SGLang ≥ v0.5.18 (FlashInfer ≥ 0.6.16), or with the one-line patch from flashinfer-ai/flashinfer#5438 applied to the FlashInfer version you are on.
