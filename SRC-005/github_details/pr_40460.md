# [PR #40460] fix(scheduler): abort over-length embedding requests before enqueuing

## 正文

## Motivation

Fixes #40459.

**Supersedes #21169 by @warren618**, who found and fixed this first. That PR and its issue #21168 were both closed by the inactivity bot rather than by review — #21168 on 2026-05-23 and #21169 on 2026-08-25. The original author has not responded to a reopen request, and I do not have the permissions to reopen either one, so this PR carries the same one-line fix forward with them credited as co-author. Please close #21169 as superseded if this lands.

`handle_embedding_request` does not call `req.set_finish_with_abort(error_msg)` when `validate_input_length()` returns an error, so the request is added to the waiting queue without ever being marked aborted:

```python
# python/sglang/srt/managers/scheduler.py -- before this PR
error_msg = validate_input_length(
    req,
    self.max_req_input_len,
    get_serving().allow_auto_truncate,
)
if error_msg:
    self._add_request_to_queue(req)   # no set_finish_with_abort(error_msg)
    return
```

`handle_generate_request` does it correctly, and so do the three other early-return branches of `handle_embedding_request` itself (`mm_input_error`, multimodal input processing, post-expansion length). This branch was the only outlier.

`set_finish_with_abort` does two things: it sets `to_finish = FINISH_ABORT(...)`, and it replaces `origin_input_ids` with a single token ("set it to one token to skip the long prefill"). Skipping it means the over-length request is admitted at full length with no finish reason attached, so instead of the intended HTTP 400 the caller receives nothing and blocks until its own timeout. The scheduler logs the validation error, but it never reaches the client.

Note for anyone reading the original report: its Impact section claimed illegal memory access and a server crash, and linked the roadmap item #12780. That was wrong — there is no crash. #40459 has the corrected analysis.

The scheduler-side check is reachable because `TokenizerManager._validate_one_request` validates against `context_len` while the scheduler validates against `max_req_input_len`, so a KV pool smaller than the context length lets a request pass the first and fail the second. That split is a known issue, marked with a standing `FIXME: unify the length validation logic with the one in the scheduler.` in `tokenizer_manager.py`; unifying it is out of scope here.

## Modifications

- `python/sglang/srt/managers/scheduler.py` — add the missing `req.set_finish_with_abort(error_msg)` in `handle_embedding_request`. `handle_batch_embedding_request` delegates to this handler, so it is covered by the same line.
