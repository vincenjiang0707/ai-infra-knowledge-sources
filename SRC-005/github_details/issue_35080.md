### Describe the bug

> An unsolved duplicate of #20709

I noticed that `flashinfer` is gated again in [srt/layers/attention/attention_registry.py#L391](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/attention/attention_registry.py#L391).

I encountered this while running [verl's Delta Weight Sync example](https://github.com/verl-project/verl/blob/main/verl/experimental/one_step_off_policy/shell/grpo_0.6b_gsm8k_fsdp2_sglang_delta_sharded_2_6.sh) with `sglang==0.5.17` and `torch==2.11.0+cu130` on **`sm_103` Blackwell GPUs (more precisely, B300)**.

The server fails during attention backend initialization with:

```bash
AssertionError: Only {'trtllm_mha', 'triton', 'fa4'} backends are supported on Blackwell GPUs for hybrid GDN models. Got attention_backend=flashinfer.
```

Is this restriction intentional in the latest distribution, or is there a recommended configuration/workaround for this setup? In particular, I'm wondering whether `flashinfer` is expected to support this workload again.

### Reproduction

Script: [verl's Delta Weight Sync example](https://github.com/verl-project/verl/blob/main/verl/experimental/one_step_off_policy/shell/grpo_0.6b_gsm8k_fsdp2_sglang_delta_sharded_2_6.sh)

Solved when specify the `attention_backend=triton`

```bash
+actor_rollout_ref.rollout.engine_kwargs.sglang.attention_backend=triton \
```

### Chishenzheng · 2026-08-25

I can reproduce this on a single NVIDIA B300 (SM 10.3) with current main (`e2b50930b`).

**Environment**

- GPU: NVIDIA B300 SXM6 (SM 10.3), driver 580.126.09
- CUDA 13.0, PyTorch 2.13.0+cu130, FlashInfer 0.6.17
- Model: `Qwen/Qwen3.5-35B-A3B` (hybrid GDN + MoE), TP=1

The failure comes from the capability gate for hybrid GDN models on Blackwell in [`attention_registry.py#L431-L442`](https://github.com/sgl-project/sglang/blob/e2b50930b9316719825c7ebcfbe40f16403d34a0/python/sglang/srt/layers/attention/attention_registry.py#L431-L442):

```
AssertionError: Only {'trtllm_mha', 'triton', 'fa4'} backends are supported on
Blackwell GPUs for hybrid GDN models. Got prefill=flashinfer, decode=flashinfer.
```

Since this model has two separate attention subsystems — full attention (`--attention-backend`) and Gated DeltaNet (`--linear-attn-backend`) — I tested them independently in a 2×2 matrix:

| full attn | GDN linear | result |
| --- | --- | --- |
| triton | triton | ✅ works |
| triton | flashinfer | ✅ works (requires `--mamba-ssm-dtype bfloat16` on SM100+) |
| flashinfer | triton | ❌ blocked by the gate above |
| flashinfer | flashinfer | ❌ blocked by the gate above |

Note that the FlashInfer **GDN linear-attention** path already works on SM103 — the docs state FlashInfer GDN support for [SM90/SM100/SM103](https://github.com/sgl-project/sglang/blob/e2b50930b9316719825c7ebcfbe40f16403d34a0/docs/docs/advanced_features/attention_backend.mdx#L390) and even [auto-select FlashInfer for GDN prefill on SM100/SM103](https://github.com/sgl-project/sglang/blob/e2b50930b9316719825c7ebcfbe40f16403d34a0/docs/docs/advanced_features/attention_backend.mdx#L341) under the right conditions. Only the **full-attention** backend is gated.

**Local bypass experiment.** After adding `flashinfer` to the allowed set for non-SM120 Blackwell, both `flashinfer`+`triton` and `flashinfer`+`flashinfer` start and generate coherent text. With `temperature=0`, outputs diverge from the triton baseline only at synonym-level points (expected from different FP reduction orders across kernels); no corruption or degraded output.

**Benchmark** ([`sglang.bench_serving`](https://docs.sglang.ai/developer_guide/bench_serving), random dataset, `--random-range-ratio 1.0`, output 128 tokens, 64 prompts, max-concurrency 8):

- **Input 1024** (3 runs): parity with triton — 1169 ± 0.2 vs 1189 ± 57 output tok/s; FlashInfer is noticeably more stable run-to-run.
- **Input 8192** (3 runs): triton shows large warmup drift (478 → 652 → 913 tok/s, likely JIT/autotune warmup) and is faster once warm; FlashInfer is stable from the first run (609 / 611 / 612 tok/s).
- **Input 32768** (5 runs): triton converges by run 3 at ~435 tok/s (mean TTFT ~375 ms); FlashInfer converges more slowly (149 → 221 → 234 → 252 → 269 tok/s) and lands roughly 1.6× slower than triton for long-context prefill in this configuration.

So on SM103 the FlashInfer full-attention path appears functionally correct and at parity with triton for short contexts, but notably slower for long-context prefill — which might be part of the motivation for the gate.

Is this restriction intentional (e.g. a known correctness or performance concern specific to GB300/B300), or would you accept a PR that adds `flashinfer` to the allowed set for non-SM120 Blackwell, together with a regression test and the validation data above? Happy to prepare it if this direction is wanted.

### janbernloehr · 2026-09-08

We tested this on a single AGX Thor (SM110) using:

- SGLang: `0.0.0.dev1+g30705c004`
- FlashInfer: `0.6.18`
- CUDA: `13.0.3`
- Models:
  - `Qwen/Qwen3.6-35B-A3B-FP8`
  - `nvidia/Qwen3.6-35B-A3B-NVFP4`

The only SGLang source change was adding `flashinfer` to the hybrid-GDN Blackwell attention-backend allow-list:

```python
allowed = {"triton", "trtllm_mha", "fa4", "flashinfer"}
```

With that change, both FP8 and NVFP4 workloads started successfully, completed short-context and 32K shared-prefix scenarios, and emitted metrics. The logs confirmed that FlashInfer was actually selected; the NVFP4 run also completed FlashInfer autotuning using an `sm110` cache path.

Preliminary single-run results (`n=1`, concurrency 1):

| Precision | Backend | 2K input / 128 output | 32K prefix + 2K input / 1K output |
|---|---:|---:|---:|
| FP8 | FlashInfer | 49.20 tok/s | 43.21 tok/s |
| FP8 | Triton | 48.21 tok/s | 31.40 tok/s |
| NVFP4 | FlashInfer | 61.37 tok/s | 54.38 tok/s |
| NVFP4 | Triton | 59.74 tok/s | 42.26 tok/s |

FlashInfer and Triton were close for the short scenario, but FlashInfer provided substantially higher output throughput for the long-prefix scenario:

- FP8: approximately **+37.6%**
- NVFP4: approximately **+28.7%**

For FP8 long-prefix, TTFT improved from 5.28 s with Triton to 2.69 s with FlashInfer. Inter-token latency improved from 26.58 ms to 20.45 ms. NVFP4 showed a similar ITL improvement, from 20.69 ms to 15.66 ms.

This indicates that the current backend restriction is too narrow for the tested SM110/Qwen3.6 path. It does not establish that every FlashInfer operation is supported on SM110, but rejecting this configuration at registry validation prevents a path that works in our testing and performs materially better for long-prefix inference.

Would you accept a change enabling the FlashInfer backend for hybrid-GDN models on SM110—preferably behind an explicit capability check rather than an `is_sm120` special case—together with SM110 coverage?
