## 正文

## Motivation

`deep_compare` in `python/sglang/srt/layers/quantization/quark/utils.py` decides whether two Quark layer quant configs are the same. Its list branch compares them as sets:

```python
elif isinstance(dict1, list):
    return set(dict1) == set(dict2)
```

That is wrong three ways:

**1. A quark config list can hold dicts, and dicts are unhashable.**

```
>>> deep_compare({"weight": {"hints": [{"dtype": "mx_fp4"}]}},
...              {"weight": {"hints": [{"dtype": "fp8_e4m3"}]}})
TypeError: cannot use 'dict' as a set element (unhashable type: 'dict')
```

**2. Order is dropped, so two different block shapes compare equal.**

```
>>> deep_compare({"block_size": [1, 128]}, {"block_size": [128, 1]})
True
```

**3. Duplicates collapse, so two different lengths compare equal.**

```
>>> deep_compare({"shape": [128, 128]}, {"shape": [128]})
True
```

2 and 3 are the ones that matter, because `deep_compare` is exactly what guards the "these have to match" checks in `quark.py`:

| call site | what it guards |
|---|---|
| `quark.py:594` | every kv_cache layer in `kv_cache_group` uses the same quantization |
| `quark.py:856` | all shards of a fused module (q/k/v, gate/up) agree |
| `quark.py:926` | per-shard configs agree |
| `quark.py:1058` | the MoE config matches the shared-expert config |

A false match there does not raise — it loads the layer with a config that does not describe its checkpoint.

The same function in vLLM (`vllm/model_executor/layers/quantization/quark/utils.py`) walks the list element by element and carries the comment *"`dict1` may be a list of dict"*, so this copy diverged from the version it was ported from.

## Modifications

```python
elif isinstance(dict1, list):
    # A quark config list may hold dicts, which are unhashable, and its
    # order is meaningful (a block shape [1, 128] is not [128, 1]), so
    # compare element by element rather than as sets.
    return len(dict1) == len(dict2) and all(
        deep_compare(item1, item2) for item1, item2 in zip(dict1, dict2)
    )
```

The explicit length check is stricter than vLLM's version, which uses `range(len(dict1))` and so returns `True` when `dict1` is a prefix of `dict2`.

Tests: `TestDeepCompare` added to `test/registered/unit/layers/quantization/test_quark_utils.py` (the existing CPU-only file for this module), covering all three cases above plus the equal-config path and the scalar / key / type mismatches.

I cannot run the sglang test suite locally (the package needs the CUDA wheels), so I verified the new implementation by executing the function in isolation against the same eight cases the unit test asserts — all pass, and cases 1-3 fail on current `main`.

## Accuracy Tests

No numerics change. The only behavior change is that configs which previously compared equal by accident (different order, different length) now compare unequal, which makes the existing `ValueError`s in `quark.py` fire when they should, and that a list of dicts no longer raises `TypeError`.

## Speed Tests and Profiling

Not applicable — config parsing at load time, on lists of a handful of elements.

### haosenwang1018 · 2026-09-23

Adding the concrete configuration, which I should have led with.

**Who hits it:** any AMD Quark checkpoint whose per-layer quant config contains a list. Two shapes matter:

1. A list of dicts anywhere in the config (the upstream vLLM copy of this function carries the comment "`dict1` may be a list of dict"). `set()` on that raises `TypeError: cannot use 'dict' as a set element` while resolving the layer's scheme, so the server fails during model load rather than reporting a config mismatch.

2. A list whose order or length carries meaning — a block shape such as `[1, 128]`. `set([1,128]) == set([128,1])`, so `deep_compare` reports two different block shapes as the same config. That one does not raise; it makes the four `ValueError` guards in `quark.py` (`:594` kv_cache group, `:856` fused-shard, `:926` per-shard, `:1058` MoE vs shared expert) pass when they should fire, and the layer is then built with a scheme that does not match its checkpoint.

Shape 2 is the reason I think this is worth fixing rather than leaving: it is silent.

I cannot run the SGLang test suite locally (the package needs the CUDA wheels), so the added unit tests are written against the CPU-only file that already exists for this module, and I verified the new implementation by executing the function standalone against the same cases the tests assert.
