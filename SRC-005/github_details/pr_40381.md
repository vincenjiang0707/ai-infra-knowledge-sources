# [PR #40381] [XPU] Enable GGUF Q4_K inference for Qwen3.5-family and Gemma4

## 正文

## Motivation

This PR introduces the first GGUF inference path for Intel XPU in upstream SGLang, without depending on the llm-scaler ESIMD extension. The implementation converts GGUF Q4_K weights at load time into the W4A16 representation already supported by `sglang-kernel-xpu`. The quantized execution path is XPU-gated, while the supporting model and loader changes touch shared Python code and therefore need cross-backend CI review.

This PR remains a draft while required upstream CI and maintainer review are in progress.

## Modifications

- Add Intel XPU GGUF linear and embedding quantization methods.
- Repack GGUF Q4_K weights into the existing XPU W4A16 layout.
- Add a hybrid GGUF MoE path:
  - Q4_K gate/up uses the XPU W4A16 grouped GEMM.
  - Q5_K/Q6_K/Q8_0 down projections are dequantized once at load time and use the native BF16 grouped GEMM.
- Add GGUF tensor-name mappings for Qwen3.5-family and Gemma4 models.
- Add Qwen GDN GGUF layout conversion and fused-shard loading support.
- Add quantization-aware Gemma4 embedding and tied LM-head handling, with a non-GGUF regression test.
- Reuse the standard colocated GGUF sidecar discovery: `config.json`, tokenizer files, and a safetensors index or shards live beside the GGUF file. No XPU-specific environment variable is introduced.
- Add focused CPU tests, CI registrations, and user-facing XPU GGUF documentation.

No new ESIMD kernel is introduced. Native Q4_K and decode-specific kernel optimization will be handled separately in `sgl-kernel-xpu`.

## Accuracy Tests

Hardware validation scope: Intel XPU only. CUDA, ROCm, and other accelerator backends were not run locally because those devices are not available in the test environment. Cross-backend regression coverage therefore relies on upstream CI and maintainer validation.

Validated with tokenizer-enabled OpenAI chat requests on two Intel XPU cards with TP=2. Natural-language responses were semantically correct for all five checkpoints:

- Qwen3.6-27B Q4_K_M
- Qwen3.8-27B UD-Q4_K_M
- Qwen3.6-35B-A3B UD-Q4_K_M
- Gemma4-31B-it Q4_K_M
- Gemma4-26B-A4B-it UD-Q4_K_M

After rebasing onto current `main`, Qwen3.8-27B was revalidated using only colocated sidecar files (no custom GGUF environment variables). The OpenAI chat endpoint returned a semantically correct Chinese answer.

## Speed Tests and Profiling

Single-request streaming decode, TP=2, temperature=0, 64 output tokens. Steady-state values use runs 2-3.

| Model | TTFT | E2E | Decode throughput |
|---|---:|---:|---:|
| Qwen3.6-27B Q4_K_M | 0.207 s | 5.592 s | 11.70 tok/s |
| Qwen3.8-27B UD-Q4_K_M | 0.206 s | 5.493 s | 11.92 tok/s |
| Qwen3.6-35B-A3B UD-Q4_K_M | 0.174 s | 4.804 s | 13.61 tok/s |
| Gemma4-31B-it Q4_K_M | 0.138 s | 4.199 s | 15.51 tok/s |
| Gemma4-26B-A4B-it UD-Q4_K_M | 0.113 s | 3.395 s | 19.20 tok/s |

Latest-upstream Qwen3.8-27B smoke test (TP=2): 124.28 s weight load, 21.41 GB/card, and 128 forced output tokens in 10.62 s (12.05 tok/s end-to-end, including prefill). The first request after startup incurred about 30 s of Triton GDN JIT compilation; precompilation and native kernel work remain follow-ups.

Qwen hybrid GDN models currently require `--disable-radix-cache` on the Intel XPU attention backend because XPU uses a paged KV cache while the upstream no-buffer Mamba radix-cache strategy requires page size 1. This is documented and intentionally not addressed by changing shared cache policy in this GGUF PR.
