# [Bug] DFLASH draft layout is assumed, not validated: anchor-first checkpoints shift every position silently

### Summary

`DFLASH` draft checkpoints carry an implicit block-layout convention, and SGLang assumes
one of the two conventions in common use without checking which one a checkpoint was
trained with. A checkpoint trained with the *anchor-as-first-prediction* layout — where
every position in the block predicts — is served without any error and produces draft
tokens shifted by one position. The server reports healthy; acceptance collapses to
roughly `1.0` (only the anchor/bonus token survives).

Isolated on a Qwen3.8-Flash-Next (`Qwen4Exp`) target with the official DeepSpec drafter
`dflash_block7_qwen38_flash_next` on 8×A800 (SM80): **accept length @ 4-token window =
1.0621** over 47,411 verify steps. The same checkpoint's card reports a *served* accepted
length of **2.7562 at block 4** and **2.9837 at its native block 7** under vLLM, where the
layout it was trained for is honoured. No warning, no assertion here — the service starts
and answers normally, at a fraction of that acceptance.

### The two conventions

| | anchor-as-first-prediction | 1+N (SGLang's assumption) |
|---|---|---|
| block positions | all `K` positions predict | position 0 is the seeded anchor/bonus token; positions `1..N` are the drafts |
| marker, when present | `sample_from_anchor: true` | `sample_from_anchor: false` |
| drafter | DeepSpec `dflash_block7_qwen38_flash_next` | speculators-format drafts |

The marker is a **speculators** config field (`DFlashSpeculatorConfig.sample_from_anchor`,
default `False`; `DSparkSpeculatorConfig` defaults `True`). The convention also determines the
token count: `False` → `block_size - 1` speculative tokens, `True` → `block_size`.

**It is not a reliable discriminator across the ecosystem, which is part of the problem.**
The official anchor-first checkpoint above carries **no `sample_from_anchor` field at all** —
neither top-level nor inside its `dflash_config`; its config exposes `num_anchors: 512` and
nothing else about the layout. So a marker-based check would read the sglang default and wave
exactly the checkpoint that mis-serves through.

**But the layout *is* declared — under a name SGLang does not read.** The upstream serving repo
ships a config override (the README notes the checkpoint's own `config.json` "does not carry the
`dflash_config` block the engine reads"). That override's `dflash_config` contains:

```json
"dflash_config": {
  "target_layer_ids": [3, 15, 23, 35, 43],
  "mask_token_id": 248077,
  "use_aux_hidden_state": true,
  "causal": false,
  "query_zero_predicts_next": true
}
```

`query_zero_predicts_next: true` is a direct, explicit statement of the anchor-first convention.
SGLang's `DFlashDraftConfig` (`speculative/dflash_utils.py:529-548`) has no field for it and
`parse_dflash_draft_config` never reads it — a tree-wide search for the identifier returns zero
hits. So the declaration exists, is unambiguous, and is silently dropped.

> **Inference, not a confirmed contract.** I am reading `query_zero_predicts_next` as "the
> query at position 0 predicts the token *after* the anchor", i.e. the anchor-first layout —
> that is what the field name says and it is consistent with the extra `block_size`-th
> prediction the layout implies, but I have not verified it against the trainer source and am
> labelling it as a hypothesis rather than a spec. If the maintainers confirm the field's
> meaning, a check on it is the natural fix; if not, the layout still has to be established
> some other way. It should not be shipped as a hard gate on my reading alone.

### Where SGLang assumes 1+N

`DFlashWorkerV2` slices the draft's hidden states to drop position 0:

```python
# python/sglang/srt/speculative/dflash_worker_v2.py:158-160
# draft tokens are block positions 1: (pos 0 is the seeded bonus token)
bs = hidden_states.shape[0] // self.block_size
hs = hidden_states.view(bs, self.block_size, -1)[:, 1:, :].reshape(
    -1, hidden_states.shape[-1]
)
```

The same slice appears in the in-worker draft path (`dflash_worker_v2.py:278`,
`# pos 0 = anchor`) and in the selector path (`:1378`, `:2572`).

A checkpoint trained anchor-first produces `K` meaningful predictions per block, but only
`K-1` of them are read, and each one is read from the *wrong* slot — a uniform off-by-one
across every draft position.

### The layout field is already parsed — just not for this

`dflash_utils.py` already reads `sample_from_anchor` off the draft config:

```python
# python/sglang/srt/speculative/dflash_utils.py:504-507
sample_from_anchor = dflash_config.get(
    "sample_from_anchor", _cfg_get(config, "sample_from_anchor", True)
)
return sample_from_anchor is False
```

Two things follow from that snippet. First, the field is already parsed at config-parse time.
Second, **its default is inverted for this purpose**: `_cfg_get(..., True)` reads the sglang
default as `True`, but the speculators default for the DFlash family is `False`. So "absent"
means *opposite* things to the two sides, which is why absence cannot be treated as safety.

Today the read is confined to `is_nemotron_35_draft_config` (`dflash_utils.py:470`), and even
there it is one of six conjunctive conditions identifying one specific published checkpoint —
it is not a general layout gate. The value is available on the DFLASH path and simply not
consulted there.

### Suggested fix (fail fast, matching vLLM)

vLLM's DFlash speculator raises on this exact layout
(`ValueError: sample_from_anchor=True is not supported for DFlash`). SGLang currently does
something worse than raising: it serves, silently, at ~1.0 acceptance.

Three options, in increasing order of how much they depend on my unverified reading above:

1. **Minimal, no inference needed for the check itself:** fail fast on the checkpoints that *do*
   declare a layout — anything SGLang can currently see (`sample_from_anchor` where present).
   Wiring up `query_zero_predicts_next` would extend this to the official checkpoint, but **that
   rests on my unverified reading of the field (hypothesis, see above) — it should only be
   treated as a gate once the semantics are confirmed.** As it stands this option would not have
   caught the official checkpoint, because SGLang reads neither field today; it is a strict
   improvement over the current state and commits to nothing uncertain.
2. **Require an explicit declaration** on the DFLASH draft config going forward, and refuse to
   serve a checkpoint that omits it. Catches everything, including this checkpoint — at the
   cost of breaking checkpoints that are in the wild today.
3. **Honour the layout** — read all `K` positions when the checkpoint is anchor-first. The most
   useful outcome, and a bounded change at the four slice sites above, but it is downstream of
   the layout actually being established.

Either way the checkpoint stops being served at a wrong-but-plausible acceptance rate.

The design constraint worth flagging: **an explicit check on `sample_from_anchor` alone would
not have caught this checkpoint** — it declares neither that field nor `speculative_tokens`
(the identifier does not appear anywhere in its config). Whatever is chosen has to *establish*
the layout rather than default it.

Two things I'd be glad to be corrected on: whether `query_zero_predicts_next` means what I read
it to mean, and whether there is a better discriminator for layout than anything proposed here
— I've only looked at one checkpoint family and would rather defer to the maintainers than guess.

### Reproduction

**Prerequisite:** this needs the Qwen4-Exp capture guard from **#38642** (rebased onto current
main). On bare main the Qwen4-Exp DFLASH path never reaches the draft at all — the server dies
during decode CUDA-graph capture (`ValueError: too many values to unpack (expected 2)`, see
#38589). With the guard, the server comes up and the numbers below reproduce.

SM80 (8×A800), main + #38642, official DeepSpec drafter, `--speculative-num-draft-tokens 4`:

```bash
python3 -m sglang.launch_server \
  --model-path <Qwen3.8-Flash-Next target> \
  --speculative-algorithm DFLASH \
  --speculative-draft-model-path <DFlash2 draft, block 4, 24 heads, taps [1,7,14,20,26,32,39,45]> \
  --speculative-num-draft-tokens 4 --tp 8 \
  --cuda-graph-max-bs-decode 8 --mem-fraction-static 0.85
```
(8xA800 SM80, driver 550.144.03, torch 2.11.0+cu130. On SM80 the tilelang/nvcc header
check also needs `NVCC_PREPEND_FLAGS=-DCCCL_DISABLE_CTK_COMPATIBILITY_CHECK`.)

Note that `--speculative-num-draft-tokens 4` is not a free choice here: Qwen4-Exp's QSA
caps the window at its compression ratio
(`layers/attention/qwen_sparse_attn_backend.py:240`, `_require_chain_speculation`), so a
`block_size=7` checkpoint cannot even be launched at its training block size.

### Measured acceptance (4-token window)

| concurrency | requests | failures | accept length | accept rate |
|---|---|---|---|---|
| 8 | 300 | 0 | **1.0621** | 0.0184 |
| 24 | 300 | 0 | 1.0643 | 0.0190 |
| 48 | 300 | 0 | 1.0629 | 0.0186 |

An earlier independent run at concurrency 8 gave 1.0604 (47,377 steps), i.e. run-to-run spread
at fixed concurrency is ~0.002.

Per-position, pooled over 47,411 verify steps (concurrency 8):

| position k | P(accept at k \| prefix matched) | P(accept length ≥ k) |
|---|---|---|
| 1 | 0.0497 | 0.0497 |
| 2 | 0.1024 | 0.0051 |
| 3 | 0.3485 | 0.0018 |

95.0% of verify steps accept **zero** draft tokens; the bottleneck is position 1. The
6×-concurrency sweep moves accept length by <0.4%, so this is steady-state behaviour, not
a load artifact.

### Related

- #38589 — the sibling report on this target: Qwen4Exp cannot emit DFlash aux hidden
  states at all. That is a prerequisite failure; this one is what remains once a drafter
  *can* be served.
- Same shape of problem, one layer down: the block-size mismatch between a draft's training
  `block_size` and the served `--speculative-num-draft-tokens` is warned about
  (`dflash_worker_v2.py:468`) and then silently forced (`:472`). DFLASH's convolution
  indexes by `position % block_size`, so a mismatch shifts positions too. Fail-fast there
  would have caught this class of problem earlier.

Happy to test either fix on the SM80 rig.
