### Describe the bug


## 1. Problem

When enabling `--kv-cache-dtype fp8_e4m3` on Hopper (H200, SM90) with the fa3 backend, **decoding slows down** compared to BF16 KV-cache, especially on small batches and short contexts. The slowdown is caused by **runtime overhead** that is absent on the BF16 path and that is **not eliminated by a static FP8 checkpoint**.

The root cause is architectural: sglang performs FP8 KV-cache quantization as a series of **separate Python-level tensor operations** (multiple kernel launches per layer per step), whereas the BF16 path is a single optimized `store_cache` call. On memory-bound decode with small batches, this overhead outweighs the 2× reduction in KV read traffic.

### Symptom

| Scenario | BF16 KV | FP8 KV (fa3) |
|----------|---------|---------------|
| Small batch (1-8), short context | baseline | **10-30% slower** |
| Small batch, long context (32K+) | baseline | possibly faster |
| Large batch (128+) | baseline | slightly faster |

## 2. Bottlenecks & comparison with vLLM

### 2.1. Bottleneck 1: Unfused K/V quantization on cache write

In [`set_kv_buffer`](https://github.com/sgl-project/sglang/blob/bc82b064004f2e17f09db52afeed52cdf53a87be/python/sglang/srt/mem_cache/memory_pool.py#L1784), quantizing K/V to FP8 is **3-4 separate operations**:

```python
# memory_pool.py:1784-1790 — 4 separate kernel launches per layer per step
if cache_k.dtype != self.dtype:
    if k_scale is not None:
        cache_k.div_(k_scale)      # launch 1: in-place divide K
    if v_scale is not None:
        cache_v.div_(v_scale)      # launch 2: in-place divide V
    cache_k = cache_k.to(self.dtype)  # launch 3: cast K → FP8
    cache_v = cache_v.to(self.dtype)  # launch 4: cast V → FP8
```

This is followed by a separate `store_cache` call to write into the paged cache. On the BF16 path, only `store_cache` runs (single optimized kernel).

**vLLM solution:** vLLM fuses quantization **into the cache-write kernel** itself. In [`reshape_and_cache_kernel_flash`](https://github.com/vllm-project/vllm/blob/26ff616bbf43c5c5ecb847589705cebdbff46706/vllm/v1/attention/ops/triton_reshape_and_cache_flash.py#L109), the division by scale and the implicit FP8 cast happen inside the same triton kernel that stores to the paged cache:

```python
# vLLM: 1 kernel launch — load → divide → implicit cast → store
if FP8_KV_CACHE:
    key_tile = key_load if key_load.dtype.is_fp8() else key_load / tl.load(k_scale)
else:
    key_tile = key_load
# ...
tl.store(key_cache_ptr + tgt_idx_k, key_tile, mask=...)  # implicit cast to FP8
```

### 2.2. Bottleneck 2: Per-layer Q→FP8 conversion in fa3 backend

In `forward_decode`, Q is converted to FP8 **on every layer, every step**:

```python
# flashattention_backend.py:1608-1615 — 3 conversions per layer per step
if self.kv_cache_dtype_str != "auto" and layer.head_dim <= 256:
    if layer.k_scale is not None:
        descale_shape = (forward_batch.batch_size, layer.tp_k_head_num)
        k_descale = layer.k_scale.expand(descale_shape)
        v_descale = layer.v_scale.expand(descale_shape)
    q = q.to(self.kv_cache_dtype)              # conversion 1: Q → FP8
    q_rope = q_rope.to(self.kv_cache_dtype)    # conversion 2: q_rope → FP8
    k_rope = k_rope.to(self.kv_cache_dtype)    # conversion 3: k_rope → FP8
```

For a model with ~64 layers, this is **64+ × 3 = ~192 `.to()` launches** per forward pass. Each `.to()` has ~2-5μs launch overhead → **~400-1000μs of pure launch overhead** per decode step, comparable to the entire attention computation on small batches.

**vLLM solution:** vLLM quantizes Q **centrally in the Attention layer** (once), not in each backend. In `Attention.forward`, a single `query_quant` call handles it, and crucially it **fuses with preceding ops via `torch.compile`**:

```python
# vLLM attention.py:511-521 — single quantization, fused via torch.compile
if self.query_quant is not None:
    # quantizing with a simple torch operation enables
    # torch.compile to fuse this into previous ops
    # which reduces overheads during decoding.
    if self.impl.supports_quant_query_input:
        query, _ = self.query_quant(query, self._q_scale)
```

### 2.3. Bottleneck 3: fa3 FP8 decode kernel less optimized than BF16

FA3 split-KV decode with FP8 Q × FP8 KV is a less-tuned path than the primary BF16 path. The `num_splits=0` auto-heuristic `flashattention_backend.py:345` adds a combine-stage overhead.

**vLLM flashinfer on SM90:** completely avoids Q quantization on decode via `resolve_query_dtype` — uses **BF16 Q × FP8 KV** (descale on read), which is both faster and more accurate (single quantization error on KV only).

### 2.4. Tabular comparison: sglang vs vLLM

| Operation | sglang (fa3) | vLLM (flash_attn) | vLLM (flashinfer SM90) |
|-----------|-------------|-------------------|------------------------|
| **Q → FP8 conversion** | ❌ `q.to()` per layer (192+ launches) | ⚠️ `query_quant` once, **fused via torch.compile** | ✅ None (BF16 Q) |
| **q_rope → FP8** | ❌ per layer | ✅ None (handled in kernel) | ✅ None |
| **k_rope → FP8** | ❌ per layer | ✅ None (handled in kernel) | ✅ None |
| **K ÷ scale** | ❌ separate `div_` launch | ✅ **fused in write kernel** | ✅ **fused in write kernel** |
| **V ÷ scale** | ❌ separate `div_` launch | ✅ **fused in write kernel** | ✅ **fused in write kernel** |
| **K → FP8 cast** | ❌ separate `.to()` launch | ✅ implicit cast in `tl.store` | ✅ implicit cast in kernel |

| **Kernel launches for K/V write** | **~5** | **1** | **1** |
| **Attention compute** | FP8 Q × FP8 KV | FP8 Q × FP8 KV (descale params) | **BF16 Q × FP8 KV** (descale on read) |
| **Accuracy** | ❌ double quant error (Q+KV) | ❌ double quant error | ✅ single quant error (KV only) |

## 3. Proposed changes

### 3.1. Fuse K/V quantization into the cache-write kernel (high impact)

**Goal:** eliminate the 4 separate `div_` + `.to()` launches in `set_kv_buffer`.

**Approach:** extend the existing `store_cache` JIT kernel (or add a triton variant) to accept `k_scale`/`v_scale` and the target dtype, performing the division + cast **inside** the write kernel — exactly as vLLM does in `reshape_and_cache_kernel_flash` .

```python
# Proposed: single fused kernel call instead of div_ + to() + store_cache
store_cache_fp8(
    k, v,
    self.k_buffer[layer_id],
    self.v_buffer[layer_id],
    loc,
    k_scale=k_scale,   # passed into kernel, division fused
    v_scale=v_scale,
    out_dtype=self.dtype,  # FP8 — implicit cast on store
)
```

**Expected benefit:** reduces ~5 kernel launches to 1 per layer per step. On a 64-layer model, this removes ~256 launches per decode step.

**Affected files:**
- `memory_pool.py` — `set_kv_buffer`, `set_kv_buffer_prefix_valid` (line 1877), and the SWA variant (line 2234)
- `sglang/jit.kernel/kvcache` — extend `store_cache` or add `store_cache_fp8`

### 3.2. Centralize Q quantization and enable torch.compile fusion (high impact)

**Goal:** eliminate per-layer `q.to(FP8)` / `q_rope.to(FP8)` / `k_rope.to(FP8)` in `forward_decode` and `forward_extend` in flashattention_backend.py.

**Approach:** move Q quantization out of the backend into the RadixAttention layer (as vLLM does in `Attention.forward` - model_executor/layers/attention/attention.py:511, so it happens **once** and can be **fused with preceding ops** (RoPE, QKV projection) via torch.compile:

```python
# Proposed: in RadixAttention.forward, before calling backend
if self.kv_cache_dtype_str != "auto" and self.supports_quant_query_input:
    # single quantization, fusable with prior ops via torch.compile
    q, _ = scaled_fp8_quant(q, self.q_scale)
    # q_rope / k_rope handled inside the attention kernel, not here
```

Then the fa3 backend receives already-quantized Q and does **no** `.to()` calls.

**Expected benefit:** removes ~192 `.to()` launches per decode step on a 64-layer model; enables compiler fusion.

**Affected files:**
- `flashattention_backend.py` — remove `q.to()` / `q_rope.to()` / `k_rope.to()` from `forward_decode` and `forward_extend`
- RadixAttention layer — add centralized `query_quant`

---

## Summary

The FP8 KV-cache decode slowdown in sglang is caused by **unfused runtime quantization** — separate `div_` + `.to()` launches for K/V and per-layer `q.to(FP8)` conversions. vLLM avoids most of this overhead by (1) fusing K/V quantization into the cache-write kernel and (2) centralizing Q quantization in the Attention layer where it fuses with preceding ops via torch.compile. On SM90, vLLM's flashinfer further avoids Q quantization entirely on decode (BF16 Q × FP8 KV).

The proposed changes would bring sglang's FP8 KV-cache path closer to vLLM's efficiency, with the fused write kernel (3.1) and centralized Q quantization (3.2) providing the largest gains.

### waynehacking8 · 2026-07-12

Datapoint from SM120 (RTX PRO 6000, CUDA 13, main 96a04cb): the write-path overhead is backend-independent -- it sits in memory_pool.py before any attention backend -- and a torch.profiler census of one MHA set_kv_buffer call at bs=1 decode shape (1 token, 8 kv heads x 128) shows exactly the structure you describe: bf16 = 1 kernel (the fused store_kvcache), fp8_e4m3 with k/v scales = 5 kernels (2x in-place div, 2x dtype cast, then the store), and synchronized per-call time goes 35us -> 103us (min-of-medians over 5x400 calls; the scale-less variant is 3 kernels / 62us). Multiplied by layer count that's ms-scale extra launch work per decode step at bs=1, which lines up with the 10-30% you measured on H200. I also ran a bs=1 end-to-end A/B (Qwen2.5-1.5B, bench_one_batch, kv auto vs fp8_e4m3) but this box is shared and the run-to-run spread swamped any delta, so I won't cite those numbers -- the census is the reliable part.
