# [PR #40453] [Model Loader] Add InstantTensor loader support

## 正文

## Motivation

Add [InstantTensor](https://github.com/scitix/InstantTensor) as an optional high-performance loader for Safetensors checkpoints.

InstantTensor supports distributed weight loading and pipelined prefetching. This integration lets users select it with `--load-format instanttensor` while preserving SGLang's existing checkpoint discovery and model-loading flow.

It has already been integrated into several other projects, such as vLLM. https://docs.vllm.ai/en/latest/models/extensions/instanttensor/

## Modifications

- Add `instanttensor` to the supported load formats and CLI choices.
- Add an InstantTensor weight iterator based on `instanttensor.safe_open`.
- Reuse the existing Safetensors file discovery, shard index filtering, and checkpoint selection logic.
- Pass SGLang's initialized device process group to InstantTensor for distributed loading.
- Support tuning through `--model-loader-extra-config`: `buffer_size`, `chunk_size`, `concurrency`, `io_depth`, `max_free_mem_usage`, and `backend`.
- Convert JSON backend names or ordered candidate lists to InstantTensor backend/policy enums. Reject unknown configuration keys and keep framework, device, process group, and tensor-copy behavior managed by SGLang.
- Add the optional `sglang[instanttensor]` dependency with `instanttensor>=0.1.9` to support these tuning options.
- Document installation, server startup, and tuning options, including environment-variable precedence.
- Extend `SRTRunner` to select the load format and pass extra loader configuration in model-loading tests.
- Add CPU unit tests and a GPU output-consistency test covering both default and explicitly configured InstantTensor loading.

### Configuration example

```bash
pip install "sglang[instanttensor]"

python -m sglang.launch_server \
  --model-path Qwen/Qwen3.5-4B \
  --load-format instanttensor \
  --model-loader-extra-config '{"backend":"MMAP","chunk_size":4194304,"concurrency":2,"io_depth":2,"max_free_mem_usage":0.25}'
```

Explicit non-null options override the corresponding `INSTANTTENSOR_*` environment variables. Omitted or `null` options retain InstantTensor's environment-variable and automatic defaults. Backend names are case-sensitive; an ordered list such as `{"backend":["URING","AIO"]}` selects the first available candidate.

## Accuracy Tests

### CPU unit tests

The InstantTensor-specific suite passes all 8 tests:

```text
Ran 8 tests in 0.010s
OK
```

These tests cover JSON configuration forwarding to `safe_open`, backend name conversion and invalid values, null options, rejection of unknown and SGLang-managed options, isolation from other load formats, current-device and process-group forwarding, non-distributed loading, missing dependency diagnostics, and reuse of Safetensors checkpoint discovery. InstantTensor and CUDA/distributed state are mocked to keep these unit tests CPU-only.

The broader regression run also includes the existing default-loader and checkpoint-prefetch suites:

```text
32 passed, 19 subtests passed
```

This consists of 8 InstantTensor tests, 2 default-loader tests, and 22 prefetch tests; it is not a count of real-model loading runs. All applicable pre-commit checks also passed.

### GPU generation consistency

Tested `Qwen/Qwen3.5-4B` on one RTX 3090 with PyTorch 2.13.0 and InstantTensor 0.1.9. The test compares a Safetensors baseline against both InstantTensor's default configuration and the explicit configuration shown above, using FP16 inference:

```text
Ran 1 test in 173.586s
OK
```

Both InstantTensor configurations produced identical generated text to the Safetensors baseline. The maximum differences in prefill and decode log probabilities were both zero. This is an output-consistency test, not a byte-for-byte comparison of the final model parameters or a loading-speed benchmark.

### Previously validated serving configurations

The original end-to-end serving validation also covered:

- Qwen3-30B-A3B, TP1
- DeepSeek-R1, TP8+EP8

For every configuration, Safetensors and InstantTensor produced the same response and token IDs.

### YitaoYuan · 2026-09-21

@shuwang21 
vLLM and SGLang share an almost identical loading pipeline. In our tests, the two achieve the same loading speed — it only depends on the choice of backend. We recently reran the benchmark on another platform, where the overall bandwidth was lower but the tail IO latency was also lower than in our earlier tests, which to some extent narrows the gap between the baselines. We used the latest versions of all baselines. Here are the results based on the **latest version of SGLang**:

| Model | Load format | TP | Weight loading time | 
|---|---|---:|---:|
| Qwen3.5-35B-A3B | Safetensors | 1 | 139.97 s | 
| Qwen3.5-35B-A3B | FastSafetensors | 1 | 49.34 s | 
| Qwen3.5-35B-A3B | RunAI Model Streamer | 1 | 7.09 s | 
| Qwen3.5-35B-A3B | InstantTensor | 1 | 6.73 s | 
| Qwen3.5-35B-A3B | Safetensors | 2 | 125.56 s | 
| Qwen3.5-35B-A3B | FastSafetensors | 2 | 32.93 s | 
| Qwen3.5-35B-A3B | RunAI Model Streamer (distributed) | 2 | 6.96 s | 
| Qwen3.5-35B-A3B | InstantTensor | 2 | 6.91 s | 

Note that although Runai achieves performance comparable to InstantTensor, it uses ~40 GB of memory per process — far more than InstantTensor. Since this was an ad-hoc test, we didn't cover larger scales this time (e.g., 8 GPUs); at larger scales the gap between InstantTensor and the baselines becomes even more pronounced.

By the way, I've updated the PR description directly, and it now includes our previous full comparison. The code will be updated within a day to add the extra parameter passing.
