# Fix Quark block-FP8 loading in DeepSeek loader

## Summary

Enable `amd/GLM-5.3-Quark-MXFP4-AttnFP8` (`GlmMoeDsaForCausalLM`) on
SGLang/ROCm by completing the DeepSeek-family weight-loading path for Quark
checkpoints that combine:

- globally quantized OCP MXFP4 experts; and
- explicitly configured block-FP8 attention linears.

SGLang PR #38546 already provides the shared Quark `layer_quant_config`
resolution and block-FP8 linear/MoE dispatch. It also handles scale names in
the `glm5_next.py` loader used by GLM-5.3-Flash. 

However, the non-Flash `GlmMoeDsaForCausalLM` architecture instead loads through
`DeepseekV2WeightLoaderMixin`, where three compatibility gaps remained.

## Bug

### Quark block-scale parameter name

Quark serializes block-FP8 scales as:

```text
*.weight_scale
```

The shared `Fp8LinearMethod` registers the corresponding runtime parameter as:

```text
*.weight_scale_inv
```

Consequences in the DeepSeek loader included missing parameters for ordinary
attention projections and fused `q_a_proj + kv_a_proj_with_mqa` scales.
MXFP4 scales cannot be renamed unconditionally because they legitimately use
`weight_scale`.

Reproduced on SGLang `main` without this change:

```text
Scheduler hit an exception:
  File "sglang/srt/models/deepseek_common/deepseek_weight_loader.py",
       line 464, in do_load_weights
    param = params_dict[param_name]
KeyError:
  'model.layers.0.self_attn.fused_qkv_a_proj_with_mqa.weight_scale'
```

The runtime parameter at that point is
`fused_qkv_a_proj_with_mqa.weight_scale_inv`; the checkpoint name has already
been fused correctly, but its Quark scale suffix has not been adapted.

### Fused indexer scale classification

`_load_fused_indexer_wk()` recognized only the `_inv` suffix as a scale. A
Quark `weight_scale` tensor could therefore be treated as a projection weight.
This is a silent-corruption path rather than a guaranteed startup failure.

### MLA absorption used the global configuration

`post_load_weights()` derived `kv_b_proj` block geometry from the global
quantization configuration. For this mixed checkpoint, the global configuration
is MXFP4 and does not describe the block-FP8 `kv_b_proj`. The exact scheme is
already available on `kv_b_proj.quant_method`.

## Changes

### `deepseek_weight_loader.py`

1. Add `_resolve_quark_fp8_block_scale_name()`.
   - Rewrite `weight_scale` to `weight_scale_inv` only when the original
     parameter is absent and the `_inv` parameter exists.
   - Genuine MXFP4 `weight_scale` parameters remain unchanged.
2. Apply the alias after fused QKV-A name resolution and in the ordinary
   parameter-loading fallthrough.
3. Recognize both `weight_scale` and `weight_scale_inv` in the fused indexer
   path.
4. Add `_resolve_layer_weight_block_size()`.
   - Prefer the constructed layer's resolved quantization method.
   - Retain the existing config-level fallback for compatibility.
5. Use the resolved per-layer block size for MLA absorption and UE8M0 handling.

No model-name or checkpoint-name gate is added. The compatibility behavior is
driven by the registered parameter and resolved quantization method.

## GLM-5.3-Flash regression validation

`amd/GLM-5.3-Flash-Quark-MXFP4` was also tested to verify that deriving MLA
block geometry from the resolved `kv_b_proj.quant_method` does not regress the
Flash path.

Current `main` loaded all 62 shards successfully, then failed during decode
graph capture in the independent CUDA-only `IndexerKPool` path:

```text
NotImplementedError: kpool indexer is only supported on CUDA
```

The loader change was therefore also applied to the ROCm Flash support branch
(`amd_glm5.3_flash` at `2fa010a4fb`), which contains the ROCm k-pool
implementation used by the validated Flash deployment.

Observed on 4× MI355X:

- all 62 shards loaded;
- decode graphs captured;
- health endpoint returned HTTP 200;
- internal chat-completion warm-up returned HTTP 200; and
- no missing-scale or loader errors were observed.

GSM8K via `benchmark/gsm8k/bench_sglang.py`, 400 questions:

```text
Accuracy:          0.920
Invalid:           0.000
Latency:           74.894 s
Output throughput: 497.087 token/s
```

This benchmark invocation is not directly comparable to the model card's
thinking-enabled `sgl-eval` recipe, but it provides a focused before-merge
serving and generation regression check.

### Flash performance A/B

The concurrency benchmark was repeated on the same support-branch revision,
hardware, checkpoint, and launch configuration with only this loader change
removed. Workload: random 8,192 input tokens and 1,024 output tokens.

| Concurrency | Baseline total tok/s | With fix total tok/s | Delta | Baseline median E2E | With fix median E2E | Delta |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 1,978.39 | 1,972.94 | -0.28% | 9,318.61 ms | 9,325.65 ms | +0.08% |
| 4 | 3,631.30 | 3,625.18 | -0.17% | 10,146.22 ms | 10,169.20 ms | +0.23% |
| 8 | 6,336.93 | 6,327.30 | -0.15% | 11,635.31 ms | 11,647.49 ms | +0.10% |

Median ITL differed by only 0.01-0.02 ms across all three points. The observed
throughput and latency differences are below 0.3% and consistent with normal
run-to-run measurement noise; no material Flash performance regression was
observed.

## Scope

This is a follow-up to the Quark mixed-precision support in #38546. It does not
replace or modify GLM-5.3-Flash's MoE/AITER layout, clamp, padding, or
model-specific loading logic. It completes the separate DeepSeek loader path
used by `GlmMoeDsaForCausalLM`.
