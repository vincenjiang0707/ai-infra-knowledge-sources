### Describe the bug

On a host where `/tmp` is mounted `noexec` (common in managed containers and hardened images), `sglang.launch_server` **hangs forever with no error**:

1. With NUMA binding enabled (the default, `SGLANG_NUMA_BIND_V2`), `configure_subprocess` writes a wrapper script `exec numactl <args> python "$@"` to a **hard-coded** `/tmp/sglang_temp_file_<ts>_<rand>.sh` (`_create_numactl_executable` in `srt/utils/numa_utils.py`) and makes it the multiprocessing spawn executable.
2. The kernel refuses to execute it (`Permission denied`), so the scheduler and detokenizer processes die immediately, before Python starts, leaving **no traceback in the log**.
3. The launcher never notices: it keeps waiting for the children to report readiness. The children stay as zombies (`<defunct>`) and the server never comes up and never exits.

Two things make this hard to diagnose:

- `_probe_numactl_args` dry-runs `numactl <args> true`, which succeeds, but it never checks that the *wrapper script itself* can be executed from its location.
- The path ignores `TMPDIR` / `tempfile.gettempdir()`, so pointing `TMPDIR` at an executable directory does not help. Only `SGLANG_NUMA_BIND_V2=0` works around it. (#25314 proposed an env var for this directory but was closed.)

### Expected behavior

- The launcher should fail fast with a clear error if a scheduler/detokenizer subprocess exits during startup, instead of waiting forever.
- The NUMA wrapper should be written somewhere executable (e.g. honor `TMPDIR` / `tempfile`, or fall back to no NUMA binding with a warning when the wrapper cannot be executed). Probing by actually executing the wrapper once would catch this.

### Reproduction

Any model; the failure happens before model loading.

```bash
# /tmp mounted noexec, e.g. inside a container:
#   tmpfs on /tmp type tmpfs (rw,nosuid,nodev,noexec,relatime,inode64)
python -m sglang.launch_server --model-path <model> --port 8000
```

Log stops right after the spawn-executable switch and nothing else is printed:

```
[2026-09-21 18:33:27] Compiled-kernel caches now live under SGLANG_CACHE_DIR (...)
[2026-09-21 18:33:28] mp.set_executable .../.venv/bin/python -> /tmp/sglang_temp_file_1790015608.0013747_6994139.sh (script='#!/bin/sh\nexec numactl --cpunodebind=0 --membind=0 .../.venv/bin/python "$@"')
```

Minutes later the children are zombies and the parent is still waiting:

```
$ pstree -p <launch_server pid>
python(128137)-+-python(128376)   # <defunct>
               |-python(128377)   # <defunct>
               ...
$ /tmp/sglang_temp_file_1790015608.0013747_6994139.sh -c "print(1)"
bash: /tmp/sglang_temp_file_1790015608.0013747_6994139.sh: Permission denied
$ numactl --cpunodebind=0 --membind=0 true; echo $?
0
```

Workarounds: `SGLANG_NUMA_BIND_V2=0` (setting `TMPDIR` does not help because the path is hard-coded).

### Environment

- sglang 0.5.20 (the relevant code is unchanged on `main` as of today), torch 2.13.0+cu130, flashinfer 0.6.18
- 1x NVIDIA B200, driver 580.95.05, CUDA 13.1, Ubuntu 24.04 container (cgroup v2, 8 CPUs)
- `/tmp`: `tmpfs (rw,nosuid,nodev,noexec)`
