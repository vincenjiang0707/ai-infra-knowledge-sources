### Motivation

Track the fixes needed to serve GLM-5.3-Flash on two 96 GB RTX PRO 6000 Blackwell GPUs (SM120), using TP2, W4A16 routed experts, FP8 KV, vision and native MTP. Upstream main alone does not yet provide this complete configuration.

### Release and validation status

Updated 2026-09-08 for [v0.4.2](https://github.com/ormandj/sglang-glm53-flash-sm120/releases/tag/v0.4.2). The release uses official SGLang main `afe90a8bc9` and FlashInfer main `9c10d2e8f2`, with checksummed integration patches. [The release lock](https://github.com/ormandj/sglang-glm53-flash-sm120/blob/v0.4.2/stack.lock.json) identifies the exact inputs and resulting trees.

Author validation of the combined build covers changed-path CPU/GPU regressions and sanitizers, full GSM8K, C1-C4 engine measurements, cold prefill, long-context controls, forced HiCache restoration, sampled startup, and a 7680x4320 image followed by four independent cold text requests. The GHCR image was built separately from the same pinned inputs and was not separately benchmarked. [Measured behavior and limitations](https://github.com/ormandj/sglang-glm53-flash-sm120/blob/v0.4.2/BENCHMARKS.md) report the new fixed-MTP comparisons; the serving launcher retains adaptive MTP.

The release retains a 524,288-token shared device token pool. Compact native GLM FP8 rows use 528 rather than 656 bytes without requantizing values. Four concurrent requests share that pool. Host KDA lengths avoid repeated device scalar reads, and small prefill tails can use breakable graphs. These changes do not establish an isolated speedup for any individual PR.

### Work still downstream

MHC auxiliary-tensor lifetime handling for breakable graphs remains downstream. Its source and validation are separate from the native KV PRs.

The mixed-row HiCache sidecar implementation and the later checkpoint and standalone-index repairs are included in the released integration. The sidecar path supports one draft runner; mismatched multiple runners remain unsupported. FP4 MLA KV storage is rejected before allocation because these transfers do not support its separate scales. Draft sidecars add host memory beyond the target host-pool budget.

Other retained downstream pieces include SM120 model/backend selection, ModelOpt E4M3-K32 preparation, the W4A16 route-prefix optimization, static Mamba admission/accounting, adaptive-MTP buffer lifetime, GLM video/DP/media-order handling, PCIe IPC all-reduce wiring, mixed-precision KDA gate fusion, optional FP8 lm_head support, recurrent-kernel tuning, and diagnostics. Hardware-specific memory/concurrency defaults need not become universal upstream defaults. FlashInfer's native backend merge does not by itself upstream the SGLang integration.

### fsadj · 2026-09-21

## Two additional bugs found while serving the pruned GLM-5.3-Flash NVFP4 checkpoint on SM120 (single GPU)

Setup: sglang PR #38430 (`ormandj:native-glm-nope-compact-kv` @ `28379a7c`), FlashInfer main
`79caeb70926b`, torch 2.13.0+cu130, RTX PRO 6000 Blackwell 96 GB, checkpoint
`Asilarkness/GLM-5.3-Flash-Uncensored-NVFP4-Pruning-62GB` (llm-compressor `nvfp4-pack-quantized`,
routed experts NVFP4, shared experts / dense layers BF16).

With the following two fixes applied on top of #38430, the model boots, the full sparse-MLA path
(compact 528 B rows), the KPool indexer, top-k, and KDA linear attention all compute correctly
(adapter unit tests 18+21 pass, topk v2 tests 278 pass, per-layer finite outputs verified), and
the server generates coherent multi-token text. Without them, every MoE output is 100 % NaN.

### Bug 1 — shared-experts fusion gate doesn't cover compressed-tensors BF16 shared experts

`Glm5NextForConditionalGeneration.shared_experts_fusion_disable_reason`
(`sglang/srt/models/glm5_next.py`) only auto-disables fusion for `modelopt_fp4` checkpoints whose
shared experts are excluded from quantization. The same structure occurs in compressed-tensors
NVFP4 checkpoints (BF16 `mlp.shared_experts.*` alongside FP4-packed `mlp.experts.*`), but the gate
returns no reason there, so `--disable-shared-experts-fusion` is the only escape — and even that
is easy to miss. Fusing the BF16 shared expert into the FP4 expert array leaves its
`weight_global_scale` slot at 0 → `w13_weight_scale_2 = 1/0 = Inf` → every token that passes the
(shared) expert path NaNs. Runtime evidence: `w13_weight_scale_2: shape=(81,) inf=1`.

Suggestion: extend the `modelopt_fp4` branch to also detect BF16 shared experts under
compressed-tensors (e.g. quant_config is compressed-tensors and the shared-expert projections are
absent from the quant config groups).

### Bug 2 — W4A4 MoE scheme assumes static activation global scales; dynamic input quant yields all-zero scales

`CompressedTensorsW4A4Nvfp4MoE.create_weights` allocates `w13/w2_input_global_scale` with
`torch.empty`, but llm-compressor checkpoints declaring
`input_activations: {type: float, dynamic: true, strategy: tensor_group}` (format
`nvfp4-pack-quantized`) store **no** such tensors — the activation global scale is meant to be
computed at runtime. At runtime the parameters were observed as **all zeros**
(`w13_input_global_scale zero=160/160`), so `w13_input_scale_quant = 0` → the FP4 activation
quantize divides by zero → NaN activations → all-NaN expert outputs (verified with
`torch.empty`-vs-checkpoint tensor dumps; the checkpoint's packed weights decode cleanly offline
with `fp4 × block_scale / weight_global_scale`, absmax ≈ 0.10, std ≈ 0.02).

Workaround we applied (quality still degraded — repetition-heavy output, presumably because the
gemm2 input scale remains a static guess): in `process_weights_after_loading`, when the input
scales are all-zero, fill `amax_est / (448 × 6)` (13: 8.0, 2: 512.0) and recompute
`w13_input_scale_quant` + `g1_alphas` per forward from `x.abs().amax()`. A proper fix needs the
gemm2 (post-SiLU intermediate) activation scale handled dynamically inside the runner as well.

### Question

Is dynamic-activation (`input_activations.dynamic = true`) NVFP4 MoE support planned for
sglang's compressed-tensors path (vLLM dispatches this shape to `CompressedTensorsW4A4Fp4(use_a16=True)`
weight-only when `input_quant is None`, but that dequantizes experts to BF16 and needs ~2× expert
memory — 96 GB single-GPU cannot fit GLM-5.3-Flash that way, so a true dynamic W4A4 path is the
only single-GPU option for pruned NVFP4 checkpoints like this one)?
