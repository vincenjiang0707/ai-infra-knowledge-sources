## 正文

### Describe the feature / gap

`DeepseekV4AttnBackend._forward_prefill_sparse()` (`sglang/srt/layers/attention/deepseek_v4_backend.py`) routes DeepSeek-V4 sparse-attention prefill through `flash_mla_sparse_fwd` (from `sgl_kernel.flash_mla`). This kernel unconditionally raises:

```
RuntimeError: Sparse Attention Forward Kernel is only supported on SM90a and SM100f architectures.
```

on any other compute capability, including **SM120 (Blackwell, e.g. RTX PRO 6000 Blackwell Max-Q)**. Since PR #29775 ("[DeepSeek V4] Enable FlashMLA sparse prefill by default", merged into `lmsysorg/sglang:latest` as of v0.5.15.post1) flipped `SGLANG_OPT_FLASHMLA_SPARSE_PREFILL`'s default from `False` to `True`, this now fires unconditionally for DeepSeek-V4 on SM120 hardware — the model cannot serve any request through the default `dsv4` attention backend without the workaround below.

This is a **feature request for native SM120 support**, not a duplicate of #29900. #29900 documents the identical error text but strictly as a *test-suite gating gap* (`test_flashmla.py` needs a compute-capability skip so the 20 already-expected-unsupported failures don't drown out real bugs) — it explicitly does not ask for SM120 support to be implemented, only for the test to skip cleanly. This issue asks for the underlying capability itself.

### Environment

- GPU: 2x NVIDIA RTX PRO 6000 Blackwell Max-Q (SM120), 97,887 MiB each
- Image: `lmsysorg/sglang:latest` resolving to sglang v0.5.15.post1
- Model: DeepSeek-V4-Flash, `--attention-backend dsv4`, `--tp-size 2`

### Evidence an SM120-compatible code path is already partially plausible

The **decode-path** kernel (`flash_mla_with_kvcache`) already has an SM120 branch (`flash_mla_with_kvcache_sm120`, added in sglang v0.5.13 via PR #24692), reachable via `SGLANG_SM120_FLASHMLA_BACKEND=triton`. Setting `SGLANG_OPT_FLASHMLA_SPARSE_PREFILL=0` (to opt back out of the sparse-prefill default) together with `SGLANG_SM120_FLASHMLA_BACKEND=triton` avoids the unsupported sparse-prefill kernel entirely and routes decode through the existing Triton SM120 fallback — this combination, plus `--mem-fraction-static` tuned to ~0.98 (headroom for the Triton autotune scratch buffer) and `--disable-cuda-graph`/`--skip-server-warmup`, lets DeepSeek-V4-Flash serve real inference requests end-to-end on SM120 today. We verified this empirically with two successful `POST /v1/chat/completions` requests returning valid completions end-to-end.

This confirms an SM120-compatible execution path already exists for the decode side of FlashMLA — it seems plausible the same Triton (or an equivalent) approach could be extended/hardened to cover the sparse-*prefill* kernel (`flash_mla_sparse_fwd`) as well, rather than requiring every SM120 user to discover and apply this env-var combination themselves.

Precedent that SM120-dispatch PRs are accepted for adjacent kernels: PR #28125 ("feat(moe): add SM120/SM121 dispatch for fp8_blockwise_scaled_grouped_mm"), referenced from #29900's `test_fp8_blockwise_moe.py` findings.

### Request

Either:
1. Add native SM120 support to `flash_mla_sparse_fwd` (mirroring the existing `flash_mla_with_kvcache_sm120` decode-path support), or
2. If native support isn't planned near-term, document `SGLANG_OPT_FLASHMLA_SPARSE_PREFILL=0` + `SGLANG_SM120_FLASHMLA_BACKEND=triton` as an official, supported fallback for SM120 users running DeepSeek-V4 so it isn't discovered ad hoc.

Related: #29900 (test-gate gap for the same error, not a fix request), #29897, PR #28125 (SM120 dispatch precedent for a different kernel).
