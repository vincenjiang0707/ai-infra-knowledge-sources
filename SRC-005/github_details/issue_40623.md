# [Issue #40623] [Bug] Illegal memory access in the Triton fused-MoE kernel when `flashinfer_megamoe` is combined with EAGLE speculative decoding (GLM-5.2-NVFP4, sm_107)

source: https://github.com/sgl-project/sglang/issues/40623
state: open | updated: 2026-09-22T19:07:26Z
labels: 

## 正文

## Summary

On a `GlmMoeDsaForCausalLM` (GLM-5.2-NVFP4, MLA + DSA) deployment, enabling
`--moe-a2a-backend flashinfer_megamoe --moe-runner-backend flashinfer_megamoe`
**together with** EAGLE speculative decoding reliably produces

```
RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered
```

Either feature alone works. With `CUDA_LAUNCH_BLOCKING=1`, the fault is attributed
to **sglang's own Triton fused-MoE kernel on the unquantized (draft-model) MoE
path** — not to any FlashInfer MegaMOE kernel:

```
srt/layers/moe/fused_moe_triton/layer.py       forward_impl -> run_moe_core
srt/layers/quantization/unquant.py:1008        apply
srt/layers/quantization/unquant.py:1110        forward_cuda
srt/layers/moe/moe_runner/triton.py:129        run
srt/layers/moe/moe_runner/triton_utils/fused_moe.py:620   _fused_moe_kernel_sequence
kernels/ops/moe/fused_moe_triton_kernels.py:1004          invoke_fused_moe_kernel
triton/runtime/jit.py -> <illegal memory access>
```

So this looks less like a MegaMOE kernel defect and more like a state/config
conflict between the two MoE backends coexisting in one server: the main model
runs MegaMOE while the EAGLE draft model runs the unquantized Triton fused-MoE
runner, and the draft path faults.

Note `GlmMoeDsaForCausalLM` is not in `validate_flashinfer_megamoe_model`'s
`validated_architectures`; we added it locally in order to evaluate MegaMOE (see
Reproduction). If the omission is deliberate, this report can be read as evidence
supporting it — but the fault location suggests the problem is not
architecture-specific.

## Ask

- Is `flashinfer_megamoe` expected to coexist with speculative decoding, given
  that the draft model dispatches through a different MoE runner?
- If the two are not meant to coexist, would a startup-time rejection be
  preferable to the current failure mode?
- We can re-run under `compute-sanitizer` and attach the kernel-level trace if
  that would help — please let us know the preferred invocation.

### Reproduction

Single node, 4 GPUs, stock container, no patches other than the allowlist line.

**Step 1 — allow the architecture.** `validate_flashinfer_megamoe_model` rejects
`GlmMoeDsaForCausalLM` before the server starts, so it must be added first. This
is the only source change:

```diff
  # python/sglang/srt/arg_groups/moe_hook.py, validate_flashinfer_megamoe_model
   validated_architectures = (
       ...
       "Glm4MoeForCausalLM",
+      "GlmMoeDsaForCausalLM",
       "NemotronHForCausalLM",
       ...
   )
```

**Step 2 — launch with MegaMOE *and* EAGLE.**

```bash
export SGLANG_FLASHINFER_MEGAMOE_MAX_TOKENS_PER_RANK=16384   # = chunked-prefill-size / dp_size
export CUDA_LAUNCH_BLOCKING=1                                # for synchronous attribution

python3 -m sglang.launch_server \
  --model-path /path/to/GLM-5.2-NVFP4 --trust-remote-code \
  --quantization modelopt_fp4 --kv-cache-dtype fp8_e4m3 \
  --tensor-parallel-size 4 --data-parallel-size 4 --expert-parallel-size 4 \
  --enable-dp-attention --enable-dp-lm-head \
  --chunked-prefill-size 65536 --max-running-requests 32 \
  --mem-fraction-static 0.8 --context-length 131072 \
  --disable-radix-cache --disable-cuda-graph --watchdog-timeout 1800 \
  --moe-a2a-backend flashinfer_megamoe --moe-runner-backend flashinfer_megamoe \
  --speculative-algorithm EAGLE --speculative-eagle-topk 1 \
  --speculative-num-steps 1 --speculative-num-draft-tokens 2
```

The server dies during startup/warmup, before serving any request. No load is
needed to trigger it.

**Step 3 — remove one of the two features and it runs.** Dropping
`--speculative-algorithm EAGLE ...` (keeping MegaMOE) serves requests normally,
including under sustained load — we verified 16 concurrent requests of ~67k
prompt tokens each, with prefill batches reaching the full 16,384 tokens/rank.

## Observed matrix

| MegaMOE | EAGLE/MTP | Result |
|---|---|---|
| on | off | works — full load, coherent output |
| **on** | **on** | **illegal memory access** in `invoke_fused_moe_kernel` |
| off | on | works (see caveat below) |

Reproduced with `--speculative-num-steps 1 --speculative-num-draft-tokens 2` and
with `3 / 4`; the outcome and the faulting frame are the same in both. Two
independent `CUDA_LAUNCH_BLOCKING=1` runs attribute the fault to
`fused_moe.py:620` and `fused_moe.py:826` respectively — both inside
`_fused_moe_kernel_sequence` → `invoke_fused_moe_kernel`.

We also tried isolating the draft path with
`--speculative-moe-runner-backend deep_gemm` (and additionally
`--speculative-moe-a2a-backend deepep`). That removes the illegal-memory-access
signature but the server still fails, with `tvm.error.InternalError` from
deep_gemm and `CUDA error 719 (CUDA_ERROR_LAUNCH_FAILED)` respectively. Given
that 719 is a typical downstream symptom of a prior asynchronous memory fault, we
do not read these as a fix.

### Caveat on the third row

The "MegaMOE off, EAGLE on" cell is **not** from this single-node harness. In our
minimal setup that configuration never finished initializing — it reaches
`fired up and ready to roll!` and then stalls inside
`_draft_extend_for_prefill (eagle_worker_v2.py:1085)` until the watchdog fires.
Seven attempts, all infrastructure-bound (cold JIT compilation is very slow here;
we lack a warm `SGLANG_DG_CACHE`). We are not reporting that stall as a bug — it
may well be specific to our environment.

That row instead comes from our production deployment: a 6-node disaggregated
prefill/decode setup running the same model with EAGLE enabled and MegaMOE off,
which completes 3,600-second benchmark runs with no errors, repeatedly. So the
two arms of the comparison come from different scales, which we note for honesty.

From reading the code (no Blackwell here, and I wasn't keen on renting 4 GPUs just to watch it crash at warmup), my guess is that the draft silently inherits `flashinfer_megamoe` as its a2a backend. Because of that, the dispatcher skips the global→local expert ID remap, but the unquantized MTP layer actually falls back to the Triton runner. So Triton gets global expert IDs with only `E/ep_size` local experts, which would explain the IMA.

If that's right, just switching the draft runner (deep_gemm, trtllm…) won't be enough as long as the a2a backend is still inherited. It would probably also affect DeepSeek NVFP4 + MegaMoE + EAGLE on CUDA, since the "bf16 nextn → triton/none" override only runs on HIP.

If the flag combo above works for you, I'm happy to open a PR that defaults the draft to a2a `none` in this case.

### wenscarl · 2026-09-22

The IMA can be reproduced on Blackwell too so it's hardware agnostic.
The global `--moe-runner-backend flashinfer_megamoe` flag and the per-layer runner backend actually selected disagree for the unquantized NextN/MTP layer, and the dispatcher trusts the global flag.

`python/sglang/srt/models/deepseek_v2.py`:657-671,700-707 — every MoE layer (including GLM-5.2's NextN/MTP draft layer, built via the DeepSeek-style NextN base class) goes through get_moe_impl_class(quant_config). For the NextN layer quant_config is None (it's in the checkpoint's quant ignore/exclude_modules list — BF16), so it resolves to UnquantizedFusedMoEMethod.

`python/sglang/srt/layers/quantization/unquant.py`:944-969 — UnquantizedFusedMoEMethod.create_moe_runner's backend-selection chain checks flashinfer_trtllm, flashinfer_cutlass, deep_gemm, triton_kernels, NPU — but has no flashinfer_megamoe branch at all. It falls through to else: backend = MoeRunnerBackend.TRITON. So this one layer silently runs Triton MoE regardless of the server-wide flag. (There's even a speculative_runner_backend / get_speculative_moe_runner_backend() field in layers/moe/utils.py:500-507 and runtime_context.py:579 that looks purpose-built to carry a per-speculative-layer override — but it's dead code, never written or read.)

`python/sglang/srt/layers/moe/token_dispatcher/standard.py`:98,112-121 — StandardDispatcher doesn't know that; it reads the global runner backend and, seeing flashinfer_megamoe, sets skip_local_expert_mapping = True ("flashinfer_megamoe routes by global expert ID inside the mega kernel"). That's correct for layers that genuinely run the mega kernel, wrong here.

Because that flag is True, dispatch() (standard.py:184-239) skips remapping topk_ids from global expert-id space [0, num_experts) down to this rank's local shard [0, num_local_experts).

But `fused_moe_triton/layer.py`:397-399,521-534 still allocates w13_weight/w2_weight EP-sharded, shape [num_experts/ep_size, ...] — same as every other quant method.

The un-remapped, global-space topk_ids then hit TritonRunnerCore.run / invoke_fused_moe_kernel (layers/moe/moe_runner/triton.py:129-168, triton_utils/fused_moe.py) indexing into weight tensors sized for only num_experts/ep_size local experts. Any token routed to an expert id >= num_local_experts (true for (ep_size-1)/ep_size of all routing decisions whenever ep_size > 1) reads/writes out of bounds inside the Triton kernel → illegal memory access.
