### Describe the bug

### Summary

`--load-format fastsafetensors` works on single-node multi-GPU but crashes on multi-node deployments. Two bugs in `fastsafetensors_weights_iterator`:

1. **Uses global rank as CUDA device index** — `pg.rank()` returns the global rank (0~N-1 across all nodes), but `torch.device(f"cuda:{rank}")` expects a local device index. On multi-node, rank 11 maps to `cuda:11` which doesn't exist on a 3-GPU node.
2. **No GDS fallback** — `SafeTensorsFileLoader(pg, device)` is called without `nogds=True`, and there's no try/except fallback when GDS is unsupported. vLLM has both fixes.

### ronhuafeng · 2026-06-28

This matches the bug already addressed by #26597. The two important parts there are exactly the two failure modes in this report:

- use the process local CUDA device (`torch.cuda.current_device()`) instead of the global process-group rank as the fastsafetensors target device;
- expose a `nogds` opt-out for filesystems where cuFile/GDS is not supported.

Until that PR lands, the safest workaround is to avoid `--load-format fastsafetensors` for multi-node TP on shared/network storage and use the normal safetensors loader. If you carry the patch locally, the NFS/GDS case should also set the new opt-out (`SGLANG_FASTSAFETENSORS_NOGDS=1` in that PR) so fastsafetensors uses the CPU-staged fallback instead of trying GDS.

### ZackSample · 2026-07-23

Hitting a related but distinct manifestation of the same root cause on single-node DGX Spark (GB10, integrated/unified memory, SM121, sglang 0.5.15.post1 / commit `0b3bb0cbe31873994c9f989fddfe2f87ca839fdd`, official `lmsysorg/sglang:latest-cu130` image). **Environment:** `nvidia/Qwen3.6-35B-A3B-NVFP4` (ModelOpt mixed FP8/NVFP4), single GPU, `--tp 1`.

**Confirmed via source read at the pinned commit** (not just observed behavior):

```python
        prefetch=weight_loader_prefetch,
        prefetch_num_threads=prefetch_num_threads,
        drop_cache_after_load=weight_loader_drop_cache_after_load,

```
So on top of the missing `nogds=True` this issue already identifies, `--weight-loader-drop-cache-after-load`, `--weight-loader-prefetch-checkpoints`, and `--weight-loader-prefetch-num-threads` (`server_args.py:2375-2390`) are all silently no-ops under `--load-format fastsafetensors` — they're computed, echoed back in the `ServerArgs` dump as set, and then simply never reach `fastsafetensors_weights_iterator`, whose signature (`weight_utils.py:984`) only accepts `hf_weights_files`.

**Consequence on integrated-memory hardware specifically:** `get_available_gpu_memory` (`utils/common.py:412-418`) correctly special-cases integrated/unified-memory GPUs (`props.is_integrated`) by using `psutil.virtual_memory().available` instead of `torch.cuda.mem_get_info()`, specifically to avoid miscounting reclaimable page cache as used. That accounting is correct — which is what makes this notable: the memory genuinely disappears, it's not a measurement bug. With no GDS available and no `nogds=True` passed, `SafeTensorsFileLoader`'s fallback path appears to stage through pinned host memory, which is *not* reclaimable, so it shows up as a real, sustained loss against the unified pool.

### ZackSample · 2026-07-23

Follow-up: opened a PR wiring `nogds` (auto-detected on integrated-memory GPUs) and thread-count config into this loader branch — sgl-project/sglang#32199.

Worth flagging though: fixing the missing `nogds` wiring did **not** resolve the memory usage on integrated-memory hardware. Isolated that to a separate leak inside `fastsafetensors` itself (`SafeTensorsFileLoader` retains ~2x each shard's file size permanently past `close()`, reproduced independently of any SGLang code, `gc.collect()`/`empty_cache()` recover nothing) — filed as foundation-model-stack/fastsafetensors#94. So the PR here closes the config gap this issue identified, but the underlying memory question needs a fix upstream in fastsafetensors, not something fixable from SGLang's side.

### ZackSample · 2026-07-24

Update from the fastsafetensors side (foundation-model-stack/fastsafetensors#94): the memory bloat has a concrete, partial fix.

The maintainer pointed out that the iterator should call `fb.close()` (close the `FilesBufferOnDevice`) before `loader.close()`. SGLang's `fastsafetensors_weights_iterator` doesn't — it only calls `loader.close()`. Adding `fb.close()` in a minimal standalone repro on DGX Spark recovers **~1× the checkpoint's size per shard that was previously never released** (was 0), taking net retention from **~2× to ~1×**.

So SGLang could likely halve the fastsafetensors memory overhead on integrated-memory hardware by adding `fb.close()` to the iterator. I haven't re-measured a full SGLang boot with the patch — SGLang's ModelOpt loader adds its own overhead on top, so the end number needs verifying in-engine — but the library-level finding is clean. Combined with the `nogds` wiring in #32199, this could plausibly make `--load-format fastsafetensors` viable on Spark rather than OOM-ing.

Refs: foundation-model-stack/fastsafetensors#94 (root cause + numbers), #32199 (nogds wiring PR).
