## Motivation

Chat template rendering and tokenization run on the HTTP event loop, so one long prompt delays health checks and response streaming for every other request on that frontend process.

Supersedes #30771. @anencore94 found this and proposed the same single-worker offload for OpenAI conversion and fallback tokenization first. This PR also covers Anthropic Messages/count_tokens and both Responses paths, keeps request validation inline so each request pays at most one thread hop, and keeps requests in arrival order.

## Modifications

- New `RequestPreprocessor` (one FIFO worker thread per `TokenizerManager`, contextvars carried over) with a single `run()` entry point. It runs `_convert_to_internal_request` in `OpenAIServingBase` and Anthropic Messages, token counting in count_tokens, and prompt rendering in both Responses paths.
- `/generate` text tokenization moves off the loop for prompts over 2048 characters. Shorter prompts tokenize inline when nothing is queued, so their dispatch timing stays the same. Offloading them too made a burst of short requests reach the scheduler in one batch, which broke the arrival-order assumptions in `test_priority_scheduling.py`.
- Requests leave preprocessing in arrival order. The worker is FIFO, and inline work runs only when no job is outstanding. A job whose request was cancelled stays outstanding until it finishes, so the tokenizer is never used from two threads at once.
- Jinja rendering and pydantic still hold the GIL. The loop no longer waits for a whole conversion, but each time it needs the GIL it can wait up to one switch interval (`sys.getswitchinterval()`, 5 ms by default) while the worker runs Python code. A single C call that keeps the GIL still blocks the loop for as long as that call runs.

## Tests

- `test/registered/unit/managers/test_request_preprocessor.py`:
  - Long-prompt tokenization and chat conversion leave the loop free. Both fail on main because the loop is blocked until the gate times out.
  - A short prompt does not overtake an earlier long one. Main passes this because it runs everything inline. It fails if inline work ignores outstanding jobs.
  - A cancelled request's running tokenization still serializes later requests. This fails on main, where a request cannot be cancelled mid-tokenization, and it fails if cancellation frees the worker slot early.
- `test_priority_scheduling.py` is unchanged from main.
- Entrypoint and TokenizerManager unit suites pass locally. The only failures are the audio-chunking and transcription tests that need torchaudio, which fail on main too.
