## 正文

## Motivation

Two problems, both around `--enable-aiter-allreduce-fusion` on ROCm.

**The auto-enable never shipped, but the log announcing it did.** The ROCm
auto-enable for this fusion landed commented out in #13747, while the
`logger.info` that announces it did not. A single-node ROCm run without DP
attention has since reported the fusion as on with nothing actually setting it.
Two sites are affected: the DeepSeek-family HIP arm and the GptOss arm of
`handle_model_specific_adjustments`.

**The switch is all-or-nothing, but the fusion is not equally worthwhile in both
phases.** Fusing the post-MLP all-reduce into the next layer's residual+RMSNorm
pays off in decode, where the collective is latency-bound and the launch count
dominates. Prefill is a different regime, and there is currently no way to keep
the fusion where it pays and drop it where it does not — the operator only gets
one boolean for the whole run. For GLM-5.2 (`GlmMoeDsaForCausalLM`) we want it
on for decode and off for prefill.

## Modifications

### 1. Per-phase opt-outs under the existing master switch

`python/sglang/srt/arg_groups/fields/exec_.py` — two new resolvable fields next
to `enable_aiter_allreduce_fusion`:

- `disable_aiter_allreduce_fusion_in_prefill`
- `disable_aiter_allreduce_fusion_in_decode`

Both default to `False`, so `--enable-aiter-allreduce-fusion` keeps meaning
"fuse everywhere" and a run that does not pass the new flags is unchanged.

### 2. Phase-aware gate

`python/sglang/srt/layers/communicator.py` — the master-switch read moves into a
helper, and `apply_aiter_all_reduce_fusion` now takes the `ForwardBatch`:

```python
def aiter_all_reduce_fusion_enabled_for(forward_mode: ForwardMode) -> bool:
    comm = get_exec().comm
    if not comm.enable_aiter_allreduce_fusion:
        return False
    if forward_mode.is_extend_or_draft_extend_or_mixed():
        return not comm.disable_aiter_allreduce_fusion_in_prefill
    return not comm.disable_aiter_allreduce_fusion_in_decode
```

### Compatibility

- All three switches default off; a run that passes none of them behaves exactly
  as before, on every platform.
- The new fields need no `field_order.py` entry. A name that is not listed there
  sorts after every name that is, which is the only backward-compatible
  position for a new field — so `ServerArgs`' positional signature is unchanged.
- The two `assert not cfg.enable_aiter_allreduce_fusion` guards in
  `parallel_hook.py` (context parallelism, `moe_dp_size > 1`), the
  deterministic-inference override in `attention_hook.py`, and the MiniMax-M3
  override in `model_overrides/minimax_m3.py` are all untouched and stay sound:
  they gate the master switch, and the new switches can only narrow it.
- `qwen3_5._fused_ar_quant_enabled` still reads the master switch. It feeds
  `LayerCommunicator(enable_fused_ar_quant=...)` at construction time, which
  decides whether the next linear receives an fp8 tuple or bf16, so it is not a
  per-phase decision and is intentionally left alone.
