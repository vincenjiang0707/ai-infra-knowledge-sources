# [Issue #57064] [Bug][ROCm][Attention][KV Connector] DeepSeek-V3.2 / GLM-5.x DSA sparse-MLA decode is garbage under CUDA graphs in PD-disaggregation (remote-prefilled KV)

source: https://github.com/vllm-project/vllm/issues/57064
state: open | updated: 2026-09-22T14:30:47Z
labels: rocm, deepseek, kv-connector, glm

## 正文


## Summary
In PD-disaggregated serving on ROCm/MI300X (MoRIIO KV connector, WideEP DP8/EP8), the **decode** engine emits degenerate repeated-token garbage (`locklocklock…` / `!!!`) for **remote-prefilled** requests whenever decode runs under **any CUDA-graph capture** (`FULL`, `PIECEWISE`, or `FULL_AND_PIECEWISE`). With `DECODE_CUDAGRAPH_MODE=NONE` (eager) the identical stack decodes **coherently**. Colocated (non-disagg) serving and vLLM v0.27.1 are unaffected.

## Environment
- vLLM **0.28.0** (`vllm/vllm-openai-rocm:v0.28.0`), AITER 0.1.19, ROCm 7.2.3
- 2× **MI300X (gfx942)**, RoCEv2; KV connector = **MoRIIOConnector** (WRITE mode), `block_size=1`, fp8 KV
- Models: **GLM-5.3-FP8** and **GLM-5.1-FP8** (both `GlmMoeDsa`, DeepSeek-V3.2-style **DSA sparse-MLA**)
- Topology: 1P1D **WideEP DP8/EP8**; MTP on or off (does not matter)

## How to reproduce
1. Launch 1P1D PD-disagg (MoRIIO WRITE) — e.g. the AMD harness `.buildkite/amd-disagg/run-slurm-disagg-test.sh` with `WIDE_EP_MODE=1 MORIIO_READ_MODE=0` — using `DECODE_CUDAGRAPH_MODE=FULL_AND_PIECEWISE`.
2. Send any request → decode returns `locklocklock…` (garbage).
3. Set `DECODE_CUDAGRAPH_MODE=NONE` (eager) → decode is coherent. (`FULL` and `PIECEWISE` are each garbage too.)

## Expected behavior
Decode under CUDA graphs produces the same coherent output as eager decode (and as colocated single-node / vLLM v0.27.1).

## Isolation — what did NOT fix it vs what WORKED
We walked the full transfer→decode path with per-step, on-device instrumentation applied identically to both engines.

**Did NOT fix it (still garbage), i.e. ruled out as the cause:**
- **KV-cache content / transfer** — the transfer is complete and **bit-exact** (producer == consumer bytes for every layer, including the sparse-indexer k_cache). Explicitly transferring the indexer k_cache changed nothing.
- **MoRI library version** — swapping v1.1.0 ↔ commit `42e895472b08` (the version used by the working v0.27.1 recipe) made no difference.
- **MoRI-EP `combine()` fix** (#56073 / ROCm/mori#475) — inert here (our EP8 runs the single-node **IntraNode** combine, not the InterNodeV1 path that fix targets).
- **Decode metadata** — byte-identical local-vs-remote for the same prompt (`num_computed_tokens`, positions, seq_len, block_table, indexer top-k, and post-remap global KV slots all match). Nothing to correct.
- **KV dtype** — reproduces with **fp8 and bf16** (so not an fp8-scale/dequant issue).
- **Transfer mode** — reproduces in **both READ and WRITE** MoRIIO modes.
- **MTP** — reproduces with speculative decode **on and off**.
- **Widening the eager CUDA-graph region** — restoring a broad `eager_break_during_capture` over the whole sparse decode (breakable/PIECEWISE) **still produced garbage**.

**WORKED (coherent), i.e. the differentiators:**
- **`DECODE_CUDAGRAPH_MODE=NONE` (eager decode)** — coherent, 3/3 prompts, MTP on and off.
- **Colocated single-node DP8/EP8** on the *same* v0.28 build/kernels/model (no remote KV) — coherent.
- **vLLM v0.27.1 + WideEP overlay** — the *same* PD-disagg path decodes coherently.

→ Coherent vs garbage turns on exactly **two conditions being simultaneously true: (1) the DSA sparse-MLA decode is captured in a CUDA graph, AND (2) it is consuming remotely-populated KV.** Removing *either* — run decode eager, or serve the same request colocated (locally-populated KV) — restores coherence. Reproduces on ≥2 DSA models (GLM-5.3-FP8, GLM-5.1-FP8). The corruption therefore lives in the **CUDA-graph capture/replay × remotely-populated-KV buffer lifecycle** of the DSA sparse-MLA decode (replayed steps appear to read stale sparse-index / remote-KV state), and it is **not** in transfer, metadata, scales, dtype, mode, MTP, or the eager-region width.

## Possibly related — and why
- **#51425 "[Perf] Narrow DeepSeek V3.2 eager CUDA graph region"** — the most direct link. It moved most of the DSA attention (query prep, norm/RoPE, GEMMs) *out* of the eager break and *into* the captured graph, leaving only `_sparse_indexer_and_attn` eager. This is the v0.28 change that first placed per-step DSA sparse-decode state under CUDA-graph capture, and GLM-5.x (DeepSeek-V3.2 architecture) rides exactly this path.
- **#51430 / #51768 / #52401 (DeepSeek-V4 analog)** — strong precedent that this class silently corrupts. #51430 applied the same narrowing to V4; #51768 then documented that **V4 + Model-Runner-V1 + PIECEWISE/FULL_AND_PIECEWISE = silent output corruption** and rejected that combo, noting **eager/NONE** as the mitigation (exactly our workaround); #52401 fixed it by choosing the eager region **per model runner**. So the fix pattern exists — but it was applied to **V4 only**, not to **V3.2 / GLM-5.x**, and not to the **PD-disagg remote-KV** case.
- **#56726 "[ROCm][Bugfix] Ignore descales for unquantized AITER caches"** — same *failure shape*: an AITER decode kernel consuming a **stale/unused scale (descale) tensor** corrupts output, and it surfaces under **CUDA-graph recapture**. Our MLA decode kernel is invoked as `mla_decode_fwd(q_scale=_q_scale, kv_scale=_k_scale)` — the direct analog; if those descales are captured stale, it matches our capture-only, dtype-independent signature. (#56726 patches the FA backend for *unquantized* caches, so it is not a drop-in fix for our MLA-sparse/fp8 path, but the mechanism is the same.)

**Why the existing fixes don't cover us:** widening the eager region (the #52401-style broad eager break over the sparse decode) **did not** restore coherence in our repro — so the corrupting operation is in a segment that stays captured even under the broad eager region. The residual defect is the **CUDA-graph × remotely-populated-KV buffer lifecycle**, which is deeper than eager-region width alone and specific to the PD-disagg (remote-prefill) decode path that none of the above PRs exercised.

## Workaround
`DECODE_CUDAGRAPH_MODE=NONE` (eager decode) — coherent, but ~5–8× slower decode throughput.

### MohitAMD · 2026-09-17

**Update: we've isolated the root cause. It is the torch `2.11.0` → `2.12.0` bump — specifically torch-2.12's `torch.cuda.CUDAGraph` capture/replay of the remote-origin DSA decode.** The original post's suspects (#56726 stale descales; "replay reads stale sparse-index / remote-KV state") are **disproven** by our own follow-up; the *trigger*, repro, and the two-condition characterization still hold.

**Head-to-head proof it's a genuine regression (not config):** the *same* working stack (vLLM **0.27.1** + AITER 0.1.19 + our WideEP overlay) runs the *same* 1P1D disagg config (`DECODE_CUDAGRAPH_MODE=FULL_AND_PIECEWISE`, MTP off) **coherently** on the same MI300X cluster where **v0.28.0 is garbage**. python / HIP / ROCm are identical between the two images; **torch is the only environmental delta (2.11.0 vs 2.12.0).**

**What we eliminated (each with an on-cluster A/B or source diff):**
| Candidate | Verdict |
|---|---|
| KV transfer bytes / dtype / mode | bit-exact; fp8 & bf16 both garbage; READ & WRITE — not it |
| Decode metadata (slot_mapping/block_table/indptr/top-k) | textbook-correct on the garbage path, refreshed, no capture-vs-replay divergence |
| FP8 descales / #56726 | neutral, pointer-stable, run **eager** under PIECEWISE — can't be stale; null-descale didn't help |
| ROCm/aiter#5194 (LRU'd `num_kv_splits_indptr`) | ported + A/B under FULL — still garbage (real capture-safety bug, but not this) |
| MoRIIO KV landing/ordering/values | writes into the model kv_cache tensor; values present at replay; `cuda.synchronize()` barrier didn't help |
| vLLM source v0.27.1↔v0.28.0 | capture/dispatch machinery byte-identical on GLM-5.3's path (#51425 off-path) |
| gfx942 indexer-logits kernel swap (flydsl, PR #49544) | exonerated — it's prefill-only; decode uses the unchanged paged `deepgemm_fp8_paged_mqa_logits` |
| AITER 0.1.19 kernel **build + source** | R18's aiter build dropped into v0.28 → still garbage; aiter source functionally identical |
| MoRI library + `moriio_connector.py` source | mori-swap → garbage; connector's only delta (DSA-indexer transfer) already grafted → still garbage |
| inductor `cudagraph_trees` | not on vLLM's path (vLLM uses its own `torch.cuda.CUDAGraph`) |
| inductor **codegen** | A/B: eager-codegen **+ capture = garbage**, eager-codegen **+ no capture = coherent** → codegen exonerated |

**Mechanism (decisive A/B):** with all of the above ruled out, the only variable that flips coherent↔garbage is **`torch.cuda.CUDAGraph` capture**. The compiled DSA decode graph is captured on a **local-origin `_dummy_run` warmup** and replayed for a **remote-origin** request whose input/state **addresses** differ from the warmup — coherent under torch 2.11, garbage under 2.12. The change is in torch's **compiled C++/HIP** CUDA-graph capture, not the Python wrapper: the `torch/cuda/graphs.py` 2.11→2.12 diff adds only an unused opt-in annotations path, while `libtorch_cpu.so` changed materially and torch's `TORCH_LIBRARY` C++ ABI broke between 2.11 and 2.12 (see confirmation status).

**Confirmation status:** **strongly corroborated, single-variable rebuild pending.** torch can't be swapped standalone to confirm — the `TORCH_LIBRARY` ABI break means `vllm._C` (bound to the 2.12 signature) must be **recompiled against torch 2.11**; the definitive A/B is to build v0.28-vLLM on torch 2.11.0 and re-run the repro (expected: REMOTE coherent). Everything else is eliminated, so this is the remaining variable.

**Ask:** (a) add a #51768-style **safety guard** so `GlmMoeDsa`/`DeepseekV32` PD-disagg remote-KV decode under CUDA graphs can't *silently* corrupt (our workaround is `DECODE_CUDAGRAPH_MODE=NONE`, ~5–8× slower); (b) treat this as a **torch 2.12 `torch.cuda.CUDAGraph` (C++/HIP) capture regression** on the remote-origin (differing-input-address) path — we can share `TORCH_LOGS` and run the torch-2.11 rebuild A/B with the build recipe; (c) independently, ROCm/aiter#5194 is a real capture-safety bug worth backporting (not this root cause). Happy to run more MI300X instrumentation.
