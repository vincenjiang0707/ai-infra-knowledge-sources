# [PR #56995] [Bugfix][Spec Decode] Implement get_top_tokens() on the generic MTP drafter

source: https://github.com/vllm-project/vllm/pull/56995
state: open | updated: 2026-09-23T04:49:29Z
labels: bug, speculative-decoding, deepseek

## 正文

## Purpose

`speculative_config.use_local_argmax_reduction` is unusable with the generic MTP
drafter: enabling it does not fall back to a slower path, it fails engine startup.

```
ValueError: use_local_argmax_reduction is enabled but draft model DeepSeekMTP
does not implement get_top_tokens().
```

The reduction itself already lives in core as `LogitsProcessor.get_top_tokens()` — each
TP rank argmaxes its own vocab shard and only `(value, index)` pairs are gathered. Both
opt-in sites probe the draft model for the method and raise without it:

- `vllm/v1/worker/gpu/spec_decode/speculator.py` (V2 model runner)
- `vllm/v1/spec_decode/llm_base_proposer.py`

`vllm/model_executor/models/deepseek_mtp.py` has `compute_logits` but no
`get_top_tokens`, so every checkpoint that resolves to it raises. On current `main` that
is the `deepseek_v3` family — DeepSeek-V3 and R1 — on every platform:

| checkpoint `model_type` | architecture | resolved draft class | platform |
|---|---|---|---|
| `deepseek_v3` | `DeepSeekMTPModel` | `deepseek_mtp.DeepSeekMTP` | all |
| `deepseek_v32`, `glm_moe_dsa` | `DeepseekV32MTPModel` | `deepseek_mtp.DeepSeekMTP` | XPU, CPU only |

`DeepSeekMTPModel` maps to `deepseek_mtp` in `registry.py` with no platform dispatch, so a
DeepSeek-V3 / R1 MTP drafter is this class on CUDA and ROCm alike. `deepseek_v32` and
`glm_moe_dsa` are dispatched in `vllm/models/deepseek_v32/__init__.py`: CUDA uses
`nvidia/mtp.py`, which already implements the method, and since #51915 ROCm uses
`amd/mtp.py`. So for the DSA family only XPU and CPU still fall back here. `amd/mtp.py`'s
own `DeepseekV32MTP` has the same gap, but it is a different file with its own pre-head
path and is out of scope for this PR.

This PR adds the two forwarding methods, mirroring the `compute_logits` pair already in
the file. The capability has been rolled out per model since the flag landed in #34049,
and `deepseek_v3` was never covered on any platform.

### Which checkpoints this actually reaches

Resolving real `config.json`s through `hf_config_override` and the registry on
`main@94f4170df3` (ROCm), then asking the speculator's own question
(`hasattr(cls, "get_top_tokens")`). Of the current flagship checkpoints that ship MTP
layers at all:

| verdict | checkpoints |
|---|---|
| **reached by this PR** | DeepSeek-R1-0528 (fp8 and MXFP4) |
| already had the method | GLM-5.3-Flash (`glm5_next` → `Glm5NextMTP`) |
| still blocked, different class | DeepSeek-V3.2, GLM-5.2, GLM-5.3 (ROCm: `amd/mtp.py`); DeepSeek-V4-Flash / -Pro, DeepSeek-V4.1-Flash, MiniMax-M3 |

What it does not reach matters as much. On ROCm the DSA family now has its own drafter
class, as do the DeepSeek-V4 line and MiniMax-M3; on CUDA the DSA family already works
through `nvidia/mtp.py`. Kimi-K3, Qwen3.5-397B, Qwen3.8-Flash-Next and Qwen3-Next-80B ship
no MTP layers in the checkpoints checked.

### Scope

Resolving every entry of `_SPECULATIVE_DECODING_MODELS` on `main@94f4170df3` and asking
`hasattr`, 27 of the 62 speculative architectures satisfy the guard and 34 do not, so this
flag is broadly unavailable rather than uniquely broken here. 24 of the 27 get it from
`LocalArgmaxMixin` (the EAGLE, DFlash and DSpark families, plus Qwen3.5 MTP); only
`Gemma4MTP`, `InklingMTP` and `Glm5NextMTP` write the method themselves (plus
`DeepseekV32MTP` in the CUDA-only `nvidia/mtp.py`).

This PR fixes one of the 34 rather than sweeping them, because the correct call differs
per family and getting it wrong is silent:

- `deepseek_mtp.py`'s draft layer returns `(pre-final-norm, post-final-norm)` and the
  proposer consumes the first element, so `compute_logits` — and therefore
  `get_top_tokens` — must apply `shared_head` (the final RMSNorm).
- `deepseek_v32/nvidia/mtp.py`'s layer returns the post-norm hidden in both tuple
  positions, so its `get_top_tokens` correctly applies the LM head only.

Reusing the second form in the first file does not raise; it just returns a different
draft token. The added test is built to fail in that case (see Test Result). Extending
this to the remaining families needs the same per-family check, which is better done in
separate PRs by people who can run those models.

A second commit amends the flag's own docstring. It currently says only "reduces
communication from O(vocab_size) to O(2 * tp_size)", which reads as unconditional; the
measurements below show it is a break-even-dependent trade, and low-concurrency serving
at high TP is the case where the current wording would mislead someone into enabling it.

`LocalArgmaxMixin` in `models/interfaces.py` is the right tool where it fits, and
`Qwen3_5MTP` shows it fits some MTP models: it owns a flat `self.lm_head` and its
`compute_logits` is just `self.logits_processor(self.lm_head, hidden_states)`. This class
is not like that. It has no `self.lm_head` at all — the head is
`self.layers[str(mtp_start + spec_step_idx)].shared_head.head`, chosen per draft step,
and the hidden state has to pass through `shared_head`'s norm first. The mixin reads
`self.lm_head` and applies no norm, so it cannot serve this class.

### What this cannot affect

`use_local_argmax_reduction` defaults to `False`, and every call site of
`get_top_tokens` is behind it — no site probes for the method to auto-enable anything.
With the flag off, this PR adds two unreachable methods and changes nothing.

## Test Plan

```bash
pytest tests/v1/spec_decode/test_mtp_local_argmax.py
pytest tests/v1/sample/test_head_dtype.py   # existing coverage of get_top_tokens
```

New `tests/v1/spec_decode/test_mtp_local_argmax.py` builds a real `SharedHead`
(RMSNorm + `ParallelLMHead`) and `LogitsProcessor` on a single vocab shard and asserts
`get_top_tokens()` picks the same token as `compute_logits().argmax(-1)`, including with
a padded vocab. The norm's weight is given a non-uniform gain on purpose: the argmax is
invariant to the norm's per-row rescale, so a default all-ones weight would let a
skipped `shared_head` pass unnoticed.

End to end, on a `deepseek_v3` checkpoint (DeepSeek-R1-0528, official fp8 weights) at TP=4,
with a fresh server per run:

```bash
vllm serve deepseek-ai/DeepSeek-R1-0528 -tp 4 --max-model-len 4096 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":1,
                         "use_local_argmax_reduction":true}'
vllm bench serve --model deepseek-ai/DeepSeek-R1-0528 --dataset-name random \
  --random-input-len 1024 --random-output-len 512 --num-prompts 288 \
  --max-concurrency 64 --ignore-eos --seed 1234 \
  --percentile-metrics ttft,tpot,itl,e2el
```

The base arm is upstream `main` with the flag off; with it on, `main` raises at engine
init.

## Test Result

Hardware for every number below: MI355X (gfx950), ROCm. Correctness and micro numbers
are at real model shapes in bf16 at TP=2 and TP=4; GSM8K and end to end are
DeepSeek-R1-0528 (official fp8 weights) at TP=4 against `main@94f4170df3`.

### Correctness

`tests/v1/spec_decode/test_mtp_local_argmax.py`: 3 passed. Mutating the patch to drop
`shared_head` from `get_top_tokens` turns 2 of the 3 into failures, so the equivalence
assertion is load-bearing rather than decorative.

`tests/v1/sample/test_head_dtype.py`: identical results with and without this PR
(7 passed, 1 pre-existing failure in the `core_model` e2e test, which downloads
`facebook/opt-125m`).

Token-for-token equivalence over a sweep at real model shapes, **TP=2**, batch sizes 1 to
1024: **agreement 1.0000 in all 20 cases**. Cross-rank tie-breaking is the part a
single-shard test cannot reach, and it agrees too. The same sweep run against a variant
that skips `shared_head` agrees on as little as **0 %** of tokens.

Before this PR, the `vllm serve` / `vllm bench` invocation above raises the `ValueError`
at engine init. After it, both workers log

```
Using local argmax reduction for draft token generation
(communication: O(2*tp_size) vs O(vocab_size)).
```

and generation completes.

### Accuracy (GSM8K)

A vocab-parallel argmax is a reduction-order change, so "the unit tests pass" does not
cover it. On DeepSeek-R1-0528, all 1319 items, 5-shot greedy: **no measurable accuracy
change on GSM8K, within the base-repeat noise floor.** Patched scores 0.9568 against
0.9530 / 0.9560 for two runs of `main` — a base-vs-base drift of 0.0030, which the
patched-vs-second-base difference (+0.0008) sits well inside. Per-sample agreement is
inside the same control range. Full table in the comment below.

### Micro benchmark

The two providers on a real vLLM process group with a real `SharedHead` and
`LogitsProcessor`, driven through the patched predictor so the only difference between
arms is the collective:

- baseline — `compute_logits(h).argmax(-1)`, what the drafter does today
- patched — `get_top_tokens(h)`

Five interleaved pairs per point, arm order alternated per pair, 300 iterations after
100 warmup, no other tenant on the box. The `delta` column is what actually matters:
both arms pay the same per-call launch overhead (~200 µs in this harness, which times
the sampling step in isolation), so the *percentage* exaggerates the cost at small batch
and the absolute difference does not.

So the trade is a **fixed per-step overhead — one extra small collective, ~20 µs at TP=2
and ~95 µs at TP=4 — against a gather that grows with `batch × vocab_size`.** The patched
arm is nearly batch-independent (382–392 µs across bs=1..512 at TP=4); the baseline is
not. Break-even draft batch is **≈ 16–32 at TP=2 and ≈ 128–256 at TP=4**, and it moves
right as `tp` grows because the reduction's own collective is latency-bound while the
gather it replaces is bandwidth-bound.

Being explicit about the cost: **below break-even this is a regression**, up to -41 % of
the sampling step at TP=4 bs=1 (which is +90 µs in absolute terms). A batch-size median
is a bad summary here since it just reflects which batch sizes one tabulates; the
crossover and the absolute delta are the honest statement. The flag is opt-in, so the
decision can be made per deployment, and the numbers above are what it should be made on.

Token agreement was asserted at every point before timing: **1.0000 in all 40 cases
across TP=2 and TP=4.** Cross-rank tie-breaking is what a single-shard test cannot
reach, and it agrees at both rank counts.

Communication per draft step, derived from `logits_processor.py` rather than measured:
the default path materializes a `[batch, vocab_size]` logits tensor on every rank, the
reduction gathers `[batch, 2 * tp_size]` fp32 instead.

### ZhengGong-amd · 2026-09-16

### Why this cannot regress NVIDIA

The measurements in the description are MI355X, so it is worth being explicit about what
this change can and cannot do on CUDA. There is no NVIDIA card on the machine I used, so
everything below is read off the dispatch tables and the call sites rather than measured
— stating which is which.

**1. The default path is untouched on every platform.**
`SpeculativeConfig.use_local_argmax_reduction` defaults to `False`, and every call site
of `get_top_tokens` sits behind it (`speculator.py`, `llm_base_proposer.py`,
`step3p5.py`). Nothing probes for the method to auto-enable anything — the two
`hasattr` checks run only *inside* `if self.use_local_argmax_reduction`. With the flag
unset, this PR adds two methods that are never called.

**2. The models that already had the method on CUDA are not touched.**
`deepseek_v32` and `glm_moe_dsa` checkpoints resolve to `DeepseekV32MTPModel`, and
`vllm/models/deepseek_v32/__init__.py` dispatches that to
`vllm/models/deepseek_v32/nvidia/mtp.py` under `current_platform.is_cuda()`. That module
implements `get_top_tokens` already. This PR edits
`vllm/model_executor/models/deepseek_mtp.py`, which is the *non*-CUDA target of that same
dispatch, so DeepSeek-V3.2 and GLM-5.2 on NVIDIA are unaffected either way.

**3. The one NVIDIA-visible change is a configuration that used to be impossible.**
To be accurate rather than reassuring: `deepseek_v3` checkpoints (DeepSeek-V3, R1) are
*not* platform-dispatched. `SpeculativeConfig.hf_config_override` gives them
`DeepSeekMTPModel`, and `registry.py` maps that to `("deepseek_mtp", "DeepSeekMTP")` with
no platform branch — so on CUDA too, a DeepSeek-V3 MTP drafter is this class. Today
`use_local_argmax_reduction=True` raises for it on NVIDIA exactly as it does on ROCm;
after this PR it starts and runs. That is a strict addition: no NVIDIA user who does not
set the flag sees any difference, and no NVIDIA user who does set it was working before.

This is also the case I exercised most heavily: DeepSeek-R1-0528 is a `deepseek_v3`
checkpoint, so the end-to-end runs in the description go through exactly the dispatch an
NVIDIA user would, and differ from CUDA only in the interconnect underneath the
collective. The logic being validated is platform-independent; only the constants are
not.

**4. Nothing platform-specific is added.**
The diff is two Python forwarding methods. No kernel, no `current_platform` branch, no
HIP or CUDA code. They call `LogitsProcessor.get_top_tokens()`, which is existing core
code with existing CUDA coverage in `tests/v1/sample/test_head_dtype.py`, and which four
other MTP families already call on CUDA.

**5. What a CUDA reviewer may want to re-measure.**
The mechanism — replacing a `[batch, vocab_size]` all-gather with a
`[batch, 2 * tp_size]` one — is interconnect-bound, so the crossover batch size will sit
somewhere else on NVLink than it does on this box. On MI355X the reduction starts paying
at draft batch ≈ 16–32 at TP=2 and ≈ 128–256 at TP=4; below that it costs a fixed
~20 µs (TP=2) to ~95 µs (TP=4) per draft step. The sign of the effect at small batch is
the part most likely to differ on NVIDIA, and it is also the part that matters least,
since the flag is opt-in.
