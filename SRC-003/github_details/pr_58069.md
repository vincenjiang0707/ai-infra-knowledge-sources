### zyongye · 2026-09-22

Heads-up: this bump breaks the DeepSeek V4/V4.1 sparse MLA backends, which aren't touched here.

On 1x GB300 (SM103), TP4, DeepSeek-V4.1-Flash with `--attention_config.backend=FLASHINFER_MLA_SPARSE_DSV41`, all four ranks die during warmup:

```
File "vllm/models/deepseek_v41/nvidia/flashinfer_sparse.py", line 595, in _forward
  flashinfer_trtllm_batch_decode_sparse_mla_dsv4(
File "flashinfer/mla/_core.py", line 2367, in trtllm_batch_decode_sparse_mla_dsv4
  raise ValueError(
ValueError: sparse_indices_are_storage_offsets must be set for strided KV pools
```

**Cause.** 0.7.0 (flashinfer-ai/flashinfer#3856) adds `sparse_indices_are_storage_offsets` and makes it mandatory when either KV pool is strided:

```python
has_strided_pages = any(
    kv_cache.stride(-2) != kv_cache.size(-1)
    or kv_cache.stride(0) != kv_cache.size(-2) * kv_cache.stride(-2)
    for kv_cache in (primary_kv_cache, swa_kv_cache))
if has_strided_pages and sparse_indices_are_storage_offsets is None:
    raise ValueError(...)
needs_index_remap = has_strided_pages and not sparse_indices_are_storage_offsets
```

vLLM's packed DSv4 KV pools hit `has_strided_pages`, and vLLM already pre-remaps logical page indices to physical storage rows itself (`_remap_flashinfer_index` in `vllm/models/deepseek_v4{,1}/common/ops/cache_utils.py`, whose comment says *"TODO: remove once flashinfer-ai/flashinfer#3856 is fixed"* — this release is that fix).

**Fix.** Pass `sparse_indices_are_storage_offsets=True` at the trtllm-gen call sites in `vllm/models/deepseek_v4/nvidia/flashinfer_sparse.py` and `vllm/models/deepseek_v41/nvidia/flashinfer_sparse.py` (both the decode and prefill launches in `_forward`). Only `backend="trtllm-gen"` accepts the kwarg — the SM120 `sparse` path raises if it's passed.

The alternative is to act on that TODO: drop vLLM's remap and pass `False`, letting FlashInfer remap. If you do, also pass a persistent `remapped_sparse_indices_buffer`, since otherwise 0.7.0 does `torch.empty_like(sparse_indices)` on every call.

**Worth care either way:** omitting the flag fails closed, but the *wrong* value fails open — `True` without vLLM's remap, or `False` with it, silently reads the wrong KV rows instead of raising. The declaration and the remap have to change together.

Two other notes:
- A signature/import diff of 0.7.0 vs 0.6.18.post1 across everything `vllm/utils/flashinfer.py` wraps comes back clean (all 24 module/symbol pairs resolve, no params removed). This break is a new *runtime* validation, so static checks won't surface it — the affected paths have to be run.
- Unit tests aren't enough here either: `tests/v1/attention/` sparse-MLA suites pass against stock 0.7.0 on this machine, because they don't construct a strided KV pool. It only fails in a real engine.

Found while validating an unrelated change on this hardware; investigation was AI-assisted.
