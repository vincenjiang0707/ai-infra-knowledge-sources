### 🐛 Describe the bug

Enabling multimodal inputs **and** native MTP speculative decoding together kills the
engine during startup memory profiling. Either feature alone works fine; only the
combination fails.

`Qwen3.8-27B` is a hybrid — 64 layers, 48 `linear_attention` (GDN) + 16 `full_attention`
— with a vision tower and a shipped `mtp.safetensors`.

**Fails:**

```bash
vllm serve Qwen/Qwen3.8-27B-FP8 \
  --max-model-len 262144 --gpu-memory-utilization 0.5 --kv-cache-dtype fp8 \
  --max-num-seqs 8 --max-num-batched-tokens 8192 \
  --limit-mm-per-prompt '{"image":2,"video":0}' \
  --speculative-config '{"method":"qwen3_5_mtp","num_speculative_tokens":2}'
```

**Works — images, no MTP:**

```bash
  --limit-mm-per-prompt '{"image":2,"video":0}'          # serves; VQA verified correct
```

**Works — MTP, no images:**

```bash
  --limit-mm-per-prompt '{"image":0,"video":0}' \
  --speculative-config '{"method":"qwen3_5_mtp","num_speculative_tokens":2}'
```

So it is images XOR MTP.

The failing access is Dynamo's `call_size` on a `None` that reaches the compiled
`qwen3_next` forward — i.e. a tensor argument the graph expects (`inputs_embeds`, by the
shape of `qwen3_5.py:591`) is `None` for the multimodal dummy run when the MTP draft is
configured, where it is not `None` without MTP.

### What I already ruled out

> Reproduced on **stock `vllm==0.30.0`** from the wheel, before any local modification.
> The site-packages edit described below was applied afterwards, and the crash is
> identical with and without it.

- **#52485 / #52481 is a different bug.** Before patching, startup logged the misleading
  pair this PR addresses:
  ```
  WARNING Model Qwen/Qwen3.8-27B-FP8 is treated as multimodal but has no registered
          multimodal processor; running in text-only mode.
  INFO    Disabled mm_prefix attention mode because multimodal inputs are
          configuration-disabled.
  ```
  I applied #52485's five-line change to `ModelConfig._supports_multimodal_for_mm_prefix`
  locally. **Those warnings disappear and the crash is unchanged** — so the registry
  misfire is real but is not this.
- **#55369** ("Resolve n_predict from text_config for Qwen3.5 multimodal MTP") is merged
  and present in 0.30.0.
- **Attention backend**: `VLLM_ATTENTION_BACKEND=TRITON_ATTN` appears to be **ignored** —
  startup still logs `Using FLASHINFER attention backend out of potential backends:
  ['FLASHINFER', 'TRITON_ATTN']`, so I could not test whether #46558 (FlashInfer mm-prefix
  attention, unmerged) is implicated. If there is a supported way to force the backend in
  0.30.0 I am happy to retest.

### Expected behaviour

Either both features work together, or the incompatibility is detected at config
validation and reported clearly, rather than surfacing as an `AttributeError` inside a
compiled graph during memory profiling.

### Impact

For an interactive coding deployment this is a real trade rather than a cosmetic one.
Measured on this machine at 30k input, `--gpu-memory-utilization 0.5`:

| concurrency | TPOT MTP on | TPOT MTP off |
|---|---|---|
| 1 | 4.16 ms | 9.43 ms |
| 4 | 26.09 ms | 21.93 ms |
| 8 | 39.62 ms | 40.66 ms |

MTP is worth ~2.3x on single-stream decode, so giving it up to gain vision is costly, and
vice versa.

### twu3202 · 2026-09-23

This looks like #50891 rather than an MTP + multimodal incompatibility. The traceback is the one from that issue: `decorators.py` loading an AOT artifact from disk (`aot_compiled_fn`), then Dynamo's `call_size` on a `None` argument inside the compiled `qwen3_next` forward. The compile-cache key includes the speculative config but not `limit_mm_per_prompt` (`ModelConfig.compute_hash()` lists `multimodal_config` and `limit_mm_per_prompt` in `ignored_factors`). So your "MTP, no images" run built the artifact for the text-only path (`input_ids`, no `inputs_embeds`), and the "images + MTP" run loaded that same artifact and called it on the multimodal path. "Images, no MTP" has a different key, compiled fresh, and works. That is the XOR you saw, and the order of the runs is what decides which combination fails.

Two things would confirm it: the failing run's log should contain `Directly load AOT compilation from path .../torch_aot_compile/<key>/rank_0_0/model`, with the same key as the working text-only MTP run; and after `rm -rf ~/.cache/vllm/torch_compile_cache/torch_aot_compile` (or a separate `--compilation-config '{"cache_dir": ...}'`) the images + MTP command should start. `--enforce-eager` also avoids it. I hit the same collision on Qwen3.8-27B (a W4A16 checkpoint, 0.29.0 and 0.30.0) between an image-enabled run and a later `--limit-mm-per-prompt '{"image":0,"video":0}'` run of the same model. #50908 and #54642 both add the limits to the hash.


### kywch · 2026-09-23

@twu3202 Confirmed — dup of #50891. Reproduced both directions on B200, vLLM 0.30.0, Qwen3.5-27B-FP8.

Hashes collide directly:

```python
from vllm.config.model import ModelConfig
m = "Qwen/Qwen3.8-27B-FP8"
ModelConfig(model=m, limit_mm_per_prompt={"image": 2, "video": 0}).compute_hash()
ModelConfig(model=m, limit_mm_per_prompt={"image": 0, "video": 0}).compute_hash()
# both f934e595be5fc64a1b90030f1826657338a37749b1a896dc34c884956b282f0d
```

With MTP on throughout: cold cache + `{"image":2}` boots and saves `e1a2cf3a…`; reusing that cache with `{"image":0}` then crashes at `qwen3_next.py:688` → `call_size` → `AttributeError: 'NoneType' object has no attribute 'size'`. Reversed order gives the same crash. Whichever config compiles first owns the artifact.

Three notes on the workaround:
- The AOT dir comes from `VLLM_CACHE_ROOT` only, so `rm -rf ~/.cache/vllm/...` misses it if you override that env var.
- `--compilation-config '{"cache_dir": ...}'` does **not** isolate it — that field is for the non-AOT backend. Use a separate `VLLM_CACHE_ROOT` per config.
- `VLLM_USE_AOT_COMPILE=0` beats `--enforce-eager`: keeps inductor + CUDA graphs, boots in ~70 s on the poisoned cache.

Multimodal + MTP is not broken — with its own cache root it runs fine: 4.18 ms TPOT / 145 tok/s at concurrency 1, 30k input (vs 9.43 ms / 85 with MTP off), spec-decode acceptance 82.9%, and a 6-test vision battery passes including two images per request.

#50908 and #54642 both fix this — #50908 hashes the zero-limit modality set, #54642 hashes the counts plus `enable_mm_embeds`. Either separates `{"image":2}` from `{"image":0}`. Anything blocking them?
