# [PR #52668] [ROCm][Perf] Use a stacked hipBLASLt GEMM for the bf16x3 router

## 正文

## Motivation

Three in-tree models build their MoE router with fp32 weights: MiniMax-M3, MiniMax-M2 and HunYuan-V3. On ROCm none of the specialized `GateLinear` tiers accept an fp32 weight, so the router falls back to `F.linear`. That fallback casts the bf16 activations up to fp32 in a separate kernel, then runs the matmul on the fp32 MFMA pipe, which on gfx950 is roughly 16x slower than the bf16 one.

MiniMax-M3 has 57 MoE layers, so every forward pass pays for this 57 times.

Everything below was measured on `amd/MiniMax-M3-MXFP4` on 4x MI350X. MiniMax-M2 and HunYuan-V3 take the same code path but were not benchmarked.

## Proposed Fix

At load time the fp32 router weight is split into three bf16 terms that add back to it exactly, since three bf16 mantissas carry the same 24 bits fp32 does.

The terms are stacked into one `(3E, K)` weight, so the router becomes a single bf16 matmul writing fp32 output, plus a small kernel that sums the three result blocks. Activations stay in bf16 and the matmul runs on the fast bf16 pipe.

Sigmoid, bias add and top-k are unchanged. Below 2048 tokens the fp32 path is faster and this tier declines. 

Scoped to gfx950 for now.

### Router GEMM, measured on one GPU

MiniMax-M3 router shape (K=6144, E=128):

| tokens | before | after | speedup |
| ------ | ------ | ----- | ------- |
| 2048   | 46.5 us | 34.1 us | 1.36x |
| 4096   | 79.1 us | 39.9 us | 1.98x |
| 8192   | 145.4 us | 60.5 us | 2.40x |
| 32768  | 618.9 us | 201.2 us | 3.08x |

A second shape (K=3072, E=256) runs 1.44x to 2.46x over the same range.

### Accuracy, against an fp64 reference

| | relative L2 error at 8192 tokens |
| --- | --- |
| fp32 fallback (before) | 1.4e-6 |
| this PR | 4.9e-7 |

Across both router shapes at 2048, 8192, 16384 and 32768 tokens, this PR picks the same experts as the fp64 reference for every token. The fp32 fallback misses one token in one of those eight cases.


### Unit tests

`tests/kernels/test_bf16x3_router_gemm_rocm.py` and additions to `tests/kernels/test_gate_linear_rocm_dispatch.py`: 29 test functions, 23 of which need no GPU and run in normal CI. They cover bit exact reconstruction of the split across the full fp32 normal range, the inf/NaN contract, the eligibility predicates, and accuracy against fp64.

## Update 17 September

#54845 landed a ROCm router kernel for the same three models while this was open. It covers up to 32 tokens while this PR starts at 2048. But they were checked in the wrong order: the low-M tier is consulted first and always returns, so this PR's kernel was never reached above 32 tokens.

Commit 2782fc4 checks this tier first and hands small batches back to the low-M kernel, so both keep their measured range. Also restores a logger #55899 removed, which this PR calls at model load. I verified on MI355X: at 32 tokens all three models use #54845's kernel, at 2048 and 8192 they use this one.
