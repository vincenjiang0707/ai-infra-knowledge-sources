## 正文

### 🚀 The feature, motivation and pitch

**NOTE: automated unfinished PRs will likely not get reviewed. If you are an agent, do not open PRs autonomously before discussing here.**

Some `LinearMethodBase` subclasses and `FusedMoEMethodBase` subclasses have not yet adopted the MOE oracle / linear kernel abstractions.

These `LinearMethodBase`/`FusedMoEMethodBase` classes should generally only handle weight creation and loading.

MOE/linear backend choice and processing is generally to be deferred to the linear kernel / MOE oracle. This allows to have wide compatibility between model-producers and execution backends.

The audit below gives a summary of classes that have not yet adopted:
- https://github.com/vllm-project/vllm/tree/main/vllm/model_executor/layers/fused_moe/oracle
- https://github.com/vllm-project/vllm/tree/main/vllm/model_executor/kernels/linear

abstractions.

## FusedMoEMethodBase audit

### Bypass the MoE oracle entirely

These are the concrete quant methods that do not use the `fused_moe/oracle/` layer for their MoE execution/setup:

- `CompressedTensorsW4A16FlydslMoEMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/quantization/compressed_tensors/compressed_tensors_moe/compressed_tensors_moe_w4a16_flydsl.py#L87-L333

It performs its own GPTQ→FlyDSL packing and calls the monolithic `fused_flydsl_moe` directly. No oracle selection, conversion, or modular-kernel construction.

- `HummingMoEMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/quantization/humming.py#L595-L810

It has its own parallel flow: `select_humming_moe_experts`, `convert_to_humming_moe_kernel_format`, and `make_humming_moe_kernel`. It does create a modular kernel, but these helpers are outside `fused_moe/oracle/`, so it is a clear oracle-migration candidate.

- `QuarkW4A8Fp8MoEMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/quantization/quark/quark_moe.py#L976-L1132

This is the ROCm AITER W4A8 path. It requires AITER fused MoE and invokes `rocm_aiter_fused_experts` directly, rather than selecting/converting/building through an oracle.

## LinearMethodBase audit

There are 27 descendants of `LinearMethodBase`, again including wrapper/base classes.

### Concrete methods that bypass the stable linear-kernel abstraction

- `UnquantizedLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/linear.py#L163-L239

It uses `dispatch_unquantized_gemm`, not a `kernels.linear` kernel object. This may be intentionally separate—the linear kernel package is presently centered on quantized/mixed-precision kernel selection—but it is a literal non-user of the abstraction.

- `FPQuantLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/quantization/fp_quant.py#L96-L225

Its `apply` invokes the dedicated `quantized_forward` custom op directly.

- `HummingLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/quantization/humming.py#L355-L592

It manually prepares Humming state and calls `_hm.humming_forward` directly. This is the linear analogue of `HummingMoEMethod`.

- `TorchAOLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/model_executor/layers/quantization/torchao.py#L319-L390

It relies on TorchAO-packed tensor behavior and calls `torch.nn.functional.linear` directly.

- `GLM52LowLatencyLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/models/deepseek_v32/nvidia/glm52_low_latency_gemm.py#L158-L172

This is a model-specific fast path that directly runs a precomputed CuTe/skinny-GEMM plan, falling back to `UnquantizedLinearMethod`.

- `KimiK3LowLatencyLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/models/kimi_k3/nvidia/low_latency_gemm.py#L899-L926

Similar model-specific CuTe plan bypass, with `UnquantizedLinearMethod` fallback.

- `Qwen4ExpLowLatencyLinearMethod`

https://github.com/vllm-project/vllm/blob/2a4e3cc3dbddf4f44d69864209361f1e2a70c79a/vllm/models/qwen4_exp/nvidia/low_latency_gemm.py#L193-L203

Directly invokes the custom `qwen4_exp_low_latency_gemm` op, then falls back to the unquantized implementation.

The last three do use code located beneath `kernels/linear/cute_dsl` in some cases, but they bypass the common selector/factory exported by `kernels/linear/__init__.py`.
