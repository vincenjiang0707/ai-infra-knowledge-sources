# [PR #55277] [Bugfix][SM120][MLA] Support NoPE sparse MLA (GLM-5.3-Flash) on the FlashInfer SM120 backend

## 正文

## Purpose

Enable native NoPE (`qk_rope_head_dim=0`) cache writes for GLM-5.3-Flash on `FLASHINFER_MLA_SPARSE_SM120`, without padding the query or allocating a synthetic RoPE tensor.

Rebased onto `a6131b0e656e18eeb3797b8856aa3dbc69efd8e5`. The former physical top-k capacity patch has been dropped: #53781 already implements it in the shared `_run_mqa_kernel`, including HiSparse paths. This PR now contains the cache-writer fix and regression tests only.

## Changes

- Accept `pe_dim` 0 or 64 for `fp8_ds_mla`.
- Preserve the existing 656-byte cache row: 512 bytes of FP8 latent, 16 bytes of FP32 tile scales, and 128 bytes of RoPE/reserved storage.
- For NoPE, do not read the empty `k_pe` tensor; zero the reserved tail. The 64-dimensional RoPE path is unchanged.
- Compare BF16 NoPE writes byte-for-byte with the existing zero-RoPE path at block sizes 64/256. Fixed slots cover a block boundary and an invalid token; explicit assertions check zero tails and untouched sentinel rows. Existing tests retain responsibility for quantization correctness.

## Dependencies and related work

FlashInfer native GLM53_NOPE support (#4802) and backend-scoped length validation (#4947) have merged. Later #5075/#5197 implementations accept the existing 656-byte padded pool through runtime row stride; this PR deliberately does not change vLLM cache allocation to compact 528-byte rows.

The validation below uses FlashInfer source revision `dc04f50c9aa3eabcdaa5feb0934edb3d85e9529a`, which includes those later changes. vLLM's default `flashinfer-python==0.6.18.post1` pin does not provide native GLM53_NOPE support: this writer change alone does not make the default pinned stack sufficient. No dependency bump is bundled here.

This is the existing native-kernel alternative to the padding approaches in #53969 and #55778, not a new duplicate PR. Native NoPE avoids manufacturing a 64-dimensional query/RoPE lane. Credit to @hamiltongaianimd for originally surfacing the kpool width issue; that part is now handled upstream. The independent warmup changes in #55264 are not included.

### Validation limitation: distributed autotune

The unmodified all-operator autotune configuration did **not** pass startup. Leader-only sparse warmup populated rank-local tuning entries; the later distributed pass showed asymmetric cache hits and follower Gloo all-reduce timeouts. Skipping only dense `fp4_gemm` exposed the same pattern in CUTLASS MoE GEMM1, whose cache keys include `tp_rank`.

Successful serving/evaluation/benchmark runs explicitly used:

```text
VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS=fp4_gemm,trtllm::fused_moe::gemm1,trtllm::fused_moe::gemm2
```

FlashInfer autotune otherwise remained enabled. This is a disclosed validation workaround, not an autotune fix or a claim that the original configuration passes. These performance numbers are specific to this configuration. No warmup workaround code is included in this PR. FP16 was not qualified; a separate scale-conversion issue also reproduces with the existing 64-dimensional RoPE writer.
