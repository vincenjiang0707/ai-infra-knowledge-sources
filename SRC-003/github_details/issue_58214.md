## 正文


### Summary

`CPUModelRunner._postprocess_triton()` installs C++ fallbacks for Triton kernels
when Triton is unavailable. Six of those patches rebind a **module-level global**
that nothing reads at call time any more, so the fallbacks are never installed.

This is the production path on `linux/arm64` and macOS: `docker/Dockerfile.cpu:139`
builds `triton-cpu` only for `TARGETARCH=amd64`, so `HAS_TRITON` is `False` there.
The x86 CPU lane has Triton, so CI never exercises these fallbacks.

### Root cause: a regression in #56323

Commit `aed894c19` (#56323, "[6/N][warmup][DSv4] Migrate sampling, and DFlash JIT
kernels") moved these kernels behind `@triton_kernel_dispatcher_with_warmup`.
The dispatcher captures the kernel into the **instance** at import time
(`jit_warmup_triton_helper.py:656`) and launches `self.kernel` (`:270`).

Before that commit the kernels were launched by module-global lookup, so the
monkey-patch worked. At parent `e19a3e172`, `rejection_sampler.py:597` read:

```python
expand_kernel[(batch_size,)](...)      # name resolved at call time
```

Today `expand_batch_to_tokens` calls the dispatcher instead
(`rejection_sampler.py:612`), and rebinding `rejection_sampler.expand_kernel`
has no effect.

#56323 updated 3 of the patches to the new `.kernel` form (+3/-4 in
`cpu_model_runner.py`) and left the rest in the old style.

### The 6 dead patches (`vllm/v1/worker/cpu_model_runner.py`)

| line | patched name | dispatcher that actually holds the kernel |
|---|---|---|
| 94  | `spec_decode_utils.copy_and_expand_dflash_inputs_kernel` | `_copy_and_expand_dflash_inputs` (utils.py:782) |
| 105 | `spec_decode_utils.eagle_step_slot_mapping_metadata_kernel` | `_eagle_step_slot_mapping_metadata` (utils.py:120) |
| 108 | `rejection_sampler.rejection_greedy_sample_kernel` | dispatcher at rejection_sampler.py:808 |
| 111 | `rejection_sampler.rejection_random_sample_kernel` | dispatcher at rejection_sampler.py:931 |
| 114 | `rejection_sampler.expand_kernel` | `_expand` (rejection_sampler.py:991) |
| 115 | `rejection_sampler.sample_recovered_tokens_kernel` | dispatcher at rejection_sampler.py:1112 |

Lines 97-104 additionally `setattr` the kernel onto the `vllm.v1.spec_decode.dflash`
module, but `dflash.py` imports the dispatcher `_copy_and_expand_dflash_inputs`
(`:16`) and calls it (`:149`); it never reads that name.

Correctly patched (for contrast): `block_table._COMPUTE_SLOT_MAPPING_KERNEL.kernel`,
`_eagle_prepare_inputs_padded.kernel`, `_eagle_prepare_next_token_padded.kernel`,
`_copy_and_expand_eagle_inputs.kernel`.

### Expected failure mode (derived from source, not yet executed)

Without Triton, `triton.jit` returns the function unchanged
(`vllm/triton_utils/importing.py:104-121`), so `self.kernel` stays a plain
function and `launch()` does `kernel[grid](**kwargs)`, which should raise:

```
TypeError: 'function' object is not subscriptable
```

This is the signature reported in #55480 for `mamba_utils.batch_memcpy`, which
reaches the same placeholder through a different route.

**I want to be explicit that I have not yet executed this.** The report above is
from reading the source and `git` history; my arm64 build is not finished. The
part I am confident in is the binding analysis, which is verifiable statically:
the dispatchers hold `self.kernel`, and nothing reads those module globals at
call time. If maintainers with a working arm64 CPU build can confirm the runtime
behaviour, that would settle it faster than my build will. I will post the
traceback here once mine completes.

### Relationship to other issues

- #55480 fixes `batch_memcpy` only, at its call site. Different kernel.
- #55005 / #55006 fix a dtype copy-back **inside** `_expand_kernel_impl`. That is
  orthogonal and currently unreachable on arm64, since the shim is never installed.

### Suggested fix

Retarget the six patches to the dispatcher objects' `.kernel`, matching the four
that are already correct, and drop the dead `dflash_module` block (which is the
only user of `import sys` in that file).

A more durable alternative, if maintainers prefer: have the dispatcher resolve
its kernel dynamically, so this class of breakage cannot recur silently.

### Verification script

Once built, this needs no model, server or GPU:

### The-iyed · 2026-09-22

## Confirmed at runtime, plus a correction and a second defect

I now have an arm64 CPU checkout importable (`HAS_TRITON = False`), so I can replace the analysis with measurements.

### 1. The dead patches are confirmed

A parametrized test over all nine dispatchers, asserting `_postprocess_triton()` actually installs each CPU fallback, on unmodified `main`:

```
6 failed, 3 passed
```

The six that fail are exactly the six patched via module-global rebinding; the three that pass are the three patched via `.kernel`. The assertion shows the mechanism directly:

```
AssertionError: assert <function sample_recovered_tokens_kernel at 0x...>
                    is <vllm.utils.cpu_triton_utils._FuncWrapper object at 0x...>
 +  where <function sample_recovered_tokens_kernel at 0x...> =
        <_DecoratedTritonJitKernel object at 0x...>.kernel
```

The dispatcher still holds the bare `@triton.jit` function (a plain function, since `triton.jit` is a no-op placeholder without Triton) rather than the CPU `_FuncWrapper`.

### 2. Correction to my predicted error message

I predicted `TypeError: 'function' object is not subscriptable`. **That was wrong.** The actual failure comes earlier, from `_kernel_arg_names` (`jit_warmup_triton_helper.py:238`) while inspecting the kernel's parameters:

```
TypeError: Cannot inspect kernel parameters for function
```

Same class and cause, different message — it never reaches the `kernel[grid]` subscript. Apologies for the inaccurate guess; it is corrected here.

### 3. A second defect: two shim signatures do not match the dispatch argument names

Retargeting the patches to `.kernel` is necessary but **not sufficient**. `_launch_binding_plan` binds each dispatch input to a kernel argument named `name`, `name_ptr`, `NAME` or `NAME_PTR`. Two CPU shims use names matching none of those, so once installed they fail:

```
TypeError: _expand_kernel_impl() missing 1 required positional argument: 'input_val'
```

- `_expand_kernel_impl` takes `input_val`; the dispatch input is `input`.
- `_eagle_step_slot_mapping_metadata_kernel_impl` takes `stride`; the dispatch input is `block_table_stride`, and that dispatch returns no launch kwargs to supply it.

The other seven bind correctly (`vocab_size` in the two sampling shims arrives via launch kwargs, so those are fine).

With both the retarget and the two renames, the call proceeds all the way into the bound C++ op — the only remaining error on my machine is `'_C' object has no attribute 'expand_kernel_impl'`, because my native extension build has not finished. That is my build, not the code path.

### Scope

So the arm64 CPU fallbacks need two changes, not one:
1. Point the six patches at the dispatchers' `.kernel`.
2. Rename the two shim parameters to the dispatch argument names.

I have both plus the regression test on a branch and will open a PR. Happy to split them if you would rather review them separately, and equally happy to defer if you prefer the durable alternative (having the dispatcher resolve its kernel dynamically), which would make item 1 unnecessary.
