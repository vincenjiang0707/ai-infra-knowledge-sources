### The bug

For Mistral models served with `--tool-call-parser mistral --enable-auto-tool-choice`, every chat completion request — including plain-text ones with `tool_choice="none"` and no `tools`— triggers a full rebuild of `MistralToolParser` → `ParserEngine` → `StreamingParserEngine`, which compiles `regex` patterns over the tokenizer's entire special-token vocabulary (`_build_drop_info` in `vllm/parser/engine/streaming_parser_engine.py`). This runs **synchronously on the main asyncio event loop**, not inside the renderer's `ThreadPoolExecutor` (unlike tokenization itself, which is offloaded via `make_async`). Under concurrent load this becomes a hard admission bottleneck: the event loop can't advance anything else while blocked on it, so requests back up long before ever reaching the scheduler.

Model: `mistralai/Mistral-Small-4-119B-2603`, served with `--tool-call-parser mistral --enable-auto-tool-choice --reasoning-parser mistral --tensor-parallel-size 2` on 2×H200. Confirmed present, unchanged, in both v0.29.0 and v0.30.0 (checked directly against source).

Root cause is `online_renderer.py`'s `preprocess_chat`:

```python
is_mistral_grammar_eligible = (
    tool_parser is not None
    and is_mistral_tool_parser(tool_parser)
    and is_mistral_tokenizer(tokenizer)
    and tokenizer.supports_grammar
)
should_adjust_request = (
    parser.reasoning_parser_cls is not None
    or tool_choice != "none"
    or is_mistral_grammar_eligible   # forces adjust_request unconditionally for Mistral
)
```

The comment above it explains this is intentional ("so that the grammar factory can prevent special-token leakage"), but the expensive part (`_build_drop_info`) depends only on the fixed tokenizer vocabulary/parser config — not on per-request `tools` or content — so it looks memoizable rather than needing reconstruction on every request.

**Reproduction:**
1. Serve a Mistral model: `vllm serve mistralai/Mistral-Small-4-119B-2603 --tool-call-parser mistral --enable-auto-tool-choice --reasoning-parser mistral --tensor-parallel-size 2 ...`
2. Send concurrent `tool_choice="none"` requests (no `tools`), e.g. `vllm bench serve --backend openai-chat --endpoint /v1/chat/completions --dataset-name random --random-input-len 512 --random-output-len 256 --num-prompts 200 --request-rate 16`.
3. Observe TTFT balloon and engine `Running` (from the periodic `Engine 000: ...` log line) stay near-flat despite high offered load, while GPU/KV-cache usage stays near-idle.
4. Remove `--tool-call-parser`/`--enable-auto-tool-choice`/`--reasoning-parser` and rerun — throughput and TTFT return to normal.

**Results observed vs. expected**, same benchmark (200 requests, request-rate=16, random 512-token prompts):

| | With the three flags | Without (diagnostic) |
|---|---|---|
| Mean TTFT | 39,013 ms | 101 ms |
| Output throughput | 604 tok/s | 3,213 tok/s |
| Engine `Running` (concurrent) | capped ~3-6 | 45-84 |
| GPU KV cache usage | ~0.1% | ~1.8% |

Expected: `Running` should scale with offered load regardless of these flags being set, the same way it does without them.

Confirmed via `py-spy dump --pid <APIServer pid>` mid-load that the `MainThread` (not a worker thread) is caught inside this exact construction path, with locals directly showing `tool_choice: "none"`, `is_mistral_grammar_eligible: True`, `should_adjust_request: True` for a request with no tools:

```
_create_chat_completion (vllm/entrypoints/openai/chat_completion/serving.py:275)
  render_chat_request (serving.py:240)
    render_chat (vllm/renderers/online_renderer.py:192)
      preprocess_chat (online_renderer.py:718)  [tool_choice: "none", is_mistral_grammar_eligible: True, should_adjust_request: True]
        MistralToolParser.__init__ (vllm/parser/engine/adapters.py:167)
          MistralParser.__init__ (vllm/parser/mistral.py:279)
            ParserEngine.__init__ (vllm/parser/engine/parser_engine.py:107)
              StreamingParserEngine.__init__ (vllm/parser/engine/streaming_parser_engine.py:133)
                _build_drop_info (streaming_parser_engine.py:73)
                  regex.compile(...)  # compiling patterns over hundreds of special tokens, per request
```

**Suggested fix:** cache `_build_drop_info`'s result (or the constructed `StreamingParserEngine`'s tokenizer-dependent state) keyed on tokenizer identity + parser config, separate from the genuinely per-request-stateful parts of the streaming parser — so `adjust_request` doesn't redo vocabulary-wide regex compilation on every request.
