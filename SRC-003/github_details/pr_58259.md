# [PR #58259] [Bugfix] Fix resumable request + async scheduling handoff race

state: open | updated: 2026-09-23T04:24:02Z

## 正文



## Purpose

Fixes a resumable-request handoff race when async scheduling is used. When a streaming turn stops, `_update_request_as_session()` uses `request.num_computed_tokens` as the prefix boundary for the next turn. That value is an optimistic frontier: it can already include input positions from older dispatches that are still in flight. When those dispatches later retire through `update_from_output()`, their output corrupts the new turn.

Consider a three-token prompt at turn 0 (`T0`). Let `A` be `all_token_ids`, `C` be `num_computed_tokens`, and `P` be `num_output_placeholders`.

```text
T0:              A=[0, 1, 2]                     P=0  C=0

  S0 scheduled:  A=[0, 1, 2]                     P=1  C=3
  S1 scheduled:  A=[0, 1, 2]                     P=2  C=4

    S0 runs worker on [0, 1, 2] and returns EOS

  S0 retired:    A=[0, 1, 2, EOS]                P=1  C=4
  _handle_stopped_request runs
  _update_request_as_session runs

T1:              A=[0, 1, 2, EOS, 3, 4]          P=1  C=4
```

`T1` is corrupted. It contains a spurious `EOS` token before the continuation. It will also receive a stale token after `S1` retires.

Other invariants are also broken.

### [#35755](https://github.com/vllm-project/vllm/issues/35755)

On the next scheduling step, the scheduler may do a chunked prefill on 2 prompt tokens:

```
T1:              A=[0, 1, 2, EOS, 3, 4]          P=1  C=4
  S2 scheduled:  A=[0, 1, 2, EOS, 3, 4]          P=1  C=6
```

Because `C < len(A) + P`, `S2` is considered to be a chunked prefill by the scheduler, so `P` isn't incremented. However, the worker will process `[3, 4]` of `[0, 1, 2, EOS, 3, 4]` as a final prefill, which yields a new token. When `S1` and `S2` eventually retire, `P` will be decremented twice, resulting in a `num_output_placeholders` underflow.


### [#52693](https://github.com/vllm-project/vllm/issues/52693)

Suppose `S1` retires before the `T1` continuation arrives and also outputs an
`EOS` token.

```
T0:
  ...
  S0 retired:    A=[0, 1, 2, EOS]                P=1  C=4
  _handle_stopped_request runs
  no continuation, request placed on skipped_waiting

    S1 runs worker on [0, 1, 2, EOS] and returns EOS again

  S1 retired:    A=[0, 1, 2, EOS, EOS]           P=0  C=4
  _handle_stopped_request
  no continuation, request placed on skipped_waiting again
```

The same request now appears on `skipped_waiting` twice. Before [PR #48245](https://github.com/vllm-project/vllm/pull/48245), this would cause `Invalid request status: RUNNING` on the next scheduler call. That PR added a call to `skipped_waiting.remove_requests()` for stopped preempted requests in `update_from_output`, removing the duplicate entries in `skipped_waiting`.

The fix resets the next turn to the safe frontier `F = C - P` before the stale placeholders. Thus `F=3` in the trace above; `F=10` is the corresponding value in [`repro_35755.py`](repro_35755.py). It marks the remaining in-flight results as stale, drops them via `drop_stale_output`, and drains them with `num_stale_output_tokens`.

#52765 is a similar but incomplete fix because it marks in-flight results stale only after `_update_request_as_session` has already used the optimistic `num_computed_tokens` boundary, allowing stale old-turn positions to remain in the next turn.
