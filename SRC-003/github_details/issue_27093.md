### 🚀 The feature, motivation and pitch

### Description of the Feature Proposal
This proposal outlines a new scheduling and execution mechanism called "Process-level PD Disaggregation". The core idea is to spatially partition a single GPU's resources to run compute-bound prefill operations and memory-bound decode operations concurrently.

This is achieved by launching separate processes for prefill and decode on the same GPU, managed by NVIDIA MPS  and multiple stream. This approach enables resource sharing between the two distinct workloads, improving overall GPU utilization and allowing the system to meet strict SLOs for both TTFT and ITL.

### Motivation for the Proposal
LLM serving in production environments faces a critical challenge: simultaneously optimizing for TTFT and ITL. During traffic surges, single-instance deployments struggle to balance these two metrics, making it difficult to meet strict SLOs, such as TTFT < 1.3s and avg. ITL < 30ms. 

The prefill stage is typically compute-bound, while the decode stage is memory-bound, leading to inefficient use of GPU resources when these operations are scheduled sequentially. A promising approach is to overlap these two phases to maximize resource utilization. This feature aims to implement such an overlapping mechanism to solve the trade-off between TTFT and ITL.

### Specific Problem
I'm working on serving a Qwen2-32B model under high, concurrent traffic and need to maintain a high-quality user experience defined by strict SLOs.

Current strategies, such as chunked prefill, are insufficient. Chunked prefill breaks a large prefill request into smaller chunks and batches them with decode requests. While this method effectively reduces ITL and improves GPU utilization compared to a prefill-priority policy, it introduces a severe regression in TTFT.

To validate this in our production environment (average output length of 4K, average input length of 12K), we tested the impact of different chunk sizes. Our findings show a direct and problematic trade-off: smaller chunk sizes lower ITL but dramatically increase TTFT. This is because each subsequent chunk must re-access the KV cache generated by previous chunks, introducing significant memory access and scheduling overhead.

The low utilization during communication  and the memory-bound nature of decode create a significant opportunity for optimization. By allowing prefill and decode to share GPU resources spatially, we can service high-priority decode requests while backfilling the GPU with compute-intensive prefill work.

### Proposed Solution
Inspired by concepts from works like Semi-PD, we propose implementing intra-instance prefill/decode disaggregation. This involves the following core features:

1. Multi-Process Architecture: For each GPU, we will launch two independent processes: one for Prefill and one for Decode. NVIDIA MPS will be used to enable spatial sharing of the GPU hardware, allowing kernels from both processes to execute concurrently.
2. Multi-Stream Execution: The Prefill and Decode processes will be mapped to separate CUDA streams. This allows the hardware to overlap operations.
3. Unified Cross-Process Memory Management: A unified memory manager will be created to handle the KV cache. This manager will use CUDA IPC to share GPU memory handles between the Prefill and Decode processes, ensuring the Decode process can seamlessly read the KV cache generated by the Prefill process.
4. SM Controller: It will dynamically modify the SM mask in the Thread Management Descriptor to control which kernels execute on which TPCs.
5. SLO-Aware Scheduler: The central scheduler will be enhanced to: 1) Route incoming requests to the Prefill and Decode processes. 2)Use an integrated simulator to predict the execution time of prefill and decode tasks. 3) Dynamically adjust the SM resource allocation based on current load and SLO targets.
6. Layer-wise Chunked Prefill: To avoid the high overhead of token-level chunking, prefill computation will be chunked at the layer level. This allows a long prefill to be paused and resumed between layers, creating opportunities for the scheduler to execute high-priority decode batches. A brief sleep or yield mechanism will be added to the prefill loop to ensure the Decode process can preemptively seize resources during contention.


Our proposed approach has been preliminarily implemented and validated on the sglang, where it has already demonstrated promising performance gains in balancing TTFT and ITL under our workload. This work is further detailed in our paper, "Boosting LLM Serving through Spatial-Temporal GPU Resource Sharing" and the proof-of-concept implementation is available at: https://github.com/zejia-lin/BulletServe.

We are currently in the process of refactoring and hardening the system for production use. We believe this “Process-level Prefill/Decode Disaggregation within a Single Instance” feature would be a valuable addition to vLLM. We are keen to collaborate with the community to integrate this functionality, enhancing vLLM's capabilities for serving mission-critical, low-latency LLM applications.
