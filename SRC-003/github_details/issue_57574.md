# [Issue #57574] [Feature]: Integer token IDs for logprobs in `/inference/v1/generate` responses (`GenerateLogProbs`)

## 正文

### 🚀 The feature, motivation and pitch

Tracking issue for the `GenerateLogProbs` shape redesign. @sagearc raised it on #42729 (https://github.com/vllm-project/vllm/issues/42729#issuecomment-4547904742).

#### The problem

`/inference/v1/generate` is a vLLM defined token in / token out API (#24261) but its output logprobs use an OpenAI shape. `GenerateResponseChoice.logprobs` and `GenerateResponseStreamChoice.logprobs` are `ChatCompletionLogProbs` where `token` is a string. The generate server has no tokenizer, so it writes every token as a `"token_id:N"` placeholder and derender parses the placeholders back out.

This causes a few problems:

- **The OpenAI shape leaks into a vLLM protocol.** Converting to OpenAI's string tokens belongs in derender (or the coupled chat / completions path), not on the generate server.
- **The format is an untyped string contract.** On the encoding side it's `_create_tokens_logprobs` in Python and `format_token_id` in the Rust frontend's `routes/inference/generate.rs`. On the decoding side it's `resolve_token_id_placeholder` and `_parse_token_id_placeholder`. Nothing in the schema says what `token` holds.
- **The two frontends already disagree on `bytes`.** Python leaves `bytes` unset. Rust sets it to the UTF-8 bytes of the placeholder itself (`"token_id:42"`). Derender overwrites it either way but a client reading generate directly gets different answers depending on the frontend.
- **One response, two shapes.** `prompt_logprobs` on the same `GenerateResponse` is already integer keyed (`list[dict[int, Logprob] | None]`). Output logprobs aren't.
- **Clients that want IDs have to parse strings.** A consumer reading generate directly (e.g. an RL rollout collector) gets top-k candidates only as placeholder strings. `rank` which the engine computes is dropped.

#### Proposal

A generate specific type with integer token IDs, for example:

```python
class GenerateLogProb(BaseModel):
    token_id: int
    logprob: float
    rank: int | None = None


class GenerateLogProbsContent(GenerateLogProb):
    top_logprobs: list[GenerateLogProb] = []


class GenerateLogProbs(BaseModel):
    content: list[GenerateLogProbsContent] | None = None
```

`content[i].logprob` and `content[i].top_logprobs[j].logprob` stay where they are today. `token` becomes `token_id` and `bytes` goes away. Derender converts this to `ChatCompletionLogProbs` / `CompletionLogProbs`, filling `token` and `bytes` from the tokenizer with the same U+FFFD correction it applies now (`_correct_decoded_token`). The placeholder parsing drops out of the generate → derender path.

`return_tokens_as_token_ids` on `/v1/chat/completions` and `/v1/completions` is out of scope. It's a user facing OpenAI option that uses the `token_id:N` format on purpose.

Scope:

- Python `/inference/v1/generate` (`scale_out/token_in_token_out`), streaming and non-streaming
- Rust frontend `/inference/v1/generate` (`routes/inference/generate`)
- derender, batch and streaming (`OnlineDerenderer`)
- docs and a release note

#### Open questions

- **Compatibility.** Generate has direct consumers. I'd lean toward replacing the field in one release with a release note. The API is vLLM defined and with the shape above, code that reads only `content[i].logprob` keeps working. The other options are an opt in request field that flips default later or a second field next to the current one (see Alternatives).
- **`rank`.** Include it? It's cheap, the engine already has it and the Rust frontend's gRPC `CandidateTokenInfo` carries it.
- **List or dict for `top_logprobs`.** A list keeps rank order explicit and maps field for field onto the OpenAI shapes. A `dict[int, float]` is smaller but JSON turns the keys into strings.
- **#57442.** That PR adds `choices[].token_logprobs: list[float]` to `GenerateResponseChoice` as a fast path for sampled token logprobs. Generate would then have three logprob shapes: placeholder strings, integer keyed `prompt_logprobs` and a flat float list. We should decide together whether `token_logprobs` stays a separate field or becomes a mode of `GenerateLogProbs`.

#### Done when

- [ ] Shape and compatibility approach agreed here, coordinated with #57442
- [ ] Python and Rust `/inference/v1/generate` return the new shape, streaming and non-streaming
- [ ] Derender converts it to the OpenAI shapes on the batch and streaming paths. Existing logprob tests pass, including U+FFFD correction and `test_derender_parity.py` logprobs still match coupled serving
- [ ] Docs describe the generate logprob shape. Release note written

### Alternatives

- **Keep the placeholders and document them.** Cheapest option. The format becomes an explicit part of the protocol, but the types stay loose and the `bytes` mismatch stays.
- **Carry raw engine `Logprob` dicts, like `prompt_logprobs`.** Reuses a shape that's already on the wire and lets derender share `_create_chat_logprobs` with coupled serving. But `Logprob.decoded_token` can't be filled without a tokenizer (the Rust frontend puts the placeholder in it) and it ties the wire format to an internal engine type.
- **Add the integer shape as a second field** instead of replacing `logprobs`. Nothing breaks but there are two shapes on the wire and both get paid for if a client asks for both.

Thanks for looping #57442 in. The two are complementary rather than competing shapes, and the measurement behind #57442 is what decides where the line should be: the cost of `logprobs=0` on generate is not the string-vs-int token, it is building one object per token (per-request `LogprobsLists` slicing → IPC → output processor → Pydantic). Skipping that path alone recovers ~1.00× at c256; keeping objects with integer ids would not. So `GenerateLogProbs` fixes the protocol problem for the top-k case, and `token_logprobs` is the "sampled token only" case that must not materialize per-token objects.

After #57574 lands that leaves two shapes with distinct semantics: top-k candidates as `GenerateLogProbs` (integer ids, rank), and sampled-only as a flat float list. #57442 already returns both when `logprobs > 0` (values identical) and only the flat list when `logprobs == 0`.

### shimib · 2026-09-21

+1 to the shape and to all three of @hickeyma's calls (replace in one release, keep `rank`, list for `top_logprobs`). Some input from the derender side and from our logprob benchmarking:

**Compatibility — replace, don't stage.** We consume generate + derender directly and treat `token_id:N` as an implementation detail, not a contract — it was never documented, and the Python/Rust `bytes` disagreement means anyone parsing it already gets frontend-dependent behavior. A one-release replace with a release note is right; a transition field would put two shapes on the wire for the exact workload where payload already hurts (see below).

**`top_logprobs` as a list — agreed, with one wire-size note.** Dense top-k is the one traffic shape we measured that stresses the derender tier (`top_logprobs=20` ≈ 355 µs/token resolution cost, frontend at 0.83 cores — the numbers in #56851). At k=20, `[{token_id, logprob, rank}, ...]` per position is a meaningfully fatter wire object than a dict, but the dict's
JSON string keys and the loss of explicit rank order aren't worth it. If payload ever matters enough, that's what `sampled` mode is for — worth a docs note steering RL/verification collectors to it.

**Derender conversion — the correction machinery is shape-independent.** 
One thing this redesign does *not* remove: the U+FFFD byte-fallback correction
needs the preceding sampled token IDs as context, and in streaming those arrive in earlier chunks. #55029 carries exactly that context across chunks (`logprob_context_token_ids`, bounded to the 4-token window `_correct_decoded_token` reads). 
That state and the correction machinery survive the move to integer IDs unchanged — what drops out of _resolve_logprobs is the placeholder-parsing layer, which the redesign deletes anyway. So the sequencing in the description is right: land #55029 on the current shape first (it's rebased onto current main and mergeable, pending review/CI), then the redesign PR swaps its input side.
@yinli-systems happy to review the derender conversion part of your PR and to adapt the streaming path on top of it.

**On `sampled` never materializing `content[i]`:** strong +1 from the measurement side — sampled-only is what spec-decode verification and RL rollout collection actually read, and it's the mode that keeps the fast path at zero per-token object cost. Filling both when `logprobs > 0` seems fine as long as the schema documents that `content=None` is the *normal* sampled-only
state, not an error.
