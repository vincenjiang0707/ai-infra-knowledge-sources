### 🐛 Describe the bug

**Summary**

When `max_model_len` is auto-fitted down because the KV cache cannot hold the full context, the V2 GPU model runner keeps using the *original* length in its `ModelState`, while attention metadata builders created afterwards size their buffers from the *reduced* `model_config.max_model_len`. For DeepSeek-V4 sparse MLA this makes `_build_c128a_metadata` fail its assertion during CUDA-graph capture, and the engine dies at startup.

It is not deterministic: it only triggers when free memory at startup is slightly too small for the full context. The same configuration started fine on a second attempt (KV cache 12.3 GiB → no reduction).

**Log**


**Root cause**

1. `ModelState.__init__` (`vllm/v1/worker/gpu/model_states/interface.py`) caches `self.max_model_len = self.model_config.max_model_len` when the model is loaded (`load_model` → `init_model_state`). No method updates it later.
2. After KV sizing, `Worker.update_max_model_len` (`vllm/v1/worker/gpu_worker.py`) writes the reduced value into `model_config.max_model_len` and calls `model_runner.update_max_model_len`.
3. `GPUModelRunner.update_max_model_len` (`vllm/v1/worker/gpu/model_runner.py`) only updates `self.max_model_len` and `self.req_states.max_model_len` — **`self.model_state` keeps the original length**.
4. The attention metadata builders are created afterwards. `DeepseekV4SparseMLAMetadataBuilder.__init__` sizes the C128A buffers from the **reduced** `model_config.max_model_len`: `c128a_max_compressed = align_up(cdiv(980224, 128), 128) = 7680`.
5. During CUDA-graph capture, `prepare_attn` in `model_states/default.py` uses `max_seq_len = self.max_model_len` (`for_capture` branch) → the **stale** 1048576 → `max_seq_len // 128 = 8192`.
6. `_build_c128a_metadata` clamps `active_topk_width` to `c128a_max_compressed` (7680) and then asserts it is `>= 8192` → `AssertionError`.

**Upstream check**

On `vllm-project/vllm` `main` (2026-09-15): `ModelState.__init__` sets `self.max_model_len` from `model_config` and never updates it; `prepare_attn` uses it for capture; `GPUModelRunner.update_max_model_len` does not touch `model_state`; `sparse_mla.py` computes `c128a_max_compressed` from `model_config.max_model_len` and has the same assertion. We have not reproduced it on a `main` build ourselves.

**Reproduction**

Any DeepSeek-V4 sparse-MLA configuration with `max_model_len` on auto (or `-1`) where the available KV cache is smaller than the full model context, e.g. lower `--gpu-memory-utilization` until the startup log shows `max_model_len: reduced from …`.

**Workaround**

Set an explicit `--max-model-len` that fits the KV cache (we use 900000). Then no auto-fit happens and both values agree.

**Suggested fix**

Propagate the update to the model state, e.g. in `GPUModelRunner.update_max_model_len`: `self.model_state.max_model_len = max_model_len` (plus any other cached copies) — or let `ModelState` read `self.model_config.max_model_len` instead of caching it.

**Related**

#46794 describes the same pattern in the V1 `GPUModelRunner` (`InputBatch` built with the original `max_model_len` before the auto-fit, stale block table → `RuntimeError` during decode). This one is the V2 runner's `ModelState`; a general fix could make every component that snapshots `max_model_len` pick up the auto-fitted value.
