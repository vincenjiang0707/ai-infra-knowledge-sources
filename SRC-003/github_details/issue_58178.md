## 正文

## Summary

Two independent host-memory problems make `--offload-backend uva` on quantized MoE checkpoints fail at scales where the arithmetic says they should fit. Both were hit bringing up `XiaomiMiMo/MiMo-V2.6-Pro-RL` (1.02T, MXFP4 experts, 527 GiB on disk) on a single DGX Station GB300 (250 GiB HBM visible, 494 GiB Grace host RAM, coherent C2C). Both have working local patches; I'm opening this as a design question rather than a PR because the right fix touches `offloader/uva.py` and the quantization `process_weights_after_loading` contract, and maintainers should pick the shape.

Image: `vllm/vllm-openai:nightly-d05da62e` (0.29.1rc1.dev422). Both code paths are unchanged on `main` as of today (`uva.py` L115 `cpu_data.pin_memory()`; `mxfp4.py` L358–361 `replace_parameter`).

## Problem 1: `pin_memory()` rounds every offloaded tensor up to a power of two

`UVAOffloader.wrap_modules` pins each offloaded parameter with `torch.Tensor.pin_memory()`, which goes through the CachingHostAllocator and rounds each allocation to the next power of two. For MiMo-Pro's per-layer expert tensors: `w13_weight` is 4.5 GiB → 8 GiB pinned, `w2_weight` 2.25 GiB → 4 GiB. Requesting `--cpu-offload-gb 305` consumed ~504 GiB of host memory and the kernel OOM-killed the EngineCore during load (host 494 GiB). Measured with a small probe that pins tensors of the real shapes and reads `Mlocked`/`Shmem` from `/proc/meminfo` before and after.

That's a ~33–45% host-RAM tax on exactly the workload UVA offload exists for, and it's invisible: the log reports "Total CPU offloaded parameters: 305 GiB" while the host holds far more.

**Local fix that works:** register the existing contiguous CPU tensor in place with `cudaHostRegister(ptr, nbytes, cudaHostRegisterPortable)` via ctypes (exact size), and keep a reference so it's never unregistered. With that, 321.75 GiB offloaded pins 321.75 GiB; the full model loads with 126 GiB host free. Read bandwidth through the resulting CUDA view was 336 GB/s vs 355 GB/s for the `pin_memory()` path on this box — a wash.

**Design question:** is an in-place `cudaHostRegister` path acceptable in `uva.py` (env-gated, or automatic above some size threshold), or would you rather expose a way to allocate exact-size pinned memory (e.g. `cudaHostAlloc` + `torch.from_blob`) so the caching allocator isn't involved at all? I can send either as a PR.

## Problem 2: `Mxfp4MoEMethod.process_weights_after_loading` un-offloads every layer via `replace_parameter`

On the Marlin/TRT-LLM MXFP4 path, `process_weights_after_loading` shuffles/re-packs the expert weights and installs the result with `replace_parameter(layer, "w13_weight", w13)` (and w2, and both scale tensors). `replace_parameter` registers the new tensor as a fresh `nn.Parameter`. The new tensor lives wherever the shuffle produced it (HBM), so the UVA view the offloader installed is dropped and the layer silently comes back onto the GPU: +7.17 GiB HBM per MoE layer on MiMo-Pro. With 46 of 69 MoE layers offloaded the box runs out of HBM after a handful of layers — the failure is a CUDA OOM inside `process_weights_after_loading`, nowhere near the offloader, so it's hard to attribute.

**Local fix that works:** when the existing parameter carries the offloader's `_vllm_is_uva_offloaded` marker and the new tensor has the same byte size, byte-copy the new contents into the existing pinned storage through a `uint8` view and re-view it to the new dtype/shape, preserving the UVA view; fall back to `replace_parameter` (with a warning) if the size changed. Verified: 5/5 greedy prompts token-exact between offloaded and non-offloaded runs of the same weights (8- and 16-layer truncations), and the full model serves correctly.

**Design question:** should `replace_parameter` itself become offload-aware (check the marker, copy in place), so every quant method benefits, or should quant methods that re-pack weights call a new helper? The former is one function; the latter is a per-backend audit (`mxfp4.py` is the one I hit; `fp8.py`, `nvfp4`, `compressed_tensors` likely have the same shape).

## Repro

```
vllm serve XiaomiMiMo/MiMo-V2.6-Pro-RL --trust-remote-code --tensor-parallel-size 1 \
  --moe-backend marlin \
  --offload-backend uva --cpu-offload-gb 320 \
  --cpu-offload-params routed_experts.w13_weight routed_experts.w2_weight \
  --max-model-len 262144 --max-num-seqs 8 --gpu-memory-utilization 0.96
```
Problem 1 shows as a host OOM-kill during load on a 494 GiB host; problem 2 shows as `torch.OutOfMemoryError` in `Mxfp4MoEMethod.process_weights_after_loading` once problem 1 is worked around. With both local patches this serves at 30 tok/s C1 / 56 tok/s aggregate at C8.

Write-up with per-boot receipts: https://al-engr.com/gb300-mimo-v26-pro-testing.html. Happy to send PRs once there's a preferred shape, and to test on this hardware.

### jmeadlock · 2026-09-22

**Correction from the reporter.** Re-reading `main` more carefully: problem 2 as I wrote it is wrong. `device_loading_context` already re-offloads a UVA parameter that `process_weights_after_loading` swapped out (`model_loader/utils.py`, the `uva_offloaded_parameters` branch), and that code was in the nightly I tested. What actually failed was that the re-offload path re-pins with `pin_memory()`, so it hits problem 1 again — a second power-of-two-rounded host copy per tensor.

Also: with `VLLM_WEIGHT_OFFLOADING_DISABLE_PIN_MEMORY=1` the `get_accelerator_view_from_cpu_tensor` path takes the `cudaHostAlloc(nbytes)` branch, which is *exact-size pinned memory* — so that env var is the workaround for problem 1 today, and a fully stock nightly loads the 320 GiB offload with 126 GiB host to spare. The variable's name suggests a downgrade; on this path it is the opposite.

So the actionable item is narrower than I filed: make the default `pin_memory=True` path in `UVAOffloader` allocate exact-size pinned memory (e.g. via the same `cudaHostAlloc` route) instead of `torch.Tensor.pin_memory()`, and avoid the second host copy on re-offload. I'll open a PR for the first part with before/after host-footprint numbers on the same boot. Apologies for the noise in the original.
