## 正文

## Purpose

The AMD QSA indexer only ever ran the unfused reference chain: Gemma RMSNorm and MRoPE on the query, group compression, RMSNorm and MRoPE on the compressed key, then three cache writes. Because `apply_qsa_rmsnorm` goes through vLLM's portable RMSNorm, each of those steps decomposes into eager aten elementwise kernels, so one QSA layer issues 37 launches per decode step where the fused kernel issues one.

The fused kernel that does the whole job already exists in this repository, as `nvidia/ops/qsa_pre_indexer.py`. It is pure Triton -- it imports `torch` and `vllm.triton_utils` -- its eligibility gate is config-shaped rather than device-shaped. Nothing about it was NVIDIA-specific; the only thing keeping it away from ROCm was the directory it lived in.

This moves the kernel to `common/ops/qsa_pre_indexer.py`, lifts the predicate alongside it as the exported `supports_fused_pre_indexer`, and gives the AMD indexer the same `use_fused_pre_indexer` branch the NVIDIA one already has. No AITER dependency, no build-system change, no new custom op registration.

The unfused chain stays in place as the `else` branch on both vendors. It is the numerics reference the unit test compares against, and it is the arm an A/B switches to.

> NB! The kernel's `num_warps` and `TILE_T_Q`/`TILE_H_Q` were tuned for 32-lane warps and are left alone here; a ROCm wavefront is 64 lanes, so retuning them is worth doing.

## Test Plan

- **Hardware:** MI355X (gfx950), ROCm 10.0, TP2
- **Model:** `amd/Qwen3.8-Flash-Next-MXFP4` for serving; unit tests are standalone
- **Image:** `vllm/vllm-openai-rocm:nightly-rocm100-d9105ea8001e0a6d77a96327d17515bb5791fb36`
- **Unit tests:** `tests/models/qwen4_exp/test_qsa_pre_indexer.py`,
  `tests/models/qwen4_exp/test_qsa_amd.py`
- **Serving sweep:** paired A/B (control and candidate) at TP2, 60k/600 and 8k/1024 at concurrency 4 and 16
- **Decode re-trace:** paired `torch` profiler capture on the same two arms, to check the launch collapse directly rather than inferring it from throughput
- **Accuracy:** GSM8K 5-shot on the checkpoint card's recipe, TP1 and TP2, n=2 per arm — neutral

## Test Result

### Unit tests

**MI355X**

On gfx950, all 8 bf16 configurations pass — the fused kernel matches the unfused reference for the query, the raw state cache bit-for-bit, and the compressed cache:

| Case | `mrope` | 2D positions | position cache | state size | Result |
| --- | --- | --- | --- | --- | --- |
| `mrope` | yes | yes | yes | 4 | pass |
| `text` | no | no | no | 4 | pass |
| `mrope-model-1d` | yes | no | yes | 8 | pass |
| `mrope-no-position-cache` | yes | yes | no | 4 | pass |
| `mrope-model-1d-no-position-cache` | yes | no | no | 8 | pass |
| `text-with-position-cache` | no | no | yes | 4 | pass |
| `fresh` (single 37-token request) | yes | yes | yes | 4 | pass |
| `tiled` (4097 tokens, crosses the tile heuristic) | yes | yes | yes | 4 | pass |

> The 8 `float8_e4m3fn` parametrisations skip on ROCm: the AMD indexer's compressed cache is constructed `bf16`-only, so no AMD path produces them. Removing that limitation is a separate change.

`test_qsa_amd.py` gains three tests, 16 passed total on gfx950:
- `test_qsa_fused_pre_indexer_replaces_the_unfused_chain` — the fused branch runs, the unfused chain does not, and the kernel receives `raw_key_cache.kv_cache` rather than the narrower `key_cache` view. That distinction is the one silent-corruption risk in this  diff: the kernel addresses the raw cache at full width and writes the MRoPE position tail itself, so passing `key_cache` would truncate every position write.
- `test_qsa_unsupported_config_keeps_the_unfused_chain` — an ineligible config still takes the reference path and never calls the kernel.
- `test_fused_pre_indexer_gate_is_config_shaped` — five cases over the predicate.
