## 正文

## Purpose

Before this change, `RDNAHybridW4A16LinearKernel` routed a decode GEMM to the HIP `wvSplitK_int4_g` kernel only when the activation row count was at most five (`M <= 5`) and the total activation size satisfied `K * M <= 32768`.

The existing C++ operator supports up to five activation rows (`N_in <= 5`) and accepts `K_in * N_in` up to `int(max_lds_len * 1.2)`. With `max_lds_len = 32768`, the effective upper limit is `39321` elements.

Python `M` maps to C++ `N_in`. For inputs above the regular LDS capacity, the medium kernel keeps the activation prefix in LDS and reads the remaining elements from global memory.

Consequently, supported shapes with `K * M` between `32768` and `39321` (exclusive of the lower bound and inclusive of the upper bound) fell back to Triton instead of using the existing HIP kernel.

This PR aligns the Python dispatch limit with the C++ operator contract. It also adds dispatch-boundary tests and numerical correctness coverage for the newly enabled range. No C++ kernel is changed.

## Duplicate-work check

Open PR searches for medium-skinny, wvSplitK W4A16, and RDNA hybrid W4A16 found no duplicate. Related PRs #46186, #51511, and #50618 do not modify this hybrid dispatch threshold.

## Test Plan

Test environment:

All tests were run locally on the following system:

| Component | Value |
| --- | --- |
| GPU | AMD Radeon 8060S |
| GPU architecture | gfx1151 |
| Memory | 128 GB unified memory (96 GiB VRAM, 32 GiB host-visible) |
| Operating system | Ubuntu 24.04.4 LTS |
| ROCm | 7.2.3 |

The end-to-end comparison covered the two medium-skinny `down_proj` shapes below:

| Model | Batch | `down_proj` shape | `K * M` | Before this PR | With this PR |
| --- | ---: | --- | ---: | --- | --- |
| `Qwen3-8B-GPTQ-Int4` | 3 | `M=3, K=12288, N=4096` | 36864 | Triton | HIP medium |
| `Qwen3-4B-GPTQ-Int4` | 4 | `M=4, K=9728, N=2560` | 38912 | Triton | HIP medium |

The end-to-end benchmark used identical settings before and after this change:

- `VLLM_ROCM_USE_AITER=0` with the `ROCM_ATTN` backend;
- eager execution (`enforce_eager=True`), with HIP Graph and `torch.compile` disabled;
- prefix caching disabled;
- fixed prompts and random seed;
- 512 output tokens per request with `temperature=0` and `ignore_eos=True`;
- one warmup followed by three measured runs.

Functional validation included dispatch tests at the regular and medium boundaries, FP16 and BF16 medium-kernel comparisons against an FP32 reference, and the complete hybrid W4A16 test file. All applicable pre-commit hooks and `git diff --check` were also run on the changed files.
