# [PR #58262] [ROCm][MoE] Support MiMo-V2.6 MXFP4 on gfx942

state: open | updated: 2026-09-23T04:20:55Z

## 正文

## Purpose

MiMo-V2.6 ships MXFP4-quantized MoE weights, and on gfx942 we should be able to use AITER's Triton MXFP4 MoE kernel (`--moe-backend aiter_triton_mxfp4_bf16`). But now using it will failed to load weight: 

```
ValueError: Mxfp4 MoE backend 'AITER_TRITON_MXFP4_BF16' does not support the deployment configuration since kernel does not support routing method 2
```

MiMo's router gets classified into `RoutingMethodType.DeepSeekV3`  (the routing method 2 in the error message) the only real difference is that MiMo routes over a single group (`n_group=1`). Aiter implements exactly this on its flat top-k (`score_mode="sigmoid"` + bias), so the deployment only needed the backend to ask for it.

So the goal here is to let MiMo-V2.6's MXFP4 weights use the AITER MXFP4 kernel that already exists.

## Changes

Two things in `AiterW4A16ExpertsMonolithic`:

* the routing gate accepts `RoutingMethodType.DeepSeekV3` (Mimo V2.6 is classified as much);
* the wrapper requests `score_mode="sigmoid"` for that router family, which is aiter's native path for an ungrouped sigmoid + correction-bias router: select on `sigmoid(logits) + bias`, return the unbiased sigmoid scores, renormalize.

## Test Plan

All serving is using Mi300x (gfx942).

Serving command:

```
VLLM_ROCM_USE_AITER=1 vllm serve XiaomiMiMo/MiMo-V2.6-Flash-RL \
  --trust-remote-code --max-model-len auto --generation-config vllm \
  --gpu-memory-utilization 0.9 --tensor-parallel-size 2 \
  --moe-backend aiter_triton_mxfp4_bf16 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}' \
  --tool-call-parser mimo --enable-auto-tool-choice --reasoning-parser mimo
```

Accuracy checks (gsm8k):
```
lm_eval --model local-chat-completions  \
  --model_args model=XiaomiMiMo/MiMo-V2.6-Flash-RL,base_url=http://127.0.0.1:8000/v1/chat/completions,num_concurrent=32,max_retries=10,max_length=32000,timeout=60000 \
  --gen_kwargs '{"max_tokens":16000,"until":[]}' --batch_size auto \
  --tasks gsm8k --num_fewshot 25 --apply_chat_template
```

Benchmark:
```
vllm bench serve --model XiaomiMiMo/MiMo-V2.6-Pro-RL --host localhost --port 8000 \
   --dataset-name random --random-input-len 1024 \
  --random-output-len 1024 --num-prompts 100 --max-concurrency 32 --trust-remote-code
```

New tests:
`tests/models/quantization/test_mimo_v2_w4a16_routing.py`:

* MiMo's router config is indeed classified as `RoutingMethodType.DeepSeekV3` (guards the premise, in case the classifier changes);
* the routing predicate accepts that family for the W4A16 scheme it handles (kMxfp4Static weights, unquantized activations);
* the same through the full config path (`is_supported_config`, device gate included), gated on `is_aiter_found_and_supported()`;
* the flat `sigmoid` + bias routing reproduces the model's own router (expert ids and weights) for **both** 256 and 384 experts, with a seeded control that the correction bias steers selection; gated on the AITER install (ROCm +
  `is_aiter_found_and_supported()`). The `sigmoid` score mode itself needs aiter >= 0.1.20 (ROCm/aiter#4688).

## Test Result

gsm8k when using `--moe-backend aiter_triton_mxfp4_bf16`:
| model | gsm8k |
|---|---|
| MiMo-V2.6-Flash-RL | 0.9598 ± 0.0054 |
| MiMo-V2.6-Pro-RL | 0.9674 ± 0.0049 |

Benchmark:
| model | MoE path | output tok/s | mean TPOT | successful requests |
|---|---|---|---|---|
| MiMo-V2.6-Flash-RL (TP2) | `aiter_triton_mxfp4_bf16` | **758.5** | **38.2 ms** | 100/100 |
| MiMo-V2.6-Flash-RL (TP2) | emulation | 117.5 | 242.3 ms | 100/100 |
| MiMo-V2.6-Pro-RL (TP4) | `aiter_triton_mxfp4_bf16` | **491.7** | **56.1 ms** | 100/100 |
| MiMo-V2.6-Pro-RL (TP4) | emulation | 70.6 | 381.9 ms | 32/32 |

Roughly **6.5x** the output throughput and **6.3x** lower TPOT against emulation for Flash, **7.0x** / **6.8x** for Pro. Emulation row for Pro used fewer prompts because it's slow, ~7x slower.
