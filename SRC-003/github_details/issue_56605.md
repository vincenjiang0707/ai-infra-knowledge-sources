### 🐛 Describe the bug

Long multi-turn agentic sessions on GLM-5.3-Flash (FP8) intermittently collapse into repeated tokens / shell-fragment word salad ((tmp)(tmp)…). Same config: clean on 0.1.dev20051+g487ecf187(08-26), degenerates on 0.28.1rc1.dev580+g385dce36b (09-08);

**Version delta:**

| Component | GOOD `sha256:2c6da6c6…` (clean) | BAD `sha256:819ec9c0…` (degenerates) |
|---|---|---|
| vLLM | `0.1.dev20051+g487ecf187` | `0.28.1rc1.dev580+g385dce36b` |
| flashinfer-python | 0.6.17 | **0.6.18** |
| transformers | 5.15.1 | **5.16.1** |
| torch | 2.13.0+cu130 | 2.13.0+cu130 |
| CUDA runtime | 13.0.88 | 13.0.88 |

So the regression lives in one (or more) of: the vLLM commit range `g487ecf187…g385dce36b`, **FlashInfer 0.6.17→0.6.18** (attention kernels — directly on the hybrid path), or **transformers 5.15.1→5.16.1** (tokenizer/chat-template/generation). torch and CUDA are unchanged.

## Symptom
- Coherent, then degenerates into repeated/incoherent tokens after many tool-call turns / large context.
- Silent: HTTP 200, normal `finished_reason`, no errors, no preemptions.
- Single-turn and short requests always clean.

## Minimal reproduction attempt (could NOT reproduce synthetically)
Against the bad build, all of the following returned **coherent** output (~30+ requests total, `clear_thinking` on and off):
- Single-turn coding / classification prompts — clean.
- 8-way concurrent short requests — clean.
- 10-turn tool-call history (`bash` tool, half the assistant turns tool_use-only/no text, shell-style tool_results incl. `/tmp`), then a final summary turn — clean.
- ~34k-token context, `max_tokens` up to 3000, `reasoning_effort=max`, run twice (2nd pass = guaranteed prefix-cache hits) — clean.

→ **Only reproduces in real agentic clients (Claude Code / OpenCode-style) over long sessions.** Not triggered by any isolated request I could construct. Evidence is the build A/B + rollback, not a standalone repro.

`--enable-mamba-cache-stochastic-rounding --mamba-ssm-cache-dtype float16`; `--default-chat-template-kwargs '{"reasoning_effort":"high","clear_thinking":true}'`; MTP disabled.

### devtyagi3909 · 2026-09-15

@gaby good catch on `glm47` dropping `tool_choice="required"`. 

the reason `ParserEngine.adjust_request` is a no-op is bc `glm47` uses native special tokens (`<|tool_call|>`), not pure json. if the engine didn't bypass it, `abstract_tool_parser` would inject an outlines json schema constraint. that would force the model into raw json and instantly break the glm token structure.

since `ParserEngine` drops the constraint to protect the tags, the model is left completely unguided, so `"required"` just silently degrades to `"auto"`. to actually enforce `"required"` on `glm47`, standard json guided decoding won't work — we'd need a custom logitprocessor or xgrammar to force the `<|tool_call|>` token prob to 1.0 at generation start.

still tracing the `glm45`/`glm47` parser collision in `serving_chat.py` for the context poisoning loop.
