# [Issue #53963] GLM-5.3-Flash (glm5_next): no SM120 sparse-MLA path for rope-free MLA (qk_rope_head_dim=0) — three failure modes on RTX PRO 6000

source: https://github.com/vllm-project/vllm/issues/53963
state: open | updated: 2026-09-22T09:41:05Z
labels: quantization, glm

## 正文

### Summary

GLM-5.3-Flash (`glm5_next`) cannot start on **SM120** (RTX PRO 6000 Blackwell, compute 12.0) with the dedicated `glm53-flash` image: the architecture's **rope-free sparse MLA** (`qk_rope_head_dim: 0`) has no working attention/KV path on this capability. Three distinct failure modes below, ending at an explicit kernel shape guard. Weight loading itself is clean (including a quantized checkpoint — Marlin NvFp4 auto-selected), so this is purely the sparse-MLA attention/KV-cache lane.

### Environment

- Image: `vllm/vllm-openai:glm53-flash-x86_64-cu130@sha256:2e771fa615452282cc331eb418b3ef21636fce355bea0491fca89e6d362ab703` (engine banner: `0.1.dev20051+g487ecf187`; per-model image published for #53906)
- GPUs: 4× NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition (96 GB, **SM120 / compute 12.0**), driver 595.71.05, host CUDA 13.2, TP=4
- Model: `zai-org/GLM-5.3-Flash` — text config `kv_lora_rank=512`, `qk_nope_head_dim=256`, **`qk_rope_head_dim=0`**, `index_topk=2048` (34 linear-attention + 11 DSA layers)
- Checkpoint under test: local weight-only NVFP4 (compressed-tensors, routed experts only; attention/vision/MTP in BF16). The failures below are independent of weight quantization — they occur in backend selection / KV-cache paths before or regardless of quantized GEMMs.
- Args: `--tensor-parallel-size 4 --max-model-len 131072 --max-num-seqs 256 --reasoning-parser glm45 --tool-call-parser glm47 --enable-prefix-caching --gpu-memory-utilization 0.90` (no speculative config)

### Failure mode 1 — default (`kv_cache_dtype=auto`, also explicit `fp8_e4m3`)

Engine init reaches CUDA-graph memory profiling, then the MLA cache write asserts:

```
RuntimeError: Worker failed with error 'concat_and_cache_mla,
/workspace/csrc/libtorch_stable/cache_kernels.cu:866, pe_dim must be 64 for fp8_ds_mla'
```

`FLASHINFER_MLA_SPARSE_SM120` requires the packed `fp8_ds_mla` layout (explicit `fp8_e4m3` is normalized into it), whose cache-write kernel hardcodes the DeepSeek entry shape (512 NoPE + 64 RoPE). Rope-free MLA (pe_dim 0) violates it.

### Failure mode 2 — `--kv-cache-dtype bfloat16`

```
ValueError: No valid attention backend found for cuda with AttentionSelectorConfig(
  head_size=512, dtype=torch.bfloat16, kv_cache_dtype=bfloat16, use_mla=True, use_sparse=True, ...)
Reasons: {TRITON_MLA: [sparse not supported],
          FLASHINFER_MLA_SPARSE_SM120: [kv_cache_dtype not supported, kv_cache_dtype not supported]}
```

Note the bf16-capable no-rope lane (`FLASHINFER_MLA_SPARSE`, which explicitly whitelists `qk_nope_head_dim=256 / kv_lora_rank=512` per its `supports_combination`) is never considered: `platforms/cuda.py::_get_backend_priorities` hardcodes the `major == 12` MLA candidates to `[TRITON_MLA, FLASHINFER_MLA_SPARSE_SM120]`.

### Failure mode 3 — experimentally widening the SM100 no-rope lane to SM120

To test whether the gap is routing-only, we injected a runtime patch (sitecustomize) that (a) appends `FLASHINFER_MLA_SPARSE` to the SM120 candidate list and (b) widens `FlashInferMLASparseTRTLLMBackend.supports_compute_capability` to `{10, 12}`. The lane is then selected, all 120 shards load cleanly, and init stops at a precise shape guard:

```
ValueError: SM120 sparse MLA v32/GLM expects kv_lora_rank=512, qk_rope_head_dim=64,
and query head dim 576; got kv_lora_rank=512, qk_rope_head_dim=0, query dim=512
```

i.e. the SM120 sparse-MLA kernel path exists only for the DeepSeek-shaped (rope-64 / query-576) case; the rope-free GLM shape (query 512) has no SM120 kernel.

### Ask

Either extend the no-rope (`qk_nope=256 / kv_lora=512`) sparse-MLA support that ships for SM100 to SM120 (kernel + `supported_kv_cache_dtypes` + the hardcoded candidate list in `platforms/cuda.py`), or document `glm5_next` as unsupported on SM120 in the model's serving notes so consumer/workstation Blackwell users don't chase configuration fixes for a kernel gap.

Happy to test candidate images/patches quickly — we have a 4× RTX PRO 6000 (SM120) TP4 environment with the model staged and can boot-verify within minutes. Full boot logs for all three modes available on request.

### shing100 · 2026-08-27

A rope-free SM120 sparse-MLA kernel does already exist — just not in upstream.

Mode 3 above concludes that the SM120 kernels only cover the DeepSeek shape
(rope-64 / query-576). That holds for upstream, but `jasl/vllm` (the SM12x
DeepSeek-V4 branch behind #41834) carries a second family that is structurally
rope-free, and it runs at GLM's numbers on my hardware.

In `vllm/v1/attention/backends/mla/sparse_mla_kernels.py` there are two paths.
The DeepSeek one splits the 512 explicitly:

```python
def accumulate_fp8ds_global_slots_sparse_mla_attention_chunk_multihead(...):
    assert q.shape[-1] == 512
    token_fp8_dim = 448      # NoPE
    token_bf16_dim = 64      # RoPE
```

The other one does not split at all — no 448/64, no rope, no positional term
anywhere in the kernel body:

```python
def accumulate_indexed_d512_split_sparse_mla_attention(...):
    assert q.shape[-1] == 512

@triton.jit
def _indexed_d512_split_score_kernel(..., HEAD_DIM: tl.constexpr):
    dim_offsets = tl.arange(0, HEAD_DIM)   # walks D as one contiguous axis
    ...
    scores = tl.dot(q, kv) * scale
```

It is a plain indexed inner product over a 512-wide D. GLM-5.3-Flash's
`text_config` gives `kv_lora_rank=512`, `qk_rope_head_dim=0`, i.e. query dim
512 with nothing to rotate — exactly what this kernel expects.

Driven at GLM's shapes on an RTX PRO 6000 Blackwell (SM120), checked against a
plain torch softmax reference:

```
one-shot T=4   H=64  D=512 topk=1024  PASS  rel=0.001171
one-shot T=16  H=64  D=512 topk=1152  PASS  rel=0.001179
chunked  T=4   H=32  D=512 topk=2048  PASS  rel=0.001111   <- GLM's index_topk
chunked  T=8   H=64  D=512 topk=2048  PASS  rel=0.001125
chunked  T=2   H=32  D=512 topk=4096  PASS  rel=0.001034

device: NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition | capability: (12, 0)
```

GLM's `index_topk` is 2048 and the one-shot entry point asserts
`indices.shape[1] <= 1152`, but the branch also ships
`accumulate_indexed_d512_chunked_sparse_mla_attention`, which takes scratch
`chunk_max_score/chunk_denom/chunk_acc` buffers and merges chunks with the
online-softmax rescale. That covers 2048 and 4096 (I did not probe higher).

Worth flagging one trap: the one-shot kernel `tl.store`s `max_score`/`denom`
rather than accumulating, so calling it repeatedly to fake chunking silently
produces wrong results — my first attempt scored rel=0.90 that way. The chunked
entry point is the one to use.

Repro script (run inside a build of the branch at tag
`sm120-pr-41834-stable-preview-20260813b`):

<summary>repro_d512_glm.py</summary>

```python
import torch
from vllm.v1.attention.backends.mla.sparse_mla_kernels import (
    accumulate_indexed_d512_split_sparse_mla_attention,
    accumulate_indexed_d512_chunked_sparse_mla_attention,
)

torch.manual_seed(0)
DEV, D = "cuda", 512

def ref(q, kv_flat, indices):
    out = torch.zeros(*q.shape, device=DEV, dtype=torch.float32)
    for t in range(q.shape[0]):
        kv = kv_flat[indices[t].long()].float()
        out[t] = torch.softmax((q[t].float() @ kv.T) / (D ** 0.5), dim=-1) @ kv
    return out

def run(T, H, C, chunked):
    q = torch.randn(T, H, D, device=DEV, dtype=torch.bfloat16) / 8
    kv_flat = torch.randn(8192, D, device=DEV, dtype=torch.bfloat16) / 8
    indices = torch.randint(0, 8192, (T, C), device=DEV, dtype=torch.int32)
    lens = torch.full((T,), C, device=DEV, dtype=torch.int32)
    mk = lambda: (torch.full((T, H), -float("inf"), device=DEV, dtype=torch.float32),
                  torch.zeros(T, H, device=DEV, dtype=torch.float32),
                  torch.zeros(T, H, D, device=DEV, dtype=torch.float32))
    max_score, denom, acc = mk()
    kw = dict(q=q, kv_flat=kv_flat, indices=indices, lens=lens,
              scale=1.0 / (D ** 0.5), max_score=max_score, denom=denom, acc=acc)
    if chunked:
        c_max, c_den, c_acc = mk()
        accumulate_indexed_d512_chunked_sparse_mla_attention(
            scores=torch.zeros(T, H, 1024, device=DEV, dtype=torch.float32),
            chunk_max_score=c_max, chunk_denom=c_den, chunk_acc=c_acc, **kw)
    else:
        accumulate_indexed_d512_split_sparse_mla_attention(
            scores=torch.zeros(T, H, C, device=DEV, dtype=torch.float32), **kw)
    torch.cuda.synchronize()
    got = acc / denom.unsqueeze(-1).clamp(min=1e-9)
    exp = ref(q, kv_flat, indices)
    rel = ((got - exp).abs().sum() / exp.abs().sum()).item()
    print(f"  {'chunked' if chunked else 'one-shot':<8} T={T:<3} H={H:<3} "
          f"topk={C:<5} {'PASS' if rel < 0.02 else 'MISMATCH'}  rel={rel:.6f}")

for T, H, C in [(4, 64, 1024), (16, 64, 1152)]:
    run(T, H, C, chunked=False)
for T, H, C in [(4, 32, 2048), (8, 64, 2048), (2, 32, 4096)]:
    run(T, H, C, chunked=True)
```

Wiring result from the SM120 box in the original report: the d512 route from @shing100 works end to end as a **runtime overlay** on the pinned image, and the integration surface is smaller than this thread assumed. Kernel-level numbers first, then the parts that are still open.

**Parity, re-measured inside `vllm/vllm-openai:glm53-flash-x86_64-cu130@sha256:2e771fa6…` (`vllm 0.1.dev20051+g487ecf187`, `torch 2.13.0+cu130`, `triton 3.7.1`), RTX PRO 6000 (SM120), against an independent fp32 eager reference, chunk width 1024:**

```
T=4  H=32  candidates=2048  rel=0.001092
T=8  H=64  candidates=2048  rel=0.001103
T=2  H=32  candidates=4096  rel=0.000798   (two chunks)
```

which reproduces @shing100's figures independently. Controls that turned out to matter: the one-shot entry does raise `assert indices.shape[1] <= 1152` at `C=2048` (so only the chunked path is usable for `index_topk=2048`), and `-1` candidates are genuinely never read.

**The wiring is one backend, not a kernel port.** GLM reaches attention through the generic MLA wrapper (`MultiHeadLatentAttentionWrapper`), so an `AttentionBackend` + `SparseMLACommonMetadataBuilder` + `SparseMLACommonImpl` subclass is the whole extension point: no model file, no C++, no image rebuild. We registered it with the override hook that already exists (`register_backend(AttentionBackendEnum.CUSTOM, "…")` from a `sitecustomize` on `PYTHONPATH`) and selected it per KV-group — `--attention-config '{"backend_per_kind": {"mla_attention": "CUSTOM"}, "sparse_mla_force_mqa": true}'` — which keeps the vision tower on its own lane. Upstream, the equivalent is a normal enum member plus a `major == 12` candidate entry; naming is yours.

API facts measured in this image, since they differ from `main`:

- `sparse_utils` has **no** `flat_kv_row_view`, and `triton_convert_req_index_to_global_index` has **no** `BLOCK_STRIDE_ROWS` parameter. The flat row view is a plain `cache.view(-1, head_size)`, which is what `FlashAttnMLASparseImpl.forward_mqa` already does here.
- `forward_mqa` receives `q = (q_nope [T,H,512], q_rope [T,H,0])` for this checkpoint — the zero-width rope half arrives intact, and `MLAAttentionImpl.supports_dense_mha_prefill = False` plus `sparse_mla_force_mqa` lets one kernel own every token (prefill included), which removed the second unproven lane (FA3/TRTLLM MLA prefill at `qk_head_dim=256 / v_head_dim=256` on SM120) from the picture.
- `--block-size 128` is mandatory, not a preference: `Glm5NextIndexerCache` asserts `block_size % (index_kpool * 32) == 0` and this checkpoint has `index_kpool=4`.

**One contract worth fixing in the kernels rather than documenting.** The `_indexed_d512_*` kernels mask candidates by `index < lens` only. A `-1` *inside* `[0, lens)` is therefore not skipped: it is scored as 0 (the value load is masked, the score is not), and its `exp(0 - max)` silently inflates the softmax denominator. We hit this by accident — our first harness sprinkled `-1` inside the valid window and every case scored `rel ≈ 0.095`, which reads exactly like a broken kernel. It is an input-shape problem, not a math problem: `triton_convert_req_index_to_global_index(..., return_valid_counts=True)` compacts valid entries to `[0, count)` and leaves `-1` in the tail, so the real pipeline cannot produce that state, and passing `return_valid_counts=True` is load-bearing. But the failure is silent and 100x over tolerance, so a `valid_kv` term in `_indexed_d512_split_stats_kernel`'s mask (and the value kernel's weight computation) would make the kernel robust to a caller mistake instead of quietly wrong. Worth deciding deliberately before this gets wired in anger.

**What we have *not* proven, to keep this from being oversold:** the model has not been booted yet. Still open on our side: the bf16 **rope-free KV write** path (failure mode 1 is the fp8 `fp8_ds_mla` layout; nothing yet confirms `concat_and_cache_mla` accepts a zero-width rope half in the bf16 branch — that is the next boot, with `--load-format dummy` to answer it cheaply), end-to-end retrieval through the top-k lane at `temperature=0`, eager-vs-CUDA-graph output equality, and decode throughput versus the SM100 TRTLLM lane (these are Triton kernels, and bf16 KV costs 2x the fp8 lane's bytes — @shing100's scoping caveat holds).

Two asks that fall out of the above, on top of the original: (1) the rope-free shape guard is worth having on any lane that can be selected for `qk_rope_head_dim == 0` — `supports_combination` rejecting the shape with a message costs about six lines and @stefanskiasan's silent-fault class disappears for it; (2) if the d512 family is headed upstream, the candidate-list entry in `platforms/cuda.py` for `major == 12` needs to accept a non-fp8 KV dtype, or bf16 KV will keep landing on `No valid attention backend found` even with the kernels present.

Still standing on the offer: 4x RTX PRO 6000 (SM120), TP4, model staged, boot-verify per attempt, both a compressed-tensors NVFP4 and FP8/BF16 checkpoints available for comparison.


### tmttodd · 2026-08-28

**Fourth failure mode (SM120, RTX PRO 6000, `vllm/vllm-openai:glm53-flash-x86_64-cu130`, `vllm 0.1.dev20051+g487ecf187`, TP4, NVFP4 weights, bf16 KV, `--block-size 128`):** the model's *kpool indexer* decode-logits path is itself block-size-incompatible with SM120, independent of which sparse-MLA backend is selected.

While booting a custom rope-free d512 sparse-MLA backend (vendor-free port of the `codex/ds4-sm120-min-enable` Triton family, selected via `--attention-config '{"backend_per_kind":{"mla_attention":"CUSTOM"},"sparse_mla_force_mqa":true}'`), the engine passes backend selection, completes hybrid page-size alignment (`Setting attention block size to 1152 tokens`, driven by the mamba page ~1.125 MiB vs attention-page >= mamba-page in `vllm/platforms/interface.py::_maybe_align`, `mamba_cache_mode='align'`) and KV sizing, then dies on the **first decode warmup step**:

```
File ".../vllm/model_executor/layers/sparse_attn_indexer_kpool.py", line 788, in sparse_attn_indexer_kpool
    logits = fp8_fp4_paged_mqa_logits(
File ".../vllm/utils/deep_gemm.py", line 639, in fp8_fp4_paged_mqa_logits
    ...
AssertionError
```

`fp8_fp4_paged_mqa_logits` (DeepGEMM paged-MQA) on SM120 requires `block_kv == 64` in the non-fp4 path (32/64 with `use_fp4_cache=True`). But the kpool cache shares the hybrid slot layout with the MLA latent and mamba state, so its storage block is the *manager* block divided by `index_kpool=4`. The mamba alignment above forces the manager block to 1152 (= 9 × 128, the smallest multiple of 128 with page bytes >= the mamba page at TP4), giving a kpool storage block of **1152 / 4 = 288** — unreachable for any `--block-size`, any kv dtype, any MLA backend. The indexer is model-level code upstream of backend selection, and the decode-logits call is unconditional on CUDA (the only env gates in `sparse_attn_indexer_kpool.py` are `VLLM_KPOOL_SKIP_TAIL_CACHE` / `VLLM_KPOOL_SKIP_DECODE_WRITE`), so there is no way to avoid it: the model can prefill (the chunked Triton logits kernel has no such constraint) but cannot take a single decode step on SM120.

Side note from the same boot: the model's `_indexer_align` votes `block_size = MultipleOf(128)` into `select_common_block_size`; with the 1152 manager block, that vote intersects the MLA backend's list with `DEEPSEEK_V32_INDEXER`'s `[64]` over the divisors of 1152 and finds no candidate (64 ∤ 128), wedging boot earlier with "The page size is too large to be split". Relieving the vote to `MultipleOf(1)` (the 128-token alignment is a manager-block constraint `Glm5NextIndexerCache.get_kv_cache_spec` enforces independently) restores the image's own else-branch minimum and gets past that stage to the DeepGEMM assert above.

So on SM120 the full set is now four: (1) fp8 KV write `pe_dim must be 64 for fp8_ds_mla`; (2) bf16 KV → no valid sparse backend; (3) SM100 bf16 no-rope lane → shape guard; (4) **kpool indexer decode logits: DeepGEMM block_kv == 64 vs hybrid-forced 288**. The first three are attention-lane; this one is indexer-lane and blocks the model regardless of attention backend.

### Mode 4 — kpool indexer decode logits (`block_kv == 64` vs hybrid-forced 288)

This is an *alignment-granularity* problem, not a hard architectural limit. Our boot log:

```
INFO [interface.py:926] Setting attention block size to 1792 tokens to ensure that
                        attention page size is >= mamba page size.
```

`1792 / index_kpool(4) = 448`, and 448 tiles by 64, so `fp8_fp4_paged_mqa_logits` never
asserts. Three landing points for the same constraint:

| alignment | manager block | kpool storage block | 64 ∣ block? |
|---|---:|---:|---|
| `--block-size 128` (this thread) | 1152 | 288 | no |
| stock `index_kpool × min(PAGED_MQA_PAGE_SIZES)` = 128 | 1664 | 416 | no |
| overlay: `index_kpool × 64` = 256 | **1792** | **448** | **yes** |

The overlay also pins the SM120 backend's page-size list to `[64]`, because
`select_kernel_block_size` walks sizes descending and would otherwise pick 256 for a 1792
manager block, while every GLM_NSA/DSV3_2 kernel is instantiated at `PAGE_BLOCK_SIZE=64`
only. At 1664 that was masked, since 256 does not divide 1664.

### Mode 1 — `pe_dim must be 64 for fp8_ds_mla`

Resolved by keeping `FLASHINFER_MLA_SPARSE_SM120` and zero-padding the 512-wide NoPE latent
into the 576-wide GLM_NSA geometry the GLM-5.2 line already uses, rather than looking for a
bf16-KV lane. A zero RoPE block contributes nothing to the QK dot, softmax is unchanged, and
the value comes from the 512 NoPE region, so the result is exact; the cost is 656 B/token
instead of ~528 over the 11 DSA layers. `MLAAttentionSpec.real_page_size_bytes` already

Field update (SM120 / RTX PRO 6000, 4x TP4): we worked around the fourth blocker — the `fp8_fp4_paged_mqa_logits` `block_kv == 64` assert on the GLM-5.3-Flash kpool indexer — without touching DeepGEMM, and the model now boots and decodes.

**What was done** (in-tree monkeypatch overlay, no fork):

1. Vendored the Triton `fp8_paged_mqa_logits` kernel family from `jasl/vllm@codex/ds4-sm120-min-enable` (the DSv4 SM120 enabler). The kernels take `block_size` as a constexpr read from the cache shape, so a 288-pool storage block (mamba-forced manager block 1152 / index_kpool 4) needs no kernel change.
2. Cache layout: the kpool writer (`_kpool_softmax_rotate_write_cache_kernel`) stores FP8 values **densely** (row stride = head_dim = 128) with the fp32 dequant scale in a **per-page trailer** at `page_start + block_size*head_dim` — structurally the same packed layout the DSv4 view assumes. Worth noting: the wrapper docstring's "last 4 bytes per (block, pos)" is the misleading document here; the writer's byte arithmetic is authoritative.
3. Patch seam: the kpool module imports `fp8_fp4_paged_mqa_logits` at module top level, so a runtime override must rebind the **consumer module's** attribute — patching `vllm.utils.deep_gemm.fp8_fp4_paged_mqa_logits` alone misses the call site.
4. CUDA-graph safe: no host syncs, one bucketed output allocation per call; FULL capture (35 batch sizes) completes cleanly with the patch active.

**Evidence**

- Kernel vs fp32 gather-reference on real SM120 (through the image's own `kv_cache_as_quant_view`): max rel 6e-8, exact top-k pool sets, exact -inf masks, across block boundaries, spec-decode `next_n=2`, zero-context rows, and a non-contiguous block-table (stride(-1) != 1) guard case.
- End to end with real NVFP4 weights at 131K ctx: a retrieval needle beyond `index_topk=2048` is exact and identical across two temperature=0 calls; eager C1 10.8 / C4 34.4 tok/s, TTFT 0.147 s; CUDA-graph mode still retrieves the needle.

Two things that might interest upstream:

- A first-class family-120 branch in `vllm/utils/deep_gemm.py` (like the DSv4 one) would make the SM120 kpool path permanent instead of an overlay; the kernels + view are Apache-2.0 and line-diff verified.
- `--enforce-eager` on this build also sets `-cc.mode=none` (disables torch.compile), so "eager vs graphs" byte-equality probes are not a valid determinism check — the two modes differ in compile mode, not just graphing. Per-mode determinism is the meaningful invariant.

### tmttodd · 2026-08-28

Follow-up (SM120 / 4x RTX PRO 6000, TP4, same overlay as my previous comment): the fallback is now end-to-end production-load-verified, and the remaining open questions from this thread — "is Triton kpool decode too slow on SM120 to be useful?" and "does spec-decode compose with the fallback?" — have measured answers.

**CUDA graphs + torch.compile on SM120 with the Triton fallback (the config that matters):**
- decode C1: 64.9 tok/s, C4 aggregate: 174.4 tok/s, TTFT 0.055s (131K ctx, bf16 KV, batch-1/4 greedy microbench)
- eager mode is a 5-6x trap (11.6 / 35.4 tok/s) — if SM120 numbers are being compared anywhere, they must be graphs+compile numbers
- GPU KV cache 3,003,999 tokens at bf16; ~22.9 concurrent 128K sequences. The fp8_ds_mla rope-free KV format (failure mode 1 above) remains the unresolved wall here and is now purely a capacity lever (1.5-2x), not a boot blocker.

**MTP spec-decode composes with the fallback, exactly:** the checkpoint ships `num_nextn_predict_layers: 1` with `index_share_for_mtp_iteration: true`, so the verifier drives the kpool indexer at `next_n=2` — the same `[B, next_n]` metadata path. With `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'`: mean acceptance length 1.66-1.94 (draft accepted 66-94% of steps), C1 120.1 tok/s (+85% over graphs), and **token-exact**: a temperature=0 wide-margin probe is byte-identical across eager / graphs / MTP modes, and needle retrieval beyond `index_topk` stayed exact in 3/3 samples under verify/reject. No SM120-specific blocker in the spec path.

**Kernel detail that made the fallback competitive:** the paged-MQA-logits Triton kernel can compute `q·k` as `tl.dot(..., input_precision="fp32")` over the fp8e4nv operands directly instead of dequanting to fp32 first. This is exact at these shapes (e4m3's 3-bit mantissa is exactly representable; fp32 accumulate): parity vs an fp32 reference max_rel 5.96e-08 with identical top-k sets, 1.31x wall-clock at decode scale (8 rows x 32768 pools).

**One behavior worth documenting somewhere regardless of this issue:** on this MoE+TP4 stack, temperature=0 greedy is **not bit-reproducible across runs for open-ended prompts** — six runs of an invented-names prompt gave five distinct fluent outputs (soft argmax ties decided by TP reduction noise; custom allreduce is off on this build). Wide-margin prompts are bit-identical across modes. Anyone writing determinism/equality CI checks for MoE TP deployments needs to probe wide-margin outputs; byte-equality on creative prompts will flake by design.

Keeping this open for the fp8 rope-free KV format (failure mode 1) — that's the last wall with no working lane.
