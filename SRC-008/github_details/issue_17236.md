### bjptw · 2026-09-23

@QwertyJack  I looked into this while going through the
DeepSeek-V4.1-Flash guide. I think the gap may be larger than a missing flag —
the multi-node path might not be reachable at all. Details below, please
correct me if I'm misreading the code.

**1. The guide's multi-node section has no Engram configuration.**
`docs/source/tutorials/models/DeepSeek-V4.1-Flash.md` section 5.1
(`Multi-Node Colocated Deployment`, 2×A3 / 4×A2) contains no `--engram-config`.

**2. Section 5.3 (single A3) uses it:**
```bash
--engram-config '{"cpu_offload": true, "dp_shared_memory": true}'
```
3. The Ascend Engram config is created automatically and its parallel check
rejects multi-node.
vllm_ascend/patch/platform/patch_engram_config.py:
line 118-120 — AscendEngramConfig() is instantiated whenever the model has
engram_layer_ids, without the user passing --engram-config:
```python

elif getattr(model_config.hf_text_config, "engram_layer_ids", None):
    self.engram_config = AscendEngramConfig()
```
line 65-79 — verify_parallel_config() rejects any topology where
parallel_config.nnodes != 1:
```pyhon
or parallel_config.nnodes != 1
...
raise ValueError("Ascend Engram requires single-node TP=1/2/4/8 with at most 16 ranks, ...")
```
Upstream vllm/config/vllm.py calls verify_parallel_config unconditionally
after resolving the config (line ~1326), so this check appears to run even when
the user does not pass --engram-config.
If that reading is correct, a 2×A3 or 4×A2 launch of DeepSeek-V4.1-Flash would
hit the single-node error regardless of the guide, i.e. section 5.1 may describe
a topology the current code does not accept.
4. The suggested --additional-config keys don't exist in this repo.
vllm_ascend/ascend_config.py has no enable_engram / engram_storage
entries, so the workaround in the report may come from a different build.
Questions:
Is multi-node DeepSeek-V4.1-Flash with INT8 Engram intended to be supported on
Ascend? If yes, should the nnodes != 1 restriction be relaxed, or does
multi-node take a different code path?
Is the reported
```text
ValueError: layers.1.engram.embed.weight: expected BF16 source for bf16
```
a separate loading issue (INT8 table not loaded as INT8), independent
of the offload topology?
I'm happy to send a doc PR once the intended behaviour is clear — I'd rather not
touch section 5.1 without knowing which side (code or doc) needs the change.
