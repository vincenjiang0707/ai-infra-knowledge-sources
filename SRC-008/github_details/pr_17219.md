# [PR #17219] [Performance][GDN] Avoid AiCPU fallback for boolean token sorting

## 正文

### What this PR does / why we need it?

Fixes #16865.

The GDN metadata builder stably partitions speculative and non-speculative tokens by sorting a boolean mask. The existing helper casts that mask to `int32`, which makes integer `argsort` fall back to AiCPU on the tested Ascend stack.

Cast **only boolean masks** to `float32` instead. Both values (0 and 1) are exactly representable, `stable=True` preserves token order within each group, and the returned indices remain `int64`. Non-boolean inputs are unchanged, including large integers that would lose precision if cast to float32.

This is a local dispatch optimization, not a global argsort replacement or a change to model activation precision. No new CANN operator, host transfer, configuration, hardware-specific branch, or scheduler behavior is introduced.

The nearby metadata-sharing optimization in #16246 is complementary: it reduces repeated metadata work, whereas this change addresses the sort's execution backend.

### Does this PR introduce _any_ user-facing change?

No API/configuration changes. The affected boolean GDN partition uses AiCore sorting instead of the integer-sort AiCPU fallback on the tested stack. Other integer sorting calls are outside this PR's scope.

### How was this patch tested?

**Environment:** A2 910B3, TP2 for real-model validation, CANN 9.1.0, torch 2.10.0, torch_npu 2.10.0.post4. Final validation uses Ascend base `dd24be2fe924a77754ae472f77b439fe3eac3091` and its verified vLLM commit `84030bbe3d74d99bad477a3d2e37a973ccd8865c`.

**Regression tests:**

```bash
pytest -q tests/ut/ops/test_gdn_attn_builder.py
# 67 passed
pytest -q tests/e2e/pull_request/one_card/test_gdn_stable_argsort.py
# 40 passed on one NPU
bash format.sh ci
# All hooks passed; the commit also passed a separate gitleaks scan.
```

- The 12 new boolean dispatch UT cases fail against the old implementation and pass with this change. They verify dispatch dtype as well as stable ordering, since output-only tests would not catch an AiCPU performance regression.
- NPU tests cover empty/singleton, constant, alternating and random masks, including non-contiguous inputs.
- An additional standalone comparison verified exact old/new index equality in 90 cases, up to 65536 elements.

**Real weights and controlled trajectory:**

- Qwen3.8-27B-w8a8, TP2, MTP=3: 25 baseline FULL_DECODE_ONLY requests and 75 patched requests (50 FULL_DECODE_ONLY + 25 eager) completed. The original ArgSort fallback warning was observed in the baseline and absent from uninstrumented patched service logs.
- Free-generation runs were not bitwise reproducible even when repeating the old implementation. Therefore those runs are service smoke/stability evidence, not an exact numerical comparison.
- For a separate controlled test, used synchronous eager scheduling, disabled prefix caching, fixed each request's output to a repeated token via a singleton allow-list, and recorded/replayed MTP draft proposals at the runner boundary. The real target and MTP forwards still execute. This is diagnostic instrumentation, **not** upstream Trace Replay (which currently rejects speculative decoding).
- Four different prompt lengths, 64 output tokens each; old/new implementations each run twice after warmup. On both TP ranks, all comparisons matched exactly: scheduler records, target forward input/position hashes, GDN partition masks/indices, returned tokens, and raw logprob dictionaries (top-5 plus selected token). Each run had 59 scheduler steps, 58 target forwards and 27 affected partition calls per rank. Every affected call also shadow-compared old/new indices directly.
- Diagnostic synchronization/shadow-sort overhead is excluded from performance measurements. No diagnostic hooks are included in this PR.

**Performance:**

For 8192 elements, a standalone 10-call kernel profile changed from `aclnnSort_SortAiCpu_Sort` to `aclnnSort_SortAiCore_Sort`; median sort-kernel duration was **579.382 µs → 11.740 µs**. A separate cast+sort microbenchmark measured **591.89 µs → 58.18 µs** (median across five synchronized 100-call rounds). These are operator-level results, **not** claims of equivalent model throughput gains. No significant end-to-end speedup is claimed from the small service workload.

**Known baseline test failures / limits:**

The broader five-file GDN UT run reports 76 passed / 2 failed with this patch, versus 63 passed / the same 2 failed on unmodified `dd24be2fe`:

- `test_connector_observes_updated_gdn_state_for_each_compiled_call`
- `test_mixed_non_spec_reuses_rearranged_qkv`

Both CPU-mock tests enter the available fused-GDN path and pass CPU tensors to NPU Triton l2norm (`Pointer argument ... cannot be accessed from Triton`). They do not originate from this change; no unrelated fixes are bundled here. Full repository tests, A3/A5 validation and long-duration soak testing are not claimed.
