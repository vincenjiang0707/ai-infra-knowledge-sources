# Describe the bug

## Summary

Enabling `enable_engram_ple_offload=true` on the tested PR revision has two observable effects:

1. It provides the intended memory benefit: approximately 12.87 GiB less model-weight memory per rank and approximately 1.97x KV-cache capacity.
2. It substantially regresses decode performance in controlled tests, and repeated full-concurrency sweeps terminate the engine with NPU error 507011 / invalid GM address at concurrency 24-32.

The same image, model, topology, DSpark depth, graph mode, driver/CANN stack, workload, and cold-cache policy are stable with only `enable_engram_ple_offload` changed to `false`.

## Controlled variable

The only intended A/B difference is:

```json
// PLE off
"enable_engram_ple_offload": false

// PLE on
"enable_engram_ple_offload": true
```

Both groups use:

- the same image digest shown above;
- DSpark with 6 speculative tokens;
- DP4 / local DP2 / TP8 / EP32;
- `FULL_DECODE_ONLY`;
- `enable_engram=true`, `engram_storage=int8`;
- `enable_mc2_hierarchy_comm=true` and `VLLM_ASCEND_ENABLE_FUSED_MC2=0`;
- `max_model_len=1048576`, `max_num_batched_tokens=4096`, `max_num_seqs=32`;
- the same W8A8 checkpoint and benchmark client;
- prefix-cache reset before each measured point.

## Repeated failure

- Sweep 1: C1-C16 completed; the engine hit error 507011 near the end of C24. Later points immediately failed because the engine was dead.
- Sweep 2 from a clean restart: C1-C24 completed; C32 returned only 32 successful HTTP requests out of 160, with 128 `Internal Server Error` responses and zero generated output tokens. The engine then became unavailable.
- Host kernel messages at the same timestamp reported `Reserve addr is invalid, should call halMemMap` for device IDs 15, 8, and 9.
- Docker inspection did not report an OOM kill.

## PLE-off stability control

With the same image and all parameters unchanged except `enable_engram_ple_offload=false`:

- 2K/2K completed C24, C32, C136, and C144 with zero failed requests;
- 16K/4K completed C24, C32, C48, C56, and C64 with zero failed requests;
- the same service remained healthy while the full sweep continued.

This does not by itself prove the exact failing operator, but it strongly associates the failure with the tested PLE-offload path rather than general KV capacity, request concurrency, DSpark, or the two-node topology.

## Expected behavior

- Engram host offload should not expose an unmapped or prematurely reused host/device address under sustained concurrent decode.
- The engine should either complete the requests or return a bounded request error without killing the EngineCore.
- The memory/capacity benefit should remain, while the synchronous host-lookup/routing overhead should either be overlapped or documented with a supported-performance envelope.

## Questions

1. The current PR head replaced the tested pinned staging-buffer path with registered host/UVA reads. Is that change expected to fix this 507011 invalid-GM failure, or should an additional lifetime/event fence be added?
2. Are there known supported limits for batch size/concurrency with two-node DP4/TP8/EP32 Engram offload?
3. Could PR #16544 add a two-node A3 offload stress test at C32 or higher, plus an offload-on/off decode benchmark, before claiming the path validated?

Related but not duplicate:

- #16375 tracks the general DeepSeek-V4.1 roadmap and explicitly asks for offload/TP and performance validation.
- #16419 concerns dual-node MoE communication failures in a different path.
- #11188 shares the low-level `halMemMap` symptom on 310P but involves a different model, operator, and hardware.
