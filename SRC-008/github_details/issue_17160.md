## 正文

## Proposal to improve performance

Please investigate the 310P-specific `NPUModelRunner310V2` FP16 path for Qwen3.5. The controlled traces below suggest two different optimization targets:

- decode-heavy workload: most of the MRv2 regression is additional device idle/free time, suggesting host dispatch, synchronization, or scheduling overhead;
- long-prefill workload: most of the regression is additional kernel execution time, despite essentially unchanged kernel counts.

This is related to the MRv2 performance-baseline work tracked in #15577.

## Report of performance regression

On one Ascend 310P3 logical NPU, Qwen3.5-9B FP16 is consistently slower with `NPUModelRunner310V2` than with `NPUModelRunner310` in eager mode.

### Controlled variables

Both arms used the same:

- container image: `quay.io/ascend/vllm-ascend@sha256:589fc7c911e3c7b83e10c0fed2637d9c6eefd8e1bbfb27a73b3699dc7e68c782`
- vLLM: `0.29.0`
- vLLM Ascend commit: `c173a64a`
- CANN inside the image: `9.1.0`
- model/checkpoint: Qwen3.5-9B FP16
- hardware: Atlas 300I Duo / Ascend 310P3, one logical NPU
- `TP=1`, eager mode, 32K max model length, `max_num_seqs=4`
- prefix caching disabled
- `mamba_ssm_cache_dtype=float16`
- identical prompts, seed, warmups, repetitions, and request ordering

The only intentional difference was:

```bash
# MRv1
unset VLLM_USE_V2_MODEL_RUNNER

# MRv2
export VLLM_USE_V2_MODEL_RUNNER=1
```

The service logs explicitly confirmed:

```text
Using NPUWorker310 and NPUModelRunner310.
Using NPUWorker310 and NPUModelRunner310V2.
```

| Workload | TTFT | TPOT | E2E | Output throughput |

A separate earlier two-case controlled run on the same image also showed the same direction, with MRv1 TPOT 8.58%–11.36% lower than MRv2. The table above is the newer dedicated profile run and is used as the primary result.

### Trace results

Three profiler sessions were collected for each runner and workload. The values below are medians across the three sessions.

| Profile workload | Runner | Device stage (ms) | Kernel compute (ms) | Device free/idle (ms) | Kernel count |
| --- | --- | ---: | ---: | ---: | ---: |
| input 128, output 8, concurrency 1 | MRv1 | 1,454.37 | 947.06 | 507.64 | 24,343 |
| input 128, output 8, concurrency 1 | MRv2 | 1,523.14 | 954.55 | 568.59 | 24,352 |
| input 4096, output 2, concurrency 1 | MRv1 | 6,376.91 | 5,791.67 | 585.24 | 43,437 |
| input 4096, output 2, concurrency 1 | MRv2 | 6,595.73 | 5,963.50 | 627.86 | 43,434 |

For the short/decode-heavy trace, MRv2 adds 68.77 ms to the device stage. About 60.94 ms (approximately 89%) is additional device free/idle time, while kernel compute increases by only 7.49 ms. Kernel count changes by only 9.

For the long-prefill trace, MRv2 adds 218.82 ms to the device stage. About 171.83 ms (approximately 79%) is additional kernel compute time, plus 42.62 ms additional free/idle time. Kernel count is effectively unchanged.

The `output=2` profile is used only for device-stage attribution; its TPOT is not treated as a meaningful performance metric.

### Expected behavior

MRv2 should reach performance parity with MRv1 for this supported 310P Qwen3.5 FP16 eager configuration, or the remaining expected overhead should be documented.

### Thymos2027 · 2026-09-22

## ABBA follow-up: the stable MRv2 regression was not reproduced

I ran a new order-balanced, non-profiled comparison to remove the main limitation of the original evidence (MRv1 always ran before MRv2).

Controlled order:

```text
MRv1-A -> MRv2-A -> MRv2-B -> MRv1-B
```

All four arms used the same image digest, CANN 9.1.0, vLLM Ascend commit `c173a64a`, Qwen3.5-9B FP16 checkpoint, one 310P3 logical NPU, TP=1, eager mode, disabled prefix cache, identical prompts and seed. Each workload used 3 warmups and 5 measured requests. The profiler was disabled.

### TPOT p50 results

| Workload | MRv1-A | MRv2-A | MRv2-B | MRv1-B | Pair A MRv2 delta | Pair B MRv2 delta | Mean-arm MRv2 delta |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| input 128, output 128, concurrency 1 | 97.949 ms | 98.790 ms | 98.193 ms | 98.632 ms | +0.86% | -0.44% | +0.20% |
| input 4096, output 128, concurrency 1 | 98.962 ms | 99.734 ms | 99.088 ms | 99.566 ms | +0.78% | -0.48% | +0.15% |

The pairwise effect reverses sign in both workloads. E2E and output-throughput effects reverse as well. The mean-arm differences are only 0.15%-0.20%, below the observed arm-to-arm drift. For 4K TTFT, MRv2 is slightly faster in both pairs; the combined effect is -0.10%.

### Correction to the original interpretation

The original sequential trace data remains valid as a description of those runs: it did contain additional device idle time and a slower high-share `MatMulV2` shape in the later MRv2 arm. However, runner selection and run order were fully confounded. The ABBA result does not support attributing those differences to a stable MRv2 regression.

I therefore withdraw the strong causal claim in the issue description. At this point the result should be treated as **not reproduced under order-balanced testing**, rather than as a confirmed MRv2 performance bug. I can provide the four raw run manifests, normalized arm/effect CSVs, and the ABBA runner/analyzer scripts if useful. I am leaving the issue open for now so maintainers can decide whether to close it or request a multi-block randomized follow-up.
