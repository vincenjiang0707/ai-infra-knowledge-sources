## 正文

### What this PR does / why we need it?
Add an Ascend adapter for the upstream `ECMooncakeConnector` so V1 workers can transfer multimodal encoder outputs between encoder and prefill/decode instances.
The adapter reuses the upstream scheduler, reservation state machine, and worker lifecycle, with NPU-specific memory and synchronization handling.

Related to the EPD roadmap in issue #6026 which tracks Mooncake-based cross-node encoder-cache sharing among other work. This PR adapts the `ECMooncakeConnector` TransferEngine data plane for Ascend.

- Register the Ascend implementation under the existing `ECMooncakeConnector`
  name through the Ascend plugin entry point.
- Reuse `MooncakeTransfer` with the process-local Ascend TransferEngine. Allocate
  registered staging and receive buffers with 2 MiB alignment, and reject direct
  registration of arbitrary source tensor views when staging is unavailable.
- Use NPU events to track source readiness and delay receive-buffer reuse until
  device work completes.
- Start EC worker services after model loading and shut them down with the worker.
- Return EC completion information from V1 encoder-only execution and steps that
  skip model forward. Previously, these return paths could omit the information
  the scheduler needs to advance asynchronous transfers.

The change also allocates the MoE load counter directly on NPU, removing the intermediate CPU allocation and device copy. V2 runner support is outside this PR.

The V1 runner changes belong in Ascend's existing `execute_model()` override:
that method owns the encoder-only and no-forward return paths where EC output must be collected. Patching the upstream runner would not update these overridden paths; replacing the Ascend method through a runtime patch would add indirection to code already maintained here. Both no-forward exits share one helper, which preserves KV output and invokes the existing EC lifecycle when metadata is present. The connector continues to own transfer scheduling and memory management. Worker shutdown follows the upstream KV-then-EC order.

### Does this PR introduce _any_ user-facing change?
Yes. On Ascend, `ec_connector="ECMooncakeConnector"` selects the NPU adapter. The adapter defaults to the `ascend` transport protocol and maps the default CUDA buffer setting to NPU. Explicit non-Ascend transport protocols are rejected.

Transfers use the configured `ec_buffer_size`. If the producer cannot stage a batch in its registered pool, it reports a transfer failure instead of falling back to registering the original tensor addresses.

#### Real-NPU TP2 validation

The TP2 consumer regression passed on three Ascend 910B1 NPUs, using a real Mooncake sender and two HCCL consumer ranks. Each rank handled six reservation callbacks on non-main control threads with the correct receive-pool device bound, including `npu:1` on rank 1. Tensor equality, cancellation, buffer reuse, pool reclamation, and cleanup checks passed.

An EPD correctness test compared a TP2 monolithic baseline with one encoder plus a TP2 consumer on the same PD devices: Qwen3.5-9B, MRV1, BF16, eager, CANN 9.1.0, and torch/torch_npu 2.10.0. Eight serial requests contained one or three 224×224 images (16 images total), with greedy decoding and 32 output tokens each. All requests completed without EC transfer errors.

- **Transfer correctness:** all 16 source embeddings matched both TP ranks'
  received tensors bit-for-bit in two diagnostic replays, including one with
  reads deferred until after sending and consumer prefill. Staging tensors also
  matched in the full-capture replay; no transfer corruption was observed.
- **Baseline comparison:** the monolithic baseline batches two images together
  on one vision rank, while EPD encodes images individually. With the baseline
  changed only to encode images individually, all 16 image embeddings, merged
  inputs on both ranks, all 80 captured logits tensors (five steps per request
  per rank), and **8/8 complete output token sequences matched bit-for-bit**.

The original batched-baseline comparison matched 6/8 outputs; both diagnostic replays matched 7/8. The reproducible mismatch was traced to batch-dependent visual numerical differences affecting greedy token selection, independently of Mooncake. 

#### End-to-end benchmarks

Qwen3.5-35B-A3B (W8A8_DYNAMIC, BF16 activations), 4 × Ascend 910B (64 GiB), CANN 9.1.0, torch/torch_npu 2.10.0, vLLM `a97dacb7106e`. Each setup uses four NPUs: DP4EP4 or 1 Encoder + 3 PD for both EPD connectors.
Client concurrency is 128; output is fixed at 64 tokens. Eager execution, no MTP, prefix caching, or profiling. DP4 and Encoder use OMP8; PD uses OMP1.
