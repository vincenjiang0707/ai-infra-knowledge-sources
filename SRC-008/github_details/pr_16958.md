# [PR #16958] [BugFix][Model] Apply DeepSeek-V4 attention sinks through the weight loader

## 正文

### What this PR does / why we need it?

Split out of #16355 (first of three PRs).

A live/layerwise weight update runs inside vLLM's layerwise reload: the layer is parked on the meta device, and only writes made through `param.weight_loader` are buffered and replayed by `finalize_layerwise_reload`. DeepSeek-V4's sink branches wrote the attention sink with a direct `param.data.copy_` / `copy_`, which bypasses that buffer and lands on the meta tensor, so the write was silently dropped.

Consequence: after any live weight update the attention sinks kept their dummy initialisation (the ±1e-3 `initialize_dummy_weights` values, visible as absmean 5.3e-4 instead of the transferred 1.0e-2). A parameter-level diff between a server that loads the transferred payload at startup and one that received the same payload live showed exactly that: `model.layers.{0..3}.self_attn.attn_sink` stayed at the dummy values while every other parameter matched. The DeepSeek-V4 lane of the weight-update E2E oracle added in #16355 cannot pass without this fix.

Changes:

- Route the sink through the parameter's loader, keeping the existing `enable_dsa_cp()` (full sink) and per-rank narrow semantics. A plain parameter falls back to `default_weight_loader`, which is the same copy as before, so normal startup loading is unchanged. All three copies of the branch are fixed: the target model (`model.py`), the MTP head (`mtp.py`) and the DSpark draft (`dspark.py`), which previously used a slicing `copy_` and had the same problem.
- Add `tests/ut/models/test_deepseek_v4_weight_loader_reload.py`: it drives the real `load_weights` over a model whose parameter set is exactly one sink and pins both behaviours — with a `weight_loader` the per-rank narrowed tensor must reach the loader and not `param.data`, and a plain parameter must keep the previous default-loader semantics. It covers the target model and the MTP copy.

The sink is a plain parameter, so the loader it resolves to is vLLM's `default_weight_loader`, which only asserts the shapes and copies. Tensor parallel sharding stays owned by `load_weights`: the checkpoint ships one sink per head and each rank receives `num_attention_heads // tp_size` consecutive heads starting at `tp_rank * heads_per_rank`. That arithmetic is untouched by this PR, and the unit test now pins the offset at TP > 1 so a future change that re-partitions an already narrowed sink (for example swapping in `row_parallel_weight_loader`, which narrows 1-D parameters as well) fails instead of silently sharding twice.

### Does this PR introduce _any_ user-facing change?

No. Behaviour only changes for layerwise/live reloads, where the sink write previously did nothing.

## Rebased on latest `main`, DeepSeek-V4-Flash lane enabled, and the remaining blocker found and fixed

Rebased onto `main` @ `5591facb3`; the two original commits apply cleanly (the upstream `rope_parameters` change in `DeepseekV4Attention` does not overlap the sink hunks). Three commits added on top.

**Enabling the case needed one more server flag.** The DeepSeek-V4 indexer always quantises its key to int8 and scatters it into the indexer K cache, so the cache must be int8 as well. With the default `auto` (bf16) cache the ACL-graph capture of the very first forward dies in `npu_scatter_nd_update_sk` ("updates dtype DT_INT8 should be same with varRef dtype DT_BFLOAT16") — *before any transfer runs*. Every other DeepSeek-V4 e2e lane already passes `--attention-config.indexer_kv_dtype int8`; this case was missing it. Skip reasons are now per lane (`skip_reasons`, keyed by the weight-transfer backend) so the one-card suite can carry the case while the two-card HCCL lane keeps its skip.

**The sink fix alone was not sufficient** — the lane still failed `updated != reference` after it, and the remaining divergence was not in the transfer. Bisect on the same branch:

| variant | result |
|---|---|
| transfer into a dummy-started lane, **no sleep** | **reproduces the reference exactly** |
| full lane, **level-1** sleep | **passes** |
| full lane, **level-2** sleep | fails |
| Qwen3.5-35B-A3B, level-2 sleep | passes |

Instrumenting the worker and diffing every parameter, buffer and reachable tensor between the startup-load server and the live lane named the culprit exactly. They differed in only three families, all of them tensors a forward reads but that are held as **plain attributes**:

| tensor | startup load | after a level-2 wake |
|---|---|---|
| `model.hc_norm.weight` | `1.0` | `0.0` |
| `model.layers.{0..3}.self_attn.q_norm_without_weight.weight` | `1.0` | `0.0` |
| `dsa_attn._q_scale` / `_k_scale` / `_v_scale` / `_prob_scale` | `1.0` | `7.39e-4` (the dummy seed) |

`CaMemAllocator.sleep(level=2)` discards every allocation taken from the sleep-managed pool, but `NPUWorker.sleep` builds its backup from `model.named_buffers()` only. `RMSNorm(has_weight=False)` keeps its weight as a plain `torch.ones` tensor — not a parameter, not a buffer — so the backup never sees it and the wake leaves it zeroed, while the Ascend `forward_oot` still hands `self.weight` to `torch_npu.npu_rms_norm`. A weightless norm multiplied by zeros collapses its activations. The second family is the mirror image: `_init_kv_cache_quant` registers the scales *persistently*, so `--load-format dummy` seeds them with its deterministic dummy value and no live update puts them back.

The fix owns both families as **non-persistent buffers** — the ownership the level-2 runtime state already uses (#16725): they leave `state_dict()` and they join the `named_buffers()` backup, while `Module.to()` and in-place updates keep working.
