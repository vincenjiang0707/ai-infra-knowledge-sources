### Describe the bug

`vllm serve` with `--data-parallel-size 2 --tensor-parallel-size 8` hangs during engine initialization (memory profiling / dummy run) and dies with:

```text
RuntimeError: synchronize:../torch_npu/csrc/core/npu/NPUEvent.cpp:215 NPU function error: aclrtSynchronizeEvent(event_), error code is 507034
[Error]: Vector core execution timed out.
```

This happens **only when all three factors are present simultaneously**:

1. `VLLM_ASCEND_ENABLE_FLASHCOMM1=1` (env var, i.e. SP enabled)
2. `multistream_overlap_shared_expert: true` (in `--additional-config`)
3. `--data-parallel-size > 1`

Removing **any one** of the three makes the service start normally. Verified with a 12-experiment matrix (below), each run on a clean 16-card machine (HBM baseline confirmed before each run).

Independently excluded (failure persists with each of these removed/changed):
- `enable_sfa_prolog_v3`, `enable_dsa_cp`, `enable_sparse_li_c8` / `enable_sparse_sfa_c8` (none present in the minimal repro)
- MTP speculative decoding (present in the passing minimal repro; disabling it does not rescue the failing combo)
- cudagraph `FULL_DECODE_ONLY` (failing combo still dies with `--enforce-eager`)
- vLLM-Ascend version (main @ d4d2957e5, main @ f640d1348, and image built-in all fail; same code passes with DP=1)
- `LD_PRELOAD` jemalloc

### To Reproduce

Failing command (GLM-5.2-w4a8c8, single node 16x 910B):

```bash
export VLLM_ASCEND_ENABLE_FLASHCOMM1=1
vllm serve /path/to/GLM-5.2-w4a8c8 --host 0.0.0.0 --port 8177 \
  --safetensors-load-strategy prefetch --api-server-count 1 \
  --data-parallel-size 2 --enable-expert-parallel --tensor-parallel-size 8 \
  --seed 1024 --served-model-name glm-5 \
  --tool-call-parser glm47 --reasoning-parser glm45 --enable-auto-tool-choice \
  --max-num-seqs 12 --max-model-len 135000 --max-num-batched-tokens 8192 \
  --trust-remote-code --gpu-memory-utilization 0.92 --quantization ascend \
  --compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}' \
  --additional-config '{"multistream_overlap_shared_expert":true}' \
  --speculative-config '{"num_speculative_tokens":3,"method":"deepseek_mtp","enforce_eager":true}'
```

The exact same command starts normally if either `VLLM_ASCEND_ENABLE_FLASHCOMM1` is unset, or `multistream_overlap_shared_expert` is removed from `--additional-config`, or `--data-parallel-size 1` (TP16) is used.

### Expected behavior

The service should start normally with FlashComm1 (SP) + `multistream_overlap_shared_expert` on DP>1, as it does with DP=1 (TP16) under the identical configuration.

### Additional context

- Hypothesis: an interaction between the FlashComm1 (SP) communication path and the shared-expert side stream (`npu_stream_switch(shared_experts_calculation_stream())` in `vllm_ascend/ops/fused_moe/fused_moe.py`) deadlocks during the DP dummy run and surfaces as a vector core timeout.
- Impact note for users: `enable_dsa_cp` **requires** SP (`vllm_ascend/utils.py:1558` raises `ValueError` if FlashComm1 is off), so users who need DSA CP cannot drop FlashComm1 - their only workaround on DP>1 today is to disable `multistream_overlap_shared_expert`.
- Related interplay: `enable_fused_mc2=1` force-disables `multistream_overlap_shared_expert` (with a warning) in `ascend_config.py`, so the fused_mc2 path is presumably unaffected.
- Environment detail: reproduced consistently across two days (2026-09-12 / 09-13), >6 failing runs, all on a freshly verified idle machine; the passing runs prove the stack itself is healthy.

### tanjiangshan · 2026-09-13

A fix has been pushed to https://github.com/huamus/vllm-ascend/tree/fix/flashcomm1-multistream-dp-hang (commit 3667f94af on top of main @ d4d2957e5).

Following the `enable_fused_mc2` auto-disable precedent, `derive_and_validate` now disables `multistream_overlap_shared_expert` when FlashComm1 is effective and `data_parallel_size > 1`, logging a warning that points to this issue. Users who need FlashComm1 on DP>1 (e.g. for DSA-CP) keep working; only the shared-expert side-stream overlap is sacrificed.

Verified on the reproduction environment (GLM-5.2-w4a8c8, DP2xTP8, single node 16x 910B, vllm 0.28.0 + vllm-ascend main):

- UT: `tests/ut/test_ascend_config.py` 109 passed, including 3 new tests (mutex triggered on DP>1; kept on DP=1; kept without FlashComm1)
- E2E: the exact failing config from this issue now starts in ~4 min with the mutex warning logged and zero vector core timeouts; the identical config without the fix still dies at ~13 min with 72 timeouts

Happy to open a PR from that branch if the approach looks right.
