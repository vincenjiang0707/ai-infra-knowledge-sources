# [Issue #17059] [Bug]: CANN feature detection can use different ACL headers from extension build

source: https://github.com/vllm-project/vllm-ascend/issues/17059
state: closed | updated: 2026-09-21T10:06:37Z
labels: triaged, custom-op

## 正文

### Your current environment

- vLLM Ascend source: current `main` after #16256
- CANN: 9.2.0 (`V100R001C12SPC001B200`)
- Python: 3.11.10
- PyTorch: 2.10.0
- torch_npu: 2.10.0.post4
- SOC: `ascend950pr_9599`

### Describe the bug

The CMake feature probe for `aclrtGetPhyDevIdByUserDevId` uses only `${ASCEND_HOME_PATH}/include`, but the `vllm_ascend_C` extension currently searches `${TORCH_NPU_PATH}/include` before that directory.

Some torch_npu wheels contain an older snapshot of the ACL headers. If that snapshot exposes `acl/acl_rt.h`, CMake detects the API in the selected CANN toolkit and defines `CANN_DEVICE_ID_MAPPING`, while the actual extension build loads the older torch_npu copy and fails:

```text
csrc/torch_binding.cpp:94:16: error: 'aclrtGetPhyDevIdByUserDevId' was not declared in this scope; did you mean 'aclrtGetPhyDevIdByLogicDevId'?
```

Both header copies use the same include guard, so the newer CANN header cannot add the missing declaration after the stale copy has been included.

The outcome currently depends on wheel layout. A torch_npu wheel that keeps its ACL snapshot below `include/third_party/acl/inc` may build successfully because `-I${TORCH_NPU_PATH}/include` does not directly resolve `acl/acl_rt.h`. A wheel that exposes the snapshot from its include search path fails from a clean build.

The following official PyPI aarch64 CPython 3.11 wheels were inspected directly. None of their bundled ACL headers declares `aclrtGetPhyDevIdByUserDevId`; the affected versions are the ones that expose the stale header at `torch_npu/include/acl/acl_rt.h`.

| torch_npu package | Bundled `acl_rt.h` location | Result before this fix |
| --- | --- | --- |
| `2.10.0`, `2.10.0.post2`, `2.10.0.post4` | `include/third_party/acl/inc/acl/acl_rt.h` | No direct collision with `-I${TORCH_NPU_PATH}/include` |
| `2.10.0.post6` | `include/acl/acl_rt.h` | Affected |
| `2.9.0.post6`, `2.7.1.post8` | `include/third_party/acl/inc/acl/acl_rt.h` | No direct collision with `-I${TORCH_NPU_PATH}/include` |
| `2.9.0.post8`, `2.7.1.post10` | `include/acl/acl_rt.h` | Affected |
| `2.11.0`, `2.12.0` | `include/third_party/acl/inc/acl/acl_rt.h` | No direct collision with `-I${TORCH_NPU_PATH}/include` |

Custom or internally repackaged wheels can differ, so the installed header path is the definitive check. The official compatibility matrix maps `2.10.0.post6` to CANN 9.1.X; using it with CANN 9.2 is outside that published pairing, but the extension should still use the same selected CANN headers as its feature probes.

### Reproduction

1. Use a CANN toolkit whose `acl/acl_rt.h` declares `aclrtGetPhyDevIdByUserDevId`.
2. Put a stale ACL snapshot without that declaration under a directory passed as `${TORCH_NPU_PATH}/include`.
3. Configure the project. The feature probe succeeds.
4. Build `csrc/torch_binding.cpp`. Compilation fails with the error above.

### Expected behavior

The native extension should compile against the same selected CANN headers used by the feature checks. `${ASCEND_HOME_PATH}/include` should take precedence over the ACL snapshot bundled with torch_npu.

This was found while validating the device mapping code merged in #16256 and a subsequent clean build of #16249.
