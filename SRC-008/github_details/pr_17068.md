# [PR #17068] [Performance][MoE] Use bf16 router GEMM with fp32 accumulation for bf16-origin weights

## 正文

## What this PR does / why we need it

`AscendGateLinear` (PR #9617) forces fp32 weights and fp32 computation for the MoE router gate, because the previous `bf16×bf16→bf16` path (bf16 accumulation, no fp32 output) caused expert-selection errors in agent workloads on NPU.

However, the fp32 path (`aclnnMatmulV2`) is ~6x slower than necessary for bf16-origin weights — the common case for models like Kimi K3, whose gate weights are stored as bf16 in safetensors.

This PR adds a bf16 fast path: when the checkpoint weight is detected as bfloat16 at load time (via `weight_loader`, before `copy_` upcasts to fp32), the router GEMM runs as:

```python
torch.mm(x_bf16, w_bf16.t(), out_dtype=torch.float32)
```

which dispatches to `aclnnMm MatMulV3` — bf16 multiplication with **fp32 accumulation**. For bf16-origin operands this is numerically equivalent to the fp32 path (each `bf16×bf16` product fits exactly in the fp32 accumulator; the only difference is K-dim summation order, ~1e-5).

### Key design decisions

- **No environment variable.** The fast path is enabled automatically when:
  - Checkpoint weight dtype is bfloat16 (recorded by overriding `weight_loader` — the only reliable observation point before `copy_` and NZ-repack)
  - Input dtype is bfloat16 (checked at `forward` time, no risky cast)
  - Output dtype is fp32 (so `torch.mm(out_dtype=fp32)` is the only out_dtype supported by `aclnnMm MatMulV3` on NPU)
  - No bias (fast path does not handle bias)
  
  All four conditions must hold simultaneously; otherwise the fp32 fallback is used.

- **No dtype conversion in `forward`.** The `_forward_bf16_router` method does not cast `x` or `weight` — it requires `x.dtype == bfloat16` as a precondition (checked by `_use_bf16_fast_path(x)`). This avoids silently introducing precision loss if upstream ever sends non-bf16-origin activations.

- **ND bf16 weight cache (measured).** The bf16 cache stays in ND layout: a layout micro-benchmark (M=3/24) showed bit-identical outputs for ND vs FRACTAL_NZ caches, no measurable benefit from NZ on this `aclnnMm MatMulV3` path, and a pre-transposed-NZ cache ~40% slower (20.1/21.8µs vs 14.7/14.2µs batched). `.t()` on ND is a free stride view (aclnnMm handles transB natively).

- **Cache invalidation on weight reload.** `weight_loader` resets `_bf16_weight` so RL weight-update flows (which reload weights in-place) are reflected on the next forward.

- **Device-mismatch fix.** The `_bf16_weight` cache is rebuilt when `self.weight.device` changes, fixing the issue raised in the original PR review.

- **Forward compatibility.** Models with true fp32 router weights, non-bf16 input, non-fp32 output dtype, or bias are unaffected — the fp32 fallback path is preserved verbatim.

## Background: why the old path was slow

PR #9617 forced fp32 because the pre-existing path was `bf16×bf16→bf16` (bf16 accumulation). The fast path uses `bf16×bf16→fp32` (fp32 accumulation via `out_dtype=torch.float32`), which avoids the precision issue while being ~6x faster:

| Path | Multiply | Accumulate | Output | NPU kernel | Speed |
|------|----------|------------|--------|------------|-------|
| Pre-#9617 (bf16 F.linear) | bf16 | bf16 | bf16 | aclnnMatmulV2 | baseline (broken) |
| #9617 (fp32 F.linear) | fp32 | fp32 | fp32 | aclnnMatmulV2 | 84.8µs |
| **This PR (bf16 mm + fp32 out)** | **bf16** | **fp32** | **fp32** | **aclnnMm MatMulV3** | **13.7µs (6.2x)** |

## Precision verification

**Methodology**: the fp32 path (`F.linear` → aclnnMatmulV2) and the bf16 path (`torch.mm(out_dtype=fp32)` → aclnnMm MatMulV3) both run **on NPU** with the production ops; the float64 reference runs **on CPU**. Shape: N=896, K=7168 (Kimi K3 router).

Findings:

- The bf16 path is closer to the float64 reference on **16/16 shapes** in both metrics: absolute-error ratio stable at **0.52–0.57** (avg 0.55), relative-error ratio at **0.56–0.68** (avg ~0.60).
- mean_abs is essentially flat across M (fp32: 4.34–4.41e-05, bf16: 2.25–2.46e-05) — the error is set by the K=7168 fp32-accumulation structure, not by M; max_abs grows slowly with M purely by extreme-value statistics.
- mean_rel sits at the ~1e-06 scale; max_rel is dominated by near-zero logits and saturates.
- **Top-16 expert selection is 100% consistent at every shape in this sweep**: bf16 vs fp32 matches on **7176/7176** rows across all 16 shapes, and both paths vs the float64 reference are likewise 100% (7176/7176 each).

## Does this PR introduce any user-facing change?

No. The fast path is transparent — it activates automatically for bf16-origin weights and falls back to the existing fp32 path otherwise.

## How was this patch tested

- Precision test on NPU (Ascend910): compared fp32 path, bf16 path, and float64 CPU reference across M=3/24/961 with bf16-origin weights (a true-fp32-weight control, forced through the bf16 math, degrades to 66.7% top-16 consistency — confirming the gate is required and works)
- M-sweep (16 shapes, M=1..896): absolute / relative errors vs float64 CPU reference — bf16 closer on 16/16 shapes; top-16 expert-set match 100% at every shape (bf16 vs fp32: 7176/7176 rows; both paths vs float64 likewise)
- Layout micro-benchmark (nz_bench.py): ND / FRACTAL_NZ / pre-transposed-NZ bf16 caches produce bit-identical outputs; ND + `.t()` selected (pre-transposed NZ ~40% slower)
- `weight_loader` override correctly records checkpoint dtype from safetensors header and invalidates the bf16 cache on reload
- NZ format applied to fp32 weights by `process_weights_after_loading` (unchanged); bf16 cache deliberately kept in ND per the layout benchmark above

> Need check deepseek v4. This Pr may lead to precision problem.

DSV4 is not affected by this PR. Verified against the actual DeepSeek-V4-Flash checkpoint:

Different code path: DSV4's gate is a ReplicatedLinear, not GateLinear — it never touches AscendGateLinear, the only class this PR modifies. Its forward explicitly computes F.linear(hidden_states.float(), self.gate.weight) with precast_fp32_weight = True, so the router stays on the fp32 MatMulV2 path by design ((https://github.com/vllm-project/vllm-ascend/blob/8e74e741e8ef407c9d1f61ce26f504e06c983752/vllm_ascend/models/deepseek_v4/model.py#L292-L295)).

Double-guarded: even if DSV4 were switched to GateLinear in the future, the fast path requires all four conditions — checkpoint weight bf16, activation x.dtype == bf16, out_dtype == fp32, and no bias. DSV4 passes fp32 activations (https://github.com/vllm-project/vllm-ascend/blob/8e74e741e8ef407c9d1f61ce26f504e06c983752/vllm_ascend/models/deepseek_v4/model.py#L404-L405), so the gate condition fails and it falls back to the fp32 path.

The bf16 fast path only activates when both inputs are bf16-origin (lossless upcast, verified bit-exact top-16 on real Kimi K3 weights). Models that deliberately force fp32 — like DSV4 — are structurally excluded.
