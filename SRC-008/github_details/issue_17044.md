### 🐛 Describe the bug

**Scope: the Hybrid connector can report receive completion after a negative transfer result without reporting the failed destination blocks.** This is a reproducible connector failure-contract defect; it is not a claim that the original device error 507035 has been reproduced or causally explained.

At the pinned revision, [`mooncake_hybrid_connector.py`](https://github.com/vllm-project/vllm-ascend/blob/f2f74a16c3c50a76f4349d807918e83edec1e35c/vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py#L591):

1. `_transfer_kv_cache_all_groups` calls `batch_transfer_sync_read`; `ret < 0` raises `RuntimeError` (lines 699–706).
2. `_handle_request` catches the exception and only logs it (599–607).
3. Its `finally` still marks the task done; when the request's task-count/final-marker conditions are met, it updates the completion tracker. It also sends `DONE_RECVING` to the producer (608–619). Producer page release remains conditional on its existing reader-count protocol; this is not a claim that every failure instantly releases every page.
4. This connector file does not override `get_block_ids_with_load_errors`, so the inherited default returns an empty set.

The [vLLM base contract](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/distributed/kv_transfer/kv_connector/v1/base.py#L375) requires asynchronous failed requests still to appear in `get_finished()`, with their failed blocks reported **no later than that same forward pass**. A same-round finished/invalid snapshot is one implementation strategy. The defect is missing failed-block information, **not `finished` by itself**. MultiConnector aggregation cannot reconstruct information that was never reported. Once global completion and other scheduler conditions hold, the request can be treated as a successful KV load; the historical incident does not prove all those conditions across every rank.

#### Candidate experiment and the separate HMA limitation

Preserved CPU tests execute actual AST-extracted source: the original source fails the candidate safety assertions (exit 1), while the local candidate passes 18 deterministic cases (exit 0); original evidence hashes remained unchanged. Cases include negative results/exceptions, earlier-task failure followed by later success, atomic finished/invalid bookkeeping, real DONE/ACK helper behavior, cancellation retention, and multi-reader producer completion.

A separate [scheduler limitation](https://github.com/vllm-project/vllm/blob/568afb3a13806beb53bb2e6bd518269357b237c0/vllm/v1/core/sched/scheduler.py#L2693) matters to a fix: `_update_requests_with_invalid_blocks` uses single-group unpacking with a TODO for HMA. An actual-function test with two KV groups raises `ValueError: too many values to unpack (expected 1)`. The fail-policy path still invokes this helper. This is a compatibility constraint on recovery, not the cause of the negative transfer or a complete explanation of the original crash.

Our **local experimental candidate, not an upstream fix**, uses a matching experimental Mooncake ABI to distinguish a drained logical failure (`-2`) from unknown quiescence (`-1`). It keeps internal finished/invalid bookkeeping, but deliberately raises from worker `get_finished` on failure instead of publishing a normal failed HMA result into that incompatible scheduler. Unknown failures latch local fatal state and withhold subsequent local submissions and DONE/finished publication.

This is **not production-ready**: there is no global rank fence, worker exceptions/process exit do not prove device or remote quiescence, concurrent batches need separate lifetime accounting, DONE lacks epoch/deduplication guarantees, and the candidate serializes receiving work. Full engine failure propagation, cross-rank containment, memory retirement, and performance remain unverified. The 18 CPU tests are not a faulted-model or original-507035 reproduction.

#### Related transport lifecycle report

[Mooncake#4247](https://github.com/kvcache-ai/Mooncake/issues/4247) reports the separate synchronous outer-timeout/quiescence contract, including controlled real-NPU delayed-submit results. A connector fix must account for that lifetime boundary, but neither report proves the historical 507035 root cause.

#### Expected behavior / maintainer questions

- Preserve destination load failures through task aggregation and honor the finished/invalid-block contract.
- Separate logical request failure from proof that a transport has stopped touching source/destination memory. A negative synchronous return alone is insufficient to release ownership if the transport can remain active.
- For unsupported HMA recovery, fail explicitly with coordinated containment rather than silently treating bad KV as successfully received. A local exception alone does not implement that coordination.

Related reports: [#5660](https://github.com/vllm-project/vllm-ascend/issues/5660), [#13439](https://github.com/vllm-project/vllm-ascend/issues/13439), and [#9220](https://github.com/vllm-project/vllm-ascend/issues/9220) describe related transfer/output symptoms, not proof of an identical root cause. These should not be merged into one asserted root cause.
