# [PR #17346] [Performance] Avoid request-count specialization in DSA-CP metadata kernel

source: https://github.com/vllm-project/vllm-ascend/pull/17346
state: open | updated: 2026-09-23T04:01:02Z
labels: module:tests, module:ops

## 正文

### What this PR does / why we need it?

The DSA context-parallel metadata kernel currently uses the request-count block size as a tl.constexpr, producing a separate compiled kernel for each request-count tier.

This change:

- uses a fixed 1024-request tile and scales the launch grid for larger batches;
- computes cumulative local query lengths directly from the clipped interval endpoint, allowing each tile to run independently;
- keeps batch- and rank-dependent scalar bounds out of the JIT specialization key;
- expands boundary coverage around tile edges and includes batches larger than one tile.

### Does this PR introduce _any_ user-facing change?

No API change. DSA context-parallel metadata generation supports request counts above 1024 while reducing runtime compilation variants.

### How was this patch tested?

- Ruff formatting and lint checks.
- Repository pre-commit hooks.
- Ascend 910B/A3 operator validation against a PyTorch reference:
  - 528/528 cases passed with exact integer equality;
  - request counts from 1 through 2048, including 1023/1024/1025 boundaries;
  - TP sizes 1, 2, and 8; first, middle, and last ranks;
  - random and graph-padding inputs;
  - both start-position modes.
- Cold-cache JIT probe: two candidate variants, corresponding to the two start-position modes.
- Alternating A/B device-event benchmark against the original kernel:
  - 22 cases, 20 warmups, 9 trials, 200 launches per sample;
  - geometric-mean speedup: 1.060x;
  - range: 1.022x to 1.114x;
  - no measured regressions.

- vLLM main: https://github.com/vllm-project/vllm/commit/84030bbe3d74d99bad477a3d2e37a973ccd8865c
