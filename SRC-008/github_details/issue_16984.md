## 正文

### Misc discussion on performance

**Setup** (P/D disaggregation, long-prompt serving):

- Model: GLM-5.3-Flash (MoE, W8A8 "ascend" quantization), `--reasoning-parser glm45`
- Topology: 2 prefill replicas (TP8, kv_producer) + 4 decode replicas (TP8, kv_consumer), separate router
- KV transfer: `MooncakeConnectorV1` with `use_ascend_direct: true`, `block_size: 640`, Mooncake store for master/metadata
- Stack: vLLM v0.28.0 + vllm-ascend (internal build dated 2026-09-16; our deployment carries a small local patch on `mooncake_connector.py` — noting this for transparency, but the observations below are engine-level scheduling behavior, not connector-logic behavior)
- Hardware: Atlas 800I A2 (Ascend 910B), 8 NPUs per node

**Observations** — single ~181K-token prompt, cold prefix cache, streaming, `max_tokens=16`, otherwise idle cluster:

| `max_num_batched_tokens` | chunks | cold-cache E2E TTFT | warm-cache E2E TTFT | decode-side KV pull (per-worker log) |
|---|---|---|---|---|
| 8192 | 22 | 37.6 s / 38.2 s | 2.79 s | 2156 ms |
| 32768 | 6 | 34.1 s / 34.6 s | 2.3–2.4 s | 354–862 ms |

What we take from this:

1. During the ~30 s prefill wall time, the engine's periodic logger reports "Avg prompt throughput" of 12.0K–18.1K tok/s ⇒ only ~10–15 s of the wall time is actual forward compute; the rest is non-compute time inside the prefill engine.
2. Cutting the chunk count 22 → 6 recovered only ~4 s ⇒ the non-compute overhead scales with token/block count (~283 KV blocks for 181K tokens at block_size 640), not with chunk count.
3. The transfer link itself is not the bottleneck: the full 181K-token KV pull on the decode side measures 0.35–0.86 s (RDMA; RoCE port utilization stays <1%), and warm-prefix requests complete end-to-end in 2.3–2.4 s.
4. Conclusion: on this path the prefill-side block upload/management appears to be serialized with forward passes (no compute/transfer pipelining), leaving the NPUs without useful work for roughly half of the prefill wall time on long prompts.

### Proposal to improve performance

Questions for the maintainers:

- Is there a plan (or existing WIP) to **overlap prefill-side KV save/upload with forward compute** on the Mooncake / ascend-direct path — e.g. per-layer or per-chunk async push with double buffering, so chunk N+1 compute runs while chunk N's blocks are uploaded?
- Related upstream work we found:
  - vllm-project/vllm#56874 — per-layer overlapped WRITE-push for the NIXL connector; its motivation ("KV transfer does not overlap with prefill compute ... leaves throughput on the table") matches our observation exactly
  - #16039 — unified layerwise pull flow with async layer readiness + batched/coalesced block-address planning
  - #16374 — decode-side scheduling improvement (poll finished KV transfers during dummy batches), which addresses the complementary wait
- If this is already on the roadmap, which release is it targeting? If not, we are happy to contribute profiling data (per-step timings, block upload traces) to support the design — our measurements suggest ~2x TTFT headroom on long prompts from pipelining alone.

### Your current environment (if you think it is necessary)

vLLM v0.28.0 (system fingerprint `vllm-0.28.0-tp8-ep`) + vllm-ascend internal build, Ascend 910B / Atlas 800I A2, 8 NPUs per node. Happy to run `collect_env.py` and attach the output, plus the benchmark script used for the numbers above, if that helps.

### FengHao777 · 2026-09-21

**Performance baseline for the reporting setup** (same deployment as the original post: GLM-5.3-Flash W8A8, vLLM v0.28.0 + vllm-ascend internal build 2026-09-16, MooncakeConnectorV1 + use_ascend_direct; topology now scaled to **4 prefill + 4 decode** workers, TP8 each, 910B x8 per node).

Benchmark: stdlib async client from the gateway host, streaming requests with `stream_options.include_usage`; TTFT = arrival of first non-role delta (reasoning or content); output tokens counted from `usage.completion_tokens` (includes reasoning tokens). Prompts are freshly generated random text per request (cold prefix cache unless noted).

**Concurrency ladder** (~3.6K-token prompts, max_tokens 512):

| concurrency | agg output (tok/s) | TTFT p50 / p90 / p99 (s) | TPOT p50 |
|---|---|---|---|
| 1 | 23.3 (single-stream) | 1.87 | 43 ms |
| 8 | 150 | 2.7 / 5.3 / 5.4 | 44 ms |
| 16 | 275 | 3.9 / 6.6 / 8.1 | 45 ms |
| 32 | 390 | 7.7 / 17.6 / 17.8 | 53 ms |
| 64 | 625 | 9.5 / 15.2 / 15.3 | 68 ms |

**Long-input anchors** (single request, cold prefix cache): ~29K-token prompt → TTFT 5.5 s (8.2 s at concurrency 8); ~181K-token prompt → TTFT 34 s cold vs 2.3 s warm. Decode-side full-KV pull for the 181K request measures 0.35–0.86 s (per-worker connector log), consistent with the original post — the transfer link itself is fast.

Two observations that may be useful for the overlap/pipelining work:

1. Long-input TTFT scales roughly linearly with prompt length (~0.19 s per 1K tokens cold), which matches the "non-compute overhead scales with token/block count" finding in the original post — doubling prefill workers from 2 to 4 did **not** change single-request long-prompt TTFT (5.5 s @29K before and after), as expected if the cost is inside the per-request prefill pipeline rather than a capacity/queueing issue.
2. The first bulk load after scaling up new prefill workers was markedly slower and unevenly distributed across workers (e.g. conc-16 aggregate 184 tok/s with TTFT p90 24.5 s, one worker taking most of the load), converging to the table above only on the second identical run (275 tok/s, p90 6.6 s). Worth keeping in mind when benchmarking freshly started PD workers.

Happy to share the benchmark script if useful.
