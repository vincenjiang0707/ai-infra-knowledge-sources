## 正文

### What this PR does / why we need it?

**Depends on https://github.com/vllm-project/vllm/pull/52162 and the structured KV-cache fix in [933ffb0adb](https://github.com/recky-c/vllm/commit/933ffb0adb130ac9ba1cc7f5de4413dce65efb1e).** The tested upstream is that fix on top of `42fc76a63aa382ff0ebe3b0adad346b5d38b91c0`. The extra fix is currently in the validation fork; the original upstream PR head alone still assumes every MRv2 cache value is a tensor and cannot initialize Ascend's tuple caches.

With the upstream change, MRv2 assigns decode requests to PCP owners when PCP > 1 and DCP = 1. Ascend must replicate all owners' KV updates before local attention, including collective participation by ranks that own no requests.

- Inherit upstream request assignment, layout indices, cache write masks and output gathering. Forward its constructor and padding arguments.
- Gather dense MLA KV and SFA main/indexer KV before local attention, preserve empty-rank participation, and restore global output layout.
- Keep native preprocessing where fused paths bypass cache synchronization, and reject combinations outside the initial support scope.
- Align the paired upstream's UVA view method, DeepSeek/index-group and graph-manager constructor arguments, SFA CPU-length metadata, and split MRv2 cache-binding API. Avoid eagerly importing an optional V4.1 architecture absent from the paired upstream.
- Check in the PCP regression tests rather than relying on an external test-only commit.

This adapts the upstream implementation instead of duplicating its partitioning algorithm. The PR remains a draft while its upstream dependencies and remaining validation scope are reviewed.

### Does this PR introduce _any_ user-facing change?

MRv2 follows the upstream sharding policy, enabled by default for PCP > 1 and DCP = 1. The paired upstream [d13f652504](https://github.com/recky-c/vllm/commit/d13f6525041b103fd566335945b0afefa321a6b0) adds `--enable-pcp-decode-sharding` / `--no-enable-pcp-decode-sharding`, allowing A/B comparisons at identical topology. Ascend consumes the same upstream option rather than adding a separate switch. Python callers can set `enable_pcp_decode_sharding=False`.

```bash
VLLM_USE_V2_MODEL_RUNNER=1 vllm serve <DeepSeek-model-path> \
    --prefill-context-parallel-size 2 \
    --decode-context-parallel-size 1 \
    --enable-expert-parallel --async-scheduling --enforce-eager \
    --enable-pcp-decode-sharding
```

The initial scope is eager, non-hybrid DeepSeek V2/V3/V3.2 with RoPE and MLA/SFA. Dense MLA requires unquantized KV. Graph execution, speculative decoding, KVPP and PCP O-proj weight sharding are rejected when decode sharding is active. MRv1, PCP = 1 and DCP > 1 retain their existing policy.

The full KV cache remains replicated. No throughput or latency improvement is claimed from these correctness tests.

For replicated-decode performance comparisons, replace the last flag with `--no-enable-pcp-decode-sharding`. Keep EP, asynchronous scheduling, topology and workload fixed. To isolate sharding from MLA preprocessing differences, set `--additional-config '{"enable_mlapo":false}'` for both runs.

### How was this patch tested?

Validated Ascend commit: `ba959f13486bf0b4b2934224ec464f0efe8b2348`.

The subsequent switch-only upstream commit `d13f652504` passed **10 targeted CLI/configuration tests**, covering default/on/off behavior, topology eligibility, unchanged world size and configuration hashing. Its new CLI option has not been rerun through NPU generation because the original validation host became unreachable. The NPU results below remain those of upstream `933ffb0adb`; the new option defaults to the same enabled policy. Ascend commit `851a3ded7` documents the toggle without changing runtime code.

**CPU regression: 499 passed, 49 skipped.** Ran the PCP manager, MRv2 runner, MLA, SFA, SFA PCP, indexer, UVA, DeepSeek patch and KV-binding suites using the normal repository CPU mock setup. The 49 skips are release-only dispatch and fused preprocessing cases. These tests do not establish device behavior.

**Real NPU generation: DeepSeek-V2-Lite-Chat, BF16, TP1/PCP2/DCP1, EP enabled, asynchronous scheduling enabled, eager, prefix caching and chunked prefill enabled.** Used max model length 4096, batch token budget 512 and max 16 sequences.

- Single requests, 2/3 concurrent requests, unequal completion lengths, mixed short/1449-token prompts, and long-prefix replay all completed.
- Compared against replicated decode at identical topology with native MLA preprocessing (`enable_mlapo=false` in the control). All **14 outputs / 669 generated token IDs matched exactly**. Two separate sharded runs also matched all 14 outputs.
- Prefix-cache hit counters increased by 4224 tokens in the warm sharded suite; cache replay was actually exercised.
- The default fused-preprocessing control produced different long-request outputs. Exact equivalence is established only for the matched native-preprocessing control, not the fused path.

**SFA execution smoke test:** a two-layer BF16 DeepSeek-V3.2 architecture with random weights, reduced hidden/expert sizes, original attention/indexer head dimensions and index_topk=2048. The same PCP2/EP/async configuration completed 14 requests / 672 generated tokens, including a 2807-token prompt and prefix replay. Every generated token logprob was finite; prefix-cache hits increased by 5376 tokens. This is execution/collective coverage, **not full V3.2 checkpoint accuracy or quantized-model validation**.

Environment: isolated ARM64 Ascend container, Python 3.12.13, PyTorch 2.10.0+cpu with torch_npu 2.10.0.post4; reused compiled artifacts from the validation image. `VLLM_VERSION=0.29.1rc1` selected the existing development API path because the image's generated version file incorrectly labels the checked-out upstream source as release 0.29.0. Commit hashes above identify the actual source. All 17 modified source/test and baseline-policy file hashes were checked against the local trees, and the temporary replicated-decode control was restored afterward.

Ruff lint/format and `git diff --check` passed. `format.sh ci` was attempted: its available checks passed, but several hooks could not execute in the Windows environment. Logger and symbolic-meta checks were subsequently run successfully in Linux. A complete hook-suite pass is not claimed.

Full V3.2 trained-weight accuracy, quantized SFA, other parallel topologies and performance remain unvalidated. Developed with OpenAI Codex assistance; human review is still required.
