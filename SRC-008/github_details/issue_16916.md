## 正文

### What happened?

Serving a hybrid GDN model (**Qwen3.6-35B-A3B**, INT4 W4A16, 40 layers: linear-attention/GDN + full attention) on Atlas 800 A3 with `--enable-prefix-caching` (mamba cache mode resolves to `align`): **concurrent long prefills are scheduled strictly one at a time.**

During a burst of 4 concurrent ~7.5k-token prefills (unique prompts, `max_tokens=2`), `vllm:num_requests_running` **peaks at 1** while the other 3 sit in `waiting` (sampled every 0.5 s from `/metrics`), and wall time equals the sum of individual latencies. Decode-only concurrency is unaffected (6 concurrent short requests → `running=6`).

**Counter-evidence on CUDA:** the same checkpoint with the same flags on the same upstream vLLM version (official `vllm-openai` **v0.28.0**, 2× RTX 3090 TP=2, FP8 weights, `--enable-prefix-caching`) does **not** show this cap — during an identical burst the running gauge climbs well above 1 (the instance also serves unrelated background traffic) and long prefills overlap with other requests.

Disabling prefix caching (no mamba `align` path) raises the long-prefill concurrency cap from 1 to only 2 on Ascend (measured on the v0.27.1-based nightly), so the hard serialization is tied to the align-mode prefill path.

This was verified on **both** the v0.27.1-based nightly (image from ~2026-09-16) and the current nightly with the **vLLM v0.28.0** base — the serialization persists across both, while CUDA v0.28.0 batches prefills. So this looks Ascend-plugin-specific rather than an upstream scheduler limitation.

### Reproduce

```bash
docker run -d --name qwen36-35b-test --shm-size 32g \
  -e ASCEND_RT_VISIBLE_DEVICES=0 -e HF_HUB_OFFLINE=1 -p 8015:8000 \
  -v /usr/local/dcmi:/usr/local/dcmi \
  -v /usr/local/bin/npu-smi:/usr/local/bin/npu-smi \
  -v /etc/ascend_install.info:/etc/ascend_install.info \
  -v /data2/models:/data2/models \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver \
  --device /dev/davinci3 --device /dev/davinci_manager \
  --device /dev/devmm_svm --device /dev/hisi_hdc \
  quay.io/ascend/vllm-ascend:nightly-main-a3 \
  vllm serve /data2/models/Avesed/Qwen3.6-35B-A3B-INT4-W4A16 \
    --served-model-name Qwen/Qwen3.6-35B-A3B \
    --tensor-parallel-size 1 --gpu-memory-utilization 0.9 \
    --reasoning-parser qwen3 --tool-call-parser qwen3_xml --enable-auto-tool-choice \
    --limit-mm-per-prompt '{"image":0,"video":0}' \
    --enable-prefix-caching --max-model-len 131072 \
    --host 0.0.0.0 --port 8000
```

Then fire 4 concurrent requests (~7.5k-token prompts, e.g. a system prompt of `"文档{i}：" + "接口定义与数据流程说明。" * 1500`, `max_tokens=2`, `chat_template_kwargs={"enable_thinking": false}`) and poll `/metrics` at 0.5 s:

```
vllm:num_requests_running  → peaks at 1
vllm:num_requests_waiting  → peaks at 3
```

Control on CUDA (same model family, FP8, same flags): `running` exceeds 1 during the same burst.

### Observed vs expected

| setup | long-prefill burst (4 concurrent ~7.5k tok) |
| --- | --- |
| A3 nightly, vLLM 0.27.1 base, APC on | `running=1`, serialized |
| A3 nightly, **vLLM 0.28.0** base, APC on | `running=1`, serialized |
| CUDA v0.28.0 (official image), APC on | `running` > 1, prefills batched |
| A3 nightly, vLLM 0.27.1 base, **APC off** | `running=2` (better, still not full) |

Expected: align-mode prefill chunks from different requests should be schedulable into the same step (upstream shares the token budget across concurrent prefills on CUDA; cf. the block-aligned chunk splitting and its concurrency fix in vLLM #51113).

### Environment

- Atlas 800 A3 node (`SOC_VERSION=ascend910_9391`, 64 GB × 16 chips), driver/npu-smi 26.1.0, CANN 9.1.0
- Image: `quay.io/ascend/vllm-ascend:nightly-main-a3`, digest `sha256:50451593c500f8b130660bb65028271e03bca1a03aae21508ed8d568b8e99689` (built 2026-09-18)
- `vllm==0.28.0+empty`, `vllm_ascend==0.19.1rc2.dev2256+gc8addbb24`, `torch_npu==2.10.0.post4`, triton-ascend 3.2.2
- One replica per chip (TP=1); also reproduced with the v0.27.1-based nightly from the same tag

### Additional context

- No accuracy problems observed; outputs are correct on both stacks. The issue is purely scheduling throughput for long prefills.
- We see this in production behind multi-turn/agent traffic where several long prompts arrive together; TTFT of requests 2..N is effectively the sum of all prefills.
- Happy to run candidate patches, capture ascend profiler traces, or test specific branches on A3.


## 评论 (1)

### Phoveran · 2026-09-19

## Correction: root cause is the default `max_num_batched_tokens=2048`, not a platform scheduling difference

I need to retract the CUDA-vs-Ascend contrast in the original report — it was confounded: the CUDA instance in my test also serves live background traffic, so `running > 1` there did not prove concurrent long prefills (its default budget is also 2048, since 24 GB < 70 GB). After instrumenting the scheduler I reproduced the **same** serialization on CUDA-class defaults.

### Actual root cause

On this hardware class the `OPENAI_API_SERVER` default of `max_num_batched_tokens` is **2048** (the `< 70 GB` else-branch default in `EngineArgs._get_default_max_num_batched_tokens`, v0.28.0; A3's 64 GB chips and RTX 3090 both fall into it). With ~10.5k-token prompts:

- each prefill needs 6 chunks of exactly 2048 tokens (one full budget per engine step, ~1.2 s/step on A3),
- the next waiting request faces a leftover budget < `block_size` (2048), so `_mamba_block_aligned_split` returns 0 and the **waiting loop `break`s** (scheduler.py, waiting-queue align handling) — head-of-line blocking for everything behind it,
- net effect: long prefills strictly serialize, `running=1`, wall time ≈ sum of individual TTFTs.

Instrumented trace (one burst, 4 requests × 10524-token prompts):

```
SCHEDDBG align_split req=A start=0     end_pre=2048  ret=2048 block=2048 budget=2048
SCHEDDBG align_split req=A start=2048  end_pre=4096  ret=2048 block=2048 budget=2048
SCHEDDBG align_split req=A start=4096  end_pre=6144  ret=2048 block=2048 budget=2048
SCHEDDBG align_split req=A start=6144  end_pre=8192  ret=2048 block=2048 budget=2048
SCHEDDBG align_split req=A start=8192  end_pre=10240 ret=2048 block=2048 budget=2048
SCHEDDBG align_split req=A start=10240 end_pre=10524 ret=284  block=2048 budget=2048
SCHEDDBG WAITING-BREAK req=C budget=2048   ← repeats until A finishes
```

### Fix (config, no code change)

`--max-num-batched-tokens 16384` (the value the official vllm-ascend Qwen3.5/3.6 recipe already uses):

| burst (4 × 10.5k-token prompts, APC on, align mode) | budget 2048 | budget 16384 |
| --- | --- | --- |
| peak `num_requests_running` | 1 | **4** |
| wall time | ≈ 4 × single (serial) | **7.4 s total, all 4 in flight simultaneously** |
| GPU KV cache size | 1,468,006 tok | 1,408,087 tok (−4%, acceptable) |

So: no vllm-plugin bug after all — the serialization is the interaction of a very small per-step token budget on <70 GB hardware with long prompts, amplified by align-mode block alignment (any leftover < `block_size` is unusable by another align-mode prefill, and the waiting-loop `break` blocks the whole queue behind the head request).

### Suggestions

1. For users on 64 GB-class accelerators (A3) serving long prompts: set `--max-num-batched-tokens` explicitly (16384+). The generic `< 70 GB` else-branch default of 2048 seems too small for this class of hardware — worth reconsidering upstream.
2. Minor: in the waiting-request loop, when `_mamba_block_aligned_split` returns 0 due to insufficient budget, later requests cannot fit either (leftover < block_size), so `break` vs `continue` is equivalent today — but if the block-grid granularity ever becomes finer, a `continue` (with a per-step attempt counter) would avoid head-of-line blocking.
3. The official docs already hint at `block_size`-related caching limits for these models; adding "long prompts + default 2048 budget → serial prefill" to the same FAQ section would have saved me a day.

Closing this as the reported behavior is configuration-reachable and explained; happy to reopen or split into a feature request for smarter defaults if maintainers prefer.
