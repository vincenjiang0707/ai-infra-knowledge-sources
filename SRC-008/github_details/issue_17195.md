# [Issue #17195] [Bug]: Encoder lookahead can cause a zero-progress scheduling loop with multimodal K3 DSpark

source: https://github.com/vllm-project/vllm-ascend/issues/17195
state: open | updated: 2026-09-22T12:46:41Z
labels: bug, triaged

## 正文

## Summary

We observed requests making no further progress during multimodal prefill with Kimi K3 and DSpark on vLLM Ascend. Scheduler instrumentation shows a circular dependency between encoder-cache reclamation and the shifted encoder scheduling window:

1. A request reaches the end of a previously encoded image.
2. The encoder entry remains referenced because reclamation requires one additional token of progress (`spec_lookahead = 1`).
3. The next image cannot fit in the remaining reclaimable encoder-cache capacity.
4. With `shift_computed_tokens = 1`, encoder scheduling truncates the request to zero tokens.
5. No progress means the previous entry cannot be released, so the same decision repeats.

This report concerns an Ascend K3 DSpark implementation. We have not reproduced it on the upstream GPU DSpark implementation or verified whether current upstream main has the same behavior.

## Environment and affected code

- Backend: vLLM Ascend, four nodes / 64 NPUs, DP=4, TP=16, EP enabled.
- Target model: Kimi K3; speculative method: `dspark`; draft model type: `k3_dspark`.
- Scheduler: `vllm.v1.core.sched.async_scheduler.AsyncScheduler`.
- Chunked multimodal prefill and Mamba block alignment enabled.
- Encoder cache capacity and initial per-step encoder compute budget: 16817 embeddings.
- The tested code includes the Mamba alignment-before-encoder-caps change from #51603.
- In the affected implementation, `SpeculativeConfig.use_eagle()` includes `dspark`, so the scheduler has `use_eagle=True`.

This is a development deployment with local diagnostic changes, rather than an unmodified published release. Exact deployed vLLM/vLLM Ascend commit IDs and the full launch configuration remain to be attached.

## Observed scheduler state

Two requests on the same DP scheduler retained their previous image entries at exactly the image end. Request IDs are replaced with A and B below; numerical values are from the captured logs.

| Field | Request A | Request B |
|---|---:|---:|
| `num_computed_tokens` | 19608 | 28059 |
| `num_output_placeholders` | 0 | 0 |
| Previous image index | 6 | 8 |
| Previous image offset | 18719 | 27051 |
| Previous image placeholder length | 889 | 1008 |
| Previous image end (exclusive) | 19608 | 28059 |
| Previous image encoder embeddings | 880 | 999 |
| Next image offset | 19609 | 28060 |
| Next image encoder embeddings | 16512 | 16485 |

The previous entries are fully consumed by the target, but the reclamation condition is false:

```python
image_end + 1 <= num_computed_tokens - num_output_placeholders
```

Both entries remain referenced. The total reclaimable capacity is:

```text
16817 - 880 - 999 = 14938
```

Neither next image fits (16512 and 16485 respectively), although either fits in the full cache. The encoder compute budget is sufficient; the allocation failure is cache capacity.

Mamba alignment produces a positive token count (360 / 357 in the captured decisions). The subsequent encoder cap produces zero:

```python
max(0, next_image_offset - (num_computed_tokens + shift_computed_tokens))

# A: 19609 - (19608 + 1) == 0
# B: 28060 - (28059 + 1) == 0
```

Consequently, neither request advances far enough to release its previous entry.

## User-visible behavior

Requests remain pending and workers repeatedly execute dummy batches. Initial Python stack samples frequently landed in the DSpark dummy path at `query_start_loc_cpu.to(self.device)`, but paired entry/return logs showed that copies returned and iterations continued. The scheduler trace identifies a zero-progress loop rather than establishing a permanently blocked device copy.

An earlier workload request eventually hit its client-side 36000-second read timeout. That timeout was not a successful model response.

## Reproduction status

The failure was observed in a workload containing concurrent requests with multiple differently sized images. A standalone curl request did not reliably reproduce it. We do not yet have a self-contained public image dataset and launch command reproducing this exact deployment.

A focused scheduler regression can construct the two-request state above:

1. Set encoder cache capacity to 16817.
2. Retain entries of 880 and 999 embeddings for requests A and B.
3. Set each request's computed frontier to its previous image end, with no output placeholders.
4. Place the next image one token after that frontier, requiring 16512 / 16485 embeddings.
5. Enable encoder scheduling shift and reclamation margin of one.
6. Verify that freeing retains both entries and encoder scheduling returns zero for both requests despite positive input token budgets.

These values describe the failure state and a proposed regression setup; they are not a claim of a completed upstream GPU reproduction.

## Why the draft implementation matters

In this Ascend K3 DSpark implementation, the draft consumes target hidden states and token embeddings. Its `embed_input_ids()` accepts multimodal arguments for interface compatibility but returns `self.embed_tokens(input_ids)`; it does not gather shifted multimodal encoder embeddings.

Therefore, using `use_eagle` as the encoder-consumer capability appears too broad for this implementation: it enables EAGLE-style encoder lookahead even though this draft does not consume those embeddings.

## Local mitigation and validation

We introduced a separate encoder lookahead helper and used it in both running/waiting encoder scheduling paths and encoder-cache reclamation:

```python
def _get_encoder_lookahead(self) -> int:
    spec = self.vllm_config.speculative_config
    if spec is not None and spec.method == "dspark":
        draft_config = getattr(spec, "draft_model_config", None)
        hf_config = getattr(draft_config, "hf_config", None)
        if getattr(hf_config, "model_type", None) == "k3_dspark":
            return 0
    return 1 if self.use_eagle else 0
```

This does not disable speculative decoding or alter speculative KV lookahead allocation. It is a narrowly scoped local mitigation, not a proposal to remove the EAGLE/MTP lifetime protection for all draft models.

After deployment, all four DP schedulers logged `shift_computed_tokens=0`. Subsequent workload logs showed forward progress and cache-reference release. For example:

```text
DP0 request:
  computed: 24960 -> 32343 -> 48768
  previous image end: 32342
  next image start: 32343
  scheduled: 7383, reaching 32343
  previous image released
  reclaimable slots: 3089 -> 16817
  next image allocation: successful

DP3 request:
  computed: 41856 -> 58368 -> 71808
  progressed to the final image (index 10)
```

One diagnostic field initially still reported `reference_lookahead=1` because the logging helper independently derived it from `use_eagle`; that diagnostic has been corrected to call the helper. The excerpts above demonstrate progress, but do not establish final completion of every request or isolate the effect of the reclamation change from the scheduling-window change.

## Related work

- #46315 adds encoder-cache lifetime protection for EAGLE/MTP draft embedding access. Its review discussion also questions whether the extra lifetime step is required. This report is about applying that policy to a draft implementation without shifted multimodal embedding consumption.
- #40707 reports a similar multimodal cache/scheduling deadlock where Mamba alignment rounds a short chunk to zero.
- #51603 changes Mamba alignment to run before encoder caps. Our captured failure occurs after that change: alignment returns a positive count, and the encoder cap then returns zero.

## Expected behavior / design question

Encoder lookahead should reflect actual draft consumption of multimodal embeddings, while preserving the required lifetime protection for EAGLE/MTP consumers. Under cache pressure, the scheduler should avoid retaining entries in a state where the progress needed to release them cannot be scheduled.

Would an explicit draft capability for shifted multimodal encoder consumption be preferable to deriving this policy from `use_eagle()`? Is there an existing upstream abstraction or fix that this implementation should use?
