# [PR #40857] [mem_cache][PD] Fix decode radix cache ownership and allow EAGLE/EAGLE3 with decode radix cache

state: open | updated: 2026-09-23T07:11:03Z

## 正文

## Motivation

Fix KV ownership during post-insert repointing and allow `--disaggregation-decode-enable-radix-cache` with EAGLE and EAGLE3. These combinations previously failed startup validation.

### Observed failure

Seen on a 1-prefill / 1-decode deployment of gpt-oss-120b (hybrid SWA, page size 64) with EAGLE3 (3 steps, top-k 1, 4 draft tokens) and `--disaggregation-decode-enable-radix-cache` on the decode server, with the speculative-decoding guard relaxed and a 65,536-token decode KV pool. Single-turn traffic, including 500 GSM8K requests at 16 concurrency, ran clean. Multi-turn traffic (second turn = first-turn prompt + first-turn output, so the prefix hit lands on KV the decode server generated itself) then killed the decode scheduler at the next idle moment, after every request had returned HTTP 200:

```
ValueError: pool memory leak detected! [full] total=65536, available=768, evictable=65152, protected=0, session_held=0, uncached=0
[swa] total=52224, available=19136, evictable=33152, protected=0, session_held=0, uncached=0
```

`available + evictable` exceeds `total` by 384 tokens (6 pages) in the full pool and by 64 (1 page) in the SWA pool. With `SGLANG_DEBUG_MEMORY_POOL=1` and a tree walk at the failure point: the tree's size counters matched the recomputed per-node sums and `sanity_check` passed, the allocator's free list held no duplicate page, but exactly 6 full pages and 1 SWA page were referenced by a tree node **and** present on the free list — real double ownership, not a counting drift. The first shared SWA page had been freed by `maybe_evict_swa` (called from `eagle_prepare_for_decode`) for a running request while a tree node still owned it. A later run tripped the pre-existing assertion directly, in `cache_unfinished_req` during decode-side admission: `AssertionError: new_prefix_len=256, len(new_indices)=0` — the insert had overlapped 256 tokens already in the tree, and the re-match returned nothing.

The same multi-turn loop reproduced the failure within 1–5 rounds in three of four runs on the base commit. Without speculative decoding, 12 rounds did not trigger it; the bigram key is what makes the short re-match likely, not what makes it possible.


### Root cause

The previous code re-matched the prefix after insertion. A normal SWA match requires a full live window, but disaggregated decode can allocate SWA slots only for the prompt's recent tail. EAGLE's bigram key can move the page-aligned insert boundary back one page, leaving less than a full live window inside the inserted range.

The re-match can therefore stop short even though the tree already owns the whole inserted range. This leaves `cache_protected_len` too small: subsequent SWA eviction or finished-request insertion can free tree-owned slots, corrupting allocator ownership and triggering the scheduler's idle pool check.

## Modifications


Repoint unfinished requests using canonical indices collected from the final insert node to the root, and assert that they cover the entire page-aligned insert. With this ownership fix in place, extend the speculative-algorithm allowlist and update the CLI help to match.
