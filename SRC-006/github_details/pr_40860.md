# [PR #40860] [DSv4.1] Support SM90 candidate indexers

source: https://github.com/sgl-project/sglang/pull/40860
state: open | updated: 2026-09-23T06:48:06Z
labels: deepseek, jit-kernel

## 正文

## Motivation

Extend the candidate indexer introduced in #40352 to SM90, following the Hopper work in #40574. The existing Hopper consumer paths score the full context before masking out positions outside the candidate pool.

DeepGEMM does not currently provide the paged sparse MQA logits kernel used by the SM100 candidate indexer on SM90. Our initial implementation gathered each query's candidate K rows and scored them with Torch. Although this reduced the number of scored positions, materializing per-query K introduced enough overhead to regress prefill TTFT at 32K and 64K.

This PR adds a Triton scorer that reads candidate K positions directly from shared BF16 K, avoiding that intermediate gather tensor. Once an appropriate DeepGEMM sparse MQA interface is available on SM90, the scorer can be replaced behind the same candidate indexer protocol.

## Modifications

- Add `TritonCandidateIndexer` and integrate SM90 prefill publication and selection through `publish_prefill` / `select_prefill`.
- Reuse `PrefillCandidateBlocks` and tail slicing. Score only candidate positions in consumer layers, with causal and padding masks applied in the Triton kernel; restore logical positions after Top-K.
- Retain dense scoring for source and non-candidate prefill layers. This change avoids per-query candidate K materialization; it does not eliminate the existing cache dequantization or fuse Top-K into scoring.
- Include SM90 decode protocol integration and candidate block addressing in the paged FP4 scorer, preserving the upstream dense invisible-tile optimization.
- Retain an independent Torch reference in tests and add candidate scorer and indexer coverage.

This PR is opened for early feedback with the initial correctness tests and prefill performance results below. Decode integration is included; dedicated decode performance tests and broader model accuracy validation will be added in follow-up updates to this PR.

## Accuracy Tests

**49 tests passed on H20** on the same source tree as the submitted commit:

- Prefill candidate scoring against an independent Torch reference.
- Indexer publication/selection, causal masking, padding, logical index mapping, and tail handling.
- Paged FP4 decode candidate scoring, including kernel-level CUDA Graph replay.

These are kernel and interface correctness results, not a completed model-level accuracy evaluation. Additional validation will be added: fixed GSM8K smoke cases, long-context retrieval, and a complete model-level benchmark such as GPQA Diamond. The partial GPQA run is not reported as an accuracy score.

Dedicated decode end-to-end correctness, DSpark/CUDA Graph integration, and performance testing are still pending. CP>1 and B200 execution of the pairwise tests have not been validated.

## Speed Tests and Profiling

Single node with 8×H20-3e, TP8/EP8/DP1/CP1, FlashInfer MXFP4 with FP8 compute, no speculation, chunked prefill size 1024, concurrency 1, and output length 1. CUDA Graphs and profiling were disabled during timing. Each length used identical input IDs across variants, a cache flush before each request, one warmup and three measured requests. Values are median streaming TTFT in seconds.

| ISL | Main (s) | Gather prototype (s) | This PR: Triton (s) | This PR vs main |
|---|---:|---:|---:|---:|
| 16K | 3.219 | 3.094 | 3.037 | −5.65% |
| 32K | 6.555 | 7.177 | 6.204 | −5.36% |
| 128K | 38.096 | 36.498 | 30.817 | −19.11% |
| 256K | 109.775 | 92.226 | 80.524 | −26.65% |

Main is `1d59ce7c90` and this PR is `48e64918d4`. “Gather prototype” is the approach we tried previously: expand each query’s candidate block IDs into K row indices, gather the corresponding dequantized BF16 K rows into a `[num_queries, num_candidates, head_dim]` tensor, then compute QK scores, apply ReLU and per-head weights, reduce across heads, and select Top-K. When candidates cover all valid K, it scores the shared K directly without materializing per-query copies. Percentages compare main and this PR, using unrounded medians.

These three-sample, single-request measurements do not establish general throughput gains. Dedicated decode measurements will follow.
