## Summary
- `SpatioTemporalScaleFactors` declared its fields as `(time, width, height)`, but every positional consumer expects `(time, height, width)` to match tensor-axis order:
  - `VideoLatentShape.from_pixel_shape()` indexed the tuple positionally (`scale_factors[1]`/`[2]`) assuming `(time, height, width)`, silently swapping the height/width divisors.
  - `get_pixel_coords()` converts the tuple to a tensor positionally (`torch.tensor(scale_factors)`) to scale `latent_coords`, whose axes are ordered `(time, height, width)`.
- `VideoLatentShape.upscale()` already used the named `.height`/`.width` fields, so downscale (`from_pixel_shape`) and upscale were not inverses of each other for any asymmetric (non-square) resolution. The bug was masked because the only current call site (`video_vae.py`) uses symmetric `height=width=32` factors.
- Fix: reorder the `NamedTuple` fields to `(time, height, width)`, and switch `from_pixel_shape()` to named-attribute access instead of positional indexing so this can't silently regress again.

Fixes #19495

## Test plan
- Added `tests/unittest/_torch/visual_gen/test_ltx2_scale_factors.py` (CPU-only, no checkpoint/GPU required), covering:
  - [x] `from_pixel_shape()` with asymmetric factors produces the correct per-axis latent shape
  - [x] `upscale()` round-trips back to the original pixel shape for asymmetric factors
  - [x] `get_pixel_coords()` scales height and width independently and correctly
  - [x] `SpatioTemporalScaleFactors.default()` stays symmetric (regression guard for the common case)
- Verified against the exact repro in the issue: old code produces `(5, 2, 8)` (matching the reported bug), fixed code produces `(5, 4, 4)` and round-trips upscale to `(9, 16, 32)`.
