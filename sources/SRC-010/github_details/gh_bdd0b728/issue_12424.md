### CodersAcademy006 · 2026-06-13

Hey @Doloxetine Traced crash. Root cause: beam-width clamping accidentally sets `mIsSWA=true` on the full-attention model.

**Chain:**

1. `get_max_atten_window_upper_bound` (`resource_manager.py`) computes upper bound as `floor(token_capacity / (max_beam_width * tokens_per_block)) * tokens_per_block`. Large `max_beam_width` (>=32) shrinks this hard.

2. When `max_seq_len > upper_bound` and `max_beam_width > 1`, extra `tokens_per_block` subtracted as safety margin. Clamped window now below `max_seq_len`.

3. `_validate_and_adjust_attention_windows` passes clamped value as window size into C++ `BlockManager`.

4. C++ sets `isSWA = (windowSize < maxSequenceLength) && (windowSize >= 0)` (`kvCacheManager.cpp` ~line 683). Clamped window < `max_seq_len` → full-attention model gets `mIsSWA=true`.

5. During generation, `adjustBlocksIfNeeded` enters `while (mIsSWA && ...)` → tries detach front blocks on a sequence never allocated as SWA → hits `"A block only go out-of-window in SWA"`.

beam_width=16 works, beam_width=32 breaks: exactly where clamped window first drops below `max_seq_len` given KV budget + `tokens_per_block`.

**Fix direction:** `_validate_and_adjust_attention_windows` must not clamp non-SWA windows below `max_seq_len` — doing so silently converts full attention to SWA at C++ level. Two options: (a) floor clamp at `max_seq_len` in Python, or (b) pass an explicit `is_swa` flag from Python to C++ instead of inferring from window/seq_len comparison.

Happy to put up PR, which direction does the team prefer?

### LiRunGuo · 2026-09-23

I tried to reproduce this on current `main` and could not; it looks like it has been fixed since 1.3.0rc8.

**Setup:** `main` at 0d4304aab6 (1.3.0rc28) built from source, PyTorch backend, 1x H200, `Qwen2.5-0.5B-Instruct` (full attention). `max_seq_len=1024`, `max_batch_size=8`, `tokens_per_block=32`, `free_gpu_memory_fraction=0.9`. Each run sent 2 sequential requests with `use_beam_search=True`, `n=best_of=beam`, `max_tokens=256`, `ignore_eos=True`.

| beam width | result |
|---|---|
| 16 | OK: 16 beams × 256 tokens, both requests |
| 32 | OK: 32 beams × 256 tokens, both requests |
| 64 | OK: 64 beams × 256 tokens, both requests |

There was no `A block only go out-of-window in SWA` assert and no hang.

The chain described above no longer applies on `main`. `get_max_atten_window_upper_bound` has been removed. `_validate_and_adjust_attention_windows` now bounds the window by `blocks_in_primary_pool * tokens_per_block`, and when it clamps the window it also lowers `max_seq_len` to match. So the window is never smaller than `max_seq_len`, and the C++ `isSWA = windowSize < maxSequenceLength` stays false for full-attention models. The log confirms `window size=1024 ... max sequence length=1024`.

While testing with small KV cache pools, I did hit a different beam-search failure: CUDA graph warmup aborts startup with `No free block found`. I filed that as #19527 and have a fix ready. If you still see the SWA assert or the hang on a recent build, please share your model and config.
