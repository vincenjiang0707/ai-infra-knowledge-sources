## 正文

## The failure

A campaign dies whenever any role ends its turn before writing the file the
next stage needs. `_require_stage_outputs` raises, and because it raises
*before* the checkpoint advances, its own docstring already names the recovery:

> Raising here leaves the checkpoint un-advanced (`stage` still names this
> role), so **simply re-running the workflow retries the same stage**

That sentence is addressed to a person. An unattended campaign does not have
one, so the recovery never happens.

**Observed.** A Gemma-4 31B NVFP4 run reached round 3 of 8 with +5.67%
cumulative gain, six hours in. Round 3's analyzer submitted a Slurm profiling
job, armed a watcher on it, and ended its turn on a note reading:

```
JOB IN FLIGHT. Slurm 839482 (g4-31b-nvfp4-analyze-r3, RUNNING, 1 node / gpu:4)
NEXT TURN MUST: collect job 839482's artifacts (nsys timing + A2a ...)
```

There is no next turn in a one-shot stage. The workflow aborted on a missing
`profile_findings.md`. The job completed **successfully 21 minutes later**
(`sacct`: `COMPLETED`, elapsed `00:26:33`) with nobody left to read it, and six
hours of work was discarded for a one-line command nobody was there to type.

For scale, that analyzer ran 19 turns / 496s. The same campaign's round-1
analyzer ran 104 turns / 3571s and round-2 ran 54 / 2110s — both waited long
enough by accident, because they still had other work to do while the job ran.
19 is not a cap: the same round's integrator ran 41 turns.

## Two halves, because the trigger and the damage are separate

### The damage is mode-independent

`_require_stage_outputs` now raises `StageOutputsMissing`, and `cli.main`
re-runs the workflow when it sees one. The checkpoint has not advanced, so the
re-run resumes into the same stage and the role gets another turn — exactly the
documented recovery, minus the person.

The budget (`--stage-retries`, default 1) is counted **per checkpoint position**,
not per run. A campaign is dozens of stages across many rounds; one global
counter would let an early hiccup spend the allowance a later one needs, and
would equally let a permanently stuck stage burn the whole budget while
appearing to make progress. Keyed on position, the count resets whenever the
campaign actually moves, and a stage stuck in one place still stops.

**Only this failure is retried.** A deliverable that exists but is *invalid* —
a roadmap failing schema validation, which has ended two other campaigns
(`baseline.value` got None; `items[3].expected_gain_pct` got 0.0) — replays the
same bytes on a re-run, so retrying could only bury the real error under
repeated attempts. That is why this has its own exception type rather than
being caught as `RuntimeError`.

### The trigger is specific to remote execution

Running on the cluster, a foreground `srun` blocks and the question cannot
arise. Over SSH the role *must* poll, and polling is what makes stopping early
possible.

The remote block added in #18789 says "Submit through the configured SSH target
and wait for Slurm to finish" but never states that the role has exactly one
turn — so "wait" was readable as something a later turn could finish. It now
says so explicitly, and says why this differs from running on the cluster.

Across the campaigns on this deployment, `Monitor`-style async waiting appears
**0 times in 20 local runs** and **4–6 times per remote run**, which is the
mechanism: remote is the only mode where ending a turn early is even available.

The prompt change lowers the probability; the retry removes the consequence.
Neither is sufficient alone — prompts are not guarantees, and a retry that
needs a person is not a retry.

## Tests

`tests/workflows/perf_optimize/test_stage_retry.py` pins the loop against a
stand-in (a real workflow is hours of GPU time): which failures retry, how many
times, that the budget is per position, that a stuck stage still stops, that
schema failures are *not* retried, and that `--stage-retries 0` restores the
previous behaviour. `test_prompts.py` pins the one-turn contract.

```
1325 passed, 3 skipped
```

## Not fixed here

Found while reading #18789, and worth its own change rather than being smuggled
into this one:

`remote_run_root` has no campaign component when set explicitly in `task.yaml`
(the default `~/agent_flow_workspace/{campaign_name}` does). Per-job isolation
beneath it is prose in the prompt — "rsync ... into an isolated directory under
the remote run root", "then remove that remote job directory" — rather than
anything the code enforces. With concurrent campaigns sharing a configured root
and every role told to delete its own job directory when done, that is a
silent-corruption risk.
