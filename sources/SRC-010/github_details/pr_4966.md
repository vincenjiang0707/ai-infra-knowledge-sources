# [PR #4966] fix(pytorch): avoid health RPC scheduling delay

## 正文

## Motivation

The PyTorch MP worker exposed `get_health_status()` as an async RPC handler even though its implementation contained no
await points. `AsyncRPCServer` schedules async handlers as separate tasks, so a health probe can be delayed when the ZMQ
socket remains busy. In a controlled RPC stress test, async health handlers timed out while equivalent synchronous
handlers remained responsive.

## Modification

- Add `Engine.get_local_health_status()` as a synchronous, local-only health snapshot.
- Keep `Engine.get_health_status()` async so the backend-facing interface remains consistent.
- Make `EngineWorkerBase.get_health_status()` synchronous and have it return the local snapshot inline.
- Add a unit test that protects the synchronous worker RPC contract.

The health checks still cover the request loop, main engine loop, engine-loop tasks, and scheduler metrics.

In three Qwen3-4B/H200 runs at concurrency 128, the worker-side sync handler changed health RPC latency as follows:

| Metric | Async baseline | Sync handler |
|---|---:|---:|
| p50 | 36.49 ms | 18.99 ms |
| p95 | 44.45 ms | 22.73 ms |
| p99 | 52.51 ms | 24.38 ms |
| Maximum | 95.10 ms | 30.53 ms |

API-process event-loop lag p99 remained effectively unchanged (1.967 ms vs 1.971 ms), and neither variant produced
inference failures.

## BC-breaking (Optional)

None. The async `get_health_status()` backend interface is unchanged.
