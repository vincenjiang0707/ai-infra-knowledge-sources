# [Issue #79611] [Bug] PD_TensorSetStrides truncates int64 strides to int on macOS x64 (c_tensor.cc:272)

state: closed | updated: 2026-08-04T22:14:41Z

## 正文

## Bug Description

`PD_TensorSetStrides` in `paddle/phi/capi/lib/c_tensor.cc:272` truncates `int64_t` stride values to `int` when constructing the DDim shape vector:

```cpp
void PD_TensorSetStrides(PD_Tensor* tensor,
                         int64_t nstrides,
                         const int64_t* strides,
                         PD_Status* status) {
  // ...
  auto cc_tensor = reinterpret_cast<phi::DenseTensor*>(tensor);
  std::vector<int> shape(strides, strides + nstrides);  // BUG: int vs int64_t
  cc_tensor->set_strides(common::make_ddim(shape));
}
```

On macOS x64 (where `sizeof(int) == 4` and `sizeof(int64_t) == 8`), any stride value exceeding `INT_MAX` (2,147,483,647) is silently truncated. This causes `ValueError: Type of attribute: strides is not right` when PaddleOCR and PaddleX initialize their inference predictors, because the tensor descriptor receives corrupted stride values.

The root cause is the mismatch between the API contract (`int64_t* strides`) and the internal storage (`std::vector<int>`). The DDim class uses `int64_t` throughout (confirmed in `paddle/common/ddim.h`: `operator[]` returns `int64_t`), so this bug silently corrupts tensor metadata on platforms where `int` is 32-bit.

## Environment

- **OS**: macOS x86_64 (Intel)
- **PaddlePaddle**: 3.0.0+
- **PaddleOCR / PaddleX**: 3.7.0+
- **Python**: 3.x
- **Reproduction**: Any inference pipeline exercising the C API path (e.g. `paddleocr`, `create_pipeline` in PaddleX)

## Minimal Reproducer

```python
from paddleocr import PaddleOCR
ocr = PaddleOCR(lang='en', use_doc_orientation_classify=False, use_doc_unwarping=False)
result = ocr.ocr('/path/to/image.png')
# ValueError: Type of attribute: strides is not right
```

## Fix

Change line 272 of `paddle/phi/capi/lib/c_tensor.cc` from:

```cpp
std::vector<int> shape(strides, strides + nstrides);
```

to:

```cpp
std::vector<int64_t> shape(strides, strides + nstrides);
```

`common::make_ddim()` accepts `int64_t` (DDim is `Dim<int64_t>` per `paddle/common/ddim.h`), so no downstream changes are needed.

**Why `std::vector<int>` was used**: Unknown — possibly pre-dating the `no-int32-type-dims.yml` CI rule. The strides field in DDim has always been `int64_t`.

## Priority

High — this silently corrupts tensor metadata on macOS x64 and any other 32-bit-int platform for any workload using the C API, which is the primary path for PaddleX and PaddleOCR inference initialization.
