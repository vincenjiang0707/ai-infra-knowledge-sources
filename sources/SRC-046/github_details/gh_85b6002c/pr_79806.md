### Description

#### 问题背景

`AttributeManager`（`paddle/fluid/pir/dialect/operator/ir/op_dialect.cc`）是 `OperatorDialect` 内部用来把算子属性名从 `std::string` 转成 C 风格字符串数组、并负责其生命周期的辅助单例，供 `RegisterOpInfo` 注册算子接口时使用。

它的析构函数用标量 `delete` 释放了由 `new[]` 分配的内存，分配与释放不配对：

- `char_pointers_[i][j]` 由 `new char[attr_name.size() + 1]` 分配
- `char_pointers_[i]` 由 `new const char*[attr_names.size()]` 分配

按 C++ 标准（[expr.delete]/2），`new[]` 分配的对象必须用 `delete[]` 释放，两者混用是未定义行为。

#### 为什么一直没有暴露

`char` 是平凡析构类型，libstdc++ 中 `operator new[]` / `operator delete[]` 对这类 POD 基本只是转发到 `malloc` / `free`，且不携带数组 cookie，因此在默认分配器（glibc）下运行时“碰巧”正常，这个 UB 长期没有被发现。在 ASan 下则会直接报 `alloc-dealloc-mismatch (operator new [] vs operator delete)`。

#### 实际暴露场景

在使用 jemalloc 作为内存分配器时，Paddle 进程运行结束后会在退出阶段崩溃，定位到正是这里的 `new[]` / `delete` 不配对。

#### 改动内容

将析构函数中两处 `delete` 改为 `delete[]`，与分配方式配对。不涉及接口、逻辑和数值行为变更。
