### Description

本 PR 将 Phi BLAS 的 GEMM 和 GEMV 接口中的矩阵维度及 leading dimension 参数升级为 `int64_t`。当参数超过 `INT_MAX` 时，调用 CUDA 12.3 及以上版本提供的 64 位 cuBLAS API。

#### 修改前 Paddle 不同数据类型的 GEMM 调用

| 数据类型 | 普通尺寸 | 64 位尺寸 |
| --- | --- | --- |
| float | flag 关闭：cublasSgemm；flag 开启：cublasSgemmEx | flag 关闭：不支持；flag 开启：cublasSgemmEx_64 |
| double | cublasDgemm | 不支持 |
| float16 | cublasGemmEx | cublasGemmEx_64 |
| bfloat16 | cublasGemmEx | cublasGemmEx_64 |
| complex64 | cublasGemmEx | cublasGemmEx_64 |
| complex128 | cublasGemmEx | cublasGemmEx_64 |

#### PyTorch 不同数据类型的 GEMM 调用

| 数据类型 | 普通尺寸 | 64 位尺寸 |
| --- | --- | --- |
| float | cublasSgemm |不支持，TORCH_CHECK报错 |
| double | cublasDgemm | 不支持，TORCH_CHECK报错 |
| float16 | cublasGemmEx | 不支持，TORCH_CHECK报错 |
| bfloat16 | cublasGemmEx | 不支持，TORCH_CHECK报错 |
| complex64 | cublasCgemm | 不支持，TORCH_CHECK报错 |
| complex128 | cublasZgemm | 不支持，TORCH_CHECK报错 |

#### 修改后不同数据类型的 GEMM 调用，与Pytorch调用的API对齐

| 数据类型 | 普通尺寸 | 64 位尺寸 |
| --- | --- | --- |
| float | `cublasSgemm` | `cublasSgemm_v2_64` |
| double | `cublasDgemm` | `cublasDgemm_v2_64` |
| float16 | `cublasGemmEx` | `cublasGemmEx_64` |
| bfloat16 | `cublasGemmEx` | `cublasGemmEx_64` |
| complex64 | `cublasCgemm` | `cublasCgemm_v2_64` |
| complex128 | `cublasZgemm` | `cublasZgemm_v2_64` |

#### API修改包括：

- FP32 GEMM 不再根据 Tensor Core flag 在 cublasSgemm 和 cublasSgemmEx 之间切换，统一使用 PyTorch 同类路径采用的 cublasSgemm。
- complex精度下不再调用cublasGemmEx，而是与Pytorch对齐，分别调用cublasCgemm、cublasZgemm。
- 对于所有的数据类型都进行了int64_t支持。

#### Tensor Core Flag 行为

**调整前**：FP32 GEMM 在 `FLAGS_enable_cublas_tensor_op_math=1` 时，会从 `cublasSgemm` 切换到 `cublasSgemmEx`。

**调整后**：`FLAGS_enable_cublas_tensor_op_math` 这个 FLAG **已被删除**（详见下方「BC Breaking」小节）。FP32 GEMM 无论如何都调用：

- 普通尺寸：`cublasSgemm`
- 64 位尺寸：`cublasSgemm_v2_64`

TF32 现在统一由 `FLAGS_cublas_allow_tf32` 控制。它不再影响所调用的 API，只决定使用哪个 cuBLAS handle：

| `FLAGS_cublas_allow_tf32` | FP32 GEMM API | Handle |
| --- | --- | --- |
| 0 | cublasSgemm / cublasSgemm_v2_64 | 默认 cuBLAS handle |
| 1 | cublasSgemm / cublasSgemm_v2_64 | Tensor Core math-mode handle（`gpu_context.cc:727`、`custom_context.cc:327`） |

#### BC Breaking：随 #79601 回移带入的接口 / FLAG 删除

为使 release/3.4 的 BLAS 实现与 develop 对齐，本 PR 随 #79601 一并删除了下列 TF32 相关的开关（与 develop 保持一致，属**有意删除**）：

| 删除项 | 类型 | 迁移方式 |
| --- | --- | --- |
| `paddle.base.core.set_cublas_switch` / `get_cublas_switch` | 公开 Python 接口（v3.2.0 / v3.3.0 / v3.4.0 均已发布） | 改用 `FLAGS_cublas_allow_tf32` |
| `FLAGS_enable_cublas_tensor_op_math` | 环境 FLAG | 改用 `FLAGS_cublas_allow_tf32` |
| `test/legacy_test/test_tf32_cublas.py::TestTF32Switch` | 单测 | 随接口删除 |

**影响面**：

- 3.4.x 用户升级到本补丁版本后，调用 `paddle.base.core.set_cublas_switch` / `get_cublas_switch` 会直接抛 `AttributeError`。
- 此前通过 `FLAGS_enable_cublas_tensor_op_math=1` 打开 TF32 的用户，需改为设置 `FLAGS_cublas_allow_tf32=1`，否则将回落到 `FLAGS_cublas_allow_tf32` 的默认行为（可能与原先不同）。

### CUDA Version Checks and Error Handling

本 PR 同时整理了 GEMM_EX 的版本判断和错误处理：

- 抽取公共的 GemmEx/GemmEx64 实现，减少 FP16、BF16 和 complex 等类型中重复的 cuBLAS 调用代码。
- cublasGemmEx 要求 CUDA 8.0 及以上。
- cublasGemmEx_64 以及其他 64 位 cuBLAS API 要求 CUDA 12.3 及以上，并且当前仅在 Linux 下启用。
- BF16 GEMM 继续要求 CUDA 11.0 及以上以及支持 BF16 的 GPU compute capability。

原有 FP16 路径在 CUDA 8.0 以下会回退到 cublasHgemm。该回退路径与正常的 cublasGemmEx 路径在 API、compute type 和计算语义上并不完全一致。

本 PR 删除这些 CUDA 8.0 以下的分散 fallback。当构建环境不支持所需 API 时，统一抛出明确错误。

---

本 PR 让**批量 GEMM / MatMul** 支持超过 `INT_MAX` 的维度，并把 bmm 在 `N == 1` 时的操作数布局对齐 PyTorch。它是 #79601（单次 GEMM/GEMV 的 int64 化）的后续：批量路径此前要么直接 `PADDLE_THROW` 拒绝，要么在 `static_cast<int>` 处静默截断。

改动的核心取舍是**「绝大多数 cuBLAS 调用形式保持不变」**：所有既有的 cuBLAS 调用实参文本逐字保留，64 位分派与 N==1 布局都通过调用之前的局部变量实现。

#### 1. 接口加宽（`blas.h`）

以下签名由 `int` 改为 `int64_t`：

- `Blas<DeviceContext>::MatMul(int64_t M, int64_t N, int64_t K, const T* A, const T* B, T* C)`
- 指针数组版 `BatchedGEMM(... int64_t M, int64_t N, int64_t K, ..., int64_t batchCount)`
- `BatchedGEMMWithHead(... int64_t W1, int64_t H1, int64_t W2, int64_t H2, ..., int64_t batchCount, ...)`
- `MatMulWithHead` / `MatMulWithHeadGradImpl` 的 `head_number`
- MKLML 打包 API：`GEMM_ALLOC`、`GEMM_PACK`、`GEMM_COMPUTE`（含其 `lda/ldb/ldc/ld`）

#### 2. GPU：`> INT_MAX` 走 cuBLAS 64 位 API（`blas_impl.cu.h`、`dynload/cublas.h`）

每个 strided / 指针数组重载里统一引入

```cpp
const bool requires_64_bit_blas = M > INT_MAX_VALUE || N > INT_MAX_VALUE ||
                                  K > INT_MAX_VALUE ||
                                  batchCount > INT_MAX_VALUE;
```

- 为真 → 走 `_64` 入口；为假 → 走原来的 32 位入口，实参文本不变，只是用 `static_cast<int>` 收窄（由上面的条件保证不会溢出）。
- `batchCount` 也纳入判断：32 位 strided API 的 `strideA/strideB/strideC` 形参本身是 `long long`，原样传递不会溢出，但 `batchCount` 是 `int`。
- 新增 `CUBlas<float/double/float16/complex64/complex128>::GEMM_STRIDED_BATCH_64` 共 5 个成员（bf16 没有 strided 主模板实例化，其批量路径是显式全特化，直接 dynload `cublasGemmStridedBatchedEx(_64)`）。
- 用到的 64 位符号：`cublas{S,D,H,C,Z}gemmStridedBatched_64`、`cublasGemmStridedBatchedEx_64`、`cublasGemmBatchedEx_64`、`cublas{S,D,C,Z}trsm_v2_64`。
- 这些声明与对应实现都包在 `CUDA_VERSION >= 12030 && defined(__linux__)` 里；条件不满足时抛出明确的 `Unimplemented`（而不是截断）。
- 顺带补齐了两处算力门控（HEAD 已存在的不一致）：bf16 strided 重载补 `cc >= 80`，fp16 的 `GEMM(bool transA, ...)` 补 `cc >= 53`。

#### 3. GPU：`N == 1` 的操作数布局对齐 PyTorch

行主序的批量 GEMM 交给列主序 cuBLAS 时，通常要交换 A/B。但 PyTorch 在 `N == 1` 时用的是**不交换**的形式（`baddbmm_out_cuda_impl` 按 out 的 stride 选择，`cublasAdjustLdLevel3` 在 `n <= 1` 时把 `ldc` 修正为 `max(m, 1)`）。

Paddle 侧不新增调用分支，而是在调用前就地改写入参：

```cpp
if (N == 1 && !FLAGS_use_legacy_gemm) {
  ldc = std::max<int64_t>(M, 1);
  std::swap(M, N);
  std::swap(lda, ldb);
  std::swap(strideA, strideB);
  std::swap(A, B);
  const cublasOperation_t cu_trans_a = cuTransA;
  cuTransA = (cuTransB == CUBLAS_OP_T) ? CUBLAS_OP_N : CUBLAS_OP_T;
  cuTransB = (cu_trans_a == CUBLAS_OP_T) ? CUBLAS_OP_N : CUBLAS_OP_T;
}
```

同一段插在 6 个 strided 重载里，因此**下面的 cuBLAS 调用一个字都不用动**。`N == 1` 时列主序 `M×1` 与行主序 `M×1` 的内存序相同，交换是安全的；四种 trans 组合下 `lda/ldb/ldc` 都满足列主序最小 ld 要求。

同时删除了 HEAD 里一个失效的重复分支：它的条件是 `N == 1 && ldc >= std::max<int64_t>(1, M) && ...`，而同函数里 `ldc` 初值就是 `N`，条件退化为 `M <= 1 && N == 1`，实际上只对 `[b,1,K] @ [b,K,1]` 生效；被它包住的调用文本保留（只是去掉了外层 `{}`，整体左移两格）。

#### 4. CPU：显式收窄 + int64 指针运算（`blas_impl.h`）

- 删除 `Blas<CPUContext>::BatchedGEMM` 顶部那句 `"CPU BatchedGEMM only supports ... not larger than INT_MAX"` 的整块 `PADDLE_THROW`，改为在真正需要 32 位参数时用 `detail::to_blas_int(M, "BatchedGEMM M")` 收窄 —— 报错信息会带上具体是哪个维度、期望值、实际值，而不是一句笼统的 `Unimplemented`。
- `const int64_t strideC = M * N;` 取代 `&C[k * M * N]`：原写法是 `int * int`，`M * N` 稍大（例如 `M = N = 50000`，即 2.5e9）就会溢出，与是否支持 int64 无关，**这是 CPU 上的一个真实正确性问题**。
- `MatMulWithHead` / `BatchedGEMMWithHead` 里的 `sub_matA_offset` / `sub_matB_offset` / `sub_matC_offset` / `lda/ldb/ldc` / 循环下标全部提到 `int64_t`（head 切分后每个子 GEMM 的维度仍然是小的，但**偏移量**会落在原张量的大坐标上）。
- `CBlas<T>` 的 `GEMM_ALLOC/GEMM_PACK/GEMM_COMPUTE` 保持 `int`，由外层 `to_blas_int` 收窄。

#### 5. MatMul 上层的守卫清理（`matmul_kernel_impl.h`）

- case 9（`GEMV(y_batch_size * N, ...)`）与 case 11（`GEMM(x_batch_size * M, ...)`）删除 `PADDLE_ENFORCE_LE_INT_MAX`。检查没有消失，而是下沉到 BLAS 层：`Blas<GPUContext>::GEMV` 内部 `if (M > INT_MAX || N > INT_MAX)` 走 `GEMV_64`（老 CUDA 干净抛出），`GEMM` 走 `requires_64_bit_blas`，CPU 侧走 `to_blas_int`。这两处从「拒绝」变成「支持」。
- case 14（广播 + 指针数组）的守卫**保留**，只是上移到 `Out->ResizeAndAllocate` 之前，避免超大批次先分配输出再报错。条件是 `is_broadcast_dims && x_batch_size != 1 && y_batch_size != 1`，与 `else` 分支（case 14）的进入条件完全等价（分支链：case 8 → 9/10 → 11/12 → 13 → else）。
- `MatMulFunctionImplWithCublasLt` 的 case 9/11 守卫删除是另一回事：`blaslt::Run` 的形参本来就是 `int64_t`，且 `cublasLtMatrixLayoutCreate` 接收 `uint64_t rows/cols`，原来的 `int` 守卫会把合法的 64 位尺寸拒掉。该函数里 `LE_INT_MAX(out_batch_size)` 与 batch 属性的 `static_cast<int>` 保持原样（`CUBLASLT_MATRIX_LAYOUT_BATCH_COUNT` 本身是 int32）。

#### 6. HIP（`blas_impl.hip.h`，顺带）

- fp16 的 `GEMM` 在 `compute_type == rocblas_datatype_f16_r` 时仍然把 `float` 的 alpha/beta 传进去，而 rocBLAS 是按 computeType 宽度读标量的，等于读了 4 字节里的前 2 字节。现在该分支改用转换后的 `phi::float16` 标量（`t_alpha`/`t_beta`），非 fp16 组合行为不变。
- 5 个 `BatchedGEMM` 重载里 `"Hip BatchedGEMM not supported for large tensor size"` 的 `PADDLE_THROW` 换成 `detail::to_blas_int` 显式校验，与 CUDA 路径的报错风格一致（HIP 没有 64 位入口，超限仍然会抛，只是信息更明确）。

#### 7. 测试

- `test/cpp/phi/kernels/test_math_function.cc`：
  - `batched_gemm_matmul_int64_dimensions`：`MatMul` 与指针数组 `BatchedGEMM` 走 int64 形参，结果都是 `{4, 5, 10, 11}`。
  - `batched_gemm_matmul_reject_invalid_dimensions`：`batchCount`/`M` 取 `INT_MAX + 1` 时抛 `EnforceNotMet`。
- `test/cpp/phi/kernels/test_math_function.cu`：
  - `batched_gemm_strided_column_output`：`BatchedGemmStridedTest` 覆盖 `(batch, m, n, k)` = `(3,5,1,4)`、`(2,1,1,6)`、`(3,5,2,4)` × 四种 `trans_a/trans_b` 组合 × float/double，与 host 参考实现比对。其中 `n == 1` 的配置即第 3 节的未交换布局，`n == 2` 的配置作为交换布局的回归护栏。
