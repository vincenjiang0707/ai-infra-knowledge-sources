# [PR #79798] [compat] Resolve a scoped spec once instead of re-entering the finder

### PR Category

### Description
`TorchProxyMetaFinder._find_spec_for_specific_module` looks up the real spec with `importlib.util.find_spec` while the proxy is disabled, which is what is meant to keep the finder out of its own lookup. That only holds while the finder is registered **once**: `enable_compat` inserts it into `sys.meta_path` unconditionally, so nested guards leave duplicates behind, while `disable_compat` drops a single occurrence. With a duplicate left in place the lookup re-enters the finder for the very same name and restarts the whole resolution, and a name that has no spec at all never converges, so the lookups compound.

Measured with a probe for a missing submodule of a package in the enabled scope:

| finder registrations in `sys.meta_path` | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| lookups per probe, before | 1 | 4 | 15 | 64 |
| lookups per probe, after | 1 | 2 | 3 | 4 |

Every lookup toggles the proxy, and every toggle walks all of `sys.modules` three times to move `torch*` in and out of the shadow table, so the cost is `O(lookups * len(sys.modules))` -- it also grows as the program imports more, because that is what makes `sys.modules` bigger. Importing one package inside a scoped guard with 7 registrations already in place expanded 7 probes for a missing module into 13699 lookups and ~90M module-name comparisons: **37.9s, of which 0.5s was the actual import work**.

**Fix**: suppress the finder for the name it is currently resolving, so the outer lookup finishes instead of starting over. Each registered copy is now asked exactly once. The proxy is still disabled around the lookup and `exec_module` still runs under its own guard, so the resulting specs, loaders and `__enable_torch_proxy__` marks are unchanged.

Verified on that same package -- identical submodule set and identical set of modules marked with `__enable_torch_proxy__` before and after:

- imported inside a scoped guard late in the process (`len(sys.modules)` = 4732): **37.9s -> 1.2s**
- the same package imported eagerly at startup: **6.6s -> 2.3s**

Tests: `test/compat/test_torch_proxy.py::TestTorchProxySpecLookupReentrancy`. A missing submodule of a scoped package is now looked up once per registered copy of the finder (2 copies cost 4 lookups before this change), and an existing submodule is still resolved by the first copy and still loaded through the proxy loader.

Note: the duplicate registrations are a defect of their own -- `enable_compat` should not insert a copy that is already registered, and `disable_compat` cannot undo nested enables by removing a single occurrence. That is left alone here because fixing it changes the enable/disable bookkeeping, whereas this change makes the lookup correct regardless of how many copies are registered. Happy to follow up in a separate PR.

### 是否引起精度变化
否

Only import-time module resolution changes. No kernel, no computation and no reduction order is touched.
