### PR Category

### PR Types
Bug fixes

### Description

`GetGpuLaunchConfig3D` 在计算 `block_z` 时，只受「总线程预算」`max_threads`（= 256）约束，没有受硬件「单维度上限」`maxThreadsDim[2]`（= 64）约束。

当输出空间尺寸退化时（`out_h * out_w <= 3`，即 `block_x * block_y < 4`），整个剩余线程预算会被推到 z 维，使 `blockDim.z` 达到 128 或 256，超过 64。驱动在 launch 时校验 block 维度并直接拒绝启动，返回 `cudaErrorInvalidValue`。

受影响的调用点：

- `paddle/phi/kernels/gpu/interpolate_kernel.cu` 的 `nearest` NCHW 前向（`GetGpuLaunchConfig3D` 调用处）
- `paddle/phi/kernels/gpu/interpolate_kernel.cu` 的 `bilinear` NCHW 前向
- `paddle/phi/kernels/gpu/interpolate_grad_kernel.cu` 的 `bilinear` NCHW 反向

最小复现（纯单算子，无需端到端训练）：

```python
import paddle
import paddle.nn.functional as F

# NCHW, float32, 输出空间退化为 1x3
x = paddle.zeros([1, 768, 52, 52]).astype("float32")
y = F.interpolate(x, size=[1, 3], mode="bilinear", align_corners=False)
paddle.base._check_last_cuda_error()  # 此处抛出 cudaErrorInvalidValue
```

实测触发边界（`n * c = 768`）：`out_h * out_w <= 3` 必崩，等价于 `(out_h == 1 && out_w <= 3) || (out_w == 1 && out_h <= 3)`，且要求 `n * c > 64`。例如 `(1,1)`、`(1,2)`、`(1,3)`、`(2,1)`、`(3,1)` 崩溃，而 `(1,4)`、`(4,1)`、`(2,2)`、`(1,63)`、`(42,63)` 正常。

修复方式：

把 `block_z` 钳制到硬件 z 维上限 64。

需要说明的是，**总线程数上限（1024）本来就已经满足**，无需额外限制：

```
block_x * block_y * block_z <= block_x * block_y * floor(max_threads / (block_x * block_y))
                             <= max_threads
                             = min(256, maxThreadsPerBlock)
                             <= maxThreadsPerBlock
```

即 `max_threads` 本身已经用 `GetMaxThreadsPerBlock()` 兜过底，缺的只是`block.z`的**单维度**上限这一条。

正确性：

kernel 通过 grid-stride 循环覆盖 `n * c`（`nc_stride = blockDim.z * gridDim.z`），`blockDim.z` 变小只会让 `gridDim.z` 相应变大（`DivUp(num_img, blockDim.z * 4)`），覆盖范围不变。

### 是否引起精度变化
否

`blockDim.z` 只影响线程数分配，kernel 的 grid-stride 循环仍覆盖全部输出元素，计算结果与修复前完全一致。
