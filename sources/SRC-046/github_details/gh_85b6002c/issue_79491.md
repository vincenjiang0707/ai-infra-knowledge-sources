### bug描述 Describe the Bug

- **Affected component:** `paddle/phi/kernels/cpu/embedding_kernel.cc` (`EmbeddingCPUFunctor::apply`)
- **Public API:** `paddle.nn.Embedding` / `paddle.nn.functional.embedding` (with `padding_idx` set)
- **Severity:** High
- **CVSS 3.1:** 8.2 (`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:H`)
- **CWE:** CWE-125 Out-of-bounds Read
- **Status:** Confirmed on `paddlepaddle==3.3.0` (heap disclosure + SIGSEGV) and via AddressSanitizer
- **Affected versions:** v3.3.0 release tag **and current `develop` HEAD** (verified)

### Affected Component
```
File: paddle/phi/kernels/cpu/embedding_kernel.cc   (line 53 on develop HEAD)
Function: phi::EmbeddingCPUFunctor<T, Context>::apply
```

### Vulnerable Code
```cpp
for (int64_t i = 0; i < ids_numel; ++i) {
  if (padding_idx_ == kNoPadding && ids[i] != padding_idx_) {   // <-- gate
    PADDLE_ENFORCE_LT(ids[i], row_number, ...);   // range check runs ONLY
    PADDLE_ENFORCE_GE(ids[i], 0, ...);            //   when no padding_idx
  }
}
...
for (int64_t i = 0; i < ids_numel; ++i) {
  if (padding_idx_ != kNoPadding && ids[i] == padding_idx_) {
    memset(output + i * row_width, 0, row_width * sizeof(T));
  } else {
    memcpy(output + i * row_width,
           table + ids[i] * row_width,            // <-- OOB: ids[i] unchecked
           row_width * sizeof(T));
  }
}
```

### Root Cause
The id-range validation is incorrectly scoped: it is nested inside
`if (padding_idx_ == kNoPadding && ...)`. `kNoPadding` is `-1`, so as soon as an embedding
layer is created with **any** `padding_idx` (e.g. the ubiquitous `padding_idx=0` for NLP
models), the bounds check is skipped for every id, and the copy loop indexes the weight table
with an attacker-controlled `ids[i]` (`int64`). Only the padding-row *zeroing* should be
conditional on `padding_idx`; the range check must be unconditional.

### Proof of Concept (public API, `paddlepaddle==3.3.0`)

**(a) Heap memory disclosure** — an out-of-range id returns raw heap bytes past the table:
```python
import paddle
paddle.set_device("cpu")
emb = paddle.nn.Embedding(16, 8, padding_idx=0)     # valid ids: 0..15
out = emb(paddle.to_tensor([[40]], dtype="int64"))  # id 40 is out of range
print(out.numpy().reshape(-1))
# -> [1.11e+27, 1.36e-14, 2.81e+23, 1.46e-19, 0.0, 7.14e+31, 0.0, 0.0]
#    (uninitialised heap contents beyond the weight matrix)
```

**(b) Remote crash (SIGSEGV)** — a large id dereferences an unmapped page:
```python
emb = paddle.nn.Embedding(16, 8, padding_idx=0)
emb(paddle.to_tensor([[10**9]], dtype="int64"))
```

### How to Reproduce
1. `pip install paddlepaddle==3.3.0`
2. Run snippet **(a)** → an out-of-range id (40) returns a vector of raw heap values instead
   of raising — heap disclosure.
3. Run snippet **(b)** → the process crashes with SIGSEGV in `EmbeddingCPUFunctor::apply`.
4. (Optional, deterministic) Compile the kernel-logic excerpt with AddressSanitizer
   (`g++ -fsanitize=address ...`) or reproduce **(b)** on a `cmake -DWITH_ASAN=ON` build to
   obtain the in-binary trace.

### Impact / Real-World Scenario
Embedding layers turn caller-supplied token ids into vectors. Any service that embeds
externally-influenced ids (text classification / retrieval / recommender inference that accept
tokenized input, or pipelines where a tokenizer/vocabulary mismatch can emit ids ≥
`num_embeddings`) is exposed:
- **Confidentiality (High):** the output vector returns raw heap bytes adjacent to the weight
  table — potentially other tensors/buffers/secrets in the process heap.
- **Availability (High):** a single crafted id crashes an inference worker.
- The attacker-controlled read offset (`ids[i] * row_width`, `ids[i]` up to `int64`) is a
  flexible OOB-read primitive.

### Suggested Remediation
Make the range check unconditional:
```cpp
for (int64_t i = 0; i < ids_numel; ++i) {
  PADDLE_ENFORCE_GE(ids[i], 0, ...);
  PADDLE_ENFORCE_LT(ids[i], row_number, ...);
}
```
Keep only the padding-row zeroing conditional on `padding_idx`. Apply the same fix to the
GPU/XPU embedding kernels, which share the pattern.

### Threat-model clarification — this is an untrusted-**input** bug, not a model-poisoning bug

Adding an explicit attacker/victim scenario, since the distinction is important for triage and severity: **this vulnerability does not require loading an attacker-supplied or "abnormal-channel" model.** It is reachable with the operator's own, normally-loaded weights.

**Why the trust boundary here is the request, not the model**
- The embedding table is a legitimate, trusted weight file. Loading it through normal channels is exactly what *arms* the bug: the vulnerable configuration is the ubiquitous `padding_idx=0`. On `develop` HEAD the id range check (`PADDLE_ENFORCE_LT` / `PADDLE_ENFORCE_GE`) is nested under `if (padding_idx_ == kNoPadding && ...)` in `embedding_kernel.cc` — so setting **any** `padding_idx` disables bounds validation for every id.
- The attacker-controlled surface is the **inference input `ids`** — request data — which then indexes the table as `table + ids[i] * row_width` with no check.

**Attacker → victim scenario**
- **Victim:** a remotely-reachable inference service built on Paddle — an embedding/retrieval microservice, semantic-search backend, recommender item-lookup, or any text model — running a normally-loaded embedding weight with `padding_idx=0`.
- **Attacker:** an unauthenticated remote client of that service (`AV:N / AC:L / PR:N / UI:N`).
- **Trigger:** a request producing an id `>= num_embeddings`.
  - *Primary (clean) case:* any endpoint that accepts token/item **ids directly** — very common for embedding, retrieval, and recommender services ("return the embedding for item id X").
  - *Secondary case:* tokenizer/vocabulary drift, where a checkpoint's table is smaller than the tokenizer's id space (resized vocab, mismatched checkpoint), so ordinary text yields an out-of-range id.
- **Result:**
  - **Confidentiality (C:H):** the returned vector is raw heap memory located `ids[i] * row_width * sizeof(T)` bytes past the weight table — adjacent tensors, buffers, or process memory. In a shared/multi-tenant worker this can disclose other requests' data.
  - **Availability (A:H):** a large id dereferences an unmapped page → SIGSEGV → worker crash / DoS.
  - `ids[i]` is a 64-bit, attacker-chosen offset, so this is a **flexible relative OOB-read primitive**, not a fixed single-slot overread.

**Evidence already in this issue reproduces exactly this** — on a stock `paddlepaddle==3.3.0` wheel with a normal model, no crafted weight file:
- heap disclosure via the public `paddle.nn.Embedding(..., padding_idx=0)` API,
- SIGSEGV with Paddle's own C++ traceback naming `EmbeddingCPUFunctor::apply`,
- AddressSanitizer `heap-buffer-overflow in memcpy` (`READ of size 32 ... located 64 bytes after` the allocated region).

In short: this is the same category as any out-of-bounds read reachable from untrusted network input in a lookup routine. Model provenance is irrelevant — the model is the victim's own; only the request payload is hostile.

Fix submitted upstream in #79507 (make the range check unconditional; keep only the padding-row *zeroing* gated on `padding_idx`). The same pattern should be mirrored in the GPU/XPU embedding kernels.
