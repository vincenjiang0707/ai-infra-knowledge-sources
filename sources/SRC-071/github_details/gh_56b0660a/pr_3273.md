## 正文

## Summary

I added a compile-time error for `reduce_max`, `reduce_min`, and `reduce_absmax` when `nan_propagate=True` requests an unsupported output dtype. The diagnostic names the operation, supported output types, and actual dtype. This implements the explicit-rejection option in #3270.

The check belongs to the native `ReduceOp` constructor, which owns the accumulator dtype contract across local reductions, fragment reductions, and write-back accumulation. Float16 and bfloat16 retain their existing backend-specific support. Calls with NaN propagation disabled retain their existing behavior.

The regression matrix exercises all three operations, both `clear` settings, both flag values, and five output dtypes through the compiler's layout-inference path. The SM100 packed-reduction regression now expects the same diagnostic for float32.

## Validation

- Rebuilt native libraries on macOS with the CPU and Metal backends.
- Restoring the original constructor and rebuilding produced 18 failures and 42 passes in the new regression matrix. Rebuilding the candidate produced 60 passes.
- `python -m pytest testing/python/language/test_tilelang_language_reduce_maxmin_nan.py testing/python/cuda/test_cuda_f32x2_intrinsics.py -q`: 68 passed, 101 CUDA-dependent cases skipped.
- `python -m pytest testing/python/cpu/test_tilelang_cpu_reduce.py -q`: 34 passed.
- The broader language reduction suite reached CUDA-only tensor creation and unavailable Metal reduction implementations in this environment. CUDA numerical execution remains pending.
- Repository formatting and `git diff --check` passed.

Fixes #3270.
