# [PR #3108] [Bugfix][Transform] Make shared-memory offset assignment deterministic

## 正文

## Symptom

Compiling the **same kernel** twice can produce different (semantically equivalent) CUDA: which merged-arena slot each shared buffer gets — most visibly which AllReduce `workspace` alias each reduction uses — flips between runs. A reducer-heavy kernel compiled 5 times produced **5 distinct device sources**. Running under `setarch -R` (ASLR disabled) made all runs identical, pinning the cause on heap-pointer-ordered iteration: `std::hash<const void*>` is the pointer value, so any `unordered_map` keyed by node addresses iterates in an order that changes with heap layout.

This is harmless for correctness (liveness constraints hold under any processing order; only the pairing of buffers to equivalent slots permutes), but it breaks reproducible builds and any byte-identical-codegen validation methodology, and it makes diffing generated code across compiles useless.

## Root causes (both in `MergeSharedMemoryAllocations`)

1. **Kill-point reordering iterated the pointer-keyed `event_map_`** (`unordered_map<const Object*, EventEntry>`). The traversal order decides the order in which moved kill points are appended to their target statements, which decides the order freed slots re-enter the free list, which decides which slot the next allocation grabs. Fixed by walking the deterministic linearized statement sequence instead.

2. **Every sort in the planner tie-broke by `name_hint`, which is not unique.** Every AllReduce scratch buffer is literally named `workspace` (one test kernel has 11 of them), and double-buffered stages share their buffer's name. Fully-tied groups (same liveness start, same size, same name) fell back to `std::sort`'s unspecified order on unordered_map-derived input. Fixed by recording each allocation's IR-visit discovery index in `AllocateCollector` and using it as the final tie-break in `PlanMemory`, `LinearScanPack`, `MakeAliasBindings`, and `PlanSequentialLayout` — every comparator is now a total order.

## ODR landmine found along the way

`lower_thread_allreduce.cc` defines a *different* `tvm::tl::AllocateCollector`. Both classes had external linkage, so the linker deduplicated their vague-linkage inline members across translation units — an ODR violation that stayed silently benign only while the two layouts happened to match, and corrupted the collector (garbage `unordered_map` state → `std::bad_alloc`) the moment this patch added a field to one of them. The collector here now lives in an anonymous namespace.

## Validation

- The 5-distinct-hashes reproducer now yields **1 identical hash across 8 runs** with ASLR enabled; two other previously-flipping kernels are likewise stable (3/3 identical each).
- Language suite: 1172 passed, 137 skipped. reducer_v2 suite: 75 passed. All 17 downstream reducer-heavy production kernels compile and pass numerics.

Discovered while validating tile-ai/tvm#68 (byte-identical codegen check kept flipping); independent of that PR.
