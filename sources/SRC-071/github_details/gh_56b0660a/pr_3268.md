# [PR #3268] [BugFix][CMake] Keep an SDK path given through the backend environment variables

## 正文


## Summary

`USE_CUDA`, `USE_ROCM`, `USE_METAL` and `USE_LLVM` are documented to take a path as well as a boolean — `TILELANG_BACKEND_DOC_CUDA` reads `Enable CUDA backend (ON/OFF/or CUDA SDK path)` — and a path works when it arrives through `-DUSE_CUDA=<path>`. Through the environment it does not: the value is coerced to `ON` or `OFF` by `if($ENV{USE_CUDA})`, and `if()` treats a string that is not a boolean constant as a variable name. `/opt/cuda` names no variable, so the test is false and the backend is turned off.

Nothing reports this. The configure step succeeds, the build succeeds, and the library it installs has no object from `src/cuda` in it. The first sign is at run time, far from the cause: `AttributeError: module 'tilelang.cuda._ffi_api' has no attribute 'AnnotateDeviceBoundTmaCopies'`.

The value now reaches the cache variable as written, which is what `-D` already does. Booleans are unaffected, because the variable is read back with `if(USE_CUDA)` and a defined variable is tested against its value rather than re-read as a name:

| `USE_CUDA=` | before | after |
|---|---|---|
| `1` | ON | true, value `1` |
| `ON` | ON | true, value `ON` |
| `OFF` | OFF | false, value `OFF` |
| `0` | OFF | false, value `0` |
| `/opt/cuda` | **OFF** | **true, value `/opt/cuda`** |

The four backends carried four copies of the same block, so the fix is one loop over the `TILELANG_BACKENDS` list the file already defines and already loops over three times above.

## Validation

The table above is `cmake -P` on CMake 4.4.3, each row a separate `set(ENV{...})`.

A/B on one GH200 (sm_90, aarch64), CUDA 13.1, configure only, same tree at `6679f913` and the same `USE_CUDA=<sdk path>` in the environment, the patch the only difference:

| | `CUDA Backend is enabled` | configure stops at |
|---|---|---|
| before | absent | `FindZ3`, on the no-CUDA path |
| after | **present** | `Could NOT find CUDAToolkit (missing: CUDA_CUDART)`, inside `src/cuda` |

The run after the patch still stops, one stage later and for a different reason: on aarch64 `find_package(CUDAToolkit)` looks for the runtime under `targets/<arch>/lib`, which a toolkit laid out with `include` and `lib64` at its root does not have. That is a separate problem and not what this changes; the discriminator here is whether the CUDA backend is entered at all.

Reading `USE_CUDA` back out of `CMakeCache.txt` does not show the difference — it says `OFF` either way. The assignment is a directory-scope variable that shadows the cache entry, so the cache keeps the `option()` default. The message is the signal.
