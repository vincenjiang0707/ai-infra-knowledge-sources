# [PR #3239] [BugFix][CUDA][RNG] Harden initialization semantics and default sequence IDs

## 正文

## Summary

Three related defects in the CUDA RNG surface:

- `rng_init(seq=None)` derived its default sequence from `threadIdx.x` and
  `blockIdx.x` only, so every thread that differed only in `y`/`z` shared one
  curand subsequence and produced identical draws.
- `rng_init` is a side-effect-only intrinsic, but binding its result produced
  `void state = ;`, which nvcc rejected as an incomplete type.
- A draw with no `rng_init` anywhere in the function emitted `curand(&)`,
  turning a TileLang semantic error into an nvcc syntax error.

Fixes #2625
Fixes #3029
Fixes #3034

## Changes

`tilelang/language/eager/builder.py`
- reject binding a value-less expression in `bind_immutable`, so `rng_init` and
  any other side-effecting intrinsic is diagnosed by name and by the offending
  expression before lowering.

`tilelang/cuda/language/random.py`
- add `_default_rng_sequence()`: a row-major linear id over every launched
  thread and block dimension. Dimensions that were not launched have extent 1
  and contribute nothing, so the historical 1-D id
  `threadIdx.x + blockIdx.x * blockDim.x` is unchanged.
- correct the `seq` and `Returns` documentation: `rng_init` is a statement and
  its result is not a state handle.

`src/cuda/codegen/codegen_cuda.cc`
- validate RNG state once per function in the existing `AddFunction` pre-scan:
  if the body contains an `rng_rand` / `rng_rand_float` but no `rng_init`,
  fail with an intentional TileLang error. Deliberately *not*
  control-flow-sensitive: an `rng_init` inside a runtime branch still counts.
- clear the per-function curand state name and type, so a draw can never
  reference the state registered by an earlier function of the same module.
- add `VisitStmt_(const BindNode *op)`, rejecting a bound `rng_init` call as a
  backstop for paths that bypass the eager builder (it previously produced
  `void state = ;`). (`Bind` is this tree's name for
  the `LetStmt` node; the override matches codegen_py.cc and
  codegen_cutedsl.cc.)

`src/cuda/codegen/codegen_cuda.h`
- declare the new `BindNode` visitor.

`testing/python/language/test_tilelang_language_rand.py`
- 15 new cases: 2-D thread and 2-D grid default-sequence coverage, 1-D layout
  and explicit-`seq` controls, all five producer shapes with and without
  `rng_init`, and the void-binding rejection. Because the frontend now rejects
  the void bind first, that regression accepts either diagnostic (frontend
  "value-less expression" or codegen "cannot be bound to variable").

**Explanation**

The PR satisfies `#2625`. `_default_rng_sequence()` folds thread and block bindings across all launched dimensions and preserves the one-dimensional layout. Tests cover thread-y, block-y, explicit sequences, and one-dimensional behavior. The PR satisfies `#3029`. `rng_init` is documented as side-effect-only, eager binding rejects value-less expressions, CUDA codegen rejects direct bindings, and bare initialized calls remain covered. The PR satisfies the no-initialization cases in `#3034` for all listed producer forms and retains initialized positive controls. However, the `#3034` requirement says that a producer must have a preceding `rng_init` in the same function. `AddFunction` sets `has_rng_init` from any call in the function and checks only `!has_rng_consumer || has_rng_init`. It does not detect a producer that appears before the first `rng_init`.

**Resolution**

Enforce the required ordering for `rng_rand` and every `rng_rand_float` variant, or define and implement an equivalent valid initialization rule. Add a regression test for a producer before `rng_init`. Keep the existing no-init diagnostics and initialized positive controls.
