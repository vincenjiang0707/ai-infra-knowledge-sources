# [PR #3280] [Bugfix] Fix candidate buffer overflow in deepseek_v32 topk selector

source: https://github.com/tile-ai/tilelang/pull/3280
state: open | updated: 2026-09-25T07:33:57Z
labels: 

## 正文

## Summary

`tl_topk` in `examples/deepseek_v32/topk_selector.py` stages radix candidates in a fixed shared buffer:

```python
s_input_idx = T.alloc_shared([2, 4096], T.int32)  # assume the threshold bucket size after first pass is less than 4K
```

Nothing bounds the threshold bucket chosen by the first radix pass to 4096 elements. Whenever more candidates land there — e.g. FP32 scores that share their low 10 mantissa bits (#1351), or simply `torch.ones(...)` with a small enough topk — the atomic appends write past the end of the buffer and the kernel crashes with `CUDA_ERROR_ILLEGAL_ADDRESS`.

## Changes

- `tl_topk_impl` now takes a `workspace: T.Tensor[(batch, 2, seq_len), T.int32]` argument. All `s_input_idx[...]` accesses become `workspace[bx, ...]`, and the fixed `SMEM_INPUT_SIZE` shared allocation is removed, so both radix buffers are bounded by `seq_len`.
- The `tl_topk` wrapper allocates the workspace with `torch.empty((batch, 2, seq_len), dtype=torch.int32, ...)` and forwards it. The public `tl_topk()` signature is unchanged.
- Tie-breaking among equal values is unchanged: the kernel never guaranteed a stable order, and this PR does not change that; only the overflow is fixed.

## Validation

RTX 4090D, CUDA 12.1, torch 2.6.0+cu124, tilelang 0.1.14 (wheel):

- New regression test `testing/python/issue/test_tilelang_issue_1351.py` — 13 parameterized cases: low-mantissa-bit inputs (positive and negative), all-equal inputs at seq_len 4095/4096/4097/32768, boundary tie buckets (exactly topk-1 larger values followed by an oversized tied bucket), partial `[starts, ends)` ranges, and random inputs. Selected values are compared against a masked `torch.topk` reference with `rtol=0, atol=0` (exact FP32 match, order-independent). **13/13 passed.**
- `compute-sanitizer --tool memcheck`: on the original kernel the first regression case (low-10-mantissa-bit input) already trips the sanitizer — `ERROR SUMMARY: 129 errors` — and the launch fails with `CUDA_ERROR_LAUNCH_FAILED` (the run stops there); the patched kernel passes the full 13-case matrix under the sanitizer with `ERROR SUMMARY: 0 errors`.
- Kernel-only latency (CUDA events, median of 5 interleaved runs):

| input shape | topk | before | after |
|---|---|---|---|
| (2, 32768) | 2048 | 23.0 µs | 25.5 µs |
| (64, 32768) | 2048 | 24.7 µs | 26.4 µs |
| (64, 8192) | 256 | 21.0 µs | 23.0 µs |

  +7-10% from global-memory candidate atomics; the wrapper additionally pays one `torch.empty` (~8 µs) for the workspace (batch × 2 × seq_len × 4 B, e.g. 16 MB at batch=64, seq_len=32768).
- `ruff check` / `ruff format --check` / `codespell` clean on both files (ruff 0.16.8, one minor version above the 0.16.6 CI pin).

Fixes #1351

### Arthur031221 · 2026-09-27

I ran this on an RTX 5090 (sm_120, driver 610.43.02, torch 2.11.0+cu130). Both copies of `examples/deepseek_v32/topk_selector.py`, main at 7a5f446f and this branch at f07dfece, were compiled by the tilelang 0.1.14 wheel from PyPI, not a source build of main. The fix looks right to me. The rest is about the test and the cost.

On main, `torch.ones` and the low-10-bit input from #1351 (batch 2, seq_len 32768, topk 2048) both hit an illegal memory access. On this branch both return the same values as `torch.topk`, with 0 errors under `compute-sanitizer --tool memcheck`. The new test passes 13/13 here. Against main's file, one process per case, 8 of 13 fail: 7 with the illegal access, and `low_bits-4097-4097` on the uniqueness assert (duplicate indices).

One case doesn't test what it looks like it tests. `equal-4097-256` passes on main. Under memcheck the same shape on main (`torch.ones`, batch 2, 4097, topk 256) shows 2 invalid `__shared__` writes, one per row, and the launch fails. Without memcheck it returns correct indices, so here, without the sanitizer, that case doesn't catch the overflow.

Cost, from `run_regression_perf` (cupti), two interleaved rounds of 3 calls. The six numbers in each cell are within 0.0006 ms:

| batch, seq_len, topk | main | this branch | shared-first variant (below) |
|---|---|---|---|
| 64, 32768, 2048 | 0.0283 ms | 0.0298 ms (+5%) | 0.0298 ms (+5%) |
| 64, 131072, 2048 | 0.0761 ms | 0.0838 ms (+10%) | 0.0808 ms (+6%) |
| 1, 131072, 2048 | 0.0615 ms | 0.0694 ms (+13%) | 0.0656 ms (+7%) |

Main's kernel with only the `workspace` argument and `torch.empty` added measures within 0.0002 ms of main in every row, so the extra kernel argument by itself doesn't change kernel time (cupti doesn't see the `torch.empty`).

The last column keeps the 4096-entry shared buffer and writes to `workspace` only for positions >= 4096. It passes the same 13 cases, with 0 memcheck errors on the #1351 input and `torch.ones` at 4097 and 32768. On the three benchmark inputs it never writes to `workspace` (largest first-pass threshold bucket 961, 2276 and 2219; a sentinel-filled `workspace` comes back untouched). It still pays all of the +5% at 32768 and more than half of the gap at 131072, so on these shapes keeping candidates in shared memory doesn't by itself win the time back. I don't know where the variant's cost comes from, and I haven't separated how much of this branch's cost is the workspace loads and stores themselves. I have no sm_90 numbers.

<details><summary>shared-first variant (sketch, on top of this branch)</summary>

```
SMEM_INPUT_SIZE = 4096
s_input_idx = T.alloc_shared([2, SMEM_INPUT_SIZE], T.int32)

# first pass
if pos < SMEM_INPUT_SIZE:
    s_input_idx[0, pos] = input_idx
else:
    workspace[bx, 0, pos] = input_idx

# tail pass: each read of workspace[bx, r_idx, i], i = s * threads + tx, becomes
T.if_then_else(i < SMEM_INPUT_SIZE, s_input_idx[r_idx, i], workspace[bx, r_idx, i])
# and the ping-pong write goes to s_input_idx[r_idx ^ 1, pos] when pos < SMEM_INPUT_SIZE,
# otherwise to workspace[bx, r_idx ^ 1, pos]
```

### liuyun7345 · 2026-09-27

Thanks @Arthur031221 — this is a very thorough check, and the sm_120 / torch 2.11.0+cu130 numbers extend the validation beyond the RTX 4090D (sm_89, torch 2.6.0+cu124) setup in the PR description. The 8-of-13 per-case breakdown against main's file is a nice confirmation of which cases carry the regression-detection load in a plain run.

On `equal-4097-256`: correct, and worth spelling out. At 4097 candidates the append runs one position past the shared buffer, and as your memcheck run shows the stray write doesn't reach anything the kernel reads back, so the indices come out right without the sanitizer. The intent of the all-equal series (4095/4096/4097/32768) is coverage of the 4096 boundary for the fixed kernel, with detection against the unfixed one coming from the memcheck run and the low-mantissa cases. I've noted this in the test docstring (321604e) so the matrix's detection capability isn't misread.

On the cost: your measurements help answer the question I left open in the PR description. The shared-first variant never spills on the three benchmark inputs (largest threshold bucket 2276 < 4096), yet still pays all of the +5% at 32768 and more than half of the gap at 131072 — so on these shapes the shared-memory staging isn't where the time goes, and the spill path would add complexity for little return. I'd keep the simple workspace version unless maintainers see shapes where it matters; happy to revisit with your sketch if so.

Appreciate the sketch and the per-case numbers.
