For reference, [LLaMA-Factory’s current hardware table](https://github.com/hiyouga/LlamaFactory#hardware-requirement) labels its numbers as **estimates** and puts a 7B model at roughly **6 GB for 4-bit QLoRA versus 16 GB for 16-bit LoRA**. I would treat those as orientation, not guarantees.

If I were starting on an 8–12 GB laptop GPU, my default route would be:

- use
**4-bit QLoRA/NF4** for the larger models,
- start with
**micro-batch size 1**,
- choose
`max_length`

from the actual token lengths in the dataset rather than automatically using the model’s maximum context,
- keep
**gradient checkpointing** enabled,
- use gradient accumulation if a larger effective batch is desired,
- run a short train + evaluation/save smoke test before committing to a long run.

That usually tells you more than a generic VRAM calculator.

For cloud vs local, I would not make it an either/or choice. **Small QLoRA experiments are quite reasonable locally.** Cloud becomes increasingly attractive when you want long contexts, full fine-tuning, lots of repeated runs/sweeps, or simply much faster iteration. A hybrid workflow — validate preprocessing/config locally, run only the expensive training in the cloud, then bring the adapter back — is also perfectly reasonable.

##
Why two 7B QLoRA runs can have very different VRAM usage

Training memory is not just the model weights.

The current [Transformers GPU memory guide](https://huggingface.co/docs/transformers/model_memory_anatomy) separates several contributors:

| Memory component |
What changes it |
| base model weights |
parameter count, dtype, quantization |
| trainable adapter weights |
LoRA rank and which modules are targeted |
| gradients |
number/dtype of trainable parameters |
| optimizer state |
optimizer and optimizer-state precision |
| activations |
**batch size, sequence length, model shape** |
| temporary tensors |
attention/loss/kernel implementation |
| framework/runtime overhead |
Trainer, kernels, allocator, evaluation path, etc. |

That activation row is particularly important on small GPUs.

A model may fit easily for inference, and even load in 4-bit with several GB free, but training still needs saved activations for backward.

This is also why **sequence length is a first-class VRAM parameter**, not a small detail.

The current [Transformers gradient-checkpointing documentation](https://huggingface.co/docs/transformers/grad_checkpointing) explains the tradeoff directly: instead of keeping all intermediate activations, checkpointing discards some of them and recomputes them during backward. You spend extra compute to save memory.

Similarly, [gradient accumulation](https://huggingface.co/docs/transformers/grad_accumulation) lets you keep the per-device micro-batch small while obtaining a larger effective batch. It does not magically make a true large batch fit; it changes how the batch is accumulated over multiple steps.

Current [TRL memory guidance](https://huggingface.co/docs/trl/reducing_memory_usage) is worth reading too. It discusses gradient checkpointing, sequence length, padding/packing, activation offload, and other levers separately rather than treating VRAM as a function of parameter count alone.

One more subtle point: **“QLoRA” is not always the exact same recipe.**

The original [QLoRA paper](https://arxiv.org/abs/2305.14314) trains LoRA adapters through a frozen 4-bit base model and introduced NF4, double quantization and paged optimizers.

Current [PEFT documentation](https://huggingface.co/docs/peft/developer_guides/quantization) describes QLoRA-style training as targeting all linear layers with:

```
LoraConfig(target_modules="all-linear", ...)
```


But real-world recipes often use only `q_proj`

/`v_proj`

, or attention projections, or attention + MLP projections. Rank also varies.

So two posts saying “7B QLoRA” may still be training materially different configurations.

The same caveat applies to the Trainer/runtime name. It is a little misleading to reduce the comparison to “Transformers vs Unsloth.” Unsloth may still use Hugging Face/TRL interfaces; the meaningful difference is often the **whole training stack** — checkpointing behavior, kernels, packing, optimizer, target modules, defaults, etc.

For example, current TRL trainers enable gradient checkpointing by default for memory efficiency according to the [TRL memory guide](https://huggingface.co/docs/trl/reducing_memory_usage). Older examples and other Trainer configurations may have different defaults.

##
Some concrete 8 GB and 12 GB examples

There are useful real examples, but I would use them as **existence proofs**, not universal requirements.

An 8 GB example

This [Qwen2.5-7B QLoRA model card](https://huggingface.co/bilalsaidumarov/ara-extract-7b-qlora) reports training on an RTX 4060 8 GB with approximately **7.6 GB peak VRAM**.

Its training configuration included:

| Parameter |
Reported value |
| Base |
Qwen2.5-7B-Instruct |
| Quantization |
4-bit NF4 + double quantization |
| Compute |
FP16 |
| LoRA |
r=16 |
| Targets |
q/k/v/o attention projections |
| Micro-batch |
1 |
| Gradient accumulation |
8 |
| Max sequence length |
768 |
| Optimizer |
paged AdamW 8-bit |
| GPU |
RTX 4060 8 GB |

So this is good evidence that **7B QLoRA can genuinely fit on an 8 GB-class GPU**.

But notice how constrained and explicit the recipe is. It is not evidence that an arbitrary 7B QLoRA configuration will fit.

A 12 GB example

The [Masafee CTF 7B model card](https://huggingface.co/masafy/masafee-ctf-7b) and its [training repository](https://github.com/masafykun/masafee-ctf-7b) document a substantially larger Qwen2.5-Coder-7B QLoRA run entirely on an RTX 3060 12 GB.

The model card reports roughly:

| Parameter |
Value |
| Base |
Qwen2.5-Coder-7B-Instruct |
| Method |
4-bit QLoRA via Unsloth |
| LoRA |
r=32, alpha=64 |
| Data |
~10.6M tokens |
| Packed sequence length |
2048 |
| Epochs |
2 |
| GPU |
RTX 3060 12 GB |
| Wall time |
12 h 17 m |

That is a useful example of what the additional headroom can buy: a longer sequence, larger adapter, broader target coverage, and a non-trivial multi-million-token run.

So I would describe the difference more as:

```
8 GB:
7B QLoRA is possible,
but you need to pay attention to the recipe.
12 GB:
still not "unlimited 7B",
but there is substantially more room to choose context length,
adapter configuration and training stack.
```


There are even more aggressive optimized-stack numbers. For example, [Unsloth’s requirements page](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements) lists **5 GB as an absolute minimum** for 7B QLoRA.

The important words there are *absolute minimum* and *Unsloth*. I would not turn that into “a 5 GB GPU is all you need for 7B fine-tuning.”

##
A small controlled check: sequence length alone moved the peak a lot

I also did a small controlled sanity check because I was curious how much the boundary would move without changing the model.

The setup was intentionally fixed:

| Setting |
Value |
| Model |
Qwen2.5-7B-Instruct |
| Base |
4-bit NF4 + double quantization |
| LoRA |
r=16 |
| Targets |
`q_proj` , `v_proj` |
| Micro-batch |
1 |
| Optimizer |
paged AdamW 8-bit |
| Gradient checkpointing |
enabled |
| Stack |
Transformers + PEFT + bitsandbytes |
| T4 compute dtype |
FP16 |

Changing only the sequence length produced approximately:

| Sequence length |
Sampled process GPU memory |
| 512 |
~9.6 GiB |
| 1024 |
~10.7 GiB |
| 2048 |
~13.1 GiB |
| 3072 |
OOM on a T4 with ~14.6 GiB visible |

This was **not an emulation of an 8 GB or 12 GB laptop GPU**, so I would not use the table as a laptop compatibility chart.

The useful observation is the shape of the curve: the same 7B QLoRA configuration moved from under 10 GiB to over 13 GiB just by changing sequence length.

I repeated the successful points on an L4 and saw essentially the same PyTorch allocation curve, while the speed was very different. That was a nice reminder that **“does it fit?” and “is it fast enough to be pleasant?” are separate questions.**

Gradient checkpointing was even more dramatic. With the same test at 1024 tokens, enabling checkpointing allowed the run to complete; disabling it caused OOM in the control run.

That matches the mechanism described in the [Transformers checkpointing guide](https://huggingface.co/docs/transformers/grad_checkpointing): activation memory can dominate, and recomputation can shift the fit/no-fit boundary quite a lot.

It also explains why an 8 GB optimized-stack example and a >8 GB standard-stack measurement are not necessarily contradictory.

##
A cheap way to test a particular laptop/configuration

If you already have the machine, I would measure the actual workload rather than trying to predict everything from the GPU model.

A fairly cheap progression is:

```
1. Tokenize the real dataset.
↓
2. Look at the token-length distribution.
↓
3. Pick a realistic max_length.
↓
4. Start with per-device batch size = 1.
↓
5. Enable gradient checkpointing.
↓
6. Run a handful of training steps.
↓
7. Also run evaluation/checkpoint saving once.
↓
8. Record peak VRAM and step time.
```


That last “evaluation” check is worth including.

A training step fitting does not guarantee every phase of the workflow fits. Evaluation may retain predictions/logits differently, and checkpointing/saving can exercise different paths. The [Transformers Trainer recipes](https://huggingface.co/docs/transformers/trainer_recipes) discuss memory controls such as `eval_accumulation_steps`

and preprocessing logits before metrics when evaluation memory becomes a problem.

I would also record the versions of at least PyTorch, Transformers/TRL/PEFT, bitsandbytes (or the corresponding optimized stack), dtype, attention backend and whether checkpointing is enabled.

Defaults and implementations change over time, so this makes somebody else’s “7B on 8 GB” result much easier to compare with yours.

##
Local vs cloud

I would base this more on the *type of work* than on a rule like “always train in the cloud.”

| Local laptop makes sense when… |
Cloud becomes attractive when… |
| You are doing 1B–3B QLoRA |
You need full fine-tuning |
| You are doing constrained 7B QLoRA |
You want long-context 7B training |
| You iterate on data formatting/prompts often |
You are running many experiments/sweeps |
| Runs are relatively short |
Wall-clock time matters a lot |
| You want zero startup/transfer friction |
Local training needs heavy CPU offload |
| Privacy/offline work matters |
You need substantially more VRAM |

There is also a very practical middle ground:

```
laptop
└─ preprocess / tokenize / smoke-test / debug config
↓
cloud GPU
└─ expensive final run
↓
laptop
└─ download adapter / merge / inference / evaluation
```


That avoids paying for a large GPU while debugging ordinary dataset or configuration mistakes, without forcing the laptop to do every large run.

Laptop-specific performance also deserves a separate note: two GPUs with the same VRAM capacity can have very different power limits, memory bandwidth, cooling behavior and sustained throughput. So **VRAM answers “can this configuration fit?” better than it answers “will training on this laptop be pleasant?”**

So, if I had to reduce it to a purchasing/usage rule of thumb:

**8 GB is not “inference only.”** It is already useful for QLoRA, including some carefully configured 7B runs.

**12 GB is not a magic 7B threshold either**, but for somebody who expects to fine-tune 7B models locally with any regularity, the extra headroom is meaningful.

And for either one, I would pay at least as much attention to **sequence length, micro-batch size, checkpointing and the training stack** as to the parameter count printed on the model card.
