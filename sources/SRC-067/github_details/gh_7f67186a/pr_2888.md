# [PR #2888] [CuTe, SM90] Fix swapped backward MMA layout and use 2-stage hdim256 config

## Summary

SM90 backward at head_dim 256 runs at ~300 TFLOP/s while hdim 128 is at parity with the C++ FA3 kernel (#2878). The cause is the hdim 256 config: it is the only SM90 backward config with `num_stages_Q=1`, so the Q/dO TMA loads and the WGMMAs are serialized every m-block. The C++ tile (64x80, 2-stage Q) does not fit next to the 64 KB smem dQaccum staging buffer, but 64x48 with `dKV_swapAB` does.

Using that config for GQA/MQA as well needs one real fix, and it turned up a second one:

1. **Swapped dK/dV postprocess layout.** `FlashAttentionBackwardPostprocess._get_tiled_mma` reversed the whole `(tile / atom_layout)` tiler for `swap_ab`, which asks `make_trivial_tiled_mma` for a WGMMA atom with M = hdim / num_wg. Every SM90 config with `dKV_swapAB` therefore fails in the GQA/MQA postprocess: `expects the M-mode to be 64, but got 192` for hdim in (128, 192] on `main` today (cf. #2087), `got 128` for `dQ_swapAB` above hdim 128. Build the tiled MMA the way the mainloop does, `tiler_mn=(64, tile / atom_layout on N)`; the accumulator register layout is unchanged.
2. **GQA dV accumulator rounding.** `dv_accum` was allocated with a fixed 32-element head-dim rounding while the kernel and the postprocess use `hdim_multiple_of` (64 with `dKV_swapAB`), so head_dim_v in {160, 200, 208, 224} reduced and read past each (batch, kv-head) region and dV came out wrong. Round it like `dk_accum`.
3. **hdim 256 config: 64x48, 2-stage Q, `dKV_swapAB`**, the same for MHA, GQA and MQA (no per-mode fallback). `dKV_swapAB` rounds `tile_hdim` to 64, so head_dim in (192, 256) (200/208/224/240, which currently abort inside the DSL compiler or fail in `get_smem_store_C`) now compiles and is correct. Block-sparse backward keeps the previous 64x64 tile because it derives its KV block size from `n_block_size`.

No new kernel or config parameters; forward and hdim <= 192 configs are untouched. 3 files, +40/-9 including tests.

| dense S=16384 H=16 D=256 | 36.5 ms · 302 TFLOP/s | **29.5 ms · 373** |
| dense causal S=16384 H=16 D=256 | 17.2 ms · 320 | **14.8 ms · 370** |

The remaining gap to C++ FA3 (~480 TFLOP/s here) is the smem dQaccum staging; that is a separate, larger change (C++ FA3's `dQacc_use_TMA=false` path) and will be a follow-up PR.
