# [PR #2892] ci: add PyTorch 2.14 to the wheel build matrix

source: https://github.com/Dao-AILab/flash-attention/pull/2892
state: closed | updated: 2026-09-16T17:30:06Z
labels: 

## 正文

## Why

PyTorch 2.14 raised the `ATen/ATen.h` header guard to C++20 (pytorch/pytorch#178150), and FA2's `setup.py` hardcodes `-std=c++17`, so building against 2.14 fails with `#error C++20 or later compatible compiler is required to use ATen` (#2863). Nothing in CI compiles FA2 against any torch newer than 2.10, so the break was only found by users building from source.

Adding 2.14 to the wheel matrix does two things:

1. Moves the failure from the user's `pip install` into the release build: the next time a torch release changes a header requirement, a `v*` tag build fails instead of a user's source build.
2. Gives 2.14 users a prebuilt wheel. `setup.py` derives the wheel name from `torch.__version__` and `torch.version.cuda` and downloads it from the release; today 2.14 users miss (no such asset), fall back to a source build, and that source build then fails on C++17. With this row they hit `+cu13torch2.14cxx11abiTRUE` (or `cu12…`) directly.

## What

- `publish.yml`: add `"2.14.0"` to `torch-version`. Exclude `cxx11_abi: FALSE` for it, same as every torch ≥ 2.7 row (PyTorch wheels ship CXX11 ABI = 1, so a FALSE wheel is unusable and would only double the job count). No CUDA exclude is needed: on the 12.9.1 runner the build picks the `cu126` torch wheel, on 13.0.1 the `cu130` one (see next point).
- `_build.yml`: extend the torch-minor → CUDA-tag map that decides which `download.pytorch.org/whl/cuNNN` index to install from ("highest published tag not above the system CUDA"). A missing key is a `KeyError` before torch is even installed, so the matrix row is useless without it. Entries are copied from what PyTorch actually publishes (checked 2026-09-16):

  | torch | published cu tags |
  |---|---|
  | 2.11.0 | 126 128 129 130 |
  | 2.12.x | 126 129 130 132 |
  | 2.13.0 | 126 129 130 132 |
  | 2.14.0 | 126 130 132 (no 128 / 129) |

  Only 2.14 is added to the publish matrix; 2.11–2.13 are in the map so `build.yml` (manual dispatch) can build them on demand.

Matrix cost: +16 jobs (2 OS × 4 Python × 2 CUDA × 1 ABI), 56 → 72 total. aarch64 `manylinux_2_28` wheels for 2.14.0 exist on all three CUDA tags, so the arm runner needs no exclude.

Wheel naming is unchanged: `_build.yml` produces `+cu{12,13}torch2.14cxx11abiTRUE`, which is exactly what `setup.py::get_wheel_url()` computes on the install side (CUDA major only, torch major.minor).

## Verification

- YAML parses; matrix expansion counted by script: 72 jobs, 16 for 2.14.0. `TORCH_CUDA_VERSION` resolves to `cu126` on CUDA 12.9.1 and `cu130` on 13.0.1.
- Local end-to-end on B200 (from reviewing #2879, now merged as f87af617): main + that setup.py change, torch 2.14.0+cu130, `FLASH_ATTN_CUDA_ARCHS=100` — full build 97/97 TUs, 3625-case `tests/test_flash_attn.py` slice passes.
- Suggest one manual `build.yml` dispatch (`ubuntu-22.04`, `3.12`, `13.0.1`, `2.14.0`, `TRUE`) before the next `v*` tag to see a full runner build.

## Not in this PR (maintainer calls)

- Whether to also publish 2.11–2.13 wheels (+16 jobs each) or drop the x86-only 2.6.0 row (−8 jobs) to offset.
- Python 3.14 (torch ≥ 2.10 ships cp314).
- `publish.yml` only runs on `v*` tags, so this catches header changes at release time, not at PR time. A PR-time guard could be a seconds-long CPU job that runs `g++ -fsyntax-only` over `flash_api.cpp`'s torch include set; happy to follow up if wanted.
