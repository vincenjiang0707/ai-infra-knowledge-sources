## 正文

## Problem

The backward preprocess (`flash_bwd_preprocess.py`) stores `lse_log2` for every row of the tile-rounded sequence:

```python
if tidx < seqlen_q_rounded - m_block * self.tile_m:
    gLSElog2[tidx] = lse_log2
```

Rows past the real row count carry `lse = +inf`, hence `lse_log2 = +inf`. With padded per-sequence offsets (the dense backward) that tail lands in the per-sequence slack. The sparse-MLA backward runs the preprocess with `use_padded_offsets=False`, where sequences sit back to back in `dpsum`/`lse_log2` with no slack: the tail aliases the first rows of the **next** sequence, or falls past the end of the buffer for the last one. The `dpsum` store right above already stops at `seqlen_limit` in that mode; `lse_log2` did not.

The preprocess tile is 128 packed (token, head) rows. At 128 Q heads every token fills a tile, so the tail is empty and this never showed. At 64 Q heads (recompute-P allowed since #2911) a tile spans two tokens, so a sequence with an **odd token count** leaves a 64-row tail that overwrites the next sequence's first token with `lse_log2 = +inf`. The recomputed P for that token is `exp2(S - inf) = 0`: its dq/dqv vanish and its dk/dv contributions are lost. Whether the tail store or the next sequence's own store lands last is a race between CTAs, so a single boundary fails intermittently (observed ~5 of 6 runs). Batched (non-varlen) inputs are affected the same way, since batch elements are contiguous. Load-P mode is unaffected (`dpsum` and `scale_p` are already guarded).

## Fix

One hunk: store the tile-rounded tail only with padded offsets; otherwise store rows below `seqlen_limit`, like `dpsum`. The main kernel never reads those rows (its tile is one token: `tile_m` = head count), so nothing else changes. The dense backward path (`use_padded_offsets=True`) compiles to the same code as before.

## Test

`test_flash_attn_mla_sparse_bwd_preprocess_tile_tail` (varlen × recompute_p): 64 heads, many odd-length sequences (12 varlen sequences incl. lengths 1/3/5, or a batch of 4 × 129 tokens), keys extending 64 tokens past the queries so every sequence's first token has a non-trivial softmax. Grads are checked per sequence against the fp32 reference and dq/dqv additionally per token, so the failure names the corrupted tokens. On main both recompute-P cases fail on every run, e.g.:

```
dQ: tokens [129, 195, 215, 346, 379, 384, 544] lost their gradient (sequence starts [0, 129, 130, 195, 212, 215, 346, 379, 384, 483, 544, 671])
dQ: tokens [258, 387] lost their gradient (sequence starts [0, 129, 258, 387])
```

With the fix the 4 cases pass (3 repeated runs); the other 114 sparse-MLA backward tests (`-k mla_sparse_bwd`) and the 132 fwd+bwd cases of `test_flash_attn_fast.py` pass on GB200 (CUTLASS DSL 4.7.1). `AI/SPARSE_MLA_RECOMPUTE_P.md` gets a paragraph on the preprocess tile tail under "Head counts".

## History

The tile-rounded `lse_log2` store predates sparse MLA (dense backward, where padded offsets make it correct). #2816 reused it for recompute-P while the sparse backward asserted exactly 128 Q heads, so no tail could exist. #2883 opened 1..128 heads and guarded the two load-P stores of the same tile (`dpsum`, `scale_p`) against the no-slack tail, but gated recompute-P to 128 heads, so the unguarded `lse_log2` store stayed unreachable. #2911 relaxed that gate to 64 heads without touching the preprocess, which made it reachable.
