## 正文

Great to see the HQQ team taking calibration-less quantization to the next level. The results are quite amazing and I can't wait to test it out. 

However, using unoptimized GPTQ code for quantization and showing a 50x decrease in speed vs HQQ is inaccurate.  There are many toggles for GPTQ quant and GPTQModel, in my humble opinion, is the most efficient (in terms of speed and quality) tool for GPTQ quantization. 

I can help since I have quantized hundreds of GPTQ models and full maintainer at GPTQModel and part-time maintainer at AutoGPTQ. 

This is different from gptq_demo.py as it uses `GPTQModel` (instead of `AutoGPTQ`) to more efficiently quantize to GPTQ format while at the same creating a higher quality quant.

Diff vs AutoGPTQ code:

1. Batching
2. Bloat/Refractor: Pass dataset as simple str: no need for complicated and often incorrect tokenization/attention mask code
3. desc_act set to True (Using  GPTQModel default)
4. damp set to 0.005 instead of 0.01 (I never understood why 0.01 is used as default. I like to use as small value as possible)
5. change max_tokens to max_length (str length) for dataset filtering.

Result of this code on A100 80GB: `PPL = 5.3972`, Quantization Time (10m quant + 2m pack): ` 721 seconds`. Roughly 2x faster than what HQQ is reporting on same A100 GPU with slightly lower PPL. Onpar with AWQ in terms of quantization speed. Cpu is Zen3 at 3.9Ghz.

Note: I made sure the code is as simple and as close to the original gptq demo as close as possible. Using C4 for calibration may not result in the best nor the current params. Quantization is hard and PPL score is only a rough indicator of how the model may perform. We have seen "good" PPL quants behave badly.

This code may not even be fastest code for a comparable GPTQ quant. Tweaking batching values, depending on gpu, may yield even more speed increases.
