# [PR #2072] Add AVX2 path for CPU 4-bit (NF4/FP4) blockwise dequantization

## 正文

## Summary

`dequantizeBlockwise4bitCpu` has NEON, AVX-512 and scalar branches but no AVX2 branch, so every x86-64 CPU without AVX-512 and every Windows x64 build (MSVC never defines `__AVX512F__`) runs the scalar loop. The bf16/fp16 cases are the slowest since the per-element conversion helpers block auto-vectorization.

This adds an AVX2 kernel with runtime dispatch, placed after the AVX-512 branch and before the scalar fallback. Output is bit-identical to the scalar path.

## Changes

- `csrc/cpu_ops_avx2.cpp` (new): 8 packed bytes (16 values) per iteration; nibble unpack, 16-entry codebook lookup via two `vpermps` + `blendv`, scale multiply, vectorized fp32/bf16/fp16 stores. Blocks are indexed over the flattened tensor like the scalar path, so any shape and any even blocksize works, with a scalar tail for a partial block.
- `csrc/cpu_ops.h`: `has_avx2()` (AVX2 + FMA + F16C), kernel declaration, `BNB_OMP_PARALLEL_FOR` moved here so both files share it.
- `csrc/cpu_ops.cpp`: call site.
- `CMakeLists.txt`: build the new file with `-mno-avx512*` appended (see below).
- `tests/test_ops.py`: `test_dequantize_4bit_matches_reference`, exact comparison against a pure-torch reference over all dtypes, fp4/nf4, blocksizes 32-4096 and shapes with partial blocks, rows shorter than a block and odd element counts (336 cases).

### Why a separate translation unit

`cpu_ops.cpp` is compiled with `-mavx512*`, which lets GCC EVEX-encode ordinary 256-bit instructions and SIGILL on non-AVX-512 CPUs (#2021). The existing `target("avx2,fma,no-avx512f")` workaround only works for code without intrinsics: the `<immintrin.h>` wrappers inherit the file-wide AVX-512 target and GCC refuses to inline them into a no-avx512 function. Compiling the kernel in its own file without those flags is the only way to guarantee VEX-only code; it is marked `noinline` so LTO cannot inline it into an AVX-512 caller. `objdump` on the resulting object: 0 EVEX instructions of 1614.

## Verification

- New test: 336 passed on Linux (GCC 15.2) and Windows (MSVC 14.44); a standalone harness also confirms the kernel is bit-exact vs the previous scalar loop over 1080 shape/blocksize/dtype cases.
- `tests/test_ops.py` (636 passed), `tests/test_functional.py -k 4bit` (349), `tests/test_linear4bit.py` (310) on a Linux build with the AVX-512 flags disabled, which is the configuration that exercises this path without hitting #2021 elsewhere.
- `pre-commit run --all-files` clean.
- I don't have an AVX-512 machine; that branch is untouched and still takes precedence.

## Benchmarks

Kernel-only, median of 30, NF4, blocksize 64, 1 thread. "before" is `main` with the standard flags.

<sub>Intel Core Ultra 7 256V (AVX2, no AVX-512), Linux/GCC 15.2, PyTorch 2.14 CPU</sub>
| shape | dtype | before | after | speedup |
|---|---|---:|---:|---:|
| 1024x1024 | fp32 | 0.280 ms | 0.163 ms | 1.7x |
| 1024x1024 | bf16 | 0.510 ms | 0.263 ms | 1.9x |
| 1024x1024 | fp16 | 0.403 ms | 0.155 ms | 2.6x |
| 4096x4096 | fp32 | 5.08 ms | 3.93 ms | 1.3x |
| 4096x4096 | bf16 | 8.34 ms | 4.49 ms | 1.9x |
| 4096x4096 | fp16 | 6.44 ms | 2.69 ms | 2.4x |

FP4 is within a few percent of NF4. With 8 threads the 4096x4096 case is memory-bound at ~40 GB/s on this laptop, so the gain is single-thread and on the conversion-heavy dtypes. On the Windows MSVC build, which had no SIMD path at all, the end-to-end op is 1.35x (fp32) to 2.3x (fp16) faster.
