# [PR #11719] [AMD] Make the membar async-load filter direction-aware

source: https://github.com/triton-lang/triton/pull/11719
state: closed | updated: 2026-09-23T04:08:28Z
labels: 

## 正文

The AMD membar filter vetoes the barrier between an async load and a
local_load synced via async_wait regardless of which of the two comes
first.

In the RAW direction (async load, then the synced local_load) the veto
is safe. The load's token proves its copy was waited for, and Membar
already emits a barrier right after that wait, so the copy is visible
to every thread before the read. A barrier in front of the load adds
nothing; any copy still in flight at that point is one the kernel chose
not to wait for, and a barrier cannot complete it either.

In the WAR direction (synced local_load, then an async load refilling
the same buffer) the veto is wrong. The wait covers the read, not what
follows it: other threads may still be reading the buffer when the
refill lands, and only a barrier orders that.

Membar passes the pending (earlier) access as op1 and the current access
as op2, so veto only when the synced local_load is op2. Dropping the
rule altogether would instead put a barrier before every synced
local_load that has an unrelated copy in flight, which multi-stage
pipelines routinely do.
