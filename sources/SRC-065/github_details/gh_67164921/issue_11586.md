## 正文

On an H100 (`e08ec196b`) this kernel aborts the process during compilation:

```
NVGPUToLLVMPass.cpp:460: WGMMAOpPattern::getPtxAsm(...): Assertion `supported && "WGMMA type or shape is not supported"' failed.
```

```python
@triton.jit
def matmul(out_ptr, a_ptr, b_ptr, M, N, K, BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr):
    a_d = tl.make_tensor_descriptor(a_ptr, shape=[M, K], strides=[K, 1], block_shape=[BLOCK_M, BLOCK_K])
    b_d = tl.make_tensor_descriptor(b_ptr, shape=[K, N], strides=[N, 1], block_shape=[BLOCK_K, BLOCK_N])
    out_d = tl.make_tensor_descriptor(out_ptr, shape=[M, N], strides=[N, 1], block_shape=[BLOCK_M, BLOCK_N])
    off_m = tl.program_id(0) * BLOCK_M
    off_n = tl.program_id(1) * BLOCK_N
    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.int32)
    for ki in tl.range(0, tl.cdiv(K, BLOCK_K), warp_specialize=True, num_stages=3):
        a = a_d.load([off_m, ki * BLOCK_K])
        b = b_d.load([ki * BLOCK_K, off_n])
        acc = tl.dot(a, b, acc, out_dtype=tl.int32)
    out_d.store([off_m, off_n], acc)

# int8 a [M, K], int8 b [K, N], int32 out; BLOCK_M, BLOCK_N, BLOCK_K = 64, 32, 32; num_warps=4
```

```
warp_specialize=True   BLOCK_M=64   assertion (also with BLOCK_M=128, BLOCK_N=64)
warp_specialize=True   BLOCK_M=32   exact (mma v2 path)
same loop without warp_specialize, BLOCK_M=64   exact
```

The same assertion fires for fp32 inputs with `input_precision="tf32"` (blocks 64x64x16, 64x128x16, 128x32x64, 128x32x16, with descriptors built in the kernel or on the host). The s8 and tf32 wgmma forms in `getPtxAsm` are only reachable when neither operand is transposed (`if (!supported && !transA && !transB)`), and the warp-specialized pipeline hands the pattern a transposed B, so it asserts instead of picking a layout it can lower. Found with a differential fuzzer of TMA matmul kernels (interpreter vs device).

### Vaisman · 2026-09-07

The shape and element types are fine, the same kernel compiles without `warp_specialize`, emitting exactly
`wgmma.mma_async.sync.aligned.m64n32k32.s32.s8.s8`. What breaks is the shared memory layout warp 
specialization picks for operand B.

Reproduced on current `main` 20e6ba8648. No H100 needed  the failure is entirely at compile time,
so an explicit `cuda:90` target is enough to hit it.

### The chain

The s8 form of WGMMA is only admitted when neither operand is transposed ([guard and assert](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/third_party/nvidia/lib/NVGPUToLLVM/NVGPUToLLVMPass.cpp#L460)). At the assert the op is `m64n32k32` with `A=s8, B=s8, C=s32` and `layoutA=row, layoutB=row` shape and types match the s8 form exactly, so it's B's layout that keeps it out.

One detail that's easy to read backwards: `transB` is computed with a negation ([`WGMMA.cpp:248`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/DotOpToLLVM/WGMMA.cpp#L248)):

```cpp
bool transB = !bLoader->getDescriptor().transposed;
```

so `layoutB=row` actually means B's descriptor is **not** transposed. It took me
a couple of passes to get that direction straight.

Without warp specialization, `AccelerateMatmul` gives B a transposed layout.
`transposed` falls straight out of `order` ([`TritonGPUAttrDefs.td:484`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L484)):

```cpp
bool transposed = order.size() > 1 && order[0] == 0;
```

and the operand index is what picks that order ([`AccelerateMatmul.cpp:171`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/lib/Dialect/TritonGPU/Transforms/AccelerateMatmul.cpp#L171), `opIdx == 1` -> `{0, 1}`). B ends up `transposed = true`, A `transposed = false`, and it compiles.

Dumping the IR around every pass, B keeps the correct layout all the way into `nvgpu-warp-specialization` and comes out with `transposed = false`, now sharing a single encoding with A. The rewrite is in `createBuffer` ([`WSCodePartition.cpp:781`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/third_party/nvidia/hopper/lib/Transforms/WarpSpecialization/WSCodePartition.cpp#L781)), which rebuilds the encoding from `ttg::getOrderForMemory(tensorType)`
([`WSCodePartition.cpp:760`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/third_party/nvidia/hopper/lib/Transforms/WarpSpecialization/WSCodePartition.cpp#L760)) — the producer's register order. That discards the operand role `AccelerateMatmul` had already worked out, and B loses its transposition.

### Why preserving the encoding isn't enough

Triton's TMA verifier currently rejects a transposed layout outright ([`Ops.cpp:660`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/lib/Dialect/TritonNvidiaGPU/IR/Ops.cpp#L660)):

```cpp
if (nvmma.getTransposed())
  return op->emitOpError("TMA descriptor layout must not be transposed");
```

That leaves operand B of an s8 dot in a bind: the layout WGMMA needs is precisely the one a descriptor isn't allowed to carry. Whether TMA could describe such a descriptor at the hardware level I genuinely don't know  what I can point at is
the constraint Triton enforces today. The non-specialized pipeline gets around it by staging B through registers (`descriptor_load` -> `local_alloc`), which is also  why `AccelerateMatmul` warns there that the pipelined load for that operand gets disabled.

In this case, warp specialization routes the descriptor load through a direct TMA channel, which forces the incompatible buffer layout.

### What I measured

On stock `main` this matches the table in the report: with `warp_specialize=True` it asserts at BLOCK_M/N/K=64/32/32 and 128/64/32, while 32/32/32 is fine (mma v2 path). All three configurations compile without warp specialization. With the
local patch below the first case compiles and the second stops elsewhere.

### Notes

The assert takes the whole process down  `triton-opt --run-reproducer` on the captured reproducer exits 134. I swapped it for a diagnostic locally, so the same reproducer now exits 1 with `error: unsupported WGMMA instruction: m64n32k32 with
A=s8, B=s8, C=s32; this instruction form exists only for untransposed operands, but got layoutA=row, layoutB=row` and no abort; that seems worth doing regardless of how the layout question gets settled.

I also have a patch routing these channels through registers instead of TMA:
64/32/32 then compiles with warp specialization still enabled, emitting the same instruction as the non-specialized path. It hits a second wall at 128/64/32, where `processProducerCommitOp` ([`WSLowerToken.cpp:74`](https://github.com/triton-lang/triton/blob/20e6ba864830b88f56b907fef85cab5097cf3892/third_party/nvidia/hopper/lib/Transforms/WarpSpecialization/WSLowerToken.cpp#L74)) implements only `TokenLoadType::TMALoadOp` and calls `report_fatal_error` for anything else, so a
register-staged producer has nowhere to commit. I've left that alone - it needs the mbarrier arrive semantics for a register-staged producer, and I don't have a Hopper GPU to validate anything I'd write there.

### Vaisman · 2026-09-14


Thanks, I picked up the register-staging path and it's working now, validated on an H100.

Keeping the transposed encoding that `AccelerateMatmul` picked and staging operand B through registers was enough to get the kernel compiling and emitting the right `wgmma.mma_async.sync.aligned.m64n32k32.s32.s8.s8`. It was still wrong on the GPU, in two separate ways.

The first is that the staged operand never got a completion edge. A and B land in the same consumer group, and the group is classified from its first channel, which is A, the TMA-filled one. So B inherited A's completion mechanism and got neither a `ProducerCommitOp` nor a `ConsumerWaitOp`. Nothing stopped the consumer from issuing `warp_group_dot` while `local_store` was still writing B.

Fixing that helped but didn't finish the job. 128/64/32 went from 99% of output elements wrong to about 10%, which is what convinced me there was a second problem rather than an incomplete first one. `local_store` writes through the generic shared-memory proxy and WGMMA reads through the async proxy, and an mbarrier doesn't publish the stores across that boundary. `FenceInsertion` can't pick it up on its own, because the use-def chain from the dot back to the store is cut at the `ttg.warp_specialize` boundary.

So the patch splits consumer groups by how their buffers actually get filled, classifies each group by the op that does the filling rather than by the channel's source op, and emits a `fence_async_shared` in the producer after the staged stores and before it signals completion.

ConSan is what exposed both runtime issues. Its result changed at every step:

| Version | ConSan result |
|---|---|
| Layout fix only | `Buffer being accessed has outstanding reads` |
| With token protocol | `Async shared-memory access is missing fence_async_shared. Operand: B` |
| With producer fence | Clean |

Validation was on an H100 PCIe with `num_warps=4`, `num_stages=3`, `num_ctas=1`. All 30 numerical cases pass: int8 64/32/32 and 128/64/32 plus the four TF32 shapes from this issue, each at 1, 2, 3, 4 and 7 K tiles. int8 is compared exactly against an int32 CPU reference, TF32 against cuBLAS with a tolerance. The same 30 pass under ConSan with no assertion. The 4- and 7-tile runs are the ones that actually reuse the three-stage buffers and flip the barrier phase. `test_warp_specialization.py` gives 145 passed, 1432 skipped, 0 failed.

On the CPU side, the lit tests in `ws_code_partition.mlir` now pin the preserved encoding and the whole token protocol: token types, `local_store` -> `fence_async_shared` -> `producer_commit`, and `consumer_wait` ahead of `warp_group_dot`. The protocol test fails on the intermediate version that passed every compile-side check and still produced wrong results on hardware, which is the case I most want to keep from regressing.

I haven't tested FP8 or multi-CTA, and I've only run this on an H100 PCIe. FP8 (`e4m3`/`e5m2`) is in the same `!transA && !transB` block of `getPtxAsm` as s8 and TF32, so I'd expect it to go down the same path, but that's untested. No performance numbers either: register staging turns off the pipelined load for this operand, which `AccelerateMatmul` already warns about.

I see #11728 covers the unsupported-WGMMA diagnostic separately in `NVGPUToLLVM`. Different files, so the two can land in either order.

I'll open a PR with this unless a maintainer would rather it took a different shape.
