# [PR #11939] [FRONTEND][NV] Skip zero-result ops when picking the reduce combiner

source: https://github.com/triton-lang/triton/pull/11939
state: open | updated: 2026-09-24T20:48:43Z
labels: 

## 正文

Fixes #11937.

## What breaks

`ReduceOpConversion` took the first op of the combine region as the combiner and asked the target for its reduction-tree arity; the NVIDIA `getReductionTreeArity` dereferences `combinerOp->getResult(0)` unconditionally. A `tt.print` (or any zero-result op) in front of the arithmetic combiner aborts assertions builds and reads past the result list in release builds.

## Fix

Walk the region and use the first op that has results as the combiner for the arity query; when no resultful op exists, fall back to arity 2 (a binary tree), which is valid for any target. Standard reduces are unchanged: their first op is the arithmetic combiner, so the selection is byte-identical there.

## Testing

- New lit case in `test/Conversion/reduce_to_llvm.mlir` (`@reduce_with_print_in_combine`): a `tt.print` ahead of `arith.addi` in the combine region; the module must convert instead of crashing.
- NOT RUN locally: this machine has no `triton-opt` build (a full LLVM toolchain build is beyond what I can justify for this diff), so the lit case is verified by structure and reviewed against the existing print/reduce cases in-tree, but it has not been executed here. CI runs the suite; the failure mode it guards is a compile-time crash in the pass, so the lit run is the meaningful gate.
- AMD's `getReductionTreeArity` never touches results (per the issue), so the selection change is behavior-neutral there.

### he-yufeng · 2026-09-24

Done in 4275e17bb, Jokeren's form: the synthesized vector region keeps its known head op, the scalar region goes through getSingleCombiner, and anything it declines falls back to a binary tree.

The original crash case is covered by the same accessor: the stray tt.print defines nothing, so getSingleCombiner walks from the returned value and returns the real combiner. One behavior note from re-pinning the lit test: a chained region (addf feeding maximumf) is not a direct two-arg combiner, so getSingleCombiner declines it and the tree stays binary there. The earlier ternary expectation only ever applied to a direct max/min region, which the existing tests already cover.
