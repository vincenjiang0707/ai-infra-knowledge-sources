# [Issue #11750] [Regression] SLSR in main's LLVM stops strength-reducing Triton's GEPs

source: https://github.com/triton-lang/triton/issues/11750
state: closed | updated: 2026-09-15T16:52:08Z
labels: 

## 正文

Compared with 3.8.0, main generates worse code for some kernels, on all four NVIDIA targets I compiled for. The cause is llvm/llvm-project#204278 (merged 2026-07-07). It is in main's LLVM pin (b010a18d) but not in the 3.8 release LLVM (5f07f818, based on upstream 62b7cf9623fc from 2026-06-01).

The LLVM fix itself is correct. A narrow GEP(getelementptr) index is sign-extended, and `sext(a + b) != sext(a) + sext(b)` when the i32 arithmetic wraps. So SLSR now strength-reduces such a GEP only when the index arithmetic has `nsw`.

Triton does not emit `nsw`. The IR builder creates `arith.addi/subi/muli` without overflow flags, and the TritonGPU to LLVM lowering drops arith flags anyway. So on main, SLSR skips every GEP whose i32 offset comes from Triton arithmetic.

### Tests 

Compile-only, main 972d18aa09 against the 3.8.0 wheel, 8 kernels x 22 configs for sm_80/86/90/100: vector add, row softmax, layernorm forward and backward, matmul, attention forward, row cumsum, atomic histogram.

The new check (`isSafeToFactorGepIndex`) fails in every kernel and config. When it fails, SLSR leaves that GEP alone, so the multiply stays instead of becoming "previous result + difference". Most of those GEPs would not change the final code anyway, but 8 cases get worse:

| kernel | target | 3.8.0 regs / SASS | main | main, offsets with `nsw` |
|---|---|---|---|---|
| attention_fwd BM64/BN64/D128 w4 fp16 | sm_100 | 168 / 3288 | 168 / 3608 | 168 / 3288 |
| attention_fwd BM64/BN64/D128 w4 fp16 | sm_80 | 255 / 2704 | 255 / 2712 | 255 / 2704 |
| attention_fwd BM64/BN64/D128 w4 fp16 | sm_86 | 168 / 2792 | 168 / 2800 | 168 / 2792 |
| attention_fwd BM64/BN64/D128 w4 fp16 | sm_90 | 168 / 2432 | 168 / 2464 | 168 / 2456 |
| matmul BM128/BN256/BK64 w8 bf16 | sm_100 | 191 / 2576 | 251 / 3168 | 191 / 2576 |
| matmul BM128/BN256/BK64 w8 fp16 | sm_100 | 191 / 2576 | 251 / 3168 | 191 / 2576 |
| matmul BM128/BN256/BK64 w8 bf16 | sm_80 | 255 / 2368 | 255 / 2376 | 255 / 2368 |
| matmul BM128/BN256/BK64 w8 fp16 | sm_80 | 255 / 2368 | 255 / 2376 | 255 / 2368 |

Registers and SASS instruction counts, same ptxas for every column (12.9.86, 13.4.59 for sm_100). The last column is a local build of main where the frontend sets `nsw` on default signed `+ - *` and the lowering carries the flag. Kernels outside these 8 are probably affected too.

### Fix? 

With `nsw` on the offset arithmetic and the LLVM fix left in place, all eight go back to their 3.8.0 values (attention on sm_90: 2456 vs 2432). But this is a semantics change, and it goes through the whole path from the frontend to the lowering. What I found:

- With `debug=True`, default `+ - *` on integers narrower than 64 bits already assert on overflow (#4589).
- Intentional wrapping is written explicitly with `sanitize_overflow=False` (e.g. `random.py`).
- In release builds overflow currently wraps. With `nsw` it becomes poison.
- The arithmetic here comes straight from user code, e.g. `a + rm[:, None] * sam + rk[None, :] * sak`, and `addptr` treats it as a signed offset.

I think it is not mine to decide whether and how to fix.
