# [PR #11663] [AMD] Enable amdgpu-use-amdgpu-trackers only when num_warps > 4 or waves_per_eu > 1

source: https://github.com/triton-lang/triton/pull/11663
state: open | updated: 2026-09-27T08:28:38Z
labels: 

## 正文

#11285 started passing LLVM's `amdgpu-use-amdgpu-trackers` for every gfx942/gfx950 compilation. That helps kernels that run several waves per SIMD and would otherwise spill, but it regresses single-wave kernels that already fit, badly so for MFMA-heavy ones. This PR passes the flag only for kernels that run at least two waves per SIMD, meaning either:
- `num_warps > 4`: a workgroup of eight or more waves puts at least two on each of the CU's four SIMDs, or
- `waves_per_eu > 1`.

## Why

The trackers make the machine scheduler chase register pressure harder. Under a tight budget that is the right trade. For a kernel at occupancy 1 with no spills, lower pressure buys nothing, and the tracker-driven schedule ends up bouncing MFMA accumulators between AGPRs and VGPRs until both register files overflow.

Measured on gfx950 by feeding fixed LLVM IR to `llc` with and without the flag (same LLVM; main loop instructions / AGPR-VGPR copies / spilled VGPRs):

| kernel (AITER) | waves_per_eu | flag off | flag on |
|---|---|---|---|
| gemm_afp4wfp4 4096x4096x4096 | 1 | 236 / 27 / 0 | 897 / 605 / 64 |
| gemm_a16w16 1x2880x4096 | 8 | 83 / 0 / 17 | 86 / 0 / 0 |
| gemm_a16w16 1x1280x8192 | 8 | 313 / 2 / 140 | 233 / 6 / 24 |

The afp4wfp4 kernel loses roughly half its throughput with the flag on (1315 vs 2639 TFLOPS in AITER's benchmark); the a16w16 kernels are the cases the flag was introduced for. The pattern is identical on every LLVM from the February 2026 pin through current main, so this is a question of which kernels should opt in rather than an LLVM regression. Two July LLVM changes to the tracker's pressure estimates (llvm/llvm-project#208574, #211139) made the afp4wfp4 case somewhat worse but did not create it.

## What changes

* `get_llvm_flags` now takes the `HIPOptions`. For gfx942/gfx950 it adds the trackers flag when `num_warps > 4 or waves_per_eu > 1`, and leaves it off otherwise. The gfx1250 expert-scheduling flag is unchanged.
* The flag is a process-wide LLVM option, so kernels with and without it can no longer overlap inside one process; `ScopedLLVMOptions` serializes them. That costs a little parallelism but doesn't affect correctness. A kernel compiled after a trackers-on kernel in the same process is byte-identical to a fresh-process compile.
* LLVM has no per-function attribute for the trackers yet. Once one exists, this should become an attribute set in `make_llir`, which would also remove the serialization. That switch will be needed anyway: llvm/llvm-project#210547 turns the trackers on inside the max-occupancy strategy. Once Triton picks that up, omitting the flag no longer means off, so the opt-out for single-wave kernels has to become explicit.
* Tests:
  * `test_amd_codegen_options` now sets `num_warps` and `waves_per_eu` and covers each branch. Its old gfx942/gfx950 cases used the default options, which no longer get the flag.
  * `test_amd_llvm_options_concurrent` compiles gfx950 with `waves_per_eu=2`, so gfx950 still sets the option that gfx1250 must not see.

## Performance

This was measured with the AITER Triton benchmark suite on gfx950: 53 benchmark scripts, 1,092 data points, each the median of 3 runs with the wheels interleaved, all on the same aiter tree and the same GPU. The wheels differ only in `third_party/amd/backend/compiler.py`:
- main: 4fd7cc5cfd
- a variant with only the `waves_per_eu > 1` condition
- this PR

| comparison | ≥2% faster | ≥2% slower | within 2% |
|---|---|---|---|
| this PR vs main | 149 (37 by ≥10%) | 128 (25 by ≥10%) | 723 |
| this PR vs `waves_per_eu`-only | 41 (7 by ≥10%) | 48 (4 by ≥10%) | 918 |

* **This PR vs main**, per-benchmark means:
  * Faster: `gemm_afp4wfp4` +14.4% (up to +109%), `gemm_a8w8_blockscale` +16.0% (up to +46%), `mla_gluon_decode` +12.2% (up to +54%), `pa_prefill` +7.1% (up to +44%).
  * Slower: `unified_attention_sparse_mla` −5.0%, `flash_kda` −3.3%, `mhc` −1.2%, `gather_kv_b_proj` −1.2%.
* **The `num_warps > 4` term alone** (this PR vs `waves_per_eu`-only):
  * Faster: `gemm_a16w8_blockscale` +6.4% (+10–13% for M ≥ 320), `moe_gemm_a8w8` batch=2 +12.8%.
  * Slower: `mla_decode_rope` −8.9% (down to −18%).

## Testing

* The AMD cases in `python/test/unit/test_knobs.py` pass on gfx950. Main's version of that file fails the two default-options cases against this change, as expected.
* A bf16 GEMM (256x256x64 tile) is correct in every (`num_warps`, `waves_per_eu`) combination. It compiles without the flag for `num_warps=4, waves_per_eu<=1` (68 B and 8 B of scratch go to 0, +62% and +38%) and is byte-identical to main otherwise.
* `pre-commit run` passes on the changed files.
