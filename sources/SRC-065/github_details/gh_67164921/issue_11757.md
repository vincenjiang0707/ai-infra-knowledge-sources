# [Issue #11757] tl.zeros fails in interpreter mode with "Cannot call @triton.jit'd outside of the scope of a kernel"

state: closed | updated: 2026-09-14T14:28:51Z

## 正文

### Describe the bug

tl.zeros fails when running a Triton kernel with TRITON_INTERPRET=1.

The equivalent tl.full(..., 0.0, ...) works correctly.

This appears related to #5142, but I can still reproduce it on a recent Triton nightly (3.8.0+gitf893845b).

Minimal reproduction
```
import os

os.environ["TRITON_INTERPRET"] = "1"

import torch
import triton
import triton.language as tl


@triton.jit
def test_kernel(
    out,
    M_BLOCK: tl.constexpr,
    K_BLOCK: tl.constexpr,
):
    # tl.zeros fails
    acc = tl.zeros((M_BLOCK, K_BLOCK), dtype=tl.float32)
    # tl.full works
    # acc = tl.full((M_BLOCK, K_BLOCK), 0.0, dtype=tl.float32)

    row = tl.arange(0, M_BLOCK)
    col = tl.arange(0, K_BLOCK)

    offsets = row[:, None] * K_BLOCK + col[None, :]
    tl.store(out + offsets, acc)


out = torch.empty(4, device="cuda", dtype=torch.float32)

test_kernel[(1,)](
    out,
    M_BLOCK=2,
    K_BLOCK=2,
)

print(out)
```

### he-yufeng · 2026-09-14

Confirmed on current main by reading the dispatch path: the interpreter patches only `@builtin` members of `tl`/`tl.core` (`_patch_builtin` in runtime/interpreter.py), while `zeros`/`zeros_like` in `standard.py` are `@jit`, so a call inside a kernel under `TRITON_INTERPRET=1` lands on `JITFunction.__call__` and raises exactly your error. `tl.full` survives because it is a builtin.

Fix up at #11772: both become builtins delegating to `core.full` with the semantic forwarded (same IR out), plus an interpreter-mode regression test. I could not run the runtime path locally (macOS, no libtriton target), so that leg is on CI.
