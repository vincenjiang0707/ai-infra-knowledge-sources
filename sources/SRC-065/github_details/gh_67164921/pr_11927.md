## 正文

# Problem

We observed unnecessary shared-memory bank conflicts on SM120 when an FP8 operand B local_load is lowered to `ldmatrix.m16n16.x2.trans.b8`. This PR removes a redundant register pre-permutation that can lead to a shared-memory unfriendly access pattern, improving performance in the tested triton_kernels workloads that use transposed b8 loads.

| Case | Before | After | Time change | Load bank conflicts |
|---|---:|---:|---:|---:|
| Dense FP8 GEMM | 66.601 µs | 63.219 µs | −5.08% | 1,057,353 -> 8,918 |
| FP8 GEMM + SwiGLU | 67.022 µs | 63.521 µs | −5.22% | 1,072,052 -> 18,988 |
| Ragged expert GEMM | 55.443 µs | 50.579 µs | −8.77% | 1,175,217 -> 60,997 |

Metric: l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum

# Changes

1. remove permReg in the transpose path.
2. add an mlir test to check that no ACC register permutation is generated.

### sinan-flash · 2026-09-23

# Analysis

In the transpose path, the offset bases must be moved forward before `divideLeft(cvt, tile)`. However,

1. `regPermForDivide()` already finds the required register permutation.

2. `permReg` uses positions from `fullTile`, which may not match those in cvt. The result is still correct because `accPermReg.inverse()` restores the register order after the load.

Take the mlir test in this PR as an example,
```llvm
#mma = #ttg.nvidia_mma<{
  versionMajor = 2, versionMinor = 0,
  warpsPerCTA = [4, 1], instrShape = [16, 8]
}>
#shared = #ttg.nvmma_shared<{
  swizzlingByteWidth = 64,
  transposed = false, elementBitWidth = 8
}>
#dot_b = #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 4}>

// shared memory -> opB registers
%opB = ttg.local_load %src
  : !ttg.memdesc<64x64xf8E4M3FN, #shared, #ttg.shared_memory, mutable>
  -> tensor<64x64xf8E4M3FN, #dot_b>
```

For this layout, we have, we get
```
fullTile.register: [(1,0), (2,0), (0,8)]  // [addr, offset]
cvt.register:      [64,144,1024,2048,8,16,32] // shared memory offsets, row K+1,K+2,K+16,K+32, N+8,...
permReg = [2,0,1,3,4,5,6]
```

Apperantly, the offset basis is at bit 2 in `fullTile`, but at register bit 4 in cvt. Applying the permutation derived from fullTile therefore moves 1024 (K+16) rather than the required offset basis 8.

<br>

Then, `regPermForDivide` then moves the required basis 8 to the front, but keeps the remaining bases in their current order. The two paths therefore produce different orders:

With `permReg`:
```
[64,144,1024,2048,8,16,32]
    -- permReg -->
[1024,64,144,2048,8,16,32]
    -- regPermForDivide -->
[8,1024,64,144,2048,16,32]
```

Without `permReg`:
```
[64,144,1024,2048,8,16,32]
    -- regPermForDivide -->
[8,64,144,1024,2048,16,32]
```

Tthe first eight address-provider lanes:
```
With permReg:     [0,16,1,17,4,20,5,21]
Without permReg:  [0,1,2,3,4,5,6,7]
```

With this access order, rows K=0 and K=16 have the same swizzle phase and map to the same bank group. The same happens for K=1/17, K=4/20, and K=5/21...
