# [Issue #11581] ptxas 12.9.86 drops the immediate of a second `add.s16x2`: wrong results on H100

source: https://github.com/triton-lang/triton/issues/11581
state: closed | updated: 2026-09-23T13:23:01Z
labels: 

## 正文

On `e08ec196b` with the bundled Hopper ptxas (12.9.86) this kernel stores wrong values on an H100; it is exact under `TRITON_INTERPRET=1` and exact on the same GPU with the bundled `ptxas-blackwell` (13.3.33) via `TRITON_PTXAS_PATH`.

```python
@triton.jit
def kernel(out_ptr, D1: tl.constexpr, D2: tl.constexpr):
    idx = tl.reshape(tl.arange(0, D1 * D2), (1, D1, D2))
    odd_row = tl.expand_dims(tl.expand_dims(tl.arange(0, D1) % 2 == 1, 0), 2)
    val = tl.where(odd_row, (idx * 9 + 1) % 1000, idx)
    tl.store(out_ptr + idx, val, mask=idx % 2 == 0)

kernel[(1,)](out, D1=32, D2=8, num_warps=1)
```

```
16 of 256 wrong
  out[136] = 224, expected 225
  out[140] = 260, expected 261
  out[152] = 368, expected 369
  out[156] = 404, expected 405
```

The `+ 1` is missing at those positions. LLVM narrows the second register group of each thread to packed 16-bit arithmetic, and the PTX (8.8, sm_90a) has two packed adds with the same register operand:

```
mov.b32     %r35, 65537;
add.s16x2   %r36, %r34, %r35;
add.s16x2   %r37, %r33, %r35;
```

ptxas 12.9.86 turns them into

```
VIADD.16x2 R5, R4, 0x10001;
VIADD.16x2 R4, R4, 0x0;
```

so the second add is a no-op on the low half. The remainder has to be by a non-power-of-two (1000, 999, 100 reproduce; 512 or no remainder do not, since the code is then not narrowed), and the masked store matters only because it changes the shape of the LLVM IR. Found with a differential fuzzer over random layout-op kernels (interpreter vs device); this was one of two mismatches in 1,000 programs. The other one has explicit `tl.int16` arithmetic (`(x.to(tl.int16) * 5 + 6) % 100` under a `where`), no narrowing needed: 256 of 1024 wrong with 12.9.86, exact with 13.3.33.
