# [Issue #10920] Float `%` gives a different result for a `constexpr` fold than for the runtime/interpreter path

source: https://github.com/triton-lang/triton/issues/10920
state: closed | updated: 2026-09-10T15:41:35Z
labels: bug

## 正文

### Describe the bug


The same float `x % y` produces a different result depending on whether it is folded at compile time (both operands `constexpr`) or evaluated at runtime — the sign of the result flips:

```python
import torch, triton, triton.language as tl

@triton.jit
def const_mod(o):
    c: tl.constexpr = (-5.0) % (3.0)
    tl.store(o + tl.arange(0, 1), tl.full((1,), c, tl.float32))

@triton.jit
def runtime_mod(a_ptr, b_ptr, o):
    tl.store(o, tl.load(a_ptr) % tl.load(b_ptr))

o = torch.zeros(1, dtype=torch.float32, device="cuda")
const_mod[(1,)](o)
print("constexpr:", o.item())          # 1.0

a = torch.tensor([-5.0], device="cuda"); b = torch.tensor([3.0], device="cuda")
o = torch.zeros(1, dtype=torch.float32, device="cuda")
runtime_mod[(1,)](a, b, o)
print("runtime:  ", o.item())          # -2.0
```

Observed `(-5.0) % (3.0)`:

| | result | convention |
|---|---|---|
| Triton, `constexpr` fold | **1.0** | Python `%` (sign of divisor) |
| Triton, runtime (`tt.frem`) | **-2.0** | C `fmod` (sign of dividend) |
| Triton, `TRITON_INTERPRET=1` | **-2.0** | matches runtime |
| Python `%` | 1.0 | sign of divisor |
| NumPy `%` / PyTorch `%` | 1.0 | sign of divisor |
| C `fmod` / NumPy `fmod` / `torch.fmod` | -2.0 | sign of dividend |

So the `constexpr` fold (Python semantics) and the runtime/interpreter path (C `fmod` semantics) disagree for the same expression — an internal inconsistency where one source expression means two different things depending on constexpr-ness.

Integer `%` is fine (both paths truncate toward zero); this is specific to float `%` (and the same applies to `//`).

## Question / expected behavior

The two paths should agree, but I'm not sure which convention is intended, so I'd rather ask than pick a direction:

- If float `%` should follow **PyTorch/NumPy `%`** (sign of divisor, `-5.0 % 3.0 == 1.0`), then the runtime lowering (`tt.frem`) and the interpreter are the ones to change — though that changes existing runtime numerics.
- If it should follow **C `fmod`** (sign of dividend, `== -2.0`, which the runtime and interpreter already do), then only the `constexpr` fold needs to change to match, with no runtime behavior change.

Which convention should `tl` float `%` (and `//`) follow?

## Root cause (where the constexpr `1.0` comes from)

The `constexpr` fold uses Python's operator directly:
[`constexpr.__mod__`, core.py](https://github.com/triton-lang/triton/blob/682f467ab85e6e4e0c5050aa44ccf1a47a65f742/python/triton/language/core.py#L267) →
`constexpr(self.value % _unwrap_if_constexpr(other))`, i.e. Python `%` (sign of divisor). The runtime path lowers `%` to `tt.frem` (C `fmod`, sign of dividend), so the two diverge for mixed-sign float operands.


### Environment details

Triton 3.7.1 / main @682f467ab (root byte-identical on main); NVIDIA L40S (sm_89); arch-independent (the fold happens in the frontend).

### alexxony · 2026-09-09

Reproduced on pip 3.6.0 (L4 GPU):

```python
@triton.jit
def const_mod(o):
    c: tl.constexpr = (-5.0) % (3.0)
    tl.store(o + tl.arange(0, 1), tl.full((1,), c, tl.float32))

@triton.jit
def runtime_mod(a_ptr, b_ptr, o):
    tl.store(o, tl.load(a_ptr) % tl.load(b_ptr))
```
```
const  (-5.0) % (3.0)   = 1.0
runtime(-5.0) % (3.0)   = -2.0
```
Matches the report exactly.

Root cause: `constexpr.__mod__` in `core.py` uses Python's `%` (divisor-sign), while runtime lowers to `tt.frem` (C `fmod`, dividend-sign). This predates the current pip release — not a recent regression.

Two ways to fix:
- (A) Change runtime/interpreter to match Python's `%` — consistent with `tl.constexpr`, PyTorch/NumPy semantics, but changes existing runtime numeric behavior (breaking change), needs `tt.frem` lowering touched.
- (B) Change `constexpr.__mod__` to match `fmod` — one-line fix, no runtime/GPU behavior change, but constexpr fold then diverges from Python `%` syntax.

Which direction do you want? Happy to send a PR either way.


### alexxony · 2026-09-10

Found a sibling case with the same root cause: `constexpr.__floordiv__` in `core.py` uses Python's `//` (floor toward -inf), while runtime `//` lowers to `create_sdiv`/`create_udiv` — truncating division (documented, see #619/#955: "these semantics are expected and documented"). Same shape as the `%` divergence above — Python semantics at compile time, C semantics at runtime.

```python
@triton.jit
def const_floordiv(o):
    c: tl.constexpr = (-7) // (2)
    tl.store(o + tl.arange(0, 1), tl.full((1,), c, tl.int32))

@triton.jit
def runtime_floordiv(a_ptr, b_ptr, o):
    tl.store(o, tl.load(a_ptr) // tl.load(b_ptr))
```

Reproduced on pip 3.6.0 (L4 GPU), both compiled and interpreter mode agree with each other and disagree with the constexpr fold:

```
=== mode=compiled ===
const  (-7) // (2) = -4
runtime(-7) // (2) = -3

=== mode=interpreter ===
const  (-7) // (2) = -4
runtime(-7) // (2) = -3
```

Whichever direction you pick for `%`, `//` likely wants the same one for consistency — a single PR could fix both `constexpr.__mod__` and `constexpr.__floordiv__` together. Happy to send a PR once you pick (A) or (B).
