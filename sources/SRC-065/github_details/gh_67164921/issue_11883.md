# [Issue #11883] TRITON_CODEGEN_BACKENDS cannot exclude nvidia/amd: core headers and libtriton include the backend trees

source: https://github.com/triton-lang/triton/issues/11883
state: open | updated: 2026-09-21T20:50:48Z
labels: 

## 正文

## Context

We build Triton from source on macOS arm64 to host an out-of-tree Apple GPU backend (the MLIR backend proposed in triton-lang/triton-ext#126). The machine has no NVIDIA and no AMD device and never will, yet every build compiles both backends and downloads the NVIDIA toolchain.

`CMakeLists.txt:27` declares `TRITON_CODEGEN_BACKENDS` as a cache variable, and `setup.py:297` already derives `-DTRITON_CODEGEN_BACKENDS` from the backend list, but `setup.py:399` fixes that list in code:

```python
backends = [*BackendInstaller.copy(["nvidia", "amd"]), *BackendInstaller.copy_externals()]
```

`TRITON_PLUGIN_DIRS` only adds externals, and no selector appears in the cmake passthrough list, so there is no supported way to ask for fewer in-tree backends from the Python build.

## What we tried, and what happened

We patched that one line to read `TRITON_CODEGEN_BACKENDS` from the environment, defaulting to `nvidia;amd` so nothing changes for anyone who sets nothing. The clean build with neither backend then fails after 107 seconds of compiling, because core code includes backend trees:

- `include/triton/Dialect/TritonGPU/Transforms/Passes.h:5` includes `nvidia/include/Dialect/NVWS/IR/Dialect.h`, whose own line 31 needs the TableGen-generated `Dialect.h.inc` that exists only when the nvidia subtree builds. This is a public core header, so everything including it inherits the dependency.
- `lib/Dialect/TritonGPU/Transforms/WarpSpecialization/PartitionLoops.cpp:10-11` includes the same NVWS dialect and its passes.
- `python/src/gluon_ir.cc:18-20`, inside libtriton itself, includes `third_party/amd/include/Dialect/TritonAMDGPU/IR/Dialect.h` and two AMD lib headers, whose dialect header needs AMD's generated `.h.inc`.

Seven core files in total, on commit `4a15f415`. So the selector the cmake side advertises cannot currently be honoured, and the hardcoded list at line 399 is arguably the accurate description of the tree rather than the bug.

## What it would be worth, measured

From a full build here, so these are measurements rather than estimates:

- the two backend subtrees are 625 MB of a 4405 MB build tree (nvidia 300 MB, amd 325 MB)
- the NVIDIA toolchain download is a further 662 MB, a pure skip on a machine that cannot use it
- roughly 290 MB of wheel payload

That is about 1.5 GB of an 8 GB footprint. In fairness, the single largest item is not the backends: `bin`, `test` and `unittest` come to 2887 MB and are already switchable today with `-DTRITON_BUILD_UT=OFF` and no patch at all. We mention it so the trade is judged honestly.

## The question

Is `TRITON_CODEGEN_BACKENDS` intended to be usable from the Python build, or are nvidia and amd considered mandatory in-tree components with the cmake variable serving another purpose? If the former, the minimum fix is either gating those seven includes behind the selector, which is the layering change, or always running the backends' TableGen while not building their libraries, which is smaller and uglier but honest.

We are happy to do the work and to test it on macOS arm64 on every pin move, but the direction is yours to set rather than ours to guess. We found no prior art for the split; #11485 looks adjacent in spirit, and #2048 is the old version of the same complaint from the other side. The one-line diff we tested is available if it is useful.
