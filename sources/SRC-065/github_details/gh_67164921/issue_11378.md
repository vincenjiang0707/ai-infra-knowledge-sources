# [Issue #11378] [AMD] scf.for with runtime trip count miscompiled on gfx1151

source: https://github.com/triton-lang/triton/issues/11378
state: open | updated: 2026-09-07T08:56:25Z
labels: bug

## 正文

### Describe the bug

I'm getting wrong results (num_warps=1), HIP illegal-address fault (num_warps>=2) 

After creating a workaround, I had my LLM look at the miscompile:

## Summary

The AMD backend miscompiles a kernel whose only dynamic control flow is a
runtime-trip-count `scf.for` (`for t in range(0, num_tokens)`, `num_tokens`
a runtime scalar). The generated TTGIR is semantically correct; the runtime
behavior is wrong or crashes, and it is layout-dependent:

| num_warps | behavior (triton 3.7.0, ROCm 7.14, gfx1151) |
|-----------|-----------------------------------------------|
| 1 | deterministic wrong results (garbage in scalar stores, ~2/3 of packed output wrong) |
| 2 / 4 | wrong results, then HIP illegal-address fault (surfaces as `RuntimeError`/`SystemError` from the launcher) |
| 8 | fault on the first launch |

The identical kernel written with `tl.static_range(0, 64)` plus masked
inactive iterations is **bit-exact** on the same stack. A grid-per-token
variant (no loop at all) is also correct. This rules out driver/firmware.

## Environment

- GPU: AMD Ryzen AI MAX+ 395 (Radeon 8060S), **gfx1151** (Strix Halo iGPU, 128 GB unified)
- Triton: `3.7.0+git88b227e2.rocm7.14.0a20260608` (ROCm vendor wheel shipping with torch, see below)
- torch: `2.13.0a0+rocm7.14.0a20260608`
- ROCm: 7.14.0
- Linux kernel: 7.1.8-100.fc43; MES firmware 0x88 (past the known gfx1151 CWSR/MES 0x83 fault window; we also ran with HIP_LAUNCH_BLOCKING=1)
- Reproduces in a single fresh process; deterministic at num_warps=1 (5/5 runs identical)

## Minimal reproducer

Attached: `ds4-triton-scf-bug.py` (self-contained; torch + triton only, no
other deps). Run with `HIP_LAUNCH_BLOCKING=1`:

```bash
python3 ds4-triton-scf-bug.py --num-warps 1   # MISMATCH (wrong results)
python3 ds4-triton-scf-bug.py --num-warps 2   # MISMATCH then FAULT
python3 ds4-triton-scf-bug.py --assume --num-warps 1   # PASS (dynamic loop + tl.assume)
python3 ds4-triton-scf-bug.py --static --num-warps 1  # PASS (unroll workaround)
```

The kernel is a single-program (grid == 1) top-k ragged-index packer. The
loop body contains: masked `tl.load` of a row, `tl.sum` reduction, a
`tl.where` on a per-token validity scalar, a scalar iteration-carried
accumulator (`running`), an indexed load through a small lookup table, and
masked stores at `ragged_ptr + running + offs`:

```python
@triton.jit
def pack_kernel(topk_indices_ptr, topk_stride, is_valid_ptr, t2r_ptr,
                block_table_ptr, bt_stride, lens_ptr, indptr_ptr, ragged_ptr,
                num_tokens, block_size, topk: tl.constexpr,
                TOPK_PAD: tl.constexpr, MAX_TOK: tl.constexpr,
                MODE: tl.constexpr):
    offs = tl.arange(0, TOPK_PAD)
    omask = offs < topk
    running = tl.zeros((), dtype=tl.int32)
    tl.store(indptr_ptr + 0, 0)
    if MODE == 1:
        for t in tl.static_range(0, 64):          # workaround A: bit-exact
            ...                                    # (masked inactive iters)
    else:
        if MODE == 2:
            tl.assume(num_tokens > 0)              # workaround B: bit-exact
        for t in range(0, num_tokens):            # the miscompiled scf.for
            idx = tl.load(topk_indices_ptr + t * topk_stride + offs,
                          mask=omask, other=-1)
            valid_tok = tl.load(is_valid_ptr + t)
            cnt = tl.sum((idx >= 0).to(tl.int32), axis=0)
            cnt = tl.where(valid_tok != 0, cnt, 0)
            tl.store(lens_ptr + t, cnt)
            out_len = cnt
            req = tl.load(t2r_ptr + t)
            pmask = omask & (offs < out_len)
            vald = pmask & (idx >= 0)
            bidx = idx // block_size
            bnum = tl.load(block_table_ptr + req * bt_stride + bidx,
                           mask=vald, other=0)
            slot = tl.where(vald, bnum * block_size + idx % block_size, -1)
            tl.store(ragged_ptr + running + offs, slot, mask=pmask)
            running = running + cnt
            tl.store(indptr_ptr + t + 1, running)
```

## Expected vs actual

Expected: `lens == [512, 0, 498, 0, 505, 0]`, `indptr == [0, 512, 512, 1010, 1010, 1515, 1515]`, and the first 1515 packed slots match the reference.

Actual (num_warps=1, deterministic across runs):

```
lens_gpu=[-2147483648, 0, -2147483648, 0, -2147483648, 0]
lens_ref=[512, 0, 498, 0, 505, 0]
indptr_gpu=[0, -2147483648, -2147483648, 0, 0, -2147483648, -2147483648]
indptr_ref=[0, 512, 512, 1010, 1010, 1515, 1515]
ragged mismatches: 1047 / 1515
```

At num_warps>=2 the launcher eventually raises a HIP error; with
HIP_LAUNCH_BLOCKING=1 it surfaces as `SystemError: <built-in method
__reversed__ of list object ...> returned a result with an exception set`
(the wrapped HIP failure inside `triton/knobs.py`), and the HIP context is
then poisoned (subsequent launches fail with `AcceleratorError`).

## Evidence the IR is correct (miscompile is below TTGIR)

- The TTGIR for the failing form is semantically correct (attached dump:
  `topk_pack_kernel.ttgir`): `scf.for %t = %c0_i32 to %num_tokens step
  %c1_i32` with correctly masked `amdg.buffer_load`/`amdg.buffer_store`,
  reduce, and select ops.
- The LLIR also looks structurally correct (loop condition
  `icmp slt %t, %num_tokens`, normal scalar-thread guards). The garbage
  appears to be introduced in the AMDGCN/ISA lowering or the buffer-op
  addressing inside the runtime loop.
- Layout dependence: wrong-but-deterministic at num_warps=1, illegal
  address at higher warp counts. Same GPU, same stack, only the loop
  construct differs — the static_range and grid-per-token variants are
  bit-exact.

## Bisect / differential testing

Fresh process per variant (same kernel, one construct changed):

| variant | result |
|---------|--------|
| runtime `for t in range(0, num_tokens)` (shipped) | corrupt / fault |
| runtime loop + guarded body | corrupt |
| `for t in range(0, 6)` (constant bound) | corrupt — same garbage pattern |
| `tl.range(0, num_tokens)` / `tl.range(..., num_stages=1)` | corrupt — same garbage pattern |
| runtime loop + `tl.assume(num_tokens > 0)` | **bit-exact** (num_warps 1/2/4/8) |
| grid-per-token (loop removed, one program per token) | correct |
| `tl.static_range(0, 64)` + masked inactive iters | bit-exact |

The constant-bound row matters: the failure is **not** specific to runtime
trip counts. `range(0, 6)` lowers to the identical guarded-loop structure
and fails identically. The trigger is the *structure* the loop lowering
emits, not the bound's provenance.

## Root-cause narrowing: what `tl.assume(num_tokens > 0)` changes

`tl.assume` is emitted as `llvm.assume` and fully consumed by LLVM before
ISel (`grep llvm.assume` in the dumped `.llir` = 0). Diffing the dumped LLIR
of the broken vs the fixed kernel, the **only** structural difference is the
loop's guarded entry:

- Broken: the loop is reached through a two-entry region — a merge block
  (`%51`) holding phis for the loop-carried values, a `.preheader` whose
  phis select `0` (the "loop may not execute" constant) vs the loop-exit
  value, then the loop header.
- Fixed (assume>0): that guard structure is gone; the loop is entered
  directly, the phis feed straight from the kernel entry.

The dumped ISA (`.amdgcn`) confirms the corruption is in the AMDGPU backend
lowering of the guarded form: the **broken kernel's outer loop has no scalar
trip-count compare at all** — there is no `s_cmp`/`s_cbranch_scc` on the
loop counter anywhere in the function. Loop control is driven purely by the
exec-masking of the inner `tl.sum` irregular-reduce flow
(`v_cmpx`/`s_cbranch_execz`), i.e. the uniform branch for `t < num_tokens`
was dropped during ISel/machine lowering. The fixed kernel has a normal
`s_cmp_lt_i32` + `s_cbranch_scc1` loop guard. So the guard structure the
Triton AMDGCN lowering emits confuses the AMDGPU backend's uniform-branch
handling and the trip-count branch is silently lost.

## Production impact

This was found in vLLM on gfx1151: a fused decode kernel with this exact
loop shape (active when <= 64 tokens in a decode step) faulted at runtime
with `HIP Memory Fault ... (device/GTT aperture)` during a 45k-token
context request, took down the NCCL watchdog and the whole TP=2 serving
process. It had passed hours of warmup and short-request traffic — the
miscompile only surfaces when the garbage lands on an illegal address or a
layout that exposes it.

## Workaround

Three verified bit-exact workarounds, in order of preference:

1. **Keep the loop dynamic; add a positivity assumption** (smallest change,
   no unroll/mask overhead, no token-count cap):
   ```python
   tl.assume(num_tokens > 0)
   for t in range(0, num_tokens):
       ...
   ```
   Bit-exact at num_warps 1/2/4/8; validated on the production kernel
   against the full crash-shaped + stress harness (38/38 cases, 11 configs
   x 20 iters). Removing the guard structure is what makes it correct.
2. Fully static unroll + masked inactive iterations (`tl.static_range`).
3. Per-token grid.

All are bit-exact vs the CPU reference and vs the stock 4-launch chain they
replace.

  or other archs.
