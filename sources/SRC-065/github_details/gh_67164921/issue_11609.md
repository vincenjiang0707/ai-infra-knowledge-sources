# [Issue #11609] TensorSizeTrait accepts over-limit tensor shapes when the element-count product exceeds the int64_t range

source: https://github.com/triton-lang/triton/issues/11609
state: closed | updated: 2026-09-07T01:42:41Z
labels: 

## 正文

## Describe the bug

The Triton `TensorSizeTrait` verifier declares a maximum of `1048576` tensor elements. For ranked static tensor types, the current implementation computes the element count by multiplying dimensions in a signed `int64_t` accumulator before comparing the result with that limit. For the input below, the mathematical product exceeds the positive range of `int64_t`, so the multiplication cannot be relied upon as a defined C++ signed-arithmetic result.

The following validly parsed Triton IR uses positive static dimensions whose mathematical product is `2^63`. The type is above the declared maximum, but the verifier accepts the operation without emitting the expected maximum-element diagnostic.

## Expected behavior

The verifier should reject any statically shaped tensor whose mathematical element-count product is greater than `1048576`, including products outside the representable positive range of `int64_t`, and should emit a maximum-element diagnostic. In the reproducer below, the expected result is rejection; the observed result is successful verification with exit status `0`.

### Minimal reproducer

Save the following as `tensor-size-int64-product-bypass.mlir`:

```mlir
tt.func @overflow_product(%x: tensor<2147483648x4294967296xi64>) {
  %y = tt.int_to_ptr %x : tensor<2147483648x4294967296xi64> -> tensor<2147483648x4294967296x!tt.ptr<f32>>
  tt.return
}
```

Run:

```bash
triton-opt --verify-each tensor-size-int64-product-bypass.mlir
```

Observed result:

```text
exit status: 0

module {
  tt.func @overflow_product(%arg0: tensor<2147483648x4294967296xi64>) {
    %0 = tt.int_to_ptr %arg0 : tensor<2147483648x4294967296xi64> -> tensor<2147483648x4294967296x!tt.ptr<f32>>
    tt.return
  }
}
```

The mathematical element count is `2147483648 * 4294967296 = 9223372036854775808` (`2^63`), which is greater than `1048576`. I expected the verifier to reject this type because it exceeds the declared tensor-size limit.

### Controls

As a small accepted control, this input is accepted:

```mlir
tt.func @small(%x: tensor<16xi64>) {
  %y = tt.int_to_ptr %x : tensor<16xi64> -> tensor<16x!tt.ptr<f32>>
  tt.return
}
```

As a safe-rejection control, this input is rejected:

```mlir
tt.func @over_limit(%x: tensor<1048577xi64>) {
  %y = tt.int_to_ptr %x : tensor<1048577xi64> -> tensor<1048577x!tt.ptr<f32>>
  tt.return
}
```

The rejection contains:

```text
tensor-size-over-limit-control.mlir:2:8: error: Maximum allowed number of elements is 1048576, but %0 = "tt.int_to_ptr"(%arg0) : (tensor<1048577xi64>) -> tensor<1048577x!tt.ptr<f32>> has more than that
  %y = tt.int_to_ptr %x : tensor<1048577xi64> -> tensor<1048577x!tt.ptr<f32>>
       ^
tensor-size-over-limit-control.mlir:2:8: note: see current operation: %0 = "tt.int_to_ptr"(%arg0) : (tensor<1048577xi64>) -> tensor<1048577x!tt.ptr<f32>>
```

The candidate was accepted, the small control was accepted, and the over-limit control was safely rejected in three repetitions each on the latest source build.

## Relevant implementation

The common `TT_Op` definition attaches `TensorSizeTrait` to registered Triton operations. The trait declares `maxTensorNumElements = 1048576`, and `lib/Dialect/Triton/IR/Traits.cpp` computes operand and result element counts with `int64_t numElements` and `numElements *= s` before checking `numElements > maxTensorNumElements`.
