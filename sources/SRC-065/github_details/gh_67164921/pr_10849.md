# [PR #10849] [LLVM] Always set the target machine when arch is specified

source: https://github.com/triton-lang/triton/pull/10849
state: open | updated: 2026-09-27T01:17:36Z
labels: 

## 正文

`optimize_module` drops the target machine whenever an LLVM-IR pass plugin is loaded (`LLVM_PASS_PLUGIN_PATH`). That guard was added in #4669 for instrumentation plugins that splice in externally (Clang-)compiled code. This PR creates the target machine whenever `arch` is known, whether or not a plugin is loaded.

## Why

Loading a plugin currently changes how the kernel itself is optimized, not only what the plugin adds. Without a target machine, the O3 pipeline runs without the AMDGPU target passes (for example `AMDGPUAttributor`) and without target cost models. Measured on gfx950 with a vector-add kernel:

| | no plugin | in-tree `GPUHello` plugin loaded |
|---|---:|---:|
| `amdgpu-no-*` attributes in LLIR, `main` | 21 | 0 |
| `amdgpu-no-*` attributes in LLIR, this PR | 21 | 21 |

`GPUHello` only prints, yet loading it removes every attribute the attributor infers for this kernel. How much that matters depends on the kernel; for a plain matmul the generated code is nearly identical, while scheduler-style plugins, such as the out-of-tree LLIR scheduler used by the gfx950 Gluon tutorials, lose performance without the target cost models. With this PR the optimized IR no longer depends on whether a plugin is loaded.

## What #4669 was working around

With a target machine, the AMDGPU attributor runs at `OptimizerLastEP` before any plugin pass, because the target machine registers its callbacks in the `PassBuilder` constructor. It marks kernels `amdgpu-no-*` for implicit inputs they do not use. An instrumentation plugin that then injects calls reading those inputs (workgroup id y/z, the implicit-argument pointer, ...) leaves the kernel with attributes that no longer hold, and the backend does not set those inputs up. Dropping the target machine avoided this by never running the attributor, at the cost of disabling every target pass for all plugins.

The correct fix is in the plugin, which should remove `amdgpu-no-*` from the functions it instruments. For Omniprobe, the instrumentation tool this guard was written for, that fix is AMDResearch/omniprobe#44 (reproduction and details in AMDResearch/omniprobe#43). I verified on gfx950 that with this PR and that fix, Omniprobe's instrumented kernels get the same implicit-input setup as today.

## Scope

Today this only affects AMD. The NVIDIA backend calls `optimize_module` without `arch`, so it never creates a target machine, with or without a plugin. If #11156 lands and passes `arch` for NVIDIA, NVIDIA plugin users get the target machine as well.

## Testing

- The table above, before and after this change.
- Omniprobe's Triton plugin with and without AMDResearch/omniprobe#44, as described above.
