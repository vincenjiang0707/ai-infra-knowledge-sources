# [PR #11890] [AMD] Do not stagger CDNA4 padded layouts over rows that do not exist

source: https://github.com/triton-lang/triton/pull/11890
state: open | updated: 2026-09-24T16:06:02Z
labels: 

## 正文

`composePaddedLayoutForAsyncCopyCDNA4` aborts the compiler for any dot operand whose contiguous row spans more than a warp of vectors. Downstream in [ROCm/rocmlirTriton](https://github.com/ROCm/rocmlirTriton) this took down a whole CI tuning stage on gfx950: a generated GEMM kernel with a 1x2048 f16 A tile died on `PaddedSharedEncodingAttr::verify` with "Broadcasting in offset dimension is not supported".

The function divides `warpSize` by `contigLanes` in two places. Once `contigLanes > warpSize` that quotient truncates to zero and both guards that depend on it stop working. `requiredRows` collapses to zero, so `xWayConflicts` always reports one and the "too few rows to stagger" path never triggers. The `useBestWrap` condition degenerates to `nonContigDim >= 0`, which is always true.

`wrap` is then forced to 16 even for a tile with a single row. Bases are added for rows 1, 2, 4 and 8 that the tile does not have, the resulting linear layout broadcasts in the offset dimension, and the verifier rejects it. In an assertions build that aborts rather than falling back to a layout that would have worked.

This compares both guards scaled by `contigLanes` instead of dividing `warpSize` by it, and additionally requires at least `bestWrap` rows before staggering over that many.

The added lit test is the failing case reduced to a dot whose A operand is a single row of 2048 f16 elements, which is 256 vectors of 8 against a warp size of 64. It aborts `triton-opt` without this change and passes with it. The failing call chain is `PipelinePass` -> `expandLoops` -> `lowerLoops` -> `lowerLoop` -> `getSharedEncIfAllUsersAreDotEnc` -> `composePaddedLayout` -> `composePaddedLayoutForAsyncCopyCDNA4`.

One caveat worth stating: this fixes one of at least two causes behind that same broadcasting error. Across 70 shape and dtype combinations it takes aborts from 8 down to 3, and the 3 that remain reach the symptom through a different arithmetic path.

Reviewed internally at AMD as part of the downstream fix in https://github.com/ROCm/rocmlirTriton/pull/508.

Thanks for bringing this up and working on a fix! However, the scaling of the values looks like we are plastering over the issue instead of fixing it. I think even after the scaling it breaks if your nonContigDim is < 8 for fp16? (Maybe those are your other non working cases)

Can you try if clamping `contigLanes`, like shown below, fixes your issues? I haven't looked at this function for a while but it looks like a more sound fix to me.
```cpp
  unsigned contigLanes = std::clamp(contigDim / vecSize, 1u, warpSize);
```
