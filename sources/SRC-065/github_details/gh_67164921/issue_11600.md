# [Issue #11600] `tl.gather` on a small tensor with more than one warp trips the `isWarpLocal` assertion in 3.8.0

source: https://github.com/triton-lang/triton/issues/11600
state: closed | updated: 2026-09-05T11:05:34Z
labels: 

## 正文

### Describe the bug

On the 3.8.0 wheel a valid `tl.gather` crashes the compiler when the tensor is small and there is more than one warp:

```
python: lib/Dialect/TritonGPU/Transforms/OptimizeThreadLocality.cpp:220: LogicalResult setOptimizedGatherLayout(GatherOp, RewriterBase &): Assertion `GatherLoweringHelper(op).isWarpLocal()' failed.
```

```python
import torch, triton, triton.language as tl

@triton.jit
def k(out_ptr, x_ptr, SRC: tl.constexpr, IDX: tl.constexpr, R: tl.constexpr):
    src = tl.load(x_ptr + tl.reshape(tl.arange(0, R * SRC), (R, SRC)))
    idx = tl.reshape(tl.arange(0, R * IDX), (R, IDX)) % SRC
    tl.store(out_ptr + tl.reshape(tl.arange(0, R * IDX), (R, IDX)), tl.gather(src, idx, 1))

x = torch.arange(4096, dtype=torch.int32, device="cuda")
out = torch.zeros(4096, dtype=torch.int32, device="cuda")
k[(1,)](out, x, SRC=2, IDX=8, R=8, num_warps=2)   # asserts; num_warps=1 is fine
```

Sweeping `R in {1,2,8}`, `SRC in {2,4,8}`, `IDX in {2,8,32}`, `num_warps in {1,2,4}` on an RTX PRO 6000 (sm_120), 15 of the 81 combinations assert, all with `num_warps >= 2`. In each of them `setOptimizedGatherLayout` runs out of non-gather dimensions to place warps on and then does `warpsPerCTA[axis] *= warpsToAlloc` under the comment "Overflow by broadcasting along the gather axis", so the layout it builds has more than one warp along the gather axis, which is what `isWarpLocal` rejects. #6958 was the rank-1 case of the same assertion.

On main at e1f944a7a the same programs compile and give the right result (all 81 match the interpreter), so I think #11541 changed the linear layout enough that the check now passes. The release branch still has the assert, and 3.8.0 is what `pip install triton` gives today. If a 3.8.1 is planned, a small fix that checks the layout it built before rewriting and returns `failure()` otherwise (the lowering already falls back to shared memory) would cover it; I have it ready with a lit test if that is the preferred shape.

The programs came out of a differential fuzzer (4-D gathers with a longer index tensor along the axis); the kernel above is the reduction.

### Environment details

Triton 3.8.0 (PyPI wheel), torch 2.11.0+cu128, NVIDIA RTX PRO 6000 Blackwell (sm_120), Ubuntu 24.04. Not reproducible on main at e1f944a7a.


## 评论 (2)

### alepot55 · 2026-09-05

Correction on the main side: it is not #11541 that makes these compile on main, it is #10838 ("Fix gather locality for larger index tensors"), which sizes the layout along the gather axis by `max(src, idx)` instead of `src`. With the release's `src`-only sizing the extent along the axis equals the index length exactly, so the leftover warp basis is not clipped and `isWarpLocal` rejects the layout; with `max` the extent is larger, the basis is clipped to zero and the same shapes come out warp local. I checked that by porting `setOptimizedGatherLayout` and the three conditions of `isWarpLocal` to Python and sweeping both versions over the 81 combinations above and 8192 4-D ones: the release version fails the 15, the main version is warp local on all of them. So the fix already exists and a 3.8.1 would only need #10838 backported.
