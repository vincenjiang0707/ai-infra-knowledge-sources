# [PR #10676] [TRITONGPU] Support two-cta mode

## 正文

Enable two-CTA MMAv5 for descriptor-loaded operands, including pairs in larger CTA clusters. Synchronize TMA loads and TMEM accumulator reuse; unsupported producers and narrow shapes fall back to one-CTA MMA. Two-CTA warp specialization follows in #10812.

Tutorial 09 on GB200, measured on this branch at [`8cae4086ab`](https://github.com/triton-lang/triton/commit/8cae4086aba81da5be6ca57e7963c7c47d82034d). FP16, FP32 accumulation, `M=N=8192`; 48 autotuning configurations per variant. **TFLOPS** (higher is better):

| K | cuBLASLt | 1 CTA | 1 CTA + WS | 2 CTAs |
| --: | --: | --: | --: | --: |
| 64 | 357.3 | 328.2 | 329.4 | 321.9 |
| 512 | 1010.7 | 919.7 | 1072.7 | 989.3 |
| 2048 | 1252.8 | 1160.6 | 1245.4 | 1242.6 |
| 8192 | 1306.7 | 1187.8 | 1247.8 | 1309.7 |

Median of two runs, each with 30 rotating CUDA-graph rounds and 32 launches per graph after warmup; host setup excluded. cuBLASLt uses its first heuristic with 32 MiB workspace.

Validation: build, four lit tests, and numerical/code-generation checks for all 12 measured Triton kernels passed; two-CTA MMA confirmed, no automatic TMA multicast. Known ConSan limitations: TMEM allocation poisoning and unresolved mixed-consumer reports.

The gather's `x_offsets` operand is a 1-D tensor, so cloning it with `newLayout` (the 2-D RHS tile layout) produces an invalid/mismatched layout for the offsets before the op is retyped. This can make eligible gather-fed matmuls fail verification or compile incorrectly; either reject gathers here or preserve an operand-specific layout for the index tensor.
