# [Issue #11889] Why does tl.dot reject uint8 inputs despite unsigned INT8 support in tcgen05.mma

source: https://github.com/triton-lang/triton/issues/11889
state: open | updated: 2026-09-23T23:33:43Z
labels: 

## 正文

I'd like to understand why tl.dot does not support uint8 × uint8 → int32 matrix multiplication.
The [tl.dot documentation](https://triton-lang.org/main/python-api/generated/triton.language.dot.html) lists int8, but not uint8, as a supported integer input type. In the current [semantic.py](https://github.com/triton-lang/triton/blob/main/python/triton/language/semantic.py), the initial dtype checks include tl.uint8, but the subsequent integer branch explicitly requires:

`assert lhs.type.scalar == tl.int8, "only int8 supported!"`

Meanwhile, NVIDIA's PTX documentation describes unsigned 8-bit A/B operands for tcgen05.mma.kind::i8, selected through the [instruction descriptor](https://docs.nvidia.com/cuda/parallel-thread-execution/#tcgen05-instruction-descriptor), with signed 32-bit accumulation. This is available on supported targets such as sm_100a; see the [instruction specification and target restrictions](https://docs.nvidia.com/cuda/parallel-thread-execution/#tcgen05-mma-instructions-mma).

Could you clarify:
1. Is this an intentional API restriction, or a currently unimplemented feature?
2. What changes would be needed beyond the frontend check—for example, preserving operand signedness through the IR and handling it in NVIDIA lowering/instruction descriptors?
3. Would architecture-specific support for uint8 × uint8 → int32 be appropriate, and is there an existing issue or implementation effort tracking it?
4. Is there a recommended way to perform this operation in Triton today while preserving unsigned semantics and using integer Tensor Cores?
I understand that hardware instruction support alone does not imply that the corresponding compiler path is implemented.

Thanks!

### he-yufeng · 2026-09-23

Read the whole path on current main (`semantic.py` -> `tt.dot` -> `AccelerateMatmul` -> `MMAv5`/`MMAv2`). Short version: it is an unimplemented feature, not an intentional restriction, and the NVIDIA side is already plumbed for it. The gap is entirely on the frontend plus one unset attribute.

The chain today:

1. `python/triton/language/semantic.py:1581` is the only hard stop: the integer branch asserts `lhs.type.scalar == tl.int8`.
2. `tt.dot` itself is signedness-agnostic. The verifier (`lib/Dialect/Triton/IR/Ops.cpp:353`) only checks that A and B have the same bit width; a `ui8` tensor flows through the type system fine.
3. On sm_100 the hardware distinction you cite is already modeled: `TTNG_TCGen5MMAOp` carries an `is_unsigned` attribute (`include/triton/Dialect/TritonNvidiaGPU/IR/TritonNvidiaGPUOps.td:699`), and the LLVM lowering encodes it into exactly the instruction-descriptor bits you linked (`third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/DotOpToLLVM/MMAv5.cpp:193`: unsigned -> 0, signed -> 1). But the `tt.dot` -> `tc_gen5_mma` conversion never sets it: `lib/Dialect/TritonGPU/Transforms/AccelerateMatmul.cpp:715` builds the op with the builder default (signed).
4. On the sm80/sm90 path (`MMAv2.cpp`) the PTX strings hardcode `s8.s8` (`:342`, `:361`), so that path would need the `u8` instruction variants selected the same way.

To your questions, concretely:

1. Unimplemented, not policy. The backend authors left the signedness bit in place; the frontend just never lets a `ui8` through.
2. A real implementation is three edits plus tests: accept `tl.uint8` in the frontend integer branch (and decide the mixed-signedness rule, I would require both operands same-signed); set `is_unsigned` from the operand element type in `AccelerateMatmul`; select the `u8` `mma.sync` variants in `MMAv2` from the same bit. Lit tests for the conversion need no GPU; numeric truth on tcgen05/mma.sync does.
3. Architecture-gating to sm_100 only would be defensible for a first slice since the descriptor path is already there, but the `mma.sync` variant is so mechanical that doing both at once is cleaner.
4. Nothing on tensor cores today. The workable stand-in on the int8 path is the bias-correct decomposition: with `x_u = x_s + 128` per operand, `u8 @ u8 = i8 @ i8' + 128 * rowsum(i8') + 128 * colsum(i8) + 16384 * K`, i.e. one signed tensor-core matmul plus two reduction terms. You pay for the extra reductions, so it only wins when the matmul dominates.

One sharper finding while reading this: the frontend gate is asymmetric. It asserts on `lhs` only, so `tl.dot(int8, uint8)` passes the frontend today and computes with signed semantics on both operands, silently wrong for any rhs value >= 128. Whatever the resolution on uint8 support, that mix should be rejected explicitly.

Happy to write the PR for the frontend gate plus the `is_unsigned` plumbing if a maintainer confirms the direction; I can cover the lit/conversion tests on CPU, and I would call out the lack of GPU-side numeric verification in the PR rather than paper over it.
