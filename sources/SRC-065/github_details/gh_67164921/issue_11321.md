# [Issue #11321] AMD CanonicalizePointers crashes on tt.pointer_range=32 pointer live across control-flow merge with nested early return.

source: https://github.com/triton-lang/triton/issues/11321
state: open | updated: 2026-09-24T09:34:11Z
labels: bug

## 正文

### Describe the bug

The AMD TTIR-to-TTGIR pipeline crashes when a small-tensor pointer with
`tt.pointer_range = 32` is derived on both sides of runtime control flow and a
nested path returns before the merge block.

This was first seen in fuzz-generated matrix transpose kernels. The original,
untransformed transpose kernel compiles for AMD with the same runtime pointer
attributes. The transformed variants compile and run on NVIDIA, but AMD fails in
`make_ttgir`.

The failure is not specific to stores: both an output pointer and an input
pointer can trigger it.

### Reproduce
Run this on an AMD system:
```
import torch
import triton
import triton.language as tl


@triton.jit
def repro_output_pointer(switch_ptr, output):
    values = tl.load(switch_ptr + tl.arange(0, 2))
    zero, one = tl.split(values)
    true_cond = zero < one
    false_cond = zero > one
    offsets = tl.arange(0, 32)

    if true_cond:
        output_ptrs = output + offsets + zero
    else:
        output_ptrs = output + offsets
        if false_cond:
            return

    if true_cond:
        tl.store(output_ptrs, offsets)


switch = torch.tensor([0, 1], dtype=torch.int32, device="cuda")
output = torch.empty(32, dtype=torch.int32, device="cuda")
repro_output_pointer[(1,)](switch, output)
torch.cuda.synchronize()
```

### Environment details

- Triton: 3.7.1
- AMD Instinct MI308X

## 评论 (1)

### alexxony · 2026-09-24

Confirmed this is a version-lag artifact, not a live bug.

Reproduced via CPU-only cross-compilation with `GPUTarget("hip", "gfx942", 64)` (no AMD hardware needed for `make_ttgir`) with `knobs.amd.use_buffer_ops = True` and `tt.pointer_range` manually attached to both pointer args — verified the attribute actually landed (2 occurrences in the TTIR) and that `TritonAMDGPUCanonicalizePointers` actually fired (buffer_load/buffer_store ops present in the TTGIR) before drawing any conclusion.

- **triton 3.7.1** (the version in this report): crash reproduces exactly as described — `PassManager::run failed` on `TritonAMDGPUCanonicalizePointers` for `@repro_output_pointer`.
- **triton 3.8.0** (pip, current): same repro compiles clean through to `hsaco`, no crash.

Something between 3.7.1 and 3.8.0 fixed this. I didn't pin down the exact PR (checked #10804, which touches the same pass but for a different symptom — asymmetric `arith.select` verifier failure, not this early-return/merge-block assert). Leaving this for a maintainer to close or link the actual fix.
