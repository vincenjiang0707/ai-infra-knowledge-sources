> **Updated after review feedback.** Two corrections to what was originally filed:
> 1. **The reproducer needs one extra step** — the stock image lacks the unversioned `librocprofiler-sdk.so`, so Proton's constructor `dlopen` fails, no client registers, and nothing deadlocks. Create the symlink (below) and it reproduces. A GPU is **not** required.
> 2. **This is already fixed on `main` by #11009** (merged 2026-07-28) — but that fix is **not in the `v3.8.0` release tag**, which still has the offending call at `RocprofSDKProfiler.cpp:905`. So the open ask is a 3.8.x backport, not a new fix.

## Summary

On ROCm, a process that imports `torch` before `triton.profiler` **hangs forever at `exit()`**. Proton's rocprofiler-sdk tool finalizer re-enters rocprofiler-sdk from inside a rocprofiler-sdk client-finalizer callback, deadlocking on a non-recursive mutex the caller already holds.

No Proton session is required. No GPU work is required. Two imports are the entire reproducer.

## Reproducer

```python
import torch
import triton.profiler   # process never exits
```

**Precondition:** the unversioned `librocprofiler-sdk.so` must resolve. The `rocm/pytorch` wheel-layout images ship only `librocprofiler-sdk.so.1`, so on a stock image Proton's constructor `dlopen` fails, the `catch (...)` swallows it, no rocprofiler-sdk client registers, and there is nothing to deadlock. A classic `/opt/rocm` install ships both spellings and needs no such step (inferred, not verified — no image on hand pairs a classic layout with Triton 3.8.0).

```console
$ docker run -it rocm/pytorch:rocm10.0_ubuntu26.04_py3.14_pytorch_release_2.13.0

# stock image: dlopen fails, so no client, so no deadlock
root@...:/# timeout 60 python -c "import torch; import triton.profiler"; echo "rc=$?"
rc=0

root@...:/# cd /opt/venv/lib/python3.14/site-packages/_rocm_sdk_core/lib
root@...:/# ln -s librocprofiler-sdk.so.1 librocprofiler-sdk.so

root@...:/# timeout 60 python -c "import torch; import triton.profiler"; echo "rc=$?"
rc=124        # 124 = timed out; hangs forever without the timeout

root@...:/# timeout 60 python -c "import triton.profiler; import torch"; echo "rc=$?"
rc=0          # reversed order is fine

root@...:/# timeout 60 python -c "import torch"; echo "rc=$?"
rc=0          # either alone is fine
```

**No GPU is required.** The hang above reproduces in a container started with no `--device /dev/kfd` and no `--device /dev/dri`.

## Stack of the wedged process

`gdb -p <pid> -batch -ex 'thread 1' -ex bt`, main thread:

```
#0  futex_wait (futex_word=0x... <rocprofiler::registration::(anonymous namespace)::get_registration_mutex()::_v>, expected=2)
#1  __GI___lll_lock_wait
#3  ___pthread_mutex_lock (mutex=0x... <...get_registration_mutex()::_v>)
#4  rocprofiler::registration::(anonymous namespace)::invoke_client_finalizer(rocprofiler_client_id_t)
      from .../_rocm_sdk_core/lib/librocprofiler-sdk.so
#5  proton::(anonymous namespace)::protonToolFini (toolData=0x... <proton::(anonymous namespace)::getRuntimeState()::state>)
      at .../third_party/proton/csrc/lib/Profiler/RocprofSDK/RocprofSDKProfiler.cpp:905
#6  rocprofiler::registration::(anonymous namespace)::invoke_client_finalizer(rocprofiler_client_id_t)
#7  std::call_once<rocprofiler::registration::finalize()::$_0> lambda
#8  __pthread_once_slow (once_control=0x... <rocprofiler::registration::finalize()::_once>)
#10 rocprofiler::registration::finalize()
#11 __run_exit_handlers (run_list_atexit=true, run_dtors=true) at ./stdlib/exit.c:118
#12 __GI_exit at ./stdlib/exit.c:148
#13 __libc_start_call_main
```

Frame 6 takes `get_registration_mutex()`; frame 4 tries to take it again on the same thread. `pthread_mutex_t` there is not recursive, so it blocks permanently.

## Mechanism

`RocprofSDKProfiler`'s constructor calls `rocprofiler_force_configure`, and `protonRocprofSDKLoadHook` (an `__attribute__((constructor))`) touches the singleton at `libproton.so` load — i.e. at `import triton.profiler`. That registers Proton as a rocprofiler-sdk client.

When `torch` is imported first, HSA is already initialised by the time that registration happens. At `exit()`, rocprofiler-sdk's atexit handler runs `registration::finalize()`, takes the registration mutex, and invokes each client's finalizer; `protonToolFini` then calls back into rocprofiler-sdk (it calls `stopContext` / `flushBuffer` and `pcSampling` teardown), which re-enters the locked region.

Importing Proton first avoids it, which is consistent with the ordering the source comment above `forceConfigure` already recommends — but that comment frames late configuration as *degraded capture quality* ("silently skip kernel-dispatch buffer tracing on already-existing queues"), not as a hang. The hang is a much harsher outcome and is not documented anywhere.

## Why this is easy to miss

The failure happens **after everything succeeded**. In our case a Proton capture ran to completion, the `.hatchet` was written and correct (15 kernel launches, valid timings), the payload printed its own `PASS`, and only then did the process fail to exit. There is no exception, no error output, and no incomplete artifact — under a test runner or CI job it looks like an unexplained hang with a green-looking result on disk.

It also affects far more than Proton users: `import torch` before `import triton.profiler` is an ordinary thing to write, and on this stack it is enough.

## Suggested fix

`protonToolFini` should not call back into rocprofiler-sdk while running as a rocprofiler-sdk client finalizer — the SDK is already tearing that client down. Skipping the `stopContext` / `flushBuffer` / PC-sampling teardown when invoked from the finalizer path (as opposed to an explicit `proton.finalize()`) would break the cycle.

I have also filed this against rocprofiler-sdk, since holding a non-recursive registration mutex across a client callback makes this failure mode reachable by any client that re-enters the API: https://github.com/ROCm/rocm-systems/issues/11123

Downstream tracking issue with the full investigation: https://github.com/ROCm/aorta/issues/434

## The fix is #11009, and the line numbers confirm it exactly

My gdb frame was:

```
#5  proton::(anonymous namespace)::protonToolFini
      at .../third_party/proton/csrc/lib/Profiler/RocprofSDK/RocprofSDKProfiler.cpp:905
```

And `RocprofSDKProfiler.cpp` at tag **`v3.8.0`**, lines 903-906:

```cpp
  rocprofiler::flushBuffer<false>(state->kernelBuffer);
  if (state->finalizeFunc && state->clientId) {
    state->finalizeFunc(*state->clientId);   // <-- line 905
  }
```

That is precisely the call #11009 deletes, and it is the frame that re-enters `get_registration_mutex()` while `registration::finalize()` already holds it. So the diagnosis and your suggested fix agree.

`main` has zero occurrences of `finalizeFunc` today, so main is clean. `v3.8.0` still has it at line 905.
