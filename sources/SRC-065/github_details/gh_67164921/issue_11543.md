### choi3171 · 2026-09-05

can be reached via python API, repro:

```python
import triton, triton.language as tl
from triton.experimental import gluon
from triton.experimental.gluon import language as ttgl
from triton.runtime.jit import MockTensor

@gluon.jit
def kernel(a, b, N: ttgl.constexpr):
    idx = ttgl.arange(0, N, ttgl.AutoLayout())
    ttgl.store(ttgl.set_auto_layout(b + idx, ttgl.CoalescedLayout()),
               ttgl.load(ttgl.set_auto_layout(a + idx, ttgl.CoalescedLayout())))

k = kernel.warmup(MockTensor(tl.float32), MockTensor(tl.float32), 128, grid=(1, ))
open("kernel.ttir", "w").write(k.asm["source"])   # what the front end emitted
triton.compile("kernel.ttir")                     # boom
```

```
Unimplemented usage of getCGALayout
UNREACHABLE executed at lib/Dialect/TritonGPU/IR/Dialect.cpp:374!
note: Pipeline failed while executing [`TritonGPUCoalesce` on 'builtin.module' operation]
```

The IR is fine. Compiled as a kernel it goes through `gluon_to_ttgir`, which resolves the encoding first. The routing is what's wrong: `IRSource` tags every IR file as Triton whatever is in it, while `ir.load_dialects()` has `GluonDialect` registered, so the file parses and then gets the Triton stage list, `-tritongpu-coalesce` included.

```python
class IRSource:

    def __init__(self, path, context, backend):
        ...
        self.language = Language.TRITON      # regardless of the file's contents
        self.src = path.read_text()
        ir.load_dialects(context)            # registers GluonDialect
```

`triton.compile()` has no `language` argument either, so a caller cannot correct it. A file holding Gluon encodings therefore runs `make_ttgir`, whose passes assume those encodings are already resolved, and `-tritongpu-coalesce` aborts on the first one it meets. Either such a file should go to `gluon_to_ttgir`, or it should be rejected. Reproduces on main and on the 3.8.0 wheel.

Routing the file through `gluon_to_ttgir` instead gives the same output as compiling the kernel from source, but doing that properly needs a few decisions I did not want to make on my own:

* how a file is recognised as Gluon IR
* where such a file enters the pipeline, given that the Gluon stage list has no entry before `ttgir`
* whether `getCGALayout` should keep asserting on an encoding it can reach

### choi3171 · 2026-09-06

What I wanted to report is that the IR file path doesn't handle gluon well. Launching the kernel directly doesn't go through `IRSource`, so it never sees this. I thought that this can be reached via python API, because the IR file of my repro is not hand-written. But I agree that this path is not so practical. 

Btw, after your comment I looked for other ways a gluon encoding can still be around when a TritonGPU pass runs. As far as I can tell there are three ways to get there from python:

1. An IR file. What I reported. 
2. A backend that misses `gluon-infer-coalesced-encodings`. AMD still does, I ran into it while looking at this and opened #11599.
3. An encoding that cannot be resolved, which is already handled. `doubleCheckEncodings` fails the pass with `'gluon.set_auto_layout' op Failed to infer return type`.

Running the pass on its own under `triton-opt` is a fourth (original repro). Putting `-gluon-infer-coalesced-encodings -gluon-resolve-auto-encodings` in front resolves it to `#ttg.blocked` and coalesce is fine, so nothing is wrong with the pass itself.

Also a triton kernel cannot produce these encodings at all, they only come from the gluon frontend. So 1 is the only one a user hits without meaning to. Fix or not is your call. I would not claim that list is exhaustive though.
