# [Issue #10730] fp16 minimum/maximum with Python float scalar literals promote through fp32

source: https://github.com/triton-lang/triton/issues/10730
state: closed | updated: 2026-09-23T12:53:18Z
labels: 

## 正文

Hi! I may be missing some intended type-promotion behavior here, but I noticed that `tl.minimum`/`tl.maximum` behave differently from other fp16 binary ops when one operand is a Python float scalar literal.

For an fp16 tensor, this natural ReLU/clamp spelling:

```python
y = tl.maximum(x, 0.0)
z = tl.minimum(y, 6.0)
```

appears to promote through fp32, while equivalent spellings using integer literals or typed fp16 constants keep the operation in fp16 and lower to packed `f16x2` min/max.

### Minimal repro

```python
import torch
import triton
import triton.language as tl

N = 1024

@triton.jit
def max_float(out, x, BLOCK: tl.constexpr):
    offs = tl.arange(0, BLOCK)
    a = tl.load(x + offs)
    tl.store(out + offs, tl.maximum(a, 0.0))

@triton.jit
def max_int(out, x, BLOCK: tl.constexpr):
    offs = tl.arange(0, BLOCK)
    a = tl.load(x + offs)
    tl.store(out + offs, tl.maximum(a, 0))

x = torch.randn((N,), device="cuda", dtype=torch.float16)
out = torch.empty_like(x)

max_float[(1,)](out, x, BLOCK=N, num_warps=8)
max_int[(1,)](out, x, BLOCK=N, num_warps=8)
```

### Observed lowering

For `tl.maximum(a, 0.0)`:

```text
PTX counts:
  max.f16x2: 0
  max.f32: 4
  cvt.f32.f16: 4

SASS includes:
  HADD2.F32 ...        // unpack fp16 lanes to fp32
  FMNMX ...
  F2FP.F16.F32.PACK_AB
```

For `tl.maximum(a, 0)`:

```text
PTX counts:
  max.f16x2: 2
  max.f32: 0
  cvt.f32.f16: 0

SASS uses packed half min/max
```

Similarly, `tl.minimum(a, 6.0)` lowers through fp32, while `tl.minimum(a, 6)` lowers to `min.f16x2`.

### Compile-time consequence

This also shows up as a loop-carried type regression:

```python
@triton.jit
def clamp_float_loop(out, x, BLOCK: tl.constexpr, REPS: tl.constexpr):
    offs = tl.arange(0, BLOCK)
    v = tl.load(x + offs)  # fp16
    for _ in range(REPS):
        v = tl.minimum(tl.maximum(v, 0.0), 6.0)
    tl.store(out + offs, v)
```

This fails to compile:

```text
AssertionError("Loop-carried variable v has initial type <['1024'], fp16> but is re-assigned to <['1024'], fp32> in loop! Please make sure that the type stays consistent.")
```

Changing the literals to `0` and `6` compiles and lowers to `max.f16x2` / `min.f16x2`.

### Why I think this might be unintended

Other fp16 tensor + Python float scalar operations seem to preserve packed fp16 lowering:

```python
a + 1.0       # HADD2
a * 0.5       # HMUL2
a * 0.5 + b   # HFMA2
```

So the behavior seems specific to `minimum` / `maximum` with Python float scalar literals.

Looking at current `origin/main`, `tl.minimum` / `tl.maximum` appear to call `_semantic.to_tensor()` on both operands before reaching `binary_op_type_checking_impl`. That turns `0.0` / `6.0` into 0-d fp32 tensors, so the scalar-does-not-participate-in-promotion rule no longer sees them as Python scalars. Is that the intended behavior?

### Environment

I reproduced this on:

```text
triton 3.7.1 from PyPI
GPU: NVIDIA GeForce RTX 4090, sm_89
torch 2.6.0+cu124
```

I also checked current `origin/main` source at:

```text
70e0929eeb8aa930db3a88404fd0a81ebe8d0c7e
```

and the `minimum` / `maximum` frontend path still appears to pre-materialize scalar literals with `_semantic.to_tensor()`.
