# [Issue #11612] [FuseNestedLoops] a flattened loop with one inner scf.for whose carried value is used afterwards crashes the pass

source: https://github.com/triton-lang/triton/issues/11612
state: closed | updated: 2026-09-18T22:41:19Z
labels: 

## 正文

`tritongpu-fuse-nested-loops` fails on a `tt.flatten` loop whose body holds an
`scf.while` next to an `scf.for` that carries a value. On 3.8.0 and 3.7.1, sm_120, the
pass dies on an assertion inside MLIR, which the crash recovery context turns into
`RuntimeError: PassManager::run failed`:

```
ilist_iterator.h:168: Assertion `!NodePtr->isKnownSentinel()' failed.
error: A signal was caught while processing the MLIR module ... marking pass as failed
note: Pipeline failed while executing [`TritonGPUFuseNestedLoops` on 'builtin.module']
```

On a slightly larger kernel the same pass instead gets as far as building an `scf.if`
whose yield does not match its results, and the verifier stops it:

```
error: 'scf.if' op along control flow edge from Operation scf.yield to parent:
       region branch point has 1 operands, but region successor needs 2 inputs
```

Dropping `flatten=True`, or the `while`, or the loop-carried value of the inner `for`,
all compile, and the order of the two inner loops does not matter.

```python
import torch
import triton
import triton.language as tl


@triton.jit
def kernel(out):
    for _i in tl.range(0, 2, flatten=True):
        acc = 0
        for j in tl.range(0, 4):  # scf.for, one result
            acc = acc + j
        w = 0
        while w < 0:  # scf.while, zero trips
            w = w + 1
        tl.store(out, acc + w)


out = torch.zeros(1, dtype=torch.int32, device="cuda")
kernel[(1,)](out)
```

The TTGIR the pass receives, which reproduces on its own with just
`tritongpu-fuse-nested-loops`:

```mlir
module attributes {"ttg.num-ctas" = 1 : i32, "ttg.num-warps" = 4 : i32, ttg.target = "cuda:120", "ttg.threads-per-warp" = 32 : i32} {
  tt.func public @kernel(%out: !tt.ptr<i32> {tt.divisibility = 16 : i32}) attributes {noinline = false} {
    %c4_i32 = arith.constant 4 : i32
    %c0_i32 = arith.constant 0 : i32
    %c1_i32 = arith.constant 1 : i32
    %c2_i32 = arith.constant 2 : i32
    scf.for %_i = %c0_i32 to %c2_i32 step %c1_i32  : i32 {
      %acc = scf.for %j = %c0_i32 to %c4_i32 step %c1_i32 iter_args(%acc_0 = %c0_i32) -> (i32)  : i32 {
        %acc_1 = arith.addi %acc_0, %j : i32
        scf.yield %acc_1 : i32
      }
      %w = scf.while (%w_0 = %c0_i32) : (i32) -> i32 {
        %1 = arith.cmpi slt, %w_0, %c0_i32 : i32
        scf.condition(%1) %w_0 : i32
      } do {
      ^bb0(%w_0: i32):
        %w_1 = arith.addi %w_0, %c1_i32 : i32
        scf.yield %w_1 : i32
      }
      %0 = arith.addi %acc, %w : i32
      tt.store %out, %0 : !tt.ptr<i32>
    } {tt.flatten}
    tt.return
  }
}
```

`constructLoopNest` treats `scf.while` as a boundary of the analysis domain and restarts
there, but the `scf.while` is still an operation of the outer loop body that
`fuseOneLevel` has to split into a prologue and an epilogue, and that is where it goes
wrong. I have not pinned the exact line.

Same on 3.7.1, so it is not new in 3.8.0. Distinct from #11519 (no `llvm.assume` in the
module) and from #11601 (nothing is hoisted; the pass never finishes).


## 评论 (1)

### alepot55 · 2026-09-06

Simpler reproducer, no `while` at all: a flattened loop whose body is one inner `for` carrying a value that is used after it. Same assertion on 3.7.1 and 3.8.0 (sm_120); it compiles with `flatten=False`, and `TRITON_INTERPRET=1` gives 6.

```python
@triton.jit
def kernel(out):
    for _i in tl.range(0, 2, flatten=True):
        acc = 0
        for j in tl.range(0, 4):
            acc = acc + j
        tl.store(out, acc)
```

If the inner result is not used the loop is folded away before the pass and everything compiles; with two inner loops the outcome depends on which results are used (both used compiles, either one alone fails), so the shape the pass mishandles seems to be the epilogue that reads a carried value of an inner loop. The TTGIR the pass alone still crashes on is the same nest with the store removed:

```mlir
scf.for %arg1 = %c0_i32 to %c2_i32 step %c1_i32  : i32 {
  %0 = scf.for %arg2 = %c0_i32 to %c4_i32 step %c1_i32 iter_args(%arg3 = %c0_i32) -> (i32)  : i32 {
    %c0_i32_0 = arith.constant 0 : i32
    scf.yield %c0_i32_0 : i32
  }
} {tt.flatten}
```
