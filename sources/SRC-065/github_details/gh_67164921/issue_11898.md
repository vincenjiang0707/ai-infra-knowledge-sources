# [Issue #11898] Same-type fp8 arithmetic passes the frontend and fails in LLVM lowering

source: https://github.com/triton-lang/triton/issues/11898
state: open | updated: 2026-09-25T02:06:14Z
labels: 

## 正文

`computation_type_impl` returns the fp8 type itself for same-type fp8 operands (rule added in #4222 so `tl.where` works on fp8, and asserted in `test_fp8_div_mod_promotion`: `(x * y).dtype == tl.float8e5`). But no backend can lower fp8 arithmetic, so `+ - *`, unary `-`, comparisons, `x * 2`, and `tl.sum` on an fp8 tensor all fail late with a verifier error instead of a frontend diagnostic:

```python
@triton.jit
def kernel(X, Y):
    offs = tl.arange(0, 128)
    x = tl.load(X + offs)          # *fp8e4nv
    tl.store(Y + offs, x * 2)
```
```
error: 'llvm.fmul' op operand #0 must be floating point LLVM type ..., but got 'i8'
RuntimeError: PassManager::run failed
```

Same on sm90/sm100 and gfx942/gfx950. `tl.maximum`, `tl.abs`, `tl.where`, `/` (promoted to fp32) work. Before #4222 this was a frontend `TypeError` (#2640, where fp8 arithmetic was described as expected-unsupported).

Options: (a) raise a clear frontend error for arithmetic/comparison on same-type fp8 while keeping selection ops (`where`, `maximum`, ...) fp8, or (b) promote same-type fp8 to fp16 like mixed fp8 already does (dtype-visible change). Happy to send whichever is preferred.

### he-yufeng · 2026-09-21

Adjacent context from the div/mod side (#10883, which added the rule-2 upcast this issue cites): the current split personality comes from two independent rules. Rule 2 upcasts div/mod to fp32 because floats below 32 bits cannot lower those ops, while rule 6 (#4222) keeps same-type fp8 as fp8 for the selection ops that can lower. `+`, `-`, `*`, comparisons and `tl.sum` fall between the two: rule 6 hands them fp8 and no backend can lower that either, so they die at the LLVM verifier exactly as shown.

On the two options, (b) is the coherent one:

- It matches the mixed-fp8 rule right below, which already returns fp16 for fp8 x fp8 with different dtypes. Same-type would stop being a special case of its own.
- It matches the div/mod precedent: promote before evaluating, because the op does not exist at fp8. `x * 2`, `x + y`, comparisons and `tl.sum` start working instead of hard-erroring, and nothing that runs today regresses, since every one of those paths currently dies in lowering anyway.
- Option (a) is only the diagnostics half of the truth. It is zero-behavior-change (every affected expression errors today), but it permanently fences off arithmetic that fp8xfp16 kernels two lines over already do in fp16.

One thing to keep in mind for (b): `test_fp8_div_mod_promotion` currently asserts `(x * y).dtype == tl.float8e5`, which pins the rule-6 behavior this changes, so the test needs to move to fp16 with it. Comparisons probably want the same promotion rather than an fp8 compare op, for the same lowering reason.

Happy to implement (b) if that is the preferred direction and you are not already on it.

### he-yufeng · 2026-09-25

Implemented option (b) in #11950: same-type fp8 arithmetic now promotes to fp16 before evaluating, through an opt-in flag on the computation-type rule so the selection ops that lower at fp8 (maximum/minimum/where/clamp) keep the narrow type. `tl.sum` picks fp16 for fp8 inputs the same way it picks int32 for narrow ints. The `test_fp8_div_mod_promotion` pins moved to fp16 as you predicted, and a new frontend test pins the promotion plus the fp8-keeping controls, including TTIR-level evidence of the fp16 operands.
