# [PR #11156] Configure the target in the LLVM middle-end pipeline

source: https://github.com/triton-lang/triton/pull/11156
state: open | updated: 2026-09-24T16:14:05Z
labels: 

## 正文

The NVIDIA path ran the LLVM middle-end with no target configured, so
passes used CPU defaults with no notion of branch divergence and could
restructure CFGs unsafely around convergent op. 

This PR attaches the NVPTX triple and a real `TargetMachine` to the
middle-end pipeline, sharing `attach_target_triple` across backends (amd and nvidia).

### 39ali · 2026-08-03

@ThomasRaoux  That's what I expected too, but the pass's convergent check is narrower than
that: it only refuses when the block it wants to *duplicate* contains
convergent ops. It does not refuse to thread just because convergent ops exist
nearby.

In this kernel the block it duplicates is a small guard block with no
convergent ops in it, so the check passes. The convergent block (the
`bar.sync`/`ldmatrix` from the layout conversion) is never duplicated it,
it just ends up with a new incoming edge from another region of the CFG. Nothing
in the pass validates that, but the extra edge removes the merge point ptxas
needs to reconverge the warp before the `ldmatrix`, which then executes
partially converged.

Verified by bisection: `-opt-bisect-limit` flips the breakage exactly at
jump-threading, and plain `opt -passes='default<O3>'` on the pre-optimization
IR reproduces it outside Triton. I'll file the missing check upstream; this PR
is the interim mitigation until the LLVM pin includes it.

So the failures appear to be a ptxas bug, at least from my investigation. What appears to occur is when the target information is provided the machine model used assumes that spills are possible and disable parts of the SLP vectorizer, which seems to expose a bug in ptxas. This PR which changes the cost modeling for NVPTX in LLVM will hide the issue, although of course it won't fix it (https://github.com/llvm/llvm-project/pull/216755).
