### Describe the bug

### Describe the bug

Running `python/tutorials/02-fused-softmax.py` in a clean Python process causes a CUDA out-of-memory error on a 6 GiB RTX 3060 Laptop GPU.

The largest benchmark shape (`M=4096, N=12672`) succeeds when tested alone. However, the complete shape sweep fails during the `naive_softmax` benchmark around `N=3712`.

Instrumentation shows that active allocated memory remains around 16 MiB between benchmark cases, while reserved memory increases across cases:

```text
N=256 provider=triton allocated=16 MiB reserved=42 MiB free=5060 MiB
N=256 provider=torch allocated=16 MiB reserved=318 MiB free=4772 MiB
N=256 provider=naive_softmax allocated=16 MiB reserved=594 MiB free=4496 MiB
...
N=3584 provider=naive_softmax allocated=16 MiB reserved=12278 MiB free=0 MiB
N=3712 provider=triton allocated=16 MiB reserved=12448 MiB free=0 MiB
N=3712 provider=torch allocated=16 MiB reserved=12506 MiB free=0 MiB
N=3712 provider=naive_softmax allocated=16 MiB reserved=12564 MiB free=0 MiB
```

This suggests that memory is accumulating across benchmark cases rather than the largest input being too large by itself.

The fused-softmax benchmark creates and sets a new stream inside every benchmark invocation:

```python
stream = getattr(torch, DEVICE.type).Stream()
getattr(torch, DEVICE.type).set_stream(stream)
```

I suspect that repeatedly creating streams may prevent allocations made by `triton.testing.do_bench` from being reused across benchmark cases. I have not yet confirmed this as the root cause.

### Steps to reproduce

1. Check out Triton commit`2074a1b8a5cd283ce584f8ebca825c4f0b215fc1`.
2. Run the tutorial in a clean Python process:
```powershell
$env:MPLBACKEND = "Agg"
python python/tutorials/02-fused-softmax.py
```
3. Observe the CUDA OOM during `naive_softmax`.
To observe the accumulation, add this before allocating `x` inside `benchmark`:
```python
free, total = torch.cuda.mem_get_info()
print(
    f"N={N} provider={provider} "
    f"allocated={torch.cuda.memory_allocated() / 2**20:.0f} MiB "
    f"reserved={torch.cuda.memory_reserved() / 2**20:.0f} MiB "
    f"free={free / 2**20:.0f} MiB",
    flush=True,
)
```
### Expected behavior
The benchmark should reuse or release temporary allocations between benchmark cases and complete when each individual input shape fits in GPU memory.

### Error

```text
torch.AcceleratorError: CUDA error: out of memory
```

The exception is reported by `di.synchronize()` inside `triton.testing.do_bench`, while benchmarking `naive_softmax`.

## 评论 (1)

### 404-notfoundjdx · 2026-09-09

I ran two additional controlled experiments in separate clean Python processes.

### 1. Remove only the per-invocation stream creation

I removed:

```python
stream = getattr(torch, DEVICE.type).Stream()
getattr(torch, DEVICE.type).set_stream(stream)
```

Memory accumulation became substantially slower, but the benchmark still failed at `N=10240`:

```text
N=9984 provider=triton allocated=16 MiB reserved=11730 MiB free=0 MiB
N=9984 provider=torch allocated=16 MiB reserved=11886 MiB free=0 MiB
N=9984 provider=naive_softmax allocated=16 MiB reserved=11886 MiB free=0 MiB
N=10112 provider=triton allocated=16 MiB reserved=12198 MiB free=0 MiB
N=10112 provider=torch allocated=16 MiB reserved=12356 MiB free=0 MiB
N=10112 provider=naive_softmax allocated=16 MiB reserved=12356 MiB free=0 MiB
N=10240 provider=triton allocated=16 MiB reserved=12672 MiB free=0 MiB
```

Without this change, the benchmark failed much earlier, around `N=3712`. This suggests that creating a new stream for every benchmark invocation aggravates the accumulation, but is not the only cause.
 
### 2. Remove the stream creation and clear unused cached memory between cases

I then added the following at the beginning of `benchmark`, before allocating `x`:

```python
torch.cuda.synchronize()
torch.cuda.empty_cache()
```

The complete benchmark finished successfully through `N=12672`.  Memory at the beginning of every case remained stable:

```text
N=256 provider=triton allocated=16 MiB reserved=20 MiB free=5082 MiB
N=256 provider=torch allocated=16 MiB reserved=20 MiB free=5082 MiB
N=256 provider=naive_softmax allocated=16 MiB reserved=20 MiB free=5082 MiB
...
N=12672 provider=triton allocated=16 MiB reserved=20 MiB free=5082 MiB
N=12672 provider=torch allocated=16 MiB reserved=20 MiB free=5082 MiB
N=12672 provider=naive_softmax allocated=16 MiB reserved=20 MiB free=5082 MiB
```

My current interpretation is that the monotonically increasing tensor shapes leave cached blocks that cannot be reused by later, larger shapes. Creating a different stream for each case makes this behavior considerably worse.

Since this was reproduced on Windows/WDDM, the allocator behavior may be platform-specific. Would clearing unused cached memory between benchmark configurations, reusing one stream, or reducing the benchmark sweep be the preferred fix for this tutorial?
