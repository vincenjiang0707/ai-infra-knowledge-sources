# [Issue #10924] Coalesce gives a store and its read-back different layouts (data race)

source: https://github.com/triton-lang/triton/issues/10924
state: closed | updated: 2026-09-23T13:00:35Z
labels: bug

## 正文

### Describe the bug

If a kernel writes a global buffer and then reads the same buffer back, `tritongpu-coalesce` can hand the store and the load different layouts. When that happens one thread reads back what another thread wrote, and there's no barrier in between, so it's a data race and the output comes out wrong (and different from run to run).

In the original code the store and the load share the same pointer and layout, so each thread just reads its own data. Coalesce is what splits them: it clamps the store to 128 bits per thread but leaves a load in the same group wider, and `warpsPerCTA` follows from that. `Membar` doesn't help, since it only  tracks shared memory and never sees a global buffer round-trip.

Repro with `triton-opt repro.mlir -tritongpu-coalesce`:

  ```mlir
  #blocked = #ttg.blocked<{sizePerThread = [1, 1], threadsPerWarp = [1, 32], warpsPerCTA = [1, 4], order = [1, 0]}>
  module attributes {"ttg.num-ctas" = 1 : i32, "ttg.num-warps" = 4 : i32, "ttg.threads-per-warp" = 32 : i32} {
    tt.func public @rb(%arg0: !tt.ptr<f32> {tt.divisibility = 16 : i32}, %arg1: !tt.ptr<f16> {tt.divisibility = 16 : i32}) {
      %cst = arith.constant dense<0.0> : tensor<8x256xf32, #blocked>
      %r = tt.make_range {end = 256 : i32, start = 0 : i32} : tensor<256xi32, #ttg.slice<{dim = 0, parent = #blocked}>>
      %re = tt.expand_dims %r {axis = 0 : i32} : tensor<256xi32, #ttg.slice<{dim = 0, parent = #blocked}>> -> tensor<1x256xi32, #blocked>
      %off = tt.broadcast %re : tensor<1x256xi32, #blocked> -> tensor<8x256xi32, #blocked>
      // a wide f16 load in the same block makes the group read layout [1, 8]
      %sp16 = tt.splat %arg1 : !tt.ptr<f16> -> tensor<8x256x!tt.ptr<f16>, #blocked>
      %p16 = tt.addptr %sp16, %off : tensor<8x256x!tt.ptr<f16>, #blocked>, tensor<8x256xi32, #blocked>
      %w = tt.load %p16 : tensor<8x256x!tt.ptr<f16>, #blocked>
      // write arg0, then read it back with the same pointer
      %sp = tt.splat %arg0 : !tt.ptr<f32> -> tensor<8x256x!tt.ptr<f32>, #blocked>
      %p = tt.addptr %sp, %off : tensor<8x256x!tt.ptr<f32>, #blocked>, tensor<8x256xi32, #blocked>
      tt.store %p, %cst : tensor<8x256x!tt.ptr<f32>, #blocked>
      %v = tt.load %p : tensor<8x256x!tt.ptr<f32>, #blocked>
      tt.return
    }
  }
  ```
The store comes out `sizePerThread = [1, 4], warpsPerCTA = [2, 2]` and the read-back `sizePerThread = [1, 8], warpsPerCTA = [4, 1]` - same memory, but the two layouts give the same element to different threads, with nothing synchronizing them. I'd expect the store and its read-back to keep one layout, or to have a barrier between them.

### Environment details

Triton: latest

### 0z5a · 2026-09-19

Following the review, I replaced the layout-clamping proposal with documentation and explicit-synchronization coverage in #11872 (Draft). Sharing a pointer does not require the coalescer to preserve thread ownership.

| Test | Reference | Result |
|---|---|---|
| Barrier-protected read-back, 256/1024 elements × 4/8 warps | Exact dense values | 4/4 passed on L20 |
| Generated NVIDIA code | Explicit block synchronization | `bar.sync` present |

Tested with Triton 3.8.0 plus the relevant main Python/test files; no native compiler rebuild. This is documentation/test coverage, not evidence of a coalescer defect or a performance fix.
