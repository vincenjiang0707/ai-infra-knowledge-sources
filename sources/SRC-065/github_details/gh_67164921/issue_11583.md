# [Issue #11583] Descriptor stores write past the tensor's inner extent, up to the next 16-byte boundary

source: https://github.com/triton-lang/triton/issues/11583
state: open | updated: 2026-09-22T06:21:41Z
labels: 

## 正文

`tensor_descriptor.store` documents that values outside the tensor bounds are ignored, and the interpreter clips them per element, but on an H100 (`e08ec196b`) a store of a block that ends beyond the inner extent `N` also writes the elements from `N` up to the next 16-byte boundary of the row. With a column slice of a larger tensor as the destination, that is another tensor's data.

```python
@triton.jit
def copy(out_d, a_d, N, BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr):
    off_m = tl.program_id(0) * BLOCK_M
    for ni in range(0, tl.cdiv(N, BLOCK_N)):
        v = a_d.load([off_m, ni * BLOCK_N])
        out_d.store([off_m, ni * BLOCK_N], v)

out = torch.full((32, 512), 7, dtype=dtype, device="cuda")
out_d = TensorDescriptor.from_tensor(out[:, :N], [32, 128])
copy[(1,)](out_d, a_d, N, BLOCK_M=32, BLOCK_N=128)
```

Columns of `out[:, N:]` no longer equal to 7 afterwards (same with a `tl.make_tensor_descriptor` built in the kernel with `shape=[M, N], strides=[512, 1]`):

```
int8   N=466: 14 columns written (466..479)      N=464: none
int16  N=470:  2 columns written (470..471)
int32  N=466:  2 columns written (466..467)      N=468: none
```

So the store clips at 16-byte granularity of the global address, and only inner extents that are a multiple of 16 bytes behave as documented. `TensorDescriptor` checks the base and the strides for 16-byte alignment but not `shape[-1] * itemsize`. Is the intended contract that the inner extent must be 16-byte aligned too (in which case the descriptor could assert it and the interpreter should match the device), or is this a lowering issue? Found with a differential fuzzer of descriptor kernels against `TRITON_INTERPRET=1`, where it shows up in about half of the programs with a ragged inner dimension.

### alexxony · 2026-09-16

Dug into the lowering to help narrow down whether this is a Triton codegen bug or hardware/undocumented-contract behavior (haven't had H100 access to re-run the repro myself, so treat the numbers above as unverified from my side, but the source-level trace is direct).

**`globalDim` is passed raw (element units) on both paths, no rounding anywhere in Triton:**
- Host path (`third_party/nvidia/backend/driver.c:205,641`): Python shape → `shapeInt` as-is → `cuTensorMapEncodeTiled(..., shapeInt, ...)`. Triton builds the value; NVIDIA's own encoder does the actual TMA descriptor encoding.
- Device path (`lib/Dialect/TritonNvidiaGPU/Transforms/TMAUtilities.cpp:187`): `globalDim(llvm::reverse(op.getShape()))`, raw. Only mutation is fp4Padded doubling (irrelevant here). Propagates unchanged through `TMAToLLVM.cpp:273`.

**Store lowering has no bounds/mask logic at all** (`TMALowering.cpp:100-119`, `lowerTMAStore`): just `LocalAlloc → FenceAsyncShared → AsyncTMACopyLocalToGlobal → TMAStoreWait`. The clip is 100% descriptor-driven, done by hardware — Triton isn't computing any mask here.

The only place Triton *does* clip in software is the non-TMA fallback (`RewriteTensorDescriptorToPointer.cpp:154`, `generateMaskFromOffsetRanges`) and the interpreter (`interpreter.py:928-930`), both of which mask at exact element granularity — consistent with this being TMA-specific, not a general Triton contract bug.

**CUDA driver docs** (`cuTensorMapEncodeTiled`) constrain `globalStrides` to a 16-byte multiple explicitly, but say nothing about `globalDim` needing 16B-aligned byte size — so this looks like an undocumented HW clip granularity rather than a documented precondition violation.

**Why this doesn't show up more often:** given the existing `globalStrides % 16 == 0` requirement, a tightly-packed tensor's row already has slack up to the next 16B boundary that belongs to itself — clipping into it is harmless. It only becomes visible when descriptor covers a narrower view than the underlying allocation (e.g. `out[:, :N]` of a wider buffer), so the padding bytes belong to someone else. That's probably why this hasn't surfaced in typical GEMM epilogues.

Given this, seems like a contract decision more than a bug fix: (A) reject unaligned `shape[-1]*itemsize` at descriptor construction (mirrors #10931's stride check, but breaks currently-working packed-tensor callers), (B) document the 16B clip and make the interpreter match device behavior, or (C) route unaligned-inner-extent descriptors through the SW fallback (precedent: #10898/#11736 already disable TMA for unaligned descriptors).

Happy to help implement whichever direction you land on.

Good catch — checked my run log and you're right that `out.stride()` can't be the trigger: `out = torch.full((32, 512), ...)`, so `out[:, :N].stride() == (512, 1)` regardless of `N`, and `512 * itemsize % 16 == 0` for every dtype tested.

The assert actually fired on `a`, the source tensor, not `out`. ### peterbell10 · 2026-09-21

I've had confirmation from NVIDIA that this is the TMA unit operating as designed. They assume that data outside of the declared tensor shape is padding, and can be safely overwritten.
