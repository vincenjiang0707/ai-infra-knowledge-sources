# [Issue #11614] Cross-warp reduce epilogue stores each warp's partial from all 32 lanes without a predicate (3.7.1 predicated it)

source: https://github.com/triton-lang/triton/issues/11614
state: open | updated: 2026-09-19T00:35:44Z
labels: 

## 正文

On 3.8.0 the shared-memory store that carries a warp's partial into the second level of a cross-warp
`tt.reduce` is emitted with no lane predicate, so all 32 lanes of the warp write the same
warp-uniform word. On 3.7.1 the same store, from the same source on the same GPU, is predicated on
lane 0 of the reduction axis. That is harmless for a combine whose butterfly leaves identical bits in
every lane, which is most of them, but the Welford combine `torch._inductor.runtime.triton_helpers`
emits for `var` and `var_mean` is not symmetric in f32, and there the lanes hold values that differ
in the last bits when the store runs.

The reproducer is a `tl.reduce` of the (mean, m2, weight) triple over an axis spanning eight warps,
with the combine copied verbatim from `triton_helpers.welford_combine`:

```python
import torch, triton, triton.language as tl


@triton.jit
def welford_combine(mean_1, m2_1, weight_1, mean_2, m2_2, weight_2):
    delta = tl.where(mean_1 == mean_2, 0.0, mean_2 - mean_1)
    new_weight = weight_1 + weight_2
    w2_over_w = tl.where(new_weight == 0.0, 0.0, weight_2 / new_weight)
    return (
        mean_1 + delta * w2_over_w,
        m2_1 + m2_2 + delta * delta * weight_1 * w2_over_w,
        new_weight,
    )


@triton.jit
def welford_kernel(MEAN, M2, W, OUT, BLOCK: tl.constexpr):
    idx = tl.arange(0, BLOCK)
    rmean, rm2, rw = tl.reduce(
        (tl.load(MEAN + idx), tl.load(M2 + idx), tl.load(W + idx)), 0, welford_combine
    )
    tl.store(OUT + 0, rmean)
    tl.store(OUT + 1, rm2)
    tl.store(OUT + 2, rw)


g = torch.Generator(device="cuda").manual_seed(20260906)
mean = torch.rand(256, generator=g, device="cuda") + 1.0
m2 = torch.rand(256, generator=g, device="cuda")
w = (torch.arange(256, device="cuda", dtype=torch.float32) % 7.0) + 1.0
out = torch.zeros(3, device="cuda")
k = welford_kernel[(1,)](mean, m2, w, out, BLOCK=256, num_warps=8)
print(k.asm["ptx"])
```

The epilogue it compiles to on 3.8.0, with `%r13` holding `%tid.x`, so the byte offset
`(tid >> 3) & 28` is `warp * 4` and the address is the same in all 32 lanes of a warp:

```
	shr.u32 	%r77, %r13, 3;
	and.b32 	%r78, %r77, 28;
	mov.b32 	%r79, global_smem;
	add.s32 	%r4, %r79, %r78;
	// begin inline asm
	st.shared::cta.b32 [ %r4 + 0 ], %r5;
	// end inline asm
	bar.sync 	0;
```

The same three lines on 3.7.1, where `%r24` is `%tid.x & 31`:

```
	setp.eq.b32 	%p1, %r24, 0;
	shr.u32 	%r88, %r22, 3;
	and.b32 	%r89, %r88, 28;
	mov.b32 	%r90, global_smem;
	add.s32 	%r4, %r90, %r89;
	// begin inline asm
	@%p1 st.shared.b32 [ %r4 + 0 ], %r5;
	// end inline asm
```

In the 3.8.0 LLVM IR it is `tail call void asm sideeffect "st.shared::cta.b32 [ $0 + 0 ], $1;",
"r,r"(...)` with no `i1` operand, against `"@$2 st.shared.b32 [ $0 + 0 ], $1;", "r,r,b"(..., i1
%134)` on 3.7.1, and in the module right after `convert-triton-gpu-to-llvm` it is
`llvm.inline_asm ... "st.shared::cta.b32 [ $0 + 0 ], $1;", "r,r" %177, %187 : (!llvm.ptr<3>,
vector<1xi32>) -> !llvm.void`, three of them, one per operand of the triple. The final global store
of the same kernel is predicated (`@%p1 st.global.b32`), which is what the shared one used to look
like.

That the lanes disagree at that point is what makes it a race rather than 32 copies of one value. A
lane computes `mean_own + delta * (n_partner / n)` and its butterfly partner computes
`mean_partner + (-delta) * (n_own / n)`, the same number in the reals and two different roundings in
f32, so the butterfly does not converge the lanes bitwise. Replaying the five `shfl.sync.bfly` stages
with the same combine on the same inputs and writing out all 32 lanes gives, for the eight warps of
the reproducer:

```
mean (stored at global_smem[warp * 4]):
  warp 0: 1 distinct   warp 1: 2 distinct, 12 lanes 3fc605af / 20 lanes 3fc605b0, 1 ulp
  warp 2: 2 distinct, 16 / 16, 1 ulp                warp 3..6: 1 distinct
  warp 7: 2 distinct, 16 / 16, 1 ulp
m2 (stored 32 bytes on):
  warp 0: 2 distinct, 41c7a62d / 41c7a62e          warp 1: 2 distinct, 28 / 4
  warp 3: 3 distinct, 41dfa2ef / 41dfa2f0 / 41dfa2f1, 2 ulp
  warp 5: 2 distinct, 24 / 8                       warp 6: 2 distinct, 16 / 16
weight: 1 distinct in every warp, as expected, the weight combine is a sum
```

so three of eight warps write two different `mean` words to one address and five of eight write two
or three different `m2` words. Which one survives is whatever the hardware serialises last.

In practice it is benign, and worth saying so: the candidates are one or two ulp apart, and the
reduction result is bit-identical across 1000 launches on this GPU, so nothing observable moves. The
objection is that nothing in the lowering makes the lanes agree, and a store of differing values by
several lanes to one address has no defined winner in the PTX memory model.

It is not specific to a hand-written kernel. `torch.compile` of `torch.var_mean(x, dim=1)` on torch
2.14 emits `triton_red_fused_var_mean_0` whose PTX carries the same three unpredicated
`st.shared::cta.b32` after the butterfly, all attributed by `.loc` to
`triton_helpers.py:450:12`, which is the `tl.reduce` inside `triton_helpers.welford`.

On where the guard went: 3.7.1 had `ReduceOpToLLVM.cpp::storeWarpReduceToSharedMemory`, which built
`Value laneZero = b.icmp_eq(laneIdAxis, b.i32_val(0))`, folded it into `write` together with the
representative lane and warp, and passed that to `targetInfo.storeShared`. In 3.8.0 that function is
gone and the epilogue goes through `ReduceOpToLLVM.cpp::convertLayoutValues`, which builds a
`ConvertLayoutOp` whose source layout is broadcast along the lane bases of the reduced axis; that
reaches `transferWithinBlockImpl` in `ConvertLayoutOpToLLVM.cpp` and then `lowerLdStShared` in
`lib/Conversion/TritonGPUToLLVM/Utility.cpp`, whose store is

```cpp
targetInfo.storeDShared(rewriter, loc, shmemAddr, ctaId, valsVec,
                        /*pred=*/b.true_val());
```

The assumption behind the hardcoded `true` is reasonable for layout conversion in general, where a
lane-broadcast value really is the same in every lane. The reduce epilogue is the case that breaks
it, because the butterfly produces the broadcast rather than replicating it.

The narrow fix is to predicate that store on the canonical lane of the broadcast group. The machinery
is already in the same file: `finalizeTensorAtomicResults` does exactly this store-then-load through
shared and passes `emitRedundantThreadPredicate(freeVarMasks, ...)` rather than `true`, and
`prepareLocalAtomicScatterRMW` builds the same predicate. Is there a reason `lowerLdStShared` can't
take a predicate the same way, defaulting to the free-variable-mask one for the lane, warp and block
dims? If that is too broad a change for a path this hot, the alternative is to keep the reduce out of
it and have `convertLayoutValues` hand down a layout that is not lane-broadcast, or restore the
lane-zero guard on the reduce side.

Versions: Triton 3.8.0 with torch 2.14.0+cu130, and Triton 3.7.1 with torch 2.13.0+cu130 for the
comparison, both on an RTX PRO 6000 Blackwell (sm_120), driver CUDA 13.3, Python 3.12.

I could not run `compute-sanitizer --tool racecheck` on this: there is no CUDA 13 build of it on
PyPI, and the 12.9 one fails to attach on a CUDA 13 driver.

### alexxony · 2026-09-14

This looks fixed on main already, as a side effect of #11175 (merged 2026-08-07, commit 7074119). Before that commit, `lowerLdStShared` hardcoded `storeDShared(..., /*pred=*/b.true_val())` — exactly the pattern in your analysis. #11175 refactored the shared store/load emitters into `makeSharedStoreEmitter`, which now threads through the real `threadPred` from `emitRedundantThreadPredicate` instead of a hardcoded `true`.

I checked the v3.8.0 tag directly and confirmed the hardcoded `true_val()` is still there — so this is a release-only regression that's already resolved on main, just not backported. I'm looking at pulling the relevant piece of #11175 into a release/3.8 backport PR; will post here if I open one.
