# [PR #11979] fix: force software NaN propagation emulation to avoid LLVM NVPTX regalloc bug (#11111)

## 正文

## Problem

A kernel that computes an fp8e5m2 value via `tl.maximum`/`tl.minimum` with `PropagateNan.ALL` and stores it to two buffers (one contiguous, one transposed) produces corrupted output in the transposed store. The contiguous store of the same value is always correct. Replacing the min/max with the numerically identical `tl.where` form makes the corruption disappear.

The corruption pattern varies with XBLOCK and num_warps (e.g. 72 NaN + 24 Inf, or 3072 Inf, or 96 NaN), which points at register allocation / store vectorization rather than a semantic issue.

**Reproducer**: https://gist.github.com/vkuzo/c7410babadd904c93beb3fd3638ffc75

## Root cause

The LLVM IR generated by Triton is identical for both variants, except for one intrinsic:

- `PropagateNan.ALL`: `llvm.intr.maximum` -> LLVM NVPTX lowers to `max.NaN.f32`
- `tl.where`: `llvm.intr.maxnum` -> LLVM NVPTX lowers to `setp+selp`

Both produce the same float value for finite inputs. The LLVM NVPTX backend has a register-allocation defect that causes the transposed store to read stale register bytes when the value was produced by `max.NaN.f32`.

## Fix

Force the software NaN-propagation emulation (`fcmp une` + `select`) on all compute capabilities. This uses `llvm.intr.maxnum` instead of `llvm.intr.maximum`, avoiding the LLVM backend bug.

The emulation is correct: if either operand is NaN, it returns NaN; otherwise it returns the max/min. This matches the IEEE 754-2019 semantics of `maximum`/`minimum`.

**Diff**: 1 file changed, 3 insertions, 11 deletions.

## Verification

With the fix, both `test_propagate_nan` and `test_no_propagate` emit `llvm.intr.maxnum` + `fcmp une` + `select` in the LLVM IR, instead of `llvm.intr.maximum` for the first variant.

## Notes

This is a workaround for an upstream LLVM NVPTX issue. The `hwNanPropagationSupported` field and constructor parameter are removed from `MinMaxFOpConversion` since they are no longer used. The function signature of `populateMinMaxFOpToLLVMPattern` retains the parameter for ABI compatibility.

Fixes #11111
