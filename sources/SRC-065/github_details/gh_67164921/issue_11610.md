# [Issue #11610] [interpreter] create_fma performs double rounding for float32 (survives the fix in #11424)

source: https://github.com/triton-lang/triton/issues/11610
state: closed | updated: 2026-09-10T14:09:06Z

## 正文

### Describe the bug

`create_fma` in the interpreter routes `float32` (and `float16`)
through a `float64` intermediate, on the premise stated in #11424 that
"float64 has enough precision to produce the correctly rounded target
result." That premise holds for `float16` (its full dynamic range fits
in a float64 mantissa, so the float64 sum is exact), but **not for
float32**: the product `a*b` is exact in float64, but `product+z` can
land exactly on the halfway point between two float32 values, and
rounding that halfway value to float64 first (round-to-nearest-even)
can already pick the wrong side before the subsequent float32 cast
ever runs. This is double rounding — the same defect class #11424 set
out to fix — surviving in the float32 path:

```python
def create_fma(self, x, y, z):
    dtype = z.data.dtype
    if dtype == np.float64:
        ret = np_fma_fp64(x.data, y.data, z.data)
    else:
        product = np.multiply(x.data, y.data, dtype=np.float64)
        ret = np.add(product, z.data, dtype=np.float64).astype(dtype)   # <- double rounding for float32
    return TensorHandle(ret, z.dtype.scalar)
```

Compiled (JIT/CUDA) `tl.math.fma` lowers to `fma.rn.f32`, which rounds
the exact product+sum **once**. The interpreter's two-step round
(float64 RN, then float32 RN) can disagree with that single-step
result whenever the exact value falls exactly on a float32 halfway
point.

```python
import os

import torch
import triton
import triton.language as tl


@triton.jit
def kernel(X, Y, Z, O):
    x = tl.load(X)
    y = tl.load(Y)
    z = tl.load(Z)
    tl.store(O, tl.math.fma(x, y, z))


def run(x, y, z):
    device = "cuda" if os.environ.get("TRITON_INTERPRET") != "1" else "cpu"
    xt = torch.tensor([x], dtype=torch.float32, device=device)
    yt = torch.tensor([y], dtype=torch.float32, device=device)
    zt = torch.tensor([z], dtype=torch.float32, device=device)
    ot = torch.empty(1, dtype=torch.float32, device=device)
    kernel[(1,)](xt, yt, zt, ot)
    return ot.item()


def main():
    x, y, z = 4097.0, 4097.0, 2.0**-30
    mode = "interpreter" if os.environ.get("TRITON_INTERPRET") == "1" else "compiled"
    print(f"mode: {mode}")
    print(f"fma({x}, {y}, {z}) = {run(x, y, z)}")


if __name__ == "__main__":
    main()
```

compiled log
```
mode: compiled
fma(4097.0, 4097.0, 9.313225746154785e-10) = 16785410.0
```

interpreter log (`TRITON_INTERPRET=1`)
```
mode: interpreter
fma(4097.0, 4097.0, 9.313225746154785e-10) = 16785408.0
```

**Why this happens**: `4097**2 = 16785409`, which sits exactly between
the two float32 neighbors `16785408.0` and `16785410.0` (float32 ulp is
2 in this range). `z = 2**-30` is below the float64 half-ulp threshold
at that magnitude, so `np.add(product, z, dtype=np.float64)` rounds
`product+z` to exactly `16785409.0`, and `.astype(float32)` then picks
`16785408.0` by ties-to-even. The true (infinitely precise) value is
`16785409 + 2**-30`, which is strictly **above** the halfway point, so
the correctly-rounded float32 result is `16785410.0` — what compiled
mode returns.

A second, independently found case from a random sweep (integer
mantissa products landing on the float32 midpoint, paired with a
sub-half-ulp `z`): `x=582656.0, y=411608.0, z=-3.34e-08` — compiled
`239825862656.0` vs interpreter (unfixed) disagreeing in the same way.

`float16` is unaffected — its full dynamic range fits inside a
float64 mantissa (24-bit product × 2 = 48 bits < 53 bits, and float16
values are far enough apart in float64 terms that the intermediate sum
is never ambiguous), so the existing `float64`-intermediate approach
already gives the correctly-rounded float16 result.

### Why CI doesn't catch this

`test_math_fma_op` generates inputs via `numpy_random`, which produces
generic-distribution values; the defect only appears when the exact
product+z falls precisely on a float32 halfway point with a
sub-half-ulp perturbation — a measure-zero-in-practice region random
sampling essentially never hits. `test_math_fma_op_special_values` is
float64-only and doesn't exercise the float32 path.

### Environment details

triton 3.8.0.dev (built from upstream/main, commit `20e6ba86`); the
same code path is also present in the current pip release (3.6.0)
albeit as `x.data*y.data + z.data` there — the double-rounding
intermediate-via-float64 approach was introduced after 3.6.0 by
#11424 and is the current `main` behavior.
