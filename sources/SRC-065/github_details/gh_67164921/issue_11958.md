## 正文

## Summary
`tl.sum(acc, axis=0)` — a reduce on the dimension the WS pass partitions the dot accumulator along — inside `tl.range(..., warp_specialize=True)` asserts at `WSDataPartition.cpp:1200` (`reduce should not happen on the partitioned dimension`). `num_ctas=1`, `num_warps=4`.

## Reproducer
Save the following script as `repro.py` and run with `python repro.py`:

```python
import torch, triton, triton.language as tl

@triton.jit
def k(a_ptr, b_ptr, c_ptr, M: tl.constexpr, N: tl.constexpr, K: tl.constexpr):
    om = tl.arange(0, M); on = tl.arange(0, N); ok = tl.arange(0, K)
    acc = tl.zeros([M, N], dtype=tl.float32)
    for i in tl.range(0, 4, warp_specialize=True):
        a = tl.load(a_ptr + om[:, None] * K + ok[None, :] + i * M * K)
        b = tl.load(b_ptr + ok[:, None] * N + on[None, :] + i * K * N)
        acc += tl.dot(a, b)
        acc = acc + tl.sum(acc, axis=0)[None, :] * 0   # reduce on partitioned dim
    tl.store(c_ptr + om[:, None] * N + on[None, :], acc)

M = N = K = 128
a = torch.randn(4 * M * K, device="cuda", dtype=torch.float16)
b = torch.randn(4 * K * N, device="cuda", dtype=torch.float16)
c = torch.empty(M * N, device="cuda", dtype=torch.float32)
k[(1,)](a, b, c, M, N, K, num_ctas=1, num_warps=4)
```

## Crash
Expected: the kernel compiles and runs (as it does when `warp_specialize=True` is removed), or fails with a user-facing diagnostic. Actual: compiler crashes with an internal assertion/error.

```
python: <triton_src>/third_party/nvidia/hopper/lib/Transforms/WarpSpecialization/WSDataPartition.cpp:1200:
Assertion `reduceOp.getAxis() != dim && "reduce should not happen on the partitioned dimension"' failed.
```

## Root cause
The data partitioner slices along dim 0 (M) of the accumulator; a reduce whose axis equals that partitioned dim has no slice implementation and asserts. The kernel compiles and runs normally when `warp_specialize=True` is removed.

## Environment
Triton `42c5e89c3` (2026-09-11, `TritonRelBuildWithAsserts`), NVIDIA H800 (sm_90a), `num_ctas=1`, `num_warps=4`. Deterministic.

### he-yufeng · 2026-09-25

Picking this up. The assert is the only thing standing between this shape and the pass's existing graceful path: `doDataPartition` returning false already makes the WS pipeline emit "failed to partition the function into warp-specialized code" and fail the compile cleanly instead of crashing. Fix: scan the final partition scheme for a `ReduceOp` whose axis equals its partition dim, and reject it with an `emitOpError` before `rewriteRematerializedOps` starts mutating IR. A real partitioned cross-task reduce is a bigger feature that needs owner alignment; this keeps the compiler honest in the meantime. Reproduced the assert with `triton-opt` on CPU (no GPU needed): the lit test aborts on the old binary at WSDataPartition.cpp:1201 and passes on the patched one; the existing ws_data_partition / ws_code_partition lit tests still pass. PR shortly.
