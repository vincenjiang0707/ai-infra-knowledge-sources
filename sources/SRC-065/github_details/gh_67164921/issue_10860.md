## 正文

## Summary

Allow a `@triton.aggregate` to be **constructed on the host** and passed to a
kernel as a single `tl.constexpr` argument. The aggregate's *runtime* data
members (e.g. `tl.tensor`, `tl.tensor_descriptor`, or scalars) are automatically
**lifted to runtime kernel parameters**, while its `tl.constexpr` members are
**baked into the compiled kernel**. Changing a runtime member reuses the already
compiled kernel; changing a compile-time member specializes a new one.

This turns an aggregate into a first-class, composable **kernel-configuration
object** — most naturally, a fused **epilogue** — that a launch site can build,
subclass, and hand to a single kernel body.

## Motivation

Today, customizing a kernel's behavior means threading an ever-growing list of
optional pointers and flags through its signature: a `bias_ptr`, a `has_bias`
flag, a `scale`, an `activation` enum, and so on. Each new fusion variant either
bloats the signature or forces a separate copy of the kernel.

We already have `@triton.aggregate` to bundle values into a struct, and
`@triton.jit` methods to attach behavior. What is missing is the ability to
**build that struct on the host from ordinary runtime data** (a `torch.Tensor`,
a `TensorDescriptor`, a Python scalar) and pass it in as one argument, without
manually splitting it into "the constexpr config" and "the runtime pointers."

The canonical use case is a composable epilogue (see
`python/tutorials/12-composable-kernel.py`):

```python
@triton.aggregate
class BiasAdd:
    bias: tl.tensor        # runtime member  -> lifted to a kernel param
    n_cols: tl.constexpr   # compile-time    -> baked in

    @triton.constexpr_function
    def __init__(self, bias, n_cols):
        self.bias = bias
        self.n_cols = tl.constexpr(n_cols)

    @triton.jit
    def apply(self, acc, offs_n):
        bias = tl.load(self.bias + offs_n, mask=offs_n < self.n_cols, other=0.0)
        return acc + bias[None, :]


@triton.aggregate
class BiasAddScale(BiasAdd):   # inherits fields + apply
    scale: tl.tensor

    @triton.constexpr_function
    def __init__(self, bias, n_cols, scale):
        self.bias = bias
        self.n_cols = tl.constexpr(n_cols)
        self.scale = scale

    @triton.jit
    def apply(self, acc, offs_n):
        return BiasAdd.apply(self, acc, offs_n) * self.scale
```

```python
@triton.jit
def matmul_kernel(a_ptr, b_ptr, c_ptr, ..., epilogue: tl.constexpr, ...):
    ...
    if not epilogue is None:
        acc = epilogue.apply(acc, offs_cn)   # concrete type selects the IR
    ...

# Two launch functions, one kernel body (grid omitted for brevity):
launch(a, b, c, BiasAdd(bias, N))              # base epilogue
launch(a, b, c, BiasAddScale(bias, N, scale))  # derived epilogue
```

Benefits:

- **One clean signature** regardless of how rich the epilogue is.
- **Compile-time polymorphism**: the aggregate's concrete type selects which
  `apply` is emitted — no runtime branching.
- **Cache-friendly**: changing the `bias` tensor or `scale` value reuses the
  compiled kernel; only compile-time members specialize a new one.
- **Composable via inheritance**: derive a richer epilogue from a base one and
  override its `@triton.jit` methods.

## Design

### User-facing contract

An aggregate field is classified by its annotation:

- Annotated `tl.constexpr` → **compile-time member**, baked into the kernel and
  participating in the compilation cache key.
- Any other annotation (`tl.tensor`, `tl.tensor_descriptor`, scalar, …) →
  **runtime member**, lifted to a runtime kernel parameter.

The aggregate is built on the host inside a `@triton.constexpr_function`
`__init__`, and passed to a kernel parameter declared `: tl.constexpr`. Nothing
else in the kernel body changes: `self.bias`, `self.scale`, `self.n_cols` are
accessed exactly as they would be for an in-kernel aggregate.

### Host construction: relaxed field typing (`language/core.py`)

`_aggregate`'s `__setattr__` previously required every assigned value to be an
instance of the field's annotated type. That rejects a raw `torch.Tensor` being
stored into a `tl.tensor` field on the host.

The check is relaxed so that, for **runtime** fields, a raw host value (a
`torch.Tensor`, a host `TensorDescriptor`, a Python scalar) is permitted. Two
guards remain:

- A `tl.constexpr` field still requires a `constexpr` value.
- A *Triton* value (`base_value`) of the wrong type is still rejected.

```python
if ann is constexpr or isinstance(value, base_value):
    raise TypeError(...)
```

This narrowly opens the door for host construction while keeping in-kernel
type-safety intact.

### Runtime lifting (`runtime/jit.py`)

A new `HostConstexprAggregate` wrapper captures, from a host-built aggregate:

- `base_cls`, `field_order`
- `const_bindings` — the compile-time members (by value)
- `runtime_names` / `runtime_values` — the runtime members
- `cache_key` — a **stable, value-based** key computed from the class, the
  compile-time member values, and the runtime member *layout* (names only).
  Runtime member *values* deliberately do **not** enter the key. Tensor members
  are keyed structurally (`tensor(shape, dtype)`), never by contents.

A new `JITFunction._specialize_host_aggregates(backend, bound_args, specialization)`
step runs inside `run()` (and is mirrored in `_filecheck.run_parser`). For each
`constexpr` argument that is a host-built aggregate with runtime members it:

1. Specializes each runtime member via `native_specialize_impl` (obtaining its
   IR type and argument attributes such as divisibility).
2. Rewrites the bound argument to a tuple `(wrapper, *runtime_values)` so the
   members flow through the **existing tuple-argument machinery** (signature,
   launcher, IR) with no new launch path.
3. Records the specialization as `(("constexpr", *member_types), (wrapper, *member_attrs))`
   so the wrapper's identity participates in the cache key and each member's
   attributes are preserved.

A **pure** compile-time aggregate (no runtime members) is left untouched — it
already works as a baked constant.

Specialization-cache serialization is extended: `HostConstexprAggregate` is
serialized as `{"constexpr_aggregate": value.cache_key}`.

### Frontend reconstruction (`compiler/code_generator.py`)

In `ast_to_ttir`, when a constant is a `HostConstexprAggregate`, the argument's
lifted tuple signature `("constexpr", *member_types)` is used to rebuild the
aggregate's type as a new `host_aggregate_type` (subclass of `_aggregate_type`):

- Compile-time members are typed from `const_bindings` and flatten to **no IR**.
- Runtime members are typed from the lifted tuple elements.

`host_aggregate_type` implements `_unflatten_ir_with_attrs`, and `ASTFunction`'s
`build_value` prefers it when present. This reconstructs the aggregate instance
from kernel handles **and** applies each runtime member's argument attributes at
its nested path (`(*path, k + 1)` — element 0 is the wrapper). The kernel body
then sees a fully-formed aggregate, indistinguishable from one built in-kernel.

### Filecheck / test parity (`_filecheck.py`)

`run_parser` calls `_specialize_host_aggregates` so parser/filecheck tests
exercise the exact lifting path `run()` uses (a no-op for kernels without
host aggregates).

## Cache-key semantics

| Member kind        | In compilation cache key? | Effect of changing it            |
| ------------------ | ------------------------- | -------------------------------- |
| `tl.constexpr`     | Yes (by value)            | Specializes a new kernel         |
| runtime (`tensor`) | Layout only (name/type)   | Reuses compiled kernel           |

This is the same trade-off as ordinary constexpr vs. runtime kernel arguments —
extended transparently through the aggregate boundary.

  - `test_host_aggregate_derived_tensor_and_constexpr_members` — a *derived*

    constexpr members are folded into the body.

## Alternatives considered

- **Manual splitting**: pass the bias pointer and constexpr config as separate
  kernel arguments. Rejected — it defeats the purpose of a composable
  configuration object and re-bloats the signature.
- **Bake everything (including tensors) as constants**: would recompile on every
  new bias tensor. Rejected on cache grounds.
- **A dedicated non-tuple launch path** for lifted members. Rejected — reusing
  the existing tuple-argument machinery keeps the launcher and IR paths unchanged.

## Backward compatibility

- Purely additive. Kernels that do not pass host-built aggregates are unaffected
  (`_specialize_host_aggregates` is a no-op for them).
- In-kernel aggregate type-checking is unchanged except for the narrowly relaxed
  runtime-field host-value case in `__setattr__`.
- Specialization-cache format gains one new serialized shape
  (`constexpr_aggregate`); existing shapes are unchanged.

## Open questions

1. **Nested aggregates** *(tested — not supported today)*: a runtime member that
   is *itself* an aggregate is **not** recursively lifted. Such a member is
   classified as an ordinary runtime member (its annotation is the aggregate
   class, not `tl.constexpr`), so `_specialize_host_aggregates` hands the whole
   aggregate instance to `native_specialize_impl`, which raises
   `TypeError: failed to specialize argument of type: <Inner>` at launch — before
   the frontend runs. Supporting this would require `HostConstexprAggregate` to
   detect aggregate-typed members and flatten their runtime members recursively
   (with correspondingly nested attribute paths). Open question: do we want this,
   or should nested aggregates be required to be pure compile-time members?
2. **Attribute paths**: the `(*path, k + 1)` convention assumes the wrapper
   occupies element 0. Should this be documented as a stable contract or hidden
   behind a helper?
3. **Cache-key robustness**: `_capture_repr` falls back to `repr(value)` for
   arbitrary compile-time members. Do we need a stricter, opt-in hashing protocol
   for user-defined constexpr member types?
4. **Gluon parity**: confirm the lifting path behaves identically under the
   Gluon AST source.
