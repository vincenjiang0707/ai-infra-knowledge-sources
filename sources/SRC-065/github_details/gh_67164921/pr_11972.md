# [PR #11972] [BACKEND][NV] Fail warp-spec data partition gracefully on partitioned-dim reduce

source: https://github.com/triton-lang/triton/pull/11972
state: open | updated: 2026-09-26T11:19:17Z
labels: 

## 正文

Fixes #11958

## What

`tl.sum(acc, axis=0)` inside a `tl.range(..., warp_specialize=True)` loop crashes the compiler at `WSDataPartition.cpp:1201` when the accumulator is partitioned along dim 0: the reduce-on-partitioned-dim case has no slice implementation, and the hard `assert` aborts the process mid-mutation.

## How

The partition scheme already has a graceful exit: `doDataPartition` returning false makes the WS pipeline emit "failed to partition the function into warp-specialized code" and fail compilation cleanly. This change scans the final scheme for a `ReduceOp` whose axis equals its partition dim and rejects it with an `emitOpError` before `rewriteRematerializedOps` starts mutating IR, so the assert is never reached with half-partitioned IR. A true cross-task partitioned reduce is a larger feature that needs owner alignment; this keeps the compiler honest in the meantime.

The semantics match `sliceOp` exactly: it reads the same `opPartitionDims` entry for the op, so the check rejects precisely the cases that would have asserted, and nothing else.

## Tests

New lit test `test/Hopper/WarpSpecialization/ws_data_partition_reduce_partitioned_dim.mlir` (the issue's repro shape: `tt.reduce` axis 0 on the dim-0-partitioned accumulator, run through `triton-opt --nvgpu-test-ws-data-partition`):

- On the unpatched binary it aborts at `WSDataPartition.cpp:1201` (the exact assert from the issue), and the FileCheck for the diagnostic fails.
- On the patched binary the pass emits `reduce on the warp-specialized partition dimension is not supported` and exits cleanly.

Regression: the full `test/Hopper/WarpSpecialization/` lit directory passes (5/5), including the softmax-shaped axis-1 reduces in `ws_code_partition.mlir`, which the check correctly does not fire on. All run locally on CPU with `triton-opt`; no GPU needed. `pre-commit run --from-ref origin/main --to-ref HEAD` passes.

### he-yufeng · 2026-09-26

Fair on the "still fails" part: on an assert build the diagnostic only changes how it fails. The case I'd make for landing it anyway is the non-assert path. The assert is the only guard this branch has, and with NDEBUG it compiles out: the partitioner then slices the accumulator input per partition and clones the reduce over the sliced operand, so a meaningful `tl.sum(acc, axis=0)` silently computes each partition's partial sum and uses it as the full one. (The #11958 repro multiplies by zero, so that specific kernel is numerically harmless, but the shape is a stress test, not the real failure mode.) So without the check, assert builds crash and release builds can produce wrong values; with it both fail loudly at the same place.

On the actual improvement you're pointing at: making the reduce work across partitions needs cross-partition partial-reduce + combine machinery, and I have no sm90 here to validate that against, so I'd rather not ship IR surgery I can't run. If the call is that the diagnostic doesn't pull its weight either, I'm fine closing this and leaving #11958 open as the feature request for the real partitioned-reduce support; just say which way you'd rather go.
