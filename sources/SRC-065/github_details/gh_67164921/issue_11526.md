# [Issue #11526] [Regression] Increased SMEM usage with tf32x3 GEMM (3.6 -> 3.8)

source: https://github.com/triton-lang/triton/issues/11526
state: closed | updated: 2026-09-04T23:31:21Z
labels: bug

## 正文

### Describe the bug

We noticed that triton 3.8 allocates more SMEM for tf32x3 GEMM, on L40 it makes the configs that were once working now crash due to allocated SMEM exceeds L40's capacity.

Here's a repro script. To reproduce, create 2 virtual python envs with triton 3.6 and 3.8, and run this script:

```
"""Minimal repro of the Triton 3.8 tf32x3 shared-memory regression.

Single tile, 1 warp, 2 pipeline stages -- ~127 lines of TTGIR.
Compile-only: no GPU and no torch needed.

    ./venv-3.6/bin/python minimal.py     -> tf32 1536  tf32x3 1536
    ./venv-3.8/bin/python minimal.py     -> tf32 1536  tf32x3 3072
"""
import triton
import triton.language as tl
from triton.backends.compiler import GPUTarget
from triton.compiler import ASTSource

BLOCK_M, BLOCK_N, STEP_K = 16, 16, 16
WARPS, STAGES = 1, 2


@triton.jit
def kernel(x_ptr, w_ptr, o_ptr, K,
           BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr,
           STEP_K: tl.constexpr, PRECISION: tl.constexpr):
    # one CTA, one output tile:  o[16,16] = sum_k x[16,k] @ w[16,k].T
    offs_m = tl.arange(0, BLOCK_M)
    offs_n = tl.arange(0, BLOCK_N)
    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
    for k in range(0, K, STEP_K):
        ks = k + tl.arange(0, STEP_K)
        x = tl.load(x_ptr + offs_m[:, None] * K + ks[None, :])   # bf16
        w = tl.load(w_ptr + offs_n[:, None] * K + ks[None, :])   # fp32
        acc = tl.dot(x.to(tl.float32), tl.trans(w, (1, 0)), acc,
                     input_precision=PRECISION, out_dtype=tl.float32)
    tl.store(o_ptr + offs_m[:, None] * BLOCK_N + offs_n[None, :], acc)


def build(precision):
    src = ASTSource(
        fn=kernel,
        signature={"x_ptr": "*bf16", "w_ptr": "*fp32", "o_ptr": "*fp32", "K": "i32",
                   "BLOCK_M": "constexpr", "BLOCK_N": "constexpr",
                   "STEP_K": "constexpr", "PRECISION": "constexpr"},
        constexprs={"BLOCK_M": BLOCK_M, "BLOCK_N": BLOCK_N,
                    "STEP_K": STEP_K, "PRECISION": precision},
    )
    return triton.compile(src, target=GPUTarget("cuda", 89, 32),
                          options={"num_warps": WARPS, "num_stages": STAGES})


if __name__ == "__main__":
    v = triton.__version__
    for prec in ("tf32", "tf32x3"):
        k = build(prec)
        path = f"min-{v}-{prec}.mlir"
        open(path, "w").write(k.asm["ttgir"])
        n = k.asm["ttgir"].count("ttg.local_alloc")
        print(f"triton {v}  {prec:<7} shared={k.metadata.shared:>6}  "
              f"local_allocs={n}  -> {path}")
```

```
  $ ./venv-3.6/bin/python minimal.py
  triton 3.6.0  tf32    shared=  1536  local_allocs=2  -> min-3.6.0-tf32.mlir
  triton 3.6.0  tf32x3  shared=  1536  local_allocs=2  -> min-3.6.0-tf32x3.mlir

  $ ./venv-3.8/bin/python minimal.py
  triton 3.8.0  tf32    shared=  1536  local_allocs=2  -> min-3.8.0-tf32.mlir
  triton 3.8.0  tf32x3  shared=  3072  local_allocs=4  -> min-3.8.0-tf32x3.mlir
```

This bug only affects tf32x3. I did some investigation that I'll attach below.

### Environment details

Triton: 3.8.0
GPU: not arch specific -- this is a MLIR issue. This script also reproduces the bug on Blackwell. Also I suspect you can directly see the problem from IR without running it.

What happens here is:
- upcast `x`, which is `acc_30` (bf16), to `acc_35` (f32)
- round `x` in fp32 which is `acc_35`, to `acc_36` (tf32), which is `x_hi`
- compute `acc_37 = acc_35 - acc_36` which is `x_lo`
- round `w`, which `acc_34` (f32 already) to `acc_38` (tf32), which `w_hi`
- compute `acc_39 = acc_34 - acc_38`, which is `w_lo`
- compute `acc_40 = x_lo @ w_hi`
- compute `acc_41 = x_hi @ w_lo + acc_40`
- (some code to handle nan which is not important here)
- compute `acc_44 = x_hi @ w_hi + acc_43`
which would be our tf32x3 matmul result (`x_lo` @ `w_lo` is skipped for being insignificant)

### choi3171 · 2026-09-01

**TL;DR:** #11029 changed when `getConvertBackwardSlice` adds a value to the slice. `hoistConvertDotOperand` now gets an empty slice for three of the six dot-operand conversions and silently bails, and `ReduceDataDuplication` turns each leftover conversion into a shared-memory round trip. That is the 1536 -> 3072. A candidate one-line fix below restores 1536 on both `main` and the release branch with no lit changes, but it is lit-only: I have no GPU here.

This also confirms @warrendeng's bisect: building the 3.8 release branch either side of the cherry-pick gives `metadata.shared` 1536 at `c8dd1a7af7` and 3072 at `675c59878a` (#11108, the backport of #11029).

All shared-memory figures below are sm_89 and compile-only: `metadata.shared`, `local_alloc` counts, and the pass's debug output. I have not measured the runtime cost of the extra shared memory.

### Why the pass diverges
---

The divergence is in `TritonGPURemoveLayoutConversions`, the invocation right after `AccelerateMatmul`. Both versions reach its hoisting phase with the same six dot-operand conversions and differ only in how many get hoisted:

|       | conversions entering the phase | hoisted |
| ----- | ------------------------------ | ------- |
| 3.7.1 | 6                              | 6       |
| 3.8.0 | 6                              | 3       |

The three that 3.8.0 leaves behind bail out of `hoistConvertDotOperand` on `innerSlice.empty()`: their backward slices come back empty. They survive to `ReduceDataDuplication`, which materializes each `blocked -> dot_op` conversion as a `local_alloc` + `local_load` round trip through shared memory. Hence `local_alloc` 2 -> 4 and `metadata.shared` 1536 -> 3072.

In the repro's TTGIR (`...` marks elision):

```mlir
// 3.7.1: each dot operand is converted where its data is staged
%x_29   = tt.load %x_28          : tensor<16x16x!tt.ptr<bf16>, #blocked>
%acc_30 = ttg.local_alloc %x_29  : (tensor<16x16xbf16, #blocked>) -> !ttg.memdesc<16x16xbf16, #shared1, #smem>
%acc_31 = ttg.local_load %acc_30 : ... -> tensor<16x16xbf16, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 2}>>
```
Two `ttg.local_alloc` in the whole kernel.

```mlir
// 3.8.0: the block above is unchanged. These two allocs are new,
// one shared-memory round trip per conversion left behind
%acc_42 = ttg.local_alloc %acc_41 : (tensor<16x16xf32, #blocked>)  -> !ttg.memdesc<16x16xf32, #shared2, #smem>
%acc_46 = ttg.local_alloc %acc_45 : (tensor<16x16xf32, #blocked1>) -> !ttg.memdesc<16x16xf32, #shared3, #smem>
...
%acc_49 = ttg.local_load %acc_42  : ... -> tensor<16x16xf32, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 2}>>
%acc_53 = ttg.local_load %acc_46  : ... -> tensor<16x16xf32, #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>>
```
`#shared2` and `#shared3` are the extra buffers: 4 `ttg.local_alloc` in total. Three conversions bail but only two allocs appear because two of the three are the same conversion, the `cvt.rna.tf32` result of `x` to `opIdx = 0`, emitted once per dot that consumes it, and `TritonLoopAwareCSE` merges the pair before `ReduceDataDuplication`. That leaves one conversion per operand side: the `#blocked -> opIdx 0` and `#blocked1 -> opIdx 1` allocs above.

### Why the slice is empty
---

The `getExistingConversion` skip itself predates the regression: it came in with #8291 and is present in v3.7.1. What changed is where the value is added to the slice relative to that skip. #11029 moved `slice.insert(currentValue)` in `getConvertBackwardSlice` from [before the check](https://github.com/triton-lang/triton/blob/c3351aa4abfe4075875bf47da35e53971db11821/lib/Dialect/TritonGPU/Transforms/Utility.cpp#L934) to [after it](https://github.com/triton-lang/triton/blob/8a53c53187cfc2965f3b5c6b5841a9b8c369d2ae/lib/Dialect/TritonGPU/Transforms/Utility.cpp#L944):

```cpp
    // before
    slice.insert(currentValue);
    if (getExistingConversion && getExistingConversion(*currentValueUse, encoding))
      continue;                      // operands skipped, value still in the slice

    // after #11029
    if (getExistingConversion && getExistingConversion(*currentValueUse, encoding))
      continue;                      // value not in the slice at all
    ...
    slice.insert(currentValue);
```

`hoistConvertDotOperand`'s root is exactly such a value, so it now receives `success()` with an empty slice, iterates over nothing, and bails.

The root is covered when an earlier conversion's slice already passed through the same value, the "two or more users" shape below. Skipping it is right for `backwardRematerialization`, which reuses that conversion, and wrong for `hoistConvertDotOperand`, which needs it next to the load so the load can be pipelined. An unintended interaction between #8291 and #11029, not a mistake in either.

### Three fixes I tried
---
1. **Moving `slice.insert` back on its own** produces invalid IR: `'arith.muli' op requires the same encoding for all operands and results`. #11029 also removed the compensating half in `rewriteSlice` (`valuesWithExistingRemat` + `slice.set_subtract`), so a value back in the slice now gets rematerialized for real. The two changes are coupled, so half a revert is not a revert.
2. **Skipping the lookup for this caller only** (a null `getExistingConversion` in `hoistConvertDotOperand`) fixes the symptom completely but regresses `TritonGPU/amd/accelerate-amd-matmul-mfma-decompose-scaled-dot.mlir`: 12 -> 13 `convert_layout` and 3 -> 4 `tt.trans`. It emits two identical conversions of the same value to the same layout, exactly what `getExistingConversion` exists to prevent. This caller does need the lookup.
3. **Bailing only when the conversion has nothing to stand on.** `innerSlice` comes up empty in three situations: (a) nothing to traverse, (b) the root itself was skipped as already covered, (c) the slice held only loads. Only (b) is recoverable: `rewriteSlice` can replace the conversion with the rematerialization that covers the root, which is what happened before #11029. The check is the bare `innerSlice.empty()` in `hoistConvertDotOperand` ([`RemoveLayoutConversions.cpp#L1346`](https://github.com/triton-lang/triton/blob/58895270e/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L1346) on `main`):

```cpp
   if (innerSlice.empty() &&
       !existingRemats.lookup({convertOp.getSrc(), targetType.getEncoding()}))
     return false;
```

The lookup is a reliable test for "not covered": `getExistingConversion` stores a null `Value` for a rematerialization that does not dominate the use, so `lookup` is null exactly in the cases we still want to bail on. Returning `true` also skips the `addRematValue` the driver does on failure, which is what we want: `rewriteSlice` erases the conversion and calls `updateRematMapping` for the replacement, so registering the erased result would reintroduce the stale mapping #11029 fixed.

This one holds up. The same diff applies unchanged to `main` (`58895270e`) and to `675c59878a`, the first bad release-branch commit:

|                            | unpatched                         | with the patch |
| -------------------------- | --------------------------------- | -------------- |

### Two things that may help with triage
---
It is not tf32x3 specific. The trigger is a load-derived value with two or more users, at least one a dot operand. tf32x3 hits it every time because its `cvt.rna.tf32` result feeds an `arith.subf` plus two `tt.dot`s, but a plain `input_precision="tf32"` kernel with a second user reproduces it too. The reported kernel's tf32 path stays at 1536 because its `x` has a single dot user.

The table uses a different kernel from the report (fp32 inputs, plain tf32, `xh = x * 2.0` standing in for the high part), so its baseline is 2048 rather than 1536. Only the users of `xh` vary. 16x16x16 / 1 warp / 2 stages:
