# [Issue #11326] [Membar] No barrier between a caller's pending shared access and a callee's first one

source: https://github.com/triton-lang/triton/issues/11326
state: closed | updated: 2026-08-29T15:15:00Z
labels: 

## 正文

## Describe the bug

The membar analysis models a `tt.call` only by the callee's **exit** state, so the caller's pending shared-memory accesses are never checked against what the callee does **first**. When the two overlap, no barrier is emitted and the accesses race.

`MembarAnalysis::update` takes the callee's summary from `funcMap` (`lib/Analysis/Membar.cpp:250-262`), and that map holds the joined exit state only (`include/triton/Analysis/Function.h:131-154`). A callee whose first shared access is a write therefore looks, at the call site, like whatever it left behind at the end. `getScratchBufferId` also deliberately excludes `triton::CallOp` (`Membar.cpp:131-137`), so the call is not modelled as a scratch op either. Nothing is emitted before the call.

The reverse direction is handled: `test/Analysis/test-membar.mlir:1497-1500` already asserts that a scratch op placed **after** a call, aliasing the call frame, needs a barrier. Moving that scratch op **before** the call exposes the gap.

## Reproducer

```mlir
#blockedCallSrc = #ttg.blocked<{sizePerThread = [1, 32], threadsPerWarp = [32, 1], warpsPerCTA = [4, 1], order = [0, 1]}>
#mmaCall = #ttg.nvidia_mma<{versionMajor = 2, versionMinor = 0, warpsPerCTA = [4, 1], instrShape = [16, 8]}>
#blockedCallDst = #ttg.dot_op<{opIdx = 0, parent = #mmaCall, kWidth = 2}>
#smem = #ttg.shared_memory

module attributes {"ttg.num-ctas" = 1 : i32, "ttg.num-warps" = 4 : i32} {
  // First shared access in the callee is the convert_layout's store.
  tt.func private @callee_writes_first() -> tensor<128x32xf16, #blockedCallDst> {
    %cst = arith.constant dense<0.0> : tensor<128x32xf16, #blockedCallSrc>
    %cvt = ttg.convert_layout %cst : tensor<128x32xf16, #blockedCallSrc> -> tensor<128x32xf16, #blockedCallDst>
    tt.return %cvt : tensor<128x32xf16, #blockedCallDst>
  }

  tt.func @caller_pending_read_then_call() -> tensor<128x32xf16, #blockedCallDst> {
    %cst = arith.constant dense<0.0> : tensor<128x32xf16, #blockedCallSrc>
    %cvt = ttg.convert_layout %cst : tensor<128x32xf16, #blockedCallSrc> -> tensor<128x32xf16, #blockedCallDst>
    %call = tt.call @callee_writes_first() : () -> tensor<128x32xf16, #blockedCallDst>
    %sum = arith.addf %call, %cvt : tensor<128x32xf16, #blockedCallDst>
    tt.return %sum : tensor<128x32xf16, #blockedCallDst>
  }
}
```

```
triton-opt repro.mlir --allocate-shared-memory -test-print-membar
```

Output on `main` (c346e50c7b), caller body:

```mlir
  tt.func @caller_pending_read_then_call() -> ... {
    %cst = arith.constant dense<0.000000e+00> : tensor<128x32xf16, #blocked>
    %0 = ttg.convert_layout %cst {allocation.offset = 0 : i32, allocation.size = 8192 : i32} : ...
    %1 = tt.call @callee_writes_first() {allocation.offset = 0 : i32} : () -> ...
    %2 = arith.addf %1, %0 : ...
    tt.return %2 : ...
  }
```

The caller's scratch is `[0, 8192)` and the call frame starts at the same offset, so the callee's own scratch lands on those bytes. There is no `ttg.barrier local` in the caller.

`ConvertLayoutOpToLLVM` lowers a conversion to store / barrier / load, with a leading barrier only for repeat rounds (`ConvertLayoutOpToLLVM.cpp:208-233`), and `ReduceOpToLLVM` is the same shape. So after the caller's conversion there is an outstanding read of those bytes, and the callee opens with a store to them: one warp can still be reading while another has entered the callee and started writing. The caller's conversion then yields wrong values.

The same hazard inside a single function is caught (`test/Analysis/test-membar.mlir:91-105`), so inlining changes whether the program is correct.

## Reachability

`tt.call` survives to TritonGPU only with `@triton.jit(noinline=True)`, which the in-tree `test_noinline[shared]` already exercises. Any caller that does a layout conversion, a reduction or a `tl.dot` before calling a `noinline` helper is ordinary code.

## Possible fixes

Two shapes, and I would rather not guess which one you want:

1. Conservative: also treat the call as writing its virtual buffer on entry, so any pending caller access that overlaps the frame forces a barrier before the call. Small change, and `tt.call` is rare enough that the extra barriers should be contained, but it is a blunt instrument.
2. Precise: give each function an entry summary alongside the exit one (the accesses before its first synchronization point) and test the caller's pending state against that. Matches what the analysis already does for sync points elsewhere, but it changes the shape of the per-function summary.

Happy to send a PR for whichever you prefer.

## Environment details

Triton `c346e50c7bb102f35f04d7200a3bc6194bec4c33`, `triton-opt` built from source, no GPU needed to reproduce.

Built `triton-opt` at `9628c80f2` (md5 `aedfc7b1ac33`) and ran the reproducer from this issue unchanged:

```
triton-opt repro.mlir --allocate-shared-memory -test-print-membar
```

```mlir
  tt.func @caller_pending_read_then_call() -> ... {
    %cst = arith.constant dense<0.000000e+00> : tensor<128x32xf16, #blocked>
    %0 = ttg.convert_layout %cst {allocation.offset = 0 : i32, allocation.size = 8192 : i32} : ...
    ttg.barrier local
    %1 = tt.call @callee_writes_first() {allocation.offset = 0 : i32, allocation.size = 8192 : i32} : ...
    %2 = arith.addf %1, %0 : ...
    tt.return %2 : ...
  }
```

The `ttg.barrier local` before the call is the one that was missing in August. `test/Analysis/test-membar.mlir` passes on the same binary.

The mechanism is the second of the two shapes I offered, the entry summary. `MembarAnalysis::update` now does

```cpp
if (summary) {
  syncIfNeeded(op, summary->entryBlockInfo, membarInfo, builder, cluster);
  membarInfo->applyCallSummary(*summary);
}
```

so the caller's pending state is tested against the callee's entry state rather than only its exit state, which is what this issue asked for. It arrived as part of the wider `BufferRegionAnalysis` rework rather than as a targeted patch, which is presumably also why #11384 was closed.

I only ran the case in this issue, so I am not claiming every inter-procedural hazard is covered, just this one.
