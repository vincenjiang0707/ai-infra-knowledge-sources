# [PR #11964] [TRITONGPU] Sink memory loads closer to first use in ReorderInstructions

source: https://github.com/triton-lang/triton/pull/11964
state: closed | updated: 2026-09-25T16:37:19Z
labels: 

## 正文

Fixes #4377.

### Motivation and Root Cause
In kernels performing GEMM followed by element-wise fused operations (epilogues such as SiLU gradient, bias-add, activations), memory loads (`tt.load`) of epilogue operands and their associated address computations (`tt.splat`, `tt.addptr`, `tt.broadcast`) are often scheduled before or alongside `tt.dot`.

Consequently, the epilogue tensor values occupy architectural registers during the entire matrix-multiply computation. When combined with the high accumulator pressure from `tt.dot` (and subsequent `convert_layout`), this leads to catastrophic register spilling and stack usage when lowered to PTX:
- An exemplar tile of 128x128 with SiLU gradient epilogue incurred 16,092 bytes of spill stores, 16,536 bytes of spill loads, and a 7,832-byte stack frame with ptxas constrained to 32 registers.

### Proposed Changes
Extend `TritonGPUReorderInstructionsPass` (`lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp`):
1. Identify `tt.load` operations whose `firstUse` in the basic block is separated by intermediate operations.
2. Ensure safety by checking that no write side-effecting operations intervene between the load and its first use via `crossWriteSideEffectingOp`.
3. Collect the backward slice of pure address-computation operations feeding the pointer that have no other uses.
4. Topologically sort the address slice and move both the address slice and `tt.load` immediately before `firstUse`.

### Validation
1. **Unit Test (`lit`)**:
   Added `sink_epilogue_load` to `test/TritonGPU/reorder-instructions.mlir`. Verified with `lit` (100% pass rate).
2. **Full TritonGPU test suite**:
   Ran `lit` on all 138 tests under `test/TritonGPU/` (137 passed, 1 pre-existing unrelated unsupported failure in `pipeline-split-cluster-unscheduled-op.mlir`).
3. **Register Spilling & Compilation Benchmark (#4377 reproducer, sm_80)**:
   - Spill stores: 16,092 bytes -> 2,424 bytes (-85%)
   - Spill loads: 16,536 bytes -> 2,424 bytes (-85%)
   - Stack frame: 7,832 bytes -> 1,960 bytes (-75%)
   - Target register allocation: restored to full 255 registers
   - ptxas compile latency: 2,185 ms -> 1,347 ms (1.6x speedup)

### agourakis82 · 2026-09-25

Thanks for the review, and agreed — moving loads to first use is not a pressure model, and the PR overreached on two fronts: (1) it claimed to fix #4377, which is actually about intra-epilogue temporaries from `tt.dot` results, not global loads; and (2) it only measured ptxas spill stats under `maxnreg=32`, with no runtime numbers. Copilot's side-effect findings (volatile loads, non-pure address slices) were also real correctness bugs.

If there is any appetite for it, I'd like to scope this down to a narrow, separate pass: sink a `tt.load` only when it is a pure `Read<GlobalMemory>`, it dominates an `scf.for` whose every use post-dominates the loop, the loop has no global writes or unknown effects, and the estimated in-loop pressure exceeds the register budget — placing it right after the loop (under the accumulator `convert_layout`) rather than at first use, so the latency stays hidden. Before writing code I would collect runtime data on GEMM+epilogue across sm_80/sm_90, sweeping K and tile sizes, against both the current baseline and the source-order workaround. Would you want that as an RFC in Discussions first, or is the project's position that source order is the schedule for out-of-loop loads?
