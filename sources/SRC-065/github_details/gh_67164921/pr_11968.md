# [PR #11968] [AMD] Add a pre-bound HIP kernel launcher

source: https://github.com/triton-lang/triton/pull/11968
state: open | updated: 2026-09-25T22:02:46Z

## 正文

## Why

The HIP launcher currently rebuilds invariant launch state and temporary parameter arrays for every invocation. This overhead is visible for very short-running kernels, where host launch work is a material part of the complete call time.

This is the first part of #11949. It reduces the final HIP launch overhead without changing specialization lookup or generated GPU code. A separate follow-up will address native specialization-key construction and cache lookup.

## What changed

- Add a C `HIPPreboundLauncher` vectorcall object that binds the loaded HIP function, launch configuration, argument extraction plan, and parameter storage once.
- On each eligible launch, update only the grid, stream, and runtime scalar/pointer values before calling the existing HIP launch helper.
- Preserve the existing generic launcher for active launch hooks, tuple or tensor-descriptor arguments, and compiler-managed scratch allocations.
- Add `TRITON_USE_PREBOUND_LAUNCHER=0` as an escape hatch.
- Fix pointer-extraction error handling shared by the generic and pre-bound paths.

## Validation

Tested on an AMD Instinct MI350X (`gfx950`):

- `make PYTHON=.venv/bin/python`
- `pre-commit run --from-ref triton_upstream/main --to-ref HEAD`
- `python/test/unit/runtime/test_launch.py`: 13 passed
- Added coverage for changing runtime scalars, zero-sized grids, launch-hook fallback, tuple-signature fallback, and CPU-pointer rejection.

For an empty one-program kernel, four fresh-process measurements were run in rotated enabled/disabled order. Each process used 1,000 warmup launches and seven samples of 20,000 launches:

| Path | Median of process medians |
|---|---:|
| Existing HIP launcher | 12.17 us/call |
| Pre-bound HIP launcher | 9.84 us/call |

This is a 19.1% reduction in complete empty-kernel call time. The benchmark measures the host call and launch path; this PR does not alter the generated GPU kernel.
