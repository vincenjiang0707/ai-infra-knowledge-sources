# [PR #11950] [FRONTEND] Promote same-type fp8 arithmetic to fp16

## 正文

## Summary

Same-type fp8 arithmetic (`x + y`, `x - y`, `x * y`, unary `-x`, comparisons, `tl.sum`) passed the frontend and died at the LLVM verifier, because rule 6 in `computation_type_impl` kept same-type fp8 as fp8 and no backend can lower those ops at fp8.

Following option (b) from the issue discussion (endorsed by the reporter): promote before evaluating, like the div/mod rule already does. Same-type fp8 arithmetic now computes in fp16:

- `computation_type_impl` gains an `fp8_arith` flag; the same-type fp8 branch returns fp16 when it is set.
- `add`, `sub`, `mul`, the six comparisons, and unary `minus` set it; `tl.sum` picks fp16 for fp8 inputs in `_pick_sum_dtype`.
- Selection ops that lower at fp8 (`tl.maximum`, `tl.minimum`, `tl.where`, `clamp`) keep fp8. Mixed fp8 operands keep their existing fp16 rule. Div/mod keep their fp32 rule.

Fixes #11898

## Tests

`test_fp8_div_mod_promotion` moves its two pins to fp16 (`x * y`, `x * 2.0`). New `test_fp8_arith_promotes_to_fp16` pins the dtype of each promoted op plus the TTIR evidence (fp16 `arith.cmpf` operands, `tt.fp_to_fp` before the fp16 reduce body, fp16 `negf`), and pins maximum/minimum/where staying fp8.

Local run (macOS arm64, no GPU): `test_frontend.py` 681/681 pass including the new test; `test_compile_only`/`test_annotations`/`test_tuple`/`test_module` pass except the CUDA-launch cases, which fail identically on the base tree here (no CUDA on this host). GPU-side numeric behavior is not covered locally; the change is frontend type promotion, and the pins above verify what reaches the backend.
