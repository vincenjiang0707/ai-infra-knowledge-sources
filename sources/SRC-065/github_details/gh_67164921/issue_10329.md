# [Issue #10329] Build Triton without Nvidia/AMD backends?

source: https://github.com/triton-lang/triton/issues/10329
state: open | updated: 2026-09-25T11:14:21Z
labels: 

## 正文

Hi, is there any plan to allow building libtriton and the triton wheel without Nvidia and/or AMD LLVM targets and Triton backends?

I did not find much discussion about this in any relevant repo. There is https://github.com/triton-lang/triton/issues/2048 but it's obviously outdated.

Recently this is brought up by Qualcomm developers as they've started porting Triton to Windows ARM, see https://github.com/triton-lang/triton-windows/issues/25 and https://github.com/triton-lang/triton-windows/pull/33 . The first intuitive idea is to disable Nvidia and AMD backends because they don't yet work on Windows ARM. Eventually we decided to make only a small change for now, so we still build with Nvidia and AMD backends, and let them fail at runtime, like what people are currently doing on macOS.

That being said, adding knobs to disable Nvidia/AMD backends is still a useful feature. I have two motivations:
1. Reduce the binary size. Currently in the triton-windows wheel, libtriton takes more than 100 MB, and ptxas takes another 24 MB, even though I've stripped all debug info and unneeded binaries like triton-lsp. The triton Linux wheel is even larger. This is not a small burden for everyone distributing packaged AI tools.
2. Ease the porting of Triton to new platforms, where the LLVM PTXAS and AMDGPU targets are not well supported.

A proposal is at https://github.com/triton-lang/triton-windows/pull/33/changes/155967dd97ce472b0998329985a40df305a8d723?w=1 and surely the design needs more discussion. Notably, the knobs disable some passes in the TTGIR pipeline but not TTIR.

## 评论 (1)

### benkelaya · 2026-09-25

**A macOS arm64 data point: the 155967dd guard set, ported to Triton `4a15f415`, builds a
libtriton with neither in-tree backend, and an out-of-tree backend still loads and runs**

Following up on #11883, where I said we would build @woct0rdho's guard set from
triton-lang/triton-windows `155967dd` on macOS arm64. Here is what we measured.

**Setup.** Apple M4 Pro, macOS 26.6, Python 3.12, LLVM `b010a18d` (the one `4a15f415`
downloads). Triton `4a15f415` (the pin of triton-lang/triton-ext `main` and of #126's
AppleGPU backend). Built with `TRITON_BUILD_NVIDIA_BACKEND=0 TRITON_BUILD_AMD_BACKEND=0`.

**Without the guards it does not build.** With `setup.py`'s backend list emptied and
nothing else changed, CMake generate fails: `The dependency target
"TritonNVIDIAGPUConversionPassIncGen" of target "MLIRDialectPlugin" does not exist`
(`examples/plugins`).

**With the guards ported, it builds and imports.** No MLIR/LLVM symbol is left undefined in
`libtriton.so`, which is 157 MiB against 260 MiB for our both-backend build. No in-tree
backend is discovered. The out-of-tree AppleGPU backend from triton-ext #126 (at `b9d5c06`
plus one local commit, the build we run; not #126's current head), built against it, is
discovered as `apple`, its target (`mps`, `apple_m`) is active, and a torch-free vector
add (n = 4099) returns exact results. The backend's own test suite gives **82 passed, 2
failed, the same as against our regular both-backend build**. The two failures are
`test_torch_free.py`, which runs kernels through `python -c`, where `triton.jit` needs a
source file.

**Limits, stated plainly.**
* **Proton is off** (`TRITON_BUILD_PROTON=0`). Its runtime includes `cuda.h`, which comes with
  the NVIDIA toolchain download that the guard set skips when NVIDIA is off. `155967dd` makes
  the same choice (`need_copy_all = build_nvidia and ...`).
* **The guard set did not apply as is at `4a15f415`: 12 of its 18 files had to be ported by
  hand**, and `4a15f415` needed **eight changes beyond it**. Each was found by a failing build
  or import:
  1. `PartitionLoops.cpp`: the helper namespace now uses NVWS (`nvws::ArefPhiOp`, the
     WarpGroup ops), so the guard covers the helpers, not only `partitionLoop`.
  2. `gluon_ir.cc`: two `third_party/amd/lib` includes, `get_scaled_upcast_fp4_scale_layout`,
     and the bank-conflict helper's `tt::AMD::TargetInfo` are new and need guards.
  3. `llvm.cc`: the AMD guard encloses `translate_mir_to_asm` only (`translate_to_asm` is
     target-neutral), and the NVPTX/AMDGPU target inits are guarded. No native AArch64 init
     is added, because `4a15f415` links no host target.
  4. Core `TritonGPUToLLVM` links `NVGPUIR` unconditionally (`CanonicalizeLLVMIR.cpp`,
     `FuncOpToLLVM.cpp`). We build the NVGPU dialect library (no codegen, no CUDA) when NVIDIA
     is off, one step beyond "always generate the dialect headers".
  5. `bin/` tools register every in-tree dialect, and the lit suite drives them. Both are built
     only with both backends; neither is in the wheel.
  6. `TritonInstrumentToLLVM` emits PTX (`PTXBuilder`, `LLVM::NVIDIA::*`) and is consumed only
     by the NVIDIA and AMD ToLLVM libraries, so it is built only with one of them. Otherwise the
     wheel builds and fails at import on unresolved symbols.
  7. `MLIRReconcileUnrealizedCasts` must be linked directly (`passes.cc` calls it; it used to
     arrive through NVVM/ROCDL).
  8. `gluon/language/amd/cdna5` (new) needs the same import guard as `cdna4`
     (`gfx1250` does not exist at `4a15f415`).
* The Windows-only hunks (STATIC object libraries, the `ARM64` arch key, the symlink
  try/except) are not taken. We ran nothing on Windows.
* This proves "builds, imports, one out-of-tree backend loads and passes its suite" on one
  platform, one pin. It says nothing about CUDA or ROCm builds with the guards ON, which we did
  not build here.

The port is 5 commits on `4a15f415`, 19 files, +297 / -46:
https://github.com/benkelaya/triton/tree/nbx/noback-guards-4a15f415 (each commit names what
it found failing). One thing this does not measure: no guard was reverted on its own, so the
result is that the set is *sufficient* on this platform at this pin, not that each guard in
it is *necessary*. And thanks for the guard set; it is what made the port a matter of
following failing builds rather than searching.
