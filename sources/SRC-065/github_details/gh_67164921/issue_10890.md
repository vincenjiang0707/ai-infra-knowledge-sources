# [Issue #10890] [Bug] TritonGPUToLLVM: tl.histogram on an int8/int16 input produces invalid IR (llvm.icmp operands (i8, i32)) and fails to compile — HistogramOpToLLVM feeds the narrow input into an i32 compare/index without zero-extending

source: https://github.com/triton-lang/triton/issues/10890
state: open | updated: 2026-09-15T00:00:57Z
labels: bug

## 正文

### Describe the bug


`tl.histogram(x, num_bins)` on an `int8` or `int16` input tensor **aborts compilation** (`RuntimeError: PassManager::run failed` inside `ConvertTritonGPUToLLVM`) instead of producing a histogram. The frontend accepts the kernel — `Semantic.histogram` only requires an integer input and hard-codes an `int32` result ([`semantic.py#L1799-L1808`](https://github.com/triton-lang/triton/blob/682f467ab85e6e4e0c5050aa44ccf1a47a65f742/python/triton/language/semantic.py#L1799-L1808), `assert input.dtype.is_int()`, no width restriction) — but the GPU lowering then crashes on that frontend-accepted input, i.e. an ICE-on-valid. `int32` input compiles and runs fine.

## Root cause

`HistogramOpToLLVM.cpp` assumes the input element is `i32`. It feeds the raw input element `srcValues[i]` (which is `i8`/`i16` for a narrow input) directly into an `i32` compare and an `i32` shared-memory index, without zero-extending to `i32` first:

- [`HistogramOpToLLVM.cpp#L39-L41`](https://github.com/triton-lang/triton/blob/682f467ab85e6e4e0c5050aa44ccf1a47a65f742/lib/Conversion/TritonGPUToLLVM/HistogramOpToLLVM.cpp#L39-L41): `Value numBinsValue = b.i32_val(numBins); ... Value updatePred = b.icmp_ult(srcValues[i], numBinsValue);` — compares an `i8` operand against an `i32` operand.
- [`HistogramOpToLLVM.cpp#L50`](https://github.com/triton-lang/triton/blob/682f467ab85e6e4e0c5050aa44ccf1a47a65f742/lib/Conversion/TritonGPUToLLVM/HistogramOpToLLVM.cpp#L50): `b.gep(baseSharedMemPtr.getType(), i32_ty, baseSharedMemPtr, srcValues[i]);` — uses the `i8` element as the (i32-typed) offset.

`llvm.icmp` requires both operands to have the same type, so the pass emits invalid IR and the MLIR verifier rejects it, aborting the pass manager.

## Reproducer

```python
import torch, triton, triton.language as tl

@triton.jit
def hist_kernel(x_ptr, z_ptr, N: tl.constexpr):
    x = tl.load(x_ptr + tl.arange(0, 256))
    z = tl.histogram(x, N)                 # frontend accepts any integer input
    tl.store(z_ptr + tl.arange(0, N), z)

for dt in (torch.int8, torch.int16, torch.int32):
    x = torch.ones(256, device="cuda", dtype=dt)
    z = torch.zeros(4, device="cuda", dtype=torch.int32)
    try:
        hist_kernel[(1,)](x, z, N=4); torch.cuda.synchronize()
        print(f"{dt}: ok -> {z.tolist()}")
    except Exception as e:
        print(f"{dt}: {type(e).__name__}: {str(e).splitlines()[0]}")
```

Observed (NVIDIA L40S, sm_89):
```
torch.int8 : RuntimeError: PassManager::run failed
torch.int16: RuntimeError: PassManager::run failed
torch.int32: ok -> [0, 256, 0, 0]
```

The exact verifier error (via `triton-opt --convert-triton-gpu-to-llvm` on a minimal `tt.histogram` of a `tensor<256xi8>`):
```
error: 'llvm.icmp' op requires all operands to have the same type
note: see current operation: %47 = "llvm.icmp"(%1, %46) <{predicate = 6 : i64}> : (i8, i32) -> i1
```

## Expected behavior

A histogram of an integer tensor of any width should compile (the count is width-independent and the result is `int32` by the frontend contract). One way to do this is to zero-extend the narrow input element to `i32` before the `icmp`/`gep`, matching the width the bins and the shared-memory index already use — e.g. `zext` `srcValues[i]` to `i32` at the top of the per-element loop.

## Disposition

support / crash (ICE-on-valid). The frontend accepts `int8`/`int16` input (it only asserts `is_int()`), so the correct fix is to support it, not to reject — matching the sibling interpreter bug (the interpreter *runs* this input, to a silently-wrong count). Both are the same root: the count/index must be `i32`, independent of the input element width; the compiled path forgets to widen (→ ICE), the interpreter accumulates in the narrow type (→ silent wrap).

Mirrors #10889.

### he-yufeng · 2026-09-15

Current state check on this: the backend still ICEs the same way on main today (`HistogramOpToLLVM.cpp` still feeds the narrow element straight into the `i32` compare and the shared-memory GEP). #11400's closure marked widening to narrow integer inputs as not the direction, and #10376 is covering the documentation side.

The piece nobody has claimed is the middle path that fits both: reject the non-i32 input in the frontend (`Semantic.histogram`) with a clear type error naming the accepted type, instead of letting it reach ConvertTritonGPUToLLVM and die as `PassManager::run failed`. That turns an ICE-on-valid into a proper diagnostic without changing what types are accepted. If that shape is welcome I'm happy to send it with a frontend test; if the maintainers prefer the ICE to stay until a deliberate widening happens, say so and I'll leave it.
