# [PR #11796] [NVIDIA] Support register-staged WGMMA operands

state: open | updated: 2026-09-25T12:39:50Z

## 正文

## Problem

  An s8 or tf32 `tl.dot` whose operands come from TMA descriptors, inside a
  `tl.range(..., warp_specialize=True)` loop, aborts during compilation on SM90:

  ```text
  NVGPUToLLVMPass.cpp: Assertion `supported && "WGMMA type or shape is not supported"' failed.
  ```

  The s8 and tf32 WGMMA forms exist only for untransposed operands, so operand B
  must reach the instruction in a shared layout with `transposed = true`. For
  operand B, `NVMMASharedEncodingAttr::transposed = true` corresponds to
  `transB = false` in WGMMA lowering.

  `AccelerateMatmul` picks exactly that encoding, but the Hopper
  warp-specialization pass rebuilt the buffer encoding in `createBuffer` from the
  producer's register order. This discarded the operand role and left B with a
  layout that WGMMA could not lower.

  ## Fix

  This PR makes four related changes in `third_party/nvidia/hopper/`:

  1. `createBuffer` reuses the encoding of the `LocalAllocOp` that the new buffer
     replaces instead of deriving it again. Since a TMA descriptor cannot describe
     the required transposed layout, the affected channel is staged through
     registers (`descriptor_load` → `local_store`) rather than filled directly by
     TMA.

  2. Consumer groups are split according to how their buffers are actually filled,
     and each group is classified using the operation that performs the fill rather
     than the channel's source operation. Without this split, the register-staged
     channel inherits the TMA channel's completion mechanism and receives neither a
     `ProducerCommit` nor a `ConsumerWait`.

  3. A `fence_async_shared` is emitted in the producer after the staged
     `local_store` and before signalling completion. This publishes the generic
     shared-memory stores to the async proxy used by WGMMA.

  4. A producer group is considered MMA-consuming if any of its channels feeds an
      MMA. Since the group shares one buffer, all such channels must agree on the
      NVMMASharedEncodingAttr. Conflicting requirements now produce an MLIR
     diagnostic instead of silently selecting the representative channel's
     encoding.

  ## Tests

  `test/Hopper/WarpSpecialization/ws_code_partition.mlir` gains three reduced
  pass-level regression cases:

  - one checks that operand B retains its transposed encoding and is staged through
    registers while operand A continues to use TMA;
  - one checks the complete token protocol: token types,
    `local_store` → `fence_async_shared` → `producer_commit`, followed by
    `consumer_wait` before `warp_group_dot`.
 - one checks that code partitioning reports a diagnostic when MMA consumers in
   one producer group require incompatible NVMMAShared encodings.


  The protocol test fails on the intermediate implementation that passed all
  compile-side checks but still produced incorrect results on hardware.

  Compiler-side validation after rebasing onto `dd34455fcf`:

  - clean build;
  - targeted `ws_code_partition.mlir`: 1 passed;
  - full lit suite: 299 passed, 2 unsupported, 0 failed;
  - compile-only int8 and TF32 configurations retained `ttg.warp_specialize`, the
    expected WGMMA instructions, and the register-staged barrier protocol.

  Runtime validation was performed on an H100 PCIe (SM90), with PyTorch
  2.8.0+cu128 and CUDA 12.8, before the reviewer follow-up that adds the
  mixed-encoding guard. On the previously validated shapes, the follow-up
  preserves the operation profile, the ordered sequence of stores, fences,
  arrivals, waits and MMAs, and the set of shared encodings:

  - 30/30 numerical cases passed without instrumentation;
  - the same 30/30 cases passed under active ConSan with no assertion;
  - `python/test/unit/language/test_warp_specialization.py`: 145 passed,
    1432 skipped, 0 failed.

  The numerical matrix covered int8 shapes 64/32/32 and 128/64/32, as well as the
  four TF32 shapes from #11586. Each shape was tested with 1, 2, 3, 4, and 7 K
  tiles. The 4- and 7-tile cases exercise reuse of the three-stage buffers and
  barrier phase changes.

  Int8 results were compared exactly against an int32 CPU reference. TF32 results
  were compared against cuBLAS with a tolerance.

  The validation used `num_warps=4`, `num_stages=3`, `num_ctas=1`, and a 2×2
  grid. FP8, multi-CTA, H200/SXM, and performance were not tested.

  ## Related work

  #11728 replaces the assertion with a diagnostic for genuinely unsupported WGMMA
  forms. This PR fixes the valid s8/tf32 warp-specialized path. The two changes
  touch different files and do not depend on landing order.

  While extending `processProducerCommitOp`, this PR also replaces the
  `report_fatal_error` for the remaining unimplemented token load types with an
  MLIR diagnostic and propagates the failure through `doTokenLowering`. This is
  separate from #11728, which handles unsupported WGMMA encodings in
  `NVGPUToLLVM`.

  Fixes #11586
