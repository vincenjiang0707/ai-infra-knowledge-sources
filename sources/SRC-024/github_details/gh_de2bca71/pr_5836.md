## 正文

## Summary

Follow-up to #5350: add three gfx950/256 A4W4 tuned shapes for the Qwen3.8-27B GDN BA projection, `(M,N,K)=(2|4|24,96,5120)`. The earlier shape generator required N to be a multiple of 128 and omitted N=96. All three rows select the existing `f4gemm_bf16_per1x32Fp4_BpreShuffle_32x128` ASM kernel (kernel ID 21, splitK 0); no kernel implementation or dispatch code changes.

## Measurement and validation

- M=2: 5.5835 µs; M=24: 5.7666 µs, from the original AITER tuner on gfx950. M=4: **5.6658 µs**, measured separately with `run_perftest` using the tuner's `run_gemm_a4w4_blockscale_asm` candidate, 10 warmups and 101 iterations (the same profiling settings used in the full tuner). All three rows have `errRatio=0` against the FP4-dequantized torch reference.
- The broad M=4 tuner sweep faulted on a CK candidate; the isolated measurement invoked **only** the selected ASM kernel. On HIP devices 6 and 7, five M=4 seeds per device passed reference comparison with zero mismatches; kernel times ranged 5.6093–5.6687 µs. The committed M=4 timing, TFLOPS and bandwidth derive from the HIP-6 seed-0 profiler measurement, not from graph replay or the earlier unmeasured trial row.
- With the completed CSV mounted into the pinned image, `gemm_a4w4` selected kernel ID 21 for M=2, M=4, and M=24; five seeds for each shape passed production-op reference comparison on each of HIP 6 and 7, and graph-captured output passed for each shape. The CSV keeps logical K=5120 (FP4 storage has K/2 packed columns).
- `python3 -m unittest op_tests.tuning_tests.test_config_shape_collision -v`: **20 tests passed, zero skips** against a disposable copy of current ROCm/aiter main (`b3d0cf4e0`) with the three rows, using a torch-enabled gfx950 container. The guard exercises runtime merging of the canonical A4W4 CSV and all model-config CSVs. `git diff --check` passed.

## Serving observation and scope

In a pinned SGLang/Quark image, AITER logs confirmed the M=4,N=96,K=5120 row was selected during the trial. Serial baseline/trial TP1 serving runs on each of HIP 6 and 7 reduced batch-four decode **graph replay** time by 6.7–7.8% and increased observed output-token throughput by 6.7–7.2% (32 requests per run). Those runs mounted a trial table containing M=2, M=4 and M=24; they did **not** isolate the M=4 row's individual end-to-end effect. Graph replay time is not full request latency. Repeated token/logprob probes varied even within the same configuration, so these observations are not a claim of model-level output equivalence.

The benchmark image baked its own AITER CSV and set `AITER_CONFIG_GEMM_A4W4` to that baked path; merging this PR alone will not update that image. A refreshed image or mounted CSV is needed to consume these rows.
