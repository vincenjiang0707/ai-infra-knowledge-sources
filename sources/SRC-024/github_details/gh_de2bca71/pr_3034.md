## 正文

## Motivation

This kernel is the AITER-side primitive for a license-clean llama.cpp fork at https://github.com/ssubbotin/llama.cpp/tree/feature/moe-expert-gpu-cache, which adds a `--moe-stream-dir` flag for streaming-MoE inference: active experts live in a per-(layer, projection) VRAM LRU cache and cold experts page in from NVMe SSD on demand. Each cache slot holds one expert at an arbitrary device address; top-k routing picks K slots per token. This kernel consumes that scattered-pointer layout directly, so the engine never has to gather the K active experts into a contiguous slab before dispatch.

End-to-end this lets large MoE models run on GPUs that can't fit the full expert set in VRAM. Measured on the same fork unchanged: Qwen3-30B-A3B-Q4_K_M (17 GiB of weights) streams on a 16 GB RX 9070 XT at **21.72 tg64 tok/s**, with the OS page cache absorbing nearly all the streaming I/O after the first forward pass (cold/warm gap ≈ 13%). The same engine and the same kernel source compile and run unchanged on MI300X (gfx942), RTX PRO 6000 Blackwell (sm_120), RX 9070 XT (gfx1201), and Strix Halo APU (gfx1151) — see the cross-architecture table under [Numbers](#numbers).

## Summary

Adds a Triton MoE matvec kernel that consumes K active experts from K **separate device buffers**, indexed by an array of per-expert device pointers plus a `(token, slot) -> unique-expert` remap. This is the core primitive needed for **streaming-MoE inference**, where expert weights are too large to fit fully in VRAM and live as slots in a per-(layer, projection) LRU cache fed from NVMe SSD on demand.

Existing AITER MoE kernels assume a contiguous `(E, N, K)` expert tensor; the streaming case has the K active experts scattered across K cache slots whose absolute device addresses are only known at dispatch time. This kernel consumes those addresses directly, avoiding the per-dispatch device-to-device slab copy that a contiguous-tensor wrapper would require.

**Format**: GGUF Q4_K_M, the dominant on-disk MoE quantization (super-block of 256 elements, 144 bytes/block: 4-byte `dm` + 12-byte packed scales/mins + 128 bytes of nibbles). The kernel decodes the layout in registers — no host-side repack needed.

**Kernel design**: each program tiles `BLOCK_SIZE_N` output rows for one (token, slot). The Q4_K_M block-loop unrolls the 8 sub-blocks (4 il-groups × low+high nibble), avoiding both 2D gather operations and runtime nibble-position arithmetic. `BLOCK_SIZE_N` is autotuned over `{4, 8, 16, 32}`.

## Validation

The pure-numpy reference dequant is **byte-exact** against `dequantize_row_q4_K` in `libggml.so` (separate cross-validation, 23 random + edge-case blocks). The Triton kernel matches the numpy reference across 8 shapes, from synthetic edge cases to a production Qwen3-A17B-shaped expert (`n_dim_in=2048, n_dim_out=1408, K=8, n_used_per_token=8`).

## ⚠️ Stride contract

Fixed, and you had the failure mode exactly right. The kernel indexes `remap` and `expert_ptrs` by linear offset and walks the last axis of `A` and `C` with unit stride, while the wrapper forwarded only `stride_a_token` / `stride_c_token` / `stride_c_slot`. A `remap = routing_table[:, :k]` slice keeps the parent's row stride, so with `n_used=2` inside a width-4 table the kernel reads stride `(4, 1)` data as if it were `(2, 1)`.

The wrapper now asserts `A.stride(1) == 1`, `C.stride(2) == 1`, and contiguity of `remap` and `expert_ptrs`, with the contract documented on the public function. Nothing is silently made contiguous: that would hide a per-dispatch copy in an inference hot path, and the caller is better placed to hoist it.

Six regression tests cover both failure modes you reproduced, the two strides that stay free (`A.stride(0)`, `C.stride(0)` / `C.stride(1)`), and the documented `.contiguous()` workaround.

## ⚠️ libggml cross-validation

Shipped in-repo, and you were right that the anchor was missing: the byte-exactness claim was real but lived only in my workspace, so nothing in the PR would have caught a layout drift that moved the reference and the kernel together.

`op_tests/triton_tests/moe/test_q4k_vs_ggml.py` plus `data/q4k_ggml_golden.npz`, 13.5 KB: 26 blocks whose fp32 output comes from `dequantize_row_q4_K` in `libggml-base.so` (llama.cpp `98ae0a0d3`). ### ssubbotin · 2026-09-24

@vgokhale Thanks for the direct question. Short answers, and I think they add up to "no":

**Use case.** Running MoE models whose experts don't fit in VRAM. Active experts sit in a VRAM LRU cache at arbitrary device addresses and cold ones page in from NVMe, so the kernel reads each expert through a pointer array instead of a contiguous `(E, N, K)` tensor. The target is a single consumer or APU part running a model larger than its memory, e.g. Qwen3-30B-A3B (17 GiB) on a 16 GB RX 9070 XT.

**Why Q4_K_M.** Only because the one consumer is my llama.cpp fork, and Q4_K_M GGUF is what its users download. There is no technical reason to prefer it: llama.cpp itself supports MXFP4, AITER's MoE kernels already take MXFP4 weights, and gfx942 and the RDNA parts have no FP4 matrix instructions, so both formats get dequantized in software there, MXFP4 being the simpler of the two.

**Does it belong in AITER.** In this form, no. The part that could matter to AITER is the scattered-pointer access (`expert_ptrs` + `remap`), and that would belong on the MXFP4 layout AITER already maintains, with a consumer inside the ROCm stack. I no longer have AMD hardware to build and validate that port, and CI has never run on this PR, so I can't offer it responsibly.

So I'll close this PR. Thanks to you and @zufayu for the time you put into it.
