# [PR #5268] feat(tune): record untuned shapes for every GEMM family, not just bf16

source: https://github.com/ROCm/aiter/pull/5268
state: open | updated: 2026-09-24T22:27:16Z

## 正文

Fixes #5267.

## Why

`AITER_TUNE_GEMM=1` makes `tuned_gemm.py` append every missed bf16 shape to `bf16_untuned_gemm.csv`. That single feature is why tuning a real bf16 deployment is self-service: run the server, collect the CSV, hand it straight back to the tuner.

The fp8 per-token, block-scale and mxfp4 families have no equivalent — they log misses at INFO and write nothing — so their shape lists have to be scraped out of server logs by hand. That is also how shape-key mistakes creep in: we shipped a tuned table that never matched anything because the engine fuses two projections and dispatches `N=2688`, while the tuned rows targeted the unfused `N=2624`. A recorded shape list makes that impossible to miss.

## What

`aiter/utility/untuned_shapes.py` — `record(tuned_file, row)` appends one de-duplicated row **in the schema that family's tuner consumes**. The destination name is derived from the tuned table's own name (`*_tuned_*` → `*_untuned_*`), so a family never has to name its untuned file twice, and a merged `/tmp/aiter_configs` copy still resolves to the right destination.

Wired into the miss paths of:
- `gemm_op_a8w8.get_CKGEMM_config` (block-scale, ± preshuffle) → `M,N,K`
- `gemm_op_a8w8.get_GEMM_config_with_quant_type` (a8w8, a8w8_bpreshuffle) → `M,N,K,q_dtype_w`
- `gemm_op_a4w4.get_GEMM_config` → `M,N,K`

## Behaviour

- Same switch as before (`AITER_TUNE_GEMM=1`) — nothing new to learn; **off by default**.
- `AITER_TUNE_GEMM_DIR` overrides the destination, for read-only package directories and containers (we had to copy the file out of a container image more than once).
- Hot path cost after a shape has been seen is one set lookup; a serving run repeats its shapes, so the append happens a handful of times.
- Never raises. A read-only configs dir or a full disk must not take down inference — it logs a warning and moves on.

## Checked

Name derivation (including the merged-copy path), per-family schemas, de-duplication across repeats, disabled-by-default, and graceful degradation on an unwritable destination.

Same campaign as #5262 / #5263–#5266.

### ThomasNing · 2026-09-19

@yzhou103 Fixed in `158a53ce0`. You were right, and the failure was worse than a lost row.

## What actually happened

Raising on a short count left an unterminated fragment at EOF, and the retry appended the whole row directly onto it. Your example is exactly right — `1,` followed by a retry of `1,2,3\n` produced:

```
M,N,K
1,1,2,3
```

Four fields under a three-column header. pandas rejects that outright, so **one interrupted write cost the entire file**, not one row — and `drop_duplicates()` can't repair a row that isn't a duplicate of anything.

## Why the remainder can't just be written again

Under `O_APPEND` a concurrent worker may have appended between our two writes, so the tail would land after *their* row — corrupting two rows instead of one. That rules out the obvious loop.

## What it does now

The fragment is closed with a **single-byte newline**, which the kernel either writes whole or not at all. The damage stays on its own line, the row stays uncached and retryable, and if even that byte can't be written the recorder remembers it owes a separator so the next append opens a fresh line:

```
M,N,K
1,
1,2,3
4,5,6
```

## The second half of the problem

That's still not something the tuner should consume. `_read_csv` only drops rows that are *entirely* empty, so `1,` survives as `M=1, N=NaN, K=NaN` and would be tuned as a shape with NaN dimensions. `get_untuned_gemm_list` now drops incomplete rows and warns with the likely cause, rather than failing deep inside a kernel launch.

The writer confines the damage; the reader discards it.

## Tests

Including the short-count case you noted was missing — the existing retry test only covered writes that persist nothing:

- a first write that **persists some bytes** before returning short, then a retry — asserts no row ends up with more fields than the header
- the same file parsed by pandas afterwards, asserting both real rows survive
- the torn row is absent from `_SEEN`, so the shape retries
- `get_untuned_gemm_list` skips the incomplete row

I ran these against the **pre-fix** code as a negative control, and the first two fail there with exactly `1,1,2,3` — so they gate the behaviour rather than merely exercising it.

One disclosure: my GPU box's access token expired mid-review, so the ten recorder tests were run in an isolated harness (the module only needs `aiter.logger`) rather than the full suite. The four that import torch — including the new `get_untuned_gemm_list` test — I have not executed locally; the `dropna` semantics behind that one I verified directly against the exact torn input. ### ThomasNing · 2026-09-19

One more fix in `8b8a48996`, found while testing this PR: **`get_CKGEMM_config`'s own default raises.**

Calling it as its signature invites — `get_CKGEMM_config(M, N, K)` with no `tuned_file` — loads `configs/a8w8_tuned_gemm.csv` and dies with

```
ValueError: DataFrame index must be unique for orient='index'
```

which names neither the file, nor the shapes, nor the reason.

## The reason: a schema grew a key column and only one reader learned

- **#1782** (2026-01-12) added `q_dtype_w` to `a8w8_tuned_gemm.csv`. It now holds an int8 row *and* an fp8 row per shape. For gfx950/256 at M=1, N=1280, K=8192: **17.69 µs** on `a8w8_rowwise_256x16x64x512` and **7.68 µs** on `a8w8_rowwise_128x16x32x128`. Both correct — different kernels for different weight dtypes.
- **#2645** (2026-04-17) gave `get_CKGEMM_config` a `(gfx, cu_num, M, N, K)` index. Five columns for a six-column key. **42 shapes collide.**
- `get_GEMM_config_with_quant_type` keys on all six and reads the file correctly.

Latent since April because every in-tree caller passes an explicit `tuned_file`. It surfaces on this branch because the miss recorder has a `uses_quant_schema = tuned_file is None` path that is **unreachable** — the load raises before any miss can be recorded.

## What changed

The load now says what is wrong:

```
.../configs/a8w8_tuned_gemm.csv is not uniquely keyed by
('gfx', 'cu_num', 'M', 'N', 'K'): 42 shape(s) carry more than one row.
Its rows are distinguished by q_dtype_w (torch.float8_e4m3fn, torch.int8),
which this lookup does not key on -- use get_GEMM_config_with_quant_type()
for this table.
```

The two index branches also collapse into one; they differed only in the column list and the warning.

## What I deliberately did not change

The default `tuned_file`, and which row wins. Silently picking one of two kernels that differ by **2.3×** would be worse than refusing. This makes an existing failure legible; choosing a default that actually works is a separate decision with an owner, and I'd rather you make it than have me guess.

Happy to split this into its own PR if you'd prefer it separate from the recorder work — it is in the same function this branch already touches, and it is what makes that branch's quant-schema path reachable, which is why I put it here.

## Verification

Two tests: the colliding table produces a message naming the file, the shape count, `q_dtype_w` and the right function; and a uniquely-keyed table is accepted, so the guard distinguishes the two rather than always firing.

**16 passed** on MI350X (torch `2.10.0+rocm7.2.4`), and the production `a8w8_blockscale_bpreshuffle` lookup is unaffected — verified at M=1/16/256, still resolving to the expected kernels.
