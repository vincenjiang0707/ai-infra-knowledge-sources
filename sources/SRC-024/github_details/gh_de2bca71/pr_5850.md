# [PR #5850] [Triton/Gluon] [Config] Route GLM-5 qkv_a_proj decode tiers to the triton split-K kernel on gfx950

source: https://github.com/ROCm/aiter/pull/5850
state: open | updated: 2026-09-27T02:01:24Z
labels: Triton/Gluon, Config

## 正文

## Motivation

GLM-5's `qkv_a_proj` is `N=2624, K=6144`. At decode sizes every gfx950/256 row for that shape selects a CK blockscale kernel whose tile leaves about 123 workgroups on 256 CUs, so the GEMM never fills the device and runs at the weight's bandwidth floor. The triton split-K preshuffled kernel fills it, but the shape has no triton config, so `--libtype all` never proposes one and the tuner cannot find it.

## Technical Details

- Replace the gfx950/256 `M = 1, 4, 8, 16, 32, 64` rows for `N=2624 K=6144` with `triton` rows.
- Drop the `M = 2` and `M = 48` CK rows. `getPaddedM` rounds `M <= 256` up to a multiple of 16 at `gl=0` and to `nextPow2` at `gl=1`, and the probe returns the first tier that hits. With the `M = 2` row present, `M = 2` stays on CK; with the `M = 48` row present, it catches `M = 33-48` before the probe reaches the `M = 64` triton tier. Both are measured below.
- Add `GEMM-A8W8_BLOCKSCALE_PRESHUFFLED-N=2624-K=6144.json` with a split-K config per M bucket.

## Test Plan

Measured on MI355X (gfx950, 256 CU) against `main` at `766e70d19`, through the production `gemm_a8w8_blockscale_bpreshuffle` dispatch, not by comparing `us` columns. Each arm is a separate process with `AITER_CONFIG_GEMM_A8W8_BLOCKSCALE_BPRESHUFFLE` pointed at the old or the new table (both `get_config_file` and `get_CKGEMM_config` are `lru_cache`d, so one process cannot see two tables). Each arm reports the `libtype` the dispatch actually chose, so a result cannot come from silently running the same kernel twice. CUDA-graph timed, best of five 20-replay rounds.

The benchmark rotates over 32 distinct weights. A single 16 MB weight stays resident in cache and inverts the ranking — CK measures 6.4-7.0 us that way and looks faster — but a decode step walks 78 different `qkv_a_proj` weights, so the bandwidth-bound regime is the one that matters. Arm order was alternated (`a` then `b`) to rule out ordering effects.

## Test Result

| M | CK (a / b) us | triton (a / b) us | ratio |
|---|---|---|---|
| 1 | 14.67 / 14.62 | 6.46 / 6.47 | 0.44x |
| 2 | 14.72 / 14.65 | 7.77 / 7.79 | 0.53x |
| 4 | 14.67 / 14.59 | 7.91 / 7.90 | 0.54x |
| 8 | 14.64 / 14.64 | 8.00 / 7.99 | 0.55x |
| 16 | 14.54 / 14.54 | 8.41 / 8.42 | 0.58x |
| 32 | 14.45 / 14.47 | 9.77 / 9.71 | 0.67x |
| 33 | 14.40 / 14.39 | 9.93 / 10.01 | 0.69x |
| 48 | 14.34 / 14.24 | 10.32 / 10.33 | 0.72x |
| 64 | 14.34 / 14.20 | 10.91 / 10.94 | 0.76x |

The two passes differ by at most 0.5%, and the arms' ranges are disjoint at every M.

**The two dropped rows.** `M = 2` now resolves through `gl=0` to the `M = 16` triton row, and `M = 33` / `M = 48` fall through to the `M = 64` triton row. Those are the `M = 2, 33, 48` lines above: each is faster than the CK row it replaces, so the deletions are not merely reachability changes.

**Numerics.** Relative L2 against a torch fp32 reference is 1.2e-4 to 3.1e-4 for both arms at every M — the two kernels are equivalent. Per-element relative error is not reported because a `K=6144` fp8 dot product cancels to a value far below its terms, so a near-zero output element inflates that ratio without any loss of accuracy.

**Control shape.** `N=6144 K=2048`, which this table does not tune, resolves identically in both arms and times 11.38 / 11.04 / 10.10 us against 11.39 / 11.07 / 10.08 us at `M = 1 / 16 / 64`. No other shape is disturbed.

End to end this ships in a GLM-5.3 MXFP4 stack together with other changes, so no isolated serving number is claimed here.
