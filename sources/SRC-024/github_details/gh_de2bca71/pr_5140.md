## 正文

## Motivation

This PR adds and optimizes a native HIP/MFMA FlashKDA prefill implementation for `gfx942` and `gfx950`.

The work is motivated by the following upstream integration changes:

- ATOM switched the Kimi K3 prefill path to aiter KDA:
  https://github.com/ROCm/ATOM/commit/16c20d3048ea4cf99d1cfc30fa8cbb01ffca12a9
- The aiter Triton KDA implementation was significantly improved:
  https://github.com/ROCm/aiter/pull/4683

After the Triton update, the original native HIP implementation was no longer competitive across the full K3 prefill workload range. This PR reworks the native preparation, recurrence, and output data flow to recover and extend the performance advantage on gfx950.

The primary optimization target is the public Kimi K3 TP8 prefill configuration:

```text
global heads = 96
tensor parallel size = 8
Hq = HV = 12 per rank
K = V = 128
```

The final gfx950 implementation was evaluated across:

- single-sequence prefill from 128 to 16K tokens;
- both fresh and resumed FP32 recurrent state at every tested length;
- uniform multi-sequence batches;
- ragged packed batches;
- multi-sequence resumed prefill;
- public zero-environment backend selection;
- ROCm graph capture and replay.

Across the 20-cell prefill matrix and three random seeds, native HIP is faster than Triton in all 60 measured seed-cells. The geometric mean speedup is `1.403x`, with speedups ranging from `1.030x` to `1.830x`.

This PR additionally adds grouped value attention (GVA) as a functional extension of the native operator. GVA is not the primary performance claim of this PR.

Pure autoregressive decode is outside the scope of this PR. Kimi K3 decode continues to use its existing specialized fused recurrence kernel rather than `chunk_kimi_delta_attn`.

The native implementation is adapted from the HIP/MFMA backend of [MoonshotAI/FlashKDA](https://github.com/MoonshotAI/FlashKDA), source revision `7557ca0`, under the MIT license. The aiter integration, packed-sequence ABI, gfx950 optimizations, dispatch policies, and GVA extension are maintained in this PR.

## Technical Details

### Native operator integration

This PR adds an architecture-specialized FlashKDA forward implementation for `gfx942` and `gfx950` and integrates it with:

- aiter JIT compilation;
- architecture-specific source selection;
- the aiter tensor ABI and pybind layer;
- the public `chunk_kimi_delta_attn` interface;
- ROCm graph capture and replay.

The native path supports the Kimi K3 prefill contract:

- BF16 Q, K, V, and raw gate inputs;
- FP32 or BF16 beta;
- FP32 `A_log` and `dt_bias`;
- `K = V = 128`;
- fused Q/K L2 normalization;
- fused gate processing;
- fused beta sigmoid;
- lower-bounded safe gate processing;
- V-first recurrent state;
- optional FP32/BF16 initial state;
- optional final-state output;
- dense and packed variable-length prefill;
- `int32` and `int64` packed sequence offsets at the Python boundary.

### Preparation fusion and data reuse

The native implementation uses two logical stages:

- K1 prepares the per-chunk operands required by the recurrence.
- K2 performs the recurrent scan and output calculation.

K1 fuses preparation work that would otherwise require multiple launches or repeated global-memory traffic, including:

- Q/K decay transformations;
- restored K operands;
- cumulative gate terms;
- beta activation;
- local inverse/Neumann terms;
- recurrence operands shared with K2.

K1 publishes these values in a layout selected for the corresponding K2 implementation. K2 reuses the prepared operands rather than reloading and recomputing them independently.

K1 and K2 remain separate physical kernels in the general path. The optimization is primarily fusion within K1 and producer/consumer reuse between K1 and K2, with selective fusion inside individual K2/output paths where the workload geometry makes it profitable.

### Shape-adaptive recurrence

The original plain C-split algorithm is retained as one valid route, but it is no longer used for every workload.

The gfx950 policy selects among several recurrence strategies:

- plain C-split;
- direct context processing;
- affine context scan;
- hybrid direct/scan processing;
- persistent and worklist-based variants.

The route is selected from sequence count, sequence length, packed geometry, recurrent-state mode, and the optional maximum-sequence-length hint.

The main algorithmic changes are:

- use a direct path when the recurrence can be completed efficiently without materializing a global scan structure;
- represent long-sequence chunks as affine state transformations so chunk-local producer work can run in parallel;
- restrict the serial scan to the compact cross-chunk state dependency;
- replay the chunk outputs in parallel after the scan;
- use hybrid routing for heterogeneous packed workloads;
- avoid unnecessary prefix construction on eligible paths;
- reuse activated beta, decay values, and recurrent operands between producer and replay stages;
- use persistent worklists to improve load balance for irregular packed inputs.

This keeps the inherently serial portion of the recurrence small while exposing preparation and output work to GPU parallelism.

### gfx950-specific implementation

The gfx950 implementation adds CDNA4-specific tuning, including:

- architecture-specific MFMA fragments and operand layouts;
- fused BT16 preparation;
- BT32 and BT64 merge paths;
- optimized register and LDS state exchange;
- multi-arena recurrence pipelines;
- packed-sequence prefix and worklist handling;
- direct global and K-split context paths;
- affine A/B producer and compact scan paths;
- persistent replay;
- specialized output replay paths;
- graph-stable, shape-based dispatch policies.

The resulting policy covers short launch-bound inputs, long low-batch inputs, large uniform batches, ragged packed inputs, and resumed prefill.

### Public backend routing

The public `chunk_kimi_delta_attn` wrapper supports:

- `backend="auto"`:
  use native HIP for supported calls on `gfx942`/`gfx950`, otherwise fall back to Triton;
- `backend="native"`:
  require native HIP and report an explicit rejection reason for unsupported inputs;
- `backend="triton"`:
  force the current Triton implementation;
- `backend="baseline"`:
  select the original Triton chunked implementation.

With no backend or KDA environment override, supported K3 prefill calls select native HIP automatically.

A host-provided `max_seqlen_upper_bound` is supported for packed inputs. This allows graph-safe route selection without copying device sequence metadata back to the host.

### Native ABI

The implementation provides validated raw-pointer entry points for the latency-sensitive dispatch path:

- raw v1 preserves the original equal-head interface;
- raw v2 appends the graph-safe maximum-sequence-length hint;
- raw v3 appends the Q/K head count required by GVA.

The v2 and v3 interfaces preserve the preceding ABI argument layout.

The adapter validates:

- tensor shapes and dtypes;
- dense and packed sequence geometry;
- recurrent-state layout;
- workspace capacity;
- GVA head ratios;
- active device;
- stream ownership;
- architecture support;
- graph-safe routing bounds.

### GVA functional support

The native operator additionally supports grouped value attention when:

```text
HV >= Hq
HV % Hq == 0
```

Value, gate, and state heads are mapped to Q/K heads using:

```text
qk_head = value_head // (HV / Hq)
```

The GVA implementation covers:

- ratio-2 and ratio-4 head mappings;
- dense and packed layouts;
- fresh and resumed prefill;
- optional final-state output;
- empty packed sequences;
- descriptor and raw-v3 equivalence;
- ROCm graph capture and replay.

GVA is an operator-level compatibility feature. The primary performance results in this PR use the current public Kimi K3 equal-head geometry, `Hq=HV=12`.

```text
Hq = HV = 12
```

```text

ragged-16K fresh
```

The formal comparison uses:

```text
backends:                    public zero-env HIP vs forced Triton
seeds:                       42, 43, 44
warmup:                      20 iterations
measurements:                120 per backend/cell/seed
execution:                   ROCm graph replay
measurement order:           alternating and position-balanced
paired bootstrap resamples:  10,000
relative-RMS tolerance:       0.04
```

A performance cell passes only when:

1. HIP p50 is faster than Triton for every seed.
2. The paired HIP win fraction is greater than 50% for every seed.
3. The upper bound of every per-seed paired-p50 95% bootstrap confidence interval is below zero.
4. The upper bound of the cross-seed paired-p50 95% bootstrap confidence interval is below zero.

The regular benchmark entry point can be used for reproduction:

```bash
python op_tests/op_benchmarks/triton/bench_flash_kda_native.py \
  --suite core \
  --heads 12 \
  --value-heads 12 \
  --backend native \
  --backend triton \
  --execution graph \
  --public-k3 \
  --warmup 20 \
  --repeat 120 \
  --seed 42 \
  --tolerance 0.04 \
  --require-arch gfx950 \
  --require-compute-units 256
```

The same benchmark is repeated for seeds `43` and `44`, and for each single sequence length with a nonzero FP32 initial state.
