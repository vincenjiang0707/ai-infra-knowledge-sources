## 正文

## Summary

`get_kernel_config_triton` hardcodes `block_k=256`, `block_n=512` and `num_stages=1` for every architecture. Those suit CDNA4's 160 KiB of LDS; CDNA3 has 64 KiB, so the gfx942 prefill tile runs at very low occupancy.

This routes the kernel through the tuned dispatch that `a8w4` already uses and ships a gfx942 table for DeepSeek-V4.1-Flash at TP4 and TP8.

- `get_moe_dispatch("A16W4", get_arch(), "triton")`, keyed by `bm<block_m>_n<N>_k<K>`
- `configs/gfx942/triton/moe/a16w4/DEFAULT.json`, 8 entries

`get_moe_dispatch` returns `{}` when no file is shipped, so untuned architectures are unaffected. On gfx942 only the 8 listed prefill shapes change; decode (`block_m` 16/32) and unlisted shapes keep the existing defaults.

## Results

## Notes on Tuning

No a16w4 tile tuner exists in-tree, so the entries come from a sweep over all six knobs the kernel forwards to the launch.

Worth knowing when adding shapes:

- `block_k=64` compiles only with `matrix_instr_nonkdim=32`, and it wins at `block_m=128` on most shapes. Sweeping with `nonkdim` fixed hides it entirely.
- `block_n=256` won on every shape; the stock 512 never did.

## Tests

- All 8 entries verified resolving to the measured tiles against a live install; decode and unlisted shapes confirmed returning the existing defaults.
- Tuned vs stock output differs by exactly 0.5 bf16 ULP, caused by `block_k` changing the K-split. `block_n`, `num_stages` and `num_warps` are bit-identical.
- GSM8K 8-shot (200 examples, chat endpoint): 0.905 exact_match (flexible-extract) on both the tuned and stock-tile arms are identical.

## Limits

- Measured on MI325X. gfx942 also covers MI300X, which shares the 64 KiB LDS but not the memory bandwidth; untested there.
- TP4 and TP8 only. TP2 needs ~287 GiB/GPU for this model and cannot load.

### vgokhale · 2026-09-25

# Review: PR #5667 — a16w4 MoE GEMM gfx942 tuned config

The config table and wrapper wiring are good: `DEFAULT.json` lands in the correct `configs/gfx942/triton/moe/a16w4/` tree, resolution goes through the standard `get_moe_dispatch → resolve_config_dir` path, and the wrapper does config-first with a clean fall-through to the stock heuristic. The `arch=arch` plumbing in `get_moe_dispatch` is a sensible addition.

My concern is `test_moe_gemm_a16w4_config.py`. I think it's substantially over-built for what this PR needs, and it sets a precedent no other tuned kernel follows.

## What actually needs testing here

There is one real gap: the existing numerics test (`test_moe_gemm_a16w4.py::test_op`) skips unless `arch_info.is_fp4_avail()` (gfx950/gfx1250), so the new **gfx942** table ships un-exercised. That justifies a narrow check — "the tuned entries resolve to the kernel on gfx942" — nothing more.

## What the test actually does

Of the six test functions, only two are about *this config*:

- `test_table_matches_measured_tiles` / `test_measured_tile_reaches_the_kernel` — verify the shipped table equals the measured tiles and reaches the kernel. Keep the essence of these (arguably one suffices).

The other four are testing the **shared dispatch framework**, not the a16w4 table:

- `test_decode_block_m_untouched`, `test_unlisted_prefill_shape_falls_back`, `test_other_arch_unaffected` — these assert `get_moe_dispatch` / `get_kernel_config_triton` fall back to the stock heuristic on a miss and don't leak across archs. That behavior is identical for a16w4, a4w4, a8w4, and every future table.
- `test_block_k_64_pairs_with_nonkdim_32` — a property of the config space, not the shipped values.

Roughly half the file (`_UNTUNED_ARCH`, `_stock_config`, the `on_gfx942` fixture, the `get_moe_dispatch.cache_clear()` dance, the `_Routing` mock) exists only to support those framework tests. That's the general-purpose testing we don't want in a per-kernel config PR.

## No other kernel does this

- a4w4 and a8w4 use the same `get_moe_dispatch` pattern and have **no config-resolution test at all** — just their numerics tests. This is the only `*_config.py` in the moe test dir.
- The established convention is to validate a tuned table *implicitly through numerics*: e.g. `test_gemm_a8w8.py` calls `get_gemm_config(...)`, runs the kernel with the resolved config, and checks the output. Nobody asserts "JSON == measured tuples" or hand-tests fallback/arch-scoping.

So this introduces a bespoke per-kernel config-test pattern with no precedent, and inconsistently: if a16w4 needs it, a4w4/a8w4 need it too. Either the framework is trusted (this is unnecessary) or it needs testing once, centrally (this is the wrong place).

## Suggested direction

1. **For the a16w4 gap:** extend the existing numerics test to run a gfx942 resolution/compile smoke over the tuned shapes, matching how a4w4/a8w4 are already covered — rather than a standalone 154-line file. If you want an explicit "table == measured" pin, keep just that one assertion (it's the one genuinely a16w4-specific, anti-tautology check).
2. **For the framework behavior** (fallback on miss, arch-scoping, and the new `arch=arch` resolution — the one actually-new behavior in this PR): put it in a single `test_moe_config_utils.py` for `get_moe_dispatch`, parametrized over the shipped moe tables. Test the contract once, not re-implemented in every future config PR.

Net: the table is fine; the test is testing shared plumbing through one kernel's keyhole. Trim it to the a16w4-specific check and move the dispatch-contract coverage to the framework, so we don't set a heavy per-kernel precedent for something the numerics tests already cover everywhere else.
