## 正文


## Motivation

Add tuned gfx950 A4W4 fused MoE configurations for the DSV4.1 TP2 execution path.

Before this change, the following DSV4.1 TP2 shapes could not find a matching tuned configuration and used the heuristic FlyDSL fallback:

- DSpark draft: `H=5120, I=1152, E=128, topk=3`
- Target model: `H=5120, I=1152, E=384, topk=6`

This PR tunes both shapes across token counts from `1` to `32768` and reduces fused MoE latency compared with the heuristic fallback at every tested token size.

## Technical Details

- Add 32 gfx950 tuned A4W4 fused MoE configurations:
  - 16 configurations for `H=5120, I=1152, E=128, topk=3`
  - 16 configurations for `H=5120, I=1152, E=384, topk=6`
  - Token counts: `1, 2, 4, ..., 32768`
- Use the selected `MXMOE G1 + FlyDSL layout-v2 G2` kernel combination.
- Add MXFP4 MoE auxiliary sort support for:
  - `(128, 5120, 1280, 3)`
  - `(384, 5120, 1280, 6)`
- `1280` is the auxiliary kernel's internally aligned support dimension; the runtime and tuned CSV intermediate dimension remains `1152`.
- Add `AITER_MXFP4_TUNE_SWIGLU_LIMIT` handling so tuning, reference execution, and configuration replay use the DSV4.1 `swiglu_limit=10` consistently.

The scope of these configurations is the DSV4.1 TP2 direct MXFP4 path. This PR does not claim general MXMOE support for EP or communication-fused MoE paths.

### Full-model serving A/B

DSV4.1 TP2 DSpark, ISL 1024, OSL 256, concurrency 16, 320 measured requests
after 32 warmups. `A` uses this PR's tuned CSV and `B` uses an empty CSV to
force the heuristic FlyDSL fallback. The runs were performed in A/B/A/B order
on `crsuse2-m2m-068`.

| Run | Path | Output throughput | Mean TPOT | Median TPOT | >5 s token gaps |
|---|---|---:|---:|---:|---:|
| A1 | Tuned | 1383.13 tok/s | 10.161 ms | 10.252 ms | 0 |
| B1 | Fallback | 1134.93 tok/s | 12.539 ms | 10.670 ms | 14 |
| A2 | Tuned | 1338.94 tok/s | 10.048 ms | 10.143 ms | 0 |
| B2 | Fallback | 1427.15 tok/s | 9.965 ms | 10.170 ms | 0 |

The B1 fallback leg was contaminated by a shared-node pause of approximately
12.14 seconds, so raw throughput from that pair is not representative. In the
stable A2/B2 pair, median TPOT is 0.26% lower with tuning, while raw throughput
is 6.18% lower. Across both pairs, the geometric mean of median TPOT shows a
2.11% tuned improvement. The hit checks confirmed 0 fallback warnings in both
tuned legs and 80/76 fallback selections in B1/B2.

### Full-model trace A/B

A second matched run profiled only the measured request window: 16 warmups,
16 measured requests, ISL 1024, OSL 256, concurrency 16. Both trace windows
were stable and had no multi-second token gap.

| Metric | Tuned | Fallback | Tuned vs fallback |
|---|---:|---:|---:|
| Output throughput | 1463.02 tok/s | 1352.05 tok/s | **8.21% higher** |
| Duration | 2.800 s | 3.029 s | **7.58% lower** |
| Mean TPOT | 6.111 ms | 6.238 ms | **2.04% lower** |
| Median TPOT | 6.035 ms | 6.128 ms | **1.52% lower** |
| P99 ITL | 21.819 ms | 21.986 ms | **0.76% lower** |

GPU kernel time was normalized per logical MoE call and averaged across both
TP ranks:

| Fused-MoE component | Tuned | Fallback | Tuned vs fallback |
|---|---:|---:|---:|
| G1 | 120.97 us | 116.75 us | 3.61% slower |
| G2 | 65.50 us | 68.67 us | 4.61% faster |
| External sort/quant | 0.35 us | 14.60 us | 97.63% lower |
| G1 + G2 + external sort/quant | 186.82 us | 200.02 us | **6.60% faster** |

G1 alone is not the source of the gain. The tuned path combines a 4.61%
faster G2 with MXMOE inline sorting, removing approximately 14.25 us of
external sort/quant work per logical MoE call. The resulting fused-MoE core is
6.60% faster. The trace-window throughput includes profiler overhead and is
used to explain the kernel-level effect rather than replace the longer
non-profiled benchmark.

### GSM8K accuracy regression

Full 1,319-question GSM8K, 5-shot, greedy decoding:

| Validation | Topology | Flexible extract | Strict match |
|---|---|---:|---:|
| Previous DSV4.1 FP4 reference | TP4 | 0.9242 +/- 0.0073 | 0.9234 +/- 0.0073 |
| This PR, tuned configurations | TP2 | 0.9280 +/- 0.0071 | 0.9272 +/- 0.0072 |

The current tuned result is +0.38 percentage points on both filters and is
well inside the combined statistical error. Because the reference and current
runs use different TP topologies, this is an accuracy-regression comparison,
not a claim that tuning improves model quality. During the TP2 GSM8K run, the
server selected the tuned path for both DSpark and target shapes and emitted no
heuristic fallback warning.
