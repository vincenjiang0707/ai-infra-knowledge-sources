# [PR #5182] [JIT] Identify MI350P, and stop hardcoding the XCD count

source: https://github.com/ROCm/aiter/pull/5182
state: open | updated: 2026-09-24T15:51:56Z
labels: ci:all, Triton/Gluon, JIT

## 正文

## Motivation

1. **`get_device_name()` misreports MI308 as MI300 on ROCm 7.1 and newer.**
   `_get_pci_chip_id` hardcoded `hipDeviceAttributePciChipId = 10019`, but 7.1 inserted
   `MaxAvailableVgprsPerThread` ahead of it and renumbered everything after. The call still
   succeeds and still returns an integer, so the result is tested against `MI308_CHIP_IDS`
   and silently misses.

2. **MI350P was not identified at all.** It is a half-size gfx950 (4 XCDs against 8 on
   MI350X/MI355X), and `get_device_name()` returned `"MI350"` for it.

3. **The XCD count was hardcoded to 8**, with a comment saying it could not be queried. It
   can, from ROCm 7.0 on. On a 4-XCD part every `remap_xcd` consumer computes its L2
   locality swizzle against the wrong die count.

## Test Result

Three parts, all HIP 7.2. Top four rows are raw HIP and sysfs reads, bottom three are what
aiter's shipped functions return:

| | MI300X (gfx942) | MI350P (gfx950) | MI355X (gfx950) |
|---|---:|---:|---:|
| raw `NumberOfXccs` (10018) | 8 | **4** | 8 |
| raw `PciChipId` old (10019) | 512 | 512 | 512 |
| raw `PciChipId` new (10020) | `0x74A1` | `0x75A8` | `0x75A3` |
| sysfs device id | `0x74A1` | `0x75A8` | `0x75A3` |
| `get_num_xcds()` | 8 | **4** | 8 |
| `_get_pci_chip_id()` | `0x74A1` | `0x75A8` | `0x75A3` |
| `get_device_name()` | `MI300` | **`MI350P`** | `MI350` |

`10019` returns 512 on every part because it is `MaxAvailableVgprsPerThread`, not a chip id.
`10020` matches sysfs everywhere. MI355X is the negative control for the new name: same
architecture as MI350P, 8 dies rather than 4, so it stays `MI350`.

Reproducible with a ctypes read of attributes 10018/10019/10020 cross-checked against
`/sys/bus/pci/devices/<bdf>/device`.

**On MI308 this is inference, not observation**. `10019` returned 512 on all
three parts above, `MaxAvailableVgprsPerThread` is an architectural constant, and MI308 is
gfx942 like the MI300X measured, so it returns 512 there too and 512 is not in
`MI308_CHIP_IDS = {0x74A2, 0x74A8, 0x74B6, 0x74BC}`. Untested: a ROCm < 7.1 box, where the
guard should still select 10019.

## Notes

**Why the die count and not the chip id.** MI350P reports `0x75A8`, which hipBLASLt's
Tensile table lists as [`mi350-unknown1`](https://github.com/ROCm/rocm-libraries/blob/develop/projects/hipblaslt/tensilelite/include/Tensile/AMDGPUPredicates.hpp#L69), alongside a sibling `0x75B8`. 
So it's unclear those ids can be considered stable enough.

**What the die count does not distinguish.** Compute partitioning (SPX/DPX/TPX/CPX) means a
partition sees a subset of the dies, so a DPX-partitioned MI350X would also report 4 XCCs
and be named `MI350P`. That may be wanted, but it deserves a comment either way.

## Review (SKU identity / non-comm enablement)

Fits [SILOTIGER-971](https://amd.atlassian.net/browse/SILOTIGER-971) / [SILOTIGER-975](https://amd.atlassian.net/browse/SILOTIGER-975): live `NumberOfXccs` is the right discriminator for the L2 swizzle (4 vs 8 dies). Hardcoded `NUM_XCDS=8` inside kernels remains [SILOTIGER-977](https://amd.atlassian.net/browse/SILOTIGER-977) and is correctly out of this PR. CU-count tuning identity is #5340, not this change.

Successful path looks right: ROCm 7.1 `PciChipId` ordinal, per-device XCC cache (addresses the earlier device-0 Copilot note), shared `hip_runtime` loader, and existing `get_num_xcds()` consumers that already pass the live value.

**Request changes** on the failure / naming contract before merge:

1. **Silent fallback to 8 XCCs / device 0.** `get_current_hip_device` and `get_num_xcds` turn query failures into values that are also valid topology. A 4-XCC gfx950 that fails `NumberOfXccs` keeps the old 8-XCD swizzle with only a warning. Prefer an explicit failure (or a fallback that cannot be confused with a real 8-XCC part).

2. **`get_device_name() == "MI350P"` from XCC count.** HIP `NumberOfXccs` is the *partition* die count. DPX on an 8-XCC gfx950 is named MI350P. The PR body already flags this; either document that the name is a partition class, or name the physical SKU from PCI chip id and keep XCC count as separate topology.

3. **Mixed device sources.** PCI/XCC now follow the current HIP device; `get_gfx()` is still a process-wide cached build/native arch. `get_device_name` can pair gfx942 architecture with another device's XCC/PCI facts.

4. **No focused tests.** The old PCI bug returned a plausible integer and did not fail a GPU op test. Add a host-side synthetic HIP-library test for 7.0 vs 7.1 ordinals, attribute failure, `set_device`, and per-device cache isolation.

I did not run this on a 4-XCC part or MI308. Series comments on #5340 / #5341 / #5342 will follow.
