## 正文

### Motivation
Using gluon instead of triton for performance improvement

### Technical Details

- Current implementation of quantization in triton has a software emulation of the same.
- Utilize the hardware implementation in gluon to speed up the process.
- The layout heuristic has been modified to better suite the shapes we need to process.
- Implement pre-fetch for certain layouts in gluon.
- Changes are all related to gluon. Triton remain same as before.

### Test Plan
Test suite as well as benchmark script for speed of quant kernel. Test script for verifying accuracy.

# Review: PR #4383 — Gluon MXFP4/MXFP8 quant (gfx950)

The kernel and the gfx950 perf are good (clean 1.06–1.46× across the board, so an unconditional gfx950→gluon dispatch is fine). But there are four things to fix, the biggest being that this invents a config mechanism the repo already has.

## 1. The `rules` config schema is a new invention — use the existing bucket-key format

`select_tuned_config()` + the `{"default", "rules":[{"if","set"}]}` schema is a **second config format and a second resolver**, and nothing else in `configs/` uses it — I grepped the whole tree. The repo already has a JSON, range-based, multi-axis shape→config system: the `unified_attention` format, e.g.

```
"D_LEQ_128.Q_LEQ_1": {...},   # axes joined by '.', only the ones that matter
"Q_GEQ_256.DT_fp8_fp8": {...},
"D_GEQ_512": {...}
```

resolved by a documented `_lookup` (walks axes in schema order; LEQ ascending, then GEQ descending, then `any`; leftmost axis wins). That already expresses exactly what these rules express — M/N/K thresholds selecting a tile — and it's already tested.

### The right way to replace the rules

Convert each rule *region* into a composite bucket key and write the **complete, flattened** config for that region (one bucket wins, no stacking). Resolve with the existing `_lookup` and delete `select_tuned_config`.

Worked example — the current mxfp4 rules:

```json
"default": { "NUM_ITER": 2, "BLOCK_SIZE_M": 64, "BLOCK_SIZE_N": 64, "NUM_WARPS": 4, "NUM_STAGES": 2 },
"rules": [
  { "if": {"M_leq": 32},                 "set": {"NUM_ITER": 1, "NUM_WARPS": 4, "NUM_STAGES": 1} },
  { "if": {"M_gt": 32, "N_leq": 16384},  "set": {"BLOCK_SIZE_M": 32, "BLOCK_SIZE_N": 256} },
  { "if": {"N_leq": 1024},               "set": {"NUM_ITER": 1, "NUM_WARPS": 4, "NUM_STAGES": 1} }
]
```

flatten to the established format (each entry complete):

```json
"M_LEQ_32":              { "NUM_ITER": 1, "BLOCK_SIZE_M": 64, "BLOCK_SIZE_N": 64,  "NUM_WARPS": 4, "NUM_STAGES": 1 },
"M_GEQ_33.N_LEQ_1024":   { "NUM_ITER": 1, "BLOCK_SIZE_M": 32, "BLOCK_SIZE_N": 256, "NUM_WARPS": 4, "NUM_STAGES": 1 },
"M_GEQ_33.N_LEQ_16384":  { "NUM_ITER": 2, "BLOCK_SIZE_M": 32, "BLOCK_SIZE_N": 256, "NUM_WARPS": 4, "NUM_STAGES": 2 },
"any":                   { "NUM_ITER": 2, "BLOCK_SIZE_M": 64, "BLOCK_SIZE_N": 64,  "NUM_WARPS": 4, "NUM_STAGES": 2 }
```

Two things this buys, beyond conforming to precedent:
- **It's unambiguous.** With the rule-tree, the config for a shape depends on replaying every matching rule in list order (mxfp8's rules 2/3/4 overlap and stack — you can't read off the effective config). One-bucket-wins removes that.
- **It surfaces dead logic.** Flattening shows rule 3 (`N_leq 1024`) is a no-op for the `M_leq 32` region — rule 1 already set those same values. The rule-tree hid that; the bucket table makes it obvious.

If range-based selection needs to be callable from the quant path specifically, reuse/generalize the *existing* `_lookup` (promote it into `config_utils` as a documented, tested helper) — that's extending the one system, not adding a parallel one. If there's a genuine reason the bucket format can't express these (I don't see one), that case should be made explicitly, because right now it fragments the config system into two schemas for two quant kernels.

## 2. Rule 1 (repr) — missing on the launched Gluon kernels

`gluon_dynamic_mxfp4_quant_kernel_gfx950` and `gluon_dynamic_mxfp8_quant_kernel_gfx950` are bare `@gluon.jit` with no `repr=`/`make_kernel_repr`. Every launched kernel needs a config-aware repr (device helpers are exempt). Add them, same as the other tuned kernels.

## 3. Top-level Gluon import breaks the established import-safety pattern

The wrapper imports the Gluon kernels at module top:

```python
from aiter.ops.triton._gluon_kernels.gfx950.quant.quant import (
    gluon_dynamic_mxfp4_quant_kernel_gfx950, gluon_dynamic_mxfp8_quant_kernel_gfx950,
)
```

and that module does `from triton.experimental import gluon` at top. So importing `aiter.ops.triton.quant.quant` — a very widely used module — pulls in the Gluon dialect unconditionally and will **raise on any build without `triton.experimental.gluon`** (older Triton / non-gluon platforms). The established pattern (`gemm/basic/gemm_a16w16.py`) keeps Gluon out of top-level imports and lazily imports it *inside* the `get_arch()` branch. Follow that: gate on `get_arch() == "gfx950"`, import the gluon kernels inside the branch.

## 4. Config-dir naming diverges from the gfx1250 sibling

This PR ships `configs/gfx950/gluon/quant/**mxfp4_quant**/` (and `mxfp8_quant`), while the gfx1250 sibling (#4894) uses `.../quant/**quant_mxfp4**/`. Same author, same kernel, two arches, two different directory names (hence two different `config_name`s). Pick one and align both.

## 5. Tests — minor

- Dtypes are clean: `@pytest.mark.parametrize("dtype", [torch.bfloat16])`, no fp16/fp32. Good.
- Shapes (5 added per test) are mostly distinct regimes, but `(16384, 7168)`, `(6000, 5000)`, and `(3333, 4004)` all cover "large, non-square" — drop one; ~4 distinct regimes (tiny-M, medium, large, one non-pow2 for masking) is enough.
- No config-resolution test, and that's correct — the numerics tests exercise the resolved config on gfx950, consistent with the other quant/moe kernels. Don't add a bespoke one.

## Summary

Good kernel, real gfx950 win. Blockers before merge: replace the invented `rules` schema with the existing composite bucket-key format + `_lookup` (flattened, complete configs, delete `select_tuned_config`); add `repr=` to the two launched kernels; make the Gluon import lazy per the `gemm_a16w16` pattern; and reconcile the config-dir name with #4894. The test matrix just needs a shape trimmed.
