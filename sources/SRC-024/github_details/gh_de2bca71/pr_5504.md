# [PR #5504] Fix the hardcoded die and CU counts in the FlyDSL kernels

source: https://github.com/ROCm/aiter/pull/5504
state: open | updated: 2026-09-25T15:47:18Z
labels: 

## 正文

Stops the FlyDSL kernels folding program ids into eight dies and sizing persistent grids for 256 units on parts that have neither. The count now comes from the device at dispatch, and from the target a job names at AOT build time.

Stacked on #5182, which resolves device identity from the live device rather than the first agent rocminfo reports. Independent of the `AITER_GPU_TARGETS` stack: the AOT half keys on the `cu_num` already carried by each CSV row, not on that build variable.

## Motivation

Every FlyDSL kernel whose program-id round-robin folds by a die count assumed eight, and the two-stage persistent grids assumed 256 units. That is already wrong on a part in the field: MI308X is gfx942 with 80 CUs and four dies, and aiter ships 3045 tuned rows for it. It is wrong again on MI350P, which is gfx950 with 128 CUs and four dies.

## Technical Details

**1. The count enters the kernel name asymmetrically, and that asymmetry is load-bearing.** The second-stage bodies run the round-robin at every swizzle value, so their names carry the count unconditionally. The first-stage bodies only emit it above swizzle zero, so theirs carry it only there. Making them uniform in either direction aliases a four-die kernel with an eight-die one in the cache. Each site says so.

**2. The signatures keep a default of eight.** Around twenty of them, so out-of-tree callers keep working. The cost is that a caller who omits the argument silently gets eight. Every in-tree caller passes the queried value.

**3. The table of non-default parts has to grow as SKUs land.** It names three, and anything absent takes the default with nothing reported.

**4. The AOT half asks the target, not the build host.** A release builds on a machine that is not the part being built for, so asking the local device would bake the wrong count whenever they differ.

**5. A 228 CU part now resolves to gfx942.** The arch lookup did not name it, so a row carrying that count and no arch column resolved to gfx950, which selects the compile target and not merely the die count. No shipped CSV carries 228, so nothing built today changes.

### Scope

FlyDSL only. The C++ and opus sites are untouched, roughly fifteen of them, and have no kwarg seam of the kind that made this mechanical here. Two literals there have to agree for the mapping to stay bijective, which is a separate change.

## Test Plan

AOT job collection for every `OpKind`, the dedup keys it builds, module imports at each commit, `ruff` and `black`.

## Test Result

Collection matches the base exactly at 781 mxfp4 MoE, 1948 MoE and 3428 GEMM jobs, with the same dedup ratio. Each of the three commits imports on its own. Clean.
