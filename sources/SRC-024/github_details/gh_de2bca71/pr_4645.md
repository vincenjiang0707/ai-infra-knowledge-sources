## 正文

## Summary

Adds an opt-in gfx942 Gluon FP8 prefill kernel for packed variable-length attention with 12 heads, D192 Q/K, and D128 V. The kernel returns BF16 output and natural-log LSE so it can be merged across chunked context segments.

## What this PR does

- Adds the gfx942 FP8 attention kernel and split reduction path.
- Adds dynamic and static per-head FP8 quantization for Q, K, and V.
- Lets calibrated callers supply immutable descales and caller-owned outputs without the partial-amax and reduction kernels.
- Exposes an architecture-guarded public entry point without changing the default attention dispatch.
- Adds synthetic gfx942 coverage for quantization, asymmetric values, causal prefill, non-causal context attention, and HIP graph replay.

## Validation

Remeasured on MI325X against current AITER FMHA v3 BF16 ASM (`fmha_fwd_hd192x128_bf16_causal_rtna_group` and `fmha_fwd_hd192x128_bf16_rtna_group`). Kernel-only medians. 5 warmup plus 20 CUDA-event iters. Quantization is not included in the FP8 kernel column. The FP8 tile is `BLOCK_M` 256, `BLOCK_N` 64, `NUM_KV_SPLITS` 3, `DIRECT_REGISTERS` True, `KV_BUFFERS` 1, `waves_per_eu` 1, `num_warps` 4.

- Early 4K/4K causal: 0.172 ms BF16 to 0.347 ms FP8 (0.50x).
- Mid 4K/65K non-causal: 4.385 ms BF16 to 3.539 ms FP8 (1.24x, 19.3%).
- Late 4K/65K causal: 4.193 ms BF16 to 4.660 ms FP8 (0.90x).

The synthetic gfx942 suite still passes all nine cases. Correctness against dequantized BF16: early out_max 0.0498, mid 0.00092, late 0.00098.

The remaining kernel win is the non-causal 4K/65K context chunk. The entry point stays opt-in.

## Notes / scope

This entry point is intentionally opt-in and restricted to gfx942, 12 heads, D192 Q/K, D128 V, BF16 output, and packed variable-length inputs. The vLLM integration is submitted separately. Rebased onto current main. The gfx942 FP8 tile now uses register K/V and 4 warps.

🔴 [verified] aiter/ops/triton/_gluon_kernels/gfx942/attention/mha.py allocates the KV-split partials with torch.empty, lets a split whose split_start_block >= n_blocks return without writing anything, and then merges all NUM_SPLITS=3 partials in _split_attention_reduce — at seqlen_k=200 or 256 (cdiv(seqlen_k,64)=4) or any short sequence packed next to a long one (k=100 beside k=4096), split 2's slice is uninitialized and the merged output is NaN/garbage whenever the allocator reuses dirty pages (reproduced on MI300X with a poisoned pool; k=257 and k=180 controls pass, and the unpoisoned k=200 run passes only because a fresh pool happened to be clean). **Author must** zero-init the partial buffers (or skip unwritten splits in the reduce) and add a regression test at cdiv(seqlen_k,64) in {1,2,4}.

⚠️ [verified] op_tests/triton_tests/attention/test_kimi_k3_fp8_prefill_gfx942.py skips unless arch == gfx942, but the default Triton CI job runs on MI35X (gfx950) runners and the MI300X job requires the ci:triton-300x label, which this PR does not carry — all 9 new tests skip in every CI run, so the only execution evidence is the author's local MI325X run and the split-boundary defect above is invisible to CI. **Author must** add the ci:triton-300x label (or a gfx942 CI lane) so the suite actually runs before merge.

⚠️ [verified] aiter/ops/triton/quant/per_head.py: _per_head_quantize was hardened to int64 index arithmetic (follow-up 6617e0a99, "Index arithmetic is now 64-bit") but _per_head_absmax_partial in the same file still computes token*stride_t in int32 — at [1000000,12,192] bf16 the absmax kernel faults the GPU (verified on MI300X; a [900000,...] control with the identical reduce BLOCK=65536 is exact), so dynamic_per_head_quant_fp8 crashes on any input past ~932K tokens with no documented bound. **Author must** widen _per_head_absmax_partial's offsets to int64 like its sibling kernel or assert a token bound.

⚠️ [verified] aiter/ops/triton/_gluon_kernels/gfx942/attention/mha.py: _get_config hardcodes the whole tile (BLOCK_M=256, BLOCK_N=64, NUM_KV_SPLITS=3, DIRECT_REGISTERS, KV_BUFFERS, waves_per_eu=1, num_warps=4) in kernel source, while the gfx950 twin of the same function loads its tile from the tuned-config JSON (AITER_TRITON_CONFIGS_PATH/{arch}/gluon/attention/mha/mha.json) — the tuning sweep can neither see nor overwrite this tile, and it was tuned on MI325X only. **Author must** move the tile into the tuned-config JSON like the gfx950 path so sweeps and other gfx942 SKUs can retune it.

📝 [verified] kimi_k3_fp8_prefill_gfx942 in aiter/ops/triton/attention/mha.py also accepts all-BF16 Q/K/V (the wrapper asserts explicitly permit it) and no test in the PR covers that path — hand-run on MI300X at 128q/4096k it is correct (out_max_abs_diff 0.0004 vs an fp32 reference). **Reviewer should ask** for a BF16 test or an fp8-only assert so the untested half of the entry point is either covered or closed.
