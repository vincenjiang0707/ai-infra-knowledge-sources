# [PR #5542] [Triton/Gluon] [Kernel] Add fused SiLU-and-multiply backward

## 正文

## Summary

Add a fused Triton backward operation for `silu(gate) * up` with concatenated
`[gate, up]` input layout.

Closes #5541.

## Motivation

AITER already provides the SiLU-and-multiply forward operation, but training
currently builds its backward from multiple eager PyTorch operations. This PR
adds the matching fused backward while keeping the implementation in the
existing activation family.

## Changes

- Add `_silu_and_mul_backward_kernel` beside the existing SiLU-and-multiply
  forward kernel and reuse the shared `_sigmoid_exp2` device helper.
- Add `silu_and_mul_backward(grad_output, x, out=None)` to
  `aiter.ops.triton.activation`.
- Evaluate SiLU and both gradient products in FP32 before converting to the
  input dtype.
- Support FP16, BF16, and FP32, arbitrary leading dimensions, strided
  `grad_output`, optional preallocated output, empty rows, and non-current-GPU
  launches.
- Add a config-aware kernel `repr`, unit tests, a benchmark, and the measured
  gfx950 tuning configuration.
- Reuse a shared `select_leq_config` helper for upper-bound config tables and
  migrate the two existing local copies in `fused_clamp_act_mul` and
  `fused_add_rmsnorm_pad`.
- Route the touched config reads through `resolve_config_dir()` and document
  the shared selector in the config rulebooks.
- Correct the shared VGPR table parser for benchmark labels containing units.

## Hardware support and tuning

This PR supports **gfx950 only**. It does not ship or claim support for gfx942;
an unsupported architecture fails required-config resolution with the missing
architecture-specific path.

The measured config is stored at:

```text
aiter/ops/triton/configs/gfx950/triton/fusions/silu_and_mul_backward/DEFAULT.json
```

`width` below is the gate/up width, so `x.shape[-1] == 2 * width`.
`select_leq_config` chooses the smallest matching `N_LEQ_*` entry and otherwise
uses `any`:

| Width | `BLOCK_M` | `BLOCK_N` | `num_warps` | `num_stages` |
|---:|---:|---:|---:|---:|
| `<= 64` | 32 | 64 | 4 | 1 |
| `<= 128` | 32 | 128 | 4 | 1 |
| `<= 256` | 16 | 256 | 4 | 1 |
| `<= 512` | 8 | 512 | 4 | 1 |
| `> 512` | 4 | 1024 | 4 | 1 |

`BLOCK_M` and `BLOCK_N` are the row and column tiles. At launch, `BLOCK_M` is
capped by the next power of two of the row count; widths above 1024 use
multiple column tiles. `num_warps` and `num_stages` control launch scheduling.
The kernel `repr` records the effective `BLOCK_M` and `BLOCK_N` specialization.

### Effective bandwidth

Logical BF16 traffic is three input reads plus two output writes per gate/up
pair:

```text
5 * rows * width * sizeof(bfloat16) = 10 * rows * width bytes
```

Utilization uses AMD's published MI350X peak theoretical HBM bandwidth of
[8.0 TB/s per GPU](https://www.amd.com/en/products/accelerators/instinct/mi350/mi350x.html),
or 8,000 GB/s in decimal units.

| Rows | Width | Logical bytes | Preallocated GB/s (% peak) | `out=None` GB/s (% peak) | FP32 eager logical GB/s (% peak) |
|---:|---:|---:|---:|---:|---:|
| 1 | 4,096 | 40,960 | 4.1 (0.05%) | 5.2 (0.07%) | 0.5 (0.01%) |
| 128 | 4,096 | 5,242,880 | 769.1 (9.61%) | 755.5 (9.44%) | 60.2 (0.75%) |
| 2,048 | 4,096 | 83,886,080 | 2,550.2 (31.88%) | 2,538.9 (31.74%) | 357.7 (4.47%) |
| 8,192 | 4,096 | 335,544,320 | 3,128.4 (39.10%) | 3,129.3 (39.12%) | 325.1 (4.06%) |
| 1 | 12,288 | 122,880 | 10.4 (0.13%) | 12.2 (0.15%) | 1.2 (0.01%) |
| 128 | 12,288 | 15,728,640 | 1,726.5 (21.58%) | 1,349.1 (16.86%) | 150.1 (1.88%) |
| 2,048 | 12,288 | 251,658,240 | 2,822.8 (35.29%) | 2,822.3 (35.28%) | 332.4 (4.15%) |
| 8,192 | 12,288 | 1,006,632,960 | 3,920.4 (49.01%) | 3,922.4 (49.03%) | 326.8 (4.09%) |

The eager path uses the same logical-byte denominator for comparison, but it
performs additional physical traffic for FP32 casts, intermediates, separate
pointwise kernels, concatenation, and the final BF16 cast. Its reported value
is useful/logical bandwidth, not measured HBM traffic. The local GPU is exposed
as a virtual function, and the 8.0 TB/s figure is an advertised theoretical
full-GPU peak rather than sustained application bandwidth.

### Roofline estimate

Per gate/up pair, the fused kernel transfers 10 logical bytes and performs
approximately 11 ordinary FP32 operations plus one `exp2`, or about
**1.1 FLOP/byte** when the transcendental is excluded from the FLOP count.
AMD publishes 144.2 TFLOP/s peak FP32 vector performance and 8.0 TB/s peak HBM
bandwidth for MI350X, giving an estimated roofline ridge point of
`144.2 / 8.0 = 18.0 FLOP/byte`.

Because 1.1 FLOP/byte is far below 18.0 FLOP/byte, the conventional roofline
predicts a bandwidth-bound kernel at sufficiently large shapes. The largest
cases reach about 39-49% of advertised peak HBM bandwidth. This is an estimate:
`exp2` throughput, non-payload traffic, virtualization, and QoS are not modeled.
