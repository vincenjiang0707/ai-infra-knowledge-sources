Thanks for the second review. Every point is fixed in the new op and kernel. Here is what changed,

2) The host op now checks that each row's size in bytes (hidden size times the data-type size) is a multiple of 64. If it is not, the op raises an error. Because of this check, the hidden size is always an exact multiple of the vector width, so we also removed the old scalar "tail" loop — with the check in place it could never run.

3) The op now always requires two things — at least one shared expert (num_shared_experts > 0) and scoring_func == "sigmoid". If either is missing, it raises an error instead of returning garbage.

4) We removed the dead "legacy" branch (the one with the uninitialized score) and the two runtime guards that could never be false (the null-gate check and the shared_expert_base >= 0 check). The new kernel now has only the fused path. About your suggestion to move the shared top-k code into one helper that both kernels include: we chose to keep the two kernels separate instead. The reason is the design goal from round 1 — the original topk_softmax kernel stays exactly the same as upstream, so every existing caller that does not use the shared gate keeps working with zero risk.

5) This buffer is scratch space: the op writes it, but nothing reads it back. The kernel fills it with a fixed stride of topk (routed slots only). So we now size it [num_tokens, topk] instead of [num_tokens, topk + num_shared], and fixed the header comment to match.

6) 
* The routed code marks a "skip this slot" entry with a special number. That number used to be num_experts, which is exactly the id of the first shared expert — so a skipped slot could be read back as shared expert 0. We changed the marker to num_experts + num_shared_experts, which is outside the range of all real ids, so it can no longer be confused with any expert.
* That path used a slow, one-element-at-a-time GEMV that was actually slower than not fusing at all. Instead of shipping it, the op now rejects non-power-of-2 expert counts with a clear error, and we deleted that slow code.
*  The test file used to contain only benchmark functions, so pytest collected the file but ran no real test. We added a real test (test_correctness) that compares the fused op and the unfused baseline against a reference for several shapes: 1, 2, and 8 shared experts; float32 inputs; and a larger hidden size that triggers the "read the gate from global memory" fallback. We also added two tests that confirm the new checks actually fire — one for a misaligned hidden size, one for a non-power-of-2 expert count.

### yzhou103 · 2026-09-24

1. `bench_unfused` is not a representative baseline, so the reported speedup is inflated.**

  The timed region is ~9 kernels, and most of them are artifacts of the torch plumbing
  rather than of "not fusing":

  ```python
  topk_softmax(r_w, r_i, r_tei, gating, renorm)                            # 1  necessary
  shared_w = torch.sigmoid(hs.float() @ gate_weight.float().t()) * scale   # 2 upcasts + mm + sigmoid + mul
  w[:, :topk] = r_w;   w[:, topk:] = shared_w                              # 2 copies
  ids[:, :topk] = r_i; ids[:, topk:] = shared_ids                          # 2 copies
 ```
  - The two .float() casts materialize an [M, H] fp32 temporary (128MB at M=8192,
  H=4096). A bf16 F.linear already accumulates in fp32 on MFMA, which is what the fused
  kernel does — so the upcast also makes the baseline more accurate than the op under
  test, which is the wrong way round.
  - The two routed copies are avoidable. The kernel indexes its outputs through
  topk_weights.stride(0) / topk_indices.stride(0), so w[:, :topk] and ids[:, :topk]
  can be passed directly as views and the routed columns get written in place. That
  strided-output path is already exercised in-repo by op_tests/test_moeTopkSoftmax.py,
  which calls the base op with torch.empty_strided buffers.
  - shared_ids depends only on (num_routing_experts, num_shared_experts), not on the
  input, so it belongs outside the timed region.

  Suggested rewrite (~4 kernels, and the sigmoid/scale/store could be folded further):

  w   = torch.empty(tokens, total, dtype=dtypes.fp32)
  ids = torch.empty(tokens, total, dtype=dtypes.i32)
  tei = torch.empty(tokens, topk,  dtype=dtypes.i32)
  w_routed, ids_routed = w[:, :topk], ids[:, :topk]      # views, written in place
  ids[:, topk:] = base + torch.arange(num_shared, dtype=dtypes.i32)   # input-independent
  logit = torch.empty(tokens, num_shared, dtype=dtype)   # reused, not reallocated

  def fn():
      topk_softmax(w_routed, ids_routed, tei, gating, renorm)
      torch.nn.functional.linear(hs, gate_weight, out=logit)   # bf16, no upcast
      torch.sigmoid(logit, out=logit)
      w[:, topk:] = logit * scale

  2. The M sweep is decode-only. --tokens defaults to [1, 4, 17, 64]. The in-kernel
  GEMV runs on VALU with THREADS_PER_ROW = 16 lanes per row and adds a full [M, H] HBM
  pass, so the interesting question is at the other end. Please extend to
  [1, 4, 16, 64, 256, 1024, 4096, 16384] so we can see whether there's a crossover, and
  where it is.

  3. Missing axes in test_correctness. It currently pins tokens=64, num_experts=512, topk=10, scale=1.0, renorm=True, so several branches are untested:

  - need_renorm=False — a separate epilogue, currently never executed under pytest.
  - shared_expert_scale != 1.0 — applied in the kernel; would pass unnoticed if dropped.
  - num_experts=256 — at E < 512 the launcher picks BYTES_PER_LDG = 32, i.e. a
  different ELTS_PER_LDG and a different vector width in the GEMV. Only the 64B path is
  covered today.
  - Token-count edge cases: M = 1, and an M that isn't a multiple of ROWS_PER_CTA
  (8 at E=512) such as M = 65, to cover the tail block. M = 0 currently yields
  num_blocks == 0 and a failed launch — worth deciding whether that should be a guarded
  no-op.
