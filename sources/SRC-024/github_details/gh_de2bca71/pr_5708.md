# [PR #5708] [HIP] [CK] Add relu2 (Squared ReLU) activation support to CK-Tile fused MoE GEMM

source: https://github.com/ROCm/aiter/pull/5708
state: open | updated: 2026-09-24T21:33:17Z
labels: HIP, CK

## 正文

## Motivation

- NemotronH's MoE layers use Squared ReLU (`relu(x)^2`) as their activation function. Tier 1 (#5689) added a standalone `relu2` kernel so aiter could compute this activation directly instead of falling back to eager PyTorch, but that PR only covered the simple elementwise case, not the fused MoE GEMM path.

- The fused MoE GEMM path (`csrc/ck_tile_gemm_moe_2stages/`) didn't support relu2 at all. 

- This PR adds real relu2 support to the fused MoE GEMM path, so NemotronH's MoE layers can run through aiter's fast CK-Tile kernels instead of falling back to a legacy path that doesn't support relu2 at all.

This is Tier 2 of a 3-PR series adding end-to-end relu2 support:

1. #5689 -- standalone aiter elementwise kernel (no dependencies)
2. This PR -- aiter CK-Tile fused MoE GEMM support for relu2 (depends
   on Tier 1)
3. vLLM AITER backend integration (depends on this PR)


## Technical Details

Root cause: `moe_dispatch` (the CK-Tile MoE GEMM's kernel-selection function) had no case for relu2's internal activation id, so relu2 calls fell through the if/else chain with no matching branch and no `return` -- genuine undefined behavior, not a crash or NaN. 

This PR adds the missing dispatch branch, along with the supporting relu2 activation functor, codegen routing, and Python-side wiring needed to reach it (`aiter.fused_moe`'s `get_2stage_cfgs` now selects the CK-Tile relu2 path instead of falling back to a legacy codegen path that has no relu2 support at all).

## Test Plan

Model: `nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-BF16`, 8x AMD Instinct MI350 (gfx950), TP=8.

- Kernel-level: `test_fmoe` (isolated CK-Tile GEMM, vs. torch-eager reference) at E=8/topk=2 across token counts {16,32,64,128,256}, and at E=512/topk=22 (NemotronH's production MoE scale).
- End-to-end: NemotronH's real checkpoint is unquantized bf16 and only reaches this fused-GEMM dispatch path when weights are quantized to fp4x2/per_1x32 at load time, so this was validated via  `--quantization mxfp4` online quantization in vLLM. Ran `vllm bench serve` (1024/1024 and 8192/1024, concurrency 128, 256 prompts) and `lm_eval` GSM8K (5-shot, n=1319) as an A/B test toggling only the `moe_dispatch` fix (identical mxfp4 quantization and hardware otherwise, fix reverted vs. applied).

## Test Result

### GPU Kernel Test

### a16w4 (weight-only mxfp4) passes cleanly at NemotronH-realistic dimensions

Testing relu2/gate-only with only the weight quantized to mxfp4 (activation left as unquantized bf16 — `AQDType=bf16`, `WQDType=fp4x2`) at `model_dim=8192, inter_dim=5120, E=8, topk=2` (NemotronH-realistic dims):

**Test configuration:**
- Shape: `model_dim=8192, inter_dim=5120, E=8, topk=2` — matches NemotronH's real hidden/intermediate dims
- Activation: `Relu2` (gate-only, `gateMode=GateMode.SEPARATED`, `use_g1u1=False`)
- Quantization: `qType=per_1x32` (mxfp4), `AQDType=bf16` (activation left unquantized), `WQDType=fp4x2` (weight quantized to mxfp4) 
- Token counts swept: 16, 32, 64, 128, 256 (single forward call each, `strict_accuracy=True`)
- Metric: `logits_diff` — aiter's own `calc_diff` cosine-similarity-based distance between the CK-Tile kernel's GEMM output and an unquantized PyTorch fp32 reference computed with identical routing/weights
- Hardware: 8x AMD Instinct MI350 (gfx950), aiter editable install at commit `f42721f0e` (`amd-aiter-0.1.23.dev98+gf42721f0e`)

| token | quant config | logits_diff | result |
|------:|:---|------------:|:------:|
| 16    | a16w4 (activation unquantized) | 4.686e-05 | **PASS** |
| 32    | a16w4 (activation unquantized) | 3.695e-05 | **PASS** |
| 64    | a16w4 (activation unquantized) | 5.848e-05 | **PASS** |
| 128   | a16w4 (activation unquantized) | 2.331e-05 | **PASS** |
| 256   | a16w4 (activation unquantized) | 4.611e-05 | **PASS** |

Every token count passes cleanly — `logits_diff` in the 2.3e-05–5.8e-05 range, consistent with ordinary MXFP4 weight-quantization rounding noise.
