# [PR #5828] [Triton/Gluon] [Config] Add gfx1250 gluon a16w16 config for MLA q_b_proj (N=24576, K=1536)

state: open | updated: 2026-09-25T02:09:55Z

## 正文

## Motivation

On gfx1250 the DSR1 FP4 decode path spends a large slice of each step in the
Triton/gluon `a16w16` GEMM. Profiling a 4-GPU DP4/EP4 server at 1k in / 4k out
showed the MLA `q_b_proj` projection (`N=24576`, `K=1536`) as the single
largest `a16w16` contributor, at roughly 11% of the decode step.

That shape has no tuned entry under
`aiter/ops/triton/configs/gfx1250/gluon/gemm/gemm_a16w16/`, so the lookup falls
through to `DEFAULT.json`. The default picks a `bandwidth_bound` tile with
`BLOCK_M=32`, which is a poor fit here: at decode the M range is in the
hundreds, and the shape is compute bound, not bandwidth bound. The result is a
kernel running well below what the shape can sustain.

## Summary

Adds a single tuned config file, `GEMM-A16W16-N=24576-K=1536.json`, with
`compute_bound` entries for the `M_LEQ_128` / `M_LEQ_256` / `any` buckets
(`BLOCK_M` 128/256/256, `BLOCK_N=128`, `BLOCK_K=64`).

Config only. No kernel, dispatch, or API change, and no other shape is
affected: the file is only consulted for `N=24576, K=1536` on gfx1250.

## Performance

Isolated `a16w16` GEMM at `N=24576, K=1536`, before (DEFAULT) vs after:

| M | before (us) | after (us) | speedup |
|---|---|---|---|
| 128 | 99.6 | 87.0 | 1.15x |
| 256 | 114.7 | 93.9 | 1.22x |
| 512 | 148.5 | 107.3 | 1.38x |

End to end on the serving workload below, the `q_b_proj` kernel drops from
70.6 us to 31.2 us per decode step and the decode step itself goes from
39.57 ms to 37.34 ms.

## Accuracy

GSM8K, 5-shot, all 1319 questions, via `lm_eval` against the running server:

| Filter | n-shot | Metric | Value | Stderr |
|---|---|---|---|---|
| flexible-extract | 5 | exact_match | 0.9484 | ±0.0061 |
| strict-match | 5 | exact_match | 0.9484 | ±0.0061 |



## E2E test scenario

Base image: `rocm/fw-bringup:gfx1250-atom-20260922` (nightly).

Model `/data/Deepseek-S3_sq_a05_v2_mlperf6_1` (FP4), 4x gfx1250, DP4 attention
+ EP4 MoE, served with `atom.entrypoints.openai_server`, ISL 1024 / OSL 4096.

Accuracy was collected with `FAKE_EPLB=0` (with `FAKE_EPLB=1` the expert
routing is faked for throughput measurement and GSM8K collapses to ~1%, which
is expected and unrelated to this change):

```
pip install lm-eval[api]

lm_eval --model local-completions \
  --model_args model=/data/Deepseek-S3_sq_a05_v2_mlperf6_1,base_url=http://localhost:8000/v1/completions,num_concurrent=64,max_retries=3,tokenized_requests=False \
  --tasks gsm8k --num_fewshot 5
```
