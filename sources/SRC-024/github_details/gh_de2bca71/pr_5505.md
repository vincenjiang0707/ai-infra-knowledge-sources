# [PR #5505] Fix the hardcoded die and CU counts in the Triton kernels

source: https://github.com/ROCm/aiter/pull/5505
state: open | updated: 2026-09-25T16:36:51Z
labels: 

## 正文

Stops the Triton kernels folding program ids into eight dies, and stops several launch budgets being sized for one part's CU count. Both now come from the running device.

Stacked on #5182, which resolves device identity from the live device rather than the first agent rocminfo reports. No file overlap with the FlyDSL half of this work.

## Motivation

The program-id remap assumed eight dies, and several launch budgets were written against 256 or 304 units. That is already wrong on a part in the field: MI308X is gfx942 with 80 CUs and four dies. It is wrong again on MI350P, which is gfx950 with 128 CUs and four dies.

## Technical Details

**1. One remap helper keeps its default of eight.** Thirteen call sites still invoke it as a bare statement and discard the result, so the swizzle is already inert there. Removing the default would turn those into compile errors, which is arguably right but is a larger change. The trap is that fixing one of them without passing the count reintroduces exactly what this branch removes, and the default says so.

**2. The two collectives keep 256 as their declared default,** and the device count is something a caller asks for by passing `None`. That path needs more than one GPU and the Iris module, so nothing here can measure it, and an opt-in ships no unmeasured change. No in-tree caller has ever passed the argument.

**3. The sparse decode budget is uncapped,** following `unified_attention` and `mla`, which both take the live count times an occupancy factor. On a 304 unit part this grows the budget, which is the behaviour those two already produce there. No other aiter backend caps a live CU count against a literal.

**4. An MLA batch the die count cannot cover is now refused.** The batch index strides by the die count, so a batch it does not divide loses its tail with nothing reported. The existing check against 64 implies this for four and eight dies but not for six.

**5. The `pod_attention` changes cannot be exercised.** That module does not import, on this branch or on main, for two unrelated reasons predating it: a symbol imported from the wrong module, and a hardcoded path to a file moved some time ago. The change there is a comment and one constant, correct on inspection, but not run.

## Test Plan

`op_tests/triton_tests/gemm/basic/test_gemm_a8w8.py` with the die and CU counts forced to four and 128, `op_tests/test_mla.py`, direct calls to the GMM variants across four die and unit combinations, module imports, `ruff` and `black`.

## Test Result

The forced four-die run gives 1089 passed and 4 skipped, identical to the unpatched baseline. GEMM at die counts of one, three, four, eight and sixteen stays at bf16 noise, including a shape the count does not divide. The GMM variants match the torch reference at every combination. Clean.
