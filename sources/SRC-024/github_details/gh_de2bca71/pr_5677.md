# Adaptive decode Top-K kernel, dispatched by one measured gate

The decode path now has four candidate kernels and no single one wins the shape space, so this adds the kernel behind a table of measured row intervals keyed by `(arch, CU count, emit, k, width)`. An `(arch, CU count)` pair the table does not name keeps today's behaviour exactly.

## How the dispatch works

Two public entry points reach the decode path, and they do not share a call chain: `topk_select()` routes its `decode` arm straight into the FlyDSL host and never passes through `top_k_per_row_decode()`. So the gate sits in both, and both ask one function rather than deciding for themselves, which is what keeps them from disagreeing about a shape.

```
  top_k_per_row_decode()              topk_select()
  aiter/ops/topk.py                   aiter/ops/topk_select.py
          |                              |- argmax / small_k / plain
          |                              |- stream
          |                              \- decode
          |                                   |
          |                                   v
          |                     flydsl_top_k_per_row_decode()
          |                     aiter/ops/flydsl/topk/topk_per_row.py
          |                                   |
    [gate here]                         [gate here]
          |                                   |
          +-----------------+-----------------+
                            v
              decode_backend_for_call()   <- the only decision
                            |
     +----------------------+---------------------+
     v                      v                     v
  adaptive               chunked              upstream
  (in a band of          (in upstream's       (not ours; the dispatch
   the measured           chunked gate,        below picks the port
   table, looked up       read at the          where enabled, else the
   at the live length)    physical width)      HIP/C++ kernel)
```

The gate never names the fallback kernel itself: it answers "not ours" and upstream's existing dispatch picks, which is the port on gfx950 and gfx1250 and the HIP/C++ kernel elsewhere. That is also why a caller wanting values never reaches the adaptive kernel, which emits indices only. Only `top_k_per_row_decode()` has that dispatch below it. In `topk_select()` the decode arm is already chosen, so "not ours" leaves the chunked kernel.

## `max_row_len`, and what a caller has to pass

A decode buffer is allocated once at the model's maximum context and a call fills whatever part of it the requests need. `seq_lens` is device-resident, so the host cannot read it without a sync, and the adaptive kernel picks its tier, part count and workspace on the host before launch. Given only the buffer, it builds a short row as if it were a full one.

So the new argument states the longest live row in the batch. A serving stack that assembles the batch already has it -- it is `max(seqLens)`. No caller in aiter passes it yet, so nothing reaches the new kernel until a stack opts in. The tables below declare it.

- **It is a guarantee, not a hint.** Part of what it selects is compiled in, so a bound below the longest live row returns wrong indices rather than merely slower ones. It cannot be checked here without the sync this path exists to avoid. A bound above it is always correct; it only costs the win.
- **`None` declines the adaptive kernel and nothing else.** The chunked bands keep reading the physical width they were fitted on, so a call that passes nothing routes exactly where it routes today.
- **It never changes a result**, only which kernel produces it.

## Results

Every cell is scored, not only the ones the gate takes. A band takes a cell when the kernel is no slower than the best of the four and at least 1.05x faster than what runs there today; a smaller margin is noise. Every entry had to satisfy that on **both** slices below, so a cell that only clears it on the diagonal is not in the table. Nothing is behind on either slice.

A ratio is today's kernel over this PR's, so a declined cell is 1.00x by construction and the geomean covers every cell. Each card's own grid and per-cell winners are below.

Protocol: all four arms are timed the same way on every cell, under graph replay, and the cell's number is the median over its repeats; cells where the arms came out close were re-timed with more.

## Verification

- Host-side unit tests over the table's structure, the k-group expansion, the bound, and which shapes the early stop is built into -- it is on by default but dropped under `ordered`, under the candidate-buffer path and on an all-short build, none of which run the pass it replaces. They walk whatever the table holds, so a card added later is a table entry and nothing else.
- A GPU-gated test, in the same file, that walks the shipped table: at each band's widths it takes the row counts just inside and just outside the band, asserts the kernel the table names is the one that launches -- by patching the launch site, not by inferring -- and that the selected values are a row's true top k. One k per group, and cells too large to allocate in a unit test are skipped. Every cell runs twice, once on planted logits whose top k sit at known positions and once on random ones; ragged `seq_lens` with the longest row exactly on the bound get the same treatment.
- Across the sweeps above, every arm's output was checked against `torch.topk` over each row's live slice: 7600 cells over four cards, no incorrect result. On the 3600 padded cells everything past the live length held a poison value, so a read past `seq_lens` would have come back as a wrong answer rather than a plausible one.

## What is still open

- **Ragged batches are calibrated optimistically.** The gate decides once per call on the longest row, because the kernel is configured once per launch, and the sweeps hold uniform batches. A row that would win 1.31x on its own measures 0.66x when a much longer row shares its batch. Correctness is unaffected; the win is.
- **Reduce the reps with `min` instead of the median** and two entries show near-ties. 304 CU reads 3 losing cells, worst 0.98x, at k=512 and a live length of 8192; 256 CU reads 2, worst 0.997x, at width 131072 and 32 rows. All five clear the kernel their own card runs -- by 1.16x to 2.19x on 256 CU -- and lose to a third kernel by under 2%.
- **gfx1250 is unmeasured** and has no entry, so the gate declines it and it runs exactly what it runs today. gfx950 is measured at one CU count.
- **CI.** The routing test skips without a device, and the widest band edges are too large to allocate inside a unit test.
- **Indices only.** Emitting values is a kernel change, not proposed here.
