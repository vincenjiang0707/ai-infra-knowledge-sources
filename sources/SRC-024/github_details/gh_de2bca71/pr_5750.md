# [PR #5750] [Triton/Gluon] [JIT] [Feature] Add tuned native group32 A8W8 Triton GEMM for gfx950

source: https://github.com/ROCm/aiter/pull/5750
state: open | updated: 2026-09-24T16:48:52Z

## 正文

DeepSeek-V4.1-Flash projections use unshuffled E4M3 weights and compact E8M0 group32 scales. This adds a gfx950 Triton backend for those operands to `gemm_a8w8_blockscale`, together with tuned configurations for TP4, TP2 and attention-DP local GEMMs.

### Implementation and dispatch

- Keep activations, weights and scales in their native formats. Support compact 32x32 or per-row 1x32 weight scales, FP32 accumulation, and BF16/FP16/FP32 output.
- Use native microscaling MFMA, packed-K execution for small M, and the existing non-atomic split-K reduction. The public interface accepts an optional native-group32 `split_k` partition count, preserving explicit caller controls while keeping configured backend selection first.
- Query `get_CKGEMM_config` before selecting a fallback. Native E8M0 operands have a separate `AITER_CONFIG_GEMM_A8W8_BLOCKSCALE_GROUP32` CSV family, so an identical M/N/K in the FP32 128x128 table cannot select an incompatible kernel. Unsupported configured backends raise instead of silently falling back.
- Add 450 DSV4.1 model-config rows: 18 geometries and 25 M buckets, all selecting `libtype=triton`. Tile, split-K and packed-variant settings remain in the existing Triton JSON configuration system. Of these rows, 262 reuse exact-shape measured timings; remaining timing fields are empty.
- Extend the shared GEMM loader with optional file-defined `M_BOUNDS`, retaining explicit-argument precedence and legacy bounds. Config copies preserve nested mutation isolation while avoiding per-scalar `deepcopy` overhead.

The new native backend requires gfx950. Existing FP32 128x128 operands retain their CK/CKTile paths. Group32 currently supports the Triton backend; configuring legacy CK/CKTile for its E8M0 operands is rejected.

### Performance

Hardware: AMD gfx950, 256 CUs; PyTorch 2.9.1 ROCm 7.1.1 and Triton 3.8.0 ROCm build. Measurements use BF16 output, CUDA graphs and at least 512 MiB of rotating weights. The baseline is the initial imported native group32 configuration in the first commit of this PR.

The sweep evaluated 49,304 candidates across 234 representative M/N/K cases and validated 603 cases, including interval boundaries. The geometric-mean speedup is **1.179x** (15.18% lower GEMM latency). Of 300 intervals checked, 252 use improved configurations and 48 retain the baseline. The largest sampled slowdown among changed configurations is 0.97%. Measurements affected by other GPU users were discarded and rerun on available cards.

### Validation

- **136 AITER tests passed** on the rebased branch: native numerical contracts, column/K tails, extreme scale codes, per-row scales, split-K, output buffers, live-input graph replay, dynamic-M fullgraph compile, CSV format isolation, and configured-backend precedence. CK/CKTile dispatch-priority tests use stubs; native numerical and graph tests execute GPU kernels.
- **100 ATOM integration tests passed** with the companion migration to the public AITER interface, covering actual backend-config lookup, blockscale projections, accumulation, GPU quantization, graph replay and dynamic batched fullgraph compilation.
- All **294,912** combinations of the 18 model geometries and integer M=1..16384 resolve through the real shared loader to Triton; unknown geometries still miss the table and reach fallback.
- Six representative cases comparing dispatch before/after the configuration-priority change have bitwise-equal BF16/FP32 outputs, identical GPU kernel sequences, and graph-latency differences below 0.5%.
- Black and Ruff pass for all seven changed Python files; `git diff --check` passes.

The sweep compares sampled outputs against an independent FP64 reference and complete BF16 outputs against the baseline. BF16 outputs are bitwise equal in 384/603 cases; the maximum BF16 relative RMS difference is 1.052e-4. One pre-existing FP32 reference-boundary outlier at M=97, N=5120, K=1152 remains: maximum absolute error changes from 0.09451294 to 0.09445190. The experiment accepts that point only when candidate error does not exceed baseline error; repository test tolerances are unchanged.
