# [PR #5600] [Triton/Gluon] fix(gluon): two-step addressing in paged MQA logits kernel (pool coord -> block column + offset)

source: https://github.com/ROCm/aiter/pull/5600
state: open | updated: 2026-09-24T13:59:30Z
labels: Triton/Gluon

## 正文

## Summary

The gluon port of `deepgemm_fp8_paged_mqa_logits` (`aiter/ops/triton/gluon/pa_mqa_logits.py`) indexes the `kv_indices` block table with the **raw pool coordinate** instead of converting it to a block-table column first. This overruns the table row by up to `KVBlockSize`× (64× on gfx942), reads a garbage physical block id, and then dereferences `KV_buffer[garbage * stride_k_seq]` → **arbitrary-address read → deterministic Memory access fault on all TP ranks**.

The Triton reference implementation (`ops/triton/_triton_kernels/attention/pa_mqa_logits.py`) already does this correctly:

```python
logical_block_idx = logical_kv_idx // KVBlockSize   # block-table column
block_offset      = logical_kv_idx % KVBlockSize    # offset within block
```

This PR ports the same **two-step addressing** to the gluon kernel at all three load sites (prologue prefetch / in-loop prefetch / `k_next` + scale consumption), and hardens the prefetch masks to bound **both** directions (`>= 0 && < context_length`) with out-of-window lanes forced to 0, so a garbage block id can never reach the `KV_buffer` dereference.

## Root cause detail

`kv_indices` rows are **BLOCK tables**: column `j` holds the physical block id for pools `[j*KVBlockSize, (j+1)*KVBlockSize)`. `context_length` is a **pool count** that can reach `max_block_len × KVBlockSize`. The buggy code used the pool coordinate directly as the column index:

```python
# before (bug): pool coord used as block-table column
context_kv_idx_next = buffer_load(
    kv_indices,
    offsets=pid_batch * max_block_len + context_idx + arange)  # overruns row 64x
k_next = buffer_load(KV_buffer, offsets=context_kv_idx_next * stride_k_seq + arange)
```

```python
# after (fix): two-step addressing, matches Triton reference semantics
block_col = pool_pos // KVBlockSize
block_off = pool_pos % KVBlockSize
context_kv_idx = buffer_load(kv_indices, offsets=pid_batch * max_block_len + block_col, mask=...)
k_next = buffer_load(KV_buffer, offsets=context_kv_idx * stride_k_seq + block_off * HiddenDim + ...)
```

## Reproduction (before fix)

- **Hardware**: 8× MI308X (gfx942), TP4, ROCm 7.2, triton 3.7
- **Model**: GLM-5.3-Flash (fp8 e4m3 KV cache, page 64, `index_kpool=4`, kpool indexer → `deepgemm_fp8_paged_mqa_logits` with `Preshuffle=False`)
- **Trigger**: any request whose KV length exceeds **16384 tokens** (= 4096 pools × 4) faults deterministically on the **first decode step** after prefill completes; 8K passes. 4 ranks fault simultaneously (KFD, `Reason: Unknown`).
- **Forensics**: `AMD_LOG_LEVEL=3` + `HIP_LAUNCH_BLOCKING=1` + `--disable-cuda-graph` pins the faulting kernel to `_gluon_deepgemm_fp8_paged_mqa_logits` (last synchronous launch before the fault).
- **Version-independence**: reproduced identically on aiter 7/29, 8/29, and 9/15-main (full Python/Triton/C++ rebuild) — the bug is in the gluon port itself.
- **No env switch**: `enable_gluon_pa_mqa_logits` auto-enables on gfx942/gfx950/gfx1250 with triton ≥ 3.5, so any GLM-5.x / DSV4-class kpool-indexer workload with > 16K context hits this on stock ROCm 7.2 containers.

## Verification (after fix)

| Seq length | tokens | before | after |
|---|---|---|---|
| 8K | 7,460 | PASS | PASS 1.4s (no regression) |
| 20K | 20,166 | **100% crash** (4-rank fault) | **PASS 3.3s** |
| 32K | 32,720 | always crash | PASS 6.9s |
| 64K | 65,697 | always crash | PASS 12.6s |
| 128K | 133,136 | always crash | PASS 32.4s |

- 20K regression ×2: stable PASS.
- CUDA graph output matches eager **token-for-token** (rules out stale pool-table in capture).
- Zero `Memory access fault` across the full sweep.

## Notes for reviewers

- The fix keeps the gluon layout idioms (SliceLayout arange, `buffer_load`, `_amd_iglp_sched_barrier`) — only the addressing arithmetic and mask bounds change.
- An alternative sglang-side workaround (switching to the `_preshuffle` variant via `Preshuffle=True`) also works but requires a pre-shuffled KV layout; this PR fixes the non-preshuffle path at the source.
- Happy to add a unit test if maintainers point me at the preferred test harness for gluon kernels (I did not find an existing `pa_mqa_logits` gluon test to extend).
