**Adds a gfx1250-only Gluon (TDM tensor-descriptor) RMSNorm kernel with a two-stage LDS software pipeline, and makes it the default `rms_norm` backend on gfx1250 via a new optional `backend="triton"|"gluon"` kwarg threaded through `rms_norm`/`_RMSNorm`.**

Review (advisory): ⚠️ NEEDS WORK
Validation (deterministic): NOT RUN — auto-validation disabled in this environment (REVIEW_AUTO_VALIDATE=0) and no head-matched report supplied; the single test target is op_tests/triton_tests/normalization/test_rmsnorm.py
Perf (advisory): NOT RUN — the runtime kernel path changed so timing was required, but the test target exposes no benchmark entry point and auto-validation was disabled; the repo's op_tests/op_benchmarks/triton/bench_rmsnorm.py already covers rms_norm and was neither run nor extended

⚠️ [verified] Default-path flip with zero CI coverage. aiter/ops/triton/normalization/rmsnorm.py resolves backend=None to "gluon" on gfx1250, so every rms_norm call on gfx1250 — including rmsnorm_forward_inference, which has no backend parameter and cannot opt out — runs the new kernel by default; but op_tests/triton_tests/normalization/test_rmsnorm.py skips every gluon case off gfx1250 and no default CI job runs gfx1250 hardware (triton CI runs on MI35X/gfx950; the gfx1250 suite is opt-in via the ci:gfx1250-ffm-triton label). The new default path can merge having never run in CI, and the description states only WHAT ("translated existing triton implementation") with no mechanism or numbers — elevated AI-code risk. **Reviewer should ask** for a gfx1250 suite run (or the ci:gfx1250-ffm-triton label) before merge, or keep the default on "triton" until the gluon path is validated on hardware.

⚠️ [verified] backend silently discarded on large-M/small-N shapes. In aiter/ops/triton/normalization/rmsnorm.py, _RMSNorm.forward routes M>8192, N<=2048 (e.g. 16380x1536 or 364800x128) to _rmsnorm_forward_large_m_small_n without forwarding or checking backend, so on gfx1250 both the default gluon selection and an explicit backend="gluon" are silently ignored with no warning; the test rows at those shapes pass through that branch, so they assert nothing about the gluon kernel even on gfx1250. **Author must** warn or assert when backend="gluon" is dropped, and stop counting the large-M rows as gluon coverage.

⚠️ [inferred] No measurement behind a default kernel swap. The PR ships zero timing data (no number in the description, no benchmark run), while op_tests/op_benchmarks/triton/bench_rmsnorm.py already covers rms_norm and the repo's own convention says a kernel ships as kernel + wrapper + test + benchmark; NUM_WARPS=4 and nStages=2 are hardcoded in aiter/ops/triton/normalization/rmsnorm.py and in the new kernel, outside the config registry (get_normalization_config / configs/gfx1250/) that the backward path in the same file already uses. Is the gluon kernel actually faster than the triton kernel it replaces as the default, and are NUM_WARPS=4/nStages=2 tuned or inherited? **Author must** run base-vs-head bench_rmsnorm.py on gfx1250 and move the launch config into the registry.

⚠️ [verified] Missing input guards the sibling gluon wrapper carries. The new branch in aiter/ops/triton/normalization/rmsnorm.py builds TDM descriptors on x/weight with strides [x.stride(0), 1] and no contiguity or shape/dtype checks, while the merged gluon sibling aiter/ops/triton/normalization/fused_rmsnorm_add.py asserts x.dim/weight shape/dtype and does x = x.contiguous() before make_tensor_descriptor. If a caller passes a column-sliced or transposed view (stride(1) != 1, e.g. bigger[:, ::2]) or a misaligned base, the descriptor would silently misdescribe the layout and read wrong values with no crash. **Author must** match the sibling wrapper's contiguous()/assert guards or state why the TDM path tolerates strided inputs.

📝 [verified] Housekeeping before merge. The new kernel file aiter/ops/triton/_gluon_kernels/gfx1250/norm/rmsnorm.py carries no SPDX/copyright header (every other kernel in the tree has one) and uses bare @gluon.jit where the repo's ops-triton convention requires make_kernel_repr + @gluon.jit(repr=...) for Gluon entry kernels (the triton kernel it translates has one); the PR is also stale against main — the large-M/small-N specialization (commit 4b6184fef) touched the same two files after this PR's base, the patch no longer applies directly (3-way applies), so any CI result on it describes a moved tree. **Author must** add the header/repr and rebase before merge.
