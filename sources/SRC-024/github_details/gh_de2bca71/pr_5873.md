# [PR #5873] [Triton/Gluon] [Bugfix] Mask the split-K tail in the blockscale GEMMs

source: https://github.com/ROCm/aiter/pull/5873
state: open | updated: 2026-09-27T00:33:19Z
labels: Triton/Gluon

## 正文

## Summary

`compute_splitk_params` rounds `SPLITK_BLOCK_SIZE` up to a multiple of `BLOCK_SIZE_K` and recomputes `NUM_KSPLIT`, so `NUM_KSPLIT * SPLITK_BLOCK_SIZE` can exceed K: the last partition starts inside K and runs past it. The blockscale kernels' `EVEN_K` heuristic only checks `K % BLOCK_SIZE_K == 0`, so that tail is loaded without masks. The output is wrong or NaN, and the stray reads can fault.

Example: the gfx942 default A8W8 config uses `NUM_KSPLIT=8` for M <= 64. With K=384 that becomes 2 splits of 256. The second split covers [256, 512), and the tile at [384, 512) is read unmasked.

Relative error against a dequantized reference (MI325X, N=6144, via `gemm_a8w8_blockscale` with the default config):

| K | M=1 | M=16 | M=64 |
|---|---:|---:|---:|
| 384, before | 11.8 | NaN | 0.58 |
| 640, before | 0.025 | 0.44 | 0.92 |
| 384 / 640, after | 0.025 | 0.026 | 0.026 |

0.025 is the fp8 quantization noise floor, the same value K=768 and K=1024 give before the fix.

We hit this serving `MiniMaxAI/MiniMax-M3-MXFP8` with SGLang at TP8 on MI325X. The shared-expert `down_proj` has K=384 per rank, so the model decoded token 0 and CUDA-graph capture hit `Memory access fault by GPU`.

## Fix

`EVEN_K` also requires `K % SPLITK_BLOCK_SIZE == 0`, in `_gemm_a8w8_blockscale_kernel` and `_gemm_a16w8_blockscale_kernel`. Without split-K, `SPLITK_BLOCK_SIZE == K`, so behavior is unchanged there. The preshuffle kernels are left alone: their wrappers size the split differently, and the a16w8 preshuffle kernel has no masked path.

## Tests

- `test_gemm_a8w8_blockscale.py`: shapes `(M, 6144, K)` for M in {1, 16, 64} and K in {640, 896}, plus `test_gemm_splitk_tail`, which forces `NUM_KSPLIT=8`.
- `test_gemm_a16w8_blockscale.py`: `test_gemm_splitk_tail`. The default gfx942 a16w8 config doesn't split K, so the test forces it.
- gfx942: 9 of the new cases fail before the fix; all 16 pass after. The existing a8w8 and a16w8 subsets still pass (212 + 26). `test_legacy_gluon_import_path_warns` fails on this box both before and after (unrelated).
- Only validated on gfx942 with the triton backend. The new shapes also run the gluon backend on gfx950 / gfx1250.

Found by [Hyperloom](https://github.com/AMD-AGI/Hyperloom); reviewed and measured by hand.
Hyperloom was optimizing `MiniMaxAI/MiniMax-M3-MXFP8` on MI325X (TP8).
