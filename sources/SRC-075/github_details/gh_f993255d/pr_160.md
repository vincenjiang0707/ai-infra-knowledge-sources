# [PR #160] fix: eval_kernel_against_ref catches only RuntimeError on model load, not other exceptions

## 正文

Fixes #159.

## Summary

`eval_kernel_against_ref` is careful to encode failures of the generated kernel in its return value rather than raising: the compilation phase catches `Exception` and returns `KernelExecResult(compiled=False, ...)`, and the correctness phase catches `Exception` and returns `KernelExecResult(compiled=True, correctness=False, ...)`.

The model-load phase between them, however, only caught `RuntimeError`:

https://github.com/ScalingIntelligence/KernelBench/blob/423217d9fda9/src/kernelbench/eval.py#L569

`ModelNew(*init_inputs)` executes arbitrary generated `__init__` code (and the `assert hasattr(custom_model, "forward")` right after it). `RuntimeError` covers the anticipated CUDA cases (launch failure, illegal memory access), but if the generated code raises anything else (`ValueError`, `TypeError`, `KeyError`, a failed `assert`, etc.), the exception propagates out of `eval_kernel_against_ref` instead of being recorded — unlike the identical situation one phase earlier or later.

## Why it matters

Callers that follow the function's own convention (a verdict on the kernel comes back in the `KernelExecResult`; an exception means the harness itself failed) misclassify these samples. A kernel whose `__init__` deterministically raises `ValueError` is a failure of the generated code and should grade as `compiled=True, correctness=False`, exactly like a `RuntimeError` from the same site — not surface as an unhandled exception indistinguishable from an environment/setup failure.

## Change

One line: `except RuntimeError as e:` → `except Exception as e:`, matching the sibling phases. `metadata["runtime_error_name"]` (via `get_error_name`) already preserves the exception class, so `RuntimeError` vs. other exception types remains distinguishable in the result metadata — nothing is lost, only broadened.

## Note

This block also wraps an operation on the *reference* model (`original_model.to(device=device, dtype=precision)`), and a failure there arguably isn't the generated kernel's fault. That's pre-existing (`.to()` failures typically raise `RuntimeError`, already caught before this change) and unrelated to the gap this PR closes, so I've left it alone — happy to hoist it out of the `try` in a follow-up if you'd like tighter attribution there too.
