### Describe the bug

On SM90, `deep_gemm.transform_sf_into_required_layout` can return a tensor aliasing the input scale without retaining the original allocation's owner. Deleting the input allows the PyTorch caching allocator to reuse its storage while the returned tensor is still live. The output then changes to the contents of an unrelated allocation.

Reproduced with the published x86_64 wheels for **sgl-deep-gemm 0.1.7 and 0.2.0**, using PyTorch 2.13.0+cu130 and apache-tvm-ffi 0.1.11 on NVIDIA H20-3e (SM90). Version 0.2.0 was installed into a separate `--target` directory and selected via `PYTHONPATH`; both its distribution version and imported module path were checked. The original shared installation was not modified.

This is a follow-up to **Bug 1 in #32188**, not a new discovery of the general ownership defect. That PR preserves ownership in SGLang's `get_mn_major_tma_aligned_tensor` wrapper and explicitly leaves the library-level fix as follow-up. Here a downstream caller uses `transform_sf_into_required_layout` directly for **weight scales**, so it does not receive that protection. #32097 also identifies this broader API impact.

I am filing here because Issues are disabled on `sgl-project/DeepGEMM`; please redirect this report if another tracking location is preferred.

### Reproduction

Save the following as `repro.py`. Select one idle SM90 GPU. No model, distributed setup, or GEMM execution is required.

```python
"""Run on one idle SM90 GPU; no model or inference framework is required."""
import gc
import importlib.metadata
import json
import sys

import torch
import deep_gemm

print(json.dumps({'sgl-deep-gemm': importlib.metadata.version('sgl-deep-gemm'),
                  'apache-tvm-ffi': importlib.metadata.version('apache-tvm-ffi'),
                  'torch': torch.__version__, 'module_file': deep_gemm.__file__}), flush=True)

clone_output = '--clone' in sys.argv
sf = torch.full((1, 128, 40), 0.0005, device='cuda', dtype=torch.float32)
source_ptr = sf.data_ptr()
out = deep_gemm.transform_sf_into_required_layout(
    sf, 16384, 5120, (1, 128, 128),
    num_groups=1, is_sfa=False, disable_ue8m0_cast=True,
)
if not isinstance(out, torch.Tensor):
    out = torch.from_dlpack(out)
if clone_output:
    out = out.clone()  # Diagnostic control: original owner is still alive here.
torch.cuda.synchronize()
before_nan = out.isnan().sum().item()
aliases_input = out.data_ptr() == source_ptr
del sf
gc.collect()
# Simulate the small allocations made by subsequent model loading/forward work.
buffers = [torch.full((1, 128, 40), float('nan'), device='cuda') for _ in range(20)]
torch.cuda.synchronize()
result = {
    'clone': clone_output,
    'aliases_input': aliases_input,
    'source_pointer_reused': any(x.data_ptr() == source_ptr for x in buffers),
    'before_nan': before_nan,
    'after_nan': out.isnan().sum().item(),
    'numel': out.numel(),
}
print(json.dumps(result), flush=True)
assert torch.isfinite(out).all().item(), 'Live output aliases recycled scale storage'
assert torch.allclose(out, torch.full_like(out, 0.0005))

```

```bash
CUDA_VISIBLE_DEVICES=0 uv run --no-project --python /path/to/venv/bin/python python repro.py
CUDA_VISIBLE_DEVICES=0 uv run --no-project --python /path/to/venv/bin/python python repro.py --clone
```

The environment must contain torch, apache-tvm-ffi 0.1.11, and sgl-deep-gemm 0.2.0. Tested with the default PyTorch caching allocator.

Observed on both 0.1.7 and 0.2.0, without cloning:

```json
{"clone": false, "aliases_input": true, "source_pointer_reused": true, "before_nan": 0, "after_nan": 5120, "numel": 5120}
```

The finite-output assertion fails. On 0.2.0 with `--clone`:

```json
{"clone": true, "aliases_input": false, "source_pointer_reused": true, "before_nan": 0, "after_nan": 0, "numel": 5120}
```

Both assertions pass. The NaN-filled buffers are a deliberate overwrite sentinel: they demonstrate allocator reuse, not a claim that the original model uses this exact fill operation. Pointer reuse depends on allocator behavior; `source_pointer_reused` makes that condition visible.

**Expected:** the returned tensor remains valid and unchanged after the caller releases its reference to the input, whether the transform copies data or returns an alias.

### Downstream impact and diagnosis

The issue was encountered in vLLM 0.29.0 with a Qwen3.8-27B-FP8 checkpoint. With external sgl-deep-gemm 0.1.7, the first `in_proj_qkvz` layer had finite inputs and weights, but 2040/5120 weight-scale values were NaN. Eventually all logits became NaN and generation degenerated into repeated tokens.

Controlled eager-mode checks on that original environment:

| Configuration | Result |
|---|---|
| External 0.1.7, original scale transform | First request fails the finite check |
| vLLM-bundled DeepGEMM | 6/6 short correctness probes pass |
| External 0.1.7, clone transformed scales while the original input is alive | 6/6 probes pass; DeepGEMM and E8M0 remain enabled |

These are short correctness checks, not full model-quality or performance validation. The full model was not rerun with 0.2.0; the standalone API reproducer above was.

The v0.1.7 source path is consistent with the observed lifetime failure:

- `csrc/utils/torch_compat.hpp::convert_to_torch_tensor` wraps `TensorView`'s raw pointer with `torch::from_blob` without retaining its owner.
- The SM90 FP32 `(128, 128)` weight-scale branch in `csrc/apis/layout.hpp` returns the unchanged tensor.
- `csrc/tvm_ffi_api.cpp::dg_transform_sf_into_required_layout` exports that non-owning view through DLPack.

Nsight Systems 2026.5.1 captured the original standalone lifetime reproducer: it contains only allocation-fill/check-related CUDA kernels, with no GEMM kernel. The direct evidence for corruption is pointer reuse and tensor values, not the profiler alone.

Could the library ensure that no-op scale-transform return values retain the input owner (or return independently owned storage), with a regression covering input deletion and allocator reuse? The clone above is a diagnostic control, not a proposed requirement to copy every transform.

### shtjww · 2026-09-17

Update: reproduced on H20 (SM90) with sgl-deep-gemm 0.2.0 — the standalone reproducer matches the reported numbers exactly (`aliases_input: true, after_nan: 5120`).

Root cause confirmed at the binding layer: `convert_to_torch_tensor()` wraps the input with a non-owning `torch::from_blob` view, and the `check_sf_layout` pass-through returns that view itself, so the DLPack export dangles once the caller frees the input.

Fix submitted at the library level: sgl-project/DeepGEMM#91 — adds an own-or-clone guard on all five scale-transform exits (zero-copy preserved on non-aliasing paths), plus a regression test that fails on the published 0.2.0 wheel and passes with the fix.
