## Motivation

Enable DeepSeek V4 DSpark speculative decoding on NPU Ascend 950 (arch35). The existing DSpark implementation only supported CUDA and older NPU (arch22). Arch35 hardware requires different sparse-attention operators, weight-loading strategies, and numerical compatibility workarounds. Several follow-up fixes address a regression where DSpark's unquantized `wo_a` path conflicted with the arch35 MXFP8 detection logic, plus NPU-specific numerical gaps.

## Modifications

- **arch35 DSpark sparse attention**: Added arch35-specific v2 sparse attention operators via a new `TorchOpLoader` extension; loaded during TP worker and DSpark draft worker initialization.
- **`wo_a` quantization fix**: `use_npu_arch35_mxfp8_wo_a()` now accepts a `wo_a_keeps_quant_config` parameter and returns `False` when DSpark explicitly disables `wo_a` quantization. This fixes a regression introduced by a previous commit that changed the assertion condition from `if fp8:` to `if quantize_wo_a:`, which caused an incorrect assertion on arch35 because DSpark's `wo_a` was not quantized. The model also caches this value instead of recomputing it at each call site.
- **DSpark stage configuration**: Added `_dspark_stage_config()` to apply draft-specific expert counts to draft stages and disable vision layers for text-only stages. Arch35 now falls back to standard vocabulary/fusion behavior instead of the arch31-specific path.
- **Weight loading**: Moved the NPU `weight_packed` → `weight` rename before stacked parameter mapping, eliminating duplicated branch logic.
- **NPU numerical compatibility**: Fall back to torch for commit-KV projection on NPU; replaced `exponential_()` (unsupported on NPU) with `uniform_ + log_ + neg_`.
