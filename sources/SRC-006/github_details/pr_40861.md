# [PR #40861] disaggregation: Support Intel XPU for staging-buffer KV transfer

## 正文

## Motivation

PD disaggregation with staging-buffer KV transfer assumes CUDA in several places along the Encoder/Prefill/Decode path. On Intel XPU these assumptions either fail immediately (for example, `torch.cuda.Event()` raises `RuntimeError: Tried to instantiate dummy base class Event`) or silently skip required synchronization because it is gated on `is_cuda`.

This PR makes the staging-buffer path device-agnostic and enables it end to end on Intel XPU, verified on 2x Intel Arc Pro B60. It also fixes two correctness issues in the PD prefill early-send path that XPU exposed but that are not XPU-specific.

`SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX` defaults to `True`, so the early-send issues affect the default PD path rather than an opt-in configuration.

### 1. CUDA-only event creation crashes the prefill scheduler on non-CUDA devices

`maybe_send_cached_prefix_chunk` creates the early-send wait event with `torch.cuda.Event()`. On builds without CUDA this raises `Tried to instantiate dummy base class Event`, so the prefill scheduler crashes when a request reuses a cached prefix under overlap scheduling.

Reproduced on Intel XPU with PD (NIXL transfer) and hierarchical cache: the second request in a group reuses the shared prefix and hits the CUDA-only event creation.

### 2. NIXL and Mooncake dropped the early-send wait event

The scheduler records a completion event on `forward_stream` and attaches it to the sender, so the transfer worker waits for the preceding prefill writes before reading the cached prefix pages. Mori consumed this event, but the NIXL and Mooncake `add_transfer_request` did not accept or propagate `wait_event`, so for those backends the event was recorded, attached, and dropped.

Without the wait, the transfer worker can read prefix pages before the preceding forward finishes writing them. The transfer still reports success because the data movement succeeds, but the transferred KV may be stale or partially written. Transfer-failure counters and performance benchmarks would not catch this; only an output-correctness check exposes it.

### 3. CUDA assumptions in the staging-buffer path

Two of these are not XPU-specific either:

- The encoder `/send` path synchronized only when `mm_embedding.is_cuda`. The sync is required on every accelerator because `transfer_sync` does not order against the device stream; without it, the transport can read a buffer before the device writes land.
- Staging initialization hard-coded `device = f"cuda:{gpu_id}"`, so a non-CUDA backend could silently allocate staging buffers on CUDA.

### Why the fixes ship together

Fixing only issue 1 makes the early-send path usable on XPU while leaving the missing synchronization in NIXL/Mooncake, which would replace an immediate scheduler crash with a silent correctness bug. The XPU staging e2e test also depends on issue 1: without it, the test fails as soon as a cached prefix is reused under overlap scheduling.

The fixes are kept as separate commits so they can be reverted, backported, and bisected independently.

## Modifications

### `0506849608` — Use the scheduler device for the PD early-send event

- `prefill.py`: replace `torch.cuda.Event()` with `self.device_module.Event()`. `self.device_module` is initialized from `self.device` in `Scheduler.init_overlap()` and is also used to build `forward_stream`, so the event and the stream it is recorded on always share an accelerator. Calling `torch.get_device_module()` without an explicit device could select the process-default accelerator instead of the scheduler's device.
- Add a CPU unit test covering event creation through the scheduler's device module.

### `fe6c3612d6` — Propagate the early-send event through NIXL and Mooncake

- `nixl/conn.py`, `mooncake/conn.py`: add `wait_event` to `add_transfer_request` and propagate it to the queued `TransferKVChunk`. The sender obtains the event through `_take_early_send_wait_event()`, and the transfer worker synchronizes it before reading or staging the KV pages. The parameter is trailing with a default, so existing call sites keep their behavior.
- The Ascend backend picks this up unchanged: `AscendKVSender` / `AscendKVManager` subclass the Mooncake sender and manager without overriding `send` or `add_transfer_request`.

**Ordering requirement.** The event must be synchronized before `gather_all_layers_to_staging()`, not only before the RDMA post. The gather synchronizes its own stream, which orders the gather before the transfer, but nothing orders the gather after the previous forward's writes. Waiting only before the RDMA post would still let the staging gather read pages the forward is still writing.

The worker-side wait blocks rather than re-queuing the chunk. Deferring would need extra bounded waiting/polling so the same chunk is not retried in a loop. The trade-off is that the worker thread can block while the covered forward is still running; this keeps the required ordering and still preserves the point of early-send, since the transfer starts as soon as the needed pages are ready instead of after the whole current forward step.

**Common sender cleanup.**

- `common/conn.py`: declare `_early_send_wait_event` on `CommonKVSender` and consume it through `_take_early_send_wait_event()` instead of `getattr()` on backend subclasses. The accessor is one-shot, so a later chunk cannot consume a stale event.
- `mori/conn.py`: switch to the shared accessor.
- `common/utils.py`: drop the Mori-specific wording from the `TransferKVChunk.wait_event` comment.

### `1324bc36e6` — Support Intel XPU for staging-buffer KV transfer

**Device helpers** (`srt/utils/common.py`)

- Add `create_device_event` and `current_device_stream`, which resolve the device module from the runtime device instead of hard-coding `torch.cuda`.

**Staging buffers** (`disaggregation/common/staging_buffer.py`)

- Device-aware allocation for CUDA, XPU, and NPU; any other device type raises with a hint to unset `SGLANG_DISAGG_STAGING_BUFFER`.
- An explicit index on the device string wins over `gpu_id` (with a warning on mismatch), so a caller passing `"xpu:3"` cannot allocate on a different device.
- Custom memory pools stay CUDA-only; XPU/NPU use the default caching allocator, and a custom pool passed on those devices is ignored with a warning.
- Triton staging kernels are restricted to CUDA. XPU `data_ptr()` values can set bit 63, which `torch.tensor(..., dtype=torch.int64)` rejects, and there is no Triton NPU backend; other supported accelerators take the torch gather/scatter path.
- Gather and scatter assert that the KV buffers and the staging buffer are on the same device, so a cross-device pair fails with a clear message instead of faulting inside a kernel.
- Allocation logs include `ptr_type=XPU-kernel-space` / `XPU-user-space` on XPU.

**Stream ordering**

- The gather orders against the calling thread's current stream, resolved per call, instead of `torch.cuda.default_stream`. The current stream is thread-local, and transfer workers run on their own threads.
- The decode scatter adds an explicit edge from `schedule_stream` before reading `req_to_token`. XPU has no CUDA-style default-stream synchronization, and a dedicated CUDA stream does not implicitly sync with unrelated work either.
- The decode scatter stream is now created eagerly, and `release_room` drains it only when the room still has an in-flight scatter. The stream is shared by all rooms, so draining unconditionally would stall the scheduler thread behind unrelated rooms on the success path.

**Staging handler and transports** (`common/staging_handler.py`, `mooncake/conn.py`, `nixl/conn.py`)

- Use the runtime device module for `Event` and `Stream` creation. `DecodeStagingHandler` derives its device from the KV buffers and requires an indexed device.
- Thread the runtime `device_type` from `server_args.device` into staging initialization.
- NIXL: use `np.uint64` for transfer descriptors so high device pointers are not truncated or read as signed. Log successful staging-memory registration, which the XPU e2e test checks. `set_kv_buffer_tensors` accepts `slot_layer_ids` for signature parity with Mooncake.

**Encoder** (`disaggregation/encoder/server.py`)

- `TensorWrapper` copies from any non-CPU device, not only CUDA.
- `/send` synchronizes for every non-CPU accelerator instead of gating on `is_cuda`, and the embedding-cache paths synchronize through `current_device_stream`.

**DCP pack** (`disaggregation/common/dcp_pack.py`)

- Order the gather against the staging buffer's producer stream instead of `torch.cuda.default_stream`, and enter it through the device-agnostic stream context.

**Metadata buffers and QK normalization** (`disaggregation/utils.py`, `models/utils.py`)

- The `INTRA_NODE_NVLINK` metadata-buffer placement now also requires `is_cuda()`. The `use_mem_pool` context stays on `torch.cuda`, since `custom_mem_pool` is a `torch.cuda.MemPool`.
- `apply_qk_norm` enters `alt_stream` through the device-agnostic stream context.

### Breaking changes for out-of-tree backends

- `init_staging_buffers` and `init_staging_allocator` take a required keyword-only `device_type`. The old implicit `"cuda"` is intentionally gone, so omitting `device_type` fails loudly instead of allocating staging on the wrong accelerator.
- `gather_all_layers_to_staging` no longer takes `gpu_id`; the device comes from the KV buffers.

### Unit tests (CPU, no accelerator required)

All new unit tests run under `register_cpu_ci` with stubs/mocks.

Early-send, 8 tests covering event creation, propagation, one-shot consumption, and worker ordering:

- `test/registered/unit/disaggregation/test_nixl_backend_basic.py`
  - `test_early_send_wait_event_is_synchronized_before_the_pages_are_read`
  - `test_early_send_wait_event_is_synchronized_before_the_staging_gather`
  - `test_add_transfer_request_forwards_the_wait_event_to_the_queued_chunk`
  - `test_taking_the_early_send_wait_event_clears_it`
- `test/registered/unit/disaggregation/test_mooncake_transfer_batching.py`
  - `test_worker_synchronizes_the_early_send_event_before_the_staging_gather`
  - `test_worker_waits_on_the_early_send_event_with_staging_disabled`
  - `test_add_transfer_request_forwards_the_wait_event_to_the_queued_chunk`
- `test/registered/unit/disaggregation/test_prefill_abort_result_cleanup.py`
  - `test_early_send_wait_event_comes_from_the_scheduler_device_module`: injects a stub device module and checks that the scheduler builds the event through it rather than through `torch.cuda`.

The worker tests verify ordering by stubbing the downstream read and checking the recorded operation order. Each test bounds the worker queue with `side_effect=[chunk, SystemExit()]`, so an implementation that stops matching the expected sequence ends the worker instead of re-dequeuing forever. `SystemExit` is used instead of `AssertionError` because the NIXL worker loop catches `Exception` and would swallow the assertion.

Staging device selection, 2 tests in `test_mooncake_transfer_batching.py` (`TestMooncakeStagingDeviceType`): check that prefill staging buffers and the decode staging allocator receive the runtime device instead of an implicit `"cuda"`. They cover the device-selection regression only, not end-to-end Mooncake staging transfer.

All ten new tests fail against the pre-fix implementation. `test/registered/unit/disaggregation/`: 379 passed.

### XPU end-to-end

`test/registered/xpu/test_disaggregation_staging_xpu.py`: 8 passed in 106s on 2x Intel Arc Pro B60 (`ZE_AFFINITY_MASK=5,6`), using the NIXL transport:

- staging buffer allocated on prefill and on decode, including the XPU kernel-space pointer format
- staging memory registered with NIXL on both sides
- single completion and deterministic output
- concurrent requests matching serial output
- multi-chunk long-sequence generation

The concurrent-vs-serial case matters most: it exercises `enable_overlap` together with a radix-cache prefix hit, which is the scenario that exposed the CUDA-only prefill event creation. It compares against the serial answers at temperature 0, so KV corruption shows up as a token mismatch.

The e2e test lives under the `xpu` vendor tree because the registered-test taxonomy rejects new paths outside the `<kind>/<subsystem>` layout, while vendor directories are exempt. It and `test/registered/disaggregation/test_disaggregation_xpu.py` are registered on `nightly-xpu-2-gpu` but stay CI-disabled until upstream NIXL XPU support lands (ai-dynamo/nixl#1536, openucx/ucx#11218); they were run locally against NIXL/UCX builds with those patches. `test_disaggregation_xpu.py` also now skips unless two XPUs are present, uses `cpu_tensor` retraction backup on decode (the host-pool backup calls `cudaHostRegister`), and no longer `pip install`s `sglang-router` at runtime.

## Performance

No CUDA-path performance regression is intended. The changes are mostly device selection and stream/event handling on initialization or correctness-critical paths.

- The gather resolves the current stream per call instead of using a fixed stream, measured at about 0.3% overhead on the affected path. The per-call lookup is intentional, because the current stream is thread-local and transfer workers run on separate threads.
- The NIXL and Mooncake transfer workers can now block on the early-send event; this is the ordering the event exists to enforce.
