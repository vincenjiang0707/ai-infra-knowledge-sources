### Describe the bug

`to_openai_style_logprobs` stores each position's top-k candidates as a dict keyed by the **decoded token text**:

```python
# python/sglang/srt/entrypoints/openai/utils.py (append_top_logprobs)
ret_logprobs.top_logprobs.append(
    {token[2]: token[0] for token in tokens}
)
```

When two distinct token ids in the top-k decode to the same string — routine with byte-fallback tokenizers, where several byte-fragment tokens all decode to U+FFFD `�` — the dict comprehension silently merges them. Two effects follow directly from the text-keyed dict collapse:

1. **Fewer entries than requested**: `top_logprobs=5` can return 4 or fewer entries for affected positions.
2. **Wrong logprob survives**: the comprehension keeps the *last* duplicate, so the surviving entry can carry a lower-ranked candidate's logprob instead of the higher-ranked one.

A related representation issue (adjacent, not caused by the collapse itself): the OpenAI layer reconstructs `bytes` by re-encoding the decoded text (`top_token.encode("utf-8")` in `serving_chat._process_logprobs_tokens`), so the original token bytes are unavailable for byte-fallback tokens — they surface as the UTF-8 of U+FFFD (`[239,191,189]`) even when no collision occurs.

### Minimal reproduction (CPU-only, no model)

```python
from sglang.srt.entrypoints.openai.utils import to_openai_style_logprobs

out = to_openai_style_logprobs(
    output_token_logprobs=[(-0.1, 1, "A")],
    output_top_logprobs=[[(-0.1, 1, "A"), (-0.5, 77, "�"), (-2.5, 88, "�")]],
)
print(len(out.top_logprobs[0]))       # 2 — expected 3
print(out.top_logprobs[0]["�"])      # -2.5 — the higher-ranked candidate was -0.5
```

### End-to-end observation

`/v1/chat/completions` with `logprobs=true, top_logprobs=5` against DeepSeek-V4-Flash-FP8 (TP4, 4×H200, both with and without EAGLE speculative decoding) returns positions whose `top_logprobs` length < 5; affected positions show `�`-decoded candidates.

### Suggested fix direction

Minimal correctness fix: preserve all candidates without keying solely by decoded text, while maintaining their order and token identity. A complete OpenAI-compatible fix may also require carrying original token bytes through the internal logprob representation rather than reconstructing them from decoded text. Happy to submit a focused PR for the minimal fix with a CPU regression test (the snippet above) if that direction sounds right.
