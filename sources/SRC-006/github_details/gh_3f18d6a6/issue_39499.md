## 正文

# Goal

This roadmap continues #14199, initiated by @ClawSeven, and builds on the community's work toward robust, efficient block-diffusion serving and Jev-style typed decisions across SGLang backends through shared components.

Carry forward unfinished serving goals alongside newer work. Full-sequence models get baseline compatibility. Checked items record merged work. Unchecked items track remaining work or evaluation. Phases can overlap, and the causal scoring and diffusion decision tracks can progress independently.

# Roadmap

- [ ] Complete shared scheduling support.

  - [x] Dynamic batching. #14883
  - [x] Prefill/decode separation. #17484

  - [ ] FDFO + LowConfidence overlap scheduling. @Betelgeu #40756
  - [ ] Extend overlap to other algorithms after state-lifetime qualification.

  - [x] Block-level radix caching. #18724

### Phase 5: Jev-style decisions across SGLang backends

- [ ] Define a shared typed decision API.

  - [ ] Accept state, named questions, and stable option IDs.
  - [ ] Declare each backend’s supported decision types and option limits.
  - [ ] Return choice, yes/no, and ordered-score results as validated JSON.
  - [ ] Return all allowed label probabilities with explicit normalization and total label mass.
  - [ ] Provide a working example, automatic capability selection, and actionable errors.

- [ ] Add a native sglang-diffusion decision pipeline backed by compatible diffusion LLMs. @rwang5203

  - [ ] Integrate with native pipeline registration, loading, and execution, starting with DiffusionGemma.
  - [ ] Reuse compatible model components and operators across SRT and sglang-diffusion.
  - [ ] Support seeded canvases, pinned positions, and bounded terminal reads.
  - [ ] Validate tokenization and map user labels to fixed answer slots.
  - [ ] Evaluate broader grammar-constrained JSON with diffusion-compatible constraints.

- [ ] Add SemIf-compatible causal scoring in SRT.

  - [ ] Reuse native Engine.score and /v1/score for direct label scoring.
  - [ ] Preserve SemIf prompts, option limits, and answer-token boundaries.
  - [ ] Qualify native prefix reuse against independently scored complete prompts.

- [ ] Qualify correctness, calibration, and serving behavior.

  - [ ] Verify mixed option counts, schemas, canvas sizes, and prompt boundaries.
  - [ ] Verify batching, cancellation, resource limits, and request-state isolation.
  - [ ] Separate normalized label probabilities from empirically validated decision confidence.
  - [ ] Evaluate quality and calibration under a frozen, independently confirmed protocol.
  - [ ] Measure latency, throughput, and memory under normal use without workload-specific tuning.

### Betelgeu · 2026-09-22

Hi @rwang5203, following up with the design outline for **Add overlap scheduling**. 

**Scope.** 
FDFO + LowConfidence only. Sync keeps many denoise steps inside one `run_batch`, so its scheduler cost is already amortized and overlap stays off. JointThreshold is not on this path yet.

**CPU/GPU overlap.** 
FDFO is one forward plus one `step()` per `run_batch`. `step()` no longer syncs the host. It still updates the block in place, and `run()` returns a `GenerationBatchResult` with the block tokens and `done` left on device. `run_batch` returns after launch. `process_batch_result_dllm` runs on the next iteration, after `copy_done`, and overlaps the in-flight forward.

**Step-result dependency.**
- Next forward: the previous step's whole block. That is what the next KV update reads. FutureMap keeps it on device (`[req_pool_size, block_size]`, by request slot). The next launch reads that tensor and does not round-trip through `dllm_incomplete_ids`.
- Next `step()`: which positions are still masked, read from that same block (`input_ids == mask_id`), plus per-request algo state. LowConfidence has none. The result still carries the state slot so JointThreshold can use this path later.


**Early block departure.** 
Overlap pre-launches only the next denoise of the current block. It does not open the next block. Output commit and departure stay in `process_batch_result_dllm`. Because that runs one iteration late, one extra step may already be in flight after the block is finished; that step does not emit again.

**KV and request slot.** 
An unresolved block keeps its slot and KV. Both are released only after process marks the block done. The in-flight forward reads the device block and that retained KV. The FutureMap row is cleared when the slot is freed, so the next request cannot pick up the previous block.

I'll opened a [draft PR](https://github.com/sgl-project/sglang/pull/40756).
If this looks right, I’ll keep refining the design and align with @ClawSeven and @wenxuewuhd. 
Please tell me if anything here is unclear, or if there’s a case I haven’t accounted for.
