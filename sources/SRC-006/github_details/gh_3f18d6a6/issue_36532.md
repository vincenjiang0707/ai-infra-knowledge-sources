### Describe the bug

On SM120, SGLang accepts `--linear-attn-prefill-backend flashinfer --linear-attn-decode-backend flashinfer --mamba-ssm-dtype bfloat16`, but Qwen3.8-Flash-Next then crashes during warmup because FlashInfer's SM120 GDN prefill path requires FP32 `state_checkpoints`:

```text
sglang/srt/layers/attention/linear/gdn_backend.py:689
sglang/srt/layers/attention/linear/kernels/gdn_flashinfer.py:332
flashinfer/gdn_prefill.py:289, in chunk_gated_delta_rule
ValueError: state_checkpoints must have dtype float32, got torch.bfloat16
```

Trying to satisfy prefill with `--mamba-ssm-dtype float32` is rejected earlier by SGLang:

```text
ValueError: --linear-attn-decode-backend flashinfer on SM100+ requires
--mamba-ssm-dtype bfloat16, got 'float32'
```

Therefore FlashInfer prefill + FlashInfer decode has mutually incompatible state-dtype requirements on SM120. The working high-performance configuration is `prefill=triton`, `decode=flashinfer`, `mamba-ssm-dtype=bfloat16`.

At minimum, the invalid all-FlashInfer combination should be rejected during argument resolution on SM120 with an actionable message. Ideally, SGLang should allocate/cast the prefill checkpoint buffer to FP32 independently from the BF16 recurrent-state cache used by FlashInfer decode.

## 评论 (1)

### SSHdotCodes · 2026-09-25

Fixed on main by #34859. On SM120, `FlashInferGDNKernel` casts the initial prefill state to float32 (`_prefill_needs_fp32_state`), allocates the checkpoints in float32 with it, and writes the final state back in the pool dtype. So `--linear-attn-prefill-backend flashinfer --linear-attn-decode-backend flashinfer --mamba-ssm-dtype bfloat16` no longer conflicts. The day-0 image was built on d91c3682, which predates that change. Closing.
