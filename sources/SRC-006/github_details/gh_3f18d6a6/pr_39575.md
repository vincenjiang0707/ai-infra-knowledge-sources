# [PR #39575] [Fix] Handle unaligned QSA extend prefixes from chunk-cache tails

state: open | updated: 2026-09-25T07:34:00Z

## 正文

## Motivation

Compressed QSA's extend write plan assumed every cached prefix length was a multiple of `compress_ratio` (4). That holds for a radix-matched prefix because QSA pages are 64 tokens, but `UnifiedRadixCache.cache_unfinished_req` can concatenate a private chunk-cache tail onto `prefix_indices`. The resulting `prefix_lens = seq_len - extend_len` is then not ratio-aligned.

Under high concurrency with `--chunked-prefill-size 16384`, a mixed EXTEND batch can therefore hit `torch._assert_async((prefix_lens % ratio == 0).all())`. On ROCm this surfaces as `HSA_STATUS_ERROR_EXCEPTION 0x1016` / scheduler `-6`; on CUDA it is a device-side assert (often reported at a later sync point). Reproduced values: `prefix_lens=842`, `842 % 4 != 0`.

This is not the same as `--enable-mixed-chunk` injecting `extend_len == 1` decode rows (`ForwardMode.MIXED`). That path is a real trigger and is what #38180 guards against, but the chunk-cache tail also breaks ordinary `ForwardMode.EXTEND`. Disabling mixed-chunk does not fix this crash.

### Why this shows up on MI355 more than MI300 / B200

The QSA grouping bug is platform-agnostic. The usual trigger is gfx950 **exact chunk fill**, which leaves an unfinished chunk-cache tail that is not a multiple of `compress_ratio`.

Upstream scheduler:

```python
def _use_exact_chunk_fill():
    return SGLANG_EXACT_CHUNK_FILL and is_gfx95_supported()
```

`SGLANG_EXACT_CHUNK_FILL` defaults to `True`, but `is_gfx95_supported()` is only true on gfx950 (MI355). Exact chunk fill hands the remaining chunk budget to a request as-is so the batch fills `--chunked-prefill-size` (better AITER kernel occupancy on gfx950). Example mixed EXTEND batch:

- batch budget = 16384
- earlier requests consume 15542
- last request gets 842 → `prefix_len = 842`, `842 % 4 == 2`

The next EXTEND then crosses a compression group (2 prefix tokens + 2 new tokens). MI300 (gfx942) and B200 (SM100) do not enable this path by default, so unfinished tails tend to stay page/ratio-aligned (`64 % 4 == 0`). That hides the bug; it does not mean those platforms handle unaligned prefixes correctly. Any other scheduler/retraction/mixed-chunk path that produces `prefix_len % 4 != 0` can still crash (CUDA: device-side assert, often at a later sync).

**A/B trigger check on MI355:** rerun the same high-concurrency workload with:

```bash
SGLANG_EXACT_CHUNK_FILL=0
```

If the crash disappears, the chain is gfx950 exact-chunk-fill → unaligned chunk-cache tail → QSA `prefix_lens % ratio` assert. This env var is a workaround for reproduction, not a substitute for this PR.

| GPU | Arch | Exact chunk fill (default) | Trigger risk |
|---|---|---|---|
| MI355X | gfx950 | on | high |
| MI300X | gfx942 | off | low / usually hidden |
| B200 | SM100 | off | low, not zero |

## Modifications

- Gate unaligned-prefix handling on `is_gfx95_supported()`. Non-gfx95 keeps `torch._assert_async((prefix_lens % ratio == 0).all())` and the original extend gather; the crossing overwrite / extra ring-slot build run only on gfx95 when a prefix is actually unaligned. Other platforms can drop this gate later if they hit the same tail.
- Drop the `prefix_lens % ratio == 0` device assert in `QwenSparseAttnBackend._qsa_build_write_plan`.
- Record `compress_prefix_members` per planned group (how many leading members sit before the current packed extend).
- Always build `compress_group_ring_locs` for extend writes so prefix-side members can be read from the pending ring.
- In `QSAIndexer`, clamp the main gather to in-chunk rows, then `_overwrite_cross_prefix_groups` recompresses crossed groups from ring keys + current `token_k`.
- Add `test_qsa_write_plan_tracks_group_crossing_extend_prefix`.
