## 正文


## Summary

Single B200 serving `nvidia/Gemma-4-31B-IT-NVFP4` with Frozen-KV MTP
(`--speculative-algorithm NEXTN`, auto-promoted to `FROZEN_KV_MTP`). Concurrent requests
come back as degenerate token mush that runs to `max_tokens`; serial requests on the same
server are clean.

**The part that contradicts the usual diagnosis:** this reproduces with plain
`/v1/chat/completions` requests carrying **no `response_format` and no `tools`**, so no
grammar object is ever constructed. In our latest run **every single unconstrained request
corrupted (8/8)** at concurrency 4. This is not a grammar bug.

**It is gated on speculative draft depth:**

- `--speculative-num-steps 5` (draft tokens 6) → **23/24 corrupt** at concurrency 4
- `--speculative-num-steps 3` (draft tokens 4) → clean at concurrency 4 **and 6**, and clean
  across **607 requests** of a real production workload
- `--speculative-num-steps 1` (draft tokens 2) → clean, 60/60 at concurrency 4
- `--speculative-num-steps 4` (draft tokens 5) → **the server does not boot**: illegal memory
  access while capturing the target verify CUDA graph (see "Second, related bug" below)

Critically, **depth 3 at concurrency 6 is clean while depth 5 at concurrency 4 corrupts** —
identical `concurrency × draft_tokens` product (24 tokens per verify batch), opposite
outcome. So this is not "the verify batch got too big"; the per-request draft chain depth is
the trigger.

Closest analogue we found: vllm-project/vllm#35288 (MTP corrupting at concurrency).
sgl-project/sglang#9187 (spec decode vs xgrammar rollback) is the lead we **falsified** —
details in "What we ruled out".

## Reproducer — lead with this one, no grammar involved

Send N concurrent plain chat completions: **no `response_format`, no `tools`**. Prompt is
~25k characters of repeated filler (roughly 6k tokens) plus a short question,
`temperature: 1`, `max_tokens: 600`,
and an explicit request for a short answer so that a correct response terminates well under
the cap — which is what makes `finish_reason: "length"` meaningful rather than ambiguous.

```python
payload = {
    "model": "google/gemma-4-31B-it",
    "messages": [{"role": "user", "content": prompt}],  # ~4k tokens filler + question
    "max_tokens": 600,
    "temperature": 1,
    # deliberately NO response_format, NO tools
}
```

Prompt tail: `"Answer in two or three short sentences of plain English."`

Run 24 of these with a client pool of 4. **Verify the requests actually overlapped
server-side** — with one container and one GPU, count maximum simultaneous in-flight
requests client-side and/or watch `sglang:num_running_reqs`. Client parallelism is not engine
parallelism if anything in front serializes; runs that serialized tell you nothing.

Every run reported here is at `temperature: 1`; we have not tested `temperature: 0` against
this configuration, so we cannot say whether sampling temperature is part of the trigger.
Concurrency 1 on the identical server is clean (6/6 and 60/60 in separate controls).

### Prompt regurgitation — likely mechanism hint

One unconstrained response did not answer at all; it **recited the prompt filler back**
almost verbatim and then stopped:

```
req17 [unconstrained] BAD finish=stop ctok=462 tail='y the drug tier, prior authorization requirements, and any copay assistance programs before I can disposition this call.'
```

The filler sentence in the prompt is: *"The pharmacy benefit verification process requires
the agent to confirm the patient's plan details, the drug tier, prior authorization
requirements, and any applicable copay assistance programs before the call can be
dispositioned."*

Reading back prompt content instead of generating a continuation looks more like the wrong
KV / wrong positions being read during the verify pass than like a sampling fault — i.e.
cross-request KV or position bookkeeping in the shared-KV speculative path when several
sequences are verified in one batch.

## The depth ladder

Same image and args throughout, `eagle-topk=1`, `num_draft_tokens = num_steps + 1`, temp 1,
genuine server-side overlap verified on every row.

| `num_steps` | draft tokens | concurrency | result |
|---|---|---|---|
| 5 | 6 | 1 (serial control) | clean (6/6; 60/60 in a separate control) |
| 5 | 6 | 2 | 1/24 corrupt (~4%) |
| 5 | 6 | 4 | **23/24 corrupt** — unconstrained 8/8, forced-tool 8/8, json_schema 7/8 |
| 4 | 5 | — | **does not boot** — illegal memory access capturing the verify graph |
| 3 | 4 | 4 | clean 12/12 |
| 3 | 4 | 6 | clean 12/12 |
| 3 | 4 | 4 | **clean across 607 requests** of a real workload (see below) |
| 1 | 2 | 4 | clean 60/60 |

### The equal-verify-token control — the row that matters

- depth 3 @ concurrency 6 → 6 × 4 = 24 draft tokens per verify batch → **clean**
- depth 5 @ concurrency 4 → 4 × 6 = 24 draft tokens per verify batch → **corrupt**

Same total verify width, opposite outcome. Any hypothesis of the form "the verify kernel
breaks above N tokens in a batch" is inconsistent with this pair. Depth is the dial.

### Powered check of the depth-3 result

24-request probes cannot exclude a low corruption rate, so we ran a 687-test production
prompt-regression suite (≈40k-token prompts, forced tool calls, temp 1) at depth 3 /
concurrency 4: **607 model-touching requests, zero corruptions** (no truncations, no invalid
JSON). Quality was unchanged versus our depth-5 and MTP-off baselines.

That gives the depth-3 claim real power: at the ~4% rate seen at depth 5 / concurrency 2 we
would have expected ~24 corruptions, and P(0 | p=0.04, n=607) ≈ 2e-11. The 95% one-sided
upper bound on the corruption rate at depth 3 is **~0.5%**. This does not prove depth 3 is
*exactly* correct — a 0.2% rate would still show zero about 30% of the time — but any rate
near the depth-5 regime is excluded.

Note it dies at **bs=5 with `num_tokens_per_req=5`** — the batch size equals the draft-token

persistent JIT cache (triton / inductor / flashinfer) and it reproduced identically, so
stale compiled kernels are **not** the cause.

Whether this shares a root cause with the corruption we cannot say — but both are
draft-depth-sensitive faults in the verify path.

## What we ruled out

1. **The grammar backend / xgrammar rollback (sglang#9187).** The unconstrained reproducer
   sends no `response_format` and no `tools`, so no grammar is constructed, and **8/8 of
   those requests corrupted** — at least as badly as the structured paths. There is no
   rollback to desync.
2. **`--constrained-json-disable-any-whitespace` (compact JSON).** With it off the symptom is
   a whitespace flood to `max_tokens`; with it on the symptom is degenerate mush to
   `max_tokens`. The flag **reshapes** the corruption, it does not prevent it — and it is
   irrelevant to the unconstrained path.
3. **The grammar × speculative-verify rework on `main`.** We deployed a nightly built from
   `main` carrying #31488, #32393, #32409 and `BatchResultProcessor.advance_grammar_fsm`
   (verified present in the container's own source, and active — the server logged
   `FROZEN_KV_MTP: supports_grammar_overlap=True`). It corrupted **9/12 at concurrency 4,
   identical to v0.5.16's 9/12**. Not fixed on `main`; cherry-picking those commits will not
   address this.
4. **Client-side / proxy serialization confounding the concurrency claim.** Every run above
   verified maximum simultaneous in-flight requests equals the requested concurrency. Runs
   that serialized were discarded as inconclusive, never counted as clean.
5. **Stale JIT/compile caches.** The depth-4 boot crash reproduces with the JIT cache dirs
   wiped.
6. **Tree drafting as a workaround.** `--speculative-eagle-topk > 1` is rejected here:
   `Frozen-KV MTP topk > 1 currently supports only the triton attention backend, got
   trtllm_mha` (`speculative/frozen_kv_mtp_worker_v2.py`). topk is therefore pinned to 1 and
   cannot be part of a mitigation, since moving to `triton` costs us far more than it buys.

### Partially tested: the verify CUDA graph

`--disable-cuda-graph` at depth 5 / concurrency 4 **does not** clean it up. Unconstrained
requests still ran to the 600-token cap, in a new shape — endless repetition of a single
special token:

```
req08 [unconstrained] finish=length ctok=600 tail='<unused6226><unused6226><unused6226><unused6226><unused6226>...'
req11 [unconstrained] finish=length ctok=600 tail='<unused6226><unused6226><unused6226><unused6226><unused6226>...'
```

So the *captured graph* is not the sole cause; the corruption survives eager execution. We
report this as suggestive rather than clean, because the run is confounded: in eager mode all
8 structured requests came back `finish_reason=abort` with 1–79 tokens, a separate
instability we have not chased.

## Impact and current mitigation

At depth 5, MTP is unusable with any real concurrency — it effectively forces
`max_running_requests=1`, discarding most of the throughput speculative decoding exists to
provide. Our mitigation is **`--speculative-num-steps 3 --speculative-num-draft-tokens 4`**,
which is clean at concurrency 4–6 and across 607 real requests, and costs only ~5%
single-stream decode throughput versus depth 5 in our own depth sweep (255 vs 269 tok/s at
`max_tokens=256`) — that sweep was run on a B300 with the same model, quantization and spec
config rather than on this B200, so treat the 5% as indicative. Depth 4 is unavailable
because of the boot crash above.

## Questions for maintainers

1. Is there draft-depth-dependent state in the Frozen-KV MTP verify path — KV slot or
   position bookkeeping sized by `num_draft_tokens`, or assuming one sequence per verify
   batch — that would explain corruption at depth 5 but not at depth 3, at equal verify
   width?
2. Is the depth-4 verify-graph capture crash at `bs == num_tokens_per_req == 5` the same
   defect surfacing as a memory fault rather than as bad output?
3. Is depth ≤3 a sound mitigation, or does it merely lower the probability enough to hide at
   our sample sizes? We can run larger samples on request.
