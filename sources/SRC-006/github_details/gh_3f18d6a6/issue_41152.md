# [Issue #41152] [Bug][AMD] aiter unified attention: Gemma 2/3 batched generations run away (Gemma 3 4B GSM8K 0.57 vs 0.83 on triton)

source: https://github.com/sgl-project/sglang/issues/41152
state: open | updated: 2026-09-25T08:50:12Z
labels: 

## 正文

### Describe the bug

On ROCm, Gemma 2 and Gemma 3 cannot use the aiter backend's paged decode (it rejects sliding-window layers: "aiter paged decode cannot honor sliding-window attention"), so the only aiter path for them is unified attention: `SGLANG_USE_AITER_UNIFIED_ATTN=1` on the single KV pool, or automatically once a hybrid SWA pool is in use. On that path, batched generations run far longer than they should and accuracy drops, while triton on the same weights is fine:

- Gemma 3 4B, unmodified tree, `SGLANG_USE_AITER_UNIFIED_ATTN=1`, single pool: GSM8K prompts are about 1,000 tokens and answers normally about 200, yet with 128 requests running the server holds 3,100-3,700 tokens per running request for as long as the eval runs. Output throughput on a 4K/1K benchmark is 275 tok/s against 3,883 on triton.
- Gemma 3 4B with a hybrid SWA pool (#41143 without its aiter guard): GSM8K strict match 0.573 against 0.830 on triton.
- Gemma 2 27B, TP 2, hybrid pool: decode also dropped the attention softcap (fixed in #41143). With that fixed, a single 4,095-token prompt continues almost word for word like triton, but under batched GSM8K the server holds about 2,800 tokens per running request against 1,200 on triton (about 120 running in both) and the eval does not finish within an hour.

Single requests looking right while batches run away suggests something in how several sequences are laid out for one decode call, but I have not narrowed it down.

### Reproduction

```
SGLANG_USE_AITER=1 SGLANG_USE_AITER_UNIFIED_ATTN=1 \
python -m sglang.launch_server --model-path google/gemma-3-4b-it --tp 1 \
  --context-length 34816 --mem-fraction-static 0.8

lm_eval --model local-chat-completions --apply_chat_template --tasks gsm8k \
  --model_args model=google/gemma-3-4b-it,base_url=http://127.0.0.1:30000/v1/chat/completions,num_concurrent=128 \
  --gen_kwargs max_tokens=4096,temperature=0
```

Then the same server with `--attention-backend triton` and no `SGLANG_USE_AITER_UNIFIED_ATTN` for comparison. The checkpoints used were the unsloth mirrors of the google -it models.

Related: #24440 (accuracy with EAGLE and aiter unified attention on Qwen3.5, closed).

### Environment

sglang at `a1b4ec02ae` (plus two fp8 patches that are not on these bf16 paths), torch 2.11 with ROCm 7.2, amd-aiter 0.1.19, 2x MI325X (gfx942) shared with a resident service.


## 评论 (1)

### siliangchen-amd · 2026-09-25

Root cause of the single-pool garbage: with `page_size` 1, `_apply_cuda_graph_metadata` never copies the decode page indices into `cuda_graph_page_table`, so every CUDA-graph replay of unified attention reads a stale table. `--disable-cuda-graph` decodes correctly on the same build. Fix and test: #41234.

On MI325X with `SGLANG_USE_AITER_UNIFIED_ATTN=1`: Gemma 3 4B now matches triton (GSM8K 0.831 vs 0.832). Qwen3-8B on the same path was also garbage and is fixed too (0.930 vs 0.935 on the aiter default backend).

Still open here:
- Unified decode is very slow at small batch and long context: 2 requests at about 5K tokens decode at about 11 tok/s on Gemma 3 4B, while triton runs one such request at about 83 tok/s. That accounts for the throughput gap above.
- The hybrid-pool Gemma 3 result (0.573) goes through the SWA branch, which already refreshed the table, so it needs a separate re-check on top of #41234.
