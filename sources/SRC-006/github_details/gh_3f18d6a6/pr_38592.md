# 3/7 — token-major dense views: a kernel-facing id IS the physical id

Base: #40327 (2/7). 3 commits, 25 files, +1091/−885.

**This is the core of the series and the PR that changes behaviour.** The other six are
hardening, adoption sweeps, deletion or consolidation around it. If you review one, review
this one — and specifically its middle commit.

## Why the layout has to change

Before, one page held a uniform array of row-blocks, one per layer per side:

```
page bytes = [L0_K * ps | L0_V * ps | L1_K * ps | L1_V * ps | ...]
```

Every per-layer view was contiguous, and the block origin was folded into its storage
offset, so layer `l` had to be addressed by a re-numbered id
`(t // ps) * (ps * blocks_per_page) + t % ps`. Views ran past the last page envelope, which
is what `view_tail_pad_bytes` sized.

That scheme is only valid **when every block has the same row width.** The old builder said
so itself, and asserted it:

> The page envelope `[L0_K*ps | L0_V*ps | L1_K*ps | ...]` is a uniform array of
> `2*layer_num` row-blocks **when K and V rows are equally wide**, so it is a valid paged
> pool under `kernel_id(t) = (t // ps) * (ps * 2 * layer_num) + t % ps`

```python
assert head_dim == v_head_dim, (
    "build_mha_views requires uniform rows (head_dim == v_head_dim); "
    "Asymmetric-KV models cannot use the unified pool (screened out at startup).")
```

One multiplier, one row shape, one stride can only address a page that is a uniform array of
equal-width blocks. Heterogeneous row widths are not *hard* under that scheme — they are
**unrepresentable**.

Now one slot's ENTRY holds every part of that token at a fixed offset:

```
page bytes  = [ entry(slot 0) | entry(slot 1) | ... ]
entry bytes = [ K_0 | V_0 | K_1 | V_1 | ... ]
```

so the per-layer view is strided with the entry as its slot stride and is indexed by
`page * ps + slot` directly.

### What that buys

Each part now carries its own geometry — `DensePart` has its own `row_shape`,
`offset_bytes` and `layer_stride_bytes`; `DenseEntryLayout.validate()` only checks
non-overlap; `mha_entry_bytes` sums `k_row_bytes` and `v_row_bytes` **separately**. No
uniform-row assert survives.

1. **Asymmetric KV** — the *layout* no longer forbids it. Startup still refuses such models,
   because the backends' read and write paths are not audited for it; what this PR removes is
   the structural obstacle, not the screen.
2. **Fused draft KV** — this one actually ships on the capability. A draft's K and V become
   *extra parts inside the same entry*, with their own row widths **and their own count**
   (lanes, not layers). Impossible under a uniform-block page. This is the concrete answer to
   "why is this churn worth it".

### Three more consequences

- **No re-numbering.** `kernel_page_multiplier` is pinned to 1 (asserted, not read from the
  spec), and `translate_kv_loc_for_kernel` now computes what `translate_kv_loc` does. The
  plumbing that carried the multiplier is dead as of this PR and is removed in **5/7** — it
  is left in place here so this PR stays the layout change and nothing else.
- **No tail pad.** The views end exactly at the last slot, so the raw buffer is allocated at
  `total_bytes`.
- `entry_bytes()` is rounded up to `ENTRY_ALIGN_BYTES` in the switch commit rather than in
  the layout types, because it feeds `page_bytes()`, buffer sizing, the sub-pool anchors,
  `move_kv_cache` envelopes and PD transfer — the alignment has to flip together with them.

## Interaction with #39477 (PD page-envelope transfers)

That PR added `_physical_to_kernel_indices` to both unified pool classes, re-numbering
physical ids by `kernel_page_blocks`. Under the token-major entry that formula is the
identity, so the method and its two call sites are removed and `get_cpu_copy` /
`load_cpu_copy` pass physical ids straight through. Verified numerically on **both** pool
classes at page sizes 1 and 4, including the round trip and that neighbouring slots are
untouched. #39477's own SWA tail-allocation tests (17 CUDA cases) pass under this series.

The one upstream test that asserted the *scaled* form
(`test_swa_transfer_page_is_physical_not_kernel_scaled`) is adapted here to assert both
paths are physical, since the multiplier it pins is what this PR removes.

## Tests

The view tests are rewritten against the new byte law `byte(t, l, K) = t * entry + l * (k + v)`,
each cross-checked against an **independent (page, slot) description** of the same bytes at
page sizes 1 and 4, for uniform and asymmetric K/V rows. That independent description is the
safety net for the whole PR: the flat builder's addressing is verified against a second
derivation rather than against itself.

## Validation

Model families exercised — a hybrid of every pool shape the unified pool supports, plus a
non-hybrid control. Perf covers the gated-deltanet hybrid (Qwen3.5-9B), the MLA hybrid
(Kimi-Linear-48B-A3B), the sliding-window hybrid (gpt-oss-20b), the tri-pool hybrid
(Inkling and Inkling-Small), and dense Llama-3.1-8B as a control. Accuracy covers the same
set and additionally the Mamba hybrid, Falcon-H1-7B. Each model is run unified against a
baseline on the same model, backend and configuration, so every delta isolates the pool.

Median inter-token latency, unified vs baseline: **+0.91%** (measured run-to-run noise floor
for this metric: 1.9%). Median GSM8K delta at n=200: **−0.25 pt** (binomial delta-sigma ≈ 3.0 pt).

Re-validated on the current base after review feedback: the stack tip (7/7) gives **+0.95%** median inter-token latency over 40 paired configurations (median per-configuration shift against the previous run of the same 40: +0.12 pp) and **−0.25 pt** median GSM8K over 26, with the full unit scope green.

The accuracy median excludes trtllm_mha, which is knowingly broken here for the reason given
below; including it the median is −0.50 pt.

## Not yet validated

fa4, trtllm_mla, cutedsl_mla and tokenspeed_mla are admitted under `--enable-unified-memory`
and supported by this change — from this commit on their kernels read per-layer views whose
slot stride is a whole entry — but our validation hardware does not
run those kernels. The same holds for trtllm_mha's SM100 kernels (trtllm-gen context and
decode) and for decode context parallelism (`--dcp-size > 1`). **Reviewers with SM100-class
hardware: please run them before merging.**

**trtllm_mha under `--enable-unified-memory` with cuda graphs is knowingly broken**, by a
defect that predates this series: the page-table refill reads a seq-lens buffer that only the
in-graph metadata kernel writes, so a replay fills too few columns. Measured on this series:
GSM8K 0.000/0.020 with graphs on against 0.900/0.900 with them off, baseline 0.905/0.900 in
both. The fix is a separate PR against `main`; it is not caused by, and does not block, this
one. Before this PR that configuration could not run at all — its prefill path OOM'd
copying a whole sub-pool — so this PR is what made the older defect reachable and measurable.
