### Describe the bug

Both `/v1/responses` and `/v1/chat/completions` decide how to hand the prompt to
the engine by looking only at `model_config.is_multimodal`, which says the
*checkpoint* can accept media — not that *this request* carries any:

`python/sglang/srt/entrypoints/openai/serving_responses.py` (current `main`, 4ea17169b):

```python
is_multimodal = self.tokenizer_manager.model_config.is_multimodal
processed_messages = self._process_messages(chat_request, is_multimodal)

if is_multimodal:
    request_prompts = [processed_messages.prompt]      # text
    engine_prompts = [processed_messages.prompt]
else:
    request_prompts = [processed_messages.prompt_ids]  # ids
    engine_prompts = [processed_messages.prompt_ids]
```

`serving_chat.py` has the same shape (`elif is_multimodal: prompt_kwargs = {"text": ...}`).

So a **text-only request served by a multimodal-capable checkpoint** throws away
the `prompt_ids` that `_process_messages` just produced and passes a string.
Downstream this costs two extra full-context tokenizations per request:

1. `serving_responses.py` re-encodes the prompt to compute the output budget:
   `prompt_length = len(tokenizer.encode(engine_prompt))` (~line 293), only
   reached because `engine_prompt` is now a `str`;
2. `TokenizerManager._tokenize_one_request` encodes the same text again before
   scheduling.

Both are O(context). On short prompts this is invisible. On **long, append-only
conversations** (agent / tool-calling traffic, where each turn resends the whole
history) it grows every turn and shows up as a steadily rising TTFT floor even
when only a few hundred new tokens are appended.

### Evidence

Qwen3.5-122B (image-capable checkpoint) driven by pure-text agent traffic,
TP4, 262144 context, prefix cache warm:

- Per-request first-byte floor scales ~2.7x with total context; late-session
  requests take >1s to first byte while appending only ~500 new tokens.
- Same boot, comparable context: `chat` 0.60s vs `responses` 1.76s — i.e. ~1.16s
  of the responses-path latency is this extra work.
- `py-spy` on the API process: **~80% of CPU in `_encode_plus`**, split roughly
  in thirds across the shared template encode, the `create_responses` length
  budget encode, and the generate path encode.
- `SGLANG_INCREMENTAL_TOKENIZE=1` only recovers the shared-template third
  (1.76s -> 1.45s); the other two bypass the cache because they re-encode text.

### Fix

Gate the text path on whether the request actually carries media
(`image_data` / `video_data` / `audio_data` on `MessageProcessingResult`).
Requests with media keep the exact previous behaviour (including the Inkling
pre-rendered-ids branch); text-only requests keep their token ids. The
`prompt_ids is str` corner case still falls back to the text path explicitly.

Measured after the change, late-session warm requests at ~100k context:

| path | before | after |
|---|---:|---:|
| `/v1/responses` | 1.72s | **0.88s (-49%)** |
| `/v1/chat/completions` | 0.49s | **0.27s (-45%)** |

A 20-request in-order replay of a real long session reproduces it
(1.73s -> 0.96s average, -45%); early short-context requests show no regression.
With incremental tokenization additionally enabled the responses floor reaches
0.51s (-70% cumulative), matching the chat path.

### Related

- #29287 — same `prompt_length` computation, other direction: for requests that
  *do* carry images the pre-expansion count under-counts and can produce a 400.
  Complementary; this issue is about text-only requests never needing that
  encode at all.
- #17206 (open, stale) — removes the encode -> decode round-trip inside
  `_apply_jinja_template` for multimodal models. Complementary: it makes the
  text path cheaper to produce, this makes text-only requests not take it.
- #27298 — also targets the jinja-path encode/decode round-trip.

### Environment

SGLang `main` @ 4ea17169b, CUDA 13.0, 4x GPU TP4, Qwen3.5-122B-A3B,
`--context-length 262144`, radix cache on. Client: pure-text OpenAI Responses
traffic from a coding agent (no image/audio/video parts in any request).
