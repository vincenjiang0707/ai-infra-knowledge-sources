## 正文

### Question

What is the recommended configuration for **DeepSeek-V4-Flash-0731 on a small node — 4×H800 (SM90), TP=4, no EP** — and is a ~40% per-stream decode deficit at concurrency 32 expected at this scale?

We benchmarked SGLang against another engine on the *same* node, same weights, same context length, and SGLang wins single-stream but trails as concurrency grows. Every scale-out lever we tried either regressed or refused to start at this size, so we would like to know whether we are simply outside the intended deployment envelope, or whether we are missing the right knobs.

### Setup

- 4×H800 80GB (SM90) on an 8-GPU NVSwitch node (4 GPUs allocated to this model), single node
- Driver 580.173.02 / CUDA 13.0
- `lmsysorg/sglang:nightly-dev-cu13-20260830-a1fe4e30` (main @ `a1fe4e30`). We use the nightly image because tagged releases cannot load this checkpoint — see #37342
- Checkpoint: local copy of `deepseek-ai/DeepSeek-V4-Flash-0731` — hybrid quantized: attention/dense `F8_E4M3`, **routed experts mxfp4-packed** (`I8` + `F8_E8M0`), so auto-detection selects `moe_runner_backend=flashinfer_mxfp4` on SM90
- Common flags: `--tp 4 --context-length 262144 --mem-fraction-static 0.80 --kv-cache-dtype fp8_e4m3 --enable-cache-report --trust-remote-code`
- Load: OpenAI-compatible streaming, short prompts (~16 tokens), 200–400 output tokens, temperature 0. Prefix scenario = 50 sessions sharing an 8k prefix, 5 incremental rounds each
- Reference engine: vLLM 0.26.0 on the same node/GPUs/weights, production-tuned over several weeks

### Measurements

| Arm | single | conc=8 | conc=32 | prefix cold TTFT p50 | prefix hot TTFT p50 | prefix hit |
|---|---|---|---|---|---|---|
| SGLang, `--speculative-algorithm DSPARK` | **221.0** | 93.2 | 39.0 | 6470 ms | 520 ms | 99.2% |
| SGLang, plain `--tp 4` (no spec) | 144.0 | 77.1 | **35.4** | 5472 ms | 523 ms | 99.2% |
| SGLang, `--dp 4 --enable-dp-attention` | 97.6 | 64.3 | 32.3 | 5905 ms | **1873 ms** | **51.6%** |
| SGLang, `--enable-two-batch-overlap` | — refused to start — | | | | | |
| *vLLM 0.26 reference* | *149.8* | *100.6* | ***58.6*** | *3588 ms* | *238 ms* | *99.2%* |

(decode tok/s per stream; all runs healthy, 100% request success except where noted)

Notes on each arm:

1. **DSPARK helps a lot single-stream** (+53% over plain TP4; accept length ≈2.05, accept rate ≈0.21) and is roughly neutral-to-positive at conc=8/32 versus plain TP4 — we did *not* observe the classic "speculation tax" here.
2. **Plain TP4 is the slowest configuration at conc=32** (35.4), which surprised us — turning speculation *off* made throughput worse, not better.
3. **dp-attention regresses at this size.** Beyond lower throughput, `--dp 4` fragments the radix cache across DP ranks: prefix hit rate falls 99.2% → 51.6% and hot TTFT rises 523 ms → 1873 ms. We understand the docs recommend the Model Gateway/Router for cache-aware DP routing; we did not deploy it for this test.
4. **two-batch-overlap cannot be enabled here**: `ValueError: When enabling two batch overlap without an EP a2a backend (moe_a2a_backend='none'), --enable-dp-attention is required (DeepSeek-V4 non-EP DP TBO path)` — so on a 4-GPU non-EP node, TBO is gated behind the lever that already regresses.

### What we would like to know

1. **Is `flashinfer_mxfp4` the right MoE runner for this checkpoint on SM90?** The routed experts are mxfp4-packed and detection routes to the trtllm-gen path. If that kernel is primarily tuned for SM100/Blackwell, is there a better-suited runner or dequantization path for Hopper at moderate batch sizes? This is our leading hypothesis for why the gap widens with batch size (at conc=32 every step is expert-bound).
2. **Is TP4/no-EP a supported optimization target for DSV4**, or is the guidance effectively "use ≥8 GPUs with dp-attention + Router / EP"? A clear answer here is genuinely useful for small-node operators; we could not find this stated in the docs.
3. Any knobs worth trying at this scale that we missed? We considered `--schedule-conservativeness`, `--cuda-graph-max-bs-decode`, and `--enable-torch-compile`, but they read as latency/small-batch levers rather than something that closes a 40% conc=32 gap — happy to be corrected.

We are not filing this as "engine X beats engine Y" — SGLang wins single-stream on this hardware and its prefix caching is excellent. We would just like to understand whether the small-node configuration is expected to trail, so we can decide between scaling the deployment out or staying put.

Happy to re-run any configuration on this hardware and report back.

### Frank-whw · 2026-09-16

We run DeepSeek-V4-Flash-0731 on single-node SM90 (4×H200, so take absolute numbers with a grain of salt vs your H800s — directionally everything below should transfer) and recently did a fairly deep nsys pass over exactly the questions you're asking. Sharing what we measured.

**TL;DR: your hypothesis in Q1 is correct, and both of your regressions have the same two root causes: (a) the mxfp4 weight-resident expert path is the wrong kernel for SM90 at batch, and (b) dp-attention without session affinity fragments the per-rank radix cache. Both are fixable with existing flags — no code changes.**

## Q1: is `flashinfer_mxfp4` the right runner on SM90? — No, and we can quantify it

We profiled both expert paths on the same checkpoint, same GPUs (nsys, per-kernel):

| expert path | per-layer expert time (decode) | share of decode GPU time |
|---|---|---|
| 4-bit weight-resident dequant GEMM (marlin-class, same family as trtllm-gen mxfp4) | **~4.3 ms/layer** | ~46% |
| FP8-resident + fused MegaMoE (`sm90_fp8_mega_moe_impl`) | **75–320 µs/layer** (24→768 tok/step) | 33–56% of a much smaller step |

That's an order of magnitude on the expert GEMM itself. At conc=32 every decode step touches nearly all experts, so the 4-bit path's dequant-per-use cost dominates — which is exactly the "gap widens with batch" shape you measured. The FP8-resident path is memory-bandwidth-bound on weight bytes (we roofline-checked: FLOP floor is ~6× below measured), so it scales gracefully with batch: in our runs, step time went 10.9 ms (1 req) → 14.4 ms (8 req) → ~20 ms (32 req) per rank, i.e. per-stream decode degrades ~2× from conc 1→32 instead of your ~5.7×.

The switch (all upstream):

```bash
SGLANG_DSV4_FP4_DEQUANT=1 \            # dequantize mxfp4 experts to FP8 at load time (env, default False)
python -m sglang.launch_server ... \
  --tp 4 --dp 4 --enable-dp-attention \
  --moe-a2a-backend megamoe            # fused single-kernel dispatch+GEMM+combine over NVLink symm-mem
```

Memory math for 4×80 GB: FP8-resident weights for this checkpoint are ~75 GB total across 4 GPUs (~19 GB/GPU), leaving room for KV at 262k context with fp8 KV — tight but it fits (we run mem-fraction 0.85 at 141 GB/GPU; at 80 GB you may need to drop context or mem-fraction).

Note `megamoe` implies EP=TP (experts get sharded 4-way) — see Q2 for why that's the right trade here anyway. It's single-node NVLink-domain only, which is exactly your topology.

## Your observation 3 (dp-attention regresses, prefix hit 99.2%→51.6%): measured the same thing, and the mechanism

The radix cache is **per DP rank**, and the DP dispatcher (`total_requests`/`total_tokens`) balances each request independently — there is no session/prefix affinity in `data_parallel_controller.py`. So with dp=4, each round of your 5-round sessions has a ~3/4 chance of landing on a rank that has never seen the prefix. We ran a multi-turn agentic replay (48 sessions × 12 turns, ~35k-token contexts) against dp=4 and got the same picture from the other side: **25–42% of turns arrived at a rank with zero prefix hit** and re-prefilled the whole context (turn latency 17 s vs 9 s warm). Your 51.6% hit rate at 5 rounds is the same phenomenon.

Two fixes, both of which we validated:

1. **Session affinity via `routed_dp_rank`** (OpenAI-protocol extra field, upstream; `data_parallel_rank` is its deprecated alias). Hash your session/conversation id to a rank client-side or in your gateway. This restores the 99% hit rate you get with plain TP because each session always lands on the rank that owns its prefix.
2. **Hierarchical cache as a backstop** (`--enable-hierarchical-cache` + a host/storage tier): in our replay, adding a shared L3 took cross-rank cold turns from 25% → **0%** and turn latency p50 from 10 s → 2.4 s, because a rank that misses locally prefetches the KV instead of recomputing (~9 ms per hit in our setup vs seconds of recompute).

Without at least one of these, dp-attention at small scale is expected to lose to plain TP on any multi-turn/prefix workload — your measurement is not an anomaly.

## Q2: is TP4/no-EP the intended envelope?

Can't speak for the maintainers, but empirically on our 4-GPU SM90 node we swept TP/DP/EP/PD topologies and **tp4 + dp4 + dp-attention + EP4-via-megamoe + DSPARK** beat plain TP4 and DeepEP-style paths at every concurrency we tested — *provided* the two fixes above are in place (FP8-resident experts; affinity or hierarchical cache). Plain TP4 no-EP keeps full expert replicas per GPU, which wastes exactly the memory you need for FP8-resident experts + KV, and it forgoes the fused a2a path. So I'd phrase the answer to your Q2 as: no-EP is not where the optimized kernels are; on a single NVLink node the intended fast path is megamoe EP=TP.

On your note 2 (plain TP4 slower than DSPARK at conc=32): consistent with our data — the expert GEMM is bandwidth-bound, so verifying ~2–3 draft tokens per step amortizes one weight sweep over more tokens; speculation is effectively free throughput at batch on this architecture. Your accept length 2.05 is notably lower than what we see (3.8–4.7 on this checkpoint) — that may be worth a separate look once you're on the FP8 path, since the draft head shares the trunk compute path and the mxfp4 runner may be affecting it.

Happy to share nsys breakdowns if useful.
