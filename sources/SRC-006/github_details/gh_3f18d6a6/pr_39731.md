# [PR #39731] [DCP] Use logical token capacity for PD admission and load reporting

source: https://github.com/sgl-project/sglang/pull/39731
state: open | updated: 2026-09-25T07:32:20Z
labels: documentation, run-ci, run-ci-extra

## 正文

Related PD/DCP/DFlash PRs: #39743, #40794, #39749, #40164. Each is independent and they can merge in any order.

## Motivation

DCP admission mixes per-rank KV rows with logical request tokens. The paged DCP allocator widens every per-rank row into `attn_dcp_size` logical ids, but the scheduler, the PD bootstrap check and load reporting compare logical request lengths against per-rank rows. A concrete failure: a 1M-token PD request is rejected against 690,240 per-rank rows although the DCP8 allocator holds 5,521,920 logical tokens. Load responses also underreport capacity while used-token counts are already logical.

## Modifications

- `KVCacheConfigurator.logical_token_capacity` converts configured per-rank rows into logical tokens: `max_total_num_tokens * attn_dcp_size` for the target's paged allocator. It does not read `allocator.size`, which under the unified Mamba pool also counts Mamba state bytes. Draft sizes are already widened (`loc_space_scale`) and pass through.
- `ModelRunner.logical_max_total_num_tokens` delegates to it. `TpModelWorker` reports it as the scheduler's `max_total_num_tokens`, and `max_req_len`, the PD prefill bootstrap check and the decode prealloc admission check (`DecodePreallocQueue`) all use the logical limit. The DCP multipliers in output budgeting and pool statistics are removed so capacity is counted once.
- Hybrid SWA: the SWA allocators never widen under DCP, so their capacity is already logical. `max_req_len` for DCP + hybrid SWA drops the old `x dcp` factor, which overstated what the allocator can hold.
- `sglang:num_pages` divides by the allocator's (widened) page size, so it keeps reporting per-rank pages.
- Under DCP, `sglang:max_total_num_tokens`, `kv_total_blocks` in KV events, `max_total_num_tokens` in `/server_info` and the load response's token capacity now report logical tokens (`x attn_dcp_size`).

## Tests

`test_dcp_logical_capacity.py` (CPU): worker capacity for DCP 1/2/8, capacity from configured rows with a real unified Mamba allocator (fails with an `allocator.size`-based capacity: 688 != 512), and draft / hybrid SWA capacity under DCP.

GPU check, Kimi K3 PD 1P1D on 8xB300 per role (prefill TP8, decode TP8), DFLASH full draft (block size 8), NIXL, GSM8K 5-shot. With prefill DCP8 → decode DCP8, the reported `max_total_num_tokens` goes from 111,168 on main to **889,344** with this PR on decode, and from 58,496 to **467,968** on prefill. That's exactly the ×8 logical capacity; for reference, a DCP1 decode reports 323,328. Accuracy and acceptance are unchanged on a build with all five PD/DCP/DFlash PRs (#39743, #40794, #39731, #39749, #40164) (prefill DCP1 → decode DCP8: 95.8% on all 1,319 questions, average accept length 5.01).
