# [Issue #40949] ValueError: pool memory leak detected! crash with LMCache (MP mode) + EAGLE speculative decoding after a load-back hit (page_size > 1)

## 正文

## Environment

- SGLang v0.5.20 (ROCm, 8x MI300-class GPUs); the code path is platform-independent
- Model: Kimi-K2.6 (MLA), `--tp 4`, `--speculative-algorithm EAGLE3` with the official EAGLE3 draft (`kimi-k2.6-eagle3-mla`)
- `--enable-lmcache` with LMCache running in MP mode (external LMCache daemon), `--page-size 16`
- The bug is model-independent: any EAGLE-family model + LMCache MP mode + `page_size > 1` triggers it

## Symptom

After a request hits the LMCache external KV store (RETRIEVE / load-back into GPU memory), the scheduler crashes at the next idle invariant check on **all TP ranks simultaneously**:

```
ValueError: pool memory leak detected! [full] total=95904, available=95520, evictable=640, protected=0, session_held=0, uncached=0
```

`available + evictable = 96160 > total = 95904`: 256 tokens (16 pages x 16 tokens/page) are double-counted in `evictable_size_`.

## Root cause

`LMCRadixCache.match_prefix` (`sglang/srt/mem_cache/storage/lmcache/lmc_radix_cache.py`) builds the MP load-back marker key from a local `key` variable that is **not bigram-normalized**:

```python
key = params.key
if self.page_size != 1:
    aligned_len = len(key) // self.page_size * self.page_size
    key = key[:aligned_len]            # slice copy made BEFORE normalization
base_res = super().match_prefix(params)  # base class flips params.key.is_bigram IN PLACE
...
self._mp_load_back_markers[req.rid] = _LMCacheLoadBackMarker(
    key=RadixKey(token_ids, key.extra_key, key.is_bigram, ...)
)
```

- The insert path (`RadixCache.cache_finished_req` -> `insert`) normalizes the key: `maybe_to_bigram_view(self.is_eagle)` then `page_aligned`. With EAGLE on, every node in the radix tree is stored with `is_bigram=True`.
- The base `RadixCache.match_prefix` normalizes `params.key` **in place** (`key.maybe_to_bigram_view(self.is_eagle)`), but the local slice in `LMCRadixCache.match_prefix` was copied **before** that flip.
- With `page_size == 1` the local `key` is just an alias of `params.key`, so it accidentally follows the in-place flip and the bug does not trigger. With `page_size > 1` the slice copy stays `is_bigram=False` forever.
- The marker key flows into `_finish_load_back`, where `key[start:end].child_key(self.page_size)` produces raw-token tuples instead of bigram pairs. These never compare equal to the bigram child keys already inserted by `cache_finished_req`, so the load-back attaches a **second radix node covering the same token range**, and `evictable_size_ += fetched` double-counts those tokens.
- At the next idle pass, `SchedulerInvariantChecker._check_all_pools` sees `available + evictable > total` and raises.

## Trigger conditions (all required)

1. EAGLE / EAGLE3 speculative decoding (`is_eagle=True`)
2. LMCache enabled in MP mode (external daemon; the load-back path is active)
3. A load-back hit: a request whose prefix already exists in the LMCache store (warm cache / re-running the same prompt)
4. `page_size > 1` (with `page_size == 1` the non-normalized copy happens to alias the normalized key, masking the bug)

## Reproduction

1. Start the engine: Kimi-K2.6, `--tp 4`, EAGLE3 draft, `--enable-lmcache` (MP mode), `--page-size 16`
2. Run one request that stores its KV, e.g.
   `sglang.bench_serving --dataset-name random --random-input 8192 --random-output 256 --num-prompt 1` (default `--seed 42`)
3. Run the same request again (same seed -> same prompt -> load-back hit). The engine crashes at the next idle check. If the server warmup request itself hits previously stored KV, the crash happens during startup — no bench needed.

Fixed by #40733.


## 评论 (1)

### htyvista · 2026-09-26

Update: this bug no longer exists on `main` as of #38652 (merged 2026-09-25), which replaced the LMCache radix cache integration with a unified implementation (`lmcache_unified_radix_cache.py`) and removed `lmc_radix_cache.py` entirely.

The new implementation eliminates this bug by construction:

- The load-back flow key is built with an explicit `is_bigram=self.tree_core.is_eagle` at construction time (`prefetch_from_storage`), not via an in-place flip that a pre-normalization slice copy could miss.
- `RadixKey.__getitem__` slices preserve the `is_bigram` flag, so every downstream slice of the flow key (`_publish_external_loaded_prefix` → `insert`) stays bigram-consistent with the insert path (`cache_finished_req`).

This issue remains valid for releases that still carry the old `lmc_radix_cache.py` (e.g. v0.5.x) — the trigger conditions and reproduction steps above apply to those versions. A fix PR (#40733) was A/B verified but superseded by the rewrite before merging.
