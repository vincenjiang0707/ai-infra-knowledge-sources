# [PR #39994] [AMD][MiniMax-M3] Optimize the MXFP8 sparse decode kernel tail on gfx950

source: https://github.com/sgl-project/sglang/pull/39994
state: open | updated: 2026-09-25T09:24:07Z
labels: amd, jit-kernel, memory-pool

## 正文

## Motivation

On MiniMax-M3-MXFP8 (TP4/EP1, MI355X/gfx950) a tail of elementwise, fill and copy kernels costs 4.05 ms/step, 18.8% of decode kernel time (over 946 launches in 57 sparse layers). It is launch-bound, not arithmetic-bound: every recurring kernel in it costs 3.9–5.1 us whether it compares two integers or copies a KV row, 4.3 us on average. Only the GEMMs are bigger, at 9.70 ms/step, and they are the arithmetic itself. The other 7.77 ms is 25 separate model, MoE and all-reduce kernels, none above 1.71 ms. So the tail is the biggest addressable lever in decode.

Most of those kernels do no useful work. One divides every K/V value by exactly 1.0. One clamps expert ids into a range they are already inside at EP1. One zeroes a buffer the next GEMM overwrites in full. This PR removes **627 kernel launches per decode step**, taking the affected kernels from 946 to 319 launches and 4.05 to 1.39 ms/step. End to end that is 8.6–11.8% more output throughput across a concurrency 4–64 sweep, with GSM8K flat (0.977 → 0.978, inside the repeat-to-repeat spread).

## Modifications

The contribution is two-fold:

- **A. Stop doing work that has no effect (−513 launches/step):** Three changes, a division by 1.0, a clamp that cannot fire, and a zero-fill the next GEMM overwrites in full.
- **B. Fuse or replace kernels that do have an effect (−114 launches/step):** Two changes, a dtype cast folded into the paged KV write, and an ATen advanced-indexing store replaced by a direct Triton scatter that is cheaper per launch at the same launch count.

**A1. The KV scale division changes nothing** (`memory_pool.py`). `MHATokenToKVPool.set_kv_buffer` divided K and V by `k_scale`/`v_scale` whenever a scale existed rather than whenever it mattered. The MiniMax sparse store passes none, so it inherited `MiniMaxSparseKVPool.set_kv_buffer`'s `1.0` default and ran `div_(1.0)` twice per layer. The new `_kv_scale_divides()` skips only a host `1.0`; a device scale still divides as before, since reading its value would break CUDA-graph capture. All seven scale-divide sites in the file share the helper. Drops both `MulFunctor<float>` rows, 57+57. **Bit-exact.**

**A2. The MoE expert-id clamp does not fire for EP1** (`mxfp8_moe_amd_gfx95.py`, `triton.py`). The MXFP8 runner clamped router ids into the local expert range. For EP1 every expert is local, so the ids are already in range and the clamp changes nothing. It is now gated on `_needs_expert_filter()`, a check the runner's non-MXFP8 branch already made, extended to also require that the weight's expert count matches the config's — the clamp bounds ids by `w13.shape[0]`, so a config whose count does not describe the addressable range keeps the clamp. Removes `compare_scalar_kernel<int>` 114, `BitwiseOrFunctor<bool>` 57, `masked_fill_kernel` 57, and 57 of the `__amd_rocclr_copyBuffer` launches, 143→86. **Bit-identical.**

**A3. The grouped-GEMM output zero-fill is dead** (`mxfp8_moe_amd_gfx95.py`). `_grouped_gemm_mxfp8` zero-filled its output as insurance against a route filtered to expert `-1` being dropped from the sort, which would leave its row unwritten. It is gated on the same boolean as A2. Nothing can be filtered there, so `torch.empty` suffices. Removes both `FillFunctor` rows, 57+57. **Bit-exact.**

**Note for Ax:** A2 and A3 hang on the same boolean, `expert_map is None and not filter_expert`, so A3 cannot fire without A2. It holds only at EP=1 with a known expert count the loaded weights agree with; under EP>1, an unknown count, or a mismatch, the clamp and the fill both run as before.

**B1. Fold the bf16 → fp8 cast into the paged write** (`memory_pool.py`). The sparse store cast K and V with `.to(self.dtype)` and then scattered. `reshape_and_cache_flash` already converts on store, so `can_store_kv_fused_cast()` and `store_kv_fused_cast()` make that one launch, not cast + scatter. K and V arrive as `dim=-1` QKV slices, so `is_contiguous()` is False. But the kernel takes the token stride as an argument, so it only needs each token's `(head, dim)` block dense, which those slices are. `_has_dense_kv_rows()` tests that instead, and also pins the token count, since the kernel grid comes from it and the slot index is read unmasked. Anything the guard rejects takes the old path. Removes both `float8_copy_kernel_cuda` rows, 57+57. Cache bytes are identical to cast + scatter on this workload; see the appendix on where the two conversions could in principle diverge.

**B2. Scatter the sparse index-K store** (`cache_move.py`, `memory_pool.py`). `MHATokenToKOnlyPool.set_k_buffer`, which `set_index_k_buffer` delegates to, ended in `k_buffer[loc] = src`, which ATen dispatches as `index_put`. All the store does is copy whole rows: for each `i`, write the row `src[i]` into slot `loc[i]`. `index_put` has to serve every use of that syntax, so it broadcasts the source, accepts index tensors of any shape, and moves data one element at a time. `store_k_slots` does only the copy, a token-parallel Triton scatter modelled on the existing `store_cache_4d`. It shares B1's `_has_dense_kv_rows()` guard rather than requiring full contiguity, since it too takes the source token stride as an argument; a source that fails the guard falls back to advanced indexing. One kernel replaces one kernel, so the win is per-launch cost rather than launch count: **4.7 → 4.4 GPU us/layer.**

### Impact on CUDA and on other AMD architectures

No change carries an architecture check, so the dispatch conditions are the whole story:

| change | file | reaches CUDA when |
| --- | --- | --- |
| A1 | `memory_pool.py` | host `1.0` scale — skipped there too, bit-exact |
| A2 | `moe_runner/triton.py`, `mxfp8_moe_amd_gfx95.py` | never — non-MXFP8 branch unchanged |
| A3 | `mxfp8_moe_amd_gfx95.py` | never — gfx95 runner only |
| B1 | `memory_pool.py` | a pool passes `can_store_kv_fused_cast()` |
| B2 | `cache_move.py`, `memory_pool.py` | a store passes `_has_dense_kv_rows()` |

`can_store_kv_fused_cast()` needs nhd layout, `store_dtype == uint8`, a non-quantized cache, a flat 3-D slot-indexed buffer, `head_dim == v_head_dim`, unit scales, equal K/V shapes and dense per-token blocks for exactly `loc.numel()` tokens; `_has_dense_kv_rows()` needs each token's `(head, dim)` block packed with leading dim `loc.numel()`. Anything a guard rejects keeps today's path, so nothing outside the table changes. gfx942 behaves exactly as gfx950: A1, B1 and B2 are identical there, and it never runs the gfx95 MXFP8 runner that holds A2 and A3.

The 57 added cases pin the contract, not the tuning. `store_k_slots` is checked against ATen advanced indexing on identical inputs, and both guards that route a store to the new path — `_has_dense_kv_rows()` and `can_store_kv_fused_cast()` — are tested on their accept and reject sides. That includes `test_store_k_slots_accepts_token_strided_source`, the layout a contiguity check would wrongly reject, and four rejection cases that must fall back to the old path.

### Reading conc 32 and 64

The median TTFT rises at those two points are a prefill-scheduling artifact, not a decode cost: p99 TTFT falls 3.6% and 4.0% at the same two points, and a slower prefill would move both. Each run falls into one of two prefill regimes — one request per batch, or the full 16384-token chunk budget. The regime favoured the candidate here, so median TPOT (−17.3%, −29.8%) and p99 E2E (−19.4%, −26.3%) at these points are a best case, not a floor; clean rounds alone put the conc-64 gain near −7%. Read p99 TPOT, median ITL and p99 TTFT here: regime-independent, and improving in all three runs.

Overall, the sweep is a win at every concurrency point: output throughput +8.6% to +11.8%, median ITL −7.4% to −11.2%, and every tail metric improving — p99 TPOT, p99 TTFT and p99 E2E without exception.
