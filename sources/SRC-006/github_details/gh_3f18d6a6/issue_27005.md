### Describe the bug

The Qwen3 Coder tool-call parser currently buffers string parameter values until it sees `</parameter>` or another terminating tag.

For large string arguments, such as a `write_file` tool with a long `content` field, this means OpenAI-compatible streaming clients do not receive incremental `delta.tool_calls[].function.arguments` fragments while the content is being generated. Instead, the whole string argument is emitted as one large chunk only after the closing parameter tag arrives.

This breaks the expected streaming behavior for tool calls with large string fields. Clients that render or process tool-call arguments incrementally cannot observe progress until the full parameter is complete.

### Expected behavior

For string-like parameters, Qwen3 Coder streaming should emit argument fragments progressively as the value arrives, while preserving valid JSON across chunks. For example, after receiving the beginning of a large `content` parameter, the stream should already include something like:

```text
{"content": "<!DOCTYPE html>\n<html>\n...
```

before the parser has seen the final `</parameter>` token.

Non-string parameters such as booleans, integers, arrays, and objects can continue using the existing complete-value parsing path.

### Actual behavior

The parser emits the parameter key and value only after the closing parameter tag is seen. With a long `content` value, the client gets one large `delta.tool_calls[].function.arguments` chunk at the end instead of incremental chunks during generation.

### Reproduction

A minimal parser-level reproduction is a Qwen3 Coder tool call where a string parameter is split across streaming chunks and the closing `</parameter>` tag is delayed or split:

```text
<tool_call>
<function=write_file>
<parameter=file_path>/tmp/demo.html</parameter>
<parameter=content>
<!DOCTYPE html>\n
<html>\n
<body>hello</body>\n
</par
ameter>
<parameter=overwrite>false</parameter>
</function>
</tool_call>
```

When these chunks are fed through `Qwen3CoderDetector.parse_streaming_increment`, no incremental `content` argument fragments are emitted before the content parameter closes. The `content` argument is buffered until `</parameter>` is complete.

### Suggested fix

Stream schema string-like parameters incrementally in `Qwen3CoderDetector`, while keeping the existing complete-value path for non-string parameters.

A proposed implementation and regression test are already available in PR #25246:

https://github.com/sgl-project/sglang/pull/25246

That PR verifies that a long `content` parameter emits before `</parameter>` is received, and that the final accumulated JSON remains valid.

### Environment

This is a parser-only issue in the Qwen3 Coder function-call detector. It does not depend on CUDA kernels, model forward execution, scheduling, or token generation speed.

Observed against the current `main` branch behavior before PR #25246.

### RedMoonnn · 2026-09-26

I reproduced this on a real long-running agent request and confirmed the root cause with a paired detector-only replay. The issue still applies to current `main` (`Qwen3CoderDetector` still waits for a parameter terminator before emitting the value).

The request used `stream=true`; the `Write` tool declared both `file_path` and `content` as JSON Schema strings. The generated `content` was 15,375 characters.

| | Existing detector | Patched detector |
|---|---:|---:|
| Completed | yes | yes |
| SSE events | 8 | 2,108 |
| Longest silence from request start | 300.893 s | 16.058 s |
| Longest gap after streaming began | 300.893 s | 0.421 s |
| Final tool arguments | identical | identical |
| Final content SHA-256 | identical | identical |

The original stream emitted the tool name and short `file_path`, then buffered the long `content` until `</parameter>`. The patched stream delivered safe JSON string fragments throughout generation. This also keeps the retained parser buffer bounded and does not fabricate a closing quote for interrupted values.

I have prepared a current-main patch with explicit-string-only streaming and regression coverage for chunk boundaries, Unicode/escaping, literal `null`, non-string types, interruption, and buffer bounds. Please consider reopening this issue; PR #41313 provides the implementation and full reproduction details.
