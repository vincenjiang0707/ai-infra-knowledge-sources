## Motivation
<!-- Describe the purpose and goals of this pull request. -->
Context: Deepseek-v4-pro uses DeepseekMoE (served as MegaMoE) as its mixure of experts with a shared expert that is activated across all tokens and a fine-grained routed experts. 
- flash model: 1 shared + 256 routed
- pro model: 1 shared + 384 routed 
>Note that the authors also chose to use FP4 with QAT such that routed expert weights are in MXFP4 while all other parameters (including the shared expert in the official checkpoints) stay in blockwise fp8 format. 

For each token $t_i$ , a V4 MoE layer does two different GEMM operations:
1. shared - dense MLP on every token (in FP8)
2. routed - grouped GEMM over the top 6 selected experts (MXFP4)

Launching each kernel independently wastes launches and stream syncs on every layer (this is true even if they shared a dtype). DeepGEMM already caught this and added native MegaMoE support via (num_shared_experts, separate shared_l1/shared_l2 weights, mixed FP8 and MXFP4).

The existing Sglang fusion logic in `deepseek-v2.py` 
```python
        # num_fused_shared_experts drives weight remapping in deepseek_weight_loader:
        # mlp.shared_experts → mlp.experts.256 when > 0.
        self.num_fused_shared_experts = 0 if _fusion_disabled else n_shared_experts
```
only works if shared and routed share a dtype/layout (from `deepseel-v4.py`):
```python 
        # Need to disable if quant precision mismatch, even if
        # --enforce-shared-experts-fusion is specified
        if quant_blocks_shared_experts_fusion(quant_config):
            return (
                "Quantization keeps shared experts at a higher precision than the "
                "routed experts, so they cannot be fused into the quantized "
                "routed-expert path."
            )
```
but the official deepseek-ai checkpoints do not, so that path does not apply on MegaMoE (it can still run on the trtllm-gen runner if you `--enforce-shared-experts-fusion` and requantize shared FP8→MXFP4, which is what #35505 did)

## Modifications

<!-- Detail the changes made in this pull request. -->

Changes mainly in mega_moe.py: 
This PR went through a lot of iterations, starting with a naive index implementation that was supposed to be easier to maintain and more local w.r.t. number of files changed. The memory and throughput overhead of maintaining a python cache of expert indices was extremely non-trivial (as seen below) which motivated for a kernel level change in `mega_moe_predispatch.cuh`. 

Fusion puts the FP8 shared expert inside routed MegaMoE (removing six standalone kernels per layer) but this regressed throughput across all batch sizes as it bypassed the existing alternate-stream fork. In the unfused profiles, the shared expert’s second GEMM overlapped routed MegaMoE in 184/184 observed calls per rank, covering a median 94.1–95.6% of its duration. Naively fusing the path without modifying `forward_mega_moe()` function returned before the existing alternate-stream fork, leaving the whole router/top-k/pre-dispatch/MegaMoE region on the current stream.

```python
  if moe.mega_shared_l1_weights is not None:
          return _run_mega_routed(
              moe, hidden_states, forward_batch, input_ids_global, num_tokens
          )
  
      sbo_overlap_flag = (
          moe.alt_stream is not None
          and moe.num_fused_shared_experts == 0
          and num_tokens > 0
          and get_is_capture_mode()
      )
```

The current iteration of this PR keeps the same kernel changes but forks the whole fused region in `forward_mega_moe()` which lets other graph work overlap it; at BS1, main, kernel-only, and kernel-plus-fork achieved 756.90, 721.97, and 759.08 tok/s.

Major files changes:
1. `_get_mega_moe_symm_buffer` includes `num_shared_experts` in its cache key and allocates the shared-expert buffer for the fused configuration
2. `_run_mega_routed` forwards the shared-expert count and transformed L1/L2 weights through gate and top-k to `run_mega_routed_experts`
3. `run_mega_routed_experts` selects the consuming MegaMoE `BLOCK_M`, passes the shared-scale destination to pre-dispatch, and launches `fp8_fp4_mega_moe` with the shared weights
4. `forward_mega_moe` forks the entire fused router/top-k/pre-dispatch/MegaMoE region onto the existing alternate stream during CUDA-graph capture and joins before returning
