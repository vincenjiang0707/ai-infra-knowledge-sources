# 4/7 — give the write loc an explicit id space

Base: #38592 (3/7). 2 commits, 38 files, +583/−78.

This is a **safety guard and a typing discipline**, not a feature. It adds no capability; it
makes a class of silent corruption impossible to reach unnoticed.

## Why it is needed *now*

A pool's write door takes ids in one of two spaces: **VIRTUAL** ids, which the allocator
hands out and the radix / accept / free paths key on, and **KERNEL-FACING** ids, which
address the pool's buffers. A unified pool needs the second; every other pool's allocation is
already physical, so the two coincide. Nothing said which one a given loc was.

Handing a unified pool a virtual loc was therefore silent: virtual ids sit **inside** the OOB
probe's bounds, so the write landed on the wrong slots and only the output was wrong.

Until 3/7 there was a numerical tell, and a probe that used it:

> A kernel-facing id is `phys_page * (page_size * blocks_per_page) + offset` with
> `offset < page_size`, so its remainder modulo the page stride is below page_size; a VIRTUAL
> id satisfies that only in the first block. **Vacuous at blocks_per_page 1.** Virtual ids are
> in range for the OOB probe, so this is the only check that separates them.

3/7 pins `blocks_per_page` to 1, which by that probe's own admission makes it vacuous — so
3/7 deletes it. **This PR replaces the lost signal with an explicit tag**, because once
kernel ids *are* physical ids the two spaces are, by value, the same kind of integer.

## The contract (commit 1)

| piece | role |
|---|---|
| `KVWriteLoc.id_space` | `"virtual"` (the default) or `"kernel"` |
| `KVWriteLoc.for_batch(fb, …)` | builds one from a batch, inheriting the batch's space — so a producer cannot forget |
| `ForwardBatch.out_cache_loc_id_space` | the batch's own space, stamped `"kernel"` by `KVIndexTranslator.rebind_write_loc` |
| `KVCache._check_write_loc_space` | a pool that sets `requires_translated_write_loc` refuses anything not marked kernel-facing. Gated on `SGLANG_ENABLE_ASYNC_ASSERT`, like the OOB probe next to it |

Note the check is a **declaration** check, not detection — the backend does not inspect ids,
it carries a marker it received. That is the only thing left once detection is impossible.

Two smaller changes ride along:

- `rebind_write_loc` now runs on non-translating pools too, to stamp the space. It still
  rebinds — and still records `out_cache_loc_virtual` — only when the pool actually
  translates, so nothing on the plain path changes shape.
- `HybridLinearKVPool`'s two write doors take `loc_info` rather than `loc`: they forward to a
  sub-pool, so they must pass the marker along instead of unwrapping to a bare tensor. The MLA
  branch's duplicated write_loc derivation is hoisted to the one place both branches use.

## The adoption (commit 2)

Two shapes, and nothing else:

```python
KVWriteLoc.for_batch(forward_batch, loc, swa_loc=...)   # at the backends' write doors
out_cache_loc_id_space="kernel"                          # at capture-time batch constructors
```

The capture-time constructors build a `ForwardBatch` outside `init_new`, so no rebind runs
over them; they fill `out_cache_loc` with ids the runner already translated (or with sink
ids), and must say so themselves.

With the producers stamped, a unified pool's write door now rejects a loc that reached it
without a rebind, instead of writing to the slots the untranslated ids happen to name.

## When a new backend must wrap

**If your backend can receive a unified pool — practically, if it carries a
`kv_index_translator` — its write door passes `KVWriteLoc.for_batch(forward_batch, loc,
swa_loc=…)`, never a bare tensor and never a bare `KVWriteLoc(...)`.** If you translated the
ids yourself, say `KVWriteLoc(loc, id_space="kernel")`. A capture-time `ForwardBatch`
constructor stamps `out_cache_loc_id_space="kernel"` itself.

Backends that never see a unified pool (`dsa`, `hpc_ops`, `intel_amx`, `minicpm` — none of
which carries a translator) are deliberately left alone; stamping them would be noise.

`aiter` **is** stamped here. Its loc is `forward_batch.out_cache_loc`, the same expression
the other backends pass, so its ids were already correct — what it lacked was the mark, which
would have made the unified door refuse a *healthy* write under
`SGLANG_ENABLE_ASYNC_ASSERT` and left its doors outside the guard entirely.

## Known gap

Nothing mechanically enforces that the adoption is **complete**. `test_write_loc_id_space.py`
tests the mechanism — propagation, the door refusing, composites forwarding — but never
enumerates the doors, and `bind_and_verify_backends` binds the translator to every reachable
backend, so there is no allow-list to diff against. The five unstamped backends above were
found by hand-enumerating all 70 write-door call sites.

The repo already has the right pattern to copy —
`test_kv_translate_ownership.py::TestUnifiedTranslateBanned` regex-scans backend sources and
asserts a banned-pattern list is empty. A follow-up should ban a bare tensor / bare
`KVWriteLoc(...)` at any write door whose backend carries a translator. Flagging it here
rather than leaving it implicit.

## Validation

Model families exercised — a hybrid of every pool shape the unified pool supports, plus a
non-hybrid control. Perf covers the gated-deltanet hybrid (Qwen3.5-9B), the MLA hybrid
(Kimi-Linear-48B-A3B), the sliding-window hybrid (gpt-oss-20b), the tri-pool hybrid
(Inkling and Inkling-Small), and dense Llama-3.1-8B as a control. Accuracy covers the same
set and additionally the Mamba hybrid, Falcon-H1-7B. Each model is run unified against a
baseline on the same model, backend and configuration, so every delta isolates the pool.

Median inter-token latency, unified vs baseline: **+1.03%** (measured run-to-run noise floor
for this metric: 1.9%). Median GSM8K delta at n=200: **+0.50 pt** (binomial delta-sigma ≈ 3.0 pt).

Re-validated on the current base after review feedback: the stack tip (7/7) gives **+0.95%** median inter-token latency over 40 paired configurations (median per-configuration shift against the previous run of the same 40: +0.12 pp) and **−0.25 pt** median GSM8K over 26, with the full unit scope green.

Against the preceding PR's run on the same matrix the median per-model shift is −0.11 pp —
this PR moves nothing.

## Not yet validated

aiter, fa4, trtllm_mla, cutedsl_mla and tokenspeed_mla are admitted under
`--enable-unified-memory` and supported by this change, whose stamped write doors include
theirs, but not yet validated: our validation hardware does not run those kernels
(aiter is ROCm). The same holds for trtllm_mha's SM100 kernels and for
`--dcp-size > 1`. **Reviewers with SM100-class or ROCm hardware: please run them before
merging.**
