### Question / observation

DeepSeek-V4-Flash-0731 on 4× RTX PRO 6000 Blackwell (SM120, 96 GB, TP=4, PCIe gen5, no NVLink), sglang v0.5.16, `dsv4` attention backend, `flashinfer_mxfp4` MoE, fp8_e4m3 KV: **prefill throughput sits at ~2-7K tok/s**, while a stock **vLLM 0.25.1 recipe on identical hardware reports ~12.5K tok/s prefill at 256K context** (marlin MoE backend, expert parallelism, fp8 KV — https://github.com/hermia-ai/deepseek-v4-flash-sm120-stock-vllm). A 4-6× gap at large context on the same GPUs suggests the SM120 dsv4 prefill path has significant headroom. Is this expected/known, and is there tuning guidance?

### Our measurements (sglang v0.5.16 + the #33407 dispatch fix, DSPARK enabled)

- Aggregate prefill, 9 concurrent ~90K-token prompts: **~5,540 tok/s** (813K prompt tokens / 146.9 s wall; outputs negligible at 61 tokens each)
- Aggregate prefill, 3 concurrent ~650K-token prompts: **~2,805 tok/s** (1.95M / 695.5 s)
- Single ~650K-token prompt: **~2,870 tok/s** (226.4 s to first token)
- Live scheduler logs show per-batch input throughput starting ~6.5K tok/s at low sequence position and declining to ~1.8-2.1K past several hundred K tokens (attention cost growth expected — but the absolute level is the question)
- `--chunked-prefill-size` 4096 vs 8192: statistically identical wall time (146.9 vs 149.0 s on the 9×90K test), so chunking overhead isn't the limiter
- Startup notes `Breakable CUDA graph is incompatible with DeepSeek-V4 (heavy capture-pool memory pressure); disabling prefill CUDA graph` — so DSV4 prefill runs graph-less on this path
- `--max-prefill-tokens` at default 16384; `--disable-flashinfer-autotune` set (SM120 autotune instability, upstream rec)

### Relevant config

```
--tp-size 4 --trust-remote-code
--mem-fraction-static 0.90 --context-length 1048576
--swa-full-tokens-ratio 0.1
--max-running-requests 64 --cuda-graph-max-bs 64
--kv-cache-dtype fp8_e4m3 --moe-runner-backend flashinfer_mxfp4
--speculative-algorithm DSPARK --speculative-attention-mode decode
--disable-custom-all-reduce --chunked-prefill-size 4096
--disable-flashinfer-autotune
```

(`--disable-custom-all-reduce` because sgl_kernel custom allreduce fails CUDA-graph capture on our PCIe GPU pairs, #11957 class.)

### Questions

1. Is dsv4-backend prefill on SM120 known to be unoptimized relative to the decode path (which benchmarks well for us — ~1,280 out tok/s at concurrency 64 with DSPARK)?
2. The vLLM recipe uses expert parallelism (`--enable-expert-parallel`) and the marlin MoE backend. Would `--ep-size 4` (or an EP/TP hybrid) be expected to materially improve MoE prefill on PCIe-only SM120 boxes with sglang, and is that combination supported with `flashinfer_mxfp4`?
3. Is the disabled prefill CUDA graph a meaningful contributor at these chunk sizes, or is the gap dominated by MoE GEMM kernel choice on SM120?
4. Any recommended experiments/flags for prefill specifically on this hardware class? Happy to run and report numbers — SM120 hardware is available for validation.

Context: prefill throughput directly bounds a fairness problem we've documented (a single large-context prefill monopolizes chunked-prefill admission for its full duration — several minutes at ~2K tok/s for near-1M prompts — starving concurrent small requests).
