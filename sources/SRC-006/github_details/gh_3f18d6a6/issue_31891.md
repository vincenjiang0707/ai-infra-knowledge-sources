### Motivation

**TL;DR: running multiple embedding servers on one GPU delivers 1.83x (RTX A6000) to 2.6x (H200 NVL) the throughput of a tuned single server on the same GPU. sglang's built-in DP is one assert away from supporting this natively; external orchestration is the only option today.**

#### Background

While benchmarking `/v1/embeddings` serving (Qwen3-Embedding-0.6B, RTX A6000), we found the short-input path is CPU-bound at saturation: GPU SM-active is only ~33% while the server tops out around 800 req/s. The bottleneck is Python-side work (tokenization/scheduling/serialization), not the GPU — the same profile that two independent sources identified before us:

- The SGLang-Omni team's [same-GPU DP with CUDA MPS guide](https://sgl-project.github.io/sglang-omni/basic_usage/same_gpu_dp.html) reports 1.4-2.1x for TTS on H100 (tuned single replica at ~29% SM-active), and explicitly invites validation on other workloads.
- Roadmap #15344 carries the item *"Multi-replica execution per single GPU (DP-style, e.g. 'DP4 on 1 GPU')"*, citing [arXiv 2512.07846](https://arxiv.org/abs/2512.07846) (multiple worker processes parallelize CPU-side overhead).

Embedding serving should be an even cleaner case than TTS — prefill-only, no decode state, weaker KV pressure — so we ran the experiment.

#### Experiment

We ported the Omni guide's deployment discipline (private MPS daemon, sequential health-gated replica launch, per-replica KV surfacing, MPS attach verification via `get_server_list`/`get_client_list`, per-replica independent saturation) to embedding serving. Setup: Qwen3-Embedding-0.6B, 50-token token-exact inputs, `--request-rate inf` with `--max-concurrency 64` per replica, 2048 prompts per replica, seeded, radix cache flushed per run, three fresh-server repetitions per arm, 32-core single-NUMA host, equal total server cores across arms (16), bench clients pinned to separate cores, `lmsysorg/sglang:latest`.

RTX A6000 (mean of 3, range in parentheses):

| arm | config | total throughput | scaling |
| --- | --- | --- | --- |
| single | 1× mf=0.80, 16 cores | 816.2 req/s (84.9) | 1.00x |
| DP2 + MPS | 2× mf=0.40, 8+8 cores | 1283.9 req/s (27.1) | 1.57x |
| DP3 + MPS | 3× mf=0.26, 5 cores each | **1490.4 req/s (166.5)** | **1.83x** |
| DP2, no MPS | as DP2, plain time-slicing | 1135.6 req/s (30.2) | 1.39x |

The same protocol repeated on 2x NVIDIA H200 NVL (one GPU measured): single 573.0 → DP2+MPS 908.3 (1.59x) → **DP3+MPS 1507.1 (2.63x; conservative min/max ratio 2.33x)** → DP2 time-slicing 1038.6 (1.81x).

#### Findings

1. **The colocation gain is robust across hardware classes.** DP3 is the best arm on both a workstation A6000 (1.83x) and a datacenter H200 (2.3-2.6x), consistent with the CPU-side-overhead thesis: replicas multiply Python-side capacity while the GPU absorbs the streams.
2. **The per-replica KV asymmetry warned about in the Omni guide reproduces on both machines**: with equal `--mem-fraction-static`, later replicas get smaller pools (161k vs 85k tokens at A6000 DP2; 326k vs 233k on H200), because each profiles remaining free memory at startup. Harmless for short-input embedding; must be handled in native support.
3. **The MPS-over-time-slicing margin is host-dependent.** On the A6000, MPS added ~13% over plain time-slicing at DP2 at sustained windows; on the (shared-tenant) H200 host the two DP2 arms overlapped and time-slicing was not behind. MPS setup is still what unlocks the best arm, but the margin should be measured on the deployment host rather than assumed.
4. **The residual gap to linear is host CPU contention between scheduler processes**, not the GPU: with equal core budgets the schedulers settle into a stable asymmetric split, and pinning each replica's scheduler to a dedicated core slice recovered a further ~3% with ~3x variance reduction (A6000, paired interleaved A/B). For CPU-bound workloads, budget cores per replica first.

Caveats: throughput numbers are means of three fresh-server repetitions per arm on each machine; absolute values are not comparable across machines (different hosts/tenancy), only scaling shapes are.

#### Why native support

Today this requires external orchestration: N launch commands, N ports, an external load balancer, hand-managed MPS daemon and CPU pinning. sglang already has almost everything needed — `--dp-size N` launches N workers behind a built-in load balancer, and the GPU assignment arithmetic (`base_gpu_id += tp_size * pp_size * gpu_id_step`) naturally places all workers on one GPU when `gpu_id_step=0`. The only hard blocker is the validation:

```python
assert self.gpu_id_step >= 1, "gpu_id_step must be positive"   # server_args.py
```

Beyond relaxing that (behind an explicit opt-in), native support needs:

- **Sequential worker startup for the same-GPU case**: the DP controller currently starts all workers concurrently (threads); colocated workers racing memory profiling is exactly why the Omni guide launches replicas sequentially behind a health gate. Alternatively, require `--max-total-tokens` so pools are declared, not profiled.
- **Per-worker memory validation**: divide/validate `--mem-fraction-static` across colocated workers, or require an explicit token cap (the Omni guide's `--max-total-tokens` approach).
- **MPS deployment guidance in docs**: daemon lifecycle, attach verification, and the fallback-to-time-slicing failure mode are worth documenting (the margin between them is host-dependent, which is itself a reason to document how to verify attach).

We have a working native implementation of the above (validation opt-in, sequential colocated startup, plus a required multi-tokenizer embedding repack fix it surfaced) with unit/E2E tests and benchmark evidence, ready to submit as a small PR stack. @narutolhy, since you signed up for the roadmap item, glad to coordinate or co-author.
