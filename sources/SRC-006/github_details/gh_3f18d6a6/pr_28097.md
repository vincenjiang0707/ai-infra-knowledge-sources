# [PR #28097] [AMD] sgl-kernel: fix host-side WARP_SIZE on wave32 targets, allow gfx1151 build

source: https://github.com/sgl-project/sglang/pull/28097
state: closed | updated: 2026-09-27T01:29:16Z
labels: amd, sgl-kernel

## 正文

Two small changes to get sgl-kernel building and running on gfx1151 (Strix Halo / Ryzen AI Max+ 395). The WARP_SIZE fix applies to every wave32 ROCm target, not just gfx1151.

**The bug:** `include/utils.h` hardcodes `WARP_SIZE` to 64 in the host compile pass. On wave32 targets the device pass picks 32, so any kernel using `WARP_SIZE` in both `__launch_bounds__` and its host-side `dim3` launch gets compiled with bounds for 128 threads but launched with 256. First MoE forward:

```
Launch params (64, 4, 1) are larger than launch bounds (128) for kernel topkGatingSoftmax<...>
hipLaunchKernel: Returned hipErrorLaunchFailure
Memory access fault by GPU node-1 ... Reason: Page not present.
```

The fault gets blamed on `moe_align_block_size`, but that's just the next kernel after the rejected launch — `AMD_SERIALIZE_KERNEL=3 AMD_LOG_LEVEL=3` shows the real one.

**The fix:** the host pass now takes the wave width from `SGL_KERNEL_WAVE_SIZE`, which setup_rocm.py derives from `AMDGPU_TARGET` (64 for CDNA gfx9xx, 32 otherwise). Defaults to 64 if unset, so any other build path behaves exactly as today. CDNA and CUDA preprocessor output is identical before/after — only the host value on wave32 targets changes, where it's currently broken. This also fixes the same latent host/device mismatch in `moe_align_kernel.cu`'s thread-count rounding and shared-mem sizing.

The other commit adds gfx1151 to the allowed arch list in setup_rocm.py — kernels compile cleanly for it, the guard was the only blocker.

Tested on a Ryzen AI Max+ 395 (Radeon 8060S, ROCm 7.13 nightly, PyTorch 2.13): `cyankiwi/Qwen3.5-35B-A3B-AWQ-4bit` (256-expert MoE) page-faults on the first request without the fix and generates fine with it. Dense models (Qwen3-0.6B, Qwen3.5-4B) behave the same before and after. I can't verify CDNA myself, but since the macro value is unchanged there the existing MI300 CI should cover it.

Earlier attempt was #25175 — I closed that one myself before anyone looked (lint was red). This version fixes the macro at its source instead of renaming identifiers in the kernel files.
