# MiniMax-M3: fuse per-token fp8 quant into add-RMSNorm and fold the MoE all-reduce into the next layer

> **Stacked on [#36574](https://github.com/sgl-project/sglang/pull/36574)**, which adds the MXFP8 dense ptpc decode path (`_ptpc_weight`, `MXFP8_DENSE_PTPC_DECODE_MAX_M`) this PR feeds. Its diff shows up here until #36574 merges; review #36574 first. This PR's own change is the files listed under **Changes**.

## Motivation

On gfx950, the MXFP8 dense linears from #36574 take a per-token fp8 `(tensor, scale)` pair when the token count is at most `MXFP8_DENSE_PTPC_DECODE_MAX_M` (128). Without this PR, a separate `per_token_quant_hip` launch builds that pair by re-reading the normed activation that was just written to HBM. This PR produces the pair in the kernel that already writes the activation.

## Changes

- **Fused add-RMSNorm emits fp8** (`kernels/ops/layernorm/minimax_m3_rmsnorm.py`). The ROCm Triton Gemma fused-add-RMSNorm gains `emit_fp8`. It writes the fp8 tensor and the per-token scale in the same pass and attaches them as `out._fp8_qinput = (fp8, scale)`. It quantizes the bf16-rounded output, so the pair is bit-identical to `per_token_quant_hip` on the unfused path.
- **Fused all-reduce + RMSNorm + per-token quant** (`parallel_state.py`, `communication_op.py`, `layernorm.py`, `communicator.py`). `GroupCoordinator.fused_allreduce_rmsnorm_quant_per_token` calls aiter's `custom_fused_ar_rms_quant(..., emit_bf16=True)`. This folds the previous layer's MoE all-reduce into the next layer's input norm and the qkv quantization. It is exposed as `LayerCommunicator(enable_fused_ar_quant_per_token=True)`. The call returns `None` whenever the backend cannot handle the request (not ROCm, no custom all-reduce, no kernel, or an exception), and the caller then falls back to the existing unquantized fused-AR-RMSNorm path.
- **Consumer** (`fp8_utils.py`). When the input carries `_fp8_qinput`, `aiter_w8a8_block_fp8_linear`'s ptpc branch uses that pair and skips `per_token_quant_hip`.
- **Opt-in per model.** `GemmaRMSNorm(emit_fp8_qinput=...)` defaults to `False`, so other `GemmaRMSNorm` users (Qwen3.5, Qwen3-Next, Gemma, Step3.5, ...) never pay for the fp8 write. MiniMax-M3 turns it on for its decoder norms on HIP, and passes `enable_fused_ar_quant_per_token=_is_hip`.
- **All-reduce deferral for sparse layers on ROCm** (`minimax_m3.py`). On ROCm, the sparse-layer MoE all-reduce may now be deferred into the next layer's fused norm. Off ROCm, the old "force the immediate all-reduce" workaround stays. `is_last_layer` is already passed on main (#40868), so the final layer never defers.

Both fp8 paths are gated on gfx950 and `M <= MXFP8_DENSE_PTPC_DECODE_MAX_M`. That is exactly the window in which the ptpc GEMM, the only consumer, is selected. Outside that window nothing extra is written.

**CUDA:** this PR's own changes do nothing on CUDA. The emission is gfx950-only, the fused-AR entry point returns `None` off ROCm, and the sparse-layer workaround is unchanged off ROCm.

## Performance

Re-measured on this head (`aa65ac1f22`) against #36574, both merged with the same `main` (`81cb895b85`). Hardware: MI350X, MiniMax-M3-MXFP8, **TP4 on 4 GPUs** (the TP8 runs in earlier revisions of this description used 8). Server and benchmark commands are the ones under Reproduction, with `--tp 4` and no `AITER_CONFIG_FMOE` on either side. Two reps per boot; the table takes the better rep on each side, because single reps moved by up to 10% at bs 4, 8 and 16. Treat the bs16 gap as noise.

| batch size | ITL #36574 (ms) | ITL this PR (ms) | change |
|---|---|---|---|
| 1 | 7.50 | 7.33 | −2.3% |
| 2 | 8.27 | 8.10 | −2.1% |
| 4 | 9.18 | 8.98 | −2.2% |
| 8 | 11.13 | 10.98 | −1.3% |
| 16 | 15.48 | 14.65 | −5.4% (noisy) |
| 32 | 20.92 | 20.97 | +0.2% |

The points where both reps agree (bs1–4) show about a **2% decode ITL reduction**, and there is none at bs32. That fits the gate: the fp8 hand-off only applies at M ≤ 128. Input throughput is flat (207–216k tok/s on both sides).

The M=1 skinny fp8 GEMV from earlier revisions was dropped. It took 4.1–5.0 µs against aiter's 6.4–7.9 µs on the four qkv shapes it covered, which is about 1% of a bs1 decode step and nothing at bs ≥ 2.

## Accuracy

gsm8k with `sgl-eval` 0.1.2: 512 examples, `max_tokens 2048`, `temperature 0`, `seed 0`, single run, same boots as the benchmark.

| | score | stop_rate | truncated_rate |
|---|---|---|---|
| #36574 | 97.07% | 98.44% | 1.56% |
| this PR | **96.48%** | 97.85% | 2.15% |

That is **−0.59 pp**, within the −1.0 pp bar. The earlier TP8 run on an older head measured −1.56 pp. As before, almost all of the drop is truncation: 3 more completions hit the 2048 cap. The fp8 pair is bit-identical to the unfused quant (see Tests), so the remaining difference comes from the all-reduce/norm fusion and the ROCm sparse-layer deferral changing accumulation order. A run with a larger `max_tokens` budget would settle whether any drop remains; it has not been done. TP8 has not been re-measured on this head.

## Also fixed here

`aiter` MoE runner: `fused_moe_kwargs` may now override `activation`. #36574's MXFP8 MoE quant info passes `activation=Swiglu` there, but the runner also passes it explicitly, so every MXFP8 launch with `--moe-runner-backend aiter` crashed with `fused_moe() got multiple values for keyword argument 'activation'`. The fix belongs in #36574 as well.

## Tests

- `test/registered/kernels/ops/layernorm/test_minimax_m3_rmsnorm.py::test_gemma_fused_add_rmsnorm_fp8_matches_per_token_quant_of_output` (gfx950 only) checks that the emitted fp8 and scale quantize the bf16-rounded output. It fails if the kernel instead quantizes the fp32 value before rounding. The whole file passes: 16 passed on MI350X.
- A manual check against `aiter.per_token_quant_hip` gave bit-identical scale and dequantized values at M = 1, 8 and 128.
- The fused all-reduce path, the communicator gate and the M3 end-to-end path have no unit test. They are covered only by the TP4 benchmark and gsm8k runs above.
- The AMD PR CI jobs default to MI300 (gfx942), where the new case is skipped.

## Deliberately not in this PR

- The skinny M=1 fp8 PTPC GEMV (dropped: ~1% at bs1 only).
- The CUDA accuracy gate for sparse-layer deferral; it stays disabled off ROCm.
- Replacing the `_fp8_qinput` tensor attribute with an explicit argument. The attribute follows the existing pattern, but it goes stale if the norm output is modified in place before the linear.

@hubertlu-tw added in 10e44b67c3. The new `--quant-type per_token|both` flag times three paths: unfused (all-reduce -> RMSNorm -> per-token quant), fused all-reduce + RMSNorm followed by a separate per-token quant, and the single-kernel `fused_allreduce_rmsnorm_quant_per_token`. ### kevin-mii · 2026-09-25

Restructured in 289ec3e36e. **End-to-end validation is still pending, so please don't merge yet.** The ITL and gsm8k numbers in the description were measured on `aa65ac1f22` and haven't been re-run on this head.

- **Hand-off.** The per-token `(fp8, scale)` pair is now passed as a tuple, the same way as the per-group fused-AR path, instead of the `_fp8_qinput` tensor attribute. `aiter_w8a8_block_fp8_linear` sends a per-token `input_scale` straight to the ptpc decode GEMM. It raises an error if such an input reaches a layer without the rowwise weight copy, or with M > 128. The fused kernel no longer writes the bf16 output that only carried the attribute.
- **Dropped the fp8 output of the Triton Gemma add-RMSNorm.** With `--enable-aiter-allreduce-fusion`, every M3 norm takes the fused-AR path, so it never ran. Without dense block convert, nothing consumed its fp8.
- **Gate.** M3 enables the per-token path only when its attention projections carry the rowwise-fp8 copy (MXFP8 -> block-fp8 convert on the aiter block GEMM, i.e. `SGLANG_FORCE_MXFP8_BLOCK_CONVERT_DENSE=1` on gfx950).

Verified on MI350X, ROCm 7.2.4:
- Through the real `Fp8LinearMethod`, a per-token tuple gives output bit-identical to main's bf16 input path at M = 1-128, at 5.2-5.5 µs.
- Every row of the fused-AR benchmark passes.
- `test_prepare_attn_steps.py` and `test_minimax_m3_rmsnorm.py` pass.
