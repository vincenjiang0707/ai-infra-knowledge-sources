# [Issue #41151] [Perf] Padded decode CUDA-graph slots cost more with longer contexts on the triton backend (bs 5 on the bs-8 graph: 27.7 -> 35.9 ms/token at 30K)

source: https://github.com/sgl-project/sglang/issues/41151
state: open | updated: 2026-09-25T07:14:57Z
labels: 

## 正文

### Describe the bug

With the default decode CUDA-graph sizes (1, 2, 4, 8, 12, ...), a batch of 5 runs the bs-8 graph. On the triton attention backend the three padded slots are not free, and what they cost grows with the context length of the real requests:

- 30000-token prompts: 5 requests take 35.9 ms per token on the bs-8 graph and 27.7 ms on an exact bs-5 graph (+30%).
- 512-token prompts: the same padding costs 11.90 vs 10.65 ms (+12%).

GEMM cost does not depend on context length, so this points at the decode attention doing work for the padded slots in proportion to the real sequence lengths. One candidate is `get_num_kv_splits` sizing the splits over a batch that includes the padded entries (whose seq_len is the fill value 1), but I have not profiled it.

At 32K a padded slot costs about 2.7 ms per step, roughly half of a real 32K-token request (about 5.2 ms). Anything that moves a KV-bound long-context workload from 4 to 5 concurrent requests loses throughput because of it: on the setup below, 48 requests of 32K at concurrency 48 went from 132 to 109 tok/s when a larger KV pool (#41012) let 5 requests run instead of 4, although the step time at equal concurrency did not change.

### Reproduction

`allenai/Olmo-3-7B-Instruct`, 1x MI325X, TP 1, bf16. The Olmo2 model override picks the triton attention backend on ROCm.

```
python -m sglang.launch_server --model-path allenai/Olmo-3-7B-Instruct --tp 1 \
  --mem-fraction-static 0.8 --context-length 40960
# second server: the same plus --cuda-graph-bs-decode 1 2 3 4 5 6 7 8 12 16 24 32

python -m sglang.bench_serving --backend sglang --dataset-name random-ids \
  --random-input-len 30000 --random-output-len 1024 --random-range-ratio 1.0 \
  --num-prompts N --max-concurrency N
```

Median TPOT (ms):

| prompts | N | default graphs | every bs up to 8 captured |
|---|---|---|---|
| 30000 tokens | 4 | 25.4 | 25.4 |
| 30000 tokens | 5 | 35.9 (bs-8 graph) | 27.7 |
| 30000 tokens | 8 | 43.4 | 43.3 |
| 512 tokens, 2048 out | 4 | 10.20 | 10.07 |
| 512 tokens, 2048 out | 5 | 11.90 (bs-8 graph) | 10.65 |
| 512 tokens, 2048 out | 8 | 12.60 | 12.49 |

A second MI325X host gave the same picture at 30000 tokens (N=4: 24.0 ms; N=5: 36.8 ms on the bs-8 graph, 27.1 ms with an exact bs-5 graph).

Capturing every size up to 8 avoids it, at the cost of more graphs. I have not tried other backends or CUDA.

### Environment

sglang at `a1b4ec02ae` (plus two fp8 patches that are not on this bf16 path), torch 2.11 with ROCm 7.2, amd-aiter 0.1.19, MI325X (gfx942), `SGLANG_USE_AITER=1`.
