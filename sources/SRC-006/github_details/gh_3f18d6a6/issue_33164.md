### Describe the bug

While writing unit tests for `srt/utils/request_logger.py` (#33077, part of #20865), I found that the `max_length` truncation contract of `--log-requests` is bypassed for list payloads, so a single request can emit a multi-MB (worst case multi-GB) log record even though truncation is enabled.

**1. JSON format (`_transform_data_for_logging`): a list longer than `max_length` skips per-element truncation entirely.**

The short-list branch recurses into elements (so each element is truncated), but the elided branch returns head/tail slices *without* transforming them:

```python
elif isinstance(data, (list, tuple)):
    if len(data) > max_length:
        half_length = max_length // 2
        return list(data[:half_length]) + ["..."] + list(data[-half_length:])  # elements NOT transformed
    return [_transform_data_for_logging(v, max_length) for v in data]          # elements transformed
```

So the *bigger* payload gets *less* truncation — exactly inverted from the intent.

**2. Text format (`_dataclass_to_string_truncated`): list elements are never truncated at all.**

Both branches stringify raw elements (`str(data)` / `str(data[:half])`), so at `--log-requests-level >= 2` (where `skip_names` is `None` and nothing is redacted), a multimodal request with e.g. one 1 MB base64 string in `image_data` writes the entire base64 into the log line.

Measured on current `main`:

```python
big = "x" * 1_000_000

# JSON format
_transform_data_for_logging([big] * 10,   2048)  # per-element truncated -> ~20 KB total  (OK)
_transform_data_for_logging([big] * 2049, 2048)  # elided branch          -> ~2.0 GB total (!)

# text format
_dataclass_to_string_truncated([big] * 10, 2048) # -> ~10 MB log line (elements untouched)
```

Expected: `max_length` bounds both the element count *and* each element's size in every branch, in both formats.

### Reproduction

CPU-only, no server needed:

```python
import json
from sglang.srt.utils.request_logger import (
    _dataclass_to_string_truncated,
    _transform_data_for_logging,
)

big = "x" * 1_000_000
print(len(json.dumps(_transform_data_for_logging([big] * 10, 2048))))    # 20550
print(len(json.dumps(_transform_data_for_logging([big] * 2049, 2048))))  # 2048008199 (~2 GB)
print(len(_dataclass_to_string_truncated([big] * 10, 2048)))             # 10000040 (~10 MB)
```

### Related question — is top-level-only `skip_names` intended?

`skip_names` filtering is applied only at the top nesting level (recursive calls drop it), so a redacted key like `"text"` nested one level deeper is kept. My unit tests in #33077 currently pin this as intended behavior (redaction targets top-level request fields); happy to adjust if the intent is recursive redaction.

I'm happy to submit a fix PR (propagate element-level truncation through both elided branches + truncate elements in the text format) once maintainers confirm the intended semantics — it would slot naturally on top of the tests in #33077.

### Environment

Reproduced on current `main` (690de09), CPU-only, Python 3.12, torch 2.9 CPU. The functions under test are pure Python, environment-independent.
