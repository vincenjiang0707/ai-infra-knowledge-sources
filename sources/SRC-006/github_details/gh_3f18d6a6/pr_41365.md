# [PR #41365] [HiCache] Store the MHA L2 host pool as INT8, 1.78x more cached tokens per GB

source: https://github.com/sgl-project/sglang/pull/41365
state: open | updated: 2026-09-27T06:33:48Z
labels: documentation, hicache

## 正文

## Motivation

HiCache stores L1 and L2 in the same dtype, so one byte of host DRAM buys one byte of cached KV. This keeps L1 BF16 for attention and stores L2 as INT8, restoring to BF16 on a hit. Caching policy, radix tree, scheduler and transfer engine are untouched; only the L2 representation changes.

For Qwen3-8B at TP=1: 82,944 host bytes/token against 147,456, so a fixed `--hicache-size` holds **1.78x more tokens**.

## Design trade-off

Every existing host pool mirrors its device pool's dtype, so the mover stays a byte copy. This one is asymmetric. The JIT mover takes separate strides but a single `element_size`, so a 2048-byte BF16 row cannot be written into a 1152-byte encoded row. Both directions stage through a same-width device buffer:

```
D2H  device BF16 -> encode -> staging -> mover -> host arena
H2D  host arena -> mover -> staging -> decode -> device BF16
```

That is 1.78x L2 capacity for two device staging buffers and an encode/decode per direction. If the codec cost dominates on some workload, a fused kernel or a mover-side adapter is the fix, and I would rather hear that now than after merge.

## Modifications

New: `pool_host/int8_codec.py` (pure tensor logic, no SGLang imports), `pool_host/int8_staging.py` (the staging buffers), `pool_host/mha_int8.py` (`MHATokenToKVPoolHostINT8`), plus unit tests.

`pool_host/mha.py`: 7 lines of dispatch in `get_mha_host_pool_cls`. MXFP8 and asymmetric pools keep precedence, since neither is representable in this record.

`environ.py` and the env-var docs: two flags.

One 1152-byte record per `(layer, K|V, token)`: 1024 B INT8 payload, 8 BF16 per-head scales, 112 B padding. `1152 = 9 x 128` because the JIT mover needs `element_size % 128 == 0`. Per-head absmax, scale computed in float32 so the BF16 quotient is exact, and the scale can never be zero or subnormal (an all-zero head would otherwise become NaN).

Off by default behind `SGLANG_EXPERIMENTAL_HICACHE_INT8`. The pool rejects at startup, by name, the geometries the fixed record cannot express: non-BF16/FP16 device pools, `head_dim != v_head_dim`, `head_num * head_dim != 1024` (a TP other than 1 on an 8-KV-head model), layer-sharded pools, `page_size != 1`, `io_backend != kernel`, and layouts other than `layer_first`.

## Accuracy

The error bound `|x_hat - x| <= (0.5 + 2**-8) * s + 2**-8 * |x_hat|` is asserted elementwise against adversarial inputs on CPU, CUDA and MPS, with zero violations.

The restore path runs in practice: the Experiment B runs below restored 167,899 tokens (INT8) and 126,997 (BF16) out of L2 while serving real requests.

**Not measured:** the same prompts generated from BF16 L2 and from INT8 L2, compared token by token. My harness could not arrange for a prompt to be demoted into L2 and still resident when re-sent, so it reported no number rather than a misleading one. Guidance on exercising L2 restores deterministically in a test would be welcome.

## Speed

`Qwen3-8B`, TP=1, host tier 8 GB, four paired runs, SGLang's own benchmark client, equal host bytes per pair.

| | BF16 L2 | INT8 L2 |
|---|---|---|
| L2 capacity | 54,254 tokens | 96,451 tokens |
| Cache hit | 56.8 - 57.6% | 72.7 - 73.4% |
| TTFT | 1,193 - 2,558 ms | 1,202 - 1,259 ms |
| Throughput | 80.0 - 105.1 tok/s | 127.8 tok/s |

Hit rate is stable across all four runs. TTFT is not: three pairs showed a large win, one **+6%**, so the range is quoted rather than a single run. The reproducible claim is that the INT8 tier is the predictable one.

## Verification

On one RTX A6000 (sm_86), against this change:

```
INT8 codec unit tests (no GPU)    25 passed
INT8 host pool tests (GPU)        36 passed
```

The pool tests run the JIT mover at `element_size = 1152`, pin the encoded arena with `cudaHostRegister`, exercise the all-layer D2H with a per-layer pointer table, and decode back through H2D.
