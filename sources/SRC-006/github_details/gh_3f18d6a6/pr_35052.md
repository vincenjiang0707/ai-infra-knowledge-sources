## 正文

## Summary

Fixes #34719. When a request that asks for token-ids logprobs (`token_ids_logprob`) shares a batch with a request that does not, the scheduler process dies with:

```
AttributeError: 'list' object has no attribute 'tolist'
```

One scoring client can take the whole server down.

## Root cause

`get_token_ids_logprobs_raw` / `get_top_logprobs_raw` (`python/sglang/srt/layers/logprob_processor.py`) build per-request lists whose entries are **heterogeneous**:

- a request that asked for the logprobs contributes a device **tensor** (`vals.append(row ...)`, e.g. L151/L172);
- a co-batched request that did **not** contributes a bare **`[]`** (L144-145, L159-165).

Both consumers in `batch_result_processor.py` — `move_logprobs_to_cpu` (prefill) and `_normalize_decode_outputs` (decode) — then call `.tolist()` unconditionally on every entry:

```python
logits_output.next_token_token_ids_logprobs_val = [
    v.tolist() for v in logits_output.next_token_token_ids_logprobs_val
]
```

The plain-`[]` entries have no `.tolist()`, so the whole batch crashes. When every request in the batch asks for the logprobs the entries are all tensors and the bug is hidden — it only surfaces on mixed batches. `next_token_top_logprobs_val` / `next_token_top_logprobs_idx` carry the identical latent pattern at both sites.

## Fix

Guard each entry with `torch.is_tensor` before converting, matching the style already used for `embeddings` a few lines above (`[tensor.tolist() for tensor in embeddings]`). Tensor entries convert exactly as before; plain-list entries pass through unchanged — no behavior change for the all-requesting case.

## Verification

Standalone reproduction of the comprehension confirms the old code raises `AttributeError: 'list' object has no attribute 'tolist'` on a mixed `[tensor, []]` list, while the guarded version returns `[[...], []]` and leaves the all-tensor case byte-identical.

### hackxixi · 2026-09-25

Confirming this on **v0.5.19** (`lmsysorg/sglang:v0.5.19-cu130`, release/v0.5.19 @ 0bcd822), and that this PR fixes it when backported.

**Setup:** Qwen3.6-35B-A3B AWQ (hybrid linear-attention + MoE), single GPU, overlap scheduler on, `--mamba-radix-cache-strategy extra_buffer --max-running-requests 16`. One client sends `/generate` with `return_logprob` + `token_ids_logprob` and `max_new_tokens=1` (label scoring). Other clients send ordinary `/v1/chat/completions` to the same server.

**Crash in production:** one normal chat request decoded in the same batch as the scoring requests:
```
File ".../scheduler_components/batch_result_processor.py", line 1053, in _normalize_decode_outputs
    v.tolist() for v in logits_output.next_token_token_ids_logprobs_val
AttributeError: 'list' object has no attribute 'tolist'
```
The scheduler SIGQUITs and the whole server goes down.

**Reproduced on the real model** with a small stdlib script that sends concurrent mixed traffic:

| image | result |
|---|---|
| stock v0.5.19 | crashes on the first scenario (long chat decode + concurrent `token_ids_logprob` requests) |
| stock v0.5.19 + `--disable-overlap-schedule` | **also crashes**, same error. Disabling overlap is not a workaround. |
| v0.5.19 + this PR's 6-line change | survives the whole matrix: 1,118 requests, 0 errors, 0 scheduler exceptions |

The matrix covered:
- decode-phase mix (long chat + scoring);
- multi-token `token_ids_logprob` decode + plain decode;
- prefill burst (scoring + plain arriving together);
- chat with `logprobs`/`top_logprobs` 1–5 + tool calls + scoring;
- ~12k-token chunked prefill with `logprob_start_len=0` + `token_ids_logprob` + `top_logprobs_num=2`, mixed with chat;
- a 1,000-request random soak.

**Scoring correctness:** label probabilities with the patch match the stock image within normal run-to-run noise. Max |Δp| ≈ 0.02–0.035, the same as two consecutive runs on the patched image (0.027). Argmax agreed on 10/10 prompts.

The PR applies cleanly in intent to v0.5.19: the same six sites, only the line numbers differ (495/1051 there). We are running the backport in production now. It would be great to get this merged, and ideally cherry-picked to the release branch. Any service that mixes label-scoring requests with normal chat can be taken down by a single chat request.
