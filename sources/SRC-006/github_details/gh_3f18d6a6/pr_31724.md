# [PR #31724] [Fix] Reject dynamic LoRA updates with tokenizer-worker-num > 1

## 正文

## What this fixes

1. With `--tokenizer-worker-num` greater than 1, each tokenizer worker process keeps its own LoRA adapter registry.
2. The dynamic endpoints `/load_lora_adapter`, `/unload_lora_adapter` and the from tensors variant only update the registry of whichever worker served the HTTP request.
3. So an adapter loaded at run time works only for requests that happen to route back to that worker, and retrying the load on another worker mints a new id and then trips the duplicate name check in the backend LoRA manager (`python/sglang/srt/lora/lora_manager.py`). The adapter appears to both not exist and already exist depending on routing.

Mitigates #31084.

## The fix

1. The three dynamic LoRA handlers in `tokenizer_control_mixin.py` now fail fast with a clear error when more than one tokenizer worker is running, before any state is changed.
2. Adapters preloaded at startup with `--lora-paths` are unaffected, because every worker seeds those at init.
3. The single worker path is unchanged.

I considered replicating the registry updates across workers over the existing pause and continue broadcast path in `multi_tokenizer_mixin.py`, but that path only confirms that the originating worker applied the change. It does not wait for the other workers, which is what LoRA state needs:

## Note on the recent dp attention change

Upstream #32708 now allows dynamic LoRA with dp attention, which relaxed the neighbouring check in these same handlers from `dp_size == 1` to `dp_size == 1 or enable_dp_attention`. That is a different axis to this change. Each tokenizer worker still keeps its own LoRA registry with no synchronization between them, so this guard is still needed, and it now also covers the dp attention setup that #32708 enabled. The new test `test_rejected_even_when_dp_attention_allows_dp_size_above_one` pins that interaction.

## Limitations

1. This makes the failure explicit. It does not add multi worker dynamic LoRA support.
2. The preload suggestion in the error message only helps adapters stored on disk. There is no startup path for adapters supplied as tensors in memory, so those callers must run with one tokenizer worker.
3. Anyone running more than one tokenizer worker today whose routing happens to pin them to a single worker will now get an explicit error where the call previously appeared to work. That is the intent, but it is a behavior change worth calling out.
4. Verified with CPU only unit tests against a mocked tokenizer manager. No multi worker server was launched end to end.
5. Unrelated to this fix, and not changed here: the `/load_lora_adapter_from_tensors` route in `http_server.py` has no `auth_level` decorator, while `/load_lora_adapter` and `/unload_lora_adapter` both require the admin token. On a server launched with only an admin API key that endpoint can be called with no credentials. This already exists on main and should be handled separately.

## Testing

1. New tests in `test/registered/unit/managers/test_tokenizer_control_mixin.py`, registered for CPU CI: all three dynamic operations are rejected with more than one worker, the backend is never contacted, the registry is untouched, and the single worker path still loads, loads from tensors, and unloads exactly as before.
2. Fail then pass: with the handler restored to main, the guard tests fail and the single worker tests pass. With the fix, all 8 pass.
3. `pre-commit run --files` on the changed files is clean.
4. AI assistance was used for this change.
