### Describe the bug


Start a server with the llama3 tool-call parser:

```bash
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.2-1B-Instruct \
  --tool-call-parser llama3 \
  --host 0.0.0.0 --port 30000
```

Send a `/v1/chat/completions` request that has `tools`.

```
input = '{}'                  -> content = ''           (the message is gone)
input = '{"a": 1} is a dict'  -> content = 'is a dict'  (the leading JSON is gone)
```

**Expected:** if the parser finds no tool call, it must not change the text. The bug shows without a GPU or a server. The bug is in the parser class.

### Reproduction

```python
# pip install "sglang[all]==0.5.17" — no GPU or server needed
from sglang.srt.entrypoints.openai.protocol import Function, Tool
from sglang.srt.function_call.function_call_parser import FunctionCallParser

tools = [Tool(type="function", function=Function(name="get_weather", parameters={}))]
parser = FunctionCallParser.ToolCallParserEnum["llama3"]()

result = parser.detect_and_parse('{"a": 1} is a dict', tools)
print(repr(result.normal_text), result.calls)  # 'is a dict' [] — {"a": 1} silently deleted
assert result.normal_text == '{"a": 1} is a dict', "leading JSON dropped from content"

```

## 评论 (2)

### CarrotSwordsman · 2026-08-27

Opened #36671 with a fix and regression tests.

Confirmed your analysis — the bug is entirely in `Llama32Detector.detect_and_parse`, no GPU or server involved. Root cause: when there is no `<|python_tag|>`, a leading `{` is treated as a tool-call candidate and the decoded objects are consumed via `safe_idx`. If `parse_base_json` then produces no calls (no `"name"` key, or a name that is not a registered tool, so it is skipped), the consumed text is never restored — hence `'{}'` -> `''` and `'{"a": 1} is a dict'` -> `'is a dict'`.

The fix returns the original text unchanged when the heuristic yields no calls, and leaves the `<|python_tag|>` path alone since there the model explicitly signalled a tool call.

### redd34 · 2026-09-26

This still reproduces on v0.5.20 and main `3ed56a3`. The streaming path is affected as well, and there it loses the whole message, not just the leading object. #35608 fixes the non-streaming path only:

```python
from sglang.srt.entrypoints.openai.protocol import Function, Tool
from sglang.srt.function_call.function_call_parser import FunctionCallParser

tools = [Tool(type="function", function=Function(name="get_weather", parameters={}))]
text = '{"a": 1} is a dict'
print("non-stream     :", repr(FunctionCallParser(tools, "llama3").parse_non_stream(text)[0]))
for label, chunks in (("stream, 1 chunk", [text]), ("stream, per char", list(text))):
    p, out = FunctionCallParser(tools, "llama3"), ""
    for c in chunks:
        out += p.parse_stream_chunk(c)[0]
    out += p.parse_stream_end()[0]  # end-of-stream flush, as serving_chat does on finish
    print(f"{label:15s}:", repr(out))
```

```
# v0.5.20 and main 3ed56a3
non-stream     : 'is a dict'
stream, 1 chunk: ''
stream, per char: ''

# main 3ed56a3 + #35608
non-stream     : '{"a": 1} is a dict'
stream, 1 chunk: ''
stream, per char: ''
```
