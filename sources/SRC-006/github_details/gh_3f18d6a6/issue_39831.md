# [Issue #39831] [Bug] GLM-5.3-Flash vision silently broken on main: pinned transformers==5.12.1 lacks glm5_next, AutoProcessor degrades to TokenizersBackend

## 正文

### Describe the bug

Serving `zai-org/GLM-5.3-Flash` from a recent `main` build starts successfully and `/model_info` reports `"has_image_understanding": true`, but **every image is silently reduced to exactly 3 tokens** (`<|begin_of_image|>` + 1×`<|image|>` + `<|end_of_image|>`), regardless of resolution or content. The `<|image|>` placeholder is never expanded into visual tokens and no `pixel_values` / `image_grid_thw` are produced, so the model answers from hallucination (e.g., describing a "person wearing a bright yellow jacket" when shown a solid red image). Text-only serving is unaffected. Reproduces via both `/v1/chat/completions` and the native `/generate`.

**Root cause (verified in-container):** the deployment pins `transformers==5.12.1` (per `python/pyproject.toml`), and the transformers **v5.12.1 release does not contain the `glm5_next` module** — it currently only exists on transformers `main`. On 5.12.1, `AutoProcessor.from_pretrained("zai-org/GLM-5.3-Flash", trust_remote_code=True)` **silently returns a `TokenizersBackend`** (a bare tokenizer) instead of raising. SGLang then starts with a tokenizer as the multimodal processor: image *loading* still runs (a corrupt base64 payload correctly returns HTTP 400), but nothing expands placeholders or encodes pixels.

This presumably affects everyone deploying GLM-5.3-Flash from main-derived builds right now. The day-0 `lmsysorg/sglang:glm-5.3-flash` image was built from the #36507 branch with a transformers main snapshot, which is why vision works there.

### Reproduction

Launch (H200 TP8/EP8; shown with secrets redacted):

```bash
python3 -m sglang.launch_server \
  --model-path zai-org/GLM-5.3-Flash --trust-remote-code \
  --tp-size 8 --ep-size 8 \
  --reasoning-parser glm45 --tool-call-parser glm47 \
  --dsa-prefill-backend tilelang --dsa-decode-backend tilelang \
  --kv-cache-dtype bfloat16 --moe-runner-backend deep_gemm \
  --speculative-algorithm EAGLE --speculative-num-steps 5 \
  --speculative-eagle-topk 1 --speculative-num-draft-tokens 6
```

1. **Server-level probe** — `POST /v1/chat/completions` with a `data:image/png;base64,...` image and `temperature: 0`:

   | Request | Expected | Actual |
   |---|---|---|
   | text only (`"Hi"`) | — | `prompt_tokens=13` |
   | + one 256×256 image | ~100+ more tokens | `prompt_tokens=16` (**+3 per image**) |
   | + three 256×256 images | — | `prompt_tokens=22` |

   Answers are hallucinated: solid-red → "Yellow", white square on black → "Triangle", and two *different* images (RGB vs RGBA) yield byte-identical responses.

2. **Framework-level root-cause check** (inside the server container):

   ```python
   import transformers  # 5.12.1
   from transformers import AutoProcessor
   from PIL import Image
   p = AutoProcessor.from_pretrained("zai-org/GLM-5.3-Flash", trust_remote_code=True)
   print(type(p).__name__)                    # TokenizersBackend  <- silent degradation
   out = p(images=[Image.new("RGB", (256, 256))], text="hi", return_tensors="pt")
   print(sorted(out.keys()))                  # ['attention_mask', 'input_ids']  (no pixel_values / image_grid_thw)
   ```

3. **Verified workaround**: install a transformers main snapshot (we used `5.18.0.dev0 @ 22e88feb58affcdd70514db734409c0af8cfa3ed`):

   ```dockerfile
   FROM lmsysorg/sglang:nightly-dev-cu13-20260916-c9a8fba9
   RUN /opt/sglang/bin/pip install --no-cache-dir \
       "transformers @ https://github.com/huggingface/transformers/archive/22e88feb58affcdd70514db734409c0af8cfa3ed.tar.gz"
   ```

   With it, `AutoProcessor` resolves to `Glm5NextProcessor`, a 256×256 image expands to **100 tokens** (grid `1×20×20`, with `pixel_values` / `image_grid_thw` / `mm_token_type_ids`), and the same probes answer correctly: solid-red → "Red", white square → "Square", RGBA red → "Salmon" (alpha composited correctly — thanks for #37320).

   Caveat we hit: transformers `main` currently requires `tokenizers>=0.23.1` while SGLang pins `tokenizers==0.22.2`; we overrode the pin locally and re-validated this workload end-to-end (tokenizer round-trip, chat template, glm45/glm47 parsers, EAGLE speculative serving), but mention it in case the pin is load-bearing elsewhere.

### Suggestions

None of these are blockers for us anymore, but they would save the next deployer a confusing afternoon:

1. Bump the `transformers` pin once a release includes `glm5_next`, or document the required snapshot for GLM-5.3-Flash serving.
2. **Fail loudly (or at least warn) at startup when a multimodal architecture resolves its processor to a bare `PreTrainedTokenizerBase`** — silent degradation turns a packaging/dependency gap into wrong answers at runtime.
3. Optionally, a tiny multimodal smoke test for GLM-5.3-Flash that asserts per-image token expansion (`prompt_tokens` grows by the grid size, not by 3).

Happy to validate any fix on our H200 setup, and thank you for the GLM-5.3-Flash support work in #36507 and the follow-ups — everything else in this build (DSA tilelang paths, deep_gemm KPool fusion, MTP, the glm45/glm47 parsers) has been solid.

### krisztian-gajdar · 2026-09-22

Confirming this on the released `sglang==0.5.20` wheel. Setup: torch 2.13.0+cu130, transformers 5.12.1, xgrammar 0.2.1, 8× H100 80GB at `--tensor-parallel-size 8`, `zai-org/GLM-5.3-Flash` at `eb9eb208eb0d988989d07a6a12d0fdeb5f52574a`.

- As reported, `AutoProcessor.from_pretrained(...)` returns `TokenizersBackend` with no image processor. Image requests to `/v1/chat/completions` are answered without the image: a solid red 448×448 PNG came back as "Navy".
- With `transformers==5.17.0` and `tokenizers==0.23.2` overlaid into the same environment, `AutoProcessor` returns `Glm5NextProcessor` with `Glm5NextImageProcessor`. Prompt tokens go from 23 for text only to 281 with a 448×448 image, and 89 with a 224×224 image. Solid red, green and blue squares are named correctly. An open question ("describe the colours in this image and where they are") on a left-red / right-blue image gets the right answer.

A caution about the user-side `pip install -U transformers` workaround suggested in #38821. On 0.5.20, the same overlay makes the Gemma 4 checkpoints we tried fail at startup: `google/gemma-4-E2B-it`, `google/gemma-4-26B-A4B-it` and `google/gemma-4-31B-it`.
