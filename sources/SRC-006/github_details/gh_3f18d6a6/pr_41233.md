# [PR #41233] [Fix] Scope the GLM47 tool grammar to requests that allow tool calls

The GLM47 grammar was installed for requests that disable tool calls, truncating output because grammar termination ends generation without consulting `ignore_eos`.

## Motivation

<!-- Describe the purpose and goals of this pull request. -->

With `--tool-call-parser glm47`, `OpenAIServingChat._process_messages` computed the constraint flag as

```python
glm_constraint = self.tool_call_parser == "glm47" and not any(
    tool.function.strict for tool in effective_tools
)
```

`not any(...)` over an **empty** tool list is `True`, so the GLM47 `full_assistant_ebnf` grammar was installed for every request that has no tools at all, and for requests that disable tool use with `tool_choice="none"`.

That grammar describes exactly one assistant turn (`root ::= assistant_turn`), so it reaches its terminal state as soon as the model finishes that turn. Grammar termination sets `FINISH_MATCHED_TOKEN` in `ScheduleBatch.update_finish_state()` (`managers/schedule_batch.py:1944`), and that branch does not consult `ignore_eos` — the token/EOS branch does (`_check_token_based_finish`, `managers/schedule_batch.py:1771`). A request-level sampling parameter is therefore silently ignored: a chat request with `ignore_eos=true` and `max_completion_tokens=2560` stops after a few dozen tokens.

Observed on a GLM-5.3 deployment served with `--tool-call-parser glm47`: `matched_stop` was 154827 (the model's `<|user|>` end-of-turn token) and the median completion length was 92 tokens against a configured 2560-5120. For a request with no tools the grammar has nothing to constrain — `functions=None` makes `tool_call_blocks ::= ""` — so the only thing it contributed there was the termination.

This is a regression introduced by #38890. Requests that use tools are not affected, and clients that leave `ignore_eos` at its default are not affected either, since the normal EOS path already stops at the same token; the bug is that an explicit request parameter is overridden.

## Modifications

<!-- Detail the changes made in this pull request. -->

Scope the grammar to requests that actually allow tool calls:

```python
glm_constraint = (
    self.tool_call_parser == "glm47"
    and bool(effective_tools)
    and request.tool_choice != "none"
    and not any(tool.function.strict for tool in effective_tools)
)
```

`bool(effective_tools) and request.tool_choice != "none"` is the same predicate the code a few lines below already uses to decide whether a request takes the tool-call path, so the grammar is now installed exactly when tool calls are possible. Non-strict tools with `tool_choice="auto"` or `"required"` are unchanged.

Deliberately **not** changed: `generate_glm_grammar`, `FunctionCallParser.get_structure_constraint`, and the grammar-termination handling in `update_finish_state()`. `TestGlm47FullAssistantGrammar.test_tool_choice_and_parallel_calls` pins "plain text is a complete assistant turn" via `matcher.is_completed()`, so that semantic is left as designed; making grammar termination respect `ignore_eos` would break it.

Two regression tests added to `test/registered/unit/entrypoints/openai/test_serving_chat.py`:

- `test_glm47_constraint_is_scoped_to_active_tools` — no tools, and tools with `tool_choice="none"`, must not construct a `FunctionCallParser` and must leave  `tool_call_constraint` unset;
- `test_glm47_constraint_remains_enabled_for_non_strict_auto_tools` — non-strict tools with   `tool_choice="auto"` still get the `full_assistant_ebnf` constraint.

## Accuracy Tests

<!-- If this pull request affects model outputs (e.g., changes to the kernel or model forward code), provide accuracy test results. -->

No change to model forward code or kernels. The affected requests are exactly those that already skip the tool-call path (`tools` is not passed to the chat template when `tool_choice="none"`, and there is nothing to pass when there are no tools), so their outputs are plain chat completions — the only difference is that the end-of-turn grammar no longer truncates them.

End-to-end check on the same worker with identical `input_ids` and DP rank:

| request | before | after |
|---|---|---|
| `/v1/chat/completions`, `ignore_eos=true`, `max_tokens=300` | 32 tokens, `finish=stop`, `matched_stop=154827` | 300 tokens, `finish=length` |
| `tools` + `tool_choice="auto"` | — | `finish_reason=tool_calls`, `get_weather({"city": "Beijing"})` |

## Speed Tests and Profiling

<!-- If this pull request impacts inference speed, provide benchmarking and profiling results. -->

No throughput change expected and none observed. The tool-calling path keeps the grammar, so tool-call latency is unaffected; for the requests that lose it, per-step grammar masking is removed rather than added.

As a signal that the intended generation length is restored, the same private long-context serving workload (GLM-5.3, GuideLLM, `ignore_eos=true`, `max_completion_tokens` 2560-5120 for coding and 1024-1536 for multi-turn) went from a median of 92 / 57 output tokens to 3837 / 1287, i.e. requests now reach their configured cap. This is a correctness signal, not a throughput benchmark.
