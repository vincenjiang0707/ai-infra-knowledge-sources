# [PR #31967] [Feature] KVarN: KV-cache compression for hybrid linear-attention models

## 正文

## Motivation

Hybrid linear-attention models (GDN/Mamba + full-attention) like Qwen 3.5 and Kimi-Linear have O(n) linear-attention layers but still retain O(n²) full-attention layers whose KV cache dominates GPU memory at long contexts. This limits the practical context length on commodity GPUs (e.g. 24 GB RTX 3090). KVarN compresses the full-attention KV cache to int4 (~8x reduction vs BF16), enabling long-context inference within bounded GPU memory.

## Modifications

### Core design

**Quantization pipeline**: Per-tile Hadamard rotation → Sinkhorn variance normalization → 4-bit packing with per-group scales. K and V are compressed independently (`k4v4` or `k4v2` presets, configurable group size). Dequant is fused into the attention kernel, avoiding a separate dequant pass.

**Attention backend** (`kvarn_backend.py`): A dedicated attention backend that manages a dual-pool architecture:
- Compressed int4 pool: the long-term cache, sized by the pool configurator at the compressed per-token cost.
- Tail fp16 pool: a small sliding window of recent tokens kept at full precision, flushed to int4 when the window slides.

**Triton kernels** (`kvarn_ops/`): Custom decode and sinkhorn kernels for the compressed attention path. The decode kernel fuses dequant with QK^T and attention.

**HiCache integration**: KVarN stores raw int4 tiles in the host memory pool (~2.7 KB/token) without dequant/requant, enabling transparent offloading of long conversation history. A new `_KVarNNopaStrategy` is registered in the hybrid cache assembler.

### Memory pool sizing

- `KVCacheConfigurator` and `DefaultPoolConfigurator` recognize the `kvarn_*` cache dtype and size the pool at the compressed per-token cost (`tile_bytes * num_heads / group`) with a 30% overhead for the tail pool and runtime allocations.
- Mamba cache sizing is capped for KVarN hybrid models to prevent the scheduler from over-allocating the linear-attention component.
- Transient prefill workspace is reserved in `_profile_available_bytes` (`chunk * hidden * dtype * 20`, target worker only) to prevent latent OOM during large-chunk prefill.
- `SGLANG_HICACHE_HOST_MEMORY_RESERVE_GB` env var (default 10.0) makes the HiCache host-memory reserve tunable. Previously hardcoded to 10 GB, which blocked HiCache on hosts with limited free RAM.

### Speculative decoding compatibility

- DFlash/EAGLE draft models can target KVarN-compressed models. The draft KV pool is sized at its real per-token cost via `compute_dflash_draft_kv_cell_size_per_token`, computed lazily in the pool configurator once the parallel state is available.
- `--speculative-draft-kv-cache-dtype` flag (default `"auto"`) allows explicit control over the draft model's KV cache dtype. Previously hardcoded; now configurable for cases where the draft uses a different dtype than the target (e.g. fp8 draft behind a KVarN target).
- DFlash draft HiCache is skipped (`maybe_register_hicache_draft` returns early) because the compact draft window never evicts, making a host pool pointless.
- Graph-capturable fused verify path for KVarN targets: the verify `ForwardBatch` is populated with correct `extend_seq_lens` / `prefix_lens` / `extend_lens`, and the target verify CUDA graph capture is skipped for KVarN (the fused verify path handles it).

## Accuracy Tests

KVarN preserves attention correctness through Hadamard + Sinkhorn preprocessing before 4-bit quantization. The `test_pool_configurator.py` unit tests verify pool sizing invariants (tokens * per_token_cost <= available_bytes). Standalone CPU unit tests for config, sinkhorn, store, dequant, flush, and hadamard modules are in a separate artifacts branch and will be submitted as a follow-up PR after converting them to the `register_cpu_ci` pattern.

## Speed Tests and Profiling

### Single GPU — RTX 3090 (24 GB)

**Qwen 3.5 9B** (KVarN k4v4_g128, no speculative decoding):
- 817K token KV pool, ~70 tok/s decode (CUDA graphs active)
- HiCache 4 GB host pool with `SGLANG_HICACHE_HOST_MEMORY_RESERVE_GB=2`
- 15-turn agentic multi-turn test (context growing 0–57K tokens): passes, server stable

**Qwen 3.5 9B** (KVarN + DFlash speculative decoding):
- Accept length 3–7.6, 105–208 tok/s decode with CUDA graphs active
- Note: DFlash decode is faster, but e2e agentic latency is higher because per-turn draft prefill + verify overhead scales with context length. DFlash is not recommended for short-turn agentic workloads; KVarN-only is the better deployment for that use case.

### Multi-GPU — 2× RTX 3090 (48 GB)

**Qwen 3.5 27B** (KVarN k4v4_g128, TP=2): deployed, serving real agentic load.
**Qwen 3.5 35B** (KVarN k4v4_g128, TP=2): deployed, serving real agentic load.

Both run with KVarN-only (no DFlash) + HiCache. The int4 compression makes these models fit in 2×24 GB with long context, which is not feasible with BF16 or FP8 KV cache.

## Rebased onto latest `main`

The branch has been rebased onto the current `main` head. Three compatibility issues surfaced during the rebase and are fixed in new commits on top of the original feature commit:

1. **`server_args` mutation during pool sizing** — The KVarN mamba-cap override was mutating `server_args.max_mamba_cache_size` directly, which is read-only after resolution on recent `main`. Routed the override through the config-override mechanism (`get_context().override`) and read the resolved value via `get_schedule()`.

2. **Missing `pool_label` kwarg in `KVarNHostKVCache`** — Upstream added a `pool_label` parameter to `HostKVCache.__init__` for HiCache host-pool labeling. `KVarNHostKVCache` didn't accept or forward it, causing a `TypeError` during HiCache construction.

3. **Missing `layer_num` / `target_layer_num` in `KVarNHostKVCache`** — Upstream moved the `layer_num` and `target_layer_num` assignments into `MHATokenToKVPoolHost.get_size_per_token()`, but KVarN's override of that method no longer set them, so the base `HostKVCache.__init__` crashed with `AttributeError` when it read them for its allocation log line. Fixed by setting both from the device pool's layer count before calling `super().__init__()`.

### End-to-end verification

The rebased branch was built and tested end-to-end with a hybrid linear-attention model (Qwen 3.5 architecture, FP8 weights, KVarN `k4v2_g128`):
- Server starts cleanly with HiCache enabled (`--enable-hierarchical-cache --hicache-size 4 --hicache-write-policy write_back`).
- CUDA decode graphs are captured and active during decode (`cuda graph: True` in every decode batch).
- KVarN pools are allocated correctly (compressed int4 pool + tail fp16 pool).
- Output quality verified with reasoning and code-generation prompts — results are coherent and correct.
- Decode throughput is ~60 tok/s (single request, CUDA graphs active).
