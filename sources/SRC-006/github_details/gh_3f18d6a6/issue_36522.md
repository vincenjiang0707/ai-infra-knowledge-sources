## 正文

## Overview

This RFC is based on SGLang v0.5.18.

This document proposes a minimal plugin API for KV cache compression across cache types such as MHA, MLA, and SSM, together with the SGLang framework changes needed to support it. Compression can lower inference costs by allowing more caches to be stored for longer periods, thereby increasing cache hit rates and reducing redundant prefill computation.

The API is intentionally minimal and delegates most responsibilities to codec implementations, simplifying HiCache maintenance and integration of newly developed codecs.

```text
┌────────┐      ╔═══════════════╗      ┌────────┐      ┌────────┐
│   L1   │ ◄──► ║ Compression / ║ ◄──► │   L2   │ ◄──► │   L3   │
│        │      ║ Decompression ║      │        │      │        │
└────────┘      ╚═══════════════╝      └────────┘      └────────┘

┌────────┐      ┌────────┐      ╔═══════════════╗      ┌────────┐
│   L1   │ ◄──► │   L2   │ ◄──► ║ Compression / ║ ◄──► │   L3   │
│        │      │        │      ║ Decompression ║      │        │
└────────┘      └────────┘      ╚═══════════════╝      └────────┘
```
In this document:
- **L1** is the device cache pool, usually in GPU memory.
- **L2** is the host cache pool in CPU DRAM, typically pinned.
- **L3** is external storage accessed through a connector such as NIXL.
- **KV cache** is used broadly for inference cache state (MHA/MLA/SSM/...) unless stated otherwise.
- **KV codec** is a compression/decompression plugin implemented as a subclass of the proposed `HostKVCache` interface.

## Summary

- SGLang adds a small set of capabilities to facilitate implementation of codecs
  - optional sequence-position metadata on all host-pool transfers,
  - a streaming multi-layer load API for codecs that operate on layer groups,
  - explicit construction context and cache metadata,
  - per-page compression-state tracking across L1, L2, and L3.
- Codecs are implemented as `HostKVCache` plugins and loaded through a factory and registry. Each codec:
  - implements support for selected pool kinds (MHA, MLA, SSM, DSA, ...) and rejects incompatible ones during init,
  - handles its own low-level requirements (such as cross-rank cache gathering and scattering, CPU or GPU execution, async compression, ...),
  - manages its representation and storage constraints (such as fixed- or variable-size payloads, L3 serialization, page boundaries, ...).

In short, SGLang provides common transfer hooks, metadata propagation, synchronization guarantees, and plugin lifecycle management; each codec is responsible for correctly and efficiently encoding and restoring the cache types it supports.

### Codec implementation considerations

The following properties determine a codec's integration requirements:

| Property | Integration impact |
| -------- | ------------------ |
| **Fidelity** | Repeated lossy encode/decode cycles can accumulate error. |
| **Scheduling and execution** | Deferred encoders need queues and temporary capacity. CPU work competes for host resources; GPU work competes with model execution. |
| **Encoded size** | Variable-size output requires a finite bound, encoded-length metadata, and an L2 allocation strategy as described in [Section 5](#5-support-variable-size-encoded-pages-optional). |
| **Cache compatibility** | A codec must validate the cache kind, layout, shape, data type, and page size it supports. |
| **Dependency scope** | Dependencies across heads, layers, or token pages may require collectives, grouped-transfer APIs, or different L3 object boundaries. Position-dependent transforms also need token positions. |
| **Codec state and hardware** | Codebooks, matrices, and scratch buffers consume memory; learned artifacts may require calibration, and hardware-specific codecs must validate device support. |
| **Token coverage** | Methods that discard or reorder tokens change the logical cache shape and are outside this API. |

#### Lossy recompression and error accumulation

Lossy error accumulates only when reconstructed KV data is encoded again:

- **L1–L2:** In normal HiCache operation, an offloaded entry retains its L2 `host_value` when restored to L1. Later offloads cover only newly generated tokens, so ordinary reuse does not re-encode old entries while that L2 copy remains available.
- **L2–L3:** If an L3 object is decoded into L2, removed from L3, and later written from L2 to L3 again, the L2–L3 codec re-encodes reconstructed data. Repeated cycles can therefore accumulate error.

Decode-worker request retraction is an exception to the normal L1–L2 path. With `--disaggregation-decode-retraction-backup=host_pool`, `UnifiedRadixCache.retraction_backup` copies the request's active cached prefix to a new, temporary L2 allocation. Restoration frees that allocation; it is not added to the radix tree or L3. If the prefix contains KV data restored from an earlier backup, each subsequent retraction may add another lossy encode/decode cycle. Compression saves spill space here but provides no caching benefit.

SGLang selects `host_pool` automatically only when decode-side radix caching and KV offload are disabled, and rejects it with decode-side KV offload. A codec that cannot tolerate retraction recompression must therefore use one of these options:

1. Use `cpu_tensor`, which bypasses the host-pool codec.
2. Allocate uncompressed retraction storage. This choice must reach `HostKVCache.alloc()`; a transfer-time flag arrives after storage allocation. A separate uncompressed retraction pool is equivalent.
3. After integrating retraction with decode-side KV offload, pin and reuse the prefix's existing `host_value` entries and back up only the new tail.

Until an option is implemented, the codec must reject `--disaggregation-decode-retraction-backup=host_pool`.

#### Deferred compression

Some codecs are too slow or resource-intensive to encode on the L1-to-L2 transfer path. A codec may instead copy the uncompressed page to L2, queue a background encode, and keep the original authoritative until encoding succeeds. It then atomically publishes the encoded representation and releases the original. A concurrent load uses the original while encoding is pending and the encoded representation after publication.

Unless encoding is in-place, this path needs enough peak memory for the uncompressed page, encoded output, and scratch space. The codec may own CPU workers or CUDA streams, but latency-critical load and decode work should take priority over background encoding.

#### GPU decompression and stream synchronization

GPU decompression should be enqueued from `load_to_device_per_layer()` on the current CUDA stream. In HiCache this is `L2TransferEngine.host_to_device_stream`; the engine records the layer's completion event on that stream after the method returns, so the event covers both the copy and decompression.

A codec that uses a private stream must make the load stream wait for its work before returning. It must also preserve temporary-buffer lifetimes with `record_stream()` or equivalent synchronization. CUDA transfer overlap normally requires pinned host memory, and staging and scratch buffers must be included in the codec's memory budget. GPU decompression may contend with model kernels for compute or memory bandwidth.

#### Cross-rank codec dependencies

A codec whose compression blocks cross tensor- or pipeline-parallel ownership boundaries must perform the required collectives using the appropriate SGLang process groups and validate the supported topology. Every participating rank must invoke collectives in the same order. A codec must reject a dependency that crosses a pipeline stage unless its transfer schedule explicitly coordinates those stages.

#### Uncompressed windows and prefix caching

A codec may keep the most recent tokens uncompressed to improve quality, but this policy is relative to each request. The same shared prefix page can be recent for one request and old for another, while this API records only one representation per page. Supporting such windows therefore requires additional versioning, duplication, or a conservative uncompressed policy. Without that support, request-relative windows are out of scope; codecs with a stable per-page representation remain compatible with prefix caching.

## Codec plugin API

Compression codecs are implemented as `HostKVCache` subclasses, and support selected KV cache pool kinds (MHA, MLA, SSM, DSA, ...) and roles (`lm` or `draft` model). The design follows a _factory_ pattern, similar to that already used for L3 through `StorageBackendFactory`. A registry maps short codec names to Python classes, implementations are loaded lazily, and external codecs may be loaded dynamically.

Importantly, compression is optional and does not change the current default behavior.

### Configuration

A single server argument, `--hicache-kvcache-codec`, defines the codec configuration. It accepts either an inline JSON string or an `@file` reference.

The configuration has two levels:

1. **Model role:** `lm` for the target model and `draft` for the MTP or speculative-decoding model.
2. **Pool kind:** `mha`, `mla`, `mamba`, `dsa`, etc.

Each pool maps to a codec specification:

```json
{
  "lm": {
    "mha": {
      "codec": "kvtc"
    },
    "mla": {
      "codec": "kvtc-mla",
      "config": "@/etc/kvtc/mla.json"
    },
    "mamba": {
      "codec": "dynamic",
      "module_path": "acme.codecs",
      "class_name": "AcmeMambaCodec"
    }
  },
  "draft": {
    "mha": {
      "codec": "kvtc"
    }
  }
}
```

 * A specification may reference a registered codec name or use `dynamic` to import an arbitrary module and class. A `dynamic` specification must supply both `module_path` and `class_name`, mirroring the required fields of `StorageBackendFactory._create_dynamic_backend`. The optional `config` field is passed directly to the codec.
 * Omitted roles and pool kinds do not involve compresssion.
 * A codec should validate the requested configuration (especially for the draft model, which might have different layer counts, head dimensions, layouts, or data types).
 * The list of pool kinds above is illustrative, not exhaustive: the valid kinds are defined by the host-pool creation sites routed through the dispatch helper and grow with model families (for example, a `dsv4_c4` kind for the DeepSeek V4 compressed-region sidecar pool). Implementations should validate against an explicit allow-list so that unknown kinds fail fast during initialization.
 * A (role, pool kind) key addresses a pool family, not an individual creation site: sites that build more than one pool of the same kind must define which of them are eligible for codec dispatch. Codec support for sliding-window (SWA) sidecar pools is optional — an implementation may keep SWA pools on their built-in host pools (for example when their transfers are not token-aligned with the full-attention anchor's position metadata) while the codec applies to the anchor pool.

### Registry and loading

The proposed registry mirrors `StorageBackendFactory`:

```python
HostKVCacheFactory.register(name, module_path, class_name)
```

`HostKVCacheFactory.resolve()` should:

1. Find the registered module and class, or read them from a `dynamic` specification.
2. Import the module lazily with `importlib`.
3. Retrieve the requested class.
4. Verify that it is a subclass of `HostKVCache`.

Invalid codec names, import failures, and incompatible classes should fail during initialization with an error that identifies the model role and pool kind.

### Host-pool construction

All host-pool creation sites should use one shared dispatch helper. The helper receives the device pool, pool kind, model role, server configuration, the built-in host-pool constructor, and pool-specific constructor arguments.

```python
def create_host_kv_pool(
    device_pool,
    kind,
    server_args,
    *pool_args,
    role="lm",
    builtin_ctor,
    **pool_kwargs,
) -> HostKVCache:
    spec = (
        codec_map(server_args.hicache_kvcache_codec)
        .get(role, {})
        .get(kind)
    )

    if spec is None:
        return builtin_ctor(
            device_pool,
            *pool_args,
            **pool_kwargs,
        )

    codec_cls = HostKVCacheFactory.resolve(
        spec,
        role=role,
        kind=kind,
    )

    return codec_cls(
        device_pool,
        *pool_args,
        codec_config=spec.get("config"),
        **pool_kwargs,
    )
```

The target-model path passes `role="lm"`, while the draft-model path passes `role="draft"`.

Built-in host pools do not share one constructor signature. For example:

* `MambaPoolHost` does not take `page_size`;
* `DSAIndexerPoolHost` requires an `anchor_host`;
* the MHA implementation may depend on the concrete device-pool type.

Each call site should therefore continue preparing the arguments it already uses and pass them through the shared helper. The helper centralizes codec selection but does not hide pool-specific construction requirements. For the same reason there is no central built-in pool dispatch: each call site passes the built-in constructor it would otherwise have invoked as `builtin_ctor`, so the helper centralizes codec selection, not built-in pool selection.

A codec is a normal `HostKVCache` subclass. It may inherit from the matching built-in host pool to reuse allocation, indexing, and page I/O, overriding only the compression and decompression behavior.

### `HostKVCache` interface

The proposed codec-facing interface is shown below. It retains the four existing `HostKVCache` operations and adds two capabilities needed by some codecs:

* optional sequence positions on device transfers; and
* a streaming multi-layer load, with a default implementation in terms of the existing per-layer load.

```python
class HostKVCache(abc.ABC):
    # Opt in to receiving the positions keyword from the transfer engine.
    wants_positions: ClassVar[bool] = False

    @abc.abstractmethod
    def load_to_device_per_layer(
        self,
        device_pool,
        host_indices,
        device_indices,
        layer_id,
        io_backend,
        positions: Optional[torch.Tensor] = None,
        *,
        is_draft: bool = False,
    ) -> None:
        ...

    @abc.abstractmethod
    def backup_from_device_all_layer(
        self,
        device_pool,
        host_indices,
        device_indices,
        io_backend,
        positions: Optional[torch.Tensor] = None,
    ) -> None:
        ...

    def load_to_device_layers_streaming(
        self,
        device_pool,
        host_indices,
        device_indices,
        layer_ids: Iterable[int],
        io_backend,
        positions: Optional[torch.Tensor] = None,
        *,
        is_draft: bool = False,
    ) -> Iterator[None]:
        load_kwargs = {"is_draft": is_draft}
        if self.wants_positions:
            load_kwargs["positions"] = positions

        for layer_id in layer_ids:
            self.load_to_device_per_layer(
                device_pool=device_pool,
                host_indices=host_indices,
                device_indices=device_indices,
                layer_id=layer_id,
                io_backend=io_backend,
                **load_kwargs,
            )
            yield

    @abc.abstractmethod
    def get_data_page(
        self,
        index,
        flat: bool = True,
    ) -> torch.Tensor:
        ...

    @abc.abstractmethod
    def set_from_flat_data_page(
        self,
        index: int,
        data_page: torch.Tensor,
    ) -> None:
        ...
```

A codec encodes data in `backup_from_device_all_layer()`, restores it through one of the load methods, and implements whole-page L3 serialization through `get_data_page()` and `set_from_flat_data_page()`. A codec that consumes positions sets `wants_positions = True`. A codec with cross-layer dependencies overrides the streaming method; other codecs inherit the per-layer wrapper.

The `is_draft` keyword represents an existing branch-specific load argument. Branches with other per-layer load keywords must expose and forward the same keywords from the streaming method.

The factory validates that a plugin is a `HostKVCache` subclass. The codec itself remains responsible for validating compatibility with the concrete pool, including its kind, layout, shape, page size, and data type.


## Required framework changes

### 1. Propagate sequence positions through host-pool transfers

Some codecs achieve higher compression rates by removing positional embeddings before compression and restoring them during decompression. These codecs must know the position ID associated with every transferred token. The optional `positions` argument in the interface above carries this metadata in one of two forms:
- **One-dimensional contiguous positions.** Standard RoPE models commonly assign positions `0, 1, 2, ...` along the sequence. HiRadix can reconstruct these positions from the location of a node in the radix tree. `positions` is a one-dimensional integer tensor with one entry per transferred token.
- **Non-contiguous or multidimensional positions.** Models using schemes such as M-RoPE may associate each token with several position IDs or with positions that cannot be inferred from sequence length. For these models, HiCache must preserve the actual position IDs produced by the model. `positions` should allow additional dimensions.

In both cases, dimension 0 of `positions` is the token dimension: one entry per transferred token, aligned element-wise with `host_indices` and `device_indices`. Multidimensional schemes use shape `(num_tokens, ...)`. The complete transfer signatures are defined in the `HostKVCache` interface above.

Host pools advertise position consumption through a `wants_positions` class attribute (default `False`), and the transfer engine passes `positions` only to pools that opt in; pools that do not use positions never receive the argument, so their signatures stay unchanged. Controllers aggregate the flag across all attached pools (anchor, sidecars, and the draft pool), so the radix-tree layer can check a single controller-level `wants_positions` to decide whether to reconstruct positions at all.

#### 1.1 Derive contiguous one-dimensional positions

For standard contiguous position IDs, HiRadix can derive the first position represented by a node from its radix-tree depth:

```text
seq_offset(node) = seq_offset(node.parent) + len(node.parent.key)
```

This value can be memoized on the node. When `_split_node` replaces `child` with `new_node -> child`, the cached offsets must be updated:

```python
old_offset = getattr(child, "_seq_offset", None)

new_node._seq_offset = old_offset
child._seq_offset = (
    None if old_offset is None
    else old_offset + split_len
)
```

A contiguous transfer beginning at `node` can then construct:

```python
positions = torch.arange(
    seq_offset(node),
    seq_offset(node) + num_tokens,
    dtype=torch.int64,
)
```

This avoids storing position metadata for every cached token while still providing codecs with the positions needed to reverse and reapply one-dimensional RoPE.

#### 1.2 Preserve non-contiguous or multidimensional positions (optional)

Radix-tree depth is insufficient for models whose position IDs are multidimensional, discontinuous, or otherwise not determined only by token order. For these models, HiCache must capture the actual position IDs used during model execution and attach them to the corresponding cache entries. The precise tensor shape depends on the model's positional scheme, but one dimension must correspond to the transferred tokens. **These positions must be stored or reconstructed together with the cache metadata**.

Implementation of this feature might be postponed, and left unsupported for codecs which require those positions.

#### 1.3 Carry positions through cache operations

The preceding subsections describe how position IDs are obtained. The codec, however, consumes them later, when the host pool executes a cache write or load. The transfer between these two points is represented by a `CacheOperation` and may be queued, merged, or reordered. Position IDs must therefore be part of the operation payload, alongside the indices of the tokens they describe:

```python
class CacheOperation:
    def __init__(
        self,
        host_indices: torch.Tensor,
        device_indices: torch.Tensor,
        node_id: int,
        priority: Optional[int] = None,
        positions: Optional[torch.Tensor] = None,
    ):
        self.host_indices = host_indices
        self.device_indices = device_indices
        self.positions = positions
        ...
```

The invariant throughout the transfer pipeline is that `positions[i]` describes the same token as `host_indices[i]` and `device_indices[i]`. This has three consequences:

* Merging operations is valid only if every operation has positions or none does. When positions are present, concatenate them in operation order along dimension 0, which is always the token dimension.
* Any permutation of the cache indices must also be applied to dimension 0 of `positions`. For example, sorting `host_indices` in the `direct` backend must reorder `device_indices` and `positions` by the same permutation.
* Positions used by an asynchronous transfer need the same stream-lifetime handling (`record_stream()`) as its index tensors.

The shared `CacheOperation` in `sglang/srt/managers/cache_controller.py` is used by both `HiCacheController` and `HybridCacheController`. Its constructor and `merge_ops`, the shared `start_writing` and `start_loading` methods, and both controllers' write, load, and index-moving paths must all preserve `positions`. Older SGLang branches that define a separate hybrid `CacheOperation` must update both definitions.

The decode-worker retraction path needs the same treatment. With `--disaggregation-decode-retraction-backup=host_pool`, `UnifiedRadixCache.retraction_backup` and `retraction_restore` construct operations directly and bypass the normal queues, so they must attach positions themselves. Each transfer contains a contiguous request prefix in sequence order, padded at the end to a page boundary; one-dimensional positions can therefore be reconstructed as `torch.arange(len(device_indices))` for both backup and restore. The call sites must also mark the operation as a retraction. If a codec uses that marker to bypass compression, the marker must reach `HostKVCache.alloc()` before host slots are allocated.

### 2. Support layer-group codecs

Some codecs share one encoded representation across several model layers. [KVTC](https://arxiv.org/abs/2511.01815), for example, applies its transform to features concatenated across layers, while [KVCodec](https://arxiv.org/abs/2602.09725) maps groups of three layers to video frame color channels. Restoring one layer can therefore require decoding data shared with other layers.

The existing `load_to_device_per_layer` interface is unsuitable for that shared work. A codec must either repeat the group decode or retain hidden staging state between independent calls. `load_to_device_layers_streaming` instead gives the codec one stateful operation for the requested layer sequence, while preserving HiCache's per-layer synchronization.

This change applies only to L2-to-L1 restoration. L1-to-L2 backup already exposes all layers through `backup_from_device_all_layer`; the separate L3 serialization API is unchanged.

The method receives the mapped layer IDs that would otherwise be passed to `load_to_device_per_layer` and returns a generator. It must yield once for each ID, in the same order, immediately after that layer's transfer has been enqueued. The yield is a readiness signal and carries no value. A grouped codec may decode a group when the generator first enters it, enqueue its layers as they are requested, and yield after each one. This lets model execution overlap with loading later groups. An implementation that loads every layer before its first yield is valid, but forgoes that overlap.

The default implementation calls `load_to_device_per_layer` and yields after each call, so existing pools keep their current behavior. This includes the Ascend all-layer fast paths: MHA uses the `page_first_direct` layout and MLA uses `page_first_kv_split`. Their per-layer methods perform the transfer on layer 0 and treat later calls as no-ops. Overrides must also preserve the interface's position handling and forward branch-specific load arguments such as `is_draft`.

#### 2.1 `L2TransferEngine` integration

`L2TransferEngine` schedules L1<->L2 cache transfers. For a host-to-device load, its `submit_host_to_device` method walks the model layers, asks each participating host pool to enqueue its part of the transfer, and signals when each layer is ready. Grouped loading must therefore be coordinated here rather than in the cache controllers, which only submit transfer requests.

A request may include several transfers: one for the target model's main KV pool, optional transfers for a speculative draft model, and auxiliary transfers for models that use more than one cache type, such as attention KV and Mamba state. If every pool uses the default streaming method, the existing per-layer loop runs unchanged. If any pool overrides it, the transfer engine coordinates all transfers as follows:

1. Build a plan of `(submission_layer_id, mapped_layer_id)` pairs for each transfer. Apply its `layer_mapper`, omit mappings that return `None`, and respect the layer count of an unmapped, non-primary pool.
2. Create one generator per transfer, passing it the mapped layer IDs from its plan. Wrap pools without the streaming method in an equivalent per-layer generator.
3. Process the submission-wide layer sequence in order. For each layer, advance every generator whose plan contains that layer, then invoke `on_layer_done`.
4. Reject generators that yield fewer or more times than their plan requires, and close every generator when scheduling ends or fails.

Scheduling runs on the engine's existing host-to-device stream. For each submission layer, the engine advances every pool loader assigned to that layer before calling `on_layer_done`, which records the layer's completion event. Model execution therefore waits until all required target, draft, and auxiliary pool data has been enqueued. A draft pool's `layer_mapper` assigns it only the layers it contains, so shorter draft models require no special handling.

No controller changes are needed because both controllers already use `submit_host_to_device`. For a model with multiple cache types, `HybridCacheController` creates a separate `L2Transfer` for each participating `HostPoolGroup` entry, so every active auxiliary pool receives its own generator and layer mapping. Retraction restore, which synchronizes immediately and has no `on_layer_done` callback, continues to work unchanged.

HiSparse's `_preload_to_device_buffer` and `naive_load_topk` are separate per-layer call sites and remain outside this change. They need adaptation only if HiSparse must support grouped codecs directly.

### 3. Provide codec construction context

A codec may need TP or PP ranks and cache metadata to select and validate rank-specific parameters. The framework should provide this context without adding many loosely related arguments to every `HostKVCache` constructor.

The initial integration requires the following changes:

* Add a `codec_config` argument when constructing a codec-backed host pool. The value may be an inline JSON object or a path to a JSON file.
* Pass the active `device_pool` to the codec, as existing host-pool constructors already do.
* Ensure that `device_pool` exposes the metadata needed by the codec, including cache shape, dtype, local layer range, and the local head or state fragments owned by the current rank.

The codec can obtain the current TP and PP ranks through SGLang's existing distributed helpers:

```python
get_tensor_model_parallel_rank()
get_pipeline_model_parallel_rank()
```

The `HostKVCache` base interface does not require a substantial redesign. The main framework change is in the codec construction path: it must pass `codec_config` and provide a `device_pool` that exposes all required local cache metadata. If some ownership information is not currently available from `device_pool`, that metadata must be added explicitly.

### 4. Coordinate compression across cache tiers

Compression may be applied at either transfer boundary:

```text
L1 device cache <-> L2 host cache <-> L3 storage
                 ^                 ^
              L1-L2 codec       L2-L3 codec
```

Both codecs may use heuristics. For example, a codec may compress only sufficiently long sequences, selected pool kinds, pages for which compression is expected to be beneficial. Configuration therefore defines **when a codec may compress**, but HiCache must record the actual decision separately for every page. In particular, no page should be compressed twice.

#### 4.1 Transfer rules

On an L1-to-L2 transfer, the L1–L2 codec either compresses the page or explicitly declines to do so. HiCache retains exactly one authoritative L2 representation: the encoded payload after successful compression, or the uncompressed KV data if compression was declined. The recorded page state identifies which representation is present.

An uncompressed page may not fit in an L2 slot sized for encoded pages. A codec may therefore decline compression only if its L2 pool can store a full-size page; otherwise the transfer must fail.

On an L2-to-L3 transfer:

* If the page is `uncompressed`, the L2–L3 codec may compress it according to its own policy.
* If the page is already compressed, it is transferred to L3 verbatim as an opaque blob.
* If the L2–L3 codec declines to compress an uncompressed page, the original L2 page is stored verbatim.

The reverse path follows the policy configured in the codec: a compressed object might be decoded either during L3-to-L2 transfer or L2-to-L1 transfer.

#### 4.2 Compression metadata

Compression state must be tracked per page, not only per host pool or request, because heuristic decisions may differ between pages in the same cache.

Each L3 object must preserve enough metadata to determine how it should be restored. At minimum, this includes:
* whether the page is compressed;
* the codec identifier and format version.

The framework must not infer compression state from payload size or configuration. A codec may be configured but choose not to compress a particular page.

This metadata may be stored in a small object header or passed through an explicit page descriptor. If `get_data_page()` and `set_from_flat_data_page()` continue to exchange only tensors, the returned blob must be self-describing. Otherwise, these methods must be extended to pass the compression descriptor together with the payload.

State changes must become visible only after the corresponding asynchronous encode, transfer, and write operation has completed successfully.

#### 4.3 L3 object boundaries and codec requirements

Each L3 key identifies one object, which HiCache reads or writes as a whole. A codec must therefore be able to encode and decode each stored object independently. The contents of that object depend on the storage layout:

* **Default layout.** HiCache stores one complete token page as one L3 object. The page contains `page_size` consecutive token slots and all tensors stored by that host pool for those tokens. Partial-page and multi-page encoding are outside this API.
* **Head-split layout.** With `should_split_heads`, HiCache stores separate K and V objects for groups of attention heads, allowing deployments with different tensor-parallel (TP) sizes to share L3 data. Each head group must be independently decodable, so a codec that encodes across head groups is incompatible with this layout. Uncompressed pages continue to use HiCache's existing head-splitting path.

**Position-dependent codecs.** Positions must be available whenever the codec requires them, during encoding, decoding, or both. If the decoder cannot reconstruct them, they must be preserved with the cached representation. Copying an already encoded page between L2 and L3 does not itself require positions, but decoding that page later may require them.

HiCache must reject an incompatible layout, missing position metadata, or an unsupported L3 representation before starting the transfer.

### 5. Support variable-size encoded pages (optional)

Some codecs, particularly entropy coders, produce pages whose encoded byte length depends on their contents. This section describes the framework support needed to store and transfer those pages without padding every page to its worst-case size. Fixed-rate codecs do not need this support.

#### 5.1 L1–L2 allocation and transfer

**Current behavior.** HiCache treats L2 as a fixed-slot pool. At startup it derives token capacity from `size_per_token`; before an L1-to-L2 transfer, `HostKVCache.alloc()` reserves enough token slots for the unencoded input.

**L2 storage options.** The encoded size of a page is known only after encoding. The codec must therefore provide a finite `max_encoded_page_bytes`, including metadata, alignment, and any fallback representation. HiCache can use one of two storage strategies:

* **Variable-size L2 allocations.** Reserve up to `max_encoded_page_bytes` before encoding, then retain only the actual encoded length. This improves L2 utilization but introduces fragmentation, which the allocator must control through size classes, coalescing, compaction, or another suitable mechanism.
* **Fixed-size L2 slots.** Allocate every slot using `max_encoded_page_bytes`. This preserves the current fixed-slot model but wastes the unused portion of each slot. HiCache must still record the actual encoded length so that L3 stores and transfers only the encoded payload, realizing the full space savings there.

#### 5.2 L2–L3 object I/O

**Current behavior.** HiCache's L2–L3 path assumes that every page has a fixed byte size. It allocates L2 storage before reading from L3, and zero-copy backends derive I/O addresses and sizes from the fixed L2 layout.

**Required changes.** L2–L3 operations must carry the actual encoded length separately from the buffer capacity:

* **L2→L3.** Store only the actual encoded payload, whether its length comes from the L2 page descriptor or an L2–L3 codec. Do not store unused bytes from a fixed-size L2 slot.
* **L3→L2 with fixed-size slots.** Allocate `max_encoded_page_bytes`, read no more than that capacity, and record the actual returned length.
* **L3→L2 with variable-size allocations.** Either obtain the encoded length from L3 metadata before allocating, or reserve `max_encoded_page_bytes` and release the unused capacity after the read.

The implementation must reject objects larger than `max_encoded_page_bytes`. A backend may add physical padding for alignment, but the page's logical length remains the actual encoded length.
