# [Issue #41236] [Bug] streaming silently loses up to 5 tokens of text when detokenizer state is evicted mid-request

source: https://github.com/sgl-project/sglang/issues/41236
state: open | updated: 2026-09-25T09:05:32Z
labels: 

## 正文

setup: with more than SGLANG_DETOKENIZER_MAX_STATES (default 65536) concurrent states, LimitedCapacityDict evicts an in-flight request's DecodeStatus (detokenizer_manager.py:153). this is the scenario from #2812 that the env var and the KeyError message at detokenizer_manager.py:378 exist for, and the re-init path at detokenizer_manager.py:311 exists to survive it without crashing.

the bug: the re-init uses recv_obj.read_offsets[i] as the count of already-committed tokens inside this chunk's decode_ids. but the scheduler sends read_offset as an absolute offset into the request's cumulative surrogate+decode id list: init_incremental_detokenize returns read_offset - surr_offset, a constant 5 (INIT_INCREMENTAL_DETOKENIZATION_OFFSET, schedule_batch.py:156) that never advances, while decode_ids is sliced to only the ids since the last send (output_streamer.py:479). on every chunk after the first, the constant 5 points at ids that are not in the chunk.

effect: after eviction re-init, while the accumulated decode_ids list has 5 or fewer entries, surr_ids == read_ids (detokenizer_manager.py:327-334), so new_text computes as "" and the text of up to the first 5 tokens generated after the eviction is never emitted in any streaming delta. if the request finishes inside that window the final chunk emits "" as well (detokenizer_manager.py:412-420 derives the tail from the same empty new_text), so the text is lost from the assembled stream entirely, not deferred. the first chunk is unaffected only because it carries the 5 prompt-tail tokens inside decode_ids, which is exactly what the constant 5 is meant to skip (first_iter branch of init_incremental_detokenize).

fix direction: send the committed-prefix count relative to the chunk, max(0, read_offset - send_decode_id_offset) at output_streamer.py:481, computed before send_decode_id_offset advances. first chunk value is unchanged (5), later chunks send 0, and the detokenizer needs no change because it is already faithful to what the field claims to be. will follow with a pr carrying a red-green test that drives the real scheduler accumulator and the real detokenizer with an injected eviction.

separately noticed while tracing this: req.decoded_text is initialized "" at schedule_batch.py:1137 and never written anywhere, so the stop-string fallback `stop_str in self.decoded_text` at schedule_batch.py:1821 never fires. not part of this fix; flagging it in case maintainers want it split out.
