# [PR #38480] [HiCache]: Fix host lock ownership across radix splits

source: https://github.com/sgl-project/sglang/pull/38480
state: open | updated: 2026-09-25T07:20:57Z

## 正文

## Motivation

HiCache can corrupt a value being written to L3 storage when a radix-tree node is split while its write-back SET is still in flight.
The SET reads directly from host KV-cache blocks. A split creates a new prefix node for the shared tokens, but that fragment does not inherit the parent's full host lock. Duplicate-host reclamation may therefore free and reuse the prefix blocks before the storage backend has finished reading them, this causes **wrong data to be written to storage**. The backend behaves correctly: it stores exactly what is in those buffers when its SET runs. The stale write is caused by SGLang changing ownership of the buffers too early.

## Modifications

* Propagate a full host lock from the original node to the prefix fragment created by a split.
* When the asynchronous SET finishes, release the lock across every fragment created after the SET began, stopping at the recorded pre-split parent. 
* Require the acquisition result when releasing a host lock. Without its pre-split boundary, a parameterless release could unlock only the original child and permanently leak the copied prefix lock.
* Apply the same ownership rule to the Python and Rust unified radix-tree implementations.

This keeps every zero-copy SET source block owned by the SET until the backend call has returned, even if the radix node is split in the meantime.


## Accuracy Tests

I tested this with both unit tests (in this PR) an [end2end reproducer (not in this PR)](https://github.com/lluki/sglang/blob/751ee8dd1656f365ba555267fd706dc054ef3d97/scripts/repro_hicache_nixl_stale_set_frontend.py). 

The e2e verifier runs SGLang with hicache nixl backend and slows down the `batch_set_*` artificially to reliably trigger the bug:
* Send an 832-token victim prompt whose deterministic answer is ZEBRA4821.
* Send a 3500-token unrelated prompt. This evicts the victim to host and starts its delayed POSIX SET.
* Send a prompt that shares the first 704 victim tokens and then diverges.
* This splits the host-backed node while its SET is in flight.
* Send a 3000-token unrelated prompt to create host pressure. On buggy code, the split prefix is reclaimed and its host blocks are reused.
* Wait for the SET, flush the memory tiers, and send the original victim completion request again so it must be loaded from POSIX storage.

The second request reports a 768-token storage hit, proving that it exercised L3. On buggy upstream code its answer changes from ZEBRA4821 to repeated Answer: tokens. This is visible entirely through the completion API.

I ran this validation and testsuite with both python and rust cores.

## Implementation changed quite a bit:
  - Full host locks now use segment UUID receipts, following the existing SWA locking model.
  - A radix split copies the Full host lock count and UUID boundary to the new prefix.
  - Unlocking walks only to the receipt’s UUID boundary, correctly handling nested locks.
  - Python and Rust receipt conversions preserve the Full host UUID.
