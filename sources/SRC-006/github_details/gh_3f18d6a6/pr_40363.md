# [PR #40363] [HiCache][perf] Queue and batch write-through backups off the request-finish path

source: https://github.com/sgl-project/sglang/pull/40363
state: open | updated: 2026-09-25T07:05:13Z
labels: hicache, unified-radix-cache

## 正文

## Motivation

With `--enable-hierarchical-cache` (write_through) the unified radix cache backs up every new tree node to host. After #39050 the D2H submits are merged per step, but the per-node bookkeeping that precedes a submit still runs inside `cache_finished_req`, on the scheduler thread, at the moment the node is inserted: `build_backup_spec` (SWA/Mamba transfer lists, `torch.cat`/`clone`), host pool `alloc` for KV + side pools (with SWA host eviction when that pool is full), `resolve_host_transfers`, `commit_backup`, `inc_lock_ref`, and the ack bookkeeping. On Inkling-Small-NVFP4 that is ~0.2 ms per node, and most of it is fixed per-call torch-op and Python overhead on small tensors, not per-token work.

The workload that exposes it finishes many requests in the same scheduler step (128 lanes, four output lengths). A 64-request finish wave is tens of ms of CPU inside `process_batch_result`, longer than the ~11 ms the GPU needs for the next step, so the launch of the next batch waits and the GPU idles. At higher load (192 lanes) the scheduler is close to CPU-bound and every extra microsecond of bookkeeping shows up in throughput.

Profile on 4x GB300, Inkling-Small-NVFP4, mxfp8 KV, TP=4, 128 lanes x 16 turns, torch profiler with Python stacks over 400 steps, main at c3aa09b0db:

| 400 scheduler steps | L1 | L2 (main) |
|---|---|---|
| compute stream busy | 75.7% | 68.6% |
| GPU idle | 1,105 ms | 1,606 ms |
| radix insert wall / in GPU-idle | 213 / 185 ms | 326 / 278 ms |
| `_execute_and_commit_kv_backup` (192 nodes) | - | 106 ms, 85% in GPU-idle |
| forward launch in GPU-idle (launch waited for the CPU) | 74 ms | 261 ms |

The backup stream itself is idle almost all the time (in a 192-lane trace it overlaps 2% of the compute-stream idle time), so the cost is the scheduler-thread CPU, not the copies.

## Modifications

1. **Queue write-through backups** instead of executing them at insert time.
   - `BackupKV` actions from the insert walk go through `_queue_write_through_backup`: each node of the chain is locked (`inc_lock_ref`, the same write-through lock the immediate path takes after the backup) and appended to `queued_backups` in chain order, ancestors first. Nothing else happens on the request-finish path.
   - `flush_pending_backups()` (already called at the end of every `process_batch_result` and from `check_hicache_events`) drains up to `SGLANG_HICACHE_BACKUP_NODES_PER_STEP` nodes, oldest first.
   - `writing_check(write_back=True)` drains the queue before its blocking wait, so every queued node is acked.
2. **Batch the drained nodes.** A drain builds each node's spec in order, then backs the batch up with one host allocation per pool (KV, SWA, Mamba, sidecars) and one `CacheOperation` whose ack lists every node. The allocation is split back per node and committed node by node, exactly as the immediate path commits.
   - If a node's covered set (the node plus the SWA nodes its transfer carries) intersects the batch, i.e. an ancestor already in the batch sits in its sliding window, the batch is committed first and the node's spec is rebuilt. It then sees that ancestor backed up, as the node-by-node path would, so no SWA slot is backed up twice.
   - If the merged allocation fails, the batch falls back to the node-by-node path, which handles host eviction and failures exactly as before.
   - `HybridCacheController.write` takes an optional `node_ids` for the multi-node ack.
3. **The queue stays opt-in**: default `SGLANG_HICACHE_BACKUP_NODES_PER_STEP=0` keeps the insert-time path byte for byte (`_execute_and_commit_kv_backup` still serves it and the write-back demote path). 16 was measured on Inkling/GB300, where 8 backlogged; other values are untested. Flipping the default is left to a follow-up because the queued path differs from the insert-time path in two Mamba cases (covered by `test_mamba_path_state_cap.py`, which assumes insert-time backups):
   - The queue-time lock keeps a queued node's Mamba state safe from the per-path cap even when its first backup attempt fails. The insert-time path leaves such a node unlocked, so the cap can tombstone it before the retry.
   - A backup deferred to the flush carries a Mamba value that the same insert re-stamped. The insert-time path runs the walk backup before the commit hooks, so it excludes that value.

What changes while a node waits in the queue: it is locked, so it cannot be evicted, and it is not yet `backuped`, so a later chain that reaches it sees it queued and skips it. If a queued node is split by a later match, the new parent is not backed up until a chain passes through it; the request that caused the split holds the path lock until it finishes and inserts, which emits that chain. If that request aborts instead, the child's host copy is unreachable until host eviction reclaims it. This is a transient host-space leak, not a correctness issue.

Not changed: what is backed up (`hicache_backup_bytes_total` is identical in every arm: 91.55 GiB at 128 lanes and 137.32 GiB at 192, SWA and Mamba pools included), the ack protocol, the tree core, and the Rust core.

## Accuracy Tests

- `test/registered/unit/mem_cache/test_unified_radix_cache_unittest.py::TestUnifiedRadixCacheQueuedWriteThrough` (8 cases):
  - queue -> flush -> ack lifecycle with lock and pending-mark checks;
  - per-step cap;
  - a queued node split before its backup;
  - host alloc failure releases the lock;
  - the default (cap 0) keeps the insert-time backup;
  - disjoint nodes share one host allocation;
  - a failed merged allocation falls back to node by node;
  - a child in the SWA window of a batched parent commits after it.
  The last three were negative-controlled: without the batching they fail, and without the overlap check the SWA case fails.
- `test/registered/unit/mem_cache/` (python core): the same failures as the base commit, none new.
- The queued, batched path issues the same transfers as the immediate one; see the backup bytes above.

## Speed Tests and Profiling

4x GB300, Inkling-Small-NVFP4, TP=4, 16 turns, `--kv-tokens 2097152 --mamba-slots 1024` (192 lanes: `3145728 / 1536`, since 2M retracts there). Throughput loss is relative to L1 (HiCache off) in the same session, with interleaved rounds (n = rounds per cell). Single-run noise is about +-0.5 pt.

Upstream main 752801e4d1 + this PR. With batching, MXFP8 lands within 0.3-0.5 pt of BF16. The only MXFP8-specific cost left on the backup path is the scale-plane submit, about 0.1% of wall time. The main column has only two rounds, so read the 192-lane MXFP8 row as no change:

| lanes | KV dtype | L2 loss, main | L2 loss, this PR with `SGLANG_HICACHE_BACKUP_NODES_PER_STEP=16` |
|---|---|---|---|
| 128 | BF16 | 2.1% (n=2) | **0.85%** (n=5) |
| 128 | MXFP8 | 2.5% (n=2) | **1.2%** (n=5) |
| 192 | BF16 | 2.6% (n=2) | **1.9%** (n=5) |
| 192 | MXFP8 | 1.9% (n=2) | **2.4%** (n=5) |

Main 16e353d93e, MXFP8, which isolates the two parts:

| lanes | main | queue only (cap 16) | queue + batching |
|---|---|---|---|
| 128 | 1.46% (n=2) | 1.12% (n=2) | **0.39%** (n=4) |
| 192 | 3.0% (n=4) | 3.4% (n=2) | **2.1%** (n=6) |

On 4x B200 (x86, slow gloo), 192 lanes, MXFP8: main 2.2% -> queue only 1.8% -> queue + batching 1.3%.

The queue alone mostly moves work around; the gain comes from batching, which turns per-node host allocs, side-pool resolves, SWA evictions and ack ops into one per batch (about 13 nodes per batch at 192 lanes). With the Rust tree core (`SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND=rust`) the 192-lane MXFP8 loss drops further to 1.7% (n=2), with L1 itself 4% faster. The pre-#39050 commit ffe98a4279 measured 5.5% at 128 lanes on the same setup.
