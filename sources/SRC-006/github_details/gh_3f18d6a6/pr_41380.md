# [PR #41380] [Fix] Stop PD-decode queue_time from counting decode time before a retraction

## 正文

## Motivation

Follow-up to #39312 (cc @surajm20061998 @sufeng-buaa).

Since #39312, `queue_time` adds `forward entry - wait_queue_entry_time` at the first forward after each retraction. That relies on the retraction re-stamping `wait_queue_entry_time`, which happens in NULL mode through `set_wait_queue_entry_time()`. On a **PD decode** worker, though, a retracted request goes `_add_request_to_queue(is_retracted=True)` → `retracted_queue` → `resume_retracted_reqs()` → `waiting_queue`, and the scheduler only calls `set_retract_time()`. Nothing on that path re-stamps the wait. At re-admission the accumulator therefore subtracts the **first** wait stamp and counts all the decoding before the retraction as queueing.

Example: a request waits 0.1 s, decodes for 10 s, is retracted, and is re-admitted 2 s later. `meta_info["queue_time"]` reports 12.1 s instead of 2.1 s, and so does the per-request time-stats log line. The Prometheus queue-time histogram only samples the first wait, so it is not affected.

## Modifications

`python/sglang/srt/managers/scheduler.py`, in the DECODE branch of `_add_request_to_queue`: for a retracted request, call `set_wait_queue_entry_time()` instead of `set_retract_time()`. For a request that has queued before, that method performs `set_retract_time(ts)` (including the trace event) and then re-stamps the wait. Queue time after a retraction then runs from retraction to re-admission, the same as NULL mode.

Rebootstrap (`hold_rebootstrap`) is unchanged: it stamps the wait after the re-transfer (`decode.py`), as `test_decode_rebootstrap_counts_both_waits` pins.

The alternative is to stamp in `resume_retracted_reqs()` instead, so that only the `waiting_queue` time counts and the time held in `retracted_queue` does not. Happy to switch if you prefer that definition.
