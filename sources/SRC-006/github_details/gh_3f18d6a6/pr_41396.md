## 正文

## Motivation

Fixes #13214. `Qwen3NextForCausalLM.load_weights()` matched shard names with a plain substring check (`if weight_name not in name`). Checkpoints that ship an already-fused `gate_up_proj` (common for AWQ-quantized Qwen3-Next MoE checkpoints, where gate/up are merged before quantization) contain `up_proj` as a substring of `gate_up_proj`, so the stacked-params pass rewrote `...mlp.shared_expert.gate_up_proj.weight` into `...mlp.shared_expert.gate_gate_up_proj.weight`, producing the `KeyError` in the issue. Community analysis on the issue (ErenAta16, Prudctual) identified the matching logic itself as the real fix.

## Modifications

- Added `_match_weight_name()` in `python/sglang/srt/models/qwen3_next.py`: anchors weight-name matching to `.`-separated path segments via `(^|\.)<name>(\.|$)`, so a pre-fused `gate_up_proj` no longer matches the `up_proj`/`gate_proj` shard entries (trailing-dot mapping names like `experts.3.gate_proj.` and `in_proj_qkv.` are handled by stripping the trailing dot before anchoring).
- Swapped the two `weight_name not in name` checks in `load_weights()` (stacked-params loop and expert-params loop) to the anchored matcher. All other load logic, including the `replaced_name not in params_dict` guards, is untouched.
- Added `test/srt/models/test_qwen3_next_weight_mapping.py` with 5 unit tests pinning the behavior (follows the existing `test_mamba2.py` precedent in the same directory).

## Accuracy Tests

Not applicable - this change only affects checkpoint weight-name matching at load time and produces byte-identical load behavior for all previously-loading checkpoints (verified by an old-vs-new match-decision differential over representative checkpoint names x every mapping entry; only the double-fuse case changes).
