# [Issue #41260] Does a keyless upstream have to go without model discovery?

source: https://github.com/sgl-project/sglang/issues/41260
state: open | updated: 2026-09-26T16:34:34Z
labels: 

## 正文

The model gateway in SGLang treats an external worker as an OpenAI compatible endpoint it can register models for, and sgl-model-gateway/src/core/steps/worker/external/discover_models.rs is where that registration starts. Discovery runs only when the worker was given an api_key: with none set, or with an empty string, the step logs that no API key was provided and that it is using wildcard mode, which accepts any model, then returns without calling /v1/models at all. create_workers.rs turns that into a single wildcard worker with an empty model list and records that the user's auth is forwarded. So an upstream with no key is reachable, but its own model list is never read and the caller's Authorization header is what travels with each request. The path is real rather than theoretical, since a routing fix for external OpenAI workers landed in #16633 in January.

BlockRun has a free /v1/models and no key anywhere, because every call settles on its own in USDC over x402 and there is nothing to send in an Authorization header. The single base URL covers chat, image, video, music, speech and sound effects, so the models a caller would want are exactly the ones that skipped call would have returned. https://blockrun.ai

So I wanted to ask whether discovery is skipped only because a key is the usual sign that the endpoint is worth reading, or whether an upstream that publishes its list for free should still get the fetch. Happy to send the exact model list or help test either path, and just as happy to hear that wildcard mode is the intended answer for an upstream with no key to give.

### Edwardssss · 2026-09-26

Thanks for digging into this. `fetch_models` already takes an `Option` and only attaches `Authorization` when a key is present; the early return was the only thing standing in the way. PR: #41361 

It attempts discovery for keyless workers, and keeps the wildcard worker as the fallback when `/v1/models` is missing, errors, or returns an empty list — so nothing that works today breaks. Keyed behavior and caller-auth forwarding are unchanged.

One thing worth checking on your side: a keyless upstream that *does* publish a list now registers per model, so an unlisted model name is no longer accepted. If your endpoint's list is partial, say so and I will adjust.
