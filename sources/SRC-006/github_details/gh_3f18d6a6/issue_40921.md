# [Issue #40921] [Bug] trtllm_mha for both prefill and decode on H200 (SM90) is accepted in v0.5.20 and returns wrong completions (gpt-oss-120b); v0.5.17 refused it; either half alone is correct

state: open | updated: 2026-09-23T19:59:15Z
labels: 

## 正文

### Summary

On **H200 (SM90)** with the `lmsysorg/sglang` **v0.5.20** image, launching gpt-oss-120b with `--attention-backend trtllm_mha` (i.e. trtllm_mha for **both** prefill and decode) **starts normally, reports `attention_backend='trtllm_mha'` in `/server_info`, serves at normal speed — and returns wrong completions**. The same command on the **v0.5.17** image refuses to start with `ValueError: TRTLLM MHA backend for prefill is only supported on Blackwell GPUs (SM100). Please use a different prefill backend.` So a configuration that used to be rejected became silently incorrect.

Each half alone is correct on v0.5.20: `--prefill-attention-backend trtllm_mha --decode-attention-backend fa3` and `--prefill-attention-backend fa3 --decode-attention-backend trtllm_mha` both pass our correctness probes; only the **both-trtllm_mha** combination fails (whether spelled as the single flag or explicitly).

### Environment

- Image `lmsysorg/sglang@sha256:06e4f2ed21afde4ff513cda65070124e727ba23ccaeff7712b8c40e1097d611f` (= tag `v0.5.20` / `latest` on 2026-09-23); inside: sglang 0.5.20, flashinfer 0.6.18 (python/cubin/jit-cache), torch 2.13.0+cu130, flash-attn-4 4.0.0b19
- Contrast image `lmsysorg/sglang@sha256:16aba8925507e631e1dc1e23d95d026533602591775f6a8db68b74ee99746155` (= tag `v0.5.17`): flashinfer 0.6.15.post1, torch 2.11.0+cu130
- 1 × NVIDIA H200 (143771 MiB), Kubernetes pod, cold caches (`HF_HOME` / `DG_CACHE_DIR` on emptyDir)
- Model: `openai/gpt-oss-120b`, snapshot `b5c939de8f754692c1647ca79fbf85e8c1e70f8a`; no speculative decoding, default KV dtype and memory settings

### Reproduction

```bash
python3 -m sglang.launch_server --model-path /models/hub/models--openai--gpt-oss-120b/snapshots/b5c939de8f754692c1647ca79fbf85e8c1e70f8a \
  --host 0.0.0.0 --port 30000 --attention-backend trtllm_mha
```
Then, with any OpenAI-compatible client at temperature 0 (`/v1/completions`):

| prompt (paraphrased) | v0.5.20, `--attention-backend trtllm_mha` | default (fa3) |
|---|---|---|
| "What is the capital of France?" | completion stops after **4 tokens, no "Paris"** | correct |
| "List the first five prime numbers." | runs to the 768-token budget, **never produces `2, 3, 5, 7, 11` in order** | correct |
| a short multiplication | correct | correct |

Observed on **5 of 6 fresh boots** of the failing configuration (identical failing prompts each time; on one boot a second pass recovered one of the two). The default server passed all three prompts on **4/4 boots, 8/8 passes**.

### Which half

| flags (v0.5.20) | `/server_info` prefill / decode | our 3-prompt probe |
|---|---|---|
| `--attention-backend trtllm_mha` | trtllm_mha / trtllm_mha | **fails** (4/4 boots) |
| `--prefill-attention-backend trtllm_mha --decode-attention-backend trtllm_mha` | trtllm_mha / trtllm_mha | **fails** |
| `--prefill-attention-backend trtllm_mha --decode-attention-backend fa3` | trtllm_mha / fa3 | passes (2/2) |
| `--prefill-attention-backend fa3 --decode-attention-backend trtllm_mha` | fa3 / trtllm_mha | passes (2/2) |
| default | fa3 / fa3 | passes (8/8) |

### What the server says at startup

Nothing: no warning, no fallback line, no SM90/SM100 message in the boot log of the failing configuration; `server_args` echoes `attention_backend='trtllm_mha'`; CUDA-graph capture logs the same `backend=breakable` (prefill) / `backend=full` (decode) strings as the fa3 server.

### Why report it

A configuration that fails loudly is safe; this one is accepted, fast (a 30-s probe on one boot gave ~+6 % tok/s over fa3 at concurrency 16) and wrong. Any selection process that checks "boots + serves + throughput" will grade it healthy. Either the SM90 guard for the trtllm_mha prefill+decode combination that v0.5.17 had should come back, or the combination needs a fix — and a correctness check for (prefill, decode) backend pairs newly accepted on a GPU generation would catch this class.

### Limitations of this report

One model (gpt-oss-120b: mxfp4 experts, GQA 64/8, head_dim 64, hybrid SWA), one GPU type, one image step in which three components moved together (sglang 0.5.17→0.5.20, flashinfer 0.6.15.post1→0.6.18, torch 2.11→2.13) — we cannot say which change opened the path or broke the numerics. We have not read the v0.5.20 source for the guard; the tables above are observations. n = 6 boots for the failing spelling, 1 boot each for the explicit half-splits.
