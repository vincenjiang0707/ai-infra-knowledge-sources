## Describe the bug

On the MLX backend (`SGLANG_USE_MLX=1`), serving `mlx-community/Hunyuan-7B-Instruct-4bit` (and any Hunyuan model whose HF config ships an `auto_map` to `modeling_hunyuan.py`) crashes during scheduler initialization, **after** the MLX model itself has loaded successfully through `mlx_lm.load`.

This is separate from the `dp_size` startup crash fixed in #32520 — it only surfaces once that one is applied.

## Reproduction

```bash
SGLANG_USE_MLX=1 python -m sglang.launch_server \
  --model-path mlx-community/Hunyuan-7B-Instruct-4bit \
  --trust-remote-code --tp-size 1 --disable-radix-cache --disable-cuda-graph \
  --mem-fraction-static 0.7 --max-running-requests 1 --context-length 2048
```

## Root cause (initial analysis)

On the MLX path the model is loaded via `mlx_lm.load()`, so `sglang/srt/models/*` and the HF `auto_map` are never needed for inference. But `kv_cache_builder.build_kv_cache` still calls `get_resolved_model_impl(model_config)` → `get_model_architecture` → `resolve_transformers_arch`, which tries to import the `auto_map` module and fails because `modeling_hunyuan.py` does not expose the class name SGLang expects (`HunyuanModel`).

This looks analogous to the `init_attention_backends()` no-op override added to the MLX stub in #30050 to skip a CUDA-only path: the MLX path likely needs to short-circuit the transformers-architecture resolution in `kv_cache_builder` as well (the MLX backend does not route inference through `sglang/srt/models`).

Models without a remote `auto_map` (e.g. the qwen2_moe / qwen3_moe repos used by the existing MLX correctness tests) do not hit this, which is why it stayed hidden.
