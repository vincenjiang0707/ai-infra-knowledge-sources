## 正文

## Motivation

[FlashInfer #5021](https://github.com/flashinfer-ai/flashinfer/pull/5021), released in 0.7.0, adds indexed, floor-aligned checkpoints to CuTe DSL KDA prefill. SGLang needs the state at the last complete chunk boundary for radix prefix caching (for example, token 128 of a 130-token extend).

## Modifications

- Add an opt-in KDA prefill adapter for BF16, 128-dimensional safe-gate KDA on SM100/SM103: `--linear-attn-prefill-backend flashinfer`.
- Map FlashInfer's packed checkpoints to SGLang's radix-cache track rows, including FP32 state pools and padded gate/beta buffers. Keep beta as logits for this path.
- Route unsupported shapes, speculative draft extend, and CUDA graph capture through the existing Triton kernel.

The FlashInfer package and Docker version pins stay unchanged in this PR. A separate dependency PR must provide FlashInfer 0.7.0 before this path can run in standard images.

## Accuracy Tests

On the 8xGB300 devbox, with FlashInfer 0.7.0 installed on both ranks:

| Test | Result |
| --- | --- |
| New FlashInfer KDA prefill tests (BF16/FP32 states, indexed and padded state pools, strided K3 beta, 130→128 checkpoint, full attention backend path) | 5 passed |
| Existing FlashInfer KDA decode/verify tests | 11 passed |
| CuTe DSL KDA prefill and FlashInfer GDN checkpoint smoke tests | 2 passed |

The GB300 tests pass, including a strided-beta case that fails if the FlashInfer adapter falls back to Triton. Format, lint, registry, and bare-pytest checks pass (the latter on the devbox with Python 3.12). A TP8/DCP8 Kimi K3 dummy-weight request completed with FlashInfer KDA prefill active. Real-weight output parity remains to be checked.

## Speed Tests and Profiling

GB300 adapter-level prefill microbenchmark, after warmup, without checkpoint tracking:

| Batch × tokens/request | Triton | FlashInfer | Speedup |
| --- | ---: | ---: | ---: |
| 4 × 128 | 481 µs | 359 µs | 1.34× |
| 16 × 128 | 552 µs | 227 µs | 2.43× |
| 64 × 256 | 620 µs | 218 µs | 2.84× |

Across nine shapes (batch 4/16/64 × 64/128/256 tokens), measured speedup was 1.14–2.84×. This measures the adapter call, including its tensor conversions; it excludes projection, convolution, scheduler work, and checkpoint-copy overhead.

For the requested 95% prefix hit shape (batch 1, 131,072 input tokens, 124,518 cached, 6,554 new; K3 TP8-like H12/D128, FP32 state), three independent synthetic adapter runs gave:

| Checkpoint tracking | Triton | FlashInfer | Triton / FlashInfer |
| --- | ---: | ---: | ---: |
| Off | 760–851 µs | 553–598 µs | 1.34–1.42× |
| On | 655–764 µs | 711–848 µs | 0.90–0.93× |

Each figure is the median of 12 calls after warmup. The tracked path includes indexed checkpoint allocation and copy. These are per-layer synthetic timings, not full K3 request latency.

### Full Kimi K3, matched dummy weights

On two nodes / 8×GB300, both arms used the same local Kimi K3 NVFP4 config with `--load-format dummy --speculative-draft-load-format dummy`; only `--linear-attn-prefill-backend` changed. Workload: batch 1, 131,072 input, 1,024 output, requested 95% prefix hit, TP8/DCP8/DP1/EP1, FP8 E4M3 KV, FP32 SSM, DSPARK (block 7, 1 step, topk 1, 8 draft tokens), simulated acceptance length 5.5, spec ReplaySSM with `extra_buffer`. The cache actually reused 124,416 tokens and extended 6,656 (94.92% hit) on both arms.

| Prefill backend | Unprofiled latency | TTFT | Output throughput | Acceptance length |
| --- | ---: | ---: | ---: | ---: |
| Triton | 9.328 s | 6.845 s | 412.30 tok/s | 5.52 |
| FlashInfer | 9.342 s | 6.844 s | 409.81 tok/s | 5.53 |

Separate CPU+GPU EXTEND and DECODE traces were captured for 16 steps on all 8 TP ranks. In the EXTEND traces, median summed KDA kernel GPU time across ranks was 29.07 ms for Triton and 15.09 ms for FlashInfer (1.93×), across 69 KDA calls per rank. FlashInfer traces contain its CuTe DSL prefill kernels and no Triton KDA compute kernels. The summed kernel durations are not request wall time; communication, MLA, and MoE dominate this TP8/DCP8 request. One unprofiled request per arm showed no measurable end-to-end gain. Dummy weights validate routing and allow a matched performance baseline, but do not establish output parity with real model weights.
