# [Simulator] Support session radix cache and fix multi-turn simulation fidelity

<!-- Working draft for the PR body. Not intended to be committed. -->

Alternative titles, if a narrower or broader framing reads better:

- `[Simulator] Simulate session radix cache under faithful multi-turn workloads`
- `[Simulator] Make multi-turn and session radix cache simulation trustworthy`

## Summary

Previously the simulator could not run multi-turn workloads at all -- the benchmark adapter accepted only `--backend sglang` while multi-turn replay is gated to chat backends -- so `--enable-session-radix-cache`, which only has an effect under multi-turn traffic, could not be simulated.

Now with this PR the simulator supports `--enable-session-radix-cache` on multi-turn chat workloads with one radix-native session per conversation, reports KV eviction, fixes three defects that let host wall-clock leak into the simulated clock, and has been validated against a real GPU server on the same workload.

## Results

Llama-3.1-8B-Instruct, B200, 3 trials each, `SILICON` predictor, `page_size 64`. Every difference is quoted against the pooled spread across repeat runs, because a gap smaller than a run's own variance says nothing. `total_output_tokens` is identical for both, confirming both ran the same work.

### Cache Simulation Results

Same 32 x 10-turn workload in both; only the KV pool changes. The working set is ~93k tokens.

| KV pool | oversubscription | evicted tokens | duration vs real | cache vs real |

Cache hit volume agrees to ~3.3%. Everything time-related is uniformly optimistic: duration 9-12% short, throughput 10-13% high, per-request latency 9-25% fast. The simulator is consistently faster than the real server rather than biased in different directions on different metrics.

`concurrency` is not an independent measurement -- it is `sum(e2e_latencies) / duration`, so it is implied by the two rows above it rather than explaining them. Its small spread is an artifact of being a ratio of covarying quantities.

The simulator is bit-identical across repeat runs in both configurations (0.00% spread on cache totals, against 0.06-0.22% for the real server). Per-request cache agreement against the real server is ~41% at 1.4x, so totals agree to 3.3% while *which* requests hit differs substantially -- unexplained.

### Known limitations

- **Cache thrashing.** Past ~2x KV oversubscription the numbers above no longer hold: duration drops to -34.5% at 2.8x (329k tokens evicted) and -34.3% at 5.7x (408k evicted). The error switches on between 1.4x and 2.8x and then saturates rather than scaling with eviction volume, and the real server destabilises at the same threshold (repeat-run spread 14.6% -> 31.7%), so the -34% figures sit against a very noisy reference. Cache volume stays within ~5% throughout; only latency collapses. Those two duration figures predate the warm-up fix below, so they understate the gap by roughly 5 points. Mechanism unidentified.
- Per-request latency is 9-23% optimistic even in the healthy regime; not usable for per-request or tail analysis.
- Validated on one model, one accelerator, `--request-rate inf`. No MoE, no long context beyond ~2.6k tokens, no paced arrivals.
- The simulator can only model `disable_overlap_schedule=True`; `compat.py` force-overrides it. Real deployments default to overlap enabled, so these numbers describe a configuration production does not run.

## Reproducing

`sim_config.json`:

```json
{
  "platform": {
    "accelerator": {"name": "b200_sxm", "hbm_capacity_gb": 180},
    "disk_read_bandwidth_gb": 8, "disk_write_bandwidth_gb": 8,
    "memory_read_bandwidth_gb": 64, "memory_write_bandwidth_gb": 64,
    "num_device_per_node": 8
  },
  "predictor": {"name": "aiconfigurator", "database_mode": "SILICON"},
  "scheduler": {
    "tp_size": 1, "ep_size": 1, "dp_size": 1,
    "backend_name": "sglang", "backend_version": "0.5.10",
    "quantization": "bf16"
  }
}
```

Use `SILICON`, not `SOL`. `SOL` is Speed Of Light -- theoretical peak, a lower bound on latency by construction. It is also not the code's default; a config setting it is overriding `time_predictor/aiconfigurator.py`.

Simulator:

```bash
export CUDA_VISIBLE_DEVICES="" SGLANG_USE_CPU_ENGINE=1
export SGLANG_SIMULATOR_OUTPUT_MODE=OFFLINE SGLANG_SIMULATOR_OUTPUT_DIR=/tmp/sim-out

python -m sglang_simulator.simulation.sglang.launch_server \
  --model-path $MODEL --tokenizer-path $MODEL --load-format dummy \
  --sim-config-path sim_config.json --port 30000 \
  --max-total-tokens 16384 --max-running-requests 16 \
  --page-size 64 --disable-overlap-schedule \
  --enable-session-radix-cache --enable-cache-report

python benchmark/simulator/bench_serving.py \
  --simulator-mode=offline --backend=sglang-oai-chat \
  --base-url=http://127.0.0.1:30000 --model=$MODEL --tokenizer=$MODEL \
  --dataset-name=generated-shared-prefix \
  --gsp-num-groups 8 --gsp-prompts-per-group 4 \
  --gsp-system-prompt-len 512 --gsp-question-len 256 --gsp-output-len 64 \
  --gsp-num-turns 10 --gsp-ordered --gsp-range-ratio 0.3 \
  --gsp-group-distribution zipf --gsp-zipf-alpha 1.2 \
  --num-prompts 32 --request-rate inf --disable-tqdm --seed 42 \
  --cache-report --output-details \
  --simulator-session-per-conversation \
  --output-file=/tmp/sim-out/bench.jsonl
```

Real server, same workload:

```bash
CUDA_VISIBLE_DEVICES=0 python -m sglang.launch_server \
  --model-path $MODEL --tokenizer-path $MODEL --load-format dummy --port 30001 \
  --max-total-tokens 16384 --max-running-requests 16 \
  --page-size 64 --disable-overlap-schedule \
  --enable-session-radix-cache --enable-cache-report
```

driven by the same client arguments minus `--simulator-mode` and `--simulator-session-per-conversation`, plus a ~60-line shim that applies the same session tagging and `/close_session` the adapter does, so the simulator and the real server receive identical traffic. `SESSION_SIM_FIDELITY.md` has the shim and the full methodology.

Three settings matter and are easy to get wrong:

- **Pin `--page-size`.** Left at its default the two silently diverge: the simulator uses `page_size 1` under `torch_native`, while a Blackwell server auto-selects `trtllm_mha`, which requires `page_size 64`. Token-exact prefix matching is strictly more generous than whole-page matching, so an unpinned simulator reports optimistic hit ratios for a configuration that cannot exist on that hardware.
- **Do not pass `--disable-cuda-graph` to the real server.** It speeds startup but inflates decode latency at these batch sizes.
- **Do not pass `--gsp-fast-prepare`.** It sets `prompt_len = 1`, making the client's `input_lens` useless as a control.

## Bugs fixed

- **Multi-turn history halved** (`simulation/sglang/model_runner.py:85`) -- the mocked sampler emitted a token that BPE-merges with itself, so each answer fed back as history re-tokenized to half its length. Latent before this PR: multi-turn was unreachable.
- **A Unix epoch could replace the simulated clock** (`simulation/sglang/scheduler.py:598`) -- `cpu_overhead` differenced against an uninitialised reference, so `duration` read ~1.79e9 s. Intermittent, triggered by the server's own warm-up request.
- **The request-ingest window was charged as scheduler CPU** (`simulation/sglang/scheduler.py:231`) -- 7.2-7.9 s of idle client send time per run, landing at t=0 when every request is queued. p95 TTFT +213% -> -43%.
- **The simulator charged its own predictor cost to the simulated clock** (`simulation/sglang/scheduler.py:598`) -- 77-80% of all charged CPU overhead was the simulator's own lookups. Single-turn duration error +23.2% -> +6.9%, and the simulator became deterministic where no eviction occurs.
- **The server's warm-up request was reported as a benchmark request** (`simulation/sglang/scheduler.py`, flag on `simulation/types.py:RequestStats`) -- it never goes through the future queue, so it carries host wall-clock, and it anchored the time normalisation at 0 while real requests started at 1.0 s. `duration` therefore carried ~1.0 s of dead time, ~13% of a 7.9 s run.
- **KV eviction was invisible** (`simulation/sglang/unified_radix_cache.py:40`) -- `evicted_tokens` and `evict_calls` are now accumulated and reported; without them a hit ratio cannot be interpreted.
