# [PR #41223] [Perf] Mamba2 selective_state_update: 16x1 launch config for dstate 128 (+7.7% output throughput, Nemotron-3-Super on 8x B200)

## 正文

## Summary

In decode, the Mamba2 `selective_state_update` Triton kernel reads and writes the whole fp32 SSM state of every running request. For 64 < dstate <= 128, its hand-written launch table uses `BLOCK_SIZE_M=4, num_warps=4`. That gives each program a 4x128 state tile, 4 elements per thread. On one B200 the kernel reaches about 3.1 TB/s at every batch size from 32 to 1024. In graphed decode of Nemotron-3-Super at batch ~360 it was the largest kernel, at 26% of GPU time. This PR changes that table entry to `BLOCK_SIZE_M=16, num_warps=1`. On the 8x B200 I measured, serving output throughput goes from 10,480 to 11,292 tok/s (**+7.7%**) and outputs are bitwise identical. I have not measured other GPUs.

1. **Launch config for 64 < dstate <= 128**. Each program now owns a 16x128 tile with one warp, so there are 4x fewer programs and each thread keeps 64 elements in flight. Each row is still reduced over dstate inside one program, so the arithmetic per element does not change. The other dstate buckets are untouched.

## Correctness Verification

I ran the baseline and this branch as servers and sent the same requests to each. I compared two sets of greedy completions:
- 64 ShareGPT prompts with 128 new tokens each.
- 8 prompts of 3.2k to 3.5k tokens with 128 new tokens each.

For every generated token I compared the token id and its logprob. I set the tolerance before the runs: exact equality, because the baseline server reproduces these outputs bit for bit across restarts. I also compared the kernel's output and updated state directly at six batch sizes. The recording script is not part of this PR, and I can share it.

Every compared value is identical.

**Hardware.** 8x NVIDIA B200 (183 GB, sm_100), driver 580.126.20, CUDA 13.0, torch 2.13.0+cu130, triton 3.7.1, flashinfer 0.6.18, sglang at `567d5925fe`.

**Model.** `nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-BF16`, TP8. 88 layers: 40 Mamba2, 40 MoE, 8 attention. Per rank the Mamba2 layers have 16 heads, headdim 64, dstate 128, and an fp32 SSM cache (`mamba_ssm_cache_dtype` in the checkpoint config).

**Measurement.**
- Measured on base `567d5925fe`. The branch is rebased onto `ec070ec8c8` for this PR; `mamba_ssm.py` is identical at both, and `test_mamba_ssm.py` passes on the rebased branch.
- Both versions run the same server command, including `--cuda-graph-max-bs-decode 1024`. That flag is not part of this PR. Without it, decode batches above 512 run without CUDA graphs on this workload, which hides kernel differences.
- 3 interleaved runs per version on one node, warm caches, ShareGPT 1000 prompts, seed 42.
- Throughput and duration are the `Benchmark duration` window that `bench_serving` reports: from the first of the 1000 requests (all sent at once) to the last response. They exclude server startup, dataset loading and warmup requests.
- The kernel table comes from a standalone script: 20 calls captured in one CUDA graph, 20 replays timed with CUDA events. State slots are drawn at random from a 4096-slot pool. x, B and C are strided views of one tensor, as in the model.

**Server**, both versions:
```
python -m sglang.launch_server --model-path nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-BF16 \
  --tp 8 --trust-remote-code --disable-radix-cache \
  --model-loader-extra-config '{"enable_multithread_load": true, "num_threads": 50}' \
  --cuda-graph-max-bs-decode 1024
```

**Client:**
```
python -m sglang.bench_serving --dataset-name sharegpt --num-prompts 1000 --seed 42 --request-rate inf --flush-cache
```

**Settings tried and rejected.**
- `BLOCK_SIZE_M=16, num_warps=4`: correct, but 94.5 / 187.6 us at batch 512 / 1024 against 86.4 / 169.4 us here.
- `(8, 1)` ran within 2% of `(16, 1)`.
- `--mamba-backend flashinfer`: similar end-to-end speed, but greedy outputs are not bitwise identical to the Triton kernel.
