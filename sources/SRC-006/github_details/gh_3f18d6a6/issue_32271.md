## Motivation

### Summary

This RFC proposes topology-transparent multi-NIC HTTP ingress for the SGLang
router/server:

> Requests arriving through multiple host-facing NICs should converge into one
> logical scheduling queue, without changing the OpenAI-compatible API or
> application request path.

This is useful on inference nodes equipped with multiple front-side
NICs/DPUs/ENIs. A single ingress NIC can become a bandwidth or packets-per-second
bottleneck even when the Prefill/Decode and KV-transfer data planes have spare
capacity on other NICs.

### What Linux already provides

With one wildcard listener (`0.0.0.0:PORT` or `[::]:PORT`), Linux already
accepts connections addressed to any matching local interface into the same
listen socket and accept queue. Therefore, the baseline multi-NIC fan-in path
does **not** require per-NIC listeners or changes to SGLang's request API.

There are two important qualifications:

1. The accept queue is ordered by TCP handshake completion, not by client send
   time or SYN arrival time. This RFC does not promise a strict total order
   across NICs.
2. `SO_REUSEPORT` or multiple server workers create multiple kernel accept
   queues. If those modes are used for higher PPS, SGLang still needs one
   logical fan-in point before request scheduling to preserve global admission,
   priority, and fairness semantics.

### Current gap

Today this behavior is implicit. Operators lack:

- an explicit and tested multi-homed ingress contract;
- startup diagnostics confirming which addresses/interfaces can reach the
  listener;
- per-ingress-interface observability for connection rate, request rate,
  errors, and queueing;
- a benchmark that compares 1/2/4 ingress NICs and detects whether traffic
  actually spreads across them;
- a supported scale-up path when one accept queue or one HTTP worker becomes
  the bottleneck;
- a documented guarantee that optional multi-listener ingress converges before
  SGLang's scheduling/admission policy.

### Proposed design

#### Phase 0: Define and validate the zero-change baseline

- Document wildcard binding as the default multi-NIC ingress mode.
- At startup, report the bound address family, port, and whether the listener is
  wildcard-bound.
- Warn when configuration unintentionally binds to one specific host address.
- Add an integration test using two local destination addresses to verify that
  both paths reach the same SGLang endpoint and scheduler.

No request schema, OpenAI-compatible API, or model-worker change is required.

#### Phase 1: Add ingress observability

Expose optional, low-overhead metrics such as:

- accepted connections and HTTP requests by local destination
  address/interface;
- accept/HTTP queue depth or queueing delay where available;
- connection errors and resets by ingress path;
- aggregate versus per-path throughput and PPS.

Interface attribution may use the accepted socket's local address plus a cached
address-to-interface mapping. It should not add per-request routing decisions to
the model-serving hot path. If reliable attribution is unavailable on a
platform, metrics should fall back to local-address or aggregate labels instead
of guessing.

Suggested metric labels must remain bounded; raw client addresses must never be
used as labels.

#### Phase 2: Optional multi-listener fan-in for PPS scaling

If profiling shows that one accept queue/HTTP worker is the bottleneck, add an
opt-in ingress mode:

```text
NIC/IP A ─ listener/worker A ─┐
NIC/IP B ─ listener/worker B ─┼─> bounded MPSC fan-in ─> one logical
NIC/IP C ─ listener/worker C ─┘                         admission/scheduling queue
```

Possible implementations include `SO_REUSEPORT` workers or explicitly bound
per-address listeners. The implementation choice should be hidden behind the
router/server boundary.

Required semantics:

- existing endpoints and request schemas remain unchanged;
- all ingress paths share the same admission, priority, deadline, and fairness
  policy;
- bounded backpressure prevents one NIC from exhausting global queue capacity;
- no strict ordering is promised across independent TCP connections;
- failure or removal of one ingress NIC does not stop healthy listeners;
- the default remains the current single wildcard listener unless benchmarks
  justify enabling another mode.

### Alternatives considered

- **Linux bonding/LACP:** useful when available, but often unavailable for cloud
  ENIs, SR-IOV VFs, or independently managed DPUs. It also hides per-path
  observability.
- **External L4/L7 load balancer:** valid for cluster-level routing, but it does
  not remove the need to validate and observe multiple local ingress paths.
- **One SGLang instance per NIC:** duplicates serving state and fragments
  admission/scheduling queues, which is the opposite of the desired contract.
- **DPDK/XDP in the first version:** significantly increases operational
  complexity. The kernel wildcard-listener baseline should be measured first.

### Non-goals

- Configuring cloud ENIs, IP addresses, routes, bonding, or DPU firmware.
- Reordering packets or connections across NICs.
- Changing Mooncake/TENT KV-transfer path selection.
- Claiming bandwidth scaling when upstream routing still sends traffic to only
  one destination IP.

### Validation plan

On a node with 1/2/4 routable host-facing NICs:

1. Send independent HTTP workloads to each NIC's local IP and the same SGLang
   port.
2. Verify that all requests reach the same logical scheduler and preserve
   existing API behavior.
3. Measure aggregate requests/s, goodput, p50/p95/p99 latency, CPU utilization,
   accept/queue delay, drops, and fairness per ingress path.
4. Compare:
   - specific-address bind;
   - one wildcard listener;
   - optional `SO_REUSEPORT`/multi-listener fan-in.
5. Disable one ingress path during load and verify bounded impact on the others.

### Open questions

1. Should the first contribution be documentation + diagnostics + benchmark
   only, with multi-listener fan-in gated on evidence?
2. Is the SGLang Router the preferred single logical queue, or should the HTTP
   server expose a generic fan-in abstraction reusable without the router?
3. Which existing queue-delay/admission metrics should be reused to avoid a
   second ingress-only metric model?

## Related resources

- Linux `ip(7)`: binding to `INADDR_ANY` accepts traffic addressed to any local
  interface.
- Linux `socket(7)`: `SO_REUSEPORT` permits multiple sockets bound to the same
  address and port and distributes incoming connections.
- SGLang HTTP server entry point:
  `python/sglang/srt/entrypoints/http_server.py`.
- Related but separate work: #28631 proposes propagating request priority into
  the KV-transfer layer. This RFC concerns HTTP ingress before that scheduling
  and transfer path.
