## Goal

Track GLM-5.2 DSpark support on AMD/ROCm and link it to the main DSpark roadmap: #30344.

Primary validation target: AMD MI350, ROCm 7.x, TP4. The implementation should stay generic where possible, but no Hopper/Blackwell claim is made until the same gates run there.

The current RedHat checkpoint is workload-sensitive. This roadmap targets a correct, reusable DSpark runtime contract; it does not claim workload-independent speedup from that checkpoint.

## Current Evidence

### F0 Accuracy

MI350 TP4, fixed seed, natural UltraChat prompts around 2k ISL, `zai-org/GLM-5.2-FP8` plus `RedHatAI/GLM-5.2-speculator.dspark`:

- Compact 256 x 128: 256/256 complete, zero errors, aggregate AR `59.62%`, aggregate AL `5.174`.
- Seeded non-greedy: 16/16 complete at `temperature=0.8`, `top_p=0.95`, exact OSL 128.
- Static verify: 16/16 complete, exact OSL 128.

Accuracy remains a required gate for every cumulative performance PR.

### Controlled Cumulative Ladder

Fixed seed 42, same natural UltraChat fixture, disjoint warmup, c16, 48 measured prompts per repeat, exact OSL 512, `ignore_eos=true`, three repeats.

| Cumulative arm | Median AR | Median AL | Median output tok/s | Target graph |
|---|---:|---:|---:|---:|
| S0 target-only | n/a | n/a | 505.73 | n/a |
| S1b / alignment off | 50.70% | 4.534 | 634.78 | 80.9% |
| S2 exact tier fill | 49.75% physical | 4.482 physical | 749.69 | 100% |

S2 is `+18.1%` output throughput versus S1b and `+48.2%` versus S0 in this controlled TP4 scenario. All repeats completed with exact OSL 512 and passed one-target-forward plus folded accept/commit invariants.

The physical AR denominator includes graph-tier filler. PR #26 therefore records both SPS-selected logical lengths and physical execution lengths. Its three-repeat c16 gate completed 144/144 requests with:

- logical AR `50.525%`, logical AL `4.519`;
- physical AR `50.277%`, physical AL `4.519`;
- target graph, folded accept, and folded commit coverage `1332/1332`;
- zero missing sidecars, prefix loss, conservation failures, or bounds violations.

### Profile Direction

On the controlled S2 c16 profile, target verify was `93.4%` of GPU step time. Estimated GPU busy time was about `96.2%`, leaving about `3.8%` bubble. DSpark layout/accept/commit was only `0.3%` of the visible critical path.

Implication: deeper accept/commit folding is not the next measured priority. Finish the controlled zero-overhead A/B, then defer model-compute and communication tuning until the intended serving parallelism is known.

Detailed commands, artifacts, kernel breakdowns, and invariants live in the corresponding PR bodies (#21, #25, #26, and #32374).

### tanth47 · 2026-07-14

GLM-5.2 + AMD/ROCm DSpark update:

- Found and fixed a compact/ragged verify batch correctness bug in the GLM DSpark anchor-block layout path.
- Root cause: compact verify-id Triton gather used `gamma` as `draft_block_ids` row stride, but GLM DSpark uses `[anchor + gamma]` block ids (`[bs, 8]`) and `[gamma]` draft tokens (`[bs, 7]`). This made request rows after 0 read the wrong anchor in batched compact verify.
- PR: https://github.com/tanth47/sglang/pull/15
- MI350 TP4 validation after fix:
  - compact conc2, 16 x 64 greedy: 16/16 OK, AR 67.20%, AL 5.51
  - compact conc4, 32 x 64 greedy: 32/32 OK, AR 61.14%, AL 5.12
  - compact conc4, 256 x 128 sampling: 256/256 OK, AR 50.09%, AL 4.47

This moves GLM-5.2 compact/ragged verify from “batch-corrupt” back to a usable correctness baseline. Next focus remains functionality/stability gates before performance work.
