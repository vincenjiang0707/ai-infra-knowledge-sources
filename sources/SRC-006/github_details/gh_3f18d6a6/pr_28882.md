## 正文

> **Experimental, default-off.** Companion to the RFC on #10585. Selection axis (compute savings); CUDA-graph support and a long-context accuracy benchmark are tracked as follow-ups below.

## Motivation

SGLang ships a sparse-attention *algorithm framework* (`python/sglang/srt/mem_cache/sparsity/`: `SparseCoordinator`, `BaseSparseAlgorithm`, `QuestAlgorithm`, `FlashAttentionAdaptor`), and `base_algorithm.py` lists Quest/SnapKV/etc. as intended algorithms. However it is **not wired into the live serving path** — `SparseCoordinator.attention_begin/attention_end` have no callers, and `--enable-hisparse` only activates the separate DeepSeek/DSA host-offload engine. So the framework is effectively dead code today (also why the earlier KVPress effort, #12607 / #12933, stalled: algorithm code that did not affect serving).

This PR makes the existing framework run: an experimental, **default-off** `--enable-sparse-attention` flag wires `QuestAlgorithm` + `FlashAttentionAdaptor` into the **non-MLA FlashAttention decode path**, so query-aware KV-cache page selection executes end to end on normal models. It intentionally adds **no new algorithm** — it turns the dormant one into a working, tested baseline that SnapKV and others can build on. Relates to #10585.

## Modifications

- **Config:** `--enable-sparse-attention` + `--sparse-attention-config` (JSON; algorithm via the existing `_ALGORITHM_REGISTRY`; decoupled from `--enable-hisparse`). `parse_sparse_attention_config()` validates the algorithm, backend, `sparsity_ratio` and `min_sparse_prompt_len`.
- **Coordinator:** `ModelRunner` builds a `SparseCoordinator` for non-MLA models, before the attention backend and CUDA-graph capture; the FA backend binds to it (true no-op when off).
- **Decode seam (`FlashAttentionBackend.forward_decode`):** on decode, `attention_begin` (select top-k pages → adaptor rewrites `page_table`/`cache_seqlens`) then `attention_end` (update page reps); on extend, build initial reps. MLA / SWA / cascade / spec-decode fall back to dense.
- **Lifecycle:** a runner-owned coordinator threaded through the scheduler and batch-result processor (no process-global); `on_request_end` cleanup on all request-release paths (prebuilt / prefill-finish / embedding / normal) before the req slot is released, so reused slots can't inherit stale page representations.
- **Framework fixes (latent bugs surfaced by actually running it):** `base_algorithm.py` index dtype cast (int32 `seq_lens` vs int64 store); `backend_adaptor.py` skip requests selecting 0 pages so `cache_seqlens` can't go 0/negative; `SparseConfig` safe defaults.
- **Tests:** CPU unit tests for config parsing/validation and for the `FlashAttentionAdaptor` metadata rewrite (active rows, zero-selected keeps dense, no-op when inactive).

## Accuracy Tests

Smoke on RTX 4090, `fa3`, `Qwen2.5-0.5B-Instruct`, `--disable-cuda-graph --disable-piecewise-cuda-graph --disable-radix-cache`: a 452-token prompt at `{"algorithm":"quest","sparsity_ratio":0.5,"num_recent_pages":4}` keeps ~16 / prunes ~12 pages per decode step, and output is **identical to the dense baseline** (greedy), no crash. CPU unit tests: 11 passing. A full long-context benchmark (RULER/LongBench) is a tracked follow-up.

## Benchmarking and Profiling

Peak GPU memory: dense 15009 MiB vs sparse ~15.4–16.5 GiB (+ Quest's representation pool) — as expected for the selection axis (compute/bandwidth savings, not memory). CUDA-graph throughput numbers pending (see Limitations).

## Limitations (experimental)

- **CUDA graph not yet supported** — run with `--disable-cuda-graph --disable-piecewise-cuda-graph`. Decode top-k retrieval is dynamic; a graph-safe path is planned.
- **FA3 + non-MLA only**; other modes fall back to dense.
- **Selection axis only** (no eviction / memory savings yet). Validated TP=1.
