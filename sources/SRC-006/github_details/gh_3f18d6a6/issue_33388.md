### Describe the bug


### Problem

`get_new_expanded_mm_items()` splits bundled multimodal tensors using views:

```python
def _slice_value(value, start, end):
    if isinstance(value, torch.Tensor):
        return value[start:end]
```

Each image item therefore retains the complete parent storage. When SGLang serializes `mm_inputs` through the default CPU/pickle transport, the parent storage is effectively serialized once per image.

## Reproduction
```python
import pickle
import torch

from sglang.srt.managers.mm_utils import get_new_expanded_mm_items
from sglang.srt.managers.schedule_batch import Modality, MultimodalDataItem

n, rows, width = 512, 8, 64

feature = torch.zeros((n * rows, width), dtype=torch.float32)
grids = torch.tensor([[1, 1, rows]] * n, dtype=torch.int64)

item = MultimodalDataItem(
    modality=Modality.IMAGE,
    feature=feature,
    offsets=[(i, i) for i in range(n)],
    model_specific_data={"image_grid_thw": grids},
)

items = get_new_expanded_mm_items([item])

logical_bytes = sum(
    x.feature.numel() * x.feature.element_size() for x in items
)
pickle_bytes = len(pickle.dumps(items, protocol=pickle.HIGHEST_PROTOCOL))

print("logical MiB:", logical_bytes / 1024**2)
print("pickle MiB:", pickle_bytes / 1024**2)
print("amplification:", pickle_bytes / logical_bytes)
```
### Result

```text
logical MiB: 1.0
pickle MiB: 518.305
amplification: 518.3x
```

This reproduces on the unmodified `origin/kimi-k3` checkout. No custom distributed processor is installed or imported.

## Impact

A production request containing 512 images produced approximately 0.646 GiB of logical features but caused more than 330 GiB of serialization-related memory growth on the tokenizer/rank-0 process, eventually causing OOM.

### Expected behavior

Serialized size should remain proportional to the logical feature size, not:

```text
image_count * parent_storage_size
```

### Suggested fix

Materialize split CPU tensors before pickle transport, including `feature`, `precomputed_embeddings`, and split tensor metadata. The change should avoid unnecessary copies for CUDA IPC or shared-memory transport.

A temporary workaround is:

```python
items = get_new_expanded_mm_items(items)
for item in items:
    if isinstance(item.feature, torch.Tensor):
        item.feature = item.feature.clone()
```

### SaltFish11 · 2026-09-25

Additional independent validation on the default pickle IPC path:

- Bundled image features are split into per-image tensor views in `get_new_expanded_mm_items()`. `TokenizerManager._send_one_request()` dispatches the request through `sock_send()` / ZMQ `send_pyobj(..., protocol=pickle.HIGHEST_PROTOCOL)`; the scheduler receives it through `sock_recv()` / `recv_pyobj()`. This is where we observed the amplified payload.
- In our PyTorch build, reducing each view creates a distinct Python `TypedStorage` wrapper around the same underlying storage. `TypedStorage.__reduce__` serializes that entire storage into a fresh `BytesIO`. Pickle therefore cannot deduplicate the views by their shared data pointer.
- Controlled check: eight 0.2 MiB views of one 1.6 MiB tensor produce a 12.8 MiB pickle; cloning the views first produces a 1.6 MiB pickle.
- In a multi-image workload, about 31 slices of a ~313 MiB parent feature tensor corresponded to a ~10.1 GiB received pickle payload. Profiling attributed the large allocation to `recv_pyobj()`. After materializing oversized CPU slices, comparable tensor-parallel process RSS at the previously failing iteration fell from ~118.5 GiB to ~18.2 GiB, and the run passed that point.

This supports the diagnosis in this issue and the materialization approach proposed in #33391. The workload measurements are from one run; the small pickle example is model-independent.
