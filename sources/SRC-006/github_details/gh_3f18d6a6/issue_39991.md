# Motivation

## Summary

#37482 switched KV cache events to tagged msgpack maps, the same encoding vLLM moved to in vllm-project/vllm#42892. The fields both engines have use the same names. A consumer however can't treat events from both engines in a standard fashion because of the following:

1. Replay responses are missing the topic frame vLLM added in vllm-project/vllm#45177.
2. There's no `lora_name` in SGLang events. vLLM always sends it and its msgspec types reject events without it.
3. The salt is in a `cache_salt` field in SGLang. vLLM puts it in `extra_keys` on block 0 which is where a consumer like llm-d looks for it.
4. Event hashes leave out `extra_key` in SGLang, so LoRA and base model blocks with the same tokens share a hash.

This RFC proposes fixing those four in SGLang's native format in three phases to align with vLLM for standardization. It doesn't propose a vLLM hash mode or a format flag. Consumers like llm-d don't need vLLM's hash recipe and the in-repo router depends on SGLang's.

## Background

### What already matches

| Area | SGLang and vLLM |
|---|---|
| Event encoding | Tagged maps, class name under `type`, `None` optionals omitted |
| Batch | Positional `[ts, events, dp_rank]` |
| Live frames | `(topic, seq, payload)` |
| `BlockStored` fields | `block_hashes`, `parent_block_hash`, `token_ids`, `block_size`, `lora_id`, `medium`, `session_id` |
| `BlockRemoved`, `AllBlocksCleared` | Same, apart from vLLM's optional `group_idx` |

### Consumers checked

| Consumer | How it reads SGLang events |
|---|---|
| llm-d `engineType: sglang` | Positional arrays only. It can't read anything since #37482. That's llm-d's to fix |
| llm-d `engineType: vllm` | Reads SGLang's maps today. Derives its own block keys from `token_ids`, `lora_name` and `extra_keys` and uses engine hashes only as opaque keys |
| `experimental/sgl-router` | Decodes SGLang maps and ignores unknown keys. Recomputes SGLang's hash recipe on the request side (`kv_events/hash.rs`). Decodes hashes as `i64`. Maps `medium` strings to tiers |
| sgl-router replay client (#32729, open) | Parses today's two frame replay reply |
| vLLM's msgspec types | Fail on SGLang events (see below) |

Dynamo wasn't checked.

## Gaps

### 1. Replay replies have no topic frame

| | Replayed batch | End marker |
|---|---|---|
| vLLM | `(client_id, b"", topic, seq, payload)` | `(client_id, b"", b"", END_SEQ, b"")` |
| SGLang (`kv_events.py:541,546`) | `(client_id, b"", seq, payload)` | `(client_id, b"", END_SEQ, b"")` |

llm-d's replay client requires three frames after the delimiter (`parseEventFrame` in `pkg/kvevents/zmq_subscriber.go`). From reading that code: with `replaySocketPort` set for an SGLang pool, every replay
is rejected as malformed and the pod's index entries are cleared. Live batches that arrive before a successful replay are dropped and the retry 30 seconds later fails the same way, so the pod never gets indexed.

### 2. No `lora_name`

vLLM declares `lora_id`, `medium` and `lora_name` without defaults, so all three are always on the wire. Decoding a SGLang batch with vLLM's struct definitions (copied from `vllm/distributed/kv_events.py` at `de24e51908`) fails:

```
msgspec.ValidationError: Object missing required field `lora_name` - at `$[1][0]`
```

The reverse direction works. llm-d also uses `lora_name` as the model name when it derives keys, so SGLang LoRA blocks are indexed as base model blocks.

### 3. The salt isn't in `extra_keys`

vLLM sends one `extra_keys` entry per block: LoRA name, multimodal identifiers, then `cache_salt` only on the block starting at token 0. llm-d reads the salt only from there. Its precise prefix cache README says salted SGLang requests "are precise-cache misses until SGLang emits `extra_keys`". Unsalted requests can also score hits against salted only copies. SGLang still isolates the cache, so this costs routing quality, not safety.

A side note that corrects the earlier #27682 discussion: vLLM's hashes are salt namespaced too because the salt in block 0's extra keys is part of the hash. Neither engine has `BlockRemoved` ambiguity across salts.

### 4. Event hashes leave out `extra_key`

`compute_node_event_hash_values` (`mem_cache/utils.py:178`) seeds the chain with the salt only. `Req` folds the LoRA uuid into `extra_key` (`schedule_batch.py:1096-1099`). So from reading the code, a LoRA block and a base model block with the same tokens emit the same hash and a `BlockRemoved` for one looks like a removal of both. Storage hashes already include the namespace (`storage_namespace_seed`, `utils.py:125`). vLLM includes the LoRA name in its block hash.

## Proposal

### Phase 1: additive fields, no consumer breaks

**1a. `lora_name`, with `medium` required.** Use vLLM's field order:

```python
class BlockStored(KVCacheEvent):
    block_hashes: list[int]
    parent_block_hash: Optional[int]
    token_ids: list[int]
    block_size: int
    lora_id: Optional[int]
    medium: Optional[str]
    lora_name: Optional[str]
    extra_keys: Optional[list[Optional[tuple]]] = None
    cache_salt: Optional[str] = None
    session_id: Optional[str] = None


class BlockRemoved(KVCacheEvent):
    block_hashes: list[int]
    medium: Optional[str]
```

msgspec needs `medium` to lose its default so that `lora_name` is always sent. Every constructor already passes `medium`. `lora_name` stays `null` until phase 3. `lora_id` stays `null` because vLLM's is a deprecated int and SGLang's is a uuid string.

**1b. `extra_keys` with the salt.** When a node's parent is the root (its first page starts at token 0) and `cache_salt` is set, send `extra_keys=[(salt,), None, ...]` lined up with `block_hashes`. `KVCacheEventRecorder.enqueue` merges parent linked stores and would extend `extra_keys` the same way. The Rust tree core's tagged tuple (`rust_tree_core/adapter.py:85`) needs the field too. Keep `cache_salt`. It's documented and vLLM decoders ignore it.

Effect: vLLM typed decoders read SGLang and llm-d routes salted SGLang traffic correctly. sgl-router ignores both keys.

### Phase 2: replay topic frame

Send `self._topic_bytes` before the sequence number in replay replies and `b""` before `END_SEQ`. That's the vLLM layout.

Replay clients should accept both layouts: two frames after the delimiter is `[seq, payload]`, three is
`[topic, seq, payload]`. Then a new router works with old and new workers. Neither in-repo client has shipped: #32729 is open and #39610's example is open. So they can take the dual parse before this lands and only external clients written against the two frame layout would break.

### Phase 3: LoRA name and namespaced event hashes

These two go together. Adding `lora_name` without the hash change would give llm-d two keys for one engine hash.

**3a.** Carry the adapter name to the tree node, either as a `RadixKey` field or through a lookup in the scheduler's LoRA manager. Fill `lora_name`. With LoRA, put the name first in each `extra_keys` entry, as vLLM does.

**3b.** When `extra_key` is set, seed event hashes with the full namespace, the same way storage hashes do. Keep the current `sglang-cache-salt-v1` seed when only a salt is set, so salted hashes don't change. Mirror it in the Rust tree core.

**sgl-router cost:** its request side hash has no namespace. Today LoRA requests match base model blocks which can't be reused anyway. After 3b they match nothing until the router hashes with the namespace. That's a follow-up in `kv_events/hash.rs`.

### Not proposed

- **Renaming `CPU_PINNED` to `CPU`.** llm-d weights unknown tier names like GPU, so `cpu_pinned` scores 1.0 instead of 0.8. But sgl-router drops stores whose `medium` it doesn't know (`Tiers::for_store`, `kv_events/tree.rs`), so a  rename would turn off host-tier routing on older routers. llm-d users can set `kvCacheBackendConfigs: [{name: cpu_pinned, weight: 0.8}]` instead. See open question 1.
- **Unsigned hashes.** vLLM sends unsigned 64-bit and SGLang sends signed. llm-d accepts both (llm-d-router#2601 widens that). sgl-router decodes `i64`, so flipping would break it.
- **A vLLM hash recipe or `--kv-events-format vllm`.** llm-d doesn't recompute engine hashes and sgl-router depends on SGLang's recipe. Two formats would be a second thing to test with no consumer asking for it.
- **`group_idx` / `kv_cache_spec_kind`.** llm-d indexes events without `group_idx` as-is. Sending `group_idx` without a kind would make llm-d skip every store.

## Compatibility

| Change | vLLM-typed decoders | llm-d `vllm` adapter | sgl-router (main) | sgl-router replay (#32729) | #39610 docs |
|---|---|---|---|---|---|
| 1a `lora_name`, required `medium` | Fixed | No change until phase 3 | Ignored | n/a | Add field |
| 1b `extra_keys` salt | Reads it | Salted routing fixed | Ignored | n/a | Add field |
| 2 Replay topic frame | n/a | Replay works | n/a | Needs dual parse | Update example |
| 3a `lora_name` filled | Reads it | LoRA indexed under adapter name | Ignored | n/a | Update |
| 3b Namespaced hashes | n/a | `BlockRemoved` unambiguous | LoRA misses until router follow-up | n/a | Note |

## Out of scope

- **Multimodal.** SGLang replaces image tokens with hash derived pad values, so `token_ids` differ from vLLM's placeholders. `extra_keys` can't fix that.
- **EAGLE bigram `token_ids`.** Tracked separately.
- **Pages smaller than llm-d's block size** (llm-d-router#2235).
- **A removal reason on `BlockRemoved`** (#39604). It's additive but it would be worth proposing to vLLM too so the schemas don't drift again.

## Open questions

1. **Tier names.** Keep `CPU_PINNED` and document the llm-d weight? Or have sgl-router accept `CPU` first and switch the engine a release later?
2. **LoRA name source.** A `RadixKey` field which also needs the Rust core or a scheduler side lookup?
3. **LoRA in `extra_keys`.** llm-d's `ParseRawExtraKeys` reads bare strings as multimodal hashes which looks like it would fold a vLLM `lora_name` into keys the request side never adds. That isn't verified. Should SGLang match vLLM anyway or wait until llm-d settles it?
4. **Snapshots.** Should snapshot payloads from #33394 / #34407 use the same event schema?
