### Describe the bug

## Environment

- Model: GLM-5.2 FP8
- `n_routed_experts=256`
- `--ep-size 16`
- DeepEP normal mode
- CPU OffloaderV2:

```bash
--offload-group-size 4 \
--offload-num-in-group 1 \
--offload-prefetch-step 1
```

## Problem

Enabling CPU OffloaderV2 causes Prefill warmup to fail with:

```
RuntimeError: unexpected N
```

The failure occurs in:

```
sglang.srt.layers.moe.moe_runner.deep_gemm
    -> copy_list_to_gpu_no_ce()
    -> sgl_kernel.copy_to_gpu_no_ce()
```

Relevant code:

```python
if get_offloader().forbid_copy_engine_usage:
    num_recv_tokens_per_expert_gpu = copy_list_to_gpu_no_ce(
        num_recv_tokens_per_expert
    )
```

When CPU OffloaderV2 is enabled, `forbid_copy_engine_usage` is `true`, so this path is taken unconditionally.

## Root Cause

`num_recv_tokens_per_expert` is a small `int32` control vector produced after DeepEP dispatch. It contains the number of received tokens for every local expert and is used by `ep_scatter()` / grouped GEMM to compute per-expert offsets and work sizes.

For this configuration:

```
global routed experts: 256
EP size:               16
local experts/rank:    16
```

Therefore, the control vector has:

```
N = 16
```

However, the installed `sgl_kernel.copy_to_gpu_no_ce` only provides fixed-size specializations for:

```
N = 32, 64, 72
```

```cpp
void copy_to_gpu_no_ce(const at::Tensor& input, at::Tensor& output) {
  int N = static_cast<int>(input.numel());
  if (N == 72) {
    copy_to_gpu_no_ce_impl<72>(input, output);
  } else if (N == 64) {
    copy_to_gpu_no_ce_impl<64>(input, output);
  } else if (N == 32) {
    copy_to_gpu_no_ce_impl<32>(input, output);
  } else {
    TORCH_CHECK(false, "unexpected N");
  }
}
```

It does not support `N=16`, which causes:

```
RuntimeError: unexpected N
```

This is not an invalid DeepEP output.

`N=16` is the expected local expert count for:

```
256 experts / EP16
```

## Expected Behavior

CPU OffloaderV2 should work with DeepEP for arbitrary valid local expert counts, including `N=16`.

## Actual Behavior

The service fails during model warmup / first Prefill forward:

```
File "sglang/srt/layers/moe/moe_runner/deep_gemm.py", line ...
    num_recv_tokens_per_expert_gpu = copy_list_to_gpu_no_ce(...)

File "sgl_kernel/elementwise.py", line 420
    torch.ops.sgl_kernel.copy_to_gpu_no_ce(input, output)

RuntimeError: unexpected N
```

## Suggested Fix

Avoid calling the fixed-shape kernel unconditionally.

### Option A: Add a generic fallback

```python
if len(num_recv_tokens_per_expert) in SUPPORTED_NO_CE_SIZES:
    use copy_to_gpu_no_ce(...)
else:
    use pinned CPU tensor.cuda(non_blocking=True)
```

### Option B: Fallback permanently after unsupported size

Catch the unsupported-size error once and permanently fall back to the regular pinned-memory H2D path for the process.

### Option C: Add an `N=16` specialization

Add a dedicated `N=16` implementation to `copy_to_gpu_no_ce`.

Option A/B is more robust because future models may use different expert counts and EP configurations.

## Workaround

Use the normal pinned-memory H2D copy path for unsupported `N`.

This does not change:

- DeepEP routing
- token counts
- expert offsets
- grouped GEMM semantics

It only disables the `copy_to_gpu_no_ce` optimization for this small control vector.

### Reproduction

## Cross-machine CP Note

This reproduction intentionally enables experimental cross-machine context
parallelism:

```bash
export SGLANG_ALLOW_CROSS_MACHINE_CP=1
```

By default, SGLang rejects cross-machine CP when `tp_size > 8`. The current
source gates this configuration behind `SGLANG_ALLOW_CROSS_MACHINE_CP`, rather
than enabling it silently.

The failure in this issue is independent of that experimental CP gate:

- Cross-machine TP16/CP16 distributed initialization succeeds.
- Mooncake RDMA initialization succeeds.
- Model weights load successfully.
- The failure occurs later, during the first Prefill warmup forward in:
  `copy_to_gpu_no_ce(num_recv_tokens_per_expert)`.

- The same cross-machine CP16 configuration starts successfully when
  OffloaderV2 is disabled.
