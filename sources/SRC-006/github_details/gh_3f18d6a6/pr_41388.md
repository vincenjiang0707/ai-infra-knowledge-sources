# [PR #41388] [AMD] [Kimi-K3] Opt-in aiter fp8-Q asm MLA decode/verify

## 正文

## Motivation

On Kimi-K3 at TP8 (12 MLA heads per rank, fp8 KV), SGLang runs MLA decode and DSpark verify on aiter's Gluon kernel. Gluon launches one program per query position, so in verify each request's KV is loaded once per position. aiter notes that `q_pos` is an extra grid axis and KV is re-read per `q_pos`, with those extra loads often served from L2/MALL at `ctx<=16384` (`aiter/ops/triton/gluon/mla_gluon.py`). At longer context and high concurrency the working set misses cache, verify is KV-bandwidth bound, and the extra loads show up in wall time.

vLLM's `ROCM_AITER_MLA` backend runs this 12-head fp8 shape on the same aiter path: pad Q to 16 heads, quantize Q to fp8, and call `mla_decode_fwd` with persistent metadata (`AiterMLAImpl.forward_mqa` in [rocm_aiter_mla.py](https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/mla/rocm_aiter_mla.py)). The kernels already ship in SGLang's pinned aiter; this PR only changes SGLang dispatch.

## Modifications

- New env var `SGLANG_AITER_MLA_A8W8_ASM` (`EnvBool`, default `False`) in `environ.py`.
- When it is set, and the rank has 12 heads zero-padded to 16, an fp8 KV cache and no DCP, `aiter_backend.py`:
  - quantizes Q to fp8 using the KV scale as `q_scale` (1.0 on this Kimi-K3 checkpoint), zero-pads 12 -> 16 heads, and calls `mla_decode_fwd` with the split count left to aiter (`_mla_decode_fwd_a8w8`);
  - builds persistent metadata with `causal=True`, `fast_mode=True`, `intra_batch_mode=False` and no per-batch split cap;
  - skips the Gluon branch at the decode and target-verify call sites;
  - zeroes KV row 0 before each call. SGLang routes CUDA-graph padding tokens' KV writes to the reserved slot 0, and their K/V can be NaN. The asm kernel loads row 0 for masked positions and weights it by 0, and 0 × NaN = NaN, so without this every request in a padded batch turns NaN (seen as accept length 1.00 and `"!!!!"` output). vLLM does not hit this because it never writes padding tokens (`PAD_SLOT_ID = -1`).
- With the env var unset, behavior is unchanged.

## Accuracy Tests

gsm8k (lm_eval, 5-shot, full 1319-question test set, greedy, strict-match), mean over rounds:

| config | A: Gluon (baseline) | B: asm a8w8 (this PR) | B - A | combined stderr |
|---|---|---|---|---|
| max 64 running | 0.9656 (3 rounds) | 0.9651 (3 rounds) | -0.0005 | 0.0071 |
| max 128 running | 0.9670 (2 rounds) | 0.9625 (2 rounds) | -0.0045 | 0.0072 |

Kernel level (7 shapes, q_len 1 and 5, KV 8.7k and 128.5k): rel_l2 against an fp32 reference is 0.027-0.028, at the floor set by quantizing Q to fp8 (0.026; Gluon is at 0.002 because it keeps Q in bf16). Cosine against Gluon is 0.9996. A regression test puts NaN in an unreferenced KV row 0: without the fix, 6 of 7 shapes turn every request NaN; with it, none do, and the output is bit-identical to a run with a finite row 0.

## Speed Tests and Profiling

Kimi-K3, 8x MI355X, TP8, fp8_e4m3 KV, DSpark (verify q_len 5), CUDA graphs. A fresh server per arm and round, 2-3 rounds. A is Gluon (baseline), B is asm. tok/s is total token throughput (includes prefill). Table is 32k8k and 128k8k only.

| workload | conc | A tok/s | B tok/s | tok/s B/A | A TPOT ms | B TPOT ms | TPOT B/A |
|---|---|---|---|---|---|---|---|
| 32k8k | 1 | 72 | 73 | 1.01 | 13.7 | 14.4 | 1.05 |
| 32k8k | 8 | 360 | 341 | 0.95 | 19.6 | 19.9 | 1.01 |
| 32k8k | 16 | 536 | 557 | 1.04 | 25.1 | 24.8 | 0.99 |
| 32k8k | 64 | 855 | 1072 | 1.25 | 59.5 | 46.6 | 0.78 |
| 128k8k | 1 | 79 | 73 | 0.93 | 11.5 | 12.5 | 1.09 |
| 128k8k | 8 | 232 | 256 | 1.11 | 30.0 | 26.1 | 0.87 |
| 128k8k | 16 | 323 | 377 | 1.17 | 42.7 | 34.5 | 0.81 |
| 128k8k | 64 | 308 | 368 | 1.19 | 51.0 | 40.3 | 0.79 |

At conc 64, tok/s is 1.25x (32k8k) and 1.19x (128k8k). Mid conc is mixed (32k8k conc 8 is 0.95x; 128k8k is already 1.11x at conc 8). Conc 1 is the loss.

Steady-state decode step (whole iteration: draft + verify, excluding prefill) is the cleaner kernel metric: 128k8k conc 64 goes from 74.2 to 50.6 ms (0.68x), 32k8k conc 64 from 102.8 to 76.6 ms (0.75x).

Not in the table: short context is flat at load (1k1k conc 64 is 0.99x). Prefill-heavy long ISL with OSL 1k (32k1k, 128k1k) is ~flat in tok/s because TTFT dominates; decode step at conc 64 is still 0.69-0.75x. At 16k8k the path is flat until conc 64 (1.14x), consistent with extra gluon KV reads still hitting cache.

Trace (128k, concurrency 8): `mla_a8w8_qh32_qseqlen4_gqaratio32_ps` takes 201 µs per call, replacing `_mla_gluon` at 507 µs. vLLM runs the same kernel at 185 µs.

Trade-off: at concurrency 1 the asm path is slower. In the table, 128k8k tok/s is 0.93x; 32k8k tok/s is ~flat because accept length moved, but TPOT is 1.05x and decode step is ~1.07-1.10x. Short-context conc 1 is the same (1k1k 0.89x, 16k8k 0.87x). The kernel microbench showed about 40 µs of extra per-call work (fp8 quant and pad, reduce, persistent launch), which Gluon skips on small problems. That is why the env var is off by default.
