### Describe the bug

On the MLX backend, output logprobs are only computed when `--mlx-enable-sampling` is set (the flag's help text says so, and `MlxTpWorker._logprob_rows` returns `None` unless `_sampling_active(batch)`). Without the flag, a `/generate` request with `return_logprob: true` succeeds and returns empty `output_token_logprobs` / `output_token_ids_logprobs`, with no warning. Nothing tells the caller the option was ignored.

`/v1/score` is built on exactly that (`GenerateReqInput(return_logprob=True, token_ids_logprob=..., max_new_tokens=0)`), so on a default MLX server every `/v1/score` call fails with an opaque 500:

```
RuntimeError: output_logprobs is empty for request <id>.
  File "sglang/srt/managers/tokenizer_manager_score_mixin.py", line 342, in _process_single_item_scoring_results
```

The Apple Metal guide (`docs/hardware-platforms/apple_metal.mdx`) lists the MLX key parameters but not `--mlx-enable-sampling`, so a user following it has no way to know that logprobs and scoring need the flag.

### Reproduction

```bash
SGLANG_USE_MLX=1 python -m sglang.launch_server --model-path Qwen/Qwen2.5-0.5B-Instruct \
  --disable-cuda-graph --port 30000
```

```python
import requests
r = requests.post("http://127.0.0.1:30000/generate", json={
    "text": "Is Paris the capital of France? Answer Yes or No.",
    "return_logprob": True, "token_ids_logprob": [9454, 2753],
    "sampling_params": {"max_new_tokens": 1, "temperature": 0}})
print(r.json()["meta_info"]["output_token_ids_logprobs"])   # []  (also [] for output_token_logprobs)

r = requests.post("http://127.0.0.1:30000/v1/score", json={
    "model": "Qwen/Qwen2.5-0.5B-Instruct", "query": "Is Paris the capital of France? Answer",
    "items": [" Yes", " No"], "label_token_ids": [9454, 2753], "apply_softmax": True})
print(r.status_code, r.json())   # 500 {"message": "Internal server error: output_logprobs is empty for request ..."}
```

Relaunching with `--mlx-enable-sampling` makes both work (`/v1/score` returns `[[0.9997, 0.0003], ...]`).

### Suggested fix

Either or both:

1. **Fail fast with a clear message.** `Scheduler.handle_generate_request` already aborts MLX requests that ask for prompt logprobs on the sampling path (`"Prompt input logprobs (logprob_start_len) are not supported on the MLX sampling path..."`). The same spot can abort a request with `return_logprob=True` when the MLX backend is active and `mlx_enable_sampling` is off: `"Output logprobs on the MLX backend require --mlx-enable-sampling."` `/v1/score` would then return that message instead of a 500, and `/generate` callers would stop getting silently empty logprobs.
2. **Document the flag** in the Apple Metal guide's key parameters, next to `SGLANG_MLX_CLEAR_CACHE_STEPS`.

I am happy to open a PR for (1) + (2) if @yeahdongcn agrees with the approach.
