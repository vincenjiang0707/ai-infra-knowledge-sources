# [PR #41206] [IPC] Send encoded messages without copying

source: https://github.com/sgl-project/sglang/pull/41206
state: open | updated: 2026-09-25T09:05:30Z
labels: 

## 正文

## Motivation

`sock_send` and `async_sock_send` carry sglang's inter-process messages:
- requests from the tokenizer manager to the scheduler;
- output batches from the scheduler to the detokenizer and on to the tokenizer manager;
- DP-controller and multi-tokenizer routing, encoder disaggregation and RPC.

Each call encodes the message (pickle or msgpack) into a fresh `bytes` object and hands it to pyzmq. With pyzmq's default `copy=True`, that object is copied into a new zmq message before the call returns. The copy sits on the sender's critical path and grows with the message. Output batches reach hundreds of MB when requests return hidden states, large logprob sets or sampling masks, and a 256 MiB `copy=True` send takes 69 ms.

Sender-side time for one send with a live receiver (pyzmq 27.2.0, libzmq 4.3.5, H100 host, p50):

| message | `copy=True` | `copy=False` |
|---|---|---|
| 1 KiB | 1.8 µs | 1.5 µs |
| 32 KiB | 6.7 µs | 6.6 µs |
| 64 KiB | 14.7 µs | 10.5 µs |
| 256 KiB | 34.5 µs | 15.0 µs |
| 1 MiB | 110 µs | 26 µs |
| 4 MiB | 406 µs | 32 µs |
| 16 MiB | 1.47 ms | 45 µs |
| 64 MiB | 17.1 ms | 97 µs |
| 256 MiB | 68.6 ms | 98 µs |
| 840 MiB | 225 ms | 85 µs |

## Contract

- **Wire bytes:** unchanged, so every receiver is unchanged.
- **Small messages:** pyzmq still copies anything below `Socket.copy_threshold` (64 KiB by default), with the same `memcpy` call as `copy=True`, so that path is identical.
- **Callers:** the change is payload-agnostic. All 16 callers of `sock_send` and `async_sock_send` pass an object that these functions encode themselves. Only that private `bytes` object is shared with libzmq, so no caller's data can be affected.

## Design

The four send calls pass `copy=False`: `send_pyobj` and `send`, sync and async. The encoded `bytes` object is created by the call itself, and `bytes` is immutable and not shared, so zmq can reference it instead of copying it.

For a message above the threshold, three things change (checked on pyzmq 27.2.0):

- **Buffer lifetime:** pyzmq keeps one reference to the `bytes` until libzmq has written it, about 1 ms after the receive in a local ipc test. Before, the sender held a full second copy.
- **Release thread:** pyzmq drops that reference from its garbage-collector thread (`zmq.utils.garbage`). That thread starts once per process, at the first large zero-copy send.
- **Shutdown:** after pyzmq's own `atexit` hook has run, a zero-copy send raises `RuntimeError("zmq gc socket requested during shutdown")`, where a copying send would still succeed. This only affects messages of at least 64 KiB sent during interpreter shutdown. No sglang `atexit` handler sends; they close sockets.

## Performance

Same-host A/B: one H100 machine runs the server from `main` (81f2b43ab5) and then with this change. Qwen3-8B, TP1, `temperature=1`, `ignore_eos`, pickle IPC.

The effect follows message size, whatever the payload. Rows are ordered by the largest messages each workload sends. Changes are in steady decode throughput, or in wall time for the prefill-bound case; positive means faster.

| workload | messages of 64 KiB or more | change with this PR |
|---|---|---|
| batch 256, per-token streaming | almost none; nearly every message is under 64 KiB | +0.5%, +0.1%, +0.1% |
| 64 prompts of ~10k tokens, 8 new tokens (wall time) | ~0.15 MB requests to the scheduler | -0.1%, +0.2%, 0.0% |
| batch 256, 512 new tokens | one ~0.25 MB output batch per 50-token emission | -0.0%, -0.0%, +0.2% |
| batch 256, `return_logprob` with 20 top logprobs | ~3.6 MB output batches | +0.8%, -2.6%, +2.9% |
| batch 256, `return_sampling_mask`, `top_k=1000`, selected / support | ~53 / ~168 MB per 50-token emission | +3.0% / +5.6% |
| batch 64, `return_hidden_states` | 148–248 MB output batches | **+6.3%, +14.4%, +6.2%** (1761–1899 → 1991–2017 tok/s) |
| batch 256, `return_sampling_mask`, `top_k=8192`, on top of #40986, selected / support | ~0.4 / ~0.8 GB per 50-token emission | **+21% / +39%** (12103 → 14674 and 8896 → 12401 tok/s) |

Rows with three values are three alternating server pairs; the others are one pair each. Across a wider throughput suite, 21 more configurations at batch 1, 64 and 256 stay within ±1.4%. These have masks off, or supports of at most ~20 tokens.

**The one workload where launch-level A/B read lower:** per-token streaming on `main` with `return_sampling_mask` at `top_k=1000`, batch 256.
- **Launch variance:** `main`'s scheduler keeps every request's support history as Python lists there. Its steady throughput varies by ±14% between server launches (9058–12133 tok/s), tracking how fast that launch's generation-1 GC walks those lists. Across 14 alternating launch pairs, this change averages -4% (median -3%), inside that spread.
- **Within one server:** toggling the send mode every 4 s inside one server removes the launch variance. Each zero-copy window, against its two copying neighbours, has median +1.1% in selected mode (14 of 24 faster) and +5.7% in support mode (22 of 36 faster).
- **Per-process counters:**
  - The scheduler's time in large sends drops from 111 to 17 ms per 6 s.
  - pyzmq's release thread uses 10–30 ms of CPU per 6 s.
  - The scheduler's main thread stays at ~97% CPU either way.
  - Garbage collection walks the same number of objects.
  - The heap neither trims nor fragments more.
- **On top of #40986:** those lists are gone and the same workload is +0.3% in both modes.

## Testing

- **CPU:** `test/registered/unit/{managers,disaggregation,utils,observability}` on the CPU image: 1714 passed, with the same 51 failures and 2 collection errors as `main` in the same run.
- **GPU:** `test/registered/sampling/test_sampling_mask.py` on 2×H100, which runs TP=2 and PP=2 servers: 34 passed, the same as `main`.
