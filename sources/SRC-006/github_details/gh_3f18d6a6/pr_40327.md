# 2/7 — build paged KV views through one helper

Base: #40326 (1/7). 1 commit, 12 files, +463/−47.

## The problem

Attention backends turn a per-layer `[slots, heads, head_dim]` buffer into the
`[num_pages, page_size, heads, head_dim]` form their paged kernels take with ad-hoc
`.view(-1, page_size, H, D)` calls. Splitting dim 0 keeps the slot stride as dim 1's
stride — **except at `page_size == 1`**, where `.view()` gives the size-1 dim the *row*
stride, which differs from the slot stride as soon as the per-layer buffer is strided.

Each site also re-derives the shape from the layer's config, and nothing states the stride
contract.

## What changes

Three helpers in `mem_cache/layout/page_major.py`, and every pool-buffer page split in the
paged backends routed through them.

### Which helper to use

This is the rule a new backend should follow; it is the whole API surface:

| you hold | the kernel wants | use |
|---|---|---|
| a **raw MHA pool buffer** from `get_kv_buffer` — rank you do not control (3-D slot-major under NHD, 4-D already-paged under HND) | `[pages, ps, H, D]` | **`paged_kv_view(buf, ps, H, D)`** |
| a tensor **already shaped** the way the kernel wants its rows | same rows, pages split | **`paged_view(t, ps)`** |
| the same, but the kernel wants each row **flat** | `[pages, ps, row_elems]` | **`paged_row_view(t, ps)`** |

In one line: **`paged_kv_view` when the pool hands you the buffer; `paged_view` when you
have already shaped the rows; `paged_row_view` when the kernel takes a flat row.**

`paged_view` is the primitive — it builds the paged view from the buffer's own strides, so
dim 1 carries the slot stride at every page size. The other two differ only in how they
prepare rows before calling it: `paged_row_view` *is* `paged_view(flat.view(slots, -1), ps)`,
and `paged_kv_view` is `paged_view` with a row reshape to `[H, D]` plus the HND escape
hatch. Only `paged_kv_view` knows about HND, because it is the only one receiving a buffer
whose rank it did not choose.

fa3 shows the contrast within 400 lines: the paged MHA cache calls `paged_kv_view` on the
raw buffer, while the cascade path does `.view(-1, H, D)` itself and then calls
`paged_view`, because it has already shaped its rows and only needs page-size-one blocks.

### Sites routed

Every pool-buffer page split in the paged backends now goes through one of the three
helpers — the MHA caches and the fused rope store through `paged_kv_view`, the MLA latent
and rope caches through `paged_view`, and the MLA backends whose kernels take a flat row
through `paged_row_view`. Each site keeps the page size it used before, including the case
where a draft worker's pool pages at a multiple of the backend's own.

Two shapes are deliberately left alone: a regrouping path that needs a contiguous page block
and raises rather than mis-addresses, and row views built inside stride-aware kernel wrappers
on their own arguments.

## Behaviour

On pools without strided views every site produces the same tensor as before — shape,
strides and storage offset — for NHD, fp8, nvfp4, HND and MLA buffers at any page size.

The one exception: fa3's absorbed-MLA views, whose size-1 dims (the single KV head, and the
page dim at `page_size 1`) now record a different stride. An index into a size-1 dim is
always 0, so this cannot change addressing; it is visible only to a kernel that reads that
stride.

Left as they are: fa3's `head_group_num` regrouping (minicpm), which needs a contiguous page
block and raises rather than mis-addresses otherwise; and row views built inside
stride-aware kernel wrappers on their arguments.

## Tests

- `test_trtllm_mha_paged_kv.py` — pins the row-then-page order on strided packed and flat
  rows (the page-size-1 cases **fail on the `.view()` form**) and the HND layout.
- `test_flashattention_paged_mha.py` — pins the paged MHA cache's page size and HND layout.
- `test_paged_view.py` — pins the helpers' strides, including `page_size == 1`.

## Validation

Model families exercised — a hybrid of every pool shape the unified pool supports, plus a
non-hybrid control. Perf covers the gated-deltanet hybrid (Qwen3.5-9B), the MLA hybrid
(Kimi-Linear-48B-A3B), the sliding-window hybrid (gpt-oss-20b), the tri-pool hybrid
(Inkling and Inkling-Small), and dense Llama-3.1-8B as a control. Accuracy covers the same
set and additionally the Mamba hybrid, Falcon-H1-7B. Each model is run unified against a
baseline on the same model, backend and configuration, so every delta isolates the pool.

Median inter-token latency, unified vs baseline: **+0.87%** (measured run-to-run noise floor
for this metric: 1.9%). Median GSM8K delta at n=200: **+0.50 pt** (binomial delta-sigma ≈ 3.0 pt).

Re-validated on the current base after review feedback: the stack tip (7/7) gives **+0.95%** median inter-token latency over 40 paired configurations (median per-configuration shift against the previous run of the same 40: +0.12 pp) and **−0.25 pt** median GSM8K over 26, with the full unit scope green.

## Not yet validated

fa4, trtllm_mla, cutedsl_mla and tokenspeed_mla are admitted under `--enable-unified-memory`
and supported by this change, but our validation hardware does not run
their kernels. The same holds for trtllm_mha's SM100 kernels (trtllm-gen context and decode) and
for decode context parallelism (`--dcp-size > 1`). **Reviewers with SM100-class hardware:
please run them before merging.**
