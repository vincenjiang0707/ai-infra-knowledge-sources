### Describe the bug

The day-0 Qwen3.8-Flash-Next SGLang image fails during server warmup on an RTX PRO 6000 Blackwell (SM120) when Qwen Sparse Attention reaches its packed sparse-decode fallback.

`QwenSparseAttnBackend._resolve_trtllm_sparse_decode()` returns `None` on SM120 because it checks only `is_sm100_supported()`. `_resolve_flash_attn_varlen_func()` then imports `flash_attn.cute.interface` from the pip package. That path compiles a generic/SM100 CUTE kernel and fails for the QSA varlen shape on SM120.

Observed tail of the traceback:

```text
sglang/srt/layers/attention/qwen_sparse_attn_backend.py:1741
    output = flash_attn_varlen_func(...)
flash_attn/cute/interface.py
flash_attn/cute/flash_fwd.py:1068
    self.epilogue(...)
flash_attn/cute/flash_fwd.py:393
    mO_cur = seqlen.offset_batch_Q(...)[None, None, head_idx]
...
cutlass._mlir...MLIRError: Operation creation failed:
error: unknown: expects `coord` and shape of view are weakly congruent,
but got '!cute.layout<"(?,?):(?{i64 div=8},1)">', '!cute.coord<"(_,_,?)">'
```

SGLang already contains an SM120-native FA4 dispatcher at `sglang.kernels.ops.attention.flash_attention_v4`. On SM120, changing the QSA fallback to return that wrapper instead of the pip `flash_attn.cute.interface` function fixes startup. With that narrow workaround, the server passed warmup, served a normal completion, sustained ~102.8 decode tokens/s, and completed a 260,000-token prompt.

Suggested direction:

```python
from sglang.srt.utils.common import is_sm120_supported

if is_sm120_supported():
    from sglang.kernels.ops.attention.flash_attention_v4 import (
        flash_attn_varlen_func,
    )
    return flash_attn_varlen_func
```

## Qwen3.8-Flash-Next NVFP4 on 4x RTX 5090 (SM120, 32GB) — TMA descriptor failure + MoE backend deadlock

Attempting to serve `RadixArk/Qwen3.8-Flash-Next-NVFP4` on **4x RTX 5090** (SM120, 32GB each, TP=4) with the same `lmsysorg/sglang:qwen38flashnext` image. Three distinct blockers encountered:

### 1. NVFP4 gated MoE padding assertion (sglang #30887)

`moe_intermediate_size=640` with TP=4 → `swizzle_blockscale` pads scale rows from 20 to 128, triggering:

```
AssertionError: The intermediate size required padding, but padding is also implemented for gated activations
```

Worked around by patching `modelopt_quant.py` to split w13 into w1/w3 halves, pad each individually, and rejoin. Patch: https://github.com/sgl-project/sglang/issues/30887

### 2. MoE backend deadlock on SM120

- `--moe-runner-backend flashinfer_cutlass` (default): **TMA descriptor initialization fails** on SM120:
  ```
  Error: Failed to initialize the TMA descriptor 700
  format 9  (NVFP4)
  globalDim (128,64,1,1,1)
  ```
- `--moe-runner-backend triton`: `NotImplementedError: Unsupported moe_runner_backend for NVFP4 MoE: MoeRunnerBackend.TRITON`

No working MoE backend for NVFP4 on SM120. The CUTLASS TMA path assumes SM100 (datacenter Blackwell), not SM120 (consumer Blackwell / 5090).

### 3. Memory pressure at TP=4 on 32GB cards

Weights consume **29.56 GB per GPU** (PLE n-gram offloaded to CPU RAM via `--ple-offload-embedding`, confirmed in logs). With 32GB total, only ~0.84 GB remains — insufficient for mamba/linear-attention state cache + KV cache. `--mem-fraction-static` must be ≥0.995 to pass the KV cache check, leaving essentially no room for activations.

The model runs on a single RTX PRO 6000 (96GB, TP=1) as reported in this issue, but 4x 5090 (128GB total, 32GB per card) cannot fit due to per-GPU weight density at TP=4.

### poorpaper · 2026-08-26

I validated this against the pinned day-0 image rather than only checking current `main`.

The `lmsysorg/sglang:qwen38flashnext` tag resolves to the reported digest, and its metadata shows a `d91c3682` base plus the Qwen model-support overlay. I extracted `qwen_sparse_attn_backend.py` directly from that image overlay; its SHA-256 is:

`c959835d05d0f395ad7eae4330cf264af9f6f7c1bff3d45a39bb953d2536f5f2`

This is byte-for-byte identical to the file at the current #36497 head (`73a255206f916366c8d26d4022f82ddfb0ab558d`). This also explains why grepping current `main` does not find the class: model support is still carried by #36497/the image overlay.

A source-level branch test confirms the reported path:

1. `is_sm100_supported()` accepts major 10, while SM120 is major 12.
2. `_resolve_trtllm_sparse_decode()` therefore returns `None` on SM120.
3. When classic FA2 is unavailable, `_resolve_flash_attn_varlen_func()` selects `flash_attn.cute.interface`.
4. The packed sparse-decode warmup then invokes that function at `qwen_sparse_attn_backend.py:1741`.

The proposed SGLang FA4 wrapper accepts the exact keyword contract used by this call, and its vendored interface reaches the architecture-owned `fa4_sm120.dispatch.try_cached_varlen` path. The reporter’s successful SM120 workaround therefore matches the source structure.

There is also an independent SM121 reproduction on #36497:
https://github.com/sgl-project/sglang/pull/36497#issuecomment-5427832100

So I consider this a confirmed bug in the normal warmup path of the Qwen3.8-Flash-Next day-0 overlay on SM12x. Scope caveat: #36497 is still open, and the published NVFP4 cookbook matrix currently lists B200/B300/GB300 rather than SM120, so this should not be described as a released-SGLang regression.

I did not find an overlapping fix PR yet. A regression test should assert the selected sparse-decode implementation on SM120 and cover the packed `max_seqlen_q=1` varlen shape. I’m planning to work on this issue.

 I’ll prepare a focused fix and regression test, then open a PR.

### jhsmith409 · 2026-08-27

Confirming this on a single **RTX PRO 6000 Blackwell Max-Q (SM120, 96GB)** with the same image (`lmsysorg/sglang@sha256:12d3392b…`) and `RadixArk/Qwen3.8-Flash-Next-NVFP4`, TP=1 — and adding a warning about the narrow workaround, because it starts the server but silently corrupts output.

## The FA4-fallback-only workaround produces token-ID-0 garbage past the first KV page

I first applied only the second half of the fix — leave `_resolve_trtllm_sparse_decode()` returning `None` on SM120 and reroute `_resolve_flash_attn_varlen_func()` to `sglang.kernels.ops.attention.flash_attention_v4`. Warmup passes, the server serves, short replies look perfect:

```
"The capital of France is"  ->  "The capital of France is **Paris**."
"Hello"                     ->  "Hello! How can I help you today?"
```

But anything longer degenerates into token ID 0, which decodes as `!` with this tokenizer:

```
" harnesses the power of ocean tides to generate electricity. ... which drive the rise and fall of!!!!!!!!!!!!!!!!!!!!"
```

**It is positional, not generative.** Using `/v1/completions` (no chat template, no reasoning/tool parsers involved) at `temperature=0`, with `--page-size 64`:

| prompt tokens | first token-0 at generation index | absolute position |
|---|---|---|
| 19 | 46 | **65** |
| 39 | 26 | **65** |
| 69 | 1 | 70 (already past it) |

The generation index slides to compensate while the absolute position stays fixed. Any prompt already longer than the boundary degenerates from essentially the first generated token.

**And the boundary tracks `--page-size`.** With `--page-size 128` it moved to absolute position **193**, invariant across eight prompt lengths from 19 to 129 tokens (generation indices 174, 164, 154, 144, 134, 124, 104, 64 respectively).

This is consistent with the docstring above `_resolve_trtllm_sparse_decode()` — the FA4 cute varlen fallback "runs a prefill-shaped kernel at decode row counts", so it appears to produce correct results only within the first KV page.

Worth flagging because the failure is quiet: the server starts, a smoke test passes, and the corruption only appears past ~65 tokens. That is easy to miss if the check is a short prompt.

## The full fix in #36556 resolves it

Switching to what #36556 does — widen the gate so SM120 uses FlashInfer's `trtllm_batch_decode_with_kv_cache`, keeping the SM120 FA4 dispatcher only as the fallback — the degeneration disappears completely. Same hardware, same checkpoint, same everything else.

Note this also requires `--attention-backend triton`, since the second `is_sm100_supported()` gate in `arg_groups/overrides.py::_qwen3_5_hybrid_overrides` returns `{}` on SM120 and so never applies the family default (thanks @hashd1ve for pinpointing that on #36497).

Results on the corrected path, TP=1, single RTX PRO 6000:

| test | result |
|---|---|
| NIAH @ ~229.5K tokens, 5 depths (0.1–0.9) | **5/5 exact**, ~24.2 s each |
| decode | 94.5 tok/s @ N=1; 307 tok/s aggregate @ N=4 |
| prefill (~25K prompts, cold, nonce-led) | 11.1k tok/s @ N=1; 11.7k @ N=4 |
| context ceiling | 262,138 input tokens; clean HTTP 400 above it |
| concurrency @ 120K ctx | clean to N=8, no failures |

The NIAH result is the direct contrast: the broken path could not stay coherent past position 65, and the corrected path retrieves a needle correctly at roughly position 206,000.

Also confirming #36532 from this hardware: `--linear-attn-prefill-backend flashinfer` + `--linear-attn-decode-backend flashinfer` is unusable on SM120, and `prefill=triton` / `decode=flashinfer` / `--mamba-ssm-dtype bfloat16` works. Note the NVFP4 cell in the cookbook's Deploy panel currently emits flashinfer for both.

One unrelated gotcha for anyone sizing this on a 96GB card: `--max-mamba-cache-size` defaults low enough that it, not `--max-running-requests`, caps real concurrency. At 16 the scheduler seated only 3 of 4 requests (`mamba num: 9`, one stuck in `#queue-req` for its whole decode, ~6.5 s TTFT); 24 seats 4 cleanly at `mamba usage: 0.50` for about 0.5 GiB.

Happy to run further tests on this hardware.
