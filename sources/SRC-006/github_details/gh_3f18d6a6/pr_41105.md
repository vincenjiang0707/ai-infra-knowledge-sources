# [PR #41105] [GLM-5.3] Capture the KDA extend in breakable prefill CUDA graphs

source: https://github.com/sgl-project/sglang/pull/41105
state: open | updated: 2026-09-27T03:38:06Z
labels: run-ci, jit-kernel, run-ci-extra

## 正文

## Motivation

GLM-5.3-Flash (`glm5_next`) interleaves 34 KDA linear-attention layers with 11 DSA layers. Prefill CUDA graphs are auto-disabled for KDA models, and `--cuda-graph-backend-prefill breakable` (BCG) opts back in, but BCG breaks the graph at every linear-attention layer: the whole KDA extend runs eagerly on each replay, about sixteen Triton launches per layer plus their Python and the host syncs in `prepare_chunk_indices`.

From profiling the eager prefill is CPU launch-bound, not GPU-bound. A prefill step issues about 2300 kernel launches, and with the profiler on it costs about 300 ms of CPU whether it carries 1K or 16K tokens; without the profiler a single 1K-token prompt still waits 152 ms for its first token. BCG halves the launches to 1182 per step, yet a 4K-token step still spends 116 ms on the CPU (with the profiler on), and the KDA chain with its glue is more than 60% of what is left.

The KDA extend cannot simply be recorded: its launch grids and index tables come from host-side lengths that change on every replay of a bucket.

- `prepare_chunk_indices` builds the (sequence, chunk) table with `.tolist()`; it and `prepare_chunk_offsets` are `tensor_cache`d on the tensor object, so inside a capture they would hand back capture-time tables without recording anything.
- `causal_conv1d_fn` sizes its grid from `seq_lens_cpu`, and the delta-rule state kernel launches one program per sequence.
- The prefix-cache track path selects rows with host lists or `nonzero` and scatters with data-dependent shapes.

## Design

<img width="2670" height="1424" alt="image" src="https://github.com/user-attachments/assets/1126b24e-cc24-4946-b5be-dcbc5c54cb5d" />

The KDA extend now runs inside the graph on static tables, and BCG breaks only at the DSA layers.

- For each token bucket `T`, capture allocates tables at the bucket's bounds: `max_seqs = min(T, SGLANG_KDA_PREFILL_GRAPH_MAX_SEQS)` (128), `max_chunks = cdiv(T, 64) + max_seqs` and `max_conv_blocks = cdiv(T, 8) + max_seqs`. The captured kernels launch fixed grids over these bounds.
- Before each replay, `KDAPrefillGraphMetadata.fill` rebuilds the tables from the batch's CPU lengths in numpy and ships them in one pinned asynchronous host-to-device copy; slots and prefix flags come from device gathers. Nothing synchronizes.
- Padded rows cost nothing. Padded sequences are empty in `cu_seqlens`, padded chunk rows point past their sequence and return on an `i_t * BT >= T` guard, padded conv blocks and state slots carry `PAD_SLOT_ID`, and rows past the batch's tokens are zeroed so the MoE and the collectives see finite values.
- Prefix-cache snapshots become a per-row table (none, final state, chunk-boundary state, conv window start, destination slot) read by two small Triton kernels, instead of host-selected scatters.
- The hybrid backend follows the runner's existing captured-metadata contract for BCG (`init_forward_metadata_for_breakable_cuda_graph_capture` / `prepare_forward_metadata_for_breakable_cuda_graph_replay`, as DeepSeek-V4 already does). DSA keeps its eager metadata init. `RadixLinearAttention` skips the eager break when the backend runs the extend in the graph.
- The path is active only under a breakable prefill backend, with the Triton KDA extend kernel and without fused-accept verify staging. A batch with more sequences than the cap runs eagerly through `can_run_prefill_cuda_graph`. `SGLANG_DISABLE_KDA_PREFILL_GRAPH_EXTEND=1` restores the per-layer break.

## Modifications

- `layers/attention/linear/kda_prefill_graph.py` (new): per-bucket tables, their refresh, the track plan, and `kda_extend_in_graph`, the forward extend on those tables.
- `kernels/ops/attention/fla/kda_prefill_graph_track.py` (new): the conv-window and SSM-state snapshot kernels over per-row modes.
- `kernels/ops/attention/fla/kda.py`: out-of-range early return in the gate cumsum, `recompute_w_u` and chunk output kernels; `chunk_kda` accepts precomputed `chunk_indices` / `chunk_offsets`.
- `kernels/ops/attention/fla/chunk_delta_h.py`: accepts `chunk_offsets` instead of deriving it through `tensor_cache`.
- `kernels/ops/mamba/causal_conv1d_triton.py`: optional (sequence, block) table that sets the grid instead of `seq_lens_cpu`.
- `layers/attention/linear/kda_backend.py`: capability checks, table capture and refresh, and the dispatch to the graph path.
- `layers/attention/hybrid_linear_attn_backend.py`, `base_attn_backend.py`, `layers/radix_linear_attention.py`: the captured-metadata contract, the replay gate and the break decision.
- `environ.py`: `SGLANG_DISABLE_KDA_PREFILL_GRAPH_EXTEND`, `SGLANG_KDA_PREFILL_GRAPH_MAX_SEQS`.
- `test/registered/kernels/ops/attention/test_kda_prefill_graph.py` (new).

## Accuracy

`test_kda_prefill_graph.py` captures one bucket and replays it for five batches of different shapes, against the production eager `forward_extend` on cloned pools. The batches cover several sequences, cached prefixes, padding, chunk-aligned and unaligned prefix-cache snapshots, and no tracking. Every replay matches bit for bit on the output, the conv and SSM pools and the track slots, and no other pool slot changes.

The existing KDA, GDN, `causal_conv1d`, mamba2, radix linear attention and hybrid backend tests pass on B300 (13 files).

End to end, the natural-language greedy probes produce exactly the text of main's BCG, and GSM8K (200 questions, greedy) scores within one question of eager prefill:

| Config | GSM8K |
|---|---|
| eager prefill (cookbook default) | 98.5% |
| main, BCG | 98.5% |
| this PR, BCG | 98.5% |
| this PR, BCG, 16K chunks | 98.5% |

## Performance

8x B300, GLM-5.3-Flash, cookbook B300 FP8 recipe (TP8, TRT-LLM DSA, FP8 KV, `flashinfer_trtllm` MoE), random-ids, all servers on one box and one tree, no profiler:

| Metric | eager (default) | main, BCG | this PR, BCG | this PR, BCG, 16K chunks |
|---|---|---|---|---|
| TTFT, 1 x 1K tokens | 152 ms | 47 ms | 37 ms | 39 ms |
| TTFT, 1 x 4K tokens | 177 ms | 152 ms | 113 ms | 95 ms |
| TTFT, 1 x 16K tokens | 495 ms | 419 ms | 384 ms | 333 ms |
| c64 1024/256 median TTFT | 968 ms | 767 ms | 696 ms | 708 ms |
| c64 1024/256 output tok/s | 4291 | 4167 | 4268 | 4477 |
| bs64 decode median ITL | 9.69 ms | 9.63 ms | 9.62 ms | 9.70 ms |

With the profiler on, a 4093-token prefill step goes from 1182 eager launches and 116 ms of CPU under main's BCG to 439 launches and 42 ms, and the GPU now finishes 33-35 ms after the last launch: the step is GPU-bound. Prefill graph capture takes 85 s instead of 165 s.

"16K chunks" adds `--chunked-prefill-size 16384 --cuda-graph-max-bs-prefill 16384 --mem-fraction-static 0.78`. GLM-5 defaults BCG prefill to 4096-token chunks, so 16K buckets alone never replay; the 16K buckets cost about 22 GB more graph memory per GPU.
