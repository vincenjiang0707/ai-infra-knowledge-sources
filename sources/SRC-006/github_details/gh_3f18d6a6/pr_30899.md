## 正文

## Motivation

Decode-side HiCache offload copies KV to host asynchronously. Retraction can return those device pages to the allocator before the copy finishes, allowing an independent writer to overwrite data the old offload still reads. A retract pause can also leave offload bookkeeping pending and prevent cache flush while paused.

Original fix and PR by Kevin Flansburg (@kflansburg). The current-main integration and validation from #40982 are consolidated here. The validated fix commit retains Kevin as its author, and this PR's original history is preserved. A follow-up hardening commit restores the fail-closed post-drain protection from Kevin's original implementation, as one retraction-only collective check.

## Modifications

Before `retract_all()` in pause/retract and before `retract_decode()` in the memory-pressure branch, the scheduler now calls `DecodeKVCacheOffloadManager.drain_before_retraction()`. That method first runs the existing `check_offload_progress()` drain unchanged, then checks whether the rank still tracks any device-to-host offload work: write acknowledgements, ongoing offloads or per-request inflight counts. It takes one MAX all-reduce of that flag on the manager's existing CPU group, the same group the drain already uses; at TP1 the check is local. If any rank reports remaining work, every participating rank raises `RuntimeError` before retraction frees KV. Pending host-to-storage backups read only host memory and do not trigger it.

Normal and overlap decode already drain before memory-pressure retraction. The PP loop selects the next batch before its drain, and abort paths release with `offload_kv=False`, without the synchronizing CPU backup. The second call protects that ordering. These are the current decode retraction entrypoints; future decode release paths must preserve it too.

The asynchronous offload path and the per-iteration decode drain are unchanged; only retraction adds the collective. Priority preemption is unchanged, and no preemption callbacks are added. The post-drain check does not rely on per-rank acknowledgement queues staying mirrored. A partial MIN drain, or an inflight count whose acknowledgement is missing, is refused rather than treated as quiescence. Ranks with no local work still participate, so all ranks make the same decision. The check is conservative: it refuses while any tracked copy remains, not only the retracted request's copy. It contains violated bookkeeping; no supported flow that produces such divergence was found. It does not recover crashed ranks, broken process groups, or exceptions raised before ranks reach the collective.

The PR adds four focused test methods, covering six scenarios: copy completion before release at both entrypoints; refusal for a peer-only copy, asymmetric acknowledgements, and inflight tracking without an acknowledgement; and release with only a storage-backup acknowledgement pending. The asymmetric case also checks that polling with no jointly ready acknowledgements remains non-refusing and that retraction joins the collective before raising. Existing fixtures and unrelated tests are unchanged.

## Accuracy Tests

### Original lifetime fix validation

These results are for the lifetime fix commit, before the hardening. They were validated on main `2909f84e` with H200, Torch 2.13.0+cu130 and sglang-kernel 0.4.7:

- **Negative control:** exactly the two new ordering assertions fail on the unmodified base.
- **Unit suites:** 87 tests plus 32 subtests pass across four relevant unit suites; direct CI-style execution passes all 23 tests.
- **Real CUDA copy/reuse controls:** these exercise both scheduler entrypoints. The base persists the next owner's values; the candidate preserves the original values. The single-GPU controls were repeated. A two-rank standalone control verifies the real TP CPU-group collective, identical per-rank releases and acknowledgement state, and correct persisted pages.
- **Qwen3-0.6B (`c1899de2`), TP1 prefill/decode, without the four guards below:**
  - paired pause, delayed pause, resume, flush and abort checks pass with exact output-token equality;
  - each variant completes four concurrent requests through 85 forced retractions, matching the uninterrupted reference;
  - delayed paused flush changes from HTTP 400 on base to HTTP 200 on the candidate.

The CUDA control uses an independent writer stream to model forward/RDMA reuse; no corruption from natural PD traffic is claimed. PP decode was not run end to end; its ordering is covered by the memory-pressure entrypoint control and source inspection. Full TP2 serving did not fit the available container host-memory budget. Its coverage is the standalone two-rank control above, not a trained TP2 serving run.

#### Guarded follow-up

The same base/candidate and TP1 workload were also tested with all four settings enabled on both roles:

- `--disaggregation-enable-kv-checksum`
- `SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE=1`
- `SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE_TIMEOUT=120`
- `SGLANG_MOONCAKE_MAX_TRANSFER_BATCH_INDICES=1` (a diagnostic value)

- **Delayed-copy trials:** all three retracted at 16 output tokens.
  - The base freed KV with a D2H copy pending and returned HTTP 400 from paused flush in 3/3 trials.
  - The candidate drained the live copy before release, had no pending copy at free, and returned HTTP 200 in 3/3.
- **Transfers and references:** initial transfers actually used the one-index cap and passed checksum verification. Three natural-pause controls per variant were clean at release, and the four uninterrupted 256-token reference outputs matched exactly.
- **Resumes:** all 12 resumed requests nevertheless aborted on a checksum mismatch at unequal spans: rebootstrap prefill hashed 15 pages while decode verified the original prompt's 14 pages.
  - This was observed on both variants and remains a separate checksum/rebootstrap issue.
  - The guarded result establishes release ordering and paused flush behavior; it does not establish resumed output equality or corrupted persisted bytes.
  - In these guarded trials, rebootstrap writes began after the stale copy drained, so no overwrite during the pending-copy window was demonstrated.
- **Transfer abort:** a separate control exercised hold, acknowledgement and release on both variants, with no live RDMA write and no timeout expiry. It does not validate a bound on the RDMA write tail.

### Hardening validation

This compares the previous PR head `bdfdd18` against it plus the hardening commit, on the same `2909f84e`-era tree, H200, Torch 2.13.0+cu130 and sglang-kernel 0.4.7. It was not re-run on a later main.

- **Unit tests after the test-only cleanup:**
  - **Candidate:** 89 tests plus 35 subtests pass across the same four suites; direct execution of the edited file passes all 25 tests.
  - **Negative controls:** the three refusal subtests fail on the previous head `bdfdd18`. On original base `2909f84e`, those refusals and all three copy-before-free assertions fail for the intended reasons.
  - **Targeted mutations:** the revised tests detect local refusal before joining MAX, skipping the KV-full guard when local tracking is empty, and moving the guard into ordinary polling. The former test set missed the first mutation.
  - This reduces the PR's added scenarios from 16 to six and removes 33 test lines. Production code is unchanged. The runtime results below retain their original source pins; the Gloo fixture code they use is unchanged.
- **Real two-process CPU Gloo control:** this runs the production entrypoints and manager methods on a real Gloo subgroup. Requests, the cache controller and the offload copies are test doubles.
  - Asymmetric acknowledgement counts, and a tracked inflight request whose acknowledgement is missing, are exercised at both entrypoints. In each case both ranks refuse with no retraction free, and the local-empty rank's MAX input of 0 is raised to 1 by its peer.
  - Healthy, empty and backup-only cases proceed.
  - The previous head releases in the fault cases.
  - Every recorded collective used synchronous CPU int32 tensors on the subgroup, with outputs equal to the cross-rank MIN/MAX of the inputs. No run hung.
- **Real CUDA healthy controls, 12 runs:** 3 repeats × both entrypoints × both versions, using real device KV, allocator reuse, D2H copy and file storage.
  - A pending copy was always waited for before release, and the same slots were reused.
  - All 917,504 persisted BF16 values per run equal the original values.
  - Both versions contain the lifetime fix, so this confirms the hardening keeps it; it is not a fault injection.
- **TP1 four-guard PD regression:** the same Qwen3-0.6B workload and four settings as above.
  - Planned trials completed on both versions.
  - All six pause trials per version drained before release, with no pending copy at free and paused flush HTTP 200.
  - On the candidate, the new check ran and passed at each of its six pauses before release.
  - Reference outputs matched exactly.
  - At TP1 the check is local, so the distributed evidence is the Gloo control above. KV-full retraction did not occur in this workload; it is covered by the unit tests, the Gloo control and the CUDA controls.
  - All 12 resumes again aborted on the known 15-versus-14-page checksum span mismatch, so end-to-end resume remains blocked by that separate issue and is not counted as passing.

Not claimed for the hardening:
- real-GPU asymmetric fault injection;
- TP2 or PP serving;
- deferred-release timeout expiry;
- post-hardening performance or retraction overhead;
- runtime validation on the latest main.
