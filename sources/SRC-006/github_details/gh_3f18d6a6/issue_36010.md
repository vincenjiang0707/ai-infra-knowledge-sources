# [Issue #36010] [Bug] NVFP4 KV cache + speculative decoding: extend_prefix_lens_cpu is None in the dequant workspace path

source: https://github.com/sgl-project/sglang/issues/36010
state: open | updated: 2026-09-23T03:31:27Z
labels: 

## 正文


## Summary

`--kv-cache-dtype nvfp4` and speculative decoding cannot be used together. Any
target-verify step crashes in the FlashInfer dequant workspace with:

```
TypeError: 'NoneType' object is not subscriptable
```

Reproduced on SM120 (RTX 5090) with native MTP (`--speculative-algorithm NEXTN`)
on `unsloth/Qwen3.8-27B-NVFP4`. Dropping only `--kv-cache-dtype nvfp4` and
keeping everything else boots and serves fine, so the NVFP4 extend path is the
trigger.

There was an earlier report of this in #36001, but it was closed after the
reporter said it had been filed by an agent using their account. The problem is
real, so here it is again with a clean repro and the call chain.

## Repro

Crashes in two different places depending on whether CUDA graphs are on.

**Graphs on - dies during decode graph capture, before the server is up:**

```bash
python -m sglang.launch_server \
  --model-path unsloth/Qwen3.8-27B-NVFP4 \
  --kv-cache-dtype nvfp4 \
  --prefill-attention-backend flashinfer \
  --decode-attention-backend trtllm_mha \
  --disable-radix-cache \
  --speculative-algorithm NEXTN \
  --speculative-num-steps 3 \
  --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 4 \
  --mamba-ssm-dtype bfloat16 \
  --context-length 131072 \
  --mem-fraction-static 0.93 \
  --cuda-graph-max-bs 2 \
  --max-running-requests 2
```

**Graphs off - starts cleanly, then dies on the first request.** Same command
with `--cuda-graph-max-bs 2` swapped for
`--disable-prefill-cuda-graph --disable-decode-cuda-graph`. It reports
`max_total_num_tokens=73280, max_running_requests=2, context_len=131072`,
logs `Application startup complete`, and then the scheduler dies as soon as a
request arrives.

So this is not specific to graph capture. The runtime target-verify path hits it
too.

```
hybrid_linear_attn_backend.py:1134           forward_extend
hybrid_attn_backend.py:213                   forward_extend

        ..., forward_batch.extend_prefix_lens_cpu, ...)
memory_pool.py:3879 -> 2565                  get_flashinfer_dequant_workspace_kv_buffer
memory_pool.py:2645                          _prepare_dequant_extend_workspace
    prev_len = int(extend_prefix_lens_cpu[i])     # None
```

Under graph capture the same chain is reached through
`capture_decode_graph -> capture_one_shape -> run_once -> qwen3_vl.py:1482
forward -> general_mm_embed_routine`, since with MTP the decode graph captures a
target-verify step, which is an extend.

## Why the field is None

`ForwardBatch.init_new` populates the `_cpu` mirrors on one path and skips them
on the other, on purpose:

```python
if isinstance(extend_seq_lens, list):
    # Main path: H2D from host lists; populate *_cpu mirrors.
    ...
    ret.extend_prefix_lens_cpu = extend_prefix_lens
    ret.extend_seq_lens_cpu = extend_seq_lens
else:
    # gpu_only: device tensors handed in directly; leave *_cpu unset.
    assert isinstance(extend_seq_lens, torch.Tensor)
    ret.extend_seq_lens = extend_seq_lens
    ret.extend_prefix_lens = extend_prefix_lens
```

Speculative decoding builds its verify batch on the gpu-only path, which avoids
a D2H sync per verify step. `_prepare_dequant_extend_workspace` needs host-side
prefix lengths to pick which pages to dequantize. Those two assumptions collide,
so the field is None whenever spec decode meets an NVFP4 KV pool.

`flashinfer_backend.py:1273` passes the field unconditionally whenever
`prefill_uses_dequant_workspace` is set, which is only true for a quantized KV
pool, which is why nothing else trips over it.

## Notes on fixing it

Populating the `_cpu` mirrors in the spec verify batch is enough to get it
running with CUDA graphs disabled. That costs a D2H sync of a bs-sized tensor per
verify step.

That does not cover the graphs-on case.
`get_flashinfer_dequant_workspace_kv_buffer` is called from inside
`forward_extend`, so it sits inside the captured region. Host values can't be
read there during capture, and capture-time values baked into the graph would
select the wrong pages on replay without raising anything. Making graphs work
looks like it needs the workspace prep moved into the plan/metadata phase, or
the fused NVFP4 extend kernel from #23354, which would drop the host dependency.

Since graphs are worth roughly 2.6x on this model for us, the graphs-off
workaround isn't much use on its own. Flagging it in case it's useful for a
partial fix or a clearer error message in the meantime.

A second thing worth mentioning: `--speculative-draft-attention-backend` takes a
single value applied to both draft prefill and decode
(`model_executor/model_runner_components/attention_backend_setup.py:171`). NVFP4 KV needs `flashinfer` for extend and
`trtllm_mha` for decode, so there's no single value that works for an external
draft model either.

### jerry-he · 2026-08-23

Adding some environment facts to help triage; everything below is
static source analysis plus production-environment facts, we have not run a reproduction.

We run the same model family in production (Qwen3.8-27B hybrid, 16 full-attention + 48 GDN
layers, SGLang 0.5.17, SM120 GPUs, TP=4, page_size=1, native MTP NEXTN 3/1/4, hierarchical
cache with write_back, 262144 context). Our target KV is fp8_e4m3 (resolved via the
checkpoint's ModelOpt KV recipe rather than a server flag), so we have not hit this crash
in production — but we traced the exact failure chain in the v0.5.17 release sources, and
it is structurally identical to your report:

- flashinfer_backend.py: `forward_extend` calls
  `get_flashinfer_dequant_workspace_kv_buffer(..., forward_batch.extend_prefix_lens_cpu, ...)`
  with no speculative-mode guard (only the metadata prep is gated by
  `is_extend_without_speculative()`), and the `dq_page_table` state left behind by a
  previous real prefill is what makes `prepare_workspace=True` on a verify forward whose
  CPU mirrors are None.
- memory_pool.py: `_prepare_dequant_extend_workspace` dereferences
  `extend_prefix_lens_cpu[i]` (v0.5.17 line 2619).

So the defect is not main-only: v0.5.17 (and per the file layout, v0.5.18) carry the same
path. Two additional facts that may help maintainers size the fix:

1. `speculative_attention_mode` defaults to "prefill" (server_args), which is why verify
   lands on the flashinfer prefill backend in the first place; routing it to a decode
   backend is one way out (this is what #36038 does), making the workspace preparation
   graph-safe is the other (#36045).
2. With an explicit `--kv-cache-dtype nvfp4`, the draft worker's KV pool becomes NVFP4 as
   well (only DFLASH/fa4 has a draft override in configure_kv_cache_dtype), so any complete
   fix also has to say what serves draft decode / draft extend.

For anyone reproducing: your report that CPU-mirror population only fixes graphs-off is
consistent with the workspace call sitting inside the captured region for the verify step.
Thanks for the detailed report — it matched our static trace link by link.

### chengye75-star · 2026-09-23

Second confirmation on the **official 0.5.20 release** (PyPI wheel, not a dev build), different card in the same family — the crash is unchanged and #36340's spec-decode enablement does not reach sm120 here.

**Setup.** 2× RTX 5060 Ti 16 GB (sm_120), TP=2, driver 595.84, torch 2.13.0+cu130, flashinfer 0.6.18. Model `sakamakismile/Qwen3.8-27B-MTP-NVFP4` (compressed-tensors, hybrid 16 full-attn / 48 GDN, 4 KV heads × head_dim 256, native MTP layer — same checkpoint family as the 5090 repro above, different quant packaging).

```
python -m sglang.launch_server --model-path <sakama ckpt> --tp 2 \
  --context-length 195000 --chunked-prefill-size 4096 --mem-fraction-static 0.93 \
  --page-size 64 --max-running-requests 4 \
  --max-mamba-cache-size 24 --mamba-track-interval 64 --mamba-ssm-dtype bfloat16 \
  --kv-cache-dtype nvfp4 --prefill-attention-backend flashinfer --decode-attention-backend trtllm_mha \
  --speculative-algorithm NEXTN --speculative-num-steps 2 --speculative-eagle-topk 1 --speculative-num-draft-tokens 3 \
  --reasoning-parser qwen3
```

Dies during startup warmup, twice deterministically (tried twice), before the server ever answers health — same call chain as the OP, pinned to the 0.5.20 wheel:

```
File ".../sglang/srt/layers/attention/flashinfer_backend.py", line 1319, in forward_extend
File ".../sglang/srt/mem_cache/memory_pool.py", line 4060, in get_flashinfer_dequant_workspace_kv_buffer
File ".../sglang/srt/mem_cache/memory_pool.py", line 2763, in get_flashinfer_dequant_workspace_kv_buffer
File ".../sglang/srt/mem_cache/memory_pool.py", line 2843, in _prepare_dequant_extend_workspace
    prev_len = int(extend_prefix_lens_cpu[i])
TypeError: 'NoneType' object is not subscriptable
```

Dropping only the `--speculative-*` flags makes the crash go away (the nvfp4 pool itself allocates fine: `KV Cache is allocated. dtype: torch.float4_e2m1fn_x2, #tokens: 200000, K size: 0.95 GB, V size: 0.95 GB` per GPU), so this is squarely the spec-decode × nvfp4-extend interaction from the OP, alive and well in the release everyone can `pip install`.

**One more 16 GB-specific trap for anyone getting here via the non-spec path:** even with NEXTN removed, startup died inside the prefill CUDA-graph capture ladder — 50 capture sizes walked `avail_mem` from 1.65 GB down to 0.01 GB and the process then died on an NCCL `unhandled cuda error` mid-capture (`num_tokens=416 avail_mem=0.01`). Only after pinning `--max-total-tokens 200000` did the pool fit; on two 16 GB cards the capture phase still finishes at ~0 GB headroom. So on 16 GB consumer cards the non-spec nvfp4 path needs its capture ladder trimmed too — worth a note in the experimental feature docs, because the default fraction math looks fine until capture starts.

Side observation while wiring NEXTN on this checkpoint (independent of the nvfp4 question, happy to move it if it's a separate issue): with fp8_e4m3 KV the same NEXTN flags boot and serve, but `accept rate: 0.00` / `accept len: 1.00` across every decode batch — the draft appears never to win a single verify on this compressed-tensors MTP checkpoint. If NEXTN + compressed-tensors MTP layers isn't a supported combination in 0.5.20, that deserves one line in the matrix, because the failure is silent (you pay draft cost, get zero benefit).

@0xdespot — #36340's title says GenMHA; is there any plan for the FA2-dequant extend path on sm12x, or is "nvfp4 KV + spec decode unsupported on sm120" the stance for now? We have a 5-minute deterministic repro box and can run candidate builds/patches against it.
