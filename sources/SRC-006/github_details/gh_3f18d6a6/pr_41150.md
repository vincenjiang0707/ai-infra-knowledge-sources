# [PR #41150] [Diffusion] Default Qwen-Image 2.1 outputs to PNG

## 正文

## Motivation

Qwen-Image 2.1 native generation returns RGBA images. When an image request omits `output_format`, the generic image API falls back to JPEG, causing valid Qwen-Image 2.1 requests to fail with:

```text
HTTP 500
OSError: cannot write mode RGBA as JPEG
```

## Modifications

- Set the Qwen-Image 2.1 model-specific default image output format to PNG.
- Preserve the existing default output behavior for other diffusion models.
- Add a unit regression test for the Qwen-Image 2.1 default output format.

The fix is scoped to Qwen-Image 2.1 because its native pipeline preserves an alpha channel in generated outputs.

## Tests
### How to reproduce

**Root cause:** When `/v1/images/generations` receives no `output_format`, `image_api.py` falls back to `sampling_params_cls.default_image_output_format()`. For Qwen-Image 2.1 that returned `None`, and `choose_output_image_ext()` then defaults to `jpg`. Saving the model's RGBA output as JPEG fails. The cookbook cURL always sends `output_format: "png"`, so it never triggers this path.

**1. Launch the server** (cookbook default recipe):

```bash
sglang serve --model-path Qwen/Qwen-Image-2.1 --port 30000
```

**2. Send a generation request without `output_format`:**

```bash
curl -s -w '\nHTTP %{http_code}\n' http://localhost:30000/v1/images/generations \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"a red apple","size":"256x256","response_format":"b64_json"}'
```

**3. Check the output format** (after the fix):

```bash
curl -s http://localhost:30000/v1/images/generations \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"a red apple","size":"256x256","response_format":"b64_json"}' \
| python -c "import sys,json,base64,io;from PIL import Image;im=Image.open(io.BytesIO(base64.b64decode(json.load(sys.stdin)['data'][0]['b64_json'])));print(im.format,im.mode,im.size)"
```
### Unit tests

```bash
python -m pytest -q python/sglang/multimodal_gen/test/unit/test_qwen_image21.py::test_default_image_output_format_preserves_rgba
python -m py_compile python/sglang/multimodal_gen/configs/sample/qwenimage21.py python/sglang/multimodal_gen/test/unit/test_qwen_image21.py
```

- Container native smoke test on AMD gfx1151:
  - Request without `output_format`: HTTP 200
  - Output: valid `256x256` RGBA PNG
  - Before this fix: HTTP 500 with `OSError: cannot write mode RGBA as JPEG`

Thanks for the fix! The `/v1/images/generations` path looks good, using `default_image_output_format()` follows the same pattern as `cosmos3.py`, and other models keep their current behavior.

One gap: `/v1/images/edits` doesn't read the model default. At `image_api.py:466` it calls `choose_output_image_ext(output_format, background)` directly, so a Qwen-Image 2.1 edit request without `output_format` still falls back to `jpg`. I'd expect it to hit the same `OSError: cannot write mode RGBA as JPEG`. Editing is one of the main Qwen-Image 2.1 workflows in the cookbook, so it'd be good to cover it in this PR:

```python
sampling_params_cls = resolve_sampling_params_cls(server_args)
ext = choose_output_image_ext(
    output_format
    if output_format is not None
    else sampling_params_cls.default_image_output_format(),
    background,
)
```

Repro (before the change above):

```bash
curl -s -w '\nHTTP %{http_code}\n' http://localhost:30000/v1/images/edit
  -F "image[]=@input.png;type=image/png" \
  -F prompt="make it blue" -F size=256x256 -F response_format=b64_json
```
