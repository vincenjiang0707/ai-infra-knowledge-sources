### Describe the bug

### Describe the bug

Serving `Qwen/Qwen-Image` with the native SGLang diffusion pipeline and
`--num-gpus 4 --sp-degree 4` causes host memory usage to grow rapidly while
loading the transformer.

One scheduler rank is eventually killed by the host OOM killer (`SIGKILL`,
exit code `-9`), followed by NCCL/TCPStore errors on the remaining ranks.

The same model can start with the Diffusers backend. The native pipeline also
works on a single RTX 6000 Ada when the DiT is GPU-resident.

### Environment

- SGLang: v0.5.10
- Commit: `1519acf37c23f2189adb93f57ca9cd2db1bebf18`
- Repository state: dirty, but no loader files were modified
- GPUs: 4 × NVIDIA RTX 6000 Ada, 48 GB each
- Host RAM: 377 GiB
- Host swap: 2 GiB
- Model: `Qwen/Qwen-Image`
- Model dtype: BF16
- PyTorch: 2.9.1+cu128

### Control experiments

#### 1. Diffusers backend

The Diffusers backend can start successfully:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 \
sglang serve \
  --backend diffusers \
  --model-path Qwen/Qwen-Image \
  --num-gpus 4 \
  --sp-degree 4 \
  --text-encoder-cpu-offload \
  --vae-cpu-offload
```

This control uses a different execution/loading path and is included only to
show that the checkpoint itself is valid and can be loaded on this machine.

#### 2. Native single-GPU pipeline

The native pipeline works on one GPU when the DiT is GPU-resident:

```bash
HF_ENDPOINT=https://huggingface.co \
CUDA_VISIBLE_DEVICES=0 \
sglang serve \
  --model-path Qwen/Qwen-Image \
  --num-gpus 1 \
  --sp-degree 1 \
  --dit-cpu-offload false \
  --text-encoder-cpu-offload \
  --vae-cpu-offload \
  --pin-cpu-memory false
```

At 512×512, the observed peak reserved GPU memory is approximately 42.1 GiB.

#### 3. Native SP=4 without DiT CPU offload

The native SP=4 pipeline is still killed by the host OOM killer during
transformer loading with:

```text
--dit-cpu-offload false --pin-cpu-memory false
```

This suggests that the failure is related to the transient multi-rank loading
peak, rather than only the final CPU-resident model size or pinned memory.

### Expected behavior

The native SP=4 pipeline should do at least one of the following:

- avoid materializing full temporary checkpoint states independently on every
  rank;
- load or shard weights directly to their destination devices;
- stagger rank loading to limit peak host memory;
- support effective FSDP weight sharding for Qwen-Image;
- document the required host-memory capacity;
- or fail early with a clear host-memory diagnostic instead of being silently
  killed by the OS.

### Suspected cause

This is a hypothesis based on code inspection and has not yet been confirmed.

Sequence parallelism splits the latent sequence but does not shard the DiT
weights. With `use_fsdp_inference=false`, every SP rank loads the complete
Qwen-Image transformer.

In addition, `hf_to_custom_state_dict()` consumes the checkpoint iterator into
a complete `custom_param_sd` before
`load_model_from_full_model_state_dict()` constructs the state passed to
`model.load_state_dict()`.

During dtype/device/offload conversion, checkpoint tensors, converted tensors,
and final parameters may coexist temporarily. When four ranks perform this
work concurrently, the transient host-memory requirement may scale with the
number of ranks.

Relevant code:

- `python/sglang/multimodal_gen/runtime/loader/utils.py`
- `python/sglang/multimodal_gen/runtime/loader/fsdp_load.py`

A potentially related report for another diffusion model is:

- https://github.com/sgl-project/sglang/issues/34902

Hey @GiggleWang,

I've been building an automated GPU triage tool called **Denpex** (https://denpex.com), and I'm testing it on real-world cluster traces to gather engineer feedback. Looking at this trace:

### Diagnosis: HOST_OOM_MODEL_LOADING (85% confidence)

### Root Cause
The process is terminated by the OS kernel OOM killer (Signal 9 / Exit code 137) during model loading. In multi-GPU / sequence parallel (SP=4) loading, if each worker process independently instantiates a full unquantized copy of the model weights on CPU RAM before transferring to GPU VRAM, total host RAM usage scales with SP * model_size, quickly exhausting system memory.

### Immediate Troubleshooting Steps
1. **Sequential / Sharded Model Loading**: Use `torch.device('meta')` or pass `load_format="safetensors"` with low CPU memory loading so weights stream directly into GPU memory rather than duplicating across all 4 worker processes.
2. **Increase Host Swap / Shared Memory**: Verify host RAM headroom with `free -h` and ensure `/dev/shm` is at least 32GB to handle inter-process tensor sharing.
3. **Stagger Worker Initialization**: Stagger worker startup to avoid concurrent peak host memory spikes during weight deserialization.
