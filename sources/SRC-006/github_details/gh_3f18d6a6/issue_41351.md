## Describe the bug

With a hybrid GDN Qwen3.8-27B NVFP4 checkpoint, repeated selected-token logprob scoring is stable when Radix Cache is disabled, but the first Radix-enabled branch scoring pass differs substantially from subsequent identical passes.

The observation is:

| Cache configuration | Max repeated selected-logprob delta | Pattern |
| --- | ---: | --- |
| Unified Radix Cache enabled | `2.551527976989746` | run 1 differs; runs 2 and 3 match exactly |
| Radix Cache disabled | `0.0` | runs 1, 2 and 3 match exactly |

The prefix is explicitly warmed before the repeated branch batches. With Radix enabled, the server log reports `#cached-token: 0` for the first branch batch and `#cached-token: 128` for later identical branch batches. With Radix disabled, the three repeated branch batches are bit-stable.

This strongly correlates the drift with the cache-hit execution path, but I do **not** want to over-attribute the root cause: the current evidence does not prove that a specific GDN recurrent-state checkpoint, restore, split, or other hybrid-cache internal operation is responsible.

This was found while gating a decision workload that consumes candidate-token logprobs directly, so cache-hit equivalence matters even when the top-1 decision itself does not change.

Related work:

- #22935 — Mamba Radix cache prefix/split behavior
- #34899 — bit-exact correctness coverage for Unified Radix Cache
- #38625 — interior/no-buffer checkpoint work

I am not assuming that #22935 or #38625 has the same root cause or fully covers this request shape. In particular, I would like to know whether a shared prefix followed by divergent option branches is expected to preserve selected-token logprobs under deterministic inference when the later identical branch requests hit the hybrid cache.

<summary>Standalone /generate reproducer</summary>

```python
#!/usr/bin/env python3
import argparse
import json
import math
import urllib.request
from uuid import uuid4

SYSTEM_PROMPT = (
    "You are a System One decision model. You read the State and answer each Question "
    "by choosing exactly one of the listed options. You never explain. You answer with "
    "the single option label only."
)
STATE = "An apple was picked from the orchard."
INSTRUCTIONS = "Which listed item is the fruit mentioned in the state?"
OPTIONS = {
    "apple": "the fruit picked from the orchard",
    "stone": "a mineral rock",
    "river": "flowing water",
}
ORDERS = (("apple", "stone", "river"), ("river", "stone", "apple"))
LABELS = ("A", "B", "C")

def prefix_text():
    return (
        f"<|im_start|>system\n{SYSTEM_PROMPT}<|im_end|>\n"
        "<|im_start|>user\n# Evidence\n"
        f"{STATE}\n\n"
    )

def branch_text(order):
    option_lines = [
        f"{label}. {key}: {OPTIONS[key]}"
        for label, key in zip(LABELS, order, strict=True)
    ]
    body = "\n".join([
        f"# Criterion\n{INSTRUCTIONS}\n",
        "# Options",
        *option_lines,
        "\nRespond with only the letter of the best option.\n",
    ])
    return f"{body}<|im_end|>\n<|im_start|>assistant\n<think>\n\n</think>\n\n"

def post(url, payload):
    req = urllib.request.Request(
        f"{url.rstrip('/')}/generate",
        data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"},
        method="POST",
    )
    with urllib.request.urlopen(req, timeout=180) as r:
        data = json.loads(r.read())
    if not isinstance(data, list):
        raise RuntimeError(type(data).__name__)
    return data

def run_batch(url, inputs, selected):
    rids = [f"radix-logprob-{uuid4().hex}-{i}" for i in range(len(inputs))]
    sampling = {
        "max_new_tokens": 1,
        "temperature": 1.0,
        "top_p": 1.0,
        "top_k": -1,
        "ignore_eos": True,
    }
    data = post(url, {
        "rid": rids,
        "input_ids": inputs,
        "sampling_params": [sampling.copy() for _ in inputs],
        "stream": False,
        "return_logprob": [True] * len(inputs),
        "token_ids_logprob": [selected[:] for _ in inputs],
        "logprob_start_len": [-1] * len(inputs),
        "top_logprobs_num": [0] * len(inputs),
        "return_text_in_logprobs": False,
    })
    by_rid = {x["meta_info"]["id"]: x for x in data}
    rows = []
    for rid in rids:
        pos = by_rid[rid]["meta_info"]["output_token_ids_logprobs"][0]
        by_id = {int(x[1]): float(x[0]) for x in pos}
        rows.append([by_id[i] for i in selected])
    return rows

def max_delta(a, b):
    return max(
        abs(x - y)
        for ra, rb in zip(a, b, strict=True)
        for x, y in zip(ra, rb, strict=True)
    )

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--model", required=True)
    p.add_argument("--url", default="http://127.0.0.1:30001")
    args = p.parse_args()

    from transformers import AutoTokenizer
    tok = AutoTokenizer.from_pretrained(args.model, local_files_only=True)

    selected = [tok.encode(x, add_special_tokens=False)[0] for x in LABELS]
    prefix = tok.encode(prefix_text(), add_special_tokens=False)
    branches = [
        tok.encode(branch_text(order), add_special_tokens=False)
        for order in ORDERS
    ]

    # Warm only the shared state prefix.
    run_batch(args.url, [prefix], [0])

    inputs = [prefix + b for b in branches]
    runs = [run_batch(args.url, inputs, selected) for _ in range(3)]

    print(json.dumps({
        "runs": runs,
        "run1_vs_run2": max_delta(runs[0], runs[1]),
        "run2_vs_run3": max_delta(runs[1], runs[2]),
        "max_repeat_delta": max(
            max_delta(runs[0], runs[1]),
            max_delta(runs[0], runs[2]),
        ),
    }, indent=2))

if __name__ == "__main__":
    main()
```

### Observed result

The already-run production-equivalent probe, using the same prefix, two branch orders, A/B/C token IDs and SGLang `/generate` parameters, produced:

```text
Radix enabled:
  max repeated logprob delta = 2.551527976989746
  run 1 differs
  run 2 == run 3 exactly

Radix disabled:
  max repeated logprob delta = 0.0
  run 1 == run 2 == run 3 exactly
```

Disabling prefill CUDA Graph while leaving Radix enabled did not change the failing delta. Enabling deterministic inference also did not remove the first-pass difference.

The standalone script above was prepared after the diagnosis and has not yet been re-run against the GPU server; I am including it to remove the higher-level decision layer from the reproduction.

## Questions

1. Under deterministic inference, is cache-hit equivalence for the same full token sequence expected to preserve selected-token logprobs for hybrid GDN models?
2. Does this request pattern — warmed shared prefix followed by divergent branches, then identical repeated branch scoring — match the known checkpoint/split limitation in #22935?
3. Does #38625 cover the `extra_buffer` case above, or is this outside that fix's intended scope?
4. Is there a recommended cache statistic/debug hook that can distinguish full-attention KV reuse from valid GDN recurrent-state reuse at the branch boundary?

## Root-cause update + validated minimal patch

I completed the follow-up diagnosis and now have a causal result for the pinned reproducer.

### Root cause observed in this workload

The first divergence is **not** in GDN recurrent-state restore/checkpointing.

A read-only operator trace localized the first difference to:

```text
model.layers.0.linear_attn.in_proj_qkvz
```

before the GDN recurrent update.

For the aligned suffix rows on both TP ranks:

- the BF16 inputs were identical;
- the FP8-quantized inputs were identical;
- the input/weight scales were identical;
- FlashInfer `bmm_fp8` produced different outputs when the same rows were evaluated as part of the cold `M=248` batch versus the warm-hit `M=120` batch;
- maximum observed operator deltas were `0.03125` on TP0 and `0.25` on TP1;
- SGLang's existing PyTorch/`torch._scaled_mm` FP8 fallback produced `0.0` delta for the same frozen rows.

A separate FP32 GDN-checkpoint candidate was tested first and **did not** fix the original end-to-end drift, so I rejected that hypothesis for this issue.

This supports a batch-shape-dependent FlashInfer FP8 BMM result as the first observed cause for this exact ModelOpt FP8 / SM120 / TP=2 deterministic workload. I am **not** claiming that this establishes a general FlashInfer defect across all models/shapes/platforms.

### Causal validation

The original standalone native `/generate` fixture was kept, including real Radix hits:

| Arm | Cache evidence | Max repeated selected-logprob delta |
| --- | --- | ---: |
| Unpatched | 128 cached tokens across the two repeated branch requests | `1.6250152588` — FAIL |
| Radix disabled control | no cache hit / full recompute | `0.0` — PASS |
| Patched | 128 cached tokens across the two repeated branch requests | `0.0` — PASS |
| Patch reverted | 128 cached tokens across the two repeated branch requests | `2.5515279770` — FAIL |

The FAIL → PASS → reverted FAIL sequence was reproduced without changing the prompt, tokenizer, model revision, SGLang pin, TP size, or comparison threshold.

### twu3202 · 2026-09-27

I checked this at the layer level on an RTX 5060 Ti (SM120), main @ b4584ab, torch 2.13 / FlashInfer 0.6.18. `ModelOptFp8LinearMethod` with random FP8 weights; the same rows computed alone and at the tail of a larger batch, 4 weight shapes × 6 batch pairs (M from 1 to 200 against up to 1024).

| path | pairs that differ | max abs diff |
| --- | --- | --- |
| main (SM120 facade, then FlashInfer `bmm_fp8`) | 16/24 | 0.0156 |
| FlashInfer `bmm_fp8` only (the SM90/SM100 path) | 16/24 | 0.0156 |
| your patch (falls back to `apply_fp8_linear`) | 6/24 | 0.0078 |
| your patch, SM120 facade still first | 8/24 | 0.0078 |

Your patch clears every pair with M ≥ 64, including 120 vs 248, so it fixes the prefill-sized case you hit. What's left is small batches. All remaining differences have M ≤ 16 and come from the fallback GEMM itself. On SM120, the facade (`try_sm120_fp8_linear`) also takes very small batches with its own kernel (M = 1 and 4 in my probe; M = 7 already goes elsewhere), so a decode row can change kernels depending on how many requests share the batch.

A fully invariant path does exist. Quantize the input as today, upcast the FP8 input and weight to BF16 (exact for e4m3), run the batch-invariant `mm` that deterministic mode already installs, then apply both scales. In the same test that gives 0/24, and its largest difference from today's output is about 0.7% of the output's peak value, at the level of BF16 rounding. On this card, though, it is 5–7x slower per linear than the fallback your patch uses: about 1.27 ms vs 0.18 ms for 5120→12288 at M ≤ 64, and about two thirds of that is the per-call weight upcast.

So I'd suggest your patch plus skipping the SM120 facade under deterministic inference, with a batch-invariance test for M ≥ 64 and a note that decode-sized batches aren't covered. Happy to open that PR based on your patch. Or would you rather take the slower, fully invariant route?
