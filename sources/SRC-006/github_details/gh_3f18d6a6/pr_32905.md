# [PR #32905] [Fix] R-Fork remote_instance weight transfer defects

state: open | updated: 2026-09-25T07:04:42Z

## 正文

## Motivation

Four defects found while running R-Fork (`--load-format remote_instance`) end to end between two Kimi-K3 instances of 32xH100 each, running a dspark draft. The Gemma-norm defect (2b) was reproduced separately on Qwen3.5-35B-A3B, which has Gemma-style norms. Each one fails silently or hangs rather than reporting anything, so they are hard to tell apart in the field.

## Modifications

**1. Keep draft models off the publish side.** The engine-info bootstrap server keys entries by `tp_rank` alone, with no per-model dimension. A seed running speculative decoding had its draft `ModelRunner` publish under the target's key; initializing second, it overwrote the target's session id and weight layout, so the client pulled the draft model's memory regions for its target model. Gated on a new `RemoteInstanceWeightTransporter.publishes_weights` (target-only). Engine init is deliberately left alone — a draft loading under `--speculative-draft-load-format` still needs its own engine to *receive* weights; only publishing is target-only.

**2a. Deadlock from a group name spelled two ways.** `loader.py` derived the client id as `socket.gethostbyname(socket.gethostname())` while `load_model_utils.py` used `NetworkAddress.resolve_host(socket.gethostname())`. `init_custom_process_group` wraps the rendezvous store in `PrefixStore(group_name, store)`, so two spellings put seed and client in disjoint key namespaces and the NCCL unique-id handshake blocks forever — no timeout, no error. Both call sites now derive it through one `local_instance_id()`.

**2b. Gemma-style norms silently degrading to w = 1.0.** `GemmaRMSNorm` caches `weight + 1` in a non-persistent buffer that `forward` actually reads, and only `_weight_loader` filled it. Bulk loaders (dummy / sharded state / remote instance / remote fs) bypass those per-parameter hooks, and remote_instance additionally transfers only `named_parameters()`, which excludes buffers. A Qwen3.5-35B-A3B instance loaded over R-Fork came up healthy with all 101 norms still at their `ones_like` init, so each silently degraded to w = 1.0 while `weight` itself looked correct; greedy decoding diverged from the seed on 8/8 prompts with no error anywhere. `_post_load_weights` now rebuilds weight-derived buffers.

**3. IPv6-unsafe seed URLs and ephemeral group ports.** The seed address was interpolated straight into `f"http://{ip}:{port}"`, which is unparsable for a bare IPv6 literal — R-Fork could not be used at all on an IPv6-only host. Now expressed through `NetworkAddress` (bracketed). Separately, `--remote-instance-weight-loader-send-weights-group-ports` are *listened* on by the seed, but the kernel also hands ports in the ephemeral range to outbound connections, so an overlapping choice races and loses with `EADDRINUSE` some fraction of the time. `validate_remote_instance_group_ports` now rejects them at startup instead.

**4. Seed refusals surfaced.** Both trigger calls are fire-and-forget on a worker thread — they have to be, since the seed does not answer until the client has joined the barrier — so nothing downstream inspected the response. A seed that refused (port taken, unknown group name, mismatched model) left the client sitting in the group build until the process-group timeout fired tens of minutes later, with no log line naming a cause. `_raise_for_seed_refusal` logs the seed's own message.

Docs for the group-port choice and the speculative-decoding interaction are added to `rfork.mdx`.

## Accuracy Tests

Defect 2b is an accuracy bug by construction: before the fix, an R-Fork-loaded Qwen3.5-35B-A3B diverged from its seed on 8/8 greedy prompts while every weight tensor looked correct, because the buffer `forward` reads was never transferred. After the fix the two instances agree. `test_derived_weight_buffers.py` pins the mechanism (buffer stale after a bulk overwrite, refreshed in place so CUDA-graph captures keep their address).

CI on this branch additionally exercises the affected paths end to end: `test_load_weights_from_remote_instance.py` (the R-Fork e2e), plus `test_gemma4_mtp_31b_extra.py` and `test_gemma4_dflash_31b_extra.py`, which cover Gemma-style norms together with speculative decoding — both sides of changes 1 and 2b.

## Speed Tests and Profiling

No effect on the serving path. Every change is on startup / weight-load, except `refresh_derived_weight_buffers`, which is one `torch.add` per Gemma-style norm at load time.

## Note on the port validation

The new startup check immediately caught a real bad configuration in this repo: the R-Fork e2e tests picked base port 60000, inside the CI hosts' ephemeral range (32768-60999). That is exactly the intermittent `EADDRINUSE` this check exists to prevent, and it argues for a hard error over a warning. The tests are moved below the range in a follow-up commit on this branch.
