### Motivation
On hybrid (mamba / Gated DeltaNet) models, `KVCacheConfigurator.resolve_max_num_reqs` (`python/sglang/srt/mem_cache/kv_cache_configurator.py`, v0.5.19) can cap concurrency well below the CLI value and only says so in the log:

```
max_running_requests is capped to 9 by the mamba state cache (max_mamba_cache_size=47, 5 state slots per request). To raise it: increase --mamba-full-memory-ratio or --max-mamba-cache-size, or halve the state size with --mamba-ssm-dtype bfloat16.
```

`GET /get_server_info` keeps returning the CLI value (`"max_running_requests": 32` in our runs), and the ready-summary line (`max_total_num_tokens=... max_running_requests=9 ...`) is again log-only.

Concrete impact: we drove a concurrency benchmark through the OpenAI-compatible API on `Jackrong/Qwopus3.6-27B-v2-FP8` (Qwen3.5-27B hybrid, RTX 6000 Ada 48 GB, `--max-running-requests 32`, default radix cache) across three rentals, believing the server ran 16–32 concurrent requests. It ran 9 and queued the rest. Every "N=16/24/32" number measured the queue, not the engine, and the inflated per-request latency looked like retraction until we read the container log. With `--disable-radix-cache` the per-request slot count drops from 5 to 1 (`_calculate_mamba_ratio`) and the cap disappears — again only visible in the log.

Proposal:
- Add `effective_max_running_requests` to `/get_server_info` (keep the CLI value as-is for compatibility), populated from the value `resolve_max_num_reqs` returns.
- Optionally expose the inputs (`max_mamba_cache_size`, mamba slots per request) so clients can explain the cap, and a gauge in `/metrics` (e.g. `sglang:max_running_requests_effective`).

### Related resources
- `kv_cache_configurator.py::resolve_max_num_reqs` (warning text above) and `_calculate_mamba_ratio` (ratio 3 + 2 with radix cache + overlap schedule; 1 with `--disable-radix-cache`).
- Ready-summary log line: `max_total_num_tokens=... chunked_prefill_size=... max_prefill_tokens=... max_running_requests=<effective> ...`.
