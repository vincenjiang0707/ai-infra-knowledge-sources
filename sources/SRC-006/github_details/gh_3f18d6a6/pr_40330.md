# 6/7 — fold the kernel translate onto `translate_kv_loc`

Base: #40329 (5/7). 1 commit, 7 files, +78/−80.

## What and why

On `main` there were **three** code paths computing the same id
`kernel_id(t) = v2p[t // ps] * ps + t % ps`:

| entry point | implementation | negative loc |
|---|---|---|
| `translate_kv_loc` → `_translate_kv_loc_impl` | `index_select` + `clamp_min` | `index_select` **raises** on a negative index; a `-1` tombstone from v2p clamps to 0 |
| `translate_kv_loc_for_kernel` → `_translate_loc_fused(dcp_size=1)` | one Triton launch | a negative loc goes to the **page-0 sink** |
| `_translate_loc_fused(dcp_size > 1)` | same kernel, DCP owner rule | — |

Three implementations of one formula, disagreeing on the ids nobody looks at. This PR takes
the first step of consolidating them.

What changes:

- `_translate_kv_loc_impl` is rewritten to a **general torch body** — any shape and dtype,
  with `out=` aliasing supported, since the canonical caller translates in place
  (`translate(loc, out=loc)`) and `torch.take` forbids index/out aliasing.
- `KVIndexTranslator._translate_full` and the pool-level
  `translate_loc_from_full_to_swa` are retargeted off `_for_kernel` onto it.

`translate_kv_loc_for_kernel` survives with **one** remaining caller
(`unified_hybrid_swa.py`), and the TODO asking for the final fold stays. Closing it is
**7/7**, which needs a kernel change first.

## The behaviour this pins

The old body **raised** on a negative virtual token; the new one resolves it to an
addressable id. That is a real semantic choice, not an incidental one, and it gets a
red-first test rather than a silent change:

`test_a_negative_loc_no_longer_raises` — red on the previous commit, green here. It
deliberately does **not** pin *which* id: this path lets the v2p lookup wrap while the fused
kernel sends it to the page-0 sink, and making the two agree is the fold in 7/7. The test is
tightened there, once the semantics are single-valued.

That deliberate slack is the honest state of the code at this commit, and it is why 7/7
exists.

## Review shape

One body rewrite, two call-site retargets, one red-first test. 7 files.

## Validation

Model families exercised — a hybrid of every pool shape the unified pool supports, plus a
non-hybrid control. Perf covers the gated-deltanet hybrid (Qwen3.5-9B), the MLA hybrid
(Kimi-Linear-48B-A3B), the sliding-window hybrid (gpt-oss-20b), the tri-pool hybrid
(Inkling and Inkling-Small), and dense Llama-3.1-8B as a control. Accuracy covers the same
set and additionally the Mamba hybrid, Falcon-H1-7B. Each model is run unified against a
baseline on the same model, backend and configuration, so every delta isolates the pool.

Median inter-token latency, unified vs baseline: **+1.07%** (measured run-to-run noise floor
for this metric: 1.9%). Median GSM8K delta at n=200: **+0.25 pt** (binomial delta-sigma ≈ 3.0 pt).

Re-validated on the current base after review feedback: the stack tip (7/7) gives **+0.95%** median inter-token latency over 40 paired configurations (median per-configuration shift against the previous run of the same 40: +0.12 pp) and **−0.25 pt** median GSM8K over 26, with the full unit scope green.

The median per-model perf shift against the preceding PR's run is −0.02 pp. Accuracy spread
(sd 1.92 pt) is the tightest of the series, against a measured same-arm floor of ±2.9 pt.

## Not yet validated

aiter, fa4, trtllm_mla, cutedsl_mla and tokenspeed_mla are admitted under
`--enable-unified-memory` and supported by this change but not yet validated on SM100-class
or ROCm hardware; the same holds for trtllm_mha's SM100 kernels and `--dcp-size > 1`.
