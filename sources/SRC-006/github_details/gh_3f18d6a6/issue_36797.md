# [Performance] NVFP4 KV cache regresses Qwen4Exp decode ~29% on DGX Spark (SM121) vs fp8_e4m3

## Summary
`--kv-cache-dtype nvfp4` (the new default, `NVFP4_KV_CACHE=1`) costs **~29% single-stream
decode throughput** for Qwen4Exp-style models (QSA sparse attention) on GB10/SM121,
versus fp8_e4m3 KV. The FP4 packed-KV path's gather-side dequant is expensive on this
silicon; on datacenter parts the tradeoff may differ, but on Spark the pool-size win
is pointless (262K native context already fits with fp8) and the decode cost is real.

## Data (2× DGX Spark TP=2, NEXTN 3/1/4, decode CUDA graphs on, n=7-10 median)
| KV dtype | single-stream decode | notes |
|---|---|---|
| nvfp4 (default since the NVFP4-KV change) | 44.0 tok/s | also occasional deep dips |
| **fp8_e4m3** (`NVFP4_KV_CACHE=0`) | **56.8-58.6 tok/s** | stable |
| bf16 | 54-59 (more variance) | |

Same cluster, same weights (RadixArk/Qwen3.8-Flash-Next-NVFP4), same bench
(`completion_tokens`-based streaming, 400-token runs).

## Suggestion
- Gate `NVFP4_KV_CACHE` default by arch: keep 1 on SM100+, default 0 on SM120/121 for
  QSA models (or autotune at first capture).
- Alternatively add a fused gather+dequant path for FP4 KV in the QSA Triton varlen
  fallback kernel (`qsa_fa_fallback.py` pattern used on SM121).

## Environment
