### Describe the bug

When serving Kimi-K3 on a single 8-GPU B300 node, the scheduler occasionally stops making progress during chunked prefill. The HTTP process remains alive and continues serving `/v1/models` and `/metrics`, but the detokenizer heartbeat stops. Ten minutes later, the PyTorch NCCL watchdog aborts the scheduler processes.

This does not look like a generic NCCL transport timeout. In two independent occurrences, the same TP `ALLREDUCE` sequence number was submitted with different tensor sizes on different ranks. The tensors are outputs of `VocabParallelEmbedding` in the Kimi-K3 multimodal embedding path.

Occurrence 1:

```text
WorkNCCL SeqNum=1320347, OpType=ALLREDUCE

rank 0/1/2/3/4/6/7: NumelIn=4501504 = 628 * 7168
rank 5:             NumelIn=8171520 = 1140 * 7168
```

Occurrence 2:

```text
WorkNCCL SeqNum=1884583, OpType=ALLREDUCE

most ranks: NumelIn=43710464 = 6098 * 7168
rank 4:     NumelIn=69400576 = 9682 * 7168
```

`7168` is the Kimi-K3 hidden size, so these sizes correspond to different token-row counts entering the same TP collective. NCCL waits because the collective contract has already diverged across ranks.

## Impact

- All in-flight generation requests stop making progress.
- Health checks begin failing because no detokenizer heartbeat is received.
- The NCCL watchdog waits for the configured 600-second distributed timeout.
- PyTorch then raises `c10::DistBackendError` and aborts the scheduler with exit code `-6` (`SIGABRT`).
- The service requires a process/container restart to recover.

Hey @PsLink,

I've been building an automated GPU triage tool called **Denpex** (https://denpex.com), and I'm testing it on real-world cluster traces to gather engineer feedback. Looking at this trace:

### Diagnosis: NCCL_COLLECTIVE_SHAPE_MISMATCH (85% confidence)

### Root Cause
Tensor parallel ranks must execute collective operations with identical buffer sizes and counts. When chunked prefill splits sequences unevenly or token padding differs between TP ranks in `VocabParallelEmbedding`, rank A invokes `all_reduce` with size N while rank B invokes it with size M, causing an immediate NCCL desynchronization or watchdog timeout.

### Immediate Troubleshooting Steps
1. **Enable NCCL Diagnostic Logging**:
   ```bash
   export NCCL_DEBUG=INFO
   export NCCL_DEBUG_SUBSYS=COLL
   export TORCH_NCCL_DESYNC_DEBUG=1
   ```
   This will output the exact collective sequence number and tensor byte counts entering the mismatched all-reduce.
2. **Verify Token Partitioning**: Check the chunked prefill logic in `VocabParallelEmbedding` to ensure token counts per chunk are synchronized across all TP ranks before launching the reduction kernel.

*(Tested via Denpex: https://denpex.com. If you test this, I'd really appreciate your feedback on whether this helps locate the mismatch!)*
