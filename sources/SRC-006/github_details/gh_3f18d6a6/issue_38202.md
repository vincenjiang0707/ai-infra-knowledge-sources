### Describe the bug

With DP attention enabled, the target KV pool consumes essentially the whole
`--mem-fraction-static` budget, and the draft worker OOMs when it allocates its
own KV pool afterwards.

The reservation for the DFLASH/DSPARK draft pool is computed from the *raw*
`tp_size`, while the draft pool is actually allocated sharded by `attn_tp_size`.
Under DP attention these differ by `attn_dp_size`, so the reservation is
under-counted by up to that factor.

### Failure chain

  1. `spec_aux_hidden_state._resolve_dflash_draft_cell_size` computes the draft
     pool's per-token cost and stores it as
     `SpecAuxHiddenStateConfig.dflash_draft_cell_size_per_token`.
  2. That config reaches the pool configurator as `spec_aux_config`.
     `DefaultPoolConfigurator.__init__` reads it via `_dflash_draft_cell_size()`
     and folds it into the per-token cell size:
     `_cell_size = target_cell_size_per_token + draft_cell_size_per_token`
     (`dflash_utils.scale_kv_cell_size_per_token_for_dflash`).
     `HybridSWAPoolConfigurator` reads the same field.
  3. `calculate_pool_sizes` turns that into the pool size:
     `max_total_num_tokens = available_bytes // _cell_size`.
  4. The draft term is computed from the raw `tp_size`, but every KV pool builder
     shards by `attn_tp_size`. With `--tp-size 16 --dp-size 16
     --enable-dp-attention`, `attn_tp_size` is `16 // 16 // 1 = 1` while the
     reservation still divides the draft's KV heads by 16.
  5. `_cell_size` therefore comes out too small, and `max_total_num_tokens` too
     large. Only the draft term is affected, so the inflation factor is
     `(target_cell + draft_cell) / (target_cell + draft_cell / attn_dp_size)`,
     not `attn_dp_size` itself.
  6. Both pools are then built at that inflated token count. The target pool stays
     within the budget — its own per-token cost was counted correctly. The draft
     pool does not: it allocates `max_total_num_tokens * draft_cell`, of which only
     `1 / attn_dp_size` was ever budgeted. The remaining `(attn_dp_size - 1) /
     attn_dp_size` is taken from the `(1 - mem_fraction_static)` runtime slack.
  7. When that slack is larger than the shortfall, startup succeeds and the
     overrun is invisible. When it is not, the draft worker OOMs while creating
     its KV buffers.

### he-yufeng · 2026-09-08

Verified the full chain against the head of `feat/kimi-k3-dflash` (PR #35784). You are exactly right, and the line numbers drifted a bit but every hop is there:

1. `model_runner_components/spec_aux_hidden_state.py:230` — `_resolve_dflash_draft_cell_size` calls `dflash_draft_cell_size_per_token(..., tp_size=server_args.tp_size)`: the raw TP size.
2. `speculative/dflash_utils.py:149` — `draft_model_config.get_num_kv_heads(tp_size)` divides the draft's KV heads by that raw `tp_size`.
3. The result is cached on `SpecAuxHiddenStateConfig.dflash_draft_cell_size_per_token` (`spec_aux_hidden_state.py:190`) and read back in `pool_configurator.py`'s `_dflash_draft_cell_size`, which folds it (times `attn_dcp_size`) into `_cell_size`.
4. Meanwhile the target side of the same file sizes with `get_parallel().attn_tp_size` (`pool_configurator.py:249/310`), and `max_total_num_tokens = available_bytes // self._cell_size` (:418-429) divides by the under-counted sum.

So under `--tp-size 16 --dp-size 16 --enable-dp-attention` the draft term is priced at 1/16 of its real per-rank cost: the draft pool is budgeted as if sharded by 16 while the worker actually shards it by `attn_tp_size` = 1. Target fits, draft OOMs out of the slack. Confirmed.

The minimal fix is at the source: `spec_aux_hidden_state.py:230` should pass the attention-sharded size the draft pool will actually be built with — `get_parallel().attn_tp_size` — instead of `server_args.tp_size` (the resolve runs inside `ModelRunner.__init__`, where `get_parallel()` is already the live context). That keeps the EAGLE fallback path untouched and makes the cached per-token cost match the allocation side by construction.

This is against the feature branch, not main, so I can send the patch as a PR onto `qqtang-code:feat/kimi-k3-dflash` if @Baichuan7 or the DFLASH authors want it in that form; otherwise the one-line change above is the whole fix.
