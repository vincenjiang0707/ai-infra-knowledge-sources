# [PR #39637] fix(quantization): reject K tiles that cross block-fp8 quantization blocks

source: https://github.com/sgl-project/sglang/pull/39637
state: open | updated: 2026-09-27T09:53:43Z
labels: jit-kernel

## 正文

## Summary

`w8a8_block_fp8_matmul_triton` indexes one `As`/`Bs` scale per compute tile, so a compute K tile must sit entirely inside one quantization K block. A hand-supplied `BLOCK_SIZE_K` that does not evenly divide the quantization block (e.g. `64` against `block_size=[32, 32]`) makes `n_tiles_k_per_group_k` zero, the scale pointer never advances past the first block, and the kernel silently returns wrong values: on the reporter's deterministic example every output is 64 where the right answer is 288. The official tuner never emits such a config, so the failure only shows for manual configurations.

The wrapper now fails closed: `w8a8_block_fp8_matmul_triton` raises a `ValueError` naming the incompatibility whenever `block_size[1] % BLOCK_SIZE_K != 0`, before launching either kernel variant (the gfx1250 variant has the same per-tile scale semantics).

## Changes

- `fp8_kernel.py`: the fail-closed check after config selection, covering both kernel variants.
- `test_block_fp8.py`: a test that runs the reporter's exact shapes both ways — `BLOCK_SIZE_K=64` raises with the incompatibility named, and the aligned `BLOCK_SIZE_K=32` still computes the expected 288.

## Verification

- Mechanism verified statically against the kernel: with `group_k // BLOCK_SIZE_K == 0`, `scale_step_k` can never advance `As_ptrs`/`Bs_ptrs` past block 0, so all 64 K elements are charged block 0's scales, exactly the reported 64-vs-288.
- The new test compiles; on this machine there is no GPU and no macOS triton build, so the runtime check (rejection fires and the aligned config computes 288) is left to GPU CI, stated plainly rather than dressed up as locally run.

Fixes #39626
