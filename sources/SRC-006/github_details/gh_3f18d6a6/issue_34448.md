## mxfp4 + `sharded_state` load format silently drops expert weights (gpt-oss-20b)

### Repro script

The script below loads `openai/gpt-oss-20b`, exports it with `save_sharded_state.py` (`--load-format sharded_state`), then compares the total size of the original checkpoint's safetensors against the exported ones. Run from the repo root:

```bash
#!/usr/bin/env bash
set -euo pipefail

MODEL_PATH="${1:?usage: $0 /path/to/openai/gpt-oss-20b [out_dir]}"
OUT_DIR="${2:-$(mktemp -d -t mxfp4-repro-XXXXXX)}"

python3 -c "import sglang; print('sglang version:', sglang.__version__)"
SGLANG_ROOT=$(python3 -c "import os, sglang; print(os.path.dirname(os.path.dirname(os.path.dirname(sglang.__file__))))")

python3 "${SGLANG_ROOT}/examples/runtime/engine/save_sharded_state.py" \
  --model-path "${MODEL_PATH}" \
  --trust-remote-code \
  --tensor-parallel-size 2 \
  --mem-fraction-static 0.7 \
  --attention-backend triton \
  --output "${OUT_DIR}"

echo "original checkpoint (safetensors only):"
du -ch "${MODEL_PATH}"/*.safetensors | tail -1
echo "sharded_state export (safetensors only):"
du -ch "${OUT_DIR}"/*.safetensors | tail -1
```

Run:

```
./repro_mxfp4_sharded_state_loss.sh /path/to/openai/gpt-oss-20b
```

### Result

Output (sglang 0.5.17, `lmsysorg/sglang:latest`, TP=2, GH200):

```
sglang version: 0.5.17
original checkpoint (safetensors only):
13G	total
sharded_state export (safetensors only):
4.0G	total
```

The export is missing every expert's packed FP4 weights (`w13_weight` / `w2_weight`); only the scales, biases, and everything else survive. Loading this checkpoint back with `--load-format sharded_state` runs every expert FFN on zeroed weights, with no error or warning.

### Problem source

This looks like a bug in sglang in the mxfp4 + `ShardedStateLoader` path.

**1. On quantization, the expert weights move off the module.** `Mxfp4MoEMethod.process_weights_after_loading` (triton_kernels branch, in `python/sglang/srt/layers/quantization/mxfp4.py`) moves the quantised weights to a helper object and then deletes them from `layer`, which is the `nn.Module`:

```python
self.w13_weight_triton_tensor = w13_weight
self.w2_weight_triton_tensor = w2_weight
del layer.w13_weight
del layer.w2_weight
```

**2. On save, `ShardedStateLoader.save_model` only sees what's still on the module.** It dumps `layer.state_dict()`, which by this point no longer contains `w13_weight` / `w2_weight`. They live on the quant-method helper object instead, which `state_dict()` never looks at.

**3. On load, the same deletion happens again, before the missing-key check can catch it.** `ShardedStateLoader.load_model` does:

```python
model = _initialize_model(...)
for _, module in model.named_modules():
    quant_method.process_weights_after_loading(module)
```

which zero-initializes the model before its missing-key check runs against it. The check is built from a `state_dict()` that's already missing `w13_weight` / `w2_weight`, so it never flags anything. The model loads "successfully" with those weights left at zero, with no error or warning.

### sohom-cs · 2026-09-26

This still reproduces by code on current `main`: `Mxfp4MoEMethod.process_weights_after_loading` (triton_kernels branch) moves `w13_weight`/`w2_weight` into the kernel wrappers on the quant method and deletes them from the layer, and `ShardedStateLoader.save_model` writes `model.state_dict()`. On load, the wrappers are built from the freshly initialized weights and nothing is copied into them, and the `Missing keys` check can't catch it because the keys are absent on both sides.

#34558 (thanks @jeremyzhang866) attempted the full round-trip and was closed after the 4×H100 `test_gpt_oss_4gpu_mxfp4.py` run failed; 4×B200 passed. Until a round-trip lands, would a fail-loud guard be welcome? Raise `NotImplementedError` in the sharded_state, presharded and remote-KV save/load paths when a module's quant method is `Mxfp4MoEMethod` with triton_kernels, so an export can no longer produce a checkpoint that loads as zeros. It's about 35 lines in `model_loader/loader.py` plus a CPU unit test, with no runtime change. @mmangkad, if you'd rather go straight to the round-trip, I'm happy to pick up #34558 instead, with credit.
