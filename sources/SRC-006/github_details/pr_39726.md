## Motivation
The load-back half of the page-unified HiCache layout, and the mirror of the staged write-back added in #39606. That PR writes a device pool out into host pages ordered

  MHA: (page, head_group, layer, 2, page_size, head_in_group, dim), K=0 V=1
  MLA: (page, layer, page_size, dim)

but stops at write-back; nothing could read those pages back. This kernel does, for one layer at a time.

Per-layer and unstaged, unlike its write-back mirror. The two directions are not symmetric in how the runtime drives them: write-back moves a whole page at once, so staging it on the device and handing the bulk copy to the copy engine costs nothing extra. Load-back is walked layer by layer by the L2 transfer engine, which unblocks the forward pass one layer at a time, so staging whole pages per layer would move num_layers times the bytes the layer actually needs. Instead the SMs read the pinned host mapping in place, the way every other layout's per-layer load already does.

Each thread moves 16 bytes; the linear index runs dim-fastest then item, so a warp's lanes read consecutive host bytes for the tokens of one (head group, layer, K/V) cell. The grid is capped by kBlockQuota as in HiCacheKernel: the load overlaps a forward pass, so extra blocks buy bandwidth by taking SMs from it.

Note that head_group == 1 is NOT page_first_direct's byte order -- the K/V axis sits inside the page block here, not outside the pool. The HG=1 cases in the test pin that.

Correctness: 123 cases pass on B200 -- 3 geometries x {uint8, fp16, bf16} x {int32, int64} indices x {0, 1, 8} tokens, for MHA and MLA, each sweeping every layer, compared for exact equality against a PyTorch-indexing reference including the rows that must keep their sentinel. Payload is seeded noise, not a counter: a counter is periodic in the layer stride, so a layer mix-up would compare equal.

Round-trip against #39606: running that PR's write-back and then this kernel over 9 configurations (including the head-cut cases) returns the device pool bit-identical, which is the actual contract between the pair.

Performance (B200, PCIe gen5, 61 layers x 8 kv heads x 128 dim, bf16, page_size 64, one layer of K+V, payload counted once):

block_quota | 1 group | 2 groups | 4 groups | 8 groups
-- | -- | -- | -- | --
2 | 15.4-16.2 GB/s | 16.2-17.1 GB/s | 16.7-17.8 GB/s | 17.3-18.2 GB/s
16 | 39.7-47.8 GB/s | 39.7-47.8 GB/s | 39.7-47.8 GB/s | 39.7-47.8 GB/s


against a 53.8 GB/s contiguous cudaMemcpyAsync ceiling. Bandwidth is flat in head-group count -- the run length does not matter, the grid cap does. The shipped default stays at 2; raising it is a measurement-led change that wants an end-to-end number, not a new-kernel PR.
