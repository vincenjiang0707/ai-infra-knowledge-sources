## Motivation

This PR adds an SGLang-native CUTLASS **MXFP4A8 (W4A8)** grouped-GEMM MoE
backend for SM90 (Hopper), targeting MXFP4-expert models such as
DeepSeek-V4-Flash.

The original implementation established the numerical path: keep expert
weights in MXFP4 (E2M1), quantize activations to FP8 (E4M3), and execute both
expert GEMMs on Hopper FP8 tensor cores with
`MMA_64x64x32_F32E4M3E4M3`. This avoids the two existing fallbacks:

- the legacy FlashInfer path upcasts activations to BF16 and executes
  `MMA_64x64x16_F32BF16BF16`;
- Marlin dequantizes the 4-bit weights to BF16 before the GEMM.

That first path demonstrated a stable large-M kernel advantage, but the
end-to-end MoE implementation still paid for separate routing, shuffle,
activation quantization, scale construction, SwiGLU, and reduction launches.
Commit `88707e39018276139fc5a9b4dedae04c521562cb` replaces that launch-heavy
sequence with a production fused runtime and shape-specialized SM90
schedulers.


## Modifications

The resulting backend is selected with:

```bash
--moe-runner-backend cutlass
```

### MXFP4A8 tensor-core path

Weights remain in checkpoint-native MXFP4, while activations are dynamically
quantized per token to FP8 E4M3. E2M1 values
`{0, 0.5, 1, 1.5, 2, 3, 4, 6}` are exactly representable in E4M3, so the
E2M1-to-E4M3 conversion uses a lossless 16-entry signed-nibble LUT. The
existing INT4-to-E4M3 conversion is unchanged.

The mixed-input mainloop no longer relies on a global group size. Each
instantiation derives its scale group from `TileK / PackedScalesNum`, allowing
the INT4A8 group-128 and MXFP4A8 group-32 kernels to share the same mainloop.

### Load-time weight preprocessing

The fused path derives a second runtime representation directly from the
untouched checkpoint tensors:

- interleaved MXFP4 weights;
- folded E8M0 offsets;
- one residual scale per expert.

The preprocessing follows the SM90 Humming layout and runs once after weight
loading. Source tensor version counters prevent duplicate preprocessing.
The original block-scale representation remains registered for the EP
fallback.

### Fused MoE execution

For `EP=1`, `cutlass_mxfp4a8_fused_moe_core` executes the expert body as:

1. build expert offsets, GEMM problem sizes, and input/output permutations;
2. reorder and quantize the routed input to FP8 while folding the expert
   residual scale into the per-token activation scale;
3. execute grouped GEMM1;
4. fuse SwiGLU, optional clamp, per-token FP8 quantization, and GEMM2 residual
   scaling;
5. execute grouped GEMM2;
6. restore token order, multiply router weights, apply
   `routed_scaling_factor`, and reduce top-k outputs.

For tiny batches (`M <= 64`), routing metadata construction and shuffled input
quantization are combined in one bounded CUDA path. Larger batches reuse the
same AOT metadata and quantization kernels without host synchronization.
Intermediate tensors are retained in reusable per-layer workspaces.

Expert parallel execution currently keeps the legacy MXFP4A8 path because the
new AOT prepare/apply protocol does not yet materialize a valid output
permutation for the EP sentinel expert.

### SM90 scheduling

The fused grouped GEMM adds two SM90 scheduling families:

- a persistent single-warpgroup ping-pong kernel for tiny and arbitrary
  serving-time shapes;
- a precomputed grouped scheduler with prebuilt TMA descriptors for validated
  large-M buckets.

The current DeepSeek-V4 dispatch uses:

| Tokens | GEMM1 config | GEMM2 config |
|---:|---:|---:|
| `M <= 64` | 100 | 100 |
| `M = 2048` | 313 | 313 |
| `M = 4096` | 320 | 334 |
| `M >= 8192` | 322 | 334 |
| Other serving shapes | 101 | 101 |

Config 334 uses a packed warp-shuffle GEMM2 epilogue. Shapes above 8192 reuse
the validated 8192-token configuration; other non-standard shapes stay on the
stable config-101 path.

### Build integration

The SM90 AOT target enables:

```cmake
CUTLASS_MIXED_GEMM_FP4_FP8_PREPROCESSED_SIGNS=1
```

The definition is scoped to `common_ops_sm90_build`; SM100+ build behavior is
unchanged.

## Code changes

### CUTLASS kernel and scheduler

- Add pre-MMA E8M0 scaling for the preprocessed MXFP4 representation.
- Add per-token-scaled epilogues for pointer-array grouped GEMM.
- Add the single-warpgroup persistent kernel.
- Add the ping-pong precomputed grouped scheduler and GPU-built work map.
- Prebuild TMA descriptors for the validated large-M configurations.
- Add the packed warp-shuffle GEMM2 epilogue.
- Preserve the original MXFP4A8 grouped GEMM as the EP-compatible fallback.

### Fused CUDA operators

- Add routing metadata generation with input/output permutation.
- Add shuffled per-token FP8 quantization with expert residual scaling.
- Add a bounded tiny-M kernel that combines routing preparation and input
  quantization.
- Add fused SwiGLU, optional clamp, FP8 quantization, and residual scaling.
- Register `cutlass_mxfp4a8_fused_moe_core` through `sgl_kernel`.

### SGLang runtime

- Add `CutlassMxfp4A8FusedMoeRunner` with reusable workspaces.
- Route `Mxfp4CutlassMoEMethod.apply()` to the fused runner.
- Keep the legacy implementation for expert parallel execution.
- Make activation-scale offsets explicit rather than treating stride and
  offset as the same value.
- Preserve CUDA graph-safe scale construction in the fallback path.

## Accuracy Tests

The existing SM90 numerical test compares
`cutlass_mxfp4a8_moe_mm` against a BF16-dequantized golden reference. It
validates:

- all 16 signed E2M1 nibbles against the E4M3 conversion LUT;
- the MXFP4 nibble permutation `[0, 2, 4, 6, 1, 3, 5, 7]`;
- group-32 E8M0 scale handling;
- single-expert and grouped-expert GEMM output;
- empty-expert and uneven-routing cases.

```bash
cd python/sglang/kernels/aot
PYTHONPATH=... python tests/test_cutlass_mxfp4a8_moe_mm.py
```

The AOT extension was also verified with a complete incremental build, wheel
installation, `sgl_kernel` import, dispatcher lookup for
`cutlass_mxfp4a8_fused_moe_core`, and import of the SGLang production wrapper.

## Speed Tests and Profiling

### Single-GPU grouped-GEMM sweep

Hardware: H20 97GB. Model shape: DeepSeek-V4-Flash MXFP4 experts
(`hidden=4096`, `intermediate=2048`, `E=256`, `topk=6`). All backends use the
same body shape, random MXFP4 weights, and router distribution. Values are
single-forward mean latency in milliseconds; lower is better.

| M | CUTLASS MXFP4A8 | FlashInfer W4A16 | Marlin | FI / CUTLASS | Marlin / CUTLASS |
|---:|---:|---:|---:|---:|---:|
| 1k | 4.675 | 4.475 | 6.880 | 0.96x | 1.47x |
| 2k | 6.548 | 8.015 | 12.748 | 1.22x | 1.95x |
| 4k | 11.147 | 14.764 | 21.947 | 1.32x | 1.97x |
| 8k | 19.255 | 26.282 | 38.312 | 1.37x | 1.99x |
| 16k | 35.469 | 48.566 | 71.131 | 1.37x | 2.01x |
| 32k | 68.354 | 93.551 | 137.324 | 1.37x | 2.01x |
| 64k | 134.044 | 183.400 | 270.432 | 1.37x | 2.02x |
| 128k | 265.712 | 362.814 | 535.340 | 1.37x | 2.02x |

CUTLASS leads from `M >= 2k`; the gain reaches approximately 1.37x over the
legacy FlashInfer W4A16 path and 2.0x over Marlin at `M >= 8k`. At `M=1k`,
fixed routing and scale overhead makes CUTLASS approximately 4% slower than
FlashInfer.

NCU profiling attributes 91%-96.5% of MoE time to the two grouped GEMMs.
Observed DRAM utilization is 2%-9.5%, so the large-M advantage comes from FP8
tensor-core compute rather than memory bandwidth.

### DeepSeek-V4-Flash GSM8K

This end-to-end comparison uses the evaluation procedure from
https://github.com/sgl-project/sglang/pull/34967. Unlike the operator table
above, the FlashInfer baseline here is the PR #34967 SM90 Humming MXFP4A8
implementation.

Deployment:

```bash
PYTHONPATH=/sgl-workspace/sglang/python \
FLASHINFER_DISABLE_VERSION_CHECK=1 \
SGLANG_ENABLE_THINKING=1 \
osl=200k \
SGLANG_DSV4_2604_SUBMODE=2604B \
SGLANG_DSV4_FP4_EXPERTS=1 \
SGLANG_JIT_DEEPGEMM_PRECOMPILE=0 \
GLOO_SOCKET_IFNAME=eth0 \
NCCL_MIN_NCHANNELS=24 \
NCCL_IB_QPS_PER_CONNECTION=8 \
python -m sglang.launch_server \
  --model-path /data/models/DeepSeek-V4-Flash \
  --trust-remote-code \
  --tp 8 \
  --attention-backend dsv4 \
  --moe-runner-backend cutlass \ #  flashinfer_mxfp4
  --cuda-graph-max-bs 32 \
  --max-running-requests 32 \
  --mem-fraction-static 0.8 \
  --speculative-algo EAGLE \
  --speculative-num-steps 3 \
  --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 4 \
  --tool-call-parser deepseekv4 \
  --reasoning-parser deepseek-v4 \
  --enable-metrics \
  --host 0.0.0.0 \
  --port 30000
```

Evaluation:

```bash
PYTHONPATH=/sgl-workspace/sglang/python \
python -m sglang.test.run_eval \
  --port 30000 \
  --eval-name gsm8k \
  --num-examples 200 \
  --api chat \
  --max-tokens 1024 \
  --num-threads 32 \
  --temperature 0 \
  --gsm8k-data-path /tmp/gsm8k-test.jsonl
```

| Backend | Total latency | Score | Output throughput |
|---|---:|---:|---:|
| CUTLASS MXFP4A8 | 64.299 s | 0.980 | **942.364 token/s** |
| FlashInfer PR #34967 | 69.557 s | 0.970 | 853.817 token/s |

At the same TP8, request-concurrency, and evaluation settings, CUTLASS
improves output throughput by **10.37%** and reduces total latency by
**7.56%**. Accuracy remains aligned: 0.980 for CUTLASS versus 0.970 for the
FlashInfer run.

| Input | CUTLASS MXFP4A8 | FlashInfer | Marlin |

## Limitations

- The fused production path currently targets SM90 and `EP=1`.
- Expert parallel execution falls back to the original MXFP4A8 path.
- Hidden and intermediate dimensions must be multiples of 128.
- Precomputed tactics are selected only for validated token counts; shapes
  above 8192 reuse the 8192-token configuration, while other non-standard
  shapes use config 101.
- The load-time fused representation currently reuses FlashInfer's SM90
  Humming weight preprocessor. Runtime execution uses SGLang AOT kernels.
- Small-M decode remains dominated by fixed routing and quantization overhead;
  Marlin is still preferred for decode in PD-disaggregated deployments.
