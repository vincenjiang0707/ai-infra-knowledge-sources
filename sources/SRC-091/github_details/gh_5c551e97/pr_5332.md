# Fix: reject empty slot_mapping in parse_mixed_slot_mapping

## What changed
- `lmcache/utils.py` (`parse_mixed_slot_mapping`): after parsing, an empty result now raises `ValueError("No slots specified")`, so it returns the standard `(None, {"error": "Invalid slot_mapping format", ...})` error like every other malformed input instead of `([], None)`.
- `tests/test_utils.py` (`test_empty_string`): updated to assert the error case instead of pinning the old `([], None)` success.

## Why
Whitespace-only (`"   "`), commas-only (`",,,"`, `" , , "`), and empty (`""`) inputs specified no slots at all but reported success. On the KVCache check endpoint those strings are truthy, so they bypassed the `if not slot_mapping` 400 guard, parsed to `([], None)`, and returned HTTP 200 with `num_chunks: 0` — while the same logical input (no slots) in another spelling got a 400. Now all slot-less inputs consistently return the invalid-format error and the endpoint answers 400.

Valid inputs are unaffected: `"1,2,3"`, `"[9,12]"`, `"1,2,3,[9,12],17,19"`, and whitespace-padded variants still parse as before.

## Verification
