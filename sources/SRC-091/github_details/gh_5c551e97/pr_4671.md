# [PR #4671] [MP][Bugfix] Bound client TCP connect attempts

## 正文

**What this PR does / why we need it**:

Fixes #4670

In MP mode on Kubernetes, the worker heartbeat can stay in degraded mode ~2 minutes after a restarted cache server is already healthy, delaying KV re-registration by the same amount. Root cause: `MessageQueueClient`'s DEALER sets no `zmq.CONNECT_TIMEOUT`, so a reconnect attempt whose SYN is silently dropped (racing the Service endpoint removal/restore during the pod restart) inherits the OS connect timeout (~127s on Linux) and monopolizes the socket — stalling every pending request, including heartbeat PINGs. Full mechanism in the linked issue.

This PR sets two socket options on the `MessageQueueClient` DEALER, before `connect()`:
- `zmq.CONNECT_TIMEOUT = 5000` ms (`CONNECT_TIMEOUT_MS`): a wedged connect attempt is abandoned and re-dialed within seconds instead of minutes. A healthy TCP handshake takes about a millisecond, so 5s only affects attempts that would otherwise hang. It is below the default 10s heartbeat interval, so one wedged attempt costs at most one missed ping.
- `zmq.RECONNECT_IVL_MAX = 1000` ms (`RECONNECT_IVL_MAX_MS`): zmq re-dials every 100ms by default with no backoff. This turns on exponential backoff (100ms → 200ms → … → 1s), so a down server is not re-dialed at a flat 100ms.

**Special notes for your reviewers**:

- Per review, the timeout is now a hardcoded constant instead of a `lmcache.mp.connect_timeout` option. That removes the factory / adapter / `ExtraConfigDefault` plumbing and the docs row. The change is now just `mq.py` and one test.
- Earlier review: the `_failed_pings` counter and throttled logging were removed.
- Only `tcp://` connects can stall this way. `ipc://` and `inproc://` connects fail fast, so the options have no practical effect there.
- Behavioral check with a pyzmq socket monitor against a blackholed endpoint (SYN dropped, no RST): the stock DEALER logs one `connect_delayed` and then stays wedged. With this change it logs `closed` → `retried` at 5.0s, re-dials after 100ms, then again at 10.1s after 200ms.
- `ruff check` / `ruff format` pass on the touched files.

### daitran-tensormesh · 2026-09-17

Rebased onto current `dev`. Since the last review the adapters build their request clients through `RequestClientFactory`, so `connect_timeout` is now threaded through the factory into the ZMQ transport (`RequestClientFactory.create(..., connect_timeout=...)` → `zmq_impl.create_request_client` → `MessageQueueClient`). It is an optional keyword like `context`; the gRPC transport manages connection attempts itself and ignores it. Added a factory-level test next to the socket test, and a sentence in `docs/design/v1/multiprocess/transport/request_transport.md`.

Scope is otherwise unchanged since the last review: bounded connect only (socket options + `lmcache.mp.connect_timeout` + tests + docs)

just a quick suggestion, what if we hardcode the timeout to something like 5? TCP should take a millisecond and should have exponential backoff .

### daitran-tensormesh · 2026-09-23

Agreed. Hardcoded to 5s (`CONNECT_TIMEOUT_MS` in `mq.py`) and dropped the `lmcache.mp.connect_timeout` knob with all its plumbing, so the PR is now just `mq.py` plus one test. On backoff: zmq doesn't back off by default (`RECONNECT_IVL_MAX=0` means a flat 100ms retry), so I kept `RECONNECT_IVL_MAX=1000`, which enables exponential backoff from 100ms up to 1s. With a socket monitor against a blackholed endpoint, the attempt is abandoned at 5.0s and re-dialed with backoff.
