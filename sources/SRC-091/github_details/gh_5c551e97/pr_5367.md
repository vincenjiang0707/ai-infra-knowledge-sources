# [PR #5367] [Observability] local disk: detect, drop and count stale index entries

state: open | updated: 2026-09-26T14:50:28Z

## 正文

**What this PR does / why we need it**:

`LocalDiskBackend` can list a key whose file is gone or truncated. This happens when
something other than LMCache deletes or shortens files in the cache directory
(tmp cleaners, operators, shared directories, remounts). Before this PR a read of such
an entry:

- `get_blocking`: raised `KeyError` and leaked the CPU staging buffer.
- prefetch (`batched_get_non_blocking`): raised `KeyError`, failing the whole batch.
- truncated file: `readinto` returned fewer bytes, which was not checked, so a
  **partly filled buffer was returned as a cache hit** (wrong KV served).
- all paths: the entry's bytes stayed in `current_cache_size`, so later puts evicted
  live keys to make room for space nobody held.

This PR:
- `read_file` returns whether the buffer was completely filled.
- On a missing file or short read, the entry is dropped under `disk_lock`, its space
  is released, the truncated file is removed, the controller gets an EVICT, and a new
  counter `lmcache:local_disk_stale_index_count` is incremented (once per entry, even
  with concurrent readers).
- Callers treat it as a miss. Prefetch returns the loaded prefix (matching the
  existing prefix contract in `prefetch_all_done_callback`) and releases the
  remaining buffers and pins.

**Special notes for your reviewers**:

- Detection is lazy (on read), so the counter is a lower bound on stale entries.
- A non-zero rate means something outside LMCache is changing the cache directory.
  That is worth alerting on, because before this PR the truncated case served
  corrupt KV silently.
- Found while reviewing the same file, not fixed here (follow-up PRs):
  1. `batched_get_non_blocking` returns on a staging-allocation failure without
     releasing `disk_lock`, and returns buffers that were never read.
  2. `remove()` called outside the eviction loop never lowers `current_cache_size`.
  3. `write_file` writes in place (no temp file + rename), so a crash can leave a
     torn file.
