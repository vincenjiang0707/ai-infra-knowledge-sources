## 正文

**What this PR does / why we need it**:

Consolidates the platform artifact build workflows into one reusable matrix workflow backed by a target-selected composite action. The existing platform-specific build, validation, artifact naming, and release paths remain available through explicit targets.

**Special notes for your reviewers**:

The unified workflow preserves target-specific runners, container environments, version handling, DockerHub authentication, artifact paths, and direct PR path filtering for CLI and CPU builds.

### VincyZhang · 2026-09-17

> 2\. all the targets have one job with `secrets: inherit` so now we have no granularity of access

The first problem can be solved by adding `continue-on-error: true`, then we can only publish the wheels that are successfully built. If no successful built wheels to publish, then fail the jobs.
I think your second point is the huge problem. Every leg in the matrix will inherit the same set of secrets, even if they don't use it. But still, it's a potential risk. There's no way to assign different set of secrets for different leg. So if this risk is not acceptable, we must use different reusable workflows
