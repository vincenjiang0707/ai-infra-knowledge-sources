This is the draft implementation discussing in https://github.com/LMCache/LMCache/issues/5073

> Problem
Hybrid models (Gemma 3, gpt-oss, Command-A, Qwen3-Next, ...) have object groups that only need the last w chunks for a prefix hit (SWA, Mamba). Older windowed chunks are never read back, and they are the big ones. default writes them all to L2. But skipping them isn't enough: once L1 evicts the window, the next turn pays a full prefill. We should commit only the last w chunks, at the turn boundary.

> Proposal
Two pieces that work together: stop writing windowed KV to L2, and copy the live window to L2 at natural timing (turn boundaries) so cross-turn prefix reuse isn't lost.

### okdshin · 2026-09-19

Hi @ApostaC, thanks for taking a look. Let me explain why this is more than a store policy.

You are right that the L2 write reduction itself comes from a store policy. `defer_windowed` is exactly that: it keeps windowed object groups (SWA, and align/all-mode Mamba / linear attention) out of the L2 write-through path and writes whole-prefix groups as `default` does.

  What a store policy cannot do is pick *which* windowed chunks to keep. It sees `select_store_targets(keys, adapters)` for the keys that just finished writing to L1, one batch at a time as the sequence grows (in the default mode, while the request is still running).
  Nothing in that batch says where the window will end, so the policy can only write every windowed chunk (which is `default`) or none of them. The last `w` chunks are only known relative to a boundary the session holds, which is why the commit lives on `END_SESSION`.
  
  Three things the commit needs are not available on the store path:
  
  1. **Chunks already in L1 are not in the batch.** The store path skips chunks that L1 already holds, so a short follow-up turn contributes fewer than `w` new chunks. The rest of the window `[p - w, p)` was written to L1 by an earlier request. Under `defer_windowed` those
  chunks reach L2 only through a commit, and the earlier request may not have committed them (aborted, length-capped) or may have committed a window that ended somewhere else (a different request sharing the prefix). The commit path resolves the window through the
  session's hash chain and copies whatever L1 holds, regardless of who wrote it.
  2. **How the request finished.** A store policy cannot tell a completed turn from an abort or a length cap, so it would commit windows no follow-up will ever resume from.
  3. **Where the prompt ends.** Templates that re-render earlier assistant turns (Qwen3 drops `<think>...</think>`) need the window at the end of the prompt, not at the end of the generation. That boundary is in the session (`lookup_end`), not in `ObjectKey` or the store
  batch.

  So the split of responsibilities is: the store policy decides what never needs to go to L2, and the commit at `END_SESSION` decides which window still must, using session state the store path does not have.

### uraniumchonk · 2026-09-25

Thanks for #5073 and the detailed write-up in #5102 — the three things the store path can't see are exactly right, and we hit the same class of problem in production. I'm adding **measured GDN (Mamba linear-attention) numbers**, because the 7.2x estimate in this thread comes from plamo3 (SWA/FA) and I don't see a Mamba/align measurement yet. On GDN the effect is sharper: the window is effectively **w = 1**.

### Setup

- vLLM 0.28.0, `LMCacheMPConnector` (`kv_role=kv_both`), TP=4, 4x RTX 3090 24GB
- Qwen3.8-27B GDN hybrid: 64 layers = 48 `linear_attention` + 16 `full_attention`; plus DFlash2 speculative decoding (its own 5 layers)
- `--block-size 1600`, `--chunk-size 1600`, `--mamba-cache-mode align`, `--kv-cache-dtype fp8_e4m3`
- LMCache 0.5.4rc5, MP mode, L1 72 GiB, L2 POSIX on NVMe (`nixl_store_dynamic`)

### Measured chunk composition (byte-exact)

The LMCache server logs 15 kernel groups; every group costs 512 B per layer per token:

```
48 GDN layers  (kv=1, hs=512, int8)  x 1600 x 512 = 39,321,600 B   <- 70%
16 attn layers (kv=2, hs=256, uint8) x 1600 x 512 = 13,107,200 B
 5 drafter     (kv=2, hs=256, uint8) x 1600 x 512 =  4,096,000 B
                                        total     = 56,524,800 B
```

which matches the observed chunk size exactly. The `1600` in the GDN group's `(nb=2160, 1600, 1, 512)` is the align-mode view, not a token axis — consistent with vLLM's own accounting:

```
2160 x 819,200 x 5 = 8,847,360,000   vs   kv_cache_memory_bytes = 8,850,000,000
```

(0.03% apart, pure page padding.) So LMCache is not over-storing relative to what vLLM registers — it faithfully snapshots every 1600-token boundary, and for GDN only the last one is ever read back.

### Why the commit (not just the store policy) matters — quantified

`defer_windowed` alone suppresses L2 writes, but the window still lives in L1, and when L1 loses it the next turn pays a full prefill. Measured on our side:

- three concurrent 8000-token requests -> `l1_memory_usage_bytes` = 3.62 GB
  (= 3 req x 5 chunks x 4 ranks x 53.9 MiB; L1 keeps one chunk per rank)
- a single 256K-token session therefore costs **~34.5 GiB of L1**; three concurrent ones need **~103.5 GiB**, which does not fit a 72 GiB pool
- over 2 hours: 266 completed prefetches, of which **69 (26%) took >2 s, worst case 29.9 s**

So on GDN/align the working set is 3.29x larger than it needs to be (69/21 layers), and the eviction tail shows up directly as prefill/latency rather than as an abstract memory number. That is the concrete cost of not having the commit at the boundary.

### GDN is w=1, sharper than SWA

For SWA the last `w` chunks are useful (w = window size). For GDN the recurrent state is cumulative, so a prefix hit needs only the **boundary snapshot** — w = 1. Keeping older snapshots is pure overhead, and they are the big ones (70% of the chunk).

### One gap I'd ask #5102 to cover: L1-side eviction

Your point 1 ("chunks already in L1 are not in the batch") is the right framing, but it assumes L1 holds the window. In our case a 72 GiB L1 cannot hold three long sessions, and the *stale* GDN snapshots for the same prefix keep occupying it. Suggestion: once a newer GDN snapshot for the same prefix is written, older GDN snapshots for that prefix should be **evicted (or dropped) from L1 first** — they can never be read again. Without this the win stays L2-write-only and the L1 footprint is unchanged.

Worth a knob too: keeping only the boundary snapshot is optimal on space but may cost hit rate when several turns share a long prefix. A "keep one GDN snapshot every K chunks" parameter would let operators trade space for hit rate. Here K=1 is clearly right; SWA-style models may want K>1.

### Sequencing blocker

`--separate-object-groups` looks like it is on this path, and **#4972** reports fp8 / turboquant L2 serde crashing on that flag, with an environment very close to ours (vLLM 0.28.0, Qwen3.8-27B GDN hybrid, 48 linear + 16 full). If #5102 depends on that flag, users on fp8 + L2 like us cannot adopt it until #4972 is fixed. Worth sequencing the two.
