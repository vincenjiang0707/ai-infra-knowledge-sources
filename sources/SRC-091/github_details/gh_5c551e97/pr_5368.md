**What this PR does / why we need it**:

`L2_STORE_COMPLETED` already carries the bytes each adapter reports in
`L2StoreResult.bytes_transferred`, but only the throughput histogram used it. There was
no counter of how much each L2 backend actually writes. For flash-backed adapters
(`fs`, `raw_block`, `nixl_store` on NVMe) that is the number that determines drive wear.

This PR adds `lmcache_mp.l2_store_bytes` (attr: `l2_name`), a counter incremented by
`bytes_transferred` on each store completion:

- Failed tasks add nothing.
- Keys the adapter skips because they are already stored add nothing.

So it measures bytes the adapter wrote, not bytes LMCache offered (`total_bytes` on
`L2_STORE_SUBMITTED`). Drive writes per day for a backend on a device of `C` bytes:

```promql
increase(lmcache_mp_l2_store_bytes_total{l2_name="fs"}[1d]) / C
```

**Special notes for your reviewers**:

- The metric comes from data the controller already emits. No controller or adapter
  code changes.
- It counts bytes the host wrote, not bytes the device wrote. Filesystem overhead and
  SSD write amplification are not included, so real NAND wear is higher. The docs
  call it write volume, not NAND writes.
- Adapters that never fill in `bytes_transferred` (it stays `0`) are undercounted.
  The design doc says so.
- The two zero-byte tests (failed store, all keys already stored) pass with or without
  the change on purpose. They guard against the counter ever counting writes that
  didn't happen.
- Sphinx build: 31 warnings, the same as `dev`, none in the changed files.
