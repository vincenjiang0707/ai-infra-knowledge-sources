## 正文

**What this PR does / why we need it**:

Adds a pure compaction-plan builder for experimental GPU-native token dropping,
under `lmcache/integration/vllm/experimental/token_dropping/`.

Token dropping decides *which* KV entries of a request survive. Compacting the
request's paged KV then needs those positions turned into physical slot copies.
`build_kv_compaction_plan()` does only that translation:

- input: `request_block_ids`, `retained_kv_sequence_indices`,
  `current_kv_sequence_length`, `tokens_per_block`
- output: `move_source_kv_slot_ids`, `move_destination_kv_slot_ids`,
  `compacted_kv_sequence_length`

Contract: `retained_kv_sequence_indices` are indices into the request's
**current** KV sequence, not original logical token positions and not physical
slot ids. Only real copies are emitted -- an entry already sitting in its
compacted slot produces no move, so keeping everything yields an empty plan and
an unchanged compacted length.

This is the first PR of the GPU-native token dropping design; it is deliberately
much smaller than that design.

**Special notes for your reviewers**:

Non-goals here -- this PR does **not** move KV bytes, implement R-KV, capture
queries, integrate with the KVConnector or dispatcher, reclaim scheduler blocks,
add a config/feature flag, or touch vLLM. No torch or CUDA dependency is
introduced; the planner is integer arithmetic over block ids.

It adds only new files. No existing production file is modified.

The argument invariants are internal programmer-error checks, so they use
`assert` per coding_standards §2.2 ("Only use `assert` for development-time
invariant checks that indicate programmer errors"), not user-facing validation.
