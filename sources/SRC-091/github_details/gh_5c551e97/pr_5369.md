## 正文

Fixes #5350.

StoreController learns about a freshly written L1 key from on_l1_keys_write_finished but takes its read lock later, on the store loop thread. In that window the key is resident and unlocked, so L1EvictionController may discard it; reserve_read then returns KEY_NOT_EXIST and the chunk is silently never written to L2, even when L2 has room. Under L1 pressure this shows up as persistent partial hits and re-prefill of the same tails.

Add write-back holds to L1Manager:
- register_write_back_listener(): every admitted non-temporary key reported to the listener gets one hold, taken in the admission critical section before the listener is notified.
- is_key_evictable() is false while a hold is outstanding. delete() ignores holds, so explicit deletes and post-store L1 deletions keep their behavior.
- release_write_back_holds() drops one hold per key and publishes no events. Holds are TTL locks (read TTL), so a leaked hold expires.

StoreController registers as a write-back listener and releases the holds once every target adapter has taken its read lock, and on stop for keys still queued.

The new CPU-only regression test reproduces the data loss on dev deterministically (write, evict before the store loop runs, key never reaches L2) and passes with this change.
