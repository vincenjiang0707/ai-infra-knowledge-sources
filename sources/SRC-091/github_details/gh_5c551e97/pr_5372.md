# [PR #5372] [MP][L2] fs_native: register persisted files at startup so restarts respect max_capacity_gb

## 正文

**What this PR does / why we need it**:

Fixes #5371.

`fs_native` chunk files persist across a server restart and are still served (lookup is a `stat` on the file), but the new process never registered them. They did not count toward `max_capacity_gb`, and the eviction policy never saw them, so they were never evicted. Each restart could strand up to a full cap of files, and disk usage grew without bound.

This PR registers persisted objects at startup:

- **Interface:** new `L2AdapterInterface.recover_persisted_objects() -> int` (default no-op, returns 0), delegated by `SerdeL2AdapterWrapper` and `FaultInjectL2Adapter`.
- **Storage manager:** `StorageManager` calls it for each adapter **after** the L2 eviction states have registered their listeners, both at init and in `add_l2_adapter`, and logs the count and resulting usage.
- **Native adapter:** `NativeConnectorL2Adapter` takes an optional `persisted_object_scanner`. `recover_persisted_objects()` records each object in `_key_sizes`, so eviction deletes decrement usage, and announces it through `_notify_keys_stored`, so usage counts it and the eviction policy tracks it.
  - Objects are announced newest first: LRU/ARC insert a batch in reverse, which puts the oldest file at the eviction head.
  - Keys already tracked, e.g. by a store that completed meanwhile, are skipped.
- **`fs_native`:** gains `recover_on_start` (default `true`) and a scanner that `os.scandir`s `base_path`.
  - It decodes `.data` names with the existing `fs_l2_adapter._filename_to_object_key` (the C++ connector writes the same reversible names) and takes `st_size` and `st_mtime`.
  - It registers only **regular files whose name is exactly the canonical filename of the key it decodes to**. A foreign name that happens to parse would be deleted under a different path, so it could never be evicted.
  - It skips `.tmp` files, directories, symlinks and entries that can't be `stat`-ed. If `base_path` can't be listed, it logs an error and skips recovery rather than failing startup.
- **Where recovery is skipped (warning logged).** `StorageManager` decides this on the adapter's effective (outermost) config, so wrappers such as `fault_inject`, which keep `shared` and `eviction` on their outer spec, can't bypass it:
  - `shared: true`: another live instance may be serving those files, and this process would evict them.
  - `IsolatedLRU` eviction: quotas are registered over HTTP after startup, and a salt with no quota is evicted entirely on the first pass, so every recovered salted file would be deleted.
- **`add_l2_adapter`:** recovers after the listeners and the eviction state are registered, but **before** the store and prefetch controllers can issue work against the new adapter.

**Special notes for your reviewers**:

- **Default:** `recover_on_start` defaults to `true`, which changes startup behaviour. If leftovers exceed the watermark, eviction runs straight after startup, and that is the point. `false` keeps today's behaviour.
- **Scan cost:** the scan is synchronous during `StorageManager` init. On a real cache of 298,492 files (849 GiB, XFS on NVMe RAID-0) it took 3.0 s to scan and ~0.5 s to register. A background scan could be a follow-up if very large directories matter.
- **Private import:** `_filename_to_object_key` / `_object_key_to_filename` are imported from `fs_l2_adapter` (lazily, like the factory's existing lazy import, to avoid a cycle). The NIXL store agents already import the same private helpers across modules. Promoting them to a public codec would touch 7 files, so it's left out of this PR.
- **Scope:** other persistent adapters (`fs`, `nixl_store`, ...) likely have the same gap. The hook is generic, but this PR only implements it for `fs_native`.
- **Validated on a real deployment.** The patch was applied to 0.5.6rc1 (commit 9a7b6050; it applies cleanly there) and the server restarted over a 911.7 GB `base_path` with `max_capacity_gb` lowered to 800:

  ```
  fs_native: found 298492 persisted objects (849.44 GiB) in /lmcache/l2 in 3.0 s (0 entries skipped)
  L2 adapter 0: registered 298492 objects recovered from persistent storage (usage 912076931072 bytes)
  L2 usage 1.06 above watermark 0.90; triggering eviction.
  L2 usage 0.96 above watermark 0.90; triggering eviction.
  ```

  - **Settled usage:** 0.86. The disk went to 738.85 GB, with 738.78 GB tracked (within 0.01% of `du`).
  - **Order:** the evicted files were the oldest by mtime.
- **Tests:** `tests/v1/distributed/test_fs_native_restart_recovery.py`, 21 tests.
  - The scanner: sizes and mtimes; skips `.tmp`, foreign names, directories and symlinks with chunk names, and non-canonical names; a listing error recovers nothing and logs.
  - Adapter recovery: usage, oldest-first LRU order, deleting a recovered object releases its bytes, no double count after a real store, and the no-scanner case.
  - Config parsing.
  - `StorageManager` end-to-end tests using the real FS extension (skipped without it):
    - leftovers are accounted, at init and via `add_l2_adapter`;
    - leftovers over the cap are evicted oldest first, waiting until the accounting matches the files still on disk;
    - `shared: true` and `IsolatedLRU` skip recovery (nothing accounted, nothing deleted), both on a direct `fs_native` spec and on a `fault_inject` wrapper around it;
    - `recover_on_start: false` leaves leftovers unaccounted.
  - I checked that each guard test fails when its guard is removed; with the `StorageManager` skip disabled, all four shared / IsolatedLRU cases fail. The `add_l2_adapter` ordering has only a functional test (its race is not reproduced deterministically).
  - **End to end:** `tests/v1/multiprocess/test_fs_native_restart_recovery_e2e.py`, 9 tests x {buffered, O_DIRECT}; needs CUDA and the FS extension. The O_DIRECT variant runs when `LMCACHE_TEST_ODIRECT_DIR` points to an O_DIRECT-capable filesystem. Each test runs the real MP server CLI (`lmcache.v1.multiprocess.http_server`) as a subprocess with `fs_native`, stores real KV blocks through the request client, restarts over the same `base_path`, and checks `/status` and bit-exact retrieval into fresh GPU blocks:
    - **Happy path:** recovered usage equals the previous run's bytes and the data is served from L2 (L1 is empty after the restart); two restarts plus re-storing every key don't double count; new writes add on top.
    - **Eviction:** restarted with usage at 0.95 of the cap, exactly the older batch (by mtime) is evicted, and the newer batch is still found and served bit-exactly.
    - **Opt-outs:** with `recover_on_start: false` or `shared: true` and a tiny cap, nothing is counted or deleted, and the files are still served.
    - **Adversarial:**
      - Foreign names, an in-flight `.tmp`, a non-canonical but parseable name, and a directory and a symlink carrying valid chunk names are ignored, never deleted, and don't stop eviction of the real files.
      - A truncated chunk file isn't served as KV data, and the server keeps serving the other keys.
    - **Known limitation:** a recovered file deleted externally stays accounted. The preconditions (stores complete, an eviction pass ran) are asserted normally; only the final accounting mismatch is `xfail`, and the test fails if the limitation goes away.
    - Each key's chunk file is recorded as it is written, rather than inferred from mtimes. The re-store test waits for the `/metrics` store-completion counter before comparing usage; I checked that it fails if re-stores charge their bytes again.
    - **Results on 0.5.6rc1 plus this change, on NVMe XFS for O_DIRECT:** 16 passed, 2 xfailed.
    - **Against stock 0.5.6rc1, no patch (buffered):** all 5 feature tests fail. The opt-out and truncated-file tests pass, as they should, since they check behaviour that matches stock.
  - Existing tests in `test_native_connector_l2_adapter`, `test_fs_native_l2_adapter_config`, `test_runtime_adapters`, `test_l2_adapter_base`, `test_fault_inject_l2_adapter`, `test_storage_manager_l2_keys` and `test_l2_adapter_factory` still pass (185 passed, 1 skipped). ruff, isort and mypy (repo config) are clean on the changed files.
- **Docs:** `fs_native.rst` states that recovery assumes this server is the only one using `base_path`, that shared directories need `"shared": true`, and when recovery is skipped.
- **Known limitations, left out of scope (existing behaviour that recovery makes more visible):**
  - A delete that reports `False` (e.g. the file is already gone) leaves the key and its bytes accounted indefinitely.
  - The `/` to `-SEP-` filename encoding isn't injective: a model name that literally contains `-SEP-` decodes to a different key.
  - Recovery's `L2_KEYS_STORED` events fire during `StorageManager` init, before the coordinator's cache-event subscriber registers, so the coordinator doesn't learn about recovered keys.
  - Very large directories are scanned into one list and registered in a single notify.
  - `fs_native`'s `relative_tmp_dir` isn't validated the way the `fs` adapter's is.
  - The `fs` adapter has the same restart gap.
