## Summary
This addresses part 1 of #5339 (the vLLM client-side `_returned_finished` retention). Part 2 (sidecar prefetch job / completion state) is intentionally **not** addressed here — see the issue discussion for why (native `Bitmap` memory lifecycle needs a maintainer-confirmed ownership handoff at session end before it's safe to touch).

- `LMCacheMPWorkerAdapter._returned_finished` tracks every request id ever reported as `finished_sending`, to keep `get_finished` from re-reporting an id after `finished_stores`/`previously_finished` have already been drained for it (`_update_and_get_finished_store`). That drain has no equivalent for `_returned_finished` itself, so it grows for the entire worker process lifetime.
- Fix: replace the plain `set[str]` with a small bounded LRU container (`_BoundedIdSet`, `max_size=100_000` by default) that evicts the least-recently-added id once the cap is exceeded.
- This deliberately does **not** try to answer whether vLLM's engine can re-mention an id after it's fully retired (one of the open questions in the issue) — it converts unbounded growth into bounded memory either way, at the cost of a very small, tunable risk of re-reporting an id whose entry has aged out of the cap. If that risk needs to be zero, this can be revisited once the vLLM connector contract question is answered.

## Test plan
- [x] Added `test_bounded_id_set_evicts_oldest_beyond_capacity`, directly exercising `_BoundedIdSet`'s eviction, recency-refresh, and high-volume-never-exceeds-cap behavior.
- [x] Added `test_returned_finished_stays_bounded_across_many_requests`, driving `LMCacheMPWorkerAdapter._process_finished_stores` 500 times with distinct request ids against a small cap and confirming the adapter's own set stays bounded.
- [x] Manually verified the standalone `_BoundedIdSet` implementation (identical to what's in this diff) against edge cases: single-eviction-at-cap, recency-refresh-on-re-add, and a 10,000-item high-volume load that never exceeds a 100-item cap.
- Was unable to run this repo's full test suite in my environment (native extension build for `nvtx`/nvtx-adjacent deps requires Cython, which isn't available here) - the two new tests only touch pure-Python adapter logic and don't depend on the native compute backend, so I'm confident in them from static + standalone validation, but flagging this so a reviewer can run the full suite if that matters here.
