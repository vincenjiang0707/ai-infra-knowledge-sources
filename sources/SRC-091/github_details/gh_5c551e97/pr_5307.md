# [PR #5307] [MP] Stream CPU KV events for eviction-aware routing

## 正文

**What this PR does / why we need it**:

Follow-up to #5076. Refs #3661.

#5076 announces completed CPU stores, but routers can retain stale placements after LMCache evicts those chunks. This PR delivers CPU/L1 store and removal events through vLLM's existing KV-event pipeline, allowing Dynamo and llm-d to update their cached-prefix placements.

For example, if workers A and B cache prefix P and A evicts it, delivery of `BlockRemoved(P, medium="CPU")` withdraws A's placement. The router can then route P to B.

LMCache MP-to-worker delivery supports gRPC and ZMQ subscriptions, without periodic KV-event fetches. 

**Event flow**:

```text
LMCache MP server
  CPU store completes / CPU chunks are evicted
                     |
                     v
                 EventBus
                     | callbacks + token/parent information
                     v
              ManagementModule
        [bounded, sequenced event log]
                     |
             +-------+--------+
             |                |
        gRPC stream      ZMQ stream
                         + acknowledgments
             |                |
             +-------+--------+
                     |
                     v
vLLM worker: LMCacheMPWorkerAdapter
  Background receiver
  [CPU event buffer + metrics]
                     |
                     | vLLM engine step drains the buffer
                     v
  LMCacheMPConnector
  BlockStored / BlockRemoved, medium="CPU"
                     |
                     v
vLLM scheduler
  Existing KVEventAggregator + ordered batches
                     |
                take_events()
                     |
                     v
  Existing vLLM KV-event publisher                                                                                                                                                           04:35:21 [28/354]
                     |
                     | ZMQ
                     v
               Dynamo / llm-d
          Update cached-prefix placements
```

**Implementation**:

- Within each vLLM engine, one rank per attached MP server opens `subscribe_kv_events`. Event callbacks wake waiting readers; idle subscriptions do not occupy ordinary request workers.
- Reuses `ManagementModule`, the existing event bus, and a bounded replay log. Completed server writes identify the chunks actually stored; store records require known tokens and parent hashes.
- gRPC uses native server streaming. ZMQ retains the subscription request ID and acknowledges consumed batches to limit in-flight responses.
- Disconnect, restart, and event loss withdraw previously announced CPU placements. Disconnects reopen the subscription. Unsupported or disabled channels retain completed-store reporting.
- Retains `KVEventAggregator` and its worker bookkeeping. Ordered batches preserve transitions such as `store -> remove -> store`.
- Exposes buffered-event count and generated, drained, received-batch, and resync counters, making a missing or slow vLLM drain visible.

The MP coordinator remains a separate consumer of storage events; it is not a forwarding hop in this path. The change stays in existing files and the MP path, with no separate vLLM patch required.

**Special notes for your reviewers**:

Enable the observability bus and vLLM KV events, and match hash algorithms and chunk geometry. The server retains 32,768 event records by default.
`--kv-event-log-size=0` or `lmcache.mp.kv_event_stream=false` disables the subscription. 
Both MP transports advertise `kv_event_stream`.

**Idle reception and publication are separate:** once subscribed, the worker receives events while idle, but vLLM drains and publishes them during engine steps. Router placements can therefore remain stale until stepping resumes.

This PR covers CPU/L1 events.

**Validation**:

- Selected regression: **1,497 passed, 13 skipped**.

| Routing test | MP server to worker | vLLM publisher to router | Result |
| --- | --- | --- | --- |
| Dynamo | ZMQ subscription | ZMQ | 6/6 correct routes with full 4,000-token hits; all 9 checks passed |
| llm-d standalone EPP + Envoy | gRPC stream | ZMQ | 6/6 correct routes with full hits; all 11 routing and 7 event-accounting checks passed |

Both runs reported zero event errors. In the llm-d test, GPU copies were evicted before routing; the surviving MP server performed **3,000 L1 chunk reads**, confirming CPU-cache use. All 793 tracked LMCache Python files matched in each of the eight MP/worker containers.

Applicable pre-commit checks passed. Sphinx completed with the same 30 existing diagnostics.

The serving profile uses two independent Qwen2.5-7B engines, TP=2 each, DP=1, unsalted sha256_cbor hashes, chunk size 16, and private 2 GiB LMCache-driven L1 caches. vLLM is `0.27.2rc1.dev111+g44fc57d7b`; Dynamo uses 1.5.0 workers and the `1.5.0.dev20260821` frontend. llm-d uses unmodified EPP `b16fa8db`, Envoy `v1.33.2`, native vLLM HTTP servers, file discovery, and speculative indexing disabled.
