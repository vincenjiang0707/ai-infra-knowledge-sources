# [PR #5105] [MP][Experimental] Share a fixed Device-DAX L1 pool across MP servers

state: open | updated: 2026-09-27T02:20:51Z

## 正文

**What this PR does / why we need it**:

Private L1 allocators cannot safely share the same physical pool. 
This patch adds a separate Memory Coordinator that owns keys, write tokens, and offsets.
Each MP maps its host-local view of the shared Device-DAX window.
KV payloads never pass through the coordinator.

### How it works

Store one shared cache copy. Other workers reuse it.
Each MP can report to the MP Coordinator for a fleet-wide view.
It asks the separate Memory Coordinator where it can write or read shared KV blocks.

```text
FLEET VIEW (optional): registration, heartbeats, cache reports

+-------------+       +-------------------------+       +-------------+
| Prefill MP  |------>| MP Coordinator          |<------| Decode MP   |
+-------------+       | Workers, cache, capacity|       +-------------+
                      +-------------------------+

MEMORY CONTROL (required for shared L1): keys and offsets; no KV bytes

+-------------+       +-------------------------+       +-------------+
| Prefill MP  |<----->| Memory Coordinator      |<----->| Decode MP   |
+-------------+       | Keys, space, ready state|       +-------------+
                      +-------------------------+

DATA: KV bytes bypass both coordinators

+-------------+       +-------------------------+       +-------------+
| Prefill GPU |------>| Shared DAX / CXL pool   |------>| Decode GPU  |
| Host A      | write | One copy per KV object  | read  | Host B      |
+-------------+       +-------------------------+       +-------------+
```

The same MP processes appear in both control rows. 
The coordinators do not call each other in this patch; MPs connect to each separately.

- **MP Coordinator:** tracks workers and reported cache locations/capacity.
  Reports can lag. It does not allocate shared space or make blocks readable.
- **Memory Coordinator:** owns shared allocations and committed block locations.
  Every shared read checks it, even if the fleet directory reports a hit.
  Its status reports allocated pool bytes, including space no longer usable.

Fleet registration uses `--coordinator-url`; cache reports use `--coordinator-event-reporting`.
Shared-memory access uses `--l1-coordinator-endpoint`. The MP Coordinator is optional for this data path.
Keep observability enabled for cache reports.

Each MP process runs the copies for its GPU. GPU working copies still exist;
the shared pool avoids separate cached copies for each MP.
One worker pair is shown. 2P4D means 2 prefill and 4 decode workers;
4P2D means 4 prefill and 2 decode workers.

### When a block can be reused

```text
STORE
Reserve space -> Copy GPU KV to DAX -> Wait for the copy
              -> Make writes visible to other hosts -> Mark ready

REUSE
Find a ready block -> Check block metadata -> Refresh the local memory view
                  -> Check the engine layout -> Copy DAX KV to the GPU
                  -> Release the local read reference after the copy finishes
```

Incomplete writes are never marked ready. Read references keep the mapping alive until the GPU copy finishes. 
Marking a block ready is not a disk backup or a recovery checkpoint.

- Keep committed objects immutable. Never reuse extents, including aborted writes.
- Fence clients on epoch changes or ambiguous write outcomes. A persistent startup marker prevents an uncoordinated allocator restart.
- Reuse existing MP events to report shared placement and capacity once.
- Add the design in `docs/design/v1/shared_devdax_l1.md` and the setup/operations guide in `docs/source/mp/shared_l1.rst`, linked from the MP overview.

**Special notes for your reviewers**:

This is an experimental TP1 path: one fixed pool, `lmcache_driven`, `noop` eviction, and a platform-qualified visibility library. It does not support L2, hybrid DRAM/DAX, GDS L1, MP P2P, CacheBlend, QStore, engine-driven transfer, or trace replay. Defaults keep private L1 unchanged.

Stop admission and drain every worker before shutdown or reset. Keep worker reaping disabled. Remove the specific startup marker only after all mapped workers have stopped. Epoch checks cannot revoke CUDA mappings. There is no automatic reclamation, persistence, HA, or restart recovery. Bearer HTTP requires a trusted network or TLS termination.

Hello @jooho-XCENA, Thanks! I agree that MP-to-MP would be the better comparison. 
I did run this one in the switched setup. I will make the comparison then after shared feature is done.

For uses_shared_l1 and abort_write, my current view is that we should avoid defining a broad shared-L1 contract too early. In #5105 those are currently implementation-level signals needed to make the native shared-pool semantics correct. 
I’d prefer to first stabilize the minimal lifecycle we actually need "reserve/write/commit-or-abort/read/reclaim" and then extract the smallest common interface that multiple backends genuinely share.

For the broader boundary, I think we should separate two responsibilities:

Cross-application / cluster-level CXL resource management: deciding which workload gets which shared-memory region, quota, isolation, resizing, etc.

LMCache-specific KV management: allocation within the region, KV ownership, reservation/commit/abort, eviction, generation, and object lifecycle.

My preference is for LMCache to own the second part.

If Maru’s main value is managing a switched CXL pool across multiple applications, I think that functionality fits more naturally below LMCache, potentially even through a Kubernetes/DRA-style resource-management layer. 
LMCache could then receive an allocated/mapped shared-memory region and manage KV semantics entirely inside that region.

That would also make the native Device-DAX path and Maru path easier to reason about:

Kubernetes / fabric manager / Maru -> provides a shared-memory resource

LMCache shared L1 -> manages KV objects and lifecycle inside that resource

So the main architectural question for me is: what functionality does the Maru MP L1 path need to provide inside LMCache beyond exposing/managing the shared memory resource itself?

If there are Maru-specific capabilities that cannot be expressed that way for example fabric-level placement, topology-aware allocation, cross-host mapping, or another primitive LMCache cannot provide natively  I think those would be useful to identify explicitly. 
That would help us define a minimal interface without duplicating lifecycle ownership between Maru and LMCache.

For sure, I will make the sharing interface when it is enough to mature.
