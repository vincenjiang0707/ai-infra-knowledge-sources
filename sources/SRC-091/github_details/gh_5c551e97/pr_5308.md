# [PR #5308] [Perf][MP] Move LMCache-driven transfer to cudaMemcpyBatchAsync 

source: https://github.com/LMCache/LMCache/pull/5308
state: closed | updated: 2026-09-24T17:32:51Z
labels: full

## 正文

**What this PR does / why we need it**:

Adds a second copy path to the MP server's LMCache-driven STORE/RETRIEVE transfer.
Instead of staging each chunk through a GPU temp buffer and scattering it with the
block transfer kernel, eligible object groups move straight between the pinned host
object and the engine's paged KV buffers with one `cudaMemcpyBatchAsync` call per
chunk -- no staging buffer, no SM kernel. The kernel path remains the fallback and
still handles every layout.

Motivation: on Kimi-Linear-48B (TP 2, 1024-token MLA pages, 128k prefix) an nsys A/B
shows the kernel path's scatter kernels each waiting ~1.6 ms to be scheduled on a GPU
busy with vLLM's prefill -- about 50 ms of stream idle per 128k retrieve -- while the
copies themselves already ran at line rate. With 1024-token MLA pages each
(layer, block) of a chunk is a contiguous ~1 MB run, so the copy engine can move it
directly and the SMs are left to vLLM.

Changes:

- `csrc/cuda`: `execute_direct_copy_transfer`, `batch_memcpy_supported`,
  `direct_copy_format_supported`, plus the `DirectCopyGroupSpec` / `DirectCopyObject`
  descriptors. One `resolve_block_addressing` switch turns each eligible
  `EngineKVFormat` into a base-pointer rule and three byte strides, mirroring
  `calculate_engine_global_offset` (including the padded `block_stride_elems` of
  pool-shared MLA rows), so the per-entry loop has no format branches. Host ranges are
  split at `LazyMemoryAllocator.PIN_CHUNK_SIZE` boundaries, since each pin chunk is a
  separate `cudaHostRegister` region. Requires CUDA runtime and driver >= 12.8;
  compiled out on HIP.
- `object_group_transfer.py`: `_HAS_BATCH_MEMCPY_ASYNC` resolves build- and
  driver-level support once at import; `direct_transfer_supported` then checks each
  object group (host block ids present, no GDS-backed object, every kernel group on a
  token-major layout whose paged block is one contiguous run).
  `transfer_kv_per_object_group` consults both before the staged fast path and hands
  eligible groups to `run_direct_transfer`, which mirrors the staged planner's window
  and `skip_first_n_tokens` logic. Ineligible layouts (HND, blocked-scale,
  (K,V)-tuple), GDS objects and older builds fall back to the kernel path; an
  ineligible layout is logged once per format.
- `transfer_kv_per_object_group` gains `block_ids_host`, the host-list view of the
  same downsampled ids already passed as device tensors. The direct path resolves
  every address on the CPU; callers that must stay on the kernel path leave it empty,
  which is how `qstore` keeps its current behaviour.
- `BaseCacheContext.get_kernel_group_offset_in_object` and
  `get_kernel_group_kv_pointer_list` (the latter cached on `GPUCacheContext` so it
  does not sync the stream).
- Torch fallbacks for the two new query functions, keeping `test_cuda_ops_parity`
  green.

There is no configuration flag: the direct path is taken automatically whenever the
build, the driver and the layout allow it, and falls back otherwise.


**If applicable**:

- [x] this PR contains user facing changes - docs added
- [x] this PR contains unit tests
  - `tests/v1/multiprocess/test_direct_copy_transfer_gpu.py`: bit-exact parity with
    the kernel path for every eligible format, both directions, a skipped block
    prefix, two-group objects, a padded MLA stride, pin-boundary splits, and rejection
    of ineligible layouts / out-of-range ids.
  - `tests/v1/multiprocess/test_direct_copy_planner_gpu.py`: end to end through
    `transfer_kv_per_object_group` with a real `GPUCacheContext` and
    `LazyMemoryAllocator`, including a Kimi-like 1024-token MLA geometry.
  - `tests/v1/multiprocess/test_direct_transfer_dispatch.py`: eligibility and dispatch
    (CPU only, no CUDA build needed).
