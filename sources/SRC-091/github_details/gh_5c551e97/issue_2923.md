# LMCache Q2 Roadmap

With the influx of AI generated code, LMCache has adopted two strategies: 
- the introduction of cursor bugbot which will serve as a first pass on PRs, which will ultimately end up still requiring two maintainer approvals.
- PRs that are overly large in scope or obviously generated by AI without any effort put into keeping the code up to standard and without a human generated PR description may end up not being reviewed. Stricter reviews are **highly recommended** as code becomes easier to generate.

## 1. LMCache MP and CLI Production Readiness

Q1 marked the development of LMCache MP mode, which is the future of LMCache, along with the LMCache Operator. Much of the documentation, observability, CI/CD, and fault tolerance that will make LMCache production ready is still missing.

- [ ] Advanced L2 store/prefetch policies 
- [ ] Dynamic prefetch admission controller
- [x] Non GPU wheels for only CLI
- [x] AMD support for MP mode
- [x] Comprehensive documentation for non-GPU CLI usage (like kubectl)
- [x] LMCache recipes & tutorials for popular open models and HW
- [x] Production deployment best practices scaling, tuning, monitoring recommendations

### Fault Tolerance:

- [x] Stress test high when requests fail, serving engines go down, LMCache goes down, high concurrency, high preemption, etc.
- [x] Add reproducible fault tolerance CI/CD

### Observability:

- [ ] Worker affinity & health check stabilization
- [x] K8s operator
- [x] Observability setup recipes like OTel collector + Grafana configuration

## 2. Core Features and KV Cache Optimizations (lead by @KuntaiDu)

LMCache aims to be the habitat of all of the latest KV Cache related research such as KV compaction, compression, codec, blending etc. providing an interface to plug in these optimizations without hacking into serving engines like vllm or hf transformers. A clean and modular interface along with many of the long awaited LMCache features like CacheBlend will finally hit the Open Source Community in the MP mode in Q2!

- [ ] Release MP mode CacheBlend support
- [x] Interface to support token dropping in KV cache (sparse KV cache optimizations)
- [x] Interface to support KV cache quantization (e.g., TurboQuant)
- [x] Interface to support KV cache encoding and decoding (i.e., KV cache <-> bytestreams e.g. CacheGen)

## 3. Northbound Tree

Continue to make LMCache more modular and more widely integrated as the KV Cache layer of various serving engines and as the caching layer for KV Cache and other types of LLM States (embeddings, encodings etc.).

All integrations should be added to regular LMCache and MP mode as well.

- [ ] vllm-omni KV, hidden states, Embedding, and potentially Diffusion Caching
- [x] Encoder Caching (https://github.com/LMCache/LMCache/pull/2634 + https://github.com/vllm-project/vllm/pull/38668)
- [x] TRTLLM KV Caching (https://github.com/LMCache/LMCache/pull/2920 + https://github.com/NVIDIA/TensorRT-LLM/pull/12626)
- [ ] Modular KV Caching
- [x] SGLang MP Mode
- [x] Ensure integration with GPU Model Runnver V2
- [ ] Grace Hopper (ARM)
- [ ] Grace Blackwell (ARM)
- [x] TP 16 (cross node) for MP
- [ ] PD in MP
- [ ] EPD Disaggregation (after encoder caching)
- [ ] MP toml configuration

## 4. Southbound Tree

Make LMCache's storage integrations more diverse and more performant. More native connectors if possible following previous patterns to batch, non-block, non-poll, and to avoid the GIL. 

- [ ] MinIO
- [x] CXL improvements
- [ ] Deepseek-3FS
- [ ] io_uring improvements
- [x] GDS for MP mode (need to think about the L1 skipping interface)

## 5. Documentation

LMCache documentation is long overdue for a major overhaul. We should not only aim for more documentation but to make the existing documentation more concise. With AI, the quality of documentation is more important than the quality. 

- [x] Code ownership documentation (CODEOWNERS)
- [ ] MP mode architecture guide redo (e.g. EventBus, L2 framework, CLI)
- [x] long overdue update LMCache README.md
