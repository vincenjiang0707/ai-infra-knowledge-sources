## 正文

Fixes #5178

## What changed

Converted the four `G004` logging f-strings in `.buildkite/correctness/async_request.py` to lazy `%`-style logging arguments, preserving the rendered log text:

- `logger.error(f"Request failed (Object name: {obj_name})")` → `logger.error("Request failed (Object name: %s)", obj_name)`
- `logger.error(f"Error: {content}")` → `logger.error("Error: %s", content)`
- `logger.info(f"Total generated tokens: {sum(generated_token)}")` → `logger.info("Total generated tokens: %s", sum(generated_token))`
- `logger.info(f"Total time: {end - start:.2f} seconds")` → `logger.info("Total time: %.2f seconds", end - start)`

Removed the now-clean `".buildkite/correctness/async_request.py" = ["G004"]` entry from `pyproject.toml` (`tool.ruff.lint.per-file-ignores`).

Non-logging f-strings (auth header, file writes, `print`) were left untouched, and no control flow was changed. This completes this slice of the cleanup tracked in #5118 (follow-up to #5125, ref #3372).

## Verification

- `python -m py_compile .buildkite/correctness/async_request.py` — passed (no output, no errors).
- Manually confirmed no `logger.*(f"...")` calls remain in the file; the only remaining f-strings are non-logging (header dict, `f.write(...)` calls, `print(...)`).
- `ruff` is not installed in this environment, so the `ruff check --select G004` commands from the issue could not be run here; the change follows the exact lazy-logging pattern the rule requires, and the matching per-file-ignore was removed.
