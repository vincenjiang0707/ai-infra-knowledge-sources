# [PR #4410] [Feat][MP] Engine-driven multi-group transfers via KVLayerGroupsManager

## 正文

Rebuilt along @ApostaC's three steps, on top of #4079 (first commit is that move; it drops out when #4079 merges):

1. Registration initializes `KVLayerGroupsManager` and derives every group's geometry from it (no per-group re-detection). The manager also validates chunk and window divisibility.
2. Block IDs are parsed per group from the manager's kernel groups; sliding-window groups keep only the trailing window of each chunk.
3. Gather/scatter call the shared helpers moved in #4079, extended with `blocks_per_window`.

The chunk token count is `blocks_in_chunk * lcm(group block sizes)`, folding in the mixed-geometry fix @skaulintel found on the old branch (gemma-4 registered half of every chunk). Covers both transports: SHM reserves per-group slots, pickle sends a group-major payload. k3 lanes: kimi_linear_tp and engine-driven HMA lm-eval, both transports.

### divyvasal · 2026-08-05

@hlin99 Nothing fundamental. It was scoped out, and `register()` fails loudly rather than silently degrading.

The multi-group path is built around the SHM slot model: `prepare_store_grouped` / `prepare_retrieve_grouped` reserve a fixed-size slot per (group, chunk) up front (all-or-nothing, group-major on the server), and the planner's copy steps resolve raw pointers into those slots. Pickle mode has neither piece. Objects are serialized whole with variable size, so there's no reservation step and no stable destination pointer for the plan executor to target.

It's doable in theory: gather each group's chunk into a staging tensor, serialize the group tensors as one object (or N keyed objects), and reverse on retrieve. But that's a different prepare/commit shape rather than a reuse of the shared plan executor, and the all-or-nothing multi-group semantics would need reimplementing on the pickle server path. Since pickle mode only arises when the server has no SHM pool (lazy L1), i.e. it's already the degraded transport, I kept the initial scope to SHM.

Pickle multi-group can be a follow-up PR later. It would pair well with your python fallback ops for non-CUDA devices.

### divyvasal · 2026-08-06

@hlin99 found the pickle bug. It was a use-after-free on the retrieve side, nothing wrong with the transport design.

Unpickled chunks arrive unpinned, so scatter_cpu_to_paged_kv pins them into temporary copies and launches the async H2D through raw pointers. Torch's stream tracking cannot see that use, so when the function returned, the temporaries were freed and the caching host allocator handed the same pinned memory to the next group's pin_memory() while the previous group's copies were still in flight. With six groups scattered back to back per retrieve, the staging memory got overwritten mid-transfer almost every time, but timing dependent. That is why the scores bounced around (0.03, 0.13, 0.50 across runs) and why the failure only showed on pickle: the SHM slot views stay referenced and the gather buffers are pre-pinned, so SHM never takes that branch.

Fix is 0cc4b50d: synchronize before releasing the temporaries, pinned inputs keep the fully async path. Verified on an 8xH100 box with a standalone repro (about 4000 corrupted blocks per run before, zero after) and the full hma gemma-4 pickle flow end to end: 0.8000 vs 0.8000, zero drift, test passed. Also added a CUDA regression test that scatters unpinned chunks across six groups back to back.

Earlier fixes on this branch (window-sized gather buffers in ab813492 and the missing sync before pickling in 052e06fd) were real bugs too, all three stacked. CI is rerunning now.

### divyvasal · 2026-08-16

Fixed the two multi-group test failures in `00e81106`.

Both hard-coded a block size of 4, which is the NHD reading of a 5-D `[2, NB, BS, NH, HS]` tensor. The vLLM detector forces HND when `torch_device_type` is `"cpu"`, so on a CPU-only CI host the same tensor reads as `[2, NB, NH, BS, HS]` and the block size is 2. Production is unaffected, since a GPU worker resolves NHD and gets the layout vLLM reports through `layout_hints`.

The sliding-window case was worse than a wrong constant. With block size 2 the chunk is 4 tokens, so the fixed 4-token window was no longer smaller than the chunk, the group quietly became full attention, and the test stopped covering sliding windows at all.

Both now derive the block size from `compute_kv_layout` (what registration itself uses) and size the window at half a chunk. I confirmed they pass under both layouts by patching the detector to report `cuda`, and checked that the patch really does flip detection (block size 2 to 4) so the second run is not vacuous.

While I was in there I also checked the production path: `compute_kv_layout` derives block size, layer count, heads, head size and kv size from the detected format, the per-group loop calls the same helper, and `vllm_layout_hints()` forwards the real layout. The NHD assumption was only in the tests, not in the feature.


### skaulintel · 2026-08-27

@divyvasal @hlin99 — ran this branch (`00e81106`) on Intel XPU and CUDA and hit a
correctness bug worth folding into your rebase. One statement in `worker_transfer.py`;
PR against `feat/engine-driven-e2e`: <LINK>.

**Symptom.** gemma-4-31B, TP2, HMA on. Registration and stores work, but the tier stores **exactly half** the bytes per token (440.00 KiB/token vs the config's 880.00) and turn 2 is a clean external hit that decodes to garbage. Hybrid-off control on the same branch answers correctly.

**Cause.** In `EngineDrivenTransferContext.register`, `chunk_tokens = blocks_in_chunk * block_size` multiplies vLLM's *scheduling* block count by the block size of whichever layer is first in `kv_caches`. Equal under one geometry only. gemma-4 has 6 groups (5 sliding at 32-token blocks + 1 global at 64), so a 256-token chunk registers as `4 * 32 = 128`; the divisibility guard stays quiet because 128 divides both. Fix is`lcm(EngineGroupInfo.tokens_per_block)`.

**Why CI is green.** `test_engine_driven_multigroup.py` is geometry-uniform in all 10 cases — group *count*, never mixed *shape*. Confirmed on hardware: gpt-oss-20b (2 groups,one geometry) is correct at 36.00 KiB/token, gemma-4 (6 groups, two geometries) corrupts.The PR adds a 3-second GPU-free test that's red on `00e81106`; `tests/v1/multiprocess/` is594 passed / 34 skipped.

**Not XPU-specific.** Same 880.00 KiB/token on 2x L40S with the fix, byte-identical to the fixed XPU run. The line is engine-driven only, which CUDA's default IPC path never reaches.

opened a pull request with the fix here - https://github.com/divyvasal/LMCache/pull/3
