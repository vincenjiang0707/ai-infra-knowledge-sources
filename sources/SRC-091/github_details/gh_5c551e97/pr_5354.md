## Summary

The Kafka cache-event source (#5286) resumes after a restart from the consumer group's own committed offset. That offset and the coordinator's own checkpoint save are independent, on independent timers (offsets commit roughly every few seconds; a checkpoint every `--checkpoint-interval`, default 60s, or only at a clean shutdown). On an ungraceful crash between two checkpoint saves, the committed offset is already ahead of what the last saved checkpoint reflects — and resuming from it, as a plain consumer group would, skips the records in between for good: the broker considers them delivered, and the checkpoint that gets restored does not.

`StreamPosition` closes that gap by checkpointing the read position itself, in the same artifact as the state it describes, recording each partition's offset only after the gate has admitted that record — so a captured position can only ever lag the state beside it, never lead it. `KafkaCacheEventSource`'s `on_assign` callback seeks every assigned partition to `StreamPosition.next_offset(...)` rather than trusting the group's committed offset, so a restart always resumes from what the coordinator's own restored state proves it has seen. A partition with no recorded position (a first run, or a genuinely new partition) falls back to the group's committed offset, or `auto.offset.reset` if the group has none either — so a deployment with no checkpoint configured still gets Kafka's own best-effort resumption, just not the stronger guarantee.

That still leaves a real question once the correct resumption point is known: how far is it from the topic's tip, and is it safe to act on the fleet yet? A coordinator resuming from a real backlog restores quotas in full (metadata) before ingest starts, but the usage those quotas are enforced against fills back in only as the poll thread applies the backlog, and planning in that window compares a real limit against partial usage — ordering evictions the fleet doesn't need.

`app.py`'s lifespan now blocks on `IngestReadiness.wait_until_ready()` — serving nothing, not even `/healthz` — until the source's lag is within `--max-ready-lag` (default `1000`, Kafka-only), logging progress on a timer while it waits. Only once that clears does it start any controller. A source that can't say how far behind it is (an unreachable broker) counts as not ready and holds startup indefinitely — the safe direction, since a coordinator that has lost sight of the stream must not come up acting on a view it knows is incomplete. HTTP deployments clear immediately: their lag is always `0`.

**Revision history**: an earlier version of this PR gated each eviction sweep individually instead of blocking startup (a `GET /readyz`, an `IngestReadiness` threaded through `ControllerRuntime` and every controller) — simplified to a single startup gate, since the only time a coordinator's view is known to be partial is right after it starts. A version before that relied only on lag/readiness without `StreamPosition`, which left the checkpoint/committed-offset race above open; `StreamPosition` closes it.

Refs #4226, #4522.
