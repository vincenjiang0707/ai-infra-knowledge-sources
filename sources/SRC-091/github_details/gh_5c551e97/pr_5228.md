## 正文

**What this PR does / why we need it**:

#2420's traceback is a `KeyError` at `self.dict[key].cached_positions` after `read_file()`
silently drops `key` from `self.dict` on a `FileNotFoundError`. The reporter noted the same
pattern exists in `async_load_bytes` (now `batched_async_load_bytes_from_disk`). Open PR #4405
guards the sibling `load_bytes_from_disk`, but doesn't touch this function, so the async
prefetch path still raises the bare `KeyError` if a concurrent `remove(key, force=True)` races
its unlocked disk read.

Fix mirrors #4405 and the already-guarded `_load_chunk_into_memory`: recover the metadata under
`disk_lock` and drop the key as a miss (`ref_count_down()`, skip) instead of indexing straight
into `self.dict`.

**Special notes for your reviewers**:

The race needs a second in-flight request removing the same key while this one is still
mid-read (e.g. `remove_after_retrieve` on a PD receiver, or an explicit cache clear), which I
didn't reproduce end to end through the full prefetch pipeline. The regression test reproduces
it directly at the function level with a threading barrier in `read_file`, on unfixed `dev` it
raises the exact `KeyError` from #2420; on this branch it returns cleanly.
