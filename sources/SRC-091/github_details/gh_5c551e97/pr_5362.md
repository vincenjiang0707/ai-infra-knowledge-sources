# [PR #5362] Reject empty slot_mapping input in parse_mixed_slot_mapping

## 正文

## Summary
- Whitespace-only, commas-only, and otherwise slot-less inputs (`"   "`, `",,,"`, `""`) parse to an empty `compressed` list, which `decompress_slot_mapping` happily turns into `([], None)` — a reported success with zero slots — unlike every other malformed input (`"[5,2]"`, `"abc"`, `"1,2]"`), which correctly returns the `"Invalid slot_mapping format"` error.
- This lets slot-less strings bypass the `if not slot_mapping` guard in the KVCache check endpoint (`lmcache/v1/internal_api_server/vllm/cache_api.py:633`) — they're non-empty, truthy strings — and flow through to a `200` response with `num_chunks=0`, instead of the `400` every other malformed input produces.
- Fix: reject an empty parsed result the same way other malformed inputs are rejected, per the direction in the issue.

## Test plan
- [x] Updated `test_empty_string` (which pinned the old `([], None)` behavior) to assert the error instead, and added `test_whitespace_only` / `test_commas_only` for the other two repro cases from the issue.
- [x] Manually verified all repro cases from the issue directly against the patched function: `"   "`, `",,,"`, `""` all now return the same error shape as `"abc"`; normal inputs (`"1,2,3"`, `"[9,12]"`) are unaffected.

Note: the issue also flags a related "fusion" case (`"1 2 3"` → `123`, from whitespace stripping before parsing) as a separate observation, not part of the "smallest fix." I kept this PR scoped to the empty-input rejection as suggested, happy to follow up separately if that's wanted.
