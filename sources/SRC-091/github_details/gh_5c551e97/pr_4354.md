  Refs #3044.

  ## Motivation

  This is a focused version of the broader v1-flattening proposal.

  MP mode is the actively developed runtime path, while several non-MP modules under lmcache/v1/ may be deprecated separately.
  Flattening only the MP components:

  - gives the active MP implementation shorter, clearer import paths;
  - keeps legacy and potentially deprecated non-MP code visibly isolated under lmcache/v1/;
  - avoids unrelated changes to api_server, cache_controller, storage backends, configuration, and utility packages;
  - makes the migration smaller and easier to review than a repository-wide flatten.

  ## Non-goals

  This PR does not:

  - flatten the entire lmcache/v1/ package;
  - move api_server, cache_controller, distributed storage, or other non-MP implementations;
  - move lmcache/storage_backend/serde/;
  - merge lmcache/utils.py with lmcache/v1/utils/;
  - change wire formats, protocol versions, OpenAI-compatible /v1/... endpoints, Kubernetes v1alpha1
      - 1 xpassed

  - Fresh isolated uv environments:
      - SGLang 0.5.15.post1
      - vLLM 0.25.1
      - PyTorch 2.11.0+cu130
      - normal CUDA/native editable builds

  - Cross-engine GPU E2E:
      - SGLang populated LMCache on GPU 0
      - vLLM reused the cache on GPU 1
      - prompt_tokens=3688
      - lmcache_l1_read_chunk_delta=14
      - cold and cache-hit outputs matched exactly
      - no remaining GPU processes or listeners after cleanup

  - Built-wheel validation:
      - all three flattened packages are present;
      - all three old package paths are absent;
      - flattened modules and native/CUDA extensions import successfully from an isolated wheel installation.

  - Static namespace audit found zero stale references to the three old package paths.
  - Sphinx A/B comparison against dev introduced zero additional warnings or errors.

  ## Special notes for reviewers

  The E2E test explicitly selected:

  lmcache.integration.vllm.lmcache_mp_connector

  and verified that LMCache’s local scheduler and worker adapters were used rather than vLLM’s vendored fallback.

  Downstream integrations that directly import any of the three old lmcache.v1.* MP paths must update those imports as part of this migration.
