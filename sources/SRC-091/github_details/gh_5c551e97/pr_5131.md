## 正文

## Summary

This PR adds a **native C++ 3FS (Fire-Flyer File System) L2 storage backend** to LMCache,
giving it high-performance distributed KV-cache storage backed directly by the
3FS **Usrbio** API.

### What this PR does / why we need it

- **What:** A complete 3FS storage backend stack — a native C++ connector, a pybind wrapper,
  a Python L2 adapter (config + factory registration), a build profile, unit/integration tests,
  and user documentation.
- **Why:** 3FS (from DeepSeek) is a high-performance distributed file system well suited
  to large, warm/cold KV-cache tiers and cross-node cache sharing. LMCache previously had no
  native 3FS backend; KV caches had to go through slower, higher-latency paths. By performing
  I/O through the 3FS Usrbio API with **GIL-free, multi-worker parallel read/write**, this PR:
  - Reduces TTFT on cold-cache misses.
  - Increases throughput for large KV caches via batched ops and multi-path balancing.
  - Provides accelerated `EXISTS` checks without hitting the filesystem (in-memory key buffer).

## How it works

The feature is layered; each layer only exposes a narrow public interface:

```
                    Hf3fsL2AdapterConfig + factory "hf3fs"
                                   │
                    hf3fs_l2_adapter.py (NativeConnectorL2Adapter)
                                   │
                    lmcache_hf3fs CppExtension (pybind.cpp → LMCacheHf3fsClient)
                                   │
                    Hf3fsConnector (connector.h/.cpp)  ── 3FS Usrbio API
```

1. **Native connector** `csrc/storage_backends/hf3fs/connector.{h,cpp}`
   - `Hf3fsConnector : ConnectorBase<WorkerHf3fsConn>` implements
     `do_single_get/set/exists/delete` and `do_batch_exists`.
   - **Per-worker connection state** (`WorkerHf3fsConn`) keeps **dual Ior + dual Iov**
     (separate read/write rings) per thread. Separate Ior are required because the 3FS Ior
     cannot handle read and write operations simultaneously; per-thread Iov avoids
     synchronization and IB-registration complexity.
   - **Multi-path load balancing:** objects are distributed across the configured
     `base_paths` based on `chunk_hash`.
   - **Accelerated `EXISTS` (key buffer):** an in-memory `sharded_flat_hash_set<std::string>`
     (built on `absl::flat_hash_set`, with per-shard locks for high write throughput) is
     populated once by scanning the base paths at startup. `do_batch_exists` then answers from
     the buffer without touching 3FS, only falling back to the FS when the buffer is disabled.
   - **Per-op worker lanes:** optional `per_op_workers` (`lookup/retrieve/store/delete`) via
     `WorkerPoolConfig` for isolated worker pools per operation class.

2. **Pybind:** `pybind.cpp` exposes the connector through a `LMCacheHf3fsClient` module.

3. **Python adapter:** `hf3fs_l2_adapter.py` adds `Hf3fsL2AdapterConfig` and registers the
   `"hf3fs"` adapter type + factory, backed by the existing `NativeConnectorL2Adapter`.

4. **Build profile:** `hf3fs.py` builds `lmcache.lmcache_hf3fs` when `BUILD_HF3FS=1`, linking
   against `libhf3fs_api_shared` and the system Abseil libs
   (`absl_hash`, `absl_city`, `absl_int128`, `absl_raw_hash_set`); Abseil availability is
   detected before building.

### Configuration example

```
[lmcache]
type = "hf3fs"
mount_point = "/3fs/stage"
base_paths  = "/3fs/stage/lmcache/p1,/3fs/stage/lmcache/p2"
num_workers = 8
# optional tunables:
ior_entries     = 256     # [128, 1024]
io_depth        = 0       # [-128, 128]
iov_size        = 209715200  # 200 MB, [100MB, 2GB]
enable_key_buffer = true
# per_op_workers = {"lookup": 2, "store": 4}
```

### Dependencies & build

- Requires the **3FS Usrbio SDK** (`hf3fs_usrbio.h`, `libhf3fs_api_shared.so`) and system
  **Abseil** (`libabsl-dev`).
- Build:
  ```bash
  export HF3FS_INCLUDE_DIR=/usr/include
  export HF3FS_LIB_DIR=/usr/lib
  BUILD_HF3FS=1 pip install -e . --verbose
  ```

### Testing

- `tests/v1/distributed/test_hf3fs_l2_adapter.py`
  - Config/validation tests (ranges, mount/base-path checks, per-op workers, key-buffer).
  - Native-connector tests: client creation, single/batch put-get roundtrip, exists, delete,
    multi-path distribution, persistence across clients.
  - L2-adapter integration: store/lookup, load, delete, end-to-end workflow, multi-object batch.
- Result on a live 3FS mount (`HF3FS_MOUNT_POINT=/3fs/stage`): **33 passed, 1 skipped**
  (the skipped case is the "extension absent" failure-path test).

### Notes for reviewers

- New public API is minimal: one connector class + one adapter config/factory.
- Files: `csrc/storage_backends/hf3fs/*`, `hf3fs_l2_adapter.py`, `hf3fs.py`,
  `test_hf3fs_l2_adapter.py`, `docs/source/mp/l2_storage/{hf3fs.rst, supported_storages.rst,
  remote_and_distributed.rst}`.

-  fs_native + CephFS cluster 
-  nixl_native +3FS cluster

For both  3FS cluster and CephFS cluster, it has two storage servers. Each data has 2 replicas. 
Generally speaking
- fs_native + CephFS has better store performance than HF3FS + 3FS when num_works <= 16
- HF3FS + 3FS has better load performance than fs_native + CephFS when num_works <= 16
