# [PR #4816] feat(mp): enable per-layer KV cache load for LMCache-driven MP mode

source: https://github.com/LMCache/LMCache/pull/4816
state: open | updated: 2026-09-25T22:51:13Z
labels: 

## 正文

Add per-layer (layerwise) KV cache transfer to LMCache-driven multiprocess mode so vLLM can overlap attention compute with the H2D transfer, instead of blocking on a single per-chunk (all layers per-request) transfer before the forward pass starts.

The feature is selected at runtime for CUDA. It activates only when the cache server is started with --layerwise-batch N for N > 0 and vLLM is pointed at the layerwise connector through kv_connector_module_path like below example.

lmcache server --layerwise-batch 8 --l1-size-gb 20 --eviction-policy LRU --port 5555

```json
vllm serve --kv-transfer-config \
'{"kv_connector":"LMCacheLayerwiseMPConnector",
"kv_connector_module_path":"lmcache.integration.vllm.lmcache_mp_connector_layerwise", "kv_role":"kv_both","kv_connector_extra_config":{"lmcache.mp.host": "tcp://localhost","lmcache.mp.port":5555}}'
```

Separate code path:
- lmcache_mp_connector_layerwise.py and vllm_multi_process_adapter_layerwise.py subclass the existing connector and worker adapter.
- modules/lmcache_layerwise_transfer.py subclasses LMCacheDrivenTransferModule and imports the helpers it reuses. lmcache_driven_transfer.py only does a minor change to accommodate per-layer path.
- protocols/layerwise.py declares REGISTER_LAYERWISE_IPC_EVENT_POOL and RETRIEVE_LAYERWISE for clear boundary without impacting existing request types.
- transfer_context/worker_layerwise_transfer.py and layerwise_futures.py hold the worker-side context and future.
- csrc/cuda/mp_mem_kernels_layerwise.cu holds the layerwise kernel and its launch code. The device helpers it shares with the per-chunk path moved verbatim into mp_mem_kernels_device.cuh, so both translation units include them rather than duplicating them.

Extension points added to existing files:
- LMCacheDrivenTransferModule.retrieve() routes every object-group copy through a new _transfer_object_group() hook so the subclass avoids hundreds of lines of duplicated code. The base implementation just calls transfer_kv_per_object_group in lmcache_driven_transfer.py.
- LMCacheMPConnector._worker_adapter_cls and LMCacheMPWorkerAdapter._create_transfer_context let the subclasses swap in their own components.
- server._build_modules selects the layerwise module when --layerwise-batch > 0

Multi-frame responses:
- MessagingFuture gains deliver() which reports whether a request is complete, and a blocking handler may declare a response_channel parameter to answer with more than one frame. Buffering intermediate frames and deciding when the exchange ends happens inside LayerwiseDeviceMessagingFuture.
- LayerwiseDeviceMessagingFuture intercepts frames by installing itself as the raw future's delivery sink, and that has to happen before the request reaches the wire. Add tests/v1/multiprocess/test_layerwise_retrieve_submit_ordering.py.

Layout:
PageBufferShapeDesc gains kv_interleaved. When set, an LMCache object uses the L2TD layout [L, 2, T, D] (K0,V0,K1,V1,...) instead of the default 2LTD layout [2, L, T, D] (all K then all V), so a per-layer transfer reads one contiguous span per layer. The flag is fixed at registration time to keep it off the per-request path.

Event pool:
EventPool in platform/base/event_pool.py allocates EVENT_POOL_SIZE IPC events once and exports their handles during REGISTER_LAYERWISE_IPC_EVENT_POOL, so the per-layer path signals a pooled event by index instead of exporting a handle per layer.

Mode exclusivity:
The two modes (per-layer and per-chunk) are mutually exclusive per server node, and the worker's mode is fixed at process start by the connector vLLM imports, not negotiated during registration.

### zxue2 · 2026-09-17

> qq on the sync load path: with load_async=False vllm already counts the hit as computed and runs the request in the same step, so any transfer problem now surfaces inside attention through wait_for_layer_load. is the plan to rely on error_block_ids to recompute after the step, or should wait_for_layer_load fall back to waiting on the whole future and never raise?

@sammshen , thanks for pointing it out. It relies on error_block_ids to recompute after the step. i.e., LMCache server detects layer X fails, aborts the remaining layers, and sends the closing frame. At the worker, the closing frame resolves the future, so every remaining wait_for_layer_load() returns immediately instead of blocking, and the forward pass completes on garbage KV for that request. The affected blocks are drained at step end and the scheduler recomputes the failed request.  May need to set kv_load_failure_policy="recompute" in KVTransferConfig as well.
