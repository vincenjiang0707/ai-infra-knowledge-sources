## 正文

##Background

This PR is aimed at resolving issue #5344. I have identified the cause of the problem: When retrieving, the determination of whether the cache is valid mainly relies on **whether the key/metadata has been published, rather than confirming that all the KV shared of TP rank have been successfully written.** 
This PR has not yet fully resolved this issue, as the problem is too extensive and requires the maintainer's confirmation before further modifications can be made. This PR is specifically aimed at addressing the issue of the release of a single TP.

## What
For the original reverse_writing function of StoreManager, it merely determined which keys failed and which keys succeeded. But in fact, there are still different states within the failed key. The modified function now carries these states instead of merely transmitting the key. In the `store` function within `lmcache_driven_transfer`, I added a piece of code to handle the `submit_callback_to_stream` for `all_dict`. This is done to clean up the staging buffers that fail halfway through.

## Why

`StorageManager.reserve_write()` filters failed reservations out of its return value. The multiprocess store path therefore could not distinguish L1 OOM from an intentionally skipped key and unconditionally reported success after iterating object groups. If a later group ran out of memory, objects reserved for earlier groups could still be committed, leaving a partial checkpoint visible.

## Scope

This is the minimal fail-closed fix for #5344. It makes each rank report failure and roll back that rank's staged objects. It does **not** implement the issue's full cross-rank two-phase commit/abort protocol; coordinated TP-wide atomicity remains follow-up work.

Existing `KEY_NOT_WRITABLE` behavior is preserved so already-resident keys continue to be skipped rather than treated as allocation failures.
