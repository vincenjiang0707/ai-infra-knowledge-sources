# [Issue #4113] [Feature Request] Add SPDK-based Native Storage Backend for Optimized KVCache Offloading

## 正文

### Motivation

LMCache currently supports offloading KVCache to SSDs via the File System Connector (FSConnector). However, existing implementations primarily rely on kernel-based file systems (e.g., ext4, XFS) or FUSE clients. When handling the high-concurrency, low-latency I/O requests generated by AI inference, these traditional approaches introduce significant overhead due to kernel context switches, interrupt handling, and lock contention, preventing NVMe SSDs from reaching their full hardware potential.

We propose developing a new storage backend for LMCache that leverages **SPDK (Storage Performance Development Kit)**. By utilizing SPDK's userspace polling drivers to bypass the kernel protocol stack and access NVMe devices directly, we aim to achieve ultimate performance for KVCache read/write operations.

### Background

SPDK (Storage Performance Development Kit) is a set of tools and libraries for writing high-performance, scalable, userspace storage applications. Its key features include:

1. **Userspace Drivers**: Runs NVMe drivers in user space, completely eliminating kernel context switch overhead.
2. **Polling Mode**: Replaces traditional interrupt handling with a polling mechanism to check for I/O completion. This drastically reduces latency jitter and is ideal for high Queue Depth (QD) scenarios.
3. **Lockless Design**: Avoids lock contention in multi-threaded environments through core pinning and per-core queues, improving multi-core scalability.
4. **Zero-copy**: Allows applications to manage memory buffers directly, reducing data copies between kernel and user space.
Performance Advantages of SPDK in KVCache Scenarios.

In AI inference scenarios, KVCache offloading and loading exhibit specific I/O patterns:

- **Prefill Phase**: Primarily large-block Sequential Writes (saving newly generated KVCache).
- **Decode Phase**: Primarily small-block Random Reads (loading historical KVCache).

Traditional kernel-based file systems suffer from higher latency and limited throughput when handling high-concurrency random reads due to interrupt processing and locking mechanisms. In contrast, SPDK offers:

- **Ultra-Low Latency**: Bypassing the kernel stack reduces random read latency to the microsecond level, significantly cutting down waiting time during token generation (Time-to-First-Token, TTFT).
- **High Throughput**: At high queue depths, SPDK maximizes NVMe SSD bandwidth, delivering far superior Random Read IOPS compared to traditional file systems, especially under concurrent loads.
- **CPU Efficiency**: While polling consumes CPU cycles, it processes significantly more I/O requests per CPU cycle under high load compared to interrupt modes, offering more predictable latency.

SPDK performance:
- Store@4KB: wins every queue depth, 2.8-3.1x faster than the original connector, now ahead of both other backends (in_flight=64: 122,529 vs. raw_block 67,759, fs_native 29,607 ops/s).
- Load@4KB/in_flight=64, the exact decode-like case this issue asks about, went 13,644 → 81,457 ops/s (6.0x), now beating both other backends there.
- Store@32/256KB barely moved. Those cells are bandwidth-bound rather than dispatch-bound, so raw_block still wins outright.

The EC2 instance's NVMe instance store has a hard aggregate write-bandwidth ceiling of roughly 145–170 MiB/s, completely independent of queue depth or how many parallel queue pairs we throw at it. Concurrency doesn't help because the hardware layer won't service it any faster:

| Test | Result |
| :--- | :--- |
| **256KB write, 1 qpair, qd=1** | 162 MiB/s |
| **256KB write, 1 qpair, qd=32** | 162 MiB/s (latency 32x higher – pure queueing, zero throughput gain) |
| **256KB write, 4 qpairs, qd=8 each** | 162 MiB/s aggregate |
| **4KB write, 1 qpair, qd=32** | 144 MiB/s |

This is likely instance-size-related: c6id.xlarge is a small size in its family, and AWS scales local-NVMe bandwidth allocation with instance size. A larger size (or .metal) would plausibly show a proportionally higher ceiling. Worth re-running the large-payload cells there before drawing conclusions on them. This time I re-ran everything on `c6id.8xlarge` at 256KB/1MB, and here are some insights I want to share and discuss:

- The old ceiling was indeed `c6id.xlarge`'s Nitro bandwidth cap. No queue/dispatch bottleneck at this instance size.
  - Raw SPDK NVMe perf on the 8xlarge: 
    - 256KB write @ qd=32 → **1,345.83** MiB/s (5,383 IOPS, 5.94ms avg lat); 
    - 1MB write @ qd=16 → **1,167.20** MiB/s (1,167 IOPS, 13.71ms avg lat). 
- At the LMCache L2-adapter level, all 3 backends scale cleanly into the 1.1–3.3 GiB/s range at 256KB/1MB, which is consistent with the raw ceiling above.
- NIXL GUSLI: plugin is real, but needs a separate server
  - The plugin includes GUSLI out of the box (memory types: `BLK_SEG`, `DRAM_SEG`).
  - Bug: Updated `nixl_store_l2_adapter.py`, changed hardcoded `BLK` to `BLK_SEG` to prevent registration failures.
  - GUSLI is a client/server architecture (NVIDIA/GUSLI docs): a separate SPDK-backed server process must be running before the NIXL client can attach. Standing that up is a follow-up work, not a config change. Happy to pick this up as an explicit follow-up if there's interest!

Across 256KB and 1MB benchmark sweeps on `c6id.8xlarge`, all backends (`spdk_v2`, `raw_block`, and `fs_native`) hit the same ~1.1–3.3 GiB/s throughput band without any clear winner. Write throughput for all backends peaks around `in_flight=8` before degrading at higher concurrency, with `fs_native` and `spdk_v2` converging to roughly 1.0–1.2 GiB/s at high queue depths (`in_flight=32/64`). This closely matches the raw hardware write ceiling measured directly via single-queue SPDK (1,167.20 MiB/s). Conversely, load throughput scales better with concurrency, reaching up to ~3.3 GiB/s. Under sustained write pressure, every backend ultimately reverts to the same underlying physical bandwidth limit; they differ only in how gracefully they reach that ceiling.

This behavior aligns with SPDK’s architectural design, which focuses on reducing fixed CPU overhead per I/O (syscalls, context switches, interrupts) rather than boosting raw payload bandwidth. For large 256KB–1MB payloads, transfer time heavily outweighs fixed per-operation costs, eliminating the performance advantage SPDK typically displays in 4KB/high-IOPS workloads. Furthermore, running on an AWS Nitro-virtualized instance caps performance at the Nitro card level, preventing guest-OS kernel-bypass optimizations from improving overall throughput, which also explains the flat ~162 MiB/s ceiling observed on the smaller `.xlarge` instance. Proving SPDK’s actual benefit in this environment would require measuring CPU utilization per I/O under high-IOPS, small-block workloads.

I guess, on bare metal, SPDK’s true value shifts from raw throughput to CPU efficiency and deterministic latency: while kernel-backed drivers can consume 4~8 CPU cores handling interrupts and context switches at maximum bandwidth, SPDK achieves the same throughput with a single polling core, freeing massive CPU capacity for vLLM tensor computation and KV-cache offloading while eliminating kernel-scheduler jitter to deliver stable P99/P999 tail latency.
