## Description

Upgrades `tokamax` to 0.0.14.

Per `docs/development/update_dependencies.md`, the source change is the floor in `base_requirements/requirements.txt` (`tokamax!=0.1.0` -> `tokamax>=0.0.14,!=0.1.0`) and the `generated_requirements/` locks were regenerated with the `seed-env` flow, the same way `bde759abd` (drjax) did it.

- Pre-training locks (`tpu`, `cuda12`) regenerated with JAX build commit `ab4c9b943c70bcb42baf4d379036a19c8aa2689d`
- Post-training lock regenerated with JAX build commit `52d5cb3893727451d0f695bfa6f8206cdd9492c7`
- `decoupled-requirements.txt` regenerated from the new GPU lock
- `requirements/requirements.txt`: stale `tokamax>=0.0.4` floor raised to `>=0.0.14`

Regenerating re-resolves each lock in full against the JAX seed and current PyPI, so the locks also carry the releases that landed since the last regeneration on 2026-08-31. `jax`, `jaxlib`, `jaxtyping`, `libtpu`, `flax`, `qwix` and `orbax-checkpoint` are unchanged; the largest unrelated move is `transformers 5.16.1 -> 5.17.0` and the rest are patch releases.

### Decoupled mode

The decoupled requirements stay pinned at `tokamax==0.0.12`. 0.0.14 still imports `xprof` at module scope (`tokamax/__init__.py` -> `tokamax/_src/benchmarking.py`), and `xprof` is filtered out of that environment, so every test reaching `maxtext.layers.moe` would fail to collect. The comment next to `PINNED_PACKAGES` records that this was re-checked against 0.0.14.

### Note for dependency owners: the xprof cap is ineffective

Pre-existing and deliberately not changed here. tokamax has required `xprof>=2.23.1` since 0.0.13, while the overrides cap it:

| File | Constraint |
| --- | --- |
| `extra_deps/tpu_overrides.txt` | `xprof<=2.23.0` |
| `extra_deps/cuda12_overrides.txt` | `xprof<=2.23.0` |
| `extra_deps/tpu_post_train_overrides.txt` | `xprof>=2.20.0,<=2.23.0` |
| generated TPU/GPU locks | `xprof>=2.20.0` |

uv `override-dependencies` *replace* a declared requirement rather than intersect with it, so during locking the cap silently wins and the locks keep `xprof>=2.20.0`. Overrides do not apply at install time, so installing any of these locks resolves `xprof` to 2.23.1 anyway to satisfy tokamax, which is what my test environment ended up with. The cap is therefore a no-op for real installs and the locked floor understates the true minimum. This surfaced when trying to re-resolve with every other package held at its current version, which fails with:

```
Because tokamax>=0.0.14 depends on xprof>=2.23.1
and your project depends on tokamax>=0.0.14 and xprof==2.20.0,
we can conclude that your project requirements are unsatisfiable.
```

Happy to lift the cap in a follow-up if that is the right call.

### Pre-existing failure, not caused by this change

`tests/unit/moe_test.py::QuantizedMoeTest::test_gmm_grad_equivalence_tokamax_v2_fp8_dynamic_ep4` fails with NaN gradients:

```
[PASS] output          | max_abs_diff: 3.418e-03 | relative_norm_diff: 6.529e-02
[FAIL] var_grad-wi_0   | max_abs_diff: nan       | relative_norm_diff: nan
[FAIL] var_grad-wi_1   | max_abs_diff: nan       | relative_norm_diff: nan
2/6 leaves exceed relative_norm_diff_threshold=0.22.
```

Swapping only the tokamax wheel in the same environment gives a byte-identical failure signature on `tokamax==0.0.13`, so this is a pre-existing gmm_v2 fp8-dynamic + EP4 issue, not a 0.0.14 regression. The `_ep1` variant of the same test and the `bf16_ep4` variant pass on both versions.
