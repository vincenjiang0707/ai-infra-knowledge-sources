## 正文

## What and why

With `retry_when_tokens_dropped`, a train step whose ragged buffer overflows is discarded and replayed with the dropless
program. The steps right after a (re)start overflow most often, because routing is least balanced there. Each such step
then pays for a normal attempt, a discard and a dropless replay, and before this change the dropless program was also
compiled lazily inside the timed loop on its first use. We would rather give those early steps a buffer that is large
enough, keep the retry as a safety net, and compile every program the loop can run before the loop starts.

`retry_dropless_first_steps=N` runs the steps with `step - start_step < N` without the normal attempt. With
`first_phase_ragged_buffer_factor=0` they run the dropless program directly. With a factor > 0 they run a first-phase
program, which is the normal train program with `RoutedMoE.ragged_buffer_factor_override` set to that factor. It keeps a
finite (larger) buffer together with the normal remat policy and token chunking, so it costs much less per step than the
dropless program. A first-phase step that still overflows is replayed with the dropless program, exactly as a normal step
is. Validation requires `retry_when_tokens_dropped=True`, and for the first-phase factor also `ragged_buffer_factor > 0`
and a factor at least as large as `ragged_buffer_factor`.

`eval_ragged_buffer_factor` gives the eval program its own ragged buffer factor through the same per-graphdef override.
`RoutedMoE.effective_ragged_buffer_factor()` returns the override when it is > 0 and `config.ragged_buffer_factor`
otherwise, and every former read of `config.ragged_buffer_factor` in moe.py goes through it. It is not supported with
`te_moe_block`.

When `retry_when_tokens_dropped` is set, setup now compiles the dropless program, the first-phase program (when enabled)
and the eval program ahead of time next to the train program (`build_dropless_graphdef`, `build_first_phase_graphdef`,
`build_eval_graphdef`, `aot_compile_step`), so no compilation happens in the timed loop.

`log_required_ragged_buffer_factor` is a probe for choosing these factors. Each RoutedMoE computes, from the per-expert
counts the overflow check already uses, the smallest ragged buffer factor for which its shard would not have dropped
tokens, takes the max over the mesh (one float32 scalar max all-reduce per MoE layer and token chunk) and logs one
`REQUIRED_RBF step=... max=... per_layer=[...] program=...` line per train program run. The value is read on the host,
so it adds a device-to-host fetch per step. It is off by default and meant for tuning runs.

The change also fixes the replay remat override. The dropless graphdef set `remat_policy_override = "full"` only on
modules named `Decoder`, which matches nothing for `NNXDecoder`, so the replay ran with the normal remat policy.
`build_dropless_graphdef` matches any module that exposes `get_remat_policy()`. #5362 made the same fix inline in
`train_loop` and has since merged to main; on main this change replaces that inline block with the helper (the only
rebase conflict, see below).

Every new option is off by default, and without the flags the training loop takes the same branches as before.

## Knobs

| option | default | recommended (MLPerf DSv3, 512 chips) |
|---|---|---|
| `retry_dropless_first_steps` | 0 (off) | 20 |
| `first_phase_ragged_buffer_factor` | 0 (off; first steps run dropless) | 4.75 |
| `ragged_buffer_factor` (existing) | -1 | 3.0 |
| `eval_ragged_buffer_factor` (from main, #5377) | -1 (dropless worst-case buffer under eval axis rules) | 4 |
| `log_required_ragged_buffer_factor` | false | false (tuning only) |

The recommendation rests on the probe: the baseline runs below logged a largest required factor of 4.62 in steps 0-19
across three seeds, and the fp30 and fp35 runs logged at most 2.80 after step 20.

## Results

Setup: 512 chips (one 8x8x8 slice), v4.0 team image with this change's source files overlaid
(`integrate_v2:mlperf61v4-stack4`), profiler off, seeds 1234, 4321 and 777. The baseline ("today") runs 10 dropless steps
and then `ragged_buffer_factor=3.5`. The new setting ("fp30") runs 20 first-phase steps at 4.75 and then
`ragged_buffer_factor=3.0`. Both arms have `eval_ragged_buffer_factor=4` and ran with the required-factor probe on, so both
include its per-step fetch. Steady is the mean of steps 21-42; e2e is run_stop - run_start. All per-seed numbers are
measured; medians and comparisons are derived.

| seed | arm | steady s/step (21-42) | replays (step) | target step (loss) | e2e s |
|---|---|---|---|---|---|
| 1234 | today | 3.8896 | none | 56 (3.592) | 308.8 |
| 1234 | fp30 | 3.8311 | none | 54 (3.597) | 281.1 |
| 4321 | today | 3.8871 | 4 (11, 12, 18, 19) | 54 (3.595) | 320.9 |
| 4321 | fp30 | 3.8297 | none | 58 (3.599) | 318.9 |
| 777 | today | 3.8883 | none | 53 (3.600) | 293.7 |
| 777 | fp30 | 3.8288 | none | 54 (3.591) | 281.1 |

The 3-seed median e2e is 308.8 s today and 281.1 s with fp30. A first-phase step at 4.75 takes 4.16-4.20 s against
5.70-5.76 s for a dropless step, and no fp30 run replayed at any step, so seed 4321's four late replays (steps 11, 12, 18
and 19, which overflowed rbf 3.5 after the dropless window) are gone. After step 20, the 3.0 buffer runs roughly 57-60 ms
per step faster than 3.5 on every seed.

The evidence has clear limits. It is n=3 seeds on one slice size. Target steps scatter from 53 to 59 across all arms we
ran, so an e2e comparison still carries that scatter (e.g. on seed 4321 fp30 reached the target four steps later than
today and the e2e margin is only 2.0 s). The per-step numbers (first-phase step time, steady step time, replay count) are
the more direct measure of the change. We have not measured other slice sizes or the probe-off setting at these factors.


Scale note: the recommended first-phase settings (20 steps at 4.75, then 3.0) were tuned at 512 and 1024 chips, where they gave zero replays on three seeds. At 2048 chips (one 8x16x16 slice, GBS 4096) the same schedule ran at 4.157 s/step (-82 ms against the dropless first phase) but replayed at steps 6 and 30, so larger batches need their own probe run to set the two buffer factors.

# Rebase note

Rebased onto main after #5377 (b33d0f687), which added its own `eval_ragged_buffer_factor` and `RoutedMoE.get_ragged_buffer_factor()`. This change now uses main's field and validation, and drops its duplicate field and its "-1 or > 0" check, so -1 follows main's semantics (the dropless worst-case buffer under eval logical axis rules) (the knob table above has been updated accordingly). `effective_ragged_buffer_factor()` is folded into main's `get_ragged_buffer_factor()`, which checks a per-graphdef `ragged_buffer_factor_override` > 0 first, so the first-phase program keeps `first_phase_ragged_buffer_factor` and a positive `eval_ragged_buffer_factor` still gives eval its own graphdef. With the r2-2k settings (eval factor 4) an AOT compile for tpu7x-4096 of main + this PR + #5381 + #5382 gives the same train, first-phase and eval memory stats and the same alpha-normalized after-optimizations HLO as before the rebase. CPU unit tests (moe, configs, pyconfig, train_utils, train_nnx and related): 355 passed, against 346 on main.
