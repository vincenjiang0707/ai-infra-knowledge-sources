## 正文

# Description

This PR makes `MaxTextTrainingEngine`, the trainer that Tunix's RL stack drives one micro-batch at a time, work
correctly at large sharded configurations such as the Qwen3.5-397B-A17B MLPerf trainer config (`custom_mesh_and_rule=cp-as-ep`).
It fixes model construction and sharding-rule handling, implements `optimizer_memory_host_offload` (previously ignored by
the engine), adds a `grad_accumulation_dtype` option, fixes mid-step checkpoint resume, turns the engine's ahead-of-time
compile tool into a per-kernel device-memory report that can also compile Tunix's GRPO loss from the command line, updates
the standalone trainer script, and adds a README with instructions and a full recipe to run all of it.

It also closes the throughput gap to `pre_train/train.py`: on 128 TPU v7x chips at the Qwen3.5-397B-A17B configuration the
engine now runs at 201.43 s/step (2,603 tokens/s/chip) against `pre_train/train.py`'s 206.12 s/step (2,544 tokens/s/chip),
and trains with float32 gradients at 217.19 s/step (see Tests).

Before this change, the engine could not be constructed at `cp-as-ep` when the caller had set a mesh, several entry points
traced the model without MaxText's logical axis rules (Tunix binds none), the offload flags were silently ignored, and the
AOT tool could not compile Qwen3.5 or Tunix losses.

## Why, and what changed

### 1. Model construction under a caller's mesh
**Problem.** The engine builds the model with flax's `nnx.eval_shape`. When the caller had set a mesh with `jax.set_mesh`,
flax re-derived shardings from logical axis names and raised on valid MaxText rule sets (at `cp-as-ep`:
`Resource axis: norm of P('norm',) is not found in mesh`). Without any rules bound, Tokamax ring attention fails instead,
because it validates its sequence sharding when the layer is constructed.
**Fix.** `_build_model` binds MaxText's logical axis rules and clears the mesh (`jax.set_mesh(None)`) for the duration of
construction. This works whether the caller uses `jax.set_mesh`, the legacy `with mesh:` (what Tunix does), or no mesh.

### 2. Sharding rules at every traced entry point
**Problem.** Tunix constructs and calls the engine under `with mesh:` only, with no logical axis rules. Entry points that
traced the model inherited whatever the caller had bound; `eval_step`, for example, traced outside the rules.
**Fix.** `fwd_bwd`, `update`, `eval_step` and `fwd_only` each enter `_sharding_ctx()` (mesh + logical axis rules)
themselves. New `model_scope(*inputs)` implements Tunix's `AbstractTrainer.model_scope`: it yields the live model and the
inputs placed on the mesh, under the rules, which Tunix's `TrainerWorker.per_token_logps` uses to score log-probs with the
trainer's weights. A `logical_axis_rules_for_eval` that differs from the training rules now raises instead of being
silently ignored.

### 3. Optimizer host offload
**Problem.** The engine never read `optimizer_memory_host_offload`: the optimizer moments always stayed in device memory,
which matters most at the forward/backward peak. `parameter_memory_host_offload` was also silently ignored.
**Fix.** With `optimizer_memory_host_offload=true`, the optimizer state lives in `pinned_host` memory between updates.
`update` moves it to the device for the optimizer arithmetic, and the kernel's output shardings return it to host memory,
mirroring what `pre_train/train.py` does. The forward/backward kernels never take the optimizer state, so it is no longer
resident during them. The placement is re-applied after a checkpoint restore, after the state setters, and on the eager
(uncompiled) path. Zero-1 (`shard_optimizer_over_data`) keeps the host memory kind. `parameter_memory_host_offload=true`
now raises `NotImplementedError` rather than doing nothing.

### 4. Gradient accumulation dtype
**Before.** Each micro-batch's gradients were cast to `grad_dtype` and summed in `grad_dtype`.
**Now.** New config key `grad_accumulation_dtype` (`""` by default, which keeps the previous behaviour). `"float32"` sums
micro-batch gradients in float32 and casts to `grad_dtype` once, after dividing by the total denominator; for float32
weights this is `pre_train/train.py`'s order and matches it bit for bit in the CPU parity test. The trade-off is a float32
accumulator kept on device between micro-batches, which is why it is opt-in. The division by the accumulated denominator
now happens in float32 (previously a bf16 division rounded the token count).

### 5. Mid-step checkpoint resume
**Problem.** The accumulator's restore target was built from the parameters, so a checkpoint saved between micro-batches
came back in `weight_dtype`. When that differs from the accumulation dtype (the default bf16 grads with float32 weights),
the compiled kernels rejected it (`Argument types differ from the types for which this computation was compiled`), and on
the lazily compiled path the step silently recompiled with a float32 accumulator.
**Fix.** `CheckpointState.accumulated_grads_target` restores the accumulator in the accumulation dtype with the parameter
shardings, and the engine casts defensively after restore.

### 6. AOT compile tool (`maxtext_engine_compile.py`)
**Problem.** `AbstractMaxTextEngine` traced the model graph under a mesh and failed on the same configurations as (1), so it
could not compile Qwen3.5 or losses written for Tunix. Its output was the raw `memory_analysis()` of each kernel, which is
easy to misread: the forward/backward kernels do not take the optimizer state as an argument, yet it stays in device memory
while they run.
**Fix.** The abstract engine traces the model the way the live engine builds it (and wraps it in the Tunix adapter when
asked). The tool prints each kernel's memory analysis and a per-device table: `resident = arg + out - alias + temp`, plus
the train state that stays in device memory without being a kernel argument, with host memory reported separately. The last
line, `TRAIN-KERNEL DEVICE PEAK`, is the largest total over the three kernels, and the legend lists what it does not cover
(weight-sync staging, `fwd_only` scoring, the eval kernel, anything the caller holds). A `WEIGHT-SYNC STAGING` line
estimates the weight-sync copy when `use_weight_converter=false`. Compiled executables are saved before the report is
printed, so a report error cannot lose them.

### 7. Standalone trainer script (`experimental/maxtext_engine/train.py`)
- Constructs and drives the engine the way Tunix does, with no outer `logical_axis_rules`. The previous outer wrap hid
  missing bindings inside the engine.
- Splits each global batch into micro-batches in `pre_train/train.py`'s order (micro-batch k = rows `k::G`), in one jitted
  call, so every device keeps its own rows and the split needs no collectives.
- Reports `Tokens/s/device` and `Tokens/s/chip`. The old per-chip number divided by the device count, which halves it on
  TPUs with two devices per chip.
- Logs memory after compile and after the first step, and times each step from dispatch until its device work drains.

### 8. Gradient accumulation kernel
**Problem.** Every micro-batch after the first ran a second forward/backward program that took the donated gradient sum as
an input. XLA folded the add into the token embedding's gradient scatter-add, which gathers an unsharded copy of that leaf
at the program's peak; on large configurations this pushed the program past the scheduler's memory limit and cost
compute/communication overlap, so the accumulating micro-steps ran slower than the first one.
**Fix.** Every micro-batch runs the same `fwd_bwd` program, and a new donated `accumulate` kernel adds each later
micro-batch's gradients and loss denominator into the running sums. The forward/backward program is compiled once instead
of twice. The trade-off: each micro-batch's gradients now sit beside the running sum until `accumulate` adds them, so
`fwd_bwd`'s peak holds one more gradient tree (two float32 trees with `grad_accumulation_dtype=float32`). That lowers the
peak only where XLA's fold was expensive, as at the Qwen3.5-397B configuration, where a TPU v7x run confirmed the speed-up;
on smaller configurations the peak rises by one gradient tree.
The accumulated gradients are unchanged bit for bit except the token-embedding leaf, which is now summed in source order
(`acc + grads`) instead of the order XLA's fold chose, so it can differ by rounding.

### 9. Casting all-reduced gradients after the all-reduce (`cast_grads_after_all_reduce`, default off)
**Problem.** Gradients are cast to the accumulation dtype inside `fwd_bwd`. For parameters sharded over none of the axes a
batch is split over (norm scales and similar), XLA can sink that cast into the backward loop and turn their
cross-device all-reduces into synchronous bf16 reductions; on the TPU configuration we profiled, this reduced how much of
the backward pass's collective time was hidden behind compute.
**Fix.** With the new key on, those gradients leave `fwd_bwd` in the parameters' dtype and are cast when they join the
running sum, after the all-reduce. Selection is by sharding, not size. With the key off, the compiled kernels are unchanged.
It is meant for TPU together with the libtpu flag `--xla_tpu_enable_offloading_copy_to_sparsecore=false`, which keeps
layout copies off the SparseCore that the backward pass's collectives also use; alone, the key can raise device memory.
The flag raises device memory too, so both are documented as per-configuration choices to check with the memory report.
With both at the Qwen3.5-397B configuration on TPU v7x, the engine ran 2.3% faster than `pre_train/train.py` (see Tests).

### 10. Compiling with Tunix's GRPO loss from the command line
`maxtext_engine_compile` could compile a Tunix loss only through its Python API. The new key `compile_engine_loss=grpo`
sets up the abstract engine as Tunix's RL trainer sets up a live one: the model behind `TunixMaxTextAdapter`, and the loss
and input mapping from Tunix's `GRPOAdapter`. `compile_engine_grpo_config` passes the trainer's `GRPOConfig` options and
`compile_engine_logps_chunk_size` computes log-probabilities in chunks as `TrainerWorker` does, so the memory report can
match a real RL trainer. With the default (`maxtext`), the tool compiles what it compiled before.

The micro-batch it compiles for is built by Tunix's own code, as its orchestrator builds one:
`GRPOAdapter.create_trainer_payloads`, the batch assembler `create_batch_assembler` picks, the reference model's
log-probabilities when the loss needs them, and the fields Tunix's sampler-trainer agreement step writes (with
`sampler_is: token`, `sampler_is_weights`).
- `compile_engine_max_seq_token_per_tpu` and `compile_engine_max_segments_per_packed_row` (Tunix's `max_seq_token_per_tpu`
  and `max_segments_per_packed_row`) compile for `SequencePackedBatchAssembler`'s packed rows, one per device of the
  mesh's data, fsdp, fsdp_transpose and expert axes, which sends Tunix's loss down its per-segment aggregation.
- `compile_engine_router_replay` has the rollouts return their MoE routing, which the micro-batch carries as
  `routed_experts` (`[sequences, tokens, layers, top_k]` int16) wherever Tunix's assembler carries it. Tunix's packed
  assembler currently leaves it out, and the tool says so when the micro-batch it compiles has no routing.
The GRPO options are rejected, rather than ignored, without `compile_engine_loss=grpo`.

### 11. Documentation
Adds `src/maxtext/training_engine/README.md`: how to run the standalone script, how to use the engine from Python, how to run
the AOT memory report (also with Tunix's GRPO loss) and the tests; "Running fast on TPU" (the libtpu flag,
`cast_grads_after_all_reduce`, float32 gradients, profiling a large step within the profiler's trace-size limit); a full
Qwen3.5-397B-A17B recipe for 128 TPU v7x chips with bfloat16 and float32 variants and the memory check; the TPU v7x results;
the flow of one optimizer step, the sharding rules, the config keys the engine honours, and how to read the memory report.

## Shortcomings and possible future improvements
- **Auxiliary losses under gradient accumulation.** With more than one micro-batch, `pre_train/train.py` adds auxiliary
  losses (MoE load balancing, MTP, indexer) to the unnormalized cross-entropy sum before dividing by the token count, which
  scales them down; the engine weights them as `pre_train/train.py` does without accumulation. When these losses are enabled,
  the engine's logged loss and perplexity also include them. All are off by default (for example
  `load_balance_loss_weight: 0.0`).
- **Routed-bias updates** (used by some DeepSeek configs) are not applied by the engine; such configs should be rejected
  explicitly.
- **Throughput.** Matching `pre_train/train.py` on large TPU configurations needs the libtpu flag and
  `cast_grads_after_all_reduce` (section 9), which are opt-in because they can raise device memory.
- The AOT report's peak covers the three training kernels only; with the default `use_weight_converter=true` the weight-sync
  copy is not estimated.

Results on the final tree: the engine suites pass 138 tests (the same 4 failures as the base branch, listed below), the
new test files pass (model build, mid-step checkpoint, compile parity, gradient cast), the script and parity suite passes
4 of 4, the compile tool's 63 of 63 with 37 subtests (including the GRPO path, packing and router replay), and the config tests 179 of 179. With the accumulate kernel, five of the six parity cases stay bit-exact; the all-float32 AdamW case
moves from exact to within its unchanged gate, because the token-embedding gradient is now summed in source order rather than
in the order XLA's fold chose (the same fold `pre_train/train.py` gets). The existing engine suites give the same results with and without this change; the same three
tests and one packing subtest fail on the base branch as well (`test_maybe_register_pathways_persistence`, two profiling
tests and `small_pack`). With `cast_grads_after_all_reduce` off, the compiled kernels are unchanged. The config tests
(`tests/unit/configs_test.py`, `configs_value_test.py`, `pyconfig_test.py`) pass. pyink and pylint report no new
findings on the changed files.

**On TPU v7x**, Qwen3.5-397B-A17B at the MLPerf trainer configuration: 128 chips (256 devices), fsdp 32 x context 4 x
expert 2 with `cp-as-ep`, sequence length 65,536, 1,024 sequences per step (16 micro-batches of 64), float32 weights,
bfloat16 compute, AdamW. The engine rows ran this PR's code with the standalone script; steady state over the steps after
step 0 (spread under 0.1 s). The full flags are in the README's recipe.
