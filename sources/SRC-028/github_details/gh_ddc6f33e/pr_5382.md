## c4_mlperf: read and cache each host's own eval batch once

On the MLPerf DeepSeek eval split (c4/en:3.0.9: 2048 tfrecord files of one pre-tokenized 32,768-token example each, so one example per host at 128 hosts), every eval made every host read the eval files from GCS again. Three things combined. The eval dataset is sharded after reading, so host i reads files 0..i to find its first example, and the tfds interleave and the prefetch read further ahead. The in-memory `cache()` covers the host's whole shard (16 examples) while the eval loop consumes `num_batches` (= 1) batch and breaks, and a partially read cache is discarded when the iterator is reset, so it never completed. And the eval iterator was built twice per eval (the explicit `reset()` in train.py, then again in `MultiHostDataLoadIterator.__iter__`).

Since the eval is a collective, the slowest host sets the eval time. In one 512-chip wave we saw evals of 7-55 s against a 1.5 s floor, only on the eval path, in wall-clock windows shared across runs, with one host blocking 18.5 s inside its pre-eval reset. The eval bucket served 10.9-19.4k req/s in the minutes of that wave against at most 1.35k req/s in the train-only minutes before it (which of the two drives the other is open).

### Changes

1. `preprocess_eval_dataset`: `take(num_batches)` before `cache()`, so the first eval completes the cache and later evals read from host memory. The eval loop never consumes more than `num_batches` batches, so the batches it sees are unchanged.
2. `make_c4_mlperf_eval_iterator`: `shard_in_read=True` when every file of the split holds exactly one example and there are at least as many files as loading hosts (checked from the split's file instructions in dataset_info). Host i then opens only files i, i + n, ..., which select the same examples in the same order as sharding after reading. Other layouts (e.g. c4/en:3.0.1 with many examples per file) keep sharding after reading, since sharding by file would change which examples a host gets.
3. `MultiHostDataLoadIterator.__iter__` skips the rebuild when `reset()` was just called and nothing has been read since. The explicit reset in train.py is the one correctness depends on, because `_ReorderedDataIterator` and `RemoteIteratorWrapper` return `self` from `__iter__` without resetting. The reset in `__iter__` stays for plain for loops (the `test_for_loop_repeatable` tests).

### Tests

`EvalReadsOwnFilesOnceTest` writes a local split of 2048 one-example files and counts the files the tfds reader reads, for hosts 0, 5, 64 and 127 of 128. The eval batch (all six features) is identical between the old read path and the new one on every eval, the first eval reads only the host's own files, later evals read none, and one eval is exactly `num_batches` long. It sleeps 0.5 s between evals to stand in for the train step, during which the prefetch completes the truncated cache; on a heavily loaded runner that window is the timing dependence of the test. A train_utils test checks that `reset()` followed by a for loop builds one local iterator.

On the real split (read-only, CPU), the eval batches of hosts 0, 5, 64 and 127 are byte-identical before and after the change, and host 127 reads its own 16 files on the first eval and 0 files on the next three. `pytest -m "not tpu_only and not gpu_only"` on the c4 / input pipeline tests and the train / config / MoE tests: the same 17 grain tests fail before and after for lack of local gcsfuse data; everything else passes.

### Validation on hardware

Two 512-chip runs of the MLPerf DeepSeek recipe with this change (same seed and flags as a run without it, images differing only in these two files): the first three evals take 1.58 / 1.45 / 1.45 s in the mllog against 3.70 / 4.42 / 3.67 s without the change, and every later eval takes 1.43-1.56 s (20 evals, none over 3 s). Train step time (3.666 vs 3.667 s) and loss (within 0.055 through step 42) are unchanged. Neither run showed the multi-second eval stalls that appeared in 7 of the earlier runs.
