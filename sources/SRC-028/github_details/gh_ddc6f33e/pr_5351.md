## 正文

## What

`decoder_segment_ids` reached `Qwen3NextGatedDeltaNet` only as `!= 0`, i.e. as a padding mask. When several sequences share a row -- which is what tunix's GRPO packer emits, up to `MAX_SEGMENTS_PER_PACKED_ROW` (16) of them per row in `mlperf_35b_256.sh` -- the delta-rule scan ran straight through the boundaries. Every sequence after the first read the recurrent state left behind by its predecessor, and the depthwise causal conv mixed the predecessor's last tokens into its first `gdn_conv_kernel_dim - 1`.

Qwen3.5-35B-A3B has 30 GatedDeltaNet layers out of 40, and `use_gdn_kernel` is `false` by default, so this is the path the MLPerf run takes.

## How

* `jax_chunk_gated_delta_rule` takes `segment_ids` and restarts the recurrence wherever the id changes. Boundaries are not assumed to be chunk-aligned: tunix's `pack_bin` advances its cursor by the exact sequence length, so they land anywhere inside a chunk. The cumulative decay is measured from each token's own segment start, and every cross-segment pair is masked before the `exp`, so no masked entry becomes `inf` and no difference is taken across a reset.
* `segmented_causal_depthwise_conv1d` evaluates the convolution one tap at a time and drops taps whose source token is in a different segment.
* Padding (id 0) is folded into the sequence that precedes it, so a trailing pad tail does not reset the state prefill hands back to the cache, and the first real token of a left-padded row still receives `initial_state`. Unpacked callers and callers that pass no ids are unchanged.

## Measurements

Four stacked GDN layers, one row holding two packed sequences, comparing the second sequence against the same tokens run alone:

| | before | after |
| --- | --- | --- |
| conv width 4, float32 | 76.7% relative error | 0 (bit-exact) |
| conv width 1, float32 (recurrence only) | 26.4% | 0 |
| conv width 4, bfloat16 | -- | 0 |

The sequence before the boundary matched exactly either way, as causality requires.

Eight sequences of length 17/23/9/41/5/33/28/51 packed into a 256-wide row, so most 64-token chunks hold more than one boundary, each checked against its solo run: worst disagreement 9.2e-5 in float32 and 7.0e-2 in bfloat16, against an output scale of roughly 7.5. That residue is reassociation, not state leakage -- a sequence sits at a different offset within its chunk in the packed and solo layouts, so the chunked matmuls group the same terms differently. Gradients through the packed row were finite.

## What this does and does not establish

This is a correctness fix. Before it, the model computed the wrong function on every packed row in 30 of its 40 layers, and gradients were taken of that wrong function.

It is **not** established that this is the origin of the `grad_norm: nan` in the 35B-A3B GRPO run. No probe produced a NaN from the unpatched GDN path on its own; the observed effect is large numerical error, not a non-finite value. A run of the same recipe from `atwigg/mlperf` HEAD with `--skip_step_on_nan` showed NaN on steps 1, 4, 5 and 6 and clean gradients on 0, 2, 3 and 7 through 13. The packed-segment bleed is present on every step, so it is not sufficient on its own -- a second, batch-dependent ingredient is involved. Whether this branch removes the NaN has to be measured, not inferred; the skip-enabled run gives a rate (4 in 14) to compare against.

## Not covered

* **Context parallelism.** The recurrence keeps its previous behaviour: the ids are withheld at the `shard_map` call site, with a `TODO` there. A shard would have to know whether a boundary falls in a later shard before handing its state on, and `kernels/attention/gdn_cp.py` folds a shard's chunks into a single affine map. The convolution is segment aware on every path including CP, so under CP one of the two leaks is fixed rather than neither.
* **The Pallas kernel path** (`use_gdn_kernel: true`) resets only at chunk-aligned boundaries (`kernels/gdn/gdn_bwd/pallas_mosaic_tpu_bwd.py`), so it is also wrong for unaligned packing. Not touched here. Either the kernel needs arbitrary boundaries or tunix's packer needs to align to `gdn_chunk_size`.
