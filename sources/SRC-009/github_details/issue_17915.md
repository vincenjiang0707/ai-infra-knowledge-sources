### Reproduction

The server entry points in `tensorrt_llm/commands/serve.py` bind their own socket and hand it to
uvicorn via `sockets=[...]`. That bypasses uvicorn's socket setup, so the `SO_REUSEADDR` uvicorn
normally applies is never set.

After any exit with established connections, the port cannot be rebound for its TIME_WAIT window
(~60s) even though nothing is listening.

Any supervised deployment restarting the server hits this: systemd `Restart=always` and Kubernetes
CrashLoopBackOff both retry faster than TIME_WAIT expires, so the restart fails on bind and the
supervisor backs off — turning a quick restart into a multi-minute outage.

### Expected behavior

The server can rebind its port immediately after exit, as it would with uvicorn's own SO_REUSEADDR.

### actual behavior

The port cannot be rebound for its ~60s TIME_WAIT window even though nothing is listening, so supervised restarts fail on bind and back off.

### additional notes

Bind and immediately listen on the server sockets, so the reuse semantics uvicorn would have applied
are preserved.

Two consequences worth stating up front:

1. The socket starts listening before model initialization completes, so TCP-connect-only readiness
   probes can report success before the HTTP application can respond. Deployments should use an
   HTTP response-based readiness check.
2. On Linux, reusing a `TIME_WAIT` address requires both the previous and replacement sockets to have
   had `SO_REUSEADDR`. The first restart after upgrading from an unpatched process may therefore
   still hit the old behaviour; subsequent restarts benefit.

Verified behaviourally with plain sockets — no GPU or model required.

**Questions for maintainers**

1. Is the earlier listen acceptable, or would you prefer the socket created with the right options
   but listened on later?

Per CONTRIBUTING.md this Issue Request precedes the patch, which is ready and applies cleanly to `main` @ `fbda11f5`.

### karljang · 2026-09-05

Thank you for reporting this.
This is already fixed on main. `tensorrt_llm/commands/serve.py:636-641` sets `SO_REUSEADDR` on the server socket before it binds, with a comment naming the same TIME_WAIT rebind window the report describes and the same reason it has to be set on the socket that owns the port first rather than only on the later bind. The other server entry points in that file do the same at lines 874, 1959 and 2288. The fix took the option-setting route rather than the bind-and-immediately-listen route, which means the concern you raised about listening before model initialization completes does not arise — readiness probes see the same behaviour as before.
