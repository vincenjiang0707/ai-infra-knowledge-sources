## 正文

## What this PR does / why we need it?

Compose pipeline parallelism, sequence parallelism and DSpark for Kimi-K3 on Model Runner V2, following the GLM-5.2 DSpark+PP layout (#15747).

K3 with expert parallelism and TP > 1 keeps sequence shards across PP stages (e.g. 8 of 64 rows at TP8), while the V2 receive path slices by the full token count. The fix mirrors MRV1's proven `sync_and_slice_intermediate_tensors` SP branch on the V2 runner: the persistent receive backing is narrowed to a local view around the upstream copy and restored after each invocation. Graph capture is untouched — the sharding lives entirely in the runner's tensor handoff path, like MRV1.

- **Spec+PP support table**: Kimi K3 targets (`KimiLinearForCausalLM`, `KimiK3ForCausalLM`, `KimiK3ForConditionalGeneration`) join `dspark` support next to DSV4 and GLM-5.2, with aux hidden states and the upstream PP guard bypass. Local K3 MLA (`K3DSparkModel`) and legacy GQA (`Qwen3DSparkModel`) drafts validate as PP=1 on the last stage.
- **PP+SP token sharding** (kimi_k3.py, AttnRes path used by K3 checkpoints): first-stage-only embedding sharding; matching hidden/residual shards carried between stages; last-stage gather; dense MLP layers gather and reduce-scatter around their TP-sharded weights while routed MoE keeps its SP path. Configurations without attention residuals keep the upstream forward unchanged.
- **Aux-state relay**: target stages carry cumulative auxiliary states on the existing transport keys; MLA drafts consume raw prefix sums without the three-dimensional AttnRes bank; legacy GQA keeps materialized capture.
- **Host-position sync**: CPU attention lengths resynchronize on every PP stage after speculative rejection (including stages without a local speculator) and after non-final prefill chunks; attention-metadata preparation waits for the copy.

## Scope notes

- K3 SP+PP under `FULL_DECODE_ONLY` graphs is **not** covered by this port (graph capture is untouched) and needs separate validation.
- MRV1 PP+SP support, the tutorial update, e2e and the sandbox-style CPU regression suite from the source branch are excluded per review scope.

## Adaptation since #16511

- `dspark` PP architecture table: union of #16511's K3 entries with main's GLM-5.2 entry.
- The buffer handling nests under main's `pcp_dispatch_context` and keeps the 0.29.0+ `valid_dummy_state_slots` signature.
- The graph-side buffer management from the source branch is dropped; the slicing follows MRV1's naming and placement instead.

### PP draft embedding ownership (follow-up fix)

vLLM main's `maybe_share_target_embed` raises when the K3 DSpark draft loads on the last PP stage — the draft shares the target input embedding (`has_own_embed_tokens = False`, checkpoint copy dropped by the upstream mapper) but the target embedding lives on PP stage 0:

```
RuntimeError: AscendK3DSparkForCausalLM needs the target input embedding, but it is unavailable on this PP stage
```

Following the pattern upstream uses for Qwen3 DSpark (weight-driven `has_own_embed_tokens`), the Ascend draft now constructs a `VocabParallelEmbedding` and loads the frozen `embed_tokens` copy shipped in the draft checkpoint when the real PP group spans multiple stages, and declares `has_own_embed_tokens` on the instance so the share check keeps it instead of raising. `lm_head` still aliases the target's last-stage head. PP=1 keeps upstream aliasing unchanged. Ownership is decided from `get_pp_group().world_size` (the draft's construction config always reports PP=1).

## Does this PR introduce _any_ user-facing change?

Yes: Kimi-K3 can run PP+SP and PP+SP+DSpark (eager) on the V2 model runner (`VLLM_USE_V2_MODEL_RUNNER=1`). Context-parallel compatibility checks still apply.

## How was this patch tested?

- CPU suites on Ascend aarch64, paired vLLM `84030bbe` — all green (**108 passed**): `tests/ut/models/test_kimi_k3_pp_sp.py` (basic PP+SP path), `tests/ut/worker/v2/test_pp_utils.py`, `tests/ut/patch/platform/test_patch_pp_mtp.py`, `tests/ut/models/test_kimi_k3_adapter.py`, `tests/ut/worker/test_model_runner_v2.py`.
- Functional validation of the underlying implementation: see #16511 (4x8 NPUs, DP1/TP8/PP4, PP+SP+MLA-DSpark, 3x120/120 requests, deterministic correctness probes).
- No hardware rerun for this port, per request.
