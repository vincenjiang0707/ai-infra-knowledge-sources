## 正文


## 问题概述

Kimi-K3 部署（MLA + MegaMoe，TP16 × 16 张 Ascend 910_93）在 prefill 跨 chunk 边界的第一步稳定打挂引擎。通过进程内探针定位到失败调用是 `MLAChunkedPrefill._compute_prefill_context`（`vllm_ascend/attention/mla_v1.py`，#15219 引入的 chunked-context 循环）里的 `DeviceOperator.kv_cache_load` → **`torch_npu.npu_gather_pa_kv_cache`**。

> **（2026-09-26 更正）** 本文最初把失败模式 1 归因为「聚集跨 ≥12 个 KV block 的尺寸上限」，该结论**不准确**：真正的触发条件是 **KV 池张量的维度顺序（布局）**，尺寸阈值只是布局错配的表象，且随算子库构建在 11~12 块之间漂移（旧布局下 64 块也正常）。详见下文「布局 A/B 实验」。

当前确认的**两个相互独立的失败模式**：

1. **不兼容 PR #16456 后段 commit 引入的 BNBD KV 池布局（根因）**。[PR #16456](https://github.com/vllm-project/vllm-ascend/pull/16456)（[Feature] Support token-fused and component-major MLA cache for A3/A5）自第 10 个 commit `b6e38b72f`（[Feature] Expose MLA cache in BNBD layout）起把 MLA KV 池布局改为 BNBD；`vllm_ascend/attention/mla_v1.py` 中池 shape 维度顺序的翻转落在 `0ce302338`：

   ```diff
   -        return num_blocks, block_size, num_kv_heads, head_size   # 旧布局 BSND
   +        return num_blocks, num_kv_heads, block_size, head_size   # 新布局 BNBD
   ```

   CANN 9.1.0 / 9.2.0 的 gather tiling 按旧布局（block_size 在 dim-1）解读输入，新布局下内部寻址越界，当一次聚集触碰的 token 数超过某个**构建相关**的边界后即挂死 / EZ9999。作为对照：跑在**旧布局**代码上（PR #16456 前 9 个 commit，本地 cherry-pick 链经 patch-id 比对与 `64c73c68e` 等价）的服务，处理 20k-40k token 长请求、跨 chunk 聚集 64 块，全程无错。
2. **非连续（交错）KV 池，与布局无关的独立问题**。池张量是 block 维步长为 `3 × block_size` 个元素的非连续视图时——这正是 `--cp-kv-cache-interleave-size 384`（384 token = 3 × 128-token 块，交错布局）产生的 per-rank 池布局——**哪怕只聚集 384 token（3 块）也挂**；且换到旧布局 BSND 下复测仍崩（507057），确认与布局无关。步长 `16 × block_size`（4096 B，页对齐）的视图正常，怀疑是 stride/对齐处理问题。

所有失败的表现一致：异步下发被接受，随后流/设备同步失败，报 `507035`（"The vector core execution is abnormal"，`rtDeviceSynchronizeWithTimeout`）。服务内约 30ms 后表现为 16 个 rank 全部 `RuntimeError: SUSPECT REMOTE ERROR, EZ9999`，CANN tiling 日志报 `blockSize is invalid`（`gather_pa_kv_cache_tiling.cpp`），引擎死亡。

## 环境

- 硬件：Atlas 800I A3（Ascend 910_93），单机 16 卡。复现只需 1 张卡。
- CANN 9.2.0（ascend-toolkit），固件/驱动 25.5.1.1
- torch 2.10.0，torch_npu 2.10.0.post6，Python 3.12
- vllm：源码安装，v0.11.0（commit `84030bbe3d`）
- vllm-ascend：源码安装，commit `b2b201ce0`（即 PR #16456 分支第 15 个 commit，**含 BNBD 布局变更**）+ 内部 MegaMoe 补丁（与本代码路径无关；`kv_cache_load` / `_compute_prefill_context` 路径来自 #15219）
- 安装方式：vllm 与 vllm-ascend 均**从源码**安装：`pip install --no-deps --no-build-isolation`（vllm 加 `VLLM_TARGET_DEVICE=empty`，不编译 CUDA 扩展），装到共享前缀后通过 `PYTHONPATH` 激活。被测算子是 torch_npu 2.10.0.post6 自带的 CANN 内置算子。我们的服务另加载了 MegaMoe 自定义算子包（`cann_ops_transformer_custom`），但下面的独立复现**不需要**它。

## 独立最小复现

每个用例必须在**全新进程**中运行（一次挂死会污染后续调用）。外层加 `timeout`，例如 `timeout 100 python3 repro_gather.py --tokens 1408 --layout bnbd`。

```python
#!/usr/bin/env python3
"""npu_gather_pa_kv_cache 挂死最小复现（含池布局变量）。

用法：
  python3 repro_gather.py --tokens 384  --layout bnbd           # 新布局（BNBD），小聚集
  python3 repro_gather.py --tokens 1408 --layout bnbd           # 新布局，11 块（多数构建挂死）
  python3 repro_gather.py --tokens 8192 --layout bsnd           # 旧布局（BSND），64 块（通过）
  python3 repro_gather.py --tokens 384  --layout bsnd --stride 3  # 旧布局 + 非连续交错视图（挂死）
"""
import argparse
import torch
import torch_npu

p = argparse.ArgumentParser()
p.add_argument("--block-size", type=int, default=128)
p.add_argument("--tokens", type=int, required=True)
p.add_argument("--layout", choices=["bsnd", "bnbd"], default="bnbd",
               help="bsnd = (blocks, block_size, heads, head_dim)，旧布局；"
                    "bnbd = (blocks, heads, block_size, head_dim)，PR #16456 新布局")
p.add_argument("--stride", type=int, default=1,
               help="block 维步长（以 block_size 为单位）；1 = 连续")
p.add_argument("--device", type=int, default=0)
a = p.parse_args()
torch.npu.set_device(a.device)
bs, toks = a.block_size, a.tokens

def make_pool(pe: bool):
    dim = 64 if pe else 512
    if a.layout == "bsnd":
        full = torch.randn(2583, bs * a.stride, 1, dim, dtype=torch.bfloat16, device="npu")
        return full[:, ::a.stride, :, :] if a.stride > 1 else full
    else:
        full = torch.randn(2583, 1, bs * a.stride, dim, dtype=torch.bfloat16, device="npu")
        return full[:, :, ::a.stride, :] if a.stride > 1 else full

pool = make_pool(pe=False)
pool_pe = make_pool(pe=True)

nb = (toks + bs - 1) // bs                                   # 触碰的 KV block 数
bt = torch.arange(nb + 4, dtype=torch.int32, device="npu").view(1, nb + 4)
bt[0, nb:] = 0                                               # 有效块 id，之后补 0
csl = torch.tensor([toks], dtype=torch.int32, device="npu")
off = torch.zeros((1,), dtype=torch.int32, device="npu")
key = torch.empty(toks, 1, 512, dtype=torch.bfloat16, device="npu")
val = torch.empty(toks, 1, 64, dtype=torch.bfloat16, device="npu")

print(f"case: layout={a.layout} pool={tuple(pool.shape)} stride={a.stride} "
      f"toks={toks} blocks={nb}", flush=True)
torch_npu.npu_gather_pa_kv_cache(pool, pool_pe, bt, csl.contiguous(),
                                 seq_offset=off, key=key, value=val)
torch.npu.current_stream().synchronize()
print("RESULT: OK", flush=True)
```

## 实测结果（单卡空闲设备，每用例独立进程）

> 注：下表用例的池张量均为 **BNBD 新布局**（对应含 PR #16456 后段 commit 的树）。旧布局（BSND）下同一批尺寸**全部通过**（见下节 A/B 实验），因此「≥12 块」应读作「BNBD 布局下的构建相关边界」，不是算子的内禀尺寸限制。

| block_size | tokens | 触碰块数 | 池 | 结果 |
|---|---|---|---|---|
| 128 | 384 | 3 | 连续 | OK |
| 128 | 1024 | 8 | 连续 | OK |
| 128 | 1025 | 9 | 连续 | OK |
| 128 | 1152 | 9 | 连续 | OK |
| 128 | 1280 | 10 | 连续 | OK |
| 128 | 1408 | 11 | 连续 | OK |
| 128 | 1472 | 12（11 整块 + 1 部分） | 连续 | **挂死（507035）** |
| 128 | 1536 | 12 | 连续 | **挂死（507035）** |
| 128 | 1920 | 15 | 连续 | **挂死（507035）** |
| 128 | 3840 | 30 | 连续 | **挂死（507035）** |
| 128 | 384 | 3 | 视图，dim-2 步长 3×128 元素（3072 B） | **挂死（507035）** |
| 128 | 384 | 3 | 视图，dim-2 步长 16×128 元素（4096 B） | OK |

（上表测于一个算子库构建；另一个构建上 1408 token / 11 块即崩——边界随构建漂移。）

挂死用例的报错输出：

```
[Error]: The vector core execution is abnormal.
EE9999: Inner Error!
EE9999: rtDeviceSynchronizeWithTimeout execution failed, reason=vector core exception
        [FUNC:FuncErrorReason][FILE:error_message_manage.cc][LINE:69]
```

注意：挂死会把 NPU 打成坏状态——挂过一次之后，连之前正常的用例也会以同样的 `vector core exception` 失败，直到物理卡被复位（容器内 `npu-smi set -t reset` 被拒绝，我们只能重建容器/复位卡）。这一点本身也值得算子侧加固。

## 布局 A/B 实验（决定性证据）

同一台机器、同一 CANN、同一算子库，**唯一变量 = 池张量的维度顺序**（用上面脚本的 `--layout` 参数）：

| 池布局 | shape | tokens | 触碰块数 | 结果 |
|---|---|---|---|---|
| BSND（旧） | (2583, 128, 1, 512) | 8192 | 64 | OK |
| BSND（旧） | (2583, 128, 1, 512) | 384 | 3 | OK |
| BNBD（新） | (2583, 1, 128, 512) | 1408 | 11 | **EZ9999（MTE 访问非法 GM 地址）** |
| BNBD（新） | (2583, 1, 128, 512) | 384 | 3 | OK |
| BSND（旧）+ block 维步长 3×128 非连续视图 | (2583, 128, 1, 512) | 384 | 3 | **崩（507057）** |

- 同矩阵在 **CANN 9.1.0 上结果完全一致**（BNBD 1408 崩 / BSND 8192 OK）→ 降级 CANN 不能规避，两个版本的 tiling 都不认新布局。
- 最后一行证明「非连续视图」问题与布局无关，是独立的第二个问题。
- 代码侧对照：池 shape 翻转前的树（PR #16456 前 9 个 commit）+ 20k-40k token 长请求 + `--max-num-batched-tokens 8192` 多 chunk prefill（即 64 块聚集）全程正常；翻转后（`b2b201ce0`）同样的负载在第一次跨 chunk 边界即崩。

## 从 vllm-ascend 服务的触发路径

`MLAChunkedPrefill._compute_prefill_context`（#15219 引入）在每层、每个 chunk 边界步调用一次 `kv_cache_load`；聚集的上下文是前面 chunk 已产出的 prefix，因此 `--max-num-batched-tokens 4096` 时第一次跨边界聚集就是 ~3840 token（30 个 128 块）→ 触发失败模式 1（此时池为 BNBD 新布局）。另外，服务带 `--cp-kv-cache-interleave-size 384` 时 per-rank KV 池是交错的非连续视图（dim-2 步长 3072 B）→ 触发失败模式 2；我们在 DCP=16 部署上单独确认过（该路径每次聚集只有 384 token）。

## 规避方式

- **失败模式 2（非连续池）**：调用前对池张量做 `.contiguous()`，服务内已验证。
- **失败模式 1（BNBD 布局）**：在 `kv_cache_load` 调用点把池 transpose 回旧布局 BSND 并 `.contiguous()`（等价于一次 contiguous 拷贝）。尺寸本身不是限制（旧布局 64 块聚集通过），**无需**切块循环——早前版本建议的「≤11 块切块循环」基于已更正的尺寸结论，作废。
- **根治**：CANN 算子侧适配 BNBD 布局（或给出明确报错），或 vllm-ascend 侧统一布局。

## 期望 vs 实际

- 期望：`npu_gather_pa_kv_cache` 对新旧两种池布局（BSND / BNBD）、连续与交错（strided view）的池都能正常工作；至少应在 tiling 阶段对新布局给出明确报错，而不是内核挂死/越界写。
- 实际：BNBD 布局（PR #16456 后段 commit 引入）超过构建相关 token 边界的聚集挂死（507035 / vector core exception）；任意布局下 block 维步长 3×block_size 的非连续视图任意聚集大小都挂死。

## 2026-09-26 更正说明

本 issue 的失败模式 1 已重新归因，标题与正文已同步更新。

**更正前**：聚集上下文跨 ≥12 个 KV block 时内核挂死（当作算子的内禀尺寸限制）。

**更正后**：触发条件是 **KV 池张量的维度顺序**。PR #16456 自第 10 个 commit `b6e38b72f`（[Feature] Expose MLA cache in BNBD layout）起把 MLA KV 池布局改为 BNBD（`vllm_ascend/attention/mla_v1.py` 中池 shape 翻转落在 `0ce302338`：`(num_blocks, block_size, num_kv_heads, head_size)` → `(num_blocks, num_kv_heads, block_size, head_size)`）。CANN 9.1.0 / 9.2.0 的 gather tiling 按旧布局（block_size 在 dim-1）解读输入，新布局下内部寻址越界——「≥12 块」只是该错配下随算子库构建在 11~12 块间漂移的表象；**旧布局下 64 块聚集完全正常**。

关键证据：

1. 同机同 CANN 的布局 A/B（唯一变量 = 维度顺序）：BSND 8192 token / 64 块 → OK；BNBD 1408 token / 11 块 → EZ9999（MTE 访问非法 GM 地址）；BNBD 384 / 3 块 → OK。CANN 9.1.0 结果一致（降级不能规避）。
2. 代码侧对照：使用 PR #16456 前 9 个 commit（本地 cherry-pick 链，patch-id 与 `64c73c68e` 等价）的旧布局树跑 20k-40k token 长 prompt + 多 chunk prefill（64 块聚集）全程无错；同一负载换到含布局变更的 `b2b201ce0` 后首次跨 chunk 边界即崩。
3. 失败模式 2（非连续交错视图）在旧布局 BSND 下复测仍崩（507057），确认为**独立的第二个问题**，维持原结论。

复现脚本已更新（新增 `--layout bsnd|bnbd`）。规避方式相应更新：调用点做布局适配（transpose + `.contiguous()`）即可，无需切块循环——原「≤11 块切块」建议基于已更正的尺寸结论，作废。
