# [PR #16930] [BugFix][KV Transfer] Register class-name aliases for KV connectors

state: open | updated: 2026-09-26T10:24:29Z

## 正文

### What this PR does / why we need it?

`MultiConnector` keys per-request transfer stats by `__class__.__name__` (`multi_connector.py::get_kv_connector_stats`) and, on the logger side, resolves those keys back through `KVConnectorFactory.get_connector_class_by_name`. The factory registry is indexed by the `kv_connector` config name, so any connector registered under a config name that differs from its class name fails the stats reconstruction lookup with:

```
ValueError: Connector 'AscendOffloadingConnector' is not registered.
```

That exception is raised in `AsyncLLM.output_handler`, which propagates it and tears down EngineCore (in-flight requests then fail with 500).

This PR registers the class names as additional aliases for the two KV connectors that emit stats while being registered under a different config name:

- `AscendOffloadingConnector` (config name `OffloadingConnector`)
- `UCMConnectorV1` (config name `UCMConnector`)

`AscendSimpleCPUOffloadConnector` (config name `SimpleCPUOffloadConnector`) does not override `get_kv_connector_stats` and inherits the base no-op that returns `None`, so it never enters this path and needs no alias. Likewise, connectors that are registered under their own class name (e.g. `AscendStoreConnector`) are unaffected.

The same mismatch also exists for `MooncakeD2RHConnectorV1`, whose class was named `MooncakeConnector` and which does emit stats (inherited from `MooncakeBaseConnector`). It cannot be fixed with a class-name alias: the key `MooncakeConnector` belongs to the upstream registration, and aliasing it would re-point `kv_connector="MooncakeConnector"` at the Ascend D2RH class. The class is renamed to its config name instead, with `MooncakeConnector` / `MooncakeD2RHConnector` kept as back-compat aliases. Without the rename, MultiConnector stats reconstruction resolves the key to the upstream class and rebuilds an upstream `MooncakeKVConnectorStats` holding the Ascend 3-key dict — a `KeyError` on every stats interval (the same teardown path as #16932, a different exception).

A matching upstream guard against unknown connectors in `MultiConnector.build_kv_connector_stats` is proposed separately in vLLM: [vllm-project/vllm#57683](https://github.com/vllm-project/vllm/pull/57683).

### Does this PR introduce _any_ user-facing change?

No API/interface change. It restores KV transfer stats for the two connectors above (previously lost) and prevents an EngineCore crash. The alias names are not intended to be used as `kv_connector` config values.

### How was this patch tested?

- New regression tests in `tests/ut/distributed/kv_transfer/test_connector_registration.py` (11 tests): the two aliases are registered and their stats keys resolve through the real importlib loader; `MultiConnector.build_kv_connector_stats` round-trips the exact #16932 path; the alias override warns and pops a pre-existing entry; the no-alias invariants are pinned (registry negative case + base-default stats); the D2RH class name matches its config name. They fail without the source change and pass with it.
