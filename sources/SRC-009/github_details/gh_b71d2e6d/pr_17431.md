## 正文

### What this PR does / why we need it?

This PR adds PIVOT query-row reuse as a separate, opt-in LightningIndexer operator on Ascend 910B/910_93.

- Adds an independent `PivotLightningIndexer` CANN operator, ACLNN ABI, and PyTorch registration. The native `lightning_indexer` source and ABI are unchanged.
- Adds `additional_config.enable_pivot_lightning_indexer` (default `false`) and routes only the enabled BF16/FP16 SFA indexer path to the new operator.
- Pools consecutive causal query rows in groups of up to four after the 4096-token boundary, runs one proxy LightningIndexer row, replicates its top-k, and restores each row's causal tail.
- Executes the native algorithm inside the new operator for unsupported shapes. Sparse LightningIndexer C8 is rejected explicitly, and A5 rejects the option because this operator is not built there.

Keeping a separate operator makes the optimization reviewable and deployable without replacing the native LightningIndexer package. Disabling the switch preserves the existing path.

### Does this PR introduce _any_ user-facing change?

Yes. Users on Ascend 910B/910_93 can opt in with:

```bash
--additional-config '{"enable_pivot_lightning_indexer":true}'
```

The default remains disabled.

### How was this patch tested?

- Unit coverage for the default/opt-in configuration, separate operator dispatch, sparse-C8 conflict, and A5 rejection. Latest CI CPU suite: 6526 passed, 49 skipped; focused A3 tests: 4 passed.
- Python compile, shell syntax, whitespace checks, and selected unit tests.
- A3 CANN 9.1.0 selected-operator package build and NPU smoke tests for both an active PIVOT shape and an exact fallback shape.
- A3 single-operator matched sweep (112 shapes, 20 warmups + 31 counterbalanced samples/arm): all 94 fallback controls were exactly equal; the 18 active shapes had 1.1098x geomean speedup, rising to 1.2409x for KV >= 64K (13/18 active shapes faster).
- A3 GLM-5.2 MTP3 natural-prompt AISBench on the then-current vLLM `84030bbe` baseline, ten serial requests per arm (40/40 successful):
  - 512 output: mean E2E 166.738s -> 118.288s (1.410x), mean TTFT 150.913s -> 101.887s (1.481x), mean TPOT 30.97ms -> 32.10ms.
  - 1024 output: mean E2E 183.312s -> 133.418s (1.374x), mean TTFT 151.067s -> 102.100s (1.480x), mean TPOT 31.52ms -> 30.61ms.

- Final rebase, unit tests, and single-operator validation use vLLM `0.30.0` (editable source).
