# [PR #17260] [Performance][Mamba] Widen temporal postprocess state copies

## 正文

### What this PR does / why we need it?

Optimize the temporal-state copy in Ascend's `postprocess_mamba_fused_kernel`: use `uint64` transfers when both addresses are 8-byte aligned, copy any 1–7 trailing bytes, and keep byte transfers for unaligned addresses. The copy decision, block mapping, convolution-state path, and kernel API do not change. The accompanying reference test is adapted to the pinned vLLM copy-function interface.

#### Reachable Ascend configurations and impact

The [Ascend worker patch](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/patch/worker/patch_mamba_utils.py) installs this kernel on hardware with `TRITON_BATCH_MEMCPY` (including A5). It is reached through vLLM's hybrid Mamba postprocessing in `mamba_cache_mode=align`: V1 requires the hybrid speculative path; V2 uses the hybrid model state's align postprocess. Prefix caching selects align mode for these hybrid models. Within the kernel, the modified branch executes only when the postprocess decision copies a temporal state (`conv_width == 0`); model support alone does not mean every request copies. [vLLM V1 postprocess](https://github.com/vllm-project/vllm/blob/84030bbe3d74d99bad477a3d2e37a973ccd8865c/vllm/v1/worker/mamba_utils.py) · [vLLM V2 hybrid state](https://github.com/vllm-project/vllm/blob/84030bbe3d74d99bad477a3d2e37a973ccd8865c/vllm/v1/worker/gpu/model_states/mamba_hybrid.py)

Validation is restricted to two configurations represented in `vllm-ascend`'s own model/e2e code:

| Ascend configuration | Why this route is relevant | Per-layer temporal state | Bytes copied when selected |
| --- | --- | --- | ---: |
| Kimi K3 dummy target, TP4, prefix caching, align, DSpark (one KDA layer in the reduced [four-card e2e config](https://github.com/vllm-project/vllm-ascend/blob/main/tests/e2e/pull_request/four_card/test_kimi_k3.py)) | `vllm-ascend` registers `AscendKimiLinearForCausalLM`; its inherited KDA state copy supplies a conv and recurrent state. The e2e config sets `linear_attn_config.num_heads=96`, `head_dim=128`, TP4. KDA's default recurrent cache dtype is FP32. | `(24, 128, 128)`, FP32 | 1,572,864 |
| Qwen3-Next-80B-A3B-Instruct, TP4, BF16, MTP, **prefix caching/align enabled** | The [Ascend four-card MTP test](https://github.com/vllm-project/vllm-ascend/blob/main/tests/e2e/pull_request/four_card/spec_decode/test_mtp_qwen3_next.py) establishes this model/TP/speculative combination; prefix caching is the additional gate for the align postprocess. Its [model config](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct/blob/main/config.json) has 32 value heads of width 128 and 48 layers, 36 of them GDN. | `(8, 128, 128)`, BF16 | 262,144 |

The Kimi K3 model wrapper is maintained by `vllm-ascend`; Qwen3-Next's model implementation and state-shape formula are in the pinned upstream vLLM, while `vllm-ascend` supplies the worker patch and its NPU execution path. The Qwen3-Next repository e2e test does **not** itself enable prefix caching, so its existing run is not evidence that this exact postprocess kernel was executed. The focused tests below invoke the Ascend kernel with these derived state sizes; they do not load model weights or measure model inference. The generic byte-edge tests remain because address alignment and tails are independent of model configuration.

### Does this PR introduce _any_ user-facing change?

No public API change. Eligible temporal-state copies use a wider internal transfer.

### How was this patch tested?

On one Ascend 950 NPU with vLLM `84030bb`, PyTorch 2.10.0, torch-npu 2.10.0.post4, and triton-ascend 3.2.2+dev20260729205041, **65/65** Ascend-kernel tests passed: 48 byte-level edge combinations (zero length, unaligned addresses, tails, guards), four Kimi K3/Qwen3-Next state-size cases with 1/4 temporal tiles, 12 full-kernel mixed-state cases (the two selected sizes and an unaligned tail, with eager/graph replay and metadata changes), and the existing full-kernel Python-reference comparison. No full-model run was performed for this PR. Ruff check/format, Python compilation, and `git diff --check` passed.

Reproduce from the repository root in an Ascend environment with the pinned vLLM version:

```bash
ASCEND_RT_VISIBLE_DEVICES=0 PYTHONPATH=. python3 -m pytest -q \
  --confcutdir=tests/e2e/nightly/single_node/ops/singlecard_ops/triton \
  tests/e2e/nightly/single_node/ops/singlecard_ops/triton/test_postprocess_temporal_copy.py \
  tests/e2e/nightly/single_node/ops/singlecard_ops/triton/test_postprocess_mamba.py
```

#### Copy-triggered kernel timing on the same A5

Synthetic one-request launches force every temporal copy decision true. They use the selected temporal bytes and recurrent-layer counts (one KDA layer in the reduced Kimi test, 36 GDN layers in Qwen3-Next). Median of seven alternating parent/PR pairs, 100 launches per pair, NPU event timing, `TEMPORAL_TILES=1`; units are **µs per full postprocess kernel launch**.

| Selected synthetic profile | Eager parent → PR | Graph replay parent → PR |
| --- | ---: | ---: |
| Kimi K3 reduced TP4, one KDA layer | 345.35 → 57.61 | 349.18 → 55.24 |
| Qwen3-Next TP4, 36 GDN layers | 117.08 → 56.78 | 121.05 → 23.68 |

These timings isolate a copy-triggered kernel launch. They do not estimate real copy frequency, model latency, or throughput; no model weights were loaded.
