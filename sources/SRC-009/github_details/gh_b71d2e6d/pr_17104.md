Title: [Performance][Attention] Free dead kv_b_proj weight on MLA decode-only nodes

---
### What this PR does / why we need it?

Part 1 of 2 (attention side). On MLA decode-only nodes (PD disaggregated decode / kv-consumer), `kv_b_proj.weight` is absorbed into `W_UV`/`W_UK_T` during `process_weights_after_loading` and the original tensor is never read again at runtime (the only two `self.kv_b_proj(...)` call sites are prefill paths, unreachable on a pure decode node). The SFA backend already disposes it (`sfa_v1.py`); the MLA backend missed the same treatment.

This PR adds a conservative `dispose_layer(self.kv_b_proj)` at the end of MLA `process_weights_after_loading`, gated on:

- `kv_transfer_config.is_kv_consumer` (decode-only role), and
- no weight transfer engine configured (`weight_transfer_config is None`) — the disposal must not break live weight updates / layerwise reload, which re-materialize weights from the checkpoint layout (#15463-class incidents).

On a DeepSeek-V3/V4-class TP8 decode node this frees roughly 0.6–1.2 GiB per card of dead weight residency, which flows directly into the KV cache pool.

Unit tests cover: dispose on kv-consumer, retention without KV transfer, retention under weight transfer.

### Follow-up

Part 2 (quantization side) removes dead fp32 MoE scale copies under MegaMoe — separate commit/PR to keep reviews small.

### How was this patch tested?

- `tests/ut/attention/test_mla_v1.py`: 4 new cases (dispose gating matrix)
- attention + quantization suites: 694 passed / 3 skipped locally
- ruff clean
- NPU e2e (DeepSeek-V3.2 decode node memory before/after) to be confirmed on CI

### What this PR does / why we need it?
This pull request introduces memory optimization for MLA (Multi-head Latent Attention) by disposing of the original `kv_b_proj` weight on KV-consumer (decode-only) nodes once `W_UK_T` and `W_UV` are resident. This frees up dead memory since decode steps read the absorbed weights instead.

However, the current implementation has a few critical issues:
1. It may prematurely dispose of `kv_b_proj` on hybrid nodes (which are both producers and consumers), leading to an `UndefinedTensorImpl` crash during prefill. We should ensure `is_kv_producer` is `False` before disposing.
2. Calling `torch.npu.empty_cache()` per-layer during initialization is a performance anti-pattern that causes expensive device synchronizations. This should be removed.

### Does this PR introduce _any_ user-facing change?
No.
