# [Bug][DeepSeek-V4 Flash][MC2/MoE] EVENT_WAIT times out after 234 seconds and all 16 Decode engines exit

## Summary

In a DeepSeek-V4 Flash P/D deployment on Ascend, all 16 Decode ranks on one node stopped making forward progress during an MC2/MoE stage. On at least two independent EP ranks, the producer stream submitted `eventRecord`, and the consumer stream then waited on the same `eventId`. The event did not reach completed/signaled state. After **234 seconds**, CANN reported `EVENT_WAIT` timeout, `rtEventSynchronize` returned `107020`, and the error propagated through torch-npu and vLLM until all 16 Decode Engine/API processes exited.

This was not host OOM and did not involve MemCache. The node used `MooncakeHybridConnector` as a KV consumer and had no MemCache/mmc container.

Restarting only the 16 Decode model processes in the existing container restored all ports and real traffic. The host, container, Prefill node, and hardware were not restarted.

We need help mapping the producer `eventRecord` to the preceding device task/kernel and identifying the first non-progressing rank/peer and owning layer: MC2 software ordering/deadlock, a stuck MoE/MC2 kernel, HCCS_SW transient, driver/runtime, or device.

All internal IP addresses, hostnames, customer prompts, and private filesystem paths are removed.

```text

  -> consumer stream 42 eventWait on the same eventId

```

`eventRecord` in ATRACE proves that the host submitted a record-event task. It does not prove that the producer stream completed all preceding device work or signaled the event. The later same-`eventId` wait timeout is direct evidence that the consumer did not observe completion.

## Error propagation

After the 234-second timeout:

```text
EVENT_WAIT timeout
  -> rtEventSynchronize returns 107020
  -> torch-npu raises RuntimeError in the worker
  -> worker/EngineCore reports fatal error
  -> vLLM EngineDeadError
  -> all 16 Decode APIs/listeners exit
  -> Prefill-side proxy has no Decode backend
```

The first rank reported by Runtime is the first detector, not necessarily the first rank whose producer work stopped.

## Host-memory exclusion

The failure cgroup recorded:

```text
memory.failcnt=0
oom_kill=0
oom_kill_local=0
under_oom=0
```

The full incident window contained no:

```text
global OOM
rtMallocHost out of memory
Memory_Allocation_Failure
```

Therefore this 16-rank exit was not triggered by host-memory exhaustion. A separate host anonymous-memory growth problem exists in the same broader deployment, but it is not the first-error chain for this incident.

## HCCS and device observations

Current/retained HCCS observations showed link health `OK`. One card/chip CLI lane had cumulative retry/error count `2`, while other lanes were zero. However:

1. the counter had no incident timestamp;
2. the value remained `2` before and after recovery and during delayed rechecks;
3. the host tool could not map that switch-uplink lane to a unique remote EP rank or communication tag.

Therefore this counter is a clue only; it is not enough to identify a physical lane as the first fault.

The device-0 MTE 546 and `MoeDistributeDispatchV2` records appeared after the other ranks had aborted. They cannot replace the earlier event-wait chain as the first cause.

## Recovery control

The container remained `Up` because its PID 1 was `bash`, `RestartPolicy=no`, and there was no container healthcheck. The actual vLLM model processes and all Decode listeners were gone.

Recovery used the original read-only deployment template and started only the 16 Decode model process sets inside the existing container. The following were not restarted or modified:

```text
host
container PID 1
Prefill node
model parameters
NPU hardware
HCCS configuration
```

Post-recovery verification:

```text
16 vLLM parent processes alive
16 NPU worker processes alive
ports 7100-7115 equivalent: 16/16 HTTP 200
existing Prefill-to-Decode real traffic reached every Decode rank
all observed requests returned HTTP 200
```

This shows that the failure was cleared by recreating the application/device execution context. It does not identify which underlying component first lost progress.

## What remains unknown

The retained ATRACE does not map the device task immediately preceding stream 46's `eventRecord` to a concrete kernel/op. Consequently we cannot determine from the current logs:

* the first device task that failed to complete;
* the first non-progressing rank;
* the remote EP peer or communication tag involved;
* whether the producer was blocked in an MC2 software step/order mismatch;
* whether a MoE/MC2 kernel itself stopped;
* whether HCCS_SW, runtime/driver, or device state caused the producer stall.
