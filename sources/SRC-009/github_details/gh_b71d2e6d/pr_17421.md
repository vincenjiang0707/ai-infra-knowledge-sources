## 正文

## What this PR does / why we need it?

Enable MegaMoe (FUSED_MC2) communication on Ascend A2 for prefill batches, in addition to the existing A3 support. Previously A2 prefill always used ALLGATHER/MC2, which is suboptimal for large prefill batches on EP-enabled deployments.

Key changes:

- **A2 prefill MegaMoe routing**: `_select_a2_moe_comm_method` now detects prefill/profile batches (via `attn_metadata.num_prefills > 0`) and routes them to `FUSED_MC2` (MegaMoe) when `enable_fused_mc2=1` and token count exceeds a 64-token threshold. Decode batches continue using ALLGATHER.
- **Dict-type attn_metadata handling**: Correctly extract the first metadata object from dict-type `attn_metadata` (v2/multi-modal path) for prefill detection.
- **num_experts > 512 fallback**: Added an early `ALLGATHER` return when `num_experts > 512` to avoid oversized all-gather.
- **attn_metadata/in_profile_run threading**: `select_moe_comm_method` signature extended with `attn_metadata` and `in_profile_run` parameters; threaded through `set_ascend_forward_context`, `platform.py` (NPUPlatform), and `model_runner_v1.py`.
- **profile_run gate**: `model_runner_v1.py` passes `in_profile_run=True` so the profile dummy-run selects the correct MoE comm method.
- **max_tokens_across_dp consistency**: `platform.py` uses `max_tokens_across_dp` instead of `num_tokens` for MoE comm method selection, ensuring consistent communication method across all DP ranks.

## Does this PR introduce _any_ user-facing change?

Yes. On A2 devices with `VLLM_ASCEND_ENABLE_FUSED_MC2=1` (or `additional_config.enable_fused_mc2=1`), prefill batches will now use MegaMoe (FUSED_MC2) instead of ALLGATHER. This improves prefill throughput for large batches on EP-enabled deployments. Decode behavior is unchanged.

## How was this patch tested?

- **Unit tests**: `tests/ut/test_ascend_forward_context.py` — 25 tests passed.
- **Manual testing**: Qwen3.5-35B (256 experts, `moe_intermediate_size=512`, TP4+EP4) on 4× Ascend 910B3 with `VLLM_ASCEND_ENABLE_FUSED_MC2=1`.
- **Benchmark**: `vllm bench serve` with 50 requests (input_len=1024, output_len=1024, max_concurrency=64):
  - 0 failed requests
  - Output throughput: 1189.86 tok/s (peak 1781 tok/s)
  - Total throughput: 2379.73 tok/s
  - Mean TPOT: 29.98 ms
  - MegaMoe C++ kernel (`npu_mega_moe.so`) compiled and loaded successfully.

- vLLM main: https://github.com/vllm-project/vllm/commit/fe784ff22e630a31fd798f392b01e0a75c18f047
