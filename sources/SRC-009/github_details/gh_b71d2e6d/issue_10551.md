### lemisky · 2026-09-21

Root cause found, and it is not a compiler problem despite what the error says.

The `MLIRCompilationError: [ConvertLinalgRToBinary] encounters error` is a red herring. Three seconds earlier in the log there is the real first exception:

```
triton/backends/ascend/compiler.py:555   lib = ctypes.CDLL(callback_path)
ctypes/__init__.py:376                   self._handle = _dlopen(self._name, mode)
OSError: /tmp/tmpXXXXXXXX/libkernel.so: failed to map segment from shared object
```

That message is glibc's loader reporting `ENOMEM` from `mmap`. It is not about free memory: the box had 979 GB available, `/tmp` had 171 GB free and was not `noexec`, and `dmesg` showed no OOM kill. What was exhausted is `vm.max_map_count`, the per-process limit on the number of VMAs, which defaults to 65530.

The leak is in triton-ascend. To read four `int64` metadata values it `dlopen`s the whole kernel callback library and never unloads it, and `ctypes.CDLL` never calls `dlclose`, so every JIT compilation leaks the mapping for the lifetime of the worker.

Measured on the affected node:

- 7.00 VMAs leaked per compilation (measured directly, 210 VMAs over 30 compilations)
- ~1200 new compilations per day, because dynamic prefill shapes keep missing the JIT cache and the rate never plateaus
- 8639 compilations accumulated over the container's lifetime: `8639 x 7.00 = 60,473`, plus ~4,782 VMAs of process baseline, gives ~65,255 against the 65,530 ceiling

Which matches the observed behaviour exactly: the engine ran for almost exactly five days and then every `dlopen` started failing. Worth noting the container stayed `Up` afterwards, because only EngineCore and the workers became zombies while the API server shell survived, so a container-level health check does not catch this.

Fix submitted upstream: https://github.com/triton-lang/triton-ascend/pull/2328

It releases the handle after the metadata has been copied out. Verified on an Ascend 910B3: 7.00 VMAs leaked per compilation before, 0.02 after, with kernel results and callback metadata unchanged.

Until that is released, raising the limit on the host is enough to keep a deployment alive, and it takes effect immediately without restarting anything:

```bash
sysctl -w vm.max_map_count=1048576
echo 'vm.max_map_count=1048576' > /etc/sysctl.d/99-vllm.conf
```

Persisting `TRITON_CACHE_DIR` to a host volume also helps a lot, since a recreated container otherwise recompiles several thousand kernels on its first day.

Leaving this open until the fix lands. Looking forward to seeing it in a new release.
