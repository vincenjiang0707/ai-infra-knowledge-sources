## Describe the Bug

**开启 `enable_dsa_cp` 会导致 vLLM 引擎在启动阶段 hang（最终 vector core timeout 崩溃）；关闭 `enable_dsa_cp` 即可正常拉起。**（关闭 `enable_dsa_cp` 后服务可正常部署，已由同事独立验证）

具体表现：在 **PD-mixed（单节点混部）** 配置下，当 `additional-config` 中 `"enable_dsa_cp": true`（配合 `--decode-context-parallel-size 16`、`--cp-kv-cache-interleave-size 128`）时，vLLM 在权重加载完成、进入 `profile_run` / cudagraph capture 阶段（尚未承接任何真实请求）即 **全局卡死**：全部 16 张卡的 HCCL AIV 通信 kernel `aiv_all_gather_bfloat16_t` 不返回，等待满 HCCL 的 AIV timeout（约 300s）后报 `vector core timeout`（runtime result = `507034`），最终 `Engine core initialization failed` → ERR99999，引擎无法启动。期间无任何请求，纯启动期 hang。

**根因（来自 plog）：两个 AIV 通信 group 并发冲突导致 HCCL AIV 死锁。** HCCL 自身的 task-exception handler 打印了诊断：

```
[TaskExceptionHandler][PrintCommAivInfo] multi groups include aiv alg, may cause execution stuck.  has aiv group count[2]
groups has aiv list[groupName]: [group_name_103] [group_name_3]
```

即同一时刻存在两个 AIV 通信 group 并发：
- `group_name_3` —— MoE expert-parallel 的 AllGather（vLLM 日志中崩溃点为 `torch.repeat_interleave` → `tag[AllGather_group_name_3]`）
- `group_name_103` —— DCP 开启后引入的 per-layer 通信 group（编号远大于 MoE group）

二者并发触发 AIV 调度死锁，跨 chip 1v1 同步 flag 永久不置位（plog 中 `chips 1v1 sync flag [ping] 0 0 0 ... 179 179 ...`，前 16 个 chip sync=0 未完成），kernel 等满 300s timeout。

**关键反证：将 `"enable_dsa_cp"` 设为 `false`（其它配置不变，保留 MTP）后，`group_name_103` 不再出现，AIV group 并发冲突消除，服务可正常启动并承接请求。** 同事已独立验证此 workaround 有效，确认死锁由 `enable_dsa_cp` 引入的通信 group 与 MoE AllGather 并发所致。

关键错误信息：
- `rtStreamSynchronizeWithTimeout execution failed, reason=vector core timeout`（runtime result = **507034**）
- `Communication_Error_Timeout(EI0002): An timeout occurs when the Notify register waits for execution. Waiting peer end: 0; taskType[Task AIV], tag[AllGather_group_name_3]`
- fault kernel = `aiv_all_gather_bfloat16_t`（HCCL AllGather 的 AIV 通信 kernel，非计算算子）
- `AIV Kernel happen error, retCode=0x30, [vector core timeout]`
- 全 16 卡 `[TaskExecStage][HeartbeatAbnormal] ExceptionType:[Stuck Occurred]`

时间线（同一批 task，全 16 卡完全一致，确定性复现）：
- task 提交时间戳：`03:43:22.xxx`
- 报错时间：`03:48:23`（正好 ~300s，即 HCCL AIV timeout 阈值）

> 背景信息备注：如果不配cudagraph_capture_sizes让框架自动计算shape会先触发一个相关的 cudagraph shape 约束错误（`Can't determine cudagraph shapes that are both a multiple of 6 (num_speculative_tokens+1) ... and 16 (tensor_parallel_size) ... please adjust num_speculative_tokens or disable sequence parallelism`），必须显式配置 `cudagraph_capture_sizes: [6,12,24,48]` 绕过（LCM(6,16)=48）才能走到本 `enable_dsa_cp` 死锁的复现点。

## Expected Behavior

开启 `enable_dsa_cp` 时，vLLM 应能正常完成启动（profile_run / cudagraph capture）并承接请求；不应出现 DCP 通信 group 与 MoE AllGather 并发导致的 AIV 调度死锁、全卡静默卡死 300s 后才报 `vector core timeout`。若 DCP 下移到 attention 层的 per-layer 通信与 MoE EP AllGather 存在已知不兼容，应在配置校验阶段拦截或在文档中说明，而非运行期 AIV 死锁。

## 规避旁路
**将 `additional-config` 中 `"enable_dsa_cp"`和 `"enable_flashcomm1"`设为 `false`，服务即可正常启动并承接请求。**

## Additional Context

- 部署模式：**单节点 PD-mixed（混部）**，非 PD-separation；TP=16，`decode-context-parallel-size=16`
- 投机推理：MTP（`deepseek_mtp`, `num_speculative_tokens=5`）
- 图模式：`cudagraph_mode=FULL_DECODE_ONLY` + `cudagraph_capture_sizes=[6,12,24,48]`（后者用于绕过 MTP+TP16 的 shape 约束，与本 bug 无关）
- **是否可稳定复现**：是，确定性 100%（在两个不同物理节点上均复现，全 16 卡完全一致的死锁，非偶发、非单卡硬件）
- 已尝试且**无法**消除死锁的改动：开关 `enable_npugraph_ex`、加/去 `--enforce-eager`、降 `--max-model-len`/`--gpu-memory-utilization`（仅改变崩溃时机，无法消除 dsa_cp 带来的 AIV group 并发死锁）
- **唯一有效 workaround**：`"enable_dsa_cp": false`+`"enable_flashcomm1":false`，服务正常启动（同事已独立验证）
- 核心问题：DCP 将通信下移到 attention 层后引入的 per-layer AIV 通信 group，与 MoE EP 的 AllGather（同走 AIV）并发时触发 HCCL 自诊断所说的 "multi groups include aiv alg, may cause execution stuck"。建议评估 DCP per-layer 通信与 MoE 通信并发时的 AIV group 复用/串行化策略，或在 `enable_dsa_cp` + MoE EP 并存时做配置校验。
