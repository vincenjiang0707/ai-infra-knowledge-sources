## 正文

### What this PR does / why we need it?
Applies the GLM 5.2 KV-offloading MemFabric read-adaptation patch to the v0.26.0rc branch.

The patch:
- selects Mooncake or MemFabric through `MooncakeConnectorV1` and carries the transfer backend/session in agent metadata;
- supports sparse shared Host KV layouts and assigns each prefill DCP shard to one decode TP owner;
- synchronizes shared-main completion and load failures across decode TP ranks;
- coalesces adjacent/overlapping MemFabric registration regions to reduce registration overhead and avoid redundant registrations;
- extends focused unit coverage for the new routing, metadata, failure handling, and registration behavior.

It also isolates sparse offload store ports by DP replica so different replicas do not reuse the same local endpoint.

### Does this PR introduce _any_ user-facing change?
Yes. `MooncakeConnectorV1` now accepts `transfer_backend: "memfabric"` in the KV transfer extra configuration and uses it for sparse shared Host KV transfers. The existing Mooncake behavior remains the default.

### How was this patch tested?
- Added/updated unit tests:
  - `tests/ut/kv_offload/test_memfabric_transfer_engine.py`
  - `tests/ut/kv_offload/test_mooncake_connector.py`
  - `tests/ut/kv_offload/test_mooncake_memfabric_layout.py`
- Local checks passed: changed-file `ruff check`, `ruff format --check`, `python -m py_compile`, and `git diff --check`.
- CI `pre-commit`, `main`, PR metadata, test selection, and recommendation checks passed.
- The repository CI gate reports that selected tests require the `ready` label. That label is not currently available to the submitter, so selected-test execution is pending repository gating.
- NPU end-to-end validation still requires NPU CI/hardware.

### ader47 · 2026-09-24 · COMMENTED

Logging-focused review: one related concern is the receive-side `KV cache transfer ... took ... ms` message in `_transfer_kv_cache_all_groups()`. It is emitted at INFO for every transfer subtask. Since the MemFabric backend now shares this path and one request may fan out across multiple `(pcp_dcp_rank, remote_tp_offset)` tasks on every D rank, this can dominate D-side logs. Please consider changing it to DEBUG, recording it as a metric, or logging only when the duration exceeds a configurable slow-transfer threshold. The measured interval also includes Python-side address/list preparation, so it is not a pure MemFabric read latency.
