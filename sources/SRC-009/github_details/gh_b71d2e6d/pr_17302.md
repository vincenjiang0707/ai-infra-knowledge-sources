# [PR #17302] [Performance][MoE] Fuse A5 TopK with logical-to-physical expert mapping

## 正文

### What this PR does / why we need it?

Return physical expert IDs directly from A5 TopK when an Ascend expert map is present, removing the separate indexing operation. Include the native operator, build and torch/Meta registration, DeviceAdaptor dispatch and routed-expert/router call sites.

Logical-ID capture, upstream EPLB routing, custom/hash/vision routing, unsupported devices and forced-load-balance paths retain their original selection and mapping behavior. Shared expert IDs are appended after routed IDs. This PR does not include EPLB statistics or weight-migration changes.

### Does this PR introduce _any_ user-facing change?

No new launch option. Eligible mapped A5 routing selects the fused operation automatically; routing weights and final physical IDs preserve the existing contract.

### How was this patch tested?

Validated PR head `12d8e0bbf0d19f3ca8ed05b33d4080458eff7829` on one A5 NPU with torch 2.10.0+cpu, torch-npu 2.10.0.post4 and vLLM `84030bb`. The native operator and PyTorch binding compiled and were installed into an isolated Python venv. For this test build only, the isolated checkout's A5 build list was temporarily narrowed to `moe_gating_top_k_with_map`; runtime source was unchanged and the checkout was restored afterward.

- CPU: 14/14 standalone capability/protocol cases, 6/6 selected router integration cases, and 6/6 supplemental eligible/fallback cases passed.
- NPU: 29/29 generic shape, dtype, grouping, mapping and tie cases passed. Another 15/15 cases shaped for current GLM-5.2, GLM-5.3-Flash and MiniMax-M2.7 configurations passed. The expanded Kimi-K3/GLM-5.2/GLM-5.3-Flash/MiniMax-M2.7 single-card matrix passed 44/44 cases: FP32 router scores at every M=1..8, plus BF16 at M=1/4/8 per profile. All 88 NPU comparisons matched the original TopK plus separate indexing exactly for final physical IDs and routing weights.
- Routing gate: GLM-5.2, GLM-5.3-Flash and MiniMax-M2.7 shaped configurations were eligible. DeepSeek-V4 Flash and Pro (`sqrtsoftplus`) were correctly excluded for every M=1..8 (16/16 checks); the old route and single logical-to-physical mapping were retained. GLM/MiniMax eligible gates passed 24/24 checks at M=1..8.
- NPUGraph replay: the PR's mapping-update test function passed when invoked directly. The nightly pytest module could not be collected in this container because its shared conftest requires the absent `modelscope` package.

The earlier latest-model cases used M=1/8/64/256 FP32 and M=8 BF16; the new matrix fills every M from 1 through 8 FP32 and checks BF16 at M=1/4/8. M is token rows in one routing call. During one-token-per-request decode it approximates active per-card concurrency, but these are single-card routing-operator tests; full-model serving, distributed execution and end-to-end ITL were not measured.

### A5 operator-path performance across M=1..8

Compared native A5 TopK followed by `log2phy[logical_ids]` with fused mapped TopK on one A5 NPU. Each block ran 100 calls and synchronized; 15 paired rounds alternated AB/BA order. Percentages below are the reduction in p50 steady-state wall microseconds per call for FP32 router scores. Graph capture time is excluded.

At M=8 FP32, old -> fused p50 was Kimi-K3 42.70 -> 29.24 us, GLM-5.2 33.67 -> 24.48 us, GLM-5.3-Flash 33.74 -> 24.43 us, and MiniMax-M2.7 33.72 -> 24.41 us. All 32 FP32 eager cases and all 12 BF16 eager cases favored fusion; BF16 speedup ranged 26.2-31.9%. Router profiles use G/Kg=1/1 and sigmoid with correction/routing bias; GLM uses scale 2.5, K3 and MiniMax use scale 1.0.

NPUGraph replay did **not** show a stable benefit: 27/44 paired medians favored fusion, 17/44 did not; old-minus-fused deltas ranged from -0.46 to +0.80 us per replay. Inference on this measured path: eager launch/indexing overhead is reduced; a graph replay workload should not assume a throughput or ITL gain from this data.

[DeepSeek-V4 Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731/blob/main/inference/config.json) has `[M,256]`, K=6; [DeepSeek-V4 Pro](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro/blob/main/inference/config.json) has `[M,384]`, K=6. Both use `sqrtsoftplus`, which this PR excludes from mapped TopK fusion. Their routing gate and fallback were checked at each M=1..8; **no fused-operator performance gain is claimed for DeepSeek-V4**.

These are model-config-shaped operator inputs, not loaded-model benchmarks. A real model enters the fusion only when it has a `log2phy` map, uses the exact eligible router and avoids capture/EPLB/custom/hash/vision/force-balance paths. A single routing call with M token rows can include more than one token per request, so M=1..8 is a decode-concurrency proxy, not a serving concurrency measurement.
