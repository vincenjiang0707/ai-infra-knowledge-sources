## 正文

### What this PR does / why we need it?

Fixes #15744.

When `enable_balance_scheduling` is enabled, `BalanceScheduler.schedule()`
performs local prefix-cache lookups but does not report them through
`KVCacheManager.record_prefix_cache_stats()`. As a result, cached requests are
served faster and expose non-zero `cached_tokens`, while
`prefix_cache_queries_total`, `prefix_cache_hits_total`, and the logged hit rate
remain zero.

This change aligns the copied balance-scheduler admission path with upstream
vLLM PR [#48860](https://github.com/vllm-project/vllm/pull/48860):

- remember whether a waiting request performed a local prefix-cache lookup;
- record local cache statistics only after slot allocation succeeds, so
  deferred or allocation-failed requests are not counted;
- remove lookup-time recording from the custom Mamba hybrid path to avoid
  double-counting;
- preserve `prefix_cache_lookup_enabled()` and `shared_prefix_boundary`
  semantics in that custom path;
- add a regression guard for the admission-time recording contract.

Manual validation on an Ascend 910B/C TP=8 / DP=2 GLM-5.3 deployment changed
the affected DP rank from zero metrics to:

```text
vllm:prefix_cache_queries_total{engine="0",model_name="glm-5.3"} 55245.0
vllm:prefix_cache_hits_total{engine="0",model_name="glm-5.3"} 42496.0
```

The periodic prefix-cache hit rate also changed from `0.0%` to approximately
`69-77%`.

### Does this PR introduce _any_ user-facing change?

Yes. With balance scheduling enabled, prefix-cache Prometheus counters and the
logged prefix-cache hit rate now reflect admitted requests and actual local
cache hits.
