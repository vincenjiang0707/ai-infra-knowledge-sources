# [PR #15441] [Feature][Quant] Introduce combine_quant_mode to force MC2 combine stage communication quantization

## 正文

  ### What does this PR do / why we need it?

  Introduces a new top-level Ascend config option `combine_quant_mode` (default `0`, disabled) that lets a model force the MC2 **combine** stage's communication quantization mode regardless of its `quant_type`.

  By default the combine `comm_quant_mode` passed to`torch.moe_distribute_combine_v2` is derived from the model's quant type (e.g. `W8A8MXFP` → `4`). When a user sets `combine_quant_mode` to a non-zero value, the combine comm quant mode is forced to that value instead, so non-MXFP models can opt into a specific combine communication quant mode (e.g. `4` = MXFP communication quantization) without changing the model weights' quantization.

  Precedence in `get_combine_mc_kwargs`:
  1. explicit `comm_quant_mode` set by a deeper per-layer quant config still wins, so the switch never silently overrides a deliberate quant decision;
  2. `additional_config.combine_quant_mode` when non-zero;
  3. otherwise the existing `quant_type`-based default.

  ### Does this PR introduce any user-facing change?

  Yes — a new optional `additional_config` key `combine_quant_mode` (int). It is documented in the additional-configuration table. Default behavior is unchanged (`0` = use the model's own quant).

  ### How was this patch tested?

  - New unit tests:
    - `tests/ut/test_ascend_config.py`: default is `0`, int-string `"4"` is lax-coerced to `4`, non-integer values are rejected.
    - `tests/ut/ops/a2/test_token_dispatcher.py`: non-zero `combine_quant_mode` forces the combine comm quant mode for a non-MXFP model; `0` keeps the default; an explicit `comm_quant_mode` still takes precedence.
