### 🐛 Describe the bug

`DSparkDeepseekV4ForCausalLM.load_weights()` maps the target checkpoint's top-level head/embed/HC keys and the `mtp.*` draft keys to the same destination parameters. When a target key arrives after its MTP counterpart, it silently replaces the trained draft parameter. The result depends on checkpoint iteration/shard completion order.

For example, both `mtp.2.head.weight` and `head.weight` map to `lm_head.weight`. Loading the former and then the latter leaves the draft model using the **target** output head. The same problem affects `embed.weight` and `hc_head_fn`, `hc_head_base`, `hc_head_scale`. The verifier still rejects incorrect proposals, so requests can succeed while speculative decoding loses most of its benefit.

#### Minimal reproducer

Run this in a vLLM Ascend Python environment. It calls the actual loader with tiny CPU tensors and mocked parallel-state accessors; it does not download a checkpoint, initialize a model, or run inference:

```python
from types import MethodType, SimpleNamespace
from unittest.mock import patch

import torch
from vllm_ascend.models.deepseek_v4 import dspark

for draft_first in (True, False):
    head = torch.nn.Parameter(torch.zeros(2, 2), requires_grad=False)
    model = SimpleNamespace(
        rotation_path=None,
        config=SimpleNamespace(num_attention_heads=8, num_hidden_layers=43),
        model=SimpleNamespace(num_dspark_layers=3, get_expert_mapping=lambda: []),
        named_parameters=lambda: [("lm_head.weight", head)],
    )
    model._remap_dspark_name = MethodType(
        dspark.DSparkDeepseekV4ForCausalLM._remap_dspark_name, model
    )
    weights = [
        ("mtp.2.head.weight", torch.full((2, 2), 7.0)),
        ("head.weight", torch.ones(2, 2)),
    ]
    if not draft_first:
        weights.reverse()
    with (
        patch.object(dspark, "get_tensor_model_parallel_world_size", return_value=1),
        patch.object(dspark, "get_tensor_model_parallel_rank", return_value=0),
    ):
        dspark.DSparkDeepseekV4ForCausalLM.load_weights(model, iter(weights))
    print(f"{draft_first=}: loaded={head[0, 0].item()}, expected=7.0")
```

Observed on unpatched main:

```text
draft_first=True: loaded=1.0, expected=7.0
draft_first=False: loaded=7.0, expected=7.0
```

Expected: `7.0` in both cases. Explicit MTP weights should take precedence independently of iteration order. Global keys should remain fallbacks when the corresponding MTP key is absent.

#### Why the September checkpoint exposes the problem

We compared two local snapshots of the same ModelScope model:

| Checkpoint | Shards | Quantization description | Loader behavior |
|---|---:|---|---|
| Earlier snapshot | 74 | Declares `optional.quarot.rotation_map.global_rotation` | `rotation_path` is set; target head/embed are skipped |
| Revision `5012d242` | 75 | `optional: {}` | `rotation_path=None`; target head/embed may overwrite draft parameters |

Both snapshots contain `optional/quarot.safetensors`, but `get_rotation_path()` uses the metadata rather than file existence. Neither snapshot has `is_rot_used=true`. Full tensor SHA256 comparisons show that the draft LM head, draft embedding and all three draft HC tensors are identical between these snapshots. Within each snapshot, target and draft head/embed/HC tensors differ. Thus overwriting a draft tensor with its target counterpart is not an equivalent substitution.

The quantization scheme also changed, so copying the earlier rotation metadata into the new snapshot is not a justified fix. HC loading is not guarded by `rotation_path` and can still be overwritten on the rotation-enabled path.

#### Regression history

For quantized checkpoints without a rotation path, the direct regression is #13506, merged on 2026-08-07, commit `683b6c009d57714eaf9363f369c7ed4fa0084f5c`. It changed the target head/embed guard from `not self.has_own_*` to `not self.rotation_path` and added target HC loading. Executing the actual loader bodies from this commit and its parent confirms the before/after behavior. The earlier #11431 implementation already had an analogous head/embed ordering issue on the non-quantized path.

#### Real-model evidence and proposed fix

- Before repair, all 8 TP draft-head shards matched the target `head.weight`, rather than `mtp.2.head.weight`; one audited rank also had overwritten HC parameters.
- Holding the running model and test input fixed, repairing draft head/HC restored mean acceptance length from approximately 1.1 to 5.1. This was a diagnostic intervention, followed by a persistent loader fix and fresh model reloads.
- After the persistent fix, all 8 draft-head shards and all draft HC parameters matched the checkpoint. No runtime repair was used for the performance retest.
- C1 pure decode TPOT recovered from **48.70 to 12.20 ms (EP off)** and **49.16 to 12.50 ms (EP on)** on the same checkpoint. These are request-mean TPOT values excluding TTFT/prefill. The private replay request set was held fixed; the repaired result uses two consecutive warm 64-request batches per concurrency/configuration. Across repaired C1/C8 runs, 512 formal requests completed without errors.

Proposed fix: remember which destination head/embed/HC parameters were loaded from `mtp.*`, ignore later target fallbacks for those parameters, and still allow later MTP tensors to overwrite earlier fallbacks. This needs only a small set of parameter names, not checkpoint buffering, and does not change sampling or acceptance rules.

Related symptom report: #13640; its root cause is not established, so this issue does not claim they are identical. #15824 fixes a different Qwen3 DSpark rotation-metadata path and does not address this loader overwrite.

AI assistance: diagnosis, code and regression tests were prepared with OpenAI Codex assistance during the deployment investigation.
