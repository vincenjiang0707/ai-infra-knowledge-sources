# [Issue #17169] [Bug]: A3 TP8 BF16 AllReduce is batch-shape dependent for identical local partials

source: https://github.com/vllm-project/vllm-ascend/issues/17169
state: open | updated: 2026-09-22T11:05:29Z
labels: triaged

## 正文

## Summary

On Ascend A3, identical per-rank BF16 inputs produce different corresponding
outputs after TP8 HCCL AllReduce when the number of repeated rows changes.
This was isolated while investigating single-request versus batched inference.
This report asks for guidance on supported batch-invariant reduction behavior;
it does not assume ordinary BF16 collectives promise bitwise batch invariance.

## Environment

- Ascend A3; CANN 9.1.0; HDK 25.5.1.1.
- PyTorch 2.10.0; torch-npu 2.10.0.post4.
- vLLM: `84030bbe3d74d99bad477a3d2e37a973ccd8865c`.
- vLLM-Ascend base: `d4511510e15eb52744089e40d8cd7c9fc23ac0f4`;
  investigation performed with the Engram follow-up #16689.
- Reduction-only replay: eight NPUs, `torch.distributed` HCCL backend,
  `HCCL_BUFFSIZE=512`, model service stopped during replay.

## Isolation procedure and observations

1. Capture each rank's local attention output-projection partial, before TP
   reduction, for one prefix and four identical copies of that prefix.
2. Check all eight ranks: corresponding local partials are byte-identical
   across batching and three single-request captures. Inputs are finite.
3. Replay only `dist.all_reduce(..., op=SUM)` on the captured partials:
   `[184, 5120]` BF16 versus four repeated prefixes `[736, 5120]` BF16.
4. Both shapes' reduction outputs exactly reproduce their respective model
   captures on all eight ranks. Two trials per shape are byte-identical.
5. Corresponding rows across shapes differ by up to **0.046875**.

| Reduction dtype | Maximum cross-shape difference | After rounding to BF16 |
| --- | ---: | --- |
| BF16 | 0.046875 | Different |
| FP32 | 5.960464477539063e-8 | Byte-identical across shapes |

For these inputs, FP32 reduction followed by BF16 cast also exactly matches
the CPU FP64 sum rounded to BF16. BF16 reduction's maximum error versus the
FP64 sum is 0.01904296875 for one prefix and 0.03106689453125 for four copies.
Byte comparisons use contiguous uint8 views, including signed-zero bits.

## Impact and boundaries

- In the investigated inference case, this is the first observed BF16
  difference, after the first attention output projection's TP reduction.
  Earlier BF16 attention computation and all eight local projection partials
  agree for corresponding inputs.
- Fixed-input HBM and host-backed VMM Engram controls agree, including logits;
  the batch dependence is not specific to host-backed Engram.
- MoE communication-path selection also affects outputs, but forcing the
  same path did not eliminate batch dependence. This report does not claim
  to explain every downstream difference.
- HCCL internal algorithm selection/order was not observed. No particular
  ring/tree implementation is asserted.
- FP32 is an operator-level counterfactual, not a proposed default fix: it
  doubles communication bytes and has not been validated for full-model
  performance or global batch invariance.
- No throughput regression is attributed to this numerical observation.

## Questions

Is this expected size-dependent BF16 reduction behavior on this stack? Is
there a supported configuration or reduction path for batch-invariant
inference without globally promoting TP communication to FP32?

## Reproducer availability / disclosure

The exact replay currently depends on captured model intermediates, which
are not attached. This is an experimentally isolated report, not a public
self-contained reproducer; synthetic random tensors have not been verified
to reproduce these exact numbers. No weights, activations, prompts, internal
hostnames/IPs, deployment paths, or credentials are included.
