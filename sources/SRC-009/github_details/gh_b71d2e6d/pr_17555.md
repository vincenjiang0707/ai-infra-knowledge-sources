# [PR #17555] [Performance]narrow the KV save fence to requests with released blocks

## 正文


## 1. Baseline and conclusion

- Baseline: the current save fence in `AscendStoreConnector`. `handle_preemptions()` calls `KVPoolWorker.wait_for_previous_save()`, which blocks the scheduler step until the **entire previous save batch** has drained — i.e. every in-flight put of every request, whether or not this step reuses any of those blocks.
- This PR narrows the fence to **exactly the requests whose blocks become reusable this step** (`finished ∪ preempted`), carried through the connector metadata as `released_req_ids`. Immediate block release is kept unchanged.
- Measured on Atlas A2 (910B, CANN 9.1.0), Qwen3-32B W8A8, TP4, single-engine `kv_both` with the mooncake backend:
  - High prefix-hit, high-churn workload (16k input / 1-token output, 89.8% external hit): **+49%~52%** Input Token Throughput over the whole-batch fence.
  - No-hit workload (240 prompts, concurrency 60, ~3.5k input): **+5.3%~5.4%** over the whole-batch fence, and **parity with no-pooling** (±0.5%, within run-to-run noise) — the residual pooling overhead in the no-hit case is eliminated.

## 2. Why the whole-batch fence is expensive

The fence exists to protect block reuse: KV blocks are freed immediately when a request finishes or is preempted, so the in-flight puts reading those blocks must complete before the scheduler can hand the blocks to a new request.

The baseline enforces this by waiting for the **whole** previous save batch on every step the hook fires. That waits for far more than reuse requires:

- Requests that are still running keep their blocks — nobody can overwrite them this step, yet the baseline waits for their puts too.
- On workloads with short outputs and high request turnover, many requests finish every step, the fence fires effectively every step, and the engine step gets serialized behind the full drain of in-flight RDMA puts.
- The cost scales with in-flight put volume per step, which matches the two measured extremes: a long-prompt no-hit workload (few save completions per step) loses ~4.7% vs no-pooling, while the high-churn hit workload gives up about a third of the achievable throughput (fence 29488 vs this patch 44400 avg, −33.6%).

## 3. Design

### 3.1 Carry `released_req_ids` in the connector metadata

- `metadata.py` — `AscendConnectorMetadata` gains `released_req_ids: set[str]`, initialized from `preempted_req_ids`.
- `pool_scheduler.py` — when building the metadata it is set to
  `set(scheduler_output.preempted_req_ids) | set(scheduler_output.finished_req_ids)`.

### 3.2 Fence only those requests on the worker

- `ascend_store_connector.py` — `handle_preemptions()` now calls
  `connector_worker.handle_released_saves(meta.released_req_ids)` instead of `wait_for_previous_save()`.
- `pool_worker.py` — `handle_released_saves()` forwards to the sending thread's `wait_for_requests_saved()`; the layerwise path is untouched (its saves are already synchronized at each step's final layer).
- `kv_transfer.py` — `KVCacheStoreSendingThread.wait_for_requests_saved()` polls `stored_requests` (1 ms interval) until none of the given request ids have a queued save chunk left:

```python
def wait_for_requests_saved(self, req_ids: set[str] | None) -> None:
    if not req_ids:
        return
    pending = set(req_ids)
    while True:
        self.raise_if_failed()
        with self.done_task_lock:
            pending &= self.stored_requests.keys()
            if not pending:
                break
        time.sleep(SAVE_REQUEST_POLL_INTERVAL_S)
```

The common case — no request released this step — costs one empty-set return.

### 3.3 Why draining once is safe

1. A request queues no new save chunks after it finishes or is preempted.
2. Its terminal state is flushed into exactly one `SchedulerOutput`, so it appears in `released_req_ids` exactly once.
3. When the fence observes the request has no queued chunks left, every put it will ever issue has completed — its blocks are safe to reallocate from then on. No later fence needs to consider it again.
4. Preempted requests are covered by the same set (`preempted_req_ids` is part of the union), and re-computation re-queues saves under the still-alive request id, which a later release will fence again.

## 4. Test environment

- Single Atlas A2 server, 8× Ascend 910B, CANN 9.1.0; two containers from the same image (host network, shared `/data`) used for cross-checks.
- Server: Qwen3-32B W8A8 (`--quantization ascend`), `--tensor-parallel-size 4` on NPU 0-3, `--block-size 128`, `--max-model-len 40960`, `AscendStoreConnector` with `kv_role=kv_both`, mooncake backend, `HCCL_INTRA_ROCE_ENABLE=1`, `PYTHONHASHSEED=1`.
- Store: fresh `mooncake_master` per leg (`--eviction_high_watermark_ratio 0.9 --eviction_ratio 0.15 --port 50088`) with a 20 GB segment config, so every leg starts from an empty pool.
- Benchmark: ais_bench; metric is **Input Token Throughput** as reported by the tool.
- Fairness: within each matrix all legs ran on the same machine state, same image, fresh master; request success counts and external hit rates are identical across legs, so the deltas are engine-side only.

## 5. Results

### 5.1 High prefix-hit, high-churn workload

`python3 aisbench_test.py --input_len 16384 --output_len 1 --data_num 160 --concurrency 32 --request_rate 0 --dataset_type prefix_cache --repeat_rate 90% --prefix_num 16 --prefix_test`

16 distinct 16k prefixes, 90% repeat rate → external (pool) hit 89.80% on **all** legs; local HBM prefix hit 0%; 160/160 requests succeeded on all legs.

| Build | Input Token Throughput | Duration | Success |
|---|---|---|---|
| fence baseline (whole batch) | 29488.41 | 88.9 s | 160/160 |
| this patch, run 1| 44880.02 | 58.4 s | 160/160 |
| this patch, run 2 | 43920.74 | 59.7 s | 160/160 |

**+49.0% ~ +52.2% vs the fence baseline.** The two patched runs differ by 2.2%, i.e. single-run noise on this ~60 s workload is ±1-2%; both runs sit far above the baseline.

### 5.2 No-hit workload vs fence baseline and vs no-pooling

gsm8k 0-shot prompts (mean input ≈ 3500 tokens, no cross-request prefix sharing → external hit ≈ 0), 240 prompts, concurrency 60.

| Build | Input Token Throughput | TTFT (mean) | ITL (mean) | vs fence | vs no-pool |
|---|---|---|---|---|---|
| fence baseline (whole batch) | 2157.02 | 7.34 s | 59.9 ms | — | −4.7% |
| this patch, run 1 | 2273.35 | 6.14 s | 57.4 ms | +5.4% | +0.5% |
| this patch, run 2 | 2271.33 | — | — | +5.3% | +0.4% |
| no-pooling, run 1 | 2262.41 | 6.15 s | 57.7 ms | +4.9% | — |
| no-pooling, run 2 | 2268.15 | — | — | +5.2% | — |

The two patched runs differ by 0.09%; the two no-pooling runs differ by 0.25%. **The patched pool matches no-pooling within ±0.5% (noise), while the fence baseline gives up ~4.7%.** TTFT and ITL of the patched pool are identical to no-pooling (6.14 s / 57.4 ms vs 6.15 s / 57.7 ms); the baseline's TTFT inflation (+1.2 s) is gone.
