## What this PR does / why we need it?

Raises the load-balanced partition counts in `test_config.yaml` so full-suite runs (ready-all / main2main) spread the selected files across one extra runner per hardware partition:

- `a3-2`: 4 → 5 (slowest shard ~62.8 → ~51.2 min)
- `a3-4`: 4 → 5 (slowest shard ~68.5 → ~54.2 min)
- `a2-1`: 5 → 6 (slowest shard ~80.5 → ~67.2 min)

PR #17052 trimmed the eight-card test cases down to four-card ones, so compared to before that optimization, adding one extra shard to the A3 two-card and four-card partitions does not increase the total number of cards consumed by the CI gate.

Figures are LPT estimates from `estimated_times.yaml` (with recent corrections for weight-transfer skips and deepseek_v4 timings), excluding the ~19-minute per-job setup overhead that is identical across partitions. The a2-1 bump removes the one-card suite as the overall critical path; the remaining bottleneck is the serial 310p-1 partition (~62.3 min).

The workflow matrices are built from the `test_groups` JSON emitted by `select_tests.py`, and the 560T reroute (`_prefer_560t_partitions`) follows `count` from the config, so no other file needs to change. Empty buckets are skipped (`if not bucket: continue`), so precise-mode selections with fewer files than the partition count do not emit empty jobs.

## Does this PR introduce any user-facing change?

No. CI-only change; test scheduling and runner counts only.

## How was this patch tested?

- Local verification of `_partition_tests` (LPT bucketing) with a line-by-line equivalent port: mock edge cases (files < count, tie-breaks, nodeid lookup, default 600s) plus real `estimated_times.yaml` data — all files placed exactly once, 5 non-empty buckets for both a3 partitions, balance ratio ≤ 1.04.
- CI: this PR touches the CI pipeline itself and will run the full `--all-tests` suite, which is the intended validation for the new sharding.
