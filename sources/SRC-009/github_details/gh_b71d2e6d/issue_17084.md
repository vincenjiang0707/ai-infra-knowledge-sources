# [Issue #17084] [CANN 9.2.0] aclnnFusedInferAttentionScoreV4 decode crash: keyRope stride-view invalid offset (int32 overflow signature) on Kimi-K3 W4A8 TP16

source: https://github.com/vllm-project/vllm-ascend/issues/17084
state: open | updated: 2026-09-24T06:57:55Z
labels: triaged, kimi, multimodal-understanding

## 正文

## Summary

On CANN 9.2.0 (aarch64, Atlas 800I A3), Kimi-K3 W4A8 (13-layer reduced hybrid linear/MLA variant, `KimiLinearForCausalLM`) served with vLLM-Ascend TP16+EP crashes in **decode** at the first real request:

```
PTA call acl api failed.
EZ9999: AclNN_Inner_Error: The tensor's offset 4790046720 is invalid, storage size is 578420736, offset must be in [0, 578420768].
TraceBack: Try create stride view for keyRope failed.
          Try normalize keyRope failed.
```

The failing op is `aclnnFusedInferAttentionScoreV4` (called via `torch_npu.npu_fused_infer_attention_score_v2`, `vllm_ascend/attention/mla_v1.py` `_forward_decode`). Prefill works; only decode is affected. The failure also occurs during decode cudagraph capture (FULL_DECODE_ONLY), i.e. before any request, and with `--enforce-eager` at request time.

We believe this is a **host-side int32 overflow in the CANN 9.2.0 aclnn host code** when normalizing the keyRope view, not a vLLM-Ascend logic bug — details below.

## Environment

- CANN 9.2.0 (`V100R001C25B114`) + custom_transformer vendor package (MegaMoe validation build, 20260920)
- torch 2.10.0+cpu, torch_npu 2.10.0.post4
- vLLM 0.27.1, vllm-ascend `megamoe-check` @ `5a9de6576` (feat(moe): enable MegaMoe for Kimi K3)
- Atlas 800I A3, single node, TP16 + EP, `--enforce-eager` (also fails with graph capture)
- Model: Kimi-K3 W4A8 reduced-layer variant (13 layers, hybrid GDN/MLA, `--quantization ascend`)

## Reproduction

1. `vllm serve <model> --tensor-parallel-size 16 --enable-expert-parallel --quantization ascend --enforce-eager ...` (full script available)
2. Server starts, `Application startup complete`
3. Send one chat request → engine dies during decode with the keyRope error above

With cudagraph (`FULL_DECODE_ONLY`) the same error appears during `capture_model()` warm-up, before any request.

## Evidence

Two independent runs produced:

| run | reported offset | storage size | offset / storage |
|---|---|---|---|
| with MegaMoe config | 4,665,288,960 | 563,355,648 | 8.2806 |
| baseline (no MegaMoe) | 4,790,046,720 | 578,420,736 | 8.2807 |

- `offset − 2^32` = 370,321,664 and 495,079,424 respectively — **both fall inside the valid storage range**. The reported offsets are consistent with a **negative int32 byte-offset wrapped around** (a multiplication overflowed int32 and was re-interpreted as unsigned), i.e. a deterministic host-side arithmetic overflow, not a stray pointer.
- The identical ratio (8.28) across runs with different cache pool sizes confirms a deterministic address-computation bug.

## Isolation

- **Not MegaMoe-related**: a baseline run with `enable_fused_mc2=0`, `enable_prefill_mc2=false` and no `mega_moe_max_tokens` reproduces the identical crash (the keyRope error appears 82 times in that log).
- **Not graph-capture-specific**: reproduces with `--enforce-eager` on real requests, and during graph capture without any request.
- **Prefill unaffected**: the first forward pass (prefill) succeeds; the failure is decode-only (`_forward_decode` path, paged KV cache view + `block_table`).
- The same model family + same vLLM-Ascend code paths run fine on the CANN 9.3.0 weekly stack (our 8-node production setup).

## Ruled out

- Non-contiguous keyRope passed from vLLM-Ascend: we patched `mla_v1.py` to pass `k_pe.contiguous()` at both the graph-update and capture call sites — the crash is unchanged, so the input tensor is dense and valid at the PyTorch level.
- MegaMoe / custom vendor interference: excluded by the baseline run above.
- Out-of-range `block_table` dummy values at capture: fails identically on real requests in eager mode with real metadata.

## Installation verification

To rule out a broken local install, we verified the environment before attributing the failure to CANN host code:

- All components report the same version line: `Ascend-cann-toolkit 9.2.0` / `Ascend-cann-A3-ops 9.2.0` / `Ascend-cann-atb (NNAL) 9.2.0`, innerversion `V100R001C25B114` (install `.info` files under `/usr/local/Ascend/cann-9.2.0/` and `/usr/local/Ascend/nnal/atb/9.2.0/`).
- Package SHA256 prefixes (full hashes available on request, also cross-checkable with our artifact issue #17055): `Ascend-cann-toolkit_9.2.0_linux-aarch64.run` `2e77883d75c52ae8…`, `Ascend-cann-nnal_9.2.0_linux-aarch64.run` `a52f38f8108f8f11…`, `Ascend-cann-A3-ops_9.2.0_linux-aarch64.run` `c871c1592eeeeafe…`, `cann-ops-transformer-custom_linux-aarch64_1.run` `e78daf18abc0349c…`.
- The failing op ships with the **built-in toolkit**: `aclnnFusedInferAttentionScoreV4` symbols are present in the official `/usr/local/Ascend/cann-9.2.0/aarch64-linux/lib64/libopapi.so` (and the `opp/built-in` copy). The custom vendor package only carries the MegaMoe dynamic ops and does not participate in this op's resolution.
- The custom-transformer vendor (`opp/vendors/custom_transformer`) and the `cann_ops_transformer_custom` wheel are installed and functional on this exact environment: a 2-card MegaMoe kernel-level smoke (`torchrun --nproc_per_node=2`) passes with `SUCCESS` on both ranks.

## Suspicions

- CANN 9.2.0 `aclnnFusedInferAttentionScoreV4` host code mishandles the keyRope paged-cache view for large KV pools (int32 overflow when computing `block_index * block_stride`-style offsets). The negative-int32 signature above supports this.
- Possibly fixed in CANN 9.3.0: our production stack (9.3.0 weekly + a vllm-ascend build that consumes `VLLM_ASCEND_FORCE_CONTIGUOUS_KEY_ROPE`) does not show this failure. Note that in the current build (torch_npu 2.10.0.post4 + vllm-ascend `megamoe-check`) that env-var switch has no consumer — we grep-verified the whole stack.

## Requested help

1. Confirm whether `aclnnFusedInferAttentionScoreV4` on CANN 9.2.0 has a known keyRope stride-view / int32 offset bug fixed in a later release.
2. Confirm the official compatibility pairing of torch_npu 2.10.0.post4 with CANN 9.2.0 vs 9.3.0.
3. If a patched 9.2.0 op build (or a minimal workaround, e.g. a supported switch) is available, we would like to complete our CANN 9.2.0 + custom ops validation, which is currently blocked at decode.

l2_weights = [torch.randn(intermediate, hidden, dtype=torch.bfloat16, device=device) * 0.02 for _ in range(local_experts)]

    topk_weights,

    l2_weights,
    sym_buffer,

)
torch.npu.synchronize()
print(

)
dist.barrier(group)
