# [Bug][DeepSeek-V4 Flash][Decode] Host private anonymous memory grows to 963 GiB without MemCache

## Summary

In a DeepSeek-V4 Flash P/D deployment on Ascend, the host RSS of Decode workers grows over service lifetime and does not return after requests become idle. On the most affected Decode node, the container cgroup reached **963.15 GiB RSS** on a host with **1005.39 GiB** physical memory, leaving only about **14.95 GiB MemAvailable**.

This is not virtual-address reservation alone. `/proc/<pid>/smaps` shows that the dominant mappings are already resident, anonymous, private-dirty `MAP_NORESERVE` pages. Sixteen vLLM workers accounted for approximately **790.50 GiB RssAnon**, of which approximately **780.38 GiB** was resident in `VmFlags: ... nr ...` mappings.

The affected nodes do **not** run MemCache/mmc. They use `MooncakeHybridConnector` as KV consumers. Therefore the growth cannot be explained by the separate 384 GiB MemCache fixed pool used in another deployment.

Stopping only the old vLLM model process tree released approximately **740.98 GiB** immediately. The host and container PID 1 were not restarted. A new 16-rank instance in the same container used approximately **222.16 GiB cgroup RSS** after startup.

We need help determining the exact allocation path and why these pages remain resident: live Python/Torch/CANN/Mooncake objects, allocator dirty/active extents after free, or a combination.

All customer IP addresses, hostnames, model prompts, and private filesystem paths are removed below.

## `/proc/<pid>/smaps` evidence

Aggregating every VMA whose `VmFlags` contains `nr` (`MAP_NORESERVE`) across all 16 old Decode workers produced:

```text
NR_TOTAL size_kb=1089925760
rss_kb=818283436
anonymous_kb=818283436
private_dirty_kb=818283436
lazyfree_kb=0
swap_kb=0
```

Key implications:

1. These pages were physically resident, not only virtually reserved.
2. They were anonymous and private-dirty, not model-file page cache.
3. `LazyFree=0` means the pages were not marked reclaimable via lazy free.
4. With `Swap=0`, the kernel could not swap them out.
5. The pages therefore remained charged to Worker RSS until purged/unmapped or process exit.

One worker still held approximately **65.07 GiB** resident `MAP_NORESERVE` memory while its metrics showed:

```text
Running: 0
GPU KV cache usage: 0.0%
```

This shows that host RSS did not return when the rank had no running request and no NPU KV-cache use.

## What we ruled out

### MemCache fixed pool

The affected Decode nodes had no MemCache/mmc container and no independent MemCache fixed pool. Their connector was `MooncakeHybridConnector`. This is not the separate 384 GiB MemCache reservation seen in another deployment.

### Model-file page cache

The anomalous container file cache was only about 1.52 GiB in the detailed process/VMA split. The dominant pages were anonymous private-dirty pages. They cannot be explained by mapped model weights.

### Docker daemon, kernel slab, or shared memory

Host and cgroup accounting did not show these as the dominant consumers. The released memory tracked only the vLLM model process tree.

### NPU HBM or active NPU KV cache

The measured pages are host anonymous RSS. A worker with `GPU KV cache usage=0.0%` still retained about 65.07 GiB host `MAP_NORESERVE` RSS.

## Code audit and related upstream fix

The installed vLLM source does not contain `_execute_worker_rpc()` introduced by upstream PR #51979:

* https://github.com/vllm-project/vllm/issues/43639
* https://github.com/vllm-project/vllm/pull/51979
* https://github.com/vllm-project/vllm/commit/4ca856b

In the old `worker_busy_loop`, the previous RPC's `method`, `args`, `kwargs`, and `output` remain referenced in the same loop frame while the next `MessageQueue.dequeue()` performs `pickle.loads`. Therefore two adjacent deserialized payloads can overlap in lifetime. PR #51979 executes each RPC in an independent `_execute_worker_rpc()` stack frame so the previous payload is released before the next dequeue.

This code path is highly relevant, but we do **not** claim that it explains the entire 740.98 GiB abnormal delta:

* upstream #43639 used different hardware and workload;
* the upstream captured allocation sizes were far smaller than this incident;
* per-rank request counts and final RSS were not positively correlated in our snapshot;
* after objects lose references, Python/Torch/jemalloc may still retain active/dirty extents, which external `smaps` cannot distinguish from live-object retention.

## Current conclusion

The direct host failure mechanism is established:

1. old Decode workers repeatedly commit new host-side anonymous pages;
2. those pages remain resident as private-dirty, non-lazy-free `MAP_NORESERVE` mappings;
3. host RSS high-water continues to rise while service health can remain green;
4. no swap and no container memory limit allow the process tree to approach total host memory;
5. process exit releases the abnormal memory immediately.

What is not established is the byte-level ownership split among Python, Torch `c10::alloc_cpu`, CANN/TBE, Mooncake, and jemalloc, or the exact fraction explained by the worker RPC payload-lifetime bug.

## Help requested

Could maintainers help determine:

1. Which component and call stack creates and commits the large `MAP_NORESERVE` mappings in this Ascend Decode path?
2. Are the retained pages still owned by live objects, or already freed into allocator active/dirty extents that are not purged?
3. Is upstream vLLM PR #51979 expected to cover this vLLM-Ascend deployment, and which vLLM/vLLM-Ascend release contains or backports it?
4. Are there additional known host-allocation retention paths in CANN, torch-npu, Mooncake, or vLLM-Ascend for this topology?
5. Can async scheduling increase adjacent RPC payload overlap or allocator high-water in this path?
6. Which counters/profilers should be enabled to separate `_PyMem_ArenaAlloc`, `c10::alloc_cpu`, CANN, Mooncake, and jemalloc retained bytes without exposing request data?
7. Please point us to an exact fix commit/build to validate under the same DP16 x TP1 Decode topology.

We can run a controlled A/B on an isolated node with the same image and workload: old/new vLLM worker RPC implementation, async on/off, and allocator/native heap profiling.
