### 🐛 Describe the bug

With `cudagraph_mode: FULL_DECODE_ONLY`, a `max_num_seqs` that is not 1, 2, 4 or a multiple of 8 leaves its largest batch sizes with **no captured graph size**. Those decode steps fall back to eager and run about **7.5x slower**. There is no warning, and the value looks perfectly reasonable.

### Cause

`vllm_ascend/platform.py:207`, `_get_default_max_cudagraph_capture_size()`:

```python
return min(max_num_seqs * decode_query_len, 512)
```

The docstring states the `* 2` removal is intentional:

> The only intentional difference from upstream is removing the CUDA-oriented trailing
> `* 2`: Ascend wants the default capture upper bound to track
> `max_num_seqs * decode_query_len`, capped at 512.

The size list is then produced by upstream logic as `[1, 2, 4] + range(8, min(max_cudagraph_capture_size + 1, 256), 8)`. Because
`max_cudagraph_capture_size == max_num_seqs` now, the ladder can no longer reach `max_num_seqs` itself unless it is already on-stride:

| `max_num_seqs` | captured sizes | largest | batches with no graph |
|--:|---|--:|---|
| 8 | 1, 2, 4, 8 | 8 | — |
| **12** | 1, 2, 4, **8** | **8** | **9-12** |
| 16 | 1, 2, 4, 8, 16 | 16 | — |
| **20** | 1, 2, 4, 8, 16 | 16 | **17-20** |
| 32 | 1, 2, 4, ... 32 | 32 | — |

Upstream's `* 2` made this unreachable: `max_num_seqs=12` gave an upper bound of 24, so 12 landed inside a captured size. vLLM's `_set_cudagraph_sizes()` docstring describes the property that is lost:

> `max_num_batched_tokens` is also appended to the list if it fits within
> `max_cudagraph_capture_size`, so the max batch size is captured **even when off-stride**.

### Minimal reproduction

The root cause reproduces with **no Ascend device**, since it is pure config logic:

```python
from vllm.config import CompilationConfig, SchedulerConfig
from vllm_ascend.platform import NPUPlatform


class Stub:
    def __init__(self, n):
        self.compilation_config = CompilationConfig()
        self.compilation_config.max_cudagraph_capture_size = None
        self.compilation_config.cudagraph_capture_sizes = None
        self.scheduler_config = SchedulerConfig(
            max_num_seqs=n, max_model_len=1024, is_encoder_decoder=False
        )
        self.speculative_config = None


for n in (8, 12, 16, 20, 24, 32):
    d = NPUPlatform._get_default_max_cudagraph_capture_size(Stub(n))
    ladder = [1, 2, 4] + list(range(8, min(d + 1, 256), 8))
    print(f"max_num_seqs={n:>3}  default={d:>3}  largest={max(ladder):>3}  "
          f"covers it? {'yes' if max(ladder) >= n else 'NO'}  {ladder}")
```

### Measured cost, and the effect of the fix

Qwen3-30B-A3B, EP=4/TP=4, `ignore_eos=True` so the decode batch stays constant, 64 generated
tokens per sequence, best of 3 repetitions. `capture_sizes` is read from
`llm.llm_engine.vllm_config.compilation_config` after init, so these are the sizes actually
used, not derived from the formula. Only the three-line patch below differs between rows.

| `max_num_seqs` | batch | `cudagraph_capture_sizes` | covers batch | tok/s | ms/decode step |
|--:|--:|---|:--:|--:|--:|
| 12 | 12 | `[1, 2, 4, 8]` | no | 69.4 | 172.79 |
| 12 | 12 | `[1, 2, 4, 8, 12]` | yes | **520.0** | **23.08** |
| 20 | 20 | `[1, 2, 4, 8, 16]` | no | 117.8 | 169.78 |
| 20 | 20 | `[1, 2, 4, 8, 16, 20]` | yes | **788.7** | **25.36** |

**7.5x** at `max_num_seqs=12` and **6.7x** at 20.

The per-step time is the diagnostic. All four uncaptured cases measured across this
investigation -- batch 12 and 20, EP=4 and EP=8 -- land at 169.8-174.6 ms, while every
captured case runs 23-27 ms. Eager decode is dominated by fixed per-step launch cost, so the
uncaptured rows converge regardless of batch size or EP width.

### Suggested fix

Keep the deliberate memory saving (no `* 2`), but let the ladder reach the configured
maximum. vLLM already does exactly this for `max_num_batched_tokens`; the same treatment for
`max_cudagraph_capture_size` costs one extra captured graph:

```diff
--- a/vllm/config/vllm.py
+++ b/vllm/config/vllm.py
@@ _set_cudagraph_sizes
                 # ensure max_num_tokens is captured if within max capture size
                 if (
                     max_num_tokens <= max_cudagraph_capture_size
                     and max_num_tokens not in cudagraph_capture_sizes
                 ):
                     cudagraph_capture_sizes.append(max_num_tokens)
+                # ensure max_cudagraph_capture_size itself is captured even when it is
+                # off-stride. The strides above are [1,2,4] then multiples of 8, so a max
+                # of e.g. 12 would otherwise top out at 8 and leave batches 9-12 with no
+                # graph to replay.
+                if max_cudagraph_capture_size not in cudagraph_capture_sizes:
+                    cudagraph_capture_sizes.append(max_cudagraph_capture_size)
                 # de-duplicate and sort the sizes
                 cudagraph_capture_sizes = sorted(set(cudagraph_capture_sizes))
```

Verified on the hardware above: the appended size survives Ascend's sequence-parallel
filtering and the later `valid_max_size` truncation, and capturing an off-stride size works
without error. It is also slightly better than the workaround of rounding `max_num_seqs` up
to 16, which pads batch 12 into a 16-wide graph (520.0 tok/s capturing 12 exactly, versus
451.0 when padded to 16).

If a config change is preferred over a behaviour change, a startup warning would at least
make the cliff visible:

```text
max_num_seqs=12 is not a capturable size ([1, 2, 4] + multiples of 8);
batches 9-12 will run eager. Consider max_num_seqs=16.
```

### MirkoDeVita98 · 2026-09-16

@zhiyu-wa 
I tested your PR on 8×910B2 (Qwen3-30B-A3B, TP=4, max_num_seqs=12, batch 12, ignore_eos, best of 3) and I don't think the padding takes effect:

```
stock     [1, 2, 4, 8]       73.3 tok/s   163.74 ms/step
your PR   [1, 2, 4, 8, 16]   73.2 tok/s   163.88 ms/step
```
The capture list gains 16 as intended, but decode still falls back to eager. In FULL_DECODE_ONLY a uniform decode batch is one token per request, so num_tokens == num_reqs ≤ max_num_seqs — with max_num_seqs=12 a captured size of 16 can never be filled, since there's no 16th request. Same list with max_num_seqs=16 instead gives 500.2 tok/s, so the graph itself is fine; it's just unreachable at 12.

Two smaller things: the > 4 guard leaves a ceiling of 3 unpadded, and 3 isn't on the [1, 2, 4] grid, so max_num_seqs=3 (or max_num_seqs=1 with 2 speculative tokens) still stops the list at 2. And padding upward costs throughput even where it is reachable — capturing 12 exactly gives 557.2 tok/s versus 500.2 padding into 16.

I have PR https://github.com/vllm-project/vllm-ascend/pull/16623 that adds the exact ceiling to the list instead of rounding it up, which keeps every captured size ≤ max_num_seqs. Happy to discuss it firther if that direction seems right.
