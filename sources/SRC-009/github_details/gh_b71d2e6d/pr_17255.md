## 正文

### What this PR does / why we need it?

Follow-up to #15352.
Refs #15353.

The shared-expert registered-linear-wrapper path previously submitted all wrapper work only after the routed path had been enqueued. For runtime-quantized methods this delayed Vector/AIV input preparation, and host-side submission order could also prevent Gate-Up from covering routed TopK and dispatch.

This PR introduces a scheme-owned `PreparedLinearInput` contract and splits shared-expert execution into three submission stages:

1. After the router input Cast, submit Gate-Up input preparation on the auxiliary stream so activation quantization overlaps the Router MatMul.
2. After recording `router_output_ready`, immediately submit Gate-Up before `routed_experts.forward_impl()` enqueues TopK and dispatch. Gate-Up remains device-ordered behind the router event and can overlap routed TopK/dispatch.
3. After routed milestones are available, append shared activation/requantization and Down. Existing backend-selected activation and combine boundaries remain in force.

No extra NPU event is introduced. The implementation reuses `shared_input_ready`, `router_output_ready`, `shared_activation_overlap_start`, and `routed_combine_start`. It changes host submission order without changing quantization math, checkpoint layout, or the registered wrapper ownership of padding, scale algorithms, output dtype, and transforms.

Backend behavior remains semantic rather than communication-type branching:

- All2All and non-fused MC2 use their fine-grained routed GMM/combine milestones.
- AllGather keeps its own GMM2 activation-overlap boundary and combine boundary.
- Fused MC2 exposes no internal stage events, so the shared MLP remains one independently queued auxiliary-stream workload.

Quantization paths:

- W8A8 and W4A8 use the fused INT8-activation path (`_run_a8_int_mlp`); W8A8 has INT8 weights and W4A8 has INT4 weights.
- W4A8MXFP uses the fused MXFP8-activation/MXFP4-weight path (`_run_a8_mxfp_mlp`).
- W8A8MXFP, W8A8 FP8/PDMix, W4A4 MXFP/FlatQuant/LAOS, dense, other schemes, and active LoRA retain their registered Linear wrappers. Eligible wrappers may split their input preparation, while unsupported wrappers retain scheme-owned execution.

### Does this PR introduce any user-facing change?

No public API or configuration change. When shared-expert multistream overlap is enabled, eligible paths submit the same operators earlier to expose more Router and routed-MoE overlap.
