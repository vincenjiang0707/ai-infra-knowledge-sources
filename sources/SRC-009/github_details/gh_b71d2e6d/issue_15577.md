## 正文

### Motivation.

The original MRv2 RFC [#5208](https://github.com/vllm-project/vllm-ascend/issues/5208) (created 2025-12-20, last updated 2026-06-30) is out of date, while the cross-platform MRv2 migration is tracked in [#15254](https://github.com/vllm-project/vllm-ascend/issues/15254).

Ascend 310P requires a dedicated RFC because it does not support Triton and needs platform-specific handling for:

- Runtime and ACLGraph execution.
- NZ-format KV cache.
- Triton-free operators and request-state processing.
- Qwen3.5 hybrid Mamba/GDN states.
- Prefix Cache.
- MTP and its interaction with cache, sampling, and graph execution.

This RFC tracks the 310P-specific implementation status, supported combinations, remaining work, and ownership.

### Proposed Change.

This RFC proposes to complete and maintain a native MRv2 path for Ascend 310P while keeping its interfaces and behavior aligned with upstream MRv2.

The scope includes:

- 310P-specific MRv2 runtime and model runner.
- Eager and ACLGraph execution.
- Triton-free operators and metadata handling.
- Tensor Parallelism for supported models.
- NZ-format attention KV cache.
- Hybrid Mamba/GDN state management.
- Prefix Cache.
- MTP.
- Unit tests, E2E tests, accuracy validation, and benchmarks.

### Thymos2027 · 2026-09-21

I opened #17160 with a controlled MRv1/MRv2 performance comparison for Qwen3.5-9B FP16 on one 310P3 logical NPU.

Summary from the dedicated run:

- MRv2 TPOT regression: **+5.30%** for input 128/output 512 and **+2.09%** for input 4096/output 128.
- Short/decode-heavy trace: about **89%** of the additional device-stage time is extra device free/idle time; kernel count is essentially unchanged.
- Long-prefill trace: about **79%** of the additional device-stage time is extra kernel execution time; kernel count is also essentially unchanged.
- Same image, checkpoint, device, service arguments, warmups, and request protocol; only VLLM_USE_V2_MODEL_RUNNER=1 changed.

This provides a concrete baseline for the “Establish accuracy and performance baselines against the existing 310P runner” item in this RFC.

### Thymos2027 · 2026-09-22

I completed a controlled 310P MRv2 W8A8 eager/ACLGraph performance baseline that may help with the **CI / Tests / Benchmarks** item in this RFC.

Environment:

- Atlas 300I DUO / Ascend 310P3, one logical NPU, TP=1
- Qwen3.5-9B-W8A8-310P, `--quantization ascend`
- `VLLM_USE_V2_MODEL_RUNNER=1`, prefix cache disabled
- vLLM Ascend `c173a64a`, vLLM `0.29.0`, CANN `9.1.0`
- fixed image digest: `sha256:589fc7c911e3c7b83e10c0fed2637d9c6eefd8e1bbfb27a73b3699dc7e68c782`
- only execution mode changed: `--enforce-eager` vs the default `VLLM_COMPILE + FULL_AND_PIECEWISE` path
- balanced order: eager-A -> graph-A -> graph-B -> eager-B; each arm used 3 warmups and 5 measured requests per workload

| Workload | Eager TPOT p50 | Graph TPOT p50 | TPOT change | Throughput change |
| --- | ---: | ---: | ---: | ---: |
| input 128 / output 512 / concurrency 1 | 102.86 ms | 68.84 ms | -33.1% | +49.0% |
| input 4096 / output 128 / concurrency 1 | 99.28 ms | 69.69 ms | -29.8% | +27.7% |

Both independent ABBA pairs had the same effect direction. All 40 measured requests completed with the requested token count and no NPU/runtime errors.

The earlier eager trace showed a median short-decode phase of about 119.6 ms, with about 66.3 ms device busy and 53.1 ms idle/gap. Graph TPOT landing near 69 ms is consistent with ACLGraph removing most host dispatch/launch gaps. I did not collect a graph-side operator trace in this run, so I am treating that as a strong mechanism-level inference rather than millisecond-exact attribution.

Operational costs and current boundaries:

- engine initialization: about 7.35 s eager vs 47.69 s graph;
- graph capture memory: about 0.20-0.21 GiB;
- this run covers concurrency 1 only; concurrency 4, soak, and semantic quality remain follow-ups;
- the graph recommendation is therefore strongest for steady-state services, not frequently restarted jobs.

I also opened #17266 to add the missing 310P W8A8 MRv2 deployment flags and this ACLGraph/eager tradeoff to the Qwen3.5-Dense tutorial.
