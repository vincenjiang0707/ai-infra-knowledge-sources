# [PR #17414] [BugFix][KV Transfer] Expand each KV group by its own physical block size in Mooncake P2P

source: https://github.com/vllm-project/vllm-ascend/pull/17414
state: open | updated: 2026-09-26T10:54:35Z

## 正文

### What this PR does / why we need it?

`MooncakeConnectorScheduler` emits the KV block size in the P2P transfer metadata from `cache_config.block_size`. On hybrid (Mamba / linear-attention) models the logical scheduler block size can legitimately be smaller than the physical KV block size of the attention groups: the KV-cache group specs are resolved at runtime per layer (a sliding-window draft layer of a speculative drafter keeps the kernel-limited 128-token block while all other groups use 1024 tokens).

`EngineCore` then collapses `cache_config.block_size` to the minimum across groups, which is synced back to the API server. The metadata then describes block ids counted in 1024-token physical blocks as if they were counted in 128-token blocks.

The scalar is equally wrong in the opposite regime: under Mamba-aligned hybrid layouts `cache_config.block_size` is the LCM across groups (e.g. 1536), so a 128-token sliding-window draft group next to 1536-token full-attention groups is sized from the 1536 scalar, and the receiver's kernel size and packing for that group are both wrong.

Observed on Qwen3.6-35B-A3B (PD disaggregation, `dspark` speculative decoding, `num_speculative_tokens=7`, TP4/EP): the producer emitted `remote_block_size=128` and the consumer's kernel expansion asserted on the first P2P transfer, killing the decode-side EngineCore:

```
AssertionError: remote_block_size(128) not divisible by kernel_size(1024)
```

MTP on the same model is unaffected because its draft layers are full attention, so every group shares the same (1024) block size and the minimum does not change the layout.

A single scalar cannot describe a mixed layout — it is only ever correct for one of the groups, and the receiver expands *every* group with it. This PR therefore reports the physical block size per KV cache group:

- `MooncakeConnectorScheduler` emits `remote_block_sizes` (one entry per KV cache group, same ordering as the block-id lists) from `group_transfer_info.tokens_per_block`, the same source the producer already uses to count the ids it ships.
- The scalar `remote_block_size` now carries the max across groups (never shrinking the logical value) and is kept for the CP path, the `num_prompt_blocks` calculation, and as the fallback for metadata produced by an older peer.
- `MooncakeConnectorWorker` expands a group's incoming block ids with that group's own physical size, falling back to the scalar when the per-group list is absent (legacy metadata) or does not cover the group.
- The serialized group spec records the group's own page (`kv_cache_spec_block_size`, from `kv_cache_spec.block_size`).
- The consumer resolves the local kernel size as `group_page // block_size_scale` (`group_kernel_block_size`): the group page wins over the global LCM, missing metadata (older peers) keeps the LCM fallback, and a page that does not tile the subdivision fails a divisibility assert instead of truncating the kernel size.
- A failed request invalidates its packed slice ids mapped back to kernel blocks (every failure path in `_handle_request` passes the per-group sizes), so a failure never invalidates the wrong KV blocks.

Consistent layouts (e.g. MTP, all groups sharing one size) keep the same block-size fields as before; the metadata additionally carries the per-group list, which legacy consumers ignore.

#### Scope

The consumer expands every group with its own size. A group whose physical size is larger than the local kernel expands many-to-one (one remote block covers several kernels, the historical direction). A size that tiles the kernel in neither direction keeps the historical scalar fallback and its loud assertion (pinned by unit tests).

A group whose physical size is smaller than the kernel and tiles it (e.g. an all-128 producer against a 1024-token consumer kernel) is packed: `kernel_size // group_size` consecutive remote blocks fill one local kernel block, the local ids are expanded to the packing-slice index inside each kernel block, and the transfer addresses each slice — with a loud assert requiring the remote block stride to tile the local kernel block exactly, so a layout that cannot be slice-addressed fails loudly instead of misplacing KV.

In the live dspark deployment the consumer's sliding-window tensors are split into 128-token blocks (kernel 128), so those groups transfer 1:1 and the packing path guards deployments where the consumer kernel stays at 1024 tokens.

The DFlash2 draft layout is the regime the group-page resolution fixes: a 128-token sliding-window draft group next to 1536-token full-attention groups makes the worker's scalar the LCM (1536), and the old code packed 12 remote 128-token blocks into one 1536-token kernel, so the receiver asserted `remote_block_stride * packing != block_stride` on the first PD request ("Packed group 4 cannot be addressed by slice offsets"); with the group's own page the mapping stays one-to-one.

The CP/DCP paths, which expand every attention group with the scalar only, reject mixed per-group layouts with a clear assertion instead of misplacing the mismatched group.

Mamba state groups are exempt on both sides: the CP path passes their ids through unexpanded, so the mixed-layout check skips them, and the producer's scalar max skips their state page so it cannot inflate the scalar the CP path expands with.

Fixes #17419

The minimum-collapse of `cache_config.block_size` is vLLM 0.28 behavior, not an Ascend misconfiguration (verified by instrumenting spec construction and group resolution in a live deployment), so the fix belongs to the consumer of the value, not to the config plumbing.

Filed upstream: vllm-project/vllm#58362. Same root-cause family upstream: vllm-project/vllm#42895, addressed by the RFC vllm-project/vllm#26744 and the merged vllm-project/vllm#30275.

#### Rolling upgrade note

The directions are **not** symmetric for hybrid models.
- **Old producer + new consumer**: safe. The old producer emits only the (buggy, min-collapsed) scalar and no per-group list; the new consumer falls back to the scalar, which for a mixed layout fails the loud `remote_block_size % kernel_size == 0` assertion — the same crash as before, not a silent misplacement.
- **New producer + old consumer**: **unsafe**. The new producer emits the scalar as `max(logical, group physical sizes)` (e.g. 1024) plus the additive per-group list; the old consumer ignores the list and expands every group with the scalar 1024.
- For the smaller (128-token) group this yields `remote_scale = 8` and an 8x expansion — a silent KV misplacement with no assertion. Mixed-version P/D deployments of hybrid models must therefore upgrade both sides together (or gate the per-group list behind a metadata version bit).

### Does this PR introduce _any_ user-facing change?

No API/interface change. It fixes the P2P transfer metadata for hybrid layouts where physical block sizes differ across KV cache groups (crash -> working transfer, and correct per-group block-id expansion on the consumer).

Layouts where all groups share one block size emit identical metadata to before, and a consumer receiving metadata from an older producer still falls back to the scalar value.

### How was this patch tested?

- New unit tests in `tests/ut/kv_offload/test_mooncake_connector.py`:

#### `TestMooncakeConnectorSchedulerTransferBlockSize`

- desync alignment (logical 128, physical 1024 -> metadata 1024)
- consistent layout stays unchanged (128 -> 128)
- fallback to `cache_config.block_size` when group specs expose no integer block size (also keeps the existing MagicMock-based scheduler tests working)
- end-to-end `request_finished` metadata (`remote_block_size=1024`, `num_prompt_blocks=1`)
- per-group report for a mixed layout (1024-token and 128-token groups -> `remote_block_sizes=(1024, 128)`)
- a compressed group (compress_ratio > 1) reports tokens per block id
- a Mamba state group's block_size (max_model_len without prefix caching) does not inflate the scalar transfer block size

#### `TestMooncakeConnectorWorkerKernelBlockIds` (receiver-side expansion)

- a group whose size is smaller than the scalar keeps 1:1 ids (the scalar would shift them 8x)
- a group whose size is larger than the local kernel expands and still applies the `num_computed_tokens` prefix skip
- a group whose 128-token physical size is smaller than a 1024-token kernel packs 8 remote blocks per local kernel block: local ids expand to the packing-slice index, remote ids keep their own granularity, and the prefix skip uses the smaller remote token size
- a packed group trims to a partial remote tail
- Mamba state groups pass through packing unchanged
- legacy metadata (empty per-group list) falls back to the scalar
- a short per-group list falls back for the groups it does not cover
- a two-group mixed layout (1024-token and 128-token kernels) expands each group with its own size
- a group size that tiles the kernel in neither direction (e.g. 192 against a 1024-token kernel) keeps the scalar fallback and its loud assertion
- a 128-token draft page against a 1536-token LCM stays one-to-one (the LCM would have packed 12 remote blocks per kernel) and the prefix skip uses the group's own page granularity
- `group_kernel_block_size` prefers the group page over the LCM and keeps the LCM fallback for legacy metadata
- the page size is recorded in the handshake metadata
- the CP/DCP entry rejects mixed per-group sizes and accepts uniform ones
- a page that does not tile the tensor subdivision fails the divisibility assert (100 with scale 8) instead of truncating the kernel size
- the CP/DCP mixed-layout check skips Mamba groups (their state page does not trip it while the attention groups stay uniform)

#### `TestCoreFunctionality` (transfer byte arithmetic)

- a packed group addresses pseudo blocks (each covering 1/packing of a kernel block) and merges consecutive slices into one contiguous copy
- the reformat-failure path maps packed slice ids back to their kernel blocks before invalidating them
