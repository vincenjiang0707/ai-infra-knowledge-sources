# [PR #17298] [Performance][Attention] Fuse MLA output gating and live-row masking

state: open | updated: 2026-09-27T08:28:24Z

## 正文

### What this PR does / why we need it?

Replace the materialized MLA output `sigmoid` followed by in-place multiply with one Triton kernel. The kernel preserves the sigmoid rounding point, handles strided rows and empty launches, and optionally masks inactive rows before a bias-free output projection. An output-copy helper zeros inactive rows and graph padding; it is available for future attention backends but is not wired into a production backend by this PR. Both helpers require contiguous columns while allowing strided rows. The optional gate mask must cover every projected row; the output helper requires equal input/output hidden widths.

### Model and call-path impact

The replacement is called once after decode/prefill MLA output assembly and before `o_proj` **only when `AscendMLAImpl` receives a non-null `g_proj`**. `AscendMlaDCPImpl` inherits this forward path. The production MLA call does not pass the optional `token_live` mask.

| Model/path in the audited vLLM revision | Gate route and impact |
| --- | --- |
| Kimi-K3 gated MLA layers, text and multimodal | `mla_use_output_gate=true` constructs and passes `g_proj`; these layers call the new kernel. The [published config](https://huggingface.co/moonshotai/Kimi-K3/blob/main/config.json) has 24 MLA layers among 93 text layers. The other 69 are KDA layers with a separate gate. |
| Kimi-K3 DSpark draft MLA | The Ascend draft adapter passes `use_output_gate=False`; it does not call this kernel. |
| DeepSeek-V2/V3-family MLA, GLM5Next MLA, Bailing MLA, OpenPangu, Sarvam and AXK1 | Their inspected `MLAModules` constructors do not pass `g_proj`; the new kernel is not launched. Bailing's separate model-level gate and the Ascend SFA backend's gate remain on their existing paths. |
| `flash_attention_output` helper | No production caller in this PR; its numerical behavior is tested, but it does not affect current model execution. |

This reachability audit uses vLLM [`84030bb`](https://github.com/vllm-project/vllm/commit/84030bbe3d74d99bad477a3d2e37a973ccd8865c) and this PR's Ascend code. It describes the current constructors, not an assumption that every MLA model has an output gate.

### Does this PR introduce _any_ user-facing change?

No configuration change. Kimi-K3 gated MLA calls use the new kernel automatically. The measured results below do **not** establish a performance improvement.

### How was this patch tested?

- CPU launch-contract tests: `python -m pytest --confcutdir=tests/ut/attention tests/ut/attention/test_flash_attention_output_cpu.py -q`: **19 passed**. Negative cases cover short/strided masks, noncontiguous columns, and narrow/wide output buffers; each rejects the input before kernel launch. Ruff lint/format and `git diff --check` passed.
- Single-card A3 and A5 numerical tests: **42/42 passed on each machine** against the materialized `sigmoid` reference after the input validation changes. The matrix covers BF16/FP16/FP32, masked NaN/Inf rows, tails, strided rows, padded output, and changed inputs on NPU graph replay. The A5 runtime uses vLLM `84030bb`; the A3 runtime uses vLLM `0.30.0`. Both load this PR's kernel module into an existing installation for the operator tests.
- Kimi-K3 has 96 attention heads and `v_head_dim=128`. For TP 1/4/8/16, the per-rank gate widths are **12288/3072/1536/768**. BF16 cases cover token rows 1, 8, 32 and 128, including inactive padded rows. These are per-rank tensor tests on one card, not multi-rank TP or full-model service tests.

### Single-operator performance

`python benchmarks/flash_attention_gate.py` alternates the original `projected.mul_(torch.sigmoid(gate))` and fused paths for seven paired trials. Each eager sample batches 100 calls; each graph-replay sample batches 200 calls. Wall time includes Python dispatch and NPU execution, with synchronization at sample boundaries; warmup, capture and allocation are excluded. BF16 Kimi-K3 shapes cover `[M,1536]` for `M=1,8,32,64,128` and `[M,12288]` for `M=1,8`.

| Device | Eager original → fused, median range | Graph replay at `[M,1536]`, `M=1,8,32,64` |
| --- | --- | --- |
| A5, current revision | 11.6–12.5 → 45.8–46.8 µs/call | Approximately 20.5–21.1 µs/call for both paths; no consistent gain |
| A3, preceding revision | 13.6–14.8 → 60.2–63.3 µs/call | Approximately 283–289 µs/call for both paths; no consistent gain |

The A3 numerical tests passed after the validation changes, but a fresh A3 benchmark overlapped other device activity and is excluded. **The fused path regresses eager launch latency in the current A5 measurements, and graph replay shows no stable benefit.** These are single-operator measurements; no full-model ITL or throughput was measured. The current branch should not be presented as a demonstrated performance gain.
