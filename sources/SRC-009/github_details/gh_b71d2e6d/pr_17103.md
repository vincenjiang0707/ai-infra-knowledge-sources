Title: [Performance][Sample] Add Triton top-k/top-p sampling kernel based on Qrita

---
### What this PR does / why we need it?

Port the upstream Qrita top-k/top-p sampling kernel (vLLM v0.28.0 `vllm/v1/sample/ops/topk_topp_triton.py`, arXiv:2602.01518) to triton-ascend, replacing the sort+mask fallback chain on the A2/A3 decode path.

**Current behavior on A2/A3** (non reduce-sample): `_apply_top_k_top_p_pytorch` runs a 7–9 kernel launch chain including a full-vocabulary `sort` (O(V log V) per row, ~1ms/step at V≈152k). The CANN `npu_top_k_top_p` op degrades severely (5–28ms) with large or mixed k values, so it is only viable on A5. Issue #14705 tracks the resulting sampling hotspot; #14138 measured the top-p/top-k post-processing at 22–31% of total device operator time.

**This PR**:

- Adds `vllm_ascend/ops/triton/v2/sample/topk_topp.py`: single-launch pivot-based truncation + selection, no full sort. triton-ascend adaptations follow in-tree precedents (`resample.py` worker-partitioned grid, dense buffers instead of scatter, int32 counters, `tl.cumsum` as already used by resample/penalties kernels).
- Tile sizes `BLOCK_SIZE=4096 / BLOCK_SIZE_TRUNC=2048` per the A3 review feedback on the earlier attempt #13847 (reverted via #14887; root cause was `BLOCK_SIZE=1024` causing 126 tile iterations plus a top-p termination edge bug — larger tiles here, termination-consistency fix kept).
- Routing in `sample/sampler.py`: A2/A3 non-reduce-sample → Triton kernel; A5 unchanged (`is_950()` keeps the CANN op path); reduce-sample mode keeps the gathered-tuple path on every device; batch-invariant mode keeps the original path.
- MRV2 entry (`worker/v2/sample/apply_top_k_top_p.py`): Triton first with pytorch fallback; the warmup branch now runs the kernel once so its workspace is reserved (fixes the OOM TODO in that file).
- Numerical parity: fp32 accumulation, same pivot semantics as upstream. Exact bitwise equality with the pytorch path holds for non-tied logits; for tied boundary groups the pytorch sort+cutoff keeps the whole tie group while this kernel truncates to the exact quota (documented in the operator doc) — both are valid top-p masks.
- Operator doc (`ops/triton/docs/v2/sample/topk_topp.md`) and e2e nightly parity test (`k/p combinations, mixed-k, no-op rows, -inf rows, tie groups, large shapes`) plus CPU-runnable dispatch/warmup UTs with routing-matrix coverage (reduce_sample × is_950 × capability).

### Performance impact

Sampling-stage: replaces a multi-launch full-vocab sort (~1ms/step at small B, worse at large B) with a single launch; expected TPOT −2~8% depending on batch/vocab, consistent with the profile in #14138/#14705.

### How was this patch tested?

- `python -m pytest tests/ut/sample/test_topk_topp_triton.py` (CPU, isolated-process verified)
- e2e parity test added at `tests/e2e/nightly/single_node/ops/singlecard_ops/triton/test_topk_topp.py` — **requires NPU CI**
- ruff check/format clean

Note: developed on a host without NPU; the kernel needs the CI e2e run (A2/A3) to confirm compile + parity + perf numbers. Kept in draft until the CI matrix is green.

Closes #14705
