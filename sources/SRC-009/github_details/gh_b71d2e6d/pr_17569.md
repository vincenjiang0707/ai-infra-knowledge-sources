# [PR #17569] [BugFix][Model] Preserve private cache groups with prefix caching disabled

## 正文

### What this PR does / why we need it?

GLM-5.3-Flash can fail during startup with `--no-enable-prefix-caching`. The block-size resolver excludes request-private tail state from scheduling/hash alignment (4480 in the reproduced configuration), but the coordinator factory selects upstream `KVCacheCoordinatorNoPrefixCache`, which requires alignment against every group's block size, including the private tail's size of 9.

Select the existing `AscendHybridKVCacheCoordinator` for configurations mixing prefix-cacheable and request-private groups, also when caching is disabled. This preserves each manager's independent geometry and propagates `enable_caching=False` to the pool/managers. Ordinary configurations without private groups retain their existing path.

Refs #15665.

### Does this PR introduce _any_ user-facing change?

GLM-5.3-Flash with prefix caching disabled can initialize without the private-tail alignment assertion. Prefix caching remains disabled; no flags, defaults, or cache layouts change.

### How was this patch tested?

- Added two regression cases in `tests/ut/patch/platform/test_prefix_cache_cp_patches.py`: ordinary full-attention and mixed full-attention/private-tail configurations. They exercise the real block-size resolver and coordinator, allocation/free across repeated requests, and absence of cached hashes or prefix hits. Before the fix: 1 failed / 1 passed; the failure is the upstream alignment assertion.
- Seven related UT files: **157 passed** (14 existing deprecation warnings). Full `bash format.sh ci` passed.
- Real Atlas A3, GLM-5.3-Flash-w8a8: **16/16 requests completed**, each with **1,000,000 input tokens and 128 output tokens**, in 1450.605 seconds. TP1/DP16/EP16, one request per rank, FULL_DECODE_ONLY graphs, MTP5, async scheduling/speculative execution, MRV1, and prefix caching disabled. All ranks' runtime configurations were checked; zero prefix hits, preemptions, or server errors. Two 16-request short-input runs also passed, with identical outputs across the repeated short run.

The hardware/UT validation used Ascend main `991eb5c2b` plus #17545, #17565, and this fix, with vLLM `ced6857afa0ea7b2e3f0846a62e1394e90f15607`. The two preceding fixes are required for that 1M workload and are not included in this PR. The publication branch is based on `fa60e23c1`; its two changed files are byte-for-byte identical to the validated Git blobs, and intervening main commits do not change these paths.

The cause remains under investigation; this PR establishes startup and functional execution, not cross-mode numerical or long-context accuracy. No nightly cases were added.
