## 正文

## Purpose
A layerwise AscendStore load failure on a hybrid (multi-group) model currently raises in the worker because group-local block IDs cannot safely identify the failed request in the scheduler. Report the failed request instead, so it can be restarted from scratch rather than terminating the engine.

## Changes
- Report multi-group layerwise load failures by request ID through the current KV transfer results API. Every worker reports completion for synchronous layerwise loads so the multi-worker aggregator can publish a failure from any rank.
- Bypass the external cache once when the failed request is re-admitted.
- Preserve newly allocated AscendStore state when preemption and re-admission happen in the same scheduler step.
- Permit the recompute policy for hybrid models using AscendStoreConnector; retain block-level reporting for single-group models.

## Validation
- Added unit cases for worker failure reporting, connector completion propagation, one-time lookup bypass, and same-step re-admission state.
- `ruff format --check`, `ruff check`, `python -m compileall`, and `git diff --check` passed for touched files.
- On the 119/121 deployment with the paired vLLM scheduler patch, the layerwise benchmark completed 40/40 prefix requests and 20/20 full requests; the non-layerwise control also completed 40/40 and 20/20. The deployment used the corresponding installed-package patch, not this exact upstream-main commit.
- Full pytest could not run on this Windows checkout: PyTorch and pytest are not installed in the available environment.

## Dependency
Current vLLM main only handles `failed_recving` for requests waiting on asynchronous KV transfers. Synchronous layerwise failures also need request-level preemption in vLLM before this change provides end-to-end recovery. No vLLM code is submitted in this PR.

- vLLM main: https://github.com/vllm-project/vllm/commit/ced6857afa0ea7b2e3f0846a62e1394e90f15607

**Suggested PR Summary:**

```markdown
### What this PR does / why we need it?
This pull request enables recomputation-based recovery for multi-group (hybrid) KV load failures in the `AscendStoreConnector`. Previously, a multi-group KV load failure would raise a `RuntimeError` and crash. This change allows the worker to report the failed request to the scheduler via `_failed_recving`, which then triggers preemption and full recomputation.

Key changes include:
- Tracking failed receiving requests in `pool_worker.py` and reporting them through `get_failed_recving()`.
- Updating `AscendStoreConnector.get_transfer_results` to include failed receiving requests.
- Updating `KVPoolScheduler` to bypass external KV lookup once for failed requests and avoid removing unfinished requests if they are rescheduled in the same step.
- Allowing hybrid models to use the `recompute` load failure policy when using `AscendStoreConnector`.

**Feedback / Review Comments:**
- **Lease Leak in `pool_worker.py`**: When a multi-group load fails, acquired leases for other groups of the request are not released, leading to a lease leak. We should set `request.load_spec.can_load = False`, release acquired leases immediately, and break the loop.
- **Multi-worker Aggregator Hang**: If `can_load` is set to `False`, the request won't be added to `results.finished_recving` in the layerwise branch, causing a hang. We should always update `results.finished_recving` with `failed_recving`.

### Does this PR introduce _any_ user-facing change?
No.

### How was this patch tested?
Unit tests were added and updated in `test_pool_scheduler.py`, `test_pool_worker.py`, and `test_kv_transfer_failures.py`.
```
