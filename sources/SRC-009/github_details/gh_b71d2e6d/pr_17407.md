# [PR #17407] [BugFix] Truncate Mooncake hybrid prefill before prefix-cache lookup

source: https://github.com/vllm-project/vllm-ascend/pull/17407
state: closed | updated: 2026-09-27T10:22:15Z
labels: module:tests, ready-precise

## 正文

### What this PR does / why we need it?

Move MooncakeHybrid's existing conditional P-side prompt truncation to `on_new_request`, before the scheduler queries the local prefix cache. Previously, `get_num_new_matched_tokens` shortened the prompt after local lookup, leaving the computed-token count inconsistent with the request length.

For example, with 128-token blocks and a warm prefix cache, a raw 513-token request can get a local hit of 512 and then be shortened to 512. The scheduler consequently computes zero new tokens and fails `assert num_new_tokens > 0`. Truncating at ingress makes local lookup return 384 and schedules the remaining 128 tokens. The existing truncation condition, idempotence guard, and P/D state-transfer protocol are preserved.

### Does this PR introduce _any_ user-facing change?

Fixes a P-side scheduler crash for hybrid models that require prompt truncation when prefix caching is enabled. No configuration changes are required.

### How was this patch tested?

CPU tests used vLLM commit `84030bbe3d74d99bad477a3d2e37a973ccd8865c` and the repository UT mocks.

- The new regression starts from raw token sequences and real `Request` objects, using the real scheduler, cache manager, and factory-created MooncakeHybrid connector. It warms the cache, completes the request, handles a simulated remote ACK, frees blocks, and reuses the prefix. It covers raw lengths 512/513/514 without speculation and with MTP/DSpark configured for five speculative tokens.
- The same regression fails on unpatched main in all three configurations and passes with this fix.
