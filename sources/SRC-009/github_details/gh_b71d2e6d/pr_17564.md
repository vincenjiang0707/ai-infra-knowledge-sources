### What this PR does / why we need it?

Migrate Kimi K3 attention-residual operators to AscendC with native forward, fused, prefill, and with-add implementations, torch/Meta bindings, and model integration.

This PR carries the changes from #17177 into a branch owned by sugm0521, preserving the original commits and authorship. It includes a merge of upstream main at 7e2c563f5e6ceddb5b0975753013832d356e096e. The build-list conflict is resolved by retaining all four A5 residual operators alongside the upstream rename to `chunk_fwd_o_vllm`; unrelated upstream changes are preserved.

### Does this PR introduce _any_ user-facing change?

Yes. Kimi K3 attention-residual execution uses the native AscendC operators and registered torch interfaces introduced by the original PR. The conflict-resolution commit adds no further API changes.

### What this PR does / why we need it?
This pull request migrates the Kimi K3 attention residual operators (`AttnResFwd`) to AscendC, providing optimized implementations for both `arch22` (A2) and `arch35` (A5/ascend950) architectures. It introduces native forward, fused, prefill, and with-add variants, along with their corresponding PyTorch and Meta bindings.

However, several critical issues were identified in the implementation:
- **32-Byte Alignment Violations**: Multiple vector instructions (e.g., `WholeReduceSum` and `StoreDist::DIST_FIRST_ELEMENT_B32`) are invoked with operands like `vecMeta_[metaIdx]` or `vecMeta_[n]` that are not guaranteed to be 32-byte aligned, which can cause silent data corruption or runtime faults.
- **Critical Race Conditions**: Asynchronous `DataCopyPad` (MTE3) operations are immediately followed by freeing the queue slot (`outQue_.FreeTensor(outLocal)`), allowing the vector engine to overwrite the buffer before the copy to GM completes.
- **Suboptimal Tiling**: The tiling logic hardcodes the available UB size to 192KB instead of dynamically using `compileInfo_.ubSize`, which unnecessarily restricts performance on platforms with larger UB.

### Does this PR introduce _any_ user-facing change?
Yes, it registers new custom PyTorch operators under `torch.ops._C_ascend`:
- `attn_res_fwd`
- `attn_res_fwd_with_add`
- `attn_res_fwd.fused`
- `attn_res_fwd.fused_prefill`

### How was this patch tested?
The changes are covered by:
- Unit tests: `tests/e2e/nightly/single_node/ops/singlecard_ops/test_attn_res_fwd.py`
- Benchmark: `tests/e2e/nightly/single_node/ops/attn_res_prefill_benchmark.py`
- Meta dispatch tests: `tests/ut/ops/test_attn_res_prefill_meta.py`
