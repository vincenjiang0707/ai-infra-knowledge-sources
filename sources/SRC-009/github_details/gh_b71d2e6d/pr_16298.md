# [PR #16298] [Feature] Add segment-level tokenizer cache for agent workloads

## 正文

## Motivation

Prefix caching removes the *compute* for a repeated conversation prefix, but tokenization is still `O(full prompt)` on every turn: the server has to know the token ids before it can look anything up in the KV cache. In agent workloads, where turn N re-sends turns 1..N-1 verbatim and appends a short suffix, the tokenizer becomes the dominant per-request frontend cost once the prefix-cache hit rate is high.

## What this PR does

- Adds a segment-level (incremental) tokenizer cache (`vllm_ascend/tokenizer_cache.py`). Prompts are cut at added-token boundaries (chat templates emit one at every message boundary), and each segment's token ids are cached, so turn N only tokenizes its own suffix.
- Correctness rests on the identity `encode(A+B) == encode(A) + encode(B)`, which holds only when the cut falls immediately after an added token. The identity is **verified empirically at startup** against a probe corpus; the cache disables itself if the check fails. Anything not covered falls through to the plain tokenizer call, so an ineligible request is bit-identical to the uncached path by construction.
- Wires the patch in `patch/platform/patch_tokenizer_cache.py` and registers it in `patch/platform/__init__.py`; adds the `VLLM_ASCEND_TOKENIZER_CACHE_GB` env variable to `envs.py`.

## Usage

```shell
export VLLM_ASCEND_TOKENIZER_CACHE_GB=2  # GiB per API server process; 0 (default) disables
```

Only pays off at very high prefix-cache hit rates; keep it at 0 otherwise.

### What this PR does / why we need it?
This pull request introduces a segment-level (incremental) tokenizer cache for high prefix-cache-hit serving on Ascend. In agent workloads where conversation history is repeatedly sent with small suffixes, tokenization overhead scales with the full prompt length and dominates frontend costs. By caching tokenization results per segment (delimited by added/special tokens), this PR avoids redundant tokenization work. The cache is enabled via the `VLLM_ASCEND_TOKENIZER_CACHE_GB` environment variable.

Feedback on this PR highlights several critical issues:
1. The imported `vllm.utils.cache.LRUCache` lacks standard support for `getsizeof`, `__setitem__`, and `stat()`, which could lead to runtime errors. A self-contained LRU cache implementation is recommended.
2. In `_tokenize_prompt`, `prompt` can be a plain string, so accessing `prompt["prompt"]` directly will raise a `TypeError`.
3. Tokenizers that are not weakly referenceable will raise a `TypeError` when used with `_CACHES` (a `WeakKeyDictionary`). Storing and retrieving from `_CACHES` should be wrapped in try-except blocks.

### Does this PR introduce _any_ user-facing change?
Yes, it introduces a new environment variable `VLLM_ASCEND_TOKENIZER_CACHE_GB` to enable and configure the size of the incremental tokenizer cache.

### How was this patch tested?
The patch includes self-checking mechanisms at startup against a probe corpus to verify the concatenation identity before enabling the cache.
