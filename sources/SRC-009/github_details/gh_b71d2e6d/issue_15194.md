# [Bug][AscendStore][MemCache][device_sdma] G2G copy returns CQE status 9 COMPERR followed by put -1/-7

## Summary

In the non-layerwise DeepSeek-V4 Flash KV-save path using vLLM-Ascend AscendStore, MemCache/MemFabric, and the `device_sdma` protocol, a direct G2G SDMA copy completed with CQE status 9 (`COMPERR`). MemFabric then returned `BM_ERROR=-1`, later operations returned `BM_TIMEOUT=-7`, and MetaService reported `REMOVING/-3101` while cleaning up the same failed keys.

The failure later caused one-rank KV-save divergence and TP collective desynchronization, but this issue specifically asks for the low-level reason why the first `device_sdma` SQE completed with CQE status 9 and for clarification of the MemFabric/MemCache address validation, timeout, and cleanup behavior.

The upper-layer vLLM-Ascend failure-propagation problem is tracked separately in:

* https://github.com/vllm-project/vllm-ascend/issues/14106

All internal IP addresses, customer request content, hostnames, and private paths are removed.

## Source audit

### MemFabric tag comparison

```text
v1.1.3  19c74dde2fc1385e8ab18c7f5ca295bda3936c69
v1.1.4  c01f3ad842b9ff7412681a44b67141ce7a124c6d
v1.2.0  999034e9320abf27bbde7be83a32d3bf4d0f7940
```

Findings:

1. `hybm_stream.cpp` is identical in 1.1.3 and 1.1.4.
2. In all inspected tags, `ReceiveCqe()` prints the SQE and returns `BM_ERROR` when CQE `errorCode != 0`.
3. `Synchronize()` uses `MAX_RETRY=1000000` and `usleep(1)` in the inspected implementations.
4. 1.2.0 adds more timeout/SQE logging.
5. `BatchCopyG2G()` still merges continuous source/destination segments and performs `InnerWait()` after submission.
6. 1.2.0 adds a `count > UINT32_MAX` check, but the failed lengths here were only 4160 and 32768 bytes, so that check does not cover this incident.

### MemCache input validation

`MmcacheStore::BatchPutFromLayers()` validates vector shape and buffer counts. `GetBufferArrays()` forwards `void *` and size as `{addr, len}`. In the inspected implementation, we did not find submission-time validation that records or rejects:

* whether `addr` belongs to a currently valid/registered KV region;
* whether `addr + len` exceeds the region boundary;
* whether the block owner/reuse epoch is still valid;
* whether every TP rank has reached a consistent save result.

If the address/GVA lifecycle is invalid, the current visible symptom is a generic completion-side `COMPERR` rather than a pre-submit error identifying the address condition.

## Controlled tests and exclusions

On homogeneous isolated nodes, we ran real requests covering:

```text
cold 64K
cold 128K
cold 256K
alternating 64K / 1K
async scheduling on / off
four concurrent fresh 128K requests
```

All returned HTTP 200 and did not reproduce CQE9.

A temporary read-only address audit covered the six hybrid KV-cache groups: physical block IDs, base/stride, submitted address/length, and visible region bounds. It did not identify a connector-visible deterministic out-of-bounds address. HCCS health was normal, retry/error counters were zero, and ECC counters were zero in the controlled environment.

These tests rule out a stable "normal long request always exceeds the visible region" bug. They do not rule out a narrow release/reuse race, remote GVA registration lifecycle problem, or device execution transient.

Separately, injecting a one-rank 220-second delay immediately before the real `BatchPutFromLayers()` deterministically reproduced the upper TP collective desynchronization. That test produced zero `error cqe` and zero `COMPERR`; it explains the service-collapse amplification path, not the original CQE9.

## Why this is not currently classified as hardware failure

CANN documentation identifies status 9 as `COMPERR`, distinct from:

```text
status 8: ECC
status 2: SMMU Terminate
status 5: DAW unmapped
```

The incident window contains no earlier ECC, HCCS link fault, AER, host OOM, or device reset. Restarting only the Prefill application processes restored service; no NPU reset, hardware replacement, or link reconfiguration was required. This does not exclude a one-time device/firmware transient, but there is not enough evidence to label the device as faulty.

## Expected behavior

1. A G2G copy using valid and still-registered source/destination GVAs should complete successfully.
2. An invalid/unregistered/reused GVA should be rejected before submission with a distinguishable error, rather than only a generic completion-side `COMPERR`.
3. `BatchCopyG2G` / `BatchPutFromLayers` logs should identify the failing segment, local/remote rank, GVA registration, owner, and address lifetime.
4. Timeout should have a deterministic deadline and preserve the last pending SQE/segment.
5. Cleanup of a failed key should be idempotent and should not add repeated `REMOVING/-3101` errors.

5. Is Meta `REMOVING/-3101` a known cleanup-idempotency issue after data-copy failure?
