## 评论 (4)

### QwertyJack · 2026-09-14

复现了，和 #15984 同根因，不是 parser 问题。

**环境**：A3 单机 8 卡 → TP8+EP（文档 A3 配置是 TP16），vLLM 0.23.0 + vllm-ascend `db701c1fd`，MTP2 / `FULL_DECODE_ONLY` / `max-model-len 133120` / `gpu-memory-utilization 0.85`。此配置下每卡权重 39.2GB，KV 只剩 9.0 GiB（`Available KV cache memory: 9.00 GiB`），块池明显小于 TP16 配置。

**长度阶梯（单请求，`max_tokens=1`）**

| `--max-num-batched-tokens` | prompt tokens | 结果 |
|---|---|---|
| 8192 | 3303 / 3447 | ✅ 0.87s |
| 8192 | 6588 | ❌ 卡死，引擎被永久毒化 |
| 4096 | 6588 / 13160 / 26303 | ✅ 1.9s / 3.4s / 6.7s |

4096 下 4 路并发 × 5724 token 全部 200；工具调用正常（5679 / 11029 token 均返回合法 `tool_call`）。
卡死后 `Running: 0 reqs, Waiting: 1 reqs, GPU KV cache usage: 0.0%`，4-token 小请求也全部超时，须重启才恢复；栈显示引擎卡在 `step_with_batch_queue → get_response`，8 个 worker 全空转、无算子在跑，属调度/准入问题而非 NPU hang（症状与 #16365 一致）。

**根因**（同 #15984）：`vllm_ascend/models/glm5_next.py` 的 `AscendGlm5NextCompressorStateCache.__init__` 中
`block_size = sliding_window = compress_ratio = index_kpool = 4`，该组由 `SlidingWindowManager` 管理，准入按 `cdiv(tokens, 4) + 1` 计块，chunk 一大就永远进不了 running，既不报错又 head-of-line 阻塞整个引擎。

**与 function call 无关**：工具字段只是让 agent 请求的 prompt 更大、越过悬崖；旧 GLM parser 全量重扫在 64K 字符时也只有 ~1.8s。

**规避**：`--max-num-batched-tokens 4096`（已验证，含并发）。根治方向同 #15984：该 state 组不应按 1/4 token 消耗共享块索引，或在启动时对 `mnbt × compress_ratio` 的超限做准入校验/告警。
