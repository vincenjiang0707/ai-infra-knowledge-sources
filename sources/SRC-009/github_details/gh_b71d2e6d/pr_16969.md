## 正文

### What this PR does / why we need it?

MRv2 EPLB maps logical expert IDs to physical slots on every MoE forward, even when load collection is disabled. This work repeats across MoE layers, so its per-layer overhead can offset the benefit of better expert placement.

This PR reduces work in that routing/collection path:

1. **Avoid duplicate routing-table rows for single-copy experts.** When physical and logical expert counts are equal, every logical expert has one physical copy and all 1024 routing-table rows would be identical. Build one row using host shape metadata and use the actual row count during lookup. Redundant-expert configurations retain the periodic table. In-place refresh is preserved when the shape is unchanged so graph replay retains stable addresses.

2. **Aggregate small-input loads before updating counters.** For at most 256 route entries (`num_tokens * top_k`) and at most 1024 physical experts, one Triton program handles the whole input. A histogram aggregates occurrences and each counter has one writer, replacing per-route atomic additions. Invalid IDs and padding use a separate discarded bin. Larger inputs retain atomic updates. This optimization relies on ordered same-layer forwards on the compute stream; it does not support concurrent non-atomic updates to the same counters from multiple streams.

3. **Skip recording-only work when collection is disabled.** Masking the final store still leaves histogram computation and counter reads in the small-input path. A device-side `if record_enabled` now encloses both histogram and atomic collection paths, including real-token-count loading and recording predicates. Mapping and output stores remain unconditional. The existing device scalar can change between graph replays without host synchronization or recapture. This folds the standalone change from #17028 into this PR.

4. **Keep useful compile-time constants while limiting dynamic specialization.** TopK and routing-table row count are constexpr so the compiler can simplify indexing. Dynamic `numel` uses `do_not_specialize`; histogram/atomic selection remains a compile-time choice.

The small-input branch is an optimization candidate, not a guarantee that every shape is faster. Histogram work, device branching, and backend compilation behavior require measurement. No new performance result is claimed for the combined revision.

### Does this PR introduce _any_ user-facing change?

No new configuration or environment variables. The intended expert mapping and load-counting results are unchanged. This PR changes neither the rebalance policy nor the collection window, rearrangement interval, or weight-migration algorithm.

When collection is disabled, physical expert IDs are still produced and existing counters remain unchanged. When enabled, only valid, non-padding routes contribute to counters.
