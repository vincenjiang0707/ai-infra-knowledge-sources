# [PR #17535] [BugFix][Attention] Rebuild the sparse MLA plan from the passed indices for MTP drafts

## 正文

### What this PR does / why we need it?

`sparse_mla` must generate the operator plan from the very tensors the operator
call receives — a plan built over different ones makes the kernel index past what
it was handed. It only regenerated the plan when the query was trimmed to the
unpadded row count, so a replayed FULL graph kept the plan written during
metadata construction.

For the GLM-5.3-Flash MTP draft on A5 (`use_smla=True`) that is fatal: the draft
replays one captured graph per step, and the plan the replayed graph reads can
describe a different step's rows. Its per-row top-k lengths then exceed what each
row's index buffer actually holds and the operator reads the `-1` padding as KV
positions:

```
aicore error, error code = 82
The extend info: errcode:(82) errorStr: The address for MTE2 to write UB and
MTE3 to write L1/UB is out of bounds.
```

Observed on the draft graph replay only: deterministic for one kernel (identical
pc on every run), gone with the draft eager, and absent on A3 (`use_smla=False`,
no plan at all).

This PR rebuilds the plan whenever the draft model is running, deriving the top-k
lengths from the indices actually passed. The target is unchanged: it refreshes
the plan from unpadded host values every step.

### Does this PR introduce _any_ user-facing change?

No.

### How was this patch tested?

Unit tests added to `tests/ut/attention/test_sfa_nope_metadata.py`:

- `test_a5_smla_rebuilds_plan_for_the_draft_model` — equal-shaped call with the
  draft model running: the plan is regenerated, and the padding row claims zero
  entries even though the prediction said three.
- `test_a5_smla_keeps_the_built_plan_for_the_target` — the equal-shaped target
  call keeps the plan written during metadata construction.

End-to-end on the reporter's A5 deployment (GLM-5.3-Flash W8A8-MXFP8, DP8×TP1+EP,
MTP `num_speculative_tokens=5`, `FULL_DECODE_ONLY`): before the change the draft
graph replay hit the device error within seconds of the first requests; after the
change the same traffic runs without it.

### Notes

- Relates to #17178, which enables the ACL-graph draft for GLM-Next MTP and is
  what exposes this latent mismatch on A5. 
- The condition is expressed as "the draft model is running" because that is the
  caller whose plan can describe rows it is not passing. A follow-up could derive
  the plan from the indices unconditionally, at the cost of one plan regeneration
  per attention layer per step.
- Still under investigation: the SMLA metadata state is keyed by
  `draft_index=None` on the capture path (`build_for_graph_capture` -> `build` ->
  `_build(draft_index=None)`) but by `draft_index=i` on the runtime path
  (`build_for_drafting`). If that keying is the reason the replayed graph reads a
  stale plan, the capture hook should use the same per-step keying; the change
  here makes the plan correct regardless.
