# [PR #17554] [BugFix][SpecDecode] Remove dead BLOCK_SIZE constexpr from Ascend DFlash input kernel

source: https://github.com/vllm-project/vllm-ascend/pull/17554
state: open | updated: 2026-09-27T03:23:31Z
labels: module:tests

## 正文

### What this PR does / why we need it?

`_prepare_dflash_inputs_kernel_ascend` declares `BLOCK_SIZE: tl.constexpr` and never reads it. Block 0 walks tokens in a scalar loop; the runtime `block_size` is only the KV-cache block size. Other blocks return immediately.

Upstream still passes `BLOCK_SIZE`, derived per step as `min(256, next_power_of_2(query span))`. Triton includes that constexpr in the cache key, so each new length compiles the same kernel again. On Ascend 910B one new bucket is about 3s. `warmup_kernels` only runs short dummy requests, so a longer real prompt still compiles on the first request. With warmup already applied, first-request TTFT went from 3.998s to 1.182s after this value left the cache key.

Delete the parameter. The patch-layer shim pops `BLOCK_SIZE` so Triton does not reject the kwarg upstream still passes.

### Does this PR introduce _any_ user-facing change?

Bug fix, no API change. The DFlash input kernel has one cache entry instead of one per length bucket.

### How was this patch tested?

- Dropped `BLOCK_SIZE` from the existing `test_prepare_dflash_inputs.py` launch, which calls the Ascend kernel directly.
- Local 910B check: with warmup already applied, removing this constexpr from the cache key took first-request TTFT from 3.998s to 1.182s.
