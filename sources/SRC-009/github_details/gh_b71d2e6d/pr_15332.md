# [PR #15332] [Feature][Kernel] Extend split_qkv_rmsnorm_rope with value normalization for Gemma4

## 正文

### What this PR does / why we need it?

Gemma4 runs its pre-attention chain (qkv split, per-head q/k RMSNorm, RoPE, and a weight-less per-head **v** RMSNorm) as separate ops on Ascend. The existing fused `split_qkv_rmsnorm_rope` kernel cannot cover it because it copies V straight out of the fused QKV tensor, and the existing `qknorm_rope_fusion_pass` has no notion of the V norm.

This PR adds a `split_qkv_rmsnorm_rope_vnorm` Triton kernel and a graph fusion pattern that rewrites Gemma4's pre-attention chain into it. It replaces the `Gemma4Attention` monkey-patch used in the earlier revision of this PR, as requested in review.

**Kernel.** A variant of `split_qkv_rmsnorm_rope` that normalizes V instead of copying it. Because V now needs the same float32 reduction scratch as Q and K, the separate wide-tile V loop that the base kernel uses for the plain copy no longer pays for itself, so V is folded into the q/k loop:

- one `tl.load` covers the whole fused row (`total_hidden_size`) instead of two separate column segments;
- one RMSNorm reduction covers every q, k **and** v head of the tile, reshaped to `(tile * (q_head_num + 2*kv_head_num), HEAD_DIM)`;
- Q, K and V are then cut out with three `extract_slice` calls at head offsets `0`, `q_head_num` and `q_head_num + kv_head_num`. Q and K apply their weights and RoPE; V has neither, so it is a cast and a store that reuses the K output index and mask.

This is valid because Gemma4's `v_norm` is the same per-head RMSNorm with the same `eps` and no learnable scale; only the weight application moves after the shared reduction. The kernel keeps everything else from `split_qkv_rmsnorm_rope`: the 1-D grid over vector cores, the batched UB tiling, the per-tile cos/sin gather shared by all heads, and partial-RoPE support. The UB tiling factor grows by `4 * kv_hidden_size` to account for the V columns now living in the tile.

**Fusion pass.** `QKVNormRopeFusionPattern` in `qknorm_rope_fusion_pass.py` matches the unfused chain (qkv split, per-head `npu_rms_norm` on q and k, `npu_rotary_embedding`, per-head `npu_rms_norm` on v) and replaces it with the new kernel.

- **One pattern per attention shape.** Gemma4 alternates sliding layers (`head_dim` 256) and full attention layers (`head_dim` 512, fewer KV heads), and `register_replacement` bakes the split sizes and head counts into the traced pattern. The pass therefore registers the pattern once per distinct `(head_dim, num_heads, num_kv_heads)` among the model's attention layers, the same approach as vLLM's own `qk_norm_rope_fusion` pass.
- **Dedup key.** `BasePattern` gains a `pattern_key()` method, which this pattern extends with its shape. Without it, the second shape's registration would be silently skipped. Existing patterns keep their keys unchanged.
- **Rejecting other shapes.** The matcher treats split sizes as wildcards and rejects a graph of another shape by re-tracing the pattern against it. A size mismatch makes `split` raise `ValueError`, which the pattern converts to the `RuntimeError` the matcher treats as "no match", as vLLM's `qk_norm_rope_fusion` does.
- The existing q/k-only patterns are unchanged and keep their `head_dim == 128` guard, so they cannot claim the q/k half of a Gemma4 layer and leave its v norm unfused.
- The replacement applies no v weight. Every `v_norm` in upstream vLLM today is weight-less; a model with a learnable v norm would need the kernel extended first.

**Proportional RoPE.** Full attention layers use `Gemma4RotaryEmbedding`, which implements proportional RoPE by zero-padding `inv_freq` and passing `rotary_dim=head_size` to the base class. Its cos/sin cache is therefore an ordinary full-width cache whose non-rotated pairs hold cos=1 and sin=0, and the kernel needs no layer-type knowledge. Upstream `Gemma4RotaryEmbedding` had no Ascend override, so these layers ran the PyTorch `rotate_half` implementation, which the pattern cannot match. This PR registers `AscendGemma4RotaryEmbedding`, which keeps Gemma4's cos/sin cache and runs the NPU rotary kernel (`npu_rotary_embedding`), as sliding layers already do.

**When a layer fuses.** The pattern is registered when:

- the model dtype is bfloat16 and Triton is available;
- the hardware profile supports the new `HardwareCapability.GRAPH_QKV_NORM_ROPE_FUSION` (Atlas A2/A3). Ascend 950 routes `split_qkv_rmsnorm_rope` to a SIMT kernel and has no SIMT variant of this operator yet, so it keeps the unfused chain;
- one token's tile fits a vector core's unified buffer. For gemma-4-31B, full attention layers need tensor parallel size 4 or more; below that they stay unfused and the pass logs it once.

Layers that cannot match stay unfused without any check: KV-shared layers have no k/v norm, and a norm bias is applied as a separate add.

### Does this PR introduce _any_ user-facing change?

No API change. In graph mode (the default), Gemma4 on Atlas A2/A3 uses the fused pre-attention path automatically. The existing `fuse_qknorm_rope` option in `ascend_compilation_config` turns it off, together with the existing q/k fusion. With `enforce_eager`, no fusion pass runs and Gemma4 keeps the unfused chain.

Full attention layers now run RoPE on the NPU rotary kernel instead of the PyTorch implementation, including when they stay unfused.

### How was this patch tested?

Tested on 910B1, TP=4, dtype bfloat16 with gemma4-31b-it.

One thing that shapes the design: Gemma4 has two attention shapes. Sliding layers use `head_dim` 256 with 16 KV heads; full attention layers use `head_dim` 512 with 4 KV heads (`global_head_dim` / `num_global_key_value_heads`, resolved per layer by `gemma4_layer_config`). The cos/sin cache width differs as well, 256 vs 512.

### Plan

Add one new pattern class to `qknorm_rope_fusion_pass.py` rather than a new file, matching how `norm_quant_fusion_pass.py` groups its patterns, and register it from a second block that keeps its own conditions:

```python
# existing block unchanged: base patterns, still registered only for head_size == 128

# new block: V-norm variant, one registration per attention shape
eps = vllm_config.model_config.hf_text_config.rms_norm_eps
for head_dim, num_heads, num_kv_heads in sorted(
    {(l.head_size, l.num_heads, l.num_kv_heads) for l in attn_layers.values()}
):
    if not qkv_rmsnorm_rope_vnorm_fits_ub(
        q_hidden_size=num_heads * head_dim,
        kv_hidden_size=num_kv_heads * head_dim,
        head_dim=head_dim,
        rope_dim=head_dim,
    ):
        continue
    QKVNormRopeFusionPattern(
        vllm_config, head_dim, num_heads, num_kv_heads, eps
    ).register(self.pattern_match_passes)
```

`rope_dim == head_dim` for both layer types, because `Gemma4RotaryEmbedding` passes `rotary_dim=head_size` to the base class, so the cos/sin cache is full-width in both cases. The new pattern derives it locally and `get_rope_dim()` stays untouched. The UB check is the same one the current patch uses, so full-attention layers still fall back below TP4.

### Registering per shape

Both shapes need their own registration, for the same reason the pass already loops over `eps`: `register_replacement` traces the pattern once and the constants become literals in the matched graph. Sliding layers emit `split_with_sizes(qkv, [2048, 1024, 1024], -1)`, full attention layers emit `[4096, 512, 512]`, so one registration cannot cover both.

That runs into the dedup key in `BasePattern.register`:

```python
# base_pattern.py:43
pattern_id = f"{self.__class__.__name__}_{self.eps}"
if pattern_id in _registered_patterns:
    return
```

It includes `eps` because `eps` varies between registrations of the same class. It omits shape only because no model has needed two shapes until now, so the second registration would silently return and only 50 of 60 layers would fuse, with no error.

I'd add a small seam so subclasses can widen that identity, leaving the dedup logic itself untouched:

```diff
 class BasePattern(ABC):
+    def pattern_key(self) -> str:
+        """Identity for dedup. Subclasses registered per shape widen this."""
+        return f"{self.__class__.__name__}_{self.eps}"
+
     def register(self, pm_pass: PatternMatcherPass) -> None:
-        pattern_id = f"{self.__class__.__name__}_{self.eps}"
+        pattern_id = self.pattern_key()
         if pattern_id in _registered_patterns:
             return
         ...
         _registered_patterns.add(pattern_id)
```

The new pattern then extends the base key with the constants that get baked into its traced graph:

```python
class QKVNormRopeFusionPattern(BasePattern):
    def pattern_key(self) -> str:
        return (
            f"{super().pattern_key()}"
            f"_hd{self.head_dim}_nh{self.num_heads}"
            f"_nkv{self.num_kv_heads}_rd{self.rope_dim}"
        )
```

On gemma-4-31B at TP=4 that yields two distinct keys, so both shapes register:

```
QKVNormRopeFusionPattern_1e-06_hd256_nh8_nkv4_rd256
QKVNormRopeFusionPattern_1e-06_hd512_nh8_nkv1_rd512
```

Three additive lines, and both existing patterns keep byte-identical keys. If you'd rather not touch `base_pattern.py` at all, I can generate a per-shape subclass inside the pass file instead, just let me know which you prefer.

### Leaving the head_size guard alone

I'd keep `head_size != 128` on the existing block as it is. If I relax it, the existing `QKNormRopeFusionPattern` also becomes eligible for Gemma4, and since its pattern is a prefix of the V-norm one it could match first and leave `v_norm` unfused. Giving the new pattern its own block avoids that and changes nothing for existing models. Also, I am not sure what effect it would have to relax that restriction.

`patch_gemma4.py` and its registry entry then go away. KV-shared layers need no special handling either, since they simply won't match the pattern.
