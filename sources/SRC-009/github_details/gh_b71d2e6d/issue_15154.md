# [Issue #15154] [Performance]: AscendStore wait_for_save significantly increases request-tail latency

source: https://github.com/vllm-project/vllm-ascend/issues/15154
state: closed | updated: 2026-09-22T06:17:53Z
labels: triaged

## 正文

### Proposal to improve performance

Reduce the request-tail latency exposed by `AscendStoreConnector`'s synchronous `wait_for_save` path while preserving the required KV-cache lifecycle ordering.

The current flow records an NPU event, submits the save request to the sending thread, and then blocks on the sending queue:

```text
record NPU event
  -> add save request
  -> request_queue.join()
  -> wait_for_save returns
```

The correctness invariant must remain:

```text
NPU KV write completes -> backend put completes -> save is reported complete -> KV block may be recycled
```

This issue does not propose directly removing the NPU event fence or the completion barrier.

### Report of performance regression

The issue was observed with the following workload:

```text
Model: DeepSeek V4 Flash
Topology: PP=4, TP=2 (8 worker ranks)
KV connector: MultiConnector with AscendStore and MooncakeConnectorV1
Version: vLLM-Ascend 0.26.0-based build
```

For the first request with KVPool enabled, `wait_for_save` took approximately:

```text
rank0-rank5: 617-679 ms per rank
rank6-rank7: 373-400 ms per rank
```

The PP0 save-path profile was dominated by waiting for the NPU event and host-side preparation, while the actual backend put was relatively small:

| Save-path component | Captured time |
| --- | ---: |
| NPU event synchronization | about 401 ms |
| Token/key preparation | about 106 ms |
| Store-mask processing | about 12 ms |
| Backend exists | about 9 ms |
| Backend put | about 29 ms |

On a repeated request served by the same process, the request hit the local HBM prefix cache and performed no backend get or put, but each rank still spent about `42-53 ms` in `wait_for_save` before determining that no put was required.

Therefore, the measured request latency is not dominated by the Mooncake `put` call itself. A substantial save tail remains synchronously exposed to request execution.

Related PR: #15150 appears to target this path by preparing saves earlier and pipelining backend puts. The profiling above can be used as an NPU end-to-end baseline for validating that change.

Expected validation before considering the issue resolved:

1. `wait_for_save` latency and end-to-end request latency are both reduced on Ascend hardware.
2. Backend keys and saved KV data remain identical.
3. No backend key becomes visible before its NPU KV write is complete.
4. KV blocks remain protected from recycling until the matching save completes.
5. Repeated requests that require no put no longer expose the same request-tail wait.

### Misc discussion on performance

The first-request measurement is a cold KVPool save. The repeated request is a local HBM prefix-cache hit, not an external KVPool load.

### zmc1997 · 2026-09-08

Progress update: #15636 is the proposed solution for this issue. It removes the same-step `request_queue.join()` from `wait_for_save()` and moves synchronization to the next step before KV cache blocks can be reused, preserving the required KV-cache lifecycle ordering while taking the save wait off the current request tail. It also replaces the full `SchedulerOutput` deepcopy on non-last PP ranks with targeted `dataclasses.replace`. Existing AscendStore tests pass (`124 passed, 41 subtests passed`). The remaining work is PR review/merge and Ascend hardware validation against the performance and correctness criteria listed in this issue.
