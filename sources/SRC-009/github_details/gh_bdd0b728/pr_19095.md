## Description

`cpp/tensorrt_llm/deep_ep/CMakeLists.txt` classifies each entry of `CMAKE_CUDA_ARCHITECTURES` and re-emits it for DeepEP. The comment directly above the branch states the requirement:

```cmake
# The FP4-related conversion instructions in DeepEP require SM100a, SM110a,
# or SM120a.
if(${CUDA_ARCH_MAJOR} EQUAL 10 AND ${CUDA_ARCH_MINOR} EQUAL 0)
```

The first branch requires `CUDA_ARCH_MINOR EQUAL 0`, so it only matches `100`. The `elseif` also requires `CUDA_ARCH_MINOR EQUAL 0`, so it only matches `110`, `120`, and later `x00` architectures. Every other member of the 10x family therefore falls through to the final `else` branch and is emitted with no suffix at all.

The regex does not capture the suffix either — `[af]?` sits outside the capture groups — so an incoming `103a-real` or `107f-real` loses its suffix on the way through.

Observed with an unmodified checkout of `main` (a76e0b2b):

| `CMAKE_CUDA_ARCHITECTURES` entry | emitted for DeepEP | |
|---|---|---|
| `90a-real`  | `90-real`   | |
| `100f-real` | `100f-real` | matches the comment |
| `103a-real` | `103-real`  | suffix dropped |
| `107f-real` | `107-real`  | suffix dropped |
| `110f-real` | `110a-real` | matches the comment |
| `120f-real` | `120a-real` | matches the comment |

`103` and `107` are the two 10x architectures currently reachable through `cuda_configuration.cmake`, and both end up with a bare target while their siblings do not.

This PR drops the `CUDA_ARCH_MINOR EQUAL 0` condition from the first branch so that the whole 10x major is routed to the existing `100` handling. That matches the stated intent in #17336 that `100f` kernels are meant to cover the whole `10x` family:

> we want `100f` kernels to cover the whole `10x` architectures to reduce build time and binary size

Only `103` and `107` change. `90`, `100`, `110` and `120` are unaffected.

Note on older CMake: when `CMAKE_VERSION < 3.31` the existing fallback emits `100a` and `103a` because family targets cannot be expressed there. That limitation is unchanged by this PR; `107` simply follows the same path `100` already takes instead of getting a bare target.

## Test Coverage

The branch logic was extracted verbatim into a standalone script and executed with `cmake -P` against both the current and the proposed condition, over the architecture strings `cuda_configuration.cmake` can produce. The table above is that output; with the change, `103a-real` and `107f-real` produce the same result as `100f-real`, and every other input is byte-identical to current behavior.

A full `build_wheel.py` configure with `-a "90-real;100-real;103-real;107-real"` was also run on the unmodified tree to capture the current `deep_ep DEEP_EP_CUDA_ARCHITECTURES:` line, which is what surfaced the bare `107-real` entry.

I do not have Rubin hardware, so this PR makes no claim about runtime performance on SM107. It only restores the suffix that the surrounding comment requires.
