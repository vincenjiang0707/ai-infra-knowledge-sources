## Description

`enable_tokenization_cache` (#18389) currently has no effect on MiniMax-M3, and nothing warns about it. `create_input_processor` passes the flag only to `DefaultInputProcessor`. Every MiniMax-M3 checkpoint declares `MiniMaxM3SparseForConditionalGeneration` / `minimax_m3_vl`, so it gets `MiniMaxM3VLInputProcessor`, whose `call_with_text_prompt` tokenizes each full prompt through the HF processor on every turn. This PR connects the cache to that processor for text-only prompts.

- `registry.py`: `create_input_processor` forwards `enable_tokenization_cache` to model-specific processors that set `supports_tokenization_cache`. It is opt-in because the other multimodal processors pass unknown kwargs on to `object.__init__` and would raise `TypeError`.
- `modeling_minimaxm3_vl.py`: `MiniMaxM3VLInputProcessor` opts in, builds the cache on the HF processor's own tokenizer, and uses it in the text-only branch. Requests with images or videos are unchanged. The per-request change is one `is not None` check.

**Why the ids are identical.** For a text-only prompt, the HF `MiniMaxVLProcessor` only calls its tokenizer, with `add_special_tokens=True`, the tokenizer default. The cache tokenizes with `add_special_tokens=False`. The two agree exactly when the tokenizer adds no special tokens. The MiniMax-M3 tokenizer adds none (`post_processor: null`), and the constructor checks `num_special_tokens_to_add() == 0`; otherwise it warns and leaves the cache off. On main, the M3 processor path ignores `add_special_tokens` and `truncate_prompt_tokens`, so the cache does not gate on them. It returns exactly what the processor would, and `/v1/completions` benefits too.

### How to use

```yaml
# trtllm-serve --config
enable_tokenization_cache: true
trust_remote_code: true
```

### Measured effect

**Input processor, CPU** (real `nvidia/MiniMax-M3-NVFP4` checkpoint). This PR's two files were overlaid on the `1.3.0rc28.dev202609220000` nightly, whose `registry.py`, `prefix_token_cache.py` and `modeling_minimaxm3_vl.py` are byte-identical to main. The input processor was built with `create_input_processor(..., enable_tokenization_cache=True)`, as `LLM` does. The workload was 8 growing agentic turns rendered with the M3 chat template (8k→64k tokens):

| | processor path (main today) | with this PR |

| `PrefixTokenCache` created with the flag on | 0 | 1 |
| ids vs processor path (chat and completions params) | n/a | identical, 8/8 turns each |

| per-request tokenization, turn 1→8 (chat) | 22→164 ms | 15→20 ms |

**Serving, B300.** The same hook on the `feat/m3_with_msa` side branch (#19373: MiniMax-M3 NVFP4, InferenceX AgentX recipe, same-server A/B with the cache toggled per arm):

## Test Coverage

- New `tests/unittest/_torch/models/test_minimax_m3_vl_prefix_token_cache.py` (CPU-only, `pytest.mark.cpu_only`, registered in `l0_cpu.yml`). It builds the M3 processor through `create_input_processor`, as `LLM` does, with a stub tokenizer and HF processor, and checks:
  - text-only prompts hit the cache, with ids equal to the processor path, and never reach the HF processor;
  - the cache is bypassed when disabled;
  - a tokenizer that adds special tokens disables it;
  - image requests bypass it;
  - other input processors do not receive the flag.

  With this PR all 5 cases pass, also under `-m cpu_only`. On main without it, 4 of 5 fail. The tests also fail if M3's `supports_tokenization_cache` is removed, or if the cache is built on the LLM tokenizer instead of the HF processor's.
- Regression on the same image, with this PR: `tests/unittest/inputs/test_prefix_token_cache.py`, `tests/unittest/inputs/test_multimodal_input_processor.py` and `tests/unittest/_torch/models/test_minimax_m3_vl.py` give 71 passed and 5 skipped. The only failures are the two `test_real_checkpoint_processor_*` cases, which need `$LLM_MODELS_ROOT/MiniMax-M3` and fail the same way without this PR.
