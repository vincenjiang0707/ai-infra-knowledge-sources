### Reproduction

When a tool parser's `has_tool_call(text)` is true but it extracts zero calls, the request returns
200 with an empty `tool_calls` array. From the client's perspective that is indistinguishable from a
model that chose not to call a tool, and the call is silently lost.

Some parsers do log something — `Qwen3ToolParser.detect_and_parse()` reports a JSON decode failure,
for example — but not all do, and none of those messages name the configured parser or point at
`--tool_parser`.

### Expected behavior

A tool call the parser could not extract is surfaced in the logs with enough context to diagnose it.

### actual behavior

The request returns 200 with an empty tool_calls array. Some parsers log a decode failure, but none name the configured parser or point at --tool_parser, so the call is lost with no actionable signal.

### additional notes

Emit one `logger.warning` on that path in the Chat Completions and Responses handlers, naming the
configured parser and listing the plausible causes: parser/template mismatch, malformed or truncated
output, an empty tool block, or arguments the parser rejected.

Log-only; no API, response-shape, or parsing change. Non-streaming path only, where the full text is
available to test.

**Questions for maintainers**

1. Is `warning` the right level, or would you prefer `debug` or an existing verbosity gate?
2. Would you rather this lived in a shared helper than in both handlers?

Per CONTRIBUTING.md this Issue Request precedes the patch, which is ready and applies cleanly to `main` @ `fbda11f5`.
