## Description

Fixes [NVBug 6702264](https://nvbugspro.nvidia.com/bug/6702264).

Allow the offload manager to pack non-overlapping dense tensors such as Wan VAE
`channels_last_3d` weights. Tensor bytes are copied in physical storage order so
the original strides and values are preserved when CPU and GPU views are rebound.
Overlapping and non-dense layouts remain unsupported.

### karljang · 2026-09-07 · APPROVED

LGTM. The three pieces line up:

- `_is_non_overlapping_and_dense` is the standard predicate (sort `(stride, size)`, skip size<=1 dims, require the recurrence `1, n0, n0*n1, ...`). It admits any dense permutation and still rejects `expand`-style overlap and strided gaps. I hand-checked it against Conv3d weights with size-1 kernel dims, e.g. `(96, 96, 1, 3, 3)` -> strides `(864, 1, 864, 288, 96)`, where the size-1 dim's stride is correctly ignored.
- `as_strided((numel,), (1,))` copies the dense span from the tensor's own `storage_offset` (`as_strided` inherits it when `storage_offset=None`), which is exactly `spec.nbytes`. This is the real fix: `reshape(-1)` materialized a copy in *logical* order, which then got reinterpreted with the physical stride at rebind time.
- `_make_views` restores `spec.stride` at the packed offset, and `stage()` is a raw byte copy of the whole stage buffer, so the layout survives the GPU transfer too.

Aliasing still behaves: two permuted views of one storage copy identical raw bytes, and each is rebound with its own stride.

One minor, non-blocking comment inline about the untested rejection branch.

Two notes:

1. The auto-generated summary in the description says "No `tests/integration/test_lists/` coverage entry was identified. Verdict: needs follow-up." That looks incorrect - `tests/integration/test_lists/test-db/l0_b200.yml:286` lists the whole file `unittest/_torch/visual_gen/test_offloading.py`, so `test_offload_preserves_channels_last_3d_layout` is collected in l0_b200. No follow-up needed there.
2. Nit on the new docstring: the tensor densely covers a contiguous span starting at its `storage_offset`, not "its storage" - a slice of a larger allocation passes the check, and should.

Disclosure: I reviewed by reading `as_strided`/`narrow`/`view` semantics and hand-evaluating the stride recurrence; I did not execute the new test locally.
