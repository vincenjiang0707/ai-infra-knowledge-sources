# [Issue #17095] [Bug] DSpark: disaggregated gen-only benchmark deadlocks under attention-DP with asymmetric (gen-only) speculative decoding

source: https://github.com/NVIDIA/TensorRT-LLM/issues/17095
state: open | updated: 2026-09-19T02:35:50Z
labels: Speculative Decoding, Disaggregated serving

## 正文

## Description

In disaggregated serving (1 ctx + 1 gen) with **attention-DP** on the generation server and **asymmetric speculative decoding** — `speculative_config` present only on the GEN worker (first-token draft produced on GEN; the CTX runs no draft) — the gen-only benchmark **deadlocks** once `draft_len >= 3`. The GEN admits ~1 request, then the PyExecutor `HangDetector` fires after 300 s -> `MPI_Abort` (exit 137). `draft_len` 1-2 complete normally.

Observed with the DSpark block speculative-decoding backend, but the deadlock is in generic attention-DP + disagg gen-only code paths. The **symmetric** config (`speculative_config` on both the ctx and gen workers) works correctly — only the **asymmetric** (gen-only draft) config deadlocks.

## Root cause (from investigation)

Under attention-DP each rank owns its own requests. The serial CTX prefill (ctx `max_batch=1`) delivers transferred requests to different GEN ranks on different iterations, and in the asymmetric config the GEN runs a per-request re-context/seed forward (GEN iter-log shows `num_ctx_requests=1, num_ctx_tokens=128`). So per-rank batches diverge — some ranks doing a context/seed forward, some decoding, some idle. Any per-iteration attention-DP collective then receives mismatched shapes and deadlocks:

1. First it hangs at the gen-only-benchmark fill-gate allgather — `_sync_gen_only_benchmark_has_insufficient_kv` -> `_allgather_model_parallel_status` (`tp_allgather`) in `py_executor.py`. Unlike its sibling `_is_benchmark_disagg_fill_complete` (explicitly rank-safe — every rank always enters the collective, per its own comment), this one returns early per-rank on a local flag (`_benchmark_fill_phase_active`) and can diverge.
2. With the fill gate disabled (`TLLM_BENCHMARK_REQ_QUEUES_SIZE=0`), the hang moves to `tp_allgather(scheduled_batch.batch_size)`, which is gated on `enable_attention_dp` (the `else` branch has no collective) — confirming the fault is generic attention-DP per-rank divergence, not the fill gate specifically.

Confirmed **not** caused by: `tokens_per_block`, dep width (dep4 hangs too), `max_num_tokens`, the rolling-window slot handling, or the benchmark client. Symmetric spec (`speculative_config` on both ctx+gen) does not diverge — requests arrive decode-ready and ranks stay in lockstep.

## Steps to reproduce

- Disaggregated 1 ctx + 1 gen, gen-only **burst** benchmark (all requests submitted up front).
- Generation server: attention-DP (e.g. `tp8`, `enable_attention_dp=true`) + `speculative_config` on the GEN worker **only** (asymmetric / first-token-draft offload), `draft_len >= 3`.
- Result: GEN admits ~1 request, then 300 s HangDetector -> MPI_Abort.

## Suggested fix direction

- Make the per-rank request mix rank-consistent under attention-DP for asymmetric spec-decode, or make the affected collectives rank-safe (mirror `_is_benchmark_disagg_fill_complete`: every model-parallel rank enters/skips the collective together).
- A continuous/rate-based client (instead of a burst gen-only benchmark) reduces the per-rank skew as a workaround.

### 0z5a · 2026-09-19

Reproduction on different hardware, with the wedge stack localized. The reported `HangDetector` → `MPI_Abort` → 137 signature reproduces here.

### Setup

3× L20 (sm_89). DSpark is Blackwell-only (`dspark_attention_custom_op.py:70-71`), so the GEN-only speculative config uses `NGram`:

| Tier | GPUs | Config |
| --- | --- | --- |
| CTX | 1× L20, `tp_size=1` | `cache_transceiver_config.backend: NIXL`; `speculative_config` deliberately absent |
| GEN | 2× L20, `tp_size=2` + `enable_attention_dp` | NIXL; `speculative_config: {decoding_type: NGram, max_draft_len: 4, max_matching_ngram_size: 4, is_keep_all: true}` |
| Router | — | `schedule_style: context_first` |

GEN worker: `TLLM_BENCHMARK_REQ_QUEUES_SIZE=64`, `TRTLLM_DISABLE_KV_CACHE_TRANSFER_OVERLAP=1`. Client: 64 prompts, isl=osl=128, `--max-concurrency 64 --request-rate inf`, `--no-test-input`. Both workers log `Using KvCacheTransceiverV2`.

### Signature

With the HangDetector at its upstream default (300 s):

```
[RANK 1] Hang detected after 300 seconds.
[RANK 1] Hang detected on rank 1 in PyExecutor; hard-killing and propagating to peer ranks.
[RANK 1] HangDetector: propagating hard-kill to all ranks via MPI_Abort.
[RANK 0] Hang detected after 300 seconds.
[RANK 0] Hang detected on rank 0 in PyExecutor; hard-killing and propagating to peer ranks.
[RANK 0] HangDetector: propagating hard-kill to all ranks via MPI_Abort.
Rank1 MGMN worker node exit code: 137
```

### Where it wedges

`py-spy` on both GEN ranks at the moment the executor stops iterating — identical on both:

```
Thread-8 (_event_loop_wrapper)  [active]
  synchronize (torch/cuda/streams.py:254)
  synchronize (tensorrt_llm/_torch/pyexecutor/sampler/sampler_features.py:570)
  update_requests (tensorrt_llm/_torch/pyexecutor/sampler/sampler.py:1484)
  _update_requests (tensorrt_llm/_torch/pyexecutor/py_executor.py:7683)
  _executor_loop (tensorrt_llm/_torch/pyexecutor/py_executor.py:4445)
```

`sampler_features.py:570` is `SamplerEvent.synchronize()` → `self.cuda_event.synchronize()`. Both GEN GPUs sit at 100% utilisation while the executor logs no further iteration at all, i.e. a CUDA event that never completes. (gdb only yields C frames here — `cuEventSynchronize` under `THCPEvent_synchronize` — because the interpreter has no Python debug extension; py-spy is what gives the frames above.) The CTX rank is idle in `queue.get()`.

Timeline: the fill gate opens, ~120–150 iterations (~4 s) of generation, then total silence for the full 300 s until the HangDetector fires. 58 of the 64 requests had completed by then.

### It is not the fill gate

With `TLLM_BENCHMARK_REQ_QUEUES_SIZE=0` — the gate never armed, zero `fill complete` lines in the worker log — the identical wedge occurs (iteration 116, GEN GPUs at 100%, CTX idle). It also reproduces with `TRTLLM_GPU_KEEPALIVE=0`, so the keepalive is not involved either.

### Repro note: the warm-up request hides the deadlock

`benchmark_serving.py:322-347` sends **one** warm-up prompt before the burst (`no_test_input=False` is the default). With the gate armed at 64 the GEN worker holds that request until 64 have been fetched, and the client blocks on the warm-up response *before* submitting the burst — so exactly one `POST /v1/completions` ever reaches the router, `num_fetch_requests` stays at 1, and the run looks like "the fill gate never opens". `--no-test-input` is what gets past that and exposes the deadlock above. Worth knowing for anyone trying to reproduce this: without it, the visible failure is a client-side deadlock, not this one.

### Result

`result.json`: `completed: 58 / 64`, `total_output_tokens: 7424`, `mean_ttft_ms: 5521`, `mean_e2el_ms: 7520`; client rc=0 once the kill dropped the last 6 connections.

This run had the #19436 fill-gate vote fix applied. That fix is orthogonal: it removes a rank-divergence in the gate's own gather, and by the control above the wedge is present with the gate disabled entirely.
