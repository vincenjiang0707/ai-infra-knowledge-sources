# [Issue #17926] KvCacheManagerV2 segfault on ~256k prompts with Nemotron-3-Ultra when max_seq_len=1M and avg_seq_len unset

source: https://github.com/NVIDIA/TensorRT-LLM/issues/17926
state: closed | updated: 2026-09-15T05:45:33Z
labels: KV-Cache Management, Pytorch

## 正文

## Summary

Serving `nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-NVFP4` with `trtllm-serve`, `TLLM_ALLOW_LONG_MAX_MODEL_LEN=1`, and `--max_seq_len 1048576` **segfaults inside `KvCacheManagerV2`** on a ~256k-token mid-document needle-in-a-haystack request when `kv_cache_config.avg_seq_len` is **not** set.

With the same setup plus `avg_seq_len: 9000`, the same server successfully completes **800k-token** mid-needle retrieval (`ORANGE-MANGO-42`).

This makes the documented long-context Ultra path unreliable: HF / deployment docs say to set `TLLM_ALLOW_LONG_MAX_MODEL_LEN=1` and `--max_seq_len <seq_len>`, but do not require `avg_seq_len`. Without it, TRT-LLM warns and falls back to `max_seq_len / 2` (= 524288), then crashes.

## Environment

- Image: `nvcr.io/nvidia/tensorrt-llm/release:1.3.0rc25.dev2026081200`
- TensorRT-LLM: `1.3.0rc25.dev2026081200`
- Hardware: 4× NVIDIA B200 (TP=4, EP=4)
- Checkpoint: `nvidia/NVIDIA-Nemotron-3-Ultra-550B-A55B-NVFP4`
- Backend: PyTorch (`MambaHybridCacheManagerV2`)

## Workaround

Set an explicit workload-average sequence length, e.g.:

```yaml
kv_cache_config:
  avg_seq_len: 9000
  # ...rest unchanged...
```

With that single change, 256k and 800k mid-needle requests succeed on the same image/hardware.

## Expected

1. Documented 1M Ultra serving should not segfault when `avg_seq_len` is omitted (or should fail fast with a clear validation error instead of corrupting/killing the engine).
2. Ideally `avg_seq_len` fallback for hybrid V2 should not use `max_seq_len/2` when `max_seq_len` has been raised far above the native HF window via `TLLM_ALLOW_LONG_MAX_MODEL_LEN`.

## Notes

- Overlap scheduler was disabled in this repro (`disable_overlap_scheduler: true`) to isolate the KV-cache manager issue.
- MTP was not enabled.
- Tokenizer still logs `Token indices sequence length is longer than the specified maximum sequence length for this model (800053 > 262144)` even when the request succeeds; that may be a separate HF tokenizer `model_max_length` warning, but it did not prevent successful 800k generation once `avg_seq_len` was set.

### thorjohnsen · 2026-09-02

Thanks for the unusually good report — the repro is self-contained, and the observation that
`avg_seq_len: 9000` makes it go away turned out to be the key to the whole thing.

**Confirmed and root-caused.** Reproduced on 4×GB200 (same Blackwell family as your B200s) with
your exact config, prompt and flags, and traced with an instrumented build. It's a real bug in
KV cache manager v2, not a configuration error on your side.

## What's happening

`enable_block_reuse` keeps committed blocks in a radix tree so later requests can reuse their KV.
Separately, each SSM (Mamba) layer periodically snapshots its state into that tree.

The crash is a re-entrancy: committing a block can allocate a page for an SSM snapshot, that
allocation can evict to make room, and eviction runs
`Block::clearStaleBlocksAfterPageUnlink()`, which walks up the tree detaching blocks that have no
children and no page for that lifecycle. On your 256k prompt that walk detaches **~2,440 blocks
in one go** — including blocks belonging to the request that is *currently mid-commit*.

That's a legal state on its own. `kv_cache_manager_v2/AGENTS.md` documents it:

> Orphan blocks may retain pages while a live `KvCache` still references them

The bug is that the commit path never implemented its side of that contract. `KvCache` caches a
`SharedPtr<Block>` for the previous ordinal and hands it to `addOrGetExistingBlock()` on the next
loop iteration, assuming it's still attached. When it isn't, `Block::tokensPerBlock()`
dereferences the null `prev` that the detach deliberately installed — which is exactly your stack:

```
Block::tokensPerBlock() const
addOrGetExistingBlock(...)
```

The precondition is only checked under `TLLM_DEBUG_MODE=1`, so in a release build it's a raw
null dereference — which is why it presents as a segfault taking down all four ranks rather than
an error.

It's deterministic, not a race: identical on every rank, every run.

## Why `avg_seq_len` changes the outcome

`avg_seq_len` sizes the pools. Unset, it falls back to `max_seq_len / 2` = **524288** — and this
model's `max_position_embeddings` is **262144**, so the fallback claims your typical request is
*twice* the model's native context. That skews the split hard toward attention:

| | attention slots | SSM slots |
|---|---|---|
| `avg_seq_len` unset | 393,216 | **104** |
| `avg_seq_len: 9000` | 86,698 | **1,270** |

A 256k-token prompt needs roughly a thousand SSM snapshots. With 104 slots the pool evicts
continuously, which is what drives the re-entrant eviction above. With 1,270 it never needs to —
in that configuration not one link of the chain executes (0 detaches, 0 evictions on that path).

**So `avg_seq_len: 9000` is a sound workaround and I'd keep using it — but please treat it as
masking the bug, not fixing it.** It removes the *pressure* that triggers the defect; the defect
is still there. Any workload that pressures the SSM pool for other reasons can still reach it.
Notably, the pool never fails an allocation — it succeeds every time *by evicting* — so you get no
OOM warning before the segfault.

## Status

A fix is written and verified end to end on the same hardware: with `avg_seq_len` **unset**, your
256k request now returns `ORANGE-MANGO-42` on every run, against a stock control on the same node
that still dies with your stack on all four ranks. It makes the commit path honour the documented
contract — an orphaned prefix stops the sequence contributing to the reuse tree instead of
faulting — and makes the precondition an unconditional check, so the failure is catchable rather
than fatal. PR to follow shortly; I'll link it here.

Two honest caveats:

- The fix removes the crash but **not** the over-eager prune. An affected request keeps working
  but loses block reuse from the detach point on, which measured ~40% higher latency on the 256k
  request than the `avg_seq_len` workaround. Making eviction not detach blocks a live `KvCache`
  is a follow-up that needs a design decision from the KV-cache owners.
- **Your point about the docs is right and is being tracked separately.** The HF/deployment docs
  prescribe `TLLM_ALLOW_LONG_MAX_MODEL_LEN=1` and `--max_seq_len` but never mention
  `avg_seq_len`, which is load-bearing for hybrid models — and the `max_seq_len / 2` fallback is
  unsound when `max_seq_len` was inflated past the model's real context, as it is here. Both
  want fixing (cap the fallback at the native context length; put a floor under the SSM pool),
  but as a separate change from the crash fix.
