# [Issue #18849] [Bug] Hybrid-Mamba KV cache manager is constructed without vocab_size; the first multimodal request hard-kills every rank

source: https://github.com/NVIDIA/TensorRT-LLM/issues/18849
state: closed | updated: 2026-09-15T16:54:06Z
labels: KV-Cache Management, Pytorch, Multimodal

## 正文

### System Info

- TensorRT-LLM **v1.3.0rc25** (`nvcr.io/nvidia/tensorrt-llm/release:1.3.0rc25`), PyTorch backend. The same code is on `main` today.
- Model: **Qwen/Qwen3.8-27B** (`Qwen3_5ForConditionalGeneration`, hybrid Gated-DeltaNet + attention, i.e. the Qwen3-Next runtime).
- 2x H100-80GB, TP2, `kv_cache_config.enable_block_reuse: true`, `use_kv_cache_manager_v2: true`, MTP `max_draft_len: 3`, vision encoder enabled.
- Served with `trtllm-serve --backend pytorch --reasoning_parser qwen3_5 --tool_parser qwen3_coder`.

### Who can help?

Whoever owns the PyTorch-backend KV cache manager and the multimodal path.

### Reproduction (one request)

Text-only chat completions are fine indefinitely — we served roughly a million tokens without incident. Then send **one** chat completion whose message content contains an `image_url` part; a 128x96 base64 PNG is enough. The executor dies:

```
[E] [_torch][RANK 0] Error in event loop: gen_multimodal_cache_key_tokens():
    incompatible function arguments. The following argument types are supported:
    (id_offset: int, multi_modal_data_digest: bytes, num_tokens: int, token_offset: int = 0)
    Invoked with types: NoneType, bytes, int, kwargs = { token_offset: int }
[E] Executor loop crashed on this rank; hard-killing all 2 ranks in 10 s
-> MPI_ABORT -> container exit 137
```

The server is then unavailable for a full engine start-up, about 6 minutes for this model. In our deployment two pods behind a session-affinity router both died within two minutes, because the client retried onto the second pod.

### Expected behaviour

An image request either works, or fails as a 4xx for that request. It should not terminate the executor.

### Root cause

Two code sites:

1. `tensorrt_llm/_torch/pyexecutor/_util.py::_create_kv_cache_manager` passes `vocab_size=config.vocab_size` on the MLA branch and on the plain-attention branch **only**. The hybrid-Mamba branch (selected via `_mamba_conv_layout_kwargs(kv_cache_manager_cls, "qwen3_next")` for Qwen3-Next / Qwen3.5 / NemotronH) constructs `kv_cache_manager_cls(...)` without the argument.
2. `tensorrt_llm/_torch/pyexecutor/kv_cache_manager_v2.py::KVCacheManagerV2.__init__` declares `vocab_size: int = None` and stores it. It is read only when building multimodal cache keys (`_augment_tokens_with_mm_run_metadata` / `_augment_tokens_with_contiguous_mm_metadata`), which is why text traffic never notices and the first image is fatal.

### Workaround we are running

A `sitecustomize.py` on `PYTHONPATH` (imported by `site` on every MPI rank) installs an import hook that wraps `KVCacheManagerV2.__init__` and fills `vocab_size` when it is missing or `None`. No image change required.

Note for anyone tempted by a configuration fix: adding a top-level `vocab_size` to the checkpoint's `config.json` does **not** help, because that code path never reads the config. We verified this on a live deployment and it crashed identically.

With the workaround plus the vision encoder enabled, images work correctly: a 1920x1927 screenshot is read accurately on both pods (3,934 prompt tokens, about 9 s), an identical repeat reports `cached_tokens: 2048` so the multimodal cache-key path reuses blocks, and image + tool list + thinking returns a valid tool call. Cost of the encoder: weights 25.45 -> 25.88 GB per rank, KV blocks -4.3%, single-stream text decode -2.3%, text TTFT unchanged.

### Suggested fixes

1. Pass `vocab_size` on the hybrid-Mamba branch of `_create_kv_cache_manager`.
2. Resolve it as `getattr(config, "vocab_size", None)` or `getattr(getattr(config, "text_config", None), "vocab_size", None)`, because composite VLM configs (`Qwen3_5Config` with a nested `text_config`) have no top-level `vocab_size` either.
3. Fail the **request** rather than the executor when multimodal metadata cannot be built. Related, same deployment: with `disable_mm_encoder: true` an `image_url` request raises "Raw multimodal inputs require a local multimodal encoder" inside the event loop and is likewise fatal for all ranks, where a 4xx for that one request would be the right behaviour.

### dibyo10 · 2026-09-09

Your analysis was right on both code sites. #18970 fixes it.

Rather than adding the argument to each hybrid branch, I moved it into `manager_extra_kwargs`, which is already gated on `issubclass(kv_cache_manager_cls, KVCacheManagerV2)`. Every branch now gets it from one place, so a branch added later can't forget it the way these three did. It also resolves through a nested `text_config`, and `_augment_tokens_for_block_reuse` raises a named error now instead of handing `None` to the binding.

Fair warning: none of it has actually run. I don't have Hopper hardware, and the CI workflows need a maintainer to approve them before they'll even build. So if you get a chance to drop the `sitecustomize.py` hook and try the branch, that's the only real evidence anyone has that it works.

There's also something I couldn't settle by reading the code, and you're in a position to. On current `main`, `is_qwen3_5` matches only `Qwen3_5MoeForCausalLM` and `Qwen3_5ForCausalLM`. The VLM wrapper keeps the composite config on `model_engine.model.model_config`, and its top-level `architectures` stays `Qwen3_5ForConditionalGeneration` (`_normalize_qwen35_vl_config` only sets that field when it's absent, and `_mirror_text_subconfig_attrs` won't overwrite an attribute that already exists). Reading it that way, `is_qwen3_hybrid` should be False for your model, you'd have landed on the plain-attention branch, and that branch already passed `vocab_size`. Which contradicts your traceback, so I'm missing something.

You were on 1.3.0rc25 and I've been reading `main`, so the routing may simply have changed between them. Could you paste the top-level `architectures` and `model_type` from your checkpoint's `config.json`? If `is_qwen3_hybrid` genuinely is False for Qwen3.5-VL on `main`, that's a separate and much larger problem, because the model would be getting no Mamba state allocated at all.

One thing that PR does not do: your suggestion 3. I kept it to a single concern, so the `disable_mm_encoder: true` case still takes down the executor. That's split out as #18971.
