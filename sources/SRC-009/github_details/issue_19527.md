### Reproduction

```python
from tensorrt_llm import LLM, SamplingParams
from tensorrt_llm.llmapi import KvCacheConfig


def main():
    llm = LLM(
        model="Qwen/Qwen2.5-0.5B-Instruct",
        max_beam_width=32,
        max_batch_size=8,
        max_seq_len=1024,
        kv_cache_config=KvCacheConfig(max_tokens=8192, tokens_per_block=32),
    )
    sp = SamplingParams(max_tokens=64, n=32, best_of=32, use_beam_search=True)
    print(llm.generate(["Write a story about a lighthouse keeper."], sp))


if __name__ == "__main__":
    main()
```

The request itself only needs ~97 of the 256 KV blocks, but executor startup fails during CUDA graph warmup.

### Expected behavior

Startup succeeds, and the beam-search request completes.

### actual behavior

Executor initialization fails inside CUDA graph warmup:

```
File ".../_torch/pyexecutor/model_engine.py", line 2817, in _capture_generation_cuda_graphs
File ".../_torch/pyexecutor/model_engine.py", line 3369, in _create_cuda_graph_warmup_request
    max_seq_len_request = kv_cache_manager.add_dummy_requests(
File ".../_torch/pyexecutor/resource_manager.py", line 1355, in add_dummy_requests
RuntimeError: No free block found. This shouldn't happen! (.../cpp/tensorrt_llm/batch_manager/evictionPolicy.cpp:160)
```

### additional notes

**Root cause.** With beam search, the C++ block manager shares only the KV blocks fully covered by the prompt among beams. The partial last prompt block, and every block allocated by `add_token`, are allocated once per beam (`allocateBlock(sequence, /*shareAmongBeams=*/beamWidth == 1)`). The V1 `KVCacheManager` ignores this when it sizes the CUDA graph warmup requests:

1. `_create_cuda_graph_warmup_request` first adds `batch_size - 1` one-token dummy requests. Each one takes `beam_width` blocks: 7 × 32 = 224 of the 256 blocks in the repro above.
2. `get_num_available_tokens` then reports `free_blocks * tokens_per_block` = 32 × 32 = 1024 tokens, which assumes one block per 32 tokens.
3. The max-length dummy request is then added with 1023 tokens and beam width 32. That needs 31 shared blocks plus 32 per-beam tail blocks, 63 in total, but only 32 are free.

`add_dummy_requests` only checks `available_blocks < 1`, so it cannot catch this either.

Results of a sweep on the model above (`max_seq_len=1024`, `max_batch_size=8`, `tokens_per_block=32`):

| beam | `kv max_tokens` | result |
|---|---|---|
| 16 / 32 / 64 | default (large pool) | OK |
| 32 | 8192 | `No free block found` at startup |
| 32 | 16384 | OK |
| 64 | 16384 | `No free block found` at startup |
| 64 | 32768 | OK |

`KVCacheManagerV2` is not affected, since it only supports `max_beam_width == 1`.

I have a fix plus unit tests ready. Per the contribution guidelines, I'd like to submit a PR if the approach sounds good:
- make `get_num_available_tokens` beam-aware;
- have `add_dummy_requests` return `None` (its existing "skip" signal) instead of failing inside the block manager when beam-search dummies can't fit.
