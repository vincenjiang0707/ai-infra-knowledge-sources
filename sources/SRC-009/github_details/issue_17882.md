### Reproduction

This is an `LLM` API reproduction. The same failure is also reproducible through `trtllm-serve` when  concurrent requests use the same model and `MAX_UTILIZATION` scheduler policy.

```python

MODEL = "nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-NVFP4"

        "Describe this synthetic image. "
        + ("Use complete sentences. " * FILLER_REPETITIONS)
        + f"Request {request_id}."
    )
    prompt = tokenizer.apply_chat_template(
        [{
            "role": "user",
            "content": [
                {"type": "image"},
                {"type": "text", "text": text},
            ],
        }],
        tokenize=False,
        add_generation_prompt=True,
        enable_thinking=True,
        reasoning_budget=16384,
    )
    return {
        "prompt": prompt,
        "multi_modal_data": {"image": [image.copy()]},
    }


def main():
    tokenizer = AutoTokenizer.from_pretrained(MODEL, trust_remote_code=True)

    image = Image.new("RGB", (512, 512), "white")
    draw = ImageDraw.Draw(image)

    llm = LLM(
        model=MODEL,
        trust_remote_code=True,
        max_batch_size=NUM_REQUESTS,
        max_seq_len=8192,
        max_num_tokens=1024,

            enable_prefix_aware_scheduling=False,
        ),
    )

    llm.generate(
        [make_request(tokenizer, image, i) for i in range(NUM_REQUESTS)],
        SamplingParams(max_tokens=4096, min_tokens=4096, ignore_eos=True),
    )


if __name__ == "__main__":
```

### Expected behavior

When `MAX_UTILIZATION` pauses a multimodal request because the V2 KV cache is full, the request should resume and complete without losing the metadata required for the resumed context forward pass.

### actual behavior

After `MAX_UTILIZATION` pauses the multimodal requests, the resumed PyTorch forward path fails with `'modality_type'`. The caller of `LLM.generate` receives `RequestError: 'modality_type'`.

### additional notes

1. [`py_executor.py`](https://github.com/NVIDIA/TensorRT-LLM/blob/v1.3.0rc23/tensorrt_llm/_torch/pyexecutor/py_executor.py#L6351-L6357) calls `_strip_py_multimodal_data_post_prefill(request)` after multimodal prefill. That function calls `strip_mm_data_for_generation`.
2. [`multimodal.py`](https://github.com/NVIDIA/TensorRT-LLM/blob/v1.3.0rc23/tensorrt_llm/inputs/multimodal.py#L151-L167) clears the multimodal dictionary and retains only `mrope_config.mrope_position_deltas`. It therefore drops `modality_type` and the prepared multimodal embedding/layout metadata.
3. [`modeling_nemotron_nano.py`](https://github.com/NVIDIA/TensorRT-LLM/blob/v1.3.0rc23/tensorrt_llm/_torch/models/modeling_nemotron_nano.py#L3091-L3093) accesses `param.multimodal_data["modality_type"]` while building multimodal embeddings.

## 评论 (2)

### lathuthavarajah · 2026-08-24

Opened #18113 with a fix. Root cause confirmed as described: under the V1 MAX_UTILIZATION pause path, `py_multimodal_data` is released both post-prefill and inside the pause-terminate itself, so the replayed prefill has nothing to rebuild embeddings from. The PR retains the multimodal payload for pause replay in exactly that configuration (V1 + MAX_UTILIZATION) and leaves the default policy and the V2 KV cache manager release behavior unchanged.

### eopXD · 2026-09-15

In rc24 directs TRT-LLM to use the v2 kv cache manager. The bug report here uses rc23 and falls back to using the v1 kv cache manager.

I tried my build on top of the latest origin/main, which leverages the v2 kv cache manager. TRT-LLM runs fine with the user's provided configuration.

I need to mention that the `max_tokens=8192` configuration indicates a 416-token pool for KV cache and will stop the request from being admitted due to a too small KV cache budget indicated by that parameter. I simply deleted the specification and the the whole snippet is good.

Closing the bug.
