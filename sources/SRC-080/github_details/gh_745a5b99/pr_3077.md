# [PR #3077] MoE Linearization and Offloading Changes

source: https://github.com/vllm-project/llm-compressor/pull/3077
state: closed | updated: 2026-09-22T18:07:55Z
labels: ready, needs-rebase

## 正文

Move moe linearization and repacking (same operation but reversed) to be handled by the pipeline. Currently linearization is handled at load time, requiring an onload + offload operation. Repacking is not currently used in any pipelines, and is also added to pipelines. 

## Implementation

We add a `disable_offloading_controlled` context which takes in a subgraph, onloads everything, then offloads at the end. Note that we have to wrap the modules in `OnloadWrapper`'s in order to keep track of onloading/offloading. The modules themselves also get a pointer to their `OnloadWrapper`. This is because when we linearize or repack, we actually generate fully new modules, so we need to maintain a way to track the most recent module. 
 * Considering having the `OnloadWrapper` attached to the model, so that it's replace function handles in swapping modules and deleting references from any hashes *

We add flags `sequential_linearize_repack` (Linearize and/or repack each subgraph during calibration onload if `True`, linearize and/or repack before/after the whole model is calibrated for `False) and `repack_moe` (Whether or not to pack experts to 3d). 

Before calibration, we trace the whole model and build a hash for fast lookup for all moe modules -- packed or not packed. This is stored on the model as `model._moe_lookup`. Generated by `get_moe_linear_status`. 

This lookup is important because using model.get_submodules(name) traverses the whole model which is a taxing operation for large models. 

From here, we have functions as follows:
`linearize_moe_model`
`linearize_moe_subgraph`
`linearize_moe_layer`

and their corresponding repacking/reverse counterparts
`repack_moe_model`
`repack_moe_subgraph`
`repack_moe_layer`

The `*_model` functions are used with `sequential_linearize_repack=False`. They iterate over moe layers, onloading/offloading each layer individually (If you can't fit an entire moe layer on gpu at once, you're out of luck). The `*_subgraph` functions are assumed to be under a `disable_offloading_controlled` context. 

Some things to note:

Weird hard-to-read code such as:
```python
    linearized = [
        (moe_lookup[module], module)
        for module in subgraph_set
        if module in moe_lookup and isinstance(module, LinearExperts2D)
    ]

    for i in tqdm.tqdm(range(len(linearized)), desc="Repacking experts in subgraph"):
        repack_moe_layer(model, linearized[i][0], linearized[i][1])
```

Under these new contexts, since we want to constantly free up memory, we need to be careful with how we put out references. Iterating naively `for name, module in linearized` makes it such that linearized maintains a reference to the module. In the case that we are linearizing/repacking and the resulting new module is a new object, we want to free the old object. To my knowledge this can only be done when the python object is garbage collected. So here we make sure that the old module's reference is deleted by the end of its iteration. This is also why we need:

```python
        gc.collect()
        if torch.accelerator.is_available():
            torch.accelerator.empty_cache()
```

At the end of the new load context. We don't generate enough objects to force automatic garbage collection (at least for the tests I've run). The cache release might have a solution but I haven't been able to dig it up yet. Without that part it seems that we constantly have allocated but unused gpu memory.

## Code Review

This pull request introduces on-the-fly linearization of Mixture of Experts (MoE) layers during sequential calibration to optimize memory usage, while updating weight and bias copying logic in linear experts. Feedback on these changes highlights several critical issues: removing the post-load linearization fallback in `oneshot` entirely will break non-sequential pipelines; using `.copy_()` for transposed weights and biases will cause runtime crashes when loading on `meta` devices (where assigning `torch.nn.Parameter` with `.contiguous()` is required instead); checking transpose conditions on 1D biases is unnecessary; and checking list membership in `linearize_moe_layer` introduces an $O(M \times N)$ performance bottleneck that can be optimized to $O(M)$ by using a set.

### src/llmcompressor/entrypoints/oneshot.py (237-243)

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Removing the post-load linearization fallback entirely from `oneshot` will break MoE model support when using non-sequential pipelines (such as `basic` or `independent`). While sequential pipelines can now linearize on-the-fly to save memory, other pipelines still require the model to be linearized upfront.

We should keep this fallback specifically for non-sequential pipelines.

```suggestion
        if self.dataset_args.pipeline != "sequential" and len(get_non_linearized_moes(self.model)) > 0:
            logger.warning(
                "Detected an MoE model which has not been linearized. First load "
                "model 'with llmcompressor.modeling.moe.linearize.load_quantizable_moe'"
                " before passing to 'oneshot'. Falling back to post-load linearization."
            )
            linearize_moe(self.model)
```

### src/llmcompressor/modeling/moe/linear_experts.py (64-71)

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

In the `else` branch (when `experts.is_transposed` is True, such as in Llama4), the weights are copied using `.copy_()`. However, if the destination parameters are uninitialized or on the `meta` device (which is common when using `skip_weights_initialize` or meta-device loading), `.copy_()` will raise a `RuntimeError: Cannot copy out of meta tensor`.

To ensure consistency with the `if` branch and prevent runtime crashes, we should assign the weights as `torch.nn.Parameter` instead. Since the transposed weights are non-contiguous views, we should also call `.contiguous()` on them.

```suggestion
        else:
            gate_weight = experts.gate_up_proj[index, :, : self.intermediate_size].T
            up_weight = experts.gate_up_proj[index, :, self.intermediate_size :].T
            down_weight = experts.down_proj[index].T

            self.gate_proj.weight = torch.nn.Parameter(gate_weight.contiguous())
            self.up_proj.weight = torch.nn.Parameter(up_weight.contiguous())
            self.down_proj.weight = torch.nn.Parameter(down_weight.contiguous())
```

### src/llmcompressor/modeling/moe/linear_experts.py (79-86)

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

For biases, checking `if not experts.is_transposed` is unnecessary because biases are 1D vectors and do not have a transpose. Furthermore, using `.copy_()` in the `else` branch will fail if the destination parameters are on the `meta` device.

We can simplify this by always assigning the biases as `torch.nn.Parameter` regardless of `is_transposed`.

```python
            self.gate_proj.bias = torch.nn.Parameter(gate_bias)
            self.up_proj.bias = torch.nn.Parameter(up_bias)
            self.down_proj.bias = torch.nn.Parameter(down_bias)
```

### src/llmcompressor/modeling/moe/linearize.py (155-163)

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

Checking `module in subgraph_modules` (where `subgraph_modules` is a list) inside a list comprehension over all named modules of the model is an $O(M \times N)$ operation, where $M$ is the total number of modules in the model and $N$ is the number of modules in the subgraph. For large models, this can be slow.

Converting `subgraph_modules` to a `set` first optimizes this lookup to $O(M)$.

```suggestion
    subgraph_modules_set = set(subgraph_modules)
    non_linearized = [
        (name, module)
        for name, module in model.named_modules()
        if module in subgraph_modules_set
        and (
            isinstance(module, FusedExpertsProtocol)
            or LinearExperts2D.get_registration(module.__class__) is not None
        )
    ]
```
