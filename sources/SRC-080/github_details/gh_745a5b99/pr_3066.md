# [PR #3066] fix(dist): write back broadcast qparams to offload storage on non-src ranks

## 正文

## Summary

`broadcast_qparams_and_cleanup` calls `dist.broadcast` on module attributes such as `weight_scale`, `weight_zero_point`, and `weight_g_idx`. When these tensors are stored in `CPUCache` (the common case with sequential pipeline `auto_offload`), `getattr(module, name)` returns a **temporary onloaded GPU tensor** — a new allocation each call. `dist.broadcast` modifies that temporary in-place, but the underlying CPU storage is never updated — leaving non-source ranks with stale or uninitialised quantization parameters.

**Trigger conditions:** multi-GPU DDP GPTQ with sequential pipeline and `auto_offload=True`, typically used to parallelize activation collection over large calibration sets. The quantization completes silently with no exception; the corruption only appears when inspecting saved checkpoints.

This PR adds an explicit `update_offload_parameter` writeback for non-source ranks after `_wait_for_comms`, which correctly flushes the broadcast result back to CPUCache storage.

## Changes

- `src/llmcompressor/utils/dist.py`: collect `(module, name, param, broadcast_param)` for non-src-rank entries before issuing async broadcasts; after comms complete, copy back and call `update_offload_parameter` (+40/-2 lines)
- `tests/llmcompressor/utils/test_broadcast_qparams_writeback.py`: unit tests covering non-src writeback, src no-writeback, missing params, and multi-module cases
- `tests/llmcompressor/utils/test_cpucache_temporary_tensor.py` (new): 3 unit tests proving CPUCache returns a new temporary CUDA tensor per `getattr` call and that in-place modification is lost without writeback
- `tests/llmcompressor/utils/test_broadcast_qparams_ddp_integration.py` (new): 2-GPU integration test using real `dist.broadcast` + real CPUCache, demonstrating the bug (Phase A) and fix (Phase B) in a single distributed session

## Empirical validation

Controlled A/B on 8× L20, `Qwen3.5-122B-A10B`, N=5120, seq=6144:

|---|---|---|

### xesdiny · 2026-09-20

Thanks for the review, @HDCharles. You are right that `DistributedCPUCache` is the _intended_ class for distributed CPU offload — and it works correctly for dense models like LLaMA-3 8B. However, for large MoE models it is physically impractical, and that is the scenario this PR addresses.

### Why DistributedCPUCache is impractical for large MoE models

`DistributedCPUCache.offload()` creates one POSIX shared-memory file in `/dev/shm` per tensor and issues two collective ops per tensor. `/dev/shm` is `tmpfs` backed by physical RAM, so each file directly consumes physical RAM. For Qwen3.5-122B-A10B this means:

- 48 layers × 256 experts × 3 projections = **36,864 expert tensors** → 36,864 `/dev/shm` files
- 36,864 × 2 = **73,728 blocking collectives** during model load

**Empirical measurement (Qwen3.5-122B-A10B, L20×8, 768 GB total RAM):**

| | Before expert load | At RAM exhaustion (OOM) |
|---|---|---|
| `/dev/shm` used | 231 GB (non-expert modules) | 351 GB (+120 GB from ~22,000 expert files) |
| `/dev/shm` files | 1,680 | ~22,085 |
| Physical RAM available | ~498 GB | **~8 GB** ← effectively OOM |

Physical RAM is exhausted before all 36,864 expert tensors can be loaded — GPTQ calibration is never reached. The 231 GB of `/dev/shm` present _before_ expert loading comes from the non-expert modules (attention, shared_expert, gate layers) and is identical in both approaches.

**Why 35B works fine with either mode (Qwen3.5-35B-A3B, L20×8):**

| Mode | `/dev/shm` peak | RAM available (nadir) | Result |
|---|---|---|---|
| DistributedCPUCache | 135 GB (+67 GB expert shm) | 532 GB | Model loads, GPTQ runs |
| CPUCache (PR fix) | 68 GB (non-expert only) | 665 GB | SCALE_CHECK CLEAN |

For 35B, expert shm peaks at ~67 GB — well within available physical RAM — so `DistributedCPUCache` works fine. `CPUCache` is only needed when expert shm would exhaust available RAM.

### How CPUCache is selected

We patch `LinearExperts2D.from_experts_module` before calling `from_pretrained`. This is called _after_ the fused 3D expert tensors are already broadcast to all ranks, so `CPUCache.from_mapping` receives real tensors (not meta tensors) on every rank. The non-expert modules (attention, shared_expert, gate) continue to use `DistributedCPUCache` through the normal `cls_from_device` path — that 231 GB of `/dev/shm` is common to both approaches.

The full working example is in this PR at `examples/big_models_with_sequential_onloading/qwen3_5_moe_w4a16_distributed.py`.

### Summary

- `DistributedCPUCache` is correct for dense models and works as designed.
- For Qwen3.5-122B-A10B with 36,864 expert tensors, `DistributedCPUCache` exhausts physical RAM before model load completes (measured: /dev/shm grows to 351 GB, RAM drops to ~8 GB available). Smaller MoE models like 35B-A3B work fine with either mode.
- `CPUCache` is used for expert tensors as a deliberate workaround; each rank holds independent pinned CPU storage with zero `/dev/shm` overhead for experts.
- Without this PR, `broadcast_qparams_and_cleanup` broadcasts into a temporary GPU tensor that is GC'd before writeback, leaving non-source ranks with stale/NaN `weight_scale`.
- This PR fixes the writeback and limits it to modules with an independent `CPUCache` (excluding `DistributedCPUCache` and non-offloaded modules).

## Problem B — Broadcast writeback bug (the actual fix in this PR)

### Pre-fix: no writeback → stale zero in CPUCache → NaN

```
src rank (r0)                            non-src ranks (r1..r7)

module._parameters = CPUCache(...)       module._parameters = CPUCache(...)
  weight_scale → CPU storage (real)        weight_scale → CPU storage (zero-init)
         │                                        │
         ▼                                        ▼
getattr(module, "weight_scale")          getattr(module, "weight_scale")
  CPUCache.__getattr__()                   CPUCache.__getattr__()
  → onloads tensor to GPU                  → onloads tensor to GPU
  → returns temporary GPU tensor T₀        → returns temporary GPU tensor T₁ (all zeros)
         │                                        │
         └─── dist.broadcast(T₀, src=0) ─────────► T₁ filled in-place with real values
                                                    BUT T₁ is a throwaway object
                                                    GC reclaims it after wait_for_comms()
                                                    CPU storage in CPUCache: still zero

GPTQ on non-src ranks: reads weight_scale = 0 → ÷0 → NaN

Result: 8/8 ranks CORRUPTED  (max NaN 3706 / 37056 weight_scales)
```

### PR fix: explicit writeback → correct values on all ranks

```
src rank (r0)                            non-src ranks (r1..r7)
         │                                        │
broadcast_param = as_broadcastable(param)         broadcast_param = as_broadcastable(param)
  → contiguous staging buffer B₀                   → all-zero staging buffer B₁
         │                                        │
         └─── dist.broadcast(B₀, src=0) ──────────► B₁ filled with real weight_scale

wait_for_comms()

writeback step (non-src × independent CPUCache only):
  param.copy_(broadcast_param.reshape_as(param))      ← write received value to CPU storage
  update_offload_parameter(module, "weight_scale", param)

GPTQ on non-src ranks: reads weight_scale = correct value  ✓

Result: 8/8 ranks CLEAN  (NaN 0 / 37056)
```

The writeback guard `isinstance(cache, CPUCache) and not isinstance(cache, DistributedCPUCache)`
ensures `DistributedCPUCache` tensors are skipped — they are already memory-shared across ranks
via the shm filename broadcast and need no separate writeback.
