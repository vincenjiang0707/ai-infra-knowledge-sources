# [PR #2554] fix(onnx): trace Transpose between DequantizeLinear and its consumer in qdq_to_dq

source: https://github.com/NVIDIA/Model-Optimizer/pull/2554
state: open | updated: 2026-09-27T00:22:42Z

## 正文

### What does this PR do?

Type of change: Bug fix

`qdq_to_dq` assumed `DequantizeLinear` feeds `Conv`/`Gemm`/`MatMul` directly, tolerating only a `Cast` in between. A weight that reaches `MatMul` transposed — as in MaxViT's attention blocks — puts `Transpose` in front of `_convert_weight`, whose `axis_map` has no entry for it:

```
RuntimeError: Failed to convert node .../qkv/weight_quantizer/QuantizeLinear:
Unsupported op_type for real weight quantization: Transpose
```

**Tracing through the `Transpose` is not sufficient on its own.** `axis_map` is expressed in the *consumer's* layout, while the scale indexes the weight *as stored*, so the axis has to be mapped back through the `Transpose`'s permutation. Skipping the `Transpose` the way `Cast` is skipped gives:

| weight | naive skip | this PR |
|---|---|---|
| non-square (96, 32) | raises `Scale shape (96,) does not match weight shape (96, 32) along axis 1` | correct |
| **square (32, 32)** | **silently quantizes along the wrong axis — 907/1024 elements wrong** | correct |

`out == in` is common for attention projections, including MaxViT's own, so the silent case is the one that matters.

`_get_successive_consumers` now walks any `Cast`/`Transpose` chain and returns the composed permutation; `_convert_weight` applies it to the axis, asserting the permutation matches the weight's rank.

### Follow-up from review: the conversion axis

Review raised that `_convert_weight` derived the conversion axis from the consumer op, while the `DequantizeLinear` left in the graph dequantizes along the axis *it* declares. Where the two disagree the weight is quantized along the wrong axis, and on a square weight the scale length still matches either axis, so validation passes and `dq_only` export silently changes the model's output.

Confirmed by running each combination end to end under onnxruntime (square weight, `MatMul`):

| Q/DQ axis | Transpose | on `main` | this PR |
|---|---|---|---|
| 0 | no | **silently wrong** (max diff 4.62) | correct |
| 0 | yes | raises `Unsupported op_type` | correct |
| 1 | no | correct | correct |
| 1 | yes | n/a (raised before this PR) | correct |

Note the first row: that mismatch reproduces on `main` and is independent of `Transpose`. The conversion now uses the axis the Q/DQ pair declares, keeping the consumer mapping as the fallback for pairs that do not declare one, which covers both rows. `test_conversion_follows_the_source_qdq_axis` pins it and fails on `main`.

### Testing

On the reported model — `mtq.quantize(maxvit_tiny_rw_256, INT8_DEFAULT_CFG)` exported with `dq_only=True`:

- on `main`: raises `Unsupported op_type for real weight quantization: Transpose`
- with this PR: exports (44 MB DQ-only vs 160 MB QDQ), and the DQ-only graph is **bit-identical to the QDQ graph under onnxruntime — max abs diff `0.0e+00`** across 457 quantizers, output range `[-1.647, 2.457]`

Added `TestQdqToDqTranspose`, parametrized over non-square and square weights, asserting ORT output equivalence after conversion. Both cases fail on `main` and pass here; the square case is what catches the wrong-axis variant.

`tests/unit/onnx` is unchanged by this PR: 651 passed / 11 failed both with and without it. Those 11 are environmental on my Windows box (int4 paths needing cupy, and three `TestColumnMajorTransformation` tests needing MSVC build tools) and fail identically on pristine `main`. `ruff check` likewise reports the same 3 pre-existing `PLR0917` findings before and after.
