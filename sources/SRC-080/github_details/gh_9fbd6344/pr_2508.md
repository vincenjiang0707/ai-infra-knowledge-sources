## 正文

### What does this PR do?

Type of change: Bug fix

Hugging Face may apply a weight conversion mapping when loading a checkpoint, so the model's in-memory tensor names can differ from the names in the original checkpoint. ModelOpt reverses those conversions during unified Hugging Face export to keep the exported checkpoint compatible with loaders that expect the original layout.

ModelOpt previously maintained part of that reverse-name handling itself. This worked for simple renames and tensor splits, but it could not reverse a scoped conversion that merged multiple in-memory tensors back into one checkpoint tensor. In that case, export could retain the in-memory names instead of restoring the original checkpoint names.

This change uses Hugging Face's `WeightConverter.rename_source_key()` as the source of truth for converter matching, scope handling, and destination names when processing merge-style reverse conversions. ModelOpt then performs the required tensor concatenation, with checks for absent or incomplete groups, collisions, incompatible shapes or dtypes, and ambiguous scalar quantization state.

The existing rename and split behavior is unchanged. Export paths that process one tensor at a time continue to reject conversions that require cross-tensor regrouping rather than producing an incorrectly named checkpoint.

### Usage

No API or command-line changes are required. Existing resident unified Hugging Face export applies the reverse conversion automatically.

No prior Claude review on this PR, so nothing here is a repeat.

### What holds up

The core design is sound and the plumbing is correct. Specifically verified:

- `apply_reverse_rules(state_dict, split_rules, rename_rules, merge_rules)` matches the signature's positional order — easy to get wrong given `_build_reverse_rules` returns `(split, merge, rename, leaves)` in a *different* order, but the call is right, and all four unpack sites were updated.
- Merge-before-rename ordering is correct: the RADIO trace `vision_model.encoder.layer.0.attention.{q,k,v}_proj.weight` → merged to `…attn.qkv.weight` → renamed to `vision_model.radio_model.model.blocks.0.attn.qkv.weight` reproduces the test's expected key.
- Groups are keyed on the full post-merge target key, so leaves stay separated (`.weight` and `.weight_scale` never land in the same group), and per-leaf collision/completeness checks are in place.
- `_MergeRule`'s "reverse of a `Chunk` conversion" docstring is consistent with `SplitRule`'s convention of naming the *forward* op, despite being built from a reverse `Concatenate`.
- The resident path is genuinely atomic — `build_reverse_name_mapper` and `revert_weight_conversion_quant_aware` are computed in one `try` and both assigned only on success — so a raised `QuantConversionUnsupportedError` cannot desync config names from weight names.

### Most impactful findings

**1. A merge rule that matches zero keys is a silent no-op** (IMPORTANT Export) — and the rename rules still fire, so blocks get hub names while q/k/v stay unfused under post-conversion names. No exception, no warning, bad checkpoint. Every *other* failure mode in `_apply_merge_rule` raises and degrades safely; this is the one gap. It is reachable because `converter.rename_source_key(key)` receives no `base_model_prefix`, while ModelOpt's own `_scope_prefixes()` treats `base_model_prefix + scope_prefix` as the primary candidate — the new test pins `base_model_prefix=""`, so the divergent case is uncovered. A `if not groups: raise` converts this into the existing warn-and-fall-back.

**2. Streaming export of RADIO VLMs now hard-fails where it used to succeed** (IMPORTANT Compatibility). Previously the scoped-converter refusal was swallowed by `_assert_no_split_rules`'s `except Exception: return`, so offload/FSDP2/layer-wise export completed with in-memory names. Now it raises `NotImplementedError` and tells the user to export resident without offload — the very thing streaming exists to avoid. Defensible as a deliberate choice, but it needs a CHANGELOG note; the current entry describes only the fix.

**3. No `hasattr` guard for `rename_source_key`** (IMPORTANT Compatibility), despite the PR title's "when available", a `transformers>=4.57,<5.15` pin, verification only on 5.14.1, and this repo already gating the symbol as version-dependent in `model_load_utils.py`. On a 5.x without it, resident export surfaces a raw `AttributeError` and streaming raises a misleading "export resident instead".

The two SUGGESTIONs cover `_as_list()` consistency for `source_patterns` and `torch.cat`'s silent dtype promotion, plus a note that the 0-d scalar guard means merges only reverse while the merged modules are unquantized — worth documenting, since quantizing the vision tower silently returns the whole model to the buggy naming.

### Risk assessment

**Moderate.** The change is well-guarded and fails safe in nearly every direction — the author clearly thought about incomplete groups, collisions, shapes, and ambiguous scalar state. Risk concentrates in the one unguarded path (finding 1), where the outcome is a silently mis-named checkpoint rather than a warning, and in the unannounced streaming regression (finding 2). Findings 1 and 3 are both small, additive guards. No algorithmic errors in the concatenation logic, and no `modelopt_state` / mode-registration / public-API surface is touched.

**The two findings**

**1. The merge scalar guard is weaker than the split one.** `_split_leaf_tensor` tests `leaf in _SCALAR_LEAF_SUFFIXES or tensor.dim() == 0`; `_apply_merge_rule` tests only `tensor.dim() == 0`. A `weight_scale_2` or `input_scale` arriving as shape `[1]` rather than 0-d therefore reaches `torch.cat` and becomes shape `[3]` — a per-tensor scale silently widened, in a checkpoint that loads without complaint. Every other failure mode in that function degrades safely; this one does not. The two paths also disagree about the same invariant: either the name check in `_split_leaf_tensor` is dead code, or this guard has a hole.

**2. Merges have no counterpart in `build_reverse_name_mapper`.** The new parenthetical says tensor transforms lack a one-to-one name mapping — true for a split, but a merge is many-to-one, which is exactly the direction a name mapper needs. So the leaf leg (q_proj/k_proj/v_proj → qkv) is lost from quant-config names: the config can name a module absent from the checkpoint while `attn.qkv` is named by nothing, which is the failure mode that function documents in its own docstring. The 0-d guard makes this mostly unreachable, and `exclude_modules` wildcard summarization usually absorbs the leaf difference, but neither is a guarantee — a weight-only block-quantized group (`weight` plus 2-D `weight_scale`, no 0-d scalars) merges *while quantized* and lands in `quantized_layers` by exact name on the MIXED_PRECISION path, where no summarization happens. The safe invariant is incidental to the 0-d check rather than enforced. Refusing a merge that carries any quantizer-state leaf makes it explicit and closes the class at the same cost as finding 1.

Both are small additive guards in `_apply_merge_rule`. The SUGGESTION covers `_MergeRule` being a private type inside the exported `apply_reverse_rules` signature, and a more actionable `base_model_prefix` in the zero-match diagnostic.

**Risk**

**Low-to-moderate**, down from the previous round. The design is sound, and every path where a mis-named checkpoint could ship silently on the *weight* side is now closed. What remains is one numerically-silent hole on the scale side and one unenforced invariant on the config side — both narrow, both fixable in a few lines. No algorithmic error in the concatenation logic, and no `modelopt_state`, mode-registration, or public-API-behaviour surface is touched.
