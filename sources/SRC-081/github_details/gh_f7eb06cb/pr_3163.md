## Summary

- add one fused native MLX Metal kernel for EXL3 channel scaling plus the immediately following normalized 128-point Hadamard transform
- support output regularization (output RMS normalization/signs followed by the right transform) and input regularization (input RMS/codebook scaling followed by the left transform)
- emit the stored `sv`/`su` scale vectors in the same pass
- keep the API standalone and opt-in; this PR does not change EXL3 processor orchestration
- add independent Torch-oracle, threshold/boundary, zero-scale, invalid-input, and complete Qwen3.8-27B coverage

This replaces two full matrix passes with one kernel. RMS calculation, global-scale search, LDLQ, Viterbi search, and packing remain separate stages.

## Numerical design

An initial seven-stage butterfly was faster but not accepted blindly: realistic post-input-scale Qwen data produced 446 of 62,914,560 values outside `atol=rtol=1e-6`, with maximum absolute drift `2.861023e-6`. Pre-normalizing before the butterfly was also tested and was slightly worse.

The submitted kernel instead evaluates each normalized Sylvester-128 dot product directly from shared memory with FMA. This matches main's dense Torch Hadamard arithmetic exactly on every tested Qwen value while retaining a substantial speedup.

Observed results:

- transformed-weight values outside tolerance: **0 in every row**
- stored-scale values outside tolerance: **0 in every row**
- maximum absolute drift: **0**
- normalized RMS drift: **0**
- speedup: **2.10×–6.46×**

Boundary coverage includes the `1e-30` zero-scale threshold and adjacent float32 values, signed zero, adjacent values around ±1, the `0.1` replacement, `1e-10` epsilon, both output-scale policy branches, and the all-zero matrix path. Threshold fixtures preserve the production invariant that a zero/tiny RMS channel cannot contain order-one weights.

EXL3 converts weights to float32 before this stage, so BF16 is intentionally not accepted.
