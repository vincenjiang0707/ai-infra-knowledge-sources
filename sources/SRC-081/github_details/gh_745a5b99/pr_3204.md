## Implementation

### Sequential Pipeline Offloading
Removed the use of the offload context in the sequential pipeline. Onload/offload is manually managed now. 

Onloading is done as
```python
offload_kwargs = onload(subgraph_modules)
```
`subgraph_modules` is a hash as dict[str, module] where the key is the module's name. 
`offload kwargs` are in the form dict[str, dict]. Values are in the form returned by `get_cache_init_kwargs`

Offloading done as:
```python
offload(offload_modules, dict(offload_kwargs))
```

We do this so that we can swap out modules from the `subgraph_modules` when doing eager linearization/repacking easily. These operations create new module objects that need to be bound to the model. In addition, the old ones need to have all references deleted so that they can be freed, regulating our memory usage. 

Onload/Offload functions under `src/llmcompressor/pipelines/sequential/offloading.py`. 


We also add in prefetching for the onload/offload processes. Controlled by oneshot flag `sequential_module_prefetch`. This determines whether we overlap prefetching the next subgraph with the calibration/propagation process. 



We add flags `moe_eager_linearize_repack` (Linearize and/or repack each subgraph during calibration onload if `True`, linearize and/or repack before/after the whole model is calibrated for `False) and `repack_moe` (Whether or not to pack experts to 3d). 

Before calibration, we trace the whole model and build a hash for fast lookup for all moe modules -- packed or not packed. This is stored on the model as `model._moe_lookup`. Generated by `get_moe_linear_status`. 

This lookup is important because using model.get_submodules(name) traverses the whole model which is a taxing operation for large models. 

From here, we have functions as follows:
`linearize_moe_model`
`linearize_moe_subgraph`
`linearize_moe_layer`

and their corresponding repacking/reverse counterparts
`repack_moe_model`
`repack_moe_subgraph`
`repack_moe_layer`

The `*_model` functions are used with `sequential_linearize_repack=False`. They iterate over moe layers, onloading/offloading each layer individually (If you can't fit an entire moe layer on gpu at once, you're out of luck). The `*_subgraph` functions are assumed to be under a `disable_offloading_controlled` context. 

Some things to note:

Weird hard-to-read code such as:
```python
    linearized = [
        (moe_lookup[module], module)
        for module in subgraph_set
        if module in moe_lookup and isinstance(module, LinearExperts2D)
    ]

    for i in tqdm.tqdm(range(len(linearized)), desc="Repacking experts in subgraph"):
        repack_moe_layer(model, linearized[i][0], linearized[i][1])
```

Under these new contexts, since we want to constantly free up memory, we need to be careful with how we put out references. Iterating naively `for name, module in linearized` makes it such that linearized maintains a reference to the module. In the case that we are linearizing/repacking and the resulting new module is a new object, we want to free the old object. To my knowledge this can only be done when the python object is garbage collected. So here we make sure that the old module's reference is deleted by the end of its iteration. This is also why we need:

```python
        gc.collect()
        if torch.accelerator.is_available():
            torch.accelerator.empty_cache()
```

At the end of the new load context. We don't generate enough objects to force automatic garbage collection (at least for the tests I've run). The cache release might have a solution but I haven't been able to dig it up yet. Without that part it seems that we constantly have allocated but unused gpu memory.

## Code Review

This pull request refactors Mixture-of-Experts (MoE) linearization and repacking to support layer-wise execution during sequential calibration, and introduces asynchronous module prefetching (sequential_module_prefetch) to overlap offloading with forward passes. While these changes significantly optimize memory management, several critical issues were identified in the implementation and tests. Specifically, resolve_eager_moe_linearization is executed too late in the pipeline to affect calibration, and multiple newly added tests will fail with AttributeErrors due to calling non-existent helper functions or passing lists instead of dictionaries to functions expecting dictionaries.
