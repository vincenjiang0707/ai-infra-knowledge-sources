# [RFC] Reasoning-Aware Compression (RAC): on-policy CoT calibration for reasoning models

## Summary

Add first-class support for **Reasoning-Aware Compression (RAC)** — calibrating compression on the
model's *own on-policy chain-of-thought traces* in addition to prompts — to `llm-compressor`.

RAC comes from *"Reasoning Models Can Be Accurately Pruned via Chain-of-Thought Reconstruction"*
(Lucas, Behdin, Wang, Song, Tang, Mazumder), accepted at
**[ICLR 2026](https://iclr.cc/virtual/2026/poster/10006931)** —
[arXiv:2509.12464](https://arxiv.org/abs/2509.12464), reference code:
https://github.com/RyanLucas3/Reasoning-Aware-Compression. I am one of the authors and am proposing
to contribute an `llm-compressor`-native implementation.

The important property for this project: **RAC is a calibration-data construction method, not a new
algorithm.** It requires no change to `SparseGPTModifier`, `WandaPruningModifier`, or `GPTQModifier`.
The proposal is therefore mostly a data-side utility plus datasets, examples, docs, and tests.

## Motivation

`llm-compressor`'s layer-wise methods (SparseGPT, Wanda, GPTQ) solve, per layer,

```
min_{Ŵ_l ∈ W}  || W_l X_l − Ŵ_l X_l ||²
```

where `X_l` is the calibration activation matrix. In practice `X_l` is populated by a forward pass
over calibration text — see `SparsityModifierBase.calibrate_module` in
`src/llmcompressor/modifiers/pruning/sparsegpt/base.py`, which accumulates the Hessian over every
token of every batch the dataloader yields.

For conventional LLM workloads this is well matched: `|prompt| >> |completion|`, so inference-time
activations really are dominated by input tokens. **Reasoning models invert this.** DeepSeek-R1-style
models emit thousands of CoT tokens per query, so `|decode| >> |prompt|`, and a calibration set built
only from prompts (or from C4) covers a distribution the model spends almost none of its inference
time in.

The consequences are not subtle. From the paper, DeepSeek-R1-Distill-Qwen-7B pruned with SparseGPT at
50% unstructured sparsity, 1M calibration tokens, MATH-500 acc@1:1:

| Calibration set | Accuracy | Eval runtime |
|---|---|---|
| C4 | 0.744 | 135.0 min |
| Task prompts only | 0.812 | 115.6 min |
| **RAC (prompts + on-policy CoT)** | **0.900** | **35.3 min** |

(Dense: 0.936 / 23.3 min.)

Two things worth highlighting for this project:

1. **Compression on reasoning models can make inference *slower*.** The C4-calibrated 7B model at 50%
   sparsity took ~5.8× the dense evaluation time, because the pruned model rambles — it generates far
   more thinking tokens and still answers worse. This is the opposite of what a user running
   `oneshot` expects to get. RAC recovers most of both the accuracy and the runtime.
2. **The gap widens with sparsity.** At 20% all three calibration sets are within noise; at 50% the
   spread is 30+ points on the 1.5B model (C4 0.356 → RAC 0.664) and 9 points on LiveCodeBench for
   7B (C4 0.099 → RAC 0.283).

Today a user who wants this has to leave `llm-compressor`: generate traces with a separate
vLLM/`open-r1` script, serialize them, and only then come back to `oneshot`. That glue is exactly
what the reference implementation is, and it is the part worth upstreaming.

## Method (what actually changes)

Standard calibration collects activations for prompt indices `P_m` only. RAC additionally samples the
model's own continuation and collects the decode-phase activations:

```
z_{t+1} ~ π_θ(· | z_{0:t}),   t ∈ D_m        # on-policy rollout from the dense model
X_l^D  ← [ X_l^D  x_{t+1}^{(l−1,m)} ]        # decode activations
X_l^RAC = [ X_l^P   X_l^D ]                  # plain concatenation, no reweighting
```

and the layer objective becomes `|| (W_l − Ŵ_l) X_l^RAC ||_F²`. Because the rollout is generated by
the same autoregressive mechanism used at inference, the empirical activation distribution during
calibration matches the deployment distribution.

**Practical consequence:** since `X_l^RAC` is a plain concatenation with no reweighting, running a
teacher-forced forward pass over the *string* `prompt + generated_CoT + answer` produces exactly the
same activation matrix. So RAC reduces to: generate on-policy traces once, then hand
`prompt + trace` text to the existing `oneshot` path. Everything downstream is unchanged.

The one thing that genuinely cannot be shortcut is **on-policy**-ness: traces must come from the model
being compressed. The paper's ablation (7B compressed with 14B-generated traces) shows off-policy
traces are close at low sparsity but lose ground where it matters — 0.876 vs 0.900 at 50%. This is
the reason to ship a *generation utility* rather than just publishing a few static trace datasets.

## Proposed change

### 1. On-policy trace generation utility

New module, e.g. `src/llmcompressor/datasets/traces.py`:

```python
from llmcompressor.datasets import generate_calibration_traces

traces = generate_calibration_traces(
    model="deepseek-ai/DeepSeek-R1-Distill-Qwen-7B",
    dataset="open-r1/OpenR1-Math-220k",
    prompt_column="problem",
    num_prompts=512,
    max_new_tokens=8192,       # T_max in the paper
    temperature=0.6,
    top_p=0.95,
    backend="auto",            # "vllm" if installed, else "transformers"
    save_to=None,              # optional; also pushable to the Hub
)   # -> datasets.Dataset with columns {prompt, completion, text}
```

Then the existing entrypoint is used unchanged:

```python
from llmcompressor import oneshot
from llmcompressor.modifiers.pruning import SparseGPTModifier

oneshot(
    model=model,
    dataset=traces,
    text_column="text",
    max_seq_length=8192,
    num_calibration_samples=128,
    recipe=SparseGPTModifier(sparsity=0.5, targets="Linear", ignore=["lm_head"]),
    pipeline="sequential",
)
```

Notes on the design:

- **Backends.** `vllm` gives a large speedup for the generation phase but is not currently a
  dependency of this project. Proposal: `transformers.generate` as the dependency-free default,
  `vllm` behind an optional extra (`pip install llmcompressor[traces]`) and auto-detected.
- **Chat template correctness.** Traces must be tokenized exactly as at inference, including the
  assistant turn opener and `<think>` markers for R1-distill checkpoints. The utility should apply
  `processor.apply_chat_template(..., add_generation_prompt=True)` for the prompt segment and
  concatenate the raw generated ids, rather than round-tripping through detokenized text.
- **Optional correctness filtering.** The reference implementation can score completions and keep
  only correct rollouts. The paper's headline results do *not* filter, so this would default off; it
  is cheap to expose as a `filter_fn` hook.
- **Token budgeting.** The paper budgets calibration in *tokens* (1M), while `oneshot` budgets in
  *samples*. The utility should report the realized token count so users can size
  `num_calibration_samples × max_seq_length` accordingly.

### 2. Registered reasoning calibration datasets

Add `TextGenerationDataset` subclasses following the existing pattern in
`src/llmcompressor/transformers/data/` (cf. `gsm8k.py`) for the prompt corpora the paper uses:

- `open_r1_math` → `open-r1/OpenR1-Math-220k`
- `codeforces` → `open-r1/codeforces` (competition-programming problem statements)

These give the "prompt-only" baseline for free and serve as the prompt source for trace generation.

### 3. Examples, docs, tests

- `examples/reasoning_aware_compression/` — end-to-end script (generate traces → SparseGPT 50% →
  save), plus a variant showing RAC + `GPTQModifier` W4A16.
- `docs/guides/` entry on calibrating reasoning models, covering the "pruning made my model slower"
  failure mode explicitly, since that is the symptom users will search for.
- Tests: unit tests for the trace builder (chat-template shape, token accounting, deterministic
  greedy mode with a tiny model) and a small end-to-end oneshot test.

### What is explicitly *not* proposed

- No new modifier and no change to Hessian accumulation. The base method needs neither.
- No prompt-vs-decode reweighting. The paper uses unweighted concatenation. A `λ` knob (there is
  precedent in `DatasetArguments.use_loss_mask` for AWQ) is a plausible follow-up, but it is not part
  of the published method and I would keep it out of scope for v1.

## Alternatives considered

1. **Docs + a published trace dataset on the Hub, no code.** Cheapest option: publish
   `prompt + CoT` datasets for a few popular R1-distill checkpoints and write a guide. Downside: it
   is off-policy for every checkpoint we did not pre-generate for, and the on-policy ablation says
   that costs real accuracy at high sparsity. It also does not help anyone compressing an internal
   reasoning model.
2. **A `RACModifier` that generates traces inline during calibration.** Closer to Algorithm 1 as
   written, but generation and layer-wise compression have very different memory/parallelism profiles,
   and it would put an autoregressive sampling loop inside the sequential pipeline. Decoupling the
   two phases (as the reference implementation does) is simpler and lets users cache and reuse traces.
3. **Wire trace generation into `oneshot` as a dataset argument** (e.g. `dataset="self-generated"`).
   Convenient, but hides a potentially hours-long generation phase inside a call users expect to be
   compression-only. Better as an explicit, separately cacheable step. Could be layered on later.

## Open questions for maintainers

1. **Is a generation dependency acceptable?** This is the main architectural question. Does the
   project want `vllm` as an optional extra, or should trace generation stay `transformers`-only (much
   slower for 8k-token rollouts at 32B scale), or live outside the package entirely?
2. **Where should the utility live** — `llmcompressor.datasets`, a new `llmcompressor.calibration`
   namespace, or `examples/` only for a first iteration?
3. **Long-sequence calibration.** 8k-token calibration rows are longer than typical `llm-compressor`
   usage. Are there known limits in the sequential pipeline's activation offloading
   (`sequential_offload_device`) that would bite at this length, and is a shorter default `T_max`
   (e.g. 4096) a better starting point?
4. **Quantization.** The paper's headline results are pruning. It reports RAC + FP8 and 2:4
   semi-structured results (e.g. 14B, 2:4 MLP, first & last third: 0.940 acc@1:1 at 1675 tok/s vs
   1426 tok/s dense), but does not systematically study GPTQ W4A16 under RAC calibration. I would
   like to run that before claiming it, and would scope the initial PR to pruning + an unvalidated
   W4A16 example unless maintainers prefer to wait for numbers.
5. **Scope of what I contribute.** Happy to do all of it, or to start with docs + examples and grow
   into the utility based on feedback.

## Proposed milestones

1. RFC discussion / design agreement (this issue).
2. PR 1: trace generation utility + tests.
3. PR 2: registered `open_r1_math` / `codeforces` calibration datasets.
4. PR 3: examples + docs guide.
5. Reproduction numbers on DeepSeek-R1-Distill-Qwen-1.5B/7B at 40–50% sparsity, posted on the issue,
   to confirm the `llm-compressor` path matches the paper's reference implementation.

## Compatibility and risk

- Purely additive; no changes to existing modifiers, recipes, or serialization.
- Main new cost is user-facing runtime for trace generation, which is opt-in and cacheable.
- Main new risk is a hidden mismatch between how traces are templated/tokenized and how the model is
  actually served — worth an explicit test.
