### Describe the bug

## Summary

`LMCRadixCache` does not implement `release_aborted_request`, so aborts fall through to the
no-op default in `base_prefix_cache.py:371`. Nothing raises, so the gap is silent.

In MP mode, `match_prefix` opens an LMCache session and may leave a pending lookup holding
daemon-side read locks; `init_load_back` is what consumes them. A request aborted between
those two points leaks, for the lifetime of the server:

- `_mp_load_back_markers[rid]` (`lmc_radix_cache.py:231`, consumed at `:303`);
- the connector-side pending lookup;
- daemon-side read locks, which block eviction of the entries they cover;
- an LMCache session that never receives `END_SESSION`.

The straightforward fix — calling `end_session(handle.rid)` from `release_aborted_request` —
is **not safe in general**, and the abort hook also cannot simply be moved later, because
another backend depends on the current ordering. Details below. Verified on `76f9213a41`.

Related closed PR (not merged): #40334, closed by me after finding the ordering problem.

## Analysis

### Why the obvious fix is unsafe

Three of the six abort call sites (`scheduler.py:3260`, `:3359`, `:5478`) never reach
`cache_finished_req`, so for those the hook is the only possible cleanup point. The other
three (`:3573`, `:5422`, `:5458`) do reach it via `release_kv_cache` (`common.py:272`).
Most notably the disaggregated-decode waiting-queue abort passes the default `is_insert=True`:

```text
scheduler.py:5422  _release_aborted_request(req)
scheduler.py:5431  release_kv_cache(req, self.tree_cache)      # is_insert=True
                     -> cache_finished_req
                        -> store_kv       (lmc_radix_cache.py:489)
                        -> end_session    (lmc_radix_cache.py:493)
```

Adding `end_session` to the abort hook turns that into `end_session -> store_kv -> end_session`.

That relies on the external LMCache implementation treating `end_session` as idempotent.
SGLang declares no `lmcache` dependency at all (it is not in `python/pyproject.toml`), so that
contract is unpinned and unverifiable from this repository. It also permits a STORE after the
session has been closed — and MP `store_kv` blocks until the daemon signals, so the failure
mode is not necessarily a silent no-op.

Tracking active sessions inside SGLang would prevent the second call, but cannot fix the
ordering: the first `end_session` still precedes the STORE.

### Why the abort hook cannot simply be moved later

Backends differ in whether they tolerate running abort cleanup after `cache_finished_req`:

- `hiradix_cache.py` does not override `cache_finished_req`, and the base implementation never
  touches `ongoing_prefetch` / `prefetch_loaded_tokens_by_reqid` that its
  `release_aborted_request` (:2014) cleans — order-independent.
- `unified_radix_cache.py:961` does override it, but does not touch the prefetch, linker or
  buffer-pipeline state cleaned by its `release_aborted_request` (:2458) — order-independent.
- `flexkv_radix_cache.py` **requires the current order**. `cache_finished_req` (:388) may
  `inc_lock_ref` a source node, launch an async store on `store_stream`, and register it in
  `_inflight_store_nodes` (:448); `release_aborted_request` (:488) pops that registration and
  `dec_lock_ref`s the node. Running cleanup afterwards would drop the lock of a store still in
  flight, letting eviction free its source slots — exactly what the comment in `evict()` guards
  against.

So the hook must run before `cache_finished_req` for FlexKV, and would need to run after it for
LMCache.

## Design gap

`release_aborted_request(handle)` conflates two lifecycle operations:

1. cancel pending lookup/prefetch work left by the aborted attempt;
2. perform final request/session cleanup after any required KV release or STORE.

It has neither the phases nor the context to know whether `cache_finished_req` will run
afterwards. A possible direction:

```text
cancel_aborted_request_work
  -> release_kv_cache / cache_finished_req / optional STORE
  -> finish_request_session
```

This preserves FlexKV's required ordering while letting LMCache close its session after the
final STORE, or immediately when no KV finalization happens.

A secondary observation: LMCache keys this state by `rid`, while the attempt lifecycle
introduced in #39318 is keyed by `CacheRequestHandle(rid, attempt_id)`. This is correct today
because the scheduler retires an attempt before starting the next, but it does not give LMCache
the attempt-level isolation FlexKV has.

### Reproduction

No single command reproduces the runtime leak; it needs an LMCache MP daemon plus an abort
landing in a specific window. Trigger conditions:

- LMCache enabled (`enable_lmcache`), MP mode (the default on non-XPU), i.e. `LMCRadixCache`
  is selected in `registry.py:118`;
- a request whose `match_prefix` reports `host_hit_length > 0`, so `_mp_match_prefix` records
  a marker and keeps the lookup locks (`lmc_radix_cache.py:231`);
- the request is aborted before `init_load_back` runs — e.g. `AbortReq` while it is still in
  the waiting queue (`scheduler.py:5422`), or `retire_unadmitted_request` (`:3260`).

The leak itself is directly reproducible in a unit test: drive `_mp_match_prefix` with a fake
connector that models the pending-lookup / read-lock bookkeeping, then call
`release_aborted_request` and observe that nothing is released. #40334 contains such a
CPU-only test (4 cases, no GPU and no `lmcache` install required).

The disaggregated-decode ordering path (abort followed by `cache_finished_req` and a STORE)
is not covered yet.

### run-qing-spo · 2026-09-19

@cctry — you introduced the per-attempt cleanup hook in #39318, so you're probably the
right person to judge the design question here: whether `release_aborted_request` should
be split into a cancel phase and a finalize phase.

The concrete finding is that the hook has to run *before* `cache_finished_req` for FlexKV
(it would otherwise release the lock of an in-flight async store) but would have to run
*after* it for LMCache (to close the session after the final STORE). No single position
works for both.

### AyushmanGarg · 2026-09-20

Confirmed against current main: LMCRadixCache has no release_aborted_request override, so aborts hit the no-op in base_prefix_cache.py, and on the abort paths that never reach cache_finished_req the MP marker, pending lookup, and session all leak for the life of the server.

I can implement the two-phase split:

1. BasePrefixCache: split release_aborted_request(handle) into cancel_aborted_request_work(handle) (runs before any KV finalization) and finish_request_session(handle) (runs after cache_finished_req, or immediately on abort paths that never reach it). Both default to no-op so existing backends are untouched.
2. FlexKV: move the current cleanup into the cancel phase unchanged - its ordering requirement is preserved.
3. LMCRadixCache: cancel drops _mp_load_back_markers[rid] and cancels the connector-side pending lookup; finish calls end_session(rid). That gives LMCache end_session after the final STORE on paths that reach cache_finished_req, and immediate cleanup on paths that don't.
4. Tests: port the CPU-only fake-connector tests from #40334 and add the uncovered disaggregated-decode ordering case (abort -> cache_finished_req -> STORE -> end_session).

One design question before writing code: on abort paths that do reach cache_finished_req, should finish_request_session be invoked inside release_kv_cache after cache_finished_req returns, or by the scheduler explicitly after release_kv_cache? The former keeps request-cache lifecycle inside the cache layer; the latter keeps the call order visible at the abort site.

If @cctry is on board with the split I'll open a draft PR.

### cs-fisha · 2026-09-21

Confirmed on current main: `LMCRadixCache` does not override `release_aborted_request`, so an abort between `match_prefix` and `init_load_back` hits the base no-op and leaks the MP load-back marker plus the LMCache session/lookup.

I would not put `end_session` in that abort hook. #40334 already showed a single cleanup site cannot satisfy both backends: FlexKV has to cancel in-flight lookup/prefetch *before* `cache_finished_req` (otherwise it can drop the lock of an async STORE), while LMCache needs to finish/end the session *after* that optional STORE, or immediately on abort paths that never STORE.

That points at two-phase hooks rather than one:

1. Cancel pending lookup/prefetch before `cache_finished_req` (FlexKV needs this).
2. Finish/end the LMCache session after STORE, or immediately if there is no STORE.

@cctry — is that split acceptable? The two-phase direction already sketched above looks right to me; if the shape is OK I can follow up with CPU fake-connector tests (no GPU / no real lmcache daemon) for the abort-before-load-back leak and the path that still reaches STORE.
