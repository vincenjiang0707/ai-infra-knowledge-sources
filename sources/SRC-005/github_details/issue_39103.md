### he-yufeng · 2026-09-11

Confirmed on current main: `include_reasoning` does not exist anywhere — not in `ChatCompletionRequest` (protocol.py) and not in the serving layer — so the field is silently dropped and `reasoning_content` always comes back whenever the reasoning parser splits one out.

The gap is one field plus two emission gates. I'm opening a PR that adds `include_reasoning` to the request schema (default keeps today's behavior) and skips reasoning emission when it is False, both on the non-stream response message and the streaming reasoning chunk. The reasoning parser still runs either way, so the visible content stays clean and token accounting is unchanged. Two no-GPU unit tests pin the suppression and the default.


### he-yufeng · 2026-09-12

One scope note so this closes cleanly: the two curls in the report are different surfaces.

`/v1/chat/completions` is the vLLM-extension surface where `include_reasoning` is a real field; my #39113 adds it to `ChatCompletionRequest` and gates both emission points (non-stream `reasoning_content` and the streaming reasoning chunk), with the default preserving current behavior.

`/v1/responses` is different: the OpenAI Responses spec has no `include_reasoning`; output control there is `reasoning.summary` plus `include: ["reasoning.encrypted_content"]`. The response shown above emits a reasoning item whose `content` carries raw reasoning text with no opt-in, which is arguably its own bug independent of this flag — but whether sglang should honor `include_reasoning` there as a vLLM-compatible extension, or steer users to `reasoning.summary`, is a maintainer call I did not want to bake into #39113 unilaterally. Happy to extend the PR either way.
