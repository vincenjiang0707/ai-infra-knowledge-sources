### Describe the bug

## Summary

When serving GLM-5.1 / GLM-5.1-derived models with EAGLE/MTP, target-verify decode CUDA graphs can become very large. In production profiling, `cudaGraphLaunch` for `step[TARGET_VERIFY ...]` takes multiple milliseconds on the scheduler main thread. This host-side launch time is not fully hidden by overlap scheduling and becomes visible latency.

The issue appears when replaying the full decode graph from:

    python/sglang/srt/model_executor/runner_backend/full_cuda_graph_backend.py(123): replay
    python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py(984): execute
    python/sglang/srt/model_executor/model_runner.py(3015): _forward_raw
    step[TARGET_VERIFY bs=...]
    python/sglang/srt/speculative/eagle_worker_v2.py(1447): verify

## Why this still matters with Spec V2 / overlap

There has been substantial work to make spec decoding overlappable:

- #11398 introduced beta EAGLE spec-overlap.
- #25879 routes `seq_lens` through `FutureMap` and removes `verify_done.wait()`.
- #25464 makes EAGLE / EAGLE3 / STANDALONE / MULTI_LAYER_EAGLE always use the V2 worker, with overlap scheduling driving it asynchronously.
- #25945 and #26380 further reduce scheduler-stream stalls and shared-buffer hazards.

However, the current profile still shows the scheduler main thread spending several milliseconds inside `cudaGraphLaunch` during target verify. Also, the event loop still has a result-processing sync path:

    python/sglang/srt/managers/scheduler.py(1549): pop_and_process
      -> process_batch_result(...)
         -> result.copy_done.synchronize()

So even in the fully overlapped V2 EAGLE worker, long host-side graph launches remain a problem: they can occupy the scheduler thread before the next useful CPU-side work can proceed, and any later `pop_and_process` synchronization can expose the launch bubble.

## Proposed fix: pipeline target-verify decode with two CUDA graphs

Instead of replaying target verify as one very large full decode graph, add an optional decode graph split:

    --decode-cuda-graph-split-nlayers N

or as CUDA graph config:

    {
      "decode": {
        "backend": "full",
        "split_nlayers": N
      }
    }

When enabled, capture two ordinary CUDA graphs per decode shape:

1. `graph_first`: metadata setup + embedding + first `N` transformer layers
2. `graph_second`: remaining layers + norm + logits

Replay:

    graph_first.replay()
    graph_second.replay()
    return graph_second_output

Both replays should happen on the same CUDA stream. No event or host sync is needed: stream ordering ensures graph 2 runs after graph 1. The benefit is that the CPU can launch `graph_second` while `graph_first` is already executing on the GPU. This should hide part of the second graph’s host submission cost behind useful GPU work.

For GLM-5.1-like 70B+ MoE models, the split point can be tuned. A starting sweep could be:

    split_nlayers = 4, 8, 16, 24, 32

The expected good region is where graph 1 has enough GPU work to cover most of graph 2’s host launch time, but graph 1 itself is still small enough to launch quickly.

## Implementation sketch

A minimal version could add a new decode backend, for example:

    LayerSplitFullCudaGraphBackend

It would be similar to `FullCudaGraphBackend`, but store:

    _graphs_first[shape_key]
    _graphs_second[shape_key]
    _outputs[shape_key]
    _bridge_tensors[shape_key]

The model forward needs a small split context:

    DecodeGraphSplitContext(
        phase="first" | "second",
        split_nlayers=N,
        hidden_states_bridge=...,
        residual_bridge=...,
        topk_indices_bridge=...,  # needed for DSA paths
    )

For GLM-5.1 DSA, this can initially be implemented in the DeepseekV2/GLM-DSA model loop:

- first phase: run layers `[start_layer, start_layer + N)`, copy `hidden_states`, `residual`, and DSA `topk_indices` into bridge tensors
- second phase: read bridge tensors, run `[start_layer + N, end_layer)`, then norm/logits normally

Important detail: metadata initialization should happen only in graph 1. Graph 2 should not rerun `attn_backend.init_forward_metadata_in_graph(...)`.

## Why not breakable CUDA graph?

Breakable CUDA graphs reduce the size of each launch but introduce eager CUDA ops between graph segments. In this case the target is different: keep the decode path as two fully captured CUDA graphs, with no eager CUDA work between them, and rely on launch pipelining on the same stream.

## Expected result

In the profiler, each target-verify step should show:

    cudaGraphLaunch(graph_first)   small host launch
    cudaGraphLaunch(graph_second)  host launch overlapping graph_first GPU execution

and no eager CUDA operations or `cudaStreamSynchronize` between the two launches.

The main metric is reduced exposed scheduler-thread time for target verify, especially for GLM-5.1 / GLM-DSA style models where the full decode graph contains thousands of graph nodes.
