# [Issue #32169] [Bug] InternVL2_5-2B fails to start: 'CLIPImageProcessor' object has no attribute 'tokenizer' in get_tokenizer_from_processor

state: closed | updated: 2026-09-22T00:28:28Z

## 正文

### Summary

Serving `OpenGVLab/InternVL2_5-2B` crashes at startup while building the tokenizer/processor. `get_processor()` resolves the model to a bare **`CLIPImageProcessor`** (an image-only processor with no `.tokenizer` attribute), and `get_tokenizer_from_processor()` then does an unguarded `return processor.tokenizer`, raising `AttributeError`. The server never becomes ready, so any workload using this model errors out before inference.

This is **device-independent** — it is pure `transformers`/HF processor-resolution logic with no CUDA/HIP involvement.

### Reproduction

Boot a server for `OpenGVLab/InternVL2_5-2B` (e.g. `sglang.launch_server --trust-remote-code`, or a VLM MMMU eval harness). The server fails during tokenizer/processor init.

```
File ".../srt/managers/tokenizer_manager.py", line 3220, in _get_processor_wrapper

```

(The log also shows HF remote-code download of InternVL2.5's `tokenization_internlm2.py`, i.e. the tokenizer ships separately from the image processor.)

### Root cause

`get_tokenizer_from_processor` (`python/sglang/srt/utils/hf_transformers/common.py:524`) assumes any processor that is not itself a tokenizer exposes a `.tokenizer`:

```python
def get_tokenizer_from_processor(processor):
    from transformers import PreTrainedTokenizerBase
    if isinstance(processor, PreTrainedTokenizerBase):
        return processor
    return processor.tokenizer          # <-- unguarded; fails for image-only processors
```

For InternVL2.5, `AutoProcessor.from_pretrained(...)` inside `get_processor` does not return a combined multimodal processor — it returns a bare `CLIPImageProcessor`. InternVL2.5's config does not bundle a proper `AutoProcessor` that HF can assemble (its tokenizer is a separate remote-code `InternLM2` tokenizer), so `AutoProcessor` falls back to the image processor alone. `processor.tokenizer` then raises.

Notably, sglang already handles this exact case correctly in the *runtime* multimodal processor `python/sglang/srt/multimodal/processors/internvl.py` (`InternVLProcessor.__init__`, line 76):

```python
if hasattr(self._processor, "tokenizer"):
    tokenizer = self._processor.tokenizer
else:
    tokenizer = self._processor
```

but the generic startup helper `get_tokenizer_from_processor` has no equivalent guard.

### Suggested fix (for discussion)

The caller `get_tokenizer_from_processor(processor)` only receives the processor object and has no `model_path`, so it cannot re-load a tokenizer on its own. The clean place to fix is in `get_processor` (`processor.py`), where `tokenizer_name`, `revision`, and `trust_remote_code` are all in scope — mirroring the existing `_TOKENIZERS_BACKEND` reload branch immediately after line 271:

- After resolving `processor`, detect the image-only case (e.g. the object is a `BaseImageProcessor`/`*ImageProcessor` with no `tokenizer` attribute) and load the tokenizer separately via `get_tokenizer(tokenizer_name, tokenizer_mode=..., trust_remote_code=..., tokenizer_revision=...)` instead of calling `get_tokenizer_from_processor(processor)`.

Optionally, also harden `get_tokenizer_from_processor` itself with a `hasattr(processor, "tokenizer")` guard that raises a clear, actionable error (naming the model and processor class) rather than a bare `AttributeError`, so future image-only-processor models fail loudly and legibly.

### Scope / risk note

This touches core processor-resolution code shared by all image-only-processor models, so the fix should be validated against a couple of other VLMs to make sure the image-only detection doesn't mis-fire on models whose combined processor legitimately exposes `.tokenizer`.
