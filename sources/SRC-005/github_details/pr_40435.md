# [PR #40435] [NPU] Gate arch35 block-FP8 -> MXFP8 requantization behind SGLANG_NPU_ARCH35_REQUANT_BLOCK_FP8

## 正文

## Motivation

Follow-up to #39823. That PR made plain block-FP8 checkpoints (fp32 block scales) on arch35 (Atlas A5) requantize to MXFP8 at load time unconditionally, so dense linears run on the native quantized GEMM instead of the Triton emulation path.

As raised in the post-merge review of #39823: fp8 per-block quantization with fp32 scaling factors is semantically different from MXFP8. Only DeepSeek-style UE8M0 checkpoints can be converted losslessly (a 128×128 block's power-of-two scale can be duplicated to its 1×32 sub-blocks exactly). For plain fp32-scale checkpoints, the load-time conversion is a lossy re-quantization (dequant to BF16 → npu_dynamic_mx_quant , granularity 128×128 → 1×32, scales rounded to powers of two), which changes the checkpoint numerics:

- Dataset-level evals are largely insensitive to this error magnitude
- Training-time consumers are not: e.g. RL rollouts served by sglang vs. reference logprobs computed elsewhere can see importance-ratio drift from the systematic numerics change
The safe default should be to serve the checkpoint as-is; the native-GEMM path should be opt-in for deployments that have validated accuracy for their workload.

## Modifications

- environ.py : add SGLANG_NPU_ARCH35_REQUANT_BLOCK_FP8 (default False )
- Fp8LinearMethod.process_weights_after_loading : only enter process_npu_arch35_mxfp8_linear_weights for UE8M0 checkpoints (lossless re-layout, unchanged) or when the env var is set; plain block-FP8 checkpoints now fall through to the generic path and keep their original layout
- fp8_utils._dispatch_auto_backend : select npu_w8a8_mxfp8_linear under the same condition ( act_scale_ue8m0 or the env var) — this must stay in sync with the weight-layout gate, otherwise the kernel and layout mismatch. arch35 + plain block-FP8 now resolves to triton_w8a8_block_fp8_linear
- w8a8_mxfp8.py : docstring updated to document the gate

## Accuracy Tests

No numeric output changes by design:

- Default path (env unset) restores the pre-#39823 bit-faithful serving path for fp32-scale checkpoints — Triton emulation on the untouched checkpoint layout
- UE8M0 checkpoints are unaffected (lossless path, unconditional)
- env=1 is opt-in and numerically identical to what #39823 shipped
Dispatch verified locally for all three combinations (mocked is_npu_arch35 ): env-unset + fp32 scales → triton_w8a8_block_fp8_linear ; env=1 + fp32 scales → npu_w8a8_mxfp8_linear ; env-unset + ue8m0 → npu_w8a8_mxfp8_linear . Also verified the fall-through path stays clean: requant_block_scale_ue8m0_for_deepgemm is a no-op without DeepGEMM, and block_fp8_as_mxfp8 requires UE8M0 + 32-wide K blocks so it cannot mis-enable on plain block-FP8.

Behavior matrix on arch35:

| Checkpoint | Env var | Weight layout | GEMM |
|---|---|---|---|
| UE8M0 (DeepSeek V3.1+) | any | MXFP8 re-layout (lossless) | native (unchanged) |
| fp32 block scales | unset (default) | plain block-FP8 | Triton emulation (pre-#39823 behavior) |
| fp32 block scales | `=1` | MXFP8 (lossy requant) | native (perf path, as merged in #39823) |

## Speed Tests and Profiling

None — this PR adds no new fast path. The perf characteristics of each path are unchanged from #39823: native MXFP8 GEMM vs. Triton emulation (~100ms per large-M linear) applies only when the env var is explicitly enabled.
