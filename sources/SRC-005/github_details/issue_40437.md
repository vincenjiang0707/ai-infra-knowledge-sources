## 正文

## Motivation

Track DeepSeek-V4-Flash MXFP4 support under #33522, following #39762.

In our earlier 8× H200 / TP=8 tests, daemon preloading succeeded, but client loading failed with 172 shape/dtype mismatches across 43 MoE layers. Both standalone and engine-managed daemon modes showed the same failure.

#39762 concerns rejecting unsupported configurations early. This issue tracks enabling safe IPC loading.

## Gaps to address

1. **Final tensor layouts:** the client must accept validated, backend-specific post-processed MXFP4 layouts instead of requiring checkpoint-time shapes/dtypes.

2. **Safe post-load lifecycle:** #38306 introduces post-load handling, but calling `post_load_weights()` alone may not be safe for DSV4. For example, `ape_converted` is client-local state; failing to restore it could cause an already-transformed APE tensor to be transformed again through shared storage.

3. **Runtime state outside registered tensors:** backend-owned tensors such as `_swiglu_limit_tensor` also need reconstruction on the correct device.

The layout mismatch was reproduced on GPUs. Items 2–3 are follow-up risks identified from code inspection, not yet GPU-validated failures.

## Suggested approach

Start with the H200 / FlashInfer CUTLASS MXFP4 path:

- Extend existing IPC metadata with the layout identity and required post-processing state.
- Validate and bind the daemon's final tensors.
- Restore client-local runtime state without rerunning weight-mutating transformations.

This could build on the manifest and post-map rebuild work in #33522, alongside #38306.

## Validation

- Tensor/layout parity and inference accuracy against ordinary loading.
- Successful client restart while reusing resident weights.
- Unchanged daemon-owned weight hashes after client attach and inference.

I have 8× H200 available and can help run these tests. Is this a reasonable initial scope, and is anyone already working on the DSV4-specific reconstruction path?
