# [PR #35694] fix: keep speculative overshoot out of the radix cache key

## 正文

## Motivation

A speculative verify step commits a whole accepted chunk, so a request's
`output_ids` can run past the point where it actually stopped — measured 0–7
tokens for DSPARK `block_size=7` at `max_new_tokens=1024`. The client is served
`output_ids_through_stop`; the radix cache is keyed on raw `output_ids`:

```python
# mem_cache/unified_radix_cache.py, cache_finished_req
token_ids = (req.origin_input_ids + req.output_ids)[:kv_len_to_handle]
```

So the tree stores a suffix no continuation can reproduce. A follow-up turn is
built from what the client received and therefore diverges from the cached
sequence at `prompt + returned`.

On a full-KV model that is wasted pages. On a hybrid model it costs the whole
decode region. Under `--mamba-radix-cache-strategy extra_buffer` the insert
carries exactly one mamba checkpoint, at
`floor(committed / interval) * interval`, and `MambaComponent.create_match_validator`
is a hard gate — a node without a mamba value cannot extend the mamba boundary.
When the checkpoint lands past the divergence point, the matched prefix has no
checkpoint at all and reuse falls back to the prefill-time insert:

```
prompt=3964 committed=1029 insert_len=4992 reachable=4988
Decode cache miss for prompt 1 | cached=3840 prompt_len=3964
```

`3840 == floor(3964 / 128) * 128` — the second turn matched a page-aligned prefix
of the prompt and none of the 1024 generated tokens. Predicate:
`floor((prompt + committed) / interval) * interval > prompt + returned`. Over a
measured 4x B200 sample of 36 first-turn prompts it fires exactly once, on the
one prompt that missed, 10/10 reps.

The window is at most `chain_len - 1` positions out of `interval`, so it reads as
intermittent — roughly one prompt in 32 — but it is deterministic given the
prompt. Without speculation `committed == returned` and the gap is empty.

## Modifications

`Req.effective_kv_committed_len()` is the single point where the finish-time KV
length is decided: `release_kv_cache` hands it to every cache implementation as
`kv_len_to_handle`, and everything past it is released as overallocated. Capping
it at what the client received keeps the overshoot out of the key and frees it in
the same step, for all eight cache implementations at once rather than patching
each `(origin_input_ids + output_ids)` site.

The method already had precedent for this shape: `strip_thinking_cache` caps at
the prompt for the same reason (#22373), "so thinking + answer fall into the
overallocated range and are reclaimed by release_kv_cache".

`StreamingSession.try_cache_finished_req` is stronger precedent still — the
session path already calls `_trim_overshoot(req, finished_len)` and sets
`slot.kv_committed_len = min(len(origin_input_ids) + finished_len, ...)`. The
overshoot was already understood to be untrustworthy for reuse there; the plain
`release_kv_cache` path never learned it.

One companion change: `_release_overallocated_kv_indices` asserts a
non-speculative request has nothing overallocated, and a stop landing before the
last committed token now legitimately breaks that, so the assert learns about it
the same way it already knows about `strip_thinking_cache`.

No leak. The tail moves from "inserted" to "freed", and `ceil_align(start_p,
page_size)` still lands on the page `cache_finished_req` just released, so the
two frees meet without a gap and without double-freeing.

### End to end, 4x B200

Two arms of the same tree, differing only in this method, same server config,
same prompts, same seed. Prompts constructed so `(prompt + max_new_tokens) % 128
== 127`, which is where the predicate can fire, plus a `% 128 == 0` control group
that it can never reach:

| prompt | before | after |
|---|---|---|
| 2431 (`%128 == 127`) | `cached=2304` **MISS** | `cached=3328` **HIT** |
| 7 other `%128 == 127` | HIT | HIT |
| 8 control `%128 == 0` | HIT | HIT |

`2304 == floor(2431 / 128) * 128` is the prefill-time insert — the second turn
reused none of the 1024 generated tokens. `3328 == floor((2431 + 1024) / 128) *
128` is exactly the length the cap produces, so the fix does not merely stop the
miss, it lands the reuse where the arithmetic says it should. Deterministic:
identical across both reps of both arms. The control group is byte-identical
between arms, so nothing is over-capped.

Model `thinkingmachines/Inkling-Small-NVFP4` + draft `RadixArk/Inkling-Small-DSpark`,
`--tp 4 --speculative-algorithm DSPARK --mamba-radix-cache-strategy extra_buffer
--mamba-track-interval 128 --page-size 128 --enable-deterministic-inference`,
`SGLANG_ENABLE_UNIFIED_RADIX_TREE=1`.

#35293 loosened `min_cache_hit_ratio` from 0.99 to 0.90 on the DSPARK class
precisely because of this, so this PR puts it back to 0.99 — that class is then
the e2e regression guard for this fix on `4-gpu-b200`, at every prompt rather
than 90% of them.
