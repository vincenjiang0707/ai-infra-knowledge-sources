## Motivation

Fixes #40835

PEFT scales an rsLoRA adapter (use_rslora=True) by lora_alpha / sqrt(r). SGLang ignores the flag and always uses lora_alpha / r. The adapter loads without any error, but its update is sqrt(r) times too weak: 4 times at r=16 and 8 times at r=64. So the served model is not the model the user trained. RL loops that sync a LoRA policy into SGLang hit the same path, and their rollout policy then differs from the trained one.

Unsloth exposes use_rslora in get_peft_model, and the diffusion LoRA loader in this repo already supports it (#35868).

## Modifications

1. LoRAConfig reads use_rslora from the adapter config. The default is False.
2. LoRAAdapter picks the divisor from that flag: sqrt(r) for rsLoRA, and r otherwise.
3. A new CPU test, test/registered/unit/lora/test_lora_adapter_scaling.py, covers both cases. The rsLoRA case fails on main (2.0 instead of 16.0) and passes with this change.

All consumers read LoRAAdapter.scaling. This includes the per-batch scale list in LoRAManager and the weights that the memory pool scales at load time, so this one value fixes all of them. rank_pattern and alpha_pattern are still ignored. I left them for a separate change.

## Accuracy Tests

The change only affects adapters with use_rslora=True. I checked the scale against PEFT itself. I saved a real PEFT adapter (r=64, lora_alpha=128) and loaded it from disk with LoRAConfig. The script is in the linked issue.

| use_rslora | PEFT | SGLang main | This PR |
|---|---|---|---|
| True | 16.0 | 2.0 | 16.0 |
| False | 2.0 | 2.0 | 2.0 |

## Speed Tests and Profiling

No effect. The scale is computed once when the adapter loads.
