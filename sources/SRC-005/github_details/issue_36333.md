### Describe the bug

> Submitted by GLM-5.3

When a streaming client disconnects mid-generation, the scheduler-side request
is never aborted and keeps decoding until `max_tokens`. Every output batch for
that request logs:

```
Received output for rid='...' but the state was deleted in TokenizerManager.
```

at a high rate (observed ~15 lines/s per request, sustained for the entire
remaining generation — in production two zombie requests burned GPU for 15+
minutes and occupied both `--max-running-requests` slots, blocking all new
requests from being scheduled).

Root cause (verified on current `main`):

1. `TokenizerManager.generate_request` has an `except BaseException` cleanup
   that calls `_discard_pending_req_states(obj)`. It was added for failures
   *before* the request reaches the scheduler (e.g. input-length validation),
   but a client disconnect raises `asyncio.CancelledError` — also a
   `BaseException` — so the state of a request that **is running on the
   scheduler** gets popped immediately at disconnect time.

2. The delayed safety net then doesn't fire: `create_abort_task` (attached to
   the `StreamingResponse` as a background task, runs ~2s after teardown)
   calls `abort_request(rid)`, which early-returns on
   `tokenizer_worker_num == 1 and rid not in self.rid_to_state`. The
   `AbortReq` is never dispatched, so the scheduler never learns the client
   is gone and decodes to `max_tokens`; each `BatchStrOutput` for that rid
   hits the deleted-state error path.

This is a regression of 71043b9dbb ("Revert parallel request lifecycle
tracking from #32588", #34160). Before the revert, #32588 handled this
correctly: `_discard_pending_req_states(obj, request_lifecycles)` dispatched
`AbortReq` for every rid whose state had `dispatched == True` **before**
removing the state. The revert deleted the `dispatched` markers and the
abort-then-remove ordering, leaving the orphan window. Presumably not covered
by CI because it requires killing a streaming client mid-generation.

(The `HEALTH_CHECK`-prefixed rid skip next to the error log is a different,
known race — unrelated, see #11925.)

Suggested minimal fix (verified in production, restores the pre-revert
invariant without reintroducing full lifecycle tracking):

1. In `generate_request`, treat cancellation separately and only discard
   state if the request was never dispatched:

```python
        dispatched = False
        try:
            ...
            self._send_one_request(tokenized_obj)
            dispatched = True
            async for response in self._wait_one_response(obj, request):
                yield response
        except (asyncio.CancelledError, GeneratorExit):
            # Client disconnect mid-request: keep the state of a dispatched
            # request so the delayed background abort still finds it; the
            # scheduler's abort echo deletes it cleanly. Discarding here
            # orphans the scheduler-side request, which then decodes to
            # max_tokens.
            if not dispatched:
                self._discard_pending_req_states(obj)
            raise
        except BaseException:
            self._discard_pending_req_states(obj)
            raise
```

2. Add a `force` flag to `abort_request` that bypasses the
   `rid not in self.rid_to_state` early-return, and pass `force=True` from
   `create_abort_task` (the scheduler's `abort_request` handler scans by rid
   prefix and no-ops unknown rids, so force-dispatching is safe — it just
   closes the window where the state was already deleted elsewhere):

```python
    def abort_request(self, rid: str = "", abort_all: bool = False, force: bool = False):
        if not abort_all and not rid:
            ...
            return
        if (
            not abort_all
            and not force
            and get_serving().tokenizer_worker_num == 1
            and rid not in self.rid_to_state
        ):
            return
```

With this patch: disconnect → decode stops within the 2s abort window, zero
error lines; normal streaming completions (`[DONE]`) unaffected.

### Reproduction

Any model; the bug is in the tokenizer-manager layer and is
hardware/model-independent.

1. Launch a server:

```bash
python -m sglang.launch_server --model <any-model> --port 30000
```

2. Start a long streaming generation, then kill the client mid-stream:

```bash
curl -sN http://127.0.0.1:30000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"<any-model>","messages":[{"role":"user","content":"Count from 1 to 5000, one number per line."}],"max_tokens":16000,"stream":true}' &
sleep 10 && kill -9 %1
```

**Actual**: `sglang:num_running_reqs` stays 1 and the request decodes until
`max_tokens`; the log floods with the message above (same rid, repeated many
times per second).

**Expected**: the request is aborted shortly after the disconnect (within the
2s background-abort window) and decode stops.

### Environment

- sglang `main` (regression introduced by 71043b9dbb / #34160, still present
  as of a1f9508dd4; no commit has touched `tokenizer_manager.py` since —
  `except BaseException` cleanup and the guard are at current lines ~825
  and ~1952)
- single GPU, TP=1, `--max-running-requests 2`; speculative decoding enabled
  (DSPARK) on our instance, but nothing here is spec-specific
- reproduced and root-caused on a fork whose `tokenizer_manager.py` is
  unmodified upstream code

### eug3 · 2026-08-30

### Additional production evidence + a working workaround (2x DGX Spark, Qwen3.8-Flash-Next-NVFP4)

We hit this exact bug in production today on **SGLang TP=2 across 2 DGX Spark nodes** (`Qwen3.8-Flash-Next-NVFP4`, speculative NEXTN, `--tokenizer-worker-num 1`). Sharing our numbers and a working mitigation in case it helps:

**Observed symptoms (identical to #36333 and #36876):**
- 3 zombie requests accumulated over hours (first at 11:58, then 13:02, then 14:41), each from a client that disconnected mid-stream.
- GPU pinned at ~95% for 2+ hours with **zero completed requests**; `sglang:num_running_reqs` stuck at 3.0.
- Log flooded with `Received output for rid=... but the state was deleted in TokenizerManager` — **~148,000 lines** sustained across hours.
- `POST /abort_request` returned 200 but had **no effect** (confirmed the `abort_request()` early-return: with `tokenizer_worker_num == 1` and `rid not in self.rid_to_state`, the `AbortReq` never reaches the scheduler — exactly as #36333 describes).
- New requests queued behind the zombies; spend/completion never logged for the zombies.

**Our workaround (patched `tokenizer_manager.py` in the running image, verified):**
1. `abort_request()`: removed the early-return when `rid not in self.rid_to_state` — always dispatch `AbortReq` to the scheduler (scheduler-side abort is safe for unknown rids; it scans queues and no-ops when absent).
2. `_handle_batch_output()`: when output arrives for an already-deleted state (orphan), proactively re-send `AbortReq(rid, abort_all=False)` to reap the scheduler-side task.

**Verification:** simulated client disconnect (kill curl 2s into a streaming responses call): `num_running_reqs` → 0 within 10s, GPU → 0%, subsequent requests unaffected. Concurrent test (3 streaming, 2 killed mid-stream, 1 completed): all slots reclaimed, the completed one finished normally. 60s observation window: zero growth of "state was deleted" after the initial reap.

**Note on #36876:** even with the AbortReq reaching the scheduler, `Scheduler.abort_request()` only sets `to_finish = FINISH_ABORT()` for requests found in `[running_batch, last_batch]` — during batch transitions (overlap scheduling / speculative decoding) a request can be in neither, leaving the same zombie. Our orphan-output reap (fix 2) happens to cover that window too, but the two fixes should ideally both land upstream. Happy to provide the full patch or a minimal repro script if useful.

### shashwat01kothari · 2026-09-08

**Validation datapoint for the suggested minimal fix: GB10 unified-memory ARM + 27B-NVFP4 + speculative decoding**

Applied the two-part minimal fix from the issue body (the `dispatched` flag + `force` flag on `abort_request`) as a read-only whole-file overlay on a dev build inside the broken window — `0.0.0.dev1+gf825d7293` (after `71043b9`, before `f478b2b`), confirmed broken pre-patch on this build. Nothing new to propose here; this is a datapoint from a topology I didn't see covered in this thread: **single NVIDIA GB10 (124608 MiB unified memory, ARM), TP=1, Qwen3.8-27B-NVFP4 with DFLASH speculative draft (incoai/Qwen3.8-27B-DFlash2)**, `--max-running-requests 8`.

**A/B method (reproducible):**

1. Baseline: unpatched, count occurrences of the exact signature line `Received output for rid='...' but the state was deleted in TokenizerManager.` across the full server log — **2692** (4B first, same signature on 27B).
2. Kill-burst: fire 3 in-flight streaming requests, confirm `num_reqs = 3` via `/get_load` at t0, `kill -9` all clients mid-stream (~114 SSE chunks each at kill), watch drain:
   - unpatched: `num_running_reqs` held at 3 until `max_tokens`
   - patched: **3 → 0 in ~5 s**
3. Functional: short `stop|length`-terminated generations complete normally with `[DONE]`; 3/3 soaks clean, **0 Traceback / 0 ERROR** in full-log scans.

**Result: 2692 → 0 error lines, zero zombie decode time, MRR slots released within the 2 s abort window.**

Two notes for triage:

- Our overlay is a strict subset of [#35255](https://github.com/sgl-project/sglang/pull/35255) (merged to main at `f478b2b`) — we don't have the chunked-prefill deferred-abort retry or the abort dedup, which is exactly why we plan to **drop the overlay entirely and rebuild from main ≥ `f478b2b`** rather than keep the local patch.
- The only thing this environment adds is confirmation that the fix holds **with the speculative-decoding draft path active on unified memory** — the disconnect/abort window behaves identically to the non-spec case above.

Happy to share the raw log excerpts and the overlay diff if useful for #35255 or the backport discussion.
