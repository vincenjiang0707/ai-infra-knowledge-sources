# [Issue #40926] [Bug] HiCache + hybrid (SSM/Mamba): failed cudaHostRegister on a secondary host pool aborts the whole instance, and the error path throws TypeError thereby hiding the real rc

source: https://github.com/sgl-project/sglang/issues/40926
state: open | updated: 2026-09-23T18:02:42Z
labels: 

## 正文

### Summary

On sglang `0.5.19` (torch `2.13.0+cu130`, CUDA 13.0, H20), starting a **hybrid SSM/Mamba** model
with `--enable-hierarchical-cache --hicache-storage-backend dynamic` fails during
`attach_hybrid_pool_to_unified_cache` and **kills the entire instance**.

Two coupled defects:

1. **`cudaHostRegister` failure is treated as fatal.** `alloc_with_host_register` raises, which
   aborts scheduler init for all TP ranks. But the failure only means "this host pool is not
   zero-copy registered" — and sglang's own non-zero-copy path (`_generic_page_get/_set`) is
   fully functional without registration. A missing acceleration is escalated into a full outage.
2. **The error path destroys its own diagnostic.** Inside the `raise`, `cudart.cudaGetErrorString(rc)`
   is called with a **plain `int`**, which raises `TypeError` on this torch build — so the real
   `rc`/`offset`/`size` are swallowed. Operators only see a bare `TypeError`.

Additionally, the failure **leaves a sticky CUDA error**, which then surfaces later at an unrelated
call site (`_create_sync_groups` → `all_gather_object` → `torch.zeros`), which made this
considerably harder to root-cause.

### Environment

- sglang `0.5.19`
- torch `2.13.0+cu130`, CUDA 13.0
- 8 × H20 (96 GiB) / 8 × H20-3e (141 GiB), driver `535.161.08`
- Model: `Qwen3.5-397B-A17B-FP8` (`Qwen3_5MoeForConditionalGeneration`, pool stack **KV + MAMBA**)
- Backend: `--hicache-storage-backend dynamic` with `interface_v1: 1` in the extra config
  (this selects the zero-copy page functions; the crash itself is in host-pool allocation and is
  not specific to any particular dynamic backend)
- Relevant flags: `--mamba-full-memory-ratio 0.37 --mamba-radix-cache-strategy extra_buffer_lazy
  --mamba-ssm-dtype bfloat16 --kv-cache-dtype fp8_e4m3 --hicache-mem-layout page_first_direct
  --hicache-io-backend direct --tp 8`

### Reproduction

```bash
python -m sglang.launch_server \
  --model-path <hybrid SSM/Mamba model, e.g. Qwen3.5-397B-A17B-FP8> \
  --tp-size 8 --trust-remote-code \
  --mem-fraction-static 0.80 \
  --enable-hierarchical-cache --hicache-ratio 1.0 \
  --hicache-storage-backend dynamic \
  --hicache-mem-layout page_first_direct \
  --hicache-io-backend direct \
  --mamba-full-memory-ratio 0.37 \
  --mamba-radix-cache-strategy extra_buffer_lazy \
  --mamba-ssm-dtype bfloat16 \
  --kv-cache-dtype fp8_e4m3 \
  --hicache-storage-backend-extra-config '{"backend_name":"...","module_path":"...","class_name":"...","interface_v1":1,...}'
```

Failures are **not deterministic per machine** — we observed the same config **succeed on a 96 GiB
box and fail on a 141 GiB box**, consistent with a pool-geometry / allocation-order dependence.

### Minimal evidence that this is the registration call

Instrumenting `_cuda_host_register` on the failing box (141 GiB) shows the KV pool registers fine
and a **secondary** pool is the one that fails:

```
reg#1 total=49676820480 (46.27GiB) granularity=3840        -> OK
reg#2 total=17765498880 (16.55GiB) granularity=11796480    -> FAILED rc=1 (cudaErrorInvalidValue) at offset=0
reg#3 total=623738880  ( 0.58GiB) granularity=414720       -> (never reached)
```

`offset=0`, the size is page aligned, and `chunk_limit=256 GiB` (i.e. a single call) — so this is
**not** an alignment, chunking, or size problem. The same three pools register fine in an
otherwise-idle process, so it is state/order dependent within the real init sequence.

### Minimal standalone reproduction of the underlying CUDA behaviour

The failure mode we traced back to is: calling `cudaHostRegister` on memory that is **already
pinned** returns `cudaErrorInvalidValue(1)` (not `cudaErrorHostMemoryAlreadyRegistered(712)`),
and leaves a sticky error that breaks the next unrelated CUDA call:

```python
import torch
cudart = torch.cuda.cudart()
print("baseline:", float((torch.ones(1024, device="cuda") * 2).sum()))   # works

SZ = 256 * 1024 * 1024
t = torch.empty(SZ, dtype=torch.uint8, pin_memory=True)                   # already pinned
rc = int(cudart.cudaHostRegister(t.data_ptr(), SZ, 0))
print("rc =", rc)                                                          # -> 1 (cudaErrorInvalidValue)

# now any CUDA op fails once:
torch.ones(1024, device="cuda") * 2     # -> AcceleratorError: CUDA error: invalid argument
```
Output on our box:
```
baseline: 2048.0
rc = 1
... torch.AcceleratorError: CUDA error: invalid argument
```

### Why we believe the `raise` is not the intended trade-off

`attach_storage_backend` explicitly keeps a **non-zero-copy** default and only opts into
zero-copy afterwards:

```python
self.page_get_func = self._generic_page_get        # default, works without registration
self.page_set_func = self._generic_page_set
if self.storage_backend_type in [...] or (
        self.storage_backend_type == "dynamic"
        and bool(self.storage_config.extra_config.get("interface_v1", 0))):
    self.page_get_func = self._page_get_zero_copy
    self.page_set_func = self._page_set_zero_copy
```

`_generic_page_get` stages through a dummy page and copies in
(`set_from_flat_data_page(...)`) — it does **not** require the host pool to be
`cudaHostRegister`-ed. So "registered" and "correct" are decoupled here: losing the registration
costs the zero-copy fast path, not correctness. Raising therefore converts a **performance
degradation** into an **instance-wide outage**.

The warning text in the raise ("*host buffer is not pinned and device transfers may silently
return stale data*") suggests the intent is to **prevent silent stale reads** — but (a) the
diagnostic it tries to emit is destroyed by the `cudaGetErrorString(int)` `TypeError`, and
(b) there is no degraded path, even though one exists and is safe.

### Suggested fix

**1. Do not `raise` on registration failure — degrade to the non-zero-copy path (main fix).**

```python
rc = int(cudart.cudaHostRegister(ptr, size, 0))
if rc != 0:
    logger.warning(
        "cudaHostRegister failed (rc=%d) at offset=%d size=%d; "
        "this host pool will not be used for zero-copy transfers",
        rc, offset, size,
    )
    _clear_sticky_cuda_error()   # see (2)
    return                        # fall back to the non-registered path
```

**2. Consume the sticky CUDA error before returning**, otherwise the very next collective
(`_create_sync_groups` → `all_gather_object` → `torch.zeros`) still fails. On this torch build a
subsequent CUDA call is enough to consume it, e.g.

```python
try:
    torch.cuda.synchronize()
except Exception:
    pass
```

**3. Fix the error path itself** — pass a `cudaError`, not a raw `int`
(and never let the diagnostic throw):

```python
from torch._C import _cudart
...
f"cudaHostRegister failed (rc={rc}, "
f"{cudart.cudaGetErrorString(_cudart.cudaError(rc))}) at offset={offset} ..."
```

**4. Consider an explicit escape hatch to disable host registration for CUDA.**
`ALLOC_MEMORY_FUNCS` only maps `npu`/`musa` to `alloc_with_pin_memory`;
on CUDA there is currently no way to opt out other than `SGLANG_HICACHE_HOST_REGISTER_CHUNK_GB`
(which only changes chunking — we verified setting it to `1` does **not** avoid this failure).

### Evidence that each proposed fix is sound (verified on the failing box)

**Claim 1 — host memory works without `cudaHostRegister` (so degrading is safe).**
Tested each in a fresh process (to avoid sticky-error cross-contamination):

```
mode=pin   (torch pin_memory, no cudaHostRegister at all)
  sum = 4096.0  (expect 4096.0)   is_pinned = True    RESULT: OK

mode=mmap  (plain unregistered host memory, is_pinned = False)
  sum = 4096.0                    RESULT: OK
```
⇒ Neither pinned nor unregistered host memory needs `cudaHostRegister` to move data to the GPU.
Losing the registration only removes the zero-copy fast path.

**Claim 2 — `cudaGetErrorString` needs a `cudaError`, not an `int`.**
```
cudaGetErrorString(1)                    -> TypeError: incompatible function arguments
cudaGetErrorString(_cudart.cudaError(1)) -> "invalid argument"        # correct
```

**Claim 3 — a failed registration leaves a sticky error; `synchronize()` clears it.**
```
baseline GPU op                                  -> 1024.0
cudaHostRegister(already-pinned, 64MiB)         -> rc=1
next GPU op                                     -> AcceleratorError: CUDA error: invalid argument
torch.cuda.synchronize()                        -> ok
GPU op after synchronize()                      -> 1024.0            # recovered
```

**Claim 4 — `cudaHostUnregister` also returns rc=1 while sticky** (so cleanup of a failed
registration cannot be relied upon to recover the state):
```
cudaHostUnregister(same buffer) -> cudaErrorInvalidValue(1)
```

### Why the existing unit tests did not catch this

`test/registered/unit/mem_cache/test_hicache_host_register.py` (added together with the chunked
registration work) covers the chunking / alignment / rollback logic thoroughly, but two gaps
explain why the real-world failure still slips through:

1. **The failure path is asserted as intended behaviour.** `test_registration_failure_rolls_back_prior_chunks`
   uses `assertRaisesRegex(RuntimeError, "offset=1073741824")` — i.e. the test *encodes* that a
   failed registration must raise. So the question "should it degrade instead of raising?" is a
   **design decision already locked in by a test**, not an oversight I am reporting as a bug.
   (Either way, I'd argue it is the wrong trade-off for the reasons in the Summary — but it is a
   design discussion, so I'm flagging it as such.)
2. **The fake `cudart` accepts an `int` for `cudaGetErrorString`, hiding the real signature:**
   ```python
   class _FakeCudart:
       def cudaGetErrorString(self, rc: int) -> str:      # permissive: accepts int
           return "injected error"
   ```
   The real object is
   `torch._C._cudart.cudart.cudaGetErrorString(arg0: torch._C._cudart.cudaError) -> str`
   and raises `TypeError` when given an `int`. Because the mock is permissive, the `TypeError`
   inside the `raise` can never surface in CI — yet that is precisely the error users see in the
   field, and it is what hides `rc`/`offset`/`size`.

### Affected code ownership (from `git log`, in case it helps routing)

- `_cuda_host_register` / `alloc_with_host_register` + `SGLANG_HICACHE_HOST_REGISTER_CHUNK_GB`
  came in with **#36798 "[HiCache] Align chunked CUDA host registrations"** (@HZY-Wade), which also
  added the unit test discussed above. That PR's own motivation mentions the same
  `invalid argument` failure mode we are hitting.
- The hybrid pool assembly path (`attach_hybrid_pool_to_unified_cache` /
  `build_hybrid_mamba_stack`) and `pool_host/base.py` are from the unified-memory HiCache work
  (@ch-wan).
- The failing line `attach_storage_backend` → `_create_sync_groups()` in
  `managers/cache_controller.py` is in the HiCache controller (@alphabetc1, @ch-wan).

Pinging @HZY-Wade and @ch-wan as the most likely owners of the affected code — apologies if this
is not your area, and feel free to redirect.

### Impact

- **Hybrid SSM/Mamba models** (which instantiate **multiple** host pools — KV + Mamba/SWA + conv)
  are much more exposed than single-pool attention models, because each additional pool is
  another chance to hit the failing registration. This makes HiCache L3 unusable for that model
  family on affected hardware, with a hard crash rather than a performance warning.
- For production this is a availability issue, and it is **not** diagnosable from the surfaced
  error alone.

### Notes / limitations of this report

- The design-intent reading above is inferred from docstrings, comments, the error text, and the
  existence of the non-zero-copy path — it is not confirmed by maintainers.
- We observed the behaviour on sglang `0.5.19` + torch `2.13.0+cu130`; we have **not** checked
  whether a newer sglang/torch already addresses it.
- We have **not** yet validated end-to-end that "degrade instead of raise" + "clear sticky error"
  yields a fully serving instance on the affected box. What *is* individually verified is:
  the registration failure and its `rc`, the destroyed diagnostic, the sticky error and its
  clearing, and that host memory does not need registration to be usable.
- The exact reason the *second* pool's registration fails is still not fully isolated. It is
  **not** page alignment (`offset=0`), **not** a single-call size limit (64 GiB registers fine
  standalone), **not** a cumulative-size cap (46 GiB then 16 GiB succeeds in a fresh process),
  and **not** chunking (`SGLANG_HICACHE_HOST_REGISTER_CHUNK_GB=1` does not avoid it). It appears
  to depend on process state / allocation order during real init.

### Edwardssss · 2026-09-23

Thanks for the write-up — it is the most complete description of this failure mode I have seen, and the four claims at the end are the right things to isolate.

Three open PRs already cover parts of this:

| PR | Files | What it does |
|---|---|---|
| [#38509](https://github.com/sgl-project/sglang/pull/38509) | `pool_host/common.py` | passes a `cudaError` to `cudaGetErrorString` instead of an `int` |
| [#39744](https://github.com/sgl-project/sglang/pull/39744) | `common.py`, `mha.py`, `mla.py`, `cache_controller.py` | on a failed chunk: halve and retry down to 4 KiB; raises only if 4 KiB also fails |
| [#38832](https://github.com/sgl-project/sglang/pull/38832) | `common.py` | idempotence, and tolerate `cudaErrorHostMemoryAlreadyRegistered` (712) per chunk |

I reproduced your minimal repro on a different stack, so it is not specific to your box — RTX 3060 Laptop / `sm_86` / WSL2, `torch 2.14.0+cu130`, CUDA 13.0, PyTorch only:

| claim | your box | this box |
|---|---|---|
| `cudaGetErrorString(1)` | `TypeError` | `TypeError`, same binding message |
| `cudaHostRegister` on already-pinned, 32 MiB | rc=1 | rc=1 (`cudaErrorInvalidValue`), `rc == 712` is false |
| next unrelated GPU op | fails | `CUDA error: invalid argument` |
| `synchronize()` then a GPU op | recovered | recovered |
| `cudaHostUnregister` while poisoned | rc=1 | rc=1 |

One distinction that decides which PR is relevant. Registering a range we already registered ourselves takes a different path, in the same process:

```
rc_first_register            = 0
rc_second_register_same_range = 712   # cudaErrorHostMemoryAlreadyRegistered
next op  ->  "part or all of the requested memory range is already mapped"
```

So 712 is the double-registration path that #38832 covers, while your failure — `cudaHostRegister` over memory pinned by a different owner — is rc=1 on both boxes. #38832 explicitly keeps raising on other codes, so it will not fix what you reported.

What looks unowned after those three is (1) degrading to the non-zero-copy path instead of aborting the instance, (2) consuming the sticky error before returning, and (4) an opt-out for CUDA. #39744 may well make your specific crash disappear (a 16.55 GiB chunk that fails at 4 GiB may succeed at 1 GiB), but the instance still dies whenever the halving bottoms out, and the sticky error has no owner. As your report notes, (1) is currently *specified* behaviour — `test_registration_failure_rolls_back_prior_chunks` asserts `RuntimeError` — so it is a design call rather than a plain bug fix.
