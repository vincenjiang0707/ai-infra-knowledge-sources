# [Issue #24656] [RFC] Agent-Aware KV Cache Phase 1 for Agentic Workloads

## 正文

## Summary

This RFC proposes Phase 1 of agent-aware KV cache support in SGLang.

The goal of this phase is to add a minimal, backward-compatible metadata path for agentic workloads so workflow information can flow from the API layer into runtime requests and KV cache nodes, and optionally affect radix cache eviction.

This is intentionally a foundation/prototype phase, not a full workflow-aware cache system.

## Motivation

Current KV cache eviction policies such as LRU, LFU, and SLRU treat requests mostly independently. That works well for standard chat/completion workloads, but it misses reuse opportunities in agentic workflows, where requests often share:

- repeated prompt prefixes across planner/tool/worker steps
- parent/child step relationships
- short-term reuse after tool calls
- workflow-level TTL or reuse intent

Without workflow-aware signals, cache entries that are likely to be reused by upcoming steps may be evicted too early.

## Proposal

Phase 1 introduces:

- an optional `agent_hints` field in OpenAI-compatible requests
- propagation of `agent_hints` through the internal request pipeline
- lightweight workflow DAG tracking in the scheduler
- radix cache node annotation with workflow metadata
- a new optional radix eviction policy: `agent_aware`

Initial `agent_hints` fields include:

- `workflow_id`
- `agent_id`
- `step_id`
- `step_index`
- `total_steps`
- `parent_step_id`
- `children_step_ids`
- `tool_name`
- `expected_tool_duration_ms`
- `cache_ttl_ms`
- `shared_prefix_hash`
- `reuse_hint`

## Scope

Phase 1 is intended to cover:

- request schema support
- metadata plumbing
- scheduler-side workflow tracking
- cache node metadata annotation
- a prototype workflow-aware eviction strategy

Phase 1 does **not** attempt to fully solve:

- `shared_prefix_hash`-driven reuse
- HiCache / storage-layer metadata inheritance
- cross-process workflow coordination
- production-tuned scoring for all agent topologies

## Backward Compatibility

- `agent_hints` is optional
- existing clients do not need to change
- existing eviction policies continue to work unchanged
- the new behavior is opt-in

## Testing

Expected validation for Phase 1:

- schema tests for `agent_hints`
- propagation tests from API request to internal request objects
- workflow DAG tests for step registration and distance computation
- radix cache node annotation tests
- eviction ordering tests for `agent_aware`
- backward-compat tests when `agent_hints` is omitted

How to Run
Start SGLang with the new eviction policy:
```
curl http://127.0.0.1:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "messages": [{"role": "user", "content": "hello"}],
    "agent_hints": {
      "workflow_id": "wf-1",
      "agent_id": "planner",
      "step_id": "step-1",
      "children_step_ids": ["step-2"],
      "cache_ttl_ms": 60000,
      "reuse_hint": "keep"
    }
  }'
```

Prototype validation already exists with dedicated unit tests for the metadata path.

## Open Questions

- Should `shared_prefix_hash` remain a hint, or become a stronger reuse primitive in a later phase?
- Should TTL be a hard protection or only a ranking signal?
- How should workflow-aware metadata eventually interact with HiCache and storage backends?
- What observability should be added next: workflow hit rate, protected eviction count, step-distance metrics?

### lawrence-harmonic · 2026-05-22

We use session-aware caching internally. We find that TTL is not a solution, because states from different sessions should be treated with equal TTL a priori, but a posteriori we may find that the newer state is less important (superseded within its session). This proves that no a priori prioritization mechanism can work; only a posteriori priority updates.

Here is the design we implemented, which allows running 100+ concurrent Qwen 3.5 35B agents on 1 GPU:

```bash
> # Session-aware cache in SGLang
> 
> ## Workload Assumptions
> 
> The workload we are optimizing for is as follows:
> 
> * N RL workers, each running 1 agent trajectory at a time, i.e. \`while(true) { do\_one\_rollout() }\`.
> 
> * Agent trajectories are not necessarily extend-only (i.e. they may revise the prompt, perform compaction, etc), but they should have a high cache hit rate assuming sticky routing.
> 
> * Within a trajectory, once prompt M is prefilled, then prompt M-1 no longer needs to be cached.
> 
> * Overall, if agent K has started, then prompts from agents 1..K-1 no longer need to be cached.
> 
> * Agents occasionally think for a long time, or make a slow tool call, during which other workers finish many trajectories.
> 
> ## The problem with LRU eviction
> 
> We will illustrate the issue using linear attention, where the issue is more severe.
> 
> Full attention caches the whole prefix, with a small amount of state per token. Thus, if AB is cached then so is A. Linear attention instead caches a larger fixed-size state per prompt. That means that caching A has an additional cost over caching AB. If we don't intend to submit any requests that start with A and not AB, then this is wasteful.
> 
> In our workload above, the only linear attention states that we actually need cached are N (the last state from each session). But if a turn is slow, then the session's last state can be preempted in the LRU by much more than N states from other sessions. This leads to unnecessary evictions.
> 
> The problem also exists in full attention, to a lesser degree: the only tokens that we need cached are N \* context\_length. But if much more than N trajectories run while waiting for a slow turn, then that session's tokens will be preempted in the LRU by much more than N \* context\_length tokens from other sessions.
> 
> ## Proposed solution
> 
> Make the cache in sglang session-aware; that is, support session ID on requests, and expire (i.e. either evict or deprioritize) states that are not referenced by either:
> 
> * the latest request for any given session ID
> 
> * a request without a session ID
> 
> Handle all components (full attention, linear attention, unified). Handle both the device (L1) and host (L2), but not storage (L3), which lacks the necessary eviction / cache management APIs as it outsources the cache management logic.
> 
> ## Related work
> 
> The desired semantics are the same as in https://github.com/sgl-project/sglang/pull/19171. However, that PR implements a purely-device-side approach, which bypasses the cache; its implementation is more like suspending active requests for later extension, rather than actually caching them. In our requirements, we want to support using host memory (L2), to support higher concurrency workloads. Unlike \#19171, latency is not a concern.
```

### lawrence-harmonic · 2026-05-28

> Would you be open to sharing more details on how you handle the priority updates in the cache when a new session_id request comes in?

Hi @stmatengss ,

I will look into whether it's possible to share some code. The basic idea is this: instead of a linked list, we use a priority heap with priority key something like (ttl_status, session_aware_priority, last_used_timestamp), where ttl_status is something like {expired past max ttl, none, more recent than min ttl}. Then session_aware_priority is used when nodes between sessions have equal ttl_status.

To update session_aware_priority, we track on each node a ref count or a set of owning sessions. Whenever a session receives a request, we move its reference from its existing node to the new node. When a node reaches 0 references, we set session_aware_priority to low.

> If the agent is Claude Code, it would theoretically spawn N sub-agents, and in the current implementation Claude Code doesn't carry any agent-hint-related fields. This would result in multiple concurrent active requests on the same session. Do you have any solution for this kind of case?

Hi @attack204 ,

This is a good point. The ideal solution would be to change the harness to use sessions or agent hints. However, we may have a black box harness (e.g. Claude Code) for which this is not possible. There are other reasons to not uniformly deprioritize non-last sessions: for example, users are more likely to edit recent messages.

We could keep LRU within sessions; then we still have the LRU fairness issue between subagents in a harness instance, but at least we still avoid the LRU fairness issue between harness instances.

This could be achieved by generalizing session_aware_priority to be a within-session LRU rank. For example, suppose we have instances A, B, C with request order [A1, B1, B2, A2, C1, C2, C3]. In this case, A2 and A1 would have a within-session rank of 0 and 1 respectively (most recent and second-most recent for A), and C1 would have rank 2 (third most recent for C). Thus, C1 would have lower priority than A1 even though C1 is more recent.

There might be a better heuristic for SSMs (e.g. Qwen 3.5) specifically. We could consider that any SSM eviction reclaims a constant amount of memory despite representing varying amount of tokens. Then we could consider that for example, if we have a token sequence with SSM states A, B, C at indices 30, 70, 120 respectively, then we could think of states A, B, C as costing 30, 40, 50 tokens respectively to evict. If we evict A, then the cost to evict B afterwards becomes 70. We could thus consider a heurstic that takes into account both this cost in addition to recency (LRU).
