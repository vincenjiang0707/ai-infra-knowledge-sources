# [PR #40838] [quant] fix: accept a pre-quantized input in FlashInfer's block-FP8 GEMM

state: open | updated: 2026-09-23T03:50:59Z

## 正文

## Motivation

**Problem:** on Blackwell GPUs, a block-FP8 linear layer crashes if its input is already FP8-quantized.

**Background:** a block-FP8 linear layer usually receives a bf16 input and quantizes it to FP8 itself before the GEMM. `Fp8LinearMethod.apply` also accepts an input that the caller already quantized, as an `(fp8 q, scales)` tuple. In that case the layer skips its own quantization and passes the pair to the GEMM runner as `input` / `input_scale`. This lets a producer kernel fuse the quantization into its own epilogue and save a full read/write pass over the activation. For example:
- a fused `silu_and_mul` + quant kernel;
- a fused norm/modulation + quant kernel;
- a tensor-parallel all-gather that moves FP8 rows instead of bf16, half the bytes.

**What breaks:** the Triton, torch and SGLang CUTLASS runners all accept `input_scale`. The FlashInfer groupwise runner (`flashinfer_gemm_w8a8_block_fp8_linear_with_fallback`) starts with `assert input_scale is None`. Auto dispatch picks this runner on every Blackwell GPU with FlashInfer installed, SM100/103 and SM120 alike. So on Blackwell, a pre-quantized input fails the assert, and none of the fusions above can be used there.

**Impact of this PR:** no code in `main` passes a block-FP8 tuple on Blackwell today, so no current behavior changes. This PR makes the FlashInfer runner accept the same input the other runners already accept, so such fusions can be added.

## Modifications

`flashinfer_gemm_w8a8_block_fp8_linear_with_fallback` in `python/sglang/srt/layers/quantization/fp8_utils.py`:
- When `input_scale` is given, it uses `input` (which must be `float8_e4m3fn`) and `input_scale` directly instead of calling `sglang_per_token_group_quant_fp8`.
- `input_scale` must have shape `(m, k // block_k)` in fp32. It can be row-major or column-major. It is laid out the way each backend reads it:
  - CUTLASS (`scale_major_mode="MN"`): transposed to a contiguous `(k // block_k, m)`, the same path the runner's own quantizer output takes.
  - TRTLLM: column-major `(m, k // block_k)`, the layout the runner requests from its own quantizer with `column_major_scales=True`.
  - TRTLLM's Triton fallback (K < 256): row-major, which is what `triton_w8a8_block_fp8_linear` expects for a pre-quantized input.
- The output is bf16, matching the Triton, torch and SGLang CUTLASS runners for a pre-quantized input.
- A wrong dtype or scale shape now fails with an explicit message.
- The path without `input_scale` is unchanged.

## Accuracy Tests

The requirement is bit-exactness. A layer given `sglang_per_token_group_quant_fp8(x, 128)` must return exactly the bits it returns for `x`, since that is the quantization the runner does internally.

- `test_fp8_blockwise_linear_backends.py::TestFp8BlockwisePrequantizedInput` (GPU) checks `torch.equal(layer((q, s)), layer(x))` with both row-major and column-major `s`, over the existing `FP8_BLOCK_SHAPES`, on `flashinfer_cutlass` (SM100/SM120) and `flashinfer_trtllm` (SM100).
- `test_flashinfer_trtllm_fp8_fallback.py::TestFlashinferPrequantizedInput` (CPU, mocked GEMMs) checks four things:
  - the scale layout each backend receives;
  - that the quantizer is not called;
  - the Triton fallback for K < 256;
  - that a wrong scale shape is rejected.

Without the change, all of the new tests fail on the `assert input_scale is None`.

Results on an RTX 5090 (SM120): both files pass (15 passed, 23 subtests), and the existing `triton` and `cutlass` backend tests are unaffected. I had no SM100 GPU, so the TRTLLM path is covered only by the CPU tests here. The GPU test for it will run on the B200 CI runner.

## Speed Tests and Profiling

This PR has no speed impact: no existing call path changes. It enables fusions that skip a separate quantization pass.
