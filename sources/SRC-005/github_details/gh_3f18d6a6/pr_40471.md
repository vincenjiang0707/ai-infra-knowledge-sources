# [PR #40471] fix(dsv4): ship the fp8 unified_kv rope pool through the direct external linker

state: open | updated: 2026-09-23T06:17:50Z

## 正文

## Problem

Under `SGLANG_DSV4_UNIFIED_KV_FP8=1` a unified_kv row is **two parallel pools** —
`unified_kv_pool.kv_buffer` (512 B packed fp8 nope) and `unified_kv_pool.kv_buffer_rope`
(128 B bf16 rope) — and one row index addresses both.

`_build_deepseek_v4_device_pool_group()` registers the compressed regions through
`_dsv4_compressed_region_buffers()` → `unified_region_buffers()`, which returns **the nope
pool only**. The direct external linker therefore offloads and restores 512 of every 640
bytes, and the rope half of a restored row keeps whatever the slot last held.

HiCache already ships the sibling (`_dsv4_rope_sibling` / `_build_dsv4_rope_entry` in
`hybrid_pool_assembler.py`); this is the linker-side mirror of it. It is backend-agnostic —
`umbp_direct_linker.py` and `mooncake_direct_linker.py` both resolve through
`resolve_hybrid_device_pool_group()`.

## Why nothing catches it

`DevicePoolEntry` derives its row stride and page size from the buffers it is handed and has
no view of the logical row width, so a short row is not a crash — it is wrong output. That is
what the pool's own docstring on `unified_rope_region_buffers()` warns about.

There is also no full-resolution fallback to mask it. With the unified layout the SWA pool is
a per-request ring, so `unified_cache_linker.py` sets `_skip_swa` and tombstones the range as
`swa_evicted_seqlen`. A linker-restored prefix therefore exists *only* as compressed c4/c128
rows, and `unified_kv_kernels/runtime.py` passes `unified_kv_rope` to both paged decode and
paged prefill as the prefix pool.

## Evidence

A plain before/after A/B **cannot** see this: `/flush_cache` frees device rows without
overwriting them, so a nope-only restore lands on rope that is still correct for exactly
those tokens. gsm8k accuracy was unchanged across five configurations up to 81.7% linker
exposure, including one that wrote 560k tokens of unrelated KV between the flushes.

To get a real signal, fill the compressed rope rows with a marker at flush time and count how
many still carry it after the next pass. DeepSeek-V4-Pro, MI355X (gfx950), TP8 +
DP-attention, `--page-size 256`, EAGLE MTP, UMBP direct external linker; gsm8k, 200
questions, temperature 0, warm → flush → measure:

| pass | marker written at flush | before this PR | with this PR |
|---|---|---:|---:|
| 1 (cold) | none | 0.965 | 0.975 |
| 2 | rope pool | **0.775** | **0.955** |
| 3 | rope + nope pools | 0.825 | 0.975 |

Rope rows written during pass 2, mean per rank, of 181,136,962: **67,465 before** vs
**268,858 with this PR**. Without the fix only the extend fraction is written — 99.96% of
rows keep the marker, and the model reads them.

## Test

`test_unified_deepseek_v4_fp8_ships_the_rope_half` fails on `main` (and only that test) and
passes with the fix. The existing bf16 unified test gains an explicit
`unified_rope_region_buffers` stub returning `None`, pinning that the bf16 path ships exactly
what it did before. `test_linker_pool_assembler.py`: 10 passed before, 11 passed after.

## Scope

`unified_rope_region_buffers()` returns `None` on every non-fp8 layout, so bf16 unified and
all other layouts are untouched. For fp8 unified_kv the linker now moves the rope half as
well: 512 → 640 B per row transferred.
