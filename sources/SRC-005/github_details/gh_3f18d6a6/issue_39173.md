### Describe the bug

On DeepSeek-V4.1-Flash (an Engram model), enabling DSpark compact ragged verify via a profiled SPS cost table makes the engine die **deterministically during CUDA-graph capture, on every rank**:

```
AssertionError: engram target-verify expects one equal block per request, got 42 tokens for 8 requests of 6
```

Removing the table (so the planner stays on the verify-all / static schedule) boots and serves fine, so weights, TP4/EP4, FP8 KV cache and the RDMA transport are all healthy.

**Suspected root cause.** The capture batch seems to get the wrong slot count. `DecodeCudaGraphRunner._ragged_capture_slots()` returns `min(num_tokens, self.max_bs)` (`model_executor/runner/decode_cuda_graph_runner.py:667-670`), while the per-tier token bucket is `bs * captured_req_width` (`_build_ragged_verify_token_buckets`, same file, line 569). For the tier `num_tokens = 42` (bs=7, width=6) with `max_bs = 8` this selects **8 slots**, so `build_capture_verify_lens(num_tokens=42, num_slots=8, num_draft_tokens=6)` returns `[6,6,5,5,5,5,5,5]` — 8 rows of unequal length summing to 42. `EngramHasher.forward()`'s target-verify branch (`srt/layers/engram.py:291-298`) requires one equal block per request (`num_tokens == bs * block` → `42 != 8*6`), so the capture batch is rejected. Only the largest tier (bs == max_bs → 48 tokens / 8 slots) survives; every smaller tier aborts. Dense-layout consumers elsewhere handle ragged layouts through `RaggedVerifyLayout.padded_to_bucket(padded_bs, cap)`, but the Engram hasher reads the raw `input_ids.shape[0]` / `req_pool_indices.shape[0]` pair before any padding.

The test escape hatch `SGLANG_TEST_RAGGED_VERIFY_FORCE_UNIFORM_CAPTURE=1` avoids the capture assertion but then dies on the first request (second traceback below), so compact ragged verify currently appears unusable for this model.

### 200lz · 2026-09-13

I reproduced the capture geometry mismatch on upstream main `18cc55dc0b2f6a5133bdde61f0ac8c02c8e3d17d` and opened #39257 with a narrow fix and regression coverage.

For `42` tokens, captured width `6`, and `max_bs=8`, current main constructs:

```text
[6, 6, 5, 5, 5, 5, 5, 5]
```

while the graph tier is generated by seven requests × six tokens and should capture:

```text
[6, 6, 6, 6, 6, 6, 6]
```

The fix derives the capture request slots from the captured request width, retaining the existing ragged layout, replay padding, and admission behavior. It also covers the historical 192-token case from #34384 / #34636.

I also investigated the later metadata `copy_()` failure separately. On the corrected normal compact-ragged path, DSV4 request/sequence metadata uses exact-range aliases and the existing copy succeeds. The overlapping-copy failure is reproducible with the force-uniform control, where request-keyed capture metadata is replayed using token-keyed graph keys. No metadata workaround is included in #39257.

I have not run the full DeepSeek-V4.1/Engram model or the reporter's TP4/EP4 DGX Spark configuration, so #39257 addresses the shared capture-geometry defect rather than claiming the entire issue is resolved.

PR: #39257

### masquerator-coder · 2026-09-19

**Reproduced on TP3/EP3 (3×DGX Spark), `--speculative-dspark-block-size 3`; capture now works with #39257 + #31016, the first request does not**

Environment: 3× DGX Spark (GB10, SM121), TP=3 / EP=3, `lmsysorg/sglang:dev-dsv41` overlay built from
commit `da64c5cb` (Sep 11 2026), DeepSeek-V4.1-Flash, FP8 KV cache, RoCE over a 3-node CX7 triangle
(no switch), `--speculative-dspark-block-size 3` (verify window 4), SPS table profiled with
`dspark_sps_profiler all --max-batch-size 4` (manifest: `verify_num_draft_tokens: 4`).

Findings, in the order they hit:

1. **The capture abort from this issue reproduces, with the same geometry.** At the `bs=3` tier the
   capture batch is 12 tokens while `_ragged_capture_slots()` returns `min(12, max_bs=4) = 4` rows,
   so `build_capture_verify_lens(12, 4, 4)` yields `[3,3,3,3]` while `spec_info.draft_token_num = 4`:

   ```
   AssertionError: engram target-verify expects one equal block per request, got 12 tokens for 4 requests of 4
   ```

   The next consumer to fail (once the engram assert is relaxed) is `dsv41_sparse.token_req_indices`:
   `repeat_interleave: Invalid output_size, expected 16 but got 12` — one root cause, several consumers.

2. **`--speculative-dspark-align-verify-tokens-to-graph-tier` is not involved.** With the flag
   explicitly off (`DSPARK_ALIGN_VERIFY_TO_TIER=0`; `server_args` shows
   `speculative_dspark_align_verify_tokens_to_graph_tier: False`) the identical assertion fires.
   Worth recording, because the flag is the natural first suspect.

3. **With #39257 + #31016 applied (as source bind-mounts, image not rebuilt) capture and warm-up both
   succeed:**

   ```
   Capture target verify CUDA graph end. elapsed=2.10 s, mem usage=0.50 GB
   DSpark draft proposal (greedy + sampling) folded into the draft cuda graph.
   Capture draft verify CUDA graph end. elapsed=2.85 s
   Warm-up done in 17s (4 prompt sizes + one batch of 4)
   ```

   Without #31016 the draft-verify capture dies in the confidence head —
   `Sizes of tensors must match except in dimension 2. Expected size 5 but got size 4`
   (`deepseek_v4_dspark.compute_confidence` → `dspark.py:441 torch.cat`) — because the checkpoint's
   baked gamma differs from the CLI `--speculative-dspark-block-size`.

4. **The first real request then dies on the trimmed runtime layout** — i.e. the "second traceback"
   mentioned in the issue body, and it is the SPS budget working as designed (3 requests verifying
   8 tokens instead of 12):

   ```
   AssertionError: engram target-verify expects one equal block per request, got 8 tokens for 3 requests of 4
     dspark_worker_v2.py:792 _forward_decode
       -> dspark_verify.py:422 run_compact -> :391 _run_ragged -> :305 _forward_prepared_verify
         -> model_runner.forward -> eager_runner.execute
           -> deepseek_v4.py:3650 _forward_layers_hc_pre_from_prev -> engram.py:296
   ```

   So after #39257 the compact path is one step from working: it needs the engram hasher
   (`engram.py:296`) **and** the low-ratio / `token_req_indices` metadata to consume
   `spec_info.ragged_verify_layout.verify_lens` instead of assuming `bs * draft_token_num`;
   ragged layouts are currently only honoured by consumers that go through `RaggedVerifyLayout` /
   `padded_to_bucket(...)`. Relaxing only the engram assert just moves the same failure to the
   attention metadata.

We can reproduce in ~15 min per iteration (bind-mount patched sources, restart, first request) and are
happy to test a patch for the engram/metadata side.

Thanks for the detailed reproduction and follow-up. [PR #40567](https://github.com/sgl-project/sglang/pull/40567) adds ragged Engram hashing and V4.1 token-to-request mapping, including empty rows and CUDA Graph padding. These changes target the first-request Engram assertion and token_req_indices failure reported after the capture geometry is corrected. It also refreshes the graph-staged extend_start_loc, with focused CPU/CUDA regression tests for changing ragged layouts and graph replay.
The initial capture-slot geometry is tracked separately in [PR #39257](https://github.com/sgl-project/sglang/pull/39257). If you can try PR #40567 with the capture fixes in your TP3/EP3 or TP4/EP4 setup, your results would be very helpful.
