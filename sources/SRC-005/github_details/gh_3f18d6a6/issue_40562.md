## Describe the bug

With component offload enabled for the DiT, text encoder, and VAE, Wan2.2-T2V-A14B fails during **synthetic server warmup request finalization** on a single NVIDIA L20.

The first OOM is in `ComponentOffloadStrategy.finish_request()` → `prepare_for_use()` → `module.to(device)`. Model loading and the warmup pipeline body have already completed. The server then retries smaller synthetic warmups, which also fail after the first failed reload leaves almost no free device memory.

On the same L20 checkout and with the same component-residency configuration, adding `--warmup-mode off` allows model loading and server startup to complete without OOM. No generation request was run in that control, so this comparison isolates the startup failure to the server-warmup path but does not establish that a full generation fits. We would like to keep warmup enabled while retaining the memory savings of component offload.

### Expected behavior

Warmup finalization should respect the available device-memory budget when restoring preferred components. A warmup request that reaches finalization under sequential component offload should not require a larger simultaneous weight footprint just to finish. If optional preloading cannot fit, the components should remain offloaded and be loaded when needed.

### Actual behavior and logs

The first L20 warmup request reaches request finalization before failing. The server retries with fewer frames, but the failed `module.to()` has no rollback. Later retries therefore fail in text-encoder execution and then enter the same failing `finish_request()` path again. These are subsequent failures; the stack above identifies the initial warmup OOM.

The loaded component sizes reported in the same run are 21.16 GB for the text encoder, 26.62 GB for each transformer, and 0.47 GB for the VAE. Reloading preferred components at request end creates a simultaneous weight footprint that does not fit the L20's 44.39 GiB allocator-reported capacity, even though sequential component offload is configured.

### Investigation

The component-offload strategy reloads a component during `finish_request()` when both `preferred` and `state.batch_is_warmup` are true. The manager processes request-end components in a single loop, so this can interleave loading preferred components with releasing other components. There is also a separate `keep_ready_after_warmup` path.

Our hypothesis is that request-end preloading creates a larger simultaneous weight footprint than the sequential offload execution requires. We have not yet captured a per-component device-residency snapshot at the allocation failure, so the exact overlapping components remain to be confirmed.

Setting both DiT `preferred_ready_after_request` declarations to `False` did not eliminate the failure. This does not disable every request-end preference: text encoding has its own preference, and the manager has a fallback when there are no explicitly preferred uses.

On September 21, 2026, source inspection of upstream `main` still showed the warmup/preferred reload branch and the single-pass request-end loop:

- [Component offload strategies](https://github.com/sgl-project/sglang/blob/main/python/sglang/multimodal_gen/runtime/managers/memory_managers/component_residency_strategies.py)
- [Component residency manager](https://github.com/sgl-project/sglang/blob/main/python/sglang/multimodal_gen/runtime/managers/memory_managers/component_manager.py)

The CUDA failure is reproduced on the latest release, v0.5.20 (`94602c9c2b7cbdb8efd5c52802dac6a1c180089e`).

Could request-end preloading be made memory-aware, with an option to leave component-offloaded modules on the CPU after warmup? Releasing unneeded components before any optional preload would address ordering, but the total preferred set would also need to fit the budget. Cleanup after a failed preload should leave the pipeline usable.

Related work found during our search: #37918 and #36703 concern residency planning, but we have not verified that either resolves this case. #34772 concerns CPU-offload decisions being lost during component loading, which appears to be a different failure stage.

## Reproduction

Run on a single NVIDIA L20:

```bash
sglang serve \
  --model-path /path/to/Wan2.2-T2V-A14B-Diffusers \
  --component-residency \
    dit=component-offload \
    text_encoder=component-offload \
    vae=component-offload
```

Model: `Wan-AI/Wan2.2-T2V-A14B-Diffusers`. In this command, `sglang serve` selects `warmup_mode=server`; FSDP and torch compilation are disabled.

1. Start the server and observe the synthetic warmup failure above. No external generation request is needed to trigger this first OOM.
2. As a comparison, restart with `--warmup-mode off` and otherwise identical settings. The model and worker initialize successfully and the server reaches `Application startup complete` without OOM. No generation request was submitted in this control run.
