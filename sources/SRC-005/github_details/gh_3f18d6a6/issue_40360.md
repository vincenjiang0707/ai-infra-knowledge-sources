## Summary

`LMCRadixCache` does not implement `release_aborted_request`, so aborts fall through to the
no-op default in `BasePrefixCache` (`base_prefix_cache.py:371`):
```python
def release_aborted_request(self, handle: CacheRequestHandle) -> None:
    """Release attempt state; caches without prefetch state have nothing to drop."""
```

Nothing raises, so the gap is silent.

In MP mode, `LMCRadixCache.match_prefix` opens an LMCache session and may leave a pending
lookup holding daemon-side read locks; `init_load_back` is what consumes them. A request
aborted between those two points leaks, for the lifetime of the server:

- `_mp_load_back_markers[rid]`, recorded in `_mp_match_prefix` (`lmc_radix_cache.py:231`) and
  consumed in `init_load_back` (`:303`);
- the connector-side pending lookup;
- daemon-side read locks, which block eviction of the entries they cover;
- an LMCache session that never receives `END_SESSION`.

Flushing the cache does not recover any of it. `LMCRadixCache.reset` (`lmc_radix_cache.py:173`)
clears the local marker dict but never calls `end_session`, so the daemon-side session and its
locks survive until the process exits.

The straightforward fix — calling `end_session(handle.rid)` from `release_aborted_request` — is
**not safe in general**, and the abort hook also cannot simply be moved later, because another
backend depends on the current ordering. Details below.

Related closed PR (not merged): #40334, closed by me after finding the ordering problem.

## Analysis

### Why the obvious fix is unsafe

On current main there are thirteen places where an abort reaches the cache layer: ten via
`Scheduler._release_aborted_request` (`scheduler.py:3239`, `:3249`, `:3257`, `:3340`, `:3556`,
`:5429`, `:5456`, `:5476`, and `disaggregation/prefill.py:1129`, `:1555`) and three that call
`finish(handle, CacheRequestOutcome.ABORT)` directly (`prefill.py:1170` in
`handle_bootstrap_failure`'s caller path, `:1201` in `handle_bootstrap_failure`, and
`decode_hicache_mixin.py:190` in `_clean_hicache_prefetch_resources`).

Four of them (`scheduler.py:3239`, `:3249`, `:3257`, `:3340` — retire-unadmitted, queue-limit
rejection, and priority preemption) never reach `cache_finished_req` at all, so for those the
abort hook is the only possible cleanup point. `prefill.py:1201` performs no KV release either.

The rest do reach it via `release_kv_cache` (`common.py:280`). Most notably the
disaggregated-decode waiting-queue abort passes the default `is_insert=True`:
```text
scheduler.py:5429   _release_aborted_request(req)
scheduler.py:5438   release_kv_cache(req, self.tree_cache)      # is_insert=True
                      -> LMCRadixCache.cache_finished_req
                         -> store_kv       (lmc_radix_cache.py:489)
                         -> end_session    (lmc_radix_cache.py:493)
```

Adding `end_session` to the abort hook turns that into `end_session -> store_kv -> end_session`.

That relies on the external LMCache implementation treating `end_session` as idempotent.
SGLang declares no `lmcache` dependency at all (it is not in `python/pyproject.toml`), so that
contract is unpinned and unverifiable from this repository. It also permits a STORE after the
session has been closed — and MP `store_kv` blocks until the daemon signals, per the comment at
`lmc_radix_cache.py:490` — so the failure mode is not necessarily a silent no-op.

Tracking active sessions inside SGLang would prevent the second call, but cannot fix the
ordering: the first `end_session` still precedes the STORE.

### Why the abort hook cannot simply be moved later

Backends differ in whether they tolerate running abort cleanup after `cache_finished_req`:

- `UnifiedRadixCache` does override `cache_finished_req` (`unified_radix_cache.py:953`), but it
  does not touch the prefetch, linker or buffer-pipeline state cleaned by its
  `release_aborted_request` (`:2587`) — order-independent.
- `FlexKVRadixCache` **requires the current order**. Its `cache_finished_req`
  (`flexkv_radix_cache.py:388`) may `inc_lock_ref` a source node, launch an async store on
  `store_stream`, and register it:
  ```python
  # flexkv_radix_cache.py:447
  with self._node_lock:
      self._inflight_store_nodes[req.cache_request_handle] = new_last_node
  ```
  while `release_aborted_request` (`:488`) pops that registration and releases the lock:
  ```python
  with self._node_lock:
      node = self._inflight_store_nodes.pop(handle, None)
  if node is not None:
      self.dec_lock_ref(node)
  ```
  Running cleanup afterwards would drop the lock of a store still in flight, letting eviction
  free its source slots — exactly what `FlexKVRadixCache.evict` (`:454`) guards against with
  `_drain_completed_stores()` and `store_stream.synchronize()`.

So the hook must run before `cache_finished_req` for FlexKV, and would need to run after it for
LMCache.

### The ordering is already inconsistent today

FlexKV's requirement is not merely at risk of being broken by a future change — it is already
violated. Most sites call the abort hook first, e.g. `Scheduler.abort_chunked_req`:
```text
scheduler.py:3556   _release_aborted_request(req)
scheduler.py:3557   release_kv_cache(req, self.tree_cache, is_insert=False)
```

but two sites in `disaggregation/prefill.py` reverse it:
```text
prefill.py:1128   release_kv_cache(req, self.tree_cache)   # -> cache_finished_req, is_insert=True
prefill.py:1129   self._release_aborted_request(req)

prefill.py:1170   self.tree_cache.finish(req.cache_request_handle, CacheRequestOutcome.ABORT)
prefill.py:1172   release_kv_cache(req, self.tree_cache, is_insert=False)   # under holds_kv
```

With FlexKV as the tree cache, an abort on the `prefill.py:1128` path runs `cache_finished_req`
first — possibly registering an in-flight store in `_inflight_store_nodes` — and only then runs
`release_aborted_request`, which pops the registration and `dec_lock_ref`s a node whose store
has not completed. That is the sequence `evict()` is written to prevent.

Because the ordering is implicit — established by the order of two adjacent statements at each
of thirteen call sites, with nothing asserting it — there is no mechanism that keeps it correct.

## Design gap

The ordering conflict is a symptom of a broader lifecycle gap.

`release_aborted_request(handle)` is attempt-cancellation cleanup: it releases pending lookup,
prefetch, and other transient work left by an aborted attempt. Its docstring describes it that
way, and FlexKV's implementation matches — it cancels, and notifies nothing externally.
Cancellation does not mean the request has reached its final lifecycle boundary.

A hook with the right name and the right signature already exists:
```python
# base_prefix_cache.py:374
def finish(self, handle: CacheRequestHandle, outcome: CacheRequestOutcome) -> None:
    """Finish an attempt without cancelling successful asynchronous cache work."""
    if outcome != CacheRequestOutcome.SUCCESS:
        self.release_aborted_request(handle)
```

However, it is not currently used as a terminal lifecycle hook. `_release_aborted_request` is
itself nothing but a call to it:
```python
# scheduler.py:3310
def _release_aborted_request(self, req: Req) -> None:
    """Drop the cache-side state an aborted request left behind."""
    self.tree_cache.finish(req.cache_request_handle, CacheRequestOutcome.ABORT)
```

so the full path on every abort is:
```text
_release_aborted_request -> finish(ABORT) -> release_aborted_request
```

The scheduler invokes `finish` from the cancellation site, usually *before* `release_kv_cache`,
and the default implementation immediately translates that call back into cancellation.
Despite its name, `finish` therefore expresses early abort cancellation on these paths rather
than final request termination — the two semantics are not merely conflated by convention, they
are made equivalent by the base implementation itself.

`CacheRequestOutcome.SUCCESS`, meanwhile, has exactly one call site in the entire tree
(`disaggregation/prefill.py:1056`), and it reaches a body that does nothing. Terminal
finalization is instead effectively attached to `cache_finished_req`.

That is problematic because `cache_finished_req` represents KV-cache processing or write-back,
not request termination. `release_kv_cache` returns early before ever reaching it when the
request holds no KV cache:
```python
# common.py:283, in release_kv_cache
if not req.kv.holds_kv:
    ...                      # free mamba state, if any
    return                   # never reaches cache_finished_req (common.py:296)
```

This is not a corner case: the canonical leak window — an `AbortReq` for a request still in the
waiting queue — is precisely the state where the LMCache session has been opened by
`match_prefix` but no KV has been allocated yet. The most common leak path therefore does not
even reach the `release_kv_cache` fallback. Conversely, an aborted request that *does* hold KV
may still need to perform a final STORE before its session can be closed.

A third case shows the gap from the other side: `_clean_hicache_prefetch_resources`
(`decode_hicache_mixin.py:185`) calls `finish(..., ABORT)` only when
`decode_req.prefix_match.prefetch_registered` is true, so on that path an attempt can terminate
without the cache receiving any notification at all.

The missing contract is therefore:

> Every cache request attempt must receive exactly one terminal `finish(handle, outcome)`
> notification, after any required KV release or STORE, regardless of whether it ever held KV
> cache state and regardless of which abort path it took.

Cancellation and finalization must remain separate steps:
```text
cancel pending attempt work          (stays where it is today)
    -> optional release_kv_cache / cache_finished_req / STORE
    -> finish(handle, outcome)       (terminal, exactly once)
```

For paths where no KV finalization will occur, `finish` should run immediately after
cancellation. For paths that still perform a STORE, it should run afterwards.

**This cannot be done by moving the existing&#x20;****`finish(..., ABORT)`****&#x20;calls later.** Because the
default implementation forwards them to `release_aborted_request`, moving them past
`cache_finished_req` would delay FlexKV's cancellation and drop the lock of an in-flight store —
the exact failure described above, relocated to another backend. Abort cancellation has to stay
where it is and remain independently callable; only the terminal notification moves.

The encouraging part is that most of the wiring already exists: `finish` is already invoked on
all thirteen abort paths. What is missing is narrower than a full call-site audit:

1. the default implementation must stop equating `finish` with `release_aborted_request`, and
   the two phases must become separately callable;
2. `finish` must be invoked on successful completion paths as well — today `SUCCESS` reaches
   the cache from exactly one place;
3. on paths that perform a STORE, the terminal call must be positioned after it;
4. the conditional call in `_clean_hicache_prefetch_resources` must become unconditional.

A secondary observation: LMCache keys this state by `rid`, while the attempt lifecycle
introduced in #39318 is keyed by `CacheRequestHandle(rid, attempt_id)`. This is correct today
because the scheduler retires an attempt before starting the next, but it does not give LMCache
the attempt-level isolation FlexKV has.

### Reproduction

No single command reproduces the runtime leak; it needs an LMCache MP daemon plus an abort
landing in a specific window. Trigger conditions:

- LMCache enabled (`enable_lmcache`), MP mode (the default on non-XPU), i.e. `LMCRadixCache`
  is selected in `registry.py:116`;
- a request whose `match_prefix` reports `host_hit_length > 0`, so `_mp_match_prefix` records a
  marker and keeps the lookup locks (`lmc_radix_cache.py:231`);
- the request is aborted before `init_load_back` runs — e.g. `AbortReq` while it is still in
  the waiting queue (`scheduler.py:5429`), or `retire_unadmitted_request` (`:3239`).

The leak itself is directly reproducible in a unit test: drive `_mp_match_prefix` with a fake
connector that models the pending-lookup / read-lock bookkeeping, then call
`release_aborted_request` and observe that nothing is released. #40334 contains such a CPU-only
test (4 cases, no GPU and no `lmcache` install required).

Three paths are not covered yet: the disaggregated-decode ordering path (abort followed by
`cache_finished_req` and a STORE), the reversed ordering at `prefill.py:1128-1129` under
FlexKV, and the conditional notification in `_clean_hicache_prefetch_resources`.

### run-qing-spo · 2026-09-19

@cctry — you introduced the per-attempt cleanup hook in #39318, so you're probably the
right person to judge the design question here: whether `release_aborted_request` should
be split into a cancel phase and a finalize phase.

The concrete finding is that the hook has to run *before* `cache_finished_req` for FlexKV
(it would otherwise release the lock of an in-flight async store) but would have to run
*after* it for LMCache (to close the session after the final STORE). No single position
works for both.

### AyushmanGarg · 2026-09-20

Confirmed against current main: LMCRadixCache has no release_aborted_request override, so aborts hit the no-op in base_prefix_cache.py, and on the abort paths that never reach cache_finished_req the MP marker, pending lookup, and session all leak for the life of the server.

I can implement the two-phase split:

1. BasePrefixCache: split release_aborted_request(handle) into cancel_aborted_request_work(handle) (runs before any KV finalization) and finish_request_session(handle) (runs after cache_finished_req, or immediately on abort paths that never reach it). Both default to no-op so existing backends are untouched.
2. FlexKV: move the current cleanup into the cancel phase unchanged - its ordering requirement is preserved.
3. LMCRadixCache: cancel drops _mp_load_back_markers[rid] and cancels the connector-side pending lookup; finish calls end_session(rid). That gives LMCache end_session after the final STORE on paths that reach cache_finished_req, and immediate cleanup on paths that don't.
4. Tests: port the CPU-only fake-connector tests from #40334 and add the uncovered disaggregated-decode ordering case (abort -> cache_finished_req -> STORE -> end_session).

One design question before writing code: on abort paths that do reach cache_finished_req, should finish_request_session be invoked inside release_kv_cache after cache_finished_req returns, or by the scheduler explicitly after release_kv_cache? The former keeps request-cache lifecycle inside the cache layer; the latter keeps the call order visible at the abort site.

If @cctry is on board with the split I'll open a draft PR.

### cs-fisha · 2026-09-21

1. Cancel pending lookup/prefetch before `cache_finished_req` (FlexKV needs this).
