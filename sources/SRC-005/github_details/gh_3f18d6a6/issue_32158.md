### Describe the bug

On commit `d6ef68881e263812d4901f632786015005c4d050`, `num_running_reqs` returned by `/v1/loads` does not account for all active requests when pipeline parallelism (PP) is enabled. The same counting path is still present on the current `main` branch.

With 16 concurrent, long-running generation requests:

| Configuration | Active requests | `num_running_reqs` | `num_waiting_reqs` |
| --- | ---: | ---: | ---: |
| `TP=2, PP=4, DP=1` | 16 | `1`, `3`, or `6` | `0` |
| `TP=8, PP=1, DP=1` | 16 | `16` | `0` |

All 16 requests were accepted and remained active during the observation interval. The workload and relevant scheduling settings were unchanged between the two cases except for the TP/PP configuration.

The source path appears to explain the difference. `SchedulerLoadInquirer.get_loads()` counts only the batch returned by `get_running_batch`:

```python
num_running_reqs = len(self.get_running_batch().reqs)
```

The callback returns the mutable `Scheduler.running_batch` pointer:

```python
get_running_batch=lambda: self.running_batch
```

In the PP event loop, `self.running_batch` is rebound to one PP slot at a time:

```python
for mb_id in range(self.pp_loop_size):
    self.running_batch = self.running_mbs[mb_id]
    # ...
    self.running_mbs[mb_id] = self.running_batch
```

Since `pp_loop_size = pp_size + pp_async_batch_depth`, requests retained in the other `running_mbs` slots are not included in a snapshot that reads only `self.running_batch`.

This makes `num_running_reqs` phase-dependent in PP mode and can cause load balancers or admission controllers to overestimate available capacity.

A possible fix is to expose an explicit per-DP-rank running-request count and, in PP mode, count unique active request IDs across all `running_mbs` slots. The count should deduplicate request IDs rather than summing `mbs`, `last_mbs`, and `running_mbs`, which may contain overlapping references.

### Reproduction

1. Start SGLang on one 8-GPU node with `TP=2`, `PP=4`, `DP=1`, and `pp_async_batch_depth=0`.
2. Send 16 concurrent generation requests that remain active long enough to sample the engine. Streaming requests with a 512-token generation limit were used in this reproduction.
3. Ensure that no unrelated inference traffic is present.
4. While all 16 requests remain active, repeatedly query `/v1/loads`.
5. Observe that `num_running_reqs` reports only a subset of the 16 requests while `num_waiting_reqs=0`.
6. Repeat the same workload with `TP=8`, `PP=1`, and `DP=1`.
7. Observe that `num_running_reqs=16` remains stable until the requests complete.

Expected result after admission in both configurations:

```text
num_running_reqs=16
num_waiting_reqs=0
```

### Environment

- SGLang commit used for runtime reproduction: `d6ef68881e263812d4901f632786015005c4d050`
- Current `main`: the same load-counting and PP-slot code path is still present
- Hardware: one node with 8 NVIDIA H20 GPUs
- `max_running_requests=512`
- `chunked_prefill_size=8192`
- `pp_async_batch_depth=0`
- `dp_size=1`
