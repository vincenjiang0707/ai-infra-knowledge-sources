### Roadmap refresh — 2026-07-30

Body updated to reflect `main` @ `22faf9fef8`. Summary of what moved since the last revision (2026-07-06):

**Landed**

- **#21637 merged 2026-07-24** — Helix A2A. Delivers `--dcp-comm-backend {ag_rs, a2a, fi_a2a}` and `--dcp-replicate-q-proj`, closing three bullets under "Helix Parallelism": the A2A backend, the FlashInfer-MNNVL backend, and query replication.
- **#32612 merged 2026-07-29** (@Fridge003, @kpham-sgl, Julien Lin) — DCP for Kimi Linear. Adds DCP to `tokenspeed_mla` and the new `cutedsl_mla` backend, plus PD-disagg / DSpark / HiCache compatibility.
- Also landed since the last revision: #30478 (DCP in `get_parallel()`), #31514 (Kimi K2.5 NVFP4), #31532 (prefill CUDA-graph interaction), #32820 (test cleanup).

**Two items in this issue were factually wrong and are now fixed**

- The DCP helpers live at `layers/dcp/`, not `layers/cp/dcp/`.
- #21637 did **not** include FA3 DCP support. `flashattention_backend.py` still has zero DCP references, and no PR for it exists anywhere — the standing ask is #26432.

**"Speculative decoding is rejected under DCP on CUDA" is no longer true**

#32612 replaced the blanket guard with an allowlist. CUDA + DCP + spec now works for `KimiLinearForCausalLM` + `DSPARK` + `--speculative-attention-mode decode` + `tokenspeed_mla`/`cutedsl_mla` + `SGLANG_RAGGED_VERIFY_MODE=static`; everything else still raises. So **DCP × DSpark is done** (with an open correctness follow-up in #32828), and the remaining work is generalizing the lift — DFlash/EAGLE-3 in #31785, then MTP/NEXTN and arbitrary MLA models.

**New sections**

- An **attention-backend × DCP support matrix**, since "which backends actually work" was not answerable from this issue before.
- A **known gaps** section covering combinations that are unguarded rather than unimplemented: prefill-CP × DCP has no guard, HIP skips the spec guard entirely, there is no `tp_size % dcp_size` assertion, DCP silently widens the physical page to `page_size * dcp_size`, and there is no upstream DCP documentation at all.
- The ~16 open DCP PRs from other contributors are now tracked inline under the relevant items rather than being invisible here.

**One thing worth a second pair of eyes** — from reading `main`, plain `trtllm_mla` + `--dcp-size > 1` appears to pass validation but have no working decode path: `_handle_dcp_validation` applies no decode-backend allowlist outside the spec branch, `_is_dcp_mla_decode_phase` returns `True` for any pure decode under DCP, and `forward_mla.py:771` then unpacks `attn_output, lse = ...` from a `forward_decode` that returns a bare tensor (`trtllm_mla_backend.py:855`; the base `_run_decode_kernel` at `:671-679` has no `cp_world`/`cp_rank`/`return_lse`). The DCP-aware call site at `:1027` is only reachable from the `tokenspeed_mla`/`cutedsl_mla` subclasses. This is a code-reading finding, not an observed failure — if it holds, it wants either a validation guard or backend wiring.

### Cerdore · 2026-08-04

Thanks for maintaining this DCP/Helix roadmap @thanhhao98. 

Could you also track  #33364 as an A2A-backend follow-up to the Helix A2A work in this roadmap?
The #33364 adds symm_a2a, a single-node NVLink symmetric-memory direct A2A for MLA decode that:
- fuses peer output+LSE dispatch and LSE-weighted combine into one CUDA kernel sequence — no NCCL collectives, no MNNVL fabric;
- reuses the "head partials + LSE exchange + local combine" model from a2a/fi_a2a, with symmetric memory as the transport;
- is complementary to --dcp-replicate-q-proj from #21637 and to fi_a2a's MNNVL path, targeting lower decode A2A latency.

We have kernel unit tests (2/4-rank, fp16/bf16, ± CUDA graph) and E2E output-parity vs ag_rs on DeepSeek-V2-Lite at TP2/TP4, plus a full serving benchmark on Kimi-K2.5 (8×H20): at concurrency 64, throughput +7.6%~10.3% and ITL p50 −10%~12% across synthetic decode-heavy/balanced/prefill-heavy/heavy-load and ShareGPT/online datasets.

The backend is single-node NVLink only (multi-node topology is rejected at init), TBO overlap is not yet supported, and the FFN side is untouched — no overlap with decoupled attention/FFN parallelism.

Flagging it here because flashinfer's trtllm-gen test only asserts the LSE's shape and finiteness, never its value, so it is easy to get backwards.

### QNan0513 · 2026-09-03

@thanhhao98 two updates on the flashmla entries in the MLA section — both lines are now a bit
out of date.

**"`flashmla`, bf16 KV only #14194"** — #14194's change to `flashmla_backend.py` is 23
insertions, and all of it is the LSE-merge half (returning `lse` alongside `o`). It never
added a rank-local page table or rank-local `seq_lens`: the decode block table is still built
from `req_to_token` with the batch's global `seq_lens`
(`create_flashmla_kv_indices_triton(..., forward_batch.seq_lens, ...)`, and
`cache_seqlens=forward_batch.seq_lens` into the kernel), while under DCP the pool is widened
to `max_total_num_tokens * dcp_size` at `page_size * dcp_size`. So flashmla bf16 + DCP does
not return correct tokens today — it simply has no assert in front of it, unlike the FP8 path.
The same PR *did* give `flashinfer_mla_backend.py` a real `update_local_kv_lens_for_dcp` path,
so that one line covers two backends whose completeness differs quite a lot.

**"`flashmla` + fp8 KV — lift the `dcp_world_size == 1` assert #29760 @Aiziyou918"** — the
assert isn't the blocker. @Aiziyou918 and I worked through this on #29760 and agreed on the
following order, with the page-table work handed to me:

1. refuse the unsafe flashmla + DCP decode path — #37735 (open, currently waiting on a
   `run-ci` label)
2. add the rank-local page table and rank-local `seq_lens` to flashmla — I'm picking this up
3. re-enable DCP and keep #29760's FP8 tuple-return fix, validated across bf16/FP8 x
   `dcp_size` 2/4

One thing still unresolved: #29760 measured GSM8K 0.955 vs 0.960 at `--dcp-size 2
--disable-radix-cache`, which I can't reconcile with the out-of-range page-table reads I
measured at `dcp_size=4` on a fragmented pool. I'm re-running the probe at `dcp_size=2` on a
fresh pool and will report on #37735.

Happy to send a PR adjusting the checklist wording if that would help.
