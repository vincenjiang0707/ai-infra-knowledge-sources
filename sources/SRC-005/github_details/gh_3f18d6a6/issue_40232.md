### Describe the bug

HiCache backup copies device KV into the host pool through the JIT kernel `python/sglang/kernels/jit/csrc/kvcacheio/staged_write_back.cuh`. The kernel has two D2H strategies and picks between them by copy granularity: per-page `cudaMemcpyAsync` for small copies, and one `cudaMemcpyBatchAsync` for `src_ptrs.size() * num_pages` descriptors once `first_page_bytes = page_size * src_stride(0) * item_size >= kLargeCopyThresholdBytes` (128 KiB, defined at `:106`, branch at `:154`, call at `:170`, call sites `:274` MLA and `:279` MHA).

For the batch call the kernel passes **the raw host virtual addresses** of the host pool as the destination pointers (`dst_ptrs[t].data_ptr() + dst_indices[...] * stride * elem`). On a platform where `cudaDevAttrCanUseHostPointerForRegisteredMem` is **0** — i.e. registered host memory is
*not* accessible at the same virtual address on the device — those addresses are not valid device-space addresses, and the copy fails with an **asynchronous `cudaErrorIllegalAddress`**. The fallback path in the same kernel uses `cudaMemcpyAsync` over the *same* addresses and works,
because that API translates host pointers for you.

**Minimal demonstration.** One program, one descriptor, 128 KiB; only the destination form varies:

| `dst` passed to `cudaMemcpyBatchAsync` | submission | sync | bytes |
|---|---|---|---|
| host VA of `mmap()` + `cudaHostRegister()` — **what the kernel does today** | `no error` | **`an illegal memory access was encountered`** | not copied |
| `cudaHostGetDevicePointer()` alias of the *same* buffer | `no error` | `no error` | correct |
| `cudaHostAlloc()` buffer | `no error` | `no error` | correct |
| host VA of plain pageable `mmap()` (never registered) | `no error` | `no error` | correct |
| per-copy `cudaMemcpyAsync()` into the registered buffer | — | `no error` | correct |

Observed on the machine described under *Environment*:

```
$ ./repro_host_va_vs_alias va
cudaDevAttrCanUseHostPointerForRegisteredMem = 0
mode=va      dst=0x72be8c02b000
  submission -> no error
  sync       -> an illegal memory access was encountered
  host[0]    = 0x00 (expected 0x11)

$ ./repro_host_va_vs_alias alias
cudaDevAttrCanUseHostPointerForRegisteredMem = 0
host VA = 0x74371c101000, device alias = 0x204c00000 (same=NO)
mode=alias   dst=0x204c00000
  submission -> no error
  sync       -> no error
  host[0]    = 0x11 (expected 0x11)
```

The same holds at the kernel's real geometry (2 host tensors x 4 pages = 8 descriptors, 128 KiB each): host VAs -> illegal memory access; the two aliases -> success with `k=0x11`, `v=0x22` verified at both the first and the last byte of both buffers.

 `cudaDevAttrCanUseHostPointerForRegisteredMem` is documented as "Device can access host registered memory at the same virtual address as the CPU". On this machine it is `0`, and it is consistent with what the runtime reports for the two host-memory flavors:

```
mmap + cudaHostRegister : host VA 0x74371c101000 != device alias 0x204c00000   (same = NO)
cudaHostAlloc          : host VA == device alias                              (same = YES)
```

On typical native Linux x86_64 with UVA the attribute is `1`, so a host VA *is* a valid device address and the raw-address usage happens to be correct. That is consistent with #21631's benchmark (~48 GiB/s through this same API) and with the absence of earlier reports. Note that
sglang already encodes this exact concept for ROCm — `_resolve_device_accessible_ptr_fn()` in `python/sglang/srt/mem_cache/pool_host/common.py` documents that "on HIP they differ" and `get_device_accessible_ptr` exists to translate; the batch destination is the one place where the translation is not applied.

The two conditions are the default combination in production: the default host pool is `mmap`-backed and registered (`ALLOC_MEMORY_FUNCS` defaults to `alloc_with_host_register`, which calls `cudart.cudaHostRegister(ptr, size, 0)`, on buffers from `HostTensorAllocator.allocate -> alloc_mmap`; only `npu`/`musa` use `alloc_with_pin_memory`), and essentially any real checkpoint exceeds 128 KiB per page (e.g. `page_size=64`, 32 layers, 8 KV heads x 128 dim, bf16 -> 4 MiB). So the batch path is the *default* path, and whether a deployment survives depends on a device attribute that differs by platform/driver — including WSL2, which is where I hit it.

The batch call returns `cudaSuccess`; the error is asynchronous and sticky, so it is only observed at the next synchronization point. In our runs the first symptom was a stream query inside the HiCache ready-count logic:

```
torch.AcceleratorError: CUDA error: an illegal memory access was encountered
  unified_radix_cache.py:3069 _count_ready_acks -> torch/cuda/streams.py query()
  reached via _produce_buffer_l3 -> _buffer_backup_and_wait -> _pump_hicache_until
           -> check_hicache_events -> _sync_hicache_ready_counts
```

The frame in that traceback is not the faulting call, and under `retry()` the test retries until the budget is exhausted, so it presents as a flaky test rather than a broken D2H.

End-to-end confirmation at the sglang level (same test, same geometry, only the host pool backing changed):

| configuration (`test_buffer_only_load_back_drops_on_sibling_published_span`, page_size=32, num_layers=16) | result |
|---|---|
| default: host pool = `mmap` + `cudaHostRegister` | **FAIL** — illegal memory access |
| host pool = `cudaHostAlloc` (`torch.empty(..., pin_memory=True)`) | **PASS** |
| default, with `cudaMemcpyBatchAsync` forced to return `cudaErrorNotSupported` via `LD_PRELOAD` (kernel then takes its existing fallback) | **PASS** |

**Note**

1. **Size / count.** The standalone program faults with 1 descriptor and 4 KiB per copy; the 128 KiB threshold only decides whether sglang enters the batch path.
2. **A memory limit.** Buffers are ~1 MiB, `cudaMemGetInfo` reports 5 GiB free, `ulimit -l` is 1 GiB.
3. **Relayout/staging kernel, or the address arithmetic.** `copy_page_first_pages_fallback()` (`:64`) uses the identical `src_ptr`/`dst_ptr` expressions and succeeds — the LD_PRELOAD row above removes only the batch call.
4. **The relayout kernel's pointer table / missing `get_device_accessible_ptr`.** This wheel (0.4.7) lacks the op, so `make_kernel_ptr_table()` hands the kernel raw addresses; injecting the real alias (confirmed to take effect by tracing the call: 2 calls, `n=16, registered=True`) leaves
   the crash identical. That table addresses the *kernel*, not the D2H descriptor, whose destination comes from the host tensor's `data_ptr()`. (The missing op does matter for any fix built on the alias helper — it would need a wheel built from `python/sglang/kernels/aot`.)
5. **`cudaMemcpyAttributes`.** The fault is identical for `srcAccessOrder` = `cudaMemcpySrcAccessOrderStream`, `...DuringApiCall` and `...Any`, with and without `srcLocHint`/`dstLocHint`, so there is no attribute-level workaround.
6. **`cudaHostRegister` flags.** `Default`, `Mapped`, `Portable` and `Mapped|Portable` all fault.
7. **Compile-time vs runtime `cudaMemcpyBatchAsync` ABI (#36302, #23136, #21869).** The JIT objects here come from `/usr/local/cuda-13.2/.../cuda_runtime.h` (nvcc 13.2) and `cudaRuntimeGetVersion()` returns 13020, so both sides use the 8-parameter signature; the standalone program is compiled the same way and faults.
8. **Mooncake/RDMA storage (#21044).** No storage backend at all here.
9. I cannot separate "WSL2/GPU-PV" from "this driver version" with a single machine, and I cannot tell whether the intended contract of `cudaMemcpyBatchAsync` is that host destinations must already be device-visible. The batch API documentation describes pointer-to-pointer copies and does not state this explicitly. What I can show is that passing the alias makes the identical copy work, so this is fixable on the sglang side regardless of how the driver question is resolved.

### Reproduction

**(1) Standalone, no sglang.** Save as `repro.cu` and run the three modes:

```cpp
// nvcc -O2 -std=c++17 -o repro repro.cu
// ./repro va | alias | pinned
#include <cuda_runtime.h>
#include <sys/mman.h>
#include <cstdio>
#include <cstring>
#include <string>
#include <vector>

#define CK(x) do { cudaError_t e_ = (x); if (e_ != cudaSuccess) { \
  printf("  %s -> %s\n", #x, cudaGetErrorString(e_)); return 1; } } while (0)

int main(int argc, char** argv) {
  const std::string mode = argc > 1 ? argv[1] : "va";
  const size_t page_bytes = 128 * 1024;

  int attr = -1;
  cudaDeviceGetAttribute(&attr, cudaDevAttrCanUseHostPointerForRegisteredMem, 0);
  printf("cudaDevAttrCanUseHostPointerForRegisteredMem = %d\n", attr);

  CK(cudaSetDevice(0));
  void* dev = nullptr;
  CK(cudaMalloc(&dev, page_bytes));
  CK(cudaMemset(dev, 0x11, page_bytes));

  void* host = nullptr;
  if (mode == "pinned") {
    CK(cudaHostAlloc(&host, page_bytes, cudaHostAllocDefault));
  } else {
    host = mmap(nullptr, page_bytes, PROT_READ | PROT_WRITE,
                MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (host == MAP_FAILED) return 1;
    CK(cudaHostRegister(host, page_bytes, 0));   // what the default HiCache pool does
    memset(host, 0, page_bytes);
  }

  void* dst = host;
  if (mode == "alias") {
    CK(cudaHostGetDevicePointer(&dst, host, 0));
    printf("host VA = %p, device alias = %p (same=%s)\n", host, dst,
           host == dst ? "YES" : "NO");
  }

  std::vector<void*> dsts{dst};
  std::vector<const void*> srcs{dev};
  std::vector<size_t> sizes{page_bytes};
  cudaMemcpyAttributes attrs{};
  attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;
  size_t attrs_idxs[1] = {0};

  cudaStream_t stream = nullptr;
  CK(cudaStreamCreate(&stream));
  printf("mode=%-7s dst=%p\n", mode.c_str(), dst);
  cudaError_t err = cudaMemcpyBatchAsync(dsts.data(), srcs.data(), sizes.data(), 1,
                                        &attrs, attrs_idxs, 1, stream);
  printf("  submission -> %s\n", cudaGetErrorString(err));
  fflush(stdout);
  cudaError_t serr = cudaStreamSynchronize(stream);
  printf("  sync       -> %s\n", cudaGetErrorString(serr));
  printf("  host[0]    = 0x%02x (expected 0x11)\n", ((unsigned char*)host)[0]);
  return serr == cudaSuccess ? 0 : 2;
}
```

### he-yufeng · 2026-09-20

Read the kernel on current main and the report holds exactly as written: the batch path builds every destination from `dst_ptrs[tensor_id].data_ptr()` (staged_write_back.cuh:147-150) and hands it to `cudaMemcpyBatchAsync` (:170), while the fallback `copy_page_first_pages_fallback` walks the same addresses through per-page `cudaMemcpyAsync` and works because that API translates host pointers. So the one place the device-accessibility translation is missing is the batch destination, matching your `cudaHostGetDevicePointer` control row.

On the fix shape, two kernel-local options, no wheel/op dependency either way:

1. Query `cudaDevAttrCanUseHostPointerForRegisteredMem` once (static cache) inside the batch helper and return false when it is 0. The caller then takes the existing fallback, which you already proved passes. Smallest possible diff, bulletproof, and the only cost is the batch fast path being unused on affected platforms.
2. Translate each batch destination through `cudaHostGetDevicePointer(..., 0)` and fall back to option 1's path if the alias call errors. Keeps the batch API on WSL2-class platforms at the price of a little more branching.

I would send option 1 as the safe default and mention 2 as a follow-up refinement; the per-page path is not the hot case on platforms where the attribute is 0 anyway.

One honest caveat: I do not have an attribute-0 platform (or any CUDA box) at hand, so my verification is code-level only and CI on UVA hardware can only prove no regression, not the fix itself. Your standalone repro is the right acceptance test for whoever lands it.

Happy to write the PR along these lines if you and the maintainers are good with the direction.

`cudaDevAttrCanUseHostPointerForRegisteredMem` is 0 on this machine, so in your build the gate returns false by construction and the existing fallback is what carries the run — exactly the outcome you predicted, and worth confirming on hardware given you flagged you had none.

Two observations, both about breadth rather than correctness:

1. The attribute query sits ahead of the `kLargeCopyThresholdBytes` check, so every staged write-back pays a `cudaDeviceGetAttribute` call — including copies that stay on the per-page path and platforms that were never affected. Your comment said "once (static cache)" while the PR body says per call; probably worth picking one and matching the other.
2. The attribute describes the device, not the memory. On an attribute-0 host it also retires the batch path for `cudaHostAlloc` / `pin_memory` pools, whose host VA is identity-mapped and was never the problem. That is the safe direction of error, just a wider brush than the defect needs.

On option 1 vs option 2, one piece of data you may not have had: option 2 is already implemented in #40233, so the "follow-up refinement" is code-complete rather than hypothetical. I put a temporary print in the batch helper to see which D2H path actually runs, and on this same attribute-0 box the batch call itself succeeds once the destination is the alias:

```
[probe] BATCH OK n=8 dst0=0x204e00000 host_va0=0x7cd2a813f000 alias_differs=1
```

So option 2 keeps the batch path on precisely the platforms where option 1 gives it up. Two smaller differences, stated plainly in both directions: the diff is 15 lines against 158; and #40233 carries a registered-host-pool regression test while #40571 has none — although, to be fair to your caveat, that test would pass on UVA CI with or without either fix, so it is a guard on affected hardware rather than a CI regression detector.

One clarification on your option 2, since it differs slightly from what #40233 does: for host memory that was never registered, `cudaHostGetDevicePointer` errors, and the helper there returns the host VA instead of falling back to per-page. That is deliberate — pageable host memory has no separate device address and the copy APIs expect the host VA, which is the combination that already worked in the report's table. Both behaviours are needed at one call site.

Suggestion for landing, maintainers' call and I am happy either way:

- if the smaller, assumption-free change is preferred, I will close #40233 and move its registered test into #40571, so the fallback path is at least covered by a test;
- if keeping the batch path on attribute-0 platforms is preferred, #40233 is ready, and #40571 folds in as an extra guard only if you want the belt-and-braces version — landing both as they stand would leave the translation unreachable on those platforms, so it is really one or the other.

I checked that they do not conflict textually (#40571's diff applies cleanly on #40233's head), so this is a choice about intended behaviour rather than merge mechanics.
