# [Bug] DFLASH draft layout is assumed, not validated: anchor-first checkpoints shift every position silently

### Summary

`DFLASH` draft checkpoints carry an implicit block-layout convention, and SGLang assumes
one of the two conventions in common use without checking which one a checkpoint was
trained with. A checkpoint trained with the *anchor-as-first-prediction* layout — where
every position in the block predicts — is served without any error and produces draft
tokens shifted by one position. The server reports healthy; acceptance collapses to
roughly `1.0` (only the anchor/bonus token survives).

Isolated on a Qwen3.8-Flash-Next (`Qwen4Exp`) target with the official DeepSpec drafter
`dflash_block7_qwen38_flash_next` on 8×A800 (SM80): **accept length @ 4-token window =
1.0621** over 47,411 verify steps. The same checkpoint's card reports a *served* accepted
length of **2.7562 at block 4** and **2.9837 at its native block 7** under vLLM, where the
layout it was trained for is honoured. No warning, no assertion here — the service starts
and answers normally, at a fraction of that acceptance.

### The two conventions

| | anchor-as-first-prediction | 1+N (SGLang's assumption) |
|---|---|---|
| block positions | all `K` positions predict | position 0 is the seeded anchor/bonus token; positions `1..N` are the drafts |
| marker, when present | `sample_from_anchor: true` | `sample_from_anchor: false` |
| drafter | DeepSpec `dflash_block7_qwen38_flash_next` | speculators-format drafts |

The marker is a **speculators** config field (`DFlashSpeculatorConfig.sample_from_anchor`,
default `False`; `DSparkSpeculatorConfig` defaults `True`). The convention also determines the
token count: `False` → `block_size - 1` speculative tokens, `True` → `block_size`.

**It is not a reliable discriminator across the ecosystem, which is part of the problem.**
The official anchor-first checkpoint above carries **no `sample_from_anchor` field at all** —
neither top-level nor inside its `dflash_config`; its config exposes `num_anchors: 512` and
nothing else about the layout. So a marker-based check would read the sglang default and wave
exactly the checkpoint that mis-serves through.

**But the layout *is* declared — under a name SGLang does not read.** The upstream serving repo
ships a config override (the README notes the checkpoint's own `config.json` "does not carry the
`dflash_config` block the engine reads"). That override's `dflash_config` contains:

```json
"dflash_config": {
  "target_layer_ids": [3, 15, 23, 35, 43],
  "mask_token_id": 248077,
  "use_aux_hidden_state": true,
  "causal": false,
  "query_zero_predicts_next": true
}
```

`query_zero_predicts_next: true` is a direct, explicit statement of the anchor-first convention.
SGLang's `DFlashDraftConfig` (`speculative/dflash_utils.py:529-548`) has no field for it and
`parse_dflash_draft_config` never reads it — a tree-wide search for the identifier returns zero
hits. So the declaration exists, is unambiguous, and is silently dropped.

```bash
> **Inference, not a confirmed contract.** I am reading `query_zero_predicts_next` as "the
> query at position 0 predicts the token *after* the anchor", i.e. the anchor-first layout —
> that is what the field name says and it is consistent with the extra `block_size`-th
> prediction the layout implies, but I have not verified it against the trainer source and am
> labelling it as a hypothesis rather than a spec. If the maintainers confirm the field's
> meaning, a check on it is the natural fix; if not, the layout still has to be established
> some other way. It should not be shipped as a hard gate on my reading alone.
```

### Where SGLang assumes 1+N

`DFlashWorkerV2` slices the draft's hidden states to drop position 0:

```python
# python/sglang/srt/speculative/dflash_worker_v2.py:158-160
# draft tokens are block positions 1: (pos 0 is the seeded bonus token)
bs = hidden_states.shape[0] // self.block_size
hs = hidden_states.view(bs, self.block_size, -1)[:, 1:, :].reshape(
    -1, hidden_states.shape[-1]
)
```

The same slice appears in the in-worker draft path (`dflash_worker_v2.py:278`,
`# pos 0 = anchor`) and in the selector path (`:1378`, `:2572`).

A checkpoint trained anchor-first produces `K` meaningful predictions per block, but only
`K-1` of them are read, and each one is read from the *wrong* slot — a uniform off-by-one
across every draft position.

### The layout field is already parsed — just not for this

`dflash_utils.py` already reads `sample_from_anchor` off the draft config:

```python
# python/sglang/srt/speculative/dflash_utils.py:504-507
sample_from_anchor = dflash_config.get(
    "sample_from_anchor", _cfg_get(config, "sample_from_anchor", True)
)
return sample_from_anchor is False
```

Two things follow from that snippet. First, the field is already parsed at config-parse time.
Second, **its default is inverted for this purpose**: `_cfg_get(..., True)` reads the sglang
default as `True`, but the speculators default for the DFlash family is `False`. So "absent"
means *opposite* things to the two sides, which is why absence cannot be treated as safety.

Today the read is confined to `is_nemotron_35_draft_config` (`dflash_utils.py:470`), and even
there it is one of six conjunctive conditions identifying one specific published checkpoint —
it is not a general layout gate. The value is available on the DFLASH path and simply not
consulted there.

### Suggested fix (fail fast, matching vLLM)

vLLM's DFlash speculator raises on this exact layout
(`ValueError: sample_from_anchor=True is not supported for DFlash`). SGLang currently does
something worse than raising: it serves, silently, at ~1.0 acceptance.

Three options, in increasing order of how much they depend on my unverified reading above:

1. **Minimal, no inference needed for the check itself:** fail fast on the checkpoints that *do*
   declare a layout — anything SGLang can currently see (`sample_from_anchor` where present).
   Wiring up `query_zero_predicts_next` would extend this to the official checkpoint, but **that
   rests on my unverified reading of the field (hypothesis, see above) — it should only be
   treated as a gate once the semantics are confirmed.** As it stands this option would not have
   caught the official checkpoint, because SGLang reads neither field today; it is a strict
   improvement over the current state and commits to nothing uncertain.
2. **Require an explicit declaration** on the DFLASH draft config going forward, and refuse to
   serve a checkpoint that omits it. Catches everything, including this checkpoint — at the
   cost of breaking checkpoints that are in the wild today.
3. **Honour the layout** — read all `K` positions when the checkpoint is anchor-first. The most
   useful outcome, and a bounded change at the four slice sites above, but it is downstream of
   the layout actually being established.

Either way the checkpoint stops being served at a wrong-but-plausible acceptance rate.

The design constraint worth flagging: **an explicit check on `sample_from_anchor` alone would
not have caught this checkpoint** — it declares neither that field nor `speculative_tokens`
(the identifier does not appear anywhere in its config). Whatever is chosen has to *establish*
the layout rather than default it.

Two things I'd be glad to be corrected on: whether `query_zero_predicts_next` means what I read
it to mean, and whether there is a better discriminator for layout than anything proposed here
— I've only looked at one checkpoint family and would rather defer to the maintainers than guess.

## DFlash draft layout: two independent width derivations, no declared binding

### 1. Phenomenon: the anchor-first layout is silently halved

A DFlash draft checkpoint can be trained in one of two query layouts. In the
**anchor-first** layout the draft block reuses the target's last committed token
as position 0 and only the remaining `block_size - 1` rows are drafted; in the
default **1+N** layout the block carries one extra query row and the accept
bookkeeping is shifted by one. Nothing in the serving path forces the resolved
layout to match what the weights were trained with.

Measured on one anchor-first checkpoint, 8-token window, TP8, 300 requests at
concurrency 8, `temperature=0`. The only difference between the two rows is
whether the checkpoint declares its layout:

| checkpoint config | resolved layout | accept length |
|---|---|---|
| layout field absent | 1+N (default) | **1.0653** |
| layout field declared (`query_zero_predicts_next: true`) | anchor-first | **1.6310** |

An undeclared checkpoint at an 8-token window measures the same as a 4-token
window (~1.06), so the window widening buys nothing and the entire +0.57 is the
layout being honoured.

Sources, so the numbers are checkable rather than asserted:

- 1.0653: 300/300 requests, 46,769 verify steps, recorded in our arm-A
  eager-mode result JSON (md5 `4f03eb8d...`).
- 1.6310: 300/300 requests, 31,822 verify steps, our arm-B eager-mode result
  JSON (md5 `716dddcb...`).
- 4-token baseline 1.0621: our earlier 4-token-window run on the same rig and workload.
- Both figures are the engine's per-request `spec_accept_length` averaged over
  requests. Convention: `completion_tokens / verify_ct`, i.e. **includes the
  bonus token** (`python/sglang/srt/managers/tokenizer_manager.py:2958`,
  comment `# accept_length: completion_tokens / verify_ct (includes bonus
  token).`). Other conventions in the same tree differ by up to ~8x
  (`spec_accept_rate` just above at :2956-2957 is a strict count with no bonus), so
  any number quoted from this family must carry the convention label.

The failure is silent because the undeclared case resolves to a legal value.
The default is not "unknown"; it is 1+N, which serves and produces fluent output
while being off by one position for the whole run.

### 2. Mechanism: two widths, derived in two places, bound by nothing

There is no single function that answers "what per-request width does this draft
layout need". There are two, and the second is not expressed in terms of the
first.

**Width A - the draft query width.** Resolved from the checkpoint config:

- `python/sglang/srt/speculative/dflash_worker_v2.py:460` sets
  `self.block_size = int(get_spec().speculative_num_draft_tokens)` and then
  compares it against the checkpoint's own `block_size`
  (`dflash_worker_v2.py:460-473`), logging
  `"DFLASH block size mismatch: using speculative_num_draft_tokens=%s but draft
  config block_size=%s."` when they differ. That is a warning about the *window*,
  not about the layout, and it does not change the width.
- The draft sampler consumes the query width by dividing the hidden-state row
  count: `bs = hidden_states.shape[0] // self.query_token_num`
  (`python/sglang/srt/speculative/dspark_components/dspark_draft_sampler.py:111`),
  where `self.query_token_num` is set from the anchor flag one line above the
  gamma (line 58).
- The DSpark sibling derives the same quantity a third time from the anchor flag:
  `self.query_token_num = self.gamma if self.sample_from_anchor else self.gamma + 1`
  (`dspark_draft_sampler.py:58`, and again at `dspark_draft.py:219` and
  `dspark_worker_v2.py:213`). Three copies of one rule, none of which reads a
  shared resolver.

**Width B - the captured verify width.** Derived from server args only:

- `python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py:293`
  computes the static capture width as
  `model_runner.decode_num_tokens_per_req(num_draft_tokens=self.speculative_num_draft_tokens)`
  and stores it as `self.captured_req_width`. That value sizes the per-request
  buffers (`decode_cuda_graph_runner.py:358`, `:386`, `:416`) and is what
  `DFlashVerifyInput` is constructed with at capture time
  (`decode_cuda_graph_runner.py:1594`,
  `draft_token_num=self.captured_req_width`).
- `decode_num_tokens_per_req` (`python/sglang/srt/model_executor/model_runner.py:801-820`)
  has an anchor-aware branch, but it is **DSpark-only**: the guard is
  `if self.spec_algorithm.is_dspark() and self.is_draft_worker:` (line 806) and
  it consults `get_dspark_sample_from_anchor` (line 811). DFLASH does not match
  that guard and falls through to the generic resolver at line 815,
  `resolve_num_tokens_per_req(phase="target_verify", ...)`.
- That resolver (`python/sglang/srt/speculative/spec_utils.py:93-120`) returns
  the algorithm hook's answer at line 117,
  `spec_algorithm.get_num_tokens_per_req_for_target_verify(num_draft_tokens,
  is_draft_worker)`. For DFLASH on main the hook is the base implementation
  (`python/sglang/srt/speculative/spec_info.py:290-300`):
  `if self.is_dspark() and is_draft_worker: return num_draft_tokens - 1`
  (line 299) / `return num_draft_tokens` (line 300). So for a DFLASH draft
  worker the capture width is `speculative_num_draft_tokens`, unconditionally.
- Its own docstring states the intended role: *"Single static derivation point
  for a spec phase's per-request token width (sizes capture shapes / buffers);
  the per-forward dynamic width lives on ``SpecInput.num_tokens_per_req``."*
  (`spec_utils.py:100-103`). The static and dynamic widths are declared to be
  the same quantity here; the layout is not part of that derivation.

**What is missing.** Nothing asserts `A == B`. The only runtime guard on the
mismatch is a replay-time comparison,
`spec_info.num_tokens_per_req != self.captured_req_width`
(`decode_cuda_graph_runner.py:672-680`), whose documented behaviour is to
**fall back to eager**, not to fail: *"Uniform-width replay invariant: the
batch's actual per-request width must match this runner's capture width;
anything else falls back to eager. (Unset widths pass: not every path fills the
field yet.)"* A silent fallback is a performance cliff, not a correctness gate,
and it fires after the wrong width has already been used to size the run.

For DFLASH specifically the two widths do not even disagree in a way that
trips that guard today: the DFLASH verify input is built with
`draft_token_num=int(self.block_size)` (`dflash_worker_v2.py:2630`), and
`DFlashVerifyInput.__post_init__` fills `num_tokens_per_req` from
`draft_token_num` when it is unset
(`python/sglang/srt/speculative/dflash_info.py:55-58`,
`if self.num_tokens_per_req == -1: self.num_tokens_per_req = int(self.draft_token_num)`).
Both sides therefore report `block_size` and the guard passes. The layout
decision never enters either value. This is the silent half of the problem: the
guard cannot catch what it is not told.

**Corroborating shape of the same defect.** The accept bookkeeping is written
against the 1+N convention and is only correct for anchor-first because the
drafted tokens are placed explicitly:

- `python/sglang/srt/speculative/dflash_worker_v2.py:2614-2615` fills the verify
  block as `draft_tokens[:, 0].copy_(block_ids[:, 0])` then
  `draft_tokens[:, 1:].copy_(draft_next)` - position 0 is the anchor, the
  `block_size - 1` drafted rows follow. (`draft_next` is itself produced with
  `block_size - 1` columns a few lines above in the same block.)
- The acceptance rule itself assumes exactly that shift
  (`python/sglang/srt/speculative/dflash_utils.py:942` (rule restated in the comment at :911),
  `accept while candidates[:, 1:] == target_predict[:, :-1] consecutively`), and
  the accept length returned is the strict draft count, with the bonus added
  separately: `return out_tokens, accept_len.to(torch.int32) + 1`
  (`dflash_worker_v2.py:188-195`, `_commit_accept`; the `+ 1` is at line 195).
  The `+ 1` is the same bonus-token convention as the metric in section 1.

So the layout is not merely a config flag: it decides which row of the block is
the anchor, and both the verify-width derivation and the accept arithmetic
depend on that decision without either of them naming it.

### 3. Impact: who is affected

The failure surface is "a draft checkpoint whose trained layout does not match
the layout the engine resolves". Concretely:

- **Any DFLASH or DSpark draft checkpoint that does not carry an explicit layout
  field.** Both `parse_dflash_draft_config`
  (`python/sglang/srt/speculative/dflash_utils.py:606`) and
  `get_dspark_sample_from_anchor`
  (`python/sglang/srt/speculative/dspark_components/dspark_config.py:29-31`)
  default the anchor flag to the 1+N side when the field is absent. A checkpoint
  exported with its layout only in a serving override, rather than in the
  weights, hits this on every launch.
- **Both spec algorithms, asymmetrically.** DSpark has an anchor-aware branch in
  `decode_num_tokens_per_req` (`model_runner.py:806-814`) and an anchor-aware
  hook (`spec_info.py:299-300`); DFLASH has neither. So the same checkpoint
  exported under the two algorithms resolves different widths on the graph side
  while the layout flag stays the same.
- **CUDA-graph decode, which is the default.** The width in question is the
  capture width. Eager runs never consult `captured_req_width`, which is why the
  measurements in section 1 had to be taken with graphs disabled; with graphs on,
  an anchor-first draft whose sampler width and capture width disagree dies
  during capture with a shape error rather than mis-serving.
- **Anything downstream that sizes buffers from the same number**:
  `max_decode_logits_rows` (`model_runner.py:824-845`, which calls
  `self.decode_num_tokens_per_req(...)` at line 840) and the capture-bs planner
  `cuda_graph_setup.py:712`, which reads
  `num_tokens_per_req = model_runner.decode_num_tokens_per_req()` for every
  speculative algorithm, both inherit width B. A correction applied only to the
  sampler would leave these at the verify width.

Not affected: EAGLE/EAGLE3, whose draft widths come from `topk` and
`speculative_num_draft_tokens` through the same resolver but have no anchor
layout; and any checkpoint that declares its layout explicitly.

### 4. Proposal: make the contract explicit and validate it at load

One change below is already prototyped in an open PR; the other is not, and is the remaining ask.

**In-flight work.** #40203 (open as of 2026-09-24, head `d9bcff33`) implements the width binding of (b) the right way: a single shared resolver (`resolve_dflash_anchor_first` / `resolve_dflash_num_draft_queries` in `dflash_utils.py`) that both the worker and the new DFLASH branch in `decode_num_tokens_per_req` (`model_runner.py`) read, with the PR's own docstring stating the invariant ("The two must never disagree"), and it rejects declarations that disagree across the two spellings and two locations instead of letting lookup precedence swallow them. This issue does not re-propose (b). What #40203 does not contain is (a): when the config declares nothing, `resolve_dflash_anchor_first` still returns `None`, the run still resolves silently to 1+N, and the checkpoint from section 1 is still served shifted.

**(a) Make the layout field required at load, and reject a missing one.**
Today the absent field is indistinguishable from an explicit 1+N. Change the
DFLASH and DSpark draft-config parsers to require the anchor-layout field and
raise a `ValueError` naming the field and the checkpoint when it is absent, the
way `DFLASH Domino requires dflash_config.gru_hidden_dim.`
(`dflash_utils.py:801-803`) already does for its own required keys. A checkpoint
that genuinely wants 1+N says so; a checkpoint that forgot is told at startup
instead of at accept-length regression time. Where the layout is declared through a serving-override channel rather than in the weights, that declaration must count — the requirement is that some declared source exists and is unambiguous, not that it live in any particular place. If a hard error
  is judged too strong for back-compatibility, the minimum acceptable is a loud
  startup warning that names the checkpoint and the resolved value — silence is
  the only unacceptable outcome. The same parser is the natural
place to reject the two-location conflict that a precedence lookup currently
swallows (`dflash_utils.py:514`,
`dflash_config.get("sample_from_anchor", _cfg_get(config,
"sample_from_anchor", True))`).

**(b) Bind width A and width B through one declared resolver, and assert the
binding.** #40203 prototypes this as one shared resolver rather than an assertion, which satisfies the binding by construction; on main today the two widths are still derived independently, so the binding still matters until that PR lands. Introduce the anchor flag as an argument to the static width
derivation, so `resolve_num_tokens_per_req(phase="target_verify", ...)` (or the
per-algorithm hook it dispatches to) returns `block_size - 1` for an
anchor-first draft worker, mirroring what DSpark's branch already does at
`model_runner.py:806-814`. Then add a startup assertion that the sampler's query
width and the runner's capture width agree, so the mismatch is a load-time
failure with both values in the message rather than a capture-time shape error
or an eager fallback. The replay-time guard at
`decode_cuda_graph_runner.py:672-680` can stay as a defensive net; it should not
be the only thing standing between a wrong width and a served request.

**Why this shape.** The general problem is that a checkpoint declares a layout
in one vocabulary, the engine derives widths in another, and neither side is
required to state the relationship. A required declaration plus a single bound derivation
turns an open-ended class of silent mis-computations into a startup error.

### Prior art in this tree

This is the same class of defect we raised upstream in
**#40143, "[Spec] QSA: let the pending index-K ring hold more than one
compression group"** (`https://github.com/sgl-project/sglang/pull/40143`).
Verified state as of 2026-09-24 via
`gh api repos/sgl-project/sglang/pulls/40143`: **`state: open`, `merged: false`,
`merged_at: null`** (opened 2026-09-18). It is not merged, and this issue does
not depend on it; it is cited only as precedent that a missing contract between
two independently derived quantities produces a silent mis-computation rather
than an error, and that the fix we propose there (state the contract, validate
it) is the same fix proposed here.

### Leslie360 · 2026-09-24

Good question — this is the natural next step beyond declaration-based resolution. My take, in three points:

**1. The weights alone can't recover an undeclared layout.** Both layouts have identical draft-block weight shapes, so a checkpoint that doesn't declare its layout carries no signature to read it back from; the discriminating signal has to be behavioral.

**2. A behavioral probe is feasible.** Concretely: take a small calibration set, run the draft head under both layouts, and score each by next-token logprob under the target's `lm_head` (or an acceptance-length proxy); take the side with a clear margin, and bail out with a loud warning if there isn't one. The cost is two forward passes over a small calibration set.

**3.
