# [PR #26501] disaggregation: Support Intel XPU for staging-buffer KV transfer

source: https://github.com/sgl-project/sglang/pull/26501
state: closed | updated: 2026-09-23T06:18:43Z
labels: intel, xpu, run-ci, PD Disaggregation

## 正文

## Motivation

PD disaggregation with staging-buffer KV transfer currently assumes CUDA in several parts of the Encoder/Prefill/Decode path. On Intel XPU, these assumptions can either fail immediately—for example, `torch.cuda.Event()` raises `RuntimeError: Tried to instantiate dummy base class Event`—or skip required synchronization because it is guarded by `is_cuda`.

This PR makes the staging-buffer path device-agnostic and enables the path end to end on Intel XPU, verified on 2x Intel Arc Pro B60.

Two issues exposed by XPU are not inherently XPU-specific:

* The encoder `/send` path synchronized only when `mm_embedding.is_cuda`. The synchronization is required because `transfer_sync` does not provide ordering with the device stream; without it, the transport can read a buffer before the device writes are complete.
* Staging initialization defaulted `device_type` to `"cuda"`, which allowed a non-CUDA backend to silently allocate staging buffers on CUDA.

### Depends on #39417

#39417 fixes the PD prefill early-send event handling and propagates the early-send wait event through NIXL and Mooncake.

This PR currently contains the one-line `prefill.py` event fix as well because the XPU staging path depends on it. Once #39417 merges, this PR should be rebased and that duplicate `prefill.py` change should be dropped.

There may also be textual conflicts around the `gather_all_layers_to_staging()` calls in `mooncake/conn.py` and `nixl/conn.py`, because both PRs modify the surrounding code. The final result should retain both changes:

* #39417: synchronize the early-send wait event before staging gather.
* This PR: pass the runtime device type through staging initialization / update the staging call arguments.

Without the event fix from #39417, the XPU staging e2e test fails when a cached prefix is reused under overlap scheduling.

## Modifications

### Device-agnostic device helpers

`sglang/srt/utils/common.py`

* Add `create_device_event` and `current_device_stream`.
* Use the device module associated with the runtime device instead of hard-coding `torch.cuda`.

### Staging buffers

`sglang/srt/disaggregation/common/staging_buffer.py`

* Support device-aware staging allocation for CUDA, XPU, and NPU.
* Resolve the device index from the explicit device string when present; otherwise fall back to `gpu_id`.
* Keep custom memory-pool allocation CUDA-only; XPU/NPU use their default allocator.
* Restrict Triton staging kernels to CUDA and use the Torch gather/scatter fallback on other supported accelerators.
* Avoid converting XPU device pointers to signed `int64`; XPU pointers can use bit 63, which is not representable as a positive `torch.int64` value.

### Stream ordering

* Resolve the current stream at gather time rather than caching it during initialization. The current stream is thread-local, while transfer workers execute on separate threads.
* Add an explicit ordering edge from the decode `schedule_stream` before reading `req_to_token`.
* This is required because XPU does not provide CUDA-style default-stream synchronization, and a dedicated CUDA stream also does not implicitly synchronize with unrelated work.

### Staging handler and transports

`sglang/srt/disaggregation/common/staging_handler.py`
`sglang/srt/disaggregation/mooncake/conn.py`
`sglang/srt/disaggregation/nixl/conn.py`

* Use the runtime `device_module` for `Event` and `Stream` creation.
* Thread the runtime `device_type` from `server_args.device` into staging initialization.
* Make `device_type` a required keyword-only argument.

This is a **breaking signature change for out-of-tree backends**. The previous `"cuda"` default is intentionally removed so that a backend cannot silently allocate staging buffers on the wrong accelerator. Omitting `device_type` now fails explicitly.

### NIXL

* Use `np.uint64` for transfer descriptors so high device pointers are not truncated or interpreted as signed values.

### Encoder

`sglang/srt/encoder/server.py`

* Select the transport according to the runtime device (`cuda_ipc` for CUDA and the existing CPU/default path otherwise).
* Allow `TensorWrapper` to copy from non-CPU devices.
* Synchronize `/send` for every non-CPU accelerator rather than gating the synchronization on `is_cuda`.

### DCP pack

`sglang/srt/disaggregation/common/dcp_pack.py`

* Order the gather against the staging buffer's producer stream rather than relying on `torch.xpu.default_stream`, which is not available.

### Metadata buffers and QK normalization

`sglang/srt/disaggregation/utils.py`
`sglang/srt/models/utils.py`

* Make tensor placement and stream handling device-agnostic.
* Keep the `INTRA_NODE_NVLINK` memory-pool path CUDA-specific.

### Prefill early-send

`prefill.py`

* Replace the CUDA-specific event creation with the scheduler's device module.

This change is duplicated with #39417 and will be dropped after rebasing onto the merged PR.

## Accuracy Tests

### XPU end-to-end

`test/registered/xpu/test_disaggregation_staging_xpu.py`

**8 tests passed in 106s** on 2x Intel Arc Pro B60 (`ZE_AFFINITY_MASK=5,6`), covering:

* single-request generation
* concurrent generation
* long sequences
* staging-buffer reuse across requests

The concurrent case is particularly important because it exercises `enable_overlap` together with a radix-cache prefix hit. This is the scenario that exposed the CUDA-only prefill event creation.

### Unit tests

`test/registered/unit/disaggregation/`

**379 tests passed**, including **2 new Mooncake staging-device tests**.

The new Mooncake tests verify that staging initialization receives the runtime device instead of implicitly using `"cuda"`. Both fail against the pre-fix implementation.

The tests specifically cover the configuration/device-selection regression; they do not claim to provide end-to-end Mooncake staging-transfer coverage.

The XPU e2e test is placed under the `xpu` vendor tree because the registered-test taxonomy rejects newly added paths outside the expected `<kind>/<subsystem>` structure, while the vendor directories are exempt.

The XPU e2e tests remain CI-disabled pending upstream NIXL/UCX support required by the test environment. They were run locally with NIXL/UCX builds containing the required patches.

### Remaining test gaps

The Mooncake staging transfer path is also not covered end to end on XPU; the end-to-end staging verification in this PR uses NIXL because that is the transport available on the test hardware.

## Performance

No CUDA-path performance regression is intended.

The changes are primarily device-selection and stream/event handling on initialization or correctness-critical paths. The gather now resolves the current stream per call instead of caching it; this was measured at approximately **0.3% overhead** on the affected path.

The per-call lookup is intentional because the current stream is thread-local and transfer workers run on separate threads.

> @kpjeeja do xpu need to set `SGLANG_STAGING_USE_TORCH`? Does triton path in `staging_buffer.py` work? triton now stores `layer_ptrs` in int64 and would possibly have address overflow on xpu.

Yes, agreed — the Triton path will not work correctly on XPU today because layer_ptrs are stored as int64, which can overflow/truncate XPU device addresses.
Instead of requiring users to set SGLANG_STAGING_USE_TORCH, I'm planning to make this device-aware. The proposed change is:
        Keep honoring the existing SGLANG_STAGING_USE_TORCH override.
        Add a helper such as _should_use_triton_staging(device).
        Automatically disable the Triton staging path for XPU devices and fall back to the torch implementation.
        Continue using the Triton path for CUDA (and other supported devices).

This way XPU users don't need any additional configuration, and the torch path is used automatically since it handles device pointers correctly without the explicit int64 conversions used by the Triton implementation.

Would you be okay with this approach?
