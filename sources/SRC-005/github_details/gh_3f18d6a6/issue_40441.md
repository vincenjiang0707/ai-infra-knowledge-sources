# [Issue #40441] [Feature][DeepSeek-V4.1] Decode graph width is pinned to --context-length; add a decode-phase max_seq_len

## 正文

### TL;DR

On SM90, `--context-length` sets the decode indexer's **scan width**, not only the maximum servable context. The decode CUDA graph is captured with `max_seq_len = MAX_SEQ_LEN_FOR_CAPTURE = req_to_token.shape[1]`, and `PagedIndexerMetadata.max_compressed_seq_len` derives the indexer kernel's fixed column count from it. A deployment that actually serves 2K-token contexts therefore pays for a 1M-token scan on every decode step.

Measured, that is a **2.68x decode lever** — and it is not escapable from config: `PhaseConfig.max_seq_len` is accepted for `Phase.PREFILL` but not for `Phase.DECODE`, so the only way to collect it is to lower `--context-length` and give up long context.

PRs #39046 / #40431 / #40176 reduce the *work* done per capacity-sized tile, but they explicitly preserve the launch grid and the graph width. This is the complementary knob: let the decode graph be captured narrow, and fall back to eager for live contexts that exceed it — mirroring what prefill already does via `max_context_size` + `can_run_prefill_cuda_graph`.

### Environment

- 8 x H200, SM90 (sm_90), driver 570.211.01 / CUDA 12.8, all-to-all NV18
- `lmsysorg/sglang:dev-cu12-dsv41` @ `824bb45e1bf7486e49034bfa4bcad59aba799540`

- `--tp-size 4 --ep-size 4 --context-length 1048576 --max-running-requests 8 --cuda-graph-max-bs-decode 8 --chunked-prefill-size 8192 --mem-fraction-static 0.70 --schedule-policy lpm --moe-runner-backend humming --speculative-algorithm DSPARK --speculative-dspark-block-size 4 --speculative-num-draft-tokens 5`
- Replica B only; replica A's container id and `StartedAt` asserted unchanged across every recreate

### Measurement

Decode tok/s **per request**, median of 5 repeats, one unmeasured warm round. Per-request (not aggregate) so batch effects are removed.

| `--context-length` | indexer capacity (cols) | 2048 x1 | 2048 x8 | 65536 x8 |
|---|---|---|---|---|
| **1048576** (baseline) | 262144 | 98.4 | **32.1** | 35.31 |
| 524288 | 131072 | 128.01 | 49.41 | 52.55 |
| 262144 | 65536 | 131.51 | 67.93 | 73.59 |
| 131072 | 32768 | **147.93** | **85.98** | **88.0** |
| **gain, 1M -> 128K** | | **1.50x** | **2.68x** | **2.49x** |

Adjacent-tier 5-repeat ranges are disjoint everywhere (e.g. 65536 x8: `33.81-35.92`, `52.38-53.82`, `70.98-75.21`, `85.02-92.99`), against a measured run-to-run spread of 10-13%.

Cell labels are nominal: the harness over-calibrated and real prompt lengths are 2658 / 84261 tokens. Prompt construction is byte-identical across tiers and variants, so the overshoot is common mode and does not bias the deltas.

Three things identify the mechanism as a per-row fixed-width scan rather than a length- or weight-proportional cost:

1. **bs=1 gains 50% and saturates; bs=8 gains 168% and is still climbing.** The same capacity reduction is worth 8x more in absolute terms at bs=8 while the step it is charged against grows far more slowly.
2. **Cost is linear in capacity.** Inverting to step time at n=8: 31.15 / 20.24 / 14.72 ms for 262144 / 131072 / 65536 columns — halving the capacity halves the saving (10.91 : 5.52 = 1.98).
3. **A registered prediction.** Fitting `step_time(n=8) = 9.27 ms + 83.2 ns * capacity_columns` predicted ~83 tok/s at the 131072 tier before that tier was run; measured **85.98**.

Service-level effect: aggregate wall-clock throughput at 2048 x8 moves 226-247 -> 347-369 tok/s at the first tier alone (+50%), with TTFT flat to noise (0.438 -> 0.442 s) and the KV pool unchanged (-0.67% once, then flat).

Fresh-boot control excludes allocator/JIT state: after restoring the 1M config on a freshly booted replica the identical probe reproduces the baseline (102.7 / 32.16 / 35.6).

### Source (main)

- `python/sglang/srt/layers/attention/dsv4/metadata.py:322-324` — `max_compressed_seq_len` = `page_table.shape[1] * compressed_page_size`
- `python/sglang/srt/layers/attention/dsv4/indexer.py:1067` — that value is handed to the decode indexer as a fixed argument
- `python/sglang/srt/layers/attention/deepseek_v4_backend.py:1214` — `MAX_SEQ_LEN_FOR_CAPTURE = self.req_to_token.shape[1]`; used for decode capture at `:2272-2298`
- `python/sglang/srt/model_executor/cuda_graph_config.py:78-88` — `ALLOWED_KEYS_PER_PHASE[Phase.DECODE]` has no `max_seq_len`; `Phase.PREFILL` has it (plus `max_context_size`)
- prefill already has the fallback this request wants for decode: `deepseek_v4_backend.py:1557-1559` (cap `num_pages` by the graph width) and `:1586-1592` (`can_run_prefill_cuda_graph`)

### Negative control

The identical `--max-model-len` change on vLLM, same box, same checkpoint, moves aggregate throughput by 3.6-4.9% (2048 x8: 1102.8 -> 1142.5; 65536 x8: 829.2 -> 869.9). vLLM's static launch shape with a per-row `[start, end)` loop has no such coupling, which rules out "this is the unavoidable price of sparse attention at 1M".

### What the lever costs today

Against 12h of production traffic, `--context-length=262144` rejects at most 1 request in 5005 (`#cached-token` p99.9 = 199,936 tokens, a 31% margin) while more than doubling decode at the concurrency production actually runs at. But 131072 is another 27% on top and cuts below p99.9 — a capability decision — and 1M becomes unreachable either way.

### Proposal

1. accept `"max_seq_len"` in `ALLOWED_KEYS_PER_PHASE[Phase.DECODE]`;
2. use it as `max_seq_len` for decode graph capture and decode metadata in place of `MAX_SEQ_LEN_FOR_CAPTURE`;
3. replay a decode batch eagerly when its live max sequence length exceeds it (mirror `can_run_prefill_cuda_graph`).

One caveat worth stating up front: the capture width cannot vary per batch, so a naive clamp inside the kernel would be *worse* than the flag — a clamped graph would silently ignore the tail of a longer sequence instead of rejecting it. A decode-only `max_seq_len` needs the same explicit eager fallback prefill has.

### Ask

Is this the intended direction, or is the plan to let #40431 / #40176 absorb the coupling at the kernel level? If the former, I am happy to prototype the config plumbing.

---

*Independent of #40431: that PR makes invisible tiles cheap while keeping the grid; this changes how many tiles exist and lets a 1M-context deployment capture a 128K decode graph.*

### songkuan-zheng · 2026-09-24

Update after re-testing on current `main` (includes #40431), 8 x H200, TP4, DSpark k=5, `--max-running-requests 8`, per-request decode tok/s, median of 5:

| `--context-length` | 2048 x1 | 2048 x8 | 65536 x8 |
|---|---|---|---|
| old image (824bb45e), 1M -> 128K | 98.4 -> 147.93 | 32.1 -> 85.98 (**2.68x**) | 35.31 -> 88.0 |
| main (ffac53d7), 1M -> 128K | 141.06 -> 150.18 | 68.87 -> 102.06 (**1.48x**) | 63.99 -> 94.67 (1.48x) |

#40431 collected most of the gap. What remains is ~1.5x per-request decode at bs=8 (ranges disjoint: 66.5-70.9 vs 101.8-103.8), negligible at bs=1.

The config-width approach proposed here does not work for the configuration that matters most: #40442 captured the full 1.5x but silently truncates context beyond the capture width under DSpark, because the no-sync overlap path deliberately leaves `seq_lens_cpu = None` and a CPU-side guard cannot see live lengths. Details and a reproduction are in the #40442 closing comment; it is closed.

Leaving this issue open as the problem statement: the right fix is kernel-side length awareness, which #40945 now provides for SM90 static target verification. Its own description notes that "ordinary/source score buffers still scale with configured capacity", so the capacity coupling remains on the paths it does not cover.
