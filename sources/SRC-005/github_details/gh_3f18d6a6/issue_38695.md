## Motivation

Router GEMM precision is critical, and it matters most on long multi-turn work, where small differences accumulate over a long CoT. For example, in #29892 the routing precision change was worth +12.6pp resolved on swe-bench Verified (66.8% to 79.4%, 500 problems, GLM-5.2-FP8 on 4xGB300), even though the per-layer logit difference was only 2.6e-7 and single-layer top-k was bit-identical over 400 samples.

The precision that matters is in the output store. cuBLAS already accumulates a bf16 GEMM in fp32, so asking for fp32 output keeps the accumulator and costs nothing. For example, in #29783 we found that doing this on DSv3 moved accept length from 3.413 to 3.894.

Upcasting the activation as well is a much more expensive way to get there. In #29892 that path took 3 kernels at 16.7us per layer against 1 kernel at 8.7us, which over 93 MoE layers came out to 292 tok/s versus 327 tok/s, so -10.5% decode. That PR was closed once we agreed the bf16 GEMM with fp32 output gives the same effect.

Currently, every model in sglang implements its own version of this. For example, `deepseek_v2` has a six-way branch (AMX, deterministic, prefill-CP, tiny-gemm, aiter, cuBLAS), while `nemotron_h` and `minimax_m3` each open-code a bf16 matmul with fp32 output. Meanwhile GLM-4 MoE, `mimo_v2`, `laguna`, `hunyuan_v3`, `sarvam_moe` and `step3p5` still run the expensive activation upcast, so they are paying roughly what #29892 measured for an effect we can get for free. Similarly, `bailing_moe_v3` uses a triton matvec below M=8 and `deepseek_v2` uses tiny-gemm below M=16, so we have two thresholds and two kernels with slightly different numerics, and neither is shared.

Because of this, fixes do not propagate. `mimo_v2` was branched from `deepseek_v2` before #29783 landed, so it still casts the correction bias to bf16. `ernie4` and `kimi_linear` have the same problem, except unconditionally. And `bailing_moe`, `bailing_moe_linear` and `llada2` compute the router in fp32 and then cast the result straight back to bf16, which throws away the precision they just paid for. All of these wrote their own gate. K3 and K2.5 reuse deepseek's, so they picked up the fix for free.

We already have the kernels for this. #34693 already folded the DSv3 router kernel into the shared tiny GEMM for `deepseek_v2`, `dots3` and `kimi_k3`, so the kernel side is consolidating. The bf16 to fp32 GEMM helper in `kernels/ops/attention/dsv4/gemm.py` is also already a four-tier dispatcher (aiter, HPC bf16 split, DeepGEMM, cuBLAS). However, it lives under an attention directory named after one model, and longcat is the only model that opts into the HPC tier or tunes its threshold. Everyone else silently falls through to cuBLAS.

## Proposal

We should add a `RouterGate` layer next to `srt/layers/moe/topk.py` that always hands top-k fp32 logits, computed in bf16. The layer owns the kernel and the output dtype. This is also roughly what vLLM does, where the checkpoint config decides precision and the gate layer picks the kernel.

Deterministic inference should also be handled in the layer. Currently only `deepseek_v2` honors it for the router, so for example `bailing_moe_v3` still switches kernel at small token counts with no guard, and the same token can route differently depending on batch size even with the flag on.

As part of this we should move the bf16 to fp32 GEMM helper out of the DSv4 attention directory, since the router is its main consumer, and move the small-token-count threshold helper out of `models/deepseek_common/`. It currently lives in a model package, which is probably why bailing wrote its own.

Independent of the refactor, there are also three small fixes we can land now: drop the bf16 correction bias in `mimo_v2`, `ernie4` and `kimi_linear`, and drop the cast back to bf16 in `bailing_moe`, `bailing_moe_linear` and `llada2`.

## Benefits

- Every model gets fp32 router logits at the cost of the bf16 GEMM.
- A router numerics fix lands in one place and applies everywhere.
- The HPC and DeepGEMM tiers become available to every model.
- The small-token-count path has one threshold and one kernel.
