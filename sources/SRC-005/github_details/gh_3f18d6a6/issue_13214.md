## 🐛 Bug: `KeyError` when loading Qwen3-Next-80B-A3B-Instruct-AWQ-4bit (MoE model)

### Describe the Bug

I am encountering a `KeyError` when attempting to launch the SGLang server using the latest Docker image (`lmsysorg/sglang:latest`) to load the **Qwen3-Next-80B-A3B-Instruct-AWQ-4bit** model. The model is an **AWQ-quantized Mixture of Experts (MoE)** architecture.

The error occurs during the model weight loading phase, specifically when SGLang's internal model runner (`qwen3_next.py`) tries to access a specific weight key that seems to be mismatched with the actual MoE structure of the provided checkpoint.

### Steps to Reproduce

1.  **Model Used:** The local model folder contains the weights for `cpatonn/Qwen3-Next-80B-A3B-Instruct-AWQ-4bit`.
2.  **Environment:** The server is launched in a Docker container with an **RTX Pro 6000 Blackwell** GPU (though the specific GPU is likely irrelevant to the `KeyError`).
3.  **Launch Command:** The following bash command is executed:

### ErenAta16 · 2026-07-12

I dug into this -- it's a real bug in `Qwen3NextForCausalLM.load_weights()` (`python/sglang/srt/models/qwen3_next.py`), not a checkpoint problem.

The `stacked_params_mapping` list has `("gate_up_proj", "up_proj", 1)`, meant to fuse checkpoints that ship separate `up_proj`/`gate_proj` tensors into the model's single `gate_up_proj` parameter. The match is a plain substring check (`if weight_name not in name: continue`), not a path-segment check.

Your checkpoint (`cpatonn/Qwen3-Next-80B-A3B-Instruct-AWQ-4bit`) ships the shared-expert MLP weight already pre-fused as `...mlp.shared_expert.gate_up_proj.weight` -- common for AWQ-quantized checkpoints, where gate/up get merged before quantization so the int4 groups line up. Since `"up_proj"` is literally a substring of `"gate_up_proj"`, the loop matches on it and does `name.replace("up_proj", "gate_up_proj")`, turning `...shared_expert.gate_up_proj.weight` into `...shared_expert.gate_gate_up_proj.weight` -- exactly the key in your traceback. That key obviously isn't in `params_dict`, hence the `KeyError`. (This fires before any shared-expert-fusion renaming -- your traceback still literally says `shared_expert`, so `enable_shared_expert_fusion` isn't even the trigger here.)

vLLM doesn't hit this because it isn't unconditionally re-running this exact substring-fuse pass against an already-fused name.

The real fix belongs in the matching logic itself (any checkpoint that ships a pre-fused `gate_up_proj` for the shared expert will hit this, not just this one AWQ variant):
```python
for param_name, weight_name, shard_id in stacked_params_mapping:
    if weight_name not in name or param_name in name:
        continue
```
or better, match `weight_name` against a whole `.`-delimited path segment instead of a raw substring.

### ErenAta16 · 2026-09-14

@Prudctual your read of the mechanism matches what I found here in July, but the answer to "unless 13594 already landed" is worth spelling out before you spend time on the PR, because it is neither yes nor no.

#13594 never landed. It is closed, not merged. @hnyls2002 closed it as superseded by #16164, with the note that the prefix plumbing for Qwen3-Next's linear-attention projections resolves the AWQ weight-loading KeyError.

That supersede does not cover this name though. #16164's diff on `python/sglang/srt/models/qwen3_next.py` is `prefix=` arguments threaded into `conv1d`, `in_proj_qkvz`, `in_proj_ba` and `out_proj`, plus giving `in_proj_ba` a real `quant_config` instead of `None`. It never touches `stacked_params_mapping` or anything on the shared-expert path, so the `gate_gate_up_proj` in this issue's title was not what it fixed.

The substring match is still on `main` exactly as you describe: `if weight_name not in name` at line 1183, `("gate_up_proj", "up_proj", 1)` in the mapping, and `replaced_name = name.replace(weight_name, param_name)` at line 1190. So a checkpoint that ships `...mlp.shared_expert.gate_up_proj.weight` pre-fused does still get rewritten into `...mlp.shared_expert.gate_gate_up_proj.weight`.

What changed is that the rewrite no longer reaches a dict lookup, and it is guarded twice rather than once, which is the part that would waste your time:

- With shared-expert fusion enabled, line 1168 rewrites `mlp.shared_expert.` into `mlp.experts.{num_experts}.` before the loop runs, and line 1187's `if "mlp.experts" in name: continue` then skips the stacked mapping for that weight entirely.
- With fusion disabled, the mapping does match and does produce the bad name, but line 1197's `if replaced_name not in params_dict: continue` throws it away. `name` is only reassigned after that guard, so the weight falls out of the loop still carrying its original spelling and gets picked up by the plain loader at the bottom.

So a unit test that asserts `KeyError` is likely not to reproduce on current `main`, and I would check which version you are actually running before building the PR around a crash. The thing still worth fixing is the matching itself, a path-segment or boundary match instead of a substring, and that is a robustness change rather than a crash fix. Same code, different pitch, and the second one is easier to get reviewed because it does not invite "cannot reproduce".

To be clear on the basis: this is a read of `main` at the lines above, not a run. I do not have the GPU stack here to load the checkpoint and confirm end to end, so if you can reproduce the `KeyError` on current `main` then something in the above is wrong and that reproduction is the most valuable thing you could post.
