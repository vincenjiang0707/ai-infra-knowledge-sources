# [PR #39709] [Elastic EP] Start a scale joiner at pipeline stage 0

source: https://github.com/sgl-project/sglang/pull/39709
state: open | updated: 2026-09-23T06:22:18Z

## 正文

## Motivation

An elastic-EP scale joiner is required to run with `--node-rank 1`, and the launch path derived `pp_rank` from `node_rank`. With `--pp-size 1` that placed the joining cohort at pipeline stage 1, so every rank it claimed came out as

```
rank_offset + tp_size * 1 + tp_rank
```

one whole `tp_size` above the window it declared to the process group. Joining a world of size `rank_offset + tp_size` at rank `rank_offset + tp_size` is out of range, and mooncake 0.3.13 rejects it outright:

```
RuntimeError: rank out of valid range
```

Older mooncake did not range-check the rank, which is why this surfaced later and elsewhere — as a joiner that reached the paired expert-location broadcast and never came out of it.

The joiner is not a node of the deployment it joins. It owns a whole TP group on one machine and always starts at pipeline stage 0; its `--node-rank` only marks it as "not the primary's node 0", so reading it as a pipeline coordinate is the bug.

## Modifications

- Pull the `(pp_rank, tp_rank)` coordinate arithmetic in `DataParallelController.launch_tensor_parallel_group` out into a module-level `resolve_local_rank_ranges`, so the joiner reading and the ordinary multi-node reading are stated in one place and the joiner case is testable without launching schedulers.
- A scale joiner now resolves to pipeline stage 0 (`range(1)`) over its full local TP span, instead of inheriting a stage from `node_rank`.
- The helper takes plain scalars and reads no runtime context itself; the call site passes `get_parallel().{pp_size,tp_size,nnodes,node_rank}` and `get_exec().moe.is_ep_scale_joiner`, which are the same namespaces this call site already read (both within the `dp_controller` entry of `ROLE_NAMESPACE_SETS`, so nothing needs widening).
- Add `TestLocalRankRanges` to the existing registered CPU test file.

The non-joiner path is unchanged. I cross-checked the new helper against the replaced block over every combination of `pp_size` in {1,2,4} x `tp_size` in {1,2,4,8} x `nnodes` in {1,2,4} x every `node_rank` (84 shapes); all four return values are identical. The only behavioral change is the joiner branch.

## Accuracy Tests

Verified on 8xH100: a 4 -> 6 scale-up now completes, the joining ranks allocate their KV pool, and requests pinned to `dp_rank` 4 and 5 return output identical to `dp_rank` 0.

## Speed Tests and Profiling

Not applicable — this is launch-path coordinate arithmetic, outside any serving hot path.
