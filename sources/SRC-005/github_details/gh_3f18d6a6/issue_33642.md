## Description

Running a PD-disaggregated **decode** instance with DSA attention + EAGLE speculative decoding (Spec V2), the server starts up normally (weight loading, CUDA graph capture and warmup all complete), but it **hangs forever on the first real decode request**. After `watchdog_timeout=300s` the watchdog fires, dumps py-spy stacks, but does not recover. The process stays hung indefinitely (only `/metrics` keeps responding).

All 8 scheduler processes (DP0~~7 / TP0~~7 / EP0~7) are blocked at the **exact same stack**, inside the CUDA driver's `cuModuleLoadData` while Triton lazily loads the freshly JIT-compiled binary of the `fused_dsa_target_verify_metadata` kernel:

```
Thread (active): "MainThread"
    cuModuleLoadData (libcuda.so.590.48.01)
    loadBinary (cuda_utils.cpython-312-x86_64-linux-gnu.so)
    _init_handles (triton/compiler/compiler.py:466)
    launch_metadata (triton/compiler/compiler.py:482)
    run (triton/runtime/jit.py:743)
    fused_dsa_target_verify_metadata (sglang/kernels/ops/attention/dsa_metadata.py:407)
    _apply_cuda_graph_metadata (dsa_backend.py:1604)
    init_forward_metadata_out_graph (dsa_backend.py:845)
    load_batch (runner/decode_cuda_graph_runner.py:1189)
    eagle_prepare_for_verify (eagle_utils.py:571)
    run_eagle_verify (eagle_worker_common.py:495)
    verify (eagle_worker_v2.py:1464)
    forward_batch_generation (eagle_worker_v2.py:1160)
    run_batch (scheduler.py:3452)
    event_loop_overlap_disagg_decode (decode.py:2273)
```

Note that the stack is already inside `loadBinary`, i.e. the Triton compile itself finished — the hang happens while the driver loads the cubin.

## Observations

1. **Timeline**: server ready at T0 (Application startup complete, CUDA graphs captured). The first decode request arrives via PD transfer (~4 input tokens, `max_new_tokens=8`). All ranks enter the first EAGLE verify and never return. Watchdog fires exactly `watchdog_timeout=300s` later.
2. `fused_dsa_target_verify_metadata` is invoked through `init_forward_metadata_out_graph`, i.e. it runs **outside** the captured CUDA graph. Therefore it is not compiled during CUDA graph capture and is lazily JIT-loaded on the first real request.
3. All 8 ranks hit this lazy load **simultaneously** (DP attention: only DP1 has a real batch, other ranks run with empty batches but still participate in the forward), and all of them deadlock inside `cuModuleLoadData`.
4. No NCCL errors, no OOM, no Python exception anywhere in the log.

## Questions / Hypotheses

* Should this out-of-graph DSA metadata kernel be warmed up at startup (like the other kernels touched during CUDA graph capture) so the first request doesn't trigger a concurrent 8-rank lazy load?

* Or is this a known CUDA driver deadlock on sm\_103 + driver 590.48.01 when multiple contexts concurrently load a newly JIT-compiled module?
