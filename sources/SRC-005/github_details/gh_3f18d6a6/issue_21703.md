## Motivation
Prefill-Decode Disaggregation has been an important and widely adopted feature for LLM inference production.
Although we have almost made it compatible with different model architectures, all parallel strategies, and almost all advanced features, there are always new models/features coming up, which we also want to support in PD mode.

This issue will act as a roadmap or a tracker for those who are interested in the latest progress of this feature (at least it will include some related experimental features we will conduct in 2026 Q2).

## Advanced feature and usage
 - [x] Context parallel compatibility after refactor https://github.com/sgl-project/sglang/pull/19504 https://github.com/sgl-project/sglang/pull/19765
 - [x] GPU staging buffer for accelerating heterogeneous TP KV transfer https://github.com/sgl-project/sglang/pull/19890 @YAMY1234 
   - For MHA/GQA models, there are many small pieces of KVCache transfer for a heterogeneous TP setup of PD, which will slow down the transfer process. This feature will gather the KV heads at prefill, then send the kvcache to decode by uniting them as a large piece through a ring-based staging buffer (really helpful for GB platforms).
 - [x] Compatibility with Hisparse https://github.com/sgl-project/sglang/pull/21591 @hzh0425 
   - This feature will allow us to send kvcache from prefill HBM to decode host memory when enabling hisparse for NSA models (DeepSeek V3.2/GLM 5). It will help us to get a much bigger batch size on the decode side since we only keep the topk sparse KVCache in HBM, and make all other KVCache stored in the host memory.
 - [x] Prefill send delta KVCache while Decode fetch prefix from Hicache for agentic use cases https://github.com/sgl-project/sglang/pull/26227 @hzh0425  
 - [x] Decode RadixCache https://github.com/sgl-project/sglang/pull/19746 @ishandhanani 
   - For agentic scenarios, decode can now use radix cache to reuse shared prefixes and request only the delta KV from prefill instead of transferring the full prefix on every turn.
 - [x] Optimistic prefill for better TTFT https://github.com/sgl-project/sglang/pull/26780 @cctry 
   -  the prefill worker may start computing before bootstrap is fully finalized. If bootstrap completes in time, the request proceeds normally. If bootstrap is still pending or fails, the request retries or falls back to the normal bootstrap path.
 - [ ] Better compatibility with Spec decode: support heterogeneous target/draft model architectures https://github.com/sgl-project/sglang/pull/20698
   - This feature will allow us to use different draft architectures from target models when enabling speculative decoding or MTP (specforge/torchspec might need it).
 - [ ] Layerwise KVCache transfer https://github.com/sgl-project/sglang/pull/19931 @zhangxiaolei123456 @UNIDY2002 https://github.com/sgl-project/sglang/pull/23515
 - [ ] Support Prefill PP + MTP for PD Disaggregation mode
 - [ ] Runtime role transitions https://github.com/sgl-project/sglang/pull/28403

### inkcherry · 2026-06-17

We're working on a joint optimization of external scheduling and PD disaggregation, and opened #28403 as a first building block.

Today each instance's role (prefill/decode) is pinned at startup, so rebalancing the P:D ratio requires draining and relaunching servers. #28403 introduces runtime prefill↔decode role switching for the first time — an operator/router can flip an instance's role live (POST /pd_role_switch), in place, without restarting or reloading weights (the KV pool is role-independent, so only the small role-specific disagg structures are rebuilt).

The value: a router can dynamically switch roles based on system metrics in response to real-time load/traffic shifts, to improve performance. It implements the basic control-plane primitive plus the mori backend implementation; the control plane is backend-agnostic, so other backends can opt in with the same pattern. Our scheduler is integrated with AMD's storage backend and will be open-sourced soon.

We'd really appreciate any feedback or suggestions, and would be glad if this could be considered as part of the PD roadmap. Thanks a lot for putting this roadmap together! cc @ShangmingCai

**Key observations:**
1. **MTP under PD is solid** — accept 3.0–3.38 (vs our b852d-based baseline 3.10), zero asserts across cells and a 60-min sustained 122B MTP3-PD soak (46,826 requests, 0 failures).
2. **DFLASH is broken on new main even single-node** — decode CUDA-graph capture crashes with `ValueError: too many values to unpack (expected 2)` at `qwen3_vl.py:1642` (`hidden_states, aux_hidden_states = hidden_states` under `capture_aux_hidden_states`), reached from the Qwen4-Exp DFLASH path. Works on the #38642 branch, which carries the Qwen4-Exp capture guard main is missing (the `not self.capture_aux_hidden_states` condition on the HC-stream overwrite); rebase-verified on 2×8 A800. Filed as #39685.
3. **DFLASH-PD dispatch (from #34285) is already in main** (`spec_info.py:214`) but is unreachable until the capture regression is fixed — the decode node dies in graph capture before any target-verify dispatch.
4. temp0 determinism: PD self 6/8 vs standalone 4/8 (no-thinking, 8 prompts) — engine is numerically nondeterministic at temp0 on SM80; PD self-consistency ≥ standalone baseline (no transfer-induced drift).

Happy to run more cells (e.g. DSPARK, or DFLASH once the capture fix lands) on request.
