# [PR #40596] [Perf] Fork workers from a preloaded forkserver (SGLANG_ENABLE_EARLY_FORKSERVER)

source: https://github.com/sgl-project/sglang/pull/40596
state: open | updated: 2026-09-23T06:37:10Z
labels: documentation, quant, run-ci, run-ci-extra, bypass-fail-fast

## 正文

Second PR of the startup stack, after #40201 (merged). The target of this PR is to enable forkserver and avoid re-import on every child process.
Next step is lift forkserver and child process spawn earlier and runs in parallel with launcher import to further reduce latency.

## Motivation

Under `spawn` every worker (scheduler, DP controller, detokenizer) is a fresh interpreter that re-imports sglang, torch and the kernel packages: 7-9 s per worker, and the DP controller pays it again for the schedulers it starts. A forkserver imports those modules once and forks each worker from itself, so a worker starts in well under a second. The launcher cannot be the fork parent: it has threads and, through `sgl_kernel`, a CUDA context.

## Modifications

`SGLANG_ENABLE_EARLY_FORKSERVER=1` (off by default): `sglang serve` starts the multiprocessing forkserver at CLI entry with the worker modules preloaded and forks the workers from it. Every other entry point keeps `spawn`.

A forkserver child differs from a spawned one in three ways. Each gets exactly one mechanism, in `entrypoints/early_forkserver.py`:

- **Process state.** The child inherits the *server's* environment and rlimits, not the launcher's. sglang registers its own start method, `sglang_forkserver`: its `_Popen` attaches the launcher's environment and rlimits to the process object, and an after-fork hook registered in the server applies them before `run()` (environment as a three-way merge of the changes made since CLI entry; what the preload imports set stays).
- **Parentage and lifetime.** The OS parent is the server. The five sites that signal their parent (workers and the watchdog) call `get_parent_process()` = `psutil.Process(multiprocessing.parent_process().pid)`, the caller of `start()`, identical to the OS parent under `spawn`. The child releases the server's alive pipe, so the launcher is its only holder: the server exits with the launcher, and the `PR_SET_PDEATHSIG` the workers already arm takes them down as under `spawn`. No watch threads, no psutil patching.
- **CUDA.** The server must never initialize CUDA. While the preload runs, the GPU probes `sgl_kernel` and flashinfer make at import are answered from NVML (torch ordinal mapped to the NVML index); the child restores the real `torch.cuda` functions and exits naming the cause if it finds itself in a bad fork.

Fallbacks: `--enable-memory-saver` (its hook is `LD_PRELOAD`ed into an exec'd worker) and a non-LLM `serve` backend stop the server and use `spawn`. When the forkserver is used, NUMA binding takes the in-process path (`SGLANG_NUMA_BIND_V2=false`, logged if the user had set it). Linux and CUDA only.

Second commit: two module-level constants derived from env vars that argument resolution writes (`MOE_NVFP4_DISPATCH`, `MM_FEATURE_CACHE_SIZE`) are read where they are used, and a static test fails on any preloaded module that snapshots, at import, a variable sglang writes at runtime (through `Envs` or raw `os.environ`).

Outside the new module: 5 lines in `cli/main.py`, 4 in `cli/serve.py`, 3 in `engine.py`, one `Envs` entry, `get_parent_process()` and its five call sites.

## Accuracy Tests

Workers run unchanged code; the flag changes only how the process is created. `/generate` on Qwen3-1.7B returns the same greedy completion with the flag on and off (single GPU, DP2, TP2).

## Speed Tests and Profiling

Qwen3-30B-A3B on 2x H200, time from `sglang serve` to `/health` 200, mean of 3 warm runs (range), knobs off vs `SGLANG_ENABLE_EARLY_FORKSERVER=1`:

| config | knobs off | forkserver |
|---|---:|---:|
| Single GPU | 62.4 s (61.4-64.4) | 59.1 s (56.4-63.4) |
| DP2 | 71.5 s (70.5-72.5) | 67.1 s (58.4-83.6) |
| TP2 | 65.4 s (60.4-74.5) | 59.7 s (57.4-62.4) |
| EP2 (DeepEP) | 57.4 s (57.4-57.4) | 54.0 s (45.3-67.5) |

Where the time goes (rank-0 log stages, seconds). Process init is imports + spawn/fork + scheduler setup, the stage this PR changes; weight loading and CUDA graph capture are untouched and now dominate:

| config | mode | process init | weights | KV pool | graph capture | ready |

| Single GPU | off | 20.9 | 14.3 | 2.3 | 21.7 | 2.7 |
| Single GPU | forkserver | 15.7 | 14.3 | 1.7 | 23.7 | 3.3 |
| DP2 | off | 28.9 | 14.3 | 2.0 | 21.7 | 4.0 |
| DP2 | forkserver | 16.3 | 14.0 | 2.3 | 29.7 | 4.3 |
| TP2 | off | 21.1 | 10.3 | 2.0 | 28.3 | 3.0 |
| TP2 | forkserver | 17.3 | 10.7 | 1.7 | 26.0 | 3.3 |
| EP2 | off | 29.1 | 8.0 | 2.0 | 14.7 | 3.0 |
| EP2 | forkserver | 19.6 | 9.0 | 2.3 | 19.7 | 3.0 |

The forkserver alone removes 4-13 s of process init (most on DP2/EP2, where the controller no longer re-imports before starting the schedulers). The remaining ~16 s of process init is the launcher's own import and argument resolution before it requests the workers; the pre-spawn PR that follows overlaps it. The two wide `forkserver` ranges (DP2, EP2) come from single graph-capture outliers (29.7 s / 19.7 s vs 21.7 / 14.7), not from process start; a reversed-order pass showed no order effect.

Behaviour checks (Qwen3-1.7B): `kill -9` of the launcher takes the server and the workers down within 2 s; `kill -9` of a scheduler triggers the usual SIGQUIT teardown (6 s, same as spawn).

Tests: `test/registered/unit/entrypoints/test_early_forkserver.py`, 14 cases on CPU CI, including a real forkserver preloading only this module, a worker forked from it and a worker forked from that worker: environment and rlimits, parentage, nested reuse, process title, and that the server and its workers go down with the launcher.
