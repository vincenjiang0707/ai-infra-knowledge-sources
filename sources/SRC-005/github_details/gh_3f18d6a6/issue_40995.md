### Motivation

Currently on pytorch images, there is  automatic AWS EFA & auto gcp nccl plugin detection & setup such that efa & gcp networks work out of the box. [source: https://docs.nvidia.com/deeplearning/frameworks/pytorch-release-notes/rel-26-07.html ] 

Unfortunately on SGLang images, using NIXL EFA & Mooncake EFA requires an massive undocumented script to download the correct EFA userspace libraries. (related workstream in vLLM community in https://github.com/vllm-project/vllm/pull/55783  )

Any chance that EFA NIXL  & EFA mooncake can work out of the box on SGLang too?

For NIXL, it requires manually installing the efa userspace libs in https://github.com/sgl-project/sglang/blob/main/docker/Dockerfile.cu134 

For Mooncake it requires uninstalling `mooncake-transfer-engine-cuda13` preinstalled in the image and then installing `mooncake-transfer-engine-efa-cuda13==0.3.13.post1` , `mooncake-transfer-engine-efa-cuda13` itself does not work with SGLang yet  then following this gaint list of instructions. Note that these list of instructions is only valdiated on nightly containers and not in current `0.5.20` release container yet

instructions from sglang community in https://github.com/sgl-project/sglang/pull/39973

```
On an x86_64 AWS EFA instance, replace the standard CUDA 13 Mooncake package with the EFA build. The two packages install the same `mooncake` Python module, so do not install them side by side.

The following commands replace the package in an SGLang CUDA 13 environment while preserving its existing Python dependencies:

python3 -m pip uninstall -y \
  mooncake-transfer-engine-cuda13 \
  mooncake-transfer-engine-efa-cuda13
python3 -m pip install --no-deps \
  mooncake-transfer-engine-efa-cuda13==0.3.13.post1

export LD_LIBRARY_PATH="/opt/amazon/efa/lib:/opt/amazon/efa/lib64:${LD_LIBRARY_PATH:-}"
export MOONCAKE_PROTOCOL=efa

python3 -c 'from mooncake import engine; assert engine.SUPPORT_EFA'
fi_info -p efa -t FI_EP_RDM

The EFA wheel expects a compatible AWS EFA userspace installation on the host and does not bundle `libfabric` or `libefa`. The current wheel is available only for x86_64. It is built without Mooncake EP/PG and the NVLink/MNNVL components, so use the standard Mooncake CUDA package for those features.

The current libfabric EFA provider cannot transfer CUDA VMM-backed buffers. Until [libfabric issue #12853](https://github.com/ofiwg/libfabric/issues/12853) is resolved, apply these settings to both prefill and decode workers:

- Do not set `SGLANG_MOONCAKE_CUSTOM_MEM_POOL` to `NVLINK` or `BAREX`.
  `INTRA_NODE_NVLINK` is supported because it uses the default CUDA allocator.
- Do not enable `expandable_segments:True` in `PYTORCH_CUDA_ALLOC_CONF` or `PYTORCH_ALLOC_CONF`.
- Post-capture KV sizing is automatically disabled for the EFA protocol because
  its KV cache uses CUDA VMM allocations.
- Do not set `MC_FORCE_MNNVL` or `NCCL_MNNVL_ENABLE`; EFA is not an MNNVL transport.

SGLang validates the first two constraints at startup to avoid a later `fi_read` or `fi_write` failure from libfabric.
```

### whn09 · 2026-09-24

Thanks @functionstackx — I maintain the Mooncake EFA wheels, so a few notes from that side.

**What "out of the box" would take.** Neither NIXL nor Mooncake bundles `libfabric`/`libefa`, so one EFA userspace install covers both. On top of that, an EFA image needs:
1. aws-efa-installer in the image (`--skip-kmod --no-verify`)
2. `mooncake-transfer-engine-efa-cuda13` instead of `mooncake-transfer-engine-cuda13`, e.g. behind a build arg, since both provide the same `mooncake` module
3. `/opt/amazon/efa/lib` on `LD_LIBRARY_PATH`, because the Ubuntu 24.04 `libfabric` in the current image is too old for the EFA provider

**The main blocker for a single default image is rdma-core.** The EFA installer replaces the Ubuntu `rdma-core`/`libibverbs` that the image installs today with its own `64.0amzn0` build, which uses a custom provider ABI (`rdmav64amzn0`). It still ships mlx5 and other providers, but everything else in the image that talks to IB/RoCE goes through that libibverbs: DeepEP/NVSHMEM, and Mooncake/NIXL over RDMA. NIXL's UCX also vendors its own libibverbs. So before EFA userspace becomes the default rather than an AWS-specific variant/tag, someone should run the existing IB/RoCE paths on it.

**On "efa-cuda13 does not work with SGLang yet":** could you share what fails? The known limitation is CUDA VMM-backed buffers (ofiwg/libfabric#12853). #39973 (thanks @nvpohanh, @ShangmingCai) turns that into a startup error for the custom mem pools and `expandable_segments`, but it isn't in 0.5.20 yet. `--enable-memory-saver` probably hits the same VMM path and isn't covered by that guard yet. That's worth a check.

**arm64:** aws-efa-installer supports aarch64, and aarch64 EFA wheels for Mooncake are merged (kvcache-ai/Mooncake#4305) and ship with the next release. They're already tested over EFA on Graviton. After that release, the "x86_64 only" note and the `0.3.13.post1` pin in the #39973 docs can be updated.

**When validating:** check the logs for the backend that was actually selected. NIXL quietly falls back to UCX when the LIBFABRIC plugin fails to load, and Mooncake falls back to TCP.
