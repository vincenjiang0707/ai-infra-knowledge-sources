# [PR #40438] [NPU] Skip fused gmm1+swiglu for swiglu_limit (SiLU-with-clamp) checkpoints

source: https://github.com/sgl-project/sglang/pull/40438
state: open | updated: 2026-09-23T07:06:47Z
labels: npu, run-ci

## 正文

## Motivation

Follow-up to #39881. The fused gmm1 kernel ( npu_grouped_matmul_swiglu_quant_v2 ) applies plain SiLU with no clamp , but _uses_fused_gmm1 selected it for W4A8 MXFP4 MoE based only on the kernel type and use_fused_gmm1 — it never looked at the activation configuration.

Checkpoints whose MoE activation is SiLU-with-clamp ( swiglu_limit , e.g. DSV4) therefore lost the clamp when the fused kernel was selected, producing incorrect numerics. This silently bypassed the clamp path ( NPUSwigluMxfp8Quant ) that #38420 had just added for exactly this case.

## Modifications

Single-file change in python/sglang/srt/layers/moe/moe_runner/ascend.py :

- _uses_fused_gmm1(kernel, config) now takes the runner config and returns False when config.swiglu_limit is set and > 0 :
  - W4A8 MXFP4 + swiglu_limit (DSV4): falls back to the unfused path — w13 gmm + NPUSwigluMxfp8Quant(config.swiglu_limit) , which applies the clamp. This restores the pre-#39881 behavior
  - MXFP8 + swiglu_limit : raises NotImplementedError at init — this method has no unfused gmm1 path, so failing loudly beats silently serving wrong numerics (no known checkpoint hits this combination today)
  - Plain-SiLU models ( swiglu_limit unset or 0 ): keep the fused kernel, unchanged
- Both call sites ( __init__ and run() ) now pass the same config, so the activation selection and the fused/unfused branch decision can never disagree

## Accuracy Tests

- Dispatch logic verified locally with mocked kernels for all combinations: W4A8 ± swiglu_limit, MXFP8 ± swiglu_limit, use_fused_gmm1=False , and non-fused kernels — all resolve as intended
- DSV4 on NPU (fp4 experts → NPUW4A8MXFP4MoEMethod , swiglu_limit from HF config) now resolves to the unfused clamp path, bit-identical to the pre-#39881 serving path

## Speed Tests and Profiling

None — this PR intentionally trades the #39881 fusion gain back for correctness on clamp checkpoints. Plain-SiLU models (e.g. Kimi-K3 MXFP4) keep the full fused-path benefit (~15% per-layer MoE latency reduction from #39881). Recovering the fusion gain for clamp checkpoints would require adding a limit parameter to the fused kernel, which is kernel-side work out of scope here.
