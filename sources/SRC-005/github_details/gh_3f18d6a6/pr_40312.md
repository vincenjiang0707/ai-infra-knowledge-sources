# [PR #40312] [HiCache] fix: bound the controller reset join so a stalled storage thread cannot hang the scheduler

source: https://github.com/sgl-project/sglang/pull/40312
state: closed | updated: 2026-09-23T03:52:57Z
labels: hicache, run-ci, bypass-fastfail, run-ci-extra

## 正文

## Motivation

`HiCacheController.reset()` previously set `storage_stop_event` and called
untimed `join()` on four storage threads. If a thread does not exit, reset can
wait indefinitely and block the scheduler. This change hardens the reset
teardown by reusing the existing detach helper, `_stop_storage_threads()`.

## Modifications

`reset()` now uses the helper's queue wakeup sentinels, bounded joins, and final
thread-liveness check before clearing shared state and restarting storage threads.
Sentinels can wake threads waiting on queues; they cannot interrupt an in-progress
`all_reduce()`. Likewise, a join timeout only bounds the caller's wait and does
not terminate the worker or cancel its collective.

The helper joins four threads sequentially, with `timeout=10` for each, so the
combined join wait can reach approximately 40 seconds, not 10 seconds total.
After all joins, it raises `RuntimeError` if any thread remains alive. This prevents
reset from clearing shared state and starting replacement threads while an old
thread is still running. The queue clearing, stop-event clearing, and thread
re-creation after a successful stop remain unchanged.

A prefetch thread blocked in a cross-rank collective is a possible stalled-thread
scenario inferred from the source, not a reproduced failure. This PR bounds the
reset wait; it does not resolve the underlying collective stall. Treat it as a
hardening change pending validation of that scenario's reachability.
