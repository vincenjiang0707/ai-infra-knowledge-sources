# [PR #38799] [AMD][DSA] Extend Triton sparse-MLA prefill to gfx942 (MI308X) via 2-query merged programs

source: https://github.com/sgl-project/sglang/pull/38799
state: open | updated: 2026-09-23T06:19:28Z
labels: jit-kernel

## 正文

## Motivation

The Triton per-query sparse-MLA prefill kernel (`SGLANG_DSA_TRITON_PREFILL=1`) is gated to **gfx950 + exactly 16 q-heads per card**: the per-query program places the head count `H` on the MFMA **M** dimension, and CDNA matrix cores require `M >= 16`. On **gfx942 (MI308X)** with GLM-5.3-class models at **TP8** there are only **8 heads per card**, so the fast path was unreachable and DSA prefill always fell back to TileLang (~3200 tok/s ceiling measured on this shape).

## Modifications

**`triton_sparse_mla.py`** — merge **2 query tokens per program**: `2 tokens × 8 heads = 16 rows`, so `M = 16` is legal with **zero wasted compute** (no head padding/duplication, which was tried first and measured 2× FLOP waste → −5.7% at C=64). The two tokens' topk KV sets are gathered into a single `NTOK*BLOCK_N` column block and kept disjoint via a structured **block-diagonal mask** (`row_tok == tok2`), so tokens never attend each other's KV. Odd `seq_len` boundaries are handled by load/store masks on the trailing token. The fp8 numerics (QK in fp8, `p` quantized to fp8 for the PV dot) are unchanged.

**`dsa_backend.py`** — gate changes:
- `_IS_GFX95` → `_is_hip` (gfx942 is also a HIP arch; the kernel itself remains shape-gated)
- `tp_q_head_num == 16` → `in (8, 16)`

## Validation

Hardware: **8× MI308X (gfx942, ROCm 7.2.0)**, GLM-5.3 (`GlmMoeDsaForCausalLM`, FP8 block 128×128), TP8, EAGLE 5/1/6, `fp8_e4m3` KV, random ISL 8192 / OSL 1024, `n = CON × 10`.

**Correctness (three layers):**
1. Kernel-level deterministic comparison vs `tilelang_sparse_fwd` on fixed fp8 tensors (seq=512, H=8, d_v=512, tail=64, topk=2048, fnuz): **max_abs_diff 0.001984**, `allclose(atol=0.03) = True` — bf16-output-level equivalent.
2. Standalone unit test (even `seq=128` and odd `seq=127` boundary cases) vs a dense softmax-over-topk reference with identical fp8 numerics: max_abs_err **0.02474 / 0.01365**, both PASS at `atol=rtol=0.03`.
3. End-to-end EAGLE accept length stays **6.00 / rate 1.00** (greedy), same as the TileLang path.

**Throughput — kernel level (primary claim):** on identical 8192-token prefill batches from the server logs (same host, same firmware `113-M3080202-101`, same selected autotune config `BLOCK_N=32/warps=2/stages=1`):

| Path | 8192-token prefill throughput (TP0, top-5 batches) |
|---|---|
| TileLang baseline | ~3205 tok/s (3223.93 / 3218.16 / 3202.79 / 3201.39 / 3200.86) |
| Triton 2-query | **~3370 tok/s** (3712.52 / 3370.69 / 3369.63 / 3367.09 / 3366.57) |

⇒ **~+5% on the isolated sparse-MLA prefill kernel at this shape (8K, H=8, topk=2048)**.

**End-to-end numbers (machine-specific context, not the primary claim):** an independent reproducer on a different MI308X host (same image/patches/driver, different VBIOS build `113-M3080101-100`) measured both backends within ~0.1–0.8% of each other at C1, and our own end-to-end table below turned out to straddle a firmware change on our host — so the end-to-end deltas are dominated by host/firmware drift, not the kernel. Kept for the record:

| Point | Metric | TileLang | Triton 2-query | Δ |
|---|---|---|---|---|
| C=64 | Output tok/s | 283.45 | 365.03 | +28.8% |
| C=64 | TPOT ms | 160.4 | 123.7 | −22.9% |
| C=1 | TTFT ms | 3626 | 2266 | −37.5% |

## Notes for reviewers

- The 2-query merge also **unblocks the 8-heads-per-card shape on gfx950** (e.g. TP8 on MI350X), which the old `== 16` gate excluded.
- Serving-time autotune compilation of the merged kernel takes **~213 s** on first use (18 configs); pre-compile it during engine init or raise `--watchdog-timeout` for the first request. After the first compile the Triton cache hits and there is no recurring cost.
- A head-padding variant (pad 8→16 by row duplication) was built and measured first: correct but **−5.7%** at C=64 (50% wasted FLOPs) — the 2-query merge is the design that actually wins on this shape.

## Heads-up from gfx950 (MI350X) validation: the 2-query kernel needs its own autotune exclusion set

While validating this 2-query merged kernel on **MI350X (gfx950, capability 9.5), Triton 3.7.0** (fp8_e4m3 KV, TP4, H=16), I hit a **different** autotune crash set than the per-query kernel (#35274):

### Per-config bisect on gfx950 (each config in its own process, seq=2624)

| config (BLOCK_N, warps, stages) | verdict |
|---|---|
| **(32, 2, 2)** | **rc=134 — LLVM `iota_range Begin <= End` assert (Sequence.h:275) during compile** |
| **(64, 4, 2)** | **rc=134 — same assert** |
| **(128, 2, 2)** | **rc=134 — same assert** |
| **(128, 4, 2)** | **rc=134 — same assert** |
| (128, 1, 2) | rc=0 PASS (compiles fine on this kernel — unlike the per-query kernel) |
| other 13 configs | rc=0 PASS, finite=True |

⇒ On gfx950 + Triton 3.7.0, **every `num_stages=2` config crashes the compiler** on this kernel's IR. The crash is **config x kernel-IR specific**: the per-query kernel crashes on (128,1,2) only, this 2-query kernel crashes on the four `num_stages=2` configs instead — the two sets are disjoint.

### Suggested guard for the gfx950 path

```python
_is_gfx950 = torch.cuda.is_available() and torch.cuda.get_device_capability(0) == (9, 5)
_AUTOTUNE_CONFIGS = [
    triton.Config({"BLOCK_N": bn}, num_warps=w, num_stages=ns)
    for bn in (32, 64, 128)
    for w in (1, 2, 4)
    for ns in (1, 2)
    if not (_is_gfx950 and ns == 2)  # LLVM iota_range compile assert on gfx950 + Triton 3.7.0
]
```

Verified with this exclusion: full seq sweep **6/6 PASS** (2624/2625/5127/8192/512/1023, incl. odd shapes), and server-level long-prompt loads (previously 100% crash x2) run clean with crash=0. gfx942 (MI308X) keeps the full grid — verified good there on 2026-09-10.

### Repro methodology (in case maintainers want to verify)

- Isolated per-config harness: pin `kernel.configs = [one triton.Config]`, fresh `TRITON_CACHE_DIR` per invocation, call the wrapper directly with synthetic fp8_e4m3 tensors (server-real dtype — the fnuz variant takes an upcast path on gfx950 that crashes on its own and is a repro artifact).
- Drop-one cross-check on the full autotune list confirms the crash set is exactly the four configs above.
- Server-level: any request with `q_nope.shape[0] >= 512` entering this path crashes all TP schedulers during serving-time autotune compile; the `>= 512` gate means short-prompt benchmarks never exercise it.

Happy to turn this into a follow-up commit on this PR (or a separate PR) if maintainers prefer — the 2-query kernel itself is sound on gfx950 once the crashing configs are excluded.
