### Describe the bug

Serving `zai-org/GLM-5.3-Flash` on **8x RTX PRO 6000 Blackwell Server Edition (sm_120)** fails at
startup. After working around the known `deep_gemm` NameError (#29738), **two further blockers**
appear, both in the DSA attention backend. Neither is reachable by configuration.

This mirrors #33194 (same model family, SM80/Ampere): the DSA/MHC kernels appear to assume
**datacenter-class** GPUs (sm_90 Hopper / sm_100 Blackwell DC). sm_120 is a workstation part with
**half the shared memory and no TMEM/tcgen05**.

### Environment

```
GPU            8x NVIDIA RTX PRO 6000 Blackwell Server Edition (sm_120)
shared mem     102,400 B / SM   (H200 sm_90: 227 KB)
driver         610.43.02
image          lmsysorg/sglang:glm-5.3-flash   (base aa8c950a3d)
model          zai-org/GLM-5.3-Flash  (index_kpool=4, 45 layers, 288 experts)
launch         --tp-size 8 --data-parallel-size 8 --enable-dp-attention
               --expert-parallel-size 8 --disable-shared-experts-fusion
               --moe-runner-backend deep_gemm --kv-cache-dtype bfloat16
               --mm-enable-dp-encoder --context-length 1048576
```

### Blocker 0 (pre-existing, #29738) — triggered automatically on sm_120

`configurer.py` deliberately excludes sm_120:

```python
# python/sglang/srt/layers/deep_gemm_wrapper/configurer.py
# "DeepGEMM requires TMEM/tcgen05 (SM100+datacenter), not available on SM120"
if sm_version == 120:
    return False        # -> ENABLE_JIT_DEEPGEMM = False
                        # -> entrypoint.py:19 `if ENABLE_JIT_DEEPGEMM: import deep_gemm` is skipped
```

but `SGLANG_OPT_DEEPGEMM_HC_PRENORM` is hardware-independent:

```python
# python/sglang/srt/environ.py
SGLANG_OPT_DEEPGEMM_HC_PRENORM = EnvBool(True)   # always True
```

so `mhc.py` still takes the deep_gemm branch and `entrypoint.py` calls it unguarded:

```
NameError: name 'deep_gemm' is not defined
  at srt/layers/deep_gemm_wrapper/entrypoint.py  tf32_hc_prenorm_gemm()
  <- kernels/ops/layernorm/mhc.py  mhc_pre
  <- srt/models/glm5_next.py  hc_attn_pre
```

Measured on this host: `ENABLE_JIT_DEEPGEMM=False` while `SGLANG_OPT_DEEPGEMM_HC_PRENORM=True`.

**On sm_120 these two flags are always inconsistent** — #29738 required setting an env manually;
here it happens out of the box. Suggest gating `SGLANG_OPT_DEEPGEMM_HC_PRENORM` on
`ENABLE_JIT_DEEPGEMM`, or guarding the call site.

**Workaround:** `SGLANG_OPT_DEEPGEMM_HC_PRENORM=0` (takes the non-deep_gemm branch in `mhc_pre`).
This works — and exposes the next two blockers.

### Blocker 1 — auto-selected `trtllm` DSA decode backend is unsupported on sm_120

```
Set DSA backends for bfloat16 KV Cache: prefill=flashmla_sparse, decode=trtllm
Capture cuda graph failed: Error in function 'TllmGenFmhaRunner'
  at /workspace/include/flashinfer/trtllm/fmha/fmhaRunner.cuh:37: Unsupported architecture
```

The auto-selector picks `trtllm` for Blackwell, but the TRT-LLM Gen FMHA kernel only supports
sm_100. `prefill=flashmla_sparse` itself passed — the failure is decode-side only.

### Blocker 2 — `tilelang` needs more shared memory than sm_120 has

Forcing both ends to tilelang (the combination used successfully on H20, and the one required by
the fp8-KV gate in #36904):

```
Set DSA backends for bfloat16 KV Cache: prefill=tilelang, decode=tilelang
tvm.error.InternalError: Failed to set the allowed dynamic shared memory size to 206848
```

```
requested   206,848 B  = 202 KB
available   102,400 B  = 100 KB   (hardware limit on sm_120)
```

This is a hard hardware limit, not configuration. It also means the **fp8 KV path of #36904 is
unreachable on sm_120**, since that gate requires tilelang on both ends.

### Reproduction

```bash
docker run --rm --gpus all --network host --ipc host --shm-size 32g \
  -v /path/to/GLM-5.3-Flash:/model:ro \
  -e SGLANG_OPT_DEEPGEMM_HC_PRENORM=0 \
  lmsysorg/sglang:glm-5.3-flash \
  python3 -m sglang.launch_server --model-path /model --trust-remote-code \
    --tp-size 8 --data-parallel-size 8 --enable-dp-attention --expert-parallel-size 8 \
    --disable-shared-experts-fusion --moe-runner-backend deep_gemm \
    --kv-cache-dtype bfloat16 --mm-enable-dp-encoder --context-length 1048576
```

### Questions

1. Is sm_120 (RTX PRO 6000 / RTX 5090 class) intended to be supported for GLM-5.3-Flash?
2. If yes, is there a DSA backend combination that fits within 100 KB shared memory?
   `prefill=flashmla_sparse` works; which decode backends are validated on sm_120?
3. Should `SGLANG_OPT_DEEPGEMM_HC_PRENORM` default be derived from `ENABLE_JIT_DEEPGEMM`
   so the sm_120 exclusion is self-consistent?

### Hansen523 · 2026-08-31

## Resolved — both blockers cleared on sm_120; posting the working configuration

Both blockers in the original report are resolved. **One conclusion in my report was too strong and I want to correct it explicitly** (details below). Everything here is measured on the hardware in the report.

### Working configuration

```
SGLANG_OPT_DEEPGEMM_HC_PRENORM=0
--dsa-prefill-backend tilelang --dsa-decode-backend tilelang
--kv-cache-dtype bfloat16
+ tilelang v1 tile: (block_I, num_stages, threads) = 64,2,256 -> 32,1,128
```

8x RTX PRO 6000 Blackwell Server Edition (sm_120, 97887 MiB), driver 610.43.02, image `lmsysorg/sglang:glm-5.3-flash` (e6f5482505e7), flashinfer 0.6.17, torch 2.13.0+cu130.
Running with `--tp 8 --dp 4 --enable-dp-attention --ep-size 8 --context-length 1048576`, `max_total_num_tokens = 1,605,888` per rank. Serves correctly.

### Blocker 1 (`TllmGenFmhaRunner: Unsupported architecture`)

Not a missing-kernel dead end — auto-selection is the problem. It lands on trtllm via `device_sm_major >= 10`, which treats all Blackwell alike. Note that **naming another backend does not help**: `_resolve_kpool_tail_backend()` redirects to trtllm for `sm_major >= 10`, so `flashmla_sparse` produces the same error. `fa3`/`flashmla_*` are SM90-only, and `flashinfer_sparse_mla` is genuinely unusable here (`index_kpool > 1`). **TileLang is the only viable DSA backend on sm_120**, and it must be set explicitly on both sides.

### Blocker 2 (`Failed to set dynamic shared memory to 206848`)

The 206,848 B figure is specific to the **fp8 KV** path. With `--kv-cache-dtype bfloat16` the request drops to 151,552 B — still above the ~99 KB sm_120 allows — and the remaining gap closes by retuning the tilelang v1 tile to `block_I=32, num_stages=1, threads=128`. Note that `block_I` alone is not enough: leaving `threads` at its default trips `Layout infer conflict between m_i and alpha`.

### Correction to my original report

I wrote that "#36904's fp8-KV path is unreachable on sm_120". **That was too strong.** Its gate is `CUDA + both-backends tilelang + SM89+`, and both-tilelang is exactly the configuration that works here — so the precondition is satisfied. We have not yet verified fp8 KV on sm_120, but it is not unreachable, and #36904 remains unverified on this architecture.

### Answers to my own three questions

1. **Is sm_120 in scope?** Empirically yes, with the configuration above.
2. **Is there a decode backend that fits in 100 KB?** Yes — tilelang, once the tile is retuned.
3. **Should `SGLANG_OPT_DEEPGEMM_HC_PRENORM` follow `ENABLE_JIT_DEEPGEMM`?** This one still stands: `configurer.py` excludes sm_120 while the env defaults to True, so the NameError is hit out of the box.

Credit: the tilelang+bf16 pairing and the tile sizing both come from the sm_12x reports in #36507 (@killy-netsphere, @beastllama). Posting here so the sm_120 path is findable from this issue.

Suggestion: having auto-selection fall to tilelang on sm12x (rather than trtllm) would remove this entire class of report.

The SGLang architecture/backend selection, packed-row layout and SM120 default changes needed to use it remain downstream; updating FlashInfer alone is not a complete upstream fix for this report.
