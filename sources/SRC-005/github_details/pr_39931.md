# [PR #39931] [ROCm] topk v2: split one long row across blocks, the CDNA cluster-path equivalent

source: https://github.com/sgl-project/sglang/pull/39931
state: open | updated: 2026-09-23T07:23:11Z
labels: run-ci, jit-kernel, bypass-fastfail

## 正文

**Where this helps:** ROCm decode top-k with a small batch over a long context — the shape a reasoning model spends its time in. It engages at `batch_size <= 64` once rows pass a batch-dependent floor (40K at small batch), and is worth most at batch 1-8 over 128K or more: 1.8-3.0x on the kernel, geomean 1.56x across everything the gate admits. Everything else is gated off and unchanged. On GLM-5.2-MXFP4, TP4 on MI355X: **1.41x on the decode top-k kernel** and **-3.8% median ITL** at 120K context, batch 1.

## The problem

Decode top-k is parallelism-bound, not bandwidth-bound. One block owns one row, so a batch of 8 over a 128K window puts 8 blocks on a 256-CU GPU and scans 512 KB twice in each. CUDA splits a row across a thread-block cluster; CDNA has neither clusters nor DSMEM, so on ROCm that shape just runs narrow.

## What this does

Two launches cooperating through global memory, with the kernel boundary as the barrier. Nothing spins.

1. `topk_split_hist` — each rank histograms its chunk into the row's histogram (counted in LDS, one global atomic per non-empty bin).
2. `topk_split_select` — each rank re-reads it, derives the threshold, rescans and appends its candidates. The last rank to arrive resolves the tie tail, re-zeroes the histogram, and applies the page-table transform.

| | |
|---|---|
| `split` | `clamp(64 / batch_size, 4, 32)` |
| fires when | `batch_size <= 64` and `max_seq_len` above the floor |
| floor | 40960 / 49152 / 65536 / 114688, by batch |
| scratch | ~2 MB, `hipMalloc`'d once per device, never freed (captured HIP graphs hold the address) |

Both constants follow from one cost balance. Splitting shortens the scan as `L / split` but pays cross-block cost — atomics in, slots out, an epilogue per row — that grows as `rows * split`. Past ~64 blocks per launch the second term wins badly: 64 rows of 128K cost 115 us spread 32 ways against 34 us spread 4. So cap blocks at 64 rather than chasing the CU count, and key the floor on batch rather than on `split`, since the unsplit path costs the same wall time at any batch that fits the machine while the split path runs its epilogue once per row.

## Scope

CUDA is untouched: preprocessing `topk_v2.cuh` without `USE_ROCM` gives a translation unit byte-identical to the baseline's, for `SUPPORT_CLUSTER` 0 and 1. Prefill / ragged / packed cannot reach the new path — separate entry points, and `batch_size <= 64` excludes any prefill chunk. One file plus its test.

## Correctness

`test_topk_v2.py` on gfx950: **294 passed** (288 existing + 6 new), `negative_infinity` 5 passed.

The invariant is that the selected set matches `torch.topk` exactly, ties included. The existing suite reaches the gate but cannot check that — its tie tests use rows of a few hundred elements, and its long rows are `randn`, whose threshold bin never fills — so `test_topk_v2_split_duplicate_scores` fills it, with rows of `nvals` distinct scores putting `seq / nvals` exact duplicates at the cut.

That also sets the histogram width. The threshold bin is resolved from at most `kMaxNumTie` staged candidates, so a bin holding more *unequal* scores than that silently drops the rest; this path matches the 12 bits of the `TopKStreaming` it replaces on ROCm rather than the 10 of the CUDA cluster path, and on 128K rows of `randint(0, n)` it is exact for every `n` from 32 to 16384, as is the baseline. 12 bits is free in LDS (the histogram overlays `tie_values`, 16 KB either way) and costs 1 MB of scratch; the time it is not free in is what the 64-block cap pays for. ROCm-only test, since CUDA takes its cluster path here.

## Performance

Baseline throughout is `topk_v2` at this PR's parent commit — the kernel this PR edits, and the one GLM takes on ROCm since #36851 turned it on by default. The other ROCm implementation, the native `topk.hip` cooperative kernel from [#37591](https://github.com/sgl-project/sglang/pull/37591), sits behind `SGLANG_OPT_USE_TOPK_V2=0` and is not touched here.

MI355X, `k=2048`, `page_size=64`, `row_starts=None` so the call reaches `transform_paged`; device time from the profiler, median of three runs of 100 iterations. `B` is the paged entry's `batch_size`, which for this layout is the batch — except under speculative decoding, where the indexer builds `[B * next_n, max_seq_len]` logits and the gate sees the draft-expanded count.

All 71 points inside the gate are >= 1.00x: worst 1.06x (B=64, 128K), best 3.03x (B=1, 256K), geomean 1.56x.

One caveat on the gate. It reads `max_seq_len` from the score tensor's width, which eager decode sizes to `seq_lens_cpu.max()` but graph capture sizes to the static KV capacity, so under capture a batch of short rows still enters the split dispatch. Selection stays correct — rank 0 retires those rows to the ordinary one-block kernel inline — but the histogram launch still costs a flat ~1.8 us, and there is no host-side fix under capture, where one captured decision must cover every length the graph may replay at. Crossover in *real* length is ~40K, exactly where the floor sits, so the practical consequence is to size `--context-length` to what is served.

## What this is worth in GLM-5.2

GLM-5.2-MXFP4 (quark, 408 GB), TP4 on MI355X, no-MTP recipe, `--context-length 131072`. Each performance pair ran both arms back to back in one session on one set of GPUs; the accuracy pair did not. Full dump in `RESULTS.md`.

### Kernel level

Matched `num_steps=300` windows over ISL 70K at concurrency 8, TP0 trace.

| ISL 70K, conc 8 | launches | us/call | us/step |
|---|---|---|---|
| baseline `topk_main_kernel` | 5103 = 243 steps x 21 | 27.73 | 582 |
| split `topk_split_hist` | 5124 = 244 steps x 21 | 4.75 | |
| split `topk_split_select` | 5124 = 244 steps x 21 | 14.97 | |
| split total | | **19.72** | **414** |

**1.41x on the kernel**, 168 us back per decode step. Both arms launch 21 times per step — the checkpoint's 21 `full` indexers, confirmed at runtime — so the split changes the cost of a launch and not the structure, and `topk_main_kernel` is absent from the split trace, so the new path is live.

Those 168 us are also the end-to-end ceiling: 1.3% of the 12.67 ms step, because the step is bound by weights and all-reduce rather than KV length. Sparse MLA costs 4685 ms and quickreduce 3248 ms against top-k's 101 ms in the same window.

### End to end

Median ITL, not TPOT or throughput: at OSL 300 these runs are prefill-dominated (median TTFT 3.0-6.1 s) and prefill is untouched.

| config | baseline ITL (ms) | split ITL (ms) | change | TTFT (ms) b/s |
|---|---|---|---|---|
| ISL 70K / OSL 300, conc 4 | 11.21 | 11.00 | -1.9% | 3001 / 3310 |
| ISL 70K / OSL 300, conc 8 | 12.89 | 12.67 | -1.7% | 5845 / 5863 |
| ISL 120K / OSL 300, conc 4 | 11.54 | 11.13 | -3.6% | 5685 / 5695 |
| ISL 8K / OSL 1024, conc 8 (below floor) | 12.31 | 12.27 | -0.3% | 348 / 350 |
| **ISL 120K / OSL 2000, conc 1** | **10.29** | **9.90** | **-3.8%** | 6097 / 6110 |

Nothing is slower, and TTFT matching on four of five pairs to within 0.8% confirms the patch stayed inside decode; the 10% spread at 70K/conc 4 is prefill scheduling variance.

The last row is the point. At batch 1 the gate opens to `split = 32` against a 120K row, where the unsplit kernel has almost no rows to spread across CUs, and concurrency 1 removes queueing, so the gain lands identically on median ITL (-3.8%), P99 ITL (-3.4%), e2e latency (26.68 -> 25.89 s) and output throughput (75.02 -> 77.19 tok/s).

ISL 8K is the config the design expects to lose — rows under the 40960 floor, admitted anyway on the 131072-wide buffer — and it comes out neutral, so the case for a host-supplied real max length is that the gate decides on the wrong quantity, not that the penalty is measurable. (An earlier pass compared arms across a host reboot and had it regressing 1.3% with throughput down 14%, which looked exactly like that penalty and was an artefact.)
