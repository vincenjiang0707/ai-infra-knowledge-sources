## Pull Request Description

power-of-two kept its own per-model, per-pod:port counters in Redis (po2_req_count:*), incremented inside Route and decremented through a registered RequestTracker. The cache already maintains a cross-gateway running-request count for every routed request, exposed through Cache.GetPodsRunningRequests, and least-request reads it. Read it from there instead.

Route now samples two distinct ready pods, reads both counts in a single GetPodsRunningRequests call, and routes to the lower one. For pods that serve several ports, the port is chosen with the same helper least-request uses. The router keeps no state of its own, so the Redis client, key rotation, tracker hooks and lastRoutingTime are gone, and power-of-two registers via init() like the other routers instead of requiring Redis (RegisterPowerOfTwoRouter and
NewPowerOfTwoRouterWithRedis are removed). Without Redis it falls back to this gateway's own counts.

Behavior changes:
- Counts are per pod, not per model, and include traffic from every router, not only power-of-two.
- Counts are shared across gateway replicas, with crashed gateways excluded by the existing liveness window.
- The increment now happens when the gateway registers the request, right after Route, rather than inside Route.
- Existing po2_req_count:* keys are no longer written and expire on their own.

The per-port metric the cache exposes holds the pod's total running count rather than a per-port count, so port choice for data-parallel pods is only approximately load-aware, as it already is for least-request.

Tests: the Redis-key tests are replaced with tests that run Route against a fake cache and against a real cache.Store with the gateway's AddRequestCount/DoneRequestCount calls around it. The routing e2e suite gains power-of-two tests for strategy registration, avoiding a pod that another gateway reports as busy, and counters draining back to zero for plain, streamed and concurrent requests.

## Review

This is a clean refactor. Power-of-two now reads the same cross-gateway running-request counter as least-request, drops the dedicated `po2_req_count:*` keys / RequestTracker / Redis constructor, and registers via `init()` like the other routers. The split between a fake cache (decision + batching) and a real `cache.Store` (AddRequestCount / DoneRequestCount lifecycle) is the right test shape, and the e2e coverage of strategy registration, cross-gateway load, and counter drain matches the behavior that actually changed.

I ran `go test ./pkg/plugins/gateway/algorithms/ -run PowerOfTwo` locally; it passed. Go unit tests on this SHA are also green.

I agree with the author’s reply that nil-pod filtering in `Route` is unnecessary: `types.Router.Route` is documented as receiving only routable pods, and the gateway already runs `FilterRoutablePods`.

### Design (no change requested unless you want it)

The old router incremented its own counter inside `Route` specifically so a concurrent `Route` would not pick the same pod. The shared counter is now incremented in `AddRequestCount` after `Route` returns (and after `enforceReplicaInflight`). `GetPodsRunningRequests` overlays this gateway’s local atomic, so it only sees the new request once `addPodStats` has run. Same-gateway bursts can therefore briefly herd onto one of the two sampled pods. That matches least-request and is called out in the PR description; just confirming it is an accepted tradeoff rather than an accidental loss of the old in-Route increment.

Power-of-two still does not implement `PodScorer`, so auto-blend of load-balance / least-request is skipped the same way as `random`. That is correct for an O(1) sampler; worth knowing so nobody expects `power-of-two,least-request` multi-strategy to work.

### Follow-ups (inline)

- `Route` / `getRequestCounts` comments overstate per-port load awareness and the error fallback.
- `getRequestCounts` should tolerate a nil map the same way least-request does (production `Store` never returns one).
- The e2e drain test deletes every `aibrix:rrq:*/*` hash; that is safe only because `test/run-e2e-tests.sh` uses `-p 1`.
- Docs still describe power-of-two as “selects the better one” and do not mention that Redis is no longer required, or that the load signal is the shared running-request count. The PR template’s `Resolves: #…` placeholder is also still there, which is likely why `triage/needs-information` was applied.

Not blocking: sampling two pods then choosing a port (instead of sampling pod:port pairs) is a real behavior change for data-parallel pods and looks intentional. Counts being per-pod rather than per-model is also called out and is the better load signal.
