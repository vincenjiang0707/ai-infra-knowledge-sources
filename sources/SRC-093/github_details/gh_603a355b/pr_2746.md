## Pull Request Description

In SGLang PD disaggregation the gateway fires the prefill leg asynchronously and lets Envoy forward the decode leg. When the prefill leg fails (dead prefill pod, non-2xx, timeout, client cancel) nothing tells the decode pod or the client: the decode pod sits in its bootstrap / prealloc queue for that `bootstrap_room` until the engine's own bootstrap timeout (minutes), holding a decode slot, and the client sees a long hang followed by an opaque decode-side error. This is #2289.

This PR keeps the prefill dispatch asynchronous (the constraint raised in #2289) and only stops discarding its result.

### What changes

1. **`utils.LoadEnvNonNegativeInt`** — `LoadEnvInt` treats every value ≤ 0 as invalid and silently falls back, so a knob whose documented value `0` means "off" cannot be switched off from the environment. The new helper accepts 0 and still refuses negative/unparseable values. `LoadEnvInt` is unchanged for its callers.

2. **Gateway-owned `rid` + decode abort on prefill failure.** SGLang's `/abort_request` matches on `rid` only (`AbortReq` has no room field) and reads `rid` from the request body, not from `X-Request-Id`. The gateway now writes `rid = <request id>-<16-hex nonce>` into both legs' bodies (fixed width because SGLang's abort match is prefix based; the nonce keeps retries with a reused request id distinct). When the async prefill leg fails, the failure is classified (`http_status`, `timeout`, `canceled`, `transport`, `request_setup`, `bad_response`) and the gateway POSTs `{"rid": ...}` to the decode pod's `/abort_request`. The abort is best-effort on its own goroutine with its own timeout, sent twice (immediately and after a short delay) because a prefill pod that refuses the connection outright lets the first abort overtake the decode leg, and the tokenizer manager silently drops an abort for an unknown rid. It is skipped once the decode pod has started responding. `bad_response` (HTTP 200 with an unparseable body) never aborts because the transfer did complete.

3. **Fail the client request immediately.** `Route()` only produces the header mutation, but the same ext_proc stream stays open for the response and is parked in `srv.Recv()` waiting for decode response headers that will not arrive until the bootstrap timeout. `srv.Recv()` moves into one reader goroutine per stream and the processing loop becomes a `select` over the reader, the stream context and a per-request prefill-failure wakeup. Non-PD streams select on exactly the two cases they had before. When a terminal prefill failure lands before the decode pod has responded, the gateway answers with an `ImmediateResponse` (503 for timeout/transport/request_setup/canceled, the upstream status for `http_status`, 502 otherwise) carrying an OpenAI-shaped error body and `x-error-pd-prefill: true`, then closes the stream with a gRPC error so `failure_mode_allow: false` makes Envoy reset the decode connection. If the decode pod has already responded, the failure is only recorded. The per-request leg state lives in a per-incarnation object captured by the prefill goroutine before launch, so a late prefill failure can never land on a recycled `RoutingContext` that another request has since taken from the pool (there is a test seam that reproduces the aliasing deterministically).

4. **Observability.** `gateway_pd_prefill_failure_total{class,stage}` (`stage` = `before_response` / `after_response`), `gateway_pd_decode_abort_total{prefill_failure_class,result}`, structured log lines `pd_prefill_fail_fast` and `pd_decode_abort`. The generic request-fail counters carry `status="pd_prefill_failure"` so a fail-fast is separable from an upstream 503. A fail-fast runs `finalizeRouterContext` exactly once and is never counted as a successful request.

5. **Env vars** (documented in `pkg/plugins/gateway/ENV_VARS.md`): `AIBRIX_PREFILL_REQUEST_TIMEOUT` (existing), `AIBRIX_DECODE_ABORT_TIMEOUT` (seconds, default 3, `0` disables the abort), `AIBRIX_DECODE_ABORT_RETRY_DELAY` (seconds, default 2, `0` sends a single attempt).

6. **Tests.** Unit tests for the failure classification, the abort scheduling (both attempts, skip-after-response, `0` semantics), the `select` and the fail-fast response, plus a regression test for the pooled-context aliasing. e2e (`test/e2e/gateway/pd/pd_fail_fast_test.go`): `TestPDPrefillFailFastRejectedPrefill` rejects the prefill leg with the mock while holding the decode leg for 10 s (new role-scoped `x-aibrix-mock-delay-role` header on the mock app) and asserts the client is answered with the prefill status + `x-error-pd-prefill: true` before the decode leg could respond, and that a decode mock recorded `/abort_request` with the gateway's rid; `TestPDPrefillFailFastPrefillTimeout` covers the `timeout` class / 503 mapping and skips itself unless the gateway is deployed with a short `AIBRIX_PREFILL_REQUEST_TIMEOUT` (exported as `AIBRIX_E2E_PREFILL_REQUEST_TIMEOUT_SECONDS`), because the shipped 60 s exceeds the mock's delay cap. The mock app gains an `/abort_request` route so the abort is observable.

### Notes for review

- Commits are separable: (1) `LoadEnvNonNegativeInt`, (2) rid + decode abort, (3) client fail-fast, (4) e2e + docs. Each builds and vets on its own.
- `http_status` passes the prefill engine's own 4xx/5xx through to the client (502 if it is not a code Envoy names); the other classes map to 503. Happy to switch to "always 503 with the upstream status in the body" if preferred.
- `AIBRIX_DECODE_ABORT_TIMEOUT=0` is the off switch for the abort. A dedicated boolean would work as well; this keeps the knob count down.
- `TestPDFailureSGLangAsyncPrefillHandoff` now normally sees the gateway's fail-fast response before the decode mock's own 500; its `>= 500` assertion still holds and the decode mock still records its handoff failure. Flagging it in case it flakes on CI.
- Race detector is clean on `pkg/plugins/gateway`, `pkg/plugins/gateway/algorithms/pd/...` and `pkg/types`; `make lint` and `make licensecheck` pass.

### Verification on a real deployment

Fault injection on a 2-prefill / 2-decode SGLang deployment with a gateway built from the equivalent change, prefill request timeout set to 3 s so that a cold ~24k-token prompt times out on the prefill leg:

| scenario | client | decode pod | prefill pod |
|---|---|---|---|
| prefill timeout, abort enabled | 6/6 got 503 at 3.01 s (before: hang until the engine's 300–600 s bootstrap timeout) | `AbortReq` dequeued + ACKed 6/6, prealloc/transfer queues back to baseline | abort notification in the same second, 6/6 released |
| prefill timeout, `AIBRIX_DECODE_ABORT_TIMEOUT=0` | same 503 at 3.01 s | released by the Envoy reset alone ≈1.1 s after the 503 | ≈1.1 s after the 503 |
| `kill -9` a prefill pod under load | requests on the dead pod: 503 in 2.2 s (`transport`); requests on the healthy pod: 200 | abort ACKed 4/4 | n/a |

No collateral under normal load (≈1,800 requests, ≈65k-token prompts, no injected failures): every abort attempt logged was the "client closed the stream after completion" echo, all after the request's own `request_end` (Δ 0.1–0.6 ms), all skipped because the decode pod had already responded; the engines' `num_aborted_requests_total` did not move on any pod. Routing overhead: `routing_time` p50 5.4 ms, p99 81 → 185 ms.

## Code Review

This pull request implements a fail-fast mechanism for PD (Prefill-Decode) disaggregation, allowing the gateway to abort the decode leg when the prefill leg fails, thereby releasing pre-allocated KV pages. The changes include logic for aborting decode requests, new metrics for tracking failures, updated documentation, and comprehensive end-to-end tests. The review identified a race condition in the `processOnce` loop where the prefill failure wakeup is disarmed prematurely, and a code suggestion was provided to ensure it is only disarmed when the failure is actually handled.
