## 正文

## Pull Request Description

Adds opt-in **generation-first (parallel) P/D scheduling for TensorRT-LLM**, closing the gap described in #2018. The PD router previously only supported context-first scheduling (prefill → wait for response → decode).

## Related Issues

Resolves: #2018

With `AIBRIX_TRT_SCHEDULE_STYLE=generation_first`, the gateway:

1. resolves the selected CTX worker's `/server_info` (`ctx_info_endpoint`, `ctx_dp_rank`, optional `encoded_opaque_state`) through a lazily populated cache (single-flighted per worker incarnation, 1-minute TTL, 1024-entry bound, 3-second lookup timeout, redirects rejected, 1 MiB response cap);
2. builds **both** request bodies up front from one shared integer `disagg_request_id`, with `schedule_style: 1` (TRT-LLM `GENERATION_FIRST`) inside `disaggregated_params`;
3. starts the `context_only` request in a goroutine and returns the decode target plus the already-mutated `generation_only` body to Envoy, so both legs overlap.

The default is unchanged: `context_first` stays the default, the mode is an immutable router-local handler (the shared engine registry is never mutated, so no other router or request is affected), and vLLM, SGLang and combined-pod routing take the same paths as before.

### Deliberate differences from the issue text

The issue describes a proxy that issues both requests itself. Three implementation choices differ, all because of how AIBrix dispatches PD today:

1. **Lazy per-worker `/server_info` load, not an init-time crawl.** The gateway's pod cache does not contain future/autoscaled CTX pods at router construction. The cache is created at init and filled for the selected worker before either leg is dispatched.
2. **The router never POSTs the decode leg.** In AIBrix the decode request is forwarded by Envoy; the router returns the decode address and the mutated body (`gateway_req_body.go`). This is the same mechanism context-first, vLLM and SGLang use, and it is what makes the two legs overlap. There is consequently no gateway-side ordering guarantee between the CTX POST and Envoy's GEN forward.
3. **`ctx_dp_rank` is taken from the selected worker's own `/server_info`** instead of a router-maintained rank table, so a rank can never be applied to a different worker. Rank `0` is never substituted for missing data: a missing/`null` rank is an error and routing fails before dispatch.

### Configuration

```yaml
# gateway plugin only, not the model containers
- name: AIBRIX_TRT_SCHEDULE_STYLE
  value: "generation_first"   # or context_first (default)
```

An unrecognized value is logged and leaves the router on `context_first`, matching the other env-driven knobs in this package. `AIBRIX_TRT_MACHINE_ID` should differ per gateway process sharing TRT workers, as with context-first.

**Worker prerequisite:** both roles must run TRT-LLM's **Python** KV-cache transceiver (`cache_transceiver_config: {backend: DEFAULT|NIXL, transceiver_runtime: PYTHON}`). Only that transceiver implements the generation-first metadata — `BindKvCacheTransceiver.get_disaggregated_params()` returns `{}` in v1.3.0rc8 — so a worker on the default C++ transceiver answers `/server_info` with an empty `disaggregated_params` and cannot be used for this mode. The sample now sets this, and the router's error message names the cause when it sees an empty `disaggregated_params`.

### Failure handling

The CTX request keeps the client's cancellation and the existing prefill timeout, and reports failures through the per-incarnation PD leg state (never through the pooled `RoutingContext`). TRT-LLM has no SGLang `rid`/`/abort_request` contract, so no abort POST is made: the gateway instead fails/resets the Envoy stream and relies on TRT-LLM cancelling the promise on HTTP disconnect. Because TRT can send SSE headers before KV is available, a terminal CTX failure after headers resets the stream rather than being treated as "decode is healthy" — this can truncate an already-streaming response, but it cannot leave a generation leg waiting indefinitely for KV.

### Notes for reviewers

- **Rebased onto `main` (`6fa937e6`)** after #2786 landed. The prefill deadline is now read per request from the routing context's resolved PD overrides (`routingCtx.PDOverrides().PrefillRequestTimeout`), so this PR no longer changes the prefill executor's constructor: the only executor override it adds is engine-handler selection. The TensorRT tests take their deadline from the same per-request overrides.
- **Scope:** the setting is process-wide for TRT — there is no per-model `routingConfig` override in this PR. Happy to add one if preferred.
- **Sample change:** `tensor-rt-pd.yaml` now sets `transceiver_runtime: PYTHON` on both roles. This also affects context-first users of the sample; without it, turning on the documented mode cannot work. Easy to reduce to a commented-out line if you prefer the sample to keep the C++ default.
- `/server_info` is copied through an explicit allowlist (`ctx_info_endpoint`, `ctx_dp_rank`, optional `encoded_opaque_state`) rather than upstream's wholesale merge, so worker metadata cannot overwrite the gateway-owned `request_type`, IDs or `schedule_style`. A future handshake field would need to be added explicitly.
- No negative caching: a flapping CTX worker costs the full 3-second lookup per request. Bounded and fail-fast, but worth a follow-up if the routing-path latency matters.
- No API/CRD/`api/` changes; no new dependencies.

Code review, separate from the simplification notes already on the diff.

The request build matches the TensorRT-LLM worker: `schedule_style` belongs inside `disaggregated_params` (`py_disaggregated_params.schedule_style`, `DisaggScheduleStyle.GENERATION_FIRST = 1`), both legs share one integer id, and `ctx_request_id` is set on the generation leg. `to_llm_disaggregated_params` copies `schedule_style` from that object, so the nested placement is the one the executor reads.
