## 正文

### Pull Request Description

The Python tests workflow upgrades pip and poetry in place and then runs `poetry install` with the default parallel installer:

```yaml
- name: Install dependencies
  run: |
    cd python/aibrix
    python -m pip install --upgrade pip
    pip install -U pip poetry
    poetry config virtualenvs.create false
    poetry install --no-root --with dev
```

That is the same window the image build hit in #2801. Poetry keeps only `uninstall` operations out of its thread pool, an `update` operation uninstalls the installed distribution before it installs the locked one, and two concurrent uninstalls read the same `site-packages` directory, so one can meet a `.dist-info` directory the other removed in between. The race is reported upstream as `python-poetry/poetry#8159` and is still open. The workflow does not pin poetry either, so `pip install -U` takes whatever is current and the drift window is wider than in the image.

### Fix

The install is serialized the same way the image is after #2801:

```yaml
poetry config virtualenvs.create false
poetry config installer.parallel false
```

The resolved package set is unchanged because the same lock file drives the same operations; only the concurrency of the install and uninstall steps is. Apart from this workflow, the only other call sites of `poetry install` are local setup steps in `python/aibrix/README.md` and `python/aibrix/AGENTS.md`.

### Evidence

- The second site was flagged in review of #2801: this workflow runs the same three steps, and it did not run on #2801 because its path filter is `python/aibrix/**`.
- In poetry 1.8.3, `poetry/installation/executor.py` computes `is_parallel_unsafe` from `job_type == "uninstall"` only, so `update` operations stay in the parallel path, and the same file sets `max_workers` to 1 when `installer.parallel` is false.
- The failure signature from the image build, a `FileNotFoundError` on a `.dist-info` directory that is not part of the failing uninstall command, is recorded in #2801.

### Test Plan

- The paths filter of this workflow includes the workflow file itself, so the three Python matrix jobs run on this change.
- `actionlint` and a YAML parse pass locally on the change.

## Design simplification

Keep the single config line next to `poetry config virtualenvs.create false`, and keep a comment that names poetry#8159. The line looks like a slowdown unless the comment says why updates still race. Match the Dockerfile comment, which states that Poetry uninstalls and reinstalls on every update. The workflow comment currently skips that clause, and that clause is what tells a reader that Poetry’s existing serial path for `uninstall` operations does not cover this failure.

Cut anything beyond that line:

- A Poetry version pin. The image pins 1.8.3 so the image is reproducible. Pinning the workflow would still leave Poetry’s own dependencies newer than the lock, which is what creates the updates. Serialization is the fix that matches #2801.
- `installer.builtin-uninstall`. Poetry 2.5.1 has it and defaults it to false. Turning it on would swap the uninstaller and would diverge from the image.
- A composite action or shared script for the Dockerfile `RUN` and this step. The shared part is one config line.
- Edits to the local README and `AGENTS.md` install snippets.
- `POETRY_INSTALLER_PARALLEL=false` as a second spelling. The environment variable is equivalent, and the repository already uses `poetry config installer.parallel false` in the image. One spelling is enough.

The pre-existing double pip upgrade (`python -m pip install --upgrade pip`, then `pip install -U pip poetry`) can stay as it is.

## Code review

The change is correct for the workflow that actually runs.

`pip install -U pip poetry` with `virtualenvs.create false` drops Poetry and its dependencies into the same environment the lockfile then updates. On this pull request, Python 3.10 installed Poetry 2.5.1 and then reported `130 installs, 16 updates`. Those updates include the same pair that failed the image build: `charset-normalizer` 3.5.1 to 3.4.6 and `urllib3` 2.8.0 to 2.6.3. An update uninstalls the installed distribution before installing the locked one. Poetry still treats only `job_type == "uninstall"` as parallel-unsafe, so those updates stay in the thread pool. `installer.parallel false` sets `max_workers` to 1, so the uninstalls no longer overlap. That is true in Poetry 2.5.1 (`src/poetry/installation/executor.py`: the config read, the `is_parallel_unsafe` check, `_install` calling `_remove` on update, and `_remove` calling `pip uninstall` while `installer.builtin-uninstall` stays at its default). Upstream [python-poetry/poetry#8159](https://github.com/python-poetry/poetry/issues/8159) is still open. The three matrix jobs passed (run 36075487258) in about three minutes each, inside the 20-minute timeout, and the 16 downgrades were timestamped one after another.

The pull request text cites Poetry 1.8.3, which is the image pin in `build/container/Dockerfile.python`. This workflow does not pin Poetry, and the run installed 2.5.1. The mitigation still holds on that version. A future Poetry that drops `installer.parallel` will fail the step at `poetry config`, which is a closed failure.

A green run does not by itself prove the race is gone. The race needs overlapping uninstalls, and this change removes that overlap. `poetry config` without `--local` writes the user config for the job. Later steps in this workflow are Ruff, mypy, and pytest, so the setting has no further effect. The lockfile, `--no-root --with dev`, and the installed set stay the same. There is no Kubernetes API, HTTP, CLI, label, or annotation change. `release-build.yaml` builds and publishes with Poetry and does not run this `poetry install`. The KV cache workflow installs from requirement files. Local `poetry install` instructions in `python/aibrix/README.md`, `AGENTS.md`, and `aibrix/batch/README.md` stay parallel; that is a local setup path, and this pull request correctly leaves it alone.
