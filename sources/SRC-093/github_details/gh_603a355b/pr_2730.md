## Pull Request Description

Add a dedicated pull-request installation smoke pipeline for AIBrix's two
supported installation entry points.

- Build the controller-manager, gateway-plugins, runtime, metadata-service,
  and vllm-mock images once, then reuse the artifacts in parallel Kustomize
  and Helm jobs.
- Run one shared Go smoke suite that creates a single-instance StormService
  and a 1P1D StormService, sends requests through Envoy Gateway and the AIBrix
  gateway plugin, and verifies resource cleanup.
- Use bounded readiness retries, per-installation failure diagnostics, and
  unconditional Kind cleanup without invoking the existing full E2E suite.

## Review summary

Thanks for this — the Helm + Kustomize installation smoke with a shared StormService gateway path is a solid CI addition.

**Verdict:** Approaching ready; please address the timeout/flake risk and clarify CI overlap with `installation-tests.yml` before merge.

### What looks good
- Build-once / test-twice layout with Kind isolation, diagnostics artifacts, and `if: always()` cleanup
- Helm coverage that the existing installation E2E does not have
- Manual Service + HTTPRoute + ReferenceGrant path correctly exercises Envoy + gateway-plugins for StormService (ModelRouter does not watch StormService today)
- Builder unit tests in `suite_test.go`

### Blocking / high
1. **Shared 9m context for two scenarios is too tight** — each scenario can spend ~4m StormService ready + route wait + inference/PD + cleanup; under Kind load both can exceed 9m even though the job allows 35m.
2. **CI cost overlap with `installation-tests.yml`** — that workflow already builds the same images and runs full E2E on PRs with largely the same path filters. This workflow rebuilds them again. Please either narrow PR triggers (smoke on PR, full E2E on main/schedule) or document why both must always run. Helm smoke is the clear new value.

### Medium
3. Large kustomize/helm job duplication — consider a reusable workflow/composite action
4. Poll helpers abort on any API `Get` error (transient apiserver blips fail the test)
5. No disk-space cleanup step (existing installation E2E has one; five images + Kind can pressure `ubuntu-latest`)
6. `runtime` image is built/loaded but unused by this smoke (no sidecar-injection annotation)

### Low
7. `intstrFromInt32` is redundant with `intstr.FromInt32`
8. `suite_test.go` name is a bit misleading (builder unit tests, not a Ginkgo suite)

### Bot review note
Gemini’s nil-deref note on `stormServiceReady` looks incorrect: `Conditions.GetCondition` returns a value with `ConditionUnknown` when missing, not `nil`. A “missing condition” unit test is still nice; the panic fix as written is not needed.
