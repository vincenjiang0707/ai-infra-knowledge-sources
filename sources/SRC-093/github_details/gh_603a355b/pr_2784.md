## Pull Request Description

The routing message the gateway uses for prefix matching is built from `messages[].content` only. Many chat templates render the tool definitions ahead of the conversation, so two requests with the same messages but different `tools` differ in the engine prompt from the first tokens. The gateway nevertheless treats them as a 100% prefix match and pins them to the same pod.

This PR gives `/v1/chat/completions` and `/v1/messages` requests a separate prefix-match text: a canonical rendering of `tools`, a single space, then the messages text.

- The text is stored in a new `RoutingContext.PrefixMatchText` field and read through `PrefixText()`, which falls back to `Message` when it is empty. Only prefix-matching code reads it. `Message` stays messages-only, so size estimates are unchanged: VTC, `PromptTokens`/`PromptLength` (SLO queue, PD prompt-length bucketing) and config-profile `promptTokensGte`/`promptTokensLt`.
- The rendering sorts object keys at every level, is compact, does not escape HTML characters and keeps number literals as sent, so the same tools produce the same text whatever the client's key order or whitespace.
- When `tools` is absent, `null`, `[]` or not an array, `PrefixMatchText` stays empty and matching is byte-identical to today.
- `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS` (default `true`, read once at startup) restores messages-only matching when set to `false`.
- `/v1/responses`, `/tokenize` and `/v1/completions` are unchanged. `/v1/responses` `tools`/`instructions` and `/v1/messages` `system` are tracked in #2799.

**Affected policies:** `prefix-cache`, `prefix-cache-preble`, and the PD prefill policies `prefix_cache`, `conductor` (including its matched/unmatched token estimate) and `hybrid_cache_load`.

**KV-sync mode:** when a chat request is tokenized through the remote chat template (vLLM `/tokenize`), its raw `tools` array is now forwarded too, so the real template places the tools. This does not depend on the flag. The plain-text fallback, `ScoreAll` and `PostRouteUpdate` hash `PrefixText()`.

Templates differ in where they place tools: most render them in the system block ahead of the conversation, which this ordering matches; a few (e.g. Mistral) place them near the last user turn. For those templates the text-based matching is less accurate: requests that share tools but not messages can see a partial match the engine won't have. Such deployments can set `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS=false`. The KV-sync chat-template path is not affected, since the template itself decides the order.

**Tests:**
- `prefix_tools_test.go`:
  - absent, `null`, `[]`, `{}` and string tools leave `PrefixMatchText` empty
  - `Message` stays messages-only when tools are present
  - OpenAI and Anthropic tool shapes render to the expected canonical text
  - different tools drop the prefix-index match below 50%, while an identical repeat still matches 100%
  - 50 seeded key-order and whitespace permutations produce one text
  - characters are not HTML-escaped
  - `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS=false` disables it
  - invalid `tools` fall back to the raw bytes
- `router_context_test.go`: the `PrefixText()` fallback, and that `reset` clears the field for pooled contexts.
- `prefix_cache_tools_test.go`:
  - the prefix-cache router matches on `PrefixText()`: same tools score 100, different tools stay below 50
  - raw tools extraction, and `buildTokenizeInputFromChatRequest` forwarding them
- `adapter_vllm_test.go`: the vLLM chat tokenize request carries `tools` verbatim, and omits the key when there are none.

Verification:
- `go test -race ./pkg/plugins/gateway/... ./pkg/types/... ./pkg/utils/tokenizer/...` passes
- golangci-lint reports no issues

### cursor[bot] · 2026-09-23

## Design feedback: simplify by not overloading `Message`

The fix for #2782 is the right idea — tools belong in the prefix-match input. The complexity is mostly from **overloading `RoutingContext.Message`**, not from the canonicalizer.

### 1. Don’t overload `Message`

Today `Message` is both:
- prefix-match / tokenizer input, and
- prompt-size input (VTC, `PromptTokens` / `PromptLength`, SLO / PD bucketing, profile `promptTokensGte`/`Lt`)

Prepending tools fixes cache pinning but also quietly changes size estimates and bucket selection. That couples two products.

Simpler shape:
- keep `Message` as messages-only (today’s bytes when tools are absent)
- add something like `PrefixMatchText` (or build the match string only at the prefix-cache / PD scorer boundary)

Then tools affect matching only; length semantics stay stable. `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS` becomes a real prefix-only switch instead of a global `Message` rewrite.

### 2. Don’t teach `parseChatMessages` a generic `prefix`

`parseChatMessages(requestID, prefix, msgs)` forces tokenize / responses / completions to pass `""`. Prefer:
- leave `parseChatMessages` as messages-only
- compose in `validateChatRequest`: `toolsText + " " + messagesText` (or the separate `PrefixMatchText` field)

Keeps the parser’s job one thing.

### 3. Default `true` is a behavior change beyond the bug

With `Message` overloaded, default-on changes bucket/profile matching for tool-heavy traffic. Safer rollout: default `false` until operators opt in, **or** do (1) so defaulting tools into prefix matching doesn’t move size buckets.

### 4. Close or narrow the KV-sync hole

Remote-tokenizer / chat-template path still matches on messages only. Either wire tools there too, or document those policies as out of scope so the feature isn’t half-applied.

### 5. Keep the canonicalizer as-is

`canonicalToolsText` is already small and fine (sorted keys, compact, no HTML escape, empty/null → no-op, invalid → raw). Little to simplify there.

---

**Bottom line:** Keep canonical tools-in-prefix. Simplify by **separating prefix-match text from `Message`**, composing tools only on the chat path, and treating the env flag as prefix-only. That removes the size/bucket side effects from the bug fix.

## Code review

**Verdict: request changes** — the fix for #2782 is right; the coupling and rollout are not.

CI is green (unit, race, integration, install E2E). Canonicalizer and tests are solid. Blocking concerns are the `Message` overload with default-on, and the still-open KV-sync path.

### What works

- `canonicalToolsText` is the right primitive: sorted keys, compact, no HTML escape, `UseNumber`, empty/`null`/`[]` → no-op, invalid → raw bytes.
- Wired through `validateChatRequest` for both `/v1/chat/completions` and `/v1/messages`.
- Tests cover the important cases: no-tools identity, OpenAI + Anthropic shapes, match drop below 50%, 50 key-order permutations, HTML escape, disable flag, invalid fallback.
- Docs honestly call out side effects and the KV-sync hole.

### Requested changes

**1. Don’t overload `Message` (still the main issue)**  
Prepending tools into `routingCtx.Message` also moves VTC estimates, `PromptTokens` / `PromptLength` (SLO + PD bucketing), and `promptTokensGte` / `Lt` profile matching. That is a silent policy change for tool-heavy traffic, not just a prefix-match fix.

Prefer `PrefixMatchText` (or compose only at the prefix-cache / PD scorer boundary) and keep `Message` messages-only. Then `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS` is actually prefix-only.

**2. Default `true` is too aggressive while `Message` is shared**  
With (1), default-on is fine. Without it, default `false` until operators opt in, or ship a migration note that profile thresholds may need retuning.

**3. Don’t add a generic `prefix` to `parseChatMessages`**  
Tokenize / responses / completions now pass `""`. Compose in `validateChatRequest` instead so the parser stays messages-only.

**4. KV-sync chat-template path still ignores tools**  
`tokenizeChatRequest` → `buildTokenizeInputFromChatRequest` never forwards tools. `vllmTokenizeChatRequest` already has a `Tools` field, but `TokenizeInput` / `PrepareTokenizeRequest` never set it. Successful chat-template tokenization still matches messages-only — the original bug for KV-sync deployments.

Either wire `tools` through `TokenizeInput` into the vLLM tokenize request, or mark those policies explicitly out of scope in the issue/PR (docs alone leave a half-fixed bug).

### Nits

- Agree with Gemini: `setIncludeTools` mutates a package `bool`. Use `atomic.Bool` (or don’t mutate a process-global from tests) so `-race` stays clean if anything parallel reads it.
- `/v1/responses` can carry `tools` too and is still messages/input-only — fine as a follow-up if you call it out.
- Non-array `tools` (e.g. `{}`) still get prepended; rare, but empty-object → `"{}"` is a slight behavior quirk.

### Bottom line

Ship the canonical tools-in-prefix idea. Block on separating prefix-match text from `Message` (or defaulting off until that lands), and either close the KV-sync tools gap or formally defer it. Canonicalizer + test suite can stay as-is.

### bolubo · 2026-09-24

Thanks, this addresses a real gap: before this change, two requests that shared their messages but not their tools could look like a full prefix match. The raw tools forwarding on the KV sync path is a nice detail as well, since the parsed request types do not model every field.

The same pattern shows up for a few more request fields that can change the rendered prompt: `chat_template`, `chat_template_kwargs` and `documents` are still invisible to both paths.

- In vLLM, those three all flow into the chat template rendering (`vllm/entrypoints/openai/chat_completion/protocol.py:340/350/359`, `build_chat_params` at 573-594).
- On the prefix text path, two requests that differ only in one of those fields produce the same `PrefixMatchText`, byte for byte, so the indexer sees a full match while the engine can render a different prompt. I checked it on this branch with a small local test (same messages and tools, only the template field changed).
- On the KV sync path, `buildTokenizeInputFromChatRequest` has no channel for those fields yet (`TokenizeInput` does not model them). `vllmTokenizeChatRequest` already declares `chat_template` and `chat_template_kwargs` (`pkg/utils/tokenizer/types.go:87-88`), and vLLM `/tokenize` accepts both (`vllm/entrypoints/serve/tokenize/protocol.py:84, 93`), so those two could be forwarded the same way tools are now.

Two small caveats: `chat_template` overrides are only accepted by engines started with `--trust-request-chat-template` (plain `chat_template_kwargs` is not gated), and `documents` is not part of the `/tokenize` schema, so the KV sync path would need engine support before it can be covered there.

None of this needs to be part of this PR. It could be a third bullet on #2799, or a follow-up. Happy to paste the probe if that helps, or dig further.
