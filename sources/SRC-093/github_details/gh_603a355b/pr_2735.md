# [PR #2735] [Bug] Purge a pod's prefix cache when the engine sleep-state metric shows it went to sleep

source: https://github.com/vllm-project/aibrix/pull/2735
state: open | updated: 2026-09-21T21:28:49Z
labels: triage/needs-information

## 正文

Closes #2287.

This grew from what it started as. Original scope was just the metric label-filtering bug below; the tracker and edge-triggered purge (the actual backstop) turned out to be ready sooner than the original PR description said to expect, so it's in the same PR now rather than a follow-up.

## The bug this fixes

`vllm:engine_sleep_state` reports one gauge family with three instances per pod, distinguished only by the `sleep_state` label (`awake`, `weights_offloaded`, `discard_all`), each its own 0/1 series. Nothing in the Prometheus exposition format guarantees scrape order, but `parseMetricFromFamily` read `metricFamily.Metric[0]` unconditionally, so which of the three series aibrix actually recorded depended on whatever order that particular scrape happened to return.

Added `Metric.RequiredLabelKey`/`RequiredLabelValue`: when set, `parseMetricFromFamily` searches the family for the instance whose label matches instead of taking the first one. Every other registered metric leaves this unset and keeps the exact `Metric[0]` behavior it has today. `EngineSleepState` now filters to `sleep_state=awake`.

## The backstop

The `AllBlocksCleared` ZMQ event handler already purges a pod's prefix cache on `/reset_prefix_cache`, OOM-driven reset, or `/sleep`. It's not complete: vLLM only flushes queued KV events from inside a scheduler step, so an idle or sleeping engine may never emit one, and ZMQ delivery is lossy. The pod stays `Running` with `/health` returning 200, so the prefix router keeps preferring it for prefixes whose blocks are gone.

`Manager.CheckSleepStateBackstop` reads the (now correctly filtered) `engine_sleep_state` value already scraped every refresh tick and purges on the awake-to-asleep transition, per (pod, model). Edge triggered, not level triggered: `RemovePrefix` takes the prefix router's write lock and is O(P) in cached prefixes for the model, so purging on every tick a sleeping pod is observed would hold that lock once per refresh interval for as long as it stays asleep. A (pod, model) pair with no prior observation is seeded as having been awake, so a gateway restart while a pod is already asleep still self-corrects on the first observation.

`Manager.PurgePodPrefixCache` factors the get-indexer-then-`RemovePrefix` logic the event handler already had into a method the backstop also calls, so a pod's cache is purged the same way whether aibrix learned about it from a ZMQ event or from this metric. `unsubscribeFromPod` now also forgets the pod's tracked sleep state, so a reused pod key is seeded fresh.

Wired into `pkg/cache`'s existing `worker()` metrics loop, right where `engine_sleep_state` is already read for Prometheus export. No new scraping. `KVEventManager.CheckSleepStateBackstop` is a no-op in the default (non-zmq) build, matching every other `KVEventManager` method: the backstop needs the sync indexer KV event sync provides.

## Review

The edge-triggered design is the right one: `RemovePrefix` is too expensive to run every scrape, and seeding the first observation as awake is what makes a gateway restart self-correct. Factoring `PurgePodPrefixCache` so the ZMQ path and the metric path purge the same way is also good.

The implementation as written will not close #2287. Three independent gaps mean the backstop either never fires, purges the wrong thing, or latches “asleep” without actually purging:

1. **Label filter is on the unused parse path.** `EngineSleepState` is `PodModelMetricScope`. The cache worker uses `FetchAllTypedMetrics` → `parseModelMetricsFromFamily`, which still last-wins across the three `sleep_state` series. `RequiredLabelKey` only affects `parseMetricFromFamily` / `FetchTypedMetric`, which is what the new test covers.

2. **Worker-loop match never hits slash-containing model names**, and even when it does, it passes the Prometheus `model_name` into `RemovePrefix` instead of the pod-metadata name the event handler and prefix router use.

3. **State is latched before a successful purge.** Combined with `PurgePodPrefixCache` returning `nil` on `ErrIndexerNotInitialized`, the restart-while-asleep case this PR is designed for can miss forever.

Inline comments have the failure modes and suggested fixes. The `kvevent` unit tests for the transition/seeding/unsubscribe cases look solid; they cannot catch (1) or (2) because they never go through the fetcher or the worker loop.

I did not re-run the `zmq`-tagged suites here. The gaps above are from the production call path, not from the isolated backstop tests.
