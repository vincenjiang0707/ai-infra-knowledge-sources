## 正文

## Pull Request Description

The ModelClaim controller calls every runtime with one 60 second timeout, on its only worker, and it reads the Pods one after another. A read that fails is not remembered. So a runtime that takes connections but never answers held the worker for 60 seconds on every read, for every claim that reads its Pod. A Pod that cannot be reached held it for 30 seconds, until the dial gave up. #2817 has the details and the measurements.

This PR bounds that in two commits, both in `pkg/controller/modelclaim/runtime_client.go`:

- **A snapshot read gets its own 10 second deadline.** A normal read takes a fraction of a second, and the runtime gives each engine's probes at most 1.5 seconds. Calls that change state keep 60 seconds.
- **A runtime whose call timed out is left alone for a minute.** Calls to it fail at once until then, without being sent. The Pod then counts as unreadable, as after any failed read: placement ranks it last, and the health check leaves its routing alone. Stopping an engine is still sent, since a claim is deleted or scaled down only once, and an engine left running would keep its memory. A call that fails fast, such as a refused connection or an error status, is not remembered. The client knows a runtime by its address, since that is what it is called with.

Measured with the real client and the default settings, against a listener that takes connections and never answers:

| Case | Before | After |
|---|---|---|
| Health check of the first claim on that Pod | 60.0 s | 10.0 s |
| Health check of a second claim on the same Pod | 60.0 s | 0.0 s |
| Placement with that Pod as the only candidate | 120.0 s | 10.0 s |
| A Pod that cannot be reached | 30.0 s | 10.0 s, then 0.0 s |

There is no API change. The docs are in "Runtime reliability" in the ModelClaim guide. Reading the Pods of one pass at the same time is left for later, since that code changes in the PR for #2795. This PR does not depend on #2647.

Tests:

- New unit tests in `runtime_client_test.go`. A snapshot read gives up at its deadline. A runtime that timed out is not called for the window, for a snapshot or for `Activate`, and is called again after it. Stopping an engine is still sent. A runtime that fails fast is called again at once. The first three were run failing before their change. Each rule was also broken once, to see a test fail.
- `go test ./pkg/... ./cmd/...` (51 packages), the envtest suite in `pkg/controller/modelclaim`, and `make test-integration-controller` (90/90).

## Code review

The deadline and the backoff do what the pull request says for a runtime that accepts a connection and never writes a response. `Snapshot` wraps the call in a 10 second context (`runtime_client.go` 337–339) while `http.Client.Timeout` stays 60 seconds, so calls that change state keep the old bound. On Go 1.22 that context expiry is a `*url.Error` whose `Timeout()` is true, because `context.DeadlineExceeded` implements `net.Error` and `url.Error.Timeout` checks the immediate wrapped error. `observe` (`runtime_client.go` 263–277) records `req.URL.Host`. `do` (`runtime_client.go` 350–357) then fails the next call with `errRuntimeSilent` before `http.Client.Do`. The hanging-server tests lock that sequence for `Snapshot` and `Activate`, the deactivate bypass, and the two fast-fail cases (HTTP 500 and a refused connection).

That classification matches this client. `Client.Do` returns transport errors only. An HTTP status is a nil error, so a 500 clears the window instead of starting one. `context.Canceled` does not report `Timeout()`, so shutting the manager down does not arm the window. A refused connection is an `OpError` that is not a timeout. The new tests follow this control flow. I did not re-run the suite.

The part the client tests do not show is what the controller does with `errRuntimeSilent` on `Activate`.

`ensureActivated` reads every candidate snapshot before it activates (`modelclaim_controller.go` 395 and 413). A snapshot that hits the 10 second deadline arms the window, and the `Activate` in that same pass is not sent. Any error from `Activate` is recorded as a failed activation (`recordActivation(..., false)` at `modelclaim_controller.go` 426), then `Phase=Failed`, condition reason `ActivateFailed`, and a requeue of 10 seconds (`modelclaim_controller.go` 198–211). Health reconciliation and pool policy run only after `ensureActivated` returns nil (`modelclaim_controller.go` 217–228), so that pass skips both.

For a listener that never answers, this is the placement number in the description (120 seconds down to 10). The second 60 seconds was `Activate`. It is a bad outcome when the snapshot is slow and the control endpoints are fine. `ModelRuntime.snapshot` probes engines one after another (`model_runtime.py` 1544–1570). Each alive engine can spend 1.0 second in `engine_ready` and 0.5 seconds in `engine_request_activity`. The 1.5 second figure in the new comment is per engine. NVML runs once, under `_nvml_lock`, before that loop. A pod whose probes are slow can cross 10 seconds, arm the window, and then renew it on every later snapshot, because `observe` starts the minute over on every timeout (`runtime_client.go` 277). While that continues, a claim that selects that pod never sends `Activate`. With that pod as the only candidate, the claim stays `Failed` and `aibrix_modelclaim_activation_total{result="failed"}` increments on every 10 second requeue. A claim that already has instances and is scaling up also stops getting health updates for those instances, because of the same early return.

Placement still prefers a pod whose snapshot succeeded (`placement.go` 141–143), so a healthy peer is chosen first. The failed phase is the pool where `selectPodForActivationWithState` returns the silent address.

Two smaller gaps sit in the same client.

`observe` only sees the error from `http.Client.Do`. `getJSON` discards the body-read error (`runtime_client.go` 370). A runtime that returns headers and then stalls becomes a decode error and is not remembered. The stuck handler this pull request measures never sends headers, so the tests do not catch it.

The silence key is `req.URL.Host` (`runtime_client.go` 351), taken from `runtimeURL` (`runtime_client.go` 280–281), which formats `http://%s:%d`. An IPv6 pod IP is not bracketed, so `URL.Host` is not a stable address. That formatting is older than this change; the new map inherits it. Expired entries are removed only on the timeout path (`runtime_client.go` 272–276). A pod that timed out and then disappeared stays in the map until some other address times out. `silent` treats an expired timestamp as open, so this is retained memory.

`Deactivate` is still sent. A response that is not a timeout clears the window (`runtime_client.go` 267–269), which `TestHTTPRuntimeStillStopsAnEngineOnARuntimeThatDidNotAnswer` locks in. A stop that itself hangs still occupies the single worker for the 60 second client timeout, once per instance in `scaleDown` and `deactivateInstances` (`modelclaim_controller.go` 653–667 and 672–685). The window does not collapse those stops. The controller does not set `MaxConcurrentReconciles`, so the default of one worker is still the bound that matters.

There is no CRD, status-schema, HTTP-route, header, CLI-flag, env-var, label, or annotation change. `RuntimeClient` is unchanged. Snapshot failure still leaves routing as it is and still ranks the pod after pods that were read, which the new paragraph under "Runtime reliability" in `modelclaim.rst` describes. A skipped `Activate` is reported as `ActivateFailed` / `Phase=Failed`, and that paragraph does not say so. The 10 second and 1 minute values are constants. Leaving them as constants keeps the compatibility surface unchanged; operators cannot tune them.

The tests are the right shape for the client. They do not cover two addresses in one map, a canceled parent context, a timeout on `Sleep` or `SetKVLimit`, or the controller status and metric effect. `TestHTTPRuntimeSnapshotGivesUpOnARuntimeThatDoesNotAnswer` allows 5 seconds against a 100 millisecond deadline, so it rejects the old 60 second timeout. The production 10 second value is checked by reading `NewRuntimeClient().snapshotTimeout`, separately from the clock.

## Design simplification

Keep the two mechanisms. Cut the bookkeeping around them. Leave the silence decision in this client, and fix the status write in the controller.

Keep:

- The 10 second context on `Snapshot` only. Mutating calls stay on the 60 second client timeout. A second `http.Client` would repeat what `context.WithTimeout` already does, including canceling the dial.
- One map from `host:port` to an expiry, written only when the error reports a timeout. Fast failures stay uncached. The shared client is what makes one timed-out read cover later claims. The snapshot cache stores successes for 5 seconds and drops failures (`snapshot.go` 74–81). Health and pool policy call `Snapshot` directly, so they need this map.
- The deactivate bypass. A stop is the call that still has to go out. Removing it leaves a stuck engine in place on scale-down and finalizer removal.
- The hanging-server tests and the injectable clock. Sleeping for a minute in the test is a worse form of the `now` function.

Cut:

- The sweep in `observe` (`runtime_client.go` 272–276). An expired timestamp is already not silent. Delete that entry when `silent` looks it up. A scan of every address on each timeout is a second policy.
- Per-endpoint backoffs, extra error types, and env vars for the two durations. One window for the address is the feature. `ListModels` can stay on `do`; the controller does not call it.

Change the controller handling, not the client shape. `errRuntimeSilent` is already in this package. When `Activate` returns it, requeue without `recordActivation(..., false)`, without `Phase=Failed`, and without `ActivateFailed`. Leave the claim pending, or on its previous phase, and still run `reconcileInstanceHealth` for instances that already exist. The client should keep refusing the RPC. The status write is what turns a deferred read into a failed claim. That is a small branch on the existing error return (`modelclaim_controller.go` 198–211 and 425–427). The docs paragraph should say that a pending claim waits out the minute and is not marked failed.

Narrowing silence to reads would delete the path check in `do`, and it would put the 60 second `Activate` back on the only worker for every retry. The measured placement win depends on that call being skipped. The status branch above keeps the win.

The comment on `runtimeSnapshotTimeout` should say that the runtime's probe caps add up across engines, plus one NVML read. A pod that is slow for that reason renews the window on every attempt. Raising the snapshot deadline, or not renewing the window when the previous expiry was also a snapshot timeout, can be a follow-up. It does not need a new type in this pull request.
