## Pull Request Description

Two concurrent requests for different models can both pass `TokenizerPool`'s capacity check, perform their health checks outside the lock, and then insert into the last available slot. A pool configured for one tokenizer can therefore retain two. The initial capacity check also prevents replacing an unhealthy tokenizer when the pool is full, even though replacing that model needs no additional slot.

Recheck capacity while holding the insertion lock and allow same-model replacements. Close clients discarded after a failed health check or a lost capacity race, and close the unhealthy client when replacing it.

The regression tests use a local HTTP server and a channel barrier to force both creations past their initial checks before allowing either to finish. They cover different-model capacity contention, same-model deduplication, recovery at capacity, and idle-connection cleanup.

## Further design simplification

The production change is already small. Under the insert lock there are three outcomes: keep the healthy entry and close ours, refuse a new model and close ours, or replace an unhealthy entry and close it.

### Cut

**The second map read in the commit section.** The commit block looks up `p.tokenizers[model]` twice. One read:

- present and healthy: close the new client, return the existing one
- present and unhealthy: close the existing client, store the new one
- absent and `len >= MaxTokenizersPerPool`: close the new client, unlock, log, return the default
- otherwise store the new client

The healthy case is then the branch itself. Logging after the unlock matches the early reject, which already drops `p.mu` before `klog.Warningf`.

**Retries inside the barrier.** Leave the handler park and the `ConnState` close signal. Raise `Timeout` above the wait so `Post` does not retry while the handler is parked. That removes the extra attempts that make two `entered` signals ambiguous. The non-blocking `ConnState` send can stay.

### Keep

- The early cap check for a model that is not in the map. It avoids building a client when the pool is already full. The locked recheck stays. It is the fix.
- Closing the client that failed health, lost the insert, or was replaced, with the same type assert as the healthy-winner path. A `closeTokenizer` helper is optional.
- `Close` on the commit path, under the lock. `cleanupStaleTokenizers` closes outside the lock because it can close many clients. This path closes one client, and `Close` is `CloseIdleConnections`. The healthy-winner path already does that.
- All three tests. The two sequential tests are sound. The concurrent test needs an honest barrier.
- The current TTL rule. A placeholder slot, or a `lastUsed` bump on every slow-path attempt, would hold a failing model for as long as traffic continues.

## Further code review

The locked recheck, the existing-model exemption, and the closes on a failed health check, a lost insert, and a replaced entry are the right fix. The warning on the locked reject, the non-blocking `ConnState` send, the `RLock` around the map length, and the comment that the replaced entry is unhealthy are already in this head. What follows is only the remaining gap.

### The different-model test can pass without the race

`TestTokenizerPoolConcurrentCapacity` parks each health check in the handler (`entered <-`, then `<-release`) and sets `Timeout` to 1 second. `createOrUpdateTokenizer` copies that into `http.Client.Timeout` and sets `MaxRetries: 3`. `IsHealthy` uses a 5 second context, and each `Do` still ends at 1 second. The test waits up to 5 seconds for the second `entered` signal.

When the second caller is more than a second behind the first, the first `Do` times out and `Post` sends another request. `entered` counts requests. Two signals can both be attempts from `"first"` while `"second"` has not reached the handler. The handler never reads `r.Context()`, so the timed-out attempt stays parked until `release` is closed.

The different-model assertions match that timeout as well as a real capacity loss: pool length 1, exactly one `DefaultTokenizer`, and one idle connection closed. A green run then does not show that both creates passed the first check and that the locked recheck picked the winner. The same-model subtest still fails closed. A timeout returns the fallback, and `assert.Same` plus `assert.NotSame` fail.

`server.Close` waits until every handler returns. A retry blocked on `entered <-` after the test has stopped receiving is not released by closing `release`, and the client timeout does not pull the handler off that send. Teardown can sit there until the Go test timeout.

Leave `Timeout` unset, as the other two tests do (the client then uses 30 seconds), or set it above the 5 second wait, so a slow start fails the barrier. After `release`, wait for one successful handler completion per caller before reading the pool.

### A replacement can drop a healthy client at the TTL boundary

The slow path does not refresh `lastUsed`. `cleanupStaleTokenizers` removes an entry once `lastUsed` is older than `TokenizerTTL` (default 300 seconds) and closes it after releasing the lock. The new recheck treats a missing entry as a new model:

```go
if !exists && len(p.tokenizers) >= p.config.MaxTokenizersPerPool {
    // close the client that just passed IsHealthy
    return p.config.DefaultTokenizer
}
```

A call that was allowed through because the unhealthy entry was present can pass `IsHealthy`, find that entry gone, and find another model in the freed slot. It closes the healthy client and returns the default. The next request for that model hits the early full-pool return and stays on the default until some other entry expires. On main a full pool returns the default without attempting this replacement, so the usual full-pool case is unchanged. The hole is in the new replace-at-capacity path, and only when cleanup and another model land during the unlocked health check.

Refreshing `lastUsed` before that health check would also keep an unhealthy model in the pool for as long as requests arrive, including attempts whose health check fails. Leave the TTL policy as it is.

### The new warning runs under the write lock

The early reject unlocks, then logs `TokenizerPool reached max size`. The locked reject logs while `defer p.mu.Unlock()` is still pending. Every `GetTokenizer` takes that write lock. Unlock before the warning, the same way the first check does.

### Tests

`TestTokenizerPoolReplaceUnhealthyAtCapacity` and `TestTokenizerPoolFailedHealthCheckReleasesClient` cover the two sequential cases: replace an unhealthy entry at the cap and close the client whose health check got a 400. Keep both. The concurrent test is the one that needs the barrier to require two successful health checks.

Unit, race, lint, integration, and installation E2E are green on `525e0a47`.

### API and compatibility

No CRD field, annotation, environment variable, header, or status change. `AIBRIX_MAX_TOKENIZERS_PER_POOL` is the same key, and overlapping creates now stay inside it. `GetTokenizer` still returns `tokenizer.Tokenizer`. The caller that loses the last slot still receives `DefaultTokenizer`. A model that already has an unhealthy entry can be replaced at the cap. That is the fix.
