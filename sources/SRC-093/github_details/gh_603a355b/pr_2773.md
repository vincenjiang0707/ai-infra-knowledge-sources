## Pull Request Description

`sessionAffinityRouter.PostRouteUpdate` is called on paths that bypass `Route`/`resolveSessionPod`: the multi-strategy router's single-remaining-candidate fast path, and blended commits. Before this change it always persisted the final target pod with the claim write (Redis `SET NX`). If Redis already held a *different* address for that session key (for example, a load-imbalance gate had excluded the previously pinned pod, so routing moved elsewhere), the `SET NX` was silently rejected. Redis then kept the stale address even though the response's `x-session-id` header and the proxied request already pointed at the new pod.

This routes `writeRepin` through a compare-and-swap and uses it from both repin call sites:

- The gated refresh script from #2768 (`sessionKeyRefreshScript`) takes an optional old address (`ARGV[3]`). If Redis still holds that old address, the script replaces it with the new one and a fresh TTL (new outcome `{3}`). The existing cases are unchanged: a missing key is re-attached, a matching value has its TTL extended, and any other value is left alone and returned so the caller converges on it. A refresh is just the case where old == new; an empty `ARGV[3]` keeps the refresh behavior exactly as before.
- `persistSessionKeyToRedis` takes the old address and sends both `writeRefresh` and `writeRepin` through that script, so the unconditional `SET` for repins is gone.
- `resolveSessionPod` now also returns the stale address it saw (from the local cache or Redis) when it falls back to a rendezvous pick. `Route` passes that through `rememberSessionKey`. A delayed repin therefore replaces the stale pod only if Redis still holds it; if another replica has since pinned a different pod, it adopts that pin instead of overwriting it.
- `PostRouteUpdate` (via `commitFinalTarget`) first reads the current pin, from the local cache when that entry is confirmed and from Redis otherwise. If it finds one, it persists with `writeRepin` against that address. If it finds nothing, it uses the claim write.

Known limitation: if the Redis read in `commitFinalTarget` fails, it falls back to the claim write. That write loses to an existing pin, so the pin stays where it was until a later request. That is the same as before this change, and it never overwrites a pin.

Design review of the observe+CAS path vs. the existing `writeRepin` primitive, plus how to get the same final-target commit under prefix-cache without copying this Lua.

The bug in #2772 is real: after #2765, `PostRouteUpdate` always uses `writeClaim` (`SET NX`). The load-imbalance gate (and any other bypass of `Route`/`resolveSessionPod`) can commit the request to pod B while Redis still holds A, and `SET NX` silently keeps A. Flipping `TestSessionAffinityPostRouteUpdateDoesNotOverwriteExistingPin` to assert the new pod is the right regression.

The new `observeSessionKeyAddr` + `commitFinalTarget` + `sessionKeyRepinScript` stack is more machinery than this call site needs, and it puts compare-and-swap on the path that should be authoritative.

**Simpler fix for #2772:** `PostRouteUpdate` already knows the committed address. `writeRepin` already exists on this branch and is still an unconditional `SET`. Keep the local store + background write, but persist as a repin:

```go
if sessionKey := ctx.ReqHeaders[constants.HeaderSessionKey]; validSessionKey(sessionKey) {
    r.rememberSessionKey(ctx, sessionKey, addr, writeRepin)
}
```

That is the remaining half of the #2742 write-semantics split: claim = `SET NX`, refresh = gated TTL, **repin = overwrite with the pod this request actually used**. It matches the issue’s user-visible requirement (“once committed to B, the caller-owned key should converge on B”) without a pre-GET, a fourth write helper, or a Lua script that `resolveSessionPod` still does not use.

CAS here can also miss that requirement. If Redis already holds C, the script leaves C in place while this request went to B and `x-session-id` names B — the same pin/target split the bug is about, just for a concurrent winner. Last-writer-wins `SET` of the committed pod is the consistent rule for this hook.

**Where CAS does belong:** `persistSessionKeyToRedis(..., writeRepin)` used by `resolveSessionPod`, which already has `staleAddr`. That is the TODO still on this function: a delayed rendezvous repin must not clobber a fresher claim. This PR adds a parallel CAS path for `PostRouteUpdate` and leaves `resolveSessionPod`’s `writeRepin` as plain `SET` — inverted relative to #2742.

If a later PR wants the Lua, fold it into `writeRepin` (and rebase onto #2768 so refresh+repin share one “SET if missing or current∈{old,new}” script, with refresh as old==new). Do not grow `commitFinalTarget` / `observeSessionKeyAddr` as a second persist API.

Gemini’s `Expire` when `oldAddr == addr` is still the wrong substitute (missing key is a no-op; confirmed-but-stale local entries never re-read Redis). The one-line `writeRepin` change does not need that branch.

**Prefix-cache:** do not copy this Redis Lua into `prefix_cache.go`.

- The prefix indexer already follows the final target. `prefixCacheRouter.PostRouteUpdate` / `kvSyncPrefixCacheRouter.PostRouteUpdate` `AddPrefix` on `targetPod`. The gateway single-candidate fast path and `multiStrategyRouter.runPostRouteUpdates` already call that after `ApplyLoadImbalanceGate`. There is no `SET NX` analog; the load-gate reroute does not leave the indexer stuck on the old pod.
- The Redis session pin is what does not move under prefix-cache. Bare `prefix-cache` auto-blends only `load-balance`, so `sessionAffinityRouter.PostRouteUpdate` never runs and `x-aibrix-session-key` is ignored. Copying pin logic into the prefix router would split Redis ownership.

Same commit, two cheap extensions (neither belongs in this bugfix PR):

1. Explicit blend, already documented: `prefix-cache:W1,session-affinity:W2`. Scoring stays prefix/load; the session-affinity `PostRouteUpdate` (after the `writeRepin` change) writes the blended/gated winner. Covers the load-gate bypass because `multiStrategyRouter` fans `PostRouteUpdate` to every wrapped updater.
2. Header-driven hook in `selectTargetPod`, next to the existing `PostRouteUpdater` call: if `x-aibrix-session-key` is present, invoke session-affinity’s `PostRouteUpdate` even when it was not the selected algorithm. Prefix-cache (or any other strategy) still picks the pod; the pin follows. Do not teach prefix-cache to `GET` Redis.

Honor the pin on the next prefix-cache request only if session-affinity is actually scoring (option 1) or prefix-cache starts consulting the pin — that second part is a product choice (cache locality vs. stickiness), not part of #2772.

Happy to drop `commitFinalTarget` down to `rememberSessionKey(..., writeRepin)` in a follow-up if that direction is acceptable.

## Code Review

This pull request introduces atomic session key repinning in the simple session affinity router using a Lua script to resolve an issue where bypass paths (such as the single-ready-pod fast path) failed to overwrite stale pins in Redis. Feedback on these changes highlights opportunities to improve robustness and efficiency: specifically, adding defensive nil checks for r.redisClient in observeSessionKeyAddr and repinSessionKeyInRedis to prevent potential nil pointer dereferences, and optimizing commitFinalTarget when the observed address already matches the target address by directly extending the TTL with an Expire command rather than triggering an inefficient sequence of Redis commands.
