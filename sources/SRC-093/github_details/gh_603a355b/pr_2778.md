## 正文

## Pull Request Description
vLLM serves pooling models (embed/classify/score tasks) at a native /pooling endpoint, but the gateway's hardcoded path switch in validateRequestBody had no case for it, so pooling requests were rejected with 404 "not found" before ever reaching an engine. Users deploying embedding or scoring models behind AIBrix could only reach them through the OpenAI-shaped /v1/embeddings, which does not exist for classify/score tasks and cannot express vLLM's pre-tokenized input form.

Add PathPooling plus a validator that requires only "model" -- the one field the gateway routes on -- and forwards the body verbatim; the engine owns the rest of the schema validation. Input is held as raw JSON rather than a typed field because vLLM accepts a string, an array of strings, or a pre-tokenized array of token ids, and a wrongly-typed input must reach the engine's validator, which names the offending field, instead of collapsing into a generic gateway 400. A body with no input at all still reaches the engine, which owns that error too. Stream is rejected when present and true, as for embeddings: pooling never streams, and a stream=true body would otherwise be forwarded just to fail in the engine with a less specific error.

Verified with gofmt, golangci-lint, go vet, and go test on ./pkg/plugins/gateway/ and ./pkg/controller/modelrouter/ (including the generated-xDS consistency test), all passing.

## Design feedback: simplify

The plumbing is right and mostly unavoidable: `PathPooling`, HTTPRoute, `modelPaths`, `validateRequestBody` case, mock, xDS, e2e. Complexity to cut is in the **validator**, not the route wiring.

### 1. Make the validator match the stated design

The PR says: require only `model`, engine owns the rest. The code then also:
- builds a routing `Message` from `input` via `parseChatMessages`
- rejects `stream=true`

That is a third dialect between `/tokenize` (best-effort `prompt`/`messages`) and `/v1/classify` (strict `input`) and `/v1/embeddings` (stream guard, no message).

Simpler shapes (pick one):

**A. Ultra-thin (closest to the description)**  
`model` required; forward body; no `Message`, no stream check. Engine owns bad `input` and `stream`. Embeddings already skip `Message`; pooling traffic rarely needs prefix-cache keys.

**B. Share with tokenize**  
One small helper: “engine-native path → model + optional raw field(s) → routing text.” Pooling passes `input` (and optionally `messages`); tokenize keeps `prompt`/`messages`. Drop the bespoke `poolingReqMinimal` / `validatePoolingRequest` copy.

Avoid inventing a one-off that is neither A nor B.

### 2. Drop or justify the routing message

Calling `parseChatMessages` with a single `contentItem{Content: req.Input}` does not turn an array into several items (comment is wrong; tests expect the raw JSON blob). For prefix-cache / VTC / profile sizing, a token-id array as `"[1,2,3]"` is a weak key anyway.

If pooling is not meant to be prefix-routed, skip `Message` entirely (option A). If it is, handle `messages` the same way as tokenize — vLLM’s chat pooling form uses `messages`, not only `input`. Half-supporting `input` adds code without covering the chat form.

### 3. Stream check: keep only if you mean “like embeddings”

Rejecting `stream=true` fights “engine owns schema.” Either:
- keep it and say explicitly “non-streaming engine paths reject stream at the edge” (embeddings + pooling), or
- drop it and let the engine fail.

Don’t keep it as an unexplained exception.

### 4. Don’t grow a classify / pooling dual stack

`/v1/classify` already validates `input` strictly. `/pooling` is the vLLM-native multi-task path. Keep them intentionally different (OpenAI-shaped vs engine-passthrough), but don’t let pooling drift toward classify’s input rules “just in case.” Passthrough or shared tokenize helper — not a third schema.

### 5. Response path is fine — leave it

Staying on the language / usage path because the engine returns `model` + `usage` is correct. Tokenize stays in `nonLanguagePrefixes` for the opposite reason. No simplification needed there; the e2e verbatim-body test is the right pin.

### 6. Leave the stack wiring alone

HTTPRoute + chart + `modelPaths` + golden xDS are the cost of a new path. Don’t try to collapse those.

---

**Bottom line:** Keep the route surface. Simplify by making `/pooling` either (A) model-only passthrough or (B) a shared tokenize-style helper — and decide whether `Message` / `stream` / `messages` are in scope. Right now the validator is slightly thicker than the design it claims.

## Further design simplification

The route surface should stay: `PathPooling`, both HTTPRoutes, `modelPaths`, the xDS golden, the mock, and the e2e. The follow-up’s shared helper is the right direction. What is left to simplify is inside that helper and the mock chat branch.

### Cut the three-way ladder

`engineNativeReqMinimal` plus one switch over `prompt`, then `input`, then `messages` is why pooling reads a field the engine ignores. The helper should take one completion value: tokenize passes `prompt`, pooling passes `input`. If that value is missing or JSON null, parse `messages`. That is the whole precedence table. The comment that treats `prompt` and `input` as one “completion form raw field” goes away with the ladder.

Keep `messages` support. Parse that field only after it is chosen, from raw JSON, so it cannot fail unmarshal of a good `input`.

### Keep the stream guard out of the shared core

The stream check is the embeddings rule, and the comment now says so. The error string is still the literal `"stream not supported for pooling"` inside `validateEngineNativeRequest`, while `endpoint` is only used in the log. Leave those four lines in `validatePoolingRequest`. The shared function then only resolves model and routing text.

### Bytes: one edge check, no second response path

JSON pooling stays on the language path. Do not add a pooling-specific response decoder for `bytes` / `bytes_only`. Reject those two `encoding_format` values next to the stream guard if the gateway is not going to forward an octet-stream. That is one field on the minimal struct and one error, and it keeps `processLanguageResponse` on the body it can actually meter.

### Mock: one shape check, then the loop

The chat branch’s nested `_msg_text` is a second normalizer, and it is what turns a bad `messages` into a 500. Require a list of objects, return the same 400 the `input` branch returns, and only then join text. One output item for the chat form is the right mock of vLLM (one conversation, one vector). Leave that.

## Further code review

Reviewed head `779cafc1` against the comments already on the PR. The follow-up fixed the array-input comment, the mock 400 for a non-string/non-list `input`, chat-form routing, and the README / `test_vllm_endpoints.py` entries. What follows is only the new material.

### `prompt` wins over `input` on `/pooling`

`validateEngineNativeRequest` picks the routing text in this order: `prompt`, then `input`, then `messages`. The comment calls that vLLM’s precedence. Current vLLM pooling does not. `PoolingCompletionRequest` takes `input` (`CompletionRequestMixin.input`: string, string list, or token ids). `prompt` is not a field on that model. `OpenAIBaseModel` is `extra="allow"`, so a body that also carries `prompt` is accepted and the engine embeds `input`.

The gateway still builds the routing message from `prompt` whenever that field is present and not JSON null, including `"prompt": ""`. Prefix-cache, VTC, and profile sizing then key off the wrong text. The new unit case only shows `input` beating `messages`. It does not include `prompt`.

Same switch on `/tokenize`: a body with no `prompt` and an `input` field now gets a routing key from `input`. Tokenize previously ignored `input`.

Select the completion field by endpoint. Tokenize reads `prompt`. Pooling reads `input`. Then fall through to `messages`.

### A non-array `messages` rejects a valid `input`

`input` stays `json.RawMessage`, which is why a badly typed input still unmarshals. `messages` is `[]contentItem`. Sonic fails the whole struct when `messages` is not an array, and the gateway returns a generic 400 with an empty param.

`{"model":"m","input":"hello","messages":"nope"}` is a legal pooling completion body: `messages` is an ignored extra, and the engine uses `input`. The gateway never forwards it. Hold `messages` as raw JSON and parse it only when `input` is absent, the same way `input` itself is held raw.

### `encoding_format` `bytes` / `bytes_only` becomes a 500

JSON pooling (`float`, `base64`) returns `model` and `usage`, and staying on the language response path is right for that body. vLLM’s other two formats return `application/octet-stream` (`request_output_to_pooling_bytes_response`). `isLanguageRequest` is true for `/pooling`, so `processLanguageResponse` buffers that body and `sonic.Unmarshal` fails. The failure path is a 500 (`HeaderErrorResponseUnmarshal`) in place of the embedding bytes. Usage for those responses lives in the `metadata` header, not in the body, so the language path would not meter them even if the unmarshal were skipped.

The mock, the unit tests, and `TestPoolingResponseIsForwardedVerbatim` only see the JSON shape. Nothing covers `encoding_format`.

Smallest fix that matches the existing stream guard: reject `bytes` and `bytes_only` at the edge with a field error, and keep JSON pooling on the language path. A passthrough has to skip `processLanguageResponse` for that request and will still not see `prompt_tokens` unless it reads the metadata header.

### Mock chat form still 500s

The `input` branch now 400s on a dict, number, or bool. The new `messages` branch does not. `input is None` goes straight to `_msg_text`, which calls `.get` on each element. A string, dict, number, or a list of non-dicts raises, and the outer `except` returns 500. `test_pooling_chat_form_uses_messages` only posts a list of objects. Guard `messages` the same way as `input` before iterating.
