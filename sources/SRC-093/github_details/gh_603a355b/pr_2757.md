# [PR #2757] [Bug] Stop LocalStorage rewriting newlines in stored text objects

state: closed | updated: 2026-09-24T01:10:43Z

## 正文

## The bug

`LocalStorage._write_file` writes text objects through a text-mode handle:

```python
with os.fdopen(fd, "w", encoding="utf-8") as f:
    f.write(str(reader))
```

Without `newline=""`, Python translates every `"\n"` written to `os.linesep`. On Windows that means a stored text object comes back with `\r\n`, so `put_object(x)` followed by `get_object()` does not return `x`. Nothing raises — the corruption is silent, and `LocalStorage` is the default local-development backend.

Minimal repro, independent of aibrix:

```python
fd, p = tempfile.mkstemp()
with os.fdopen(fd, "w", encoding="utf-8") as f:
    f.write("a\nb")
open(p, "rb").read()      # b'a\r\nb' on Windows, b'a\nb' with newline=""
```

## Why it has gone unnoticed

`os.linesep` is `"\n"` on Linux, so the translation is a no-op there and CI stays green. It is only observable on Windows, where it already makes an existing spec fail:

```
tests/storage/test_reader.py::TestReaderIntegration::test_reader_with_different_file_types_in_storage
AssertionError: assert b'name,age\r\nAlice,30\r\nBob,25' == b'name,age\nAlice,30\nBob,25'
```

## The fix

Pass `newline=""` so the bytes are written exactly as given. That is the standard way to ask Python for no newline translation — the same thing the `csv` module's docs require when opening files.

Scope is deliberately one line. `_write_json_file` uses the same text-mode pattern but is not affected: `json.dump` emits no bare newlines and escapes `\n` inside values, so nothing reaches the translation layer. Happy to harden it defensively in a follow-up if maintainers prefer.

## Tests

Added `test_text_content_round_trips_without_newline_translation`, which stores a string containing `\n`, reads it back, and asserts the bytes are unchanged. Removing `newline=""` again turns it red on Windows with a diagnostic failure:

```
assert b'first\r\nsecond\r\nthird' == b'first\nsecond\nthird'
```

**One honest limitation:** this spec cannot fail on Linux CI, for the same reason the bug is invisible there. I could not find a way to catch it on Linux without asserting on the implementation (e.g. mocking `os.fdopen` and checking the arguments), which seemed worse than leaving it platform-gated. The structural answer is Windows coverage in CI, which is beyond this PR — flagging it rather than pretending the spec guards every platform.

With the fix, `pytest tests/storage` is 156 passed / 13 skipped on Windows; previously 154 passed / 1 failed.
