## 正文


## Pull Request Description

The Redis counter key currently rotates at wall-clock bucket boundaries, while its TTL starts with the first write. A request can therefore reach a new counter before the original window expires.

The counter key is now stable for each limiter, logical key, and configured duration, so Redis expiry determines the window boundary. This applies to model RPS and the shared limiter used by user RPM/TPM.

## What Changed

- `pkg/plugins/gateway/ratelimiter/redis.go` (+4/-4): replace the wall-clock bucket in `genKey` with a stable `name:key:windowMilliseconds:counter` key.
- `pkg/plugins/gateway/ratelimiter/ratelimiter_test.go` (+72): cover first-write windows for a two-second model override and a one-minute user limit, plus separation when the configured duration changes.
- `pkg/plugins/gateway/replica_rps_test.go` (+2/-1): advance miniredis time instead of sleeping, so the test checks Redis key expiry.
- `pkg/plugins/gateway/ratelimiter/README.md` (+10/-14): update the key description and document the rollout risk.

The key-format change starts fresh counters on deployment. During a rolling upgrade, old and new gateway instances count separately and may temporarily admit more than the configured limit. Where strict limits are required, avoid serving rate-limited traffic from both versions at once. The limiter README documents this rollout consideration.

## Code review

The change is correct, and it is the fix the existing script already assumes. `incrAndExpireScript` (`redis.go` 95–101) sets `PEXPIRE` only when `PTTL` is `-1`, so the deadline is the first write. `genKey` on main still appends `time.Now().Unix()/windowSeconds % 64` (`redis.go` 77 on main). A call that crosses that boundary reads and writes a new key while the previous key is still inside its TTL, so the request is admitted against an empty counter. Issue #2805 measured that as about one failure in thirty on `TestModelReplicaRPS_Half_AllowsOneRequestEveryTwoSeconds`, `TestHandleRequestBody_ReplicaInflightCoexistsWithReplicaRPS`, and `TestEnforceModelRPS_RejectDoesNotPostponeNextWindow`.

`Incr` computes one duration and passes it to both `genKey` and `incrAndExpire` (`redis.go` 67–72). `Get` uses the same function with the limiter’s `windowSize` (`redis.go` 48–49). User RPM and TPM never pass an override, so `checkRPM`, `incrRPM`, `checkTPM`, and the response-body TPM increment share `aibrix:{user}_{RPM|TPM}_CURRENT:60000:counter`. Model RPS passes `rateWindow` (`gateway_ratelimit.go` 164–171): nil for a window of 1 second or less, otherwise `N * time.Second` with `N >= 2`. That becomes `aibrix_model:{model}_MODEL_RPS_CURRENT:{N*1000}:counter`. Refunds in `enforceModelRPS` and `decrModelRPS` pass the same `rateWindow` value, so a refund hits the charge for as long as the key lives. Gateway clocks no longer have to agree; the window is the Redis TTL.

A fixed window can still admit `limit` at the end of one TTL and `limit` at the start of the next. That boundary is the window length after the first write, which is what the script and the A1 tests already require. RPM and TPM for one user are separate keys, so their 60-second windows start at the first request and the first token update respectively. Replica-count changes that alter `RateWindowSeconds` (`rpsToLimitWindow`, up to `maxRateWindowSeconds` of 3600) publish a new key and the new window starts at zero. The old key expires on its own TTL. `TestRedisRateLimiter_DifferentWindowSizesUseSeparateCounters` locks that split, and `Get` stays on the default-window key (`ratelimiter_test.go` 135–137).

The rolling-upgrade note is accurate (`README.md` 82–84). Legacy keys are `{name}:{key}:{0..63}`. New keys carry a millisecond component of at least 1000 and a `:counter` suffix, so a new pod cannot read an old bin or a `GetLimit` key (`name:key`). During a mixed rollout the two versions count separately and can together exceed the configured limit. After cutover every counter starts fresh for one window. That is the right compatibility plan for keys whose TTL is the window (1 second to 1 hour). No Kubernetes API, CRD, HTTP field, header, CLI flag, env var, label, or annotation changes. The `RateLimiter` interface already had the variadic window; this diff does not change it. `docs/source` does not document the Redis key format. The package README is the operator-facing description, and it now matches the code, including the Lua script that the old README still called a pipeline.

`decrModelRPS` can still seed the next window with `-1` if the refund arrives after the key has expired (`gateway_ratelimit.go` 147–150). That now requires the failure path to outlive the whole TTL, rather than to cross a wall-clock bin. A negative seed then lasts for the new window, which for a sub-1 rps limit can be as long as an hour. The existing comment already declines a floor-at-zero script. This pull request does not make that worse often enough to add one.

The sub-millisecond clamp suggested on `genKey` does not belong in this diff. `NewRedisAccountRateLimiter` already floors the constructor window at 1 second (`redis.go` 37–38). `rateWindow` only supplies whole seconds of 2 or more. `Incr` ignores a non-positive override (`redis.go` 69–70). A direct caller that passed a positive duration under 1 millisecond would format `:0:counter` and `PEXPIRE` 0, and Redis would drop the key. Clamping only inside `genKey` would label the key with 1000 while `incrAndExpire` still sends the original millisecond value (`redis.go` 104). Any clamp has to happen once, on `w`, before both calls. No gateway path needs it.

The tests cover the regression. `TestRedisRateLimiter_WindowStartsWithFirstWrite` (`ratelimiter_test.go` 68–117) asserts the production key strings (`:2000:counter` and `:60000:counter`), a shared count at half the TTL, and a fresh count after the TTL plus 1 millisecond. `miniredis` does not move `time.Now()`, and the new key does not read `time.Now()`, so the constant key is the wall-clock assertion. `FastForward` is what expires the TTL. Replacing `time.Sleep(2100ms)` in `TestModelReplicaRPS_Half_AllowsOneRequestEveryTwoSeconds` (`replica_rps_test.go` 120–121) is required: after this change a sleep leaves the miniredis key in place and the third request stays rejected. The other two A1 tests already use either immediate calls or `FastForward`, and the stable key removes their bucket race without further edits. `TestRedisRateLimiter_RejectedIncrementDoesNotExtendTTL` still guards the script. The localhost Redis tests still call `genKey` and still skip when Redis is absent; they are not the coverage for this bug.

### bolubo · 2026-09-26

I was looking into the red Installation E2E on this branch, and I think it's the two E2E helpers, which were written for the old wall-clock behavior. The limiter change itself looks good to me.

Both fail with `allowed=0` and the same message, "exactly one request should be allowed within the 1 RPS window":

- `TestModelReplicaRPSLimit/second_request_in_same_window_is_rejected`
- `TestModelRPSLimit/requests_succeed_after_window_resets`

Here's the failing job: https://github.com/vllm-project/aibrix/actions/runs/36177820883/job/108234123094

The helpers wait for the next wall-clock second plus 50ms:

```go
nextWindow := time.Now().Truncate(time.Second).Add(time.Second + 50*time.Millisecond)
time.Sleep(time.Until(nextWindow))
```

That worked before because the key rotated at every bucket boundary. Now the counter expires one window after its first write, and that write happens right after the helper returns, so the next wait lands almost exactly on the previous counter's expiry. When the counter is still alive, the burst sees a full window and both requests get 429.

Runs of this workflow on main look green recently, so I don't think it's an environment flake.

If it helps, the helper could wait a full window plus a small margin from the last request, in both `model_rps_limit_test.go` and `model_replica_rps_limit_test.go`:

```go
waitForFreshWindow := func() {
    // Windows are anchored to the first write now, so a fresh window means
    // one full window since the last request.
    time.Sleep(time.Second + 100*time.Millisecond)
}
```

For context, the same assumption makes the unit tests in #2805 A1 flake on main, at roughly one red run in thirty.

This pull request refactors the Redis rate limiter to use a first-write window strategy instead of wall-clock buckets, updating the counter key format to include the window size in milliseconds and setting the TTL atomically on the first write.
