## Pull Request Description

  This PR updates ModelClaim fixed-topology validation to account for vLLM
  prefill context parallelism (PCP).

  The required GPU group size is now calculated consistently by both the
  ModelClaim controller and the runtime sidecar as:

  ```text
  tensor-parallel-size
    × pipeline-parallel-size
    × prefill-context-parallel-size

  This prevents a ModelClaim using PCP from being scheduled onto a warm Pod with
  fewer GPUs than the engine topology requires. The runtime repeats the same
  validation before activation so that direct or stale controller requests cannot
  bypass the topology check.

  The change also:

  - treats omitted TP, PP, PCP, and DCP values as 1;
  - rejects non-positive or malformed context-parallel values;
  - keeps data parallelism unsupported for fixed-topology pools;
  - adds overflow checks for the TP × PP × PCP calculation;
  - extends controller and runtime tests for PCP placement;
  - updates the ModelClaim documentation and sample topology contract.

  ### Why DCP is not included in the GPU topology constraint

  Decode context parallelism (DCP) is intentionally validated as a positive
  integer but is not multiplied into the required GPU count.

  Unlike PCP, DCP does not create an additional set of ranks. It reuses ranks
  from the existing TP/PCP topology during decode. Including DCP in the topology
  formula would therefore overestimate the number of GPUs required and reject
  otherwise valid warm Pods. For example, a TP=4, DCP=2 configuration still
  requires four GPUs, not eight.

  This layer is responsible for verifying the physical resource contract between
  a ModelClaim and a warm Pod. More specific semantic constraints between DCP and
  the engine topology, such as supported divisibility or grouping rules, should
  remain with vLLM. Those rules are engine- and version-dependent, and duplicating
  them in both the controller and runtime sidecar could drift from the validation
  performed by the engine itself.

  Accordingly, AIBrix only verifies that the supplied DCP value is syntactically
  valid and positive. It does not use DCP to calculate or further restrict the
  Pod GPU count.

### cursor[bot] · 2026-09-23

## Design feedback: simplify

The formula and dual-path check (controller + runtime) are right. Little to cut structurally; the main design choices are what belongs in the sizing function.

### 1. Keep one job for `vllmParallelism`

It should answer: **how many GPUs does this claim need?**  
`TP × PP × PCP`, omit → 1, reject non-positive / DP≠1, overflow-safe. That is the whole contract.

### 2. Don’t half-validate DCP inside the sizer

Validating `--decode-context-parallel-size` as positive while **not** multiplying it mixes “resource contract” with “engine arg lint.” The PR already argues DCP semantics stay with vLLM.

Simpler: drop DCP from `vllmParallelism` / `vllm_parallelism`. If you want early rejection later, add a separate lint. Documenting “DCP ignored for GPU count” is enough for this layer.

### 3. Make multiplicative factors explicit

A small list beats an open-coded product that grows with each new dim:

```text
gpuFactors = TP, PP, PCP
validateOnly / ignore = DCP, …
```

Same list in Go and Python comments (or shared docs). Next CP variant is one entry, not another special case.

### 4. Keep dual validation; fix parity, don’t add a third copy

Controller filters warm pods; runtime re-checks before activate. That duplication is intentional. Don’t add a webhook/CRD field for the same number. Do keep Go and Python defaults identical (empty string — see code review).

### 5. Docs are fine

Formula, sample args, troubleshooting “TP×PP×PCP” updates are the right surface. No extra API.

**Bottom line:** Keep `TP×PP×PCP`. Simplify by treating the function as GPU-count only (drop DCP from it) and aligning Go/Python defaults.
