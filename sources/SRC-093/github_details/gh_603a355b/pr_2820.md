## 正文

## Pull Request Description

**Problem.** Prefix matching from KV events stops after the first block of each `BlockStored` event. A three-block event matches 33% of a request that shares all three blocks.

**Root cause.** `ProcessBlockStored` in `pkg/utils/syncprefixcacheindexer/sync_hash.go` computed every block's AIBrix hash from `event.ParentBlockHash`. That field is the parent of the first block only. On the request path `GetPrefixHashes` chains each block from the one before it, so blocks after the first got hashes the gateway never looks up. vLLM batches newly full blocks into one event, so multi-block events are the normal case for long prefills.

**Fix.** Look up the parent once before the loop. Then carry the previous block's hash forward, using the existing mapping when a block is already known.

**Tests.** Added `TestProcessBlockStoredMultiBlockChain`, which covers three cases:
- one event with all blocks (33% before the fix, 100% after)
- an event whose first block is already mapped (33% before, 100% after)
- an event continuing from a known parent block (66% before, 100% after)

Checks run:
- `go test ./pkg/utils/syncprefixcacheindexer/ ./pkg/cache/ ./pkg/plugins/gateway/algorithms/` passes.
- `go test -race ./pkg/utils/syncprefixcacheindexer/` passes.
- `golangci-lint run ./pkg/utils/syncprefixcacheindexer/...` reports 0 issues.

## Code review

The happy path is the right fix. `ParentBlockHash` is the parent of the first block only (`events.go`). `GetPrefixHashes` walks `H(seed, b0)`, `H(h0, b1)`, … (`sync_hash.go`). The old loop recomputed every block from `event.ParentBlockHash`, so block `i > 0` never matched a request. vLLM sends one event for a batch of newly full blocks, and `convertTokenIDs` already splits that batch into one token slice per block, so this is the normal long-prefill case.

The new code looks the parent up once (`sync_hash.go` 271–276), then sets `parentAibrixHash` from the block it just handled. Both branches do that: a new block assigns the hash it computed (293), and an already-mapped block assigns the stored hash (286) before `continue`. The second assignment is required. A repeat of block 0 must still be the parent of block 1. `TestProcessBlockStoredMultiBlockChain` covers the three cases from the issue, and `MatchPrefix == 100` is the right oracle. I ran that test on `674f50dd`; all three subtests pass.

No compatibility surface moves. `BlockStored`, `ProcessBlockStored`, and `MatchPrefix` keep their fields and signatures. There is no CRD, webhook, HTTP route, header, status code, CLI flag, env var, label, or annotation change. The table is in memory. A gateway restart drops hashes written by the old loop, so a rollout does not need a migration. During a mixed rollout, new pods match the whole event and old pods still stop after the first block. The idempotent branch will not recompute a hash that this process already stored, which matters only inside one process that indexed multi-block events before the new binary was loaded.

The behavior change past the bugfix is an unknown parent. If `ParentBlockHash != nil` and that engine hash is absent from `engineToAibrix`, the code still starts at `s.seed` and then chains the rest of the event (271–276, 292–293). I probed that on this commit: two blocks whose parent is missing match a request that starts at those blocks at 100%. The same probe against the old loop matches at 50%, because the second block was hashed from the seed and did not equal `GetPrefixHashes`. A request for the real prefix, including the missing parent block, matches at 0% either way. So the new chain turns a lost parent into a full false hit on the suffix. Prefix routing will prefer that pod. The pod has those tokens only after the missing parent, so the engine prefix lookup misses.

That parent is missing when an earlier event was dropped. The ZMQ client already counts sequence gaps and still advances `lastSeq` (`zmq_client.go` 331–361). `HandleEvent` logs an error and continues; it does not retry the batch. Writing the suffix anyway stores engine hashes that the idempotent path will keep, so a later copy of the same event cannot repair them.

Skip that event. When the parent pointer is set and the lookup misses, log a warning and return nil before the loop. Returning an error only increments `handle_event` and still drops the batch. A warning that still writes the chain leaves the 100% suffix hit in place. `TestProcessBlockStored` uses parent `999`, which is not in the map, and only checks that two mappings exist, so it stays green either way. Add one case: unknown parent, suffix `MatchPrefix` stays 0.

`bs := NewSyncPrefixHashTable().blockSize` (`sync_hash_test.go` 276) starts the eviction worker and never calls `Close`. The subtests close their own tables. Read `prefixCacheBlockSize` instead. The `func() *int64` inside the third composite literal is the same pointer a local `parent := int64(1)` would be.

## Design simplification

Keep the loop as it is. One local `parentAibrixHash`, one lookup before the loop, and an update in both branches. That is the whole fix. Leave `computeHash` and `GetPrefixHashes` alone.

Keep the three table cases and the single `MatchPrefix == 100` check. The older test counts `engineToAibrix` entries and stayed green while this bug shipped. Extra map-length asserts in the new test would repeat that blind spot.

Cut the throwaway table on line 276 and the closure that boxes `*int64`. Use `prefixCacheBlockSize` and a local `parent`.

The missing-parent guard belongs in `ProcessBlockStored`, in place of the seed fallback, and nowhere else. No new error type, no chain type, no replay buffer. A lost parent event stays a cache miss until the engine emits those blocks again.
