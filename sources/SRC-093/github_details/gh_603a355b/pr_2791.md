## 正文

**Title:** [Bug] Infer StormService mode from spec.replicas when spec.mode is unset

## Pull Request Description

Fixes #2780.

When a PodAutoscaler scales a single role through `subTargetSelector.roleName`, it first works out which mode the target StormService is in. `stormServiceScalingMode` used to return pooled mode whenever `spec.mode` was absent and the PodAutoscaler carried no deprecated annotation. The stormservice controller does not agree: it uses `ResolvedMode()`, where `replicas > 1` means replica mode.

Once the autoscaler settles on pooled, what it reads and what it writes stop being the same quantity. It reads `status.roleStatuses[role].replicas`, which is the role summed over every RoleSet, and writes `spec.template.spec.roles[role].replicas`, which the controller copies into each RoleSet. The two differ by the number of RoleSets, so it can never converge. On kind, with `replicas: 3` and `maxReplicas: 10`, the decode role ended up at 30 Pods while the PodAutoscaler kept reporting `actualScale=30 desiredScale=10`, rewriting the template on every reconcile and rebuilding the RoleSets as it went.

The change is one line: when neither the mode nor the annotation is present, fall back to `ss.Spec.ResolvedMode()`, which is the same inference the controller applies. That is the compatibility rule #2449 recorded in its backward-compatibility section. A declared `spec.mode` and the deprecated annotation keep their precedence.

One behaviour change worth calling out: `annotation: pool` combined with `replicas > 1` now resolves to replica mode. That combination contradicts itself (`pool` is not a valid value either — the code only ever matched `replica`), and I added a case to pin the new behaviour down. Happy to keep it pooled instead if you would rather not change it.

## Tests

Six cases added to the `TestStormServiceScalingMode` table:

- no mode with `replicas` of 3, 1 and 0
- `spec.mode: Pooled` with `replicas: 3` stays pooled
- annotation `replica` with `replicas: 1` stays replica
- annotation `pool` with `replicas: 3` infers replica

The last three guard the precedence order, so the fallback is the only thing that moved. The eight existing cases are untouched.

Two more tests cover the read and write paths:

- `TestGetCurrentReplicasInferredReplicaMode` deliberately sets `spec.replicas=3` against an aggregated status of 6 and asserts the autoscaler reads 3
- `TestSetDesiredReplicasInferredReplicaMode` asserts `spec.replicas` is what changes and the role replicas in the template are left alone

What I ran:

```
go test ./pkg/controller/podautoscaler/...      all pass
golangci-lint v2.13.1                           0 issues
```

I also reverted the one line to the old behaviour to check the tests actually catch this: the four new cases fail and the eight existing ones still pass.

Verified on a cluster too. With the patched controller and the same setup, `spec.replicas` climbs from 3 to 10 and stops, the template's `decode: 2` is never touched, and the following two minutes show zero RoleSet rebuilds and zero rescale calls.

## Review

This is the right fix for #2780. `stormServiceScalingMode` was the only remaining caller that treated an omitted `spec.mode` as pooled, while `StormServiceSpec.ResolvedMode()` (and the stormservice controller) already infers Replica when `replicas > 1`. Role-level PA then read the RoleSet-aggregated status and wrote the per-RoleSet template, so `actualScale` could never meet `desiredScale` and RoleSets rebuilt on every reconcile. Falling through to `ResolvedMode()` is option 1 from the issue thread and matches #2449.

The new table cases plus `GetCurrentReplicas` / `SetDesiredReplicas` tests hit the actual read/write mismatch, not just the helper. Keep the `annotation: pool` + `replicas: 3` → Replica case. `pool` was never a matched value (only `"replica"` is), and preserving pooled there would reintroduce the same controller disagreement Copilot's "restrict inference to absent annotations" suggestion would restore.

**Must fix:** the comment on `stormServiceScalingMode` still says `spec.replicas` is intentionally unused. That is now false.

**Document, do not special-case:** scaling an inferred-Replica object down to `replicas == 1` flips both the controller and the PA to pooled on the next reconcile (`ResolvedMode` treats `<= 1` as pooled). Subsequent scale-up then writes `template.spec.roles[].replicas` instead of `spec.replicas`. That is the existing inference contract, not a PA-only bug. A one-line warning in the helper comment (and a table case that `replicas: 1` after an inferred replica scale-down is pooled) is enough. Autoscaled StormServices that need to go to 1 RoleSet should set `spec.mode: Replica`.

Samples that omit `spec.mode` with `replicas > 1` become safe under this PA; still worth setting `spec.mode` explicitly, but that can be a follow-up.

Not blocking: no other callers of the old pooled default showed up in this path.

### googs1025 · 2026-09-23 · COMMENTED

I suggest keeping this fix small while making the compatibility boundary explicit:

  1. Keep the ss.Spec.ResolvedMode() fallback for legacy StormServices, but only when both spec.mode and the legacy PodAutoscaler annotation are absent.
  2. Preserve the existing semantics of an explicitly present legacy annotation. Please distinguish annotation absence from a non-"replica" value:
```
  if value, exists := pa.Annotations[AutoscalingStormServiceModeAnnotationKey]; exists {
      if value == "replica" {
          return orchestrationv1alpha1.StormServiceReplicaMode
      }
      return orchestrationv1alpha1.StormServicePooledMode
  }
  return ss.Spec.ResolvedMode()
```
  This ensures that an explicitly present "pool" or other legacy non-"replica" value retains the historical Pooled behavior rather than falling through to replicas-based inference.

  3. Update the function comment, which currently says that spec.replicas is not used for inference and therefore contradicts the new implementation.
  4. Add a user-facing note to the autoscaling documentation describing the one-way-flip limitation. When both spec.mode and the legacy annotation are absent, an inferred Replica-mode StormService that scales down to spec.replicas: 1 will subsequently resolve as Pooled. Recommend explicitly setting spec.mode as the stable source of scaling semantics and the supported way to prevent this transition.

  5. Keep the examples on explicit spec.mode (Replica or Pooled) so that recommended configurations have stable scaling semantics.
  6. Describe replicas-based inference as best-effort backward compatibility for legacy objects, not as a fully stable autoscaling mode. Users who need Replica autoscaling to scale down to one should explicitly configure:
```
  spec:
    mode: Replica
```
