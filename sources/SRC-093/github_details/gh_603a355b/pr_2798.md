## 正文

### Pull Request Description

BucketServe (arXiv 2507.17120) serves prompts of similar length together so the engine batches are length-homogeneous. A gateway cannot form engine batches, so this PR lands the gateway half of the idea: where several rolesets declare overlapping prompt-length ranges, the gateway splits the overlap into one band per roleset, adapts the cut points to the traffic it observes, and the prefill path prefers the roleset a request length is banded to. Each roleset then receives a length-homogeneous slice of the load, which is what lets the engine-side batches be homogeneous in turn.

The plan is advisory on purpose. `filterPrefillDecodePods` applies it after the load-imbalance fast paths and only while the banded roleset still has both a prefill and a decode candidate; when it does not, or when the plan holds no band for the request's length, the fast paths' choice stands. A stale band therefore costs balance, never correctness.

**Scope**: gateway routing only. No pod, engine, deployment, autoscaling, or CRD change. Off by default (`AIBRIX_BUCKET_SERVE=false`), and with the switch off the routing path is unchanged. The feature requires prompt-length bucketing to be on, because the plan only re-orders the rolesets that bucketing already filtered to.

### How it works

- Per model, the tracker keeps a log2 histogram of the prompt lengths this gateway routes, decayed with a 30s EWMA half-life, and recomputes the plan at most once every 5s or when the roleset set changes.
- The declared ranges are cut into segments whose covering set does not change. Every roleset is first charged the traffic only it can serve, and the remaining cuts are placed so each roleset ends up carrying the model's traffic in proportion to its prefill replica count. A segment shared by two or more rolesets needs 5% of the model's traffic before it is split, and one plan holds at most 16 affinity bands; a wide overlap that cannot afford a band per needing roleset splits into as many bands as the budget left allows, and an interval that is not split keeps every covering roleset a candidate.
- `AIBRIX_BUCKET_SERVE_MODE` picks what the cuts balance: `throughput` (default) places them at prompt-token quantiles, `rps` at request-count quantiles.
- Both the switch and the mode are per profile (`routingConfig.bucketServe` and `routingConfig.bucketServeMode`), so one model can run the plan while another does not.
- The plan is computed outside `selectMu`, the way the policy Prepare step is, and only its application runs under the lock.

```
bucketServeBand()   before selectMu, one call per request
    observe promptLength -> groups -> plan -> band

filterPrefillDecodePods()
    steps 1-5: bucket filter and the load-imbalance fast paths
    banded roleset still has both sides  -> narrow to it
    otherwise                            -> fast paths' choice stands
```

Metrics: `pd_bucket_serve_band_total` and `pd_bucket_serve_prompt_tokens_total` (label `roleset`) count the requests and the prompt tokens each banded roleset carried, so a counter joins the pods that received the band, and the `pd_bucket_serve_band_max` gauge holds the current upper prompt-length bound of the band a roleset holds, deleted when the roleset leaves the plan.

## Design simplification

Keep the safety property and the segment table. Cut the planner's ceremony.

Keep the off switch, the bucketing prerequisite, and the apply site after the fast paths. That is the whole routing change, and it is in the right place. Keep `bucketServeSegments`, including the `MaxInt` clamp: the overlapping ranges really are a sweep line, and the tests for the partition are the ones worth having. Keep one EWMA histogram and both modes. Updating `weights` and `masses` together is a few adds, and it is what makes a mode switch use data the gateway already has. Keep the profile pointers and the env loader. Keep the three routing specs.

Cut `ValidBucketModes`. Cut `Enabled` on `BucketServeConfig`. The gateway already returns before the tracker when the request is off, and `computeBands` never reads the flag. Cut `Configure`, `Observe`, and `Plan` as three locked calls. One `Band(model, mode, length, now, groups)` observes, decays, and returns the roleset. The 5s cache key includes the mode, so two profiles stop clearing each other's plan. Cut unassigned bands from the returned plan. A gap means no preference. `GroupFor` already treats an empty group as no preference, and the routing path only uses the roleset. The partition tests can assert the cuts without making "no opinion" a band that occupies an index and a gauge series. Cut `BucketPlanEvents`, `bucketServePlanDiff`, and `bucketServeCutsOf`. They exist to increment split and merge counters. A roleset-labeled request counter and a roleset-labeled upper bound replace the index, and they do not need a cut-set diff. Delete the gauge series when a roleset leaves the plan.

The assignment loop should use a weight the caller already has. `eligiblePDRolesets` knows how many prefill replicas the roleset has, and the segment table knows the exclusive tail. Give `BucketGroup` a replica count, charge each roleset its exclusive mass, and place the shared cuts so remaining work is proportional to replicas. That replaces name order. It is smaller than the event diff it would displace, and it is the difference between a band the fast path leaves alone and a band the fast path immediately undoes. The cap then splits a segment into at most the remaining band budget, instead of dropping a 17-way overlap on the floor.

Leave the half-life, refresh, share, and cap as constants, the way this PR already does. A knob for them is a later change. Do not add a second tracker, a per-pod histogram, or engine feedback in this PR.

## Code review

### Correctness

The safety property holds. `bucketServeBand` runs only when prompt-length bucketing is already on, and it returns before taking the tracker lock when the request's resolved switch is off. The band is applied after the combined-pod path and both load-imbalance fast paths, and only when the banded roleset still has a prefill candidate and a decode candidate. Otherwise the fast paths' choice stands. A stale plan cannot route a length to a roleset the bucket filter already removed, and it cannot drop the last candidate. The tracker lock is not taken under `selectMu`. With the switch off, the selected pods are the ones today's filter would select.

`podPromptLenBucketBounds` preserves `isPodSuitableForPromptLength`. A pod with no profile still returns `(0, math.MaxInt32)` and is treated as unbounded. The `math.MaxInt` clamp in `bucketServeSegments` is the right fix: production's open range is `math.MaxInt32`, which is `math.MaxInt` on a 32-bit build, and `Max+1` would wrap. Shortening that sentinel by one token does not change a real bucket.

The quantile math does what the tests lock in, and that policy is narrower than the description. Covering rolesets are ordered by `(Min, Max, Name)`. The lower slice goes to the first of those. Identical ranges therefore give the lexicographically first roleset the short prompts and the next name the long ones. `TestBucketServePlanSplitsSharedRange` and the routing spec both assert that order (`dep-a` / `rs-a` on the short side). Nothing in the planner reads replica count. `bucketServeGroups` has the roleset's pod lists from `eligiblePDRolesets` and keeps only `prefills[0]`'s range.

Partial overlap is unbalanced by construction. For `short` at `[0, 4096]` and `general` at `[0, 8192]`, the shared segment is split at a quantile and the exclusive tail stays unassigned, so only `general` serves it. `general` receives its share of the overlap plus the whole tail. `TestBucketServeSegmentsRespectDeclaredRanges` locks the geometry (lower shared slice to `a`, upper shared slice to `b`, tail unassigned) and does not account for that extra mass. The histogram records demand, including requests whose band the fast path later discards, so an override does not move the cut. The default prefill fast path fires when in-flight counts differ by more than `AIBRIX_PREFILL_LOAD_IMBALANCE_MIN_SPREAD` (16). Once replica counts differ, or the wider roleset is carrying a tail, that fast path is what actually balances, and the band stops applying. The feature then fails open, which is safe, and it also stops shaping the traffic it observed.

Per-request mode is implemented as one config on the model. `Configure` replaces that config and clears `planAt`. Alternating profiles on one model each get a plan for their own mode, and each flip recomputes immediately, ignoring the 5s refresh. The same length is then banded to different rolesets depending on which profile handled the request, which mixes lengths at the engine. Split, merge, and `pd_bucket_serve_band_max` follow the flap.

Bin resolution is about 9% per octave, and weight is the sum of bins whose center lies inside the segment. A cut lands on a center, so requests that share a bin can fall on either side of it. A declared max that sits mid-bin drops that bin's mass from the segment. Power-of-two maxima, the usual bucket edge, only mis-attribute the single endpoint length, because that length is the start of the next bin and the center sits about 4% above the edge. This is a resolution limit, not a routing-safety bug.

`prefills[0]` is the first prefill in ready-list order. The comment says a roleset shares one profile. If it does not, the plan's range follows whichever pod the list happened to put first, while bucketing still filters pod by pod. The band stays inside the already filtered set, so this cannot admit an out-of-range pod. It can assign the roleset a range that is not the range of every pod in it.

The 16-band cap unsplits whole segments, lightest first. One shared range covered by 17 rolesets is 17 affinity bands, the cap drops the segment, and the overlap is not split at all. `TestBucketServeMaxBandsCapKeepsIntervalsWhole` locks that cliff for 3 rolesets and `MaxBands = 2`.

### Risks

`pd_bucket_serve_band_total` and `pd_bucket_serve_prompt_tokens_total` are labeled with the band's index. The index is the position in the current plan, including unassigned segments. A refresh that inserts a slice renames every later series, and the counters are not reset. `pd_bucket_serve_band_max` is the only way to decode an index, and it is rewritten in place. When the plan shrinks, higher indexes are left at the previous max. There is no `DeleteGaugeMetric`, which the token-load gauges do use. Unassigned segments are outside `MaxBands`, so the label space is the segment count, which is linear in the number of roleset boundaries, not capped at 16. The series also carry no roleset, so a counter cannot be joined to the pods that received the band.

Each gateway builds its own histogram. Roleset names make the short-band assignment agree across gateways, but the cut itself follows that gateway's traffic. Two gateways that see different mixes will band the same length to different rolesets. Engine batches then mix those lengths. The PR describes a per-gateway picture; the docs do not say that homogeneity stops at the gateway boundary.

`models` has no eviction. A model that appears once keeps two 168-bin vectors for the life of the process. Model names here are deployment names, so this stays small. The single tracker mutex is the right lock, and holding it outside `selectMu` is the right order. Every enabled request still takes it three times (`Configure`, `Observe`, `Plan`) and rebuilds the groups key under the lock even when the plan is cached.

`pd_readme.md` says the plan never changes which rolesets may serve a prompt length, and that the off path is bit-for-bit today's behavior. The off path selects the same pods. The on path removes every other covering roleset whenever the band survives the fast paths. That is the feature. The sentence describes the fallback, not the steady state.

### Tests

The planner specs cover the behavior that is implemented: name-ordered split, mode moving the cut, the 5% share, the all-or-nothing cap, the `MaxInt` clamp, cache versus fleet-key invalidation, EWMA half-life, nil tracker, per-model `Configure`, and the env parser (`true` / `1` / `yes`, case-insensitive mode, unknown mode). The three routing specs match the three claims in the test plan: the band picks the roleset and emits `band=0` then `band=1` plus a split; a loaded `prefill-b` keeps the fast path and emits no band counter; the switch off emits nothing. I did not re-run `go test`.

Gaps that hide the balance bugs: no spec where replica counts differ; no spec that the exclusive tail is charged to the wider roleset; no routing spec for `throughput`, for bucketing off with the switch on, or for two profiles on one model; `pd_bucket_serve_prompt_tokens_total` is captured and never asserted. The off spec seeds the tracker before the call, so it shows the request path does not emit. It does not show that a tracker left enabled from a previous profile stays idle.

### API and compatibility

Additive and off by default. `routingConfig.bucketServe` and `bucketServeMode` are omitempty pointers, so an absent profile keeps the env value and an explicit `false` can turn a process-wide switch off. `PDOverrides` grows two fields; the zero mode string fails `ParseBucketMode` and the tracker mode remains. No CRD, header, status, or existing metric name changes. The new series are gateway metrics in the same `PodMetricScope` / `PodRawMetrics` shape as the other gateway counters, emitted with a nil pod, so they label `model`, `lora_adapter`, and `gateway_pod`. The engine fetcher skips them because they have no engine name mapping.

Profile mode is case-sensitive (`knownBucketMode` requires the canonical lowercase name, same pattern as VTC) and the env var is not (`ParseBucketMode` folds case). `Throughput` in a profile warns once and keeps the env mode. The env default and the profile default are the same word, `throughput`, so this only bites a profile that changes the mode.

`ValidBucketModes` is exported and unused. `BucketPlan.Bands` aliases the tracker's slice. Callers only read it today. The comment is the contract.
