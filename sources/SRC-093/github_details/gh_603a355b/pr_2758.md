## 正文

## Pull Request Description

Adds the opt-in `AIBRIX_DISABLE_RATE_LIMITING` gateway setting. The default remains `false`, preserving the existing behavior.

When `AIBRIX_DISABLE_RATE_LIMITING=true`:

- Redis remains connected for session affinity, asynchronous job storage, state synchronization, and other gateway features.
- The gateway installs the existing `NoopRateLimiter`.
- AIBrix user lookup and user quota checks are skipped.
- An unknown `user` header no longer causes an HTTP 500 response.
- `RoutingContext.User` remains empty, so the unauthenticated header is not used as routing identity.
- The incoming `user` header and the OpenAI request-body `user` field are forwarded unchanged.
- User and model quota counters are not updated.
- The per-replica `requestsInflight` guard remains active.

### Asynchronous video jobs

Because disabled mode leaves the routing user identity empty, asynchronous video jobs use the shared ownership scope. The unauthenticated `user` header is not an isolation boundary and does not separate one caller's video jobs from another caller's jobs in this mode.

### Validation

- `go test ./pkg/plugins/gateway -count=1`
- `go vet ./cmd/plugins ./pkg/plugins/gateway`
- `bin/golangci-lint-v2.13.1 run ./pkg/plugins/gateway`
- `git diff --check`

The gateway lint scope passes with no `gocyclo` findings.

Resolves #2747

## Review: this can be much smaller

The goal is right: keep Redis connected for session affinity, async jobs, and state sync, while turning off AIBrix quota enforcement. The current patch is larger than that goal needs. `NoopRateLimiter` already exists, and Redis is already used for more than rate limiting. The missing piece is only that a non-nil Redis client currently implies “install Redis quota limiters and look up users.”

### What already exists

When Redis is absent, the gateway already disables quotas:

```go
if redisClient != nil {
    r = ratelimiter.NewRedisAccountRateLimiter("aibrix", redisClient, 1*time.Minute)
    mr = ratelimiter.NewRedisAccountRateLimiter("aibrix_model", redisClient, 1*time.Second)
} else {
    r = ratelimiter.NewNoopRateLimiter()
    mr = ratelimiter.NewNoopRateLimiter()
}
```

`NoopRateLimiter.Incr` always returns `0`, so RPM / TPM / model RPS never 429 and do not write quota keys.

User lookup is a separate Redis-client check in `HandleRequestHeaders`, not a limiter check:

```go
if username != "" && s.redisClient != nil {
    user, err = utils.GetUser(...)
    rpm, errRes, err = s.checkLimits(...)
}
```

That is the real coupling. With Redis kept for routing state, an unknown `user` header still hits `GetUser` and 500s even if the limiter is a no-op.

### Minimal change

Three production edits are enough:

1. Read `AIBRIX_DISABLE_RATE_LIMITING` into `ServerOptions` (default `false`).
2. Keep the Redis client, but install `NoopRateLimiter` when the flag is true:

```go
if redisClient != nil && !options.DisableRateLimiting {
    r = ratelimiter.NewRedisAccountRateLimiter("aibrix", redisClient, 1*time.Minute)
    mr = ratelimiter.NewRedisAccountRateLimiter("aibrix_model", redisClient, 1*time.Second)
} else {
    r = ratelimiter.NewNoopRateLimiter()
    mr = ratelimiter.NewNoopRateLimiter()
}
```

3. Skip user lookup / `checkLimits` with the same flag:

```go
if !s.disableRateLimiting && username != "" && s.redisClient != nil {
    user, err = utils.GetUser(...)
    rpm, errRes, err = s.checkLimits(...)
}
```

That already covers the issue:

| Wanted behavior | Why the small change is enough |
|---|---|
| Unknown `user` header does not 500 | `GetUser` is skipped |
| No RPM / TPM / RPS counters | noop limiter + no `checkLimits` |
| No rate-limit response headers | `user.Name` stays empty, so response-body TPM accounting does not run |
| No `stream_options.include_usage` requirement | that check is `user.Tpm > 0`; skipped lookup leaves TPM at 0 |
| Header does not feed user-aware routers | `NewRoutingContext(..., user.Name)` gets `""` if you also stop assigning `user.Name` when disabled |
| `requestsInflight` still works | it is independent of the limiter |
| Redis still used for session affinity / jobs / sync | `redisClient` is unchanged |

Do **not** put the incoming `user` header into `RoutingContext.User` when the flag is on, if the contract is that the header must not affect routing. You do not need a new identity field for that.

### Please drop from this PR

These layers re-implement “disabled” on top of the noop limiter and are not needed:

- `enforceModelRPSForPolicy` / `rollbackModelRPSForPolicy`
- `applyConfigProfile(..., rateLimitingEnabled)` zeroing `RequestsPerSecond`
- `requestValidationUser()` blanking the user again
- extra skip in response-body TPM accounting
- `AsyncJobOwner` on `RoutingContext`

That last item is a separate product decision. #2747 asks that the header not affect routing or admission. Video-job isolation via an unauthenticated `user` header is extra API surface, and it is what produced the empty-username ownership bug. If job isolation still matters, it should be a follow-up; this PR’s docs already say a trusted proxy must overwrite that header.

### Flag polarity

Please store `disableRateLimiting bool` on `Server`, matching `ServerOptions.DisableRateLimiting`.

`rateLimitingEnabled bool` has a Go zero value of `false`, so every existing `&Server{...}` test started behaving as “rate limiting off.” A large part of this diff is mechanical `rateLimitingEnabled: true` in unrelated tests. With `disableRateLimiting`, those tests keep current behavior without edits.

### Suggested test set

The new unit/integration coverage is much broader than the contract. A smaller set is enough:

- Redis present + flag on: gateway still starts and routes
- unknown `user` header does not look up a user record or 500
- a profile with `requestsPerSecond` does not 429 and creates no quota keys
- `requestsInflight` still 429s
- default / unset flag preserves current Redis quota behavior

Docs for the env var, default, and “Redis remains required for other features” are still worth keeping.

### Suggested shape for the author

Keep:

- `AIBRIX_DISABLE_RATE_LIMITING` (default `false`)
- constructor limiter choice
- skip `GetUser` / `checkLimits` (and do not assign `RoutingContext.User`) when disabled
- env-var / production docs

Remove the rest of the plumbing and the unrelated test churn. The feature should be a small constructor + header-path change, not a flag threaded through profile application, RPS helpers, response accounting, and routing context.
