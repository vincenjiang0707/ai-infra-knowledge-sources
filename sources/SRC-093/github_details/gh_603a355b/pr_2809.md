## 正文

## Pull Request Description

The gateway learns about ModelClaims only from the routing annotations the controller writes on warm pods. A claim that is not placed has no pod yet. So a request for its model was answered with 400, "model ... does not exist". That is the answer for a model that nobody serves (#526). Once the claim is placed, the same request gets 503 with `Retry-After` while the engine starts.

This PR closes that gap:

- **The cache knows ModelClaim objects.** In the gateway, the Kubernetes discovery provider also watches ModelClaims. The cache keeps one record per claim: the name it serves, its phase, and the controller's reason. The reason comes from its `Scheduled` condition while it waits, or from its `Ready` condition once it has failed. A claim being deleted is forgotten, since its model is going away.
- **The gateway answers 503 for a claimed model with no pod.** The message reads like `model qwen is pending (NoMatchingPods); retry shortly`, with `Retry-After: 10`. A claim that waiting does not help gets no `Retry-After`. That is one that has to be changed first, such as one with `InvalidEngineConfig`, or one whose engine failed for good (`EngineFailed`). Other refusals get it, a failed activation included, since the controller tries it again. A model that no claim serves still gets 400.
- **Only the reason reaches the client.** The condition's full message names pods and card figures, which a client does not need.
- **RBAC.** The gateway's role can get, list and watch ModelClaims, in `config/rbac/gateway/role_gateway.yaml` and the Helm chart. The gateway lists claims once when it starts. On Forbidden or NotFound, it says so once in its log and does not watch them. Such a model is then answered with 400, as before. The ModelClaim informer is also left out of the startup sync.

There is no API change. The docs are in the "Sleeping request behavior" section of the ModelClaim guide.

Tests:

- Unit tests: the cache records, follows and forgets claims, with conditions as the controller writes them (`pkg/cache/modelclaim_test.go`). The gateway answers pending, failed and unknown models, and still wakes a sleeping claim it also knows as an object (`gateway_req_body_test.go`). The one-time list check skips claims on Forbidden or NotFound (`pkg/cache/discovery/kubernetes_test.go`). Each test was run failing before the change.
- `make test-integration-gateway` (36/36) and `make test-integration-controller` (90/90).
- A new e2e case, `TestModelClaimNotPlacedYetIsRetryable`. A claim that selects no pod is answered with 503 and `Retry-After: 10`, until it is deleted. Then it is answered with 400.

This PR does not depend on #2647.

## Design simplification

The behavior to keep is small. If no pod advertises the model and a ModelClaim serves that name, answer 503, include the controller's reason, and set `Retry-After` unless the failure is terminal.

### Cut

**The second index.** `claims` is `served name → namespace/name → record`, and `served` is the reverse map so a rename or delete can find the previous name. That shape is the pod-binding map, which exists because many pods can advertise one model. A ModelClaim is one object. Store `map[namespace/name]record` and put the served name on the record. Lookup walks the map. Delete is one key. A rename overwrites that key. The lexicographic winner falls out of the walk. `clearClaimLocked` and the nil-map init in `setClaim` go away, and the two maps cannot drift.

**`unplacedModelClaimState`.** It exists so `Failed` becomes `failed` and the retry check can reuse the routing-state constant. Compare the phase enum (and the reason, per the code review) when choosing the header. Format the sentence at the call site. The routing states stay on the annotation path.

**Scheduled-then-Ready as a fixed scan.** Replace it with the phase rule above. That is a shorter read and it matches the conditions the controller updates. A controller follow-up that sets `Scheduled=True` once a pod is selected would make the condition true again; this PR still has to read the objects the current controller writes.

### Keep

- `ModelClaimStatus` as its own lookup, after `ModelClaimBinding`. The binding returns a pod because a sleeping model has to wake that pod. Putting status into the binding return would make a nil pod mean "claimed, no advertisement" and would mix the object and the annotation in one entry.
- The optional `ModelClaimStatusProvider` interface. A cache that does not implement it still returns 400, which is the old-role behavior. `MockCache` grows one map, same as the binding mock.
- Recording phase and reason on the informer event, and forgetting the object when `DeletionTimestamp` is set. Keeping the whole `ModelClaim` would hold spec the request path does not read.
- Skipping `WaitForCacheSync` for this informer. Classifying Forbidden versus a slow list is more code for the same fallback. Log once when `Watch` returns and the claim informer has not synced, so the 400 window is visible in the gateway log.
- get/list/watch in both RBAC files, the cache and gateway unit tests, and the single e2e. The doc sentences can stay short. They sit under "Sleeping request behavior"; this answer comes from the ModelClaim object and does not wake anything. Say that next to the status-code rules.

## Code review

The unplaced path matches the case the e2e covers. No pod matches the selector, the phase stays `Pending`, `Scheduled` is False with `NoMatchingPods`, and the client gets 503, `Retry-After: 10`, and a body that names the phase and a reason. A model with no claim stays 400. A claim with a deletion timestamp is dropped, so the next request is 400 again. The served name matches the controller: `spec.modelName` when set, otherwise the object name. The body gets `condition.Reason` only, so the condition message (the select error, which names pods) stays off the client. Both `config/rbac/gateway/role_gateway.yaml` and `dist/chart/templates/gateway-plugin/rbac.yaml` gain get, list, and watch on `modelclaims`. That is what the typed informer needs. Leaving that informer out of `WaitForCacheSync` lets a gateway whose role cannot list claims still start.

### A stale Scheduled reason hides the later failure

`modelClaimReason` returns the reason on the first False condition in the order `Scheduled`, then `Ready`.

The controller sets `Scheduled=False` / `NoMatchingPods` in `ensureActivated` and nowhere else (`pkg/controller/modelclaim/modelclaim_controller.go`). It never sets that condition to True. The integration case that recovers once a warm pod appears does not read `Scheduled` again after the phase leaves `Pending`. After the first time placement misses, `Scheduled` stays False for the life of the object.

`Ready` is updated later, and this read never reaches it:

- `ActivateFailed` is set when `Runtime.Activate` returns an error, before `annotateWarmPod`. There is no routing annotation, `HasModel` is false, and the new status path is the one that runs. Phase is `Failed`, `Ready` is False / `ActivateFailed`, and `Scheduled` is still False / `NoMatchingPods` if placement missed on an earlier pass. The body says `failed (NoMatchingPods)`.
- `InvalidEngineConfig` is the same mask on a claim that was already pending. The controller returns without requeue. The client is told the wrong reason.

`TestModelClaimStatusFollowsUpdatesAndDeletion` builds `Scheduled=True` and `Ready=False` / `ActivateFailed`. The controller does not write `Scheduled=True`, so that test exercises the helper against a status shape reconcile does not produce.

Read by phase, against the conditions as they are written today:

- `Pending`: use `Scheduled` when it is False. On the steady unplaced claim, `Ready` is absent and this stays `NoMatchingPods`.
- `Failed`: use `Ready` when it is False, so `ActivateFailed`, `InvalidEngineConfig`, and `EngineFailed` win over a leftover `NoMatchingPods`.
- Any other phase on this path: use `Ready` when it is False, and leave the reason empty when `Ready` is True. A leftover `NoMatchingPods` on an Active claim would otherwise be appended to `model qwen is active`.

Add a cache test that stacks the conditions reconcile actually leaves behind: `Scheduled` still False / `NoMatchingPods`, then `Ready` False / `ActivateFailed`, phase `Failed`.

### Failed phase suppresses retry while ActivateFailed is still requeued

`unplacedModelClaimState` lowercases the API phase, and `modelClaimRetryResponse` omits `Retry-After` when that string equals `constants.ModelClaimRoutingStateFailed` (`"failed"`). The match depends on `ModelClaimFailed` (`"Failed"`) and the routing-state constant spelling the same word.

`ActivateFailed` sets phase `Failed` and returns `RequeueAfter: DefaultRequeueDuration` (10s). A client that honors `Retry-After` stops while the controller is still retrying the activate call. `InvalidEngineConfig` is terminal (no requeue). `EngineFailed` matches a placed binding, which already omits `Retry-After`. `ActivateFailed` has no annotation yet; this path is the first time that error is what the client sees.

Choose the header from the reason. Omit `Retry-After` for `InvalidEngineConfig` and `EngineFailed`. Keep it for `ActivateFailed` and for every non-failed phase. Compare `claim.Status.Phase` to the phase constant when the sentence is built, and keep the lowercased phase in the text.

### Other risks

Startup still answers 400 until the claim list completes. Handlers are registered and the factory is started, and the claim informer is excluded from `WaitForCacheSync`. With permission, the reflector fills the cache in the background. A request after the gateway is ready and before that list finishes still takes the old 400 path. The e2e poll (60s) covers the window. A list error (the previous role, or the CRD absent) stays on 400, which is the compatibility behavior in the PR description. The doc should say the same 400 window exists on a healthy start, until the first list finishes.

A claim whose phase is `Sleeping` but whose pod annotation is not in the cache yet is answered 503 and is not woken. `RequestWake` runs only on the binding branch. The next request after the annotation lands does wake it.

Two claims with the same served name: the smallest `namespace/name` answers, including a `Failed` claim in front of a `Pending` one. Bindings already pick that way, and replicas are capped at 1. The body reason can be the other object's. One sentence in the doc is enough.

### Tests

These cover the behavior they construct, and they are the right set to keep:

- Cache: record a claim no pod advertises, fall back to the object name, follow a rename, delete, drop a claim with a deletion timestamp, and pick between two claims for one name.
- Gateway: pending with `Retry-After: 10` and the reason in the body, failed with no `Retry-After`, unknown model still 400 / `model qwen does not exist`.
- E2E `TestModelClaimNotPlacedYetIsRetryable`: a selector that matches nothing, body contains `is pending (`, `Retry-After: 10`, and after delete the model is 400. Leaving the exact reason to the controller is right.

Add the two cases the bugs above need: the condition history reconcile writes, and `ActivateFailed` still carrying `Retry-After` while `InvalidEngineConfig` does not. Add one gateway case where a sleeping binding and a claim record both exist for the name, and assert `RequestWake` still runs. Swapping the two type assertions would skip the wake, and nothing covers that order.

### API and compatibility

No CRD field, annotation, or routing-annotation change. The client-visible change is the gateway error when a ModelClaim serves the model and no pod advertises it:

| Before | After |
| --- | --- |
| 400, code `model_not_found`, body `model <name> does not exist` | 503, code `service_unavailable`, body `model <name> is <phase> (<reason>); retry shortly` |
| no `Retry-After` | `Retry-After: 10`, omitted when the lowercased phase is `failed` |

A model with no claim is unchanged. A placed claim, including port 0, still uses the binding path and the wake path. `X-Error-No-Model-Backends` stays the model name, as on that path.

A cluster that does not roll the gateway ClusterRole keeps today's 400 for an unplaced claim. `modelclaims/status` is unnecessary; list and watch already return `.status`.

### Zeyu-ZEYU · 2026-09-24

Thanks for both reviews. Most points were fixed in the commits pushed after them.

- **Stale `Scheduled` reason.** Fixed in c1ea36ca. The reason comes from the condition the phase is about: `Scheduled` while the claim waits, and `Ready` otherwise. The cache test now writes the conditions the way the controller leaves them.
- **Retry-After by phase.** Fixed in 1fcae085. It is left out only for the reasons the controller does not get past by itself. `ActivateFailed` keeps it. `EngineFailed` now joins that set too (a0aa1b10).
- **Wake order.** A new test holds it (a5ff477e). With a sleeping binding and a claim record for one name, the engine is woken, and the Pod's answer is used.
- **Docs.** They now say three things (a5ff477e). This answer wakes nothing. For a name two claims serve, the first by namespace and name answers. A gateway that has just started answers 400 until its first list finishes.
- **Second index.** Removed in 459d6577. The cache keeps one record per claim, keyed by namespace/name, with the served name on the record. A lookup walks the records. It runs only for a model that no pod advertises.

Kept as is:

- **The list check at start** (89455805). Without it, a gateway on the old role logs a failed list every 30 to 60 seconds, for as long as it runs. With it, the gateway logs once and does not start the informer. The answer is the same 400 either way.
- **`unplacedModelClaimState`.** It now only words the phase for the message. The retry choice no longer depends on it.
- **A sleeping claim whose Pod annotation is not in the cache yet** gets 503 and no wake. The next request after the annotation lands wakes it.
