## Pull Request Description

The concurrent capacity test added in #2719 could count a retry from one caller as a second caller: its 1s client timeout expired while the health handler waited at a 5s barrier. A health-check failure could then satisfy the different-model fallback assertion without exercising the locked capacity recheck.

- Use the default 30s client timeout, cancellable handler waits, and bounded waits for both callers. Require zero tokenizer-creation failures so a health-check timeout cannot masquerade as a capacity rejection. Caller completion and the failure counter establish client-side health-check success without a separate response-write signal. Release handlers and join callers before closing the pool.
- Look up the model entry once in the commit section and unlock before logging. Preserve the existing capacity checks and closing of discarded or replaced clients.

The two sequential regression tests and the TTL policy are retained. An entry that expires during a health check does not reserve its old slot; refreshing `lastUsed` for failing attempts would change eviction behavior. No API or configuration changes.

## Design simplification

The production edit is already the small form. One map read, then unlock before either log. Leave that structure in place.

### Cut

**The `completed` channel and the third select in the handler.** Wait for both `finished` channels, require zero creation failures, and keep the length, identity, and `ConnState` assertions. Those require two successful health checks and one closed idle connection. `completed` counts responses, the same kind of signal as `entered`, and its select can discard a write the client accepted.

Leave the two context selects on `entered` and `release`. They let a cancelled request return so `server.Close` can finish.

### Keep

- The single lookup and the three explicit unlocks. A wrapper that unlocks once would also pull `Close` out of the critical section. This path closes one client through `CloseIdleConnections`. Keep that close next to the decision, under the lock, as the healthy-winner path already does.
- The early cap check for a model that is absent from the map. It skips building a client when the pool is already full. The locked recheck stays.
- `Timeout` left unset, the zero-failure assertion, and the cleanup that releases the handler and joins both callers before `pool.Close`.
- Indexed `results` and the `finished` channels. The body observes completion before it reads `results`. The defer joins again when the body fatals first. A shared helper would only wrap those two waits.
- Both sequential tests, the non-blocking `ConnState` send, and the current TTL rule. Leave `lastUsed` as it is on a slow-path attempt that may fail.

## Code review

The commit section is correct, and the concurrent test now fails closed when a health check fails.

### Lock and lookup

`createOrUpdateTokenizer` reads `p.tokenizers[model]` once after it re-acquires `p.mu` (`tokenizer_pool.go` line 329). The map cannot change while that lock is held, so this read is the same pointer and the same `exists` bit as the old second lookup. The three outcomes are unchanged:

- Present and healthy (lines 330–338): refresh `lastUsed`, close the client just created, unlock, return the pooled tokenizer.
- Absent and `len(p.tokenizers) >= MaxTokenizersPerPool` (lines 342–348): close the new client, unlock, log the existing warning, return `DefaultTokenizer`. This path leaves `tokenizerCreationFailures` unchanged.
- Otherwise (lines 350–372): an entry that is present is unhealthy, because the healthy case already returned. Close that client, store the new one, update the gauge and the success counter, unlock, then log at V(3).

Every path unlocks. The warning at line 347 and the info log at line 370 run after `Unlock`. The early full-pool return at lines 274–277 already logged after unlock. Callers still receive the same tokenizer. The capacity rule and the replace-at-capacity exemption are the same.

`Close` on the discarded or replaced client still runs before unlock. That `Close` is `CloseIdleConnections` and does not take `p.mu`. A panic inside `Close` would leave `p.mu` locked, because this block no longer uses `defer`. The rest of `createOrUpdateTokenizer` already unlocks explicitly, and this `Close` does not take the pool lock. That residual is small.

`lastUsed` is updated for a healthy hit and for a stored entry. A model that expires during `IsHealthy` does not keep its slot, and a failing attempt does not pin an unhealthy entry for the TTL.

### Test

`Timeout` is left unset. `validateRemoteConfig` turns `Timeout <= 0` into 30 seconds. `createOrUpdateTokenizer` still sets `MaxRetries: 3`, and `IsHealthy` still uses a 5 second context. `Post` returns on `ctx.Done()` before another attempt, so the old 1 second client timeout can no longer expire while the handler is parked and count a retry as the second caller.

The handler selects on `r.Context()` around the `entered` send and the `release` wait (`tokenizer_pool_capacity_test.go` lines 45–54). A cancelled request leaves the handler, so `server.Close` is not left waiting on `<-release` after the client has gone.

`require.Zero` on `pool.metrics.tokenizerCreationFailures` (line 135) is the check that separates a capacity loss from a health-check failure. A failed `IsHealthy`, a `NewRemoteTokenizer` error, and a missing endpoint all increment that counter. The locked reject does not. With failures at 0, pool length 1, and exactly one `DefaultTokenizer`, both health checks succeeded and the locked recheck chose the winner. The same-model subtest still requires both results to be the pooled tokenizer.

`entered` still counts HTTP requests. A transport error inside the 5 second context can still retry. On an `httptest` server that is outside the steady path. A retry that fails the health check trips the counter. The timeout that used to satisfy the different-model fallback assertion no longer does.

Defers run in LIFO order. The cleanup defer closes `release` when the barrier is still shut, waits on `finished`, and only then `pool.Close` runs. `Close` closes `stopCh`, swaps the map, and closes the remaining client. Joining first keeps that off the commit section of `GetTokenizer`. The cleanup wait uses `t.Error`, so a stuck caller still reaches `pool.Close`. On the success path the body has already received from `finished`, and the defer receive returns immediately.

The closure at lines 104–107 captures `i` and `model`. The module is Go 1.22.5, so each loop iteration has its own variables. `results[i]` is written before `close(finished[i])`, and the test reads `results` after that receive.

`completed` (lines 56–59 and 119–126) can disagree with the caller. After `Write`, the handler selects between sending the error and `r.Context().Done()`. For a server request that context becomes ready when the client disconnects. When both arms are ready, the select can drop a successful write, and the test fatals after `GetTokenizer` has succeeded. The caller wait and the failure counter already require both health checks to succeed.

`TestTokenizerPoolReplaceUnhealthyAtCapacity` and `TestTokenizerPoolFailedHealthCheckReleasesClient` are unchanged.
