## Pull Request Description

The Redis write-through for session-key pinning still refreshed with an unconditional `SET`: a TTL refresh for an old address that landed after another replica had repinned the session silently wrote the old address back, reverting the newer pinning, and it also pushed out the TTL of whatever value was stored by the time it ran.

This gates the refresh on the stored value through a small Lua script that compares and writes in one atomic step:

```go
var sessionKeyRefreshScript = redis.NewScript(`
local current = redis.call('GET', KEYS[1])
if not current then
  redis.call('SET', KEYS[1], ARGV[1], 'PX', tonumber(ARGV[2]))
  return {2}
end
if current == ARGV[1] then
  redis.call('PEXPIRE', KEYS[1], tonumber(ARGV[2]))
  return {1}
end
return {0, current}
`)
```

The TTL is extended when the stored value still matches `addr`, the pin is re-attached with a fresh TTL when the key is missing (so an actively used session cannot lose its affinity right at the expiry boundary, and nothing can be overwritten), and nothing is written when the key holds a different address. On that mismatch the script returns the stored value with the outcome, so the refresh converges the local entry on the exact value that rejected it, without a second read that could miss a key expiring in between, even a confirmed entry, since the refresh just established that Redis no longer vouches for it, the same way a lost claim already converges; the stale replica therefore follows the newer pin instead of routing from the old address until the next sync pass. A Lua script rather than GET followed by SET/EXPIRE is used because the gate has to hold against concurrent writers; it goes through `redis.NewScript`, so refreshes on the hot path run by EVALSHA once the server has it cached, matching the pattern already used for the gateway's async-job scripts. A reply the script cannot emit is treated as a failure rather than a confirmation. Failover repins keep the unconditional write; their compare-and-swap is the remaining follow-up recorded in the TODO.

This is the refresh half of the write-semantics feedback from the #2742 review (discussion_r4037407790), split out after the claim half (#2765) merged. Say the word if you would rather see the remaining repin CAS folded in here instead.

Verified by reverting the fix locally: with the gated refresh replaced by the plain SET, the new regression spec fails with `10.0.0.1:8000` reappearing over the repinned `10.0.0.2:8000` and its TTL being extended; with the fix it passes. `go test -race ./pkg/plugins/gateway/algorithms/`, `go vet ./pkg/plugins/gateway/algorithms/`, and `go test ./pkg/plugins/gateway/... ./pkg/utils/...` all pass.

## Review

**Verdict: Approve.** This is the right fix for the second #2742 race (discussion_r4037407790), scoped cleanly on top of the #2765 claim work.

### What broke

TTL refresh still used an unconditional `SET`. A delayed refresh for the old address that landed after another replica had repinned the session wrote the old address back and also slid the newer pin’s TTL.

### What this PR does

The Lua script is the correct primitive: GET + compare + `PEXPIRE`/`SET PX` in one atomic step, via `redis.NewScript` so the hot path is EVALSHA. The three outcomes match the three states that matter:

- value == `addr` → slide TTL
- key missing → re-attach (only on a missing key, so it cannot overwrite)
- value != `addr` → write nothing, then converge the local cache

That last path is the actual bug. `reconcileStaleRefresh` correctly overwrites a *confirmed* local entry, unlike `reconcileLostClaim`, because the script just proved Redis no longer vouches for it. The CAS still bails if the local addr has already moved.

Leaving `writeRepin` as a plain `SET` is the right split. Folding CAS into this PR would mix two races; keep it as the recorded follow-up.

Re-attaching on a missing key is a deliberate expansion of the original “EXPIRE only if the value still matches” suggestion. It is justified: an active session should not lose cross-replica affinity at the expiry boundary, and Lua still serializes against a concurrent `SET NX` claim.

Gemini’s `NewScript` / `tonumber` / `.Run` notes are already addressed in 82d81318.

### Tests

The three new specs cover the important cases: delayed refresh must not revert or extend a newer pin and must adopt it locally; missing key re-attaches with a full TTL; matching value still slides. Revert-checking the regression spec is the right way to lock this in. Existing #2765 claim specs still pin the other write mode.

### Nits (non-blocking)

- **Return the mismatched value from the script** (inline below): the follow-up GET can see a different key than the one that rejected the refresh.
- `TestSessionAffinityResolveReportsPersistIntent` still says a confirmed local hit is “the one case where a plain TTL refresh is safe” — leftover from #2765; it is now the gated Lua path.
- Optional: treat a Lua outcome other than 0/1/2 as an error instead of confirming.

No API/compatibility surface changes. I would not fold the repin CAS in here.
