## Pull Request Description

The gateway's SLO queue (`routingAlgorithm=slo`) is invisible on the metrics surface: nothing reports how long a request waits for a slot, how deep the queue runs, how requests leave it, or whether the queue is serving FIFO because no profile was usable. This adds four metrics around the queue, emitted from the request path itself:

| Metric | Type | Extra label | Meaning |
|---|---|---|---|
| `gateway_queue_wait_time_bucket_total` | Counter | `bucket` | Time from enqueue to leaving the queue |
| `gateway_queue_pending_requests` | Gauge | - | Current queue depth for the model |
| `gateway_queue_outcome_total` | Counter | `outcome` | How the request left: `routed`, `slo_failure`, `capacity_reached`, `error` |
| `gateway_queue_fifo_fallback_total` | Counter | `reason` | Dispatches served by the FIFO fallback: `no_profile`, `no_slo_info` |

Wait time is stamped on the routing context when the request is enqueued (`RoutingContext.QueueStartTime`), so the bucket measures residency in the queue rather than time since arrival; a context that was never stamped falls back to `RequestTime`. The bucket bounds (10ms to 60s) are coarser than the request-path duration buckets because a request can wait tens of seconds for capacity, and they follow the existing label convention (`low-highms`, `Nms+`) instead of introducing a histogram.

`outcome` is classified with `errors.Is`, so wrapped errors still land in the right bucket: `ErrorSLOFailureRequest` -> `slo_failure`, `ErrorLoadCapacityReached` -> `capacity_reached`, anything else -> `error`. The FIFO fallback is recorded where the decision is made: `SLOQueue.Peek` marks the fallback candidate with its reason and `Dequeue` counts it once.

All four are emitted with the same low-cardinality label set as the other gateway request metrics (`model`, `lora_adapter`, `gateway_pod`) and never with pod labels, keeping the cardinality direction discussed in #2569; the pod that serves the request is already covered by the per-pod request metrics. Pending depth is set (`Set(Len())`) after enqueue and after dequeue rather than incremented and decremented, so an error between the two cannot drift the gauge.

Tests: `TestQueueWaitBucketLabel` pins the bucket bounds, `TestQueueOutcomeLabel` pins the four outcomes (including a wrapped error), `TestQueueMetricsRegistered` guards against a metric being dropped silently because it is missing from the registry, and `TestQueueRouterEmitsQueueMetricsByOutcome` drives a `queueRouter` end to end with a fake queue and backend for the four outcomes, checking the emitted labels and the pending sequence `1 -> 0`. The SLOQueue fallback reasons are covered by two ginkgo specs plus a ranked-candidate control case.

`gofmt` and `go vet` are clean; `go test ./pkg/plugins/gateway/... ./pkg/types/... ./pkg/metrics/...` and `go test -race` on the two touched packages pass.

### cursor[bot] · 2026-09-22

The four metrics and the low-cardinality labels are the right surface for the SLO queue. Stamping `QueueStartTime` before `Enqueue`, `errors.Is` on outcomes, `Set(Len())` instead of inc/dec, and counting FIFO fallback on `Dequeue` (not every `Peek`) are all the right call sites. Gemini’s race and nil-subqueue notes are already addressed in 20cbce61.

The `len(dequeueCandidates) == 1` FIFO heuristic is also correct, not a coincidence: fallback always occupies `[0]`, and a successfully ranked candidate from a single subqueue is `len == 2` after the append. The new ginkgo cases pin both reasons plus the ranked control.

Two things I’d still change, neither blocking the direction:

1. `emitQueueOutcomeMetrics` runs before `Dequeue`. If dequeue fails (including the new `subqueue not found` path), the request is still queued, Peek state is consumed, and the next serve loop can Peek it again and increment wait/outcome a second time. Emit after `dequeued == ctx`.
2. `gateway_queue_pending_requests` is `Set(Len())` from both the request goroutine (after enqueue) and `serve` (after dequeue). Concurrent snapshots can last-writer-wins a stale depth (0 with 1 pending, or 1 with 2). The sequential `1 → 0` test does not catch this. Own the gauge on one goroutine, or document it as eventually-consistent.

Nits: wait time is enqueue → post-`Route`, so it includes the dispatch attempt (Peek ranking + backend `Route`), not only idle queue time — fine if the description says so. `capacity_reached` is the backend `Route` error after a candidate was chosen; Peek’s “all pods at capacity, return nil and keep waiting” path correctly emits nothing. `msBucketLabel` is duplicated from `gateway_rsp_body.go`.

Tests cover buckets, wrapped SLO errors, registry presence, and both fallback reasons. Happy to take this after the outcome-vs-dequeue ordering is flipped.
