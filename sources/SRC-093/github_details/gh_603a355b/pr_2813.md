## Pull Request Description

Prefix-cache routing treated requests with different prompt instructions as the same prefix when they used the Anthropic Messages or OpenAI Responses APIs. A changed `system`, `instructions`, or `tools` field could therefore reuse a prefix built for another request.

The parser now includes those fields in `PrefixMatchText` while leaving the existing message text used for token accounting unchanged. Chat completions keep their current tool-prefix behavior.

## Related Issues

Resolves: https://github.com/vllm-project/aibrix/issues/2799

## Testing Done

### cursor[bot] · 2026-09-25

## Code review

The bug in #2799 is real, and this change does close the full-match hole for the cases the new test covers. `Message` stays the messages or `input` text, so token accounting is unchanged. `/v1/chat/completions` still hashes tools the same way. The remaining problem is the text those new fields contribute: a JSON re-encoding, where the rendered prompt has the raw string.

### Correctness

`validateRequestBody` already returned `prefixText` for chat and left it empty for `/v1/responses`. The dispatcher now keeps the responses value (`util.go` 189). `gateway_req_body.go` already assigns that return value to `RoutingContext.PrefixMatchText`. `PrefixText()` uses it whenever it is non-empty and otherwise uses `Message` (`pkg/types/router_context.go` 237–243). Local prefix routing, the KV-sync router, and the prefill scorer all tokenize `PrefixText()`.

`prefixMatchText` now goes through `combinePrefixText`. With an empty tools string the result is still `""`. With tools set it is still `tools + " " + message`, including the trailing space when `message` is empty. Existing chat prefix tests lock that. `/v1/chat/completions` does not read the new `system` field (`util.go` 234). A system role inside `messages` is already inside `Message`.

For `/v1/messages`, a non-empty system is placed before tools and the messages (`util.go` 234–242). For `/v1/responses`, `instructions`, then tools, then `input` (`util.go` 279–283). Responses tools go through `canonicalToolsText`, so `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS=false` still drops them. System and instructions ignore that flag. A canonicalization failure logs at V(4) and uses the raw bytes (`prefix_tools.go` 81–88). The request still succeeds. Absent and JSON `null` stay empty (`prefix_tools.go` 76).

`canonicalRequestFieldText` then unmarshals the value and marshals it again (`prefix_tools.go` 80–90). A JSON string comes back with quotes. The new test locks that in: the messages prefix must be `"You are concise." [{"name":"weather","type":"function"}] hello` (`prefix_tools_test.go` 126), and the responses prefix must start with `"Be brief."` (line 136). `parseChatMessages` does the other thing for message content. A value that starts with `"` is decoded and written as text (`util.go` 127–132).

Chat templates insert `system` and `instructions` as that decoded text. They render tool definitions with `tojson`, which is why `canonicalToolsText` should stay canonical JSON. A quoted system does still separate `"You are concise."` from `"You are verbose."` on the gateway’s own index, so the reported 100% match is gone for string fields. It does not match the prompt the engine caches.

The KV-sync router tokenizes `PrefixText()` and matches those ids against engine block hashes (`pkg/plugins/gateway/algorithms/prefix_cache.go` 527 and 603). The rendered prompt starts with the system text, so the first block differs from a string that starts with `"`. With the default block size of 4, every later block misses too. The same requests previously hashed `Message` alone, which is the unquoted conversation. After this change, a messages request that carries a string `system`, and a responses request that carries `instructions`, score as a KV-sync miss even when the pod holds that prefix.

Issue #2799 also calls out a list of content blocks. `{"system":[{"type":"text","text":"You are concise."}]}` remarshals to a JSON document with sorted keys, `[{"text":"You are concise.","type":"text"}]`. The template inserts `You are concise.`. The same words sent as a string and as a text block do not share a prefix, and `cache_control` on a block changes the hash without changing the prompt. An empty array remarshals to `[]`, which is non-empty, so the prefix becomes `[] hello`. `canonicalToolsText` treats an empty array as absent (`prefix_tools.go` 112–113).

Field order is system or instructions, then tools, then the conversation. That matches templates that emit the system text and then the tool JSON. A template that emits tools first still shares every block of a long system when only the tools differ. That is a smaller hole than a 100% match, and it is a large false hit when the system is long.

The branch at `util.go` 237–241 is consistent with today’s `prefixMatchText`: an empty prefix means tools contributed nothing, and a non-empty prefix already ends with `message`. Prepending `systemText` is right only while that stays true.

### Risks

KV-sync prefix hits drop for `/v1/messages` with a string `system` and for `/v1/responses` with `instructions`, because the hashed text no longer starts with prompt text. The in-memory index is self-consistent for identical quoted strings, so two equal requests still match each other there. Different systems no longer look like a full match.

Rolling a gateway rebuilds the local index. Hashes added under the old messages-only and input-only text stop matching these requests. Engine KV events are unchanged.

`chatReqMinimal` is shared. Every chat completion now retains a `system` raw message it does not use (`util.go` 68). The cost is one extra raw field on the hot path. The `PathMessages` check is the only thing that keeps a top-level `system` off `/v1/chat/completions`.

### Tests

`TestRequestPrefixText_IncludesPromptFields` covers the regression that shipped: different `system` strings, different `instructions`, and different responses tools, with `Message` equal across the pairs that should keep it equal (`prefix_tools_test.go` 115–146). Because the two systems differ, `messageA == messageB` does show that the system text stayed out of `Message`. The exact string on line 126 locks order, the space separators, tool key sorting, and the JSON quotes.

These cases are still open:

- `system` as a list of text blocks, including a block whose only extra field is `cache_control`.
- `system` absent, `null`, `""`, and `[]` on `/v1/messages`, with and without tools. The prefix should stay the tools text, or `""` when tools are absent.
- `/v1/chat/completions` with a top-level `system`. The prefix should stay tools-only.
- `/v1/responses` with neither `instructions` nor `tools`, so `prefixText` stays `""` and `PrefixText()` falls back to `Message`.
- `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS=false`. System and instructions stay. Tools drop on both `/v1/messages` and `/v1/responses`.
- A content-block `system` whose object key order differs, and a string that contains `<`.

The author’s `go test ./pkg/plugins/gateway/...` and race run are on the PR. I reviewed the diff and the caller on main. I did not re-run those tests.

### API and compatibility

No HTTP field, status code, header, CRD, env var, or CLI flag changes. `validateResponsesRequest` gains an unexported `prefixText` result. Its only caller is the dispatcher.

`Message` is still the text used for size estimates. Chat-completions prefix bytes are unchanged when tools are the only extra field. `/v1/messages` requests that include `system`, and `/v1/responses` requests that include `instructions` or `tools`, now set `PrefixMatchText`. Policies that hash `PrefixText()` see the new string. The comment on `RoutingContext.PrefixMatchText` (`pkg/types/router_context.go` 127–132) still says the gateway sets it for tool definitions. That comment is the contract the routers read, and it should name `system` and `instructions`.

## Design simplification

One composer, and prompt text for prompt fields. Tools stay canonical JSON.

### Simpler structure

Render each leading field, then join once:

```go
prefixText = combinePrefixText(message, systemText, toolsText)
```

`combinePrefixText` already skips empty parts and returns `""` when none remain, so `PrefixText()` keeps falling back to `Message`. Both validators call that once.

- `/v1/chat/completions`: `systemText` is `""`. `toolsText` is `canonicalToolsText`.
- `/v1/messages`: `systemText` is the system prompt text. `toolsText` is `canonicalToolsText`.
- `/v1/responses`: `systemText` is the `instructions` text. `toolsText` is `canonicalToolsText`.

`canonicalToolsText` keeps the flag, the leading `[`, and the empty-array check. The unmarshal, remarshal, and raw-byte fallback live in one helper. Tools call it after those checks. `system` and `instructions` use a smaller helper: a JSON string returns the decoded text, and an array returns the `text` of each block joined in order with a space. `cache_control` is left out. An empty string and an empty array return `""`.

### Cut

- The `prefixText == ""` branch and the `systemText + " " + prefixText` prepend (`util.go` 237–241). The message is already appended inside `combinePrefixText`.
- `prefixMatchText`. Its only caller is `validateChatRequest`, and it only forwards tools.
- The second remarshal in `canonicalToolsText` (`prefix_tools.go` 106–119).
- The quoted-string expectation in `TestRequestPrefixText_IncludesPromptFields` (lines 126 and 136). The expected messages prefix becomes `You are concise. [{"name":"weather","type":"function"}] hello`.

### Keep

- `Message` as the messages or `input` text, used for size estimates.
- An empty `prefixText` when system, instructions, and tools contribute nothing.
- Canonical tool JSON, `AIBRIX_PREFIX_CACHE_INCLUDE_TOOLS`, and the same tools helper for chat, messages, and responses.
- The `PathMessages` gate, so a top-level `system` on `/v1/chat/completions` stays out of the prefix.
- The raw-byte fallback that still accepts the request.
- The regression property in the new test: different system, instructions, or tools, and an equal `Message` for the pairs that share one.

## Code Review

This pull request updates the gateway plugin to include additional prompt fields, such as 'system' instructions and 'tools', in the prefix-match text generation for chat and responses APIs. The feedback focuses on optimizing performance in these high-throughput paths. Specifically, it is recommended to use direct string concatenation instead of the helper function 'combinePrefixText' where applicable to avoid unnecessary slice allocations, and to implement a fast path in 'canonicalRequestFieldText' for simple JSON strings to bypass expensive JSON marshaling and unmarshaling operations.
