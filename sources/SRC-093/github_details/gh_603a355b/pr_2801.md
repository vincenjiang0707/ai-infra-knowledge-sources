## 正文

### Pull Request Description

The smoke build of the `metadata-service` image (`runtime` builds from the same Dockerfile) fails on `poetry install` with a signature that points at two different packages, one of which is not part of the command that failed:

```text
Package operations: 103 installs, 12 updates, 0 removals
  - Downgrading urllib3 (2.8.0 -> 2.6.3)
  Command '['/usr/local/bin/python3.11', '-m', 'pip', 'uninstall', 'urllib3', '-y']' returned non-zero exit status 2.
  FileNotFoundError: [Errno 2] No such file or directory: '/usr/local/lib/python3.11/site-packages/charset_normalizer-3.5.1.dist-info'
Cannot install urllib3.
```

Two things combine here.

The builder stage installs poetry with pip right before it runs `poetry install`, so poetry's own transitive dependencies are resolved to their latest releases (`urllib3 2.8.0`, `charset-normalizer 3.5.1`). Those are newer than the pins in `poetry.lock`, so the locked versions arrive as twelve `update` operations rather than as installs.

Poetry then runs the operations in a thread pool by default, and it keeps only `uninstall` operations out of that pool. An `update` operation uninstalls the installed distribution before it installs the locked one, so the twelve updates run `pip uninstall` against the same `site-packages` directory at the same time. A `pip uninstall` of one package reads the installed distributions it finds, so it can meet a `.dist-info` directory that another update removed in between, which is the `FileNotFoundError` above.

### Fix

The install now runs with `installer.parallel` disabled, which makes poetry execute the operations one at a time and removes the concurrency the failure needs:

```dockerfile
RUN poetry config virtualenvs.create false \
    && poetry config installer.parallel false \
    && poetry install --no-interaction --without profiling --without dev \
    && poetry build -f wheel
```

The set of packages and versions that ends up in the image is unchanged, because the same lock file drives the same operations; only the concurrency of the install and uninstall steps is. Upgrading poetry is not an option: the race is reported upstream as `python-poetry/poetry#8159`, it is still open, and the current poetry main branch does not fix it.

### Evidence

- The failing job is `Build smoke image (metadata-service)` of run `35953390757` (Installation Smoke, commit `2af26eb3`). The other jobs of that run, and the same build of the `runtime` image, passed, which fits a race rather than a broken lock file.
- In poetry 1.8.3, `poetry/installation/executor.py` computes `is_parallel_unsafe` from `operation.job_type == "uninstall"` plus a source-type check, so `update` operations stay in the parallel path, and the constructor of the executor in the same file sets `max_workers` to 1 when `installer.parallel` is false.
- `builder` stages of this Dockerfile are the only place in the repository that runs `poetry install` inside an image build (the other call sites are local setup steps in `python/aibrix/README.md`, `python/aibrix/AGENTS.md` and `python-aibrix-tests.yml`).

### Test Plan

- This pull request runs the Installation Smoke workflow, which builds both images that use this Dockerfile, so the changed line is covered by its own checks.
- The builder stage of this Dockerfile was built locally with the change: `poetry install` completed and `poetry build -f wheel` produced the wheel, after the same twelve `update` operations were printed.
- The failure is timing dependent, so a green run alone does not prove that it is gone. The evidence is that the twelve concurrent updates are now serial, and the race needs that concurrency: with `installer.parallel` disabled, poetry executes one operation at a time and no two `pip` processes touch `site-packages` at once.

### Related Issues

No tracking issue in this repository. The race is reported upstream as python-poetry/poetry#8159 and is still open there.

## Code review

### Correctness

The diagnosis matches the code that actually runs.

`POETRY_VERSION` is 1.8.3, installed with `pip install` into the slim image's system `site-packages` immediately before `poetry install --without profiling --without dev` with `virtualenvs.create false`. Pip resolves Poetry's own dependencies to whatever is current. The lock file pins `urllib3` 2.6.3 and `charset-normalizer` 3.4.6, so a fresh builder turns those newer installs into updates. The reported failure is that shape: `Downgrading urllib3 (2.8.0 -> 2.6.3)` and `FileNotFoundError` on `charset_normalizer-3.5.1.dist-info` during `pip uninstall urllib3`.

In Poetry 1.8.3 `executor.py`, `is_parallel_unsafe` is true only for `operation.job_type == "uninstall"` (and for editable directory/git installs). An update stays in the thread pool. `_install` for `job_type == "update"` calls `_remove`, and `_remove` is `python -m pip uninstall <name> -y`, which walks every distribution under `site-packages` while building pip's user agent. Two of those processes can delete a `.dist-info` directory the other is listing. That is the window in [python-poetry/poetry#8159](https://github.com/python-poetry/poetry/issues/8159). The same `is_parallel_unsafe` test and the same `_remove` call are still on Poetry `master`, so leaving the pin at 1.8.3 is consistent with the upstream state.

`installer.parallel false` is read in `Executor.__init__`: `parallel` becomes false and `_max_workers` is set to 1 before the `ThreadPoolExecutor` is created. One operation runs at a time, so two `pip uninstall` processes never share `site-packages`. The locked set is unchanged because the solver still reads `poetry.lock`. `poetry build -f wheel` does not install packages, so the flag does not change the wheel.

The flag is builder-only. The final stage copies `/app/dist/*.whl` and installs it with pip. `/root/.config/pypoetry/config.toml` stays in the discarded builder.

### Risks

The race needs those concurrent updates. A clean image only produces them because Poetry's dependencies share the target `site-packages`. Serializing the installer closes the window that failed the build. It leaves the shared `site-packages` in place, so the twelve downgrades still happen, one after another. That is the right scope for this failure.

Build time grows when this layer is rebuilt. About 103 installs and 12 updates that used to overlap now run one by one. Upstream discussion of the same flag measured a modest hit once wheels were cached, and a cold download is where it would show. The smoke times on this PR (metadata-service 6m16s, runtime 5m55s) are not a before/after: changing the RUN instruction misses the `installation-smoke-*` GHA cache. The failed job on run `35953390757` died about a minute in, while the runtime image from the same commit built in about four and a half minutes, which fits a race between two builds of one Dockerfile.

`.github/workflows/python-aibrix-tests.yml` still does `pip install -U pip poetry` and then `poetry install` with `virtualenvs.create false` and the default parallel installer. That is the same pattern, with an unpinned Poetry. It did not run on this PR (path filter is `python/aibrix/**`). Worth a follow-up, and it does not belong in this diff.

A later `poetry install` added to this stage inherits the global config, because `poetry config` writes the user config rather than a one-shot environment variable. In this Dockerfile the only later Poetry command is `poetry build`, which ignores the installer.

### Tests

No new test, which is appropriate. The behavior is a Docker build flag around a timing-dependent pip failure.

This PR's Installation Smoke (`35962516489`) built both consumers of `Dockerfile.python` (`runtime`, `metadata-service`) and then passed Helm and Kustomize. Installation E2E (`35962516406`) rebuilt the same Dockerfile and passed. A green run does not by itself prove the race is gone. The proof is `_max_workers = 1` in the 1.8.3 executor, which removes the second `pip` process the traceback needs.

### API and compatibility

No Kubernetes API, CRD, webhook, HTTP route, header, CLI flag, label, annotation, or runtime environment variable changes.

`POETRY_VERSION` stays 1.8.3. `poetry.lock` and `pyproject.toml` are untouched. The final image is still `pip install` of the wheel built from the same source, so the package set users pull from `aibrix/runtime` and `aibrix/metadata-service` is the same. Both images, plus the chart and release workflows that point at this Dockerfile, pick up the flag together because they share the file.

## Design simplification

Keep the one config line and a short comment. Cut everything else that this failure might suggest.

The builder already has the shape it needs: one `pip install poetry==${POETRY_VERSION}`, then one RUN that configures Poetry, installs from the lock file, and builds the wheel. The failure is concurrency inside that install. `poetry config installer.parallel false` is the switch Poetry already implements for it, and it matches the `poetry config virtualenvs.create false` on the line above. The three-line comment earns its place: without it, the flag reads as an unexplained slowdown. Pointing at poetry#8159 is enough for the next person who wants to delete it.

Leave these out of this PR:

- A retry around `poetry install`. That hides the race and still fails the unlucky run.
- Pins or a constraints file for Poetry's transitive dependencies. The lock file already pins the project. Chasing `urllib3` and `charset-normalizer` as they drift is a second lock.
- A Poetry upgrade. Current `master` still classifies updates as parallel-safe and still shells out to `pip uninstall` for them.
- Splitting the RUN, a second Dockerfile, or a change to the final-stage `pip install ./*.whl`. The wheel copy is the compatibility boundary, and pip installing one wheel is a single process.
- The same flag in `python-aibrix-tests.yml`, the README, or `AGENTS.md`. Those are separate call sites. Folding them in widens a four-line CI fix.

The only smaller form of this exact change is to put the flag on the install command instead of in Poetry's user config:

```dockerfile
RUN poetry config virtualenvs.create false \
    && POETRY_INSTALLER_PARALLEL=false poetry install --no-interaction --without profiling --without dev \
    && poetry build -f wheel
```

That drops the second `poetry config` process and keeps the setting on the one command that needs it. It is optional. The config line is easier to read next to `virtualenvs.create false`, and `poetry build` does not consult the installer. Either form is the whole fix. The config line that is already in the diff should land.
