## Pull Request Description

The PD router's per-pod load state lives on the single `pdRouter` instance and is shared across every model and namespace. It was keyed by the bare pod name, however, so same-named pods in two namespaces merged their accounting: each pod carried the other's token load and in-flight counts, and they shared one metric series. This PR keys that state by `namespace/name`.

- The three router-level trackers now key by `namespace/name`, the same format as `utils.GeneratePodKey` and the key the gateway cache already uses for per-pod state:
  - `TokenLoadTracker`
  - `PrefillRequestTracker`
  - `PendingDecodeTracker`

  The tracker APIs still take a string, now documented as the pod key. Releases look up by request ID, and the key recorded when a charge is taken is reused on release, so charges cannot be released under a different key form.
- A new `pd.PodKey(pod)` helper builds the key with plain concatenation, byte-identical to `utils.GeneratePodKey`, which a test asserts. It avoids adding `fmt.Sprintf` calls inside the `selectMu` critical section.
- The `pd_token_load_active_tokens` and `pd_token_load_kv_tokens` gauges gain a `namespace` label, following the separate namespace/pod labels of the other per-pod gateway metrics.
  - `pod_name` keeps the bare pod name, so existing queries and the e2e scrape keep working.
  - The janitor's idle-pod pruning deletes the series with the same label values it set.
- Tracker log lines use `pod=<namespace/name>` instead of `pod_name`.
- Left as is: `matchedPods` and the per-request score maps, including the map returned by `GetPrefillRequestCountsForPods`, stay keyed by pod name. The prefix match comes from the per-model prefix index shared with the `prefix_cache` router. A single model name served from two namespaces can still put two same-named pods into one candidate list. That problem predates this change and is out of scope here.

`BenchmarkFilterPrefillDecodePods`, 8 prefill + 8 decode pods, `-benchmem -count=6`:

| | least_request | prefix_cache |
|---|---|---|
| main | ~21.3–22.5 µs, 232 allocs | ~72.7–74.4 µs, 240 allocs |
| this PR | ~21.0–21.3 µs, 218 allocs | ~72.7–73.2 µs, 226 allocs |

Tests:
- same-named pods in two namespaces keep separate token-load counters, gauge series and pruning (`TestTokenLoadTracker_SameNameInTwoNamespaces`)
- token_load scores stay independent (`TestTokenLoadPrefillPolicy_SameNameInTwoNamespaces`)
- the prefill and decode request trackers keep separate counts (`TestRequestTrackers_SameNameInTwoNamespaces`)
- `PodKey` matches `GeneratePodKey`
- existing tests are updated to pod keys

Verification:
- `go test -race ./pkg/plugins/gateway/algorithms/... ./pkg/plugins/gateway/` passes
- `go vet ./test/e2e/...` passes
- golangci-lint reports no issues

## Design feedback: simplify the key space

This PR is already a focused, correct fix for #2783. The remaining complexity is mostly a half-migrated key space, not the bug itself.

### 1. One key format end-to-end

Trackers now use `namespace/name`, but `GetPrefillRequestCountsForPods` (and other per-request score / `matchedPods` maps) still key by bare `pod.Name`. The PR correctly calls out that two same-named pods in one candidate list can still collide.

Simplest shape: **every** PD per-pod map uses `PodKey` (or drop name-keyed maps and index by pod pointer / key consistently). Leaving a second key space means the next collision bug is already designed in.

If full migration is too big for this PR, say so and open a follow-up for score/`matchedPods` maps — don’t leave it as a permanent “out of scope” exception without a tracking issue.

### 2. Don’t fork `GeneratePodKey`

`pd.PodKey` exists only to avoid `fmt.Sprintf` under `selectMu`, with a test asserting byte-identity with `utils.GeneratePodKey`.

Prefer one implementation:
- change `utils.GeneratePodKey` to concatenation (or add `GeneratePodKeyFromPod(*v1.Pod)` there), and call that from PD; or
- keep `PodKey` in `pd` and have `utils.GeneratePodKey` delegate to the same helper.

Two functions that must stay identical is the unnecessary part.

### 3. Reuse `ParsePodKey` for metrics

`tokenLoadGaugeLabelValues` reimplements split-on-`/`. `utils.ParsePodKey` already exists. Use it so key format and metric labels share one parse path.

### 4. Optional: take `*v1.Pod` at tracker boundaries

APIs that still take a free-form `podKey string` invite call sites to pass `.Name` again. Prefer `AcquirePrefill(id, pod *v1.Pod, …)` / `AddPrefillRequest(id, pod *v1.Pod)` and key internally (releases can keep the stored key). That removes a class of mistakes more than it removes lines.

---

**Bottom line:** Keep the namespace/name ledger and the `namespace`+`pod_name` gauges. Simplify by collapsing to **one key helper in utils** and **one key format in all PD maps**, or explicitly stage the score-map half as a follow-up.

@googs1025 Thanks for the review. I went through the gateway for other per-pod state keyed by the bare pod name and opened #2800 with the full list. In short:

- **High:** the rate history in `pkg/cache` (`rateCalculator`) is process-wide and keyed by pod name only. For the 1-minute rates the key does not include the model either. Two same-named pods in different namespaces mix their counters. In a quick test, the per-second throughput rate came out about 2000 times too high. This feeds the PD decode drain-rate scoring and the load-balance router's capacity estimate.
- **Medium:**
  - the per-model throughput rates, which share the same history
  - the history purge on pod delete, which matches on the name only
  - the prefix hash index used by `prefix-cache` and the PD router, which stores bare pod names per model
- **Low:** the per-request score maps and `FilterPodByName` lookups. These only collide when one model is served from two namespaces with the same pod names.
