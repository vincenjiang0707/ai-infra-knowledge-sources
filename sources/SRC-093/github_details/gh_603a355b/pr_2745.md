## 正文

fix [2744](https://github.com/vllm-project/aibrix/issues/2744)
Add an optional requiredHBMBytesPerGPU spec field that sets the minimum free GPU memory a candidate warm pod must report before the model is activated on it. Pods without a memory observation or with less free HBM than requested are skipped; when no candidate qualifies the claim stays Pending and reports NoMatchingPods with the unmet requirement.

- api: add the field, deepcopy, CRD schema, and apply configuration
- placement: filter candidates by confirmed free HBM when the limit is set
- docs: document the new spec field

## Review

The HBM filter matches #2744 and the existing snapshot summary (max slot for TP=1, min-free rank for TP>1). `TestReconcilePlacementRequiresHBM` covers the original bug: a cached pod under the limit loses to a pod with confirmed capacity.

Please address the two operator-facing issues below before merge:

1. **Docs are now internally inconsistent.** The new spec field is a hard admission filter, but the Observability section still says HBM “is not a hard admission or reservation signal.” Troubleshooting also only covers zero candidates, not `Candidates > 0` + `NoMatchingPods` because of HBM.
2. **HBM error attribution is too broad.** If there are no eligible candidates at all, the claim still reports a missing-HBM error. Gemini called this out on `placement.go`; please only use that message when a pod was actually skipped for HBM, and add tests for empty / already-on candidates.

Nits (non-blocking): fill `Resolves: #2744` so the `triage/needs-information` label can drop; the repo title convention wants `[API][Docs]` rather than `feat(modelclaim):`. `resource.Quantity` (`40Gi`) would be easier for users than raw bytes, but that can be a follow-up while this is still v1alpha1.
