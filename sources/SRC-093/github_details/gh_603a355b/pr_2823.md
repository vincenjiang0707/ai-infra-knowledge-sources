## 正文

### Pull Request Description

This is the API step of the two-step plan discussed in #1418, split out of #2804 so the public surface can be agreed on its own before the behavior is reviewed.

The surface it adds:

- `spec.predictive.mode`: `Preview` (the default when omitted) or `Auto`.
- `spec.predictive.horizonSeconds`: 1 to 3600, default 120 when unset.
- `status.predictive` reports the latest evaluation with `mode`, `metric`, `observedValue`, `predictedValue`, `predictedReplicas`, `reactiveReplicas`, `wouldBeReplicas` and `lastUpdated`.
- The validating webhook rejects the block with `scalingStrategy: HPA`, where the native HorizontalPodAutoscaler owns the decision, and reports the mode and horizon range; the CRD schema enforces the enum and the bounds as well.
- Generated artifacts, the docs page and a sample.

`Preview` records the projection without touching the decision. `Auto` lets the projection raise the replica floor while reactive scaling keeps scale-down. `wouldBeReplicas` next to `reactiveReplicas` answers the question from #1418: whether `Auto` would change anything for this workload.

### Review Guide

The files worth reading are the type definitions in `api/autoscaling/v1alpha1/podautoscaler_types.go`, the validation in `pkg/webhook/podautoscaler_webhook.go` with its test, and the contract in `docs/source/features/autoscaling/predictive-autoscaling.rst`. The deepcopy, the two CRD copies and the apply configuration are generated.

Scope: this PR is API only. The projection, the floor composition and the status writes land in the follow-up that reshapes #2804, with the integration and E2E tests discussed there; until it lands the block validates and does not act yet.

## Code review

The spec shape is a compatible addition on `autoscaling.aibrix.ai/v1alpha1`. `spec.predictive` is an optional pointer, so objects that omit the block stay valid. `mode` is `Preview` or `Auto`. `horizonSeconds` is an optional `*int64` with CRD bounds 1 to 3600, the same bounds as `observeWindowSeconds` and `panicWindowSeconds`. `status.predictive` is an optional pointer. Deepcopy, both CRD copies (`config/crd` and `dist/chart`), and the applyconfiguration types match the new structs. No existing field, JSON tag, printer column, or condition is renamed.

`validatePredictive` is wired from `validatePodAutoscaler` and uses `field.Forbidden`, `field.NotSupported`, and `field.Invalid` the same way `validateHPARoleSubtarget` and `validateMetricWindows` do. An empty `mode` is accepted, which is what an omitted field decodes to. The HPA check is independent of the mode and horizon checks, so one object can report all three. The CRD schema still enforces the enum and the numeric bounds when the webhook is down. The HPA combination is webhook-only. The validating webhook is registered with `failurePolicy=ignore` (`pkg/webhook/podautoscaler_webhook.go` line 83), same as the existing role-subtarget rule, so a skipped webhook admits `spec.predictive` together with `scalingStrategy: HPA`.

Three status counts use `omitempty` on a plain `int32`:

```go
PredictedReplicas int32 `json:"predictedReplicas,omitempty"`
ReactiveReplicas  int32 `json:"reactiveReplicas,omitempty"`
WouldBeReplicas   int32 `json:"wouldBeReplicas,omitempty"`
```

`minReplicas` may be 0. `validateReplicaBounds` rejects only negatives. A projection that asks for 0 is a real Preview answer, and `wouldBeReplicas: 0` is how a reader learns that Auto would scale to zero. `omitempty` drops that 0, so an evaluation that produced zero serializes like a status object that never set the field. `ScheduledBoundsStatus` in the same file leaves `effectiveMinReplicas` and `effectiveMaxReplicas` without `omitempty` so a zero bound is stored. Drop `omitempty` on these three fields before a controller writes them. Changing the tag after clients exist changes the serialized object.

The type comments and `docs/source/features/autoscaling/predictive-autoscaling.rst` disagree on fields this PR is publishing.

- `ObservedValue` is "the stable metric value the projection started from." The page says it is the mean of the samples used by the fit.
- `LastUpdated` is "when the prediction was computed." The page says the timestamp moves only when the projection changes, and a steady series keeps the previous time.
- `HorizonSeconds` says the autoscaler uses its internal default. The page and the PR description fix that default at 120 seconds. The sibling window fields use the same "internal default" wording and keep the number in code (`defaultObserveWindowSeconds` is 180). If 120 is part of this contract, the godoc should state it. If the controller may still change it, the page should not state it yet.

`status.predictive.mode` is an open string in the CRD. `spec.predictive.mode` is an enum. A status reader can observe a value the spec would reject.

The page is written as behavior that already runs: a least-squares fit, evaluation "at the horizon," a floor of zero, a cap at four times the observed mean, a gate of three samples spanning half of `observeWindowSeconds`, KPA `ceil(projected / target)`, APA `ceil(currentReplicas * projected / target)`, and `final = max(reactive, projected)` after the scale-up rate, replica bounds, schedules, and the scale-up cooldown. None of that code is in this diff. The PR body says the block validates and does not act until the follow-up. The glance row added to `autoscaling.rst` describes the same floor as current behavior. That page's introduction still says "The two child pages" after the toctree gains a third entry.

"Evaluated at the horizon" does not name the anchor. The line at now + `horizonSeconds` and the line at the mean sample time plus `horizonSeconds` differ by about half the observe window. The sample pairs `observeWindowSeconds: 180` with `horizonSeconds: 120`, so one reading is about 30 seconds ahead of now and the other is 120. The field comment has to say "the fitted line at now + horizonSeconds" if this page remains the contract. The KPA and APA ceil lines also skip the tolerance band that keeps the current replica count (`kpa.go` around the stable/panic thresholds, `apa.go` `computeTargetReplicas`). They match the out-of-tolerance term only, and only when the projected number is in the same unit as the stable sample: KPA divides a total by `targetValue`, APA multiplies current replicas by per-pod use over target.

`wouldBeReplicas` is the field that answers #1418. Its comment is the contract to keep: the reactive count raised where the projection asks for more, after the same caps, bounds, and cooldown as the applied decision; equal to the applied count in Auto; the counterfactual in Preview. A follow-up that stores the pre-cooldown floor in this field will not match the type. `reactiveReplicas` is the reactive count before that floor.

`observedValue` and `predictedValue` are strings, matching `targetValue`. The type should say they are decimals in the same unit as the metric sample and as `targetValue`. A later change of precision, or of "mean" versus "value at now," is an API change once a controller emits them. `metric` is the winning source's `targetMetric`. Multi-metric autoscaling already selects the source that asks for the most replicas. Two sources can share a `targetMetric`, and the status then cannot tell which one won. That matches the name the rest of the API already uses. A source index would be a new key.

`TestValidatePodAutoscalerPredictive` covers the matrix in the PR body: Preview on KPA, Auto with horizon 120 on APA, HPA rejected with both `spec.predictive` and `scalingStrategy=HPA` in the message, an unknown mode rejected, horizons 0 and 3601 rejected, and a nil block accepted on HPA. The helper sets a scale target and one resource metric, so the cases go through `validatePodAutoscaler`. This review did not re-run the package. Worth adding before the contract is frozen: a present block with `mode` omitted, horizons 1 and 3600 accepted, and a negative horizon. The CRD marker and `maxMetricWindowSeconds` both hardcode 3600. The observe and panic windows already have that split.

API and compatibility. Empty `mode` and omitted `mode` are the same on the wire because the field is a string with `omitempty`, and the webhook treats `""` as legal. There is no `+kubebuilder:default=Preview`, and `PodAutoscalerCustomDefaulter.Default` is still a no-op, so the apiserver does not persist `Preview`. Every reader, including the follow-up controller, treats a present block with an empty mode as Preview. That matches `observeWindowSeconds`. `status.predictive` being a pointer keeps "no evaluation" distinct from a recorded one, and the comment says the object is cleared when the spec block is removed. Status writes on main are full `Status().Update` calls (`podautoscaler_controller.go` at the update sites in `updateStatus` and the scale path). A controller built with this type writes the new field. A controller built without it replaces status and drops the field. That is safe while nothing reads it. The sample correctly uses `mode: Preview`. The user page should say this change accepts the block and writes neither `status.predictive` nor a new replica count.
