## Pull Request Description

Follow-up to #2718, where review noted that the specs covered `queueRank` (a path gated behind `queueOverallSLO = false`) but not the live `rank()` path that `Peek` actually calls, nor the SLO branch precedence in `rankImpl`. This PR closes that gap. No production code is changed.

**`rank()`** — three specs:

- zero elapsed time: `rank = expected − target` on a profile that meets the SLO (negative rank, no violation)
- elapsed term: passing `RequestTime + 2s` shifts the rank by exactly +2
- a profile with no SLOs propagates `errNoSLO`

**`rankImpl()` branch precedence** — the dispatch order `TPOT > TTFT > TPAT > E2E` ( slo_queue.go ) is pinned through the `target` value each branch computes. SLO values are chosen so every branch yields a *distinct* target (TPOT: `0.1×100+0.5 = 10.5`, TTFT: `0.5`, TPAT: `0.01×(2+100) = 1.02`, E2E: `9`), so the asserted number reveals which branch ran. Each spec drops one higher-priority SLO and asserts the target falls through to the next branch.

The TPAT spec calls `req.PromptLength()` rather than hardcoding the prompt token count, so a tokenizer change breaks the existing signature-pinning spec instead of silently corrupting this one.

Also asserts `expected` alongside `target` in the TPOT/TTFT specs, with profile tables filled with distinct values (E2E=1.0, TTFT=0.2) so a branch reading the wrong table fails.

Mutation check: swapping the TPOT and TTFT branches in `rankImpl` fails exactly the precedence spec and nothing else, confirming the assertions pin the dispatch order.

Coverage for the touched functions: `rank` 0%→100%, `rankImplTTFT` 0%→100%, `rankImplTPOT` 0%→83%, `rankImplTPAT` 0%→78%, `rankImpl` 62.5%→87.5%. The remaining statements are the "should not reach here" error paths on prompt/token length.
