## Pull Request Description

#2776 recovers panics on the ExtProc request path, but the queue router does not run there. `queueRouter` starts `serve()` on its own goroutine and `tryRoute` only signals that goroutine through `chRouteTrigger`, so a panic raised while that loop peeks, routes or dequeues never crosses the interceptor and still ends the `aibrix-gateway-plugins` process. The crashes named in #2756 and #1284 happen exactly on that goroutine: `SLOQueue.rank` and `ModelGPUProfile.GetSignature` run during `Peek`, and the queue index arithmetic in `Peek`/`Dequeue` runs there too. When it ends the process, every request already queued keeps waiting for a target pod that never comes.

This adds the recovery to the serve loop itself. The drain body moves into `routeNext`, which routes at most one candidate (peek, `Route`, dequeue) and reports whether the loop may pick the next one. Recovering around the whole drain instead would keep the goroutine alive but leave the candidate that panicked at the queue head, so the next trigger would route it into the same panic again:

- the request being routed fails with `gateway routing recovered from an internal error`, so its waiter returns; an entry that carries no routing context is skipped, because there is nothing to fail and a nil dereference there would only add a second panic;
- a panic during `Route` leaves the candidate queued, so the recovery drops it. Leaving it there would hand it to the router again on the next iteration, hit the same panic, and block every entry behind it;
- a panic inside `Peek` or `Dequeue` leaves the queue at an unknown position, so the drain stops and waits for the next trigger instead of advancing from it, and the entry is not dequeued twice;
- a `Dequeue` that comes back with a different entry than the peeked candidate means the queue no longer matches what the loop acted on, so the drain stops there too: the rest of the queue is not routed from a position the queue disagrees with, and the candidate is not reported as a departure it did not verifiably make;
- after a routing panic the loop keeps draining, so the entries behind the defective candidate are routed on the same trigger.

All of the recovery runs inside `recoverCandidate`, under its own recover, because every action there calls back into the queue or into the metrics pipeline, which is the code that raised the first panic. A queue that panics twice must not take the serve goroutine down either.

The dropped candidate is reported like any other queue departure (`gateway_queue_outcome_total` with `outcome=error`, plus a fresh depth sample), so the queue metrics added in #2774 stay consistent when the recovery path runs. Every recovered panic logs its stack together with the stage it hit (`peek`, `route`, `dequeue` or `recovery`) and counts `gateway_request_panic_total` with the `pod_name` label, the same accounting #2776 uses on the request path. The panic value stays in the log; the failing request only gets the generic internal error.

Tests drive a hand-wired `queueRouter` with a queue that can be made to panic or fail inside `Peek` or `Dequeue`, and a backend router that panics on one request:

- `TestServeRecoversRoutePanicAndKeepsDraining`: the poisoned request fails with `errRouteRecovered`, the candidate behind it is still routed, the panic counter carries `pod_name`, and both departures are reported as `outcome=error` with the pending sequence `1 -> 0`;
- `TestServeRecoversDequeuePanicWithoutRetrying`: one `Peek`, one `Dequeue`, the entry stays queued, and no departure is reported for an entry that did not verifiably leave the queue;
- `TestServeRecoversPeekPanicAndStopsDraining`: draining stops, the request is untouched, and the same serve goroutine routes it once the queue stops panicking;
- `TestServeStopsDrainingWhenTheCandidateCannotBeDropped`: the drop fails with an error, and with a second panic that is recovered and counted; the entry stays queued and the failed drop is not retried;
- `TestServeStopsDrainingWhenTheQueueHandsBackAnotherEntry`: a mismatched dequeue stops the drain, the candidate stays queued with no departure reported, and the depth is sampled again;
- `TestServeRecoversPanicOnAnEntryWithoutRoutingContext`: an entry without a routing context is recovered once and dropped without a second panic;
- `TestServeRoutesRequestsWithoutPanic` keeps the unpatched path covered.

## Test Plan

- `go test ./pkg/plugins/gateway/algorithms/... -count=1` and `go test -race ./pkg/plugins/gateway/algorithms/ -run 'TestServe|TestQueue' -count=1`.
- `go test ./pkg/plugins/... ./pkg/metrics/... ./pkg/types/... -count=1`, `go vet` and `gofmt` clean.
- With the recovery removed, the same serve loop with a panicking router ends the test binary with `panic: boom` inside `queueRouter.serve`. That is the blast radius this PR removes.

Recovery is a last line of defense, not a replacement for fixing the defect.
