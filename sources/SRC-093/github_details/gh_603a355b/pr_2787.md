# [PR #2787] [Feat] Map the request priority tier to the vLLM request priority

## 正文

### Pull Request Description

Requests that share a model endpoint have different latency needs, and there is currently no way for a caller to say which one it is. An interactive turn can end up queued behind a nightly batch backfill even though the batch job would be perfectly happy to wait.

This adds the opt-in mapping proposed in #2286, with the v0 scope that was stated there. When `AIBRIX_PRIORITY_TIER_ENABLED=true`, a request carrying the `x-aibrix-priority-tier` header has the matching value written into the `priority` field of its backend request body:

| `x-aibrix-priority-tier` | `priority` | Notes |
| --- | --- | --- |
| `batch` | `100` | Below the engine default of `0`, so batch work yields to interactive requests. |
| `background` | `1000` | Yields to both interactive and `batch` work. |
| _(other or missing)_ | _(unchanged)_ | Forwarded untouched. |

vLLM serves smaller `priority` values first, so both entries sit below the engine default of `0` and the mapping can only de-prioritize. There is no path by which enabling this feature pulls a request ahead of one that did not set a tier, which is what makes it safe to switch on for a shared endpoint. The engine does the actual scheduling, so vLLM deployments need a priority-aware scheduler (`--scheduling-policy=priority`) for the field to have an effect.

### Semantics

- **Off by default.** While `AIBRIX_PRIORITY_TIER_ENABLED` is unset or `false`, the header is ignored and request bodies are forwarded byte for byte. There is no behavior change for existing deployments.
- **De-prioritize only.** The table has no value that outranks a request without a tier. A latency-sensitive tier can get an explicit head start later if that is wanted; doing it in a separate change keeps this one incapable of delaying traffic that opted out of nothing.
- **The caller wins.** A `priority` already present in the request body is never overwritten, so a client can pick a value for a tier the table maps, or use the field directly for a tier it does not.
- **Fail-open.** Only a well formed JSON object is extended. An empty body, JSON `null`, a JSON string or array, a truncated body, and the non-JSON endpoints such as the multipart audio and video paths are forwarded byte for byte, and none of that relies on `sjson` error behaviour. The tier is a hint and never fails or blocks a request.
- **No new artifact.** The tier rides on a request header rather than a new CRD or profile field, which keeps this usable from any client the gateway already serves.
- Tier names are matched case-insensitively, and the value is trimmed where the header is recorded on the routing context.

### Implementation

- `pkg/plugins/gateway/gateway_req_priority.go` holds the tier table and the rewrite. The object guard runs first, then the body is edited in place on `routingCtx.ReqBody` with `sjson`, the same helper the PD path uses, so no field other than `priority` changes.
- `gateway_req_headers.go` records the trimmed header value on the routing context.
- `gateway_req_body.go` applies the mapping before routing, and forwards the routing context body with a `content-length` computed from it. The placement matters twice over:
  - the PD router builds the prefill payload out of `routingCtx.ReqBody` while it routes, so a rewrite that waited for the target pod would leave the prefill leg, the heavy one, at the engine default. Applying before routing gives both legs the field from a single edit;
  - the forwarded body is then the only body, so there is no second copy to keep in sync and no content-length rule per dispatch path.
- One behavior change to call out on the delegated path: `RouterNotSet` now sets `content-length` where it previously set only `model`. The response replaces the upstream body with `routingCtx.ReqBody`, and the size is what Envoy validates the upstream request against, so the header describes the body that is actually forwarded. While the opt-in is off the body is untouched and the value matches the length that would have been sent anyway; it becomes load bearing only once a tier is mapped. Setting it conditionally would bring back the per-path branch this change removes.
- `cmd/plugins/main.go` reads the new environment variable, defaulting to `false`.

### Test Plan

- `go build ./...`, `go vet ./pkg/plugins/gateway/...`, `staticcheck -checks='QF*'` on the gateway and plugin packages, a focused `-race` run, and a `sphinx-build -W --keep-going` pass are all clean.
- `go test ./pkg/plugins/gateway/... ./pkg/types/... ./cmd/...` passes.
- New tests in `gateway_req_priority_test.go` cover the tier lookup (case-insensitive, unknown, empty, whitespace-only), the injection rules on the routing context alone (opt-out byte for byte, unmapped tier, caller-set `priority` including `0`, and the non-object bodies: array, empty, `null`, JSON string, truncated), and the end-to-end handler in both dispatch modes: routed and unrouted, with and without a mapped tier, each asserting the `content-length` header matches the forwarded body. Removing the `RouterNotSet` content-length line makes the two unrouted cases fail, so that part of the change is pinned rather than incidental.
- `TestHandleRequestBody_PriorityTierBeforeRouting` captures the routing context inside `Route` and asserts the priority is already in the body the router sees, and that the forwarded body is the same one. This is the PD prefill guarantee, and it needs two ready pods: a single ready pod takes the pinned-pod fast path in `selectTargetPod` that never calls the router.
- `TestHandleRequestHeaders_PriorityTierIsTrimmed` pins that the header value is trimmed when it is recorded, which is where the tier lookup expects that to happen.
- `gateway_req_body_test.go` asserts the exact header set of an unrouted request, now including `content-length: 74` for a 74-byte body, which is what pins the opt-out path as byte-for-byte.

The additions here sit away from that change's hunks (a new section before **Headers Reference** and one table row at the end of **Target and General Headers**), and the PR still merges cleanly against the current base.

## Design feedback: simplify

The v0 policy is already the right shape: opt-in, de-prioritize-only, caller wins, fail-open, fixed table, no CRD. Complexity to cut is **where** the rewrite runs and how it threads through `HandleRequestBody`.

### 1. Apply once on `ReqBody` before routing — drop `outboundBody`

Today the flow is: route (PD may rewrite `ReqBody`) → `applySLOTierPriority` returns a **new** slice → local `outboundBody` + dual `content-length` paths.

Simpler and matches PD’s own pattern (mutate `ReqBody` in place with `sjson`):

1. When the flag is on, rewrite `routingCtx.ReqBody` once **before** `selectTargetPod`
2. Forward `routingCtx.ReqBody`
3. Always set `content-length` from `len(routingCtx.ReqBody)`

That removes the `outboundBody` variable and the RouterNotSet vs routed special-casing that Gemini already tripped over.

### 2. Same change fixes PD (real gap, not a nit)

Prefill runs inside routing, **before** today’s apply. So for PD:

- prefill leg → no mapped `priority`
- decode leg → gets `priority`

Prefill is often the heavy, queue-blocking work. Applying before routing means both legs inherit the field from one edit. Documenting “decode only” as v0 is a weaker alternative than moving the call.

### 3. Keep the policy table as-is — don’t grow it

Hardcoded `batch=100` / `background=1000`, no negative priorities, no env-tunable values, no interactive boost: keep that. Tunables and “latency-sensitive head start” belong in a follow-up; adding them here undoes the safety story.

### 4. Name it as an engine priority hint, not gateway SLO

`slo.go` / `SLOQueue` are latency-profile queues, not named tiers. `x-aibrix-slo-tier` sounds like it plugs into that path; it doesn’t. Either:

- keep the header but say clearly in docs “engine scheduling hint; independent of the SLO router”, or  
- prefer a name like `x-aibrix-priority-tier`

Avoid implying one control plane when there are two.

### 5. Don’t invent another config surface

Header + env flag is enough. Don’t fold this into config profiles or a CRD for v0 — the PR correctly resists that.

### 6. Small cleanups (optional)

- Trim once (headers already `TrimSpace`; lookup doesn’t need to again)
- Skip non-JSON / multipart early instead of relying on `sjson` fail-open (clearer than “error means leave alone”)
- Nil-`RoutingContext` guard is unnecessary here (agree with author); empty-body early return is fine

### 7. Tests

Handler e2e that pins `content-length` is valuable. A lot of the table duplicates `apply` unit cases — fine to keep, not a design blocker. Add one PD case if you move apply earlier (prefill body carries `priority`).

---

**Bottom line:** Keep the opt-in de-prioritize mapping. Simplify by **mutating `ReqBody` once before routing** and forwarding that body everywhere. That deletes `outboundBody` / dual content-length logic and makes PD correct without a second policy.

## Code review

**Verdict: request changes** — policy and tests are strong; two correctness gaps before merge.

CI is green (unit, race, lint, install E2E). Opt-in / de-prioritize-only / caller-wins (including `priority: 0`) / docs are in good shape. Gemini’s `RouterNotSet` `content-length` fix in `b26e814d` looks right.

### Requested changes

**1. Fail-open is incomplete — `sjson` rewrites non-objects**

`applySLOTierPriority` assumes `sjson.SetBytes` errors on anything that isn’t a JSON object. It doesn’t:

| input | `sjson.SetBytes(..., "priority", 100)` |
| --- | --- |
| `[1,2,3]` | error → forwarded (tested ✓) |
| `""` | success → `{"priority":100}` |
| `null` | success → `{"priority":100}` |
| `"hi"` | success → `{"priority":100}` |

So an empty body, JSON `null`, or a JSON string is **replaced**, not left untouched. That breaks the documented fail-open story (and the multipart / non-JSON claim relies on luck).

Guard like the PD path already does:

```go
if !gjson.ValidBytes(routingCtx.ReqBody) || !gjson.ParseBytes(routingCtx.ReqBody).IsObject() {
    return routingCtx.ReqBody
}
```

Add table cases for `""`, `null`, and `"hi"`. An empty-body early return alone is not enough (`null` / string still slip through).

**2. PD prefill never gets the mapped priority**

`applySLOTierPriority` runs **after** `selectTargetPod`. Prefill is sent during routing from the original body; only the decode/`BodyMutation` path sees `priority`.

For batch/background on PD, the heavy prefill leg stays at engine default `0`. Apply **once on `ReqBody` before routing** (and forward that body) so both legs inherit the field — also removes `outboundBody` and the dual content-length paths.

### Nits

- **RouterNotSet always sets `content-length` now**, even when the feature is off. Harmless if intentional (pin it in the PR description); otherwise only set it when the body actually changed.
- **`ReqBody` stays stale** when apply returns a new slice — anything later reading `routingCtx.ReqBody` sees the pre-rewrite bytes. In-place update (or apply-before-routing) fixes this.
- Double `TrimSpace` (headers + `sloTierPriorityFor`) is fine; one is enough.
- Agree with rejecting a nil-`RoutingContext` guard here — `HandleRequestBody` already dereferences it.
- Test struct field `wantUnknownKey` is unused.

### What works

- Fixed table + case-insensitive tiers + caller `priority` preserved via `gjson.Exists()` (including `0`)
- Opt-in default `false` / ServerOptions wiring
- Handler tests that assert `content-length == len(forwarded)` for routed and unrouted
- Docs clearly require `--scheduling-policy=priority` and describe de-prioritize-only

### Bottom line

Ship the mapping. Before merge: **IsObject (or equivalent) before `sjson`**, and **apply before PD routing** (or document decode-only and accept the prefill hole). Canonicalizer-level policy can stay as-is.
