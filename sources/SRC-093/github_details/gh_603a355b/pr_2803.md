## 正文

### Pull Request Description

The static endpoints file is the first thing a new deployment writes, and its shape depends on where the reader comes from. The TRT-LLM recipes spell the simple backend list `workers` and the disaggregated pair `prefill_workers` and `decode_workers`, while this repository spells the same two things `endpoints` and a `rolesets` list whose entries carry a name, a prefill list and a decode list.

This is the static config piece of #2031, which the issue thread asked to handle first. The provider itself was already renamed to `StaticProvider`, so what is left on the naming side is the file format:

- `workers` is accepted as an alias of `endpoints`.
- `prefill_workers` and `decode_workers` are accepted as the shorthand for a single roleset named `default`.
- The existing `endpoints` and `rolesets` keys keep working, so no deployment has to move, and the `rolesets` form stays the way to express multiple groups or an explicit group name.

`StaticModelConfig.resolve()` turns whichever spelling the file uses into the `(endpoints, rolesets)` pair the provider already built pods from, so the cache, the pod labels and the PD router are untouched. `default` is the roleset name the shipped configs and the PD docs already used, and the role labels stay an implementation detail of the provider, as discussed in the issue.

Nothing is guessed silently: the three combinations that cannot be reconciled, `endpoints` with `workers`, `rolesets` with the shorthand, and the non-disaggregated form with the disaggregated one, fail the load with a message that names the model.

The load also got the checks the format change left open: a model with an empty name, which produced pods named `-vllm-0` with an empty `model.aibrix.ai/name` that nothing could route to, and a model with no backends at all, which loaded cleanly and contributed no pods. Both fail the load now. The shorthand must list both sides, and a named roleset must declare at least one worker, so a config that could never be routed fails at load instead of loading into a model that serves nothing.

## Code review

### Correctness

`resolve` is the right seam. It returns the `(endpoints, rolesets)` pair `load` already walked, and the three combinations that cannot be merged fail before any pod is built. `workers` is used when `endpoints` is empty. Both lists non-empty is an error, including when the addresses are the same. `prefill_workers` and `decode_workers` become one `RoleSetConfig` named `default`. That matches the pairing key `groupPDPodsByRoleset` reads from `roleset-name`, and it matches the `default` roleset already shipped in `samples/disaggregation/neuron/pool.yaml`. `workers` together with an explicit `rolesets` list hits the third check (`len(endpoints) > 0 && len(roleSets) > 0`). The shorthand branch can overwrite `roleSets` only after the mutual-exclusion return, so dropping the extra length guard in the second commit is correct. `Watch` returns the error before `initDiscoveryProvider` delivers an event, so a bad file does not leave a partial pod set in the cache.

The empty-name check closes a real hole. `addressToPod` builds the pod name from `sanitizeName(modelName)`, and `sanitizeName("")` is empty, so the pod was named `-host-0` with an empty `model.aibrix.ai/name`. Nothing could select it by model.

The "no backends" check does not cover the case the second commit describes. It rejects a model only when both normalized slices have length zero. Any `rolesets` entry counts, including one that has a name and no addresses:

```yaml
models:
  - name: test-model
    rolesets:
      - name: default
```

`len(roleSets) > 0`, `resolve` returns success, the loop adds nothing, and `Watch` returns nil. That is the silent empty load, still reachable. `prefill_workers: []` does fail, because `workerRoles` requires `len > 0`. The two spellings disagree.

A one-sided shorthand is accepted. `TestStaticProviderPrefillWorkersOnly` expects a pod labeled `role-name=prefill` and `roleset-name=default`. `isPDRolesetEligible` (`pkg/plugins/gateway/algorithms/pd_roleset.go`) requires a prefill replica and a decode replica, and `finalPDScore` skips a roleset with no decode score. The updated discovery README and `deployment/standalone/configs/endpoints-pd.yaml` already say a roleset serves traffic only when both sides have a worker. The loader accepts a config the router will never select, and the new test locks that in. The existing `rolesets` form already allowed a one-sided group; the shorthand makes that the shortest PD example.

Empty address strings still become pods. `workers: [""]` has length 1, `net.SplitHostPort("")` fails, and `addressToPod` stores host `""` with port 8000. `FilterReadyPod` drops an empty `PodIP`, so the process starts and the model has nothing routable. That path already existed for `endpoints`. The new required-field check looks at list length, not at the strings inside the lists.

A name of `" "` passes `Name == ""`. `sanitizeName` does not trim spaces, so the model label is a space.

### Risks

Startup now fails for files that used to load: `name: ""`, a missing name key, and a model that sets only `engine`. That is the right failure for a provider that reads the file once. It is a behavior change for a placeholder model left in the file.

`docs/source/getting_started/installation/local-mode.rst` used to show `rolesets[].name: qwen-pd`. The replacement shorthand always labels the pods `roleset-name=default`. The install page does not say that, and it no longer shows `rolesets`. A reader of that page cannot name a group. The discovery README still has the multi-group example, and it calls `endpoints` and `rolesets` "the older spellings", then only defines `workers` as an alias of `endpoints`. `rolesets` is how a file names a group or declares more than one. Describing it as older points people away from the form they need once the shorthand is not enough.

Conflict errors include the model name. The empty-name error has no index, so a file with several models reports `model name is required` and does not identify the entry. Two models may both use the shorthand; each gets `roleset-name=default`. The router receives the ready pods for the request, so those labels meet only inside one model.

The `endpoints` + `rolesets` error text changed. It still contains `mutually exclusive` and the model name. `TestStaticProviderMutuallyExclusive` still passes because it matches that substring.

### Tests

The new cases cover the workers alias (two pods, no role labels), the both-sides shorthand (three pods, `default`, engine label), prefill-only, the three conflicts (`endpoints`+`workers`, `rolesets`+`prefill_workers`, `workers`+`prefill_workers`), an empty name, and a model with only `engine`. Label and pod-IP assertions match what `load` writes. The three error strings are distinct enough for a substring match.

These cases are untested, and the first one hides the hole above:

- a named `rolesets` entry with no addresses, which loads today
- `workers` together with `rolesets` (the code path exists; no test names it)
- decode-only shorthand
- the model name inside a conflict error
- one file that uses `workers` on one model and `rolesets` on another

I did not re-run `go test`.

### API and compatibility

No CRD, HTTP field, header, CLI flag, label key, annotation, or env var changes. `NewStaticProvider` and `Provider` are unchanged. `StaticModelConfig` gains `Workers`, `PrefillWorkers`, and `DecodeWorkers`, all `omitempty`. A Go composite literal that sets `Endpoints` and `RoleSets` behaves as before.

The config keys `endpoints` and `rolesets` still unmarshal. `workers`, `prefill_workers`, and `decode_workers` are new. Pod labels for the old keys are unchanged. The shorthand sets `role-name` and `roleset-name=default`, which the PD router already consumes. In this repo, `cmd/plugins/main.go` is the caller that passes the file to `NewStaticProvider`.

The shipped examples under `deployment/local`, `deployment/standalone`, and the local-mode doc now use the new keys. A checkout that copied those files into a second parser that expects `endpoints` would see a different document. Nothing else in this repo parses them.

## Design simplification

Keep `resolve` and the two existing keys. Close the empty-roleset hole, and stop treating a one-sided shorthand as a successful PD config. In the docs, describe `rolesets` as the multi-group form.

Keep one struct and the normalization to `(endpoints, rolesets)`. The pod loop in `load` can stay. Keep reject-don't-merge, including when the two alias lists are identical, and keep the three errors that name the model and the keys. Keep `defaultRoleSetName` with the provider constants. A name, or a second group, belongs on `rolesets`; the shorthand should not grow a name field. Keep the empty-name check. Keep the tests for the workers alias, the both-sides shorthand, the three conflicts, the empty name, and the engine-only model.

Replace `len(endpoints) == 0 && len(roleSets) == 0` with a count of addresses after normalization. A roleset entry with no `prefill` and no `decode` then fails the same way an engine-only model fails. One condition covers both spellings. Today `prefill_workers: []` errors and `rolesets: [{name: default}]` succeeds.

On the shorthand, require `prefill_workers` and `decode_workers` both non-empty. The TRT-LLM shape this alias copies lists both, and `isPDRolesetEligible` will not select a one-sided group. Drop `TestStaticProviderPrefillWorkersOnly` as a success. The `rolesets` form can keep accepting a partial group so an existing file still loads. Leave a custom `UnmarshalJSON`, a second config type, and a rename of the Go field `Endpoints` out of this change. Three extra slices plus `resolve` is the small version.

In the docs, keep the shorthand examples. Put back one `rolesets` example on the install page that used to show `qwen-pd`, or one sentence that a custom name uses `rolesets`. `endpoints` is the spelling the examples are moving off of. `rolesets` stays the way to name a group.

Thanks, both holes are real and are fixed in 7e4698ed.

- The backend check counts addresses after normalization instead of lists, so `rolesets: [{name: default}]` now fails the same way `prefill_workers: []` does, and one condition covers both spellings. The `rolesets` form still accepts a partial group so an existing file keeps loading.
