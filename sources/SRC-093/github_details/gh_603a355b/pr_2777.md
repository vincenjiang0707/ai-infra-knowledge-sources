## Pull Request Description

Superseded runs stay in the queue and keep holding runners while the newest push waits behind them.

Measured on 2026-09-22 (UTC) in this repository:

- At 07:39Z, 31 workflow runs were queued or in progress, and 12 of them were already at a commit that is no longer the head of its pull request. One of those had been waiting since 03:17Z.
- Queue time dominates the wall clock. Sampled `Linter and Unit Tests` runs waited 38 minutes to 2 hours 35 minutes for their first job, while the jobs themselves run in 2 to 9 minutes.
- A pull request pushed at 06:56Z had 19 checks. Its first job started 30 minutes later, and the remaining checks were still queued 45 minutes after the push.

Changes:

- Add a `concurrency` group to the workflows that run on pull requests. The group is keyed on the pull request number, so a newer push cancels the run it supersedes. `push` and `workflow_dispatch` runs fall back to a per-run group, so their behavior is unchanged. The triage bot uses the issue or pull request number.
- Add `timeout-minutes` to jobs that did not set one. The default is 360 minutes, so a job that hangs can hold a runner for six hours. The values stay well above the observed runtimes. The longest job, `Installation E2E Tests`, already takes about 41 minutes and is capped at 75.

Nothing changes about what is verified: the checks that gate a pull request always run for its current head. Cancel-in-progress only drops runs for commits that a newer push has already replaced.

### cursor[bot] · 2026-09-22

The concurrency key is the right one: `${{ github.workflow }}-${{ github.event.pull_request.number || github.run_id }}` with `cancel-in-progress` only on `pull_request`. Same-PR pushes cancel each other; `push` / `workflow_dispatch` stay unique via `run_id` and are not cancelled. Workflow name in the group keeps lint from cancelling installation, which is what you want. `docker-build-images.yml` is correctly left alone (`aibrix-disabled`). Timeouts are well above the measured runtimes and beat the 360-minute default.

The bot group (`pull_request.number || issue.number`) is the same GitHub ID space, and `cancel-in-progress: true` is appropriate because that workflow is `pull_request_target`, not `pull_request`.

One follow-up that this change makes more visible: `installation-tests.yml` `delete-artifacts` is `if: always() && !cancelled()`. Cancel-in-progress will now skip that job on every superseded run, so image tarballs sit until `retention-days: 1`. Kind cleanup on the runner is fine (the VM dies). Prefer `if: always()` for the delete job so a cancelled run still drops the artifacts.

Required checks on the current HEAD are unchanged; cancelled runs are only for replaced SHAs. That matches the queue data in the description. Happy to take this; the artifact-delete tweak can land here or as a follow-up.
