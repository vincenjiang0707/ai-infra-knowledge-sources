## 正文

### Pull Request Description

`Peek` picked the next request to serve with a comparator that had no tie-break, and sorted each candidate's profile list with an unstable comparison, so equal ranks left the pick to the `sync.Map` iteration order that collects the subqueue candidates. The same queued set could therefore be served in a different order from one gateway process to the next. This change pins the order `Peek` uses and covers it with tests.

- Candidates are ordered by the rank of the candidate's most relaxing profile, descending: the request closest to a violation is served first. Equal finite ranks break on arrival time (FIFO) and then on the subqueue key, which is unique within one `Peek`, so the order is total. A NaN rank cannot be compared, so it sorts after every comparable rank and such a candidate is served last; two NaN ranks fall back to arrival time and then to the subqueue key.
- A candidate's profiles are ordered by rank ascending with the profile key as tie-break. That is the order the relaxer walks when it stops before the first profile whose rank is above zero, so the walk no longer depends on how pod indexes are enumerated.
- The queue service time in the queue-wide rank keeps its `(Len()-1)/throughput` meaning and now says so in the comment: `Len()` counts the head, whose own serving time is accounted separately.

### Switch matrix

The four policy switches live on a `queueOptions` struct on `SLOQueue`, so every branch is reachable from tests. Production runs the shipped values, which `NewSLOQueue` writes down once:

| Switch | Default | `true` | `false` |
| --- | --- | --- | --- |
| `fifoOnNonSLOViolation` | `false` | candidates that both rank below zero are served in arrival order | candidates are always compared by rank |
| `queueOverallSLO` | `false` | rank accounts for the requests queued behind the head (`queueRank`) | rank is computed per request (`rank`) |
| `monogenousGPURouting` | `true` | a candidate is routed per deployment profile, most relaxing first | a candidate is routed against the whole pod set in one call |
| `monogenousGPURoutingOnly` | `false` | only the most relaxing profile is tried | profiles are tried until one succeeds or the first violating one is reached |

`monogenousGPURoutingOnly` is read only inside the `monogenousGPURouting` branch, so it has no effect unless profile routing is on.

### Behavior change

Two observable changes. Equal finite ranks previously followed the candidate collection order, which is the `sync.Map` iteration order and changes between processes, and now follow arrival time and then the subqueue key. A NaN rank previously left the order undefined and now sorts after every comparable rank. NaN last is a policy choice: `LatencySeconds` returns a NaN cell with a nil error for an unmeasured bucket, so the request stays in the ranked set, an unknown rank is the least urgent rather than the most urgent, and a candidate whose every profile is NaN is served in the same last place. The tie-break reads the request's `RequestTime`, the same field the FIFO branch used, which is stable for the duration of a `Peek`. Rank differences between comparable ranks are unaffected, so no request that ranked higher before is served later now.

## Code review

### Correctness

The ordering fix is right, and it is a real bug. `higherRank` was `rank1 - rank2`. A NaN rank makes that difference NaN, and both `NaN < 0` and `NaN > 0` are false, so `sort.Slice` no longer has a strict weak ordering. With ranks NaN, 1, and 2, the finite pair is ordered and each is incomparable to NaN, which is enough for pdqsort to panic or reshuffle. `profileLess` and `candidateLess` decide NaN before any `<` / `>` and then break remaining ties on a unique key, so both comparators are total.

`profileLess` sorts rank ascending and NaN last, then profile key. That matches the relaxer, which walks from index 0 and stops at the first later profile with rank `> 0`. Putting NaN last also means `Profiles[0]` is a comparable rank whenever the candidate has one, which is what `candidateLess` reads.

`candidateLess` serves the higher `Profiles[0]` rank first. Equal finite ranks, and NaN compared with NaN, use `RequestTime` then `SubKey`. `SubKey` is one per subqueue inside a single `Peek`, so the order no longer depends on `sync.Map` iteration. The `fifoOnNonSLOViolation` branch only skips the rank comparison when both ranks are finite and negative; it still finishes on time and key, so that mode is a total order too. I checked the switch: the empty first case does not fall through into the rank return, and execution continues at the time comparison. That matches the old `if` / `else`.

The `queueRank` comment matches the code that was already there. `SimpleQueue.Len` is `enqueueCursor - dequeueCursor`, which includes the head `Peek` returns, and `headServingTime` already accounts for that head. `Len()-1` is the right count of requests behind it. No formula change.

`NewSLOQueue` still applies the old constants: `fifoOnNonSLOViolation` false, `queueOverallSLO` false, `monogenousGPURouting` true, `monogenousGPURoutingOnly` false. `algorithms/slo.go` is the only production constructor and still calls `NewSLOQueue`, so those four branches stay at the shipped values. `normalized()` forcing `monogenousGPURouting` when `monogenousGPURoutingOnly` is set preserves the old `monogenousGPURouting && false` implication for the one contradictory combination.

### Risks

The PR description still says equal ranks, NaN included, break on arrival time. That was the first commit. The second commit and the tests do something else: a NaN rank sorts after every finite rank, even when the NaN candidate is older. NaN versus NaN still uses arrival time. The description should be updated so the contract people review is the one the code implements. "Default behavior is unchanged except for ties" is also too narrow. Tie order changes, and so does every NaN rank, which used to be undefined.

NaN-last is the right way to keep the sort valid, and it is a policy choice. `LatencySeconds` returns a NaN cell with a nil error, so the candidate stays in the ranked set instead of taking the existing no-SLO fallback. A request whose best profile is NaN now waits behind every finite rank, including a large negative one. That deprioritizes an unmeasured request relative to a request that still has slack. Sorting NaN first would also be a strict weak order and would treat unknown as urgent. The profile sort should stay NaN-last so `Profiles[0]` stays comparable; the candidate-level choice for an all-NaN profile list should be called out as intentional.

The relaxer stop `i > 0 && profile.Rank > 0` does not treat NaN as a stop, because `NaN > 0` is false. NaN profiles are sorted after every positive rank, so a known violation still cuts the walk before them. If every finite rank is `<= 0`, the walk continues into NaN profiles and will try a deployment whose latency was not measured. If NaN means "do not prefer this profile", the loop should stop on NaN as well.

`candidateLess` reads `RequestTime` on the embedded `RoutingContext`, the same field the old FIFO branch used. `QueueEntry.EnqueuedAt` is the timestamp frozen because the pooled context can be reset after the requester is unblocked. This tie-break makes `RequestTime` load-bearing for cross-process order. It is stable for the duration of `Peek`, and each gateway orders its own queue, so this is not a new race. It is also not enqueue order when context creation and `Enqueue` differ.

`queueOptions`'s zero value is not the shipped policy: `monogenousGPURouting` defaults to true in `defaultQueueOptions` and to false in a bare `SLOQueue{}`. Production goes through `newSLOQueue`, and current tests that use a composite literal do not `Peek`. A later literal that forgets `opts` silently switches to whole-pod-set routing.

### Tests

The comparator specs are the ones that pin the bug. The adversarial `candidateLess` sort starts from the wrong input order for both arrival time and subqueue key. The NaN specs, including the `Peek` where the older request's only cell is NaN and must lose to a finite rank of -3, fail if the NaN guard is removed. Rank arithmetic in the fixtures matches `Features()` (`output` then `prompt`), the log2 buckets `{0, 3}`, and `elapsed + expected - target`.

The equal-rank `Peek` loop of 20 does not reshuffle the `sync.Map`. Iteration order is stable for one map inside one process, so a comparator that left equal elements alone could still pass that spec whenever the map already yields the older key first. The unit sort is what makes the tie-break red. One `Peek` plus the adversarial sort is enough.

Gaps, none of which hide the main bug: equal finite profile ranks are not shown to break on profile key; two all-NaN candidates are not shown to break on arrival time; the relaxer is not shown to skip or attempt a NaN profile. The switch specs do cover the four non-default branches, the `normalized()` implication, the queue-wide rank flip (`-12.5` versus `-14`), and the cross-profile pick (effective ranks `-7` and `-8`, first route `dep-a`). I did not re-run `go test`.

### API and compatibility

No exported signature, CRD, HTTP field, header, env var, label, or annotation changes. `NewSLOQueue(provider, modelName)` is unchanged, and the options type and `newSLOQueue` are unexported, so this does not add a configuration surface callers can depend on. `higherRank` was unexported and only used by the old sorts and one test.

Observable behavior changes inside one gateway process. Equal finite ranks, previously `sync.Map` order, are now `RequestTime` then `SubKey`. A higher finite rank still wins, so a request that strictly outranked another is not served later. NaN ranks move from an invalid ordering to a defined last place. The four policy switches stay at the values that shipped. Nothing here needs a migration. Leave the switches unexported until a real config path exists; promoting them later is the compatibility decision, and this PR does not take it.

## Design simplification

Keep the sort contract. Cut the options framework.

Keep `profileLess`, `candidateLess`, and the deletion of `higherRank`. Subtraction cannot order NaN, and a total order is the whole bugfix. Keep NaN handling in both comparators, rank as the primary candidate key, then `RequestTime`, then `SubKey`. Keep the `Len()-1` comment on `queueRank`. Keep tests that exercise the production path: adversarial `candidateLess`, NaN through `Peek`, the relaxer stop on a positive rank, and the cross-profile pick. Those lock default behavior.

Cut `queue_options.go`: the default-constant block, `defaultQueueOptions`, `normalized`, and the `NewSLOQueue` / `newSLOQueue` split. The four bools are still package-level policy with one production value each, set in `NewSLORouter` only through `NewSLOQueue`. No config, flag, or annotation reads them. The struct exists so tests can reach branches that production cannot select, and `normalized()` exists so a test can set the pair the old constant `monogenousGPURouting && false` made unrepresentable. That is test scaffolding for a later configuration API the PR does not add.

The smaller shape is the one already on `main`. Leave the four switches as constants with the shipped values. `candidateLess` reads `fifoOnNonSLOViolation` the way `Peek` already reads the other three. `Peek`'s profile loop stays inline. The ordering helpers sit next to `Peek` and do not need a new type.

If the non-default branches are worth pinning before a config API exists, assign an unexported struct literal in the test after `NewSLOQueue` and do not normalize. Document that `monogenousGPURoutingOnly` is consulted only inside the `monogenousGPURouting` branch, which the `if` already guarantees. Do not add a constructor, a default-constant mirror, or a spec whose only job is to undo `monogenousGPURouting: false`.

The new harness repeats `fakePodList`, `newTestSLOQueue`, and `newRankedTestRequest`. A recording router and `ListByIndex` pods are worth having for the relaxer and cross-profile specs; the second profile installer and enqueue helper are not. Drop the 20-iteration loop. The `rankImpl` SLO-priority comment is accurate and independent of ordering; it can stay, and it does not need to ride with the options work.
