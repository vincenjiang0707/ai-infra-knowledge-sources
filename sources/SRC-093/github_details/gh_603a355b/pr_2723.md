# [PR #2723] [Bug] Scope BlockRemoved prefix eviction to the pod that sent it

## 正文

## Pull Request Description
With KV event sync enabled and more than one replica behind a model, one pod evicting a KV block drops that prefix for every pod, so `MatchPrefix` reports 0% for replicas that still hold the block and the router falls back to load-based selection. vLLM emits `BlockRemoved` on every eviction, so this fires continuously under memory pressure, which is when KV-cache-aware routing matters most.

The cause is `pkg/utils/syncprefixcacheindexer/sync_hash.go:354-362`: `ProcessBlockRemoved` calls `delete(contextData.prefixStore.prefixMap, aibrixHash)` on the outer map even though `prefixMap[hash]` is a `map[podName]*PodInfo`, and it never reads `event.SourcePod`, which the per-pod ZMQ subscriber already sets (`pkg/kvevent/handler.go:119`) and `pkg/cache/store_providers.go:195` forwards. The sibling `RemovePrefix` in the same file already does the per-pod thing. The `totalPrefixes--` on the next line is equally unconditional: it runs once per resolved engine hash whether or not `prefixMap` held that entry, so a `BlockRemoved` that arrives after `RemovePrefix` already dropped the prefix takes the counter negative. `AddPrefix` compares that counter against `maxPrefixesPerContext`, so a drifted counter silently raises the `AIBRIX_SYNC_MAX_PREFIXES_PER_CONTEXT` memory cap.

`ProcessBlockRemoved` now resolves the engine hashes without mutating, deletes only `event.SourcePod` from each prefix entry, and drops the entry, the `engineToAibrix` mapping, and the reverse block index only once no pod holds the block. `totalPrefixes` is decremented only when an entry is actually removed. Lock order stays `mappingMu` then `prefixMu`, matching `ProcessBlockStored`, and the `updateBlockIndex` calls run after `prefixMu` is released so `blockIndexMu` is never nested under it.

Behaviour change: a prefix now survives on the replicas that still hold the block instead of being cleared fleet-wide. A `BlockRemoved` with an empty `SourcePod` still clears the whole entry, so the existing call sites that omit it, such as `TestReverseIndex` and the stress suite, behave exactly as before.

### What was broken

`prefixMap` is `prefixHash → map[podName]*PodInfo`, and production `BlockRemoved` events already carry `SourcePod` (`pkg/kvevent/handler.go` → `pkg/cache/store_providers.go`). `ProcessBlockRemoved` ignored that and deleted the whole outer entry, so one replica evicting a block dropped the prefix for every replica. Under memory pressure that is exactly when prefix routing matters.

The unconditional `totalPrefixes--` was a second real bug: a `BlockRemoved` after `RemovePrefix` already dropped the entry drove the counter negative and silently weakened `AIBRIX_SYNC_MAX_PREFIXES_PER_CONTEXT`.

### Why the fix is correct

The new flow is:

1. Resolve engine hash → aibrix hash under `mappingMu` without mutating.
2. Under `prefixMu`, delete only `event.SourcePod` (or the whole entry if `SourcePod == ""`).
3. Drop `engineToAibrix` and the reverse block index only when no pod still holds the prefix.
4. Decrement `totalPrefixes` only when an entry is actually removed.

Holding `mappingMu` across the prefix update is required, not just stylistic. Releasing it between resolve and mutate would let `ProcessBlockStored` recreate a mapping that this path then deletes, leaving pods in `prefixMap` with no way for a later `BlockRemoved` to find them. Lock order stays `mappingMu` then `prefixMu`, matching store, and `blockIndexMu` is still never taken under `prefixMu`.

Keeping the mapping until the last pod is also required: `engineToAibrix` is context-level and content-hash based (same vLLM block hash on every replica). Deleting it when the first replica evicts would make the second replica’s `BlockRemoved` a no-op. The `"both pods evict the block"` case covers that indirectly.

Empty `SourcePod` still wipes the whole entry, so `TestReverseIndex`, `TestMemoryCleanup`, and the stress suite stay compatible.

Related issues #2287 / #2285 are the same class (indexer invalidation / dropped event fields) but they do not cover this eviction scope; no overlap with the current change.
