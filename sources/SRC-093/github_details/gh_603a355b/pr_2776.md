## Pull Request Description

The plugin had no panic recovery on the ExtProc path: `grpc.NewServer` in `cmd/plugins/main.go` is built with the OTel stats handler and a max message size and nothing else, so one panic in the stream handler ends the whole `aibrix-gateway-plugins` process together with every request in flight on it. #2756 hit exactly that on the routing path (a malformed profile making `ModelGPUProfile.GetSignature` panic); #1284 (index out of range in the queue) and #2049 (pod restarts under high concurrency) have the same blast radius on the same path.

This recovers at the server boundary, with no new dependency:

```go
opts = append(opts, grpc.StreamInterceptor(gateway.StreamPanicRecoveryInterceptor()))
```

A recovered panic logs the stack trace, counts a new `gateway_request_panic_total` counter, and fails only the stream it happened on with `codes.Internal`. The panic value stays in the log and the reply only names the method, the way other internal errors on the request path are reported.

Both questions from the issue are answered by the change: the stream interceptor is the primary home because it covers every handler on that server, and the `Process` defer stays as the fallback for callers that never go through the transport. The metric follows the existing gateway naming, pod-scoped with the `pod_name` label, since no constraint was recorded. A handler error is passed through unchanged rather than being rewritten as a panic.

Verified by:
- a real gRPC server with the interceptor registered: the stream whose handler panics ends with `codes.Internal`, and a second stream on the same server still runs;
- reverting the interceptor locally: the same test dies with the raw `panic: boom in Process`, which is the blast radius this PR removes;
- `go test ./pkg/plugins/gateway/... ./pkg/metrics/...`, `go test -race ./pkg/plugins/gateway/ ./pkg/metrics/`, `go vet` and `gofmt` clean.

Recovery is a last line of defense, not a replacement for fixing the defect, and it cannot catch runtime-fatal conditions such as concurrent map writes or OOM.

### cursor[bot] · 2026-09-22

The gRPC stream interceptor plus `Process` fallback is the right server-boundary shape, and the tests actually prove the blast-radius claim (second stream still runs; handler errors pass through; panic value stays out of the status). Defer order in `Process` is also right: recover is registered first so it runs last, and the existing in-flight/`finishRequestCount` defer still runs on the way out.

Gemini’s high-priority nil-ctx note is a false positive. `metricModelLabels` already returns empty strings for a nil `RoutingContext`, and `EmitMetricToPrometheus(nil, nil, …)` is used elsewhere. An empty `&types.RoutingContext{}` matches `GatewayRequestTotal` but is not required to keep recovery from panicking.

The important gap is the bugs this PR cites. `#2756` (`ModelGPUProfile.GetSignature`) and `#1284` (queue index) run in `queueRouter.serve()` — Peek/rank/`GetSignature` and the backend `Route` — not on the ExtProc stream goroutine. `queueRouter.Route` only enqueues and waits on `TargetPod()`. A panic there still kills the process; neither the interceptor nor the `Process` defer will see it. The interceptor is still worth landing for header/body/`selectTargetPod` panics. To cover the motivating SLO/queue crashes, recover inside the `serve()` loop (log + the same counter, `SetError` on the peeked ctx if any, keep looping). Same last-line-of-defense rule: it cannot catch concurrent map writes or OOM.

Nits: extra `pod_name` duplicates the default `gateway_pod` label the same way `GatewayRequestTotal` already does — fine for consistency, not required. Unary Health on this server is still unprotected; not the ExtProc path. Recovery is last-ditch, as the PR says.

## Code Review

This pull request introduces a gRPC stream interceptor and fallback recovery logic to gracefully handle panics on the request path in the gateway plugin, preventing a single panicking request from crashing the entire process. It also adds a new Prometheus metric to track recovered panics and includes comprehensive unit tests. The review feedback correctly identifies a potential nil pointer dereference in the recovery path when calling `metrics.EmitMetricToPrometheus` with a `nil` routing context, which could cause a secondary panic and crash the process. To address this, the reviewer suggests passing an empty `&types.RoutingContext{}` and using structured logging with `klog.ErrorS`.
