## 正文

## Pull Request Description

This change adds an opt-in `authoritativeRoutingPolicy` field to the existing `model.aibrix.ai/config` annotation.

When the policy is enabled, the model configuration becomes authoritative for request routing:

- The configured `defaultProfile` is used instead of an application-supplied named or `auto` `config-profile`.
- An application-supplied `routing-strategy` cannot override the configured routing strategy.
- An application-supplied `external-filter` cannot change the eligible Pod set.
- Gateway-generated routing information and request mutations are preserved internally.
- The gateway omits `routing-strategy`, `target-pod`, `target-pod-ip`, and `x-aibrix-config-profile` from the response.

The field defaults to `false`, so existing deployments retain their current request-header precedence and response behavior.

This complements the `lockedRoutingStrategy` support added by #2544. The existing field pins the routing algorithm, while `authoritativeRoutingPolicy` also protects profile parameters and replica selection from request-level overrides.

The change includes documentation and regression coverage for:

- Named and automatic configuration profiles.
- Default-profile routing parameters.
- Locked routing algorithms.
- Matching and nonmatching external filters.
- Preservation of gateway-generated routing information.
- Suppression of routing diagnostic response headers.
- Backward-compatible behavior when the policy is disabled.

## Design feedback

The operator-facing flag and the behavior look right. The implementation is doing the same lock in five places, and there is a simpler way to get there.

`authoritativeRoutingPolicy` is currently a second precedence path next to `lockedRoutingStrategy`. It is plumbed as a 4-tuple from `ResolveConfigPolicyForRequest`, copied onto `ResolvedConfigProfile`, then re-checked in profile selection, strategy derivation, `external-filter`, auto-profile response headers, and diagnostic suppression.

Most of that goes away if the flag only means: **treat the request as if the client did not send routing headers**.

### Simpler design

Keep the bool. After the model config is parsed in `applyConfigProfile` (the body phase, which is the first time pod annotations are available), neutralize the client inputs once:

```go
if cfg.AuthoritativeRoutingPolicy {
    routingCtx.ReqConfigProfile = ""
    delete(routingCtx.ReqHeaders, HeaderRoutingStrategy)
    delete(routingCtx.ReqHeaders, HeaderExternalFilter)
}
```

Then run the existing resolver unchanged. Empty `config-profile` already selects `defaultProfile`. Empty `routing-strategy` already falls through to the profile, then `lockedRoutingStrategy`, then `ROUTING_ALGORITHM`. Empty `external-filter` already means “do not shrink the pod set.” `config-profile: auto` never runs.

You still need the flag on `routingCtx.ConfigProfile` for **one** extra concern: omitting `routing-strategy`, `target-pod`, `target-pod-ip`, and `x-aibrix-config-profile` from the **client response**. Those headers are gateway-generated after routing, so they cannot be handled by stripping request headers. That is the only place a new branch is justified.

That removes:

- `ResolveConfigPolicyForRequest` and the extra return value
- the new branch in `deriveRoutingStrategyFromContext`
- the `externalFilter = ""` special case in `HandleRequestBody`
- teaching `ResolveConfigForRequest` about `auto` vs default under the flag

The docs example that sets both `lockedRoutingStrategy` and `authoritativeRoutingPolicy` also gets simpler: authoritative ignores the client; `lockedRoutingStrategy` stays the algorithm pin against the profile and the env. They are not substitutes, and they should not be implemented as two overlapping “always win” checks.

### What not to do

Do not fold this into `lockedRoutingStrategy`. #2544 is explicit that a locked algorithm still lets `config-profile` choose `routingConfig` / RPS. Changing that would break operators who pin `pd` but still expose batch vs online profiles.

Do not strip in `HandleRequestHeaders`. The model config lives on pods and is not known until the body phase.

A rename such as `ignoreClientRoutingHeaders` would match the simpler semantics, but it is optional; the bool is fine if the body-phase strip is the enforcement point.
