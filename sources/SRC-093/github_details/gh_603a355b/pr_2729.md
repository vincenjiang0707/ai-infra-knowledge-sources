## 正文

## What

Adds an explicit **Area** dropdown to all three Issue Forms (bug report,
feature request, RFC) and makes `classify_issue()` use it as the primary
source for the `area/*` label, falling back to the existing keyword regex
matching only when it's absent or set to "Not sure".

## Why

Closes part of #2714: "Issue labeling can still assign unrelated `area/*`
labels because the bot matches broad keywords across the entire Issue
body." For example, a bug report describing a runtime issue that also
happens to mention "CI failures" and a "helm upgrade" in passing currently
gets `area/runtime`, `area/cicd`, **and** `area/installation` all at once.

This implements two of #2714's proposed-direction bullets:
- Add an explicit Area field to Issue Forms.
- Use keyword matching only as a fallback for Issues.

I scoped this PR to the Issue-labeling half only. The PR-side of #2714
(area labels from changed file paths) is already handled by #2711's
path-based labeler (merged). The remaining bullets - default `kind/*`
labels baked into the forms themselves, an Area section on the PR
template, and reconciling labels from older bot versions - are
independent of this change and are better left for separate, smaller
follow-ups rather than one large PR.

## How

- `AREA_FORM_OPTIONS` maps each dropdown option to its existing
  `area/*` label (no new labels introduced), keyed by the same
  `_clean_heading()` normalizer already used for Issue Form section
  parsing, so punctuation in the option text (e.g. "CI/CD") doesn't
  need to match the submitted answer exactly.
- `classify_issue()` reads the Area section from the parsed body; if it
  resolves to a known option, that's the *only* area label applied. If
  not (no Issue Form, field left as "Not sure", or an issue filed
  before this change), behavior is 100% unchanged from today.
- This is purely additive - no existing classification changes unless a
  submitter opts into picking an area.

## Testing

Extended `--self-test` with two new cases and ran it locally:

```
$ python3 .github/scripts/aibrix-bot.py --self-test
AIBrix bot self-test passed
```

1. A bug report with an explicit `Area: Runtime` selection, whose body
   also matches the `cicd` and `installation` keyword patterns - asserts
   only `area/runtime` is applied.
2. The same body with `Area: Not sure` - asserts the original
   multi-label keyword-matching output is preserved unchanged
   (`area/runtime`, `area/cicd`, `area/installation`), confirming the
   fallback path has no regression.

Pure Python stdlib + GitHub Actions YAML, no OS-specific code - runs the
same on Linux/Mac/Windows and in CI (`ubuntu-latest`).
