## Pull Request Description

This PR implements the first four Gateway E2E follow-ups from #2708 using the shared backend recorder pattern from #2675.

It adds coverage for:

- the actual HTTP request body and headers received by ordinary and PD backends after Gateway processing;
- matching Gateway-selected target Pod headers against the Pod that actually receives the request;
- an initial backend 500 followed by a successful Envoy retry;
- backend timeout, refused connection, and final error-body propagation.

The backend assertions are isolated by request ID and queried through the Kubernetes Pod proxy. The development mock backend now supports deterministic, request-scoped failure attempts for retry testing.

A test-only Envoy route overlay configures a one-second timeout and one retry for `5xx`, connection failures, and resets. Production Gateway code and default production configuration are unchanged.

## Review

**Verdict:** Good coverage direction for the first four Gateway E2E follow-ups in #2708, and the mock `fail-attempts` / `backend` fault headers are useful. I would not merge yet: the shared test Envoy overlay has cluster-wide blast radius, the new recorder duplicates the existing framework API, and one PD failure test looks misaligned with what it claims to assert. Kind E2E was not run locally, so those risks are unverified.

### What works well
- Request-ID isolation via `traceparent` → gateway request ID → recorder filter is the right shape for parallel E2E.
- Mock changes preserve “always fail” when `x-aibrix-mock-fail-attempts` is omitted (`fail_attempts == 0`), and limit retries when set.
- Ordinary backend cases (body/header fidelity, retry-once, error-body after retries, timeout, refused connection) are coherent and well commented.
- Test-only Envoy overlay keeps production `config/gateway` defaults unchanged.
- Unit coverage for the new fault-header parsing and request-scoped fail attempts looks solid.

### Must address

1. **`config/test` Envoy overlay affects every Kind E2E install**

```yaml
timeout: 1s
retry_policy:
  retry_on: 5xx,connect-failure,reset
  num_retries: 1
```

`make` / CI apply `config/test`, so this is not scoped to the new tests. Concrete risks:
- Existing suites that assume a single upstream 500 (no Envoy retry) can see doubled recorder entries or different client statuses.
- Suites that hold a backend longer than 1s under the Envoy route (e.g. PD fail-fast decode hold of 10s while waiting on the client path) may start timing out at Envoy instead of exercising the intended gateway behavior.

Please either narrow the overlay, gate it somehow, or explicitly re-run the existing gateway E2E packages and call out what was verified. “Not run locally” is not enough given the shared config change.

2. **Duplicate recorder API — extend `framework/recorder.go` instead**

`test/e2e/framework` already has `MockRequestRecord`, `QueryMockRequests`, and wait helpers used by PD suites. This PR adds a parallel `BackendRequestRecord` / `BackendRequestRecords` / `WaitForBackendRequestRecords` stack that hits the same `/debug/requests` endpoint.

Prefer extending `MockRequestRecord` with `Headers` / `DelayMS` (and a wait-for-count helper) over a second type and query path. That keeps #2675’s shared recorder as the single E2E contract.

3. **`TestPDPrefillConnectionFailureIsPropagated` looks misnamed / weaker than the ordinary analogue**

- It asserts `"error on selecting target pod"` (gateway routing selection path in `gateway_req_body.go`), not an Envoy/upstream connection failure with `target-pod` still set like `TestOrdinaryBackendConnectionFailureIsPropagated`.
- It reuses one `requestID` across `Eventually` polls; the ordinary test correctly mints a new ID per attempt.
- It never asserts that the refused connection did not reach the recorder.

If the intent is “PD routing fails after the port label changes,” rename and assert that. If the intent is connection failure propagation, align it with the ordinary test’s expectations.

### Should fix

4. **Pod label updates should use `retry.RetryOnConflict`** — agreed with Gemini here. The rest of `test/e2e` already does this; Get→Update without retry is a flaky source, including in `t.Cleanup` restores.

5. **Empty/`None` request ID + `fail-attempts`** — Gemini’s point is real for manual/non-E2E use: `count(request_id=None)` aggregates every ID-less record, so attempt budgeting leaks across requests. E2E always sets IDs, so not a blocker for these tests, but worth failing closed (treat missing ID as “always fail this attempt” or reject `fail-attempts` without a request ID).

6. **#2708 checklist** — the issue asks follow-ups to check off covered cases in the PR description or an issue comment. Please mark the four claimed E2E items so the help-wanted list stays accurate.

### Nits
- Substantial helper duplication between `gateway/pd` and `gateway/routing` (`headerValue` / `ordinaryRecordHeader`, label mutators, response wrappers). Fine for a first pass; consider sharing later.
- `BackendRequestRecord.Sequence` is `int64` while `MockRequestRecord.Sequence` is `int` — another reason to consolidate types.
- No startup/docs note that Kind E2E now depends on a 1s route timeout for the timeout cases.

### Recommendation
Request changes: consolidate onto the existing framework recorder, fix or clarify the PD connection-failure test, and prove the shared 1s/retry Envoy overlay does not regress the rest of the gateway E2E suite (or narrow it). The mock fault-header work and ordinary backend coverage are otherwise in good shape.
