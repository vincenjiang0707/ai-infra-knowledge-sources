## 正文

## Pull Request Description

Adds the namespaced `model.aibrix.ai/v1alpha1` `ModelWarmup` API for preloading container images onto explicitly selected Kubernetes nodes.

- supports explicit node names and label selectors with union/deduplication and source reporting
- creates safe, node-pinned Jobs with configurable image pull policy, parallelism, timeout, retries, TTL, and pull secrets
- reports per-node diagnostics, aggregate status, mutually exclusive Ready/Progressing/Degraded conditions, and deterministic revisions
- adds mutating/defaulting and validating admission webhooks
- includes generated clients/CRD/RBAC/webhook manifests, samples, and user documentation
- adds unit, controller/webhook integration, and live-cluster E2E coverage for success, selector expansion, image cache reuse, admission, and failure paths

## Design feedback: easier alternative

The operator goal in #2560 is right: get these images onto these nodes before scale-out, with Kubernetes status as the verify-before-rollout gate. A standalone CR is still the right object (do not fold this into StormService).

The implementation is heavier than that MVP. It rebuilds “one pod on every matching node” with per-node Jobs, a target-union model, revision hashing, parallelism, a global timeout, required per-image commands, per-node status, and three exclusive conditions. Kubernetes already has that primitive: a DaemonSet.

### Simpler v1

Keep a small `ModelWarmup` CR and have the controller create **one** DaemonSet:

```yaml
apiVersion: model.aibrix.ai/v1alpha1
kind: ModelWarmup
metadata:
  name: qwen-image-warmup
spec:
  nodeSelector:
    matchLabels:
      resource-pool.aibrix.ai/name: latency-pool
  images:
  - registry.example.com/vllm@sha256:...
  imagePullSecrets:
  - name: registry-secret
```

DaemonSet shape:

- one container per image
- default command `["sleep", "infinity"]` (override the inference entrypoint; request no GPU)
- tolerate taints, `IfNotPresent`, configured pull secrets
- status from the DaemonSet: desired / ready / unavailable

Selector expansion for later scale-out is free. Deleted pods come back. `NumberReady == DesiredNumberScheduled` is the rollout gate.

A sleeping container also **pins** the image. The Job path exits, then kubelet GC can evict the cache — the docs already call that a point-in-time observation. For warmup, pinning is the better default.

### Drop from v1

- `targets[]` with per-entry `nodes` vs `nodeSelector`, union, and source reporting
- required `command` on every image (controller default is enough)
- `imagePreload` wrapper and `policies` (parallelism, global timeout, retry, TTL)
- SHA revision of the Job template
- one Job per node (and the 63-char name collision Gemini flagged)
- per-node status array; `kubectl get ds/pods` is the per-node view until someone needs it
- webhook defaulting that only copies constants (use CRD defaults / CEL)

Keep CEL for “at least one image” and a non-empty selector. Workload refs (`StormService` / `RoleSet`) stay out.

Explicit node names can wait: label the nodes, or add a later `nodeNames` that becomes required nodeAffinity. Mixing names and selectors in v1 is what forces the union machinery.

### What not to do

Do not keep Jobs just for “completion.” A DaemonSet’s ready count is the completion signal; backoff is kubelet restart. Jobs are for one-shot work that should disappear. Warmup wants the opposite: stay scheduled on the pool.

If you really want pull-and-leave, make that a later `spec.mode: Once` that uses Jobs. Don’t start there.

The Gemini Job-failure / name-truncation / zero-node issues mostly vanish if there is no per-node Job.

### cursor[bot] · 2026-09-22

## Design check (HEAD 86793445)

Gemini's JobFailed / name-truncation / zero-node fixes landed. The API and execution model did not: this is still a per-node Job controller with a nested spec. I would not freeze this `v1alpha1` shape.

### Prefer one DaemonSet, not N Jobs

The operator goal is "these images are on this pool before scale-out." Kubernetes already has "run this pod on every matching node": a DaemonSet.

Jobs are the wrong default lifecycle:

- They complete and TTL away (`ttlSecondsAfterFinished: 3600`).
- The docs already admit the result is a point-in-time observation because kubelet GC can evict the image.
- For warmup, **pinning** (`sleep infinity`, no GPU) is the useful default. Pull-and-leave can be a later `spec.mode: Once`.

A thin CR that owns one DaemonSet also gives selector expansion, pod replace-on-delete, and `NumberReady == DesiredNumberScheduled` as the rollout gate. Dropping workload refs from v1 is the right cut.

Issue #2560 preferred Jobs over a *bare Pod* for retry/completion. That objection does not apply to a DaemonSet: kubelet restart is retry, ready count is completion, and the object is meant to stay.

### Freeze a small API

Shipping this spec as-is makes the nested shape a compatibility surface. Flatten v1 to:

```yaml
spec:
  nodeSelector:
    matchLabels:
      resource-pool.aibrix.ai/name: latency-pool
  images:
  - registry.example.com/vllm@sha256:...
  imagePullSecrets:
  - name: registry-secret
```

Drop from v1:

- `targets[]` union of names + selectors + source reporting
- `imagePreload` wrapper (that reserves stage slots the MVP said are out of scope)
- required per-image `command` / `args` (controller default)
- `policies` (parallelism, global timeout, retry, TTL)
- SHA revision of the Job template
- per-node `status.targets` (etcd-sized; `kubectl get ds/pods` is the node view)
- `Failed` phase, which is defined and never written

Keep CEL for a non-empty selector and at least one image. Explicit `nodeNames` can wait; mixing names and selectors is what forces the union machinery. If Jobs are kept anyway, still flatten the spec.

### Other design issues on this HEAD

1. **Selector expansion is polled, not watched.** `#2560` wanted newly labeled nodes to pick up work. The controller `For`s ModelWarmup and `Owns` Jobs, then `RequeueAfter: 15s`. Nodes are listed in-band but never watched, so scale-out warmup waits on a timer and idle CRs churn status forever. A DaemonSet (or a Node watch) is the actual expansion mechanism.

2. **`NodeName` + `TolerationOpExists` is cluster-scoped scheduling from a namespaced CR.** Any namespace that can create `ModelWarmup` can bind a pod to an arbitrary node, including control-plane, and tolerate every taint. Use required nodeAffinity from a selector, default only the taints a GPU pool actually needs, and/or an opt-in node label.

3. **Global timeout + `parallelism` starves later nodes.** `ActiveDeadlineSeconds` is set to the *remaining* workflow timeout. Lexicographically later nodes wait behind `parallelism: 8` and then inherit leftover time.

4. **Revision hashes operational knobs.** Changing TTL / parallelism / timeout recreates every Job. Revision should be the image identity (and pull secrets), not scheduler policy.

5. **Succeeded is not durable, and Degraded is terminal.** One missing or failed node flips the whole CR to Degraded, sets `completionTime`, and `isTerminalPhase` treats that as done. Combined with TTL, the object can look finished while the pool is only partly warmed and successful images are eligible for GC. If status is the verify-before-rollout gate, Ready should mean "currently pinned on the matched set," not "Jobs once exited 0."

6. **Mutating webhook writes defaults into spec.** `Default()` materializes parallelism / timeout / retry / TTL, so later default changes cannot land. Use CRD defaults / `omitempty`.

7. **Required `command` is an operator footgun.** Distroless vLLM images often have no `sh`. The controller should override the entrypoint. For pin mode that is `["sleep","infinity"]`, not a user-supplied shell snippet.

8. **No resolved digest in status.** Tags can move under `IfNotPresent`. Require `@sha256:` in admission, or record the pulled digest.

Tests are thorough for the Job model. The model is still heavier than the MVP.

## Follow-up on the proposed Once / Jobs plan

The finite-snapshot choice is coherent. I will not keep pushing DaemonSet for this PR if `Once` is the v1 contract.

Accepted as stated: spec immutability, Node watch with skip-on-terminal, per-Job `jobTimeoutSeconds`, no catch-all `NodeName`/toleration, controller-side policy defaults, compact per-node diagnostics.

Remaining bar if Jobs/`Once` stay:

1. **Do not sell Succeeded as scale-out coverage.** Terminal Once ignoring later nodes means autoscaler-added nodes stay cold. Document that, and name `Continuous` (or a pin mode) as the scale-out path.
2. **TTL + kubelet GC still undoes the snapshot.** Either retain Jobs until the CR is deleted, or document that Ready is not durable.
3. **Keep v1 authorization as one opt-in node label** plus reject control-plane. Do not add namespace→node IAM in this PR.
4. **Drop the `imagePreload` wrapper** (`spec.images` + `spec.policies` is already grouped). Default the pull command in the controller; distroless vLLM images often have no `sh`.
5. **Cap status size**, not only field width: full detail for failed/pending nodes, counts for succeeded, plus a serialized-size test.
6. **Require digest or record the resolved one.** Tags plus `IfNotPresent` make Succeeded unreproducible.

The implementation nits (poll, remaining-budget timeout, webhook-materialized defaults, hard-bind) look addressed in the plan. The product hole is still treating a completed, TTL-expired Job as a warm pool.

## Re-check of `8bf1932d` (review-feedback commit)

The Once snapshot contract is now explicit, and most of the implementation nits landed. I would not keep blocking on DaemonSet.

**Landed**

- Immutable spec; `mode` is Once-only
- Node watch; terminal Once is not enqueued
- Per-Job `jobTimeoutSeconds`; revision no longer hashes policies
- Required node affinity instead of `NodeName`; no catch-all taint
- Opt-in `model.aibrix.ai/warmup-enabled=true`; control-plane excluded
- Controller-side policy defaults; mutating webhook removed
- Pending/failed details only, compact source, `OmittedTargetDetails`
- Docs: selector expansion only while running; Continuous is future; cache is not durable
- `Complete` (not `Ready`) for a finished Once; `Failed` is actually used

**Still blocking for a GPU warmup API**

1. **Zero tolerations will not schedule on typical GPU nodes.** Removing `TolerationOpExists` was right; shipping an empty toleration list is too far. `nvidia.com/gpu` / dedicated-pool NoSchedule taints are the common case. Copy the *target node's* taints onto that Job (or a small allowlist). Do not restore a cluster-wide exists-operator.

2. **Namespace↔node pool equality is extra IAM.** Opt-in + not-control-plane was enough. Requiring `resource-pool.aibrix.ai/name` on the *namespace* to match the node means a CR in `default` / `aibrix-system` cannot warm `latency-pool` unless that namespace is labeled as the pool. The sample is `namespace: default` with a pool selector and will fail authorization as written. Either drop the namespace pool check, or put ModelWarmup in a namespace that is the pool (and fix the sample).

**Still open, not merge-blocking if documented**

- Required per-image `command` still fails distroless vLLM images. Default it in the controller.
- `imagePreload` wrapper is still unused staging. `spec.images` + `spec.policies` is enough.
- Tags remain allowed; Succeeded is unreproducible without a digest.
- Default TTL 3600 is acceptable only because the docs now say the cache is not durable. Do not treat `Complete` as a long-lived rollout gate.
- Truncating `status.targets` by node name can drop failures and keep pending. Sort failed first, then pending, then omit.

The product hole that remains is operational: a Once Job that cannot tolerate GPU taints, and an authorization rule that the sample itself does not satisfy.
