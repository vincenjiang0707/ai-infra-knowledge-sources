### cursor[bot] · 2026-09-14

**Request changes.** This correctly blocks the selector/template mismatch from #1423, but it still lets a Fleet drop its own children, and Go lint is failing on this PR.

The create-path check, webhook wiring (controller, envtest, kustomize, Helm), and the distinction between RayCluster template labels vs head/worker Pod labels all look right. I would not merge until the items below are addressed.

### Blockers

1. **`spec.selector` is still mutable.** `ValidateUpdate` ignores `oldObj` and only re-checks that the *new* selector matches the *new* template. Changing both in one update orphans existing `RayClusterReplicaSet`s / `RayCluster`s — the same class of leak as #1423. Kubernetes Deployments make the selector immutable for this reason. Please compare `oldObj` vs `newObj` (prefer `equality.Semantic.DeepEqual`) and add unit + integration tests that change selector *and* template labels together so the current match check would otherwise pass. This matches @googs1025's request.

2. **Expression-only selectors are accepted, but the ReplicaSet controller cannot use them.** The webhook uses `LabelSelectorAsSelector`, and the new tests encode `matchExpressions` as supported. `RayClusterReplicaSetReconciler` lists with `client.MatchingLabels(replicaset.Spec.Selector.MatchLabels)` only. Empty `MatchLabels` is `labels.Everything()`, so an expression-only Fleet copies that selector onto the ReplicaSet and then lists every RayCluster in the namespace. Until the ReplicaSet reconciler uses the full selector, reject `matchExpressions` (or require non-empty `matchLabels` and document that expressions are ignored). Do not add tests that treat expressions as a supported Fleet API.

3. **Go lint is failing on this PR.** Two `lll` violations in `test/integration/webhook/rayclusterfleet_webhook_test.go` (124 > 120). Wrap those `gomega.Expect` lines.

### Already discussed

`failurePolicy=Ignore` is consistent with the other AIBrix webhooks; I agree with keeping it. The docs line “With webhooks enabled…” is the right caveat. Existing mismatched Fleets are not repaired, which is fine: there is no Fleet finalizer, so delete still works via owner refs.

### googs1025 · 2026-09-14 · COMMENTED

  Could we make `spec.selector` immutable during updates by comparing `oldObj` and `newObj`?

  `ValidateUpdate` currently ignores `oldObj`, so a user can change both the selector and the template labels in the same update. Existing RayClusterReplicaSets and RayClusters still carry the old labels, while the Fleet controller starts listing resources with the new selector. Those existing resources then become invisible to the Fleet and may be left orphaned/ unmanaged, reintroducing the same class of resource-leak issue described in #1423.

  This should behave similarly to a Kubernetes Deployment, where the selector is immutable. Please consider adding unit and integration tests covering an attempted selector change.
