### Pull Request Description

Issue #2288 asks the autoscaler to drive elastic expert parallelism for MoE serving, and asks to start observe-only before acting on it. This PR is that first step on the read side. The custom autoscaling path records the observed engine scaling state in the PodAutoscaler status and changes no replica decision.

The engine answers `POST /is_scaling_elastic_ep` with a boolean. While a scaling commit is in flight the engine answers every HTTP request with a 503 whose body says the model is currently scaling, so the probe maps that response to scaling as well. The DP coordinator wave state stays inside the engine process and has no HTTP surface today, so this step observes the endpoint only.

On each reconcile of the custom autoscaling path used by KPA and APA, the controller:

- selects the engine pods of the scale target that are ready, have an IP, and enable elastic EP on the command line through `--enable-elastic-ep` or `--elastic-ep-max-dp-size`
- resolves the engine ports the way the gateway does, the `model.aibrix.ai/port` label with the data parallel size first, then `--port`, `VLLM_PORT`, and the declared container ports
- probes the endpoint with a 2 second timeout per probe, at most 8 probes in flight, and a 3 second budget for the whole observation
- records the aggregate in `status.elasticEPScaling`, which carries `inProgress`, `observedEngines`, `scalingEngines`, and `lastTransitionTime`

The deliberate choices worth reviewing:

- An engine that does not answer is not counted. When no engine reports a state, the observation returns nothing and the previous status is kept, so a timeout never reads as not scaling.
- `lastTransitionTime` moves only when `inProgress` changes, so a steady state does not rewrite the status on every reconcile.
- Pods that do not enable elastic EP are never probed, so the observation adds no traffic for targets that do not use it.
- Enablement through a vLLM config file is not detected, only the command line flags.
- The HPA path is untouched and no scaling behavior depends on the new field yet. Acting on the state is the next step of #2288.

## Design simplification

Keep one pod list, one port, and three observation results.

### Simpler structure

List the scale-target pods once, with `getPodsForScale`, and pass that slice into the metric computation and into the observation. The observation returns one of three results:

- No selected pod enables elastic EP: clear `status.elasticEPScaling`.
- At least one selected pod did not answer: leave the previous status.
- Every selected pod answered: merge the counts, and move `lastTransitionTime` only when `inProgress` changes.

Select a pod that has an IP and the CLI flag. Readiness is a poor filter for a signal produced by the 503 that fails readiness. Probe one port per pod. Use the `model.aibrix.ai/port` label when it is set. Otherwise use `--port`, then `VLLM_PORT`, then the first container port.

### Cut

- The data-parallel port list from `GetPortsForPod` and the loop in `probeElasticEPTarget`. Elastic EP publishes this flag on the API server. The extra ports are the routing fan-out. They spend the 3s budget on connection timeouts, and an idle answer on one port covers a miss on another.
- The second LIST inside `observeElasticEPScaling`.
- `defaultElasticEPProber`. `newReconciler` already stores the client on the reconciler. Tests can set that field.
- Publishing `inProgress: false` from a subset of the selected pods.

### Keep

- The status type, the CRD and generated deepcopy and apply configuration, and the three status constructors copying the field.
- The CLI gate (`--enable-elastic-ep`, `--elastic-ep-max-dp-size`) so other targets do no HTTP. Config-file enablement can stay out of this step.
- `POST /is_scaling_elastic_ep`, the 200 boolean, and the 503 body marker restricted to status 503.
- The 2s probe timeout, the 3s observation budget, and the 8-wide cap.
- `lastTransitionTime` moving only with `inProgress`.
- The probe matrix, the merge table, and the status carry-through tests. Add the NotReady, clear-on-disable, and partial-miss cases beside them.
- HPA left off this path. Replica math stays independent of the field until a follow-up of #2288 acts on it.

## Code review

The observe-only wiring sits in the right place. `reconcileCustomPA` records `status.elasticEPScaling` after the replica decision, and KPA/APA replica math ignores the field. The probe matches the two responses current vLLM produces while idle and during a scaling commit. The way pods are chosen and the way partial answers are folded will record the wrong `inProgress` bit once a later change starts acting on this field.

### Correctness

vLLM `ScalingMiddleware` answers every HTTP request with 503 and `The model is currently scaling. Please try again later.` while a scaling commit is in flight. That includes `/health` and `POST /is_scaling_elastic_ep`. The middleware runs before the route, so the 200 body `{"is_scaling_elastic_ep": true}` does not come back during the commit. `probe` maps that 503 body to scaling, and it accepts the marker only on status 503 (`elastic_ep.go` lines 139–145). A 429 with the same sentence stays unavailable. The matrix test covers both.

`observeElasticEPScaling` then skips any pod that fails `IsPodReady` (line 261). The same 503 fails the kubelet readiness probe, so the API pod is the pod most likely to be NotReady for the whole commit. vLLM elastic EP currently serves one API server (`api-server-count` 1). With default readiness (three failures, 10s apart) there is a short window while the pod is still Ready. The autoscaler resyncs every 10s (`DefaultResyncInterval`), so a reconcile can land in that window, get the 503, and set `inProgress: true`. A faster readiness probe, or a reconcile that lands after the pod is already NotReady, builds an empty target list and returns nil (line 276). `reconcileCustomPA` assigns the field only when the observation is non-nil, so the stored value stays `inProgress: false`. The commit never appears in status.

A partial answer has the same shape. Engines that time out are omitted, and `inProgress` is `scalingEngines > 0` over the engines that answered (lines 318–323). One idle response plus one timeout becomes `inProgress: false` and overwrites a previous true. The all-miss case is the one that keeps the previous status. The mixed case clears it.

That nil return also covers a target that no longer has an elastic-EP pod: the flag removed, scale to zero, or the pod list error logged at V(4). `setStatus`, `computeStatus`, and `setInvalidSpecStatus` copy the old pointer forward. `inProgress: true` stays on the object after the engines are gone. `reconcileHPA` updates PodAutoscaler status in place, so a switch from KPA/APA to HPA keeps the last observation and never refreshes it.

A 200 body with the field absent decodes as idle. `json.Unmarshal` into a `bool` leaves the zero value, and `TestElasticEPProber` names that case idle. vLLM’s handler always sends the field. Any other 200 body without it is recorded as “not scaling”, which is the outcome `probe`’s comment reserves for an unusable response.

`getPodsForScale` still adds the RayClusterFleet `ray.io/node-type=head` requirement, and role selectors still come from `GetPodSelectorFromScale`. Replica decisions are unchanged.

### Risks

The observation uses the reconcile context. `Reconcile` caps that context at `DefaultReconcileTimeoutDuration` (10s). The probe runs after `SetDesiredReplicas` and before `updateStatusIfNeeded`, with a 3s child budget. A slow metric pass can leave the status write on a cancelled context. The scale has already been applied. The following reconcile writes the status.

Every KPA/APA reconcile lists pods twice. `computeMetricBasedReplicas` lists them, then `observeElasticEPScaling` lists them again. Targets without the flag do no HTTP, and they still pay the second LIST. When one engine alternates between timeout and idle, `observedEngines` changes while `inProgress` stays the same. `lastTransitionTime` stays put, the counts differ, and `Semantic.DeepEqual` writes status on every 10s resync.

The request is plain `http://podIP:port` with an empty body and no API key. That matches the existing direct pod metric fetch. An engine that requires a key answers 401, the probe treats it as unavailable, and the status stays at the previous value for as long as every probe fails.

### Tests

The new tables cover the response matrix, the port resolution order, multi-port fallthrough, aggregation against a fake client and live test servers, transition-time rules, and carry-through of the field in `setStatus`, `computeStatus`, and `setInvalidSpecStatus`. The per-index writes are safe: one goroutine per target, and the read happens after `Wait`.

These cases are still open:

- A NotReady pod with the flag and a 503 body that contains the marker.
- Elastic EP removed from the target, with the status cleared.
- Two selected engines, one idle and one timed out, with a previous `inProgress: true` left in place.
- `reconcileCustomPA` writes the field. The helper tests still pass if that call site is removed.

The 3s budget and the 8-wide cap have no test. I reviewed the diff and the controller on main. I did not re-run `go test ./pkg/controller/podautoscaler/...`.

### API and compatibility

`status.elasticEPScaling` is an optional pointer on `PodAutoscalerStatus`. `inProgress` is a required bool. A missing object and `inProgress: false` stay different values. Deepcopy, both CRD copies (`config/crd` and `dist/chart`), and the apply configuration include the type. There is no printer column, webhook, or HPA spec change. Old clients ignore the field. v1alpha1 still means the JSON name `elasticEPScaling` and the 503 marker become compatibility surface once a release ships them.

`observedEngines` and `scalingEngines` use `omitempty`. An idle observation stores `scalingEngines: 0`, and JSON omits it. Drop `omitempty` on those two counters before release so a successful observation always shows both numbers. Leave `omitempty` on `lastTransitionTime`.
