## 正文

**Title:** [Bug] Scope StormService RoleSet lookups to the owning StormService

## Pull Request Description

Fixes #2779.

`getRoleSetList` listed RoleSets using only the user-supplied selector — no namespace restriction and no ownership check. `sync` (deciding how many to create), `rollout`, `finalize` (cleanup on delete) and `revision` all call it, so a StormService treated every RoleSet in the cluster whose labels happened to match as its own.

Two namespaces sharing a selector label doesn't take a misconfiguration: `samples/quickstart/pd-model.yaml` and `samples/disaggregation/vllm/1p1d.yaml` both use `app: vllm-1p1d`, both use the same object name, and neither pins a namespace, so two people each running the quickstart in their own namespace collide. What I saw on kind: the one created second brought up no RoleSets at all (the lookup already returned two), yet reported `replicas=2 ready=2`; deleting it made its finalize delete the other namespace's RoleSets, which that controller then recreated — 16 deletions and 25 Pod kills over two minutes — while its own deletion never completed.

The fix passes the StormService in, restricts the list to its namespace, and then keeps only the RoleSets it controls. Namespace scoping closes the cross-namespace case; the owner check handles overlapping selectors inside one namespace, which still reproduces once the namespace restriction is in place — I tried it, and the StormService created second owned zero RoleSets with 8 rebuilds in 60 seconds.

The reasoning: RoleSets are namespaced, their ownerReferences have pointed at the StormService in the same namespace since the controller was introduced (`e3bb459a`), the ControllerRevision and RayClusterFleet lookups already scope by namespace, and `IsControlledBy` is already used in `rayclusterfleet`.

## One thing I'd like you to decide

A RoleSet without a controller reference is now skipped and logged at V(4) rather than adopted.

The cost is that if a RoleSet ever loses its ownerReference, the controller won't take it back — it creates a new one and the old object stays around forever. Before this change, label matching picked such an object up implicitly.

I lean towards skipping, since `renderRoleSet` has always set the reference and an orphan can only come from a hand-made object or one that had its reference stripped. Doing proper adoption the way the ReplicaSet controller does is also an option, it's just a larger change. Your call.

Related to that: the existing `TestScalingPooledModeNeverCreatesSecondRoleSet` broke with this change, because its fixture builds RoleSets without an ownerReference, so the new logic filtered them out and the controller created another one. I gave the fixture an ownerReference to match what `renderRoleSet` actually does. It's a concrete example of the trade-off above.

## Tests

`TestGetRoleSetList` is rewritten with seven cases: nil and invalid selector, an owned RoleSet is returned, matching labels in another namespace are excluded, matching labels owned by another StormService in the same namespace are excluded, an orphan is excluded, and a mix returns only the owned ones.

Two more:

- `TestGetRoleSetListRestrictsTheListToTheNamespace` uses an interceptor to assert the List call carries the right namespace. I added it because the cases above don't actually pin the namespace restriction — drop `InNamespace` and they still pass, since the owner filter happens to hide the cross-namespace object too.
- `TestFinalizeOnlyDeletesOwnedRoleSets` (in `sync_test.go`) runs finalize twice: the first pass deletes its own RoleSet and reports it isn't done, the second removes the finalizer, and the other namespace's RoleSet is untouched throughout.

What I ran:

```
go test ./pkg/controller/stormservice/ -skip TestControllers    all pass
golangci-lint v2.13.1                                           0 issues
```

`TestControllers` doesn't run on my machine — the envtest etcd binary is missing — and it fails the same way on unmodified code.

I mutated the fix twice to check the tests hold: dropping `InNamespace` fails the interceptor test, and dropping the owner filter fails three cases in `TestGetRoleSetList`.

Also verified end to end on a cluster, with a controller built from this branch, across three scenarios:

Two StormServices with the same selector in one namespace each own 2 RoleSets, with zero rebuilds over 60 seconds (before the change the second one owned zero and there were 8 rebuilds in 60 seconds). Deleting one leaves the other's RoleSet UIDs unchanged with zero Pods killed, and the deleted one completes immediately.

Cross-namespace, following the reproduction steps from the issue: team-a and team-b each create 2 RoleSets, and after deleting svc-b the UID hash on team-a's RoleSets doesn't change for 40 seconds, with 0 deletions and 0 Pods killed.

The environment is a single-node kind v1.30.0 with lightweight containers standing in for the workload and no GPU — this path is in the control plane's resource listing and doesn't involve the inference engine.

## Design review

Namespace + `IsControlledBy` is the right fix for #2779. A label selector is not an ownership claim, RoleSets are namespaced, and `finalize` deleting whatever the list returns is how one StormService killed another namespace’s Pods. Matching RayClusterFleet, ControllerRevision, and the ownerReferences `renderRoleSet` has always set.

This should land. The remaining design choice is **what to list before the owner filter**, not whether to own.

### List by controller identity, not the user selector

`getRoleSetList` still does `MatchingLabelsSelector{stormService.Spec.Selector}` then `IsControlledBy`. That mixes two different questions: “which RoleSets did the user describe?” vs “which RoleSets does this object own?”

`spec.selector` is a create-time constraint (`renderRoleSet` already rejects a template that does not match). It is a bad membership index:

- Samples share `app: vllm-1p1d`. Two StormServices in one namespace with that selector is a supported shape after this PR; the owner filter saves you, but the List still returns the peer’s objects on every reconcile.
- An owned RoleSet whose labels drift, or a selector update, disappears from scaling, status, **and finalize**. Delete then leaks RoleSets/Pods. That is the dual of the original bug.
- The controller already stamps a unique identity: `storm-service-name=<StormService.Name>` (also the headless Service selector and `status.scalingTargetSelector`).

I would make ownership the list contract, as @varungup90 suggested:

```go
r.List(ctx, list,
  client.InNamespace(stormService.Namespace),
  client.MatchingLabels{constants.StormServiceNameLabelKey: stormService.Name},
)
// then keep metav1.IsControlledBy
```

Or list all RoleSets in the namespace and filter `IsControlledBy` only — complete, no label dependency, cheap at StormService scale. Either is better than the user selector. Keep `spec.selector` on the create/render path only.

That also makes the interceptor test unnecessary: the behavioral cases already encode “owned in this namespace; not foreign, not other-NS, not orphan.”

### Do not adopt orphans in this PR

Skipping ownerless RoleSets is the correct bugfix default. Label-matched adoption is how the old code treated someone else’s objects as its own. ReplicaSet-style `ControllerRefManager` adoption is a separate lifecycle policy (agree with the PR body and @varungup90).

I would **not** take Copilot’s “delete matching orphans in finalize.” Finalize deleting every RoleSet that happens to match `app: vllm-1p1d` is the original cross-object delete, just in-namespace. If a later change wants orphan GC, key it off `storm-service-name` (controller-stamped) plus “no controller or this controller,” never off the user selector.

A stripped `ownerReference` then leaking until manual delete is acceptable for v1 of this fix; log those skips louder than V(4) so they are not invisible.

### Tests

The table plus `TestFinalizeOnlyDeletesOwnedRoleSets` cover the actual failure (cross-NS delete loop). Assert `Get` of the deleting StormService instead of `if err == nil` (Gemini). If you switch the List key to `storm-service-name`, add one case: owned RoleSet whose labels no longer match `spec.selector` is still returned — that is the leak the selector list would still have.

Not blocking: `nil` StormService check is defensive noise; callers always pass the reconciled object.

## Code review

The namespace + `IsControlledBy` filter is wired through every caller (`scaling`, `rollout`, `updateStatus`, `truncateHistory`, `finalize`). That is the right surface. A few implementation issues:

**`getRoleSetList` still keys the List on `spec.selector`.** After the owner filter this is no longer just extra work. An owned RoleSet that does not match the selector (label drift, selector edit) is omitted from `finalize` and `truncateHistory`: delete leaves RoleSets/Pods, and live revisions can be GC’d while RoleSets still reference them. `renderRoleSet` already stamps `storm-service-name`. Use that (or namespace + `IsControlledBy` only) as the List key; keep `spec.selector` on create. Same point as the design thread, with a concrete leak on this path.

**`selector == nil` now fails the whole lookup.** `finalize` treats any error as retry (`RequeueAfter`). A deleting StormService with a nil selector never drops its finalizer. If you keep the selector on this path, treat nil the same as “no RoleSets” during deletion, or list by `storm-service-name` so finalize does not depend on it.

**Skipped RoleSets are logged at V(4).** Default verbosity will not show an orphan or a stripped `ownerReference`. Use `klog.InfoS` (include namespace/name/uid). `Owns(&RoleSet{})` will also never enqueue the StormService for an ownerless object, so reconcile will not notice it later.

**`TestFinalizeOnlyDeletesOwnedRoleSets` swallows `Get` errors.** `if err == nil { assert.NotContains(...) }` lets a failed finalizer patch pass. Assert `NoError` on `Get` (Gemini). The fake client does not garbage-collect the StormService when the finalizer is removed, so `Get` should succeed.

**`pooledRoleSet` builds the owner ref from a fresh `newPooledStormServiceWithSurge(2)`.** It works only because that helper hard-codes `UID: pooled-storm-uid`. Pass the test’s StormService in, or the next UID change silently recreates the “fixture without owner” failure this PR fixed.

Nits: `klog.Errorf` on List then `return err` double-logs with `finalize failed`. `%v` on the selector parse should be `%w`. The `stormService == nil` guard is dead. The interceptor test is fine until the List key changes; after that the behavioral table is enough.

I would not add ReplicaSet-style adoption or “delete every selector-matched orphan in finalize” in this change. That is how the original cross-object delete happened.

### varungup90 · 2026-09-23 · COMMENTED

The overall direction makes sense — RoleSet ownership should be scoped to the StormService rather than inferred only from a potentially overlapping user selector.

One simplification question: now that `getRoleSetList` takes the `StormService` and explicitly checks `IsControlledBy`, do we still want the StormService selector to participate in determining which RoleSets belong to it?

Conceptually, it may be cleaner if the invariant is simply:

`getRoleSetList(stormService)` → all RoleSets controlled by this StormService in its namespace.

That would make Kubernetes ownership the single source of truth and avoid mixing selection semantics with ownership semantics. If listing all RoleSets in the namespace is a scalability concern, we could eventually add/index a controller-owned label for efficient lookup.

I would also keep orphan adoption out of this bug fix. Whether an ownerless RoleSet should be adopted/recovered is a separate lifecycle policy and can be handled independently rather than reintroducing implicit ownership through selector matching.

On the tests, I think we can potentially simplify them around the behavioral invariant: owned RoleSets are returned; RoleSets owned by another StormService, in another namespace, or without ownership are not. The interceptor test that specifically verifies `InNamespace` feels somewhat implementation-specific if the behavioral isolation cases already cover the contract.
