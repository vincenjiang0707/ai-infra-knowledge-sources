## 正文

## Pull Request Description
Deleting one workload (Deployment, ModelAdapter, Fleet) removed the shared per-model HTTPRoute even while other workloads still served the model, causing 503s until a controller restart. `deleteHTTPRoute` now checks for remaining workloads serving the same model across all namespaces before deleting, mirroring the existing ReferenceGrant guard but model-specific and cluster-wide. On list failure the route is kept: an orphaned route is cheaper than an outage.

## Design simplification

Keep one scanner. `namespaceHasModelWorkload` already lists Deployments, ModelAdapters, RayClusterFleets, and `watchedWorkloads`, and it already treats NoMatch as absent and any other list error as an error. Give it a model-name argument. An empty model name preserves today's grant behavior (any model in that namespace). The route call passes the deleted workload's namespace and its model name. That is the #2824 fix: both heterogeneous deployments live in `default`.

Keep the fail-closed rule, `ModelNameFromMetadata`, and the NoMatch continue. Keep `deleteReferenceGrant` after the route decision on every path, whether the route was kept, deleted, or spared because a list failed.

Cut `modelHasRemainingWorkload`. It repeats the four loops, the logs, and the NoMatch branch, and it drops the namespace. Cut the cluster-wide List. The route's backend is one namespace; a hit in another namespace neither proves this Service still has endpoints nor allows the grant in the emptied namespace to be removed. Retargeting `backendRefs` when the owning namespace is gone is a separate change. Cut the `deletionTimestamp` filter suggested on the existing review: the object under deletion is already out of the store, and a terminating sibling can still be selected by the Service.

Rewrite the test around the issue. Two deployments, namespace `default`, model `deepseek-coder-7b`. Remove one from the client, then call `deleteRouteFromDeployment`, and expect the route and the `default` ReferenceGrant to remain. Remove the other, call again, and expect both gone. Add the list-error case: the route and the grant stay. Drop the call that fires while the deleted deployment is still stored. `newEventTestRouter` already builds this scheme.

## Code review

The reported failure is real, and a remaining-workload check is the right guard. `samples/heterogeneous` puts `deepseek-coder-7b-l20` and `deepseek-coder-7b-v100` in `default`, both labeled `model.aibrix.ai/name: deepseek-coder-7b`, behind one Service of that name. `createHTTPRoute` (lines 279–315) writes one HTTPRoute, `<model>-router` in `aibrix-system`, whose single backend is that Service in the creating namespace. On main, every Delete handler calls `deleteHTTPRoute` and that function always deletes the route. The controller registers Add and Delete only, so the route stays gone until a process restart replays Add for the survivor. Issue #2824 is that sequence.

`modelHasRemainingWorkload` (lines 519–599) matches through `constants.ModelNameFromMetadata`, so a label and an annotation-only name (a name containing `/`) both count. A list error returns the error, and `deleteHTTPRoute` (lines 389–391) keeps the route. `meta.IsNoMatchError` on LeaderWorkerSet still means "CRD absent," same as `namespaceHasModelWorkload` (lines 499–502). The informer removes an object from the store before it calls DeleteFunc, so the workload being deleted is already absent when this list runs. A sibling that only has `deletionTimestamp` set is still in the store, and the shared Service still selects its pods. Counting that sibling is what keeps the route up until that object's own delete event. Skipping `deletionTimestamp` would drop the route while those pods can still serve.

The early returns at lines 389–394 skip the ReferenceGrant cleanup at lines 412–417. The grant is per namespace (`deleteReferenceGrant` / `namespaceHasModelWorkload`). The new check is per model, across every namespace. Delete the last `deepseek-coder-7b` workload in `team-a` while `team-b` still has that model: `modelHasRemainingWorkload` returns true, the function returns, and `aibrix-system-reserved-referencegrant-in-team-a` stays. Nothing in `team-a` emits another delete, so the grant stays for the life of the process. A list error takes the same return and skips the grant as well. `deleteReferenceGrant` already refuses to delete when its own list fails, so it can run on every path, including the "keep the route" path.

The cluster-wide predicate also pins a stale backend. The route stores one namespace, one service name, and one port. A second namespace does not receive this route's traffic. Delete the last workload in the backend namespace while another namespace still has the model: this PR keeps the route, `createHTTPRoute` treats AlreadyExists as success and does not patch `backendRefs` (lines 319–322), and a controller restart replays Add into that same AlreadyExists path. Before this PR the route was deleted, and the restart recreate pointed at the surviving namespace. For #2824 both deployments share `default` and Service `deepseek-coder-7b`, so keeping the route fixes the 503. The test encodes the other case.

`TestDeleteHTTPRouteKeepsSharedModelRoute` (lines 256–311) builds deployments in `team-a` and `team-b` and a hand-written route. The call at line 295 runs while `team-a` is still in the fake client, which is the opposite of informer order, and the test asserts nothing until after the client Delete and the second call. The assertion that then passes is "a different namespace with the same model name keeps the route." The #2824 shape — two deployments, one namespace, one Service — is not in the test. There is no list-error case for the new helper (the grant has `TestDeleteReferenceGrantDoesNotDeleteOnListError`), no NoMatch case for the new helper, and no ReferenceGrant assertion. Existing cases in `TestRouteAndReferenceGrantCleanupAfterWorkloadDeletion` still expect the route to disappear when the other object is a different model. They still pass, because those tests never insert the deleted object into the client, so the new scan only sees the other model.

A list failure leaves the route in place with no later reconcile. Restart replays Add, not Delete, and Add will not remove it. That is a sound trade against a 503, and it should be explicit: the orphan lasts until a later delete of that model observes an empty scan. Lists go through the cached client the informers already populate. No new RBAC, CRD, header, status field, flag, or annotation key. The behavior change is the route lifetime, plus the grant leak above. Gateway lookup is still `<model>-router` in `aibrix-system`.
