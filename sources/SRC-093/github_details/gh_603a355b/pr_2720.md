## Pull Request Description

The adaptive concurrency controller calculates `base * 2**errors` before applying its backoff cap. With 1,026 overload errors in one sample window, converting that intermediate integer to a float raises `OverflowError`, so the controller never applies its configured delay or reduces concurrency.

The window is the larger of the current concurrency limit and `healthy_window`. This can therefore also happen with concurrency limited to 32 and a configured `adaptive_healthy_window` of 2,048.

Use `math.ldexp` to scale the floating-point base directly, saturating to the configured cap when the result exceeds the float range. This preserves the ordinary exponential sequence, zero-valued backoff settings, and very small positive bases that can still have a finite scaled result.

The tests drive the public `on_complete` API with overload outcomes. They cover the ordinary sequence and cap boundary, large concurrency and healthy windows, zero base/cap settings, the smallest positive float base, and recovery after a successful request.

**Verdict: approve, with a few nits.** The overflow is real, `math.ldexp` is the right primitive, and the tests cover the cases that matter. CI is green.

### Bug

`_refresh_backoff_until` currently does `base * (2**exponent)`. `2**exponent` is an unbounded Python int; converting it to float raises `OverflowError` once `exponent >= 1024`. With default `failure_backoff_after=2`, that is 1026 overload errors in one sample window.

The window is `max(healthy_window, current_limit)`, so this is not only a huge-window misconfig. A job with concurrency ≥ 1026 hits it on a fully overloaded window.

The failure is worse than a missed delay. `on_complete` applies backoff **before** decreasing the limit, and it runs inside `_ConcurrencyAdmission.release()` after inflight is decremented and before `notify_all()`. An uncaught `OverflowError` therefore:

1. Never reduces concurrency.
2. Never applies the cap delay.
3. Escapes the admission lock without notifying waiters.

That can stall admission and leave the controller stuck at a high limit under overload.

### Fix

`ldexp(base, exponent)` computes `base * 2**exponent` on the float exponent field. It avoids allocating a huge int and still raises `OverflowError` when the product itself is out of range, which the `except` saturates to the configured cap.

That is a better fit here than clamping the exponent (as `_get_session_retry_delay_s` does). The exponent is an error count, not a retry attempt, so clamping it would change delay math for tiny or zero bases. `ldexp` preserves those and the ordinary `0.5, 1, 2, 4, …` sequence until the cap.

Boundary check: original `0.5 * (2**1024)` raises; `ldexp(0.5, 1024)` is finite (`2**1023`) and then `min(..., 10)` caps it. The `except OverflowError` path is what the 2048 / 4096 cases exercise. Both are needed.

### Tests

The table-driven cases are the right ones: ordinary sequence, cap without overflow, original crash boundary (1026), `ldexp` overflow saturation (4096), zero base/max, subnormal scaled result, and backoff clear on success. The extra `healthy_window=2048` test matches the write-up (limit 32 → 28, delay 10s). Freezing `monotonic` at `0.0` makes the delay assertions exact.

No API, config, or docs change is needed. Inline nits below are non-blocking.
