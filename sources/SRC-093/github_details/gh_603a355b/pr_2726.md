## Pull Request Description

Adds two config-profile fields so a model can cap load **per replica**, not only as a cluster-wide RPS total:

- `requestsInflight`: per-pod concurrent-request cap. Saturated replicas are filtered out before scoring; if every replica is at the cap (or the chosen target is still full), the gateway returns **429** (`replica_inflight_exceeded`).
- `requestsPerSecondPerReplica`: per-replica RPS. The gateway multiplies it by the current routable replica count and enforces that as the existing model RPS limit, so throughput scales with replica count. Takes precedence over `requestsPerSecond` when both are set. Values below 1 are expressed as “1 request every N seconds” (window capped at 1 hour).

Either field forces routing to **least-request** so the per-replica figure actually holds. Redis-backed running-request counts (per-pod hash keyed by gateway instance, with heartbeat liveness so a crashed gateway’s contribution is excluded/pruned) drive inflight admission and several routers (`least_request`, `prefix_cache`, `pd_disaggregation`, `load_balance`). If Redis is unavailable, those reads fall back to the local atomic counter.

Also refunds a rejected model-RPS increment immediately, and uses `ExpireNX` so refunds cannot stretch the rate-limit window.

Includes unit, integration, and e2e coverage, plus the mock `replica-limits.yaml` profile.

Example:

```json
{
  "defaultProfile": "default",
  "profiles": {
    "default": {
      "routingStrategy": "least-request",
      "requestsInflight": 4,
      "requestsPerSecondPerReplica": 2
    }
  }
}
```

## Review

Thanks for this — the config-profile API and the Redis running-request design (per-gateway hash fields, start-time-salted identity, incr/decr pairing) are in good shape. A few issues should be fixed before merge.

**Request changes**

1. **`requestsInflight` is check-then-act and can over-admit.** `filterSaturatedReplicaInflight` / `enforceReplicaInflight` only read the counter; `AddRequestCount` runs after that, and the Redis `HINCRBY` is async. Concurrent (and even fast sequential) requests can all see `running < limit`. This is the opposite of `enforceModelRPS` (incr-then-check). Please admit in one Lua script, or at least include this gateway's local atomic in the read. The unit tests stub 0 then 1, so they don't catch the race; the e2e concurrent case will be flaky for the same reason.

2. **Stale comment on `applyConfigProfile`.** It says inflight is raised to `ceil(replica RPS)` when both limits are set; the tests and `warnIfReplicaInflightBelowRPS` keep the configured value.

3. **Live Redis reads on every least-request / prefix-cache / PD / load-balance score**, not only when these limits are set. That is a latency change for default routing and overlaps `cache_gateway_snapshot.go`. Prefer keeping live reads on the inflight admission path.

4. **"Force least-request" loses to `routing-strategy` and `lockedRoutingStrategy`.** `requestsPerSecondPerReplica` is also aggregate (`replicaRPS × replicaCount` on the model RPS key), so sticky routing can dump the whole budget on one pod.

5. **Docs.** Please document the new profile fields (and 429 codes) in `docs/source/features/gateway-plugins.rst` / `docs/source/production/model-deployment.rst`, and drop the `Resolves: #[Insert issue number(s)]` placeholder.

Line comments below have details. I agree with Gemini on clock-drift liveness (I'd use Redis `TIME` for the ZADD score and cutoff rather than per-key TTLs) and the redundant nil check in `enforceReplicaInflight`. `ExpireNX` is fine if Redis 7+ is the supported floor; please state that if so. There are also no unit tests for `cache_running_requests.go` (~564 lines of Lua / liveness / prune logic).

### Suppressed comments (3)

**pkg/plugins/gateway/algorithms/pd_disaggregation.go:705**
* `GetPodsRunningRequests` returns a local-atomic fallback for every pod known to `Store`, even when `RealtimeNumRequestsRunning` has never been reported. Thus `runningErr` is nil and this branch treats metric-less decode pods as count 0, putting them into the request-imbalance min/max calculation; the documented cold-start behavior explicitly excludes such pods. Keep metric availability separate from the live count so a freshly restarted pod is not selected solely because it lacks a metric.
```
			requestCount += float64(runningReqCounts[utils.GeneratePodKey(pod.Namespace, pod.Name)])
```
**pkg/plugins/gateway/algorithms/router.go:496**
* This performs one synchronous Redis read per candidate while building a diagnostic log. At verbosity 4, a model with N replicas adds N round trips (each with the read timeout) to the routing path, despite the new batch API being available. Fetch `GetPodsRunningRequests(pods)` once and index the result in the loop.
```
				if count, err := c.GetPodRunningRequests(pod.Name, pod.Namespace); err == nil {
					outstandingStr = fmt.Sprintf("%d", count)
```
**pkg/plugins/gateway/gateway_ratelimit.go:155**
* With `RateWindowSeconds > 1`, this rollback can run after `genKey` has moved to the next fixed-window bucket. The existing rationale above only covers a one-second window; keep the original bucket identity for compensation or make refunds floor at zero without creating a missing bucket.
