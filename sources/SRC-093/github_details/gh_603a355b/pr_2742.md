## Pull Request Description

Adds Redis-backed session-key pinning so `session-affinity` can keep concurrent agentic
requests on the same inference pod across gateway replicas, plus follow-up correctness
fixes so that stickiness actually holds after scale-out, cache isolation, and blend
behavior.
### Agentic routing
`x-session-id` only works after the first response comes back, which is too late for
agentic workloads that fan out concurrent tool calls or sub-agent requests. Callers can
now send a stable `x-aibrix-session-key` from the first request:
- Sequential multi-turn chat still uses the gateway-issued `x-session-id`.
- Concurrent/agentic requests use a caller-owned `x-aibrix-session-key` (conversation ID,
  agent-run ID, etc.).
- With `REDIS_HOST` configured, the key→pod pinning is shared across gateway replicas
  (1-hour sliding TTL). Without Redis, mapping stays deterministic via rendezvous hashing
  over the current ready pod set.
- Keys longer than 256 bytes are treated as unset and fall back to normal
  session-affinity resolution.
- The same header can be reused by PD `token_load` / `hybrid_cache_load` policies.
Docs: `docs/source/features/agentic-routing.rst`.

### Correctness Follow-ups

- **Drop the session-affinity load-balance auto-blend:** Session-affinity `ScoreAll` is binary (1 for the resolved pod, 0 elsewhere), so the previous 5:4 blend could never be overridden by load-balance disagreement. Bare `session-affinity` now runs unblended, like `pd` / `slo*` / standalone `load-balance`. Prefix-cache keeps the 5:4 ratio because its scoring is graded.
- **Honor stickiness on the single-ready-pod fast path:** `selectTargetPod` used to return that pod without calling `router.Route()`, so a session started while only one pod was ready never got a Redis pin or `x-session-id` header. After scale-out, rendezvous hashing could move the session. The router's `PostRouteUpdate` hook now runs on that path, including through `multiStrategyRouter`.
- **Isolate and bound the session-key cache:** Redis/local cache keys are scoped by model (`sessionCacheKey`) so two models sharing Redis — or a reused session-key value — don't overwrite each other. The local `sessionKeyPods` cache is capped by `AIBRIX_SESSION_AFFINITY_MAX_LOCAL_KEYS` (default 100k); past the cap, new keys still resolve via Redis or rendezvous hashing.
- **Harden Lookup / local-cache races:** `Lookup` rejects a nil provider instead of dereferencing it. `storeSessionKeyLocal` uses a `LoadOrStore` / `CompareAndSwap` retry loop so concurrent writes can't clobber a newer pinning or un-confirm one whose Redis write already landed.

> **Note / Known Leftover:** `persistSessionKeyToRedis`'s unconditional `SET` is shared by initial-claim, TTL-refresh, and failover-repin writes and can still race across gateway replicas. Called out with a `TODO` in code; not addressed here.
