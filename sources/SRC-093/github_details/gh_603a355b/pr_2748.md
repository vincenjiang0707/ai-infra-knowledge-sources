## What this PR does

`featuresKey` and `higherRank` were the last two pure helpers in `slo_queue.go` still without coverage. This adds a spec for each.

- **`featuresKey`** — requests whose features fall in the same `log2` bucket (`round(log2(x))`) must produce the same sub-queue key, and requests in different buckets must produce different keys. Verified with `{100,100}` and `{120,120}` (both `round(log2)=7`) mapping to one key, and `{1000,1000}` (`round(log2)=10`) to another.
- **`higherRank`** — returns the difference between two ranks; asserted against a hand-computed value.

Test-only; no production code is touched.

### stywzn · 2026-09-18

Applied the non-mutation fix in b9a04f5f, with one correction to the reasoning.

The double-transformation you describe cannot actually occur on the current code. `ctx.Features()` builds and returns a **fresh** slice on every call:

```go
return RequestFeatures{float64(outputLen), float64(promptLen)}, nil
```

It is not cached on the `RoutingContext`. So the slice `featuresKey` mutates in `Enqueue` is a throwaway, and the later `req.Features()` in `rankImpl` recomputes a brand-new slice from the token lengths — it never sees the log2-transformed values. No caller observes the mutation today, so there is no live routing bug.

That said, your recommendation is right regardless: a "compute a key" helper mutating its argument is a latent footgun that is only safe by luck (the sole caller happens not to reuse the slice). It would bite the moment `Features()` cached or a second caller reused the slice. So `featuresKey` now copies into a local slice before transforming, and the spec asserts the input is left unchanged — using your test, which is exactly right.

Since this turns the PR from test-only into a small production change, I kept the fix in its own commit with that reasoning in the message.
