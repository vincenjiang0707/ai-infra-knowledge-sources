## Pull Request Description
The KPA/APA cooldown windows in `stabilizeRecommendation` (`pkg/controller/podautoscaler/podautoscaler_controller.go`) looked at the wrong end of the recommendation history. Scale-down took the **min** over the scale-down window and scale-up took the **max** over the scale-up window. The current recommendation is always in the window, so the stabilized value was always at least as aggressive as the raw one. In practice the default 5m `scale-down-cooldown-window` never held replicas back, and a non-zero `scale-up-cooldown-window` never delayed a scale-up.

The fix uses the same logic as Kubernetes HPA's `stabilizeRecommendationWithBehaviors`. The scale-up bound is the min recommendation over the scale-up window, the scale-down bound is the max over the scale-down window, and current replicas are clamped between them. The function comment and the annotation docs already describe this behavior, and the HPA strategy passes the same annotations through as `stabilizationWindowSeconds`.

**Behavior change:** KPA/APA now scale down only after every recommendation in the scale-down window is lower, and only to the highest of them. With the defaults this delays scale-downs, including scale-to-zero, by up to 5 minutes. That is what the documented window describes. Scale-up is unchanged with the default 0s scale-up window. The history is kept in memory, so the first reconcile after a controller restart is not held. That was also true before, and matches HPA.

## Design simplification

Keep the function as the HPA clamp. One slice per PodAutoscaler, prune to the longer window, append the raw recommendation, min over the scale-up cutoff, max over the scale-down cutoff, clamp current replicas between them. The direction branch, `selectMax`, and the early return when the recommendation equals current are already gone. An equal recommendation still has to be stored. It is the high-water mark the down window reads on a later call. The clamp leaves current replicas unchanged in that case, so the early return would only repeat the same result.

Keep `cleanOldRecommendations`. It is what bounds the slice, and calling it before the append is the ordering constraint. Folding the prune into the min/max scan hides the zero-window case. Kubernetes overwrites one expired slot and can leave older expired samples in the slice. Compacting to the longer window is the smaller rule. Keep it.

Keep the table test and the fixed `now` hook. Add the one case where both windows are non-zero. Skip map-length assertions, a second history type, and a full-reconciler test for this function.

Cut the rest of HPA normalization. No `AbleToScale` reason strings, no scale-event log for the rate policy, no select-policy enum, and no second map split by direction. The V(4) fields that replaced `windowDuration` and `selectMax` are the log line to keep. Rate limiting stays in `kpa.go` and `apa.go`. A follow-up that wants one window for the whole scale-down passes the pre-rate target in and applies the rate once to the returned value. That change does not belong inside the clamp.

The in-memory map and the HPA skip stay. Removing the map entry from `cleanupDeletedPA` is a separate cleanup.

## Code review

The clamp is the right fix. On main, a recommendation below current replicas takes the min over the scale-down window, and a recommendation above current takes the max over the scale-up window (`podautoscaler_controller.go` 1336–1367). The sample just recorded is inside the chosen window, so the min is at most the new low value and the max is at least the new high value. The default 5 minute scale-down window cannot hold replicas. A non-zero scale-up window can also move the target up to an older spike still in that window.

The new function (`podautoscaler_controller.go` 1327–1355 on `ea5b8dd8`) matches Kubernetes 1.32 `stabilizeRecommendationWithBehaviors`. Both seed the up bound and the down bound with the raw recommendation, take the min of samples strictly after the scale-up cutoff and the max of samples strictly after the scale-down cutoff, then raise current replicas to the up bound and lower them to the down bound. `timestamp.After` leaves a sample that lands exactly on the cutoff outside the window, which is the same edge HPA uses. The raw recommendation is in both bounds, so the up bound stays less than or equal to the down bound and the two assignments stay ordered.

Cleaning before the append (`1327–1332`) is the right order. `cleanOldRecommendations` keeps a sample only when `timestamp.After(now - maxWindow)`. A zero window’s cutoff is `now`, and `now.After(now)` is false, so append-then-clean drops the sample just written. Seeding the bounds with the raw recommendation still answers that one call. The following call would then see an empty slice and would skip a hold that the window was supposed to provide. Cleaning first leaves the new sample in the slice for a later reconcile.

`computeScaleDecision` still calls this only when the strategy is not HPA (`1205–1208`), then clamps to the scheduled min and max (`1216–1224`). The HPA strategy still receives the same annotations as `stabilizationWindowSeconds` in `buildHPABehavior`. Tolerance, KPA panic mode, and the pending-replica guard still run inside `ComputeDesiredReplicas`. This function only sees the integer they return.

The behavior change is larger than a single 5 minute pause on a sustained scale-down. KPA and APA apply `max-scale-down-rate` before this function. The default rate is 2, so a raw target of 2 with 10 replicas is stored as 5 (`kpa.go` 118–141, `apa.go` 100–104). The window then holds the current replica count until every stored recommendation in the last 5 minutes is lower, and the value it releases is that 5. Those 5s fill the window, so the next rate step waits another full window. With the defaults, 16 → 8 → 4 → 2 is one window per step, and scale-to-zero (`floor(1/2) = 0` on the last pod) waits out each of those steps. HPA stabilizes the raw target once, then applies its rate policy on the policy period (`buildHPABehavior` uses 60 seconds). The pull request text says the default window delays scale-down, including scale-to-zero, by up to 5 minutes. That describes the wait before the first step. Reaching the raw target under the default rate takes one window per rate step. Leave that composition alone in this change. A follow-up that wants HPA’s order would pass the pre-rate target into this function and apply the rate once to the returned value.

History stays an in-memory map keyed by `namespace/name`, guarded by `recommendationsMu`. After a controller restart or leader change the slice is empty, both bounds equal the raw recommendation, and the first reconcile scales immediately. That matches HPA and the previous code. `cleanupDeletedPA` (`360–368`) removes the scaling-target indexes and leaves the recommendation slice in place. That leftover is pre-existing. A 5 minute window at the 10 second resync is a few dozen samples per object. This fix does not need a deletion hook.

A held scale-down returns the current replica count, so `computeScaleDecision` records reason `stable`. The V(4) line now logs both windows and the stabilized value (`1357–1364`). That log is the right signal for this fix.

`TestStabilizeRecommendationHoldsWithinCooldownWindows` (`podautoscaler_controller_test.go` 1234–1313) is the right test. Each case gets a fresh reconciler and a fixed clock. I ran it on `ea5b8dd8`: `go test ./pkg/controller/podautoscaler/ -run TestStabilizeRecommendationHoldsWithinCooldownWindows -count=1` passed. The same test against the main function failed the dip, the expiry case, and the spike at the first aggressive step (`rec=2, current=10` returned 2; `rec=4, current=10` returned 4; `rec=10, current=2` returned 10). The expiry case locks the HPA detail that matters: at 5m+1s the result is 4, the highest sample still inside the window, while the latest recommendation is 3. Zero windows follow the recommendation, and a zero scale-up window with a 5 minute scale-down window still scales up on the next step. `NewBaseScalingContext` defaults the down window to 300s, and the test then assigns both fields, so an omitted window is 0 inside the test. That is what the zero-window cases need.

One case with both windows non-zero is still missing. With a 1 minute scale-up window and a 5 minute scale-down window, a dip to 2 while current is 10 stays at 10, and a later recommendation of 12 also stays at 10 until that 2 leaves the scale-up window, because the up bound is the min. After the 2 ages out, the up bound can rise and current moves up, while the down window still refuses to go below its max. The five existing cases keep one of the two windows at 0, so the two bounds never differ. That extra case would lock the clamp.

API and compatibility: no CRD field, printer column, webhook, status, HTTP route, header, CLI flag, environment variable, label, or annotation key changes. Defaults stay 0s scale-up and 300s scale-down (`context.go` 112–113). The metric-autoscaling doc already calls both annotations stabilization windows. After this patch the KPA and APA path does what that doc and the HPA path already describe. Samples that set `scale-down-cooldown-window: 0s`, including the optimizer example, keep immediate scale-down. Existing KPA and APA objects that were scaling down on the first low sample will start holding. That is the bugfix, and it belongs in the release note. A mixed rollout is per process: a new controller holds, an old controller scales on the sample, and a failover onto a cold process scales on the first reconcile. There is no stored history to migrate.
