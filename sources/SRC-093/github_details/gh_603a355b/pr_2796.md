## 正文

### Pull Request Description

#2786 gave a model config profile a `routingConfig` whose knobs override the gateway's environment defaults for that profile's requests. The knobs that configure state shared by every model of a gateway process were left out of it, and for a good reason: a value read per request cannot be applied to an already built tracker, cache or timer. This change scopes the group whose state can be built per configuration, the VTC token tracker:

| Profile field | What it now bounds for this profile's requests |
| --- | --- |
| `vtc.inputTokenWeight`, `vtc.outputTokenWeight` | the weights of the VTC token tracker they use |
| `vtc.tokenTrackerWindowSize`, `vtc.tokenTrackerTimeUnit`, `vtc.tokenTrackerMinTokens`, `vtc.tokenTrackerMaxTokens` | the sliding window, its bucket size, and the token floors reported while the window holds little activity |

The remaining state-sharing knobs of #1961 stay environment-only and no longer appear in the profile config. A value that acts as a ceiling on state every profile shares, the session-affinity pin cache, the routing-string caches or the token-load session table, cannot be honored per request, because the count it would be compared against is the process-wide one. The preble histogram window and its eviction loop need per-profile histograms and eviction schedules, which is a design of its own. `pkg/types/routing_knobs.go` carries the rule the fields follow: a state-sharing knob keeps a profile field only where the read site can give the profile its own instance of that state, keyed by the resolved values.

### Semantics

- **Scoping, not retuning.** A profile that sets one of these knobs does not touch the shared instance: the gateway builds a tracker keyed by the resolved values, so profiles that agree share one and a profile that sets none reads the shared tracker exactly as before. The number of instances is tied to the distinct configurations rather than to the number of profiles.
- **Bounded.** VTC trackers are capped at 16 per process. Past the cap a request keeps the shared tracker, and it is both scored and priced with that tracker's own floors and weights rather than the profile's, which is the behaviour it had before this change. A request never fails because too many profiles asked for their own tracker, and the cap is logged once.
- **No cost until asked.** A request whose profile sets none of the six knobs reads the same tracker object as before, and the default path only compares the resolved values.
- **Weights belong to their scope.** The two token weights are baked into a tracker, so a profile that changes one gets a tracker of its own instead of mixing its counts with the shared tracker's; they are not multipliers that could be applied at read time.
- **`WithWindowSize` stops leaking.** The option used to overwrite the process-wide default, so one tracker built with a 100 ms window silently retuned every tracker built afterwards. It now configures the tracker it is applied to and leaves the default alone.

### Implementation

- `pkg/plugins/gateway/algorithms/vtc/tracker_scope.go` adds the scope key (window, unit, floors and the two weights) and the bounded registry that builds one tracker per scope outside the lock and keeps the winner of a race.
- `pkg/plugins/gateway/algorithms/vtc/vtc_basic.go` resolves the request to its tracker once per routing pass (`trackerFor`), which returns the tracker together with the knobs it was built from, and both the route and the scoring path size the bucket from those knobs. `ScoreAll` still never updates the tracker it scores with, so scoring a candidate cannot commit a request the blend may route elsewhere.
- `pkg/plugins/gateway/algorithms/vtc/token_tracker.go` takes the window, floors and unit from the knobs it is constructed with (`NewScopedInMemorySlidingWindowTokenTracker`), and the process-wide constructor now goes through the same path with the environment knobs.
- `pkg/plugins/gateway/algorithms/profile_knobs.go` resolves and validates the six fields, dropping a value the matching environment variable would reject.
- `pkg/plugins/gateway/ENV_VARS.md` and `docs/source/features/gateway-plugins.rst` move the six knobs into the profile tables and keep the other state-sharing knobs in the environment-only lists.

Design and code review.

The VTC tracker scoping holds up. A profile that changes the window, the time unit, the floors, or either weight gets a tracker built from those values. Profiles that resolve to the same six values share one tracker. A request that leaves them at the process defaults keeps the router's existing tracker, so the default path only compares the six values. Building the tracker outside the lock and keeping the winner is the right race handling, and stopping `WithWindowSize` from overwriting the process-wide default is a real fix. Sixteen scopes, then falling back to the shared tracker instead of failing the request, is a reasonable bound.

The preble fields should not land in this pull request. `preble.slidingWindowPeriodMinutes` and `preble.evictionLoopIntervalMilliseconds` are accepted, stored on `PrebleOverrides`, and documented as giving the profile its own histogram and eviction schedule. Nothing reads them. `prefix_cache_preble.go` still builds the histogram from the package-level `slidingWindowPeriod` and `evictionLoopInterval`. The description says those two knobs follow in a second change. Shipping the API now means a profile that sets them is accepted and then ignored.

`sessionAffinity.maxLocalKeys`, `router.maxCachedAlgorithmStrings`, and `pd.tokenLoadMaxSessions` are checked against the process-wide entry count. A profile value of 10 means "do not insert once the whole process already holds 10 entries," not "this profile may add 10 of its own." On a gateway whose session cache is already past that number, the profile never caches a new key. That is a different mechanism from the VTC tracker, and it does not match the data: a session pin is a fact about a model and a session, shared by every profile. Either count entries per resolved scope, the way the VTC registry does, or leave these three environment-only until that counter exists.

The token-load cap also races. `recordSessionPrompt` still does `sessionCount.Add(1)` and then compares with the caller's `maxSessions`. A profile whose cap is already below the live count increments the shared counter, fails the check, and decrements. A concurrent admission that is under the environment cap can observe that extra increment, decide the table is full, and decrement as well. Both refuse, and the free slot is lost. The same failure sets `sessionsFull`, so the one-time "table is full" warning can fire for a profile cap of 1 while the tracker's own cap is still far above the live count. Check the current count against the caller's cap before incrementing, and only mark the table full when the refusal is against the tracker's own cap.

Past the 16-tracker bound, the request is not actually back on the environment values. `trackerFor` returns the shared tracker, so the update is priced with the shared tracker's weights and written into the shared counts. The bucket size in `Route` and `ScoreAll` still uses `vtcWeights.TokenTracker.MinTokens` from the profile. The fallback both pollutes the shared tracker and scores with the profile's floor. If the bound is hit, score and update with the shared tracker's floors as well.

`applyDuration` does `time.Duration(*v) * unit`, the same overflow `windowSizeDuration` just closed for the VTC window. It only matters while the preble knobs stay in the resolver. If those fields stay, saturate the multiplication the same way. If they move to the follow-up, this helper should go with them.

## Code Review

This pull request introduces the ability to override process-wide environment variables (such as VTC token tracker settings, session affinity local key limits, router algorithm string cache caps, and PD token load max sessions) via model config profiles. Instead of retuning the shared process-wide state, these overrides scope separate instances (up to a safe ceiling to prevent unbounded growth) or claim a share of the process-wide budget. The review feedback suggests two improvements: adding a defensive check against integer overflow when calculating the sliding window size in the token tracker, and copying the existing `r.config` instead of constructing a new `VTCConfig` from scratch to preserve other configuration fields in the scoped tracker.
