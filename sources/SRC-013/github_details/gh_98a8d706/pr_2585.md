## Complete the `fast-model-actuation-base` rename: fix stale `llm-d.ai/guide` label values

Follow-up to #2521, which renamed the FMA guide directory
`guides/fast-model-actuation` → `guides/fast-model-actuation-base` but left the
`llm-d.ai/guide` label *values* inside the guide's manifests at the old
`fast-model-actuation`.

### Why this breaks the nightly

The base FMA nightly (`nightly-e2e-fast-model-actuation-base-ibm-acc-gpu-vllm-x`)
stands the stack up fine — controller, launcher-populator, requester, and all
launcher pods reach `Running` — but the benchmark's kustomize standup readiness
gate derives its pod selector from the guide directory name:

```python
# llm-d-benchmark: standup/steps/step_05_kustomize_deploy.py
label=f"llm-d.ai/guide={guide_name.split('/')[-1]}"   # -> llm-d.ai/guide=fast-model-actuation-base
```

Because the pods were labeled llm-d.ai/guide=fast-model-actuation (old value),
the gate matched zero pods and timed out after 2400s with no pods found,
failing standup despite a healthy deployment.

### Changes

Update the llm-d.ai/guide value fast-model-actuation → fast-model-actuation-base
(the requester and router selector must move together so the InferencePool
still binds the same backends):

- modelserver/inferenceserverconfig.yaml
- requester/deployment.yaml (Deployment label + pod-template label)
- router/fast-model-actuation-base.values.yaml (InferencePool matchLabels + header comment)

### Evidence

Failing run: https://github.com/llm-d/llm-d/actions/runs/36088778005/job/107926494262
— debug dump shows all FMA pods Running/ready while the gate polls
llm-d.ai/guide=fast-model-actuation-base and reports no pods found for the
full 40-minute window.
