## 正文

`check_models` discards the status it has just reported. `helpers/smoke-test/healthcheck.sh:184` fails with the real code, and `:185` overwrites it with `000`, which is the sentinel `curl` produces when nothing answered at all.

So a reachable endpoint returning 503 reads as unreachable in the summary table, while the failure list directly below it shows the true code. Both come from the same variable in the same run:

```
║  /health          HTTP 503               ║
║  /v1/models       HTTP 000   count=-     ║
║  /v1/chat/completions HTTP 503   8     ms   ║
...
Failures:
  - /v1/models returned HTTP 503
  - /v1/chat/completions returned HTTP 503
```

`/health` and `/v1/chat/completions` both report 503 correctly. `/v1/models` is the outlier.

Every other exit from this code keeps the status: `check_health` at `:171`, and `check_models` itself at `:194` and `:210`. This is the only path that loses it.

## The change

Reporting `${http_code}` covers both cases, because `curl` already yields `000` when the connection fails. Verified against a 503 server and against a port nothing listens on:

```
=== 503 server ===
║  /v1/models       HTTP 503   count=-     ║
=== nothing listening ===
║  /v1/models       HTTP 000   count=-     ║
```

The sentinel survives where it is real, and the true code survives where there is one.

## Test

`tests/test_healthcheck_failure.py` already stands up a `ThreadingHTTPServer` answering 503 to everything, but asserted only the exit code, the `UNHEALTHY` banner and the word `failed`. It now also asserts the row.

```
$ python -m pytest helpers/smoke-test/tests/
1 passed

$ shellcheck -x --severity=warning helpers/smoke-test/healthcheck.sh
(exit 0)
```

Revert the script, keep the test, and it fails on the new assertion.
