# [PR #1715] [Docs] Replace deprecated `kv_both` for NIXLConnector and with explicit P/D Roles

source: https://github.com/llm-d/llm-d/pull/1715
state: closed | updated: 2026-09-22T19:21:33Z
labels: 

## 正文

We're deprecating `kv_both` in vLLM for the NixlConnector in favor of explicit roles https://github.com/vllm-project/vllm/issues/43807 so startup vllm serve commands for P and D will be asymmetric (they already are when configuring things like DeepEP but anyway..).
The TL;DR: this allows vLLM to have finer control at config time, that is prior to handshaking/pod discovery, to handle some important edge-cases more cleanly. 

This PR simply changes the docs to recommend setting roles.
Mind that at the time of writing `kv_both` isn't yet fully deprecated, so nothing is happening in the current release when setting kv_both.

### junuxyz · 2026-09-03

@Gregory-Pereira

> I have some questions here, traditionally in llm-d decode can do both types of work, and so I would assume its default role would be kv_both.

To my understanding, a decode worker performing local prefill or recomputation does not make it a NIXL producer (`kv_producer`). As described in llm-d’s [failure handling docs](https://github.com/llm-d/llm-d/blob/main/docs/operations/disaggregation/vllm.md#prefill-instance-failure), the decode worker runs the full request locally, including prefill. Since there is no remote KV handoff occurring here, this shouldn't affect its NIXL role.

> Also what about cases like using NIXL bidirectional transfer?

Think this was previously discussed in the [upstream vLLM RFC](https://github.com/vllm-project/vllm/issues/43807#issuecomment-4564937443). The conclusion was: bidirectional transfer is a secondary capability and does not change the primary P/D roles. Likewise, the [current vLLM documentation](https://github.com/vllm-project/vllm/blob/main/docs/features/nixl_connector_usage.md#configuration) configures bidirectional transfer with kv_producer on P and kv_consumer on D.
