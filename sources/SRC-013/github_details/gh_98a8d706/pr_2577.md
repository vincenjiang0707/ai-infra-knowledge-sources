**What this PR does / why we need it**:

This is a pure refactor: it consolidates the two overlapping KEDA + EPP autoscaling guides into one and changes no deployed behavior on the default path.

Previously `keda-epp-queue` and `keda-epp-saturation` were two near-duplicate guides that differed only in which EPP metric drives scaling. This PR merges them into a single `guides/workload-autoscaling/keda-epp` guide where the scaling signal (queue vs saturation) is a kustomize Component axis with queue as the default, and platform (generic Kubernetes vs OpenShift) is the other axis.

- The new `keda-epp` guide is built from a trigger-agnostic base plus `trigger-queue`, `trigger-saturation`, and `ocp-auth` kustomize Components, composed into four leaves: `k8s-queue`, `k8s-saturation`, `ocp-queue`, `ocp-saturation`.
- The queue leaves render byte-identical to the old `keda-epp-queue` overlays, so the default path is provably unchanged; the saturation leaves differ only by the shared-base reconciliation and a single consolidated OCP `TriggerAuthentication` name.
- The old `keda-epp-queue` and `keda-epp-saturation` directories are reduced to redirect stubs, and every inbound reference is repointed: the workload-autoscaling index, the autoscaling architecture doc, token-aware, kueue-rebalancing, multi-inference-pool, recipes/autoscaling, and fast-model-actuation-keda.
- `fast-model-actuation-keda` is repointed to the new `keda-epp` `k8s-queue` leaf and its build stays byte-identical.

Verified locally: kustomize build across all guide overlays, `guide.py render --check` and schema check, and markdownlint plus yamllint on all changed and new files. The queue and fast-model-actuation-keda builds were confirmed byte-identical to the pre-refactor output, and the saturation build diff matches only the enumerated reconciliation.

## Live test on OpenShift - both signals(Queue and Saturation)

Stood up an isolated stack on an OCP cluster and ran the guide's own `verify.tests.scale_event` against both scaling signals from the consolidated `keda-epp/` guide.

**Setup (faithful to the consolidated overlays):**
- Real `optimized-baseline` stack: router (gateway + EPP with `flowControl` on via the guide's `keda-epp/optimized-baseline/router.values.yaml`) + a single vLLM decode replica, monitored (ServiceMonitor into user-workload-monitoring).
- ScaledObjects applied straight from the consolidated leaf overlays `optimized-baseline/ocp-queue` and `optimized-baseline/ocp-saturation`. 

**KEDA -> Thanos auth resolved on both paths** (no x509, no 401): the HPA external metrics populated (`0/1` + `0/16` for queue; `0/700m` + `0/16` for saturation), and the ScaledObject reached `READY=True`.

**Queue signal (default)** - `ocp-queue`:
```
-- firing burst (concurrency=30 total=400) to drive running-requests over threshold --
  scale-up decision: desiredReplicas=2
-- load stopped; waiting up to 360s for scale-down (matches the 300s scaleDown window) --
  scale-down decision: desiredReplicas=1
Scale-event verified (QUEUE): min 1 -> >1 -> 1
```

**Saturation signal** - `ocp-saturation` (note `maxReplicaCount` 10, from the saturation component):
```
-- firing burst (concurrency=30 total=400) to drive pool-saturation/running over threshold --
  scale-up decision: desiredReplicas=2
-- load stopped; waiting up to 360s for scale-down --
  scale-down decision: desiredReplicas=1
Scale-event verified (SATURATION): min 1 -> >1 -> 1
```

Both signals drove a real 1 -> 2 -> 1 autoscaling decision end to end (EPP metric -> Thanos -> KEDA over threshold -> HPA raises the target -> drains back to min). This is on top of the `kustomize build` byte-identical check per leaf, which is the structural proof that this PR is a pure refactor; the live run confirms both consolidated OCP overlays deploy and scale.
