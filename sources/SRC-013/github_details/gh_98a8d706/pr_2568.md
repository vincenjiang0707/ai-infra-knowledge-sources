# [PR #2568] fix(no-kubernetes-deployment): enable EPP health checking for Envoy

## 正文

Fixes #2567

## What

The no-Kubernetes guide's `envoy.yaml` health-checks the EPP with `grpc_health_check` on the ext-proc port (`9002`). The EPP only serves `grpc.health.v1.Health` on that port when started with `--health-checking=true`, and neither EPP command in the guide passed it. Every check failed, Envoy held the EPP at `/failed_active_hc`, and requests reached it only through Envoy's panic routing.

This PR adds `--health-checking=true` to both EPP commands (container and from-source), which matches the router chart in priority-routing mode, where it passes the flag and fails the render if it's set to false (`routerlib/templates/_helpers.tpl`: *"priorityRouting requires EPP's gRPC health service on port 9002"*).

## Why it matters

With one EPP, completions succeed either way. That's why this went unnoticed. But:

- the health check the guide says it carries over from the standalone preset has never passed;
- a second EPP added for failover gets no health-based failover, because every EPP looks equally unhealthy and Envoy load-balances across all of them in panic mode.

| Envoy stat (`ext_proc` cluster) | main | this PR |
|---|---|---|
| `health_check.success` / `failure` | 0 / 6 | 1 / 0 |
| `lb_healthy_panic` | 1 | 0 |
| `health_flags` | `/failed_active_hc` | `healthy` |
| completion via Envoy `:8081` | 200 | 200 |

Probing the EPP directly on main: port `9002` returns `UNIMPLEMENTED unknown service grpc.health.v1.Health`, and port `9003` returns `SERVING`.

## Changes

- `README.md`: `--health-checking=true` in both EPP commands; a paragraph on what it does and how it differs from `--grpc-health-port`; a `health_flags` check in **Verification**; the `failed_active_hc` symptom in **Troubleshooting**.
- `router/envoy/envoy.yaml`: a comment above `health_checks:` stating the requirement, since the guide tells users to copy this file to hosts on its own.

I considered dropping `health_checks` from `envoy.yaml` instead, but decided against it. The guide says it mirrors the standalone preset's health checks, and the health check is what makes a multi-EPP setup fail over.

## Testing

Ran the full guide on one host with Docker and 2 GPUs (RTX 3080 + RTX 3090). Two vLLM `v0.19.1` workers served Qwen3-0.6B, one per GPU, both listed in `endpoints.yaml`, behind EPP `main` and Envoy `distroless-v1.33.2`.

- [x] Before/after Envoy stats as in the table above; completions return 200 in both cases
- [x] `--health-checking` is present in the `v0.10.0` and `main` EPP images (`--help`)
- [x] Routing is unaffected: requests that share a prefix stay on one worker (90% prefix-cache hit rate), and unique prompts spread across workers
- [x] `envoy --mode validate` passes on the edited `envoy.yaml`
- [x] `prek` hooks pass on both files. markdownlint reports 6 MD060 table errors at README lines 29–31, which already exist on `main` and are untouched here

## Related

The router chart's default standalone preset renders the same unconditional `health_checks` block but passes `--health-checking=true` only under priority routing, so it may show the same thing in Kubernetes. I haven't reproduced that, so I'm raising it as a question in llm-d-router rather than touching it here.
