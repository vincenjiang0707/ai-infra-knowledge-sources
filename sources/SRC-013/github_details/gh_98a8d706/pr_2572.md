## p2p-kv-cache-sharing: token-aware placement for document Q&A, and self-describing CPU-tier events

### Why

The guide's document Q&A scenario recommends load-aware + P2P because it beats affinity there. Token-aware placement was never measured. On the guide's own document Q&A profile it beats both existing arms. Separately, the model-server manifest omits `self_describing_kv_events`, which can keep CPU-tier blocks out of the precise index under churn.

### What changes

- **Model server:** `self_describing_kv_events: true` in the offloading connector config. Without it, CPU-tier store events carry no tokens or parent hash, and the router can attribute a CPU-tier block only through the mapping learned from the same block's GPU-tier store. Under churn the GPU removal can arrive first, and the CPU copy a peer would pull never enters the index.
- **New EPP arms:** `benchmarking/epp-tokenaware-p2p.yaml` and `benchmarking/epp-tokenaware.yaml`, token-aware placement (in-flight uncached tokens on the precise index) with and without the pull.
- **Report:** `benchmark-results/gpt-oss-120b-docqa-token-aware.md`.
- **Guide text:**
  - a token-aware placement bullet and two configuration table rows;
  - token-aware + P2P recommended for session-pinned workloads;
  - the calibration result over TCP;
  - the self-describing events requirement in Best Practices.

The shipped default stays affinity + P2P, because token-aware placement has not been measured on the uniform pool, where affinity leads.

### Results

All runs use the guide's document Q&A profile (llm-d-benchmark#1656 at the pinned commit) through the llm-d-benchmark `v0.7.0` harness, scaled from 16 to 8 pods (96 conversations, 64 in flight). The fleet is 8 x gpt-oss-120b TP=1 on H200, pulls over TCP. Every run starts from empty caches.

| Placement | Pull | Served req/s | TTFT p50 / p90 ms | TPOT p90 ms | Request latency p50 s |
| --- | --- | --- | --- | --- | --- |
| token-aware | yes | **6.03** | 609 / **7,191** | **33.2** | 5.3 |
| token-aware | no | 5.02 | 1,758 / 7,221 | 45.8 | 8.7 |
| load-aware | yes | 4.26 | 2,993 / 8,882 | 51.2 | 9.0 |
| load-aware | no | 2.75 | 3,555 / 8,840 | 97.4 | 13.9 |
| affinity (default) | yes | 2.75 | 528 / 14,054 | 139.4 | 5.0 |
| affinity (default) | no | 2.66 | 637 / 14,624 | 110.5 | 5.7 |

**Token-aware placement, with and without the pull, four paired runs each** (chart attached): served throughput +15%, TTFT p50 -26%, TPOT p90 -15%, request latency p50 -26%, TTFT p90 -2%. TTFT p90 is set by each conversation's cold 48K-token first turn, which no pull can serve.

### Follow-up

A cost-model decision for the pull (llm-d-router `p2p-source-producer` `costModel`, crediting the prefill a pull saves on a loaded pod) matched the fixed-delta rule on TTFT p90 across four paired runs. It made about 30% fewer pulls. It is not referenced here until that router change lands.
