## 正文

The CPU installer sorts cached wheel filenames lexicographically, so `nixl-0.9.0` can win over `nixl-0.10.0`. Parse wheel metadata and compare PEP 440 versions using packaging, which is already installed by the CPU vLLM build requirements before this script runs. Ignore malformed wheel names and other distributions sharing the nixl prefix.

Validation: `python -m pytest -q docker/scripts/cpu/test_install_nixl.py`: 5 passed, covering numeric versions, prerelease/final/dev/postrelease ordering, and unrelated or invalid wheels.
Changed-file pre-commit checks passed.

### chrikrah · 2026-09-26 · COMMENTED

Correct and well-tested. Both defect hypotheses I went looking for came out false. Harness: `uv venv` plus `packaging` 26.3 and `pytest` 9.1.1 on Python 3.13.15. The base and head copies of `install_nixl.py` load side by side, and `find_nixl_wheel_in_cache` runs directly over directories of touched files.

```
case                                  BASE                  HEAD
0.10.0 vs 0.9.0                       nixl-0.9.0  (wrong)   nixl-0.10.0
1.10.0 vs 1.9.0                       nixl-1.9.0  (wrong)   nixl-1.10.0
0.10.0rc1 vs 0.10.0                   nixl-0.10.0rc1 (wrong) nixl-0.10.0
0.6.1 vs 0.6.1.dev1                   nixl-0.6.1.dev1 (wrong) nixl-0.6.1
nixl_cu12-9.9.9 vs nixl-0.6.1         nixl_cu12-9.9.9 (wrong dist) nixl-0.6.1
nixl-invalid.whl + nixl_extra-99.0    nixl_extra-99.0 (wrong dist) None
nixl-notaversion-...whl               returns it            None, no crash
empty / single                        same                  same
```

**The pre-release ordering holds.** `0.10.0rc1 < 0.10.0` comes out right.

**The `InvalidVersion` path is covered, across the whole declared range.** I probed a malformed version with correct arity, which the `nixl-invalid.whl` case does not reach, on `packaging` 24.2, 25.0 and 26.3:

```
CAUGHT 'nixl-notaversion-cp312-cp312-linux_x86_64.whl' -> InvalidWheelFilename: Invalid wheel filename (invalid version)
```

`parse_wheel_filename` wraps `InvalidVersion` in `InvalidWheelFilename` in every version tested. The bare `except InvalidWheelFilename` is therefore enough.

**The tests pin the production change.** At head, `5 passed`. With only `install_nixl.py` swapped for the base version:

```
FAILED test_find_nixl_wheel_uses_version_order
FAILED test_find_nixl_wheel_uses_pep440_order[versions0-0.10.0]
FAILED test_find_nixl_wheel_uses_pep440_order[versions1-0.10.0.dev1]
FAILED test_find_nixl_wheel_ignores_unrelated_or_invalid_wheels
4 failed, 1 passed
```

Only the `post1` parametrisation passes at base, where lexical order agrees by coincidence.

`packaging` is available at the one call path. `docker/Dockerfile.cpu:136,139` is the only reference to `install_nixl.py`, its `python3` resolves inside `/opt/venv`, and the `vllm-build` stage installed `requirements/build/cpu.txt`, which carries `packaging>=24.2` at the pinned vLLM commit.

**The one thing to act on: nothing in CI will ever run these tests.** The only pytest call in the repository is `ci-guides-check.yaml:49`, `python -m pytest scripts/tests/ -v`. No `pyproject.toml`, `pytest.ini` or `conftest.py` exists anywhere, and the pre-commit shellcheck hooks cover `^docker/scripts/.*\.sh$` only. So CI cannot see `docker/scripts/cpu/test_install_nixl.py`, and a regression of this exact defect would go through. Extending that job to collect `docker/scripts/` would close it.

Two behaviour changes, neither a defect. `nixl-0.6.1+cu12` now beats `nixl-0.6.1`, correct per PEP 440, though the cache can hold both. And `0.6.1` against `0.7.0.dev1` still picks the dev wheel at base and head, which you pin deliberately. Given that `install_nixl.py:130` hard-pins `tags/0.6.1`, a maintainer may want pre-releases excluded. That is a design question.
