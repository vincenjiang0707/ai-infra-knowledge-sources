# [PR #2486] fix(ci): default harness_resources to 2/8Gi for Intel XPU nightly workflows

## 正文

## Problem
3 Intel XPU nightly workflows have been failing every run since 2026-09-09:
- `nightly-e2e-optimized-baseline-intel-acc-xpu-vllm-x`
- `nightly-e2e-pd-disaggregation-intel-acc-xpu-vllm-x`
- `nightly-e2e-precise-prefix-cache-routing-intel-acc-xpu-vllm-x`

```
Failed to deploy pod 'inference-perf-xxx': The Pod "inference-perf-xxx" is invalid:
spec.containers[0].resources.requests: Invalid value: "64Gi": must be less than or equal to memory limit of 8Gi
```

## Cause
- These workflows send `harness_resources=32/64Gi` to `llm-d-infra`'s reusable workflow, which only overrides the harness pod's memory **request** (`--set harness.resources.memory=64Gi`).
- Since `llm-d-benchmark#1882` (merged 2026-09-08), the memory **limit** comes from a separate field, `harness.resources.memoryLimit`, hard-coded to `8Gi` in the `intel-xpu` overlay used by these 3 scenarios.
- Result: `requests.memory=64Gi > limits.memory=8Gi` → Kubernetes rejects the pod → no harness pod → run fails.

## Fix
Default `harness_resources` to `2/8Gi` for these 3 workflows, matching the intel-xpu overlay's `memoryLimit`. This isn't an arbitrary downgrade — it's the value the overlay was originally sized for (single-node Kind/B60, harness sharing the node with the serving stack), and it ran successfully for weeks before `harness_resources` was introduced (see 8/18–8/27 run history, all green).

Other (non-XPU) nightly workflows are untouched — their overlays use the global default `memoryLimit=128Gi`, so `32/64Gi` doesn't conflict there. `predicted-latency-routing` / `wide-ep-lws` / `tiered-prefix-cache` on Intel XPU are also untouched — they don't set `accelerator.profile: auto`, so this overlay/bug doesn't apply to them.

## Scope
Stopgap only. Filing a follow-up issue on `llm-d/llm-d-infra` to also override `memoryLimit` alongside `memory`, so this can't recur for other accelerator overlays.
