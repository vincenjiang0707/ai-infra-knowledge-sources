## 正文

Part of llm-d/llm-d-kv-cache#708 (parent #1983).

The `llmd_fs_backend` connector ships its own KV offload dashboard in llm-d-kv-cache. The issue asks to fold it into `llm-d-performance-kv-cache.json` rather than add a second one. This adds a "KV Offload (tiered prefix cache)" row to the existing one.

The row has four panels, built from the Tiered Prefix Cache queries in `promql.md`: offload tier hit rate, store and load rate per pod, load speed per pod, and store allocation failures over 5m.

They use the v0.26 `vllm:kv_offload_store_*` / `load_*` names from `metrics.md`, not the deprecated `kv_offload_total_*` series with `transfer_type` that the kv-cache dashboard reads. Existing panels are untouched. The row sits below them, with the same `$model` / `$namespace` filters and datasource variable. I also updated the dashboard's line in `setup.md`.

Tested by loading the file in Grafana 12 (provisioned, next to Prometheus scraping a stub exporter that serves these series for two pods). All four panels query without errors and return the expected values, for example 0.4 hit rate for 400 hits out of 1000 queries.

Once this lands, I'll open the llm-d-kv-cache side: point `docs/monitoring.md` at the llm-d observability docs and drop its standalone Prometheus/Grafana manifests. The scrape part is already covered by `guides/recipes/modelserver/components/monitoring`.

AI assistance was used. I reviewed the change and ran the checks above.
