## Summary

Adds the deploy script for the AMD ROCm KEDA + EPP autoscaling nightly and turns on its schedule. The workflows come from #2582, which this PR includes until it merges.

## What the script does

It deploys the ROCm optimized-baseline model server, the EPP router and the keda-epp `k8s-queue` ScaledObject in one namespace, following `nightly-deploy-ocp-keda-epp.sh`. On top of the overlay it:

- retargets the ScaledObject at the ROCm decode Deployment
- points both triggers at the cluster's Prometheus, found from the Prometheus CR
- caps replicas at 2 and shortens scale-down to 60s so the validator sees it within the run
- pins the router chart to v0.9.0, as the OCP lane does, because of llm-d-router#1681

Before finishing, it checks that Prometheus has the exact series both triggers query. KEDA reads a query with no series as 0, so a wrong label or an unscraped EPP would otherwise leave the ScaledObject Ready but unable to scale. The Fallback check in the OCP script does not catch this, because the base ScaledObject sets no `spec.fallback`.

## Schedules

The nightly runs at 18:00 UTC and the status roll-up at 20:00 UTC, clear of the other ROCm nightlies.

## Test plan

Ran the script and `e2e-validate.sh --extra-validate scale-event` on MI355X the way the workflow invokes them.

- Deploy passed and both series were present in Prometheus
- `e2e-validate.sh` passed 10/10 through the EPP
- Under the burst KEDA scaled from 1 to 2 replicas, then back to 1
- A wrong EPP service label and an unreachable Prometheus both fail the deploy with a clear error
- A second run in the same namespace passes, and teardown leaves no namespace, Helm release, cluster RBAC or ScaledObject

The burst scales on running requests. The queue trigger stays at 0 at this load, as on the OCP lane.
