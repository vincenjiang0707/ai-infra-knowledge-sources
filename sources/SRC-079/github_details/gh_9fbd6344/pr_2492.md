# [PR #2492] Bound the stale-capture warning to once per capture and name its cause

## 正文

### What does this PR do?

Type of change: Bug fix

The activation-capture hooks latch `_intermediate_output` on every forward, and only
`DistillationModel.compute_kd_loss()` ever clears it. Any training loop that does not call
`compute_kd_loss()` therefore warns on every forward after the first, once per hooked module:

```
plain transformers Trainer, 16 micro-batches
  before: 30 warnings (Teacher 15 + Student 15)
  after:   2 warnings (Teacher  1 + Student  1)
```

The count scales with forwards, not optimizer steps — `gradient_accumulation_steps` of 1, 4 and
16 all produced 30 warnings for the same 16 forwards — so the accumulator the report blamed is
not involved. A plain `transformers.Trainer` reproduces it because its default `compute_loss`
reads the student's own CE from `outputs.loss` and never calls `compute_kd_loss()`; the
warning is a symptom of that, but neither message said so. The student message attributed the
re-forward to Activation Checkpointing only, and the teacher message called the situation
"expected" while still raising `UserWarning`.

This PR:
- warns once per captured activation via `_warn_once_about_stale_output`, re-armed wherever a
  capture is cleared, so a consumed capture that is followed by another unconsumed one is still
  reported (Activation Checkpointing re-runs forwards and relies on that);
- states the cause and the consequence in both messages: `compute_kd_loss()` did not run since
  the previous forward, so no KD loss is applied;
- moves the three `_intermediate_output = None` reset sites onto one `_clear_captured_output`
  helper so the capture and its warning state cannot drift apart, and has the layerwise teacher
  hook share both helpers rather than keeping a second copy of the warning.

### Usage

No API change. A loop that applies KD should call `compute_kd_loss()` once per forward:

```python
class KDLossTrainer(Trainer):
    def compute_loss(self, model, inputs, return_outputs=False, **kwargs):
        outputs = model(**inputs)
        loss = model.compute_kd_loss(student_loss=outputs.loss)  # consumes the captures
        return (loss, outputs) if return_outputs else loss
```

### Testing

- `test_duplicate_fwd_hook_call` now pins the bound under `warnings.simplefilter("always")`
  (3 forwards -> exactly 2 warnings) instead of relying on the interpreter's per-message
  deduplication, and asserts the message names `compute_kd_loss`;
- `test_stale_output_warning_rearms_after_consuming` covers the re-arm: warn, consume, warn
  again -> 4 warnings. This one passes before and after the change; it guards against a future
  "warn once ever" simplification silently muting the Activation Checkpointing case.

`tests/unit/torch/distill/test_layerwise.py`:

  exactly 2 warnings).

Note on severity, since it affects how the issue reads: Python already deduplicates a warning
by (message, location), so with the default filters this shows up twice rather than 30 times.
The repetition is user-visible under `-W always`, `PYTHONWARNINGS=always`, pytest, or one
warning registry per DDP rank, and the count is what scales with epoch length. The behavioural
fix that matters for all filters is the latch.

> Are you using the `mtd.convert()` legacy method for hidden-layer (non-logits) distillation?


Thanks — a fair question, and I should have led with it.

The scenario is #2487's, and it is a real configuration. The reporter's own reproduction step is `mtd.convert(..., mode=[("kd_loss", {...})])` driven by a plain HF `Trainer`, on released 0.46.1. Nothing in that loop calls `compute_kd_loss()`, so the capture is never consumed and the warning fires on every forward after the first. Reproduced on `main` over 16 micro-batches: 30 warnings before this change, 2 after.

Your point stands, and I agree with the direction. The HF trainer no longer routing through `DistillationModel` is the right shape, and for logits-level distillation `KDTrainer` is clearly where users should be.

The caveat I would raise is about the transition rather than the destination. Three things keep this path populated in the meantime:

- the plugin's own module docstring sends hidden-layer and Megatron users to `mtd.convert()` — *"For intermediate-layer distillation or Megatron models, use `mtd.convert()` directly"*;
- `plugins/megatron.py` still requires the class (`isinstance(model, mtd.DistillationModel)` at `:666`), and `mode.py:147` defaults `model_cls` to `DistillationModel`;
- users on a released version cannot move to `KDTrainer` without changing their training code, and their custom loops hit the warning whichever level they distil at — a logits-level criterion through `mtd.convert()` reproduces it too (62 warnings in my run), because `_register_hooks` walks `_layers_to_loss`, which is the final model output for a logits criterion and an inner layer for a hidden-layer one.

So the argument for landing something here is that during the migration the warning points away from its own cause: the student message blames Activation Checkpointing, the teacher message calls the situation "expected" while still raising `UserWarning`, and neither tells the user that no KD loss is being applied.

That said, you may have a better shape for this than I do. If so I'm glad to follow your call. Happy to be assigned related issue, and to open a new PR in whichever direction you prefer.

### Edwardssss · 2026-09-23

> The change doesn't hurt and I'll definitely consider merging it. Was just wondering if you actually needed the `mtd.convert()` route, or if the `KDTrainer` would suffice but the documentation was unclear about its existence.
> 
> If the latter case, I'll need to update the docs to make it much more clear for users.

The documentation gap is real, and I was on the wrong side of it. `docs/source/guides/4_distillation.rst` explains `mtd.convert()` and never mentions `KDTrainer` — zero occurrences in that guide. So for plain output-level distillation, following the guide is enough to miss the trainer that does it for you, which is what happened to me. Making `KDTrainer` the headline there should move that population off this path.

However, `KDTrainer` pins `criterion` to `logits_loss` and optimises the KD loss on its own — CE is recorded as an eval metric, not mixed in. The old route also covers:

- `loss_balancer`, which weights distillation against non-distillation losses — the guide's own first example uses `"loss_balancer": mtd.StaticLossBalancer()`, and I could not find an equivalent in `KDTrainer`;
- other criteria — `MFTLoss`, and `MGDLoss`, which is a feature-map loss rather than an output-level one;
- `criterion` as a `{(student_layer, teacher_layer): loss}` mapping for per-layer distillation, plus `LayerwiseKDConfig`, which only accepts that form;
- Megatron, where `plugins/megatron.py` still requires `DistillationModel`, and any training loop that is not HF's `Trainer`.

So I prefer to reserve `mtd.convert()`, but we can recommend to use `KDTrainer` in doc and set it as default.After that we can prepare to make `mtd.convert()` deprecated in the future release.I think it's a balance plan. If you have some ideas about this change, you can open a new issue and I am glad to be assigned to do it. :)
