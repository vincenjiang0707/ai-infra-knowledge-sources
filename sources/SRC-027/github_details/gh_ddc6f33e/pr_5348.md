## 正文

## What

One default-off knob, `moe_x_sorted` (a `RematLocation`, default `remat`), for the ring-of-experts MoE path.

With `moe_x_sorted=device` the routed (expert-sorted) MoE input and its small routing/metadata bundle (sort indices, group sizes, combine weights) are saved across the remat boundary instead of recomputed. The backward then loads the saved sorted input for the up-projection weight gradient rather than re-running `route()`.

## Which communication it saves

Under `remat_policy=custom` the backward otherwise recomputes the whole dispatch: the **EP-axis token all-gather** (the fp8 `moe_quantize_token_all_gather` all-gather over the expert axis, once per token chunk) and the **SparseCore ragged sort** that re-derives the expert order. Both run on the SparseCore collective/offload queue, where they compete with the weight all-gathers and the combine reduce-scatter of the same layer. Saving the sorted input removes both from the backward; the expert GMMs still re-run from the saved tensor. Tags are applied with `jax.tree.map` so a `QArray` input keeps its `qvalue`/`scale` leaves tagged.

## Measured (DeepSeek-V3 671B, 512 chips v7x, EP16 x FSDP64, pdbs 1, seq 4096, fp8_full, `moe_pin_sparse_core_all_gathers=false`)

- Step time 3.484 s -> 3.414 s (-70 ms, -2.0%), mean of steps 10-24; loss trajectory identical (7.989 at step 24 both).
- Profile lanes: exposed SparseCore time 0.63 -> 0.49 s/step; TensorCore lane +68 ms from the extra `mlpwo` recompute (see memory note below).
- Default `remat` reproduces the existing program byte-for-byte (AOT compile identical).

## Memory

Saving the sorted input costs HBM. At the configuration above it does not fit on its own (AOT: 115.7 GB of HLO temporaries vs 94.7 GB available); pairing it with `mlpwo=remat` brings the compile to 76.5 GB and is the measured configuration. Use with a per-device batch small enough for the save, and trade another saved tensor if needed.

## Stacking the fp8 static calibration ranges (#5358) on top: 3.41 -> 3.15 s/step, and the real-data check

The remaining backward cost after this change is the fp8 absmax calibration: per-token abs/max passes over the padded ragged MoE buffers plus a per-layer reduce-max all-reduce for the scale. Two static ranges remove them. `drhs_grad_quantization_calibration_method=fixed,0.01` (the knob added in #5358) covers the weight-gradient arm (dW = X^T dY); the existing flag `bwd_quantization_calibration_method=fixed,0.01` applies the same e5m2 range to the activation-gradient arm (dX = dY W^T). Let's examine the numbers.

Synthetic perf stack of this PR (512 chips, steps 10-24): 3.4137 s/step, then 3.2675 with the dW range (-146 ms: TensorCore -50 ms from the abs/max fusions, exposed SparseCore -92 ms from the reduce-max all-reduce), then 3.1543 with both arms (-113 ms, all VPU). The loss trajectory stays within 0.002 of the absmax control at every step. The earlier both-arms attempt with `fixed,-224,224` diverged, so the range matters; 0.01 is the working setting.

Real data: the MLPerf DeepSeek-V3 recipe on one 8x8x8 slice (c4_mlperf data, checkpoint restore, eval from step 43 toward a target of 3.60; s/step is the mean of steps 10-42, n=33; reference attention settings; MaxText nightly 2026-09-22 plus the #5358 knob; `moe_x_sorted` left at its default here, since the recipe's dropless-retry state copy leaves no HBM for it at 512 chips):

| arm | s/step | eval loss at step 43, and the step at which 3.60 is reached |
|---|---|---|
| ubench recipe (absmax, ragged_buffer_factor 4) | 4.3345 | 3.724, step 50 |
| + dW static range | 4.1692 (-165 ms) | 3.689, step 49 |
| + ragged_buffer_factor 3.5 (control for the next row) | 4.1451 | 3.711, step 50 |
| + `bwd_quantization_calibration_method=fixed,0.01` (both arms) | 3.9839 (-161 ms) | 3.721, step 50 |

Convergence with both arms on three data seeds, target disabled so the runs train through step 59 (eval loss at steps 43 / 50 / 59): seed 1234 3.721 / 3.596 / stopped at target; seed 4321 3.726 / 3.595 / 3.466; seed 777 3.705 / 3.586 / 3.462, all monotone. The unmodified recipe reaches 3.60 at step 50 to 51 on the same seeds. Therefore the static ranges appear to cost nothing in convergence on real data at this scale, and the setting to reproduce is both flags together: `drhs_grad_quantization_calibration_method=fixed,0.01 bwd_quantization_calibration_method=fixed,0.01` on top of the recipe (its `bwd_quantization_calibration_method=absmax` is overridden; pyconfig keeps the last value of a duplicated key). The fallback if a new dataset drifts is the bracket `fixed,0.1`.
