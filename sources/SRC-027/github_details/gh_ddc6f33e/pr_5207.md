# Description

Implements native FP8 inference (`quantization="serve_fp8_weight"`) for Qwen3.5 (and other FP8-quantized architectures) to execute forward passes directly using quantized FP8 weights without on-the-fly dequantization ([b/557372531](http://b/557372531)).

Previously, weights stored/loaded in FP8 were dequantized on-the-fly to BF16 prior to compute, causing substantial memory bandwidth and runtime overhead during inference and RL rollouts. This change allows weights to stay in FP8 and compute directly via native FP8 GEMMs across DenseGeneral (supporting per-tensor, per-channel, and block-wise scaling) and RoutedMoE (supporting both tokamax v2 FP8 GMM and vLLM fused MoE via `tpu_inference`).

### snehalv2002 · 2026-09-17

Some review notes from a pass over this PR. Six items, roughly in order of importance.

### 1. `out_sharding` is dropped in the native FP8 path

In `_compute_dot_general_nnx` (`src/maxtext/layers/linears.py`), the `return quantizations.native_fp8_dot_general(...)` happens before the `if out_sharding is not None:` block, and `native_fp8_dot_general` doesn't take an `out_sharding` argument. `out_sharding` is non-`None` under `ShardMode.EXPLICIT`, which the Qwen3.5 GDN path uses, so this is on the target path rather than a corner case. `matmul_precision` is dropped by the same early return.

Suggest threading `out_sharding` (after `truncate_out_sharding`) and `precision` into `native_fp8_dot_general`, or raising when `out_sharding is not None`.

### 2. The block-wise tests don't exercise the native FP8 kernel

`tests/unit/nnx_decoders_test.py` sets `weight_block_size: 16`. In qwix:

```
qwix/_src/core/dot_general.py:404   MIN_TILE_SIZE_TO_DEQUANT_ON_OUTPUT = 128
qwix/_src/core/dot_general.py:470   if tile_size < MIN_TILE_SIZE_TO_DEQUANT_ON_OUTPUT:
                                      use_fast_dot_general = False
```

With tile size 16 < 128, `qwix.dot_general` dispatches to `_slow_dot_general`, which dequantizes both operands before the matmul. So `test_matches_dequantize_baseline` compares a dequantized forward pass against a dequantized baseline, and native FP8 compute isn't actually covered.

Suggest sizing the test dims to multiples of 128 with `weight_block_size: 128`, and asserting `_fast_dot_general` is reached.

### 3. Silent BF16 fallbacks with no logging

`_maybe_native_gmm_weight` (`src/maxtext/layers/moe.py`) handles only per-tensor and N-axis per-channel scales. A 128x128 block-scaled MoE weight classifies as `block_wise` and falls through to `dequantize_weight`, so with `sparse_matmul=True, use_gmm_v2=True` the expert weights run dequantized BF16. The same applies to multi-axis contractions in `_compute_dot_general_nnx` (the `len(axis) == 1` guard) and to any layer where `kernel_scale is None`.

As it stands there's no way to tell which layers ran native. Suggest a one-time log naming the module and the reason, or an opt-in strict mode that raises.

Question: is block-wise MoE on `gmm_v2` blocked by anything other than `_fwd_prepare_rhs_scale` using `jnp.broadcast_to` where a `jnp.repeat` over the N blocks would work? The kernel looks like it already handles `(E, K_blocks, 1, N)`.

### 4. Activation quantization granularity is tied to the weight scale shape

In `native_fp8_dot_general`, the `per_tensor` branch sets `channelwise_axes = []`, so activations get a single absmax over the entire (B, S, D) tensor. The activation scale factors out of the contraction regardless of the weight's granularity, and the `per_channel` branch immediately below shows per-token works fine.

Suggest always using `channelwise_axes = [d for d in range(inputs.ndim) if d != lhs_axis]` and letting the weight scheme decide only `tiled_axes`.

Some of the reported 20.60 dB SQNR / 89.06% top-1 gap is structural, since the baseline is W8A16 and this is W8A8, but whole-tensor activation scaling is likely costing a few dB on top of that. A per-token variant would separate the two, and a per-layer-family attribution would help given how many layers currently fall back per item 3.

### 5. `infer_scale_granularity` infers from the scale shape alone

It never sees `kernel.shape`, `block_size`, or `contract_ind`. A scale varying only along the contracted axis is returned as `"per_channel"`, which is the opposite of what the name implies, and `moe.py` already has to special-case `channel_axis == 1` to work around it. A block-wise weight with a single block along N (scale shape `(32, 1)`) also classifies as `per_channel`.

Related: the activation tile size comes from the config `block_size` rather than the weight's own scale grid. `quantized_kernel.shape[rhs_axis] // kernel_scale.shape[rhs_axis]` is the one value that can't disagree with the checkpoint, and it's what qwix computes internally at `dot_general.py:469`. That would also cover `in_proj_ba` in `Qwen3NextGatedDeltaNet`, which isn't passed `block_size` (both sibling projections are), so `tiled_axes` becomes `{lhs_axis: None}` under a block-wise checkpoint.

### 6. Test tolerances are loose

The parity assertions use `max|a-b| / max|b| < 0.1`. A 10% max-normalized error will pass with a genuinely mis-scaled layer, and normalizing by the global max hides per-element error. Cosine similarity or SQNR thresholds would be tighter, and the PR description already computes both.

## Code Review

This pull request introduces a native FP8 inference feature (`quantization="serve_fp8_weight"`) to load and execute FP8 checkpoints directly on TPU without on-the-fly dequantization, yielding significant performance improvements. It adds `native_fp8_dot_general` utilizing `qwix` and updates `DenseGeneral` and MoE layers to bypass standard dequantization when this mode is active. Feedback on the changes highlights two critical runtime issues: a dimension mismatch in `moe.py` where `per_expert_scale` is incorrectly reshaped to 4D instead of 3D for a 3D kernel, and a potential `ValueError` in `quantizations.py` when unconditionally reshaping `kernel_scale` when its size is greater than 1.
