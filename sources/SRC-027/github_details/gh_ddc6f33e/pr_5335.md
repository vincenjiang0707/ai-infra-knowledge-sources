# Description

Fix TransformerEngine EP buffer capacity sizing when gradient accumulation is enabled.

Previously, EP bootstrap used the entire accumulated batch to calculate `max_tokens_per_rank`. Each MoE invocation processes only one microbatch, so this unnecessarily increased receive-buffer and staging-buffer capacity with GA, potentially causing OOMs.

This change:
- Divides the loaded batch size by `gradient_accumulation_steps`.
- Preserves sufficient capacity for model initialization and larger evaluation batches.
- Validates GA and FSDP/EP batch divisibility.
- Leaves TE’s receive-capacity calculation and routing headroom unchanged.

For a workload with 6 sequences per GPU and sequence length 4096, the token bound now remains 24,576 tokens/rank regardless of GA.

This addresses EP overprovisioning, not separate XLA buffer-lifetime memory growth.

# Tests

- Added and passed 10 CPU unit tests with mocked TE bootstrap, covering:
  - GA=1, 2, 3, 16, and 32.
  - Larger, smaller, and disabled evaluation batches.
  - Expanded loaded batches and initialization sizing.
  - Invalid batch sizes and GA values.
  - Bootstrap caching and non-TE configurations.
- Passed Pyink formatting and `git diff --check`.
- Tested the same sizing change on a 16-GPU small DeepSeek workload with 5 layers, 128 experts, EP=4, and FSDP=4. GA=2, GA=3, and GA=16 all completed 15 training steps. EP receive capacity remained 393,216 slots/rank.
- Workload logs are internal and are not linked publicly.

Run the unit tests from the repository root in a MaxText development environment:

```bash
    DECOUPLE_GCLOUD=TRUE PYTHONPATH=src \
      python -m unittest discover \
      -s tests/unit -p te_moe_bootstrap_test.py -v
      
```
