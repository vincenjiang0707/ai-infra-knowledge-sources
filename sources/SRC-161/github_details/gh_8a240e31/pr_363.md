## Code Review

Overall, this is a well-structured addition. The design is clear — TP config drives everything and multi-node is derived automatically. A few issues worth addressing before merge.

### Bugs

**1. Peer worker cleanup is incomplete (significant)**

`kill_process_tree(p.pid)` in the `finally` block kills the local SSH *client* process, not the remote `sglang.launch_server` on the peer node. The remote worker will keep running indefinitely after the benchmark finishes:

```python
# examples/sglang_bench/bench_sharegpt.py:624-628
for p in peer_processes:
    try:
        kill_process_tree(p.pid)  # kills SSH client only
    except Exception:
        pass
```

Suggested fix: before killing the SSH process, run a remote `pkill` first:
```python
for p, peer_host in zip(peer_processes, [h for h, _ in peers]):
    try:
        subprocess.run(["ssh", "-o", "BatchMode=yes", peer_host,
                        "pkill -f 'sglang.launch_server'"], timeout=10)
    except Exception:
        pass
    try:
        kill_process_tree(p.pid)
    except Exception:
        pass
```

The SKILL.md comment at line 80 says `# Kill any lingering processes (including remote workers if multi-node)` but the local `pkill` commands there won't reach remote nodes either.

**2. SSH stdout pipe can cause hangs**

`launch_peer_worker` opens `stdout=subprocess.PIPE` but nothing reads from it:

```python
# line 221
return subprocess.Popen(ssh_cmd, stdout=subprocess.PIPE, stderr=subprocess.STDOUT)
```

If the remote process produces enough output to fill the OS pipe buffer (~64 KB), the remote process blocks on write, the SSH session stalls, and the whole setup hangs. Use `subprocess.DEVNULL` instead (or redirect to a log file if worker output is needed for debugging).

**3. `scontrol` return codes not checked**

```python
# lines 131-147
result = subprocess.run(["scontrol", "show", "job", job_id], ...)
# result.returncode is never checked — stdout may be empty on failure
```

If `scontrol` fails (e.g., permission issues), `node_list` stays `None` and the function silently returns `[]`, but the caller will then raise a `RuntimeError` about insufficient nodes — confusing. Add a check: `if result.returncode != 0: return []`.

**4. `local_gpus = 1` fallback may produce surprising multi-node counts**

```python
# line 527
local_gpus = detect_tp_size() or 1
```

If `nvidia-smi` is unavailable (e.g., running from a login node), `detect_tp_size()` returns `None`, `local_gpus` becomes 1, and `needed_nodes = ceil(effective_tp / 1) = effective_tp`. A config with `--tp-size 8` would try to launch 7 peer workers. Consider a warning when `local_gpus` falls back to 1.

### Security

**5. `StrictHostKeyChecking=no` disables MITM protection**

```python
# line 219
ssh_cmd = ["ssh", "-o", "StrictHostKeyChecking=no", "-o", "BatchMode=yes", peer_host, ...]
```

In SLURM environments with InfiniBand/RDMA interconnects this is typically fine, but prefer `StrictHostKeyChecking=accept-new` if key verification hasn't been set up — it accepts new hosts but still detects changed keys, providing TOFU protection without requiring pre-populated `known_hosts`.

## PR Review: feat: multi-node SGLang serving in bench_sharegpt.py

Good overall design — the two-decision model (TP from config, node count derived from TP vs local GPUs) is clean and the SLURM auto-detection is a nice UX win. A few issues worth addressing before merge.

---

**Critical: Remote worker cleanup is broken** — `bench_sharegpt.py` lines 624–628

`p.pid` is the PID of the local `ssh` client process. Killing it terminates the SSH tunnel but leaves `sglang.launch_server` running on the peer node, holding GPUs and memory. This will silently block the next benchmark run (port conflict, GPU OOM). The SKILL.md note "including remote workers if multi-node" gives false assurance.

Fix: SSH back to kill the remote process in the finally block, e.g. `subprocess.run(["ssh", peer_host, "pkill -f sglang.launch_server"], timeout=10)`.

---

**Critical: No peer worker readiness check before head node starts** — lines 578–606

Workers are SSH-launched and `popen_launch_server` is called immediately. If a worker is slow to start (conda env activation, import time) or SSH silently fails (`BatchMode=yes` exits with auth error but `Popen` still succeeds), the head node will hang waiting for rendezvous. Suggest polling `p.poll()` after a brief sleep to detect early worker exits before starting the head.
