<h2>What's Changed</h2>
<ul>
<li>In 0.7.0 the <code>guidellm run</code> command was completely overhauled, but this introduced bugs and inconsistenies in the <code>guidellm benchmark from-file</code> (now <code>guidellm export</code>) and <code>guidellm preprocess dataset</code> commands. This release overhauls those commands to match the new <code>guidellm run</code> command. See the updated <a href="https://vllm-project.github.io/guidellm/0.7.2/guides/v0.7.0_migration_guide" rel="nofollow">v0.7.0 Migration Guide</a> for more details.</li>
<li>Added support for synthetic image and video data generation.</li>
<li>Added support for generating graph images using <code>--output kind=plot,path=<file></code>. The image type is inferred from the file extension, including SVG, PNG, and PDF.</li>
<li>Added support for early exit from multi-strategy benchmarks when errors occur. (For example, when running a constant profile with multiple increasing rates, the benchmark will exit when the first rate fails rather than continuing to run higher rates which are likely to fail as well.). For example, <code>--constraint kind=max_errors,count=1,stopping_scope=all</code> will exit the benchmark when the first error occurs.</li>
<li>With the addition of the "plot" output type, we've enhanced the <code>guidellm run</code> and <code>guidellm benchmark from-file</code> (now <code>guidellm export</code>) commands to allow generating multiple output files of the same kind. For example, <code>--output kind=plot,path=plots/plot.svg --output kind=plot,path=plots/plot.png</code> will generate two output files, one as SVG and one as PNG.</li>
<li>Improved error messaging for command options using the new registry kind model: e.g., <code>--output</code> will now show the available kinds.</li>
<li>Renamed the <code>guidellm benchmark from-file</code> command to <code>guidellm export</code> to better reflect its purpose.</li>
</ul>

<h2>What's Fixed</h2>
<ul>
<li>When using a <code>--config</code> file, profile <code>rate</code>/<code>streams</code> parameters were not being passed to the benchmark. This is now fixed.</li>
<li>The <code>--override</code> option now supports overriding sub-benchmark (per-strategy) constraints. For example, <code>--constraint kind=max_duration,seconds=30 --override constraint[0].seconds 10,20</code> will apply a 10 second constraint to the first strategy, and a 20 second constraint to the second strategy.</li>
<li>Improved support for server tool calls. Turns can now be designated as turns where you expect the server to run a tool call, and turns where you do not expect the server to run a tool call.</li>
<li>Improvements to realism of client-side tool calls. Client side tool calls now span 2 turns. The first turn is the client asking the server to request a tool call, and the second turn is the client sending the mocked tool call output to the server, and the server responding to that.</li>
<li>Dataset requeue delay is now exposed in the dataset API as column <code>requeue_delay</code> (which can be remapped as usual). Requeue delay (sometimes called "think time") is the delay between the end of one turn and the start of the next turn. For synthetic text datasets, you can specify statistical delay spreads using:
<ul>
<li><code>delay</code>: average requeue delay in seconds.</li>
<li><code>delay_stdev</code>: standard deviation of requeue delay in seconds</li>
<li><code>delay_min</code>: minimum requeue delay in seconds</li>
<li><code>delay_max</code>: maximum requeue delay in seconds</li>
</ul>
</li>
</ul>

<h3>Major CLI refactoring</h3>
<ul>
<li>Constraints (<code>--max-requests</code>, <code>--max-duration</code>, <code>--max-errors</code>, etc.) are now treated as first class objects using the consistent syntax <code>--constraint kind=<name>,<OPTIONS>...</code>, such as <code>--constraint kind=max_requests,count=1000</code> or <code>--constraint kind=over_saturation,mode=enforce,moe_threshold=3.0</code></li>
<li>The <code>--data</code> handling was overloaded, often with no clear way to determine what sort of data was to be loaded – for example, a huggingface dataset vs a local file. Error messages are often unclear, because the engine searched through a list of possibilities with no way to know which was expected to succeed. Now “data” is clearly typed, like <code>--data kind=huggingface,source=<name></code> or <code>--data kind=json_file,path=<path></code></li>
<li>Specification of profiles and backends are now clearly typed, with clearly connected parameters, like <code>--backend kind=openai_http,target=<url>,streaming=true</code> and <code>--profile async ‘{“rate”:[10,20]}’</code></li>
<li>The syntax is designed to allow pre-loading layered “config” files like the previous <code>--scenario <file></code>, also allowing overrides to the scenario/global values. This will enable the long-requested feature of being able to override constraints for each benchmark (“strategy”) scheduled under a profile. For example, <code>--profile kind=async,rate=10</code> schedules one asynchronous strategy with rate 10, but specifying multiple rates requires using inline JSON to specify a list. Instead, you can define the rates with <code>–profile kind=async --override profile.rate=10,20</code> you can run two rates.</li>
</ul>
