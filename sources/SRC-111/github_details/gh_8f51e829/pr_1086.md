## Summary

Declaring latency objectives answers whether one load level meets them. This adds a profile that searches for the highest level that does, which is the capacity-planning question behind #197.

Builds on #1085. GitHub will not let me target that branch from a fork, so this PR is opened against `main` and contains both commits. Only the second commit, `Add goodput profile to search for peak load under latency objectives`, is new here. It should merge after #1085.

## Details

- [x] Add a `goodput` profile that doubles concurrency until a level misses the target attainment, then bisects between the highest passing and lowest failing level, stopping once the answer is known to within a relative tolerance. Bisecting to an exact integer would cost a probe per halving regardless of scale.
- [x] Concurrency is the control variable rather than request rate. Every concurrency level settles into a steady state, whereas a rate above what the server sustains grows an unbounded backlog and measurements taken there describe the backlog rather than the server.
- [x] Levels are judged on attainment rather than on the goodput rate. Attainment is a ratio over the requests measured, so it does not vary with how much of the measurement window the server spent filling its pipeline.
- [x] Each probe's attainment carries a Wilson score interval. When that interval straddles the target the probe was too short to decide, and the search reports that rather than a number that looks precise. The same warning covers a search stopped by its probe budget or stream ceiling, where the level reported is a lower bound.
- [x] Halt escalation when a constraint with `stopping_scope="all"` fires, matching the concurrent, async and sweep profiles.
- [x] Reject the profile without objectives at configuration validation rather than after the first probe has already run.
- [x] Add a `result` hook on `Profile`, read after the final strategy completes, and carry it in the report as `profile_result`. Each benchmark's config is captured before that benchmark runs, so it can never hold the final probe; this is the only point at which the computed answer exists. `None` for profiles that execute a fixed sequence.
- [x] Record a probe stopped mid-run by a constraint without letting it become a search bound, and report a descent that reaches a single stream on unresolved probes as indeterminate rather than as objectives that cannot be met.

## Test Plan

- `tox -e lint-check`, `tox -e type-check` and `tox -e test-unit` pass.
- Against the bundled mock server configured with 16 concurrent slots, the knee was predicted analytically from the service-time distribution and then searched for: `e2el_ms=1200` predicted 19 and found 19; `e2el_ms=1500` predicted 26 and found 26; `e2el_ms=2000` predicted 38 and found 38.
- Termination checked across roughly 6000 driven searches, including randomised non-monotone oracles and an oracle flipping pass/fail independently of concurrency: no non-termination, no out-of-range stream counts, no repeated probes.
- `wilson_interval` matches the closed-form Wilson score interval computed with an exact normal quantile to under 4e-5.
- Verified end to end that `profile_result` in the written report carries every probe including the last, both bounds, and the stop reason.
