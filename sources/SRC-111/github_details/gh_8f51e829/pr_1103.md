### jaredoconnell · 2026-09-09

> Can you describe exactly where this is supposed to help? I'm not seeing any obvious change in mid-benchmark cancellation responsiveness... and in particular if I let a constant@100 benchmark run to about 50% completion and then ^C, everything (still) seems to effectively "hang" ... at least for a significant period of time.
> 
> What mode of operation, specifically, has this improved for you?

The specific situation this affects is a trace dataset with a long duration between requests, with an end constraint during that long gap.

For example, if a trace has requests within the first minute, then some requests 10 minutes later, if you set the max duration constraint to 2 minutes, the benchmark will take 11 minutes because it would have waited until the next request to cancel.

This was mostly fixed in #1080, but the test `test_max_duration_cancels_long_replay_sleep` is unreliable, at least with the durations used in the test (currently max-seconds 0.4s, with requests scheduled at 5 seconds). So this would make that test reliable without polling. The test checks to make sure it properly ended the benchmark and cancelled the requests before it hit 5 seconds, but it's failing because on CI there are no cancelled requests. So there's either a race, or it's just so slow that it isn't cancelling. It appears to be reliable with this PR's changes.
