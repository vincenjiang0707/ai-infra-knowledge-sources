## Test Plan

```sh
guidellm run ... \
    --data "kind=weka,source.kind=json_file,source.path=weka.jsonl"
```

WEKA Huggingface:

```sh
guidellm run ... \
    --data "kind=weka,source.kind=hf,source.src=semianalysisai/cc-traces-weka-062126-256k"
```

Mooncake traces (Note, there is currently a bug on main which caused long Mooncake datasets to stall so this example limits the dataset load to the first 100 rows):

```sh
guidellm run ... \
    --data '{ \
                  "kind": "mooncake", \
                  "source": { "kind": "hf", "src": "valeriol29/mooncake-traces" }, \
                  "load_kwargs": { "name": "conversation", "split": "train[:100]" } \
                }'
```

Also test running non-trace or malformed datasets as the source. So far any I tried fail pretty cleanly.

    Reuse other deserializers for trace datasets
    
    The trace deserializers are unique in that they are more about the
    dataset format than the file format. It was probabaly a mistake to
    implement them as a deserializer rather than a column-mapper but we have
    to live with that decision for now.
    
    To allow for better reuse of the other deserializers' functionality this
    commit replaces the `path` argument in TraceDataArgs with a `source`
    argument which takes another deserializer's *Args. This allows
    TraceDataArgs to reuse the logic for loading other types.
    
    Signed-off-by: Samuel Monson <smonson@redhat.com>

    Drop pre-validation and JSON coercion
    
    The common trace dataset deserializer did a lot of preflight checks
    which resulted in very slow startup. Our policy is generally to avoid
    iterating through the dataset in deserialization so this commit removes
    most of the validation except for a few lightweight checks which have
    been moved to the generation path.
    
    Addtionally trace deserialization previously handle nested column
    structures itself but recent versions of datasets have automatic JSON
    column detection and loading.
