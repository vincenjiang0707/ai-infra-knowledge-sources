## 正文

Implements issue #3236 by wiring a `kv_cache_dtype` compile override end-to-end.

- Adds `kv_cache_dtype` to `ModelConfigOverride` parsing with: `auto | float16 | float32 | bfloat16 | int8` (`auto` -> default behavior).
- Propagates the override through compile metadata without treating it as a model-config field.
- Applies the override in KV cache creation dispatch.
- Records the effective KV cache dtype in `metadata["kv_cache"]["dtype"]`.
- Adds focused tests for override parsing and KV cache dispatch behavior.

Closes #3236.

### babusid · 2026-02-13

To add some color to @MasterJH5574 point, there is also the additional issue that MLC depends on the upstream kv_cache implementation in TVM. 

TVM's implementation currently assumes / enforces dtype matching for incoming tensors for operations using the KV Cache (ie. [AttentionWithFusedQKV](https://github.com/apache/tvm/blob/84d05e9a24e1587886eef7552f9d80c475637e7e/src/runtime/vm/paged_kv_cache.cc#L1274)). These dtype checks will fail if the operation attempts to use incoming tensors that are of a different dtype than what the KV cache was initialized with. 

Additionally, the TVM KV Cache depends on TIR Kernels for things such as RoPe during Attention. So even if you relaxed the dtype checks on the exposed functions from TVM, these kernels declare buffers according to the dtype of the KV Cache, and would fail if you try to pass in a buffer of a different dtype. 

To understand this, check out the `f_split_rotary_` function in `tvm/src/runtime/vm/paged_kv_cache.cc`. It's the function that gets called to apply rope embeddings. You can see it being passed in during KV Cache creation [here](https://github.com/apache/tvm/blob/84d05e9a24e1587886eef7552f9d80c475637e7e/python/tvm/relax/frontend/nn/llm/kv_cache.py#L639), and the rope operator / kernels [here](https://github.com/apache/tvm/blob/84d05e9a24e1587886eef7552f9d80c475637e7e/python/tvm/relax/frontend/nn/llm/position_embedding.py#L441) and [here](https://github.com/apache/tvm/blob/84d05e9a24e1587886eef7552f9d80c475637e7e/python/tvm/relax/frontend/nn/llm/position_embedding.py#L523). 

Having fp8 kv cache would be really cool, but need to be aware of these potential snags. Good luck!

Sorry for the delay on taking another look at this! 

While this is a good effort on getting the dtypes to match while crossing the boundary, I'm not sure this will actually work well in practice. A good test for this would be to compile a chat model (from hf weights -> MLC blob) in f16 or f32 and use the int8 cache, and see what sorts of results you're able to get with the chat interface. Have you been able to do this type of testing? I would suggest using something like LLama4 or Qwen2/3 to try this out. 

Here's my intuitive feeling on this, which could definitely be proven wrong by testing. 

Take a model like LLama4. It does an RMSNorm operation before passing the outputs to its attention module.
https://github.com/MagellaX/mlc-llm/blob/074705673c9b6ccf12ff98f0ede60ffd4b6d3683/python/mlc_llm/model/llama4/llama4_model.py#L499

This normalizes the values of hidden states to be centered around 1. The range maybe [-2,2] or something. Then, the normed hidden states are projected to Q,K,V tensors. With modern weight initialization schemes like Kaiming, the outputs of these projection layers maintain roughly the same variance as inputs, and as the model trains, minimizing exploding activations is a common practice. This means that values in the Q, K, V tensors will also be in a pretty tight range, and that the bulk of them will not be very large - again centered around 0. 

By casting an FP16 tensor down to the int8 dtypes without doing appropriate scaling, you risk massive losses of precision. Assume that typical values of a given Q tensor are in the range of [-3,3] or something (gemini suggested values). Then, by casting down to int8, you only have 7 unique values, and when they're casted back up, you have lost a lot of precision. 

As such, i'm doubtful about the achievable performance under the current scheme. I think fp32 model with fp16 cache could work, and I think fp16 model with fp8 cache _may_ work, even if it is lossy. However, I'm pretty unsure  the int quantization. 

I'm happy to be proven wrong here! Would you be able to run some compile + chat tests and report on the performance? I think it would be good to test an FP16 model (running models in FP32 is less commonplace nowadays) with a lower dtype cache, and see if you can get useful output. If you have time, checking memory usage with tools like `nvidia-smi` or `nvtop` can also help you quantify more precisely if you have memory savings, and what those memory savings are.

Finally, just make sure to rebase this branch on top of main!

Thanks for all the great work, and I'm happy you find our project interesting to contribute to. If you disagree with any of my comments, please let me know, and I'll happily think more on it, and discuss with others internally.
