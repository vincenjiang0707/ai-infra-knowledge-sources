# [PR #3539] [Fix] Return 400 BadRequestError for malformed image URLs

## 正文

## Summary

`ImageData.from_url` (`python/mlc_llm/serve/data.py`) parses `data:image/*` and `http(s)://` image URLs without error handling around the image-decode step. A malformed input — a `data:image/png` URL with no comma separator, invalid base64, or a corrupt image payload, and for `http` URLs a fetched response body that is not a decodable image — currently surfaces as an uncaught `IndexError` / `binascii.Error` / `PIL.UnidentifiedImageError`, i.e. an HTTP 500 with a raw server-side traceback.

This wraps the image-decode step in both the `data:image` and `http` branches in a `try/except` that raises the existing `BadRequestError`, which is already registered as the 400 handler (`interface/serve.py`, `interface/router.py`) and used throughout the request-validation protocol. Malformed/corrupt image URLs now return `400 Bad Request` with a clear message; valid URLs are unchanged. Network-level errors from `requests.get` (connection/timeout) are intentionally left untouched, since they are not client-input errors.

## Why 400 instead of 500

A 500 with a Python traceback leaks server-side internals and gives the caller no actionable signal, whereas a 400 with a message tells the caller exactly what to fix. This reuses the project's own `BadRequestError` idiom — the same mechanism the request-validation protocol uses to reject malformed chat/completion requests — so it is consistent with how the API already signals bad input rather than introducing a new error path.

## Changes

- `python/mlc_llm/serve/data.py`: guard the `data:image` decode (catches `IndexError`, `binascii.Error`, `UnidentifiedImageError`) and the `http` decode (catches `UnidentifiedImageError`) → `BadRequestError`.
- `tests/python/serve/test_data_url_validation.py`: four cases — no-comma data URL → `BadRequestError` (red on `main`, where it raises `IndexError`), invalid-base64 data URL → `BadRequestError`, valid 1x1 PNG data URL → no error (regression guard), and a corrupt `http` image body → `BadRequestError` (network faked via `monkeypatch`; `from_url` itself is not mocked).

Prior multimodal PRs (e.g. #3429, #3463) did not add URL validation; this is a focused, self-contained guard rather than a model-arch change.
