# [PR #11857] UCT/IB/MLX5: Purge outstanding AM short operations

source: https://github.com/openucx/ucx/pull/11857
state: closed | updated: 2026-09-16T07:09:07Z
labels: 

## 正文

## What?
Add native RC mlx5 outstanding-operation purge support for active messages posted with `uct_ep_am_short()`.

The purge path:
- walks outstanding SEND WQEs in posting order
- uses the existing cumulative PSN tracking to distinguish delivered from undelivered packets
- reconstructs AM short operations for the callback
- skips internal NOP and flow-control-only WQEs
- rejects unsupported WQE layouts before invoking callbacks

## Why?
Fault-tolerance recovery needs the transport to report AM short operations that were not delivered after an endpoint is invalidated. RC mlx5 currently lacks native purge support for this operation.

This replaces the narrowly scoped UCT purge work from #11785.

## How?
Parse the outstanding send queue without adding send-time PSN bookkeeping. First validate the outstanding WQE range and derive packet PSNs from the existing `next_wqe_psn`, then report undelivered AM short operations through the UCT purge callback.

```c
for (ci = start_ci; ci != end_ci;
     ci = uct_ib_mlx5_txwq_next_ci(ci, wqe_size)) {
    ctrl     = uct_ib_mlx5_txwq_get_wqe(txwq, ci);
```

<details><summary>Full analysis</summary>

**Summary:** gtest crashed (SIGSEGV, core dumped, `make: *** [Makefile:4690: test] Segmentation fault`) at the start of `ud_mlx5/test_uct_perf.envelope/1` on the roce/worker-3 Azure job.

```
Caught signal 11 (Segmentation fault: address not mapped to object at address (nil))

 2 ucx_perf_global_init()         src/tools/perf/lib/libperf_memory.c:415
 3 ucx_perf_run()                 src/tools/perf/lib/libperf.c:2239
```

The faulting thread is `p-1` (the second of the two perf threads). `test_perf::run_multi_threaded()` (test/gtest/common/test_perf.cc:283-293) spawns **two** threads that each call `ucx_perf_run()`, and `ucx_perf_run()` unconditionally calls `ucx_perf_global_init()` (libperf.c:2239) with no once-guard or lock. Both threads therefore execute the allocator-registration code concurrently on the shared globals `ucx_perf_allocators[]` / `ucx_perf_num_allocators`.
