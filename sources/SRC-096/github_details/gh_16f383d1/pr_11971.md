# [PR #11971] UCP/WIREUP: Activate AM lane iface while EP config is used

source: https://github.com/openucx/ucx/pull/11971
state: open | updated: 2026-09-20T20:42:39Z
labels: 

## 正文

## What?

Fix post wireup freeze by activating the interface of the AM lane during wireup, by adding that lane to the protocol lane map of the endpoint configuration.

Valid workaround: `UCX_ADAPTIVE_PROGRESS=n` as it otherwise deactivate interface in `ucp_worker_iface_init()`.

`UCX_LOG_LEVEL=data` triggers it because it sets `progress_wrapper_enabled` which disables short proto init that otherwise activate AM lane.

Non reduced repro:
```
env -u UCX_NET_DEVICES UCX_LOG_LEVEL=data \
    UCX_PROTO_INFO=used UCX_TLS=^gdr_copy \
    UCX_PROTOS=^get/rndv,put/rndv \
        ucx_perftest -t ucp_put_bw -m cuda -n 10`
```

## Why?

- The wireup ACK is sent on the AM lane, so its interface has to be progressed during wireup, before any data operation is issued.
- Today nothing progresses it at that point: the sender never reaps the ACK send completion, the peer never dispatches it, and both hang in a worker flush.
- It usually goes unnoticed because the interface is armed for events and something else wakes it up, or another endpoint or lane on the same interface has already activated it. Setups with several devices, where the AM lane sits on an interface nothing else uses, hit it.

## How?

- `ucp_ep_config_init()` seeds `proto_lane_map` with `key.am_lane`, so the interface is activated with the first endpoint using the configuration and released with the last one.
- `ucp_proto_select_elem_progress_ifaces()` already masks out the lanes of that map, so a protocol later selecting the AM lane does not activate it twice.
- Activating it from `ucp_wireup_should_activate_wiface()` instead would never be released, because `ucp_ep_unprogress_uct_ep()` is a no-op there.
- An interface which received messages is no longer kept activated once its last endpoint is destroyed: the counting proxy handler that used to activate it only runs while the interface is not activated, and that activation was never released. `test_ucp_sockaddr_iface_activate.iface_activate_count` is updated accordingly and still fails without the fix.
- New `test_ucp_wireup_1sided.am_lane_iface_activation` verifies the AM lane interface is activated after wireup, before any data operation.

🤖 **CI Triage Agent** — `UCX PR (Tests gpu on worker 1)` · commit `57f9a892`

**TL;DR:** Not a PR regression — `cudaMallocAsync` on the GPU worker failed with "out of memory" even for `size=1`, and the resulting `UCS_TEST_ABORT` exception was thrown from inside a UCP AM callback running under `ucp_worker_progress()`, skipping the `--worker->inprogress` decrement and making the next progress call hit the fatal assertion that killed the whole gtest binary.

<details><summary>Full analysis</summary>

**Summary:** `rcx/test_ucp_am_nbx_rndv_memtype.rndv/{15,31,51}` (all `cuda-async` parameterizations) failed with `cudaMallocAsync(...) failed: out of memory: size=1`, and the run then aborted with `ucp_worker.c:3266 Assertion 'worker->inprogress++ == 0' failed` (core dumped, `make test` exit 2).

**Root cause:** Two layers:
1. Environmental/GPU-state: the CUDA stream-ordered allocator on `swx-rdmz-ucx-gpu-02` could not satisfy even a 1-byte request (`test/gtest/common/mem_buffer.cc:489`), while plain `cudaMalloc` paths in the same run (`cuda`, `cuda-managed`) all passed. That pattern means the default async mem pool / device memory was exhausted (memory retained by the async pool or another concurrent gtest worker on the same GPU), not a bug in the `wireup_ack_am_lane` changes — the PR touches wireup lanes and nothing in the CUDA test path.
2. Crash amplification (real UCX-side bug): `CUDA_CALL` → `UCS_TEST_ABORT` throws a C++ exception. In this test the memtype buffer is allocated from the AM receive callback, i.e. while executing inside `ucp_worker_progress()`. The exception unwinds past `src/ucp/core/ucp_worker.c:3271`, so `worker->inprogress` is never decremented; the next `ucp_worker_progress()` call (test teardown) trips `ucs_assert(worker->inprogress++ == 0)` at line 3266 and calls `ucs_fatal_error`, turning 3 recoverable test failures into a process abort that fails the entire job. Note `mem_buffer::release()` already guards against this with a `try/catch` (lines 585–629), but `mem_buffer::allocate()` does not.

**Implicated commit:** unknown for the OOM (infrastructure/GPU state; commit `57f9a892` under test is not implicated). The throwing async-alloc path dates to `6a0c6c1f` "GTEST/COMMON: Added test for cuda async allocated buffers" (rakhmets), most recently touched by `2054662d` (Peter Andreas Entschev, #11922).

**File:** `test/gtest/common/mem_buffer.cc:489` (failure origin); `src/ucp/core/ucp_worker.c:3266` (fatal assertion)

**Suggested fix:**
- Short term: re-run the PR job; check the GPU worker with `nvidia-smi` for leaked/held device memory and, in the gtest teardown for async tests, trim the pool (`cudaMemPoolTrimTo(pool, 0)` / set a release threshold) so async-pool memory is returned between test cases.
- Robustness fix worth a separate PR: make async allocation failures non-fatal and non-throwing from inside callbacks — e.g. in `mem_buffer::allocate()` treat `cudaErrorMemoryAllocation` from `cudaMallocAsync`/`cudaMallocFromPoolAsync` as `UCS_TEST_SKIP_R("no GPU memory for async allocation")` performed outside the progress loop, or have the AM-callback path pre-allocate the receive buffer before progress. Optionally harden `ucp_worker_progress()` (or the gtest progress wrapper) so `worker->inprogress` is restored on unwind, so one CUDA OOM cannot abort the whole suite.

**Related:** #11922 (recent async-managed-memory change in `mem_buffer.cc`); no existing issue found for `cudaMallocAsync ... out of memory: size=1` — worth opening one.

</details>
