# [Issue #11505] Infinite loop in ucp_add_tl_resources() when num_tl_resources == 256

source: https://github.com/openucx/ucx/issues/11505
state: closed | updated: 2026-06-23T02:30:34Z
labels: Bug

## 正文

We observed a hang during UCP resource discovery on a system with many RDMA VFs. The process appeared to be looping in `ucp_str_array_search()` / `strcmp()`, with repeated comparisons such as `"self"` vs `"rc"`.

### Environment / trigger

- ucx version: 1.18.0
- The machine has 256 net device
- `UCX_NET_DEVICES` was already restricted.
- `UCX_TLS` was restricted to `rc,tcp`.
- During `ucp_add_tl_resources()`, `num_tl_resources` reached 256.

### Root cause

In `ucp_add_tl_resources()`, the loop over `num_tl_resources` used `ucp_rsc_index_t` as the loop variable in the affected code path:

```c
ucp_rsc_index_t i;

for (i = 0; i < num_tl_resources; ++i) {
    ...
}
```

`ucp_rsc_index_t` is `uint8_t`, so when `num_tl_resources == 256`, the loop variable wraps from 255 back to 0. The loop condition remains true forever:

```text
i = 255
++i -> 0
0 < 256 => true
```

As a result, the loop repeatedly calls `ucp_add_tl_resource_if_enabled()`, which then repeatedly enters the transport filtering path:

```text
ucp_add_tl_resource_if_enabled()
  -> ucp_is_resource_enabled()
    -> ucp_is_resource_in_transports_list()
      -> ucp_transports_list_search()
        -> ucp_str_array_search()
          -> strcmp(...)
```

This explains why the process appeared to be stuck in `ucp_str_array_search()` rather than in the outer loop itself.
