# [PR #11685] UCP/PROTO/RNDV: Isolate remote system device namespace

source: https://github.com/openucx/ucx/pull/11685
state: closed | updated: 2026-09-14T09:23:48Z
labels: 

## 正文

## What?

Fix UCP rendezvous protocol selection for Direct NIC when system-device IDs
belong to different topology namespaces. Model GET/PUT mtype network lanes
using the staging fragment device.

## Why?

Direct NIC RNDV can fail in `find_lanes`: while estimating the protocol the
peer will select, UCX interprets a peer-local `sys_dev` from the rkey in the
local topology and can reject a valid lane. This remote-namespace correction
applies to both mtype and non-mtype protocols. For mtype GET/PUT, network I/O
accesses the staging fragment (for example, a host bounce buffer for CUDA),
but protocol selection still needs the user buffer `sys_dev` for lane
spreading.

## How?

Never interpret the rkey's peer-local `sys_dev` in the local topology. For
nested remote estimation, use the local `select_param.sys_dev` as a
namespace-safe topology proxy when the local and remote memory types match;
otherwise use `UCS_SYS_DEVICE_ID_UNKNOWN`. For mtype probes, keep the
user/final device in `select_param.sys_dev` and pass the staging fragment
through `reg_mem_info`. The common minimum-fragment filter validates
transport reachability once against `reg_mem_info`: for `SEND_ZCOPY` this
describes the selected user buffer, while RNDV mtype protocols supply their
staging fragment.

Keep the existing GPU peer-failure pipeline test deterministic by using a host
staging fragment; it still exercises CUDA user memory through
`rndv/put/mtype` and retains the original failure assertions. Regression
tests independently cover remote namespace isolation and the user/fragment
device roles.

<details><summary>Full analysis</summary>

**Summary:** `make -C build/bindings/go test` failed — `panic: test timed out after 10m0s` with the sole live test goroutine parked in `TestUcpWorkerEfd` at `worker_test.go:74`.

**Root cause:** Deadlock caused by a test-harness bug, not by the PR's code. Log timeline proves a hang, not slowness:

- `02:29:46.4413` — `worker_test.go:61: Failed to call epoll_wait interrupted system call`
- `02:39:40.7338` — `panic: test timed out after 10m0s`

That is a ~9m54s gap with zero output — the entire remaining runtime. The stack trace names the culprit precisely:

```
goroutine 9 [chan receive, 9 minutes]:
github.com/openucx/ucx/bindings/go/tests.TestUcpWorkerEfd(0xc0000f29c0)
	.../bindings/go/tests/worker_test.go:74 +0x2d4
goroutine 1 [chan receive, 9 minutes]:   # blocked in testing.(*T).Run
```

Mechanism, from `bindings/go/tests/worker_test.go`:

1. Line 59: the worker goroutine blocks in `syscall.EpollWait(epfdLocal, events[:], -1)`. Go's `syscall.EpollWait` is a raw wrapper with **no `EINTR` retry loop**, so any signal delivered to that thread — routinely the Go runtime's own async-preemption `SIGURG` (Go ≥1.14), and this job runs Go 1.18.2 — makes it return `EINTR`.
2. Lines 60–62: `err != nil`, so `t.Fatalf("Failed to call epoll_wait %v", err)` fires. This is the line 61 message in the log, confirming `EINTR` was hit.
3. `t.Fatalf` is documented as valid only from the goroutine running the test. From a spawned goroutine it calls `runtime.Goexit()`, killing *only that goroutine* — it does **not** fail/unblock the test.
4. Line 64 `eventsChan <- nevents` is therefore never reached, and `eventsChan` is unbuffered and never closed. The test goroutine at line 74 (`nevents := <-eventsChan`) blocks forever until the 10m alarm panics the process.

This is a latent flake dating to the test's introduction, not a regression from this PR. The earlier passing tests (`TestUcpContext`, `TestUcpEpTag`, `TestUcpEpAm`, `TestUcpListener`, `TestUcpMmap`) all passed, and the PR (`agent/fix-rndv-remote-sysdev`) touches rendezvous/system-device logic with no relation to worker efd/epoll wakeup. Expect this to reproduce intermittently on unrelated PRs. Note also the leftover `gtest`/`ucx_perftest` processes still holding GPU memory in the `nvidia-smi` dump, which is normal noise from prior stages, not a cause here.

**Implicated commit:** `2bbf7cfe` — "BINDINGS/GO: Ucp endpoint functionality." (Peter Rudenko, 2021-08-02) introduced this test pattern; not the PR commit `d093cd3d`.

**File:** `bindings/go/tests/worker_test.go:59-64` (blocking receive that deadlocks is line 74)

**Suggested fix:** Retry on `EINTR` and make the goroutine always unblock the test:

```go
go func() {
	defer close(eventsChan)   // guarantees line 74 never blocks forever
	...
	var nevents int
	for {
		nevents, err = syscall.EpollWait(epfdLocal, events[:], -1)
		if err != syscall.EINTR {   // retry across preemption signals
			break
		}
	}
	if err != nil {
		t.Errorf("Failed to call epoll_wait %v", err)  // Errorf, not Fatalf
		return
	}
	eventsChan <- nevents
}()
```

Two independent hardening points: (1) `syscall.EINTR` from `EpollWait` is expected under the Go runtime and must be looped over, and (2) replace every `t.Fatalf` inside the spawned goroutine (lines 39, 44, 51, 61) with `t.Errorf` + `return`, since `Fatalf`/`Goexit` from a non-test goroutine silently strands the parent. Adding `defer close(eventsChan)` converts any future goroutine death into an immediate zero-value receive and a clean failure instead of a 10-minute timeout. Optionally guard line 74 with a `select` + `time.After` so the failure mode is a fast, self-describing error rather than a whole-job wall-clock kill.

### jeffnvidia · 2026-08-27

@guy-ealey-morag The fragment device is used unconditionally because it describes the buffer touched by the network operation, whereas the original `select_param->sys_dev` describes the user buffer.

For GET mtype, `ucp_proto_rndv_mtype_next_iov()` builds the GET IOV from `req->send.rndv.mdesc->ptr`, then the fragment is copied to the user buffer. For PUT mtype, the user buffer is first copied into that same mdesc and the network PUT IOV is built from it. `frag_mem_info.sys_dev` is also the device stored in the protocol private data and later passed to `ucp_rndv_mpool_get()`, so it is the authoritative device for lane modeling.

Limiting the override to `UNKNOWN` would keep modeling the network lane by the user GPU whenever that GPU is known, even when the staging fragment is host memory on a different device. The new GET/PUT tests deliberately use distinct, known user and fragment accelerator ordinals and equal-bandwidth NICs; they assert the fragment-selected lane, and the conditional behavior would select the opposite lane. The wrapper changes only the copied nested-probe parameters, so the original protocol lookup key remains unchanged.
