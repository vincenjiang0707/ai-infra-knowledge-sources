## Symptom

An importer that has mapped a peer's `CU_MEM_HANDLE_TYPE_FABRIC` (VMM) memory
over the cuda_ipc transport **keeps that mapping alive for its entire process
lifetime**. Releasing every handle the transport/consumer layer exposes does
not free it; the exporter-side allocation therefore stays resident on the
exporter GPU for as long as *any* importer process is alive — even after the
importer has finished all transfers and torn down its endpoints/agent.

At fleet scale this is a real operational hazard: tearing down a subset of a
fabric memory domain leaves exporter-GPU memory (in our case ~200 GiB/GPU)
pinned and unreclaimable until the surviving importer processes on other nodes
exit.

## Minimal reproduction (2 process, in-process, no framework)

Two small Python processes (exporter allocates a `CU_MEM_HANDLE_TYPE_FABRIC`
VMM buffer, registers it; importer maps it via one cuda_ipc READ, then walks a
graded teardown ladder while staying alive). Per-step exporter-GPU HBM sampled
with `nvidia-smi`, real rc per step. Scripts + raw logs:
`lifecycle_repro*.py`, `lifecycle_{E,v5}.sh`, `lifecycle_*/controller.log`.

**Graded destruction ladder inside a LIVING importer** (exporter killed first;
exporter-GPU HBM, serving baseline 237.7 GiB, +8–9 GiB test buffer):

| step (importer stays alive) | exporter HBM |
|---|---|
| release transfer handle | pinned (~245.9 GiB) |
| remove remote agent | pinned |
| deregister own memory | pinned |
| destroy entire agent object + gc | **pinned** |
| **importer process exit** | **freed (→ 237.7 GiB)** |

Also measured with `UCX_CUDA_IPC_CACHE=n`: still pinned until process exit
(env recognition positive-controlled — a bogus `UCX_*` var warns "unused",
this one does not, so the toggle is parsed). A plausible reading, **consistent
with the source but not proven by this experiment alone**, is that the
consumer-layer teardown never reaches the unmap path so the cache toggle has
nothing to act on.

## Where it comes from (source reading, v1.21.0 `cuda_ipc_cache.c`)

- Imported mappings live in a **module-global** cache
  `uct_cuda_ipc_remote_cache` (hash + recursive spinlock), keyed by the remote
  `{pid, pid_ns, cu_device}` triple.
- The import path (`uct_cuda_ipc_map_memhandle` → `..._open_memhandle_vmm`:
  `cuMemImportFromShareableHandle` + `cuMemAddressReserve` + `cuMemMap` +
  `cuMemSetAccess`) inserts into that cache with refcount semantics.
- Hash **entries are destroyed only in `UCS_STATIC_CLEANUP`** (library
  unload / process exit). Endpoint/worker/context/md teardown never removes a
  peer's entry. `uct_cuda_ipc_cache_purge` is `static`; the LRU capacity path
  is an insert-pressure valve, not a peer-close path.
- **There is no public API to evict one peer's cached mappings.** So a consumer
  that has finished with a peer (peer gone, or last endpoint closed) has no way
  to release the imported mappings short of exiting.

> Confidence: the symptom (release-only-at-process-exit) is directly measured
> and reproducible; the "module-global cache, static-cleanup-only" mechanism is
> from source reading of the matching tag and is **consistent with** the
> measurements, but I have not instrumented the running binary at that line
> (this `libucs` build has `ucs_trace` compiled out). Independent confirmation
> on a from-source build would be welcome.

## Proposed direction (for maintainer feedback — not a submitted patch)

A per-peer eviction entry point, callable by a transport/consumer that knows a
peer is done, e.g.:

```c
ucs_status_t uct_cuda_ipc_remote_cache_evict(pid_t pid, ucs_sys_ns_t pid_ns,
                                             int cu_device);
```

Design notes we've worked through (full doc: `UCX_PURGE_API_DESIGN.md`):

- **In-place region eviction, cache object stays in the hash** — avoids both a
  use-after-free of the cache object and the unmap-relookup-by-key hazard (the
  existing unmap path re-looks-up the cache by triple key and asserts the
  region is present, so detach-and-replace of the whole cache object is unsafe).
- **Drain-before-evict precondition** (caller closes admission for the peer and
  waits for in-flight region refcounts to reach 0), so eviction is a clean
  two-phase scan-then-remove: phase 1 under the cache lock verifies all regions
  are idle (else `UCS_ERR_BUSY`, no side effect); phase 2 removes from pgtable
  and closes handles after dropping the lock (no CUDA call under any lock).
- **Idempotent**, per-peer isolation (only that key's pgtable touched), triple
  key so container PID-ns / PID reuse is disambiguated.

Open questions for maintainers:
1. Is a per-peer eviction API the right shape, or is there an existing
   mechanism I've missed (beyond LRU capacity limits and static cleanup)?
2. Ownership/lifetime: does UCX expect the transport md/ep teardown to drive
   this, or a new explicit call from the consumer (NIXL, in our case)?
3. The separate `uct_cuda_ipc_rem_mpool_cache` (fabric mempool path) has the
   same static-cleanup-only lifetime — should a fix cover both?

I'm happy to prepare a PR with CPU-race unit tests (TSAN/ASan) and a
compute-sanitizer'd 2-process test if the direction is acceptable. Attaching
the minimal repro, per-step HBM logs, source-anchored analysis, and the API
design doc.

### Follow-up: two maintainer decisions that gate a PR for this issue

I have a drafted per-peer eviction change for the cuda_ipc remote-cache
lifetime problem above, plus a CPU stub-model test (contract semantics, TSAN/
ASan-clean) and a design writeup for the consumer (NIXL) side. Before I open a
PR I'd like a maintainer steer on **two decisions**, because each determines the
function signature and where the drain/`UCS_ERR_BUSY` contract lives. I don't
want to guess the layering and send a PR shaped the wrong way.

The draft primitive (internal shape) is:

```c
ucs_status_t uct_cuda_ipc_remote_cache_evict(pid_t pid, ucs_sys_ns_t pid_ns,
                                             CUdevice cu_device);
```

with drain-before-evict semantics: caller closes admission + drains the peer;
`UCS_ERR_BUSY` (any live refcount) is a zero-side-effect no-op; a clean scan
purges the peer's regions in place; the cache object itself is never removed
from the module-global hash (so a concurrent `unmap` re-lookup by triple always
resolves to the same object); a CUDA-close failure is reported as a *partial*
teardown rather than a false `UCS_OK`.

#### Decision 1 — API ownership / reachability

In v1.21.0, `cuda_ipc_cache.h` is in `noinst_HEADERS` and the implementation is
in the separate `libuct_cuda` module; a UCP consumer (e.g. NIXL) links
`-lucp -lucs -luct`, not `-luct_cuda`, and does not hold the cuda_ipc MD/iface.
So a bare new symbol in that internal header is neither a stable public API nor
guaranteed link/load-reachable by the consumer. Which boundary do you prefer?

- **(a) Transport-teardown self-driven** — no new public symbol; eviction is
  driven internally from an existing teardown path. My concern: the
  module-global cache is shared across endpoints and (in v1.21.0)
  `uct_cuda_ipc_ep_t` carries only `remote_pid` (the key also needs `pid_ns` +
  `CUdevice`), and there is no last-owner refcount — so a single ep/iface/md
  close doesn't obviously mean "this peer's imports are done." **Is there a
  reliable last-owner lifecycle point I've missed, or would you accept adding a
  per-peer last-owner refcount so one can be defined?**
- **(b) A UCP-reachable explicit cleanup hook** that UCP routes internally down
  to cuda_ipc — so the consumer calls installed UCP/UCT surface it already
  links, **without** linking `libuct_cuda`. (I could not find an existing public
  `uct_md_control`/`uct_iface_control` entry to ride in v1.21.0; if there is
  one, pointing me at it is all I need.)
- **(c) A formally installed CUDA-specific public API** — promote the symbol to
  an installed header with an explicit export/link story. Heaviest ABI burden;
  listed for completeness.

If the answer is "(b), extend *this* op" or "(a), hook *this* event / yes add a
last-owner count," that's enough for me to shape the whole PR.

#### Decision 2 — close-failure resource policy

Once a region is detached and freed, a failed `cuMemUnmap`/`cuIpcCloseMemHandle`
leaves an **untracked** driver mapping — there's no handle left to retry.
Returning the error (instead of a false `UCS_OK`) is necessary but not closure.
Which policy do you want?

- **(i) Fatal** — treat as unrecoverable (abort / poison the domain).
- **(ii) Quarantine + retry list** — on close failure, do **not** free the
  region; move it to a UCX-internal list retaining handle/addr/len so the close
  can be retried. (Note: this must be **UCX-side** — a consumer that only sees
  the error status has nothing left to retry.)
- **(iii) Defer to process teardown** — accept leak-until-exit (today's status
  quo for the whole cache) and only surface the error for observability.

My tentative lean is (ii), but it adds per-cache state + a retry driver and
interacts with Decision 1 (who owns the retry), so I'd rather you choose.

I'm ready to build the PR to whichever answers you give. And if there's an
existing peer-close eviction mechanism I've overlooked (beyond LRU capacity
limits and `UCS_STATIC_CLEANUP`), I'd much rather use that than add anything new.

### Follow-up: how this relates to the just-reverted #11335 / #11744, and a concrete refcount-gated design

Since filing this I've been tracking the recent churn in `cuda_ipc_cache.c`, and I think it sharpens the proposal — this eviction API is specifically the *safe* form of the lifecycle release that #11744 just backed out.

**Context I'm building on**

- #11335 added destruction of the remote cache at `ep_destroy`.
- #11744 reverted it, with the reason (rakhmets): *"It is not safe to unconditionally destroy cache at endpoint destruction. As it may unregister memory that is still in use."* (backported to v1.22.x in #11777.)
- #11501 split the remote-cache accessor into lookup-only `uct_cuda_ipc_remote_cache_get()` + get-or-create `uct_cuda_ipc_remote_cache_put()`. Current master also guards the global cache with `ucs_rw_spinlock` (read for lookup in `unmap`, write around `put` in `map`) rather than the recursive spinlock the v1.21.0 base used.

**Why the proposed `uct_cuda_ipc_remote_cache_evict()` doesn't hit the #11744 hazard**

The revert reason is exactly the failure mode this API is designed to make structurally impossible:

1. **Never unconditional.** It is an explicit, caller-invoked per-peer evict — not automatic teardown on `ep_destroy`. The caller invokes it only when it has admission-closed and drained that peer.
2. **Refcount-gated, atomic no-op on "still in use."** Under the per-cache write lock, phase 1 scans the peer's regions; if *any* region has `refcount > 0` it drops the lock and returns `UCS_ERR_BUSY` having removed/closed **nothing**. So it cannot "unregister memory that is still in use" — that path removes zero regions. Only a fully-drained peer reaches phase 2 (detach) and the post-lock close.
3. **No CUDA call under any lock; cache object never removed from the global hash.** `cuMemUnmap`/`cuIpcCloseMemHandle` run after the per-cache lock is dropped. The cache object stays in the global hash, so an in-flight `unmap_memhandle` that re-looks-up by `{pid, pid_ns, cu_device}` still resolves to the same live object (no UAF, no relookup-by-key routing hazard).
4. **First close failure ⇒ non-OK return, documented as partial teardown** (region already detached but driver mapping may remain), so callers can't treat it as a retryable success.

**Rebased to current master (not the v1.21.0 base I first drafted against)**

On master this no longer needs a new lookup helper: evict takes `ucs_rw_spinlock_read_lock(&uct_cuda_ipc_remote_cache.lock)`, reuses the existing lookup-only `uct_cuda_ipc_remote_cache_get()` (returning `UCS_OK` by genuine absence for an unknown peer), then takes the per-cache `pthread_rwlock` for the scan/detach. `uct_cuda_ipc_cache_region_remove()` grows a return value so the detach path can fail-stop instead of half-detaching.

**Evidence so far (honest maturity)**

- The eviction path has been exercised against genuine UCX runtime datastructures (pgtable + LRU + region lifecycle) under ASan/UBSan/TSan on aarch64 (GB300), with a **before/after** demo where a sanitizer catches the use-after-free the design avoids. *This validates the memory-safety of the path; it is a controlled observation, not a full transport build.*
- **Not yet demonstrated:** that calling evict on a real 2-GPU fabric actually releases the pinned exporter-side VMM/HBM (the operational payoff). I can build UCX-with-patch and add that direct measurement if the direction is accepted.

**Ask**

Is this direction — an explicit, drain-before-evict, refcount-gated per-peer eviction entry point — acceptable, given #11744? If so I'll open the PR (rebased onto master, with the sanitizer harness as a test and the fabric HBM-release measurement). If you'd instead prefer this handled internally (e.g. tied into a future safe `ep_destroy` path now that #11335 is out), I'm happy to align to that.
