# [PR #11887] UCM/ROCM: intercept HSA allocator with bistro

source: https://github.com/openucx/ucx/pull/11887
state: open | updated: 2026-09-25T17:04:08Z

## 正文

The ROCm memory hook installed only ELF relocation (GOT) patches on hsa_amd_memory_pool_allocate/free. This PR introduces the bistro approach.

Add binary-instrumentation (bistro) interception for the HSA allocator: patch the function body so callers are caught regardless of how they resolved the symbol. Add UCX_MEM_ROCM_HOOK_MODE (bitmap of bistro,reloc; default bistro+reloc) to select the mode, keeping reloc as a fallback where bistro cannot patch (e.g. write-xor-execute (W^X) memory protection, which forbids making a code page writable to install the patch).

Missing early-out when all hook modes are disabled. cudamem.c:417 short-circuits with UCS_ERR_UNSUPPORTED when cuda_hook_modes == 0. The reworked ucm_rocmmem_install() dropped the old "TODO: check mem reloc" but did not add the equivalent check. With UCX_MEM_ROCM_HOOK_MODE=none, both install-hook calls return UCS_OK and ucm_rocmmem_install() reports success even though nothing was installed. Suggest: if ucm_global_opts.rocm_hook_modes == 0, log and return UCS_ERR_UNSUPPORTED so the caller knows hooks are disabled.


Test coverage gap: The new x86 bistro relocation cases (endbr64 copy-through and RIP-relative mov disp32(%rip), %reg translation) are the risky part of this change — incorrect machine-code emission corrupts the trampoline. There is no unit test in test/gtest/ucm/ exercising ucm_bistro_relocate_one for these new opcodes. Consider adding a focused test, since these paths only trigger on specific HSA/CET builds and would otherwise be untested in CI.


Test coverage gap: CUDA has buildlib/pr/cuda/test_malloc_hook.sh exercising both reloc and bistro modes. There is no equivalent for the new UCX_MEM_ROCM_HOOK_MODE. Per REVIEW.md, user-facing configure/runtime options should get CI coverage for the enable/disable path. Consider adding coverage for UCX_MEM_ROCM_HOOK_MODE=reloc/bistro similar to the CUDA script.

### svc-ucx · 2026-09-18

🤖 **CI Triage Agent** — `UCX PR (AddressSanitizer roce on worker 0)` · commit `05800324`

**TL;DR:** The ASAN/RoCE gtest run died because the shared UMR QP on `mlx5_1` stopped completing work requests — `ibv_post_send(BIND_MW)` never generated a completion, so `uct_ib_mlx5_devx_umr_post_sync()` spun for its full 30 s timeout, and since the 1-entry send queue stays full afterwards the UMR QP is permanently wedged, failing every subsequent `ucp_rkey_pack()` and finally aborting the suite with an rcache "destroying inuse region" fatal. This is not caused by the ROCm PR content; the fix belongs in the UMR error path (reset/recreate the UMR QP on timeout instead of re-posting into a full SQ, and don't turn a pack failure into a core dump).

<details><summary>Full analysis</summary>

**Summary:** `shm_ib/test_ucp_wireup_2sided.multi_ep_2sided/1`, `shm_ib_ipc/test_ucp_rma_reg.put_blocking/3` and `.get_blocking/1` failed with `mlx5_1: ibv_poll_cq(UMR CQ, registration, UMR mkey ... index 0x4323) timed out`, then the gtest process aborted on `Assertion 'region->refcount == 0' failed ... of ucp_rcache` during `ucp_cleanup`.

**Root cause:** Evidence in the log:
- 19:47:16.648 → 19:47:46.728 is a 30 s dead gap with zero output — exactly the hard-coded 30 s poll timeout in `uct_ib_mlx5_devx_umr_post_sync()` (src/uct/ib/mlx5/dv/ib_mlx5dv_md.c:1447-1452). So the process was *hung* waiting for a UMR completion on `mlx5_1`, not slow.
- The UMR work request is the `IBV_WR_BIND_MW` posted in `uct_ib_mlx5_devx_umr_mkey_bind()` (:1548) on the per-MD self-loopback UMR QP created in `uct_ib_mlx5_devx_umr_create_qp()`/`_modify_qp()` (:1145-1266). That QP is created with `max_send_wr = 1`.
- After the timeout, the error path calls `uct_ib_mlx5_devx_umr_mkey_invalidate()` (:1550), which posts *another* WR into the still-occupied 1-entry SQ; it fails with `ibv_post_send(...) returned 12` (ENOMEM, SQ full). From that point the UMR QP is unusable: every later exported-mkey pack on `mlx5_1` fails identically (same `index 0x4323`, 19:48:33 and 19:49:04), always as `Error: Input/output error` out of `ucp_rkey_pack()` (test_ucp_wireup.cc:222, test_ucp_memheap.cc:68).
- The final core dump is a second-order bug: when `ASSERT_UCS_OK` fires at test_ucp_memheap.cc:68 the already-mapped `memheap_memh` is never unmapped, so `ucp_cleanup()` destroys the rcache with a live region (`ucp_rcache: destroying inuse region ... ref 1 md[2]=mlx5_0 md[3]=mlx5_1`) → `ucs_fatal` → `make: *** [test] Aborted (core dumped)`, which kills the whole suite instead of reporting 3 failed tests.
- The failing device is always `mlx5_1` on `swx-rain04` (RoCE), while `mlx5_0` UMR work succeeds — i.e. a device/port-specific UMR QP problem, consistent with the known UMR-QP-on-RoCE-LAG issue tracked in PR #11780. Nothing in the failing path touches ROCm, so PR #11887 is very unlikely to be the trigger.

**Implicated commit:** unknown — no ROCm/UMR commit in the failing path; most recent related change to this file is `[REDACTED:Hex High Entropy String]` "UCT/IB: Allow ODP with DDP for FW >= 49.1014 (#11914)" (Thomas Vegas, 2026-09-14), which widens ODP/GVA usage on these devices and is worth ruling out by re-running with `UCX_IB_ODP_ENABLE=n`.

**File:** src/uct/ib/mlx5/dv/ib_mlx5dv_md.c:1447 (poll timeout) and :1548-1552 (wedging error path); secondary: test/gtest/ucp/test_ucp_memheap.cc:57-68

**Suggested fix:**
1. Make the UMR error path non-wedging: on `UCS_ERR_TIMED_OUT`/WC error in `uct_ib_mlx5_devx_umr_post_sync()`, flush the QP (modify to `IBV_QPS_RESET` and re-run `uct_ib_mlx5_devx_umr_modify_qp()`, or tear down and lazily re-init `md->umr.qp`/`cq`) and mark the MD's UMR path failed, instead of calling `uct_ib_mlx5_devx_umr_mkey_invalidate()` which posts into a full 1-entry SQ; in `uct_ib_mlx5_devx_umr_mkey_bind()` call `uct_ib_mlx5_devx_umr_mkey_destroy()` directly on failure so the broken mkey is not recycled into `md->umr.mkey_pool`.
2. Give the UMR QP more than one SQ entry (`max_send_wr = 1` leaves no room for the recovery WR) and log `wc.status`/QP state on timeout so the next occurrence is diagnosable.
3. Stop a single registration failure from core-dumping the suite: unmap `memheap_memh` (scoped guard / `ucp_mem_unmap` in the failure path) at test/gtest/ucp/test_ucp_memheap.cc:57-68 so a failed `ucp_rkey_pack` doesn't leave an in-use rcache region at `ucp_cleanup`.
4. Meanwhile, verify `mlx5_1` health/FW on `swx-rain04` (the same UMR QP works on `mlx5_0`) — re-run the job to confirm this is node-specific before blaming PR #11887.

**Related:** https://github.com/openucx/ucx/pull/11780 (UMR QP setup failures on LAG-bonded RoCE devices), https://github.com/openucx/ucx/pull/11914 (recent ODP/DDP enablement in the same file)

</details>
