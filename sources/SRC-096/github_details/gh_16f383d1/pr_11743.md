# [PR #11743] UCT/ROCM: Propagate asynchronous copy signal failures

## 正文

## Summary

HSA completion signals use `0` for successful completion and a negative value for an asynchronous failure. `uct_rocm_base_progress()` previously extracted only signals equal to `0`, so a failed ROCm copy remained in the pending queue and its UCT completion was never invoked.

This change:

- treats non-positive completion signals as terminal;
- reports `UCS_OK` for `0` and `UCS_ERR_IO_ERROR` for negative values;
- logs the failing HSA signal value;
- adds a focused GTest that drives the real HSA signal mpool and verifies the error callback.

This is intentionally independent of the ROCm IPC peer-capability work in #11299.

## Validation

On an AMD W7900 with the ROCm SDK in the vLLM container:

- out-of-source `contrib/configure-devel` build, `make -j16`, and `make install`: passed;
- `test_rocm_signal.async_error`: passed;
- negative control with the source predicate restored to `signal == 0`: failed as expected (`progress=0`, callback count `0`, queue non-empty);
- existing W7900 IPC/copy experiments continue to report successful 1 GiB transfers and preserve the previously tested peer-exit behavior.

The broad `*rocm*` GTest run was stopped after an unrelated `rocm_copy/uct_p2p_rma_test.put_short` payload mismatch (after approximately 511 s); it did not involve the new signal test or this code path.

## Scope

This fixes propagation when ROCr produces a negative completion signal. It does not claim to solve exporter-invalidated stale IPC registrations where ROCr leaves the signal pending; that case needs a separate registration-generation/retirement protocol.

**Root cause:** Not the PR under test. PR #11743 ("UCT/ROCM: Propagate asynchronous copy signal failures") touches only the ROCm transport, which is not present/exercised on the BlueField ARM worker; the whole run is clean (8608 passed, no aborts, no timeouts, no gaps in log timestamps) except one UCP AM eager multi-fragment test over `rc_x` with proto v1.

That test is inherently non-deterministic: `test_ucp_am_nbx_seg_size::init()` picks a *random* segment size each run (`m_size = ucs_max(UCS_KBYTE, ucs::rand() % (64 * UCS_KBYTE))`, test/gtest/ucp/test_ucp_am.cc:1674) and creates a third entity whose `*_SEG_SIZE` differs from the receiver's, while the base fixture sets `MAX_EAGER_LANES=2` (line 58). So fragments of a long AM are sent over two lanes with mismatched segmentation and can be reassembled out of order — a classic source of intermittent failure in this suite.

Looking at the reassembly code, there is a concrete latent defect that matches this profile: in `ucp_am_handle_unfinished()` the loop over `ep_ext->am.started_ams` does `return` when the *head* message is still incomplete (src/ucp/core/ucp_am.c:1466-1472) instead of `continue`. Any message later in the list that is already fully assembled is therefore not delivered to the AM callback until the head message completes — head-of-line blocking that makes `m_recv_counter != m_send_counter` and the test fail/time out for unlucky segment-size/lane-ordering combinations. This region was reworked recently (interval-tree fragment tracking and resend eviction).

Note: the retrievable Azure log is only the tail of the job, so the exact assertion text for the failing test was truncated — the diagnosis above is based on the failure identity plus the test/source code.

**Implicated commit:** Not the PR commit e312ad3c. Most likely area: `2bafbb02` (Evgeny Leksikov, "UCP/AM/FT: introduce resend flag for first fragment retransmissions", #11452) and `311e3506` (nbellalou, "UCS/RCACHE: Change inv_q type to interval tree", #11248), which introduced/changed the interval-tree fragment tracking used here.

**File:** src/ucp/core/ucp_am.c:1466-1472 (and test/gtest/ucp/test_ucp_am.cc:1664-1713)

**Suggested fix:**

2. Real fix in the AM path: change the early `return` at src/ucp/core/ucp_am.c:1471 to `continue` so that fully-assembled messages later in `started_ams` are delivered independently of an incomplete head message (the loop already uses `ucs_list_for_each_safe`, so continuing is safe).
3. To reproduce/confirm, run the test in a loop with a fixed seed and verbose logging, e.g.
   `UCX_LOG_LEVEL=debug ./gtest --gtest_filter='rcx/test_ucp_am_nbx_seg_size.multi/1' --gtest_repeat=200` (the `UCS_TEST_MESSAGE << "seg size ... data size ..."` line will show which random segment size triggers it), and capture the assertion text that the truncated CI log dropped.
