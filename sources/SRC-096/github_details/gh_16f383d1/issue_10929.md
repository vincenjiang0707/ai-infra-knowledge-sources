# [Issue #10929] ib_write_bw --use_cuda_dmabuf works, but UCX fails on H100

source: https://github.com/openucx/ucx/issues/10929
state: closed | updated: 2026-01-20T16:53:37Z
labels: Bug

## 正文

### Summary

On Stampede3's H100 nodes with `mlx5_0`, UCX 1.18.1 advertises **DMABUF** support for both CUDA and `mlx5_0` (see `ucx_info` below). However, for inter-node CUDA→CUDA transfers **UCX does not select the DMABUF path**. When I disable the `*_copy` transports, `ucx_perftest` fails with:

```
ERROR no copy across memory types transport ...
```

and/or “Out of memory,” instead of using `mlx5_0`+DMABUF.
By contrast, **rdma-core perftest (`ib_write_bw`) with `--use_cuda_dmabuf` works** between the same two nodes, so the kernel/driver path for CUDA DMA-BUF is functional.

---

### Environment

* UCX: **1.18.1** (`ucp_context.c:2257 UCX INFO Version 1.18.1`)
* GPUs: NVIDIA H100 (CUDA device 0 in these runs)
* IB device: **`mlx5_0`** (Mellanox; UCX detects and opens DEVX)
* A second HCAs shows up as **`hfi1_0`** (OPA) on these nodes and is *not* DMABUF capable.
* Cluster: Stampede3 H100 nodes connected via the `mlx5_0` IB fabric
* CUDA runtime present (CUDA 12 libs on nodes)

---

### Capability checks

`ucx_info -d` for `mlx5_0` shows DMABUF registration:

```
#             register: unlimited, dmabuf, cost: 16000 + 0.060 * N nsec
```

UCX init logs also say:

```
cuda_copy_md.c:103  UCX  DEBUG dmabuf is supported on cuda device 0
...
ib_md.c:1209 UCX DEBUG mlx5_0: dmabuf is supported
```

So UCX sees DMABUF capability for CUDA and `mlx5_0`.

---

### Reproducer (UCX)

Two-node tag BW test with device memory, explicitly avoiding “copy” transports so UCX must use GPUDirect/DMABUF:

```bash
# Common env (both ranks)
export UCX_LOG_LEVEL=debug
export UCX_NET_DEVICES=mlx5_0:1
export UCX_TLS=rc_mlx5,ud_mlx5,cuda_ipc,self          # no *_copy
export UCX_SOCKADDR_TLS_PRIORITY=rdmacm
export UCX_IB_GPU_DIRECT_RDMA=y
# Optional “DMABUF-or-fail” knob I also tried:
# export UCX_IB_REG_METHODS=dmabuf
# (I also tried forcing rendezvous PUT path:)
# export UCX_RNDV_SCHEME=put_zcopy

# Server
ucx_perftest -t tag_bw -m cuda -s 4194304 -n 200

# Client
ucx_perftest <server-hostname> -t tag_bw -m cuda -s 4194304 -n 200
```

#### What happens

* UCX **creates** `rc_mlx5` and `ud_mlx5` ifaces on `mlx5_0`, and repeatedly logs DMABUF “supported.”
* But when the endpoint is selected, UCX prints:

```
register cuda memory on: cuda_ipc
...
select.c:644  UCX  ERROR   no copy across memory types transport to <peer>:
   self/memory - Destination is unreachable,
   cuda_ipc/cuda - no host,
   rc_mlx5/mlx5_0:1 - Destination is unreachable,
   ud_mlx5/mlx5_0:1 - no put short
```

* In other attempts (with/without the env tweaks above), the run ends with:

  ```
  perftest_run.c:348  UCX  ERROR Failed to run test: Out of memory
  ```

Key point: **there is never a line where UCX registers CUDA memory on `mlx5_0`**. Instead, it always says:

```
ucp_context.c:1712 UCX DEBUG register cuda memory on: cuda_ipc
```

which is intra-node only.

I also observed occasional messages like these:

```
uct_md.c:96  UCX  DEBUG failed to query gga_mlx5 resources: No such device
ucp_context.c:1188 UCX  DEBUG No tl resources found for md mlx5_0
```

after which UCX closes `mlx5_0` and we’re stuck with no inter-node memtype path once `*_copy` is disabled.

---

### Control experiment (rdma-core perftest)

This script uses **rdma-core perftest** with `--use_cuda_dmabuf`:

```bash
ib_write_bw -d mlx5_0 -s 4M --iters 200 \
  --use_cuda=0 --use_cuda_dmabuf --report_gbits          # server (no host arg)

ib_write_bw <server> -d mlx5_0 -s 4M --iters 200 \
  --use_cuda=0 --use_cuda_dmabuf --report_gbits          # client
```

Result: **succeeds**, good inter-node throughput, confirming that **CUDA DMA-BUF → mlx5** works on this system.

---

### What I expected

Given that:

* `ucx_info -d` and UCX DEBUG logs show **DMABUF supported** for CUDA and `mlx5_0`; and
* rdma-core perftest proves the **kernel/driver/userland path** for CUDA DMA-BUF is OK,

I expected UCX to select a DMABUF-based registration on `mlx5_0` for inter-node CUDA buffers (and to log something like `register cuda memory on: cuda_ipc, mlx5_0`). Instead, UCX never registers CUDA memory on `mlx5_0` and aborts when staging/copy transports are disallowed.

---

### Questions for UCX maintainers

1. **How should UCX be configured to force/enable the DMABUF path** for inter-node CUDA→CUDA (i.e., to register CUDA memory on `mlx5_0` via DMABUF)?

   * Is `UCX_IB_REG_METHODS=dmabuf` sufficient, or are there additional prerequisites (RNDV knobs, lane policies, etc.)?
2. Are the following DEBUG lines expected, and could they be preventing selection of `mlx5_0` for CUDA mem?

   * `failed to query gga_mlx5 resources: No such device`
   * `No tl resources found for md mlx5_0`
3. Is there any reason that **`select.c: no copy across memory types transport`** would be emitted even when DMABUF is supported by both CUDA and `mlx5_0`?
4. Could the presence of an OPA HCA (`hfi1_0`) be interfering, even when `UCX_NET_DEVICES=mlx5_0:1` is set?
