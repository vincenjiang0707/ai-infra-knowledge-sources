# [PR #11283] UCT/CUDA_IPC: Support VMM with multiple memory allocations

source: https://github.com/openucx/ucx/pull/11283
state: open | updated: 2026-09-14T08:32:47Z
labels: WIP-DNM

## 正文

## What?
Add support for CUDA VMM allocations that span multiple underlying physical allocations (cuMemCreate chunks) in the cuda_ipc transport.

## Why?
A user-visible VA range may be backed by several independently created and mapped VMM chunks. Currently, cuda_ipc only exports a single fabric handle per region, which covers just the first chunk. This means transfers involving multi-chunk VMM regions silently access only the first chunk's memory, producing incorrect results for offsets beyond the first chunk boundary.

## How?
Introduce `UCT_CUDA_IPC_KEY_HANDLE_TYPE_VMM_MULTI`. During `mkey_pack`, cuda_ipc detects when the requested VMM range spans multiple allocation buffer IDs, discovers the chunks covering the expanded VA range, exports each chunk’s fabric handle, and writes the chunk descriptors into a GPU-resident metadata buffer. A small GPU-resident header points to that descriptor buffer, and the header fabric handle is packed in the rkey.
During `rkey_unpack`, the receiver imports the metadata header, performs a blocking DtoH copy of the header, imports the chunk-descriptor buffer, and performs another blocking DtoH copy to fetch all chunk handles. The VMM_MULTI memhandle open path then imports and maps the chunks into one contiguous local VA range, which is cached like other cuda_ipc mappings.

## Notes
1. Will be split into multiple PRs. This is just for completeness.
2. Posting performance is better than splitting the operation into one transfer per chunk, but worse than a single-allocation buffer because the resulting mapped range still has higher `cuMemcpyAsync` overhead.
3. A new cache is introduced for multi-allocation views, because now an allocation can map into multiple views but since the local buffer will be different these can't be merged

This PR adds roughly 2,600 lines across two independent changes: a generic `ucs_rbtree` core + `interval_tree` refactor + new `ucs_interval_map`, and the cuda_ipc multi-chunk VMM feature. `REVIEW.md` caps a PR at 500 added lines, and requires refactoring to be in a separate PR with no functional changes. Please split into at least:

1. `UCS/DATASTRUCT: Extract generic red-black tree from interval_tree` (+ shared `rbtree_check.h`, no functional change).
2. `UCS/DATASTRUCT: Add interval map` (+ `test_interval_map.cc`).
3. `UCT/CUDA_IPC: Support multi-chunk VMM registrations`.

The unrelated fixes bundled in (pgtable cleanup leak in `uct_cuda_ipc_create_cache`, `release_empty_rkey` test, whitespace/typo touch-ups) should also move out of the feature PR.


`src/ucs/AGENTS.md` (datastruct bullet): pls add `rbtree` and `interval_map` to the `datastruct/` list, so the new containers are discoverable from the subtree guide.


Coverage gap: `ucs_rbtree_remove()`'s successor-splice path is only exercised indirectly through `test_interval_map.random_stress` and `interval_tree` pops. That looks sufficient for the invariants, but there is no direct test that a caller-held node pointer stays valid across a two-child removal — which is the stated reason for relinking instead of copying keys.


Coverage gap: `uct_cuda_ipc_multi_cache_purge()` with `refcount > 0` (the `ucs_warn` + unindexed-but-live path) is not covered; that is also the path where a still referenced view can outlive its cache.


Coverage gap: the multi-chunk data path itself is only covered by `test/mpi` (`VMM_Multi` allocator), which does not run in the gtest CI matrix. Is there a fabric-capable CI job that exercises it?
