# [PR #11979] UCT/CUDA: Reject IPC without P2P read/write support

source: https://github.com/openucx/ucx/pull/11979
state: open | updated: 2026-09-22T08:40:57Z
labels: Optimization, Ready for Review

## 正文

## What?

Prevent CUDA IPC from being selected when NVML explicitly reports that the local and remote GPU pair does not support P2P read or write access.

CUDA IPC rkey unpack now resolves the local and remote GPU UUIDs through NVML and marks the rkey unreachable when either P2P capability is unsupported. UCP also excludes unreachable memory domains when modeling the nested rendezvous protocol, allowing the existing host-staged pipeline to be selected.

NVML lookup failures and unknown P2P status retain the existing IPC handle mapping probe as a fallback. A focused multi-GPU regression test compares the NVML result with `cuDeviceCanAccessPeer()` across the locally visible devices.

## Why?

Successfully importing a CUDA IPC handle does not guarantee that the GPU pair supports P2P read and write access. On an AWS `g7e.48xlarge` containing 8 x NVIDIA RTX PRO 6000 Blackwell Server Edition GPUs, CUDA permits mapping
memory between GPUs connected through different PCIe bridges even though NVML reports P2P access as unsupported. Transfers through that mapping are extremely slow.

Consequently, enabling `cuda_ipc` prevented UCX from selecting its faster host-staged pipeline and required users to explicitly disable the transport.

The system has eight GPUs arranged as four same-bridge pairs:

- `GPU0-GPU1`, `GPU2-GPU3`, `GPU4-GPU5`, and `GPU6-GPU7`: `PIX`
- GPU pairs behind different PCIe bridges in the same NUMA node: `NODE`
- GPU pairs across NUMA nodes: `SYS`

NVML reports read, write, and PCIe P2P support for the `PIX` pairs and `NVML_P2P_STATUS_NOT_SUPPORTED` for the tested `NODE` and `SYS` pairs. The capability matrix was reproduced on a second identical `g7e.48xlarge`.

For example:

- `GPU0-GPU1`: `PIX`, P2P read/write supported
- `GPU0-GPU2`: `NODE`, P2P read/write unsupported

Results for 100 MiB messages with SRD disabled and `-O 2`:

| GPU pair | Topology | Unpatched | Patched | Selected data path |
|----------|----------|-----------|---------|--------------------|
| GPU0 -> GPU2 | `NODE`, P2P unsupported | 0.88 GB/s | 32.42 GB/s | `cuda_copy`/CMA host-staged pipeline |
| GPU0 -> GPU1 | `PIX`, P2P supported | N/A | 52.45 GB/s | CUDA IPC |

The cross-bridge result used `UCX_TLS=^srd`, so `cuda_ipc` remained enabled and was rejected automatically only for the unsupported GPU pair.

## How?

The packed CUDA IPC rkey already contains the remote GPU UUID. During rkey unpack, UCX now:

1. Resolves the local and remote UUIDs to NVML devices.
2. Queries P2P read and write capability.
3. Keeps CUDA IPC when both capabilities are supported.
4. Returns `UCS_ERR_UNREACHABLE` when either capability is explicitly unsupported.
5. Falls back to the existing handle-mapping probe when NVML cannot resolve the peer or reports an unknown result.

The unreachable CUDA IPC memory domain is then removed from the synthetic remote rkey used for nested rendezvous protocol selection. This preserves the local staging registration map while preventing the rejected CUDA IPC lane from
being selected again.

This is intentionally a conservative capability check rather than a bandwidth heuristic. GPU pairs for which NVML reports P2P read and write support remain eligible for CUDA IPC.

<details><summary>Full analysis</summary>

**Summary:** `Build ucx artifact` stage failed with `-Werror` compile errors in `src/uct/cuda/cuda_ipc/cuda_ipc_md.c` — `'NVML_DEVICE_UUID_ASCII_LEN' undeclared`.

**Root cause:** The build container uses CUDA 11.2 (log: `Detected CUDA version: 11.2`, plus `nvmlDeviceGetGpuFabricInfoV ... no`, `NVML_FI_DEV_C2C_LINK_COUNT ... no` — i.e. an old `nvml.h`). `NVML_DEVICE_UUID_ASCII_LEN` was introduced in a later NVML/CUDA release, so on this image the identifier is undefined:


The two "unused variable" errors are secondary fallout from the failed array-size expansion. UCX builds with `-Wall -Werror`, so this is fatal. Nothing in `src/uct/cuda/base/cuda_nvml.h` or `configure` provides a fallback definition for this macro, and the code that formats the UUID (`uct_cuda_ipc_uuid_to_string`, line 492) is UCX's own and does not actually need an NVML-provided size.

**Implicated commit:** [REDACTED:Hex High Entropy String] — "UCT/CUDA: Reject IPC without native peer access", Peter Andreas Entschev

**File:** src/uct/cuda/cuda_ipc/cuda_ipc_md.c:509-510

**Suggested fix:** Don't depend on the newer NVML macro. The string produced by `uct_cuda_ipc_uuid_to_string()` is a fixed `GPU-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` form (40 bytes + NUL), so define a local constant and use it:

```c
/* "GPU-" + 32 hex chars + 4 dashes + '\0' */
#define UCT_CUDA_IPC_UUID_STR_LEN 41
...
char local_uuid_string[UCT_CUDA_IPC_UUID_STR_LEN];
char remote_uuid_string[UCT_CUDA_IPC_UUID_STR_LEN];
```

Alternatively use the long-standing `NVML_DEVICE_UUID_BUFFER_SIZE` (present since early NVML), or add a compatibility fallback in `src/uct/cuda/base/cuda_nvml.h`:

```c
#ifndef NVML_DEVICE_UUID_ASCII_LEN
#define NVML_DEVICE_UUID_ASCII_LEN NVML_DEVICE_UUID_BUFFER_SIZE
#endif
```
The first option is preferable since it keeps the buffer size tied to UCX's own formatter. Also note `uct_cuda_ipc_nvml_peer_accessible()` is declared `int` but returns `UCS_YES/UCS_NO/UCS_TRY`; consider `ucs_ternary_value_t` for clarity while touching this code.
