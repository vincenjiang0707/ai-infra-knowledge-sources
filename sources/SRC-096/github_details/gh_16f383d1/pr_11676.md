# [PR #11676] UCP/RKEY: Keep configurations at stable addresses

source: https://github.com/openucx/ucx/pull/11676
state: open | updated: 2026-09-23T17:46:53Z

## 正文

## What?

Store each rkey configuration separately from the resizable index array, and
update its users and tests for pointer-based storage.

This PR now contains only the stable-storage change. It depends on #11817 to
keep protocol selection out of async context; it does not add async locking.

## Why?

Protocol selection can recursively create another rkey configuration. With
inline storage, growing the array copies a partially initialized configuration
while the outer selection continues updating the old address. Later lookups
then use an incomplete copy.

This is reachable without an injected configuration: on Gaia, normal
default-reserve traffic naturally moved the array from 32 to 64 while an outer
rkey configuration was live. A diagnostic consistency check observed
`put_short` diverging between the old and current copies in 4/5 runs.

## How?

The resizable array stores pointers to separately allocated configurations.
Growing the array can move the pointer slots, but it cannot move a live
configuration. Worker cleanup destroys and frees each configuration.

## Validation

- Rebased onto current `master` and updated all current-master rkey-config
  test accesses.
- Exact #11817: 20/20 ordinary runs completed; the observation-only natural
  relocation check detected stale/current state divergence in 4/5 runs.
- Current `master` + #11817 + this PR: clean build, 31/31 selected tests,
  20/20 natural two-node runs, and 5/5 forced 32-to-33 pointer-array
  relocations. Every forced marker reported synchronous context.

### jeffnvidia · 2026-08-24

Yes, they are related. After comparing both current heads, I think they address the same underlying rkey-config address-instability, but with different coverage.

#11802 keeps worker->rkey_config as an inline object array and reloads proto_select / rkey_config from the config indexes after nested calls that may grow the worker arrays. That addresses the synchronous recursive-allocation path while avoiding extra indirection. It also includes analogous ep_config reloads.

#11676 instead makes each rkey configuration a separate allocation. Growing the index array can then no longer move a live rkey config, its key, or its proto_select; this makes pointer stability an invariant rather than requiring every nested-call boundary to be audited. It additionally serializes rkey_config_hash lookup/create with the worker async context. #11802 does not change that hash synchronization, and ucp_rkey_proto_resolve() still has the raw lookup/direct-add path there.

So I see the rkey relocation changes as alternative strategies, with a tradeoff between allocation/indirection and maintaining a complete reload audit. The async hash serialization is complementary and should be retained whichever storage strategy is selected. If inline storage is preferred, I would evaluate the reloads from #11802 together with the async serialization from #11676. Conversely, the ep_config reload work in #11802 is complementary to #11676, since #11676 only stabilizes rkey configs.

### jeffnvidia · 2026-08-27

Assuming the last link meant #11802: we do not need all three rkey approaches.

#11817 addresses the async-context race by keeping protocol selection out of async context, but it does not prevent synchronous recursive rkey-array relocation.

For that remaining issue, #11676 and the rkey portion of #11802 are alternative strategies: #11676 provides stable object addresses, while #11802 reloads array-derived pointers after nested allocation. The ep-config reloads in #11802 are complementary because #11676 only changes rkey storage.

So the complete choices are:
- #11817 + #11676, optionally with the ep-config-only part of #11802; or
- #11817 + #11802.

The rkey portions of #11676 and #11802 are not both required.

The only code change on this branch is the UCP configuration-storage rework: `worker->rkey_config` became an array of heap pointers (`ucp_worker.h:301`, `ucp_worker.c:2306-2422`, `ucp_rkey.inl:40-45`) and a new realloc-with-deferred-free scheme was added (`ucp_worker_config_array_append` / `ucp_worker_config_array_release_old`, `ucp_worker.c:2205-2233`). `ep_config` entries are still stored **by value** in that same array, and protocol selection still keeps raw pointers into it — `init_params.ep_config_key = &ucs_array_elem(&worker->ep_config, ep_cfg_index).key` (`proto_select.c:202-203`) is captured before the probe loop (`proto_select.c:222-237`), and `proto_select->cache.value` is cached with the still-present `/* FIXME proto_select could get invalidated by adding rkey config */` (`proto_select.inl:111`). Under the new scheme the old buffer is memcpy'd and freed asynchronously, so a selection made against a stale `ep_config`/cached select element picks lanes/thresholds from an outdated configuration — the send is posted on a lane that is not the one actually wired up/registered for progress (`ucp_proto_select_wiface_activate` / `ep_config->proto_lane_map`, `proto_select.c:454-469`), producing exactly the observed symptom: no error, no completion, endless progress. This is the highest-probability cause given the evidence; the hang is single-occurrence, so a pre-existing flake cannot be fully excluded until the test is looped on master.
