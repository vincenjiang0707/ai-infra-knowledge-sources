# [Issue #10423] Bug report for UD connection when creq length > max_inline_size

source: https://github.com/openucx/ucx/issues/10423
state: closed | updated: 2026-09-01T12:08:27Z
labels: Bug

## 正文

### Describe the bug
For the UD transport layer, if the creq in the connection packet is greater than the value of max_inline_size, the connection will established in non-inline mode. In this case, a bug exists. The following is an example:
#6040  Problem treating incoming creq as ack 

### Steps to Reproduce
- Cmd:mpirun --allow-run-as-root --mca coll ^ucg --mca pml ucx -mca btl ^vader,tcp,openib,uct,ofi,usnic -np 800 -N 400 --hostfile ./hostfile -x PATH -x LD_LIBRARY_PATH -x UCX_LOG_LEVEL=0 -x VERBS_LOG_LEVEL=0 -x UCX_TLS=ud -x UCX_RNDV_THRESH=8k  ./osu_ialltoallw

### Setup and versions
- OS version (Linux openEuler 22.03) + CPU architecture (aarch64)

### Additional information (depending on the issue)
- OpenMPI version:openmpi 4.1.4

### hjelmn · 2025-09-16

I have confirmed there is a bug where UD will release an skb when there is an active send operation using it. The sequence is:

1. Original send posted (may or may not use an skb, it really doesn't matter).
2. Original send timed out and packet resent. This allocates a control skb for the resend.
3. Ack arrives for the original send. This frees the control skb allocated in 2.
4. The skb is reallocated to another operation.
5. The send from 2 finally completes with a combination of the data from the original send and the send from 4.

I have a fix which deals with early freeing of the skb but it needs further testing before I open a PR. This is only one possible race and there may be others that have a similar flavor.

Is there a new bug to cover this or should we re-open it?
