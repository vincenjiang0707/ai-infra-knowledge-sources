# [PR #11542] UCT/IB/MLX5: Add AArch64 ST64B BF copy mode

state: open | updated: 2026-09-23T19:58:50Z

## 正文

## What?
Add an aarch64 `st64b` BlueFlame copy mode for mlx5, with runtime selection and generic-copy fallback.

## Why?

`st64b` can issue a single 64-byte store for BlueFlame doorbell writes, which may improve MMIO write-combining behavior on LS64-capable ARM CPUs.

## How?

Detect LS64 support with `getauxval(AT_HWCAP3) & HWCAP3_LS64`, add an mlx5 BF copy function using `st64b`, select it through the BF copy-mode config, and add a gtest variant for the ST64B MMIO path.

### Testing
```
UCX_RC_MLX5_MMIO_MODE=bf_post UCX_DC_MLX5_MMIO_MODE=bf_post \
UCX_UD_MLX5_MMIO_MODE=bf_post UCX_GGA_MLX5_MMIO_MODE=bf_post \
UCX_RC_MLX5_BF_COPY_MODE=st64b UCX_DC_MLX5_BF_COPY_MODE=st64b \
UCX_UD_MLX5_BF_COPY_MODE=st64b UCX_GGA_MLX5_BF_COPY_MODE=st64b \
./test/gtest/gtest --gtest_filter='rc_mlx5/*:dc_mlx5/*:ud_mlx5/*:gga_mlx5/*'

./test/gtest/gtest --gtest_filter='*test_rc_mlx5_bf_copy*'
```

### svc-nvidia-pr-review · 2026-09-23


Residual coverage gap: the `st64b` path is only exercised when the build machine's assembler supports `.arch_extension ls64` **and** the runtime CPU reports `HWCAP3_LS64`; otherwise both the new gtest and the new configure define are inert. Per `REVIEW.md` (configure/build options should have CI coverage for the changed path), it is worth confirming whether any aarch64 CI job actually compiles `HAVE_AARCH64_ST64B_ASM=1` and runs `test_rc_mlx5_bf_copy_st64b`, otherwise this feature ships untested in CI.


Residual note: `UCT_IB_MLX5_BF_COPY_MODE` is exposed for every mlx5 TL through `uct_ib_mlx5_iface_config_table`, but `gdaki` hard-codes `GENERIC`, so `st64b` is silently ignored there while it errors out on other TLs. Harmless today (gdaki uses `MMIO_MODE_DB`), so not raised inline.
