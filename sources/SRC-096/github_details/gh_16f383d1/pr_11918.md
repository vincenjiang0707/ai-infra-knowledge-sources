# [PR #11918] UCT/TCP: Stop writing PUT data of a canceled EP, report RMA invalidation

source: https://github.com/openucx/ucx/pull/11918
state: open | updated: 2026-09-15T08:26:15Z
labels: 

## 正文

Closes #11929

## What?

1. `uct_ep_flush(UCT_FLUSH_FLAG_CANCEL)` on a TCP EP now also stops PUT data which arrives from the peer from being written. The connection is closed, so nothing lands and the peer's PUT and flush complete with `UCS_ERR_CONNECTION_RESET`.
2. TCP MD reports `UCT_MD_FLAG_INVALIDATE_RMA`.

`uct_ep_destroy()` is not changed: an EP which is destroyed without being canceled keeps receiving, which the disconnect flows rely on.

## Why?

1. Cancel means the user gives up on the operations of the EP and may free or reuse their memory. On RDMA the QP is moved to the error state, so data which the peer is still writing does not land and the peer's operation fails. On TCP the cancel only purged the local operations, so a PUT which was in flight kept being written to the address from the PUT header, into memory the user already reused. We hit this in production: after a request was aborted and its buffer handed to another request, a 4MB PUT landed in it.

   UCP issues this cancel when an endpoint is closed with `UCP_EP_CLOSE_FLAG_FORCE` and when it discards the lanes of a failed endpoint (`ucp_ep_close_nbx`, `ucp_worker_discard_uct_ep`), which are exactly the paths after which the buffer is reused.

2. With `UCP_ERR_HANDLING_MODE_PEER` and rendezvous enabled, `ucp_wireup_add_rma_bw_lanes()` requires `UCT_MD_FLAG_INVALIDATE_RMA` from the MD. TCP MD did not report it, so `ucp_put` over TCP ran the AM based emulation (8KB fragments, a completion message each) instead of `put_zcopy`:

   | ucx_perftest -t ucp_put_bw -s 4M, tcp/lo | MB/s |
   |---|---|
   | without error handling (put_zcopy) | 11935 |
   | `-epeer` (AM emulation) | 2211 |

   On our TCP hosts the receiving CPU stayed at 100% in `ucp_put_handler` / `ucp_rma_sw_send_cmpl` and a connection was limited to 0.3-0.6 GB/s, against over 2 GB/s with put_zcopy.

   TCP MD registers no memory, so there is nothing to invalidate; what the flag has to guarantee, that a canceled operation does not land in memory the user reused and that the peer learns, is provided by the first commit. TCP has no atomics, so `UCT_MD_FLAG_INVALIDATE_AMO` is not reported, and with it not `UCT_MD_FLAG_INVALIDATE`, which means both.

## How?

`UCT_TCP_EP_FLAG_CANCELED` is set in `uct_tcp_ep_flush()`. `uct_tcp_ep_progress_am_rx()` closes the connection when a PUT request arrives on such an EP, and `uct_tcp_ep_progress_put_rx()` does the same for the rest of a PUT which was already in progress. AM is unaffected.

## Tests

`GTEST/UCT/TCP: Add a PUT after cancel test` - a 64MB PUT, so it spans many RX segments and is also received by `uct_tcp_ep_progress_put_rx()`. The receiver cancels its EP while the PUT is being received. Without the first commit the rest of the PUT is written into the canceled EP's buffer and the sender completes with success; with it nothing is written after the cancel and the sender gets `UCS_ERR_CONNECTION_RESET`.

`test_ucp_peer_failure_rndv_abort.put_zcopy_memory_invalidation` and `put_zcopy_force_flush_memory_invalidation` skipped on TCP until now ("transport has no rma_bw lanes"); they run and pass with this series.

`test_invalidate_rma_bw_lane()` expected a TCP RMA BW lane without invalidation support when rendezvous is disabled, and is updated.

Two UCP fixes are needed once TCP is used as an RMA BW lane. Both problems exist on master before this series and can be reproduced there by making TCP an RMA BW lane with `UCX_RNDV_THRESH=inf`:

- `ucp_request_get_invalidation_map()` asserted that every non p2p RMA BW lane supports get_zcopy, while such a lane can be put_zcopy only. This is what fails in `tcp/test_ucp_peer_failure_rndv_abort` on the IB workers.
- In `UCP_ERR_HANDLING_MODE_FAILOVER` only protocols which report `UCP_PROTO_COMMON_INIT_FLAG_FAILOVER` are selected, and the AM based GET emulation does not report it, so a transport without get_zcopy and get_bcopy has no GET protocol at all. `tcp/test_ucp_fault_tolerance` fails on all its GET variants without this.

Full gtest on x86_64, clean build of this series: 16123 passed, 1 failed - `malloc_hook_cplusplus.new_delete`, which fails the same way on master on this machine.

### svc-ucx · 2026-09-08

🤖 **CI Triage Agent** — `UCX PR (Tests althca on worker 1)` · commit `52394249`

**TL;DR:** `tcp/test_ucp_peer_failure_rndv_abort.put_zcopy_force_flush/0` aborts on `ucs_assert(ucp_ep_get_iface_attr(ep, lane)->cap.flags & UCT_IFACE_FLAG_GET_ZCOPY)` in `ucp_request_get_invalidation_map()`, because this PR makes the TCP MD advertise `UCT_MD_FLAG_INVALIDATE_RMA` while the TCP iface only ever reports `PUT_ZCOPY` — the GET_ZCOPY-only assertion is IB-centric and must be relaxed to "GET_ZCOPY **or** PUT_ZCOPY".

<details><summary>Full analysis</summary>

**Summary:** gtest job "althca on worker 1" aborted (`make: *** [test] Aborted`, Bash exit code 2) during `tcp/test_ucp_peer_failure_rndv_abort.put_zcopy_force_flush/0 <tcp/am>` with an assertion failure at `src/ucp/core/ucp_request.c:394`.

**Root cause:** Log backtrace path: `ucp_worker_progress → ucp_worker_discard_uct_ep_destroy_progress → ucp_ep_discard_lanes_callback → ucp_ep_reqs_purge → ucp_proto_rndv_rtr_abort (rndv_rtr.c:304) → ucp_request_memh_invalidate (ucp_request.c:440) → ucp_request_get_invalidation_map (ucp_request.c:393)`.
`ucp_request_get_invalidation_map()` walks `key->rma_bw_lanes[]` and, for every non-p2p lane, asserts the lane's iface supports `UCT_IFACE_FLAG_GET_ZCOPY` and its MD supports `UCT_MD_FLAG_INVALIDATE_RMA`. That first assertion encodes an IB/RC-style assumption that any invalidation-capable, connect-to-iface RMA-BW lane can do GET zcopy.

This PR's commit `88f1455d` ("UCT/TCP: Report RMA memory invalidation support") adds `attr->flags |= UCT_MD_FLAG_INVALIDATE_RMA;` in `uct_tcp_md_query()` (src/uct/tcp/tcp_md.c:38), and companion test commit `fec88a8b` ("GTEST/UCP: TCP RMA BW lanes now support invalidation") lets these rndv-abort tests run over TCP. But `uct_tcp_iface_query()` only ever sets `UCT_IFACE_FLAG_PUT_ZCOPY` (src/uct/tcp/tcp_iface.c:393) and never `GET_ZCOPY`; TCP is also connect-to-iface, so `ucp_ep_is_lane_p2p()` is false and the assert branch is taken. Result: a debug-build assertion abort on the RTR abort/memh-invalidate path for a TCP rma_bw lane. This is a new-code/assert mismatch introduced by the PR, not flakiness or a timeout.

**Implicated commit:** `88f1455d` "UCT/TCP: Report RMA memory invalidation support" (Maor Vanmak, 2026-09-08), together with `fec88a8b` "GTEST/UCP: TCP RMA BW lanes now support invalidation" (same author/date), on branch `tcp-cancel-fences-rma` (PR #11918).

**File:** `src/ucp/core/ucp_request.c:381-402` (assert at :393-394); related: `src/uct/tcp/tcp_md.c:38`, `src/uct/tcp/tcp_iface.c:356-394`.

**Suggested fix:** Relax the capability assertion in `ucp_request_get_invalidation_map()` so a non-p2p RMA-BW lane qualifies if it supports *either* zcopy RMA direction, and keep the MD check as the real gate for adding the bit, e.g.:

```c
if (!ucp_ep_is_lane_p2p(ep, lane)) {
    ucs_assert(ucp_ep_get_iface_attr(ep, lane)->cap.flags &
               (UCT_IFACE_FLAG_GET_ZCOPY | UCT_IFACE_FLAG_PUT_ZCOPY));
    ucs_assert(ucp_ep_md_attr(ep, lane)->flags &
               UCT_MD_FLAG_INVALIDATE_RMA);
    inv_map |= UCS_BIT(ucp_ep_md_index(ep, lane));
}
```

(Alternatively, make the MD flag the condition rather than an assertion: `if (ucp_ep_md_attr(ep, lane)->flags & UCT_MD_FLAG_INVALIDATE_RMA) inv_map |= ...;` and skip lanes that lack it — this is more robust for mixed-transport rma_bw lane sets such as tcp+shm.) Since the TCP MD registers no memory, its md index can never appear in `memh->md_map`, so including/excluding it is functionally harmless; the assertion is what needs updating. Please re-run the `althca` gtest job after the change, as this test also covers `shm+tcp` lane mixes.

**Related:** PR #11918 (branch `tcp-cancel-fences-rma`); no existing issue found matching this assertion.

</details>

<details><summary>Full analysis</summary>

**Summary:** Azure Pipelines "Tests gpu on worker 0" step `./contrib/test_jenkins.sh` failed (bash exit 255) — `ucp_hello_world` with CUDA memory types crashed with SIGSEGV and the final `-w -m cuda` run failed with `unable to send UCX data message`.

**Root cause:** CUDA is non-functional on the runner. From the very first process launch onward every run logs:
- `cuda_util.c:185 UCX DIAG cuDeviceGetCount(&num_devices) failed: initialization error`
- `cuda_nvml.c:191 UCX DIAG failed to initialize nvml`
- `cuda_ctx.c:52 UCX ERROR cuDeviceGetCount(&num_devices) failed: initialization error`
- `ucp_context.c:1508 WARN transport 'cuda' is not available`

Consequently `cudaMalloc`/`cudaMallocManaged` fail with `no CUDA-capable device is detected`. In `mem_type_malloc()` the `CUDA_FUNC()` macro only *prints* the CUDA error and does not propagate it, so the function returns the **uninitialized local `ptr`**. The example then passes that garbage pointer to `ucp_tag_send_nbx`, which crashes:
`memcpy → uct_mm_ep_am_short → ucp_tag_send_nbx → ucp_hello_world` — "address not mapped to object at address 0x1eb" (two core dumps, pids 59507 and 59588). The same bad pointer also produced `tcp_ep.c:1260 send(26) failed: Input/output error` in the final `tcp,cuda` run, which is what returned non-zero and killed the step. No code in this PR (TCP cancel/fences/RMA) is on any of these paths; the `-m host` runs all passed (`----- UCP TEST SUCCESS ----`).

**Implicated commit:** unknown — not a code regression. The unchecked-allocation weakness dates to pre-existing code (last touched by `2be620aa`, rakhmets, "EXAMPLES: Fixed checking for memory type support"); the trigger is node state on `swx-rdmz-ucx-gpu-02`.

**File:** `examples/hello_world_util.h:69-92` (`mem_type_malloc`, `CUDA_FUNC` at line 50); crash surfaced via `examples/ucp_hello_world.c` → `uct_mm_ep_am_short`

**Suggested fix:**
1. Infra (primary): fix/reset the GPU node — the container is not getting the NVIDIA devices/driver (check `nvidia-smi` inside the container, `--gpus`/`nvidia-container-runtime` mounts, driver/DOCA `ubuntu2404_doca31_gpunetio` image version, and stale persistence-mode state). Re-run the PR job once the node reports a device.
2. Hardening (recommended, prevents this masking as a bogus segfault): make CUDA allocation failures fatal instead of returning an uninitialized pointer, e.g.
   ```c
   void *mem_type_malloc(size_t length) {
       void *ptr = NULL;   /* initialize */
       ...
       case UCS_MEMORY_TYPE_CUDA:
           if (cudaMalloc(&ptr, length) != cudaSuccess) { ptr = NULL; }
           break;
   ```
   and have the callers `CHKERR_JUMP(ptr == NULL, "allocate memory", err)`.
3. Optionally have `contrib/test_jenkins.sh` skip the `cuda`/`cuda-managed` mem_types (or fail early with a clear message) when no CUDA device is present, so a broken GPU node yields an actionable error rather than a core dump.

**Related:** none found (searches for this signature returned no matching issues/PRs; PR #11918 is the build under test)
