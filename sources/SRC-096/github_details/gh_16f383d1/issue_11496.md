# [Issue #11496] dc_mlx5 auto-selected for intra-node rendezvous causes significant performance regression on multi-NUMA systems

source: https://github.com/openucx/ucx/issues/11496
state: closed | updated: 2026-06-08T14:49:53Z
labels: 

## 正文

Hello.  Please see the following report regarding what appears to be a regression due to a significant amount of intra-node communications being routed through dc_mlx5 rather than shared memory.  I'm not sure if this mix of shared memory + HCA loopback comms is intended behavior or not - but if it is, I'd like to ask if anyone can recommend a workaround that's viable for multi-node jobs (since we can't just set UCX_TLS=shm,self when using mutliple nodes).  Thank you for your time and assistance!

## Summary

UCX 1.20.0 protocol selection routes 45% of large intra-node messages through `dc_mlx5` (InfiniBand HCA loopback) instead of pure shared memory transports. On a dual-socket AMD EPYC 9454 system with 8 NUMA domains and the HCA attached to NUMA node 0, this causes a (at worst) **2.7x performance regression** in a real-world MPI application compared to Intel MPI, and a **2.5x regression** compared to the same UCX build with `UCX_TLS=shm,self`.  On average, most cases exhibit around a **20-30%** increase in wall clock time compared to shared memory only.

The workaround `UCX_TLS=shm,self` fully resolves the issue for single-node jobs, but is not viable for multi-node jobs where `dc_mlx5` is needed for inter-node communication.

## Problem

When running a 96-rank MPI application on a single node with default `UCX_TLS`, UCX selects `dc_mlx5` as a transport candidate for **intra-node** communication. The `UCX_PROTO_INFO=y` output shows that for large messages, UCX splits rendezvous traffic between shared memory and the HCA:

```

  |    2825..77859 | (?) rendezvous copy from mapped remote memory | xpmem/memory                                   |
  |     77860..inf | (?) rendezvous zero-copy read from remote     | 55% on knem/memory and 45% on dc_mlx5/mlx5_0:1 |

tagged message by ucp_tag_send*(fast-completion) from host memory:
```

The same pattern applies to all active message variants. For RMA put operations, UCX correctly uses only shared memory (xpmem/knem), so the issue is specific to tagged and active message rendezvous.

## Performance impact

Benchmark: industrial FEA implicit solver (PAM-CRASH/CSM), 96 MPI ranks on a single node.

| Configuration | Elapsed (s) | Ratio vs Intel MPI 2021.14 | CPU/Elapsed |
|---|---|---|---|
| Intel MPI 2021.14 (baseline) | 75.1 | 1.00x | — |
| MPICH+UCX, default `UCX_TLS` | 203.3 | **2.71x** | 90.1% |
| MPICH+UCX, `UCX_TLS=shm,self` | 79.7 | 1.06x | 97.4% |

The `CPU/ELAPSED` ratio is also telling: 90.1% with default transports vs 97.4% with `shm,self`, indicating that the default configuration introduces significant idle time (likely from HCA round-trips).

The regression is not limited to this one case. Across a suite of ~30 single-node benchmarks on this hardware:

| Partition | Cores | HCA | Worst regression | Typical range |
|---|---|---|---|---|
| c96m768 (AMD EPYC 9454) | 96 | mlx5 ConnectX-6 | **5.5x** | 1.1x - 3.6x |
| c64m512 (64-core) | 64 | mlx5 | 1.5x | 1.06x - 1.29x |
| c36m384 (OmniPath, no mlx5) | 36 | hfi1 | — | ~1.0x (no regression) |

The severity scales with core count and NUMA complexity. The c96m768 nodes (8 NUMA domains, HCA on node 0) are most affected because many ranks must cross the inter-socket link to reach the HCA.

## Workaround and its limitation

Setting `UCX_TLS=shm,self` on single-node jobs eliminates the regression. However, this is **not viable for multi-node jobs** because `dc_mlx5` is essential for inter-node communication — removing it causes job timeouts.

For multi-node jobs, intra-node communication between co-located ranks still suffers from the same `dc_mlx5` loopback penalty, but there is no way to tell UCX "use `dc_mlx5` only for inter-node, use shared memory for intra-node" via environment variables.

## Expected behavior

For intra-node communication where shared memory transports (xpmem, knem, sysv) are available, UCX should prefer them over `dc_mlx5` for all message sizes, especially on systems where the HCA is remote from most NUMA domains. The HCA loopback path adds latency and contention without the bandwidth advantage it provides for inter-node transfers.

Possible approaches (from a user perspective):
1. Adjust the protocol scoring so that `dc_mlx5` does not win for intra-node rendezvous when knem/xpmem are available
2. Provide a way to configure per-distance transport preferences (e.g., exclude `dc_mlx5` from intra-node but keep it for inter-node)
3. Account for NUMA distance to the HCA in the transport scoring for intra-node paths

## Steps to reproduce

1. Run any MPI application with >=64 ranks on a single ConnectX-equipped node with xpmem and knem available
2. Set `UCX_PROTO_INFO=y UCX_LOG_LEVEL=info`
3. Observe that `dc_mlx5` appears in the intra-node protocol selection for large messages
4. Compare elapsed time with and without `UCX_TLS=shm,self`

### gsm-esi · 2026-06-08

Hello again.  After analyzing the UCX source, I found that explicitly setting UCX_NUM_PPN to the number of cores on each node resolved the transport selection behavior such that intranode communication now occurs only via shared memory rather than partially over dc_mlx5.  The regression I observed has also largely disappeared as a result.
