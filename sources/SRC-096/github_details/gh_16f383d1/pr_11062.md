# [PR #11062] UCP/RNDV: Throttle rndv fragment requests

source: https://github.com/openucx/ucx/pull/11062
state: open | updated: 2026-09-22T19:11:59Z
labels: Ready for Review

## 正文

## What?
Added a worker-level throttling mechanism for rndv fragment requests (both pipeline and standalone mtype requests).

## Why?
Without throttling, rendezvous protocols can spawn an unbounded number of concurrent fragment requests, each allocating staging memory from GPU memory pools. Under heavy workloads, this leads to GPU memory exhaustion (OOM), as tracked in https://nvbugspro.nvidia.com/bug/5359018. The throttling mechanism bounds the number of in-flight fragments per worker, preventing resource exhaustion while allowing work to progress as fragments complete.

## How?
The throttling is implemented using a worker-level flow control state (`worker->rndv_ppln_fc`) consisting of:
- An `active_frags` counter tracking currently in-flight fragment operations
- A `pending_q` queue holding throttled requests waiting for resources

When a new fragment request would exceed `UCX_RNDV_PPLN_WORKER_MAX_FRAGS`, the request is queued in `pending_q`. When fragments complete, `active_frags` is decremented and one queued request is rescheduled via `ucs_callbackq_add_oneshot()` to the main progress loop.

The mechanism applies to:
- Pipeline fragment dispatch in `rndv_ppln.c`
- Standalone `mtype` protocols in `rndv_rtr.c`, `rndv_get.c`, and `rndv_put.c`.

🤖 **CI Triage Agent** — `UCX PR (AddressSanitizer gpu on worker 0)` · commit `4c746e90`

**TL;DR:** The new gtest `dcx/test_ucp_peer_failure_rndv_put_ppln_abort.rtr_mtype_fc_pending` segfaults because `ucp_proto_rndv_rtr_mtype_abort()` releases `req->send.rndv.mdesc` for a request that was *throttled* and therefore never got an mdesc — the field still holds uninitialized garbage, which is then passed to `ucs_mpool_put_inline()`. <details><summary>Full analysis</summary>

**Summary:** ASan GPU job fails with `SEGV on unknown address 0xef1600008326` in `ucs_mpool_add_to_freelist` (`src/ucs/datastruct/mpool.inl:80`) while running `dcx/test_ucp_peer_failure_rndv_put_ppln_abort.rtr_mtype_fc_pending/1`, making `make test` exit with error 1.

```

#1 ucs_mpool_put_inline           src/ucs/datastruct/mpool.inl:104
#2 ucp_proto_rndv_mtype_mdesc_release  src/ucp/rndv/rndv_mtype.inl:278
#3 ucp_proto_rndv_rtr_mtype_complete   src/ucp/rndv/rndv_rtr.c:363
#4 ucp_proto_rndv_rtr_mtype_abort      src/ucp/rndv/rndv_rtr.c:389

```

The test deliberately drains the CUDA fragment mpool (`hold_cuda_fragments()`), so `ucp_proto_rndv_mtype_request_init()` takes the new throttling path: `ucp_rndv_mpool_get()` returns `UCS_ERR_NO_RESOURCE` **without writing `req->send.rndv.mdesc`**, the request is pushed onto `worker->rndv_mtype_fc.pending_q[]` (rndv_mtype.inl:58-81), and `ucp_proto_rndv_rtr_mtype_progress()` returns early *without* setting `UCP_REQUEST_FLAG_PROTO_INITIALIZED` (rndv_rtr.c:437-451).

The test then aborts every request sitting in the pending queues. `ucp_proto_rndv_rtr_mtype_abort()` calls `ucp_proto_rndv_rtr_mtype_complete(req, 1)`, whose only guard is:

```c
if (!abort || (req->send.rndv.mdesc != NULL)) {
    ucp_proto_rndv_mtype_mdesc_release(req);
}
```

`req->send.rndv.mdesc` is never initialized to NULL on the throttle path (it aliases `rkey_ptr_addr`/`rkey_buffer` in the `send.rndv` union and holds stale data from the recycled request), so the NULL check passes and a garbage pointer is handed to `ucs_mpool_put_inline()` → SEGV. Note the sibling reset path `ucp_proto_rndv_rtr_mtype_reset()` (rndv_rtr.c:392-400) correctly uses `UCP_REQUEST_FLAG_PROTO_INITIALIZED` as the guard and clears `mdesc` — the abort path is inconsistent with it. Secondary bug: even if it didn't crash, releasing here would also call `ucp_proto_rndv_mtype_fc_reschedule_pending()` for a fragment that was never taken from the pool, corrupting the FC accounting.

**Implicated commit:** `89505d2a` "UCP/RNDV: add abort path support" (Alma Mastbaum), with follow-up `d52d74c3` "UCP/RNDV: abort gtest fix" — both on PR #11062 branch `add_throttling_to_rndv_fragment_requests` (tested head `4c746e90`).

**File:** `src/ucp/rndv/rndv_rtr.c:360-364` (and `src/ucp/rndv/rndv_mtype.inl:48-82`, `:275-280`)

**Suggested fix:**
1. Make the throttle path leave the field in a defined state — in `ucp_proto_rndv_mtype_request_init()`, before `ucs_queue_push()`, add `req->send.rndv.mdesc = NULL;`.
2. More robustly, use the same guard as the reset path in `ucp_proto_rndv_rtr_mtype_complete()`:
```c
if (!abort || (req->flags & UCP_REQUEST_FLAG_PROTO_INITIALIZED)) {
    ucp_proto_rndv_mtype_mdesc_release(req);
}
```
so no mdesc release / FC reschedule happens for a request that never obtained a fragment.
3. Audit the equivalent PUT/GET mtype abort paths for the same "aborted while queued in `rndv_mtype_fc.pending_q`" case, and add an `ucs_assert(req->send.rndv.mdesc != NULL)` inside `ucp_proto_rndv_mtype_mdesc_release()` to catch this class of bug in debug builds.

`src/ucp/rndv/proto_rndv.c:778-785` (`ucp_proto_rndv_rts_reset`, called from `ucp_proto_rndv_rts_abort`) asserts that a `PROTO_INITIALIZED` RTS request has `completed_size == 0`. That invariant does not hold in this scenario:

```c
ucs_status_t ucp_proto_rndv_rts_reset(ucp_request_t *req)

        /* Fragments already acknowledged by partial RTRs are dropped on abort */

```
