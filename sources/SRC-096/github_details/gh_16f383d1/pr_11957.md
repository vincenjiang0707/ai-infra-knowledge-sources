# [PR #11957] UCT/ROCM: Enable dmabuf by default with peermem fallback  - v1.23.x

## 正文

(cherry picked from commit 57c450e5e962ef4b460eb05a5c8806352cd5c14b)

## What?
Use dma-buf for GPU-direct when the kernel supports it, and keep peermem as the fallback on older kernels. Also report allocation-base offsets for interior ROCm addresses.

## Why?
The rocm components in UCX have support for the dma-buf mechanism to enable direct data transfer between an RDMA NIC and a GPU. However, the user explicitly needs to request that support by setting UCX_ROCM_COPY_DMABUF=y, dma-buf support is not turned on by default.

## How?
Starting from linux kernel > 6.0, the peermem mechanism that was used previously is not useable in the vast majority of deployments, necessitating using dma-buf instead. The goal of this story is to enable dma-buf by default in the rocm components of UCX, and ensure that if dma-buf support is not available (e.g. linux kernel 5.15 in most cases) we can fall back to the peermem mechanism if that is available.

🤖 **CI Triage Agent** — `UCX PR (Tests gpu on worker 2)` · commit `31635467`

**TL;DR:** The GPU perftest client aborted with a UCS fatal assertion `!(region->flags & UCS_RCACHE_REGION_FLAG_PGTABLE)` at `rcache.c:396` while `ucp_mem_unmap` released a gdrcopy rcache region — the region's refcount hit 0 while it was still in the page table, i.e. the page-table's own +1 reference was lost by the non-atomic `region->refcount++` on the gdrcopy fast-path lookup (`rcache.inl:103`); fix is to make that increment atomic (use `ucs_rcache_region_hold()`).

<details><summary>Full analysis</summary>

**Summary:** `ucx_perftest` client (job "Tests gpu on worker 2") aborted with SIGABRT (exit 134) right after `ucp_contig_cuda_host_tag_lat/2097152`, on the `UCX_MEMTYPE_CACHE=y` / `UCX_IB_GPU_DIRECT_RDMA=y` gdrcopy iteration of `contrib/test_jenkins.sh`.

**Root cause:** From the log backtrace: `ucp_mem_unmap` → `uct_gdr_copy_mem_rcache_dereg` (`libuct_cuda_gdrcopy.so`) → `ucs_rcache_region_put` → `ucs_mem_region_destroy_internal`, which fatally asserted `!(region->flags & UCS_RCACHE_REGION_FLAG_PGTABLE)` (`src/ucs/memory/rcache.c:396`). A live rcache region is created with `refcount = 2` ("page-table + user", `rcache.c:1028`), so reaching refcount 0 while `FLAG_PGTABLE` is still set means the page-table's reference was lost (or the region was released once too many). The gdrcopy MD's fast registration path calls `ucs_rcache_lookup()` (`src/uct/cuda/gdr_copy/gdr_copy_md.c:425`), which lands in `ucs_rcache_lookup_unsafe()` where the reference is taken with a **plain, non-atomic** `region->refcount++` while holding only the rcache *read* lock (`src/ucs/memory/rcache.inl:103`), plus an unlocked `ucs_rcache_region_lru_get()`. Every other path uses atomics (`ucs_rcache_region_hold()` → `ucs_atomic_add32`, `rcache.c:1055`; `ucs_atomic_fsub32` in `ucs_rcache_region_put_internal`, `rcache.c:450`; purge, `rcache.c:667`). A lost increment there leaves the count one short, so the matching `ucs_rcache_region_put()` at dereg destroys the region while it is still in the page table — exactly the observed assert (and, in release builds, a use-after-free of a still-linked pgtable region). This is unrelated to PR #11957 ("UCT/ROCM: Enable dmabuf by default with peermem fallback"), which touches no CUDA/gdrcopy/rcache code — the failure is a pre-existing race in the v1.23.x gdrcopy rcache path, not a regression from the PR.

**Implicated commit:** `21d6cd66` — Artemy Kovalyov, "UCT/GDR_COPY: Use fast-path cache lookup" (introduced use of the unsafe lookup from gdrcopy); related locking rework `5687e9a8` — Colin Hirsch, "UCS/RCACHE: Fix locking for gdrcopy (#11149)".

**File:** `src/ucs/memory/rcache.inl:103` (refcount increment) — assert fires at `src/ucs/memory/rcache.c:396`; caller `src/uct/cuda/gdr_copy/gdr_copy_md.c:425` / `:455`.

**Suggested fix:**
1. In `ucs_rcache_lookup_unsafe()` replace `region->refcount++` with the atomic form, e.g. `ucs_atomic_add32(&region->refcount, 1)` (or call `ucs_rcache_region_hold()`), matching the read-lock-only context; likewise ensure `ucs_rcache_region_lru_get()` there runs in `UCS_RCACHE_LRU_LOCKED` mode for the gdrcopy rcache (`UCS_RCACHE_FLAG_NEED_LRU_LOCK`).
2. Harden `ucs_mem_region_destroy_internal()` to log the region/refcount state (`ucs_rcache_region_error` with flags and refcount) instead of a bare `ucs_assert`, so this is diagnosable in future CI hits.
3. Since PR #11957 is unrelated, re-run this job to unblock the backport; track the rcache fix separately and cherry-pick it to `v1.23.x`.

**Related:** PR https://github.com/openucx/ucx/pull/11957 (the PR under test, unrelated to the crash); rcache/gdrcopy locking PR https://github.com/openucx/ucx/pull/11149. No existing issue found for this assertion signature — worth opening one.
