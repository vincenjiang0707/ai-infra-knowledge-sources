### svc-ucx · 2026-09-01

🤖 **CI Triage Agent** — `UCX PR (AddressSanitizer new on worker 0)` · commit `f0e7095c`

**TL;DR:** The only failing test in the whole 8532-test ASan run is the newly added `test_rcache_inv_q_growth.inv_q_bounded_with_interval_tree`, whose hard-coded resource budgets (≤512 KB VmRSS growth / ≤100 interval-tree nodes over 40 000 munmap iterations) are not satisfiable in an AddressSanitizer build; the fix is to drop the RSS-based assertion (or skip the test under sanitizers/valgrind) and assert only on `ucs_interval_tree_count()`.

<details><summary>Full analysis</summary>

**Summary:** `make test` in the "AddressSanitizer new on worker 0" job exited 1 because `test_rcache_inv_q_growth.inv_q_bounded_with_interval_tree` failed (`[ PASSED ] 8531 tests`, `[ FAILED ] 1 test`, `make: *** [Makefile:4713: test] Error 1`).

**Root cause:** The test is a resource-usage regression test, not a functional one. It performs 40 000 `munmap`+`mmap` iterations on an rcache created with `UCS_RCACHE_FLAG_SYNC_EVENTS` and `max_unreleased = SIZE_MAX`, so every unmap event goes through `ucs_rcache_unmapped_callback()` → `ucs_interval_tree_insert()` (src/ucs/memory/rcache.c:636-650), and then asserts:
- `EXPECT_LE(q_delta, 100)` (interval-tree node count), and
- `EXPECT_LE(rss_delta, 512 /* KB */)` — a `VmRSS` delta read from `/proc/self/status`.

Under AddressSanitizer neither budget is realistic: every interval-tree node allocation carries redzones plus a retained malloc stack trace, freed nodes go into ASan's quarantine instead of back to the OS, and ASan's allocator never trims — 40 000 insert/merge/free cycles inflate `VmRSS` well past 512 KB even though the interval tree itself stays compact. `VmRSS` is also a process-global metric, and this ASan binary runs the entire gtest suite in one process, so unrelated background allocations land inside the measurement window. The drain assertion (`EXPECT_EQ(0u, inv_q_length())`) is sound — `ucs_rcache_check_inv_queue()` (rcache.c:538-561) pops the whole tree — so the failure is one of the two threshold checks, most plausibly the RSS one.

**Implicated commit:** [REDACTED:Hex High Entropy String] (PR #11861, branch `agent/pr11685-azure-test-isolation`) — `test_rcache_inv_q_growth` does not exist in any upstream commit touching `test/gtest/ucs/test_rcache.cc` (latest upstream is 311e3506 "UCS/RCACHE: Change inv_q type to interval tree (#11248)", nbellalou), so the test class was introduced by this PR.

**File:** test/gtest/ucs/test_rcache.cc:1100-1138 (thresholds at lines 1106-1107, failing checks at lines 1124 and 1130); related product code src/ucs/memory/rcache.c:636-650

**Suggested fix:**
1. Remove the `VmRSS` measurement from the test — RSS is not a deterministic property of the rcache and cannot be bounded in an instrumented (ASan) or shared-process run. Keep only the data-structure invariant, which is what the interval-tree fix actually guarantees:
   ```c
   size_t q_delta = inv_q_length() - q_before;
   EXPECT_LE(q_delta, max_expected_nodes);   /* interval tree merges ranges */
   ...
   EXPECT_EQ(0u, inv_q_length());            /* one get() drains the tree */
   ```
2. If an RSS check is really wanted, gate it out for sanitizer/valgrind builds, e.g.
   ```c
   #if defined(__SANITIZE_ADDRESS__) || defined(__has_feature) /* asan */
       UCS_TEST_SKIP_R("RSS accounting is unreliable under AddressSanitizer");
   #endif
       if (RUNNING_ON_VALGRIND) { UCS_TEST_SKIP_R("valgrind"); }
   ```
   (`src/ucs/sys/checker.h` currently only provides `RUNNING_ON_VALGRIND`; an ASan predicate would need to be added there.)
3. Also reduce `num_iters` (40 000 iterations of mlock/munmap plus UCM event dispatch is very slow under ASan) — a few thousand iterations already demonstrate bounded tree growth.

**Related:** upstream interval-tree work this test guards: 311e3506 (#11248 "UCS/RCACHE: Change inv_q type to interval tree"), c0b9ee38 (#11213 "Interval tree fixes"), 6b256526 (#11120 "Introduce interval tree data structure"); no existing issue/PR mentions `test_rcache_inv_q_growth`.
