# [PR #11975] UCT/IB: Dump complete packets in trace-data logs

source: https://github.com/openucx/ucx/pull/11975
state: open | updated: 2026-09-25T07:08:31Z
labels: 

## 正文

## What?

`uct_ib_log_dump_sg_list()` copies the packet into a fixed `char data[256]` before handing it to the dump callback, which then parses past the end of the copy for any larger packet. That is an out-of-bounds read of the stack buffer, and it prints a bogus description. Only reachable with trace-data logging enabled (`UCX_LOG_LEVEL=data` or more verbose); nothing is wrong on the wire.

A 325-byte `WIREUP REQ`, before and after:

```
am 1 WIREUP REQ [<malformed address> uuid 0x0 src_ep_id 0x15554c607140 ...]
am 1 WIREUP REQ [funk03:1604837 uuid 0xd3a9b6897678a217 src_ep_id 0x15554c607140 ...] s...
```

## Why?

The dump callbacks parse a message by its own headers and get no length they can rely on — `ucp_address_unpack()` takes none at all — so a truncated copy makes them walk off its end. Only the send path was affected; receive completions pass the real buffer through.

## How?

Size the gather buffer to the message with `ucs_alloc_on_stack()`, so only large packets reach the heap. Skip the callback when nothing was collected, since it has no header to read. A description can still be cut by the log line length, so stamp the line end with an ellipsis; one that fits keeps its own terminator and hides the stamp. Verified on ConnectX with loopback `ucx_perftest` and the `rc_mlx5`/`ud_mlx5` p2p gtests under `UCX_LOG_LEVEL=data`.

<details><summary>Full analysis</summary>

**Summary:** `make test` in the `centos8_cuda11_asan` container exited with error 1 because 1 of 10193 gtests failed: `mem_type/test_memtype_cache_deferred_create.mt_cache_init/mt_8/2` (`GetParam() = 2` → `UCS_MEMORY_TYPE_CUDA_MANAGED`); all other 10192 tests passed.

**Root cause:** Evidence from the log: the only failure is in the multi-threaded memtype-cache test; no ASAN report, no crash, no timeout (the suite ran to completion and tore down normally, largest inter-line gap is a few seconds). Reading the test, `UCS_MT_TEST_P(test_memtype_cache_deferred_create, mt_cache_init, 8)` runs `test_alloc_before_init(1000000, false, 0)` in 8 threads simultaneously, each allocating a 1 MB CUDA-managed buffer and then asserting on the *single global* memtype cache:
- `test_unknown_region_found(b)` requires the lookup to return `UCS_OK` (the region must already be in the cache), which depends on the racing order of "buffer allocated" vs. "another thread triggered deferred cache creation + `UCM_EVENT_FLAG_EXISTING_ALLOC` scan" (test/gtest/ucs/test_memtype_cache.cc:517-535).
- `test_region_not_found(b)` / `test_ptr_not_found()` look up `[ptr, size + UCS_PGT_ADDR_ALIGN)` and require either `UCS_ERR_NO_ELEM` or `UCS_MEMORY_TYPE_UNKNOWN` (test_memtype_cache.cc:45-52, :92-93). With 8 threads allocating same-type (cuda-managed) buffers concurrently, CUDA frequently hands out adjacent VA ranges, and `ucs_memtype_cache_update_internal()` explicitly **merges adjacent/overlapping regions of the same mem_type and mem_flags** (src/ucs/memory/memtype_cache.c:222-232). The merged region then contains the deliberately-overrun lookup range, so the lookup returns `UCS_OK` with `type = cuda-managed` and `EXPECT_EQ(UCS_MEMORY_TYPE_UNKNOWN, mem_info.type)` fails.
Neither the memtype cache nor CUDA memory handling is touched by this PR (branch `wireup_malformed_overrun`, a UCP wireup-address change), so this is pre-existing MT-test flakiness amplified by the slow ASAN build.

**Implicated commit:** unknown — not the PR head `00e218e3`; the racy test and the region-merge logic predate it (nearest relevant changes: `b6b85316` tomerg-nvidia "UCP/UCT/UCS: Add memory registration flags", `09c96769` Leonid Genkin "UCM: Propagate memory attributes in allocation events", both of which added the `mem_flags`-sensitive merge path)

**File:** test/gtest/ucs/test_memtype_cache.cc:572 (`mt_cache_init`), with the failing assertions at test/gtest/ucs/test_memtype_cache.cc:45-52 and :92-93; merge logic at src/ucs/memory/memtype_cache.c:222-232

**Suggested fix:** Re-run the `gpu on worker 3` job to unblock PR #11975 — it is not a regression. For a durable fix, make the MT test not assert on "not found" ranges that other threads can influence: in `test_alloc_before_init`, skip `test_region_not_found()` / `test_ptr_not_found()` when running multi-threaded (e.g. guard with `barrier()`-synchronized single-thread sections or `if (num_threads() == 1)`), or serialize the allocate-and-check sequence with a mutex so only one 1 MB cuda-managed buffer is live per check. Alternatively restrict `mt_cache_init` to verifying concurrent deferred cache creation (the lookup/`UCS_OK` part) and drop the adjacency/overrun negative checks, which are already covered by the single-threaded `allocate_and_update` / `lookup_adjacent_regions` variants.

**Related:** none found (no existing issue/PR matches `test_memtype_cache_deferred_create` / `mt_cache_init` in this repo)
