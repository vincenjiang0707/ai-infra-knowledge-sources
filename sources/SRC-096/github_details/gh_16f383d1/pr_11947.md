# [PR #11947] UCP: Split an SGL put between the lanes by bytes

source: https://github.com/openucx/ucx/pull/11947
state: open | updated: 2026-09-15T19:21:55Z
labels: 

## 正文

## What?
Count the SGL iterator length and offset in bytes, and give every lane an equal share of the message, splitting elements where a share ends.

## Why?
Elements were distributed by count, so a single element used one lane only and lost about 50% of the WRITE bandwidth, and any element count which is not a multiple of the lane count left the lanes unevenly loaded.

## How?
The SGL iterator now keeps the byte length and offset like the IOV one, and a batch of fragments is limited by its total length, so one post covers the whole lane payload returned by `ucp_proto_multi_max_payload()`.

<details><summary>Full analysis</summary>

**Summary:** `make` failed in `test/gtest` — `ucp/gtest-test_ucp_dt.o` compile error (`-Werror`, "too few arguments to function `ucp_datatype_iter_sgl_init`"), aborting the "Build on aarch64" step with exit code 2.

**Root cause:** Signature/call-site mismatch introduced by this PR's series. `src/ucp/dt/datatype_iter.h:118-123` now declares:

```
ucs_status_t ucp_datatype_iter_sgl_init(ucp_context_h context,
                                        ucp_datatype_iter_t *dt_iter,
                                        const ucp_dt_local_sgl_t *local,
                                        const ucp_dt_remote_sgl_t *remote,
                                        size_t count, size_t length,
                                        const ucp_request_param_t *param);
```

but the gtest still calls it with only 6 arguments (`test/gtest/ucp/test_ucp_dt.cc:342-344`), so `&param` is bound to the `size_t length` slot — producing both `invalid conversion from 'ucp_request_param_t*' to 'size_t'` and `too few arguments to function`. The implementation at `src/ucp/dt/datatype_iter.c:286-299` assigns `dt_iter->length = length`, confirming the new parameter is the total SGL length in bytes. This is not aarch64-specific; it is a plain compile error that would fail any `--enable-gtest` build.

**Implicated commit:** `[REDACTED:Hex High Entropy String]` — "UCP/DT: Count the SGL iterator length and offset in bytes", Michal Shalev (touched `src/ucp/dt/datatype_iter.h` on 2026-09-14, hours before this build; PR head `2c9bd4935`)

```cpp

While doing so, audit the rest of `test_ucp_dt_sgl` for the same semantic change — since `dt_iter->length`/`offset` are now counted in bytes rather than elements, expectations around `m_dt_iter.length`, `offset` and `m_elem_index` in `next_frags()` may also need updating. 🤖 **CI Triage Agent** — `UCX PR (Tests roce on worker 1)` · commit `bbce163f`

**TL;DR:** The `roce on worker 1` gtest run failed on a single test, `rcx/test_ucp_fault_tolerance.probe_gated_recovery/6 (rc_x/AM)`, which is a white-box fault-tolerance test that samples internal recovery state (`recovery_arg->probe[lane].comp.func`) between progress loops — a race unrelated to PR #11947's SGL-PUT lane-splitting change; make the probe-arming check deterministic (mock `ep_check` / use a cumulative counter) rather than polling.

<details><summary>Full analysis</summary>

**Summary:** `make test` in the gtest step exited with error because 1 of 8727 tests failed: `rcx/test_ucp_fault_tolerance.probe_gated_recovery/6, where GetParam() = rc_x/AM` (log lines 19:18:07, `make: *** [Makefile:4713: test] Error 1`, `##[error]Bash exited with code '2'`).

**Root cause:** The only failing test is the probe-gated-recovery fault-tolerance test. Its own assertions are the only thing distinguishing it from the sibling tests `initiator_failure`/`target_failure`, which run the *same* pure-AM variant (`skip_unless_rc_probe_gate()` skips every non-AM variant) and passed — so AM failover, protocol coverage (`check_proto_coverage`) and error-callback accounting on the rc_x AM path are all fine in this build. What is unique to `probe_gated_recovery` is the white-box observation loop at `test/gtest/ucp/test_ucp_fault_tolerance.cc:922-943`: it polls `ep->ext->recovery_arg->probe[lane].comp.func != NULL` inside `wait_for_cond` and then asserts `EXPECT_TRUE(probe_armed) << "RC p2p lane recovery completed without arming an aux probe"`. Because `recovery_arg` is allocated, the aux `uct_ep_check` probe armed, completed and the arg freed entirely inside one `short_progress_loop()` iteration (and for `FAILURE_SIDE_TARGET` the local lane may even be recovered/cleared before any probe is armed), the sampling can legitimately miss the arming window and `failed_lanes` reaches 0 with `probe_armed == false` → spurious failure. This is a timing-dependent test assertion, not a product regression from the PR: PR #11947 ("UCP: Split an SGL put between the lanes by bytes") touches the multi-lane PUT/SGL split path, which this AM-only test does not exercise. Note: the exact assertion text is outside the retrievable log tail (only the gtest summary lines are in the last ~500 lines), so this is inferred from which test failed plus the test source.

**Implicated commit:** `db208ee4` — Evgeny Leksikov, "UCP/FT: probe-gated lane recovery via aux uct_ep_check (#11563)" (added the `probe_gated_recovery` test and the polled `probe_armed` check). PR #11947 (commit bbce163f) is not implicated.

**File:** `test/gtest/ucp/test_ucp_fault_tolerance.cc:922-943` (specifically the `EXPECT_TRUE(probe_armed)` at line 941)

**Suggested fix:**
1. Make the arming observation race-free instead of polling: use the same technique the neighbouring tests already use — `ucs::mock mock; mock_recovery_probe(sender().worker(), mock, recovery_probe_hold);` (lines 945-975) — so the probe is guaranteed observable (held in flight) before checking, then release it with `mock_invoke_completion(UCS_OK)` and wait for `ucp_ep_get_failed_lanes() == 0`.
2. Alternatively, have UCP expose a monotonic counter (e.g. a per-ep/worker `recovery_probes` counter incremented where the aux `uct_ep_check` is issued) and assert `counter > 0` after recovery, instead of sampling a transient `comp.func` pointer.
3. Short term for this PR: re-run the `roce on worker 1` job — the failure is unrelated to the SGL PUT split change; if it reproduces on the PR but not on master, re-check the multi-lane split code for effects on AM BW lane selection.
