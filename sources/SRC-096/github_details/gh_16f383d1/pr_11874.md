<details><summary>Full analysis</summary>

**Summary:** Azure Pipelines "Static checks" job failed at the `cstools reports` step — `csgrep`/`cslinker` found a `CLANG_WARNING: core.NullDereference` in `src/uct/ib/mlx5/rc/rc_mlx5_common.c:123`, which is treated as a hard error (`##[error]static checkers found errors`).

**Root cause:** In `uct_rc_mlx5_op_info_fill_put()`, the `wqe_size == header_size` branch only takes the success path when `(op != NULL) && (op->handler == uct_rc_ep_send_op_completion_handler)` (line 114). Therefore the `ucs_fatal()` at lines 122–123 is reachable with `op == NULL`, and it unconditionally dereferences `op->handler` while formatting the message — a genuine NULL dereference that clang correctly reports. Note the inconsistency: the second branch at line 126 explicitly accepts `op == NULL` as a valid case (`(op == NULL) || (op->handler == ...)`), so the zero-size branch's rejection of NULL `op` looks unintentional. The same warning is emitted twice (the file is compiled into two objects), so both instances stem from the single line. This is not an infra/flake issue — the build itself succeeded; only the static analyzer gate failed.

**Implicated commit:** 236a2b5f — "UCT/IB/MLX5: Add WQE parser for zcopy" (Zihao Zhao, 2026-09-01), the new code introduced by PR #11874

**File:** src/uct/ib/mlx5/rc/rc_mlx5_common.c:113-124 (warning at line 123)

**Suggested fix:** Align the zero-payload branch with the branch below it and/or make the diagnostic NULL-safe. Minimal change:

```c
    if (wqe_size == header_size) {
        if ((op == NULL) ||
            (op->handler == uct_rc_ep_send_op_completion_handler)) {
            uct_rc_mlx5_op_info_fill_put_zcopy(info, txwq, op, raddr, 0,
                                               callback_data);
            return UCS_OK;
        }

        ucs_fatal("unsupported put op %p handler %s", op,
                  ucs_debug_get_symbol_name((void*)op->handler));
    }
```

If a NULL `op` really must be fatal for a zero-size WQE, keep the `op != NULL` check but guard the message instead, e.g.:

```c
        ucs_fatal("unsupported put op %p handler %s", op,
                  (op == NULL) ? "<null>" :
                  ucs_debug_get_symbol_name((void*)op->handler));
```

Either change removes the `core.NullDereference` finding and unblocks the Static_check gate. Also note the earlier non-fatal `1 warning generated.` from the same line in the compile log (15:50:35) — same root cause.

**Related:** PR #11874 (this PR), sibling PRs #11836 and #11866 contain the same `ucs_fatal(... op->handler)` pattern and will likely hit the identical static-check error.

**File:** `src/uct/ib/mlx5/rc/rc_mlx5_common.c:122-123`

**Suggested fix:** Make the fatal message null-safe so it matches the reachable condition, e.g.:

```c

```

Alternatively, if `op == NULL` with `wqe_size == header_size` is genuinely legal (line 126 treats `op == NULL` as a valid zcopy case), restructure line 114 to mirror line 126 — `if ((op == NULL) || (op->handler == uct_rc_ep_send_op_completion_handler))` — which both removes the dereference and makes the zero-length-payload path consistent with the non-zero path.
