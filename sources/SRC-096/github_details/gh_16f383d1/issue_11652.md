# [Issue #11652] `cuda_copy` transport in `UCX_TLS` degrades LLM inference throughput

source: https://github.com/openucx/ucx/issues/11652
state: open | updated: 2026-07-15T03:06:26Z

## 正文

## Summary

Adding `cuda_copy` to the `UCX_TLS` allowlist causes a significant drop in LLM inference throughput (requests-per-second) in our serving runtime. When `cuda_copy` is excluded from `UCX_TLS`, QPS returns to baseline. We'd like the maintainers' input on where in the `cuda_copy` transport this overhead might originate and how to keep `cuda_copy` available as a fallback without the throughput penalty.

- Runtime that consumes UCX: an in-house LLM inference engine that uses NIXL on top of UCX for P2P KV Cache transfer. In our benchmark, only one process runs on one GPU and the code execution path does not touch real RDMA Read/Write: we just init `nixlAgent` with the `ucx` backend and register a DRAM region and a VRAM region, then the QPS of inference decreases noticeably. ## Setup

We run a benchmark that sends a fixed batch of inference requests to the runtime and measures end-to-end throughput. The only variable between the two configurations below is whether `cuda_copy` is allowed in `UCX_TLS`.

- **Baseline (no `cuda_copy`):**
  ```bash
  export UCX_TLS=ib,tcp,self,sm
  # benchmark invocation
  ```
- **With `cuda_copy`:**
  ```bash
  export UCX_TLS=ib,tcp,self,sm,cuda_copy  # or simply default (no restriction)
  # same benchmark invocation
  ```

All other `UCX_*` environment variables are identical between the two runs.

## Observations

| Run | `UCX_TLS` | QPS (req/s) |
|-----|-----------|-------------|
| Baseline | `ib,tcp,self,sm` (`cuda_copy` excluded) | 2952 |
| `cuda_copy` enabled | `ib,tcp,self,sm,cuda_copy` (`cuda_copy` allowed) | 2411 |


> In our runs the QPS drop is roughly **18%**. The regression is fully reproducible and only depends on whether `cuda_copy` is in the TLS list.

### What we confirmed

1. **The regression disappears when `cuda_copy` is excluded from `UCX_TLS`.** Toggling `UCX_TLS` alone reproduces or fixes the issue; no other change is needed.

2. **The penalty is paid even when `cuda_copy` carries no traffic.** In our runtime, `cuda_copy` is listed because we register a VRAM region for RDMA communication. However in our benchmark execution path, the real KV Cache transfer path is within one process by calling `cudaMemcpyAsync` and `cudaMemcpy2DAsync` API.
   - For KV Cache Offload: We firstly call `cudaMemcpy2DAsync` to gather the per-layer KV Cache from Paged Attention VRAM region to the VRAM middle buffer region (which is registered for RDMA communication), then we call `cudaMemcpyAsync` to transfer the KV Cache to lower DRAM tier (the whole DRAM tier region is registered for RDMA communication).
   - For KV Cache Onload: Similar to Offload but just reverse, we first call `cudaMemcpyAsync` to transfer the KV Cache from DRAM to VRAM middle buffer, then call `cudaMemcpy2DAsync` to scatter the all-layers KV Cache to the per-layer Paged Attention VRAM region.

## Questions for the maintainers

1. What global side effects does `cuda_copy` MD open (or component load) have on the CUDA context or driver state that could affect the performance of unrelated CUDA work in the same process? We see the regression even when `cuda_copy` is never selected for a transfer.

2. Is there a supported way to keep `cuda_copy` in `UCX_TLS` (as a fallback) without the throughput penalty, or is excluding it via `UCX_TLS=^cuda_copy` the intended workaround? We'd prefer to keep the fallback available.

3. Are there other transports (e.g. `cuda_ipc`) that apply similar process-global side effects on MD open that we should be aware of?

4. Is there any guidance on which transports are safe to keep in `UCX_TLS` for a latency-sensitive, high-concurrency CUDA application that relies on async copy/kernel overlap?

## Reproducer sketch

Since the benchmark is based on our in-house inference engine, it's hard to provide a full reproducer script, but the minimal reproduction steps are:

1. Build UCX with CUDA support.
2. Construct `nixlAgent` with the `ucx` backend in-process.
3. Start a CUDA application that relies on async `cudaMemcpyAsync` overlap for throughput (in our case, an LLM inference server with one thread dedicated to inference and another to request preprocessing, which drives data offloading and onloading).
4. Run the workload twice, toggling only `UCX_TLS`:
   - `UCX_TLS=ib,tcp,self,sm` (`cuda_copy` excluded) — baseline QPS.
   - `UCX_TLS` left default, or `cuda_copy` explicitly allowed — QPS drops by ~18% (from 2952 to 2411 req/s).

Happy to provide logs, `ucx_info` output, or any other information required.

Hi @yosefe  @brminich , thanks for your suggestions! We tried both, and while neither restored QPS on its own, they helped us narrow down the root cause. We now suspect the regression originates from the **UCM CUDA memory hook infrastructure** being installed process-globally as a side effect of `cuda_copy` MD declaring `detect_mem_types`. We'd appreciate the maintainers' confirmation on whether this is the intended behavior and whether the workaround we found is safe for production.

## Response to suggestion 1: commenting out `CU_CTX_SYNC_MEMOPS`

We tried commenting out the `UCT_CUDADRV_FUNC(cuda_cuCtxSetFlags_func(CU_CTX_SYNC_MEMOPS), ...)` call in `cuda_copy_md.c` (line 319), but the QPS regression persisted. This led us to rule out `CU_CTX_SYNC_MEMOPS` (and the downstream `CU_POINTER_ATTRIBUTE_SYNC_MEMOPS` per-pointer sync, which is gated behind the same code path) as the root cause.

## Response to suggestion 2: `UCX_SELECT_DISTANCE_MD=""`

We tried setting `UCX_SELECT_DISTANCE_MD=""` with `cuda_copy` still in `UCX_TLS`, but QPS did not recover. From our reading, this variable controls transport selection scoring (`ucp_worker_iface_set_sys_device_distance`, `ucp/core/ucp_worker.c:1225-1243`), not UCM hook installation. Setting it to `""` means no MD name matches, so all ifaces keep `ucs_topo_default_distance` — but the hooks are still installed. We'd appreciate confirmation if this understanding is correct.

## Our suspected root cause chain

With the help of Claude, we read through the UCX source code and traced the following chain from `ucp_init` to the hooks landing on every `cudaMalloc`/`cudaFree`. We also verified our hypothesis experimentally via the two patches/workarounds described below. However, we are not fully certain this is the intended behavior and would like to ask the maintainers to confirm.

1. **`cuda_copy` MD declares `detect_mem_types`** (`uct/cuda/cuda_copy/cuda_copy_md.c:131-132`):
   ```c
   md_attr->detect_mem_types = UCS_BIT(UCS_MEMORY_TYPE_CUDA) |
                               UCS_BIT(UCS_MEMORY_TYPE_CUDA_MANAGED);
   ```
   This is the **only** CUDA transport that sets `detect_mem_types`. `cuda_ipc` does not.

2. **UCP context collects it** (`ucp/core/ucp_context.c:1670-1674`): during `ucp_init`, any MD with `detect_mem_types` is added to `context->mem_type_detect_mds[]`, making `num_mem_type_detect_mds > 0`.

3. **First `ucp_mem_map` triggers memtype cache lazy creation**: when nixl calls `ucp_mem_map` without specifying `memory_type`, UCP calls `ucp_memory_detect` (`ucp_context.h:678-715`). Because `num_mem_type_detect_mds > 0`, it takes the slow path and calls `ucs_memtype_cache_lookup`, which lazily creates the global memtype cache instance.

4. **Memtype cache constructor registers UCM event handler** (`ucs/memory/memtype_cache.c:391-395`):
   ```c
   ucm_set_event_handler(UCM_EVENT_MEM_TYPE_ALLOC |
                         UCM_EVENT_MEM_TYPE_FREE  |
                         UCM_EVENT_FLAG_EXISTING_ALLOC,
                         1000, ucs_memtype_cache_event_callback, self);
   ```

5. **`ucm_set_event_handler` installs BISTRO + RELOC hooks on ALL CUDA alloc/free functions** (`ucm/cuda/cudamem.c`): `ucm_event_install` → `UCS_MODULE_FRAMEWORK_LOAD(ucm)` (dlopen `libucm_cuda.so`) → `ucm_cudamem_install` → `ucm_cuda_install_hooks` patches every `cudaMalloc`, `cudaFree`, `cudaMallocAsync`, `cudaFreeAsync`, `cudaMallocManaged`, `cuMemAlloc`, `cuMemFree`, `cuMemFreeAsync`, etc. via BISTRO (binary patch at function entry) and RELOC (GOT/PLT redirection).

## Per-call overhead we suspect is being paid after hooks are installed

Our reading of the code suggests that every hooked CUDA alloc/free in the entire process would go through:

```
ucm_event_enter()                        // pthread_rwlock_rdlock(&ucm_event_lock)
  → original CUDA alloc/free call
  → ucm_event_dispatch(MEM_TYPE_ALLOC|FREE)
      → ucs_memtype_cache_event_callback()
          → ucs_memtype_cache_update_internal()
              → ucs_spin_lock(&memtype_cache->lock)
              → ucs_pgtable_search_range()  // page table search
              → ucs_pgtable_remove()        // remove overlapping region
              → ucs_memtype_cache_insert()  // insert new region
              → ucs_spin_unlock(&memtype_cache->lock)
ucm_event_leave()                        // pthread_rwlock_unlock(&ucm_event_lock)
```

For `cudaFree`/`cudaFreeAsync`/`cudaFreeHost`, there is an **additional** `cuMemGetAddressRange()` driver call inside `ucm_cuda_dispatch_mem_free` (because the size parameter is 0 for these wrappers), extending the lock-hold duration.

In our inference engine, the KV Cache offload/onload path calls `cudaMemcpyAsync`/`cudaMemcpy2DAsync` frequently, and **the inference engine itself calls `cudaMallocAsync`/`cudaFreeAsync` for temporary buffers**. We suspect that every one of these calls pays the rwlock + spinlock + page table overhead, which would compress the async-copy/kernel overlap window and degrade QPS by ~18%. We'd appreciate confirmation on whether this overhead profile matches what the maintainers would expect.

## Verification: early return in `ucm_cudamem_install` appears to restore QPS

As a sanity check, we tried adding an early return at the top of `ucm_cudamem_install` in `ucx/src/ucm/cuda/cudamem.c`, which prevents the BISTRO/RELOC hooks from being installed while still allowing `cuda_copy` MD to open and `detect_mem_types` to be declared:

```c
static ucs_status_t ucm_cudamem_install(int events)
{
    static pthread_mutex_t install_mutex = PTHREAD_MUTEX_INITIALIZER;
    static int driver_api_hooks          = 0;
    static int runtime_api_hooks         = 0;
    ucs_status_t status                  = UCS_OK;

    printf("ucm_cudamem_install early return\n");

    return status;   // ← hooks never installed, QPS restored to baseline
    // ... rest of function unreachable ...
}
```

With this patch and `cuda_copy` still in `UCX_TLS`, **QPS returned to the baseline level** (matching the `UCX_TLS=ib,tcp,self,sm` run) in our tests. We take this as strong evidence that:

- The `detect_mem_types` declaration itself is harmless.
- The **UCM CUDA memory hooks** are the likely cause of the QPS regression.

We'd appreciate the maintainers' perspective on whether this conclusion is correct.

## Verification: `UCX_MEMTYPE_CACHE=no` also appears to restore QPS

As a second data point, setting `UCX_MEMTYPE_CACHE=no` with `cuda_copy` still in `UCX_TLS` also restored QPS to baseline in our tests:

```bash
export UCX_TLS=ib,tcp,self,sm,cuda_copy
export UCX_MEMTYPE_CACHE=no
# benchmark invocation — QPS matches baseline
```

`UCX_MEMTYPE_CACHE=no` causes `ucs_memtype_cache_get_global()` (`ucs/memory/memtype_cache.c:59`) to return NULL without creating the cache, so the `ucm_set_event_handler` call inside the cache constructor (`memtype_cache.c:391-395`) is never reached and the UCM hooks are never installed. The trade-off is that `num_mem_type_detect_mds` is still > 0, so each `ucp_mem_map` without an explicit memory type falls through to `ucp_memory_detect_slowpath`, which calls `uct_md_mem_query` on every `mem_type_detect_md` (`ucp_context.c:2589-2591`). This adds a per-registration CUDA driver pointer-attribute query but avoids the per-alloc/free hook overhead — a favorable trade-off for our workload.

## Questions for the maintainers

1. Could the maintainers confirm whether the UCM CUDA memory hooks being installed process-globally as a side effect of `cuda_copy` MD declaring `detect_mem_types` is the intended behavior? If so, is there a recommended way to keep `cuda_copy` in `UCX_TLS` (as a fallback) without triggering the hooks — or is `UCX_MEMTYPE_CACHE=no` the intended workaround?

2. Is `UCX_MEMTYPE_CACHE=no` safe for production use when `cuda_copy` is kept in `UCX_TLS`? Are there any correctness concerns with relying on `ucp_memory_detect_slowpath` (per-registration `uct_md_mem_query`) instead of the memtype cache?

3. Are there other transports (e.g. `cuda_ipc`) that apply similar process-global side effects on MD open that we should be aware of?
