### svc-ucx · 2026-09-21

🤖 **CI Triage Agent** — `UCX PR (Build build_icc_pgi centos7_x86_64)` · commit `1af05f22`

**TL;DR:** The ICC/ICX (clang-based) build fails with `-Werror,-Wtypedef-redefinition` because commit 1af05f22 added a duplicate `typedef struct ucp_gpu_nic_assignment ucp_gpu_nic_assignment_t;` in `ucp_context.h` while the same typedef already exists in `ucp_gpu_nic_assignment.h`; drop the duplicate typedef (forward-declare the bare `struct` instead, or include the header).

<details><summary>Full analysis</summary>

**Summary:** `build_icc_pgi centos7_x86_64` failed compiling `src/ucp/core/ucp_context.c` with icx: `error: redefinition of typedef 'ucp_gpu_nic_assignment_t' is a C11 feature [-Werror,-Wtypedef-redefinition]`.

**Root cause:** `src/ucp/core/ucp_context.c` includes `ucp_gpu_nic_assignment.h` (which defines `typedef struct ucp_gpu_nic_assignment {...} ucp_gpu_nic_assignment_t;` at line 26–35) and also `ucp_context.h`, which as of the tip commit repeats the same typedef as a "forward declaration" at line 399. Repeating a typedef is only legal in C11; the ICX build compiles in a pre-C11 mode with `-Wall -Werror` and clang's `-Wtypedef-redefinition` is not suppressed (unlike GCC, which accepts it silently in the gnu dialects — hence other CI jobs pass). The duplicate typedef is redundant anyway since `ucp_context` only stores a pointer (`ucp_gpu_nic_assignment_t *gpu_nic_assignment;`, ucp_context.h:458).

**Implicated commit:** [REDACTED:Hex High Entropy String] — "UCP/CORE: ucp_gpu_nic_assignment forward declaration", Guy Ealey Morag

**File:** src/ucp/core/ucp_context.h:398-399 (conflicting definition at src/ucp/core/ucp_gpu_nic_assignment.h:26-35)

**Suggested fix:** Replace the duplicate typedef with a plain struct forward declaration and use the struct tag for the member, e.g. in `ucp_context.h`:
```c
/* Forward declaration */
struct ucp_gpu_nic_assignment;
...
    /* GPU-to-NIC assignment, set to NULL when not in use */
    struct ucp_gpu_nic_assignment *gpu_nic_assignment;
```
Alternatively, `#include "ucp_gpu_nic_assignment.h"` from `ucp_context.h` and remove the local typedef entirely (that header only pulls in `ucs/datastruct/static_bitmap.h` and `ucs/sys/topo/base/topo_groups.h`, so no include cycle). Either way, no typedef must be declared twice, since the ICX/ICC job compiles pre-C11 with `-Werror`.

**Related:** PR #11976 (this PR); earlier feature PR #11868 "UCP/CORE: Implement GPU to NIC assignment logic" introduced `ucp_gpu_nic_assignment.h`.

</details>

### svc-ucx · 2026-09-22

🤖 **CI Triage Agent** — `UCX PR (Tests gpu on worker 3)` · commit `2bfab52a`

**TL;DR:** The gpu-worker-3 gtest shard failed on a single test, `rc_gda/test_ucp_device.get_remote_mem_list_length/1` (cuda), which aborts at `ASSERT_UCS_OK` when `ucp_device_remote_mem_list_create()` returns a non‑retryable error for a not-yet-fully-wired endpoint; this is a race in the device mem-list lane lookup, not a regression from PR #11976 (which only builds/logs the GPU‑NIC assignment object).

<details><summary>Full analysis</summary>

**Summary:** `make test` in the "gpu on worker 3" job exited with code 2 — 1 of 10286 gtests failed: `rc_gda/test_ucp_device.get_remote_mem_list_length/1, where GetParam() = rc,rc_gda,cuda_copy,rocm_copy/cuda`.

**Root cause:** The retained log tail only contains the gtest summary (the per-test error line is earlier in the truncated log), but the failure is bounded to `test_ucp_device::mem_list` construction / length check. Decisive evidence from the same run: the sibling test `get_local_mem_list_length/1` — which builds an *identical* 8-element, 1 KB `mem_list` on the same transport/variant — passed, as did `test_ucp_device_xfer.put`/`counter` on rc_gda. So the failing path is non-deterministic, i.e. a wireup race in `ucp_device_remote_mem_list_create()`:
- `ucp_device_remote_mem_list_params_check()` only treats a missing `UCP_EP_FLAG_REMOTE_CONNECTED` as the retryable `UCS_ERR_NOT_CONNECTED` (src/ucp/core/ucp_device.c:766-773), and the test loops only on that status (test/gtest/ucp/test_ucp_device.cc:210-214).
- Once the flag is set but lanes are not yet fully configured, `ucp_device_ep_check_lanes()` / `ucp_device_ep_find_lane()` fail and `ucp_device_remote_mem_list_create_handle()` returns the *hard* `UCS_ERR_INVALID_PARAM` ("lane not found for element %zd", src/ucp/core/ucp_device.c:690-703) or `UCS_ERR_NO_DEVICE` from `ucp_device_remote_mem_list_element_pack()` (line 545-548). The test's `ASSERT_UCS_OK` (test_ucp_device.cc:219) expands to `UCS_TEST_ABORT` → fatal gtest failure, exactly matching a lone FAILED entry with no crash/abort of the process.

PR #11976 (`UCS/TOPO: Initialize GPU-NIC assignment object in UCP context`) only constructs and debug-logs `ucp_gpu_nic_assignment_t`; nothing in `src/ucp/core/ucp_gpu_nic_assignment.c` is consumed by wireup/device-lane selection yet, so it cannot deterministically change rc_gda lane sets. Treat this as a pre-existing flaky device-lane race, not a PR regression.

**Implicated commit:** Not the PR head (2bfab52a, Guy Ealey Morag). The fragile logic comes from 5fb8bfc4 "UCP/DEVICE: Require connected EP for remote mem list (#11704)" (amastbaum) and [REDACTED:Hex High Entropy String] "UCP/DEVICE: Check no-lkey lanes before lkey (#11807)" (Artemy Kovalyov).

**File:** src/ucp/core/ucp_device.c:690-703 (hard `UCS_ERR_INVALID_PARAM` on missing lane) and src/ucp/core/ucp_device.c:766-773; test side: test/gtest/ucp/test_ucp_device.cc:210-220

**Suggested fix:**
1. Make the lane-lookup failure retryable: in `ucp_device_remote_mem_list_create_handle()`, when no `tl_type` bitmap matches the ep's lanes (or `ucp_device_ep_find_lane()` returns `UCP_NULL_LANE`) while the ep is still in wireup (`ucp_ep_has_wireup_lanes`/`UCP_EP_FLAG_LOCAL_CONNECTED` not complete), return `UCS_ERR_NOT_CONNECTED` and demote the `ucs_error` to `ucs_diag`, so the existing test/application retry-with-progress loop handles it.
2. Harden the test: in `test_ucp_device::mem_list`, retry on `UCS_ERR_NOT_CONNECTED` **and** `UCS_ERR_INVALID_PARAM`/`UCS_ERR_NO_DEVICE` under a bounded `wait_for_cond`, or call `flush_ep(sender())` before `ucp_device_remote_mem_list_create()` so lanes are guaranteed configured.
3. Re-run the gpu-worker-3 shard to confirm the failure does not reproduce; if it does reproduce consistently on this PR, re-check `ucp_device_get_tl_bitmap()` (ctl_device vs `local_sys_dev` filtering, src/ucp/core/ucp_device.c:203-221) against the newly built GPU-NIC assignment.

**Related:** PR #11976 (this PR); PR #11704, PR #11807 (device remote mem-list lane logic); PR #11968 "UCT/DEVICE: fix gda qp state and uar" (recent rc_gda device fixes)

</details>
