# [PR #5443] [CK] [Bugfix][Perf] fused_moe: tune the non-temporal load hint per tuned row

state: closed | updated: 2026-09-24T09:39:06Z

## 正文

## What's wrong

`get_2stage_cfgs()` initialises the non-temporal load hint to `False` and assigns it only
inside the heuristic branch:

```python
use_non_temporal_load = False
if cfg is None or bypass_tuned_config:
    use_non_temporal_load = use_nt(token, topk, expert)   # heuristic branch only
else:
    ...                                                   # tuned branch: never assigned
```

A shape loses non-temporal weight loads the moment it gains a tuned CSV row, and
`AITER_USE_NT` is dead there as well, because the override lives inside `use_nt()`.

An earlier revision of this PR simply derived the flag on the tuned path too. Review pointed
out why that is not sound, and measurements agree: the tuner never passes `non_temporal_load`
(`gemm_moe_tune.py` -> `ck_moe_stage{1,2}_fwd_out`), so **every** candidate in every shipped
row was ranked with the hint off. Turning it on at runtime runs the selected kernel outside
the conditions it was selected in, and the recorded `us1`/`us2` stop describing runtime. On
gfx942 that shows up directly: the shipped `ds_v3` row for `7168x2048 e33 topk9` at token 128
(`block_m=32`) is **6.6 % slower** with the hint on, while the same shape at tokens 16 and 64
is 5.0 % / 3.5 % faster. One shape family, no constant right answer.

## Fix

Make the hint part of what gets tuned instead of something derived next to the tuned row. The
tuner sweeps both values for the quant types whose kernels read it, ranks
`(kernel, block_m, nt)` jointly by `us1 + us2`, and records the winner in a new `nt` column;
the runtime reads that column.

```diff
     else:
         block_m = cfg["block_m"]
+        # rows tuned before the nt column keep the hint off
+        nt_override = int(os.environ.get("AITER_USE_NT", "-1"))
+        if nt_override != -1:
+            use_non_temporal_load = bool(nt_override)
+        elif "nt" in cfg:
+            use_non_temporal_load = bool(int(cfg["nt"]))
```

`use_nt()` and the heuristic branch are untouched, so nothing changes for shapes without a
tuned row. Rows without the column keep `nt=False`, which is today's behaviour, so no shipped
config changes until it is retuned. `AITER_USE_NT` now overrides both paths, as it was
documented to. On the tuner side `nt` is threaded exactly like the existing `flat` / `xbf16`
columns: it rides in the candidate tag, becomes a column in the candidate table, joins the
dedup key and the stage1 x stage2 merge key (so both stages of a row agree on it), and is
written out. The sweep is gated to `per_1x128`, so every other quant type keeps its candidate
count.

## Results, MI325X (gfx942, 304 CU)

DSv3 EP shape `7168x2048 e33 topk9`, per_1x128 fp8 blockscale, preshuffled weights.

**Tuner level** — same box, same harness, the extra dimension is the only difference:

| token | without the nt sweep    | with the nt sweep               | gain   |
| ----- | ----------------------- | ------------------------------- | ------ |
| 16    | `block_m=16`, 360.34 us | `block_m=16`, `nt=1`, 329.59 us | +8.5 % |
| 64    | `block_m=32`, 375.48 us | `block_m=32`, `nt=1`, 358.88 us | +4.4 % |
| 128   | `block_m=64`, 404.58 us | `block_m=64`, `nt=1`, 395.84 us | +2.2 % |

**Runtime level** — whole `fused_moe` op, CUDA-graph replay, 200 iters after 40 warmup, 8
rotated weight sets, 3 interleaved rounds per config, median:

| token | shipped rows | retuned, no nt sweep | retuned, nt swept | vs shipped |
| ----- | ------------ | -------------------- | ----------------- | ---------- |
| 16    | 383.2 us     | 374.5 us             | 329.6 us          | +14.0 %    |
| 64    | 398.0 us     | 411.5 us             | 365.0 us          | +8.3 %     |
| 128   | 455.4 us     | 431.2 us             | 417.2 us          | +8.4 %     |

Retuning with the hint in the search is worth +3.3 % to +12.0 % over retuning without it on
the same box.

**Why this cannot be a heuristic.** The `block_m` the tuner picks and the best value of the
hint are coupled: what the hint discards is weight reuse between M-tiles of the same expert,
so it wins while an expert stays inside one tile and loses once it spans two. At token 128 on
this shape, stage2 measured alone with `rocprofv3` is 161.0 -> 191.8 us with the hint at
`block_m=32`, but 153.1 -> 135.7 us at `block_m=64`; `rocprofv3 --pmc TCC_HIT_sum TCC_MISS_sum`
attributes the whole difference to cache hit rate (42.8 % -> 28.5 %, 722 MB -> 920 MB below L2
against 2 x 484 MB of logical B reads, both arms sustaining ~4 TB/s). A predicate over token
count cannot see `block_m`, and under imbalanced routing it cannot see the tail experts that
cross into a second tile before the mean does either. Tuning it removes the guesswork.

## Results, MI355X (gfx950, 256 CU)

Second architecture, independent box. 26 shapes from three families (`4096x384 e128 topk8`,
`7168x512 e257 topk9`, `3072x1536 e256 topk8`), same machine, same harness, same
single-process settings, one card, tuned **three times per arm** at the PR's parent `c3caa55`
and at the head `c26f391`. 23 of the 26 resolve a winner on every run of both arms (the other
three are under *Caveats*). Times are the tuner's own per-candidate measurement for the
winning row; gain is median-of-three, spread is max-min within an arm.

The result separates by winning path. The 16 asm 1-stage shapes do not read the flag and do
not move: all keep `nt=0`, median gain +0.07 % over a range of -0.7 % .. +0.8 % against
per-arm spreads up to 1.4 %. The 7 CK 2-stage shapes are one family, `4096x384 e128 topk8`,
`doweight_stage1=1`, all at `block_m=16`:

| token | parent    | PR        | gain   | per-arm spread | `nt`                |
| ----- | --------- | --------- | ------ | -------------- | ------------------- |
| 1     | 38.62 us  | 38.19 us  | +1.1 % | 7.1 % / 4.6 %  | `0`/`1`, unstable   |
| 2     | 42.65 us  | 41.38 us  | +3.0 % | 6.2 % / 1.5 %  | `1`                 |
| 4     | 50.69 us  | 47.30 us  | +6.7 % | 6.2 % / 3.6 %  | `1`                 |
| 8     | 61.86 us  | 57.14 us  | +7.6 % | 1.3 % / 2.7 %  | `1`                 |
| 16    | 83.12 us  | 76.54 us  | +7.9 % | 1.4 % / 1.7 %  | `1`                 |
| 32    | 113.93 us | 105.10 us | +7.8 % | 0.3 % / 0.4 %  | `1`                 |
| 64    | 122.32 us | 113.05 us | +7.6 % | 0.2 % / 0.4 %  | `1`                 |

From token 8 up, the gain is several times either arm's spread and holds within half a point
across four shapes. At tokens 1-4 the shape runs in tens of microseconds, the arms overlap,
and token 1 does not even settle on a value across repeats — the flag genuinely does not
matter there, so nothing is claimed. Both arms pick the same kernel pair at tokens 1-16; at
tokens 32 and 64 the PR arm's winner is the `128x16x128x128` variant rather than
`256x16x128x256`, which is the ranking doing its job once `nt` is in the search space. An
isolated single-shape rerun where both arms converged on the identical kernel and `block_m`
isolates the flag on its own: 121.76 us -> 114.31 us, +6.1 % (stage1 +7.0 %, stage2 +4.5 %).


## Cost and compatibility

* CK candidates double for `per_1x128` only: 10 -> 20 per shape here, one shape 19 s -> 38 s,
  roughly 10 min for a full model file. Verified that a `per_Token` tune is unchanged.
* Rows without the column behave exactly as today. The 46 shipped blockscale 2-stage rows with
  `use_nt() == True` (38 at `cu_num` 256, 8 at `cu_num` 304) keep the hint off until someone
  retunes them; retuning shipped configs is out of scope here.
* No C++ change: `ck_moe_stage{1,2}_fwd` already take the flag and `gen_instances.py` already
  compiles both NT instantiations.

## Verification

* Runtime decision table, all five cases checked against `get_2stage_cfgs` on **both** gfx942
  and gfx950: legacy CSV (no column) -> off; `nt=0` -> off; `nt=1` -> on; legacy +
  `AITER_USE_NT=1` -> on; `nt=1` + `AITER_USE_NT=0` -> off. At the parent commit all five
  return off, which is the bug.
* Shipped-config regression, exhaustive: all **179** `cu_num=256` blockscale 2-stage rows across
  the 7 shipped CSVs (`ds_v3`, `glm5`, `minimax-m2_5`, `qwen3_235b`, `qwen3_5_397b`, and the
  untuned files) resolved through `get_2stage_cfgs` on both arms and compared field by field —
  `block_m`, `ksplit`, both kernel names, `nt_stage1`, `nt_stage2`. **Zero differences.** 119 of
  those rows are ones where `use_nt()` would return `True`; they stay off on both arms,
  confirming the heuristic was already inert on the tuned path and that this change does not
  switch it on.
* Tuner smoke test: the dispatch list shows each CK kernel twice, once per value; the candidate
  table and the tuned CSV carry `nt`; `per_Token` keeps its candidate count.
* Hand-written rows confirm the column drives the kernel: the same shipped config with `nt=1`
  reproduces +5.0 % / +3.5 % / -6.6 % at tokens 16 / 64 / 128.
* Numerics: the flag only selects `AmdBufferCoherenceEnum`, no arithmetic changes. Measured on
  gfx950, per-candidate reference error is identical between the two arms and between `nt=0` and
  `nt=1` (stage1 0.1 % in every group; stage2 within 0.1 pp).
* `op_tests/test_moe_blockscale.py` exits 0 with the same six checks; instrumenting
  `get_2stage_cfgs` shows it never enters the tuned branch (asm path only), so it does not cover
  this change.
* `ruff` clean on both files; no new findings (3 pre-existing in the tuner, 34 pre-existing E501
  in `fused_moe.py`, unchanged).

## Caveats

* The rankings above were produced with the catastrophic-mismatch check relaxed locally, because
  the tuner's reference comparison rejects blockscale stage1 candidates — asm and CK alike — on
  both of my boxes, while `per_Token` is unaffected. That blocks blockscale tuning independently
  of this change: the two files involved are untouched by this PR, and the parent commit fails
  identically on the same shapes. On gfx950 it is what leaves the three shapes above unresolved.
  The measurements are unaffected, since both arms are gated identically and the per-candidate
  errors match between them.
* Per-stage tuning of the hint is deliberately not attempted: the runtime passes one flag to both
  stages, so the merge forces stage1 and stage2 of a row to agree.

The block_m guard avoids the known multi-M-tile regression, but it does not make the tuned configuration consistent with runtime. Every CK candidate in the tuning CSV was ranked with use_non_temporal_load=False, while this line runs the selected candidate with nt=True.
