## 正文

## Summary

Add 16 gfx950 tuning rows for the DeepSeek V4.1 Flash TP4 backbone and draft MoE shapes. These shapes currently have no exact entries in the shipped tuning tables and use heuristic FlyDSL configurations.

## Configuration

- H5120; TP-local logical intermediate 576, padded to 640.
- Backbone: 384 experts, top6; draft: 128 experts, top3; expert parallelism disabled.
- Token buckets 8/16/32/64/128/256/512/1024 for each geometry. Actual tested decode rows were backbone M6/12/24/48/96/192/384/768 and draft M5/10/20/40/80/160/320/640.
- BF16 output, FP8 activations, MXFP4 weights, per-1x32 scaling, interleaved gate/up, SiLU and no stage-one routing-weight multiplication.
- Existing unfused stage-one N128 kernels with M16/M32 tiles; stage-two N128/N256. Exact names and `ksplit=-1` are in the CSV.

The model-specific table contains only the 16 new keys, with explicit `gfx950`. Existing rows are unchanged. Kernel timing/error columns are blank: the measurements below include the complete local shared/routed MoE and TP collective, so they are not valid stage-one/stage-two kernel timings.

## Performance on the measured runtime

MI355X, TP4, Torch 2.12.0+rocm10.0.0, HIP 7.15.26333, Triton 3.8.0, AITER 0.1.21.post1 with the merged sorter fix from #5295. `AITER_BF16_FP8_MOE_BOUND=0`, fusion and routed-first scheduling disabled. This explicitly measures the A8W4 path; the CSV does not change activation-dtype selection policy.

Seeded synthetic weights/inputs, warm repeated routes, native shared-first MoE including gating, quantization, shared expert, routed expert and BF16 TP4 RCCL. Each of 31 alternating paired measurements takes the maximum rank latency over 16 graph replays. The other four GPUs were idle during confirmation.

## Validation and limits

- The original native CSV lookup resolved all 16 expected kernel pairs, without metadata overrides. Each geometry also passed M31/32/33/255/256/257 boundary checks.
- Eager and changed-input graph checks covered original, changed-input, concentrated-routing and restored-input cases. Fixed per-rank `atol=rtol=.02`, explicit FP64 local error budgets, propagated FP32 TP-sum budgets, input preservation and finite timed outputs passed. Strict FP32/BF16 aggregate parity diagnostics include mismatches and are retained separately; this is not a claim of bitwise or independent full-model accuracy.
- The benchmark retained one capture stream and diagnostic graphs/output buffers until synchronized cleanup after reproducing a graph-lifetime fault. No kernel arithmetic or scheduling change is included here.
- N64 stage-one variants were excluded because the investigated padded path left part of the intermediate unwritten.
- Full-model accuracy, every shape inside each lookup bucket, and GPU execution/serving throughput on this branch's current upstream runtime have **not** been validated. A short serving comparison on the measured private runtime is reported below.

Measured source identities include `moe_kernels.py` SHA256 `c6898ef73fa21fd519593592c511b29ae41443e3e753ce6165bc866271c2bd73` and `mixed_moe_gemm_2stage_common.py` SHA256 `bba3e08a6ac16c2106a8bde9b06a98aea6fb0c7764117b2630a3a091265e1853`. Upstream base `b0ced008d89f3fe8ad9fa9388d78b615fd53cb0b` has newer FlyDSL/LDS and stage-two addressing code. All 10 selected kernel names still register with identical parameters, but that CPU check does not establish equivalent performance or correctness on the newer implementation.

## Related work

Open PR #5562 targets DSV4.1 **EP4** with H5120/I2304, 96 local experts and top5. This table targets **TP4** with H5120/I640, E384/top6 and E128/top3, so its lookup keys are distinct. Open-PR searches for DSV4.1, `640 fmoe`, and `fmoe CSV` found no proposal for these exact keys. #5315 addresses explicit architecture fields across existing tables; this new table already supplies `gfx950`.
