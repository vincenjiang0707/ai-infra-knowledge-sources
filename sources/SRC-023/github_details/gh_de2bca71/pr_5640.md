## Motivation

<!-- Explain the purpose of this PR and the goals it aims to achieve. -->
This PR adds  Triton Conv3D implementation with optimized
routing for common video-model and VAE workloads.

The public API supports FP16 and BF16 inputs, NCDHW and channels-last-3D
execution, optional bias, asymmetric stride/padding/dilation, and activations.
## Technical Details

The Conv3D router selects between the following kernel families:

- Specialized 1x1x1 Conv3D
- NCDHWc 3x3x3 Conv3D with fused activation packing
- Native NDHWC 3x3x3 Conv3D
- General im2col-free Conv3D
- Winograd F(4x4, 3x3) over the H/W axes
- Winograd with an NCDHWc input path

The implementation also adds:

- Conv3D weight-prepack and Winograd-filter caches
- Layout-preserving NCDHW and channels-last-3D behavior
- Shape-driven production routing
- Complete launch keys containing all three spatial axes
- Tuned gfx1201 launch configurations
- Configuration-table coverage for gfx1200, gfx942, and gfx950, initially
  seeded from the gfx1201 values
- Public export through `aiter.ops.triton`
- Real-model-derived benchmark shape coverage for:
  - Wan2.2 A14B VAE
  - Wan2.2 TI2V-5B VAE
  - LTX-Video 0.9.5 VAE
  - InternVideo2 and Qwen-family video patch embeddings

The benchmark reports per-layer correctness, selected Triton kernels,
kernel-only and repack-inclusive performance, aggregate throughput, and
call-count-weighted encoder/decoder totals. It exits nonzero when a requested
shape errors or fails correctness.

## Test Plan

The Conv3D test suite covers:

- FP16 and BF16
- NCDHW and channels-last-3D layouts
- Every direct Conv3D route
- Optional bias
- `none`, `relu`, `relu6`, and `gelu` activations
- Asymmetric dimensions, stride, padding, and dilation
- Batched, odd-channel, and tail-masking shapes
- Winograd transform and output correctness
- Output dtype preservation
- Weight-cache reuse, invalidation, and LRU eviction
- Actual production-router dispatch
- Benchmark database, reporting, and CLI behavior
- Invalid argument and unsupported configuration handling

* Each new 3-D cache uses the inherited 256-entry count while retaining both the source weight and packed item. A single 1024×1024×3×3×3 FP16 Winograd entry is roughly 270 MiB, so 256 entries can retain tens of GiB and cause avoidable OOMs in long-running model processes; use a byte-bounded or substantially smaller 3-D cache policy.
