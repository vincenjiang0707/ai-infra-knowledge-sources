## 正文

## Motivation

Add gfx1151 (RDNA3 / Strix Halo, Radeon 8060S) tuned Triton `GEMM-A8W8_BLOCKSCALE` config files for the DeepSeek-V4-Flash FP8 block-scale GEMM shapes.

On gfx1151 these blockscale GEMMs previously had no per-shape tuned config, so AITER fell back to the default kernel configuration and vLLM logged `Using default W8A8 Block FP8 kernel config` for the uncovered shapes. This PR records measured tuned configs for the DeepSeek-V4 W8A8 block-scale shapes seen in the 1M TP=2 serving run so those shapes use tuned parameters instead of the default fallback.

This is part of the DeepSeek-V4 gfx1151/RDNA3 AITER enablement stack:

- Dependency: <https://github.com/vllm-project/vllm/pull/52970> (officially supporting AITER Triton kernels + dsv4 on RDNA3). That PR routes the RDNA3 FP8 block-scale linear path through AITER's Triton kernels, which is what consumes these gfx1151 config files.

## Technical Details

This PR only adds tuning/config data. It does not add or modify any kernel.

All files land under:

```text
aiter/ops/triton/configs/gfx1151/triton/gemm/gemm_a8w8_blockscale/
```

Added configs:

- `DEFAULT.json` (gfx1151 blockscale default entries)
- `GEMM-A8W8_BLOCKSCALE-N=512-K=4096.json`
- `GEMM-A8W8_BLOCKSCALE-N=1536-K=4096.json`
- `GEMM-A8W8_BLOCKSCALE-N=2048-K=4096.json`
- `GEMM-A8W8_BLOCKSCALE-N=4096-K=256.json`
- `GEMM-A8W8_BLOCKSCALE-N=4096-K=1024.json`
- `GEMM-A8W8_BLOCKSCALE-N=4096-K=4096.json`
- `GEMM-A8W8_BLOCKSCALE-N=4096-K=12288.json`
- `GEMM-A8W8_BLOCKSCALE-N=8192-K=1024.json`
- `GEMM-A8W8_BLOCKSCALE-N=16384-K=1024.json`

Each per-shape file is keyed by `M_LEQ_*` buckets and stores the standard Triton GEMM tuning parameters (`BLOCK_SIZE_M/N/K`, `GROUP_SIZE_M`, `num_warps`, `num_stages`, `waves_per_eu`, `matrix_instr_nonkdim`, `cache_modifier`, `NUM_KSPLIT`, `kpack`) for the FP8 `[128, 128]` block-scale GEMM.

The `(N, K)` shapes correspond to the DeepSeek-V4-Flash W8A8 block-scale GEMMs observed on the gfx1151 1M TP=2 route.

## Test Plan

- Load the model on gfx1151 with the AITER Triton FP8 block-scale path enabled (via the vLLM dependency above) and confirm each added shape resolves to its tuned config instead of the default fallback.
- Confirm the `Using default W8A8 Block FP8 kernel config` warnings for these `(N, K)` shapes no longer appear during startup/serving.

## Test Result

- With these configs present, the previously uncovered DeepSeek-V4 W8A8 block-scale shapes are served with tuned parameters and no longer fall back to the default kernel config.

### System-level E2E result

These configs deliver a clear end-to-end win on the DeepSeek-V4-Flash gfx1151 1M TP=2 route, exercised through the RDNA3 AITER Triton path enabled by the vLLM dependency (<https://github.com/vllm-project/vllm/pull/52970>). Comparing an untuned image against the tuned image on the same prompt, the tuned build cuts end-to-end latency by roughly 1.4x to 1.6x and nearly doubles output token throughput.

Prompt: `Tell me a random fun fact about the Roman Empire` (seed `0`, max tokens `256`).

| Metric | Untuned | Tuned | Ratio |
|---|---:|---:|---:|
| Prewarm E2E (s) | `60.91` | `38.44` | ~1.58x faster |
| Warmed follow-up E2E (s) | `52.80` | `36.94` | ~1.43x faster |
| Warmed follow-up output tok/s (E2E) | `3.49` | `6.93` | ~1.99x faster |

### 1. `kpack` consistency

### 2. What was the default fallback + will `kpack` error?

> What was the default that it was falling back to? If even DEFAULT.json, this kernel would probably error out.

From what I understand, before this PR, gfx1151 had **no** blockscale config files at all. So the fallback was handled on the **vLLM side**, which logged `Using default W8A8 Block FP8 kernel config` and supplied a hardcoded generic configuration.

Regarding `kpack` issue, actually it won't error. `kpack` is a Triton AMD **backend compiler option** (`HIPOptions` field), not a kernel meta-parameter. Triton's JIT binder extracts it from kwargs before the kernel-parameter check, same as `num_warps` and `waves_per_eu`:

```python
# triton/third_party/amd/backend/compiler.py
@dataclass
class HIPOptions:
    ...
    matrix_instr_nonkdim: int = 0
    kpack: int = 1
    ...

def parse_options(self, opts):
    args.update({k: opts[k] for k in HIPOptions.__dataclass_fields__.keys()
                 if k in opts and opts[k] is not None})
    return HIPOptions(**args)
```

```python
# triton/runtime/jit.py _pack_args():
options = backend.parse_options(kwargs)   # pulls kpack, num_warps, waves_per_eu, etc.
for k in kwargs:
    if k not in options.__dict__ and k not in sigkeys:
        raise KeyError("Keyword argument %s was specified but unrecognised" % k)
```

Since `kpack` is in `HIPOptions.__dataclass_fields__`, it passes the check. This is consistent with every existing blockscale config on main -- `gfx942-GEMM-A8W8_BLOCKSCALE.json`, `gfx1201-GEMM-A8W8_BLOCKSCALE.json` (#3228), and all gfx1201 per-shape files all include `"kpack": 2`.
