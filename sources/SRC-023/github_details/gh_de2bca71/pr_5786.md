# [PR #5786] [JIT] [Build] Make CK fmha kernel generation follow GPU_ARCHS

source: https://github.com/ROCm/aiter/pull/5786
state: open | updated: 2026-09-24T11:50:50Z
labels: JIT, Build

## 正文

CK's FMHA codegen was never told which GPU architecture to build for — it either fell back to `gfx9,gfx950`, or was handed a device name it does not recognize, leaving gfx11/gfx12 with no usable FA kernels. This PR derives CK's `--targets` from `GPU_ARCHS` and passes it at every `01_fmha/generate.py` call site.

## Why

Two independent bugs, both silent until dispatch:

- **`mha_recipes._ck_targets_flag()` passed a raw device name** (`gfx1100`) as `--targets`. CK's factory keys are coarser than device names — `gfx11` covers `gfx1100`–`gfx1103` — so it matched nothing, produced an empty kernel set, and `mha_fwd` failed with `invalid argument for fmha_fwd`. **FA did not work on gfx11/gfx12 at all.**
- **Every other call site omitted `--targets`**, so CK fell back to its built-in `gfx9,gfx950` and `GPU_ARCHS` was ignored.

## What changed

203 lines production, 451 tests. Start at `build_targets.py`, then the gates in `mha.py`:

| File | |
|---|---|
| `aiter/jit/utils/build_targets.py` | +69 — the mapping table (§1) |
| `aiter/ops/mha.py` | +100/−23 — call sites and arch gates (§3, the subtle one) |
| `optCompilerConfig.json` · `mha_recipes.py` · `cpp/mha/compile.py` · `core.py` | remaining `--targets` sites (§2) |
| `op_tests/test_ck_fmha_targets*.py` | +339 — no-GPU tests for the table and every gate |

**§1 — Map `GPU_ARCHS` to a CK factory key.**

```
GPU_ARCHS         CK --targets
─────────────────────────────
gfx950       -->  gfx950
gfx125x      -->  gfx125
gfx120x      -->  gfx12
gfx115x      -->  gfx115
gfx11xx      -->  gfx11
other gfx9*  -->  gfx9
unmapped     -->  gfx9,gfx950   (CK's own default — unchanged)
```

`batch_prefill` needs a gfx9-only variant of this, because CK drops *every* batch_prefill kernel if any `--targets` token is not `gfx9*`.

**§2 — Every `generate.py` invocation now passes it**, across the four files that launch it: `optCompilerConfig.json`, the `cmdGenFunc_*` hooks in `mha.py`, `mha_recipes.py`, and the standalone `op_tests/cpp/mha/compile.py`.

**§3 — fp8 / batch_prefill gates, and which arch they read.** fp8 has no CK factory on gfx11/gfx115, and `batch_prefill` is gfx9-only, so both now raise `NotImplementedError` up front instead of failing deep inside CK dispatch.

The catch: `compile_ops` re-runs `gen_func` on **every** call to build its module-name cache key, so the gate sits on the hot path, not just the build path — and it has to read the *live* card, not `GPU_ARCHS`:

```
live call
└── flash_attn_fp8_pertensor_func(...)
    ├── _check_fp8_factory(get_gfx_runtime(), ...)   # public API: the real card
    └── mha_fwd(...)                                  [compile_ops]
        └── _cmdGenFunc_mha_fwd_lookup(...)           # NEW — runs on every call
            ├── _check_fp8_factory(get_gfx_runtime(), ...)
            └── cmdGenFunc_mha_fwd(..., check_build_arch=False)
```

`GPU_ARCHS=gfx942;gfx1100` makes `get_gfx()` return `gfx1100` (last token wins), so gating on `get_gfx()` would reject fp8 on a real gfx942 card. Every production entry point therefore reads `get_gfx_runtime()`: all three `compile_ops` registrations — `mha_fwd`, `mha_varlen_fwd`, `mha_batch_prefill` — go through a `_*_lookup` wrapper that passes `check_build_arch=False`.

`check_build_arch=True` (the default) selects the `get_gfx()` variant for a no-GPU build-time caller. **No such caller exists today** — `setup.py`'s prebuild drives codegen through `get_args_of_build` + `get_mha_varlen_prebuild_variants_by_names` and never calls `cmdGenFunc_*` — so that branch is currently reached only from `test_ck_fmha_targets_wiring.py`. I can drop the parameter if reviewers prefer it gone.

## ⚠️ Behavior change

`GPU_ARCHS="gfx942"` wheels no longer contain gfx950 FA kernels — CK's `gfx9,gfx950` default used to slip them in regardless. **Set `GPU_ARCHS` to every arch the wheel must run on.** `docs/installation.rst` updated.

### 4b. `_cmdGenFunc_mha_fwd_lookup` and keyword `q`

> also `_cmdGenFunc_mha_fwd_lookup(q, *args, **kwargs)` now TypeErrors if `q` arrives as a keyword where the old gen_func hook accepted it. **Author must** (...) confirm no caller passes `q` by keyword.

**This doesn't reproduce — no call shape raises.** Since the failure mode matters, both readings laid out:

**The concern, as I read it:** the wrapper introduces a named first parameter where the old hook had none, so a keyword call such as `mha_fwd(q=..., k=...)` would either

- **(a)** fail to bind `q` at all, or
- **(b)** bind it and then collide on the forward — `cmdGenFunc_mha_fwd(q, *args, **kwargs)` passes `q` positionally, so if `**kwargs` still carried `q` the result would be `TypeError: got multiple values for argument 'q'`.

**Why neither happens:**

- `q` is *positional-or-keyword*, not positional-only — there is no `/` in the signature — so `_lookup(q=tensor, ...)` binds it normally. (a) doesn't occur.
- Binding *consumes* it: once `q` is matched, Python removes it from `**kwargs`. So the positional forward has nothing to collide with. (b) doesn't occur.
- Separately, `check_build_arch` sits after `*`, making it keyword-only, so it cannot be filled positionally even when all 21 parameters are passed positionally.

All three call shapes:

```python
>>> def cmdGenFunc_mha_fwd(q, k, v, dropout_p, *, check_build_arch=True):
...     return (q, k, v, dropout_p, check_build_arch)
>>> def _lookup(q, *args, **kwargs):
...     return cmdGenFunc_mha_fwd(q, *args, **kwargs, check_build_arch=False)
>>> _lookup(1, 2, 3, 0.0)                    # all positional
(1, 2, 3, 0.0, False)
>>> _lookup(q=1, k=2, v=3, dropout_p=0.0)    # q as keyword
(1, 2, 3, 0.0, False)
>>> _lookup(1, 2, v=3, dropout_p=0.0)        # mixed
(1, 2, 3, 0.0, False)
```

Scope: `compile_ops` forwards verbatim — `custom_build_args.update(gen_func(*args, **kwargs))` at `aiter/jit/core.py:1978` — so whatever shape reaches `mha_fwd` reaches the hook unchanged, and the three above are exhaustive. No change made here; happy to be shown a failing case if I've missed one.
