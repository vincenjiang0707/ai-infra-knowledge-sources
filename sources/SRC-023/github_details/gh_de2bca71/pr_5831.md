## 正文

## Motivation

Three defects in the `moe_gemm_mxfp8` wrapper. They are grouped because they share one file pair and one theme: how the wrapper handles its output buffer, its routing conversion, and its weight layout.

### 1. Uninitialized output buffer

The kernel writes only rows covered by `ExptHist`/`ExptOffs`, that is `[0, sum(group_sizes))`. A caller that deliberately excludes rows, such as a foreign expert under EP or `-1` top-k padding, leaves the tail of `torch.empty` holding whatever the caching allocator last put there.

Those rows are not safe to ignore. A NaN there survives a downstream `* 0` mask, because `NaN * 0 == NaN`, and the top-k reduction spreads it across the whole token. The failure depends on allocator state, so it passes smoke tests and corrupts output later.

The reference in `op_tests/triton_tests/moe/test_moe_gemm_mxfp8.py` already builds its expected result with `torch.zeros`, so this change makes the kernel match its own test.

### 2. `group_sizes_to_expt_tensors` blocks CUDA graph capture

```python
total_blocks = int(n_blocks_per_expert.sum().item())  # single sync at end
```

`.item()` is a device to host sync, so the call fails under graph capture with `hipErrorStreamCaptureUnsupported`. vLLM captures the MoE forward, so the op cannot be used there today.

This is also unfinished review feedback on #5658. Comment [r4045560427](https://github.com/ROCm/aiter/pull/5658#discussion_r4045560427) asked for the mapping to be built "with tensor operations (or reuse the existing GPU-side helper)". The per-expert Python loop was removed; the final `.sum().item()` stayed.

The fix reuses the pattern that `build_block_mapping()` in this same file already documents. Every expert wastes at most one partial block, so `cdiv(total_tokens, block_m) + E` bounds the real count with no sync. Surplus slots are stamped `ExptData = -1`, which the kernel already returns early on (`moe_op_gemm_a8w8.py:271-273`). Verified over 2000 random routings.

`total_tokens` is optional and defaults to `None`, which preserves the exact legacy path for existing callers.

### 3. The weight is re-copied on every call

```python
rhs_kn = rhs.permute(0, 2, 1).contiguous()
w_scale_kn = w_scale.permute(0, 2, 1).contiguous()
```

MoE expert weights are static after load, so this re-materializes the whole tensor on every invocation. That costs 2.4 ms for `rhs` alone at `E=32, N=2048, K=6144` on gfx942, and it transiently doubles the weight footprint. Callers that already store K-major now get a view instead.

## Test Result

MI325X (gfx942), ROCm 7.2.3. Existing tests pass unchanged.

| check | result |
|---|---|
| correctness, 13 shape/layout configs | cosine >= 0.999999 vs fp32 |
| NK vs KN inputs | bitwise identical output |
| CUDA graph capture + replay | fails on main, passes here |
| NaN-poisoned allocator, half-foreign map | 100% NaN before, 0/16384 after |

Shapes cover `K=96` and `K=32`, which exercise the partial and single K-block cases, plus ragged group sizes `[0,7,64,1,100,0,84,0]` including zero-token experts.
