## Motivation

## Potential problem
Using TRITON=`3.8.0+git4cff872c.rocm10.1.0a20260811`, the compiler has an **uneven** cost upcasting fp8 to bf16/fp16, and the following local patch is required in vLLM to always pass in bf16 Q into the kernel.
`vllm/v1/attention/backends/rocm_aiter_unified_attn.py`, in `RocmAiterUnifiedAttentionImpl.__init__`:

```python
from vllm.platforms.rocm import on_gfx11
self.supports_quant_query_input = not on_gfx11()
```

Without it, `Attention.__init__` builds a `query_quant` whenever the KV cache is fp8 (`vllm/model_executor/layers/attention/attention.py:464-470`) and the query is quantized alongside the KV cache to fp8. 

### REASON
As gfx1151 has no fp8 WMMA, passing in fp8 Q is not only a pure precision loss, but also causes the kernel to regress up to 4 times. The Triton compiler's current default WMMA upcasting dtype is fp16, not bf16. Fp16 uses a lot more cmp instructions and causes the kernel to regress badly. Leaving Q in bf16, then inside kernel do `K_load.to(Q.dtype)`, `V_load.to(Q.dtype)` explicitly uses bf16 and bypasses the compiler problem. This is what the above table measurements are based on.

For conclusion, this is a pure use case problem, and this PR stays valid. Investigation into Triton compiler's RDNA3 fp8 upcasting dtype (fp16/bf16) is ongoing.
