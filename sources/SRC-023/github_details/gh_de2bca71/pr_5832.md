# [PR #5832] [Triton/Gluon] [Perf] MXFP8 MoE: keep the MFMA in FP8 when MX_SCALE_BLOCK_K == 1

source: https://github.com/ROCm/aiter/pull/5832
state: open | updated: 2026-09-25T02:10:08Z
labels: ci:triton-300x, Triton/Gluon

## 正文

## Motivation

The `USE_FNUZ` path added by #5658 upcasts both operands to fp32 and broadcasts both scale tiles across the full K tile, plus a `tl.trans`, before `tl.dot`. That promotes an FP8 MFMA to an FP32 one at 4x the operand footprint.

It is never a win. #5658 itself closed off the other configurations: in response to review comment [r4045560377](https://github.com/ROCm/aiter/pull/5658#discussion_r4045560377) the wrapper now asserts

```python
assert quant_block_size == 32, "_moe_gemm_a8w8 hardcodes MX_PACK_DIVISOR=32"
```

and `MX_SCALE_BLOCK_K = BLOCK_K // MX_PACK_DIVISOR`, so `MX_SCALE_BLOCK_K` is always 1 on every MXFP8 MoE call. That means one scale per operand per K-step, constant across the dot.

When the scale is constant across the dot, scaling the `[BLOCK_M, BLOCK_N]` result is equivalent to scaling the `[*, BLOCK_K]` operands, and the operands can stay in FP8:

```python
acc += (
    tl.dot(x, w, input_precision="ieee")
    * tl.sum(a_sc, axis=1)[:, None]
    * tl.sum(b_sc, axis=1)[None, :]
)
```

This keeps the merged kernel and fixes that path. It does not revert #5658.

## Technical Details

Applied to both the main loop and the `not EVEN_K` tail. The `MX_SCALE_BLOCK_K > 1` branches are preserved byte for byte.

Those branches are unreachable today, since the assert pins `BLOCK_K = 32`. They also disagree with each other: the main loop broadcasts the weight scale on axis 2 and then transposes, while the tail broadcasts on axis 1 and does not. At most one can be correct. I have left both alone, since fixing an unreachable path is a separate concern, but reviewers should know those configurations are untested and that this PR does not try to measure them.

pytest op_tests/triton_tests/moe/test_moe_gemm_mxfp8.py -v

## Test Result

MI325X (gfx942), ROCm 7.2.3, idle node, Triton cache cleared between arms, best of 5 timing runs.

`E=32, N=2048, K=6144`, weights already stored K-major:

| tokens | main | this PR |
|---|---|---|
| 8 | 0.99 ms | 0.30 ms |
| 64 | 0.99 ms | 0.31 ms |
| 512 | 0.99 ms | 0.33 ms |
| 2048 | 1.00 ms | 0.41 ms |

About 3.2x at decode-sized batches.

The same measurement with NK weights, where both arms pay the wrapper's per-call transpose, shows the hoist alone is worth about 0.7 ms (3.43 ms down to 2.75 ms). The remaining gap between 2.75 ms and 0.31 ms is that transpose, which the companion wrapper PR removes for callers that already store K-major.

Correctness across 13 shape and layout configurations with random E8M0 scales, including `K=96` and `K=32`, plus ragged group sizes `[0,7,64,1,100,0,84,0]` with zero-token experts: cosine >= 0.999999 against an fp32 reference in every case.

End to end on vLLM 0.30.1rc1, 8x MI325X, TP=8, `tencent/Hy4-preview-FP8` with real weights, with both this PR and the wrapper PR applied: decode throughput 1.68 to 10.01 tok/s, TPOT 97.65 ms, GSM8K unchanged within noise (84.00% vs 85.50% last-number, n=200, 0 errors in both arms).


## Notes for reviewers

Please add `ci:triton-300x`. The default Triton CI targets gfx950, and this path is exercised on gfx942.

The companion wrapper fix is `akii96:fix/mxfp8-moe-wrapper`. The two branches are cut from the same base and touch disjoint files, so either can land first. This one alone is numerically correct but not CUDA graph capturable, since that fix lives in the wrapper PR.

The benchmark's in-tree shapes are DSv4 oriented (`8,7168,2048` and `64,2048,7168`), so the Hy4 MoE shape above is not among them.
