## 正文

## Summary

Integrate the current main APIs / DeepJIT runtime and native SM120 kernels into **`nv_dev`**, while preserving its branch-specific functionality. This is a substantial release integration, not a small SM120-only patch. The API/runtime baseline is main's Public Release 26/09 (#432); the intended merge target is **nv_dev**, not main.

### SM120 support

- Native BF16, FP8, FP4 and mixed FP8/FP4 dense GEMM; M-grouped contiguous/masked paths; BF16/FP8 K-grouped paths.
- FP8 einsum, native BF16 forward einsum and batch reduction, and HC prenorm.
- Dense/paged FP8 and MXFP4 MQA, plus **DSv4.1 MXFP8/MXFP4 sparse and paged sparse MQA**, using the current metadata APIs.
- Current scaling-factor/layout interfaces, dispatch validation, focused regression tests and support documentation.

The existing SM120 kernel algorithms, heuristics and pipelines are retained through the API migration. DeepSelect is a separate project and is not included here. README and scaling-factor documentation describe unsupported combinations; this does not add SM120 MegaMoE, Mega Gate or Mega mHC support.

### Preserve nv_dev features

- SM90 FP8 MegaMoE, including split L1/L2 execution and natural FP32 block-128 weight scales (#383).
- NVFP4 MegaMoE with BF16 shared experts, per-expert scales and routed scaling (#409).
- SiTU for both routed and shared experts (#396).
- SM100 **dense** MQA with FP16 weights, preserving its dedicated MMA path rather than replacing it with BF16. FP16 paged MQA is not added.
- SM90 paged MQA with physical page sizes 32/64, next_n=1/2/4, and zero-work/scheduler safety fixes.

The restored SM90/NVFP4 paths retain a private dynamic-counter workspace (LCM 384), separate from main's workspace (LCM 1920). NVFP4 uses E4M3 scales per 16 elements and is not aliased to main's MXFP4/UE8M0 enum or layout.

### Correctness changes distinguished from mechanical migration

- Restore removed math/shuffle helpers privately and adapt host launches to DeepJIT without replacing kernel arithmetic.
- Validate SM90 output/device/rank inputs and reject incompatible buffer protocols/layouts.
- Restrict NVFP4 `base=` reuse to identical supported configurations, including the configured SM count; main-compatible buffer reuse remains available.
- Fix an **inherited NVFP4 combine double-buffer WAR hazard** with one warp synchronization before issuing a TMA overwrite. PC/source correlation and a one-token, non-graph reproduction established missing consumer completion before stage reuse. The pre-fix combine region matched nv_dev; the fix changes no arithmetic or rounding order.

## Note: m-grouped contiguous labels contract

A downstream field report ("middle empty group corrupts later groups") was root-caused to a caller-contract violation, not a kernel bug: labels built at a finer granularity than the runtime `mk_alignment_for_contiguous_layout` put a group boundary inside a `BLOCK_M` tile whose B/SFB is selected from the tile's first-row label (verified with the reporter's exact shapes at alignments 32/64/128 — contract-respecting layouts are always safe). The opt-in host checker and regression coverage are proposed arch-generically to main in #450; this branch intentionally carries no fork-local copy and will pick the checker up at the next sync once #450 lands.

## CUDA 13.3 toolchain note (f7bea76)

CUDA 13.3's ptxas crashes (SIGSEGV) compiling the non-warp-specialized MXFP4 sparse MQA logits kernel at `-O3` with any `--register-usage-level` — a compiler bug, not a kernel defect (root-caused in [DeepGEMM-sm120#2](https://github.com/lucifer1004/DeepGEMM-sm120/issues/2); CUDA 13.2 remains the validated toolchain). So downstream users on 13.3 are not broken, this kernel now carries a toolchain-gated per-compile override (DeepJIT `CompilerOptions::extra_nvcc_flags`): on nvcc >= 13.3 the affected instantiations build with ptxas `-O2`, which reproduces the 13.2 register allocation exactly (REG:101 reference). The warp-specialized variant is unaffected and untouched. Validated on sm_120a: sparse MQA suite 9/9 under both CUDA 13.3.73 (gate active; previously 3 failures) and 13.2.86 (gate inactive, default path unchanged).

## Follow-up folded in (b6acafe): FP8 paged MQA PAGE_KV=32

Vendored DeepGEMM-sm120 **v0.1.4** plus host enablement: FP8 paged MQA logits admits block_kv=32 (API + launcher gates), `tile_kv = min(block_kv, 64)`, and a two-KV-stage fallback for page32 + 64 heads + paired queries (three stages exceed the 99 KiB SMEM budget by 4 bytes). Motivation: DSv4.1 indexer caches mix 64- and 32-state pages (vllm-project/DeepGEMM#14; kernel design mirrors the FP4 sibling). Validated on sm_120a from a fresh JIT cache: paged MQA suite 20/20 passed, including new (fp8, page32) contract cases, a focused two-stage-fallback case (page32 x 64 heads, paired/varlen), graph replay and legacy-API cross-checks.

## Follow-up folded in (d9aa49d): SM90 paged MQA scheduler perf

Local review found the migration's stale/OOB-metadata protection sat in the per-task hot path (SM90 paged MQA logits: ~+1% upstream shapes, +13-16% at next_n=4). The protection now runs once at scheduler construction (clamp end to the in-batch sentinel, collapse out-of-range starts), and the per-task end test is a single ordered 64-bit compare on packed (q_atom, kv) keys — which also preserves the hang fix (overshooting advances are caught by >=, never exact equality). Validated on H200: 24/24 paged cases pass; next_n=4 is 9-11% faster than the pre-patch head, upstream-shape sweep at parity or better.

Second review item (k-grouped SF pack, +1.7% on SM100): the suggestion was to keep the psum `align` and revert only `ceil_div` to `/` on SM90/100. That is provably exact there (psum ends are k_alignment-multiples, gran_k | k_alignment, so aligned_group_k % gran_k == 0) — an earlier counter-test of mine that failed on B300 had additionally dropped the `align`, which *is* load-bearing; the reviewer's actual suggestion stands. Landed as `3aca951` + `1f78b85`: a power-of-two shift fast path (pow2 holds at every call site, host-asserted) that subsumes the revert — shift forms equal exact division on SM90/100 and ceil on SM120 — with the generic division path retained for non-pow2 alignments. Follow-up `4b3571e` (review: non-pow2 k_alignment regressed under the runtime pow2 branch): gran_k/k_alignment moved into the JIT template, folding the align/ceil_div at compile time for pow2 AND non-pow2 alike; measured 38.8 -> 14.0 us at k_alignment=128 and 65.2 -> 32.3 us at 384 (B300, bitwise-identical). Pack output bitwise identical (128-group psum, B300); pack kernel 38.7 -> 22.1 us/call (-43%) on that shape; SM100 fp8/bf16 k-grouped suites pass on B300, SM120 k-grouped regressions pass on sm_120a.


## Follow-up folded in (381e2d7): v0.1.5 generic-proxy WAR fences

Vendored [DeepGEMM-sm120](https://github.com/lucifer1004/DeepGEMM-sm120) **v0.1.5** (`b31a688`): ports #453 (thanks @Sunt-ing) and extends it to every site with the same hazard — 14 `fence_view_async_shared()` insertions across 8 SM120 kernel headers. The SM120 kernels read TMA-written smem through `ldmatrix`/`ld_shared` (generic proxy), so the empty-barrier arrive that hands a stage back to the TMA producer must be ordered after those reads; without the fence the next TMA can overlap the consumer's reads (generic/async proxy WAR hazard). Upstream's SM100 kernels carry the same fence for the analogous UMMA case ("Release KV smem only after UMMA commits TMEM"); the SM120 ports had inherited the barrier protocol but not the fences. Sites: bf16_gemm (the #453 report), bmk_bnk_mn, tf32_hc_prenorm_gemm, fp8_fp4_gemm_1d1d (×3), fp8/fp4 dense MQA logits (empty_kv + empty_q each), fp8/fp4 paged MQA logits (empty_q stage release + empty_kv each). Sparse MQA is exempt (legacy cp.async producer). Evidence: #453 author reproduces 2/6000 failures on RTX 5090 without the fence, 0/6000 with it; local RTX PRO 6000 30k-iteration soak does not reproduce either way, so the fence rests on the memory model plus the author's A/B/A, not on local observation. Perf A/B (bf16 GEMM, fp8 dense/paged MQA, 3 runs each): all deltas within run-to-run noise. SM120 suite re-run at this head from a fresh JIT cache: 235 passed.

### 📍 未定位到 diff 的评论

🟡 **warning** `deep_gemm/include/deep_gemm/scheduler/sm90_paged_mqa_logits.cuh:L249`: The zero-context skip loop terminates only on exact equality `current_q_atom_idx == end_q_atom_idx && current_kv_idx == end_kv_idx`. If `current_q_atom_idx` ever steps past `end_q_atom_idx` (metadata built from a different `context_lens` than the kernel observes — e.g. user mutates `context_lens` between the metadata launch and the logits launch, or a malformed sentinel row), this spins forever and hangs the GPU instead of trapping. `exist_q_atom_idx()` already encodes the correct bound. Suggest:

```cpp
while (current_num_kv == 0 and exist_q_atom_idx(current_q_atom_idx)) { ... }
...
if (not exist_q_atom_idx(current_q_atom_idx))
    return false;
```

This keeps the intended skip semantics but makes the loop bounded. <sub>🤖 v5</sub>
