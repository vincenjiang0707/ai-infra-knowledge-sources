# Description

In `sm90_paged_mqa_logits.cuh`, [we compute `num_segs` using diff of `prefix_sum`](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb6994a58b8a15b4b93bf13ccc16edf247/deep_gemm/include/deep_gemm/scheduler/sm90_paged_mqa_logits.cuh#L113), but current diff calculation logic is unsafe as `q_idx` can be `batch_size` after the binary search which is out of bound of `prefix_sum` if `batch_size` is aligned. In this case, we should instead refer to the already computed segment sum (the would-be `prefix_sum[batch_size]`).

The overall math is trivial, so no further comments added in this ternary.

We have hit this error in production, the following is the CUDA coredump - `sm90_paged_mqa_logits_metadata<kAlignedBatchSize=96, SPLIT_KV=256, kNumSMs=132, kIsVarlen=false>` hits the problematic line with 16 sequences with next_n=6:

审查结论：修复正确，可以合入。问题根因是 sm90_paged_mqa_logits_metadata 非 varlen 分支中，二分查找的 hi = batch_size 使得 q_idx 可能取到 batch_size（当 batch_size 与 kAlignedBatchSize 对齐时），旧代码随即读取 prefix_sum[q_idx] = prefix_sum[batch_size]，而 prefix_sum 只有 kAlignedBatchSize 个元素（索引 0..kAlignedBatchSize-1），导致 CUDBG_EXCEPTION_WARP_OUT_OF_RANGE_ADDRESS。修复将其改为 (q_idx == batch_size ? sum : prefix_sum[q_idx])，其中 `sum` 是循环累加的总和；由于非 varlen 路径中 q_idx &gt;= batch_size 的项 context_len = 0、对前缀和贡献为 0，所以 sum 恰好等于应有的 prefix_sum[batch_size]，语义完全正确。边界行为也已核对：q_idx == batch_size 时 q_atom_idx == batch_size * num_next_n_atoms，与 line ~133 写入 schedule_metadata[kNumSMs*2] 的结束哨兵一致，映射到该范围的 SM 会正确终止；offset_in_q 仅访问 prefix_sum[q_idx - 1]（q_idx - 1 &lt;= batch_size - 1），仍在界内。varlen 分支不受影响：其二分查找 hi = num_items，且只读取 prefix_sum[atom_idx - 1]（atom_idx - 1 &lt;= num_items - 1 &lt;= kAlignedBatchSize - 1），不存在同类越界。修复为单行最小改动，与调度器其余逻辑一致，未发现其他问题。

### v5
该 MR 修复了 `sm90_paged_mqa_logits_metadata` 中 `prefix_sum` 的越界读取问题（CUDBG_EXCEPTION_WARP_OUT_OF_RANGE_ADDRESS）。在非 varlen 分支中，二分查找区间为 [0, batch_size)，当 `seg_starts` 落在最后一个前缀边界之后时 `q_idx == lo` 可能等于 `batch_size`，此时原代码 `prefix_sum[q_idx]` 会越界读取。修复通过三元表达式在 `q_idx == batch_size` 时改用已计算的段总和 `sum`（即逻辑上的 `prefix_sum[batch_size]`），数学语义完全等价：此时 num_segs_q = sum - prefix_sum[batch_size-1] = 0，由第 114-115 行的 `num_segs_q &gt; 0` 保护分支正确兜底。经核查，同行附近的 `offset_in_q`（第 112 行）只访问 `prefix_sum[q_idx - 1]`，下标最大为 batch_size-1，不存在越界；varlen 分支（第 89-90 行）对 `atom_idx == num_items` 也已有显式保护，本修复覆盖了最后一处越界路径。改动最小、正确，且与 coredump 中报告的场景（16 sequences, next_n=6, kAlignedBatchSize=96）吻合。建议合并。
