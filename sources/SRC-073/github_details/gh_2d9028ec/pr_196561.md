## PR Review: #196561

### Summary
Sets `_emitted_device_tma = True` in `store_reduction()` so a reduction store that directly formats a `TensorDescriptorOptions` is counted as device TMA, which stops `codegen_kernel()` from popping `tma_min_block_sizes`. The direction is correct and the placement matches the invariant at `codegen_block_ptr()` — but the justifying comment asserts something that is not true, one consequence of that is a real (narrow) metadata bug, and the test-file comment describes coverage that does not exist.

### Code Quality

- **`torch/_inductor/codegen/triton.py:6359-6365` — the comment's central claim is false.** The comment says a `TensorDescriptorOptions` here "is therefore necessarily emitted as an in-kernel device-TMA descriptor." It is not. The line is wrapped in `DeferredLine(name, store_line)` (line 6366), and `DeferredLine.__call__` returns `None` when `is_buffer_removed(name)` (`codegen/common.py:1687-1690`). The flag is set unconditionally at body-codegen time; whether the descriptor actually reaches the output is decided later.

  Concretely reachable ordering:
  1. `CSEProxy.store_reduction` (`common.py:3138`) only guards on `name not in V.graph.removed_buffers` — it cannot check the kernel-local `removed_buffers`, which does not exist yet.
  2. `kernel.store_reduction()` runs and sets `_emitted_device_tma = True` (line 6365).
  3. `Kernel.__exit__` → `remove_kernel_local_buffers()` (`common.py:2593`, `2596-2634`) moves the buffer into `kernel.removed_buffers` if it is created and last-used in this kernel. A reduction output consumed by a fused pointwise epilogue is the canonical case this pass targets.
  4. `codegen_kernel()` runs *after* that (`codegen/simd.py:4124` then `4133`), reads `self.uses_tma` at `triton.py:7626`, and so does **not** pop `tma_min_block_sizes` — defeating the guard whose own comment says "a stale constraint regresses non-TMA kernels" (`triton.py:7627-7628`).           | self.inplaced_to_remove
