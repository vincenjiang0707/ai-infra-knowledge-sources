## Summary

On aarch64 CPU `operator_benchmark` (eager, `short` tag), one `matmul` config is ~25× slower than the checked-in expected CSV. Neighboring GEMMs on the **same job** got *faster*, so this is not a slower runner or a globally stale ARM baseline.

Tracked from empty PR https://github.com/pytorch/pytorch/pull/195472 (no functional change; two `ciflow/op-benchmark` runs, including a rebase).

## Case

`matmul_M256_N256_K256_trans_aFalse_trans_bTrue_cpu`

- Job: `aarch64-opbenchmark-test` / `cpu_operator_benchmark_short`
- Runner: `mt-l-arm64g4-16-62` (`linux.arm64.m8g.4xlarge`)
- Checker: `benchmarks/operator_benchmark/check_perf_csv.py` (FAIL if actual > 2× expected)
- CSV: `aarch64_expected_ci_operator_benchmark_eager_float32_cpu.csv`

## Times (`Execution Time`)

| | Expected | Run 1 | Run 2 |
|---|---:|---:|---:|
| `matmul_M256 … trans_a=False trans_b=True` | 234.09 | **5573** (23.8×) | **6599** (28.2×) |
| `matmul_M128 … trans_a=True trans_b=False` (same job) | 233.29 | 128.84 (improved) | 127.17 (improved) |
| `mm_M64_N64_K64` f32 (same job) | 99.35 | 52.82 (improved) | 52.36 (improved) |

Expected for the 256 `trans_b` row is almost the same number as 128 `trans_a` (234 vs 233), which is also suspicious.

## What we did on the PR

Skipped this case in `SKIP_TEST_LISTS` so CPU op-benchmark CI can go green **without** writing ~6k into the expected CSV (that would hide a 25× regression). Drop the skip once this path is fixed.

## Ask

Confirm whether 256×256 `trans_b=True` on this ARM SKU is supposed to be ~234 or ~6k. If ~234 was real, this is a GEMM/transpose path regression on `main`.
