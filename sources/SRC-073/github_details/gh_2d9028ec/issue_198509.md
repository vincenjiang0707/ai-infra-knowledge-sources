## 正文

Two coupled defects in the fp32 SDPA fusion gate in `torch/_inductor/fx_passes/fuse_attention.py`. Filing as one issue because fixing the first without the second regresses ROCm.

**1. `_sfdp_pattern_24` never runs its extra check.**

At line 1338 the pattern is registered with the factory passed uncalled:

```python
(
    _sfdp_pattern_24,
    _sfdp_replacement_24,
    [g(), g(), g(), b_float()],
    {},
    _sfdp_extra_check,        # every other site passes _sfdp_extra_check(...) or _sfdp_params_check
),
```

`_sfdp_extra_check(scale_factor_op=None, disable_cuda=False)` is a factory returning an inner `fn`. The matcher calls `extra_check(match)` at `pattern_matcher.py:2141`, which binds `scale_factor_op=match` and returns that inner closure -- a truthy function object. So the check always "passes" and `_sfdp_params_check` never runs for this pattern.

That means pattern 24 skips all four of its validations: the `inv_scale` check, the q/k/v dtype-and-device consistency check, the tf32 gate, and the attn_mask dtype/device/rank check. The pattern takes a mask (`b_float()`), so the mask validation is not vacuous.

**2. The tf32 gate's premise is inverted on ROCm.**

```python
# fused kernels use tf32
if (query.device.type == "cuda" and query.dtype == torch.float32
        and torch.backends.cuda.matmul.fp32_precision != "tf32"):
    return False
```

On ROCm the fused kernel does not use reduced precision. `_fused_sdp_choice` selects AOTriton mem-efficient attention, which computes in full fp32 and is bit-identical whether the flag says `ieee` or `tf32`. Measured on gfx942 against an fp64 gold at shapes (4,2,16,32) with a mask: the fused result is 2.456e-06 from gold under both settings, while the eager `bmm` reference degrades from 2.41e-06 to 6.04e-03 because hipBLASLt honors the flag as XF32. Same picture on gfx950 (7.44e-05). So on ROCm the gate refuses to fuse in exactly the configuration where the fused kernel is the more accurate one.

**Why they are one issue.**

Fixing (1) alone regresses ROCm. Changing line 1338 to `_sfdp_extra_check()` makes `test_pattern_fails_with_mismatched_view_grouping_gpu` fail immediately with `AssertionError: 0 not greater than or equal to 1` on the `fuse_attention` counter, because that test now runs at `ieee` on ROCm (#198220 follow-up) and the gate then refuses the fusion. Fixing (2) alone is safe but leaves pattern 24 unchecked.

Repro for (1), on any device:

```python
import torch, torch.nn.functional as F
from torch._dynamo.utils import counters
bs, n_head, seq_len, embed_dim = 4, 2, 16, 32

def f(q, k, v, mask):
    qq = q.view(bs*n_head, seq_len, embed_dim)
    kk = k.reshape(bs*n_head, seq_len, embed_dim)
    vv = v.reshape(bs*n_head, seq_len, embed_dim)
    w = torch.bmm(qq, kk.transpose(1, 2))
    w = (w.view(bs, n_head, seq_len, seq_len) + mask).view(bs*n_head, seq_len, seq_len)
    return torch.bmm(F.softmax(w, dim=-1), vv).view(bs, n_head, seq_len, embed_dim)

for prec in ("tf32", "ieee"):
    torch.backends.cuda.matmul.fp32_precision = prec
    torch._dynamo.reset(); counters.clear()
    args = [torch.randn(bs, n_head, seq_len, embed_dim, device="cuda") for _ in range(3)]
    args.append(torch.randn(1, 1, seq_len, seq_len, device="cuda"))
    torch.compile(f, fullgraph=True)(*args)
    print(prec, counters["inductor"]["fuse_attention"])
```

Both print `1`. With the gate actually wired up, `ieee` should print `0` on CUDA.

## 评论 (1)

### JingHao-Leon · 2026-09-24

Stable-release confirmation of **part 1** (I can't speak to the ROCm half — no such hardware here): the uncalled-factory registration is present verbatim in **torch 2.14.0** at `torch/_inductor/fx_passes/fuse_attention.py` L1332-1337 —

```python
_sfdp_pattern_24,
_sfdp_replacement_24,
[g(), g(), g(), b_float()],
{},
_sfdp_extra_check,        # factory passed uncalled
```

The contrast with every neighboring site is visible in the same file: patterns at L1140/1147/1154/1161 call the factory (`_sfdp_extra_check(aten.div.Tensor)` etc.), and the sites at L1168-1189 pass `_sfdp_params_check`, which is a plain `match`-taking function — correct to pass bare. Only pattern 24 passes the uncalled factory, so when the matcher invokes `extra_check(match)`, `match` binds to `scale_factor_op` and the returned inner closure is the "check" — truthy function object, always passes. Pattern 24's `_sfdp_params_check` validations (inv_scale, dtype/device consistency, tf32 gate, mask checks) therefore never run on 2.14.0 either.
