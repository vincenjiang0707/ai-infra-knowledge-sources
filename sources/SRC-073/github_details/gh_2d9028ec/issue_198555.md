# [Issue #198555] [inductor][cpu] Integer neg is signed overflow in the generated C++, and argmax after it can return other indices than eager

source: https://github.com/pytorch/pytorch/issues/198555
state: open | updated: 2026-09-24T21:49:25Z
labels: oncall: cpu inductor, bot-triaged

## 正文

### 🐛 Describe the bug

```python
import torch

torch.manual_seed(0)
x = torch.randint(-100, 100, (8, 8))
x[torch.rand(8, 8) < 0.25] = torch.iinfo(torch.int64).min
x = x.mT.contiguous().mT


def f(x):
    return (-(x & x.flip(-2))).argmax(-1)


print(f(x).tolist())
print(torch.compile(f)(x).tolist())
```

```
[0, 1, 1, 1, 1, 1, 1, 0]
[0, 2, 2, 1, 1, 2, 2, 0]
```

2.14.0 CPU, gcc 13.3. The contiguous input (vectorized loop) is right; `* -1` or `0 - ...` in place of the unary minus is right too.

`CppOverrides.neg` emits `decltype(x)(-x)`, and `-INT64_MIN` is signed overflow, undefined behavior in C++; here it feeds the scalar argmax loop and gcc uses the no-overflow assumption on the comparisons. `add`, `sub` and `mul` already go through `std::make_unsigned_t` for this reason (`arith_promoted`), `neg` doesn't. Negating through the unsigned type for int32 and int64 makes this right. `std::abs` of the minimum is the same kind of UB; I haven't seen it go wrong. I have the `neg` change with a test and can open a PR.

### JingHao-Leon · 2026-09-24

Also reproduces on **torch 2.14.0, CPU on Apple Silicon arm64 (clang/macOS 26.5)** — same script, same eager output `[0, 1, 1, 1, 1, 1, 1, 0]`, but the compiled result is a *different* wrong answer than your gcc run: `[0, 0, 0, 2, 2, 0, 0, 0]` vs your `[0, 2, 2, 1, 1, 2, 2, 0]`.

Two compilers producing two different wrong answers from the same generated C++ is exactly the fingerprint of the signed-overflow UB you identified in `CppOverrides.neg` (`-INT64_MIN`), and it widens the impact beyond gcc/x86 — this needs the `std::make_unsigned_t` treatment that `add`/`sub`/`mul` already get. Please do open the PR.
