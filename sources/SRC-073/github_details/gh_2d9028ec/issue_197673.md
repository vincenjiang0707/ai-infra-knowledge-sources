# [Issue #197673] [CUDA] `torch.arange` silently leaves every element from index 2**32 onward as zero when N > 2**32

## 正文

## 🐛 Describe the bug

On CUDA, `torch.arange(N, dtype=torch.int64)` with `N > 2**32` returns a tensor whose first `2**32` elements are correct and whose remaining elements are all zero. No error or warning is raised. The same call on CPU is correct.

```python
import torch

N = 2**32 + 2**20  # ~34 GB as int64
x = torch.arange(N, dtype=torch.int64, device="cuda")
print(x[2**32 - 1].item(), x[2**32].item(), x[-1].item())
print("nonzero from 2**32 on:", (x[2**32:] != 0).sum().item(), "of", N - 2**32)
```

Output on an A100-SXM4-80GB with torch 2.11.0+cu128:

```
4294967295 0 0
nonzero from 2**32 on: 0 of 1048576
```

Expected (and what CPU gives): `4294967295 4294967296 4296015871`, with all `2**20` trailing elements nonzero.

Additional observations:

- `x[2**32]` and `x[-1]` are also 0 on torch 2.12.1+cu130, 2.13.0+cu130 and 2.14.0+cu130.
- On 2.11.0+cu128, `N = 2**32 + 5` also leaves the last 5 elements at zero, and `N = 2**31 + 5` is correct.
- On 2.11.0+cu128, `torch.empty(N, dtype=torch.int64, device="cuda").fill_(7)` with the same `N` is correct up to the last element, so indexing and reading back large tensors work. Only the values written by `arange` are wrong.

### Related

- #182657 fixed the same symptom on ROCm ("accepted silently with the kernel never executing, leaving zero-initialized output") for `N >= 2**32`. Its description says the non-ROCm path was left untouched.
- `test_range_factories_64bit_indexing` in `test/test_tensor_creation_ops.py` (`@onlyCUDA`) checks `N = 2**31 + 1` on every GPU build, but checks `N = 2**32 + 1` and `N = 2**33 + 1` only under `TEST_WITH_ROCM`. So the CUDA path is not tested above `2**32`.
- Found while checking a similar problem on MPS (#197636).
