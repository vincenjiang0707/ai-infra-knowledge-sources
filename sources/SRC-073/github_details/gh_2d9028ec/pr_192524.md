## 正文

## Summary

This PR enables `NCCLSymmetricMemory` on ROCm. ROCm cannot reuse the CUDA path: HIP graph capture, RCCL window registration, and the device reduce APIs do not behave the same way. The changes below are the smallest set that make allocation, rendezvous, capture, and the three device ops work on the tested RCCL stack.

Almost all of the C++ under `torch/csrc` is `USE_ROCM`-guarded. Five fixes are not, and do change CUDA behavior; they are enumerated under "Changes that affect the default path". `NCCL_HAS_SYMMEM_DEVICE_SUPPORT` on CUDA stays at NCCL 2.28.0.

## Problem

`NCCLSymmetricMemory` was CUDA-only. Opening the same gates on ROCm is not enough:

- RCCL `ncclMemAlloc` without CUMEM falls back to `hipMalloc`. Capture rejects that.
- A synchronous `hipMemset` or `hipMemcpy` during Global capture returns HIP 906 and kills the capture (901).
- An async memset recorded on the capturing stream becomes a graph node and can wipe a peer signal pad on every replay.
- RCCL 2.30.4 window registration fails during capture. 2.30.7 succeeds.
- A fused multi-destination reduce-scatter launch faults with `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION` on gfx942 and gfx950.
- A retained handle after process-group destroy launched a barrier kernel through a dead communicator and hit `HSA_STATUS_ERROR_MEMORY_FAULT`.

## Solution

On ROCm, a per-device `NCCLDevCommManager` snapshots RCCL device-API support at communicator init. That snapshot requires CUMEM and WIN to have been set before the communicator was created. Fresh windows use CUMEM plus an async zero on a non-captured setup stream wherever that path is supported. Peer tables upload on the same stream, under a Relaxed capture-mode guard, so rendezvous returns with initialized device pointers. Device comms are created once and cached. Reduce-scatter still launches one kernel per destination. On ROCm, `ProcessGroupNCCL` retires its registry identity before RCCL abort or destroy, and every ROCm accessor that can touch a communicator checks that registration is still live.

The suite runs on any ROCm with RCCL >= 2.30.4 and a host-compatible `nccl_device.h`. MI350 additionally requires ROCm 10.1, because the symmetric-memory defect that motivates a version floor only reproduced there.

## Design choices

**`nccl_device.h` presence is not enough.** A host C++ TU cannot compile every RCCL that ships the header. CMake probes the installed header. ROCm also requires RCCL >= 2.30.4 (`NCCL_HAS_SYMMEM_SUPPORT`), written as `#if !defined(USE_ROCM) || defined(NCCL_HAS_SYMMEM_SUPPORT)` so CUDA's `NCCL_HAS_SYMMEM_DEVICE_SUPPORT` threshold stays at NCCL 2.28.0. hipcc needs CUDA's extended-lambda macro and a local `__half operator+` because PyTorch defines `__HIP_NO_HALF_OPERATORS__`.

**Device API support is a runtime snapshot, not a compile-time gate.** RCCL reports `deviceApiSupport=0` unless both `NCCL_CUMEM_ENABLE` and `NCCL_WIN_ENABLE` are set before communicator init. A qualifying header can still sit on a communicator that has no device API. `NCCLDevCommManager` records `ncclCommQueryProperties` at register time and binds it to that communicator identity. Turning the env vars on later does not enable an already-created comm. Rendezvous therefore rejects that case outside capture, which is the test that reaches `comm_has_device_api_support()`.

**Capability, not capture state, selects the allocation path.** The CUMEM + setup-stream path is correct outside capture too, so keying on `capture_allocation_supported()` gives one path on a supported stack. HIP only reports capture state for the current stream, so this PR adds no `is_graph_capture_active()` call site: the CUMEM path runs under the Relaxed guard, performs no capture-illegal host wait, and writes the pad and peer tables as immutable host-side setup rather than graph nodes, so a Global capture on another thread does not need a process-wide query. The current-stream `TORCH_CHECK` exists only as the diagnostic for configurations that do not support that path.

**`TORCH_NCCL_SYMM_MEM_DISABLE_CAPTURE_ALLOC=1` keeps the plain path.** It is read inside `capture_allocation_supported()`, so it selects `ncclMemAlloc` plus synchronous memset for allocation *and* a synchronous `cudaMemcpy` for the rendezvous peer-table upload. That is the allocate-then-capture fallback for stacks that cannot allocate under capture, and it is how the two allocation paths were compared: both arms produce the same peer digest, which is what justifies keying on capability rather than on capture state.

**One shared setup stream is created when a qualifying comm registers.** Signal-pad zero and peer-table H2D need a stream that is not the capturing stream. HIP allows `hipStreamCreate` during Global capture; the pre-create is so every alloc/rendezvous reuses one per-device stream rather than creating one per call. Use of that stream is serialized. It is created at registration regardless of the kill switch.

**A host-side wait is illegal under Global capture, even on a non-captured stream.** Moving the H2D copy off the capturing stream is not enough. `cudaStreamSynchronize` on the setup stream still returns HIP 900. `alloc()` therefore wraps its whole `ncclMemAlloc` / async-zero / synchronize sequence in `CUDAStreamCaptureModeGuard{Relaxed}`, and rendezvous does the same for the peer-table upload. The peer tables and signal pad are immutable for the object's lifetime, so they are initialized on the setup stream and are not recorded as graph nodes. `hipStreamWaitEvent` would also work, but it would only guarantee the tables are ready before later device work, not when rendezvous returns on the host.

**Fresh capture allocation requires RCCL >= 2.30.7.** Direct window registration during Global capture succeeds on 2.30.7 (mode stays Global, capture stays active). 2.30.4 fails in worker-side synchronization. Older RCCL still works if the tensor is allocated and rendezvoused before capture.

**`ncclDevCommCreate` is a direct call, then cached per op.** First create during Global capture succeeds on 2.30.7, keeps Global mode and an active capture, and the captured graph replays. All-to-all and reduce-scatter each create a devcomm once and cache it under their own op key, so neither pays creation cost per launch. There is no extra ROCm-only capture guard around create. The symmetric-memory barrier uses the signal pads directly and needs no devcomm.

**RCCL leaks Relaxed mode on window deregister and device-comm destroy.** Direct `ncclCommWindowDeregister` and `ncclDevCommDestroy` change the caller's capture thread mode from Global to Relaxed. Destroy during an active capture also invalidates the capture. Both calls sit in a balanced `CUDAStreamCaptureModeGuard{Relaxed}` so the caller gets its mode back. Same idiom as the setup-stream wait.

**The manager destructor keeps `cudaDeviceSynchronize`.** HIP returns 900 for that wait under an active capture in both Global and Relaxed thread mode, so a Relaxed guard would not make teardown capture-safe. This enablement does not change destructor synchronization.

**Reduce-scatter is serialized per destination, not fused.** The fused launch faults on gfx942 and gfx950 with RCCL 2.30.7. Row tiles that write one destination are safe. ROCm drives the existing shared kernel with a one-slot `ReduceScatterOffsetsInfo` rather than getting a kernel of its own. With `n_owned == 1` the barrier index collapses to `blockIdx.x`, so the per-destination launches are expected to agree bit for bit with a fused launch of the same shape.

**`dst_block_size` stays a `uint16_t`.** The shared kernel layout is the CUDA struct and sizes above 65535 do not fit that field. This PR keeps the layout and validates the size on the host instead; see "Changes that affect the default path" for why that check is not ROCm-scoped.

**On ROCm, `ProcessGroupNCCL` retires the registry identity before RCCL abort or destroy, and retirement carries a generation.** NCCL2 already retired early; the stock path did not, so a retained handle could launch a barrier through a dead communicator. Retirement is the first line, and it is `USE_ROCM`-guarded at the abort and shutdown call sites. On ROCm it must also run for *aborted* comms: retirement only erases map entries and makes no RCCL call, so skipping it would leave the registry pointing at a dead communicator and cause the very deregister-through-a-dead-comm failure it was meant to avoid. Because an aborted-comm path can run from a destructor, it reads the handle through `getNcclCommUnchecked()` and uses it only as an identity token. A monotonic generation covers the remaining case: the peer-alloc object records the generation it registered under and skips destructor deregistration unless that exact registration is still live, which is what makes a successor that reuses the same `ncclComm_t` address safe.

**A stale handle is recoverable, not permanently dead.** Re-rendezvous drops a cached handle whose communicator has been replaced and rebuilds against the successor. The gate is the presence of a successor rather than staleness, because the rebuild runs a collective window registration while the liveness test is rank-local: gating on staleness would let a rank that is further along in teardown enter that collective alone. With no successor registered, every rank sees the same thing and the call raises instead. Recovery is per-rendezvous, not in-place, in two senses: a reference the caller is still holding keeps naming the retired registration and keeps raising, and recovery is only safe if every rank re-rendezvouses the same tensors in the same order.

**Liveness checks are ROCm-only.** The use-after-destroy bug is not ROCm-specific, but it surfaced here as an HSA memory fault. CUDA accessors are left unchanged on purpose. `get_window_offset()` is the existing CUDA+ROCm unification from PR #195516; this PR does not split it. It is arithmetic over two immutable members (`buffer_offset_ + offset_`), so it does not gain a liveness check. `get_offset()`, `get_buffer_size()`, `get_rank()`, `get_world_size()`, and `get_device()` are the same: scalars that cannot touch a dead communicator. Callers that then use the offset go through `get_window()` or a CFT accessor, which do check. `get_group_name()` checks as well: resolving a communicator from a name is the hazard, so the guard sits on the accessor rather than on the call sites that happen to reach it today.

**Allocation size is rounded to `NCCL_WIN_REQUIRED_ALIGNMENT` on ROCm only.** An unrounded backing allocation produced wrong `put_wait_signal` data and a teardown timeout. The registration size itself does not need to be a 4096 multiple. CUDA allocation size is not changed.

## Changes that affect the default path

Five fixes here are not under `USE_ROCM` and do change CUDA behavior. Each is a pre-existing defect in shared code that this PR restructures, or a direct consequence of one. Listing them explicitly because the rest of the PR is ROCm-scoped and a reviewer should not have to grep for the exceptions.

- **Reduce-scatter silently truncated blocks larger than 65535.** `ReduceScatterOffsetsInfo::dst_block_size` is a `uint16_t` and the host wrote `static_cast<uint16_t>(owned_sizes[j])` with no bound - the only prior check was on block *count* (`n_owned <= RS_MAX_BLOCKS_PER_RANK`). A taller shard reduced `owned_sizes[j] % 65536` rows and returned wrong data with no error. Now a host-side `TORCH_CHECK` (`nccl_reduce_scatter_offset.cu:341`), placed before the ROCm/CUDA launch split so both paths get it. Widening the field would change the shared struct layout. The inputs this rejects are exactly the ones that were already producing wrong results, so it cannot regress a correct program. It had no Python coverage at all; `test_reduce_scatter_offset_rejects_oversized_block` adds it, asserting both that the first oversized block raises and that the largest block that still fits reduces correctly.

- **Cached device comms survived a communicator replacement.** `register_comm` is last-write-wins, but a cached `ncclDevComm` is built from one specific host comm. When a successor process group registered a different comm under the same uid (restart-after-error), `get_devcomm` kept handing kernels devcomms naming a comm the registry no longer owned, and `~NCCLDevCommManager` would pass the *successor's* comm to `ncclDevCommDestroy` alongside a predecessor-built devcomm. Reachable on CUDA, which has registered under `getGroupUid()` since before this PR. `register_comm` now evicts `devcomm_registry_` on replacement (`nccl_devcomm_manager.hpp:275`); re-publishing the same pointer is not a replacement. Covered by `NCCLDevCommManagerTest.ReplacementRegistrationEvictsDevComms`, which also asserts a bystander group's devcomm survives, so a future refactor to a blanket `clear()` fails the test.

- **`get_devcomm` handed out a reference into a map it then unlocked.** `get_devcomm` and `register_devcomm` returned `std::optional<std::reference_wrapper<ncclDevComm>>` and released `mutex_` on return; both ops bound that as `ncclDevComm&` and used it as a kernel launch argument hundreds of unlocked lines later. The eviction above widens that window, so both now return `std::optional<ncclDevComm>` by value and the two call sites bind a copy (`nccl_all_to_all_nd.cu:183`, `nccl_reduce_scatter_offset.cu:218`). `ncclDevComm` is copied into the launch anyway, so this costs nothing. It is a signature change on a public-header class; `git grep` finds no other in-tree caller.

- **A late destructor could erase a live successor's registration.** `~ProcessGroupNCCL` unregistered by group uid alone (the key-only `unregister_comm` overload), so a predecessor destroyed after a same-uid successor registered would wipe the successor's entry and leave symmetric memory unable to resolve a communicator. It now goes through `unregisterSymmetricMemoryComm` (`ProcessGroupNCCL.cpp:299`), which calls the identity-safe `unregister_comm(uid, comm)` - a no-op unless that exact registration is still live. That overload already existed and had no callers; this PR wires CUDA to it. One residual stays open on CUDA and is documented at the call site: `ncclComm_t` addresses are recycled, so a successor handed the predecessor's address still compares equal. Closing that needs a generation token threaded through registration, which would change `NCCLDevCommManager`'s interface and add process-group state; this PR keeps the generation ROCm-side rather than reshaping a working CUDA path. The pointer check alone is strictly better than the key-only erase it replaces.

- **The one-sided ops dereferenced an unchecked `dynamic_cast`.** `nccl_put_signal` and `nccl_wait_signal` are schema'd over the `SymmetricMemory` base class, so a handle from another backend is a legal argument, and both used the cast result without testing it - a null deref. Now `TORCH_CHECK`ed (`nccl_extension.cu:372`, `:407`), matching what the sibling ops already did. `NCCLOneSidedOpHandleTypeTest::test_one_sided_ops_reject_foreign_handle` covers it.

Also visible on CUDA, but not behavioral: `#include <vector_types.h>` is dropped from `NCCLSymmetricMemory.cu` (nothing in that translation unit references a CUDA vector type, and the header does not exist on ROCm); `ProcessGroupNCCL` gains an unconditionally-declared `symmMemCommGenerationMap_`, populated only on ROCm - declaring it behind a macro would make the class layout differ across translation units; `nccl_dev_cap.hpp` only ever *adds* ROCm terms to its conditions, so the CUDA truth value of `NCCL_HAS_SYMMEM_SUPPORT` and `NCCL_HAS_SYMMEM_DEVICE_SUPPORT` is unchanged, and the `NCCL_HAS_DEVCOMM` / `NCCL_HAS_ONE_SIDED_API` hunk merges two byte-identical `#if` conditions into one block; plus a `<limits>` include, a `[[maybe_unused]]`, and `_is_nccl_symmem_available()`, which is additive and only used by the test suite to pick a skip predicate.

## Tests

`test/distributed/test_nccl.py` no longer carries a blanket `TEST_WITH_ROCM` skip on the symmetric-memory classes. The blanket skip is replaced by three narrower, individually-justified gates, all of which are no-ops on CUDA:

- `skip_if_rccl_symmem_not_compiled` - the build-time probe result, exposed to Python as `_is_nccl_symmem_available()`.
- `skip_if_rccl_lt_2_30_4` - the RCCL host device-API floor.
- `skip_if_mi350_rocm_lt_10_1` - MI350 on pre-10.1 ROCm only, because that is where the defect reproduced.

New coverage, all of it running on the preview label:

- `NCCLSymmetricMemoryLifecycleTest` (ROCm-only, 4 items) - retirement before abort, and stale-handle recovery across a same-name restart, each on both `nccl` and `nccl-legacy` (only `nccl-legacy` goes through stock `ProcessGroupNCCL::abortCommsFromMap`).
- `NCCLSymmetricMemoryCapabilityGateTest` (ROCm-only, 3 items) - the runtime device-API snapshot, and the `TORCH_NCCL_SYMM_MEM_DISABLE_CAPTURE_ALLOC` kill switch.
- `NCCLSymmetricMemorySubgroupTest` (ROCm-only, 1 item) - subgroup-first rendezvous in a fresh process.
- `NCCLSymmetricMemoryRestartTest` (**not** ROCm-gated, 2 items) - allocation after a default-PG restart, and a successor PG surviving its predecessor's teardown.
- `NCCLOneSidedOpHandleTypeTest` (**not** ROCm-gated, 1 item) - `put_signal`/`wait_signal` reject a non-NCCL handle instead of dereferencing a null `dynamic_cast`.
- `NCCLSymmetricMemoryTest::test_reduce_scatter_offset_rejects_oversized_block` (**not** ROCm-gated) - the `uint16_t` block bound. This one also runs on the CUDA `sm90-symm` job.

Plus `NCCLDevCommManagerTest::ReplacementRegistrationEvictsDevComms` (C++, **not** ROCm-gated) - devcomm eviction on communicator replacement, that eviction does not touch a bystander group, and that a predecessor's late retirement cannot unpublish its successor. That binary is built on both platforms but is not wired into any CI script, on `main` or here; see the CUDA coverage table below.

Still skipped on ROCm, each for a named reason: `test_nccl_symmem_rendezvous_subgroup` (RCCL hangs in `ncclRmaCeInit`'s bootstrap barrier when WORLD already holds a window), `test_put_wait_signal` and `test_nccl_symmem_signal_rank_out_of_bounds` (pre-existing ROCm skip), and `SymmMemCftHandleTest` (host-side CFT is not this PR).

### Preview is the only label with live coverage, and why

47 passed on gfx950 / ROCm 10.1 / RCCL 2.30.7. The 5 skips are the ones this PR deliberately keeps: `test_nccl_symmem_rendezvous_subgroup`, `test_put_wait_signal`, `test_nccl_symmem_signal_rank_out_of_bounds`, and the two `SymmMemCftHandleTest` cases.

The three ROCm 10.0 labels skip, but **not all for the same reason**, and the difference is the point:

| Label | Skip reason in the XML | Count |
|---|---|---|
| trunk mi350 | `MI350 symmetric memory requires ROCm 10.1 or newer` | 50 |
| trunk mi350 | ` NCCL_HAS_HOST_CFT (nccl_dev_cap.hpp:51-54) needs NCCL >=2.31.2` | 2 |
| mi300 / mi200 | `RCCL symmetric memory was disabled at build time; nccl_device.h did not pass the host-translation-unit compatibility probe` | 47 |
| mi300 / mi200 | `Capture-time symmetric allocation requires RCCL 2.30.7 or newer` | 3 |
| mi300 / mi200 | ` NCCL_HAS_HOST_CFT (nccl_dev_cap.hpp:51-54) needs NCCL >=2.31.2` | 2 |

Narrowing the version floor from a blanket ROCm gate to an MI350-only one did what it was meant to: MI200 and MI300 no longer skip on a version floor. They now fall through to the build-time gate, and that gate is the binding constraint - the `nccl_device.h` in those images does not compile in a host translation unit, so the feature is compiled out of the binary entirely and no test-side predicate can produce coverage there. Widening coverage past preview is therefore a matter of the periodic ROCm images carrying a qualifying RCCL, not of test gating.

trunk mi350 is the useful control for the remaining floor: it is the *same gfx950 hardware* as preview, on a ROCm 10.0 container, and it skips on exactly the MI350 predicate. That is the intended behavior of the narrowed gate.

The rebuild runs `ncclCommWindowRegister(..., NCCL_WIN_COLL_SYMMETRIC)`, which is collective, but the liveness test is rank-local. Gating on staleness would let a rank whose PG destructor has already run enter that collective while a rank still holding its predecessor does not — a one-sided hang, in exactly the restart-after-error scenario this is for.
