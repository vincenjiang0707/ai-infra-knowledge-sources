# [PR #194881] [DCP] Optimize FsspecReader with Batched cat_ranges and Async Prefetching

## 正文

## Problem
When loading distributed checkpoints (e.g., FSDP or Model Parallel) from object storage backends (like gcsfs or s3fs), the current `FsspecReader` processes byte intervals individually in a strictly sequential, single-threaded loop. This exposes several performance bottlenecks:
1. **Request Serialization**: Issuing thousands of individual HTTP range requests creates massive connection and latency overhead.
2. **Synchronous Starvation**: Because network I/O, `torch.load` unpickling, and tensor slicing occur sequentially on the main thread, the network stream is routinely starved while waiting for CPU deserialization.

## Solution
This PR introduces a concurrent, double-buffered pipeline and native batch range reading for `FsspecReader`:
- **Batched cat_ranges**:
  - Replaces per-item single range reads with a single `fs.cat_ranges(paths, starts, ends)` call per batch.
  - Range coalescing policy is left entirely to the storage backend. `FsspecReader` passes only paths, starts and ends, so backends that coalesce may do so under their own policy, and backends that do not are unaffected. No capability probing or argument-level fallback is required.
- **Double-Buffered Async Prefetching**:
  - Decouples network I/O from CPU deserialization: a dedicated single-threaded prefetch executor fetches batch k+1 while a multi-worker CPU thread pool deserializes batch k in parallel.
- **Configurable Batching & Concurrency**:
  - Exposes `max_batch_size` (default 64) to bound transient memory and `cpu_workers` to maximize deserialization throughput.

## Benchmark Results

### Skylion007 · 2026-08-27

This looks like a nice improvement. One question: are we duplicating any concurrency/caching machinery that fsspec already provides here?

In particular, cat_ranges() on async implementations such as gcsfs already issues the individual range reads concurrently through fsspec’s async machinery. I think the DCP-level pipelining still makes sense—we want to overlap fetching batch N+1 with deserialization/copy of batch N—but I am less sure we need configurable io_workers on top of that. Multiple threads calling cat_ranges() may just add another layer of concurrency around fsspec’s existing concurrency.

Similarly, I think cache_type="none" is actually the right choice here rather than using simplecache/filecache/blockcache: DCP already knows the exact ranges it needs, so readahead/block caching can fetch bytes we will never consume.

One thing that might be worth considering instead is coalescing/grouping ranges by checkpoint file before calling cat_ranges(), particularly for nearby ranges. That could reduce the number of HTTP range requests in addition to parallelizing them.

Also, hasattr(self.fs.fs, "cat_ranges") may not tell us whether the backend has an efficient batched implementation, since AbstractFileSystem itself provides a fallback cat_ranges() that can just call cat_file() serially.

So I wonder if the simpler model should be: let fsspec/backend own concurrency within a cat_ranges() batch, and have DCP own the higher-level pipeline between I/O and deserialization/copy, rather than adding another general I/O thread pool here.

## PR Review: #194881

### Summary
Adds batched `cat_ranges` + a double-buffered prefetch/deserialize pipeline to `FsspecReader`, and extracts `FileSystemReader._load_item` so both paths share deserialization. Two blocking issues: the fast path is not actually gated on backend capability (so it likely regresses sync backends), and deserialization is now multi-threaded against a `LoadPlanner` interface that documents no thread-safety guarantee.

### Thread Safety

- `_fsspec_filesystem.py:204-231` — `process_chunk` is submitted to a `cpu_workers`-wide pool, so `planner.load_bytes()`, `planner.resolve_tensor()`, and `planner.commit_tensor()` are now called concurrently from many threads. This was strictly sequential before. `LoadPlanner` documents no such contract — contrast `SavePlanner.resolve_data`, which explicitly promises "idempotency and thread-safety" (`planner.py:286`); the `LoadPlanner` docstring (`planner.py:324-327`) only says these are "called multiple times on each rank".

  This is not hypothetical for the default planner: with `flatten_state_dict=True` (the default, `default_planner.py:308`), `DefaultLoadPlanner.load_bytes` (`default_planner.py:383-389`) calls `set_element`, which walks and mutates shared nested containers via `cur_container.setdefault(...)` and `extend_list`'s `while len(lst) <= idx: lst.append(None)` loop (`_traverse.py:126-150`). Two threads landing on the same intermediate list/dict is a read-modify-write race.

  Worse for third parties: the `LoadPlanner` class docstring's own recommended extension pattern is `def commit_tensor(self, read_item, tensor): self.state_dict[read_item.dest_index.fqn] = tensor` (`planner.py:374-375`). Any planner written against that documented example is now called from N threads. `_ReaderWithOffset` (`optimizer.py:157-172`) and `DynamicMetaLoadPlanner` (`format_utils.py:162`) are in-tree subclasses in the same position.

  Pick one and make it explicit: either serialize the planner calls behind a lock (keeping `torch.load` — the actual CPU cost — parallel), or amend the `LoadPlanner` docstring in `planner.py` to state that `load_bytes`/`resolve_tensor`/`commit_tensor` must be thread-safe. Silently changing the contract of a public extension point is the part that needs to not ship. [Fix this →](https://claude.ai/code?q=On%20branch%20optimize-fsspec-dcp-load%2C%20in%20torch%2Fdistributed%2Fcheckpoint%2F_fsspec_filesystem.py%20around%20lines%20204-231%2C%20the%20new%20cpu_workers%20ThreadPoolExecutor%20calls%20planner.load_bytes%2Fresolve_tensor%2Fcommit_tensor%20concurrently.%20LoadPlanner%20documents%20no%20thread-safety%20contract%20(unlike%20SavePlanner.resolve_data%20at%20planner.py%3A286)%2C%20and%20DefaultLoadPlanner.load_bytes%20calls%20set_element%20which%20does%20non-atomic%20mutation%20of%20shared%20nested%20containers%20in%20_traverse.py%3A126-150.%20Serialize%20the%20planner%20calls%20behind%20a%20lock%20while%20keeping%20torch.load%20parallel%2C%20and%20document%20the%20contract%20in%20planner.py.&repo=pytorch/pytorch)

### Backward Compatibility

- `_fsspec_filesystem.py:66-68` — `kwargs.setdefault("cache_type", "none")` in `FileSystem.init_path` is a global default change affecting **every existing `FsspecWriter` and `FsspecReader` user**, not just the new read path. Three concerns:
  1. `cache_type` is an `AbstractFileSystem.open()`/`_open()` argument, not a filesystem-constructor argument. `url_to_fs(path, **kwargs)` routes these into `storage_options`, i.e. the constructor. So this most likely does nothing at all, and on backends that validate their `__init__` kwargs it could raise `TypeError`.
  2. fsspec caches filesystem instances keyed on storage options. Adding a kwarg changes the cache key, so PyTorch now gets a *different* fs instance than other code in the same process opening the same URL — surprising for users who pre-configure a filesystem.
  3. It applies on the write path too, where the stated rationale ("redundant memory copies during batched range reads") does not hold.

  If the intent is to avoid readahead on the new path, set it at `open()` time in the code that opens files, not as a global constructor default. I could not verify (1) and (2) directly — fsspec is not installed in this environment and network fetches were blocked — so please confirm against the `fsspec` version you tested with. Also note `requirements.txt:10` pins `fsspec>=0.8.5`, which is old enough that `cat_ranges` may not exist at the floor.

### Performance

- `_fsspec_filesystem.py:185` — `hasattr(self.fs.fs, "cat_ranges")` is not a capability check. `fsspec.AbstractFileSystem` defines `cat_ranges` for *all* filesystems, so this is always true and the `return super().read_data(plan, planner)` fallback at line 249 is dead code. Evidence from this PR itself: commit `1473d1af` deleted `type(self.fs.fs).cat_ranges is not fsspec.AbstractFileSystem.cat_ranges` — which only type-checks if the base attribute exists.

  The consequence is a likely **regression** for synchronous backends. `LocalFileSystem` and other sync filesystems inherit the base `cat_ranges`, which loops serially issuing a ranged `cat_file` per range — i.e. open+seek+read per read item. The old `FileSystemReader.read_data` opened each file **once** and sliced it (`filesystem.py:925-932`). So for local checkpoints and any non-async backend, this trades one open per file for one open per item, plus new thread-pool overhead, for zero I/O concurrency gain.

  This is exactly Skylion007's earlier point that `hasattr` "may not tell us whether the backend has an efficient batched implementation" — the removal of the probe in `1473d1af` addressed the `max_gap` argument but left the capability gap. Gate on something real: `isinstance(self.fs.fs, fsspec.asyn.AsyncFileSystem)`, or restore the `type(fs).cat_ranges is not AbstractFileSystem.cat_ranges` check. [Fix this →](https://claude.ai/code?q=On%20branch%20optimize-fsspec-dcp-load%2C%20torch%2Fdistributed%2Fcheckpoint%2F_fsspec_filesystem.py%3A185%20uses%20hasattr(self.fs.fs%2C%20%22cat_ranges%22)%20to%20gate%20the%20batched%20read%20path.%20fsspec.AbstractFileSystem%20defines%20cat_ranges%20for%20all%20filesystems%2C%20so%20this%20is%20always%20True%2C%20the%20super().read_data%20fallback%20at%20line%20249%20is%20dead%20code%2C%20and%20sync%20backends%20like%20LocalFileSystem%20fall%20into%20the%20base%20serial%20cat_ranges%20(one%20open%2Bseek%2Bread%20per%20item)%20instead%20of%20the%20old%20open-file-once-and-slice.%20Replace%20the%20hasattr%20check%20with%20a%20real%20capability%20check%20such%20as%20isinstance(fs%2C%20fsspec.asyn.AsyncFileSystem)%20or%20type(fs).cat_ranges%20is%20not%20AbstractFileSystem.cat_ranges.&repo=pytorch/pytorch)

- `_fsspec_filesystem.py:186-197` — batches are cut straight out of `plan.items` in plan order with no grouping or sorting, so one batch straddles multiple files and the offsets within a path are unordered. The PR explicitly delegates coalescing to the backend, but backend coalescing works on adjacent/sorted ranges per path — feeding it unsorted, file-interleaved ranges defeats it. Note the base `FileSystemReader.read_data` already groups by file (`filesystem.py:918-923`), and even carries a `# TODO sort by offset` at line 928. Sort by `(relative_path, offset)` before slicing batches.

- `_fsspec_filesystem.py:169`, `187` — `max_batch_size` bounds item *count*, not bytes, so the PR description's "bound transient memory" claim does not hold: 64 items of a large-shard checkpoint, doubled by prefetching, is unbounded in bytes. `item_md.length` is right there in the loop — bound the batch on cumulative bytes with a count cap as a secondary limit. Relatedly, `io.BytesIO(chunk_data)` at line 205 copies every chunk, which sits oddly next to the `cache_type="none"` comment about avoiding "redundant memory copies".

### API Design

- `_fsspec_filesystem.py:161-174` — `max_batch_size` and `cpu_workers` are new public constructor parameters with no docstring at all. `FsspecWriter.__init__` documents each of its arguments (`_fsspec_filesystem.py:128-141`); match that, and state the units/tradeoff for `max_batch_size` and the memory implication of prefetching.

- `_fsspec_filesystem.py:170-172` — `cpu_workers` defaults to `min(16, os.cpu_count() or 4)`. DCP load is per-rank, so on an 8-rank host this is up to 128 deserialization threads contending for the same cores plus whatever fsspec's own async pool is running. The comparable knob on the write side, `FileSystemWriter.thread_count`, defaults to `1` (`filesystem.py:597`). Default conservatively and let users opt into more.

- `_fsspec_filesystem.py:169-172` — `max(1, ...)` silently rewrites `max_batch_size=0` or `-100` to `1`. Raise `ValueError` instead; silently accepting nonsense hides caller bugs. (`test_fsspec_reader_clamp_max_batch_size` currently pins the silent behavior in place.)

- `filesystem.py:869-915` — `_load_item` was correctly extracted into the base class, but the batching/prefetch pipeline that consumes it lives entirely in `FsspecReader`. Nothing about it is fsspec-specific; a base-class pipeline parameterized by a "fetch these ranges" hook would let `FileSystemReader` and other subclasses benefit, and would give the thread-safety contract a single place to live. Worth considering before this shape ossifies.

### Testing

- `test_fsspec.py:259-299` — no test asserts the batched path was actually taken. `test_fsspec_reader_batched_cat_ranges` varies `max_batch_size` over `(1, 2, 64)` but only checks final tensor values, which the `super().read_data()` fallback also satisfies. Combined with the dead `hasattr` gate above, the entire feature could silently stop engaging and the suite stays green. Patch/spy `cat_ranges` and assert it was called `ceil(n_items / max_batch_size)` times with the expected `(paths, starts, ends)`.

- `test_fsspec.py:359-383` — `test_fsspec_reader_concurrent_shutdown` contains zero assertions: it wraps `dcp.load` in `try: ... except (Exception, CheckpointException): pass`. It can only fail by hanging. If the intent is "executors do not leak on failure", assert that — e.g. compare `threading.active_count()` before/after, or assert the pool threads are joined.

- `test_fsspec.py:301-305`, `385-388` — `test_fsspec_reader_clamp_max_batch_size` and `test_fsspec_reader_workers_config` only assert that constructor arguments were stored on the instance. That tests `__init__` assignment, not behavior; neither would catch a bug in how the values are used.

- No test exercises `cpu_workers > 1` over enough items to surface the planner race, and none covers the `LoadItemType.BYTE_IO` branch of `_load_item` concurrently — which is precisely the `set_element` path flagged under Thread Safety. A nested/flattened state dict with several `BytesIO` entries and `cpu_workers=8` would be the regression test for whatever mitigation you choose.

- `test_fsspec.py:350` — `assertRaises((Exception, CheckpointException))` is broad enough to pass on an unrelated failure such as a `TypeError` from a typo in the test body. `CheckpointException` derives from `BaseException` (`api.py:30`), so name only the type you expect. The `assertIn("simulated cpu crash", ...)` on the next line does most of the real work.

- Per `CLAUDE.md`: use `@parametrize` for the `for batch_size in (1, 2, 64)` loop rather than a bare loop (a failure at `batch_size=1` currently hides the remaining cases), and `self.assertEqual` rather than `self.assertTrue(torch.allclose(...))` at `test_fsspec.py:292-295`.

### Code Quality

- `_fsspec_filesystem.py:236-243` — `sys.version_info >= (3, 9)` is dead: `pyproject.toml:348` sets `requires-python = ">=3.10"`. Drop the branch, and with it the `import sys` at line 7, which exists only to serve it.

- `_fsspec_filesystem.py:207-243` — the `try/finally` shutdown duplicates work the `with` statement already does; `ThreadPoolExecutor.__exit__` calls `shutdown(wait=True)`. And `cancel_futures=True` has nothing to cancel: the loop blocks on `f.result()` for every CPU future before advancing (lines 230-231) and at most one prefetch future is ever outstanding. Delete the `finally` block and keep the `with`.

- `_fsspec_filesystem.py:233-234` — `del chunks` / `del b_reqs` do nothing: both are rebound at the top of the next iteration, and the completed `next_io` future holds the reference regardless. Remove.

- `_fsspec_filesystem.py:13-14` — `from torch.futures import Future` sits above `from fsspec.core import url_to_fs`, mixing first-party into the third-party block.

- `_fsspec_filesystem.py:177-181` — the empty-plan early return is redundant; `FileSystemReader.read_data` already handles an empty `plan.items` (empty `per_file`, loop body never runs, completed future returned).

- `_fsspec_filesystem.py:193` + `filesystem.py:875` — `self.storage_data[req.storage_index]` is looked up in the batching loop and again inside `_load_item`. Since `_load_item` needs it anyway, drop the local `item_md` binding at the call site or pass it through.

### Recommendation

**Request Changes**

The `hasattr` gate and the undocumented `LoadPlanner` concurrency change are the two that block: the first means sync backends silently get slower rather than falling back, and the second changes the contract of a public extension point without saying so. The missing "was `cat_ranges` actually called" assertion is what would let the first one regress unnoticed. The `cache_type="none"` default also deserves to be split out or dropped, since it touches every existing `FsspecWriter`/`FsspecReader` caller and is unrelated to the read optimization.
