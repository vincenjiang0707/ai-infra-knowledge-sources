# [PR #198532] [inductor][triton] 1/N UDTK Support aggregate types: Capture structured arguments for user-defined Triton kernels

## 正文

## Summary

This PR adds Python-wrapper support for recursively nested tuple and NamedTuple arguments to user-defined Triton kernels compiled through Dynamo and Inductor.

Kernel source remains unchanged: structured arguments are flattened while tracing, carried through Inductor as ordinary tensor/ scalar leaves, and reconstructed immediately before the Triton Python launcher call.

The full implementation is given below, but this feature will be added via stacked PRs. This PR adds FX literal metadata for tuple types. Dynamo flattens these types into the existing HOP argument and constant paths. The HOP reconstructs those values for eager dispatch and TTIR mutation analysis. Inductor aggregate launches remain explicitly unsupported in this PR.

## Full Implementation Notes

- Introduces FX-compatible aggregate metadata describing tuple and NamedTuple structure, leaf keys, field names, and explicit tl.constexpr nodes. This metadata is used in a similar way to how TMA descriptor metadata is used.

- Flattens aggregate arguments during Dynamo capture while preserving tensors, symbolic scalars, constants, and TMA descriptor metadata in their existing storage paths.
   - symbolic values that are wrapped with tl.constexpr are specialised

- Keeps Inductor dependencies, mutation tracking, scheduling, and buffer lifetimes based on flat leaves.
- Reconstructs aggregates for:
    - generated Python launcher calls;
    - TTIR generation;
    - compile-time autotuning;
    - Triton signature and constants construction.

- Adds recursive signature support for:
    - nested tensor and scalar types;
    - constexpr leaves and whole constexpr subtrees;
    - nested tt.divisibility and equal-to-one specialization paths.

- Supports empty, singleton, multi-element, and recursively nested plain tuples.
- Preserves NamedTuple field access using generated structural classes. Generated names use the form \_udtk_<8-character digest>_<original name> to avoid collisions between equal user-provided names with different layouts.
      - The exact user type name is not necessary to preserve as Triton does not preserve this information. Additionally user autotune arguments such as pre_hook / post_hook, config pruning is handled at the dynamo level where the exact user type is preserved.

- Shares structural NamedTuple construction across signature generation, wrapper codegen, and autotuner pickle reconstruction.
- Prevents generated structural classes from being treated as importable constexpr types while continuing to discover importable types in their fields.

- Extends functionalization to clone and return only mutated aggregate tensor leaves, including views, multiple mutations, and aliased leaves.

- Extends user-defined-kernel epilogue fusion to replace aggregate output leaves without mutating persistent reconstructed IR state.
- Supports compile-time autotuning for runtime aggregates, whole constexpr aggregates, nested constexpr aggregates, callable grids, pruning callbacks, performance models, and heuristics.

- Materializes tensor descriptors before aggregate reconstruction, including descriptors nested in NamedTuples.

Callers without aggregate arguments continue to pass an empty aggregate_type_metadata dictionary.

### Preserving explicit `tl.constexpr` wrappers in Dynamo

Storing a value in Dynamo's constant side table is not enough to determine whether the user explicitly wrapped that value in `tl.constexpr`. Ordinary Python constants and explicit `tl.constexpr` values can have the same payload, but Triton gives the wrapper semantic meaning during specialization. This distinction is especially important for aggregates because the wrapper may apply to one leaf or to a complete tuple or NamedTuple subtree.

Dedicated Dynamo tracking for the wrapper is added:

- `VariableBuilder` recognizes existing `tl.constexpr` instances, including values supplied through globals or closures, and wraps their payload in a `TritonConstexprVariable`.
- Calls to `tl.constexpr(...)`, using either the positional or `value=` form, are handled by a `TritonConstexprClassVariable` rather than tracing through and discarding the wrapper. Wrapping an already constexpr value is idempotent, matching Triton.
- Aggregate flattening records `is_constexpr` on the exact leaf or container spec before unwrapping the tracked payload. A parent constexpr marker applies to the complete subtree, but it is not copied onto each child; this preserves the difference between `tl.constexpr((a, b))` and `(tl.constexpr(a), b)`.
- Symbolic leaves below a constexpr node are specialized and guarded, and every leaf in that subtree must be representable as a Python constant. Tensor and tensor-descriptor leaves are rejected in a whole constexpr subtree.
- Reconstruction first rebuilds the complete marked leaf, tuple, or NamedTuple and only then reapplies `tl.constexpr`. This gives Triton the same structured constexpr value that appeared at the original call site.

Kernel parameters declared `: tl.constexpr` remain identified from Triton's kernel-parameter metadata. The new Dynamo variables preserve the separate call-site form where the argument or a nested value was explicitly constructed with `tl.constexpr(...)`.

## Supported scope

V1 supports:

- exact built-in tuples;
- NamedTuples;
- recursive combinations of tuples and NamedTuples;
- tensor and symbolic-scalar leaves;
- supported Python scalar constants;
- explicit scalar tl.constexpr leaves;
- aggregates or nested subtrees wrapped in tl.constexpr;
- kernel formals declared as whole tl.constexpr aggregates;
- GPU tensor descriptors where the backend provides the required TMA support.

NamedTuples are treated structurally at the Triton boundary. Their field names are preserved, but the original Python class identity, custom methods, and user-provided type name are not part of the compiled contract.

Aggregate support requires Triton’s V4 attrs-dict interface or later. Older Triton signature formats receive an explicit error.

## Explicitly unsupported

- Dataclasses and arbitrary tuple subclasses.
- Aggregate arguments with the C++ wrapper or AOTInductor. Can be handled in a follow up PR.
- Aggregate arguments through FX-wrapper code generation. Can be handled in a follow up PR.
- Aggregate formals named by Triton’s restore_value or reset_to_zero. Triton does not support aggregate types in these arguments.
- User pre_hook, user post_hook, and Config.pre_hook. Dynamo does not support these today.
- Tensor leaves inside a whole constexpr aggregate.
- Raw tl.dtype values in ordinary runtime aggregates; these must be explicitly constexpr to match Triton support.
- Preservation of the original NamedTuple class or its custom behavior.

These paths fail with targeted diagnostics rather than reaching incomplete lowering or launcher behavior.
