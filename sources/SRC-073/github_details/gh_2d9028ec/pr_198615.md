# [PR #198615] [XPU] make the device-wide wait in syncStreamsOnDevice opt-in

source: https://github.com/pytorch/pytorch/pull/198615
state: open | updated: 2026-09-25T11:00:52Z
labels: open source

## 正文

https://github.com/pytorch/pytorch/pull/191900/ made syncStreamsOnDevice() delegate to device_synchronization(), i.e. a device-wide ext_oneapi_wait_and_throw(), instead of draining the SYCL queues PyTorch owns. Those are two different contracts:
1. syncStreamsOnDevice - the work WE submitted on this device has finished
2. device_synchronize - all work by ANYONE on this device has finished

Every caller of syncStreamsOnDevice needs only the narrow one. The caching allocator calls it to make a block safe to reuse, and torch.xpu.synchronize() has always meant it on this backend. Routing them through the stronger wait makes them block on GPU work PyTorch neither owns nor tracks - on the allocator hot path, that means another library's kernels. This file's own comment states the narrow property: the legacy path "only drains queues we own; SYCL queues outside our pools are unaffected."

To be explicit, because the two arguments are easy to fuse: that is a SEMANTIC objection, not the explanation for the slowdown below. I measured whether the device-wide wait is blocking on foreign work here and it is not - after draining our own pool queues it finds only ~11us of anything left, and everything this process dispatches already runs on our streams (Triton included, via
torch.xpu.current_stream().sycl_queue). The contract mismatch matters for workloads that DO share the device with another SYCL component; it does not explain the numbers.

On ARC B580 (BMG/Xe2) this measurably regressed dynamo inference. Restoring the narrow wait is faster in five independent experiments.

Three of them run ONE binary and pick the path at runtime with the environment variable introduced below: one group of runs with it unset (narrow wait), one with it set to 1 (device-wide), the two groups alternating in blocks so that machine drift affects both equally. Nothing else differs between the groups - identical object code in the same install - so build nondeterminism, inlining and install state cannot contribute:
- one binary, env var unset vs =1, on nightly-20260805: faster by 4.86%
- one binary, env var unset vs =1, on current man: faster by 7.43%
- one binary, env var unset vs =1, repeated on main: faster by 8.37% The other two compile the tree twice from a single commit - once as-is, once with #191900 reverted - and compare the two binaries:
- two builds of nightly-20260805, revert vs as-is: faster by 7.42%
- two buidls of current main, revert vs as-is: faster by 4.51%

Measured on BlenderbotSmallForCausalLM, bs=2, --backend=inductor -n10 --cold-start-latency --float32, cold caches, 10-15 measured runs per group.

No mechanism is claimed, and the obvious one is ruled out: measured standalone, the device-wide primitive is CHEAPER than walking the 96 pool queues (~22us vs ~46us in an eager-like regime) and is O(1) in queue count where the walk is O(N). 13 hypotheses were tested and none held, including GPU clock and kernel-execution effects (device-side time is identical, 46 vs 45.9ms for identical work), roreign-queue work (there is none in this process), allocator behaviour (all 110 memory_states counters byte-identical between the two configurations), and cost displaced onto later kernel launches. The effect reproduces robustly; its cause is still open.

This PR keeps device_synchronize() and the fast path intact but makes taking it opt-in via TORCH_XPU_SYNC_STREAMS_DEVICE_WIDE=1, restoring the previous default. The flag is named for syncStreamsOnDevice.

On the planned deprecation: PR #182630 said syncStreamsOnDevice would be deprecated "when oneapi upgrade to 2026.1", and the TODOs here say to drop the latency fallback once a suitable driver is widely deployed. If these callers are rerouted to device_synchronize(0 they inherit a stronger contract they don't need. Separately,
syncl_ext_oneapi_device_wait is an *EXPERIMENTAL* extension whose specification states that shipping software products should not rely on it; deleting the fallback would make it the only synchronization path in PyTorch-XPU

Fixes: https://github.com/intel/torch-xpu-ops/issues/5150
