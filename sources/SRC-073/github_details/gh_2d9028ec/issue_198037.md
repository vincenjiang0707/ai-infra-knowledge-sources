## 正文

I'm building a llm for the purpose of learning using FlexAttentions, and noticed how it's slower than other approaches such as SDPA, codex also suggested a different kernel that it's claiming to be 3x the throughput in many attention scenarios. I'm fairly new to this and surprised that a gap like this could exist, so maybe it's missing something obvious, just thought it may still be useful to report.

> ## Summary
>
> **AI disclosure:** This report, the benchmark code, and the experimental patch

> measurements come from local benchmark executions, not AI estimates. The analysis

> an eager blockwise SDPA reference for equivalent sliding-window attention.

> ## Environment and reproduction
>
> - Apple M4 (10 GPU cores, 16 GiB), macOS 26.6.2 (25G83), Python 3.12.14 arm64.
> - PyTorch 2.14.0, git `08187d9e0fba026dc8217405802ab5381dc88d90`.
> - MPS fallback, fast-math and prefer-Metal environment flags unset.

> offset Boolean masks, not rectangular `is_causal=True`.

> <details>
> <summary>Self-contained reproduction (stock PyTorch; AI-assisted code)</summary>
>
> ```python
> """Stock PyTorch only. Apple Silicon MPS. Forward-only latency reproduction."""
> import random
> import statistics
> import time
>
> import torch
> import torch.nn.functional as F
> from torch.nn.attention.flex_attention import create_block_mask, flex_attention
>
>
> @torch.no_grad()
> def main():
>     assert torch.backends.mps.is_available(), "Run on an MPS-capable Mac"
>     print("torch:", torch.__version__, "git:", torch.version.git_version)
>     torch.manual_seed(91626)
>     B, H, T, D, W = 1, 8, 2048, 96, 256
>     q, k, v = [torch.randn(B, T, H, D, device="mps").transpose(1, 2)
>                for _ in range(3)]
>
>     def mask_mod(b, h, qi, ki):
>         return (qi >= ki) & (qi - ki < W)
>
>     mask = create_block_mask(mask_mod, None, None, T, T,
>                              device="cpu", BLOCK_SIZE=128).to("mps")
>     compiled = torch.compile(flex_attention, backend="inductor",
>                              fullgraph=True, dynamic=False)
>     methods = {"compiled_flex": lambda: compiled(q, k, v, block_mask=mask)}
>     for block_size in (128, 256):
>         blocks = []
>         for start in range(0, T, block_size):
>             end, left = min(T, start + block_size), max(0, start - W + 1)
>             distance = (torch.arange(start, end, device="mps")[:, None]
>                         - torch.arange(left, end, device="mps")[None, :])
>             blocks.append((start, end, left, (distance >= 0) & (distance < W)))
>
>         def blockwise(blocks=blocks):
>             return torch.cat([F.scaled_dot_product_attention(
>                 q[:, :, start:end], k[:, :, left:end], v[:, :, left:end],
>                 attn_mask=allowed, dropout_p=0.0, is_causal=False,
>             ) for start, end, left, allowed in blocks], dim=2)
>
>         methods[f"block_sdpa_{block_size}"] = blockwise
>     reference = methods["block_sdpa_256"]()
>     for fn in methods.values():
>         torch.testing.assert_close(fn(), reference, atol=8e-5, rtol=1e-3)
>         for _ in range(5):
>             fn()
>     torch.mps.synchronize()
>     samples = {name: [] for name in methods}
>     rng = random.Random(91626)
>     with torch.compiler.set_stance("fail_on_recompile"):
>         for _ in range(17):
>             names = list(methods)
>             rng.shuffle(names)
>             for name in names:
>                 torch.mps.synchronize()
>                 start = time.perf_counter()
>                 output = methods[name]()
>                 torch.mps.synchronize()
>                 samples[name].append((time.perf_counter() - start) * 1000)
>                 del output
>     for name, values in samples.items():
>         print(f"{name}: median={statistics.median(values):.3f} ms")
>
>
> if __name__ == "__main__":
>     main()
> ```

> ## Measurements
>
> **Stock-only reproduction:** FP32, B1/H8/T2048/D96, window256, sparse-mask
> block128. Median synchronized latency from 17 randomized rounds, five warmups:
>
> | Implementation | Latency |
> |---|---:|
> | Compiled FlexAttention | 30.196 ms |
> | Eager SDPA, query block128 | 3.398 ms |
> | Eager SDPA, query block256 | 2.706 ms |
>
> **Stock versus experimental FlexAttention:** selected matched-workload
> throughput results below combine the mask and dimension sweeps. Both are
> compiled; defaults are B1/H8/T2048, transposed layout, sparse-mask block128.
> Sliding-window rows use window256. Rates are **thousands of completed attention
> input tokens/s**, not generated tokens/s, and are measured separately from latency.
>
> | Run | Workload | Dtype / head width | Stock k tokens/s | Experiment k tokens/s | Ratio |
> |---|---|---|---:|---:|---:|
> | Q | Sliding window | FP16 / 96 | 153.69 | 492.76 | 3.21× |
> | Q | Full causal | FP16 / 96 | 50.16 | 177.41 | 3.54× |
> | Q | Dense | FP16 / 96 | 38.56 | 92.50 | 2.40× |
> | Q | Uneven packed documents | FP16 / 96 | 192.64 | 624.49 | 3.24× |
> | Q | Prefix LM | FP16 / 96 | 47.94 | 174.71 | 3.64× |
> | Q | Dense | FP16 / 256 | 2.87 | 36.30 | 12.64× |
> | L | Sliding window | FP32 / 96 | 62.27 | 529.80 | 8.505× [8.504–8.512] |
> | L | Sliding window | FP16 / 256 | 19.34 | 215.54 | 11.135× [11.032–11.155] |
> | L | Sliding window | FP32 / 512 | 5.50 | 61.52 | 11.246× [11.140–11.345] |
>
> - **Q — quick mask checks (September 21):** exact clean patch; one >=5-second
>   window per method, not repeated medians or confidence intervals.
> - **L — longer dimension sweep (September 19):** earlier prototype; seven
>   randomized >=10-second windows after bounded stabilization. Rates are medians;
>   paired ratios include IQR. Clean/prototype executable shader tokens matched
>   in 112 generation checks, which does not prove identical compiled performance.
> - Both use three resident input sets and synchronize after bursts of 16 calls.
>   Timing includes dispatch, allocation and synchronization, but excludes
>   compilation, mask construction and transfers. Throughput is `calls * B * T / seconds`.
>
> The broader prototype **regressed FP16/D32** (0.817× at B1; 0.758× at B4), so
> the clean patch excludes these cases. Full results, separate latency samples
> and bounded batch/queue searches with fresh 30-second confirmations are retained
> locally, not included in the patch attachment. Those operating points are **not**
> matched-workload speedups or demonstrated maximum throughput.
>
> ## Experimental change and limitations
>
> The rewrite assigns 128 threads to eight query rows, shares key work and
> distributes softmax/value accumulation across lanes. It retains tile-level
> online-softmax rescaling and uses vector QK dot products, not matrix-engine QK.
> Its provisional guard selects FP16/FP32 equal QK/V widths 48–768 with unit
> feature stride; other cases retain stock. This is evidence from one GPU,
> not a recommended universal dispatch rule.
>
> - All 13 corrected mask workloads passed both reference checks. The separate
>   clean-patch suite had 73 passes and two feature-strided cases failing for
>   both stock and experiment, with no new failures.
> - The first mask harness attempt failed its CPU oracle before timing; the
>   corrected transfer and failed records are retained. Tolerances were unchanged.
> - **GPU saturation is unverified:** Instruments profiling failed, so there is
>   no usable GPU timeline. The quick checks do not establish thermal stability;
>   the desktop was not exclusively reserved.
> - No backward, dynamic-shape, other-GPU or upstream-main binary validation.
>   Installed PyTorch files were unchanged; experimental tests used process-local
>   compiler hooks. The patch is not merge-ready.
