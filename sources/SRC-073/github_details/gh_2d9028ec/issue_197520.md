## 正文

### 🐛 Describe the bug

Calling `torch.xpu.empty_cache()` right after submitting a reduction (`index_add_`) that is fed by a long asynchronous kernel chain **silently corrupts the reduction result to all-NaN** on Intel Arc A-Series (Alchemist) / Windows. No error, no crash — the program keeps running with wrong data. The corruption is deterministic in the setup below (7/7 runs in separate processes).

This is the "silent wrong results" sibling of the `AssertHandler::printMessage` crash in #157714 (same workload, same hardware class; the crash itself is currently intermittent on this machine, the data corruption is not).

**Environment:** Windows 11, Intel Arc A730M, driver 32.0.101.8992, torch 2.14.0+xpu (Python 3.14).

**Reproducer (self-contained):**

```python
import torch

def _v2(x):
    lowbit = x & -x
    v = torch.round(lowbit.to(torch.float32).log2())
    return torch.where(x > 0, v, torch.zeros_like(v)).to(torch.int64)

def kronecker_chain(Dv, nf, rounds=160):
    a = torch.as_tensor(Dv, dtype=torch.int64, device=nf.device)
    if a.dim() == 0:
        a = a.expand(nf.shape)
    nabs = nf.abs()
    v2 = _v2(nabs)
    n_odd = torch.where(nabs > 0, nabs >> v2, nabs)
    res = torch.ones_like(n_odd)
    res = torch.where((v2 > 0) & (a % 2 == 0), torch.zeros_like(res), res)
    a8 = a % 8
    base8 = torch.where((a8 == 1) | (a8 == 7), torch.ones_like(res), -torch.ones_like(res))
    res = torch.where((v2 % 2 == 1) & (a % 2 == 1), base8.expand_as(res), res)
    m = torch.where(n_odd > 0, n_odd, torch.ones_like(n_odd))
    a_j = torch.where(n_odd > 0, a % m, torch.zeros_like(m))
    jr = torch.ones_like(m)
    for _ in range(rounds):
        active = a_j != 0
        tz = _v2(a_j)
        shifted = a_j >> tz
        m8 = m % 8
        flip = ((m8 == 3) | (m8 == 5)) & (tz % 2 == 1)
        a_j = torch.where(active, shifted, a_j)
        jr = torch.where(active & flip, -jr, jr)
        a_old, m_old = a_j, m
        a_j = torch.where(active, m_old, a_old)
        m = torch.where(active, a_old, m_old)
        flip2 = (a_j % 4 == 3) & (m % 4 == 3)
        jr = torch.where(active & flip2, -jr, jr)
        m_safe = torch.where(m != 0, m, torch.ones_like(m))
        a_j = torch.where(active, a_j % m_safe, a_j)
    jacobi_out = torch.where(m == 1, jr, torch.zeros_like(jr))
    res = res * jacobi_out
    out = torch.where(nf == 0, torch.where(a.abs() == 1, torch.ones_like(res), torch.zeros_like(res)), res)
    mult = torch.where(a < 0, -torch.ones_like(out), torch.ones_like(out))
    return torch.where(nf < 0, out * mult, out)

def heavy_block(dvals):
    counts = torch.tensor([D - 1 for D in dvals], dtype=torch.int64, device='xpu')
    seg = torch.repeat_interleave(torch.arange(len(dvals), dtype=torch.int64, device='xpu'), counts)
    n_rel = torch.arange(seg.numel(), dtype=torch.int64, device='xpu') - (torch.cumsum(counts, 0) - counts)[seg]
    start_n = torch.ones(len(dvals), dtype=torch.int64, device='xpu'); start_n[0] = 1
    nf = n_rel + start_n[seg]
    Dval = torch.tensor(dvals, dtype=torch.int64, device='xpu')[seg]
    chi = kronecker_chain(Dval, nf).float()
    logv = torch.log(torch.clamp(torch.abs(
        2.0 * torch.sin(torch.pi * nf.to(torch.float32) / Dval.to(torch.float32))),
        min=torch.finfo(torch.float32).tiny))
    return seg, chi * logv

def fundamental_discriminants(limit):
    out = []
    for D in range(2, limit + 1):
        if D % 4 == 1 and _squarefree(D):
            out.append(D)
        elif D % 4 == 0:
            m = D // 4
            if m % 4 in (2, 3) and _squarefree(m):
                out.append(D)
    return out

def _squarefree(n):
    d = 2
    while d * d <= n:
        if n % (d * d) == 0:
            return False
        d += 1
    return True

dvals = fundamental_discriminants(11000)          # 3342 discriminants, T ~10.3M elements
seg, prod = heavy_block(dvals)
S = torch.zeros(len(dvals), dtype=torch.float32, device='xpu')
S.index_add_(0, seg, prod)
torch.xpu.empty_cache()                            # <-- trigger
torch.xpu.synchronize()
print(S[0].item())                                 # nan (expected -0.962424...)
```

Output: `S[0] = nan`, and all 3342 entries of `S` are non-finite (`(~torch.isfinite(S)).sum() == 3342`).

### Expected behavior

`S[0] == -0.962424...` (the correct value; `empty_cache()` must not change already-computed results).

### Control experiments (same chain, same data)

| variant | result |
|---|---|
| no `empty_cache()` | correct (`-0.962424...`) |
| `S[0].item()` read before `empty_cache()` | correct — the D2H copy appears to drain the driver's deferred state |
| `torch.xpu.synchronize()` before `empty_cache()` | still corrupted (at least once; intermittent) |
| plain `index_add_` without the chain (10M/50M elements) + `empty_cache()` | correct |
| chain tensors dropped (function scope) before `empty_cache()` | correct — tensors must stay referenced |

The corruption depends on `empty_cache()` hitting the driver's deferred state left by the heavy chain, with the reduction's inputs still referenced. It is deterministic in the exact script above (7/7 separate processes), but sensitive to process history — likely the same family as the CUDA-side `empty_cache()`-frees-memory-with-queued-writers bugs #196257 / #196258, and it means any long-running XPU workload that calls `empty_cache()` risks silent data corruption.

Also on this hardware: the same chain with a *second* write to the same tensor crashes with `AssertHandler::printMessage` + SIGSEGV (see #157714; currently intermittent).

### chiangchenghsin-hash · 2026-09-18

I did a code-level pass on the allocator path to try to pinpoint where the corruption originates, since the reproducer is stable. Summary of what I found (torch 2.14 source, `c10/xpu/XPUCachingAllocator.cpp`):

**The torch-side free path looks correct by design:**
- `free()` recycles a block only after recording per-stream events (`insert_events`) for any `stream_uses`; single-stream blocks go straight to the free pool (same-queue in-order guarantees).
- `emptyCache()` → `release_cached_blocks()` first calls `synchronize_and_free_events()` and then `syncStreamsOnDevice(device)` (device-wide wait when `ext_oneapi_device_wait` is available, otherwise `wait()` on all 32×3 reserved pool queues) **before** any `sycl::free`.

**So all torch-level synchronization is already in place — and our experiments show it is not sufficient:**
- `torch.xpu.synchronize()` immediately before `empty_cache()` **still** corrupts (observed once in the same process configuration).
- A host read of the result (`S[0].item()`, a D2H copy) before `empty_cache()` **prevents** the corruption every time.
- Dropping the chain tensors to function scope (so their blocks sit in the cache) also prevents it.

A D2H copy forces the copy engine / host-visible path to retire deferred command-list state that `queue.wait()` apparently does not retire on this stack. That, combined with the fact that the corruption survives torch-level syncs, points **below torch**: at the SYCL/UR → Level Zero memory-management path (`zeMemFree` / deferred retirement) on Arc A-Series + Windows + driver 32.0.101.8992 — not at a missing sync in the PyTorch allocator code.

Two adjacent data points that may be the same underlying Windows/UR memory-management issue:
- #194418 (XPU caching allocator memory not returned to the driver on Windows; B580 user saw VRAM grow until OOM).
- On this machine, `empty_cache()` frees the blocks, but the freed USM allocations appear to interact badly with the driver's deferred state.

Suggested next steps on your side: run the reproducer with `ZE_ENABLE_DEBUG=1` / `ze_debug=1` or UR tracing to see what `zeMemFree` does to the queue state, and/or test on a newer driver. If you can confirm a driver-side root cause I'm happy to help bisect further (I can test driver versions or build a pure SYCL-level reproducer if that helps isolate torch vs runtime).

### chiangchenghsin-hash · 2026-09-18

Progress update with new control experiments — this narrows the fault layer further:

**1. Allocator block-reuse is ruled out.** In the reproducer, `S` is allocated *after* the heavy chain, so it could be reusing a cached block. I re-ran with `S` allocated *before* the chain (dedicated fresh block, no reuse possible): still all-NaN, 3/3. So `empty_cache()` freeing the chain's intermediate blocks corrupts **other live allocations** regardless of where they live — this is not a torch-caching-allocator bookkeeping issue.

**2. Pure-SYCL mirror is clean on the 2025.0 runtime.** I built a self-contained SYCL C++ program (oneAPI 2025.0) mirroring the pattern: in-order queue, ~160-round int64 kernel chain over 10M elements, scatter-add reduction, then `sycl::free()` of the intermediates — in both *immediate* (free without wait) and *synced* (wait before free) modes. Both: CLEAN, all outputs finite. So the simple pattern does not corrupt under the 2025.0 runtime.

**3. The two cross-cells could not be run locally, and why:** torch 2.14's binary (2026.1-built) crashes at load on the 2025.0 runtime (0xC0000005), and the 2026.1 SYCL headers require a Clang 20+ compiler while this machine only has Clang 19 (oneAPI 2025.0). So I could not directly test *"2026.1 runtime + simple pattern"* here.

Net picture: the corruption survives every torch-level synchronization (events + device-wide sync before `sycl::free`), is independent of block reuse, and does not appear under the 2025.0 runtime — pointing at the **2026.1 UR/Level-Zero memory-management path on Arc A-Series + Windows** (`zeMemFree`/deferred retirement corrupting live allocations). It would be very useful if someone with a Clang 20+ toolchain ran the SYCL mirror linked against the 2026.1 runtime (headers/libs in the pip `intel-sycl-rt` package) to close that cell; happy to share the ~120-line mirror program. Also worth trying `ZE_ENABLE_DEBUG=1`/UR tracing on the Python reproducer to see what `zeMemFree` does.

    while d * d <= n:
        if n % (d * d) == 0:
            return False
        d += 1
    return True

def fundamental_discriminants(limit):
    out = []
    for D in range(2, limit + 1):
        if D % 4 == 1 and _squarefree(D):
            out.append(D)
        elif D % 4 == 0:
            m = D // 4
            if m % 4 in (2, 3) and _squarefree(m):
                out.append(D)
    return out

dvals = fundamental_discriminants(11000)  # 3342 discriminants, ~10.3M elements
seg, prod = heavy_block(dvals)
S = torch.zeros(len(dvals), dtype=torch.float32, device='xpu')
S.index_add_(0, seg, prod)
torch.xpu.empty_cache()   # <- trigger
torch.xpu.synchronize()
val = S[0].item()   # <- DEVICE_LOST here (A770M) / silent all-NaN (A730M)
print(val)
