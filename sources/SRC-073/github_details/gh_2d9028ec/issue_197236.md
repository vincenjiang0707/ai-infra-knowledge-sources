# [Issue #197236] [MPS] linalg solves return row-major where CPU and CUDA return column-major

state: open | updated: 2026-09-24T20:00:40Z

## 正文

### 🐛 Describe the bug

`linalg.solve_triangular`, `cholesky_solve` and `linalg.solve` return a row-major result on MPS where CPU and CUDA return column-major. (makes for a runtime error -> see below)

```python
import torch

torch.manual_seed(0)
a = torch.randn(5, 5)
a = a @ a.T + 5 * torch.eye(5)
L = torch.linalg.cholesky(a)
B = torch.randn(5, 5)

for dev in ("cpu", "mps"):
    print(dev, torch.linalg.solve_triangular(L.to(dev), B.to(dev), upper=False).stride())
```

```text
cpu (1, 5)
mps (5, 1)
```

`cholesky_solve` and `linalg.solve` do the same. Values agree to ~6e-08.

Eager returns whatever the kernel produced and nothing checks that layout against a prediction, so this stays invisible in the eager suites. The compile path does catch it, but `instantiate_device_type_tests(TestInductorOpInfo, ...)` in `test/inductor/test_torchinductor_opinfo.py` doesn't produce an MPS class, so none of these ops are compiled on MPS in CI. Under `torch.compile` inductor bakes the meta's predicted stride into the generated code and it fails at runtime:

```text
AssertionError: expected size 5==5, stride 5==1 at dim=0; expected size 5==5, stride 1==5 at dim=1
Error in op: torch.ops.aten.linalg_solve_triangular.default
```

Eager users doing `.view()` or `.reshape()` on the result, or passing it to anything stride-sensitive, already get device-dependent behaviour today.

There are three layers to it:

1. The kernel ignores the output's strides. `linalg_solve_triangular_mps_impl` in `aten/src/ATen/native/mps/operations/LinearAlgebra.mm` calls `resize_output(out, ...)` then writes raw bytes through `getMTLBufferStorage(out)` with an `MPSMatrixDescriptor` whose `rowBytes` is `cols * elemSize`. That path is row-major only. It also means a caller-supplied non-row-contiguous `out` silently receives transposed data.

2. The C++ meta already carves MPS out. `TORCH_META_FUNC(_linalg_solve_ex)` in `aten/src/ATen/native/BatchLinearAlgebra.cpp:604`:

```cpp
auto result_strides = at::native::batched_matrix_contiguous_strides(
    result_shape, /*f_contig=*/A.device().type() != at::kMPS ? left : false);
```

with the same pattern for `LU_strides` on line 612. The Python meta `_linalg_solve_ex` in `torch/_meta_registrations.py:1901` is unconditionally F-contiguous. The two disagree and inductor uses the Python one.

3. The contract doesn't look like it's meant to be device-dependent. The Python metas, the C++ metas for the other linalg ops (`cholesky_ex`, `lu_factor_ex`, `lu_solve`, `inv_ex`) and eager probes of `cholesky` and `lu_solve` all agree on F-contiguous.

Reproduces with stock `torch==2.14.0` and a source build of `2.15.0a0+gitc5a3ee1` (main at c5a3ee18b93).
