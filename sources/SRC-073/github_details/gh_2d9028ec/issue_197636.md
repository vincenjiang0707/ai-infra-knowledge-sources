## 正文

## 🐛 Describe the bug

On macOS 15+, `torch.bmm` on MPS silently returns wrong values when the output has more than 2**32 elements and either input is a non-contiguous view, e.g. a transposed `k` in attention (`q @ k.transpose(-1, -2)`). No error or warning is raised. With contiguous inputs the same shapes are correct.

The shapes involved are realistic: attention scores `(B*H, L, L)` exceed 2**32 elements at, e.g., 32 heads × 4k context × batch 9. The case most likely to go unnoticed is batched feature extraction or probing on Apple Silicon, and attention-map analysis with `output_attentions=True` (which forces eager attention). There the corrupted activations can look like a mildly worse downstream metric rather than an obvious failure.

The reference in the script below is the CPU result for the same batch element.

```python
import torch

torch.manual_seed(0)
L, D = 256, 64
for B in (65536 - 16, 65536 + 16):  # output numel crosses 2**32 at B = 65536
    q = torch.randn(B, L, D, device="mps")
    k = torch.randn(B, L, D, device="mps")
    out = torch.bmm(q, k.transpose(1, 2))  # batch2 is a transposed (non-contiguous) view
    for i in (0, B - 1):
        ref = q[i].cpu() @ k[i].cpu().T
        err = ((out[i].cpu() - ref).abs().max() / ref.abs().max()).item()
        print(f"B={B} numel/2**32={B * L * L / 2**32:.4f} batch={i} rel_err={err:.2e}")
    del q, k, out
    torch.mps.empty_cache()
```

Output (torch 2.14.0, macOS 27.0, M2 Ultra):

```
B=65520 numel/2**32=0.9998 batch=0 rel_err=0.00e+00
B=65520 numel/2**32=0.9998 batch=65519 rel_err=0.00e+00
B=65552 numel/2**32=1.0002 batch=0 rel_err=1.51e+00
B=65552 numel/2**32=1.0002 batch=65551 rel_err=1.49e+00
```

Additional observations:

- Wrong results with a transposed `batch2` reproduce on torch 2.11.0, 2.12.1, 2.13.0 and 2.14.0. They appear at every batch index checked (0, 1, 32767, 65535, 65536, 65537, last), not only in the last tile.
- With `.contiguous()` inputs the same shape is correct on 2.11.0, 2.12.1 and 2.14.0 (rel_err 0). On 2.13.0 the contiguous case segfaults instead, which looks like a separate problem that 2.14.0 fixed.
- A non-contiguous `batch1` also gives wrong results on 2.14.0, and segfaults on 2.11.0.
- On 2.11.0–2.13.0, a later large `bmm` in the same process can segfault after the wrong-result call, so the strided read may also go out of bounds.
- The same failure reaches 4-D `torch.matmul(q, k.transpose(-1, -2))`, i.e. eager attention in HF `transformers` (found with DistilBERT, `(B, H, L, L) = (5712, 12, 256, 256)`).
- On macOS < 15 this shape raises `Tiling of batch matmul for larger than 2**32 entries only available from MacOS15 onwards`, so upgrading the OS turns a hard error into silently wrong output.

### Likely cause

`bmm_out_mps_impl` sends outputs larger than 2**32 elements to `tiled_bmm_out_mps_impl` (`aten/src/ATen/native/mps/operations/LinearAlgebra.mm`). That function takes the raw buffers via `getMTLBufferStorage` and builds `MPSNDArrayDescriptor`s from sizes alone, assuming a packed row-major layout. It never looks at the input strides. The code that materialises transposed views (`if (batch2.is_view() && !batch2.is_contiguous())`) runs only on macOS < 15, on the assumption that the strided kernels handle views on macOS 15+. The tiled path does not go through those kernels. The same structure is still on `main` as of 2026-09-16 (1943e23e).

A likely fix is to call `.contiguous()` on `batch1` and `batch2` before `tiled_bmm_out_mps_impl` (the call site already does `resolve_conj()`), or to raise an error for non-contiguous inputs.

### he-yufeng · 2026-09-19

Located the root cause on current main (`LinearAlgebra.mm`); the bug is not fixed there.

When the output numel crosses 2^32, `bmm_out_mps_impl` routes to the tiled path (`tiled_bmm_out_mps_impl`), handing the operands over with only `resolve_conj()` applied (line 1643-1646). Nothing makes them contiguous. The tiled path then builds `MPSNDArrayDescriptor`s with `preferPackedRows` and computes per-batch and per-tile buffer offsets assuming dense packing (`aArrayOffset = i * batchSize * aCols * aRows + ...`, lines 1554-1566). For `k.transpose(1, 2)` the batch stride still matches the packed assumption, but the intra-matrix strides are swapped, and the descriptor reads the buffer as packed anyway, so every tile is fed the wrong elements. Contiguous inputs work precisely because their layout is the packed layout, which matches your observation, including that every batch index is affected, not just the tail tile.

The non-tiled path next door is careful about the analogous cases: non-contiguous output on pre-26 macOS and gather-needing outputs fall back to `do_metal_bmm`, which honors strides (lines 1605-1615). The tiled entry has no equivalent guard for non-contiguous inputs.

On your follow-up (inputs >2^32 with a small output, contiguous): that takes the other branch, since the tiled gate keys on output size only. The non-tiled path's only 2^32 check is on output dims (1591-1594), so oversized inputs go straight into MPSGraph. I have not pinned the exact overflow point inside that path, so treat this half as inference, but the missing input-numel routing on the pytorch side is real either way.

Fix shape for defect 1: materialize packed operands before the tiled call (`batch1.contiguous()` is a no-op for already-packed inputs, so the common case keeps zero-copy and only the transposed/view case pays for the copy), or thread the true strides into the NDArray descriptors. The stride route avoids the extra copy but needs on-device verification of the MPSNDArray matmul under strided layouts; the contiguous route is provably correct from the layout rules alone. Happy to prepare the patch if a maintainer confirms the direction; I cannot run the >2^32 repro locally (24 GB machine), so device verification would need CI or your rig regardless.

### jniimi · 2026-09-21

**Follow-up: the backward pass is affected too — gradients are silently wrong while the forward result is correct**

I spent some time investigating this unusual MPS behavior, as it also affects my own research. While extending the measurements behind this issue, I found a case that the forward-only report above does not cover. I think it matters for triage because it affects training on configurations where inference is fine.

### What happens

For `y = torch.bmm(a, b)` with contiguous `a` of shape `(B, 256, 64)` and `b` of shape `(B, 64, 256)`:

- up to `B = 65536` (output = exactly 2**32 elements), `y`, `grad_a` and `grad_b` are all correct;
- at `B = 65537` and `65538` (output just above 2**32 elements), **`y` is correct, but `grad_a` and `grad_b` are silently wrong** in exactly the batches from index 65536 on, i.e. the batches that lie beyond element 2**32 of the upstream gradient. No exception, no warning, no NaN/Inf.

The wrong values are not noise. In every comparison over all elements, the wrong gradient batches equal the product formed with the upstream gradient read from the beginning again (flat index wrapped at 2**32): `grad_a[65536]` equals `G[0] @ b[65536].T`. This is the same pattern as the forward failure for a contiguous *input* above 2**32 elements reported above; here the large contiguous tensor is the upstream gradient, which has the size of the output. I can only observe values, so I state this as an agreement of values, not as a root cause.

With sliced operands the result is the same (forward correct, both gradients wrong). With a transposed operand, the forward output is wrong in every batch as already reported, and the gradients are wrong in the same last batches. fp32 and fp16 behave identically. With the input-side shape `(B, 256, 256) x (B, 256, 64)`, every run from `B = 32768` raises the `INT_MAX` error instead; for contiguous operands it is raised during the backward pass, after a successful forward pass.

### Minimal reproduction

Needs about 60 GB of unified memory.

```python
import torch

B, M, K, N = 65537, 256, 64, 256          # output (B, 256, 256) has 2**32 + 65536 elements
torch.manual_seed(0)
a = torch.rand(B, M, K, device="mps", requires_grad=True)
b = torch.rand(B, K, N, device="mps", requires_grad=True)
G = torch.rand(B, M, N, device="mps")      # upstream gradient, contiguous

y = torch.bmm(a, b)
grad_a, grad_b = torch.autograd.grad(y, (a, b), G)

def rel_err(x, ref):
    return ((x.double() - ref).abs().max() / ref.abs().max()).item()

for i in (0, B - 2, B - 1):                # batch B-1 = 65536 lies beyond element 2**32 of y and G
    ai, bi, Gi = a[i].detach().cpu().double(), b[i].detach().cpu().double(), G[i].cpu().double()
    print(f"batch {i:5d}  forward {rel_err(y[i].detach().cpu(), ai @ bi):.2e}"
          f"  grad_a {rel_err(grad_a[i].cpu(), Gi @ bi.T):.2e}  grad_b {rel_err(grad_b[i].cpu(), ai.T @ Gi):.2e}")

# what the last batch of grad_a equals instead: the product formed with batch 0 of G
G0, bl = G[0].cpu().double(), b[B - 1].detach().cpu().double()
print("grad_a[65536] vs G[0] @ b[65536].T :", f"{rel_err(grad_a[B - 1].cpu(), G0 @ bl.T):.2e}")
```

Output on PyTorch 2.14.0, macOS 27.0 (26A428), Mac Studio M2 Ultra 192 GB:

```
batch     0  forward 4.31e-07  grad_a 7.49e-07  grad_b 7.46e-07
batch 65535  forward 3.87e-07  grad_a 7.85e-07  grad_b 8.39e-07
batch 65536  forward 5.58e-07  grad_a 2.10e-01  grad_b 1.90e-01
grad_a[65536] vs G[0] @ b[65536].T : 7.10e-07
```

(With inputs uniform on [-1, 1], as in the systematic runs, the relative error of the wrong gradient batches is between 1.16 and 1.57.)

### How it was measured

- Systematic sweep of forward + backward: 604 runs on PyTorch 2.14.0 (two shapes, fp32/fp16, contiguous / `b` transposed / `a` transposed / sliced, batch sizes around 2**31 and 2**32 elements), every tensor judged against a float64 computation on the CPU, each run in a fresh process. 420 runs are correct in all three tensors, 40 are silently wrong in at least one, 144 raise.
- **Reproduced bit for bit on three configurations**: 
   - Mac Studio (M2 Ultra, macOS 27.0)
   - MacBook Pro (M2 Max, macOS 26.6.2)
   - the same MacBook Pro after upgrading to macOS 27.0. 
   All 592 backward runs outside calibration, and 6156 runs over all series, agree in every recorded quantity, including the value of the largest error. So this is not specific to one machine, one chip, or macOS 27.
- **CUDA control**: the same harness (same script hashes) on an A100 80 GB with PyTorch 2.14.0+cu130. All 568 backward runs are correct in all three tensors (largest relative error 1.5e-6 in fp32, 4.9e-4 in fp16), including `B = 65537` and `65538` for the shape above and the input-side runs from `B = 32768` that raise on MPS.
- The forward-only sweep on the A100 (1494 runs) is correct everywhere as well.

### Workaround

Until this is fixed, keeping every MPS tensor below 2**32 elements (splitting the batch before it reaches the device) avoids both the forward and the backward failure: the forward output has the size of the upstream gradient, so it is the first tensor to cross the limit.
