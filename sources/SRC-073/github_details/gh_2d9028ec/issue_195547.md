# [Issue #195547] ☂️ Missing shape checks result in out-of-bounds access of Tensor data

source: https://github.com/pytorch/pytorch/issues/195547
state: open | updated: 2026-09-25T02:18:54Z
labels: module: crash, module: error checking, triaged, module: sanitizers, module: correctness (silent), module: edge cases, module: mps, bot-triaged

## 正文

This is an umbrella tracking issue for a **class** of problems, not a single one: operators that are missing shape/size validation on their inputs and, as a result, index or write past the end of a tensor's storage (or past a metadata vector such as `padding` / `output_size` / `stride`). Under ASAN these show up as `heap-buffer-overflow` reads and writes; without a sanitizer they are
usually silent, occasionally a `SIGSEGV`, and in the worst case silent memory corruption of unrelated data.

### The shared root cause

Every report in this class has the same shape:

- An operator derives its iteration geometry from one argument (typically `input` or `grad_output` for a backward) and  dereferences other arguments (an output buffer, a running stat, a `weight`) **without checking that the second argument is actually of expected shape or even has the right number of dimensions.

The missing check is almost always a one-line `TORCH_CHECK` on a size or a list length. That is exactly what makes this class deceptive: each individual instance looks trivially fixable, but with the rise of LLMs fix often targets exactly the case/device it was reported against rather than problem at large.

Several classes of issues are duplicated into this one (often marked with `topic: fuzzer`) are often of hardening nature, not something typical PyTorch user will encounter during their normal development flow:
 - Issues reachable by calling a ATen ops directly with an  invalid inputs are likely already rejected by higher level abstractions this op supports.  For example, majority of the backward ops are expected to be invoked only thru autograd-generated call-sities, and imply that their forward arguments have already been validated by successful forward call.  I.e. they are real missing-validation bugs, but they are typically **not reachable thru public API usage**.
 - Issues involving extreme values(for example, convolution dilation of $2^{63}-1$) and/or empty tensors, where existing boundary check will fail due to the overflow or operation execution should finish early because there are no items to perform computation on.
 - Issues observable only under undefined behavior sanitizers (out-of-bound cast, add/mul overflows), which are often closely related to previous categories

### What we are asking for (please read before sending a PR)

**We are not looking for one PR per operator.**
A steady stream of PRs each adding a single `TORCH_CHECK` to a single kernel is not a good trade for this project: it is a large review burden, it only covers the operators someone happened to fuzz, it often adds redundant checks scattered across backend-specific kernels, and it leaves the same hole open in a very similar operator that has not been reported/fuzzed yet. Fixes of that shape are likely to sit unreviewed or be declined.

What we do want is a **holistic fix that closes the class at once**:

- Validation that happens it the correct location  (often **outside of the iteration loop**) and is **device-agnostic**-  checked once, before dispatch reaches any backend kernels, so most of in-tree get the fixe at once rather than each re-implementing (or forgetting) it.
- Validation **derived from the operator's schema / meta function** rather than hand-written per kernel, so that operators nobody has fuzzed are covered too.
- Concretely, this likely means continuing the **structured kernel migration**: structured ops already declare their shape contract in a `meta` function that runs before the impl, which is precisely the hook this class of bug needs.

Note on symptoms: a **divide-by-zero / floating-point exception** in a kernel usually
reflects the *same* missing boundary check as an out-of-bounds read — an unvalidated
zero-size or degenerate dimension reaching arithmetic that assumes it is positive. Whether
the defect surfaces as a SIGFPE or as an OOB access depends on where the bad value lands,
not on the root cause, so those reports belong here too.
