# [Issue #198584] torch.linalg.svdvals silently returns NaN for inf input while NaN input raises LinAlgError

## 正文

### 🐛 Describe the bug

### Description
torch.linalg.svdvals rejects a matrix containing NaN with LinAlgError: linalg.svd: The algorithm failed to converge because the input matrix contained non-finite values, but a matrix containing inf (equally non-finite) is accepted and returns NaN singular values, with no error or warning. NaN violates the documented contract that singular values are returned (non-negative) in descending order, and the NaN propagates silently into matrix_norm(..., 'nuc'), cond, matrix_rank and pinv. NumPy's linalg.svd(A, compute_uv=False), which the documentation names as the equivalent, raises LinAlgError: array must not contain infs or NaNs for both inputs.

### Steps to reproduce
```
import torch
print(torch.linalg.svdvals(torch.tensor([[float("inf")]])))   # tensor([nan])
torch.linalg.svdvals(torch.tensor([[float("nan")]]))          # LinAlgError: ... non-finite values
```

###  Expected
inf is rejected like NaN (the error message already says "non-finite values").

### Versions

Environment
PyTorch 2.14.0 (the latest release, CPU wheel) and 2.12.0, Python 3.12, Ubuntu 24.04, x86_64

### JingHao-Leon · 2026-09-25

Cross-platform datapoint on **torch 2.14.0, CPU wheel, Apple Silicon arm64 (macOS 26.5)**: the `LinAlgError` branch doesn't fire here at all — **both** inputs are accepted and silently return `tensor([nan])`:

```
inf input : accepted, returns [nan]
nan input : accepted, returns [nan]
```

So the inconsistent NaN-vs-inf rejection the report shows on x86_64 comes from platform LAPACK error surfacing, not from a uniform guard — on arm64 even the NaN case slips through. That strengthens the suggested fix: an explicit non-finite check before dispatch (matching NumPy's `linalg.svd`, which raises `LinAlgError` for both on every platform) is the only way to make this contract platform-independent. Either way, the silent `NaN` propagation into `matrix_norm(..., 'nuc')` / `cond` / `pinv` reported here is real on this build too.


### malfet · 2026-09-25

Duplicate of #71911. Thanks for the clear report — closing it in favor of the long-standing tracking issue, because the NaN-vs-inf split shown here comes from the underlying LAPACK, not from a PyTorch guard that forgets `inf`.

As @JingHao-Leon's datapoint above shows, on arm64 **both** inputs are silently accepted and return `nan`; the `LinAlgError` for NaN on x86_64 is surfaced by that platform's LAPACK. That backend dependence is exactly what #71911 describes (Reference-LAPACK changed SVD behavior on non-finite input, picked up by MKL 2022+ and OpenBLAS 0.3.15+), and its open question — *raise, or propagate inf/nan?* — is the one this issue asks.

For the record, the blast radius is wider than `svdvals`. On torch 2.13.0, CPU, arm64, for `A = [[inf, 1], [1, 2]]`:

| call | result |
|---|---|
| `linalg.svdvals(A)` / `linalg.svd(A).S` | `[nan, nan]` |
| `linalg.eigvalsh(A)` | `[nan, nan]` |
| `linalg.cond(A)` | `nan` |
| `linalg.matrix_rank(A)` | **`0`** |
| `linalg.pinv(A)` | **all zeros** |

The last two are the dangerous ones — they look like ordinary answers rather than errors.

@Ko496-glitch, if you want to work on this, #71911 is the place: the first step there is agreeing whether non-finite input should raise (as NumPy does) or propagate, and a device-agnostic `isfinite` check ahead of the LAPACK call would make the behavior uniform across platforms. Please follow #71911.
