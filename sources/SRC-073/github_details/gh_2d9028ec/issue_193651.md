# [Issue #193651] torchaudio is missing from the cu132 wheel index (only stale ≤2.2.0 wheels are listed)

source: https://github.com/pytorch/pytorch/issues/193651
state: open | updated: 2026-09-25T12:49:35Z
labels: module: binaries, triaged, bot-triaged

## 正文

## Describe the bug

`https://download.pytorch.org/whl/cu132/` publishes `torch` and `torchvision` for the current release train, but `torchaudio` is effectively absent from it. The listing is not empty — it contains 248 links — however every one of them is a legacy wheel (`≤ 2.2.0`), all uploaded on 2023-10-06, and none of them carries a `+cu132` local version or a modern ABI tag.

```console
$ curl -s https://download.pytorch.org/whl/cu132/torchaudio/ | grep -c '<a href'
248

$ curl -s https://download.pytorch.org/whl/cu132/torchaudio/ \
    | grep -oE 'torchaudio-[0-9]+\.[0-9]+\.[0-9]+' | sort -uV | tail -5
torchaudio-2.0.2
torchaudio-2.1.0
torchaudio-2.1.1
torchaudio-2.1.2
torchaudio-2.2.0

$ curl -s https://download.pytorch.org/whl/cu132/torchaudio/ | grep -cE 'cu13|cp313|cp314'
0
```

For comparison, the same index does serve the current versions of the other two packages: `torch-2.13.0+cu132` and `torchvision-0.28.0+cu132` install from it without problems.

This produces two distinct failure modes for anything that depends on `torchaudio`.

### 1. Resolution failure when the resolver is restricted to the cu132 index

`uv --torch-backend=cu132` routes all torch-family packages to that index. `vllm==0.27.1` hard-pins `torchaudio==2.11.0`, which the index does not have:

```console
$ uv pip install vllm==0.27.1 torch==2.13.0 torchvision==0.28.0 \
    --torch-backend=cu132 \
    --extra-index-url https://download.pytorch.org/whl/cu132 \
    --index-strategy unsafe-best-match

  × No solution found when resolving dependencies:
  ╰─▶ Because there is no version of torchaudio==2.11.0 and vllm>=0.27.1 depends on torchaudio==2.11.0, we can
      conclude that vllm>=0.27.1 cannot be used.
      And because you require vllm==0.27.1, we can conclude that your requirements are unsatisfiable.
```

### 2. Runtime failure when torchaudio is taken from PyPI instead

Dropping `--torch-backend` lets the resolver mix indexes: `torch`/`torchvision` come from cu132, `torchaudio` from PyPI. Installation succeeds, but the PyPI build of `torchaudio` is compiled against CUDA 13.0, so importing it next to a CUDA 13.2 `torch` raises:

```python-traceback
  File ".../transformers/audio_utils.py", line 58, in <module>
    import torchaudio
  File ".../torchaudio/_extension/__init__.py", line 36, in <module>
    _check_cuda_version()
  File ".../torchaudio/_extension/utils.py", line 124, in _check_cuda_version
    raise RuntimeError(
RuntimeError: Detected that PyTorch and TorchAudio were compiled with different CUDA versions.
PyTorch has CUDA version 13.2 whereas TorchAudio has CUDA version 13.0.
Please install the TorchAudio version that matches your PyTorch version.
```

The import is not opt-in from the user's side: `transformers` imports `torchaudio` as soon as it is installed, so any vLLM entry point dies immediately — even `vllm --version`.

## Expected behavior

Either of these would resolve it:

1. Publish `torchaudio` for the current release train into `/whl/cu132/`, built against CUDA 13.2, matching the `torch`/`torchvision` builds already served there.
2. If `torchaudio` is intentionally not built for CUDA 13.2, say so in the release notes and **remove the stale `≤2.2.0` wheels from that index**. Their presence is worse than an empty listing: the index looks populated, resolvers treat it as a valid source for the package, and the resulting error message (`there is no version of torchaudio==2.11.0`) points at the requirement rather than at the missing build.
