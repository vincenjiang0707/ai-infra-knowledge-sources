# [Issue #189971] [MPS] embedding_bag accepts index == num_embeddings and reads one row past the weight table

source: https://github.com/pytorch/pytorch/issues/189971
state: closed | updated: 2026-09-25T02:19:30Z
labels: triaged, module: correctness (silent), module: embedding, module: mps, bot-triaged

## 正文

### 🐛 Describe the bug

The MPS `embedding_bag` weight-index bounds check is off by one: the kernel
uses `> num_weights` instead of `>= num_weights`, so index exactly equal to
`num_embeddings` silently reads one row past the weight table. Backward can
apply the same invalid row as an out-of-range gradient write.

```python
import torch

# Weight table = first 5 rows of a 6-row buffer, so the out-of-bounds row
# (index 5 == num_weights) lands on known adjacent data big[5] = [15,16,17].
big = torch.arange(18.0).reshape(6, 3)
W = big.to("mps")[:5]                     # num_weights = 5, valid idx 0..4
idx = torch.tensor([5], device="mps")     # == num_weights
offs = torch.tensor([0], device="mps")
out = torch.nn.functional.embedding_bag(idx, W, offs, mode="sum")
torch.mps.synchronize()
print("MPS returned:", out.cpu().tolist())  # [[15.0, 16.0, 17.0]] -- the row past the table
```

Index 6 correctly raises (`Index 0 is out of bounds: 6, range 0 to 5`),
pinning the failure to exactly the equality boundary. CPU raises for index 5.
Output on a source build of current main (2.14.0a0+git2662808); also
reproduces on 2.13.0 stable.

The guard is at
https://github.com/pytorch/pytorch/blob/26628087023e5102381849e9a27c3f09b6d485a4/aten/src/ATen/native/mps/kernels/EmbeddingBag.metal#L185-L194
-- `static_cast<uint32_t>(weight_idx) > num_weights` passes `weight_idx ==
num_weights`, and the subsequent row read uses it unchecked.

History: #163630 reported missing index validation and #168930 added this
check, but with `>` rather than `>=`; its regression test used index 6
against a 4-row table, which does not cover the equality boundary.

### Versions

PyTorch 2.14.0a0+git2662808 (source build of main) and 2.13.0; macOS 26.5.2 (arm64), Apple M5 Max, Python 3.12.13.

## 评论 (2)

### CodersAcademy006 · 2026-07-16

Confirmed the off-by-one in `EmbeddingBag.metal:186`:

```cpp
if (weight_idx < 0 || static_cast<uint32_t>(weight_idx) > num_weights) {
```

Valid rows are `0 .. num_weights-1`, so `weight_idx == num_weights` must be rejected, but `> num_weights` lets it through and the kernel then reads row `num_weights`, one past the table. Changing this to `>= num_weights` matches the CPU/CUDA bounds and fixes both the forward read and the mirrored backward gradient write. Worth checking the padding-idx comparison a few lines down for the same `>` vs `>=` while touching it. @malfet
