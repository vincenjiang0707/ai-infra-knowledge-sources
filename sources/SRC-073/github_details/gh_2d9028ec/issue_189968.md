# [Issue #189968] [MPS] index_copy_ does not validate indices and silently writes out of bounds

source: https://github.com/pytorch/pytorch/issues/189968
state: closed | updated: 2026-09-25T02:19:17Z
labels: module: crash, module: error checking, triaged, module: mps, bot-triaged

## 正文

### 🐛 Describe the bug

`index_copy_` on MPS performs no bounds check on index values. An out-of-range
or negative index silently writes outside the tensor instead of raising like
CPU (or CUDA's device assert). With views the write lands at a deterministic
spot in the backing storage; with whole tensors it corrupts adjacent
allocations.

```python
import torch

storage = torch.zeros(64, device="mps")
v = storage[:5]
v.index_copy_(0, torch.tensor([8], device="mps"), torch.tensor([999.0], device="mps"))
torch.mps.synchronize()
print("storage[8]:", storage[8].item())  # 999.0 -- written 3 elements past the view

storage2 = torch.zeros(64, device="mps")
v2 = storage2[8:13]
v2.index_copy_(0, torch.tensor([-1], device="mps"), torch.tensor([555.0], device="mps"))
torch.mps.synchronize()
print("storage2[7]:", storage2[7].item())  # 555.0 -- written before the view

torch.zeros(5).index_copy_(0, torch.tensor([8]), torch.tensor([999.0]))  # CPU: IndexError
```

Output on a source build of current main (2.14.0a0+git2662808); also
reproduces on 2.13.0 stable:

```text
storage[8]: 999.0
storage2[7]: 555.0
IndexError: index_copy_(): index 8 is out of bounds for dimension 0 with size 5
```

The non-contiguous (strided) kernel path reproduces as well, and an
out-of-range index on a whole tensor was observed corrupting a separately
allocated tensor. Negative indices are rejected by CPU `index_copy_` but MPS's
strided kernel wraps them once and writes.

The host dispatch never encodes the shared index bounds check that
`index_add_` and `index_select` already use
(https://github.com/pytorch/pytorch/blob/26628087023e5102381849e9a27c3f09b6d485a4/aten/src/ATen/native/mps/operations/Indexing.mm#L543-L554),
and the kernels use the index directly:
https://github.com/pytorch/pytorch/blob/26628087023e5102381849e9a27c3f09b6d485a4/aten/src/ATen/native/mps/kernels/Indexing.metal#L639-L684

### Versions

PyTorch 2.14.0a0+git2662808 (source build of main) and 2.13.0; macOS 26.5.2 (arm64), Apple M5 Max, Python 3.12.13.

### CodersAcademy006 · 2026-07-16

The gap is that `index_copy_out_mps` (`aten/src/ATen/native/mps/operations/Indexing.mm`, ~L224) dispatches straight to the `index_copy_{}_{}_{}_{}` kernel (~L288) without ever validating the index values against `dim_size = result.size(dim)` (which it already computes at ~L291). It does the size/shape checks (L234-264) but no value-range check, so an out-of-range or negative index becomes a raw out-of-bounds store, unlike CPU (which raises) or CUDA (device assert). Notably this file already ships a bounds-check kernel, `index_check_bounds_{}` (~L548), used by other indexing paths — routing `index_copy_` through the same check (or asserting `0 <= idx < dim_size` in the kernel) would close this consistently with the rest of the module. @malfet
