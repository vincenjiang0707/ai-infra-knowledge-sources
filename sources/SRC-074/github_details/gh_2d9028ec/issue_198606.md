# [Issue #198606] [inductor][cpu] int64 vector multiply is signed overflow on AVX2: (x * x) % 72 and (x * x) // 72 are wrong when the square wraps

## 正文

### 🐛 Describe the bug

```python
import torch


def f(x):
    return (x * x) % 72, (x * x) // 72


x = torch.full((8,), 2**62 + 1, dtype=torch.int64)
print(f(x))
print(torch.compile(f)(x))
```

Eager gives 65 and -128102389400760776 in every element, compiled gives 9 and 128102389400760775. 2.14.0 and the 21 Sep nightly, CPU, gcc 13.3, AVX2 (an i7-12700 and an i5-1240P). CUDA is right. `x * y` with `y` a tensor holding the same values is right, and so are `config.cpp.simdlen = 1`, `-fwrapv` and `-O0`.

On AVX2, `Vectorized<int64_t>::operator*` in aten/src/ATen/cpu/vec/vec256/vec256_int.h multiplies lane by lane with a signed `int64_t` multiply, and the comment above it says the UB is ignored on purpose. In eager each op is its own kernel. In the C++ Inductor generates, the multiply is inlined next to `remainder_integral` and the integer floor division, which also work lane by lane, and gcc uses `x * x >= 0`: it drops the sign fixup and divides unsigned. `x * x` is 2**63 + 1 read as unsigned, and (2**63 + 1) % 72 is 9. The scalar path is right because `CppOverrides.mul` goes through the unsigned type (`arith_promoted`, from #191132, which left the vector ops out of scope); `CppVecOverrides.mul` emits `a * b`.

Doing the lane multiply in `uint64_t` in vec256_int.h makes both right and compiles to the same `imul`. I have it with a test and can open a PR. Same kind of UB as the neg in #198555.

Read both sides of this. Your mechanism is right, and it narrows to one site: `_mm256_mullo_epi64` doesn't exist, so `Vectorized<int64_t>::operator*` on AVX2 goes through the `emulate()` lambda with a signed multiply — that's where gcc learns `x * x` can't wrap and rewrites the neighboring division to unsigned. The AVX-512 path (`_mm512_mullo_epi64`) wraps by hardware, and the scalar codegen already does the unsigned cast from #191132. So the lane multiply in `uint64_t` inside that lambda fixes every consumer of the operator, and `__ubsan_ignore_undefined__` can come off it.

Unless you're already writing it, I'll take this with the uint64 lane multiply plus an inductor CPU regression test of your repro (red on this build, green after).
