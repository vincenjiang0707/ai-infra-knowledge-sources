## 正文

Stack from [ghstack](https://github.com/ezyang/ghstack/tree/0.15.0) (oldest at bottom):
* #198706
* #198704
* #198703
* #198700
* __->__ #198705

_linux-build.yml discards a `runner` input that does not start with `l-` and
falls back to a default pod, so the EC2 labels its callers pass have not
selected anything since the ARC switch. Three callers also pass an
already-prefixed `mt-l-` label, which fails the same test while looking
correct -- `runner_prefix` supplies the prefix, so the label has to be bare.

Rather than start honouring those labels, which would change what 30 builds
run on, each caller now names the pod it already resolves to. For 26 of them
that pod is the input default, so the line is simply dropped rather than
repeating the default; the four arm64 callers name their pod because it
differs.

The default itself was `linux.c7i.2xlarge`, which resolved the same way; it is
now that pod by name. With every caller resolving to a pod, `runs-on` collapses
to the prefix plus the runner.

Whether some of these should have the larger box they nominally asked for is
now a visible question rather than one buried in an expression.

No job changes runner.

<summary>Extended analysis (ai-generated section)</summary>

**What this changes**

Every `_linux-build.yml` caller now names the ARC pod its build runs on, and `runs-on` collapses to `${{ inputs.runner_prefix }}${{ inputs.runner }}`. The expression it replaces discarded any `runner` value not starting with `l-`, so the EC2 labels callers passed had selected nothing since the ARC switch. Twenty-six callers drop the `runner:` line and fall through to the input default, which becomes `l-x86iavx512-8-64`; four arm64 callers write `l-arm64g4-16-62` because they resolve elsewhere. No job moves pod.

**What it gets right**

The "no job changes runner" claim survives checking. Every deleted label starts with `li`, not `l-`, and contains no `arm64`, so the old expression already collapsed all 26 to `l-x86iavx512-8-64`; `l-arm64g4-16-62` is exactly what the `contains(inputs.runner, 'arm64')` branch produced for the four arm64 callers. Deleting an expression that silently substituted a pod for whatever the caller asked for is the right direction, and the mis-sizing it concealed is now a line in a file rather than a branch in a ternary.

**Where the risk is**

The findings concentrate in two places and share one root. The first is `_linux-build.yml:165` and the input declared just above it: six findings land there, and one edit settles them — the description still reads "Label of the runner this job should run on" while the value is now interpolated verbatim and must be a bare pod name, and nothing in the workflow, in actionlint, or in the lint adapters checks it. That six independent passes converged on this one line is itself the signal; the input's accepted vocabulary narrowed and neither the prose nor any guard moved with it.

The second is comment rot: five findings on `inductor-perf-test-nightly-h100.yml:103-106` and `inductor-perf-test-nightly.yml:88`, where blocks written to justify a `runner:` line now sit above `build-environment:` and describe nothing.

The root under both is that the build pod bypasses `.github/arc.yaml` while the test matrix in the same job goes through `map_ec2_to_arc.py`. That is what makes the default finding matter: `arc.yaml` maps six of the deleted labels to much larger pods, and deleting the declaration rather than translating it removes the only in-repo record of what these builds were sized for. It is also why the arm64 literals are worth noting — `trunk.yml:467` pins the build to the g4 pod while its test matrix still names `linux.arm64.m7g.4xlarge`, which resolves to g3. The recurring mistake is discarding a declaration instead of translating it, and the orphaned comments compound it by erasing the rationale alongside the label.

**Before merge, and after**

Before: settle the sizing question the change surfaces. The `l-x86iavx512-8-64` default giving 26 builds 8 vCPU and 64 GiB, in `_linux-build.yml` and its callers, is a per-call-site decision rather than a one-line fix, and the same answer determines whether the orphaned comments in `inductor-perf-test-nightly-h100.yml` and `inductor-perf-test-nightly.yml` get deleted or get a pod. Also cheap now: the stale `runner` description, and the PR body's claim that three callers pass an already-prefixed `mt-l-` label — no caller does.

After: the enforcement half of the input contract, whether a lint adapter, a guard step, or routing `inputs.runner` through `arc.yaml`; and the `l-arm64g4-16-62` literal duplicated across four callers with nothing tying it to the table.
