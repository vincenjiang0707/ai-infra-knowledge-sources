# [PR #194093] [inductor] Fix Triton reduction CSE for logical arg indices

## 正文

## Summary

Include the logical reduction index in Triton's reduction CSE cache key.

This addresses the remaining Triton cache-key blocker described in #193661 and on #193680: two arg reductions can operate on the same value expression while using different logical index mappings. Caching only by `(src_dtype, reduction_type, value)` can therefore incorrectly reuse one reduction for the other.

The C++ codegen already includes the logical index in its reduction cache key. This change makes Triton follow the same rule.

## Regression

Add focused CUDA/Triton coverage that compiles `x.argmax()` and `x.t().argmax()` in the same graph. They share the same underlying values but require different logical indices, directly exercising the reduction-CSE collision.

## Context

This PR previously targeted the narrower adaptive-average-pool symptom from #193492. That issue was closed in favor of the broader logical-vs-physical reduction indexing problem in #193661. The branch is repurposed to address the explicit Triton CSE blocker for the broader fix in #193680.

### Context I verified

- `torch/_inductor/codegen/cpp.py:2484-2488` and `cpp.py:3276-3278` already build `reduction_key` exactly this way, so the change is a faithful port of the established rule to Triton. Good.
- `ReductionCacheKey` (`torch/_inductor/codegen/common.py:2060-2064`) is `tuple[torch.dtype, ReductionType, CSEVariable | tuple[CSEVariable, ...]]`, so the nested-tuple key type-checks without touching the alias.
- `cast` is already imported at `triton.py:19`.
- The collision is plausible: for a transposed arg-reduction, Inductor is free to load the buffer with a flattened contiguous index (reordering the reduction is legal for the *value*), so `value` can CSE to the same var as the untransposed reduction while only the returned *index* differs. That's precisely what `logical_index` carries, and the old key dropped it.
- Other backends (`halide.py:1346`, `mps.py:655`, `pallas.py:3318`) use the same 3-tuple key, but `_make_reduction_inner` only emits the tuple form when `is_triton(x) or (cpu and config.cpu_backend == "cpp")` (`lowering.py:7280-7282`), so they can't receive a `logical_index` today. No parallel fix needed — just noting it, since that guard is the only thing keeping them correct.

### Main concern: the regression test is unvalidated and possibly a no-op

The PR description states validation was only:

```
python -m py_compile torch/_inductor/codegen/triton.py test/inductor/test_triton_reduction_cse.py
git diff --check
```

`py_compile` proves the file parses; it proves nothing about the test catching the bug. Two specific risks:

1. **The reduction cache is per-kernel.** If `x.argmax()` and `x.t().argmax()` are scheduled into two separate Triton kernels, `self.cse.reduction_cache` is never shared and the test passes identically with and without the patch. The test needs to establish that both reductions land in one kernel — e.g. via `run_and_get_triton_code` plus an assertion that two distinct `triton_helpers.max_with_index` calls are emitted, or at minimum an inline comment explaining why fusion is guaranteed here.

2. **The test discriminates the wrong axis.** For contiguous `x`, `should_compute_logical_index` is `False` (`lowering.py:7298-7304`: `StorageBox`/`Buffer` with a contiguous layout), so `x.argmax()` produces a bare `value` and `x.t().argmax()` produces `(value, logical_index)`. The two keys therefore already differ *structurally* — `(dt, rt, value)` vs `(dt, rt, (value, li))`. What the PR body describes as the bug ("two arg reductions ... using different logical index mappings") is the case where **both** carry a logical index but a *different* one, and that case isn't covered. Worth adding a pair where both sides are non-contiguous views with distinct index mappings (e.g. `x.t().argmax()` alongside a strided slice like `x[:, ::2].argmax()`), or stating explicitly that the present-vs-absent case is the only reachable one.

Please run the test on a GPU box both with and without the `triton.py` hunk and report the before/after. If it passes at base, it isn't a regression test.

### Test placement duplicates existing coverage

`test/inductor/test_torchinductor.py:19048-19083` already has `test_triton_argmin_argmax_transpose_logical_index`, which covers `(x.t().argmin(), x.t().argmax())`, permutes, strided slices, and column-major inputs via `self.common`. A whole new top-level file for one test fragments that coverage and duplicates the harness. Folding the case into that existing test is the smaller change and gets CPU/`cpp`-backend coverage for free — relevant since `cpp.py` implements the same rule.

Related: the test currently hardcodes `GPU_TYPE` rather than using `instantiate_device_type_tests`, which CLAUDE.md asks for on numerics tests. Defensible for a Triton-codegen-specific test, but reusing `self.common` in the existing test sidesteps the question.

### Code style nits (`torch/_inductor/codegen/triton.py:5559-5563`)

```python
if logical_index is not None:
    logical_index_key = cast(CSEVariable, logical_index)
    cache_key = src_dtype, reduction_type, (value, logical_index_key)
else:
    cache_key = src_dtype, reduction_type, value
```

- The `cast` is a no-op that buys nothing here. `value` is declared `CSEVariable | tuple[CSEVariable, ...]` at `triton.py:5351`, so after `value, logical_index = value` the checker already knows `logical_index` is a `CSEVariable`. Note `cpp.py:3270-3277` guards the cast with a real `isinstance` assertion; this copy took the cast without the check, which is the worse half of the pattern. Either drop the cast or add the assertion.
- Without the cast the whole thing collapses to one line, which reads better and matches the original:
  ```python
  index_key = value if logical_index is None else (value, logical_index)
  cache_key = (src_dtype, reduction_type, index_key)
  ```
- The removed line had explicit parens (`cache_key = (src_dtype, ...)`); the replacements drop them. Minor, but keep the original form.
- Optional: this key construction now appears three times (here, `cpp.py:2484`, `cpp.py:3276`). A shared helper in `common.py` next to the `ReductionCacheKey` alias would keep the two backends from drifting again — which is exactly the failure mode this PR is fixing.

### Coverage gap

The key is shared by `argmax_value` / `argmin_value` / `argmax_with_value` / `argmin_with_value` (`triton.py:5436-5451`), all of which take the tuple form. A `torch.max(x.t(), dim=...)`-style case alongside the plain `argmax` would exercise the `_with_value` path through the same key.

### Not blocking

- Branch name (`fix/inductor-adaptive-pool-noncontiguous`) no longer matches the content; the PR body already explains the repurposing, so this is cosmetic.
- Dr. CI's two "new failures" (`mobilenetv2_100`, `vit_base_patch16_siglip_256`, both `eager_fail_to_run`) reproduce on trunk and are unrelated to this change.

### Verdict

The codegen change is the right fix and I'd support it. Before merge I'd want: (1) evidence the test fails without the patch, (2) the test folded into `test_triton_argmin_argmax_transpose_logical_index`, and (3) the redundant `cast` dropped.
