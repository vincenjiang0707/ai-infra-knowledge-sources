### Answer to @ezyang: "Why does this change need coding at all?"

- [x] Read the diff (`torch/csrc/utils/cpp_stacktraces.cpp`, `test/test_cpp_extensions_jit.py`, `docs/source/distributed.md`)
- [x] Check how `TORCH_DISTRIBUTED_DEBUG` is already parsed and where the coupling could live
- [x] Answer the question

**Short answer: it doesn't — at least not here.** The behavior this PR wants ("DETAIL implies C++ stacktraces, unless explicitly set to 0") already falls out of existing machinery, so the new C++ in `cpp_stacktraces.cpp` is redundant.

**1. The generic util shouldn't know about a distributed env var.**
`torch/csrc/utils/cpp_stacktraces.cpp` is a core, non-distributed utility. The PR makes it read `TORCH_DISTRIBUTED_DEBUG` and re-implement the case-insensitive `"DETAIL"` parse that `c10d::detail::loadDebugLevelFromEnvironment()` already does in `torch/csrc/distributed/c10d/debug.cpp:20-51`. That's a duplicated parser and a backwards layering dependency (core → distributed).

**2. If the coupling is wanted, it's a one-liner on the distributed side, with no new semantics.**
`c10::utils::set_env` already has exactly the "don't clobber an explicit user setting" behavior via `overwrite=false` (`c10/util/env.cpp:16`). So in `setDebugLevelFromEnvironment()`/`setDebugLevel()`:

```cpp
if (level == DebugLevel::Detail) {
  c10::utils::set_env("TORCH_SHOW_CPP_STACKTRACES", "1", /*overwrite=*/false);
}
```

or equivalently one line in `torch/distributed/__init__.py` next to the existing `set_debug_level_from_env()` call (line 196):

```python
if get_debug_level() == DebugLevel.DETAIL:
    os.environ.setdefault("TORCH_SHOW_CPP_STACKTRACES", "1")
```

Both get the `=0` opt-out for free, add no duplicated parsing, and run before `get_cpp_stacktraces_enabled()`'s static is first computed (that cache is populated on first error, not at import).

**3. As written, it also misses the programmatic path.** `dist.set_debug_level(DebugLevel.DETAIL)` (documented right above the changed paragraph in `docs/source/distributed.md`) will *not* enable stacktraces, because the new code only looks at the env var. The `setDebugLevel` variant above covers it.

**4. Minor behavior change worth noting.** Previously `TORCH_SHOW_CPP_STACKTRACES=yes` warned and evaluated to false. Now `check_env` returns `nullopt` for any non-`0`/`1` value, so it silently falls through to the `TORCH_DISTRIBUTED_DEBUG` check — an invalid explicit value can now turn stacktraces *on*.

**5. And it's fair to ask whether even the one-liner is wanted**, since `TORCH_DISTRIBUTED_DEBUG=DETAIL TORCH_SHOW_CPP_STACKTRACES=1` already works and is what the docs told users to do. If the complaint in #78842 is really discoverability, a docs-only change is the whole fix — no code, no 5-subprocess test matrix in `test/test_cpp_extensions_jit.py`.

Recommendation: revert `cpp_stacktraces.cpp` to its original one-liner and either (a) drop the code entirely and keep just the docs update, or (b) do the `set_env(..., overwrite=false)` one-liner in `c10d::setDebugLevel`. I haven't made any changes — happy to implement whichever you prefer.
