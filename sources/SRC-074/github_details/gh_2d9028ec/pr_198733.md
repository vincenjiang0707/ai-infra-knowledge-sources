# [PR #198733] [inductor] Proven int32 size arguments for the dynamic-concat kernel in #189940 (opt-in, for review)

## 正文

## What

When `config.triton.narrow_proven_size_args` is on (default **off**), a Triton pointwise kernel's `ks*` size
arguments are declared `i32` instead of `i64`, but only if the kernel is in a proven class and Inductor's own
symbolic state establishes the premises. Every other kernel is unchanged.

Supported class today: exactly the kernel Inductor emits for the nested 6-segment concatenation along a dynamic last
dimension in #189940.

The flag is a staging mechanism for review, not the proposed end state. Following the discussion in #190034 (fix the
root cause; avoid a dedicated knob), the question we want to put to reviewers is whether this proven eligibility
condition can become an automatic compiler decision at the right internal representation.

## Why

`signature_to_meta` widens every `ks*` to `int64`, because a product or sum of symbols can overflow even when each
symbol fits. For this kernel that makes every index operation 64-bit, including `xindex % ks0` and `xindex // ks0`,
and roughly doubles the per-element SASS.

## Related work

- **#193614** (open, "Fixes #189940") and **#193964** address a different cost in the same kernel: missing
  divisibility metadata, which keeps loads scalar. They dispatch at runtime to an alignment-hinted variant and report
  that dynamic latency matches static on H100. Those variants keep the `ks*` argument types unchanged. This PR
  addresses index width (`i64` → `i32`) and leaves alignment alone. The two could compose, but we have not measured
  them together, and we have not measured on H100.
- **`assume_32bit_indexing`** (#167784; honoured in `_decide_tl_dtype` since #194127) narrows `ks*` for every kernel
  on the user's promise. This PR narrows one proven kernel class without that promise, using facts Inductor already
  holds.

## Evidence (two stacks; please read them separately)

- **Performance, measured on torch 2.14.0 / Triton 3.8.0, one L4.** A local prototype of this rule produced the
  `ks*: i32` kernel. In a paired, pre-registered confirmation over a 14-shape dynamic sequence, it reduced warm
  complete-sequence time by 26% against the emitted kernel (median 601 → 444 ms; paired ratio 1.35×), with
  non-regression shown at all 10 small shapes tested. Output was bitwise identical to eager at every shape.
- **This patch, tested on nightly 2.15.0.dev20260926 (cu130; git 6aa9e2fc, the nightly build of `main` ef166fb2),
  one L4.** It applies; the four tests below pass; the 14-shape sequence is bitwise equal to eager with all seven `ks`
  as `i32`. That build emits the same kernel source byte for byte. This branch is based on ef166fb2, where the two
  modified files are byte-identical to the tested build.
- **This patch, timed flag off versus on, on the same nightly and one L4.** It was pre-registered and run once.
  OFF/ON on the 14-shape sequence is **1.388× (95% CI 1.378–1.408)**; median 592 → 427 ms. Non-regression was shown
  at all 10 small shapes, with every CI lower bound ≥ 1.29. Output was bitwise equal to eager, and there were no
  recompiles during measurement. The executed ON kernel was verified to be the `i32` build.
  - Compile cost: the eligibility check takes 14.7 ms per compile of the target kernel and about 95 µs per rejected
    unrelated kernel. It runs once per compile, never per call.
  - Scope: one L4, one program. H100 is untested.

Full report, including negative results and the selection history: https://github.com/scasella/veritile-narrow-cat/blob/stage15-patch-timing/bench/optimizations/inductor_narrow/REPORT.md

## Premises

Implemented in `torch/_inductor/codegen/triton_size_arg_narrowing.py`.
- **C1 (structure):** a pointwise kernel on a 1-D grid with no fixed config, reduction or cooperative mode; the
  proved argument list and signature; and a body whose canonical IR (indexing, masks, payload dataflow, dead
  statements) has the proved SHA-256. The recognizer rejects any construct it does not model.
- **C2 (symbolic facts, never size hints):**
  - `ks1..ks6` are size symbols with a `var_to_range` lower bound ≥ 1;
  - `ks0`'s precomputed definition equals `ks1 + … + ks6`;
  - `numel == s * ks0` for a size symbol `s` with lower bound ≥ 1;
  - the index dtype is int32, and the guard `numel <= 2**31 - 1` is installed (or statically known).
- **When a premise fails later:** if the guard fails, Dynamo recompiles, Inductor chooses int64 indexing, and that
  kernel is not in the class. Exercised at `numel = 2**31`: bitwise identical to eager.

## Why this is sound

A Lean 4 proof (standard axioms only), `NarrowCat.narrow_cat_equiv` and companions: https://github.com/scasella/veritile-narrow-cat/blob/stage15-review/bench/optimizations/inductor_narrow/NarrowCat.lean. It models the
kernel's integer semantics (int32/int64 promotion, two's-complement wrap at every operation, truncating `%` and `//`,
`i32` argument packing). Under the premises, for every lane of the grid, the `i64` and `i32` kernels agree on the
store mask, store address, stored value and every memory read. Companion lemmas: equal positive divisors (no new
undefined behaviour); every `ks_i` in `[0, 2**31)` given positive widths and rows (exact `i32` packing); no
`xindex` wraparound on the grid. The payload is symbolic, so no floating-point claim is made.

**Why not `assume_32bit_indexing`.** That flag is a user's promise that every symbol fits. Our boundary tests show
lanes where every `ks_i < 2**31` yet the two kernels disagree, because `ks1 + ks2 + ks3` overflows. This rule relies
on relations Inductor already knows instead.

**Trusted, not proved:** SymPy and the `sizevars` / `shape_env` facts; the recognizer's parse of the generated source
(binding-tested against the IR the proof is stated over); Triton's lowering; masked-off lanes never dereferencing
their (possibly wrapped) addresses, as the `i64` kernel already assumes for past-the-end addresses.

## Tests

`test/inductor/test_triton_size_arg_narrowing.py`, four GPU tests; all passed on one L4 at the pinned revision
(correctness only). They are targeted tests, not a substitute for the usual CI.
- `test_narrows_proven_cat_kernel`: flag on → `ks*` are `i32`, output bitwise equal to eager at two shapes.
- `test_default_is_unchanged`: flag off → `ks*` stay `i64`.
- `test_other_kernel_is_unchanged`: a 3-segment cat keeps `i64`.
- `test_recognizer_rejects_mutations`: an extra size use, a changed index and a changed cast all fail recognition.

The GPU tests and the timing above ran on the first commit, 406a839. The third commit, 293565c, limits the two tests
that expect recognition to CUDA; see Limitations. The second commit, ad17abc, only applies lint fixes: formatting, `OrderedSet` in place of `set`, and type annotations/`cast` for pyrefly. The test file's AST is
unchanged. We re-checked ad17abc on the pinned nightly's CPU codegen path:
- the target kernel is accepted and narrowed to `i32`;
- four unrelated kernels are rejected and keep `i64`;
- the canonical digest still matches the proved kernel;
- all three recognizer mutations are still rejected.

## Limitations

- **One kernel class, recognised by digest.** The digest is an identity check, not an explanation of why a class of
  programs is eligible; each new class would currently need its own extraction and proof. The upstream form may
  need to be a structural or range-based rule rather than a list of generated kernels. We would rather get
  direction on that before building it.
- **Safe failure direction.** Recognition keys on generated-source structure, including argument naming and
  temporary numbering. A benign codegen change makes the rule stop firing (the kernel keeps `i64`); it does not
  misfire, provided the recognizer is correct.
- **One device.** Measured on L4 only; the issue's H100 is untested.
- **CUDA only.** The proven class is pinned to the source Inductor emits on NVIDIA CUDA. On other backends (ROCm,
  XPU) the emitted code may differ, and then the rule does not fire and the kernel keeps `i64`. The two tests that
  expect recognition therefore run on CUDA only.

## Review questions

1. Is generated-source recognition acceptable as an initial implementation, or should the rule operate earlier, on
   typed indexing expressions?
2. Does the symbolic-fact extraction establish exactly the theorem's premises, including their maintenance across
   later invocations?
3. What evidence would justify enabling this automatically for eligible kernels instead of behind a flag?
