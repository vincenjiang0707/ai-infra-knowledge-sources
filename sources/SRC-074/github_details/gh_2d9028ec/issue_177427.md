## 正文

### 🚀 The feature, motivation and pitch

## Motivation

PyTorch's distributed communication primitives (`all_gather_into_tensor`,
`reduce_scatter_tensor`, `all_to_all_single`, etc.) require contiguous input
tensors. Today, any time a tensor with a non-contiguous memory layout reaches a
collective, the runtime either:

1. silently calls `.contiguous()`, materializing a full copy, or
2. raises an error (FSDP explicitly raises `NotImplementedError` for
   non-contiguous parameters in `_fsdp_param.py`).

Modern distributed DL workloads increasingly operate on tensors that are
*structurally* non-contiguous: column-wise shards of tensors in tensor/sequence
parallelism, and block-wise shards in Shampoo optimizer (illustrated below).
More recent examples include: 
[Memory Sharded Tensor (MST)](https://github.com/pytorch/pytorch/compare/main...ailing/mst#diff-e326c855a215daccfd35d8953f8ce5f7c75cf2c446eb9880b22b512a8b1d7158), and [a FSDP proposal based upon](https://github.com/pytorch/torchtitan/pull/2378).
Forcing these to be contiguous wastes memory bandwidth and increases peak 
memory.

This RFC proposes first-class collective APIs that accept and produce
non-contiguous tensors with column-wise or block-wise shard layouts, and
describes the semantics, implementation path, and integration points.

## Background

### Column-wise Sharding

In sequence parallelism an activation tensor of shape `[B, S, H]` is split
along the sequence dimension `S` across `P` ranks. Each rank owns a contiguous
band of sequence positions.

```
  Activation tensor  [B × S × H]

  ◄──────────────────── S ────────────────────►
  ◄─── S/P ───►◄─── S/P ───►     ◄─── S/P ───►

  ┌────────────┬────────────┬─ … ─┬────────────┐  ▲
  │            │            │     │            │  │
  │   rank 0   │   rank 1   │     │  rank P-1  │  B
  │            │            │     │            │  │
  └────────────┴────────────┴─ … ─┴────────────┘  ▼
  ◄──────────────── H (hidden dim) ───────────────►
```

In row-major layout the full tensor has strides `(S·H, H, 1)` across `(B, S, H)`.
Each rank's shard `T[:, k·S/P : (k+1)·S/P, :]` has:

```
  shape   = [B, S/P, H]
  strides = (S·H,  H,  1)
              ↑
              outer stride is S·H, not S/P·H  ← non-contiguous
```

The batch stride spans the full sequence length `S`, not the local shard length
`S/P`, so consecutive batch elements in the shard are separated by `S·H`
elements rather than `S/P·H`. Today's collectives reject this strided view and
require a `.contiguous()` copy before every all-gather or reduce-scatter on the
sequence-parallel activation.

### Mixture of Experts + Muon

In EP, each GPU runs Grouped GEMM over its local experts, whose weights are
concatenated column-wise into a single matrix `[hidden_dim, E_local × ffn_dim]`.
With FSDP, each expert's weight is owned by a different FSDP rank, so the
reduce-scatter of gradients must send each expert's block to its owning rank.
The same non-contiguous layout arises with the Muon optimizer, which applies an
independent Newton-Schulz step to each expert's weight matrix in-place; the
all-reduce of each expert's gradient operates on a strided column-block of the
larger Grouped GEMM buffer.

```
  Grouped GEMM weight on one GPU  [hidden_dim × (E_local × ffn_dim)]

  ◄─ ffn_dim ─►◄─ ffn_dim ─►◄─ ffn_dim ─►◄─ ffn_dim ─►
┌─────────────┬─────────────┬─────────────┬─────────────┐  ▲
│             │             │             │             │  │
│   Expert 0  │   Expert 1  │   Expert 2  │   Expert 3  │ h_dim
│             │             │             │             │  │
└─────────────┴─────────────┴─────────────┴─────────────┘  ▼
       │             │             │             │
       ▼             ▼             ▼             ▼
   FSDP rank 0   FSDP rank 1   FSDP rank 2   FSDP rank 3
   (owns E0 grad) (owns E1 grad) (owns E2 grad) (owns E3 grad)

  Each expert block: shape  [hidden_dim, ffn_dim]
                     stride (E_local × ffn_dim, 1)  ← non-contiguous
```

Each expert's block has outer stride `E_local × ffn_dim` rather than `ffn_dim`,
making it non-contiguous. Today every reduce-scatter or all-reduce on these
blocks requires a pack copy into a contiguous staging buffer.

### Block-wise Sharding from Shampoo

A 2-D tensor `A` of shape `[M, N]` is split into `B = Br × Bc` rectangular
blocks. Ownership is assigned round-robin across ranks: block with flat index
`i = r*Bc + c` is owned by rank `i % world_size`. There is no 2-D process-group
mesh; a single flat process group suffices.

```
Global A  [M × N]
┌──────────┬──────────┬──────────┬──────────┐
│  B(0,0)  │  B(0,1)  │  B(0,2)  │  B(0,3)  │
├──────────┼──────────┼──────────┼──────────┤
│  B(1,0)  │  B(1,1)  │  B(1,2)  │  B(1,3)  │
├──────────┼──────────┼──────────┼──────────┤
│  B(2,0)  │  B(2,1)  │  B(2,2)  │  B(2,3)  │
└──────────┴──────────┴──────────┴──────────┘

Round-robin ownership across 4 ranks (world_size = 4):
  B(0,0)→rank 0  B(0,1)→rank 1  B(0,2)→rank 2  B(0,3)→rank 3
  B(1,0)→rank 0  B(1,1)→rank 1  B(1,2)→rank 2  B(1,3)→rank 3
  B(2,0)→rank 0  B(2,1)→rank 1  B(2,2)→rank 2  B(2,3)→rank 3

Each block B(r,c): shape  [M/Br, N/Bc]
                   strides (N, 1)  ← outer stride is N (full row width),
                                      not N/Bc  ⇒ non-contiguous
```

Each block is a 2-D slice of the global tensor with outer stride `N` rather
than `N/Bc`. It is therefore non-contiguous in memory and today cannot
participate in a collective without a copy. The Shampoo optimizer is a canonical
user of this layout: it maintains a Kronecker-factor preconditioner per weight
block and must all-reduce each block's gradient across data-parallel ranks,
operating directly on these strided views.

### Pipeline Parallelism Micro-batch Buffering

In 1F1B pipeline schedules, activations for multiple micro-batches can reside in
a pre-allocated ring buffer. Frameworks that keep the sequence dimension outermost
use a sequence-first layout `[S, num_microbatches, H]`. A single micro-batch
slice `buffer[:, i, :]` is then non-contiguous:

```
  shape   = [S, H]
  strides = (num_microbatches × H,  1)   ← outer stride ≠ H  ⇒ non-contiguous
```

Point-to-point sends (`isend`/`irecv`) require contiguous buffers today;
supporting strided P2P would eliminate the staging copy at every pipeline
boundary.

### Sequence Parallelism + Context Parallelism

In context parallelism the sequence is split across ranks. Positional encoding
and attention masks that depend on global sequence position are stored as
column-wise shards of a 2-D positional embedding matrix. All-gather over these
shards reconstructs the full context. The shard is again a strided view of the
full embedding table.

## Proposed API

### Primitive Extension

Extend the existing signature to accept non-contiguous input and output:

```python
# Proposed (backward-compatible — contiguous tensors behave identically)
dist.all_gather_into_tensor(
    output_tensor: Tensor,   # contiguous
    input_tensor: Tensor,    # contiguous or column-shard layout
    group: Optional[ProcessGroup] = None,
    async_op: bool = False,
) -> Optional[Work]
```

Or, alternatively, as dedicated ops:

```python
dist.all_gather_column_shard(output, input, group=group, async_op=async_op)
dist.reduce_scatter_column_shard(output, input, group=group, op=ReduceOp.SUM, async_op=async_op)
```

Dedicated ops are preferred in the first iteration to avoid changing the
semantics of existing primitives and to allow backend-specific dispatch without
a `layout` string.

### Grouped Reduce for MoE

In the MoE case, all expert gradient blocks on a GPU must be reduced to their
respective owning FSDP ranks in one shot. Rather than issuing `E_local` separate
reduce calls, we expose a grouped variant that takes a list of (tensor, dst_rank)
pairs and fuses them into a single communication call:

```python
# Each element is one expert's gradient block — a non-contiguous strided view
# of the Grouped GEMM weight matrix [hidden_dim, E_local × ffn_dim].
expert_grads = [
    grouped_gemm_weight_grad[:, 0 * ffn_dim : 1 * ffn_dim],  # Expert 0 → rank 0
    grouped_gemm_weight_grad[:, 1 * ffn_dim : 2 * ffn_dim],  # Expert 1 → rank 1
    grouped_gemm_weight_grad[:, 2 * ffn_dim : 3 * ffn_dim],  # Expert 2 → rank 2
    grouped_gemm_weight_grad[:, 3 * ffn_dim : 4 * ffn_dim],  # Expert 3 → rank 3
]
# expert_grads[i].is_contiguous() == False
# expert_grads[i].stride() == (E_local * ffn_dim, 1)

dst_ranks = [0, 1, 2, 3]

dist.grouped_reduce(expert_grads, dst_ranks, op=ReduceOp.SUM, group=fsdp_group)
```

`grouped_reduce` packs all non-contiguous blocks into a single NCCL call (or a
fused kernel + reduce-scatter), avoiding one `.contiguous()` copy per expert per
backward pass.

## Implementation Approach

**Option A. NCCL Device APIs.**

NCCL device APIs allow a custom CUDA kernel to participate directly in a
collective. We write such a kernel that is aware of the strided layout of the
input and output tensors, assigning one Cooperative Group per contiguous region.
Each Cooperative Group reads or writes its region directly from the
non-contiguous tensor, with no staging buffer, no pack copy, and no extra
memory traffic.

**Option B. Staging buffer with fused pack kernel.**

Allocate a contiguous staging buffer in symmetric memory, emit a CUDA pack kernel
that copies the non-contiguous shard into it, then issue the standard NCCL
collective. The pack kernel can be fused with the preceding compute kernel via
stream ordering, hiding some of the copy latency. Rejected because it still
requires a full staging allocation (`O(shard_mem)` extra peak memory) and a
complete memory copy of the shard on every collective call, whereas the proposed
NCCL device API approach accesses the non-contiguous tensor in-place with no
extra allocation.

---

## Alternatives Considered

**A. Always force `.contiguous()` at the caller.**
Current behavior. Simple but wastes bandwidth and memory. Rejected because the
cost grows with model size and is paid on every forward/backward pass.

## Memory and Performance Considerations

| Use case | Collective | Today | Proposed |
|---|---|---|---|
| Sequence parallelism `[B, S, H]` shard | all-gather / reduce-scatter | Host `.contiguous()` copy + collective; `O(shard_mem)` extra allocation | In-place strided access via NCCL device API; zero extra allocation |
| MoE + Muon: per-expert gradient | `grouped_reduce` to owning FSDP rank | `E_local` separate copies + reduces; `E_local × expert_mem` staging | Single grouped call; Cooperative Groups access each expert block in-place |
| Shampoo: per-block gradient | all-reduce per strided block | Copy each block to contiguous staging + all-reduce | Strided block accessed in-place; no staging allocation |
| Pipeline P2P `[S, M, H]` micro-batch | `isend` / `irecv` | Copy micro-batch slice before send; `O(slice_mem)` staging | Strided send/recv with in-place access; no staging allocation |

Across all cases, the NCCL device API approach eliminates the staging allocation
and the associated memory copy, trading them for Cooperative Group indexing
arithmetic inside the collective kernel.

---

## Open Questions

1. Should the API be extended in-place on existing primitives (via `layout=`)
   or as new ops (`all_gather_column_shard`, `grouped_reduce`)? New ops are
   safer but add surface area.

2. Cooperative Group granularity: should groups be mapped one-per-logical-shard
   (e.g., one per expert block) or should the mapping be tuned based on shard
   size to avoid under- or over-subscribing the GPU?

3. `grouped_reduce` atomicity: should all reduces in a `grouped_reduce` call be
   issued as a single NCCL operation, or as a sequence of dependent ops under
   one `Work` handle?
