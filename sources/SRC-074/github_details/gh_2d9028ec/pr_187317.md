* __->__ #187317

Motivation: Most PyTorch code is shared across accelerator backends (CUDA,XPU, ROCm, MPS), but community contributors typically only have CUDA hardware. As a result, CUDA-specific code regularly leaks into device-generic paths
(e.g. torch.cuda.* calls, hardcoded device="cuda", CUDA-only backend classes like CUDACodeCache, hardcoded "cuda" in expected-string test assertions). These slip through review and only break later on other accelerators such as XPU.

This PR adds a "Device Portability" subsection to the PR review checklist covering these common failure modes, with guidance to derive the device from inputs / use device-agnostic APIs, and an explicit carve-out that device-specific code behind a proper device guard is fine. A matching bullet is added to the Review Philosophy so reviewers consistently apply it.

Test:
With this PR, the review of #181640 can catch the `CUDACodeCache` hardcode in acclerrator shared code which break XPU.
```
PR Review: #181640

  Summary

  Enables CUTLASS GEMM templates under JIT cpp_wrapper (non-AOT) mode by emitting bare extern "C" call sites and linking each precompiled kernel .so via extra_flags.
  There is a functional device-portability bug on XPU plus several secondary issues.

  ---
  Device Portability

  CUDACodeCache invoked on XPU. cutlass/scheduling.py::define_kernel adds:

  if V.graph.cpp_wrapper and not V.graph.aot_mode:
      from ...codecache import CUDACodeCache
      so_path, _, _ = CUDACodeCache.compile(src_code, "so")

  CUTLASSScheduling is instantiated by XPUCombinedScheduling (codegen/xpu/xpu_combined_scheduling.py:45), so this branch is reachable when V.graph.device_type ==
  "xpu". CUDACodeCache.compile invokes nvcc on a SYCL source file — this will crash or produce a wrong artifact on XPU. The fix requires dispatching to XPUCodeCache
  when on XPU, analogous to how other cache calls in the codebase already do.


PR Review: #189108
Recommendation
Request Changes

test_int64_index_intermediate lost its SM80 guard (correctness regression) and torch.cuda.synchronize() will crash on XPU CI. Both are must-fix correctness bugs.
```

**1. Self-contradiction on `torch.cuda.is_available()`** — must fix.

The section lead-in names it as an acceptable guard:

> unless it is guarded by an explicit device check that makes it reachable only on that device (e.g. `if device.type == "cuda":`, `torch.cuda.is_available()`, ...)

**3. `CUDACompileError` in the third bullet is a false-positive generator.**

The bullet asks reviewers to flag references to `CUDACompileError` in shared code. The name is misleading but the class is genuinely device-shared, so this entry will fire on correct code. Drop it, or note explicitly that only `CUDACodeCache`/`nvcc` are the real signals while `CUDACompileError` is a shared misnomer.

### Skill structure and maintainability

**7. The SKILL.md addition is a checklist item wearing a philosophy item's clothes.**
