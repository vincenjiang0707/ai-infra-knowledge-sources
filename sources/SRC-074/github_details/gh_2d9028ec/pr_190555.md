# [PR #190555] [inductor] Partition cross-device fallbacks from CUDA graphs

## 正文

## Summary

> - Split any extern kernel whose FX node reads or produces tensors on more than one device, ignoring meta tensors. This covers `FallbackKernel`, `ExternKernelOut` (custom ops with a `Tag.out` overload), `IndexPutFallback`, and multi-output ops together with their `MultiOutput` children.
> - Keep same-device kernels eligible for CUDA graph capture.
> - Rename and simplify the deterministic `device_put` regression.
> - Add regressions for a CPU-to-CUDA custom op, with and without a `Tag.out` overload, for multi-output ops with a CPU scalar input and with a CPU output, and for `index_put` with CPU indices. Each one checks results against eager and counts the recorded graphs.
> - Add a regression that SDPA with dropout stays in one forward and one backward CUDA graph, so the rule doesn't split attention over the RNG state its backward reads.

## Root cause

CUDAGraph partitions must not read tensor storage allocated outside the active CUDA memory pool. `Scheduler.should_partition` recognized explicit `ir.DeviceCopy` nodes, but a fallback kernel could report a CUDA output device while reading a CPU tensor input. That fallback passed the normal GPU-node check and could be recorded in a CUDA partition, where `check_memory_pool` rejected the CPU storage.

> The scheduler now checks the FX node behind each extern kernel: if the kernel's inputs and outputs span more than one device, it gets its own partition. Deciding on the FX node keeps a multi-output op and its `MultiOutput` children together, the way `is_cudagraph_unsafe_op` already does. Same-device kernels remain eligible for CUDA graph capture. The partition reason is now `cross-device ops`.

Issue #188677 is the earlier CI quarantine of this same regression; #190233 tracks the underlying failure.

## PR Review: #190555

### Summary
Adds `prims.device_put.default` fallbacks to the set of nodes that force a cudagraph partition boundary, and re-enables the previously skipped `test_graph_partition_view_fallback` with a forced fallback so the repro is architecture-independent. The diagnosis and the fix are right; my concerns are about the scope of the predicate and a couple of test details.

### Code Quality

**`torch/_inductor/scheduler.py:9053-9057` — the guard is op-identity-based where the underlying invariant is device-based.**

I traced the failure path to confirm the root cause as described, and the invariant that is actually being protected is "a node inside a cudagraph partition must not read a buffer that lives outside the cudagraph memory pool":

- `get_graph_partition_signature` has no device predicate — a CPU-device buffer read by a GPU-device node becomes a partition input (`scheduler.py:9310-9319`) and, if not freed in the partition, is also promoted to a partition output (`scheduler.py:9355-9361`).
- On the recording path, non-static partition inputs are wrapped unconditionally into the `check_memory_pool` list (`cudagraph_trees.py:1441-1448`), and outputs likewise (`cudagraph_trees.py:1564`) — there is no `is_cuda` filter on either (the only such filter is in `CUDAWarmupNode.run`, `cudagraph_trees.py:812`).
- Nothing upstream rejects it: `check_multiple_devices_or_any_cpu_nodes` deliberately pops CPU devices when partitioning is on (`cudagraph_utils.py:350-352`).

So the *only* thing that has ever shielded this path is that cross-device transfers normally lower to `ir.DeviceCopy` (`lowering.py:1091`, `1094-1095`) and `should_partition` splits those out. Any `FallbackKernel` with a CPU input and a GPU output bypasses that shield, because `node.is_gpu()` reads the *output* layout's device. `prims.device_put` is the instance you hit; an implicitly-fallen-back custom op that takes a CPU tensor and returns a CUDA tensor reaches the identical crash. (`aten.copy_` is not reachable — its lowering inserts `to_device`, `lowering.py:7633`.)

Checking the actual device mismatch is barely more code and covers the class rather than the instance:

```python
if isinstance(node.node, ir.DeviceCopy) or (
    isinstance(node.node, ir.FallbackKernel)
    and any(
        (d := inp.get_device()) is not None and d != node.get_device()
        for inp in node.node.inputs
    )
):
    return "cross-device copy ops"
```

If you deliberately want to stay narrow for this fix (the PR description says so explicitly), please say *why* in the code — the current inline story is only in the PR body, and the next person to hit this with a different op has no pointer. Also note the `MultiOutputLayout` case would need care in the general version, which is a legitimate reason to defer.

Two smaller points on the same clause:
- The returned reason string `"DeviceCopy ops"` is now attached to nodes that are not `ir.DeviceCopy`. It only feeds `cudagraphs_log.debug` (`scheduler.py:9656-9669`), but the log also prints `ir=FallbackKernel`, so the pairing reads as a contradiction. `"device_put fallback"` costs nothing.
- The predicate fires on *any* `device_put` fallback, including a same-device or GPU-to-GPU one (the lowering's same-device short-circuit at `lowering.py:1089-1090` does not apply once the op is forced/implicitly fallen back). That is a needless partition split. The device-mismatch form above avoids it for free.

### PR Review: #190555

### Summary
The PR splits an extern kernel into its own partition whenever its FX node reads or produces tensors on more than one device (meta tensors ignored), so that cross-device fallbacks are never recorded into a CUDA graph. The design matches how `is_cudagraph_unsafe_op` already works: `ExternKernel.fx_node` is `V.graph.current_node` (`ir.py:7207`), which `MultiOutput` children share with their parent. Two issues remain, both in the tests.

### Testing

- **No test covers the meta-tensor exclusion, even though it is what keeps SDPA inside CUDA graphs.** `fx_node_crosses_devices` (`torch/_inductor/utils.py:5116`) only avoids splitting flash, efficient and cuDNN attention because their meta registrations return `philox_seed`/`philox_offset` on `device="meta"` (`_meta_registrations.py:6461-6465`, `6535`, `6602`, `6837`, `7002`, `7188`). Results stay correct, so only a graph-count assertion would notice. Please add a test in `test_cudagraph_trees.py` that runs SDPA forward and backward with `dropout_p > 0` under `graph_partition=True` and asserts that no partition is split for "cross-device ops" (for example with `new_graph_id().id` or `get_num_partitions`).
