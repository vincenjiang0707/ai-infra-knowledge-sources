# [Issue #193760] [eager][cuda] Eager Does Inconsistent Extra Boolean Bit Normalization Depending on Striding

source: https://github.com/pytorch/pytorch/issues/193760
state: open | updated: 2026-09-25T15:11:14Z
labels: high priority, triage review, module: cuda, module: correctness (silent), bot-triaged

## 正文

Edit: root of the bug is that eager inconsistently normalizes extra boolean bits. See https://github.com/pytorch/pytorch/issues/193760#issuecomment-5834688081.  

### 🐛 Describe the bug

`torch.compile` with the Inductor backend silently corrupts data for a bitwise copy chain `x.view(torch.bool).copy_(y.view(torch.bool)).view(torch.float32)`. Eager executes the same code correctly: the copy replaces `x`'s storage with `y`'s bytes, and the result is bitwise equal to `y`. The compiled result is `2.37e-38` in every element (every 4-byte word is `0x01010101`, i.e. every byte is `0x01`, the encoding of bool `True`) — the kernel fills the destination with `True` instead of copying the source bytes, and no error is raised.

Reproduces on CUDA with torch 2.13.0+cu130 and nightly 2.15.0.dev20260816+cu130 (identical output). On torch 2.5.1 the same code raises a lowering error (`TypeError: torch.bool is not supported by torch.iinfo`) instead.

### To reproduce

```python
import torch

torch.manual_seed(1234)
a = torch.randn(8, 8, device="cuda") * 10
b = torch.randn(8, 8, device="cuda") * 10

def fn(x, y):
    return x.view(torch.bool).copy_(y.view(torch.bool)).view(torch.float32)

eager = fn(a.clone(), b)
torch._dynamo.reset()
compiled = torch.compile(fn)(a.clone(), b)

print("eager == b (bitwise):", torch.equal(eager, b))        # True
print("compiled == b (bitwise):", torch.equal(compiled, b))  # False
print("maxdiff:", (eager - compiled).abs().max().item())     # 21.2665
print("compiled row0[:4]:", compiled[0, :4].tolist())        # [2.37e-38, ...] (bytes 0x01 = bool True)
```

### Expected behavior

`torch.compile` should match eager: the bitwise copy should make the result equal to `y`, not replace it with garbage.

### maxxlife · 2026-08-17

I inspected the generated Inductor code with TORCH_COMPILE_DEBUG=1.
The corruption appears to be present in the generated Inductor/Triton code before Triton lowering. Inductor generates an intermediate bool buffer and a pointwise kernel that loads from `y.view(torch.bool)` as `*i1`, then explicitly converts the loaded value to `tl.int1`:
```
tmp0 = tl.load(in_ptr0 + (x0), xmask).to(tl.int1)
tl.store(out_ptr0 + (x0), tmp0, xmask)
```
This looks like it is normalizing each byte to boolean 0/1 instead of preserving the raw byte value from the original float32 storage. The generated code then reinterprets this bool buffer as float32, which explains the observed `0x01010101` pattern `/ 2.3694278276172396e-38` values.
So the likely problem is in Inductor handling of `view(dtype=torch.bool)` + `copy_ `+ `view(dtype=torch.float32)`: it treats the operation as a semantic bool copy rather than a bitwise storage copy.
Relevant generated code shape:
```
buf2 = torch.ops.aten.view.dtype(arg1_1, torch.bool)
buf4 = empty_strided_cuda((8, 32), (32, 1), torch.bool)

triton_poi_fused_view_0.run(buf3, buf4, 256, stream=raw_stream0)

buf5 = torch.ops.aten.view.dtype(buf4, torch.float32)

triton_poi_fused_copy__1.run(buf6, arg0_1, 64, stream=raw_stream0)
```
This matches the observed behavior: the compiled path creates a bool-normalized temporary and then reinterprets it as `float32`, instead of copying the original bytes from `y` into `x`.

### maxxlife · 2026-08-18

I tested my idea of local fallback for this issue.

From debug prints in `torch/_inductor/lowering.py`, the failing case is distinguishable from a normal bool tensor copy. In the failing case, both `self` and `src` in `aten.copy` lowering are `TensorBox(StorageBox(MultiOutput(...)))`, where the `MultiOutput` input is a `FallbackKernel` for `aten.view.dtype` with `constant_args=(torch.bool,)`. The base input is a non-bool tensor, in my repro `torch.float32`.

So the unsafe pattern is specifically a copy between `torch.bool` dtype-reinterpret views.

The problematic path appears to be in `aten.copy` lowering:

```python
if self.get_size() != src.get_size():
    out = expand(x, self.get_size())
    result = clone(out)
else:
    result = clone(x)
```

For this case, `clone(x)` lowers the bool dtype-reinterpret view as a semantic bool pointwise clone. The generated Triton code then normalizes bytes to `0`/`1`:

```python
tmp0 = tl.load(in_ptr0 + (x0), xmask).to(tl.int1)
tl.store(out_ptr0 + (x0), tmp0, xmask)
```

As a local correctness experiment, I added a conservative fallback for this specific unsafe pattern:

```python
def _is_bool_dtype_view_from_non_bool(x):
    if x.get_dtype() != torch.bool:
        return False

    try:
        node = x.data.data
    except AttributeError:
        return False

    if not isinstance(node, ir.MultiOutput):
        return False

    if len(node.inputs) != 1:
        return False

    view_node = node.inputs[0]

    if getattr(view_node, "op_overload", None) is not aten.view.dtype:
        return False

    if getattr(view_node, "constant_args", None) != (torch.bool,):
        return False

    try:
        base = view_node.inputs[0]
        return base.get_dtype() != torch.bool
    except AttributeError:
        return False
```

and in `aten.copy` lowering:

```python
if _is_bool_dtype_view_from_non_bool(self) and _is_bool_dtype_view_from_non_bool(src):
    return fallback_handler(
        aten.copy.default,
        add_to_fallback_set=False,
    )(self, src, non_blocking=non_blocking)
```

With this fallback, the original reproducer passes:

```text
eager == b: True
compiled == b: True
eager == compiled: True
maxdiff: 0.0
```

I also reran the dtype matrix test. All tested dtype reinterpretation chains now match eager:

```text
torch.bool:     compiled == eager: True
torch.uint8:    compiled == eager: True
torch.int8:     compiled == eager: True
torch.int16:    compiled == eager: True
torch.float16:  compiled == eager: True
torch.bfloat16: compiled == eager: True
torch.int32:    compiled == eager: True
torch.float32:  compiled == eager: True
torch.int64:    compiled == eager: True
```

So this seems to confirm that the corruption comes from lowering `aten.copy` through `clone(x)` for a `torch.bool` dtype-reinterpret view. My correctness fix above is to fallback this specific unsafe pattern. Might be a good idea to create a more optimized fix that could lower this as a raw byte copy instead of a semantic bool copy.


### eellison · 2026-09-25

Looking into this more, eager has inconsistent semantics here. Depending on input striding, eager CUDA either does a raw memcpy (which preserves the non-0/1 bytes) or runs an elementwise copy kernel (which normalizes them to 0/1).

```
import torch

# Bool tensor whose storage bytes are 7 (not 0/1).
m = torch.full((2, 2), 7, dtype=torch.uint8, device="cuda").view(torch.bool)

def raw(t):
    return t.view(torch.uint8).flatten().tolist()

print(raw(m.clone()))              # [7, 7, 7, 7]  contiguous -> memcpy, raw bytes kept
print(raw(m.t().contiguous()))     # [1, 1, 1, 1]  strided -> copy kernel, normalized
```
