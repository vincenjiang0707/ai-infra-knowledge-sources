### Summary
Adds forward-mode AD for `grid_sampler_2d`, `grid_sampler_3d`, and `cudnn_grid_sampler` by repurposing the existing `grid_sampler_{2d,3d}_double_backward` helpers as JVP rules, and fixes an unrelated indexing bug in the functorch both-batched grid_sample batch rule. ### Code Quality

**`tools/autograd/derivatives.yaml:772,779,2772` + `torch/csrc/autograd/FunctionsManual.cpp:8317,8575` — the `Tensor()` for `grad_output` is an undocumented landmine.**

The reuse is mathematically valid: `d_grad_output = ggI·(∂out/∂input) + ggGrid·(∂out/∂grid)`, which is exactly the JVP, precisely *because* the backward is linear in `grad_output` and so `d_grad_output` has no `grad_output` dependence. That is why passing an undefined `Tensor()` works.

But nothing in the code says so. I traced every branch reachable under `{true, false, false}` — `FunctionsManual.cpp:8335-8338`, `8392-8399`, `8499-8506`, `8683-8692` — and confirmed none reference `grad_output` today. Meanwhile `grad_output` *is* used at `8341`, `8406`, `8415`, `8511`, `8543` under the other two mask bits. Anyone who later adds a `grad_output` term to an `output_mask[0]` branch (e.g. while extending bicubic or 3D coverage) will get a crash or silent garbage from an undefined tensor, with no hint of why.

Add a `TORCH_INTERNAL_ASSERT` making the contract enforceable rather than aspirational, plus a one-line comment at the top of both functions:

```cpp

// grad_output and output_mask {true, false, false}: d_grad_output is the JVP
// and is independent of grad_output. Branches under output_mask[0] must
// therefore never read grad_output.
if (!output_mask[1] && !output_mask[2]) {
  // ok: grad_output unused below
} else {
  TORCH_INTERNAL_ASSERT(grad_output.defined());
}
```

**`torch/csrc/autograd/FunctionsManual.cpp:8843-8845` — blocking: raises on 5-D bicubic under forward AD.**

The new `result:` formula for `grid_sampler_3d` (`derivatives.yaml:779`) passes a literal `Tensor()` for `grad_output` with `output_mask = {true, false, false}`. In the bicubic branch that reaches:

```cpp

  d_grad_output = d_grad_output.to(grad_output.scalar_type());   // 8844

```

The guard is on `d_grad_output`, but the tensor being dereferenced is `grad_output` — a different variable, and the undefined one. Tracing the path:

- `ggGrid` (= `grid_t`) is defined and non-`ZeroTensor` whenever `grid` carries a tangent, so the early return at `8669-8672` is not taken and the bicubic branch at `8674` is entered.
- The `kz`/`jy` double loop at `8751` runs unconditionally; `output_mask[0]` is true, so `8775-8782` assigns `d_grad_output`, making it **defined**.
- Therefore `8844` executes and calls `.scalar_type()` on the undefined `grad_output`. `TensorBase::scalar_type()` forwards to `TypeMeta::toScalarType()`, which hits `error_unsupported_typemeta` (`c10/util/typeid.cpp:16`) and throws `Unsupported TypeMeta in ATen: ... (please report this error)`.

This is reachable from public API. `torch/nn/functional.py` grid_sample accepts `mode='bicubic'` for 5-D input (the docstring at line 5577 documents it as tricubic), and neither `grid_sampler_3d_cpu` (`GridSampler.cpp:1135`) nor `launch_grid_sampler_3d_forward_kernel` (`cuda/GridSampler.cu:1005`) rejects it — both call the **2-argument** `check_grid_sampler_3d` overload, which has no interpolation-mode check; only the 3-argument overload at `GridSamplerUtils.h:89-100` refuses bicubic, and nothing in-tree calls it.

The fix is a one-liner: `grad_output` has the dtype of the forward output, which for `grid_sampler_3d` is `input.scalar_type()`. Use that instead — it is already what lines `8846-8847` use for `d_input`, and it removes the dependence on an argument the JVP caller does not supply.
