## 正文

### 🚀 The feature, motivation and pitch

I would like to speed up the native Metal matmul kernels in `aten/src/ATen/native/mps/kernels/LinearAlgebra.metal` and wanted to agree the approach before opening a PR.

The kernels (`matmul`, `addmm`, `naive_bmm`, `naive_baddbmm`) use 16x16 threadgroup tiles with one output element per thread, no register blocking and no simdgroup matrices. The same file already has a simdgroup-matrix GEMM (`gemmSimdLU`) and an MPP one (`gemmLU`) for the LU factorisation. On an M4 Max, the Metal kernels run at 1.1 to 1.4 TFLOPS on every shape I measured except one (below), while MPSGraph reaches 7.8 to 12.0 TFLOPS from 512 x 512 x 512 upwards.

**Who uses this path today.** On current main, `use_metal_mm` routes these calls to the Metal kernels:

- all integer `mm`
- complex `mm` with K > 2048, and all complex `addmm`
- some strided or offset outputs
- on Apple7/8 (M1/M2, macOS 14.4+), matmuls with K > 32768 and both output dims >= 16, because MPSGraph can return wrong results there (#183535, #195163); #195012 extends this to `bmm`/`baddbmm`/`addbmm`
- anything run with `PYTORCH_MPS_PREFER_METAL` set

In #195012, routing M1/M2 matmuls to the Metal kernels unconditionally rather than adding more conditions was raised. If Apple7/8 GPUs show ratios similar to the M4 Max below (I haven't been able to measure them), that would currently cost roughly 6-10x on ordinary shapes, so a faster kernel looks like a prerequisite.

**Measurements.** Apple M4 Max, macOS 26.6.2, torch 2.15.0.dev20260921 (git afa73d98ee). Each mode runs in its own process, since `PYTORCH_MPS_PREFER_METAL` is read once. Time is the median of 5 repeats of back-to-back `torch.mm(out=...)` calls bracketed by `torch.mps.synchronize()`. Values are Metal time / MPSGraph time for two full runs (run 1 / run 2):

| M x K x N | float32 | float16 | bfloat16 |
|---|---:|---:|---:|
| 256 x 256 x 256 | 2.0x / 1.9x | 2.1x / 2.1x | 2.1x / 2.1x |
| 512 x 512 x 512 | 7.0x / 6.4x | 8.8x / 7.4x | 8.7x / 7.5x |
| 1024 x 1024 x 1024 | 8.6x / 6.8x | 9.7x / 7.6x | 9.6x / 7.9x |
| 2048 x 2048 x 2048 | 8.8x / 7.3x | 9.7x / 8.1x | 9.8x / 8.2x |
| 4096 x 4096 x 4096 | 7.8x / 6.5x | 7.9x / 7.2x | 7.3x / 7.9x |
| 128 x 4096 x 4096 | 6.3x / 6.0x | 7.2x / 7.6x | 7.5x / 7.8x |
| 2048 x 1024 x 4096 | 7.5x / 6.8x | 8.4x / 8.0x | 8.8x / 8.3x |
| 25 x 40000 x 25 | 11.6x / 11.6x | 15.4x / 15.4x | 15.1x / 15.1x |
| 256 x 40000 x 256 | 8.1x / 7.5x | 8.7x / 7.9x | 8.7x / 8.0x |
| 1024 x 40000 x 1024 | 8.0x / 6.4x | 8.6x / 7.6x | 8.0x / 9.3x |

MPSGraph timings varied by up to 28% between runs (the Metal kernel by up to 11%), so the ratios are best read as ranges: excluding the launch-bound 256 x 256 x 256 case and the small-output case, 6.0x to 9.8x, median 7.9x. Half precision gives the Metal kernel no speed-up; float16 and bfloat16 run at the same rate as float32, since inputs are converted to float in threadgroup memory.

**Small output with large K is the worst case.** 25 x 40000 x 25, the reproducer shape from #195163 and exactly the kind of shape the Apple7/8 workaround reroutes, runs 11.6x (float32) to 15.4x (float16) slower, at 28 to 37 GFLOPS. With a 25 x 25 output the kernel launches four 16x16 threadgroups and each thread performs 40,000 sequential multiply-adds, so almost all of the GPU is idle.

Both paths agree numerically: no result exceeded the error threshold against a float64 CPU reference.

**Proposal**

1. Rewrite the 2D float/half/bfloat16 `matmul` kernel with `simdgroup_matrix` tiles and register blocking, following `gemmSimdLU` in the same file. Integer and complex paths remain unchanged.
2. Add a split-K variant for small-output, large-K shapes, so the Apple7/8 large-K workaround doesn't leave most of the GPU idle.
3. Apply the same to `addmm` and the batched kernels in follow-up PRs if this is successful.

Questions before I start:

- Would PRs along these lines be accepted?
- The LU code uses MPP `matmul2d` (`gemmLU`) when `has_mpp()` is true (macOS 26.2+) and `gemmSimdLU` otherwise. Should matmul follow the same two-tier pattern, or start with `simdgroup_matrix` only, since the main consumers are M1/M2 machines that may be on older macOS?
- How would you like CI to exercise the new kernel, given CI doesn't set `PYTORCH_MPS_PREFER_METAL`?
