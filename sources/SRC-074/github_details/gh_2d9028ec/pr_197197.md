## Summary

CPU `topk` selection builds a `std::vector<std::pair<accscalar_t, int64_t>>` spanning the whole reduced dimension and runs `std::partial_sort` over it. The value component exists only so the comparator can read it, but it doubles the working set (16 B/element vs 8 B).

This adds a fast path that sorts a `std::vector<int64_t>` of indices, with the comparator dereferencing `tmp_values` directly. It is gated on two conditions, both required:

- `tmp_values_stride == 1`. With a non-unit stride the comparator's dereference becomes a scattered gather, which removes the locality gain the change depends on.
- `k * 64 <= dim_size`. This is the pre-existing threshold that already selects `partial_sort` over `nth_element` in this file. `partial_sort` preserves `idx[i] == i` for positions its tail scan hasn't touched; `nth_element`'s in-place swaps destroy that, which is what keeps the comparator's extra indirection amortized rather than net-negative. So the fast path is restricted to the `partial_sort` regime.

Inputs failing either predicate fall through to the original pair-based implementation, which is untouched.

## Benchmarks

Baseline is the parent commit `cd96aa6ae45` built from source on the same machine with the same flags; patched is this commit built the same way. Single-threaded, 5 rounds x 300 iterations, fixed seed per shape, AMD Ryzen 9 7945HX.

| shape | k | baseline | patched | delta |
| --- | --- | --- | --- | --- |
| (1, 50257) | 50 | 175.1 us | 95.4 us | **-45.5%** |
| (32, 50257) | 50 | 4395 us | 3095 us | **-29.6%** |
| (1, 100) | 50 | 4.23 us | 4.20 us | ~0 |
| (10000, 64) | 8 | 13406 us | 13464 us | +0.4% |
| (100000, 8) | 2 | 13643 us | 13810 us | +1.2% |

The last three shapes do not satisfy `k * 64 <= dim_size`, so the fast path never runs and the executed code is identical to baseline; the ~1% there is binary-layout noise from rebuilding, not a regression.

## Tests

## Note for review

The fast path and the fallback are extensionally equivalent: they can differ in which branch runs, never in what is returned. So no output-comparison test can distinguish "fast path ran" from "fallback ran and got the same answer", and a change that silently widens or narrows the guard would not be caught by the tests here. Please check `tmp_values_stride == 1 && k * 64 <= dim_size` by inspection.

The mechanism does strictly reduce memory traffic, which makes a smaller, currently unmeasured energy benefit plausible, but confirming that would need power instrumentation scoped to `topk_impl_loop` rather than an end-to-end measurement.
