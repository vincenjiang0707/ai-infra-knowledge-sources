## 正文

Summary:
## Problem

PT2 traces dynamic tensor dimensions as symbolic shape values. A runtime shape check such as `x.shape[0] <= 128` is input-shape-dependent, not tensor-data-dependent: `x.shape[0]` is a `SymInt` like `s72`, and the comparison is a scalar `SymBool` represented by SymPy as a relational boolean such as `LessThan(s72, 128)`.

This becomes visible when graph partitioning or piecewise compilation exposes that predicate at a graph boundary. One compiled graph can produce or carry `s72 <= 128`, while a later compiled graph receives that predicate as a real FX placeholder and consumes it in `aten._assert_scalar`.

## Solution

Inductor's Python wrapper already handles tensors and numeric symbolic scalar inputs. Numeric `SymInt`/`SymFloat` placeholders are `sympy.Expr` values, and wrapper code may generate local numeric bindings such as `s72 = arg1_1` so later generated Python can use `s72` for allocation, size checks, and stride logic.

A relational `SymBool` input is different. The wrapper still receives and unpacks the graph input, but the relation itself is not a numeric shape symbol that can be assigned. There is no meaningful generated binding like `s72 <= 128 = arg...`; the numeric symbol inside the relation, such as `s72`, is bound separately through the normal `SymInt` or tensor-shape path.

On master, when a relational `SymBool` becomes a compiled graph input, shared wrapper codegen tries to classify it as an input symbol assignment and fails before backend execution with:

```
Unknown value type: <class 'sympy.core.relational.LessThan'>
```

The DeepSeek/MTIA repro hits this with an AOT graph input like `arg11_1: "Sym(s72 <= 262144)"` consumed by `aten._assert_scalar.default(arg11_1, ...)`. Without this change, compilation stops in `codegen_input_symbol_assignment`; with this change, generated Python still unpacks `arg11_1`, emits numeric bindings such as `s72 = arg1_1`, and proceeds through wrapper/kernel generation.

## Change

Teach shared Python wrapper input-symbol codegen to recognize relational `SymBool` inputs represented as SymPy booleans. These inputs are intentionally skipped by `codegen_input_symbol_assignment` because they do not define wrapper-local numeric shape-symbol assignments.

This preserves existing tensor and numeric `SymInt`/`SymFloat` handling while covering the scalar shape-predicate case. The fix belongs in common wrapper code rather than an MTIA-specific wrapper because CPU, GPU, and MTIA can all reach this wrapper failure when a relational `SymBool` predicate crosses a compiled graph boundary.

Tests cover both levels of the behavior: a wrapper-codegen unit test verifies a SymPy relation emits no symbol binding, and a CPU dynamic-shapes regression covers the original `_check`/`_assert_scalar` path plus the reviewer-suggested `int(a)` use. The `keepdim=a` variant is not included because it is rejected earlier by Dynamo/fake tensor validation (`keepdim` must be a concrete bool), before wrapper codegen.

**Short answer: I think you're right, and the codebase already leans that way — but the machinery lives in two different partitioners, and this PR's repro isn't actually hitting inductor's `graph_partition`.**

<details>
<summary>Full analysis</summary>

#### 1. The invariant you're describing already exists — partially

`torch/_functorch/partitioners.py:230-237` is literally your proposal, scoped to the min-cut partitioner:

```python
def _is_assert_only_symbool(node: fx.Node) -> bool:
    return (
        isinstance(node.meta.get("val"), torch.SymBool)
        and len(node.users) > 0
        and all(user.target is torch.ops.aten._assert_scalar.default for user in node.users)
    )
```

Applied at `partitioners.py:1777-1779` and `:4271-4272` to drop assert-only SymBools from `saved_sym_nodes` rather than save them across the fwd/bwd boundary. So "don't let assert-only SymBool cross a graph boundary" is already an accepted principle here; it just isn't enforced at the boundary this PR's repro crosses.

Notably the repro is an **AOT graph input** (`arg11_1: "Sym(s72 <= 262144)"`), and the new CPU test runs under `@config.patch("graph_partition", False)`. Inductor's own `graph_partition` path already swallows this at `wrapper.py:2676-2679`:

```python
else:
    if torch._inductor.config.graph_partition:
        pass
    else:
        raise AssertionError(f"Unknown value type: {type(value)}")
```

So the PR is generalizing an existing escape hatch, not adding a new capability. That's worth stating explicitly in the summary, since "graph partitioning ... exposes that predicate" reads like inductor's partitioner is the producer, and the fix is really about a placeholder that was already relational before inductor saw it.

#### 2. Why "SymInts only" is the better invariant

**It fixes more backends.** `cpp_wrapper_cpu.py:749-750` still has the same `raise AssertionError(f"Unknown value type: {type(value)}")`, untouched by this PR. Same input into AOTI/cpp wrapper still dies. `wrapper_fxir.py` has its own `_sympy_interp` (`:647-671`) that only base-cases `BooleanAtom`, not `Relational`. A producer-side invariant fixes all three at once; the consumer-side skip fixes exactly one.

**A relational input isn't representable in the partition signature anyway.** `get_graph_partition_symbol_inputs` (`scheduler.py:9355-9375`) filters candidate symbols to `SymT.SIZE / FLOAT / UNBACKED_INT / UNBACKED_FLOAT`. There is no SymBool `SymT`. So the partition signature genuinely can only carry numeric symbols — the relational input is an artifact that has no home in inductor's own IR for boundaries.

**The recompute side is already built.** `ir.AssertScalar` (`ir.py:9282-9342`) takes a `SympyBoolean` and emits it as Python or C++ from bound numeric symbols, and `torch/fx/passes/runtime_assert.py` reconstructs predicates from SymInt nodes via `sympy_interp`. So "receive `s72`, rebuild `s72 <= 262144` inside the subgraph, assert it" needs no new printing or interpretation machinery.

**And it preserves the assert.** This is my main functional concern with the patch as written: `codegen_input_symbol_assignment` silently `return`s on the relational input, so the wrapper just ignores the predicate. If the corresponding `_assert_scalar` isn't independently re-materialized from `s72` (which it should be here, via the deferred-runtime-assert path), the runtime check quietly disappears. Neither test asserts the check still fires — the `AssertModel` test only runs `batch_size=8`, which satisfies `<= 128`. A test at `batch_size=256` expecting a raise would pin down whether the assert survives. Under your proposal the assert is structurally guaranteed to survive because the predicate is rebuilt, not dropped.

#### 3. Where the invariant gets awkward (the real cost)

Not every SymBool decomposes into a SymInt that's *bindable on the receiving side*:

- `create_unbacked_symbool` (`symbolic_shapes.py:5642-5666`) produces `Eq(u0, 1)` over an unbacked `u0`. Fine in principle — pass `u0`. But `u0` then has to be bindable in the receiving subgraph, and unbacked symbol binding requires a defining tensor/scalar that actually crosses. Forcing `u0` across can keep alive a symbol the partitioner would otherwise have dropped.
- Multi-symbol relations (`u0 <= u1`) multiply that: now two unbacked symbols must both be bindable at the boundary.
- For the fwd/bwd case, turning a saved SymBool into a saved SymInt changes the saved-tensors ABI, which is exactly what `_is_assert_only_symbool` sidestepped by dropping instead of converting.

So the invariant is clean for the backed-shape-predicate case in this repro (`s72 <= 262144`, where `s72` already crosses via tensor shapes) and gets fiddly for data-dependent unbacked predicates.

#### 4. What I'd suggest concretely

Three layers, in increasing invasiveness:

**(a) Narrowest, and closest to your intent:** handle it at `graph.py:1308-1312`, where inductor first classifies the placeholder:

```python
if isinstance(example, SymTypes):
    expr = _get_placeholder_expr(example.node)
    self.graph_inputs[target] = expr
```

If `expr` is a `SympyBoolean` that isn't a plain `Symbol`, don't register it in `graph_inputs` as a symbol-bearing input at all — treat it like the `BackwardState` / `None` cases at `:1323-1330` (accepted, unused), while ensuring `expr.free_symbols` are in scope so `AssertScalar` can rebuild the check. One place, both wrappers fixed, assert preserved. This is still "inductor tolerates it" rather than "the producer never emits it," but it establishes the `graph_inputs`-only-holds-`Symbol`-for-scalars invariant that every downstream consumer wants.

**(b) Your proposal proper:** enforce at the boundary producer, so relational SymBool never becomes a placeholder. Cleanest long term; requires deciding what to do for the unbacked multi-symbol cases in §3, and touching whichever pass splits the MTIA/piecewise graph, not just `min_cut_rematerialization_partition`.

**(c) The PR as-is:** if it ships as an unblock, I'd at minimum (i) mirror it into `cpp_wrapper_cpu.py:749`, since AOTI hits the identical assert, and (ii) add the negative test (`batch_size=256` raises) so the skip can't silently delete a runtime check.

#### 5. One verification note

The guard depends on `sympy.LessThan` not being a `sympy.Expr`:

```python
if isinstance(value, sympy.logic.boolalg.Boolean) and not isinstance(value, sympy.Expr):
    return
```

In modern sympy `Relational(Boolean, EvalfMixin)`, so this holds and the `not isinstance(..., Expr)` clause is defensive. The unit test asserting it (`test_relational_symbool_input_does_not_bind_symbol`) never actually ran per the test plan — the TestInfra run timed out during listing — so it'd be good to confirm it executes in OSS CI. Incidentally this also unblocks plain `bool` graph inputs, which go through `sympy.sympify(example)` at `graph.py:1313-1317` and yield `BooleanTrue` / `BooleanFalse` — also `Boolean` and not `Expr`, so previously hitting the same assert outside `graph_partition` mode.

</details>
