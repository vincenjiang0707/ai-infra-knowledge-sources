# [PR #198290] [MPS] Fix silent corruption in bmm for non-contiguous inputs > 2**32 elements

source: https://github.com/pytorch/pytorch/pull/198290
state: open | updated: 2026-09-27T01:05:30Z
labels: triaged, open source, release notes: mps, ciflow/mps

## 正文

Fixes #197636.

### Description
This PR addresses a critical bug in the MPS backend where `bmm` silently returns corrupted outputs (and corrupted gradients on the backward pass) when the output exceeds 2**32 elements and the inputs are non-contiguous views (e.g., in eager attention `q @ k.transpose()`). 

**Root Cause:**
When inputs cross the 2**32 element threshold, `bmm_out_mps_impl` routes them to `tiled_bmm_out_mps_impl`. However, `tiled_bmm_out_mps_impl` passes the raw `MTLBuffer` objects directly to `MPSNDArrayDescriptor` without accounting for memory strides. For transposed or sliced inputs, the Metal kernel blindly reads the memory sequentially, causing complete math corruption. 

Because the backward pass calculates gradients using `bmm(G, b.transpose(-1, -2))`, this lack of a `.contiguous()` check also silently corrupts the backward gradients even when the forward pass inputs were perfectly contiguous.

**Fix:**
We explicitly enforce `.contiguous()` on both `batch1` and `batch2` immediately before routing to the `tiled_bmm_out_mps_impl` function. This forces PyTorch to pack the memory into a row-major layout, allowing the Metal tiled kernel to read the correct values safely and resolving both the forward and backward pass corruptions.

### Testing
- Relying on PyTorch CI for MPS regression test suites.
- Resolves the exact reproduction harness outlined in Issue #197636.

### jniimi · 2026-09-23

Thanks for picking this up! I think this change fixes one of the failure modes in #197636, but not all of them. So I'd suggest changing `Fixes #197636` to `Partially addresses #197636`; otherwise GitHub will close the issue on merge.

**Covered by this PR:** the output has more than 2\*\*32 elements and an operand is a non-contiguous view, e.g. `q @ k.transpose(-2, -1)`. This case goes through `tiled_bmm_out_mps_impl`, and as @he-yufeng traced in #197636, that path reads the operands as densely packed. Adding `.contiguous()` before the call should fix it. In my measurements, every wrong element in this case equals the value you get when the transposed operand's storage is read as if it were contiguous, which is consistent with that diagnosis.

**Not covered:**

1. **An input has more than 2\*\*32 elements, all operands are contiguous, and the output is small** (see my comments of 2026-09-19 and 2026-09-21 in #197636, e.g. `w: (65552, 256, 256) @ v: (65552, 256, 64)`). The output has fewer than 2\*\*32 elements, so this never reaches the tiled branch. The batches beyond element 2\*\*32 of the input are silently wrong. This is the second product of eager attention, `softmax(QK^T) @ V`.
2. **The backward pass** (see my comment of 2026-09-21). With contiguous `a: (B, 256, 64)` and `b: (B, 64, 256)` at `B = 65537`, the forward output is correct, but `grad_a` and `grad_b` are wrong in the batches from index 65536 on. The gradients are `G @ b^T` → `(B, 256, 64)` and `a^T @ G` → `(B, 64, 256)`. Their outputs are small, so they do not take the tiled path either. They fail because the input `G` exceeds 2\*\*32 elements, which is case 1 above. The PR description says `.contiguous()` fixes the backward corruption, but I don't think it can: the change only affects the branch taken when the *output* exceeds 2\*\*32 elements.

Your earlier comment mentioned moving the Metal shader indexing to 64-bit. That change would presumably address cases 1 and 2, but it isn't in the current diff.

### FaizPalwala · 2026-09-23

Wow, yeah, you're completely right. I've updated the patch.
The core issue in cases 1 and 2 is that Apple's `MPSGraph` matrix multiplication silently corrupts data when *any* input tensor exceeds 2**32 elements. We were originally only checking if the output exceeded 2**32 before routing to the `tiled_bmm_out_mps_impl` workaround.
I just pushed a commit that changes the dispatch condition to check if `aSize > pow(2, 32) || bSize > pow(2, 32) || resultSize > pow(2, 32)`. If any tensor is massive, it routes to `tiled_bmm`. I also updated the internal `largestSupportedBatchSize` calculation in `tiled_bmm_out_mps_impl` to calculate the max dimension across all three tensors (A, B, and Result) so it correctly chunks massive inputs into safe sizes for `MPSMatrixMultiplication`.
I hope this finally solves all three cases. Let me know how the harness looks on your M2!

### FaizPalwala · 2026-09-27

Thanks for running the sweep — glad to see the main forward and backward cases passing now.

Good catch on the single-matrix `batch2` crash. `tiled_bmm` only tiles the batch dimension and $A$'s rows, leaving $B$ un-tiled. Routing a single $> 2^{32}$ $B$ matrix into `MPSNDArrayMatrixMultiplication` hits kernel dimension limits where `MPSGraph` would otherwise handle it fine.

I just pushed a commit to guard against this:

```cpp
uint64_t bMatrixSize = batch2.size(-2) * batch2.size(-1);
if (resultSize > pow(2, 32) || aSize > pow(2, 32) || (bSize > pow(2, 32) && bMatrixSize <= pow(2, 32)))
```

This keeps batched overflows (like `grad_b = a^T @ G`) on the tiled path while leaving unbatched single large $B$ matrices on `MPSGraph`. 

Let me know if this clears the crash on your end.
