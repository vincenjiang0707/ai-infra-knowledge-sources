## 正文

### 🐛 Describe the bug

This is found by our fuzzer, here is the code to reproduce:

```

import torch
import torch.nn as nn

class Model(nn.Module):
    def __init__(self):
        super().__init__()

    def forward(self, x):
        b = x.expand(2, *x.shape)
        b[0, 0] = 1.0
        idx = (b[0].to(torch.int64))
        return idx


torch.manual_seed(0)
x1 = torch.tensor([[ -1.5410, -0.2934],
        [-2.1788,  0.5684]])
torch.manual_seed(0)
x2 = torch.tensor([[ -1.5410, -0.2934],
        [-2.1788,  0.5684]])
model = Model()
cmodel = torch.compile(Model())
out1 = model(x1)
print(out1)
'''
tensor([[ 1,  1],
        [-2,  0]])
'''
out2 = cmodel(x2)
'''
tensor([[ 0,  1],
        [-2,  0]])
'''
print(out2)
torch.testing.assert_close(out1, out2)

```

Error:

```
AssertionError: Tensor-likes are not equal!

Mismatched elements: 1 / 4 (25.0%)
Greatest absolute difference: 1 at index (0, 0)
Greatest relative difference: inf at index (0, 0)
```

The bug is triggered only when all of the following conditions are met:

1. The expanded tensor `b` has exactly 2 dimensions (e.g., b = x.expand(2, x.shape[0]) where x is 1D).
2. The in-place assignment b[0, 0] = 1.0 is executed first.
3. The slice b[0] (the entire first row) is converted to int64 via .to(torch.int64). Converting b[0, 0] instead does not trigger the bug.

## 评论 (1)

### JingHao-Leon · 2026-09-23

Reproduced on **torch 2.14.0, CPU-only, Apple Silicon arm64 (macOS 26.5)** — same single-element mismatch (eager 1 vs compiled 0 at `[0, 0]`), so this is not CUDA-specific.

I also checked the stated trigger conditions, and the bug is **wider than the "only when" list suggests**. All four variants miscompile on this box:

| variant | eager | compiled | match |
|---|---|---|---|
| issue repro (x 2D → `b` 3D, `b[0].to(int64)`) | `[1, 1, -2, 0]` | `[0, 1, -2, 0]` | ✗ |
| same shape, `b[0, 0].to(int64)` instead | `[1, 1]` | `[0, 1]` | ✗ |
| 2D expand per condition 1 (`x` 1D, `b = x.expand(2, x.shape[0])`), `b[0].to(int64)` | `[1, 0]` | `[0, 0]` | ✗ |
| same, scalar `b[0, 0].to(int64)` (condition 3 claims no trigger) | `[1]` | `[0]` | ✗ |

Two notes for triage:

- The issue's own repro has `x` as 2×2, so `b = x.expand(2, *x.shape)` is 3D — conditions 1 and 3 as written don't describe the repro code above them.
- The scalar-conversion escape hatch claimed in condition 3 doesn't hold: `b[0, 0].to(torch.int64)` miscompiles in both the 3D and the claimed-2D setup. Across all four variants the compiled path reads `0` at the mutated position — which is neither the post-write value (`1`) nor the toward-zero truncation of the pre-write value (`-1` for `-1.5410`), so it isn't reading either the mutated or the original storage.

Repro script for the table: same module with `convert_slice` / 1D-vs-2D `x` swapped; happy to paste a single runnable file if useful.
