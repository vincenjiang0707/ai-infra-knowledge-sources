# [Issue #198583] torch.special.bessel_j0 / bessel_j1 / bessel_y0 lose ~9 significant digits in float64: the Cephes p1evl denominators drop their implied leading 1

source: https://github.com/pytorch/pytorch/issues/198583
state: open | updated: 2026-09-25T04:31:09Z
labels: triage review, module: correctness (silent), module: special, bot-triaged, release triage

## 正文

Description

The CPU implementations of `torch.special.bessel_j0`, `bessel_j1` and `bessel_y0` are ports of Cephes
`j0.c`, `j1.c`, `y0.c`. Cephes evaluates the rational approximations' denominators with `p1evl`, which
treats the coefficient array as a monic polynomial (an implied leading coefficient of 1). The ports
evaluate those denominators with a plain Horner loop seeded at 0, i.e. one degree too low. The results
are wrong by up to ~1e-6 relative in float64 (about 9 lost digits), and the functions jump at the internal
branch point x = 5.

### Steps to reproduce

```python
import mpmath, torch
mpmath.mp.dps = 40
for f, ref, x in [(torch.special.bessel_y0, lambda v: mpmath.bessely(0, v), 5.004),
                  (torch.special.bessel_j1, lambda v: mpmath.besselj(1, v), 7.0),
                  (torch.special.bessel_j0, lambda v: mpmath.besselj(0, v), 5.01)]:
    got = f(torch.tensor(x, dtype=torch.float64)).item()
    want = float(ref(mpmath.mpf(x)))
    print(f.__name__, x, got, want, abs(got - want) / abs(want))
# relative errors ~7e-7, 6e-6, 2e-6 instead of ~1e-15
```

Expected

Relative error near double-precision rounding (~1e-15), as Cephes and `scipy.special.j0/j1/y0` give.



### Versions

Environment

PyTorch 2.14.0 (the latest release, CPU wheel) and 2.12.0, Python 3.12, Ubuntu 24.04, x86_64

## 评论 (1)

### Nicholas022400701 · 2026-09-25

Two more functions in the same header have the same slip, and one of them is off by more than the three above:

- `bessel_y1`: `YQ` (x <= 5) and `QQ` (x > 5) are `p1evl` tables as well. On a 4801-point grid over (0, 1e4] the float64 result is off by up to 8.7e-7 absolute; next to the zero of Y1 at 5.43 that is `-1.0897e-4` for a true value of `-1.0854e-4` (0.4 % relative). Away from the zero, x = 5.26993 gives `0.0549552` for `0.0549557` (1.0e-5 relative), which is worse than any of j0/j1/y0.
- `airy_ai`: `AFD` and `AGD` in the x < -2.09 branch. Up to 3.0e-6 absolute on [-100, 9]; at x = -2.30154 it returns `0.0256290` for `0.0256282` (3.3e-5 relative).

So it is ten accumulators in total: `rq`/`qq` in j0 and j1, `yq`/`qq` in y0 and y1, `afd`/`agd` in airy_ai. Seeding each of them with `1.0` instead of `0.0` is the whole fix.

Why the OpInfo tests do not see it: `torch/testing/_internal/opinfo/definitions/special.py` sets `precisionOverride({torch.float64: 1e-05})` for all five ops and for the two `_refs` mirrors, and every wrong value on the grid is below 1e-5 absolute. I compiled `Math.h` on its own with g++ (the compiled `bessel_j0_forward<double>` reproduces `torch.special.bessel_j0` bit for bit) and compared with scipy on 20000 uniform samples in [-9, 9], the `make_tensor` range of the reference tests, at the default float64 tolerance (rtol 1e-7, atol 1e-7): the current code fails 1596 (j0), 605 (j1), 248 (y0), 2330 (y1) and 564 (airy_ai) of them; with the ten `1.0` seeds every one of the 100000 values is bit-identical to scipy, and the large-value samples of j0/j1/y0/y1 (+-501 ... +-1e20) pass too. Against mpmath at 120 bits the fixed code stays within 1.3e-13 (j0), 1.1e-12 (j1), 5.0e-14 (y0), 2.5e-12 (y1) and 5.9e-13 (airy_ai) relative on the affected branches, median 1 to 3 ulps. float32 is unchanged before and after: its error is dominated by evaluating the double-precision Cephes tables in float32 (about 1e-5 relative near the zeros), so the float32 overrides have to stay.
