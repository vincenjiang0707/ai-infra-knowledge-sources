# [PR #196920] [ROCm] Always eagerly allocate hipBLAS(Lt) workspaces

state: open | updated: 2026-09-25T12:01:28Z

## 正文

## Summary

- Make per-operation BLAS workspaces the default on ROCm, as they are on CUDA since #194311. ATen's hipBLAS and hipBLASLt operations allocate their workspace from the HIP caching allocator for each operation, so during capture it comes from the graph's memory pool. `TORCH_CUBLAS_WORKSPACE_CACHE=1` keeps the previous persistent workspace cache.
- Run ATen's rocBLAS operations on internal per-thread handles that release the arena rocBLAS allocates when it creates a handle. Binding a workspace makes rocBLAS free that arena, and the free is illegal under stream capture.
- Give each (thread, stream) its own public handle, the one `torch.cuda.current_blas_handle()` and `at::cuda::getCurrentCUDABlasHandle()` return. ATen never binds a workspace to it, so it keeps its rocBLAS arena, and a workspace a caller binds stays bound. `capture_begin` keeps one spare, so the first request on a capture stream does not create a handle during capture.
- Route TunableOp's rocBLAS GEMMs and solution listing through the internal handle and its per-operation workspace, and give its hipBLASLt GEMMs the per-operation hipBLASLt workspace.
- Enable the existing eager-workspace tests on ROCm, add a C++ handle-pool test and ROCm graph-capture tests, isolate the FSDP2 MemTracker tests from BLAS workspaces, and document the ROCm behaviour in the HIP notes.

## Motivation

A persistently cached workspace is shared by every graph captured on the same handle and stream, so replaying one graph can overwrite a workspace another graph still uses. A per-operation workspace allocated during capture comes from that graph's pool, so no two graphs share one. `test_graph_capture_cublas_workspace_separate_graphs` catches this: with `TORCH_CUBLAS_WORKSPACE_CACHE=1` it faults on SM90 and gfx90a and corrupts its canary on gfx950 (MI355X) and gfx942 (MI308X), and it passes with per-operation workspaces.

## Why ROCm needs a public handle per stream

cuBLAS resets a handle to its default workspace pool on every `cublasSetStream`, and that pool is guarded against concurrent use ([cuBLAS documentation](https://docs.nvidia.com/cuda/cublas/index.html#cublassetworkspace)). rocBLAS has neither: a handle's arena is one buffer, and `rocblas_set_stream` keeps whatever workspace is bound and does not wait for the old stream. A public handle shared by a thread's streams could therefore run GEMMs on two streams in the same arena at once, so on ROCm each stream gets its own.

## Behaviour for callers of the public handle on ROCm

- `torch.cuda.current_blas_handle()` returns a different handle on each stream. A caller that keeps a handle and moves it to another stream with `rocblas_set_stream` must synchronize the old stream first, as rocBLAS requires.
- A workspace bound with `rocblas_set_workspace` stays bound, even after the buffer is freed and after the thread exits and the handle passes to another thread. Unbind it with `rocblas_set_workspace(handle, nullptr, 0)` before freeing the buffer. The handle then has no workspace of its own: its GEMMs use kernels that need none, and other calls make rocBLAS allocate one, which capture does not allow.
- `HIPBLAS_WORKSPACE_CONFIG=:0:0` makes rocBLAS GEMMs use kernels that need no workspace, but other rocBLAS calls such as `torch.dot` then allocate their own, so they cannot be captured.

The first rocBLAS use on a thread cannot be captured, in cached or eager mode, and this PR does not change that. On MI308X, capturing `torch.dot` on a new thread whose earlier GEMMs all went to hipBLASLt fails at the merge base and with this PR alike. Handle initialization and TunableOp tuning must happen before capture. This is tracked by [ROCm/rocm-libraries#11838](https://github.com/ROCm/rocm-libraries/issues/11838).

## Cost

- Each public handle keeps the arena rocBLAS allocates when it creates the handle, outside the caching allocator. On MI355X a new public handle took 162 MiB outside the caching allocator, 128 MiB of it the arena. The arena size depends on the GPU and the rocBLAS version.
- There is one public handle per (thread, stream) that requests it, plus one spare once a capture has begun on a device where a public handle was requested. Handles are never destroyed, and an exited thread's handles pass to other threads and streams, so this memory stays allocated for the life of the process.
- ATen's own rocBLAS operations use the internal handles, which hold no arena, so a process that never requests the public handle pays none of this. Two ATen paths still request it and so create a public handle on each stream they run on: MAGMA queue creation and the batched BLAS3 LU kernel.
- Per-operation workspaces cost a caching-allocator allocation per operation; see Performance.

## Validation

MI355X (gfx950) and MI308X (gfx942), same results on both:

- `hip_cublas_handle_pool_test`: 6 pass and 1 skips; with `TORCH_CUBLAS_WORKSPACE_CACHE=1`, 2 pass and the eager-only tests skip.
- `test/test_cuda.py -k cublas -k workspace -k blas_handle`: 22 tests pass, 3 skip. With `TORCH_CUBLAS_WORKSPACE_CACHE=1`, `test_cublaslt_workspace_eager_resize_and_zero` and both shapes of `test_graph_capture_cublas_workspace_separate_graphs` fail, as expected; the separate-graphs test fails in each of three runs and passes in each of three runs without it.
- `test_graph_capture_tunableop_cublas_workspace` passes and replays a rocBLAS solution; it skips when TunableOp picks none.
- A TunableOp GEMM on a new stream no longer creates a public handle: 0 MiB outside the caching allocator, down from 162 MiB (MI355X).
- On MI355X, the 43 `test/test_linalg.py` TunableOp tests, each in its own process, give the same results at the merge base and with this PR.
- FSDP2 MemTracker tests pass with per-operation workspaces and with `TORCH_CUBLAS_WORKSPACE_CACHE=1`.
- Bounded workspace OOM tests raise a normal `OutOfMemoryError` and recover, for rocBLAS (128 MiB workspace) and hipBLASLt (80 MiB), in both modes.

## Performance

Following #194311: BF16 `torch.mm`, synchronized `torch.utils.benchmark.Timer.blocked_autorange(min_run_time=2.0)`, shapes labelled `(M,N,K)`, and one process per (mode, backend) because the caching mode latches into a function-local static on first use.

Two adjustments were needed for the numbers to be stable on these parts.

First, the dominant noise term is a per-process offset, not within-process jitter: the spread of per-process medians reached 4.3 us while the within-process Timer IQR is 0.01-0.8 us. So the run uses **20 alternating-order trials** and reports a **paired** statistic - `eager - cached` within a single trial - with a 95% bootstrap confidence interval and the per-trial sign count. Raising `min_run_time` does not help, since it only shrinks the term that was already small.

Second, that offset was tracked to CPU socket placement. The `gfx950` host is dual-socket with the GPU on one socket's PCIe root; at 11-17 us these GEMMs are dispatch-bound, so the measurement is dominated by host-side launch traffic, and a process scheduled onto the far socket pays an interconnect hop on every launch. Five pinned processes per socket measured +0.6 us for the far socket, and pinning collapsed the per-process spread from 1.95 us to 0.39 us. Both arms are therefore pinned to the GPU-local CPU list. The `gfx942` numbers are unpinned but do not need this: their same-mode control is 0.023 us median / 0.156 us worst case.

The control referred to above is a same-mode null - splitting one mode's own trials in half and differencing them, where the true answer is zero by construction, so the result is the noise floor of the instrument. Two further checks on the protocol: a negative delta is not physically possible here, since eager performs strictly more allocator work than cached, so any negative row indicates drift rather than a speedup; and the eager path was confirmed active in each binary by measuring per-operation workspace scratch after a warmup GEMM, 76-80 MiB in eager mode against 0 in cached mode.

This part carries the least per-process drift of the two, and unlike gfx950 it spans both duration regimes, so the rows are bimodal by operation duration:

- **Short, launch-bound** (11-19 us; the 64^3 and 256^3 shapes) - eager costs +0.13 to +0.33 us, three of four significant, worst relative case +2.93%.
- **Long, GPU-bound** (24-484 us; the 1024^3 and large-K shapes) - -0.02 to +0.00 us, none significant, and the intervals exclude +0.3 us, so the cost is absent rather than merely unresolvable.

The two regimes are not averaged together here, since a pooled figure would mix a real +0.3 us against four rows pinned at zero.

### Interpretation

The eager cost is CPU-side caching-allocator bookkeeping, and `torch.mm` is asynchronous. On a long GEMM that work overlaps GPU execution of the preceding operation and is free; on a short one, dispatch is the critical path and it shows up in full. The two parts agree on this: every gfx950 shape is launch-bound and all eight carry the cost at +0.16 us, while on gfx942 only the launch-bound rows carry it, at +0.13 to +0.33 us, and the GPU-bound rows are pinned at zero with intervals that exclude +0.3 us. So the data is consistent with a fixed per-operation cost of roughly 0.15-0.35 us, worth at most a few percent on operations short enough that launch overhead already dominates, and absent on any GEMM doing substantial work.

That is the same order as CUDA PR #194311 (0.07-0.85 us / 0.5-5.1%), and below it in absolute terms, despite the hipBLASLt workspace being 76-80 MiB against cuBLASLt's 1 MiB - the caching allocator returns the same block on every call, so workspace size does not enter the per-operation cost.

### jeffdaily · 2026-09-22

I looked into two things on ROCm after this change: what the public BLAS handle looks like, and whether the unskipped workspace test still catches the bug. Summary below (analysis drafted with Claude; the numbers are from my runs on gfx90a).

> **1. The public handle on ROCm is left with no usable workspace.** ATen's own ops get per-op caching-allocator workspaces through `getCurrentCUDABlasHandleWithWorkspace()`, which is the goal. But `getCurrentCUDABlasHandle()` / `torch.cuda.current_blas_handle()` (extensions, AOTI shim) now return a handle after `hipblasSetWorkspace(handle, nullptr, 0)`. On CUDA the equivalent state is cuBLAS's default workspace, which is usable. On ROCm it is rocBLAS-managed with size 0:
>
> - GEMMs silently select kernels that need no workspace. gfx90a, bf16, `rocblas_gemm_ex`, bound vs unbound: (32,10944,2048) 0.063 -> 0.286 ms, (32,65536,2048) 0.34 -> 1.72 ms, and the outputs differ. Where rocBLAS routes a GEMM to hipBLASLt internally, the algo workspace is capped at the handle's `get_available_workspace()`, which is also 0 here.
> - Non-GEMM calls (e.g. `rocblas_sdot`) regrow a 32 MiB arena with a synchronous `hipMalloc` outside the caching allocator, and the next ATen bind `hipFree`s it.
> - The workaround documented in `hip.rst` and `current_blas_handle` (bind with `rocblas_set_workspace` before capture) does not stick: `~CUDABlasHandleWithWorkspace` unbinds unconditionally after every ATen BLAS op on that thread's handle.
>
> Before this PR, ROCm bound ATen's cached workspace to this handle, so this is a regression for external callers. Suggested fix, in two parts:
>
> - In the `WorkspaceMode::Default` case of `setupCUDABlasHandle` on ROCm, bind the cached per-(handle, stream) workspace (`setWorkspaceForHandle`) instead of unbinding. ATen ops stay eager; only the public handle keeps a persistent workspace. This matches what `getCUDABlasLtWorkspace()` already hands to external hipBLASLt callers, which is cache-owned even with caching disabled.
> - In `~CUDABlasHandleWithWorkspace` on ROCm, re-bind that cached workspace for `(handle_, stream_)` instead of calling `hipblasSetWorkspace(handle_, nullptr, 0)`. Only re-bind if a cached entry already exists, and unbind otherwise, so the destructor never allocates, which matters under capture. The handle still stops referencing the eager block, and the public handle keeps its binding between ATen ops. From rocBLAS's point of view the outgoing binding is user-owned, so the re-bind frees nothing.
>
> The cross-graph hazard then remains only for external hipBLAS calls captured on the public handle, the same as for external hipBLASLt callers today.
>
> **2. The ROCm shape swap makes `test_graph_capture_cublas_workspace_separate_graphs` vacuous on gfx90a.** I ran the test body against main (the pre-fix cached workspace) in fresh processes, 3 runs per shape:
>
> - original `(32768, 640, 640)`: memory access fault 3/3
> - this PR's ROCm shape `(32, 65536, 2048)`: pass 3/3
>
> So on gfx90a the new shape passes with or without the fix. The original shape does exercise the workspace on gfx9: the split-K GEMM is the backward's weight gradient (K=32768), not the forward. Please keep the original shape on ROCm (run both if gfx942 needs the new one), and note in the test which archs were shown to fail with `TORCH_CUBLAS_WORKSPACE_CACHE=1`. The cross-thread test's comment ("gfx9 needs a larger K than SM90") also doesn't hold on gfx90a, where K=10944 already selects a workspace-using kernel (bound 0.063 ms vs unbound 0.286 ms).
