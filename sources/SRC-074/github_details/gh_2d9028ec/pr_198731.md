# [PR #198731] [dynamo] Add experimental speculative guard evaluation

## 正文

> ## Summary
>
> This draft adds an experimental, disabled-by-default Dynamo mechanism for
> overlapping cache-entry guard evaluation with execution of a predicted
> backend artifact.
>
> An opted-in backend callable can attach a private speculative descriptor. On
> a cache hit, Dynamo asks the descriptor to launch a transactionally isolated
> artifact, performs the normal complete guard lookup, and commits only if the
> predicted cache entry was selected. A mismatch, cache miss, guard-hook
> rejection, or error aborts the speculative ticket before the normal path
> continues.
>
> Inductor provides an initial conservative implementation for single-device,
> mutation-free CUDA inference graphs. This is a draft for feedback on the
> Dynamo/backend boundary, admission rules, and failure semantics; the feature
> remains off by default.
>
> ## Motivation
>
> Dynamo guard lookup runs before the compiled artifact and can leave an idle
> GPU waiting on latency-sensitive inference. In local Qwen3-8B experiments on
> an NVIDIA A100:
>
> - mutation-free prefill median improved from 20.01 ms to 16.76 ms (16.3%);
> - single-token decode hit median improved from 14.15 ms to 12.95 ms (8.5%);
> - logits and the complete KV cache matched the reference bitwise; and
> - two decode mispredictions cost 26.46 ms and 69.20 ms, demonstrating that
>   hit rate and tail latency are central constraints.
>
> Kineto confirmed that cache lookup ran while the predicted device artifact
> was active. These measurements show available latency headroom, not that the
> mechanism is universally profitable; queued serving can already hide much of
> the same CPU work.
>
> ## Design
>
> - Add private `SpeculationDescriptor.launch()` and
>   `SpeculationTicket.commit()/abort()` protocols, plus a bytecode-resume
>   ticket for backends that produce flattened graph outputs.
> - Propagate an opted-in descriptor through `GuardedCode` into `CacheEntry`.
> - Predict the first backend-compatible entry in normal cache order.
> - Give `launch()` a copy of frame locals, then run the existing cache lookup
>   and guard-complete hook unchanged.
> - Compare the selected and predicted guard managers by retained identity;
>   commit only on an exact match.
> - Re-fetch cache state after arbitrary descriptor code, clear descriptors on
>   invalidation, and preserve primary exceptions and eval-frame state.
> - Keep the ordinary path cheap with an O(1) count of descriptor-bearing
>   entries.
> - Add Kineto ranges for speculative launch, commit, and abort.
> - Let eligible Inductor callables enqueue once, retain private outputs, and
>   hand those outputs to the ordinary Dynamo bytecode after an exact hit. This
>   preserves arbitrary Python output reconstruction.
> - Persist both positive and negative Inductor eligibility decisions through
>   FX and AOTAutograd caches.
>
> Dynamo only captures descriptors for fullgraph, non-export, non-package
> compilations without recorded external Python side effects, backward state,
> or inlined `__torch_function__` subclass dispatch. The backend remains
> responsible for artifact-level safety, including mutation, aliasing, RNG,
> device/stream assumptions, backend specialization, and concurrency.
>
> Inductor currently requires exact direct-local tensor metadata; treats
> weakly held warmed module parameters and buffers as static inputs guarded by
> exact tensor metadata and version; and rejects mutation, RNG, effect tokens,
> CUDA Graph Trees, graph partitions, unsupported source forms, generated
> device assertions, and indirect memory accesses. Commit inserts a CUDA-event
> dependency, while abort synchronizes the event before fallback. Admission is
> checked first on the AOT graph and again after lowering so untagged operations
> such as `aten.gather` are rejected when their generated kernels contain
> indirect memory accesses.
>
> With exact parameter checks enabled, two controlled Qwen prefill runs measured
> 25.88 ms versus 24.10 ms and 21.00 ms versus 19.30 ms (6.9-8.1%). They
> explicitly supplied the model invariant that token IDs were in range.
> Automatic admission rejects Qwen today because `aten.index.Tensor` can
> asynchronously device-assert on a wrong-path launch; the unsafe waiver is not
> part of this diff.
>
> The detailed design and proposed Inductor/KV-cache follow-up are documented
> in
> `docs/source/user_guide/torch_compiler/compile/speculative_guard_evaluation.md`.
>
> ## Feedback requested
>
> - Is a backend-owned launch/commit/abort descriptor the right abstraction?
> - Should admission be split into `prepare()` and `launch()` so launch cannot
>   fail after enqueue but before returning a ticket?
> - Are the initial Dynamo eligibility checks appropriately conservative?
> - Is the two-stage AOT/Inductor admission check the right place to certify a
>   mutation-free, non-faulting artifact?
> - What interface should certify value-domain invariants such as valid token
>   ranges without synchronizing the device before launch?
> - Where should an append-only KV-cache transaction live?
>
