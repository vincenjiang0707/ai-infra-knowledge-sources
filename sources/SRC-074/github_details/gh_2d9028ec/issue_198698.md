# [Issue #198698] MPS: large-tensor tests gate on macOS version instead of available memory

source: https://github.com/pytorch/pytorch/issues/198698
state: open | updated: 2026-09-26T03:46:14Z
labels: module: tests, triaged, module: mps, bot-triaged

## 正文

Four MPS tests gate on `MACOS_VERSION` as a stand-in for how much memory the host has:

| Test | Gate |
|---|---|
| `test_nn.py::TestNNDeviceTypeMPS::test_grid_sample_large_index_2d_mps_float32` | `skipMPSIf(MACOS_VERSION < 15.0, "macOS 14 runners have lower memory")` |
| `test_nn.py::TestNNDeviceTypeMPS::test_grid_sample_large_index_3d_mps_float32` | same |
| `test_mps.py::TestMPS::test_large_bmm_float16` | `xfailIf(MACOS_VERSION < 15.0)` |
| `test_mps.py::TestMPS::test_large_bmm_bfloat16` | same |

That held only while macOS 14 meant M1 (16 GB) and macOS 15 meant M2 Pro (32 GB). Once M1 runners moved to macOS 15, the gates opened on 16 GB hosts and all four began failing consistently — see run [36181945977](https://github.com/pytorch/pytorch/actions/runs/36181945977) on `macos-m1-15`, green on `macos-m2-15`.

Footprints, from the test bodies:

- `grid_sample_large_index_2d` / `3d`: ~8.2 GiB each, per the `largeTensorTest` expression.
- `test_large_bmm`: ~8.35 GiB on device — the `11x20064x20064` output alone is 8.25 GiB. This test has no `largeTensorTest` or `largeMPSBufferTest` decorator, so nothing checks memory before it allocates.

The two `grid_sample` tests do carry `largeTensorTest`, and `_has_sufficient_memory` routes `mps` through the psutil path, which is correct for unified memory. It compares against available memory with no headroom, so a 16 GB host passes the check and then fails the test — which is why the manual `skipMPSIf` was layered on top.

#198689 restored green by widening the gates to `or IS_APPLE_M1`, which is still a hardware proxy rather than a memory check.

### shyamsharmas124-commits · 2026-09-26

Hi @huydhn 
The gate breaking here isn't a memory problem so much as a proxy problem — macOS version was only ever a stand-in for host memory, and it held by coincidence (M1→14, M2 Pro→15) rather than by construction. Once that pairing broke, the gate stopped meaning anything.

Worth noting `test_large_bmm_float16`/`bfloat16` have no memory check at all today — they just allocate the ~8.35 GiB output unconditionally. And the `largeTensorTest`-gated `grid_sample` tests aren't actually safe either: `_has_sufficient_memory` compares against available memory with zero headroom, so a 16 GB host with nothing else running passes the check and then OOMs anyway — which is presumably why the manual `skipMPSIf` got layered on top in the first place.

Two ways to close this properly, happy to take either:

1. Add headroom to `_has_sufficient_memory` so it actually fails hosts too close to the line, and put a memory-check decorator on `test_large_bmm_*`, which is currently unguarded entirely.
2. Same as above, plus drop the `MACOS_VERSION`/`IS_APPLE_M1` gates once the memory check can be trusted on its own — otherwise they just sit there as a second, weaker check that can silently drift out of sync again the next time runner assignment changes, same as this time.

I'd lean toward (2) since (1) alone leaves the version-based gates in as unnecessary and misleading once the real check works, but wanted to check before ripping them out — is there a reason beyond memory (flakiness, perf budget on those specific runners) that the macOS-14 exclusion existed, or was it always purely a memory proxy? If it's purely memory, I can put up a PR for (2).
