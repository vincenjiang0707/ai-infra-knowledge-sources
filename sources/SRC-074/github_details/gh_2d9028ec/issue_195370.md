# [Issue #195370] `symm_mem.get`: docs + test treat a "regular CUDA tensor" as a valid destination, but NVSHMEM requires `dest` to be symmetric / registered / P2P-backed

source: https://github.com/pytorch/pytorch/issues/195370
state: open | updated: 2026-09-25T21:04:18Z
labels: oncall: distributed, triaged, bot-triaged, oncall: distributed infra

## 正文

### 🐛 Describe the bug

The symmetric-memory one-sided `get` API documents the local destination `dst` as being allowed to be **any** regular CUDA tensor, and its test exercises exactly that. This is only valid on P2P (intra-node NVLink) transports; it violates the NVSHMEM RMA contract for the local (`dest`) buffer in general and is expected to fail on a remote / IBRC (inter-node RDMA) transport.

#### 1. NVIDIA NVSHMEM docs (RMA get)

https://docs.nvidia.com/nvshmem/api/latest/gen/api/rma.html

For a GET, the local destination is constrained (verbatim):
> "Symmetric address or host/device address registered via
> `nvshmemx_buffer_register` of the data object to be updated. Additionally,
> it can also be backed by device shared memory when devices are connected via
> peer-to-peer transport."

And the remote source (verbatim):
> "Symmetric address of the source data object."

So `dest` must be (a) symmetric, (b) registered via `nvshmemx_buffer_register`, or (c) device shared memory when the peer is P2P-reachable. A plain, unregistered CUDA allocation is not a generally valid `dest`.

#### 2. PyTorch docs claim it unconditionally

`docs/source/symmetric_memory.md` (One-sided get):
> `dst` may be a regular CUDA tensor or another symmetric tensor; it must be on
> the same device as `hdl` and backed by contiguous memory.

`torch/distributed/_symmetric_memory/__init__.py`, `get()` docstring:
> `dst` can be a regular CUDA tensor or a symmetric-memory tensor; it must be on
> the same device as `hdl` and backed by contiguous memory.

#### 3. The implementation passes that tensor straight in as NVSHMEM `dest`

`torch/csrc/distributed/c10d/symm_mem/nvshmem_extension.cu`, `nvshmem_get_out`:
```cpp
TORCH_CHECK(dst.is_cuda(), "symm_mem.get: expected a CUDA tensor");
...
nvshmemx_getmem_on_stream(
    dst.mutable_data_ptr(), src_ptr, nbytes, global_peer, stream);
```
`dst` is validated only for `is_cuda()` + contiguity + device match, never for being symmetric or registered before use as the NVSHMEM `dest`. The remote `source` (`src_ptr`, from `hdl->get_buffer_ptrs()`) is correctly symmetric.

#### 4. The test only covers the P2P-valid case

`test/distributed/test_nvshmem.py::NVSHMEMSymmetricMemoryTest::test_get`
constructs `dst` with `torch.empty*`, i.e. a regular CUDA tensor:
```python
dst = torch.empty_like(src)
symm_mem.get(dst, hdl, peer=1)
...
dst = torch.empty(numel, dtype=dtype, device=self.device)
larger_dst = torch.full((numel + 1,), -1, dtype=dtype, device=self.device)
noncontig_dst = torch.empty(2 * numel, dtype=dtype, device=self.device)[::2]
```
On a P2P transport (intra-node NVLink) the local `dst` is directly writable by the peer without registration, matching NVSHMEM's "device shared memory when devices are connected via peer-to-peer transport" allowance, so the test passes.
On a transport that requires the local buffer to be registered (IBRC / inter-node RDMA), a plain unregistered CUDA allocation is not a valid `dest`, so the same test is expected to fail or misbehave. Allocating `dst` from the symmetric heap (`symm_mem.empty`) makes it a valid `dest` on all transports.

### Discussion and potential fixes

- Fix the docs to state that `dst` must be a symmetric-memory tensor, or a
  regular CUDA tensor **only** when the peer is P2P-reachable (otherwise it must
  be registered via `nvshmemx_buffer_register`).
- Update `test_get` to allocate `dst` from symmetric memory so it is transport-agnostic (and/or add a remote-transport variant). This, however, would be more meaningful if we set up a cross-node symmetric memory test infra, since the current symmetric memory tests are intranode only, these bugs do not result in a test failure.
- Optionally, add a runtime check in `nvshmem_get_out` for the non-P2P case.
