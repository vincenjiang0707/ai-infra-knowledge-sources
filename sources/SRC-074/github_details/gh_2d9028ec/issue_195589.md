# [Issue #195589] [inductor] SDPA fusion on 5-D attention operands produces an invalid addmm: RuntimeError: a must be 2D

source: https://github.com/pytorch/pytorch/issues/195589
state: open | updated: 2026-09-25T23:44:34Z
labels: triaged, oncall: pt2, module: inductor, module: sdpa, bot-triaged, release triage

## 正文

## 🐛 Describe the bug

An attention block written over 5-D tensors compiles into an invalid `addmm` and fails with `RuntimeError: a must be 2D`. Eager runs the same model fine. Disabling the pattern matcher makes it compile and match eager, and a monkeypatch shows `_sfdp_replacement_1` firing on the way in, so the SDPA fusion is what introduces the bad graph.

## Reproduction

```python
import torch
import torch.nn as nn

D = 8

class M(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(D, D)

    def forward(self, q, k, v):
        q5 = q.view(1, 1, 2, 1, D)
        k5 = k.view(1, 1, 2, 2, D)
        v5 = v.view(1, 1, 2, 2, D)
        out = (torch.matmul(q5, k5.transpose(-2, -1)) / D ** 0.5).softmax(-1).matmul(v5)
        return self.fc(out.view(2, 1, D))

m = M().eval()
q = torch.randn(2, 1, D)
k = torch.randn(2, 2, D)
v = torch.randn(2, 2, D)

with torch.no_grad():
    print("eager:", tuple(m(q, k, v).shape))
    torch.compile(m, backend="inductor")(q, k, v)
```

```
eager: (2, 1, 8)
torch._dynamo.exc.InductorError: RuntimeError: a must be 2D
```

The failure is reported on an `addmm` the compiler itself produced from the `nn.Linear`:

```
While executing %addmm_3 : [num_users=1] = call_function[target=torch.ops.aten.addmm.default](args = (%arg10_1, %view_default_5, %permute...))
```

## It is the SDPA fusion

```python
import torch._inductor.config as cfg
cfg.pattern_matcher = False
```

| | run 1 | run 2 |
|---|---|---|
| `pattern_matcher = True` (default) | `RuntimeError: a must be 2D` | `RuntimeError: a must be 2D` |
| `pattern_matcher = False` | OK, maxdiff `5.96e-08` | OK, maxdiff `5.96e-08` |

Wrapping every `_sfdp_replacement_*` to record which one runs shows **`_sfdp_replacement_1`** firing before the failure.

## What is needed to trigger it

All three parts are required; dropping any one compiles cleanly:

| model | compiled |
|---|---|
| 5-D attention → `view` back to 3-D → `nn.Linear` | **RuntimeError: a must be 2D** |
| same without the `nn.Linear` | OK |
| same without the 5-D `view` (plain 3-D attention) | OK |
| same without the `view` back to 3-D | OK |
| 5-D tensor → `view` → `nn.Linear`, no attention pattern | OK |
| attention without the `/ scale` (so the pattern does not match) | OK |
| attention without the `softmax` (so the pattern does not match) | OK |

The last two are the point: the failure only appears when the ops form the complete `matmul → div → softmax → matmul` shape that `_sfdp_pattern_*` matches.

## Versions

Reproduces identically on:

- PyTorch `2.11.0`
- PyTorch `2.14.0+cpu`

CPU, Linux x86_64, Python 3.11. `D = 768` (the original size) behaves the same as `D = 8`.

## Additional context

I searched for existing reports of `a must be 2D` from Inductor and of the SDPA fusion on higher-rank inputs and found nothing matching. The nearest SDPA-fusion reports I am aware of concern which tensor the matcher binds as `key` (#195282, #195320, fixed by #195383) and the type of the `scale` argument (#191203, fixed by #191496); this one is about the rank of the attention operands rather than either of those.

Found by differential testing over StarCoder-generated programs; reduced from a corpus program that built multi-head attention by viewing its operands up to 5-D and back.

### egeboy35 · 2026-09-02

Reproduced on CPU. Two things I measured that change the framing, and one mechanism note.

**It is not specific to 5-D.** Holding the model shape fixed and varying only the attention rank:

| rank | eager | compiled |
|---|---|---|
| 3-D | (2, 1, 8) | (2, 1, 8), matches |
| 4-D | (2, 1, 8) | `RuntimeError: a must be 2D` |
| 5-D | (2, 1, 8) | `RuntimeError: a must be 2D` |
| 6-D | (2, 1, 8) | `RuntimeError: a must be 2D` |

4-D is the rank the patterns are traced for, and it fails too.

**The trigger is the rank-reducing `view` before the `Linear`, not the attention rank.** Same 4-D attention, only the tail varies:

```
Linear directly on the 4-D output      -> OK
out.view(2, 1, D) then Linear          -> RuntimeError: a must be 2D
no Linear at all                       -> OK
out.reshape(-1, D) then Linear         -> OK
```

**On the mechanism.** `scaled_dot_product_attention` in eager accepts 3-, 4-, 5- and 6-D and is numerically identical to the explicit `matmul/softmax/matmul` at every one of those ranks, with identical strides — so the replacement is not wrong in itself, and a plain "reject unless 4-D" guard in `_sfdp_params_check` would decline fusions that eager handles fine.

What is different under inductor is which kernel the replacement resolves to. `torch/_decomp/decompositions.py:5836` does check `query.dim() == 4 and key.dim() == 4 and value.dim() == 4`, but that decomposition is removed from inductor's table at `torch/_inductor/decomposition.py:122` ("See comments in torch/\_decomp/decompositions.py") and registered as a fallback instead at `torch/_inductor/lowering.py:3956`, so that rank check never runs on this path. The failure then surfaces as `meta_mm`'s `torch._check(a.dim() == 2, "a must be 2D")`.

I have not pinned down the exact node that ends up non-2-D, so I am not proposing a patch yet. Posting the above because the "5-D operands" framing sends the fix at the wrong constraint, and because `pattern_matcher=False` producing a result equal to eager rules out the replacement being semantically wrong.

Happy to keep digging unless someone is already on it.

### egeboy35 · 2026-09-25

I closed my PR #195706 because this looks fixed on main by #195383. Summary of the check below (drafted with Claude; I reviewed it and re-ran it):

> On main the SDPA pattern matcher re-traces each match with the real inputs. For the reproducer above, the old match ran past the attention output into the `view(2, 8)` that feeds the `Linear`. The re-traced pattern does not match there, so the attention is left unfused and lowering no longer hits `a must be 2D`. Checked by loading main's `pattern_matcher.py` and `fuse_attention.py` over an Aug-21 build, through lowering only.
