# [PR #198620] [dynamo] Acquire the pairwise iterator when called

## 正文

I reproduced this myself with a small script. In plain Python, `itertools.pairwise(0)` raises `TypeError` right at the call. Under `torch.compile`, the same call inside `try/except TypeError` returned as if nothing was wrong, which is a silent wrong result; I saw the same pattern with a zero `range` step. The cause is `yield`: because of it, the body of Dynamo's `pairwise` never runs when it is only called. With this PR the `TypeError` is raised at the call as in eager.

_(My comment above was assembled from my own notes while reviewing this change and translated from Turkish with AI assistance.)_

> **AI-generated technical summary (Claude), reviewed by me:**
>
> Part of #195901 (acquire the `pairwise` iterator when called).
>
> The `itertools.pairwise` polyfill was a generator function, so its body, including the `iter()` call on the input, ran only when the result was consumed. CPython's `itertools.pairwise` acquires the input iterator at call time. The polyfill now calls `iter()` in an outer function and returns an inner generator for the pairs, so pairs are still produced lazily and a non-iterable raises `TypeError` at the call. Keeping a single generator function would leave the timing mismatch intact.
>
> **Tests**
>
> - `test_polyfills.py::TestPairwise::test_call_time_iteration`: under `fullgraph=True`, calling `pairwise` inside `try/except TypeError` matches eager for `0`, `None`, `[]` and `[1, 2, 3]`, and `list(pairwise(...))` matches eager for `[]`, `[1]` and `[1, 2, 3]`. Fails without the fix.
>
> CPython `test_itertools` under Dynamo: `TestBasicOps.test_pairwise` and `TestVariousIteratorArgs.test_pairwise` go from error to passing and no test goes from passing to failing; their expected-failure markers are removed. The other tests in `test/dynamo/test_polyfills.py` show the same results with and without the change.
