# [PR #198755] [dynamo] Don't import DTensor, ONNX and networkx to build trace rules

Two eager imports that the torch.compile warm path doesn't need.

`get_torch_obj_rule_map()` resolves every string in `torch_name_rule_map`
to its object, importing the object's module if necessary. The map is first
built while Dynamo is being imported (`substitute_in_graph` checks each
polyfill against it), so building it imported torch.distributed.tensor
(for `DTensor.from_local`) and torch.onnx (for two entries). Together that
was ~130ms, including the DTensor op registrations. The build now skips
entries whose module isn't in sys.modules yet and keeps them pending per
module. `get_torch_obj_rule_map()` adds a module's pending rules once that
module shows up in sys.modules. This is safe because an object can't reach
Dynamo before the module that defines it has been imported. The cached
builder returns the pending dict along with the map, so the existing
`cache_clear()` and the tests that patch in the uncached builder keep
working. A lookup still costs ~0.24us, since only ~5 modules are ever
pending. An alternative was to defer only the polyfill duplicate check, but
tracing calls the same map, so DTensor would just have been imported during
the first compile instead.

partitioners.py imported GraphInfoProvider, KnapsackEvaluator and
minimum_cut at module level, and all three import networkx (~75ms). The
min-cut path already imports networkx lazily in `solve_min_cut`, so
`minimum_cut` is now imported there too. The other two are imported in the
experimental dynamic_memory_budget_dp branch, the only place that uses
them. A warm FX-graph-cache hit never partitions, so networkx isn't needed
at all.

After these changes, `import torch._dynamo` takes 0.53s instead of 0.70s.
