# [Issue #161129] autograd assertion error in cuda backend when privateuse1 is renamed

## 正文

### 🐛 Describe the bug

Calling `torch.utils.rename_privateuse1_backend` triggers the following assert in autograd with the CUDA backend starting with PyTorch 2.8.0 and later.

The same code works correctly in PyTorch 2.7.1. Note that the privateuse1 backend is merely registered, while the rest of code entirely uses the built-in CUDA backend.

```
import torch
import numpy

def main():
    from foo_module import FooModule
    torch.utils.rename_privateuse1_backend("foo") # commenting this line fixes the assert error
    # torch._register_device_module("foo", FooModule)
    # torch.utils.generate_methods_for_privateuse1_backend(
    #     for_tensor=True, for_module=True, for_storage=True, unsupported_dtype=[]
    # )

    numpy.random.seed(42)
    torch.random.manual_seed(42)

    device = torch.device("cuda:0")
    model = torch.nn.Sequential(torch.nn.Linear(1, 64), torch.nn.ReLU(), torch.nn.Linear(64, 1)).to(device)

    n_samples = 100
    x_train = numpy.random.uniform(-3, 3, size=(n_samples, 1)).astype('float32')
    y_train = x_train ** 2
    x_train = torch.tensor(x_train, device=device)
    y_train = torch.tensor(y_train, device=device)

    loss_fn = torch.nn.MSELoss()
    optimizer = torch.optim.Adam(model.parameters())

    for i in range(100):
        outputs = model(x_train)
        loss = loss_fn(outputs, y_train)
        print(f"Iteration {i} loss = {loss}", flush=True)
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()


if __name__ == "__main__":
    main()
```

This bug occurs because the autograd code was changed to use `at::getAccelerator()` and `at::isAccelerator()` in order to obtain the parent stream instead of deriving the parent stream from the inputs. `at::getAccelerator()` and `at::isAccelerator()` make the assumption that only a single accelerator exists and if the PrivateUse1 backend is renamed, it returns the PrivateUse1 backend in all cases even if all tensors and models are on the built-in CUDA device.

### Versions

PyTorch 2.8.0 and later. The same code works in PyTorch 2.7.1.

### soulitzer · 2025-08-29

Discussed with @albanD offline:
-  There are APIs like pin_memory, e.g., torch.rand(1., pin_memory=True) where you don't actually have access to the device and must rely on a global one. It would not be realistic to change all factories to be able to work in this new way.
- Not being able to assume a single global accelerator would mean a clunkier API, and harder to convince people to write device-agnostic code, e.g. you don't always have device tensor around, so you may need to thread around a device instead.

If changing the basic assumption isn't really realistic, I don't think its really meaningful to make fixes to any local parts of the code.

### ymcrcat · 2026-09-27

A second use case for this, still reproducing on 2.14.0, and on MPS as well as CUDA.

[rgpu](https://github.com/ymcrcat/rgpu) is a PrivateUse1 backend that forwards tensor operations to a GPU on another machine. The ordinary client has no local GPU, but two real cases put both devices in one process:

- a benchmark on the GPU host that trains natively on `cuda` and through the remote device, to measure the overhead of remoting on the same hardware;
- a script on a Mac that compares local `mps` training against the remote GPU.

Neither mixes devices within one graph. Each backward pass is entirely on one device, as in the original report.

Minimal reproduction, with no backend code at all:

```python
import torch
torch.utils.rename_privateuse1_backend("foo")
x = torch.randn(4, 4, device="mps", requires_grad=True)   # or "cuda"
(x @ x).sum().backward()
```

```
RuntimeError: opt_ready_stream && opt_parent_stream INTERNAL ASSERT FAILED at
"torch/csrc/autograd/engine.cpp":1141
```

`torch.accelerator.current_accelerator()` is `mps` before the rename and `foo` after it. Registering the backend through `_setup_privateuseone_for_python_backend` without a name does not trigger the assertion, so it is the rename alone.

As far as I can tell from 2.14.0, the mismatch is between two questions asked of different sources. `Engine::evaluate_function` decides whether a gradient needs stream handling with `isAccelerator(device.type())`, which is true for every accelerator type, while `Node::stream()` finds the stream by comparing input devices against `getAccelerator()`, which returns PrivateUse1 whenever it has been named. For a CUDA or MPS node the first says yes and the second yields no stream.

Agreed with the point above that deriving the stream from the node's inputs would be the more robust approach. Short of that, a clear error naming the single-accelerator policy would already help: the current message reads as internal corruption, and it took a bisection down to the rename to find the cause.

We work around it by running native and remote training in separate processes.
