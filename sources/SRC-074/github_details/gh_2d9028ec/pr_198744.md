# [PR #198744] [aarch64] Narrow float/half/bfloat16 -> uint8 via int32 in at::vec::convert

source: https://github.com/pytorch/pytorch/pull/198744
state: open | updated: 2026-09-27T05:24:04Z
labels: module: cpu, open source, ciflow/trunk

## 正文

On aarch64, contiguous `x.byte()` for float16/bfloat16 still does a direct `static_cast<uint8_t>`, which clang lowers to a saturating `fcvtzu` (-1 -> 0), while strided copies go through `c10::convert`, which narrows via int64 (-1 -> 255). This breaks `test_non_contig_byte_cpu_{float16,bfloat16}`, `test_contig_vs_every_other_byte_cpu_{float16,bfloat16}` and their `_refs` variants on Apple Silicon (e.g. https://github.com/pytorch/pytorch/actions/runs/36282025606/job/108516516926). #196646 fixed the same mismatch for float32, but by widening to int64, which on NEON means going through float64 and halves the lane count.

This adds float16/bfloat16 specializations and switches float32 to narrow via int32 instead, using the fact that a type with p significant bits has only multiples of 256 above 2^(p+7): every finite fp16 fits in int32; bf16 is clamped to +-2^16; float32 maps |x| >= 2^31 to 0. All three match `c10::convert` bit for bit wherever it is defined (|x| < 2^63), verified exhaustively for every float16, bfloat16 and float32 bit pattern.

Performance of `x.byte()`, 4M elements, single thread, M5 Pro (us):

 | dtype    | main | this PR |
 |----------|------|---------|
 | float32  | 353  | 294     |
 | float16  | 101  | 172     |
 | bfloat16 | 170  | 281     |

 For reference, a direct (UB) float32 -> uint8 cast takes ~180us, so the defined float32 path is now ~1.6x the plain cast instead of ~2x.

The register-level `VecConvert<uint8_t, 1, float, N>` from #196646 (used by inductor) is left unchanged; it still narrows via int64 and gives identical results.
