Any process that ran torch.compile spawns the SubprocPool sidecar through
the async-compile warm pool. At exit, the atexit handler (and the
multiprocessing Finalize backup) called `SubprocPool.shutdown()`. That sends
SHUTDOWN and then blocks in `process.wait(300)` until the sidecar exits. For
short runs the sidecar is often still importing torch and booting its worker
pool when the parent finishes, so the parent sat idle for seconds. In the
torchtitan PR53 regional-compile repro, this was about 3s of the ~8s wall
time on a warm cache.

`shutdown` now takes `wait` (default True, so explicit callers are
unchanged). The exit handlers pass `wait=False`: they still send SHUTDOWN and
close the pipe, which the sidecar handles on its own (it also exits on EOF),
but they don't block on it. Pending futures still fail in the `finally`.
Another option was to kill the sidecar outright. That would skip its orderly
teardown of the worker pool and could leak its children, so I didn't do it.

Test Plan:
```
python test/inductor/test_compile_worker.py -k shutdown
python test/inductor/test_async_compile.py
```
The new test_shutdown_no_wait passes. In test_async_compile,
test_pool_method_fork and test_forked_daemon_process_clears_inherited_ready_future
also fail at HEAD on this machine (OMP kmp_affinity abort in forked children).
