Each Triton kernel submitted to the compile pool usually lands on a worker
that has never compiled anything, so it pays per-process one-time costs:
importing triton.compiler.code_generator and
torch._inductor.runtime.triton_heuristics (~40ms), and the CUDA backend's
hash(), part of every Triton cache key, shelling out to `ptxas --version`
twice (NvidiaTool.from_path and get_ptxas_version, both lru_cached, ~30ms).

The workers are forked from the sidecar after pre_fork_setup(), which
already warms triton_key() and initializes CUDA for the same reason. It now
also imports those two modules and computes the backend hash for the current
device, so every forked worker inherits them.

Routing kernels to already-warm workers would need changes to the pool's
scheduling, and warming each worker with a dummy compile costs more than it
saves for short compiles.

Test Plan:

torchtitan PR53 regional compiles on H100: cold first-call total
7.07s -> 6.71s median of 3 (warm unchanged); per-kernel worker compile time
225-252ms -> 210ms.


test_async_compile has two failures (test_pool_method_fork,
test_forked_daemon_process_clears_inherited_ready_future) that also fail
without this change on this machine (libomp kmp_affinity abort in forked
children).
