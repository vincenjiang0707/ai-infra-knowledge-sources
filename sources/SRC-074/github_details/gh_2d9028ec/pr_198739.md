## 正文

* #198738

Same MPSGraph abort as the previous commit, opposite resolution, so the two are best read together.

`addbmm` and `huber_loss_backward` are the ops from the same sweep whose reference *rejects* a mixed pair rather than promoting it, so promoting them would make MPS compute something no other backend will.

The constraint is not CPU-specific. `huber_loss_backward_out` builds a bare `TensorIteratorConfig` -- unlike its own forward and unlike `smooth_l1_loss_backward_out` -- so it inherits the default `check_all_same_dtype`, and that check at TensorIterator.cpp:423 throws without consulting the device. CUDA rejects the same combinations, and for addbmm demands matching dtypes explicitly at Blas.cpp:1131.

Test Plan:

```
python -m pytest test/test_mps.py -q -k "mixed_dtype"
```

Both new tests abort the interpreter without this change and pass with it.

Checked that the checks reject exactly what CPU rejects and no more, over all 27 dtype combinations of (input, batch1, batch2) in {float32, float16, bfloat16}:

```
python -c "
import torch, itertools
FD = [torch.float32, torch.float16, torch.bfloat16]
for a, b, c in itertools.product(FD, FD, FD):
    res = {}
    for d in ('cpu', 'mps'):
        try:
            r = torch.addbmm(torch.ones(2, 2, dtype=a, device=d),
                             torch.ones(1, 2, 2, dtype=b, device=d),
                             torch.ones(1, 2, 2, dtype=c, device=d))
            res[d] = ('ok', r.dtype)
        except Exception:
            res[d] = ('raise',)
    assert res['cpu'] == res['mps'], (a, b, c, res)
print('all 27 combinations agree with CPU')
"
```
