## Issue

Fixes #196212

## Summary

Fixes `torch.compile` failing to trace `iter()` on `list_reverseiterator` (objects returned by `reversed([list])`).

Previously, `list_reverseiterator` lacked a dedicated `VariableTracker` model and fell back to `UserDefinedObjectVariable`. When tracing `iter(it)`, Dynamo attempted to trace the C-level `__iter__` slot without an internal model, raising:
`torch._dynamo.exc.Unsupported: C-implemented special method without VariableTracker model ('list_reverseiterator' implements '__iter__' in C and Dynamo has no model for it)`.

This PR:
1. Implements `ListReverseIteratorVariable(BaseListIteratorVariable)` to model CPython's `list_reverseiterator`.
2. Registers `(list_reverseiterator, wrap_list_reverseiterator)` in `VariableBuilder`.
3. Adds `ListReverseIteratorGetItemSource` and `GuardBuilder.LIST_REVERSEITERATOR_LEN` guard manager support.
4. Adds regression and unit tests to `test/dynamo/test_iterators.py`.

## PR Review: #197454

### Summary
Adds `ListReverseIteratorVariable` so Dynamo models CPython's `list_reverseiterator` instead of falling back to `UserDefinedObjectVariable`, fixing #196212. The shape of the change is right and mirrors the existing sibling VTs, but there are correctness/placement issues in `lists.py`, a hot-path guard cost, and the new offset arithmetic is not covered by any test.

### Code Quality

- **`torch/_dynamo/variables/lists.py:748-765` — `__reversed__` is registered on the wrong class.** The PR narrows the comment from `# list/tuple/namedtuple __reversed__` to `# list __reversed__`, correctly acknowledging that only `list` has a `__reversed__` slot, but leaves `Method(list_reversed)` in `BaseListVariable.tp_methods`. `_lookup_tp_table` walks the full MRO (`base.py:1782-1788`), so `TupleVariable` (`lists.py:1940`) and `SizeVariable` (`lists.py:2026`) still resolve `__reversed__` to this handler and now get a `list_reverseiterator` back. In CPython `tuple` has no `__reversed__` at all — `reversed(some_tuple)` goes through `PySequence_Check` and returns a `reversed` object (`PyReversed_Type`), a different type. Note the two sibling classes that genuinely own the slot each declare it locally: `DequeVariable.tp_methods` at `lists.py:1936` and `RangeVariable.tp_methods` at `lists.py:1138`. Move the `"__reversed__": Method(list_reversed)` entry into `ListVariable.tp_methods` (`lists.py:1379-1389`) to match. This was already inaccurate pre-PR (it returned `ListIteratorVariable`), but the PR now attaches a concrete `_cpython_type` claim to the result, so the divergence becomes load-bearing. [Fix this →](https://claude.ai/code?q=In%20the%20pytorch%20repo%20on%20branch%20fix-dynamo-list-reverseiterator%2C%20move%20the%20%22__reversed__%22%3A%20Method(list_reversed)%20entry%20out%20of%20BaseListVariable.tp_methods%20(torch%2F_dynamo%2Fvariables%2Flists.py%20around%20line%20761-765)%20and%20into%20ListVariable.tp_methods%20(around%20line%201379-1389)%2C%20since%20only%20list%20has%20a%20__reversed__%20slot%20in%20CPython%20and%20TupleVariable%20%2F%20SizeVariable%20currently%20inherit%20it%20through%20the%20MRO%20via%20_lookup_tp_table.%20Keep%20list_reversed%20itself%20defined%20on%20BaseListVariable%20if%20other%20call%20sites%20need%20it.&repo=pytorch/pytorch)

- **`torch/_dynamo/utils.py:3311-3316` — the exhausted-iterator guard is unreachable defensive code.**
  ```python
  def list_reverseiterator_getitem(it, index):
      res = it.__reduce__()

- **`torch/_dynamo/variables/lists.py:2594-2597` — the double-reverse in `as_python_constant` is unreadable.** `reversed(list(reversed([...])))` round-trips the list twice to get back to iteration order. Since `self.items` is already stored in iteration order, this is `reversed(original_list)`. Either construct the backing list directly and add a one-line comment stating that `items` is stored in iteration order (the invariant is not local — `list_reversed` at `lists.py:755` is what reverses on the way in), or drop the redundant pair. ### Testing

- **The `start - index` arithmetic is never exercised.** Every new test passes a *freshly created* iterator, so `start` is always `len(list) - 1` and the offset math degenerates to a plain reverse walk. Add a case that consumes the iterator before handing it to the compiled function:
  ```python
  it = reversed([10, 20, 30, 40])
  next(it)                       # start is now 2, not 3
  self.assertEqual(opt_fn(it, torch.tensor(0)), torch.tensor(60))
  ```
  This is the only new non-trivial computation in the PR and it is the piece most likely to be off by one.

- **Caller-side iterator advancement (side-effect replay) is unverified.** The PR wires `ListReverseIteratorVariable` into `_codegen_list_iterator_mutation` (`side_effects.py:2103-2126`), whose whole job is replaying `iter_next(source)` `var.index` times so the *caller's* iterator object ends up where tracing left it. No test checks that. The precedent for the tuple path is `test/dynamo/test_subgraphs.py:566-579`:
  ```python

Note that `test_list_reverseiterator_arg_guards` uses `sum(it)`, which goes through `unpack_var_sequence` (and `ListReverseIteratorVariable` was added to `_unpack_fast_types`, `utils.py:1391`) — that path sets `is_exhausted` without bumping `index`, so it is worth confirming explicitly that the caller's iterator is left in the right state after `sum(it)`.

- **No coverage for an empty or exhausted input iterator.** `reversed([])` (where `it_index == -1` and `__length_hint__` is `0`) and a fully-consumed iterator both reach `wrap_list_reverseiterator` with length `0`. Given the `len(res) < 3` branch above, these boundaries deserve an explicit test.

### Performance

- **`torch/_dynamo/guards.py:2150-2159` uses a Python `lambda_manager` where the tuple path uses a C++ accessor.** `TupleIteratorGetItemSource` dispatches to `base_guard_manager.tuple_iterator_getitem_manager(index=...)` (`guards.py:2141-2149`), which resolves the item entirely in C++. The new `ListReverseIteratorGetItemSource` branch instead installs a Python lambda that calls `list_reverseiterator_getitem` → `it.__reduce__()`. Because `wrap_list_reverseiterator` installs one such accessor *per item*, guarding an N-element reversed iterator costs N Python calls and N `__reduce__()` tuple allocations on every cache-lookup, versus N C++ accessor hits for the equivalent tuple iterator. `COUNT_ITERATOR_MATCH` (`guards.py:3276-3292`) is not a counter-example — it's a single leaf guard, not a fan-out of accessors. `reversed(large_list)` as a compiled-function argument isn't exotic, so either add the C++ accessor mirroring `tuple_iterator_getitem_manager`, or add a comment at the `lambda_manager` call recording that this is a known O(N)-Python-calls-per-guard-check deviation and why the C++ accessor was not added.

  For completeness on the guard itself: I checked whether `@register_guard_check_spec` + `add_lambda_guard` in `LIST_REVERSEITERATOR_LEN` (`guards.py:3294-3317`) creates a serialization problem, since `TUPLE_ITERATOR_LEN` uses the C++ `add_tuple_iterator_length_guard`. It does not — `guard_check_spec` feeds the in-memory `invoke_subgraph` fast path, and `UNSUPPORTED_SERIALIZATION_GUARD_TYPES` doesn't cover lambda-backed guards. And the existing C++ guard genuinely can't be reused: it casts to `_PyTupleIterObject` and calls `PyTuple_GET_SIZE`. So the leaf guard's use of a lambda is fine; it's the per-item accessors that are the cost.

### Recommendation
**Request Changes**

The missing test for the `start - index` offset arithmetic and for caller-side side-effect replay is the blocker — those are the two pieces of new machinery the PR adds, and nothing currently exercises either. The `__reversed__` placement on `BaseListVariable` is a one-line move that should go in the same change, since the PR's own comment edit already establishes that the handler is list-only.

## PR Review: #197454

### Summary
Adds `ListReverseIteratorVariable` so Dynamo models CPython's `list_reverseiterator` instead of falling back to `UserDefinedObjectVariable`, fixing #196212. Follow-ups from the previous round landed correctly. Remaining problems: the `reconstruct` / `as_python_constant` codegen path is untested, and the per-item guard accessors are O(N) Python calls where the tuple-iterator equivalent is C++.

### Answering @guilhermeleobas on `torch/_dynamo/guards.py:3307` ("Do we really need this extra guard?")

Yes — dropping it produces silent wrong results, not just a missed recompile.

`wrap_list_reverseiterator` (`builder.py:2596-2605`) unrolls the iterator into N `VariableTracker`s at trace time and installs one `ListReverseIteratorGetItemSource` accessor per index. Each accessor computes `obj[start - index]` (`utils.py:3310-3312`). Nothing else in the guard tree pins N, and **negative indices silently wrap** instead of erroring:

```
guarded on reversed([t1, t2, t3, t4])  ->  start=3, accessors read obj[3], obj[2], obj[1], obj[0]
later called with reversed([t1, t2])   ->  start=1, same accessors read obj[1], obj[0], obj[-1], obj[-2]
```

All four reads succeed. For tensor items the leaf guard is `TENSOR_MATCH` (dtype/shape/device only), so a 2-element reversed iterator of same-shaped tensors **passes the guard check and reuses code compiled for a 4-element one**. With `reversed([t1])` you instead get `obj[-2]` → `IndexError` → `PythonLambdaGuardAccessor::check_nopybind` swallows it and returns false (`torch/csrc/dynamo/guards.cpp:7284-7289`), so the failure mode is inconsistent but the wrong-result case is real.

The existing generic guards can't substitute: `SEQUENCE_LENGTH` calls `len(value)` (`guards.py:245`) and `list_reverseiterator` has no `__len__`, only `__length_hint__`; `TUPLE_ITERATOR_LEN` bottoms out in a C++ guard that casts to `_PyTupleIterObject` and calls `PyTuple_GET_SIZE`, so it can't be reused either.

What *could* legitimately remove this guard is a different decomposition — see the Performance finding below. `__reduce__()` already hands you `(iter, (backing_list,), start)`, so the iterator's entire state is "a list plus an int". Sourcing the backing list directly would let the existing `SEQUENCE_LENGTH` + `ListGetItemSource` C++ machinery cover length *and* items, leaving only a small guard on `start`. That deletes `LIST_REVERSEITERATOR_LEN`, `ListReverseIteratorGetItemSource`, `list_reverseiterator_getitem`, and the `lambda_manager` all at once. That's a design question worth settling before this lands, since it's the difference between ~60 new lines of guard plumbing and ~10.

### Performance

- **`torch/_dynamo/guards.py:2150-2162` — per-item `lambda_manager` costs N Python calls and N tuple allocations on every cache lookup.** The tuple-iterator equivalent at `:2141-2149` resolves items entirely in C++ via `tuple_iterator_getitem_manager`. Here each of the N accessors invokes `list_reverseiterator_getitem` → `it.__reduce__()`, which allocates a fresh tuple per call. `reversed(large_list)` as a compiled-function argument isn't exotic. The added NOTE is accurate — CPython's `listreviterobject` isn't exported in any internal header the way `_PyTupleIterObject` is in `pycore_tuple.h` — but note `guards.cpp:108-112` already hand-copies the `_PyTupleIterObject` struct for pre-3.12, so the precedent for doing the same here exists. The cleanest resolution is the backing-list decomposition described in the answer to @guilhermeleobas above, which removes the fan-out entirely rather than making it faster.

### Code Quality

- **`torch/_dynamo/variables/lists.py:2600-2606` — the suppression forces a three-line split of a one-line call.** The base-class equivalent is a single line with a single suppression:
  ```python
  # lists.py:2486-2488
  codegen.add_push_null(
      lambda: codegen.append_output(codegen.create_load_python_module(iter))  # type: ignore[arg-type]

  The new code needs both `# pyrefly: ignore [bad-argument-type]` *and* `# type: ignore[arg-type]` for the structurally identical call with `reversed`. Per CLAUDE.md, splitting across lines to fit a linter is less readable than keeping it on one. Worth checking whether the pyrefly suppression is actually needed, or whether the real fix is the `mod: types.ModuleType` annotation on `create_load_python_module` (`codegen.py:697`), which is already wrong for the pre-existing `iter` and `range` callers.

- **`torch/_dynamo/variables/lists.py:2597` — the comment explains the wrong half of the double-reverse.** `# self.items is in iteration order; reversed() expects the backing sequence` is true but doesn't say why the outer `reversed()` is there. The non-obvious part is that `iter(items)` would be simpler and yield identical *values* but the wrong *type* (`list_iterator` instead of `list_reverseiterator`), which is the entire point of this VT. Two reviewers have now misread this line as a redundant round-trip — one of them proposed "simplifying" it to `reversed([... for x in self.items])`, which would have inverted the iteration order. State the type-fidelity reason and the trap closes. Same comment at `:2608`.

### Verified as non-issues

Recording these so the next reviewer doesn't relitigate them:

- **Moving `__reversed__` from `BaseListVariable.tp_methods` to `ListVariable.tp_methods` does not regress tuples.** CPython's `tuple` has no `__reversed__` slot at all, so `call_reversed` (`builtin.py:2877-2890`) finds nothing via `inspect.getattr_static`, falls through to `pysequence_check`, and uses the `reversed_sequence_iterator` polyfill — which is exactly CPython's own behavior (`reversed(some_tuple)` is a `PyReversed_Type`, not a `tuple_reverseiterator`). `torch.Size` and namedtuples inherit that. `RangeVariable` (`:1137`) and `DequeVariable` (`:1936`) already declare their own. `test_tuple_does_not_have_reversed_slot` (`test_iterators.py:677-686`) pins this.
- The prior round's `len(res) < 3` dead branch in `list_reverseiterator_getitem` is gone.
- Leaf guards run before child accessors (`guards.cpp:3660-3667`), so `LIST_REVERSEITERATOR_LEN` is evaluated before any `start - index` accessor, meaning the in-bounds invariant the accessors rely on holds by construction.
- Empty (`reversed([])`, `start == -1`, length hint `0`) and fully-exhausted iterators both build zero items and install zero accessors, so `start == -1` is never used as an index.
- The `LIST_REVERSEITERATOR_LEN` lambda-backed guard creates no `aot_compile` serialization problem — `UNSUPPORTED_SERIALIZATION_GUARD_TYPES` (`guards.py:5164`) doesn't cover it, and `COUNT_ITERATOR_MATCH` (`:3279-3295`) is the existing precedent for a lambda guard plus `register_guard_check_spec`.
- No missing registry entries: `_cpython_type` is auto-collected by `VariableTrackerMeta`, and `_unpack_fast_types` (`utils.py:1392`), `side_effects.py:2110/2123`, and the `iter_vts` tuple in `symbolic_convert.py:6592` are all updated.

New functionality without tests: `reconstruct` and `as_python_constant` are untested, and `reconstruct` contains the PR's most error-prone logic. Beyond that, the guard-plumbing design question in the answer to @guilhermeleobas is worth resolving before this lands, since the simpler decomposition would delete most of the new code in `guards.py`, `source.py`, and `utils.py`.

> **1. Crash on `reversed()` of a list subclass (regression, works on main)**
>
> `wrap_list_reverseiterator` reads `backing_vt.list_vt`, but `UserDefinedListVariable` stores the list as `_base_vt`:
>
> ```python
> import torch
>
> class MyList(list):
>     pass
>
> def fn(it):
>     return list(it)
>
> torch.compile(fn, backend="eager")(reversed(MyList([1, 2, 3])))
> # InternalTorchDynamoError: AttributeError: 'UserDefinedListVariable' object has no attribute 'list_vt'
> ```
>
> **2. `reconstruct` drops the aliasing with the backing list**
>
> `reconstruct` emits `reversed([...])` over a fresh list, so the reconstructed iterator no longer sees the original list:
>
> ```python
> import torch
>
> def fn(x):
>     lst = [1, 2, 3]
>     it = reversed(lst)
>     next(it)
>     torch._dynamo.graph_break()
>     lst[0] = 99
>     return list(it)
>
> x = torch.tensor(0)
> fn(x)                                    # [2, 99]
> torch.compile(fn, backend="eager")(x)    # [2, 1]
> ```
>
> The same happens when a fullgraph region returns both `lst` and `it`. Since `source_seq` already models the aliasing, `reconstruct` could codegen `source_seq`, call `reversed` on it, then `__setstate__(it_index)` if needed. Please add tests for both cases.
>
> **Smaller items**
> - The `items=` branch in `ListReverseIteratorVariable.__init__` is dead code: both callers pass `source_seq`. Removing it also removes the `assert` that fails S101.
> - The no-op `items` setter throws away the `items=[]` passed to `super().__init__`. The class overrides nearly everything in `BaseListIteratorVariable`, so consider subclassing `IteratorVariable` directly. That would also fix the pyrefly error.
