# [Issue #198563] `TORCHINDUCTOR_DETERMINISTIC=1` is turned off by the first compiled frame: Dynamo's global-state restore calls `use_deterministic_algorithms(False)`, which also assigns `torch._inductor.config.deterministic`

source: https://github.com/pytorch/pytorch/issues/198563
state: open | updated: 2026-09-25T01:53:53Z
labels: triage review, module: determinism, oncall: pt2, module: dynamo, bot-triaged

## 正文

### 🐛 Describe the bug

`TORCHINDUCTOR_DETERMINISTIC=1` sets `torch._inductor.config.deterministic` when the config module is imported. The setting does not survive the first `torch.compile` frame.

After every frame it compiles, Dynamo restores global state and calls `torch.use_deterministic_algorithms(prior_deterministic, warn_only=prior_warn_only)`, where `prior_deterministic = torch.are_deterministic_algorithms_enabled()` (`torch/_dynamo/convert_frame.py`, lines 350 and 380 on main at `2e07892c26b3`). `use_deterministic_algorithms` also assigns `inductor_config.deterministic = mode` (`torch/__init__.py`, line 1910 on the same commit). The global flag is `False` unless the user enabled it, so the first compiled frame sets Inductor's `deterministic` to `False`. Every kernel generated after that carries `'deterministic': False` in its `inductor_meta`, and reductions go back to benchmarking their candidate configs.

Minimal reproduction (CPU is enough):

```python
# TORCHINDUCTOR_DETERMINISTIC=1 python repro.py
import torch
import torch._inductor.config as c

print("before compile:", c.deterministic, "| global flag:", torch.are_deterministic_algorithms_enabled())
f = torch.compile(lambda x: (x * 2).sum(), backend="eager")
f(torch.randn(8))
print("after one compiled frame:", c.deterministic)
```

Output with torch 2.13.0+cu130:

```
before compile: True | global flag: False
after one compiled frame: False
```

**Expected:** `torch._inductor.config.deterministic` stays `True` unless the user changes it. The environment variable asks for Inductor's deterministic mode without asking for `torch.use_deterministic_algorithms(True)` on every op.

**Actual:** it becomes `False` after the first compiled frame.

How we found it: we serve a model on two GPUs with tensor parallelism. One module that both ranks compute identically (not sharded) runs a `torch.compile`d layer norm, which Inductor turns into a persistent reduction with three candidate configs (`XBLOCK` 1, 8 and 32). Each rank picked its config by benchmarking at startup, and `XBLOCK=1` gives different bits from the other two (2 of 2,048 rows on a fixed input). When the ranks picked configs from different classes, their outputs differed and the model's greedy completions changed from launch to launch. `TORCHINDUCTOR_DETERMINISTIC=1` should have fixed this, because `filter_reduction_configs_for_determinism` narrows the candidates to one (8 here), but the generated kernels still carried `'deterministic': False`. Wrapping the `ContextVar` behind the config entry in the serving process recorded fifteen writes of `False`. Every one came from the `use_deterministic_algorithms` call in `convert_frame.py`, on the main thread, during model load.

Workaround: set `torch._inductor.config._config["deterministic"].env_value_force = True` after the config module is imported. `__getattr__` returns `env_value_force` before `user_override`, so the setting then survives the restore. With that in place, the same frame leaves `deterministic` at `True`.

Possible fixes (for the maintainers to judge):
- save and restore `torch._inductor.config.deterministic` separately in Dynamo's global-state wrapper, instead of routing it through `use_deterministic_algorithms`;
- or have `use_deterministic_algorithms(False)` leave Inductor's setting alone when the environment variable or the user set it independently;
- or define the entry with `env_name_force="TORCHINDUCTOR_DETERMINISTIC"`, so the variable takes precedence over the assignment.

Related, but not the same: #174386 (`torch.compile` ignores `torch.use_deterministic_algorithms(True)` on `empty_like`).

### Bizuayeu · 2026-09-25

Also reproduces on torch 2.12.1 (CPU wheel, `2.12.1+cpu`, same script): `before compile: True`, `after one compiled frame: False`, and forcing the entry keeps it `True`. So this is not a 2.13 regression. First reported on `2.12.1+cu130` by hclsys in vllm-project/vllm#58636.
