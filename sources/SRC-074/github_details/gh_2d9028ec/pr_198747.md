`torch_key`/`triton_key` hash the torch and triton sources the first time an
FX graph cache key is computed, which blocks the first compile for ~140ms
even on a warm cache. They already support `prefetch()` via
`prefetchable_cache`, but nothing called it.

`codecache.prefetch_cache_keys()` starts both in a background thread (once).
torch.compile(backend="inductor") calls it as soon as the wrapper is created,
so the hashing overlaps with everything before the first call (model init,
data loading) as well as Dynamo and AOTAutograd tracing. Dynamo's `_compile`
also calls it for Inductor backends reached without torch.compile (e.g.
torch._dynamo.optimize). The prefetchers are bound at codecache import so
tests that `mock.patch` `torch_key` keep working; `TestCacheKeyStrategy`
now clears `triton_key` in setUp because it assumed nothing earlier in the
process had computed the real value.

The cost is importing torch._inductor.codecache inside torch.compile()
instead of inside the first compile, which would have imported it anyway.
Starting only from `_compile` was the first version, but with small
compiled regions Dynamo tracing is too short to hide the hash. Making
torch_key itself faster is complementary and wouldn't remove the wait.
