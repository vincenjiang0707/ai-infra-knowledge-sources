> ## Summary
>
> Re-enable `batch_linear_lhs` by default on XPU with per-linear layout and
> alias-safety checks.
>
> The feature was temporarily disabled in #194225, with the release backport
> in #194312, after a Qwen/vLLM regression. Combining parallel linears into a
> wide GEMM produces split views whose strides and alias behavior differ from
> the original contiguous outputs.
>
> This PR excludes unsafe linears while retaining fusion for supported safe
> consumers.
>
> Fixes #193490.
> Alternative to #193264.
>
> ## Changes
>
> - Recognize torch functions by identity and inspect applicable operator
>   schemas. Functional packet calls remain eligible; actual mutable and
>   `out=` calls are rejected.
> - Follow views, conditional aliases, conversions, and clone operations.
>   Reject layout-sensitive consumers and uncertain layout-changing paths.
> - Continue checking alias safety after `contiguous()`. Permit supported
>   direct multirow materialization paths without overlooking downstream
>   mutations or opaque alias comparisons.
> - Protect storage-sensitive operations such as `as_strided_copy` and
>   singleton/empty-tensor stride observations.
> - Reject unsupported broadcast biases and zero-width projections.
> - Keep the stronger checks local to `batch_linear_lhs`, preserving the
>   shared `batch_linear` mutation helper's previous behavior.
> - Add discriminating correctness and fusion-preservation regressions.
>

### Summary
Skips `batch_linear_lhs` fusion for individual linear nodes whose FX users can observe layout (graph output, stride/contiguity methods, non-aten ops). The approach is sound and better than blanket `contiguous()` copies, but the custom-op detection misses the `OpOverloadPacket` call form, the layout-sensitivity analysis is only one hop deep, and the negative test passes for the wrong reason.

### Code Quality

**`_has_layout_sensitive_user` misses `OpOverloadPacket` targets** — `torch/_inductor/fx_passes/group_batch_fusion.py:511-515`

```python
if (
    isinstance(user.target, torch._ops.OpOverload)
    and user.target.namespace != "aten"
):
```

`OpOverload` and `OpOverloadPacket` are unrelated classes (`torch/_ops.py:1237` vs the `OpOverload` definition), and both can appear as `call_function` targets. The PR's test calls the op through the `CustomOpDef` object, which resolves to `self._opoverload` (`torch/_library/custom_ops.py:866`) and therefore *is* an `OpOverload` — so the test passes. But a user writing the packet form `torch.ops.mylib.myop(x)` (no `.default`) gets an `OpOverloadPacket` target and slips straight through the guard, silently reintroducing exactly the bug this PR fixes.

Both classes expose `.namespace`, so the fix is a one-liner:

```python
if isinstance(
    user.target, (torch._ops.OpOverload, torch._ops.OpOverloadPacket)
) and user.target.namespace != "aten":
```

### API Design

**The layout analysis is only one hop deep.** The guard inspects direct users of the linear node, but layout-sensitivity propagates through aten view ops, which are all in the `aten` namespace and therefore pass the guard. `linear(x, w).view(32, 6, 32)` succeeds on a contiguous `(192, 1)` tensor and fails on a `(208, 1)` slice of the fused GEMM. Note `view_to_reshape` (`torch/_inductor/compile_fx.py:1621`) only runs post-grad, well after AOTAutograd has traced the `.view()` against the already-fused fake tensor — so the failure surfaces at trace time. This is pre-existing rather than introduced here, but since the PR frames itself as fixing layout sensitivity, either extend the walk through layout-preserving aten views or state the limitation in the comment at `:522-523`.

**Consider whether the constraint belongs on the op instead.** Custom ops default to `needs_exact_strides` (`torch/_functorch/config.py:272-274`, via `get_layout_constraint_tag` at `torch/_library/utils.py:594-604`). "Exact strides" means inductor faithfully reproduces whatever the fake tensor says — which post-fusion is `(208, 1)`. So the reported XPU GDN failure is really an op that requires contiguity but never declared it. Tagging that op `needs_contiguous_strides` (dispatched at `torch/_inductor/lowering.py:206-207`) would make inductor insert the copy exactly where needed, and would fix it for *every* layout-changing pass rather than teaching one fusion pass to guess. That is a stronger fix than this heuristic and it composes; the guard here treats every non-aten op as contiguity-requiring, which is a blunt proxy for a constraint the op can state precisely. Worth confirming why the tag route was not taken — if it was because the op is third-party and untaggable, say so in the PR description.

### Performance

**The `output`-node branch will disable this fusion for a broad class of real models** — `group_batch_fusion.py:503-504`. This branch is *correct* and load-bearing, and I want to be explicit about why, since it is subtle: `keep_output_stride` (default `True`, `torch/_inductor/config.py:893`) does restore "original" output strides via `require_exact_strides` (`torch/_inductor/graph.py:2101-2146`) — but `_recursive_record_original_output_strides` runs at `compile_fx.py:2811`, on the AOTAutograd-traced graph. Pre-grad passes run earlier, at `torch/_functorch/aot_autograd.py:1181`. So the strides recorded as "original" are already the **post-fusion** `(208, 1)` strides, and inductor faithfully preserves the wrong ones. The guard is needed.

The cost is that any model returning a projection directly from `forward` now loses the fusion entirely. The existing tests happen to dodge this (`MyModule4` returns through `torch.cat`), so CI will not show it. Given the pass is default-enabled for XPU (`torch/_inductor/config.py:367-372`), please confirm the target workload still fuses after this change — a guard that silently turns the optimization off on the very models it was added for would be worse than the layout bug.

### Recommendation
**Request Changes**

The `OpOverloadPacket` gap leaves the reported class of bug reachable through a common call form, and the primary negative test does not actually verify the guard's behavior. Both are small fixes. The design question about `needs_contiguous_strides` and the fusion-coverage regression from the `output` branch are worth answering before this is cherry-picked to the release branch, since a cherry-pick makes the conservative fallback harder to walk back.

### New: `higher_order` namespace slips through the guard

`group_batch_fusion.py:610-618` handles `OpOverload` and `OpOverloadPacket` but returns `None` for `HigherOrderOperator`, which is neither (`torch/_ops.py:282` — it extends `OperatorBase` directly, alongside `OpOverload` at `:837`). `None` is in the allowlist at `:635`, so HOO users are treated as layout-insensitive.

The concrete case is user-written Triton kernels: dynamo emits `create_proxy("call_function", triton_kernel_wrapper_mutation, ...)` (`torch/_dynamo/variables/functions.py:3579-3591`), so the node target is the HOO instance.
```python
if isinstance(tgt, (torch._ops.OpOverload, torch._ops.HigherOrderOperator)):
    return tgt.namespace
```

Note the kwargs wrinkle: `triton_kernel_wrapper_mutation` passes tensors via a `kwargs` dict, so the linear node still appears in `node.users` (FX tracks users through kwargs), and the guard fires. Worth a test with a small `triton.jit` kernel consuming one of three linears.

### @guangyey's comment is correct — and the fix also bounds a worse case

`torch/_inductor/fx_passes/group_batch_fusion.py:686` recurses with no `visited` set:

```python
if kind == "propagate" and _has_layout_sensitive_user(user):

```

Two costs, and the second is the one that matters:

1. **Re-visits, as flagged.** A diamond (`t = lin(x).transpose(0,1)` consumed by two `unsqueeze`s that both feed a `permute`) visits the shared descendant once per path.
2. **Exponential in depth, not just quadratic.** Because there is no memoization *and* no early caching of negative results, a chain of `k` view nodes each having 2 view users costs O(2^k). View chains that wide are uncommon, but nothing in the guard bounds it, and `match()` runs this walk independently for *every* linear node in the graph — so the per-graph cost is `n_linears x subgraph_size` even in the well-behaved case. `SEARCH_EXCLUSIONS` (`:57`) exists in this very file because getitem traversal cost 60s of optimizer compile time, so the file already has precedent for taking this seriously.

An iterative worklist fixes both and is no longer than the recursive form:

```python
def _has_layout_sensitive_user(node: torch.fx.Node) -> bool:
    queue = [node]
    seen = OrderedSet([node])
    while queue:
        for user in queue.pop().users:
            if user.op == "output":
                return True
            if user.op == "call_method" and user.target in (
                "is_contiguous", "storage_offset", "stride",
            ):
                return True
            if _op_namespace(user.target) not in (None, "aten"):
                return True
            kind = _view_op_kind(user)
            if kind == "crash":
                return True
            if kind == "propagate" and user not in seen:
                seen.add(user)
                queue.append(user)
    return False
```

| where | form | note |

### 3. The blocker: pre-grad targets are mostly *not* `OpOverload`

| source | node | has a schema? |
|---|---|---|
| `x.view(-1)`, `x.permute(...)` | `call_method`, target is the **string** `"view"` | no |

| `x.T` | `call_function`, target `torch.ops.aten.numpy_T` (**`OpOverloadPacket`**, `_dynamo/variables/tensor.py:163`) | not via `.is_view` |
| occasional aten call | `call_function`, target `OpOverload` | yes |

### 4. Concrete shape

```python
def _is_aten_view_name(name: str) -> bool:

    # torch.split, or as torch.ops.aten.numpy_T, so match on the op name and
    # ask aten's schema whether that op aliases its input.
    packet = getattr(torch.ops.aten, name, None)
    if packet is None:
        return False
    return any(getattr(packet, o).is_view for o in packet.overloads())
```

**2. The post-`contiguous()` ancestry walk searches the whole upstream graph** (the `pending` / `visited` loop in the non-exposed branch)

For every opaque-op input other than `current`, the loop follows `all_input_nodes` all the way up to the placeholders, and it builds a new `visited` set for each input. A custom op that takes the residual stream, a KV cache or a weight therefore walks every earlier layer. That cost is paid for each candidate linear, so compile time grows as linears × graph size in a pass that is on by default. FX graphs are topologically ordered and `Node` supports `<` (`torch/csrc/fx/node.cpp:453`), so adding `if candidate < node: continue` stops the walk at `node` without changing the result.
