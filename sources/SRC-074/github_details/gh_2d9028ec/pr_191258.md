### PR Review: #191258

### Summary
Routes the reduction-output block-pointer/TMA store in `TritonKernel.store_reduction` through `codegen_block_ptr` instead of `indexing.format(var)`. I verified the fix rationale is correct: `_emitted_device_tma = True` is only set inside `codegen_block_ptr` (`torch/_inductor/codegen/triton.py:4307`), and `codegen_kernel` pops `tma_min_block_sizes` from `inductor_meta` when neither `host_tma_descriptor_args` nor `_emitted_device_tma` is set (`triton.py:7231-7237`). So before this change, a kernel whose only TMA access was the reduction store lost its min-block constraint, `_maybe_filter_configs_for_tma_restrictions` (`torch/_inductor/runtime/triton_heuristics.py:4326`) never filtered configs, XBLOCK=1 was picked, and the emitted `make_tensor_descriptor(...).store(...)` failed the 16-byte last-dim rule. One issue found: the new call also enables host-side TMA registration on a path that lacks the alignment guards the other two call sites have.

### Code Quality
`store_reduction` (`triton.py:6048-6070`) is now the third caller of `codegen_block_ptr`, but it is missing both guards the other two callers apply before descriptor construction:

- `store()` calls `_check_buffer_alignment(name, var, dtype)` at `triton.py:4973` and passes `buffer_name=name` into `tma_compatibility_checker_cls` (`triton.py:4983`).
- `load()` does the same at `triton.py:4756-4758` / `4767`, plus consults `_host_tma_non_materializable_buffers`.
- `store_reduction` constructs the checker with no `buffer_name` (`triton.py:6051-6056`) and never calls `_check_buffer_alignment`.

Without `buffer_name`, the `is_unaligned_buffer_name` rejection at `triton.py:3046` is skipped, so a reduction output on a `NonOwningLayout` that can't be guarded aligned still gets a descriptor. Without `_check_buffer_alignment`, a non-16-byte-aligned layout offset is not caught, and `codegen_block_ptr` can register the buffer in `host_tma_descriptor_args` (`triton.py:4282-4292`).

That registration is the part that worries me most. For a *store*, the launcher path at `torch/_inductor/runtime/triton_heuristics.py:2776-2786` emits `X_aligned = _host_tma_aligned(X, "X")`, and `_host_tma_aligned` (`triton_heuristics.py:225-232`) silently `clone()`s a misaligned tensor with only a `log.warning`. The kernel then writes the reduction result into the clone, and the real output buffer is never written — silent wrong results rather than a compile error. Please mirror `store()`: pass `buffer_name=name` to the checker, and gate on `_check_buffer_alignment` before building it.

Mitigating context: `triton.enable_host_side_tma` is off by default (`torch/_inductor/config.py:2204`), so this is an experimental-path hazard, not a default-config regression. The missing `buffer_name` is still worth fixing regardless of that flag since it also affects device-side TMA eligibility.

Related consistency gap (pre-existing, but now more reachable since this path participates in descriptor registration): the non-block-pointer branch of `store_reduction` (`triton.py:6096-6101`) emits a plain `tl.store(out_ptr + ...)` without the `_host_tma_non_materializable.add(var)` / `host_tma_descriptor_args.pop(var, None)` bookkeeping that `store()` performs at `triton.py:5033-5034`. If another access to the same output var registers a host descriptor, the signature becomes `tensordesc<...>` while this line still does pointer arithmetic.

### Testing
No new test. The PR relies on the existing `TritonTensorDescriptorTestCUDA.test_welford_non_block_pointer_cuda` regression, which is adequate coverage for the reported failure. But nothing pins the actual invariant being fixed — that `tma_min_block_sizes` survives into `inductor_meta` when the reduction store is the kernel's only TMA access. A one-line `self.assertIn("tma_min_block_sizes", code)` (or an assertion that the chosen XBLOCK >= 4) in that test would prevent a future refactor from silently reintroducing the drop, since the current test only fails when a config with too-small XBLOCK happens to be selected.

### Recommendation
**Needs Discussion**

The core change is right and the mechanism checks out. Before landing, please either add the two alignment guards to `store_reduction` to match `store()`, or explain why reduction outputs are guaranteed aligned here so host-side TMA registration can't hand the kernel a cloned buffer.
