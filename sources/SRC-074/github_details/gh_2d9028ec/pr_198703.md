**What this changes**

The change rewrites runner labels across 27 GitHub Actions workflow files, replacing EC2 instance names such as `linux.aws.h100` and `linux.g5.4xlarge.nvidia.gpu` with the ARC pod names they currently map to in `.github/arc.yaml` — `l-x86iamx-22-225-h100`, `l-x86aavx2-11-41-a10g`, and so on. Two forms appear. Entries that already carried `${{ needs.get-label-type.outputs.label-type }}` keep that expression and gain a bare `l-…` name; entries written raw get a literal `mt-` prefix, about 157 sites across 19 files. These matrices are not consumed literally: `_linux-build.yml:206-219` still pipes every one through `.github/scripts/map_ec2_to_arc.py`, so the labels remain inputs to that script rather than final values. That is where the change stops being a rename.

**What it gets right**

The transcription itself is accurate. Every distinct pod name written here matches the corresponding value in `arc.yaml`'s `runner_mapping`, checked entry by entry, which is the hard part of a mechanical rewrite this wide. The prefixed form is the correct translation and matches the precedent already set in `pull.yml`, keeping fleet selection expressed once. Partner hardware that `arc.yaml` passes through unchanged — B200, XPU, ROCm — is left alone, and per-entry metadata survives in place, including `owners:`, the `unstable:` keys and the staging comment above the `inductor_aoti_fallback` shards in `inductor-unittest.yml:192-198`.

**Where the risk is**

All of it concentrates in the raw `mt-` form, and four independent reviews landed on the same lines from four different angles — that convergence is the strongest signal in the run. The mechanism is one thing (`c-001`): `strip_prefix` in `map_ec2_to_arc.py:38-41` removes only the prefix it is handed, so when the determinator resolves `label-type` to `lf-`, a literal `mt-l-…` is neither a mapping key nor `l-`-prefixed and `map_ec2_to_arc.py:101-102` exits 1, failing the build job before anything compiles. One edit settles all four. Whether that path fires today depends on the lf rollout state, which lives outside this repository and could not be settled from the checkout.

A second cluster (`c-002`) reads the same lines for what they mean rather than what they crash: `arc.yaml:124-127` declares exactly three Meta-only runners, and the literal `mt-` is now written for roughly eleven runner types that are not on that list, so fleet policy is stated in two places that disagree — visibly within one job at `operator_benchmark.yml:87` versus `:92`. These two clusters compound. Fixing the crash narrowly, by teaching the mapper to accept `mt-l-…` under any prefix, converts the hard failure into the silent fleet pin, and leaves `test_non_h100_keeps_lf_prefix` guarding an invariant the workflows no longer follow. Deciding whether Meta pinning is intended therefore picks the fix for the crash; it is not a separate question.

A third cluster (`c-003`) is one consequence of the rewrite's premise: pod names take the unvalidated `l-` passthrough at `map_ec2_to_arc.py:99`, so a future typo no longer fails fast, and `arc.yaml`'s table is now duplicated into the workflows with nothing comparing them. Separately and unrelated to any of the above, two documents name labels this change renames: `benchmarks/operator_benchmark/README.md` lines 157, 158, 177 and 178, and the job-name example at `benchmarks/dynamo/perf_cli.py:88`.

**Before merge, and after**

Settle the fleet question first, then fix the mapper crash in the way that answer implies — "raw `mt-` runner labels crash the build job's map_ec2_to_arc.py step" in the raw-label workflows, and "raw labels are hardcoded with the `mt-` fleet prefix for runners that arc.yaml's `meta_only_runners` does not declare Meta-only" in `operator_benchmark.yml` and its siblings. Writing the determinator expression for non-Meta-only hardware resolves both at once and keeps the change a pure rename, as the description claims it is. The four stale labels in `benchmarks/operator_benchmark/README.md` are a four-line edit and `operator_microbenchmark.yml:2` already asks that the file be kept in sync, so they are cheap to include here.

As follow-up: where runner-label validation should live, raised by "naming ARC pods directly routes these runner labels around map_ec2_to_arc.py's validation" and "ARC pod names are copied out of arc.yaml's `runner_mapping` into 27 workflows". That needs a design decision about the end state of the migration rather than a patch to this diff, and nothing is broken by it today. The `perf_cli.py:88` example is a comment fix whenever convenient.
