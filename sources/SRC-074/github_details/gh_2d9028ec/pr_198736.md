## Issue

Fixes #198581

Supersedes #198587, which GitHub auto-closed when its head fork was deleted. Same commit, same diff.

## Summary

- `cuWelfordCombine` merged two partial means as a weighted average, `nA*dataA.mean + nB*dataB.mean`, which is exact only when `nA + nB == 1` - something no reciprocal guarantees. On constant input the saved mean came back one ulp low and `rsqrt(eps)` amplified it, so `F.layer_norm(torch.ones(4, 384), (384,), eps=1e-5)` returned `1.88e-05` on gfx950 instead of `0`.
- Replaced with Welford's increment, `dataA.mean + delta * nB`, which cannot move the mean when both partials agree, whatever the reciprocal did. This matches `WelfordOps::combine` in `SharedReduceOps.h`, already used by `torch.mean` and by LayerNorm's own `N % 4 != 0` fallback.
- Making the reciprocal exact instead is measurably not a fix: with correctly-rounded `1.0f/count` the old formula still fails 131 of 1024 widths on hardware. Only the formula change gives 0.
- Measured on MI355X (gfx950) and MI300X (gfx942); the failure and the saved-mean bit patterns are identical on both, and reproduce as far back as torch 2.7.1+rocm6.4.1. The CUDA block shape is covered by arithmetic reasoning, not by execution.

## BC-breaking?

No API change. It does change bitwise forward output for non-constant input on every GPU backend, since `mA + delta*nB` and `nA*mA + nB*mB` round differently - the new form is the better-conditioned one and is what the rest of ATen already uses. Tolerance-based suites pass on gfx950 (`test_nn.py -k LayerNorm` 50, `-k rmsnorm` 12, `test_ops.py -k layer_norm` 164).

> ## Summary
>
> `cuWelfordCombine` in the vectorized LayerNorm kernel merges two partial means as a weighted average, `nA*dataA.mean + nB*dataB.mean`, which is exact only when `nA + nB == 1` — something no reciprocal guarantees. On a constant input, where the mean must be exact for the output to be zero, this makes `F.layer_norm` return non-zero. This replaces it with Welford's increment, `dataA.mean + delta * nB`, which is exactly mean-preserving when both partials agree. Fixes #198581.
>
> ## What changed
>
> - **`aten/src/ATen/native/cuda/layer_norm_kernel.cu`** — `cuWelfordCombine` now uses Welford's increment for the mean instead of a weighted average of the two partial means; `nA` is no longer needed. `sigma2` is untouched, since it already uses `nB` and is Chan's `M2` term, independent of how `mean` is formed.
> - **`test/test_nn.py`** — device-generic regression test asserting that a constant input gives a bit-exact mean and an exactly-zero output, over widths covering the vectorized kernel, the `N % 4 != 0` fallback, and a power-of-two control.
>
> ## Architecture / design notes
>
> The weighted-average form is not the Welford combine. The canonical in-tree one, `WelfordOps::combine` in `aten/src/ATen/native/SharedReduceOps.h`, already uses `a.mean + delta * nb_over_n`; this change brings `cuWelfordCombine` into agreement with it. That divergence is also why `torch.mean` and `torch.var` are exact on the same tensors that `layer_norm` gets wrong, and why widths with `N % 4 != 0` are clean — they miss the vectorized dispatch and fall back to `RowwiseMomentsCUDAKernel`, which uses `WelfordOps`.
>
> Sweeping all 1024 widths from 4 to 4096 on an MI355X, with the reciprocal and the formula independently switchable in one binary:
>
> | reciprocal | mean formula | failing widths |
> |---|---|---|
> | `__builtin_amdgcn_rcpf` | weighted average (current) | 691 / 1024 |
> | `1.0f / count` (IEEE) | weighted average (current) | 131 / 1024 |
> | either | Welford increment (this PR) | 0 / 1024 |
>
> The second row is why the fix is the formula and not the reciprocal: **with a correctly-rounded reciprocal the current code still fails at 131 widths**, smallest 164, 188, 220, 244. So switching the combine to the true-divide `fn_rcp(count)`, or flipping ROCm's `USE_LAYERNORM_FAST_RECIPROCAL` default off, is measurably not a fix. Carrying the same arithmetic through the CUDA block shape (warp 32, 128 threads) in correctly-rounded fp32 predicts 6 failing widths there — 244, 328, 332, 372, 460, 488 — and the same computation reproduces the measured wave64 list exactly, which is the basis for quoting it. **But I had no NVIDIA device: nothing in this paragraph was executed on CUDA.** It also does not model nvcc's default FMA contraction, which should not affect whether the first deviation occurs (both partial means are still exactly 1.0 there, so `fma(nA, 1, nB)` and `nA*1 + nB*1` agree) but could shift the set afterwards. Treat the specific widths as predicted, not measured. If someone with an A100 or similar can run the snippet below, I will fold the result in:
>
> ```python
> x = torch.ones(4, 244, dtype=torch.float32, device='cuda')
> F.layer_norm(x, (244,), eps=1e-5).abs().max()   # predicted non-zero
> ```
>
> ROCm is hit far harder only because `coef` comes from `__builtin_amdgcn_rcpf`, which on gfx950 is exact at every power of two and at 5, 9, 10, 20, 36, 40, 80 but 1 ulp low at 3, 6, 12, 24, 48, 96, 192, 384, 768, 1536 — hence the `3 * 2^k` widths that dominate reports. The carve-out at that line names only gfx90a, so gfx942 and gfx950 both take it. Measured on an MI300X (gfx942), the failure is bit-identical to gfx950 at every width tried - W=12 `5.654592678e-05`, W=24 `7.539457147e-05`, W=48 `9.424321615e-05`, W=192 `1.319404982e-04`, W=384 `1.884864287e-05`, W=1536 `3.769728573e-05`, with the same saved-mean bit patterns, and 16/20/36/40/80/256/4096 exactly zero. That run used torch 2.7.1+rocm6.4.1, so this is long-standing rather than a recent regression. Note W=244 fails there too (`7.539457147e-05`), which is one of the widths predicted for the CUDA layout. The fix needs no architecture-specific handling: `delta == 0` on constant input holds regardless of reciprocal accuracy, covering gfx90a, gfx942, gfx950 and CUDA uniformly.
>
> Two deliberate limits. `sigma2` still multiplies by `nB`, so variance and `rstd` remain inexact for non-constant input — ordinary accuracy, not the exactness bug fixed here. And `cuWelfordCombine` guards `dataA.count == 0` but not `dataB.count == 0`, where `SharedReduceOps.h` guards both; the unguarded side relies on `delta * 0 == 0`, which would be NaN if a partial mean were infinite, but no call ordering reaches it — `compute_stats` passes the denser accumulator first at both call sites — so a branch was not added to the reduction for an unreachable case.
>
> ## Benchmark results
>
> fp32 forward, MI355X (gfx950), same tree and build flags, best of 5 medians per run, ~256 MB of input at each width:
