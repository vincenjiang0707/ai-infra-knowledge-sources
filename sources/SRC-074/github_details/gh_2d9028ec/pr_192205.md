## 正文

bytearray has no VariableTracker model in Dynamo and any attempt to use
it results in a graph break. This is the first PR in a series to close
this gap (see #192126).

This PR adds ByteArrayVariable (inheriting BaseListVariable) with
read-only operations and construction support. Read the changes starting
from ByteArrayVariable in lists.py, then ByteArrayBuiltinVariable in
builtin.py for construction, then the wiring in builder.py and
trace_rules.py.

Mutation (append, extend, setitem, +=) and method support (decode, hex)
are deferred to follow-up PRs.

Co-authored with an AI assistant.

Test Plan:
Tests ported from CPython's Lib/test/test_bytes.py (BaseBytesTest),
covering construction, len, getitem, slicing, iteration, contains,
comparison, repeat, repr, bool, isinstance, and unhashable.

### Summary
Adds `ByteArrayVariable` (read-only ops) plus a `ByteArrayBuiltinVariable` constructor and wires `bytearray` into `builder.py`/`trace_rules.py`. The read-only sequence surface is mostly sound, but `ByteArrayBuiltinVariable.call_function` has one silent-wrong-answer bug and a systematic exception-translation gap, the "mutable" wiring is registered without any mutation support (leaving a bare `AssertionError` trap for PR 2), and the test file never exercises the `builder.py` code path this PR changes.

### Code Quality

**`bytearray(-1)` silently returns an empty bytearray instead of raising.** `torch/_dynamo/variables/builtin.py:3831-3833`:

```python
if isinstance(val, int):
    items = [ConstantVariable.create(0) for _ in range(val)]
    return ByteArrayVariable(items, mutation_type=ValueMutationNew())
```

`range(-1)` is empty, so `bytearray(-1)` compiles to `bytearray(b"")`. CPython raises `ValueError: negative count`. This is a silent divergence between compiled and eager behavior — the worst failure class, since nothing surfaces to the user. Note the fix falls out of the redundancy below: deleting this special case routes `-1` through the generic `bytearray(arg.as_python_constant())` path, which raises correctly (though it still needs wrapping, see next item).

**The kwargs guard validates `args` but then unpacks `kwargs`.** `builtin.py:3798-3811`:

```python
if kwargs or len(args) > 3:
    if not all(isinstance(a, ConstantVariable) for a in args):
        unimplemented(
            gb_type="bytearray constructor with non-constant args",
            explanation="Dynamo cannot trace bytearray() with non-constant keyword arguments.",
            ...
        )
    all_args = [a.as_python_constant() for a in args]
    all_kwargs = {k: v.as_python_constant() for k, v in kwargs.items()}
```

The check iterates `args`; the `explanation` says "non-constant **keyword** arguments". A non-constant kwarg value (e.g. `bytearray(source=some_traced_value)`) passes the guard and then hits `v.as_python_constant()`, raising `AsPythonConstantNotImplementedError` — an uncaught `NotImplementedError`, not the intended graph break. The guard needs to cover `kwargs.values()` too. [Fix this →](https://claude.ai/code?q=In%20torch%2F_dynamo%2Fvariables%2Fbuiltin.py%20around%20lines%203798-3811%20on%20branch%20krastogi%2F192126%2C%20ByteArrayBuiltinVariable.call_function%20has%20a%20guard%20%60if%20not%20all(isinstance(a%2C%20ConstantVariable)%20for%20a%20in%20args)%60%20whose%20explanation%20string%20says%20%22non-constant%20keyword%20arguments%22%2C%20but%20it%20only%20validates%20args%20-%20not%20kwargs%20values.%20The%20very%20next%20line%20calls%20v.as_python_constant()%20on%20every%20kwargs%20value%2C%20so%20a%20non-constant%20kwarg%20raises%20an%20uncaught%20AsPythonConstantNotImplementedError%20instead%20of%20graph%20breaking.%20Extend%20the%20guard%20to%20cover%20kwargs.values()%20as%20well%20as%20args.&repo=pytorch%2Fpytorch)

**Seven lines of redundant special-casing.** `builtin.py:3829-3843` special-cases `int` and `(bytes, bytearray)` for `ConstantVariable`, then immediately falls through to:

```python
if arg.is_python_constant():
    result = bytearray(arg.as_python_constant())
```

which handles all three identically and correctly. There is no input for which the special cases differ — except `bytearray(-1)`, where the special case is what produces the wrong answer. Deleting lines 3829-3836 is a net simplification *and* a bug fix. Per `CLAUDE.md` ("If uncertain, choose the simpler, more concise implementation") this should go.

**`len(args) > 3` is unreachable-as-intended.** `bytearray` takes at most 3 positional args, so any call landing in that branch for arity reasons will have `bytearray(*all_args)` raise `TypeError` at trace time — see the exception-translation issue below. The condition reads as defensive coding for a case that cannot succeed; if it is meant to produce the user-visible `TypeError`, that needs to be explicit via `raise_observed_exception`.

**`debug_repr` and `reconstruct_pycode` deviate from the sibling pattern.** `lists.py:1905-1907` and `1920-1921` both call `item.as_python_constant()` directly. Compare `TupleVariable.reconstruct_pycode` (`lists.py:1830-1834`), which recurses via `item.reconstruct_pycode(codegen)`, and `BaseListVariable.debug_repr_helper` (`lists.py:166-167`), which uses `i.debug_repr()`. Both new methods will raise `AsPythonConstantNotImplementedError` if any item is not a constant — reachable if an element of an input bytearray gets wrapped as a `SymNodeVariable` under automatic dynamic shapes. Lower confidence on reachability, but the deviation from the established pattern is unambiguous and the delegating form has no downside.

### API Design

**`bytearray` is registered as mutable while implementing zero mutation, which sets a trap rather than deferring cleanly.** Two independent places now claim mutability that nothing backs:

1. `builder.py:2490` adds `bytearray` to `track_mutable`, giving input bytearrays `ValueMutationExisting`. But `side_effects.py` dispatches replay handlers by `isinstance` — `ListVariable` at line 1545, `DequeVariable` at line 1569 — and `ByteArrayVariable` subclasses `BaseListVariable` directly, so neither matches. `codegen_update_mutated` then hits `raise AssertionError(type(var))` at `side_effects.py:1508-1510`. This is unreachable today only because `BaseListVariable.call_method` exposes just `index`/`count`, so `is_modified` can never become `True`. The moment PR 2 adds `append`, this becomes a bare `AssertionError` with no diagnostic.

2. `ByteArrayVariable` does not override `sq_repeat_impl`, so it inherits `lists.py:352-368`, where `if issubclass(self.python_type(), list)` is `False` for `bytearray`. `b * 3` therefore returns a `ByteArrayVariable` with `mutation_type=None` — an immutable tracker for a value that is mutable in Python. Same shape of latency: harmless now, wrong the moment mutation lands.

Both are cheap to close now (register a replay handler; broaden the `issubclass` check to cover mutable sequence types). If the intent is genuinely to defer, then adding `bytearray` to `track_mutable` in this PR is premature and should move to PR 2 alongside the handler — otherwise the tree carries a landmine whose failure mode is an assertion with no message. Please pick one; leaving it half-wired is the option that costs the next debugger the most.

**Missing `__new__` handling relative to siblings.** Both `ListBuiltinVariable.call_method` (`builtin.py:3746-3765`) and `DictBuiltinVariable.call_method` (`builtin.py:3147-3186`) override `call_method` to handle `__new__` for subclass construction. `ByteArrayBuiltinVariable` does not. If `class MyBA(bytearray)` is out of scope, that is fine, but it is a silent gap — and relatedly, `BaseListVariable.cls_for` (`lists.py:129-140`) is an exact-type dict, so `bytearray` subclasses will not resolve to `ByteArrayVariable` at all. Worth a comment stating subclasses are unsupported, so the next reader does not have to derive it.

**`__all__` entries are misplaced.** `variables/__init__.py`: `"ByteArrayBuiltinVariable"` is inserted between `"LazyVariableTracker"` and `"ListBuiltinVariable"`, and `"ByteArrayVariable"` is appended after `"ZipLongestVariable"` at the very end of the list. The surrounding list is alphabetical. Also, `ByteArrayIteratorVariable` is not exported even though the analogous `TupleIteratorVariable` is (line 131).

### Testing

**No test exercises `builder.py`, which this PR modifies.** `make_dynamo_test` wraps a zero-argument closure (`torch/testing/_internal/common_utils.py:2281-2289`), so every bytearray in the test file is constructed *inside* the traced region — exercising only the `builtin.py` constructor path. Nothing passes a bytearray as an argument to a compiled function, which is the `wrap_listlike` / `GetItemSource` / `SEQUENCE_LENGTH` path the diff touches at `builder.py:2379` and `2490`. Two of the behaviors changed in this PR (input wrapping and `track_mutable` registration) have zero coverage. This needs a `torch.compile`d function taking a `bytearray` parameter.

**No error-path coverage at all.** The test file contains no `assertRaises(TypeError)` / `assertRaises(ValueError)` for constructor misuse. Given that every branch calling the real constructor can raise (`bytearray("abc")` → `TypeError: string argument without an encoding`; `bytearray([256])` → `ValueError: byte must be in range(0, 256)`; `bytearray(-1)` → `ValueError`), and that none of those calls are wrapped in `raise_observed_exception` (contrast `lists.py:363` and `lists.py:485`, and `raise_type_error` in `ListBuiltinVariable.call_function`), these currently escape as internal Dynamo errors rather than exceptions the traced program can catch. Tests for these would have caught both the missing translation and the `bytearray(-1)` bug.

**`reconstruct` is never exercised.** No test forces a graph break with a live bytearray, and `test/dynamo/test_reconstruct.py` has no `bytearray` coverage. `ByteArrayVariable.reconstruct` (`lists.py:1912-1918`) is dead code as far as the test suite is concerned.

**Mixed `bytes`/`bytearray` comparison is untested.** `richcompare_impl` passes `accepted_type=bytearray` to `_seq_richcompare` (`lists.py:1897-1903`), which returns `NotImplemented` unless `issubclass(other_type, bytearray)` (`lists.py:391-392`). `bytes` is not a subclass of `bytearray`, yet `bytearray(b"ab") == b"ab"` is `True` in CPython. It may still resolve correctly via the reflected path through the `bytes` `ConstantVariable`, but that is exactly why it needs a test — `test_compare` only compares bytearray-to-bytearray, and `test_compare_to_str` only covers str. This is the most common real-world bytearray comparison and it is unverified in both directions, including ordering (`bytearray(b"ab") < b"b"`).

**`test_repr` / `test_repr_empty` cannot fail.** `test/dynamo/test_bytearray.py:216-218`:

```python
b = self.type2test(b"abc")
self.assertEqual(repr(b), repr(self.type2test(b"abc")))
```

Both operands are produced by the same traced construction, so this asserts `repr(x) == repr(x)`. It confirms `repr` does not crash, but never validates that Dynamo's output matches CPython's `"bytearray(b'abc')"`. Compare against a hardcoded literal instead.

**`BaseBytesTest` is a mixin with one subclass.** The docstring promises "`type2test = bytearray` (or bytes for cross-validation)" but only `ByteArrayTest` exists. The pattern itself is idiomatic here — `test_contains_protocol.py` uses it with 20+ subclasses — so either add the `bytes` subclass the docstring advertises (it would also close the mixed-comparison gap above) or drop the mixin and the claim. Per `CLAUDE.md`, unused generality should not land.

### Performance

**Per-byte `VariableTracker` expansion has no size guard on the input path.** `wrap_listlike` (`builder.py:2400-2407`) wraps every element with a `GetItemSource`, and the only specialization escape hatch is the `torch.Size` branch at line 2381. A bytearray is a natural container for large binary buffers, so a multi-kilobyte input becomes thousands of `LazyVariableTracker`s plus per-element guards. `list`/`deque` have the same characteristic, but they are rarely megabyte-scale in traced signatures, whereas that is a normal thing to do with a bytearray. Worth deciding explicitly: either cap the length and graph-break above it, or document why the unbounded expansion is acceptable. Also note the resulting asymmetry with immutable `bytes`, which stays a single `ConstantVariable` (`constant.py:53`) — the same buffer costs O(1) trackers as `bytes` and O(n) as `bytearray`.

### Recommendation

**Request Changes**

Blocking: the `bytearray(-1)` silent miscompile, the kwargs guard validating the wrong operand, missing exception translation on every real-constructor call, and no test coverage for the `builder.py` input path the PR modifies. The two latent mutation issues are not blocking on their own but should either be closed here or have their `builder.py` wiring deferred to PR 2, so the tree does not carry a message-less `AssertionError` in the interim.
