# [Issue #194053] [CPU] inductor::_alloc_from_pool creates out-of-bounds views from unchecked byte offsets

source: https://github.com/pytorch/pytorch/issues/194053
state: closed | updated: 2026-09-25T20:06:14Z
labels: module: crash, triaged, oncall: pt2, module: inductor, module: aotinductor, bot-triaged

## 正文

### 🐛 Describe the bug

`inductor::_alloc_from_pool` accepts a byte offset, dtype, size, and stride
without checking whether the resulting tensor fits in the source storage.

### Reproduction

```python
import torch

base = torch.arange(8, dtype=torch.int64)
view = torch.ops.inductor._alloc_from_pool(
    base, 64, torch.int64, [1], [1]
)
print(view.item())
```

### Expected behavior

The operator should validate the byte offset, dtype item size, size, and stride
against the source storage bounds.

### Additional context

The implementation in `torch/csrc/inductor/inductor_ops.cpp` creates a new
`TensorImpl` sharing the original storage, converts `offset_bytes` using the
requested dtype's element size, and directly installs the supplied size and
stride. No final storage-bounds validation is performed.

### hanbaiGG · 2026-08-22

Thanks for asking. This was found as one result of an unpublished fuzzing project that exercises registered operators through `torch.ops` and the JIT dispatcher, rather than through production use of Inductor memory planning.

We understand that memory planning is opt-in and that `_alloc_from_pool` is intended as an internal, trusted-caller operator. Our concern is that the operator is currently registered and directly reachable through `torch.ops` / JIT, where caller-supplied metadata can construct an out-of-bounds tensor and lead to a native ASAN-detectable memory access.

Given that exposure, it may be worth either adding suitable validation—potentially in a form that avoids affecting the normal generated-code path—or preventing direct `torch.ops` / JIT exposure if the operator is only intended for trusted internal callers. We are happy to defer to the maintainers on which contract is appropriate.
