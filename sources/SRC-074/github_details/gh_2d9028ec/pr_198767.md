Part of the set of changes the two-phase precompile workflow needs at pytorch tip, on top of the open precompile stack that ends in #198558. In that workflow, one GPU captures the model against a fake process group of the serving world size, and then every rank replays the saved artifact with recompilation refused. The set was found by running the workflow end to end at tip on a large production FSDP2 recommendation model. With the full set, the replay completed on all 16 ranks for 100 batches with no refusals.

**What.** Adds `torch.compiler.precompile.no_compilation()`, a process-wide policy with a matching `TORCH_PRECOMPILE_NO_COMPILATION=1` environment variable that workers inherit. While it is active, any compiler work raises instead of running silently. The check, `torch.compiler._no_compile.check_compilation_allowed`, is placed at every compile site:
- Dynamo and Inductor graph compilation;
- Triton kernel compilation, cache misses and autotuning;
- multi-kernel autotuning;
- C++ and GPU kernel compilation and cache misses;
- CuTe DSL, FlyDSL, Pallas and Halide runtime JIT;
- `cpp_extension` JIT builds.

Under the policy, `precompile.load` becomes strict: the cache envelope must verify, and cache hydration must succeed. Triton itself stays usable: cached kernels still load and launch.

**Why it's needed.** The replay is meant to prove that serving does zero compilation. At tip, nothing enforces that, and a serving process can recompile, rebench and autotune kernels while reporting "0 serve-time compilations".

**Evidence status.** The end-to-end run without this change completes, but only because tip enforces nothing beyond the refuse-recompile check. Instrumented replay at tip counted, per rank: 13 Triton kernel compiles, 12 Triton cache misses and 844 autotunes, plus C++ kernel compiles on 4 ranks, all while serving an artifact that claims zero serve-time compilation. An end-to-end run of the strict zero-compile replay with this change is pending.
