# [PR #197799] Fix ctc_loss CPU OOB access on out-of-range target values

state: open | updated: 2026-09-26T20:45:32Z

## 正文

## Issue

Fixes #193794

## Summary

`torch.nn.functional.ctc_loss` accepted out-of-range target values. On CPU the kernels use each target value as an index into `log_probs` and into its gradient, and `get_target_prime()` in `aten/src/ATen/native/LossCTC.cpp` does not bound-check. A negative value, or a value `>= num_labels`, caused an out-of-bounds read in the forward and an out-of-bounds write in the backward, corrupting the heap. The issue reports the process aborting with `double free or corruption (out)` on Linux.

Root cause: `ctc_loss_allocate_outputs` validated `BLANK`, the shapes and lengths, and `target_lengths >= 0`, but never the target values, and `ctc_loss_backward_cpu_template` trusted the forward ("assume that the forward did").

Fix: a file-local helper `check_target_values` validates the first `target_lengths[b]` entries of each batch using the same offset and stride math as the kernels. It is called from the forward allocator and from the CPU backward, which now revalidates because autograd can reach it with a targets tensor mutated after the forward (`.data` does not bump the version counter) and direct callers of the private `_ctc_loss_backward` bypass the forward. This follows the nll_loss precedent of checking targets in the backward. The CPU backward entry point also size-checks the length lists against the batch size, mirroring the forward allocator.

The scan is deliberately conservative: it validates the first `target_lengths[b]` entries even in the rare cases where the kernel would not read them (for example `input_lengths[b] == 0`), and it never validates padding beyond `target_lengths[b]`. The forward check is gated on `targets.device().is_cpu()`: meta tensors have no data, and with meta `log_probs` plus accelerator targets the meta kernel reaches the shared allocator, where host-dereferencing a device pointer would be undefined behavior.

Errors raised by the two paths:

```
RuntimeError: Expected target values to be in the range [0, 6), but got value 6 for batch 0 (while checking arguments for ctc_loss_allocate_outputs)
RuntimeError: Expected target values to be in the range [0, 6), but got value 99 for batch 0 (while checking arguments for ctc_loss_backward_cpu)
```

## BC-breaking?

No. The change turns previously undefined behavior into a clear error. Inputs with valid target values behave exactly as before.

## Notes

- CPU forward and CPU backward both reject out-of-range used target values now; the CPU gate lives in the forward allocator, and the CPU backward calls the same helper unconditionally. The validation runs before the indexing kernels in both directions.
- CPU-only gating rationale: meta target tensors have no data to read, and with meta `log_probs` plus accelerator targets the meta kernel reaches the shared allocator, where dereferencing a device pointer from the host would be undefined behavior. Accelerator target tensors are never host-dereferenced.
- Padding entries beyond `target_lengths[b]` are intentionally not validated; the kernels never read them.
- Conservative superset caveat: the scan validates the first `target_lengths[b]` entries even where the kernel would not read all of them (for example `input_lengths[b] == 0`, or some middle entries when `input_lengths[b] == 1`). Rejecting a value the kernel would have ignored is deliberate.
- The CPU backward now also size-checks `input_lengths` and `target_lengths` against the batch size like the forward allocator does, so the shared target-value check cannot index past the per-batch offsets vector; this also fixes a pre-existing case where a too-short list was silently accepted.
- Direct CPU `_ctc_loss_backward` calls and `.data`-mutated saved targets now raise instead of reading or writing out of bounds: `.data` bypasses autograd's version counter and the private op bypasses the forward, so both paths are validated in the backward itself (out-of-range values by the shared check, malformed length lists by the new size checks).
- Remaining scope: CUDA, XPU, and MPS kernels are untouched. The CUDA implementation documents the same gap at `aten/src/ATen/native/cuda/LossCTC.cu:212-214`; validating there needs a device sync, so it is left for a separate change.

### ezyang · 2026-09-21 · CHANGES_REQUESTED

Review from Sol agent:

I agree with checking each target once rather than adding a bounds branch to `get_target_prime()`: the latter repeats the check throughout the dynamic program. If we want to avoid a serial phase, I would put a once-per-batch scan at the start of each existing `parallel_for` batch iteration.

I benchmarked extracted versions of this CPU kernel on an M4 Max. For representative `T=100, B=16, L=30, C=32` forward+backward, the serial scan was within noise (about 1.94 ms with or without it, single-threaded). The overhead is visible for computationally trivial inputs: with `T=1, B=256, L=128`, forward+backward rose from about 29 us to 50 us single-threaded. That is a large relative change but only ~21 us absolute. A per-batch scan used existing parallelism and reduced the multithreaded penalty; checking on every access showed a small ordinary-workload regression. I would qualify the "negligible" claim, but performance alone would not block this fix.

I do think two correctness changes are needed:

1. Please move value validation out of `ctc_loss_allocate_outputs()` and into the CPU implementation. `ctc_loss_meta()` also calls this allocator, and `targets.device().is_cpu()` means a meta invocation with real CPU targets now reads their values and has data-dependent success/failure. The shared allocator should remain metadata-only.

2. Please validate the backward scan's indexing metadata before it reads target storage. Checking only that the length lists match `batch_size` does not establish that `target_lengths` are nonnegative or fit `targets`. The new scan occurs before the `zero_infinity` early return, so a direct backward call with `nll=+inf`, `zero_infinity=True`, and an oversized target length can now read out of bounds in the validator itself; that branch previously skipped target reads. Full hardening of the private backward op can be separate, but the new validator must make its own reads safe.

One preexisting issue surfaced here: for concatenated noncontiguous 1D targets, `tg_batch_offsets[i] = pos` omits `targets.stride(0)`, while access later uses `offset + stride * j`. I confirmed that a multi-batch `storage[::2]` target produces a different result from its contiguous copy, and the validator follows the same wrong addresses. The new noncontiguous test covers only 2D. Please either fix the 1D offset in forward/backward with a regression test or explicitly track it as a follow-up.
