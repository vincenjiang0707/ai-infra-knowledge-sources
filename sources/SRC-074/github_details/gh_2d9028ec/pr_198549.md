# [PR #198549] [inductor] Don't swing a realized buffer in mutate_to

source: https://github.com/pytorch/pytorch/pull/198549
state: open | updated: 2026-09-27T05:23:41Z
labels: triaged, open source, module: inductor, ciflow/inductor, ciflow/torchtitan

## 正文

Fixes #198533

`mutate_to`'s fast path replaces the data of the mutated StorageBox with the new value. A realized StorageBox may already be referenced by name: by a ReinterpretView, whose loader looks the name up only when it runs, or by an extern kernel's inputs. Everything lowered before the mutation through those references then reads the new value, including the new value itself. With `y = x + x.sum(-2, keepdim=True)` and a mask of `y.roll(-1, -2) == y.transpose(-1, -2)`, `y.index_put_((mask,), v)` gives wrong values on CPU and CUDA. When an mm reads `y.t()` before the fill, the scheduler fails with a `KeyError`.

The fast path is now taken only for a StorageBox that is not realized. A realized one goes through the existing `realize_into` path, which writes the value into its buffer in place. Inputs, module buffers and NopKernels are all realized nodes, so their three checks are gone. Writing in place means two tensors must not share a buffer:

- A `copy_` node used to give the target its source's buffer, and a later in-place write to either would now change both, so it copies. The values a lowering writes back to a mutated argument (`propagate_mutation`, e.g. after an in-place collective) are still taken as they are, so that code is unchanged.
- An empty buffer that nothing has written yet keeps the fast path, the value copied into its layout, so `empty_like(x).fill_(0)` generates the same code as before.
- `realize_into` no longer uses `unsafe_alias` (the in-place foreach ops) for a realized intermediate, because the foreach value can read it at other positions, as in `_foreach_add_([y], [y.flip(0)])`.

Writing in place also exposes a ConcatKernel bug, found and fixed in #198715: ConcatKernel computes a flexible-layout input straight into the concat buffer, so an in-place mutation of that input after the cat changes the concat. `index_put_` with integer indices after `cat` was already wrong; the masked form was right only because `mutate_to` swung the pointer. The fix is #198715's: GraphLowering collects the fake storages that some node writes in place (including inside control_deps subgraphs), and ConcatKernel copies such inputs instead of computing them into its buffer. `test_cat_input_mutated_after_cat` and the two control_deps tests are from #198715 too.

Test plan, on 2.14 with the change applied at runtime (RTX 4070):

- New tests in test_torchinductor.py: `test_index_put_as_masked_fill_mask_reads_target_view` (wrong values), `..._by_extern_kernel` (`KeyError`), `test_mutate_realized_buffer_in_make_fx_graph` (make_fx graphs that keep `copy_`, `add_` and a foreach flip), `test_cat_input_mutated_after_cat`, and `test_masked_fill_of_realized_buffer_kernel_count`, which checks that a masked fill of an mm output stays one kernel written in place. Halide skips that one: it refuses to fuse a read of the buffer a kernel writes in place, so there the fill is two kernels. All pass on CPU and CUDA in test_torchinductor{,_dynamic_shapes,_codegen_dynamic_shapes}.py and on HalideCpuTests (the kernel-count test skipped, pip halide 21.0.0); without the change 18 of the 30 fail. test_control_deps.py: 13 passed (the two new tests fail without the change).
- `test_inductor_steal_buffer` and the rest of `TestCollectivesInductor` pass (single-rank NCCL), with the same generated code as before; `test_triton_kernel_clone_wekdeps` generates the same code as before, default and cpp_wrapper.
- A/B, same outcome test by test apart from the new tests (about 2,100 tests): the mutation/copy/fill/index_put/cat/concat/scatter/inplace/foreach/alias selections of test_torchinductor{,_dynamic_shapes,_codegen_dynamic_shapes}.py, test_foreach.py, test_inplacing_pass.py, test_auto_functionalize.py, test_triton_kernels.py KernelTests, the cat/stack/index_put/scatter OpInfo tests and TestCollectivesInductor.

Kernels and allocations, before -> after (CUDA; on the C++ CPU backend the same number of kernels or fewer; Halide takes 2 kernels for the masked fill of an mm output):

| Pattern | Before | After |
|---|---|---|
| `s = x @ w; s.index_put_((m,), -inf)`, and `s[s < 0] = 0` | 1 kernel | 1 kernel |
| fill_, add_ or foreach add_ on a realized mm output, `empty_like(x).fill_(0)`, in-place collectives | same | same |
| `copy_` of an mm output into an empty or unrealized buffer | 0 kernels | 1 kernel |
| `copy_` of an mm output into another realized mm output | 1 kernel, 2 allocations | 2 kernels, 3 allocations |
| foreach add_ into a realized mm output `y` of a value that reads `y` elsewhere (`y.flip(0)`) | 1 kernel | 2 kernels (CPU: 1) |
| A masked fill of a realized buffer whose mask reads that buffer at other positions (`y.roll`) | 2 kernels | 3 kernels (CPU: 1) |

The `copy_` and foreach rows come only from graphs that keep their mutations (make_fx + compile_fx_inner): torch.compile functionalizes them away. In the last row the mask has to be computed before the in-place write.

The fix is sound: once a StorageBox is realized, other nodes may refer to its buffer by name and look that name up late, so swinging the data pointer isn't safe. It needs changes before merge, though: the new branch forces an extra materialized buffer and repeats the existing slow path, and two CI failures come straight from this PR.

<details>
<summary>Full review</summary>

### Summary
This PR changes `mutate_to` to write into an already-realized target with `realize_into` instead of swapping `StorageBox.data`. The invariant it relies on is correct: `ReinterpretView.make_loader` and `ExternKernel` inputs resolve `StorageBox.get_name()` late, while readers of an unrealized box inline `inner_fn` during lowering. So after this PR the fast path only applies to unrealized data. The problems are in how the change is structured, what it costs, and the tests.

### Code Quality
- `torch/_inductor/lowering.py:7763-7773`: `val.realize()` now runs before the new branch. On the old slow path (`:7778`), `val` was not realized first, so `realize_into` inlined `val`'s `inner_fn` into the copy `Pointwise`. Now `val` becomes its own named `ComputedBuffer` first. The copy kernel then does `ops.load` from it, so each realized-target mutation lowers to two nodes and depends on scheduler fusion to remove the intermediate. When `val` is a reduction or an extern/template output (e.g. `copy_` from an `mm` result), the intermediate stays: you get a full extra buffer plus a copy kernel, where the old path copied nothing.
  - The new block also just repeats the fall-through `realize_into` call at `:7778`. A simpler fix that addresses both points is to put the check in the fast-path guard and delete the new block:
    ```python
    if (
        isinstance(changed_data, ir.StorageBox)
        and not IRNode.is_realized_node(changed_data.data)
        and not (changed_data.is_input_buffer() or changed_data.is_module_buffer() or isinstance(changed_data.data, ir.NopKernel))
    ):
    ```
    (Split lines as lint requires.) With that guard, `is_input_buffer()` and `is_module_buffer()` are redundant for realized data. Only the `NopKernel` case still matters.
  - The comment describes the hazard as specific to `ReinterpretView`. The actual rule is "a realized StorageBox may already be referenced by name (views, extern kernel inputs), so its data can't be replaced". A one-line comment at the guard that says this is enough.

### Testing
- The PR breaks `test/inductor/test_triton_kernels.py::KernelTests::test_triton_kernel_clone_wekdeps`. `torch.empty_like(x).fill_(0.0)` goes through the new path because the empty buffer is a zero-range `ComputedBuffer`, not a `NopKernel`. Buffer naming and lifetimes change, and the `FileCheck("del buf3")` assertion fails. The test needs updating, and someone should confirm that the new code for the empty+fill pattern is no worse (no extra allocation, no extra kernel).
- The new `test_index_put_as_masked_fill_mask_reads_target_view` fails in `test_torchinductor_codegen_dynamic_shapes.py` (`DynamicShapesCodegenCpuTests`) with "Failed to find dynamic for loop variable". Either add it to that file's `test_failures` dict with a reason, or change the test so it really exercises dynamic sizes.
- The regression test only covers `index_put_as_masked_fill`. The change applies to every `mutate_to` caller: `fill_`, `copy_`, `register_inplace` ops, the foreach in-place ops (`unsafe_alias=True`) and `fsdp.copy_`. At least one case where an extern kernel reads the realized target before the mutation would cover the `codegen_reference`/`get_read_writes` side of the same bug.

### Performance
- Mutating a realized intermediate now always emits a copy through a `MutationLayoutSHOULDREMOVE` node instead of reusing `val`'s buffer. For `register_inplace` ops and `copy_`/`fill_` coming from decompositions or reinplacing, this can add a buffer and a kernel. The PR's evidence is correctness only. Please add a perf check (e.g. the inductor dashboard or TorchBench via `ciflow/inductor-perf-test-nightly`) or a codegen count assertion showing that the common cases still produce one kernel. The restructuring above removes most of the risk.

### Recommendation
**Request Changes**: two CI failures come directly from this PR (`test_triton_kernel_clone_wekdeps` and the dynamic-shapes codegen variant of the new test). The `val.realize()` placement should also be fixed so realized-target mutations don't materialize an extra buffer.
