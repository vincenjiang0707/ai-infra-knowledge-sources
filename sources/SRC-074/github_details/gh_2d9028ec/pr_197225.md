# [PR #197225] [inductor] Preserve repeated tensor aliases in Triton HOPs

source: https://github.com/pytorch/pytorch/pull/197225
state: open | updated: 2026-09-25T13:01:21Z
labels: triaged, open source, ciflow/trunk, topic: not user facing, module: inductor, ciflow/inductor, ciflow/torchtitan

## 正文

The functional Triton HOP cloned every mutated argument independently. When multiple kernel arguments referenced the same tensor, the kernel received distinct storage, so writes through one pointer were not visible through the other and compiled results silently differed from eager execution.

Record the exact input-identity groups when the functional HOP is formed and clone once per group. Carry this partition through proxy tracing, fake tensor execution, functionalization, and reinplacing, since later graph rewrites can merge originally distinct arguments and make current object identity insufficient to reconstruct the original semantics. This covers repeated references to one tensor object, but not distinct views that share storage.

Preserve identity when wrapping functionalized outputs, and keep older or symbolic FX graphs compatible by deriving omitted alias groups only when concrete inputs are available. Functional-only alias metadata is removed before lowering to the mutation HOP.

Add coverage for repeated aliases, mutation through aliased outputs, no-op rewrites that merge distinct arguments, and pass-level cases where an alias group can be reinplaced or must stay cloned because its value remains live or another reinplaced argument shares storage. Also cover symbolic FX tracing, serialization, and legacy graphs without alias metadata.

Fixes https://github.com/pytorch/pytorch/issues/196657

## PR Review: #197225

### Summary
The functional Triton HOP now records which of its mutated kwargs were the same tensor object (`tensor_alias_groups`). It clones once per group and carries the groups through proxy, fake, functionalize and reinplace.

That fixes the eager/compile mismatch for `k(y, y)`. However, it gives up reinplacing entirely for aliased arguments, and it adds `None`-fallback code in several places where it can't run.

### Performance
- **`torch/_inductor/fx_passes/reinplace.py:766-805`: repeated-alias groups are never reinplaced.** Any arg in a group of size > 1, or any repeated FX node in the legacy path, gets `should_attempt_reinplace = False`. So `k(y, y)` now always costs a clone of `y` and a `copy_` back, even when `can_inplace(node, y)` holds.
  - Before this PR, the first alias was reinplaced. That was buggy: the pointers got distinct storage.
  - The right fix is to treat the group as one unit. If the shared tensor can be inplaced and nothing with the same storage was already reinplaced, reinplace every member of the group together. All the kernel's pointers then target the same buffer, which matches eager.
  - The change to `test_triton_kernel_clone_wekdeps` (next section) points to this regression: with the original `k(x, buf, buf)` the extra clone would break the `run(x_1, buf0,` FileCheck.

### Testing
- **`test/inductor/test_triton_kernels.py:~801-823` (`test_triton_kernel_clone_wekdeps`): the test was changed to avoid the aliased case.** It used to pass the same `full_default` as both `out_ptr0` and `out_ptr1`. The PR rewrites it to use `full_default0.view_as(full_default0)`, which is exactly the view-aliasing case the PR says it doesn't handle.
  - The test now checks a different graph, and nothing covers the original same-tensor weak-dep scenario.
  - Please keep the original form and fix the reinplace behavior above so the FileCheck still passes. At minimum, add a separate aliased variant.
- **No test checks reinplacing for aliased groups.** `test_repeated_alias_compile` only compares numerics. Please add a check on generated code or clone count for `k(y, y)` where `y` is a dead intermediate, so regressions in reinplacing show up.
- **The view-alias case is still silently wrong and not called out.** `_get_tensor_alias_groups` groups only by `id()`, so `k(y, y.view_as(y))` or `k(y, y[:])` still gives the kernel distinct storage under compile, while eager shares it. This predates the PR (see the TODO at `triton_kernel_wrap.py:1772`). Since the PR claims to fix aliasing, please either add an xfail/expected-failure test for it or say explicitly in the PR description that issue #196657 is only fixed for identical tensors.

### Code Quality
- **`torch/_higher_order_ops/triton_kernel_wrap.py` (fake, proxy and functionalize impls): the `tensor_alias_groups is None` fallbacks there look unreachable (low confidence, please confirm).**
  - `TritonKernelWrapperFunctional.__call__` already derives the groups whenever inputs are concrete, and every dispatch impl is reached through `__call__`.
  - The only callers that skip `__call__` are the direct `triton_kernel_wrapper_functional_dense(...)` call in `post_grad.decompose_triton_kernel_wrapper_functional` and the legacy branch in reinplace.
  - Suggestion: keep the derivation in `__call__` and `_dense` only, and remove the copies in `_fake_tensor_mode`, `_proxy_torch_dispatch_mode` and `_functionalize`. That leaves one source of truth instead of five.
- **The `__call__` guard at `triton_kernel_wrap.py:1519-1530` is hard to read.** It checks `fx.Proxy` in three separate ways. A short helper such as `_has_concrete_clone_keys(kwargs, tensors_to_clone)`, or one `pytree.tree_any(lambda x: isinstance(x, fx.Proxy), (kwargs, tensors_to_clone))`, would state the intent directly.
- **Undocumented invariant.** After reinplace narrows `tensors_to_clone`, `tensor_alias_groups` still lists the original keys. It then covers more keys than `tensors_to_clone` instead of being an exact partition of it. `_clone_mutated_args` relies on every remaining key still being in `group_by_key`, which holds only because groups of size > 1 are never reinplaced. If the reinplace change above goes in, either trim the groups in reinplace (`reinplace.py:1056-1058`) along with `tensors_to_clone`, or document in `_get_tensor_alias_groups` that the groups may cover more keys than `tensors_to_clone`.
- **Parameter order is inconsistent.** `tensor_alias_groups` comes after `tensor_bases` in `__call__`, but before `launch_kwargs`/`tensor_bases` in the impl signatures. It's keyword-only, but it should match within the file.

### Recommendation
**Request Changes**

The blockers:
1. Aliased groups should be reinplaced as a unit instead of excluded.
2. `test_triton_kernel_clone_wekdeps` should go back to its aliased form, or get a new aliased variant, rather than being changed to avoid the case.
