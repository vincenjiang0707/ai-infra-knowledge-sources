# [Issue #198017] ☂️ Forward-mode and higher-order AD return wrong derivatives

source: https://github.com/pytorch/pytorch/issues/198017
state: open | updated: 2026-09-25T07:44:44Z
labels: module: autograd, triaged, module: derivatives, module: correctness (silent), module: forward ad

## 正文

Umbrella tracking issue for a **class** of bugs: `torch.func.jvp` / `torch.autograd.forward_ad`, nested (second-order) forward AD, `jacfwd`, and `hessian` return **numerically wrong derivatives** for ops whose first-order backward is correct. No error is raised; the wrong number flows into an optimizer, an implicit-layer solve or a physics model and surfaces as a training problem rather than a stack trace.

This is the forward-mode sibling of the eager-vs-compiled correctness umbrellas (#195547, #197554). If the repro only misbehaves under `torch.compile`, it belongs on `oncall: pt2`, not here.

### The shared root cause

Every member is a **per-op formula bug in a hand-written derivative rule** (`tools/autograd/derivatives.yaml` / `torch/csrc/autograd/FunctionsManual.cpp`), not an infrastructure bug in the forward-AD machinery:

- a JVP written with the factors in the wrong order for a non-commutative product (`cholesky_inverse`, `cholesky_solve`);
- a second-order term dropped when the JVP rule is itself differentiated (`linalg.solve`, `det`, `slogdet`, `householder_product`, `batch_norm`, `layer_norm`);
- a rule that is only right on the generic branch and wrong at a boundary the sample inputs never hit (`cumprod` at a zero factor, `scatter_reduce(prod)` with a zero, `triangular_solve(unitriangular=True)`, `logcumsumexp` with an underflowing prefix, `sinc` / `logaddexp` at a removable singularity);
- a custom `autograd.Function` whose `jvp` is not re-entered for higher derivatives (#197867).

Each one needs its own derivation and a float64 / complex128 finite-difference check. They are cheap to fix individually, but that is exactly why they keep coming back: the class is **under-tested**, so each fix only covers the op somebody happened to sweep.

### Why CI did not catch these

All of the affected ops declare `supports_forward_ad=True` and `supports_fwgrad_bwgrad=True` in their `OpInfo`, and none of the second-order ones carry a skip. The gap is in what the harness checks:

| Order | What is tested today | Reference |
|---|---|---|
| first-order JVP | `test_forward_mode_AD` (`gradcheck(check_forward_ad=True)`) | finite differences |
| reverse-over-forward | `test_fn_fwgrad_bwgrad` | finite differences |
| reverse-over-reverse | `test_fn_gradgrad` | finite differences |
| **forward-over-forward** (nested JVP) | `functorch` `test_jvpjvpvmap` only | **vmap-vs-loop consistency, no numerical reference**, and only over `autograd_function_db` |

So a wrong second-order JVP passes CI as long as it is wrong the same way with and without `vmap`. The first-order members slipped through a different hole: `sample_inputs` never exercise the failing regime (zero factors, `unitriangular=True`, underflowing prefixes), and `cholesky_solve` has `test_forward_mode_AD` skipped outright.

### What would close the class

**Not one PR per op.** Per-op fixes are welcome (two are already up) and each member stays open as the record for its reproducer, but the ask that actually closes the class is test infrastructure:

- [ ] an `OpInfo` test that checks **forward-over-forward** against a finite-difference reference (`gradcheck` already has `check_forward_ad`; add a nested variant or extend `gradgradcheck` with a `check_fwd_over_fwd` mode) and turn it on for every op with `supports_forward_ad=True`;
- [ ] audit ops whose forward-AD tests are skipped or whose `sample_inputs` avoid the singular / boundary regime, and add `error_inputs`-style boundary samples for derivative checks;
- [ ] for `autograd.Function`, a test that `jvp` composes with itself (`jacfwd(jacfwd(f))`) over `autograd_function_db`.

### Out of scope

- Forward AD **raising** `NotImplementedError` / "not supported" for an op (a missing rule, not a wrong one), e.g. #182641, #182661, #182842, #191787.
- Low-precision `inf`/`nan` in a derivative where the float64 formula is right (dynamic range, not a formula bug).
- Wrong derivatives that appear only under `torch.compile` (e.g. #190855) — `oncall: pt2`.
- First-order **backward** formula bugs; those go on their own tracker.
