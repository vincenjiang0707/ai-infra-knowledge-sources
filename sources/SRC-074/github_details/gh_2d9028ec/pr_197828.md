## 正文

[dynamo] Migrate AutogradFunctionVariable.apply attribute access to tp_getset

apply's call dispatch was already migrated to the declarative tp_methods table in #195180, but referencing .apply as a bare attribute and without calling it, it still went through a hardcoded if name == "apply": branch in tp_getattro_impl. This moves that branch to a tp_getset entry instead by following the same pattern.

It uses unmodeled_setter instead of a readonly_setter. The reason is that eager Python allows you to write to MyFn.apply directly. Dynamo simply does not model the write. Therefore it should graph-break instead of raise AttributeError.

Part of #195165

## PR Review: #197828

### Summary
This PR moves the `name == "apply"` case in `AutogradFunctionVariable.tp_getattro_impl` into a `tp_getset` entry that uses `unmodeled_setter`. Reads of `MyFn.apply` behave the same as before. There are three problems: the entry misdescribes the CPython type, the setter it adds is never reached, and the lookup added to `tp_getattro_impl` duplicates work the object protocol already does.

### API Design
- **`apply` is a method, not a getset** (`torch/_dynamo/variables/misc.py:1487`). `tp_getset` is meant to mirror `PyGetSetDef`, which is a data descriptor (see the `GetSet` docstring in `base.py:438`). But `Function.apply` is `_C._FunctionBase.__dict__["apply"]` (`torch/autograd/function.py:741`). That is a `METH_CLASS` entry in `_FunctionBase`'s `tp_methods`, so it's a non-data classmethod descriptor, and this VT already declares it in `tp_methods` (`misc.py:1484`, from #195180).
  - Declaring the same name in both tables tells the object protocol that `apply` is a data descriptor. That affects the data-descriptor precedence checks, e.g. `object_protocol.py:2380-2385` and the checks before `tp_getattro_impl`.
  - A more faithful fix would build the bound method from the existing `tp_methods["apply"]` entry during attribute lookup. Another option is to keep the special case until the base protocol can bind `tp_methods` entries generically.
  - If `tp_getset` is kept as a stopgap, it needs a comment saying this entry doesn't mirror a real `PyGetSetDef`.

### Code Quality
- **The `unmodeled_setter` is never called**, so the PR description's reasoning doesn't hold. Setters in `tp_getset` only run through descriptor paths: `GetSetDescriptorVariable` / `MemberDescriptorVariable.tp_descr_set_impl` (`functions.py:5114`, `:5209`) or a VT-specific `call_setattr` (e.g. `TracebackVariable`, `misc.py:556`).
  - `MyFn.apply = x` goes `STORE_ATTR` -> `BuiltinVariable._call_setattr` (`builtin.py:3709`).
  - `AutogradFunctionVariable` isn't in that function's `isinstance` list, and it doesn't override `get_value_for_setattr`, so the write falls through to the existing generic handling. The new entry plays no part.
  - In eager, the write goes through `type.__setattr__` into the class `__dict__`, not through a getset setter. The choice between `unmodeled_setter` and `readonly_setter` therefore has no effect.
- **The lookup added to `tp_getattro_impl` is redundant** (`misc.py:1582-1586`). `object_protocol.py:2397-2403` already checks `tp_getset`/`tp_members` before calling `tp_getattro_impl`. Its comment says this is "so a tp_getattro_impl override need not repeat the consult". `VariableTracker.tp_getattro_impl` (`base.py:2189`) does the lookup only because it is the default implementation. Overrides of `tp_getattro_impl` elsewhere don't repeat it, so this block should be removed.
- **`_get_apply` is more verbose than the code around it** (`misc.py:1471-1481`):
  - The `self` annotation isn't needed.
  - The return type says `| None`, but the getter never declines.
  - The four-line `if/else` for `source` can be the one-line `AttrSource(self.source, "apply") if self.source is not None else None` used a few lines below.
  - The temporary `result` variable can go. The whole body fits in one `return`.

### Testing
- There's no test for a write to `MyFn.apply` inside a compiled region, which the PR describes as its intended behavior change. Reads are already covered by `test/dynamo/test_autograd_function.py:1326` and `:1347`. If the setter is kept, add a test that it is actually reached. Given the analysis above, I expect such a test would show it isn't.

### Recommendation
**Request Changes**

The main blocker is the design question: `apply` is a `tp_methods` classmethod, not a `PyGetSetDef`. Either bind it from `tp_methods` or document why `tp_getset` is used here. Also remove the duplicated lookup in `tp_getattro_impl` and the setter that is never called (or test it).
