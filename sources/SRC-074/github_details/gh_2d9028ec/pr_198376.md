# [PR #198376] [inductor] Always in-place user defined Triton kernels

## 正文

This pull request improves the re-inplacement pass by additionally allowing it to re-inplace ops against views of graph inputs. It matches the inverse write back pattern created during functionalization and recorded in the fx metadata. It should always be possible to inplace these functional wrapper ops created this way without tracing back from the epilogue copy, we just have to update the users of the pattern, and we can separately investigate the epilogue copy's eligibility for removal.

I found the original missed re-inplacement opportunity in particular against a private implementation of a model that has integrates custom Triton kernels that writes back to slices, which prevented re-inplacement because the view replay nodes (`slice_scatter`, canonicalized to `_generalized_scatter`) appeared between it and the epilogue copy.

It is inspired by the reply by Claude in #190548 which mentioned that I should probably look at what happens with that PR and an unknown op write to the result of an inplaced op. That PR would abort re-inplacement in this case; this redesign looks at ancestry to associate the chain with its epilogue copy that reflects the changes back to the graph input.

I have used AI-assisted tools to generate the tests for this PR, to create scenarios and tests and get an understanding of how the pass works. However, the changes to the pass itself are my own.
