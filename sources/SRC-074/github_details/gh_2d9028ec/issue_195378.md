# [Issue #195378] Expose green context resource query - allocated SM count is not visible to Python

source: https://github.com/pytorch/pytorch/issues/195378
state: closed | updated: 2026-09-26T03:47:06Z
labels: module: cuda, triaged, function request, bot-triaged

## 正文

### 🐛 Describe the bug

**Summary:**
when we creare a Green Context using:
`torch.cuda.green_contexts.GreenContext.create(num_sms=N)`
the cuda driver may allocate fewer SMs than we requested. However, Pytorch curently does not provide any way to check the actual number of allocated SMs from Python.

The CUDA driver already provides information through `cuGreenCtxGetDevResource`, but Pytorch does not expose it.

```python
import torch
g = torch.cuda.green_contexts.GreenContext.create(num_sms=120,device_id=0
)
print([a for a in dir(g) if not a.startswith("_")])

Output=
[W830 22:26:32.284452558 CUDAGreenContext.cpp:42] Warning: Attempted to create a green context but there was no primary context! Creating a primary context... (function GreenContext)
requested 120 SMs -> ['Stream', 'create', 'max_workqueue_concurrency', 'pop_context', 'set_context']
requested  22 SMs -> ['Stream', 'create', 'max_workqueue_concurrency', 'pop_context', 'set_context']
```

There is no attribute or method that tells us how many SMs were actually allocated.

**What happens in practice:**
For example, on nvidia L40s, which has 142 SMs, I requested 120 SMs:
```python
g = torch.cuda.green_contexts.GreenContext.create(num_sms=120)
```
But the driver actually allocated 114 SMs.

Nsight Systems shows:
```
SM Allocation: 114 of 142 available on device
TPC Allocation: 57 of 71 available on device
```
`Context ID: 2
SM Allocation: 114 of 142 available on device
TPC Allocation: 57 of 71 available on device
TPCs: 0-3,5-9,11-15,17-21,24-27,30-33,35-39,41-45,47-51,53-57,59-63,65-69
Workqueue Sharing Scope: 0 (DEVICE_CTX)`

<img width="398" height="205" alt="Image" src="https://github.com/user-attachments/assets/5027daf2-7efb-4306-9aa4-2c175f7a77ec" />

The rounding is expected because Green Contexts have architecture-specific SM allocation granularity.

The issue is that this information is not available from Python. The only way I found to check it was through the profiler.

**Why this matters:**
This becomes important when doing experiments where we divide the GPU into different SM allocations.
For example, if I request 120 SMs but the driver gives me 114, I might record my experiment as a 120-SM configuration, even though it is actually running with 114 SMs.

Also, requesting 120 SMs and requesting 114 SMs can result in the same actual allocation. So during a sweep, two configurations that look different may actually be identical.

Having access to the actual allocation would make these experiments much easier to verify and reproduce.

**Proposed change**
Could PyTorch expose the actual allocated SM count through the GreenContext object?
```python
g.sm_count
or
g.sm_count()
```
Internally, this could use the CUDA driver's `cuGreenCtxGetDevResource` API for `CU_DEV_RESOURCE_TYPE_SM`.

It would also be useful to expose the allocated TPC/SM IDs in the future, since that would allow users to check whether two Green Contexts are actually disjoint. But I think exposing the SM count alone would solve the most common use case.

I also noticed that cuDevSmResourceSplit / cuDevSmResourceSplitByCount are not currently exposed in Python. This seems like a related issue, although I'm happy to file that separately if it should be a different discussion.

### Umang-projects · 2026-09-02

Update: The alternative is implemented to verify that overlap is indeed avoidable.

The following simple CUDA wrapper that invokes `cuDeviceGetDevResource` -> `cuDevSmResourceSplitByCount` (in one call) -> `cuDevResourceGenerateDesc` -> `cuGreenCtxCreate`, giving group[0] to one context and the rest of the groups and leftovers to the other one, results in a nice separation. `cuGreenCtxGetDevResource` verifies that 22 + 120 = 142 and there are no overlaps and no unused TPCs.

It turns out that the overlap appears because every call to `GreenContext.create()` runs its own split independently, and it vanishes when using a single split whose components are assigned explicitly.

The problem with such approach is that it cannot be reached from the Python code since there are no bindings for `cuDevSmResourceSplit` 
or `cuDevSmResourceSplitByCount`.

Happy to create a separate issue if needed.

### Umang-projects · 2026-09-10

@ngimel I have this design, example of the problem due to overlapping, for an L40S (142 SMs, `smCoscheduledAlignment` = 2, `minSmPartitionSize` = 4):

```python
a = GreenContext.create(num_sms=120)
b = GreenContext.create(num_sms=22)
```

As `create()` does its own split, the driver selects different TPCs for each one, without being aware of the other one. The commonality between the two resulting sets is 6 TPCs, and 6 TPCs are left out in both sets. The numbers of SMs return correctly, 120 and 22, but the partitioning is not disjoint, and therefore the isolation promised by the API does not hold. There is nothing in the Python API that will allow you to see that.

Using just one split that outputs both sets results in a proper partitioning. This was tested locally with a small modification.

**Two independent components:**

1. Read-only accessor through `cuGreenCtxGetDevResource` for `CU_DEV_RESOURCE_TYPE_SM`, which makes the resource accessible and not only a counter. The TPC/SM identity is the thing that will tell you whether two contexts overlap or not – only `sm_count` isn’t enough.
2. Ability to create several sets out of one partition so that all partitions are disjoint from each other.

The first one is relatively small and independent from the design part of (2) – feel free to raise a PR if you like it.

### Umang-projects · 2026-09-26

Hello, thank you guys for all the help in fixing this.
This is what I was doing in my code just for reference. I have split SM resource using cuDevSmResourceSplitByCount and created individual green streams for prefill and decoding[project work].
I had also tried using cuDevSmResourceSplit, but there was an issue with driver where driver/resource state has not been updated yet. CuDevSmResourceSplitByCount did work for me, so posting this code for reference.
```cpp
#include <cuda.h>
#include <cstdint>

static CUgreenCtx prefillCtx=nullptr,decodeCtx=nullptr;
static CUstream prefillStream=nullptr,decodeStream=nullptr;

extern "C" int create_green_contexts(int p_percent,uint64_t *p_stream_ptr,uint64_t *d_stream_ptr,int *p_sms,int *d_sms){
    cuInit(0);
    CUdevice device;
    cuDeviceGet(&device,0);
    CUdevResource input;
    cuDeviceGetDevResource(device,&input,CU_DEV_RESOURCE_TYPE_SM);

    unsigned int align=input.sm.smCoscheduledAlignment?input.sm.smCoscheduledAlignment:2;
    unsigned int min_part=input.sm.minSmPartitionSize?input.sm.minSmPartitionSize:4;

    unsigned int wanted=(input.sm.smCount*p_percent/100)/align*align;
    if(wanted<min_part) wanted=min_part;
    if(input.sm.smCount-wanted<min_part) wanted=input.sm.smCount-min_part;

    CUdevResource prefillRes,decodeRes;
    unsigned int nbGroups=1;
    CUresult res=cuDevSmResourceSplitByCount(&prefillRes,&nbGroups,&input,&decodeRes,0,wanted);
    if(res!=CUDA_SUCCESS) return (int)res;

    CUdevResourceDesc prefillDesc,decodeDesc;
    cuDevResourceGenerateDesc(&prefillDesc,&prefillRes,1);
    cuDevResourceGenerateDesc(&decodeDesc,&decodeRes,1);

    cuGreenCtxCreate(&prefillCtx,prefillDesc,device,CU_GREEN_CTX_DEFAULT_STREAM);
    cuGreenCtxCreate(&decodeCtx,decodeDesc,device,CU_GREEN_CTX_DEFAULT_STREAM);

    CUdevResource pGot,dGot;
    cuGreenCtxGetDevResource(prefillCtx,&pGot,CU_DEV_RESOURCE_TYPE_SM);
    cuGreenCtxGetDevResource(decodeCtx,&dGot,CU_DEV_RESOURCE_TYPE_SM);

    *p_sms=pGot.sm.smCount;
    *d_sms=dGot.sm.smCount;

    cuGreenCtxStreamCreate(&prefillStream,prefillCtx,CU_STREAM_NON_BLOCKING,0);
    cuGreenCtxStreamCreate(&decodeStream,decodeCtx,CU_STREAM_NON_BLOCKING,0);

    *p_stream_ptr=(uint64_t)prefillStream;
    *d_stream_ptr=(uint64_t)decodeStream;
    return 0;
}

extern "C" void destroy_green_contexts(){
    if(prefillStream) cuStreamDestroy(prefillStream);
    if(decodeStream) cuStreamDestroy(decodeStream);
    if(prefillCtx) cuGreenCtxDestroy(prefillCtx);
    if(decodeCtx) cuGreenCtxDestroy(decodeCtx);
    prefillStream=decodeStream=nullptr;
    prefillCtx=decodeCtx=nullptr;
}
```
