  ┌───────┬─────────────────────────────────────────────────────────────────────┬────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 时刻  │                                事件                                 │                                              证据来源                                              │
  ├───────┼─────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ T     │ 本进程提交的 kernel 读了非法地址 → GPU MMU Fault                    │ dmesg：Xid 31, pid=845434, name=celery … faulted @ 0x5615_65f02000，pid 就是后来落 core 的那个进程 │
  ├───────┼─────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ T     │ 该地址落在这个进程自己的堆段内（0x56155cbcd000–0x561568b44000）     │ core A 的 PT_LOAD 段                                                                               │
  ├───────┼─────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ T+72s │ CUDA runtime 把 context 标坏后，下一次 CUDA 调用返回 error 700      │ core 里 ExternalError: CUDA error(700) … gpu_info.cc:348                                           │
  ├───────┼─────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ T+72s │ Paddle 抛 EnforceNotMet → 析构里二次抛出 → std::terminate → abort() │ core B 里的两条 C++ 栈 + 你贴的 terminate called …                                                 │
  ├───────┼─────────────────────────────────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ T+72s │ SIGABRT → glog banner → core                                        │ Aborted at 1790154384 / 1790204519                                                                 │
  └───────┴─────────────────────────────────────────────────────────────────────┴────────────────────────────────────────────────────────────────────────────────────────────────────┘

  关键在于 dmesg 里的 pid 是发起那个 GPU channel 的进程，也就是谁提交的 kernel 谁背这个 fault。两次 core 的 dmesg pid 与 core 文件名 pid
  完全一致（845434、2685061），所以不是"别人先崩、本进程被动躺枪"。再加上故障地址落在它自己的 CPU 堆里（UVA 下设备 VA 不可能和 brk 堆重叠），指针就是从它自己内存里来的 → 是它自己把主机指针喂给了 kernel。

  层次关系（700 是"回声"，不是新故障）

  本进程提交 kernel，kernel 读到无效地址
     ↓        ← 这是唯一的原始事件，发生在 GPU 侧
  驱动记 Xid 31（dmesg），并把该 context 标记为损坏
     ↓
  CUDA runtime 在进程下次触到该 context 时返回 cudaErrorIllegalAddress(=700)
     ↓
  Paddle 把它包成 EnforceNotMet；此时若发生在析构里且正在 unwinding → terminate → abort

  cudaErrorIllegalAddress 的字面意思就是"设备遇到了非法内存访问"，它就是那次 MMU fault 的运行时表达，不是第二个 bug。所以严格说：700 和 abort 都只是信使，原始缺陷在"把坏指针送进
  kernel"的那段推理/加载代码里（Paddle/PaddleX 侧）。
```

## 补充证据：同一问题在 3.3.1 + cuda11.8 镜像上 3 天复现 12 次，并附 release/3.4 核查结论

  本问题在我们环境中持续复现，抓到了 2 个完整 core dump（20 GB / 2 GB），并从 core 与驱动日志里还原出完整链条。**结论先说**：这不是硬件故障，而是一条可用于定位的框架侧路径；且经逐文件对比，**这三处在 `release/3.4`
   上原样存在**。

  ### 环境

  - 镜像：`paddlepaddle/paddle:3.3.1-gpu-cuda11.8-cudnn8.9`（PaddlePaddle 3.3.1 / CUDA 11.8 build）
  - GPU：RTX 4090（sm_89）；驱动 580.105.08
  - 业务侧：Python 3.10 + `paddleocr` 的 `LayoutDetection` / `TableCellsDetection`（PP-DocLayoutV3 等公开模型），`device="gpu"`、`engine="paddle"`（Paddle Inference + PIR 新执行器）

  ### 关键证据 1：坏地址是「页对齐的主机（CPU）堆地址」，不是设备地址

  我把 core 的 `PT_LOAD` 与 `NT_FILE` 解析后，把 dmesg 里的故障地址按段还原：

  | 故障地址 | 落点 |
  |---|---|
  | `0x5615_65f02000` | 该进程自己的 rw 段内（247 MB，段基址 `0x56155cbcd000`），偏移 +154.4 MB |
  | `0x563e_fb94a000` | 该进程自己的 rw 段内（266 MB，段基址 `0x563ef31eb000`），偏移 +141.9 MB |
  | `0x563e_fc07f000` | 同一段（兄弟进程，fork 继承同基址），+149.5 MB |
  | `0x563e_fc44c000` | 同一段，+153.5 MB |

  三点判据：

  1. **12/12 条地址 `% 4096 == 0`**（页对齐）。随机内部偏移命中页对齐的概率约 1/256~1/1024，12 次全中约 10⁻²⁹ 量级 ⇒ 这些是**缓冲区基地址**。像 `cudaHostAlloc` 这类 pinned 分配就是页对齐的。
  2. **这些页能被 core dump 出来**（内核只 dump 普通 VMA，CUDA 设备映射属 `VM_IO|VM_PFNMAP|VM_DONTDUMP` 一类，不会写进 core）⇒ 它们是**普通进程内存**（段内同时含 Python 对象与模型参数名，即主程序堆区）。
  3. UVA 下主机/设备共用一套 VA 空间，驱动不可能把设备分配放在与既有堆映射重叠的地址。

  页内容也不是随机内存：两个 4 KB 页的熵为 7.31 / 7.37 bits/byte，高字节集中在 `3c/3d/be/bf`，按 float32 解码即 `0x3dd8378a≈0.105`、`0xbf0fb4c0≈-0.561` 这类正常数值 —— 形态与张量数据一致。

  ⇒ **GPU 侧（kernel 或由 GRAPHICS 引擎执行的小/中尺寸 H2D 拷贝）拿到的是一个主机缓冲基地址**，GPU 页表里没有它的映射，故 `FAULT_PDE`。

  ### 关键证据 2：崩溃发生在**模型加载 / predictor 构造期**

  - 栈 A 的 frame 0 就是 `paddle_infer::Predictor::Predictor(paddle::AnalysisConfig const&)`，即**构造 predictor 的时刻**；栈 A 的 1/2 帧是 `~AnalysisPredictor`（构造过程中旧 predictor 被析构）。
  - 出问题的进程堆中**一个模型权重参数名都没有**，但存在 `create_predictor`、`AnalysisConfig`、`inference.json`、`warmup`、`PP-DocLayout*` 等字符串 ⇒ 当时正在加载模型，且**该次加载从未成功**。
  - 栈 B 的 `TensorCopySync` 与"加载期把权重/输入送上 GPU"这一步吻合。
  - glog 在崩溃同一秒留下的最后两条日志也指向同一处：`pir interpreter is running by multi-thread mode`（新解释器创建）与 `Instruction OP id: 1, Ir OP id: <n>, pd_op.cast raises an EnforceNotMet exception`。
  - 补充：两次崩溃的输入图像（从 core 堆中提取、格式与送入模型的 PNG 一致）**互不重合**，所以不是"某张特定坏页面"触发，而是加载/预热路径上的系统性问题。

  ### 关键证据 3：现场显存已耗尽

  同一批 core 堆内存在多起真实 OOM 记录（多个不同尺寸）：

  ```

  ### 源码侧：三处希望 upstream 确认 / 修复的点（均在 `release/3.3`，`release/3.4` 同样存在）

  1. **pinned 主机内存没有流安全延迟释放。**
     `paddle/phi/core/memory/allocation/pinned_allocator.cc` 的 `FreeImpl`：
     `PADDLE_ENFORCE_GPU_SUCCESS(cudaFreeHost(allocation->ptr()));` —— 无 `cudaStreamSynchronize`、无 event 查询，**立即解映射**。
     对比设备内存走 `StreamSafeCUDAAllocator` + `CanBeFreed()`（`cudaEventQuery`）做延迟释放，二者不对称；且 `allocator_facade.cc` 里 `InitNaiveBestFitCUDAPinnedAllocator()` **从不被 `WrapStreamSafe*` 包裹**（只有
   CUDA/XPU/CustomDevice 设备分配器被包裹）。
     而 `paddle/phi/core/memory/memcpy.cc` 的 `Copy<phi::GPUPlace, phi::GPUPinnedPlace>` 是 `GpuMemcpyAsync(dst, src, num, cudaMemcpyHostToDevice, stream)`，**源是裸主机指针，不持有源、不 `Wait()`**。
     ⇒ 已入队的异步 H2D 读 + 该主机缓冲被提前 `cudaFreeHost`，就能产生"页对齐主机地址上的读故障"，与本 issue 的 `FAULT_PDE ACCESS_TYPE_VIRT_READ` 逐项吻合。

  2. **析构函数内抛异常导致不可捕获的 `std::terminate`。**
     `paddle/fluid/inference/api/analysis_predictor.cc` 中 `CreatePaddlePredictor` 以 `unique_ptr` 持有 `new AnalysisPredictor(config)`，`Init()` 失败抛出（如权重 `TensorCopySync` 的分配失败）时，`unique_ptr`
  **在构造函数内部析构** → `~AnalysisPredictor` → `memory::Release(place_)`（同样无 stream sync）。释放路径里 `CUDAAllocator::FreeImpl` 再抛异常 ⇒ 析构抛异常 ⇒ `abort()`。
     **无论根因是什么，这一条本身就是缺陷**：它把"可捕获的 CUDA error"升级成"进程硬 abort"，使上层完全失去重试与清理的机会。

  3. **PIR 多线程错误路径不做同步。**
     `paddle/fluid/framework/new_executor/pir_interpreter.cc` 中 `exception_holder_.IsCaught()` 分支：仅 `async_work_queue_->Cancel()`（取消**尚未执行**的任务）+ `async_work_queue_.reset()`，随后
  `exception_holder_.ReThrow();` —— **不 join 运行中的 worker、不 `cudaStreamSynchronize`**。于是展开路径上释放内存时，运行中/已入队的异步操作仍在引用这些缓冲。

  ### release/3.4 核查结论：这三处在 3.4.0 上原样存在

  对比 `release/3.3` @`7cc2ef095` → `release/3.4` @`74e22eafe`（`ahead_by=1145`）：

  | 文件 | 改动 | 是否影响 |
  |---|---|---|
  | `pinned_allocator.cc` | 仅 `phi::GPUPinnedPlace()`→`GPUPinnedPlace()` 等限定符/换行 | **否**：`FreeImpl` 仍立即 `cudaFreeHost` |
