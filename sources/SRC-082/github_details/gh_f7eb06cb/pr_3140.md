## 正文

## Scope

FP8 only. Compatible E4M3FN tensor/row inverse scaled checkpoints transfer exact FP8 bytes to native MLX MXFP8 matmul. `FP8MlxQuantLinear` keeps BaseQuantLinear validation; compatible layers auto-select this path on MLX. E5M2, FNUZ, E8M0, block scaled, invalid, and unaligned sources retain the dense fallback. Packed weights use about 48% less storage than main's FP16 decoded weight matrix.

**Activation dtype:** FP16 inputs yield FP16 outputs; BF16 inputs yield BF16 outputs. The unscaled dot product and checkpoint scaling run in FP32 to prevent intermediate FP16 overflow, then the final result is rounded once to the input dtype. The previous PR revision briefly returned FP32; this revision restores the model's activation dtype as requested. This also avoids propagated FP32 activations and their memory/speed cost.

## Accuracy vs independent Torch oracle

Apple M5 Ultra, MLX 0.32.2. All nine Qwen3.8-27B projection shapes at 1 and 16 rows, with FP16 and BF16 inputs, E4M3FN weights, FP32 row inverse scales and FP16 bias. The independent Torch oracle decodes FP8, divides by inverse scales, and computes matmul+bias in float64. Internal FP32 arithmetic is checked with `rtol=atol=1e-5`; all 36 cases pass. FP16 outputs pass `rtol=atol=2e-3` against the float64 oracle. For BF16, comparison to raw float64 can exceed 2e-3 solely from mandatory BF16 rounding; outputs are compared to a BF16-rounded Torch oracle and must be within one BF16 step or 2e-3. All 18 BF16 cases pass with **zero** rounding violations. Raw 2e-3 ratios above 1 are shown, not hidden. Main's dense FP8 path on `e114733d` returns FP32 for BF16 inputs because it mixes BF16 activations with FP16 weights; this is part of the separate merged-method dtype audit.
