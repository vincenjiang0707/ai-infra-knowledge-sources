## 正文

## Bug

\`Qwen2AttentionFused.__init__\` resolves \`config.rope_scaling\` to a scalar that is later passed to the awq_inference_engine kernel during decode:

\`\`\`python
```python
self.rope_scaling = config.rope_scaling
if self.rope_scaling is None:
    self.rope_scaling = 1.0
```
elif isinstance(self.rope_scaling, dict):
    self.rope_scaling = self.rope_scaling.get(\"factor\", 1.0)
\`\`\`

For e.g. \`{\"type\": \"linear\", \"factor\": 4.0}\` it stores \`4.0\` and then calls

\`\`\`python
awq_inference_engine.single_query_attention(
    ..., self.rope_theta, self.rope_scaling, True,
)
\`\`\`

## Root cause

The prefill path in the same file (\`Transformer.__init__\`, lines 343-347) precomputes the rotary frequencies with \`1.0 / rope_scale[\"factor\"]\`, and the sibling tinychat models do the same:

- \`tinychat/models/llama.py:104\` — \`self.rope_scaling = 1.0 / self.rope_scaling[\"factor\"]\`
- \`tinychat/models/falcon.py:132\` — \`self.rope_scaling = 1.0 / self.rope_scaling[\"factor\"]\`

Only Qwen2 stores the raw factor, so the decode-time per-token rotary uses a different scale than the precomputed prefill freqs. The two paths disagree, silently shifting positions during long-context generation on Qwen2 models that actually configure rope scaling.

## Fix

Apply the same \`1.0 /\` so the decode-time scalar matches the prefill convention and the LLaMA / Falcon implementations.
