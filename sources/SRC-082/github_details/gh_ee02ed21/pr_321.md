# [PR #321] fix(fused_mlp): drop extra '-8 * scales' shift on gemm path

source: https://github.com/mit-han-lab/llm-awq/pull/321
state: closed | updated: 2026-05-29T10:26:43Z
labels: 

## 正文

### Bug

In ` QuantLlamaMLP.our_llama_mlp ` (` tinychat/modules/fused_mlp.py `), the gemm path passes ` scaled_zeros - 8 * scales ` as the zero-point argument to ` gemm_forward_cuda_new `:

```python
gate_output = awq_inference_engine.gemm_forward_cuda_new(
    x,
    self.gate_proj_qweight,
    self.gate_proj_scales,
    self.gate_proj_scaled_zeros - 8 * self.gate_proj_scales,
)
```

This is inconsistent with both:

- The gemv path a few lines above, which passes ` self.gate_proj_scaled_zeros ` unmodified.
- ` WQLinear.forward ` in ` awq/quantize/qmodule.py ` (the canonical quantized linear), whose gemm call is ` gemm_forward_cuda_new(inputs, qweight, scales, scaled_zeros) ` — the trailing ` # - 8.0 * self.scales) ` comment is a leftover noting that this shift was removed.

### Root cause

` dequantize_s4_to_fp16x2 ` in ` awq/kernels/csrc/quantization_new/dequantize.cuh ` keeps the int4 weights *unsigned* in ` [0, 15] ` (see the explicit comment "Haotian: subtract {1024, 1024} instead, we do not need to map to [-8, 7]" / ` FP16_TOP_MAGIC_NUM = 0x6400 `). The gemm kernel in ` awq/kernels/csrc/quantization_new/gemm/gemm_cuda.cu ` then applies ` __hfma2(loaded, scale, zero) ` — i.e., ` raw * scale + zero `.

For this to recover the original ` (raw - zero_point) * scale `, the kernel needs ` zero == -zero_point * scale `. That is exactly what ` WQLinear.from_linear ` builds into ` scaled_zeros ` (` scaled_zeros[:, :scales.shape[1]] = -(qscales * zeros) `).

Subtracting another ` 8 * scales ` here therefore biases every dequantized weight by an extra ` -8 * scale `, so each fused MLP output is off by ` -8 * scale_sum_over_K ` per output channel whenever the gemm branch fires (` x.numel() / x.shape[-1] >= 8 `, e.g. prefill).

### Fix

Pass ` scaled_zeros ` directly, matching both the gemv branch and ` WQLinear.forward `:

```python
self.gate_proj_scaled_zeros,
...
self.up_proj_scaled_zeros,
```

The gemv path (` numel/last_dim < 8 `) already uses these tensors as-is, so behavior on small batches is unchanged; only the previously-broken gemm path on larger batches is corrected.
