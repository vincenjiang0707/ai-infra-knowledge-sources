## 正文

## Bug

`FalconAttentionFused.__init__` in \`tinychat/models/falcon.py\` constructs its prefill `RotaryEmbedding` with the default `base=10000`, ignoring the configured `rope_theta`. The decode path of the same class uses `self.rope_theta` when calling the fused kernel, so prefill and decode end up applying different rotary base frequencies for any Falcon variant whose \`config.rope_theta\` isn't 10000.

## Root cause

\`\`\`python
# __init__
self.rotary_emb = RotaryEmbedding(self.head_dim)      # <-- base defaults to 10000
self.rope_theta = args.rope_theta
self.rope_scaling = args.rope_scaling
...

# forward, prefill (seqlen > 1)
xq, xk = self.rotary_emb(xq, xk)                      # uses the default 10000 base

# forward, decode (seqlen == 1)
output = awq_inference_engine.single_query_attention(
    xq, xk, xv, self.cache_k, self.cache_v,
    None, None,
    start_pos, self.head_dim,
    self.rope_theta, self.rope_scaling, True,          # uses args.rope_theta
)
\`\`\`

`RotaryEmbedding.__init__` computes `inv_freq = 1.0 / (base ** (torch.arange(0, head_dim, 2).float() / head_dim))`, so the `base` parameter directly controls the rotary frequencies baked into `cos_cached`/`sin_cached`. With the prefill hard-coded to 10000, q/k are rotated with one set of frequencies during the context stage, and then with a different set for every subsequent decode step — silently corrupting attention as soon as generation transitions past the prompt.

The same class already reads `args.rope_theta` and threads it through the decode path, confirming that the intent was for the layer to use the configured value end-to-end.

## Fix

Pass `base=self.rope_theta` to `RotaryEmbedding` at construction time so both prefill and decode share the same rotary base:

\`\`\`diff
-        self.rotary_emb = RotaryEmbedding(self.head_dim)
         self.rope_theta = args.rope_theta
         self.rope_scaling = args.rope_scaling
+        self.rotary_emb = RotaryEmbedding(self.head_dim, base=self.rope_theta)
\`\`\`

For the common case `rope_theta == 10000` behavior is unchanged (the default already matched the hard-coded value), so this is a pure correctness fix for non-default Falcon configurations.

## Notes

- Not touching `rope_scaling`: the prefill `RotaryEmbedding` doesn't currently implement scaling at all, and wiring it up is a larger change than the scope of this PR. This PR keeps the change strictly to restoring parity on `rope_theta`.
