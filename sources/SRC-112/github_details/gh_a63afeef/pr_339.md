## Changes

### Warmup

We add the `--num-warmups n` argument to the `benchmark_serving.py` script, which takes in a positive integer `n`. When specified, the `benchmark_serving.py` script invokes this loop within the benchmark function to send the first randomly generated request `n` times to the server. This ends up being a one-line change in terms of how benchmarks are launched—now we just add the `--num-warmups` flag.

**Before:**

```bash
python3 benchmark_serving.py \
    --model "$model" \
    --backend "$backend" \
    --base-url "http://0.0.0.0:$port" \
    --dataset-name random \
    --random-input-len "$input_len" \
    --random-output-len "$output_len" \
    --random-range-ratio "$random_range_ratio" \
    --num-prompts "$num_prompts" \
    --max-concurrency "$max_concurrency" \
    --request-rate inf \
    --ignore-eos \
    --save-result \
    --percentile-metrics 'ttft,tpot,itl,e2el' \
    --result-dir "$result_dir" \
    --result-filename "$result_filename.json"
```

**After:**

```bash
# vllm & sglang benchmark_serving.py also have --num-warmup & inferencemax
# benchmark_serving closely follows vllm script
python3 benchmark_serving.py \
    --model "$model" \
    --backend "$backend" \
    --base-url "http://0.0.0.0:$port" \
    --dataset-name random \
    --random-input-len "$input_len" \
    --random-output-len "$output_len" \
    --random-range-ratio "$random_range_ratio" \
    --num-prompts "$num_prompts" \
    --num-warmups "$num_warmups" \
    --max-concurrency "$max_concurrency" \
    --request-rate inf \
    --ignore-eos \
    --save-result \
    --percentile-metrics 'ttft,tpot,itl,e2el' \
    --result-dir "$result_dir" \
    --result-filename "$result_filename.json"
```

Each benchmark run will invoke this script up to `--num-warmups=(2 * CONC)`, where `CONC` is the maximum number of concurrent requests that can be in-flight at any single point in time.

We note that this is the standard implementation as seen in SGLang and vLLM, hence InferenceMAX will be following suit with this implementation. This is important as it is our goal to remain consistent with the broader ML community.

### Code Upstream

Currently, we utilize a benchmark suite in a downstream repository, which is a fork of another repository, which is a fork of the original vLLM benchmark serving suite (which has since been refactored). We will be upstreaming the relevant code from this repository into InferenceMAX for maximum transparency.

> **Note:** Multinode runs will be upstreamed at a later day due to the fact that multinode scripts are not fully upstreamed to the InferenceMAX repository at this point.
