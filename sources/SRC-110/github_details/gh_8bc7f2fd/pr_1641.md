## 正文

## Summary

Closed-loop runs report a `p99` TTFT that is several times the server's real steady-state `p99`, because the start-up burst lands inside the measured window. Enabling `--warmup-num` did not help. This PR hands the concurrency slots from warmup over to the measured requests without draining them in between, which puts the reported percentiles on the steady-state values.

Fixes #1627

### Relation to #1547

#1547 (`startup_ramp_seconds`) targets the same underlying phenomenon -- a cohort of requests released simultaneously at the start of a phase -- but on the multi-turn path, and it addresses it by staggering the release itself. This PR does not touch multi-turn and does not supersede that discussion; it shows that on the single-turn closed-loop path the burst can be absorbed by the warmup requests that are already being sent, with no new CLI surface and no under-loaded stretch inside the measured window. Whether the same reasoning should replace the ramp for multi-turn is left to #1547.

## Root cause

A closed-loop run at concurrency `N` measures a closed queueing network with `N` circulating jobs. The quantity of interest is the stationary TTFT distribution at occupancy `N`, where the `N` in-flight requests are spread across phases — a few prefilling, most decoding.

The dispatcher started from the worst possible initial condition. `_run_phase` ended with a barrier (`await asyncio.gather(*in_flight)`), so warmup drained server occupancy back to zero, and the measured phase then released its first `N` requests within the same event-loop tick. All `N` were in the prefill phase simultaneously, so each queued behind the others' prefill:

* prefill queue depth at the start: `N`
* prefill queue depth in steady state: `N × (prefill time / whole request time)`, normally well below one

TTFT is the metric most sensitive to that difference. The collected samples are therefore a **mixture** of `N` start-up samples and `number − N` steady-state samples, while `calculate_percentiles` treats them as a single distribution. Once `N / number` exceeds 1%, `p99` is determined by the start-up samples alone.

Warmup could not fix this on its own: because of the barrier, occupancy returned to zero and the measured window re-created the same synchronised burst.

## What changed

* `ClosedLoopStrategy` dispatches warmup and measured requests through **one loop and one semaphore**, with no barrier between them. Each warmup completion releases exactly one measured request into a server that already holds `parallel - 1` requests mid-flight, so the measured portion inherits a steady-state arrival pattern from its first sample onwards.
* `BenchmarkStrategy._collect_requests()` keeps the `(request, is_warmup)` stream in order; `_partition_requests` is untouched and still used by open-loop.
* The `--duration` deadline is armed when the **first measured request is actually sent**, i.e. once it holds a concurrency slot, so warmup does not consume the timed budget. Arming on task creation would not work: creation is bounded by `max_in_flight` rather than by the semaphore, so measured tasks are queued while warmup still holds every slot and the clock would start at ~t0. With the send-based anchor the measured window begins exactly where measurement begins.
* `metrics_consumer` closes the warmup progress bar on completion count instead of on the first measured item, because warmup and measured results now interleave briefly around the hand-over.
* `run_benchmark` warns when warmup cannot cover every concurrency slot, and names the value that would.

Only the closed-loop single-turn path is touched. Open-loop and multi-turn dispatch are unchanged.

## Verification on a real endpoint

Qwen2.5-0.5B on vLLM, `--parallel 32 --number 320`, ~4k-token prompts, `--max-tokens 64`.

*Contaminated* = measured requests in the opening cohort whose TTFT exceeds the steady-state (tail) `p99`. It is used instead of a head/tail ratio because the server's baseline latency drifts between runs, while this count is normalised per run.

| `--warmup-num` | opening cohort dispatched over | contaminated | reported p99 | steady-state p99 | overstated | reported max | steady-state max |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 9 ms | 32 / 32 | 1609 ms | 384 ms | 4.19x | 1724 ms | 457 ms |
| 8 | 1555 ms | 25 / 32 | 1362 ms | 546 ms | 2.50x | 1476 ms | 556 ms |
| 32 (= `--parallel`) | 934 ms | 0 / 32 | 321 ms | 321 ms | 1.00x | 355 ms | 355 ms |
| 64 (= 2x `--parallel`) | 1207 ms | 0 / 32 | 410 ms | 416 ms | 0.99x | 430 ms | 430 ms |

Readings:

* At `--warmup-num >= --parallel` the reported `p99` equals the steady-state `p99` exactly, and so does `max`.
* The dispatch span of the opening cohort is the direct signature of the hand-over: 9 ms when every request is released at once, ~1 s once warmup releases them one at a time.
* The warning is quantitatively accurate. At `--warmup-num 8` it states that 24 measured requests are released at once alongside the warmup ones; the measured contamination is 25 of 32, i.e. the arithmetic in the warning matches reality to within one sample.
* For reference, the previous code with `--warmup-num 32` still reported `p99` 2178 ms against a steady-state 818 ms, confirming that warmup alone could not remove the burst before this change.

A residual single outlier in the `max` column at `--warmup-num == --parallel` was observed in some runs and not in others. The cause was not investigated -- one hypothesis is two warmup completions coinciding and releasing two measured requests at once -- so it is not documented as a mechanism; the docs only suggest a larger value when the `max` column matters.

### One case this does not fix: a fixed output length

`--min-tokens == --max-tokens` (plus `ignore_eos`) is the usual way to make a run reproducible, but it also removes all service-time variance, so a cohort that starts together finishes together and is re-released together. That synchronised state is a fixed point of the closed loop, so the burst repeats every cycle instead of decaying: neither warmup nor a larger `--number` helps, and the symptom is a TTFT ramp with a period of `--parallel`.

Measured on the same endpoint (`parallel=8 number=96 prompt=2000`), using the **second half** of each run so a decaying transient cannot be mistaken for the effect. Mean TTFT by within-cycle position:

| config | out tokens | mean TTFT by position (ms) | ramp |
| --- | --- | --- | --- |
| fixed 64 + `ignore_eos` | all 64 | 41 52 50 40 53 65 68 75 | **1.86x** |
| `--max-tokens 48 64` | 17 distinct, 48-64 | 49 49 60 60 64 54 44 49 | 1.00x |
| `--open-loop --rate 4`, fixed 64 | all 64 | 34 31 32 32 33 31 32 33 | 1.00x |

The lock needs both zero variance **and** the closed-loop feedback, so breaking either removes it. No code change is warranted -- a deterministic closed network genuinely has the synchronised state as its steady state, and both remedies already exist. This PR only documents it under `--min-tokens`, which is where users configure it. (`--min-tokens` alone cannot restore variance: `ignore_eos` plus a fixed `--max-tokens` pins the length regardless of the floor.)

## Behaviour changes

**`--warmup-num` no longer drains before the measured window.** Warmup requests are still excluded from every metric, but they now overlap the start of the measured portion instead of finishing in isolation. Users who already pass `--warmup-num` will see their reported `p99` drop, because it stops including the start-up burst. Runs without warmup are unaffected.

**A value below `--parallel` degrades gracefully.** It leaves part of the burst inside the measured window; the run warns and names the value that would cover every slot (`--parallel`, or `2 x --parallel` when the `max` column also matters). No auto-adjustment of the value is introduced.

**`--rate` pacing now spans the whole stream.** Inter-arrival targets are computed once over `warmup + number` requests (`total / rate`) rather than per phase. The total target time is unchanged and the existing "behind schedule dispatches immediately" handling still applies, but the measured requests' absolute targets are no longer re-anchored after warmup has drained. This makes `--rate` a single global request rate.

## Tests

`tests/perf/test_closed_loop_warmup_handoff.py` (12 cases), driven with a fake client that records server occupancy at each dispatch, plus one end-to-end case through `run_benchmark` against a mock OpenAI server:

* the first measured request dispatches while `parallel - 1` requests are still in flight, and occupancy never returns to zero mid-stream
* dispatch order, occupancy cap, and graceful degradation when warmup covers only part of the slots
* `--duration` armed on the first measured send: warmup is exempt from the cap, and the anchor is asserted to fall no earlier than the first freed slot (a `duration=0` case cannot distinguish the two anchors)
* warning text for warmup disabled / partially covering, and silence when it covers every slot
* end to end: warmup requests reach the server and stay out of the result database

Scope note: cases covering code this PR does not change were deliberately left out -- `Arguments.warmup_count` is untouched here, the semaphore cap is pre-existing, and failure/cancellation for `ClosedLoopStrategy` is already parametrized in `test_async_lifecycle.py::test_strategy_failure_cancels_in_flight_requests`.

Regressions: `pytest tests/perf` (excluding the cases that need a live endpoint) and `tests/cli/test_all.py::TestRun::test_ci_lite` pass; `pre-commit` is clean.
