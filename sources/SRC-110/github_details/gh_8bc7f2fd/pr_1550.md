## 正文

## Summary

Integrates [ScreenSpot-Pro](https://arxiv.org/abs/2504.07981) (`lmms-lab/ScreenSpot-Pro`) — a GUI grounding benchmark of 1,581 expert-annotated instructions over authentic high-resolution professional desktop screenshots (up to 6016x3384). Given an instruction, the model must output a click point locating the target UI element.

Implemented as a `VisionLanguageAdapter` reusing the standard dataset flow; no new framework mechanisms.

## Design

- **Subsets**: `reformat_subset` groups samples by the record's `group` field into the 6 paper-standard domains (`CAD`, `Creative`, `Dev`, `OS`, `Office`, `Scientific`). Counts sum to exactly 1,581 — no samples dropped.
- **Metrics**: `acc` plus `text_acc` / `icon_acc`. The `ui_type`-specific key is emitted only for applicable samples, so the stock `Mean` aggregator averages each over its own population — reproducing the reference implementation's three metrics without a custom aggregator.
- **Scoring**: strict point-in-bbox against ground truth normalized by `img_size`, matching the official protocol. The effective tolerance is the target element itself (median 57x25 px; icons 26x24 px).

## Two correctness issues found while validating

The first real-API run scored **0.0**. Both causes were genuine defects also present in the lmms-eval reference approach:

1. **First-match parsing.** The prompt states the `[0, 1]` range, so responses that restate the prompt or reason step by step had `[0, 1]` extracted as their answer. Parsing now anchors on the **last** match of each pattern.
2. **Coordinate convention.** `qwen3-vl-plus` answers on a **0–1000 grid**, not in pixels (`805/0.8056 ≈ 999` against ground truth). Normalizing by image size scored **0.0** where the thousandths reading scored **0.5625** on the identical predictions.

Coordinate handling is therefore explicit via a `coordinate_space` extra_param (`auto` / `normalized` / `thousandths` / `pixel`). `auto` infers by magnitude; the 1–1000 window is inherently ambiguous, so the convention can be pinned rather than silently guessed. Pixel-space answers are normalized against the size of the image *actually sent*, since `max_image_bytes` may downscale it (verified: 2880x1800 -> 2592x1620 at `300kb`).

## Verification

- **All 6 subsets** evaluated with `qwen3-vl-plus`, 10 samples each (60 total): overall **acc 0.5**; CAD 0.8, Creative 0.6, Dev 0.3, OS 0.4, Office 0.6, Scientific 0.3. text 0.867 >> icon 0.133 avg, matching the published difficulty profile.
- **All 60 stored scores re-derived independently** from raw predictions — every one matched, including the `ui_type` metric split. 0 unparseable predictions, 0 points out of range after mapping.
- **Dashboard rendering** confirmed via `evalscope service`: overall score, all 6 subsets, all 3 metrics, and per-sample drill-down with the base64 PNG screenshot rendering correctly. No console errors.
- `pytest tests/benchmark/test_vlm.py::TestVLMBenchmark::test_screenspot_pro_mock` and `tests/cli/test_all.py::TestRun::test_ci_lite` pass; `make lint` clean.

## Notes

- `eval_split='train'`: the ModelScope repo exposes only a `train` split (loading `test` fails).
- Docs generated via `make docs-pipeline BENCHMARK="screenspot_pro" FORCE=1`.
- Scoring precision: `extract_answer` formats the point to 4 decimals and `match_score` re-parses that string, so comparison precision is 1e-4 (~0.29 px on a 2880-wide image). Negligible against >=10 px targets, but noting it since a point within ~0.15 px of a box edge could in principle flip.
