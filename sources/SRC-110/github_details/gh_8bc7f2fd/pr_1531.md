# feat(perf): long-context prefix injection via `prefix_file` / `prefix_role`

Closes #1524

## What

Benchmarking 128K/256K-scale long contexts with **real text** was previously impossible: `random` gives fixed lengths but high-entropy meaningless tokens (prefix-cache hit rate / MTP acceptance rate unrealistic), while real instruction datasets are mostly 4K-8K tokens, so a 128K `target_input_len` filters everything out.

This PR adds prefix injection to the perf dataset pipeline: point `prefix_file` at a long text corpus, and the framework slices it to exactly `target_input_len − prompt_len` tokens, prepending it to each short prompt as a `system` (default) or `user` message — every request hits the target length while keeping real-language entropy.

```bash
evalscope perf \
  --dataset openqa \
  --tokenizer-path Qwen/Qwen2.5-0.5B-Instruct \
  --dataset-args '{"target_input_len": 8192, "prefix_file": "long_text.txt", "prefix_role": "system"}' \
  ...
```

## 👋 Review Summary
Nice work on adding real-text long-context prefix injection and centralizing the token-length convergence logic. The design is thoughtfully wired through the perf datasets and backed by solid unit and integration tests with fake tokenizers.

## 🛡️ Key Risks & Issues
- Long-context prefix combined with `input_len_mode='drop'` ends up effectively disabling the prefix: only prompts whose bare-token length already equals `target_input_len` are kept, which in turn gives a zero prefix budget, so no prefix is ever injected even when `prefix_file` is set. This makes that configuration misleading for users who expect genuine long-context behavior.
- For multi-turn ShareGPT datasets, the prefix budget is measured only against the last user turn, while earlier conversation history remains untouched. That means the total input length (history + prefix + last user turn) can significantly exceed `target_input_len` and potentially the backend’s context window. This is more of a semantic/operational risk than a bug, but it would be good to clarify or enforce bounds so perf runs don’t accidentally push requests beyond supported limits.
- The new `converge_to_token_len` helper does repeated decode/re-encode loops over long token sequences for both random prompts and prefixes. At large `target_input_len` values and high request counts, this can become a noticeable CPU cost on the driver side, and the drift-warning path in `fit_prefix_to_budget` may produce a lot of log output if a real tokenizer fails to converge, which could impact perf runs.

## 🧪 Verification Advice
- Add a targeted test that exercises `prefix_file` together with `input_len_mode='drop'` and `target_input_len`, making the current behavior explicit and providing a guard rail if you decide to change semantics (e.g., by rejecting this combination or warning at construction).
- Extend prefix-injection integration tests beyond `line_by_line`/`share_gpt_zh` to include `openqa` and `longalpaca`, using small local fixtures and a fake tokenizer. This will help ensure `prepare_messages` and `apply_prefix_to_messages` behave as expected across all wired datasets.
- Consider a lightweight perf/CLI smoke test that uses `prefix_file` through `run_perf_benchmark` (with a fake tokenizer and tiny dataset) to validate the end-to-end wiring from CLI `dataset_args` to the plugins.

## 💡 Thoughts & Suggestions
- It may be worth tightening or documenting the semantics around `prefix_file` + `input_len_mode='drop'` so users don’t accidentally configure a long prefix that never applies. A schema-level validator or constructor warning would make intent clearer.
- For multi-turn datasets like ShareGPT, consider whether `target_input_len` should represent the total request length (including history) or just the final turn. If the former, introducing an optional cap on overall message tokens or documenting the current behavior explicitly would help avoid context overruns.
- If prefix-based long-context perf runs become common at very high token counts, you might want to monitor and, if necessary, optimize `converge_to_token_len` (e.g., by reducing retries when drift is small or caching converged slices for repeated budgets) to keep the driver overhead under control.
