## #1546 — GPQA-Diamond misjudged when the model leaves its reasoning in the output

**Two independent causes.**

1. `parse_answers` allowed its capture group to match whitespace only. When a model restated the required format (`ANSWER: [LETTER]`) before answering, that echo matched first with an empty capture and the real answer was discarded. The line-anchored pattern also misses an answer that directly follows an unpaired `</think>` tag. The capture group now has to start with an alphanumeric character.

2. More importantly, **configured filters never reached multi-choice extraction.** `filter_prediction()` runs the filter ensemble and passes the filtered text into `extract_answer(prediction, task_state)`, but `MultiChoiceAdapter.extract_answer` (and the mmmu / a_okvqa / ai2d / cmmu / agieval adapters) dropped the `prediction` argument and let `parse_answers` re-read `task_state.output.completion`. A user who set `filters={'remove_until': '</think>'}` to strip a reasoning block still got the raw completion parsed, so there was no way to work around bad extraction. `parse_answers` / `parse_answers_zh` now accept an optional `completion` argument and those callers pass the filtered prediction.

This is not a regression: both mechanisms landed in the same v1.0 refactor (#739) and were never wired together. `parse_answers(state)` follows the upstream inspect_ai style where scorers read `TaskState` directly and no filter layer exists, while `filters` follows the lm-eval-harness style of operating on prediction strings. `extract_answer` is the seam where they should meet.

**Verification** — 20 gpqa_diamond + 40 iquiz samples (iquiz exercises the Chinese `parse_answers_zh` path), re-scored from identical cached predictions via `use_cache` + `rerun_review`:

| | gpqa | iquiz IQ | iquiz EQ |
| --- | --- | --- | --- |
| before | 0.75 | 1.0 | 0.75 |
| after | 0.75 | 1.0 | 0.75 |

60/60 samples identical per-sample (`extracted_prediction` and `value`), so default runs are unaffected. No benchmark ships default `filters`; they only ever come from user `dataset_args`.

Counter-check that filters are genuinely wired now — same cached predictions with a deliberately non-matching `regex` filter:

| | gpqa mean_acc |
| --- | --- |
| before | 0.75 (filter silently ignored) |
| after | 0.0 (filter respected) |

## #1543 — ifeval scores differ for identical responses

Pinning `DetectorFactory.seed` alone was not enough. `langdetect.detect()` builds its process-global detector factory lazily and **without a lock**, so concurrent first calls race and some threads detect against language profiles that are still half-loaded. That is exactly the shape of a real evaluation: cold start plus parallel review. The factory is now built once, under a lock, before any detection — ifeval does it on first use via double-checked locking, multi-if at import time while still single-threaded.

**Verification** — 128 checks over 16 threads against a cold factory, for one identical response:

| | result set |
| --- | --- |
| before any fix | `{False, True}` |
| seed pinned only | `{False, True}` |
| seed + locked warm-up | `{True}` |

The regression test reproduces the race by dropping the private global factory and fails on both earlier variants. `evalscope eval --datasets ifeval --limit 5 --repeats 3` is now consistent across repeats.

## #1542 — Tau-bench docs said pass@k while the default reports pass^k

`mean_and_pass_hat_k` computes `C(c, k) / C(n, k)`, the probability that *all* k attempts succeed, which is the `pass^k` metric defined by the tau-bench paper. The default aggregation is therefore correct and the wording was wrong. The descriptions of `tau_bench`, `tau2_bench` and `tau3_bench` now say `pass^k`, spell out the difference from `pass@k`, and point at `mean_and_pass_at_k` for users who want the latter. Benchmark pages and `_meta` caches were regenerated through the `benchmark-info` pipeline; the two hand-written `third_party/tau3_bench.md` pages were updated directly.

`tau3_bench` also could not be regenerated at all: its adapter resolved the dataset in `__init__`, which crashes with `AttributeError: 'NoneType' object has no attribute 'dataset_hub'` when the docs pipeline instantiates adapters without a task config. Dataset preparation is now skipped when there is no task config.

## #1541 — LiveCodeBench did not send the official system prompt

The system messages defined in `live_code_bench/prompts.py` were never used as a system message, so EvalScope sent only a user message while the official `lcb_runner` sends system + user. `SYSTEM_MESSAGE_GENERIC` is now registered as the benchmark system prompt.

**⚠️ Behaviour change:** LiveCodeBench scores are no longer directly comparable with earlier EvalScope runs. Users who need the previous behaviour can set `dataset_args={'live_code_bench': {'system_prompt': None}}`.

Verified on a real `release_v1` run that the request really carries `role=system` followed by `role=user`, and that evaluation still completes (8/8 on those samples, with and without the system prompt — too small a sample to quantify the score delta reported in the issue).

## Deliberately not in this PR

- **Unpaired `</think>` is still not stripped automatically.** `parse_content_with_reasoning` only handles paired tags, while thinking models prefill `<think>` via their chat template and emit only the closing tag. Rather than changing what every benchmark records as `prediction`, the FAQ now documents that limit and recommends enabling a reasoning parser on the inference engine, configuring `remove_until`, or using `judge_strategy=llm_recall`. Also corrected: the FAQ previously claimed `<think>...</think>` is handled automatically without qualification.
- **`_fallback_parse_answer` remains unconstrained.** It scans the whole text for the last uppercase letter and returns it without validating against the available choices, so `ANSWER: [B] because XYZ` still yields `Z`. Left for a follow-up because tightening it lowers scores for samples that currently pass by accident.
