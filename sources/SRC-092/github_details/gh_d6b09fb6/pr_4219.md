# [PR #4219] [CI] Stabilize HP TCP lane-distribution flake

source: https://github.com/kvcache-ai/Mooncake/pull/4219
state: open | updated: 2026-09-24T10:59:43Z
labels: run-ci, Transfer Engine

## 正文

Fixes #4080.

`InterleavedPeersUseEveryConfiguredLane/1` (sliced read) flakes on contended CI when a recycled RPC port hits a stale process-wide pooled connection. The cited failure fails at `submitTransferTasks(...).ok()` (before the session-count check) and shows the same RPC port reused between the WRITE and sliced-READ cases.

- retry `getRemoteCached` once on `RpcServiceError` after `openRemote`
- print submit status on failure so the next flake is diagnosable

Keeps the strict per-peer lane/session assertion from #3987 (no relaxation).

Test-only.

### jacklin78911-collab · 2026-09-22

Thanks for the fix. I would keep the metadata-query retry and the submit-status diagnostic, but preserve the strict lane-count assertion.

The [failing CI job cited by #4080](https://github.com/kvcache-ai/Mooncake/actions/runs/34746572253/job/103695672351) fails at `submitTransferTasks(batch, {request}).ok()` (line 893), before reaching the session-count check. It also shows RPC port 15358 reused between the WRITE and sliced-READ cases. That is consistent with the stale pooled-connection explanation, although the old assertion does not print the error needed to confirm it. This log does not establish a lane-utilization flake.

At `a7f239a`, lane selection in `planTask()` is deterministic: with two rails and four lanes, each READ submits two slices, and the per-peer sequence alternates between lane pairs {0, 1} and {2, 3}. The test waits for every request to complete before submitting the next one. Scheduling delays alone therefore do not explain skipping a selected lane.

This assertion was added in #3987 to catch interleaved requests pinning each peer to one lane per rail. Allowing 1–4 sessions would let that original sliced-READ regression pass with only two sessions per peer.

Could we drop the assertion relaxation and update the description to match the observed submission failure? If there is a separate failure at the session-count assertion, please include that log so we can address its cause while retaining the lane-distribution coverage.
