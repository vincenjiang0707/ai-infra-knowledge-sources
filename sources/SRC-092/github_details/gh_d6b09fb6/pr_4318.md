## Description

With only SHM enabled, `allocateLocalMemory(&ptr, size)` followed by `registerLocalMemory(ptr, size)` succeeds, but a peer's READ/WRITE fails because the buffer is never advertised for SHM. The basic allocation overload discards its temporary `MemoryOptions`, and basic registration supplies fresh options without the backing path. The native Python basic APIs have the same failure.

When no explicit path is provided, recover it from SHM's existing allocation map under its existing mutex. Explicit paths keep their behavior; unrelated allocations remain unregistered for SHM. This changes only registration, with no new state or transfer-path mechanism.

This follows #4250: allocation now succeeds, but the basic registration path still loses the backing name. The regression covers scalar/vector registration and READ/WRITE payloads between two SHM-only engines. It is separate from #3581's remote relocation-cache issue.

### he-yufeng · 2026-09-24 · COMMENTED

Went through this line by line and ran it locally.

Mechanism checks out. `createSharedMemory` records `addr -> path` under `shm_path_mutex_`, and `freeLocalMemory` erases the entry under the same mutex, so a recovered path cannot outlive the allocation it names; an address reused by a later non-SHM allocation finds no entry. The lookup only fires when `options.shm_path` is empty, so explicit paths behave exactly as before, and a miss keeps the old silent no-advertise outcome instead of inventing a registration. Keying on the exact base pointer also means a registration at an interior offset does not accidentally adopt the pool's path. The allocation map and the registration descriptor stay separate: `removeMemoryBuffer` only clears `desc.shm_path`, which is right, since the map tracks allocation ownership.

Local verification (container `mc-dev:local`, `USE_TENT=ON`, built `tent_local_memory_lifecycle_test`): with this patch all 5 tests pass, including the new READ + WRITE round trip. Reverting just `shm_transport.cpp` to main makes the new test fail as expected, since with only SHM enabled the unadvertised buffer leaves `transferSync` no usable transport. So the test is a true red-to-green repro of the reported gap.

One thing I confirmed is consistent rather than a new hole: registering a strict prefix of an SHM allocation (same base address, shorter length) now advertises the object's path, and peer-side offset arithmetic bounds what actually gets touched, same as when a caller passes the path explicitly. No behavior change needed there.

Nice follow-through on #4250. Leaving this as a comment per my review habit; the change itself LGTM.
