## Description

`NvlinkTransport` sends transfers to the wrong address when a registered GPU buffer does not start at the beginning of its `cudaMalloc` allocation. Only the `cudaIpc*` path is affected. It is used when `MC_USE_NVLINK_IPC` is set or the GPUs lack fabric handle support.

The IPC branch of `registerLocalMemory` publishes `desc.addr = addr` with the handle from `cudaIpcGetMemHandle(addr)`. On the peer, `cudaIpcOpenMemHandle` returns the base of the whole allocation, and `relocateSharedMemoryAddress` computes `dest - entry.addr + shm_addr`. So a buffer that starts `N` bytes into its allocation gets every transfer `N` bytes early. Writes land on whatever sits at the start of the allocation, and reads return the wrong data. PyTorch's caching allocator places tensors inside larger segments like this.

`HipTransport` has the same bug and gets the same fix in #4340. We found it there, through weight corruption in same-node SGLang prefill/decode disaggregation on MI355X.

**Fix.** `registerLocalMemory` looks up the containing allocation with `cuPointerGetAttribute` (`RANGE_START_ADDR`/`RANGE_SIZE`). `cuMemGetAddressRange` can fail unless the allocation's context is current on the calling thread. On a B200 with CUDA 13.0 it returned `CUDA_ERROR_INVALID_CONTEXT` on a thread with no current context, and `CUDA_ERROR_NOT_FOUND` with a context of another device current. SUPA keeps `cuMemGetAddressRange`, because `supa.h` has no alias for the range start attribute. It exports the handle from the allocation base and appends the buffer's offset to the handle in `shm_name` when the offset is non-zero. It rejects a range that runs past the end of its allocation. The peer stores the offset with the opened mapping and adds it when relocating.

`desc.addr`/`desc.length` still describe the registered buffer, so the published buffer boundaries and `unregisterLocalMemory(addr)` are unchanged. As before, the peer opens the handle once per registered buffer. CUDA refcounts repeated opens of one handle in a context, and the test puts three buffers in one allocation.

**Compatibility.**
- Buffers at offset 0 publish the same 64-byte handle as before, so they work between old and new peers.
- For other buffers a new exporter sends 72 bytes: the handle plus a host-order `uint64` offset (144 hex characters in `shm_name` instead of 128). An old importer rejects that with "Mismatched NVLink data transfer method", so the transfer fails instead of corrupting memory.
- An old exporter still sends 64 bytes for those buffers, and a new importer relocates them the old, wrong way. Both sides need this change.

`MusaTransport` runs this same code through `GpuIpcTransportPolicy`, so it changes too, and `musa.h` gets the `CU_POINTER_ATTRIBUTE_RANGE_START_ADDR` alias it needs. I have not built or tested it on MUSA.

The fabric branch of `registerLocalMemory` still calls `cuMemGetAddressRange` directly, so it has the same context requirement. I left it alone.

## How Has This Been Tested?

`nvlink_transport_test` gets `NvlinkIpcTest.TransfersHitBuffersInsideLargerAllocation`, registered with CTest as `nvlink_ipc_test` so it runs without the metadata server the other tests there need. It sets `MC_USE_NVLINK_IPC`, so it covers the `cudaIpc*` path. The destination runs in a second process (the test binary re-executed), since transfers to the process's own segment use `LOCAL_SEGMENT_ID`, which bypasses relocation. It registers three buffers in one zeroed 4 MiB allocation, at offsets 0, 1 MiB + 512 and 2 MiB + 4 KiB. The source writes the first buffer, writes the second one twice (the second write takes the cached-mapping path) and reads the third. The test checks the data that was read and every byte of the destination allocation. The source buffer is registered from a fresh thread, on a second GPU when one has peer access to the first, and ranges past the end of its allocation must be rejected, including one whose length wraps around.

**Test commands:**
```bash
cmake .. -DUSE_CUDA=ON -DUSE_MNNVL=ON -DBUILD_UNIT_TESTS=ON \
    -DUSE_ETCD=OFF -DWITH_STORE=OFF -DWITH_STORE_RUST=OFF
make -j nvlink_transport_test
ctest -R '^nvlink_ipc_test$' --output-on-failure
```

**Test results** on 2× B200 (source buffer on the second GPU), CUDA 13.0, driver 595.91:

| | `NvlinkIpcTest.TransfersHitBuffersInsideLargerAllocation` |
|---|---|
| this PR | pass |
| this PR, `nvlink_transport.{cpp,h}` reverted | fail: the past-end ranges are accepted, the read returns none of the buffer's data, and the second buffer's writes land at byte 0 of the allocation |
