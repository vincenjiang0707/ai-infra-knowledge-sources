## Description

This PR integrates the managed weight metadata model introduced by #4116 into
Mooncake Store's Master and HA paths. It is the second implementation step for 
revision-level model-weight management in Mooncake Store.

The PR:

- publishes manifest-backed weight revisions through `MasterService` and the
  Store RPC layer;
- fences revision access with leases so readers and destructive lifecycle
  operations are coordinated;
- replicates weight metadata mutations through the existing operation log;
- includes weight metadata in Master snapshots and restores it on standby and
  hot-standby nodes; and
- adds focused coverage for publication, leases, operation-log replay,
  snapshots, standby restoration, and HA behavior.

This PR covers the control-plane integration and HA durability of managed
weight revisions. Higher-level residency migration, reconciliation, and Python
WeightStore workflows remain in follow-up PRs.

RFC: [#4017](https://github.com/kvcache-ai/Mooncake/issues/4017).

### Bo-Vincent · 2026-09-24

> Thanks for the latest updates. The batch snapshot and lease replay changes make the HA path much clearer. I have two points I would like to clarify before considering this ready.
> 
> 1. Revision lease and payload lifecycle
>    Could you clarify where the revision lease is enforced for destructive operations on the underlying payload objects?
>    The new lease is maintained by `WeightStoreManager`, while the existing object removal paths appear to continue checking the object-level lease. For example, `Remove`/batch removal and eviction paths seem to operate on `ObjectMetadata` without an explicit revision-lease check.
>    Is the intended contract that callers must perform this coordination before invoking those paths, or is there another managed-group integration point that I have missed? It would be helpful to have either:
>    
>    * a test showing that an active revision lease prevents removal/eviction of its payload group; or
>    * a short explanation of where this protection is enforced.
> 2. Store RPC exposure
>    The PR description says that the managed revision APIs are published through the Store RPC layer. In the current diff, I can find the `MasterService` methods and the HA plumbing, but I do not see corresponding `WrappedMasterService` methods or RPC handler registrations for the import, lookup, and lease APIs. Is RPC exposure intentionally deferred to a follow-up PR?
> 
> These may be intentional staging decisions, so I would appreciate clarification on the expected boundary for this PR.

Both points reflect the intended staging boundary, but the PR description overstates what is included.
1. Revision leases: This PR implements lease acquisition, renewal, release, and HA replication/recovery. It does not yet connect revision leases to the underlying payload removal or eviction paths. That enforcement belongs to the follow-up managed-group lifecycle work, where generic removal/eviction will skip managed groups and destructive weight operations will check revision leases. The intended contract is server-side enforcement, not caller-side coordination.
2. RPC exposure: This PR adds the internal MasterService methods, but the corresponding WrappedMasterService methods and RPC registrations are deferred to a follow-up PR.
I’ll update the PR description and clarify the delivery status in the design document so they distinguish the functionality implemented here from the follow-up work. This PR’s scope is the internal Master management primitives and HA durability of weight metadata and revision leases.
