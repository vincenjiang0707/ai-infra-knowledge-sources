# [PR #3665] [Store] Reuse an in-process master for tests and evaluation

## 正文

## Description

Promote the existing test-only `InProcMaster` to a reusable `EmbeddedMaster` owned by `RealClient`, so in-process tests and local evaluation can exercise Store Put/Get without launching `mooncake_master`. This is opt-in test/evaluation plumbing, not an additional client hosting or deployment mode. In an application using the embedded client, the application, client and master share one process. Existing multi-node/HA deployments continue to use a dedicated master.

In embedded mode, the external `master_server_addr` argument is ignored and each client owns an independent master.

The opt-in is `enable_embedded_master=True` in Python setup, `"enable_embedded_master": true` in a setup dictionary, or `MOONCAKE_ENABLE_EMBEDDED_MASTER=true`. Missing metadata defaults to `P2PHANDSHAKE` only for the embedded-master path. There is no new standalone-service or CLI deployment mode.

Review fixes:
- Bind the embedded RPC, admin and optional HTTP metadata listeners to `127.0.0.1`. Honor the metadata server's existing host argument, allocate automatic ports by binding port zero, and clean up listeners after failed startup. Preserve the last bound addresses after Stop for same-port restart.
- Preserve setup calls that reuse an initialized TransferEngine without repeating its metadata connection string, including HTTP/P2PHANDSHAKE routing semantics in classic and TENT builds. An empty metadata address is still rejected when a new engine is needed.
- Merge current `main`, preserving the current allocation paths, Python GIL release, CI structure and non-RDMA build guards.
- Add runtime regressions for listener scope, concurrent startup, failed-start cleanup/retry, same-port restart, default-address independence and TransferEngine reuse with distinct logical/transport names. Run metadata-reuse regressions under TENT as well. Keep wheel E2E coverage before any external master starts.

I think deployment complexity and maintenance cost are affected by two dimensions: the number of components that need to be deployed, and the number of deployment modes that users need to choose from.

One example is the client side. After we introduced three deployment options — embedded, real client, and standalone service — we received quite a few questions for a long time about which mode to use, what the differences were, and how each mode should be deployed.

From that perspective, adding another mode may actually increase the overall deployment complexity. At the same time, the scenarios where this new mode would be useful seem relatively limited. Given that, do we think the additional deployment mode is necessary?

This is not a fourth client hosting mode.

The existing three options (embedded client, mooncake_store_service, mooncake_client) are still how the client is hosted. enable_standalone only changes whether master is an external mooncake_master process or is started in-process (EmbeddedMaster). The flag is opt-in on top of those same three client paths; it does not add a new way to run the client.

The intended use is single-process evaluation and embedding: a notebook, a unit/e2e test, or a library that wants Put/Get without launching mooncake_master (and without a metadata service, via P2PHANDSHAKE). Multi-node and HA still require a dedicated master. Linux CI runs this path in test-wheel-ubuntu and asserts that no mooncake_master process is present.

On naming: in the current docs, “standalone” already means the store service / real-client process. Reusing it here for “no external master” is confusing. I can rename the flag and docs to something like enable_embedded_master / “in-process master” if that is preferred.

### Icedcoco · 2026-09-16

Thanks for narrowing the scope to in-process testing and evaluation. I reviewed the latest revision and noticed two points that I’d like to discuss:

1. Listener scope: In EmbeddedMaster::Start(), the RPC server binds to 0.0.0.0, and MasterAdminServer also defaults to all interfaces. This exposes administrative endpoints, including /api/v1/remove_all, beyond the local process’s loopback connection. Since the intended use is local testing and evaluation, could we bind both listeners to 127.0.0.1 and add a check for this?

2. Compatibility when reusing a TransferEngine: The new check in RealClient::setup_internal() rejects an empty metadata_server whenever embedded master is disabled. However, Client::Create() skips TransferEngine initialization when an existing engine is supplied. From the code, this appears to reject previously valid setup calls that reuse an initialized engine without supplying the metadata connection string again. Could we preserve that path and add a regression test?

The new E2E tests passed in CI, which is useful evidence for the main path. The two cases above do not appear to be covered yet; these observations are from code review rather than a local runtime reproduction.

### stmatengss · 2026-09-24

Addressed in 49c2a59a05dbffa34c63f83cb0f5707f983db842, including the merge with current `main` (056f67a5). GitHub now reports `MERGEABLE`.

For the listener-scope comment, EmbeddedMaster's RPC and admin listeners now bind to `127.0.0.1`. The optional HTTP metadata server now honors its existing host argument as well. The new `embedded_master_test` checks actual loopback connections, verifies that the same ports remain available on a non-loopback interface, and exercises cleanup/retry after each listener fails to bind.

For TransferEngine compatibility, empty metadata is accepted when an initialized engine is supplied and embedded-master mode is disabled. The regression initializes the caller-owned TCP engine separately, checks that its endpoint/metadata state is preserved, and exercises Put/Get through it. Setup without either metadata or an existing engine remains rejected.

The PR title and description now reflect the existing narrowed scope: `enable_embedded_master` is opt-in in-process test/evaluation plumbing, with the embedded application client and master sharing one process. It adds no new client hosting/CLI mode and does not replace dedicated-master deployment guidance.
