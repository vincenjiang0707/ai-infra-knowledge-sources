## Description
A Redis HA cluster could already elect a leader, but the batch OpLog could not follow it. OrderedOpLogWriter and the standby reader talk to a HaKvBackend: one compare-and-swap transaction per batch, then a lexicographic range to catch up. Only the etcd backend implemented that contract, so --enable_oplog=true with ha_backend_type=redis was rejected at startup, and a cluster that already ran Redis still needed a second etcd just to store acknowledged batches. Leadership and the log are separate; this change gives the log a Redis implementation and leaves snapshots on etcd.

What changes

RedisHaKvBackend implements the existing KV contract. The writer, the standby reader, and the applier are unchanged. CreateHaKvBackend is the only place that opens the backend, and the master writer, ClaimProducerView, and the standby follower all go through it. etcd still takes the etcd branch. k8s is rejected. A build without STORE_USE_REDIS or STORE_USE_ETCD returns UNAVAILABLE_IN_CURRENT_MODE from the factory, so the no-backend stub that aborts the process is never called.

Logical keys stay /oplog/{cluster}/producer_view, durable_prefix, and batches/{id}. Redis stores the bytes at mooncake-store/{cluster}/oplog/... and orders those logical keys in the ZSET mooncake-store/{tag}/oplog-index. The hash tag puts the index and the records on one slot, so the Lua script is valid on Redis Cluster. The connection is the backend's own; it is not the connection the leader renew thread uses.

One acknowledged batch is one EVAL. The script checks that producer_view equals the claimed view and durable_prefix equals the expected prefix, then writes the batch record and advances the prefix. A failed compare returns ETCD_TRANSACTION_FAIL. A reply that never comes back resets the connection and returns ETCD_OPERATION_ERROR; the existing read-back path treats that as ambiguous and reconciles. kCreateRevisionEquals returns INVALID_PARAMS before any command is sent. Redis has no create revision, and the snapshot maintenance lease still needs one.

Splitting the log from the snapshot leaves two races the commit of a batch already had, and the Redis mapping has to preserve them:

A range or a delete is [begin, end). limit 0 means the whole interval; a Redis COUNT of 0 would return nothing. The next page starts at last_key + '\0'. Bounds that are empty, a single NUL, or begin > end are rejected, and one transaction may not touch two cluster ids.

A dropped connection can hide a script that did commit. The backend does not retry that call. The caller reads the prefix back and continues from what Redis actually stored.

Behavior change: --enable_oplog on Redis. With STORE_USE_REDIS and a connstring, ha_backend_type=redis now creates the batch writer and the standby follows the same Redis. Before, that combination fataled, and an empty connstring still skips the writer. enable_oplog_snapshot and snapshot restore still require ha_backend_type=etcd. Redis has to run AOF with appendfsync everysec or always; a restart without it can drop batches the master has already acknowledged.

Smaller changes:

HaBackendSupportsOpLog is one switch on HABackendType. Adding a backend is that case plus a factory branch.
The shard scan copies buffer descriptors only for replicas on the segments being re-adopted. The Redis range copies values only for keys inside the requested interval.
NoF placeholder allocators stay out of this path. Nothing in the Redis backend adopts them.
The deployment guide states that the same Redis holds leader election and the batch log, and that clients still use the redis:// master address. The restore-side log is unchanged.
CreateRevisionCompareIsRejected always runs. The four integration tests run only when the binary is built with STORE_USE_REDIS and --redis_endpoint is set; gtest_main does not parse gflags, so this target supplies its own main.

## 评论 (1)

### Icedcoco · 2026-09-24

Thanks for working on Redis-backed OpLog support. The overall direction makes sense: it removes the extra etcd dependency for deployments that already use Redis for HA leadership, while reusing the existing HaKvBackend contract.

I have a few concerns that I think should be discussed before merging.

1. Redis persistence semantics need to be defined more strictly

    The current documentation recommends either appendfsync everysec or always. I do not think everysec is safe for this OpLog use case. It can acknowledge a batch and then lose only part of the recent history after a crash. That is more dangerous than losing the entire Redis dataset, because a partially missing OpLog can leave the standby with an inconsistent state and make promotion unsafe.
    
    Could we choose one of these two explicit models?
    
    - No durability guarantee: Redis is treated as an ephemeral coordination/log store. If Redis loses its data, the system detects the empty or invalid OpLog namespace and rebuilds the whole cluster from zero.
    - Strict durability: every acknowledged OpLog write is synchronously persisted, using appendfsync always or an equivalent mechanism. A single acknowledged batch must not disappear independently.
    
    I would avoid a middle ground where only part of the acknowledged OpLog may be lost. The current implementation treats a successful transaction as committed, so the persistence guarantee needs to match that assumption.

2. The Redis failure/recovery behavior should be tested explicitly

    The current tests cover the KV mapping and Lua transaction behavior, but they do not appear to cover:
    
    - primary writing batches and standby applying them through Redis;
    - leader promotion followed by continued OpLog writes;
    - a connection failure after Redis has committed the Lua script;
    - Redis restart with either a completely empty dataset or a partially missing dataset.
    
    A focused HA-level test would help establish the intended recovery semantics.

3. The PR contains unrelated repository changes

    Please also remove the unrelated deletion of the extern/pybind11 submodule and the committed Vim swap file:
    
    - extern/pybind11
    - mooncake-store/src/ha/kv/.ha_kv_backend_factory.cpp.swp
    
    The submodule deletion currently causes a normal non-SKBUILD CMake configure to fail because the top-level build unconditionally calls add_subdirectory(extern/pybind11).

4. Redis Cluster support

    The PR description mentions Redis Cluster hash-slot compatibility. The implementation uses the regular hiredis connection API, so it is worth clarifying whether Redis Cluster is actually supported. Hash tags ensure that the keys share a slot, but the client still needs to connect to the node that owns that slot or use a cluster-aware client/proxy.

The feature itself is useful, but I would prefer to settle the durability model and recovery behavior before merging. Once those semantics are explicit and covered by tests, the Redis-backed OpLog design should be much easier to review and operate safely.
