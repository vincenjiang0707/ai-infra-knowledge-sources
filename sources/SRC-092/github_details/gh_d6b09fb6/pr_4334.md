# [PR #4334] [Store] Avoid racing with detached hot-cache fills during key scans

## Description

Concurrent Store hot-cache fills can race with key scans. `GetFreeBlock()` detaches a zero-reader block and gives its caller exclusive ownership; `SubmitPutTask()` then assigns `key_` outside the cache mutex. However, `hasActiveBlockForKeyLocked()` and the removed-reader path in `ReleaseHotKey()` scan every allocated block and compare `key_` before checking its reference count. They can read a string while the fill owner replaces its storage, despite holding the cache mutex.

Check the existing reference count first in both scans. Under the cache mutex, a positive count identifies a reader-held block whose key is stable; detached fill blocks are skipped. The fix adds no lock or state.

#2376 addresses a missing release in the client size-mismatch path; this fixes the independent concurrent reads inside the cache.

## How Has This Been Tested?

- Built the new regression with the real current cache and SHM allocation sources using GCC ThreadSanitizer. Original code: exit 66 with six data-race reports, including both affected scans. Fixed code: exit 0, no race reports.
- The regression also verifies that removed reader-held blocks cannot be reused before release, and that the detached fill can still be published afterwards. Detecting the original race requires a sanitizer build; ordinary assertions alone do not detect it.
- Full CPU Store build from `16b7ba3c` and both CTest targets below pass:

```bash
cmake --build build --target local_hot_cache_concurrency_test client_local_hot_cache_test -j4
ctest --test-dir build --output-on-failure --no-tests=error \
  -R '^(local_hot_cache_concurrency_test|client_local_hot_cache_test)$'
```
