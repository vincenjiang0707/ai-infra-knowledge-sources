## Description

Add a CUDA-only completion barrier that lets a captured graph wait for a Store `TransferFuture` or a background `Client::BatchGet`. The barrier uses a mapped pinned host flag and `cuStreamWaitValue32`; it can be rearmed after each replay. `StartBatchGetWithCudaBarrier` retains the existing replica selection and read lease path. A failed read still releases the graph wait, and callers must discard graph output unless `barrier->wait()` returns `ErrorCode::OK`.

This is an incremental piece of #3610. It does not route the user's stream through Store transports, add `RealClient`/`PyClient` `*_on_stream` APIs, or cover Ascend/ADXL.

## Review (1)

### he-yufeng · 2026-09-21 · COMMENTED

Went through the barrier mechanism and the CUDA driver call semantics; this is well put together.

The memory ordering holds: the worker writes result_ before the release-store of the mapped flag, and result() pairs it with an acquire-load, so a flag==1 read always sees a valid result_. The 0->1 flag lifecycle across rearm is also right: start() joins the previous worker only after result() reports ready, resets to 0 before spawning, and every exit path of the worker (success, operation error, exception, even thread-creation failure) still lands on flag=1, so a graph wait can never be stranded by a failed read.

The tests are the convincing part. CudaGraphWaitsForTransferFutureOnReplay has the negative control that matters (stream stays cudaErrorNotReady and result() stays empty until the future completes, then unblocks), covers OK/OK/FAIL across rearms, and BatchGetSignalsCudaGraphAfterGpuRead proves the real BatchGet path into a registered CUDA buffer, including the missing-key release. The failed-read contract (wait releases, caller checks wait() before trusting graph output) is documented on the class and exercised in the test.

One small observation, not a request: start() returns false both for an empty operation and for "previous operation still in flight". The header contract implies the second meaning, but a one-line note there would save a future caller from treating a busy barrier as a programming error.
