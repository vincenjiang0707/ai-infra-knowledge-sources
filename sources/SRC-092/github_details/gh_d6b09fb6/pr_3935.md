## Description

Adds Intel XPU (oneAPI Level Zero) support to the Transfer Engine, so XPU device
memory can be registered and moved over the existing RDMA (dma_buf) and TCP
transports. XPU reuses those transports through a cuda-alike shim layer rather
than adding a new transport.

Intel XPUs use Level Zero, a different stack from CUDA/HIP/MUSA. This follows the
same `gpu_vendor/` + `cuda_alike.h` seam the MUSA and MACA ports already use, so
no transport or engine code needed restructuring:

- `USE_XPU` cmake option with Level Zero auto-detection
- `gpu_vendor/xpu.h` / `xpu.cpp` — cuda-alike surface over Level Zero
  (ZeRuntime singleton, device alloc/free, H2D/D2H memcpy, pointer attributes,
  PCI bus id, allocation-base query, dma_buf export)
- `USE_XPU` added to the existing GPU-vendor guards in `cuda_alike.h`,
  `memory_location.cpp`, `topology.cpp` and the TCP staging path
- `rdma_context.cpp` — dma_buf export for XPU device memory
- `scripts/build_xpu.sh` for conda-based XPU builds

Scope note: this is the first phase of Intel XPU support — transports and memory
registration only. The MoE EP layer is a separate, stacked PR. The full phased
design is in the linked RFC issue rather than a file in the tree.

### Asynchronous copies

`cudaMemcpyAsync` is a real asynchronous copy rather than a synchronous
fallback, with the minimum stream API to use it safely
(`cudaStreamCreate`/`CreateWithFlags`/`Destroy`/`Synchronize`/`Query` and
`cudaDeviceSynchronize`). A `cudaStream_t` is an in-order asynchronous Level
Zero immediate command list plus the device it was created on.

Three findings from bringing this up, each of which would have corrupted data
silently:

| Finding | Consequence |
|---|---|
| Level Zero immediate command lists are **not** in-order by default | A small copy overtakes a preceding large copy to the same address. Fixed with `ZE_COMMAND_QUEUE_FLAG_IN_ORDER`; `StreamPreservesSubmissionOrder` fails without it. |
| `zeMemFree` does no in-flight checking, unlike `cudaFree`'s implicit device sync | Freeing a buffer with a copy in flight corrupts silently once copies are truly async. `cudaFree`/`cudaFreeHost` now drain first. |
| `zeCommandListAppendMemoryCopy` must not be called concurrently on one command list | The per-device list is shared by every thread calling `cudaMemcpy`; the multi-threaded TCP transport would have hit this. Now locked. |

The ordering test is a real detector, not a smoke test: it needs a
write-after-write to one address, asymmetric sizes (large then <=4 KiB), and
pinned host sources. Weaken any of the three and it passes against the broken
implementation — measured, and recorded in a comment so it is not "simplified"
later.

`cudaEvent_t` is deliberately not implemented (needs an event pool, no consumer
in the XPU build yet) — callers get a link error, not silent misbehaviour.

## Caveats / reviewer notes

- **The RDMA dma_buf path is not verified on hardware.** This host has no
  InfiniBand, so `exportDmabuf()` is unit-tested (a valid fd is produced,
  caller-owned, with the right base/offset) but `ibv_reg_dmabuf_mr` and an
  actual GPU-direct RDMA transfer are untested. Only the TCP path is covered
  end to end. Happy to run this on a Mellanox host if someone can point me at one.
- `exportDmaBufFd()` extracts the fd from the first `sizeof(int)` bytes of
  `ze_ipc_mem_handle_t.data`. That is how the xe/i915 driver lays it out today,
  but it is not guaranteed by the Level Zero spec — flagging it as the most
  driver-version-sensitive assumption here.
- `build-xpu/` added to `.gitignore` — the default build dir of the new
  `scripts/build_xpu.sh`.

**mooncake-transfer-engine/include/gpu_vendor/xpu.h:30**
* `cudaErrorNotReady` here is not the CUDA Runtime value: 600 is the CUDA Driver API's `CUDA_ERROR_NOT_READY`, while the runtime error is 34. `cudaStreamQuery` therefore returns a value incompatible with the cuda-alike contract, and the comment above is false; define the runtime value (34) or introduce an explicitly XPU-specific error instead.
```
#define cudaErrorNotReady 600
```
**mooncake-transfer-engine/src/gpu_vendor/xpu.cpp:418**
* The host-allocation path has the same unchecked synchronization failure as `cudaFree`: if a stream cannot be drained, this still calls `zeMemFree` and may free a buffer used by an in-flight H2D/D2H copy. Propagate the failure before freeing the host allocation.
```
    syncAllOutstanding();  // host staging buffers feed in-flight H2D copies
```
**mooncake-transfer-engine/src/gpu_vendor/xpu.cpp:372**
* Stream destruction is not coordinated with stream operations: it does not take `s->mu`, while `cudaMemcpyAsync` may be appending under that mutex, and `cudaStreamSynchronize`/`cudaStreamQuery` read `s->list` without `rt.mu`. A concurrent destroy can therefore destroy the Level Zero list or delete `s` while another call uses it, causing use-after-free and violating the no-concurrent-append rule. Add a stream lifetime/operation protocol before reclaiming the handle.
```
    std::lock_guard<std::mutex> lock(rt.mu);
    auto it = std::find(rt.streams.begin(), rt.streams.end(), s);
    if (it == rt.streams.end()) return cudaSuccess;
    rt.streams.erase(it);

    // Drain first: an in-flight copy must not outlive the list.
    if (s->list) {
        zeCommandListHostSynchronize(s->list, UINT64_MAX);
        zeCommandListDestroy(s->list);
        s->list = nullptr;
    }
    delete s;
```
**mooncake-transfer-engine/src/gpu_vendor/xpu.cpp:392**
* `cudaDeviceSynchronize()` snapshots raw list handles and then releases `rt.mu`; a concurrent stream destroy can invalidate one before the wait at line 397 synchronizes it. The wait needs a lifetime reference/lock through completion rather than only snapshotting the pointer.
```
        for (auto *s : rt.streams) {
            if (s->device == dev && s->list) to_wait.push_back(s->list);
        }
```
**mooncake-transfer-engine/src/gpu_vendor/xpu.cpp:566**
* The Level Zero spec defines `ze_ipc_mem_handle_t.data` as opaque; it does not guarantee that its first four bytes are a dma_buf fd. On a different Intel driver/layout this can duplicate an unrelated fd and feed it to `ibv_reg_dmabuf_mr`.
