## Description

Implements standalone DFS shard allocator recovery proposed in #3819, rebased onto the current `ShardAllocator` interface after the allocator rename and bucket backend addition.

The shard allocator now persists allocation ownership in per-shard checkpoints and WALs, then reconciles recovered allocations with standalone Master snapshots before serving requests. In particular:

- Persist `ALLOC` before exposing a descriptor and `RELEASE` before reusing a deferred extent.
- Recover from checksummed checkpoints and WAL records, with configurable compaction.
- Seal shard allocations during snapshot reconciliation, retain matching replicas, prune stale descriptors, and quarantine orphan allocations.
- Reject incomplete, corrupt, or incompatible sidecars, and preserve allocation ownership across online shard expansion and restart.
- Carry a persistent allocation ID in DFS descriptors to reject stale references after extent reuse.

The new immutable bucket allocator remains a separate DFS mode. This PR applies metadata persistence and snapshot reconciliation to `ShardAllocator` only; bucket mode retains its own allocation and eviction behavior and remains incompatible with snapshot restore. Compatibility validation uses stable per-shard identity instead of total shard count. The WAL compaction setting is `MOONCAKE_DFS_METADATA_WAL_COMPACTION_THRESHOLD_BYTES`.

### Compatibility and scope

The client data path and existing Put/Upsert RPC signatures remain unchanged. Existing roots containing only `.data` files cannot be migrated in place; upgrade and rollback require a new empty shard DFS root. HA, OpLog recovery, standby promotion, and multi-tenant DFS remain unsupported. Metadata persistence does not add data-file `fsync` durability.
