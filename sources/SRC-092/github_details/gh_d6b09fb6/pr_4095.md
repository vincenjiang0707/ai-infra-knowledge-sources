## 正文

## Description

Add a reusable ranged-read metadata snapshot for Store reads and use it in the Engram and reconstructed-shard read paths.

The motivation is to reduce TTFT-sized Engram read latency by avoiding repeated Store query/lease metadata work when the same key set is read repeatedly. The actual TransferEngine/RDMA data path is unchanged in this PR.

### API and behavior

- Add `PyClient::RangedReadSnapshot`, a caller-owned snapshot of fresh `batch_query()` results.
- Add `prepare_get_into_ranges_snapshot(keys)` and `refresh_get_into_ranges_snapshot(...)`.
- Add `get_into_ranges_from_snapshot(...)` for reads that must use the supplied snapshot and must not re-query or renew leases.
- Cache one snapshot per `EngramStore` layer and invalidate it on `populate()` and successful `remove_from_store()`.
- Reuse the same snapshot abstraction in the parallel/reconstructed-shard read path when query results are already cached.

Snapshot refresh time is derived from the earliest lease timeout and is set to halfway through the remaining lease window. If any key fails query or has an expired lease, the snapshot is not treated as reusable. Ordinary `get_into_ranges` keeps the existing query-refresh behavior.

## Reshard metadata-snapshot integration

Commit `4e41b71b` extends the PR1 snapshot fast path to Reshard weight loading.

### Implementation

- Expose `prepare_get_into_ranges_snapshot` and `get_into_ranges_from_snapshot` on the Python Store binding.
- Prepare one snapshot for the immutable source-object set of a Reshard load and reuse it across all ranged-read batches.
- Refresh at the read-lease midpoint before submitting a later batch.
- Preserve compatibility with older Store builds where both optional methods are absent; a partially implemented snapshot API fails closed.

### Validation

- Release build passed for `store` and `mooncake_master`.
- Reshard model-weight Store suite against the newly built Store extension: `108 passed`.
- Python type checking: 0 errors.
- Every benchmark iteration validates output byte for byte.

Tests used two A10 + ERDMA peers. Snapshot preparation is included in the optimized timings.

| Workload | Location | Plain p50 | Snapshot p50 | Speedup |
|---|---|---:|---:|---:|
| 64 ranges x 1 MiB | Local | 7.046 ms | 6.764 ms | 1.04x |
| 64 ranges x 1 MiB | Cross-machine | 7.156 ms | 6.627 ms | 1.08x |
| 98,304 ranges x 264 B | Local | 178.33 ms | 103.22 ms | 1.73x |
| 98,304 ranges x 264 B | Cross-machine | 318.60 ms | 134.88 ms | 2.36x |

For the many-small case, optimized end-to-end useful throughput is 1.54 Gbit/s at the existing 1,024-range batch size. That low throughput is expected to remain after PR1 because snapshot reuse removes metadata queries, not the 98,304 small RDMA work requests. Owner-side gather and bulk transfer belong to PR2.
