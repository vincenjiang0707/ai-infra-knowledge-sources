## Description

Classic TCP currently bounds each connection group's waiting work by item
count. Because each item retains its source payload until it starts or leaves
the waiting queues, large requests can retain a much larger byte extent than
the item limits suggest. This became more important after #3710 raised the
default queue and pending-admission limits to 65,535. Its review identified a
byte-based limit as follow-up work.

This change adds the opt-in `MC_TCP_MAX_QUEUED_BYTES_PER_PEER` setting. For each
TCP `ConnectionKey`, it bounds:

```text
sum(queue.length) + sum(pending_admissions.length)
```

A request that would exceed the limit receives the existing `QUEUE_FULL`
terminal result. Moving an item from pending admission to the queue is
accounting-neutral; its charge is released when it starts on a lane or leaves a
waiting container through timeout, error, retirement, or shutdown.

Unset or `0` preserves existing behavior. Active lanes are excluded because
their count is already bounded by `MC_TCP_LANES_PER_PEER`. The limit remains
opt-in because selecting a nonzero default requires representative
slow/stalled-peer and caller-recovery measurements.

Admission is per transport work item, not atomic over a multi-descriptor
`batchTransferSync` call. An earlier descriptor can be accepted before a later
one is rejected. The documentation therefore warns callers not to treat a
nonzero batch result as proof that no destination bytes changed or that all
source buffers can immediately be released.

This is a resource-admission bound, not a throughput or RSS-reduction claim.

Related: #2930, #3710, #3446

### adenzhou1350 · 2026-09-12

Follow-up pushed in `74d26b56`: preserve the queued TCP pump after a queue-full rejection.

While qualifying partial-batch failure and immediate source-buffer reuse, a deterministic classic-TCP loopback exposed a same-peer liveness race: an oversized rejected request could create a replacement pump epoch, but the rejection branch suppressed `postGroupPump`, stranding already accepted work and a later recovery transfer. The fix makes rejected-item completion and replacement-pump posting independent.

Validation on the exact PR head, CPU-only with `USE_CUDA=OFF`:

- clean rebuild and clang-format: PASS
- deterministic regression: 3/3 PASS
- combined classic-TCP loopback matrix: 3/3 PASS
- admitted payload remains correct; rejected destination remains canary-clean
- immediate source slab free/reuse+poison remains safe
- later same-peer recovery completes

This establishes the liveness correction for CPU classic TCP only. It does not add an RDMA, accelerator, multi-host, performance, or representative production-workload claim.
