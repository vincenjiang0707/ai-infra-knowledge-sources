## Description

TENT only selects a GPU platform under `USE_CUDA` / `USE_HIP` / `USE_SUNRISE`
(and the other vendor macros). A Biren build therefore fell back to
`CpuPlatform`, and TENT's RDMA context and benchmark had no SUPA paths at all.
This change reuses the existing CUDA platform through the `cuda_alike.h`
abstraction, so SUPA gets the same device probing, allocation, copy and
topology behaviour as the other CUDA-compatible accelerators.

> **Stacked on the Biren (SUPA) integration PR (#PR1).** The two commits from
> that PR are the base of this branch. Merge/rebase it first, or target this PR
> at the PR1 branch.

- **TENT platform**
  - `runtime/platform.cpp`: select `CudaPlatform` for `USE_CUDA || USE_SUPA`.
  - platform CUDA sources (`cuda.h`, `cuda_utils.h`, `cuda_allocator.cpp`,
    `cuda_probe.cpp`): include `cuda_alike.h` instead of `<cuda.h>` /
    `<cuda_runtime.h>`; the `CUDART_VERSION` ABI check is guarded with
    `USE_CUDA` because SUPA has no `CUDART_VERSION`.
  - `common/status.h`: expose `CHECK_CUDA` / `CHECK_CU` under SUPA.
  - `platform/cuda/CMakeLists.txt`: build the platform when `USE_SUPA` is on and
    link `${SUPA_LIBRARIES}`.
- **TENT RDMA**
  - `transport/rdma/context.cpp`: compile the GPU memory-registration path under
    SUPA as well.
  - `transport/rdma/rdma_transport.cpp`: treat the `biren` driver as a
    GPUDirect source. Biren exposes GPU memory through DMA-BUF and has no
    peer-memory module, so the module-based heuristic previously disabled
    GPUDirect on Biren.
- **SUPA shim** (`gpu_vendor/supa.h`): map `cudaRuntimeGetVersion`,
  `cuCtxGetCurrent`, `cuDevicePrimaryCtxGetState` and
  `CUDA_ERROR_NOT_INITIALIZED` to their SUPA equivalents.
- **Benchmark** (`benchmark/te_backend.cpp`, `tent_backend.cpp`, `utils.h` and
  `benchmark/CMakeLists.txt`): treat SUPA like CUDA/Sunrise, and resolve the
  `supa:` location prefix for NUMA binding in the classic backend.

## How Has This Been Tested?



Tested inside a Biren SUPA dev container on a host with 8x Biren166M (64 GB
each), Hygon C86-4G CPU and 8x RoCE NICs, using SUPA SDK 1.10.

**Test commands:**
```bash
# 1. TENT + SUPA build
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DUSE_TENT=ON -DUSE_SUPA=ON \
      -DBIREN_HOME=/usr/local/birensupa/sdk/latest -DWITH_STORE_RUST=OFF
ninja -C build tent tent_shared tebench

# 2. Default TENT regression (no SUPA)
cmake -S . -B build_default -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DUSE_TENT=ON -DWITH_STORE_RUST=OFF
ninja -C build_default tent tebench

# 3. TENT VRAM runtime smoke test (target mode)
./build/mooncake-transfer-engine/benchmark/tebench \
  --seg_type=VRAM --total_buffer_size=134217728
```

**Test results:**
- [ ] Unit tests pass
- [ ] Integration tests pass (if applicable)
- [x] Manual testing done (describe below)

- `-DUSE_TENT=ON -DUSE_SUPA=ON`: **0 compiler errors**; `tent`, `tent_shared`
  and `tebench` build and link, and `tebench` resolves `libsupa-runtime.so.1`.
- `nm` on the SUPA-built `platform.cpp.o` shows it references only
  `CudaPlatform` (no `CpuPlatform`), confirming TENT selects the GPU platform.
- `tebench --seg_type=VRAM --total_buffer_size=134217728`: TENT detects the
  Biren devices, allocates a single 128 MiB **VRAM** buffer and registers it
  successfully.
- Default TENT build (`USE_SUPA=OFF`): **0 compiler errors**, no regression.
- Not covered here: RDMA end-to-end transfer could not be exercised inside the
  container because the `zrdma`/`dinghai10e` NIC userspace provider is not
  installed there (`ibv_devices` is empty). A follow-up run on a bare host (or
  an image with the vendor RDMA provider) is recommended before merging.
- Unrelated: the full-tree build fails to link only
  `mooncake-store/tests/ordered_oplog_writer_test` on this host due to an
  `io_getevents`/libaio link issue; it is independent of this change.
