## Description

Prevent ROCm release artifacts from silently shipping without the multi-protocol routing required for combined RDMA and HIP segments.

The published `mooncake-transfer-engine-rocm==0.3.13.post1` CPython 3.10 wheel was built from `v0.3.13.post1` (`719735896c86b56fabec6cf3e825fb2ea640597a`). Its release workflow enabled HIP but omitted `-DENABLE_MULTI_PROTOCOL=ON`, while that CMake option defaults to `OFF`. In a reported two-node MI355X test using `lmsysorg/sglang:v0.5.18-rocm720-mi35x`, a cross-host GPU WRITE selected HIP IPC and failed with `hipIpcOpenMemHandle: invalid device context`. Rebuilding the same source with multi-protocol support enabled passed 16 bidirectional 2 MiB GPU WRITEs with full source and destination byte-integrity checks.

PR #3338 already corrected the current ROCm CI and release configuration to pass `-DENABLE_MULTI_PROTOCOL=ON`. This PR adds the missing artifact-level guard so a future workflow/configuration regression cannot publish another incorrectly configured ROCm wheel:

- expose `mooncake.engine.SUPPORT_MULTI_PROTOCOL` from the compiled extension;
- require ROCm wheel verification to reject an explicitly disabled capability;
- retain a narrow binary-marker fallback for workflow-dispatch backfills of older tags that predate the Python capability attribute;
- add positive and deliberately broken negative unit tests, including a chunk-boundary marker test.

Independent artifact inspection reproduced the build mismatch:

- affected PyPI CPython 3.10 wheel SHA-256: `4263d8a48c8bd05a340c19fa7533e012a3d4b9ac284161142a3062c24a4de4c6`; its `engine.so` lacks the multi-protocol-only `MC_DISABLE_HIP` marker and is rejected by this guard;
- current-main CI artifact from run `34701684601`, head `6ae74b3512c4d0ce70c4a7c22bc4f33aeb7d3ff8`, SHA-256 `084de7e711884f0fe9602ad0d5de0b46589526655e5a7c8b71ac8f53f616fe7a`; its `engine.so` contains the marker and is accepted.

This PR prevents recurrence but does not replace the immutable PyPI `0.3.13.post1` files. A new ROCm package version is still required to make the corrected build available through normal `pip install`.

Related: #3108, #3338. Open PR #3970 also edits the verifier, and #4177 moves the E2E verifier path; this change is intentionally narrow and may need to be carried across whichever layout lands first.
