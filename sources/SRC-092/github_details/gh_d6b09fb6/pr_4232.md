## Description

Fixes #4097. A successful `BatchOffload` can omit duplicate keys (or individual failed file writes) from its completion callback. Those keys remain in `all_bucket_keys`, so the existing sweep never NACKs them and the Master retains their offload tasks and source-replica references until timeout.

Record the keys successfully reported by each completion callback and send the existing `data_size=-1` NACK for the remaining inputs after a successful batch. This releases their tasks without fabricating disk replicas. Existing batch-error handling, storage commits, rollback behavior, RPCs and disk formats are unchanged.

Related work: #3009 handles tasks deferred during bucket grouping; this change handles keys already passed to `BatchOffload` but omitted from its completion callback. #3226 parallelizes per-bucket execution and currently retains the same notification gap; this focused fix may need to be carried into its extracted bucket worker when the two changes are integrated.

### he-yufeng · 2026-09-20 · COMMENTED

Verified the mechanism against current main. The completion callback only reports the keys it is handed, so keys the batch skipped (a duplicate committed by a concurrent offload, or a write that failed inside an otherwise successful batch) never reach NotifyOffloadSuccess, and their offload tasks plus source-replica refs linger until timeout. The reused NACK path is the existing one: failed_tasks to NotifyOffloadSuccess with data_size=-1 (file_storage.cpp:543), and task_by_storage_key is built from every key in the batch, so the .at() cannot miss. Inserting into reported_keys only on ErrorCode::OK keeps partially-failed callbacks honest, and ConcurrentOffloadBackend is a good deterministic way to pin the race without a second thread.

One note for future readers, not a blocker: bucket_complete_handler captures reported_keys by reference, which is only safe because every backend completes synchronously inside OffloadObjects today. If a backend ever defers completion past the call frame this dangles. A comment near the capture or moving the set into shared state would make that assumption explicit.
