## Description

We run SSD offload in production. It gives us a much larger cache tier than DRAM
alone and measurably lifts our KVCache hit rate. Our serving hosts, however,
have several SSDs each, and today offload can only use one of them: the rest of
the disks sit idle while the single configured disk caps both our offload
capacity and our offload bandwidth. To actually use the hardware we have, SSD
offload needs to span multiple disks.

`BucketStorageBackend` assumes a single offload root throughout: one quota, one
FIFO/LRU eviction order, one path builder. This PR lets
`MOONCAKE_OFFLOAD_FILE_STORAGE_PATH` take a comma-separated list of roots and
makes the bucket backend per-disk end to end. A single path keeps behaving
exactly as before — the single-disk case is just a list of length one.

RFC: #4230

**Configuration**

```bash
# Two offload disks, 200 GiB on each
export MOONCAKE_OFFLOAD_FILE_STORAGE_PATH=/nvme0/mooncake,/nvme1/mooncake
export MOONCAKE_OFFLOAD_BUCKET_MAX_TOTAL_SIZE_LIST=214748364800,214748364800
```

- `MOONCAKE_OFFLOAD_FILE_STORAGE_PATH` accepts a comma list; whitespace around
  entries is trimmed. Each root is validated on its own (`stat` of the raw list
  string would always be `ENOENT`). An empty entry (`/d0,,/d1`, a leading or
  trailing comma) is a startup error rather than being dropped: every entry
  names one disk, so dropping one would silently run on fewer disks than the
  list has entries.
- `MOONCAKE_OFFLOAD_BUCKET_MAX_TOTAL_SIZE_LIST` is a new, optional per-disk
  quota list, positionally aligned with the path list. Unset or blank means
  the scalar `MOONCAKE_OFFLOAD_BUCKET_MAX_TOTAL_SIZE` applies to every disk.
  When set, it must have exactly one entry per path, and anything the backend
  would otherwise have to guess at is a startup error: an empty or unparsable
  entry, or a length that differs from the number of paths. Skipping an entry
  or reusing the last one would put a disk on its neighbour's quota, and
  falling back to the scalar would silently ignore the configured limits.
  Entries must be `> 0`, which is deliberately stricter than the scalar (where
  `<= 0` means "derive a default").
- **Limitation:** only `bucket_storage_backend` understands the list.
  `file_per_key_storage_backend` and `offset_allocator_storage_backend` use
  `storage_filepath` as a single directory, so they must stay on one path.

**Design points**

- **Per-disk accounting.** New `DiskState` holds `max_total_size`,
  `total_size`, `pending_write_size`, `pending_eviction_size`, its own
  FIFO/LRU eviction indices and its own `ActualDiskBytesUsed` scan cache.
  Quotas must not be global: a write reserved on one disk counted against
  another would make that disk evict to make room for bytes it never receives.
- **Disk selection is round-robin**, not most-free-wins. Free-space-greedy
  selection collapses onto one disk once the disks equalize, undoing the point
  of spreading writes.
- **Selection, reservation and eviction happen in one critical section**, so a
  concurrent writer cannot pick the same disk on stale free-space numbers. The
  chosen disk travels in `PendingEviction::disk_index` and every
  restore/commit/release step credits that same disk.
- **`BucketMetadata::disk_index`** routes path construction. It is not
  serialized: `Init()` re-derives it from the disk whose root the `.meta` file
  was found under, so existing on-disk data is readable without migration.
- **Watermark eviction is per-disk**, driven one disk at a time rather than off
  a single global watermark. `MOONCAKE_OFFLOAD_BUCKET_MAX_PHYSICAL_BYTES`
  likewise becomes a per-disk cap, since the `du`-equivalent scan runs per root.
- **Overlapping roots are rejected at `Init()`**, compared by path component so
  `/data/d1` is not mistaken for a child of `/data/d`.
- **The one-live-client-per-path lock from #4172 covers every root.** A client
  that shares any one disk with another live client would collide on that
  disk's bucket files, so each root gets its own `.mooncake_local_disk.lock`.
  The locks are taken after the overlap check (a root listed twice would
  otherwise fail against its own lock and hide the overlap error), and a
  client that fails part-way releases the roots it already locked.

Split into four reviewable commits:

1. `[Store] Parse multi-disk offload configuration` — config/env parsing,
   `SplitAsciiList`, `ResolveOffloadDiskPaths`, validation. Compiles and passes
   tests on its own.
2. `[Store] Spread bucket offload across several disks` — the backend
   conversion, including the per-root ownership lock.
3. `[Doc] Document multi-disk SSD offload configuration` — deployment docs for
   the new path form and quota list.
4. `[Store] Reject misaligned per-disk quota lists at startup` — review
   follow-up: empty entries in either list, and a quota list whose length does
   not match the paths, now fail startup instead of being skipped, reused or
   replaced by the scalar quota. `BucketBackendConfig::FromEnvironment()`
   returns `tl::expected`; `BucketStorageBackend::Init()` repeats the path and
   length checks for callers that skip `Validate()`.

### he-yufeng · 2026-09-21 · COMMENTED

Read the whole mechanism end to end, since this touches the write, read, eviction and recovery paths at once. The per-disk decomposition holds up everywhere I looked:

- Quota accounting is per-disk all the way through (total/pending_write/pending_eviction), and the reservation, commit, restore and release steps all credit the same disk the reservation was taken from. ReleasePreparedWriteLocked is also on the all-keys-persisted early return, so the reservation cannot leak.
- Reads route by the bucket's own disk_index from the moment BatchLoad builds its plans, and Init re-derives it from whichever root the .meta was found on, so restart recovery is consistent with what the file layout says.
- SelectEvictionCandidate self-heals stale FIFO/LRU entries, and PrepareEviction/RestorePreparedEviction restore BOTH indexes. Forgetting fifo_index there would have made a restored bucket invisible to FIFO eviction forever.
- Watermark eviction runs the full notify/commit/finalize sequence per disk instead of merging disks into one notification, which is what keeps a partial master failure roll-backable.
- The config edges are handled the way I'd want: overlapping roots refuse to start, an unparsable quota entry drops the whole list loudly rather than shifting every later disk onto its neighbour's quota, and no synthetic 90% quota appears when eviction is off.

Single-disk behavior is preserved by construction (length-1 vectors, fifo_index order equals the old buckets_ order), and the test suite backs the claims that matter, especially the starvation-under-eviction regression and Init recovery from every disk.

One operational question, not a blocker. Going from one disk to several on a live node: the existing disk starts full while the new ones start empty, and round-robin spreads only new writes, so the old disk keeps evicting under pressure while the others underfill until its buckets age out. Under LRU, hot old buckets may never really migrate. That settles eventually and the starvation rationale for avoiding most-free-wins is sound, but a short note in ssd-offload.md about the rebalance period (or a sentence saying it is intentional) would save operators a surprise. CI is green either way.
