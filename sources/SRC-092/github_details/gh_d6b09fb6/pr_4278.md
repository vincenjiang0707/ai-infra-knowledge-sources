## Description

`MasterClient::BatchReplicaClear` previously omitted its configured tenant when invoking the RPC. The server wrapper therefore used the default tenant, which could silently leave the requested tenant's replicas untouched and clear same-named replicas in the default tenant instead.

This change:
- carries the client's tenant through the `BatchReplicaClear` RPC;
- resolves and validates that tenant in `WrappedMasterService` before forwarding to the existing tenant-aware service overload;
- preserves default-tenant behavior when tenant quotas are disabled; and
- adds an in-process RPC regression test with the same object key in two tenants.

Fixes #4262.

### he-yufeng · 2026-09-22 · COMMENTED

Cross-checked this against #4262 (which I filed) and the existing tenant-resolution conventions in this file. The fix matches the house pattern exactly: WithRequestTenant plus the IsTenantQuotaEnabled gate is the same composition GetReplicaListByRegex and the other tenant-carrying handlers already use, so resolution stays consistent across RPCs instead of inventing a second rule.

The test is the convincing part: same key under both tenants, clear through a tenant-a MasterClient, assert tenant-a's copy is gone while the default copy survives, then clear default. That is precisely the failure #4262 reported (the default-scoped fallback could not touch the requested tenant's objects), and it proves no cross-tenant wipe in the other direction either.

One operational note worth a line in the description, not a code change: this changes the RPC's wire shape, so during a rolling upgrade an older client calling the new 4-arg handler will fail deserialization and see its clear error out loudly. That is the safe direction (a loud error, never a clear against the wrong tenant), but operators doing staged rollouts should know the window exists.
