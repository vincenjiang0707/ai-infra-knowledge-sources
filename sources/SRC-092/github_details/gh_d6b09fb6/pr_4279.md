## Description

#4259 already reuses the last-hit device inside one MR. The first-attempt
`selectDevice` / `selectPeerDevice` still runs for every request in a
submission, including the topology walk, even when the snapshot is a single
HCA with unique, non-overlapping coverage.

This change keeps a function-local cache for that first attempt. Consecutive
requests that stay inside the same buffer reuse `buffer_id` / `device_id`
without calling `selectDevice` again. The cache is not used on retries,
multi-HCA topology, overlapping range indexes, or `segments:` names.

#4273 already reuses `selectTransport` across consecutive same-`target_id`
requests. This PR also gates that reuse on `globalConfig().metacache`, so
`MC_DISABLE_METACACHE=1` still re-runs MultiTransport routing (protocol to
`Transport*`) on every request. It does not restore a per-request RDMA
`SegmentDesc` fetch; `submitTransferTask` still deduplicates by `target_id`.

Measured `submitTransfer` p50 on same-host H20 / `mlx5_bond_0` RDMA (classic
tebench, VRAM, GPU0→GPU1 READ, 4 KiB blocks). First two iterations skipped.
Wait / bandwidth is completion time and is not claimed. Baseline is current
`origin/main` (already includes #4259 and #4273). The cache is inactive on
multi-HCA topology, so these numbers apply to single-HCA hosts.

| batch | origin/main | this PR | change |
|---:|---:|---:|---|
| 4,096 | 1.500 ms | 1.398 ms | −7% |
| 65,536 | 13.986 ms | 12.460 ms | −11% |
| 207,360 | 43.803 ms | 38.667 ms | −12% |

Yes. The cache is per-submit and hits when consecutive requests stay inside one registered buffer on a single-HCA snapshot — the same shape as a large TransferEngine batch, not a tebench-only pattern. The number we report is submitTransfer CPU; completion wait / bandwidth is not claimed. On multi-HCA hosts the cache is inactive.
