# [PR #4291] [Store] Scan a standby remount under the shared snapshot lock

## 正文

## Description

After an HA promotion, `ReMountSegment` walks all 1024 metadata shards to find the replicas that survived on a standby-restored segment, and until now it did that holding `snapshot_mutex_` exclusively, from the first validation to the last replica. Every data-plane operation on the master waits for the whole walk, which is seconds on a store with a few million objects, and concurrent remounts run one after another. This is the snapshot-lock half of the join-storm stall described in #3937 and RFC #4181 (scenario S1).

### What changes

**Two stages.** `ReMountSegment` now prepares under the shared lock and commits under the exclusive one:

- `PrepareRemount` (shared): validates the request, scans the shards for surviving replicas and rebuilds each segment's allocator from the regions they occupy. None of this mutates anything, so it only blocks the snapshot fork.
- `CommitRemount` (exclusive): mounts the segment, swaps in the rebuilt allocator, re-points the replicas by key and ends the orphan. Its critical section is bounded by the number of replicas on the segment, not by the size of the store.

Splitting the operation lets the scan's findings go stale, which the commit stage handles:

- A replica can disappear between the stages, so the scan records its key rather than a `Replica*`; the commit stage looks the key up again and re-matches the replica against the region of the buffer imported for it. A buffer nobody claims is dropped while the exclusive lock still covers the allocator its region returns to.
- An HA restore can rewrite the state the scan read. A generation counter, advanced by every restore, is compared across the gap; a remount that loses the race returns `UNAVAILABLE_IN_CURRENT_STATUS` and the client retries.
- The allocator a mount creates treats the whole segment as free, so the mount and the swap to the rebuilt allocator happen inside one segment-manager critical section.

**`OrphanedSegments`** (`include/ha/orphaned_segments.h`). What an HA restore leaves behind for such segments — the segment list, the bytes still charged to them, the allocators keeping their buffers alive and which endpoints are unreadable — was four `MasterService` members keyed three different ways, stitched together by callers. It is now one record per segment, and the interface follows the segment's lifecycle: `Reset` on restore, `Find` while preparing a remount, `Adopt` when committing it, `IsUnreadable` for readers, `ReleaseAll` on shutdown. `Reset` is the only way to install orphans and always advances the generation, so the check the commit stage depends on cannot be skipped by a future restore path.

**Behavior change: allocated-memory metrics.** Adopting a segment now releases everything still charged to it. Before, only the bytes of the replicas the remount found were released, so the bytes of replicas that died while their segment was orphaned stayed on that segment's allocated-memory metric until the next restore or shutdown, and the leftover entry sent later remounts of the segment through the full scan again. The re-adopted allocator already counts the surviving replicas itself (`OffsetBufferAllocator::Restore`, `CachelibBufferAllocator::adoptImportedBuffer`).

Smaller changes:

- The placeholder allocators a restore creates for NoF replicas are kept in their own member instead of the memory-segment keepalive map, since no memory remount adopts them.
- The scan no longer copies the buffer descriptor of every memory replica in the store, only of those on the segments being re-adopted.
- The restore log line reports `unreadable_segments=<n>` (a segment count) instead of `invalid_endpoints=<n>` (an alias count).

### Relation to open work

- **RFC #4181 / #4180 / #4183.** #4180 takes `client_mutex_` off this path and #4183 moves `Ping` onto its own RPC server; this PR shortens the `snapshot_mutex_` hold. Neither alone stops the mass expiry. This is meant to land before #4180, which will rebase onto it.
- **#3858** separates restored NoF placeholders from the memory-segment keepalive for the same reason as here, and additionally quarantines NoF endpoints. Whichever lands second folds `restored_nof_allocators_` and `standby_nof_allocator_keepalive_` into one; the NoF quarantine stays outside `OrphanedSegments`, which only tracks memory segments awaiting a remount.
- **#3666** changes `ReMountSegment`'s signature for a different purpose; the two will conflict textually in the same function.
