## Description

Related to #3808 (E01). This is the **runtime accounting-fields slice**: an
`AllocatedBuffer` now distinguishes the caller's requested byte count from the
extent its allocator actually reserved, for both the CacheLib and
OffsetAllocator backends.

E01 in the roadmap reads "Distinguish requested bytes from allocator-reserved
bytes while keeping old descriptors readable". This patch does that at runtime
and keeps old descriptors readable by rebuilding the extent from real backend
metadata after a restore. It deliberately **adds no field to any writer**, so it
does not claim completion of a persisted descriptor schema extension. If a
persisted field is what E01 is meant to require, that is a separate wire
contract and this patch is its prerequisite, not its substitute.

What changes:

- `AllocatedBuffer::requested_size()` names the existing `size()` value;
  `size()` keeps its meaning as the transfer length for the descriptor and the
  requested-based usage counters.
- `AllocatedBuffer::reserved_size()` returns `std::optional<std::size_t>`.
  `nullopt` means "no physical allocation has been reconstructed yet" — never
  zero, never `requested_size()`.
- The owning constructor now takes `reserved_size` as a **required** parameter,
  so every production allocation site had to state where its value comes from.
  All five sites were audited: CacheLib fresh allocate, CacheLib import, Offset
  fresh allocate, Offset import, and the descriptor rebinding in
  `Serializer<AllocatedBuffer>::deserialize`.
- CacheLib reads the allocation class size from the chunk's own slab header
  (`MemoryAllocator::getAllocInfo(...).allocSize`), for fresh allocations and for
  `importAllocations` alike. `padding_size = max(requested, kMinSliceSize)` is
  only the allocation *input*; class rounding can reserve more, so it is no
  longer treated as the extent.
- OffsetAllocator reads the real node extent (`node.dataSize <<
  multiplier_bits`) while the allocation lock is already held and carries it on
  the handle. `createHandleAtNode` and the new bounds-checked
  `allocationReservedSize()` read the same source, so a handle rebuilt from
  persisted state reports the extent it was actually allocated with instead of
  re-deriving it from the current rounding rules. `OFFSET_ALLOCATOR_NOT_ROUND_UP`
  and legacy size classes therefore stay correct.
- Both backends **enforce** `reserved_size() >= requested_size()`. An extent that
  is missing or smaller than the request rolls the allocation back (the raw chunk
  is freed / the node released), records no usage, and fails the call. `nullopt`
  is consequently reachable only for buffers that own no physical allocation —
  it is not a silent fallback for a failed lookup.
- `ImportCachelibBufferAllocator` resolves every extent **before** the first
  `adoptImportedBuffer` call records usage, so a partially adopted import cannot
  publish accounting.
- `AllocatedBuffer` move construction/assignment were declared in the header but
  never defined, so no object-level move existed. They are now defined so the new
  field follows ownership: the destination releases its previous allocation
  exactly once, self-assignment is an explicit no-op, and the moved-from object
  owns nothing. `SegmentLifetime::isAvailable()` also treats a moved-out token as
  unavailable instead of dereferencing a null pointer.

**This changes two public constructor signatures** (`AllocatedBuffer` and
`OffsetAllocationHandle` gained a required parameter), which is a source-level
breaking change for any out-of-tree caller. In-tree call sites are updated,
including the test double in `tests/test_buffer_allocator.h`.

Requested-based accounting is untouched: `RecordAllocation`,
`RecordDeallocation`, `SetUsageBytesForRestore` and `GetUsageBytes` still operate
on requested bytes, and `deallocate` still frees the whole chunk/node and
decrements by `size()`.

18 new cases are added (13 in `buffer_allocator_test`, 5 in

handling, concurrency, failure paths and zero-length behaviour. Zero-length
behaviour was additionally measured with a probe binary built against both
revisions: identical output.

**Cross-version wire compatibility.** A fixture tool was compiled against both
revisions with identical flags and link line, so the two binaries differ only by
this patch. It emits the exact `Serializer<AllocatedBuffer>` bytes and reads them
back:

- `base emit` and `patched emit` are **byte-identical** (same sha256).
- old→old, **old→new**, new→new and **new→old** all pass with 0 failures over
  `requested = {477, 4097, 100000}` on an OFFSET and a CACHELIB region.
- The patched reader reconstructs, with no persisted field at all:
  OFFSET `477 → 480`, `4097 → 4608`, `100000 → 106496`;
  CACHELIB `477 → 480`, `4097 → 4544`, `100000 → 103496`. The two backends
  legitimately disagree for the same request, which is precisely why each must
  report its own metadata.
- Wire shape is asserted directly: every buffer record is a 5-element array and
  every offset record's nested handle is a 3-element array.

**Performance.** The expected cost is one extra metadata read per allocation (a
slab-header read for CacheLib, one node read under the already-held lock for
Offset), against 250.8–299.9 ns/op measured at one thread. A paired 72-arm
fresh-process screen could not resolve it and is reported as inconclusive: the
A/A control, which runs the *same baseline binary in both arms*, reported a
nominally significant **+11.72 %** (95 % interval [+0.72, +23.93]), and every
A/P interval crossed zero. No performance claim is made in either direction; a
verdict needs a quiet, dedicated machine with clock/power stabilisation.

**Object size:** `AllocatedBuffer` 176 → 208 B and `OffsetAllocationHandle`
40 → 56 B (`std::optional` fields). This is per live replica, not per segment.

**Not tested:** real CXL / NoF device I/O (no hardware; the address-representation
half is covered by a metadata-level test that confirms a CXL offset is *not*
attributed to slab metadata), and real-etcd HA restore E2E.

### he-yufeng · 2026-09-18 · COMMENTED

Mechanism read through the allocator interface, both backends, the serializer, and the import path. The accounting discipline holds everywhere I tried to break it.

The honest-unknown semantics are the right spine for this: `reserved_size` is `optional` end to end, `nullopt` means "not reconstructed" and is never silently substituted with `requested_size`, and the default `lookupReservedSize` returns `nullopt` so backends that cannot attribute an address stay honest rather than inventing an extent. The wire format stays unchanged, and the restore path rebuilds the extent from real backend metadata — the offset-allocator path reads the restored node under the allocator lock, the CacheLib path reads the slab header via `getAllocInfo` with `isValidSlab` rejection, and both fall back to unknown rather than guessing.

The parts I probed hardest and why they hold:

- Import resolves every recovered chunk's real extent BEFORE any usage is recorded, and a failed or too-small lookup aborts the whole import instead of publishing partial accounting. The `reserved < requested` sanity check catches metadata/offset misalignment at the same gate.
- The bundled move-constructor/move-assignment work is correct RAII hygiene, not incidental churn: move-assign releases the destination's previous allocation exactly once before adopting, and the moved-from source is nulled so its destructor can't release the chunk or decrement the counters again. The `SegmentLifetime::isAvailable` null guard closes the moved-from UB that the same move made reachable.
- Concurrency: the live-path lookup happens at construction time on a buffer this same call just allocated, and the restore-path lookup runs under the allocator lock, so neither reads a chunk mid-free.

Not blocking, one note for the reviewer who follows: `getAllocInfo` on CacheLib reads internal slab state; if CacheLib ever changes what `allocSize` reports for a chunk (rather than how it's laid out), the accounting here inherits that silently. A one-line comment pinning "allocSize is the class extent of the owning chunk" is already there, which is the right amount of pinning.
