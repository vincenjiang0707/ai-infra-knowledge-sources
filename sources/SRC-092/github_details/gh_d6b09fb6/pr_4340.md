## 正文

## Description

`HipTransport` and `NvlinkTransport`'s `cudaIpc*` path send transfers to the wrong address when a registered GPU buffer does not start at the beginning of its allocation. The NVLink path is the one used when `MC_USE_NVLINK_IPC` is set or the GPUs lack fabric handle support.

Both transports publish `desc.addr = addr` with the handle from `hipIpcGetMemHandle(addr)` / `cudaIpcGetMemHandle(addr)`. On the peer, `hipIpcOpenMemHandle` / `cudaIpcOpenMemHandle` returns the base of the whole allocation, and `relocateSharedMemoryAddress` computes `dest - entry.addr + shm_addr`. So a buffer that starts `N` bytes into its allocation gets every transfer `N` bytes early. Writes land on whatever sits at the start of the allocation, and reads return the wrong data.

Caching allocators sub-allocate like this routinely. We hit it with SGLang prefill/decode disaggregation on one MI355X node. The decode's DSA index-K cache buffers shared a PyTorch segment with a MoE weight-scale tensor, and the prefill's index-K writes overwrote those weights.

**Fix.** `registerLocalMemory` looks up the containing allocation. It exports the handle from the allocation base and appends the buffer's offset to the handle in `shm_name` when the offset is non-zero. It rejects a range that runs past the end of its allocation. The peer stores the offset with the opened mapping and adds it when relocating, on both the first-open and the cached path.
- **HIP:** the lookup uses `hipMemGetAddressRange`.
- **NVLink:** the lookup uses `cuPointerGetAttribute` (`RANGE_START_ADDR`/`RANGE_SIZE`), because `cuMemGetAddressRange` can fail unless the allocation's context is current on the calling thread. On a B200 with CUDA 13.0 it returned `CUDA_ERROR_INVALID_CONTEXT` on a thread with no current context, and `CUDA_ERROR_NOT_FOUND` with a context of another device current. `musa.h` gets the `RANGE_START_ADDR` alias. SUPA keeps `cuMemGetAddressRange`, because `supa.h` has no alias for that attribute.

`desc.addr`/`desc.length` still describe the registered buffer, so the published buffer boundaries and `unregisterLocalMemory(addr)` are unchanged. Publishing the allocation range instead would make the entry cover memory the caller never registered. As before, the peer opens the handle once per registered buffer. HIP and CUDA both refcount repeated opens of one handle, and the tests put three buffers in one allocation.

**Compatibility.**
- Buffers at offset 0 publish the same 64-byte handle as before, so they work between old and new peers.
- For other buffers a new exporter sends 72 bytes: the handle plus a host-order `uint64` offset (144 hex characters in `shm_name` instead of 128). An old importer rejects that with "Mismatched HIP/NVLink data transfer method", so the transfer fails instead of corrupting memory. There is no fallback to another transport.
- An old exporter still sends 64 bytes for those buffers, and a new importer relocates them the old, wrong way. Both sides need this change.

**Not covered here.**
- `MusaTransport` runs the NVLink code through `GpuIpcTransportPolicy`, so it changes too. I have not built or tested it on MUSA or SUPA.
- The fabric branches of both transports publish the allocation range with no dedupe, and NVLink's still calls `cuMemGetAddressRange` directly. I left them alone.
- `remap_entries_` is keyed by `(target_id, entry.addr)` and never invalidated. If a peer unregisters a buffer and later registers a new one at the same address in a different allocation, the cached mapping is stale. This predates the PR.

## How Has This Been Tested?

`hip_transport_test` gets `HipTransportTest.IpcTransfersHitBuffersInsideLargerAllocation`. `nvlink_transport_test` gets `NvlinkIpcTest.TransfersHitBuffersInsideLargerAllocation`, registered with CTest as `nvlink_ipc_test` so it runs without the metadata server the other tests there need. Both tests work the same way:
- **Processes.** The destination runs in a second process (the test binary re-executed), since transfers to the process's own segment use `LOCAL_SEGMENT_ID`, which bypasses relocation.
- **IPC mode.** Both processes are forced onto the IPC path through `MC_USE_HIP_IPC` / `MC_USE_NVLINK_IPC`.
- **Layout.** The destination registers three buffers in one zeroed 4 MiB allocation, at offsets 0, 1 MiB + 512 and 2 MiB + 4 KiB.
- **Transfers.** The source writes the first buffer, writes the second one twice (the second write takes the cached-mapping path) and reads the third.
- **Checks.** The test checks the data that was read and every byte of the destination allocation.
- **Source registration.** The source buffer is registered from a fresh thread, on a second GPU when one has peer access to the first. Ranges past the end of its allocation must be rejected, including one whose length wraps around.

The second commit fixes the existing `RestoresActiveDeviceAfterTransfer`. In `P2PHANDSHAKE` mode the engine binds a free port, so opening the name passed to `init()` failed with "connection refused". It now opens `getLocalIpAndPort()`.

**Test commands:**
```bash
# HIP
cmake .. -DUSE_HIP=ON -DENABLE_MULTI_PROTOCOL=ON -DBUILD_UNIT_TESTS=ON \
    -DUSE_ETCD=OFF -DWITH_STORE=OFF -DWITH_STORE_RUST=OFF -DUSE_HIP_DMABUF=OFF
make -j hip_transport_test && ./mooncake-transfer-engine/tests/hip_transport_test
# CUDA
cmake .. -DUSE_CUDA=ON -DUSE_MNNVL=ON -DBUILD_UNIT_TESTS=ON \
    -DUSE_ETCD=OFF -DWITH_STORE=OFF -DWITH_STORE_RUST=OFF
make -j nvlink_transport_test && ctest -R '^nvlink_ipc_test$' --output-on-failure
```

**Test results**, with the source buffer on the second GPU:

| | 2× MI355X, ROCm 7.2.4 | 2× B200, CUDA 13.0, driver 595.91 |
|---|---|---|
| this PR | both HIP tests pass | `nvlink_ipc_test` passes |
| this PR with the transport changes reverted | new test fails, `RestoresActiveDeviceAfterTransfer` passes | fails |

With the transport changes reverted, the new tests fail the same way on both machines:
- both past-end ranges are accepted;
- the read returns none of the buffer's data;
- the second buffer's writes land at byte 0 of the allocation.
