## Description

We run SSD offload in production. A single batch's LOCAL_DISK replicas routinely
live on several offload endpoints rather than on one peer.

The client already groups such a batch by transport endpoint, but then reads the
groups one endpoint at a time:

```cpp
for (auto &[endpoint, objects] : offload_objects) {
    auto read_result = batch_get_into_offload_object_internal(endpoint, objects);
    ...
}
```

The groups are independent — different peers, different disks, different RPCs — so
the batch ends up waiting for the *sum* of the per-endpoint latencies instead of the
slowest one. Every extra peer a batch spans adds its full read to the total, and the
effect gets worse exactly as the cluster gets bigger. The client thread spends that
whole time blocked on `syncAwait`, not on CPU.

This PR reads the endpoints concurrently instead.

### Commits

**1. `[Store] Add ParallelExecute, a pool-backed bounded fan-out helper`**

`ParallelExecute(items, task, pool)` runs independent items on a persistent
`ThreadPool` the caller owns and returns one result per item **in input order**, so
the caller's existing merge loop needs no change at all. Design points worth a
comment:

- **All but the last item are dispatched; the last runs inline on the caller thread.**
  This keeps a single-item call off the pool entirely, and guarantees progress even
  when every worker is busy with something else.
- **A pool that cannot accept work degrades to serial execution** rather than
  failing — e.g. a pool already stopped during teardown. Correctness does not depend
  on the pool being alive.
- **A throwing task is reported as `INTERNAL_ERROR` for that item only.** Letting an
  exception escape a pool worker would terminate the process, and an unset promise
  would hang the caller forever in `future::get()`.
- **The pool is persistent by design.** The first consumer is the per-request read
  path, where creating threads per batch would cost more than the overlap saves.

This commit is self-contained and adds no caller; it compiles and tests on its own.

**2. `[Store] Read a batch's LOCAL_DISK endpoints in parallel`**

Three call sites shared that serial loop — `batch_get_buffer_internal`,
`batch_get_into_internal` and `batch_get_into_multi_buffers_internal`. The grouping
and the read now go through one private helper, `RealClient::read_local_disk_endpoints`,
which returns one entry per non-empty endpoint carrying that read's status. Each site
keeps its own merge loop unchanged.

**Only the reads move off the caller thread.** Checksum verification and every write
into the result vectors stay on the caller thread, after the join. The three merge
loops therefore need no concurrency reasoning, and the diff stays confined to how the
reads are issued.

On the reader being safe to call concurrently:

- `ClientRequester::invoke_rpc` enters through an atomic `RpcDrainGuard` and blocks on
  `syncAwait` while a separate io context pool drives the RPC.
- `Client::BatchGetOffloadObject` goes through `TransferSubmitter`, which
  `stress_workload_test` already drives from many threads.
- The pinned-arena local path shares `LoadBatch` with `FileStorage::BatchGet`, which
  coro_rpc handlers already call concurrently.

Worker count comes from `MC_OFFLOAD_PARALLEL_WORKERS`, default `8`. The workers spend
their time blocked on the peer RPC rather than on CPU, and the useful upper bound is
however many peers one batch spans.

**Two behavior notes, called out so they are not a surprise in review:**

- Endpoints with an empty batch are now skipped uniformly. Two of the three sites
  already did this; the third cannot produce one, since it emplaces a key immediately
  after `try_emplace` on the endpoint.
- The failure log in `batch_get_into_internal` now names the endpoint, which the log
  order no longer implies once the reads overlap.

**3. `[Doc] Document MC_OFFLOAD_PARALLEL_WORKERS in the SSD offload guide`**

A row in the core settings table plus a short note on what the workers block on.

### Limitations / non-goals

- **A batch confined to a single endpoint gains nothing** — it takes the inline path
  and never touches the pool. The win scales with how many peers a batch spans.
- **No change to error semantics.** Per-endpoint failures land on exactly the same
  keys as before.
- The pool is per `RealClient` and sized once at construction; it is not resized at
  runtime.

Non-test, non-config code is roughly 290 lines, so no RFC issue was filed.

### he-yufeng · 2026-09-22 · COMMENTED

Read the full mechanism end to end. The design holds up:

`ParallelExecute`: dispatching all but the last item and running that one inline gives progress when every worker is busy and keeps a single item off the pool entirely. The reference captures are safe because the caller joins on the futures before returning. `InvokeParallelTask` covering both exception shapes is the right containment: an escape would terminate the process from a worker or leave a promise unset and hang the join. The inline degradation paths rely on `ThreadPool::enqueue` throwing on stop, which the header documents, and the destructor draining pending tasks matches the client's lifetime contract (no call outlives the client, same as every other method).

`read_local_disk_endpoints`: the pointers reference into the unordered_map, which is not modified during the call, and `reserve` is exact so the vector never reallocates. Statuses merge back by index, which relies on the per-index promise ordering the tests pin. The important safety property is that only the reads go concurrent: checksum verification and every write into the result vectors stay on the caller thread in all three merge loops, so the integration adds no new shared-state reasoning. The concurrency claims check out by cross-reference: `invoke_rpc` enters through the atomic `RpcDrainGuard` and blocks on `syncAwait` with a separate io pool driving the RPC, `BatchGetOffloadObject` goes through `TransferSubmitter` (which `stress_workload_test` already drives from many threads), and the pinned-arena path shares `LoadBatch` with `FileStorage::BatchGet`, already called concurrently from coro_rpc handlers. The two behavior notes (uniform empty-batch skip, endpoint named in the failure log) are the right adjustments once reads overlap.

One observation, not blocking: `MC_OFFLOAD_PARALLEL_WORKERS` defaults to 8 per `RealClient` instance. Hosts that embed several clients (pybind users constructing many) each get their own pool, so the doc note about sizing by peers-per-batch might also say the count is per client, not per process. The workers block on `syncAwait` rather than CPU, so this is a resource-shape question, not a contention one.
