## 正文

## Summary
Fixes silent L3 corruption when multiple clients share one `storage_path` ([#3528](https://github.com/kvcache-ai/Mooncake/issues/3528)).

Aligns with maintainer guidance (standalone / **one client per `storage_path`**) plus the independent hardenings called out on the issue:

1. **Fail-fast** — exclusive flock on `{storage_path}/.mooncake_local_disk.lock` in `BucketStorageBackend::Init`
2. **Salt** — `BucketIdGenerator` mixes `getpid()` into the low bits so same-second clients do not share a sequence
3. **`O_EXCL`** — new bucket/meta opens no longer use silent `O_TRUNC`

Does **not** implement layout-independent `owner_id` (RFC option B).

### he-yufeng · 2026-09-17

Read the diff end to end against #3528. The three layers compose coherently and each covers the next layer's hole:

- The flock is the real contract enforcer: `LOCK_EX | LOCK_NB` on a lockfile inside the path, held for process lifetime with `O_CLOEXEC`, so a second live client fails `Init` fast with an actionable error, and a killed client frees the path through the kernel's fd cleanup instead of leaving a stale lock. The lockfile itself can't be mistaken for a bucket since scans are suffix-filtered.
- The pid salt is correctly scoped to restart safety, not concurrency: within one second a crashed client and its successor can no longer share an id sequence, so leftover files from the previous life are never silently continued. Noted for completeness that `getpid() & SEQUENCE_MASK` aliases once `pid_max` exceeds the mask width, which is fine here precisely because the flock and `O_EXCL` are the load-bearing guards and the salt only narrows the leftover-file window.
- `O_EXCL` on new paths is the right shape: same-client rewrites keep `O_TRUNC`, first creates fail loudly on a colliding name instead of truncating another tenant's file.

The "not owner_id (RFC option B)" scoping is honest, and the error message tells the operator exactly which contract was violated and what the remedies are. Verified by reading, no local build; the C++ suite should carry the two-client Init case the test plan lists.

### LujhCoconut · 2026-09-19

Thanks for the contribution. I've read the diff end to end against #3528 and the surrounding mainline code. On correctness and completeness I have no concerns: the three layers interlock as described (the flock is the load-bearing contract, with the pid salt and `O_EXCL` as defense in depth), every failure mode is loud, the restart/recovery paths still work, and the test adaptations cover every same-path re-Init case I could find. Overall LGTM.

One small suggestion before merge: could you update the relevant parts of `docs/source/design/store/ssd-offload.md` to document the contract and the limits of the pid salt? Concretely:

- State the ownership contract: one live client per `storage_path`; a second live client fails `Init` fast with an actionable error. Worth noting too that the lock file must not be deleted while a client is running, and that `flock` is only meaningful on local filesystems.
- Note that the pid salt only narrows the restart window: pids alias mod 4096 (`SEQUENCE_MASK`), and the flock + `O_EXCL` remain the load-bearing guards.
- While you're there: the "Physical disk cap" paragraphs that describe several instances sharing one offload directory on the same `ssd_offload_path` describe a configuration that will now fail at startup. Worth rewording so the docs don't point users at a deployment shape that no longer runs.

That would help both users and future maintainers/contributors understand the design intent. Thanks again!
