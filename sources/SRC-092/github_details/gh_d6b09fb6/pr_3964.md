## Description

This PR adds the resource-neutral Transfer Engine execution and completion
foundation used by heterogeneous resharding.

It extends the native Scatter transfer path with completion tickets for both
read and write operations. A ticket distinguishes completed transfers,
drained failures, and completion-unknown outcomes. The TENT path also preserves
completion ownership when transfer tasks are merged.

The Reshard layer introduces backend-facing transfer batch contracts,
registration leases, completion fencing, pending-operation ownership,
restart-required quarantine, and a scoped `TransferSubmission` API. Resources
and registrations are released only after a terminal outcome is known. An
unknown outcome remains fenced so callers cannot reuse or free affected memory
prematurely.

This layer is resource-neutral. Model-weight validation, N-D lowering,
Reader/Sink adapters, Store persistence, and framework integration are handled
by later PRs.

Related RFC: #3111

### staryxchen · 2026-09-22 · COMMENTED

Two behaviors need a decision before merge:

1. TENT `submitScatter` no longer uses `submitTransfer`. The new path requires a cancellable transport, rejects staging, and disables runtime-queue admission and auto failover. TCP and the other transports whose `supportsCancellation()` is false fail the whole batch, and `Status::Context` hides the `NotImplemented`. Please document that contract on `submitScatter` and test it through the public API, or keep non-cancellable routes on the normal submit path.

2. A drained one-fragment legacy task is always `failPending`'d. Grouped tasks consult per-slice status; a single request whose slices already succeeded is still reported as failure, and its callback runs after `freeBatch`. Please derive that outcome from the slice counters.

The `slice_count == 0` fast path, the `USE_EVENT_DRIVEN_COMPLETION` race on the forced `is_finished` store, and stale `type` / `sub_task_id` on derived tasks after poll-stage failover are inline. The first two are safe if the transport contract and the non-event-driven build are what you intend; the third is safe for the call sites this PR updates.
