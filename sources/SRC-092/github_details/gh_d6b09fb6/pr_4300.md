# [PR #4300] [Bugfix][Python] Use the buffer byte length instead of the element count in put and upsert

source: https://github.com/kvcache-ai/Mooncake/pull/4300
state: open | updated: 2026-09-24T16:04:35Z

## 正文

## Description

`put`, `upsert`, `put_batch` and `upsert_batch` in `mooncake-integration/store/store_py.cpp` built their value span from `py::buffer_info::size`. In pybind11 that is the number of elements, not bytes, so any non-byte buffer (a numpy `float32` array, `array.array("f")`, a multi-byte `memoryview`) was silently truncated to one byte per element while the call still returned `0`. Strides were also ignored, so a non-contiguous view stored the wrong bytes. `put_parts` and `upsert_parts` already guarded against this; the four functions above did not.

This PR adds one helper, `contiguous_buffer_span`, that returns `size * itemsize` bytes and raises `ValueError` for a strided buffer, and uses it in the four bindings. The check runs before the GIL is released. Byte inputs behave exactly as before; contiguous typed buffers now store their full contents; strided views are rejected instead of being mis-stored. `put_parts` / `upsert_parts` are unchanged.

Fixes #4299

## How Has This Been Tested?

Added `test_put_typed_buffer_stores_all_bytes` to `mooncake-wheel/tests/test_dummy_client.py`. It puts, upserts and batch-puts an `array.array("f")` of 1024 elements and checks that `get_size` and `get` return all 4096 bytes, then checks that `memoryview(...)[::2]` raises `ValueError` and stores nothing. It runs on the dummy client, so it needs no master, and this file is already part of `scripts/run_tests.sh`.

The helper was also compiled on its own with g++ 13 (`-std=c++20 -Wall -Wextra -Werror`) and exercised against plain bytes, a float array, a 2-D C-contiguous array, size-1 dimensions, empty shapes, a `[::2]` stride and a Fortran-order array; all cases behave as expected.

### he-yufeng · 2026-09-23 · COMMENTED

Read this line by line against main. The fix is right and complete.

The byte-length change (`size * itemsize`) is the actual repair for #4299, and the stride walk in `contiguous_buffer_span` is the correct C-contiguity test: it exempts size-1 dims (their strides carry no meaning), rejects reversed or sliced views by mismatch, and leaves `ndim == 0` scalars alone. Throwing `py::value_error` maps to Python `ValueError`, which is what the test asserts. GIL ordering is respected at every call site: the helper may raise, and all four callers invoke it before `gil_scoped_release` (the batch loops included, where the span is built inside the `infos.emplace_back` loop ahead of the release).

Coverage matches the bug surface exactly. Main has six `info.size`-as-bytes constructions; two of them are `put_parts`/`upsert_parts`, which already enforce `ndim == 1 && itemsize == 1`, so `size == bytes` there and they were never wrong. The four this PR touches are precisely the four unguarded ones the issue named.

The tests do the thing that matters: a typed `array('f', ...)` round-trips through put, upsert, and put_batch with `get_size` and `get` assertions, and a strided view is rejected instead of stored wrong. CI ran all of it green across the wheel lanes.

One non-blocking observation, for a follow-up if anyone cares: after this, `put`/`upsert` accept typed buffers while `put_parts`/`upsert_parts` still reject `itemsize != 1`. Both behaviors are now loud and correct, so nothing is on fire, but the two surfaces will answer the same numpy array differently. Aligning the parts variants later (same span helper) would make the binding feel of one piece.

Good to land from my reading.
