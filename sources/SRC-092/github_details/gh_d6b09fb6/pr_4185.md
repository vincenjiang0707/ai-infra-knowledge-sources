## Description

`mooncake_client` crashloops on startup when `MC_LOG_DIR` points to a valid, writable directory (observed on a 0.3.12 source build; glog >= 0.6.0 CHECK-fails with `You called InitGoogleLogging() twice!`).

Order of events:

1. `mooncake-transfer-engine/src/transport/rdma_transport/worker_pool.cpp` evaluates `globalConfig()` from a **static initializer before `main()`**; `loadGlobalConfig()` sees `MC_LOG_DIR`, calls `InitGoogleLogging()`, and — for a valid directory — also sets `FLAGS_log_dir`.
2. `main()` (`real_client_main.cpp`, init added in #1925) then sees a non-empty `FLAGS_log_dir` and calls `InitGoogleLogging()` a second time → CHECK fail.

The guard added in #3727 covers the opposite order (a host program pre-initializes glog before loading mooncake) and cannot help here: in a standalone binary, `loadGlobalConfig()` is the *first* initializer, so the guard lets it through and `main()` still double-initializes. `master.cpp` has the same unguarded pattern (identical crash once `MC_LOG_DIR` is set for the master).

**Fix**: extract the version-conditional "already initialized" check from `config.cpp` into `mooncake-transfer-engine/include/glog_compat.h` as `mooncake::InitGoogleLoggingOnce()`, and use it in both standalone mains and in `config.cpp` — one implementation instead of three diverging copies. A regression test reproduces the static-init-then-main order on top of the existing `glog_preinitialized_test`.
