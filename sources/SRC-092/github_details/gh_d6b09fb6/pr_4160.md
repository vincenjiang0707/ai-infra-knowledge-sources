## Description

Implements the **P01 codec evidence experiment** in #3808 without changing production persistence or writer selection.

**Depends on #4141 (W02), pinned to `e92af584fa106668c3e311b66e1592bd8922b42b`.** This is a separate dependent branch, not an addition to the W02 PR. Until W02 merges, this draft's main-based diff includes its two prerequisite commits; the P01-specific commit adds only `benchmarks/oplog_codec/`. Rebase/drop those prerequisites after #4141 merges.

- Compare production JsonCpp JSON, a same-library nlohmann JSON/base64 control, CBOR, and MessagePack using production batch validators/checksums.
- Add six opaque-payload profiles and five generated production-schema profiles with actual struct_pack metadata/Segment serialization.
- Exercise the latest asynchronous durable awaiter through production writer/storage and a test-only backend bridge on isolated real etcd namespaces.
- Restart etcd, audit every acknowledged operation, replay through production OpLogApplier/StandbyMetadataStore, and check fencing/corruption and duplicate replay.
- Publish two complete raw measurement passes, summaries, environment/hash metadata, and the eight-case E2E report under `benchmarks/oplog_codec/results/2026-09-16/`.

Generated-schema payload sizes shrink approximately 24–26%. Final-pass observed CPU ratios versus the same-library control span 3.00–14.36× encode and 1.37–3.57× decode. These are shared-host codec microbenchmarks with substantial variability, **not service-throughput gains or a CBOR/MessagePack selection**. The test bridge's transcoding overhead is not timed. RPC/HA promotion/resource rebuilding is outside scope; P02/P03 remain conditional.

This is benchmark/test-only work covered by the P01 roadmap, not a >500 LOC production architectural change. Kept draft for the W02 dependency and human review.

### he-yufeng · 2026-09-16 · COMMENTED

Verified the experiment end to end, and it holds up unusually well.

Scope and hygiene check first: the P01 commit (39f7a7ad) touches only `benchmarks/oplog_codec/`, so the "no production persistence or writer selection change" claim is literal, and the two W02 prerequisites are separate commits with the draft pinned to e92af584 exactly as the body says. The dependent-branch story is clean.

Methodology check: `candidate_codecs.cpp` includes production `ha/oplog/oplog_batch_codec.h` and `common/base64.h`, so the candidates run through the production batch validators and checksum pipeline rather than a reimplementation. The etcd E2E requires `P01_ETCD_ENDPOINT` and connects via `EtcdHelper::ConnectToEtcdStoreClient`, i.e. a real etcd 3.7.1 server, not a shim. The same-library JSON/base64 control is the right design for separating library choice from format choice, and RESULTS.md is honest about the rest: no CPU isolation or frequency pinning, min/max is not a confidence interval, no fine-grained CBOR/MessagePack ranking claimed, and the nlohmann-based MessagePack candidate disclosed rather than presented as msgpack-cxx.

The evidence itself: ~24-26% size reduction for CBOR/MessagePack across the production-schema profiles, 269 codec checks, 50/50 W02 tests plus TSan clean, and 8/8 real-etcd persist/restart cases including the lifecycle audits (tenant isolation, replica identity, duplicate idempotence, corrupted-record rejection). Two passes committed separately is the right call given the repetition-id restart.

One thing to double-check before this feeds P02: the E2E's descriptor memory addresses are fixtures per RESULTS.md, so the replay verification covers metadata/schema fidelity but not rebuilt serving buffers or resources. Worth stating explicitly in the P02 gating notes whether that gap matters for the codec decision or only for a later rollout decision. Otherwise this is exactly the standard an evidence experiment should hit.
