## Description

Fixes #4003.

`RedisStoragePlugin` in `mooncake-transfer-engine/src/transfer_metadata_plugin.cpp`
held a single long-lived `redisContext` and never rebuilt it. hiredis latches any
I/O error into the context and rejects every subsequent command, so **one
disconnect permanently disabled metadata publishing and lookup for the rest of the
process lifetime**: `get()` / `set()` / `remove()` returned false forever, segment
registration and lookup failed, and only restarting the process recovered.

We hit this in production with a managed Redis reached through a TCP load balancer
that reclaims connections idle for more than ~4000s. The connection is only touched
on segment (un)registration and on the first lookup of a given remote segment, so it
sits idle for hours; with no TCP keepalive nothing is sent during that window and the
load balancer silently reclaims the socket. Redis itself stayed healthy the whole
time — the broken state lived entirely in the client's cached context, so restarting
Redis did not help.

### What changed

1. **Reconnect and retry once on connection-level failure** (`execLocked`). Only null
   replies are retried: a `REDIS_REPLY_ERROR` means the server answered and rejected
   the command, so retrying cannot help. GET/SET/DEL are idempotent, so the retry is
   safe.
2. **AUTH/SELECT moved into the connect path** so they are replayed on every
   reconnect, and a construction-time failure is no longer terminal. Previously, a
   Redis that was unreachable at startup left `client_` null forever.
3. **Connect timeout, command timeout and TCP keepalive.** There was previously no
   timeout at all, so a slow or blackholed Redis could block the caller indefinitely
   while holding `access_client_mutex_`. The 3s values match the Redis client already
   used by Mooncake Store HA
   (`mooncake-store/src/ha/common/redis/redis_connection.cpp`). Keepalive matters
   because this connection is idle for long stretches, and the command timeout is what
   makes recovery work when a middlebox drops the flow without resetting it.
4. **`getWithStatus()` routed through the same retry path.** #3072 added that override
   so `syncSegmentCache()` can tell an absent key from a backend outage, but it issued
   its own `redisCommand()` with `if (!client_) return kUnavailable;` and no reconnect.
   Rebasing onto current main without touching it would have left #4003 reproducible
   through that entry point, and `syncSegmentCache()` calls it periodically. `get()` now
   delegates to it, which also removes the duplicated GET handling. A null reply after
   `execLocked()` means the backend is unreachable, so it maps to `kUnavailable` and
   never to `kNotFound`, preserving the invariant #3072 added.
5. **CI now executes the Redis regression tests.** The job that runs `ctest` configured
   the tree without `-DUSE_REDIS=ON`, so the suite was compiled but never run; the job
   that enables `USE_REDIS` builds without running `ctest`. Adding the flag is enough —
   `dependencies.sh` already installs `libhiredis-dev` on that runner and the top-level
   `CMakeLists.txt` calls `enable_testing()`.

No public interface changes. `MetadataStoragePlugin::Create()` could already return a
plugin with a dead connection, and no caller inspects connectivity, so behaviour for
callers is unchanged apart from now recovering.

One observable change for operators: `get()` now logs a nil reply at WARNING instead of
ERROR. An absent key is an expected outcome when resolving a segment that is not
registered yet, so the previous level reported a normal lookup miss as an error. The
message text is unchanged (`RedisStoragePlugin: unable to get <key> from <uri>`), so
anything matching on the text still matches, but alerting that keys on ERROR level will
no longer fire for lookup misses. The connection-level failure path — which is what
actually indicates a problem — is unaffected.

**Production validation:** the reconnect, timeout and keepalive changes have been
cherry-picked onto v0.3.11.post1 and run for 5 days in a prefill/decode disaggregated
deployment on 8 H800 nodes, against the same managed Redis behind an L4 load balancer
described in #4003, where idle connections are reclaimed after roughly 4000s. Before the
patch the failure was fully deterministic there: SGLang (Store client) was restarted
roughly every 4 hours, and every restart reproduced it. The two intervals are different
things — the load balancer reclaims the connection about 4000s after the last Redis
access, but the dead context is only discovered at the next metadata operation, and a
restart is what forces those segment registrations and lookups to happen. Once
discovered, metadata publishing and lookup stayed broken for the remaining lifetime of
that process. After the patch the same restart cadence has not reproduced it once over
the 5-day run; a reclaimed connection now shows up only as a single warning followed by
a successful retry:

    RedisStoragePlugin: SET mooncake/ram/<segment> failed on <host>:6379: Server closed
    the connection; reconnecting and retrying once

To be precise about what that run covers: the deployed build predates `getWithStatus()`
(added by #3072), so the routing of that entry point through the same retry path is
covered by the unit tests above rather than by the production run.

CI coverage: the job that runs `ctest` previously configured without `-DUSE_REDIS=ON`,
so these tests were compiled but never executed. This PR adds the flag to that job, so
`transfer_metadata_redis_plugin_test` now runs in CI. It needs no Redis server.

### Known limitations, called out deliberately

- **No reconnect backoff.** While Redis is unreachable, every operation now attempts a
  fresh connection instead of failing immediately, and it does so while holding
  `access_client_mutex_`. Worst case for a blackholed Redis is roughly command timeout
  plus reconnect plus command timeout. This is still bounded, whereas before this PR
  the same situation could block forever with no timeout at all, but if maintainers
  prefer a cooldown (skip reconnect attempts for N ms after a failure) I am glad to
  add one.
- **SIGPIPE.** Writing to a socket the peer has closed can raise SIGPIPE on Linux, and
  no Mooncake code installs `SIG_IGN`. This exposure is unchanged by this PR — the
  pre-existing code issued the same write on the same dead socket — so it is not
  addressed here, but it seems worth a separate look.
- **`set`/`remove` do not inspect `reply->type`.** A server-level error such as
  `-READONLY` during a failover is still reported as success. This is pre-existing
  behaviour, left untouched to keep the diff focused, and tracked separately as
  requested.
