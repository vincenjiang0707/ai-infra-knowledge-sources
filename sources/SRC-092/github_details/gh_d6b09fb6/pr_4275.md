## Description

Contributes to #3809 by extracting internal ownership of the master metrics
bootstrap settings without introducing a new public configuration schema.

This PR pilots Phase 2 configuration ownership on the master metrics bootstrap settings:

- introduce `MetricsBootstrapConfig` as the owner of metrics bootstrap defaults;
- resolve the existing flat keys and explicit command-line overrides in one place;
- preserve the existing precedence `defaults < flat configuration keys < explicit command-line flags`;
- reject an effective metrics port outside `0..65535` before it is narrowed for the HTTP server;
- pass the owned configuration through both HA and non-HA master startup paths while preserving the existing serving-layer compatibility fields.

Existing configuration keys and command-line flags remain supported. Ports `0`
and `65535` are valid; larger values and negative CLI values now fail startup
with an error. Public grouped keys are left for a separately reviewed schema
change.

## 评论 (2)

### Icedcoco · 2026-09-23

Thanks for putting this configuration ownership change together. The new MetricsBootstrapConfig and centralized precedence handling make the startup flow easier to follow, and the existing compatibility paths are preserved for normal values. I have two points that may be worth discussing before merging.

1. Port range validation

    In mooncake-store/src/config/metrics_bootstrap_config_loader.cpp:16, metrics_port is loaded as uint32_t and later narrowed to uint16_t in the serving configuration. This means values such as 65536, UINT32_MAX, or a negative CLI value can be silently converted to a different port.
    
    I realize this behavior was already possible through the old path, and the compatibility goal is understandable. Since this loader is now becoming the owner of the metrics bootstrap settings, would it make sense to validate the value here and reject ports outside the supported range? Keeping 0 valid, if it is intentionally used for an automatically selected port, would also be fine. A few boundary tests for YAML/JSON/CLI inputs would make the intended behavior clear.

2. Structured configuration format

    The new bootstrap.metrics.* keys are a useful step toward the configuration model described in #2694. At the same time, #3809 currently describes structured configuration as a later phase whose schema and compatibility design still need to be reviewed.
    
    Could we confirm that this grouped format is considered stable enough to introduce in this PR? If so, it may be helpful to add a small example to the master configuration files or documentation, along with the expected behavior for invalid or unknown grouped values. Otherwise, we could keep this PR focused on the internal ownership refactor and introduce the public grouped keys after the schema has been agreed upon.

The current CI results are all green, so these are mainly questions about configuration safety and the long-term compatibility contract rather than concerns about the normal startup path.

### bitborne · 2026-09-23

Both points are addressed in follow-up commits.

1. The loader now validates the effective metrics port before the `uint16_t` conversion. Ports `0..65535` are accepted; larger values and negative CLI values cause a startup error instead of silently binding a different port. Boundary tests cover YAML, JSON, and CLI inputs, and I checked the master process exits with an error for `--metrics_port=65536` and `--metrics_port=-1`.

2. I removed parsing for `bootstrap.metrics.*` and its tests. The PR accepts the existing flat file keys and CLI flags. A public grouped format can follow once the schema and compatibility contract in #3809 have been reviewed.
