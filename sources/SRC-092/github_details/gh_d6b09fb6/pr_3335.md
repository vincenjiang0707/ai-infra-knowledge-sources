## 正文

## Description

Add a default-off, Provider-owned EGM Store pool for RFC #2914. HOST_NUMA
allocations are mounted as ordinary NVLink Store segments; the Master schema,
placement policy and Consumer Put/Get API are unchanged.

This is **[2/3]**: #2966 supplies the merged Transfer Engine prerequisite,
this PR adds the Store pool, and #3431 enables direct remote GPU reads. This
branch is based on `main`; #3431 remains its child.

## Implementation

- `enable_egm_store_pool` enables the pool; `egm_numa_nodes` selects `auto` or
  a comma-separated NUMA list. EGM requires `protocol=nvlink`, nonzero global
  capacity and `local_buffer_size=0`. The parsed config is passed explicitly
  through a private setup overload; auto-discovery is a named mode, not an empty
  node-list sentinel. Positional setup keeps EGM disabled.
- The normal Client initialization path can now install `nvlink` with
  discovery disabled. An EGM Provider checks the actual engine before allocating:
  it must be classic Transfer Engine with NVLink installed, not TENT or a
  different transport selected by discovery.
- The existing global-segment loop allocates and mounts EGM before local
  services start. RealClient directly owns the native HOST_NUMA allocations.
  Capacity is rounded down to the largest Store/CUDA alignment, divided across
  the selected nodes and balanced into chunks using the existing helper.
  `max_mr_size` applies only to the EGM branch, not all NVLink registrations.
- Cleanup is terminal. After callers quiesce in-flight requests, close stops
  local services and EGM offload workers, unmounts EGM segments, then
  releases backing memory. A failed unmount or CUDA release retains the affected
  allocation until process exit and logs the error; other cleanup continues.
  `close()` reports failure but clears the Python client's native references.
  Calling it again does not retry resource recovery.
- Failed or throwing mounts go through the same teardown. If there is a Client
  record, cleanup can unmount and release the allocation; a missing record or
  failed unmount retains it. The outer setup catch also covers later exceptions
  such as FileStorage construction, then rethrows. This does not promise
  synchronous removal of an uncertain remote record.

The earlier factory/hooks, caller-supplied UUID transaction, retry state machine
and global Python setup guard have been removed. Generic mount/MR failure cleanup
stays with #2336; the Python repeated-setup contract is tracked in #4294.

### Configuration

Use `MC_MS_AUTO_DISC=0` on both Provider and Consumer for explicit NVLink setup.
If discovery is enabled, `MC_FORCE_MNNVL=1` selects MNNVL on hosts with RDMA
HCAs; the EGM Provider still checks what was actually installed. Full
Provider/Consumer examples are in the updated Python API and supported-protocols
documentation.

### MNNVL bandwidth

`EGM → HBM` means a Consumer GPU reading Provider EGM. `HBM → EGM` means a Consumer GPU writing Provider EGM.

| Direction | Single-GPU sustained p50 | Four-GPU aggregate p50 |
|---|---:|---:|
| EGM → HBM | 211.77–211.90 GB/s | 390.62 GB/s |
| HBM → EGM | 193.66–193.88 GB/s | 336.98 GB/s |

The scan selected 4 GiB with one stream for both directions. Increasing the payload from 2 GiB to 4 GiB changed throughput by only 0.025% for EGM → HBM and 0.014% for HBM → EGM, so the matrix reached a clear plateau. Sustained-run variation was well below the 5% stability limit.

For context, `nvidia-smi c2c -s` reported a per-GPU C2C capacity sum of 223.56 GB/s on these nodes. The measured single-GPU results are approximately 94.8% and 86.7% of that runtime-reported value; these ratios are not a general NVLink-utilization metric. The separate 450 GB/s architectural reference uses a different reporting basis and is recorded only for comparison, not as a pass threshold.

### Store path

- Put aggregate p50: 191.10 GiB/s

The Provider publishes approximately 150 MiB Store segments, so logical payloads larger than one segment were tested as batches of Store objects no larger than 128 MiB each. These numbers measure aggregate Store throughput; they do not imply that one Store key spans multiple segments.

### neverhook · 2026-09-24

@Aionw, I've reworked this around the existing Store path. The earlier version had grown a separate lifecycle around EGM, with interfaces used mainly by the tests. I agree that was too much machinery for adding another kind of segment backing.

NVLink now uses normal transport initialization. EGM allocation and mounting run in the existing segment loop, before the IPC/HTTP servers start, and RealClient owns the native HOST_NUMA allocations directly. The factory, allocation adapter, hooks, caller-supplied UUID transaction and retryable-close state machine are gone.

I kept the `max_mr_size` cap local to EGM. Moving it into the generic NVLink path would also change ordinary registration and dynamic mounts, which this pool doesn't need.

Close still checks each EGM unmount result: `Client` destruction only logs failures, so it cannot tell the allocation owner whether Master cleanup succeeded. FileStorage workers stop first because they can still access those segments. A failed or uncertain mount/unmount retains the allocation until process exit; a CUDA release failure retains whatever resources remain. Close reports the error and finishes without keeping a client for another cleanup attempt. This trades reclamation after an error for a simpler lifecycle. It still requires callers to quiesce in-flight requests before close and does not promise immediate remote cleanup.

Generic mount/MR rollback remains outside this PR; related work is in the separate, still-open #2336. The Python repeated-setup guard is also removed, with that API decision tracked in #4294. Tests now focus on config/capacity rules and real Client initialization.

CI is green, including the full CTest sweep and docs build. This revision has not been rerun on GB200; the earlier hardware results aren't validation of the new cleanup behavior.

Could you take another look, particularly at the EGM-only cap and explicit unmount checks? I've left those two inline discussions open for your confirmation.

### Aionw · 2026-09-23 · COMMENTED

The EGM ownership model still makes sense. However, most of the Store-side complexity in this revision is there so that each step can be injected in unit tests; production does not need it. Two facts already in the tree make most of it unnecessary:

1. `NvlinkTransport` recognizes HOST_NUMA ranges by exact address (`FindExactOwnedRange`), so an EGM chunk can be mounted through the ordinary `Client::MountSegment(ptr, size, "nvlink")`.
2. The existing global-segment path already has a teardown order: `~Client` unmounts every entry in `mounted_segments_`, and RealClient frees the backing memory afterwards. `NvlinkHostNumaAllocation` is already an RAII owner whose destructor calls `Release()`.

Suggested shape:
- Add an `nvlink` case to `Client::InitTransferEngine`, next to ascend/ubshmem/sunrise_link, and drop the manual TE factory.
- Allocate EGM chunks as one more branch of the existing allocation loop in `setup_internal`. Hold them in `std::vector<std::unique_ptr<NvlinkHostNumaAllocation>>`, mount them through the same `MountSegment` call, and release them after `client_.reset()`.
- On release failure, leak and log, as `setup_segment_memory_must_leak_` already does.

With that, the following can be deleted: `client_internal.h`, the `SegmentMountOperations` seams, the `EgmStorePoolHooks`/allocation interface, the retryable Setup/Rollback/Teardown state machine, the cleanup-pending setup guard, and most of `egm_store_pool_test.cpp`. The Store part should shrink substantially. Details inline.

This partly revisits my earlier comments. Injecting a pre-built TE and sharing a caller-supplied-ID mount transaction ended up needing more seams than they save; a transport case in `InitTransferEngine` plus the existing `MountSegment` is simpler.
