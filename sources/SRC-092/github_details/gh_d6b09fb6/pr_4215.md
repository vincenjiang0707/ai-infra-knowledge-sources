## Description

The tenancy layer of the tenant-first metadata model ([RFC #3670](https://github.com/kvcache-ai/Mooncake/issues/3670)), split out of #3822. It adds the two types that own per-tenant metadata, under `mooncake-store/include/metadata/`, with unit tests and one benchmark. Nothing resolves through them yet, so runtime behaviour is unchanged.

The object-model types it composes (`ObjectEntry`, `ObjectIndex`, `GroupIndex`, `DynamicReplicationLeaseTable`) are already in `main` from #4161, so this diff is the tenancy layer alone.

The types:

- `metadata::TenantRegistry` — tenant id to a strong handle to that tenant's metadata, plus the lifecycle rules around it. The table is copy-on-write: a lookup is one acquire load of an immutable frame plus one map find, and a create or a remove copies the frame and publishes the replacement. One `Tenant` per id, created atomically through a factory bound at construction, and the handle is a `std::shared_ptr` rather than a template parameter, so the guarantee that a loaded frame stays alive is structural.
- `metadata::Tenant` — one tenant's metadata: the object route (`ObjectIndex`), the group table (`GroupIndex`, membership plus one shared replica-action lease per group), the in-flight replica-action lease table, the promotion-candidate index and the bound quota account. Those interfaces are private, and callers go through the tenant's own operations.

What the layer guarantees, and where each guarantee lives:

- **Reads take no lock.** `TenantRegistry::Lookup` loads the published frame, and the handle it returns keeps that frame alive, so a publish in flight cannot invalidate a lookup.
- **A tenant is built once.** `GetOrCreateTenant` re-checks under the write lock before running the factory, so concurrent callers for an absent tenant all receive the winner's handle, and only one tenant is built — fully initialized before it is published.
- **A walk sees one frame.** `Visit` passes const handles taken from the frame it loaded, so a callback cannot replace a published entry; a publish made from inside the callback is visible to the next walk only.
- **A handle keeps an entry alive, not current.** `TenantRegistry::Remove` drops a tenant from the registry while handles callers already hold stay valid, and a later create for the same id builds a fresh tenant. An object is recognised by the handle the route publishes: an entry instance stands for exactly one publication, which `ObjectIndex::Insert` asserts, so `EraseObjectIf` compares handles and no caller records a number to tell its object apart from a replacement.
- **Publication and teardown are atomic per object.** `Tenant::InsertObject` wires the route slot and the group lease under the entry's own lock, so a grouped object is never reachable before its group lease is in place, and a rejected insert registers nothing. `RemoveObject` is the single teardown entry point: it drops everything a key carries — route slot, group membership, the replica-action leases of that key and its promotion-candidate index entry — so those records cannot be left disagreeing about a key. `ResetDynamicReplicationState` is the other path that ends a lease: it clears the pending proposal, the cooldown and the leases while leaving the object routed.
- **A teardown cannot outrun a republish.** `RemoveObject` settles ownership and drops a key's records under one hold of the route lock. A slot still holding the entry means the records are its, so they go with the slot; a slot holding another entry means a newer publication of the same key owns them, so none of them is touched; an empty slot means no publication owns them, so they go as well, which is what undoes the records a publish registered before it failed. A teardown therefore never drops what a newer publication of the same key just registered.
- **Lock order runs one way: entry lock, then the route lock, then the tenant's own indexes.** Nothing is held across a public call except in `RemoveObject`, which holds the route lock while it drops a key's records for the reason above; nothing takes the route lock while holding one of those indexes. `RemoveObject` requires the caller to hold the entry's own lock, which is what keeps a publication still wiring its state from being torn down half-registered.

### Aionw · 2026-09-24

I pushed commits on top of `3f8e1233`. Here is what the refactor and the CI change do and why, so you don't have to reconstruct it from the diff:

**`3d194bbe` refactor(store): keep Tenant to routing and group lifecycle**

- **Lease table and promotion index are out of `Tenant`.** They are other subsystems' state, and they were only here because `TenantState` had them. Keeping them here is what made `RemoveObject` hold the route lock across their locks. That meant a `Get` could end up waiting on a full `EraseExpired` sweep or a `PromotionCandidateKeys` copy. At cutover, the idea is for each subsystem to validate what it holds against the entry the route publishes before acting on it, rather than have `Tenant` retract it eagerly. The subsystem can still clean up after `RemoveObject` as an optimization.
- **`RemoveObject` only acts when the slot holds the entry.** It drops the slot and the membership only in that case, and otherwise touches nothing. The "empty slot still clears records" branch existed for records registered after removal, and those can no longer end up in `Tenant`.
- **`EraseObjectIf` is gone.** Since `InsertObject` wires the slot and the membership in one step, erasing only the slot always left a grouped entry's membership behind.
- **The quota account is passed to the `Tenant` constructor by the factory.** No `Bind` is needed: `TenantQuotaTable` keeps one stable account per tenant id and never erases it, and a policy recompute updates the account in place.
- **`TenantRegistry` is one map under a `shared_mutex`.** It replaces the copy-on-write frame. libstdc++'s `atomic_load(shared_ptr)` takes a mutex hashed by address, so every lookup was serialized anyway. A standalone microbenchmark shows the read lock 1.4–2.3x faster at 1–16 threads. The factory now runs outside the lock, so it can take the quota table's lock without nesting. A losing racer's build is dropped, which means the factory must not have side effects that can't be repeated. `Visit` copies the handles and walks them unlocked.

The tests follow the point of this layer, which is concurrency:

- **`SameKeyChurnKeepsTheRouteAndTheGroupConsistent`.** Writers, stale removers (tearing down whatever handle `Get` returns), `WithPublishedObject` mutators and a two-key observer all run on one group. The run checks that a mutation only lands on the live, published entry, that two live members share one lease, and that at rest the group lists exactly the routed keys. Every teardown follows the caller protocol: claim `is_torn_down` under the entry lock, then call `RemoveObject`.
- **`MixedLookupCreateRemoveAndVisitStayConsistent`.** All four registry operations run together, including create and remove from inside a `Visit` callback.
- **`ConcurrentMembershipAcrossStripesStaysConsistent`.** Concurrent add/remove on `StripedGroupIndex<4>` across colliding groups.

These replace `AGroupSurvivesConcurrentReplacementOfItsKeys` and `LookupsDuringWritesSeeOneWholePublish`. To check they catch real bugs, I tried two mutations. Dropping the membership outside the route lock failed 3/3 runs. Wiring the group lease outside the entry lock also failed 3/3, and it left orphan members behind.

**`881b26f6` ci: run the metadata concurrency suites under TSAN**

This adds an `ENABLE_TSAN` option and a `tsan-tests` CI job, gated like `unit-tests`. It builds only the five object-model/tenancy suites under TSAN and runs them, so a data race fails CI even when no assertion trips. Locally, all five pass under TSAN with no reports.

**Open for the cutover, not this PR:**
1. **Tenant reclamation.** `Remove` and an emptiness check are not atomic with writers holding an old handle; `RemoveDropsTheTenantButNotTheHandle` shows such a write landing in a tenant the registry has already dropped. We need to decide who calls `Remove`, and under what exclusion from in-flight writes.
2. **Teardown protocol.** `RemoveObject` requires the caller to hold the entry lock, but only the comment says so. Worth an assertion, or a teardown entry point that takes the lock itself.
3. **`WithPublishedObject` returning false.** False can mean "absent" or "lost a race to a replacement". Retrying internally would leave false meaning only "absent".
4. **Route striping.** The route is one `shared_mutex` per tenant, while main shards the default tenant 1024 ways. Critical sections are small, but an `unordered_map` rehash under the exclusive lock stalls the whole tenant. Let's decide this with a benchmark against main rather than up front.

### he-yufeng · 2026-09-19 · COMMENTED

Design-conformance review against RFC #3670, reading the three types and their tests. As an additive slice with no runtime wiring, what this can be checked for is self-consistency with the RFC's ownership model, and it holds.

The RFC's spine is "tenant registry COW snapshots, one lock per object entry". `TenantDirectory` implements exactly that: acquire-load snapshot + map find for reads, copy-publish under a write mutex for the rare creates/removes, so an in-flight lookup keeps its frame alive through a concurrent publish (the stated reason COW exists at all). `MetadataCatalog` adds the lifecycle rule the RFC needs: a tenant is created atomically inside the write lock, fully initialized (quota bound) before its handle is published, and every racer observes the same winner. `TenantCatalog` keeps one internal lock per container and wires the route slot + group lease under the entry's own lock, so a reader reaching an entry through the route can't observe a grouped object before its group lease exists.

The invariants aren't just comments: `RemovingATenantKeepsAnOutstandingHandleAlive` pins alive-not-current (the old handle keeps value 7 while the recreated tenant reads 99 under a different pointer), `GetOrCreateGivesEveryRacerTheWinningHandle` pins the single-winner guarantee with actual racers, and `LookupsDuringWritesSeeOneWholePublish` pins snapshot atomicity. The honest constraints are documented where a future caller needs them (factory runs under the write lock and must not re-enter; `Visit` walks one frame and a publish joins the next walk).

Two notes for the wiring slices that follow, not for this one: the RFC moves the mutation boundary to one lock per `ObjectEntry`, and this slice's containers make that promise locally; the integration risk (callers holding a stale handle across a same-key replacement) is already named by the "resolve through the route again + identity-check before mutating" rule, so the wiring PRs should show that discipline at their call sites. And since nothing resolves through these types yet, this slice is safe to land on its own, which the description states and the diff confirms.
