## 正文

## Description

Fixes #3546.

`hipIpcGetMemHandle` always exports the entire `hipMalloc` allocation, but the
HIP IPC registration path recorded the caller's sub-range address as the buffer
base. The reader's relocation (`dest_addr - entry.addr + shm_addr`) therefore
collapsed every sub-range onto the allocation base, and each buffer silently
returned the first buffer's bytes with `rc=0`. Framework caching allocators
sub-allocate constantly, so any caller registering individual tensors out of one
allocation is affected — including `batch_register_memory`, which loops over the
same function.

The CUDA IPC paths had exactly this bug and it was fixed by registering the
allocation base instead of the requested range — #1622 for
`intranode_nvlink_transport` and #1831 for TENT. The HIP port was missed: its only
`hipMemGetAddressRange` calls are in the fabric-memory branch and in the free
logic, never in the IPC branch. This applies the same fix there: resolve the real
base with `hipMemGetAddressRange`, skip allocations already exported, take the IPC
handle for the base, record the whole allocation in `BufferDesc`, and key
unregistration off that base as well, matching
`IntraNodeNvlinkTransport::registerLocalMemory` and `unregisterLocalMemory`.

Thanks for the validation and analysis — I reproduced the same table on MI308X and agree the root cause is that all transports share one buffer list in the local segment, where removeLocalMemoryBuffer matches by addr only, so a same-address entry from another transport can be deleted by mistake.

Two directions to fix:
A. Ownership (general): add an unconditional owner field on `BufferDesc` and match addr && owner on remove which immunizes every transport pair (incl. nvlink/maca), but touches ~12 transports; better as a follow-up PR.
B. Predicate removal (small, this PR): add a removeLocalMemoryBuffer(addr, pred, update_metadata) overload where a transport removes only entries it recognizes as its own; HIP's descs are the only ones with a non-empty shm_name (serialized IPC handle), so that's an exact discriminator; touches only transfer_metadata.{h,cpp} + hip_transport.cpp.
 
I'm inclined to go with B here and A as a follow-up — @Lzy17 does that work for you?

  both go beyond what we reported.

  One thing we should have caught in our first comment: B makes ownership opt-in per
  transport, and only TCP and HIP opted in. `RdmaTransport` still calls the match-all
  overload at `rdma_transport.cpp:374`, `:567` and `:619`. `transport_map_` is a
  `std::map`, so `listTransports()` yields hip before rdma — HIP's base-keyed desc is
  appended first, and RDMA's unfiltered removal takes it.

  Same allocation, `v0` at the base, all four registered, then unregistered in
  ascending order — no repeated or unpaired call anywhere:

  | build | transports | v0 | v1 | v2 | v3 | re-register v3 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 16ebc541 | rdma+hip | 0 | 0 | 0 | 0 | 0 |
  | 4fc9c99f | tcp+hip | 0 | 0 | 0 | 0 | 0 |
  | **4fc9c99f** | **rdma+hip** | 0 | 0 | 0 | **-3** | **-7** |

  `unregister(v0)` has HIP only decrement its refcount, so RDMA's match-all removal
  erases HIP's desc instead of its own; the last alias then finds nothing, and
  `TransferEngineImpl::unregisterLocalMemory` returns on `first_error` before
  `eraseMemoryRegionLocked`, so the VA can no longer be re-registered
  (`ERR_ADDRESS_OVERLAPPED`). Unregistering in descending order is clean, which is the
  ordering dependency. Your own new `test_base_address_view_double_unregister` also
  fails on 4fc9c99f in an rdma+hip engine and passes in tcp+hip.

  This matters for us specifically because SGLang's ROCm image builds
  `-DUSE_HIP=ON -DENABLE_MULTI_PROTOCOL=ON` and registers the device KV pool under
  both transports.

  We verified a fix: give RDMA the same predicate, reusing the ownership test its
  submit path already applies at `:1171` (`protocol.empty() || protocol == "rdma"`,
  so legacy untagged descs stay covered). 21 insertions in one file. With it, all
  three orderings are clean in rdma+hip, re-registration succeeds, tcp+hip is
  unchanged, and all five tests pass in both configurations. Happy to open it as a
  commit against your branch, or paste the diff here — whichever you prefer.

## Pull request overview

This PR fixes HIP IPC transfers for sub-allocated device buffers by registering and exporting HIP IPC handles at the *allocation base* (hipMalloc segment granularity), aligning HIP behavior with the previously-fixed CUDA IPC paths and preventing silent offset-collapsing on the receiver.

**Changes:**
- Resolve the true hipMalloc allocation base via `hipMemGetAddressRange()` and register IPC handles using that base + full allocation length.
- Track already-exported allocation bases to avoid duplicate IPC registrations for multiple subranges.
- Add a two-process Python regression test that reproduces and guards against sub-allocation offset corruption on HIP.
