## 正文

**Title**: `[Store] Prefetch SSD-only objects to DRAM on exist`

## Description

With SSD offload enabled, a key whose MEMORY replica has been evicted keeps serving reads from a `LOCAL_DISK` replica — paid synchronously on the get() critical path. For workloads that probe with `exist` before reading (prefix cache lookup, async scheduling), the probe is a strong, early "will read soon" signal.

This PR adds an **opt-in, best-effort** prefetch: `is_exist` / `batch_is_exist` with `ExistOptions.prefetch_to_memory=true` starts an asynchronous SSD→DRAM promotion for keys that turn out SSD-only, so the follow-up `get()` can be served from DRAM. Promotion happens inside the probe→get queueing window; if it does not finish in time, or fails, or DRAM is saturated, behavior degrades to exactly today's SSD read. No correctness contract changes anywhere.

Mechanism, briefly:

- The exist path does a per-key dedup lookup and a thread-pool enqueue only — no RPC added to the probe (a sharded `PrefetchThrottle` with TTL dedup and a DRAM-saturation cooldown).
- A bounded pool (4 threads) classifies candidates via read-only admin replica queries (no lease, no promotion-on-hit, no metrics side effects), then promotes local keys via a new `RegisterPrefetchTask` master RPC plus the **same execution chain promotion-on-hit uses** (`PromotionAllocStart → AllocateBatch → BatchLoad → PromotionWrite → NotifyPromotionSuccess`, extracted as a shared helper), or delegates to remote holders through a new additive `prefetch_offload_object` RPC.
- `RegisterPrefetchTask` is tenant-aware, holder-checked (`holder_id == client_id`), shares the `promotion_in_flight_` cap and the per-key `promotion_tasks` entry with promotion-on-hit (double promotion is impossible), and reports `PROMOTION_ALREADY_EXISTS` distinctly so best-effort callers skip quietly. `NotifyPromotionSuccess` grants the usual read lease for prefetch promotions so the DRAM replica survives until the follow-up get().
- With `ssd_get_wait_ms > 0` (default 0 = off), a batch get headed for SSD gets one demand-side promotion attempt for its disk keys (`ignore_cooldown` bypasses only the client-side throttle backoff — never a master-side gate: the shared in-flight cap, holder check, and dedup TTL all still apply). The get then waits, within **one deadline shared by the whole batch**, for promotions already in flight — and only while a local promotion is actually `kInFlight`/`kCompleted`.

Default configuration is a complete no-op: `enable_ssd_prefetch=false`, `ssd_get_wait_ms=0`.

## Relationship to prior work

- RFC: **#2213** (@Pz1116). The API shape (`ExistOptions` struct rather than a bare bool) follows @LujhCoconut's suggestion on that RFC and the `ReplicateConfig` pattern.
- This PR builds on the design pioneered by **#2646** (@huangdong2022) and presents a new implementation on current main, shaped by the community's feedback on that PR (core commits credit huangdong2022 as co-author). Beyond a clean rebase, this version:
  - shares the promotion execution chain with promotion-on-hit instead of duplicating it (one chain, one failure-handling posture);
  - makes zero wire-protocol changes to existing RPCs (read-only queries ride the pre-existing admin RPCs; new RPCs are purely additive);
  - addresses the review findings on #2646 (throttle entries expiring while in-flight; per-key get-side master polling; missing completion callbacks; tenant handling in task registration);
  - ships a test plan that covers the feature end to end: unit tests for the throttle state machine and the master RPC semantics, a Python integration test with a negative control (plain `exist` must not promote) wired into `scripts/ci/run_ssd_offload_smoke.sh` with its own master instance (`promotion_on_hit=false` so the control is meaningful), and a reproducible A/B benchmark methodology.
- **RFC #3417** (@LujhCoconut): see the alignment discussion there. This PR's mechanism layer (task registration, shared chain, dedup, lease, holder-local execution) is what #3417's router-side explicit trigger would also build on; the exist-probe trigger is the RFC's "engine SDK without a router" path. We deliberately skip the frequency sketch (an explicit probe *is* the hotness signal) and the watermark gate in favor of a DRAM-saturation cooldown that yields to eviction/offload; promotion_in_flight quota is shared, not bypassed. A dedicated prefetch buffer / soft partition is left as follow-up.

## Measured impact

DSv4-Flash + vllm-ascend on Ascend A2; 48 long prefixes (at the prefix-cache hit granularity); fill → overflow-to-SSD → settle → measure; `promotion_on_hit=false`; same dataset and seed across rounds. Absolute latency values are omitted; numbers are TTFT decrease relative to the offload-only baseline of the same round, computed as (baseline − prefetch) / baseline.

**Concurrency 2** (store DRAM comfortably sized):

| metric | TTFT decrease with prefetch |
|---|---:|
| median | **5.2%** |
| mean | **5.1%** |
| p99 | **22.0%** |

**Concurrency 4** (deliberately DRAM-constrained store, ~97.5% full — a
stress regime where eviction churns constantly):

| metric | TTFT decrease with prefetch |
|---|---:|
| median | **85.2%** |
| mean | **81.4%** |
| p99 | **44.9%** |

**NVIDIA H20**:

| metric | TTFT decrease with prefetch |
|---|---:|
| median | **27.4%** |
| mean | **6.7%** |
| p99 | **0.3%** |

Why the rounds differ so much: without prefetch, a queued request pays serial SSD reads on the critical path, so the offload-only baseline's TTFT degrades roughly linearly with queue depth, while the prefetch round hides those reads inside the queueing window and stays flat. The decrease scales with queue depth and with the SSD-read share of TTFT; an idle, serial workload sees ≈ 0 decrease by design.

Honest stress metric from the DRAM-constrained run: promotion **completed 503, failed 860** (DRAM saturation), and the memory-pressure cooldown correctly yielded ~2.1k times — prefetch never starves eviction; it just loses.

## Rolling-upgrade compatibility

- No existing RPC signature changes.
- New RPCs (`RegisterPrefetchTask`, `prefetch_offload_object`) are additive: old masters/peers reject them and prefetch degrades to a no-op.
- Read-only queries reuse the pre-existing admin RPC handlers.
- All knobs default off: `enable_ssd_prefetch=false`, `ssd_get_wait_ms=0`.
