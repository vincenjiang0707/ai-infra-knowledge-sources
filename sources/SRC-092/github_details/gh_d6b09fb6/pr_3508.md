## 正文

## Summary

This PR fixes transfer-engine resource leaks around timed-out or failed transfer batches and Barex submission/registration failure paths.

Changes include:

- Reclaim timed-out transfer batches safely through deferred cleanup.
- Free Python wrapper batch IDs on submit failure, timeout, and status-check timeout.
- Mark Barex slices as failed when they are prepared but cannot be submitted.
- Roll back Barex memory registration on partial registration or metadata update failures.
- Harden Barex resource cleanup for partially initialized transports.

## Timeout Cleanup Tradeoff

A transfer `TIMEOUT` only means polling observed that a slice exceeded its timeout. It does not guarantee that the underlying transport operation has stopped or that transport callbacks will no longer touch the batch/task/slice memory.

Freeing `BatchDesc` immediately on timeout can therefore introduce use-after-free if a late callback later calls `markSuccess()` or `markFailed()`.

This PR uses a deferred cleanup worker as a conservative short-term fix:

- The worker is started lazily only when `freeBatchID()` sees a busy timed-out/failed batch.
- Normal completed transfers do not create the worker.
- The worker retries reclamation off the hot path until callbacks make the batch terminal.
- During shutdown, it performs a final retry and exits even if unresolved batches remain busy, logging a warning instead of blocking teardown indefinitely.

This trades a small amount of exceptional-path complexity and one lazily-created thread for avoiding both immediate UAF risk and permanent leaks for recoverable late-completion cases.

A longer-term alternative would be to make slice completion strictly idempotent and allow timeout paths to force pending slices into a terminal failed state, but that requires a broader transport callback semantics change.
