## Description

Repeated writes to existing objects can flood the master logs with `object_already_exists` messages. For example, when SGLang resumes using Mooncake as its L3 backend after temporarily unavailability.

Replace the per-key INFO logs and duplicate-specific batch VLOG messages with separate Prometheus counters for PutStart requests and BatchPutStart items. Display both counters in existing Grafana panels.

### he-yufeng · 2026-09-23 · COMMENTED

Verified the whole path against the PR head. The storm source is exactly where the fix lands, and the counting is wired correctly:

All four per-key `LOG(INFO) ... object_already_exists` sites in `master_service.cpp` (two in `InsertMetadata`, one in `AllocateAndInsertMetadata`, one in the `PutStart` discard check) are gone — the file goes from 4 to 0. The single-put counter increments at one point, the `WrappedMasterService::PutStart` wrapper on an `OBJECT_ALREADY_EXISTS` result, so every service-side producer funnels through it. The batch path replaces the per-item `VLOG(1)` with an `already_exists_count` accumulated in the result loop and one `inc_batch_put_start_object_already_exists` call after the join, which keeps the per-item semantics the old messages had without paying per-item log cost. The counters themselves follow the manager's existing patterns (zero-initialized in `update_metrics_for_zero_output`, getters, serialized names in the tests).

Coverage boundary, checked method by method: the remaining producers of `OBJECT_ALREADY_EXISTS` are `UpsertStart` (line ~5766), `CopyStart` (~6450), and the standby-restore paths (~3640/3790). The restore paths are startup recovery, not a rate path. Upsert overwrites by design and CopyStart is not the SGLang-resume storm shape, so scoping the counters to PutStart/BatchPutStart matches the described incident; if an operator ever sees those two storm, the same wrapper pattern applies one-for-one. Worth one line in the PR description that the scope decision is deliberate.

Tests cover zero-init and metric-name serialization for both counters plus the log-sink suppression case, and CI is green (21 success, the 2 skips are the usual scope detects).

Verification scope, honestly: this is a source-level review of the mechanism and the counting semantics; I did not run a local build of the new metric tests and rely on the PR's suite plus CI for that.
