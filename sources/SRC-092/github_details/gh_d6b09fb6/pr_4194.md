## Summary

P02 reader half of the batch-OpLog format migration. The production writer is
unchanged: it still emits the existing JSON batch record, and this PR adds no
writer selector, no environment variable, no default switch and no history
migration.

What it does:

- adds **one** format/version dispatch point at the existing
  `DecodeOpLogBatchRecord` entry, whose signature is unchanged. A complete
  binary magic selects the binary decoder, a non-empty truncation of the magic
  is its own error, and every other input goes to the **unchanged JSON reader
  exactly once** (no `try A then B` fallback chain), so the historical
  whitespace/BOM/parser acceptance domain, base64 canonicality checks and error
  strings do not change;
- adds a single binary encoding (MessagePack body inside a fixed 16-byte
  envelope) decoded by a bounded reader written for this six-element schema
  only: declared lengths are checked against the remaining bytes and the field
  budgets before any allocation, only unsigned integer encodings are accepted,
  `payload` must be `BIN` (STR/EXT rejected, including extension subtypes),
  `op_type` is range-checked before narrowing, and the whole body must be
  consumed;
- verifies the **existing canonical logical batch checksum**, so both physical
  encodings of the same logical batch agree on the checksum value. This
  deliberately does not change the JSON checksum algorithm, the JSON writer
  output, the durable prefix encoding or the snapshot encodings. A consequence
  worth stating: this version therefore does **not** remove the base64/JSON
  projection cost, so the P01 decode-speed multiples do not carry over to it;
- keeps failure atomic: validation happens on local candidates and the caller's
  record is assigned exactly once on success, so a failed decode cannot expose
  half a batch.

Startup prefix validation, the writer's ambiguous-transaction readback and the
batch auditor inherit the capability through the shared entry point with no
further edits.

## Known blocker (not fixed here)

The production etcd **Range** read path is not binary-transparent: the Go bridge
marshals range results through `encoding/json`, which rewrites every byte
`>= 0x80` to U+FFFD. A controlled probe shows a 256-byte value returning as 512
bytes from `Range` while `Get` is byte-exact. So `ReadBatch` (single key) reads a
framed binary batch correctly end to end, while `ReadBatchesAfter` cannot deliver
binary bytes, which means range-based replay of binary history cannot succeed
yet.

This is pre-existing infrastructure behaviour and outside the reader diff, but
it must be resolved before any binary writer can ship. Options: hex/base64 the
range response, return lengths plus raw pointers, or read the replay range by
key. Happy to take whichever direction maintainers prefer.

What I verified by reading:

- Dispatch collision-safety: the magic's first byte is `\x89`, which cannot start a valid JSON record (JSON text starts with `{`, whitespace, or a literal starter), so "complete magic → binary, truncated magic → its own error, everything else → the unchanged JSON reader exactly once" cannot misroute a historical record. Keeping the JSON path byte-identical with no try-then-fallback chain is what preserves the old acceptance domain, and the diff does exactly that.
- Framing: minimum-size check precedes the `body_length` arithmetic, `body_length` is compared against the remaining size (no `16 + length` overflow), and version/codec/flags are exact-match rejections.
- The reserve is doubly justified before it happens: sequence continuity (`last - first == count - 1`) pins `entry_count` to the declared range, and the explicit `entry_count > reader.Remaining()` rejection pins it to the bytes actually present. A forged array32 header cannot manufacture a giant reserve.
- Entry tail: per-entry checksum is recomputed from the decoded payload rather than trusted from the wire, op_type is range-checked wide before narrowing, payload must be BIN (STR/EXT rejected), the body must be fully consumed, the canonical batch checksum is verified, and the caller's record is assigned exactly once after every check passes. Failure atomicity holds.
- Format symmetry: the binary decode zeroes `timestamp_ms` and `prefix_hash`, which could have made the two encodings disagree semantically. It does not: the existing JSON decoder zeroes the same two fields on current main (`oplog_batch_codec.cpp:135,141`), and both sides recompute the entry checksum from the payload, so the canonical batch checksum genuinely means the same logical batch in both encodings.

One forward-looking observation, not an objection: the checksum helper is now exported outside the anonymous namespace as the single shared contract. That is the right minimal move, but it makes the JSON projection's field set the de facto wire schema for any future binary writer — worth keeping the "projection is the contract" comment near it when P03 lands, so a future field addition updates both encodings deliberately rather than by accident.
