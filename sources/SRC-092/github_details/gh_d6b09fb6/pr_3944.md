## Description

This PR improves Transfer Engine metadata handling for node replacement scenarios.

** Code are fully revised: ** #3837 -> #3072 -> #3944

When an RDMA failure suggests that cached remote metadata may be stale, the worker now triggers metadata cache invalidation. The invalidation keeps existing segment IDs as handles for in-flight retry paths, but marks remote segment descriptors stale and clears cached RPC metadata so the next lookup reloads fresh metadata from the metadata backend.

The change intentionally does not proactively disconnect all cached RDMA endpoints. Existing endpoint failure cleanup remains responsible for the failed endpoint, while metadata refresh is handled lazily on the next lookup.

### staryxchen · 2026-09-08

This PR and #3072 / #3944 look complementary rather than duplicate: both fix stale remote metadata in Transfer Engine, but from different sides.

- #3072 covers “peer is gone”: `syncSegmentCache` currently never invalidates, so a remote that unmounted or expired stays cached and keeps being used. The poller-side `kNotFound` vs `kUnavailable` distinction is the right way to drop that entry only on an authoritative absence.
- #3944 covers “peer was replaced”: on RDMA failure, mark remote metadata stale, keep the `SegmentID` for in-flight retries, and force the next lookup to reload — instead of waiting for the next poll.

Dumping the two diffs together would leave two invalidation models (erase vs mark-stale). Would you be open to co-working on one cache lifecycle instead? Something like Fresh / Stale / Gone, with the poller driving Gone only on authoritative `kNotFound`, and transport failures driving per-peer Stale (keep the ID, reload on next lookup, rather than invalidating every remote on any RDMA error). Happy to help sync on the design if that’s useful.

### staryxchen · 2026-09-23 · APPROVED

LGTM overall. Two non-blocking notes:

1. On P2P, and whenever `metadata_version == 0`, `shouldInstallFetchedSegmentDesc` accepts every fetched descriptor. `submitPostSend` and `redispatch` can force-fetch the same id at the same time, and each clears the refresh bit before the fetch. A slower fetch of the pre-replacement rkey can overwrite the newer one, and later submits keep using it until the next remote completion failure. Versioned etcd/HTTP metadata rejects that older writeback. A local generation checked at install time would close this.

2. `sendHandshake` refreshes RPC metadata on every non-P2P failure via `getRpcMetaEntryInternal(..., true)`, which holds `rpc_meta_lock_` across the backend read. One handshake failure then stalls other peers' RPC lookups for that round trip. Fetching outside the lock would keep the recovery behavior. A rejection or a `notify_rq_depth` decode failure means the address was reachable and does not need a refresh.
