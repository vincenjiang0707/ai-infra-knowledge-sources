## Description

Running a workload producer alongside the master can make producer contention part of a CPU-only master benchmark. This adds a Python launcher and C++ MasterClient replayer that consume an external timestamped JSONL trace after the producer has stopped, then measure a dedicated real master.

The replayer preserves physical keys, batch/object/slice boundaries, completion dependencies and explicit setup/workload/teardown phases. Scheduled times stay fixed under overload; results separate dispatch lag, client-call latency, issued calls, per-key outcomes, heartbeats and lifecycle overhead. The launcher records CPU/RSS, existing master metrics, background eviction and allocation/unfinished-write failures, plus commands and input/binary hashes.

Only benchmark code, documentation, tests and a small handwritten example are included. SGLang changes, simulator code, generated RPC traces and model-specific experiment artifacts are external. Production master behavior and RPC schemas are unchanged. Segments have fake addresses; no KV payload is allocated or transferred.

Design RFC: #4337

Related work: #3147 generates stateful synthetic traffic at runtime; this PR replays a previously generated timestamped/dependency-aware sequence and monitors a separate master. #3665 provides an in-process master for tests; this PR uses the existing RPC path and separate processes. Both distinctions are discussed in the RFC; this PR does not replace either effort. Related roadmap item: #1035.

Limits are documented: fixed-intent replay does not model serving feedback or guarantee the producer's hit rate, logical GPU count is not calibrated serving throughput, and CPU affinity does not isolate shared memory bandwidth. Eviction and incomplete-write cleanup are reported separately; optional write-timeout overrides are recorded explicitly.

## How Has This Been Tested?

Local environment: Ubuntu 22.04 on WSL2, CPU-only Release build, AMD Ryzen 7 8845H. Build and test paths below use conventional names for the corresponding local build directories.

The final rebuild initially exhausted this host's memory at requested parallelism 16 (the repository job pool limited compilation to 6 jobs). Retrying with parallelism 2 completed successfully, and the real-master smoke tests were rerun against the resulting binaries.

**Test commands:**
```bash
cmake --build build --target master_rpc_trace_bench mooncake_master -j 2
ctest --test-dir build-trace-tests --output-on-failure
python3 mooncake-store/benchmarks/master_rpc_trace/tests/test_rpc_smoke.py \
  --master build/mooncake-store/src/mooncake_master \
  --replayer build/mooncake-store/benchmarks/master_rpc_trace_bench
pre-commit run --files $(git diff --name-only --diff-filter=ACMR origin/main...HEAD)
bash scripts/code_format.sh --base origin/main --changed-lines --check
git diff --check
```

**Test results:**
- [x] Unit tests pass: parser/scheduler and Python monitor CTest groups (2/2).
- [x] Integration tests pass: 5 real-master RPC tests covering cross-client reuse, explicit lifecycle, multi-slice objects, partial puts, revoke and remove.
- [x] Manual testing done: an external 765,754-intent trace with 1,088 logical clients and fixed 4 TiB logical capacity completed with healthy heartbeats, no RPC/allocation errors and clean unmount. The master performed 16 successful background evictions, freeing 681,055 keys / approximately 1.86 TiB. No client Remove calls were injected.

The capacity-pressure run used speed 4, 64 workers, 4 master RPC threads, zero KV lease TTL, eviction high-watermark 0.9, eviction ratio 0.05 and explicit discard/release timeouts of 600/900 seconds to isolate capacity eviction. A separate default-timeout overload run produced PutEnd errors and is not counted as a passing run. These are functional stress checks, not a claim about production throughput or a performance improvement. The large input remains external; the included smoke fixtures are independently runnable.
