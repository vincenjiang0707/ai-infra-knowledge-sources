## Description

Centralize client registration, remount readiness, heartbeat/liveness monitoring, host hints, and offboarding lifecycle in `ClientSessionManager` instead of `MasterService`.

- Add lock-scoped session admission, registration rollback, staged restore, and ordered state-change listeners.
- Keep resource cleanup in the MasterService listener while the manager owns monitoring, offboarding workers, and the snapshot cleanup barrier.
- Bind memory buffers and local-disk replicas to the exact client incarnation via read-only `ClientSessionSharedPtr`; replacing a session invalidates old segment generations rather than silently transferring their resources.
- Check local-disk staleness using the bound session rather than a point-in-time registry complement.
- Adapt snapshot restore, metrics, and tests. No RPC or snapshot wire-format change is intended.

### Related work and scope

Searched existing issues/open PRs for client sessions and liveness before opening:
- #3707 / RFC #3360 reorganize mounted-region ownership around SegmentPool and explicitly exclude ClientSession redesign. This PR retains the existing segment manager and focuses on session ownership; the two changes will need integration coordination.
- #3936 proposes mass-expiry deferral under master stalls. This PR does not add that policy.
- #4130 fixes SSD registration deduplication across different client UUIDs. This PR instead preserves exact session identity and centralizes lifecycle/admission.

## 评论 (1)

### Icedcoco · 2026-09-21

Thanks for the substantial lifecycle refactor. I did find one correctness issue that should be addressed before merge: Session incarnation race in host hint updates

ClientSessionRegistry::UpdateHostId() first looks up the slot under a shared lock, releases that lock, and then reacquires the registry lock to update the host hint. Between those two lock acquisitions, the old session can be removed and a new incarnation with the same client UUID can be registered. The update would then be applied to the new incarnation even though it originated from the old one.

This can affect later host-based placement decisions when the request does not provide an explicit host hint. Please keep the lookup and update tied to the same slot incarnation, for example by updating under one exclusive lock or by revalidating the slot before writing.

There are also two OpLog/offboarding topics that seem worth discussing as follow-up work rather than blockers for this PR:

1. Offboarding changes in-memory segment state before the corresponding SEGMENT_UNMOUNT OpLog entry becomes durable. A process failure in that window could leave recovery dependent on a later reconciliation or snapshot.
2. Metadata cleanup and segment-unmount records are emitted through separate steps. The replay and promotion behavior should be tested explicitly when only part of that sequence has become durable.

The current retry tests are useful evidence for the local retry behavior. I suggest tracking the crash-window and replay-order questions as follow-up design work, with promotion/failure-injection coverage added there.

### Juhyun-Kim-Memphis · 2026-09-21 · COMMENTED

**Summary.** In a join-storm test, this PR (head `9a698e02`) does not reduce false OFFLINE transitions compared with main, and with a short TTL it produces about six times more. The reason is that pings still stall in the RPC thread pool: removing `client_mutex_` from `Ping` does not help while remount handlers waiting on `snapshot_mutex_` occupy every io thread. The PR's independent expiry then acts on those stalls, which main's lock-bound monitor partly misses. Disclosure: I opened RFC #4181 and #4183 on the same problem.

**Numbers.** OFFLINE transitions per run, three runs each. No client is ever stopped, so all of them are false.

| TTL active/suspicion | main | this PR |
|--|--|--|
| 20/20 s | 0 / 1 / 1 | 1 / 0 / 2 |
| 3/6 s | 3 / 4 / 3 | 20 / 23 / 18 |

With `--rpc_thread_num=32`, more threads than clients, this PR had 0 SUSPECTED and 0 OFFLINE in 2 runs at 20/20. That points at the thread sharing, not the lock.

**Setup.** Same tree for both arms: main `7faef38b`, and main plus this PR. Master with `--rpc_thread_num=8` and 7.8M keys. 12 clients ping every second while 16 threads run `BatchExistKey`. At t=30 s, 12 more clients mount at once, and each `ReMountSegment` is forced onto the post-promotion shard walk (about 4.5 s per walk here). `ReMountSegment` holds `snapshot_mutex_` for the whole walk (`master_service.cpp` L973-L1088), and coro_rpc runs handlers inline on the connection's io thread.

**What this does not say.** Nothing about production scale, x86 or HA deployments. Nothing against the session or ownership logic: the unit tests pass, and dead clients were detected on schedule in both arms (SUSPECTED at +10.7 s, OFFLINE at +30.7 s with TTL 10/20).

**Reproduce.** Branches `inf-522/rig-A` (main) and `inf-522/rig-B` (this PR) on github.com/vessl-ai/Mooncake carry the harness. Run the master with `MC_RIG_FORCE_REMOUNT_SCAN=1 --rpc_thread_num=8 --client_active_ttl_sec=20 --client_suspicion_ttl_sec=20`, then `master_bench --num_segments=12 --segment_size=515396075520 --independent_ping=true --wait_register_sec=120 --num_clients=4 --num_threads=4 --num_keys=487500 --operation=BatchExistKey --batch_size=128 --value_size=4096 --duration=150 --mount_extra_at_sec=30 --extra_clients=12`, and compare `master_client_liveness_offline_transitions_total` before and after.
