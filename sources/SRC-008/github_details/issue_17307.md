# MegaMoe (W4A8) on Atlas 800I A3: garbage output, AICore crash on long prefill; 9.2.0-built ops vendor loses attributes on 9.1.0 base

## Environment

- Hardware: 4 x Atlas 800I A3 (Ascend 910_93, 16 dies each), supernode-colocated
- Topology: TP16 / DP4, `--data-parallel-hybrid-lb`, external LB round-robin across 4 API servers (each node hosts 1 local DP rank)
- Model: Kimi-K3 full weights, W4A8 ModelSlim quantization (993k-entry quant_model_description.json, includes `mm_projector.rot_proj.weight` + `optional/quarot.safetensors`)
- vllm: main @ 84030bbe3d (NFS source tree)
- vllm-ascend: d9ce0aa6f5 ("Constants adapt to A5" era; `load_cann_mega_moe_ops()` uses native `cann_ops_transformer.ops`)
- torch_npu: 2.10.0.post6
- CANN: 9.1.0 (case 1) / 9.2.0 (case 2), a3 profile
- Service args (same for all cases, MegaMoe ON):

```
vllm serve /home/admin/model-csi/model --host 0.0.0.0 --port 8001 --served-model-name kimi-k3 \
  --trust-remote-code --quantization ascend --tensor-parallel-size 16 --data-parallel-size 4 \
  --data-parallel-size-local 1 --data-parallel-hybrid-lb --decode-context-parallel-size 16 \
  --block-size 384 --enable-expert-parallel --max-num-seqs 16 --max-model-len 1048576 \
  --max-num-batched-tokens 8192 --gpu-memory-utilization 0.9 --safetensors_load_strategy prefetch \
  --enable-prefix-caching --tokenizer-mode kimi_k3 \
  --additional-config '{"enable_flashcomm1":true, "multistream_overlap_shared_expert":true, "enable_shared_expert_dp":false, "recompute_scheduler_enable":false, "enable_fused_mc2":2, "enable_prefill_mc2":true, "mega_moe_max_tokens":65536}' \
  --mm-encoder-tp-mode data --limit-mm-per-prompt '{"vision_chunk": 2}' \
  --enable-auto-tool-choice --reasoning-parser kimi_k3 --tool-call-parser kimi_k3
```

## Case 1 — 9.1.0 base + 9.2.0-built custom ops vendor: `Invalid_Attr(EZ0002)`, activation attribute arrives empty

Install of the 9.2.0-built `cann-ops-transformer-custom_linux-aarch64.run` into the 9.1.0 base
reports success (dlopen check OK, comm_context.cpp JIT-compiles OK, op_impl/op_api files merged
into `vendors/custom_transformer`, note: "no need to upgrade custom.proto files").

Weight loading completes, but the first `npu_mega_moe` call fails on every rank:

```
RuntimeError: call aclnnMegaMoe failed, detail:[PID: 49646]
  Invalid_Attr(EZ0002): Attribute activation of MegaMoe has incorrect value .
  It should be one of {swiglu, swiglustep, swigluoai, situglu}.
  Solution: Check whether the operator attribute is correct.
```

vllm-ascend calls `self.mega_moe(...)` (vllm_ascend/ops/fused_moe/moe_comm_method.py) **without**
passing `activation`, so the CANN python wrapper default `"swiglu"`
(cann_ops_transformer/ops/mega_moe.py: `activation: str = "swiglu"`) applies. The value reaches the
operator as empty — i.e. the attribute is lost between the 9.2.0-built `libcust_opapi.so` and the
9.1.0 framework (op_proto enum is known to the framework, so only the opapi→framework attribute
marshalling is broken). This looks like an ABI mismatch that file-level merging cannot fix.

## Case 2 — CANN 9.2.0 native (no vendor): starts, but garbage output + AICore crash on long prompts

With CANN 9.2.0 (native `cann_ops_transformer.ops.mega_moe` present, `ops/mc2/common` layout), the
same serve command starts cleanly: graph capture succeeds, `MegaMoe symm buffer:
max_recv_token_num is set from mega_moe_max_tokens=65536` logged, 4-node DP4 cluster fully up.

- Short prompt (greedy, temperature=0), repeated runs: output is **garbage**, e.g.

  ```
  Q: 1+1等于几？直接回答数字。
  A: !!..阿. uns桌子上だけ排便 well should但是有一是CRE熄火!!!image不能有肚子疼的控制.!鸽子!...
  ```

- 40k-token prefill prompt: **AICore execution abnormal (EE9999)**, worker dies, engine crash:

  ```
  RuntimeError: query:../torch_npu/csrc/core/npu/NPUEvent.cpp:95 NPU function error:
    acl::AclQueryEventRecordedStatus(event_, &currStatus) ...
  [Error]: The aicore execution is abnormal.
  EE9999: Internal error! rtStreamSynchronizeWithTimeout execution failed
  ```

  Full 4-node service logs: archived (vllm_p_node{0-3}.log, gzipped tar available on request).

## Control — MegaMoe OFF is fully functional on the same setup

Same cluster / model / code, only `--additional-config` without the MegaMoe triple
(`enable_fused_mc2`, `enable_prefill_mc2`, `mega_moe_max_tokens`):

- 4P0D prefill benchmark (cc=12, 120 prompts, 20k-40k text-only, output-len=1): 120/120 success,
  3,343,747 input tokens in 433.84 s ≈ 7,707 tok/s input throughput
- Deterministic math/word-problem accuracy set (200 problems, greedy): **90.0%**, 0 request errors

So the cluster, weight assets, and the standard MoE path are healthy; the failures above are
specific to the MegaMoe path with W4A8 on A3. (The code comment in
`_get_cann_mega_moe_quant_settings` already mentions the W4A8 accuracy root cause being on the
operator side — the garbage output here is consistent with that; the long-prompt AICore crash and
the 9.1.0 opapi attribute loss are additional.)

## Also observed (asset side, for completeness)

Some mounts of the model deliver `quant_model_description.json` with `"optional": {}` while
`optional/quarot.safetensors` and `mm_projector.rot_proj.weight` exist in the index. With that
inconsistent description, `get_rotation_path()` returns None, the projector skips building
`rot_proj`, and weight loading crashes with
`ValueError: There is no module or parameter named 'mm_projector.rot_proj'`. Restoring the
`optional` block in the description fixes loading. Worth a check on the model-asset side.

## Ask

1. Case 1: is a 9.1.0-compatible build of the custom ops package (or a version upgrade path that
   also updates the opapi marshalling) available? File merging alone is not sufficient.
2. Case 2: W4A8 MegaMoe on A3 currently produces unusable output and crashes on long prompts —
   is W4A8+MegaMoe on A3 expected to work at this CANN version, and is there a known-good
   combination?
