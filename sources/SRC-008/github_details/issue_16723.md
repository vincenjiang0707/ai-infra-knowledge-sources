# [Bug] `IndexError: list index out of range` in `MooncakeConnectorWorker._get_remote_rank` for asymmetric Prefill/Decode TP (P-TP8 / D-TP1)

## Summary

When running PD-disaggregated serving with **asymmetric tensor-parallel sizes between Prefill (P) and Decode (D) nodes** (e.g. P-TP8, D-TP1), the P node crashes with:

```
IndexError: list index out of range
  at mooncake_connector.py:3715 _get_remote_rank
    return self._get_remote_ranks_for_req(req_id, prefill_tp_size)[self.tp_rank]
```

This happens only when **an external data-parallel load balancer (DPLB) is enabled**, which causes the P node to perform a *cross-P KV load* (`start_load_kv`) for requests whose KV was produced by another P rank.

## Environment

- vllm: `releases/v0.26.0` (also reproduced on v0.23.0, v0.27.1rc, master)
- vllm-ascend: `releases/v0.26.0rc`
- Model: GLM-5.3 (sparse attention + MXFP4 KV)
- Topology:
  - P node: `DP2 TP8` (kv_producer), 8 cards
  - D node: `DP16 TP1` (kv_consumer), 16 processes
  - External EPLB enabled (`--data-parallel-rank` explicitly set → `data_parallel_external_lb=True`)
- kv-transfer-config (P node):
  ```json
  {
    "kv_connector": "MultiConnector",
    "kv_connector_extra_config": {
      "connectors": [{
        "kv_connector": "MooncakeConnectorV1",
        "kv_connector_extra_config": {
          "prefill": {"dp_size": 2, "tp_size": 8},
          "decode": {"dp_size": 16, "tp_size": 1}
        },
        "kv_role": "kv_producer"
      }]
    }
  }
  ```

  → model_runner_v1.execute_model:1910

## Root Cause

`MooncakeConnectorWorker._get_remote_rank` (vllm-ascend `mooncake_connector.py` L3714-3715):

```python
def _get_remote_rank(self, req_id: str, prefill_tp_size: int | None = None) -> list[int]:
    return self._get_remote_ranks_for_req(req_id, prefill_tp_size)[self.tp_rank]
```

`_get_remote_ranks_for_req` builds a list of remote-P rank groups whose length depends on the TP mapping:

```python
if prefill_tp_size == self._decode_tp_size:
    sampled_nums = [...]                    # length = prefill_tp_size (safe)
    return sampled_nums
# asymmetric path (prefill_tp != decode_tp):
num_groups = max(1, prefill_tp_size // num_kv_head)   # e.g. max(1, 8//1) = 8 (sparse)
# then sampled_nums length = decode-side grouping, often < prefill_tp_size
```

For **P-TP8 / D-TP1** (non-sparse `num_kv_head >= 2`), the resulting list length is `<= 4`, which is **less than `tp_rank + 1` (= 6 for tp_rank=5)**, so `[self.tp_rank]` raises `IndexError`.

The root problem is that **vllm-ascend's `MooncakeConnectorWorker` implements its own rank-mapping logic (`_get_remote_rank` / `_get_remote_ranks_for_req`) which does not support asymmetric P/D TP**, whereas **upstream vLLM's `MooncakeConnector` supports heterogeneous TP via `_get_tp_ratio` / `_compute_sender_transfer_plan`** (see `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py` L98-216 in v0.22.1 and v0.26.0).

### Why only with external DPLB

- **Without DPLB**: P node only *saves* KV (`save_kv`), it never calls `start_load_kv` → `_get_remote_rank` is never reached.
- **With external DPLB**: requests are dispatched to arbitrary P ranks; a P rank may need to *load* KV produced by another P rank (`do_remote_prefill` path) → `start_load_kv` → `_get_kv_split_metadata` → `_get_remote_rank` → crash.

### Versions affected

| Version   | `_get_remote_rank` | Affected |
| --------- | -------------------- | -------- |
| v0.23.0   | L3546                | ✅       |
| v0.26.0rc | L3714                | ✅       |
| v0.27.1rc | L3824                | ✅       |
| master    | L3890                | ✅       |

This is **not a regression** introduced in v0.26 — the same logic has existed since at least v0.23.0.

## Expected Behavior

Asymmetric P/D TP (e.g. P-TP8 / D-TP1) should be supported for cross-P KV loads, consistent with upstream vLLM's heterogeneous TP support (which only requires `tp_size` divisibility, e.g. `8 % 1 == 0`). At minimum, a clear error message (assertion) should be raised instead of a raw `IndexError`.

## Suggestion / Fix Direction

1. **Support asymmetric TP**: adapt upstream vLLM's `_get_tp_ratio` / `_compute_sender_transfer_plan` heterogeneous transfer planning into `MooncakeConnectorWorker._get_remote_rank` (or reuse the upstream helpers), so P/D TP need only satisfy divisibility.
2. **Or add a guard**: if `len(remote_ranks) <= self.tp_rank`, fall back to `remote_ranks[self.tp_rank % len(remote_ranks)]` with a warning, or raise an explicit `ValueError` explaining the unsupported TP combination.

## Workarounds (current)

- Align P/D TP (e.g. both TP8) so `prefill_tp_size == decode_tp_size` uses the safe branch.
- Use `MooncakeLayerwiseConnector` / the layerwise prefill-then-decode connector (which maps TP via `tp_rank % tp_ratio` and supports asymmetric TP).

### cs-fisha · 2026-09-21

I'm working on a fix for this.

`_get_remote_ranks_for_req` returns a list indexed by decode TP rank (length ≈ D-TP). `_get_remote_rank` currently always does `[self.tp_rank]`, which is correct for decode consumers and for symmetric P/D TP, but a P-side (`kv_producer`) worker doing a DPLB cross-P `start_load_kv` has P-side `tp_rank` in `0..P-TP-1`. For P-TP8 / D-TP1 that list has length 1, so `tp_rank=5` raises `IndexError`.

Plan (no new shuffle):
- Decode consumers keep `[decode_tp_rank]`.
- Symmetric P/D TP still indexes by `tp_rank` (list length == TP).
- Prefill producer whose `tp_rank` is out of range uses decode-group 0 (same as the D-TP1 consumer mapping / `_prefill_get_remote_rank` for a single group). Not `tp_rank % len(ranks)`.

Will patch both `mooncake_connector.py` and `mooncake_hybrid_connector.py`, plus CPU unit tests with fake rank lists. No NPU required.
