# [CANN/cann_ops_transformer] MegaMoe host API mismatch with CANN 9.2.0 aclnnMegaMoe

## Summary

While validating the MegaMoe path on Atlas A3 with CANN 9.2.0, the MegaMoe Python/C++ extension can create the MC2 symmetric buffer, but the first real `mega_moe` kernel invocation fails inside `aclnnMegaMoeGetWorkspaceSize` with:

```text
AclNN_Parameter_Error(EZ1001): activation must not be nullptr.
```

The Python caller explicitly passes `activation="swiglu"`. Additional inspection and diagnostic wrapper rebuilds show that this is a host-side ABI/signature mismatch between the installed `cann_ops_transformer` extension and the custom MegaMoe vendor host API shipped for CANN 9.2.0.

This is not a vLLM-Ascend logic bug. I am filing it in the vLLM-Ascend community only because the issue was found while integrating the vLLM-Ascend MegaMoe path.

## Environment

- Hardware: Atlas A3 / Ascend910_93
- CANN toolkit / nnal / A3-ops: 9.2.0
- Custom vendor package: `custom_transformer`, installed under `/usr/local/Ascend/cann-9.2.0/opp/vendors/custom_transformer`
- `cann_ops_transformer`: 1.0.0
- vLLM: 0.27.1
- vLLM-Ascend: 0.27.1, branch `megamoe-check`, commit `5a9de65760563f7d17c19627b647a5106235e057`
- torch: 2.10.0+cpu
- torch_npu: 2.10.0.post4
- Minimal reproduction: 2 NPUs, one EP process group

## What works

- `cann_ops_transformer` imports successfully from the CANN 9.2.0 path.
- MegaMoe Python APIs are visible:
  - `cann_ops_transformer.ops.mega_moe`
  - `cann_ops_transformer.ops.get_symm_buffer_for_mega_moe`
- A 2-NPU HCCL group initializes successfully.
- The MegaMoe symmetric buffer and MC2 context are created successfully on both ranks:
  - `ccl_buffer_size=419430400`
  - context devices are `npu:0` / `npu:1`

## Minimal kernel smoke

The minimal 2-NPU kernel call uses:

```python
world_size = 2
num_experts = 8
tokens_per_rank = 8
topk = 2
hidden = 1024
intermediate_hidden = 1024
dtype = torch.bfloat16
activation = "swiglu"
```

Each rank creates four local expert weight tensors and calls:

```python
out, expert_tokens = mega_moe(
    x,
    topk_ids,
    topk_weights,
    l1_weights,
    l2_weights,
    sym_buffer,
    activation="swiglu",
)
```

The call fails on both ranks with:

```text
RuntimeError: call aclnnMegaMoe failed, detail:
AclNN_Parameter_Error(EZ1001): activation must not be nullptr.
```

The original plog contains:

```text
[ERROR] OP(...): [aclnn_mega_moe.cpp:122][NNOP][aclnnMegaMoeGetWorkspaceSize]
errno[161001] activation must not be nullptr.
```

## Why this looks like an ABI/signature mismatch

The installed C++ wrapper's `ACLNN_CMD(aclnnMegaMoe, ...)` call passes 34 positional arguments after the API name. It has slots for `x_active_mask`, shared weights/biases, `mask_buffer`, quant/activation/topo attrs, and the two outputs, but no slot for newer fields exposed by the installed dynamic MegaMoe definitions.

CANN 9.2.0 built-in `MegaMoe` dynamic definition exposes:

```text
scales_in
activation_out_dtype
transpose_weight1
transpose_weight2
weight1_interleave
```

The custom vendor dynamic definition additionally exposes:

```text
shared_expert_quant_out_dtype
```

These fields are optional at the dynamic-op semantic level, but the ACL host API is a positional C ABI: an optional value must still be represented by an explicit `nullptr`/default-value slot. Omitting the slot shifts later arguments, which is consistent with the misleading `activation must not be nullptr` error despite Python passing `activation="swiglu"`.

Additional inspection of the installed package strengthens this conclusion:

- The installed C++ wrapper's `ACLNN_CMD(aclnnMegaMoe, ...)` call passes 34 positional arguments after the API name. It has no slot for the five newer fields listed above.
- CANN 9.2.0 built-in dynamic `MegaMoe` exposes 40 arguments before internal build helpers and includes those five fields.
- The custom vendor dynamic definition exposes 41 arguments and additionally includes `shared_expert_quant_out_dtype`.

## Diagnostic rebuild results

To avoid treating the signature mismatch as a purely theoretical issue, I rebuilt only the local `cann_ops_transformer` C++ wrapper with additional ACL positional slots. No Python-facing API was changed. The purpose was diagnostic only.

| Wrapper call shape | Result |
|---|---|
| Original wrapper | `activation must not be nullptr` |
| Add vendor-visible slots: `scales_in`, `shared_expert_quant_out_dtype`, `activation_out_dtype`, `transpose_weight1`, `transpose_weight2`, `weight1_interleave`; outputs at end | `Expected a value of type [aclTensor] for argument [yOut] but instead found nullptr` |
| Remove `shared_expert_quant_out_dtype`; keep the other five slots; outputs at end | Same `yOut` error |
| Move `yOut` / `expertTokenNumsOut` before attrs, matching dynamic-definition order | `Expected a value of type [aclTensor] for argument [expertTokenNumsOut] but instead found nullptr` |
| Restore `shared_expert_quant_out_dtype`; add diagnostic null slots before outputs | Returns to `yOut` error |

The error position changes as the C++ positional call shape changes, which confirms that the original wrapper is not aligned with the installed vendor host API. It also shows that blindly inserting optional slots is not a valid fix: the exact generated `aclnnMegaMoeGetWorkspaceSize` prototype is required.

`LD_DEBUG=bindings` also confirms that the runtime resolves MegaMoe from the custom vendor library:

```text
binding file .../opp/vendors/custom_transformer/op_api/lib/libcust_opapi.so to
.../opp/vendors/custom_transformer/op_api/lib/libcust_opapi.so:
normal symbol `aclnnMegaMoeGetWorkspaceSize`
```

### linnea-lin-00638949 · 2026-09-21

### Follow-up: custom MegaMoe wheel packaging is incomplete

We additionally tried the provided `cann_ops_transformer_custom-1.0.0-py3-none-any.whl` with:

```bash
python3 -m pip install cann_ops_transformer_custom-1.0.0-py3-none-any.whl \
  --force-reinstall --no-deps
```

The MegaMoe host ABI mismatch is resolved by this wheel, and a 2-NPU MegaMoe smoke test passes. However, the wheel is currently not self-contained.

While loading it, we found two missing pieces:

1. `cann_ops_transformer_custom/ops/mc2/common` is missing from the wheel. Importing the package fails with:

```text
No module named 'cann_ops_transformer_custom.ops.mc2.common'
```

2. `cann_ops_transformer_custom/csrc/mc2/comm_context.cpp` is missing. After making `mc2.common` importable, building `CommContextManager` fails with:

```text
FileNotFoundError: No such file or directory:
/usr/local/python3.12.13/lib/python3.12/site-packages/cann_ops_transformer_custom/csrc/mc2/comm_context.cpp
```

For validation, we temporarily copied these pieces from the CANN 9.2.0 `cann_ops_transformer` package. After that, the custom MegaMoe wrapper builds and runs successfully.

One additional packaging detail is that, once `common` is restored, the generic ops auto-discovery logic tries to load it as an op and can cause duplicate registration of `engram_fetch`. We had to exclude `common` from auto-discovery for the validation package.

Could the next custom wheel either ship the complete runtime/source dependency set, or explicitly document and implement it as an overlay package with the required base package version? The current wheel works as a validation artifact but is not suitable as a standalone installation package.
