### What this PR does / why we need it?
This PR is based on #16981 for Qwen3.8-Flash-Next.

It adapts the qwen4_exp hybrid model to the V2 model runner on Ascend, enabling V2 serving with FULL aclgraph decode mode, MTP speculative decoding and async scheduling. Three commits, one per functional layer:

**1. Six-region KV cache consumption in the V2 runner** (`attn_utils.py`)

The qwen4_exp hybrid model uses a six-region KV cache layout: one shared slot backing carries six physical slabs (GDN states, QSA main K/V, raw/compressed QSA states, PLE n-gram states). The V2 runner previously had no consumption path for this layout, so the V1 contract (shared backing allocation + per-role view rebuild in the reshape step) is mirrored into the V2 allocation/reshape entry points. Configurations that cannot take the shared backing (KV transfer connectors outside the allowlist, DSV4) still fall back to vLLM's own allocator.

**2. Hybrid FULL aclgraph replay** (`aclgraph_utils.py`, `qwen4_exp/model_state.py`, `qwen4_exp/qsa.py`)

FULL aclgraph replay previously assumed a single executable attention backend and a model state that stores attn_metadata. Both assumptions break for qwen4_exp:

- Hybrid models own more than one executable backend (main attention, QSA side cache; GDN groups are metadata-only), so `_get_graph_update_backends` now collects all distinct backends with an executable attention impl and refreshes every one of them before replay.
- `AscendQwen4ExpModelState` is added via multiple inheritance (`Qwen4ExpModelState` + `AscendMambaHybridModelState`): MRO keeps the upstream PLE input preparation while `prepare_attn` resolves to the Ascend implementation that builds and stores attention metadata for replay.
- QSA kernels are custom Triton ops reading persistent buffers rewritten per step, so `update_graph_params` is a documented no-op for QSA, mirroring the V1 gate for sparse/compressed models and the MiniMax-M3 indexer precedent.

**3. MTP draft support in the autoregressive speculator** (`speculator.py`)

The qwen4_exp MTP draft reuses the target model's QSA backend, which derives from vllm's `FlashAttentionBackend` (not `AscendAttentionBackend`) and therefore missed the architecture classification in `set_attn`. QSA is now classified into its own branch whose draft KV semantics follow the GQA behavior group (standard block-table slot mappings), and the host-side FIA metadata patch is skipped for QSA since its metadata aliases the shared input buffers and the patched fields do not exist on `QSAForwardMetadata`.

### Does this PR introduce _any_ user-facing change?
No.

### How was this patch tested?
Tested on 8 × Ascend 910C (A3) with Qwen3.8-Flash-Next-w8a8 (TP8/EP8): V2 serving starts up normally in graph mode with MTP enabled, and single-curl requests return correct responses in all four configurations (V2 eager, V2 + graph, V2 + MTP, V2 + graph + MTP).

Multimodal (image) input is also verified on V2: the same base64-image chat request returns a correct answer (dominant color + shape recognition) with identical prompt token counts as the V1 baseline, confirming the vision encoder path works under the V2 runner.
