# [PR #17500] [Performance][Worker] Skip PP token broadcast when no consumer exists

## 正文

### What this PR does / why we need it?

On a disaggregated-prefill (P) node with pipeline parallelism, chunked prefill serializes at request boundaries: PP0 finishes the final chunk's forward, then stalls until the last PP rank finishes sampling and the sampled-token broadcast round-trips, before the next chunk can start.

Root cause: `PPHandler.receive`/`broadcast`/`broadcast_drafts` only skip the token collective for **non-final** prefill chunks (`compute_need_sampled_mask`). The final chunk of every request triggers a real broadcast, even where its payload has no consumer:

- Non-last PP ranks use the broadcast tokens only to build the inputs of a follow-up step (decode / spec verification) for the same request.
- A request that leaves the engine right after its final prefill chunk (`max_tokens=1`, as disaggregated-prefill routers submit) never reads that payload — the deferred consumer (`get_prev_sampled_outputs`) discards it via its freed-request filter anyway.
- The collective couples all PP ranks at every request boundary and contends with the next chunk's activation p2p transfer. With short prompts (e.g. 8k / 4096-token chunks = 2 chunks per request) this drain dominates and looks like a per-chunk forced sync between PP0 and PP1.

This PR skips the broadcast when **every** sample-producing request is a final prefill chunk that reaches its length cap with its single sampled token (`prefill_len + 1 >= max_seq_len`). The condition is per-request and **role-agnostic**: it fires for `max_tokens=1` requests on pure prefill nodes and on hybrid producer-consumer (混部) instances alike, while any batch where a request keeps decoding on this engine retains the broadcast. Both PP ranks derive the verdict from identical per-step batch/request state, so sender and receivers always agree — no mismatched collectives.

Changes:
- `vllm_ascend/patch/platform/patch_pp_token_broadcast.py`: patch `PPHandler.receive`/`broadcast`/`broadcast_drafts` with the no-consumer skip (no-op on vLLM versions without the deferred PP token broadcast).
- `vllm_ascend/worker/v2/model_runner.py`: attach the request states to the PP handler so the skip can read per-request length caps (`RequestState.max_seq_len`).
- `tests/ut/patch/platform/test_patch_pp_token_broadcast.py`: UT for the skip verdict (finishing final chunk skips — alone or alongside mid-prefill requests; remaining budget / decode-in-batch / missing states keep the broadcast) and the patched entry points.

Long-term this skip condition belongs upstream next to `compute_need_sampled_mask`; the patch follows the plugin pattern until then.

### Does this PR introduce _any_ user-facing change?

No API/config change. Pure performance optimization: with PP, the inter-stage token broadcast at request boundaries is skipped when its payload is provably unconsumed.

### How was this patch tested?

- Unit tests added: `pytest -sv tests/ut/patch/platform/test_patch_pp_token_broadcast.py`.
- Local logic validation of the patch module against a stub replicating upstream `compute_need_sampled_mask`/`PPHandler` (pure-P and hybrid cases all passed).
- `ruff check` + `ruff format` clean on changed files.
- NPU verification (PD-disagg P node, PP2×TP8 chunked prefill) pending CI / hardware run.
- vLLM main: https://github.com/vllm-project/vllm/commit/ced6857afa0ea7b2e3f0846a62e1394e90f15607
