## 原因分析

循环导入路径如下：
```
model_runner_v1
  -> attention_v1
  -> device.device_op
  -> ops.triton.fla.chunk_scaled_dot_kkt
  -> ops/__init__.py
  -> ops.fused_moe.fused_moe
  -> ops.fused_moe.experts_selector
  -> device.device_op.DeviceOperator
```

device_op.py 在模块顶层导入了 Triton kernel：

```
from vllm_ascend.ops.triton.fla.chunk_scaled_dot_kkt import (
    chunk_scaled_dot_kkt_fwd_kernel,
)
```

当 Python 导入 vllm_ascend.ops.triton 下的子模块时，会先初始化 vllm_ascend.ops 包，并执行 ops/__init__.py，ops/__init__.py 会立即导入 fused_moe：
```
import vllm_ascend.ops.fused_moe.fused_moe
```

随后，fused_moe.py 导入 experts_selector.py，而 experts_selector.py 又尝试从 device_op.py 导入 DeviceOperator。
此时 device_op.py 仍处于初始化过程中，并且 DeviceOperator 需要到文件末尾才会完成赋值：

```
DeviceOperator: type["BaseDeviceAdaptor"] = get_device_adaptor()
```

因此，experts_selector.py 无法从尚未完成初始化的模块中导入 DeviceOperator，最终触发循环导入异常。

### slippersss · 2026-09-02

Thanks for reporting this.

In the normal initialization flow, `NPUPlatform.pre_register_and_update()` applies the platform patches and initializes the required ops before the worker and model runner are loaded, so this circular import is not triggered.

Directly importing `model_runner_v1` bypasses that initialization flow. As an internal implementation module, `model_runner_v1` is not currently guaranteed to support standalone imports, so this behavior is outside the expected usage path.
