# [PR #17529] [BugFix][Performance] Bound fused slot-mapping JIT specializations and prewarm them

state: open | updated: 2026-09-25T05:47:50Z
labels: module:tests, module:ops

## 正文

### What this PR does / why we need it?

Fixes #17527.

The fused multi-group slot-mapping kernels from #15289 take `NUM_REQS` and
`PARALLEL_TILES` as `tl.constexpr`. Every new `(num_reqs, tile)` pair seen at
runtime therefore compiles a new Triton specialization on the hot path
(~5.5 s bisheng compile on 910B2), and every in-flight request stalls for
the whole compile. On DSV4-Flash + MRV1 at concurrency 64 this cost ~1.8x
throughput on average over 5 rounds (413 vs 762 tok/s). Details and
evidence are in #17527.

Changes:

1. `num_reqs` / `parallel_tiles` become `do_not_specialize` runtime
   arguments, and the kernels launch on a `(group, req[, tile])` grid.
   `_select_slot_mapping_launch_config` is unchanged, so every shape picks
   the same kernel and tile as before. The key space becomes 7 per
   `HAS_CIRCULAR` variant: adaptive tiles 16..512 plus the parallel
   `TILE_BLOCK_SIZE=1024`. The values are not recovered from
   `tl.num_programs()`: on 910B2 that form added ~27 us device time per
   call (msprof `aiv_time`).
2. A new `slot_mapping` entry in `kernel_warmup` prewarms all of those
   keys. It runs after `initialize_kv_cache`, when the multi-group block
   table exists, and before graph capture. `profile_run` is too early: the
   input batch still has one block table there, so the fused path isn't
   set up.
3. `MultiGroupBlockTable` passes `is_circular_ptr=None` when no group is
   circular, so the circular path is compiled out (today every engine runs
   it), and the hot-loop `int32 % block_size` becomes a multiply-subtract.
   For engines without a circular group (e.g. DSV4) the kernel's device
   time drops to 0.10x-0.76x of main.
4. Under `HAS_CIRCULAR`, negative positions are padded in every group and
   kept out of the block-table window base (#17528, latent). This part
   is also available standalone as #17530. With it, engines that do have a
   circular group (DSV4.1, GLM-5-Next) take 1.05x-1.61x of main's device
   time (+1 to +7 us per call); it can be dropped from this PR if preferred.

Relation to open PRs: #16829 marks `NUM_REQS` `do_not_specialize`, which is
change 1 without `PARALLEL_TILES`. It has no prewarm, so each key still
compiles once on the hot path after a cold start. #17353 (draft) uses
`tl.num_programs(1)`, see the note in change 1. This PR is a superset of
#16829; happy to rebase onto it if it lands first.

Backport: #15530 already brought the fused kernel to `releases/v0.26.0rc`
(not in any tag yet), so this fix should go there too before the next
release from that branch; happy to open the cherry-pick.

### Does this PR introduce _any_ user-facing change?

No API or configuration change. Engine startup gains the slot-mapping
prewarm. On an empty Triton cache that is a one-time ~40 s per worker
(7 keys x ~5.5 s, before graph capture); with a warm cache the keys load
from disk. Negative positions in mixed circular/non-circular layouts now
map to `PAD_SLOT_ID` in every group (no current caller produces them).

### How was this patch tested?

On 8x 910B2, CANN 9.1.0, vLLM 0.30.0, at base `39fef3f8f`:

- `tests/e2e/nightly/single_node/ops/singlecard_ops/triton/test_compute_slot_mapping_fused_groups.py`
  (new): 29 passed. It covers the #15289 shape matrix against the
  per-group kernel, negative positions (including `pos <= -block_size`
  and all-negative requests), `is_circular_ptr=None` equivalence, bounded
  JIT cache over a batch-shape sweep, and no new key after prewarm, both
  directly and through `MultiGroupBlockTable`.
- `tests/ut/model_executor/warmup/`: 21 passed, including the new
  `test_slot_mapping_triton_warmup.py`.
- E2E, DeepSeek-V4-Flash w8a8, TP8+EP, MRV1, FULL_DECODE_ONLY,
  200 prompts at concurrency 64:
  - main: 4 of 5 rounds stalled at 262-373 tok/s with 6.3-6.5 s stalls;
    the clean round did 762 tok/s.
  - this PR's kernel, warm Triton cache: 6 of 6 rounds clean, 749-763
    tok/s, zero ITL > 1 s, no new slot-mapping cache entries.
  - this PR, empty `TRITON_CACHE_DIR`: `slot_mapping Triton warmup
    complete in` 39.7-40.9 s per rank, the slot-mapping cache stays at 7
    keys from readiness to shutdown, 755 / 756 tok/s, zero ITL > 1 s.
- msprof device time per call for both `HAS_CIRCULAR` variants across
  the #15289 matrix is in #17527.

After testing, the branch was rebased onto `bea70ab8f`. The only conflict
was import context in `block_table.py` from #17470. The NPU tests have not
been re-run on the new base.
