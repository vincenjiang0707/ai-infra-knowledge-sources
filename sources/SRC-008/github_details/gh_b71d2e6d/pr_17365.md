## 正文

### What this PR does / why we need it?

Ports upstream **Encoder-side SWA bounded replay** (vLLM [#56227](https://github.com/vllm-project/vllm/pull/56227)) to Ascend, for DeepSeek-V4.1 on model runner V1.

On a prefix hit upstream rewinds the request to `replay_start = H - min(window, H)`, recomputes the hit's last window, and keeps the sliding-window KV out of the prefix cache so that the recompute is what rebuilds it: the group gets `prefix_cacheable=False` and `prefix_replay_tokens=window`, and the scheduler only ever names a request that it rewound.  The positions below `replay_start` were retired and replaced by the null block, whose KV upstream documents as all-zero: a window reaching into them does not read another request's data, it reads phantom keys that score zero and take weight in the replayed token's softmax -- wrong, quiet, and only on a prefix hit. Upstream applies the clamp per request inside its SWA kernel (`start_pos = max(start_pos, replay_start)`); this PR is the Ascend equivalent, in five parts.

- **Read side** (`attention/dsa_v41.py`) -- `build_replay_swa_visible_lens` turns `replay_start` into a per-token visible ori KV length and hands it to `npu_sparse_flash_mla` through `ori_topk_length` in band mode. The operator bounds a window with one scalar for the whole call (`ori_win_left`), which cannot express a per-token floor, so the floor travels on the one channel that can. Every layer reads the ori side from the same `metadata.swa`, so no layer escapes the floor.
- **Write side** (`worker/block_table.py`, `ops/triton/compute_slot_mapping.py`) -- a Triton pass writes `PAD_SLOT_ID` over the replayed positions of every prefix-cacheable group, so the replayed recompute cannot land in blocks still shared with other requests that hit the same prefix. The bounded-replay sliding-window group is the one that keeps writing them, because that write is what rebuilds its window.
- **Carrier** (`worker/model_runner_v1.py`, `attention/utils.py`) -- a per-request `replay_start` buffer on the runner, rebuilt from zero every step on the CPU and carried to the backends on `AscendCommonAttentionMetadata`. It is `None` rather than zeros on a step that does not replay, so a dummy/profiling/capture batch cannot inherit the previous real step's values.
- **Scheduler** (`patch/platform/patch_swa_bounded_replay.py`) -- upstream reports a rewind on `NewRequestData` only, because its V2 runner folds resumed requests into the new-request list. The V1 runner resumes a preempted request through `CachedRequestData`, and a resumed request is exactly the one that can be rewound a second time (preemption clears the computed count, so readmission runs the lookup again), so the field is declared on that payload and filled from the resumed requests.
- **Operator** (`csrc/attention/sparse_flash_mla/`) -- band mode now reads `ori_topk_length` as a per-token visible length and floors the window's left edge at `right - count + 1`: arch22 in the SWA block-vector mask and in the CSA band setup, arch35 in `ComputeS2LoopInfo` before `oriKvLoopEndIdx` (on that path the loop count is the only mask there is). The width stays the scalar `ori_win_left`, so the band remains the upper bound and a supplied count can only narrow it.

`_downgrade_swa_bounded_replay` additionally turns the switch off at startup for the Ascend scheduling modes whose `schedule()` is a pinned copy of an older upstream body: they cannot rewind a prefix hit at all, so they must not have the switch on. `resolve_bounded_replay` keeps upstream's other two conditions and adds nothing of its own.

### Does this PR introduce _any_ user-facing change?

Yes, for DeepSeek-V4.1 on model runner V1 only. Prefix hits now recompute the hit's last window instead of reusing its KV, and the sliding-window group leaves the prefix cache (no new user flag -- upstream's switch defaults to on). That is a trade the feature makes deliberately: the window is rebuilt so it can be bounded at `replay_start`. Other models never read the switch, and the release lane has neither the field nor the constructor argument.

### How was this patch tested?

Unit tests, CPU only (no NPU required), 58 new cases in 5 files:

- `tests/ut/worker/test_replay_slot_padding.py` (19) -- the write side: which group is padded, the pointers and window that reach the kernel launch, and the per-request `replay_start` build.
- `tests/ut/models/test_deepseek_v41_cache.py` (6) -- the read side: the per-token counts for a replayed batch, for a step that does not replay, and for the requests in the same batch that are not replaying.
- `tests/ut/core/test_kv_cache_interface.py` (15) -- the spec gate, and the group merge carrying `bounded_replay` across.
- `tests/ut/core/test_swa_replay_downgrade.py` (9) -- the scheduling modes that must turn the switch off.
- `tests/ut/patch/platform/test_patch_swa_bounded_replay.py` (9) -- the `CachedRequestData` field surviving msgpack and being filled from resumed requests.

**Not executed locally.** This branch was written on a machine without vLLM or an NPU, so the unit tests above and e2e tests have not been run.

**Not yet covered**

1. Operator equivalence for a single `npu_sparse_flash_mla` call: band mode with a count >= the window must be bit-identical to band mode without a count, and with a count below it, equal to band mode with `ori_win_left` narrowed by hand. This is the check that the `csrc` change does nothing when it should do nothing.
2. That the PAD pass really reaches the slot mappings the kernels read -- i.e. that a shared block's KV bytes are unchanged after a replay step.
3. DeepSeek-V4.1 e2e, gsm8k two-pass with the switch on vs off: first pass flat, second within 0.5pt, and a TTFT drop on the second pass.
