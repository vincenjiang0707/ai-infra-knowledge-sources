# [PR #17414] [BugFix][KV Transfer] Report per-group physical KV block sizes in Mooncake P2P transfer metadata

source: https://github.com/vllm-project/vllm-ascend/pull/17414
state: open | updated: 2026-09-24T10:26:28Z
labels: module:tests

## 正文

### What this PR does / why we need it?

`MooncakeConnectorScheduler` emits the KV block size in the P2P transfer
metadata from `cache_config.block_size`. On hybrid (Mamba / linear-attention)
models the logical scheduler block size can legitimately be smaller than the
physical KV block size of the attention groups: the KV-cache group specs are
resolved at runtime per layer (a sliding-window draft layer of a speculative
drafter keeps the kernel-limited 128-token block while all other groups use
1024 tokens), and `EngineCore` then collapses `cache_config.block_size` to the
minimum across groups, which is synced back to the API server. The metadata
then describes block ids counted in 1024-token physical blocks as if they were
counted in 128-token blocks.

Observed on Qwen3.6-35B-A3B (PD disaggregation, `dspark` speculative decoding,
`num_speculative_tokens=7`, TP4/EP): the producer emitted
`remote_block_size=128` and the consumer's kernel expansion asserted on the
first P2P transfer, killing the decode-side EngineCore:

```
AssertionError: remote_block_size(128) not divisible by kernel_size(1024)
```

MTP on the same model is unaffected because its draft layers are full
attention, so every group shares the same (1024) block size and the minimum
does not change the layout.

A single scalar cannot describe a mixed layout — it is only ever correct for
one of the groups, and the receiver expands *every* group with it. This PR
therefore reports the physical block size per KV cache group:

- `MooncakeConnectorScheduler` emits `remote_block_sizes` (one entry per KV
  cache group, same ordering as the block-id lists) from
  `group_transfer_info.tokens_per_block`, the same source the producer already
  uses to count the ids it ships. The scalar `remote_block_size` now carries
  the max across groups (never shrinking the logical value) and is kept for the
  CP path, the `num_prompt_blocks` calculation, and as the fallback for
  metadata produced by an older peer.
- `MooncakeConnectorWorker` expands a group's incoming block ids with that
  group's own physical size, falling back to the scalar when the per-group list
  is absent (legacy metadata) or does not cover the group.

Consistent layouts (e.g. MTP, all groups sharing one size) keep the same
block-size fields as before; the metadata additionally carries the per-group
list, which legacy consumers ignore.

Scope: the consumer expands every group with its own size. A group whose
physical size is larger than the local kernel expands many-to-one (one remote
block covers several kernels, the historical direction). A group whose
physical size is smaller than the kernel and tiles it (e.g. an all-128
producer against a 1024-token consumer kernel) is packed:
`kernel_size // group_size` consecutive remote blocks fill one local kernel
block, the local ids are expanded to the packing-slice index inside each
kernel block, and the transfer addresses each slice — with a loud assert
requiring the remote block stride to tile the local kernel block exactly, so a
layout that cannot be slice-addressed fails loudly instead of misplacing KV.
A size that tiles the kernel in neither direction keeps the historical scalar
fallback and its loud assertion (pinned by unit tests). In the live dspark
deployment the consumer's sliding-window tensors are split into 128-token
blocks (kernel 128), so those groups transfer 1:1 and the packing path guards
deployments where the consumer kernel stays at 1024 tokens. The CP/DCP paths,
which expand every group with the scalar only, reject mixed per-group layouts
with a clear assertion instead of misplacing the mismatched group.

Fixes #17419

The minimum-collapse of `cache_config.block_size` is vLLM 0.28 behavior, not
an Ascend misconfiguration (verified by instrumenting spec construction and
group resolution in a live deployment), so the fix belongs to the consumer of
the value, not to the config plumbing.
(filed upstream: vllm-project/vllm#58362)

### Does this PR introduce _any_ user-facing change?

No API/interface change. It fixes the P2P transfer metadata for hybrid layouts
where physical block sizes differ across KV cache groups (crash -> working
transfer, and correct per-group block-id expansion on the consumer). Layouts
where all groups share one block size emit identical metadata to before, and a
consumer receiving metadata from an older producer still falls back to the
scalar value.

### How was this patch tested?

- New unit tests in `tests/ut/kv_offload/test_mooncake_connector.py`:

  `TestMooncakeConnectorSchedulerTransferBlockSize`
  - desync alignment (logical 128, physical 1024 -> metadata 1024)
  - consistent layout stays unchanged (128 -> 128)
  - fallback to `cache_config.block_size` when group specs expose no integer
    block size (also keeps the existing MagicMock-based scheduler tests working)
  - end-to-end `request_finished` metadata (`remote_block_size=1024`,
    `num_prompt_blocks=1`)
  - per-group report for a mixed layout (1024-token and 128-token groups ->
    `remote_block_sizes=(1024, 128)`)
  - a compressed group (compress_ratio > 1) reports tokens per block id

  `TestMooncakeConnectorWorkerKernelBlockIds` (receiver-side expansion)
  - a group whose size is smaller than the scalar keeps 1:1 ids (the scalar
    would shift them 8x)
  - a group whose size is larger than the local kernel expands and still applies
    the `num_computed_tokens` prefix skip
  - a group whose 128-token physical size is smaller than a 1024-token kernel
    packs 8 remote blocks per local kernel block: local ids expand to the
    packing-slice index, remote ids keep their own granularity, and the prefix
    skip uses the smaller remote token size
  - a packed group trims to a partial remote tail
  - Mamba state groups pass through packing unchanged
  - legacy metadata (empty per-group list) falls back to the scalar
  - a short per-group list falls back for the groups it does not cover
  - a two-group mixed layout (1024-token and 128-token kernels) expands each
    group with its own size
  - a group size that tiles the kernel in neither direction (e.g. 192 against
    a 1024-token kernel) keeps the scalar fallback and its loud assertion
  - the CP/DCP entry rejects mixed per-group sizes and accepts uniform ones

  `TestCoreFunctionality` (transfer byte arithmetic)
  - a packed group addresses pseudo blocks (each covering 1/packing of a kernel
    block) and merges consecutive slices into one contiguous copy

  All pass, and the full Mooncake connector suite is green
  (152 passed in a vLLM 0.30.0 environment).

- Live validation on 910B PD-disaggregation deployment (vLLM 0.28.0,
  Qwen3.6-35B-A3B-W8A8, TP4/EP, dspark K=7, 9 KV cache groups with
  gcd=128/lcm=1024): before the fix the first request crashed the decode
  EngineCore with the assertion above; after the fix requests with 64 and
  384 output tokens complete end-to-end through the proxy with zero
  `not divisible` errors on either side and both instances staying healthy.
  Receiver-side block-id traces on the vLLM 0.30.0 rebuild of the same
  deployment confirm the dspark layout transfers 1:1 (consumer sliding-window
  tensors are split into 128-token blocks, so its kernel is 128 and matches
  the producer), which is the regime the packing path does not alter.

- vLLM main: https://github.com/vllm-project/vllm/commit/ced6857afa0ea7b2e3f0846a62e1394e90f15607
