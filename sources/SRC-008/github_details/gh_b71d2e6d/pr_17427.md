## 正文

### What this PR does / why we need it?

Engram currently treats the global DP group as its table-sharing group and rejects replicas on different nodes. This makes the multi-node DeepSeek V4.1 topologies described in #17236 unreachable on the current implementation.

Use vLLM's node-local Engram DP (EDP) group from https://github.com/vllm-project/vllm/pull/56512 on the current verified pin. Keep the matching grouping backport in Ascend's distributed initialization and cleanup for revisions without that API. Tables remain head-sharded: without shared memory, lookup exchanges stay within TP × local EDP; with shared memory, local DP replicas map the same TP head shard and look up their own tokens. The global DP/EP groups are unchanged.

Reuse upstream Engram CLI parsing, the shared-memory field and validation on the current pin. Keep only the resolver adapter needed to select the Ascend config before CUDA-only validation, together with Ascend-specific restrictions.

For example, dual A3 TP8/DP4 creates EDP2 on each node. TP position 0 uses groups `[0, 8]` and `[16, 24]`, with a separate shared table on each node. TP replicas must stay within one node. Idle replicas retain their participation in non-shared EDP lookups.

Related to #17236. The BF16 checkpoint-loading error is outside this change.

### Does this PR introduce _any_ user-facing change?

Multi-node DP is accepted when TP replicas fit within nodes. `dp_shared_memory` shares tables only among node-local peers and resolves to ordinary TP shards where the local EDP size is one. Explicit sharing still requires CPU offload and global DP > 1. The existing PP/PCP/DCP and uniform-head constraints remain.

The deployment guide now enables host offload and shared memory for dual A3, where 24 heads cannot divide over 16 non-shared local shards. The four-A2 example keeps TP8-sharded tables in device memory. The guide documents the required build and IPC setup; hardware validation scope and tested revisions are listed below.

### How was this patch tested?

- 52 CPU unit tests passed against the updated verified vLLM pin `ced6857afa0ea7b2e3f0846a62e1394e90f15607` (vLLM 0.30.0): `tests/ut/distributed/test_parallel_state.py`, `tests/ut/models/test_engram.py`, and `tests/ut/patch/platform/test_patch_engram_config.py`. Coverage includes topology grouping, upstream-group reuse, destroy/reinitialize, second-node SHM leader rank, local token padding including idle replicas, TP/EDP locality rejection, and CLI/default target and draft config resolution with DBO/load-format rejection.
- A local four-process CPU probe with two simulated node groups passed using real Gloo groups and POSIX shared memory. Distinct per-rank requests matched full-table references with and without sharing, and the two groups had independent shared backing. CANN registration, device lookup, and the row-selection kernel were CPU doubles; physical node discovery was not tested by this probe.
- `bash format.sh ci` and `git diff --check` passed. The format check used an ARM64 gitleaks binary on this ARM host.

Hardware smoke tests passed on the pre-main2main revision `fee3090dc` with vLLM `84030bbe3d74d99bad477a3d2e37a973ccd8865c`, using DeepSeek-V4.1-Flash-W8A8-no-wq-wkv and `cpu_offload=true, dp_shared_memory=true`:

- Dual A3 TP8/global DP4/EP32: logs confirm a 32-rank HCCL world spanning both nodes and EDP2 per node. All four external-DP endpoints became ready, completed FULL decode graph capture, and returned nonempty chat completions. Subsequent serving benchmarks completed without failed requests.
- Dual A3 1P1D, each side TP8/DP2/EP16: proxy requests and serving benchmarks completed, and decode-worker logs recorded cross-node Mooncake KV transfers. This covers P/D compatibility on A3, not the four-A2 EDP1 topology.

These runs used the v0.26.0rc1-a3 image and an existing CANN vendor op pack. They validate the Ascend EDP backport on the old pin; the current head's upstream EDP/config path on `ced6857` has CPU coverage but has not been rerun on hardware. Non-shared multi-node lookup and four-A2 deployment remain unvalidated on hardware. Request checks and single-repeat benchmarks are smoke evidence, not accuracy, sustained-stability or performance sign-off.
