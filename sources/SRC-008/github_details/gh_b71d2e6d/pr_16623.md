# [PR #16623] [BugFix] Capture the default cudagraph ceiling off_grid max_num_seqs 

source: https://github.com/vllm-project/vllm-ascend/pull/16623
state: open | updated: 2026-09-24T12:50:09Z
labels: module:tests, module:core, merge-conflicts

## 正文

With cudagraph_mode FULL_DECODE_ONLY, a max_num_seqs that is not 1, 2, 4 or a multiple of 8 leaves its largest decode batches with no captured graph. Those steps fall back to eager and run about 7.5x slower. The only hint is a "Truncating max_cudagraph_capture_size" warning, which does not say that decode will fall back to eager.

Upstream builds the capture list on a fixed grid -- 1, 2, 4, then multiples of 8 -- and the only off-grid value it adds is max_num_batched_tokens, so the largest entry is the last grid point at or below max_cudagraph_capture_size.
Upstream's own default overshoots (max_num_seqs * decode_query_len * 2), which keeps the configured maximum comfortably inside the list. Ascend deliberately drops that * 2 to save capture memory, which moves the ceiling to the very end of the list, where an off-grid value is unreachable:

```
max_num_seqs=12 -> [1, 2, 4, 8] largest 8, batches 9-12 eager
max_num_seqs=20 -> [1, 2, 4, 8, 16] largest 16, batches 17-20 eager
```
Keep the memory saving and seed the capture list directly instead of the ceiling, adding max_num_seqs * decode_query_len to the grid. This costs exactly
one extra captured graph.

The maximum has to be added to the grid rather than rounded up onto it. A uniform decode batch is one token per request, so num_tokens == num_reqs <=
max_num_seqs; a captured size above max_num_seqs has no batch that can fill it and is never dispatched.

Measured on Qwen3-30B-A3B, EP=4/TP=4, ignore_eos so the decode batch stays constant, best of 3:

```
max_num_seqs=12, batch 12: 69.4 -> 520.0 tok/s (172.79 -> 23.08 ms/step)
max_num_seqs=20, batch 20: 117.8 -> 788.7 tok/s (169.78 -> 25.36 ms/step)
```

Capturing the exact size also beats rounding max_num_seqs up to 16, which pads batch 12 into a 16-wide graph: 520.0 vs 451.0 tok/s.

max_cudagraph_capture_size is left unset so upstream takes it from the list.
That keeps a later pass which drops sizes -- sequence parallelism filtering to TP-divisible values -- a truncation rather than a mismatch between the two fields. A user-supplied max_cudagraph_capture_size or cudagraph_capture_sizes is left exactly as given, and performance_mode="interactivity" is left to upstream, which builds a contiguous 1..min(max, 32) list there that has no grid to fall off.

### What this PR does / why we need it?
This PR introduces a mechanism to restore the Ascend-specific default CUDA graph capture ceiling inside the capture size list. Upstream builds the capture size list on a fixed grid, which can truncate the ceiling if it is off-grid (e.g., max_num_seqs=12 truncates to 8), causing decode batches to fall back to eager mode and run significantly slower. This PR carries the injected ceiling across VllmConfig initialization to append it back to the capture sizes.

Feedback: The current implementation uses a single global variable `_injected_max_cudagraph_capture_size` to carry the ceiling. This is not safe if multiple `VllmConfig` instances are initialized in the same process (e.g., speculative decoding). It is recommended to use a global dictionary keyed by `id(vllm_config)` to prevent nested configurations from overwriting each other.

### Does this PR introduce _any_ user-facing change?
No, this is an internal optimization to prevent fallback to eager execution for off-grid sequence lengths.

### How was this patch tested?
Added unit tests in `tests/ut/test_platform.py` covering various scenarios for restoring the default capture ceiling.
