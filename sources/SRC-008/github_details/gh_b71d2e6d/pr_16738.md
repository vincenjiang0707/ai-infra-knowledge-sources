## 正文

### Summary
Temporary same-environment router acceptance diagnostic. The BF16 direct-linear implementation remains the experiment branch default; the new explicit diagnostic test runs four router variants sequentially in fresh subprocesses within one CI job:

1. Original FP32 router algorithm, including the original cast placement.
2. FP32 router with the unused-cast cleanup retained.
3. BF16 direct F.linear.
4. BF16 native gate wrapper.

Each variant runs twice, reversing the order on the second pass. All variants share the same rebased source, installed dependencies, model cache, hardware allocation, and unchanged DSpark acceptance assertion. Production source is restored in a finally block. The parent diagnostic succeeds when all eight measurements are collected; this does NOT mean all child acceptance assertions passed. Child return codes, acceptance arrays, full generated/prompt token IDs, token hashes, and variant source hashes are printed as ROUTER_AB_RECORD in the uploaded test log.

### Why
Separate comment runs used different base SHAs. The FP32 control also failed once on upstream main, so the previous evidence cannot establish a unique precision root cause. This experiment measures within-arm reproducibility as well as between-arm differences.

### Verification
Ruff check, Ruff format, git diff --check passed. All four generated source variants were syntax-compiled locally and FP32 pre-cast policy checked. NPU E2E is pending via the explicit comment command. This diagnostic bypasses generic gate contracts and modifies the local test checkout transiently; it is not a production-ready fix.
