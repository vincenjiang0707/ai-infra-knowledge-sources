### 🐛 Describe the bug

一、标题
gemma4 系列模型在 910B 上图模式（cudagraph/aclgraph）全部不可用：四种 cudagraph_mode 均无法跑通，12B/31B 共 4 组配置 0/4 失败（Atlas 800T A2 / 910B3, vllm 0.23.0 + vllm-ascend 0.23.0）

二、环境概述
硬件：Atlas 800T A2 单机，8 × Ascend 910B3（每卡 64GB HBM），openEuler 24.03 LTS-SP3 aarch64
软件：vllm 0.23.0（V1 引擎）+ vllm-ascend 0.23.0（源码部署于 /vllm-workspace），Python 3.12.13，PyTorch 2.10.0 / torch_npu 2.10.0.post4，CANN 9.1.0，NPU 驱动 24.1.1，固件 7.5.0.6.220
模型：gemma-4-12B-it、gemma-4-31B-it（model_type=gemma4_unified，Gemma4UnifiedForConditionalGeneration，hybrid attention：sliding_attention/full_attention 交替，head_dim=256，global_head_dim=512；12B 48 层、31B 60 层）
完整环境信息见 vllm-ascend环境信息/env_info.txt（collect_env.py 输出）
本问题不开投机解码（无 speculative-config），纯图模式路径；测试期间未修改 vllm / vllm-ascend 任何源码
三、问题现象
gemma4 在 910B 上关闭 --enforce-eager 后，默认与显式指定的图模式均无法正常服务。

1. FULL_AND_PIECEWISE（默认模式）
日志确认 enforce_eager=False，cudagraph_mode=<CUDAGraphMode.FULL_AND_PIECEWISE: (2, 1)>，4 组全部失败：

组	表现
12B TP1	启动阶段 decode FULL graph capture 第 1 步（0/19）即崩，PagedAttentionOperation 内部错误导致 AclmdlRICaptureEnd 107033，进程直接退出（复测一次同样失败，可复现）
12B TP2	capture 19+19 全部成功、服务 ready（health 200），但第一个真实请求（1024-token prefill 完成后的第一步 decode）即触发 vllm-ascend 运行期 Python 异常，两个 TP worker 同栈（见下），随后 EngineDeadError，后续请求全部 500
31B TP2	PIECEWISE capture 进行到 84%（16/19）时第 17 个 graph 的 AclmdlRICaptureBegin 207005（driver error:resource alloc fail），worker 崩溃
31B TP4	与 31B TP2 完全同型，PIECEWISE 84% 处 207005
12B TP2 首请求崩溃堆栈（两个 worker 同栈）：

File "/vllm-workspace/vllm-ascend/vllm_ascend/compilation/acl_graph.py", line 281, in update_full_graph_params
File "/vllm-workspace/vllm-ascend/vllm_ascend/attention/attention_v1.py", line 715, in update_graph_params
ValueError: not enough values to unpack (expected 22, got 9)
2. FULL_DECODE_ONLY（官网推荐配置）
--compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}'，4 组也全部失败：

该模式确实绕开了 31B 组 PIECEWISE capture 的 207005（31B TP4 decode FULL 19/19 capture 成功、服务 ready），说明 PIECEWISE 阶段问题与 decode FULL 阶段问题相互独立
但 12B TP1 仍在 decode FULL capture 第 1 步崩 107033（两次复现，与 TP 度相关）
12B TP2、31B TP4 capture 成功、服务 ready 后，第一个真实请求的第一次 full-graph decode 100% 触发 attention_v1.py:715 的解包 ValueError（expected 22, got 9），引擎即死——与 FULL_AND_PIECEWISE 下 12B TP2 完全同型，跨图模式确定性复现
31B TP2 在 decode FULL capture 第 1 步崩 107033（PIECEWISE 绕开后失败点前移）
3. 结论
四种 cudagraph_mode（NONE 之外的 PIECEWISE/FULL/FULL_AND_PIECEWISE/FULL_DECODE_ONLY 相关组合均覆盖）下 gemma4 无任何一组能完整服务一个请求。失败模式稳定、跨两次独立测试一致，没有任何一组发生"自动回退 eager"（capture 失败时进程直接崩溃退出，不是降级运行）。

目前 910B 上 gemma4 只能用 --enforce-eager 运行，图编译/算子融合收益完全拿不到，eager 模式下该模型与我们 A100 基准环境的吞吐差距在 15-18 倍量级，图模式不可用是重要原因之一。
