# [PR #17523] [CI] Improve nightly image build and publishing workflow

source: https://github.com/vllm-project/vllm-ascend/pull/17523
state: open | updated: 2026-09-24T17:22:55Z
labels: ci/build

## 正文

### What this PR does / why we need it?
The manually triggered nightly image build workflow previously supported building a specific vLLM commit together with a specific vLLM Ascend commit. However, it had several limitations:

1. `vllm_commit` only accepted a commit hash and could not directly use a vLLM release tag such as `v0.29.0`.
2. Temporary image names truncated the vLLM revision to seven characters. This is appropriate for commit hashes, but truncates release tags and may cause ambiguous image names.
3. The A5 Dockerfiles always cloned vLLM by tag and did not explicitly support checking out an exact vLLM commit.
4. Images built from specified commits were limited to the temporary repository, making it difficult to reuse them as the base image for subsequent `nightly-ci-*` builds.
5. The separate `tag` and `branch` workflow inputs consumed two manual-dispatch input slots and made it difficult to add an explicit publishing option.

This PR updates the nightly image build workflow so that a complete pipeline can be run with specified vLLM and vLLM Ascend revisions:

1. Build the base image from the specified revisions.
2. Optionally publish a daily build using the release-compatible `nightly-main[-suffix]` tags.
3. Reuse that image when building `nightly-ci-main-a2`, `nightly-ci-main-a3`, and other nightly CI images.
4. Run nightly tests against the same vLLM Ascend revision contained in the selected base image.

#### Support vLLM release tags in commit mode

The `vllm_commit` workflow input now accepts either:

- A 7–40 character hexadecimal commit hash.
- A vLLM release tag such as `v0.29.0`, `v0.30.0rc1`, or a supported post/dev release tag.

The image build passes only one corresponding Docker build argument:

- `VLLM_COMMIT` when a commit hash is provided.
- `VLLM_TAG` when a release tag is provided.

This allows release builds to preserve the correct vLLM version metadata, which is required by version-dependent code paths such as `vllm_version_is()`.

The `vllm_ascend_commit` input remains an exact commit hash so that the selected vLLM Ascend source revision is deterministic.

#### Support exact vLLM commits in A5 Dockerfiles

`Dockerfile.a5` and `Dockerfile.a5.openEuler` now accept an optional `VLLM_COMMIT` build argument.

When `VLLM_COMMIT` is provided, the Dockerfile initializes the vLLM repository, fetches the specified commit, and checks out `FETCH_HEAD`. Otherwise, it keeps the existing tag-based shallow clone behavior using `VLLM_TAG`.

This keeps the default A5 build behavior unchanged while ensuring that commit-mode builds actually use the requested vLLM commit.

#### Preserve complete vLLM release tags in temporary image names

For commit hashes, temporary image names continue to use the first seven characters.

For release tags, the complete tag is retained. For example:

```text
vllm_commit=v0.29.0
vllm_ascend_commit=abcdef123456...

vllm-ascend-v0.29.0-abcdef1
```

This prevents release tags from being truncated and avoids collisions between versions that share the same initial characters.

#### Combine Docker branch and tag inputs

The separate `tag` and `branch` workflow inputs are replaced by a single `docker_ref` choice input.

The values are interpreted as follows:

- `main` and `releases/*` select a branch.
- `v*` selects a release tag.
- `tag:main` preserves the previous manual Docker tag behavior for `main`.
- `none` enables commit mode when both revision inputs are provided.

This preserves the existing branch and tag build paths while freeing a workflow-dispatch input slot for the publishing option.

External scripts that manually dispatch the workflow must replace the old `tag` or `branch` parameter with `docker_ref`.

#### Publish specified revisions for downstream nightly CI builds

Commit-mode builds now follow these publishing rules:

| Build type | `publish_nightly_main` | Result |
| --- | --- | --- |
| `release` | `false` or `true` | Publish using `nightly-main[-suffix]` |
| `daily` | `false` | Keep the existing temporary-only behavior |
| `daily` | `true` | Publish using the release-compatible `nightly-main[-suffix]` tags |

The publishing switch only changes daily commit-mode behavior. Release commit builds already publish their final image and therefore do not depend on this option.

When `publish_nightly_main` is enabled for a daily commit build:

- The image is still built with the selected daily dependencies and CANN image.
- The final multi-architecture image is published to the same repository used by release nightly images.
- The final image uses the same `nightly-main[-suffix]` naming convention as a release build.
- The dated daily tag is not used as the final published tag for this promotion path.

For example:

```text
nightly-main
nightly-main-a3
nightly-main-310p
nightly-main-a5
nightly-main-openeuler
nightly-main-a3-openeuler
```

This is required because release-mode nightly CI image builds use images such as:

```text
swr.cn-north-12.myhuaweicloud.com/ascend/vllm-ascend:nightly-main
```

as their base image. Publishing a daily build only with a CANN-versioned and dated tag would not be picked up by the subsequent `nightly-ci-*` workflow.

After promotion, manually triggering a nightly CI build with `build_type=release` produces images such as:

```text
nightly-ci-main-a2
nightly-ci-main-a3
nightly-ci-main-310p
nightly-ci-main-a5
```

These images inherit the exact vLLM and vLLM Ascend revisions already contained in the promoted `nightly-main` base image. The downstream Docker build does not replace them with the latest vLLM Ascend `main` source.

### Does this PR introduce _any_ user-facing change?

Yes. The manual workflow dispatch interface changes in the following ways:

- The previous `tag` and `branch` inputs are replaced by `docker_ref`.
- `vllm_commit` accepts either a commit hash or a vLLM release tag.
- A new `publish_nightly_main` checkbox is available for daily commit-mode builds.
- Release commit-mode builds publish `nightly-main[-suffix]` images directly.
- Daily commit-mode builds can explicitly promote their output to the same release-compatible image names.

The publishing option defaults to `false`, so daily commit builds retain their temporary-only behavior unless promotion is explicitly requested.

Scheduled builds, pull request label builds, and existing daily builds that do not enable this option retain their previous publishing behavior.
