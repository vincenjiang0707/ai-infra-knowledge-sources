[Feature][EC Transfer] Add MemCache-backed L1 encoder cache
### What this PR does / why we need it?

This PR introduces `ECMemcacheConnector`, a MemCache-backed L1 cache
for multimodal encoder outputs. It integrates with vLLM through the
existing EC connector framework and uses the multimodal feature
identifier (`mm_hash`) as the cache key.

Repeated image or video inputs can reuse previously computed encoder
embeddings instead of running the multimodal encoder again.

- Add a scheduler-side MemCache client that checks multiple `mm_hash`
  values in one request and records cache hits and misses.
- Send per-step load/save metadata from the scheduler to workers:
  cache hits are loaded from MemCache, while misses run the encoder and
  publish the resulting embeddings.
- Load multiple encoder outputs directly into preallocated NPU tensors
  with `batch_get_into`.
- Use `KeyInfo.size()` together with the model dtype and encoder hidden
  dimension to reconstruct each cached tensor as
  `[num_encoder_tokens, hidden_dim]`.
- Publish newly computed encoder outputs directly from NPU memory with
  `put_from`.
- Record an NPU event before dispatching the put operation to a background
  thread, so MemCache waits for encoder computation without blocking the
  model-runner thread.
- Save only from TP rank 0 and PCP rank 0. Encoder outputs are identical
  across TP/PCP ranks, so publishing from every rank would duplicate data
  and cause concurrent writes to the same `mm_hash`.
- Keep eviction management inside MemCache. The connector does not add a
  separate local eviction policy.
- Track cumulative cache hits, misses, and hit rate for debugging and
  observability.

This PR also extends MemcacheBackend with:
- batch_get_into, for copying multiple values into flat destination
  buffers.
- put_from, for publishing one value directly from a device buffer.
- Optional transfer-direction arguments for the existing get and put
  wrappers while preserving their previous default directions.
When the connector is not configured, the existing encoder execution and
cache behavior remain unchanged.

Does this PR introduce any user-facing change?
Yes, when ECMemcacheConnector is explicitly enabled.

The connector can be enabled without modifying vLLM:

```bash
vllm serve <model> \
  --ec-transfer-config '{
     "ec_connector": "ECMemcacheConnector",
     "ec_connector_module_path": "vllm_ascend.distributed.ec_transfer.ec_memcache_connector",
     "ec_role": "ec_both",
  "ec_connector_extra_config": {
     "recv_buffer_tokens": 8192
  }
}'
```
