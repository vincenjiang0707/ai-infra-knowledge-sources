### zhaochuang001 · 2026-09-23

This issue appears to match the QLI v2 K-scale address overflow fixed by #16824 (merged into `main`). On A3/arch22, the paged QLI kernel calculated `physical_block_id * key_dequant_scale_stride` using `int32_t`. With a stride of 73,856 elements, the offset overflows starting at physical block ID 29,077, so the kernel can read the wrong K-scale data and select incorrect sparse-attention candidates.

We reproduced this on a two-node A3 DeepSeek-V4.1-Flash W8A8 deployment. In an A/B/A check at physical block ID 29,198, the original kernel matched 0/512 CPU-reference Top-K candidates and produced corrupted output; the rebuilt `int64_t` kernel matched 512/512 and produced normal output; restoring the original kernel reproduced the failure. The PR also adds an A2/A3 high-physical-page regression test.

Please note that updating the `.h` source alone does not fix an already deployed service: the QLI operator must be rebuilt and the installed `.o`/matching `.json` updated, then the service restarted. The issue description does not include the actual physical block IDs or operator binary, so I cannot confirm that every reported bad response has this exact cause; checking whether the deployed QLI binary contains #16824 is the first verification step.
