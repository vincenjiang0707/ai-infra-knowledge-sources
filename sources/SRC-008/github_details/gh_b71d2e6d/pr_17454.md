## 正文


> **Draft — based on vllm-project/vllm#55873 and vllm-project/vllm#55875 (unmerged). Do not merge until the upstream series lands.** This PR tracks the Ascend-side portion of the port proposed in #17352 so the rebase is ready when upstream merges.

### What this PR does / why we need it?

vLLM core (#55875) adds the application-directed Mamba checkpoint state machine to the V1 scheduler: producer chunks clip at the declared checkpoint position, the checkpoint entry is registered behind an unready-hash gate, and waiting consumers sharing the checkpoint prefix are deferred until the committing forward publishes the entry. On Ascend, async scheduling runs `update_from_output` of step N only *after* `schedule()` of step N+1, so the core's readiness publication alone delays consumer wake-up by a full pass.

This PR adds `patch_mamba_checkpoint.py`, following the repository's scheduler-patch pattern (`patch_mamba_block_aligned_split.py`): it wraps `Scheduler.schedule` / `Scheduler.update_from_output` to:

1. publish checkpoint entries whose committing forward was dispatched in the previous pass at pass start (the device executes steps in submission order, so the snapshot is committed by the time this pass's forward runs);
2. mark entries ready in `update_from_output` after their committing forward completes.

Every hook is inert unless the running vLLM provides the checkpoint state (`Request.mamba_checkpoint_position` / `KVCacheManager.mark_checkpoint_ready`) — i.e. until the upstream series lands — so CI and existing workloads are unaffected.

### Dependency on the vllm-core port

The hooks call `Request.mamba_checkpoint_position`, `BlockPool.unready_block_hashes`, `KVCacheManager.mark_checkpoint_ready` / `has_unready_checkpoint` and `MambaManager._cache_checkpoint_block`, which are part of the vllm-core port of #55873/#55875. They are **not** in upstream vllm yet. The reference port (marker input processing, unready-hash gate, mamba checkpoint registration, scheduler deferral) is published on the contributor's vllm fork at [`curnane-lab/vllm:exp/appdir-mamba-checkpoint`](https://github.com/curnane-lab/vllm/tree/exp/appdir-mamba-checkpoint) (based on vllm `568afb3`); when the upstream series merges it is dropped in favor of upstream's implementation and this PR reduces to the hooks above.

### Does this PR introduce any user-facing change?

No by default. The feature is gated on the vllm-core flags `--enable-mamba-checkpoint` / `--mamba-checkpoint-token` (default off). With the flag on, Qwen3.5-class hybrid GDN models on Ascend support application-directed prefix checkpoints; prompts carrying `<|mamba_checkpoint|>` (stripped engine-side) get checkpointed recurrent state at the declared boundary.

### How was this patch tested?

- Unit tests (vllm-core port, 13/13 pass): producer chunk clipping at the checkpoint, unready→wakeup state machine, checkpoint-only caching, hit block table layout, alignment dispatch regression (full-block vs partial-hash), marker extraction/edge cases. Test command: `pytest tests/v1/core/test_mamba_checkpoint_scheduler.py tests/v1/engine/test_mamba_checkpoint_input.py`
- Offline scheduler-trace validation on 910B3 (Qwen3.5-4B, in-process engine): with all 10 requests of a fan-out group added before the first schedule pass, pass 1 schedules only the producer ([0, cp) chunk) and defers the 9 consumers (`waiting_for_mamba_checkpoint=True`); pass 2 publishes the dispatched checkpoint and consumers resume with hits at exactly the declared boundary.
- A/B serving benchmark, Qwen3.5-9B on one 910B3 per arm, 60 groups × 10 requests (1 producer + 9 consumers, shared anchor p≈624 tokens, suffixes 350–658, greedy, 3 reps for the headline config; baseline = same server flags without the marker mechanism):

| geometry | scenario | QPS A→B | TTFT p50 A→B | TTFT p90 A→B |
|---|---|---|---|---|
| unaligned (realistic template case) | 4 out tok | 4.72→5.25 (+11.3%) | 2.03→1.84 (−9.1%) | −12.4% |
| unaligned | 32 out tok | 3.67→4.06 (+10.6%) | 2.05→1.84 (−10.4%) | −14.8% |
| block-aligned checkpoint (cp=1024) | 4 out tok | 6.73→11.07 (+64.4%) | 1.41→0.84 (−40.2%) | −42.3% |
| block-aligned checkpoint (cp=1024) | 32 out tok | 4.86→6.79 (+39.8%) | 1.43→0.85 (−40.5%) | −42.1% |

Actually processed prefill tokens: −53.6% (upstream RFC reports −53.4% on L40S). Isolated single-request correctness (checkpoint resume vs full prefill, greedy, 48 tokens): 11/12 (unaligned) and 12/12 (aligned) exact text match; the single differing case produces degenerate continuations on both sides.

### Known gaps (intentional, tracked for follow-ups)

- The two-phase grouped GDN prefill kernel (#55876 counterpart) is **not** included; consumer resume uses the existing align-mode copy-on-write/restore path. Same-pass producer/consumer pairing is therefore deferred by the existing same-step block guard (correct, one extra pass).
- Multimodal placeholder offset calibration on Ascend (called out in #17352) is pending; the ported input-processing handles the shifts but has not been validated against a vision model.
- MRV1 only (matches the issue's default plan; MRV2 hooks to be confirmed with maintainers per #17352 ask 3).
- Unit tests for the hook wiring inside vllm-ascend's `tests/ut/` are pending and will be added before the PR leaves draft.
