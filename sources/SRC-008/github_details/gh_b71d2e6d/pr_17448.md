## 正文

### What this PR does / why we need it?

  Fixes the GLM c8 issue: the SFA sparse KV cache dtype was wrongly resolved from `attention_config.indexer_kv_dtype` (the indexer's own cache dtype), which is unrelated to the KV cache dtype the user actually configured.

  This PR makes the SFA c8 KV cache dtype follow `cache_config.cache_dtype` (via `kv_cache_dtype_str_to_dtype`), consistent with the upstream change in vLLM main commit `ced6857afa0ea7b2e3f0846a62e1394e90f15607`:

  - `vllm_ascend/attention/sfa_v1.py`: drop the `enable_sparse_li_c8`-based dtype resolution and derive `c8_cache_dtype` from `cache_config.cache_dtype` when `enable_sparse_sfa_c8` is enabled; use it as `dst_type` for the KV repack op.
  - `vllm_ascend/worker/model_runner_v1.py`: compute `c8_cache_dtype` from `cache_config.cache_dtype` for the SFA c8 path and use it in `_reshape_kv_cache_tensors` and `get_kv_cache_spec`.
  - `vllm_ascend/worker/v2/attn_utils.py`: apply the same fix in the v2 `get_kv_cache_spec` so the SFA c8 KV cache spec gets the user-configured dtype.

  As a result, the KVCacheSpec dtype now matches the actually allocated KV cache, and GLM models with a float8 KV cache (e.g. `--kv-cache-dtype float8_e4m3fn` / `int8`) no longer hit cache dtype mismatch / wrong cache dtype on the sparse SFA c8 path.

### Does this PR introduce _any_ user-facing change?

  No. Bug fix only; no new options or config changes.

### How was this patch tested?


- vLLM main: https://github.com/vllm-project/vllm/commit/ced6857afa0ea7b2e3f0846a62e1394e90f15607
