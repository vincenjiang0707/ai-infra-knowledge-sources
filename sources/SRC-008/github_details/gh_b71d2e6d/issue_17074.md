## Follow-up: root-cause refinement + clean calibration data

After further measurement and source reading, we refined the analysis in the original report. The earlier statement that "the four-token group receives only ~1/20th of capacity" was **not accurate** — the actual mechanism is subtler. Corrected findings below.

### Corrected mechanism

The GLM-5.3-Flash hybrid cache has 5 groups (`group_block_sizes=(640, 4, 640, 640, 640)`) sharing **one block-ID space** (`num_blocks`, DeepseekV4-style allocator: `num_blocks = available_memory // Σ(page_size × slots)` in `_get_kv_cache_config_deepseek_v4`, `kv_cache_utils.py:1221`).

Per-request block demand per group:

1. **Four full-attention groups (block_size=640)**: `4 × ceil(tokens/640)` — grows linearly with prompt length.
2. **Mamba group (block_size=4, `mamba_cache_mode="align"`)**: **constant 4 blocks per request** (`1 + num_speculative_blocks`, see `MambaManager.get_num_blocks_to_allocate`, `single_type_kv_cache_manager.py:1054`) — independent of length.
3. **Indexer K-pool group (`AscendIndexerKPoolStateSpec`, a SWA-MLA group with block_size=64)**: sliding-window demand that **saturates at ≈1,795 blocks for prompts ≳115K tokens** (measured), i.e. a fixed floor.

Because one block ID serves all groups simultaneously, the effective budget for the four 640-token groups is:

```
num_blocks − indexer_saturation(≈1795) − mamba(4) ≈ num_blocks − 1799
```

With `num_blocks=2175` only **~376 blocks** remain for the four 640-token groups → **≈60K tokens per request** → matches the measured admission boundary (68,873 tokens OK / ~72,700 hangs).

### Clean calibration (no prefix hits, usage zeroed after each request, dense 0.3 s sampling)

`num_blocks = 2175`:

| Prompt tokens | Peak `vllm:kv_cache_usage_perc` | Blocks in use | Decomposition (4×attn + indexer floor + mamba) |
|---|---|---|---|
| 11,360 | 31.0% | 674 | 72 + ~598 + 4 |
| 22,745 | 90.3% | 1,963 | 144 + ~1,815 + 4 |
| 37,842 | 91.6% | 1,993 | 240 + ~1,749 + 4 |
| 45,929 | 92.3% | 2,008 | 288 + ~1,716 + 4 |
| 64,645 | 94.4% | 2,053 | 408 + ~1,641 + 4 |

The near-constant block usage beyond ~23K tokens is the indexer group's sliding-window saturation (~1,795 blocks ≈ 115K tokens × 64 tok/block), not a fixed leak.

### Why another deployment with the *same image* does not hit this

An identical-image deployment with `--max-model-len 275000 --max-num-seqs 8` gets `num_blocks = 3612`. Same indexer floor (window is a model property), but the remainder for the four 640-token groups is `3612 − 1799 = 1813` blocks → ≈290K tokens per request. A 207,524-token request (`Delaying free of 51881 blocks`, 4-token kernel blocks) completes successfully there, while `--max-model-len 524400` reduces `num_blocks` to 2175 and fails at ~69K tokens.

### Implication

The admission failure is driven by the **indexer K-pool group's sliding-window floor (~1,795 blocks) being carved out of the single shared block-ID space**. For GLM-5.3-Flash the planner effectively reserves the window regardless of the served request lengths, so `num_blocks` (which shrinks as `max_model_len` grows) becomes the only lever:

- `max_model_len ≤ ~300K` → `num_blocks ≈ 3600` → requests up to ~290K tokens pass.
- `max_model_len = 524400` → `num_blocks = 2175` → requests above ~69K tokens hang.

Possible fixes to consider:
1. Reserve the indexer window lazily (only for requests actually exceeding the window), or
2. Exclude the SWA indexer group from the shared block-ID space (give it its own pool), or
3. At minimum, fail fast with a clear error when `4 × ceil(tokens/640) + indexer_floor + mamba > num_blocks` instead of retrying forever in the waiting queue.
