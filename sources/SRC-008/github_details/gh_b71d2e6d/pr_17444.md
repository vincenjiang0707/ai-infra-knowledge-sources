## 正文

### What this PR does / why we need it?

[PR #16640](https://github.com/vllm-project/vllm-ascend/pull/16640) introduces
two standalone AscendC operators that together cover the operator-level
workflow for large-sequence sparse KV cache offloading:

```text
fused_lightning_indexer_manage                fused_scatter_copy_sparse_flash_attention
  LI TopK + sparse-cache management     -->     miss-KV scatter copy + sparse flash attention
  (topk_src/dst, route_miss,                  (consumes the stage-1 metadata
   miss_src/dst, miss_counts)                  with zero host round-trip)
```

To further reduce the HBM footprint of this workflow, we need a quantized
(C8) variant of the stage-1 operator: moving the Lightning Indexer query and
index key cache from bf16 to int8 halves the memory occupied by the index KV
cache, which is the dominant resident buffer of the sparse offload path.

**This PR adds `fused_quant_lightning_indexer_manage` for that purpose.** It
is a drop-in quantized (int8) variant of the stage-1 operator: identical
19-parameter ABI, identical management semantics, and an int8 scoring
pipeline instead of bf16. The miss metadata it produces is bit-compatible
with the stage-2 `fused_scatter_copy_sparse_flash_attention` consumer (same
dtypes, shapes and ordering contracts), so the two-operator workflow of
PR #16640 carries over unchanged.

The primary motivation is **memory-footprint optimization**: the int8 index
KV cache halves the HBM budget of the sparse offload path (index key cache
and the workspace around it), and the performance target is **no
degradation** versus the bf16 stage-1 operator (see the end-to-end results
below).

#### `fused_quant_lightning_indexer_manage`

In a single NPU invocation the operator performs:

- Lightning Indexer TopK retrieval over **int8-quantized** query and index
  key (per-(token, head) and per-token fp16 dequant scales folded into a
  two-stage int8 mma pipeline with a hardware DEQF16 ×2⁻¹⁰ rounding point);
- initialization and steady-state eviction of the HBM sparse KV cache;
- TopK union management for multiple MTP query routes;
- cache-hit and cache-miss classification;
- generation of cache-miss source IDs and destination HBM slots.

A single batch may contain mixed request states, exactly as in PR #16640:

- non-offload requests (`request_state = -3`);
- first-offload requests (`request_state = -2`);
- steady-state offload requests (`request_state = -1`).

Each request supports 1 to 14 query routes (the generalized union path was
verified on-board for Q=8..14). The operator maintains the persistent mapping
from source token IDs to HBM logical slots through `cache_slots_pool`
(in-place update), and rewrites the masked suffix of each TopK row to `-1`
when fewer than TopK keys are visible — the same masked-tail contract that
PR #16640's `fix(ops): pad short LIM top-k outputs` establishes.

The current implementation supports:

- int8 query / index key with fp16 dequant scales, BFLOAT16 index weights
  (versus bf16/fp16 data path with reserved fp32 scales in PR #16640);
- 32 and 64 index heads;
- a fixed index head dimension of 128;
- a fixed TopK size of 2048;
- a cache block size of 128;
- source capacity up to `2^21`, miss buffer capacity 32768 per request;
- Atlas A3 products (ascend910_93), with the A2 build target registered
  alongside, mirroring PR #16640's dual-SoC build list.

#### Interface compatibility with the PR #16640 workflow

| aspect | PR #16640 stage-1 (bf16) | this operator |
|---|---|---|
| parameters | 19 (13 in + 7 out) | identical, same order |
| `cache_slots_pool` | in-place read-write | identical |
| topk / miss outputs | int32, `[T,1,2048]` / `[B,32768]` | identical shapes & dtypes |
| miss metadata semantics | union order, dst-slot landing | identical (verified: deviation vs bf16 variant ≡ quantization noise) |
| scoring inputs | bf16/fp16 + reserved fp32 scales | **int8 + fp16 scales (consumed)** |
| stage-2 consumer | `fused_scatter_copy_sparse_flash_attention` | **same consumer, unchanged** |

This PR only introduces the standalone operator and its operator-level tests.
Framework-side metadata construction, cache-manager integration and model
execution integration are not included and will be submitted separately (same
scoping as PR #16640).

### Does this PR introduce _any_ user-facing change?

Yes.

One new PyTorch custom operator is exposed:

```python
torch.ops._C_ascend.npu_fused_quant_lightning_indexer_manage(...)
```

No existing API, model execution path or default behavior is changed. The
operator is not connected to the vLLM model execution path in this PR.

### How was this patch tested?

The operator was built and tested on an Ascend NPU environment.

Test environment:

- Device: Ascend 910_93 (A3)
- CANN: 9.1.0
- torch_npu: 2.10.0
- OS: Linux aarch64
- Python: 3.11

#### Lightning Indexer and cache-management tests

Test command:

```bash
pytest -sv \
  tests/e2e/nightly/single_node/ops/singlecard_ops/test_fused_quant_lightning_indexer_manage.py
```

Test result: **93 passed** (all scenarios).

The tests mirror the PR #16640 scenario matrix within the quantized ABI,
using the official quantized indexer (`npu_lightning_indexer_quant`) as the
TopK reference, compared as sets — tie order between two int8 pipelines is
not contractual — while every management output is asserted exactly:

- 32/64 index heads;
- all query route counts from Q1 to Q14;
- non-offload, first-offload and steady-state requests;
- mixed request states, mixed batches and lifecycle transitions;
- cache initialization, eviction, hit/miss classification and miss union;
- repeated invocation and all-hit convergence (pool bitwise fixed point);
- miss-occurrence boundaries at 2048/2049/4095/4096/4097;
- long source IDs from `2^17` to near the `2^21` upper limit;
- short-visibility masked-tail `-1` padding;
- invalid inputs (fp32 scales rejected, miss capacity, contiguity, and
  out-of-spec route count rejected on the host with
  `total_queries must satisfy B <= T <= 14B`).

Representative operator-level latency measurements for this operator, the
bf16 fused variant, and both official lightning indexers are included in the
operator's `README.md` (reference data only, not test thresholds), following
the same presentation as PR #16640.

### End-to-end inference results

The operator was evaluated end-to-end with C8 (quantized sparse KV offload)
toggled ON vs OFF on the same build, GLM serving with 29.7K input / 1K output
tokens, 128 requests, concurrency 16, seed 14:

| 指标 | C8 ON | C8 OFF | 差异 |
|---|---|---|---|
| 压测时长 | 234.28 s | 234.40 s | ≈ |
| TTFT avg | 1752.7 ms | 1624.3 ms | OFF 快 7.3% |
| TTFT min/max | 954.9 / 5494.9 | 932.6 / 5396.1 | ≈ |
| TTFT P90 | 4337.7 ms | 4275.5 ms | ≈ (−1.4%) |
| **TPOT avg** | **25.9 ms** | **26.2 ms** | **ON 快 1.1%** |
| TPOT SLO_P90 | 28.0 ms | 28.3 ms | ≈ |
| **ITL avg** | **85.3 ms** | **86.1 ms** | **≈** |
| E2E avg | 28264.9 ms | 28402.7 ms | ≈ (ON 快 0.5%) |
| Output 吞吐 | 559.46 tok/s | 559.18 tok/s | ≈ (−0.05%) |
| 总 token 吞吐 | 16790.6 tok/s | 16782.1 tok/s | ≈ |
| Prefill 吞吐 | 16949.6 tok/s | 18290.1 tok/s | OFF 高 7.9%* |
| QPS | 0.5463 | 0.5461 | ≈ |

Read-out against the operator's goal (**memory-footprint optimization with no
performance degradation**): all decode-path and end-to-end metrics (TPOT,
ITL, E2E, throughput, QPS) are at parity or slightly in favor of C8 ON
(±1% noise band), while the int8 path halves the index KV cache footprint of
the sparse offload. TTFT / prefill throughput shows a ~7–8% overhead under
this stress form, attributed to the offload metadata construction during
prefill, which is amortized over decode and does not affect E2E latency
parity.

These numbers are provided as reference data only and are not used as test
thresholds.
