## 正文

### What this PR does / why we need it?

Optimizes the 310P (`arch20`) unified-core implementations of the two GDN chunked-prefill AscendC operators, `chunk_fwd_o` and `chunk_gated_delta_rule_fwd_h`, and removes the dead code the rewrite left behind.

Measured on Ascend 310P3 (`msprof op`, B1 T4096 Hv8 K192 V128 — the Qwen3.5 GDN shape; 20-iter kernel Task Duration):

| op | before | after | speedup |
|---|---|---|---|
| `chunk_gated_delta_rule_fwd_h` | 2100.9 us | **1043 us** | **2.01x** |
| `chunk_fwd_o` | 1412.7 us | **928 us** | **1.52x** (2.44x vs the pre-series baseline) |

`chunk_gated_delta_rule_fwd_h`:
- Hand mmads replace Catlass `BlockMmadTla` for both cubes via a shared single-tile `M200Gemm::HandMmad` (`csrc/moe/common/kernel_utils/gemm/hand_mmad_310p.hpp`), including a new `A_COL_MAJOR` path for `k^T @ v_update` (Nd2Nz of the stored block + per-fractal-transposed L1→L0A, mirroring Catlass's nZ→zZ transposed-A copy).
- The recurrence state h never leaves the chip mid-task: it lives in L1 as zN f16, one 48 KB bank per interleaved head. Cube1 consumes it as its B operand with no load. The update phase is one fused m=192 tile: mmad → NZ stage → `Axpy` (f32 dst += f16 scale × f16 src folds the decay into the accumulate) → cast → bank writeback, with a strided zN store of the per-chunk h output.
- Cross-op zN h contract: the h tensor between the two ops stays a zN image in GM (one flat 48 KB burst on each side, no Nd2Nz row walk); the host binding pre-packs `initial_state` into slot 0 (varlen-aware).
- v_work is UB-resident (the vnew epilogue consumes the deformat window in place); `exp(g_last)` hoisted to once per chunk; `v_update` loaded once per body instead of per m-tile.
- Host tiling skips the now-unread v_work/h_work workspace regions on 310P (~1.3 MB at 8 cores).
- Cleanup: unreachable `ProcessSplitCore` and the update epilogue file deleted, vnew epilogue reduced to a single buffer bank (750→510 / 365→225 lines).

`chunk_fwd_o`:
- Software-pipelined loads: every GM tile task i needs (Q, K, the h zN burst, v) is issued into its own double-buffered L1 bank at the top of body i, and the whole MTE2 stream runs under task i−1's compute; all three mmads read L1 only. Q+K gate Cube1 through their own flag so it never stalls on the h/v bytes it does not read.
- Vec1 and Vec2 are NZ-native: the causal-mask/decay pass and the o-epilogue both consume the cube staging buffers in place (no NZ→ND deformats; on m200 a UB→UB `DataCopy` issues on the V pipe, so those deformats were pure V-pipe cost). exp(g) broadcasts as one row-block replicated per Z-column, and o leaves UB as one strided zN→ND descriptor per Z-column.
- Cube2's A operand is the same Q tile Cube1 already loaded, kept in a double-buffered L1 slot and reused.

Sync is tool-verified rather than hand-guessed: the kernel bodies are modeled for npu-pipe-optimizer, `auto_flag --validate-existing` reports zero uncovered cross-pipe hazards (it caught one real WAR the first hand fix had only masked), and a checker-proven transitive-reduction pass (`reduce_flags`) justified dropping 9 (fwd_o) / 15 (fwd_h) redundant Set/Wait pairs per body — exposed as `LEAN_TAIL` / `NO_MTE1_MTE2` / `NO_M_MTE1` template flags on `HandMmad`, used only at the proven call sites.

Notable facts encoded in code comments: on m200, UB→UB `DataCopy` issues on the V pipe (not MTE3/MTE2); the 310P kernel entry keeps the 13-param signature in sync with the generated tilingkey wrappers.

910B (`arch22`) paths are untouched.

### Does this PR introduce _any_ user-facing change?

No.

### How was this patch tested?

On-device (Ascend 310P3): 48-shape `chunk_gated_delta_rule_fwd_h` sweep vs an fp64 torch reference — mae bit-identical to the previous implementation at every commit of the series; 24-shape `chunk_fwd_o` sweep plus an exact-mae diag (unchanged, bit-stable); `msprof op` per-pipe profiles for every step. Race analysis with npu-pipe-optimizer kernel models: `auto_flag --validate-existing` at 0 uncovered cross-pipe hazards, every fence removal proven by the `reduce_flags` checker.
