# [PR #16783] [BugFix][Attention] Fix transdata F.pad row/col swap for non-aligned inputs

source: https://github.com/vllm-project/vllm-ascend/pull/16783
state: open | updated: 2026-09-25T08:23:43Z
labels: module:tests

## 正文

**What this PR does / why we need it?**

`transdata` in `vllm_ascend/attention/utils.py` pads a 2-D weight matrix up to a multiple of `block_size` before the NZ (fractal) block reshape. The `F.pad` call passes the row and column pad widths swapped:

```python
nd_mat = F.pad(nd_mat, (0, r_pad, 0, c_pad))
```

PyTorch interprets the 4-tuple from the innermost dimension outward — `(last_dim_left, last_dim_right, dim-2_left, dim-2_right)` — so the code actually pads the **columns** by `r_pad` and the **rows** by `c_pad`, the transpose of the intended `(0, c_pad, 0, r_pad)`.

Consequences for any input not already aligned to the block size:

- The subsequent `reshape((r // b0, b0, c // b1, b1))` receives a tensor of shape `(rows + c_pad, cols + r_pad)` instead of `(r, c)`. When the element count mismatches the call raises `RuntimeError` (e.g. a `(16, 31)` matrix with block `(16, 32)` is padded to `(17, 31)` instead of `(16, 32)`).
- When the element count coincidentally matches, the reshape succeeds but the data is silently misaligned, corrupting the NZ layout.

Both current call sites (`sfa_v1.py:975` `wd_qkv`, `sfa_v1.py:997` `wu_q`) feed dimensions that are multiples of 32, so the padding is a no-op and the bug is latent today; any non-32-aligned weight shape (e.g. new MLAPO model configs) would hit it immediately.

This PR swaps the pad widths to `F.pad(nd_mat, (0, c_pad, 0, r_pad))` and adds CPU unit tests covering a non-aligned input (exact per-block data layout — fails on the old code) and an aligned input (no-op padding).

**Does this PR introduce any user-facing change?**

No. Behavior is unchanged for all currently shipped shapes (where the padding is a no-op); the fix only makes `transdata` correct for non-aligned inputs.

**How was this patch tested?**

- Added regression tests in `tests/ut/attention/test_attention_utils.py`:
  - `test_transdata_pads_rows_and_columns_to_block_alignment`: non-aligned `(5, 6)` input with block `(4, 4)`, asserts both shape and the exact per-block data placement including zero padding (raises `RuntimeError` on the old code);
  - `test_transdata_aligned_input_is_unchanged_by_padding`: aligned `(8, 8)` input verifies the padding stays a no-op.
- Both tests verified offline with a pure-Python simulation of the pad/reshape/permute semantics; the expected tensors were generated and cross-checked independently. Full NPU suite left to CI.
