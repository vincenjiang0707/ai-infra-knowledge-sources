### 🐛 Describe the bug

https://github.com/vllm-project/vllm-ascend/blob/e8f47fc11c81f3eb3efeb9b40400db8b0fa6eef3/vllm_ascend/attention/sfa_v1.py#L610-L611
# `dispose_layer(kv_b_proj)` breaks live weight synchronization for SFA models

## Summary

`AscendSFAImpl.process_weights_after_loading()` disposes `kv_b_proj` after deriving the SFA kernel weights `W_UK_T` and `W_UV`.

This is safe for inference-only decoding, but it breaks live weight synchronization used by RL systems such as VERL. The `kv_b_proj.weight` parameter remains registered, but its tensor storage is replaced with an empty tensor and its shape becomes `[0]`.

When VERL later sends an updated `kv_b_proj.weight` from the Megatron actor, vLLM resolves the destination parameter successfully but cannot copy the incoming weight into the empty destination. The column-parallel weight loader consequently fails with a shape assertion.

## Impact

This blocks live Megatron-to-vLLM weight synchronization for GLM-5.2/SFA rollout workers.

It is especially problematic with:

```yaml
load_format: dummy
```

## Environment

```text
Model: GLM-5.2
Tensor parallelism: TP=4
Rollout load format: dummy
vLLM: v0.23.0
vLLM Ascend: v0.23.0
Megatron-LM: core_r0.18.0
MindSpeed: core_r0.18.0
Megatron-Bridge: v0.5.0
MindSpeed Bridge: v0.5.0
VERL: v0.9.0
```

## Reproduction steps

1. Start a VERL RL job using a Megatron actor and vLLM Ascend rollout workers, with model GLM5.2 (containing `index_topk` so that `AscendSFABackend` is selected).
2. Configure rollout workers with `load_format="dummy"`.
3. Allow initial model post-processing to run.
4. Synchronize the actor weights to the rollout workers.
5. Observe the failure while loading `model.layers.*.self_attn.kv_b_proj.weight`.

The relevant lifecycle is:

```text
Create dummy kv_b_proj.weight
        │
        ▼
AscendSFAImpl.process_weights_after_loading()
        │
        ├── Derive W_UK_T and W_UV
        └── Dispose kv_b_proj.weight
                shape becomes [0]
        │
        ▼
VERL exports updated Megatron weights
        │
        ▼
vLLM resolves kv_b_proj.weight by name
        │
        ▼
Column-parallel loader tries to copy the incoming tensor
        │
        ▼
Shape assertion fails
```

## Actual behavior

Before disposal, the TP-local parameter has approximately this shape:

```text
kv_b_proj.weight: [7168, 512]
```

`dispose_layer()` ultimately applies:

```python
x.set_(torch.empty((0,), device=x.device, dtype=x.dtype))
```

Afterward:

```text
kv_b_proj.weight: [0]
```

During synchronization, the loader attempts to write a normal `kv_b_proj` tensor or TP shard into the empty parameter and fails:

```text
AssertionError: param_data.shape == loaded_weight.shape
```

Representative shapes:

```text
destination parameter: [0]
incoming TP shard:     [7168, 512]
```

The exact incoming shape can depend on where TP sharding is performed, but the destination is no longer a valid two-dimensional parameter in either case.

## Root cause

`dispose_layer()` assumes that the original linear parameter will never be loaded again.

That assumption is valid for inference-only decoding, but not for rollout workers that support live model updates. The optimization invalidates the storage of a registered parameter without making its weight loader reload-aware.

As a result, the model exposes a parameter through `named_parameters()` and `load_weights()`, while that parameter no longer has valid destination storage.

## Suggested fix

Do not dispose `kv_b_proj` when future weight updates are possible:

```python
if not self.live_weight_reload_enabled:
    dispose_layer(self.kv_b_proj)
```

Live reload should be controlled by an explicit configuration/capability flag.

Checking only:

```python
vllm_config.weight_transfer_config is not None
```

may not be sufficient because VERL can use its own ZMQ/IPC transport and call `model.load_weights()` directly.

Checking only `load_format == "dummy"` is also incomplete because a rollout worker may load a real checkpoint initially and still receive later updates.


## Memory tradeoff

For the representative TP-local BF16 shape `[7168, 512]`, retaining `kv_b_proj.weight` costs approximately:

```text
7168 × 512 × 2 bytes = 7 MiB per local SFA layer
```

Inference-only deployments can still use disposal when live reload is explicitly disabled.
