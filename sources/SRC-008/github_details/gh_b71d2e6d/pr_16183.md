## 正文

### What this PR does / why we need it?

Add STAIR for Model Runner V2 EPLB, combining FlashLB-style temporal load modeling and bounded replica search with Swift-style directed rank-pair migration limits. The implementation reuses the existing asynchronous EPLB worker and per-layer commit lifecycle.

- Model STAIR as `StairEplbPolicy(AbstractEplbPolicy)`, so it shares the same upstream abstraction as `DefaultEplbPolicy`. The standard `rebalance_experts` entry point provides placement-only compatibility, while the Ascend runtime uses the same class's richer planning entry point to preserve explicit migration sources, configurable STAIR behavior, and committed-score hysteresis.
- Keep the complete STAIR algorithm in `distributed/eplb/policy/stair.py`. Load statistics, replica search, source-aware placement, slot alignment, hysteresis, validation, and multi-layer planning are methods of `StairEplbPolicy`; only immutable result data carriers remain at module scope.
- Record logical-expert load history for `all`, `prefill`, or `decode` traffic and compress chronological samples before transferring planning data to the CPU. Phase-filtered windows advance only when a matching batch contributes load.
- Skip zero-load or sufficiently balanced layers, and apply hysteresis against the predicted score of the last committed placement.
- Use bounded FlashTree-style replica search and risk-aware LPT placement with a configurable per-layer directed rank-pair transfer cap, defaulting to one expert.
- Support zero redundant experts by exchanging unique experts between ranks when that improves balance. Preserve retained experts' slots and select valid sources while prioritizing fewer cross-node transfers.
- Validate placement and source invariants before broadcast. Require non-worsening mean imbalance and enforce the p95 regression guard; numerical tie tolerance is an internal constant.
- Treat planning failures as no-ops and update hysteresis anchors only after the placement is committed.

Review hotspots are the logical-load window in `distributed/eplb/state.py`, the policy implementation in `distributed/eplb/policy/stair.py`, and the async worker/commit integration in `patch/platform/patch_eplb.py`. User-facing configuration and EPLB documentation are updated together.

### Does this PR introduce _any_ user-facing change?

Yes. MRv2 uses STAIR whenever `--enable-eplb` is enabled; there is no additional algorithm selector. Advanced tuning is available through `additional_config.eplb_config.stair_config`, with defaults for ordinary use.

STAIR supports `load_collection_phase=all`, `prefill`, and `decode`, and it supports `num_redundant_experts=0` by swapping physical expert positions. STAIR selection is internal and does not inspect the upstream EPLB `policy` field. It still requires asynchronous Gloo EPLB and non-elastic EP. Existing MRv1 EPLB behavior is unchanged.

Mean imbalance is the optimization objective; p95 is an admission guard, not a weighted mean+p95 objective. Scores are load-balance proxies, not measured latency improvements.
