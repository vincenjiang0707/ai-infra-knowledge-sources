### 🐛 Describe the bug

`MultiConnector` can crash `EngineCore` while reconstructing KV transfer stats, whenever a child connector is registered under a `kv_connector` config name that differs from its Python class name.

The two vllm-ascend connectors that trigger this are:

- `AscendOffloadingConnector` — registered as config name `OffloadingConnector`
- `UCMConnectorV1` — registered as config name `UCMConnector`

#### Why this is a real code path (not a synthetic mismatch)

The worker and logger sides disagree on the key space of the transfer-stats dict:

1. **Worker emits stats keyed by class name.** `multi_connector.py::get_kv_connector_stats()` builds the dict with `connector_id = c.__class__.__name__` (e.g. `"AscendOffloadingConnector"`). `AscendOffloadingConnector` inherits `OffloadingConnector.get_kv_connector_stats()`, which returns `self.connector_scheduler.get_stats()`; so as soon as offloading is enabled this key is always produced. `MultiKVConnectorStats.to_dict()` serializes it unchanged.
2. **Logger resolves that key through the factory, which is keyed by config name.** `metrics.py::KVConnectorLogging.observe()` calls `self.connector_cls.build_kv_connector_stats(transfer_stats_data)`, where `connector_cls` is the configured `MultiConnector` (here `AscendMultiConnector`).
3. **`build_kv_connector_stats` assumes the two key spaces are identical.** It does `KVConnectorFactory.get_connector_class_by_name(connector_name)` with **no try/except**. That lookup succeeds only for connectors whose registration name equals their class name — true for upstream connectors (`OffloadingConnector`, `NixlConnector`, …) and for `AscendStoreConnector`, but false for the two connectors above.

So this is not a matter of preference: the invariant "every key the worker emits is a registered connector name" is violated by a plugin that overrides an upstream connector with a differently-named class. The result is an unhandled `ValueError` on the stats interval path, which per the field report propagates out of `AsyncLLM.output_handler` and tears down `EngineCore` (in-flight requests then fail with HTTP 500).

The same applies to `UCMConnectorV1`. Note that `AscendSimpleCPUOffloadConnector` (config name `SimpleCPUOffloadConnector`) is **not** affected: it does not override `get_kv_connector_stats`, and the base implementation returns `None`, so no stats key is ever emitted for it.

#### Minimal reproduction (CPU, no NPU required)

The defect is a pure registry-lookup mismatch, so it reproduces on any machine with `vllm==0.28.0` installed. The payload below is exactly what the worker produces in production and what `KVConnectorLogging.observe()` passes on:

```python
from vllm.distributed.kv_transfer.kv_connector.v1.multi_connector import MultiConnector

# Keyed by __class__.__name__, as produced by get_kv_connector_stats().
MultiConnector.build_kv_connector_stats({"AscendOffloadingConnector": {"data": {}}})
```

#### End-to-end manifestation

On the reported deployment (1P1D, `MultiConnector(MooncakeConnectorV1 + OffloadingConnector)`, host-DRAM offload enabled), the first stats interval after a request produces this `ValueError`, the engine exits, and the request returns 500. Patching the registry lookup to resolve the class name yields zero such errors over a full benchmark run.

#### Fix direction

Two complementary changes:

- **vllm-ascend**: register the class names as aliases (`AscendOffloadingConnector`, `UCMConnectorV1`) so the existing lookup resolves — proposed in #16930.
- **vLLM (upstream)**: `MultiConnector.build_kv_connector_stats()` should not hard-fail on a key it cannot resolve; it should skip unknown connectors with a warning and keep the remaining stats. The introducing PR vllm-project/vllm#27366 described exactly this "skip with warning" behavior, but the merged code has no such guard.

#### Workaround

For deployments that cannot wait for the fix, re-register the alias in `vllm_ascend/distributed/kv_transfer/__init__.py::register_connector()` or re-apply the container-level patch described in the internal ops note for this deployment.
