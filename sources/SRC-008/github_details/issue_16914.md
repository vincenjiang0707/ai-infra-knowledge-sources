# [Bug] MegaMoe on Kimi K3 (A3, PD-disaggregated 4P4D) produces garbled output and vector-core crash (acl error 507035)

## Summary

When enabling MegaMoe (`enable_fused_mc2: 2` + `enable_prefill_mc2: true`) for Kimi K3 W4A8 on Atlas 800I A3, **every request returns garbled tokens**, and the prefill nodes eventually **crash with an AI-vector-core exception (`aclrtSynchronizeEvent` error 507035)** followed by glibc heap corruption (`corrupted size vs. prev_size`) on shutdown.

Disabling MegaMoe on the exact same build/environment produces correct output — so the problem is isolated to the MegaMoe path.

**Important note**: MegaMoe enablement for Kimi K3 was **cherry-picked** as commit `5a9de6576` ("feat(moe): enable MegaMoe for Kimi K3") on top of the v0.27.1rc nightly (`67dd25526`). We are not sure whether the issue is introduced by the picked changes or by the interaction between the picked code and the CANN weekly ops package — the full diff of the pick is attached below.

## Environment

- Hardware: Atlas 800I A3 (910_93), 8 nodes x 16 NPU
- Deployment: **PD-disaggregated 4P4D**, both sides DP4/TP16 + DCP16, MooncakeConnectorV1 KV transfer, dspark speculative decoding (draft=7)
- vLLM: 0.27.1 (editable install)
- vllm-ascend: 0.27.1 (editable install, nightly `67dd25526` = `0.19.1rc2.dev1908` + cherry-pick `5a9de6576`)
- CANN: 9.3.0 weekly `20260916.01` (the A3-ops package bundles `cann-A3-ops-transformer_9.2.0`)
- torch_npu / torch: image-bundled (torch_npu 2.10.0)

## Reproduction

1. Launch the PD service with the config above (prefill side MegaMoe enabled).
2. Startup completes normally. Symm-buffer allocation log shows the MC2 group spans **64 EP ranks across the 4 prefill nodes**:

```
CANN MegaMoe sym-buffer alloc (must match across all EP ranks): ep_rank=0 ep_world=64 global_bs=0
```

3. Send any request (even `1+1=?`, max_tokens=24, greedy) through the API.
4. **Actual**: response is garbled tokens. Repeated requests garble every time. On the first run (right after a fresh JIT build of the custom ops), all 4 prefill API servers aborted ~1 min after the first request.
5. **Expected**: coherent output (the identical request returns a correct answer when MegaMoe is disabled).

## Isolation test

Same code build + same CANN 9.3.0 weekly, only difference = MegaMoe flags:

| Config | Result |
|---|---|
| `enable_fused_mc2: 2` + `enable_prefill_mc2: true` | garbled output on every request; vector-core crash (507035) on first run |
| `enable_fused_mc2: false` | correct output (both direct prefill-node request and full P→D path through the load-balance proxy) |

Decode-only nodes with the same build but MegaMoe disabled run stable throughout.

## What we ruled out

- Attention path change: DSA-CP disabled in both runs, attention identical
- KV transfer / decode side: garbled output occurs on a direct prefill-node request that never touches the decode cluster
- HCCL comm kernel: plog says the failing task is not from HCCL
- SiTUGLU support: the weekly `cann_ops_transformer` `mega_moe` signature exposes `activation`/`activation_params`, so the capability check passes
- W4A8 weight packing: `w4a8.py` applies `maybe_trans_nz()` before building `cann_mega_moe_*_weight_list`

## Suspicions

1. `mega_moe_max_tokens=8192` far below the safe upper bound (458752) — but the tiny-request garble suggests something more
2. Version mismatch between the picked code and the weekly CANN package (`cann-A3-ops-transformer_9.2.0` bundled inside 9.3.0 weekly) — the picked code mentions SiTUGLU requires "ops-transformer commit 0a5860c or newer"
3. Cross-node MC2 group topology (ep_world_size=64 spanning 4 nodes, HCCS_SW links) with the symm-buffer handshake

## Requested help

- Whether `mega_moe_max_tokens` must be >= the safe upper bound (458752) for correctness on P nodes, or it only degrades under real overflow
- Whether the picked commit `5a9de6576` is known to work with the CANN 9.3.0 weekly (20260916.01) A3-ops package, and which ops-transformer build it expects
- Any known issue with MegaMoe + W4A8 (A8W4-INT) Kimi K3 + PD-disaggregated prefill (ep_world_size=64)

+### Fused MC2 / MegaMoe prefill capacity
+
+`enable_fused_mc2` and `enable_prefill_mc2` control different behaviors:
+
+- `enable_fused_mc2=1` selects the fused MC2 path (`dispatch_ffn_combine` or MegaMoe).
+- `enable_prefill_mc2=true` sizes the MC2/MegaMoe token capacity from
+  `max_num_batched_tokens` instead of the decode-only ACL graph capacity. It
+  does not enable MegaMoe by itself.
+
+Enable `enable_prefill_mc2` when the fused path can process prefill or startup
+profiling batches larger than the decode-only capacity. Otherwise, the
+MegaMoe symmetric buffer can be initialized too small and CANN may fail during
+tiling with an error similar to:
+
+```text
+num_max_tokens_per_rank is invalid, should be >= bs(512), but got 16
+```
+
+For example, with `max_num_batched_tokens=8192`, TP=16, and a maximum decode
+graph size of 256:
+
+- decode-only sizing reserves `256 / 16 = 16` tokens per rank;
+- prefill sizing reserves `8192 / 16 = 512` tokens per rank.
+
+The second value is required if the startup profile or prefill forward passes
+512 tokens per rank. Keep `max_num_batched_tokens` no larger than
+`tp_size * 512`, as recommended for prefill MC2.
+
+```bash
+vllm serve <model> \
+  --tensor-parallel-size 16 \
+  --max-num-batched-tokens 8192 \
+  --enable-expert-parallel \
+  --additional-config \
+  '{"enable_fused_mc2":1,"enable_prefill_mc2":true,"multistream_overlap_shared_expert":false}'
+```
+
+When fused MC2 is disabled and the prefill batch exceeds the decode-only MC2
+capacity, the normal communication selector can fall back to AlltoAll instead
+of producing this MegaMoe buffer error. Therefore, `enable_prefill_mc2=false`

## Root-cause localization: MegaMoe output is numerically wrong; the crash is a secondary interaction with speculative decoding

With `ASCEND_LAUNCH_BLOCKING=1` (synchronous launches) the first fault surfaces at `get_cos_and_sin_mla` (`vllm_ascend/ops/rotary_embedding.py:94`) during the **dspark draft-proposal step** (`propose_draft_token_ids -> build_draft_attn_metadata -> mla_cp build_decode_metadata`) — i.e., AFTER the full 93-layer target forward with MegaMoe completed without a synchronous error. A probe at that call site shows the gather indices are perfectly legal (`positions min=92 max=99` against a (1048576, 64) cache), so the rotary op itself is innocent — the vector-core fault is pending from an earlier async kernel.

**Decisive bisection — disabling speculative decoding (USE_DSPARK=0, everything else identical, MegaMoe ON):**

- **No crash at all** (0x 507035), engine stays healthy across requests
- But the output is still **wrong**: `1+1=?` -> `"!!!!!!!!!!!!!!!!!!!!!!!!"` (degenerate greedy output), vs `"The answer is 2"` with MegaMoe disabled on the same build

So there are two coupled symptoms:

1. **MegaMoe computes wrong results** — deterministic, input-size-independent, not a crash by itself. This is an operator-correctness bug in the CANN MegaMoe path (weekly ops-transformer) for this workload: Kimi K3 W4A8 latent-MoE (hidden 3584 / intermediate 3072 / 896 experts / top-16), cross-node MC2 group of 64 EP ranks.
2. **The crash requires speculative decoding** — with dspark enabled, the draft/proposal path hits the pending vector-core fault (MTE, non-HCCL task on stream 47) left behind by the MegaMoe forward, aborting all 4 prefill nodes.

Everything else remains ruled out as before (capacity parameter in all forms, x_active_mask — we forced it to `None` and it still crashes, attention path, HCCL task, pick logic audit).
