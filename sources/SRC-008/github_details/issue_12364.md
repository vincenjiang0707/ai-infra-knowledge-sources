state: open | updated: 2026-09-23T02:54:29Z

## 正文

### 🚀 The feature, motivation and pitch

**Feature:** Add support for using the standard `vllm-project/router` (the Rust
router, `pip install vllm-router`) as the front-end for PD-disaggregated
serving on Ascend, i.e. make the vLLM-Ascend Mooncake P2P connector
interoperable with the router's Mooncake PD path (`--vllm-pd-disaggregation
--kv-connector mooncake`).

**Motivation / problem:**

Today, the only supported way to drive multi-instance PD disaggregation on
Ascend is the example script
`examples/disaggregated_prefill_v1/load_balance_proxy_server_example.py`
(adapted from vLLM's NIXL `toy_proxy_server.py`). This works, but it is
explicitly an *example* single-process FastAPI proxy, and it does not scale
well to large deployments. We would like to use the
production-grade `vllm-project/router` instead, as is already possible on the
GPU/Mooncake path.

The blocker is a **handshake-model mismatch** between the router's Mooncake PD
support and the vLLM-Ascend Mooncake P2P connector:

- The router's Mooncake path performs **active discovery**: at startup it queries
  each prefiller's **Mooncake bootstrap server** over HTTP (`/query`) to learn
  the per-DP-rank `engine_id`, then injects
  `transfer_id` / `remote_bootstrap_addr` / `remote_engine_id` into each
  request's `kv_transfer_params`.
- The vLLM-Ascend P2P connector
  (`vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_connector.py`) uses a
  completely different, **passive** model: each prefill worker opens a **ZMQ
  ROUTER side-channel** (`handshake_port = side_channel_port + device_index`)
  and exchanges a msgpack-encoded `MooncakeAgentMetadata` on demand
  (`GET_META_MSG` → metadata → `batch_transfer_sync_read`). **There is no HTTP
  bootstrap server and no `/query` endpoint at all.** The `kv_transfer_params`
  (`remote_host` / `remote_port` / `remote_engine_id`) are relayed passively
  through the request/response body by whatever proxy sits in front.

Because the connector exposes no bootstrap server, the router's discovery step
has nothing to query, so the standard router cannot currently be pointed at an
Ascend PD deployment. Users are effectively locked into the example proxy.

**Pitch — a few possible directions (any one would unblock us):**

1. Add an HTTP bootstrap `/query`-compatible endpoint to the Ascend Mooncake P2P
   connector, exposing per-DP-rank `engine_id` in the schema the router expects,
   so the router's existing Mooncake path works unchanged; **or**
2. Provide/document a **passthrough / relay** mode in the router (no bootstrap
   discovery, just relay `kv_transfer_params` from the prefiller response) that
   matches this connector's passive model; **or**
3. Provide an official adapter/shim so the router can drive the ZMQ side-channel
   handshake used here.


### Alternatives

- **Current workaround:** keep using
  `load_balance_proxy_server_example.py`. It functions (flat single pool of
  prefill/decode clients, passive `kv_transfer_params` relay, so multiple
  independent EP groups are transparent to it), but it is a single-process
  example proxy, not intended as a production load balancer, and it lacks the
  routing policies / throughput headroom of `vllm-project/router` at 10s of
  endpoints.
- We considered pointing the router at the connector directly with
  `--kv-connector mooncake`, but it fails because there is no bootstrap server
  for the router to discover (see above).


### Additional context

`vllm-project/router` currently exposes only *active-discovery*
PD modes — either `--vllm-discovery-address <addr>` (external discovery
service) or `--kv-connector mooncake` (which, per the router README/PyPI docs,
"queries each prefill node's Mooncake bootstrap server at startup to learn
engine_id per DP rank"). There is **no passthrough/relay mode** that simply
forwards the `kv_transfer_params` returned in the prefiller's response.

The vLLM-Ascend Mooncake P2P connector provides neither of these: no HTTP
bootstrap server for the Mooncake path to query, and no discovery endpoint for
`--vllm-discovery-address`. It relies purely on ZMQ side-channel metadata
exchange + passive relay of `kv_transfer_params`. As a result the router cannot
currently front an Ascend PD deployment through either mode — this is a missing
capability, not a misconfiguration.
