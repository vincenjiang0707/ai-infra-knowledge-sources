source: https://github.com/vllm-project/vllm-ascend/issues/16944

## 正文

### Your current environment

<details>
<summary>当前实现是先初始化memcache，再进行cpu binding。本rank处于cpu binding时，可能其它的rank正与此rank进行memcache建链，容易造成建链超时</summary>
```text
环境信息是：A2
memcache配置成使用 device-rdma
模型选择 deepseek-v4-flash
节点个数4节点（2P2D）
```
</details>


### 🐛 Describe the bug

初始化memcache 和执行 bind_cpus的调用顺序关系如下：
```
initialize_from_config():
  collective_rpc("initialize_from_config")        abstract.py:123
     └─ NPUWorker.initialize_from_config           worker.py:907
        └─ ensure_kv_transfer_initialized          worker.py:909
           └─ MemcacheBackend._setup_store()       memcache_backend.py:58
              └─ store.init()          ← MMC 初始化

  collective_rpc("compile_or_warm_up_model")       abstract.py:124
     └─ NPUWorker.compile_or_warm_up_model         worker.py:706
        └─ bind_cpus()                 ← CPU 绑定
```

在bind_cpus时，主要做以下事情：
| 阶段 | 作用 | 关键位置 |
| --- | --- | --- |
| `build_cpu_pools()` | 按设备类型计算每个 NPU 的 CPU 池。A2/310P/A5 用 `topo_affinity`（读 `npu-smi info -t topo`），A3 用 `global_slice`（按全局逻辑 NPU 号均分，保证多进程不重叠）。A5 额外绑 host 的 `uvb_poll_window_thread` | `cpu_binding.py:538` |
| `allocate()` | 角色切分：默认最前 2 个 CPU 给 IRQ，最后 2 个分别给 `acl_thread`、`release_thread`，中间给主进程；每 NPU 至少 5 个 CPU。A5 整个池给主进程 | `cpu_binding.py:606` |
| `print_plan()` | 打印分配计划 | `cpu_binding.py:625` |
| `bind_threads()` | `taskset -acp` 绑主进程及子线程，`taskset -cp` 绑 `acl_thread`/`release_thread`；再用 `migratepages` 把该进程内存页迁到 NPU 所在 NUMA | `cpu_binding.py:677-694` |
| `bind_npu_irq()` | 写 `/proc/irq/<id>/smp_affinity` 绑 NPU 的 `sq_send_trigger_irq`/`cq_update_irq`；A5 跳过 | `cpu_binding.py:702` |

其中的在 `migratepages`（`cpu_binding.py:643`）：耗时正比于当时进程 RSS。此时 KV cache、权重、graph 内存都已分配，大模型下可能是**数秒到数十秒级**。
在这个过程中，本rank memcache已初始化完成，其它rank若刚启动，正处于init_mmc 阶段，会向本rank建链，本rank处于migratepages无法响应，会最终让建链超时。

另外，由于memcache分配的dram过程是在bind_cpus之前，这样分配的内存不具备numa亲和性，影响后续缓存的访问性能。
