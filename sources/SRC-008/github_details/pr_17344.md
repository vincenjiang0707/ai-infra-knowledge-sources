# [PR #17344] [v0.26.0rc][BugFix][MoE] Guard fused MC2 dispatch against silent capacity truncation

source: https://github.com/vllm-project/vllm-ascend/pull/17344
state: open | updated: 2026-09-23T03:54:45Z
labels: module:ops

## 正文

### What this PR does / why we need it?

Fixes silent output corruption in the fused MC2 MoE path (`enable_fused_mc2=1`) for long-context prefill.

**Root cause.** The `dispatch_ffn_combine` op sizes its internal per-rank token buffers from `max_output_size` and **silently discards work** once the per-rank post-dispatch token count reaches it:

```cpp
if (preCurrentmSum >= params.maxOutputSize) { currentM = 0; }
else if (preCurrentmSum + currentM > params.maxOutputSize)
    currentM = params.maxOutputSize - preCurrentmSum;
```

No error is raised — the affected tokens simply receive a corrupted MoE output, which surfaces as repeated/garbage tokens (issue #16941) and destroys the argmax margin.

`additional_config.mega_moe_max_tokens` is documented (`ascend_config.py`) as sizing **both** the op's `max_output_size` **and** the CANN MegaMoe symmetric buffer's `max_recv_token_num`, but only the op side was effectively guarded. The mean post-dispatch count per rank is `num_tokens * num_experts_per_tok`; measured load reaches **~4.9x that mean** on GLM-5.2 w4a8 / A3 / EP16, so the historical `65536` default does not cover long-context prefill chunks.

**Measured** (GLM-5.2-w4a8, A3, EP16, `--max-num-batched-tokens 8192` with 4-way context parallelism → 2048 tokens per rank per op call, topk 8):

| | per-rank post-dispatch load |
|---|---|
| median | 14,923 |
| p99 | 44,332 |
| max | 70,990 |
| single expert max | 31,711 (4.3x mean, **108% of the 65536 default**) |

Same service, same 67531-token request, greedy, 512 tokens:

| op capacity | peer buffer | truncated calls | clean requests |
|---|---|---|---|
| 65536 | 65536 | 9 / 58800 | 0 / 6 |
| **131072** | 65536 | 0 / 58800 | 6 / 6 |
| 131072 | 131072 | — | 6 / 6 |

Reproduced independently with `mega_moe_max_tokens=8192` on a 67531-token prompt: **273/288 op calls truncated and 28/288 produced NaN rows**, while the same request with `65536` answers correctly.

**Changes:**

- `_fused_mc2_required_capacity()` — rank-invariant lower bound derived **only from compile-time configuration** (the symmetric buffer is allocated by a collective handshake, so every EP rank must compute the same value):
  `max(token_dispatcher.max_num_tokens_per_rank, global_bs // ep_world_size, max_num_batched_tokens // tensor_parallel_size) * num_experts_per_tok * 8`. Cached, logged once.
- `_fused_mc2_capacity()` — `max(configured, required)` plus a one-time warning naming both buffers and the `--max-num-batched-tokens` alternative.
- Use it for **both** the op's `max_output_size` and the P / PD-mixed peer buffer (`max_recv_token_num`), instead of the raw configured value.
- `_verify_fused_mc2_no_truncation()` — raise instead of returning silently corrupted tokens. Skipped when truncation is provably impossible (`num_tokens * topk * ep_world_size < max_output_size`), so the decode path stays free of device syncs.
- Pass a **copy** of `topk_ids` as `expert_idx`: the op rewrites non-active entries in place (`ApplyXActiveMask` writes `expertPerRank * EP`), mutating the caller's routing tensor.

### Does this PR introduce *any* user-facing change?

Yes, two ways:

1. **Long-context prefill output changes** — previously silently corrupted under the fused MC2 path, now correct.
2. **Memory cost**: raising the capacity from `65536` to `131072` takes **21632 KV cache tokens** on this model (207744 → 186112, **−10.4%**), because the operator workspace and the peer buffer scale linearly with the value. Lowering `--max-num-batched-tokens` shrinks the requirement by the same factor if the KV cache is needed. A one-time warning states the value in use and how to silence it.

Previously valid configurations keep their exact behaviour when the computed requirement does not exceed the configured value.

### How was this patch tested?

- **Operator capacity A/B** (table above): identical request, capacity switched at runtime — `65536` → 9/58800 truncated, 0/6 clean; `131072` → 0/58800 truncated, 6/6 clean.
- **Minimal repro** with `mega_moe_max_tokens=8192` on a 67531-token prompt: 273/288 calls truncated + 28/288 NaN rows before; correct after.
- **Changing the op capacity alone** is sufficient for this workload, which confirms silent truncation is the root cause of the garbled long-context output. The peer buffer is raised as well so both stay consistent, as the vendor comment requires.

### Remaining (not addressed here, needs the operator side)

The fused MC2 path is **still not bit-reproducible**. Two identical greedy prefills of the same 67531-token prompt disagree on **17–36%** of positions at capacity `65536` and on **1–2%** at `131072` (top-1 agreement 0.64–0.83 per position bin), while `enable_fused_mc2=0` is bit-exact. The truncation fix roughly halves the drift but does not remove it.
