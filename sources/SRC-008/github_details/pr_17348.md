# [PR #17348] [BugFix][Engram] Skip HOST_UVA page migration during CPU binding

## 正文

### What this PR does / why we need it?

Fixes #17286.

With Engram HOST_UVA offload, post-warmup CPU binding runs `migratepages` after the large host tables have already been registered and pinned. Migrating the whole worker can stall startup for many minutes, and DP replicas sharing a backing can request different NUMA destinations.

Keep CPU thread and IRQ affinity at the existing post-warmup/post-capture point, but skip process-wide page migration when `engram_config.cpu_offload` is enabled. Move the migration call out of the thread-binding methods so it can be skipped independently. Other configurations retain the existing migration behavior and ordering.

### Does this PR introduce _any_ user-facing change?

Engram HOST_UVA workloads can keep CPU binding enabled without the process-wide `migratepages` startup stall. No new configuration is required. Shared-table placement and selective page migration are outside this fix.

### How was this patch tested?

- The complete existing CPU-binding and V1 worker unit-test files passed (151 tests). Only existing CPU-binding expectations were updated for the migration call location and argument forwarding. No new test cases were added; mock-only tests cannot reproduce the pinned HOST_UVA page-migration stall, which was validated on hardware as described below.
- `bash format.sh ci` and `git diff --check` passed.
- The same production-code change was validated earlier on A3, CANN 9.1, 16 NPUs, TP2/DP8, shared Engram HOST_UVA, async scheduling, DSpark5 with eager draft, and FULL_DECODE_ONLY, against Ascend `2cd0042f1` and the vLLM pin below. All 16 workers completed post-capture affinity binding in 4–7 seconds; 1,257 measured requests succeeded. Two fixed 128-token probes matched the no-binding control exactly in tokens and logprobs. This was standalone serving under UID 1000; IRQ writes were skipped due to permissions, and full P/D was not rerun on this PR head.
