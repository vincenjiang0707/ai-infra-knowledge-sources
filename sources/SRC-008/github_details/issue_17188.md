### 🐛 Describe the bug

GLM-5.3-Flash-w8a8基于0day镜像（quay.io/ascend/vllm-ascend:glm-5.3-flash）部署PD分离（1P+1D），出现以下报错：
1、P/D节点启动报错：Assertion failed, Hybrid models do not support recompute mode kv load failure policy now.
规避方案：将`--kv-transfer-config`参数中 "kv_load_failure_policy": "recompute" 修改为"kv_load_failure_policy": "fail" 

2、Curl测试D节点崩溃：AssertionError: remote_block_size(4) not divisible by kernel_size(128)
规避方案：将`--kv-transfer-config`参数中  "kv_connector": "MooncakeConnectorV1"修改为 "kv_connector": "MooncakeHybridConnector"

3、Curl测试乱码D节点报错：ValueError: operands could not be broadcast together with shapes (0,) (3,)
规避方案：将P节点所有配置和D节点修改一致。

4、Curl测试乱码D节点报错：`RuntimeError: Mooncake transfer failed, ret: -1`
规避方案：无

你可以参考一下我的环境 （4P4D+MoonCake），运行情况可见#16984：
### 我们生产环境的完整配置（跑了一周 + 384 请求压测验证）

**P 节点（prefill）**：

```
--kv-transfer-config {"kv_connector":"MooncakeConnectorV1","kv_role":"kv_producer","kv_port":"30000","engine_id":"$POD_NAME",
  "kv_connector_extra_config":{"use_ascend_direct":true,"prefill":{"dp_size":1,"tp_size":8},"decode":{"dp_size":1,"tp_size":8}}}
```

**D 节点（decode）**：同款，只改 `"kv_role":"kv_consumer"` 和 `"kv_port":"30100"`。

配套的还有：`--block-size 640`、`--reasoning-parser glm45 --tool-call-parser glm47`，以及网络面 `GLOO/TP/HCCL_SOCKET_IFNAME=bond1`、`HCCL_IF_IP=<本机 IP>`。P/D 两端的 config 除 role/port 外**逐字一致**（这正是你报错 3 的规避方向）。

### 对你现在这套（0day 镜像 + 1P+1D）的建议

你用 `MooncakeHybridConnector` 绕过报错 2 之后再连撞报错 3（shapes broadcast）和报错 4（transfer failed ret:-1，乱码说明 KV 数据根本没通）——我建议**别在 hybrid connector 上继续修，回退到 ConnectorV1 + ascend_direct**，理由：

1. `MooncakeHybridConnector` 是给**异构 PD KV 传输**准备的组件（vllm-ascend PR #16962，9 月中才加），你的 1P+1D 如果两边都是 910B，同构场景用它是绕路；它自身也很年轻，报错 3/4 大概率是它对 GLM-5.3 KV 布局的适配问题，而不是你的配置错。
2. `use_ascend_direct: true` 是 vllm-ascend 官方 GLM PD 配方的一部分，且在我们 4P4D 生产上稳定验证过（KV 拉取 181K 实测 0.35–2.1s，零失败）。按上面模板改，大概率把报错 2/3/4 一起消掉。
3. 报错 1 同理：我们没配 `kv_load_failure_policy`（用默认），GLM-5.3 是 hybrid 模型、不支持 recompute 策略——你删掉这个参数或设 "fail" 即可，这条你的规避方向没错。
