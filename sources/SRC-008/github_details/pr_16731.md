## 正文

### What this PR does / why we need it?

Replace the remaining plugin-owned quantized Lightning Indexer and standard MoE gating kernels with the corresponding CANN operators exposed by `torch_npu`. This removes duplicate kernel code and its build and Torch registration paths.

- `BaseDeviceAdaptor` now calls `torch_npu.npu_quant_lightning_indexer` for the quantized Lightning Indexer path. Both the base and A5 paths pass `INT64_MAX` for the native `pre_tokens` and `next_tokens` arguments; A5 already used this native operator before this PR.
- `BaseDeviceAdaptor.moe_gating_top_k` now calls `torch_npu.npu_moe_gating_top_k`, maps `bias_opt` to the native `bias` argument, forwards the other routing options, and continues returning expert IDs as `int32`. The existing A5 override is unchanged.
- Remove the `lightning_indexer_quant` and `moe_gating_top_k` custom kernel directories, their `build_aclnn.sh` entries, and the `_C_ascend.npu_lightning_indexer_quant` and `_C_ascend.moe_gating_top_k` bindings and meta implementations. The hash router and quantized Lightning Indexer V2 implementation remain.
- Update the MoE device and nightly tests to exercise the adapter and update the SFA unit test to check the native LI call arguments.

### Does this PR introduce _any_ user-facing change?

Yes. The affected paths use the CANN operators through `torch_npu`. The `DeviceOperator` interface remains, including `int32` expert IDs for standard MoE gating. Direct calls to the removed private `torch.ops._C_ascend.moe_gating_top_k` and `torch.ops._C_ascend.npu_lightning_indexer_quant` schemas need to migrate to the native APIs.

### Kernel performance comparison

This pre-rebase comparison was run on CANN 9.2.0-beta.2 and Ascend 910B4-1 with isolated old/native processes. Each case used 50 warmups and 20 `torch_npu.profiler` samples; the reported value is the median target-kernel `Duration(us)`, excluding input generation, H2D copies, compilation, correctness checks, and profiler setup. CV is the population standard deviation divided by the sample mean.

- `lightning_indexer_quant`: 19 eligible cases covering prefill/decode, variable lengths, sparse counts, 127/128/129 block boundaries, TND and PA_BSND layouts, masked/unmasked modes, and tied scores. Across all cases, the old/native median kernel durations were `24.98 us / 22.87 us`. Representative measurements were `19.99 us / 15.38 us` at the 128-token block boundary and `42.94 us / 41.70 us` for the long sparse case. The two non-64-head cases were excluded because the old custom kernel raised an AICore address/UB error before profiling.
- `moe_gating_top_k`: 292 cases covering the baseline matrix plus large shapes, FP32/FP16/BF16, bias, group configurations, Softmax/Sigmoid, renorm, `out_flag`, and routed scaling factors. Across all cases, the old/native median kernel durations were `3.70 us / 4.40 us`; for the 16 large-shape cases they were `18.15 us / 18.75 us`. Representative large cases were `64.90 us / 64.55 us` for FP16 2048x256 and `119.30 us / 119.87 us` for FP16 2048x512. The measurements are in the same microsecond range overall; the native implementation does not show a general MoE kernel-time improvement in this matrix.

The complete per-case kernel tables and raw CSV/JSON results are retained with the test artifacts used for this comparison. These results are kernel-only and eager-mode; no graph capture/replay performance claim is made.
