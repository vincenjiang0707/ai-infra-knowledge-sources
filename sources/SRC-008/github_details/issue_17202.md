## 正文

### Environment

- Hardware: Atlas 800I A3 (910_93), 16 NPUs, supernode deployment
- Deployment: Kimi-K3 (W4A8, reduced-layer variant, 13 MoE layers) TP16 = EP16, PD-separated prefill node, `max_num_batched_tokens=8192`, MoE `topk=16`
- Software: vLLM 0.27.1 + vLLM-Ascend megamoe integration branch (0.27.1-based), CANN 9.2.0, cann_ops_transformer_custom mega-moe wheel
- The failure lives in the CANN MegaMoe op / HCCL layer, so it is expected to reproduce on any base using the same wheel (current `main` not re-tested, see "Scope" below)

### Symptom

With `mega_moe_max_tokens=6144` (the default in the 0.27.1-era megamoe integration), the service **hard-crashes on the first long-prefill request**:

```
Worker_TP6 SUSPECT REMOTE ERROR 507057
```

All in-flight requests fail (30/30 in the repro), the engine dies. This is not recoverable.

### Root cause analysis

`mega_moe_max_tokens` is not a tuning knob — it is passed to the CANN MegaMoe op as `max_recv_token_num` and participates in the **collective symmetric-memory handshake** (`moe_comm_method.py`, `get_symm_buffer_for_mega_moe` path): it declares "the maximum number of tokens this rank may receive after MoE dispatch". The value must be identical on all EP ranks, and must be >= the actual per-rank received token count.

The actual received count is deterministic under load:

```
prefill chunk                  = 8192 tokens/step
dispatch replication (topk)    = 16
global token-expert pairs      = 8192 x 16 = 131072
balanced per-rank receive (EP16) = 131072 / 16 = 8192 tokens
```

So **even with perfectly balanced expert load, every rank receives ~8192 tokens** (more under expert hotspots). `6144 < 8192` → the symmetric receive window overflows → HCCL collective state is corrupted → hard error `507057`.

The "SUSPECT REMOTE" signature is expected: the window is a collectively-registered HCCL resource, so the violation surfaces from the group's shared state — the reporting rank (TP6) is not the root cause.

### Gap vs. documented behavior

The config docstring and the `warning_once` in `moe_comm_method.py` describe undersized values as causing **token truncation -> precision degradation** (a soft failure). We observed a **hard crash** instead, on the very first long prefill. The real-world failure mode is one severity class worse than documented, and is not detectable as a precision issue beforehand.

### Evidence

| `mega_moe_max_tokens` | Result |
|---|---|
| 6144 (previous default) | First long prefill request: `SUSPECT REMOTE ERROR 507057` at Worker_TP6, 30/30 requests fail, engine dead |
| 65536 (current main default) | Clean; 120/120 bench, deterministic |
| 0 (auto) | Clean; two identical runs show **zero token divergence and zero logprob drift**; throughput/TTFT equivalent to 65536 within noise |

Repro: 30 real-world prompts (with system prompt), `temperature=0`, `max_tokens=1`, logprobs requested; the first long prompt (chunked prefill over 8192) triggers the crash.

### Why the framework cannot statically reject undersized positive values

The safe lower bound is a function of runtime load distribution (chunk size x topk / EP size, expert hotness), not of static config. The framework can only reject clearly invalid values (PR #17162 adds `>= 0` validation with a fast failure at startup). Undersized *positive* values need guidance or op-side support:

1. **Op-side (preferred)**: `get_symm_buffer_for_mega_moe` could return the required lower bound for the given config, so the framework can validate at startup; or the op could fail with a clear "received X tokens > max_recv_token_num Y" error instead of a raw HCCL `507057` far from the root cause.
2. **Docs**: recommend the default `65536` or `0` (auto). On A3, `0` costs no extra HBM (the A3 buffer formula is decoupled from this value; the op expands to its internal safe upper bound). The knob is only meaningful as an HBM-saving lever on A2 (910B) where the buffer scales linearly with it.

### Scope

Verified on the 0.27.1-based megamoe integration branch + CANN 9.2.0. Not re-tested on current `main`, but `main` uses the same op/wheel and the same `mega_moe_max_tokens` -> `max_recv_token_num` chain on P/PD-mixed nodes (decode-only nodes already use the absolute safe bound), so the mechanism applies unchanged.

Related PR: #17162 (startup validation for negative values + `0 = auto` documentation).

...and the service then hard-crashes on the next forward:

(Worker_TP0_EP0 pid=598) ERROR [multiproc_executor.py:991] RuntimeError: synchronize:../torch_npu/csrc/core/npu/NPUEvent.cpp:215
    NPU function error: aclrtSynchronizeEvent(event_), error code is 507015
(Worker_TP0_EP0 pid=598) ERROR [ERROR] 2026-09-22-07:12:08 (PID:598, Device:0, RankID:-1) ERR00100 PTA call acl api failed

Notes:

- The concrete error signature differs from the 0.27.1-era observation (`SUSPECT REMOTE ERROR 507057` at a worker): on `main` it surfaces as `aclrtSynchronizeEvent` failure with code `507015` / "aicore execution is abnormal" on rank 0. Both are HCCL-family hard failures from the same capacity-contract violation — the code seen depends on where the corruption is first detected.
- Sequence "small request OK → long prefill dead" matches the capacity mechanism exactly: a tiny prefill stays under `6144` received tokens; the 8192-token chunk with topk 16 / EP16 pushes per-rank receive to ~8192 > 6144.
- The `warning_once` text ("precision degradation will occur") underestimates the real failure mode — an unrecoverable engine death, not degraded output.

This strengthens the case for an op-side clear capacity error (or exposing the required lower bound) instead of a raw HCCL/AICORE failure far from the root cause.
