### Describe the bug

The checkpoint is recognized as ModelSlim `W8A8_DYNAMIC` and all weights finish loading. Startup then fails consistently during:

```text
EngineCore.determine_available_memory -> profile_run
```

The device DFX log identifies the actual faulting kernel:

```text
QuantBatchMatmulV3_NZ_NZ_int8_int8_fp16_high_performance_21
kernel hash: 5247287448945562503
runtime error: 507015
error: L0C read/write conflict
```

The same failure was reproduced three times:

1. Default multimodal model startup.
2. With `--language-model-only`.
3. With `--language-model-only --max-num-batched-tokens 512`.

The Python traceback sometimes reports a later asynchronous synchronization point such as `aclnnDynamicQuantV2` or `aclnnRmsNorm`, but the device log identifies the same QuantBatchMatmulV3 kernel and hash on every attempt.

### Relevant comparison

On the same 310P server and runtime family:

- Qwen3.8-27B-W8A8 text-only TP=1 has previously started and served a request.
- Qwen3.8-27B-W8A8 TP=2 hit a QuantBatchMatmulV3 failure.
- Qwen3.6-35B-A3B-W8A8 TP=2 has served requests.
- Qwen3.5-9B FP16 TP=1 runs successfully.

This suggests a shape/tiling-specific W8A8 kernel failure rather than damaged model files, insufficient memory, or general lack of W8A8 support.

### Possible relation to existing issues

This is the same kernel name and hash reported in #10122. A maintainer wrote there that the affected quantization operator has a CANN-side fix in the `9.1.0.beta2` branch. However, the current `v0.23.0rc1-310p` image still contains `9.1.0-beta.1`.

The 310P Model Runner V2 RFC #15577 also says Qwen3.5 W8A8 dynamic support is merged into `main` and remains opt-in with `VLLM_USE_V2_MODEL_RUNNER=1`. The locally available generic `v0.23.0` image cannot be used for this verification because its installed package targets A2 and rejects 310P before model loading.

### Expected behavior / questions

The published 310P W8A8 checkpoint should pass the startup profile and expose a serving endpoint on a supported 310P image.

Could maintainers please clarify:

1. Which current 310P image/tag contains both CANN 9.1.0.beta2 (or the operator fix) and the merged MRv2 Qwen3.5 W8A8 dynamic path?
2. Is this expected to be fixed by switching to that image with `VLLM_USE_V2_MODEL_RUNNER=1`, or is the V1 path in `v0.23.0rc1-310p` also expected to work?
3. If a beta2-based 310P image already exists, we can immediately retest this exact reproducer and provide the result.

### Thymos2027 · 2026-09-21

Retest update: the original failure is no longer reproducible with the current 310P nightly when Model Runner V2 is explicitly enabled.

Validated stack:

- Hardware: Atlas 300I Duo / Ascend 310P3, one logical NPU, TP=1
- Image: `quay.io/ascend/vllm-ascend:nightly-main-310p`
- Pinned digest: `sha256:589fc7c911e3c7b83e10c0fed2637d9c6eefd8e1bbfb27a73b3699dc7e68c782`
- CANN: `9.1.0` (`V100R001C11SPC001B243`)
- vLLM: `0.29.0+empty`, commit `98dff2a81d747d1dba01a47f939f48c3526d4206`
- vLLM Ascend: `0.19.1rc2.dev2294+gc173a64a4`, commit `c173a64a44dec4ba97aaba6277b1dfc1562eda19`
- Model runner: `NPUModelRunner310V2`
- Opt-in: `VLLM_USE_V2_MODEL_RUNNER=1`
- Same checkpoint/revision as the report: `Eco-Tech/Qwen3.5-9B-W8A8-310P@1bdfd32119177461d7b8f03f01ce100572043c59`
- Quantization remained ModelSlim `W8A8_DYNAMIC` / `--quantization ascend`; there was no FP16 fallback.

Results:

1. The worker log explicitly reported `Using NPUWorker310 and NPUModelRunner310V2`.
2. Model loading, startup profiling, health check, and greedy text generation all succeeded. The previous `507015` / `QuantBatchMatmulV3` L0C conflict did not recur.
3. A controlled `baseline-v1-core` run then completed 8 workload cases (128/4096 input targets, 128/512 output targets, concurrency 1/4), with 24 warm-up requests and 100 measured requests. All requests succeeded; full streamed output reconstruction and SHA-256 validation passed. Prefix caching was explicitly disabled.
4. The container exited normally with code 0, and the NPU was idle after shutdown.

For the tested MRv2 + CANN 9.1.0 stack, this unblocks Qwen3.5-9B W8A8 serving on 310P. However, this does **not** isolate the fix to MRv2 alone: both CANN (`9.1.0-beta.1` -> `9.1.0`) and the 310P model runner (V1 -> V2) changed. The original V1-path question therefore remains unresolved unless that combination is tested separately.

There also appears to be a useful regression-test gap: a single-card 310P hardware E2E covering Qwen3.5 Dense W8A8 with MRv2, startup/profile execution, and at least one greedy generation would protect this path. Existing mocked W8A8 unit coverage cannot catch a real `QuantBatchMatmulV3` device fault.
