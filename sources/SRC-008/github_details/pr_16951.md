# [PR #16951] [BugFix] Enable local KV communication resource loading on A3

## 正文

### What this PR does / why we need it?

A3 deployment examples already allow `kv_connector_extra_config.ascend_local_comm_res_path`, but the worker only invokes `setup_ascend_local_comm_res` for hardware profiles with `LOCAL_KV_COMM_RESOURCE`. That capability was enabled only for A5, so an explicit local communication resource was ignored on A3.

This PR adds `LOCAL_KV_COMM_RESOURCE` to the A3 hardware profile and updates the profile regression test. When the path is not configured, the existing helper remains a no-op.

This is complementary to:
- vllm-ascend #16280, which recognizes `Ascend910_9363` as A3 at the framework level.
- hicann/hixl#1, which adds `Ascend910_9363` to HIXL's V3/A3 SoC mapping for automatic endpoint generation.

The explicit resource path remains a useful compatibility fallback for HIXL/CANN versions that do not yet contain the SoC mapping fix.

### Does this PR introduce _any_ user-facing change?

Yes. A3 workers now honor an explicitly configured `ascend_local_comm_res_path` for Mooncake/HIXL KV transfer. Deployments without this option are unchanged.

### How was this patch tested?

- Updated `tests/ut/device/test_hardware_profile.py` to include `LOCAL_KV_COMM_RESOURCE` in the exact A3 capability set.
- `python -m py_compile vllm_ascend/device/hardware_profile.py vllm_ascend/utils.py tests/ut/device/test_hardware_profile.py`: passed.
- `git diff --check`: passed.
- Attempted `pytest -q tests/ut/device/test_hardware_profile.py` in the deployment container. Collection was blocked by the container's installed vLLM version, which does not provide `vllm.v1.attention.ops.pcp` required by the current main branch.
