---
Depending on how the workers are triggered, the underlying executable (`sys.executable`)  isn't necessarily the one used for the main process. This results in disparate envs.

**This PR adds to `compose_end_to_end` via `Fuser.runner`, the ability to optionally use multiprocessing** instead subprocess (which makes a clone of the existing process env per process). 

This is enabled by a `FUSER_COMPOSE_USE_SYS_EXECUTABLE` environment flag (defaulting to existing subprocess path)

## 评论 (3)

### Laurawly · 2025-12-02

My take of this PR: 
Process does make the env/interpreter story more robust in theory, and it lines up with the upstream change. But in this repo, we don’t currently have a concrete, reproducible env-mismatch bug that this solves.

On the flip side, the new approach:
Adds quite a bit of complexity (custom exec logic, manual os.dup2, env mutation, etc.).
Changes semantics around sys.argv (unless we fix that) and process cleanup (we now terminate a single process instead of a process group).

For this repo, we don’t currently have a concrete, reproducible env-mismatch bug in “plain” venv/Python setups, so I’d prefer to keep both use cases happy via a small runtime switch rather than fully dropping the simpler path. Something like:

```
USE_MP = os.getenv("KA_USE_MULTIPROCESSING", "1") == "1"

if USE_MP:
    # multiprocessing path
else:
    # original subprocess.Popen path (simpler for normal envs)
```

## Review (5)

### Laurawly · 2025-12-02 · CHANGES_REQUESTED

The old implementation used start_new_session=True + os.killpg to kill the entire candidate process group on cancel/timeout.
With multiprocessing.Process, we now only terminate/kill the single child process. If the candidate script spawns subprocesses, those could be left running.
If process-group-level cleanup was intentional, we may need an equivalent mechanism here or at least document the change in semantics.

The os.environ.clear(); os.environ.update(env) pattern in the child reproduces what env=env in subprocess.Popen did, which is good. It might be worth a short comment noting that we’re intentionally replacing the child’s env to match what we used to pass to Popen.
