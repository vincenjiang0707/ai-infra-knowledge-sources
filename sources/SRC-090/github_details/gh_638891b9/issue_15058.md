## 正文

## Summary

Propose the metrics and structured-log observability design for the standalone EPP, covering [DEP #11661](https://github.com/ai-dynamo/dynamo/issues/11661) **Milestone 9: Embedded EPP Observability**. This issue is the design artifact before implementation: it draws from the existing Dynamo Frontend/router telemetry and from the llm-d EPP, and defines exactly which series are added, where they are emitted, and how they behave across EPP deployment modes.

## Motivation

**Today the standalone EPP is nearly unobservable.** It exposes exactly **one** metric — `dynamo_epp_cached_tokens{model}` — on a private `prometheus::Registry` served at `DYN_EPP_METRICS_PORT` (default 9090), and its logging is `tracing_subscriber::fmt()` with `RUST_LOG`, **text-only** (no JSONL), unlike the Dynamo runtime (`DYN_LOGGING_JSONL` / `DYN_LOGGING_CONSOLE_FORMAT`). The decode sidecar (`deploy/inference-gateway/sidecar/`) has **zero metrics, no metrics port, and only a little`tracing` calls**.

**Scope** (from #11661 M9): *"The standalone EPP provides metrics and structured-log observability at parity with the relevant Dynamo Frontend/router behavior for equivalent request paths. Operators can diagnose EPP-owned request processing, routing, selection, reservation lifecycle, replica behavior, and disaggregated handoff without requiring the Dynamo runtime."*

**Target configuration.** `DYN_EPP_MODE=standalone` with vanilla (non-Dynamo) engines — the on-ramp example's backend is *"Raw vLLM aggregated worker pool. Vanilla image"* (`examples/onramp/agg.yaml:57-58`). 

**Goals.** Cover the M9 diagnostic domains with Prometheus metrics; structured logs at parity with the runtime (JSONL, consistent fields, span-carried identity); every metric documented in `metrics-catalog.mdx` with an availability-by-configuration matrix.

## Proposal

### Design inputs

- Dynamo Frontend/router telemetry:

  - lib/llm/src/kv_router/metrics.rs — router metric families.
  - lib/llm/src/http/service/metrics.rs — frontend request metrics, InflightGuard.
  - docs/fern/pages/reference/observability/metrics-catalog.mdx and metric-labels.mdx.

- llm-d EPP metrics: the reference implementation we compare against. llm-d is mid-migration from `inference_*` to `llm_d_epp_*` with both names registered — a useful precedent if Dynamo ever renames an EPP series.

- PR [#13143](https://github.com/ai-dynamo/dynamo/pull/13143) (open, not yet merged): frontend metrics namespace attribution. This design adopts its post-merge shape as the parity baseline and follows its compatibility discipline.

- DEP #11661 component boundary: EPP owns the Envoy ext_proc/GAIE protocol, tokenization, Kubernetes worker discovery, and selection-lifecycle reporting; embedded SelectionService owns the catalog, KV index, scoring, queue, and reservation state.

### Design principles

1. **Parity, not duplication.** The EPP exposes the *service-level* view of the same quantities the frontend/router expose — parity of *diagnosability*, not name-for-name parity.
2. **No DRT dependency.** The standalone EPP holds no `DistributedRuntime` past startup; all new series go on the existing private registry — same rationale as `dynamo_epp_cached_tokens`.
3. **Cardinality safety.** All identity labels are bound at startup or drawn from closed enums:
   - `model` — bound once via `set_served_model()` (existing mechanism; never from the request body).
   - `inference_pool` — const label bound once at startup from `DYN_EPP_INFERENCE_POOL_NAME`. This is **EPP-owned deployment identity**: it separates several pools in one cluster. 
   - `worker_type` — closed enum, values taken from `WorkerType` (`aggregated` / `prefill` / `decode` / `encode`. But the standalone EPP builds exactly one Aggregated SelectionService today, so this label is currently constant.
   - `reason` / `error_type` / `status` / `action` / `event_type` — closed enums only.
   - `dynamo_namespace` — **not carried**: because standalone holds no `DistributedRuntime`.
   - **No `worker_id`, pod name, or endpoint labels on hot-path metrics.** Per-worker debugging is served by logs and by the worker-side.
4. **Labels are added, never renamed or removed** (PR #13143 discipline) 
5. **Availability is documented per configuration.** Metric groups register/populate differently across `aggregated` vs `disaggregated`, KV events on/off, single vs multi replica — following the existing "Availability by configuration" matrix format in `metrics-catalog.mdx`.

### Proposed metrics

> ⚠️ **Prefix pending.** Some Series are listed **without their prefix**. New series use **`dynamo_epp_`**, The prefix for the (_inherited_) rows is still open: `dynamo_epp_` (this DEP's proposal) or `dynamo_component_router_` (inherit the router's namespace). Every other decision here is independent of that choice.

All names carry the existing `dynamo_epp_` prefix and the startup-bound const label set `model` + `inference_pool` (only variable labels shown in tables for brevity). 

**Histogram buckets** are frozen at design time and aligned to the existing Frontend/Router series.
All reason / phase label values in this doc are proposed naming introduced by this issue, not existing code identifiers.

**Priority**: `P0` = required in M9a; `P1` = M9b; `P2` = M9c or undecided.

#### Domain 6 — Disaggregated handoff (decode sidecar)

The sidecar is a separate binary, an HTTP proxy inside the decode pod. It exposes no metrics endpoint today, hence the new env `DYN_SIDECAR_METRICS_PORT` (default 9091, `0` disables — same semantics as `DYN_EPP_METRICS_PORT=0`), same private-registry pattern. Its series take the prefix `dynamo_sidecar_`.

**P/D handoff is not implemented yet**: the sidecar binary ships with `UnavailablePdAdapter`.

### Structured logging

Logs should reach parity with the Dynamo runtime on three axes: **format** (same JSONL init and field style), **fields** (request identity), and **behavior** (the same events at the same lifecycle moments, at the same levels).

#### Design decisions

1. **Use the runtime logging init** for EPP and sidecar: replace the local `tracing_subscriber::fmt()` + `EnvFilter` with call `logging::init()` (`lib/runtime/src/logging.rs`).
2. **One span per ext_proc request**, following the frontend `InflightGuard.span` convention.
3. **Level discipline.** Request path: `trace`/`debug` only. Lifecycle: `info`. Recoverable anomalies (such as watch reconnect): `warn`. Operator action required (server exit, init failure): `error`.
4. **Rate-limited warnings** for per-event faults that can fire indefinitely, following the `record_unsupported_residency_event` pattern.
5. **Payload hygiene** Logs and metrics carry identifiers only, like `request_id`, `reservation_id`, `worker_id`, `model` — never request bodies, prompts, token IDs, or response content.

Log events are co-located with the metric instrumentation sites defined above — logs and metrics are emitted together, not designed separately.

### tmonty12 · 2026-09-22

Hey @flpanbin, great proposal. A few thoughts:

**Exposing `dynamo_component_router_*` on the EPP port**

The `RouterRequestMetrics` struct in `lib/llm/src/kv_router/metrics.rs` already tracks request count, TTFT, ITL, ISL, OSL, KV hit rate, and overlap metrics — exactly the series this DEP re-proposes under `dynamo_epp_*`. Right now these are gated behind `from_component()` which requires a `DistributedRuntime`, which standalone EPP does not have.

The fix is a second constructor `from_registry(registry, prefix, const_labels)` that takes a plain `prometheus::Registry` and registers the same series with no DRT dependency. The standalone EPP passes in its existing private registry (already serving `dynamo_epp_cached_tokens` on port 9090) with appropriate const labels.

**On naming**: rather than rename these to `dynamo_epp_*`, I would suggest keeping them as `dynamo_component_router_*` even on the EPP port. This keeps naming consistent with the DRT/frontend mode (which keeps `dynamo_component_router_*` on port 8000), avoids a parallel renamed set, and makes it clear the same router logic is running regardless of deployment mode.

**Metrics to remove from the DEP** (covered by `dynamo_component_router_*`):

Note: `dynamo_epp_requests_total` and `dynamo_epp_time_to_first_token_seconds` should stay as EPP owned series. The EPP request total counts at the ext_proc boundary and includes requests that fail before reaching the SelectionService (tokenization failure, semaphore rejection, etc.) — the router counter only increments after admission. Similarly, EPP TTFT is service level (ext_proc receipt to first token back) while the router TTFT starts after tokenization and selection. Both are useful but they measure different things. ITL and OSL are the same in both: they come from the same token stream and response usage field.

| Remove | Covered by |
|---|---|
| `dynamo_epp_request_input_tokens` | `dynamo_component_router_input_sequence_tokens` |
| `dynamo_epp_request_output_tokens` | `dynamo_component_router_output_sequence_tokens` |

ITL, KV hit rate, shared cache hit rate, and non-max-overlap selections also come for free.

**Metrics to add** (not covered by router metrics, genuinely EPP owned):

| Metric | Type | Notes |
|---|---|---|
| `dynamo_epp_tokenizer_duration_seconds` | Histogram | EPP owned tokenization step; distinguishes slow tokenization from slow selection |
| `dynamo_epp_selection_duration_seconds` | Histogram | Time inside `SelectionService.pick()`. Equivalent of `dynamo_routing_overhead_total` which is frontend only today |
| `dynamo_epp_selection_errors_total` | Counter | Selection failures by `reason`: `no_workers`, `queue_full`, `timeout`, `capacity_exceeded`. Needed to diagnose 503s without log parsing |
| `dynamo_epp_workers_registered` | Gauge | Live worker count in the SelectionService. No analog on EPP port today |
| `dynamo_epp_workers_ready` | Gauge | Ready subset of registered workers. Gap between this and `workers_registered` surfaces stale discovery or failed health checks |

**Labels for all EPP metrics**

Const labels (bound once at startup, never from request body):
- `model` — from `set_served_model()`, existing mechanism
- `inference_pool` — from `DYN_EPP_INFERENCE_POOL_NAME`

`dynamo_epp_selection_errors_total` adds `reason` (closed enum).
`dynamo_epp_workers_*` adds `worker_type` (closed enum: `aggregated`/`prefill`/`decode`/`encode`).

No `worker_id`, pod name, or endpoint labels on hot path metrics per the cardinality safety principle already in this DEP.

### flpanbin · 2026-09-22

Hi @tmonty12 Thanks for the review. Point by point:
1. **from_registry** — agreed. Reusing `RouterRequestMetrics` gives us the definitions, but it does not give us the observations. Most of those series is fed from inside `RoutingHost` / `RequestGuard`, none of which the EPP runs. So each series still needs an EPP-side observe call at a point where the EPP actually holds the data. That's why I listed "where (file::fn)" per row in the DEP. And even the definitions need one change. The help strings are hardcoded in `from_component` — six of the twelve say "observed at the router" or "processed by the router", which isn't true of the EPP, Frontend and router already share the name constant while writing their own help text, so could `from_registry` take the observer name, or a help override?

2. **Naming — would `prefix = dynamo_epp` be better than `dynamo_component_router_`**?​  
  Same struct, same buckets, only the prefix differs. Reasons:
    - **Precedent inside Dynamo**. Frontend and the KV router already observe the same request-level quantities from the same `frontend_service::*` constants, and emit two names, such as: `dynamo_frontend_input_sequence_tokens` vs `dynamo_component_router_input_sequence_tokens`. The EPP is a third observer, like the frontend, it has no `dynamo_namespace` / `dynamo_component` labels. So `dynamo_epp_*` follows the same rule.
    - **dynamo_component_router_ implies a registered Dynamo component**, which the EPP is not. It carries no `dynamo_namespace` / `dynamo_component` labels. Same name with a different label set silently breaks consumers, include the `planner` and `Grafana`, EPP metrics samples would be summed into the same distribution with no error.
    - **llm-d does the same** — its endpoint picker uses `llm_d_epp_*` for these quantities.

 3. **On "ITL, KV hit rate, shared cache hit rate, non-max-overlap" come for free**​ — free for registration, not for data. such as `non-max-overlap / overlap_blocks_lost` needs a crate change: the value is a scheduler-internal comparison (highest-overlap worker vs. the one selected) that isn't in the selection result. So **may be we can register `from_registry` only a subset.** Not every series in `RouterRequestMetrics` can be fed on day one, and their priorities differ. We can add the rest as each producer lands.

4. **Remaining metrics - still in progress** I'm still working through the other domains (such as reservation lifecycle, Worker discovery and catalog, Disaggregated handoff). There are some details need to confirm, like the observation point, and which values a label can take. One example: For `dynamo_epp_selection_errors_total` you metioned, I noticed the `SelectionError` —` bad_request / not_ready / not_found / conflict / internal / scheduler / sequence` defined. The values in your comment don't match that set. But I think the reasons you suggested makes more sense. I have updated in DEP.
