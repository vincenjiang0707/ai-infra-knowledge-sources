## Summary

Request-received events now log at DEBUG in the HTTP frontend and request-plane ingress. Frontend successful completions use DEBUG, errors remain at ERROR, and cancellations and HTTP access logs remain at INFO. Structured fields and metrics are unchanged.

The ingress completion guard is outcome-agnostic: its completion event uses DEBUG on success, error, and cancellation. At the default INFO level, the unchanged cancellation_total and error counters are the intended observability surface for worker cancellations and failures, alongside existing WARN/ERROR diagnostics. A per-request ingress completion record requires DEBUG; this change does not add outcome tracking to the guard.

The aggregated fixtures share setup. CPU regressions selected by generic runtime CI verify exact frontend/worker request IDs and INFO filtering, using bounded log waits and graceful worker drain before inspecting completion logs.

The Triton test workflow receives its required `framework` input. Router benchmark helpers load the trace synthesizer only when synthesis is requested, allowing CPU test collection without synthesis-only dependencies. Its import location and comment now match main to avoid a duplicate import when merged.

# Plan — Reduce high-volume request-plane lifecycle logs to debug

Route: implementation
Template: change-build-deploy-measure
Engine: vllm

## User intent

GitHub issue [ai-dynamo/dynamo#12310](https://github.com/ai-dynamo/dynamo/issues/12310) reports that the
request plane emits a pair of INFO-level lines for **every single request** that crosses the ingress
path — `request received` on entry and `request completed` on teardown. At production request rates
these two lines dominate the log volume of an otherwise quiet worker: an operator tailing a worker at
the default level sees nothing but a scrolling wall of per-request chatter, and the INFO lines that
actually matter (startup, endpoint registration, shutdown, transport failures, backpressure alerts)
are buried underneath it. Log storage and ingestion cost scale linearly with request rate for
information that is, in steady state, entirely uninteresting.

The ask is narrow and behavioural, not structural: move those per-request lifecycle events from INFO
down to DEBUG so that they disappear from the default-level stream but remain fully available to
anyone who opts in with `DYN_LOG=debug`. Three things must survive the move untouched. First, the
**`request_id` fields stay on the logs** — the whole value of these lines when you do turn them on is
correlating a single request across the frontend and the worker, and stripping the correlation key
would leave a log that is quieter but useless. Second, **metrics are unchanged**: the Prometheus
counters, gauges and histograms that live alongside these log statements (`request_counter`,
`inflight_requests`, `request_duration`, `request_bytes`) are the supported observability surface for
request volume and latency, and they must keep firing on exactly the same code paths with exactly the
same values. Third, **INFO/WARN/ERROR logs for startup, shutdown, transport errors, backpressure and
abnormal failures are left alone** — this change removes routine chatter, not diagnostics.

A carry-over constraint from the issue governs everything written into the repository as a result of
this work: use **synthetic request IDs and dummy payloads only** in examples, tests, fixtures and
documentation. No customer prompts, no production request IDs, no internal URLs, no credentials and
no customer identifiers may appear in any file or in any recorded validation output. The existing test
fixtures already satisfy this (they use placeholder model names and throwaway prompt strings), and any
new or adapted assertion must keep it that way. Sandbox credentials are supplied by the runtime; they
are never to be printed, persisted or inspected.

## Non-goals

**Changing what the logs say, or what fields they carry.** This is a level change and only a level
change. The message strings `request received` and `request completed` stay byte-identical, and every
structured field — `request_id`, and on the frontend also `model`, `endpoint`, `request_type`,
`status`, `elapsed_ms` — stays exactly as it is. Anyone who greps for these strings at DEBUG finds
precisely what they found before at INFO.

**Touching metrics in any way.** No counter is renamed, no label is added or removed, no observation
moves to a different code path, and no metric becomes conditional on log level. The `Drop` impls that
carry both the metric update and the log line keep the metric update unconditional; only the
`tracing::` macro name changes. A reviewer should be able to confirm this by reading the diff alone.

**Demoting anything that is not a routine per-request lifecycle event.** Explicitly out of scope and
explicitly to be left at their current levels: every startup/bind/registration INFO in
`nats_server.rs`, `push_endpoint.rs` and `shared_tcp_endpoint.rs`; the cancellation-signal shutdown
INFOs; `lib/runtime/src/transports/zmq.rs:216` (`response stream was closed`) which carries a
`request_id` but reports an *abnormal* stream teardown and sits directly beside the backpressure
warning at line 220; and the `Status::Error` completion branch in the frontend's `InflightGuard`,
which is already `tracing::error!` and must stay ERROR.

**`http response sent` in `lib/llm/src/http/service/service_v2.rs:1117`.** This is a genuine
third per-request INFO line in the same request path, and it is deliberately left alone. The issue
names exactly two events by their message strings, and this one belongs to the Axum HTTP access-log
layer rather than the request-plane lifecycle instrumentation the issue is about. Sweeping it in
would broaden the blast radius and entangle this change with the access-log story; it is called out
here so the omission is visibly a decision rather than an oversight, and so a follow-up can pick it
up if operators still find the default stream too noisy.

**Adding a log-level configuration knob.** No new environment variable, no new CLI flag, no new
builder parameter. `DYN_LOG` already provides per-target level control and is the supported mechanism;
this change simply makes the default level do the right thing.

## Discovery

### The lifecycle logging sites

The instrumentation was introduced in a single commit — `679d9f145`, *"feat: request lifecycle logging
+ metrics capture [DIS-1643] (#7840)"* (Neelay Shah, 2026-04-02, 13 files) — which is why the worker
and frontend halves are structurally identical: in both, the *received* line fires inline at request
admission next to the counter increments, and the *completed* line fires from the `Drop` impl of an
RAII guard that also observes the duration histogram and decrements the inflight gauge. Understanding
that shape matters, because it means the log and the metric are physically adjacent in the same
statement block and a careless edit could move one while intending to move the other.

**Worker side — `lib/runtime/src/pipeline/network/ingress/push_handler.rs`.** Two sites, both
demotion targets:

- **Line 599**, inside `handle_payload_shared`, in the closure that builds the `RequestMetricsGuard`.
  The closure increments `request_counter`, `inflight_requests` and `request_bytes`, then emits
  `tracing::info!(request_id = %rid, "request received")` before constructing the guard. Only the
  macro changes; the three metric increments and the guard construction are untouched.
- **Line 138**, inside `impl Drop for RequestMetricsGuard`. The drop decrements `inflight_requests`,
  observes `request_duration` with the elapsed time, and then — guarded by `if let Some(request_id)` —
  emits `tracing::info!(request_id = %request_id, "request completed")`. Again only the macro changes;
  the `dec()` and the `observe()` stay exactly where they are, above the log, unconditional.

This file is the ingress dispatch point for **both** request-plane transports (TCP and NATS) and for
both the unary `SingleIn`/`HeaderAndData` and the bidirectional `ManyIn`/`HeaderOnly` paths, so a
single edit at each site covers every worker-side request. A sweep of the whole
`lib/runtime/src/pipeline/network/ingress/` directory found twenty `tracing::info!` call sites; the two
above are the only per-request ones. The other eighteen are all lifecycle-of-the-*process* events —
`nats_server.rs:72/100/119/140/167/194/213` (service group creation and endpoint registration),
`push_endpoint.rs:68` (`PushEndpoint received cancellation signal, shutting down service`) and `:159`,
`shared_tcp_endpoint.rs:173/272/353/358/410/446/460/1112` (TCP bind, register/unregister, cancellation
shutdown) plus one inside a `#[cfg(test)]` block at `:977`. Every one of them fires O(1) times per
process, not O(1) times per request, and every one of them stays. The must-stay error paths in
`push_handler.rs` itself are `tracing::error!` at lines 178 (`failed to encode request-plane
response`), 209 and 243 and 279 (publish failures), and 678 (`Failed to generate response stream`),
plus `tracing::warn!` at 206 — none of these are touched.

**Frontend side — `lib/llm/src/http/service/metrics.rs`.** The mirror image, in `InflightGuard`:

- **Line ~1390**, in `InflightGuard::new`: `tracing::info!(request_id = %request_id, model = %model,
  endpoint = %endpoint, request_type = %request_type, "request received")`. Demotion target.
- **Line 1477**, in `impl Drop for InflightGuard`, the `Status::Error` branch:
  `tracing::error!(..., error_type, error_detail, elapsed_ms, "request completed")`. **Stays ERROR** —
  this is an abnormal-failure line and the issue's carve-out covers it explicitly. This is the single
  most likely place for an implementer to over-reach, so it is called out here by line number.
- **Line 1488**, the `Status::Success` branch: `tracing::info!(request_id, model, endpoint,
  request_type, status, elapsed_ms, "request completed")`. Demotion target.

The issue's title says "request-plane", and one could argue for a worker-only change. Including the
frontend pair is the right call: they are the same two message strings, introduced by the same commit
for the same purpose, and they fire on every request through the very same logical path. Demoting only
the worker half would leave the operator still staring at two INFO lines per request from the
frontend, which does not deliver the outcome the issue asks for. This is recorded as a deliberate
scope decision, not scope creep.

**Filtering behaviour is confirmed to make the demotion effective.** `lib/runtime/src/logging.rs`
builds the request span with `tracing::info_span!(target: "request_span", "http-request", ...)` and its
comment at 1633–1636 notes that infrastructure request *spans* are always allowed regardless of
`DYN_LOG`. That applies to span creation only; the *events* emitted inside the span follow ordinary
`EnvFilter` level filtering. So demoting the events genuinely removes them from a default-level
(`info`) stream, and `DYN_LOG=debug` genuinely brings them back with fields intact. The default level
is documented as `info` at `logging.rs:18`.

### Existing tests — RUN / IGNORE verdicts

**`tests/frontend/test_request_tracing_logs.py` — RUN. This is the decisive finding.** 729 lines,
added by `73f8557a3` *"test: e2e JSONL log verification for request tracing (#7817)"*. It is the
authoritative coverage for exactly the lines this change touches, and it will fail after a naive
demotion. It launches a frontend and a mocker worker with `JSONL_ENV = {"DYN_LOGGING_JSONL": "1",

`"request completed"` / `"http response sent"`. Concretely:

- `test_agg_unary_success` asserts `received[0]["level"] == "INFO"` (line 306) and asserts the worker
  logged exactly one `request received` and one `request completed` (lines 325–326).
- `test_disagg_streaming_success` repeats the worker-side lifecycle count assertions (lines 528–529).
- `test_agg_404_error` asserts `completed[0]["level"] == "ERROR"` (line 371) — this is the assertion

Because this file already encodes the *old* contract, the implementer must **adapt it, not duplicate

lifecycle assertions with `DYN_LOG=debug` and assert the events are present at level `DEBUG` with

**`tests/fault_tolerance/cancellation/test_vllm.py` — RUN, with a caveat the implementer must
resolve.** At lines 565–575 it uses the log line as a synchronisation barrier, polling the prefill
worker's output for `f"request completed request_id={request_id}"`, with a comment explaining the
reasoning: the line fires on the same `RequestMetricsGuard::drop` that observes the histogram, so
seeing it means the metric is already up to date. That coupling is unaffected by the level change —
but whether the barrier still *sees* the line depends on the harness level. Discovery resolves this
favourably: `tests/fault_tolerance/cancellation/utils.py:29` sets `"DYN_LOG": "debug"` in the shared
worker env and `test_vllm.py:138` sets `env["DYN_LOG"] = "debug"` directly. The barrier therefore
survives the demotion as-is. The implementer must nonetheless *verify* this rather than assume it, and
must not silently weaken the barrier. The test is parametrised over `request_plane` in
`["nats", "tcp"]` and carries markers `fault_tolerance, vllm, e2e`; it needs real GPU vLLM workers, so
it is a CI-fidelity concern rather than something to run in this sandbox.

**Rust unit tests in `push_handler.rs` (`#[cfg(test)] mod tests`, lines 761–1006) — IGNORE.** Five
`tokio::test` cases, all covering `pump_response_stream` error classification. None asserts on log
level or captures log output. They must keep compiling and passing (`cargo test -p dynamo-runtime`
covers that) but they require no edits.

**No Rust log-capture harness exists — IGNORE for new Rust assertions.** Neither `lib/runtime/
Cargo.toml` nor `lib/llm/Cargo.toml` depends on `tracing-test` or `test-log`; only the workspace
`tracing-subscriber` is present. Building a Rust-level log-level assertion would mean introducing a
new dev-dependency and a subscriber harness — disproportionate for a level change that the existing
Python e2e test already covers end-to-end at exactly the right granularity. The behavioural proof
belongs in the Python layer.

`tests/CLAUDE.md` prefers structured surfaces over log scraping, which is why the adapted assertions
should continue to go through the existing JSONL parsing helper (a shared structured-event helper)
rather than raw string grepping — the file's existing design already complies.

## Chosen approach

Change four `tracing::info!` macros to `tracing::debug!` and nothing else in the production code, then
bring the tests that encode the old contract into line with the new one.

In `lib/runtime/src/pipeline/network/ingress/push_handler.rs`, line 599 becomes
`tracing::debug!(request_id = %rid, "request received")` and line 138 becomes
`tracing::debug!(request_id = %request_id, "request completed")`. The field bindings, the message
strings, the surrounding `if let Some(...)` guard and — critically — every metric call above them
(`request_counter.inc()`, `inflight_requests.inc()`/`dec()`, `request_bytes.inc_by(...)`,
`request_duration.observe(...)`) are copied through untouched. In `lib/llm/src/http/service/
metrics.rs`, the `InflightGuard::new` event at ~1390 and the `Status::Success` completion event at
1488 get the same treatment, preserving all of `request_id`, `model`, `endpoint`, `request_type`,
`status` and `elapsed_ms`. The `Status::Error` branch at 1477 is left as `tracing::error!`. Nothing
else in either file moves.

The value of this shape is that it is verifiable by inspection: the diff is four one-token changes,
so "metrics unchanged" and "fields preserved" are not claims requiring trust but properties visible in
the patch. It also composes correctly with `DYN_LOG`, which already supports per-target overrides —
an operator who wants the old behaviour back for one component can ask for it without a code change or
a restart flag.

On the test side, `tests/frontend/test_request_tracing_logs.py` is adapted rather than duplicated. The
lifecycle assertions move to a `DYN_LOG=debug` fixture and assert `level == "DEBUG"` with `request_id`
present and non-empty; a case running at the default `DYN_LOG=info` asserts the two lifecycle messages
are absent, which is the actual user-visible outcome the issue asks for and is worth pinning so a
future change cannot silently promote them back. The existing `test_agg_404_error` assertion that the
error-path completion is `ERROR` stays exactly as it is and serves as the guard on the carve-out. All
fixture data stays synthetic — placeholder model names, dummy prompts, generated request IDs — with no
customer prompts, production IDs, internal URLs, credentials or customer identifiers anywhere in the
diff or in any recorded output. Finally, the implementer verifies (does not assume) that the
cancellation barrier in `tests/fault_tolerance/cancellation/test_vllm.py:565` still resolves, relying
on the `DYN_LOG=debug` already set at `utils.py:29` and `test_vllm.py:138`.

Sequencing is: edit the four Rust sites, run `cargo check --workspace --all-targets` and
`cargo clippy` to prove nothing structural moved, adapt the Python test, then run the behavioural
before/after comparison described below.

## Rejected alternatives

**Introduce a configurable log-level parameter** — e.g. a `lifecycle_log_level` field on the ingress
builder or a dedicated `DYN_REQUEST_LOG_LEVEL` environment variable, so operators could choose per
deployment. Rejected primarily because **it forces changes on callers**: adding a *required* field to
the guard or handler constructor breaks every construction site across `lib/runtime` and `lib/llm` and
any downstream crate that builds an ingress; making it *optional* (a `Default` impl or `Option<Level>`
defaulting to DEBUG) avoids the breakage but then adds a configuration surface that has to be
documented, tested and supported forever in exchange for capability `DYN_LOG` already provides. The
chosen approach adds **no parameter at all** — required or optional — so no caller anywhere changes,
and `cargo check --workspace --all-targets` passing on an otherwise-untouched workspace is the proof
that no signature moved.

**Demote only the worker-side pair in `push_handler.rs`.** A defensible literal reading of
"request-plane", and it would have produced a two-line diff. Rejected because it does not achieve the
issue's stated outcome: the frontend would still emit two INFO lines per request with the same message
strings, so an operator at the default level would see barely any reduction in volume. Forces no
changes on callers either way, so the deciding factor is purely whether the user's problem is
actually solved.

**Also demote `http response sent` (`service_v2.rs:1117`) in the same change.** Tempting for
completeness — it is a third per-request INFO in the same path. Rejected as scope discipline: the
issue enumerates two message strings, this line belongs to the HTTP access-log layer with different
operational semantics (many operators deliberately want an access log at INFO), and folding it in
would make the change harder to review and harder to revert independently. Recorded as a non-goal
above so a follow-up can take it up deliberately. No caller impact.

**Remove the lifecycle logs entirely and rely on metrics.** The metrics genuinely do cover the
aggregate volume and latency story, so the logs are arguably redundant in steady state. Rejected
because they are not redundant during incident response, where correlating one specific `request_id`
across the frontend and worker is exactly what you need and no counter can give you. DEBUG is the
correct level for "off by default, indispensable when you turn it on". No caller impact, but it would
break the cancellation test's synchronisation barrier outright rather than merely requiring it to be
re-verified.

**Add a Rust-level log-capture test asserting the emitted level.** Rejected on cost: it requires a new
`tracing-test` or `test-log` dev-dependency in `lib/runtime` and `lib/llm` (neither has one today) plus
a subscriber harness, to assert something the existing Python e2e test already asserts end-to-end
through the real JSONL output that operators actually consume. Adding a dev-dependency does not force
changes on callers, but it does add a build-graph obligation for the whole workspace in exchange for a
weaker signal than the test we already have.

## Validation strategy

The claim to be proven is behavioural and has two halves, and both are demonstrable in this sandbox
without spending meaningful GPU time. Half one: at the default level, the two lifecycle messages no
longer appear. Half two: at `DYN_LOG=debug`, they appear with `request_id` intact. That shape maps
cleanly onto the change-build-deploy-measure template's before-proof/after pattern, run as a pair
under a single recipe id.

`00-dynamo-editable-install` comes first and is non-optional: `import dynamo._core` currently fails in
`/opt/dynamo/venv`, so nothing that imports `dynamo.*` can run until the editable install is recorded
green. `02-rust-cargo-check` is the primary build gate and carries most of the safety argument for this
change — because the diff is four macro renames, a clean `cargo check --workspace --all-targets` plus
clippy is direct evidence that no signature moved, no caller changed, and the `#[cfg(test)]` module in
`push_handler.rs` still compiles. `01-python-lint` covers the edited test file. `03-python-unit-tests-
mocker` exercises the mocker-backed Python surface without a GPU and catches collateral damage in the
runtime bindings.
