## 正文

## Overview:

vLLM's OpenAI server accepts `vllm_xargs` and passes it to `SamplingParams.extra_args`. Custom extensions and model-specific request options read that field. One example is DiffusionGemma's structured "read" requests, added in vllm-project/vllm#57250. They send `diffusion_seed_canvas`, `diffusion_max_steps`, `diffusion_read_only` and similar fields. Dynamo's OpenAI frontend rejects `vllm_xargs` with `Unsupported parameter(s)`. With `DYN_IGNORE_OPENAI_FE_UNSUPPORTED_FIELDS` set, it silently drops the field instead. Either way, these workloads can't run behind the Dynamo frontend and KV router.

This PR forwards `vllm_xargs` the same way `logprob_token_ids` and the other extra-body sampling fields are already forwarded. It also raises the `/v1/completions` `logprobs` cap from 5 to 20, the chat `top_logprobs` limit. Those structured reads also call `/v1/completions` with token-id prompts and ask for the top 20 candidates.

## Details:

**Commit 1: `feat(frontend): forward vllm_xargs to vLLM SamplingParams.extra_args`**
- `lib/llm/src/protocols/openai/validate.rs`: `vllm_xargs` is added to `PASSTHROUGH_EXTRA_FIELDS`. It is validated against vLLM's schema: an object whose values are strings, numbers or booleans, or arrays of those. Booleans are accepted because vLLM's pydantic model coerces them.
  - `kv_transfer_params` and `ec_transfer_params` are rejected. vLLM fills those keys from dedicated request fields, and Dynamo only forwards router-generated connector inputs.
- `lib/llm/src/preprocessor.rs`: `vllm_xargs` is forwarded in `extra_args.sampling_options`, next to `logprob_token_ids`.
- `components/src/dynamo/vllm/handlers.py`: `build_sampling_params` pops `vllm_xargs` before the generic `setattr` loop. It then merges the field over any default `extra_args`. The worker drops the two connector keys as well, as a second line of defense, so the router's `kv_hint` handling is unchanged.
- Backend gating: token-input vLLM workers advertise a `vllm_xargs` runtime capability (`VLLM_XARGS_CAPABILITY` in `runtime_config.rs`; published by `dynamo.vllm` for base and LoRA model cards). For chat and completions requests carrying `vllm_xargs`, `Model::get_{chat,completions}_engine_with_parsing` select only WorkerSets that advertise it, so a mixed deployment routes these requests to vLLM. When a served model has no such WorkerSet (SGLang, TensorRT-LLM, text-input or older vLLM workers), the new `ModelManagerError::CapabilityUnsupported` becomes a 400 instead of the field being dropped silently. The text-input path is covered too, since it forwards the raw request and drops passthrough fields.

**Commit 2: `feat(frontend): allow completions logprobs up to 20`**
- `MAX_LOGPROBS` changes from 5 to 20, matching `MAX_TOP_LOGPROBS` and vLLM's default `--max-logprobs`.
- Backends already receive up to 20 through chat `top_logprobs`, which maps to the same `output_options.logprobs`. So this doesn't add any new backend-facing range.

Requests without `vllm_xargs` are unaffected on every backend.

## Where should the reviewer start?

- `validate_vllm_xargs` in `lib/llm/src/protocols/openai/validate.rs`: the accepted value shapes and the reserved keys.
- `get_chat_engine_with_parsing` / `capability_engine_error` in `lib/llm/src/discovery/model.rs`: capability-filtered WorkerSet selection and the 400 vs 404/503 decision.
- `build_sampling_params` in `components/src/dynamo/vllm/handlers.py`: how the merge interacts with `default_sampling_params["extra_args"]` and with the later `kv_hint` / `kv_transfer_params` handling.
- Commit 2 is a separate policy change: it moves away from OpenAI's legacy completions cap. I can split it into its own PR if you'd prefer.

End-to-end, the same change backported to v1.5.0 has been serving DiffusionGemma NVFP4 behind `dynamo.frontend --router-mode kv --router-kv-events`. The setup is 8 `dynamo.vllm` workers, each on its own RTX PRO 6000 Blackwell GPU, on Kubernetes through the Dynamo operator:
- Chat and completions reads with `vllm_xargs`, `logprob_token_ids` and `return_tokens_as_token_ids` returned correct per-slot label distributions. The prompt Dynamo rendered from the chat template had the same token count as Hugging Face's rendering (206 tokens).
- A public structured-decision benchmark of 231 tasks completed with 0 failures. A 60 s load run with 32 clients returned 5,163 of 5,163 requests successfully.

Two other things came up during that integration. They are not changed in this PR, and I can open issues for them if useful:
1. vLLM rejects the default vLLM health-check canary (`temperature: 0.0`) for diffusion models, whose sampler runs a fixed schedule. Workers never become healthy unless `DYN_HEALTH_CHECK_PAYLOAD` is overridden.
2. vLLM's read-only diffusion path sets `ignore_eos` internally, but Dynamo's own EOS stop handling still truncates the emitted canvas. Clients have to send `ignore_eos: true` explicitly.
