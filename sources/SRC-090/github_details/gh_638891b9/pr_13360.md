# [PR #13360] feat(sidecar): add multimodal-aware vLLM KV routing

## 正文

#### Summary

The KV router matches cached blocks by hashing the token ids in each KV event. For an image, the frontend (built with `mm-routing`) replaces each image placeholder run with a pad value derived from the image hash. The worker's KV event publisher must apply the same rewrite, and for that it needs the model's image placeholder token. The vLLM sidecar publisher always sent `image_token_id: None`, so image blocks never matched and a repeated image request reused only its text prefix.

This PR resolves the image placeholder token in the vLLM sidecar and passes it to the KV event publisher.

Repro (frontend wheel built with `--features mm-routing`):

```bash
vllm-rs serve Qwen/Qwen3-VL-2B-Instruct --grpc-port 50051 --limit-mm-per-prompt '{"image":1}' \
  -- --kv-events-config '{"publisher":"zmq","topic":"kv-events","endpoint":"tcp://*:5557","enable_kv_cache_events":true}'
dynamo-vllm-sidecar --grpc-endpoint 127.0.0.1:50051
DYN_LOG=info,dynamo_llm::kv_router=debug python -m dynamo.frontend --router-mode kv --kv-cache-block-size 16
# Send the same text + image chat request twice and read the "[ROUTING] ... blocks overlap" line.
```

Second request with the same image:

```text
before: [ROUTING] Best: worker_... dp_rank=0 with 8/74 blocks overlap
after:  [ROUTING] Best: worker_... dp_rank=0 with 73/74 blocks overlap
```

#### Details

- **The sidecar resolves the token.** The sidecar turns vLLM's KV events into router hashes, and vLLM's gRPC `ModelInfo` does not report the placeholder token. The sidecar calls the resolver that the frontend uses, so both sides get the same token.
- **Resolve once, fall back on failure.** The token is fixed for a model, so the sidecar resolves it once at start. Exact routing is an optimization, so a slow or missing model hub must not block startup: the fetch is capped at 30 seconds and still honors an earlier overall startup deadline, and image requests keep text-prefix routing.
- **A fallback cannot misroute.** The router accepts only a frontend-issued image hash in a KV event. A mismatch between the two sides loses reuse but never matches a different image.
- **`supports_multimodal` is part of the model identity.** The token comes from the model seen at start, so startup fails if its multimodal support differs from the model registered at bootstrap.
- **`mm-routing` is a sidecar feature, on by default.** The Python bindings compile the sidecar in. They turn the feature off and forward their own opt-in `mm-routing`, so the default wheel stays lean.

#### Validation

One frontend with the KV router in front of two vLLM sidecar workers, serving `Qwen/Qwen3-VL-2B-Instruct`. Every request has the same text and one image, so only the image can steer placement. Images A and B go out first at the same time, so load puts them on different workers. Then A and B alternate four times each, then a new image C and one repeat. Each run starts with cold engines.

| | main | this PR |
| --- | --- | --- |
| A/B repeats routed to the worker that holds the image | 4 of 8 | 8 of 8 |
| Router overlap on A/B repeats | 8/74 (text only) | 73/74 |
| New image C, first request / repeat | 8/74, 8/74 | 8/74, 73/74 (same worker) |
| vLLM prefix-cache hits, both engines | 61% (8,560 of 14,040 tokens) | 76% (10,640 of 14,040 tokens) |

On main both workers hold only the shared text, so the router sees a tie and half the repeats land on the worker without the image.
