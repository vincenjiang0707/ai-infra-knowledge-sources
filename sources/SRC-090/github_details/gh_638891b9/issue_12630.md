# [Issue #12630] [Bug] streaming detokenizer emits U+FFFD and drops completed characters on multi-byte UTF-8 (CJK) at chunk boundaries

source: https://github.com/ai-dynamo/dynamo/issues/12630
state: closed | updated: 2026-09-23T05:39:31Z
labels: bug, language::python, backend::sglang, frontend

## 正文

## Summary

With `--dyn-chat-processor sglang`, the frontend's streaming detokenizer (`dynamo/frontend/sglang_prepost.py::_incremental_decode`) permanently corrupts multi-byte UTF-8 output. Every Korean reply in our production testing lost **5–13 hangul syllables**, each replaced by U+FFFD (e.g. `삼겹살` → `삼겹�`).

Version: `ai-dynamo==1.4.0.dev20260803`, model Kimi K3 (TikToken tokenizer), SGLang workers, PD disaggregated.

The Rust processor path (`--dyn-chat-processor dynamo`, the default) shows the same class of corruption (slightly worse in our runs), so the issue likely exists in both detokenization paths; this report analyzes and fixes the python one.

## Measurements

Identical Korean prompt ("no emoji" to exclude surrogate effects), streamed, counting U+FFFD in the concatenated deltas:

| path | broken chars (2 runs) |
|---|---|
| SGLang server direct (`/v1/chat/completions`) | **0** |
| dynamo frontend, chat processor `dynamo` (Rust) | 13 |
| dynamo frontend, chat processor `sglang` | 10 |
| dynamo frontend, non-streaming | 1 |

## Root cause (sglang processor path)

`_incremental_decode` re-decodes a small lookback window and slices the delta by decoded prefix length:

```python
prefix_text = tokenizer.decode(prefix_tokens)          # lookback only
window_text = tokenizer.decode(prefix_tokens + new)    # lookback + new
return window_text[len(prefix_text):]
```

Failure sequence when a chunk's last token ends inside a multi-byte character:

1. This call: `window_text` ends with the incomplete bytes rendered as U+FFFD → the replacement char is **emitted to the client**.
2. Next call: the same incomplete bytes are now in the prefix. `prefix_text` renders them as U+FFFD (1 char) while `window_text` renders the real combined character (also 1 char). The length-based slice therefore starts **after** the completed character — it is never emitted.

Net effect: the client keeps one U+FFFD in place of the real character, stream stays length-aligned, so the corruption is silent and permanent. CJK is hit constantly because hangul/CJK characters (3-byte UTF-8) frequently span BPE token boundaries in TikToken vocabularies.

Note: `--tokenizer {default,fastokens}` cannot help — per its own help text it has no effect on TikToken models, and decoding happens in this code path regardless of the chat processor's parsing delegation.

## Fix (verified)

Replace the length-sliced lookback window with an emitted-character marker over a running decode of the retained sequence, and **hold back trailing replacement-char runs** until the completing token arrives. Byte-level BPE token decode is context-free, so re-decoding the retained tail is stable across calls; the trim path re-anchors the marker.

```python
    def _incremental_decode(self, new_token_ids: list[int]) -> str:
        self._all_token_ids.extend(new_token_ids)

        max_keep = self.LOOKBACK * 1024
        tail_start = self._decode_base
        if len(self._all_token_ids) - tail_start > max_keep:
            new_base = len(self._all_token_ids) - (self.LOOKBACK * 256)
            kept_text = self.tokenizer.decode(
                self._all_token_ids[tail_start:new_base],
                skip_special_tokens=self._skip_special_tokens,
            )
            self._emitted_chars = max(0, self._emitted_chars - len(kept_text))
            self._decode_base = new_base
            tail_start = new_base

        full_text = self.tokenizer.decode(
            self._all_token_ids[tail_start:],
            skip_special_tokens=self._skip_special_tokens,
        )

        emit_upto = len(full_text)
        while emit_upto > self._emitted_chars and full_text[emit_upto - 1] == "�":
            emit_upto -= 1

        if emit_upto <= self._emitted_chars:
            return ""
        delta = full_text[self._emitted_chars : emit_upto]
        self._emitted_chars = emit_upto
        return delta
```

(plus `self._emitted_chars = 0` / `self._decode_base = 0` in `__init__`)

**After the fix**: 6,788 streamed Korean characters with **zero** U+FFFD (previously 10–13 per reply); tool-call parsing and consecutive tool-call chains unaffected (the delta feed to reasoning/tool parsers is unchanged in shape).

Caveat: a model that legitimately generates U+FFFD as the final characters before finish would have them held back; flushing held chars on `finish_reason` would cover that edge if desired.

Happy to turn this into a PR if useful. The equivalent boundary handling probably deserves a look in the Rust incremental decode path as well, given the measurements above.
