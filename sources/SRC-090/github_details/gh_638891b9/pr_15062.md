## Summary

- Add LPX component support to Dynamo for LPU-backed inference workloads.
- Include the LPX API, controller and handoff lifecycle, Dynamo rendering/runtime integration, scheduler and Grove integration, Helm configuration, generated API artifacts, tests, and documentation.

### sttts · 2026-09-23

**Grove architecture sign-off requested: LPX eviction and recovery**

@sanjaychatterjee @unmarshall @danbar2 Could you review and explicitly sign off on the recovery boundary between LPX and Grove in this PR?

Here is my understanding of the current path. When an LPX Agent Pod gets a deletion timestamp and a `DisruptionTarget` condition for one of the handled eviction reasons, the LPX controller queues that **Pod’s name**. On reconcile, it reads the Pod, verifies the Pod → PodClique → PCSG → PCS → LGD ownership chain, selects other Agents from the same component, PCSG replica, PodClique, and template revision, then uses the immutable LPX runtime ConfigMap to retain only Agents in the same runtime partition. Finally, it **directly deletes those peer Pods**. The ownership verification is appropriate for a destructive action; my concern is the separate Pod lifecycle controller and its interaction with Grove.

For example, one LGD may render two independent engines into a shared PCS:

```text
shared PCS
├── engine A / PCSG
│   └── Agent PodClique: A0 A1 A2 A3 | A4 A5 A6 A7
│                          partition 0 | partition 1
└── engine B / PCSG
```

If A0 is evicted, LPX wants to restart A0–A3 together while preserving A4–A7 and engine B. Grove cannot infer that partition from the PodClique alone; LPX derives it from its runtime table. Grove does, however, own replacement of missing PodClique Pods and gang termination after a sustained `minAvailable` breach. My reading is that Grove may replace A0 individually, while a persistent breach can eventually cause a broader restart, potentially at PCS replica scope. Please correct this reading if I have missed a Grove guarantee.

This creates two related concerns:

1. **Durability:** The LPX queue contains only the trigger Pod’s key. If that Pod disappears before reconciliation, `NotFound` currently completes the request; a controller restart or a failure partway through peer deletion has the same underlying problem. Grove may replace A0, but nothing durably records that A1–A3 still need a coordinated restart. This is the issue raised in [#15071](https://github.com/ai-dynamo/dynamo/issues/15071).
2. **Ownership of recovery:** LPX defines the semantic failure cohort, but it also deletes Grove-managed Pods to execute the restart. We need to know whether direct peer-Pod deletion is a supported Grove integration pattern, including its interaction with Grove’s own replacement and gang-termination controllers. We also need confidence that recovery cannot spill over to an unrelated engine in the shared PCS.

Would you recommend expressing this cohort and a durable restart intent through Grove topology or a Grove API? If the current LPX-owned deletion path is the intended design, what contract should we rely on to make it convergent across lost events, controller restarts, partial deletions, and concurrent Grove reconciliation?

I would like Grove’s explicit sign-off on that contract before merge. Fixing the lost trigger alone would address the immediate correctness bug, but it would not settle the controller ownership boundary.
