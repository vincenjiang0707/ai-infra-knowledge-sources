# [Issue #14079] fix(operator): deprecate unrestricted WithSharedOwnership

source: https://github.com/ai-dynamo/dynamo/issues/14079
state: open | updated: 2026-09-22T17:22:49Z
labels: bug, language::go, dynamo-deploy, deployment::k8s, fix, GMS, operator

## 正文

## Summary

`WithSharedOwnership` bypasses controller-owner validation for an existing same-named resource. It does not verify that the existing controller owner belongs to the intended lifecycle.

It currently supports two different resource lifecycles: a model-scoped HeadlessService and a checkpoint Job DRA `ResourceClaimTemplate` (RCT). Neither is unrestricted shared ownership.

`WithSharedOwnership` should be deprecated. It cannot establish that an existing resource belongs to the intended lifecycle, so new lifecycle implementations must not depend on it.

## Current layouts

### Model HeadlessService

`ReconcileModelServicesForComponents` creates one deterministic Service per `(namespace, baseModelName)`.

```text
DGD A, model-A
  └── HeadlessService(model-A), controller owner = DGD A

DGD B, model-A
  └── reconciles that same Service with WithSharedOwnership
```

The Service selects all pods serving `model-A` and produces EndpointSlices consumed by `DynamoModel` endpoint discovery.

Problems:

- The first DGD/DCD becomes the sole controller owner of a model-scoped resource.
- Deleting that owner can garbage-collect the Service while other DGDs/DCDs still serve the base model.
- A later reconciler accepts an ownerless Service or one controlled by an unrelated object, provided its name and namespace collide.
- Multiple controller owner references are not an appropriate solution: the Service should have one controller owner.

Relevant source: `deploy/operator/internal/dynamo/model_service.go`.

### Checkpoint GMS/DRA ResourceClaimTemplate

A DGD-managed checkpoint creates a separate RCT for its checkpoint Job:

```text
DGD serving workload RCT:
  chat-worker-gpu
  controller owner = DGD

Checkpoint Job RCT:
  checkpoint-<checkpointID>-worker-gpu
  initial controller owner = DGD
  final controller owner = DynamoCheckpoint
```

Current sequence:

1. The DGD derives GPU count and DeviceClass from the component.
2. It creates the checkpoint RCT with itself as parent.
3. It prepares the checkpoint Job pod template to reference that RCT.
4. It creates or finds the automatic `DynamoCheckpoint`.
5. It transfers the RCT controller owner to the `DynamoCheckpoint`.
6. Subsequent DGD reconciles use `WithSharedOwnership` to access the now-checkpoint-owned RCT.

Problems:

- This is an ownership handoff, not shared ownership.
- The DGD reconcile can operate on an arbitrary same-named RCT rather than the expected checkpoint-owned one.
- The handoff exists because the DGD currently prepares the checkpoint pod template before creating the checkpoint CR.

Relevant source: `deploy/operator/internal/controller/dgd_checkpoints_reconciler.go`.

## Proposed resolution

### Model HeadlessService lifecycle

Move the Service under one model-scoped controller owner.

Options:

1. Introduce a dedicated model-service/base-model CR keyed by `(namespace, baseModelName)`. It owns the HeadlessService.
2. Formalize one canonical `DynamoModel` with `modelType: base` per `(namespace, baseModelName)` and make it own the Service. This requires deterministic identity plus uniqueness/conflict handling; today `base` is only a supported type, not an enforced singleton.

DGD/DCD components then contribute selected pods only. LoRA `DynamoModel`s discover the EndpointSlices but do not own the Service.

Do not solve this with multiple controller owner references.

### Checkpoint RCT lifecycle

Preferred: move checkpoint-RCT creation into `DynamoCheckpointReconciler`.

```text
DGD
  └── creates DynamoCheckpoint with checkpoint DRA inputs

DynamoCheckpoint controller
  ├── creates/updates checkpoint RCT, parent = DynamoCheckpoint
  └── renders checkpoint Job with its deterministic RCT reference
```

This removes the DGD-to-checkpoint owner transfer and the `WithSharedOwnership` call.

The `DynamoCheckpoint` API/controller must retain or explicitly carry the input needed to render the RCT—GPU count and DeviceClass—before DRA preparation removes scalar GPU resources from the pod template.

A smaller alternative is an explicit, exact DGD-to-`DynamoCheckpoint` handoff policy. It must validate the deterministic checkpoint identity and must not permit arbitrary RCT ownership.

## Acceptance criteria

- `WithSharedOwnership` is deprecated, and both lifecycle implementations no longer require it.
- The model HeadlessService has one model-scoped lifecycle owner, independent of which DGD/DCD first served the model.
- A checkpoint RCT has `DynamoCheckpoint` as its controller owner throughout its durable lifecycle.
- Tests cover ownerless and foreign-controller resources, expected lifecycle ownership, stale/recreated owner UID, and delete behavior.

### julienmancuso · 2026-09-22

I traced the two current `WithSharedOwnership` callers against the post-#14076 code and think the fix should be split into three parts:

1. **Give the model HeadlessService a model-scoped owner.** Introduce a deterministic namespaced CR/controller (for example, `DynamoBaseModelService`) keyed by `baseModelName`. DGD/DCD objects would only contribute selected pods; the model-scoped controller would own and reconcile the Service, define its metadata, and delete it only after the last DGD/DCD consumer disappears. I do not think the existing `DynamoModel` is a safe owner without first adding canonical-singleton and lifecycle semantics. This part changes the operator API/architecture, so I believe it should have a DEP.

2. **Harden the checkpoint RCT handoff in Dynamo.** Since #14076 removed `DynamoCheckpoint`, the durable owner is now the external `SnapshotJob`. For the current API, Dynamo should implement an explicit state machine: accept only an RCT controlled by the exact current DGD UID before handoff, or by the exact expected `SnapshotJob` UID afterward; reject ownerless, foreign, and stale-UID resources. The adoption step must require the exact DGD owner before replacing it, rather than removing any controller reference. This looks like a localized correctness fix that does not need a DEP. A future design in which Snapshot creates the RCT from the beginning would be cleaner but would require a coordinated Snapshot API/controller change.

3. **Deprecate and remove `WithSharedOwnership`.** Once both callers migrate, keep `SyncResource` strict and delete the unrestricted bypass rather than replacing it with another generic ownership callback. Add regression coverage for foreign/ownerless/stale-UID collisions, two model consumers and first-owner deletion, last-consumer cleanup, and idempotent DGD-to-`SnapshotJob` handoff.

Suggested sequencing: land the Dynamo-local checkpoint fix first; write/approve the model-service DEP; implement the model-scoped controller plus migration; then remove `WithSharedOwnership`.

@tmonty12, does this split and sequencing match what you had in mind? In particular, do you agree that the checkpoint portion should now target the exact DGD → `SnapshotJob` handoff in Dynamo, while only the model-service lifecycle needs a Dynamo DEP?
