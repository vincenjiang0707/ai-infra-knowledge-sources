## 正文

## Summary

Endpoint startup published local routing and health state before request-plane and discovery registration finished. If startup failed, or an endpoint shut down, process-wide state could remain visible after the endpoint stopped serving. A restart could then inherit the earlier endpoint's engine, canary target, notifier, or readiness state.

Each endpoint start now owns a scoped registration with idempotent drop cleanup. Discovery setup runs in the owned cleanup task so caller cancellation still unregisters a completed backend write and its request-plane handler. Rollback and shutdown release its local engine, health-check target, notifier, readiness entry, discovery record, request-plane handler, and graceful-shutdown registration. Local engines and canary targets carry registration identity, so late cleanup removes only its own state and can re-expose another outstanding registration.

Canary probes carry that identity through completion. Results from released registrations are discarded, and a replacement monitor cannot be marked ready by the outgoing handler. Configured health entries remain `NotReady` after their final target is released; unconfigured entries are removed.

Request-plane routes and cleanup include the namespace, component, endpoint name, and runtime instance ID. Same-named endpoints in different namespaces or components can coexist, and TCP and NATS remove only the requested handler. TCP discovery publishes the complete routing path; NATS retains its existing service-scoped subjects. NATS reserves an instance route before creating its subscription and owns setup through listener shutdown in one task. Unregistration waits for setup cleanup before a replacement can reuse the route. Caller cancellation cancels the owned task while retaining its reservation through cleanup. TCP serializes handler ownership and readiness changes. TCP and NATS share transport registration counts and keep a shared endpoint ready until its final handler stops. Cleanup uses main’s compatible `unregister_endpoint_instance` API and escaped TCP routing paths. Re-exposing a canary target also re-arms the manager with that registration’s notifier.

The startup retry path also preserves timeout context when an etcd connection error arrives at the deadline, retaining the underlying error for diagnosis. This keeps deadline reporting consistent with the existing startup-timeout test.

# Plan — ai-dynamo/dynamo#13475: endpoint rollback and shutdown retain canary and local-engine state

Route: implementation
Template: debug-investigation
Engine: vllm

## User intent

The caller wants the endpoint lifecycle in `lib/runtime` made symmetric. Today, starting an
endpoint installs three pieces of process-wide, endpoint-keyed state — the local engine in
`LocalEndpointRegistry`, the canary health-check target/notifier in `SystemHealth`, and the
derived `NotReady` endpoint-health entry — and nothing ever takes them out again. Neither the
two rollback paths inside `EndpointConfigBuilder::start_with_registration` nor a clean
`StartedEndpoint::shutdown` releases them. The concrete asks are: give `LocalEndpointRegistry`
a removal operation; make `start_with_registration` acquire the local-engine and health-check
registrations transactionally; release every endpoint-scoped registration on each failure path
and on endpoint-scoped shutdown; and add regression coverage that (a) forces request-plane and
discovery registration failures *after* local-engine and health-target setup and asserts no
endpoint-scoped state survives, and (b) starts, shuts down, and restarts the same endpoint name
with a different engine and payload and asserts the *new* instance is the one checked and
reported.

## Non-goals

- Runtime-wide health-check manager teardown. That is the subject of open PR #13434 and stays
  out of this diff; our cleanup is scoped to one endpoint instance.
- Bounding or reshaping the health-check response drain (open PR #13436).
- Changing canary readiness *aggregation* semantics — how `/health` combines endpoint statuses
  is open PR #8592's territory. We change only which endpoints are present in the maps, and we
  must not regress the four aggregation behaviors already pinned by tests in `system_health.rs`.
- Operator-side canary enablement (open PR #11083).
- Any change to discovery, the request-plane transports, or the graceful-shutdown tracker
  beyond calling the release path they already have.
- Re-architecting `EndpointConfigBuilder` beyond what transactional acquisition requires.

## Symptom, and what would reproduce it

**Symptom.** In one process, start an endpoint named `generate` with a health-check payload and
a registered local engine, then either (i) let request-plane or discovery registration fail, or
(ii) shut the endpoint down cleanly and start a *new* endpoint under the same name with a
different engine and payload. In case (i) the process is left with a callable local engine and
a live canary target for an endpoint that has no request-plane or discovery presence; the canary
keeps firing against it and can mark that phantom record `Ready`. In case (ii) the second start
silently keeps the *first* endpoint's `Instance`, payload, notifier, and monitor task — the
health check reports on an object that no longer exists.

**Ranked hypotheses, and the smallest observation that separates them.**

| # | Hypothesis | Smallest distinguishing observation |
|---|---|---|
| H1 | State is installed before the fallible steps and no release exists at all. | Read `start_with_registration`: is there any call that removes from `LocalEndpointRegistry` or `SystemHealth` on any path? |
| H2 | Release exists but only some paths call it. | Compare the request-plane-failure return, the discovery-failure arm, and the cleanup task for asymmetry. |
| H3 | Release exists and is called, but `SystemHealth` refuses the *re*-registration, so restart is the only broken case. | Read `register_health_check_target`'s duplicate handling. |
| H4 | The registry entry is removed but the canary task outlives it and panics or spins. | Read the canary loop's behavior when `get_health_check_target` returns `None`. |

Discovery below settles this: **H1 is true** (there is no removal API on `LocalEndpointRegistry`
at all, so no path can release it), **H2 is true** for the health-check target (the discovery
arm rolls back request-plane and tracker but nothing else), **H3 is true** independently
(`register_health_check_target` warns and returns on a duplicate), and **H4 is a consequence we
must handle**: the canary loop treats a missing target as a "CRITICAL … indicates a bug"
condition, and the endpoint-monitor treats a repeat registration as a reason to `break` the
whole dynamic-discovery loop.

## Chosen approach

Make the endpoint-scoped registrations a single acquire/release unit, and thread that unit
through every exit from `start_with_registration`.

**1. `LocalEndpointRegistry` gets a removal operation.** Add `remove(&self, endpoint_name: &str)
-> Option<LocalAsyncEngine>`, and — because a restart can legitimately overwrite the entry before
a slow release runs — a pointer-identity-conditional variant so a stale scope removes only the
engine it installed (`Arc::ptr_eq` against the stored value). Purely additive; the existing
`register`/`get` signatures do not move, so no caller anywhere changes.

**2. Registration of the local engine moves from builder time into `start_with_registration`.**
`register_local_engine` keeps its exact signature (`self, engine) -> Result<Self>`) and instead
stores the engine on a new `#[builder(default)] local_engine: Option<LocalAsyncEngine>` field of
`EndpointConfig`. The actual `registry.register(...)` happens inside `start_with_registration`,
as the first step of acquisition. This is what makes acquisition genuinely transactional: before
today's fallible steps run, *nothing* is installed by the builder that survives the builder. The
pre-flight bail at endpoint.rs:171–177 then consults the builder-held engine rather than the
registry. Both in-tree callers register-then-start in the same expression, so no behavior they
depend on changes; the only observable difference for an out-of-tree caller is that the engine
becomes visible in the registry at `start()` rather than at `.register_local_engine()`, which is
the more defensible contract given the canary is the only consumer.

**3. An endpoint-scoped state handle.** Introduce a small struct in `endpoint.rs` — call it
`EndpointScopedState` — holding the endpoint name, a `LocalEndpointRegistry` handle, the
`Arc<Mutex<SystemHealth>>`, and the identity of the engine it installed. It offers `acquire`
(register local engine, then register the health target/notifier/`NotReady` status, in that
order so the canary can never observe a target without a callable engine) and `release`
(the exact inverse). This struct is the transactional boundary the issue asks for, and it is
constructible from a plain `LocalEndpointRegistry::new()` plus a plain `SystemHealth::new(...)` —
no `DistributedRuntime`, no NATS — which is what makes the regression coverage runnable under
default features. That is a deliberate refactor for testability in the spirit of
`learnings/agency-refactors-for-testability.md`: the fix is only worth landing if its proof can
execute.

**4. Every exit releases.** The request-plane `?` at line 216 becomes an explicit match that
releases the scope before returning the error. The discovery-failure arm releases the scope in
addition to the request-plane and tracker unregistration it already does. On success the scope is
moved into the spawned cleanup task and released there, after discovery and request-plane
unregistration — which covers `StartedEndpoint::shutdown` and runtime-wide cancellation with one
code path, since both cancel the same token the task awaits.

**5. `SystemHealth` gains replace semantics and a deregistration method.**
`register_health_check_target` overwrites an occupied entry's `instance` and `payload` instead of
warning and returning, reuses or creates the notifier, resets `endpoint_health` for that key to
`NotReady`, and — the part the current early return silently skips — always sends on
`new_endpoint_tx` so the manager learns about the new incarnation. A new
`deregister_health_check_target(&self, endpoint_subject: &str)` removes the target, the notifier,
and the `endpoint_health` entry together. Removing the `endpoint_health` entry matters: leaving a
`NotReady` status for a departed endpoint would hold the worker unhealthy forever.

**6. `health_check.rs` learns that targets can disappear.** Three minimal edits, kept small to
limit collision with #13434 and #13436. The `.expect("Notifier should exist…")` in
`spawn_endpoint_health_check_task` becomes a graceful skip (the endpoint was released between the
channel send and the spawn — a race, not a bug). The canary loop's `None` arm stops shouting
`CRITICAL` and exits quietly, because a removed target is now the normal end of an endpoint's
life. And `spawn_new_endpoint_monitor` stops `break`ing the whole receive loop on a repeat
registration: a repeat now means a restart, so it aborts the prior task for that name, drops it
from `endpoint_tasks`, and spawns a fresh one. Leaving that `break` in place would be the worst
possible outcome of enabling replace semantics — one restart would silently disable dynamic
endpoint discovery for the entire process.

**Parameter shape, stated explicitly** (per the brief's note on callers in crates never opened):
every addition here is **optional or additive**. `local_engine` is a `#[builder(default)]
Option<…>` field reached only through the existing `register_local_engine` setter, whose
signature is unchanged. `LocalEndpointRegistry::remove` and
`SystemHealth::deregister_health_check_target` are new methods, not new parameters.
`register_health_check_target` keeps its three-argument signature and changes only behavior.
Nothing forces a churn edit on `rl.rs`, `worker.rs`, `state_agent.rs`, `state_agent_host.rs`,
`worker_query.rs`, `worker_query_endpoint.rs`, or the Python bindings. `cargo check --workspace
--all-targets` plus the separate `lib/bindings/python/Cargo.toml` check is what proves that
claim, and it is why Recipe 02 is non-negotiable here.

## Rejected alternatives

- **Make the release the caller's job** — hand `StartedEndpoint` a list of things to clean up and
  let each of the six calling crates do it. Rejected: it pushes an invariant into consumers who
  have no reason to know about `SystemHealth`, and it cannot fix the two *failure* paths, which
  never produce a `StartedEndpoint` at all.
- **Add a required `local_engine` parameter to `start_with_registration` (or to
  `EndpointConfig::build`)**. Rejected on exactly the ground the brief flags: it would force an
  edit in every caller, including callers in crates outside the ones this plan examined. An
  optional builder-held field achieves the same transactional ordering with a zero-caller diff.
- **Keep eager registration in `register_local_engine` and merely record the name for later
  removal.** Simpler diff, but it is not transactional: a builder that is configured and then
  dropped without `.start()` still leaks an engine into a process-wide map, which is the same
  class of bug we are fixing. Deferring is barely larger and closes that hole too.
- **Leave `register_health_check_target` ignoring duplicates and rely purely on removal.** This
  is tempting — if shutdown always removes, a duplicate should never arrive. Rejected because it
  makes correctness depend on perfect ordering: a restart that races a slow release, or any
  future path that registers without a matching release, silently pins the dead instance *and*
  silently skips the `new_endpoint_tx` send, producing an endpoint with no monitor at all. Replace
  semantics make the failure mode benign instead of silent.
- **Implement removal as an RAII `Drop` on the scope handle.** Attractive, but release must run
  *after* async discovery and request-plane unregistration inside the cleanup task, and `Drop`
  cannot express that ordering or be skipped on the success-hand-off path without a
  defuse flag. An explicit `release` is clearer to review and easier to assert on.
- **Write the regression tests only as `#[cfg(feature = "integration")]` tests against a real
  DRT.** Rejected as the *primary* coverage. Those tests need a live NATS server
  (`create_test_drt_async` passes `nats_config: Some(...)`), so they do not run under the
  crate's default `cargo test -p dynamo-runtime --lib`, which is what Recipe 02 and ordinary
  contributors execute. The fix would ship with proof that nothing routinely runs. The
  acquire/release refactor in item 3 exists specifically so the core assertions run on default
  features; an integration-gated end-to-end test is added *in addition*, not instead.

## Regression coverage plan

- `local_endpoint_registry.rs` gains its first test module: register → `get` is `Some`; `remove`
