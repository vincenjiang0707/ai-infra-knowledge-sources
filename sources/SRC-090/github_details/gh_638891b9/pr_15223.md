# [PR #15223] feat(power-agent): gate pod readiness on cap enforcement

## 正文

Implements [DEP #14767](https://github.com/ai-dynamo/dynamo/issues/14767), following the execute-ready implementation design posted in that issue's comments.

## Summary

Today a PowerAgent pod has no readiness probe, so it is Ready from the moment its container starts and stays Ready while every reconcile cycle fails. `kubectl get pods` shows `1/1 Running` for an agent that has enforced nothing since startup, and `kubectl rollout status` reports success for a rollout of non-functional agents.

This makes pod readiness mean that the agent is enforcing power caps. The claim published is narrow and self-reported:

> The agent's last reconcile cycle completed every enforcement action it was required to take with no reported failure, and completed recently.

A GPU with no running workload is intentionally skipped, so the claim covers the actions the cycle was required to take, not the live state of every GPU on the node.

### 1. The actuator reports whether its writes actually landed

`apply_cap` returns a `CapWriteResult(effective_w, ok)` NamedTuple instead of a bare int. `effective_w` keeps the existing contract exactly — the post-clamp value the agent *intended* to apply, returned regardless of the write's outcome. `ok` is the new information.

This could not be fixed at the call site by inspecting the return value: both actuators catch their write errors, increment `apply_failures_total`, and return a plausible post-clamp wattage anyway, so **a clean return from `apply_cap` was never evidence that a cap is live.** A `NamedTuple` specifically, so every existing wattage consumer has to be edited rather than silently keep working against a value that now means something else.

On the DCGM side five distinct early returns leave the GPU unwritten and now report `ok=False`; only the `_apply_cap_inner` normal return issued a Set. `_apply_cap_inner`, `restore_default`, and `restore_default_by_uuid` are unchanged — the last already returned `Optional[bool]` with exactly the semantics needed.

### 2. `reconcile_once()` folds that into a whole-cycle enforcement boolean

True iff every enforcement action the cycle was required to take completed, and the inputs it depended on were obtained. Every path that currently swallows a failure to keep the loop running now drives it false: a failed cap write, a cap skipped on unconfirmed GPU identity or mid-write re-enumeration, a failed PID snapshot, a failed release, a failed pod list, a failed device-count refresh.

**The runtime behaviour of those paths is unchanged** — the agent still never drops caps on failure, and a failing cycle does not exit the process (a NotReady agent that keeps reconciling can recover, while a restart drops in-memory GPU ownership). What changes is that the outcome is now observable as *state* rather than only as a counter.

Two things stay deliberately outside the fold:

- The persistence-only retries in `_flush_pending_retirements` / `_flush_pending_acquisitions`. Each retries a durable record whose hardware write and in-memory ownership already succeeded, so live enforcement is correct and only a *restarted* agent would notice.
- A cgroup read that yields no pod UID, which is indistinguishable from a non-Kubernetes process and so is not a failure the cycle can observe at all.

Two details the tests pin explicitly:

- The fold is `_reconcile_gpu(...) and ok`, never `ok and _reconcile_gpu(...)` — the second form short-circuits, so once one GPU failed no later GPU would be reconciled.
- Both `_shutdown` short-circuits return the fold accumulated so far, never a literal `True`. An unconditional `True` would publish a fresh successful timestamp at the exact moment `_shutdown_cleanup` starts restoring default caps, so `/readyz` would claim enforcement while enforcement was being torn down.

### 3. A fixed `GET /readyz` on container port 8081

Backed by one monotonic float, `_last_good_cycle`, assigned exactly once per cycle after the `try` — so a reader on the server thread cannot see a torn mix, an exception cannot leave a stale *successful* timestamp in place, and no lock is required. `0.0` covers both "no cycle has ever succeeded" and "the last one failed".

Ready iff that timestamp is non-zero and younger than `STALE_AFTER_S = 3 * RECONCILE_INTERVAL_S` (45 s at the default). The staleness bound is what catches a *hung* cycle, which nothing else can: `run()` has no watchdog, NVML and DCGM calls are unbounded, and the probe's `failureThreshold` cannot see a blocked cycle because nothing is failing — the timestamp is simply not advancing. The bound restarts nothing. The multiplier of 3 tolerates a healthy cycle lasting up to `2 * RECONCILE_INTERVAL_S`, since `run()` sleeps *after* each cycle.

Served from its own `wsgiref` server on a daemon thread, deliberately **not** from the Prometheus server, which `--prometheus-port=0` disables — readiness must not be optional. Started before `run()`'s `try` so a bind failure propagates uncaught and the pod CrashLoops, rather than sending a never-enforcing agent through the full `_shutdown_cleanup` restore sweep. The response body carries the age (`ok last_good_cycle_age_s=3.2`), which is what makes a 503 diagnosable with `kubectl exec ... curl` and no log access.

### 4. Chart

The DaemonSet gains the `readyz` container port and a `readinessProbe` against it. Probe values are hard-coded rather than templated: the port is fixed in the agent with no CLI flag, so a chart value that could disagree with it is a footgun, and a configurable `failureThreshold` would let an operator dial the debounce until readiness means nothing.

No liveness probe, no `startupProbe`, `updateStrategy` untouched, `dev-pod.yaml` unchanged.

Chart `1.3.1` → `1.4.0` and `appVersion` `"1.2.0"` → `"1.3.0"`: the `/readyz` server is new runtime code in the image, so **chart >=1.4.0 requires image >=v1.3.0** — an older image has no `/readyz`, so every pod is permanently NotReady and the rollout stalls at the first node.

### Behavioural change for existing installs

Documented in `NOTES.txt` and the `daemonset.updateStrategy` comment block (there is no `README.md` under the chart):

> Power Agent pods now carry a readiness probe tied to cap enforcement. An agent that is not enforcing goes NotReady, which consumes the DaemonSet rollout budget under `rollingUpdate.maxUnavailable: 1` and can stall a `helm upgrade` that previously completed. This is intended — an upgrade rolling over a node whose agent is not enforcing should not be reported as progress. The update strategy itself is unchanged.

### Out of scope

Per the DEP: no liveness probe, no operator / CRD / DGD-status / Planner change, no update-strategy change, no post-write readback, no per-pod enforcement records.

### Applied

**Zero discovered GPUs now fails the cycle.** The strongest finding. The GPU loop simply never ran, so the fold stayed at its initial `True` and `/readyz` published 200 for a node whose caps are entirely unmanaged. `DcgmActuator.device_count`'s own docstring already documents how this happens in practice — an agent that connected before the hostengine finished enumerating GPUs — and mitigates it by re-probing. If that re-probe still returns empty, the cycle cannot know what it was required to do, which is exactly the failure this endpoint exists to surface. Regression test added.

**Socket timeout on the readiness handler.** Confirmed: `wsgiref`'s server is single-threaded and `StreamRequestHandler.timeout` defaults to `None`, so `handle()` blocks in `rfile.readline()` for as long as an established client withholds its request line, stalling every kubelet probe behind it. `_QuietWSGIHandler` now sets `timeout = 5`, with a behavioural test that a stalled client does not block a later probe.

**Ephemeral port in the bind-collision test.** Correct that the literal 8081 made it flaky and parallel-unsafe. The test now occupies an ephemeral port and patches `READYZ_PORT`. The wildcard address is kept deliberately — a loopback-only collision against a wildcard bind is kernel-dependent.

**`test_serves_with_prometheus_disabled` rewritten.** Correct that it was non-discriminating: it drove `_readyz_app` directly and never started either HTTP server, so it proved nothing about the two being separate, which is the entire property. It now starts the real readiness server with `PowerAgentMetrics(0)` and issues an actual HTTP GET.

Also: `_start_readyz_server` now returns the server so tests can shut it down rather than leak a bound listener per test, and the four comment blocks that restated an adjacent docstring are removed.

### Not applied

**Render-time Helm check rejecting `prometheusPort: 8081`.** The implementation design considered and declined this: a failed bind should be fatal and visible, and a sixth `validate*` helper plus its helm suite is not worth an operator's self-inflicted typo. The added detail is right — the metrics server binds first and wins, so `/readyz` is what fails — but the outcome is still CrashLoopBackOff, which is the designed behaviour. `values.yaml` documents the constraint next to the field.

**Clearing readiness as soon as shutdown is observed.** The design deliberately keeps readiness serving through the termination grace period; taking every terminating pod NotReady would consume DaemonSet rollout budget under `maxUnavailable: 1`. The related rule that actually matters — a shutdown must not launder an earlier GPU failure, or `/readyz` would claim enforcement while `_shutdown_cleanup` tears it down — is already implemented and covered by `TestShutdownDoesNotLaunderTheCycleBoolean`.

**CodeQL's wildcard-bind alert on the test.** Test-only, and the wildcard is deliberate per the design note above.


### kaim-eng · 2026-09-24

Good catch, and the diagnosis is exactly right. Fixed in `06f54d663e`.

`settimeout` is per-**operation** and resets on every byte received, so `timeout = 5` bounded only how long a connection may go *silent*. A client trickling its request line never trips it, and with `WSGIServer` servicing one connection at a time it holds the accept loop and starves every probe behind it. The timeout was treating a symptom; the serialization was the cause.

**Two changes:**

- **`_ThreadingWSGIServer(ThreadingMixIn, WSGIServer)`** with `daemon_threads`. Serving concurrently is what actually decouples one client's pace from another's — no per-connection timeout can, while connections are serialized. Daemon threads so a connection in flight never holds the process open during shutdown, matching the `serve_forever` thread.

- **`max_connection_seconds = 15`**, an absolute lifetime bound enforced by a watchdog timer. Threading alone stops a slow client from blocking probes but would let such connections and their threads accumulate without limit.

  One implementation detail worth flagging, since it bit me: the watchdog calls `shutdown(SHUT_RDWR)`, not `close()`. `StreamRequestHandler` wraps the same descriptor in `rfile`/`wfile`, so `socket.close()` only drops a refcount — the fd stays open, the peer sees neither EOF nor an error, and the blocked read hangs on regardless. My first version used `close()` and the test was intermittently failing for precisely that reason.

`timeout = 5` stays as the idle bound, and the test pinning it now states explicitly why it is not sufficient alone.

**On the test gap you identified** — correct, the old test used a client that sends nothing, which the idle timeout already handled, so it could never have caught this. The new one drips one byte at a time: a request line followed by an endless run of padding headers, so it never completes and never looks idle.

Both new tests were checked to **discriminate**, by running them against a plain single-threaded `WSGIServer`:

- slow-drip probe: `TimeoutError` after 5.6s instead of being served
- watchdog: times out rather than observing the connection torn down

A test that passed both before and after the fix would have been worth nothing here, which is the same failure mode flagged earlier on `test_serves_with_prometheus_disabled`.

365 tests pass, run three times after the `shutdown`/`close` correction to confirm the flakiness is gone.
