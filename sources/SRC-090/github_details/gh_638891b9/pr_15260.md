# [PR #15260] feat(kv-router): preserve shared-cache event eligibility

## 正文

## Overview:

KV store events lose information when they are normalized. After normalization, a router cannot tell whether a block came from a plain text request or from a request that must never be served from a shared cache: multimodal, EAGLE, an unresolved LoRA, or one with unrecognized extra keys. This PR adds a `shared_cache_eligible` flag to `KvCacheStoreData`. The flag is computed from the raw worker event before normalization, and it is carried through the publisher, the coalescer, and radix-tree dump and replay.

This is the second of three independent PRs split out of #14965. The first is #15258. Nothing in this PR reads dump eligibility yet. The Mooncake Store shared-cache observer in #14965 is the consumer. This PR shares no files or commits with #15258, so the two can merge in either order.

## Details:

**Wire field and decoders**

- `KvCacheStoreData` gains `shared_cache_eligible: bool` with `#[serde(default)]`. Legacy JSON, named MessagePack, and positional MessagePack payloads without the field decode as ineligible. Missing provenance therefore never authorizes shared-cache learning.
- `KvCacheStoreData` deliberately has no `Default`. Because of that, 40 files change by one or two lines to set `shared_cache_eligible: false` in a struct literal. A missed literal is a compile error, not a silently ineligible store.
- Both ZMQ decoders in `lib/kv-router/src/zmq_wire/deserialize.rs` compute eligibility. A store is eligible only when all of these are true: the wire flag is absent or `true`, it is not EAGLE, the LoRA is either the base model or named, there is no multimodal block info, and every extra key is the LoRA name or the Dynamo cache-salt namespace (`extra_keys_are_text_only`). In the named-map decoder, unknown value types for `lora_id`, `is_eagle`, and `shared_cache_eligible` make the store ineligible instead of rejecting a GPU event that is otherwise usable.
- The positional decoder now reads slot 5 (`lora_id`) instead of discarding it.
- `extra_keys_to_cache_namespace` and the multimodal-hash parser also accept `Binary` extra keys that hold UTF-8, so GPU namespace normalization does not depend on the key encoding.

**Coalescing**

- `PlacementEventCoalescer` treats eligibility as part of store compatibility. A chain that mixes eligible and ineligible stores flushes as two events. The alternative was to collapse the merged event to ineligible, and then the eligible prefix would lose its provenance.

**Radix-tree provenance and dump restore**

- `RadixTree` can keep a per-worker map from `ExternalSequenceBlockHash` to `LocalBlockHash` for eligible blocks. Ineligible stores, removals, and worker or DP-rank resets clear the matching entries.
- `dump_tree_as_events` splits each dumped chain into runs of equal eligibility, so replaying a dump restores the flag block by block.
- The map is opt-in through `KvIndexerBuilder::shared_cache_provenance`, so a default router pays nothing. The frontend indexer enables it only when `shared_cache_type` is not `SharedCacheType::None`. The worker-side `LocalKvIndexer` always enables it, because its `TreeDump` is the production consumer and the worker does not know the router configuration. That map holds only the worker's own blocks.

**Test and bench fallout**

- The `kvbm-consolidator` test helper and the kv-router listener fixture used the positional encoder. With the new trailing field, a boolean landed in the `lora_id` slot (`invalid type: boolean, expected u64`). Both now encode events as named maps, as the production publishers already do.
- `dynamo-bench` boxes prepared Mooncake trace events to satisfy clippy `large_enum_variant`, because `RouterEvent` grew.

## Where should the reviewer start?

- `lib/llm/src/kv_router/publisher/batching.rs`: the coalescing rule in `compatible_data`.
- `lib/kv-router/src/zmq_wire/tests.rs`: decoder coverage for each ineligible case.
