# [Issue #14417] DEP (light): Explicit roles for compound components

source: https://github.com/ai-dynamo/dynamo/issues/14417
state: closed | updated: 2026-09-23T12:18:50Z
labels: enhancement, dynamo-deploy, deployment::k8s, dep:completed, operator

## 正文

## Summary

Introduce explicit `roles` as the internal structure of compound Dynamo components. A component remains the logical inference, lifecycle, scaling, service, rollout, and status unit; roles expose its distinct Pod-producing parts. The first use case is a multinode engine with `leader` and `worker` roles, allowing role-specific provider configuration without turning those roles into sibling DGD components. Existing manifests without `roles` retain their implicit behavior. Complete multinode role PodTemplates and their component-status projection are tracked by the follow-up DEP [#12696](https://github.com/ai-dynamo/dynamo/issues/12696).

The 1.5 foundation in [#14419](https://github.com/ai-dynamo/dynamo/pull/14419) deliberately excludes `roles[].replicas` and `roles[].podTemplate`. The additive role-cardinality API in [#14477](https://github.com/ai-dynamo/dynamo/pull/14477) and the deny-by-default shared PodTemplate field in [#14544](https://github.com/ai-dynamo/dynamo/pull/14544) have also merged. Multinode cardinality remains determined by `multinode.nodeCount`; the shared PodTemplate field does not itself enable role-template mode.

## Motivation

Dynamo components are already compound. A multinode engine is one logical component but produces a leader and one or more worker Pods. The Grove path lowers those Pods into multiple PodCliques within one PodCliqueScalingGroup. GMS can add further internal Pod roles. Today most of this structure is implicit.

[#12696](https://github.com/ai-dynamo/dynamo/issues/12696) needs different leader and worker Pod configuration. Its original API direction kept the component `podTemplate` as the leader and common base, then added a restricted `multinode.worker.podTemplateOverrides` overlay. That solves the immediate case but establishes a multinode-specific patch language.

The provider-native override API exposed the same structural issue. [#13273](https://github.com/ai-dynamo/dynamo/pull/13273) added `multinode.leader.providerOverride` and `multinode.worker.providerOverride`. These fields model internal roles but place them inside a multinode-specific structure.

Leader and worker are not independently meaningful graph nodes. They form one mandatory engine, scale as complete engine instances, and expose one component-level service and readiness result. Grouping graph-level components and structuring the inside of one component are different concerns.

The API should expose the existing compound structure inward while preserving the component as Dynamo's inference-aware semantic boundary.

## Proposal

### Semantic model

A role is a named, type-defined part of one component:

- The component remains the DGD graph node.
- `component.replicas` remains the number of complete component instances.
- The component owns rollout, scaling, Service identity, discovery, lifecycle, aggregate status, and the provider-neutral facts consumed by higher-level controllers.
- A role may produce one or more Pods and may lower to a provider-specific workload unit such as a Grove PodClique.
- A role is not independently deployable, routable, or scalable unless a future component-type contract explicitly says otherwise.
- Provider resource names are not role identity and are not exposed through this API.

Allowed role names, required membership, cardinality, and role-specific configuration are defined by the enclosing component type. Users cannot attach arbitrary roles to a component type that does not define them.

This is inward composition:

```text
component: decode
└── roles
    ├── leader
    └── worker
```

It is distinct from grouping graph-level components:

```text
component group
├── component A
└── component B
```

### 1.5 API foundation

Add a map-keyed role list to `DynamoComponentDeploymentSharedSpec`:

```go
type ComponentRoleSpec struct {
    // Name identifies a role within the enclosing component. The component
    // type defines the allowed and required names.
    Name string `json:"name"`

    // ProviderOverride configures the provider-native workload unit generated
    // for this role. Its availability follows the existing DGD/provider rules.
    ProviderOverride *ProviderOverride `json:"providerOverride,omitempty"`
}

type DynamoComponentDeploymentSharedSpec struct {
    // Existing fields...

    // +optional
    // +listType=map
    // +listMapKey=name
    Roles []ComponentRoleSpec `json:"roles,omitempty"`
}
```

The JSON API is a typed list keyed by semantic `name`, not an unstructured map or a list keyed by generated workload names.

`roles[].replicas` and `roles[].podTemplate` are not part of this first delivery. They are independent additive follow-ups. Keeping them out makes the initial API and its 1.5 backport a structural migration of existing role-scoped provider overrides rather than a change to multinode cardinality or Pod rendering.

### Multinode contract

Multinode is the first closed role schema. `multinode.nodeCount` remains authoritative and means the total number of Pods/nodes in one complete multinode engine instance.

```text
component.replicas  = complete engine instances
multinode.nodeCount = Pods/nodes per engine instance
leader Pods         = 1 per engine instance
worker Pods         = multinode.nodeCount - 1 per engine instance
```

When `roles` is absent, current behavior remains:

```yaml
replicas: 2
multinode:
  nodeCount: 8
podTemplate: ...
```

When `roles` is present, it must contain the complete, closed role set:

```yaml
spec:
  components:
  - name: decode
    type: worker
    replicas: 2
    multinode:
      nodeCount: 8
    roles:
    - name: leader
    - name: worker
    podTemplate:
      spec:
        containers:
        - name: main
          image: example/engine:latest
```

Both forms create two complete engines, each with one leader and seven workers. An explicit list containing only `leader` or only `worker` is invalid. The operator does not synthesize missing role entries.

### ProviderOverride migration

Move the existing multinode role-level paths:

```text
multinode.leader.providerOverride -> roles[name=leader].providerOverride
multinode.worker.providerOverride -> roles[name=worker].providerOverride
```

`MultinodeSpec` keeps only `nodeCount`:

```go
type MultinodeSpec struct {
    NodeCount int32 `json:"nodeCount"`
}
```

The root and component fields remain unchanged because they address different provider scopes:

```text
spec.providerOverride                 -> graph-level provider resource
components[].providerOverride         -> primary component workload unit
components[].roles[].providerOverride -> workload unit for one internal role
```

For Grove, these currently correspond to a PodCliqueSet, a component PodClique or PodCliqueScalingGroup, and an internal role's PodClique template. This mapping is lowering behavior, not role identity.

A worker-only topology override still declares both roles:

```yaml
roles:
- name: leader
- name: worker
  providerOverride:
    apiVersion: grove.io/v1alpha1
    target: PodCliqueTemplateSpec
    value:
      topologyConstraint:
        topologyName: cluster
        pack:
          required: rack
```

### Compatibility and rollout

The multinode `leader` and `worker` provider-override fields were introduced for the upcoming 1.5 API. The structural correction should land before those paths become a released contract.

Existing manifests without `roles` preserve their rendered workload, rollout identity, and implicit multinode behavior. A deployment may make the fixed `{leader, worker}` structure explicit without changing or rolling the rendered workload when neither role carries provider-specific behavior. The reverse transition is equivalent only when removing roles does not discard role-specific configuration.

The role structure is shared by embedded DGD components and standalone DCD specs. Provider-native overrides retain their DGD/provider-specific exposure restrictions.

### Multinode PodTemplate follow-up — tracked by #12696

The following records design context for [#12696](https://github.com/ai-dynamo/dynamo/issues/12696). Its implementation and validation are completion criteria for that follow-up, not for this roles DEP. #12696 adds complete role-specific PodTemplates to the established role entries without changing component semantics:

```yaml
roles:
- name: leader
  podTemplate:
    spec:
      containers:
      - name: main
        image: example/engine-leader:latest
- name: worker
  podTemplate:
    spec:
      containers:
      - name: main
        image: example/engine-worker:latest
```

Role-template mode is a Planner-runtime-dependent feature. Planner versions through 1.5 discover model, runtime, GPU, and power facts from `components[].podTemplate`, which is intentionally absent in this mode. If a DGD contains any `type: planner` component, every Planner must therefore resolve to Dynamo runtime 1.6.0 or later before any component may use `roles[].podTemplate`.

Admission resolves the Planner component's `runtimeVersionOverride` when it is set; otherwise it derives the version from the Planner image tag. The override is authoritative and does not change the image. This gate applies to Planner components, not to the Leader or Worker runtime images. A DGD without a Planner component and a DGD that stays in global-template mode have no new version restriction.

For example, this is valid even when the engine role images themselves remain on 1.5:

```yaml
spec:
  components:
  - name: planner
    type: planner
    runtimeVersionOverride: 1.6.0
    podTemplate:
      spec:
        containers:
        - name: main
          image: example/custom-planner-build
  - name: decode
    type: decode
    multinode:
      nodeCount: 2
    roles:
    - name: leader
      podTemplate:
        spec:
          containers:
          - name: main
            image: example/engine:1.5.0
    - name: worker
      podTemplate:
        spec:
          containers:
          - name: main
            image: example/engine:1.5.0
```

The same DGD is rejected if the Planner resolves to 1.5.x or earlier. A transition from the shared component PodTemplate to role-specific PodTemplates may atomically upgrade the Planner to 1.6 or later in the same update.

The operator, not each consumer, resolves the complete role templates. For multinode, `leader` is the serving role. Both the DCD/LeaderWorkerSet path and the Grove path publish the same component-level projection from the fully rendered serving Pod:

```yaml
status:
  observedGeneration: 7
  components:
    decode:
      servedModelName: Qwen/Qwen3-8B
      runtimeComponentName: custom-decode
      gpuPowerLimitWatts: 300
      gpusPerEngine: 8
      gpusPerReplica: 8
```

`servedModelName` and `runtimeComponentName` are omitted when the rendered command does not declare the corresponding model or endpoint override. `gpuPowerLimitWatts` is omitted when no component-level power limit is configured. `gpusPerEngine` and `gpusPerReplica` keep their existing explicit-zero and unavailable semantics.

Consumers such as the Planner read only current component status (`status.observedGeneration == metadata.generation`). They do not inspect `podTemplate`, select a role, or depend on provider workload names. During a worker rolling update, the status projection continues to describe the old active revision until cutover, together with the existing runtime namespace.

This projection is intentionally narrow. It covers the values whose old `components[].podTemplate` lookup becomes ambiguous once leader and worker can have different complete templates: served model name, endpoint component override, GPU shape, and per-GPU power limit. It does not expose the role structure as a second consumer API.

Complete role-specific PodTemplates do not turn roles into sibling components or independent scale targets.

### Role cardinality follow-up

The 1.5 API does not expose role cardinality. Multinode does not need it because `nodeCount` already defines the fixed leader/worker shape.

[#14477](https://github.com/ai-dynamo/dynamo/pull/14477) added optional `roles[].replicas`. For multinode, admission derives and persists `leader = 1` and `worker = multinode.nodeCount - 1` when omitted, and checks authored values against that same fixed shape. Other component types can define their own role-cardinality contracts; multinode roles are not independently scalable.

### Validation

Admission for the 1.5 foundation covers:

| Configuration | Result |
| --- | --- |
| Multinode, no roles | Valid; current implicit behavior |
| Complete `leader`/`worker` roles | Valid; cardinality still comes from `nodeCount` |
| Update from implicit roles to an equivalent explicit list | Valid; representation-only migration |
| Update from explicit roles to implicit roles without losing role settings | Valid |
| Only leader or only worker | Invalid |
| Unknown or duplicate role | Invalid |
| Roles on a type without a role schema | Invalid |
| Complete roles, provider override only on worker | Valid |
| Role provider override on a standalone DCD | Rejected by the standalone OpenAPI schema |

The following role-template cases belong to the [#12696](https://github.com/ai-dynamo/dynamo/issues/12696) follow-up and are not completion criteria for this DEP:

| Configuration | Result |
| --- | --- |
| Role PodTemplates with no Planner component | Valid; no Planner consumer is present |
| Role PodTemplates with every Planner resolving to runtime 1.6.0 or later | Valid |
| Role PodTemplates with any Planner resolving below runtime 1.6.0 | Invalid |
| Shared component PodTemplate with a pre-1.6 Planner | Valid; existing discovery contract |

For this DEP, conversion tests cover absent roles, complete roles, role-scoped provider overrides, and v1alpha1/v1beta1 round trips. Hash and lowering tests prove that the representation-only migration preserves the existing workload shape and rollout identity. The #12696 follow-up owns status tests for the serving-role projection across workload providers, v1alpha1/v1beta1 conversion, current-generation reads, and old-revision preservation during rolling updates.

### Alternatives

**Keep `multinode.leader` and `multinode.worker`.** This solves multinode locally but requires each compound component type to invent another structural API.

**Add only `multinode.worker.podTemplateOverrides`.** This is asymmetric and establishes user-visible merge semantics that do not naturally handle two complete heterogeneous PodTemplates.

**Allow partial role lists and infer missing roles.** This hides part of the desired structure and becomes ambiguous as role-level fields grow.

**Promote internal roles to sibling DGD components and group them.** This turns implementation fragments into graph nodes and moves the lifecycle boundary from the component to a group.

**Keep all roles implicit.** This cannot express the role-specific PodTemplates and provider configuration required by #12696 and future compound engines.

### Non-goals

This DEP does not define Component Group scaling, arbitrary subgraphs, graph-level workload programs, separate workload CRs, compiler ownership, SSA ownership of Grove resources, cross-resource transactions, KV-transfer wiring, TP/EP communication, Grove scheduling semantics, independent role autoscaling, or per-role public Services and status.

### sttts · 2026-09-07

One concern with the current update semantics: making the implicit → explicit transition immutable creates a migration hurdle.

An existing deployment cannot first make its already-existing roles explicit and then, in a later update, add role-specific NIC or PodTemplate configuration. For multinode, the implicit form already resolves to `leader=1` and `worker=multinode.nodeCount-1`. Replacing that with an explicit role list carrying exactly the same semantics should therefore be allowed as a representation-only migration and should not by itself change or roll the workload.

Actual role-specific configuration or template changes after that transition should follow the defined enclosing-component rollout semantics.

We should relax the DEP and implementation accordingly: compare the resolved role model rather than treating `roles: omitted` and `roles: present` as inherently different component topologies.

### sttts · 2026-09-08

The additive role-cardinality follow-up is now available as #14477. #14419 has merged, and #14477 is rebased on `main`.

It resolves the multinode defaulting question conservatively: `roles[].replicas` is optional. When omitted from an explicit role list, DGD and standalone DCD admission persist `leader = 1` and `worker = multinode.nodeCount - 1`; when provided, admission requires those exact values. Omitting `roles` still preserves the existing implicit multinode form.

The field therefore does not make multinode roles independently scalable or introduce a second conflicting source of truth. `component.replicas` remains the scale target for complete engine instances. The PR also preserves rollout-neutral implicit ↔ explicit migrations for equivalent role structures and requires an explicit worker count to change together with `nodeCount` when both are authored.

The role schema remains component-shape-owned. The only schema implemented today is multinode `leader` + `worker`; future compound types may use different defaulting and validation rules.

### sttts · 2026-09-09

### DEP change log — 2026-09-09: multinode role cardinality

After discussion with @jmancuso, the role-cardinality follow-up is now defined by #14477:

- `roles[].replicas` is part of the additive follow-up API rather than the 1.5/backport foundation in #14419.
- For multinode, `multinode.nodeCount` remains the authoritative shape and becomes immutable after creation.
- When an explicit `leader`/`worker` role list omits replica values, admission defaults and persists `leader = 1` and `worker = nodeCount - 1`.
- Explicit values remain consistency assertions and must match that fixed shape. They do not make roles independently scalable.
- Lowering continues to derive the Grove cardinalities from `nodeCount`, not from the assertion.
- Omitting `roles` still preserves the legacy implicit multinode representation. A semantically equivalent implicit ↔ explicit migration remains allowed and rollout-neutral.
- v1alpha1 requests receive the same defaults through conversion to the v1beta1 hub and an equivalent-version mutating webhook; there is no separate v1alpha1 defaulting implementation.

The compatibility tradeoff is explicit: existing objects remain valid, but changing an existing multinode `nodeCount` in place is no longer allowed. Changing the multinode shape requires recreation. This makes persisted role defaults stable and avoids requiring callers to atomically maintain a newly introduced derived field.

This supersedes the earlier #14477 note in this thread that allowed `nodeCount` and an explicit worker count to change together, and it replaces the original proposal's “Role cardinality follow-up” placeholder with the concrete #14477 contract.

The delivery is split one step further so the shared role API can land before either LPX or multinode depends on it:
