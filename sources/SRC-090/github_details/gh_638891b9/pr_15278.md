## Summary

Add an opt-in external PREDICT plugin that runs the public `theforecastingcompany/t0-beta` forecasting model locally. It maintains a bounded history of request counts and mean input/output token lengths, places all three signals in one multivariate group to forecast the next observation interval, and leaves replica sizing and GPU/SLO constraints to Dynamo's existing planner. The example has its own `tfc-t0>=0.5.0` requirements; no dependency is added to the default installation.

The built-in predictor currently runs at priority 0 and wins the first-writer merge before an external forecast can contribute. Move it to fallback priority 100 so an external predictor at priority 10 can supply traffic predictions. Nonfinal responses keep the built-in predictor's history warm and let it supply cache-hit and speculative-acceptance metadata. Existing deployments without external predictors retain the same predictor behavior.

The example includes loopback gRPC deployment configuration, warmup/invalid-input fallback, bounded inference concurrency across RPC cancellation, and explicit inference failures for the planner's existing fallback/circuit-breaker handling.

## Validation

- **188 focused tests passed**, covering the new predictor, actual tiny t0 model adapter (no weight download), real localhost gRPC, planner precedence/fallback, and existing external-plugin/merge tests. The new precedence regression failed before the priority change (`100 != 300`) and passed afterward. The grouping regression uses a real tiny t0 model and failed before shared group IDs were supplied. Idle-window regressions also failed before the fix and now pass: token lengths retain the last known request shape rather than learning artificial zero-length requests.
- These were run on macOS with a local harness bypassing eager `dynamo.planner` package initialization and substituting Python logging for native Rust logging configuration. Planner classes, gRPC transport, and the installed AIC native model were real. This does **not** establish native Dynamo startup or deployment compatibility.
- **20 new predictor/server tests also passed in a Linux container** with the actual `ai-dynamo-runtime==1.5.0`, v1.5.0 Python source plus the new example, normal planner package initialization, and real gRPC. No native or logging shims were used in that run. This is compatibility coverage for the example, not a full main-branch integration run.
- Repository pre-commit hooks passed for all changed files. Focused `ty check` passed for the new example and tests. README configuration parsed successfully through `PlannerConfig`.
- Full repository checks were attempted: pytest stopped with 144 collection errors (67 skipped) from unavailable optional/native dependencies; repository-wide Ruff and ty reported broad diagnostics outside this change. Full Linux CI remains pending.

Before the grouping change, an illustrative native v1.5 replay of 65,545 held-out BurstGPT requests on the documented Llama-3.1-8B FP8 / H200 configuration used 24 simulated GPU-hours for both the constant baseline and t0 p90, with all requests meeting the configured TTFT/ITL targets. All 288 held-out t0 responses matched the planner’s applied predictions. The workload stayed at the one-GPU floor, so this demonstrates integration, not GPU savings. These are simulated performance estimates, not physical GPU measurements.

Draft pending full main-branch Linux CI and broader workload evaluation. No GPU-cost reduction or SLO-improvement claim is made. Customer savings should be measured by replaying identical public/customer traffic with matched model, hardware, startup delays, budgets, and SLO targets, comparing native GPU-hours/goodput, and subtracting the forecasting process's provisioned cost.
