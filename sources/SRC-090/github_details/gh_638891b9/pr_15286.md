# [PR #15286] fix(vllm): unset disabled top_k/min_p, rerun SamplingParams post-init

## 正文

#### Overview

When the Python vLLM chat processor (`--dyn-chat-processor vllm`) runs in front of the vLLM gRPC sidecar, most chat requests fail with HTTP 500. The processor sends `top_k=0` or `min_p=0` when the client did not set them. The sidecar rejects these values because vllm-proto 0.3 cannot tell "disabled" from "unset". This PR sends the two controls as unset when the client did not ask to disable them.

The PR also makes the two sampling builders of the Python vLLM worker rerun vLLM's `SamplingParams.__post_init__`. Without this, a greedy request fails under speculative decoding when `generation_config` sets `min_p`. This failure also occurs on the default Rust preprocessor path on main.

**Repro**

```bash
DYN_CHAT_PROCESSOR=vllm lib/sidecar/vllm/launch/agg.sh --model Qwen/Qwen3-VL-2B-Instruct

curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "Qwen/Qwen3-VL-2B-Instruct", "max_tokens": 16, "temperature": 0,
  "messages": [{"role": "user", "content": "Say OK."}]}'
```

**Before**:

#### Details

**Why requests fail.** The processor resolves sampling through a vLLM `SamplingParams`: vLLM defaults, then `generation_config`, then the client fields. It then copies each resolved value into `sampling_options`. The greedy reset sets `top_k=0` and `min_p=0`, and a model with no `min_p` in `generation_config` resolves `min_p=0`. So most requests carry a "disabled" value that the client never sent. In vllm-proto 0.3, 0 means "unset" for these two fields, and the vLLM gRPC server replaces "unset" with the model default. The sidecar rejects 0 on purpose, so that a disabled `top_k` does not silently become the model's `top_k=20`.

**Fix 1: send unset, not disabled.** The processor is the layer that mixes up "the client did not set it" and "the client disabled it", so the fix goes there. A new helper, `_disabled_as_unset`, sends `top_k` or `min_p` as `None` when the value is disabled only because of the greedy reset or a missing `generation_config` entry. An explicit client value still goes on the wire, so the sidecar rule does not change.

**Fix 2: the worker bug that this exposes.** With `min_p` unset, the Python vLLM worker now applies the `min_p` from its `generation_config`. This exposes a bug that main already has on the Rust preprocessor path. The two sampling builders create `SamplingParams(**defaults)` and then `setattr` each request option, which skips `__post_init__` (the temperature clamp, the argument checks, and the greedy reset). vLLM checks the params before it runs `__post_init__` again, so a greedy request keeps the configured `min_p` and fails under speculative decoding. Both builders now call `__post_init__` after the overlays. Requests that passed on main get the same params, and invalid values still return 400. The prefill handler now sets `max_tokens=1` and `min_tokens=1` before the builder runs, so the rerun does not reject a client `min_tokens` above 1.

**Other sampling options.** No other option needs the helper. For `top_p` and `repetition_penalty`, the neutral value is 1.0, which both backends accept (vLLM rejects 0). For the presence and frequency penalties, 0 means "no penalty" in vllm-proto, and neither backend reads them from `generation_config`. `temperature` and `seed` are optional proto fields, and `n` defaults to 1.

**Limits.**

- A worker with its own `generation_config` override now applies its `top_k` or `min_p`. Before, the frontend overwrote it with 0.
- A client that explicitly sends `top_k=-1`, `top_k=0` or `min_p=0` still gets a sidecar rejection, as intended.
- A worker with speculative decoding and a `min_p` in `generation_config` now rejects a sampled request with no client `min_p`, the same as on the Rust preprocessor path. On main, the frontend `min_p=0` hid this.

Out of scope, and the same as on main: the processor still sends its resolved `temperature`, `top_p` and `repetition_penalty`, and a sidecar rejection caused by the client still returns HTTP 500.
