# [Issue #14473] DEP: LPX Component Type Integration

state: open | updated: 2026-09-23T10:57:34Z
labels: enhancement, dynamo-deploy, deployment::k8s, dep:draft, operator

## 正文

> **Credit:** The design and implementation described in this DEP are the work of @andrewpaprotsky. I only collected the discussion and wrote it down here.

## Summary

Add `lpx` as a DynamoGraphDeployment (DGD) component type for deploying LPU-backed inference engines.

Unlike existing component types, an LPX component is lowered through an LPX-specific compiler. Starting from the component configuration, role-specific PodTemplates, and an immutable build, this compiler derives the complete LPU workload: LPU agent Pods and a conductor role materialized as either an LPU-only conductor or a GPU-side cyborg, together with runtime configuration, placement requests, and Grove topology.

The selected Grove workload program sends `type: lpx` components through this dedicated lowering path. LPX requires the Grove provider; the DCD workload program does not materialize LPX components. `LPXGraphDeployment` (LGD) is the generated Kubernetes object that persists the handoff to the LPX controller and exposes its status. It is an implementation boundary of the lowering path, not the main abstraction proposed by this DEP.

## Motivation

Dynamo component types already have type-specific semantics. A vLLM, SGLang, or TensorRT-LLM component is not merely a PodTemplate: Dynamo interprets its engine type, topology, backend configuration, and role in the inference graph before producing Kubernetes workloads.

LPU-backed engines require another such lowering path. LPX is the compiler and runtime stack used to materialize them.

An LPX component describes a logical inference engine, but the resulting workload cannot be obtained by rendering its PodTemplate directly. Its immutable build and component roles must be processed by the LPX compiler to determine:

- a `conductor` role materialized as an LPU-only conductor or a hybrid GPU-side cyborg, according to the immutable build;
- the number and configuration of LPU `agent` roles;
- LPU partition and rank assignments;
- runtime configuration and commands;
- model preparation;
- scheduler placement intent;
- the resulting Grove `PodCliqueSet`, `PodCliqueScalingGroup`, and `PodClique` structure.

Adding this behavior as conditionals throughout the existing Grove renderer would make `type: lpx` a global mode of the DGD controller. The desired integration is another component lowering path selected through the workload-program architecture.

## Guiding principles

1. **A component type owns inference semantics.**

   The `roles` mechanism is shared across component types, but each component type defines the semantic role vocabulary and its interpretation. The LPX component implementation understands LPX builds, roles, compilation, runtime wiring, and readiness.

2. **Roles are semantic parts of a component.**

   LPX exposes `agent` for LPU execution and `conductor` for the coordinating role. The immutable build determines whether the conductor is materialized as an LPU-only Pod or a GPU-side cyborg. These remain roles inside one logical LPX engine component. They are not independent components reconstructed through a group.

3. **The Grove workload program selects the lowerer.**

   Every DGD component is claimed by exactly one materializer. Existing component types retain their current lowering.

4. **Groups are not semantic.**

   Scaling Groups, as explored separately in #14469, would provide an explicit outer scaling dimension and may optionally add a gang constraint. `component.replicas` and `scalingGroup.replicas` remain independent, multiplicative dimensions. Group membership must never change the meaning or validity of `component.replicas`, and groups must not encode what an LPX engine means.

5. **The selected lowerer owns its materialization details.**

   The DGD controller dispatches LPX intent and aggregates status. It does not interpret LPX compiler output or the resulting Grove child topology.

## Goals

- Support `type: lpx` as a DGD inference component type.
- Add a dedicated lowering path for LPU-backed components.
- Require the Grove workload provider for LPX components.
- Give the LPX lowering its own retryable and observable controller boundary.
- In the initial `v1alpha1`, allow one DGD-scoped LGD to claim all LPX components, including supported multi-component LPX workloads.
- Explicitly defer plural LGDs, component- or Scaling-Group-based claim partitioning, and claim transfer until Scaling Groups exist.
- Preserve DGD as the only user-authored API in the initial integration.
- Project LPX readiness and failures into ordinary DGD status.
- Keep deployments without LPX components on their existing reconciliation paths.
- Preserve a future path toward joint Grove graph assembly when explicitly required.

## Non-goals

- Making LGD a user-authored API in the initial version.
- Defining the final self-contained LGD specification.
- Introducing Component Groups or Scaling Groups.
- Creating multiple LGDs for one DGD in the initial integration.
- Partitioning LPX components into component- or Scaling-Group-scoped LGD claims in the initial integration.
- Defining claim-transfer or two-phase handoff semantics before plural LGDs and Scaling Groups exist.

- Allowing multiple controllers to modify the initial LPX-owned PCS.
- Providing Grove constraints across the ordinary and LPX PCS boundaries.
- Selecting Server-Side Apply or a render collector for future joint PCS assembly.
- Changing the behavior of non-LPX component types.

## Proposal

### LPX component shape

Users describe an LPX-backed engine as a normal DGD component:

```yaml
spec:
  components:
  - name: decode
    type: lpx
    replicas: 2

    lpx:
      buildId: model/build-abc

    roles:
    - name: conductor
      podTemplate:
        spec:
          containers:
          - name: main
            image: lpu-conductor-runtime

    - name: agent
      podTemplate:
        spec:
          containers:
          - name: main
            image: lpu-agent-runtime
```

The `roles` field is the shared DGD mechanism defined separately by #14417. It is encoded as a Kubernetes list-map keyed semantically by `name`. The mechanism is generic; its vocabulary is not. Each component type defines which role names are valid and what they mean during lowering. LPX uses `agent` and `conductor` for both LPU-only and hybrid engines. The build determines whether `conductor` becomes an LPU-only coordinator or a GPU-side cyborg.

> **Implementation status:** [PR #15062](https://github.com/ai-dynamo/dynamo/pull/15062) exposes the semantic `conductor` and `agent` roles. A hybrid build maps its `conductor` role to a GPU-side cyborg workload.

`component.replicas` remains the component-local multiplicity. Without an enclosing Scaling Group, the effective number of component instances equals `component.replicas`; with a future Scaling Group, it equals `scalingGroup.replicas × component.replicas`. Group membership must not change the field's meaning or validation. Exact role cardinalities and validation against the immutable build remain LPX lowering semantics; this DEP does not freeze them.

### Dedicated workload lowering

The selected Grove workload program partitions the graph according to component type:

```text
DynamoGraphDeployment
├── frontend, prefill, ... ──> existing lowerers
└── type: lpx ───────────────> LPX lowerer
```

The ordinary Grove lowerer ignores components claimed by LPX. The DCD workload program rejects LPX components because LPX requires Grove. Every component must be claimed exactly once. Deployments without LPX components remain unchanged.

Before Scaling Groups exist, all LPX components in one DGD form one implicit DGD-scoped materialization unit and are handed to one LGD. This is an initial compatibility rule, not the permanent composition model. The initial DGD reconciler is not required to model claim sets, partition LPX components, reconcile plural LGDs, or implement two-phase claim transfer. Those concerns are explicitly deferred to the Scaling Group follow-up.

### `LPXGraphDeployment` as persisted handoff

The DGD controller initially creates at most one LGD for a DGD. When LPX components exist, that LGD represents the implicit materialization unit containing all of them.

In the initial `v1alpha1`, the LGD spec contains only a controller-computed revision of the effective LPX inputs. Source identity is carried by an exact DGD controller `OwnerReference`, including the DGD name and UID. The initial singleton LGD may use the same namespace and name as its source DGD for lookup compatibility, but name equality is not the long-term identity contract and must not be required by the controller boundary. The LGD does not copy the DGD configuration:

```yaml
apiVersion: nvidia.com/v1alpha1
kind: LPXGraphDeployment
metadata:
  name: model
  namespace: default
  ownerReferences:
  - apiVersion: nvidia.com/v1beta1
    kind: DynamoGraphDeployment
    name: model
    uid: "<DGD UID>"
    controller: true
spec:
  inputRevision: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

The DGD controller calculates `inputRevision` from only the effective inputs to LPX lowering, including the selected restart token. In the initial singleton this means all LPX components. Once plural LGDs exist, each revision covers only the components and shared inputs of its claimed materialization unit. Changes outside that unit do not create a new LPX revision. The field is controller-populated rather than user-authored configuration.

The LGD controller validates that its controller `OwnerReference` exactly matches the source DGD identity, including API version, kind, name, and UID. It obtains the source DGD name from that owner reference rather than from the LGD name, extracts the claimed LPX components and relevant graph-level defaults, and reconciles the exact effective-input revision identified by `inputRevision`. Together, the exact owner identity, materialization-unit claim, and input revision provide the identity and fencing boundary for the handoff.

This intentionally avoids defining a second copy of the relevant DGD schema in the initial integration.

### Initial LGD and PCS identity

The initial integration creates at most one LGD per DGD. The singleton may use the source DGD name for lookup compatibility. Its exact DGD controller `OwnerReference`, including UID, remains the authoritative source identity.

The DGD controller selects and owns the LGD identity. The LGD controller selects and owns the PCS identity below that LGD and keeps the PCS identity private to its own reconciliation. No PCS name or reference is part of the DGD-to-LGD control contract. An optional status reference may be added later for a concrete observability or tooling use case, but DGD must not consume it and reconciliation correctness must not depend on it.

The owning LGD is the naming and reconciliation root for every resource it controls. PCS, runtime ConfigMaps, LPUPipelineRequests, endpoint resources, and other materialization children derive their names and reconciliation keys from the LGD or an explicit LGD-local materialization key, never from the source DGD name. The DGD name and component metadata may still be propagated through LGD PodTemplates onto Pods for discovery, observability, and user-facing attribution. Such labels are metadata, not lookup, ownership, fencing, or deletion authority. The LGD controller obtains source identity from the exact DGD controller OwnerReference.

### Materialization revision boundary

An LGD inputRevision defines one immutable materialization revision. Resources consumed by running Pods must not be changed in place from one revision to the next while the old workload can still run. Runtime ConfigMaps are therefore revision-specific snapshots whose names are rooted in the LGD identity and include a bounded input-revision or content digest. The controller creates the successor resources, references them only from the successor PCS, retains the previous resources while the previous PCS exists, and garbage-collects them after retirement.

Recovery and other destructive actions establish authority through the concrete LGD-owned Kubernetes object chain. For Grove Pods this means validating the owner chain from Pod through PodClique, PodCliqueScalingGroup, and PodCliqueSet to the exact LGD name and UID. Revision annotations may provide additional fencing, but source-DGD labels never substitute for ownership.

### Future: plural LGDs and claim handoff

> This section records follow-up constraints for the Scaling Group design. It is not an implementation requirement for the initial LPX integration.

Once Scaling Groups and plural LGD reconciliation exist, the durable identity of an LGD is expected to be its source DGD plus a materialization-unit key:

```text
(DGD UID, component, <component name>)
or
(DGD UID, scaling-group, <group name>)
```

The future DGD controller would own the desired set of LGD claims and allocate a stable, collision-resistant LGD name from that key. LGD naming must not depend on a compiled Grove graph or PCS name.

Changing the future partition from one unit to another is an ownership transfer. To prevent two active LGDs from materializing the same component, that design will need a fenced handoff, conceptually:

1. **Prepare:** allocate or update the desired LGD identities and revisions without giving a new LGD overlapping materialization authority.
2. **Commit:** activate the new claim only after any predecessor LGD that claimed the same component has fenced and retired its workload.

The exact future claim API, naming scheme, and handoff protocol belong to the Scaling Group follow-up. They are deliberately not selected by this DEP and need not be implemented by the initial PR.

### LPX lowering responsibilities

The LPX controller performs the complete type-specific lowering:

```text
LPX component intent
        │
        ▼
resolve immutable build
        │
        ▼
prepare model artifacts
        │
        ▼
compile roles and LPU topology
        │
        ▼
render runtime configuration
        │
        ▼
create LPUPipelineRequest and Grove workload
        │
        ▼
observe placement, readiness, and recovery
```

It owns the resulting LPX-specific resources and behavior, including:

- runtime `ConfigMap` and `Service` objects;
- `LPUPipelineRequest`;
- the LPX `PodCliqueSet`;
- scheduler and placement interaction;
- retry, fencing, recovery, and cleanup;
- detailed LPX status.

The DGD controller owns workload selection, LGD creation, ordinary component lowering, aggregate status, and deletion ordering. It must not reproduce the LPX state machine or depend on the names of LPX Grove children.

### Initial singleton and future materialization-unit partitioning

LGD is a deployment and materialization boundary, not a compiler artifact. Each LPX component references its own immutable compiler artifact through `buildId`.

Before Scaling Groups exist, the initial integration has exactly zero or one LGD per DGD. If LPX components exist, the single LGD claims all of them. It supports either multiple independent complete LPX engines, each with its own `conductor` and `agent` roles, or one shared uniform speculative-decoding draft/target pair. A shared pair cannot be mixed with additional independent LPX engines. The shared pair lowers as:

```text
DGD
├── frontend
├── draft   type: lpx, buildId: draft/build-abc ─┐
└── target  type: lpx, buildId: target/build-def ┴──> implicit all-LPX unit
                                                        └──> one LGD
                                                             └──> one coupled LPX Grove workload
```

The compiler artifacts remain distinct, while LPX lowers them into one coupled SpecDecode workload. In the current implementation, target component replicas are restricted to one; draft component replicas express draft multiplicity and are unfolded into distinct Agent clique templates inside one LPX PCSG whose replica count is also one. This is a type-specific restriction, not a rule conditional on group membership.

For independent complete engines, the same LGD claims every LPX component and owns one LPX PCS containing a separate workload group for each engine. Sharing that initial LGD and PCS is a materialization choice; the engines remain distinct DGD components with independent serving semantics and component replica counts. This initial all-LPX claim does not define the future partition.

The implicit all-LPX unit is the complete scope of the initial integration. Plural LGDs and component- or group-based partitioning are a follow-up that starts only once Scaling Groups exist. The expected future partition is:

```text
ungrouped LPX component                  -> one LGD for that component
LPX components in the same Scaling Group -> one LGD for that group
```

Two ungrouped LPX components therefore produce two LGDs. They may still participate in speculative-decoding wiring, but they do not gain one materialization, scaling, or gang boundary merely because both have `type: lpx`. If they require one shared LPX materialization and Grove scheduling scope, an explicit Scaling Group supplies that boundary.

The Scaling Group does not define speculative-decoding semantics and does not combine compiler artifacts. LPX component and wiring logic still decides whether the claimed component set is a valid SpecDecode shape and how its separate builds interact. The group only establishes the shared materialization unit, outer replica dimension, and optional gang constraint.

### Status projection

LGD exposes rich status from the initial version, including:

- observed source input;
- compilation and placement state;
- model-preparation state;
- readiness for each claimed DGD component;
- retry, recovery, and terminal failures;

The DGD controller projects this into normal component status and computes aggregate DGD readiness. Users continue to observe the DGD as the primary resource.

### Future self-contained LGD spec

A future API revision may make LGD independently reconcilable by copying the relevant part of the DGD into its spec. This would make LGD effectively a filtered DGD.

The following sketch is illustrative. It shows the expected shape and data ownership, but does not propose final field names, nesting, or another API version:

```yaml
apiVersion: nvidia.com/<future-version>
kind: LPXGraphDeployment
metadata:
  name: model-lpx
spec:
  inputRevision: sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef

  # Illustrative future selector; exact field names are not proposed here.
  materializationUnit:
    scalingGroup: specdecode

  scheduling: ...
  labels:
    example: value
  annotations:
    example: value
  env:
  - name: EXAMPLE
    value: value
  priorityClassName: high-priority
  backendFramework: ...

  components:
  - name: draft
    type: lpx
    replicas: 2
    lpx:
      buildId: draft/build-abc
    roles:
    - name: agent
      podTemplate: ...

  - name: target
    type: lpx
    replicas: 1
    lpx:
      buildId: target/build-def
    roles:
    - name: conductor
      podTemplate: ...
    - name: agent
      podTemplate: ...
```

The illustrative `materializationUnit` identifies the subset claimed from the owning DGD. A single ungrouped engine would instead identify `component: decode`. It is not another reference to the source DGD; source identity remains the exact controller `OwnerReference`. The field name and union encoding are intentionally not fixed here.

This illustrative speculative-decoding shape is LPU-only, so the target's `conductor` materializes as an LPU-only Pod. A separately supported hybrid engine also uses the `conductor` role, materialized as a GPU-side cyborg; this example does not imply hybrid SpecDecode support. The component replica values remain local multiplicities; the selected Scaling Group supplies the independent outer multiplier.

The two `buildId` values deliberately remain separate compiler artifacts. Their pairing and shared materialization are LPX lowering semantics, not evidence of a combined compiler artifact.

The exact DGD controller `OwnerReference` remains the ownership and source-identity boundary, while the copied LGD spec becomes the authoritative reconciliation input. Until that future API is defined, the initial `v1alpha1` contains only `inputRevision`; the initial LGD implicitly claims all LPX components and reads their effective inputs from the DGD named by its controller owner reference.

Only actual LPX inputs should be copied. LGD should not become a second complete DGD API.

### Initial Grove materialization

The initial integration uses separate Grove objects:

```text
existing DGD lowering             LPX lowering
         │                             │
         ▼                             ▼
PodCliqueSet / normal          PodCliqueSet / lpx
owner: DGD                     owner: LGD
```

This provides unambiguous writer, retry, finalizer, and deletion ownership.

Runtime traffic may cross the boundary through Dynamo discovery and services. Grove-native constraints cannot initially cross it, including colocation, `startsAfter`, shared PCSG indices, or one Grove rollout envelope.

#### Initial implementation assumption: Grove naming and addressing

The initial LPX lowerer follows the same compatibility boundary as today's multi-node Grove lowering. It may render peer addresses from Grove-injected environment variables and Grove's published name-generation helpers. For example, current multi-node rendering configures a leader address with a form equivalent to:

```text
$(GROVE_PCSG_NAME)-$(GROVE_PCSG_INDEX)-<component>-ldr-0.$(GROVE_HEADLESS_SERVICE)
```

The controller constructs this expression; the Pod only expands the environment variables injected by Grove. The assumption is therefore not that generated names are opaque. It is that their shape is a published, versioned Grove API contract. A breaking change in that contract is a compatibility risk already shared by multi-node components; LPX does not introduce a new category of coupling here.

This does not permit the DGD controller to select, reconstruct, or watch LGD-owned Grove child names. In particular, the DGD-to-LGD handoff selects the LGD identity, not its PCS name. The LPX controller chooses, owns, and privately reconciles the PCS identity and may use Grove's published contract while materializing and wiring descendants. Neither controller should duplicate undocumented Grove naming rules or introduce LPX-specific naming conventions. A future Grove API may provide explicit sibling references or addresses and remove descendant-name reconstruction for both multi-node and LPX, but that is not required by this DEP.

### Future joint Grove materialization

Separate PCSs are not necessarily a permanent restriction.

DEP #14420 describes how independent workload lowerers could eventually contribute to one joint PCS when an explicit Grove-level constraint requires it. Possible mechanisms include:

- multi-writer Server-Side Apply with disjoint field managers; or
- a Grove render collector acting as the sole PCS writer.

This DEP does not select or implement either mechanism. The initial LPX integration must merely preserve the prerequisites identified by #14420: stable contribution identities, explicit references, collision-free keys, generation-aware results, singular deletion authority, and no dependency on undocumented or LPX-specific Grove naming rules.

### Scaling Groups

Scaling Groups are explored separately in #14469 and are outside the initial LPX integration.

A Scaling Group introduces an outer replica dimension without changing the meaning of any member component. Its replica count composes multiplicatively with each member's component-local replica count:

```text
effective component instances
    = scalingGroup.replicas × component.replicas
```

Without an enclosing Scaling Group, the outer multiplier is implicitly one. For example:

```yaml
components:
- name: draft
  type: lpx
  replicas: 2
- name: target
  type: lpx
  replicas: 1

experimental:
  scalingGroups:
  - name: specdec
    replicas: 10
    components:
    - draft
    - target
```

This describes twenty draft instances and ten target instances. The outer Grove PCSG replica count is ten, derived exclusively from `scalingGroup.replicas`. The component-local multiplicities are represented inside each group replica, through deterministic unfolding or a future nested Grove graph representation. Role-level Pod cardinalities remain a separate component-type concern and may, as for LPX Agents, be derived from an immutable build.

Membership in a Scaling Group must never make an otherwise valid `component.replicas` value invalid, or make an otherwise invalid value valid. An LPX component type may impose an unconditional replica restriction, but it cannot make that restriction depend on group membership.

Once plural LGDs are supported, a Scaling Group may additionally select one shared LGD materialization boundary for its LPX members; ungrouped LPX components receive separate LGDs. This follows from the requested shared scaling and scheduling scope and does not make the group semantic.

The boundary between both concepts is intentional: LPX component and wiring logic supplies component-type and SpecDecode semantics, while a Scaling Group provides a materialization boundary, outer scaling dimension, and optional gang coupling for otherwise independently meaningful components. It must not provide LPX compiler semantics or reconstruct one LPX engine from fragments that cannot exist independently.

## Alternate solutions

### Add LPX conditionals to the existing Grove renderer

This can produce the required objects, but turns LPX into a cross-cutting DGD mode and mixes two substantially different lowering processes.

### Expose conductor and agents as sibling components

This makes compiler-generated LPX roles appear independently meaningful and requires another API object to reconstruct the engine. Role-aware components preserve the logical engine boundary.

### Always create one LGD per LPX component

This is not sufficient as a universal rule. It is the future default for ungrouped LPX components, but an explicit Scaling Group may require several LPX components to share one LGD, one outer replica dimension, and one Grove scheduling scope.

The initial implementation temporarily chooses the opposite fallback—one LGD for all LPX components—because claim partitioning and plural LGDs are deferred. This includes multiple independent complete engines as well as a shared uniform SpecDecode pair. Neither fallback is the permanent model. The materialization-unit partition determines LGD cardinality.

### Route every LPX component through a DCD

A DCD represents one component lifecycle. An LGD may claim several components within one materialization boundary, whether they form a coupled SpecDecode workload or remain independent engines, so a single DCD is not its natural ownership boundary. Grove workload programs may also already materialize selected graph subsets without a DCD per component.

### Define a complete standalone LGD API immediately

This remains a possible follow-up. Doing it initially would stabilize the copied DGD surface before its actual dependency boundary is understood.

### Produce one shared PCS immediately

Deferred, not rejected. #14420 keeps both SSA and collector-based assembly available when an explicit cross-boundary Grove constraint requires it.

## Requirements

### Initial integration requirements

1. DGD accepts `type: lpx` as an inference component type.
2. The selected Grove workload program assigns every component to exactly one lowerer; LPX requires Grove.
3. The ordinary Grove lowerer ignores components claimed by LPX; the DCD workload program rejects LPX.
4. Deployments without LPX components retain their current behavior.
5. The `roles` mechanism is shared across component types, while each component type owns its semantic role vocabulary and interpretation. LPX accepts `agent` and `conductor`; the build determines whether the conductor materializes as an LPU-only Pod or a GPU-side cyborg.
6. Before Scaling Groups exist, a DGD has at most one LGD, and that LGD claims all LPX components in the DGD.
7. Initial multi-component LPX claims may contain multiple independent complete engines or one shared uniform SpecDecode draft/target pair. The pair retains separate compiler artifacts and cannot be mixed with additional independent LPX engines.
8. The LGD uses an exact DGD controller `OwnerReference`, including UID, as its source identity.
9. The singleton LGD may use the DGD name initially, but source validation and lookup use the exact controller owner identity rather than treating name equality as ownership.
10. `inputRevision` covers the effective inputs of all LPX components in the initial singleton, including the selected restart token; unrelated non-LPX changes do not create its revision.
11. The DGD controller selects the LGD identity but does not assign or infer its PCS name.
12. The LPX controller selects, owns, and privately reconciles the LPX PCS identity. No PCS name or reference is required by or consumed by the DGD controller.
13. Every LGD-owned child name and reconciliation key is rooted in the LGD or an explicit LGD-local materialization key, never in the source DGD name.
14. DGD and component labels may be propagated through LGD PodTemplates for discovery and attribution, but the LPX controller must not use them as lookup, ownership, fencing, or deletion authority.
15. Runtime configuration and other revision-sensitive resources consumed by Pods are immutable per-LGD-revision snapshots. A successor revision must not update resources still consumed by the retiring workload.
16. Recovery and eviction validate the exact LGD-owned Kubernetes owner chain and revision before mutating workload children.
17. The LPX controller owns LPX compilation, resources, retries, recovery, and status.
18. DGD projects LGD results into normal component and aggregate status.
19. The LPX lowerer may use Grove's published, versioned identity and addressing contract, as existing multi-node lowering does, but must not duplicate undocumented rules or introduce LPX-specific naming conventions.
20. The initial integration uses exclusive PCS ownership.
21. Scaling Groups, plural LGDs, component- or group-based claim partitioning, and two-phase claim transfer are not initial requirements; they are deferred to #14469 and its follow-up implementation.
22. The design preserves the future joint-PCS options described by #14420.

### Scaling Group follow-up invariants

These constraints apply when Scaling Groups and plural LGD reconciliation are designed. They do not expand the scope of the initial LPX PR.

1. Future plural reconciliation creates one LGD per ungrouped LPX component and one LGD per Scaling Group claimed by LPX.
2. A Scaling Group establishes a shared materialization boundary, outer replica dimension, and optional gang constraint. It does not define LPX or SpecDecode semantics.
3. Every LPX component belongs to exactly one desired materialization-unit claim and at most one active LGD.
4. LGD identity is derived from the exact source DGD identity and a stable component- or Scaling-Group-based materialization-unit key, not from a compiled Grove graph or PCS name.
5. A materialization-unit repartition uses a fenced handoff; a successor LGD cannot materialize a component until its predecessor has retired that claim.
6. Each LGD's `inputRevision` covers only the effective inputs of its claimed materialization unit.
7. `component.replicas` and `scalingGroup.replicas` are independent, multiplicative dimensions; group membership must not change component replica semantics or validation.
8. For grouped components, the outer PCS or PCSG replica count comes from the Scaling Group dimension. Member component multiplicities are represented within each group replica through unfolding or hierarchy.

This is a conceptual clarification only. Scaling Groups remain outside the initial LPX integration, and this DEP does not select their API or implementation.
