# [PR #15289] fix(frontend): stop the media-loader NIXL agent from spinning a core

source: https://github.com/ai-dynamo/dynamo/pull/15289
state: open | updated: 2026-09-27T05:39:36Z

## 正文

## Overview:

An idle frontend with frontend decoding uses up to 2 full CPU cores for each multimodal worker set. The cause is the NIXL agent that the media loader creates: its UCX progress thread polls with a zero timeout, so it never sleeps. This PR gives that agent a 1 ms progress-thread delay. Idle CPU drops from 200% to 1.9%, and same-host read latency does not change. `DYN_MM_NIXL_PROGRESS_DELAY_US=0` restores the old behavior without a rebuild.

**Repro**

```bash
python -m dynamo.frontend --http-port 8000 &
python -m dynamo.vllm --model Qwen/Qwen3-VL-2B-Instruct --enable-multimodal --frontend-decoding &
# After the model shows in /v1/models, send no requests and watch the frontend threads:
top -H -p "$(pgrep -f '[d]ynamo.frontend')"
```

**Before / after** (per-thread CPU over 10 s, no requests in flight, NIXL 1.3.2, UCX 1.22.0)

```text
main:         frontend 200.3%   tokio-rt-worker 100.0%   tokio-rt-worker 100.0%
this branch:  frontend   1.8%   tokio-rt-worker   0.8%   tokio-rt-worker   0.8%
```

The busy threads are UCX progress threads. They keep the name of the tokio worker that started them.

## Details:

**Why it spins.** The frontend creates one media-loader agent for the chat pipeline and one more for completions. NIXL's default progress-thread delay is 0, and the UCX backend uses that delay as its `poll()` timeout. A zero timeout turns the thread into a busy loop, one core per agent.

**The fix.** `get_nixl_agent()` in `lib/llm/src/preprocessor/media/rdma.rs` now creates the agent with a 1 ms delay. To pass a configuration, `lib/memory` adds `NixlAgent::new_with_config`. `NixlAgent::new` does not change, so KVBM and every other caller behave as before. The delay is 1 ms and not larger because some UCX events do not wake `poll()` and wait for the timeout. In a write-plus-notification test, a 10 ms delay gave stalls of 10 to 18 ms, and 1 ms kept the maximum at 1.5 ms.

**The trade-off.** When the frontend and the reader cannot share memory or use RDMA (for example, a frontend pod with no RDMA device), UCX falls back to TCP. The frontend agent must then progress each read, and each wakeup adds time: about 0.7 ms per 3 MiB image and 3 ms per 12 MiB image. `DYN_MM_NIXL_PROGRESS_DELAY_US` lets an operator trade the core back for that latency. It accepts 0 to 1,000,000 µs. Any other value logs one warning and uses the default, because NIXL 1.4.1 and earlier wrap large values into wrong timeouts. The media README and the fern "Parallel Media Decoding" page document the variable and the trade-off.

**Compatibility.** The runtime wheel loads NIXL at run time. The configured-agent entry point exists in every NIXL release since 0.6.1, and stub mode returns the same error as before.

**Not in this PR.** KVBM agents and the Python NIXL agents still use a zero delay. KVBM needs its own latency measurement, and the Python API needs a NIXL change.

### Performance

Same host, UCX shared memory, 3 interleaved rounds per build, 1000 timed reads per round, each read checked byte for byte. Medians over the rounds:

| Build | Idle CPU | 3 MiB p50 / p99 | 12 MiB p50 / p99 |
|---|---|---|---|
| main | 200.3% | 0.323 / 0.393 ms | 1.96 / 2.91 ms |
| this branch | 1.9% | 0.310 / 0.397 ms | 1.89 / 3.73 ms |

The 12 MiB p99 varied between rounds by about as much as the gap between builds. Not measured: two-pod transport choice, one-sided RDMA reads, and cross-node connection setup.
