# [Issue #13891] DEP: Pluggable Router Flow Control and Policy Scheduling

## 正文

### Area

router

### Summary

This DEP defines the router ordering **Classify → Order → Place** and the user-facing Pluggable Flow Control interface. For each request, an asynchronous `classify()` hook in Classify can (1) defer the request by remaining pending and (2) provide or override per-request inputs for the router-owned scheduler, subject to router validation, including policy class, due time, and scheduling cost. Every valid, still-live request released by `classify()` then enters Order, the router-owned Policy Class / DRR / Queue stage that provides the common priority, fairness, SLA, and overload protection needed with or without a custom algorithm. The initial implementation preserves the current Place worker-selection interface and algorithms; moving that existing entry point into the same trait for direct state sharing remains a possible follow-up.

### Motivation

Some routing algorithms need to delay an otherwise runnable request according to algorithm-specific state: task width, a pause/resume predicate, tenant state, or another deployment policy. The same decision may need to change how the router-owned scheduler treats that specific request by supplying its policy class, due time, or scheduling cost. The router therefore needs the user-facing Classify stage before Order.

The earlier draft exposed deferral through a policy-facing `Bypass / Ready / Defer` state machine, together with wake identifiers, release actions, and reconciliation callbacks. That requires a custom policy to translate an ordinary asynchronous wait into a separate router protocol and preserve its decision state across callbacks. The proposed interface instead lets plugin code wait inside an asynchronous `classify()` call and return when the request is ready, without externalizing its continuation state to the router.

The ordering between the two stages is part of the design. Classify must run first because its decision may both delay the request and change the inputs used by Order. Order must run afterward because Classify answers an algorithm-specific question—**may this request be released, and with what scheduling metadata?**—while Order answers the deployment-wide question—**which released request should receive the next available capacity?**

Together, Classify and Order cover priority, fairness, SLA, and overload protection without requiring a custom algorithm to implement the full router scheduler. For example, a plugin may correctly release one request from each task, but a deployment can have more tasks than workers. The released set can still overload the deployment and still needs fair ordering and due-time rejection. Conversely, when no custom plugin behavior is configured, `classify()` returns immediately and Order remains the router's shared scheduler and overload boundary.

Place is adjacent but not required to implement this flow-control boundary. The current worker-selection interface and algorithms can be preserved after Order. A later change may move that existing selection entry point into the same trait so Classify and Place can read the same private state without serializing it through a second interface.

### Proposal

#### Scope

This DEP defines:

- the ordering **Classify → Order → Place**;
- the user-facing Pluggable Flow Control interface used by Classify;
- its two per-request controls: defer release and provide or override scheduling inputs subject to router validation;
- the handoff from Classify into Order; and
- how Classify and Order compose to provide priority, fairness, SLA, and overload protection.

The current Place worker-selection interface, algorithms, and subsequent dispatch are downstream context, not initial implementation requirements. This DEP records a possible future consolidation in which the existing worker-selection entry point moves into the same trait as `classify()` and `on_event()` to enable direct state sharing between Classify and Place.

It does not define frontend admission, backend or engine-local rejection, engine preemption, KV retention across tool gaps, cross-deployment retry, durable plugin state across router restarts, runtime loading of arbitrary Rust binaries, or a standard session/task identity. ThunderAgent, llm-d sticky routing, and TAPER are validation examples; this DEP does not standardize those algorithms.

#### Router Flow

```text
Router receives request
  └─ register original ingress time, authoritative deadline,
     cancellation, and router-wide accounting
       │
       ▼
Preprocess [outside this DEP]
       │
       ▼
Classify [user classifier plugin]
  └─ async classify (request)
       ├─ scheduling inputs
       │    └─ may set or override policy class, due time,
       │       and scheduling cost
       ├─ release timing
       │    ├─ return immediately
       │    └─ remain pending until a plugin condition changes
       │
       ▼
Order [router-owned Policy Class / DRR / Queue]
  ├─ queue admission
  │    ├─ due time already passed → reject
  │    ├─ selected class queue is full → reject
  │    └─ enqueue in that class ordered by due time
  └─ downstream capacity available
       ├─ select a policy class with cross-class DRR
       ├─ select that class's earliest-due request
       ├─ due time now passed → reject and select again
       └─ release request to Place
       │
       │ [pull only when slot(s) are available]
       ▼
Place [outside this DEP]
  └─ filter / score / pick [non-blocking]
       │
       ▼
Reserve [where routers sync conceptually] [outside this DEP]
       │
       ▼
Existing router dispatch path [outside this DEP]
```

The router does not bypass Order when downstream capacity is immediately available and no requests are already waiting. Every valid, still-live request returned by `classify()` enters Order. Enqueue and selection may happen in the same scheduler turn, but the request still passes through the common checks and accounting.

#### User-Facing Pluggable Flow Control Interface

The user-facing interface gives `classify()` two independent per-request controls:

1. **Release control:** return immediately or remain pending to defer the request until custom logic permits it to continue.
2. **Scheduling-input control:** return effective policy class, due time, and scheduling cost values that alter how Order handles that request after router validation.

The second control changes the inputs to Order for one request; it does not replace Order or allow the plugin to enqueue, order, or dispatch work directly.

The proposal introduces one logical flow-control surface. The table distinguishes the initial Classify contract from the possible Place consolidation:

The user-pluggable surface consists of the Classify interfaces introduced by this DEP and the existing Filter, Score, and Pick interfaces used by Place.

##### `RequestClassifier::classify()`

```rust
async fn classify(
    &mut self,
    request: mut Request,
) -> Result<Request, DynamoError>;
```

`classify()` receives one router request and returns the same logical request. The plugin may modify the request metadata consumed by Order, including its policy class, due time, and scheduling cost, but does not replace the request identity or payload.

Release timing is independent of this input/output contract. The asynchronous call may return immediately or remain pending until a plugin condition changes; in either case, its output remains the same request. The default implementation returns the request immediately without modifying it.

##### `RequestClassifier::on_event()`

```rust
async fn on_event(&mut self, event: QueueAdmissionEvent<'_>);
```

`on_event()` uses the lifecycle-event notification pattern from [PR #13019](https://github.com/ai-dynamo/dynamo/pull/13019), adapted to the asynchronous `classify()` model. It receives one router lifecycle event and may update plugin state or notify pending `classify()` calls. This DEP uses the following event vocabulary:

- `Sent { request_id, worker }`: the request was sent to the specified worker and DP rank.
- `Received { request_id, worker }`: the request was received by the specified worker and DP rank. This notification is optional.
- `Responding { request_id, worker }`: the first response was received from the specified worker and DP rank, transitioning the request from sent or received to responding.
- `Completed { request_id, worker, context_tokens }`: the request completed on the specified worker and DP rank; `context_tokens`, when available, contains the final input-plus-output context size.
- `Aborted { request_id, optional<worker>, optional<DynamoError> }`: the request terminated without completing normally; the worker and underlying `DynamoError` are included when known.

`on_event()` may update plugin state and notify pending `classify()` calls. It does not release, enqueue, order, select, or dispatch a request directly. The default implementation ignores the event.

##### Filter: `WorkerFilter::keep()`

```rust
fn required_worker_inputs(&self) -> WorkerInputs;

fn keep(
    &mut self,
    context: &WorkerSelectionContext<'_>,
    candidate: &WorkerCandidate,
) -> Result<bool, WorkerSelectionPolicyError>;
```

Filter receives the request-level selection context and one router-eligible worker/DP-rank candidate. It returns `true` to retain that candidate or `false` to remove it. Filters run in declaration order for each candidate. `required_worker_inputs()` defaults to `WorkerInputs::NONE`.

##### Score: `WorkerScorer::score()`

```rust
fn required_worker_inputs(&self) -> WorkerInputs;

fn score(
    &mut self,
    context: &WorkerSelectionContext<'_>,
    candidate: &WorkerCandidate,
) -> Result<f64, WorkerSelectionPolicyError>;
```

Score receives the request-level selection context and one retained candidate. It returns one finite, lower-is-better cost contribution for that candidate. Contributions from all configured scorers are added together. `required_worker_inputs()` defaults to `WorkerInputs::NONE`.

##### Pick: `WorkerPicker::pick()`

```rust
fn required_worker_inputs(&self) -> WorkerInputs;

fn pick(
    &mut self,
    context: &WorkerSelectionContext<'_>,
    input: WorkerInputView<'_>,
) -> Result<usize, WorkerSelectionPolicyError>;
```

Pick receives the request-level selection context and the host-owned table of scored candidates, together with any optional worker inputs it requested. It returns the row index of one candidate. Candidate order is unspecified, so the implementation must inspect candidate data instead of relying on a stable position. `required_worker_inputs()` defaults to `WorkerInputs::NONE`.

The Filter, Score, and Pick signatures repeat Dynamo's [current worker-selection policy interface](https://github.com/ai-dynamo/dynamo/blob/main/lib/kv-router/src/scheduling/selector/policy.rs); this DEP does not redefine them.

#### Open Questions: Request and Reservation Ownership

The proposal above leaves open whether the KV router should own the application request at all. One possible boundary is for the enclosing layer to retain ownership of the request while the KV router operates on that request, or on its scheduling inputs, only for Classify, Order, and Place. Place would assign the request to a worker and DP rank, but the enclosing layer would remain responsible for routing the original request to the engine.

```text
Request owner outside the KV router
  -> Preprocess
  -> Classify
  -> Order
  -> Place: choose worker and DP rank
  -> Reserve: selected capacity
Request owner routes the request to the engine
```

##### User-Facing Pluggable Flow Control Interface

The layer above the KV router owns the request; the KV router operates on borrowed request references.

###### Classify: `RequestClassifier::classify()`

```rust
async fn classify(
    &mut self,
    request: &mut Request,
) -> Result<(), DynamoError>;
```

May defer the request and modify its scheduling metadata.

###### Filter: `WorkerFilter::keep()`

`WorkerFilter::keep(context, candidate)` uses the existing worker-filter interface unchanged.

###### Score: `WorkerScorer::score()`

`WorkerScorer::score(context, candidate)` uses the existing worker-scoring interface unchanged.

###### Pick: `WorkerPicker::pick()`

`WorkerPicker::pick(context, input)` uses the existing worker-picker interface unchanged.

###### Reserve: `Reserver::reserve()`

```rust
pub struct WorkerWithDpRank {
    pub worker_id: WorkerId,
    pub dp_rank: DpRank,
}

fn reserve(
    &mut self,
    request: &mut Request,
    selected: WorkerWithDpRank,
) -> Result<(), DynamoError>;
```

Receives the selected request and worker/DP rank that would otherwise be passed to PushRouter. Request lifecycle updates are handled by `Reserver`, replacing `RequestClassifier::on_event()`.

###### Capacity: `Reserver::read_capacity()`

```rust
pub struct RankCapacity {
    pub available_request_slots: usize,
    pub available_prefill_tokens: usize,
    pub available_kv_blocks: usize,
}

fn read_capacity(
    &mut self,
) -> Result<HashMap<WorkerWithDpRank, RankCapacity>, DynamoError>;
```

This is an explicit read, rather than a watcher, of the capacity currently reported by the layer outside KV-router. The returned map contains the current worker IDs, their DP ranks, and each rank's available request, prefill-token, and KV-block capacity. KV-router calls `reserve()` and `read_capacity()` sequentially; it does not call the two methods concurrently.

#### Relationship to the Original Admission-Control DEP

[DEP issue #9755](https://github.com/ai-dynamo/dynamo/issues/9755) originally filed the broader request admission and rejection design, including the router-owned policy-class, queue-admission, due-time, and DRR behavior. This DEP does not replace that router policy. It clarifies the router's internal composition for implementing it.

##### Cumulative Admission Metrics

KV-router exposes three cumulative counters: requests received by KV-router, requests rejected because their due time has already passed, and requests rejected because they are predicted to miss their due time. Each rejected request is counted under one rejection reason.

An upstream observer reads the counters at `t1` and `t2` and computes each period value as the cumulative-counter delta. With `Δreceived` as the denominator, each reason-specific rejection ratio is `Δrejected_reason / Δreceived`, and the total rejection ratio is `(Δrejected_due_time_passed + Δrejected_predicted_miss) / Δreceived`. The acceptance ratio is `1 - total rejection ratio`: for 10 received requests and 1 rejected request, the rejection ratio is `0.1` and the acceptance ratio is `0.9`.

### Alternate Solutions

**Keep the explicit `Bypass / Ready / Defer` protocol from issue #11477.** This makes deferral visible as a host-managed protocol, but adds identifiers, actions, reconciliation, stored execution state, duplicate-action handling, and separate ready/deferred transitions. A pending asynchronous invocation expresses the same wait while keeping policy execution state inside the policy.

**Keep metadata resolution and request deferral as separate plugins.** Both decisions occur in Classify and often depend on the same private state. A single flow-control hook gives them one atomic handoff and prevents the class, due time, or cost from changing after entry into Order.

**Attach one admission strategy to each policy class.** The effective class may itself be the result of flow control, so selecting the extension by class before calling it is circular. One plugin may still implement class-specific behavior internally after examining trusted request inputs.

**Preserve a direct path when the queue is empty.** This saves one enqueue/select cycle, but creates different expiry, accounting, fairness, and capacity paths depending on incidental backlog. The scheduler may optimize an enqueue followed by immediate selection without exposing a semantic bypass.

**Let each custom policy own ordering, queueing, and overload protection.** This duplicates request storage, cancellation, per-class queue-size enforcement, DRR, SLA enforcement, and metrics for every new algorithm. It also allows an agentic policy to release work without a whole-deployment capacity throttle.

**Consolidate Place into the Classify plugin in the initial implementation.** Sharing one plugin instance could make state flow directly from Classify into Place, but it would unnecessarily redefine the existing worker-selection surface. The initial implementation preserves the current Filter, Score, and Pick interfaces; consolidation can remain a separate follow-up.

**Await `classify()` inside the scheduler actor.** A blocked call would prevent other requests and the events needed to release the call from progressing. Supervised, independently pollable calls preserve scheduler and event-loop liveness.

### Requirements

- Router request processing **MUST** follow **Classify → Order → Place** before dispatch.
- `classify(request)` **MUST** receive one request and return the same logical request. It **MAY** modify the request's policy class, due time, and scheduling cost, but **MUST NOT** replace its identity or payload.
- The default `classify()` implementation **MUST** return the request immediately without modifying it.
- A `classify()` call **MAY** remain pending to defer release. One pending call **MUST NOT** block other requests, Order, or `on_event()` delivery.
- The router **MUST** validate the scheduling metadata carried by a returned request before it enters Order.
- Every valid, still-live request returned by `classify()` **MUST** enter Order. Classify **MUST NOT** enqueue, order, select, reserve, or dispatch the request directly.
- Order **MUST** remain router-owned and **MUST** apply the shared Policy Class / DRR / Queue mechanisms for priority, fairness, SLA, and overload protection using the validated per-request scheduling inputs.
- `on_event()` **MUST** be notification-only and **MUST** provide a default no-op implementation. It **MAY** update plugin state and notify pending `classify()` calls, but **MUST NOT** release or dispatch a request directly.
- The `on_event()` interface **MUST** support `Sent`, optional `Received`, `Responding`, `Completed`, and `Aborted` lifecycle notifications with the payloads defined in the Proposal.
- Place **MUST** preserve the existing `WorkerFilter`, `WorkerScorer`, and `WorkerPicker` interfaces, including `keep()`, `score()`, and `pick()`.
- KV-router **MUST** publish cumulative counters for requests received by KV-router, requests rejected because their due time has already passed, and requests rejected because they are predicted to miss their due time.
- Each rejected request **MUST** increment exactly one rejection-reason counter.
- The cumulative counters **MUST** support upstream interval-delta calculations and reason-specific and total rejection ratios using the received-request delta as the denominator.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are interpreted as described by RFC 2119.

### ishandhanani · 2026-09-01

Replacement implementation: #14123.

Deviations from this draft DEP:

1. `on_event()` is synchronous because `Drop` is the exactly-once terminal backstop and cannot await; the classifier runtime enters a captured Tokio handle before invoking it.
2. The undefined predicted-to-miss-due-time counter is not implemented. The cumulative received and due-time-passed counters are implemented.
3. The lifecycle event type is named `ClassifyEvent`, not `QueueAdmissionEvent`.
4. Router-wide token accounting for requests pending in Classify is deferred.

The PR is intentionally draft and its description records the current minimality, performance, endpoint-mapping, and test gaps. This does not amend or advance the DEP from `dep:draft`.
