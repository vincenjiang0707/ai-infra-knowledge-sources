## Summary

Dropping the final model binding used to leave its served-indexer service registered. Rebuilding a router with a different `use_kv_events` setting then failed until the process restarted.

Retire unused services before replacing them, reject conflicting modes while live bindings remain, and evict services during runtime shutdown. Topology checks ignore only the retired instance's stale discovery records. Preserve current main's fully qualified request-plane cleanup.

Keep acquired endpoints owned during cancelled startup, install cleanup before awaiting discovery acquisition, and retain a shared retirement-completion barrier across caller cancellation. Shutdown waits for discovery-lease release as well as request-plane cleanup before replacement proceeds.

Closes #13374.

## User intent

Make the process-global served-indexer registry survive a router's lifetime
instead of outliving it. Today the first `KvRouter` to request a served indexer
for a given `(connection_id, namespace, component)` permanently fixes that key's
`ServedIndexerMode`. When that router retires — which happens routinely, because
`materialization_fingerprint` retires and reconstructs a router whenever
`use_kv_events` changes — the registry entry survives with zero bindings, and the
next router for the same key is rejected with
`cannot mix event-driven and approximate served indexers under {ns}.{component}`.
Only a full process restart clears it.

The work item asks for the fix plus three regression tests:

1. dropping the final `ServedIndexerHandle` leaves no bindings and allows a
   served indexer of the *other* mode to start for the same key;
2. a live binding still rejects a conflicting mode (the guard must not be
   weakened into uselessness);
3. the registry entry is evicted on runtime teardown, so a fresh runtime in the
   same process starts clean.

## Non-goals

- Cross-process coordination. The registry is process-global and keyed on
  `drt().connection_id()`; making two OS processes agree on a mode is a
  different problem (see PR #9302 under Discovery, which attempted it and was
  closed unmerged). Do not revive it here.
- Changing what `ServedIndexerMode` *means*, changing
  `from_use_kv_events`, or changing when `KvRouter` decides to serve an indexer
  (`kv_router_config.serve_indexer`).
- Changing the discovery-watcher retire/reconstruct policy in
  `lib/llm/src/discovery/watcher.rs`. That path is correct; it is the registry
  that fails to keep up with it.
- Any Python, Kubernetes, container, or engine-integration change. This is a
  Rust-only change inside `lib/llm`.
- Reworking `verify_service_topology`'s intent. It must keep rejecting a genuine
  conflict; it should simply stop seeing endpoints belonging to a service this
  process has already retired.

`lib/llm/src/discovery/watcher.rs:1269-1289` — `materialization_fingerprint`

### Why eviction alone is not enough (the finding that shapes the fix)

Because `start_query_endpoint` / `start_record_endpoint` are fire-and-forget,
the retired service's endpoints stay registered in discovery for the life of the
`DistributedRuntime`. Trace the three mode transitions assuming a fix that only
removes the map entry:

| Transition | Result after map-eviction-only |
|---|---|
| EventDriven → EventDriven | works (`verify_service_topology` for EventDriven only rejects a stale *record* endpoint) |
| **EventDriven → Approximate** | **still fails** — `verify_service_topology` rejects because the stale *query* endpoint exists |
| **Approximate → EventDriven** | **still fails** — the stale *record* endpoint exists |

So the headline bug survives a map-eviction-only fix on both of the transitions
that matter. **Retirement must actually stop the endpoints and let discovery
unregister them.** That capability exists but is unused:
`lib/runtime/src/component/endpoint.rs` L57-78 defines `StartedEndpoint` with
`pub async fn shutdown(self) -> Result<()>` (cancel token, await the task); the
plain `start()` at L128 throws that handle away. The endpoint's spawned cleanup
task (L273-302) unregisters from discovery and the request plane when its token
is cancelled.

### Runtime teardown ordering — `lib/runtime/src/runtime.rs`

`shutdown()` is three-phase: phase 1 cancels `endpoint_shutdown_token`, phase 2
drains the graceful-shutdown tracker, phase 3 cancels the main token.
`child_token()` (L308) is a child of the phase-1 token; `primary_token()` (L303)
is the phase-3 token. A teardown-eviction watcher must key on `child_token()`:
it fires immediately at phase 1, whereas phase 3 is gated behind a drain plus a
timeout and would make the third regression test slow or hang.

## Symptom, hypotheses, and the distinguishing observation

**Reproducible symptom.** In one process, against one `DistributedRuntime`:
construct a served indexer for `(ns, component)` with
`ServedIndexerMode::EventDriven`; drop the returned `ServedIndexerHandle`;
construct one for the same `(ns, component)` with
`ServedIndexerMode::Approximate`. Expected: success. Actual: `Err` — either
`cannot mix event-driven and approximate served indexers under {ns}.{component}`
(the cached entry is returned by `get_or_start_service`) or, if the entry were
evicted, `cannot start approximate served indexer on {ns}.{component}` from
`verify_service_topology` (the stale query endpoint is still registered).

| # | Hypothesis | Smallest distinguishing observation | Prior |
|---|---|---|---|
| H1 | `Drop` clears the binding but never the registry entry, so the stale `Arc` with its frozen `mode` is returned | after dropping the last handle, `SERVED_INDEXER_SERVICES` still contains the key and its `bindings` map is empty | confirmed by reading `Drop` at remote.rs:264 |
| H2 | Even with the entry evicted, the retired service's endpoints stay registered, so `verify_service_topology` rejects the new mode | evict the key by hand in a test, then start the other mode: the error text changes from `cannot mix …` to `cannot start approximate served indexer on …` | high — follows directly from `start()` discarding the endpoint handle |
| H3 | The entry is never evicted at runtime teardown, so a second runtime in the same process inherits stale state | after `Runtime::shutdown()`, the key from the dead runtime is still present in the map | high — no code path removes keys at all |
| H4 | The watcher does not actually retire the router on a `use_kv_events` change, so the scenario is unreachable | `materialization_fingerprint` includes the canonicalized router config | **rejected** — read at watcher.rs:1269-1289; it does include it |

H1 and H2 are both true and both must be fixed; the error-text flip is the
observation that separates them and the reason a map-eviction-only patch would
look plausible and still fail.

## Chosen approach

**Retire lazily on the async creation path, and evict on runtime teardown.**
Two coordinated pieces, neither of which performs async work from `Drop`.

**1. Retain the started endpoints.** Change `start_query_endpoint` /
`start_record_endpoint` to `async` functions that `await`
`start_with_registration()` and return the `StartedEndpoint`, and store those on
`ServedIndexerService`. This is required for the fix (H2) and has two useful
side effects: endpoint registration becomes deterministic rather than a spawned
race, and a registration failure surfaces as an error from
`ensure_served_indexer_service` instead of a swallowed `tracing::error!`.

*Behaviour change to declare in `change.md`:* `ServedIndexerService::start` now
returns only after the endpoints are registered, and a registration failure now
fails router construction. Both are improvements, but they are changes; the
implementer should call them out rather than let a reviewer discover them. The
Python helper `wait_for_served_indexer` in `tests/router/common.py` polls for
endpoint availability and remains valid — it simply converges sooner.

**2. Retire under the existing `SERVICE_CREATION_LOCK`.** In
`get_or_start_service`, restrict the lock-free fast path to a cached entry whose
`mode` **matches** the request. On a mismatch, fall through to the slow path;
under the lock, re-read the entry and, if it has zero bindings, retire it —
`shutdown().await` each `StartedEndpoint`, remove the key, then start a fresh
service in the requested mode. If it still has bindings, keep today's error.

Retirement therefore happens only on an async path already serialized by the
creation lock, which is what makes the whole design safe:

- No `.await` is ever needed inside `Drop`, so the `tokio::sync::Mutex` is never
  reached from a sync context, and there is no `tokio::spawn` from `Drop` (which
  would panic when a handle is dropped during runtime teardown, with no reactor
  running).
- Endpoint shutdown is *awaited* before the replacement service runs
  `verify_service_topology`, so there is no window in which discovery still
  advertises the retired endpoints. A spawn-and-hope design would reintroduce
  exactly that flake.
- `Drop` stays as it is: remove the binding, nothing else. Cheap, infallible,
  reactor-independent.

**3. Close the resurrection window.** A reader can clone the `Arc` on the fast
path and then insert a binding while another task is retiring that service.
Guard it with a `retired: AtomicBool` on the service: retirement sets it while
holding the `bindings` write lock and observing an empty map; binding insertion
checks it under the same write lock and, if set, drops the guard and retries
`get_or_start_service`. Bound the retry (a single retry is sufficient, since the
retired flag is terminal for that `Arc`) and return a clear error if it somehow
recurs, rather than looping.

**4. Evict on runtime teardown.** At service creation, spawn a task that awaits
`component.drt().child_token().cancelled()`, then removes the key and shuts the
endpoints down. `child_token()` is a child of the phase-1
`endpoint_shutdown_token`, so it fires at the start of `Runtime::shutdown()`;
`primary_token()` (phase 3) is gated behind the graceful drain and a timeout and
would make the third regression test slow or hanging. This spawn happens on the
async creation path, where a reactor is guaranteed.

**Locking hazards to respect while implementing** (each is a real way to get
this wrong):

- Never drop an `Arc<ServedIndexerService>` while holding a `DashMap` shard
  guard. Bind the result of `remove` to a local, let the guard go out of scope,
  then drop the local. Holding a shard guard while another shard operation runs
  in a `Drop` is a self-deadlock.
- `bindings` is a `parking_lot::RwLock`; its guard is not `Send` and must never
  be held across an `.await`. Today's code scopes the write guard inside a
  block — keep that discipline in every new path, especially the
  retired-flag check.
- Do not hold `SERVICE_CREATION_LOCK` across endpoint shutdown *and* a call that
  could re-enter `get_or_start_service`. The lock is not reentrant.

**Signature churn: none expected, and that is deliberate.** The service key is
derivable from the `Component` that `ensure_served_indexer_service` already
receives, and the endpoints live on the service, so no new parameter — required
or optional — needs threading anywhere. `ServedIndexerHandle` gains private
fields only. `ensure_served_indexer_service` keeps its public signature, which
matters because it is a `pub` export of `dynamo-llm` (`kv_router.rs:62`). If the
implementer finds a case for changing it anyway, it must be a **required**
parameter rather than an `Option` — a silently-defaulting lifetime scope is the
kind of thing that reintroduces this class of leak — and the justification must
be written into `change.md`. `cargo check --workspace` (recipe 02) is the proof
that every caller was found; combined with the grep showing the out-of-workspace
`lib/bindings/python` does not reference these symbols, coverage is complete.

## Rejected alternatives

- **Evict the entry from `Drop` via `DashMap::remove_if(|_, s| s.bindings.read().is_empty())`.**
  Rejected on two counts. First, it does not fix the bug: as the transition
  table above shows, both interesting mode changes still fail inside
  `verify_service_topology` because the retired endpoints remain registered.
  Second, it opens a resurrection race — a reader that cloned the `Arc` on the
  fast path just before the final `Drop` will insert a binding into a service
  that is no longer in the map, producing a second, invisible service whose
  endpoints nobody owns.
- **Mutate `mode` in place and reconfigure the empty service.** Attractive
  because it avoids eviction entirely, but it must still start or stop the
  record endpoint to change mode, and it cannot remove the endpoint that the old
  mode registered. `verify_service_topology` continues to reject. It also turns
  `mode` into shared mutable state read on the hot binding path for no
  compensating benefit.
- **Hold `Weak<ServedIndexerService>` in the map.** Does not address the
  reported bug at all: the value is still keyed to one immutable mode, and a
  weak reference gives no deterministic point at which endpoints are stopped —
  upgrade failure is observed only on the *next* lookup, which may be long after
  discovery has gone stale. It also makes the teardown test non-deterministic.
- **Eager eviction driven by `primary_token()` instead of `child_token()`.**
  Correct in principle but fires in phase 3 of `Runtime::shutdown()`, after the
  graceful-drain tracker and its timeout. The teardown regression test would
  either need a long timeout or would hang; and the endpoints would remain
  advertised throughout the drain.
- **PR #9302's cross-process `try_claim_singleton`.** A claim with no release
  path makes the retirement problem strictly worse and addresses cross-process

## The bug

`SERVED_INDEXER_SERVICES` (the process-global `DashMap` in
`lib/llm/src/kv_router/indexer/remote.rs`, keyed by
`ServiceKey = (connection_id, namespace, component)`) permanently retained a
component's first `ServedIndexerMode`. `ServedIndexerHandle::drop` removed only
the model binding from `bindings`; it never removed the registry entry. So after
every user of a component's served indexer went away, reconstructing a
`KvRouter` for that same component with a different `use_kv_events` failed with

```
cannot mix event-driven and approximate served indexers
```

even though nothing was still using the old service.

## What the fix does

Map eviction alone is **not** sufficient, and this was the load-bearing finding
of the investigation. `start_query_endpoint` and `start_record_endpoint` were
fire-and-forget `tokio::spawn`s that discarded the endpoint handle. A retired
service's endpoints therefore stayed registered in discovery, and
`verify_service_topology` still rejected *both* transitions — the registry entry
was gone but the wire state was not. Retirement has to actually stop the
endpoints and await their shutdown.

Five coordinated pieces, all in `remote.rs`:

1. **Retain started endpoints.** Both starters are now
   `async fn ... -> Result<StartedEndpoint>` that `await`
   `start_with_registration()` and return the handle, which the service stores in
   `endpoints: parking_lot::Mutex<Vec<StartedEndpoint>>`. A partial start (query
   endpoint up, record endpoint fails) shuts the query endpoint back down before
   propagating the error.

2. **Retire lazily under the existing `SERVICE_CREATION_LOCK`.** On a mode
   mismatch the entry is re-read under the lock; if `bindings` is empty the
   endpoints are shut down (awaited), the key is removed, and a fresh service
   starts. A mismatch with live bindings still returns today's error — that case
   is a genuine conflict, not a stale entry. `Drop` is unchanged: it removes the
   binding only, with no `.await` and no `tokio::spawn`.

3. **Never hand back a retired entry** (added this iteration —
   `get_or_start_service`, `remote.rs:416-434`). Retirement sets `retired`
   *before* it awaits endpoint shutdown, so for the whole of that window — up to
   two endpoint-shutdown round trips — the map advertises a service carrying the
   flag. Both lookups, the lock-free fast path and the double-check under the
   lock, now require `!existing.is_retired()`, so such an entry always falls
   through to the retire-and-replace path. See
   [Response to review, finding 1](#finding-1-blocking--retired-entry-handed-back-by-the-fast-path)
   for why one guard was not enough.

4. **Close the resurrection window.** `retired: AtomicBool` is set under the
   `bindings` write lock while the map is observed empty. Binding insertion
   checks the flag under that same lock and, if it lost the race, retries
   `get_or_start_service` **once**. The retry is bounded on purpose: a
   pathological race yields a clear error rather than an unbounded loop. This is
   expressed with a `BindOutcome` enum and a two-iteration loop in
   `ensure_served_indexer_service`. Because piece 3 guarantees the retry never
   lands on a service that is already retired, one retry is sufficient unless a
   *second* mode switch retires the replacement inside the same narrow window.

5. **Evict on runtime teardown.** A task awaits
   `component.drt().child_token().cancelled()` and removes the entry. It holds a
   `Weak<ServedIndexerService>`, so the watcher never keeps the service alive.
   `child_token()` (shutdown phase 1) is used deliberately, not `primary_token()`
   (phase 3) — the entry must be gone before late phases run. As of this
   iteration the task also calls `mark_retired()` *before* removing the key, so
   the same resurrection window piece 4 closes on the mode-switch path is closed
   here too.

### Locking hazards respected

- An `Arc<ServedIndexerService>` is never dropped while a `DashMap` shard guard
  is held. `remove_if`'s result is bound to a local, the guard falls out of
  scope, and only then is the local dropped.
- The `bindings` `parking_lot::RwLock` guard is `!Send` and never crosses an
  `.await`. `mark_retired()` holds it across an `AtomicBool` store only.
- `SERVICE_CREATION_LOCK` is not reentrant and is never re-acquired on a path
  that already holds it.

### `SERVICE_CREATION_LOCK` is a process-global, and this change lengthens its hold

Worth a reviewer's attention even though it is not new: `SERVICE_CREATION_LOCK`
is one `tokio::sync::Mutex<()>` for the whole process, not one per `ServiceKey`.
Everything from `remote.rs:430` to `remote.rs:458` runs under it, and after this
change that region can contain up to **five** unbounded discovery round trips:
two endpoint shutdowns in `stop_endpoints()`, one `verify_service_topology`
lookup, and two `start_with_registration()` calls. Before this change it held
only the verify plus two `tokio::spawn`s that returned immediately. A slow or
wedged discovery backend now stalls served-indexer creation for *every*
component in the process, not just the one being created.

I considered moving `ServedIndexerService::start` outside the guard and
concluded it must stay inside. The lock is the only thing making
verify-then-start atomic for a key: `verify_service_topology` reads discovery
rather than the map, so two callers requesting opposite modes for the same
component could both pass verification and both register endpoints if `start`
ran unguarded. Narrowing the blast radius properly means sharding the lock by
`ServiceKey` — a real improvement, but a larger change than this fix, and one
that would want its own contention measurement. Recorded as a follow-up rather
than done here.

## Findings

### 1. nit — `remote.rs:436-440`: the comment states an invariant this same commit broke

The comment justifies the `retire_if_unused()` call below it with two claims:
"retirement runs while holding this lock, so no retirement is in flight", and "its
bindings are empty by construction (the flag is only ever set over an empty map)".

(`remote.rs:299`, added in `29d86d0a3` in response to nit 5) sets the flag regardless of

registrations stay advertised in discovery, and a later opposite-mode caller fails
`verify_service_topology` with the issue's own "cannot mix event-driven and approximate

I record it as a nit rather than blocking for three reasons: it needs a cancellation
inside a narrow window; the endpoints' tokens are children of the runtime's phase-1
token, so the leak is bounded by runtime lifetime; and on `f6f99696d` the endpoints were
never stopped at all, so this is strictly an improvement rather than a new hazard. Worth
a sentence in the MR description under the same heading as behaviour change 3, since it
is the same "cancellation destroys working state" family.
