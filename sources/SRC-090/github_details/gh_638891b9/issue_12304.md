## Summary

Discovery endpoint watchers should not publish an empty instance list to local clients when the watcher is shutting down because the local runtime or HTTP frontend is cancelling.

## Motivation

During graceful frontend shutdown, in-flight request handlers may still need the last known endpoint instances while the HTTP server drains. If a local discovery watcher publishes an empty list as part of its own cancellation path, those in-flight requests can incorrectly treat a healthy router/backend as unavailable and fail with errors like "instance not found and no other instances available".

This is a generic shutdown/discovery invariant: local watcher teardown should not look like an authoritative remote deletion unless discovery actually observed the endpoint becoming empty.

## Expected behavior

* On local cancellation/shutdown of the endpoint watcher, preserve the last known snapshot or otherwise distinguish local watcher termination from an authoritative empty discovery update.
* Continue publishing real empty snapshots when discovery genuinely reports that all instances are gone.
* In-flight request drains should be able to complete using existing endpoint state until the graceful drain ends or the request itself is cancelled.
* Logs/metrics should make local watcher cancellation distinguishable from remote endpoint removal.

## Reproduction scenario

1. Start a synthetic frontend and one synthetic backend/router instance.
2. Begin a long-running dummy streaming request, for example with prompt text "synthetic long request" and no customer data.
3. Trigger graceful shutdown of the frontend while allowing HTTP drain to continue.
4. The local endpoint watcher should stop without publishing an authoritative empty instance list to the in-flight handler.
5. The in-flight request should not fail solely because the local watcher cancelled.

Please keep reproductions fully synthetic: fake endpoint names, fake request IDs, no real prompts, no customer identifiers, no internal URLs, and no credentials.
