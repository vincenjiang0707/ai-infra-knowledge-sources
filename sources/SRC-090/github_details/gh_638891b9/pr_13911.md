## 正文

## Summary

Adds the `engine_stream` error type to the component errors metric for typed engine failures and untyped error envelopes after a response stream opens. The shared ingress pump counts at most one per request, excluding cancellation, explicit worker shutdown, and response serialization failures.

- Preserves the public `EncodedResponseFrame` construction shape through an additive classified-encoder method.
- Explicit Python shutdown paths use `WorkerShutdown`, an `EngineShutdown` subclass, mapped to the existing migratable and inhibited `WorkerUnavailable` type. Engine crashes remain counted; generic generator closure remains cancellation.
- Serialization fallback frames still reach the client and increment `serialization`.
- Documents the metric population in Rust and the generated Python mirror.

## Validation

Added or extended pump accounting, response encoding, wire-identity, and vLLM shutdown-signal regression coverage. Rustfmt 1.96.1, Black, isort, Ruff, and standalone Flake8 passed for the repair. Tests, builds, and benchmarks are validated through remote CI only.

## User intent

Add a new `error_type` value, `engine_stream`, to the existing
`dynamo_component_errors_total` counter family so that a typed engine error
which arrives *after* the response stream has already opened is visible in
Prometheus. Today that class of failure is invisible: the counter distinguishes
only pre-`generate` transport failure (`response_stream`), `generate()` setup
failure (`generate`), response encoding failure (`serialization`), and
frame/marker delivery failure (`publish_response`, `publish_final`). A worker
whose engine dies halfway through a stream — an upstream 5xx from a sidecar, a
malformed frame the engine emitted, an EOF the engine reported as a typed error
— increments none of them.

The increment must fire **at most once per request**, on the first typed error
frame, and must be emitted from the one shared response pump so every unified
backend (vLLM, SGLang, and any other) inherits it without per-backend work.

Three exclusions are load-bearing and are the substance of the change, not
incidental: setup failures must keep counting as `generate` and must not
double-count as `engine_stream`; a stream that completes normally must not
increment; and a request terminated by user cancellation or by worker shutdown
must not increment. The new label value must add exactly one bounded series per
endpoint — no request ID, endpoint name, channel index, model path, or error
string may enter the label set.

Ship it with the docs row that describes the new value and an example
error-ratio / alert query, so an operator reading the metric knows what a
non-zero `engine_stream` rate means.

## Non-goals

- No change to how `generate`, `response_stream`, `serialization`,
  `publish_response`, or `publish_final` are classified today. In particular the
  `publish_final` narrowing that distinguishes a stopped context from a killed
  one stays exactly as it is.
- No new metric family, no histogram, no per-error-kind breakdown of
  `engine_stream` (a `BackendError` variant label would be a second decision
  with its own cardinality argument; this ticket asks for one value).
- No change to engine-side behavior: the pump still yields the error frame
  downstream and still ends the stream the way it does today. This is
  observation only.
- No fix for `publish_response` being inflated by client cancellation. That is a
  known, documented property of a different label value and a separate ticket.
- No Kubernetes, Helm, operator, or Grafana dashboard work. The Grafana JSON
  under `deploy/observability/` and `dev/observability/` enumerates error types
  in a couple of panels, but they are wildcard/`sum by (error_type)` shaped and
  pick the new value up without editing.
- No SGLang or TensorRT-LLM runtime exercise. The declared engine is vLLM, and
  the change is in the shared pump precisely so that one engine's proof is
  representative.

## Discovery

survey. Findings below are what I read, not what I intend to read.

### The counter, its owner, and its value enumeration

`dynamo_component_errors_total` is the work-handler error counter. It is
declared as `work_handler::ERRORS_TOTAL` in
`lib/runtime/src/metrics/prometheus_names.rs`, labeled by the single label
`work_handler::ERROR_TYPE_LABEL` (`"error_type"`), and registered in
`WorkHandlerMetrics::from_endpoint` in
`lib/runtime/src/pipeline/network/ingress/push_handler.rs` via
`create_intcountervec(work_handler::ERRORS_TOTAL, …, &[work_handler::ERROR_TYPE_LABEL], metrics_labels)`.

The permitted values live in one place, `pub mod error_types` inside
`work_handler` in `lib/runtime/src/metrics/prometheus_names.rs`: `deserialization`,
`invalid_message`, `response_stream`, `generate`, `serialization`,
`publish_response`, `publish_final`. Every emission site references one of these
constants; there are no string literals at the call sites. So the label set is
already closed, and adding one constant adds exactly one series per endpoint —
the cardinality requirement is satisfied structurally by using the same
mechanism, not by an audit.

That file has a generated Python mirror,
`lib/bindings/python/src/dynamo/prometheus_names.py`, whose header says
`AUTO-GENERATED from lib/runtime/src/metrics/prometheus_names.rs` and which
carries a `class error_types` with the same seven values. It is produced by
`cargo run -p dynamo-codegen --bin gen-python-prometheus-names`
(`lib/bindings/python/codegen/README.md`). I found **no pre-commit hook and no CI
job that enforces the sync** — a grep for the codegen binary name across
`.pre-commit-config.yaml`, CI YAML, and shell scripts returns nothing — and a
previously merged change exists whose whole subject is re-syncing that file after
it drifted. Regenerating it is therefore a required, easily-forgotten deliverable
of this change, not an optional nicety.

### Where `generate` is emitted (the setup path that must not change)

`handle_payload_shared` in `push_handler.rs` calls `segment.generate(request)`
and, on `Err`, increments `error_types::GENERATE`. This is strictly the setup
failure: `generate()` returned an error instead of a stream, so no frame ever
flowed. It is a different function from the pump, on a different side of the
`?`, so an increment placed inside the pump is structurally incapable of
double-counting with it — there is no request for which both run.

The unified backend's mirror of that boundary is in
`lib/backend-common/src/adapter.rs`: `EngineAdapter::generate` awaits
`self.engine.generate(request, gen_ctx)` and records `error_kind = "setup_failed"`
on the span before returning `Err`, which is what surfaces as `generate` at the
ingress. Everything after that point is inside the stream.

### The common response pump, and which one it is

There are two candidates and they are not equivalent.

The first is `EngineAdapter::generate`'s `async_stream::stream!` loop in
`lib/backend-common/src/adapter.rs`. Its error arm is unmistakably the ticket's
subject — it logs literally `"engine stream yielded typed error"`, records
`error_kind` from `dynamo_err.error_type()`, yields `Annotated::from_err(dynamo_err)`,
marks the finalizer completed, and `break`s. `RawEngineAdapter::generate` repeats
the same shape for the raw/media path.

The second is `Ingress::pump_response_stream` in
`lib/runtime/src/pipeline/network/ingress/push_handler.rs`. Its loop already
computes exactly the signal needed:

```rust
let is_error = encoded.is_error;
saw_error_response |= is_error;
```

and it already holds `self.metrics()` — the very `WorkHandlerMetrics` that owns
`error_counter`. Both `serialization` and `publish_response` are incremented from
inside this loop today.

I chose the second, and the deciding evidence is ownership, not taste:

- `lib/backend-common/` contains **zero** references to `error_counter`,
  `errors_total`, or `error_types::` — grep across the whole crate returns
  nothing. Its metrics surface is `EngineMetrics` in
  `lib/backend-common/src/metrics.rs`, a `MetricsHierarchy` handed to the engine
  via `LLMEngine::setup_metrics`; it is a different object from
  `WorkHandlerMetrics` and does not own this counter.
- The construction order in `lib/backend-common/src/worker.rs` makes the counter
  unavailable at adapter-construction time: `EngineAdapter::new(engine, mode)` is
  built first, wrapped in `Arc`, and only then passed to
  `Ingress::for_engine(...)`. `WorkHandlerMetrics` is attached later still, by the
  runtime, in `add_metrics(endpoint, labels)` at endpoint-start. Emitting from
  `backend-common` therefore means threading a metrics handle through
  `EngineAdapter::new`, `RawEngineAdapter::new`, `with_first_token_source`, and
  `JsonProbeAdapter` — and then doing it a second time for any future adapter.
- The pump in `push_handler.rs` is *below* every backend, Rust or Python. A
  Python worker's frames arrive through `PythonIngressPayloadAdapter` and land in
  the same loop. Emitting there covers vLLM, SGLang, push-mode Python handlers,
  and pure-Rust engines with one call site. Emitting in `EngineAdapter` covers
  only requests that happen to route through that adapter.

### Why `is_error` alone is not a sufficient predicate

`EncodedResponseFrame` (`lib/runtime/src/pipeline/network.rs`) is
`{ bytes, is_error, stop_stream }`. `is_error` is derived identically on both
encoder paths: `SerdeIngressPayloadAdapter::encode_response` computes
`response.err().is_some()`, and `encode_python_response` in
`lib/bindings/python/rust/python_payload.rs` uses `annotated.is_error()`, which
is `event == Some("error")` — set by both `Annotated::from_err` and
`Annotated::from_error`. So the flag is uniform Rust↔Python.

But cancellation and shutdown reach the wire as ordinary typed error frames:

- `lib/runtime/src/error.rs` defines both `ErrorType::Cancelled` and
  `BackendError::Cancelled`.
- `map_python_exception` in `lib/bindings/python/rust/engine.rs` maps
  `PyGeneratorExit` to `BackendError::EngineShutdown` ("engine shutting down")
  and a cancellation exception to `BackendError::Cancelled`.
- `lib/bindings/python/rust/push_egress.rs` closes a stream with
  `close_with_dynamo_error(map_python_exception(error))`, which becomes
  `PushFrame::error(Annotated::from_err(error))` — and its own test asserts
  "terminal frames must be flagged is_error". Its doc comment states outright
  that preserving the type matters because `BackendError::EngineShutdown` drives
  request migration.

Therefore a naive `if encoded.is_error { inc() }` would count exactly the two
categories the ticket forbids. This single fact drives the API-shape decision
below.

Gating on context state instead (`context.is_stopped()` / `is_killed()`) is also
insufficient on its own: an engine-reported cancellation — for example an
upstream premature EOF that the vLLM sidecar decode path maps to `Cancelled`,
which has a dedicated test today — arrives as a typed frame without the local
context having been stopped.

Prior art for the right predicate already exists in the tree:
`error::match_error_chain(err, &[ErrorType::Cancelled], &[])` walks the error
`source()` chain and is used for exactly this purpose in
`lib/llm/src/migration.rs` (whose `NON_MIGRATABLE` list is
`&[ErrorType::Cancelled, ErrorType::ResourceExhausted]`) and in
`lib/llm/src/kv_router/routing_host.rs`.

### The generic bound that forces the shape

`IngressResponseEncoder<U>` in `lib/runtime/src/pipeline/network.rs` bounds only
`U: Data`. `pump_response_stream` is generic over that same `U` and moves `resp`
into `encode_response` before it sees anything. It therefore **cannot** inspect
the response's error type itself — only `SerdeIngressPayloadAdapter`'s impl
carries the `U: MaybeError` bound that makes `err()` and `error_type()`
reachable. Classification has to be produced by the encoder and carried on
`EncodedResponseFrame`. This is a compiler-enforced constraint, not a preference.

`EncodedResponseFrame` has 8 construction sites, all inside `lib/`: two in
`lib/runtime/src/pipeline/network.rs`, five in
`lib/bindings/python/rust/python_payload.rs`, two in
`lib/bindings/python/rust/push_egress.rs` (`into_encoded`, both codec branches),
and one in the integration test `lib/runtime/tests/bidirectional_e2e_json.rs`.
It derives no `Default`.

## Chosen approach

Rust-side, in `lib/runtime/`, plus a regenerated Python mirror and a Fern docs
edit. No Python logic changes.

1. **Add the constant.** One new entry in
   `work_handler::error_types` in `lib/runtime/src/metrics/prometheus_names.rs`:
   `pub const ENGINE_STREAM: &str = "engine_stream";`, with the doc comment the
   codegen turns into the Python comment.

2. **Carry the classification on the frame.** Replace
   `EncodedResponseFrame::is_error: bool` with a **required, non-defaulted**
   field that distinguishes the three cases the pump must tell apart — data,
   engine error, and cancellation/shutdown — and keep an `is_error()` accessor so
   the existing readers (the pump's health-check gate, the push-egress
   round-trip) express the same thing they do now. A three-state field rather
   than a second parallel `bool` because `is_error: false, is_cancellation: true`
   is an unrepresentable state that a bool pair would let a call site construct.

3. **Classify in the encoders, where the type is reachable.**
   `SerdeIngressPayloadAdapter::encode_response` already calls
   `response.err()`; feed the resulting `DynamoError` to
   `error::match_error_chain(err, &[ErrorType::Cancelled], &[])` — reusing the
   helper `migration.rs` and `routing_host.rs` already trust — and additionally
   treat the engine-shutdown variant as cancellation, so a worker draining for
   shutdown does not light up an alert. Mirror the identical classification in
   `encode_python_response` and in `PushFrame::into_encoded`
   (`lib/bindings/python/rust/push_egress.rs`), which is the path a push-mode
   Python handler's `close_with_dynamo_error` takes.

4. **Increment once, in the pump.** In `pump_response_stream`, alongside the
   existing `saw_error_response |= is_error;`, add a `bool` latch and increment
   `error_types::ENGINE_STREAM` on the first frame classified as an engine error:

   ```rust
   if frame_is_engine_error && !counted_engine_stream_error {
       counted_engine_stream_error = true;
       if let Some(m) = self.metrics() {
           m.error_counter
               .with_label_values(&[work_handler::error_types::ENGINE_STREAM])
               .inc();
       }
   }
   ```

   The latch is what makes it at-most-once even for an engine that emits several
   error frames before the stream ends. The `serialization` branch above it and
   the `publish_response` / `publish_final` branches below it are untouched, so
   a request can still be counted under more than one *distinct* value when more
   than one distinct thing failed — which is the existing, intended behavior —
   but never twice under `engine_stream`, and never under both `generate` and
   `engine_stream`, since `generate` is emitted from a function that only runs
   when the pump never does.

5. **Regenerate the Python mirror.** Run
   `cargo run -p dynamo-codegen --bin gen-python-prometheus-names` and commit the
   resulting `lib/bindings/python/src/dynamo/prometheus_names.py`. Do not
   hand-edit it.

6. **Tests**, all in the existing `#[cfg(test)] mod tests` in `push_handler.rs`,
   driving `pump_response_stream` directly through the existing harness and
   asserting on `error_counter.with_label_values(...).get()`. Each asserts the
   `engine_stream` count *and* that the neighbouring values did not move, which
   is what makes them non-tautological — they pin a classification boundary, not
   the code that was just written:
   - a mid-stream typed engine error after N good frames → `engine_stream == 1`
   - several consecutive engine error frames in one stream → `engine_stream == 1`
     (the latch)
   - a frame whose error chain carries `ErrorType::Cancelled` → `engine_stream == 0`
   - an engine-shutdown-typed error frame → `engine_stream == 0`
   - a clean stream of data frames plus the complete-final marker →
     `engine_stream == 0` (extending the existing clean-stream test's assertions
     rather than adding a second one)
   - the encoder returning `Err` (the malformed/unserializable response) → the
     existing `serialization` count still increments and `engine_stream` stays 0,
     so the two are not conflated
   - a label-set assertion that the counter's variable label names are exactly
     `["error_type"]`, which is the executable form of the no-unbounded-labels
     requirement

7. **Docs.** In
   `docs/fern/pages/reference/observability/metric-labels.mdx`, add the
   `engine_stream` row to the `### Component error types` table (Stage:
   Streaming; Meaning: the engine returned a typed error after the response
   stream had already opened — counted once per request, and explicitly *not*
   incremented by user cancellation or worker shutdown); amend the `generate`
   row so it reads as the setup-failure case rather than as the single
   engine-failure counter; add the missing `serialization` row while editing that
   table, since leaving a known-incomplete enumeration next to a new row is worse
   than the one-line fix. Add an example error-ratio and alert query in the house
   style, e.g.

   ```
   sum by (dynamo_component) (rate(dynamo_component_errors_total{error_type="engine_stream"}[5m]))
     /
   sum by (dynamo_component) (rate(dynamo_component_requests_total[5m]))
   ```

   Cross-reference it from the `dynamo_component_errors_total` entry in
   `metrics-catalog.mdx`.

## Rejected alternatives

**Increment inside `EngineAdapter::generate`'s error arm
(`lib/backend-common/src/adapter.rs`).** This is where the ticket's language
points, and the arm already has the `DynamoError` in hand
(`dynamo_err.error_type()` is formatted into the span there), so classification
would be free. Rejected on ownership: `backend-common` has no reference to this
counter anywhere, the adapter is constructed before `Ingress` attaches
`WorkHandlerMetrics`, and the fix would have to be repeated for
`RawEngineAdapter` and for every future adapter. It would also miss push-mode
Python handlers entirely, which reach the pump through a different egress. The
ticket asks for consistency "across vLLM, SGLang, and other unified backends";
the pump is the only place where that is true by construction rather than by
diligence.

**Threading a metrics handle into `EngineAdapter::new` as an optional
parameter** (`Option<Arc<…>>`, or a builder `with_metrics(...)` alongside the
existing `with_first_token_source(...)`). Rejected specifically *because* it is
optional: an adapter constructed without it silently emits nothing, and the
failure mode is a metric that reads zero on some deployment paths — the exact
class of bug that is invisible until an incident. Making it required instead
would break `EngineAdapter::new`, `RawEngineAdapter::new`, `JsonProbeAdapter`,
and every test constructor in `adapter.rs` and `testing.rs`, for a placement
already rejected above.

**On the API-shape question for `EncodedResponseFrame`: required, not
optional.** The alternative was to keep `is_error: bool` untouched and add a
second field with a `Default` impl plus `..Default::default()` at the call
sites, so existing constructions keep compiling. Rejected. There are 8
construction sites and the crucial ones are the *other* language's path —
`python_payload.rs` and `push_egress.rs` — which is exactly where a
`PyGeneratorExit`-derived shutdown error becomes an error frame. A defaulted
field would let those sites keep the default classification, which is "engine
error", and the resulting over-count would be silent: the tests would pass, the
build would pass, and the counter would be wrong only in production, only during
shutdown. A required field converts that into a compile error at every site,
and `cargo check --workspace` — Recipe `02-rust-cargo-check`, Section 2 — is the
proof that every caller was found, because `lib/bindings/python` is a separate
crate from `lib/runtime` and a `-p dynamo-runtime` check would not see it. That
is the single most important reason the recipe ladder must include a
workspace-scoped check rather than a per-crate one.

**Gate on `AsyncEngineContext` state (`!context.is_stopped()`) instead of
classifying the error.** Zero API change, which is genuinely attractive.
Rejected because it is both too narrow and too broad: too narrow because an
engine-reported cancellation (upstream premature EOF mapped to `Cancelled`)
arrives with the local context still live and would be counted; too broad
because the existing `publish_final` tests establish that `is_stopped()` is also
true after `kill()`, and a killed context is a real failure the maintainers
deliberately kept counted. Reusing a predicate the tree has already documented as
"too coarse a guard" would be a regression of a merged fix.

**A `reason` or `error_kind` label on the new value.** Rejected on cardinality.
`BackendError` is a closed enum today, so it would be bounded in principle, but
the ticket explicitly asks that no new label dimensions be introduced, and the
`Display` strings are not stable API. If per-kind breakdown is wanted later it is
a separate proposal with its own cardinality budget.

**Emitting from the frontend instead of the worker.** The frontend sees the
error frame too, but `dynamo_component_errors_total` is a worker/work-handler
family; attributing a worker-side engine failure to the frontend would put the
value on the wrong component and break the error-ratio query against
`dynamo_component_requests_total`.
