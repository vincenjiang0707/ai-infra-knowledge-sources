### tmonty12 · 2026-09-23

**The re-fetch before status write is the wrong fix for this conflict.**

The status written in `persistWorkloadProgramResult` is computed from the DGD object fetched at the start of `Reconcile`. Re-fetching just before the `Status().Update` means you're stamping status derived from generation N onto an object that may now be at generation N+1 (after the DGDSA bumped it). That's a correctness problem, not just a style issue — you're writing a stale status computation onto a newer resource version.

The `AGENTS.md` in `internal/controller/` also flags this directly:
> Uncached API-server ("quorum") reads are most likely the wrong solution to informer-cache races.

**Root cause is in the DGDSA controller**, not in `persistWorkloadProgramResult`. The DGDSA controller does a full `r.Update(ctx, dgd)` to write a single component's replica count (`dynamographdeploymentscalingadapter_controller.go:117`). That full update touches the DGD's `resourceVersion` and races with the DGD controller's `Status().Update`.

**Suggested fix:** Switch the DGDSA controller to a targeted merge patch:

```go
base := dgd.DeepCopy()
component.Replicas = &adapter.Spec.Replicas
if err := r.Patch(ctx, dgd, client.MergeFrom(base)); err != nil { ... }
```

For this to be safe with a multi-component DGD, `spec.components` needs `patchMergeKey:"componentName"` added to the struct tag in the API types (analogous to how `spec.template.spec.containers` uses `patchMergeKey:"name"` in the upstream Kubernetes types). Without the merge key, a JSON merge patch replaces the entire components array. With it, only the targeted component element is patched.

This eliminates the write conflict entirely: the patch body contains no `resourceVersion`, so the API server applies it to the current object version without a conflict check, and the DGD controller's status write proceeds unobstructed. The `persistWorkloadProgramResult` change should be reverted.
