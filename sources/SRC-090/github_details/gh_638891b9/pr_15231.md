## Summary

Add a standalone Velo response plane with TCP and optional UCX message transport. Select it with `DYN_RESPONSE_PLANE=velo` and `DYN_VELO_RESPONSE_TRANSPORT=tcp|ucx`; UCX uses the `velo-ucx` build feature. Keep TCP as the default and QUIC as a separate implementation.

Use one shared process service on the serving runtime, prebound stream tickets, and native Velo stop/cancel signals. Preserve response framing, typed errors, final output, and completion checks while polling the Velo stream directly. Pin `da848eb78eec6331d670b8d80b5b0b8333b464cc` from [Velo #90](https://github.com/ai-dynamo/velo/pull/90), update all three lockfiles, and expose Velo metrics through Dynamo.

Extend the existing Tyche harness and include the [completed four-way report](https://github.com/ai-dynamo/dynamo/blob/507c1961b95ac75a9dbbf446fca7d75b73c7830d/benchmark-harness/velo-response/report/README.md), with source/build hashes, per-run results, hardware packet counts, and retained errors. All four modes use the same frozen UCX-enabled binary and 2,048 speedup-10 mock workers. All 16 measured runs are retained: 9,854,326 completed exported records, including five empty-content errors.

Velo TCP delivered 66.5% more output tokens/s than TCP, with 21.6% less frontend CPU/request and 46.6% fewer RX packets/output token. QUIC had the best throughput, CPU/request, and packet cost. Velo RDMA showed no clear throughput gain over Velo TCP and used 16.5% more combined wire packets/output token. Velo improved p99 TTFT against TCP but increased p99 per-request mean ITL. The report separates fabric differences, client limits, and TCP drain cancellations. These are directional results; defaults are unchanged.
