## What this is — and isn't

This is an **observability/resilience improvement only**. It does **not** claim to fix the
underlying cause of the repeated `EndpointSlice`/`DynamoWorkerMetadata` watch-stream failures
reported in #15276 — that root cause is still undetermined and may be environment-specific
(e.g. an intermediary closing long-lived HTTP/2 watch connections). What this PR does is make
that failure mode visible and less silently harmful when it does happen, regardless of cause.

## Changes (`lib/runtime/src/discovery/kube/daemon.rs`)

All three reflector loops (`EndpointSlice`, `Pod`, `DynamoWorkerMetadata` CR) get the same three changes:

1. **Escalate log level.** A small `ReflectorHealth` tracker (consecutive failure count +
   last-success timestamp) escalates the per-error log from `WARN` to `ERROR` once a reflector
   has failed `REFLECTOR_ERROR_ESCALATION_FAILURES` (3) times in a row or gone
   `REFLECTOR_ERROR_ESCALATION_AGE` (60s) without a successful list/watch cycle.
2. **Fallback `list()` polling.** Once a reflector has gone `REFLECTOR_FALLBACK_LIST_AFTER` (45s)
   without success, a ticker (every `REFLECTOR_FALLBACK_LIST_INTERVAL` = 30s) issues a plain
   `Api::list()` (same label selector as the watch) and feeds the result through the existing
   `Apply`-event path, so discovery gets eventually-consistent data instead of staying empty
   forever purely because the long-lived watch keeps dying.
3. **Distinguish expected relists from real failures.** `watcher::Error::WatchError(resp)` (the
   apiserver's structured error — e.g. 410 Gone / expired resourceVersion) is now logged at
   `DEBUG` as an expected relist trigger, separately from `watcher::Error::WatchFailed(_)` and
   other variants, which go through the health-tracked WARN/ERROR path above. Previously both
   were logged identically at `WARN`, making it impossible to tell a normal relist from a real
   problem from the logs alone.

The fallback `list()` reuses the exact same `Config`/label selector the watch itself was built
with (captured before it's moved into `watcher()`), so it lists the same object set. Deletions
that happened while the watch was down are not reconciled by the fallback list (it only applies
adds/updates) — that's a deliberate, minimal scope: it turns "watch is stuck forever" into
"eventually consistent for existing objects," not a full alternate list-based reconciliation
loop.

No behavior changes outside the three points above; no unrelated refactoring.

## Testing

**Compile-check only** — I have not run this against a live cluster or reproduced the original
watch-stream failure with this patch applied.

```
cargo check -p dynamo-runtime --all-features
```

Result: passes cleanly (0 errors, 0 warnings) on native Linux (`rust:1.90-slim`, ~1m16s). Note: a
macOS host build of this same crate fails, but on 3 pre-existing errors in
`pipeline/network/egress/tcp_client.rs` (`libc::SOL_TCP`/`TCP_QUICKACK`/`SO_BUSY_POLL` — Linux-only
constants used without a `target_os` guard) — unrelated to this diff, which only touches
`discovery/kube/daemon.rs`, confirmed absent on the Linux check above.

## Why not a full fix

The existing `reflector(writer, watcher(api, cfg)).default_backoff()` pattern in this file is
already the standard, correct kube-rs idiom. From outside the process we could not conclusively
determine why the watch stream repeatedly fails in our cluster (environment-specific stream
termination vs. something else), so we're not confident enough to submit a specific "fix" for
that. This PR only makes the failure mode observable and less silently total.
