# [PR #15287] feat(sidecar): accept video media in vLLM sidecar encode role

## 正文

#### Overview

The vLLM sidecar Encode worker now accepts video media, and image and video media together in one request. The Encode worker now encodes video in the E+PD and E+P+D topologies. Before this change, the Encode worker rejected each media item that was not an image. The frontend then sent each video request to the downstream engine for inline encoding and logged one ERROR for each request.

**Repro**

```bash
./lib/sidecar/vllm/launch/disagg_multimodal_e_pd.sh --model Qwen/Qwen3-VL-2B-Instruct

curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "Qwen/Qwen3-VL-2B-Instruct",
  "max_tokens": 48,
  "temperature": 0,
  "messages": [{"role": "user", "content": [
    {"type": "text", "text": "Describe this video in one sentence."},
    {"type": "video_url", "video_url": {"url": "<http, https, or data: URI of an MP4 file>"}}
  ]}]
}'
```

**Before** (main): the Encode worker rejects the video, and the downstream engine encodes it inline.

```text
ERROR dynamo_llm::kv_router::encoder_router: Encoder hop failed; falling back to downstream inline encoding error=Unavailable: Worker generate() failed before response stream: Generate Error: InvalidRequest: encode requests support image media only
```

**After**: the encoder-only engine saves the video embedding, and the downstream engine loads it. The caption is the same as in aggregated serving.

```text
encoder engine: Save cache successful for mm_hash dd6fb9efbfbe1ec04036d3697c211944a2438d8d7108a55a2c6059ec40e5f75c
PD engine:      Success load encoder cache for hash dd6fb9efbfbe1ec04036d3697c211944a2438d8d7108a55a2c6059ec40e5f75c
```

#### Details

A video request that went through an Encode worker failed at the encoder hop. The frontend logged an ERROR and sent the request to the downstream engine, which encoded the video inline. The Encode worker did no work for video requests.

The cause was the Encode modality check in the vLLM sidecar, which accepted image media only. The rest of the path needed no change: vLLM decodes the video, and the EC connector saves and loads the video embedding in the same way as an image embedding.

This change lets the check accept image and video media, also together in one request. The check still rejects audio, because audio through an Encode worker is not validated. A request that contains audio fails as a whole, and the frontend encodes all of its media inline, as before. The change also removes a duplicate image-only check. The remaining check runs on the built gRPC media list, so it covers raw media and preprocessed features. The sidecar sends each video item without a UUID. `vllm-rs` then keys the video by a hash of its bytes, so the Encode engine and the downstream engine use the same encoder-cache key.

The unit tests send image, video, and image+video requests through Encode, E+PD, and E+P+D, and check that the Encode worker rejects each request that contains audio. The README and the Fern vLLM sidecar page now say that Encode workers accept image and video media, and give the earliest validated vLLM release for each topology.

Limits:

- Each vLLM engine host needs the `ffmpeg` and `ffprobe` executables, with a decoder for the codec of each input video. The Dynamo vLLM runtime image does not include `ffprobe`, its image build policy does not allow adding it, and its `ffmpeg` decodes only VP8, VP9, and raw video.
- E+PD works with vLLM `0.29.0`. E+P+D needs vLLM `0.30.0`, because decode needs vllm-project/vllm#54814.
- The Encode worker removes only the vision encoder work from the downstream engine. Each downstream engine still fetches and decodes each video.

Out of scope: audio through an Encode worker, performance measurements for video encoder disaggregation, and video codec support in the runtime image.
