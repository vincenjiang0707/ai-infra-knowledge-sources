# [Issue #14842] [FEATURE]: Shared-cache tier for the vLLM MooncakeStoreConnector (--shared-cache-type mooncake-store)

source: https://github.com/ai-dynamo/dynamo/issues/14842
state: open | updated: 2026-09-25T03:58:28Z
labels: enhancement, language::rust, dynamo-llm, backend::vllm, router

## 正文

### Feature request

Add a shared-cache tier implementation for the vLLM `MooncakeStoreConnector`, e.g. `--shared-cache-type mooncake-store` (a `VllmMooncakeStore` next to `HicacheSharedKvCache`), so the KV router can see blocks that live only in the shared Mooncake store when the engine is vLLM.

Today `--shared-cache-type hicache` (`lib/llm/src/kv_router/shared_cache.rs`) consumes the Mooncake master's KV-event stream (`ENABLE_KV_EVENTS`, ZMQ PUB of `stored` / `removed` per object) but derives keys with SGLang's HiCache scheme (`{sha256 page hash}_{rank}_k/v` from the `sglang_hicache_mooncake` model card). With a vLLM worker it is inert: the vLLM connector's object keys look like

```
{cache_prefix}@{model}{namespace}@tp_rank:R@pcp0@dcp{D}@pp_rank:0@group:{G}@{chunk_hash_hex}
```

with one Mooncake `group_id` per chunk (`vllm-mooncake-store:{cache_prefix}@{model}{namespace}@{chunk_hash_hex}`) shared by the per-rank / per-KV-group objects, so nothing the hicache client computes ever matches.

### Describe the problem you're encountering

Setup: vLLM main (post vllm#55531) with `MooncakeStoreConnector` as the L3 in a `MultiConnector`, PD disaggregated on GB300 (TP4 / DCP4, hybrid MLA + linear-attention model with two prefix-cacheable KV cache groups), Dynamo frontend at `202478991b`, Mooncake `0.3.13+gb46235d` built from source with `-DENABLE_KV_EVENTS=ON`.

The router indexes only the workers' GPU-tier KV events. The connector's own store events arrive with `medium="cpu"` (lowercase) and are dropped by `StorageTier::from_kv_medium`, which is arguably correct since they describe a rack-shared pool, not the publishing worker's host tier. The result is that a prefix that is fully present in the shared store is scored as cold, so worker selection ignores L3 locality and, for anyone using booked prefill tokens for admission, the request is booked as a full cold prefill.

Points that shaped the design we ended up with, in case they help whoever picks this up:

- vLLM's chunk hash is sha256 over a pickled `(parent_hash, tokens, extra_keys)` chained from a process-seeded `NONE_HASH`, so the router cannot recompute the keys from tokens the way the hicache client does. But the workers' GPU `stored` events already carry the exact chain: `KvCacheStoredBlockData { block_hash (external, u64 = low 64 bits of the chunk hash), tokens_hash }` plus `parent_hash`. Learning a `(parent_external, tokens_hash) -> external` map from those events, tapped in `Indexer::try_apply_event` before the radix tree's parent check (so events rejected as `parent_block_not_found` still teach the chain), gives router-granularity keys with zero dependence on vLLM's pickle format.
- Presence can be keyed by the chunk hash parsed from the event's `group_id` (trailing hex after the last `@`) rather than `object_key`, which collapses the `dcp × groups` objects of one chunk into one entry. A `removed` for the group should drop the chunk (the engine needs every rank namespace present, so a partial chunk must read as a miss). A sequence gap or subscriber reconnect should clear presence but keep the learned chain.
- Lookup then walks the chain over the request's per-block `LocalBlockHash`es and returns the prefix run, since the connector can only extend a prefix.
- The chain map needs a bound that fits real stores (the existing `MAX_MOONCAKE_INDEX_ENTRIES` of 1,000,000 is far below a multi-TB store's key count); a two-generation sweep works.
- Useful extra metrics: present entries, chain entries, and blocks that stopped on a missing chain link rather than an absent hash (tells whether learning coverage is the bottleneck).
- Mooncake side: the publisher is a compile-time option that upstream defaults off, and its `dependencies.sh` only installs libzmq on the Debian/Ubuntu branch, so a manylinux (AlmaLinux) wheel build needs `zeromq-devel` added by hand before configure.

### Describe alternatives you've tried

- `--shared-cache-type hicache` against the vLLM connector: inert, as above.
- Admitting the connector's lowercase `cpu` events as a host tier: wrong, it would credit rack-shared blocks as host residency of one worker and double count against the disk weight.
- We implemented the approach above as a patch on our frontend build (new `SharedCacheType::MooncakeStore`, `SharedKvCache::observe_stored` / `check_blocks_by_local_hashes` trait additions, `Arc<dyn SharedKvCache>` shared between the router and the indexer), and it passes the kv-router and dynamo-llm test suites. Happy to share it as a reference for whoever takes this upstream; a native implementation would let us drop the patch.
