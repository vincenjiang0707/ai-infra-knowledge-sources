# [Issue #14936] [BUG]: --dyn-chat-processor vllm is unusable for gpt-oss (GptOssReasoningParser raises NotImplementedError)

source: https://github.com/ai-dynamo/dynamo/issues/14936
state: open | updated: 2026-09-18T05:15:57Z
labels: bug, language::python, backend::vllm, frontend

## 正文

### Describe the Bug

`--dyn-chat-processor vllm` (`dynamo.chatProcessor: vllm`) cannot serve gpt-oss-class models.
It is a documented, supported flag, but selecting it for gpt-oss fails with HTTP 500 for an
architectural reason, not a configuration one.

`components/src/dynamo/frontend/prepost.py:1353` calls:

```python
delta_message = self.reasoning_parser.extract_reasoning_streaming(
    self.previous_text, current_text, delta_text,
    self.previous_token_ids, current_token_ids, delta_token_ids,
)
```

vLLM's `GptOssReasoningParser` raises `NotImplementedError` on **all three** output-parsing
methods — `extract_reasoning_streaming`, `extract_reasoning`, and the batch variant
(`vllm/reasoning/gptoss_reasoning_parser.py`, lines 36, 50 and 60):

```python
raise NotImplementedError(
    "GptOssReasoningParser only provides boundary detection. "
    "Use HarmonyParser for output parsing."
)
```

So the parser vLLM registers for gpt-oss deliberately does not implement the interface Dynamo's
vLLM chat processor calls. The two cannot meet.

The parser's own message points at `HarmonyParser` as the intended counterpart, but no Dynamo
code path reaches it. Across the entire `components/src/dynamo/` tree:

```
$ grep -rn -i harmony components/src/dynamo/ | wc -l
1
```

— and that single hit is a line in a test-case `.md`, not code. vLLM's `harmony.py` is reachable
only from vLLM's own entrypoints, which Dynamo bypasses.

### Steps to Reproduce

Deploy a gpt-oss model with the vLLM chat processor:

```
dynamo.chatProcessor: vllm
toolCallParser: openai
reasoningParser: openai_gptoss
```

Send any chat completion request.

### Expected Behavior

Either the request is served, or startup rejects the combination with a clear error explaining
that this processor cannot serve this model family — rather than accepting the configuration and
failing per-request at runtime.

### Actual Behavior

HTTP 500 from the `NotImplementedError` above, on every request.

A second, separate failure is hit first and is worth recording because it masks the above: the
gpt-oss chat template does

```jinja
{{- "Reasoning: " + reasoning_effort + "\n\n" }}
```

guarded only by `is not defined`. The vLLM processor passes `reasoning_effort=None`, which *is*
defined, so the template evaluates `str + None` and the request fails with HTTP 400. That one is
workaroundable with `chat_template_kwargs: {"reasoning_effort": "medium"}` — after which the 500
above is reached.

### Environment

`prepost.py:1353` verified on `main` at `c76d3208f32b`. `GptOssReasoningParser` verified in a
current vLLM checkout. The HTTP 400/500 behaviours were observed in a deployment on vLLM 0.27.1;
the two code-level claims above were re-verified independently from source.

### Additional Context

This is independent of, but was found while investigating, #14935 — switching to the vLLM chat
processor is the obvious workaround for the Rust preprocessor's reasoning-finalization gap, and
it turns out not to be available for the affected model family. Recording it separately because
it is independently useful: a documented flag that cannot work for a supported model family
should either work or say so up front.

Fixing it would mean routing gpt-oss through `HarmonyParser` on the vLLM-processor path rather
than through the `ReasoningParser` interface, which is a design question rather than a patch, so
I am filing it rather than proposing a PR.
