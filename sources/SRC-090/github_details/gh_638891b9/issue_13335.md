## Description

The multimodal embedding-cache indexer is registered through a `Weak` pointer, but two process-scoped background tasks retain strong `Arc` references to it. Dropping the last `PushRouter` therefore cannot release the indexer while the runtime remains active.

The ownership cycle is visible in the current implementation:

* [`SHARED_INDEXERS`](<https://github.com/ai-dynamo/dynamo/blob/8097ac7b9ea636ff5983c4d9da16fd6bde84f426/lib/llm/src/kv_router/indexer/embedding_cache.rs#L56-L100>) stores `Weak<dyn MultimodalCacheIndex>` entries and prunes entries whose strong count reaches zero.
* [`start_subscriber`](<https://github.com/ai-dynamo/dynamo/blob/8097ac7b9ea636ff5983c4d9da16fd6bde84f426/lib/llm/src/kv_router/indexer/embedding_cache.rs#L169-L253>) clones `Arc<Self>` into a task that reconnects until the runtime child token is cancelled. That task alone prevents the strong count from reaching zero.
* [`spawn_multimodal_cache_cleanup_watcher`](<https://github.com/ai-dynamo/dynamo/blob/8097ac7b9ea636ff5983c4d9da16fd6bde84f426/lib/runtime/src/pipeline/network/egress/push_router.rs#L419-L507>) also moves an `Arc<dyn MultimodalCacheIndex>` into a task. [`PushRouter::from_client_with_state`](<https://github.com/ai-dynamo/dynamo/blob/8097ac7b9ea636ff5983c4d9da16fd6bde84f426/lib/runtime/src/pipeline/network/egress/push_router.rs#L584-L643>) scopes that task to the runtime primary token rather than to the router that requested it.

After every router for a runtime endpoint is dropped, the indexer can therefore remain registered, retain its cache maps and discovery/event subscriptions, and be returned to a later router generation. The registry key is `(connection_id, endpoint_id)`, so a stable key retains one indexer rather than adding one per router; distinct retired keys can accumulate until runtime shutdown.

The instance-removal watcher lifecycle reports and fixes around `PushRouter` do not cover this object. In particular, PR ai-dynamo/dynamo#13224 explicitly left `spawn_multimodal_cache_cleanup_watcher` unchanged, and the current open PRs touching `push_router.rs` do not change this ownership path.

## Expected behavior

When no router consumes a runtime endpoint's multimodal cache index, the indexer and both associated watchers should stop and the weak registry entry should become prunable. A newly constructed router may then build a fresh indexer. Shared use by concurrent routers must continue to use one live indexer.

## Suggested regression test

Construct an indexer and cleanup watcher with a lifecycle that remains active, retain a `Weak<EmbeddingCacheIndexer>`, and drop the final external/router `Arc`. Assert that the weak pointer can no longer be upgraded and that both subscriptions stop. Repeat with a second router sharing the endpoint to verify that dropping only one consumer does not stop shared state.

This report is based on source inspection at commit `8097ac7b9ea636ff5983c4d9da16fd6bde84f426`; it does not include a deployed reproduction.

### LOGO127 · 2026-09-05

AI-assisted follow-up: I reproduced both retention paths on current main `4abae7b780c5` with test-only changes, process-local discovery, and no model/GPU or external NATS/etcd service.

- Runtime: construct `PushRouter::from_client_with_state` with the existing static cache test implementation, clone the router, then drop both consumers. The cache stays alive during a bounded 500 ms observation; cancelling the runtime releases it.
- LLM: obtain two handles through `try_build_cache_indexer` (the real subscriber is started), confirm they share the same object, then drop them. The cache again survives until runtime cancellation.

Both new assertions fail on unchanged production code, after their runtime-cancellation cleanup controls succeed. The existing 39 push-router tests and 4 embedding-indexer tests pass with those two new regression cases excluded. This was CPU-only WSL/Rust 1.98 testing, not validation of the pinned 1.96.1 toolchain or a deployed backend.

Would a focused follow-up covering both ownership paths be welcome? I would preserve shared consumers, end idle/reconnecting tasks when the last cache generation owner goes away, and test immediate recreation so an old watcher cannot clear its successor's registration. Merely weakening the pointer would not wake an idle task.

No production fix or PR yet; I am checking the lifecycle boundary with the Router/Runtime owners before implementing across both components.
