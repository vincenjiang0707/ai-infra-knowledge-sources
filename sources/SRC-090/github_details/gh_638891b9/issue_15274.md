## 正文

## Summary

This DEP adds `POST /v1/systemone` to the Dynamo frontend. The route implements the TypeSafe/Jev wire protocol, where a client asks `noul`, `choice` and `score` questions about a state and gets probabilities back instead of generated text.

The scope is the generative readout, which works with any chat model Dynamo already serves. The handler renders the state once, then scores each question as a one-token completion over the shared token prefix, using `logprob_token_ids`. The vLLM backend supports this today without engine changes.

The design copies the behavior of SGLang's merged `/v1/systemone` route ([SGLang PR 41208](https://github.com/sgl-project/sglang/pull/41208)): same prompt, labels, scoring, confidence and response. A client should get the same answers from either server. What Dynamo adds is placement across replicas, so all the questions of a request land on the worker holding the state prefix, and one route that works over several backends.

## Motivation

A System One model answers structured questions about a state with calibrated probabilities. Each question costs one prefill and one scored token, with no decode loop. The TypeSafe/Jev HTTP API has become the common interface for these models and the official SDKs target it. Today the options for serving it are side-car wrappers (openjev-sglang, AnyJev used as a library), SGLang's single-engine route, or the closed Jev API.

Dynamo already has most of the pieces:

- The frontend enables routes per model type. `POST /v1/classify` and `/v1/pooling` are registered in `get_endpoints_router` and switched on through `state.flags` when a worker of that type registers. `/v1/systemone` can follow the same pattern.
- `logprob_token_ids` already flows from the request allowlist through the preprocessor to vLLM's sampling params, so the vLLM path needs no engine change.
- The KV-aware router can place the state prefix on one worker, and worker pinning can keep the rest of the request there. A single-engine route or a side-car cannot do this across replicas.

## Goals and non-goals

Goals:

1. Serve `/v1/systemone` from the Dynamo frontend.
2. Support any served chat model, with per-backend capability checks.
3. Return the same answers as SGLang's `/v1/systemone` for the same model and chat template, and match TypeSafe's documented examples and the official SDKs.

Non-goals for v1:

- `/permute` and `/separate` (Jev and LocalAI extensions), the `stats` and `assets_used` fields, and streaming.
- System One models that are not chat models (see Future work).

## Wire protocol

```
POST /v1/systemone
{ "model": "<served-model>",
  "state": <string|object|array>,
  "questions": { "<id>": { "type": "noul|choice|score",
                            "instructions": "...",
                            "criteria": ... } } }
```

The three question types:

- `noul` is a yes/no question. `criteria` is optional and can describe each side as `{"true": ..., "false": ...}`. The answer is `noul`, the probability of true, with no `confidence`.
- `choice` takes `criteria` as a map from option name to description (the description can be `null`). The answer has `choice`, `probabilities` keyed by option name, and `confidence`.
- `score` takes `criteria` as an ordered list of levels. The answer has `score` (the expected level index, starting at 0), `legend` and `probabilities` keyed `"0"` to `"L-1"`, and `confidence`.

The response is `{ "model", "answers": { <id>: ... }, "usage": { "input_tokens", "output_tokens" } }`. Validation errors return 422 with FastAPI's `{"detail":[...]}` list. Overload returns 529 with `Retry-After`, which is already Dynamo's default overload status (`DYN_HTTP_OVERLOAD_STATUS_CODE`). The SDKs send a Bearer token, which Dynamo treats as it does for its other routes. The protocol does not define `usage`, so we follow SGLang: `input_tokens` counts every scored prompt and `output_tokens` is 0.

### Confidence

Every implementation we checked computes choice confidence the same way, clamped to [0, 1]. Score confidence has two versions in the wild:

```
choice:           (K * pmax - 1) / (K - 1)
score (adapter):  1 - E|i - mode| / mean|i - (L-1)/2|     # typesafe-ai/system-one-adapter-python
score (alt):      (L * pmax - 1) / (L - 1)                # choice formula applied to levels
```

TypeSafe's docs have one score example (`p = [0, 0.95, 0.05]`), and both formulas give 0.925 on it, so the docs don't decide. They differ on spread-out distributions: `p = [0.5, 0, 0.5]` gives 0 with the adapter formula and 0.25 with the other. We use the adapter formula, floored at 0, as SGLang does. It is TypeSafe's own published code and it takes the order of the levels into account. A question with a single option or level gets confidence 1.

## Design

### Why a core endpoint

The frontend extension hook only supports static GET routes (`frontend_extension.rs`: "Currently only `GET` routes are supported") and can't call engines. So the endpoint follows the pattern of the experimental Anthropic messages API: an off-by-default flag and a handler that translates to the OpenAI protocol internally and calls an existing engine. Here that engine is the completions engine, called with token-ID prompts.

### Handler

Steps tagged (SGLang) match SGLang's route (`python/sglang/srt/entrypoints/systemone/` and `openai/serving_decisions.py`) so the answers are the same. The other steps are specific to running across several workers.

1. Validate (SGLang). Errors return 422 with FastAPI's detail list, without the `input` echo. A request needs at least one question. Choice questions take 1 to 255 options with distinct names, score questions take 1 to 10 levels, and a noul question needs instructions or a true/false description. Unknown keys inside a question are rejected, because a typo there would silently ask a different question. Unknown top-level fields are ignored, as the published schema allows. The `/v1/decisions` fields that would change answers (`temperature`, `prompt_format_version`, `return_prompt_token_ids`) are rejected by name. Dynamo adds configurable limits of 128 questions, 32,768 tokens per prompt and 65,536 tokens per request. The handler then resolves the model (`resolve_canonical_name`) and gets the completions engine (`ModelManager::get_completions_engine`, `discovery/model_manager.rs:1379`).

2. Build the prompt (SGLang). Each question is one user message containing the state (a string as is, anything else as compact JSON), a blank line, and a question block:
   - choice: `Question: <instructions>`, then one line per option, `A: <name> - <description>` or just `A: <name>`, then `Answer with the letter of one option only.`
   - score: `Question: <instructions>`, then one line per level, `0: <level>`, then `Answer with the number of one level only.`
   - noul: `Is the following true? <instructions>`, then `yes: <true description>` and `no: <false description>` if given, then `Answer with yes or no only.`

   The `Question:` line is left out when `instructions` is blank. The message is rendered with the model card's chat template (`prompt_formatter_from_mdc`, `preprocessor/prompt.rs:381`) with `add_generation_prompt=true` and the template's reasoning toggle set to false. The toggle is found from the configured reasoning parser, as in SGLang. It has to be set explicitly because Dynamo's Anthropic handler enables thinking whenever a reasoning parser is configured. The handler accepts SGLang's `chat_template_kwargs` extension. It returns 400 if a request turns the toggle on, or if the template always opens a reasoning block where the answer should go.

3. Pick labels (SGLang). Noul uses `yes` and `no`, choice uses `A` to `Z`, and score uses `0` to `9`. Above 26 options every option gets a two-letter label (`AA`, `AB`, and so on). Checking hundreds of labels against the full prompt is slow, so this only works when the template puts an added token, such as Qwen's `</think>`, between the message and the answer position. Labels can then be checked against the end of the template alone. Otherwise the request gets a 400. A label is valid only if `encode(prompt + label) == encode(prompt) + [id]` and `id` differs from every other label's ID. The tokenizer comes from the worker's model card (`ModelDeploymentCard::tokenizer()`), and the two-letter label set is cached per model and template.

4. Tokenize the state once. All prompts in a request start with the same template header, state and blank line. The handler renders once with a marker where the question block goes, splits the result into a prefix and an ending, and tokenizes the prefix once. Each branch prompt is the prefix IDs followed by the tokenized question block and ending, sent as a token-ID prompt (`PromptInput::Tokens` is already supported). Tokens can merge across the split, for example when the state ends in newlines. So on each request the handler compares the split tokens of the first question with its whole-prompt tokens, and tokenizes every prompt whole if they differ. This keeps the prompt tokens identical to SGLang's.

5. Place the prefix, then fan out. SGLang scores all questions in one engine call and its radix cache shares the prefix between them. With several replicas, Dynamo has to keep them together itself. It sends the first question alone through the KV-aware router, which computes the shared prefix on one worker. It then sends the remaining questions to that worker with `nvext.backend_instance_id`, because the router's view of the cache lags behind a request that just finished. Each branch uses `max_tokens=1` and `logprob_token_ids=[labels]`. The fan-out reuses the `completions_batch` pattern (`openai.rs:1556`):
   - each branch gets a child context `{id}-{qid}` linked to the parent, so a client disconnect or the first failure cancels all branches;
   - a request deadline cancels all branches and returns 504;
   - a `max_branches` semaphore, separate from request slots, stops a wide fan-out from starving other traffic, and returns 529 with `Retry-After` when full.

   If the pinned worker goes away mid-request, the request fails with 503 instead of rescoring on a cold worker.

6. Handle more than 128 labels. vLLM caps `logprob_token_ids` at 128 (`MAX_LOGPROB_TOKEN_IDS`). The handler splits the labels into chunks of at most 128 with the same prompt and joins the raw logprobs before one softmax.

7. Score (SGLang). A softmax over the raw label logprobs, which gives the same result as SGLang's softmax over the label logits at temperature 1. `noul` is p(yes). `choice` is the most likely option, with ties going to the first option in request order. `score` is the sum of i times p_i. Confidence is computed as described above. Each answer also has `type` and `x_label_mass`, the sum of exp(raw logprob) over the labels, which shows how much of the model's probability landed on the offered labels. A non-finite value fails the request with 500. `model` is the served model name. `usage.input_tokens` is the sum of prompt tokens over the questions, counting each question once, and `usage.output_tokens` is 0.

8. Later (v1.1): permutation debiasing for choice questions, averaging K cyclic shifts of the options with a geometric mean as AnyJev does. It is cheap once the prefix is cached. It stays off by default because it changes the answers compared with SGLang.

### Backend support

| Backend | Status |
|---|---|
| vLLM | Works today. `logprob_token_ids` is allowlisted (`validate.rs:116`), forwarded (`preprocessor.rs:1877`) and applied in the worker (`vllm/handlers.py:855`, which clears `logprobs` because vLLM raises unless `logprobs == len(logprob_token_ids)`). We still need a test showing the IDs come back as raw logprobs, so that `x_label_mass` is exact. The limit is 128 IDs per request (step 6). With speculative decoding, restricted logprobs can crash the rejection sampler ([vLLM issue 42592](https://github.com/vllm-project/vllm/issues/42592), fix pending in [vLLM PR 44727](https://github.com/vllm-project/vllm/pull/44727)), and vLLM's Rust scoring route rejects such engines ([vLLM PR 46427](https://github.com/vllm-project/vllm/pull/46427)). The route should reject those workers too until the fix lands. A faster path for scoring a fixed set of tokens is proposed in [vLLM issue 56767](https://github.com/vllm-project/vllm/issues/56767) and [vLLM PR 56782](https://github.com/vllm-project/vllm/pull/56782). |
| SGLang | Missing. `build_sglang_logprob_kwargs` (`common/backend/logprobs.py:268`) only maps `logprobs` and `prompt_logprobs`. It needs to map `logprob_token_ids` to `return_logprob=True, token_ids_logprob=[...]` and parse `meta_info.output_token_ids_logprobs`. The `DYN_SGL_ALLOW_TOP_LOGPROBS` gate isn't needed since this skips the costly top-k detokenization. SGLang's own route is validated with NEXTN speculative decoding, but it scores through `/v1/score` rather than generation, so PR 1 tests the generation path with speculative decoding on. |
| TRT-LLM | Only top-k logprobs (`handler_base.py:1106`), so labels outside the top k would be missing. Either leave it unsupported or offer best effort with a warning. |

### Reference implementation: SGLang

[SGLang PR 41208](https://github.com/sgl-project/sglang/pull/41208), merged on 2026-09-25, serves the protocol inside one SGLang server. It goes through the `/v1/score` path (`score_prompts` with `apply_softmax=True`), with one prefill per question and no generated text. This DEP matches it on every point the protocol leaves open:

| Topic | SGLang's route | This DEP |
|---|---|---|
| Prompt | One user message: state, blank line, question block, reasoning off (prompt format version 1) | Same (step 2) |
| Labels | `yes`/`no`, `A` to `Z`, `0` to `9`, two-letter labels above 26 options when the template allows | Same (step 3) |
| Limits | 1 to 255 options, 1 to 10 levels | Same, plus request limits |
| Errors | 422 detail list without `input`, 400 when the model or template can't serve the request, 500 for non-finite scores | Same |
| Confidence | Official adapter formulas | Same |
| Response | `type` and `x_label_mass` per answer, served model name, `output_tokens` 0, unrounded values | Same |
| Scale-out | One engine, radix cache shares the prefix | First question places the prefix, the rest are pinned to that worker; several backends |

What the PR and its docs (`docs/docs/supported-models/decision_models.mdx`) report:

- The official Python and JS SDKs work with only the base URL changed. The unofficial `jevcompat` checker passes all 32 of its MUST checks.
- Tested on one H200 in BF16 with Qwen3.8-27B (with and without NEXTN speculative decoding) and Qwen3.5-35B-A3B. A request with 62 questions over a 31K-token state takes about 9.5 s, and 64 concurrent requests all return 200. Answers are bitwise equal to SGLang's `/v1/decisions` route on the same prompts.
- Known caveats. On hybrid-attention models (Qwen3.5), probabilities can move by up to 0.07 and label mass by about 0.14 between cold and cached requests or with different batch compositions. The chosen option stayed the same in their tests, and `--disable-radix-cache` makes repeated runs identical. The SDKs also time out after 10 s and retry, so long requests need a higher client timeout.

The same cold versus cached drift can happen in Dynamo, since the first question runs cold and the others hit its cache. Parity tests should use dense models, or allow for SGLang's documented drift.

## Alternatives considered

1. Side-car wrappers only, like openjev-sglang. No changes to engines or Dynamo, but also no routing, no prefix reuse across replicas, no multi-model dispatch and no lifecycle management. This is what exists today, and we reject it as the only option.
2. The frontend extension hook. It only supports GET routes and can't reach engines (see `frontend_extension.rs`).
3. An adapter in an API gateway above Dynamo. This works, but every deployment has to set it up and Dynamo knows nothing about the route. It can live alongside native support but doesn't replace it.
4. Rely on each engine's own route (SGLang's now, vLLM's if it adds one). This works per engine but gives no routing across replicas and no common behavior across backends. Since this DEP matches SGLang, clients can still switch between the two and get the same answers.

## Open questions

SGLang's route already answers the error format, score confidence, `usage`, labels and `x_label_mass`. These are still open:

| Question | Proposal |
|---|---|
| Model naming (`jev-latest` alias?) | When exactly one System One capable model is served, accept any `model` value and return the served name, as SGLang does, so existing Jev clients work unchanged. With several models, require the served name. Aliases belong in a layer above Dynamo. |
| Rounding | Return unrounded values like SGLang. TypeSafe's examples show 2 decimals, and clients that compare strings can round. |
| Prompt format changes | Pin to SGLang's prompt format version 1 and only change it together with SGLang. Document the version on the docs page. |
| Per-request cache salt | Off by default so identical states reuse the prefix across requests. Offer it as an option for tenant isolation, knowing that salting every request turns that reuse off. Dynamo already forwards `cache_salt`. |
| `GET /v1/models` format | Leave Dynamo's OpenAI list as is. The TypeSafe catalog format stays provider-specific. |
| Choice debiasing by default | Single pass in v1, like SGLang. K cyclic shifts behind a flag in v1.1. |

## Implementation plan

1. SGLang backend: pass `logprob_token_ids` through as `token_ids_logprob` and parse the response, with tests, including one with speculative decoding on. This is useful even without System One.
2. Protocol and scoring in Rust (`lib/llm/src/protocols/systemone/`): types, prompt builder, label tokenization, softmax scoring. Unit tests use TypeSafe's documented examples (the score example must give 0.92) and prompt, label and answer vectors generated from SGLang's route for the same inputs.
3. Handler, flag, route, metrics and docs, tested on the vLLM backend. This covers rendering once, token-ID branches, placement and pinning, chunking above 128 labels, the deadline, reasoning checks, and a per-request prefix cache hit ratio (`cached_tokens` / `prompt_tokens`) so prefix reuse can be monitored. Acceptance is measured on JevBench's 231 items, with the same dense model and chat template served by Dynamo and by SGLang's route:
   - identical prompt tokens and label IDs;
   - with the SGLang backend from PR 1, the same chosen option and probabilities within 0.01;
   - with the vLLM backend, the same chosen option on at least 99% of items and a JevBench score within run-to-run noise, since the two engines' kernels differ numerically;
   - the official SDKs work with only the base URL changed, and `jevcompat` passes its MUST checks.
4. Optional: permutation debiasing and calibration knobs (prior, temperature), off by default.

PRs follow the contribution guide (DCO sign-off, Apache-2.0 SPDX headers), and recipes follow `recipes/CONTRIBUTING.md`.

## Future work

Some System One models are not chat models. They use an encoder with small trained heads and answer from embeddings rather than label logprobs, which is less accurate but much faster. Serving them needs a different engine path (an embedding worker plus a component running the heads), so they are out of scope here and could be covered by a separate DEP. Nothing in this DEP blocks that. The handler already resolves `model` to a served model, so a later DEP can register those models and forward their requests while reusing the wire protocol, validation, error formats and test vectors defined here.

### MorrisZJ · 2026-09-26

@walkoss Hey, AnyJev author here — saw the DEP cites it, so a couple of things we ran into building the same thing that might save you a round trip on steps 3 and 8.

**Step 8, the K-shift mean.** Go with the geometric mean (i.e. average in log space, then renormalise), not the plain average of probabilities. If position bias is additive in logit space, the log-space mean cancels it exactly and the result no longer depends on how the client ordered the options; the probability-space mean only survives cyclic rotations. Numbers at K=20 on Qwen3-8B / Qwen2.5-7B / Qwen3-30B-A3B: reversing the option list flips 13–24% of single-pass answers, 7–17% after the K-shift mean, zero labels ([table](https://github.com/nokia-applied-research/AnyJev/blob/72d07ca/docs/results_bench.md)). So "off by default because it changes the answers" is exactly right — the answers it changes are the ones that were order-dependent to begin with.

**"Cheap once the prefix is cached"** — true on the generate path. We measured L0 at K=20 on a ~1000-token state dropping from 19.5× to 5.5× a single pass once vLLM 0.7.0's prefix caching was on. One thing for the future-work section though: on vLLM's *embed* path (`--task embed`, which is how you'd serve encoder-style decision models) prefix caching does nothing in 0.7.0 — we got 1.01–1.06× for the identical long prompt sent twice, vs 1.86–2.37× on generate. Bit us, so flagging it.

**Step 3, two-letter labels.** Might be worth validating per model card that every label is a single token. `AA`–`ZZ` are one token for some pairs and two for others in the Qwen and Llama vocabs, and a two-token label just reads the wrong logit, no error. That's the whole reason we still cap at 26.

If a v1.1 PR for the K-shift path would be useful, happy to send one, parity script against transformers included. 



### IRONICBo · 2026-09-26

On the cache-salt question, a stable salt derived from the authenticated tenant or principal seems safer than either global reuse or per-request salting: it preserves prefix reuse within a tenant while preventing cross-tenant reuse and timing leakage for sensitive state. Jev Social can send evidence from a logged-in browser as state, so I’d include a two-tenant test proving identical prefixes never report shared cached tokens across auth boundaries.
