# [PR #15288] feat(trtllm-sidecar): forward data-URI images to TensorRT-LLM

## 正文

#### Overview

The TensorRT-LLM sidecar now accepts image requests from the Rust preprocessor. Before this change, the sidecar rejected every image request with HTTP 400, although TensorRT-LLM's gRPC `GenerateRequest` has a field for image bytes (`MultimodalInput.image_data`). The sidecar now decodes each base64 data URI and sends the image bytes to TensorRT-LLM in request order. TensorRT-LLM decodes and processes the images.

**Repro**

```bash
./lib/sidecar/trtllm/launch/agg.sh --model Qwen/Qwen3-VL-2B-Instruct

IMG=$(base64 -w0 cat.jpg)
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "Qwen/Qwen3-VL-2B-Instruct",
  "max_tokens": 48,
  "messages": [{"role": "user", "content": [
    {"type": "text", "text": "Describe this image in one sentence."},
    {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,'"$IMG"'"}}
  ]}]
}'
```

**Before**

```
HTTP 400
{"message":"Invalid request","type":"Bad Request","code":400}
```

The sidecar log shows the cause: `multimodal requests are not supported by the TensorRT-LLM sidecar`.

**After**

```
HTTP 200
"content": "A grey tabby cat with striking yellow eyes is comfortably resting on a white laptop, its paws gently draped over the keyboard, creating a peaceful and relaxed scene."
```

A request with two images gets one correct description for each image, in request order. Text requests do not change.

An image URL that the sidecar cannot use now gets a 400 that tells the client why:

```
HTTP 400
{"message":"the TensorRT-LLM sidecar cannot fetch image URLs; send images as base64 data URIs","type":"Bad Request","code":400}
```

#### Details

Image requests to the TensorRT-LLM sidecar returned HTTP 400. TensorRT-LLM's gRPC `GenerateRequest` has a field for image bytes (`MultimodalInput.image_data`), but the request converter did not map media to it. The converter rejected each request that carried media. It also rejected each request that carried `mm_routing_info`, which the frontend attaches to image requests when multimodal routing is compiled in, as in the container builds.

This change maps each `image_url` item to `MultimodalInput.image_data`, in request order. The sidecar accepts base64 data URIs (`data:<type>;base64,<data>`). It percent-decodes the payload and then decodes the base64 data. It does not check the media type, because TensorRT-LLM identifies the image format from the bytes. The sidecar now ignores `mm_routing_info`, because the engine does not use routing data.

Before the RPC, the sidecar rejects the inputs that TensorRT-LLM cannot take: video and audio, UUID-only media, media that the frontend decoded, data URIs that do not decode, and image options in `mm_processor_kwargs` or `media_io_kwargs`. The gRPC request has no field for image options, so TensorRT-LLM would silently use its defaults. Each new image refusal has a fixed public message, so the client gets the reason instead of `Invalid request`. Decoder detail stays in the private error message.

Limits:

- The sidecar refuses `http://` and `https://` image URLs. The current proto takes image bytes only.
- For an image request, `usage.prompt_tokens` counts the prompt before image expansion, because TensorRT-LLM's gRPC service reports the token IDs that it received. This is an upstream limit. For the same reason, when the client omits `max_tokens`, the sidecar's default is an upper bound, and TensorRT-LLM reduces it to fit the expanded prompt.
- TensorRT-LLM does not report whether the model accepts images. An image request to a text-only model, or image bytes that TensorRT-LLM cannot decode, fails with an internal error.

Next: image URL fetch comes with the OpenEngine proto change in #14349. That PR should merge after this one.
