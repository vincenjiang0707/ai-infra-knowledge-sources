## Describe the bug

Case-level follow-up to #13383 and its [earlier validation report](https://github.com/ai-dynamo/dynamo/issues/13383#issuecomment-5594559029). This issue tracks **`vllm-omni-audio-agg`** specifically so the corresponding local workflow and Kubernetes translation can have explicit pass/fail acceptance criteria.

On matched public Dynamo **1.4.2** images, startup/model discovery succeed, but `POST /v1/audio/speech` returns only the initial **0.08-second silent WAV chunk** even though the worker generates later non-silent audio.

**Release-specific scope:** #12100 already merged speech-streaming work. This is a 1.4.2 qualification/backport/support-boundary report, **not** a claim that current `main` still lacks that change.

## Expected behavior

A complete WAV containing the requested utterance, or a correctly implemented streaming response preserving all audio chunks. The returned waveform must not consist solely of an initial silent chunk.

## Actual behavior

- HTTP **200**, `Content-Type: audio/wav`.
- Exactly **3,884 bytes**, mono 16-bit PCM, 24 kHz, 1,920 frames: **0.08 s**.
- RMS **0**, peak **0**, **0 nonzero samples**.
- SHA-256 `056e096196265b3e34608224a2e81e7c607daf5cadb366f5cd84d00c302b3350`, identical to the earlier failed run.
- For that same HTTP request, worker logs record three WAV chunks:

  ```text
  1920 samples, sr=24000, 3884 bytes wav
  48000 samples, sr=24000, 96044 bytes wav
  40320 samples, sr=24000, 80684 bytes wav
  ```

  That is 3.76 s of encoded worker output, but only the first 0.08 s reaches the HTTP caller.

A separate direct-to-worker request captured all three chunks: 0.08 s silent, 2.00 s non-silent, 0.72 s non-silent (2.80 s total). Its first chunk is byte-identical to the HTTP output. This proves subsequent worker audio exists; **it is not an end-to-end HTTP pass or a listening/transcription claim**.

**Important correction to the earlier umbrella report:** raw WAV is the intended frontend response here, even with `data_source=b64_json`. The absence of a JSON/base64 envelope is not the bug. Selecting only the first WAV is.

## Diagnosis and suggested scope

The [1.4.2 frontend speech handler](https://github.com/ai-dynamo/dynamo/blob/v1.4.2/lib/llm/src/http/service/openai.rs) folds the response stream, then selects `response.data.first()` and decodes only that item's base64 into the HTTP body. The [audio aggregator](https://github.com/ai-dynamo/dynamo/blob/v1.4.2/lib/llm/src/protocols/openai/audios/aggregator.rs) extends the data list; it does not concatenate complete waveform payloads into that first entry.

[PR #12100](https://github.com/ai-dynamo/dynamo/pull/12100), commit `a97afd2d51819f88d1033522312137b35feabc9d`, merged speech-streaming/compatibility work. It is present on the tested example branch but is **not an ancestor of tag v1.4.2**. Include the appropriate frontend and worker changes in matched images, then rerun this case. If backporting is not appropriate, explicitly document which image/release revision is required rather than marking the stock 1.4.2 DGD as working.

This is **not a missing CLI flag**: `--trust-remote-code`, `--enforce-eager`, and `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` were already aligned with the launcher and present in the tested deployment.

## Verified fixed with matched August 26 nightly images

Retested the exact request in this issue on **September 18, 2026 UTC**, using one H100 worker and the existing **Dynamo platform/chart and operator 1.4.2**, without upgrading Helm or the operator.

### Tested image and version boundary

- Frontend: `nvcr.io/nvidia/ai-dynamo/dynamo-frontend-nightly:20260826-27f09d5`
- Worker: `nvcr.io/nvidia/ai-dynamo/vllm-runtime-nightly:20260826-27f09d5`
- Both `ai-dynamo` and `ai-dynamo-runtime`: **1.5.0.dev20260826**.
- Worker backend versions: **vLLM 0.27.1**, **vLLM-Omni 0.27.0rc1**.
- Both DGD components used `runtimeVersionOverride: "1.5.0"`, since dated nightly tags are not semantic-version tags. This describes the runtime, not the operator.

The build's source commit, `27f09d5bcdcf333aa1a74b73245b2ccaff23f91c`, contains #12100 (`a97afd2d51819f88d1033522312137b35feabc9d`). Both running pod image IDs were checked against the registry digests.

### End-to-end result

The DGD reached Ready, `/v1/models` listed `Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice`, and both pods stayed healthy with zero restarts. Three identical `POST /v1/audio/speech` requests returned HTTP 200 with raw `audio/wav`:

```json
{
  "input": "Hey, this is generated using NVIDIA Dynamo.",
  "model": "Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice",
  "voice": "vivian",
  "language": "English",
  "data_source": "b64_json",
  "response_format": "wav"
}
```

| Trial | Response bytes | Audio duration | Nonzero PCM samples | RMS (PCM16) |
|---|---:|---:|---:|---:|
| 1 | 176,684 | 3.68 s | 85,347 | 2750.80 |
| 2 | 153,644 | 3.20 s | 73,339 | 3090.33 |
| 3 | 157,484 | 3.28 s | 76,519 | 3858.00 |

All three outputs were 24 kHz mono PCM16 with a single RIFF header. The initial 80 ms was still silent, **but the HTTP response continued with the later non-silent audio**. The reported 3,884-byte / 80-ms-only failure did not reproduce. Streaming response bytes were retained unchanged; file-playback copies only finalized the open-ended WAV lengths, with PCM byte identity verified. This is waveform/framing validation, not a listening/transcription claim or a performance benchmark.

The portable audio DGD is now included in #14660, with both tested image references, package versions, the runtime override, and the 1.4.2 limitation documented inline. Temporary test resources were removed after capture; the existing shared platform was unchanged.

**Closing as fixed by #12100 and verified with the matched images above. Stock 1.4.2 frontend/worker images remain affected; this is not a 1.4.x backport claim, and updating only the worker image is not the validated configuration.** The mixed-version check applies to this one-frontend/one-worker audio template, not every 1.5 feature.
