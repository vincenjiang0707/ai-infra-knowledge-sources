## 正文

## Overview:

Short mocker sleeps can occasionally wake about one second late on macOS, while Linux normally uses a different timer backend. This change adds controls and measurements for investigating that delay without changing the default behavior.

## Summary

`DYN_MOCKER_SLEEP_BACKEND` selects the platform default, Linux `timerfd`, or Tokio's time driver. Timerfd creation and completion failures fall back to the time driver. `DYN_MOCKER_SLEEP_DRIFT` records requested and actual wake times and periodically logs per-backend summaries. `DYN_FPM_HEARTBEAT_INTERVAL_MS` can vary the Rust direct publisher's one-second heartbeat, and the Python bindings expose an optional `tokio-console` feature.

The environment variables and console feature are off by default. Platform-default selection is checked through `SleepBackend::Auto.resolve()`. The Linux measured-`Auto` test explicitly checks the Tokio test fixture; separate timerfd fixtures exercise the real Linux backend. The measured sleeps use 20 ms deadlines, and the short-sleep regression test retains its 200 ms drift limit. This change provides diagnostics; it does not claim to fix or reproduce the macOS delay.

## Details:

Test-image dependencies explicitly pin `networkx==3.6.1`, required when router benchmark tests are collected across the workspace.

DGDR deployment tests now pass the runtime semantic version explicitly for SHA-tagged planner images, satisfying the admission webhook requirement.

The queued-selection overlap test waits for the scheduler to apply worker registration before creating explicit reservations, removing a setup race observed in remote CI.

# Plan — DYN-4051: ~1 s Tokio wake delay in the Dynamo mocker

Route: implementation

Template: debug-investigation

Engine: vllm

## User intent

The caller reports that the Dynamo mocker, running on macOS, occasionally takes
about a second to wake from a sleep that was scheduled for a few milliseconds.
The distribution is bimodal: the bulk of wakes land where they should, and a
separate mode sits at roughly 1000 ms. An external notification arriving on an
unrelated 100 ms cadence made the peak move to ~100 ms, which is the signature
of a wake that is riding somebody else's timer rather than its own. The reporter
could not reproduce it with a standalone Tokio program.

The caller asks three specific questions, and the plan is organized around
answering them rather than around producing a narrative:

1. Does changing the forward-pass-metrics (fpm) timer interval move the
   anomalous 1000 ms peak? If it does, the mocker's short sleeps are being
   coalesced onto that timer.
2. Can `tokio-console` be used to see what the Tokio side is doing during the
   stall?
3. Can we distinguish a *timer-driver* failure (the runtime is parked and the
   deadline is simply not honored) from *runtime-worker starvation* (the timer
   fired on time and no worker was free to poll the task)?

Underneath those three, the caller wants the investigation to leave behind
something committable — instrumentation and a regression fixture — not a prose
incident report.

## Non-goals

- Not shipping a speculative fix for the macOS stall. Nothing read in discovery
  identifies a specific defect with enough confidence to patch it, and guessing
  at a one-line change in a timer path is how a real bug gets buried under a
  plausible-looking commit.
- Not claiming an in-sandbox reproduction of the macOS symptom. See
  "The reproduction constraint" below; this is load-bearing and is stated as a
  limit, not worked around.
- Not touching the vLLM, SGLang, or TensorRT-LLM engine paths. The fpm heartbeat
  has a Python mirror in `components/src/dynamo/vllm/instrumented_scheduler.py`;
  this work item deliberately leaves that file alone (see Rejected alternatives).
- Not changing default runtime behavior. Every knob added is opt-in and the
  default path must be byte-for-byte the behavior on `main` today.
- Not re-litigating merged PR #13352. It is on `main` and is respected as the

## Chosen approach

Discovery did not find a defect to patch, and the debug-investigation template is
explicit that a no-change incident report is not a deliverable. So the diff is
the smallest set of changes that makes the caller's three questions *answerable*
on the reporter's own machine, and that leaves behind a test which fails if
someone breaks the mechanism later. Four pieces, all opt-in, default behavior
unchanged:

1. **A sleep-backend selector in `lib/mocker/src/common/utils.rs`.** Replace the
   bare `#[cfg]` fork with an enum — `Auto`, `Timerfd`, `TimeDriver` — resolved
   once from `DYN_MOCKER_SLEEP_BACKEND`. `Auto` is the default and reproduces
   today's behavior exactly: timerfd on Linux, time driver elsewhere. The point
   is `TimeDriver`, which makes the macOS code path *reachable and testable on
   Linux*. This is what turns H2 from an untestable assertion into an
   experiment, and it is the difference between an investigation that ships a
   test and one that ships a paragraph.
2. **Sleep-drift instrumentation.** `sleep_until_precise` records requested
   versus actual wake, labelled by the backend that served it, into a histogram
   whose buckets straddle both modes (single-digit ms through 2 s). Recording is
   gated on a process-level `Lazy<bool>` read from `DYN_MOCKER_SLEEP_DRIFT`, so
   the default cost is one relaxed load, not a `Instant::now()` per pass
   boundary at high speedup ratios. Bucket boundaries mirror the existing
   `EVENT_LOOP_DELAY_SECONDS` canary so the two are readable side by side.
3. **An env-configurable fpm idle heartbeat.** `IDLE_HEARTBEAT_INTERVAL` in
   `lib/llm/src/fpm_publisher.rs` becomes a default rather than a constant,
   overridable by `DYN_FPM_HEARTBEAT_INTERVAL_MS` (name registered in
   `lib/runtime/src/config/environment_names.rs` alongside the existing
   `DYN_*` entries). This exists solely to make H1's ablation a restart rather
   than a rebuild — the reporter should be able to answer ask #1 in a minute,
   not an hour. The comment asserting parity with Python's `HEARTBEAT_INTERVAL`
   is updated to say the *default* matches and the override is Rust-side.
4. **A `tokio-console` feature passthrough in `lib/bindings/python/Cargo.toml`**
   (`tokio-console = ["dynamo-runtime/tokio-console"]`), off by default. This is
   the whole of what stands between the reporter and ask #2, since
   `tokio_unstable` is already set repo-wide and the feature already exists in
   `dynamo-runtime`. The plan states the cost plainly rather than selling it: a
   console build loses the normal logging stack and adds `tokio/tracing`
   overhead, so numbers taken under console are for topology, not for timing.

For ask #3, nothing new is needed beyond wiring: the plan directs the reporter to
`DYN_ENABLE_POLL_HISTOGRAM` plus the existing `worker_park_count` /
`worker_mean_poll_time` / queue-depth exports, which discriminate H4 from H1/H2
with code that is already on `main`.

**Parameter shape.** Every knob here is optional and read from the environment
rather than threaded through a signature. `sleep_until_precise` keeps its
existing `(deadline: Instant)` signature, so none of its call sites in
`generalized_live.rs` change and no crate outside `lib/mocker` is disturbed. The
fpm interval is resolved inside the publisher rather than added as a parameter to
its constructor, for the same reason. If a required parameter had been added
instead, callers in crates not opened here would have had to change;
`cargo check --workspace --all-targets` under Recipe 2 is what proves this
choice actually held.

## Regression fixture and negative control

**The fixture (must fail for the original behavior).** In `lib/mocker`, a
`#[tokio::test(flavor = "multi_thread", worker_threads = 2)]` arms a 1 s timer —
standing in for the fpm heartbeat — concurrently with a `sleep_until_precise`
whose deadline is 2 ms out, with the backend forced to `TimeDriver`. It asserts
two things: that the backend actually used was the one requested (readable from
the drift record's backend label), and that observed drift stayed under 200 ms.
That bound is chosen deliberately: roughly two orders of magnitude above
scheduling noise on a loaded CI box, and five times below the 1000 ms mode under
investigation, so it separates the two regimes without being a flake generator.

This is not tautological, and the printer records the proof under the same recipe
id: with the selector stubbed to ignore the requested backend — the pre-change
behavior, where the `#[cfg]` decides and nothing else can — the first assertion

## Ask #1 — is the 1 s FPM idle heartbeat implicated?

The mocker worker starts one FPM idle-heartbeat task per dp_rank, at a 1 s period
by default (`lib/llm/src/mocker.rs:465` constructs `FpmDirectPublisher`;

timer, pushing its period out should move or remove the mode. This is the
ablation.

Interpretation: if the ~1 s mode is present in the baseline and gone (or moved to
~60 s) in the ablation, the FPM heartbeat's timer is implicated. If it is present
in both, it is not.

Names verified: `DYN_FPM_HEARTBEAT_INTERVAL_MS`, `DYN_MOCKER_SLEEP_DRIFT`, and
`DYN_MOCKER_SLEEP_BACKEND` are all registered in
`lib/runtime/src/config/environment_names.rs`; `--discovery-backend file` is a
real choice in `components/src/dynamo/mocker/args.py:592-596` (choices are
`kubernetes`, `etcd`, `file`, `mem`), and using it avoids needing etcd running.

Three caveats, all from source:

- **Accepted range is 1–300000 ms.** Above 300 s the value is rejected with a
  warning and the 1 s default is kept (`MAX_IDLE_HEARTBEAT_INTERVAL`,
  `lib/llm/src/fpm_publisher.rs:50`). `60000` is well inside the range; do not
  reach for `999999999` expecting it to take.
- **This is an ablation, not a setting to keep.** At 60 s the FPM stream goes
  quiet for a minute at a time, so anything consuming forward-pass metrics
  (planner, KV router load signals) sees stale data. Unset it afterwards.
- **It reaches the Rust direct publisher only.** It does not reach
  `FpmEventRelay` (which has no periodic timer at all) and it does not reach the
  vLLM path's Python heartbeat, `_FpmPublisherThread.HEARTBEAT_INTERVAL = 1.0` in
  `components/src/dynamo/vllm/instrumented_scheduler.py:1354`. If your repro is a
  vLLM worker rather than the mocker, this variable will do nothing and the 1 s
  timer you are chasing is that Python constant.

While you are here, the second lever this branch adds is the backend selector.
`DYN_MOCKER_SLEEP_BACKEND=time_driver` forces the pure-Tokio time-driver path even
on Linux, and `=timerfd` forces the timerfd path; `auto` (the default) is the
previous platform behavior. On macOS `auto` already means the time driver, so the
useful comparison there is a drift histogram with the sleep accounting on, not a
backend swap.

## Ask #3 — `worker_park_count` and the poll histogram

Both live behind the Tokio performance metrics in
`lib/runtime/src/metrics/tokio_perf.rs`. The important structural fact, verified
by grep: the sampling loop `tokio_metrics_and_canary_loop` and the registration
call `ensure_tokio_perf_metrics_registered_prometheus` have callers **only** in
`lib/llm/src/http/service/service_v2.rs` (`:868`, `:927`, `:1215`) — that is, the
HTTP **frontend**. There is no `dynamo_tokio_*` series on a mocker worker process,
however you configure it. Read these from the frontend.

```bash

python -m dynamo.frontend \
  --discovery-backend file \
  --http-port 8000
```

```bash
# Terminal 4 — read the series
curl -s localhost:8000/metrics | grep -E '^dynamo_tokio_|^dynamo_frontend_event_loop_'
```

Two prefixes, which is easy to get wrong: the per-worker runtime series are
`dynamo_tokio_*` (`name_prefix::TOKIO`), but the event-loop canary is
`dynamo_frontend_*` (`name_prefix::FRONTEND`, applied at `tokio_perf.rs:138-160`).
The series exported:

- `dynamo_tokio_worker_park_count_total{worker="N"}` — ask #3's counter. Sampled
  once a second as a delta into a Prometheus counter, so scrape twice and
  subtract, or use `rate()`.
- `dynamo_tokio_worker_mean_poll_time_ns{worker="N"}`
- `dynamo_tokio_worker_busy_ratio{worker="N"}`
- `dynamo_tokio_worker_local_queue_depth{worker="N"}`,
  `dynamo_tokio_worker_steal_count_total{worker="N"}`,
  `dynamo_tokio_worker_overflow_count_total{worker="N"}`
- `dynamo_tokio_global_queue_depth`, `dynamo_tokio_alive_tasks`,
  `dynamo_tokio_budget_forced_yield_total`,
  `dynamo_tokio_blocking_threads` / `_blocking_idle_threads` / `_blocking_queue_depth`
- `dynamo_frontend_event_loop_delay_seconds` — a 10 ms canary histogram whose
  bucket bounds are `[0.0, 0.001, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0]`,
  the same ten the mocker drift histogram reuses (plus 1.5 and 2.0), so the two are
  directly comparable — and `dynamo_frontend_event_loop_stall_total`, incremented
  when that delay exceeds 5 ms.

`DYN_ENABLE_POLL_HISTOGRAM` is read at runtime construction
(`lib/runtime/src/config.rs:368-385`): when truthy it calls
`builder.enable_metrics_poll_time_histogram()` and logs a warning that the code
itself states — expect roughly 2× `Instant::now()` overhead per task poll. Set it
in the process whose runtime you want instrumented, and leave it off for any run
whose timings you intend to quote as a baseline.

Do **not** reach for `DYN_SYSTEM_ENABLED` to get a `/metrics` endpoint on the
worker for this: it is marked deprecated in `environment_names.rs`, and it would
not help anyway, because nothing registers or samples the Tokio series outside the
frontend.
