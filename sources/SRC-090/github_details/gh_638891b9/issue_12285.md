# [Issue #12285] Delay Anthropic tool_use content_block_stop until streamed arguments are complete JSON

source: https://github.com/ai-dynamo/dynamo/issues/12285
state: closed | updated: 2026-09-22T04:48:41Z
labels: bug, language::rust, frontend

## 正文

## Summary

When converting OpenAI-style streamed tool calls to Anthropic Messages SSE, Dynamo should not emit `content_block_stop` for a `tool_use` block until the accumulated `input_json_delta` fragments form complete JSON.

Some Anthropic clients treat `content_block_stop` as the point where the tool input is final. If Dynamo sends the stop event while the accumulated input is still incomplete, clients can discard trailing fragments or observe `{}` / malformed tool input.

## Desired behavior

For a streamed tool call whose arguments arrive in fragments:

```text
delta 1: id=call_1, name=read_file, arguments=""
delta 2: arguments="{\"path\":"
delta 3: arguments="\"/tmp/example.txt\"}"
finish_reason: tool_calls
```

the Anthropic stream should emit:

```text
content_block_start tool_use input={}
content_block_delta input_json_delta partial_json=""
content_block_delta input_json_delta partial_json="{\"path\":"
content_block_delta input_json_delta partial_json="\"/tmp/example.txt\"}"
content_block_stop
```

but should not emit `content_block_stop` after only deltas 1 and 2, because the accumulated arguments are not complete JSON yet.

## Repro shape

Use synthetic tool names and dummy paths only. No customer prompt, model output, file contents, request IDs, API keys, URLs, or tenant/model identifiers are needed.

Suggested unit coverage:

1. Feed a tool-call stream where `finish_reason=tool_calls` arrives before the accumulated arguments parse as JSON.
2. Assert Dynamo does not emit `content_block_stop` for that `tool_use` yet.
3. Feed the final argument fragment.
4. Assert the converter emits the stop event after the accumulated JSON parses successfully.

Confirm, yes this is needed MF

### ayaangazali · 2026-08-21

This looks already fixed on `main`, and I think the version you saw it on explains the gap.

The Anthropic converter no longer emits tool events as they arrive. `record_tool_call` buffers the whole `tool_use` block, and `append_buffered_tool_events` drains it only on a tool-call finish reason, with EOF as the fallback for backends that omit one. Because `content_block_start`, every `input_json_delta`, and `content_block_stop` are drained together, a stop cannot be emitted after only deltas 1 and 2 — nothing at all is emitted at that point.

`test_fragmented_tool_arguments_flush_on_tool_calls_finish` in `lib/llm/src/protocols/anthropic/stream_converter.rs` is your repro almost exactly, down to the split point: `arguments=""`, then `{"path":"/tmp`, then `"}`. It asserts each intermediate chunk produces no events, then that the finish chunk produces

```
content_block_start, content_block_delta, content_block_delta, content_block_delta, content_block_stop
```

which is the desired sequence in your description.

I ran it on current `main` (`d023c6af5`) rather than only reading it: `cargo test -p dynamo-llm --lib --no-default-features anthropic::stream_converter` gives 18 passed, 0 failed, including that test and `test_parallel_tool_calls_flush_sequentially_on_finish`.

The buffering came in with #10988 on 2026-06-30. That lands after v1.3.1 and before v1.4.0, which I checked with `git merge-base --is-ancestor 370dc707f v1.3.1` (not an ancestor) and against `v1.4.0` (ancestor). So on 1.3.x the old emit-as-you-go behaviour is exactly what you describe, and on v1.4.0 or newer it should be gone. If you were on 1.3.x when you filed, that fits.

One part of your suggested coverage is genuinely not implemented, and I did not want to gloss over it: a `finish_reason` that arrives while the accumulated arguments still do not parse as JSON. Today the converter treats the finish reason as the completeness signal and flushes anyway, and the comment above the flush says so deliberately. Holding the block until the JSON parses would need an answer for the case where it never does, since a truncated tool call would otherwise never close. That is a separate design call rather than a bug, so I have not touched it. Happy to open a focused issue for it if you think it is worth pinning, but I would rather not assume.

If you can still reproduce this on v1.4.0 or later, say so and I will dig further — there may be a path through the converter that the test does not cover.
