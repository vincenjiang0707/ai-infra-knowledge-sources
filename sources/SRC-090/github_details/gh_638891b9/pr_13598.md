## 正文

Overview:

Adds `tests/frontend/test_request_tracing_logs_native_preprocessor.py`, the engine-native preprocessor (`--dyn-chat-processor vllm`) counterpart to `test_request_tracing_logs.py` (which covers the default Rust preprocessor).

## Details

Under topology 2, the vLLM-native chat processor runs in the frontend and re-enters Rust through PyO3. The tracing "current span" is task-local and is **not** inherited by a fresh pyo3 tokio task, so the downstream `kv_router.route_request` span can be minted on a new trace_id — silently disconnecting the router spans from the request trace. `RoutedEngine` guards against this by rebuilding a span from the carried context and instrumenting the re-entry future (`dispatch_span` in `routed_engine.rs`).

The default Rust preprocessor path is all-Rust / same async task, so it inherits the trace for free and never exercises this boundary — hence existing tracing tests do not cover it. This test is the regression guard: it sends a request with a W3C `traceparent` and asserts both the frontend `http-request` span and the downstream `kv_router.route_request` span carry the same inbound `trace_id`.

The assertion is intentionally **unfiltered** (it does not pre-filter by request-id/trace-id) so a disconnected `route_request` span on a different trace would be caught rather than hidden.

## Where should the reviewer start?

`122-124`: _🩺 Stability & Availability_ | _🔵 Trivial_ | _⚡ Quick win_

**Poll for the expected spans instead of sleeping for a fixed 1 second.**

The frontend writes spans asynchronously. If the flush takes longer than 1 second on a loaded CI runner, `route_traces` is empty and the test fails at Line 147 with a message that points at chat-processor or router misconfiguration instead of the real cause. A bounded poll on the log content removes that race and keeps the failure message accurate.
