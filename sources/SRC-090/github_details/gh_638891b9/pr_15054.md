# [PR #15054] fix(llm): coalesce duplicate-index entries in streaming chat chunks

state: open | updated: 2026-09-24T19:44:03Z

## 正文

## Overview

A streaming chat chunk leaving the tool-calling jail can carry **more than one entry for the same index** — either two `choices` entries sharing a choice index, or two `delta.tool_calls` entries sharing a call index. With `n = 1` that is not valid OpenAI streaming, and it silently corrupts tool calls for any client that keys on `index` and keeps one entry per index per chunk.

This normalizes those chunks at the jail boundary adapter.

## The bug

Observed in production against a GLM-4.7-family model served through Dynamo with a forced `tool_choice`. Two shapes appear, both captured from the wire:

```jsonc
// duplicate tool_calls index — an opener beside its own first argument fragment
"tool_calls": [
  {"index":0, "id":"call-4bfb…", "function":{"name":"calculate","arguments":""}},
  {"index":0,                     "function":{"arguments":"{\"expression\": \""}}
]

// duplicate choices index — a final argument fragment beside a bare finish flush
"choices": [
  {"index":0, "delta":{"tool_calls":[{"index":0,"function":{"arguments":"6\"}"}}]}, "finish_reason":null},
  {"index":0, "delta":{"content":""},                                               "finish_reason":null}
]
```

Assembled by iterating **every** entry, the call is complete and correct:

```
{"expression": "123 * 456"}
```

Assembled by keeping the **last** entry per index — a reasonable reading of the spec, since a chunk is not supposed to contain two entries for one index — the final fragment is displaced:

```
{"expression": "123 * 45      ← unparseable
```

The damage is silent. `finish_reason` still reports `tool_calls`, `usage` still accounts for the tokens that produced the full arguments, and no error is raised anywhere. The caller simply receives a tool call whose `arguments` are not valid JSON, mid-value, with nothing in the response indicating truncation.

Measured rate on the affected path: roughly **1 duplicate-`choices` frame per ~120 frames**, about one request in nine. Clean on the same model with `tool_choice: "auto"` (492 frames, zero), and clean on other model families under the same forced `tool_choice` through the same gateway.

## The fix

`OpenAIPreprocessor::coalesce_duplicate_stream_indices`, called on each chunk in the jail boundary adapter in `preprocessor.rs` — the adapter whose documented job is already converting the published `dynamo-parsers` jail output into Dynamo's stream. Per chunk it folds entries sharing an index:

- **choices** — concatenates `content` / `reasoning_content` text, unions `tool_calls`, takes the first `role` / `refusal` / `function_call`, and carries `finish_reason` and `logprobs` onto the merged choice so a flush arriving as a separate entry cannot strand them
- **tool_calls** — takes the first `id` / `type` / `name`, and concatenates `arguments` fragments in arrival order

Normalizing at this boundary keeps the malformed shape off the wire regardless of which `dynamo-parsers` release is pinned, which matters because the jail is a published dependency rather than in-tree.

Non-text `content` variants have no defined concatenation, so the first is kept rather than guessed at.

**Well-formed chunks are untouched.** Both helpers scan for a duplicate index first and return before allocating, so the overwhelmingly common one-entry-per-index chunk takes an allocation-free path.

The regression that matters is `coalesces_duplicate_choice_indices_without_losing_the_final_fragment`.
Its input is the real captured frame from production — a final `arguments` fragment beside a bare
finish flush, both at choice index 0. Before the fix, assembling that stream by keeping the last
entry per index yields `{"expression": "123 * 45` (unparseable); after it, `{"expression": "123 * 456"}`.

**The bug itself was measured in production**, against a GLM-4.7-family model with
`tool_choice: "required"`, 40 streaming requests:

| | |
|---|---|
| frames with duplicate `choices` index | 16 |
| requests whose tool call was corrupted | **16 / 40** |
| valid JSON when assembling `choices[0]` | **40 / 40** |
| valid JSON when assembling `choices[-1]` | 24 / 40 |

Identical bytes on the wire; only the client's assembly strategy differs. That is the evidence the
model emits every call completely and the corruption is purely the duplicate framing. Observed
truncations included `{"expression": "1+`, `{"expression": "2 +`, `{"expression": "1`.

A second `tool_choice: "auto"` control on the same model showed 0 duplicates in 492 frames, and
three other model families showed 0 in 51,795 frames under the same forced `tool_choice` — so the
trigger is specific to this parser path, not general to the gateway or to forced tool choice.

**Verified end-to-end on a live prefill/decode deployment.** A release wheel built from this
branch (`ai_dynamo_runtime` 1.5.0, manylinux_2_39_x86_64) replaced `dynamo/_core.abi3.so` in the
frontend of a 16-worker disaggregated GLM-4.7-family deployment. Same image, same 24 frontend
flags, same discovered workers, same `--dyn-chat-processor dynamo` / `--dyn-tool-call-parser
glm47` path — the only variable is the binary.

Measured against that frontend, 40 identical `tool_choice: "required"` streaming requests before
and after:

| | stock `_core` | patched `_core` |
|---|---|---|
| frames | 719 | 727 |
| frames carrying a duplicate `choices` index | **12** | **0** |
| frames carrying a duplicate `tool_calls` index | **40** | **0** |
| valid JSON assembling `choices[0]` | 40 / 40 | 40 / 40 |
| valid JSON assembling `choices[-1]` | **28 / 40** | **40 / 40** |

An earlier A/B ran a patched frontend *in parallel* with the stock one against the same worker
pool, to rule out the workers as the variable: stock 12 duplicate-choice frames, patched 0.

A 100-request confirmation pass on the patched frontend, validating **each `tool_calls` index
separately** under both assembly strategies:

```
requests 100 | frames 1705
  frames carrying a duplicate choices index    : 0
  frames carrying a duplicate tool_calls index : 0
  every tool call valid JSON via choices[0]    : 100/100
  every tool call valid JSON via choices[-1]   : 100/100
  requests emitting >1 distinct tool call      : 4
```

That last row is the negative control that matters: 4 of the 100 requests legitimately emitted
two separate `calculate` calls at `tool_calls` index 0 and 1. The coalescer left them as two
distinct entries — it merges duplicate indices without collapsing genuine parallel tool calls,
which is what `distinct_tool_call_indices_are_left_alone` asserts at the unit level.

No new `ERROR` lines in the frontend log, and the two `WARN` families present (structural tag
unsupported by the `glm47` parser, migration disabled for guided decoding) are identical to stock.

## Scope and risk

- Affects only chunks that are already malformed; valid chunks return before allocating.
- Confirmed in production traffic shape: 1,705 frames through the patched path with zero
  behavioural change other than the duplicates disappearing.
- Runs unconditionally on the streaming path for every model. That is deliberate — the wire
  contract applies generally and gating on one parser would leave others exposed — but it is the
  main thing worth challenging in review, since the bug was observed on one model family.
- No API, type, or behavioural change for conforming streams.
- Does not address the root cause, which is in the published `dynamo-parsers` jail emitting the duplicates. This is defensive normalization at the boundary — appropriate independently, since the adapter should enforce the wire contract, but a fix in `dynamo-parsers` would be the complete one.

### stu-cao · 2026-09-18

Follow-up commit `1ec795b` addresses three issues found in a self-review after the initial push. Recording the reasoning here because the first is a correctness constraint that isn't obvious from the diff.

**1. The normalization must run *before* the glm47 recovery block, not after.**

That block keys per-choice state on `choice.index` and accumulates `emitted_text`:

```rust
for choice in &mut data.inner.choices {
    let state = recovery.entry(choice.index).or_default();
    ...
    state.emitted_text.push_str(content);
}
```

It assumes one entry per index. On a duplicate-index chunk it runs twice against the same state, so its `strip_prefix(&state.emitted_text)` arithmetic operates on a state the first iteration already advanced — corrupting the truncation bookkeeping on exactly the malformed chunks this PR exists to handle. The original placement left that intact. Normalizing first makes the block's own invariant true.

**2. Chunks that cannot be folded without losing content are now left alone.**

`ChatCompletionMessageContent::Parts` has no defined concatenation. The first version kept one side and dropped the other, which is strictly worse than the malformed-but-intact chunk it replaced. Such chunks now pass through unchanged; `unmergeable_multimodal_content_passes_through_untouched` covers it.

**3. The delta is destructured exhaustively on the merge path.**

`dynamo-protocols` is separately versioned. A field added there should break this build rather than be silently dropped when two entries are folded. Verified against 5.4.1: the struct has six fields and is not `#[non_exhaustive]`, so exhaustive destructuring compiles and will fail loudly on a future addition.

Also worth flagging for reviewers: the duplicate-emitting code is in the published `dynamo-parsers` jail, not in this repo, so this is defensive normalization at the boundary rather than a root-cause fix. A fix in `dynamo-parsers` would be the complete one.
