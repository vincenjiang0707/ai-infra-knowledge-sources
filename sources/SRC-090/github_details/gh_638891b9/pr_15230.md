# [PR #15230] fix(runtime): exit the ingress response pump when the request context is cancelled

source: https://github.com/ai-dynamo/dynamo/pull/15230
state: open | updated: 2026-09-25T01:25:27Z
labels: external-contribution, size/L, fix, trusted-contributor

## 正文

## Problem

`pump_response_stream` awaited `stream.next()` with no cancellation escape, so a response stream that stopped yielding without terminating pinned the work handler for the rest of the process lifetime. `RequestMetricsGuard` never dropped, leaking `dynamo_component_inflight_requests` (and any queue accounting built on the same request lifecycle) until the process restarted.

Observed in production serving under frequent client disconnects with an engine that stopped honoring cancellation: the worker's inflight gauge pinned in the hundreds while the engine idled, most new requests were shed with queue-limit 429s, and a process restart restored serving instantly.

## Fix

Select on the request context's `stopped()`/`killed()` futures alongside `stream.next()` (pinned once outside the loop), with two distinct exits that preserve the existing error-accounting invariants:

- **stopped** (peer-requested stop): return without the complete-final marker. The response-plane reader already tears down on stop and treats a closed stream as a clean end; the caller's existing `reset_on_stop()` handling still sends the QUIC logical reset.
- **killed** (client disconnect, protocol violation, transport read error): break out of the pump but still attempt the complete-final marker, so a peer that is already gone stays a *counted* `publish_final` error rather than a silent teardown. A receiver that is still attached observes a clean terminal frame.

`killed` is checked before `stopped` in the biased select because a killed context also resolves `stopped()`.

## Testing

- `hung_response_stream_exits_on_context_cancellation`: a stream that never wakes the pump must not block it; stop exits without a final frame or health notification, kill still attempts the final and notifies health when the receiver is attached. Also covers cancellation winning over an already-ready EOF.
- `normal_eof_sends_final_and_notifies_health`: clean EOF still sends `complete_final` and notifies endpoint health.
- All pre-existing `push_handler` tests pass unchanged, including the teardown-race suite (`test_publish_final_with_killed_context_is_still_an_error`, `test_publish_final_after_connection_read_error_is_still_an_error`, `test_publish_final_race_with_stopped_context_is_not_an_error`).
