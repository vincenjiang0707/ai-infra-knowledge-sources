## 正文

## Feature request

Update the diffusion documentation and examples so users can deploy every documented diffusion workflow through `DynamoGraphDeployment` (DGD), and make the local launch instructions transparent instead of presenting shell scripts as black boxes.

The operator and runtime are already expressive enough to represent the baseline workflows without a new DGD API or operator-controller change. The documentation should make that explicit and provide v1beta1 DGD examples for:

- Text-to-image
- Text-to-video
- Image-to-video
- Text-to-audio
- Text-to-text diffusion

At least one documented DGD path should exist for each workflow. Suggested baseline paths are:

| Workflow | Suggested DGD path |
|---|---|
| Text-to-image | SGLang FLUX, with vLLM-Omni as an additional example |
| Text-to-video | SGLang Wan or vLLM-Omni; cross-link the existing FastVideo DGD |
| Image-to-video | vLLM-Omni Wan I2V |
| Text-to-audio | vLLM-Omni Qwen3-TTS |
| Text-to-text diffusion | SGLang LLaDA |

### Show the commands behind local launch scripts

The workflow pages and local deployment examples currently show commands such as:

```bash
./launch/image_diffusion.sh
./launch/text-to-video-diffusion.sh
./launch/diffusion_llada.sh
bash examples/backends/vllm/launch/agg_omni_image.sh
```

These are useful convenience wrappers, but they hide the actual topology and backend flags. Each local example should show the expanded commands that the script launches, including:

- `python -m dynamo.frontend`
- The backend entrypoint (`dynamo.sglang`, `dynamo.vllm.omni`, `dynamo.trtllm`, or a custom worker)
- Model and modality flags
- Dynamo endpoint/discovery settings when relevant
- Media-storage configuration
- GPU or tensor-parallel requirements
- Any required environment variables

The script should remain available as the shortest launch path. The example should present it as an optional wrapper and link to the corresponding Recipes/CLI Templates/DGD page for the complete deployment shape.

### Add diffusion DGD documentation and recipes

Add a DGD section to the diffusion overview and each workflow page that covers:

1. A complete `nvidia.com/v1beta1` DGD manifest or a link to a checked-in recipe/template.
2. Frontend and worker component commands.
3. `backendFramework` selection and custom/no-op worker behavior.
4. Kubernetes discovery and the operator-injected Dynamo namespace.
5. Runtime image requirements and whether a stock release image or custom image is required.
6. Hugging Face credentials and model-cache PVC guidance.
7. GPU resources, shared memory, node selection, and multi-GPU requirements.
8. Media storage, public URL rewriting, retention, and cleanup.
9. A port-forward command and endpoint-specific smoke test.
10. A support matrix that distinguishes:
    - Expressible as DGD
    - Checked-in example available
    - Tested configuration
    - Experimental or custom-image requirement

Where practical, use a shared template for the aggregated vLLM-Omni workflows; image, video, I2V, and audio primarily differ by model, `--output-modalities`, resources, and request format.

### Clarify the support boundary

The docs should state that all five workflow types can be expressed as DGDs without operator code changes. They should separately identify the combinations that are not yet turnkey:

- TensorRT-LLM image/video diffusion requires a runtime containing the optional `visual_gen` module and may need a custom image.
- Disaggregated vLLM-Omni GLM-Image needs a multi-component DGD, stage configuration, NIXL connectors, GPU placement, and interconnect validation.
- SGLang image-to-video accepts `input_reference` in the handler, but the referenced launcher does not identify a tested I2V model or provide the promised I2V request example.
- Generated media needs an explicit object-storage or base64 strategy; pod-local `file://` URLs are not usable by remote clients.
- Diffusion-aware Planner/autoscaling behavior and scaling signals remain unvalidated.

### Suggested documentation and example scope

Likely affected areas include:

- `docs/fern/pages/use-cases/diffusion/overview.md`
- `docs/fern/pages/use-cases/diffusion/workflows/`
- SGLang and vLLM-Omni backend example/template pages
- `examples/backends/sglang/launch/`
- `examples/backends/vllm/launch/`
- `examples/diffusers/deploy/`
- New or existing Kubernetes recipe/template directories for diffusion

Acceptance criteria:

- Every workflow has at least one complete DGD path or an explicit explanation of the remaining blocker.
- Local docs display the underlying frontend and worker commands, not only a script invocation.
- Launch scripts remain available and are cross-linked with the relevant recipes/templates.
- Each DGD example includes a working endpoint smoke test.
- Media output guidance avoids presenting pod-local `file://` URLs as remotely retrievable URLs.
- The support matrix clearly separates DGD capability from test coverage and runtime-image availability.

## Describe the problem you're encountering

The current diffusion overview says that built-in diffusion backends use local CLI launch scripts and generally do not ship prebuilt Kubernetes recipes. This can be read as a missing operator capability, even though DGD is modality-agnostic and can run arbitrary frontend and worker commands with Kubernetes discovery.

A concrete v1beta1 SGLang FLUX DGD demonstrates the basic frontend-plus-worker shape. The repository also contains a v1beta1 FastVideo DGD with a custom worker. Source inspection shows that the built-in workers register the model types required by the frontend:

- vLLM-Omni registers image, video, and audio model types from `--output-modalities`.
- SGLang registers image and video generation workers and selects its text diffusion handler from `--dllm-algorithm`.
- The frontend exposes the corresponding image, video, audio, chat, and completion endpoints.

The gap is therefore primarily discoverability, command transparency, and checked-in DGD examples.

The local workflow documentation compounds the problem by showing only shell-script invocations. A user cannot tell from the page which processes are started, which flags are required, which settings belong to the frontend versus the worker, or how to translate the local launch into a DGD.

The existing examples also leave important operational behavior implicit:

- A worker using `--media-output-fs-url file:///...` returns a path local to that worker pod unless base64 output or object storage is configured.
- Generated media has no built-in TTL or garbage collection.
- A model-cache PVC mounted by both frontend and worker can cause a multi-attach failure when it is ReadWriteOnce and the pods land on different nodes; the frontend generally does not need that mount.
- SGLang diffusion compile configuration is not equivalent to passing the same-named LLM parser flag.
- Stock-image versus custom-image requirements are not summarized per backend.

Without DGD examples and expanded commands, users must reverse-engineer the shell scripts and backend source to discover that the operator already supports these deployment shapes.

## Describe alternatives you've tried

- Read every diffusion workflow page and followed the referenced launch scripts into the repository.
- Expanded the SGLang and vLLM-Omni launchers into their underlying frontend and worker commands.
- Inspected the v1beta1 DGD API and operator behavior for custom commands, backend detection, Kubernetes discovery, worker probes, PVCs, and repeated worker components.
- Compared a local SGLang FLUX DGD with the checked-in FastVideo DGD.
- Mapped each workflow to at least one existing backend that can register the required model type through a DGD.

This confirms that separate operator feature work is not required for the baseline aggregated paths. Maintaining private manifests or asking users to infer Kubernetes deployments from shell scripts would duplicate effort and continue to hide supported functionality, so checked-in recipes and documentation are preferable.

### DGD derivation notes

These were intentionally derived as Kubernetes translations of the existing local launchers: `dynamo.frontend` becomes the frontend component, backend commands/flags become worker components, and the model/modality/media settings remain aligned with the scripts. This supports the issue's premise that the baseline workflows are DGD-expressible without a new operator API.

The main exception is GLM-Image disaggregation: the local launcher co-locates processes and can use shared memory, while a DGD places stages in separate pods. The manifests therefore use the NIXL-capable stage config for inter-pod handoff; the NIXL variant additionally enforces cross-node AR/DiT placement.
