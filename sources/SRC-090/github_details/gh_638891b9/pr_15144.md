## 正文

## Summary

Adds a documented channel for custom-modality inputs on the Completions API, for models that register their own vLLM multimodal processor.

Today a completion request has no field that can carry them, and no existing field can be repurposed:

- **An unrecognized top-level field never reaches the worker.** By default it is rejected at admission — `Unsupported parameter(s): \`multi_modal_data\`` — unless it is one of the six named `PASSTHROUGH_EXTRA_FIELDS`. With `DYN_IGNORE_OPENAI_FE_UNSUPPORTED_FIELDS` set it is dropped instead of rejected. Either way the payload is gone before preprocessing.
- **`multi_modal_data` on the internal wire is frontend-owned.** `MultimodalDataMap`'s variants (`Url | RawUrl | Decoded(RdmaMediaDataDescriptor)`) are produced by the preprocessor from chat content parts; it is not a client-writable request field on either endpoint.
- **`prompt_embeds` replaces the entire prompt**, so it cannot express "text plus one custom modality" — the client would have to own the LM embedding table.
- **`mm_processor_kwargs` is chat-only.** `NvCreateCompletionRequest` does not implement `OAIChatLikeRequest::mm_processor_kwargs`, so it resolves to the trait default `None` and the completions operator never reads it. Even on chat it would be insufficient alone: vLLM runs the multimodal processor only when `multi_modal_data` is non-empty.

### What changes

- **`NvCreateCompletionRequest.multi_modal_data`** — a typed, JSON-safe `map<string, any>` the frontend admits but never interprets. The key matches the engine-side name the payload is installed under.
- **`PreprocessedRequest.backend_multi_modal_data`** — the frontend-to-worker wire field. Deliberately *not* `multi_modal_data`: keeping them separate is what lets the worker tell "media the frontend already resolved" from "a payload only the engine's processor understands".
- **vLLM worker** installs the payload as the engine's `multi_modal_data`; the registered modality processor owns all value validation.

```bash
curl http://localhost:8000/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<model>",
    "prompt": [1, 2, 3],
    "max_tokens": 16,
    "multi_modal_data": {
      "custom_input": {"dtype": "float32-le", "shape": [2, 4], "data_base64": "AAAAAA=="}
    }
  }'
```

### Fail-closed behavior

A silently ignored payload returns a plausible text-only answer, which is the worst outcome available. Every path that cannot install it rejects the request instead:

| Path | Behavior |
|---|---|
| vLLM, aggregated | Installs the payload |
| vLLM, disaggregated — generic models | Prefill installs it; decode continues from `expanded_prompt_token_ids` |
| vLLM, disaggregated — geometry-handoff families | Rejected |
| vLLM, text-in-text-out (`--use-vllm-tokenizer`) | Rejected |
| SGLang, TensorRT-LLM | Rejected |

Disaggregation works for models whose decode leg continues from the prefill worker's expanded prompt token IDs — the same generic handoff every model without a family-specific decode contract already uses. Families that rebuild position IDs from modality geometry (Qwen-VL rebuilds mRoPE from `image_grid_thw`) refuse the payload: Dynamo cannot derive that handoff from something it does not interpret, and generating against wrong positions is worse than failing.

The backend rejections reuse the existing `reject_unsupported_multimodal_uuids` capability-guard pattern, at the same six call sites.

### Frontend validation

The frontend enforces only the invariants a backend cannot recover from, and leaves the values alone:

- **Empty map rejected** — it carries no payload and would otherwise trip the worker's multimodal opt-in check.
- **`prompt_embeds` combination rejected** — that replaces the whole prompt, leaving no placeholder sequence for a processor to expand.
- **Batched prompt rejected** — the HTTP batch path clones the whole request per prompt, so one payload would be applied to every prompt in the batch. The frontend cannot split a value it does not interpret, so it refuses rather than silently answering N-1 prompts against the wrong input. Send one request per prompt.

## Notes for reviewers

- The wire name differs from the request name on purpose (see above). If reviewers prefer one name end to end, `backend_multi_modal_data` on the request is a mechanical change.
- **KV routing scores this request on its placeholder prompt tokens alone**, because the frontend cannot hash a payload it does not interpret. Two requests with the same prompt and different payloads look identical to the router. vLLM folds multimodal identity into its own block hashes, so engine-side prefix caching stays correct; only the router's prefix-overlap estimate is optimistic. Documented in the vLLM reference guide.
- **Modality names are the engine processor's to choose**, including names the frontend uses for its own media. A backend-owned payload is built through a path that skips frontend UUID inference and structural pad expansion (`backend_owned` on `build_tokens_prompt`), so `compute_mm_uuids` and the Kimi pad expansion never read it. Reserving names would have banned a legitimate processor that registers a modality called `image`.
