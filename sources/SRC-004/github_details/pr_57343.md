## 正文

## Purpose

Fixes #57342.

With `canonical_layout`, CPU→GPU copies are submitted per mapped fragment, but `_select_swap_blocks_fn` picked the load path from the page size. A page ≥ 28 KiB whose fragments are smaller ended up on `cuMemcpyBatchAsync`, in exactly the small-copy regime #42212 moved to Triton.

This makes the selector look at the sizes that are actually submitted: page sizes for the direct layout, `run.fragment_size` for the canonical layout. The 28 KiB threshold and the 8-byte alignment check (the kernel copies `size // 8` words per descriptor) use those. The kernel chunk size still follows the page: sizing it to the fragment was slower for 512-byte fragments (8 KV heads × 128, bf16, TP=8, token-major: 408 ms vs 356 ms for a 32K-token load on an A30) and within 2–4% either way for 1–2 KiB fragments, so loads that already took the Triton path keep their kernel configuration. `canonical_layout` defaults to `False` in the selector, so direct behaviour is unchanged, and stores still always use DMA.

On the default CUDA path (packed K‖V views under LBHNC) the canonical mapping is a single run per page, so nothing changes there either. It matters for mappings with more than one run per page; details and numbers are in the issue.

Not a duplicate: I searched open PRs for `swap_blocks triton offload`, `select_swap_blocks_fn`, `canonical layout triton`, `canonical fragment`, `kv offload triton threshold` and `THRESHOLD_BYTES` (2026-09-17, against `08633cb5cd`). Nothing touches the selector. Closest neighbours are #48936 (block-copy benchmark script), #53971 (attrIdxs bounds in the C++ batch path) and #53544 (skip canonical mappings for packed caches).

Two tests added to the existing `test_gpu_worker.py`:

- `test_canonical_load_path_follows_fragment_size`: a 32 KiB page mapped as two 16 KiB fragments resolves to DMA for direct and to the Triton path for canonical; a 4 KiB page split into 2 KiB fragments still gets a 4 KiB (page-derived) chunk.
- `test_canonical_load_path_requires_aligned_fragments`: an 8-byte-aligned page with unaligned fragments (508 B / 516 B) stays on DMA, since the kernel would drop the trailing bytes of each fragment.

## Test Result

A30, torch 2.13.0+cu126, editable install with `VLLM_USE_PRECOMPILED=1` (precompiled artifacts from nightly `cd10ed6f9f`; this change is Python-only).

- `tests/v1/kv_offload/cpu/test_gpu_worker.py`: 42 passed, 1 skipped (the ROCm-only test).
- Both new tests fail without the source change and pass with it.
- Canonical suites, including the GPU roundtrips and `test_cross_topology_roundtrip`, whose small fragments now go through the Triton kernel: 38 passed.
- `ruff check`, `ruff format`, `mypy-3.10`, `mypy-3.12`: passed.

Load time for the case from the issue (TP=2, 32 KiB page mapped as 2 × 16 KiB, 80 layers, A30, median of 7, byte-exact):

| prefix | direct (DMA) | canonical before (DMA) | canonical after (Triton) |
|---:|---:|---:|---:|
| 1K tokens | 10.7 ms | 26.0 ms | 6.7 ms |
| 4K tokens | 30.0 ms | 103.9 ms | 26.6 ms |
| 32K tokens | 216 ms | 826 ms | 212 ms |

Host-side submit time on the model runner thread for the 32K-token load goes from 826 ms to under 1 ms. These numbers come from a standalone harness (verbatim `_swap_blocks_kernel`, single `cuMemcpyBatchAsync` call as in `swap_blocks_batch`), using the CUDA 12.8 forward-compat libcuda on a 535 kernel driver.

No model eval: the change only chooses between two byte-exact copy primitives, and the GPU roundtrip tests cover correctness.

AI assistance (Claude) was used for the investigation, implementation and tests. I reviewed every changed line and ran the tests and measurements above on my own hardware.

### Alex-ai-future · 2026-09-18 · COMMENTED

One concern is that this change still relies on a single empirically tuned `THRESHOLD_BYTES`, while the DMA/Triton crossover likely depends on both payload size and descriptor count. `_select_swap_blocks_fn` runs at handler initialization and does not know the actual batch size N; the Triton wrapper only falls back to DMA for very small N.

In a local H100 sweep, for example, DMA was faster for 28 KiB descriptors at N=64, while Triton was faster at N=256. Similarly, the crossover for 8 KiB descriptors moved between N=16 and N=64.

Could we add a small size × descriptor-count benchmark, or document why a single 28 KiB cutoff is expected to generalize across workloads and devices? If runtime autotuning is out of scope for this PR, this seems like a good follow-up for a per-device/per-N dispatch policy. The fragment-size fix itself still makes sense.
