# [PR #52297] [Attention] Move GDN common metadata compute out of per-group build

source: https://github.com/vllm-project/vllm/pull/52297
state: open | updated: 2026-09-23T06:45:49Z
labels: ready, needs-rebase, mrv2

## 正文

## Purpose

During profiling I notice GDNAttentionMetadataBuilder.build() takes a long time (~900µs), because the batch level GDN spec decode metadata (masks, decode/prefill/spec split, token indices, query_start_loc cumsums) is computed repeatedly in each group build(). This compute can be moved one level up out of each group build().

* Compute the batch level GDN spec decode metadata once per step in `compute_spec_metadata` and store it on model_specific_attn_metadata, instead of recomputing it inside each GDN group's build(). Only the block_table dependent state index gathers stay per-group in build().
* e2e output throughput improves 61% at batch size 1,  12% at batch size 16 with DFlash (tested on H200).

### MarkXCloud · 2026-09-23

Thanks a lot for this PR, @xyang16, and to @tomasruizt for the detailed benchmarking in #49730. We ran into the same bottleneck independently while using vLLM as the rollout engine for RL training (NeMo-RL), and the diagnosis here matches what we measured, so I wanted to share our data in case it is useful.

**Setup:** Qwen3.5-27B + z-lab/Qwen3.5-27B-DFlash, vLLM 0.26.0 (V2 model runner, forced by the DFlash drafter), TP1, `num_speculative_tokens=15`, FULL cudagraph for the verify step, single GB200 (Grace CPU).

**What we saw (unpatched):** at batch size 1, a DFlash step took ~26 ms vs 10.4 ms for plain decode, although GPU busy time was only ~15 ms. The ~11 ms of exposed host time came from ~700 CUDA API calls per step, of which 672 were in `GDNAttentionMetadataBuilder.build`: 48 GDN KV-cache groups × ~14 calls per build.

**Local workaround:** until an upstream fix lands, we use a temporary local patch to `build` that only handles the steady-state spec-decode shape (all real rows are spec rows, padding at the back); every other shape falls back to the stock code. Results on the same setup:

| | stock | patched |
|---|---:|---:|
| GDN-build CUDA API calls / step | 672 | 96 |
| step time, batch 1 | 27.7 ms | 14.3 ms |
| throughput, batch 1 | 169 tok/s | 294 tok/s |
| throughput, batch 16 (drain) | 1739 tok/s | 2262 tok/s |

This PR is the proper upstream fix for most of that, and we're glad to see it moving. Reading the current head (66e191db), two per-group items remain that our numbers suggest are still worth a bit. These are only suggestions, and you may already have plans for them:

1. `spec_state_indices_tensor` is still gathered with a CPU boolean mask in every group ([L478-L490](https://github.com/xyang16/vllm/blob/66e191dbad699fcb026b65ef87c18b78373384f7/vllm/v1/attention/backends/gdn_attn.py#L478-L490)). This means an H2D copy plus an index kernel per group. In the pure-spec case the spec rows form a prefix, so `block_table_tensor[:num_spec_decodes, : self.num_spec + 1]` gives the same result as a view.
2. In the full-cudagraph branch ([L554-L599](https://github.com/xyang16/vllm/blob/66e191dbad699fcb026b65ef87c18b78373384f7/vllm/v1/attention/backends/gdn_attn.py#L554-L599)), each group copies/fills the same batch-level values into its own persistent buffers: `spec_sequence_masks`, `spec_token_indx`, `non_spec_token_indx`, `spec_query_start_loc`, and `num_accepted_tokens`. Only `spec_state_indices_tensor` depends on the group's block table. If the builders could share those buffers and write them once per step, most of the remaining per-group launches would go away.

One caveat from our side: our temporary patch skips rewriting buffers that already hold the right values *across* steps. That approach does not interact well with sleep mode. The builder buffers live in the `kv_cache` CuMem pool, so `sleep(level=2)` / `wake_up()` discards their contents. It only worked for us because every generate call starts with a prefill that resets the state. Doing the sharing within a step, as this PR does for the precomputed metadata, avoids that problem.

Thanks again for working on this!
