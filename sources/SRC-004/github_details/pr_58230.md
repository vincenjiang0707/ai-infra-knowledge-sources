# [PR #58230] [ROCm] Fuse AllReduce + RMSNorm + per-token FP8 quant on AITER

state: closed | updated: 2026-09-23T02:14:58Z

## 正文

## Purpose

`RocmAiterAllReduceFusionPass` absorbs a trailing FP8 quant into the
all-reduce epilogue **only for per-group scales**. Models whose linear weights
are not FP8 block-scaled quantise activations **per token**, so they never
match those patterns: they fall through to the AR+RMS-only fusion and the
quant launches as a separate kernel after every all-reduce.

AITER already supports the fused form. `CustomAllreduce.fused_ar_rms` takes a
`post_per_token_quant` keyword that emits the FP8 output *and* a per-token
scale from the same launcher:

```python
ops.fused_allreduce_rmsnorm_quant(...)   # returns out, res_out, scale_out
```

It was simply never wrapped as a custom op, so no pattern could target it.
This PR adds the wrapper and the matching pattern.

## Changes

* `_aiter_ops.py` — `rocm_aiter_fused_allreduce_rmsnorm_quant` (impl + fake +
  accessor), calling `fused_ar_rms(..., post_per_token_quant=True)`
* `allreduce_rms_fusion.py` —
  `AiterAllreduceFusedAddRMSNormPerTokenQuantFP8Pattern`, matching
  `all_reduce -> fused_add_rms_norm -> per-token FP8 quant`
* `aiter_custom_all_reduce.py` — `supports_per_token_quant`, probed from the
  `fused_ar_rms` signature (the keyword is a parameter, not a separate method,
  so `hasattr` does not work here as it does for the per-group kernel)

The new pattern is registered **before** the AR+RMS-only patterns, following
the existing comment in the pass: registering them the other way round lets
AR+RMS consume the `all_reduce` node first and strands the trailing quant.

**Inert unless it applies.** On aiter builds whose `fused_ar_rms` lacks the
keyword, the pass logs and registers nothing new, leaving today's behaviour
unchanged. Models using per-group scales are untouched.

## Why this is not a duplicate

Checked before and during this work:

* **#41825** wires the AR+RMS half; this adds the per-token quant epilogue
  that PR deliberately leaves standalone.
* **ROCm/aiter#2823** added the *per-group* AR+RMS+quant launcher, already
  wired in vLLM as `rocm_aiter_fused_allreduce_rmsnorm_quant_per_group`.
  Per-token is a different scale granularity and a different launcher path.
* `gh search prs` for `fused_allreduce_rmsnorm_quant`,
  `allreduce rmsnorm quant per token`, `aiter allreduce fusion quant`, and
  `AllreduceFusedAddRMSNorm` returned no open PRs.

No open PR wraps `post_per_token_quant` or registers a per-token AR+quant
pattern.

## How this was found

Profiling a TP8 decode workload on MI355X, **every** all-reduce was
immediately followed by a norm op, yet none were fused — 290 collectives per
step, none overlapping any kernel. Tracing the cause showed the graph shape
was right but the registered patterns only covered per-group scales, while
this model quantises per token (`aiter::dynamic_per_token_scaled_quant_kernel`
appearing as standalone launches confirms it).

### fululi12 · 2026-09-23

Closing this.

**Why:** the pattern is registered in `RocmAiterAllReduceFusionPass`, which matches against a `torch.compile`-produced FX graph. The model this was written for (Kimi-K3, ROCm path) carries no `@support_torch_compile` — per the direction in #42770 it has already migrated to calling fused kernels directly from model code. With no compiled graph there is nothing for the pattern to match, so it would never fire for the target model.

That is also the real reason the existing AR+RMS patterns don't fire there. I had diagnosed it as a scale-granularity gap (the registered AR+quant pattern is per-group; this model quantises per token). That observation is true but not the cause, and a per-token pattern does not fix it.

**Sizing, in case it is useful to someone on a compiled model:** on MI355X TP8 at concurrency 1, the standalone `add_rmsnorm_quant` kernels this would absorb measure **0.495 ms/step of a 26.32 ms step = 1.88%**, and that is the ceiling assuming the fused epilogue is free. Realistically ~1.2%. Rewriting it as a direct call site instead of a pattern would additionally require plumbing the FP8 output and its per-token scale into the following Linear, which is invasive for that return.

**Possibly still useful to others:** aiter exposes three fused AR launchers and vLLM wraps only two — `fused_ar_rms` accepts a `post_per_token_quant=True` keyword that emits the FP8 output and a per-token scale from the same launcher, and it is not wrapped as a custom op. Anyone wanting the per-token AR+RMS+quant fusion on a still-compiled model can pick that up; note the capability probe has to inspect the `fused_ar_rms` signature rather than use `hasattr`, since it is a keyword rather than a separate method.

No reviewer time was spent on this — closing before it costs any.
