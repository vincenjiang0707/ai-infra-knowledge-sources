# [PR #58256] [ROCm][Bugfix][Spec Decode] Add compact_topk_indices to the ROCm DSA MTP drafter

## 正文

## Purpose

On ROCm, MTP speculative decoding for GLM-5.x crashes on the first draft step on current
`main`, with the reduction flag off and nothing unusual in the config:

```
File "vllm/v1/spec_decode/llm_base_proposer.py", line 613, in propose
    self.model.model.compact_topk_indices(token_indices_to_sample)
AttributeError: 'DeepseekV32MultiTokenPredictor' object has no attribute
'compact_topk_indices'
```

#51915 routed `deepseek_v32` and `glm_moe_dsa` to `vllm/models/deepseek_v32/amd/` on
ROCm. That module's `DeepseekV32MultiTokenPredictor` implements `set_skip_topk` but not
`compact_topk_indices`, which #47238 added only to the generic drafter in
`deepseek_mtp.py`. GLM-5.x checkpoints set `index_share_for_mtp_iteration: true`, and
with that set the legacy proposer calls both methods — it checks for the first and then
calls the second:

```python
if self._share_mtp_indices and hasattr(self.model.model, "set_skip_topk"):
    self.model.model.set_skip_topk(True)
    self.model.model.compact_topk_indices(token_indices_to_sample)
```

It is the only drafter on `main` with `set_skip_topk` and without
`compact_topk_indices`; the generic, NVIDIA DSA, GLM-5-Next, HY-V4 and both Qwen4-Exp
drafters have both. #51915 reworked the amd attention path and switched the dispatch in
`deepseek_v32/__init__.py`, but did not touch `amd/mtp.py`, which is how the two came
apart.

### Change

- `amd/mtp.py`: add `compact_topk_indices` to `DeepseekV32MultiTokenPredictor`. It
  follows the amd drafter's own layout rather than the generic one: here
  `topk_indices_buffer` lives on `self_attn` itself, where `set_skip_topk` already looks
  for `skip_topk`, not under `self_attn.mla_attn`. Copying the generic method body would
  find no buffer and silently leave it uncompacted, so steps 1+ would reuse the wrong
  rows instead of crashing.
- `llm_base_proposer.py`: decide index sharing once, after the draft model is loaded, and
  require both methods — which is what the V2 MTP speculator already does
  (`vllm/v1/worker/gpu/spec_decode/mtp/speculator.py`). The two use sites then read that
  flag instead of each re-checking one method.

Every other drafter on `main` has both methods, so the proposer change leaves their
behaviour as it is. The one behaviour change is the amd DSA drafter going from a crash to
index sharing as the checkpoint asks for. Until this lands, `"index_share_for_mtp_iteration":
false` in `--speculative-config` avoids the crash on `main`.

### Which checkpoints this reaches

Each checkpoint's real `config.json` was resolved through the draft-model registry on both
`main` and this branch, and each one then ran on ROCm with its architecture truncated and
dummy weights:

| checkpoint | `model_type` | drafter on ROCm | `main` | this PR |
|---|---|---|---|---|
| GLM-5.3 (fp8), GLM-5.3-Quark-MXFP4-AttnFP8, GLM-5.2-FP8, GLM-5.2-MXFP4 | `glm_moe_dsa` | `deepseek_v32/amd/mtp.py` | `AttributeError` on the first draft step | index sharing on |
| DeepSeek-V3.2 | `deepseek_v32` | `deepseek_v32/amd/mtp.py` | runs, no sharing (config does not ask) | same |
| GLM-5.3-Flash | `glm5_next` | V2 model runner's MTP speculator | runs | same — never reaches this proposer |

GLM-5.3-BF16 has the same config as GLM-5.3 and was not run separately. The other
first-tier checkpoints (DeepSeek-V4 line, Kimi, MiniMax, Qwen, gpt-oss, gemma-4, Llama)
have no DSA indexer, or no MTP drafter, and resolve identically on both trees.

Open PRs touching the same file: #55081 edits the `DeepseekV32MTP` wrapper and #53953 the
`DeepseekV32MultiTokenPredictorLayer`; neither adds this method, and both are in
different hunks.

## Test Plan

```bash
pytest tests/models/deepseek_v32/test_amd_mtp.py   # ROCm only; skipped elsewhere
```

The new tests build the amd predictor with real `topk_indices_buffer` tensors and check
that `compact_topk_indices` gathers the requested rows to the front, leaves the rest
alone, covers every MTP layer, and compacts identically to the generic drafter given the
same buffer and slots.

## Test Result

MI355X (gfx950), ROCm, against `main@94f4170df3`.

**Reproduction on `main`.** GLM-5.3 (official fp8 weights), TP=4, `mtp` with one draft
token, `use_local_argmax_reduction` off: the engine starts and the first draft step fails
on all four TP workers with the `AttributeError` above. The same happens for the other
three `glm_moe_dsa` checkpoints in the table. With this PR, every one of them runs with
`compact_topk_indices` and `set_skip_topk(True)` called on every draft step.

**Unit tests, each run against three trees** so that the assertions are shown to
discriminate rather than merely pass:

| tree | result |
|---|---|
| `main` | 4 failed — the method does not exist |
| the generic drafter's body copied in (`self_attn.mla_attn` path) | 3 failed, 1 passed — the method exists but compacts nothing |
| this PR | 4 passed |

These were run from a directory outside the repository, with the imported module's
`__file__` checked for each tree. Run from inside the checkout, pytest's rootdir
insertion made all three trees import the checkout's own `vllm`, and they all passed.

**Performance.** This is a crash fix and makes no speed claim. The drafter was timed with
index sharing (this PR) against the `main` workaround with sharing off, on a truncated
GLM-5.3 at context up to 97k and batch up to 83. At `num_speculative_tokens=3` and `=1`,
`propose()` does not move beyond the spread between two identical runs of the baseline.
On MI355X at these shapes the draft step is a roughly fixed ~2.3 ms, and the indexer that
sharing skips is a small part of it.

Still to come, as a comment: the full micro tables, including `num_speculative_tokens=2`,
which is being re-checked, and a real-weights GLM-5.3 A/B (acceptance, `vllm bench serve`,
GSM8K).

### Drafter micro benchmark

Same truncated GLM-5.3 (fp8), dummy weights, TP=1, compiled with full decode CUDA graphs. Every `SpecDecodeBaseProposer.propose()` call is timed with a device sync on each side, decode steps only. Each cell is run three times, the first discarded, and the median over the rest reported. All arms in a table ran at the same time, one per GPU, so they saw the same host.

- `base`, `base2`: `main`, `"index_share_for_mtp_iteration": false` — the only way it runs on `main`. `base2` is a repeat, for the noise floor.
- `null`: this PR, sharing forced off.
- `patched`: this PR, sharing as the checkpoint asks.

`propose()` in ms, `num_speculative_tokens=3`, 300 output tokens, `max_num_batched_tokens=65536`:

|---|---|---|---|---|---|
| 30000 | 1 | 6.55 | 6.65 | 6.56 | 6.78 |
| 30000 | 13 | 6.86 | 6.88 | 6.71 | 6.88 |
| 30000 | 37 | 6.97 | 7.10 | 6.91 | 7.01 |
| 30000 | 83 | 7.25 | 7.37 | 7.29 | 7.40 |
| 97000 | 1 | 6.60 | 6.69 | 6.60 | 6.74 |
| 97000 | 13 | 6.76 | 6.86 | 6.74 | 6.92 |
| 97000 | 37 | 6.94 | 7.15 | 6.90 | 6.96 |
| 97000 | 83 | 7.39 | 7.54 | 9.59* | 9.76* |

\* One warm run in each of these cells spiked to about 12 ms. `null` has sharing off and spikes the same way, so the spike is not the sharing path. The other run in the `patched` cell was 7.41 ms.

At `num_speculative_tokens=2` the first pass had one cell (30000/37) where both warm patched runs read 8.7 ms against 4.9 ms for base. A second pass ran two base and two patched arms, each on a GPU the first pass had not used for k=2, over contexts 30000 and 97000 at batch 13/37/83. There were no spikes. That cell read 4.98 / 4.78 ms for the two base arms and 4.92 / 4.95 ms for the two patched arms. Over the whole grid, base spans 4.74–5.24 ms and patched 4.83–5.17 ms. At 1500 and 7000 tokens of context, with 48 output tokens, k=3 base is 6.82–7.68 ms against patched 6.73–7.53 ms. At k=1 there is no later step to share indices with, and the extra compaction does not show up: base 2.41–2.77 ms, patched 2.39–2.71 ms.

The patched arms called `compact_topk_indices` and `set_skip_topk(True)` 7968 times each over the long-context grid, so a flat result is a measurement, not a path that never ran. At k=3, patched minus base is +0.2 % to +3.5 % outside the spike cell, and base2 minus base is +0.3 % to +3.0 %, so the difference does not rise above the noise floor. `propose()` time barely changes between 1.5k and 97k tokens of context, so at these shapes the draft step is a roughly fixed ~2.3 ms per step, and the indexer that sharing skips is too small a part of it to show. I could not time the indexer on its own: it is captured inside the decode graph. Dummy weights make acceptance meaningless, so the real-weights A/B below covers acceptance.

### Real weights: GLM-5.3 (official fp8), TP=4, `num_speculative_tokens=3`

Base is `main` with `"index_share_for_mtp_iteration": false`. Patched is this PR, with sharing as the checkpoint asks.

**GSM8K.** `lm_eval`, 5-shot, greedy, all 1319 items, `max_model_len=4096`, `max_gen_toks=256`, prefix caching off, `seed=1234`. `null` is this PR with sharing forced off.

| arm | strict-match |
|---|---|
| base | 0.9181 |
| base2 (repeat) | 0.9196 |
| null | 0.9212 |
| patched | 0.9174 |

The base-vs-base drift is 0.0015. Patched is −0.0008 from `base` and −0.0023 from `base2`, which is within the spread of the three sharing-off arms (0.9181–0.9212). Per-sample same-verdict is 95.91 % for base vs base2 and 95.75 % for base vs null, against 96.44 % and 95.68 % for base and base2 vs patched. Prompt hashes match on all items. So there is no measurable accuracy change on GSM8K, within the noise floor of these repeats. GSM8K is short-answer greedy math, so this says nothing about long context or sampling.

**End to end.** `vllm bench serve`, random dataset, 1024 in / 512 out, 288 prompts, `--max-concurrency 64`, `--ignore-eos --seed 1234`. Fresh server per run, on-disk compile caches kept per arm. Four runs per arm as consecutive blocks, base then patched, with the cold first run dropped. Medians over runs 2–4, on a host with nothing else running:

| metric | base | spread | patched | spread | Δ |
|---|---|---|---|---|---|
| Total tok/s | 2673.1 | 0.7 % | 2676.5 | 2.7 % | +0.1 % |
| Mean TPOT (ms) | 63.79 | 1.2 % | 64.04 | 2.7 % | +0.4 % |
| Median TPOT (ms) | 67.33 | 6.4 % | 71.42 | 5.4 % | +6.1 % |
| Mean TTFT (ms) | 1153.0 | 2.7 % | 1187.5 | 10.6 % | +3.0 % |
| Median TTFT (ms) | 369.6 | 0.2 % | 370.5 | 19.7 % | +0.2 % |
| Draft acceptance | 8.4 % | | 7.7 % | | |

Throughput and mean TPOT are flat. Median TPOT moves by about the within-arm spread, and it follows each run's acceptance rate, which ranged 7.4–9.1 % inside the patched block. So sharing neither speeds up nor slows down decode here, which matches the drafter micro benchmark.

A first pass of this A/B read +7.9 % throughput for patched and is discarded. Its base block ran while the GSM8K arms were loading and evaluating on the other four GPUs (1-minute load average 148–188 at run start), and its patched block ran after they had finished (about 55). The base block also rose monotonically across its runs, 2484 → 2512 → 2606 tok/s. The rerun on a quiet host put base at 2673 tok/s, which removes the gap.
