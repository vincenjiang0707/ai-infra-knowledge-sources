### 🐛 Describe the bug

## Summary

Serving `DeepSeek-V4.1-Flash` (hybrid KV: full-attention MLA + sliding-window/circular-buffer groups) with the `SimpleCPUOffloadConnector` crashes the EngineCore on the **first scheduled request** with:

```
(EngineCore pid=536) [ASSERT-DEBUG] resolve_block_hashes: block_size=8, hash_block_size=32, modulo=8   <-- our instrumented print, see note below
(EngineCore pid=536) ERROR ... assert block_size % hash_block_size == 0
AssertionError
```

(The `[ASSERT-DEBUG]` line is **not** stock vLLM output — we volume-mounted a patched `kv_cache_utils.py` into the container that prints `block_size`/`hash_block_size`/modulo just before the assert, since the bare `AssertionError` carries no values. Stock vLLM produces only the assert line; details in *Extra context*.)

Note `block_size (8) < hash_block_size (32)` — the call asks `resolve_block_hashes` to view 32-token-granularity hashes at a *finer* 8-token granularity, but the function only supports the coarsening direction (`block_size >= hash_block_size`, enforced by the divisibility assert). With 8 < 32 the assert `8 % 32 == 0` can never hold, so the crash is deterministic on the first request.

## Root cause analysis

The offload path mixes up per-group block geometry with the global hash granularity:

1. `resolve_kv_cache_block_sizes()` (`vllm/v1/core/kv_cache_utils.py:~726-792`) computes for multi-group models:
   - `hash_block_size = gcd(group_block_sizes)` over **prefix-cacheable** groups — for DSV4.1-Flash: gcd(32, 8) = 8? No — in our crash the resolved `hash_block_size=32` and the group's `group_size=8`, meaning the SWA/circular-buffer group (block_size 8) was **excluded** from the hashing_sizes GCD (its `prefix_cacheable` is False for `CircularBufferSpec`/Kpool-tail style specs), so `hash_block_size` followed the full-attention group (32).
   - `SimpleCPUOffloadScheduler` stores this as `self.hash_block_size` and asserts `self.block_size % self.hash_block_size == 0` at init (manager.py:129) — which passes because `self.block_size` is the **scheduler** block size (LCM), not any single group's size.

2. At request time, `_select_eager_blocks_to_store()` (manager.py:720) iterates **all** KV cache groups — including the non-prefix-cacheable SWA group — and calls:
   ```python
   resolved_hashes = resolve_block_hashes(
       request.block_hashes, self.hash_block_size, group_size)
   ```
   with `group_size = 8` (the SWA group) and `hash_block_size = 32`.

3. `resolve_block_hashes()` (kv_cache_utils.py:2770-2789) only supports viewing fine hashes at a **coarser** granularity (`block_size >= hash_block_size`, enforced by the assert). Receiving `block_size(8) < hash_block_size(32)` violates its contract.

Two contributing bugs:
- `_select_eager_blocks_to_store` passes a group-local block size into a function whose contract assumes the caller wants a **scheduler-level** view; for groups with `block_size < hash_block_size` the call is meaningless (there are no per-group hashes at 8-token granularity — hashes only exist at 32-token boundaries).
- The init-time assert (manager.py:129) checks the wrong invariant (`scheduler_block_size % hash_block_size == 0`), which is trivially true and hides the per-group mismatch until the first request.

## Suggested fixes

Any of these would unblock DSV4.1-Flash-class hybrid models; (1)+(2) together are probably the right combination:

1. **Skip hash resolution for non-prefix-cacheable groups** in `_select_eager_blocks_to_store` (and the lazy variant): the SWA/circular-buffer group's KV is windowed/evicted anyway, so offloading it by content hash is not meaningful. Only resolve hashes for groups whose `kv_cache_spec.prefix_cacheable` is True and whose `block_size >= hash_block_size`.

2. **Clamp per-group block size in the manager**: when calling `resolve_block_hashes`, pass `max(group_size, self.hash_block_size)` or round `group_size` up to a multiple of `hash_block_size`, mirroring what `BlockHashListWithBlockSize` does for the coarser direction.

3. **Harden `resolve_block_hashes`**: replace the bare assert with a descriptive error, and/or support the `block_size < hash_block_size` direction by returning the finest available view with an offset warning — though semantically this case should be prevented by the caller (fix 1).
