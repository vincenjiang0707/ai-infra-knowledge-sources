# [ROCm] HiSparse: host-resident sparse-MLA hot-buffering on gfx950

## Purpose

Enables HiSparse (#53781) on AMD ROCm, verified on gfx950 (MI350X, CDNA4).

HiSparse keeps the bulk of the sparse-MLA KV cache in pinned host memory and
pulls only the indexer-selected rows back just in time, so long-context agentic
sessions stop getting preempted. #53781 landed it CUDA-only.

**Draft.** bf16 KV is complete and benchmarked; `fp8` KV plus HiSparse still
faults on ≥16k prefills (last bullet under Limitations). That is being fixed,
and this PR stays in draft until it is.

## Changes

### 1. Route HiSparse attention through the int64-safe Triton kernel (`rocm_aiter_mla_sparse.py`)

HiSparse points attention at
`PagedCacheView.attention_cache`, a view over the **whole multi-layer KV slab**,
so the row indices it emits scale with the total block count rather than with
one layer's page table. Off HiSparse the same model emits a max row index of 33;
on HiSparse it reaches 7.5 million. AITER's decode kernel computes
`row_index * row_width` in int32, so on GLM-5.3 (`row_width=576`) it wraps above
row 3,728,270 and answers with approximately zero — no NaN, no assert, no
kernel error.

The backend already carries a Triton ragged path that promotes the slot index to
`tl.int64`, so it is immune past that point. Under HiSparse it becomes
unconditional: `use_hisparse_triton_attn` is set from
`isinstance(index_group, HiSparseMLAIndexGroup)` at construction, and the prefill
call additionally passes `allow_aiter_opus=False` so the dispatcher inside
`rocm_sparse_attn_prefill` cannot fall back into the OPUS ASM kernel, whose KV
addressing width is likewise unverified. No flag, no env var — HiSparse on ROCm
is always on the int64 path.

### 2. ROCm backend wiring (`rocm_aiter_mla_sparse.py`)

Every CUDA HiSparse backend consumes a **dense** `[tokens, topk]` index tensor
plus `valid_counts`; AITER's tuned decode kernel consumes a **ragged** flat list
plus an indptr. Bridging that is the bulk of the diff:

- `ROCMAiterMLASparseImpl` accepts an `index_group_builder` and registers with
  it, which is what makes `mla_attention.py:575` pick up `hisparse_cache` and
  drive KV mirroring.
- Decode: `convert_decode_logical_to_physical_topk` → dense physical top-k →
  compacted to ragged → attention runs against `physical_kv_cache` (the hot
  buffer) instead of the paged KV cache.
- Prefill: mirrors the CUDA guard, staging host rows via `stage_prefill_rows`
  when the context is not fully resident. This is not optional — once a context
  has been offloaded, `all_context_pages_resident` is False and
  `index_group.py:232` asserts outright.
- AITER's persistent work-stealing metadata is disabled under HiSparse: its
  buffers are sized in `build()`, but HiSparse rewrites the indptr at forward
  time from resolver counts. Correctness first; noted as a perf follow-up.

One new Triton kernel, `compact_topk_to_ragged_triton`. The existing
`fetch_id_to_ragged_triton` was not reusable: a mid-row `-1` must *drop out*
rather than displace a valid entry.


### 3. HIP kernel port (`csrc/`)

The four fused HiSparse cache ops now build and run on ROCm. Mechanical:
vectorized copy widths, `__nv_bfloat16` → `hip_bfloat16`, and warp-primitive
shims added to `csrc/cuda_compat.h`. No algorithmic change; CUDA codegen is
unaffected.

### 4. Config gate (`vllm/config/vllm.py`)

Opens HiSparse for ROCm, with `fp8_ds_mla` (the 656-byte packed row) rejected by
name rather than failing deep in a kernel. Every other platform keeps the
existing rejection.

## Platform-neutral fixes

These are in shared code and affect CUDA too.

**`vllm/v1/attention/backends/mla/index_group.py` — event record does not
survive nested `torch.compile`.** `self.logical_topk_ready.record(...)` is
traceable, so Dynamo lowers it to a `torch.ops.streams.record_event` node whose
event lives in a process-global side table. `reset_user_object_tracking()`
clears that table on compile entry. vLLM nests compiles
(`CustomOp.maybe_compile` wraps `forward_native`), so an inner compile firing
during an outer graph's execution wipes the entry that graph's node depends on.
Replaced with an opaque custom op keyed by an integer group handle, so the event
never becomes a graph input. CUDA appears not to have hit this only because its
call path reaches `set_logical_topk_ready` from outside the compiled region.

**`vllm/distributed/.../hisparse/worker.py` — mirror guard for unbracketed
runs.** Warmup and profiling runs execute the model with the connector disabled,
so `start_step`/`finish_forward` never bracket them and `_per_layer_mirrored` is
never cleared between passes. The second warmup pass then trips
`RuntimeError: HiSparse layer 0 mirrored twice.` Added a `_step_in_flight` flag
so mirroring is skipped outside a real step. The double-mirror check is
unchanged inside a step.

**`vllm/v1/worker/worker_base.py` — layout query runs outside the config
scope.** `get_supported_kv_cache_layouts` is an RPC that calls
`get_current_attn_backends(self.vllm_config)` with no config set, but a
backend's supported set can depend on the config — HiSparse changes how ROCm
sparse MLA addresses pages. Wrapped in `set_current_vllm_config`.

**`vllm/v1/hisparse/runtime.py` — `cudaGetLastError` is absent on ROCm.**
`release_pinned_state` clears the sticky error flag after a failed unregister,
but ROCm's `torch.cuda.cudart()` exposes only `cudaError`,
`cudaGetErrorString`, `cudaHostRegister`, `cudaHostUnregister`. The handler
would itself raise `AttributeError` and mask the real error. Guarded with
`getattr`; the clear is best-effort cleanup, so skipping it is correct rather
than degraded.

## Required AITER fix (out of tree)

**This branch does not run on stock AITER.** With HiSparse enabled, gfx950 takes
a `Memory access fault` inside AITER's 1-stage fp8-blockscale MoE,
`fmoe_fp8_blockscale_g1u1`. It is not a HiSparse bug, but HiSparse is what makes
it fire, so it gates this PR.

AITER Issue: [ROCm/aiter/issue#]()

**[ROCm/aiter#5764](https://github.com/ROCm/aiter/pull/5764)** backs the tail
with real memory at the `per_1x128` launch site, returning a view with the
original shape so no observable value changes. It makes the over-read harmless
rather than removing it. **Every number in this PR was produced with that patch
applied.**

## ROCm-specific workarounds

**Imported IPC events are capped at 32 record/wait cycles on ROCm.** The 33rd
raises `hipErrorInvalidValue` even with the two sides fully serialized, so it is
a resource limit and not a race. HiSparse's shared host pool records one per
step, so any run decoding past 32 steps at TP>1 would fail. On ROCm the worker
falls back to a local-event handshake plus a TP barrier
(`HiSparseConnectorWorker.sync_host_writes`), which orders the same writes
without an interprocess object.

## Model Evaluation

GSM8K, 200 questions, 5-shot, greedy (`temperature=0`), seed 42. GLM-5.3, TP4,
full 78-layer model, gfx950. Production serving config: 32k context, fp8 KV
cache, cudagraphs enabled. HiSparse arm adds a 128 GiB pinned host pool.

Model Runner V2 is forced in **both** arms — HiSparse enables it implicitly, and
comparing against an MRV1 baseline reintroduces a confound.

| Arm | Accuracy (run 1 / run 2) | Output tok/s |
|---|---|---|
| HiSparse **off** | 0.905 / **0.915** | 1171 / 1212 |
| HiSparse **on** | 0.890 / **0.925** | 200 / 233 |

On AITER's int32 decode kernel, the identical configuration scored
**0.000–0.005** — near-zero attention for every row above the wrap point. (These
GSM8K numbers were taken with the block-count cap that preceded the Triton
routing; both avoid the overflow, and the Triton path is the one that ships.)

The throughput gap above is real but misleading as a verdict on HiSparse: GSM8K
prompts are short and concurrency is low, so nothing is ever under memory
pressure and the indexer is pure overhead. The benchmark below is the one that
answers the question.

**Accuracy while the host path is actually live.** GSM8K above runs below
HiSparse's offload watermark, where every page stays GPU-resident and no host DMA
happens at all — so it does not exercise the feature. A needle-in-a-haystack
probe on 8× MI350X (GLM-5.3, TP=8, `--max-model-len 80000`, 256 GiB host pool)
loads the pool with long-generation holder requests until KV usage sits just
under the watermark, then measures with short probes alongside them:

| | |
|---|---|
| needle accuracy | **60/60 = 1.000** |
| by depth (10/30/50/70/90%) | 12/12 at every depth |
| host→device **during the probe window** | **245.4 GiB** |
| KV usage during window | min 0.775, mean 0.836 |
| preemptions | 0 |

A 25-probe run at a lighter load agrees (25/25, 9.2 GiB moved), as does a control
below the watermark where nothing offloads (25/25). The 245 GiB figure is a delta
across the probe window, not a cumulative counter.

## Throughput

The workload from the GLM-5.3 hybrid-offloading blog post, which is what HiSparse
was built for: OpenHands-style agentic conversations, 13 turns, first turn ~74k
tokens and later turns 753, output pinned to 220. GLM-5.3, **TP4 on 4× MI350X**
(the blog ran TP8 on H200), `--max-model-len 131072`,
`--gpu-memory-utilization 0.92`, `--max-num-batched-tokens 32768`, 128
conversations, sequential arms, a fresh server per point.

**Every arm runs bf16 KV, a deviation from the blog's fp8** — forced by the fp8
limitation below. It roughly doubles KV bytes and so lowers absolute throughput
for all arms alike; the comparison between arms is unaffected.

Throughput is logical total tokens/s per GPU; interactivity is `1000 / mean TPOT`.

| arm | conc | reqs | interactivity | tok/s/GPU | TPOT ms | TTFT med |
|---|---|---|---|---|---|---|
| no offloading | 1 | 28 | 50.6 | 3444 | 19.8 | 276 |
| no offloading | 8 | 223 | 5.5 | 2753 | 182.5 | 15069 |
| no offloading | 16 | 448 | 4.4 | 2265 | 228.3 | 86827 |
| CPU offload 512 GiB | 1 | 28 | 49.0 | 2978 | 20.4 | 278 |
| CPU offload 512 GiB | 8, 16, 24 | — | **crashed** | | | |
| **HiSparse 512 GiB** | 1 | 28 | 21.3 | 1499 | 46.9 | 665 |
| **HiSparse 512 GiB** | 8 | 224 | 8.0 | **4129** | 125.5 | 1754 |
| **HiSparse 512 GiB** | 16 | 435 | 3.3 | **4141** | 298.7 | 1620 |
| **HiSparse 512 GiB** | 24 | 661 | 1.9 | 3330 | 526.4 | 1360 |
| hybrid 384+128 GiB | 1, 8, 16 | — | **crashed** | | | |

The shape matches the blog. The no-offload baseline **degrades** as concurrency
rises (3444 → 2753 → 2265) because 74k-token contexts get preempted and
re-prefilled; HiSparse climbs and then holds (1499 → 4129 → 4141), and at
concurrency 16 delivers **1.83× the baseline's throughput** with TTFT median 54×
lower (1.6 s vs 87 s). HiSparse loses at concurrency 1, as expected: with no
memory pressure the indexer is pure overhead.

The trade is visible in the interactivity column: at concurrency 16 HiSparse's
per-token latency is worse (299 ms TPOT vs 228 ms), because it keeps far more
requests in flight instead of preempting them. That is throughput/latency
exchange, not a free win — but the first
token arrives in 1.6 s rather than 87 s, which for an agentic workload is the
number that is felt.

Two arms crash, and neither crash is in code this PR touches:

- **CPU offload** dies in `swap_blocks_batch` / `hipMemcpyBatchAsync`
  (`cache_kernels.hip:223`) at concurrency ≥ 8, with 27 GB already staged. That
  is the generic `OffloadingConnector` DMA path, unmodified here.
- **hybrid** (`MultiConnector` wrapping both) dies seconds after the first
  request at every concurrency, although each connector passes **alone** at the
  identical configuration. Under investigation; not a blocker for HiSparse
  standalone.

So on ROCm today HiSparse is not merely faster than CPU offloading — at
concurrency ≥ 8 it is the only offload arm that runs at all.

## Limitations

- **HiSparse cannot use AITER's tuned ASM sparse decode kernel on ROCm** until
  its row offset is widened to 64 bits; it is prebuilt assembly and out of tree.
  The Triton ragged path is correct but not equally tuned.
- **`fp8_ds_mla` is not supported on ROCm** and is rejected with a clear error.
  bf16 and standard fp8 rows work — the HiSparse runtime is dtype-generic
  (`row_width` is a constructor parameter).
- **Gated on [ROCm/aiter#5764](https://github.com/ROCm/aiter/pull/5764)** (see
  above). Stock AITER faults in `fmoe_fp8_blockscale_g1u1` whenever HiSparse is
  enabled on gfx950.
- **`fp8` KV plus HiSparse faults on prefills at or above ~16k tokens**, even
  with the AITER fix above applied. **Being fixed — this PR stays in draft until
  it is.** It is the *interaction*: the same configuration with `auto` KV passes
  16k and 74k, and fp8 with HiSparse off passes both. bf16 KV is the workaround
  and is what the benchmark above uses.

  It is an **async ordering bug**: under `AMD_SERIALIZE_KERNEL=3
  AMD_SERIALIZE_COPY=3 HIP_LAUNCH_BLOCKING=1` all of 1k/4k/16k/32k pass, where
  the unserialized run fails hard at 16k. Rank 0 dies by silent host SIGSEGV —
  no traceback, no `Memory access fault` — immediately after an AITER
  `per_1x128` MoE dispatch; the other ranks are victims parked in a barrier.
  Narrowing which synchronization is missing is in progress.
- **AITER's persistent work-stealing decode path is disabled under HiSparse.**
- **`MultiConnector` combining HiSparse with `OffloadingConnector` crashes** on
  ROCm (see above). Each connector works alone. It presents with the same
  signature as the fp8 fault above, so the two are plausibly the same race;
  being investigated together.
- **MTP under HiSparse on ROCm is untested.**
- Verified on gfx950 only. Other CDNA targets are untested.
