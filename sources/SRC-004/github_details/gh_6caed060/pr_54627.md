# [PR #54627] [Core][V1] Apply prefill_schedule_interval outside data parallelism

## 正文

## Purpose

`prefill_schedule_interval` defers new prefills to every Nth engine step, so that decode
runs in longer uninterrupted stretches instead of meeting prefill on most steps. Today it
only takes effect under data parallelism: `DPEngineCoreProc._should_throttle_prefills()`
drives the cadence from a `step_counter` shared across ranks, while the base
`EngineCore._should_throttle_prefills()` returns `False` unconditionally. Setting the
option on a single engine is silently a no-op, with no warning.

This applies the same interval in the scheduler when `data_parallel_size == 1`. Without
peers there is nothing to align to, so the interval is measured from the last step that
carried prefill rather than against a global grid, which means no shared counter is
needed. Data-parallel deployments are untouched and keep their rank-aligned cadence.

As with the existing DP gate, prefill is deferred only when a running request can decode
in its place (`any(not r.is_prefill_chunk for r in self.running)`), so the interval never
leaves the model idle. The default interval of `1` disables the gate, leaving admission
behavior unchanged.

The motivating deployment is a single engine using decode context parallelism
(`--decode-context-parallel-size 8`). DCP is parallelism *within* one engine, so the
existing DP-only wiring never reaches it, even though the workload benefits from the
cadence as much as a DP deployment does.

## Why this is not duplicating an existing PR

No open PR touches `prefill_schedule_interval` or `_should_throttle_prefills`. The only
open PR matching `throttle_prefills` is #52969, an unrelated fix for aborted requests.

Two open PRs are adjacent but solve different problems:

- **#49075** (`max_num_partial_prefills` / `max_long_partial_prefills` in V1) bounds *how
  many* prefills run concurrently. This PR controls *how often* a step carries prefill at
  all. The two compose, and neither subsumes the other. Note that #49075 edits both
  scheduling loops, so a textual conflict is possible depending on merge order.
- **#53571** (SLO-aware scheduling policy) reorders the waiting queue by TTFT target,
  changing *which* request is admitted. This PR changes *whether* prefill is admitted on
  a given step, and does not reorder anything.

## Test Plan

Five new tests in `tests/v1/core/test_scheduler.py`, covering the behavior contract:

- `test_local_prefill_interval_holds_prefill_between_bursts[2,4]` — a waiting prefill is
  held for the remainder of the interval while running requests keep decoding, then
  admitted once it elapses.
- `test_local_prefill_interval_defaults_to_no_gating` — the default of 1 admits on the
  next step, i.e. no behavior change.
- `test_local_prefill_interval_left_to_engine_under_dp` — at `data_parallel_size > 1` the
  scheduler does not gate, leaving the rank-aligned cadence to the engine.
- `test_local_prefill_interval_never_idles_the_model` — with nothing running to decode,
  prefill is admitted regardless of the interval.

`create_scheduler` gains a `prefill_schedule_interval` parameter.

### fululi12 · 2026-09-01

Thanks @njhill for the pointer, and thanks @F21HGG for the detailed writeup — I've
read through #54145 and I agree with your framing that these are adjacent rather
than duplicative.

The distinction I'd draw is in the control variable. #54145 is size-aware: it
defers chunks *below* a token threshold in order to aggregate them into fewer,
larger prefill launches, targeting batching efficiency. This PR is time-aware: it
spaces *all* prefill on a cadence measured from the last prefill-carrying step,
targeting uninterrupted decode stretches. A workload with many small chunks and
one with a few large ones are affected by opposite mechanisms.

One scope note on this PR specifically: it adds no new knob. `prefill_schedule_interval`
already exists and is already documented, but it is driven entirely by the DP engine
core, so setting it on a single-engine deployment silently does nothing today. This
PR makes the existing config behave as documented outside data parallelism, reusing
the existing `defer_prefills` mechanism rather than adding a second gating path. That
gap exists independently of how #54145 lands.

On precedence — your observation is correct, and I think we can state the bound
precisely. This PR's gate sets the existing `defer_prefills`, which upstream consumes
both in the running loop (in-progress prefill chunks) and in the waiting loop (new
admissions). Both of those sit upstream of where #54145 applies its checks, so while
the cadence gate is closed, the threshold/age release cannot fire on that step —
for running and waiting chunks alike.

The overshoot is bounded, though: `last_prefill_step` only advances on a step that
actually carried prefill, so if all prefill is deferred the gap grows monotonically
and the gate opens after at most `interval` steps. So a pending chunk can exceed
`max_prefill_chunk_delay_steps` by at most `interval - 1` steps — with your
production 192 and the interval 33 I've been testing, a worst case of ~224 steps.

If the two are ever composed, I'd suggest the age-based release win, since it is a
deadline while the cadence is a spacing preference. Concretely, `release_small_prefill_chunks`
is computed at the top of `schedule()`, before this PR's gate, so it is a single extra
clause on the gate condition (`and not release_small_prefill_chunks`). Worth noting the
two policies already share a safety invariant — neither defers unless something else can
decode — so composed they still cannot idle the model. I agree with you that neither
should be enabled together by default without an interaction benchmark.

On comparing performance on my workload: happy to, with the caveat that it is a very
different regime from your single-GPU measurements, so it would be a second data point
rather than a replication. Mine is Kimi-K3 (2.8T MoE) FP4 on 8x MI355X, TP8 with decode
context parallelism and CPU KV offload, replaying an agentic-coding trace with ~73k
median ISL, ~290 median OSL, ~90% prefix cache hit, concurrency 52 and a 16,384-token
batch budget; the objective is per-GPU throughput and p90 interactivity rather than an
average E2E budget.

I'd expect your threshold to actually bind there: with that prefix hit rate the uncached
prefill work per request is a few thousand tokens, so per-step chunks should straddle
your 1,024-3,072 range — but that is a prediction I'd rather measure than assert. I'm
currently running a three-arm A/B (control / this PR / this PR + #54625) on a patched
nightly to publish clean per-PR deltas; preliminary numbers from an earlier
runtime-patched build had the cadence gate throughput-neutral with a double-digit p90
interactivity gain, and I'll update the description once the clean run lands. I can add
a #54145-only arm against the same control after that.

A combined arm is also possible, but both PRs touch the same region of `schedule()`, so
it needs the overlap resolved first, and per your recommendation I would not propose it
as a default. Each arm is ~85 minutes of exclusive 8-GPU time on a shared node, so this
lands over the next several days rather than today.

Measured it, @njhill — and thanks @F21HGG for updating #54145's description and for raising the precedence point, which I've now been able to test rather than reason about.

Below is a 2x2 over the two policies on my workload, run as four arms from a single image with both features off by default, so each arm differs only in the flags named.

Setup: Kimi-K3 (2.8T MoE) FP4 on 8x MI355X, TP8 with decode context parallelism and CPU KV offload, replaying an agentic-coding trace at concurrency 52 with a 16,384-token batch budget, ~78k median ISL, ~285 median OSL, ~90% prefix cache hit.

**The two PRs are optimizing different objectives, and that should be stated before the numbers, because it determines what the numbers can and cannot show.** @F21HGG defines #54145's target as average E2E latency under a budget — maximizing stable per-GPU QPS while the mean stays inside a bound. My objective is p90 interactivity: the per-user token rate seen by the slowest decile. These are agentic coding sessions with a human waiting on a stream, so a tail user stuck at half the median token rate is the failure we care about, and an average-E2E target is largely blind to it. Per-GPU throughput is a capacity constraint I need to hold flat, not maximize.

So the table below is **not** a like-for-like scoring of the two PRs, and it is not evidence about #54145's own target. It answers one question only: which policy moves *our* objective on *our* workload.

To be unambiguous about it: #54145 is effective on its own terms. Its controlled single-GPU results — average E2E 2.931s to 2.388s at QPS 12, and the <=3s stable knee moving from 11 to 13 QPS — are a real win against the objective it targets, and nothing I measured casts doubt on them. My arm D says only that its lever does not reach *my* metric on *my* trace. Both policies look worth having; they serve different deployments.

| arm | config | tok/s/GPU | p90 interactivity (tok/s/user) |
|-----|--------|----------:|-------------------------------:|
| A | neither (control) | 8054 | 9.4 |
| B | this PR only, `--prefill-schedule-interval 33` | 7826 | 14.1 |
| D | #54145 only, `--min-prefill-chunk-tokens 4096 --max-prefill-chunk-delay-steps 16` | 8013 | 9.9 |
| E | both | 7743 | 14.1 |

The headline is that only one of the two policies moves our primary metric. The cadence gate lifts p90 interactivity from 9.4 to 14.1, about +50%, at a cost of 2.8% per-GPU throughput. #54145 does not deliver an uplift on this metric on this workload: 9.9 against 9.4 is inside the ~4% run-to-run band I measured on repeat controls, so arm D is indistinguishable from the control on interactivity while being throughput-neutral.

The reason is mechanical, and it follows from the objective split above rather than from any defect in #54145. p90 interactivity is set by how often a decode stream is interrupted by prefill, so the policy that improves it has to reduce interruption *frequency*, which is what a cadence gate does directly. #54145 changes the *shape* of prefill launches — batching small chunks into fewer, larger ones — which improves prefill efficiency but leaves the number of decode-interrupting steps essentially unchanged. Fewer, larger prefill launches are exactly what an average-E2E objective wants, which is why the same mechanism pays off in @F21HGG's setting and does not in mine. It is the right lever for a different metric, not a weaker version of this one.

Two corrections to what I wrote earlier in this thread, from the clean run. First, I had called the cadence gate throughput-neutral based on an earlier runtime-patched build; on the clean image it costs 2.8%. Second, that cost is recoverable — pairing it with the cache-aware admission ordering from #54625 gives 8017 tok/s/GPU with p90 interactivity 13.6, i.e. throughput back to control parity while keeping ~45% of the interactivity gain. That pairing, not the gate alone, is the configuration I would actually propose for this workload.

Config choices, so they are auditable: `--prefill-schedule-interval 33` is the value I tuned on this trace in an earlier sweep. For #54145 I used `--min-prefill-chunk-tokens 4096` (one quarter of the 16,384-token batch budget, so that a deferred chunk is small relative to what one step can absorb) and `--max-prefill-chunk-delay-steps 16` (the upstream default). If @F21HGG would prefer a different operating point for arm D I am happy to rerun it — the threshold is the one parameter I am least confident I picked in your intended range.

On the precedence question @F21HGG raised, arm E is the composed case and it tests the bound directly. The cadence gate sets `defer_prefills`, which upstream consumes in both the running and waiting loops before #54145's threshold and age checks are reached, so while the gate is closed the age-based release cannot fire. That predicts arm E should track arm B rather than landing between B and D, and it does: 7743 tok/s/GPU at p90 interactivity 14.1, against arm B's 7826 and 14.1 — indistinguishable on the objective and within ~1% on throughput. Composed, the pair behaves as the cadence gate alone.

My view on the resolution is unchanged: if these ever compose, the age-based release should win, since it is a deadline while the cadence is a spacing preference, and that is one extra clause on the gate condition (`and not release_small_prefill_chunks`). I also agree with @F21HGG that neither should be enabled together by default without exactly this kind of interaction benchmark.

Caveats. Arms A and B ran 3629s windows; arms D and E ran 929s and 930s. Repeat controls put run-to-run variation at ~0.8% on throughput and ~4% on p90 interactivity, and the two length-matched short controls I have (1513s and 1827s) read 7988/9.0 and 8045/9.5, so arm D's 8013/9.9 sits at or just above the top of that band rather than clearly outside it. The #54145 parameters were also tuned by me rather than by its author, and my KV pool ran ~30% occupied throughout, so there was no eviction pressure in any arm.

### sethforprivacy · 2026-09-02

Field data in support of applying `prefill_schedule_interval` outside DP, from a single-engine `--decode-context-parallel-size 4` deployment (GLM-5.3-Flash NVFP4 on 4× NVIDIA GB10, TP4/DCP4, 24 GiB FP8 KV per rank, 8,192-token scheduler budget, chunked prefill, DFlash speculative decoding k=7). The runtime is a vLLM fork whose scheduler honors the interval on the single engine, so this is a measurement of what the knob does once it takes effect on a non-DP engine — which is exactly the case this PR enables.

**What interval 8 costs under bursty long-prompt arrival.** Idle engine, distinct-prefix prompts of ~6K tokens, 300 output tokens, all requests fired simultaneously:

| interval | c | aggregate tok/s | slowest stream tok/s | TTFT mean / max |
|---|---|---|---|---|
| 8 | 1 | 25.3 | 33.4 | 2.9 / 2.9 s |
| 8 | 4 | 40.7 | 14.6 | 10.2 / 12.1 s |
| 8 | 8 | 39.9 | 5.7 | 23.7 / **34.0 s** |
| 2 | 8 | 49.0 | 7.0 | 18.5 / 24.2 s |
| 1 | 8 | 49.1 | 6.9 | 18.5 / 24.1 s |

Zero preemptions in every run (4.3M-token KV pool), so this is admission cadence, not capacity. A ~6K prompt is one chunk under an 8,192 budget and the scheduler admits one partial prefill at a time, so eight arrivals become eight prefill steps spaced eight decode steps apart: 8 × (~2.6 s prefill + 7 × ~0.25 s decode) ≈ 35 s, matching the measured max. Short prompts (~200 tokens) are unaffected: aggregate scales 33 → 126 tok/s from c=1 to c=16 at every interval tested.

**Two observations that may be useful for the docs/defaults discussion here:**

1. Interval 1 and 2 were indistinguishable (every 6K cell within 1%), so on this shape the decode-protection benefit of a larger interval had already saturated by 2, while its TTFT cost kept growing linearly with the interval.
2. The interval only accounts for ~10 s of the 34 s. The remaining ~24 s at c=8 is the one-partial-prefill admission limit itself; combining this knob with `max_num_partial_prefills` / `long_prefill_token_threshold` is probably the right story for burst arrival, and worth a sentence wherever the option is documented once it applies to non-DP engines.

Happy to re-run any of these shapes on upstream once this lands, if a non-DP validation datapoint would help.

**2. Chunked prefills stall for N-1 steps — confirmed, and the tests do miss it.**

Verified at `scheduler.py:667`:

```python
if defer_prefills and request.is_prefill_chunk:
    req_index += 1
    continue
```

So the contract is **"no prefill work at all this step"**, not "no new admits" — an in-progress chunk is held too. That is inherited from the existing DP path rather than introduced here, but this PR extends it to single-engine, so it's on me to document and cover it. The tests use 8-token prompts that complete in one chunk and genuinely never exercise the stall.

I'll state the contract in the docstring and add a chunked-prefill test that asserts a partially computed request is held for the interval while decodes continue.

**3. Async KV loads don't refresh the interval — confirmed, and intended; I'll say so in a comment.**

Verified: the `load_kv_async` branch at `scheduler.py:1231` sets `WAITING_FOR_REMOTE_KVS`, prepends to the skipped queue and `continue`s, before `prefill_admitted` is set at line 1294.

It should not refresh, though. `num_new_tokens = 0` is set for that path at line 1050, so the step carries no prefill compute for that request — the interval is meant to be timed from steps that actually did prefill work. Refreshing there would start the cadence from a step that did nothing. I'll add a comment at the `continue` so the next reader doesn't have to re-derive it.

**4. DCP=8 and `data_parallel_size == 1` — checked; the serve really is single-engine.**
