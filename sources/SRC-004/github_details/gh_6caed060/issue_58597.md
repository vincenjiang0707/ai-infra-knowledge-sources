## 正文

### Your current environment

RTX 4090 24 GB (spec 1,008 GB/s; memory clock 10,501 MHz per `nvidia-smi -q`), driver 590.48.01 (CUDA 13.1), Ubuntu 24.04, vLLM `0.30.1rc1.dev80+g26f49e336` (nightly cu130 wheel), torch 2.13.0+cu130, transformers 5.17.0. The rented machine is gone, so I do not have `collect_env.py` output; `vllm/v1/metrics/` is unchanged between `26f49e336` and current `main` (`8b84e150`, 2026-09-24).

### 🐛 Describe the bug

`AttentionMetrics` bills full attention (QKV/O weights, KV-cache reads, attention FLOPs) for every one of `num_hidden_layers`. Hybrid models with linear-attention layers only have full attention in a fraction of them: Qwen3.5 and Qwen3-Next use 3 Gated DeltaNet layers for every full-attention layer (`layer_types`, `full_attention_interval: 4`). #55624 handles sliding-window/full alternation but not linear-attention or Mamba layers, so the reported MBU for these models is not physically possible.

Config-only check (no GPU):

```python
from tests.v1.metrics.test_perf_metrics import create_mock_vllm_config
from vllm.transformers_utils.config import get_config
from vllm.v1.metrics.perf import ModelMetrics

mm = ModelMetrics(create_mock_vllm_config(get_config("Qwen/Qwen3.5-4B", trust_remote_code=False)))
print({m.component_type(): getattr(m, "num_hidden_layers", None) for m in mm.metrics})
# {'attn': 32, 'ffn': 32, 'unembed': None}; layer_types has 8 "full_attention" and 24 "linear_attention"
```

Measured with `vllm serve Qwen/Qwen3.5-4B --enable-mfu-metrics` (`VLLM_LOG_STATS_INTERVAL=2`) and `vllm bench serve` (random prompts, 512 output tokens, `--ignore-eos`, 3 × batch requests per cell). The table only uses 2-second log intervals inside the benchmark's wall time that have no prefill in them (`Avg prompt throughput: 0.0`), so it is pure decode:

| batch × context | reported GB/s, median (run 1 / run 2) | intervals above 1,008 GB/s | same cells, layer count corrected (see below) |
|---|---|---|---|
| 8 × 8k | 1,164 / 1,165 | 8/8, 8/8 | 602, 0/9 above |
| 8 × 16k | 1,538 / 1,536 | 10/10, 11/11 | 652, 0/11 above |
| 32 × 8k | 1,821 / 1,831 | 10/10, 10/10 | 645, 0/13 above |

- A device-to-device copy on the same card reaches 918 GB/s (read + write, 3 trials), so the reported numbers are not physically possible.
- Control: Qwen3-4B (dense, same size, same script, same machine) never exceeds the peak: 0 of 32 decode intervals, max 881 GB/s.
- Intervention: counting only the 8 full-attention layers (a small parser reading `layer_types` / `layers_block_type`) removes every over-peak interval on the same cells.

The corrected column is not the right answer either. Dropping the 24 linear-attention layers from attention without billing them as anything leaves out their weights (1,011 M parameters for Qwen3.5-4B, counted from the safetensors headers) and their recurrent state, so the estimate becomes about 0.75× of the bytes actually moved. A correct fix needs a linear-attention component: weights, the per-request recurrent and conv state read and written every step, and nothing that grows with context. Hand accounting of what the model actually reads shows the current code over-bills bytes per decode step by about 1.43× at 8 × 8k and about 2× at 32 × 8k, and under-bills slightly at 1 × 1k.

A smaller related gap: the Qwen3.5 / Qwen3-Next attention has an output gate (`attn_output_gate: true`; `q_proj` is `[8192, 2560]`, twice the query width), which `qkv_weight` / `qkv_proj` do not include.

Limits of this report: one GPU and one hybrid model measured; Qwen3-Next, Jamba, Falcon-H1 only checked at config level. `ncu` DRAM counters were not available in the container, so "bytes actually moved" comes from the parameter and state accounting above, not a hardware counter.

Not a duplicate as far as I can tell: no open or closed issue or PR covers MFU/MBU for linear-attention or Mamba layers (searched 2026-09-25). The two open PRs touching `perf.py` (#55474, #54228) do not touch layer counting.

I'd like to work on the fix (linear-attention component plus layer-type parsing, with tests) if that direction sounds right to the maintainers of this area.

AI assistance (Claude Code) was used to write the scripts, drive the measurements on my rented GPU and draft this report. I reviewed the logs and the results.

### jayzuccarelli · 2026-09-25

Root cause is in vllm/v1/metrics/perf.py:432-450: SlidingWindowAttentionParser only reads layer_types when sliding_window > 0 and only counts "sliding" entries, so linear_attention layers are never subtracted and AttentionMetrics._layer_counts (perf.py:552) bills all num_hidden_layers as full attention. Reproduced on current main with a Qwen3NextConfig(num_hidden_layers=32, full_attention_interval=4): layer_types is 8 full / 24 linear, but _layer_counts returns (32, 32, 0). Since dropping those layers alone would under-bill (your 0.75x point), the fix does both: count linear layers from layer_types independent of sliding_window and exclude them from AttentionMetrics, and add a LinearAttentionMetrics component for GDN layers that bills their weights plus the per-request recurrent and conv state read/written each step, with no context term. Mamba2 layers_block_type and the attn_output_gate q_proj width I'd leave as follow-ups. I'll open a PR with a regression test in tests/v1/metrics/test_perf_metrics.py.
