# [Issue #58733] [Bug]: DeepSeek-V4-Flash + DFlash speculator fails at startup (fp8_ds_mla draft KV dtype; 16384 vs 4096 hidden states)

source: https://github.com/vllm-project/vllm/issues/58733
state: open | updated: 2026-09-25T18:55:52Z
labels: bug, deepseek, DSv4

## 正文

### Your current environment

vLLM `main` @ 73a78e6f1f, 2× B300 (SM100), TP2 + expert parallel. Reproduced with `--load-format dummy` (the failures are at startup, before any weights matter).

### 🐛 Describe the bug

`DeepSeek-V4-Flash` + the `RedHatAI/DeepSeek-V4-Flash-speculator.dflash` DFlash drafter fails at startup on current `main`, in one of two ways depending on the drafter's KV cache dtype.

**1. fp8 target KV cache (default draft KV dtype): no attention backend for the drafter**

```bash
vllm serve RedHatAI/DeepSeek-V4-Flash --tokenizer-mode deepseek_v4 --trust-remote-code \
  --max-model-len 131072 --tensor-parallel-size 2 --enable-expert-parallel \
  --block-size 256 --kv-cache-dtype fp8 --load-format dummy --enforce-eager \
  --speculative-config '{"method":"dflash","model":"RedHatAI/DeepSeek-V4-Flash-speculator.dflash","num_speculative_tokens":7}'
```

The drafter's sliding-window layers inherit the target's `fp8_ds_mla` KV cache dtype, which no non-MLA backend supports:

```
ValueError: No valid attention backend found for cuda with AttentionSelectorConfig(head_size=256, dtype=torch.bfloat16, kv_cache_dtype=fp8_ds_mla, block_size=256, use_mla=False, ..., has_sliding_window=True, ...). Reasons: {FLASHINFER: [kv_cache_dtype not supported], FLASH_ATTN: [kv_cache_dtype not supported, FP8 KV cache requires FA3 on SM90, FA4 with head_size=512 on SM90, or FA4 on SM100], TRITON_ATTN: [kv_cache_dtype not supported], FLEX_ATTENTION: [kv_cache_dtype not supported], TURBOQUANT: [kv_cache_dtype not supported, sliding window not supported]}.
```

(Forcing `"attention_backend": "FLASH_ATTN"` in the speculative config fails the same way: `kv_cache_dtype not supported`.)

**2. bf16 draft KV cache: hidden-state width mismatch in `propose`**

Same command, with `"attention_backend":"FLASH_ATTN","kv_cache_dtype":"auto"` added to the speculative config. The backend check passes, and the profile run then fails:

```
File "vllm/v1/worker/gpu/model_runner.py", line 947, in profile_run
File "vllm/v1/worker/gpu/model_runner.py", line 887, in _dummy_run
File "vllm/v1/worker/gpu/spec_decode/dflash/speculator.py", line 376, in propose
    self.hidden_states[:num_target_tokens].copy_(hidden_states[:num_target_tokens])
RuntimeError: The size of tensor a (16384) must match the size of tensor b (4096) at non-singleton dimension 1
```

`aux_hidden_states` is empty here, so `propose` falls back to the target's final hidden states. For DeepSeek-V4 those are 16384 wide (4 hyper-connection streams × 4096), while the drafter's buffer is 4096 wide. It looks like DeepSeek-V4 doesn't expose aux hidden states for DFlash, similar to what #55682 adds for GLM-5.3-Flash.

**Expected:** DeepSeek-V4-Flash + its DFlash speculator starts. Suggested fixes: pick a draft KV cache dtype the draft's backend supports instead of inheriting `fp8_ds_mla`, and capture the aux hidden states DFlash expects from DeepSeek-V4.

For reference, `deepseek-ai/DeepSeek-V4-Flash-DSpark` (bundled DSpark drafter) starts fine on the same setup.

Found while testing KV cache grouping for #58638. AI assistance (Claude Code) was used to reproduce and write this up; I reviewed it.

### he-yufeng · 2026-09-25

Taking the first half of this (the KV cache dtype inheritance). Root cause: when the target's sparse MLA layers are built, `_canonicalize_sparse_mla_kv_cache_dtype` writes the canonical `fp8_ds_mla` back into the shared `cache_config.cache_dtype`. `load_dflash_model` then hands that same cache_config to the drafter untouched whenever the speculative config doesn't pin a `kv_cache_dtype`, so the drafter's sliding-window layers get asked for a backend that serves `fp8_ds_mla` and none exists. Fix: a non-MLA drafter no longer inherits the ds_mla family, it falls back to `auto`; an explicit speculative `kv_cache_dtype` still wins. This also unbreaks any other sparse-MLA target + non-MLA drafter combo on quantized KV (GLM-5.3-Flash + DFlash2 + `--kv-cache-dtype fp8` hits the same wall). The aux hidden-state half I'll leave to the #55682 line of work, since it needs acceptance validation on hardware I don't have. PR in a moment.
