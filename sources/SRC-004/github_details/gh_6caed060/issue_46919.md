# [Issue #46919] [Bug][Metrics] `get_metrics_snapshot()` raises on unknown metric types, crashing LLM.get_metrics() and the ORCA header path

state: open | updated: 2026-09-26T01:46:05Z

## 正文

### 🐛 Describe the bug

`vllm/v1/metrics/reader.py::get_metrics_snapshot()` dispatches over
`metric.type` for every `vllm:`-prefixed entry in
`prometheus_client.REGISTRY`, but its dispatch is closed over
`{gauge, counter, histogram}`. The trailing `else` branch raises:

```python
else:
    raise AssertionError(f"Unknown metric type {metric.type}")
```

(`vllm/v1/metrics/reader.py:141` on current `main`.)

### Impact

`prometheus_client` ships `Summary`, `Info`, `Stateset`, and `untyped`
as first-class metric types, and OTel's `gen_ai.server.request.duration`
semantic convention is conventionally exported as `Summary`. The day
anyone adds a `Summary`-typed metric (or any custom collector that
returns `metric.type == \"untyped\"`) prefixed `vllm:`, two live code
paths crash:

1. **`vllm/v1/engine/llm_engine.py:380` → public `LLM.get_metrics()`**
   offline library API. Every offline caller reading in-memory metrics
   would crash.
2. **`vllm/entrypoints/serve/utils/orca_metrics.py:90` → `metrics_header()`**
   on `/v1/chat/completions` requests that opt into the
   `endpoint-load-metrics` ORCA header. Every such requests returns
   HTTP 500.

### Root cause

The available prometheus_client family of metric types is wider than
the three the reader handles, and the trailing branch fails loudly
instead of degrading gracefully.

### Suggested fix

Replace the `raise AssertionError(...)` with a graceful
`logger.debug(\"Skipping unknown metric type %s for metric %s\", ...)`
+ `continue`, matching the existing unknown-type handling pattern
already used elsewhere in the codebase (e.g.
`vllm/distributed/kv_transfer/kv_connector/v1/offloading/metrics.py:189`,
`:216`, `:451`).

### Relationship to existing work

- [PR #35649](https://github.com/vllm-project/vllm/pull/35649)
  \"Replace bare AssertionError with specific exception types\" touches
  the same line and proposes `raise ValueError(...)`. That keeps the
  production hazard: the reader still crashes both live consumers; it
  just does so with a different exception class. The behaviour this
  issue proposes (skip, not raise) is materially different: it
  prioritises availability for the library/header consumers, which were
  never in a position to read a metric type they have no dataclass for
  anyway.

### Environment

Found while auditing the V1 metrics subsystem on `main` at
`867fd5e8ed6b0bfcf84b24f82658c9fb698a6d35` (2026-06-27). The bug is
not environment-specific: it reproduces whenever any future
`vllm:`-prefixed metric uses a type outside `{gauge, counter, histogram}`.
