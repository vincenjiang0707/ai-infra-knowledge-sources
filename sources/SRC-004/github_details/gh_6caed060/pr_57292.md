## Draft — dependency and duplicate-work review required

Partially addresses #56461 / #56702. **Do not merge as a standalone complete SM120 fix.**

### Scope

The proposed change selects a 64-token sparse-MLA/indexer kernel page on SM120 and a 64-token SWA cache page instead of treating SM120 like SM100. The three backend declarations are in:

- `vllm/models/deepseek_v41/sparse_mla.py`
- `vllm/models/deepseek_v41/nvidia/flashinfer_sparse.py`
- `vllm/v1/attention/backends/mla/indexer.py`

The SWA allocation is in `vllm/models/deepseek_v41/attention.py`. Other architecture branches are intended to remain unchanged.

For DeepSeek-V4.1 ratio-1/ratio-2 layers, a 64-token kernel block yields 64/32-state indexer pages. The pinned DeepGEMM **SM120 FP8** path still rejects page32; allowing it is a separate dependency, not something this Python patch fixes.

### Duplicate-work check (2026-09-17)

Re-read #56461 / #56702 and checked open PRs referencing them and SM120 block geometry. Existing #56509 substantially overlaps this PR (including the SWA and backend declarations). I am keeping this PR draft and am not opening another geometry PR or claiming this one is non-duplicative. The two should be consolidated with the maintainers before further advancement; a smaller test suite or helper extraction alone is not a material reason to duplicate the fix.

The **separate** FP8 page32 kernel gap is now proposed as vllm-project/DeepGEMM#14. This is distinct from the vLLM geometry PRs.

### Required dependency integration

1. Merge/resolve the DeepGEMM FP8 page32 support, then update both `cmake/external_projects/deepgemm.cmake` and `tools/install_deepgemm.sh` to the accepted fork commit. Both currently pin `a6bbb8000161c0dc3a85a0300a905f76898a7913`.
2. FlashInfer dual-cache prefill needs 32-token extra pages. Existing flashinfer-ai/flashinfer#5174 already addresses this with tests; no duplicate PR is being opened.
3. The older deployed FlashInfer 0.6.18 needed a local `(8,1152)` decode specialization. Inspection of current FlashInfer main shows runtime top-k in the DSV4 decode launcher, so the old fixed-specialization workaround should not be proposed unchanged upstream.

It is removed in the local working tree because validation needs to respect the manager/kernel block distinction and initialization order; that removal has NOT yet been pushed. This remains a review item, not a completed fix.

- Do not attribute the old image's `topk=1152` to DSpark without tracing its metadata. #56461 documents the image-prefix/window contribution; the earlier DSpark-only explanation was not established.

### Validation and provenance

An earlier **backport** of the geometry changes, together with a DeepGEMM 2.6.1 page32 backport and FlashInfer decode/prefill patches, started on 8x RTX PRO 5000 72GB (SM120) with TP8/EP, FP8 KV, DSpark K=5, `--block-size 64`, and `--max-model-len 262144`.

The recorded pod was Ready with no restarts at the end of that experiment. Pod-local `/v1/models` succeeded, and `/v1/chat/completions` returned `323` for `17*19`. This is only a short serving smoke test, not a precision evaluation, long-context validation, or proof of correctness of this PR head against current dependency pins.

The separately tested DeepGEMM fork patch has 72 added correctness cases and 10 existing cases passing on SM120; details and limitations are in vllm-project/DeepGEMM#14.

Submission-time `git diff --check` passed on the local vLLM branch/worktree diff. This update changes the PR description only; it does not assert that this PR head's unit tests, full pre-commit suite or current-main end-to-end run were rerun. Human review, applicable test reproduction, model evaluation and dependency-closed build validation are outstanding.
