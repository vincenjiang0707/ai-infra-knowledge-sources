## Summary

TurboQuant KV cache (`k8v4`) combined with **hybrid MoE models** (Qwen3.6-35B-A3B-FP8 — 30 MoE + 10 dense layers, E=256, top_k=8, `block_shape=[128,128]`) **does not work on Ampere GPUs** (SM 80-86). Multiple code paths assume Hopper+ (SM ≥ 89) and hybrid model geometry is not handled correctly.

We have identified and fixed 13 issues, packaged as a runtime monkey-patch applied at container startup. All patches are available as open source:

**Repository: https://github.com/Sandermage/genesis-vllm-patches**

## Environment

- **vLLM**: `0.19.1rc1` nightly (`vllm/vllm-openai:nightly` as of 2026-04-16)
- **GPUs**: 2× NVIDIA RTX A5000 24 GB (SM86, Ampere), `tensor_parallel_size=2`
- **Model**: `Qwen/Qwen3-35B-A3B-FP8` — hybrid MoE, `block_shape=[128,128]`
- **Config**: `kv_cache_dtype=turboquant_k8v4`, `max_model_len=163840`, `gpu_memory_utilization=0.905`
- **Driver**: NVIDIA 570.211.01, CUDA 12.8

## Key Findings

1. **FP8 on Ampere works via Marlin** — Triton FP8 kernels must be bypassed (patches 1-2)
2. **TurboQuant hybrid model support is incomplete** — multiple issues with skip-layer handling (patches 4-7, relates to #39931)
3. **Expert Parallelism NOT needed** for 3B active params — TP=2 sufficient
4. **160k context achievable** on 2×24 GB with TQ K8V4

So basically, Qwen3.6-35B-A3B is a hybrid model — it has 30 MoE layers + 10 dense attention-only layers, which means `is_hybrid = True`. And TurboQuant just doesn't expect that at all right now.

Here's the chain of errors we hit, one after another:

**Patch 4** — the very first wall. In `arg_utils.py` there's a hard block:
```
NotImplementedError: TurboQuant KV cache is not supported for hybrid 
(attention + Mamba) models. Boundary layer protection requires 
uniform attention layers.
```
Model doesn't even start. The fix removes this blanket rejection and instead detects which layers are full-attention (using `layer_types`, `layers_block_type`, or `attn_type_list` depending on the model architecture) so TQ can work around them.

**Patch 5** — once you get past that, `unify_kv_cache_spec_page_size()` crashes:
```
NotImplementedError: The page size of the layer is not divisible by 
the maximum page size. Cannot unify by adjusting block_size.
```
TurboQuant k8v4 with `head_dim=128` gives `page_size = 12416 bytes`, while the DeltaNet/Mamba state is ~12.6 MiB. Obviously not divisible. The original code just throws. We pad the max page size up to the nearest LCM of all smaller sizes — memory overhead is <0.1%.

**Patch 6** — more subtle. `interface.py` computes `attn_page_size_1_token` using `FullAttentionSpec`, but TurboQuant has a packed K|V layout with different per-token sizes. So the mamba padding calculation ends up wrong — no crash, but cache allocation is off.

**Patch 7** — when you set `kv_cache_dtype=turboquant_k8v4` globally, the backend selector in `cuda.py` forces `TURBOQUANT` backend for every layer, including Mamba/skip layers that don't actually use TQ. Those layers don't have `turboquant_*` dtype → shape mismatch at runtime. Simple fix: check dtype per-layer, fall through to FlashAttn for non-TQ layers.

All of this is closely related to #39931 which addresses TQ hybrid support. Our patches are basically the same idea, just adapted for the current nightly where #39931 isn't merged yet.

I don't have the raw tracebacks saved anymore since we've been running with patches applied for a while, but I can try to reproduce them on a clean container if that would help.

Two things to add to this tracking issue: a hardware-generalization datapoint, and a limitation that I believe lives in the upstream `profile_run` / `determine_available_memory` path but which I can so far only reproduce *through* your patches (caveat spelled out below).

**1. Generalizes to Ada SM89 + production.** Your reference rig is 2× A5000 (SM86). We run `vllm-qwen36-genesis-tq` (v7.72.5 on nightly `01d4d1ad3`) on **2× RTX 4090 (SM89), TP=2 + EP=2**, `turboquant_k8v4`, `max_model_len=262144`, gpu-util 0.82. KV cache **~2.0M tokens**, **35h+ continuous production soak clean**, full CUDA graphs, vision OK. So the 13-patch stack is not A5000-specific — it holds on Ada and under sustained multi-tenant load.

**2. A `profile_run` / `determine_available_memory` large-batch limitation.** With `--max-num-batched-tokens > 4096` we hit one of two crashes depending on whether the profile-shape cap (your P72) is engaged:

- **At boot (no profile cap):** Dynamo fake-tensor mismatch during `determine_available_memory()`'s profiling forward:
  ```
  mul(FakeTensor(..., 65536, 128), FakeTensor(..., 16*s59, 128))   # 65536 = 2 × max_num_batched_tokens
  ```
  The TQ-k8v4 GQA path can't specialize that symbolic shape at large batch, so the profiling forward never completes.
- **At runtime (profile shape capped at 4096 to dodge the above):** the engine boots, but the `qwen3_next` (GatedDeltaNet) compiled buffers are then **sized from the profiled shape (4096), not from `--max-num-batched-tokens`**. Any single combined forward in `(4096, max_num_batched_tokens]` overflows:
  ```
  RuntimeError: setStorage: sizes [5536, 16, 128] ... requiring a storage size of 22675456
  are out of bounds for storage of size 16777216         # qwen3_next.py:495
  # 16777216 = 4096×16×128×2 (buffer @ cap) ; 22675456 = 5536×16×128×2 (real forward)
  ```
  This took real mixed traffic (long-context + decode co-scheduled into one step) to trigger ~1h25 into a deploy; synthetic single-prefill / low-concurrency benches don't reach a forward in that window.

The common root is that **GDN buffer allocation is coupled to the `profile_run` shape**, and the profiling forward can't specialize the TQ path at the true `max_num_batched_tokens`. Net effect: batch is effectively pinned at the profile cap; we're stuck at 4096 and can't use the larger batch the ~2M-token KV cache would otherwise allow.

**Honest caveat (so this isn't mistaken for a clean upstream repro):** I have **only** reproduced this on your patched image. Stock vLLM TQ+hybrid doesn't boot here without your patches 4-7, so I can't yet isolate it on pure upstream. The failing functions (`determine_available_memory`, the profiling forward's Dynamo specialization) are upstream, but they only fire through the TQ-k8v4 kernel your tree enables. **I'm happy to put together a minimal repro** — ideally a stock-supported GDN-hybrid config at large batch with TQ off, to localize whether the fake-tensor mismatch is upstream-intrinsic or patch-coupled — if that would help you or the maintainers. Just point me at the shape you'd want exercised.

Also noting #40384 (your Patch 9, token-capacity filter) is still OPEN — that one merging would let everyone drop one more patch.
