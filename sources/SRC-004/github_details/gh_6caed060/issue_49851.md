## Summary

On vLLM 0.25.1 / ROCm 7.15, loading a multimodal model on AMD Radeon AI PRO
R9700 (RDNA4, gfx1201) fails during model initialization inside the vision
encoder attention path. Every worker rank fails identically. Text-only models on
the same build, same hardware, same launch path load and serve fine.

## Environment

- vLLM: `0.25.1+rocm715` (built from tag `v0.25.1`, commit `752a3a5044`)
- PyTorch: `2.11.0+rocm7.15.0a20260721`
- ROCm: 7.15 (TheRock nightly, `rocm-sdk` wheels, `gfx1201` device package)
- Triton: `3.7.1+git0263a6a6.rocm7.15.0a20260721`
- GPU: 6x AMD Radeon AI PRO R9700 (gfx1201 / RDNA4), 32 GB each
- OS: Fedora 43 container, host Fedora 43
- Model: `cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit`
  (resolves to `Qwen3_5MoeForConditionalGeneration`)
- Launch: `--tensor-parallel-size 2 --pipeline-parallel-size 3
  --distributed-executor-backend ray`

Note the path: `custom_op.forward_hip` → `mm_encoder_attention.forward_cuda` →
`_forward_sdpa` → `vit_torch_sdpa_wrapper`. The HIP dispatch lands in the
`forward_cuda` implementation of encoder attention.

## What rules out the obvious alternatives

- **Not distributed / not PP-related — verified single-node.** Reproduced with
  `--tensor-parallel-size 2 --distributed-executor-backend mp`, on one node,
  with no Ray and no pipeline parallelism at all: both `Worker_TP0` and
  `Worker_TP1` fail with the identical traceback. It also fails on all six ranks
  of the TP=2/PP=3 Ray configuration (`Worker_PP0_TP0` … `Worker_PP2_TP1`),
  local and remote alike.
- **Not the hardware or the build.** The same image on the same 6 GPUs loads and
  serves `Qwen/Qwen2.5-14B-Instruct-AWQ` (text-only, `Qwen2ForCausalLM`) with
  the identical launch command, completes startup, and answers requests. The
  only difference is the presence of a vision tower.
- **Not a device-visibility issue.** `invalid argument` here, not `invalid
  device ordinal`; the error is raised by a kernel launch inside the ViT
  attention op, after device init has succeeded on every rank.

## Reproduction

1. ROCm 7.15 + vLLM 0.25.1 on gfx1201.
2. Single node, no Ray, no PP — this is enough to reproduce:
   ```
   vllm serve cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit \
     --tensor-parallel-size 2 \
     --distributed-executor-backend mp \
     --gpu-memory-utilization 0.88 --max-model-len 8192 --trust-remote-code
   ```
3. Fails during model load in the vision-encoder attention path, after the
   safetensors shards finish loading. Engine core initialization fails.

Swap to any text-only model on the same build to confirm the rest of the stack
is healthy.

## Expected

Either the ViT SDPA path works on gfx1201, or vLLM falls back to a supported
attention backend for the vision encoder on RDNA4 instead of failing to load.

## Additional context

Found while retesting
[#49826](https://github.com/vllm-project/vllm/issues/49826) (cross-node PP on
this hardware, which 0.25.1 fixes). This is a separate, unrelated blocker that
prevented testing that issue with a multimodal model. Happy to gather
`AMD_SERIALIZE_KERNEL=3` output or test a proposed backend fallback.

### bertinillo · 2026-08-01

Follow-up to my earlier comment, where I said we hadn't isolated why our own
build doesn't hit the `hipIpcGetMemHandle` failure. We've now dug into it. The
short version: the difference appears to be **which GPU targets the shipped
RCCL was built for**, not the RCCL version number itself.

## What differs between the two images

| | Our working build | Stock `vllm-openai-rocm:v0.26.0` |
|---|---|---|
| vLLM | `0.25.1+rocm715` | `0.26.0+rocm723` |
| torch | `2.11.0+rocm7.15.0a20260721` | `2.11.0+gitd0c8b1f` |
| RCCL | `2.30.4` (ROCm `7.15.0.0-9999-03d8462e`) | `2.27.7` (ROCm `7.2.3.0-90-c2d9476115`) |

Every complete `gfx` architecture name appearing in each `librccl.so`:

- **Ours (2.30.4):** `gfx906 gfx908 gfx90a gfx942 gfx950 gfx1030 gfx1100
  gfx1101 gfx1102 gfx1151 gfx1200 gfx1201 gfx1250`
- **Stock (2.27.7):** `gfx906 gfx908 gfx90a gfx942 gfx950` — CDNA only, no
  complete RDNA architecture name.

Caveat so this isn't overread: both libraries also contain short family-prefix
strings (`gfx9`, `gfx12`, `gfx95`). Those appear in *both*, including the one
that works, so they are not evidence of target support either way. What
differs is the presence of complete RDNA arch names.

That is consistent with the stock image's RCCL having been built without
`gfx1201` among its offload targets, which would explain
`hipIpcGetMemHandle failed : invalid argument` when setting up the direct-P2P
transport between two gfx1201 devices.

**This is inference from binary strings, not a definitive target enumeration.**
Direct enumeration wasn't possible in that image — `roc-obj-ls` is broken there
(`Can't locate File/Which.pm`) and the library carries no
`__CLANG_OFFLOAD_BUNDLE__` magic to parse. If someone on the vLLM/ROCm side can
confirm the actual `AMDGPU_TARGETS` used for the RCCL in this image, that would
settle it.

## What this is *not*

It's **not** that RCCL 2.27.7 is incapable of gfx1201. ROCm/rocm-systems#5480
has someone building RCCL 2.27.7 from the rocm-7.2.1 branch *with* a gfx1201
target on the same class of hardware (dual R9700). So the version number alone
isn't the story — the build configuration is.

Worth noting the ROCm 7.1.0 release notes enable gfx1150/1151/1200/1201 for
components like hipBLAS but don't mention gfx1200/gfx1201 in the RCCL section.

## Relationship to ROCm/rocm-systems#5480

That issue is **related but a distinct failure**, and I don't want to conflate
them:

| | #5480 | Ours |
|---|---|---|
| `ncclCommInitRank` | completes successfully | **fails** at `hipIpcGetMemHandle` |
| Symptom | deadlock at first collective, GPUs pinned at 100% | hard fail during init, exit 1 |
| `NCCL_P2P_DISABLE=1` | no effect, still deadlocks | gets past init to `Init COMPLETE` |
| RCCL | 2.27.7 built *with* gfx1201 target | 2.27.7 as shipped in the stock image |

Same hardware family and same general area (RDNA4 P2P transport), different
observed fault. Possibly the same underlying weakness in the RDNA4 P2P path
surfacing two ways, but I'm not claiming that.

## Correction to my earlier comment

I previously suggested `NCCL_P2P_DISABLE=1` as a lead. Tempering that: if the
shipped RCCL genuinely lacks gfx1201 device code, disabling P2P would not
rescue a real workload — the SHM transport still needs device-side collective
kernels. We stopped that run before any collective executed, so we never
established it does more than get past init. Treat it as a diagnostic
observation only. #5480 reporting `NCCL_P2P_DISABLE=1` as ineffective for their
deadlock is consistent with that caution.

## Scope of what we actually demonstrated

To be precise about the limits: we showed that **the default P2P path fails for
TP>1 on gfx1201 with this image**, for one model and flag combination. We did
**not** demonstrate that no TP>1 configuration can work — we never tried, for
example, `NCCL_P2P_DISABLE=1` with a text-only model, and SHM fallback did
reach `Init COMPLETE` in our own testing. So the practical takeaway is "the
out-of-the-box multi-GPU path is broken here," not "multi-GPU is impossible."

## Separately, on RDNA coverage in this image

Unrelated to RCCL, but in the same vein: the image ships
`AITER_ROCM_ARCH=gfx942;gfx950` and `MORI_GPU_ARCHS=gfx942;gfx950`, and our run
logged `AITER is not found or not supported on the current platform`. AITER is
a separate kernel library from RCCL, so this doesn't corroborate the RCCL
finding — it's an independent data point that RDNA4 coverage in this image is
partial. Notably its PyTorch *is* built for gfx1201
(`PYTORCH_ROCM_ARCH=...;gfx1201;...`), so the image isn't CDNA-only across the
board.

## Still unverified on our side

- Whether our working stack's intra-node TP=2 pairs actually exercise the
  direct-P2P path at all (we don't run with `NCCL_DEBUG`, so we have no
  transport lines to confirm it).
- The ViT/SDPA fix in this issue remains untested by us — the P2P failure
  blocks reaching the vision encoder.

### Diagnosis: ROCM_SDPA_WRAPPER_INVALID_ARGUMENT (80% confidence)

### Root Cause
`torch_sdpa_wrapper` throws `invalid argument` when concatenating vision transformer context layers. On RDNA4 / gfx1201 hardware, PyTorch's native SDPA hipBLAS backend rejects unaligned head dimensions or causal mask flags that differ from standard RoCm MI300 configurations.

### Immediate Troubleshooting Steps
1. **Enable PyTorch SDPA Math Fallback**: Disable fused FlashAttention / memory-efficient attention backends:
   ```python
   torch.backends.cuda.enable_flash_sdp(False)
   torch.backends.cuda.enable_mem_efficient_sdp(False)
   torch.backends.cuda.enable_math_sdp(True)
   ```
2. **Inspect Vision Encoder Inputs**: Ensure image patch tensors entering `mm_encoder_attention.py` have contiguous memory layouts before passing into `torch.cat`.
