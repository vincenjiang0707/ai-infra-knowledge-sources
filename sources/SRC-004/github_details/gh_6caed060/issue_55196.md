# [Issue #55196] [RFC]: fp8 KV cache gives little to no memory benefit on Mamba/GDN hybrid models

source: https://github.com/vllm-project/vllm/issues/55196
state: open | updated: 2026-09-25T20:07:43Z
labels: quantization

## 正文

**TL;DR**
- `--kv-cache-dtype fp8` roughly doubles KV cache capacity on attention-only models (measured 2.00x), but on Mamba/GDN + attention hybrids it gives 1.84x at 32k context and 1.00x (no gain) at short context.
- Root cause is the known hybrid page-pinning behavior (#37121, #40696): the Mamba state is not quantized by `--kv-cache-dtype` and all groups share one uniform page, so the bf16 Mamba page pins bytes-per-block and the fp8 attention page cannot shrink the pool.
- Fix is parity work: quantize the Mamba state too (SGLang already does this at int8) and/or decouple per-group page size (SGLang/TRT-LLM/llama.cpp already use separate pools). This RFC contributes the fp8-capacity characterization plus wiring a fix into vLLM.

### Motivation.

fp8 KV cache is advertised as a ~2x capacity/concurrency lever. On Mamba/attention hybrids (Falcon-H1, Qwen3-Next, Granite-4, Jamba, Nemotron-H) that lever is mostly or entirely dead, and there is no caveat in the docs. Numbers below are from vLLM's own `get_kv_cache_configs`/`get_kv_cache_capacity` (offline, no forward pass; `gpu_memory_utilization=0.85`, `max_model_len=32768`, default `block_size`, A10G). For Qwen2.5-3B and Falcon-H1 the offline bf16 result reproduces the live-served `GPU KV cache size` exactly, which validates the method; gpt-oss-20b is offline-computed and not anchored to a live run.

| model | bf16 KV tokens | fp8 KV tokens | ratio |
|---|---|---|---|
| Qwen2.5-3B (attention only, live-anchored) | 334,256 | 668,512 | **2.00x** |
| gpt-oss-20b (sliding-window + full, offline/unanchored) | 562,283 | 1,124,567 | **2.00x** |
| Falcon-H1-1.5B (Mamba + attention, live-anchored) | 603,229 | 1,111,381 | **1.84x** |

Falcon-H1 by context length: 512 tok 1.00x, 1024 tok 1.00x, 2048 tok 1.51x, 8192 tok 1.76x, 32768 tok 1.84x. Sliding window alone does not cause this (gpt-oss gets a clean 2.00x); the effect requires a non-attention group co-resident in the pool.

The mechanism is already filed. #37121 reports the ~7x KV memory over-estimation on hybrids: the attention block size is inflated up to the larger Mamba page, and the Mamba state is padded to match, so both grow to a common page. #40696 reports the prefix-caching consequence of the same block-size pinning. This RFC adds the fp8-capacity consequence and proposes the fix.

Why fp8 fails to help, concretely:
1. `get_mamba_state_dtype_from_config` returns bf16 regardless of `--kv-cache-dtype`, so the Mamba page is a fixed ~1.59 MB.
2. `get_uniform_page_size` asserts one page across all groups, and `_align_hybrid_block_size` (`vllm/platforms/interface.py`) enforces `attention_page >= mamba_page` by inflating the attention `block_size` (Falcon-H1: 1568 tokens at bf16, 3120 at fp8). The per-token attention page halves exactly under fp8 (1024 -> 512 B), so the block size roughly doubles (it lands one alignment step short of 2x), leaving the product pinned to the Mamba page.
3. Once pages are unified, `num_blocks` is effectively `available_memory // (uniform_page * num_groups)` (in code, `available_memory // bytes_per_block` where `bytes_per_block` is the max over groups of the summed page size). That uniform page is 1,605,632 B (bf16) vs 1,597,440 B (fp8) — essentially unchanged, so `num_blocks` moves only 405 -> 407. fp8's only gain comes from the larger block, dragged below 2x by the never-shrinking Mamba group and coarse block quantization (a short request fits in one attention block either way — the 1.00x rows).

### Proposed Change.

Two independent levers; either helps, together they recover the full 2x. Neither is novel — both exist in other engines — so the deliverable is the vLLM implementation plus the characterization above.

1. **Quantize the Mamba state alongside attention KV.** vLLM already exposes `--mamba-cache-dtype` / `--mamba-ssm-cache-dtype`, but the allowed values are only `auto/float32/float16/bfloat16` (no fp8 or int8), so today the state cannot be shrunk at all. This is the natural insertion point. SGLang ships state quantization at int8 (`--enable-int8-mamba-checkpoint`, `Int8CheckpointStore`, cited as ~2x prefix capacity), and Quamba2 (arXiv:2503.22879) quantizes the ssm_state at int8. Not yet done anywhere: fp8, and the conv_state (not just ssm_state). The recurrent path is the most quantization-sensitive component (Q-S5, arXiv:2406.09477), so this must ship with its own accuracy check (perplexity + one downstream task), not on an assumption of safety. Larger change: needs a quantized Mamba kernel path.

2. **Decouple per-group page size.** Relax the single-uniform-page invariant so an attention group keeps its smaller fp8 page instead of being inflated to the Mamba page; the pool tracks per-group bytes. This is what SGLang (separate `MambaPool`), TensorRT-LLM (separate cache managers), and llama.cpp (`llama_memory_hybrid`) already do via separate pools; academic cover in Jenga (SOSP 2025) and AVMP (preprint, arXiv:2605.22416). KV-cache-manager change only, no kernels.

Suggested phasing: (2) first as a self-contained KV-cache-manager PR that removes the pinning for the attention group (recovers most of the long-context gain, kernel-free). (1) as a follow-up that also shrinks the Mamba group, gated on the accuracy check. The characterization/probe can land as a test that asserts fp8 recovers ~2x on a small hybrid.

Out of scope: the sliding-window in-flight admission reserve (#54703, different mechanism) and block-pool logging (#54840).

### Any Other Things.

Honest severity: the 1.00x rows are at short context, where KV is not the bottleneck, so the practical impact there is small. The impact that matters is long context, where fp8 under-delivers by ~8-16% on Mamba hybrids (1.84x vs 2.00x at 32k). Real and fixable, on a growing model class; not a crash or correctness bug.

Limitations of the measurement: one anchor hybrid (Falcon-H1) plus two attention-only controls. The mechanism is architecture-level (any non-quantized co-resident group pins the shared page), so it should generalize across Qwen3-Next/Granite-4/Jamba/Nemotron-H, but that is asserted, not yet measured per-model.

Reproduction (offline, no GPU forward pass, so it dodges any fp8 attention-kernel issues): build a `VllmConfig` via `EngineArgs.create_engine_config()`, construct per-layer `KVCacheSpec`s (Mamba shapes from `get_mamba_state_{shape,dtype}_from_config`), run `_align_hybrid_block_size` for the resolved backend, then call `get_kv_cache_configs` with a hypothetical `available_memory` and read `get_kv_cache_capacity`. bf16 reproduces live-served KV tokens exactly, which validates the fp8 numbers.

Not claimed as novel: the state-vs-KV asymmetry (Marconi, MLSys 2025), page decoupling (SGLang/TRT-LLM/llama.cpp, AVMP, Jenga), or int8 Mamba-state quantization (SGLang, Quamba2). The unpublished pieces are the fp8-capacity characterization on hybrids and, if pursued, fp8 + conv_state quantization with an accuracy frontier.
