### 🐛 Describe the bug

`Llama3JsonToolParser.extract_tool_calls_streaming` decides between content and tool call from the first character only (`current_text.startswith("{")` or `<|python_tag|>`), and never falls back. So streaming and non-streaming disagree on three kinds of plain Llama 3.x output:

1. **A plain answer that starts with `{` but is not a call** (a JSON answer, `{}`, `{"a": 1} is a dict`). Non-streaming returns it as `content`. Streaming returns `content=None` and no tool calls, so the answer disappears.
2. **A call with empty arguments.** Non-streaming gives `arguments='{}'`, streaming gives `arguments=''`.
3. **Text before the call** (`Let me check. {"name": ...}`; with the default `skip_special_tokens=True` this is also what a `<|python_tag|>` call looks like after detokenization). Non-streaming returns the call and drops the text (the docstring says surrounding text is ignored). Streaming returns everything, JSON included, as `content`, with no tool call.

Case 1 is the most serious one: a client that streams loses the model's whole reply.

```python
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
from vllm.tokenizers import get_tokenizer
from vllm.tool_parsers.llama_tool_parser import Llama3JsonToolParser

tok = get_tokenizer("unsloth/Llama-3.3-70B-Instruct",
                    revision="99cd0d2c829e92a67c844f9144c2509632e5c87f")
tools = [{"type": "function", "function": {"name": "get_weather", "parameters": {
    "type": "object", "properties": {"city": {"type": "string"}}}}},
         {"type": "function", "function": {"name": "get_time", "parameters": {
    "type": "object", "properties": {}}}}]
req = ChatCompletionRequest(model="m", messages=[{"role": "user", "content": "hi"}],
                            tools=tools, tool_choice="auto")

def stream(text):
    """One token per delta."""
    ids = tok.encode(text, add_special_tokens=False)
    p = Llama3JsonToolParser(tok, req.tools)
    prev_text, content, calls = "", "", {}
    for i in range(len(ids)):
        cur_text = tok.decode(ids[: i + 1])
        d = p.extract_tool_calls_streaming(prev_text, cur_text, cur_text[len(prev_text):],
                                           ids[:i], ids[: i + 1], ids[i : i + 1], req)
        if d and d.content:
            content += d.content
        for tc in (d.tool_calls if d else []):
            c = calls.setdefault(tc.index, ["", ""])
            c[0] += (tc.function.name or "") if tc.function else ""
            c[1] += (tc.function.arguments or "") if tc.function else ""
        prev_text = cur_text
    return content or None, [tuple(c) for c in calls.values()]

for text in ['{"capital": "Paris", "country": "France"}',
             '{"a": 1} is a dict',
             '{}',
             '{"name": "get_time", "parameters": {}}',
             'Let me check. {"name": "get_weather", "parameters": {"city": "Tokyo"}}']:
    info = Llama3JsonToolParser(tok, req.tools).extract_tool_calls(text, req)
    print(repr(text))
    print("  non-streaming:", info.content, [(t.function.name, t.function.arguments) for t in info.tool_calls])
    print("  streaming    :", *stream(text))
```

Larger deltas (4 tokens, or the whole output in one delta) give the same result for cases 1 and 3.

**Expected:** streaming returns the same content and tool calls as non-streaming. For case 1, when the buffered `{...}` turns out not to be a call (no `name` key, or text after the object), it should be flushed as content. For case 3, the text before the call should be content in both modes, as SGLang's Llama 3.2 detector test expects ([`test_llama32_detector.py#L84-L88`](https://github.com/sgl-project/sglang/blob/94602c9c2b7cbdb8efd5c52802dac6a1c180089e/test/registered/unit/function_call/test_llama32_detector.py#L84-L88)).

**Related:** I applied the open PR #51577 (llama3_json on the ParserEngine) to main @ 3b4566c, and it fixes all five cases in both modes: content is kept in case 1, `'{}'` in case 2, and `content='Let me check.'` plus the call in case 3. So this issue may simply be tracked by that PR. #48294 (whole call in one delta) is a different bug in the same function. [sglang#35562](https://github.com/sgl-project/sglang/issues/35562) is the same class of bug in SGLang.

### neevmodh · 2026-09-26

A scoped fix for case 1 (the content-loss case) is up in #58829.

**Fix:** Tracks whether a buffered `{...}` has finished parsing without ever producing a `name` key (nor `parameters`/`arguments`). Once confirmed, everything buffered so far is flushed as content and the remainder of the stream is passed through as plain content instead of being silently dropped.

This intentionally does not address cases 2/3 (empty-arguments formatting, text-before-call) — those are already covered by the broader `ParserEngine` port in #51577, which you noted may supersede this issue. Happy to close #58829 in favor of that PR once it lands; opened it in the meantime since the content-loss case is independently reviewable and low-risk.

### he-yufeng · 2026-09-26

Read both competing fixes since I work this parser family. Where they land on the mechanism:

- #58826 handles only the MalformedJSON branch mid-stream and only while no tool call has started. Once the buffer finishes parsing as valid JSON without a `name` key (the exact plain-JSON answer in this report), execution falls to `function_name = current_tool_call.get("name")` = None and the answer is still dropped. It fixes the interim, not the completion.
- #58829's latch is the right shape for the completion case: buffer completes with no `name`/`parameters`/`arguments`, flush everything as content, pass the rest through. Two gaps before it can merge: (1) no regression tests in either PR, and this file's reviewers have bounced test-less parser changes before; (2) once the latch flips it never flips back, so a completion that starts with a plain JSON answer and then makes a real tool call in the same stream would swallow that call as content. Probably rare, but worth a sentence in the PR and a test either way.

Happy to take the complete version (latch + tests for plain-JSON-first, real-tool-call-after, and the malformed interim) if the maintainers would rather have one PR than two partial ones; otherwise the notes above should be enough to finish #58829.
