## 正文

## Purpose

This keeps multimodal PrefixLM batches on the native FlashInfer backend. It is the vLLM adapter for FlashInfer's mm-prefix batch-prefill wrapper: it builds per-query `[start, end]` rows from request metadata, decides when the path is eligible, and calls the wrapper, whose attention variant evaluates `(causal AND sliding_window) OR mm_prefix` on every KV tile. No `O(qo_len * kv_len)` mask is materialized; the ranges are one `int32 (N, 2)` buffer sized by scheduled tokens, 128 KiB at 16384 tokens. The prefill still traverses the full rectangle, so the gain is memory, not FLOPs.

The wrapper comes from FlashInfer PR 5189, merged into FlashInfer main on September 18. It is not in FlashInfer 0.7.0, which main pins, so until the next FlashInfer release and pin bump `supports_mm_prefix()` returns `False` and this backend is demoted before selection. FlashInfer builds the variant's JIT module when the wrapper is constructed.

On SM100, `FLASHINFER` is offered ahead of the `TRITON_FLASHINFER` composite for mm-prefix batches, and the composite stays the fallback for what FlashInfer rejects: FP8, `nvfp4_4over6`, NVFP4 on SM100, sinks, DCP, `logits_soft_cap`, forced trtllm-gen and page sizes of 128 and above. The ubatch split now carries `mm_req_doc_ranges`, re-keyed to local request indices, and `is_prefilling`, so a short chunked-prefill tail inside a range stays a prefill. The `validate_configuration` override forwards `use_rswa`; without it, selection through this backend raises `TypeError`.

#47118 also enables FlashInfer for Gemma 4 multimodal models, but only for text-only requests; this PR serves the mm-prefix batches.

## Test Result

The CPU tests pass, and breaking each check they cover (the KV dtype, NVFP4-on-SM100, sink, page-size and wrapper-availability rejections, DCP, `use_rswa` forwarding, block-size advertising, and ubatch re-keying and slicing) fails the matching case. The GPU tests compare builder, impl and wrapper against a dense float32 reference on paged KV, with a sliding window narrower than the widest range so both window formulas are checked, and they cover the causal fallback, text-only and decode-only gating, short-extend reclassification and fail-fast on soft-cap and forced trtllm-gen. They need a FlashInfer build that carries the wrapper; on sm_80 they passed on the previous revision (45 passed, 22 hardware skips) and were not rerun for this one. pre-commit passes.

Caveats, so the table is not read for more than it says:

- The concurrency-32 FlashInfer figure is the mean of three seeds (10032/10033/10034: 426.6 / 427.0 / 426.7, spread 0.09%). The `TRITON_ATTN` figure on that row is a **single seed**, so its 2.6% lead carries an unmeasured seed-variance error bar and should not be read as a real difference. Concurrency 1 and 128 are single-seed on both sides.
- At concurrency 32, the measured inputs are 1295-1297 tokens with 1024 output tokens, putting the maximum full-request footprint at approximately 74K tokens, above either KV budget; concurrency 128 is more constrained. Scheduling and cache pressure can therefore affect these rows, and they do not isolate attention-kernel cost.
- The two arms do not get identical KV budgets: FlashInfer reserves its attention workspace during profiling and lands at 49,593 tokens against the baseline's 51,515. The FlashInfer configuration is therefore measured with approximately 3.7% less KV capacity.

### geunamja-gimhae · 2026-08-27

**Real-world impact report + offer to test on SM120 (production Gemma-4 multimodal)**

We run vLLM in production serving `gemma-4-26B-A4B-it-FP8` (multimodal, `is_mm_prefix_lm=True`) on 2× RTX 5090 (SM120), TP=2, fp8 KV cache, `ngram_gpu` speculative decoding (k=8), mostly long-context RAG traffic.

Because the FlashInfer backend does not declare `supports_mm_prefix`, backend selection disqualifies it for this model and falls back to `TRITON_ATTN` — for every request, including the 100%-text traffic that dominates our workload. Verified on v0.25.1 and again on v0.28.0 (boot log: `Using AttentionBackendEnum.TRITON_ATTN backend.`). `--limit-mm-per-prompt '{"image": 0, "video": 0}'` does not lift the gate, since `is_mm_prefix_lm` is a model-architecture property rather than an input question (and attempting that flag with a warm compile cache also runs into the cache-key collision from #50891). So there is currently no configuration that lets an mm-prefix model reach the SM12x XQA decode path added in #49718.

The cost on consumer Blackwell is large: flashinfer-ai/flashinfer#4137 measured XQA against vLLM's Triton unified-attention kernel on RTX PRO 6000 (SM120) at 2.4–3.6× for m=1 decode, and up to 14–18× for spec-decode verification (m=4/8) on full-attention layers at 32k context — exactly our decode profile. Today, mm-prefix models are excluded from all of it.

This PR would unblock a real production speedup for Gemma-4-class multimodal models. If it helps, we are happy to run correctness and throughput A/B on our 2× RTX 5090 setup once the PR is in a reviewable state — we have 0.25.1 baselines and a test harness ready.

*Disclosure: drafted with AI assistance; the deployment details and observations above are from our own production system.*
