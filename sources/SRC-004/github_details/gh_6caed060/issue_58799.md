## 正文

### Current serving results (replaces older serving snapshots)

Three GuideLLM 0.7.4 runs per tier, 10 s warmup, separate 8xH20 nodes. Humming W4A8 on original MXFP4: Decode c256 4,725 ± 66 output tok/s; fixed-1K Prefill c64 9,875 ± 63 input tok/s. Tuned FP8-128 + flashinfer_cutlass: 6,459 ± 173 output tok/s (+36.7%) and 15,048 ± 818 input tok/s (+52.4%), respectively. Values are means ± sample standard deviations. Paired GSM8K: Humming 476/494 correct, tuned 475/494; one-question difference (0.20 percentage points). The [blog PR #350](https://github.com/vllm-project/vllm-project.github.io/pull/350) has per-run data and methods. These whole-recipe gains are not attributable to the FlashInfer patch alone; the isolated operator A/B below remains its direct evidence. AI assistance was used to prepare this update.

### Proposal to improve performance

Track an upstream FlashInfer dispatch optimization affecting vLLM's SM90 block-FP8 `flashinfer_cutlass` MoE path, and validate its integration once a release containing the fix is available.

Upstream implementation and reproduction script: https://github.com/flashinfer-ai/flashinfer/pull/5560 (open, not yet merged).

The FlashInfer grouped GEMM runner uses the unexpanded input token count as `expected_m_`, but the dispatch threshold and tile selection operate on rows per expert. On our H20 EP8 configuration, a 288-token input with top-k=6 and 400 physical experts has an average of 4.32 routed rows per physical expert, not 288. The mismatched estimate selects an unfavorable GEMM branch/tile for decode-sized batches.

The proposed fix configures `max(1, ceil(tokens * top_k / (local_experts * ep_size)))` after worst-case workspace sizing. It keeps workspace virtual signatures, allocation logic and existing kernels unchanged. EPLB replicas are physical execution slots; this remains an average-load heuristic, not a measured routing histogram.

vLLM already forwards `ep_size`, `ep_rank` and `use_deepseek_fp8_block_scale` to FlashInfer. We are not proposing a duplicate dispatch implementation or LD_PRELOAD workaround in vLLM. The requested follow-up is dependency uptake and integration/performance validation after the upstream fix is reviewed and released.

### Report of performance regression

This is a suboptimal-dispatch report, **not a bisected vLLM release regression**.

Actual source-built comparison on eight H20 ranks, using the full local `cutlass_fused_moe` API:

| Input tokens / routing | Baseline ms | Proposed fix ms | Speedup |
|---|---:|---:|---:|
| 192 / uniform | 1.796432 | 0.554240 | 3.24x |
| 288 / uniform | 1.808480 | 0.564064 | 3.21x |
| 2048 / uniform | 1.904528 | 0.720464 | 2.64x |
| 288 / 75% routed to six experts | 2.020800 | 1.018144 | 1.98x |
| 288 / six active experts, seven ranks empty | 0.791280 | 0.751328 | 1.05x |
| 1 / uniform | 0.114720 | 0.115152 | ~1.00x |
| Draft geometry, 288 / uniform | 0.633360 | 0.217456 | 2.91x |

Five warmups, 24 CUDA Graph/event samples, explicit 64 MiB L2 flush outside timing; median of per-sample maximum latency across eight ranks. CUPTI was unavailable and GPU clocks were not locked. Cross-rank output reduction was checked **outside** the timed region.

All 64 rank/case output comparisons (including two draft cases) had maximum absolute difference zero; combined outputs also passed. No LD_PRELOAD was used for these source-build results.

**These are local MoE operator measurements, not communication-inclusive latency or serving TPS. We do not claim a 3.21x end-to-end vLLM throughput improvement.**

### Misc discussion on performance

Reproduction: the upstream PR includes the eight-rank synthetic `full_moe.py` harness, build isolation instructions and baseline/candidate commands. It does not require access to our checkpoint. Run the baseline before the candidate to generate identical-input reference tensors.

Validation boundaries:

- The full extension compiled, linked and loaded from an isolated FlashInfer 0.6.18.post1 source copy with the patch backported. The measured baseline retains EP-argument plumbing from an earlier iteration but restores the original estimate; it is a controlled ablation, not a pristine upstream binary.
- Exact upstream-base build and unmodified pytest execution remain pending. The proposed upstream base is `bf82326b0c524048c7f810da9f0022f8316ac3ff`.
- EP8 sequential-shard reference checks passed at hidden/intermediate=128 with batch 512 → 192 → 1 → 288 and unchanged tolerance. These are distinct from the real eight-rank A/B checks above.
- A hidden=512/intermediate=256 independent-reference case failed identically on baseline and patch (5,330/262,144 elements). Its cause is not fully established; this is not recorded as a passing accuracy test.
- Highly concentrated routing is not universally faster: a separate cold-L2 experiment showed about 7.6% regression for FC1 alone with one active expert, despite a small combined FC1+FC2 gain.
- Only H20 EP8 was validated. EP1/EP2 deployments, H100/H200, broad model quality parity and matched source-serving A/B are not claimed; a paired 500-item GSM8K sanity check is reported above.

Related but distinct:

- #57772 requests a fused SM90 MegaMoE path; this report concerns dispatch in the existing converted block-FP8 CUTLASS MoE path.
- #57423 / #57635 concern FlashInfer autotune cache restart deadlock, not this dispatch estimate.

AI assistance was used for diagnosis, implementation, validation and preparation of this report.
