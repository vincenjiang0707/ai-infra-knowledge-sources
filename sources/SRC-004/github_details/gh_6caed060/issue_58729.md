### 🐛 Describe the bug

RedHatAI/GLM-5.3-MXFP4 served with vLLM 0.30.0 on 8× NVIDIA GB200 (aggregated DEP8 + expert parallel) produces effectively unusable GSM8K outputs.

Symptoms on MXFP4:

1. 1,178 / 1,319 requests logged API returned null content (answer in reasoning_content, content is null/empty).
2. Of 1,319 samples, 2,356 / 2,638 response slots are empty strings; only 8 contain a #### <number> answer pattern.
3. Non-empty responses are degenerate/repetitive.

```
vllm serve RedHatAI/GLM-5.3-MXFP4 \
  --port 8000 \
  --tensor-parallel-size 1 \
  --enable-expert-parallel \
  --data-parallel-size 8 \
  --data-parallel-start-rank 0 \
  --data-parallel-size-local 4 \
  --data-parallel-address ${LWS_LEADER_ADDRESS} \
  --data-parallel-rpc-port 5555 \
  --data-parallel-multi-port-external-lb \
  --data-parallel-supervisor-port 8100 \
  --kv_transfer_config '{"kv_connector":"OffloadingConnector","kv_role":"kv_both","kv_connector_extra_config":{"spec_name":"TieringOffloadingSpec","cpu_bytes_to_use":107374182400,"eviction_policy":"lru","offload_prompt_only":true,"self_describing_kv_events":true,"secondary_tiers":[{"type":"p2p","host":"10.244.12.10","port":7777,"backends":["UCX"],"num_threads":4}]}}' \
  --served-model-name RedHatAI/GLM-5.3-MXFP4 \
  --trust-remote-code \
  --enable-cumem-allocator \
  --enable-ep-weight-filter \
  --kv-cache-dtype fp8_e4m3 \
  --reasoning-parser glm47 \
  --tool-call-parser glm47 \
  --enable-auto-tool-choice \
  --numa-bind \
  --gpu-memory-utilization 0.87 \

  --max-num-seqs 64 \
  --max-num-batched-tokens 8192 \
  --max-cudagraph-capture-size 64 \
  --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY","mode":0}'
```


Expected behavior
MXFP4 should be within reasonable range of NVFP4/BF16 on the same stack (e.g. >90% GSM8K flexible-extract, similar to other published GLM-5.3 MXFP4 results).

Same behavior is on GLM5.2-mxfp4-fp8 model. Looks like degradation because on nightly 2026-09-14, there was no gsm8k accuracy drop.
