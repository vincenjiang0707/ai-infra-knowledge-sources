### whn09 · 2026-09-24

Hi all, I maintain Mooncake's EFA transport. A few notes from the Mooncake side:

@functionstackx is right about the root cause. The default mooncake-transfer-engine wheel is built without EFA, so the image also needs to swap in mooncake-transfer-engine-efa (CUDA 12) or mooncake-transfer-engine-efa-cuda13. The swap can follow the existing cuda13 swap in the Dockerfile, and versions are released in lockstep.

@snadampal, agreed that a single EFA install covers both NIXL and Mooncake. Both use the system libfabric, and neither bundles it. Two caveats:

1. rdma-core. The EFA installer replaces the base image's rdma-core. On AWS that's required, otherwise you get libefa.so.1: version 'EFA_1.4' not found. If EFA userspace ships in the default image, though, it changes the rdma-core that every ibverbs user sees on non-AWS clusters. That includes Mooncake's rdma transport, NIXL/UCX (which vendors its own libibverbs but still loads providers from the system), and DeepEP. Before making it the default, we should confirm IB/RoCE (mlx5) still works, or scope EFA to a separate build/tag. I can test the Mooncake rdma path.
2. arm64. The Mooncake EFA wheels are currently x86_64 only, and they hard-link libfabric, so they can't be installed unconditionally. For now I'd suggest swapping them in only on x86_64 when EFA is installed. We'll add aarch64 builds.

Also, when validating, check the backend that was actually selected in the logs. NIXL silently falls back to UCX if the LIBFABRIC plugin can't load, and Mooncake falls back to TCP if the efa provider is unavailable.

I'm happy to review the PR and validate Mooncake on p5/p5en/p6.
