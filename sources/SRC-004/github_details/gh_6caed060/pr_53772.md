## Purpose

Fix the promotion-starvation mechanism analyzed in #53130.

Requests parked in `skipped_waiting` (`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR` / `WAITING_FOR_REMOTE_KVS` / `WAITING_FOR_STREAMING_REQ`) are only promoted while the waiting loop of `schedule()` traverses them, and that loop stops on the token-budget and `max_num_seqs` capacity checks. On steps where running requests consume the entire token budget (e.g. long chunked prefills) or occupy every request slot, the loop never reaches the parked requests, so:

- a parked request whose grammar has finished compiling is never promoted, and
- a parked request whose grammar compile **failed** is never detected and never terminated.

Under sustained saturation both conditions hold indefinitely: parked requests are stuck until a restart while the engine reports healthy (the incident in #53130). This matches "mechanism A" reproduced at the scheduler level by @Ddhjx-code, and implements the fix direction sketched by @kenhaesler in the same thread (sketch 5).

Change: after the waiting loop, promote the requests it left unvisited in `skipped_waiting`. Everything the loop did traverse has already had its promotion check and sits in `step_skipped_waiting`, so on a normal step the sweep does no work; only a starved remainder is visited, and only when starvation occurs. Promotion order is irrelevant to the sweep (it only advances state; scheduling order is still decided by the queue), so it uses a new `RequestQueue.iter_unordered()` that walks the underlying deque/heap without copying or sorting — `PriorityRequestQueue.__iter__` copies and re-heapifies the queue, which is not acceptable on the hot path under `--scheduling-policy priority`. Promotion is idempotent (state-gated by `_is_blocked_waiting_status`), and promoted requests stay in `skipped_waiting` so cross-queue FCFS/priority order (`_select_waiting_queue_for_scheduling`) is unchanged.

Companion: #55931 makes the grammar-future poll non-blocking (split out of this PR at review request); with it, each promotion check is O(1).

Out of scope: admission of new requests while the token budget is saturated is unchanged (inherent chunked-prefill semantics), as is the eviction/re-prefill feeder discussed in the issue.

**Not a duplicate**: #53321 adds a timeout for `WAITING_FOR_STREAMING_REQ` only (orthogonal and complementary — it handles a status that has no promotion path, while this PR fixes the gates that starve promotion for all parked statuses). #45406 un-strands `WAITING_FOR_REMOTE_KVS` requests stuck behind an unschedulable queue head — a different mechanism (scan aborted mid-loop) from this one (loop never entered).
