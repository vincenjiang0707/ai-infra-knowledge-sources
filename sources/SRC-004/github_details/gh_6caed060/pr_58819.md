## Purpose

DeepSeek V4.1's MXFP4 MoE runs AITER's a4w4 (FP4-activation) kernel by
default as of the first commit on this PR. That commit forced a4w4 via
AITER's `_q_dtype_a` override but kept vLLM's existing `GateMode.INTERLEAVE`
weight shuffle. AITER's INTERLEAVE stage-1 GEMM has no tuned FlyDSL config
for fp4x2 activations at this shape and silently falls back to a heuristic
kernel that produces degenerate output end-to-end — AITER's own
`op_tests/test_moe_2stage.py` cosine-similarity check (used to validate the
first commit) does not catch this, but real-model GSM8K does (near-chance
accuracy, garbled reasoning traces).

The second commit fixes that by switching a4w4 to ATOM's `GateMode.SEPARATED`
gate/up weight layout instead, which AITER validates for fp4x2 activations on
this checkpoint. It's a single `is_guinterleave=False` flag flip in AITER's own
`shuffle_weight`/`shuffle_scale` — no new shuffle function needed — gated on
the same `FusedMoEConfig.use_mxfp4_w4a4_dsv4` flag that already gates the
forced a4w4 activation dtype. a8w4 (default for every other MXFP4 model on
this code path) is untouched.

The third commit **scopes the auto-detection to DeepSeek V4.1 only**
(`deepseek_v41`/`deepseek_v41_text`). DeepSeek V4 shares the same MoE shape
and dispatch path but has not had the same GSM8K/AgentX validation yet — see
the separate untested/draft follow-up in #58869.

Real-model validation on DeepSeek-V4.1-Flash, TP2, AITER `MXFP4_BF16` backend
(a4w4 = this PR's `use_mxfp4_w4a4_dsv4` path vs a8w4 = default fallback):

- **GSM8K** (`lm_eval`, DSpark w/ real `block` rejection sampling): a4w4 and
  a8w4 both score `exact_match,strict=0.9712` / `flexible=0.9704` — identical.
- **AgentX** (`aiperf` `inferencex-agentx-mvp`, DSpark synthetic-AL=3.51
  rejection, settings matched to the public InferenceX dashboard run
  [`36101751233` attempt 2](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/36101751233/attempts/2),
  3600s each, 0 errors):

  | Concurrency | Output tok/s (a4w4 vs a8w4) | Inter-token latency |
  |---|---|---|
  | c1  | 142.7 vs 144.1 (**-1.0%**) | 3.46 vs 3.37ms (+2.7%) |
  | c8  | 404.1 vs 404.5 (parity) | 4.39 vs 4.40ms (parity) |
  | c64 | 303.4 vs 274.5 (**+10.5%**) | 138.8 vs 149.0ms (**-6.9%**) |

  a4w4's fixed fp4-activation-quantization overhead isn't amortized at
  batch=1 (c1), reaches parity at c8, and wins clearly at c64 once the
  halved weight-read bandwidth dominates — consistent with a genuine
  compute/bandwidth crossover, not noise.
