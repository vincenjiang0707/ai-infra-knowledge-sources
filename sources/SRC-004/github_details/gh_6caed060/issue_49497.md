Install: `VLLM_USE_PRECOMPILED=1 uv pip install --editable .` at commit 910cc8543 on WSL2. **No system CUDA toolkit** — no `/usr/local/cuda`, no nvcc on PATH — which is the normal state for wheel-based installs (and the documented setup for WSL2, which uses the Windows driver via passthrough).

### 🐛 Describe the bug

With a default config, the FlashInfer top-k/top-p sampler is auto-selected ("Using FlashInfer for top-p & top-k sampling"), then engine startup crashes when FlashInfer JIT-compiles its sampling module:

```text
  File ".../site-packages/flashinfer/jit/cpp_ext.py", line 61, in get_cuda_path
    raise RuntimeError(
RuntimeError: Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist
RuntimeError: Engine core initialization failed. See root cause above.
```

It reproduces in **both** sampler code paths:

- **V1 model runner:** during `profile_run` → `_dummy_sampler_run` (`vllm/v1/sample/ops/topk_topp_sampler.py:504` → `flashinfer.sampling.top_k_top_p_sampling_from_logits`)
- **V2 model runner:** during `compile_or_warm_up_model` → `warmup_kernels` → `sample_tokens` (`vllm/v1/worker/gpu/sample/sampler.py:234` → same call)

Minimal repro on any machine without a discoverable toolkit:

```python
from vllm import LLM, SamplingParams

if __name__ == "__main__":
    llm = LLM(model="facebook/opt-125m")
    out = llm.generate(["Hello, my name is"], SamplingParams(max_tokens=20))
    print(out[0].outputs[0].text)
```

Workaround: `VLLM_USE_FLASHINFER_SAMPLER=0` — inference then works normally via the native sampler.

**Two observations:**

1. **The failure escapes vLLM's existing gate.** `flashinfer_sampler_supported()` (`vllm/v1/sample/ops/topk_topp_sampler.py`) already implements the right policy for unsupported configs: warn once and fall back to native, or raise a clear error if the user explicitly forced `VLLM_USE_FLASHINFER_SAMPLER=1`. But it only checks platform and compute capability — not whether FlashInfer can actually build or load its kernels. So a default install crashes at engine init with an error pointing at `/usr/local/cuda`, which wheel users have no reason to have.

2. **nvcc is actually present, just undiscoverable.** The wheel install pulls in `nvidia-cuda-nvcc==13.3.73` as a pip package, so a compiler exists inside `site-packages` — but FlashInfer's `get_cuda_path()` only consults `CUDA_HOME` and `/usr/local/cuda`. (Compare #44305, where CUDA_HOME pointed into the pip `nvidia/` tree and nvcc WAS found.)

Related but distinct: #44305 (closed; Blackwell, nvcc found but toolkit headers incompatible), #26642 (old FlashInfer 0.4.0). Also mentioned briefly in my comment on #47292.

Happy to submit a PR. My preferred direction: extend `flashinfer_sampler_supported()` to verify sampling-kernel availability (prebuilt cubin/jit-cache, or a usable toolkit for JIT — possibly including the pip-installed nvcc per observation 2) using the existing warn-and-fallback / raise-if-forced structure. Open to guidance on whether the pip-nvcc discovery belongs in vLLM or upstream in FlashInfer.

@joynerwk03 you're right about #49314 and thanks for actually rebuilding it rather than reading the description — I checked my branch head and it is `except ImportError` only, no `has_flashinfer()` call. On your box FlashInfer *is* installed, so it catches nothing.

Which leaves a question for whoever's sequencing this: #51741 recovers at the call site after the build has been attempted; a gate would skip the attempt entirely, which is what you saw as "never attempts the build".
