# [Issue #58849] [Performance]: WSL2: `VLLM_WSL2_ENABLE_PIN_MEMORY=1` makes the default V2 runner ~12% faster per decode step

source: https://github.com/vllm-project/vllm/issues/58849
state: open | updated: 2026-09-27T03:19:10Z
labels: performance

## 正文

### Proposal to improve performance

On #54655, @njhill suggested evaluating "whether we want to change the default of [`VLLM_WSL2_ENABLE_PIN_MEMORY`] generally." Here's that evaluation on one WSL2 machine, default (off) vs on, runs alternated:

- **Batch-1 decode, Qwen3-8B-AWQ: 8.7-9.0 → 7.7-7.8 ms per token (−12%)**, pip install and Docker image alike. BF16 saves the same ~1.1 ms per step (21.3-21.9 → 20.2-20.4 ms).
- **Throughput** (`vllm bench serve`, random 256/256): +13-14% at concurrency 1, +8% at 16, +3.8% at 64.
- **Why:** in a torch profile, GPU-busy time per step is unchanged (7.56 vs 7.61 ms). With the default, the trace shows pageable host-to-device copies and the GPU idles 1.29 ms per step; with pinned memory on, 0.16 ms.

#41496's review measured a <2% throughput cost for pinned memory on WSL2 (RTX 5080, a 4B model). With today's V2 runner it goes the other way here. Happy to test a default change on this setup.

<details><summary>Setup and reproduction</summary>

Greedy, 64 output tokens, median gap between streamed tokens; 3 requests per run, 2 runs per arm, arms alternated (off, on, off, on). KV cache pinned so both arms get the same capacity. The desktop was idle (a GPU-engine monitor showed only VS Code, at ~2% of the 3D engine).

| Batch-1 time per output token | Default | `VLLM_WSL2_ENABLE_PIN_MEMORY=1` |
|---|---|---|
| Docker image, AWQ | 8.69-8.88 ms | 7.65-7.79 ms |
| pip install, AWQ | 8.81-9.02 ms | 7.75-7.81 ms |
| Docker image, BF16 | 21.30-21.93 ms | 20.18-20.38 ms |

```bash
# the flags used here (the Windows desktop holds ~2.5 GB of the 24 GB)
ARGS="--gpu-memory-utilization 0.80 --max-model-len 8192 --kv-cache-memory-bytes 12438208512"
vllm serve Qwen/Qwen3-8B-AWQ $ARGS                                  # default
VLLM_WSL2_ENABLE_PIN_MEMORY=1 vllm serve Qwen/Qwen3-8B-AWQ $ARGS    # pinned
# then: vllm bench serve --dataset-name random --random-input-len 256
#   --random-output-len 256 --max-concurrency 1 --temperature 0
```
</details>

## 评论 (1)

### joynerwk03 · 2026-09-27

Found the cause, and a two-line change that removes the penalty here: **V2's fallback for missing pinned memory copies with a blocking `copy_()`.** PyTorch finishes each blocking host-to-device copy with `cudaStreamSynchronize`, so preparing step N+1 waits for step N to finish, 16 times per step.

```diff
# vllm/v1/worker/gpu/buffer_utils.py, NonUvaBuffer.uva()
-            return self._uva.copy_(self.cpu)
-        return self._uva[:n].copy_(self.cpu[:n])
+            return self._uva.copy_(self.cpu, non_blocking=True)
+        return self._uva[:n].copy_(self.cpu[:n], non_blocking=True)
```

Same machine, V2 runner, `VLLM_WSL2_ENABLE_PIN_MEMORY` unset except the last column; arms alternated:

| Batch 1, per decode step | Default | Patched | Pinned memory on |
|---|---|---|---|
| Wall time (all timed requests) | 8.88-9.08 ms | **7.63-7.66 ms** | 7.69-7.71 ms |
| `cudaStreamSynchronize` | 16.3 | **0** | 0 |
| GPU idle | 1.32-1.46 ms | 0.01-0.18 ms | 0.10 ms |
| Throughput, c=1 / c=16 (tok/s) | 106 / 1,011 | 123-124 / 1,114-1,128 | 123 / 1,119 |

- The patched run still makes the same ~18 pageable copies per step; only the waits are gone. V1's `CpuGpuBuffer.copy_to_gpu` already copies pageable memory with `non_blocking=True`.
- Outputs: at c=1, all 48 greedy responses identical across default, patched and pinned runs. At c=16, patched-vs-default agreement (175-186 of 192) is within run-to-run variation (177 default vs default).

Happy to open a PR with this if the approach looks right.

`vllm/vllm-openai:v0.30.0` with the patched `buffer_utils.py` bind-mounted (`NonUvaBuffer` is unchanged on main). Qwen3-8B-AWQ, RTX 3090, WSL2. Arms: default, patched, default, patched, pinned (default and patched ran twice, pinned once).
