## Your current environment

- xgrammar 0.2.7; llguidance 1.7.6; outlines-core 0.2.14; jsonschema 4.26.0

## 🐛 Describe the bug

[`has_guidance_unsupported_json_features()`](https://github.com/vllm-project/vllm/blob/fa94450b743766d466021a40e5b5f5f5746c92b9/vllm/v1/structured_output/backend_guidance.py#L50-L73) returns `True` as soon as any dictionary at any depth contains a `patternProperties` key ([L58](https://github.com/vllm-project/vllm/blob/fa94450b743766d466021a40e5b5f5f5746c92b9/vllm/v1/structured_output/backend_guidance.py#L58)), then recurses into every dict and list value. It does not distinguish schema keywords from property names or instance data.

In the schema below, `patternProperties` is a **property name**, not a JSON Schema keyword at that location. The gate nevertheless reports Guidance as unsupported. Since the numeric `multipleOf` rule also excludes Xgrammar, `auto` selects Outlines. Outlines-core's schema-to-regex conversion ignores `multipleOf`, so the generated regex accepts an output that violates the original schema. Renaming the property to `p` leaves everything else identical and `auto` selects Guidance, so the property name alone causes the fallback.

The same false positive occurs when `patternProperties` is literal data under `const` or appears only in an unused `$defs` entry.

### Minimal reproduction

Run from this vLLM checkout with the listed dependencies:

```python
import json
from types import SimpleNamespace

import regex
from jsonschema import Draft202012Validator
from outlines_core.json_schema import build_regex_from_schema

from vllm.config import StructuredOutputsConfig
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
from vllm.v1.structured_output.backend_guidance import (
    has_guidance_unsupported_json_features,
)


def auto_backend(schema):
    request = ChatCompletionRequest.model_validate_json(json.dumps({
        "model": "audit",
        "max_tokens": 32,
        "messages": [{"role": "user", "content": "Produce a value."}],
        "structured_outputs": {"json": schema},
    }))
    params = request.to_sampling_params(32, {})
    params.verify(
        SimpleNamespace(is_diffusion=False, max_logprobs=20),
        None,
        StructuredOutputsConfig(backend="auto"),
        object(),
    )
    return params.structured_outputs._backend


def make_schema(name):
    return {
        "type": "object",
        "properties": {
            name: {"type": "string"},
            "n": {"type": "number", "multipleOf": 3},
        },
        "required": [name, "n"],
        "additionalProperties": False,
    }


schema = make_schema("patternProperties")
renamed = make_schema("p")  # control: same schema, different property name
Draft202012Validator.check_schema(schema)
invalid = {"patternProperties": "x", "n": 7}
invalid_json = json.dumps(invalid, separators=(",", ":"))
print(json.dumps({
    "guidance_gate_reports_unsupported": has_guidance_unsupported_json_features(schema),
    "auto_backend": auto_backend(schema),
    "renamed_auto_backend": auto_backend(renamed),
    "original_schema_accepts_n7": Draft202012Validator(schema).is_valid(invalid),
    "outlines_regex_accepts_n7": bool(regex.fullmatch(
        build_regex_from_schema(json.dumps(schema)), invalid_json
    )),
    "literal_data_gate": has_guidance_unsupported_json_features({
        "const": {"patternProperties": "x"}
    }),
    "unused_defs_gate": has_guidance_unsupported_json_features({
        "type": "string",
        "$defs": {"unused": {"type": "object", "patternProperties": {"^x": True}}},
    }),
    "actual_pattern_properties_gate": has_guidance_unsupported_json_features({
        "type": "object", "patternProperties": {"^x": {"type": "string"}}
    }),
}))
```

Observed output (excluding import-time warnings):

```json
{"guidance_gate_reports_unsupported": true, "auto_backend": "outlines", "renamed_auto_backend": "guidance", "original_schema_accepts_n7": false, "outlines_regex_accepts_n7": true, "literal_data_gate": true, "unused_defs_gate": true, "actual_pattern_properties_gate": true}
```

A separate direct llguidance matcher check (byte-level tokenizer with EOS) on this schema accepted `n=6` followed by EOS, and rejected `n=7` at the closing `}`. Neither the completed object nor EOS is accepted. The false gate therefore bypasses a backend that enforces this example.

### Background and scope

The gate was introduced in #30730 after a report about Guidance and `patternProperties` ([guidance-ai/llguidance#265](https://github.com/guidance-ai/llguidance/issues/265)). This issue concerns false positives in vLLM's traversal; it does not ask to remove the gate for a genuine `patternProperties` keyword.

### Expected behavior

- The Guidance gate should inspect `patternProperties` only where it is a keyword of a schema node: ordinary property names, values under `const`/`enum`/`default`/`examples`, and unreferenced definitions should not trigger it.
- `$defs` entries that are reached through `$ref` must still be checked (this needs reference resolution with cycle tracking); only unreferenced definitions are exempt.
- As long as the gate exists, a real `patternProperties` keyword must continue to trigger it.
- For this example, `auto` should select Guidance under the existing fallback order and reject `n=7`.

### Duplicate check

Searched current and past vLLM issues/PRs for `has_guidance_unsupported_json_features`, `patternProperties`, `llguidance patternProperties`, `outlines multipleOf`, and related terms on September 25, 2026. I found no report of this false positive.

- #30730 (merged) introduced the gate; the underlying premise is still open in guidance-ai/llguidance#265.
- #57592 (open) fixes the same kind of property-name / literal-data false positive in the **Xgrammar** detector (`backend_xgrammar.py` only). It does not touch this Guidance gate, but it is a close precedent for the fix.

I published [RFC #58697](https://github.com/vllm-project/vllm/issues/58697) and propose addressing this bug through its shared schema-aware document layer. The Guidance gate would inspect `patternProperties` only on schema nodes that may constrain the root instance. Property names, literal `const`/`enum` data, and unreferenced `$defs` would no longer trigger this gate, while a genuine `patternProperties` keyword would still be checked.

The RFC describes the target contract. This bug can be fixed in a focused incremental PR without waiting for a complete parser.
