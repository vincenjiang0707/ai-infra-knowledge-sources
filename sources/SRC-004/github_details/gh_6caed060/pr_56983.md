## 正文

## Summary

`incoai/GLM-5.3-Flash-DFlash2` is the block-diffusion (DFlash2) drafter published for `zai-org/GLM-5.3-Flash`. On current `main` the pair cannot be served: `vllm serve zai-org/GLM-5.3-Flash --speculative-config '{"method":"dflash","model":"incoai/GLM-5.3-Flash-DFlash2",...}'` fails during startup, and fixing one failure exposes the next. This PR makes the combination start and serve on NVIDIA (8x H100, TP8 + EP), adds unit coverage for the two non-model changes, and reports a throughput sweep against the existing MTP path. No kernels, defaults, or MTP behaviour are changed.

The three blockers on `main` (9d4d9aa5bc), in the order they surface:

| # | Stage | Error on `main` | Root cause |
|---|---|---|---|
| 1 | draft model load | `RuntimeError: Model does not support EAGLE3 interface` | `Glm5NextForCausalLM` / `Glm5NextForConditionalGeneration` (the architecture the DFlash2 checkpoint targets) do not declare `SupportsEagle3`, and `Glm5NextModel` is not an `EagleModelMixin`, so the DFlash speculator cannot register its aux hidden-state layers (`target_layer_ids + 1 = [6, 15, 25, 34, 43]`). |
| 2 | KV cache init | `NotImplementedError: Layer language_model.model.layers.3.self_attn.indexer.k_cache: page size is not divisible by the maximum page size and cannot be padded. Padding is only supported for non-MLA attention layers.` | `_get_kv_cache_groups_glm5_next` bails out as soon as a non-MLA attention layer (the draft's sliding-window GQA layers) is present, so the generic page unifier runs on a spec set it cannot unify (MLA 655,360 B, indexer 21,120 B and draft 163,840 B pages at block_size 640). |
| 3 | config | `ValueError: Number of experts in the model must be greater than 0 when expert parallelism is enabled` | `create_draft_parallel_config` copies `enable_expert_parallel` from the MoE target onto the dense drafter (introduced by #55914 for the DeepSeek-V4 MegaMoE drafter). |

### Changes

- **`vllm/models/glm5next/nvidia/model.py` (aux hidden-state capture).** `Glm5NextModel` becomes an `EagleModelMixin`; `Glm5NextForCausalLM` and `Glm5NextForConditionalGeneration` declare `SupportsEagle3`. The tensor handed to the drafter is not `hidden_states + residual`: GLM-5.3-Flash layers run mHC with 4 residual streams and defer each layer's `hc_post` into the next layer's fused post+pre kernel, so at a layer boundary `residual` is the widened `(T, 4 * hidden)` stream (a naive `hidden + residual` fails with `The size of tensor a (8192) must match the size of tensor b (4) at non-singleton dimension 1`) and `hidden_states` alone is the raw layer output. `_aux_hidden_state()` completes the deferred `hc_post` through a dedicated `MHCPostOp` and contracts the streams back to `hidden_size` with `hc_contract`, which is the quantity SGLang's `_prepare_aux_hidden_state` feeds DFlash2. The capture is read-only: the layer loop keeps consuming the original `(hidden_states, residual, post, comb)` tuple. Non-mHC layer boundaries already carry the summed stream in `hidden_states` and are returned as-is. When any aux layer is requested, `forward` returns `(hidden_states, aux_hidden_states)`; otherwise the return type is unchanged.

- **`vllm/v1/core/kv_cache_utils.py` (draft KV group inside the GLM hybrid layout).** Attention layers that are not `MLAAttentionSpec` (the draft's `SlidingWindowSpec` layers) are split out of the MLA/indexer set into their own `UniformTypeKVCacheSpecs` group, keeping their native page geometry and independent block ids; the target's MLA/indexer slot-sharing layout is untouched. `_glm5_next_tensor_layout` returns that group as a ninth element and its three consumers account for it: bytes per block (`_glm5_foreign_bytes_per_block`), tensor placement (a layer-outermost region after the target's MLA and indexer slots), and the max-memory estimate. Group order becomes `[MLA+indexer, kpool tail, draft, mamba...]`. Mixed foreign spec types or more than one foreign uniform group fall back to the generic path (`return None`) exactly as before.

- **`vllm/config/speculative.py` (expert parallelism only for MoE drafters).** `create_draft_parallel_config(target_parallel_config, draft_tp, draft_is_moe=True)` inherits `enable_expert_parallel` only when the drafter has experts; the call site passes `draft_model_config.is_moe`. DeepSeek-V4 MTP (MoE drafter, #55914) keeps EP; DFlash and EAGLE dense heads no longer trip `_verify_with_expert_parallelism`.

- **Tests.** `tests/v1/core/test_kv_cache_utils.py::test_get_kv_cache_config_glm5_with_dflash_draft_group` builds the GLM-like spec set plus five sliding-window draft layers and asserts the six groups, the layout's draft slot, bytes per block (`11 * mla + 11 * idx + 5 * draft`), and the draft tensors' offsets and strides after the target region. `tests/test_config.py::test_draft_parallel_config_inherits_ep_only_for_moe_drafters` covers both values of `draft_is_moe`.

## Performance

**Setup.** 8x NVIDIA H100 80GB HBM3 (driver 535.154.05), TP8 + EP, torch 2.13.0+cu129, FlashInfer 0.6.18, Python 3.12, vLLM `main` 9d4d9aa5bc + this branch, V2 model runner (`VLLM_USE_V2_MODEL_RUNNER=1`). Takeaways:

- `num_speculative_tokens` is the dominant knob. Acceptance decays to ~0 beyond position 8 (the drafter's block_size), so k=16 pays a 17-token verify per step for the same ~3.3-3.6 accepted tokens; going to k=6 raises conc-32 throughput from 707 to 2924 tok/s (4.1x). k=4..6 is the sweet spot on this workload, k=8 is slightly worse.
- Against MTP k=5 at identical settings, DFlash2 k=6 is faster at every concurrency: +40% single stream, +26% at 8, +23% at 32, +15% at 64.
- FlashInfer as the draft attention backend is 7-9% slower than the auto-selected FlashAttention.
- `--max-num-seqs 96` vs 48: +2-3%, no preemption at concurrency 64.

**KV cache capacity (cost of the separate draft region).**

| Config | Available KV memory | KV capacity | Max concurrency at 131072 tokens |
|---|---|---|---|
| MTP k=5 | 23.61 GiB | 1,802,673 tokens | 13.75x |
| DFlash2 k=6 | 23.49 GiB | 1,358,649 tokens | 10.37x |

Per block (block_size 640) the target uses 11 x 655,360 B MLA pages plus 11 x 21,120 B indexer pages (kpool tails aliased into them); the draft adds 5 x 163,840 B pages and its own per-request block demand to the group-aware capacity estimate, hence 24.6% fewer tokens than MTP at the same memory. #55423's slot-aliasing design avoids this at the price of re-blocking the draft to the MLA page; that is the main trade-off between the two PRs. At `--max-num-seqs 96` this still leaves ~14k tokens per sequence.

The two accuracies differ by 0.8 points (about 10 of 1319 questions), inside the run-to-run spread of this greedy-but-nondeterministic stack (see below); output-token counts match within 2%. DFlash2 delivers the same accuracy at 2.0x the single-stream decode speed.

**Greedy output determinism.** Exact token-level lossless verification is not possible on this stack: with `temperature=0` the same server produces different continuations run to run (16 sweep prompts, 512 tokens, sequential, prompt already cached): target-only 0/16 identical across three runs (median common prefix 272-306 characters before the first divergence), DFlash2 k=6 0/16 identical across three runs (median 237-306), and DFlash2 vs target-only 0/16 identical (median 222-237). The run-to-run spread of the target alone is the same size as the DFlash2-vs-target spread, so the divergence comes from the fp8 MoE + EP numerics of the target (near-tie argmax flips), not from the speculative path; the GSM8K parity above (0.919 vs 0.911) is the meaningful losslessness check.

**Pre-existing crash observed while testing, not introduced by this PR (#55626).** Any step that co-schedules a ~600+ token prefill with a speculative verify step, or a burst of a dozen ~630-token prefills, kills the engine with an asynchronous CUDA fault. It reproduces identically with MTP, whose KV layout on this branch is byte-for-byte the `main` layout, so it is a property of the target's FlashInfer SM90 sparse-MLA path with speculative decoding, matching the traceback location and the FlashInfer core dump posted in #55626.

## Known limitations / follow-ups

- #55626 (above) affects every speculative configuration of GLM-5.3-Flash on SM90 and needs a separate fix; the DFlash2 path inherits it.
- The separate draft region costs KV capacity relative to the slot-aliasing design in #55423 (24.6% fewer tokens than MTP at the same memory); the two designs should be reconciled in review.
- Aux hidden states are not all-gathered under sequence parallelism (`compilation_config.pass_config.enable_sp`); the tested configuration runs with compilation mode NONE, where SP is off. Pipeline parallelism is already gated off for GLM-5.3-Flash and was not exercised.
- Tested with greedy sampling for throughput and the default sampling of the tool-calling scripts; `disable_eagle_block_drop` was left at its default.
- Only the NVIDIA model file is changed; the ROCm copy (#54451) is not addressed.

### 1. KV cache grouping

Following @ivanium's [reference commit](https://github.com/ivanium/vllm/commit/1dd640818b78c1a0fc81b81c37ce3882564b39b2), the DFlash drafter's KV is now allocated as `FullAttentionSpec` and joins the target's MLA/indexer `UniformTypeKVCacheSpecs`, while the GLM planner in `kv_cache_utils.py` no longer detects or promotes draft layers: it only accepts full-attention pages next to the MLA/indexer pages and sizes blocks from the attention group's `page_size_bytes`, as in the reference. The difference is how the drafter gets that spec: instead of rewriting the draft architectures in `Glm5NextModel.__init__` and patching `get_kv_cache_spec` on the attention instances, the target owns the policy through `Glm5NextForCausalLM.adapt_draft_kv_cache_spec` (sliding-window draft spec → `FullAttentionSpec` at the target block size, window kept for compute), which `DraftModelSpeculator` applies to the draft layers only when the V2 runner collects KV cache specs; the generic drafter (`qwen3_dflash*.py`) and the shared `Attention` layer stay untouched, so this is orthogonal to #50457. On 8×H100 (TP8) this gives 6 KV cache groups instead of 7 with the original separate draft group, and raises KV capacity from 1,359,138 to 1,542,574 tokens (+13.5%).

### 2. Upstream issue re-opened by this layout (#54374)

Booking the windowed drafter on full-attention pages silently re-opens #54374: with an MLA target the drafter is the only FlashAttention consumer, so FA3's AOT split schedule stays on and acceptance collapses to ~1.0 under full CUDA graphs, because the guard in [`DFlashSpeculator.set_attn`](https://github.com/vllm-project/vllm/blob/e9f169d16b9408bb9ae44f75072b91a5521d733c/vllm/v1/worker/gpu/spec_decode/dflash/speculator.py#L189-L200) detects the window via [`get_kv_cache_spec_sliding_window`](https://github.com/vllm-project/vllm/blob/e9f169d16b9408bb9ae44f75072b91a5521d733c/vllm/v1/kv_cache_interface.py#L1367-L1376), which only returns it for `SlidingWindowSpec`. Both the previous head [`8c5a676`](https://github.com/vllm-project/vllm/pull/56983/commits/8c5a676a707d8516d1487507629749e223310e9e) and the reference commit hit it, and it is easy to miss because copy-from-context prompts (needle, long documents) keep normal acceptance while generation-heavy requests collapse (outputs stay correct since verification is lossless).

[`0986790`](https://github.com/vllm-project/vllm/pull/56983/commits/09867903637a0fce3c0f3dc4db61ebdc109b82de) makes the guard read the spec's `sliding_window` attribute, as #54374 intended, and leaves `get_kv_cache_spec_sliding_window` unchanged since the KV cache manager and offloading use it for eviction semantics; a regression test covers it. On 8×H100 (TP8 + EP, k=6, full CUDA graphs), arithmetic prompts at concurrency 8 go from acceptance 1.21 / 375 tok/s with the reference to 5.68 / 1172 tok/s, the same short prompt needs 24 instead of 103 draft steps (acceptance 1.28 → 5.50), GSM8K-200 at concurrency 1 reaches accuracy 0.930 at 204.4 tok/s with acceptance 4.70, and needle prompts are unchanged (4.29 vs 4.25).
