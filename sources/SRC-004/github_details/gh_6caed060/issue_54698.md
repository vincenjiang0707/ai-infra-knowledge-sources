### Model Input Dumps

Not applicable — this is a hang, not a crash/incorrect-output bug, so there is no failing request payload to attach. Happy to capture one if it would help.

### 🐛 Describe the bug

Under sustained concurrent load (2 agentic API clients issuing overlapping long-running
chat completions against the same server), the vLLM EngineCore process periodically
enters a genuine infinite spin inside `torch.xpu.graphs.replay()` (the CUDA/XPU-graph
replay call), pegging one CPU core at 100% and never returning. The server stops
responding to new requests; from the outside this looks like a hang, and our
`llama-swap`-based reverse proxy eventually kills and restarts the whole backend
service after its health probe (a real inference call) itself gets stuck behind the
spin.

This has recurred roughly every 10–25 minutes of concurrent-load runtime over
multiple independent sessions on this box, on both an MTP-enabled and an MTP-disabled
configuration, and is not correlated with `vllm:num_preemptions_total` (confirmed 0 at
the moment of at least one capture) or KV-cache eviction — i.e. it is not simply
"ran out of KV cache and got stuck recovering." It occurs while other engine threads
are otherwise idle (`Thread-1`/`Thread-2` housekeeping threads shown idle in every
capture below).

We confirmed this is a genuine spin, not a slow-but-progressing call, by taking
repeated `py-spy dump` snapshots of the same EngineCore PID several seconds apart:
the captured Python frame is byte-identical across snapshots, and `/proc/<pid>/stat`
cumulative CPU ticks climb steadily between snapshots (e.g. one PID: 55960 → 124899 →
263597 → 293561 ticks across four captures ~10–70 min apart, same top frame every time).

**Two distinct stack-trace variants of the same underlying `replay()` spin have been
observed** on this box, depending on whether speculative decoding (MTP) is enabled:

**Variant A — via the MTP/speculative-decode draft-proposal path:**

**Variant B — via the regular (non-speculative) decode forward path, observed after
disabling MTP as a mitigation attempt:**

Both bottom out at the identical frame: `replay (torch/xpu/graphs.py:107)` called from
`vllm/compilation/cuda_graph.py:360`. This strongly suggests the bug is in the XPU
graph-replay call itself (or the state it depends on), not in either calling path —
MTP just changes which code path reaches it first/more often.

**Mitigation tried:** disabling MTP (speculative decoding) reduces frequency and
appears to make the spin less likely to require a full service restart to recover
from, and improves realized end-to-end throughput under concurrent load (measured
~44% higher tokens/sec over a wall-clock window, accounting for outage time), but does
**not** eliminate the spin — Variant B above was captured with MTP fully disabled.

**Independent third-party corroboration:** a public benchmarking log for the same
GPU (`steveseguin/b70-optimization-lab`, README) documents XPU-graph + MTP
producing corrupted/zero-acceptance output on this hardware generation:
> `MTP1 + XPU graph | 7.63 tok/s | 0.00 acceptance | corrupt (0/25) - do not use`
> `MTP off, XPU graph on (two boots) | 30.22 / 30.26 tok/s | - | faithful (23/25, within boot envelope)`

That log documents output corruption specifically with MTP+graph, which is a
different symptom (wrong output vs. our hang) but points at the same suspect
component (XPU graph replay interacting with speculative decoding) on the same GPU
family, and independently supports MTP+graph being unreliable on Battlemage.

Related-but-not-identical issues we found and ruled out as duplicates:
- vllm-project/vllm#48327 — same class of Intel-XPU CUDA-graph-replay issue, but
  reported as producing garbage output, not a hang.
- pytorch/pytorch#187277 — XPU graph replay crash (not a spin) on similar hardware.

Neither exactly matches a genuine infinite spin with climbing CPU and no crash/error,
so filing this as a distinct report rather than a duplicate.

### Steps to reproduce

1. Serve a GPTQ-quantized model on a single Intel Arc Pro B70 (Battlemage) via vLLM's
   native XPU backend, with CUDA/XPU graph capture enabled (default), `--kv-cache-dtype fp8`.
2. Drive sustained concurrent load: 2+ long-running agentic/chat-completion clients
   issuing overlapping requests continuously for tens of minutes.
3. Periodically (observed every ~10–25 min of concurrent runtime), the EngineCore
   process's MainThread enters `torch.xpu.graphs.replay()` and never returns; CPU
   usage for that thread pegs at 100% indefinitely. Confirm via repeated `py-spy dump`
   of the EngineCore PID showing an identical frame with climbing `/proc/<pid>/stat`
   CPU ticks across snapshots taken minutes apart.
4. The server stops answering any new request; recovery currently requires a full
   process restart (nothing short of restart has been found to un-stick it).
