### Your current environment

- vLLM v0.30.0, image `docker.io/vllm/vllm-openai-rocm:v0.30.0` (amd64 `sha256:2e7da1ad1c66836802072588adea75f9f4991da5f9545b4318e91d422c22ce6a`) with fastokens 0.3.1 added, nothing else changed
- 8x AMD Instinct MI325X (gfx942), ROCm driver 6.19.14
- Kubernetes, TP 4 on four of the eight cards
- The same failure on v0.29.0


### 🐛 Describe the bug

`Qwen/Qwen3.8-Flash-Next-FP8` at revision `236dfdf285828023ca3bcd3f37366c58a3469b13` fails in weight loading on ROCm. Every worker dies with the same error:

```
ValueError: There is no module or parameter named 'ngram_embedding.weight_scale' in Qwen4ExpNGramEmbedding. The available parameters belonging to ngram_embedding (PLEVocabParallelEmbedding) are: {'ngram_embedding.weight'}
```

Command, run inside the image:

```
vllm serve Qwen/Qwen3.8-Flash-Next-FP8 \
  --revision 236dfdf285828023ca3bcd3f37366c58a3469b13 \
  --tensor-parallel-size 4 --enable-expert-parallel \
  --max-model-len 262144 --gpu-memory-utilization 0.85
```

The checkpoint is `quant_method: fp8` with `weight_block_size: [128, 128]` and dynamic activations. Its n-gram embedding table is F8_E4M3 with one BF16 global scale stored as `ngram_embedding.weight_scale`.

**Why it still fails after #54722 and #54882.** Both PRs are in v0.30.0, and both fix the FP8 PLE scale in the NVIDIA model path only (`vllm/models/qwen4_exp/nvidia/`). The ROCm build takes `vllm/models/qwen4_exp/amd/ple_layer.py`, which defines its own `Qwen4ExpNGramEmbedding` with no FP8 method and no `weight_scale` parameter. The scale tensor has nowhere to land on AMD. This is still true on main after #57497. #54765 is the NVIDIA report of the same error.

**What works.** `--enable-expert-parallel` gets the checkpoint past the block-quant check that stops plain TP 4 and TP 8 (expert width 640 against a 128 block gives 160 or 80 per rank). With EP the workers reach weight loading and fail only on the scale above. The bf16 checkpoint `Qwen/Qwen3.8-Flash-Next` serves on the same box and image.

**Ask.** Port the FP8 PLE weight-scale handling into the AMD `Qwen4ExpNGramEmbedding`, or share one embedding method between the two paths. Until then the FP8 checkpoint cannot be served on ROCm at any TP, on MI325X or MI355X.

I can test a fix on MI325X.

### Akhilesh-Chandewar · 2026-09-25

Verified the AMD FP8 PLE path against current `main` (`25b0add`, 2026-09-25) — the pieces this report asks for appear to already be in place post-v0.30.0:

1. **Method selection**: with an `Fp8Config(weight_block_size=[128, 128])` checkpoint, `Qwen4ExpPLEEmbeddingMethod.from_quant_config()` selects `Qwen4ExpPLEFp8EmbeddingMethod` for the `*.ple.ple_embedding.ngram_embedding` prefix — so `create_weights` registers `weight_scale` and the whole-object dequantize path applies the global scale (verified programmatically on CPU).

2. **AMD FP8 loading has dedicated coverage on main**: `tests/models/qwen4_exp/test_ple.py::test_amd_fp8_embedding_loads_checkpoint_shards_and_global_scale` ("AMD checkpoint loading must accept and apply the global FP8 scale") asserts `weight.dtype == torch.float8_e4m3fn` and the loaded scale, across `[cpu-resident, cpu-offload]` params. This test is not in v0.30.0.

3. The shared `Qwen4ExpPLEFp8EmbeddingMethod` (in `vllm/models/qwen4_exp/common/ngram_embedding.py`) now raises a clear `ValueError` in `process_weights_after_loading` if the global scale is missing — the fail-open guard from #54722, applied to both backends.

Since the failing run was on the v0.30.0 release image, could you retry with a current nightly (`vllm/vllm-openai-rocm:nightly` or main)? If it still fails on main at revision `236dfdf285828023ca3bcd3f37366c58a3469b13`, the new error message (if any) would pinpoint whether this is a different gap than the one the merged NVIDIA-path fixes covered.
