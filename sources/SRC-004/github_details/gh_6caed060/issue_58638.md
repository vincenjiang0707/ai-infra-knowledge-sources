# [Issue #58638] [RFC]: KV cache grouping for hybrid models with speculative drafters

source: https://github.com/vllm-project/vllm/issues/58638
state: open | updated: 2026-09-26T06:12:12Z
labels: RFC, kimi

## 正文

**Status:** Draft · **PRs:** #58207 (group size), #58380 (prefer `BLHNC`, stacked on #58207)

## TL;DR

Speculative drafters on hybrid models add a small KV cache bucket of their own, which breaks vLLM's KV cache grouping heuristic in two ways:

- **Too many groups (Qwen3.5 / 3.6 + DFlash):** a one-layer drafter bucket forces **one group per layer**: Qwen3.5-27B goes from 4 to 70 groups (#49730), Qwen3.6-35B-A3B from 4 to 46. Each group rebuilds attention metadata every step, so DFlash loses much of its speedup; forcing fewer groups today costs KV cache capacity.
- **Full attention padding (MiMo-V2.5 + DFlash):** the 5-layer drafter bucket sets the group size, which doesn't divide the target's 9 full attention layers, so a full attention padding layer is allocated for the whole context (#58175). Kimi-K3 + DSpark has the same problem: its 5-layer drafter bucket pads the 24 MLA (full attention) layers, with 20 groups.

Checked and unaffected (identical grouping with and without these PRs): GLM-5.3-Flash + DFlash2, MiniMax-M3 + DSpark, DeepSeek-V4-Flash + DSpark.

A two-part proposal fixes both:

| part | problem | fix | Qwen3.6-35B-A3B + DFlash | MiMo-V2.5 + DFlash |
|---|---|---|---|---|
| **1 · #58207** | small drafter buckets force per-layer KV groups, or full attn padding | pick the group size by worst-case padding **bytes**; `--min-kv-cache-group-layers` (default 3) | 46 → **17** groups, **+54%** tok/s @c=1, **+36%** @c=32 | 11 → **7** groups, no full attn padding, KV capacity 5.76M → 5.96M |
| **2 · #58380** | `LBHNC` forces padding when drafter bytes/token ≠ target's | prefer `BLHNC` when the backends can run it and it avoids full attn padding or needs fewer groups | **5** groups, no padding, 7.53M tokens (> main's 7.42M); Triton only today | stays `LBHNC` at 7 groups (`BLHNC` would need 12 and has no full attn padding to remove) |

The parts are complementary: part 2 picks the path; part 1 is the fallback path (§5).

## 1. Background

**Motivation.** Enabling DFlash on Qwen3.5-27B raises the number of KV cache groups from 4 to **70**. Without a drafter, its 64 layers (48 GDN + 16 full attention) form 4 groups of 16; with DFlash, every layer gets its own group (64 target + 6 drafter). The drafter adds a one-layer full attention bucket, and the grouping heuristic falls back to one group per layer (#49730). Every group rebuilds its attention metadata each step, and GDN (linear attention) metadata builders are expensive, so this becomes per-step host overhead and DFlash runs well below its expected speedup; the effect is larger on Qwen3.5-4B. Forcing a larger group size recovers the throughput but, with today's grouping, costs KV cache capacity.

A drafter can also cost KV cache capacity rather than speed. MiMo-V2.5 + its DFlash drafter has buckets `[9 full, 39 SW, 5 drafter SW]`: the drafter bucket is the smallest, so the group size becomes 5, and the 9 full attention layers get a padding layer that grows with context (#58175 reports ~10% more KV capacity once it's removed). Kimi-K3 + its DSpark drafter behaves the same way (Case 3).

Related reports:

| report | model | groups | effect |
|---|---|---|---|
| #49730 | Qwen3.5-27B / 4B + DFlash (H100) | 4 without DFlash → 70 with (one per layer) | DFlash ITL much slower than expected; forcing gs=16 recovers ~10% tok/s on 27B but shrinks KV capacity 216k → 141k tokens |
| #51742 | Qwen3.6-35B-A3B + DFlash (H200) | 46 | `build_attn_metadata` ~31 ms/step vs ~6 ms at 10 groups; output tok/s ~2× at c=1 with fewer groups |
| #52297 | Qwen3.6-35B-A3B + DFlash | — | one GDN `build()` takes ~900 µs and is repeated per group |
| #58175 | MiMo-V2.5 + DFlash | 11 | 1 full attn padding layer; removing it gives +10.57% KV capacity (their setup); +8.4% in ours (5.76M → 6.25M) |
| this RFC | Kimi-K3 + DSpark (`RedHatAI/Kimi-K3-speculator.dspark`, TP4) | 20 | 1 MLA (full attn) padding layer; #58207: 17 groups, no MLA padding, +0.37% KV capacity |
| #42505, #46462 | Qwen3.5 / 3.6-35B-A3B + DFlash | — | DFlash slower than expected / than baseline at higher concurrency; not root-caused, likely related |

This RFC's own measurement (§4.1): Qwen3.6-35B-A3B + DFlash on B300 goes from 460 → 733 tok/s at c=1 when the 46 groups drop to 17.

### 1.0 Terms

| term | meaning |
|---|---|
| bucket | all layers whose KV cache specs merge (same attention type and shape) |
| group / `group_size` (gs) | a KV cache group shares one block table; buckets are split into groups of `group_size` layers |
| page | one layer's slice of a block; its size is that layer's bytes/token × block size |
| padding | layer slots in a group with no layer behind them; allocated but never written |
| manager vs kernel block | the KV manager allocates *manager* blocks; attention kernels may need them split into smaller *kernel* blocks |
| `LBHNC` | layer-outermost `KVCacheLayout` (today's default): every page is resized to one size, each group gets `group_size` pages per block |
| `BLHNC` | block-outermost `KVCacheLayout`: a block is one contiguous run of per-layer pages, so pages of different sizes share a block. `LBNHC`/`BLNHC` group the same way as `LBHNC`/`BLHNC` |

### 1.1 Buckets, groups, padding

```
Legend:  F/f = target/DRAFTER full attn   S/s = target/DRAFTER sliding window   M = mamba/GDN
         ▓ = full attn padding (grows with context, up to max_model_len)
         ░ = SW / mamba padding or idle page (bounded by window / state)

drafter full-attn group, group_size = 5 (one physical block):
│ f │ ▓ │ ▓ │ ▓ │ ▓ │   4 of 5 pages never written

every group's block has the same byte size (block IDs are shared across groups)
```

| cost | grows with | note |
|---|---|---|
| per-step metadata | # groups | one block table + builder call per group; GDN builders are expensive |
| KV capacity | padded slots × bytes/request | full attn slot: up to `max_model_len` tokens; SW / mamba slot: bounded |

### 1.2 Bad cases

```python
group_size = min(bucket sizes)                       # main
if max(bucket sizes) < 1.5 * min(bucket sizes):
    group_size = max(bucket sizes)
```

The heuristic sizes groups from bucket **counts** only. A drafter adds a small bucket of its own, which breaks it in the ways below. Each group is drawn as `[ ]` with one letter per layer slot.

#### Case 1: Qwen3.5 / 3.6 + DFlash: a one-layer drafter bucket forces one group per layer

Qwen3.5-27B + DFlash (4 → 70 groups), Qwen3.6-35B-A3B + DFlash (4 → 46), Qwen3.5-35B-A3B + Eagle3 (4 → 41). Per-step metadata overhead grows with the layer count.

```
Qwen3.6 alone:     buckets [30 M, 10 F]              gs = 10  →  4 groups
Qwen3.6 + DFlash:  buckets [30 M, 10 F, 5 s, 1 f]    gs = min(30, 10, 5, 1) = 1

bucket                   layers   groups on main (one layer each)
target mamba/GDN    M      30     [M][M][M][M][M][M][M][M][M][M] … [M]   30
target full attn    F      10     [F][F][F][F][F][F][F][F][F][F]         10
drafter SW          s       5     [s][s][s][s][s]                         5
drafter full attn   f       1     [f]   ← smallest bucket sets gs = 1     1
                                                                        ────
                                        metadata builds per step:        46
```

With #58207: Qwen3.6 + DFlash 17 groups, Qwen3.5 + Eagle3 9 groups.

#### Case 2: MiMo-V2.5 + DFlash: the drafter's bucket doesn't divide the target's

MiMo-V2.5 + DFlash. The 5-layer drafter bucket is the smallest, so it sets gs=5, and the 9 full attention layers get a padding slot that grows with context.

Why full attention padding is the one that matters: a padding slot costs whatever a real layer of that type would hold for each request.

| padding slot | holds per request | MiMo-V2.5, per slot |
|---|---|---|
| full attention | every token of the context | 2.5 KiB/token × 256k tokens ≈ **640 MiB** (≈ 2.5 GiB at 1M) |
| sliding window | only the window (128 tokens), plus tokens in flight | 5 KiB/token × 128 ≈ **0.6 MiB** (≈ 41 MiB worst case with 8k in-flight tokens) |

So one full attention padding slot wastes as much as hundreds of sliding-window slots, and it keeps growing with context length.

```
main    gs = 5 → 11 groups
  F  [FFFFF][FFFF▓]              ← full attn padding
  S  [SSSSS] ×7 + [SSSS░]
  s  [sssss]

#58207  gs = 9 → 7 groups
  F  [FFFFFFFFF]                 ← no full attn padding
  S  [SSSSSSSS░] ×4 + [SSSSSSS░░]
  s  [sssss░░░░]
```

#### Case 3: Kimi-K3 + DSpark: same as Case 2, with MLA

Kimi-K3 has 69 KDA (linear attention) and 24 MLA (full attention) layers; the DSpark drafter (`RedHatAI/Kimi-K3-speculator.dspark`) adds 5 sliding-window layers. The drafter bucket sets gs=5, which doesn't divide 24, so an MLA padding slot is allocated for the whole context.

```
L = KDA (linear attention)

main    gs = 5 → 20 groups
  L  [LLLLL] ×13 + [LLLL░]
  F  [FFFFF] ×4 + [FFFF▓]        ← MLA (full attn) padding
  s  [sssss]

#58207  gs = 6 → 17 groups
  L  [LLLLLL] ×9 + [LLLLL░] ×3
  F  [FFFFFF] ×4                 ← no MLA padding
  s  [sssss░]
```

Served (Kimi-K3-pruned75, same 93 layers, TP4): KV capacity 4.76M → 4.78M tokens at 131k context. #58380 keeps `LBNHC` here.

## 2. Part 1 · #58207: group size by worst-case padding bytes

Replace the [min / 1.5×-max heuristic](https://github.com/vllm-project/vllm/blob/b3a87b2d04e6439e2a1aef0cbf9ca65328076c86/vllm/v1/core/kv_cache_utils.py#L1547-L1558) with a search over group sizes that minimizes **worst-case padding bytes** per request, bounded below so groups can't explode:

```python
lo = max(smallest bucket, min(min_kv_cache_group_layers, largest bucket))
group_size = argmin over gs in [lo, largest bucket] of
    (Σ padding_slots(bucket, gs) × spec.max_memory_usage_bytes(vllm_config), num_groups(gs))
```

Padding is costed in bytes, so full attention padding (which grows with `max_model_len`) is avoided in favor of bounded sliding-window / mamba padding. The lower bound keeps groups from exploding: never below the smallest bucket, and never below `--min-kv-cache-group-layers` (default 3), so a one-layer drafter bucket can't force one group per layer.

```
Qwen3.6 + DFlash, gs = 3 → 17 groups (each bucket padded independently)
  M  [MMM] ×10    F  [FFF][FFF][FF▓][FF▓]    s  [sss][ss░]    f  [f▓▓]
```

## 3. Part 2 · #58380: prefer `BLHNC`

In `BLHNC` a block is one contiguous run of per-layer pages, so pages of different sizes share a block instead of being padded to one size. The widest non-state bucket sets the block; mamba / SW groups split to fit it. #58380 prefers these layouts when specs have mixed page sizes **and** every backend runs each attention block unsplit, since packed blocks can't be split into smaller kernel blocks:

| backend (B300) | kernel block sizes | can use `BLHNC` |
|---|---|---|
| Triton | any multiple of 16 | yes |
| FlashInfer | 16 / 32 / 64 | no |
| FlashAttention hd256 (FA4) | 128 | no |

**`BLHNC` cost check:** `BLHNC` is not always better (MiMo below: 7 → 12 groups), so #58380 also computes both groupings from the specs and picks `BLHNC` only if the `LBHNC` grouping would pad full attention, or `BLHNC` needs fewer groups.

Each row below is a separate group; rows align because every block is the same size:

```
Qwen3.6 + DFlash: 5 groups, 12-page blocks
full-attn ×1   │ F │ F │ F │ F │ F │ F │ F │ F │ F │ F │   f   │   10 target + drafter (2 pages): no padding
mamba ×3       │ M │ M │ M │ M │ M │ M │ M │ M │ M │ M │ ░ │ ░ │   10 GDN states each, 2 idle pages
drafter sw ×1  │   s   │   s   │   s   │   s   │   s   │ ░ │ ░ │   5 layers × 2 pages, 2 idle pages

MiMo-V2.5 + DFlash under `BLHNC` (not picked by the cost check): 12 groups, 9-page blocks
full-attn ×1   │ F │ F │ F │ F │ F │ F │ F │ F │ F │   9 full pages: no padding
SWA ×10        │   S   │   S   │   S   │   S   │ ░ │   4 layers × 2 pages, 1 idle page (one group has 3)
drafter SW ×1  │  d d d d d  (1.6 pages each)  │ ░ │   5 layers × 64 KiB = 8 pages, 1 idle page
```

## 5. How the two parts fit together

**Defaults after both PRs merge** (default backends, no `VLLM_KV_CACHE_LAYOUT`). Padding is per request at 256k context (worst case, 8192 in-flight tokens):

| model (B300 backend) | main today | after #58207 + #58380 |
|---|---|---|
| Qwen3.6 + DFlash (FlashInfer/FA) | `LBHNC`, 46 groups, no padding | `LBHNC`, **17** groups, 3.05 GiB padding (full attn) |
| Qwen3.6 + DFlash (`--attention-backend TRITON_ATTN`) | `LBHNC`, 46 groups, no padding | **`BLHNC`, 5** groups, 58 MiB padding |
| MiMo-V2.5 + DFlash (FA) | `LBHNC`, 11 groups, 726 MiB padding (640 MiB full attn) | `LBHNC`, **7** groups, 469 MiB padding (no full attn) |
| Kimi-K3 + DSpark (TP4) | `LBHNC`, 20 groups, 1 MLA padding layer | `LBHNC`, **17** groups, no MLA padding |
| MiMo-V2.6 + MTP (FA) | `LBHNC`, 6 groups, 203 MiB padding (SW) | unchanged |
| Qwen3.5 + Eagle3 (FlashInfer/FA) | `LBHNC`, 41 groups, no padding | `LBHNC`, 9 groups, 4 drafter full attn padding slots |
| GLM-5.3-Flash + DFlash2, MiniMax-M3 + DSpark, DeepSeek-V4-Flash + DSpark | unchanged | unchanged |
| single page size (Gemma3, gpt-oss, Llama4, Qwen3.5, …) | unchanged | unchanged |

**Recommendation:** land #58207 first (helps every layout/backend), then #58380. `VLLM_KV_CACHE_LAYOUT` / connector preferences still win.

## 6. Alternatives considered

Other open PRs that change this heuristic, and what each gives for Qwen3.6 + DFlash:

| PR | approach | Qwen3.6 + DFlash | shortcoming |
|---|---|---|---|
| #51742 | ignore one-layer buckets when taking the min | gs=5, 10 groups | pads the drafter's full attn layer with 4 slots that grow with context |
| #58175 | shrink gs to a divisor of the full attn bucket sizes (targets MiMo) | gs=1, 46 groups | doesn't help drafters |
| #49472 | minimize padding + number of groups, counted in layers | gs=5, 10 groups | a padded full attn layer counts the same as a sliding-window one, so it pads full attn |

Other approaches:

- **Bigger `block_size` for the lone drafter group** (same bytes, fewer layers): prefix-cache hits align to the LCM of group block sizes, so hits get ~5× coarser for every group.
- **Only forbid one layer per group (`group_size ≥ 2`) and minimize padding:** still 24 groups for Qwen3.6 + DFlash, and over-splits models with cheap padding (Gemma3-27B 7 → 31 groups).
- **Absolute cap on the number of groups:** the right cap depends on the backend (GDN vs FlashAttention metadata cost).
- **Drafter-aware sizing** (size groups from target buckets, pad the drafter): worst case when the drafter has a full attention layer, and drafter layers can only be identified heuristically at grouping time.
- **Separate KV pool for drafter layers:** removes the constraint entirely, but is a much larger allocator change.
- **#58345 (rescale sliding-window blocks for `BLHNC`):** on main (since #53007) sliding-window layers already use the full attention block size when the backend allows it (group block sizes 262144 ×3, 592, 592); when it doesn't, rescaling would need kernel-block splitting, which `BLHNC` can't do.

## 7. Open questions

1. **Default `--min-kv-cache-group-layers`:** 3 (17 groups, −30% KV capacity on Qwen3.6 + DFlash) or 4 (10 groups, +2–5% tok/s, −35%)? Should it depend on whether the model has GDN layers?
2. **`BLHNC` with FlashInfer / FlashAttention:** re-page inside the kernels (as #55219 / #57169 do for sparse MLA), or stop inflating the block size for block-outermost layouts (but then few GDN states fit per block)?
3. **FlashAttention drafter block size:** the 128-only FA4 hd256 kernel block is derived from the *target's* head size and applied to a hd128 drafter, causing `No common block size for 592` on main unless `--block-size 128` is set. Fixed separately by #58630.
4. **Validation:** #58380 switches mixed-page-size models to `BLHNC` when the cost check passes on capable backends; needs accuracy and throughput validation beyond DFlash and MiMo.

## 8. Methodology

```bash
vllm serve Qwen/Qwen3.6-35B-A3B-FP8 --max-num-seqs 32 --no-enable-prefix-caching --block-size 128 \
  --mamba-cache-dtype bfloat16 --mamba-ssm-cache-dtype bfloat16 [--min-kv-cache-group-layers N] \
  [--attention-backend TRITON_ATTN] \
  --speculative-config '{"model":"z-lab/Qwen3.6-35B-A3B-DFlash","method":"dflash","num_speculative_tokens":7}'
vllm bench serve --model Qwen/Qwen3.6-35B-A3B-FP8 --dataset-name hf --dataset-path openai/gsm8k --hf-split test \
  --num-prompts max(32, 8*C) --max-concurrency C --num-warmups 2*C
```

| item | value |
|---|---|
| hardware | 1× B300 per run (MiMo: TP2, `max_model_len` 1M) |
| runs | single; noise ~2–3% (repeated gs=5) |
| interactivity | 1000 / p99 TPOT |
| acceptance length | 5.1–5.2 in all Qwen runs |
| `--block-size 128` | needed on all variants, including main: FlashAttention's 128-only FA4 hd256 kernel block is derived from the target's head size and also applied to the hd128 drafter, which otherwise fails with `No common block size for 592` |
