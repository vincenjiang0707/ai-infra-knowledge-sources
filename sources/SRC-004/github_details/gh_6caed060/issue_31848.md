### Motivation.

Authors: @hao-aaron @SumanthRH 

vLLM serves not only as an inference runtime for serving requests from end users, but also as a means of serving requests for large language model post-training. The vLLM model weights must be synced periodically in order to make sure that the rollouts match the distribution that would have been generated by the base model weights during post-training. Currently, the official methodology for performing weight sync is to inject additional functionality to each worker class to support the creation of process groups and broadcasting functionality, see: https://github.com/vllm-project/vllm/blob/main/examples/offline_inference/rlhf.py.

However, there are no standardized methods for performing online weight syncing. Open source projects like [SkyRL](https://github.com/NovaSky-AI/SkyRL/blob/01b4ee09f9983e8452258a8fa88a6fc025da6cfb/skyrl-train/skyrl_train/inference_engines/vllm/vllm_engine.py#L69), [VeRL](https://github.com/volcengine/verl/blob/252d76908b903ad8fb6969eb3a5e5f873c95ea2b/verl/experimental/one_step_off_policy/fsdp_workers.py#L52), and [TRL](https://github.com/huggingface/trl/blob/42cce51cf016e3c9502274a0ed05da53d488506c/trl/scripts/vllm_serve.py#L83) need to include their own implementations of the weight syncing infrastructure, leading to added complexity for developers seeking to adopt vLLM as their inference server for post-training workloads.

The lack of consistent weight syncing APIs leads to duplicated efforts on the side of users attempting to adopt vLLM. It requires users to version lock to specific implementations of the weight syncing infrastructure, as well as locking into specific torch.distributed backends.

Other relevant RFCs
[Online quantization with model_loader](https://github.com/vllm-project/vllm/issues/30359): This RFC proposes a way to improve the online quantization which matches the proposal here about having a step for finalizing the weight syncing operation

### Background
Weight syncing with NCCL (with disaggregated training and inference) is typically done in many RL frameworks (SkyRL, SLIME, OpenRLHF etc) by having rank 0 of the trainer form a process group with all ranks of the inference engine.

There are two methods that are typically implemented per worker:
`init_weight_update_group(master_address, master_port, rank_offset, world_size)`
- Initializes the process group. Should run on all the worker ranks.
- master_address and master_port are the IP and a free port for the machine with rank 0 of the trainer
- rank_offset is the rank offset in the process group for this particular worker. For example, if you have 2 vLLM replicas with TP 2, then the TP rank 0 for the 2nd replica has rank_offset of 3 (1 for rank 0 of trainer + 2)
- world_size is the global world size

`update_weight(name, src_dtype, shape)`
Initiates a weight update with NCCL. Should run on all the worker ranks.

Each worker will allocate a fixed buffer based on src_dtype and shape and then update the weights. The data is received by a NCCL broadcast operation from rank 0. We then simply call model_runner.model.load_weights after receiving weights.

Most of the logic can stay the same → just issue torch.distributed.broadcast in a loop, and call load_weights once. Trainers can still just call this one by one if needed by just formatting a single input as a list.

### Proposed Change.

We propose native support for weight syncing, both through offline inference via LLM and AsyncLLM, as well as through HTTP calls via the OpenAI-compatible API. A first draft implementation can be found here: https://github.com/vllm-project/vllm/compare/main...ahao-anyscale:vllm:weight_transfer_prototype

### New API Endpoints

The main features of this new API include exposing the following new endpoints:

#### `POST /init_weight_transfer`

Initializes the weight transfer mechanism by creating a process group between the trainer and all vLLM workers.

**Parameters (NCCL backend):**
| Parameter | Type | Description |
|-----------|------|-------------|
| `master_address` | string | IP address of the trainer (rank 0) |
| `master_port` | int | Free port on the trainer machine for NCCL rendezvous |
| `rank_offset` | int | Starting rank for vLLM workers in the process group. Typically 1 (trainer is rank 0) |
| `world_size` | int | Total number of processes (1 trainer + N vLLM workers across all DP/TP ranks) |

**Worker Behavior:**
1. Each worker computes its unique global rank: `rank = (dp_rank * world_size_per_dp + tp_rank) + rank_offset`
2. Creates a `StatelessProcessGroup` connected to the trainer's master address/port
3. Initializes a `PyNcclCommunicator` on the current CUDA device for subsequent broadcasts


While this is being called, a process on the trainer side must also simultaneously join the process group.


#### `POST /update_weights`

Receives weight tensors from the trainer and loads them into the model. Weights are transferred and loaded incrementally to avoid OOM.

**Parameters (NCCL backend):**
| Parameter | Type | Description |
|-----------|------|-------------|
| `names` | list[str] | List of parameter names matching the model's state dict keys |
| `dtype_names` | list[str] | List of torch dtype names (e.g., "bfloat16", "float32") |
| `shapes` | list[list[int]] | List of tensor shapes for each parameter |

**Worker Behavior:**
1. For each weight in the batch:
   - Allocates an empty CUDA tensor with the specified dtype and shape
   - Receives the tensor data via `nccl.broadcast(src=0)` from the trainer
   - Immediately calls `model.load_weights([(name, tensor)])` to load into the model
   - Frees the temporary tensor to avoid memory accumulation

The trainer must issue corresponding `broadcast` calls for each weight in the same order.


#### `POST /finalize_weight_update`

Finalizes the weight update by running post-processing required for quantized or custom kernel formats.

**Request Body:** None

**Worker Behavior:**
1. Calls `process_weights_after_loading(model, model_config, device)`
2. This handles any necessary weight transformations such as:
   - Quantization to target precision (e.g., FP8, INT8)
   - Packing weights for optimized CUDA kernels
   - Re-computing any cached values derived from weights

NOTE: this may change depending on the results of https://github.com/vllm-project/vllm/issues/30359

**EDIT: this endpoint is made redundant by https://github.com/vllm-project/vllm/issues/30359, and will not be included in final version**


### Architecture

The implementation introduces a pluggable `WeightTransferEngine` abstraction that separates weight transfer transport logic from the worker implementation, allowing different backends to be plugged in.

**Supported Backends:**
- **NCCL**: Uses NCCL broadcast operations for distributed weight transfer
- **IPC**: Uses CUDA IPC for same-node weight transfer via shared memory handles

### Usage Example
A full RL example with the LLM interface can be found [here](https://github.com/ahao-anyscale/vllm/blob/weight_transfer_prototype/examples/offline_inference/new_weight_syncing/rlhf.py). An http example is [here](https://github.com/ahao-anyscale/vllm/blob/weight_transfer_prototype/examples/offline_inference/new_weight_syncing/rlhf_http.py).

The main structure of the two are the same. We begin by initializing process groups. The following code is from a process on the trainer side. We launch an LLM instance as a Ray actor, and save the handle so the trainer can make calls.
```
# Set up the communication channel between the training process and the
# inference engine.
master_address = get_ip()
master_port = get_open_port()

handle = llm.init_weight_transfer.remote(
    WeightTransferInitRequest(
        init_info=asdict(
            NCCLInitInfo(
                master_address=master_address,
                master_port=master_port,
                rank_offset=1,
                world_size=3,
            )
        )
    )
)

model_update_group = stateless_init_process_group(
    master_address, master_port, 0, 3, torch.device("cuda:0")
)
ray.get(handle)
```
We then sync the weights by asynchronously calling the vllm endpoint while also broadcasting the trainer side weights
```
# Synchronize the updated weights to the inference engine using batched API.
# Collect all weight metadata
names = []
dtype_names = []
shapes = []
for name, p in train_model.named_parameters():
    names.append(name)
    dtype_names.append(str(p.dtype).split(".")[-1])
    shapes.append(p.shape)

# Issue update_weights call with NCCL-specific update info
handle = llm.update_weights.remote(
    WeightUpdateRequest(
        update_info=asdict(
            NCCLUpdateInfo(
                names=names,
                dtype_names=dtype_names,
                shapes=shapes,
            )
        )
    )
)

# Broadcast all weights from trainer
for name, p in train_model.named_parameters():
    model_update_group.broadcast(p, src=0, stream=torch.cuda.current_stream())

ray.get(handle)

# Finalize the weight update (processes weights for quantization/kernel format)
ray.get(llm.finalize_weight_update.remote())
```
### Open Questions
- How should we handle online quantization? Should we merge /finalize_weights together with the /update_weights API? There could be situations where update weights API is called multiple times before calling finalize weights which would motivate disaggregating the apis. Our pattern of calling update_weight before finalizing seems to align with https://github.com/vllm-project/vllm/issues/30359
One answer is that the API keeps the flexibility of keeping the operations separate, regardless of how the engine handles the weight syncing under the hood, i.e. whether it is fusing load_weights and process_weights or keeping them separate. 
- The existing pause and resume endpoints can be combined with the above API to implement fully async RL training workflows, see [here](https://skyrl.readthedocs.io/en/latest/tutorials/fully_async.html) for various async RL strategies. Are the current pause and resume APIs sufficient for current and future RL use cases?

### kouroshHakha · 2026-01-12

Given [[WIP] [QeRL] Layerwise Reloading #32133](https://github.com/vllm-project/vllm/pull/32133) and [[RFC] [QeRL]: Online Quantization and Model Reloading #30359](https://github.com/vllm-project/vllm/issues/30359) my recommendation is this:


1) Standardize on a single entrypoint (either call it update_weights or reload_weights) (also called out by @rizar). They are basically one thing. For the sake of argument let's go with `update_weights`

2) update weights should support batching so that the bucketing is supported from the client side. i.e. client can send a single layer at a time, multiple layers batch together or all weights batch together -- the execution of weight sync and weight update can be per layer to minimize the memory overhead in the quantization case but we should make this an implementation detail (@rizar)

3) What is missing from the current proposal is to also have a checkpoint format. Right now the engine wouldn't know what format the synced weights would be in. **We could augment the request body to include this information**, e.g.

```
WeightFormat:
       type: Literal["checkpoint", "kernel"]
       # reserve this type of other future bits of information that we might need to pass in
       

class BaseUpdateInfo:
       format: WeightFormat

class NCCLUpdateInfo(BaseUpdateInfo):
       names: list[str]
       dtype_names: list[str]
       shapes: list[list[int]]

# Usage
handle = llm.update_weights.remote(
    WeightUpdateRequest(
        update_info=asdict(
            NCCLUpdateInfo(
                names=names,
                dtype_names=dtype_names,
                shapes=shapes,
                weight_format={"type": "checkpoint"|"kernel"}
            )
        )
    )
)
```

4) Given [[WIP] [QeRL] Layerwise Reloading #32133](https://github.com/vllm-project/vllm/pull/32133) it seems like `/finalize_update_weight` will be redundant. I think having it depends on when the above lands. If QERL PR were to land then the `process_weights_after_loading` will be called per layer in case of `checkpoint` format, so even if there was a `/finalize_update_weight` it should become a no-op to keep the backwards compatibility (and make a reservation to do anything that might need full weight context). **I think of it as more like as keeping API expressivity high than a functional thing for future proof-ness**. This is because of (1). Since `update_weight` need to support partial update and bucketing, if there are things that need to be done after all weights have been actually loaded (e.g. similar to the current way of doing online quantization which is not memory efficient),  we need another API like the `/finalize` api.

To implement (3), in [[WIP] [QeRL] Layerwise Reloading #32133](https://github.com/vllm-project/vllm/pull/32133) it is preferable to  make the `update_weights` API on the `model_runner` compatible with `WeightFormat` type from above (i.e. don't make it a boolean) and in [`gpu_worker` ](https://github.com/vllm-project/vllm/pull/31943/changes#diff-62b35645ec2e0a565f1367fda869f582ca181cdc04d7b8ca36db71218216d6d7 ) where we call `weight_transfer_engine.recieve_weights` we do it on `self.model_runner.update_weights` rather than `self.model_runner.model.load_weights`. i.e.


```
# in gpu_worker.py

def update_weights(self, update_info: dict) -> None:
    """
    Batched weight update from the trainer.

    Args:
        update_info: Dictionary containing backend-specific update info
    """
    if self.weight_transfer_engine is None:
        raise RuntimeError("Weight transfer not initialized.")

    # Parse dict into backend-specific typed dataclass
    typed_update_info = self.weight_transfer_engine.parse_update_info(update_info)

    # Receive and load weights incrementally to avoid OOM
    self.weight_transfer_engine.receive_weights(
        typed_update_info,
        update_weights_fn=self.model_runner.update_weights, # instead of self.model_runner.model.load_weights
    )

```

This implies adopting `receive_weights` implementations to conform to `ModelRunner.update_weights` API creating a dependency on the [[WIP] [QeRL] Layerwise Reloading #32133](https://github.com/vllm-project/vllm/pull/32133) PR.
