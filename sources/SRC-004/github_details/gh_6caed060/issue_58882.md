## 正文

## The feature, motivation and pitch

Could `ROCM_AITER_UNIFIED_ATTN` support an explicit `LBNHC` (NHD) cache layout for compatible configurations, while retaining its existing default layout?

The backend currently advertises only `LBHNC` and `LHBNC` without a KV connector, and only `LBHNC` with a connector. Consequently, requesting `LBNHC` fails during layout resolution. This remains true in [upstream main at a9eafde59c](https://github.com/vllm-project/vllm/blob/a9eafde59cbd55182dc2265cc398b7186f0a0eaa/vllm/v1/attention/backends/rocm_aiter_unified_attn.py#L121-L129).

In our BF16, TP=1, non-connector experiments, changing only the backend's supported-layout declaration allowed its existing attention and cache-write paths to execute on NHD. We did not modify attention kernels. We are investigating whether a common physical KV layout can avoid layout conversion between different execution backends; an explicit NHD option would allow that path to be evaluated using the AITER unified kernels.

Is there a remaining kernel, fused writer, or feature constraint that requires excluding `LBNHC` in this configuration? If so, could the restriction be conditional and documented?

### Minimal configuration

Run the following as a Python script in an unmodified ROCm vLLM environment, without a runtime layout patch:

```python
import os

os.environ["VLLM_ROCM_USE_AITER"] = "1"
os.environ["VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT"] = "0"
os.environ["VLLM_KV_CACHE_LAYOUT"] = "LBNHC"

from vllm import LLM

if __name__ == "__main__":
    llm = LLM(
        model="Qwen/Qwen3-8B",
        attention_backend="ROCM_AITER_UNIFIED_ATTN",
        tensor_parallel_size=1,
        dtype="bfloat16",
        kv_cache_dtype="auto",
        block_size=64,
        max_model_len=4096,
    )
```

The [layout resolver](https://github.com/vllm-project/vllm/blob/ced6857afa0ea7b2e3f0846a62e1394e90f15607/vllm/v1/attention/backends/utils.py#L301-L307) rejects this request because `LBNHC` is absent from the backend's advertised set. The error begins:

```text
VLLM_KV_CACHE_LAYOUT=LBNHC does not satisfy every supported set
```

### Experimental evidence

Our experimental override, installed in the engine workers, was limited to:

```python
RocmAiterUnifiedAttentionBackend.supported_kv_cache_layouts = classmethod(
    lambda cls: (KVCacheLayout.LBNHC,)
)
```

This is an experimental override, not a proposed unconditional upstream implementation.

For Qwen3-32B, we compared the default head-major configuration with this NHD configuration at context lengths 1,024, 4,096, 16,384 and 32,768. For cold runs and prefix-reuse runs separately, the saved generated tokens, first-token top-5 log-probabilities, and cache-hit counts matched exactly between layouts.

At 32,768 tokens, both layouts used the same set of 16 prompts in four fixed groups of four, with a 24,576-token cached prefix per prompt and 64 generated tokens. Every prompt reused its complete expected prefix in both layouts (16/16); cold, prefix-fill and reuse submissions were checked for atomicity. Engine logs confirmed that the patched run selected `LBNHC`.

These results are limited to the tested BF16, TP=1 configurations without KV connectors.

## Alternatives

We can currently select NHD with the vLLM Triton backend, or retain the AITER unified backend's head-major layout. In our tests, enabling NHD with AITER unified required a local override of `supported_kv_cache_layouts`.
