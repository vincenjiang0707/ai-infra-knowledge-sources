# [Issue #58677] Speculative-decoding draft model (EAGLE/MTP head) compile cache key flips between two values with byte-identical startup args — shared `VllmConfig` mutated in-place during main-model full-compile startup (v0.27.1; deterministic on 0.29)

source: https://github.com/vllm-project/vllm/issues/58677
state: open | updated: 2026-09-26T02:14:13Z
labels: speculative-decoding, quantization

## 正文

## Summary

On vLLM 0.27.1 with speculative decoding (MTP head, k=1), the **draft model's** torch.compile cache identity deterministically flips between exactly two values across restarts with **byte-identical argv and environment**. The flip factor is not the command line — it is whether the **main model compiles (cold start) or loads from cache (warm start)** on that startup.

Forensics on `cache_key_factors.json` (which records the actual hash factors) show the draft's `config_hash` differs between the two generations while env/compiler factors are identical: the shared `VllmConfig` object is **mutated in-place during the main model's warmup/CUDA-graph-capture phase**, after the backbone compiles with a clean hash but before the eagle head compiles. On a 0.29 development build (commit `g38537331d`, the same build referenced in #58653) the same forensics show `eagle_head config_hash == backbone config_hash` in **9/9 compile-era startups** across two independent deployments — i.e. 0.29 appears immune.

## Environment

- vLLM **0.27.1** (stable release), single GPU, single rank
- Model: Qwen3.8-27B (W4A16 quantized), hybrid attention (linear/GDN + full), MTP module
- Speculative decoding: MTP k=1; CUDA graph `PIECEWISE`; fp8 KV cache
- 0.27.1 evidence from deployment A; 0.29 control (dev build `g38537331d`, 2026-09-19) from deployment A's current build and deployment B

## Symptom

- The draft model's AOT/compile cache directory alternates between two values (`40a960c…` ↔ `81aa37e7…`) across **17 same-signature restarts** observed during one incident window, all with identical startup args.
- Every flip costs a full draft recompile (~196 s) at the next startup whose expected generation doesn't match — the draft cache hit rate is determined by the *previous startup's shape*, not by config.

## Forensics: `cache_key_factors.json`

vLLM writes `torch_compile_cache/<short_hash>/rank_0_0/<backbone|eagle_head>/cache_key_factors.json` recording the real hash factors. Comparing the **eagle head** across the two generations:

| factor | generation 1 (main compiled) | generation 2 (main loaded) | verdict |
|---|---|---|---|
| env_hash (231 keys) | `2e9cfbbedb14f457` | same | SAME |
| compiler_hash | `8e33489fd9` | same | SAME |
| **config_hash** | **`06b5820a50`** | **`b398c1fc03`** | **DIFF — the flip factor** |
| code_hash | `2b706e49…` | `91b0ecb5…` | DIFF (dynamo compile-counter side effect) |

Key observation: in generation 2 (clean), the eagle head's `config_hash` **equals the backbone's** (`b398c1fc03`) — the draft derives from the main config without changing hash factors. In generation 1, eagle ≠ backbone for the same process, i.e. between the backbone's compile and the eagle's compile, **something changed the config that feeds `compute_hash()`**.

## Why "same cache dir, diverging jsons"

- `compilation/backends.py:1053` (0.27.1): `if not self.compilation_config.cache_dir:` — the **shared** `CompilationConfig.cache_dir` is set by the backbone's compile; the eagle head then **reuses the backbone's cache dir** instead of deriving its own from its (now-dirty) factors.
- But each `cache_key_factors.json`'s `config_hash` is recomputed fresh at `__call__` entry (`backends.py:1034`, no caching).
- Result: both roles land in one directory while their jsons record diverging config hashes — the forensic signature that led us here.

## Startup-shape bisection (timeline, UTC)

| startup | main model | warmup+capture window | eagle config_hash | draft AOT saved as |
|---|---|---|---|---|
| 2026-09-17 00:09–00:12 | full compile | **present, 67.6 s** | `06b5820a50` (dirty) | `81aa37e7` |
| 2026-09-17 00:37 | direct load | absent | `b398c1fc03` (clean) | `40a960c` |
| 2026-09-20 04:09 | full compile | present | dirty | `81aa37e7` |
| 2026-09-22 19:35 | direct load | absent | clean | `40a960c` |

The warmup+capture phase exists **only** on full-compile startups, and it runs **between** backbone compile and eagle compile — exactly where the mutation must occur. **Flip factor = whether the main model compiles on that startup.**

## Mechanism chain

1. Backbone `__call__` computes `config_hash` fresh (clean).
2. Main-model warmup + CUDA-graph capture runs (full-compile startups only) — **this phase mutates the shared `VllmConfig` in-place** (exact field not yet isolated).
3. Eagle head `__call__` recomputes `config_hash` from the now-mutated config → different value.
4. Draft AOT save dir (derived from `[env_hash, config_hash, code_hash, compiler_hash]`) flips; the torch_compile_cache dir does not (reuse) → diverging-jsons signature.

## Ruled out (all with file:line in 0.27.1)

- `traced_files` / `cache_dir` / `local_cache_dir`: in `CompilationConfig` ignored_factors (`compilation/config.py:792-800`)
- `num_gpu_blocks` / `num_gpu_blocks_override`: in `CacheConfig` ignored_factors
- `cudagraph_mode`: byte-identical CUDAGraphMode traces in both generations' draft AOT pickles (both `PIECEWISE`); the resolve-time downgrade warning fires **after** each draft compile in both startups
- `adjust_cudagraph_sizes_for_spec_decode`: write-back happens at `resolve()`, outside the window
- Engine-phase speculative-config mutation: `SpeculativeConfig.compute_hash` for MTP is constant `[False]`; `update_arch_*` all in `__post_init__` (construction time, identical both generations)
- `CudaGraphManager` internals (`cudagraph_utils.py:122`): own attributes, no config write points
- "0.29 caches the hash" hypothesis: 0.29's `backends.py` computes `config_hash` fresh, code isomorphic to 0.27.1 — immunity is behavioral, not a caching change

## Cross-version control (0.29 immune)

- Deployment B (0.29 dev build `g38537331d`): **9/9** compile-era startups have `eagle_head config_hash == backbone config_hash` (json forensics, same method).
- Deployment A's 0.29 build: two generations (2026-09-23, 2026-09-24 windows), likewise `backbone == draft config_hash`.
- ⇒ On 0.29 the in-window mutation either no longer happens or no longer feeds hash factors. **0.27.1 affected; 0.29 (dev) appears immune.**

> **Note — candidate explanations for the immunity (testable).** (a) 0.29's `compute_hash` factor set changed, so whatever mutates in the window no longer feeds any hash factor; (b) 0.29's warmup path no longer mutates `VllmConfig` in place; (c) both. One measured datum supports (a): the recorded `cache_key_factors` env-key set grew from **231 keys (0.27.1) to 238 (0.29)** across our two deployments — 26 added feature-flag knobs (new decoder kernels, data/context parallelism, XPU and CPU-offload switches, hardware-agnostic keys, etc.) and 19 removed legacy keys. Pinning the immunity to (a), (b), or (c) requires the field-diff instrumentation outlined below.

## Impact

- The draft compile cache is effectively **startup-history-dependent**: identical configs produce different cache identities depending on whether the main model compiles. Warm-start fleets see surprise recompiles (~196 s per flip; 17 same-signature restarts in one incident window here).
- More generally: **any in-place mutation of `VllmConfig` between the first and last compile of a single startup silently changes derived cache keys** — a reproducibility hazard for torch.compile caching beyond speculative decoding.

## Isolating the field (planned)

Static analysis is exhausted (12+ write points audited). The only leak-free method is instrumenting a real 0.27.1 engine: monkeypatch `VllmConfig.compute_hash` and dump every sub-config's `get_hash_factors()` at backbone vs eagle `__call__`, then field-diff. We plan to run this and will comment with the exact field(s).

> **Note.** Offline worker-derive attempts (calling `VllmConfig.compute_hash` from a separate probe process) produce a `config_hash` different from the in-engine value; all forensic claims in this issue therefore rely exclusively on the on-disk `cache_key_factors.json` snapshots as the source of record.

### sudhirpol522 · 2026-09-25

I think I've found the mutated field: the enabled_custom_ops / disabled_custom_ops counters on CompilationConfig.

Mechanism in v0.27.1:

They're hashed. Neither counter is in CompilationConfig.compute_hash()'s ignored_factors. Counter is normalized as a Mapping, so the per-op counts end up in config_hash.
They move on full-compile startups only. On a full compile, the backbone's VllmBackend.__call__ runs configure_post_pass(). The fusion-pass matchers then instantiate CustomOps (e.g. MatcherQuantFP8 → QuantFP8), and CustomOp.dispatch_forward() bumps the counters. When the backbone is AOT-loaded instead (the default since torch ≥ 2.10), that path never runs.
The draft sees two states. The EAGLE/MTP head then compiles against the same shared VllmConfig, so it hashes one of two counter states. That would give exactly the two alternating values you saw (06b5820a50 / b398c1fc03).

Why 0.29 looks immune: #53378 (merged for Elastic EP) added both counters to ignored_factors. It's in v0.29.0 but not v0.28.0.

If you still have the forensic snapshots: comparing compilation_config.enabled_custom_ops at the backbone and eagle compile points should confirm this directly.

Reproduced on 1×A100, v0.27.1 vs v0.29.0.

**Cause:** in v0.27.1, `CompilationConfig.enabled_custom_ops`/`disabled_custom_ops` are hashed. On a full-compile startup the backbone's fusion passes create CustomOps and bump these counters; when the backbone is AOT-loaded they don't. The draft hashes the same `VllmConfig`, so its cache key depends on startup history.

**Repro** (Qwen3-8B + EAGLE-3, `custom_ops=["+rms_norm"]`, 3 startups):
- 0.27.1: eagle_head hash `c60c5f85f2` cold → `2191053773` warm → draft recompiles
- 0.29.0: eagle_head == backbone (`6ae35f447c`), nothing recompiles

**Fix:** already in v0.29.0 via #53378. I'll open a PR adding regression tests (fail on 0.27.1, pass on 0.29.0). This can be closed as fixed in 0.29.0.
