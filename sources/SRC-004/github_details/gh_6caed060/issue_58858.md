# [Issue #58858] [Question][ROCm] GLM-5.3-Flash kpool indexer: does the 640-token block table reach 32-pool pages on gfx942/gfx950 too?

source: https://github.com/vllm-project/vllm/issues/58858
state: open | updated: 2026-09-26T21:15:09Z
labels: rocm, glm

## 正文

We found this on hardware vLLM doesn't support (gfx1030, Radeon Pro V620), running GLM-5.3-Flash without aiter. The code path involved is shared with gfx942/gfx950, and we have no MI300/MI355 to check it on. Could someone with one confirm or rule it out?

**What we see.** `Glm5NextIndexerCache` stores pooled keys in pages of 32 pools (storage block 128 tokens at `index_kpool=4`). The hybrid KDA page rule makes the attention block 640. On ROCm the sparse-MLA and indexer backends accept `MultipleOf(16)` (`get_supported_kernel_block_sizes`), so `select_common_block_size` keeps kernel block 640. The indexer metadata builder only converts the table when the storage block is a multiple of the kernel block (`vllm/v1/attention/backends/mla/indexer.py`, prefill and decode branches; unchanged on main):

```python
if (
    kernel_block_size is not None
    and self.kv_cache_spec.block_size != kernel_block_size
    and self.kv_cache_spec.block_size % kernel_block_size == 0
):
    factor = self.kv_cache_spec.block_size // kernel_block_size
    indexer_block_table = (block_table[:, ::factor] // factor).contiguous()
```

128 % 640 ≠ 0, so the 640-token table goes to `get_compressed_slot_mapping` (the kpool writer) and to `cp_gather_indexer_k_quant_cache_triton` as if each entry named one 32-pool page. With per-chunk block allocation:
- pools written before their block exists land in padding;
- positions past the allocated blocks alias block 0;
- positions past the 52-column table (at `max_model_len` 32768) are masked by the gather.

On NVIDIA the kernel block is 64, so the `// factor` branch applies. As far as we can tell nothing here is aiter-specific: the kpool path uses `forward_cuda` on ROCm whether aiter is on or off.

**Reproducer.** One GPU, stock vLLM only, no model: [`repro_rocm_kpool_table.py`](https://github.com/Omnicef/vllm/blob/glm53-v030/tests/local/repro_rocm_kpool_table.py). It writes a 9,432-token prompt in the served prefill chunks with the real ROCm kpool writer and slot mapping, gathers it back with the real gather, and compares against the writer's own output. The two arms are the table as the builder produces it and a page-granular table (block `b` → pages `5b … 5b+4`). On gfx1030, identical over two runs:

```
table as the builder produces it  : ooo000000000000xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxmmmmmmmmmmmmmmmmmmmmmm  (3/74 pages correct)
page-granular table               : oooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooooo  (74/74 pages correct)
```

(`o` correct, `0` all-zero, `x` wrong keys, `m` masked.) Above `index_topk`, where the indexer actually selects, this breaks long-context retrieval: a two-fact needle at ~9k tokens failed for us until the table was expanded. If it reproduces on MI300, the fix we use expands each kernel-block id into its storage pages when the kernel block is a multiple of the storage block (about 20 lines in the builder, happy to send).

**Secondary note (tile order).** With aiter off (`VLLM_ROCM_USE_AITER` unset), the decode logits fall back to `fp8_paged_mqa_logits_torch`. It reads each page token-major, while two ROCm writers store values in 16×16 tiles when `block_size > 1`: `indexer_k_quant_and_cache_triton` and the GLM-5.3 kpool writer. DeepSeek-V4's C4A compressor (`compress_norm_rope_store_triton`) writes token-major, so its pages are unaffected. See the correction on #51555 for numbers. aiter's reader passes `Preshuffle=block_size > 1` and isn't affected.
