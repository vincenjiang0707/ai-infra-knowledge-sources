## Bug: Mamba-2 Triton ops produce `cudaErrorIllegalInstruction` in async mode on SM121

### Environment
- **GPU:** NVIDIA GB10 (SM121) — DGX Spark
- **Driver:** 580.126.09
- **CUDA:** 13.0 (forward compat 13.1)
- **vLLM:** 0.17.2rc1.dev7+g9c7cab5eb (eugr/spark-vllm-docker prebuilt wheels, March 17 2026)
- **PyTorch:** 2.10.0a0+a36e1d3 (NGC 26.01)
- **Triton:** 3.6.0
- **Model:** `nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-NVFP4` (NemotronHForCausalLM, hybrid Mamba-2 + Transformer + MoE)
- **Platform:** aarch64 (Grace CPU)

### Description

NemotronH models that use Mamba-2 layers crash with `CUDA error: an illegal instruction was encountered` during inference on SM121 GPUs. The crash originates in vLLM's **Triton-based** Mamba ops (not the `causal-conv1d` / `mamba-ssm` packages, which are not used by vLLM).

Setting `CUDA_LAUNCH_BLOCKING=1` makes the model fully stable but **degrades throughput from ~14 tok/s (expected) to ~8.8 tok/s** (~37% penalty) and limits GPU utilization to ~60%.

### Crash location

The error surfaces at `mamba_mixer2.py:127` in `forward_native`:
```
x_grouped = x_grouped * torch.rsqrt(variance + self.variance_epsilon)
```
But with `CUDA_LAUNCH_BLOCKING=1` we confirmed this is an **async error from a preceding Triton kernel** — the actual crash is in one of:
- `vllm/model_executor/layers/mamba/ops/causal_conv1d.py` (`_causal_conv1d_fwd_kernel`)
- `vllm/model_executor/layers/mamba/ops/ssd_chunk_scan.py` (`_chunk_scan_fwd`)
- `vllm/model_executor/layers/mamba/ops/ssd_chunk_state.py` (`_chunk_cumsum_fwd_kernel` / `_chunk_state_fwd_kernel`)
- `vllm/model_executor/layers/mamba/ops/ssd_state_passing.py`

### Call chain
```
NemotronHForCausalLM.forward
  → NemotronHDecoderLayer.forward (Mamba layer)
    → MambaMixer2.forward
      → torch.ops.vllm.mamba_mixer2
        → conv_ssm_forward  (Triton kernels: causal_conv1d_fn, mamba_chunk_scan_combined_varlen, selective_state_update)
      → self.norm(ssm_output, gate)  ← async error surfaces here
```

### Key findings

1. **Individual Triton SSM kernels work in isolation** — `_chunk_cumsum_fwd` passes with correct tensor shapes
2. **Basic Triton JIT kernels work on SM121** — simple `@triton.jit` pow/mean kernels run fine
3. **The crash only happens in async mode** — `CUDA_LAUNCH_BLOCKING=1` makes everything stable
4. **Targeted `torch.cuda.synchronize()` after `conv_ssm_forward` does NOT fix it** — the issue is at the CUDA driver dispatch level, not Python-level synchronization
5. **`CUDA_DEVICE_MAX_CONNECTIONS=1` causes deadlock** at engine startup (profiling phase)
6. **CUDA graphs are incompatible** — `--enforce-eager` is required alongside `CUDA_LAUNCH_BLOCKING=1` because the sync patch inside `conv_ssm_forward` breaks graph capture
7. **The native `causal-conv1d` 1.6.1 package compiles and works for SM121** — but vLLM doesn't use it (uses its own Triton reimplementation instead)
8. **llama.cpp / Ollama achieve ~14 tok/s on the same hardware** with their own CUDA kernels — the issue is specific to vLLM's Triton Mamba ops

### Workaround

```yaml
env:
  CUDA_LAUNCH_BLOCKING: "1"
command: |
  vllm serve nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-NVFP4 \
    --enforce-eager \
    --mamba-ssm-cache-dtype float32 \
    --attention-backend TRITON_ATTN \
    --kv-cache-dtype fp8 \
    ...
```

Result: stable at **8.8 tok/s** (vs ~14 tok/s expected).

### Suggested fix directions

1. **Preferred:** Investigate the Triton code generation for SM121 async execution — there may be a missing memory barrier or wrong PTX target in the JIT output for the Mamba kernels
2. **Alternative:** Allow vLLM to optionally use the native `causal-conv1d` / `mamba-ssm` CUDA kernels (which work on SM121) instead of the Triton fallback, similar to how flash-attn can be swapped for different backends
3. **Minimal:** Add per-layer `torch.cuda.synchronize()` only around Mamba ops when running on SM12x, instead of requiring global `CUDA_LAUNCH_BLOCKING=1`

| Config | Decode tok/s | GPU util |
|--------|-------------|----------|
| `CUDA_LAUNCH_BLOCKING=1` + `--enforce-eager` | 8.8 | ~60% |
| Ollama (same model, same hardware) | ~14 | ~90%+ |
| Expected (no workaround) | ~14-17 | ~90%+ |

## Additional bisection data: FLA GDN linear_attention subgraph, batch size >= 8

We've been hitting this on a DGX Spark (GB10, SM121) with **Qwen3.5-122B-A10B-NVFP4** (hybrid MoE + Mamba/GDN architecture) and narrowed it down further.

### Setup
- vLLM built from source (main branch, ~Mar 24 2026) with CUTLASS v4.4.2 + FlashInfer SM121 patches
- MTP speculative decoding (n=1), NVFP4 quantization, FLASH_ATTN backend
- Model uses `Qwen3NextGatedDeltaNet` layers (`linear_attention` type) which call FLA Triton ops

### Bisection results

| CUDA graph config | Stable? |
|---|---|
| `cudagraph_mode: "none"` (eager) | ✅ Stable at 4+ concurrent reqs for 30+ min |
| `cudagraph_capture_sizes: [2]` | ✅ Stable |
| `cudagraph_capture_sizes: [2, 4]` | ✅ Stable |
| `cudagraph_capture_sizes: [2, 4, 8]` | ❌ Crashes within ~2 min with 3-4 concurrent reqs |
| Default `[2, 4, 8, 16]` | ❌ Crashes within ~2 min |

Both crashes had `total_num_scheduled_tokens=8` (4 reqs × 2 tokens with MTP, or 3 reqs × 2 tokens + padding to size-8 graph).

### Piecewise graph capture narrows to specific subgraph

With `cudagraph_mode: "piecewise"` and `cudagraph_capture_sizes: [8]`, the crash points to:

```
File "<eval_with_key>.103", line 356, in forward
    submod_12 = self.submod_12(...)
    # args reference: layers_modules_5_modules_linear_attn_*
File "vllm/compilation/cuda_graph.py", line 355, in __call__
    entry.cudagraph.replay()
torch.AcceleratorError: CUDA error: an illegal instruction was encountered
```

**`submod_12` is the piecewise subgraph for layer 5's `linear_attn` (GDN) module** — specifically the `Qwen3NextGatedDeltaNet` which calls:
- `causal_conv1d_update` (Triton, from `vllm.model_executor.layers.mamba.ops.causal_conv1d`)
- `fused_recurrent_gated_delta_rule_packed_decode` (Triton, from `vllm.model_executor.layers.fla.ops.fused_recurrent`)

### Key observation

The kernels work fine eagerly at the same batch size — the illegal instruction only manifests during **CUDA graph replay** at batch size ≥ 8. This suggests the Triton JIT-compiled kernel uses a codepath or instruction during graph capture that doesn't hold at replay time, rather than the kernel itself being incompatible with SM121.

### Current workaround

`cudagraph_capture_sizes: [2, 4]` with piecewise mode — avoids the problematic batch size while keeping CUDA graph acceleration for single/dual request decode. No need for `CUDA_LAUNCH_BLOCKING=1` or `--enforce-eager`. Throughput is ~47 tok/s with MTP on Qwen3.5-122B NVFP4 on a single DGX Spark.

### cipherfoxie · 2026-06-12

That non-reproduction is itself a strong signal. Put the two halves together: earlier, rolling *back* appeared to restore the fast path; now, reinstalling the *same* 6.17 / 580.159.03 stack also produces a healthy system. The common factor in both "fixes" is not the version, it is the act of (re)installing. That points at whatever an install resets rather than the driver or kernel bits themselves, with the CUDA JIT/PTX cache as the prime suspect: SM121 has no fat binaries in most wheels, so a lot of kernels are JIT-compiled and cached, and a cache populated under one driver can be picked up under another.

Two cheap tests that would falsify or confirm this without another driver swap:

1. On a currently healthy system, clear the compute cache (`rm -rf ~/.nv/ComputeCache`, or run once with `CUDA_CACHE_DISABLE=1`) and re-run the battery. If it stays green, the cache was innocent and the hypothesis dies.
2. If you still have access to a box in the bad state, save `~/.nv/ComputeCache` before any reinstall, restore it afterwards, and see if the regression comes back with it.

Either result would be worth more than another full driver/kernel cross-matrix, because it tests the one variable the reinstall path actually changes. Agreed on not overclaiming the 580.159.03-on-6.11 split until someone runs the isolated combination; and Xatter's synthetic-green-but-prod-crash datapoint fits the same picture, since a production workload walks a much wider set of kernel shapes than a fixed battery, and each new shape is a fresh JIT compile.

Adding to this thread from a configuration it does not yet cover: every report here is TP=1 on a

### Environment

- **2× NVIDIA DGX Spark (GB10, `sm_121`)**, aarch64, TP=2 + EP over RoCE, one rank per node

- `MarlinNvFp4LinearKernel` / MARLIN NvFp4 MoE backend (same as #54331 and #52225)

### The failure

Signature matches this thread. At the fatal step the scheduler dump showed a low-KV, low-concurrency
decode — not saturation of the KV pool:

```
num_running_reqs=3, num_waiting_reqs=0, kv_cache_usage=0.1016

num_scheduled_tokens=4 per request, num_spec_tokens_to_schedule=3

        faulted @ 0x187bf_2ef5c000, FAULT_PDE ACCESS_TYPE_VIRT_READ

PID→container map every 15 s, so the Xid PIDs resolve to a specific service. That is what let us
establish which process faulted. A co-resident model on the same MPS context died seconds later with

collateral damage from the poisoned shared context. Without the pre-crash PID map we would have
attributed this to the wrong service.

### Two refuted hypotheses

Both were live candidates in the adjacent threads. Reporting them as negatives so nobody re-spends
the time:

**1. #55506 (mamba spec-decode block tables indexed by request slot) does not fix this.** We applied
a semantic backport of `c89ebdc40` onto our build. It qualified cleanly — three concurrent
64,930-token prompts exact cold/warm, 95.76 % warm prefix hit, a 10-minute co-resident soak with

PP1/TP2/GB10.

**2. #50729 (overlapping mamba state copy race) is already present and does not prevent it.** This
was proposed in #53726 as the best fit for the write-heavy Xid distribution. Our build is 812 commits
after that merge, so the fix is in — and the fault still occurs. For anyone planning the soak matrix
suggested there: on this hardware that arm is already answered, and negative.

**Root cause (evidence).** The FlashInfer SM120 CUTLASS grouped GEMMs used by the NVFP4 MoE are launched with PDL enabled: `device_support_pdl()` is `major >= 9`. In FlashInfer 0.6.4 they contain no `griddepcontrol.wait`, so a GEMM can start before its producer kernel has finished.

| FlashInfer | SM120 grouped-GEMM kernels with `griddepcontrol.wait` |
|---|---|
| 0.6.4 | 0 / 40 |
| 0.6.4 + `-DCUTLASS_ENABLE_GDC_FOR_SM100=1` | 0 / 40 (also still crashed, 30 s) |
| 0.6.6 | 0 / 40 |
| 0.6.8.post1 | 40 / 40 |
| 0.7.0 | 88 / 88 |

Two upstream FlashInfer changes are involved, and the flag alone is not enough:
- https://github.com/flashinfer-ai/flashinfer/pull/2798 (CUTLASS 4.2.1 → 4.4.2) adds the `wait_on_dependent_grids()` call in `sm90_gemm_array_tma_warpspecialized_cooperative.hpp`. That is the kernel behind `KernelPtrArrayTmaWarpSpecializedCooperativeBlockScaledSm120`.
- https://github.com/flashinfer-ai/flashinfer/pull/2913 adds `-DCUTLASS_ENABLE_GDC_FOR_SM100=1` to the SM120 fused-MoE JIT. Without it, that call compiles to nothing. Its description gives the same mechanism.
