### 🐛 Describe the bug

Three interacting gates currently make DeepSeek-V4 (and presumably any model using the DSA sparse indexer with `fp8_ds_mla`) impossible to run on ROCm GPUs other than MI3xx — while torch reference fallbacks for exactly this situation already exist in-tree, are wired with correct arguments, and work when made reachable (verified on a 2× gfx1151 cluster, now serving).

**Gate 1 — the indexer requires AITER.** During the profiling forward pass, `sparse_attn_indexer.py::forward_hip` raises:

```
Sparse attention indexer ROCm path is only supported on AITER.
Please enable aiter with VLLM_ROCM_USE_AITER=1
```

**Gate 2 — the advice in that error cannot work.** `VLLM_ROCM_USE_AITER=1` is silently ignored on non-MI3xx because `vllm/_aiter_ops.py` hard-gates on platform:

```python
def is_aiter_found_and_supported() -> bool:
    ...
    if current_platform.is_rocm() and IS_AITER_FOUND:
        from vllm.platforms.rocm import on_mi3xx
        return on_mi3xx()
    return False
```

So the user is sent in a loop: the error demands an env var that the platform gate then discards, even with AITER installed and importable.

**Gate 3 — the in-tree fallbacks are unreachable.** `vllm/v1/attention/ops/rocm_aiter_mla_sparse.py` contains `fp8_paged_mqa_logits_torch` and `fp8_mqa_logits_torch`, and both dispatchers (`rocm_fp8_paged_mqa_logits`, `rocm_fp8_mqa_logits`) already call them in their `else` branches when the AITER Triton module is unavailable. But reaching the dispatchers requires AITER enabled (gates 1–2), and with AITER enabled the module lookup always succeeds, so the AITER Triton kernels are always selected.

On RDNA3/3.5 those AITER Triton kernels cannot compile regardless (no fp8 WMMA), so whitelisting the arch in gate 2 just moves the failure into Triton:

```
triton.compiler.errors.CompilationError
  o = tl.dot(q, k.T)
      ^
Unsupported lhs dtype fp8e4nv
(aiter/ops/triton/attention/pa_mqa_logits.py, deepgemm_fp8_paged_mqa_logits_stage1)
```

i.e. every path on this hardware terminates in an error one step before working fallback code.

### Reproduction

1. 2× gfx1151, DeepSeek-V4-Flash, serve command in the environment section → gate 1 error.
2. Add `VLLM_ROCM_USE_AITER=1` → identical error (gate 2).
3. Whitelist gfx1151 in `is_aiter_found_and_supported()` → Triton `fp8e4nv` CompilationError in the AITER paged-MQA kernel (gate 3).

### Tested fix (cluster is serving with this)

**a) `vllm/_aiter_ops.py`** — accept gfx1151 as AITER-capable:

```diff
-        from vllm.platforms.rocm import on_mi3xx
-
-        return on_mi3xx()
+        from vllm.platforms.rocm import on_mi3xx, on_gfx1151
+
+        return on_mi3xx() or on_gfx1151()
```

**b) `vllm/v1/attention/ops/rocm_aiter_mla_sparse.py`** — skip the AITER Triton module lookup on gfx1151 so the existing torch fallbacks run (same change in both dispatchers):

```diff
-    if rocm_aiter_ops.is_enabled():
+    from vllm.platforms.rocm import on_gfx1151
+
+    # gfx1151: Triton cannot compile tl.dot with fp8e4nv inputs; skip the
+    # AITER Triton kernels so the torch reference fallback below is used.
+    if rocm_aiter_ops.is_enabled() and not on_gfx1151():
         aiter_paged_mqa_logits_module = paged_mqa_logits_module()
```

```diff
+    from vllm.platforms.rocm import on_gfx1151
+
     aiter_mqa_logits_module = None
-    if rocm_aiter_ops.is_enabled():
+    if rocm_aiter_ops.is_enabled() and not on_gfx1151():
         aiter_mqa_logits_module = mqa_logits_module()
```

The prefill dispatcher (`rocm_fp8_mqa_logits`) needs the same gate: its AITER kernel performs the same fp8 `tl.dot` and fails identically on the first real prefill if only the paged path is patched.

A cleaner resolution than piling onto the arch whitelist is probably per-kernel capability gating: dispatchers select the AITER Triton kernel only on archs where it is known to compile (mi3xx / gfx942 / gfx950 — the gfx942 special case already exists in `rocm_fp8_mqa_logits`), else torch fallback — and gate 1's error message should not recommend an env var that gate 2 ignores. Happy to turn this into a PR if maintainers agree on the preferred shape.

Note: the sparse-attention Triton kernels in the same file are unaffected — they dequantize fp8→bf16 in-kernel before `tl.dot` and compile fine on gfx1151.

### Secondary finding: torch fallback vs FULL cudagraph capture

Once reachable, `fp8_paged_mqa_logits_torch` is not capture-safe (`.item()` / data-dependent host loops), but `@eager_break_during_capture` intentionally runs ops inline when `forward_context.cudagraph_runtime_mode == CUDAGraphMode.FULL` (`compilation/breakable_cudagraph.py`), so FULL capture crashes:

```
File ".../rocm_aiter_mla_sparse.py", line 290, in fp8_paged_mqa_logits_torch
    seq_len = int(context_lens[i].item())
torch.AcceleratorError: CUDA error: operation not permitted when stream is capturing
(hipErrorStreamCaptureUnsupported)
```

If the fallbacks become officially reachable, the op should be treated as non-capturable when the torch path is active (or cudagraph disabled for it). We run with `--enforce-eager` (also required on this cluster: piecewise capture deadlocked in RCCL NET/Socket collectives; related to #32180).
