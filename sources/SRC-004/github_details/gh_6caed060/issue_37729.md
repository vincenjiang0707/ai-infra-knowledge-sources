## Describe the bug

  The V1 engine core silently deadlocks under concurrent load using default configuration. The API server remains healthy (/health returns 200, /metrics responds), but zero tokens are generated. Requests stay in "running" state indefinitely and
   the engine never recovers without a pod restart.

  vLLM serve command:
```
  vllm serve "$MODEL_DIR" \
      --tokenizer Qwen/Qwen3.5-4B \
      --dtype bfloat16 \
      --gpu-memory-utilization 0.95 \
      --max-num-batched-tokens 16384 \
      --max-model-len 16384 \
      --max-num-seqs 128 \
      --quantization fp8 \
      --trust-remote-code \
      --enable-prefix-caching \
      --async-scheduling \
      --default-chat-template-kwargs '{"enable_thinking": false}'
```

  How to reproduce:

  1. Deploy vLLM with the configuration above
  2. Send concurrent requests (8-64 concurrency) — works fine initially
  3. Under sustained load or after a brief spike, the engine freezes
  4. No specific error triggers it — no OOM, no CUDA error, no validation error

  Engine log sequence showing the deadlock:
```
  13:57:45  Avg prompt throughput: 2598.6 tokens/s, Avg generation throughput: 1684.2 tokens/s, Running: 2 reqs, Waiting: 0 reqs, GPU KV cache usage: 0.3%, Prefix cache hit rate: 96.9%
  13:57:55  Avg prompt throughput: 83.6 tokens/s, Avg generation throughput: 1.8 tokens/s, Running: 11 reqs, Waiting: 0 reqs, GPU KV cache usage: 1.3%, Prefix cache hit rate: 96.9%
  13:58:05  Avg prompt throughput: 0.0 tokens/s, Avg generation throughput: 0.0 tokens/s, Running: 11 reqs, Waiting: 0 reqs, GPU KV cache usage: 1.3%, Prefix cache hit rate: 96.9%
```
  After 13:58:05, throughput stays at 0.0 permanently. Running count stays at 11. KV cache stays at 1.3%. The engine never recovers.

### Key observations:

  - Not resource exhaustion: Only 11/128 request slots used, 1.3% KV cache
  - API server alive: /health returns 200, /metrics responds
  - Engine core frozen: Zero tokens generated, forward pass never executes
  - Affects arbitrary request counts: Seen with 11, 124, and other counts
  - Does not self-recover: Requires pod restart
  - --request-timeout does not help: Engine core is frozen, can't enforce timeouts

  Investigation — deadlock tied to CUDA graph code paths:

  Systematic testing to isolate the trigger:
```
  ┌──────────────────────────────────┬────────────────────────────────────┐
  │              Config              │               Result               │
  ├──────────────────────────────────┼────────────────────────────────────┤
  │ Default V1 + async-scheduling    │ DEADLOCK                           │
  ├──────────────────────────────────┼────────────────────────────────────┤
  │ Default V1 + no async-scheduling │ DEADLOCK                           │
  ├──────────────────────────────────┼────────────────────────────────────┤
  │ Default V1 + --enforce-eager     │ Didn't run enough but ~8x slower (not viable) │
  └──────────────────────────────────┴────────────────────────────────────┘
```

  Incident 1 (nightly build): During a production spike, autoscaler scaled from 6→20→6 replicas. Two surviving replicas entered deadlock with 123-124 running requests each, stayed frozen 4+ hours until manual restart.

  Incident 2 (v0.17.1 stable): Same deadlock reproduced within minutes of a load test. Single replica, low concurrency (8→16 ramp). Froze at 11 running requests. No autoscaling involved.

  Current workaround: --enforce-eager prevents the deadlock but with ~8x throughput regression, making it unviable for production. Restarting affected replicas is the only practical mitigation.

**Confirming this deadlock on a different GPU architecture and model.**

**Setup:**
- vLLM v0.18.1 (`vllm/vllm-openai:v0.18.1-cu130`)
- Model: MiniMax-M2.5-NVFP4 (~256B param MoE, ~46B active, ~200K vocab)
- GPUs: 2× RTX PRO 6000 (Blackwell SM120, 96GB, PCIe — no NVLink)
- TP=2, EP=1 (pplx all2all), FlashInfer attention, FP8 KV cache
- `--enable-prefix-caching --enable-chunked-prefill --async-scheduling`
- `COMPILATION_CONFIG='{"mode": "VLLM_COMPILE", "cudagraph_mode": "FULL_DECODE_ONLY"}'`

**Symptoms — identical to yours:**
- Engine deadlocks under concurrent load (~33 requests in our case)
- GPUs at 100% utilization, 0.0 tok/s throughput
- `/health` returns 200, `/metrics` responds, but zero tokens generated
- Never self-recovers; requires pod restart

**What we tested (7 configs):**

| Config Change | Result |
|---|---|
| Default v0.18.1 (EP=1, async-scheduling, CUDA graphs FULL_DECODE_ONLY) | **Deadlock** at ~33 concurrent reqs |
| Disabled `--performance-mode throughput` | **Deadlock** |
| Disabled `VLLM_SLEEP_WHEN_IDLE` | **Deadlock** |
| Increased CPU cores (8→16, aligned OMP/compile threads) | **Deadlock** |
| `cudagraph_mode: NONE` | **Stable** — 64 running + 32 waiting, ~1500 tok/s batch |
| Disabled Expert Parallel (EP=0, TP-only) | No output (model too large for TP-only) |
| CUDA graphs on + `--async-scheduling` off | Not tested (abandoned after other results) |

**Key finding:** `cudagraph_mode: NONE` completely resolves the deadlock (consistent with your `--enforce-eager` finding), but single-stream generation throughput drops ~55% (90 → 40 tok/s), making it unviable for production.

**Important data point for narrowing the cause:** Our model (MiniMax-M2.5) is a Mixture-of-Experts architecture — it does **not** use GDN. Given your latest finding about `--gdn-prefill-kernel`, the fact that we see the same deadlock without any GDN involvement suggests the root cause may not be limited to the GDN/FlashInfer prefill kernel path. It could be a more general issue in the CUDA graph capture/replay code that manifests through different kernels depending on the model architecture.

**Baseline comparison:** vLLM v0.16.0 with an identical CUDA graph config (`FULL_DECODE_ONLY`) on the same hardware and model is completely stable, confirming the regression is in v0.17–v0.18.

Currently staying on v0.16.0 as a workaround. Happy to test patches or diagnostic builds if that would help narrow this down.

This is the part I most want to flag, because every dashboard we had showed the wedged engine as healthy. Over 4.7 days of 10-second telemetry we caught 4 deadlocks. In every one:

- `nvidia-smi` **GPU utilisation stayed at 94–96%** — identical to healthy generation. It counts a resident kernel, not forward progress, so a spinning deadlocked kernel reads as fully busy.
- **GPU power collapsed to idle** while utilisation stayed pegged, and **temperature fell** (no actual compute).

| state | requests running | KV cache | GPU util | GPU power | GPU temp |
|---|---|---|---|---|---|
| healthy generation (avg) | — | — | 95% | **45 W** (16–93 W) | steady |
| deadlock (4 events) | 8–64 | 12–27% | 94–96% | **17–27 W** | falling |

So on GB10, **`generation_tokens_total` frozen while `num_requests_running > 0` AND GPU power at idle while utilisation is pegged** is an unambiguous detector. Utilisation alone is not — it's identical in both states. (The same high-util / low-power spin signature appears in #46097, "~15W", and #40980, so this may generalise beyond this platform.)

KV cache was 12–27% at every onset — well short of full — which argues against memory pressure and toward a scheduler/CUDA-graph deadlock.

### 2. Reproduction — request preemption/cancellation looks like a contributing factor

We were able to reproduce the deadlock, and in our runs one factor stood out that I haven't seen mentioned in the thread: **request preemption from client cancellations seemed to matter more than raw load.** Offered as an observation, not a claim that it's the only path — the original report reproduces from concurrent load alone, so there may be more than one route in (or a hardware/backend difference).

- **Sustained concurrent load, on its own, did not wedge it for us.** Two 17-minute runs at 64 concurrent (`max-num-seqs` ceiling) — large prefills interleaved with long decode — stayed healthy. `generation_tokens_total` climbed smoothly; power swung 41–101 W the whole time. Every token-freeze in those runs was just a long prefill (frozen counter but **normal power**, 46–90 W).
- **Adding cancellation churn on top of that load reproduced the deadlock within minutes.** Many workers opening *streaming* completions with large (~40k-token) prompts and abruptly closing the socket (`SO_LINGER 0` → RST) ~1 s in — forcing continuous sequence preemption while prefills are admitted — produced the deadlock:

  ```
  num_requests_running = 52 (frozen)   generation_tokens_total = 241532 (frozen >90s)
  GPU util = 94%   GPU power = 21 W   GPU temp 67→59 °C   KV cache ≈ 14%
  ```

- **It's intermittent / a race.** The first compounded run wedged in a few minutes; a second, heavier ~30-minute run did not reproduce it. That variance suggests an abort has to land in a narrow prefill-admission window rather than a deterministic threshold — which may be why it shows up roughly once every 1–2 days under normal traffic rather than on every saturated batch.

1. vLLM serving normally with the flags above.
2. Background: ~16 long decode streams (2–3k output tokens) + repeated waves of ~24 concurrent 8k-token-prompt requests. (Not sufficient alone.)
3. Compound with ~28 workers each opening a **streaming** chat completion with a ~40k-token prompt and RST-closing the socket ~1 s after first bytes, in a tight loop.

Single machine, n=4 deadlocks; the specific 30 W power threshold is fitted to this GPU/model/config, not a universal constant (others should read their own healthy-vs-wedged power bands). The preemption finding is "reliably triggered it for us and saturation alone did not," not proof of the only path — the original report reproduces from load alone, so there may be more than one route in, or a hardware/backend difference.

    return sum(isinstance(value, float) for value in results.values())

### anencore94 · 2026-07-20

## Correction + sharper trigger condition: it is tile misalignment (`seq_len % 128 != 0`), not raggedness

Follow-up to my earlier comment. Two things there need correcting, and the
replacement condition is precise enough to check against your own traffic.

### 1. What I got wrong

I described the hanging batches as "ragged" (uneven row lengths). That is not
the discriminator. A counterexample from our B300 rig: a batch of **15 rows of
415/416 tokens** — essentially uniform — hangs, while genuinely uneven batches
whose rows are all multiples of 128 do not.

I then guessed the boundary was the kernel's chunk size `b_t = 64`
(`gdn_kernels/blackwell/gated_delta_net_chunked.py`). That is also wrong, and
this one matters because reading the source makes 64 look obvious:
**`[1984] * 5` hangs even though `1984 = 31 * 64` is a clean multiple of 64.**
`1984 % 128 == 64`. The empirical boundary is 128, not 64.

### 2. The trigger condition (measured)

On flashinfer <= 0.6.13, a Blackwell GDN prefill launch can hang forever when
**all** of these hold:

- `initial_state is not None` (a zeros tensor is enough — it is the code path,
  not the values)
- the batch has **>= 5 rows**
- **at least one row has `seq_len % 128 != 0`**

Both of the last two terms are necessary — each one alone is safe. Measured on
the same rig, same build (flashinfer 0.6.13), 50 launches per shape:

| shape | rows | rows with `%128 != 0` | result |
|---|---|---|---|
| `[1984] * 4` | 4 | 4 | pass (also ~35k such launches across our engine runs, no hang) |
| `[1024] * 7` | 7 | 0 | **pass** |
| `[1984] * 5` | 5 | 5 | **hang** |
| `[1984, 1984, 1984, 1984, 254]` | 5 | 5 | **hang** |
| `[415] * 9 + [416] * 6` | 15 | 15 | **hang** (within ~2 launches) |
| `[5994, 643, 642, 642, 642]` (the flashinfer-ai/flashinfer#3565 shape) | 5 | 5 | **hang** |

The `[1024] * 7` row is the useful one: it has *more* rows than the hanging
cases and still passes, so "too many rows" is not the explanation.

Hang probability scales with how many rows are tile-misaligned. One misaligned
row among four aligned ones — the shape vLLM's chunked prefill naturally
produces — hangs at roughly 2e-4 per launch (2 wedges over ~10.5k such launches
in our engine logs). A batch where every row is misaligned hangs within a couple
of launches. That range explains why this looks random in production: the engine
mostly emits the low-hazard variant, so it is a when-not-if race rather than a
reproducible failure.

Zero-length rows in `cu_seqlens` are a separate, deterministic class (fixed by
flashinfer-ai/flashinfer#3536).

### 3. Version boundary, re-verified with a regression test

I wrote a parametrized regression test for these shapes (each launch batch runs
in a child process with a hard timeout, so a regressed build fails in minutes
instead of hanging CI) and ran it on the same B300, changing only the flashinfer
packages:

```
flashinfer 0.6.13:  4 failed, 1 passed   (1832 s)
flashinfer 0.6.15:  5 passed             (781 s)
```

The four failures are the four hang shapes above; the pass in both columns is
the `[1024] * 7` control. This is consistent with flashinfer-ai/flashinfer#3581 (the
`o_store_producer.tail()` removal) being the fix for this class.

For anyone reproducing: match flashinfer's own test conventions
(`int64` `cu_seqlens`, l2-normalized `k`, `use_qk_l2norm_in_kernel=True`) —
deviating from them produced misleading failures for me before I noticed.

### 4. Practical takeaway

On this cohort, use flashinfer **0.6.14**, or pin the GDN prefill backend to
Triton as a stopgap. I verified the hang shapes above on 0.6.15 because that is
what I had staged, but 0.6.14 already contains both GDN fixes (flashinfer-ai/flashinfer#3581, flashinfer-ai/flashinfer#3536) and
avoids the 0.6.15 autotuner regression reported in flashinfer-ai/flashinfer#4043 (O(n^2) host
overhead, ~2x throughput loss). 0.6.15's extra fix (flashinfer-ai/flashinfer#3973,
nvfp4 MoE hang) does not apply to dense non-MoE deployments like ours.

> **Update (2026-08-07)**: flashinfer-ai/flashinfer#4043 is fixed, but the fix commit landed
> ~17h *after* the v0.6.15 tag, so 0.6.15 itself still carries the regression
> while 0.6.16 and later contain the fix (verified by comparing the merge
> commit against each tag). vllm-project/vllm#48914 has since merged and vLLM main now pins
> 0.6.16.post3. So the version guidance is: **0.6.14 or >=0.6.16**, skip 0.6.15.
> Our hang-shape verification was run on 0.6.14/0.6.15; we have not re-run it on
> the 0.6.16 line, though both GDN fixes are of course still present there.

What is new is that you can now *check* whether your traffic is exposed:
if your prefill batches reach 5+ rows and any row length is not a multiple of
128, you are in the hazardous class — and with `max_num_batched_tokens` splitting
a fixed budget across concurrent prefills, a stub remainder row appears easily.

I'm happy to open the regression test as a PR against flashinfer if maintainers
there want it; the shapes and the child-process timeout harness are already
validated on B300.
