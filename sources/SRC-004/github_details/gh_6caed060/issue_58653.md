**Title**: `[Hybrid GDN] Explicit --block-size misaligned with mamba page makes SimpleCPU KV offload silently write-only; startup should reject or warn`

## Summary

On hybrid GDN models (Qwen3.5/Qwen3.8 family, `linear_attention` + periodic `full_attention`), enabling the SimpleCPU KV offload connector (`VLLM_USE_SIMPLE_KV_OFFLOAD=1`) together with an **explicit** `--block-size` that does not match the mamba-page alignment results in the offload connector becoming **write-only**: blocks are stored to CPU (RSS grows, write path active) but the read path never serves a single token (`external_kv_transfer` stays 0, re-prefill after forced eviction costs the same as a cold prefill). Omitting `--block-size` (letting the engine auto-compute the aligned size) makes the same setup fully functional. The failure is **silent** — no error, no warning — and looks exactly like "offload enabled" from the outside.

## Environment (two independent deployments, same wheel)

- vLLM `0.29.1rc1.dev400+g38537331d`; model Qwen3.8-27B W4A16 (AutoRound / AWQ-INT4), `Qwen3_5ForConditionalGeneration`, hybrid GDN: 48 GDN `linear_attention` + 16 `full_attention` (interval=4), mamba align, 1 MTP layer
- **Deployment A (llm-1)**: fp8 KV, MTP on, `gpu_memory_utilization=0.93`, `--kv-offloading-size 16` (GiB), mamba cache fp16
- **Deployment B (f280)**: fp8 KV, MTP on, `--kv-cache-memory 8105442816` (pool 208,005 tok), CPU offload 30 GB / 584 blocks, mamba cache fp32
- Both: `VLLM_USE_SIMPLE_KV_OFFLOAD=1`, prefix caching on, `max_model_len=131072`

> Note on version: filed against a dev build (`0.29.1rc1.dev400`) because both deployments run it in production; the same checks have **not** yet been run on a stable release. If the stable branch behaves differently we will report back.

## Symptom (deployment A, explicit `--block-size 128`)

- Startup log: `Setting attention block size to 896 tokens to ensure that attention page size is >= mamba page size` → `kv cache group sizes [896, 896, 896, 896]`
- Write path alive: connector RSS grows ~16 GiB under eviction pressure (all FA blocks)
- Read path dead: probe = T1 cold prefill of a 30k-token doc, T2 warm re-ask (local hit), force eviction with 6×35k-token filler docs, 75 s drain, T3 re-ask:
  - **T3/T1 = 1.006–1.46** (re-ask after eviction ≈ full cold prefill)
  - **Δ`prompt_tokens_by_source{external_kv_transfer}` = 0** across the T3 window
- No error/warning anywhere in logs.

## Fix-by-configuration (both deployments, read path fully functional)

Dropping the explicit flag → engine auto-computes the aligned block size:

| Deployment | Startup fingerprint | T3/T1 | Δ external_kv_transfer (T3 window) |
|---|---|---|---|
| A, `--block-size 128` | `[896×4]` | 1.006–1.46 | **0** |
| A, flag omitted | `Setting attention block size to 816` / `[816×4]` | **0.032 / 0.048** (two windows) | **+29,376** |
| B, flag omitted (fp32 mamba) | `Setting attention block size to 1584` / `[1584×4]` | **0.044** (re-run 0.0438; instrumented variant 0.1279) | **+28,512** |

Answers identical across T1/T2/T3 in all runs. The only changed variable between the broken and working rows on deployment A is the explicit `--block-size` flag (single-variable matrix over {mamba dtype, async_scheduling, cumem, block-size} — block-size was the only HIT).

## Expected behavior

When a hybrid-GDN model is configured with an explicit `--block-size` whose resulting attention page geometry is incompatible with the mamba page / offload connector granularity, vLLM should **refuse to start or at least emit a loud WARN**, instead of running silently with a write-only offload connector.

Suggested improvements (joint appendix):
1. **Startup validation**: reject or WARN when explicit `--block-size` conflicts with mamba-page alignment for hybrid models (the auto-align path `interface.py:918` already computes the correct value — the explicit-flag path appears to bypass the same protection, raising to a value (896) that satisfies the page-size inequality but breaks connector store/load granularity).
2. **Connector robustness**: SimpleCPU connector should detect the granularity mismatch and fail loudly rather than store-never-load.
3. **Observability**: expose store/load counter pairs in `/metrics` so "write-only offload" is directly visible (today only `external_kv_transfer` hits/queries tell the story indirectly).

## Notes

- Without KV offloading, the explicit `--block-size 128` is harmless: it is raised to 896 and never actually runs at 128 — inference correctness is unaffected. The bug only bites the offload read path.
- Reproduction probe and full datasets available on request (both deployments, archived JSON + logs).

*Joint report by the maintainers of two independent production deployments (anonymous), independent reproductions on an identical wheel build, 2026-09-24.*
