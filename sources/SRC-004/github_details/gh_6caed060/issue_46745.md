# [Issue #46745] [Bug]: No clamp-capable batched NVFP4 fused-MoE backend → DeepEP / wide-EP unusable for MiniMax-M3 NVFP4

state: open | updated: 2026-09-26T01:46:13Z

## 正文

### Environment

vLLM mainline with the NVFP4 MiniMax-M3 MoE path (the standard `vllm/vllm-openai:minimax-m3`
build + the NVFP4 MoE support from PR #46380), on Blackwell sm_100, NVLink-only (no InfiniBand),
with `deep_ep` and `nvshmem` available.

### What's wrong

NVFP4 MiniMax-M3 serves fine with normal expert parallelism. But the moment you turn on
**DeepEP** for wide-EP on the decode workers (e.g. `data-parallel-size: 16` +
`all2all-backend: deepep_low_latency`), it dies at startup:

```
NotImplementedError: No NvFp4 MoE backend supports the deployment configuration.
  (vllm/model_executor/layers/fused_moe/oracle/nvfp4.py, select_nvfp4_moe_backend)
```

DeepEP itself comes up fine first — you can see `Using DeepEPLLAll2AllManager` and the EP rank
map being built — so this isn't a DeepEP or NVSHMEM problem. It's that none of the NVFP4 MoE
kernels can handle DeepEP's batched layout **and** MiniMax-M3's SwiGLU clamp at the same time.

### Why it happens

MiniMax-M3's experts use SwiGLU-OAI with a clamp (`swiglu_limit`). Two requirements collide:

- **The clamp** is only implemented by one NVFP4 backend, `FLASHINFER_TRTLLM`. When
  `swiglu_limit` is set, the backend picker (`NVFP4_BACKENDS_WITH_CLAMP`) narrows the choices
  down to TRTLLM only.
- **DeepEP** needs the *batched* activation format, and the only NVFP4 backend that provides it,
  `FLASHINFER_CUTEDSL_BATCHED`, does SILU only — no SwiGLU, no clamp.

So "I need the clamp" forces TRTLLM (which is standard-layout only), and "I need DeepEP" forces
the batched kernel (which has no clamp). No single backend does both:

| backend | applies SwiGLU clamp? | supports batched (DeepEP) layout? | activations |
|---|---|---|---|
| `FLASHINFER_TRTLLM` | ✅ (the only one) | ❌ standard only | SILU, RELU2, GELU(_TANH), SWIGLUOAI, SWIGLUOAI_UNINTERLEAVE |
| `FLASHINFER_CUTEDSL_BATCHED` | ❌ | ✅ (the only one) | SILU only |
| `FLASHINFER_CUTLASS` | ❌ | ❌ | SILU, GELU_TANH, RELU2, SWIGLUOAI |

Forcing the batched backend by hand doesn't get around it either — you just hit a guard:
`ValueError: Model sets swiglu_limit=..., but the requested moe_backend does not apply the SwiGLU clamp.`

### A separate snag on NVLink-only systems

If you reach for `deepep_high_throughput` instead, it fails even earlier, while DeepEP is
setting up its buffers:

```
deep_ep/buffer.py ... RuntimeError: CUDA error 'invalid resource handle'
```

High-throughput mode expects InfiniBand RDMA between nodes. On NVLink-only multi-node systems
there's no IB, so it can't start. `deepep_low_latency` + `VLLM_DEEPEP_LOW_LATENCY_USE_MNNVL=1`
is the right transport there, and it *does* start — it just then runs into the backend gap above.

### How to tell it's activation-specific, not a clamp bug

A SiLU-activated NVFP4 MoE (`hidden_act="silu"` + clamp) works fine, because SILU is supported by
both TRTLLM (clamp, standard layout) and CUTEDSL_BATCHED. The gap is specifically the
**SwiGLU-OAI + clamp** combination on a **batched** NVFP4 kernel.

### What would fix it

Teach a *batched* NVFP4 MoE backend to do SwiGLU-OAI (uninterleaved) with the clamp, and add it
to `NVFP4_BACKENDS_WITH_CLAMP`. Two plausible routes:

1. Add a **masked**-layout version of the cute-DSL swiglu-fusion kernel that already exists for
   the contiguous layout (`flashinfer/.../blockscaled_contiguous_gather_grouped_gemm_swiglu_fusion`).
   The DeepEP/batched path uses the masked grouped GEMM, which currently has no swiglu fusion.
2. Or add a `swigluoai_clamp_scaled_nvfp4_experts_quantize` op (like the existing SILU-only
   `silu_and_mul_scaled_nvfp4_experts_quantize`) and wire it into `FLASHINFER_CUTEDSL_BATCHED`.

This is basically the batched counterpart of #45624, which added the same activation + clamp to
the standard-layout TRTLLM backend. Until something like it lands, NVFP4 MiniMax-M3 is limited to
standard EP and can't use DeepEP wide-EP.

### jesco-absolut · 2026-06-27

I reproduced this on a true SM100-family host (`8x B200`) with `vllm/vllm-openai:nightly` (`0.23.1rc1.dev515+g68ee8300a`).

A useful fast repro does not require downloading model weights:

```bash
timeout 240s env CUDA_VISIBLE_DEVICES=0,1 VLLM_LOGGING_LEVEL=DEBUG \
  vllm serve nvidia/MiniMax-M3-NVFP4 \
  --host 0.0.0.0 --port 8000 \
  --load-format dummy \
  --max-model-len 1024 \
  --tensor-parallel-size 1 \
  --data-parallel-size 2 \
  --data-parallel-size-local 2 \
  --enable-expert-parallel \
  --all2all-backend deepep_low_latency \
  --gpu-memory-utilization 0.25
```

This reaches model construction and fails at:

```text
MiniMaxM3MoE.__init__
  -> FusedMoE
  -> RoutedExperts._get_quant_method
  -> ModelOptNvFp4FusedMoE.__init__
  -> select_nvfp4_moe_backend()
  -> NotImplementedError: No NvFp4 MoE backend supports the deployment configuration.
```

The worker log confirms the relevant config:

```text
activation=SWIGLUOAI_UNINTERLEAVE
swiglu_limit=7.0
swiglu_alpha=1.702
swiglu_beta=1.0
all2all_backend='deepep_low_latency'
use_ep=True
```

I also ran the existing masked CuteDSL NVFP4 smoke test on the same host:

```text
test_flashinfer_cutedsl_moe_masked: 6 passed
```

So the baseline batched CuteDSL NVFP4/SILU path is healthy. The gap appears specifically to be batched DeepEP layout + clamped MiniMax SwiGLU-OAI (`SWIGLUOAI_UNINTERLEAVE`) activation/requantization. Today `FlashInferCuteDSLBatchedExperts` supports only `MoEActivation.SILU` and calls `silu_and_mul_scaled_nvfp4_experts_quantize`; I do not see an equivalent clamped batched SwiGLU-OAI NVFP4 activation+quantize primitive exposed to vLLM.

Before attempting an implementation: would maintainers prefer this to be solved by adding/exposing the missing FlashInfer primitive first, or is a vLLM-side custom op/prototype acceptable?
