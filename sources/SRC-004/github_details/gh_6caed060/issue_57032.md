# [Issue #57032] [Spec Decode][dflash] Drafter KV group is never identified, so prefix-cache reuse is silently disabled for the Mamba groups

## 正文

AI-authored (disclosed): produced and verified on our live CMP 170HX cluster; the account owner is a user, not a vLLM dev.

### Summary

With `method="dflash"` the drafter's KV cache group is never identified, so the consumer falls back to treating **every** group as a draft group -- including the Mamba/GDN groups -- and prefix-cache reuse across requests is silently disabled for those layers. The warning is printed on every start:

```
Speculative decoding (method=dflash) is enabled but no KV cache group could be
identified as the draft model's, so every group -- including Mamba groups [0, 1, 2, 3]
-- will be treated as a draft group. A Mamba group cannot satisfy the widened lookup
window that implies, so prefix-cache reuse across requests will be disabled ...
```

`_uses_trailing_mtp_layers()` (the positional fallback generalized in #55390) is gated on `spec_config.method == "mtp"`. `dflash` drafts reuse the target's decoder-layer architecture, so their attention spec is indistinguishable from the target's and the spec-driven rule cannot find them either.

### Measured consequence -- corrected

**Correction (2026-09-16, see the validation comment below):** this section originally attributed the
36.4 s prefix-child TTFT to the missing draft-group annotation. That attribution is wrong. With the
annotation patch applied (`xiaoba17/vllm@40681e0c9d`) the same 35-36 s reproduces and the engine's
prefix-cache counters are byte-identical; the annotation fix is correct and worth carrying, but it does
not gate this symptom.

What does gate it is the **Mamba checkpoint retention policy** plus prefill chunk granularity. On the
same box, same payload: `--prefix-cache-retention-interval 832` takes the 51.8k prefix child from
35.15 s to 5.83 s (+74,880 reused tokens = 10 x 7,488), and `--max-num-batched-tokens 1664` takes it to
1.47 s (= an exact re-send) for ~13 % extra on the cold parent prefill. The default
`prefix_cache_retention_interval=0` keeps only semantic replay boundaries, so a child that extends a
cached parent resumes from a much earlier checkpoint. For reference, an **identical** re-send resumes
in 1.5 s in every configuration -- which is why the original comparison looked like an annotation
problem.

### Ask

Extend the trailing-layer positional fallback (with the `_groups_partition_layers_exactly` guard added in #55390) to `method == "dflash"`, or state why it cannot apply there. If dflash drafts are guaranteed to register their KV layers after every target layer the same way MTP drafts do, the rule should transfer; if they are not, some other annotation path is needed, because the flag-all fallback quietly costs the Mamba-group reuse in any dflash deployment.

### Environment / evidence

- vLLM v0.13.0 line (fork image `vllm/vllm-backport:cmp170hx`, sha256 `2d27fe8655b0c57b953dc3dff72034df0a98abf2a1ff07387e48f6a0af886a2a`), V2 GPU model runner.
- Reproducible on every start; no special flags beyond the ones above. Raw server logs, per-request TTFT/JSONL and the harness are kept on the machine and available on request.

| arm | file | extra engine flags | (1) | (2) | (3) | (4) | hits |
|---|---|---|---|---|---|---|---|
| D | image | `--prefix-cache-retention-interval 832` | 115.25 | **5.83** | 1.42 | **2.27** | 654,784 |

- The annotation is orthogonal in every configuration: D vs E are 0.04 s apart with byte-identical counters, exactly like A vs B.
- The gate is the Mamba checkpoint retention policy -- `prefix_cache_retention_interval` defaults to 0 (semantic replay boundaries only). At one checkpoint per block the same prefix children resume: +74,880 reused tokens = 10 x 7,488, i.e. the parent's prefill chunk.
- The residual ~5.9 s is prefill chunk granularity. At `--max-num-batched-tokens 1664` the hit moves to 51,584 and the prefix child matches an exact re-send (1.47 s), at the cost of ~13 % on the cold 133k prefill. Counter check: 661,440 - 654,784 = 6,656 = 8 x 832.
- Reproduced on a second dflash profile (fp8 KV -> FlashInfer): **38.40 -> 16.21 s** with the flag (+85,696 = 13 x 6,592; that profile's scheduler block is 6,592 tokens, so each hit still carries ~5.5 s of recompute). Its engine prints the caveat directly: `Disabling fine-grained prefix-cache hits because these KV cache managers require block-aligned lookups: SlidingWindowManager.` -- our draft has 5 sliding layers, so `--prefix-match-unit`-based paths cannot engage on this model. Note the flag must be a multiple of the **scheduler** block size (6,592 here, not 1,648).

**Correction to this issue.** The "Measured consequence" paragraph attributed the 36.4 s to the annotation gap. That is wrong: with your patch applied the same 35-36 s reproduces, and the real gate is the retention/chunk configuration above. Our earlier comparison measured a prefix child against an identical re-send without controlling for that. We are editing the issue text, and we apologize for the wrong lead.

**Where that leaves your patch.** We would carry it for the annotation fix itself: the flag-all fallback silently mislabels the Mamba groups, your layer-index rule is exactly what a last-layer fallback cannot express for mixed full/sliding drafts, and the direct dump shows it lands correctly (draft group annotated, no Mamba group touched). We would not carry it as a prefix-reuse fix -- on this deployment that is a configuration matter.

### xiaoba17 · 2026-09-17

Thanks for the thorough hardware validation and for correcting the original performance attribution.

Before opening the PR, I expanded the duplicate and architecture review and found two important related PRs:
- #54041 implemented essentially the same marker-based approach: identify DFlash draft KV groups and mark them as is_eagle_group.
- #54041 was subsequently closed as superseded by #54163.

The validation recorded in #54041 is decisive. With #54163 alone, a repeated 20,021-token prefix restored 19,776 cached tokens with 0.529s / 0.464s TTFT. When the DFlash draft-group marker was composed with #54163, restored tokens dropped to zero and TTFT regressed to 12.134s / 12.101s.

This changes my interpretation of is_eagle_group. It is not merely descriptive draft-layer metadata; it enables EAGLE-specific volatile last-block handling. DFlash/DSpark use their own KV cache and do not write speculative KV into the target groups, so marking a DFlash group as an EAGLE group is not the correct long-term capability model, even though the layer-range detection itself works and removes the warning on current main.

Your A/B result is consistent with that distinction: my patch changes the annotation exactly as intended, but does not change TTFT or prefix-cache counters on the current deployment.

I therefore will not open a PR for commit 40681e0c9d. The branch will remain available as a reference, but the proper upstream direction appears to be #54163, which scopes the last-block drop to drafter families that actually preserve and modify target KV cache groups.

Thanks again for running the detailed validation. It prevented this from becoming a duplicate—and potentially conflicting—PR.
