# [Issue #42803] [Bug] MiMoV2 load_weights: fused qkv_proj path uses naive chunk(tp,dim=0)[rank], misplaces Q values into K/V slots

source: https://github.com/vllm-project/vllm/issues/42803
state: closed | updated: 2026-09-26T01:50:29Z
labels: stale

## 正文

## Summary

`vllm/model_executor/models/mimo_v2.py:load_weights` has a code path for fused-`qkv_proj` checkpoints (MiMo-V2 Pro variants) that does

```python
if "qkv_proj" in name:
    if name in params_dict:
        param = params_dict[name]
        loaded_weight = loaded_weight.chunk(tp_size, dim=0)[tp_rank]
        default_weight_loader(param, loaded_weight)
    continue
```

For a checkpoint where the fused tensor is laid out `[Q | K | V]` along dim 0 — which is the case for at least `festr2/MiMo-V2.5-Pro-NVFP4-MXFP8-attn-TP8` — a naive `chunk(tp_size, dim=0)[tp_rank]` gives 7 of 8 ranks (at TP=8) rows that fall entirely inside the Q region. Those ranks' `QKVParallelLinear` parameter slots for K and V end up filled with Q values; only the last rank gets any real K/V data. Attention is therefore severely broken on 7 of 8 ranks.

The proper loader (`QKVParallelLinear.weight_loader` with `shard_id="q"/"k"/"v"`) handles the TP split per-section correctly. It's already used by the `stacked_params_mapping` path for checkpoints that store Q/K/V as separate tensors; the fused path just doesn't reach it.

## Repro

Model: `festr2/MiMo-V2.5-Pro-NVFP4-MXFP8-attn-TP8` (the only Pro-format quant I'm aware of that hits the fused branch; the Flash variant stores split q_proj/k_proj/v_proj and goes through `stacked_params_mapping`, which is correct).

Cluster: 8-node DGX Spark (GB10, sm_121), TP=8, Ray distributed executor. With other patches in place (MXFP8 dispatch wired into `modelopt_mixed`, `weight_scale_inv` -> `weight_scale` rename for the modelopt MXFP8 scale parameter), the model reaches Application startup and serves requests, but inference returns degenerate token loops (`*\0` / `Müslü` / `the` style — varies with prompt but never coherent).

## Empirical evidence the layout is `Q→K→V` (not per-rank pre-sharded)

For layer 0 `model.layers.0.self_attn.qkv_proj.weight_scale_inv` (shape `[27136, 192]`, uint8 E8M0):

| Region (dim-0 slice) | Rows | Mean byte | Interpretation |
|---|---|---|---|
| Q section `[0:24576]` | 24576 | **114.55** | 24576 = 128 Q heads × 192 head_dim |
| K section `[24576:26112]` | 1536 | **115.99** | 1536 = 8 KV heads × 192 head_dim |
| V section `[26112:27136]` | 1024 | **113.27** | 1024 = 8 KV heads × 128 v_head_dim |

The three sections have distinguishable scale-byte distributions (note V is systematically smaller-magnitude, consistent with `attention_value_scale=0.612` applied to V before attention). If the tensor were per-rank pre-sharded (8 chunks of `[Q|K|V]` concatenated), every chunk would have the same internal structure and the per-rank means would be identical; instead they're flat ~114 for the first 7 chunks (all-Q) and a weighted mix for chunk 7 (which spans the Q/K/V boundaries).

## Fix

Split the fused tensor by `(q_size, k_size, v_size)` using config dims (distinguishing full vs. SWA layers via `hybrid_layer_pattern`), then call the existing `QKVParallelLinear.weight_loader` three times with `shard_id` `"q"`, `"k"`, `"v"`. Each call lets the proper loader take this rank's TP-slice of that section, identical to the existing stacked path.

Proposed patch against `vllm/model_executor/models/mimo_v2.py` (replacing the `if "qkv_proj" in name:` block):

```python
if "qkv_proj" in name:
    if name in params_dict:
        param = params_dict[name]
        try:
            _li = int(name.split(".layers.")[1].split(".")[0])
        except (IndexError, ValueError):
            _li = -1
        _is_swa = (
            _li >= 0
            and hasattr(self.config, "hybrid_layer_pattern")
            and self.config.hybrid_layer_pattern[_li] == 1
        )
        if _is_swa:
            _nh = self.config.swa_num_attention_heads
            _nkv = self.config.swa_num_key_value_heads
            _hd = self.config.swa_head_dim
            _vhd = getattr(self.config, "swa_v_head_dim", _hd)
        else:
            _nh = self.config.num_attention_heads
            _nkv = self.config.num_key_value_heads
            _hd = self.config.head_dim
            _vhd = getattr(self.config, "v_head_dim", _hd)
        _qs = _nh * _hd
        _ks = _nkv * _hd
        _vs = _nkv * _vhd
        if loaded_weight.shape[0] == _qs + _ks + _vs:
            _q = loaded_weight[:_qs]
            _k = loaded_weight[_qs : _qs + _ks]
            _v = loaded_weight[_qs + _ks : _qs + _ks + _vs]
            _wl = getattr(param, "weight_loader", default_weight_loader)
            _wl(param, _q, "q")
            _wl(param, _k, "k")
            _wl(param, _v, "v")
            loaded_params.add(name)
        else:
            # Unexpected shape — keep old behavior.
            loaded_weight = loaded_weight.chunk(tp_size, dim=0)[tp_rank]
            default_weight_loader(param, loaded_weight)
    continue
```

I have this running on a TP=8 cluster; with the patch, the same model produces coherent output for chat and completion prompts (`12 × 7` → `84`, `def fibonacci(n):` → proper Python recursion, etc.). Without the patch, the same configuration produces the degenerate token loops described above.

The patch handles both full and SWA layers (MiMo-V2 has full attention layers at positions where `hybrid_layer_pattern[layer] == 0` and SWA layers elsewhere). It applies to both the FP8 weight tensor and the uint8 E8M0 scale tensor (`weight_scale_inv`) because both share the `qkv_proj` name prefix.

## Why this also affects users who don't see the symptom

The Flash-format MiMo-V2 checkpoints (separate `q_proj`/`k_proj`/`v_proj`) go through the `stacked_params_mapping` path before hitting this branch, so they're fine. Only fused-`qkv_proj` Pro checkpoints reach the buggy path. To my knowledge today that's `festr2/MiMo-V2.5-Pro-NVFP4-MXFP8-attn-TP8` and the BF16 source `XiaomiMiMo/MiMo-V2.5-Pro` (if anyone tries to serve it directly).

### idonati · 2026-05-21

@catsled — short version: the fused `qkv_proj` tensor in MiMo-V2.5 / V2.5-Pro is laid out as TP-sharded `[Q|K|V]` chunks, not as a contiguous Q-then-K-then-V block. The loader's `loaded_weight.chunk(tp_size, dim=0)[tp_rank]` slices the fused tensor naively along dim 0 and ends up dropping Q rows into the K/V parameter slots on `tp_size − 1` of `tp_size` ranks. The model loads fine and decode looks plausible at a glance, but the outputs are silently wrong.

Fixes by path:
- **BF16/FP16**: explicit `[q_size, k_size, v_size]` split per shard (this issue).
- **FP8 (Pro checkpoint)**: also has pre-sharded `weight_scale_inv` rows that have to be loaded together — @amd-satre's PR #42270 handles that.
- **INT8 (your case)**: same Q/K/V split applies to the weight tensor; for the scale tensor it depends on which quant method you're using.

If you can share the quant scheme (compressed-tensors W8A8? bitsandbytes? something custom?) and a short snippet of the broken output, easier to point at the right loader path.

### idonati · 2026-05-25

@catsled — `d1 d2 )___((()) d3 d4 ...` is the exact signature of QKV mis-allocation. compressed-tensors W8A8 per-channel on the fused `qkv_proj` runs through the same `loaded_weight.chunk(tp_size, dim=0)` path that's broken for BF16/FP8 — it just bites differently because the weight AND scale tensors both need the explicit `[q_size, k_size, v_size]` split per shard:

- **weight** (INT8, shape `[hidden, q+k+v]`): same fix as the BF16 issue — slice each rank along dim=0 with the explicit Q/K/V sizes, not `chunk(tp, dim=0)[rank]`.
- **`weight_scale`** (per-channel, shape `[q+k+v]`): also needs the same split, since compressed-tensors stores one scale per output channel.
- **`input_scale`** (per-tensor for W8A8): single scalar, no split needed.

If you point compressed-tensors at the patched loader from #42270 (once it merges) it should "just work" because the same explicit-split helper applies in the INT8 branch. If you want to confirm before that lands, the patch I'm running on FP8 (Pro checkpoint) for reference is `patch_mimo_v2_qkv_split.py` in https://github.com/idonati/spark-vllm-docker-festr2 — port the helper to the INT8 path and the gibberish should clear.

Bonus diagnostic: dump `model.layers.0.self_attn.qkv_proj.weight` post-load, slice the Q portion `[:q_size, :]`, do a forward pass with K=V=0, and check whether the output magnitude is sensible. If it is, scales are fine and only the weight split is wrong. If it's garbage, the scale split is also off.
