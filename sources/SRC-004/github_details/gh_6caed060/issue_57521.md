## 正文

## Summary

[#54674](https://github.com/vllm-project/vllm/pull/54674) ("[Perf][DSpark] Stack DeepSeek V4 context WKV projections", merged 2026-09-17) is a **TTFT regression of ~3.2-3.3%** on 2-node DGX Spark (GB10 / SM121, TP=2) serving DeepSeek-V4-Flash-0731 NVFP4. It also costs ~1.5% of the KV pool. We measured no compensating decode or acceptance-rate gain.

Since the PR targets the context/prefill path, a TTFT regression is the opposite of its intended effect, so we are reporting it rather than just dropping the patch locally.

## Why the usual A/B is not enough here, and what we did instead

Throughput metrics on this platform have a large boot-to-boot spread, so a single A-vs-B comparison cannot resolve a few percent. We ran **A-B-A** (three full engine restarts) and used the two A runs to calibrate the noise floor:

| metric | A1 (without #54674) | B (with #54674) | A2 (without #54674) | A1↔A2 spread |
|---|---|---|---|---|
| greedy 32K decode tok/s | 65.62 | 64.57 | 60.92 | **7.2%** |
| temp0.6 8K decode tok/s (mean of 3) | 61.54 | 65.70 | 65.23 | **6.0%** |
| temp0.6 acceptance rate | 0.6539 | 0.7016 | 0.6961 | **6.5%** |
| **TTFT 8K (s)** | **2.502** | **2.589** | **2.512** | **0.4%** |
| **TTFT 32K (s)** | **10.191** | **10.551** | **10.221** | **0.3%** |

Decode throughput and DSpark acceptance rate swing 6-7% between two boots of the *same* build, so every apparent "gain" for B in those rows is inside the noise band. TTFT, by contrast, is stable to 0.3-0.4% across the two A runs — and B is consistently **+3.2%** (8K) and **+3.3%** (32K) relative to the A mean, which is roughly an order of magnitude outside that spread.

A 128K-prefill probe agrees in direction: 62.6 s with the patch vs 61.9 / 62.1 s without.

Secondary cost: GPU KV cache pool drops from **1,655,061** to **1,630,430** tokens (-1.5%), and reported max concurrency at 1M context from 1.58x to 1.55x.

## Hypothesis

With `--max-num-seqs 6` on a 2-node TP=2 GB10 pair, the stacked WKV projection does not have enough concurrent context work to amortize its extra setup, so the stacking overhead lands directly on TTFT. Configurations with larger batch or more GPUs may still benefit — we are not claiming the PR is wrong in general, only that it is a net loss in this shape.

## Reproduction

Serve command (2 nodes, one GB10 each, RoCE):

```
vllm serve nvidia/DeepSeek-V4-Flash-0731-NVFP4 \
  --revision f1caa71142bd0be02f728c79f75042ac1e461579 \
  --tensor-parallel-size 2 --nnodes 2 --distributed-executor-backend mp \
  --trust-remote-code --max-num-seqs 6 --max-num-batched-tokens 8192 \
  --max-model-len 1048576 --kv-cache-dtype fp8_ds_mla --block-size 256 \
  --enable-chunked-prefill --quantization deepseek_v4_fp8 \
  --gpu-memory-utilization 0.825 \
  --tokenizer-mode deepseek_v4 --reasoning-parser deepseek_v4 \
  --enable-auto-tool-choice --tool-call-parser deepseek_v4 \
  --compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY"}' \
  --speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic","disable_eagle_block_drop":true}' \
  --no-async-scheduling --enable-flashinfer-autotune
```

Measure TTFT at 8K and 32K prompt with 384 output tokens, greedy. **Restart the engine between arms and run A-B-A**; a single A/B will not separate a 3% TTFT effect from the decode noise if you look at throughput, and will look like a *win* if you look at `temp0.6` decode or acceptance rate.

## Environment

- 2x DGX Spark (GB10, SM121, 48 SMs, driver 580.173.02), TP=2 over RoCE, unified 128 GB/node
- vLLM nightly `2671fedf` + the merged `#54674` diff applied as a source overlay (byte-identical to the merged version apart from the `diff --git`/`index` headers)
- flashinfer 0.6.18.post1 with the #4802 SM120 sparse-MLA sources overlaid (+#5048, +#5097)
- DeepSeek-V4-Flash-0731 NVFP4, `fp8_ds_mla` KV, DSpark k=5
- Benchmarks run on an idle cluster with periodic synthetic load disabled

Happy to re-run with different `--max-num-seqs` or on a larger batch shape if that would help locate the crossover.
