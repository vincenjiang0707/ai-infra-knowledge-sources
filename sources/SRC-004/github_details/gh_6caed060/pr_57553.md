# [PR #57553] fix(parser): keep fenced code examples out of qwen3 tool calls

source: https://github.com/vllm-project/vllm/pull/57553
state: open | updated: 2026-09-23T00:57:13Z

## 正文

keep fenced code examples out of qwen3 tool calls

Fixes #57541

## what happens

qwen3 models document the tool call format inside markdown fences. the parser has no fence state at all, so it reads the example XML as a real call header and emits a phantom bash tool call while swallowing most of the answer text

the reporter measured it at chunk sizes 1, 7 and 10000, all agree. on v0.29.0 and on the #56661 backport the content comes back as 59 of 149 chars and the parser reports a tool call named Bash that the model never made. i reproduced it verbatim on master at 4c6c1a4 with their CPU-only snippet, same output, no gpu needed

## the fix

a FENCE terminal on the qwen3 config plus a FENCED engine state. a fenced span runs from the first ``` to the next ``` and everything in between is emitted as plain text, streaming and non streaming

- (CONTENT, FENCE) enters FENCED and re-emits the fence itself as text
- (FENCED, FENCE) returns to CONTENT the same way
- FENCED has no tool transitions, so XML inside it can never promote
- an unterminated fence settles back to CONTENT in finish(), it never turns into a call

```xml
<tool_call>
<function=Bash>
<parameter=command>ls -la</parameter>
</function>
</tool_call>
```

stays exactly the text you see there. a real call right after a fenced example still parses, and backticks inside a parameter value never open a fence (TOOL_ARGS content is untouched)

## why this is not duplicating an existing PR

- search for PRs referencing #57541: 0 hits
- #56658 and #56661 fix a different case, a bare <tool_call> in prose with no fence. the reporter measured their case still broken with #56661 applied
- no open PR touches fenced example handling (157 open qwen3 and parser PRs scanned by title and by fence keyword searches)

## why engine/ changed

the vllm/parser AGENTS.md says keep model fixes in the model file and change engine/ only when the behavior is wrong for every parser. the fence semantics live in the shared state machine: FENCED is a new ParserState with a default content_events row, and finish() normalizes it like the other non-final states. without the state in engine/, the FENCE transitions cannot exist in a declarative config

Data point from a deployment, in support of this PR.

Tool-call conformance matrix on Qwen3.8-27B-NVFP4 / vLLM 0.28.0 / `qwen3_coder`, 3,600 requests with every raw generation retained. Spans were enumerated by replaying each generation through the Qwen3 parser itself rather than by pattern-matching the text: **167 spans sit inside a ``` fence**, and of the duplicate-call failures we classified, 86 are the fenced shape this PR resolves.

The other roughly three quarters are unfenced — the model quotes the markup in its reasoning block or in ordinary content. Two today-defects we hit while measuring that are filed separately and may be of interest here, since both involve the parser's treatment of quoted markup: #58227 (an unclosed `<tool_call>` opener written in prose holds the state machine in tool state through `</think>` and swallows a later genuine call) and #58228 (`finish_reason: "tool_calls"` masks a `max_tokens` truncation).

Raw generations for the fenced cases are available as fixtures if useful; they are synthetic weather/file-write calls, nothing private.
