## Bug Description

`--speculative-config '{"method":"mtp",...}'` crashes at weight-load time when the target checkpoint is **compressed-tensors pack-quantized** and ships its MTP head as **dense BF16** in a separate shard. The MTP predictor's Linear layers are built from the *target's* quant config, so the loader expects packed parameter names (`weight_packed`) while the checkpoint provides dense `mtp.*.weight` tensors.

## Environment

- vLLM v0.30.0, official docker image `vllm/vllm-openai:v0.30.0` (stock, no patches)
- Model: [`ukisai/Swift-1.5-Qwen3.8-27b-W4A16-AWQ`](https://huggingface.co/ukisai/Swift-1.5-Qwen3.8-27b-W4A16-AWQ) (dense 27B, `Qwen3_5ForConditionalGeneration`, hybrid GDN + full attention, vision preserved)
- Flags: `vllm serve ukisai/Swift-1.5-Qwen3.8-27b-W4A16-AWQ --tensor-parallel-size 2 --speculative-config '{"method":"mtp","num_speculative_tokens":3}'` (+ kv fp8; the crash is at load, the rest is irrelevant)

## Crash

```
ValueError: There is no module or parameter named 'fc.weight' in Qwen3_5MultiTokenPredictor
```

Raised from the weight-map walk in `vllm/model_executor/models/utils.py` (`_load_module`, the "no module or parameter named" branch), reached via `Qwen3_5MultiTokenPredictor.load_weights` (`vllm/model_executor/models/qwen3_5_mtp.py`). The engine never reaches runtime — deterministic at boot.

## Root Cause

`Qwen3_5MultiTokenPredictor.__init__` builds its `fc` (`ColumnParallelLinear`) and decoder layers from `vllm_config.quant_config` — the **target's** config. The file already contains two workarounds for the dense-draft-on-quantized-target family:

1. `modelopt_fp4`: `fc_quant = None` because "mtp.fc is stored as BF16 in NVFP4 checkpoints but is missing from hf_quant_config.json exclude_modules" (PR #38650)
2. GPTQ: `quantization_config.dynamic` `-:mtp` patterns → build all MTP layers unquantized

**Neither covers compressed-tensors.** For this checkpoint:

- `config.json` → `quantization_config.format: "pack-quantized"`, method `compressed-tensors`; the `ignore` list covers `model.visual.*`, `model.language_model.layers.*.linear_attn*`, `lm_head` — **no `mtp` entry**
- `model.safetensors.index.json` → 15 `mtp.*` tensors, **all dense** (plain `.weight` names, e.g. `mtp.fc.weight`, `mtp.layers.0.mlp.down_proj.weight`), all in a dedicated `model-mtp-bf16.safetensors` shard

So the quantizer left the MTP head unquantized **without declaring it in `ignore`**, vLLM builds the MTP Linears pack-quantized, and the dense names cannot resolve.

This is a cousin of #51581 (DFlash2 `_build_context_kv_buffers` slicing `.weight` on a pack-quantized target) — same family of draft/MTP structures assuming dense parameters on quantized targets.

## Suggested Fix

Extend the existing workaround family: when the target quant config is compressed-tensors (pack-quantized) and the checkpoint's MTP tensors are dense — detectable either from the safetensors index (plain `mtp.*.weight` names, no packed variants) or from a dedicated bf16 MTP shard — build the MTP predictor unquantized, mirroring the `modelopt_fp4` path for `fc` and the GPTQ `dynamic` path for the layers.

Happy to provide the full boot log or test a fix branch — the checkpoint and repro are on hand.

### he-yufeng · 2026-09-26

Picking this up, following the existing workaround family in qwen3_5_mtp.py. The detection reads the checkpoint's actual tensor names from the safetensors index (same repo-file channel config-time code already uses for recipe.yaml): any `mtp.*` tensor carrying a quantization artifact suffix (weight_packed/weight_scale/weight_zero_point/input_scale/input_zero_point) means a properly quantized head and nothing changes; plain `.weight`-only mtp.* keys (your case, all 15 dense in the bf16 shard) mean the head ships dense, so the whole predictor builds unquantized, mirroring the GPTQ `dynamic` path for the layers and the modelopt_fp4 path for fc. Single-file checkpoints have no index, so they keep current behavior. PR with red-green coverage of the naming contract shortly.
