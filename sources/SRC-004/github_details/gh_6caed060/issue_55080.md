### 🐛 Describe the bug


```python
# pip install vllm==0.28.0 — CPU only, no GPU/server/checkpoint needed
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
from vllm.parser import ParserManager

class _Tok:                    # tokenizer stub: the defect is in the dispatch
    def get_vocab(self): return {}
    @property
    def vocab(self): return {}
    def encode(self, t, **k): return [ord(c) % 1000 for c in t]
    def decode(self, ids, **k): return "".join(chr(i) for i in ids)
    def convert_tokens_to_ids(self, t): return 90000
    def convert_ids_to_tokens(self, ids): return [str(i) for i in ids]
    @property
    def all_special_tokens(self): return []
    def __len__(self): return 100000

TEXT = '<tool_call>\n{"name": "get_weather", "arguments": {"city": "SF"}}\n</tool_call>'
req = ChatCompletionRequest(model="m",
                            messages=[{"role": "user", "content": "hi"}],
                            tool_choice="none")

cls = ParserManager.get_parser(tool_parser_name="glm45", enable_auto_tools=True)
parser = cls(tokenizer=_Tok())
calls, content = parser._extract_tool_calls(TEXT, req)
print(f"calls={calls} content={content!r}")   # calls=[] content=None
```

When `enable_auto_tools=True` , `DelegatingParser._extract_tool_calls` , The engine-based branch returns whatever survived parsing instead of the model text.

Affected (non-streaming): glm45, glm47, ling3, mimo, qwen3_coder, qwen3_xml (content -> None); with the full sweep also mistral, kimi_k2, seed_oss. Every affected parser has `engine_based_streaming = True`.

### Expected behavior

Under `tool_choice="none"` both branches return the original model text; tool calling is off, so the detector's consumed-text output is irrelevant.

### DIYer22 · 2026-09-05

I encountered the same bug in recent version: after setting `tool_choice="none"`, all tool-call-related content is removed.

I would especially like to ask @bbrowning and the participants in [#46875](https://github.com/vllm-project/vllm/pull/46875) about this. I understand that the PR mainly aims to prevent internal tool-call markers from leaking into ordinary user-facing text. That goal is understandable, but I believe hiding markers and the API semantics of `tool_choice="none"` should be treated separately.

## Legacy behavior (and my expectation)

When a request includes `tools` and sets `tool_choice: "none"`:

- The server should **not** return a structured `message.tool_calls` field or use `tool_calls` as the finish reason.
- Tool definitions should still be included in the prompt by default, so the model may still generate tool-call-shaped text.
- If the model does generate `<tool_call>` together with the function name and arguments, that content should be preserved in `message.content`, as it was with the legacy parser.
- It should not be silently deleted, since doing so breaks the completeness and coherence of the output at the engine level.

In other words, `none` should control how the API represents the result, but should not rewrite or discard text that the model has already generated.

If the goal is to prevent the model from generating tool calls, the request can omit `tools`, or the prompt/chat template can explicitly tell the model not to call tools. If the goal is only to hide internal markers, that should be a separate, explicit option; I do not think either goal should be implicitly attached to `tool_choice="none"`.

## Minimal reproduction

The following keeps only the vLLM startup options relevant to parsing:

```bash
vllm serve cyankiwi/Qwen3.5-2B-AWQ-4bit \
  --tool-call-parser qwen3_xml \
  --enable-auto-tool-choice \
  --reasoning-parser qwen3
```

Then run:

```bash
curl -sS http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "cyankiwi/Qwen3.5-2B-AWQ-4bit",
    "messages": [{
      "role": "user",
      "content": "Call get_weather for San Francisco. Return only the tool call."
    }],
    "tools": [
      {
        "type": "function",
        "function": {
          "name": "get_weather",
          "parameters": {
            "type": "object",
            "properties": {
              "location": {"type": "string"}
            },
            "required": ["location"]
          }
        }
      }
    ],
    "tool_choice": "none",
    "temperature": 0,
    "max_tokens": 128,
    "skip_special_tokens": false
  }'
```

Expected behavior:

- `choices[0].message.content` is non-empty and preserves the tool-call-shaped text generated by the model (for example, `<tool_call>`, `get_weather`, and its arguments).
- `choices[0].message.tool_calls` is absent or empty.
- `finish_reason` is not `tool_calls`.

With the current engine-backed parser, `content` may be empty or `null`. When the model output consists almost entirely of a tool block, the whole response appears empty. The model has already generated these tokens, but the parser consumes and discards the tool events while constructing the API response instead of mapping the corresponding text to `content`.

A run in the current environment returned, in essence:

```json
{
  "choices": [
    {
      "message": {"content": null},
      "finish_reason": "stop"
    }
  ]
}
```

## Why the complete text should be preserved

Silently discarding output causes several practical problems:

1. It breaks the existing `tool_choice="none"` protocol and applications that depend on the legacy parser; this usage already has broad downstream dependencies.
2. A request whose output is entirely a tool block returns empty content, making it difficult to distinguish an empty model response from server-side data loss.
3. The API response no longer matches what the model actually generated, which affects replay, debugging, and continuation.
4. Users cannot tell whether the model attempted a tool call or decide at the application layer how to handle that text.

I would therefore like to ask the maintainers to consider defining `tool_choice="none"` as “do not return structured tool calls, but preserve the original generated text,” with the engine-backed and legacy parsers following the same behavior. If these tool markers need to be hidden, could that be a separate explicit setting instead?

### kabishou11 · 2026-09-16

Thanks @ammo-man — confirmed the same root cause on the wider shape you measured.

With `--enable-auto-tool-choice` and an engine-based parser (`qwen3_xml` / `glm45`), `DelegatingParser` was still running tool extraction when tools were absent. ### bvisible · 2026-09-25

Two details from a third setup that are not in this thread yet, in case they help the review of #55089. Same `DelegatingParser` branch as above.

**Setup:**

- vLLM 0.28.0, a derived image whose patches do not touch `vllm/parser/`.
- Qwen3.8-27B (W4A16), `--reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder`. In 0.28.0, `qwen3_coder`, `qwen3_xml` and `mimo` resolve to the same engine-based parser.
- `/v1/chat/completions`, `temperature: 0`, `chat_template_kwargs: {"enable_thinking": false}`, and **no `tools`**.
- The model is asked to copy a text that contains a `<tool_call><function=kanban_block><parameter=reason>…</parameter></function></tool_call>` block.

**1. The text after the block is lost too, not only the block.** Asked to copy `Voici ma question.`, then the block, then `Fin.`, the non-streaming answer is `content: "Voici ma question."` with `finish_reason: "stop"` and 44 completion tokens. `Fin.` never comes back. A caller therefore cannot recover the answer by stripping the markup: everything the model writes after a tool-call-shaped span is dropped as well. The block alone gives `content: null` and 37 completion tokens.

**2. Streaming and non-streaming disagree on the same request.** Same request with `stream: true`, still without `tools`:

- the content is `"Voici ma question.\n"`;
- then come four `delta.tool_calls` chunks for `kanban_block`, a function that was never declared;
- then `finish_reason: "tool_calls"`, and `Fin.` is lost here too.

So the non-streaming path deletes the call while the streaming path emits it. The streaming side is #42868.

With the tool declared and `tool_choice: "auto"`, the answer is a correct `tool_calls` entry. With the tool declared and `tool_choice: "none"`, the call is deleted, as in the no-tools case.

**Where this showed up for us.** An agent loop made a tool-free "summarise what you found" call to a model that is prompted to finish with a tool call. The call came back empty, with no error. Until #55089 lands, our workaround is to keep the tools declared on that call and read the answer from the tool call's arguments.
