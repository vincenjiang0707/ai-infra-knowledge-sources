## 正文

### Your current environment

vLLM 0.29.0 (image vllm/vllm-openai:v0.29.0 + ray 2.56.1, pip package b12x 1.3.0)
torch 2.13.0+cu130, CUDA 13.0, transformers 5.16.1
GPU: 6x NVIDIA RTX PRO 6000 Blackwell Server Edition (SM120), driver 595.91.07
Host: Ubuntu, kernel 7.0.0-31-generic, Docker
Cluster: two nodes (4 + 2 GPUs), Ray 2.56.1, 100 GbE direct link
Model: nvidia/GLM-5.2-NVFP4, PP=3 / TP=2, VLLM_PP_LAYER_PARTITION=31,29,18

Launch command:

  vllm serve nvidia/GLM-5.2-NVFP4 --distributed-executor-backend ray \
    --pipeline-parallel-size 3 --tensor-parallel-size 2 \
    --kernel-config '{"moe_backend":"b12x","linear_backend":"flashinfer_b12x",
                      "enable_cutedsl_warmup":true,"enable_flashinfer_autotune":true}' \
    --attention-config '{"sparse_mla_force_mqa":true}' \
    --disable-custom-all-reduce --no-async-scheduling \
    --max-model-len 262144 --max-num-batched-tokens 2048 --max-num-seqs 32 \
    --gpu-memory-utilization 0.98

Note: --disable-custom-all-reduce is required on SM120, so every reduction goes
through the pynccl path.

(collect_env.py output can be provided on request - the engine runs inside a
container on a two-node Ray cluster, so the script does not capture the full
picture.)


### 🐛 Describe the bug

Roughly every third engine start dies during CUDA graph capture. The crash is a
driver-level Xid 31 MMU fault; on the Python side it surfaces as an NCCL error
inside the tensor-parallel all_reduce that is being captured. It is intermittent:
the identical command succeeds on the next attempt, and once the engine is up it
serves for days without a single Xid.

Kernel log:

    NVRM: Xid (PCI:0000:41:00): 31, pid=147307, name=ray::vllm_Worke,
    channel 0x00000002, intr 00000000. MMU Fault: ENGINE GRAPHICS GPC0
    GPCCLIENT_T1_0 faulted @ 0x284_e8006000.
    Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ

Engine log - the crash happens at "Capturing CUDA graphs (FULL): 71%|5/7",
in Worker_PP1_TP0:

    reduced = tensor_model_parallel_all_reduce(hidden_states)
      -> get_tp_group().all_reduce(input_)
      -> torch.ops.vllm.all_reduce(input_, group_name=...)
      -> group._all_reduce_out_place(tensor)
      -> self.device_communicator.all_reduce(input_)
      -> out = pynccl_comm.all_reduce(input_)
      -> self.nccl.ncclAllReduce(...)
      -> RuntimeError: NCCL error: unhandled cuda error
    During handling of the above exception, another exception occurred:
      torch.AcceleratorError: CUDA error: an illegal memory access was encountered

## Controlled comparison

Same hardware, same command, only --enforce-eager added. All other models shut
down, GPUs verified free between runs:

    with graph capture   first-attempt failures ~30 % (6 of 22)   startup ~3:00 min
    --enforce-eager      first-attempt failures 0 of 8            startup ~1:45 min

22 first attempts recorded over five days; 6 died this way. Two further failures
were an unrelated out-of-memory condition and are excluded. In a deliberate
reproduction run today the failure appeared on the 4th consecutive start.

Seven Xid occurrences so far, on all four GPUs of the head node (PCI 01:00,
21:00, 41:00, 61:00), so this is not a defective card. The faulting addresses
repeat across incidents (0x284_e8006000 four times, 0x24f_78006000 twice).

## What we ruled out

- GPU memory pressure: same behaviour at --gpu-memory-utilization 0.97 and 0.98.
  At crash time the cards sit at 95.8 GiB of 97.9 GiB, 350 W power cap, 33 C.
- Defective hardware: all four GPUs of the head node produced the fault.
- #50189: that is a *write* fault under concurrent load with the flashinfer_b12x
  MoE backend. We use the native b12x MoE backend, our fault is a *read* at
  startup, and the engine never faults while serving.
- #40742: requires PDL (we set neither TRTLLM_ENABLE_PDL nor
  TORCHINDUCTOR_ENABLE_PDL) and raises "operation not permitted when stream is
  capturing", not a driver Xid.
- #30044: GH200, no Xid, deterministic rather than intermittent.

## Guess at the mechanism

Capturing an ncclAllReduce inside a CUDA graph appears to hit a race. The
faulting addresses repeat across incidents, which looks more like a deterministic
allocation being touched at the wrong moment than random corruption. We cannot
verify this from the outside.

## Workaround

Our autostart script retries up to five times, waiting for all GPUs to be
released between attempts; attempt 1 or 2 normally succeeds. --enforce-eager
avoids the fault entirely at the cost of throughput.

Full engine log, dmesg excerpt and nvidia-smi output of a failing run are saved
and can be attached on request.
