# [Issue #57571] [Feature]: Parser cache for streaming chat derender and stable tool call IDs on retried calls

## 正文

### 🚀 The feature, motivation and pitch

Tracking issue for work deferred from the streaming derender RFC #47161 and PR #50550: server side parser state for streaming chat derender, and keeping tool call IDs stable when a chunk is retried.

#### Where things stand

With a reasoning or tool parser configured, streaming chat derender keeps nothing on the server. Each chunk builds a fresh parser, replays the history the client echoes back in `stream_state` (`output_token_ids`, split by `output_chunk_lens`) through `parse_delta`, then feeds the new chunk (`OnlineDerenderer._derender_chat_stream_parsed`). Any replica can serve any chunk and the client carried state is the only source of truth.

The price is replay. It's O(n²) `parse_delta` calls over a generation and O(n³) character work for parsers that re-scan accumulated text (Hermes tool call JSON, DeepSeek-R1 reasoning). The "Streaming cost" section of `derenderer.md` documents this. @shimib measured it on 1×A100-40G with Qwen3-8B and the hermes + qwen3 parsers (https://github.com/vllm-project/vllm/issues/56851#issuecomment-5685698033): ~9× the in-process CPU at matched load, +15% E2E p50 on multi-thousand-token reasoning outputs and a saturated tier under concurrent parsed streams with the default `renderer_num_workers=1`.

Latency sensitive P/D goes to #56851 where the parser lives with the request on the decode pool and there's no replay. This issue covers the consumers that keep using streaming derender: RL, batch and gateways that own postprocessing.

#### 1. Parser cache

An LRU of live `Parser` instances on the derenderer, keyed by `(request_id, choice_index)`, as the "Future" note in #47161 describes. Each entry records how many chunks its parser has consumed. On a hit where that matches `len(stream_state.output_chunk_lens)`, skip replay and feed only the new chunk, so compute drops to O(delta). Anything else falls back to full replay: first chunk, eviction, a chunk that landed on another replica, a retry or out of order input. `stream_state` stays authoritative, so there's no protocol change and a hit has to produce exactly what replay would.

Design questions:

- **What a hit must check.** `request_id` comes from the client (`generate_chunk.request_id`), so the key alone can't be trusted. A hit needs to confirm the cached parser saw the same `prompt_token_ids`, `chat_request` and output history, e.g. with a digest stored in the entry. Otherwise one stream can pick up another stream's parser state.
- **Memory bounds and eviction.** Bound by entry count and TTL, and evict on the finish chunk. Streams abandoned midway never send a finish chunk, so the TTL has to cover them.
- **Concurrency.** Parsing runs on the renderer executor's thread pool and a retry can race the original call. Taking the entry out of the cache for the duration of the call and putting it back at its new position keeps two calls from sharing a parser.
- **Routing.** Without session affinity, a stream's chunks spread across N replicas and the hit rate drops to about 1/N. We should document routing on `request_id` for deployments that want the cache to pay off.
- **Default.** I'd make it opt in and off by default, so a stateless render tier stays the default.
- **What to cache.** A bare `Parser` or the shared per choice `ChatStreamProcessor` (#57572) if that lands first.

#### 2. Tool call ID stability on retried calls

Raised by @sagearc in the #50550 review (https://github.com/vllm-project/vllm/pull/50550#discussion_r3913963783).

Within one stream, IDs are already stable. `stream_state.last_tool_call_ids` pins the ID emitted for each tool call index, so replay never changes an ID the client saw on an earlier chunk. The gap is the chunk where a tool call's ID first appears. With the default `tool_call_id_type` (`random`), `make_tool_call_id` returns `chatcmpl-tool-{random_uuid()}`. If the client retries that chunk with the same `stream_state` (lost response, timeout, retry on another replica), the retry gets a new ID. If the first response reached anyone anyway, the same call now has two IDs. Rerunning a whole stream over the same generate output gives new IDs too. `kimi_k2` IDs (`functions.{name}:{idx}`) are derived from the input, so they aren't affected.

Options:

- **The cache remembers the IDs it assigned** per `(request_id, choice_index, tool call index)`. This only helps on a hit, on the same replica and within the TTL.
- **Derive the ID from the request**, e.g. a hash of `request_id`, `choice_index` and the tool call index. It's stateless, so it works on any replica and could also cover the batch path. But `request_id` is client supplied, so two requests that reuse one would share tool call IDs and it changes what `random` means for `tool_call_id_type`.
- **Document it as a limitation.** A client that retries a chunk treats the retried response as replacing the first one.

### Alternatives

- **Serialize parser state into `stream_state`.** Dropped. Parsers hold internals we can't cheaply round trip (`prev_tool_call_arr`, `current_tool_id`, `streamed_args_for_tool`, engine lexer buffers) and #32713 was closed as not planned.
- **Parse on the decode pool (#56851).** This is the answer for latency sensitive P/D. It doesn't help consumers that want a stateless render tier or do their own postprocessing.
- **Keep replay only.** Size `renderer_num_workers` for concurrent parsed streams and accept the cost. That's where things are after #50550.
- **Bidirectional streaming derender.** Suggested by @andylolu2. One stream per request holds the parser, so there's no cache, hit check, TTL or routing affinity. It needs a new streaming endpoint (WebSocket or gRPC) and a client change, so it doesn't replace the cache for existing clients. See https://github.com/vllm-project/vllm/issues/57571#issuecomment-5764095680 for more details.

The design should cover:

- **Cache hit check.** Hashing `request_id`, `prompt_token_ids`, and `choice_index` is not enough. Since `request_id` comes from the client and RL rollouts often send the same prompt repeatedly, two streams can match all three values and still be different requests. A cache hit should also verify that the parser was built from the same `chat_request` settings (such as tools, `tool_choice`, and `chat_template_kwargs`) and that it has seen the same output so far. For example, store a digest of the echoed `output_token_ids` or `output_chunk_lens` and compare it on lookup. Calculating this digest is O(n) per chunk but it is still much cheaper than replaying the stream.
- **Limits and cleanup.** Use both a maximum entry count and a TTL. Remove entries when the final chunk is processed and rely on the TTL to clean up streams that are abandoned before completion.
- **Concurrency.** Removing the entry while it is in use and putting it back afterward seems fine. If a retry happens at the same time as the original request, it simply won't find the entry and will fall back to replay.
- **Routing.** Agree that deployments should document `request_id` affinity if they want to benefit from the cache.
- **Default behavior.** Make the feature opt-in and disabled by default so the default deployment remains stateless.
- **What to cache.** Cache only the `Parser`. Since #57572 is blocked on #55029 and the parsed path work, there is no need to wait for it.

### hickeyma · 2026-09-21

@andylolu2 raised an alternative in feedback on slack that's worth mentioning here: a bidirectional streaming derender. @devtyagi3909 This doesn't change what I asked for above, its just an alternative approach. 

The client opens one stream per request, sends `chat_request` and `prompt_token_ids` once in the first message, then forwards each generate chunk. The server keeps the parser and incremental detokenizer for the life of the stream and sends back chat stream chunks. No `stream_state` echo and no replay.

It changes most of the design questions in the description as follows:

| | Parser cache | Bidi stream |
|---|---|---|
| Hit check | digest of `chat_request` and output history | not needed, state belongs to the stream |
| Bounds and cleanup | entry cap and TTL, evict on finish | freed on close, cancel or deadline, with a cap on concurrent streams |
| Concurrency | take the entry out while it's in use | messages arrive in order and a retry is a new stream |
| Routing | `request_id` affinity, otherwise ~1/N hit rate | the stream is pinned to one replica |
| Parser work per chunk | O(delta) on a hit, full replay on a miss | always O(delta) |
| Payload per chunk | O(n): `prompt_token_ids`, `chat_request` and the full `output_token_ids` echo, same as today | O(delta) after the first message |
| Client change | none | new endpoint and client loop |

Trade-offs:

- It's a new endpoint and client contract. The cache helps existing HTTP clients with no protocol change which is why I'd keep the cache as the near term plan.
- Every chunk still makes a hop to the derender tier. That's fine for RL, batch and gateways which accept it today. Latency sensitive P/D goes through #56851.
- If a replica dies mid-stream, the parser goes with it. The client reconnects and sends the history and `last_tool_call_ids` in the first message. The server replays once with the #50550 code and the tool call IDs stay stable. That also covers part of section 2.
- Transport is open. A WebSocket on the render server could reuse `GenerateStreamResponse` in and `ChatCompletionStreamResponse` out with only a small init message as new schema. vLLM already serves WebSockets for realtime speech-to-text. gRPC fits the Rust frontend which already has a gRPC listener and parsers. The Python render server has no gRPC listener though and vLLM's gRPC port has no auth by default.

@sagearc @bbrowning @shimib @vMaroon: would streaming derender consumers use a streaming endpoint like this if it got rid of replay? If not, the cache is enough and this stays under "Alternatives".

### devtyagi3909 · 2026-09-22

@hickeyma here's the design for the parser cache you asked for.

cache hit check: we'll hash request_id, prompt_token_ids, choice_index, the chat_request settings (tools, tool_choice, chat_template_kwargs), and a digest of output_token_ids. this ensures the parser state perfectly matches the echoed stream.

limits and cleanup: we'll set a max entry count and a ttl. the ttl takes care of abandoned streams. for successful streams, we just drop the entry on the final chunk.

concurrency: we'll check out (remove) the entry on use and put it back after. if there's a cache miss during a retry, it just falls back to replay.

routing: this needs request_id affinity. i'll document that subsequent requests must route to the same worker.

default behavior: strictly opt-in and disabled by default.

what to cache: only the parser object itself.

tool call id stability: on retries, tool call ids need to be stable. i recommend deterministically generating them using request_id, tool_name, and index (or seeding an rng with these).

let me know if this looks good to proceed.

Thanks @devtyagi3909. This mostly repeats my earlier points, so there is some work to be done yet. Can you answer the questions below before starting on code? A comment is fine.

**What to cache.** Correction to my earlier comment: the `Parser` alone isn't enough. `_derender_chat_stream_parsed` carries a detok window (`detok_state`) through replay into the current chunk. A hit skips replay, so the new chunk would be decoded from a fresh window and come out wrong (split multi-byte characters, leading spaces). The entry needs the parser, the detok window and the chunk count.

**Hit check.** What's the key and what does the entry store to check a hit? If it's one hash of everything, how does the entry get re-keyed after each chunk? The digest needs `output_chunk_lens` too. Replay calls `parse_delta` once per chunk, so different chunk boundaries can leave the parser in a different state. `request_id` comes from the client, so use a collision- esistant hash (e.g. `hashlib.blake2b`) over a canonical serialization. I'd hash the whole `chat_request` rather than pick fields, since `parse_delta` gets all of it. `prompt_token_ids` can be `None`.

**Bounds and failure.** What are the flag names and defaults for the entry cap and TTL? Is the TTL from last access and is expiry lazy or a background sweep? If `parse_delta` raises, the entry shouldn't go back in. And roughly how much memory per entry? A parser holds the accumulated text, so the worst case is about cap × `max_model_len`.

**Concurrency.** Check out and put back happen on the `renderer._executor` thread pool, so they need a lock. Where does it go?

**Routing.** Affinity only helps the hit rate. A miss replays and gives the same output, so the docs should say "should", not "must". The cache is also per process, so with `--api-server-count > 1` affinity at the load balancer isn't enough. What will the docs say there?

**Tool call IDs.**
- `choice_index` is missing. With `n > 1` the choices share a `request_id`, so two choices calling the same tool at index 0 get the same ID.
- What about a client reusing a `request_id`, e.g. across turns of an RL episode? Call 0 would get the same ID every turn.
- Where is the ID generated? `make_tool_call_id` is called from ~30 parsers but the derenderer already rewrites `tc.id` in one place when it pins IDs (`online_derenderer.py`). Doing it there keeps the change in the derender path. You can leave `kimi_k2` IDs alone.
- Same PR as the cache or separate? I'd go separate.

**Tests.** Output should match with the cache on and off across the chunked path: plain, reasoning, tool, reasoning + tool, a multi-token chunk, a finish only chunk and forced evictions midstream. Please also cover a retried chunk and a miss from different chunk boundaries over the same tokens.
