## 正文

### Report of performance regression

Not a regression; a platform-dependent cost in the default safetensors load path. Related work on other hardware: #49991 (ROCm) and #50794 (Ascend NPU).

**Summary.** On GB10, `param.copy_(loaded_weight)` from a CPU tensor backed by the checkpoint's file mmap costs ~7× more than the same copy from ordinary (anonymous) memory. The cost is paid per tensor, so it dominates weight loading for checkpoints with many small tensors. Per-expert MoE checkpoints are the main case.

Reading the tensors into anonymous memory before the copy (`clone()`, or `pread` into a fresh tensor) gives identical bytes and removes most of it.

**Micro-benchmark.** For each variant: copy every routed-expert weight (800 KiB NVFP4) and block scale (100 KiB) of one real 9 GiB shard to the GPU, one tensor at a time, as `RoutedExperts._load_w13` / `_load_w2` do. Each variant ran in a fresh process on a shard no earlier run touched, with the page cache dropped first. All variants produced byte-identical weights.

| variant | ms / tensor |
|---|---|
| A: mmap view → `param.copy_()` (current) | 1.74 |
| E: shard read into the page cache first, then A | 1.86–1.89 |
| F: `.clone()` the mmap view, then the same `copy_` | **0.23** |
| B: reused pinned bounce buffer | 0.22–0.26 |
| C: pinned staging per 3,072 tensors + GPU scatter | 0.25 |

E shows the page cache is not the issue: the copy is slow whenever its source is a file-backed page, resident or not. F shows a plain clone does as well as pinned staging. A native profile shows the time in `cuMemcpyHtoDAsync_v2` from pageable memory, with the CPU spinning in `libcuda`. I have not established why file-backed pages are slower than anonymous ones on this path. The likely place is the driver's pageable-copy handling on GB10's unified memory; #49991 found a related VMA-permission effect in KFD on ROCm.

**The read path, separately.** Reading one whole 9 GiB expert shard in the loader's order (`f.keys()`), CPU only, client page cache cold (checked with `mincore`), bytes identical:

| read path | time | throughput |
|---|---|---|
| mmap `get_tensor` + `.clone()` | 3.95–4.13 s | 2.2 GiB/s |
| `pread` each tensor into a fresh CPU tensor | 0.82 s | 10.9 GiB/s |

The checkpoint was on NFS over RDMA with the files in the server's RAM. mmap faults do not pipeline the way buffered reads with readahead do; that is an inference from these numbers, not a measurement of fault behavior.

**End to end.** `nvidia/Qwen3.8-Flash-Next-NVFP4` (512 experts, ~297k expert tensors), "Loading weights" for the main model, with out-of-tree patches:

| machine, base, weights on | stock | + clone in `_load_w13` / `_load_w2` | + `pread` in `safetensors_weights_iterator` (≤ 64 MiB) and 2 smaller fixes |
|---|---|---|---|
| Spark 1, preview image, NFS over RDMA (server RAM) | 450–541 s (5 boots) | 150 s | 35.5 s |
| Spark 1, v0.30.0, local NVMe | not measured | 189.5 s | 97.4 / 99.5 s |
| Spark 2, v0.29.0, local NVMe | 452 s | 242 s | not measured |
| Spark 2, v0.30.0, local NVMe | not measured | 231 s | not measured |

Spark 2 is a different machine, measured by its owner. The last column also includes an indexed expert-name lookup (#58720) and chunked `embed_tokens` / `lm_head` copies, so it is not `pread` alone. Greedy outputs were identical between each patched and unpatched run.

### Proposal to improve performance

#49991 gates a clone on ROCm behind an env var. #50794 clones every tensor on Ascend. GB10 is a third platform with the same shape of problem. Rather than a third per-vendor switch, could the default iterator hand out anonymous-memory tensors when the destination is an accelerator? Options, cheapest first:

1. Clone before the H2D copy at the consumers (`RoutedExperts._load_w13` / `_load_w2`, linear `weight_loader`s, `VocabParallelEmbedding.weight_loader`). Local, but there are many call sites.
2. `pread` small tensors into fresh CPU tensors in `safetensors_weights_iterator` instead of yielding mmap views, keeping views above a size cap. This fixes every consumer at once and is also the faster read path above. The cost is one transient CPU tensor per yielded weight.
3. Make it a load strategy (`--safetensors-load-strategy`), default per platform.

For option 2, a size cap must keep very large tensors as views. Some models serve a table from the checkpoint by mmap at runtime and must not have it read into RAM; Qwen3.8-Flash-Next's 47.7 GiB PLE table is one (#54129, #58439).

Happy to put up a PR for whichever direction maintainers prefer. I didn't want to open a third per-platform PR next to #49991 and #50794.

### hclsys · 2026-09-25

Follow-up from the second GB10, with a matched cold/warm pair this time. Short version: on my card this is a **page-fault** cost, not a pageable-memory-type cost, and the ranking inverts once the pages are resident.

**VMA type doesn't matter.** 400 x 800 KiB, every page pre-faulted (`mincore` = 1.000), timing `dst.copy_(src)` only:

```
anonymous (torch.empty)         0.021 ms/tensor
anonymous mmap                  0.021
file mmap MAP_PRIVATE           0.021
file mmap MAP_SHARED            0.021
tmpfs mmap MAP_PRIVATE          0.021
file mmap, every page COW'd     0.022
```

Anonymous and file-backed are indistinguishable, so I can't reproduce a memory-type effect on resident pages.

**Cold vs warm**, same code, same file, safetensors `get_tensor`, residency checked with `mincore`, output checksums equal:

```
                       A (mmap -> copy_)   F (clone -> copy_)
cold (resident 0.000)      4.51-4.90            0.78-0.90      A 5.8x slower
warm (resident 1.000)      0.027                0.119-0.136    A 4.4x faster
```

So the cost is in taking the faults, not in copying from file-backed memory. Reading the same bytes through `memcpy` inside `clone()` gets readahead; the same read taken as faults from inside `cuMemcpyHtoDAsync` seems not to — about 0.17 GiB/s against 0.96 GiB/s for the same file on the same disk.

That should make your E land near F, and it doesn't, so one of us has something else going on. Worth an `mincore` check on E — a 9 GiB shard over NFS may not have stayed resident between the warming read and the copy loop.

If the fault path is really the whole story there's a cheaper option than either clone or pread: **fault the view in place before the copy.** One byte per page of that tensor, no clone, no allocation:

```
A  mmap -> copy_                  4.51-4.90 ms/tensor
F  clone -> copy_                 0.78-0.90
P  touch 1 byte/page -> copy_     0.43-0.54      cold, same checksum
```

Faster than the clone and it allocates nothing, which also keeps it usable for the 47.7 GiB PLE table (#54129, #58439): page cache is reclaimable, an anonymous clone isn't. `madvise(MADV_WILLNEED)` over the whole mapping did nothing for me (4.45) — it returns immediately and doesn't populate.

One thing the warm row implies for option 1: an unconditional clone is a 4x regression for anyone whose checkpoint is already in page cache, e.g. repeat boots or several ranks reading the same shard. Probably an argument for making it conditional however it lands.

320 MiB synthetic file on local NVMe, so the absolutes are mine and only the ratios are comparable to yours.


### hclsys · 2026-09-26

Following my last comment — I went looking for where a prefault would go and found that variant E is already a shipped strategy, which I think changes what needs building here.

`safetensors_weights_iterator` has `--safetensors-load-strategy=prefetch`, and `_prefetch_checkpoint` is a plain blocking read of the whole file in blocks, i.e. exactly your E. It also auto-enables itself:

```python
if safetensors_load_strategy is None:
    if is_net_fs and fits_in_ram:
        should_prefetch = True
```

`is_net_fs` is `nfs/nfs4/lustre`. Your checkpoint is on NFS and 9 GiB shards against 128 GB, so unless `_get_fs_type` misread the mount, **prefetch was already on in your stock 450–541 s runs** — which would make your A and your E the same configuration and explain why E showed nothing. Cheap to confirm from a boot log:

```
Prefetching checkpoint files into page cache started (in background, ...)
Prefetching checkpoint files into page cache finished in %.2fs
```

If those lines are there, E isn't a control.

Two things follow, if that's what happened:

- It's started on a **daemon background thread** and nothing waits on it, so "prefetch ran" and "the pages were resident when `copy_` reached them" aren't the same claim. Worth comparing the "finished in" timestamp against when loading ended.
- On my card warming really does fix it — `A` goes 4.51-4.90 → **0.027** ms/tensor with the pages verified resident. So either your pages weren't actually resident, or GB10-on-NFS behaves differently from GB10-on-NVMe here, and those want different fixes.

Also relevant to your option list: on local NVMe prefetch is off by default and the code says so explicitly —

```
Auto-prefetch is disabled because the filesystem (%s) is not a recognized
network FS (NFS/Lustre). If you want to force prefetching, start vLLM with
--safetensors-load-strategy=prefetch.
```

which is your Spark-1-on-NVMe and Spark-2 rows. That rule keys on the filesystem, but the thing that's slow on GB10 is the consumer, not the storage. Might be that the whole fix here is a platform-aware default rather than new machinery in the iterator.

Worth measuring `--safetensors-load-strategy=prefetch` on your 297k-tensor model before writing anything — I can't, I don't have that checkpoint.

Boot A/B on the Spark with the full model (`nvidia/Qwen3.8-Flash-Next-NVFP4`, weights on NFS). The client cache was dropped before every boot and the configurations were interleaved. Only the loader changed between boots.

| loader | main "Loading weights" (s) | start to `/health` (s) | swapped out during the load (GiB) |
|---|---|---|---|
| mmap views, no fix | 443 | 549 | 5.2 |
| touch 1 byte/page of each view ≤ 64 MiB before yielding it | 26.1–26.7 | 118–119 | 2.8–2.9 |
| `pread` each tensor ≤ 64 MiB into a fresh CPU tensor | 21.9–22.5 | 103–104 | 0.01–0.24 |

Three boots each for the last two rows, one for the first. Greedy outputs (5 prompts × 400 tokens) and first-token logprobs were identical in all seven. My other out-of-tree patches are in every row. Three of them touch loading: the expert-name index (merged since as #58720), an MTP name prefilter, and a chunked clone-then-copy for the 1.2 GiB `embed_tokens` / `lm_head`, which are above the 64 MiB cap.

**Proposal:** touch the pages in the default branch of `safetensors_weights_iterator` before yielding each tensor:

```python
param = f.get_tensor(name)
if prefault and 0 < param.nbytes <= cap:
    flat = param.reshape(-1).view(torch.uint8)
    flat[::page_size].sum()
    flat[-1:].sum()
yield name, param
```

It keeps the tensors as views, allocates nothing, and covers every consumer at once. It might also cover the Ascend hang in #50794 (a copy from non-present PTEs), which I can't test. It probably wouldn't change the ROCm write-fault case in #49991.

`pread` is about 4.3 s faster on this load. I'd keep it out of this change, since it's a separate read-path optimization. One cost of prefault on this box: those boots swapped out ~2.9 GiB of other memory during the load (`pread` boots under 0.25 GiB), and vLLM then counted that as free memory for the KV cache. I haven't looked into why yet.

Two questions before I open a PR:

1. **Gate:** `current_platform.is_integrated_gpu()` or always on? On a discrete GPU the pageable copy is staged through a CPU memcpy that faults the pages anyway, so I'd expect the touch to cost close to nothing there. I haven't measured that yet.
2. **Cap:** tensors above it keep the slow path; here that's the embeddings. Without a cap, a model that serves a large checkpoint table from the mmap at runtime (the PLE in #58439) would read all of it at load time. Options are a cap plus a chunked touch in `VocabParallelEmbedding.weight_loader`, or no cap. Happy to go with whichever you prefer.


### gitbisector · 2026-09-26

On your two questions, from running the prefault snippet on a different shape: `DeepSeek-V4.1-Flash`, TP4 across four GB10s. These were load-only boots from local NVMe, with the page cache dropped before each one.

**Cap:** 64 MiB is fine here. 99% of this checkpoint's GPU-bound bytes are in tensors of 64 MiB or less, mostly 4–16 MiB.

**Gate:** what decided it for us was TP and readahead rather than integrated vs discrete.

- **With `read_ahead_kb=1024` on every node, it's a clear win: 192 s → 111 s to a loaded model (1.7x),** with every rank's weights pass at 80–88 s. That's one boot per arm; the two nodes that were at 1024 in every run matched within ~2% across three boots.
- **With the default `read_ahead_kb=128` it made our load slower: 202 s → 241 s.** Two of our nodes still had the default. The drives are identical (O_DIRECT reads 10.7 GB/s on all four), but cold page-cache reads run at the pace readahead allows:

| `read_ahead_kb` | touch 1 B/page (mmap) | buffered `dd` |
|---|---:|---:|
| 128 (default) | 1.0 GiB/s | 1.1–1.2 GB/s |
| 1024 | 6.8–8.8 GiB/s | 6.4–7.4 GB/s |

`MADV_SEQUENTIAL`, per-tensor `MADV_WILLNEED` and a 16 MiB buffered `pread` ahead of the touch all stayed under ~1.2 GiB/s at 128.

It hurt because under TP, prefault reads whole tensors. The iterator doesn't know which rows a rank keeps, so every rank faulted ~287 GiB. The unpatched path reads only the rank's slice plus readahead: 158–165 GiB at 128, 238–265 GiB at 1024. At ~1 GiB/s the extra bytes cost more than prefault saves. Raising readahead alone is not the fix either: without prefault it moved us only 202 s → 192 s, since the slower ranks now read more.

If you have local-NVMe rows, it may be worth checking `/sys/block/nvme0n1/queue/read_ahead_kb` on those Sparks.

Separately, a consumer that buffers the iterator defeats a yield-time prefault. `DeepSeek-V4.1` on main sorts the whole weight stream before copying (`vllm/models/deepseek_v41/nvidia/vl_model.py:320`), so pages are touched long before their copy, evicted, and read again: 446–532 GiB per rank, against 179–357 without prefault. On our 128 KiB nodes that made the load 2.2x slower. On the 1024 nodes it was about even despite reading 1.5x more. That one is a model-side problem.

For comparison, `--load-format fastsafetensors` reads with O_DIRECT, so readahead doesn't apply to it. On the same model, image and nodes it takes 52–58 s for the weights pass and 85–88 s to a loaded model, while still reading the full 286 GiB per rank. That's what we serve with. On unified memory it needs the budget fix in #55985 to fit (disclosure: that PR is ours).


### Willian-Zhang · 2026-09-26

Thanks, this is the case I couldn't test here. Two things on my side fit your result.

**My A/B was the best case for prefault.** It ran at TP1, from NFS with the client's `read_ahead_kb` at 16384. This Spark's local NVMe is at the default 128 (`max_hw_sectors_kb` is 128 too), and I haven't booted prefault from it. The per-tensor micro-benchmark in my earlier comment did run from that NVMe at 128, TP1, on one shard (19,714 expert tensors, cache dropped): the plain copy took 1.69–2.58 ms per tensor, touch-then-copy 0.21–0.64. So at TP1 the touch still wins at 128 KiB, at least per tensor. What turns it into a loss for you is reading the other ranks' slices.

**`pread` in the iterator has the same over-read**, since it also reads whole tensors before the rank narrows them. Under a consumer that buffers the stream it would be worse than prefault: every small tensor would stay in RAM until its copy, which at your ~287 GiB per rank would not fit. Besides the `sorted()` in `deepseek_v41/{nvidia,amd}/vl_model.py`, a few smaller models (`bert`, `roberta`, `colpali`, …) call `list(weights)`.

So I'd move the touch out of the iterator, to just before the H2D copy, on the slice the rank actually copies:

- Under TP each rank touches only its slice. For a dim-0 narrow (`w13`, column-parallel) that is one contiguous byte range. For a dim-1 narrow (`w2`, row-parallel) it touches only the pages that hold the slice, which are the pages the plain copy faults anyway.
- The touch runs right before the copy, so a consumer that buffers the stream can't have the pages evicted in between.
- Only tensors that get copied are touched. A table the model serves from the mapping (#58439) is never read, so the size cap goes away, and the embeddings, which the cap left on the slow path, are covered.

The cost is the call sites. On a checkout of main from 09-25, `.copy_(loaded_weight…)` appears 58 times in 32 files; 25 of them are in `linear.py`, `parameter.py`, `routed_experts.py`, `vocab_parallel_embedding.py` and `weight_utils.py`. A helper called there covers the common path. Model-specific loaders that copy on their own keep today's behaviour until they call it.

**Discrete GPU:** I ran the same micro-benchmark on a discrete Ada Lovelace GPU (PCIe, x86, same shard copied to a local NVMe at `read_ahead_kb=128`, three passes). There the plain copy is fastest in every state, and the touch only adds its own cost. ms per tensor:

| pages before the copy loop | view → `copy_` | touch, then `copy_` |
|---|---|---|
| not cached | 0.161–0.165 | 0.187–0.188 |
| cached, not mapped | 0.087–0.092 | 0.114–0.120 |
| cached and mapped | 0.069–0.070 | 0.093–0.096 |

The touch costs ~0.02 ms per tensor even when every page is already mapped, and from the phase split the faults cost about the same whether the touch or the copy takes them. So I'd gate it on `current_platform.is_integrated_gpu()`; that card reports `is_integrated=0`.

If the copy-site version sounds right to maintainers, I'll write it that way.
