# [PR #57451] [ROCm][DSv4][Perf] Fuse the inverse RoPE into the sparse decode reduce

## 正文

## Purpose

DeepSeek-V4 shares the ROCm sparse decode kernels with V4.1, so the reduce
epilogue added in #57435 applies here with no kernel work at all — only the
call site has to opt in. On decode-only steps the standalone
`_inverse_rope_gptj_kernel` stops launching entirely; on V4.1 that measured
201.6 us per step against 8.3 us added to the reduce, for 193 us net.

#57435 has since merged, so this is no longer stacked: the epilogue, the
`inverse_rope` switch on `rocm_inv_rope_einsum`, and the
`rocm_inverse_rope_rows_` helper are all on main. What is left here is 27 lines
in one file.

## What changes

`_forward_decode` passes the positions and the cos/sin cache into
`rocm_sparse_attn_decode`, so the rotation happens on the fp32 accumulators in
the reduce rather than in a separate pass over the already-rounded bf16 output,
and `_o_proj` no longer rotates.

Which rows still owe a rotation is batch-dependent — the reduce rotates the
decode rows it produced, prefill rows have none, and a decode path that does
not fuse rotates nothing — so `forward_mqa` settles it from the count the
decode reports, in the eager attention segment. That placement is the point:
vLLM compiles with `skip_all_guards_unsafe`, so the same value read from inside
the compiled `_o_proj` freezes at its trace-time value. In #57435 that mistake
cost 0.087 GSM8K against a 0.902 baseline, with fluent output and no error.

One thing V4 has that V4.1 does not: the FP8 `wo_a` path from #54894, whose
`inverse_rope_group_quant` rotates while it quantizes. Fusing there would
rotate twice, so the fusion is gated on `self._wo_a_fp8_weight is None` — which
is exactly the condition under which `_o_proj` takes the BF16 einsum branch
that stops rotating. When the FP8 path is active the decode is handed no
positions, returns a rotated count of 0, the settle pass is skipped, and the
path is left byte-identical to today. The gate is a load-time constant, not a
batch-dependent one, so reading it here raises none of the tracing concerns
above.

## Not a duplicate

- #57435 is the same optimization for `deepseek_v41` and was the parent of this
  branch; it has merged. The V4.1 call site cannot cover V4: they are separate
  attention classes in separate files.
- #57078 tiles the standalone inverse-RoPE kernel for sparse prefill. The two
  compose rather than collide: this PR removes the pass on decode-only steps
  and leaves prefill rows going through that same kernel, which #57078 makes
  faster.
- #54894 moved `wo_a` to an FP8 output projection in this same `_o_proj` and
  has landed. The textual conflict predicted here is resolved, and the
  correctness interaction it created is handled by the gate described above.

## Test results

Unit tests, on the branch, MI355X:

```
$ pytest tests/kernels/attention/test_rocm_triton_attn_dsv4.py -q
74 passed in 65.82s
```

Kernel equivalence, MI355X: the real decode kernels run fused, then unfused
followed by `_fused_inverse_rope_gptj`, on identical inputs, at V4's head dims
(nope 448, rope 64). NoPE lanes are bit-exact and rope lanes agree to bf16
rounding at every shape tried — `(queries, heads)` of (2, 3), (1, 128),
(8, 128), (32, 128):

| | max abs diff |
|---|---|
| NoPE lanes | 0.0 (32 queries: 4.9e-4) |
| rope lanes | <= 2.0e-3, against \|rope\| up to 0.29 |

The kernel-level evidence for the epilogue itself, including the decode trace
and the GSM8K parity runs, is in #57435, and those kernels are untouched here.

## What is not measured

**No DeepSeek-V4 model has been run end to end on this branch.** The V4.1
sibling was validated with GSM8K at 1319 questions (0.918 against a 0.901
baseline) and a decode trace, but that exercises the V4.1 call site, not this
one. What supports this change is the shared kernels plus reading the V4 path:
`forward_mqa` is the sole attention entry point for
`DeepseekV4ROCMAiterMLAAttention` (`forward_mha` is not implemented for these
model classes, so `sparse_mla_force_mqa` does not route around it), decode rows
occupy the leading rows of the output buffer, and the base class slices
`o_padded[:, :n_local_heads, :]` before `_o_proj`, which is exactly the region
rotated here.

The FP8 `wo_a` gate is likewise unmeasured on a real V4 checkpoint. It is
argued from the code — no positions in means a rotated count of 0 out, and the
settle pass is skipped — rather than from a run on FP8 weights.

That reasoning is not a substitute for an eval, and the V4.1 experience is the
reason to say so plainly: the failure mode of getting this wrong is fluent
output with wrong answers and no error anywhere. A V4 eval, on both the BF16
and FP8 `wo_a` paths, should gate this leaving draft.

## Kernel benchmark: fused vs unfused, MI355X

Measured the segment the fusion actually changes, per attention layer, on a
decode-only batch:

- **unfused** — reduce kernel, then the standalone `rocm_inverse_rope_rows_`
  over every decode row (what `main` does today for V4)
- **fused** — reduce kernel with `FUSE_INV_ROPE`, nothing after it

The main attention kernel is identical on both sides, so it cancels and is left
out. Both paths were checked to produce the same output before timing.

gfx950 / MI355X, V4 head dims (nope 448, rope 64, head_dim 512), bf16 output.
CUDA-graph replay timed with hipEvents, median of 9 reps x 50 iterations,
candidates alternated so clock drift is shared. Split counts come from the
production `_decode_gfx950_num_splits` heuristic rather than being picked by
hand. V4 has 128 attention heads, sharded by TP.

|---|---|---|---|---|---|---|---|---|---|---|
| TP1 | 128 | 1 | 32 | 3.78 | 2.03 | 5.52 | 3.80 | +0.02 | 1.72 | 1.45x |
| TP1 | 128 | 4 | 4 | 2.21 | 2.09 | 4.16 | 2.26 | +0.05 | 1.90 | 1.84x |
| TP1 | 128 | 16 | 3 | 3.41 | 2.83 | 5.99 | 3.69 | +0.29 | 2.30 | 1.62x |
| TP1 | 128 | 32 | 2 | 4.61 | 4.05 | 8.35 | 4.82 | +0.21 | 3.53 | 1.73x |
| TP1 | 128 | 64 | 1 | 6.23 | 6.42 | 11.63 | 6.03 | -0.20 | 5.60 | 1.93x |

| TP4 | 32 | 1 | 32 | 3.62 | 2.01 | 5.32 | 3.66 | +0.04 | 1.66 | 1.45x |

| TP8 | 16 | 1 | 32 | 3.61 | 1.99 | 5.45 | 3.66 | +0.04 | 1.79 | 1.49x |
| TP8 | 16 | 4 | 32 | 3.68 | 2.03 | 5.44 | 3.72 | +0.04 | 1.72 | 1.46x |

Times are microseconds per attention layer. `epilogue` is `fused - reduce`,
i.e. what the rotation costs once it rides inside the reduce.

Faster at every point measured: **1.45x to 2.10x**, saving 1.7-12.6 us per
attention layer. The mechanism is the one the PR claims. Folding the rotation
into the reduce costs roughly 0 to 0.8 us because it works on values already
live in registers, and it deletes a standalone pass costing 2.0-10.6 us that
has to re-read and re-write the entire bf16 output through HBM. The two
slightly negative `epilogue` entries are run-to-run noise at the ~0.2 us level,
not a real speedup from adding work.

The saving grows with batch size, since the standalone pass scales with row
count while the epilogue nearly does not. TP1 at q=128 is the best case at
12.6 us per layer; the low-concurrency points that dominate latency still save
1.7-1.9 us per layer.

### One note on the epilogue's numerics, not specific to this PR

`test_sparse_attn_decode_reduce_inverse_rope_epilogue` (added in #57435)
asserts the NoPE lanes come back bit-identical, "not merely close". That holds
at every split count I tried except `NUM_SPLITS=2`, where 9-17 elements out of
1.8M shift by a single bf16 ULP (<= 3.9e-3), reproducibly across trials and
independently at both TP1 q=32 and TP4 q=128 above. Every other split count
(1, 3, 4, 8, 16, 32) is exactly equal.

The epilogue is mathematically exact on those lanes — they take cos=1/sin=0 —
so this looks like codegen rather than algebra: the `FUSE_INV_ROPE` constexpr
changes FMA contraction in the split accumulation. Numerically it is nothing,
and it does not change the conclusion above. It is worth flagging only because
`NUM_SPLITS=2` is reachable from the production heuristic, so the existing
assertion is stricter than the kernel actually guarantees and could surface as
a flake if that test is ever parameterized over more shapes.
