# [Issue #58719] [Bug]: MFU/MBU counts speculative-decoding steps as prefill (`is_prefill = num_tokens > 1`)

## 正文

### Your current environment

RTX 4090 24 GB, vLLM `0.30.1rc1.dev80+g26f49e336` (nightly cu130), torch 2.13.0+cu130. `vllm/v1/metrics/` is unchanged on `main` (`73a78e6f`, 25/09).

### 🐛 Describe the bug

`ModelMetrics.get_step_perf_stats_per_gpu` classifies a running request as prefill when it has more than one scheduled token:

```python
# Cached requests are typically in decode phase (num_tokens == 1)
# unless they're doing chunked prefill (num_tokens > 1)
is_prefill = num_tokens > 1
```

With speculative decoding, every decode step of a running request schedules `1 + k` tokens, so every decode step is counted as prefill.

Measured on `Qwen/Qwen3.5-4B`, 8 concurrent requests, 8,192-token prompts, 512 output tokens, 24 requests, `VLLM_DEBUG_MFU_METRICS=1 VLLM_LOGGING_LEVEL=DEBUG`, totals of the `MFU details` debug lines (with the debug crash from #58596 patched locally; fix proposed in #58615):

| | `decode_reqs` | `prefill_reqs` | `prefill_num_tokens` |
|---|---|---|---|
| no speculative decoding | 12,264 (= 12,288 output tokens − 24 first tokens) | 144 | 196,608 (= input tokens exactly) |
| MTP, `num_speculative_tokens=2`, run 1 | **0** | 9,522 | 224,712 |
| MTP, run 2 | **0** | 9,395 | 224,331 |

Consequences, from the formulas in `perf.py`:

- Unembedding is billed for one token per "prefill" request (`num_logits_tokens = num_prefill_requests + decode_num_tokens`), but a verification step computes logits for all `1 + k` tokens. For Qwen3.5-4B each of the `k` missing tokens is `2 × hidden × vocab` ≈ 1.27 GFLOP under-billed. The config-only check matches: one 3-token step bills 21.47 GF against 24.01 GF if counted as decode, a gap of 2 × 1.27 GF.
- K/V reads are billed at the activation dtype instead of the KV-cache dtype, which matters with an fp8 KV cache.

The draft model's own forward passes are not billed either; that is the broader MTP gap mentioned in #38170 and is out of scope here.

A possible fix: subtract `len(scheduler_output.scheduled_spec_decode_tokens.get(req_id, ()))` before the `> 1` test, or classify by prompt progress rather than token count. A unit test that feeds a fake step with `num_scheduled_tokens={"r0": 3}` and `scheduled_spec_decode_tokens={"r0": [11, 12]}` fails on main today.

AI assistance (Claude Code) was used for the scripts and this report; I ran the measurements and reviewed the results.
