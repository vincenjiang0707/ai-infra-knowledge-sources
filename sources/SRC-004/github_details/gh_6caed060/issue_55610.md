# [Issue #55610] [Perf]: turboquant_k8v4 decode penalty scales with context length (-2.8% at 3k, -31% at 55k) on Ampere SM86, no speculative decoding

source: https://github.com/vllm-project/vllm/issues/55610
state: open | updated: 2026-09-26T03:36:22Z
labels: speculative-decoding, quantization

## 正文

### Summary

On a hybrid GDN + full-attention model, `--kv-cache-dtype turboquant_k8v4` costs almost nothing at short context but roughly a third of decode throughput at 55k prompt tokens, compared to `fp8_e4m3` with everything else identical. Speculative decoding is **off** in both arms, so this is separate from #53180 / #52475 / #53406 / #53410.

The KV-cache saving is real and large (+37% pool on the same GPUs), but on our hardware the throughput loss lands exactly on the long-context requests the bigger pool is meant to serve, which makes the feature unusable for us today.

### Environment

- vLLM **0.27.1**, stock (pip, no local patches)
- 2x RTX 3090 (**Ampere, SM 8.6**), TP=2, 250 W each
- Model: Qwen3.8-27B, hybrid GDN + full attention, own mixed W8/W4 GPTQ weight quant, `dtype=bfloat16`
  - 64 layers, `full_attention_interval=4` -> 16 full-attention layers (engine log: `TQ hybrid: full-attention layers [3, 7, 11, ..., 63]`)
  - `head_dim=256`, 24 query heads / 4 KV heads (**GQA group size 6**)

### Reproduction

Two servers, launched from the same script; the **only** difference in `non-default args` is `kv_cache_dtype`. Both without `speculative_config`.

```
vllm serve <model> \
  --dtype bfloat16 --tensor-parallel-size 2 --disable-custom-all-reduce \
  --max-model-len 156000 --gpu-memory-utilization 0.86 \
  --kv-cache-dtype turboquant_k8v4 \
  --enable-prefix-caching --prefix-match-unit 16 \
  --mamba-cache-mode align \
  --max-num-batched-tokens 8192 --max-num-seqs 4 \
  --long-prefill-token-threshold 2048 --enable-chunked-prefill
```

Arm C is the same line with `--kv-cache-dtype fp8_e4m3`.

Load: single stream, no concurrency, warm (same prompt run twice back to back), 800 output tokens per run, server-side sampling override (`temperature=1.0, top_p=0.95, top_k=20, presence_penalty=1.0`). Two prompt sizes: **3,216** and **55,344** prompt tokens.

### Measurements

| | `fp8_e4m3` | `turboquant_k8v4` | delta |
|---|---:|---:|---:|
| KV cache pool (engine log) | 357,622 tokens | 491,111 tokens | **+37.3%** |
| Max concurrency @156k | 2.29x | 3.15x | |
| Decode, 3,216 prompt tokens | 53.33 / 53.32 t/s | 51.83 / 51.82 t/s | **-2.8%** |
| Decode, 55,344 prompt tokens | 50.18 / 50.20 t/s | 34.58 / 34.58 t/s | **-31.1%** |

(Two runs per cell, both listed; run-to-run spread is <0.1 t/s.)

Engine log lines:

```
GPU KV cache size: 357,622 tokens | Maximum concurrency for 156,000 tokens per request: 2.29x   # fp8_e4m3
GPU KV cache size: 491,111 tokens | Maximum concurrency for 156,000 tokens per request: 3.15x   # turboquant_k8v4
```

Secondary observation (same runs, not isolated from prefix-cache state, so weaker evidence): TTFT on the warm 55k prompt was 1.05 s with TurboQuant vs 0.56 s with fp8, and 0.69 s vs 0.09 s on the warm 3k prompt.

Output quality with TurboQuant and no speculative decoding was clean: 0 degenerate responses across 8 probes plus a 42-item internal eval run.

### What we think is happening

The penalty is near-zero at 3k and ~31% at 55k, i.e. it tracks the number of quantized KV positions read back per decode step rather than a fixed per-step overhead. That is consistent with the dequant/rotation work sitting in the per-position read path of the Triton decode kernel, but we have not profiled it — this is an observation, not a diagnosis.

### Questions

1. Is a context-length-scaling decode penalty of this size expected for the current Triton decode kernels, or does it indicate a missed fast path for this geometry?
2. Our config (`k8v4`, GQA group size 6, `head_dim` 256) falls outside the dispatch gates of #53060 (K4V4-NC only) and #48235 (GQA group size 4). #40792 targets exactly `k8v4` GQA grouping and reports +16.5–27.2% on A100/H100 — would it be expected to change the *slope* here, or only the constant?
3. #40069 lists "CUDA/cutedsl kernels to replace the triton kernels" under Performance. Is that the tracking item for this, and is there a benchmark shape you would like measured on SM86? We can run more points on this hardware.

### Expected

Either the decode penalty stays roughly constant with context length, or the context-scaling behaviour is documented so the compression/throughput trade-off can be evaluated before deployment.

@karls0r Worth adding: with --max-num-seqs 4, your fp8 pool (357,622 tokens) already fits four 55,344-token requests, so at that length turboquant's +37.3% pool buys no concurrency and the -31% is pure cost. It only pays for much longer prompts.

I built Throttle for this tradeoff: $/M tokens per config, no verdict until repeats measure noise.

```sh
pipx install throttle-pro
throttle check --url http://localhost:8000 --gpu-hourly-rate <usd> --concurrency 4 --requests-per-block 4 --label fp8_e4m3
```
