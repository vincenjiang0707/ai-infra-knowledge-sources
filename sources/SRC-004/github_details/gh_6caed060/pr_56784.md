## 正文

## Purpose

Allow users of `FLASHINFER_MLA` to explicitly select FlashInfer's existing CuTe DSL decode kernel:

```bash
vllm serve MODEL --attention-backend FLASHINFER_MLA \
    --attention-config.flashinfer_mla_decode_backend cute-dsl
```

The default `auto` preserves existing dispatch, including the fallback for query-head counts unsupported by TRTLLM-GEN. Native DCP still selects CuTe DSL regardless of this option. Explicit selection delegates hardware and shape validation to FlashInfer. The option participates in the attention configuration hash; prefill and MoE are unaffected.

This exposes a kernel choice for workload-specific tuning, without changing automatic selection or adding a kernel implementation.

Related work checked on September 14:

- #54507 warms up decode autotuning before graph capture. This PR adds an explicit override and does not modify autotuning.
- #54012 introduced native DCP support; its dispatch is preserved.
- #52990 migrates the FlashInfer API call. This PR retains the current entry point and can be adapted when that migration lands.

Open PRs and issues were searched for MLA decode, CuTe DSL, and `flashinfer_mla_decode_backend`; no existing PR adding this user-selectable option was found.

### Main-branch model smoke test

Both `auto` and `cute-dsl` passed `vllm bench latency` with an internal 30B MLA model, BF16, TP1, batch size 8, input/output lengths 128/32, two warmup iterations, and three measured iterations. Compilation and CUDA Graph capture were enabled and completed successfully.

These runs used **`--moe-backend triton`**. The first attempt with the default FlashInfer TRTLLM MoE backend was stopped during its long initial compilation before inference; that default-MoE configuration is not validated by this smoke test. The smoke test checks execution, not accuracy or comparative performance.

### Model evaluation: equivalent v0.28.0 backport

These measurements are from the equivalent selector backport, **not this main-branch commit**. We evaluated an internal model with the same architecture as [kakaocorp/kanana-2-30b-a3b-thinking](https://huggingface.co/kakaocorp/kanana-2-30b-a3b-thinking), using BF16 weights on one B200 node with eight independent TP1 replicas, FlashInfer 0.6.16.post3, and no speculative decoding. AIME25 and AIME26 each ran 30 repeats, concurrently within each arm. Auto ran first, then CuTe DSL in the same allocation.

Both arms used `max_num_seqs=256`, `max_num_batched_tokens=8192`, `max_model_len=131072`, GPU memory utilization 0.9, global concurrency 2048, temperature 0.6, top-p 0.95, output cap 81920, and server seed 42.

| Metric | auto | cute-dsl |
| --- | ---: | ---: |
| Completed responses | 1,800 | 1,800 |
| Generated tokens | 44,660,699 | 45,294,627 |
| Generation makespan | 4,488.00 s | 3,600.66 s |
| Aggregate output throughput | 9,951.14 tokens/s | 12,579.54 tokens/s |
| AIME25 mean pass@1 | 86.89% | 85.56% |
| AIME26 mean pass@1 | 85.33% | 87.00% |
| Generation / grading failures | 0 / 0 | 0 / 0 |
| Output-cap hits | 173 | 172 |

Throughput is total generated tokens divided by the interval from the first request start to the last generation end, including prefill and queueing but excluding model loading. Observed throughput increased **26.4%** and generation makespan decreased **19.8%**. This is one sequential A/B comparison with sampled outputs, not a kernel-only benchmark or a general speedup guarantee. No statistical equivalence claim is made for scores.
