## 正文

### Your current environment

## Environment

- vLLM V1
- `/v1/realtime`
- Realtime audio transcription, e.g. Voxtral realtime models

### 🐛 Describe the bug

## Summary

In the `/v1/realtime` audio WebSocket API, a client can keep a realtime session alive indefinitely by leaving the WebSocket connection open and never sending `input_audio_buffer.commit` with `final: true`.

For V1 realtime streaming requests, normal non-final commits keep the request resumable and extend the session context. KV blocks are only released when the request is actually finalized, aborted, or the WebSocket connection is closed. If the client remains connected but stops sending audio/final, the server has no application-layer idle timeout to force cleanup.

## Impact

This can cause KV cache usage to grow or remain pinned for stale realtime sessions. In production, stale clients can eventually push KV cache usage to 100%, requiring manual intervention such as closing client connections or restarting pods.

## Current Behavior

A realtime audio session is cleaned up when:

- The client sends `input_audio_buffer.commit` with `final: true`
- The WebSocket disconnects
- The server detects the connection is gone and cleanup runs

However, if the WebSocket stays open and the client stops sending valid audio or never sends `final: true`, the realtime session can continue occupying engine-side resources.

Repeated non-final commits also do not represent actual new audio input, but they can keep the application-level session alive.

## Expected Behavior

Realtime audio WebSocket sessions should have a server-side idle policy. If no valid audio input is received for a configurable timeout, the server should gracefully finalize or close the session so the underlying engine request can unwind and release KV cache.

## Proposed Fix

Add an application-layer idle watchdog to `RealtimeConnection`:

- Default timeout: 30 seconds
- Configurable via an environment variable
- Reset the watchdog on valid `input_audio_buffer.append`
- Reset on non-final `commit` only when it actually starts generation
- Do not let repeated no-op commits keep the session alive
- On timeout, enqueue the final audio sentinel to gracefully finish the streaming request
- If graceful finalization does not complete within a short grace period, cancel the generation task and close the WebSocket

This gives operators a practical safety valve for stale realtime clients while preserving explicit `final=True` behavior for well-behaved clients.

### GodlyDonuts · 2026-06-27

Opened #46926 for this.

Added an idle watchdog to RealtimeConnection behind a new VLLM_REALTIME_IDLE_TIMEOUT_S env var (default 30s, 0 disables). It only resets on real activity (a valid append, or a non-final commit that actually starts generation), so repeated no-op commits won't keep a dead session alive. On timeout it sends the None sentinel so generation finishes and frees the KV cache, cancels it if it doesn't stop within a few seconds, then closes the socket. Clients that stream audio and send final=True are unaffected.

Happy to change the default or make the grace period configurable if you'd prefer.
