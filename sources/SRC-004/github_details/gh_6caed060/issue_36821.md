**Describe the issue**

vLLM fails to start on NVIDIA DGX Spark (GB10 Blackwell, sm_121) because the bundled PyTorch binary only includes compiled CUDA kernels through sm_120. The GPU is detected but no compatible kernels exist for the actual compute capability.

This is a build-time issue — the shipped .so files lack sm_121 targets. Runtime workarounds (TORCH_CUDA_ARCH_LIST, LD_LIBRARY_PATH compat libs) have no effect on prebuilt binaries.

**Error behavior**

vLLM crashes at startup during CUDA kernel initialization. PyTorch reports supported architectures up to sm_120 but the GPU requires sm_121.

**Expected behavior**

vLLM should support sm_121 (Blackwell) on aarch64, either via:
1. Official PyTorch wheels built with sm_121 + aarch64 targets
2. vLLM Docker images compiled against sm_121-capable PyTorch
3. Documentation of the supported build path for DGX Spark users

**Context**

The NVIDIA DGX Spark (and its OEM variant Acer Veriton GN100) is shipping to customers now. It is an ARM64-only device with 128 GB unified memory and sm_121 Blackwell GPU. This is becoming a common edge AI inference platform. Currently the only working local LLM serving option on this hardware is Ollama (which ships its own llama.cpp backend with Blackwell support).

**Workaround**

Use Ollama for inference. vLLM is not functional on this hardware with any available container image.

**Additional context**

- PyTorch nightly may have sm_121 support but no official aarch64 + cu130 wheels are published yet
- NVIDIA NIM containers may work but are model-limited and require enterprise licensing
- Community image avarok/vllm-dgx-spark:v11 was the closest attempt but its PyTorch build stops at sm_120

### 🐛 Describe the bug

vLLM's prebuilt container ships PyTorch binaries compiled with CUDA kernels for GPU architectures up to sm_120. The DGX Spark's Blackwell GPU requires sm_121. Since there are no matching kernels in the binary, vLLM crashes at startup. It's a compile-time gap — the fix has to come from rebuilding PyTorch and vLLM with sm_121 targets, not from runtime configuration.

### JCorners68 · 2026-03-29

## Build config fix for SM121 in published artifacts

I've opened #38484 to add SM121 (12.1) to `TORCH_CUDA_ARCH_LIST` across all build configurations (release wheels, Docker images, FlashInfer AOT).

The vLLM `CMakeLists.txt` already supports 12.1 in `CUDA_SUPPORTED_ARCHS` and all kernel-specific arch lists — the gap was purely that the build scripts never included `12.1` in `TORCH_CUDA_ARCH_LIST`, so the intersection filtering excluded it from every published artifact.

**Upstream PyTorch status:** The CMake auto-detection bug that corrupts `12.1` → `12.1(2.0)` when building PyTorch from source on SM121 hardware has fixes in review:
- pytorch/pytorch#174065
- pytorch/pytorch#173754

I independently reproduced and verified both fixes on DGX Spark (GB10, aarch64, CUDA 13.0). PyTorch cu130 aarch64 nightly wheels already ship `12.0+PTX` which provides SM121 forward compatibility via JIT.

With #38484 merged, published vLLM wheels and Docker images would include native SM121 kernels — no source builds or `--enforce-eager` workarounds needed.

### MikeWang0316tw · 2026-09-10

Measurement against the **published 0.29.0 aarch64 wheel**, in case it helps decide whether this can be closed: it is very close to working on GB10 now, but `_qutlass_C` is still an outright gap.

Environment: ASUS GX10 (DGX Spark class), GB10 sm_121, aarch64, CUDA 13.0, DGX OS 7.5.0, driver 580.173.02.

`vllm-0.29.0-cp38-abi3-manylinux_2_28_aarch64.whl` (296 MB) declares `torch==2.13.0` and `nvidia-cutlass-dsl[cu13]==4.6.2`, so it is a CUDA-13 aarch64 build and matches this machine's runtime. Per-extension SASS coverage, compared with a local source build of the same tag using `TORCH_CUDA_ARCH_LIST="12.0"`:

| extension | published wheel | local `12.0` build |
|---|---|---|
| `_C_stable_libtorch` | sm_80 sm_86 sm_87 sm_89 sm_90 sm_90a sm_100 sm_110 **sm_120** | sm_80 sm_89 sm_90 **sm_120** |
| `_moe_C_stable_libtorch` | sm_80 sm_87 sm_89 sm_90 sm_100 sm_110 **sm_120** | sm_80 **sm_120** |
| `_flashkda_C` | sm_90a sm_100 **sm_120** | **sm_120** |
| `_qutlass_C` | **sm_100 only** | **sm_120** |

Reproduce with:

```bash
python -m pip download vllm==0.29.0 --no-deps --only-binary :all:
unzip -q vllm-0.29.0-cp38-abi3-manylinux_2_28_aarch64.whl -d whl
cuobjdump -lelf whl/vllm/_qutlass_C.abi3.so | grep -oE 'sm_[0-9]+[a-z]?' | sort -u
```

Two observations:

1. **No extension in the wheel carries a literal `sm_121` cubin, and that is fine.** The `12.0f` family target is what covers GB10. Worth noting for anyone auditing this: `cuobjdump -lelf` names a family-target cubin plain `sm_120`, identical to an arch-specific one — a local build known to have emitted `Building SM12x NVFP4 for archs: 12.0f` produces `_C_stable_libtorch.abi3.N.sm_120.cubin` exactly like the wheel does. So "wheel shows sm_120, not sm_121" is not by itself evidence of a gap, and `cuobjdump` alone cannot distinguish `12.0` from `12.0f`.

2. **`_qutlass_C` is a real gap.** It ships sm_100 only, so on any SM12x device there is no compatible image for the qutlass kernels: `matmul_mxf4_bf16_tn`, `fusedQuantizeMxQuest` / `fusedQuantizeMxAbsMax`, `fusedQuantizeNvAbsMax`, and the compressed-tensors NVFP4 transform scheme (`compressed_tensors/transform/schemes/linear_qutlass_nvfp4.py`), plus `fp_quant.py`.

The failure mode this produces is a late one rather than a clean unsupported path: `vllm/platforms/cuda.py` imports `_qutlass_C` under `contextlib.suppress(ImportError)` and `_custom_ops.py` gates on `hasattr(torch.ops, "_qutlass_C")`. The shared object loads and the ops register regardless of which cubins are inside, so both checks pass and the error would only surface at kernel launch.

Scope of what I actually verified: this is a static cubin-coverage measurement. I did **not** run an MXFP4 or transform-based NVFP4 model against the wheel to observe the launch failure, so treat the runtime consequence as inferred from the missing image rather than reproduced. Models that never enter a qutlass path are unaffected — a plain compressed-tensors NVFP4 model (no transforms) served fine here, and its NVFP4 GEMMs come from `_C_stable_libtorch`, which does carry sm_120.

So from this box's perspective the answer to "can this be closed" is: mostly yes, except that a published-wheel user on SM120/SM121 silently has no qutlass kernels. That looks like it belongs with #38484, and as an arch-matrix data point for #45260.

I build from source here for unrelated reasons (a local patch), so this is not blocking me; posting the numbers since they seemed worth having on the record.
