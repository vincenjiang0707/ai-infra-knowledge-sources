# [PR #58618] [Bugfix][KV Offload] Anchor the partial-tail lookup on the full-attention prefix

source: https://github.com/vllm-project/vllm/pull/58618
state: open | updated: 2026-09-27T05:07:07Z
labels: bug, kv-connector

## 正文

## Purpose

Split out of #57216 per @orozery's review (part 1 of 2): the lookup half. The DCP store half is #58619.

`_lookup` anchors the partial-tail search on `_lookup_complete_chunks`, which requires *every* KV cache group to have a complete chunk at the anchor boundary, including the recurrent groups. A recurrent `align` group holds state only where a scheduler step ended on one of its block boundaries: in practice at the producer prompt's last full recurrent block and at its tail.

With **uniform block sizes** (dcp=1, the only shape `supports_partial_tail` admits today) the last-full-block boundary is also a full-attention chunk multiple, so that aligned row lands on the chunk grid, `complete_hit` reaches it, and the existing one-window probe finds the tail. The anchor only fails when that row is missing, e.g. evicted separately from the tail. So on `main` today this is a robustness fix.

With **mixed block sizes** -- under DCP the full-attention offload block is `dcp x` the attention block while recurrent blocks stay unsharded (12288 vs 1536 at DCP 8) -- the aligned row sits at a recurrent multiple that is essentially never a full-attention multiple. `complete_hit` is then 0 for any prompt past the first chunk, the search is capped at one window from zero, and a correctly stored tail further out is never probed although it is resident. That is the state #58619 (the DCP store side) would land in without this PR: tails get stored, but only those within one window of the complete-chunk hit are ever found -- the "#58619 only" column of the hardware table below. **This PR is the prerequisite for #58619's lookups to work.**

Instrumented `_lookup` on a replay (chunk 12288, hash 128), before the change:

```
n=12620  complete_hit=12288  complete_boundary=12288  max_boundary=12544
           boundary=12544 ALL GROUPS HIT                  <- restores
n=15136  complete_hit=0      complete_boundary=0      max_boundary=12160
           boundary=12160 group=0 MISS ... 11776 MISS     <- tail stored at 15104,
                                                            never probed
```

Fix: anchor on the full-attention complete prefix and check recurrent groups only at the candidate boundary. Following the review suggestion, the anchor is `_lookup_complete_chunks` itself restricted to the full-attention groups via a new `lookup_groups` parameter, so it honours the same `max_num_new_tokens` / `max_load_tokens` caps, deferral and being-loaded rules as the all-groups hit, and only chunks verified resident can be requested by the load path. No new lookup method.

The returned boundary is always strictly greater than the complete-chunk hit, so the change can only widen what a lookup reports, never shrink it; wherever the aligned row is on the chunk grid the anchor equals `complete_hit` and the behaviour is unchanged. The probe window stays bounded at one full-attention block.

## Test Plan

Eleven tests on the existing dcp=1 hybrid fixture (`_make_partial_tail_scheduler`: 16-token full-attention and Mamba blocks, hash 4):

```
pytest tests/v1/kv_connector/unit/offloading_connector/ -q
```

Fail on `main`, pass here (they guard the fix):
- tail found with no recurrent state at the chunk boundary (30-token prompt, tail at 28)
- the same across **two** complete chunks (46-token prompt, tail at 44) -- the production shape, where the complete-chunk anchor is 0
- the load path requests only the verified chunk keys plus the tail keys
- `_lookup_complete_chunks(lookup_groups=full_attention_groups)` returns the full-attention prefix while the default still requires every group
- `max_num_new_tokens` caps which tail the anchored search may report
- deferral while the anchor chunk is being loaded, and while it is `HIT_PENDING`

Pass on both (regression guards for what the anchor must not change):
- 0 when no tail was stored; 0 when the full-attention chunk is not resident
- the tail is preferred over an aligned recurrent state at the chunk boundary
- a tail is found after a GPU prefix hit (`num_computed_tokens = 16`)
