### 🐛 Describe the bug

When launching `moonshotai/Kimi-K3` (or a local copy of the weights) with the official `vllm/vllm-openai:kimi-k3` image on **NVIDIA A100 (Ampere, SM80)**, the engine fails during the memory profiling / dummy run stage with:
torch.AcceleratorError: CUDA error: no kernel image is available for execution on the device
The failure occurs inside the MoE router (`gate_linear.py`) while executing `output.to(self.out_dtype)`.

This strongly suggests that some Kimi-K3 specialized CUDA kernels (especially the fused MoE router / gate linear path) in the `kimi-k3` Docker image were **not compiled for compute capability 8.0**.

### Diagnosis: CUDA_ARCH_NO_KERNEL_IMAGE (90% confidence)

### Root Cause
`torch.AcceleratorError: CUDA error: no kernel image is available for execution on the device` occurs when precompiled binary extensions or fused CUDA kernels in the Docker image were built without PTX or SASS support for the target GPU compute capability. On an A100 (compute capability 8.0 / sm_80), this means the custom MoE router or FlashInfer kernels were compiled targeting only Ada (sm_89) or Hopper (sm_90).

### Immediate Troubleshooting Steps
1. **Verify Binary Architectures**: Inspect which compute capabilities are packaged into your installed extensions:
   ```bash
   python -c "import torch; print(torch.cuda.get_arch_list())"
   ```
2. **Rebuild with Native Architecture**: Force compiling for Ampere sm_80:
   ```bash
   export TORCH_CUDA_ARCH_LIST="8.0"
   pip install --no-build-isolation --force-reinstall flashinfer
   ```
3. **Use Standard vLLM Image**: Switch from the specialized container to official `vllm/vllm-openai:latest` which packages universal multi-arch binary fatbins (sm_75, sm_80, sm_89, sm_90).
