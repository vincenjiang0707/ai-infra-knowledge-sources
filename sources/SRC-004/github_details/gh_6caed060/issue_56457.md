## 正文

## Your current environment

- vLLM `0.28.1rc1.dev628+g2a02f6efe` (nightly image `vllm/vllm-openai@sha256:96b234afa2867031ad0a226b149a06483861e613e3a3083da53398d347b5ffbd`, arm64), CUDA 13, V2 model runner.
- 2× NVIDIA DGX Spark (GB10, SM121, **unified memory**, 119 GB each), TP=2 across the two nodes (Ray-less multi-node, `--nnodes 2`).
- Model: `RadixArk/Qwen3.8-Flash-Next-NVFP4` (Qwen4Exp architecture: 12 QSA sparse-attention layers with indexer, 36 GDN layers, PLE), `--kv-cache-dtype fp8`, `--max-model-len 262144`, `--max-num-batched-tokens 4096`, chunked prefill, prefix caching, MTP k=3, `cudagraph_mode FULL_DECODE_ONLY`, `gpu_memory_utilization 0.8`.
- `indexer_compress_ratio=4`, `indexer_budget=2048` (model config). KV block size on this hybrid: 3200 tokens.
- Note: we run a few local overlays on top of this nightly (fp8 KV for QSA from #55557, a refusal-direction hook), but `vllm/models/qwen4_exp/nvidia/ops/qsa_indexer.py` (the code path below) is unmodified upstream. The previous nightly we ran (`8a728663`, `0.28.1rc1.dev388`) does not show the problem with the same model, hardware and flags.

## 🐛 Describe the bug

A single 254K-token cold prefill kills the engine on GB10: the step hangs at exactly **166,400 computed tokens**, the driver logs `NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY] ... _memdescAllocInternal(pMemDesc) @ mem_desc.c:1359` on both nodes, and after 300 s the EngineCore dies with `TimeoutError: RPC call to sample_tokens timed out.` (dumped `SchedulerOutput`: `num_computed_tokens=[..., 166400]`, `num_scheduled_tokens={...: 3200}`).

Node-exporter shows each rank consuming ~9–14 GB **outside the KV pool** during the last ~60 s of the prefill (worker 13 → 4 GB available, head 9 → 0 GB), whereas on `8a728663` the same prefill leaves memory flat.

### Root cause

`qsa_select_paged_prefill` in `vllm/models/qwen4_exp/nvidia/ops/qsa_indexer.py` now sizes the indexer logits buffer by the batch's `max_seq_len`:

```python
logits_width = triton.cdiv(triton.cdiv(max_seq_len, compress_ratio), 64) * 64
logits_width = min(max(64, logits_width), page_table.shape[1] * k_cache.shape[1])
max_logits_bytes = envs.VLLM_SPARSE_INDEXER_MAX_LOGITS_MB * 1024 * 1024   # 512 MB default
rows_per_chunk = max(1, max_logits_bytes // (logits_width * 4))
...
logits = torch.empty((num_queries, logits_width), dtype=torch.float32, ...)
```

Previously (`8a728663`) the width was the fixed page-table width (`columns = page_table.shape[1] * k_cache.shape[1]`), so every chunk allocated the same 512 MB buffer and the caching allocator reused it.

With chunked prefill (3200-token chunks here) and `compress_ratio=4`, chunk *i* of a long prompt now allocates `3200 × (800·i) × 4 B = 10.24 MB × i`, a **strictly increasing** size per chunk, until 3200 rows no longer fit under the 512 MB cap: `i = 52` → `52 × 3200 = 166,400 tokens`, exactly where the engine died. The PyTorch caching allocator never finds a cached block large enough for the next request, so it `cudaMalloc`s a new one each chunk and keeps the previous ones: `Σ 10.24 MB × i (i ≤ 52) ≈ 14 GB per rank`. On a discrete GPU `cudaMalloc` would eventually fail and the allocator would flush its cache and retry; on unified-memory GB10 `cudaMalloc` keeps succeeding until the driver has nothing left, and the failure surfaces as a GPU hang (`NV_ERR_NO_MEMORY` in dmesg) instead of a Python OOM.

### Evidence

- Attempt 1 (defaults): hang at 166,400 tokens, `NV_ERR_NO_MEMORY` ×7 on the worker node at the hang time, EngineCore dead 300 s later.
- Attempt 2 (`gdn_prefill_backend=triton`, to rule out the new FlashInfer GDN prefill path on SM12x): node memory still dropping during the prefill (head 9 → 6 GB in 49 s), probe aborted by a watchdog. GDN kernel is not the cause.
- Attempt 3 (`VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=64`): the per-chunk request saturates at ~21K tokens (chunk 7) and is reused from there. Memory flat for the whole 254K prefill and for 8 concurrent 254K prompts; no errors. The cold prefill is even ~10% faster than on `8a728663` (92 s vs ~102 s single 254K prompt).

### Workaround

`VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=64` (cost: up to 8 kernel launches per chunk and layer at 166K context instead of 1).

### Suggested fix

Round `logits_width` up to coarse buckets (e.g. multiples of 16K compressed columns), or allocate the buffer once at the page-table width as before, or take it from the workspace manager, so the caching allocator can reuse one block across chunks. Any allocation whose size grows monotonically per chunk will reproduce this on unified-memory devices.

The width change is a5c9179e73, "[Qwen3.8-Flash-Next] Compact indexer logits workspace to improve
prefill efficiency" (#54915), 2026-09-04. That is five commits after 8a728663, the nightly you have
working, and the computation is still there in 2a02f6efe.

At its parent the allocation sat in the private helper `_prefill_logits`, at a fixed width, the
page-table width times the page size:

```python
    columns = page_table.shape[1] * k_cache.shape[1]
    logits = torch.empty((num_queries, columns), dtype=torch.float32, device=q.device)
```

The commit gives `qsa_select_paged_prefill` a new `max_seq_len` argument and computes the width
from it:

```python
    logits_width = triton.cdiv(triton.cdiv(max_seq_len, compress_ratio), 64) * 64
    logits_width = min(max(64, logits_width), page_table.shape[1] * k_cache.shape[1])
```

`_prefill_logits` gains it as a parameter:

```python
    logits_width: int,
```

and allocates with it:

```python
    assert 0 < logits_width <= page_table.shape[1] * k_cache.shape[1]

    logits = torch.empty(
        (num_queries, logits_width), dtype=torch.float32, device=q.device
    )
```

Neither `logits_width` nor `max_seq_len` appears anywhere in `qsa_indexer.py` at a5c9179e73^.

| cold prompt | driver figure |
|---|---|
| tool loop and decode cells up to 90k | flat |
