### baljinderhothi-cohere · 2026-09-26

dug into this for a bit, sharing what i found

i replayed the benchmark pattern on cpu through the real CPUOffloadingManager + LRU at ab35354 vs f12fe10 (64 concurrent 5 turn convos, 256 x 20K prefixes, block_size 1024), including async fs promotions, cascade pinning, and the hybrid swa group. f12fe10 came out equal or better everywhere. at ~700 cpu chunks it does 63K fs promotions vs 94K and 3.8K re-promotions vs 35K, cpu hit share stays within ~1pt, and manager overhead is negligible (~34us vs ~15us per step)

also ruled out the tiering changes, store accounting, positions getting serialized to workers, and the bisect range (ab35354 is the direct parent)

only real behavior change i found: when a request mixes gpu prefix cache hits with cpu hits, the gpu hit chunks dont get recency refreshed anymore, so a hot prefix can get evicted over a cold one. tiny effect in the replays though, so i dont think it explains ~14%

so i couldnt find it from the policy side. my guess is something only a proper run shows (fs io timing, transfer overlap, or variance)
