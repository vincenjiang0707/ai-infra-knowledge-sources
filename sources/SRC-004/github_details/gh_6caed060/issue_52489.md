### 🐛 Describe the bug

The Anthropic-compatible `/v1/messages` endpoint crashes whenever a client sends a `tool_result` content block whose `content` array includes an Anthropic `tool_reference` item. This happens organically with Claude Code sessions that have a large number of tools available (multiple MCP servers configured), where the Anthropic API's tool-search/dynamic-tool-discovery beta feature lets a tool result reference another tool by name instead of re-embedding its full definition. Once a `tool_reference` block appears anywhere in a conversation's history, every subsequent request in that conversation fails — the coding agent gets no further responses.

**Root cause:** `_convert_user_tool_result` in [`vllm/entrypoints/anthropic/serving.py`](https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/anthropic/serving.py) converts every other known item type (`text`, `image`) into a template-safe OpenAI content item, but for `tool_reference` it appends the **raw, unconverted** Anthropic-shaped block instead:

```python
elif item_type == "tool_reference":
    ref_name = item.get("tool_name") or item.get("name")
    if ref_name:
        tool_reference.append(
            {"type": "tool_reference", "name": ref_name}
        )
...
if tool_reference:
    openai_messages.append(
        {
            "role": "tool",
            "tool_call_id": block.tool_use_id or "",
            "content": tool_reference,  # <-- raw Anthropic-shaped items, never converted
        }
    )
```

That raw `{"type": "tool_reference", "name": ...}` dict is handed straight to the model's chat template as the `content` of a `tool`-role message. Most Jinja chat templates (including Qwen3's, confirmed here) only understand content items shaped like `{"type": "text", "text": ...}` or `{"type": "image"/"image_url", ...}`; anything else falls through to a catch-all `raise_exception(...)` branch, so the request fails regardless of which model is served.

### Expected behavior

`tool_reference` items inside a `tool_result` block should be converted to a template-safe content item (e.g. a `text` item describing the referenced tool), the same way `text` and `image` items already are, so the request completes successfully regardless of which chat template the served model uses.

### Suggested fix

In `_convert_user_tool_result`, convert `tool_reference` items to a `text` item instead of passing the raw block through, mirroring how `text`/`image` items are already handled:

```python
elif item_type == "tool_reference":
    ref_name = item.get("tool_name") or item.get("name")
    if ref_name:
        tool_reference.append(
            {"type": "text", "text": f"[tool reference: {ref_name}]"}
        )
```

Verified locally: this one-line change resolves the crash and `/v1/messages` requests complete normally against `unsloth/Qwen3.8-27B-NVFP4` with a conversation history containing `tool_reference` blocks.

### Additional notes

This is distinct from, but similar in spirit to, other known cases where agentic clients send content shapes that trip strict Jinja chat templates (e.g. mid-conversation system messages tripping some Qwen templates' "System message must be at the beginning" check). Those are template-author decisions vLLM can't relax; this one is squarely a vLLM conversion-layer bug, since vLLM itself is the one constructing the malformed content item — no template author could reasonably be expected to handle a client-side content type by name.

### D4rk4 · 2026-09-26

AI-assisted reproduction and validation report for the Anthropic conversion path, adding evidence here instead of opening a duplicate PR.

In vLLM 0.30.0, a `tool_result` containing `tool_reference` reaches the chat template as a nonstandard content block. With a template that rejects that block, both Anthropic token counting and message generation fail with `Unexpected item type in content.`

There is also a representation issue: `_convert_user_tool_result` emits an empty or text-only tool message, followed by another tool message with the same `tool_call_id` for the references.

A small workaround that preserves the reference names and avoids that duplicate message is to append each reference to the existing `text_parts` list:

```python
elif item_type == "tool_reference":
    ref_name = item.get("tool_name") or item.get("name")
    if ref_name:
        text_parts.append(f"[tool reference: {ref_name}]")
```

Remove the separate `tool_reference` accumulator and its final `openai_messages.append` block. The existing text join then produces one tool result per call, keeping text/reference order. Image extraction remains unchanged.

Minimal synthetic regression:

```python
from types import SimpleNamespace
from vllm.entrypoints.anthropic.serving import AnthropicServingMessages

messages = []
AnthropicServingMessages._convert_user_tool_result(
    SimpleNamespace(
        tool_use_id="test-call",
        content=[
            {"type": "text", "text": "Found one tool."},
            {"type": "tool_reference", "tool_name": "example_tool"},
        ],
    ),
    messages,
)
assert messages == [{
    "role": "tool",
    "tool_call_id": "test-call",
    "content": "Found one tool.\n[tool reference: example_tool]",
}]
```

Validation on vLLM 0.30.0:

- Before the patch, a plain-text token-count request succeeded, while the synthetic reference history failed with HTTP 400 for both token counting and generation.
- After the patch was loaded by a restarted server, both token counting and generation succeeded. A request with a reference counted more input than the same history with an empty tool result; mixed text/reference content counted more than reference-only content. The unchanged plain-text control retained its original count.
- Generation returned the expected synthetic `tool_use` name and arguments. No external tool was executed.
- A targeted converter check failed against the original source and passed against the patch, including with the installed vLLM class and native protocol objects. It covers plain text, reference-only content, mixed text/reference content, the `name` fallback, a nameless reference, preserved call IDs, and image conversion. The complete patched module also passed syntax compilation.

Scope: this addresses the shared Anthropic converter used by token counting and generation. It does not claim to fix the separate direct OpenAI content-parser path or provide a broad model-quality evaluation. All examples above are synthetic.
