# [PR #46963] [Attention] Support NVFP4 KV cache on SM8x with FlashInfer

## 正文

## Purpose

`--kv-cache-dtype nvfp4` has a paged KV write path only on SM100, where trtllm-gen provides the native store. On SM8x there is no matching write and read pair, so the dtype cannot be used there at all.

This connects the two ends: KV writes go through FlashInfer's `nvfp4_quantize_append_paged_kv_cache_with_slot_mapping`, and the same pages are read back by the native paged-attention wrapper, which is already the decode kernel on SM8x. Queries stay in model dtype on that path and FP8 queries remain on trtllm-gen, which extends the gating from #47485 to the `nvfp4` branch. `validate_configuration` rejects SM90 and SM12x, whose XQA decode has no NVFP4 support, and DCP, whose prefill has no NVFP4 handling. Scale-search variants such as `nvfp4_4over6` still require the trtllm-gen store. Both FlashInfer entry points are in the pinned 0.7.0, so no version bump is needed. On the sm_80 host used for validation, KV cache capacity went from 1,446,932 to 4,805,405 tokens (3.32x).

It does not duplicate #46329 or #56550, which target the SM120/121 path; this one is SM8x only and does not enable SM12x. RFC #47684 tracks the wider work.

I used Codex and Claude while implementing and preparing this PR. I reviewed the final diff and ran the tests below.

## Test Result

The 23 CPU tests pass, and breaking each new check in the backend (the arch and DCP rejections, the dtype gate, the query dtype, the writer requirement, the page split and the view cache) fails the matching test. The GPU test writes a combined page through `do_kv_cache_update()` and compares native prefill against attention over the values that writer stored. It is unchanged from the previous revision, where it passed on sm_80, and was not rerun for this one. pre-commit passes.

MRCR on Qwen3.5-4B, 30 samples across needles 2/4/8 with prompts of 16,626 to 33,231 tokens, measured on the previous revision; the backend change is the same here:

| KV dtype | Match ratio | Prefix hit rate | n2 | n4 | n8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| auto | 0.8523 | 1.0000 | 0.9949 | 0.7987 | 0.7633 |
| nvfp4 | 0.8452 | 0.9667 | 0.8951 | 0.8773 | 0.7633 |

Only sm_80 was measured; SM86, SM89 and SM100 are untested locally.

### lesj0610 · 2026-09-12

@LucasWilkinson @pavanimajety @vadiklyutiy, could one of you take a look at the NVFP4 path here? I'd particularly like a check of `attention.py` and the FlashInfer backend.

On pre-SM100, `--kv-cache-dtype nvfp4` is missing the paged-KV write path that trtllm-gen provides on SM100. This PR uses FlashInfer's slot-mapping writer there and adds the matching prefill reader, query-dtype handling and packed-cache views. Both FlashInfer APIs are already available in the version vLLM pins.

Two details deserve a careful check:

- FP8 queries must only be used with trtllm-gen. The native FA2 path has to keep queries in model dtype. If that gate is wrong, results can change silently instead of raising an error.
- Mixed K/V head dimensions require the update and forward paths to use the same canonical packed views.

Across four tested models, NVFP4 provided roughly three times the `auto` cache capacity. One measured row went from `291,999` to `884,736` tokens with the same MRCR result on the sampled data. The full results and model-specific caveats are in the description.

I could not locally verify the SM100 path or run the OpenPanGU/MIMO V2 mixed-head cases with real weights. Sliding-window layers also still reserve full-context prefill scratch.
