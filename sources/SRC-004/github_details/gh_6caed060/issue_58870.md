# [Issue #58870] [Bug]: MRotaryEmbedding + YaRN uses 4x original_max_position_embeddings for the YaRN correction range and cache size

## 正文

### Your current environment

vLLM v0.30.0 (`vllm/vllm-openai:v0.30.0`), transformers 5.17.0. The same code is on `main` at eb0f2ca. The repro below runs on CPU.

### 🐛 Describe the bug

When `rope_parameters` contain `mrope_section` and `rope_type: "yarn"` (e.g. Qwen3.5 / Qwen3-VL with YaRN enabled for long context), `get_rope` builds an `MRotaryEmbedding` with `max_position_embeddings = original_max_position_embeddings` ([`__init__.py#L257-L260`](https://github.com/vllm-project/vllm/blob/eb0f2ca37f65e496e8c67a7497e818c8a92bae46/vllm/model_executor/layers/rotary_embedding/__init__.py#L257-L260)). `MRotaryEmbedding.__init__` multiplies it by 4 for cache headroom and passes the product to the base class as `max_position_embeddings` ([`mrope.py#L349-L353`](https://github.com/vllm-project/vllm/blob/eb0f2ca37f65e496e8c67a7497e818c8a92bae46/vllm/model_executor/layers/rotary_embedding/mrope.py#L349-L353)). The YaRN code then reads this attribute as the original context length in two places:

1. **Frequencies.** `yarn_find_correction_range` gets 4 × original ([`yarn_scaling_rope.py#L63`](https://github.com/vllm-project/vllm/blob/eb0f2ca37f65e496e8c67a7497e818c8a92bae46/vllm/model_executor/layers/rotary_embedding/yarn_scaling_rope.py#L63)). HF transformers (`_compute_yarn_parameters`, used by `Qwen3_5TextRotaryEmbedding`) uses `original_max_position_embeddings`. With rotary_dim 64 and rope_theta 1e7, the ramp moves from [14, 22] to [16, 24], and 9 of the 32 inverse frequencies no longer match HF.
2. **Cache size.** The cache has `max_position_embeddings * scaling_factor` rows ([`yarn_scaling_rope.py#L79`](https://github.com/vllm-project/vllm/blob/eb0f2ca37f65e496e8c67a7497e818c8a92bae46/vllm/model_executor/layers/rotary_embedding/yarn_scaling_rope.py#L79)), i.e. 4 × original × factor.

**Repro**

```python
import torch
from transformers import PretrainedConfig
from transformers.modeling_rope_utils import ROPE_INIT_FUNCTIONS
from vllm.config import DeviceConfig, VllmConfig, set_current_vllm_config
from vllm.model_executor.layers.rotary_embedding import get_rope

# Qwen3.5-style text config with static YaRN enabled
rope = {"rope_type": "yarn", "factor": 2.5, "original_max_position_embeddings": 262144,
        "rope_theta": 1e7, "partial_rotary_factor": 0.25,
        "mrope_section": [11, 11, 10], "mrope_interleaved": True}

hf_cfg = PretrainedConfig(hidden_size=5120, num_attention_heads=20, head_dim=256,
                          max_position_embeddings=262144, rope_parameters=rope)
hf_inv_freq, _ = ROPE_INIT_FUNCTIONS["yarn"](hf_cfg, "cpu")

with set_current_vllm_config(VllmConfig(device_config=DeviceConfig(device="cpu"))):
    emb = get_rope(head_size=256, max_position=262144, rope_parameters=rope, dtype=torch.bfloat16)
vllm_inv_freq = emb._compute_inv_freq(emb.scaling_factor)

print(type(emb).__name__, "max_position_embeddings =", emb.max_position_embeddings)
print("cos_sin_cache rows =", emb.cos_sin_cache.shape[0])
ratio = vllm_inv_freq / hf_inv_freq
print("dims where vLLM != HF:", {i: round(r, 3) for i, r in enumerate(ratio.tolist()) if abs(r - 1) > 1e-6})
```

```
MRotaryEmbedding max_position_embeddings = 1048576
cos_sin_cache rows = 2621440
dims where vLLM != HF: {15: 1.081, 16: 1.176, 17: 1.194, 18: 1.214, 19: 1.24, 20: 1.273, 21: 1.316, 22: 1.375, 23: 1.188}
```

**Impact**

- The low-frequency dimensions are interpolated less than YaRN intends. Dims 22 and 23 (wavelengths 408K and 675K tokens) complete less than one turn within the 262,144-token pretraining window. At factor 2.5 their rotation angle leaves the pretrained range from ~477K and ~552K tokens; standard YaRN keeps it in range up to 655,360 (original × factor). At factor 1.4 this starts at ~334K instead of 367K. I have not measured the end-task effect; needle retrieval still passes at 620K on a Qwen3.5-architecture 27B model.
- The cache is 4× longer than needed. Qwen3-VL-style mrope position ids never exceed the token index (an image grid of h × w tokens advances the position by max(h, w)), so 655,360 rows suffice at factor 2.5, while 2,621,440 rows (320 MiB in bf16) are allocated.

**Possible fix**

Keep `original_max_position` on `MRotaryEmbedding` and use it for the YaRN correction range, and size the cache separately. The 4× came with MRoPE + YaRN support in #25384; if the shifted ramp is intended, a comment in the code would help.


## 评论 (1)

### adimalkar · 2026-09-27

I reproduced this on current `main` (a9eafde) with transformers 5.17.0 and got the same output: `max_position_embeddings = 1048576`, 2,621,440 cache rows, and dims 15–23 off from HF by the same ratios.

As a control, the same `rope_parameters` without `mrope_section` go through `YaRNScalingRotaryEmbedding` and match HF exactly (max |Δ| = 0.0, 655,360 cache rows). So it is specific to the mRoPE path: `MRotaryEmbedding` passes `4 × max_position_embeddings` to the base class as cache headroom, and the borrowed `YaRNScalingRotaryEmbedding._compute_inv_freq` then reads that as the original context length. `yarn_find_correction_range` returns (16, 24) instead of HF's (14, 22).

I'm working on a fix: keep the original length separately and use it for the correction range, with a test against `ROPE_INIT_FUNCTIONS["yarn"]`. I'd leave the cache size out of it, since the 4× headroom is documented as intentional for Qwen2.5-VL video positions. #53964 also touches `MRotaryEmbedding`, but it still takes the correction range from the enlarged length, so it doesn't cover this.
