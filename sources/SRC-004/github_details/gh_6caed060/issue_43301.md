# [Issue #43301] [Hybrid SSM] Investigate accuracy divergence between `mamba_chunk_scan` and `selective_state_update` kernels

## 正文

## Context

PR #43186 lowered the gsm8k accuracy threshold for `ibm-granite/granite-4.0-h-tiny` under NIXL PD disagg after #42430 rerouted the D-side 1-token recompute from `mamba_chunk_scan_combined_varlen` to `selective_state_update` (SSU).

The two kernels produce different bf16 outputs due (supposedly) different reduction orders:
- `mamba_chunk_scan_combined_varlen` goes through bf16 matmul with intermediate bf16 casts (`tl.dot`)
- `selective_state_update` keeps the SSM step in fp32 throughout

As noted in [this comment](https://github.com/vllm-project/vllm/pull/43186#issuecomment-2893988543), this seems like a large accuracy drop for something meant to be algebraically equivalent.

## Goal

Investigate the kernel-level numerical divergence **in isolation** to:
1. **Quantify the magnitude**: Run both kernels on identical inputs for a single prompt (prefill + decode) and measure the output divergence (max abs diff, relative error distribution).
2. **Determine hardware dependence**: Test on at least **Ampere (A100)** and **Hopper (H100)** to see if the divergence magnitude or direction is architecture-dependent.
3. **Recommend a fix or acceptable tolerance**: Based on findings, either align the kernels' numeric behavior or document the expected tolerance.

## Reproduction Plan

- Isolate the two kernels (`mamba_chunk_scan_combined_varlen` and `selective_state_update`) with a single-prompt workload (1 prefill + N decode steps).
- Compare outputs element-wise against each other and against an fp64 reference.
- Run on Ampere (A100) and Hopper (H100) hardware.

### haosdent · 2026-05-23

I could not reproduce in A30 as well, so I add some log in CI to try to figure out what's wrong. Here is the finding so far

The TP=2 gsm8k drop is a numerical-precision bug at the **lm_head GEMM**, not in the SSM kernel itself. PR #42430 is the trigger because it changes the SSM state cache, which feeds slightly different hidden states into lm_head, but the actual sensitivity is at lm_head, downstream of anything PR #42430 touches.

### Direct evidence (CI build #67745)

Single SHA, sequential greedy decode (`NUM_CONCURRENT=1`, `GSM8K_LIMIT=50`), only variable is `VLLM_D43301_FORCE_FP32_LMHEAD={0,1}`:

|        | bf16 lm_head | fp32 lm_head |
|--------|--------------|--------------|
| TP=1   | **0.78**     | **0.76**     |
| TP=2   | **0.74**     | **0.76**     |
| ΔTP    | **0.04**     | **0.00**     |

Buildkite step: <https://buildkite.com/vllm/ci/builds/67745#019e5079-cdde-41a0-b843-b01d4348d44d>

Mechanism: L4 cuBLAS picks a different bf16 GEMM kernel for `N=vocab` (TP=1) vs `N=vocab/TP` (TP=2). Different kernel → different accumulation order → outputs differ in the last mantissa bits. When the top-1/top-2 logit gap is below bf16 ULP at that magnitude (smallest gap we observed is `1.13e-5` vs bf16 ULP `~4e-3`), the sampler argmax flips. The sampler already casts to fp32, but the bf16 rounding at the GEMM output has already destroyed the precision.

### How PR #42430 triggers it

PR #42430 reroutes 1-token D-side recompute from `chunk_scan_combined_varlen` to `selective_state_update`. A CMP shadow probe on L4 (build #67422 step <https://buildkite.com/vllm/ci/builds/67422#019e4b38-6927-423f-bdf2-0567a70d5c9d>) shows the two kernels are **not** bit-identical:

```
layer 0:  y_max=4.8e-7  state_max=9.8e-4  state_ndiff=15%
layer 1:  y_max=2.0e-3  state_ndiff=11%
layer 3:  y_max=7.8e-3
```

This `~1e-3` per-layer drift propagates through ~100 decode steps. By the time hidden states reach lm_head, they are slightly different from the pre-PR (chunk_scan) trajectory — enough to push 1-2 specific prompts past L4's narrow bf16 ULP boundary at lm_head, flipping their generated answer.

### Why H100 / A30 don't fail

The same SSU-vs-chunk_scan numerical drift exists on every HW (it's bf16 reduction order, not HW-specific). But H100/A30 cuBLAS picks the same kernel pattern for `N=vocab` and `N=vocab/2`, giving wide bf16 ULP safe zones, the drift doesn't flip any argmax. L4/Ada has a tighter ULP safe zone and the same drift just barely tips a few prompts over.

Standalone repro of the ULP-flip mechanism on any GPU (forces different bf16 reduction order via K-split): [`repro_43301_lmhead.py`](https://github.com/haosdent/vllm/blob/fix/43301-fp32-lmhead/repro_43301_lmhead.py) → 17/1024 argmax flips at bf16 vs 0/1024 at fp32 on synthetic granite-tiny shapes.
