# [PR #58703] [Platform] Add supports_v2_model_runner capability for out-of-tree platforms

## 正文

## Purpose

Platform plugins that replace the Platform/Worker/Model Runner cannot always install Triton (for example an OpenVINO backend, which is incompatible with `torch.compile`/Inductor). Today such a plugin only gets the global `HAS_TRITON` probe: `VllmConfig.use_v2_model_runner` falls back to V1 with a "Model Runner V2 requires Triton" warning, and there is no documented, supported way for the plugin to opt out.

This PR adds a small documented platform capability, addressing question 3 of #57684 ("would a small documented interface for replacement runners be an acceptable contribution"):

- Add `Platform.supports_v2_model_runner` classmethod, default `True`.
- When a platform overrides it to return `False`:
    - `VllmConfig.use_v2_model_runner` selects the V1 model runner directly, without probing for Triton and without emitting the fallback warning, so shared components (scheduler, input processor, ...) consistently use V1 semantics;
    - `VllmConfig._validate_v2_model_runner` raises a clear error if the V2 model runner is still forced (for example `VLLM_USE_V2_MODEL_RUNNER=1`, or a V2-only feature), instead of the generic Triton message.
- Document the hook in the platform plugin guide (`docs/design/plugin_system.md`).

Scope note: this only provides the interface for replacement runners. Questions 1 and 2 of #57684 (V1 runner support window, and whether the non-Triton work covers plugins that replace the runner entirely) are policy decisions for maintainers and are not answered here.
