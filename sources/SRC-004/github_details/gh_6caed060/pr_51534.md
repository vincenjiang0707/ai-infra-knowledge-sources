# [PR #51534] Fix missing q_scale fallback for FP8 KV cache

## 正文

## Purpose

Fix the missing `q_scale` fallback for quantized KV caches.

When a checkpoint provides `k_scale` and `v_scale` but omits `q_scale`, `process_weights_after_loading()` logs that it will use `k_scale`. The method previously wrote that fallback directly to `layer._q_scale`, then later recomputed `q_scale` from the still-invalid `layer.q_scale` parameter and overwrote the fallback with `1.0`.

This change preserves `k_scale` as a local fallback and applies it during the method's final, canonical `q_scale` assignment. This matters for FP8 attention backends such as FlashAttention and FlashInfer.

### spandantiwari · 2026-09-27

I believe this fixes a real, silently-wrong-output bug — thanks for picking it up. 
A couple of notes that may help reviewers weigh correctness, especially on AMD backends:

The elif placement is load-bearing for the ROCm/FNUZ path — worth a comment so it isn't "simplified" away. On FNUZ platforms, k_scale has already been doubled a few lines up (if current_platform.is_fp8_fnuz(): k_scale *= 2). By applying the fallback in a new elif fallback_q_scale is not None: branch that sits before else, you correctly avoid re-applying the ×2. If a future refactor ever moved this into the if layer.q_scale > 0.0: branch (which does q_scale *= 2), FNUZ would double-count and halve-then-mis-scale the query. Suggestion: A one-line comment noting "fallback is pre-adjusted for FNUZ; do not route through the *= 2 branch" would help protect that.

This affects both NVIDIA and AMD backends. _q_scale is consumed whenever the backend sets supports_quant_query_input=True. On ROCm that's the AITER unified-attention backend (rocm_aiter_unified_attn.py) and the AITER MLA path, both of which quantize Q with _q_scale. So FP8-KV-cache models on those backends currently get q_scale=1.0 → E4M3 saturation above 448 → degraded attention. (The ROCm Triton backend gates this to current_platform.is_cuda(), so it's unaffected.) Might be worth widening the PR description beyond "flash-attn or flashinfer" so AMD backend users know the benefit for them.

A small regression test would lock this in. The fallback path is otherwise uncovered. A CPU-only unit test that drives process_weights_after_loading with k/v scales present and q_scale omitted, asserting _q_scale resolves to k_scale (×2 when current_platform.is_fp8_fnuz()), fails on the old code and passes on this fix — happy to share a snippet if useful.
