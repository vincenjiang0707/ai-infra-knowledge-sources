Tracking issue to organize the adaptive verification support for DSpark speculative decoding

## Backend Support

Adaptive verification has a firm requirement that the attention backend must not use the CPU-side query lengths as a source-of-truth, instead using the gpu tensors (so that we can run the confidence-based assignment on the GPU without synchronizing the CPU).

Additionally, kernels must be able to support decode batches where requests have different query lengths per request.

Currently, the following backends are known to support variable lengths:
- FLASH_ATTN
- DSV4 Attention

- - CUTLASS backend of FlashInfer may need additional support to avoid the cpu query lengths


## Online Profiling

The initial version does profiling at startup to estimate the verification step time by replaying the recorded CUDA graphs. This is known to have some drift:

<img width="3240" height="972" alt="Image" src="https://github.com/user-attachments/assets/9f403fd8-5c0f-4a7d-9136-badc6626c60c" />

We want to extend this to fully online profiling in the future. However, there are some challenges that make this tricky:
- Online profiling may lead to "dead spots": one-time latency spikes make a certain batch size appear unattractive, leading to the adaptive verifier to never select that batch size, which leads to negative feedback and stale data limiting our range of profiled values. Generally there is an "exploration vs exploitation" problem here, as well as a requirement for some way to detect and eliminate outliers (such as those caused by JIT compilation)
- Variable sequence lengths make it hard to measure a single reliable estimate of execution time for a given number of tokens. In practice we will want some way to account for this: either tracking measured points in 2D (num_tokens, max_seq_len or mean_seq_len), or estimating the overhead added per-token of KV reads

## Tuning Confidence Scores

The confidence scores are not always perfectly calibrated. In particular, it seems like the deeper positions have higher variance and some bias in their expectation. The DSpark paper suggests [Sequential Temperature Scaling (STS)](https://arxiv.org/html/2607.05147v1) as an online solution to calibrating these estimates. I did not see much benefit when adding this feature, but we should experiment more thoroughly and assess the potential benefit of improved confidence estimates.

## First-Class Observability

### Exposing Timings and Adaptive-SD Metrics

Now that we are profiling different phases of the worker execution (model runner, proposer), and tracking the step time by batch size, we will want to expose these to the user for observability. This will help with performance tuning and development, as well as for monitoring of production deployments at scale. We will want to propagate the metrics to both the prometheus / frontend, as well as to the iteration-level logging feature.

We will also want some way to report our other metrics for adaptive verification: confidence success rate (mismatch between "expected" AL and "achieved" AL), performance model reliability (difference between "expected" step time and "actual" step time), etc.

### Benchmarking Compatibility

Adaptive speculative decoding will change what it means for speculative decoding to have high acceptance rate. AL is no longer a "golden" metric for success. 

As a start, this PR enables detailed, per-request and per-step speculative decoding metrics to be exposed in the OpenAI response. This can be used to report exact speculative decoding statistics and aggregated on the client to fit the use-case. https://github.com/vllm-project/vllm/pull/48915

## Scope proposal (starting minimal)

I'd like to start with a **narrow scope** to keep the PR reviewable and to avoid stepping on ongoing work:

**Metric 1: Confidence success rate.** For each step, emit the mismatch between predicted and observed acceptance. Concretely, at each step DSpark's `AdaptiveVerificationManager.get_num_tokens` computes `num_tokens_to_estimated_accepted_tokens[draft_budget]` — the confidence-model's prediction of how many drafts will be accepted at the chosen budget. Comparing that to the actual accepted count (available on the existing counting path) gives a per-step calibration error. I'd propose exposing:

- `vllm:adaptive_sd_expected_accepted_tokens_total` (counter)
- `vllm:adaptive_sd_confidence_calibration_error` (histogram of `expected − actual` per step)
- Iteration-level `SpecDecodingLogging` line addition: `Confidence calibration: mean|expected−actual|=X.YZ`

**Metric 2: Performance-model reliability.** DSpark's `cost_tables` predict step time as a function of `(num_reqs, num_target_tokens)`. Comparing the prediction at the chosen point to actual `forward_ms` per step gives a similar calibration error. Same shape as Metric 1: counter + histogram + iteration-log line.

Both metrics are additive — no changes to the verification logic in `adaptive_verification.py`, only new hooks that capture already-computed quantities and pass them to the metrics pipeline.

- Step-time-by-batch-size histogram (harder to make useful without labels — could be a follow-up)

### Suppressor72 · 2026-08-28


Context for the **GDN (Qwen3.x)** line under Backend Support TODO — plus two
defects found while e2e-validating that look relevant to the whole tracker:

The GDN capability plumbing was comparatively straightforward. #51869 has
the compatibility audit (both config-time blockers identified; GDN's decode
state path already reads per-request boundaries from device tensors), and
#53929 implements the capability design (`VARLEN_DECODE` level, GDN mismatch
declaration, manager-gate membership). It boots and runs adaptive on our
stack (SM120, 2×RTX 5090, Qwen3.8-27B-FP8 + DSpark drafter).

End-to-end validation on #53929's head surfaced two defects in machinery the
whole tracker depends on. Both are root-caused with a validated fix —
details, repro, and a fix branch the PR author can pick up are on the PR
thread: https://github.com/vllm-project/vllm/pull/53929#issuecomment-5445153817

1. **`enable_adaptive_verification` is missing from
   `SpeculativeConfig.compute_hash()`** — otherwise-matching flag-true and
   flag-false boots can share torch-compile cache dirs; on our interleaved
   stack, adaptive boots consumed stale flag=false artifacts. Cold-cache CI
   does not exercise that collision, while defect 2 escaped because the e2e
   neither proves a varlen FULL descriptor replayed nor checks output against
   a greedy oracle. One-line fix.

2. **Varlen decode descriptors over-claim their capture geometry.** The
   descriptor promises `max_query_len = 1 + num_speculative_tokens`, but the
   capture dummy spreads tokens evenly across
   `num_reqs = min(T, max_num_reqs)` requests — at small capture sizes that
   exercises 1 token where 8 are promised. Verify steps padding into such
   graphs replay corrupted output. With hash separation in place, 0/8
   concurrent generations were coherent and roughly half of single-stream
   runs corrupted — including at c=1, where no ragged batch exists. On our
   stack this was proven not specific to GDN, the spec method, trimming, or
   either model tested (dense hybrid-GDN and a non-GDN MoE), and it
   reproduces on #53929's head; the trigger is verify steps dispatched to
   varlen-keyed FULL decode graphs. The complete fix — hash separation, an
   honest descriptor ladder, a priority-layout capture dummy, and cross-DP
   request-count synchronization — validates 16/16 coherent generations with
   a greedy oracle (token-identical to static decoding through ~50 tokens),
   a DP=2 smoke test, and replay-site evidence for both ladder rungs.

Whether the already-listed varlen backends share defect 2 was the open
question, so we ran a desk audit of stock main (`b74ac0bc61`) before
posting this. **Both adaptive-reachable paths are affected by the same
claimed-vs-captured geometry gap:**

- FLASH_ATTN is conditional on main — FA3 reports `ALWAYS` (adaptive
  reaches it: **affected**); FA2/FA4 report `UNIFORM_BATCH` and are
  rejected at the gate. The tracker's blanket "FLASH_ATTN" entry is worth
  splitting.
- DSV4 FlashMLA reports `ALWAYS` (adaptive reaches it: **affected**); DSV4
  FlashInfer inherits `UNIFORM_BATCH` and is rejected.

The chain on stock main: adaptive verification requires `ALWAYS`
(adaptive_verification.py:481), forces `FULL_AND_PIECEWISE` with
`varlen_decode=True` (model_runner.py:620-632), and the shared
`cudagraph_utils.py:237-245` creates one varlen descriptor per capture size
T with `num_reqs = min(T, max_num_reqs)` and `max_query_len = 1+K` — while
`InputBatch.make_dummy`'s even spread exercises only `ceil(T/R)` per
request. For K=7 and max_num_reqs=256, T=8 captures 8×1 but claims to
accept 1×8; the actionable gap starts at T=2. With default capture sizes,
no size through the 512 cap (4 through Blackwell's 1024) ever exercises
more than 2 tokens/request at capture — the claimed window of 8 is never
captured. Runtime compatibility (`_is_compatible`) checks only
`desc.max_query_len >= batch.max_query_len` and request/token capacity —
nothing constrains replay to the captured distribution, and FA3's
AOT-metadata refresh at replay doesn't tighten it. Desk-only (high
confidence on code path; no runtime replay confirmation on FA3/DSV4 — we
can't boot DSV4 hardware). The honest-ladder + priority-dummy fix validated
on the GDN PR applies to the shared path unchanged.

One SM120 datapoint for the backend-support lines: FlashInfer's wrapper path
opts out of the device-CPU query-len mismatch (its `plan()` reads the indptr
arrays on the CPU by design), so adaptive with our production FP8-KV
configuration currently requires TRITON full-attention — fine for
short-prompt bursts (the fixed adaptive config runs 1.71× our production
DFlash2 tier configuration at c=4, 1.16× at c=8), but ~4× slower than our
production long-context path at ~49k-token contexts. Scoping the unlock:
flashinfer 0.6.17's direct XQA decode API already accepts device-ragged
sequence-length inputs, so the remaining blocker is vLLM-side (CPU-side
decode classification/mask) — consistent with this tracker's "just needs to
be plugged into vLLM" note on FlashInfer GQA; we estimate ~3–7 days for a
narrow implementation on our stack, or ~1–2 weeks for production-quality
handling of the capability and fallback cases.

Repro configs, boot/probe logs, and the full isolation-experiment chain are
available on request — we can also run runtime confirmation of the FA3
geometry finding on this hardware (we can boot FLASH_ATTN here), and are
glad to pair with anyone who can do the DSV4-side check on datacenter
GPUs.


### Suppressor72 · 2026-08-28

Following up on the FlashInfer line in this tracker: we've been running
adaptive DSpark verification end-to-end on FlashInfer (GQA via the
dedicated XQA API) on SM120 (2× RTX 5090), using a local patch that
makes the backend conditionally accept the device/CPU query-length
mismatch. This addresses the SM12x-XQA portion of the FlashInfer TODO
(SM100 TRTLLM/CUTLASS and hybrid/linear backends are not covered).

How it works:
- The backend capability method, the manager's independent mismatch
  scan, and the builder's VARLEN_DECODE cudagraph result all consult
  one shared configuration predicate (adaptive on, SM120/SM121, DCP=1,
  causal target, not forced-native). The selector and manager therefore
  reach the same answer; builder finalization additionally fails
  closed if the instantiated group cannot use dedicated XQA.
- Decode classification never reads the CPU even-distribution except
  for the provable all-widths-1 fast path; the device q_cu passes
  through untouched with the runner-resolved decode width as the fixed
  XQA bound, and anything wider than that bound routes through prefill.
- The mandatory q_seq_len>1 draft mask is a persistent, preallocated,
  device-built packed buffer (Triton kernel; binary search over device
  offsets; tail re-zeroed each launch), so it also replays safely
  under captured FULL graphs.
- Cascade is disabled for mismatch batches before any wrapper planning.

Validation on our hardware (the same ~49K-context warm-decode
harness): serving-time FULL-cudagraph replays with
device≠CPU widths (e.g. widths [6,2,1,7,0…] against a CPU
[4,4,4,4,0…] schedule) logged immediately before each replay; greedy
identity vs static was token-identical on 8/8 generations; adaptive
long-context decode moved from 32–41 tok/s (Triton) to ~82 tok/s, vs
141 static-DFlash2 / 96.6 static-DSpark on the same harness. The
remaining gap to static is the drafter (DSpark AR≈2.0 vs DFlash2
3.36) plus an adaptive width-policy trim we measured as a net loss at
c=1 — details in the patch notes.

Builds directly on #49718 (XQA decode + ragged q_cu + packed mask),
architecturally matches RFC #47839 (fixed max_q_len + device
cum_seq_lens_q), and is the GQA/XQA counterpart of #52988 (MLA/KDA
varlen under adaptive).

Code: https://github.com/Suppressor72/vllm/tree/feat/flashinfer-adaptive-mismatch
(4 commits on top of our GDN varlen lineage from #53929, which this
stacks on; happy to split or rebase as maintainers prefer.)

Scope caveats: validated on SM120 only (SM121 expected via the same
dedicated XQA API but not run); SM100 deliberately disabled; not yet
smoke-tested under DP>1 (blocked locally on a small current-generation
DSpark draft checkpoint — none published as of today).

AI-assisted implementation and review were used; I reviewed every
changed line and ran the unit matrix, CUDA-graph replay validation,
and serving benchmarks cited above on my own hardware.

### Suppressor72 · 2026-08-30

**[Design discussion] Adaptive verification beyond DSpark: DFlash2 selector scores as an acceptance-estimate provider (reference implementation on a branch)**

Adaptive verification is currently coupled to DSpark's confidence head, so DFlash2 draft users get static widths only. We've been running a provider-decoupled variant in production and think the direction is worth discussing on this tracker.

**The abstraction**: per-request acceptance estimates don't have to come from a learned head — they just have to be conditional per-position probabilities. We made the confidence feed a speculator capability, auto-selected by drafter: DSpark keeps its head; DFlash2 publishes the softmax top-1 of its realized top-k selector scores — a signal it already computes.

**Evidence on your open "Tuning Confidence Scores" item**: on Qwen3.8-27B-FP8 + the DFlash2 draft (one RTX 5090 pair, TP=2; one checkpoint; greedy + temperature-0.7 chat/essay workloads at concurrencies 1–8), the selector feature had held-out pooled AUC **0.865**, versus **0.527** for a position-history baseline. Its per-position AUCs at positions 1–5 were 0.883/0.857/0.815/0.853/0.790. A monotone calibration fitted on 4,478 training observations scored held-out AUC 0.864 / Brier 0.132; the discretized map in the reference branch scored 0.862 / 0.133. The selector is a promising acceptance signal on this checkpoint.

**Serving results** (matched harness; makespan primary): at c=1, +14.7% in the two-block P3 battery and +26.2% in the three-block adjudication battery versus static K=7. At c=4, +37% versus static K=7 and +40% versus no speculation. At c=8 burst makespan tied the tier-configured incumbent (+0.4%); varied-prompt staggered c=8 was +37%.

**Reference implementation** (RFC, not merge-ready): branch [feat/adflash-provider @ 510b0acda9](https://github.com/Suppressor72/vllm/tree/feat/adflash-provider) on our fork. It contains the provider hook, the calibrated DFlash2 selector feed, a concurrency-gated width floor, and an opt-in audit arm — with CPU-only unit tests. We'd propose a first landing of just the provider capability + raw selector scores (no calibration, no floor); each additional mechanism should be evaluated separately.

**Limitations**: evidence is from one checkpoint, one RTX 5090 pair at TP=2, and the tested workloads, temperatures, and concurrencies. The calibration is checkpoint-specific experimental data. Adaptive requests with `logprobs` also crash on the older base we tested — see our comment under Feature Compatibility below.

**Repro + triage data for the logprob item**

We hit this head-on: with adaptive verification enabled, any request with `logprobs` returns HTTP 500 and the engine dies silently (no engine-side traceback even at DEBUG; `EngineDeadError` with an empty body). Reproduced deterministically on our tested b05ae5dc-era TP=2 stack with both native DSpark-adaptive and backported DFlash2-adaptive, so the failure is not specific to the DFlash2 backport. Requests without logprobs succeeded, and static speculative decoding served logprobs on the same wheel.

A newer g99013d77d-era lineage with the rebased branch served adaptive+logprobs correctly, so the failure did not reproduce there. One relevant delta changes the rejection sampler's generated-token boundaries from stale host `cu_num_logits_np` values to device-side `cu_num_logits` under the compacted adaptive layout. Porting that boundary handling alone, in both attempted forms, did not fix the older base; at least one additional delta or deeper incompatibility remains. Happy to share the repro commands.
