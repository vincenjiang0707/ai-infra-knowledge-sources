## 正文

## Purpose

`combine_topk_swa_indices` runs V4.1's mixed-prefill path through ordinary Torch indexing. The fused Triton kernel inherited from V4 is still in the file but unused, after it misbehaved on the warmup batch. This puts prefill back on the kernel: one launch in place of the ninety elementwise and indexing ops the Torch path builds.

## What changes

The kernel needs one thing the Torch path already did — clamp both lengths at zero:

```python
topk_len = tl.maximum(tl.minimum((pos + 1) // COMPRESS_RATIO, TOP_K), 0)
swa_len = tl.maximum(tl.minimum(pos + 1, WINDOW_SIZE), 0)
```

`combined_lens` is stored unmasked, so a length derived from a negative `pos` reaches the output and the sparse prefill reads it. That is the whole kernel diff; everything else here is the wrapper calling the kernel instead of building the Torch path, plus tests.

The layers with `compress_ratio == 0` reach it with `topk == 0`, so `TOP_K` is zero there and `COMPRESS_RATIO` takes a `max(., 1)` to keep the constexpr off a `// 0` at JIT time. The Torch path divided by that zero and leaned on the clamp to discard the result.

## Tests

`tests/kernels/attention/test_rocm_triton_attn_dsv4.py` compares the kernel against the Torch path it replaces, copied over unchanged so the reference cannot drift toward the kernel, across the inputs that path accepts: `seq_len` below `query_len`, `compress_ratio == 0`, and windows 64/128/256.

```bash
pytest -q tests/kernels/attention/test_rocm_triton_attn_dsv4.py
```

```
gfx950 (MI355X)   73 passed,  0 skipped, 0 failed
gfx942 (MI300X)   61 passed, 12 skipped, 0 failed
```

61 + 12 matches the 73 collected on gfx950; the skips are the sparse decode partials that stay gfx950-only. The tests take a marker that matches what the kernel needs, so they run wherever the kernel runs rather than on gfx950 alone.

## Measurements

MI355X, TP4, `vllm/vllm-openai-rocm:nightly-cd10ed6f`. Arm A is the Torch path as shipped, arm B is this branch, nothing else differs. Each arm is a fresh server, the first repetition is discarded as process warm-up, and five are recorded.

```bash
# server, one per arm
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 \
vllm serve DeepSeek-V4.1-Flash --port 8200 \
  --tokenizer-mode deepseek_v41 --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.9 --moe-backend aiter \
  --max-model-len 65536 --max-num-seqs 16 --no-enable-prefix-caching \
  --limit-mm-per-prompt '{"image":0,"video":0}' \
  --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'

# one repetition; discard the first, record seeds 21..25
vllm bench serve --backend openai --base-url http://127.0.0.1:8200 \
  --model DeepSeek-V4.1-Flash --dataset-name random \
  --random-input-len 8192 --random-output-len 1024 \
  --num-prompts 4 --max-concurrency 1 --seed $SEED \
  --percentile-metrics ttft,tpot,e2el --metric-percentiles 90,99
```

**8192 in / 1024 out**, prefix caching off:

| metric, conc. 1 (n=5/arm) | A (Torch) | B (kernel) | delta |
| --- | --- | --- | --- |
| TTFT median (ms) | 301.0 ± 2.4 | 261.9 ± 1.9 | **−13.0 %** |
| E2E median (ms) | 9785.4 ± 5.6 | 9767.2 ± 4.8 | −0.2 % |
| total token throughput (tok/s) | 899 ± 95 | 901 ± 96 | +0.2 % (overlaps) |

TTFT has non-overlapping ranges: A [298.3, 304.8] against B [259.6, 264.4].

The TTFT saving is real and repeatable; at a thousand output tokens it amortizes away end to end, which is the honest bound on what this buys.

**Why it is faster.** Profiling `combine_topk_swa_indices` alone, four requests,
identical inputs on both paths, counting device kernels under `torch.profiler` with `ProfilerActivity.CUDA` after three warm-up calls:

| num_tokens | Torch launches | kernel launches | device time |
| --- | --- | --- | --- |
| 2048 | 90 | 2 | 286 us → 8 us |
| 8192 | 90 | 2 | 399 us → 16 us |
| 16384 | 90 | 2 | 543 us → 27 us |

The Torch launch count does not move with the token count — it is a fixed sequence of ops — which is why it shows up as fixed cost in TTFT.

**On a real workload.** An agentic multi-turn trace replay (long inputs, high
prefix reuse), same two arms, one 900 s run each — one run per arm, so this is corroboration rather than the measurement:

| | requests | TTFT median (ms) | E2E median (ms) |
| --- | --- | --- | --- |
| conc. 1, ISL p50 129k / OSL p50 345 | 103 | 417.6 → 357.3 (−14.4 %) | 2304.0 → 2208.1 (−4.2 %) |
| conc. 8, ISL p50 85k / OSL p50 257 | 285 | 285.2 → 233.6 (−18.1 %) | 1780.8 → 1585.1 (−11.0 %) |

Those are the conditions this kernel is for: long inputs, short outputs, and a prefix cache that makes the fixed launch cost a large share of what is left.

### ChuanLi1101 · 2026-09-13

A few concerns before merging:

1.Perf gain is not clear. TPOT is basically unchanged, while the TTFT improvement is based on a very small / single-run comparison. Please provide a more stable A/B result showing a repeatable gain.

2.The scope is broader than gfx950. The fused path is not gated to gfx950, but all new tests are @requires_gfx950. Either gate it to gfx950 or add coverage for the other ROCm architectures affected.

3.The num_tokens clamp changes semantics. It prevents OOB, but also changes query_len / token positions. We should clamp the iteration range without changing the metadata-derived position calculation.

4.The test reference is not fully independent. The Torch reference already includes several behaviors introduced by this PR, so both implementations could make the same mistake and still pass.

Given the additional ROCm-specific complexity, I think we should first demonstrate a clear perf benefit and tighten the correctness/coverage story.
