# [Issue #57684] [Question] Support path for platform plugins that cannot install Triton (MRV2 requires it)

state: open | updated: 2026-09-26T22:58:50Z

## 正文

### Context

We maintain a platform plugin ([vllm-openvino](https://github.com/belonghim/vllm-openvino)) that replaces the Platform, Worker and Model Runner for an OpenVINO backend. OpenVINO is incompatible with `torch.compile`/Inductor, so the plugin cannot install Triton (its install docs require `pip uninstall -y triton`). The plugin's runner consumes `vllm.v1.worker.gpu_input_batch` (`InputBatch`, `CachedRequestState`) and builds its attention metadata directly from the scheduler output.

### Observation (v0.29.0)

- `VllmConfig.use_v2_model_runner` silently falls back to the V1 runner when Triton is absent — the plugin sees `Model Runner V2 requires Triton; using the V1 model runner instead.`
- `VllmConfig._validate_v2_model_runner` raises `ValueError("Model Runner V2 requires Triton.")` when V2 is requested explicitly.

So MRV2 is currently unreachable for backends that cannot ship Triton, and such backends stay on V1 runner internals.

### Questions

1. Is there a deprecation or removal plan for the V1 model runner / `vllm.v1.worker.gpu_input_batch`? If so, what support window should plugins that use those modules plan for?
2. Does the non-Triton work (e.g. #55847 CPU torch fallbacks, #45133 Triton kernel dispatcher, #51212 pluggable V2 design) intend to cover non-CPU plugins that replace the runner entirely, or should such backends plan to stop depending on runner internals?
3. If the latter, would a small documented interface for replacement runners be an acceptable contribution, instead of plugins importing from `v1/worker/*`?

We can test V2-related changes on CPU/OpenVINO and are happy to provide feedback or help.

## 评论 (1)

### belonghim · 2026-09-26

Quick note now that #58703 (Q3) is in review: Q1 and Q2 are still open.

Q1 — V1 model runner support window: the v0.29.0 release notes have
a "⚠️ Model Runner V1 Deprecation" section stating:

> Now that Model Runner V2 is used by default, we are considering
> Model Runner V1 deprecated and are targeting v0.32 for its removal.
> We do not intend to accept any more MRV1-specific improvements or
> optimizations.

For platform plugins that ship their own worker/model runner and
cannot install Triton (so MRV2 isn't reachable), what's the intended
path after v0.32? A concrete support horizon would help plugin
maintainers plan.

Q2 — does the ongoing non-Triton effort cover plugins that replace
the runner entirely, or only the built-in runner path? If the
latter, we'd need either a documented plugin-side runner interface
or a maintained V1 runner beyond v0.32.

Not asking to relitigate Q3 — #58703 handles the immediate escape
hatch. These are the policy pieces that determine whether the
escape hatch is enough long-term.
