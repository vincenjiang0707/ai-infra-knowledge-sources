## 正文

## Purpose

Addresses #58726.

On integrated GPUs (DGX Spark / GB10), the shared weight loaders copy each checkpoint tensor to the GPU with `param.copy_(loaded_weight)` straight from the safetensors mmap view. For a contiguous, same-dtype source, PyTorch passes that pageable pointer directly to the driver copy, so the page faults happen inside the copy. On GB10 that is several times slower than faulting the same pages on the CPU first: 1.7–3.0 ms vs 0.08–0.64 ms per 800 KiB tensor in #58726. `nvidia/Qwen3.8-Flash-Next-NVFP4` has at least 140k such tensors, and its main weight load takes 452 s from NFS and 475 s from local NVMe.

This adds `copy_weight_(dst, src)` to `vllm/model_executor/utils.py`. On an integrated GPU it touches one byte per page of `src`, then runs `dst.copy_(src)`. It is used at the 26 copy sites of the shared loaders: `linear.py` (8), `parameter.py` (6), `routed_experts.py` (8), `vocab_parallel_embedding.py` (2) and `default_weight_loader` (2).

- **Gate:** `current_platform.is_integrated_gpu()` for a CUDA destination, cached per device. On a discrete Ada Lovelace GPU the same micro-benchmark shows the plain copy is fastest in every cache state, and the touch adds 0.022–0.028 ms per tensor, so it stays off there. When off, the extra checks cost ~0.46 µs per call (0.91 vs 0.45 µs for a 16-byte CPU copy), about 0.14 s per 300k tensors.
- **Only contiguous, same-dtype CPU sources are touched.** Non-contiguous or dtype-converting copies already go through a CPU temporary in PyTorch (`copy_requires_temporaries` in `aten/src/ATen/native/cuda/Copy.cu`), which faults the pages on the CPU.
- **Why at the copy site rather than in `safetensors_weights_iterator`** (discussed with @gitbisector in #58726):
  - Under TP each rank touches only the slice it copies. A prefault in the iterator read whole tensors: ~287 GiB per rank on DeepSeek-V4.1 TP4, and a slower load at the default `read_ahead_kb=128`.
  - The touch runs right before the copy, so a consumer that buffers the weight stream can't have the pages evicted in between.
  - Tensors a model serves from the mapping (#58439) are never copied, so they are never touched, and no size cap is needed.
- **Not covered:** model-specific loaders that call `.copy_()` or `.to(device)` themselves keep today's behaviour until they call the helper.
- **Measured only on GB10** (TP=1 below, TP=4 by @gitbisector). Other integrated devices, such as Jetson Orin / Thor, will take the touch path but are untested. I haven't checked what GH200 reports as `is_integrated`; if it reports 0, nothing changes there.

### Boot A/B, DGX Spark (GB10), TP=1

Nine full server boots of `nvidia/Qwen3.8-Flash-Next-NVFP4`, interleaved, with the client page cache for the checkpoint dropped before each one.

- **Build:** the image is vLLM v0.30.0 plus out-of-tree patches, not `main`. The helper is copied from this branch and applied to v0.30.0's copies of the same files (25 sites; v0.30.0's `_load_w2` has no chunk loop). It predates a cleanup that renamed the gate function and dropped a redundant `numel() > 0` check, which doesn't change behaviour here. A counting wrapper, not part of this PR, logged the gate and how many copies were touched.
- **Out-of-tree patches on in every arm:** the expert-name index (= #58720, merged), an MTP name prefilter, and the PLE table served from the mapping (never copied).
- **Storage:** NFS with the client's `read_ahead_kb` at 16384, or local NVMe at the default 128.

|---|---|---:|---:|---:|---:|
| stock | NFS | 451.8 | 36.1 | 584 | 4.4 |
| this PR (3 boots) | NFS | 25.9 / 27.0 / 28.0 | 0.8 | 124–129 | 3.6–4.3 |
| stock | NVMe | 475.2 | 31.7 | 609 | 4.2 |
| this PR (2 boots) | NVMe | 46.4 / 54.5 | 2.6–2.9 | 149–153 | 3.2–4.0 |
| *out-of-tree, for reference: `pread` tensors ≤ 64 MiB in the iterator, clone / chunked copy above that* | NFS / NVMe | 21.0 / 88.5 | 1.2 / 1.3 | 113 / 179 | 0 / 0 |

- The gate logged `cuda:0 = True` in every boot with this PR. By the counter's last line (140,000 calls), 139,965 copies (63.4 GiB) had been touched. The other 35 were copies PyTorch stages through a CPU temporary anyway.
- Greedy outputs (5 prompts × 400 tokens, temperature 0) and first-token logprobs are identical in all nine boots, and decode speed is unchanged. No accuracy eval was run: the touch only reads the source, so the loaded weights are byte-identical (unit test above).
- Swap: loading from mmap views pushes 3.2–4.4 GiB of other memory to swap on this 128 GB machine, and stock loading does it as much as this PR. The pread variant doesn't map the files and doesn't swap. vLLM counts the swapped-out memory as free when it sizes the KV cache. I haven't looked into why the kernel swaps here.
### TP=4 (from @gitbisector, [comment](https://github.com/vllm-project/vllm/pull/58868#issuecomment-5852543296))

`DeepSeek-V4.1-Flash` on four GB10s, this PR ported to a v0.28.1-based build (25 of the 26 sites), load-only boots, page cache dropped before each, arms interleaved. Times are `Model loading took` on the slowest rank.

| `read_ahead_kb` | boots | stock | this PR | read per rank vs stock |
|---|---|---:|---:|---:|
| 1024 | 3 + 3 | 192–195 s | 156–161 s (−18%) | +0–8 GiB |
| 128 | 3 + 3 | 205–207 s | 149–151 s (−27%) | +0–8 GiB |
| 1024, consumer that sorts the stream | 1 + 1 | 248 s | 225 s | +2–10 GiB |

At 128 the iterator-level prefault made this load slower (202 → 241 s) because every rank read whole tensors (~287 GiB); at the copy site each rank reads about what stock reads. Most of the gain is the slowest rank catching up: in stock, the ranks holding slices 0 and 2 lag by 25–60 s on small same-dtype slices (expert scales, FP8 attention rows). The routed experts there are `I8` loaded into `uint8` params, a converting copy that PyTorch already stages on the CPU, so the helper touches 5.6 of 72.3 GiB per rank.

### gitbisector · 2026-09-27

As promised, we ran #58868 on DeepSeek-V4.1-Flash at TP4 across four GB10s. It's ported onto our 0.28.1-based build: 25 of the 26 sites, since the chunked `_load_w2` branch isn't in that version. These were load-only boots with the page cache dropped before each, arms interleaved.

| `read_ahead_kb` | boots | stock | #58868 | read per rank vs stock |
|---|---|---|---|---|
| 1024 | 3 + 3 | 192–195 s | 156–161 s (−18%) | +0–8 GiB |
| 128 | 3 + 3 | 205–207 s | 149–151 s (−27%) | +0–8 GiB |
| 1024, consumer that sorts the stream | 1 + 1 | 248 s | 225 s | +2–10 GiB |

Times are `Model loading took` on the slowest rank. The copy site keeps the gain without the iterator version's TP over-read (~287 GiB per rank here), and it holds up under a consumer that buffers the stream.

Most of that gain comes from TP slice position, which fits the PR. In stock, ranks 0 and 2 finish 25–60 s after ranks 1 and 3. A per-slice benchmark on all four nodes shows the lag follows the slice, not the node: slices 0 and 2 load 1.3–2.2 s slower per two shards on every node. The slow part is the small same-dtype slices (the expert scales and FP8 attention rows) that the driver faults in from a cold cache. With the touch, all four slices take the same time, so the slowest rank catches up. The direct saving on ranks 1 and 3 is about 10 s.

Coverage: on this checkpoint the helper touches 5.6 of 72.3 GiB per rank. The 64.7 GiB of routed experts are stored as `I8` and loaded into `uint8` params, so the dtype gate skips them. That's correct: the converting copy already faults on the CPU, and at 128 it was faster in a micro-benchmark than touch-then-copy.

For comparison, `--load-format fastsafetensors` reads with O_DIRECT, so neither readahead nor these page faults apply to it. On the same model and nodes it loads in ~88 s against 156–161 s here. On unified memory it needs #55985 (ours) plus some fastsafetensors fixes that aren't upstream yet.


### Willian-Zhang · 2026-09-27

Thanks for running this. The 128 KiB row is the one I couldn't test: it goes from slower with the iterator prefault (202 → 241 s) to 27% faster with the copy-site touch, with the per-rank read back to stock plus 0–8 GiB.
