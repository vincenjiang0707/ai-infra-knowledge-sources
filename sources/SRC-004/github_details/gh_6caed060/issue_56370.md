## 正文

### Your current environment

- vLLM main @ 7470082f5 (2026-09-10), Python sources with the v0.29.0 precompiled kernels (`VLLM_USE_PRECOMPILED=1`); also reproduced with the v0.29.0 wheel
- torch 2.13.0+cu130, triton 3.7.1, NCCL 2.27.3
- 4x NVIDIA RTX PRO 6000 Blackwell (sm_120, 96 GB), PCIe only (no NVLink), driver 580.159.04
- Model: `Qwen/Qwen3-1.7B` (bf16), attention backend `TRITON_ATTN`

### 🐛 Describe the bug

`VLLM_BATCH_INVARIANT=1` is supposed to make outputs independent of the batch composition. With tensor parallelism it holds as long as sequence parallelism is **off**, but as soon as `pass_config.enable_sp=True` is set (or `fuse_gemm_comms=True`, which implies it), the same request produces different logprobs — and with greedy sampling different tokens — depending on how many other requests are in the batch.

Nothing in the config guards against this combination: `enable_sp` / `fuse_gemm_comms` are never checked against `VLLM_BATCH_INVARIANT` (compare the existing guards for cascade attention and the fused allreduce+RMSNorm path in `vllm/config/vllm.py`). `docs/features/batch_invariance.md` also does not mention SP / async TP.

**Measurement.** 64 prompts, greedy (`temperature=0`, `max_tokens=24`, `logprobs=1`, `ignore_eos=True`), `seed=0`, `max_model_len=512`, `max_num_seqs=64`, `gpu_memory_utilization=0.5`, default compilation (SP forces full-graph + `cudagraph_mode=FULL`). Each prompt is generated once alone (`bs=1`) and once with all 64 prompts in a single `generate()` call (`bs=64`); token ids and sampled-token logprobs are compared bitwise. `sp_min_token_num` is set explicitly because the SP threshold heuristic returns `None` on sm_120 (it only has SM90/SM100 buckets); on H100/B200 the heuristic enables SP automatically once `enable_sp=True`, so the same paths are hit there.

| TP | `enable_sp` | `sp_min_token_num` | tokens with different logprob | prompts whose greedy output changed | max abs logprob diff |
|---|---|---|---|---|---|
| 4 | False | – | **0 / 1536** | 0 / 64 | 0 |
| 4 | True | 64 | 1522 / 1536 | 17 / 64 | 2.98 |
| 4 | True | 1 (SP on every compile range) | 1527 / 1536 | 15 / 64 | 2.04 |
| 2 | True | 64 | 1239 / 1536 | 6 / 64 | 2.13 |
| 2 | True | 1 | 4 / 1536 | 0 / 64 | 3.1e-6 |

So:

1. Batch invariance under TP=4 is clean without SP (row 1), so this is not a general TP problem.
2. With SP it is broken both when batches straddle the SP threshold (rows 2, 4: below the threshold the graph keeps `all_reduce`, above it the `SequenceParallelismPass` rewrites `all_reduce + rms_norm` into `reduce_scatter + rms_norm + all_gather`) **and** when SP is applied to every compile range (row 3). The SP path itself is not batch-invariant.
3. TP=2 with SP everywhere is almost invariant (row 5), TP=4 is not (row 3). That is what you get if the reduction order of the reduce-scatter depends on which rank owns a token's output chunk: with 2 ranks `a+b` is commutative, with 4 ranks the ring order starting at the owner rank changes as the batch composition changes. (`reduce_scatterv` already has a deterministic root-0 reduce+scatter branch for the MoE combine under batch invariance, added in #45683 for exactly this class of problem; the plain `reduce_scatter` used by the SP pass has no such branch.)

### Proposed fix

1. Short term: when `VLLM_BATCH_INVARIANT=1`, force `pass_config.enable_sp = pass_config.fuse_gemm_comms = False` with a `warning_once`, next to the existing batch-invariance guards in `vllm/config/vllm.py`, and add a multi-GPU regression test (TP=4, prompts on both sides of `sp_min_token_num`) to `tests/v1/determinism/`. Document the limitation in `docs/features/batch_invariance.md`.
2. Longer term: keep SP under batch invariance by giving the SP pass's reduce-scatter a fixed, owner-independent reduction order (e.g. the root-0 `reduce` + `scatter` path that `reduce_scatterv` already uses for the MoE combine), then re-enable it.

I'm happy to send the PR for (1) with the test. @mosafariuk since #50505 is about custom allreduce under batch invariance and mentions AG/RS guards as a follow-up: does that follow-up already cover the SP reduce-scatter path, or should this be handled separately?

Observations:

1. **The TP=2 residual is a prefix-caching interaction, not a second numerical effect in the SP collectives.** With prefix caching disabled, TP=2 + SP is bitwise invariant (row 4). With it enabled, the 4 differing tokens are deterministic (same positions in both repeats) and all sit in prompts whose prefix was already cached by an earlier prompt in the `bs=1` loop (my 64 prompts reuse 16 bases, so prompts ≥ 16 hit the cache): the cached-prefix path computes a different number of new tokens than the batched run, and under SP that changes the padded token count that the reduce-scatter/all-gather operate on. The attention backend only moves which 4 tokens are affected. So at TP=2 the 2-rank sum being commutative does hold, and TP=2 does not need its own reduction-order fix; the cache interaction is a separate (small) thing to keep in mind for any SP-under-batch-invariance work.
2. **NCCL algorithm selection is not the cause.** `NCCL_DEBUG_SUBSYS=TUNING` on the TP=2 SP run shows every ReduceScatter/AllGather across all message sizes (4 KiB … 32 MiB) selecting `Algo RING proto SIMPLE channel{0..0}`, i.e. the batch-invariance env pins are in effect and the collective never changes shape.
3. **TP=4 + SP is not merely batch-dependent — batched execution is not run-to-run deterministic.** With prefix caching off, two identical `bs=64` runs inside one engine differ in 1175 / 865 / 1030 of 1536 sampled-token logprobs across three separate processes (9-12 greedy sequences change, from prompt 0 / step 0 onward); `bs=16` repeats differ in 121/384. In the same processes `bs=1` runs are bitwise identical to each other and across processes, and with SP off every comparison (bs=1 and bs=64, within and across processes) is bitwise identical. `NCCL_DEBUG_SUBSYS=TUNING` at TP=4 again shows every ReduceScatter/AllGather as `RING / SIMPLE / channel{0..0}`, so the NCCL side is pinned. That rules out "reduction order depends on chunk ownership" as the whole explanation at TP=4: something in the SP path is nondeterministic for multi-token batches at world size 4 while being deterministic for single-token batches and at world size 2. Two more data points on what it is and is not: (a) with `cudagraph_mode=NONE` (still compiled, SP still applied) the repeat-run difference drops from ~1000 to 118/1536 but does not vanish, so it is timing-sensitive rather than a CUDA-graph-capture artifact; (b) it grows with world size (TP=8: 1366/1536). Per prompt, the first differing step is mostly step 0 (i.e. the prefill step with ~700 scheduled tokens) but a few prompts first diverge at decode steps 1, 21 or 23, so both prefill and decode are affected. Taken together — deterministic for single-token batches and at world size 2, nondeterministic and timing-sensitive for multi-token batches at world size ≥ 4, NCCL pinned — this looks like a synchronization/ordering issue in the SP reduce-scatter → rms_norm → all-gather path (`torch.ops.vllm.reduce_scatter` / `all_gather` → `_reduce_scatter_out_place` / `_all_gather_out_place` → PyNccl on `current_stream()`) rather than a reduction-order artifact, but I have not located it in code yet; I'm noting it here so the longer-term SP fix is scoped correctly. Happy to run further discriminators (e.g. `CUDA_LAUNCH_BLOCKING=1`, or a standalone RS→AG loop outside the model) if someone has a specific hypothesis.

Raw logs and per-token mismatch positions are kept; happy to share the harness (it is a ~60-line script around `LLM.generate` with `logprobs=1`).

### rybruscoe · 2026-09-13

@LioEinaudi that four-arm layout (bs1_a, bsN_a, bs1_b, bsN_b) is the right instrument. It separates two things that usually get lumped together, and your traces already show which one is broken: repeats are stable (bs1_a vs bs1_b 0/1536) and composition is not.

Here's a mechanism that fits that exact pattern. With sequence parallelism the token axis is sharded across the TP ranks, so two things change with batch composition at once: the shape each rank's GEMM sees, and the reduce-scatter / all-gather that stitches the shards back together. A kernel can be batch-invariant on its own shard and the result still won't be, because the collective sums the partials in a grouping that depends on how many tokens are in flight. Same batch twice gives the same grouping, so repeats stay stable. Different batch, different grouping, different bits. That's why `VLLM_BATCH_INVARIANT=1` holds with SP off and breaks the moment `enable_sp` is on, and why the guard you proposed is the right fix rather than a kernel change.

One run that would pin it: SP on with TP=1. There's no collective, so if invariance comes back, the recombination is the culprit and the sharded GEMM is fine. If it still fails at TP=1, it's the per-shard tile selection.

For what it's worth we ran the same solo-vs-concurrent shape against two engines: a stock one, where concurrent greedy gave several distinct outputs across repeats, and one where every dot product accumulates into a 256-bit fixed-point register so the sum can't depend on order or grouping, where it gave one. That's measured, write-up pending, so take it as a data point and not a citation. The exact-accumulation path is a llama.cpp fork, not a vLLM patch, and it costs throughput (integer path, no tensor cores). The gate we use to check a whole graph bit for bit is here if it helps when building the SP guard's test: https://github.com/anomly-labs/llama-cpp-et/blob/main/docs/anomly/deterministic-graph.md

Disclosure: I work on that fork at Anomly.
