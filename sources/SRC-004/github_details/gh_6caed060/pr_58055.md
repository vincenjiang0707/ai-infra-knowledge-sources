## Summary
- Follow-up to #54867 (test-tethering check): wires all 17 root-level `tests/test_*.py` files that were sitting on the tethering allowlist into `misc.yaml`'s `cpu-params-env-tokenizers-parser` job, matching its existing by-name pytest pattern.
- Since these tests hadn't run in CI, running them locally surfaced two real, pre-existing bugs, now fixed:
  - `vllm/version.py::_prev_minor_version_was()` asserted `__version_tuple__[0] == 0`, but its return line already generalizes to any major version - the assert just blocked it. Removed; all parametrized test cases (including the `1.x` ones) now pass.
  - `test_zen_cpu_platform_detection.py`'s 3 `caplog`-based tests never saw log output because `vllm/logger.py` configures the `"vllm"` logger with `propagate=False`, so records never reach the root logger `caplog` listens on. Added a `caplog_vllm` fixture that attaches `caplog`'s handler directly to the `"vllm"` logger.
  - Also fixed `test_no_triton_fallback` leaking a fake `HAS_TRITON=False` `vllm.triton_utils` into `sys.modules` process-wide (unlike its sibling helper `_has_triton_for_backends`, it never restored the real modules it popped).
- `test_version_tuple`'s assertion was also widened from a hardcoded `len(...) in (3, 4, 5)` to `>= 3`, since `setuptools_scm` can legitimately produce a 6-element tuple (release + pre-release tag + dev-distance + git-hash all at once).
