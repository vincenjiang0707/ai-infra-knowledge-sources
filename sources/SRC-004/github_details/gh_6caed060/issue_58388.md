## 正文

> **Edited:** the original report blamed prefix caching. That was incidental. The real trigger is a large first request after startup, and the root cause is in torch-XCCL / oneCCL; details in the comments.

### Your current environment

- vLLM: `vllm/vllm-openai-xpu:v0.30.0`, and the nightly image built from main at `e97573215` (2026-09-23); both are stock images
- torch 2.13.0+xpu, vllm_xpu_kernels 0.1.14.1
- 2x Intel Arc Pro B70 (BMG-G31), TP=2, Linux 7.0.0-31-generic

### 🐛 Describe the bug

With Model Runner V2 and XPU graphs enabled at TP=2, the engine dies if the **first request after startup is a prefill of more than a few hundred tokens**. A short first request avoids it, and the engine then serves large prompts fine.

```
VLLM_XPU_ENABLE_XPU_GRAPH=1 FI_PROVIDER=shm CCL_ATL_SHM=1 \
vllm serve Qwen/Qwen3.8-27B --tensor-parallel-size 2 --dtype bfloat16 --quantization fp8 \
  --max-model-len 262144 --gpu-memory-utilization 0.93 --max-num-seqs 4 \
  --max-num-batched-tokens 8192 --attention-backend FLASH_ATTN \
  --speculative-config '{"method":"mtp","num_speculative_tokens":4}'
```
Then send one chat request of ~2k tokens as the first request.

With MTP:
```
File ".../v1/worker/gpu/spec_decode/autoregressive/speculator.py", line 593, in _fused_multi_step_decode
    self.decode_cudagraph_manager.run_fullgraph(batch_desc)

```
Without `--speculative-config`, the same request fails in a different place:
```
File ".../v1/worker/gpu/async_utils.py", line 170, in get_output
    self.copy_event.synchronize()
RuntimeError: wait method cannot be used for an event associated with a command graph.
```

| first request after startup | result |
|---|---|
| 84 or 144 tokens | OK; later requests of any size are fine too |
| ~2k, ~6k or 8.9k tokens | crash |
| same, with `VLLM_XPU_ENABLE_XPU_GRAPH=0` | OK |

The first eager all-reduce after XPU graph capture leaves the stream recording into a command graph when it's larger than roughly 4-8 MB. See the comments for the cause, a standalone repro and a fix.

### benklop · 2026-09-23

**Correction + root cause** (the title and description above are edited to match). Prefix caching isn't the trigger. The crash happens whenever the **first request after startup is a prefill of more than a few hundred tokens**. The prefix-caching test just happened to start with a ~6k-token prompt; a short request first avoids it, with or without prefix caching.

**Root cause (torch XCCL / oneCCL, not vLLM):** after an XPU graph capture, the first eager `all_reduce` above roughly 4-8 MB leaves the calling stream recording into a command graph. oneCCL chains each collective on the previous one's completion event. After a capture that event belongs to the captured graph, and the large-message path submits with an explicit dependency on it, which pulls the caller's queue into the recording. Small messages don't do this, and one small eager all-reduce first resets the chain.

V2 hits this because this model's embed all-reduce runs eagerly at the start of every step, so a large first prefill is the first collective after capture.

Standalone repro, no vLLM (2 ranks, `torchrun --nproc-per-node 2`, stock `vllm/vllm-openai-xpu:v0.30.0`):
```python
import os, torch, torch.distributed as dist
torch.xpu.set_device(int(os.environ["LOCAL_RANK"])); dist.init_process_group("xccl")
small = torch.ones(40, 5120, dtype=torch.bfloat16, device="xpu")
large = torch.ones(2000, 5120, dtype=torch.bfloat16, device="xpu")    # 20 MB; 400 rows (4 MB) is fine
s, g = torch.xpu.Stream(), torch.xpu.XPUGraph()
with torch.xpu.stream(s):
    dist.all_reduce(small); torch.xpu.synchronize()
    with torch.xpu.graph(g, stream=s):
        dist.all_reduce(small)
torch.xpu.synchronize()
with torch.xpu.stream(torch.xpu.Stream()):
    dist.all_reduce(large)
    print(torch.xpu.is_current_stream_capturing())                       # True
    g.replay()   # RuntimeError: Cannot prepare for replay during capturing stage ... Recording
```
A small eager `all_reduce` right after the capture (on any stream) makes it print `False`, and replay and synchronize then work, including after further replays.

**Fix in vLLM:** one tiny eager all-reduce on the device group at the end of `GroupCoordinator.graph_capture` on XPU, with a 2-XPU regression test, CPU unit tests and a 2-card Intel CI step. Branch: https://github.com/klopstack/vllm-intel/tree/xpu-reset-oneccl-after-graph-capture (PR to follow). On the nightly image it turns the regression test from FAILED into PASSED, and the original config (V2 + MTP + XPU graphs + prefix caching, TP=2) then serves an 8.9k-token first request with prefix caching working. The underlying behaviour probably also deserves an issue against torch-xpu-ops or oneCCL.
