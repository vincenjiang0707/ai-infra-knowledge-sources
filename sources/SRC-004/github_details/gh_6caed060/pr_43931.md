# [PR #43931] [Bugfix] V1: clear stale allowed_token_ids mask in InputBatch.condense

## 正文


## Purpose
Fixes #43894.

`InputBatch.condense()` copies `allowed_token_ids_mask_cpu_tensor` from a moved request's row into the freed index but never clears the source row. `add_request` only writes that row when the new request sets `allowed_token_ids`, so unrestricted request that later reuses the index keeps the previous request's whitelist and is sampled against a stale mask. This clears the vacated row with `fill_(False)`, the same way `remove_request` does.

### ErenAta16 · 2026-07-17 · APPROVED

Confirmed the fix is correct: `fill_(False)` matches the mask's own semantics (`False` = allowed, verified against the new test — the constrained row has `VOCAB_SIZE - 1` `True` entries and exactly one `False` at the allowed token), so clearing to all-`False` is genuinely "unrestricted," not just zeroed data that happens to look empty.

Audited the rest of `condense()` for the same bug class (copy into `empty_index` without clearing `last_req_index`, where `add_request()` only conditionally writes that field), since that's exactly the gap this PR closes for `allowed_token_ids_mask_cpu_tensor`. Nothing else in the function has it:

- `request_lora_mapping`: also copied without clearing the source row, but `add_request()` has an explicit `else: self.request_lora_mapping[req_index] = 0` branch (line 480-482) — every request gets a fresh value regardless of whether it uses LoRA, so a stale row is always overwritten before it could leak.
- `temperature_cpu`/`top_p_cpu`/`top_k_cpu`/`frequency_penalties_cpu`/`presence_penalties_cpu`/`repetition_penalties_cpu`: same story, each has exactly one unconditional write per request in `add_request()`.
- `generators` and `bad_words_token_ids`: dict-based and already correctly handled via `.pop(last_req_index, None)`, which removes the key outright rather than leaving a stale array slot.

So `allowed_token_ids_mask_cpu_tensor` is the only field in `condense()` with this leak pattern, this PR is complete on its own. Combined with #48419 (the separate `swap_states()` view-aliasing bug on the same field), both ways this mask can go stale are now covered.
