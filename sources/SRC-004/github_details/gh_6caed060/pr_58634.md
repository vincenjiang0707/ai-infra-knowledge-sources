## 正文

## Purpose

On SM100/SM103, the DSv4.1 O-projection runs four kernels per layer. At decode batch sizes the first three are latency-bound and together take 11-12 µs on GB200 (DSv4.1-Flash, TP=4):

```
before: attn_out ─▶ [Triton] inverse RoPE + per-32 FP8 quant ─▶ [DeepGEMM] fp8_einsum wo_a ─BF16─▶ [FlashInfer] MXFP8 quantize ─▶ [FlashInfer CuTe-DSL] wo_b
after:  attn_out ─▶ [FusedWoAKernel] inverse RoPE + quant + wo_a + MXFP8 quant ──────────────────────────────────────────▶ [FlashInfer CuTe-DSL] wo_b
```

This PR adds `FusedWoAKernel`, a CuTe-DSL kernel that replaces the first three and hands `wo_b` a pre-quantized `QuantizedActivation`, so `wo_b` skips its own quantize. Each cluster owns 128 `wo_a` output rows and each of its CTAs one head of K (split-K by heads per group); at TP=4 that is 128 CTAs per token tile in clusters of 8:

1. **Weight prefetch under PDL:** before `griddepcontrol.wait`, each CTA TMA-loads its 64 KiB FP8 weight slice and TMA-loads its packed weight scales, overlapping the attention kernel. The MMA warp transposes the scales into the `tcgen05.cp` layout before use. TMEM is allocated after the wait, since a PDL predecessor may still hold it.
2. **Inverse RoPE + quant into SMEM:** the CTA reads its head of the BF16 attention output, applies inverse RoPE to the last 64 dims, quantizes per 32 elements with UE8M0 scales, and writes straight into the swizzled SMEM MMA operand, with no global round trip.
3. **Pipelined block-scaled MMA:** `tcgen05` MXFP8 MMA with the weight as the 128-row operand and tokens as N, accumulating in TMEM. Each 128-wide K stage has its own mbarrier, so the MMA starts on a stage once its weights land and its activations are quantized; the last stage triggers `griddepcontrol.launch_dependents` for `wo_b`.
4. **Split-K reduce + output quant:** partials are reduced over DSMEM (each CTA reduces a subset of tokens), rounded to BF16 like the unfused `z`, and quantized to MXFP8 in FlashInfer's F8_128x4 scale layout, including the zero padding FlashInfer's quantizer writes.

The latest kernel update preloads the RoPE coefficients across tokens to overlap global loads, narrows two CTA barriers to the 128 TMEM readers, and uses `redux.sync.max.abs.f32` for output amax. Explicit `mul.rn.f32` / `fma.rn.f32` preserves the prior RoPE rounding order; split-K accumulation and BF16 rounding are unchanged.

`dsv41_o_proj(layer, attn_out, positions)`, which the FlashMLA and FlashInfer backends call directly, takes the fused path on SM100/SM103 when each group has at most 8 local heads (one portable cluster), `o_lora_rank` is a multiple of 128, `wo_a` is per-32 FP8 and `wo_b` is FlashInfer CuTe-DSL MXFP8. The pushed head supports 1–32 tokens. The local extension measured below supports 1–96 when `n_local_heads * (o_lora_rank // 128) <= 128` (DSv4.1-Flash TP4/TP8), retaining 1–32 for TP1/TP2. Other batches and unsupported layouts use `deep_gemm_fp8_o_proj`. Mega Attention retains its own output-projection path.

The extension keeps each compute tile at most 32 tokens and adds token tiles in the launch grid. For T65–96 it balances three tiles in multiples of four (24/28/32 tokens per tile). Scale stores use the global token row within the existing 128-row F8_128x4 layout; the extension preserves split-K accumulation and BF16 rounding.

The kernel follows the `VllmCuTeDSLJitKernel` warmup contract. The FlashMLA and FlashInfer SM100/SM103 backends register it at construction, and warmup compiles every token count accepted by dispatch: 32 on the pushed head, and 96 for eligible shapes in the local extension (all 96 TP4 keys compiled in 54.11 s in the earlier extension check): target graphs, DSpark draft graphs and eager batches land on different counts, so covering the whole range keeps runtime compile-free. `_wo_b_proj` keeps pre-quantized activations off GEMM-RS, which only runs from 128 tokens.

The kernel binds `amax`, `exponent` and `inv` before its output stage. vLLM imports `quack`, which rewrites `if const_expr(S) or D:` process-wide into a constexpr if; without the binding, token counts whose input stage takes the dynamic path (3, 5, 6, 7, 9, ...) fail warmup with `TYPE_UNSTABLE_JOIN` inside a server even though they compile in isolation.

Why not DeepGEMM: its 26/09 release lets `fp8_einsum` emit FP8 with packed UE8M0 scales from the GEMM epilogue, which covers only the third kernel and can only feed a DeepGEMM `wo_b`. It has no hook on the A-operand side, so the inverse RoPE + quant cannot be fused into it.

Duplicate check: searched open PRs for `wo_a`, `fused wo_a`, `DSv4.1 o_proj`, `inverse RoPE MXFP8`, `fused_inv_rope` and `o_proj cutedsl`. #57977 (draft) also targets the `wo_a` to `wo_b` handoff, but keeps `fp8_einsum`, has it emit MXFP8, and moves `wo_b` to DeepGEMM; this PR instead collapses the whole pre-`wo_b` chain into one kernel for small batches. Both touch the same call sites; if #57977 lands first, the fused kernel could emit DeepGEMM's packed scale layout for that `wo_b` instead. #58621 changes DSv4, not DSv4.1.

The fused kernel should cut decode latency at small batch sizes without changing what the model produces. The kernel microbenchmark below was rerun on the local 96-token extension based on `4f59bdde4b`, against the unfused path unchanged from merge-base `e33de821c0`; rows 97–128 were added on the PR head `813bcd4042`.
