# [Issue #58227] [Bug]: an unclosed <tool_call> opener written in prose holds the Qwen3 parser in tool state and swallows a later genuine tool call

source: https://github.com/vllm-project/vllm/issues/58227
state: open | updated: 2026-09-27T01:11:59Z
labels: tool-calling

## 正文

**Environment.** As in A (Qwen3.8-27B-NVFP4, vLLM 0.28.0, `qwen3_coder`, template sha256 `0a20a467…abab9ab`).

**Describe the bug.** When the model mentions `<tool_call>` in prose without closing it — common when it explains or demonstrates the tool-call format — the state machine stays in tool state. Everything after is consumed as that span's body, including `</think>` and including a subsequent genuine tool call, which is therefore never emitted. The client receives a call named after the *first*, quoted block and does not receive the real one.

**Frequency.** 131 of 3,600 generations (3.6%) in our suite contain unbalanced `<tool_call>` markup (openers ≠ closers); 119 of those come from a prompt that asks the model to show the markup. At least one loses a genuine call as described.

**Concrete instance.** One generation, character offsets into the decoded output:

```
 2470  <tool_call>            <- opener, never closed
 2482  <function=function_name
 2890  <tool_call>            <- second opener, never closed
 4493  </think>
 4503  <tool_call>
 4515  <function=get_weather  <- the genuine call
 4586  </tool_call>           <- closes the span opened at 2470
```

The server returned `['function_name', 'get_weather', 'function_name']`; the final `function_name` is the span opened at 2,470 and closed at 4,586, and the real `get_weather` at 4,503 is inside its body. Replaying this through `Qwen3Parser` reproduces it exactly.

**Why the adjacent work does not cover it.** #56658 / #56661 add a function-header check before committing a span; this span *has* a header (`<function=function_name`), so that check confirms it rather than rejecting it. #50986 (`validate_tool_names`) drops the outer span because `function_name` is not offered — but the genuine call is inside that span's body and is dropped with it. Neither recovers the lost call.

**Suggested direction.** Bound how far a tool span may run — a turn-boundary or `</think>` token inside an open span is strong evidence the opener was prose, not markup — or reconsider the span at `finish()` when it never closed lexically. Raw generations available.

AI assistance was used for the investigation and the measurement harness; I reviewed the findings and ran everything described here on my own hardware.

### ragulramesh1819 · 2026-09-23

Hi, I'd like to work on this. I reproduced it on current main with a unit test and checked it against the open PRs: #57553 (fenced blocks), #56661, and #50986 don't recover the genuine call in this case.

Proposed minimal fix: in qwen3_config, treat a <tool_call> that arrives while a span is still in TOOL_NAME/TOOL_ARGS as closing the open span and starting a new one. This works in streaming because nothing already emitted has to be retracted. With this change the genuine get_weather call is emitted again, and the existing Qwen/parser-engine tests pass. The quoted function_name span is still emitted, and #50986's tool-name validation would drop it.

Also closing the span at </think> would recover the reasoning text too, but it conflicts with the current tests for </think> passthrough, so I'd leave that for a follow-up unless you prefer it here. @chaunceyjiang @aarnphm does this direction sound OK?

### Pranjulcr7 · 2026-09-27

I'm contributing a positive-control case for the proposed `TOOL_NAME`/`TOOL_ARGS` restart so recovery does not truncate a legitimate argument.

```text
<tool_call><function=write_file><parameter=content>Document <tool_call> usage</parameter></function></tool_call>
```

On main `eb0f2ca`, the streaming engine preserves `Document <tool_call> usage` in the argument span. An in-memory experiment adding unconditional `TOOL_NAME`/`TOOL_ARGS` + `TOOL_START` transitions to end the old call and start a new one recovers the later `get_weather` call in the unclosed-header and unclosed-args repros, but truncates this argument to `Document `.

The result is consistent at chunk sizes 1, 7, and whole-input. Please include this case alongside the lost-call repro. Recovery needs to distinguish an opener inside a parameter value, or explicitly define a change to that format contract.

This evaluates the transition strategy described above, not a submitted implementation. Validation is limited to the real streaming engine/configuration with package-level server imports bypassed, no tokenizer, and text-only feeds. No model/server evaluation.
