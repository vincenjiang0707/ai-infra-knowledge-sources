# [Issue #58421] [Bug]: Responses API `truncation: "auto"` truncates at the token level from the left, dropping `instructions` first and cutting mid-item

source: https://github.com/vllm-project/vllm/issues/58421
state: open | updated: 2026-09-26T16:32:10Z
labels: bug

## 正文

### Your current environment

vLLM `main` (also affects the pending Harmony fixes #38143 / #39413). The field exists but was a no-op in v0.15.1.

### 🐛 Describe the bug

`truncation: "auto"` on `/v1/responses` is implemented by mapping the request to
`truncate_prompt_tokens=-1`:

- `vllm/entrypoints/openai/responses/serving.py` (main), inside `get_max_tokens(...)`:
  `truncate_prompt_tokens=(-1 if request.truncation != "disabled" else None)` — appears twice (initial request and the built-in-tools loop).
- `-1` resolves to `max_model_len` in `vllm/entrypoints/utils.py::_validate_truncation_size`, and the prompt is then cut to the **last** N tokens of the fully rendered prompt (`SamplingParams.truncate_prompt_tokens` docstring: "will use only the last k tokens from the prompt (i.e., left truncation)").

That differs from the OpenAI spec this field is meant to mirror (`openai-python`, `response_create_params.py`):

> `auto`: If the input to this Response exceeds the model's context window size, the model will truncate the response to fit the context window by **dropping items from the beginning of the conversation**.

Two consequences of the current implementation:

1. **`instructions` is discarded first.** `instructions` is a top-level parameter, not an input item, so under the spec it is never dropped. In vLLM it is rendered as the system/developer message at the head of the token sequence, so it is the first thing a left cut removes. The model then answers with no instructions while the response object still reports `truncation: "auto"`.
2. **Truncation is not item-aligned.** The cut can land in the middle of a message, or in the middle of the chat-template header, leaving the model a prompt that starts with half a message and stray template tokens.

### Expected behavior

Match the spec: drop whole items from the front of `input` until the rendered prompt fits `max_model_len - max_output_tokens`, keep `instructions` (and the final user item) intact, and never split an item. If a single item is itself too large to fit, return the existing 400 rather than silently truncating inside it.

### Suggested fix

Implement `auto` at the item level in the Responses serving path before rendering (iteratively drop `input[0]`, re-render, re-count), and stop passing `truncate_prompt_tokens=-1` for this mode. #38143 / #39413 could adopt the same helper for the Harmony path instead of adding a second token-level left cut.

- #38143, #39413 (pending Harmony fixes, both token-level left truncation)
- #37011 (structured `context_length_exceeded` error code; would help clients that opt to handle truncation themselves)

### 🐛 Describe the bug

On `/v1/responses`, `truncation: "auto"` is implemented as token-level left truncation of the fully rendered prompt (`truncate_prompt_tokens=-1`), not as the item-level "drop items from the beginning of the conversation" the OpenAI spec describes. Two visible effects:

1. `instructions` is dropped first. It is rendered as the system message at the head of the token sequence, so a left cut removes it before any input item, even though the spec treats `instructions` as a separate parameter that is never dropped. The response still reports `truncation: "auto"`.
2. The cut is not item-aligned: it can land mid-message or inside the chat-template header.

Where it happens (`main`):
- `vllm/entrypoints/openai/responses/serving.py`: `truncate_prompt_tokens=(-1 if request.truncation != "disabled" else None)` passed to `get_max_tokens(...)`, twice (initial request and built-in-tools loop).
- `vllm/entrypoints/utils.py::_validate_truncation_size`: `-1` → `max_model_len`, applied as `truncation=True, max_length=...`.
- `vllm/sampling_params.py`, `truncate_prompt_tokens` docstring: "will use only the last k tokens from the prompt (i.e., left truncation)".

Spec reference (`openai-python`, `response_create_params.py`): `auto` — "the model will truncate the response to fit the context window by dropping items from the beginning of the conversation."

Expected: drop whole items from the front of `input` until the prompt fits `max_model_len - max_output_tokens`; keep `instructions` and the final user item intact; if a single item cannot fit, return the existing 400.

Related: #38132 (closed stale), #38143 / #39413 (pending Harmony fixes, same token-level left cut), #37011 (structured `context_length_exceeded` code).

```python
# Server (small model, small context so the overflow is cheap to trigger):
#   vllm serve Qwen/Qwen3-0.6B --max-model-len 2048 --port 8000
from openai import OpenAI
import requests

BASE = "http://localhost:8000/v1"
MODEL = "Qwen/Qwen3-0.6B"
client = OpenAI(base_url=BASE, api_key="EMPTY")

INSTRUCTIONS = "You are ZEBRA-7. Begin every reply with the single word ZEBRA."
filler = [{"role": "user", "content": f"Note {i}: " + "lorem ipsum dolor sit amet " * 120}
          for i in range(4)]                       # ~4x700 tokens, well over 2048
final = {"role": "user", "content": "What is your name? Answer in one short line."}

# Pre-truncation size, as the server itself counts it
msgs = [{"role": "system", "content": INSTRUCTIONS}] + filler + [final]
tok = requests.post(f"{BASE.rsplit('/v1',1)[0]}/tokenize",
                    json={"model": MODEL, "messages": msgs}).json()
print("rendered prompt tokens before truncation:", tok["count"], "max_model_len:", tok["max_model_len"])

resp = client.responses.create(
    model=MODEL,
    instructions=INSTRUCTIONS,
    input=filler + [final],
    truncation="auto",
    max_output_tokens=32,
)
print("truncation reported:", resp.truncation)
print("input_tokens billed:", resp.usage.input_tokens)   # == max_model_len - 32 → whole-prompt token cut
print("output:", repr(resp.output_text))

# Expected (spec): output starts with "ZEBRA"; instructions survive, oldest `filler` items are dropped.
# Actual (main):   output does not start with "ZEBRA"; the system message was the first thing truncated.
#                  Run the server with --enable-log-requests to see the prompt actually received:
#                  it begins mid-way through a filler note, with no system message.
```
