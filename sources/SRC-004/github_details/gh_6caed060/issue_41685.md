### Motivation

vLLM's current Pipeline Parallelism implementation is positioned in the [official docs](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/) as a *capacity or memory* fallback:

> *"Multi-node multi-GPU using tensor parallel and pipeline parallel inference: if the model is too large for a single node, combine tensor parallelism with pipeline parallelism."*

This positioning is correct for the original PP use case, but it leaves a sizable performance opportunity on the table for **long-context disaggregated serving**, where PP on the prefill side is the right tool to (a) compress the prefill pool (fewer prefill GPUs feeding the same number of decode GPUs) and (b) hide long-context attention bubbles via micro-batched stages.

[SGLang's chunked-pipeline blog (2026-01-15)](https://www.lmsys.org/blog/2026-01-15-chunked-pipeline/) demonstrates that long-context PP needs a specific *combination* of three techniques to actually win. Reference numbers (DeepSeek-V3.1 on H20):

- **PP4 TP8 with DCK 12K → 3.31× prefill throughput** over the TP8 baseline.
- At matched GPU count (32 GPUs), **PP4 TP8 outperforms PP1 TP32 by 30.5%** with DCK, and still by 18.4% even with fixed 12K chunks — i.e. the architectural advantage is not just from dynamic chunking.
- **Strong-scaling efficiency at PP4: 82.8%** — the bubble overhead is effectively absorbed once `M ≫ P`.

vLLM today has **none** of the three pieces SGLang relies on. As a result, in our own measurements on GB300 NVL72 (DeepSeek-R1-0528-FP4, ISL=128K / OSL=1, aggregated), PP4 + chunked prefill (1,536 TPS/GPU) is *slower* than PP4 with no chunking (1,678 TPS/GPU), because the existing chunked-prefill path was designed for TP-only continuous batching ([SARATHI](https://arxiv.org/pdf/2308.16369), [DeepSpeed-FastGen Dynamic SplitFuse](https://arxiv.org/pdf/2401.08671)) and does not address PP bubble reduction.


### 🐛 Describe the bug

### Proposed feature

Add a long-context-optimized PP path with the following three components, gated behind an opt-in flag (e.g. `--pipeline-parallel-mode long-context`):

1. **Chunked Pipeline Parallelism (CPP)** — split a *single* long prompt into pipeline micro-batches that flow concurrently through stages. This is distinct from vLLM's existing chunked prefill (which targets *inter-request* decode piggybacking).
2. **Asynchronous P2P** — overlap GPU computation with stage-to-stage p2p transfers to reduce idle bubbles (today's PP path serializes compute with P2P).
3. **Dynamic Chunking (DCK)** — choose chunk size as a function of the per-request prefix length so attention runtime is roughly uniform across stages, minimizing bubbles caused by quadratic attention.

### Companion / pre-requisite

- [#40674](https://github.com/vllm-project/vllm/issues/40674) — PP + `NixlConnector` for disaggregated serving. Long-context PP is most useful on the prefill side of disagg deployments, which today cannot use PP because of the connector gap. This RFC assumes #40674 lands first or in parallel.

### Use case / context

- Model: DeepSeek-R1 (FP4) on Blackwell (GB300 NVL72), ISL=128K / OSL=8K, disaggregated.
- Goal: shrink the prefill pool via PP on prefill workers (matching the deployment pattern already validated by SGLang on the same model class) while keeping decode on TP / DP+EP. Prefill-pool compression is the largest single architectural-level gap we observe between vLLM and SGLang on GB300 long-context.
