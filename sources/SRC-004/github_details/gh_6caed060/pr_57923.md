# [PR #57923] [Bugfix][ROCm] Fix startup OOM in AITER MLA FP8 prefill workspace sizing

## 正文



## Purpose

Fixes a startup OOM on Kimi K2.5 (or similar) when using the AITER ASM MLA prefill kernel, caused by overly pessimistic bounds on the size of the required persistent metadata buffers. These sizes were subsequently passed to the workspace manager which triggered the OOM.

**Triggered by**: The AITER bump to v0.1.22post1 picked up ROCm/aiter#3606 which slightly changed the logic for workspace sizing. 

**Long term fix in AITER**: https://github.com/ROCm/aiter/pull/5759

### Why

For causal FP8 MLA the AITER backend uses a persistent kernel. It needs buffers to hold the work items to be completed by each work group. The metadata scheduler is responsible for sizing these buffers so that they are sufficiently large to handle any requests that might come in.  

The MLA metadata scheduler now emits a very loose bound. The bound is based on the assumption that every request can use max_qlen query tokens. (The actual upper bound is that the sum of query tokens equals max_num_batched_tokens). If one uses these to size the logits/attn_lse partial buffers we get huge KV reservations:

| max_num_batched_tokens | before aiter#3606 | after aiter#3606 (OOM) | this PR |
|---|---|---|---|
| 8192  | 1.88 GiB | 64.03 GiB  | 2.56 GiB |
| 16384 | 3.75 GiB | 128.03 GiB | 2.62 GiB |

**Short term fix**: Size with assumption that the total query tokens is bounded by the token budget.

**Long term fix**: AITER should give us this budget-aware max buffer size. Ticket: https://github.com/ROCm/aiter/issues/5729

- Failing AITER CI: https://github.com/ROCm/aiter/actions/runs/35502267299/job/106056017860#step:6:35
