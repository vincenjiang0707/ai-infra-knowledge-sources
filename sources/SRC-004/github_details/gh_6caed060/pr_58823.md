## 正文

## Purpose

Addresses #58647, item 6: "Images in a tool_result become a separate user message inserted between tool messages".

The Anthropic converter extracts images from `tool_result` into a separate
`user` message. With parallel tool calls, this produces
`assistant → tool → user(image) → tool`, breaking tool-result continuity
and causing some renderers to reject the conversation or drop later results.

Keep text and image parts in the corresponding `tool` message, preserving
their order and `tool_call_id`. String and text-only results retain their
existing string representation.

```text
Before:
assistant(tool_calls A, B)
tool(A, "")
user(image A)
tool(B, "result_B")

After conversion:
assistant(tool_calls A, B)
tool(A, [image A])
tool(B, "result_B")
```

Real Ministral validation exposed an additional compatibility requirement:
its v13 tokenizer rejects image chunks in tool messages with HTTP 400.

Add a compatibility adapter at the Mistral renderer boundary:

- Tokenizer v15+ keeps images in tool messages.
- For older tokenizers, collect tool-result images and place them after
  the entire consecutive tool-result group, merging them into the next
  user message when present.

This fallback preserves tool-result continuity and image input, but cannot
preserve native image-in-tool attribution on older Mistral tokenizers.

A small CPU-level regression suggestion for the renderer fallback at `a9cdfa3b645773684b40359e11e78fb49f4c57e8`: exercise **image-only tool results through the real Mistral message validator**, alongside the current dictionary-shape assertions.

I checked the unchanged `_adapt_tool_images_for_mistral` with `mistral-common==1.11.7`, using `convert_openai_messages` and `MistralRequestValidatorV13/V15` in `ValidationMode.serving`:

- V13 rejects the original image-bearing tool message with `InvalidToolMessageException`; after adaptation it accepts the complete parallel-call history. The image-only tool's remaining `content=[]` is accepted, and the image appears after both tool results.
- V15 accepts the image in its original tool message, and the helper returns the input object unchanged.
- A following user text remains intact; repeated adaptation does not duplicate the relocated image or mutate the input.
- Duplicate, missing, and unknown tool-result IDs still fail validation after adaptation. The missing-result case specifically uses **serving** mode, rather than relying on the validator's default test mode.

These are **7 passing local tests**, not additional server/model runs. No blocker found in those cases. A compact extension inside the existing `test_adapt_tool_images_for_pre_v15_mistral`, using its unadapted `messages` fixture, would be:

```python
from copy import deepcopy
from mistral_common.exceptions import InvalidToolMessageException
from mistral_common.protocol.instruct.converters import convert_openai_messages
from mistral_common.protocol.instruct.validator import (
    MistralRequestValidatorV13, ValidationMode,
)

image_only = deepcopy(messages)
image_only[2]["content"] = [
    p for p in image_only[2]["content"] if p["type"] == "image_url"
]
validator = MistralRequestValidatorV13(mode=ValidationMode.serving)
with pytest.raises(InvalidToolMessageException):
    validator.validate_messages(convert_openai_messages(image_only), False)

adapted = _adapt_tool_images_for_mistral(image_only, tokenizer_version=13)
validator.validate_messages(convert_openai_messages(adapted), False)
assert adapted[2]["content"] == []
assert adapted[-1]["content"] == image_only[2]["content"]
```

Scope: the helper was extracted unchanged from the pinned source; the installed Mistral conversion classes and validators were real, not mocked. Python 3.12.14 / Pydantic 2.13.5. I did **not** import the full vLLM stack, decode images, load a tokenizer, run an endpoint/model, or establish preserved image-to-tool attribution after the documented pre-v15 relocation. This supplements the PR author's broader validation rather than claiming it as our work. The separate error-marker composition consideration remains in #58700; no duplicate patch is proposed here.
