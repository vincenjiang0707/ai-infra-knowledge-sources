## 正文

## Purpose

Adds an opt-in AITER ASM route for decode context parallelism (DCP) combined with speculative decoding on ROCm gfx950.

With DCP, each rank holds a round-robin shard of the KV cache (token `t` on rank `t % dcp_world_size`). A causal verify step of `qlen > 1` cannot run on the ordinary decode kernel, because that kernel applies causality on local indices, which is wrong over a round-robin shard. Today these steps are served by the segmented route (#51705), which expands each verify group into one single-query row per token and runs the Triton decode kernel.

This PR adds the AITER round-robin (`cprr`) ASM decode as an alternative. It keeps the verify group as one row of `qlen` queries and rebuilds each token's global position in-kernel from `g_kv_indptr`, `cp_rank` and `cp_world_size`, so the causal window is applied inside the kernel.

`VLLM_ROCM_AITER_MLA_DCP_VERIFY` selects the route (validated by `env_with_choices`):

- `segmented` (default): existing behavior.
- `asm`: opt-in AITER round-robin ASM decode.

### Per-batch routing

The metadata builder selects exactly one route per decode batch and stores it in the decode metadata:

| route | when |
|---|---|
| PLAIN | `qlen == 1`, or a non-causal block |
| CPRR | causal, `qlen >= 3`, `asm` selected, gfx950, DCP with interleave size 1, speculative decoding |
| SEGMENTED | every other causal `qlen > 1` batch, including `qlen == 2` |

There is no `cprr` kernel below `qlen == 3`, so a `qlen == 2` batch (configured `num_speculative_tokens=1`, or a larger configuration clamped at runtime) uses segmented MLA under `asm` as well. The plain kernel never serves a causal `qlen > 1` batch.

The `cprr` kernels exist only at the native DCP-gathered head counts (16, 32, 64, 128). Other counts are padded up (96 → 128). The output is sliced back as a view; a post-kernel copy would race the symmetric-memory all-to-all combine.

### Non-causal DCP drafts

`supports_non_causal_multi_token_dcp = True` lets a non-causal draft (for example a DSpark draft with `dflash_config.causal = false`) run under DCP. Such a batch takes the PLAIN route: each rank attends its whole local shard without a mask, and the per-row LSE merge across ranks is exact, because non-causal attention needs no cross-shard causal window. This does not depend on `VLLM_ROCM_AITER_MLA_DCP_VERIFY` and was validated end to end on the default `segmented` route (below).

### KV split cap (CPRR only)

When CPRR is selected, `max_split_per_batch` is capped at the device CU count. At low batch size, splitting the KV axis is the main source of parallelism; without a cap, AITER's reduction scratch can reach about 9.35 GiB. Scratch sizing, metadata generation, and the kernel launch all use the same cap, so the buffers they share cannot disagree. The default segmented route is unchanged.

## End-to-end validation

Same build, model, and hardware for every row. Only `VLLM_ROCM_AITER_MLA_DCP_VERIFY`, `num_speculative_tokens`, and (last row) the draft's causality change.

- 8× MI355X (gfx950), TP8, DCP8, fp8 KV cache
- `moonshotai/Kimi-K3` (MXFP4) + `Inferact/Kimi-K3-DSpark` draft, probabilistic drafting, block rejection sampling
- Image `vllm/vllm-openai-rocm:nightly-rocm100-dee37d89115db4c94a820a79a78a7828e141c910` (AITER 0.1.21.post1) with this PR's `vllm/envs.py` and `vllm/v1/attention/backends/mla/rocm_aiter_mla.py` applied

Serve command:

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_AITER_MLA_DCP_VERIFY={asm|segmented} \
vllm serve moonshotai/Kimi-K3 \
  --tensor-parallel-size 8 --decode-context-parallel-size 8 \
  --dcp-comm-backend a2a --cp-kv-cache-interleave-size 1 \
  --gpu-memory-utilization 0.90 --max-num-seqs 16 \
  --max-model-len 1048576 --max-num-batched-tokens 16384 \
  --trust-remote-code --load-format fastsafetensors --moe-backend auto \
  --language-model-only --kv-cache-dtype fp8 \
  --attention-backend ROCM_AITER_MLA \
  --attention-config '{"mla_prefill_backend":"ROCM_AITER_FA"}' \
  --enable-prefix-caching --prefix-cache-retention-interval 12288 \
  --compilation-config '{"mode":3,"cudagraph_mode":"FULL_DECODE_ONLY","max_cudagraph_capture_size":128,"custom_ops":["+fused_rms_norm_gated","+situ_and_mul"]}' \
  --speculative-config '{"model":"Inferact/Kimi-K3-DSpark","method":"dspark","num_speculative_tokens":N,"attention_backend":"ROCM_AITER_MLA","kv_cache_dtype":"fp8","draft_sample_method":"probabilistic","rejection_sample_method":"block"}'
```

### Accuracy: GSM8K

```bash
lm_eval --model local-completions \
  --model_args model=moonshotai/Kimi-K3,base_url=http://127.0.0.1:8000/v1/completions,num_concurrent=16,tokenized_requests=False,tokenizer=moonshotai/Kimi-K3,trust_remote_code=True \
  --tasks gsm8k --num_fewshot 5
```

5-shot, all 1319 questions. Standard error is about ±0.005.

| route | `num_speculative_tokens` | strict-match | flexible-extract | acceptance rate | acceptance length |
|---|---:|---:|---:|---:|---:|
| asm | 7 | 0.9666 | 0.9659 | 0.418 | 3.92 |
| segmented | 7 | 0.9606 | 0.9606 | 0.418 | 3.93 |
| asm (qlen 2 → segmented fallback) | 1 | 0.9613 | 0.9613 | 0.937 | 1.94 |
| segmented | 1 | 0.9606 | 0.9598 | 0.937 | 1.94 |
| segmented, **non-causal draft** | 7 | 0.9606 | 0.9606 | 0.446 | 4.12 |

All routes are within one standard error, and acceptance is unchanged by the route, as expected: only the target's attention kernel differs.

### Performance: `vllm bench serve`, ISL 100K, OSL 256

```bash
vllm bench serve --backend vllm --endpoint /v1/completions \
  --model moonshotai/Kimi-K3 --trust-remote-code \
```

### Routes actually taken

Counted from the per-batch route in the decode metadata (local instrumentation, not part of this PR):

- `asm`, N=7: target (96 heads) and draft (64 heads) verify batches all on CPRR; PLAIN only for qlen 1 warmup.
- `asm`, N=1: about 6,600 target verify batches at qlen 2 on SEGMENTED, plus a qlen 3 batch on CPRR in the same server, so the mixed CPRR/segmented path runs end to end under `asm`.
- `segmented`, N=7: all verify batches on SEGMENTED.
- `segmented`, non-causal draft: draft batches (qlen 7, non-causal) on PLAIN, target on SEGMENTED.

Note: on this image, Kimi-K3 with a DSpark draft and CUDA graphs fails during startup on either route, independent of this PR. The draft caches its KV-cache pointers during CUDA graph memory profiling, which runs against a throwaway KV cache that is freed before the real one is allocated. These runs include a small fix that refreshes those pointers when the allocation changes; it will be sent as a separate PR.

### YukioZzz · 2026-09-20

Thanks for the commits.

I see that this PR already handles the qlen-2 case deliberately: it rejects a configured qlen of 2 at initialization and also fails loudly if a larger configured speculative width is dynamically clamped to qlen 2 at runtime. I agree that falling back to the plain MLA kernel would be incorrect, since it would apply causality using rank-local positions over the round-robin KV shard.

The additional issue I found is that the runtime guard is reachable in a normal K=4 workload, rather than only in a pathological near-max-model-length case. In a TP8/DCP8 Kimi-K3 AgentX c48 run, the scheduler produced `max_qo_len == 2` after about 185 seconds of profiling, and the intentional guard terminated the EngineCore:
  ```
      RuntimeError: AITER cprr DCP verify got a batch with max_qo_len=2,
      which has no cprr kernel (minimum 3)
```

This leaves a liveness gap for otherwise valid partial-draft scheduling.

One possible resolution is to retain segmented DCP verification as a per-batch correctness fallback only below the CPRR kernel floor:
```
      use_segmented = (
          supports_segmented
          and causal
          and max_qo_len > 1
          and (not asm_selected or max_qo_len < MIN_CPRR_QLEN)
      )
```

For this fallback batch, the builder should not construct `g_kv_indptr` or CPRR persistent metadata. Full-CUDA-graph configurations also need segmented metadata buffers allocated even when CPRR is the preferred route. If segmented verification is unavailable, the existing fail-fast behavior should remain.

A native qlen-2 CPRR kernel would also remove the need for this fallback, and a two-stage Gluon experiment in #57703 is also a broader alternative but was not the implementation validated here.

### YukioZzz · 2026-09-23

The causal term added to `_use_segmented_dcp_verify` at line 244 in commit 3 is right, but only half the change landed: the guard at line 2381 was not updated, so a non-causal draft can now reach neither segmented nor CPRR below `qlen 3`, and went from being silently mis-masked to raising. The same guard fires at `qlen ≥ 3` whenever CPRR is off (`segmented`, `segmented:64`, `interleave != 1`). The root cause is that CPRR is treated as a general route when it exists only to reconstruct a causal window over a round-robin shard: a non-causal block has no mask, so it just pays the `96→128` head pad and lands on `msk0_lse_cprr`, which carries its own `# Untested` note at line 2516 and has no coverage.

Suggest a per-batch predicate the way `use_segmented_dcp_verify` already is: `use_cprr = self._asm_dcp_verify and causal and max_qo_len >= _MIN_CPRR_QLEN`, with four sites derived from it: the `g_kv_indptr` build at line 1431; the persistent-metadata exclusion at line 1459; the guard at line 2381, which needs `attn_metadata.causal`; and line 2477, which should read `if decode.g_kv_indptr is not None`. `asm_decode_num_heads` is process-level, so otherwise a non-causal batch trips `assert g_kv_indptr is not None`; the `elif` raise below it then duplicates line 2381 and can go. Separately, line 1459 is missing a lower bound: `max_qo_len < _MIN_CPRR_QLEN` also holds at `qlen 1`, so it suppresses the persistent schedule for every single-token decode step—compare line 749, which correctly writes `1 < ... < _MIN_CPRR_QLEN`.

That makes this PR a strict superset of #57085, which could then be closed as superseded, provided its GSM8K comes across with attribution (`8×MI355X TP8/DCP8`, strict `==` flexible, `0.9598 / 0.9651`). It is the only e2e evidence that the non-causal draft is not being silently causal-masked, and this PR has none.
