# [PR #54316] [Bugfix][Quantization] Decline CUTLASS int8 w8a8 on SM100+ so Triton fallback is reachable

source: https://github.com/vllm-project/vllm/pull/54316
state: open | updated: 2026-09-27T05:18:12Z
labels: bug, nvidia, quantization

## 正文

## Purpose

Fixes #54311. `CutlassInt8ScaledMMLinearKernel.is_supported()` takes `compute_capability` but ignores it and always returns `True` on CUDA. So CUTLASS claims every int8 w8a8 layer — but the SM100/SM120 dispatchers wire the int8 func as `nullptr` (`scaled_mm_c3x_sm120.cu`: `nullptr, // int8 not supported on SM120`, same on `sm100`), so the C++ hard-errors at runtime:

```
Int8 not supported on SM121. Use FP8 quantization instead, or run on older arch (SM < 100).
```

The working `TritonInt8ScaledMMLinearKernel` — next in `_POSSIBLE_INT8_KERNELS[CUDA]` — never gets a chance.

## Fix

Decline in `is_supported()` when `compute_capability >= 100` (SM100/SM120/SM121 Blackwell; CUTLASS int8 is only wired for SM < 100), mirroring the sibling `AiterInt8ScaledMMLinearKernel`'s capability guard. Kernel selection then falls through to `TritonInt8`, which overrides `is_supported()` and supports these arches. FP8 is unaffected (SM120 wires the fp8 func).

## Verified on a GB10 (sm_121)

```
CutlassInt8ScaledMMLinearKernel.is_supported(121)
  -> (False, 'CUTLASS int8 w8a8 is not supported on SM100+ (Blackwell); use the Triton int8 kernel.')
TritonInt8ScaledMMLinearKernel.is_supported(121) -> (True, None)
_POSSIBLE_INT8_KERNELS[CUDA] == [Cutlass, Triton, Humming]  # Triton now reachable
```

## Tests

Device-free (`tests/model_executor/kernels/test_cutlass_int8_sm_gate.py`): declines on SM100/120/121, stays supported on SM90/89/80/75, and `compute_capability=None` stays supported (back-compat).

### hclsys · 2026-09-13

@Munsik-Kim thanks for that — a cleaner repro than mine, and useful to have a second card on it (your 5080/sm_120 vs my GB10/sm_121).

@cuihangbin on decode perf: I haven't benchmarked Triton int8 against bf16, so I'm not going to dispute your number. It's worth separating from what this PR changes, though. The diff only touches `CutlassInt8ScaledMMLinearKernel.is_supported`; picking Triton comes from `_POSSIBLE_INT8_KERNELS[PlatformEnum.CUDA] = [CutlassInt8, TritonInt8, HummingInt8]` in `kernels/linear/__init__.py:392`, which this PR leaves alone. And today that config doesn't run slowly on SM100+ — it fails at startup (`Int8 not supported on SM120`), because CUTLASS claims the layer and the C++ dispatcher then hits a nullptr int8 func.

So if Triton int8 really is a net loss against bf16 there, the conclusion I'd draw is that an int8 w8a8 checkpoint isn't worth running on SM100+ — which is worth telling the user plainly rather than leaving them with a startup crash. Two ways to do that: a one-time warning when the int8 fallback is selected on SM100+, or have it decline the quant outright with a clear message. Either is a small change on top of this one, but which you want is a maintainer call — say which and I'll add it.

If a decode comparison at a realistic model size would help settle it, I have the sm_121 hardware and can run it.
