## Purpose

With async scheduling, `FLASHINFER_MLA_SPARSE_SM90` did a blocking D2H copy on every metadata build. FlashInfer bakes each row's `kv_len` into its schedule on the host, and `seq_lens_cpu_upper_bound` is optimistic under async spec decode, so the builder copied `positions` / `seq_lens` back to get exact lengths. With MTP that happens on every draft step too. On GLM-5.3-Flash this made async scheduling *slower* than `--no-async-scheduling` (11.1 vs 7.7 ms TPOT at c=1).

How it works:

1. **Plan on the CPU with the upper bound plus slack.** The host bound, padded by 32 tokens and capped at the max valid count, is available without touching the GPU, so there's no sync.
2. **Clamp on the GPU.** FlashInfer keeps the plan in its int workspace as a list of work items with `kv_start`/`kv_end`. A small Triton kernel (`_clamp_work_kv_end`) computes each row's exact valid count on device from `seq_lens` / `query_start_loc` / `req_id_per_token` (same formula as before) and clamps every work item's `kv_end` to it. The FA3 kernel never reads past `kv_end`, so the slack (and the `-1` tail of the index buffer) is never touched.
3. **Reuse the plan across steps.** Contexts grow by a few tokens per step and the slack absorbs that, so while the new bounds still fit, `wrapper.plan()` is skipped and only the clamp runs. This is also why no-async gets slightly faster.

```
before:  GPU seq_lens --(blocking D2H)--> CPU exact lens --> plan --> run
after:   CPU upper bound + 32 --> plan (usually reused)
         GPU: clamp kv_end to exact lens (Triton, no sync) --> run
```

Notes:
- This reads `wrapper._plan_info` and the planned int workspace (the `MLAPlanInfo` layout from `scheduler.cuh`). The plan-info length is asserted, and the per-work capacity is read from the layout rather than hardcoded.
- With adaptive verification the host query split may not match the device one, so the host bound falls back to the batch max for every row.
- The exact (syncing) path is only used when there's no host upper bound.
- Only affects `FLASHINFER_MLA_SPARSE_SM90` (Hopper; the default sparse backend for NoPE models such as GLM-5.3-Flash).

**Not a duplicate:** I searched open PRs touching this backend. #55222 fixes the fp8 plan dtype and indexer workspace sizing, and #58260 chunks plan/run for >16k-row steps. Neither addresses the sync. #58260 does touch `plan()` / `build()`, so whichever lands second needs a small rebase; I'm happy to do it.

## Test Plan

- Unit tests: `pytest tests/v1/attention/test_flashinfer_mla_sparse_sm90.py` on H100. I updated the existing tests to the new `plan()` signature and added two GPU tests against real FlashInfer. One checks that an upper-bound plan plus the device clamp matches an exact plan (including MTP-style multi-query rows around `index_topk` and a batch spanning several clamp blocks). The other checks that the plan is reused across growing contexts without replanning.
- E2E: `zai-org/GLM-5.3-Flash`, TP8 on H100, fp8 KV cache, MTP with 5 speculative tokens, `max-model-len 32768`. Benchmark: `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 128 --ignore-eos` at concurrency 1/8/32, at least 32 prompts, each point run twice, no profiler.
- Accuracy: `tests/evals/gsm8k/gsm8k_eval.py` (1319 questions, 5-shot).
- Syncs: a torch profiler trace on the patched server shows no blocking sync left in the draft-step metadata build (before: 13 per ~5 steps, ~79 ms total, at `_kv_lens_host`).

All E2E runs, baseline included, have the fp8 plan-dtype fix from #55222 applied locally, since fp8 KV on this backend fails without it.

GSM8K is unchanged: 0.913 → 0.921 (async), 0.911 → 0.917 (no-async). MTP mean acceptance length stays ~4.2. The random-token bench has ~no draft acceptance, so its TPOT is close to the worst case for spec decode.
