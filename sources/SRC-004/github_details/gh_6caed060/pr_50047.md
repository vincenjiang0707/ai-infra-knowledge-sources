# [PR #50047] [Bugfix][NIXL] Release a dead peer's NIXL state without waiting for TTL

## 正文

## Purpose

When a pull-mode prefiller restarts with a new engine ID at the same host and port, the decoder can keep the previous peer's NIXL resources and cached metadata until TTL cleanup.

This PR detects the replacement after a successful handshake and marks the old peer for cleanup. It waits for requests using the old peer and pending handshakes to finish before releasing the old state. This avoids removing resources that are still in use and allows cleanup without restarting the decoder or waiting for TTL eviction.

I'd like to add a perspective on the responsibility split.

I agree that monitoring the health status of P/D and other peer nodes is the router's job. That's a separate concern. But the issue here is different: a P or D node is holding a stale NIXL communication handle. From a responsibility standpoint, when P and D are able to clean up their own stale handles, they should do so locally rather than depending entirely on an external component to tell them to.

There's a key point worth emphasizing: in this scenario the IP:port remains unchanged, and only the engine ID changes after a restart. That is a very strong, deterministic signal that the P node has restarted — not a flaky heuristic like "a transfer failed once." Given that, cleaning up the old handle immediately is clearly correct and reasonable.

And there's another important consideration: if the router doesn't currently support this, the changes required on the router side would be enormous. It would also require P and D to implement a new interface for the cleanup logic.

The cost here is worth calling out clearly:

Router-side changes are substantial. To notify D to clean up P's handles, the router would need health-check/heartbeat capabilities to detect P crashes or scale-downs — something many routers (e.g. simple load balancers) simply don't have. It would also need to maintain a P→D topology mapping to know which D instances are connected to which P, plus a reliable delivery mechanism (retries, acknowledgements) and strict ordering guarantees (the notification must arrive before D sends its next request to P).

P and D still need to implement the cleanup interface. And here's the key point: the cleanup logic D runs when it receives a peer_gone event is essentially the same code D would run if it detected the stale handle itself. So the router-based approach doesn't save any D-side work — it only moves the trigger from "D detects it internally" to "D waits for the router to tell it."

Compared to that, the D-side approach (detecting the stale handle locally) requires changes only in base_worker.py, no router changes, no new interfaces, and no external dependency. It solves the same problem at a fraction of the cost.

Given that, I'd suggest the D-side detection as the immediate fix, with the router notification as a future enhancement (to cover scale-down/migration scenarios) rather than a replacement.
