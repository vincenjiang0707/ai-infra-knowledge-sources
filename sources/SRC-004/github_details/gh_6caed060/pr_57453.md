# [PR #57453] [Bugfix][KV Offload] Retain offload event metadata through batch translation

source: https://github.com/vllm-project/vllm/pull/57453
state: open | updated: 2026-09-23T04:31:57Z
labels: bug, kv-connector

## 正文

## Purpose

`OffloadingEventsTracker` caches a `BlockStored` payload per offload key and drops it when the key's last residency goes away. The drop happened inline in `_take_removed_event`, so within a single `take_events` batch a removal could delete the payload that a *later* event in that same batch still needed — a primary removal preceding a queued secondary (KVCR) store. That store then fell back to the placeholder payload, publishing an event with no block hashes and no token ids.

Fix: collect the removed keys during the batch and drop their payloads once, after every event in the batch has had a chance to register its residencies.

Scope: this does not address a store that only completes in a later batch; that needs the in-flight store set and is left for a follow-up.

Not a duplicate of #52103, which touches the same files to add request provenance to stored events.

## Test Plan

```bash
pytest tests/v1/kv_connector/unit/offloading_connector/test_events.py
```

`test_primary_removal_preserves_metadata_for_same_batch_kvcr_store` is added to the existing suite, parametrized over the secondary removal landing in the same batch or the next one. It asserts the store keeps its full payload, and that the payload is still dropped once no residency remains.
