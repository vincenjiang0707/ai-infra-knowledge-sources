## 正文

## Purpose

Online `nvfp4_per_token` previously advertised the ordinary NVFP4 activation scheme even though execution uses per-token scales. This could select an incompatible backend. One-sided dispatch also sized its buffer for packed FP4 although the per-token path sends unpacked activations and quantizes inside the expert kernel.

- Add `kNvfp4DynamicToken` and use it for online NVFP4 MoE selection.
- Declare TRTLLM support and size modular expert workspaces for unpacked inputs.
- Size one-sided communication buffers with an optional `input_dtype` override. An explicit BF16/FP16 dtype reserves `hidden_dim * input_dtype.itemsize` activation bytes and zero scale bytes; `None` preserves quant-config-based sizing. Per-token NVFP4 supplies `moe_config.in_dtype`. This supports deferred quantization without relying on another BF16 layer enlarging the shared buffer.
- Cover both packed/deferred dispatch sizing, including BF16/FP16 dtype overrides and early rejection of FP32, FP8 E4M3, FP8 E5M2, and INT8 overrides. FlashInfer’s per-token NVFP4 quantizer accepts only BF16/FP16 activations; its FP32 per-token scales do not imply FP32 activation support.

Depends on #57091 and must merge after it. All Marlin capability changes belong to that PR's generic activation contract; there is no Marlin diff here. CuTe-DSL per-token support remains in #50030. The per-token backend-contract tests were removed from this PR because they need #57091; they should return with it.

- Isolated two-B300-GPU check: `uv run --no-sync --project /home/matej/prime-rl-stack-clean torchrun --standalone --nproc_per_node=2 /home/matej/prime-rl/outputs/glm53-rl-startup/20260922/nvfp4-one-sided/gpu_dispatch_check.py` — FlashInfer one-sided BF16 dispatch/combine using this checkout's dtype override, hidden size 6144, capacity 320, batches of 1/96/320 tokens per rank, three repetitions each. **All 9 round trips matched the original input exactly**; no BF16 model layer or manager growth was used to provision the buffer. The initial harness incorrectly assumed token order is preserved during dispatch; the corrected check compares dispatched value multisets per source rank and requires exact original token order/values after combine.

These checks validate configuration and GPU communication, not full-model numerical accuracy. No full-model evaluation was rerun for this update, and the live GLM-5.3 RL deployment remains on its previous wheel.

Prior validation, before the sizing update: 30 configuration tests passed with prerequisite #57091 applied. Historical single-GPU and DP2/EP2 TRTLLM comparisons were reported for the original implementation; those were not rerun here.
