# [PR #58415] [Bugfix][XPU] Reset oneCCL's collective chain after XPU graph capture

source: https://github.com/vllm-project/vllm/pull/58415
state: open | updated: 2026-09-27T06:37:37Z
labels: bug, intel-gpu, ci/build

## 正文


## Purpose

Fixes #58388.

On XPU with TP>1, the first eager all-reduce above roughly 4-8 MB after an XPU graph capture leaves the calling stream recording into a command graph. Every later graph replay then fails with `Cannot prepare for replay during capturing stage ... xpuStreamCaptureStatus: Recording`, and every wait with `wait cannot be called for a queue which is recording to a command graph`.

oneCCL chains each collective on the previous one's completion event. After a capture, that event belongs to the captured graph. The large-message all-reduce path submits with an explicit dependency on it, which in SYCL's graph model pulls the submitting queue into the recording. Small messages don't do this, and one small eager all-reduce resets the chain.

In vLLM this kills Model Runner V2 whenever the first request after startup is a prefill of more than a few hundred tokens, because the model's embed all-reduce runs eagerly at the start of every step. Prefix caching and MTP, which #58388 originally pointed at, are incidental.

This PR ends `GroupCoordinator.graph_capture()` with `XpuCommunicator.reset_after_graph_capture()`: one 1-element eager all-reduce on the device group, skipped for a single rank or while a capture is active. Graph replays don't touch oneCCL's host-side state, so once per capture context is enough. The cost is one tiny collective at startup.

The underlying behaviour is in torch-XCCL / oneCCL. A standalone two-rank repro without vLLM is in #58388.

## Test Plan

- `tests/distributed/test_xpu_graph_capture_all_reduce.py` (new, 2 XPUs, skipped otherwise): captures an all-reduce through `graph_capture()`, runs the first eager all-reduce after it at 20 MB on a fresh stream, then asserts the stream isn't recording and the graph still replays.
- `tests/distributed/test_xpu_communicator.py` (new, CPU, mocked): the reset issues one tiny all-reduce on the device group and is skipped for 1 rank or during capture; `graph_capture()` calls it on normal exit and not when the capture raises.
- Both are wired into a new 2-card step, "Distributed XPU Graph Capture (2 GPUs)", in `.buildkite/intel_jobs/misc_intel.yaml`, since no Intel job currently runs the communicator tests.
- End to end: `Qwen/Qwen3.8-27B`, TP=2, V2, MTP, XPU graphs, prefix caching, first request of 8.9k tokens.

## Test Result

2x Arc Pro B70, `vllm/vllm-openai-xpu:nightly` (main at `e97573215`; the patched files are identical on this branch's base) with this PR's two source files mounted:

| | without fix | with fix |
|---|---|---|
| `test_xpu_graph_capture_all_reduce.py` | FAILED: `eager all-reduce after graph capture left the stream recording` | PASSED (~16 s) |
| `test_xpu_communicator.py` (5 tests) | 5 FAILED | 5 PASSED (under 1 s; also passes in a container with no XPU devices) |
| E2E: 8.9k-token first request (V2 + MTP + graphs + prefix caching) | engine dies | OK; prefix-cache check passes, 0 graph errors |

Also validated downstream on a v0.30.0-based build with the same config plus FP8 KV (serving throughput, concurrent prefill + spec-decode stress, json_schema and tool calls all clean).
