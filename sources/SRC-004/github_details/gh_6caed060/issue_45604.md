### 🐛 Describe the bug

# CUDA invalid argument in FlashInfer AllReduce norm fusion on MiniMax-M3 MXFP8, 4x H200

## Title

`Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:455 'invalid argument'` when serving MiniMax-M3-MXFP8 with TP=4/EP=4 on 4x H200

## Bug description

I am trying to serve `MiniMax-M3-MXFP8` with the dedicated MiniMax-M3 vLLM image on 4x NVIDIA H200 GPUs using tensor parallelism and expert parallelism.

The model loads successfully and reaches CUDA graph memory profiling, but vLLM then auto-selects the FlashInfer all-reduce backend:

```text
[flashinfer_all_reduce.py:111] Auto-selected flashinfer allreduce backend: trtllm
[flashinfer_all_reduce.py:151] Initialized FlashInfer Allreduce norm fusion workspace with backend=trtllm
```

Immediately after that, startup fails with:

```text
NCCL version 2.28.9+cuda13.0
Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:455 'invalid argument'
Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:455 'invalid argument'
Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:455 'invalid argument'
Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:455 'invalid argument'
```

Then the engine shuts down:

```text
[multiproc_executor.py:284] Worker proc VllmWorker-2 died unexpectedly, shutting down executor.
[core.py:1195] EngineCore failed to start.
RuntimeError: cancelled
RuntimeError: Engine core initialization failed. See root cause above.
```

This looks related to the FlashInfer/TRT-LLM all-reduce norm fusion path or custom all-reduce path during startup.

## Expected behavior

The engine should start successfully using TP=4 and EP=4 on 4x H200, or vLLM should fall back safely to NCCL/PyNCCL if the FlashInfer/TRT-LLM/custom all-reduce fusion path is unsupported for this setup.

## Actual behavior

The engine crashes during startup after FlashInfer AllReduce norm fusion initializes with `backend=trtllm`, with:

```text
Failed: Cuda error /workspace/csrc/custom_all_reduce.cuh:455 'invalid argument'
```

## Workaround

The crash is avoided by disabling the custom/fused all-reduce path:

```bash
--disable-custom-all-reduce \
--compilation-config.pass_config.fuse_allreduce_rms false
```

With that change, the engine config shows:

```text
disable_custom_all_reduce=True
pass_config: {
  fuse_norm_quant: True,
  fuse_act_quant: True,
  fuse_allreduce_rms: False
}
```

and TP/EP all-reduce falls back to:

```text
Using ['PYNCCL'] all-reduce backends
```

However, this disables a performance optimization, so it would be useful to know whether this path is expected to work on H200 for MiniMax-M3-MXFP8, or whether vLLM should automatically avoid selecting this backend.

## Questions

1. Is FlashInfer/TRT-LLM all-reduce norm fusion expected to work on Hopper/H200 for MiniMax-M3-MXFP8 with TP=4 and EP=4?
2. Should `flashinfer_all_reduce.py` avoid selecting `backend=trtllm` on this hardware/configuration?
3. Should `--disable-custom-all-reduce` also prevent the FlashInfer all-reduce norm fusion path, or is `--compilation-config.pass_config.fuse_allreduce_rms false` required separately?
4. Is this a known incompatibility between MiniMax-M3 MXFP8, Breakable CUDA Graph, FlashAttention 3, and FlashInfer all-reduce fusion?

## Additional notes

There were previous startup issues that were resolved before this report:

* For this MiniMax-M3 NVIDIA fused path, forcing `--kv-cache-dtype fp8` failed with `kv_cache dtype must match qkv (bf16 cache only)`. This was resolved by using `kv_cache_dtype=auto`.
* Forcing `--attention-config.backend FLASHINFER` with `--block-size 128` failed earlier because FlashInfer page size 128 required a TRT-LLM generation backend. This was resolved by using `--attention-backend FLASH_ATTN`.
* The remaining issue reported here is specifically the `custom_all_reduce.cuh:455 'invalid argument'` failure after `flashinfer_all_reduce.py` selects `backend=trtllm`.

### Tobi-Adesoye · 2026-06-15

This specific CUDA invalid argument crash during AllReduce norm fusion on an MXFP8 layout typically points to a memory stride mismatch or a variance underflow during the inter-GPU communication barrier. 

When you scale across a 4x H200 topology using fused FlashInfer layouts, the microscaling factors are highly sensitive to dynamic sequence ranges. If the internal sequence slices become non-contiguous in memory during the distributed reduction pass, standard PyTorch/vLLM graph allocation logic attempts to pass mismatched block dimensions to the underlying C++ pointer, triggering the invalid argument panic.

Furthermore, extreme low-bit compression formats (like MXFP8) often experience a severe variance flatline over specific token windows. If your running variance drops beneath the typical hardware epsilon threshold during the fused normalization pass, the reciprocal square root calculation collapses arithmetic accuracy and disconnects the autograd memory handle.

I ran into this exact non-contiguous view manipulation and variance collapse pattern during massive cluster stress testing. I ended up building an isolated hardware-aware fallback layout engine called `renorm-native` that explicitly implements a strict micro-variance floor and decouples analytical view slices from the parent shared memory fabric during custom backward passes to guarantee cluster stability under aggressive quantization: 
https://github.com/Tobi-Adesoye/renorm-native

If your trace reveals that the memory pointers are losing alignment across the NVLink bounds when tracking dynamic batch layouts, wrapping your linear projection blocks in an explicitly isolated variance-bounded layer could completely anchor the execution graph.
