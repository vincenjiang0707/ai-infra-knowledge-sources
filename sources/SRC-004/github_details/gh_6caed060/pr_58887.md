# [PR #58887] [Bugfix][ROCm] Fix race on AITER MLA FP8 prefill scheduling metadata under async scheduling

source: https://github.com/vllm-project/vllm/pull/58887
state: open | updated: 2026-09-27T08:46:16Z
labels: bug, rocm

## 正文

Fixes #58886

## Purpose

**Type:** bugfix. **Backend:** `ROCM_AITER_MLA`, FP8 KV cache, gfx950 (FP8 ASM prefill path).
**Affected:** MLA models served with async scheduling on this path. Reproduced with Kimi-K3
(TP8, MI355X).

`AiterMLAMetadataBuilder._build_fp8_prefill_ps_metadata` passes one set of persistent device
buffers to `aiter.get_ps_metadata_v1`. That function plans on the host and writes the plan
back with blocking `hipMemcpy`, which is not ordered on the current stream. With async
scheduling, step N+1's metadata is built while step N's prefill kernels
(`mla_prefill_ps_asm_fwd` and `mla_reduce_v1`, one launch per layer) are still queued, so
step N can run with step N+1's work/reduce maps. The existing `.item()` sync on
`reduce_indptr[-1]` happens after the rewrite, so it does not prevent this.

Symptom: `Memory access fault by GPU ... Write access to a read-only page` during serving, at
a deterministic point for a given request stream. When the stale indices stay in bounds, the
prefill attention output is silently wrong instead.

This PR plans into pinned host buffers (two slots) and copies them to the device with
`copy_(non_blocking=True)` on the current stream, so the update is ordered after previously
launched kernels. A slot is reused only after its previous copy completes (CUDA event). As a
side effect, `num_partial_tiles` is read from the host plan, which removes a GPU sync per
prefill step. No AITER change is needed. The AITER-side hazard (stream-less copies in the host
planner) is tracked in [ROCm/aiter#5879](https://github.com/ROCm/aiter/issues/5879).

## Test Plan

Kimi-K3 TP8 on MI355X, ROCm 10 nightly (`29468dde`), FP8 KV cache,
`max_num_batched_tokens=16384`, `max_num_seqs=256`, `FULL_AND_PIECEWISE`, async scheduling.

1. Crash: `sglang.bench_serving`, random 8k/1k, on request streams that fault without the fix,
   before vs after.
2. Performance: same benchmark at concurrency 4 and 32, before vs after.
3. Accuracy: `niah_single_2` (real weights) at 4k (concurrency 4/32/64) and at 64k/128k
   (concurrency 32), before vs after.
4. Plan equivalence: `get_ps_metadata_v1` with pinned host outputs produces byte-identical
   plans to device outputs (5 batch shapes, including the crash batch; checked once on MI355X).

## Test Result

**Crash.** Every stream that faults without the fix completes with it:

| Request stream (8k/1k) | Before | After |
| --- | --- | --- |
| concurrency 32, 1024 prompts | fault at request 111 (also with `--enforce-eager`) | 1024/1024 |
| concurrency 32, 2048 prompts | fault at request 79 | 2048/2048 |
| concurrency 64, 1024 prompts | fault at request 61 | 1024/1024 |
| concurrency 32, 1024 prompts, other seed | fault at request 117 | 1024/1024 |

Isolating the cause (before, no fix): the fault disappears with the FP8 ASM prefill path
disabled, with `--no-async-scheduling`, or with a `torch.cuda.synchronize()` just before
`get_ps_metadata_v1`.

**Not Kimi-K3 specific: DeepSeek-V3.** `deepseek-ai/DeepSeek-V3` on the same ROCm 10 nightly,
TP8 (128 heads, 16 per rank, so no head padding), dummy weights, same server flags (FP8 KV
cache, async scheduling, `max_num_batched_tokens=16384`, `max_num_seqs=256`) without the
Kimi-K3-specific parser options, same 8k/1k benchmark at concurrency 32, 1024 prompts:

| Request stream | Before | After |
| --- | --- | --- |
| seed 4 | fault at request 111 | 1024/1024 |
| seed 5 | fault at request 117 | not run |

The engine dump at the fault shows the same crash batch as with Kimi-K3: one new 8175-token
prefill with 32 running requests.

**Performance.** No change:

| 8k/1k | Output tok/s (before / after) | Median ITL (before / after) |
| --- | --- | --- |
| concurrency 4 | 236.05 / 236.05 | 15.49 / 15.50 ms |
| concurrency 32 | 1083.0 / 1082.6 | 18.14 / 18.14 ms |

**Accuracy.** No regression (single runs):

| `niah_single_2` | Before | After |
| --- | --- | --- |
| 4k, concurrency 4 / 32 / 64 | 0.974 / 0.954 / 0.970 | 0.974 / 0.978 / 0.984 |
| 64k, concurrency 32 | 0.922 | 0.928 |
| 128k, concurrency 32 | 0.888 | 0.888 |

**Reproducing on ROCm 7.2.** The bug is not ROCm 10 specific. Use the ROCm 7.2 image of the
same nightly (`vllm/vllm-openai-rocm:nightly-29468dde…`), the same `vllm serve` and benchmark
commands as above, and add one HIP runtime variable to the server:

| ROCm 7.2 server env | Benchmark stream | Without this PR | With this PR |
| --- | --- | --- | --- |
| none (defaults) | any above | no crash | no crash |
| `DEBUG_HIP_DYNAMIC_QUEUES=1` | 1024 prompts, `--seed 5` | crash at request 117 (x3, on 2 machines) | 1024/1024 |
| `GPU_MAX_HW_QUEUES=16` | 1024 prompts, `--seed 4` | crash at request 111 (x2, on 2 machines) | 1024/1024 |

The crash is `CUDA error: an illegal memory access was encountered`, on the same kind of
batch as on ROCm 10: one new ~8.1k-token prefill plus ~30 decodes.

**Why these variables expose it.** `get_ps_metadata_v1`'s first copy is tiny (1 KiB), so HIP
runs it as a small copy kernel on the default stream's hardware queue. Hardware queues run in
order, and with more streams than queues (default 4) several streams share one. With default
settings, ROCm 7.2 happens to put vLLM's prefill stream on the same queue as the default
stream. The plan copy then waits behind the running prefill, which hides the race. Both
variables change how streams are assigned to hardware queues, so the copy stops waiting and
lands while the prefill is still reading the plan, as it always does on ROCm 10. So ROCm 7.2
is protected by an accident of queue assignment, not by any ordering guarantee. This PR orders
the copy explicitly on every version.

With this PR, the ROCm 7.2 build with default settings also completes 1024/1024 (8k/1k,
concurrency 32), so the change does not regress 7.2. A standalone single-GPU reproducer is
attached to #58886.

Not related to #58814 (DSpark startup fault): that fault reproduces with this PR applied and is
fixed by #58814 alone.
