## Summary

This is a follow-up to **[RFC #45585: RL CI Matrix for vLLM: Behavioral + Physical + Protocol Coverage](https://github.com/vllm-project/vllm/issues/45585)**.

We propose keeping its three functional categories:

1. **State transitions**
2. **Information retrieval**
3. **Consistency**

The change is how those categories map to **existing test files, new tests, and CI execution**. RL-related coverage already exists in entrypoints, engines, workers, allocators, model loaders, model-specific tests, and kernels. Consolidation should account for that coverage before adding or moving suites.

Specifically:

- Keep component-level regressions next to the component they test.
- Consolidate duplicate tests at the same interface/layer.
- Use `tests/entrypoints/serve/dev/rlhf/` for RL HTTP contracts and cross-component lifecycle tests.
- Document category scope and existing coverage locations in the **`rlhf/__init__.py` module docstring**, and explain each test module's contract and boundaries in its own **module docstring**. No new test README is proposed.
- Give each test/configuration an explicit CI execution owner, with appropriate GPU count, backend, and platform selection.
- Amend the existing PRs rather than replacing them with a new umbrella implementation PR.

This issue proposes the reorganization; the file moves, test changes, and CI changes below are not implemented by opening this RFC.

## Relationship to existing RFCs

#45585 remains the umbrella motivation and behavioral/physical/protocol coverage framework. This proposal revises its blanket migration approach and updates the implementation plan against coverage that has since landed.

It does not replace the product contracts in the related RFCs:

- #48311 — Engine Sleep/Wake/Drain Lifecycle for RL
- #48310 — Sleep/Wake Correctness for RL
- #48312 — Weight Reload Correctness for RL
- #48306 — RL Information Retrieval: APIs & Introspection
- #42259 — Logprobs/Logits Semantics and Determinism
- #51476 — DP pause/sleep correctness and layering

Those RFCs define the relevant semantics. This issue defines where their regression coverage belongs, how the current test PRs should be adjusted, and how CI should execute it. Proposed semantics must not be treated as already implemented contracts.

## Why revisit the file mapping?

The original breakdown was largely one topic/file/PR at a time. The broad categories still make sense, but the repository now has overlapping coverage at different layers.

Examples:

- `test_mem.py` covers more than allocator flags: it includes CUDA graphs, offline sleep/reload, LoRA, async deep sleep, and FP8 KV cache.
- `test_weight_transfer_llm.py` uses a mock transfer engine to test the LLM API contract; it does not replace real IPC/NCCL transfer tests.
- `test_reload.py` already changes checkpoints and checks their effect, including quantized and distributed configurations.
- Engine and DP suites already cover pause/resume, late requests, drain, and race/deadlock regressions.
- Routed-experts tests exist at frontend, model-executor, and kernel layers.

Moving every one of these into an HTTP test directory would obscure ownership. Adding a new HTTP test for every existing lower-level case would increase cost without necessarily adding useful coverage.

The inventory below is based on a repository source audit and targeted upstream-main checks. It is a coverage inventory, **not a claim that every listed configuration currently passes CI**.

## Proposed ownership rules

1. **Place tests near their direct subject.** Allocator, worker, loader, and kernel invariants normally stay in their component suites.
2. **Merge duplication within a layer.** Two HTTP tests checking the same endpoint behavior are candidates for consolidation. A worker error-path test and an HTTP lifecycle test can be complementary.
3. **Review mixed files by test group.** A file containing allocator and offline-LLM cases must not be moved wholesale based on its name.
4. **Preserve execution coverage when moving tests.** Preserve frontend variants, eager/graph coverage, supported platforms, and resource requirements.
5. **Test the production state owner.** Do not create an independent test-only state machine just to populate a planned file.
6. **Use the cheapest effective level.** Exhaustive input validation and local invariants belong in unit tests; retain a small E2E set for actual cross-layer behavior.

## Coverage documentation through docstrings

### Package docstring

Add a concise, documentation-only `tests/entrypoints/serve/dev/rlhf/__init__.py` describing:

- The three categories and their behavioral scope.
- RL HTTP/lifecycle modules maintained under this package.
- Existing component coverage outside this package, with repository-relative paths and representative function/class names.
- The distinction between local coverage and referenced coverage.
- Links to #45585 and this follow-up RFC.

It must not import the referenced suites, initialize GPU dependencies, or change test collection.

### Test-module docstrings

Each affected test module should explain:

- The production interface/contract it tests.
- The observable failure or regression it guards.
- Important coverage already owned by another test module.
- Non-obvious execution requirements or matrix boundaries.

For example, the sleep/wake module could document the following intended boundary:

```python
"""HTTP sleep/wake lifecycle coverage for RL rollout.

Checks request gating during partial wake and successful generation after
memory and weights are restored. Resource-only and long-cycle cases are
selected separately from the small lifecycle smoke suite.

Related coverage:
    tests/basic_correctness/test_mem.py: allocator and offline sleep/reload.
    tests/v1/distributed/test_async_llm_dp.py: DP pause/drain regressions.
    tests/models/language/generation/test_gdn_sleep_wake.py: hybrid state cache.
"""
```

The final wording must describe assertions actually implemented by the module.

Keep volatile PR status and outstanding work in this RFC, rather than embedding “done” claims in Python files. Docstrings record stable scope and ownership; CI configuration remains authoritative for execution. Update affected cross-references in the same change as a move or rename. No symlinks, wrapper imports, or new README are needed.

## Planned changes to existing PRs

### #54930 — Sleep/wake

- Move the suite to `state_transitions/` and consolidate the old HTTP sleep test with explicit coverage parity.
- Replace “request was not successful” checks with precise pending/rejected/completed semantics.
- For partial wake, observe that the **same request** does not complete prematurely and does complete after full wake; propagate background exceptions and join all threads.
- Cover both tag orders where supported. A fresh successful request after wake is not sufficient to prove the earlier request survived.
- Separate level-2 flag/resource checks from recovery tests. A level-2 recovery test must restore weights before generation; a shared fixture cannot treat wake alone as weight restoration.
- Verify cache effects directly, rather than only checking that a repeated prompt generates.
- Merge redundant flag/cycle cases; keep representative runner and graph coverage.
- Separate long-cycle resource checks from smoke. Put dedicated performance benchmarks under the benchmark infrastructure rather than making general CI depend on machine-specific latency limits.
- Use exact idempotency/error contracts instead of accepting unrelated status codes such as both 200 and 400.

### #52144 — Pause/resume

Keep the merged suite and its focused contract. Amend helpers only through a coordinated infrastructure change.

Changes motivated by #51476 should track the relevant implementation contract. Do not change admission expectations solely because a proposed semantic change exists. Also distinguish engine completion from the client's receipt of the final streaming chunk when synchronizing assertions.

### #53541 — Weight update and metrics

Separate the test increment from product-design changes:

1. Real HTTP transfer and protocol tests.
2. Metrics implementation/semantics and associated tests.
3. Any additional state-management feature, only after demonstrating a gap in the existing engine/worker ownership.

Required test changes:

- Success tests use a configured/initialized backend and require success; HTTP 500 is not a successful protocol outcome.
- Invalid-order tests have explicit expected responses and state-preservation/recovery checks.
- Provide deterministic compatible A/B weights in CI. Core transfer coverage must not silently disappear because `VLLM_TEST_MODEL_ALT` is unset.
- Compare warm-updated B with a B reference, or another controlled numerical oracle; “text changed” alone does not establish correct transfer.
- Warm the relevant cache under A, update to B, and verify cache coherence and B results.
- Remove or relocate the reload smoke that only calls initialize/finalize without loading replacement weights. Reuse `test_reload.py` for actual model/quantization reload coverage.
- Exercise real metric transitions: active 0→1→0, successful counter increments, histogram observation count, and the agreed failure behavior.
- Define multi-API-process and DP metric/state ownership; frontend-local state and a fixed engine label need explicit justification.

There is also a cross-PR contract conflict: #52864 tests the existing `weight_version` response, while #53541 introduces `weight_gen/weight_label` and expands `/weight_info`. Resolve the API design first. Weakening schema tests to accept both is not the resolution. This proposal defaults to the upstream `weight_version` contract; any additional counter has separate semantics.

### #51350 — Weight checker

Keep this as a feature PR with its own focused tests.

- Align documentation and tests with the latest checksum/reset/compare baseline lifecycle, including compare's one-shot behavior.
- Ensure tests independently establish/consume their baseline and restore mutated weights.
- Use small unit tests for supported tensor types, hashing/coverage policy, and key merging.
- Verify the complete rank-qualified key inventory and negative cases such as missing ranks/tensors or changed values.
- Retain distributed reset→reload→compare; add real-transfer restoration as a distinct integration path.
- Schedule TP2×DP2×EP on an explicitly provisioned four-GPU job.

### #52864 — Schema and weight information

Keep the current scope. Use router-level CPU tests with a fake engine client for exhaustive field/input validation where practical, plus a small real-engine E2E set.

A schema matrix does not need to multiply every case by runner and parallelism. Successful transfer's version-commit behavior belongs in weight-update/compound lifecycle coverage.

### #52902 — Routed experts

Reconcile the PR description and reported results with the latest diff before expanding it.

The inspected version primarily checks capture shape/range across frontends/models and TP2×DP2. That should not be described as complete routing-replay correctness.

- Preserve cheap single-GPU frontend smoke when adding distributed/model cases.
- Add exact token/row alignment, cache-hit recovery, mixed-batch isolation, and lifecycle-related stale-routing checks.
- Shape/range alone cannot detect a valid-range all-zero capture; use a controlled/reference routing oracle where applicable.
- Repeated deterministic generation is not a test of consuming captured routes for replay. Add actual replay validation only through an available supported path; otherwise track it as a gap.
- Keep backend-specific checks near kernel tests and explicitly select supported hardware.
- Reduced-geometry dummy models establish code-path coverage, not real-checkpoint numerical correctness.
- Preserve graph coverage explicitly; a shared harness that forces eager cannot establish graph behavior.

### Shared infrastructure

Resolve the differing `server()` signatures/defaults across these PRs in one coordinated change. Prefer the repository's existing server utilities where they fit. Make model, environment, sleep enablement, execution mode, port handling, logging, and process cleanup explicit.

Do not collapse transport exceptions into a generic unsuccessful response for behavioral assertions. Reuse servers only when state is restored reliably; destructive weight changes need restoration or isolation.

## CI integration

Keep the three functional categories, and split execution within them by cost and resource requirements.

| Execution group | Scope | Resource policy |
|---|---|---|
| CPU/unit | Router contracts, actual engine/worker invariants, checker small-tensor behavior | Verify collection and execution without GPU dependencies |
| State transitions smoke | Core pause/sleep behavior, real IPC, minimal compound step | One GPU where topology permits; critical MRV1/MRV2 compatibility paths |
| Information retrieval smoke | Schema/version; small real-engine cross-check | CPU plus a small one-GPU E2E subset |
| Consistency smoke | Small-MoE capture/alignment and lifecycle correctness | One GPU, selected eager/graph scenarios |
| Distributed | NCCL, TP, DP/EP, rank completeness | Explicit two/four-GPU topology, including trainer resources |
| Hardware/extended | Supported quantization/kernel paths, long cycles, larger models | Dedicated hardware and explicit optional/scheduled selection |

Operational requirements:

- The existing entrypoints API-server job recursively collects `entrypoints/serve`. Its upstream four-way sharding does not provide four GPUs to an individual test.
- If dedicated RL jobs take ownership, exclude those tests from the former recursive job in the same change, including applicable AMD mirrors.
- Existing component jobs should remain the primary owners of their suites. The RL docstrings reference them without causing duplicate collection.
- Update source-file dependencies as well as pytest commands when moving tests.
- Use supported markers and explicit job selection. Adding a `nightly` marker alone does not schedule a job.
- Record passed, skipped, and deselected configurations separately. An advertised critical lane that skips its only transfer/hardware case is not established coverage.
- Avoid a full model × runner × backend × parallelism Cartesian product. Select combinations that exercise materially different paths.

A representative level-2 compound step is:

```text
rollout with A
→ pause/quiesce according to the implemented contract
→ sleep(level=2)
→ wake(weights)
→ transfer B and finish(weight_version=B)
→ wake(kv_cache), restore scheduling as required
→ rollout and compare with B reference
→ repeat for the next version
```

Assert request liveness, restored output/logprobs, committed version, and cache coherence. Metrics/checker assertions can be added as their features land; they need not block the initial compound test.

Coordinate physical tests with the earlier contributions linked in #45585. Its discussion also contains ownership of parallel-sampling abort-count/parent-child cleanup work; this reorganization should not duplicate that feature work.

## Acceptance criteria and feedback requested

Consolidation is complete when:

- Every claimed behavior has an identifiable test implementation and CI execution path.
- File moves preserve relevant platforms, frontends, and execution modes.
- Same-layer duplicates are removed; complementary component tests remain discoverable.
- Package and module docstrings describe implemented scope and point to existing coverage.
- Core real-transfer and lifecycle tests run in their designated lanes with meaningful oracles.
- PR descriptions match the current diff and separate source-audited coverage from actually executed validation.

Feedback requested: agreement on the ownership/migration table, frontend routed-experts placement, and resource-based CI partitioning before implementing the reorganization.

**Validation for this RFC:** source/diff review and targeted upstream-main/CI inspection only. No code changes or GPU test runs are claimed.
