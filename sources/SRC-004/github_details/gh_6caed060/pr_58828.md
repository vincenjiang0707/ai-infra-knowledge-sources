### Validation results: GLM-5.3-MXFP4 CUTLASS EP8 correctness and performance

I tested the CUDA `expert_map` implementation at commit `e53e37f9917aa1a2b31cea2291d140b69cab300f`.

- Model: `RedHatAI/GLM-5.3-MXFP4`
- Model configuration:
  - 256 routed experts
  - top-k = 8
  - compressed-tensors MXFP4 W4A4
- GPUs: 8x NVIDIA B300 SXM6, 275,040 MiB each
- PyTorch: `2.13.0+cu130`
- CUDA: 13.0
- vLLM base version: `0.28.1rc1.dev1534+g9bf44c401`

#### Observations

1. The patched CUTLASS MXFP4 path completed all 8,076 requests across TP8/DP1, TP4/DP2, TP2/DP4, and TP1/DP8 without request failures or NaN exceptions.

2. TP8/DP1 provides the best low-concurrency performance because a single request can use all eight GPUs for tensor parallelism.

3. TP1/DP8 provides the best throughput at concurrency 512 for all three workloads.

4. The largest DP8 advantage occurs in the prefill-heavy 8192/1024 workload. At concurrency 512, TP1/DP8 reaches `32,874 total tok/s`, which is:
   - 75.2% faster than TP8/DP1;
   - 22.2% faster than TP4/DP2;
   - 7.0% faster than TP2/DP4.

5. At concurrency 512, TP1/DP8 is also:
   - 1.2% faster than TP2/DP4 for 1024/1024;
   - 1.5% faster than TP2/DP4 for 1024/8192.

6. These measurements use one full-concurrency request wave (`num_prompts == max_concurrency`). Therefore, concurrency-1 results are inherently noisy and should not be interpreted as a stable production throughput measurement. The high-concurrency trend is much more representative.

#### FP4 profiling limit observed with DP8

With TP1/DP8, the initial profile run generated:

```text
m_numtopk = 2,097,152
```

The default `VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE=163840` was insufficient because:

```text
2,097,152 / top-k 8 = 262,144
```

The DP8 run was therefore started with:

```bash
VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE=262144
```

This was required only to allow the initialization/profile run to cover the configured `max_num_batched_tokens=32768` with DP8. It did not change the expert mapping or numerical computation.

Overall, the results indicate that consuming the canonical global-to-local `expert_map` inside the CUTLASS MXFP4 metadata/permutation CUDA path restores EP8 correctness and allows the backend to operate across mixed TP/DP layouts without adding a Python-side mapping operation in each MoE layer.

### Follow-up: DP8 without EP vs DP8 + EP8 (GLM-5.3-MXFP4, B300)

To check whether EP pays off for this model, I ran the same serving matrix as above with **TP1/DP8 and EP disabled**. Without EP, MoE falls back to the existing non-EP `CutlassExpertsMxfp4` path on `main`. The DP8+EP8 numbers are config **D (TP1/DP8/EP8)** from my validation comment above.

#### Environment

- 8x NVIDIA B300 SXM6 (275,040 MiB each)
- PyTorch `2.13.0+cu130`, CUDA 13.0
- vLLM `main` @ `4be061c5afab`, C extensions rebuilt from `main`
- Model: `RedHatAI/GLM-5.3-MXFP4` (256 routed experts, top-k 8)
- MoE backend: `CutlassExpertsMxfp4` in both runs

#### Note on `--max-num-batched-tokens`

With DP8 and no EP, startup at `--max-num-batched-tokens 32768` crashes during FlashInfer autotune (#58864). The root cause is in the MoE, not in the sparse MLA index conversion that shows up in the stack trace:

- `mxfp4_experts_quant` allocates its blockscale buffer with `VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE * topk` rows.
- `blockscale_offsets` pads every expert to a multiple of 128 rows, so the real requirement is up to `m_numtopk + num_experts * 127` rows.
- Without EP, each rank quantizes the all-gathered batch: 8 × 32768 × 8 = 2,097,152 rows. With `VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE=262144`, that leaves zero slack.
- With random routing, the padding needs 16,384 extra rows, about 3 MB written out of bounds per w1 quant call. `profile_run` does not hit this because all tokens route to the same 8 experts, so no padding is needed.

EP is not affected, because only rank-local rows are counted in the offsets. Details are in #58864.

To stay inside the safe bound, the no-EP run below uses **`--max-num-batched-tokens 32256`**. With `VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE=262144`, the bound is 32,260. For reference:

- 32768 tokens with `VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE=270000`, which leaves enough slack for the padding, also starts and scores 0.880 on GSM8K.
- With `CUDA_LAUNCH_BLOCKING=1`, the 32768 config also gets through startup, but the out-of-bounds write still happens; it just does not fault.

#### Correctness (DP8, no EP, 32256 tokens)

GSM8K, 5-shot, greedy, 512 max tokens, 500 questions, concurrency 64:

| Run | Accuracy | Invalid |
|---|---:|---:|
| Run 1 | 0.874 | 0.000 |
| Run 2 | 0.880 | 0.000 |

This is in line with patched CUTLASS EP8 (0.868) and Marlin EP8 (0.882) above; those two were measured at concurrency 8.

#### Observations

1. **EP8 is faster than no-EP at every point.** The gain is +13–16% at concurrency 1 and +25–38% at concurrency 32 and above.
2. **The gap is largest for the decode-heavy 1024/8192 workload** (+36–38%). Prefill-heavy 8192/1024 gains about +25–27%.
3. A likely explanation, not yet profiled: without EP, every rank runs all 256 experts at `N = moe_intermediate_size / 8 = 256` on the full all-gathered batch. It also permutes and quantizes every `m × topk` row redundantly on all 8 ranks. With EP, each rank runs 32 full-width experts and only quantizes rank-local rows. This makes the grouped GEMMs larger and cuts the redundant activation work.

Caveats:
- This is not a same-session A/B. The EP8 numbers come from the earlier run in this PR, on the PR build `e53e37f9` with `--max-num-batched-tokens 32768` and `VLLM_RAISE_ON_LOGIT_NANS=1`. The no-EP run uses `main` with 32256 tokens and no NaN check.
- Both differences, if anything, favor the no-EP run.
- Concurrency 1 is a single request per point and is noisy.
