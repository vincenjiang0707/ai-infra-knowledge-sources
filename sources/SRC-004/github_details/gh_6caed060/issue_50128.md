## 正文

This comes from an old comment and was never backed by measurements, so the first
task is to establish whether the effect is real at all. It may not be.

Runtime throughput was brought in line with native implementations in #47187, but
nobody has measured startup time either before or since.

### Step 1: is there a difference?

Time engine init for a model that has both implementations, e.g.:

    vllm serve Qwen/Qwen3-0.6B --model-impl transformers
    vllm serve Qwen/Qwen3-0.6B --model-impl vllm

Compare time-to-ready across a few runs and a couple of model sizes. Warm vs cold
HF cache matters, so control for it.

If there is no meaningful difference, say so and close this issue. That is a
perfectly good outcome and still worth having measured.

### Step 2: only if a delta shows up

The backend does some work at load time that native implementations do not, so
these are plausible starting points rather than known causes:

- `fuser.py` — `get_fuser` traces each module class with `fx` to match it against
  the available fusers. Cached per class, but tracing is not free.
- `base.py` — `recursive_replace` walks the module tree applying fusers per instance.
- Config resolution and `auto_map` handling for remote-code models.

A profile of init (py-spy or cProfile) will be more informative than guessing from
this list.

### Done when

Either the startup delta is quantified and explained, or it is shown that there
isn't a meaningful one and this is closed.

### YuchyJ · 2026-08-18

Hi, I tested this case on my RTX 3050 Laptop (4GB VRAM), driver 610.88 / CUDA 13.0.
The difference on my machine is real and large, and ~41% of the gap is
`recursive_replace`. But the cost is inside `RMSNormFuser.fuse()`, not in
`get_fuser`.

## Env

1. The operating system is WSL2 (Ubuntu, kernel 6.6.87.2) on Windows 11. I'm using
   vLLM `0.1.dev20005+gc94cdd0ae`, installed with `VLLM_USE_PRECOMPILED=1`, torch
   2.13.0+cu130; ran `Qwen/Qwen3-0.6B` with a warm HF cache.
2. Config: `enforce_eager=True`, `max_model_len=2048`,
   `gpu_memory_utilization=0.70`, plus
   `VLLM_WSL2_ENABLE_PIN_MEMORY=1 VLLM_USE_FLASHINFER_SAMPLER=0`.

   Note: I used `enforce_eager=True` because CUDA graph capture does not fit in
   4GB, so these numbers exclude compile/cudagraph time. The two env vars are
   needed to start vLLM at all on WSL2 (that looks like a separate `startup-ux`
   problem and I'm happy to file it on its own.)

## Method

I timed `LLM(...)` construction only (no HTTP server), with one process per run, to
avoid recording repeated engine init inside a single process:

```python
import sys, time
from vllm import LLM

def main():
    impl = sys.argv[1]
    t0 = time.perf_counter()
    LLM(model="Qwen/Qwen3-0.6B", model_impl=impl, max_model_len=2048,
        gpu_memory_utilization=0.70, enforce_eager=True)
    print(f"RESULT\t{impl}\t{time.perf_counter() - t0:.3f}")

if __name__ == "__main__":
    main()
```

Each timing is a fresh `python` process -- the shell loop re-invokes the script, so
no state from a previous run leaks into the next one:

```bash
{ for i in 1 2 3; do python bench_init.py transformers; done;
  for i in 1 2 3; do python bench_init.py vllm; done; } 2>&1 \
  | grep --line-buffered RESULT | tee results.txt
```

I first ran one of each to check the setup worked (50.9s and 35.3s -- these are
the cold numbers referenced below), then ran the loop above, and reran the same
loop about an hour later. The two sets of six agree with each other.

| impl | steady-state runs (s) | steady median |
| --- | --- | --- |
| `transformers` | (excluding 1 cold start for 51.8s), 45.247, 45.744, 45.846, 47.337, 48.018  | **45.85** |
| `vllm` | 26.960, 27.071, 27.214, 27.442, 27.978, 28.120 | **27.33** |

**Steady-state gap: 18.5s (1.68x).** Within-group spread is under 3s and the two
groups do not overlap at all, so the effect is well clear of the noise here.

One caching note: besides the HF cache mentioned in the issue, the first
`transformers` run of a session was ~5s slower than steady state in both sessions
(50.9 and 51.8 vs ~45.8). I assume this is the OS page cache holding the torch
shared objects. I only have one comparable cold measurement for `vllm` (35.3) and
it is not a clean comparison(since the `vllm impl` runs directly after the
`transformers` impl), so I would not draw a conclusion about the two
backends' cold-start behaviour, just noting that controlling for the HF cache
alone is not enough.

## What it is not

Two things I ruled out:

1. **Not weight I/O.** vLLM's own log line `Loading weights took` is 0.44s
   (transformers) vs 0.45s (vllm), single logged run each. In the same runs,
   `Model loading took` is 6.98s vs 2.72s, so the gap is in *building* the
   model, not in reading the checkpoint.
2. **Not import cost.** From the py-spy profiles, the `from vllm import LLM`
   frame is 1202 samples (transformers) vs 1364 (vllm) -- comparable in absolute
   terms.

## Where it is

py-spy, `--subprocesses`, default 100Hz. 8650 samples (transformers) vs 5652
(vllm), so the profiled delta is 2998 samples. Counts sum all non-nested boxes per
function -- `_recursive_replace` recurses, so several of these appear in more than
one stack and the single widest box understates them.

```
causal.py:39              __init__                1727   58% of the 2998 gap
`-- base.py:172             recursive_replace()   1220   41%
    `-- rms_norm.py:199       fuse                1126   38%
        `-- _symbolic_trace.py:914  trace         1077   36%
```

These are inclusive counts along a single call chain: each line is contained in
the line above, so they do not sum. All four frames have 0 samples in the `vllm`
profile.

**Key discovery:** `RMSNormFuser.fuse()` calls `trace(module)` per module
**instance**, and the fx trace accounts for ~96% of `fuse`'s time and ~88% of all
`recursive_replace` time.

Qwen3-0.6B has 113 RMSNorm instances (28 layers x 4, plus the final norm), so 113
full symbolic traces run during startup, purely to recover the scalar `eps`. This
should scale linearly with layer count, so I would expect it to be worse on deeper
models.

**One correction to your guess:** `get_fuser` (`fuser.py:82`) is only 51 samples,
0.59% of the profile. The per-class cached tracing is cheap. The cost is the
fuser's own per-instance trace inside `fuse()`.

## Possible directions

I have not benchmarked this and I may still be missing a constraint.

My first thought was just to read the `eps` attribute directly, but that is not
safe on its own: `LlamaRMSNorm` / `Qwen3RMSNorm` / `MistralRMSNorm` / `T5LayerNorm`
store `variance_epsilon`, while `GemmaRMSNorm` / `Gemma2RMSNorm` store `eps`. A
missing name is harmless (fall back to tracing), but an attribute that exists and
is *not* the one `forward` actually uses would silently produce a wrong `eps` --
and since the fuser matches on dataflow, it can be handed a class nobody has
inspected.

Caching the trace per class is also unsafe: the `get_fuser` cache key is
`(type, child names)`, which does not distinguish instances, so two instances of
the same class configured with different `eps` would collide.

What might work is to *verify the attribute name once per class*, reusing the
trace that `get_fuser` already does:

- `RMSNormFuser.match()` already receives the graph and already extracts
  `zero_centered` from it. It could additionally resolve `eps` from the graph,
  compare it against candidate attribute names (`variance_epsilon`, `eps`, ...),
  and store the name that matches on the fuser -- which is already cached per class.
- `fuse()` then does `getattr(module, resolved_name)` per instance: free, still
  per-instance, and verified against the real dataflow for that class.
- If no name matches, fall back to the current per-instance trace.

This is safe because `forward` is the same code for every instance of a class, so
the attribute *name* generalises even though the *value* must not.

Happy to prototype either if that would be useful.

## Caveats

- Single low-end consumer environment; the absolute numbers will not transfer.
- `enforce_eager=True`, and a very small model -- fixed per-module overhead is a
  larger share here than it would be with a large model.
- py-spy inflates the run (75.5s under the profiler vs ~46s unprofiled). fx
  tracing is Python-call-heavy, so its share is probably somewhat overstated. The
  sample counts above are of the profiled runs.
