### Model

```
deepseek-ai/DeepSeek-V4-Flash-0731
```

### 🐛 Describe the bug

With `--load_format fastsafetensors`, the server starts and serves requests without error, but generation output is incoherent (not just low-quality — literal token salad mixing unrelated languages/scripts/digits), **even under greedy decoding (`temperature=0`)**. Switching to the default loader (removing the flag entirely) with an otherwise-identical launch command produces fluent, well-formed text for the same prompt and sampling parameters.

This looks like a weight-loading correctness bug specific to `fastsafetensors` for this model's TP+EP sharding, not a config or template issue — we independently ruled out chat-template/prompt-encoding as the cause (verified via `/tokenize` that the prompt's special tokens resolve to the exact expected IDs), and ruled out sampling randomness (reproduced identically at `temperature=0`).

### Launch command (bugged)

```bash
vllm serve deepseek-ai/DeepSeek-V4-Flash-0731 \
  --tensor-parallel-size 2 \
  --enable-expert-parallel \
  --trust-remote-code \
  --max-model-len 262144 \
  --distributed-executor-backend ray \
  --load_format fastsafetensors \
  --kv-cache-dtype fp8 \
  --block-size 256 \
  --gpu-memory-utilization 0.8
```

### Repro

Prompt (raw `/v1/completions`, DeepSeek-V4's own chat-mode encoding, `add_special_tokens=false`):
```
<｜begin▁of▁sentence｜><｜User｜>What is 2+2? Answer in one word.<｜Assistant｜></think>
```

**With `--load_format fastsafetensors`** (`temperature=1.0`, `max_tokens=32`):
```
eBook '++lang()' non e 'undefined'.
        // In quel caso non deve essere tradotto.
        // Nota: menzionare un OG
```

**Without `--load_format fastsafetensors`** (identical prompt/params, only the loader changed):
```
eBook. Please don't try to read it directly.","price":0,"duration":0,"currency":null,"url":"https://www.smashwords.com/books/view/860089"}]...
```
(Still doesn't answer the question — that's a separate, likely attention/kernel-level issue we're still isolating — but the text is grammatically well-formed English/JSON rather than token salad.)

### Expected behavior

Output coherence (grammaticality) should not depend on the weight-loading backend used, given both claim to load the same checkpoint bit-for-bit. This suggests `fastsafetensors` is either mis-mapping tensors (e.g. quantization scale tensors paired with the wrong weight tensor) or mis-sharding weights for this model's TP+EP configuration.

### gitbisector · 2026-09-26

Tried to reproduce on 2x GB10 (TP2 + `--enable-expert-parallel`, your flags plus `--enforce-eager`, vLLM's multi-node launcher instead of Ray) with both current main and 0.26.0, fastsafetensors 0.3.3 and 0.4.0. It does not reproduce. After loading, all parameters matched `--load-format auto` on both ranks, and greedy output matched too; your prompt answers `4`. Your default-loader run also didn't answer "2+2", so the problem may be downstream of loading on your setup. Ray, CUDA graphs and your exact wheels are what we didn't match.

To check the loader on your setup, add this right after `model.load_weights(...)` in `DefaultModelLoader.load_weights`, boot once with each load format, and diff the output per rank:

```python
import hashlib
r = torch.distributed.get_rank()
for n, p in model.named_parameters():
    b = p.detach().contiguous().reshape(-1).view(torch.uint8)
    h = hashlib.sha1(b[:4096].cpu().numpy().tobytes() + b[-4096:].cpu().numpy().tobytes()).hexdigest()[:12]
    print("DIGEST", r, n, p.dtype, tuple(p.shape), int(b.sum(dtype=torch.int64)), h)
```

If the digests match between loaders, the loader is ruled out.
