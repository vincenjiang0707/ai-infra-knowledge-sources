### wenyili · 2026-05-12

The OOM happens during the profiling phase, not real KV cache allocation — the traceback points at `_init_minimal_kv_cache_for_profiling`, which sets up a "minimal" KV cache so cudagraph capture has something to measure against. For this model that allocation isn't minimal at all:

- Qwen3.6-35B-A3B is hybrid (Mamba `linear_attn` + `self_attn`), so the 32 layers get split into **8 KV cache groups**.
- To align attention pages with mamba pages, `block_size` is bumped to **2096** (`Setting attention block size to 2096 tokens...` in your log).
- Per group, the profile cache is sized for `max_cudagraph_capture_size × block_size = 512 × 2096 ≈ 1.07 M tokens`, which with fp8 KV works out to ~1 GiB — matching the `Tried to allocate 1.02 GiB` in your error.
- **8 groups × ~1 GiB ≈ 8 GiB** of profile-only allocation, on top of the 15.4 GiB of weights already on GPU.

### About `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0`

Despite the name, setting it to `0` does **not** skip the cudagraph profiling step. Looking at `gpu_worker.py:determine_available_memory()`, `profile_cudagraph_memory()` is called unconditionally whenever cudagraph is enabled; the flag only controls whether the measured value is *subtracted* from the KV-cache budget afterwards. So in this OOM the flag has no effect — the measurement (and its OOM-prone minimal KV allocation) still runs.

### Workarounds

1. `--enforce-eager` — sets `cudagraph_mode=NONE`, which is the only condition under which `profile_cudagraph_memory()` is fully skipped.
2. `--compilation-config.max_cudagraph_capture_size=64` (or lower) — keeps cudagraph on but shrinks the per-group profile allocation from ~1 GiB to ~128 MiB.
3. Raise `--cpu-offload-gb` to free more GPU memory before profiling.
