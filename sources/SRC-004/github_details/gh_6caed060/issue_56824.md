# [Issue #56824] [Bug]: Engine startup on DGX Spark (GB10, unified memory) collapses host memory — NV_ERR_NO_MEMORY while MemAvailable reports ~22 GiB

source: https://github.com/vllm-project/vllm/issues/56824
state: open | updated: 2026-09-27T10:12:18Z
labels: quantization

## 正文

### Your current environment

- **Hardware:** NVIDIA DGX Spark / GB10, SM121, aarch64, **121.7 GiB unified memory**, driver **580.173.02**, CUDA 13.0, kernel **7.0.0-1019-nvidia**
- **vLLM:** 0.29.0 (torch 2.13.0+cu130)
- **Model:** `RadixArk/Qwen3.8-Flash-Next-NVFP4` (Qwen4Exp architecture), `--tensor-parallel-size 1`
- **Flags:** `--quantization modelopt`, `--kv-cache-dtype fp8_e4m3`, `--gpu-memory-utilization 0.70`, MTP k=3 via `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`, `--compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[4,8,12,16,20,24]}'`, `--no-enable-flashinfer-autotune`, `--no-enable-prefix-caching`, `VLLM_USE_V2_MODEL_RUNNER=1`, `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`
- **Important:** **no request is served.** This happens during engine initialization only, at the KV-cache / graph-capture phase, right after `Loading weights took 549.60 seconds` and the encoder-cache initialization.

### Describe the bug

The engine drives the unified memory pool to exhaustion during startup and the driver reports failure while the host still reports plenty of free memory. Host memory collapses within seconds (sampled every 2 s):

| ts | MemAvailable | physical used | cgroup `memory.current` | residual |
|---|---|---|---|---|
| 13:23:44 | 29.083 | 92.605 | 23.581 | 82.050 |
| 13:23:46 | 29.081 | 92.607 | 23.581 | 82.053 |
| 13:23:48 | 29.079 | 92.609 | 23.582 | 82.055 |
| 13:23:50 | 29.077 | 92.611 | 23.581 | 82.057 |
| 13:23:52 | 25.931 | 95.757 | 25.999 | 82.653 |
| 13:23:55 | 20.180 | 101.508 | 31.671 | 80.722 |
| 13:23:57 | 11.469 | 110.219 | 33.197 | 80.859 |
| 13:23:59 | **2.538** | **119.150** | 33.972 | 81.343 |

(values in GiB; `physical used = MemTotal - MemAvailable`; `residual = MemTotal - MemFree - Active - Inactive - Slab - PageTables - Unevictable`)

**29 GiB disappeared in 9 seconds.** At the same time the driver logged:

```
NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY] (0x00000051) returned from _memdescAllocInternal(pMemDesc) @ mem_desc.c:1359
```

### Why the host cannot see it

- physical peak **119.2 / 121.7 GiB**, while the engine's process RSS was **1.8 GiB** and its cgroup `memory.current` never exceeded **34 GiB**
- not page cache: `Cached` was 19.8 GiB and is fully accounted for
- on the same host at idle the residual is **1.1 GiB**; under load it is **77-90 GiB**
- `MemAvailable` reported **22.5 GiB free at the moment the driver failed**

Consequence for operators: no host-side signal (meminfo, PSI, vmstat) can trigger a guard before the device allocation is already failing.

### Workaround

Reducing the startup allocation footprint keeps the host healthy (same host, same model, same flags otherwise):

| config | min MemAvailable | max physical | max cgroup `memory.current` |
|---|---|---|---|
| `--max-num-seqs 256`, `--max-model-len 32768` | **2.54 GiB** | 119.2 GiB | 34 GiB |
| `--max-num-seqs 32`, `--max-model-len 16384` | **22.5 GiB** | 99.2 GiB | 16.7 GiB |

Note: `NV_ERR_NO_MEMORY` still appears with the reduced configuration, so that message alone is not a reliable indicator — it looks like a retry pattern. The reliable signal is the host-side residual.

An external 2-second host guard (stop the unit below a hard `MemAvailable` line) is what kept this box out of a kernel OOM: 0 `oom-kill` events across all runs, while a comparable earlier configuration produced 197 kernel OOM dumps over two days.

### Hypothesis

Same class as #56457 / #55569: allocations streamed through the caching allocator whose size grows monotonically. On a discrete GPU `cudaMalloc` eventually fails and the allocator flushes its cache and retries; on unified-memory GB10 `cudaMalloc` keeps succeeding until the driver has nothing left, so the failure surfaces as a device-allocation error (and a host-memory collapse) instead of a Python OOM. Here the source is the startup KV-cache profiling / graph capture rather than a long prefill.

The fix direction from those issues (reusable or coarse-rounded buckets / workspace manager) would address this case as well.

### Disclosure

Local overlays are applied to this build: PLE disk-offload (model weights partially NVMe-backed), an MTP index remap, and a one-line `modelopt.py` dispatch fix. `models/qwen4_exp/nvidia/ops/qsa_indexer.py` is **unmodified** upstream — we verified it uses the fixed page-table width (`columns = page_table.shape[1] * k_cache.shape[1]`) and therefore does **not** carry the #56457 regression. The startup curve is therefore partially build-specific; the invisibility mechanism is not.

Full 2-second telemetry (all runs, TSV) and the sampling script are available on request.

Run summary: `min MemAvailable 6.27 GiB`, `max physical 115.4 GiB`, `max cgroup memory.current 33.9 GiB`, and **10 new** `NV_ERR_NO_MEMORY` driver messages. Our host guard stopped the unit at 6.27 GiB, so the engine never reached a request-serving state.

Also note that `max cgroup memory.current` at the collapse is **~34 GiB in both the 256-seq and the 32-seq runs** — i.e. this phase allocates a roughly fixed ~10 GiB inside the cgroup plus ~16 GiB that the cgroup cannot see, regardless of `max-num-seqs` / `max-model-len`.

**Corrected statement:** lowering `max-num-seqs` / `max-model-len` reduces the footprint during weight loading, but does **not** remove the post-load peak (KV-cache sizing / CUDA graph capture). On this host an external 2-second guard is currently the only thing standing between this phase and a kernel OOM — we have recorded 0 `oom-kill` events across all runs, but only because the engine was stopped by that guard.

Next levers we are testing, in order:
1. reduce `cudagraph_capture_sizes` (currently `[4,8,12,16,20,24]` with `FULL_DECODE_ONLY`) or disable graph capture entirely;
2. `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=64` (the mitigation from #56457 / #55569) — cheap and targeted at the churn pattern;
3. `--enforce-eager` as the fallback, accepting the throughput cost.

I will report back with measurements rather than estimates.
