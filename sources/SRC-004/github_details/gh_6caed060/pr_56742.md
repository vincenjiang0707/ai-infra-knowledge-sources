## 正文

## Purpose

This PR addresses three Qwen4Exp issues found during model bring-up. It places the MTP hidden buffer on the configured device, handles two config compatibility cases (M-RoPE keys and Transformers' `layer_types` spelling), and includes Qwen4Exp in the existing Qwen Triton warmup dispatch.

## Changes

### The MTP hidden buffer's device

`torch.empty` for the spec-decode hidden buffer passes no `device`, so the buffer follows the ambient default instead of `vllm_config.device_config.device`. The NVIDIA and AMD backends carried the same allocation.

Both now call `make_mtp_hidden_buffer()` in `vllm/models/qwen4_exp/common/mtp.py`, which keeps the existing condition (`speculative_config.method == "mtp"` on the last pipeline stage), shape (`max_num_batched_tokens x hc_count * hidden_size`) and dtype, and passes the configured device.

### Config parsing

- **M-RoPE keys.** Qwen4Exp uses `mrope_section` and `mrope_interleaved`, which transformers' rope validator does not know for `rope_type="default"`, so it reports them as unrecognized during config loading. Both are added to `ignore_keys_at_rope_validation` on the text config and on the outer config that mirrors its `rope_parameters`; other unknown keys still warn.
- **`layer_types` spelling.** transformers' Qwen4Exp config canonicalizes `full_attention` entries to `qwen_sparse_attention`, so checkpoints re-exported through it serialize that name, and vLLM — which keys on `full_attention` plus `indexer_n_heads` — does not classify those entries as QSA layers. The spelling is mapped back at config construction.

### Triton warmup

`qwen_triton_warmup` covers the gated RMS norm, the causal conv, the post-conv preparation and the decode state update. For Qwen4Exp, these remain Triton kernels regardless of the selected prefill backend, but `qwen4_exp` and `qwen4_exp_text` are not in `_QWEN_MODEL_TYPES`, so the warmup returns at the gate. Without the dispatch entry, these kernels can compile on first use.

`qwen4_exp_mtp` is not added: `kernel_warmup` passes `worker.vllm_config.model_config`, which is the target model's.

## Notes

The device test allocates on `meta`, which is never the ambient default, so it catches an implicit allocation without requiring CUDA. The warmup test stops at the dispatch gate; the kernels themselves are covered by the existing CUDA test in the same file.
