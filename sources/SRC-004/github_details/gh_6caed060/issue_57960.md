## 正文

### 🚀 The feature, motivation and pitch

`tencent/Hy4-preview-FP8` runs on gfx950 through the ROCm support added in #57526, but its ModelOpt MXFP8 operations currently use Triton even when `VLLM_ROCM_USE_AITER=1`:
```text
Using RocmDotScaledMxfp8LinearKernel for MXFP8 GEMM
Using 'TRITON_MXFP8' MxFp8 MoE backend.
```
This feature request tracks two independent AITER enablement categories. 

cc: @akii96 (I know you're focused on gfx942, but wanted to keep you in the loop)

### 1. MXFP8 MoE enablement
vLLM already provides `AiterMxfp8Experts`, but its compatibility check rejects Hy4.
The current AITER implementation requires:
- `SWIGLUOAI_UNINTERLEAVE`
- SwiGLU alpha `1.702`
- SwiGLU beta `1.0`
Hy4 instead uses clamped SwiGLU:
```text
gate = clamp(gate, max=limit)
up   = clamp(up, -limit, limit)
out  = silu(gate) * up
```
The published checkpoint sets `swiglu_limit=10.0`.

#### AITER work
- Support Hy4’s gate/up layout and clamped SwiGLU semantics in the gfx950 MXFP8 fused-MoE kernel.
- Preserve native 1×32 E8M0 weights/scales.
- Support Hy4 routing, expert masks and tensor-parallel execution.
- Add correctness tests against a BF16/dequantized reference.

#### vLLM work
- Represent Hy4’s activation semantics accurately in `FusedMoEConfig`.
- Update `AiterMxfp8Experts.is_supported_config`.
- Forward activation, clamp and gate-layout arguments to AITER.
- Verify automatic selection and explicit `--moe-backend aiter`.
- Preserve `TRITON_MXFP8` fallback.
- Add Hy4 MXFP8 MoE unit and end-to-end coverage.

### 2. MXFP8 dense linear/GEMM enablement
Hy4’s dense projections use ModelOpt MXFP8:
- E4M3 values
- E8M0 scales
- 1×32 scaling blocks
- BF16 output
This is not format-compatible with AITER’s conventional FP8 128×128 block-scale GEMMs. vLLM therefore selects `RocmDotScaledMxfp8LinearKernel`.

#### AITER work
- Add a gfx950 dense MXFP8 GEMM accepting the 1×32 E8M0 format.
- Support dynamic `M`, weight pre-shuffling, split-K and caller-owned output buffers.
- Add runtime configuration lookup, shape logging and a gfx950 tuner.
- Add correctness tests against dequantized BF16.

#### vLLM work
- Add an AITER-backed `Mxfp8LinearKernel`.
- Register it in `_POSSIBLE_MXFP8_KERNELS[PlatformEnum.ROCM]` ahead of Triton when supported.
- Implement gfx950, AITER and scale-layout capability checks.
- Add weight/scale preprocessing and pre-shuffling.
- Support `torch.compile` and full/piecewise cudagraph capture.
- Preserve Triton and emulation fallbacks.
- Add kernel-selection and end-to-end tests.


### Alternatives

- Continue using `RocmDotScaledMxfp8LinearKernel` and `TRITON_MXFP8`.
- Dequantize MXFP8 weights to BF16, with additional memory and performance cost.
- Generic AITER A8W8 block-scale kernels are not a valid substitute because their scale format differs from ModelOpt MXFP8.
