### 🐛 Describe the bug

### Summary

Under `pipeline-parallel-size > 1`, the vLLM scheduler dispatches up to `max_running_seq` sequences at once to the first pipeline stage instead of splitting them into `max_running_seq / PP_size` micro-batches per stage. As a result, enabling chunked prefill under PP adds scheduling and kernel-launch overhead **without** activating pipeline parallelism — chunks are serialized rather than pipelined.

### Environment

- Hardware: NVIDIA GB300 (SM103) NVL72
- Model: DeepSeek-R1-0528-FP4
- Workload: ISL = 128K, OSL = 1, aggregated mode, single 4-GPU node

### Reproduction

Configuration: `--pipeline-parallel-size 4 --tensor-parallel-size 1 --enable-chunked-prefill --max-num-batched-tokens <chunk>`. Sweep `<chunk>` over {4K, 12K, 32K} and compare against no-chunk baseline. All other knobs identical.

### Observed behavior — chunk-size sweep on GB300, PP4, ISL=128K / OSL=1

| Config         | Peak TPS/GPU |
|----------------|:------------:|
| No-chunk       |   **1,678**  |
| Chunk 32K      |    ~1,500    |
| Chunk 12K      |    1,536     |
| Chunk 4K       |    1,347     |

Under correctly pipelined micro batching, more chunks per request should produce **more** pipeline fill and **higher** throughput (4K > 12K > 32K > no-chunk). We observe the **opposite** ordering: smaller chunks are strictly worse, and every chunked configuration loses the concurrency scaling that the no-chunk baseline has.

this is the empirical signature of chunks being serialized through the pipeline rather than flowing through stages as micro-batches.

### Root cause (from internal code review)

In the PP scheduler path, the running set is dispatched in a single batch up to `max_running_seq` sequences, sent to the first pipeline stage. There is no splitting into `max_running_seq / PP_size` micro-batches across stages, so the remaining stages are starved instead of overlapped.

### njhill · 2026-05-24

The main cause of this issue is that we were not actually pipelining at all with async scheduling due to how the broadcast of sampled tokens is being done (with the exception of the chunked-prefill-only case with ModelRunner V1, where intra-request pipelining works after https://github.com/vllm-project/vllm/pull/38726).

This should be fixed in Model Runner V2 with https://github.com/vllm-project/vllm/pull/42187 (should be merged soon).

Though this does not cover possible additional scheduler optimizations to improve balancing of new requests between microbatches. But as long as requests are arriving at a steady rate, they should still be reasonably balanced.
