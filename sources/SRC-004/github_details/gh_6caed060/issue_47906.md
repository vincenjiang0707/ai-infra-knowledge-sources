### 🐛 Describe the bug

Since the Gemma4 parsers were replaced with the engine-based implementation (#45588, first shipped in v0.24.0), `_parse_gemma4_args` returns every*bare argument value as a JSON string. Up to v0.23.0, the legacy `Gemma4ToolParser` converted bare values to their JSON types (`int` / `float` / `true` / `false`).

### Reproduction (no GPU)

```python
from transformers import AutoTokenizer
from vllm.tool_parsers import ToolParserManager

tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")  # any tokenizer
parser = ToolParserManager.get_tool_parser("gemma4")(tok)

out = parser.extract_tool_calls(
    "<|tool_call>call:f{n:5,x:22.8,b:true,arr:[1,2.5]}<tool_call|>", None)
print(out.tool_calls[0].function.arguments)
# v0.24.0:  {"n": "5", "x": "22.8", "b": "true", "arr": ["1", "2.5"]}
# expected: {"n": 5, "x": 22.8, "b": true, "arr": [1, 2.5]}   (v0.23.0 behavior)
```

### redd34 · 2026-09-26

This still reproduces on v0.30.0 and on main @ 3b4566c. It also affects values nested inside objects and arrays whose schema doesn't give them a type, so schema-based coercion doesn't fix them:

```python
from vllm.parser.gemma4 import _parse_gemma4_args
print(_parse_gemma4_args('location:<|"|>Tokyo<|"|>,details:{temp:25,unit:<|"|>celsius<|"|>},flags:[true,1,null]'))
```

```text
v0.30.0 / main 3b4566c: {'location': 'Tokyo', 'details': {'temp': '25', 'unit': 'celsius'}, 'flags': ['true', '1', 'null']}
main + #47909:          {'location': 'Tokyo', 'details': {'temp': 25, 'unit': 'celsius'}, 'flags': [True, 1, None]}
```

`gemma4` `extract_tool_calls` gives the same result, with a tool whose schema declares `details: {"type": "object"}` and `flags: {"type": "array"}`: `{"details": {"temp": "25", ...}, "flags": ["true", "1", "null"]}`. #47909 still applies cleanly to current main and fixes this case too. For comparison, SGLang's and Ollama's Gemma 4 parsers keep the types, since Gemma 4 marks every string explicitly with `<|"|>`.
