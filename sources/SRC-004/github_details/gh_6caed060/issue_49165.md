## 正文

## Environment

- vLLM: `v0.25.1` (`752a3a504485790a2e8491cacbb35c137339ad34`)
- Container: `vllm/vllm-openai:v0.25.1`
- FlashInfer: `flashinfer-python==0.6.13`, `flashinfer-cubin==0.6.13`
- GPU: NVIDIA H100 80 GB HBM3, driver 580.105.08
- CUDA: 13.0 (`torch==2.11.0+cu130`)
- Model: `nvidia/DeepSeek-V4-Pro-NVFP4`
- Serving topology: flat TP16 on two eight-GPU nodes
- FlashInfer issue: https://github.com/flashinfer-ai/flashinfer/issues/4062

## Summary

vLLM 0.25.1 selects `FlashInferFp8DeepGEMMDynamicBlockScaledKernel` before its pure DeepGEMM
candidate for a compatible dense block-FP8 linear. At runtime, the hybrid sends `M < 32` to
FlashInfer's `fp8_blockscale_gemm_sm90`.

DeepSeek-V4-Pro's mandatory mixed warmup reaches that branch at `M=16` on every TP rank. Eight
workers on each node then cold-build the same embedded TensorRT-LLM DeepGEMM kernel against one
shared cache. FlashInfer 0.6.13 has no inter-process cache-key build lock and can fail in its CUDA
driver-library load sequence. In the captured failing launch, startup terminated with eight
copies of:

```text
CUDA error: invalid argument
```

The server starts, captures CUDA graphs, and serves coherent output when the existing vLLM
candidate gate is disabled:

```bash
export VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0
```

A direct eight-H100 operator A/B established that this is a cold-cache race, not an unsupported
`M=16` shape: the exact operator passes on all eight GPUs with per-worker JIT caches. A separate
cold stock/default-selector full-server launch also succeeded and served coherent output, which
confirms that failure is timing-dependent rather than inevitable. The final source-level patch
passed both a genuinely rebuilt-wrapper shared-cache test and a complete two-node/16-H100 TP16
server with the FlashInfer selector enabled.

## End-to-end reproduction

Start one process launcher on each eight-GPU node, with `NODE_RANK=0` on the API node,
`NODE_RANK=1` on the second node, and `HEAD_NODE` set to the API node's routable hostname. Leave
`VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER` at its default value of `1`:

```bash
ENDPOINT=--headless
if [ "$NODE_RANK" -eq 0 ]; then
  ENDPOINT="--api-server-count 1 --host 0.0.0.0 --port 8000"
fi

vllm serve /model \
  --served-model-name deepseek-ai/DeepSeek-V4-Pro \
  --tensor-parallel-size 16 \
  --nnodes 2 --node-rank "$NODE_RANK" \
  --master-addr "$HEAD_NODE" --master-port 29500 \
  --max-model-len 2200 \
  --max-num-seqs 256 \
  --kv-cache-dtype fp8 \
  --block-size 256 \
  --gpu-memory-utilization 0.90 \
  $ENDPOINT
```

The selected backends and captured failure were:

```text
Selected FlashInferFp8DeepGEMMDynamicBlockScaledKernel for Fp8LinearMethod
Using 'MARLIN' NvFp4 MoE backend
Warming up DeepSeek V4 sparse MLA attention for mixed tokens=16.
CUDA error: invalid argument
CUDA error: invalid argument
CUDA error: invalid argument
CUDA error: invalid argument
CUDA error: invalid argument
CUDA error: invalid argument
CUDA error: invalid argument
CUDA error: invalid argument
```

A separate localization launch used `--enforce-eager` and failed before CUDA graph capture, so the
error is not a graph replay failure. Operator-boundary synchronization places it in the dense
replicated `fused_wqa_wkv` projection before routed-expert MoE in that forward pass. The
reproduction command above does not require eager mode.

Repeat with:

```bash
export VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0
```

The same image, checkpoint, and launch select `DeepGemmFp8BlockScaledMMKernel`, retain the Marlin
NVFP4 MoE backend, complete mixed warmup and normal CUDA graph capture, and start the API. An
additional check completed eight simultaneous requests with exactly 1,024 input and 1,024 output
tokens each: 8/8 responses, zero errors, followed by a clean CUDA/illegal-memory-access scan.

## Direct operator evidence

The model projection has these exact arguments:

```text
activation:   [16, 7168], torch.bfloat16
weight:       [2048, 7168], torch.float8_e4m3fn
weight scale: [16, 56], torch.float32, stride=(56, 1), contiguous
blocks:       128x128
```

With a new shared `TRTLLM_DG_CACHE_DIR`, eight concurrent workers reproduced `CUDA error: invalid
argument`. With the cache path made unique per local rank, every worker passed:

```text
PASS cosine=0.99966240 relative_l1=0.02618705
EXIT=0
```

The complete reproducer, lower-level source analysis, cache-hardening results, and patched
full-server validation are in the linked FlashInfer issue.

## Why vLLM reaches the race

`FlashInferFp8DeepGEMMDynamicBlockScaledKernel` is an eligible CUDA block-FP8 candidate and its
`apply_block_scaled_mm` invokes `dynamic_flashinfer_deepgemm_blockscale_gemm`. That operation uses
`torch.cond` to dispatch:

```text
M < 32  -> flashinfer.gemm.fp8_blockscale_gemm_sm90
M >= 32 -> vLLM DeepGEMM
```

This is why the mandatory `M=16` warmup is sufficient to trigger the problem before the API is
ready. The FlashInfer operator internally JIT-compiles a shape-specific SM90 cubin. All local TP
workers inherit the same default TensorRT-LLM cache root and reach the cold cache together.

The direct A/B also rules out a suspected scale handoff bug. On H100, vLLM's DeepGEMM
post-processing leaves this checkpoint's 128x128 FP32 scale tensor contiguous at `[16, 56]` with
stride `(56, 1)`. Both BF16-weight and FP8-weight forms pass when the JIT build is not raced.

## Expected behavior

A stock, supported multi-GPU vLLM configuration should not fail mandatory startup because all
local ranks cold-compile the same selected backend kernel.

## Actual behavior

The candidate passes vLLM's support checks, but FlashInfer 0.6.13 can fail during its first
multi-process JIT build. In the captured failing launch, the engine exited before serving any
request. Another stock cold launch passed, as expected for a timing-dependent race.

## Suggested resolution

The primary fix belongs in FlashInfer's embedded TensorRT-LLM compiler: serialize each cache-key
build, recheck after acquiring the lock, reject failed or empty NVCC output, require a regular
nonempty cached cubin, and propagate publication failures. The lower-level patch has completed its
exact eight-H100 rebuilt-wrapper before/after and three two-node cache-hardening tests. It also
passed a complete two-node/16-H100 TP16 server: every rank selected the FlashInfer candidate,
mixed warmup and CUDA graph capture completed, and both functional requests returned HTTP 200 with
coherent answers.

For vLLM, please consider gating this candidate for the affected FlashInfer release in
multi-worker serving, or changing its default to the pure DeepGEMM candidate until a fixed
FlashInfer version is packaged. Once the lower-level fix is available, the small-`M` optimization
can be enabled again without forcing users to know about the cache race.

## Workaround and tradeoff

```bash
export VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0
```

This removes only the hybrid FlashInfer block-FP8 candidate. It does not cap request concurrency,
dequantize the checkpoint, change KV-cache precision, or alter the separate NVFP4/Marlin MoE
operators. The tradeoff is that small-`M` dense block-FP8 operations use pure DeepGEMM instead of
FlashInfer's swap-AB path, so some decode shapes may lose an optimization.

### ZxxXinI · 2026-07-20

Thanks for the thorough analysis and for filing the upstream counterpart (flashinfer-ai/flashinfer#4062) — cold multi-process JIT builds racing on a shared cache is a recurring failure mode (Triton hit the same class of bug and ended up doing build-in-tmpdir + atomic rename).

A couple of additional mitigations that worked for me in similar setups, for anyone who lands here before a fix ships:

- **Single-process cache pre-warm**: run a one-rank throwaway load (or a tiny script that just calls the `fp8_blockscale_gemm_sm90` path at `M=16`) before launching the TP16 job. Once the cache is hot, the race window disappears entirely and you keep the FlashInfer swap-AB optimization instead of falling back via `VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0`.
- **Per-rank JIT cache dir**: pointing each local rank at its own FlashInfer workspace/cache directory trades disk space and duplicate compile time for correctness — ugly, but useful when you can't pre-warm.

On the vLLM side, beyond gating the hybrid candidate for affected FlashInfer versions, it might be worth adding a generic guard: stagger or serialize the first-touch JIT warmup across *local* ranks (e.g. local-rank-0 builds first behind a file lock, others wait and hit the warm cache). That would protect against this entire class of bug for any JIT-backed kernel candidate, not just this one, since kernel selection happening before warmup means vLLM is effectively the one orchestrating N concurrent cold builds.

Agreed the root fix (per-cache-key build lock + recheck-after-acquire + reject empty/invalid cubins) belongs upstream, but a version-gated default here would save a lot of people a confusing multi-node startup failure.
