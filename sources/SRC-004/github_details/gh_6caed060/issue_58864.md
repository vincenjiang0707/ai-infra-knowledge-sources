### Description

GLM-5.3-MXFP4 fails to start with TP1/DP8 and expert parallelism disabled. The crash occurs during the 32K-token FlashInfer autotune dummy run in sparse MLA logical-to-physical top-k index conversion.

This reproduces on a clean vLLM `main` build and is unrelated to our CUTLASS MXFP4 EP changes.

### Reproduction

Hardware: 8× NVIDIA B300  
vLLM commit: `4be061c5afab`  
PyTorch: `2.13.0+cu130`

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
VLLM_MAX_TOKENS_PER_EXPERT_FP4_MOE=262144 \
vllm serve RedHatAI/GLM-5.3-MXFP4 \
  --trust-remote-code \
  --reasoning-parser glm47 \
  --data-parallel-size 8 \
  --data-parallel-size-local 8 \
  --max-model-len 16384 \
  --max-num-batched-tokens 32768 \
  --max-num-seqs 512 \
  --block-size 64 \
  --gpu-memory-utilization 0.90 \
  --kv-cache-dtype fp8_e4m3 \
  --no-enable-prefix-caching
Do not pass --enable-expert-parallel.
Error
All eight DP workers fail after:
Running FlashInfer autotune with 32768 tokens
The relevant stack is:
flashinfer_mla_sparse.py::forward_mqa
sparse_mla_attention.py::_convert_logical_to_physical_topk
index_group.py::_convert_once
sparse_utils.py::triton_convert_req_index_to_global_index
```

### he-yufeng · 2026-09-27

Read the crash path on current main (eb0f2ca37f). What is certain statically:

The conversion kernel's `block_table` read is guarded only on the column side: `valid_block = (block_id < max_num_blocks_per_req) & (block_id >= 0)` (sparse_utils.py, ConvertReqIndexToGlobalIndexKernel). The row index `req` loaded from `req_id` is never bounds-checked against `block_table.shape[0]`. So any req_id value >= num_requests rows reads out of bounds and produces exactly this signature: CUDA illegal memory access in `triton_convert_req_index_to_global_index`. The Python wrapper already asserts only the length match (req_id vs token_indices), with a comment that knows this family ("a longer req_id writes out of bounds"), so values out of range are the uncovered half.

What I cannot pin without the B300: why DP8-noEP generates out-of-range req_id values during the FlashInfer autotune dummy run at 32K tokens. The suspects, in order: (a) the dummy batch fabricates req_id indices in a global space while block_table stays DP-rank-local; (b) the m_numtopk=2097152 overflow path you mention changes which buffer branch _convert_once takes (the no-buffer path allocates like token_indices with a grid sized by req_id). A 3-line debug print of `req_id_per_token.max()`, `req_id_per_token.shape`, and `block_table.shape` at the crash would settle it.

On fix shape, one caution for whoever picks it up: a silent kernel-side row guard (mask to -1) would stop the crash but silently drop those tokens' attention, which is arguably worse than failing loud. The honest fix fails fast with the named mismatch (req_id range vs block_table rows) at the dummy-run/metadata-construction layer, then the DP8 root cause gets fixed where the ids are built. Happy to write that once the reporter's numbers land; I have no GPU here so I am deliberately not opening a blind patch.
