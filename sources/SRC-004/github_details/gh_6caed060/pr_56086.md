## Purpose

Fixes https://github.com/vllm-project/vllm/issues/39929

In case request has both response_format and tool_choice=auto then we construct structural tags for both constraints and do OR of them.

**IMPORTANT:** to construct structural tag for tools we do a simple trick. Since tool_choice=auto allows by default a tool call or any text, then we cannot use that structural tag. Instead we create a structural tag manually specifying tool_choice to be set as `required`. In that case structural tag would not allow arbitrary text but only valid tool call.

Some time ago there was added support for response_format + tool_choice=required case: https://github.com/vllm-project/vllm/pull/32127
But the idea of this PR #32127 was a bit different and simplier to drop response_format from request and allow only tool call. Current PR #56086 saves both constraints, so the logic behind this patch is a little bit more complicated.

Previous attempts to fix this bug:
* https://github.com/vllm-project/vllm/pull/39969
* https://github.com/vllm-project/vllm/pull/47439
* https://github.com/vllm-project/vllm/pull/47394

All these PRs were closed for unknown reasons, I added authors of these PRs to co-authors.

### yzong-rh · 2026-09-10

Agree with Vadim here. Don't think clearing `repsonse_format` when `tool_choice=auto` is the desired behavior.

On main, when both are set, we honor `response_format` and disallow tool calls. I think this is chosen because `tool_choice=auto` is the default, so if the user specifies `response_format`, we should honor it.

With the branch's changes, we would honor `tool_choice=auto` instead of `response_format`. `response_format` would be silently ignored even if the user specifies it.

From Arvind's report, the desired behavior is to allow both: if the model decides to call a tool, then allow the tool call. If the model decides to generate text content, then apply the constraint.

I think we can accomplish this by: 1) converting `response_format` into a structural tag format ([using such utllity](https://github.com/vllm-project/vllm/blob/7470082f57a0245703be7482544f4b0fd410e1f2/vllm/parser/harmony.py#L508-L542)) and 2) OR the response_format structural tag with the tool_choice auto structural tag. This allows the model to generate either tool call or format compliant final response.

Two downsides: 1) we need to support tool calling structural tag for the model and 2) strict tool calling is implicitly turned on when `response_format` is used. The implementation is non-trivial and doesn't follow from the normal `response_format` path.

A middleground imo could be to warn the user that tool call will be disabled when `response_format` is use.

### vadiklyutiy · 2026-09-27 · COMMENTED

Two issues, same root cause: `structured_outputs_to_format()` moves the constraint into a structural tag, so `validate_xgrammar_grammar()` takes the `structural_tag` branch and skips the per-type logic the constraint used to go through.

**1. JSON Schema support check is lost.** With `tool_choice="auto"` and a strict tool, the response schema becomes a `JSONSchemaFormat` inside the tag, so `has_xgrammar_unsupported_json_features()` never sees it. For `{"type": "number", "multipleOf": 0.5}` — which xgrammar silently ignores — `tool_choice="none"` raises `VLLMValidationError: ... not supported by xgrammar`, while `"auto"` passes validation and compiles a grammar that accepts `{"value": 0.3}`. That exception is also what triggers the `backend="auto"` fallback to guidance/outlines, which do honor `multipleOf`, so the request now silently stays on xgrammar with the constraint dropped. Fix: validate the original `structured_outputs` before merging it into the tag.

**2. Valid Lark grammar is handed to the EBNF compiler.** `params.grammar` goes straight into `GrammarFormat`, which is EBNF-only, bypassing the `grammar_is_likely_lark()` / `from_lark()` path. `Grammar.from_lark('start: "ok"')` succeeds, but the same string inside `GrammarFormat` fails with `EBNF lexer error at line 1, column 6: Unexpected character: ':'`. So a strict tool plus `tool_choice="auto"` plus `structured_outputs={"grammar": "start: \"ok\""}` fails validation instead of returning a response or a tool call, and the fallback does not help either: `serialize_guidance_grammar()` only understands the legacy `structures`/`triggers` tag shape, not the new `format` shape. Fix: convert Lark to EBNF before building the `GrammarFormat`, and cover both syntaxes alongside tools.

Minor, same cause: `regex` loses its `compile_regex_with_timeout()` guard when routed through `RegexFormat`.
