###  Describe the bug

`DeepSeekV3ToolParser.extract_tool_calls_streaming` (and the near-identical `DeepSeekV31ToolParser`) silently drops a tool call whenever its start and end tokens (`<｜tool▁call▁begin｜>` / `<｜tool▁call▁end｜>`) land in the same streaming delta, instead of one token at a time.

The state machine branches purely on comparing start/end token counts between `previous_token_ids` and `current_token_ids`:

```python
# case -- we're starting a new tool call
if cur_tool_start_count > cur_tool_end_count and cur_tool_start_count > prev_tool_start_count:
    ...
# case -- the current tool call is being closed.
elif cur_tool_start_count == cur_tool_end_count and cur_tool_end_count >= prev_tool_end_count:
    if self.prev_tool_call_arr is None or len(self.prev_tool_call_arr) == 0:
        logger.debug("attempting to close tool call, but no tool call")
        return None
```
(`vllm/tool_parsers/deepseekv3_tool_parser.py`, around line 178 and line 208; same shape in `deepseekv31_tool_parser.py`.)

This assumes a tool call always spends at least one delta with `start_count > end_count` (i.e., the opening tag is observed strictly before the closing tag in a *separate* call). When a single delta instead contains a *complete* tool call — start tag, name, arguments, and end tag all at once — `cur_tool_start_count` and `cur_tool_end_count` become equal in the very first call for that tool. The code takes the "closing" branch, finds `prev_tool_call_arr` empty (nothing was ever opened), logs `"attempting to close tool call, but no tool call"`, and returns `None`. The tool call is gone — not delayed, not merged into the next delta, just dropped. `extract_tool_calls` (non-streaming) parses the exact same text correctly, so this is a streaming-only regression relative to the final output.

This isn't an exotic corner case: any time a chunk boundary batches more than one token together — a short function name/arguments, `--stream-interval > 1`, or plain scheduler batching under load — the whole call can arrive in one delta.

This is the same failure mode already fixed for DeepSeek-V3.2 in #36056 ("[Bugfix] Fix Deepseekv32 tool parser when stream interval > 1"), which replaced V3.2's incremental character-by-character state machine with a buffer-until-complete-block strategy specifically because "with stream_interval > 1, multiple parameters or closing tags can arrive in a single delta, causing the state machine to skip parameters and silently drop arguments." `deepseekv3_tool_parser.py` and `deepseekv31_tool_parser.py` still use the old per-token-assumption approach and hit the identical problem — they just never got the same fix.

### Reproduction (no GPU, real vLLM + real DeepSeek-V3 tokenizer)

```python
from transformers import AutoTokenizer
from vllm.tool_parsers.deepseekv3_tool_parser import DeepSeekV3ToolParser

tok = AutoTokenizer.from_pretrained("deepseek-ai/DeepSeek-V3", trust_remote_code=True)

text = (
    '<｜tool▁calls▁begin｜>'
    '<｜tool▁call▁begin｜>function<｜tool▁sep｜>get_weather\n'
    '```json\n{"x": 42}\n```<｜tool▁call▁end｜>'
    '<｜tool▁calls▁end｜>'
)

# Non-streaming: parses correctly.
final = DeepSeekV3ToolParser(tok).extract_tool_calls(text, None)
print("final:", [(c.function.name, c.function.arguments) for c in final.tool_calls])
# final: [('get_weather', '{"x": 42}')]

# Streaming: the whole tool call arrives in a single delta.
token_ids = tok.encode(text, add_special_tokens=False)
dm = DeepSeekV3ToolParser(tok).extract_tool_calls_streaming(
    previous_text="", current_text=text, delta_text=text,
    previous_token_ids=[], current_token_ids=token_ids, delta_token_ids=token_ids,
    request=None,
)
print("streamed:", dm)
# streamed: None   <-- tool call silently dropped
```

Swapping in `DeepSeekV31ToolParser` with the V3.1-style delimiter format (`<｜tool▁sep｜>` without the ```` ```json ```` fence) reproduces the same `None`.

Character-by-character streaming (feeding the text one character at a time, as most real single-token deltas would) does *not* trigger this — it's specifically the "start and end both show up before the parser ever sees a start-only state" case that's mishandled.

### ErenAta16 · 2026-07-08

Same root cause shows up in a third, unrelated parser: `FunctionGemmaToolParser` (`vllm/tool_parsers/functiongemma_tool_parser.py`).

Its streaming state machine branches on `start_count`/`end_count`/`prev_start_count`/`prev_end_count` computed from plain substring counts on `current_text`/`previous_text` (not token ids, but the same idea):

```python
if start_count > prev_start_count and start_count > end_count:
    # starts a new call, appends placeholders, returns None
if start_count > end_count:
    # mid-call
if end_count > prev_end_count:
    # call just ended
```

If a delta contains a complete call (start and end tag together), `start_count` and `end_count` become equal in the same step, so neither the "starting" branch nor the "mid-call" branch fires. Only the "just ended" branch fires, and it guards on `self.current_tool_id >= 0`, which is still `-1` because the call was never opened. Nothing gets appended, no delta is emitted, and no error is raised.

Confirmed against the real class, no stubbing:

```python
from vllm.tool_parsers.functiongemma_tool_parser import FunctionGemmaToolParser

text = "<start_function_call>call:get_weather{location:<escape>Paris<escape>}<end_function_call>"

final = FunctionGemmaToolParser(tokenizer=None).extract_tool_calls(text, None)
print([(c.function.name, c.function.arguments) for c in final.tool_calls])
# [('get_weather', '{"location": "Paris"}')]

dm = FunctionGemmaToolParser(tokenizer=None).extract_tool_calls_streaming(
    previous_text="", current_text=text, delta_text=text,
    previous_token_ids=[], current_token_ids=[], delta_token_ids=[],
    request=None,
)
print(dm)
# None
```

Character-by-character streaming works fine for it too, same as the DeepSeek parsers above. Given this is now three independent implementations hitting the identical assumption (a call always spends at least one delta in a "started but not finished" state before the parser sees it), it might be worth treating as one systemic gap rather than three one-off patches, similar to how #36056 replaced DeepSeek-V3.2's incremental approach with a buffer-until-complete-block strategy. Happy to help however is useful, just flagging what I found.


### ErenAta16 · 2026-07-08

Fourth instance of the same symptom class, different mechanism this time: `Internlm2ToolParser` (`vllm/tool_parsers/internlm2_tool_parser.py`).

Here the bug isn't a count comparison, it's that sending the function name and sending the arguments are structured as two separate streaming calls by design:

```python
if not self.current_tool_name_sent:
    function_name = tool_call_arr.get("name")
    if function_name:
        ...
        delta = DeltaMessage(tool_calls=[DeltaToolCall(
            function=DeltaFunctionCall(name=function_name).model_dump(exclude_none=True)
        )])
        self.current_tool_name_sent = True
        self.streamed_args_for_tool.append("")
    else:
        delta = None
else:
    # arguments are only ever computed/sent from here
    ...
```

The first time `extract_tool_calls_streaming` sees a parseable name, it returns immediately with just the name and flips `current_tool_name_sent = True`. Arguments are only ever read and sent on a *later* call, once that flag is already set. If the entire tool call (name and arguments together) arrives in one streaming delta, there is no later call: the method sends the name once and nothing else, and the arguments are gone for good, not deferred.

```python
from vllm.tool_parsers.internlm2_tool_parser import Internlm2ToolParser

text = '<|action_start|><|plugin|>{"name": "get_weather", "parameters": {"x": 42}}<|action_end|>'

final = Internlm2ToolParser(tokenizer=None).extract_tool_calls(text, None)
print([(c.function.name, c.function.arguments) for c in final.tool_calls])
# [('get_weather', '{"x": 42}')]

dm = Internlm2ToolParser(tokenizer=None).extract_tool_calls_streaming(
    previous_text="", current_text=text, delta_text=text,
    previous_token_ids=[], current_token_ids=[], delta_token_ids=[],
    request=None,
)
print(dm)
# tool_calls=[DeltaToolCall(..., function=DeltaFunctionCall(name='get_weather', arguments=None))]
# arguments never sent, and there is no follow-up call coming since this is the whole message.
```

I'll stop adding parsers here rather than turn this into a survey of the whole directory, but between this, the two DeepSeek parsers, and FunctionGemma, it does look like "assume the client gets at least two calls per tool call" is a recurring, implicit assumption across several of the hand-rolled (non buffer-until-complete) parsers, which a single well-timed delta can violate.

### ErenAta16 · 2026-07-09

Sounds good, thanks for picking this up.

Quick orientation since this thread now covers four parsers rather than just the original DeepSeek-V3/V3.1 report: the same underlying assumption (that a tool call's opening and closing markers arrive in separate streaming deltas, never together) also breaks `FunctionGemmaToolParser` and `Internlm2ToolParser`, though each hits it through a different mechanism:

- `deepseekv3_tool_parser.py` / `deepseekv31_tool_parser.py`: token-count comparison between `previous_token_ids` and `current_token_ids` never sees a state where start_count > end_count, so it goes straight to the "closing" branch with no call ever opened.
- `functiongemma_tool_parser.py`: same idea but on substring counts (`start_count`/`end_count`) instead of token ids.
- `internlm2_tool_parser.py`: different mechanism entirely — the function name and the arguments are hard-coded to be sent as two separate streaming calls, so if the whole tool call shows up in one delta, the name is sent but `arguments` stays `None` since there's no second call to fill it in.

If you're starting with DeepSeek-V3, the merged PR #36056 fixed the identical symptom in a different parser and is a reasonable reference for the shape of the fix (tracking whether a call was actually opened, rather than inferring it from a count comparison that assumes multi-delta arrival).

Happy to verify against a real vLLM install once you have something up, the way I did for #48022. Let me know if it'd help to split this into one PR per parser or handle it together, given they're independent code paths that happen to share the same bug class.

### redd34 · 2026-09-26

This still reproduces on v0.30.0 and on main @ 3b4566c, for both `deepseek_v3` and `deepseek_v31`. I applied #48636 on top of main and it fixes the whole-call-in-one-delta case. One neighbouring split still loses the arguments with #48636 applied: the name arrives in one delta, then the complete argument JSON arrives in the same delta as `<｜tool▁call▁end｜>`. The call is then emitted with `arguments=''`. #48343 (V3) and #58806 (V3.1) do not change this either; I tried each of them on main.

```python
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
from vllm.tokenizers import get_tokenizer
from vllm.tool_parsers.deepseekv3_tool_parser import DeepSeekV3ToolParser

tok = get_tokenizer("deepseek-ai/DeepSeek-V3-0324", revision="e9b33add76883f293d6bf61f6bd89b497e80e335")
req = ChatCompletionRequest(model="m", messages=[{"role": "user", "content": "hi"}])

def stream(deltas):
    p = DeepSeekV3ToolParser(tok)
    prev_text, prev_ids, calls = "", [], {}
    for delta in deltas:
        ids = tok.encode(delta, add_special_tokens=False)
        cur_text, cur_ids = prev_text + delta, prev_ids + ids
        d = p.extract_tool_calls_streaming(prev_text, cur_text, delta, prev_ids, cur_ids, ids, req)
        for tc in (d.tool_calls if d else []):
            c = calls.setdefault(tc.index, ["", ""])
            c[0] += (tc.function.name or "") if tc.function else ""
            c[1] += (tc.function.arguments or "") if tc.function else ""
        prev_text, prev_ids = cur_text, cur_ids
    return [tuple(c) for c in calls.values()]

head = "<｜tool▁calls▁begin｜><｜tool▁call▁begin｜>function<｜tool▁sep｜>get_weather\n```json\n"
args = '{"city": "Paris"}\n```'
tail = "<｜tool▁call▁end｜><｜tool▁calls▁end｜>"
print("non-streaming       :", [(t.function.name, t.function.arguments)
      for t in DeepSeekV3ToolParser(tok).extract_tool_calls(head + args + tail, req).tool_calls])
print("A [head+args+tail]  :", stream([head + args + tail]))
print("B [head, args+tail] :", stream([head, args + tail]))
print("C [head, args, tail]:", stream([head, args, tail]))
```
