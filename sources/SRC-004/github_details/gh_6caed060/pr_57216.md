## Purpose

`OffloadingConnector` never yields a CPU-tier hit for a **hybrid model** (recurrent/SSM groups
alongside full-attention groups) once the prompt is longer than one full-attention chunk. Reuse
reads 0 regardless of how large the CPU pool is.

There are two independent causes. Both are required for the tier to work at all, so they are in
two separate commits.

### 1. Store — partial tails are disabled under DCP, and the store path mis-addresses groups

`supports_partial_tail` required `len(group_block_sizes) == 1` **and**
`decode_context_parallel_size == 1`. Under DCP the full-attention offload block is `dcp ×` the
attention block while recurrent blocks stay unsharded (12288 vs 1536 at DCP 8 — attention groups
are scaled by DCP in `build_offloading_config`/`resolve_dcp_kv_block_size`, `MambaManager.__init__`
explicitly undoes the scaling for recurrent state). Both conditions fail, so the feature is off.

The store path also addressed every group with a single shared physical block index
(`boundary // self._partial_tail_block_size`), which is wrong once block sizes differ, and
`_partial_tail_block_size` was read from `kv_group_configs[0]`, which need not be the
full-attention group.

Fix: allow mixed block sizes when every recurrent block divides the full-attention block,
recurrent blocks are hash-aligned, and hash boundaries split evenly across DCP ranks; address each
group's source block in its own block size; take the window from the full-attention group
explicitly (`partial_tail_window`).

At `dcp == 1` the scale factor is 1, so the guard change is a no-op and the store path resolves to
the same single block index as before.

### 2. Lookup — the search is anchored on a boundary recurrent groups never have

`_lookup` anchored the partial-tail search on `_lookup_complete_chunks`, which requires *every*
group to have a complete chunk at the boundary — including recurrent groups that by construction
hold no state there. The `align` manager CoW-copies its state at the producing prompt's last hash
boundary, which is essentially never a full-attention chunk multiple. So the anchor is 0, the
search is capped at one window from zero, and a correctly stored tail further out is never probed
even though it is resident.

**This half is independent of DCP** and affects every hybrid + `OffloadingConnector` deployment.

Instrumented `_lookup` on a replay, before the change (chunk 12288, hash 128):

```
n=12620  complete_hit=12288  complete_boundary=12288  max_boundary=12544
           boundary=12544 ALL GROUPS HIT                  <- restores
n=15136  complete_hit=0      complete_boundary=0      max_boundary=12160
           boundary=12160 group=0 MISS ... 11776 MISS     <- tail stored at 15104,
                                                            never probed
```

Fix: anchor on the full-attention complete prefix and check recurrent groups only at the candidate
boundary. The anchor honours the same `max_num_new_tokens` / `max_load_tokens` caps as the
complete-chunk lookup, and only chunks verified resident are requested, so the load path cannot
fetch an unverified chunk.

The returned boundary is always strictly greater than the complete-chunk hit, so the change is
additive: it can only widen what a lookup reports, never shrink it. That is also the argument that
it cannot regress an existing deployment.

## Test Plan

New unit coverage in `tests/v1/kv_connector/unit/offloading_connector/test_scheduler.py`, on a
DCP-shaped hybrid fixture (full-attention offload block = `dcp × attention block` = 32, unsharded
16-token Mamba block, hash 4) — the same shape as 12288 vs 1536 at DCP 8:

```
pytest tests/v1/kv_connector/unit/offloading_connector/ -q
```

- 3 store tests: the guard accepts mixed block sizes under DCP and still rejects DCP-indivisible
  hashes, EAGLE, and a recurrent block that does not divide the full-attention block; the store
  addresses each group in its own block size; an aligned boundary still goes to the aligned path.
- 7 lookup tests: the tail is found with no recurrent state at the chunk boundary; 0 when no tail
  was stored; 0 when the full-attention chunks are not resident; the tail is preferred over an
  aligned recurrent state; deferral while the anchor chunk is loading; a recurrent state is still
  required at the candidate boundary; and the load path addresses each group correctly.

Hardware validation was done on a 2-node GB300 deployment of a KDA + MLA hybrid at TP8/DCP8 with a
deliberately small 16 GiB CPU pool, using per-prompt isolated trials with a GPU-only prefix-cache
reset between store and replay and a reference run asserted cold (`cached == 0`), so the
comparison is CPU-restore vs full recompute rather than restore vs restore.

## Notes for reviewers

- **`dcp == 1` is untested on hardware.** That is the default upstream configuration. The
  store-side guard change is a no-op there by construction (the scaling factor is 1), and the unit
  tests cover the existing `dcp == 1` paths, but nothing was measured on a device.
- **Only one hybrid architecture was exercised** (KDA + MLA). Mamba/SSM + full attention should
  behave identically by the same code path, but was not run.
- **EAGLE/MTP remains excluded** by the guard (volatile draft tail) and is untested.
- The lookup fix adds a second `manager.lookup()` pass over the full-attention groups when
  recurrent groups are present. `record_lookup` is idempotent, so no duplicate KV events are
  emitted, but it is extra probe work on the hybrid path. Happy to gate it more tightly if you
  would prefer.
- Related prior work on the sibling connector: #52832 fixed the analogous producer-partial-tail
  gap for Mooncake.
- Two further changes exist on our side but are deliberately **not** in this PR, as they are pool
  efficiency rather than correctness: skipping aligned recurrent stores whose boundary is not a
  full-attention chunk multiple (unreachable rows), and a `min_partial_tail_tokens` knob. Happy to
  send either as a follow-up if they are wanted.
