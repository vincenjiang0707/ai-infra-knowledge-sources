## Purpose

Split out of #57216 (part 3 of 3). #58619 keeps only the **longest** boundary of a partial-tail hand-off. This PR proposes storing **every** boundary the KV cache manager retained inside the trailing full-attention block, and states the trade-off so it can be accepted or closed.

A request-end hand-off drains every recurrent `align` manager for the step, so besides the prompt tail it carries every other retained boundary inside the trailing full-attention block: the last full recurrent block, or one per retained segment under a non-zero `prefix_cache_retention_interval`. Under DCP none of these is a full-attention block multiple, so the partial-tail path owns them.

With longest-only, each of those boundaries ends up with a recurrent row in the pool (the aligned path stores it) but **no full-attention partner**, so a consumer that diverges from the producer between a retained boundary and the tail finds nothing there and recomputes from the last complete chunk. This PR stores each boundary as its own pair, longest first — the order a consumer's descending probe reads them in — moving the per-boundary body into `_build_partial_tail_store_job`.

## Trade-off (the decision)

| | longest-only (#58619) | every boundary (this PR) |
|---|---|---|
| CPU pool per request-end hand-off | 1 FA row + 1 recurrent row | + 1 FA row + 1 recurrent row per extra retained boundary (K3 @ DCP 8: one extra pair, for the last full 1536-token recurrent block) |
| reachable by | consumers extending or diverging *after* the tail | additionally: consumers diverging inside the last recurrent block before the tail (≤ 1535 tokens on K3) |
| with `prefix_cache_retention_interval` | retained boundaries in the trailing FA block are dead rows | each is restorable from CPU |

The benefit is bounded by the same span as the cost. On Kimi-K3 shadow traces the divergence-inside-the-last-block case is a minority of an already-minority (regenerate/edit) flow; on the other hand, it is the only way retained boundaries under a retention interval become reachable from the CPU tier under DCP. Happy to close this if longest-only is preferred.

Not in this PR: the assert-to-skip conversions from #57216. I could not construct a reachable case for either — every `align` manager shares one block size (`resolve_mamba_align_size` asserts it), so all retain and hand off the same boundaries, and full-attention block ids of a live request are never the null block — so the asserts stay.

### nvyutwu · 2026-09-27

Closing. #58619 keeps only the longest boundary of a multi-boundary hand-off, and the question was whether storing every boundary is worth an extra FA + recurrent row per boundary.

On GB300 (Kimi-Linear-48B, KDA + MLA, TP4/DCP4, full-attention offload block 2048, recurrent block 512, hash 128), #58618 + #58619 and this PR produced identical results on every trial: same tokens restored, same store bytes. That includes a consumer diverging between the last recurrent block and the tail, which resumed at the earlier boundary without this PR. The retained boundaries arrived in separate hand-offs, so longest-only already stored each pair. Without a case where a single hand-off carries several boundaries that matter, this adds nothing, so longest-only stays as in #58619.
