### ajinkyajawale14499 · 2026-06-27

Root cause is a TOCTOU race in the single-node distributed-init port selection.

For a single-node engine using `MultiprocExecutor`, the init method is built here:

`vllm/v1/executor/multiproc_executor.py:128` (main; `:122` in v0.18.0)

```python
distributed_init_method = get_distributed_init_method(get_loopback_ip(), get_open_port())
```

`get_open_port()` -> `_get_open_port()` binds a throwaway socket to `("", 0)`, reads the OS-assigned port, then closes the socket (the `with` block exits) and returns just the integer. The port is free again the moment it is returned. torch binds it only later, when `init_process_group` brings up the TCPStore on `tcp://127.0.0.1:<port>`.

Between "port chosen" and "TCPStore binds" the port is owned by nobody, and worker processes are spawned in that gap, so the window is wide. When two or more engines start on the same node concurrently (multiple servers, DP replicas, or an RL framework launching several rollout engines per node), each can observe the same port as free and then both try to bind it. The second loses with `EADDRINUSE`.

I hit the same thing from verl (volcengine/verl#6677): multiple vLLM rollout instances per node collide on this exact path. There have been related reports too (#21638 for DP serve, #15987 for NCCL setup), so this seems to be the general version on the `MultiprocExecutor` path.

Two fix directions, both local to the port handoff:

1. Retry on bind failure: re-pick a port and retry a bounded number of times if the store bind hits `EADDRINUSE`. Simple, but the retry has to live where the store is created, not where the port is chosen.
2. Reserve the port across the gap: keep the reserving socket bound (with `SO_REUSEADDR`) until the real listener takes over, so the port is never released in between. This closes the window instead of retrying through it. verl already uses this pattern for its own ports.

Is there a direction you'd prefer for a general fix here? Happy to put up a PR for whichever you'd accept.
