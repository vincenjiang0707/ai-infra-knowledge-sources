## Purpose

Fixes #58776.

With async scheduling, a resumable (streaming-input) request can be preempted while a step is still in flight. That step's output is delivered as stale output, and if it hits a stop condition the request stops in `PREEMPTED` state. Two things then go wrong:

1. **The session drops out of every queue.** `_handle_stopped_request` re-enqueues the resumable request, but the stopped-while-preempted cleanup in `update_from_output` removes every occurrence from `waiting` and `skipped_waiting`, including that new entry. A `WAITING_FOR_STREAMING_REQ` session is only rescheduled by staying in `skipped_waiting`, so it is never scheduled again.
2. **The fold deletes the prompt.** `_update_request_as_session` keeps `all_token_ids[num_prompt_tokens:num_computed_tokens]` and deletes the rest. After preemption `num_computed_tokens == 0`, so it deletes the whole list, while `prompt_token_ids` (a separate list) is only extended; `num_prompt_tokens` then no longer matches `all_token_ids`, and the previous turn's output is lost.

Changes:

- After the stopped-while-preempted cleanup, re-enqueue requests that did not finish, so each ends up in exactly one queue.
- In the fold, keep up to `max(num_computed_tokens, num_tokens - 1)`. On a normal stop `num_computed_tokens == num_tokens - 1`, so nothing changes; after preemption the session keeps all but the final sampled token, and `num_computed_tokens` stays 0 so everything is recomputed.

Searched open and closed issues and PRs for this path (`stopped_preempted_reqs`, streaming/resumable + preempt, `_update_request_as_session`, session hang symptoms); none found. #58668 fixes a different case where `num_computed_tokens` is wrong at the fold (a speculative step stopping on an accepted draft). Both PRs append a test to `tests/v1/streaming_input/test_scheduler_streaming.py`, so whichever lands second needs a trivial rebase.

- `test_session_resumes_after_stop_while_preempted` (next chunk queued before / after the stop) reproduces #58776. - `test_non_resumable_request_stays_dequeued_after_stop_while_preempted` guards the re-enqueue: a request that finishes while preempted must stay out of the queues. It passes on main and fails if the `is_finished()` check is dropped.

### twu3202 · 2026-09-27 · APPROVED

Tested this end to end on one RTX 6000 Ada with Qwen3-ASR-0.6B realtime (`Qwen3ASRRealtimeGeneration`), async scheduling, V2 model runner, `--no-enable-prefix-caching`.

To get preemptions I capped the KV cache with `--num-gpu-blocks-override 300` and kept four `/v1/completions` requests (1000 tokens, `ignore_eos`) running next to 8 realtime sessions, each streaming 30 s of audio at 2x real time, 20 rounds per build. Half of the sessions stream silence, so each 5 s segment ends after a few tokens and a preempted session is more likely to have its stop token in flight. To count the trigger I added a local log line for resumable requests in the `stopped_preempted_reqs` branch.

On main this load kills the engine with the #35755 placeholder assertion in the third round, so both builds below include #58259.

| build | trigger hits | sessions finished |
| --- | --- | --- |
| #58259 only | 3 | 157/160 |
| #58259 + this PR | 3 | 160/160 |

On the first build each hit left its session in `WAITING_FOR_STREAMING_REQ` with no queue entry, and that session never got `transcription.done`, while `/health` stayed OK. With this PR every session finished. All hits were the case without a queued chunk (with paced input the next chunk usually hasn't arrived yet), so the fold change is covered only by the unit test here.

On CPU, the repro from #58776 and the new tests fail on the base commit and pass on the PR head, also on top of #58259. `tests/v1/streaming_input`, `tests/v1/core/test_scheduler.py` and `tests/v1/core/test_async_scheduler.py` pass except the four tests that need a GPU, same as on the base commit.
