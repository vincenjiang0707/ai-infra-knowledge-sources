# [Issue #58774] [RFC]: Native span pooling for contextual chunk embeddings

## 正文

## Motivation

Retrieval applications often index paragraphs separately. Encoding each paragraph in isolation loses cross-paragraph context: “its maintenance team” may refer to a company named in an earlier paragraph. [Late chunking](https://arxiv.org/abs/2409.04701) encodes the document first, then pools token representations within each chunk.

vLLM already returns token embeddings. For suitable models, an application can disable token normalization with `use_activation=False`, export the representations and pool them correctly outside the worker. This proposal adds a native way to return only the requested chunk vectors, with a shared request contract and worker-side aggregation.

The existing [long-text embedding feature](https://github.com/vllm-project/vllm/pull/22280) splits an oversized input into independent forwards and combines their outputs into one document vector. Here, multiple chunk vectors come from one shared document encoding, within the model's context limit. The algorithm is established; the proposed contribution is its integration into vLLM's pooling path.

## Proposed change

Add an opt-in span-pooling task, tentatively named `span_embed`, through `LLM.encode` and the existing `/pooling` endpoint. The default embedding APIs keep their current behavior.

### Request semantics

For the first release, use the existing token-ID input path. Each request contains one complete, unpadded token sequence and one or more ordered, non-overlapping ranges. This makes the worker's input unambiguous and avoids introducing a second server-side tokenization path.

Illustrative request; the task and `token_spans` field are proposed:

```json
{
  "model": "span-enabled-encoder",
  "task": "span_embed",
  "input": [101, 2023, 2003, 1037, 7953, 1012, 102],
  "add_special_tokens": false,
  "token_spans": [[0, 4], [4, 7]]
}
```

Token IDs are illustrative; callers must use the served model's tokenizer and pinned revision.

- Ranges are zero-based and half-open: `[start, end)`. They refer to the exact submitted token sequence. Reject empty, reversed, overlapping or out-of-bounds ranges, and enforce a server-side span-count limit.
- All input tokens provide context. Only tokens within each range participate in its mean. Special tokens and instructions are included if their positions are selected; the engine never silently includes or excludes them.
- Require `add_special_tokens=false` and reject request/config options that would truncate, pad, rewrite or split this input. Ordinary internal batch padding is not part of the sequence or its ranges. Oversized inputs fail validation.
- Return one `[K, D]` matrix in the existing pooling response, where row `i` corresponds to input span `i`. Count input tokens once per document. Concurrent requests remain independently batched by the engine.

Ship a text-to-token example with the first release so users can start from text and paragraph boundaries. It uses the same pinned tokenizer as the deployment, tokenizes the complete model input once, and sends those exact IDs with the resolved ranges. It rejects boundaries inside a token. The late-chunking reference example follows the paper's convention of including prefix tokens in the first chunk and suffix tokens in the last. A content-only example must be identified as a different convention. A text/character-span server API can follow once this operation is established.

### Shared implementation, explicit model support

Implement the reduction once in the common pooler layer:

```text
full-document model forward
  -> span means, accumulated in FP32
  -> validated model-specific embedding head
  -> K output vectors, copied from the worker
```

The head includes the supported projection, dtype conversion and normalization in the model's verified order. We must not move nonlinear transformations across the mean or assume that exported token embeddings always equal raw hidden states.

Start with an explicitly enabled bidirectional MEAN-pooling model. `nomic-ai/nomic-embed-text-v1`, at the revision pinned by existing vLLM tests, is the initial integration candidate; its HF compatibility constraint remains in place. MiniLM provides inexpensive reference coverage. Additional models reuse the reducer but require validation of their head and input conventions. Unsupported models fail before scheduling. LAST/CLS models are not automatically enabled.

The integration covers:

1. Pooling request/offline input validation and typed `token_spans` in `PoolingParams`.
2. Task registration, parameter defaults, model capability reporting and `DispatchPooler` selection. A compatible head must explicitly support the new task; existing heads must not advertise support globally.
3. Request metadata transport and batch slicing, preserving the association between each request's ranges and hidden states through reordering and task grouping.
4. Reduction before worker output copying, using the existing variable-row pooling output. Extend existing pooling tests and examples.

This uses the current scheduler and model forward path. Initial encoder targets keep their existing restrictions on prefix caching and chunked prefill. Documents must fit a full supported context. Automatic segmentation, cross-window context, decoder models and multimodal inputs are outside the first release.

### Alternatives and related work

A correct token-export/client-pooling path is the first baseline. An IO processor can also aggregate outputs before the HTTP response, although token-level worker output has already been produced. A custom model pooler combined with a plugin can perform aggregation inside the worker too.

The argument for native support is a reusable contract and validated model integration, rather than requiring separate model wrappers. Plugins are a legitimate alternative: [#37344](https://github.com/vllm-project/vllm/issues/37344#issuecomment-4080081406) recommended them for custom span-shaped outputs. I would like feedback on whether this use case warrants a native task.

This differs from existing multi-head embedding output and late-interaction scoring. It also differs from [#56916](https://github.com/vllm-project/vllm/issues/56916), which concerns capturing hidden states during response generation. External demand exists, for example [TEI #434](https://github.com/huggingface/text-embeddings-inference/issues/434); vLLM users' models and workloads would help establish the priority here.

### Validation and delivery

A local CPU probe combined a real MiniLM encoder with vLLM's pooler/head components on four documents and eleven spans. The component results matched direct reference calculations. This is feasibility evidence, not an end-to-end implementation or a performance result.

Implementation acceptance should cover:

- Numerical agreement with a fixed-revision HF reference using identical token IDs, ranges and head semantics, including special-token selection.
- Online/offline agreement, mixed-length and mixed-task batching, invalid inputs, context limits and unchanged existing embedding results.
- Comparison with correctly configured token export plus client pooling: worker-output bytes, host memory and end-to-end latency at matched workloads. A worker-side plugin can establish whether native integration adds any overhead, rather than assuming it must be faster.
- A representative retrieval comparison with independent-chunk encoding, reporting gains and regressions. [Subsequent evaluation](https://arxiv.org/abs/2602.16974) finds task-dependent effects; this is an optional capability, not a universal retrieval upgrade.

Reducing output from `N × D` to `K × D` values does not reduce the full-document attention cost or establish an end-to-end speedup.

I propose three implementation steps: the shared reducer and offline reference tests; online request integration plus the text-to-token example; then end-to-end validation and documentation for the first supported model. I would like to drive the implementation and maintain this path.

## Feedback period

Initial feedback through October 2, 2026; discussion can continue afterward. The main questions are whether native support is preferable to a plugin, whether the token-range contract is suitable, and which initial model/workload users would actually deploy. Task naming and exact field placement can be settled in review.

### noooop · 2026-09-26

LATE chunking is great—let's figure out how to land it.

If we support LATE chunking with arbitrary dynamic lengths, users would need to run tokenization first to get token IDs, and the interaction would be very complicated.

Let's first implement fixed-length LATE chunking, where users provide a chunk size per request, and see what feedback the community has.

One detail: pooling models currently only support one pooling task. Normal sequence embeddings use the embed task, while for LATE chunking I expect we'll need to use the token_embed task, so we cannot support both normal embeddings and LATE chunking in the same vLLM instance.

For those who are unfamiliar with sequence embeddings and token embeddings, you can refer to the following document.
- https://docs.vllm.ai/en/latest/models/pooling_models/embed/
- https://docs.vllm.ai/en/latest/models/pooling_models/token_embed/
