# [Issue #56402] [RFC]: Efficient Routed-Expert Replay with Prefix Omission and KV Cache Offloading

source: https://github.com/vllm-project/vllm/issues/56402
state: open | updated: 2026-09-22T12:33:13Z
labels: RFC

## 正文

### Motivation.

vLLM can return routed-expert IDs for replay and training. In multi-turn workloads, however, returning routes for the full prompt on every request repeatedly gathers, transfers, and concatenates historical data that the caller already owns.

Prefix caching avoids recomputing KV, but the routed-expert output path does not currently share the same ownership boundary. KV offloading makes this harder because a cached block may be restored to a different GPU block while the routed-expert table is indexed by GPU slots.

This RFC proposes prefix omission for routed-expert output and defines the compatibility contract for same-engine KV offloading, while preserving the existing behavior by default.

**Preliminary performance.** Step 3.5 FP8 on 8 × H200 (TP=8, PP=1), with async scheduling enabled and KV offloading disabled: 128 concurrent lanes × 100 turns, starting with 640 prompt tokens and adding 320 generated + 320 random tokens per turn, with a 1 s inter-turn pause. RPM includes these pauses; results are normalized to routed-expert return disabled. 

| Configuration | Mean latency (s) | RPM |
|-|-|-|
| Routed-expert return disabled | 5.695 (1.00×) | 1144.20 (1.00×) |
| Full routed-expert output | 6.642 (1.17×) | 999.29 (0.87×) |
| Prefix omission | 5.793 (1.02×) | 1127.64 (0.99×) |

### Proposed Change.

## Current behavior

Workers return routed-expert IDs with model output. `RoutedExpertsManager` stores them by full-attention GPU slot, gathers prompt routes with NumPy indexing, and appends decode routes to request state. The API returns the complete accumulated route sequence. Routed-expert return is currently rejected when KV transfer is enabled.

## Scope and non-goals

This RFC covers routed-expert prefix omission and compatibility with same-engine store/load KV offloading. Initial connector support targets SimpleCPUOffloadConnector, OffloadingConnector, and MooncakeStoreConnector. OffloadingConnector support is initially limited to the built-in CPUOffloadingSpec; TieringOffloadingSpec, secondary storage tiers, and custom offloading specs are out of scope. Prefill-decode disaggregation, `PP`/`DCP`/`PCP` greater than 1, more than two overlapping asynchronous scheduler batches, and the caller-side route storage implementation are out of scope for the initial implementation.

## Proposed API

Add `--enable-omit-prefix-routed-experts`. It is valid only with `--enable-return-routed-experts` and is disabled by default.

When prefix omission is enabled, vLLM omits routed experts for the cached prefix. The caller is responsible for receiving and retaining returned route chunks and correctly merging them with previously retained routes under the same session/cache identity. vLLM does not manage or verify this cross-request accumulation. 

The first completed GPU-plus-connector cache lookup sets `request.num_cached_tokens` as the immutable cached-prefix boundary. Scheduling, preemption, reset, and KV load may change computed or resident KV state, but must not change this boundary.

The returned range starts at:

```python
prompt_start = max(
    request.sampling_params.routed_experts_prompt_start or 0,
    request.num_cached_tokens,
)
```

## Internal design

**Prefix omission.** Slice the prompt slot mapping at `prompt_start` before the NumPy gather. This avoids materializing routed-expert data that will be discarded and leaves decode handling unchanged.

**Session isolation.** Use the existing request `cache_salt` mechanism to encode the stable session/cache identity in the first block hash, so shared prefixes, such as system prompts, are not reused across identities whose routed experts are owned separately. All three initial connector targets already preserve cache salt through their existing block-hash keys.

**Recovery after preemption.** The initial cache lookup remains unchanged and may combine GPU and connector hits. Once decode has started, routes for previously forwarded output tokens are retained in the frontend state of the same request, so recovery may use normal GPU and connector lookup. Before decode starts, recovery caps GPU prefix reuse at `request.num_cached_tokens` and bypasses external lookup. We will add a lightweight bypass hook to each of the three initial connector targets, preserving the initialization, state updates, and cleanup required for a zero-external-hit scheduling path without initiating a new external lookup or load plan.

**Offload safety (optional).** This proposal supports same-engine store/load offloading, not prefill-decode disaggregation. As an optional defense in depth, the scheduler may derive the routed-expert slots for the accepted external-token range from the allocated request block table. The scheduler invalidates these slots before the external KV load begins and reapplies invalidation after storing an older asynchronous output, without clearing slots for newly computed tokens outside that range. No routed-expert sidecar is transferred with KV.

## Alternatives considered

- **Always return the full route history.** This preserves current semantics but retains repeated collection and transfer overhead.
- **Transfer routed experts as a KV sidecar.** This restores historical routes with offloaded KV but substantially expands the connector protocol and data volume.

## Compatibility

- With prefix omission disabled, routed-expert output is unchanged.
- With routed-expert return enabled, KV offloading is supported only when prefix omission is enabled and the connector provides the external-lookup bypass capability. Both requirements are checked during server initialization; unsupported configurations are rejected, and every child of a composite connector must support the bypass capability.

## Risks

- **Cache identity consistency.** The three initial connector targets preserve the GPU cache identity, including `cache_salt`. This has not been established for other connectors; losing the salt during external key construction may allow cross-session hits and cause vLLM to omit routes the caller does not own. Requests without a stable session/cache identity are rejected rather than falling back to full routed-expert output.
- **Caller-side route reconstruction.** The caller must retain and correctly merge routes across requests sharing the same identity. Tokenization is not associative across independently rendered fragments, so route reconstruction must preserve alignment between expert positions and the corresponding tokens. vLLM does not verify the caller's retained routes or cross-request reconstruction.

### Any Other Things.

Frontend concatenation of routed-expert chunks can block an API process when many requests finish together. Existing deployments can reduce this contention by increasing `--api-server-count`; this is operational guidance, not part of the proposed design.

A preliminary implementation is available in [this branch](https://github.com/cccyy123/vllm/tree/routed-expert-prefix-omit) for reference. Optional slot invalidation is not included.

### aoshen02 · 2026-09-16

Related measurements from our auxiliary-output connector experiments (not a benchmark of this RFC's implementation):

**Setup:** DeepSeek-V4-Flash-Base, 2 GB200 nodes, TP1/DP8/EP, async scheduling, 256K-token prompts, concurrency 64, one generated token. Mean of two runs; all variants return R3.

| Implementation | Tokens/s | vs native R3 |
|---|---:|---:|
| Native vLLM R3 | 84,652 | baseline |
| CPU-side assembly + store | 82,343 | -2.73% |
| GPU-side assembly + batched publication | 81,415 | -3.83% |

Profiling exposed millions of tiny per-block GPU→CPU copies (effective R3 block size: 4 tokens / 1,032 bytes). Batching publication improved the GPU variant from **75,305 to 81,415 tokens/s (+8.11%)** in a separate controlled A/B.

This supports avoiding fragmented R3 transfers. These are **cold, prefill-dominated** measurements, not multi-turn prefix-omission or sustained-decode results; they do not isolate copy cost from assembly/storage overhead. Prefix-reuse correctness checks passed separately.


### cccyy123 · 2026-09-16

Thanks @aoshen02 for sharing these results! The transfer batching you described seems complementary to the prefix omission proposed here.

Our production use case is multi-turn agentic RL, where agents alternate between model generation and tool calls. As the conversation grows, requests repeatedly carry a prefix whose routes are already retained by the RL side. We'd like to avoid assembling and returning that history again.

In our synthetic multi-turn benchmark, omission reduced mean-latency overhead from about 17% to 2% relative to expert return disabled, with worker-side D2H unchanged and KV offloading disabled. So the two optimizations address different parts of the cost.

For KV offloading, the same ownership contract could let us restore an omitted prefix's KV without also restoring its expert blocks. Routes that still need to be returned must remain available or be recomputed during recovery.

We'd be happy to adapt our implementation in #57025 to AuxOutput and contribute multi-turn agent, offload, and recovery tests. Would it make sense to coordinate this as a follow-up to #45635?
