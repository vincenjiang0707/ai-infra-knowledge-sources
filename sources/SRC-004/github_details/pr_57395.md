The Qwen4Exp QSA path uses a custom Triton sparse-attention kernel, but both platform owners (amd/qsa.py, nvidia/qsa.py) still derived from the FlashAttention backend/impl and gated construction on is_flash_attn_varlen_func_available(). FlashAttention is never invoked over the QSA cache, so this was an unnecessary runtime dependency and misleading naming. This PR makes QSA a first-class Triton backend and preserves the fp8_e4m3 main-KV-cache support added on the NVIDIA path. 

Follwoing are the changes:

1. Qwen4ExpQSAFlashAttentionBackend -> Qwen4ExpQSABackend, now subclassing AttentionBackend (was FlashAttentionBackend). Set forward_includes_kv_cache_update = False explicitly to preserve slot-mapping padding behavior.
2. Qwen4ExpQSAFlashAttentionImpl -> Qwen4ExpQSAImpl, now subclassing AttentionImpl (was FlashAttentionImpl).
Removed the is_flash_attn_varlen_func_available() construction gate and the fa_utils/FlashAttentionImpl imports.
3. Reimplemented do_kv_cache_update with vllm._custom_ops.reshape_and_cache_flash (same op the inherited FA path used), so no flash-attn package is required.
4. Added the AttentionImpl.forward stub (QSA runs through forward_qsa via the layer/op).
5. Trimmed the constructor to QSA-relevant arguments (num_heads, head_size, scale, num_kv_heads, kv_cache_dtype, attn_type); dropped ALiBi / sliding-window / logits-softcap / KV-sharing / sinks (QSA rejects all of them).
6. Kept FlashAttentionMetadata/FlashAttentionMetadataBuilder for the paged-KV metadata (no flash-attn runtime dependency).

NVIDIA only
1. Preserved fp8_e4m3 main KV cache: supported_kv_cache_dtypes keeps fp8/fp8_e4m3, and forward_qsa keeps the fp8 view + host dequant scales. Dropped the now-redundant supports_kv_cache_dtype/supports_combination overrides (base  AttentionBackend accepts any dtype listed and returns None for combination). Removed the fp8->"auto" parent-probe workaround.
2. AMD remains bf16-only (["auto","bfloat16"]).
