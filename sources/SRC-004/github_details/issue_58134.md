#### Root cause: the HIP fallback re-enters the subclass override

`_DecodeConcatQuantFP8` (`vllm/model_executor/layers/attention/mla_attention.py:1540-1568`) builds all three of its forward methods from one factory, so every method has the 4-argument signature `(decode_ql_nope, decode_q_pe, scale, scale_ub)`:

```python
forward_native = _make_forward(QuantFP8.forward_native)
forward_cuda = _make_forward(QuantFP8.forward_cuda)
forward_hip = _make_forward(QuantFP8.forward_hip)
```

`QuantFP8.forward_hip` ends with a fallback to the CUDA implementation (`vllm/model_executor/layers/quantization/input_quant_fp8.py:159`):

```python
# Fallback to CUDA implementation
return self.forward_cuda(x, scale, scale_ub)
```

On `_DecodeConcatQuantFP8`, `self.forward_cuda` is the *wrapped* 4-argument method, not `QuantFP8.forward_cuda`. So the 3-argument fallback call re-enters the wrapper with arguments shifted by one: `decode_q_pe` binds to the per-tensor `scale` (a 0-dim tensor, `tensor(0.3000)`), and `decode_q_pe.shape[-1]` raises `IndexError`.

CUDA never re-dispatches, which is why only the ROCm lane fails. On MI355 the AITER early-return branches in `forward_hip` are not taken for this configuration, so the fallback path is reached.

A minimal fix is to call the base implementation unbound, so the fallback cannot re-enter a subclass override with a different signature:

```python
return QuantFP8.forward_cuda(self, x, scale, scale_ub)
```

I have not opened a PR for this — I have no MI355 hardware to verify a fix, and I would rather leave it to the ROCm/attention owners than push an unverified change through CI.
