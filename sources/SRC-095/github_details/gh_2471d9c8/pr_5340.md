# [PR #5340] [History Server] Derive HTTP WriteTimeout from session process timeout

## 正文

## Why are these changes needed?

The History Server HTTP server's `WriteTimeout` is hard-coded to **35s**, but the `enter_cluster` handler blocks while the session loader cold-loads a session, which is allowed to run for `--session-process-timeout` (**default 2m**, user-configurable to any larger value).

Any session whose cold-load takes between 35s and 2m can therefore **never** return a response to the client:

- At ~35s the HTTP connection can no longer be written, so the gateway/LB returns **504** to the browser.
- Meanwhile the server-side cold-load keeps running to completion (the singleflight continues in the background and the snapshot gets cached), so the next request for the same session succeeds — making the failure appear intermittent and only affecting the first visitor of "slow" sessions.

We observed this in production: a session with ~a dozen event files on OSS took ~100s to cold-load (serial reads, ~10s each). The first `GET /enter_cluster/...` always failed with a gateway 504 ~34s in, while the server logs showed `Failed to load session ...: context canceled` followed by continued background loading.

Note the two timeouts already encode an alignment intent — the existing comment says `WriteTimeout` must be `>= httpClient.Timeout (30s)` for live-cluster proxying — the session cold-load path was simply not accounted for.

## What changes are proposed?

Derive the write timeout from the session process timeout:

```go
writeTimeout := max(35*time.Second, s.sessionLoader.ProcessTimeout()+15*time.Second)
```

- Default: `2m + 15s = 2m15s` (previously 35s).
- The 35s floor preserves the original live-cluster proxy requirement (`>= httpClient.Timeout` 30s).
- The 15s buffer covers event decode + response write after the load finishes.
- If an operator raises `--session-process-timeout`, the write timeout follows automatically; the two budgets can never conflict again.
- No new flag is introduced.

Also log the effective timeouts at startup for diagnosability.

### yujiabin123 · 2026-09-25

Thanks @cursor[bot] — valid catch.

`resolveSession()` indeed runs before `LoadSession()` and does a `reader.List()` over object storage, so the previous 15s buffer only covered decode + response write, not session resolution.

Pushed f8d2620a to address it: the buffer is widened from 15s to **30s** so the write timeout now also absorbs a slow session resolution on top of the full cold-load budget (default: 2m + 30s = 2m30s).

Two notes on severity/remaining edge:

1. `resolveSession()` is a single listing call and returns in seconds under normal conditions; the 2m figure is the per-operation hard cap in the GCS backend (`timeout = 2 * time.Minute` in `gcs_handler.go`), i.e. a worst case, not the typical path.
2. Fully accounting for that worst case would mean budgeting `resolveSession` (up to 2m) + `processTimeout` + write, which would push the default write timeout to ~4.5m. That feels like over-budgeting for a pathological case, and the underlying issue there is the storage layer's own hard-coded timeouts rather than this derivation. Happy to reconsider if maintainers prefer the fully conservative formula.
