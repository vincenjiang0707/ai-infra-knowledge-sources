# [PR #5207] [Feature][History Server] Make the collector image configurable on the operator

## 正文

## Why are these changes needed?

Today the collector sidecar image can only be set per RayCluster, through
`spec.historyServerOptions.collectorOptions.image`, and the field is required. That has two
consequences:

- Every RayCluster manifest carries a collector image tag that has to be bumped by hand on every
  KubeRay upgrade, and the docs currently point people at a `nightly` tag.
- Users whose clusters cannot pull from Docker Hub or `quay.io` have no way to point all of their
  RayClusters at a mirror registry, other than editing every manifest.

Pinning the collector version in the operator code instead would only move the problem: it would
have to be updated on every release.

This PR makes the collector image an operator-level setting and lets the default tag follow the
KubeRay version, so the collector stays in sync with the operator without a release-time code
change. The image is now resolved in this order:

1. `spec.historyServerOptions.collectorOptions.image` on the RayCluster, if set.
2. The image configured on the operator: the `--collector-image` flag, the `collectorImage` field
   of the operator configuration file, or the `collectorImage` value of the `kuberay-operator`
   Helm chart.
3. `quay.io/kuberay/collector` with the tag matching the KubeRay version (`nightly` on master, the
   release tag on a release).

To make (1) optional, `collectorOptions.image` is no longer rejected when empty; the RayCluster
then inherits the operator-level image. The field was already `+optional` in the CRD, so there is
no CRD change. This only relaxes validation, so existing manifests keep working unchanged.

Changes:

- `ray-operator`: new `collectorImage` field on the `Configuration` API with defaulting, the
  matching `--collector-image` flag, and the value plumbed through `RayClusterReconcilerOptions`
  into the head and worker Pod builders.
- `ray-operator`: `validateCollectorOptions` no longer requires `collectorOptions.image`.
- `helm-chart/kuberay-operator`: new `collectorImage` value, wired into both the flag and the
  operator configuration ConfigMap paths.
- Docs and the `ray-cluster.historyserver.yaml` sample no longer hardcode a collector image, and
  describe how to configure it on the operator.

Example:

```sh
helm install kuberay-operator kuberay/kuberay-operator \
  --set collectorImage=my-registry.io/kuberay/collector:v1.7.0
```

### KunWuLuan · 2026-08-31

In the sample you linked the container is named `collector` and the RayCluster doesn't set
`historyServerOptions`, so the operator never touches it — `SetDefaultCollectorImage` only
fills an *empty* image on the injected `ray-history-collector` container, so `${COLLECTOR_IMAGE}`
is preserved either way. Covering the manual case would mean requiring users to name the
container `ray-history-collector`, which validation rejects once `collectorOptions` is set, so
I'd rather just document that the operator-level image applies to the injected collector only.
WDYT?

### KunWuLuan · 2026-09-01

Good point — added a warning to `historyserver/docs/README.md` in 9c47e7f4. It spells out that injection is keyed on the `ray-history-collector` container name, so validation only catches that exact name and a sidecar added by hand under any other name (like the `collector` in the sample) stays in place, giving you two collectors per Pod. The doc now says to remove the manual sidecar in the same patch that enables `collectorOptions`.

CI is green, so this should be ready for another look.
