## Why are these changes needed?

Our CI is sometimes flaky. Maintainer need to push an empty commit to start CI again.

This PR adds a new workflow, `.github/workflows/retest.yaml`. Maintainer can comment (`/retest` or `/retest-all`) on a PR to rerun CI:

| Comment | GitHub Actions | Buildkite |
| --- | --- | --- |
| `/retest` | Re-run only the failed jobs | Retry only the failed jobs in the latest build |
| `/retest-all` | Re-run all jobs | Rebuild the latest build |

- Only the PR author or people with write access can use it.
- The bot adds 🚀 when it starts, 👍 when it is done, and 😕 when it fails.
- It posts a comment that shows what it did for each workflow and for Buildkite.
- It skips runs that already passed (for `/retest`) and runs that are still running.
- It does nothing on closed or merged PRs.

### Safety

This workflow has secrets and write permissions, so:

- It never checks out or runs the PR code. It only calls the GitHub and Buildkite APIs.
- It never creates a new Buildkite build. It only retries or rebuilds a build that
  Buildkite already made from the webhook. So it cannot skip Buildkite's fork checks,
  and the PR cannot choose the branch name.
- It skips runs that are waiting for a maintainer to approve them
  (`action_required`), so it cannot skip the approval step for new contributors.

### Setup needed before merge

A maintainer needs to add the `BUILDKITE_API_TOKEN` repository secret.
The token needs the `read_builds` and `write_builds` scopes for the
`ray-project/ray-ecosystem-ci-kuberay-ci` pipeline.
Without the token, the Buildkite part is skipped and only GitHub Actions is re-run.

Note: `issue_comment` workflows only run from the default branch.
So `/retest` will start to work only after this PR is merged.

### Manual test instructions

I tested the same workflow in a test repo with a flaky GitHub Actions workflow
and a flaky Buildkite pipeline. The only change is the Buildkite org and pipeline names.
You can see all the bot comments here: https://github.com/yjaw/retest-experiment/pull/2

| Case | Result |
| --- | --- |
| `/retest` when everything passed | All skipped |
| `/retest` when some GitHub Actions jobs failed | Only the failed jobs ran again |
| `/retest-all` | All GitHub Actions jobs ran again, Buildkite #7 was rebuilt as #11 |
| `/retest` when the Buildkite build failed | Failed jobs were retried in the same build (#11) |
| `/retest` while a workflow is still running | Skipped (`still queued`) |
| `/retesting please` | Ignored, no reaction |
| `/retest` on a merged PR | 😕 and no re-run |
