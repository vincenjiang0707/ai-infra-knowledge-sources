# [PR #5086] [history server] Land on the dashboard from the enter_cluster URL itself

source: https://github.com/ray-project/kuberay/pull/5086
state: open | updated: 2026-09-23T06:25:41Z
labels: 

## 正文

## Why

`enter_cluster` answered with JSON, so a browser following the link still had to load
the dashboard separately. The `?redirect=` variant originally proposed in this PR could
not close that gap: the Ray dashboard's `--proxy-server-url` middleware follows redirects
server-side and consumes both the redirect and the `Set-Cookie` headers that ride on it,
so the browser never receives them (root cause analysis in
https://github.com/ray-project/kuberay/pull/5086#issuecomment-5489460659). Per the
discussion, the URL is now deterministic instead and the redirect feature is dropped:
https://github.com/ray-project/kuberay/pull/5086#issuecomment-5504342791

## What

Serve a bootstrap page from `enter_cluster` once the cluster context cookies are set:

- The cookies ride on a **200** response, which every proxy in front of the History
  Server passes through with its headers.
- The page hands the URL fragment (e.g. `#/overview`), which never reaches the server,
  to the dashboard root client-side, so the landing page is chosen by the URL itself
  and no server-side redirect ever happens. There is no client-controlled redirect
  target to validate.
- The route drops its JSON `Consumes`/`Produces` declaration and declares
  `text/html` instead, so browser-style navigations (`Accept: text/html`, or a
  `Content-Type` added by a proxy in front) are not rejected with 406/415.

One navigation to

```
http://<entry>/enter_cluster/<namespace>/raycluster/<name>/#/overview
```

lands on a rendered overview with the cluster context applied. Verified end to end in a
browser behind both a reverse-proxy entry and the Ray dashboard's own
`--proxy-server-url` middleware.

### KunWuLuan · 2026-09-01

Thanks for testing! I reproduced the exact same `404: Not Found` and tracked it down — it's not a session-resolution failure on the history server side.

**Root cause.** With `--proxy-server-url`, the Ray dashboard proxies `/enter_cluster/...` to the history server. The history server does answer correctly: it resolves the session, sets the context cookies, and returns `302 Location: /#/overview`. But the dashboard's proxy middleware calls `session.request(...)` without `allow_redirects=False`, so *aiohttp itself* follows the 302 — it re-requests `/` on the history server, which has no route for `/` and returns 404. The middleware sees a final 404, discards the body, and falls back to the local dashboard handler, which has no `/enter_cluster` route either. That fallback is the `404: Not Found` you saw. The `Set-Cookie` headers are consumed on the intermediate hop and never reach the browser, so even a 200 redirect target wouldn't work in this topology.

Trace from a verbatim copy of the middleware:

```
-> GET /enter_cluster/default/raycluster/raycluster-historyserver?redirect=/%23/overview
   hops=[(302, '/#/overview')]  final=404  final_url=.../
   Set-Cookie on final resp = []
   FALLBACK, discarded body=b'404 page not found\n'
<- 404 Not Found, Content-Length: 14, body "404: Not Found"
```

**Why this works in the deployment we run.** In the history server solution we provide, the dashboard is not the front door — an Envoy entry proxy is. Envoy owns the browser-facing port, routes the history-server paths (`/enter_cluster`, `/clusters`, `/select_cluster`, ...) to the history server and everything else to the Ray dashboard, and passes the 302 plus `Set-Cookie` straight back to the browser. The dashboard still gets `--proxy-server-url` pointed at the history server for its own API calls.

That topology is exactly what makes `redirect=` a single link: one navigation to

```
http://<entry>/enter_cluster/<ns>/raycluster/<name>?redirect=/%23/overview
```

lands the user on a rendered `#/overview` with all context cookies set. Verified end-to-end in a browser — title `Overview | Ray Dashboard`, cookies present, and the history-server-specific strings render in the page, so the SPA's XHRs are resolving against the history server.

Minimal standalone version of that entry proxy:

```yaml

metadata:
  name: ray-history-entry-envoy
data:
  envoy.yaml: |
    static_resources:
      listeners:
      - address:

        filter_chains:
        - filters:

            typed_config:
              "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
              stat_prefix: ingress_http
              use_remote_address: true
              stream_idle_timeout: 0s
              upgrade_configs:
              - upgrade_type: websocket
              route_config:
                virtual_hosts:
                - name: all
                  domains: ["*"]
                  routes:
                  - match: {path_separated_prefix: "/enter_cluster"}
                    route: {cluster: historyserver, timeout: 0s}
                  - match: {path_separated_prefix: "/clusters"}
                    route: {cluster: historyserver, timeout: 0s}
                  - match: {path_separated_prefix: "/select_cluster"}

      labels: {app: ray-history-entry}

      containers:
      - name: envoy

        args: ["-c", "/etc/envoy/envoy.yaml"]
        ports:
        - containerPort: 8088
        volumeMounts:
        - {name: cfg, mountPath: /etc/envoy}

      - name: cfg
        configMap: {name: ray-history-entry-envoy}
---

kind: Service

  name: ray-history-entry
spec:
  selector: {app: ray-history-entry}
```

### KunWuLuan · 2026-09-17

@machichima 

Picking this PR back up with the deterministic URL approach we discussed. It is rebuilt on top of master as a single commit, and the `?redirect=` parameter is dropped.

`/enter_cluster` resolves the session and sets the context cookies as before, but now serves a bootstrap page instead of a JSON body:

```html
<script>location.replace("/" + location.hash)</script>
```

A single navigation to `http://<entry>/enter_cluster/<ns>/raycluster/<name>/#/overview` lands on the dashboard overview with the cluster context applied. The landing page travels in the URL fragment, which never reaches the server, so the URL is itself the address and no server-side redirect is involved.

Two properties worth noting for review:

- The cookies ride on a 200 response rather than a 302. The dashboard's proxy middleware follows redirects itself and discards both the redirect and its `Set-Cookie` headers, but it passes 200 responses through with their headers, so the flow works with either a reverse-proxy entry or the dashboard (`--proxy-server-url`) as the front door. Verified end to end in a browser in both topologies.
- The route no longer declares `Consumes(MIME_JSON).Produces(MIME_JSON)`. Under that declaration go-restful answers browser-style navigations with 406/415, so the route now declares `text/html`.

The JSON response is removed. `curl` usage is unchanged (cookies are saved with `-c`, noted in the docs); unit tests cover the bootstrap contract and browser-style headers; the e2e helpers assert the resolved cluster and session through the response cookies.
