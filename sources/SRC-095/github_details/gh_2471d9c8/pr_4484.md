## Why are these changes needed?

According to https://github.com/ray-project/kuberay/pull/4160#issuecomment-3693559643 ,this PR uses the informer cache to list RayJobs and query the `JobInfo` in advance before calling getJobInfo. Additionally, it makes the query interval and etc configurable.

How it works:
- There a goroutine to list RayJobs from the informer cache and put them into queue.
- A group of workers retrieve a RayJob in the queue individually and get the JobInfo stored into a cache storage for later use.

This is actually the same situation we ran into with the flaky tests before. https://github.com/ray-project/kuberay/pull/4433
In our e2e tests, we assume that `RayJobStatus` must already be terminated before `RayJobDeploymentStatus` reaches a terminal state.

For example:
https://github.com/ray-project/kuberay/blob/ddb56db5f0e2423229d7fd9db03a342ead650bd6/ray-operator/test/e2erayjob/rayjob_sidecar_mode_test.go#L83-L110

In the `JobDeploymentStatusRunning` case, the reconciler executes steps in this order:
1. checkSubmitterAndUpdateStatusIfNeeded: Set `JobDeploymentStatus=Failed` if Submitter container ExitCode != 0 
https://github.com/ray-project/kuberay/blob/ddb56db5f0e2423229d7fd9db03a342ead650bd6/ray-operator/controllers/ray/rayjob_controller.go#L1014-L1062

2. `GetJobInfo`: updates `JobStatus` from Ray dashboard if job is terminated

https://github.com/ray-project/kuberay/blob/ddb56db5f0e2423229d7fd9db03a342ead650bd6/ray-operator/controllers/ray/rayjob_controller.go#L291-L344


When the sidecar container terminates (non-zero exit), step 1 sets `JobDeploymentStatus=Failed` and breaks before step 2, so `JobStatus` is never updated. This is an existing issue, but async cache (ErrAgain) significantly widens the window.

- Without async cache, earlier reconcile iterations would call the dashboard directly at step 2 and successfully update `JobStatus` (e.g., to RUNNING or FAILED). So by the time step 1 detects the sidecar failure, `JobStatus` is already reasonably up to date.

- With async cache, earlier iterations may return `ErrAgain` at step 2 (cache miss) and requeue without updating `JobStatus`. If the sidecar terminates before the cache is populated, the reconciler hits step 1 → shouldUpdate=true → breaks, and JobStatus remains empty or stale.

This also affects the Reason classification. `rayJob.Status.JobStatus == rayv1.JobStatusFailed` to distinguish `AppFailed` from `SubmissionFailed`, but with a stale `JobStatus`, this check is unreliable.

This is a pre-existing issue that predates this PR, but since async cache makes it more likely to surface, it's worth considering.

I am thinking we can change this logic for async.

https://github.com/ray-project/kuberay/blob/ddb56db5f0e2423229d7fd9db03a342ead650bd6/ray-operator/controllers/ray/rayjob_controller.go#L1057-L1061

## Pull request overview

This PR refactors the async job info query feature to use the informer cache for proactive RayJob discovery and background job info fetching, replacing the previous on-demand caching approach. The implementation introduces a worker pool that periodically lists RayJobs from the informer cache and dispatches workers to query job status from Ray dashboards in parallel, storing results in a shared cache. The query interval, worker pool size, and cache expiry are now configurable via environment variables.

- Removes context parameter from dashboard client initialization functions throughout the codebase

@chiayi 
To ensure fairness during load testing, we should configure the concurrency numbers like this:

sync RayJob controller concurrency = async RayJob controller concurrency + worker pool concurrency

Under this setup, both RayJob controller implementations use the same number of goroutines, making the comparison fair.
