## 📌 Description

Add a planned CuTe DSL runner for native MXFP4 W4A8 routed MoE with runtime
SiTU `beta` and optional `linear_beta` on NVIDIA B300 (H=7168, I=3072,
896 global experts, top-k=16, EP8/local112). Native packed E2M1 weights use
group-32 UE8M0 scales; activations are E4M3 and the output is the combined
rank-local BF16 result.

`CuteDslMxfp4MoEWrapper` provides metadata-only workspace sizing and a stable
`plan(...)` / `run()` lifecycle. Planning binds caller-owned output/workspace
and prepares kernels before graph capture. Execution uses precomputed global
routing plus a local expert offset, runtime scalar/per-expert parameters and
the caller's stream, without forward allocation, host synchronization,
device-to-host metadata or compilation. Weights are rearranged losslessly at
load time, and GEMM1 explicitly quantizes its FP32 activation to MXFP8.

An optional paired W1/scale representation,
`prepare_cute_dsl_mxfp4_decode_weights(w1, w1_scale)`, can be passed to
`plan(paired_decode_weights=...)` next to the four canonical prepared
weights. It is selected only for B300 SiTU decode at T=2, 4 and 16 at the
full shape above (PDL off, default tactics, 16-byte-aligned activations);
every other plan binds the canonical weights, and anything but the exact
prepared pair is rejected where the pair would be selected. It retains
`E * 2*I * (H/2 + H/32)` bytes (2,620,391,424 bytes for 112 local experts)
beside the canonical bank; W2 is shared.

Default decode on B300 with SiTU, PDL off, at most 112 local experts and
top-k at most 16 has **two launches** at T1..16: GEMM1 with the routing
folded into its prologue (routing unpack/conversion, output clear and the
local expert histogram/prefix/scatter, recomputed deterministically by every
CTA; the block-0 CTA rewrites the routing words the finalize consumes) and
GEMM2 with finalize. Plans outside that scope keep a separate fused route
preprocess launch ahead of GEMM1 and GEMM2 (three launches). On B300 with SiTU,
PDL off and both GEMMs on the M128/N128, cluster1, non-raster tactics,
T1..16 uses a skinny gather GEMM1 (aligned 16-byte K-vector loads; at T16 a
constant-shape scheduler with per-slot planes), a skinny finalize GEMM2 at
T8/T16, a compact-output finalize at T4 and the 16-row narrow A transfer
otherwise. At T4 and T16 the skinny finalize splits the last partial round
of work items across the grid in K slices when the item count exceeds the
grid (a stream-K tail: each slice is a fresh accumulation that is
reduce-added into the cleared BF16 output), so at those two token counts
with balanced routing the output is not bit-reproducible run to run; it
stays within the documented tolerances and the FP64 gates. At the full shape with T=512 the routing kernel also sorts
assignments, GEMM1 runs as dense and sparse route-tile launches with a
sparse-prefill epilogue, GEMM2 adds an N16 sparse finalize and a separate
combine kernel accumulates weighted expanded contributions; at T=1024 the
routing kernel clears the output with a single-pass vectorized clear. Other
routing/finalize configurations retain their existing paths. Native
approximate FP32 tanh is restricted to mixed W4A8 SiTU gate/up-clamp
evaluation. Shared counted-barrier (unaligned named barrier) and TMEM
ordering (tcgen05 fences) helpers are included. Public layouts, workspace
sizing, dispatch conditions and memory use are documented in
`docs/mxfp4_situ_moe.rst`.

One prepared bank occupies 3,930,587,136 bytes. `get_workspace_size(T)` at
the full shape with the default tactics returns 6,499,072 (T1), 12,995,328
(T2), 25,987,840 (T4), 45,477,888 (T8), 45,885,440 (T16), 51,591,168 (T128),
58,112,512 (T256), 188,594,688 (T512, including the 117,440,512-byte BF16
expanded-contribution buffer), 97,238,016 (T1024), 149,412,864 (T2048) and
253,748,224 (T4096) bytes; activations/output and load-time temporary storage
are separate. Measured kernel activities per forward at that shape (identical
for eager and Graph and for balanced, empty-expert and hot routing) are two
for T1..16 (the routing is folded into GEMM1), four for T128/T256 and
T1024/T2048/T4096, and six for T512;
TRT-LLM Gen launches four for every T. These are per-forward counts, not a
count of compiled variants. Default GEMM1/GEMM2 shared storage is
228,352/207,872 bytes per CTA with 512 TMEM columns each; the folded decode
GEMM1 adds 8,192 shared bytes per CTA (227,328 dynamic bytes for the T1/T8
skinny gather, 228,352 at T2, 225,280 at T4/T16), with TMEM allocation,
workspace layout and sizes unchanged.

### Update: decode routing folded into GEMM1 (T=1..16)

* **Two device-kernel launches per default decode forward instead of three.** On the dedicated B300 decode kernels
  (SiTU, PDL disabled) with at most 112 local experts and top-k at most 16, the GEMM1 gather kernel now unpacks and
  converts the routing, clears the output and rebuilds the local expert histogram / prefix / scatter tables itself.
  Every CTA recomputes the routing deterministically from the caller's top-k ids in shared memory (a warp-level
  match/rank over the at most 256 assignments and per-warp expert counts); the CTA with block id 0 rewrites the routing
  words in workspace that the GEMM2 finalize consumes. Plans outside that scope (PDL enabled, more than 112 local
  experts, top-k above 16, other shapes) keep the previous launches unchanged. On every qualification stage the GEMM1
  intermediates are byte-identical to the previous revision and the rewritten routing words are equal up to the
  (unspecified) rank of an assignment inside its expert tile; the BF16 output is byte-identical to the previous
  revision where the previous revision was reproducible.
* **Host**: the plan selects the fold from the same information it already validates (decode specialization, local
  expert count, top-k, 512-multiple hidden size, 4-byte aligned output, no expanded-contribution combine); fold
  arguments that would not reach a folded kernel raise instead of being dropped. The plan's warm-up still runs the
  native path once and then one two-launch forward, so the plan keeps its valid-output postcondition before capture.
* **Public tests**: `test_full_kimi_decode_route_fold_graph` (T1/2/4/8/16: the fold is selected; the separate-sort plan
  is the cross-kernel oracle; routing words are poisoned and rewritten under an existing CUDA Graph capture while the
  packed routing is changed in place over hot / balanced / empty distributions; no compilation) and
  `test_full_kimi_decode_route_fold_guard` (113 local experts: fold off, separate preprocess kept, FP64 / TRT-LLM Gen
  bound, Graph replay). Docs: launch counts, shared-memory note and the kernel-activity table.
* Upstream pre-commit formatting and lint/typing markers are applied to the exported files; `pre-commit run` passes on
  every changed file at the head.

**Security architecture risk:** _🟠 High_ · up to `be130`

The new decode path relies on unique routing IDs to keep GPU scratch writes in bounds, but planning does not verify that condition. Malformed routing can therefore exceed the space reserved for an expert. The exposure depends on whether an application lets untrusted inputs influence those IDs.

**Retained concerns**
