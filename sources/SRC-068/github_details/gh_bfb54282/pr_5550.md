## 📌 Description

Adds `CakeW4A8MegaMoeEp16CuteDsl`, an explicit experimental API for a complete
MXFP4-weight / MXFP8-activation MegaMoE forward on 16 mutually NVLink-accessible
GB300 GPUs. Inputs and outputs are BF16; geometry is H=3072, I=5120, E=512,
top-k=8, with 32 contiguous experts per rank. Each GPU requires SM103a and 152 SMs.

One CuTeDSL device image handles equal local token counts from 0 through 384.
Its single eager kernel includes input quantization, dispatch, communication,
FC1/SwiGLU, intermediate quantization, FC2, ordered combination and cleanup.
`session.prepare(x, router_weights, out=output)` binds storage and the setup
stream once; subsequent calls read the live contents. `session.forward(...)`
is also supported. Static weight repacking preserves quantized values and scales.
A small host C++ extension retains the native CUDA launch configuration; all
device code is compiled through CuTeDSL.

The core entry point imports the experimental implementation lazily. There
is no AOT registration or automatic backend selection. Routing IDs and token
count are fixed during collective session setup; activations and normalized
FP32 router weights may change on every call. Calls must be serialized on
the setup stream with disjoint caller-owned output. CUDA Graph capture and
concurrent session use are unsupported.

Validation uses CuTeDSL 4.7, CUDA 13.3 and DeepGEMM
`559d79fb6994a58b8a15b4b93bf13ccc16edf247`. The measured cubin is
`9cb93b4526e10c0b94dee66ea5468c8ce6d2e4b1aefac5c9dcfaa13b4843fcf6`.
The actual public API passes all 11 canonical/stress fixtures against
DeepGEMM at `atol=rtol=1e-2`, relative L2 below 0.02, and finite-output checks.
The ten checked-in tests pass on all 16 ranks (160 results, no skips), with
three consecutive forwards per case, changed contents at fixed addresses,
closed-launch rejection, empty input, duplicate routes, extreme 17-token
input and 384-token all-hot routing. A subprocess test verifies first-time
compilation and cache reload without CuTe artifact environment variables.
The setup fix preserves the measured object and cubin byte-for-byte, and
does not change the device program or eager forward submission code.

Performance compares **D CUDA Graph / C eager / Q eager**. D retains FlashInfer
`2f1dd17d0c40badb0a866d5ca370ac5b428eed91` and the DeepGEMM revision above.
Only the new public Q feature is imported over that dependency tree; its nine
shared support modules are byte-identical in the public checkout and pinned
FlashInfer tree. Correctness tests also run separately from the public checkout.
C is the separately sealed fused CUDA control, cubin
`0f7d043d8728c81d30d1cc83ed74f1c83fe3744889d55c0487b896c174e4009a`.
The related CUDA implementation in #5480 is not an interchangeable compiled control.

Latency is in microseconds; T is the global token count. Each row uses three
balanced-order groups, 100 ms warmup and 1,000 ms measurement per arm. Cold-L2
CUPTI spans cover the complete forward, including copies, memsets, gaps and
cleanup. Reduction takes the maximum across 16 ranks per sample, the median
within each group, and the median of three groups. D Graph captures the full
native forward; graph construction is setup.

Q group medians range from 153.857–154.4005, 155.552–156.608,
159.168–161.472, 153.248–154.144, 156.129–156.992 and
164.3205–164.544 microseconds, respectively. Every row meets D/Q >= 1.10
and C/Q >= 1.0 without rounding the acceptance ratios.

The final campaign uses three fresh EP16 processes, each with 32 saved
replays on all six canonical rows. An independent audit reopens 9,216 Q and
9,216 C outputs and verifies bitwise identity within and across processes,
identical input bindings and the same Q object/image on all ranks. The exact
final public source is `5a5761ba577d6aa8becfee89a28f76d83d291149`.
No sanitizer result from a different image is attributed to this executable.
