## Agent Notes

Two 64-head tokens share a 128-row cluster tile (the kernel's existing 2-tokens-per-tile pack-GQA case, so no padding) and one gather list. The CTA rank selects the token: `m_idx = 2 * cluster_m_block + cta_rank_in_cluster`, peer `m_idx ^ 1`. The gather pointer for a slot is `max(own, peer)`; the validity bitmask uses the CTA's own list, so its 64 rows are masked to its token's selection with the existing mask path. Causal `seqlen_k_limit` is per token (the gather itself uses the pair max). Forward and backward, non-varlen. H <= 64: fewer heads pad to the 64-row half-tile with #2883's mechanism (each CTA still holds one token, so the per-CTA mask is unchanged); verified at H = 16, 32, 48. 64 < H < 128 stays on the single-token padded tile.

Index contract (`_flash_attn_fwd(..., gather_kv_token_pairs=True)`): rows `2p` and `2p+1` of `gather_kv_indices` hold the same pair-union list, padded to a multiple of 128, with `-1` at the slots that token does not attend. `-1` is the minimum, so `max(own, peer)` recovers the union without a third tensor.

Unchanged: attention math, the 128-head path, tiling, pipeline synchronization, #2883's padding path (still used for other head counts).

## Why it helps

Per token the padded tile does 128 rows x K slots of MMA for 64 useful rows. The pair tile does 128 rows x |A u B| slots, all rows useful. Useful MMA fraction = K / |A u B| instead of 1/2, and the pair's KV rows are gathered once. The tile count also halves, which matters because the forward is latency-limited at 1 CTA/SM (NCU in #2883: tensor pipe 38%, no eligible warp 80% of cycles).

Union size from synthetic DSv4-shaped indices (window 128 + causal compressed top-k 512, T=4096):

| indices | \|A\|+\|B\| | \|A u B\| padded to 128 | useful MMA | gather rows vs per-token |
|---|---:|---:|---:|---:|
| random top-k | 764 | 573 | 67% | 67% |
| 80%-local top-k | 764 | 474 | 81% | 53% |

Random picks are the floor; a trained indexer should be far more local (smooth scores across adjacent queries, recency skew, and the 128-slot window overlaps 127/128 by construction). At K/N << 1 (very long sequences) the random union approaches 2K and the gain falls back to the tile-count effect unless the indexer is local or tokens are paired by list similarity.

## Experiment: real DeepSeek-V4-Flash indices

The synthetic tables above assume how much nearby tokens' top-k lists overlap. We measured this with
PG-19 books and concatenated PyTorch source, 32k–256k tokens each. We ran the released
`deepseek-ai/DeepSeek-V4-Flash`, layers 0–2 only, using its reference `inference/model.py`. We checked
that the chunked indexer matched the unchunked reference bit-exactly. We saved the layer-2
lightning-indexer output: each token's list of `index_topk = 512` compressed-KV slots (compress ratio 4).
We passed these lists unchanged to `bench.py --real`: a 4096-token window at each position, H=64,
D=64/512, gathering from the full compressed KV. We compared the padded #2883 path with this PR's pair
path, using CUDA-graph medians on GB200.

![Real V4-Flash indexer: neighbour overlap and pair-union width vs document position](https://github.com/user-attachments/assets/f640b73e-d448-4541-88e4-b91e86ed0a10)

Left: how many of token t's 512 picks token t+1 also picks, as a fraction. This falls from 0.8 early
in a document to 0.5 at 256k. Right: the width of each pair's union. A typical pair needs 600–770 slots.
But the kernel runs every tile at the widest pair's width in the call
(`n_block_max = topk_length // tile_n`). That width reaches 2K from ~32k tokens on in prose and ~128k
in code.

![Speedup of token pairs over padding with real indices, forward and forward+backward](https://github.com/user-attachments/assets/50773ea6-e745-4208-8fc2-64fc638c2fe9)

Forward: pairs are 10–40% faster at every position. Forward+backward: pairs are 11–18% faster while the
widest pair stays under ~900 slots (through 8k in prose, 32k in code). They are 10–15% slower once one
pair pushes the call width to 2K. This is because P/dS and the backward gathers scale with that width.

![Pair speedup vs kernel union width, synthetic and real](https://github.com/user-attachments/assets/690428d8-d1bc-4542-a51c-e954ffb541a4)

Synthetic (K=1024) and real (K=512) runs follow one curve when plotted against union-width/K. The gain
depends on the width the kernel runs, not the average overlap. The follow-up to make long-context rows
faster: set `n_block_max` per tile using each token's valid count. This skips each pair's trailing
all-`-1` blocks in the forward, backward main and dQ/dQv/dK kernels. The typical pair's 1.2–1.5x width
predicts ~1.1–1.3x forward+backward everywhere. We also tested 4x32 / 8x16 tiles for H=32 / 16 on these
lists. They are no faster than the padded path: the union grows faster than the rows saved. So these
tiles are not planned.

Harness and data: `agent_space/realistic/` (`samplers.py`, `bench.py`, `plots.py`, `v4flash/run_indexer.py`,
saved lists in `v4flash/indices/*.pt`).
