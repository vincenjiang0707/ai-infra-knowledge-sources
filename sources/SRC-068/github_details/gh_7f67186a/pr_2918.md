# [PR #2918] [CuTe, SM100] Keep tile_n=128 for FP8 diff-headdim SplitKV

## 正文

## Problem

FP8 forward (q/k/v `float8_e4m3fn` with q/k/v descales) with `head_dim != head_dim_v`, e.g. 192/128, on SM100/SM110 returns wrong output without raising once SplitKV is used and the KV length reaches 64 tiles, i.e. `seqlen_k >= 8192` at tile_n=128:

- 8K to 20K: output cosine 0.63 to 0.73 against a reference, or NaN.
- About 60K: illegal memory access.
- Below 8K, `_get_fwd_config` forces `num_splits=1` and the output is correct (cosine 0.9996). Forcing `num_splits=1` at 8K and above is also correct.

Cause, as far as I can tell: since #2338, diff-headdim SplitKV drops to tile_n=64 when `num_n_blocks >= 64`, so the float32 partial O fits in shared memory. The tile_n=64 forward kernel is wrong for FP8. The failure is not specific to SplitKV or to 192/128. Forcing `tile_mn=(128, 64)` with FP8, `num_splits=1`, 128/128 and non-paged KV also gives an illegal memory access on the same GPU. Capping `kv_stage` (22 to 11 for 128/128, 13 to 6 for 192/128) makes no difference. On SM100 the default config never otherwise picks tile_n=64, so this branch is the only automatic route into that kernel.

I found no existing issue or PR for this.

## Fix

This PR avoids the FP8 tile_n=64 kernel. It does not fix it.

- `_get_fwd_config` takes `is_fp8`. For FP8 inputs, the diff-headdim SplitKV branch keeps tile_n=128 and the splits instead of dropping to tile_n=64. FP8 K/V tiles are half the bytes, so tile_n=128 fits with the float32 partial O: `kv_stage` for 192/128 is 6 at q_stage=1 and 4 at q_stage=2. The `num_splits=1` fallback for `num_n_blocks < 64` and `head_dim_v == 512` is unchanged.
- `_flash_attn_fwd` passes its existing `is_fp8`.
- `get_scheduler_metadata` gets a `qkv_dtype` argument (default bf16, same name as in the FA3 API). Metadata precomputed for an FP8 call then uses the same tile_n and num_splits as the forward.

A real fix for the FP8 tile_n=64 kernel would be welcome. If one lands, this branch can go back to the old behavior.

## Results

All numbers are from an NVIDIA GB300 (SM103, 152 SMs), driver 595.91.07, CUDA 13.0. I found the bug through vLLM (0.30.1rc1.dev143) serving MiMo-V2.6-Pro with an FP8 KV cache. That is 192/128 DiffKV, 8 KV heads and 128 Q heads per rank.

**Correctness** (main `e9cf2c1` vs this branch). One decode token, 8 KV heads, 128 Q heads, 192/128, FP8 e4m3 with unit descales. Paged KV uses page size 16 in a vLLM-style fused `[pages, kv_heads, 16, 192+128]` cache, with K/V as strided views. The request's pages sit at the tail of a 4000-page pool. The reference is FP32 attention on the dequantized inputs. `num_splits=0` (auto).

| seqlen_k | main: config | main: cosine | this PR: config | this PR: cosine |
|---:|---|---|---|---|
| 4096 | tile_n 128, 1 split | 0.99964 | tile_n 128, 1 split | 0.99964 |
| 8192 | tile_n 64, 19 splits | 0.65274 | tile_n 128, 19 splits | 0.99963 |
| 16384 | tile_n 64, 19 splits | NaN | tile_n 128, 19 splits | 0.99965 |
| 60000 | tile_n 64, 19 splits | illegal memory access | tile_n 128, 19 splits | 0.99965 |

These cases were also correct with this PR (cosine 0.9996 to 0.9997):
- `seqlen_q=32` (q_stage=2, 9 splits) at 8K, 16K and 60K.
- 1 KV head with 16 Q heads (64 and 128 splits) at 8K, 16K and 60K.
- Metadata precomputed with `get_scheduler_metadata(..., qkv_dtype=torch.float8_e4m3fn)`.

BF16 192/128 still picks tile_n=64 with 19 splits and matches the reference (cosine 1.00000).

**Decode timing** (main `e9cf2c1` + this PR). Same shape as above, contiguous pages, CUDA graph replay, mean of 100 replays. The ranges cover two rounds. Another process was serving on this GPU at the same time, so treat absolute times as noisy. Lower is better.

| seqlen_k | FP8, auto splits (this PR) | FP8, num_splits=1 | BF16, auto splits |
|---:|---:|---:|---:|
| 8K | 18.5 to 20.6 us | 136.5 to 141.0 us | 46.4 to 49.1 us |
| 64K | 99.9 to 100.0 us | 958.4 to 958.7 us | 147.4 to 150.7 us |
| 256K | 325.6 to 329.4 us | 3775 to 3812 us | 584.5 to 585.1 us |

I also measured the same change through vLLM's vendored FA4 copy (synced from vllm-project/flash-attention), with the same shape per layer. FP8 took 20, 50, 143 and 503 us against 23, 74, 240 and 911 us for BF16 at 8K, 64K, 256K and 1M. Forcing `num_splits=1` for FP8 instead was correct but about 7x slower at 1M.

## Test plan

- New `test_flash_attn_fp8_paged_decode_diff_headdim_splitkv` (SM100-only, like the other FP8 paged decode tests). It runs one query token with 16 Q heads, 2 KV heads and 192/128 FP8, over `page_size` {16, 128}, `seqlen_k` {8192, 20000} and `num_splits` {0 (auto), 3}. It asserts no NaN and cosine > 0.99 against `_fp8_decode_reference`. `_run_fp8_paged_decode` now takes `head_dim_v` from `v` and accepts `num_splits`.
- On main `e9cf2c1`, all 8 new cases fail, each run in its own process (cosine 0.7042 at 8192, 0.6292 at 20000). With this PR, all 8 pass.
- With this PR, `-k "paged_deepseek or cumsum_metadata_paths or seqlen_k_per_split or fp8_paged_decode"` in `test_flash_attn.py`, plus `test_splitkv_forwards_explicit_arch` in `test_flash_attn_combine.py`: 34 passed.
- Environment: `tests/cute` from this checkout, with `flash_attn.cute` from the checkout on `PYTHONPATH`, run inside the `vllm/vllm-openai` nightly image (nvidia-cutlass-dsl 4.7.1, torch 2.13.0+cu130, quack-kernels 0.6.5, apache-tvm-ffi 0.1.11) with `FLASH_ATTENTION_CUTE_DSL_CACHE_ENABLED=1`. I did not run the full suite because the GPU was shared with a serving process.
