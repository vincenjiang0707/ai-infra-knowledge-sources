## 正文

# Summary

TVM FFI allows passing `torch.Tensor` directly at runtime instead of `from_dlpack` conversion on every call, reducing launch overhead (~0.5μs per call per NVIDIA docs). Lets see if thats true :)

## What Works
- Simple forward pass (non-varlen, non-paged, no block sparsity, no aux tensors)
- `None` optional arguments need some shenanigans  (cutlass DSL 4.3.1+)
- Backward pass works works 

## Known Issues / warts

`**Blocker**`: Optional args dont seem to be working (at least as I expect) they seem to need to be all None or maybe all not None but no mixed. Following up with some folks

1. No kwargs at runtime
```python
# Fails: compiled_fn(..., mdQ_semaphore=value)
# Works: compiled_fn(..., value)  # positional only
```

2. BlockSparseTensors NamedTuple not supported
```
DSLRuntimeError: Unsupported argument type: <class 'BlockSparseTensors'>
```
TVM FFI arg spec converter can't handle custom NamedTuples - reported to cute folks

## TODO

### 1. Restructure compilation flow
Currently calling `from_dlpack` every invocation even on cache hit. Should:
- Check cache first
- Only convert tensors if compilation needed
- Pass torch tensors directly on cache hit

### 2. Use `make_fake_compact_tensor`
For compilation, use fake tensors with symbolic shapes (per CUTLASS examples) instead of real tensor conversion. Claims this is better perf and kind of get AOT for freeish

### 3. Debug ICE issues
Investigate LLVM operand count mismatches in certain kernel configurations.

### 4. BlockSparseTensors
Either wait for NVIDIA NamedTuple support or restructure to pass individual tensors.

### tqchen · 2025-12-03

Thanks @drisspg, these comments are very valuable! I want to chime in and provide some updates here.

> None mixing issue

This is indeed a bug when we have cute.jit function that has default value and also has positional values passed in, somehow we take the default value. We confirmed the bug and have a patch to fix this.


> Supporting namedtuple

This is a great suggestion, named tuple makes a lot of sense to logically group things together. We build a patch to add support so it should work in upcoming releases. Under the hood, it will pass as a normal tuple as ABI but all logics should work.

> Supporting kwargs in compiled functions

This was a case where we deliberately wanted to minimize the things we do at the interface level. From ABI pov, we deliberately do not support kwargs  with understanding that one-level of python wrapping would be able to provide interfaces needed for kwargs if needed.

```python
def foo(a, b, c=None, d=None):
     compiled_func(a, b, c, d)
```

Effectively something like above could work. There is a possibility to automatically generate such a python wrapper maybe but could need a bit more work, but my guess is that having a wrapper should work together.

Also want to clarify expected numbers, the 0.5us level number was referring to the cost from python to the FFI ABI layer(excluding kernel launch), if we include kernel launch what we observed so far was 2us level (in hot loop) and definitely moving checks into tvm-ffi could help (our previous experiences is that most such checks will be free and won't impact host perf as they are compiled), here are some [general notes on host perf minimization](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/cute_dsl_general/compile_with_tvm_ffi.html#minimizing-host-overhead)

The fixes mentioned above should land internally at NV hopefully today and we will work with the team (@fengxie and others) to ship as soon as possible in the incoming patch release. Thanks a lot for all the valuable suggestions and trying things out!

### tqchen · 2025-12-12

@yjk21 This is an issue that have been fixed in PyTorch upstream https://github.com/pytorch/pytorch/pull/164161 (but not yet in the latest release), if you try from_dlpack with tvm_ffi enabled, it may already solve the problem because tvm-ffi based dlpack conversion have the patch applied for that specific path.
