## Summary

The softmax warps of the sparse-MLA backward (`flash_bwd_mla_sm100.py`) rounded three intermediates to bf16 before forming `dS = P ⊙ (dP − dPsum) · softmax_scale`: the normalization scale `scale_p`, the normalized `P`, and `(dP − dPsum) · softmax_scale`. This PR keeps an fp32 copy of `P^T` and forms the product in fp32, rounding to bf16 exactly once for the dS store.

- **Load-P path (default):** the saved bf16 `p` is upcast, normalized with the fp32 `scale_p`, and rounded to bf16 once for the `dV += P^T·dO` mma operand; the fp32 copy is used for dS.
- **Recompute-P path (`gather_bwd_recompute_p=True`):** the fp32 `exp2` result already exists; it now stays live for dS instead of being re-read from the bf16 staging copy.
- Unchanged: forward kernel, saved activations, dS storage dtype, all mma operand dtypes, smem layout.
- `AI/SPARSE_MLA_RECOMPUTE_P.md` numerics section updated.

Both backward paths (load-P and recompute-P) get the same treatment so their dS numerics stay on one scheme.

### abcdabcd987 · 2026-09-23

@jayhshah Confirmed, the `seqlen_q=1` fault is on the PyTorch side, not in the FA4 kernels.

torch 2.14.0+cu130 routes `aten::bmm` through a Triton kernel (`torch/_native/ops/bmm_outer_product/triton_kernels.py`) whenever the contraction dim is 1. At `seqlen_q=1` the reference backward's `dV = Pᵀ @ dO` hits exactly that shape (B = batch·heads = 1536, M = seqlen_k, N = 512). The kernel forms the output batch offset as `pid_b * stride_ob` in int32, so once `(B-1)·M·N ≥ 2^31` the offset overflows and the store goes out of bounds → illegal memory access. The sticky error then surfaces at the next CUDA call, which is why the traceback pointed at Triton's module load.

Reproduces with no FA4 involved (GB200, `CUDA_LAUNCH_BLOCKING=1`), bf16 and fp32 alike:

```python
import torch
B, M = 1536, 8192
a = torch.randn(B, M, 1, device="cuda", dtype=torch.bfloat16)
b = torch.randn(B, 1, 512, device="cuda", dtype=torch.bfloat16)
torch.bmm(a, b)  # RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered
```

The boundary is exact: `B=1024, M=4096, N=512` passes (offset `1023·2^21 < 2^31`), `B=1025` faults (offset `== 2^31`).

Workaround: `TORCH_DISABLE_NATIVE_JIT=1` disables the `torch._native` overrides. With it, both previously failing cases pass on this branch:

```
test_flash_attn_mla_absorbed[0-1-8192-False-True-64-False-0-False-False-mqa-dtype0] PASSED
test_flash_attn_mla_absorbed_varlen[...-1-4096-...-mqa-dtype0] PASSED
```

So the PR-body note about a "pre-existing" `seqlen_q=1` fault should be read as a torch bug hitting the test's reference path; I'll report it upstream to PyTorch.
