## 正文

## Summary

Adds early `can_implement()` guards before `cute.compile()` so invalid tile, head-dimension, or shared-memory configurations fail with a descriptive `RuntimeError` instead of an opaque CuTeDSL error.

Reachable guarded paths:

- Forward: `FlashAttentionForwardSm80`, `FlashAttentionForwardSm120`
- Backward: `FlashAttentionBackwardSm90`, `FlashAttentionBackwardSm120`

SM90/SM100 forward and SM100 backward do not expose compatible predicates and remain unchanged. SM80 backward is not supported by the current interface, so this PR no longer claims or tests that interface path.

The rebase exposed a stale SM90 backward predicate: `num_threads` includes a 128-thread producer warp group, while the old SM80-style divisibility rule rejected the dispatcher's valid 384-thread configurations. The predicate now validates complete producer/MMA warp groups and is tested against current SM90 tiles.

## Merge dependency

#2751 owns the SM80 forward tile heuristic and architecture-aware SMEM-capacity parameter. This PR intentionally does not duplicate it. Once #2751 lands, the SM8x forward guard here must pass `smem_capacity_arch=f"sm_{arch}"` only for SM8x and add the `_arch=89`, `head_dim=256`, `tile_mn=(128, 64)` pre-compile rejection regression. Please do not merge #2609 before that integration is complete.

Backward SM8x capacity parameterization is left to a separate change if SM8x backward support is restored.

### arbi-dev · 2026-07-31

Nice, this is a real gap that's worth closing. One thing worth fixing before/alongside merge: `FlashAttentionForwardSm80.can_implement` (and `FlashAttentionBackwardSm80.can_implement`, same pattern), which this PR wires up, still compute their SMEM budget from a hardcoded `"sm_80"` string:

```python
# flash_attn/cute/flash_fwd.py:168-169 (main @ c75d019)
# TODO: sm86 and sm89
smem_capacity = utils_basic.get_smem_capacity_in_bytes("sm_80")
```

`SMEM_CAPACITY_MAP` in `cutlass.utils` gives `sm_80: 166912` (A100) but `sm_86: 101376` and `sm_89: 101376` (RTX 30xx/40xx) — a 39% smaller budget. So on sm_86/sm_89 this guard checks against the wrong (larger) capacity and will incorrectly pass configs that actually overflow at launch.

Concretely: `_flash_attn_fwd`'s SM80 branch (`interface.py:539`, `fwd_cfg = FwdConfig(128, 64, True, True)  # SM80, should tune`) picks the same `tile_m=128, tile_n=64` for every head_dim. At `head_dim=256` that needs `2*(128*256) + 2*64*(256+256) = 131072` bytes of static SMEM. `can_implement` as wired by this PR would compute `131072 <= 166912` → `True` (guard passes) on an RTX 4090 (sm_89), but the real launch-time budget there is `101376` bytes, so the kernel still crashes with a raw `cudaErrorInvalidValue: Allocated: 131072 bytes. Max: 101376 bytes.` — the exact opaque failure this PR is trying to turn into a clean error. I reproduced this on an actual RTX 4090.

I'm filing a follow-up issue + PR for the underlying root cause (the SM80 tile heuristic has no head-dim branching at all, unlike `_tile_size_fwd_sm90`) plus a fix for this capacity-constant bug specifically, since it's a separate issue from what this PR addresses (wiring the guard calls). My fix parameterizes `can_implement`'s capacity lookup (defaulting to `"sm_80"` for backward compatibility with existing call sites) so a caller — including this PR's guards, once rebased — can pass the actual detected arch (e.g. `f"sm_{arch}"`) instead of the hardcoded constant.

Thanks for pushing this forward — the early-guard idea here is the right shape, this is just one more piece needed for it to actually catch the sm_86/sm_89 case.
