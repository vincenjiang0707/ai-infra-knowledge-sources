## 正文

### Human note

Adds pack gqa support; nice wins

## Problem

The SM100 hd256 forward kernel never packed GQA. `interface.py` silently forced `pack_gqa=False`, so every
Q head got its own 2CTA cluster whose 256-row Q tile held `seqlen_q` real rows, and each KV tile was read
once per Q head. For decode that means `h_r`× redundant KV traffic: on Qwen3.5-27B (24 q / 4 kv heads,
d=256), batched decode was 6-7x slower than TRT-LLM's decode kernel.

## Fix

The kernel packs the `h_r` Q heads of a KV head into the row mode, as in `FlashAttentionForwardSm100`:
Q/O/LSE get a `(h_r, s)` row mode (`pack_gqa_rows`), K/V drop the `h_r` broadcast, and BlockInfo, the tile
grids, `tile_has_work`, the causal mask (`index_transform`) and the LSE/O guards work on packed rows.

- `h_r` divides 128: Q loads by TMA as before over the packed layout.
- Otherwise (e.g. 27B's `h_r=6`): the load warp in each CTA gathers its 128 packed rows with cp.async
  (`PackGQA.load_Q`), signalled to the leader MMA through a `PipelineAsyncUmma` whose producer group spans
  both CTAs (`cp.async.mbarrier.arrive` cannot reach the peer CTA's barrier). Q is committed after the K0
  TMA is issued so the gather overlaps it. The epilogue already has one thread per row, so O is written
  through per-row pointers. The interface uses this path only when `max_seqlen_q <= 128`: at longer
  queries tiles are full anyway and the gather measured 0.93-1.02x.

Packing only regroups Q rows into tiles; per-row math and KV order are unchanged, so packed and unpacked
outputs are bitwise identical. The unpacked path is behind `const_expr` branches (a few
`* qhead_per_kvhead_packgqa` factors are `* 1` when unpacked and fold away). Backward is unchanged.

Not in this PR: batched decode is still ~1.5x behind TRT-LLM. Profiling 27B 64x8k shows both kernels read
the same 2.15 GB, but FA4 spends 74% tensor-pipe time on 256-row MMAs holding 6 real rows, while
TRT-LLM's decode kernel swaps A/B (KV in M, 8 query rows in N) and reaches 86% of HBM bandwidth. That
needs a decode-specialized swap-AB kernel.

## Performance

GB200, Qwen3.5-27B attention layer (24 q / 4 kv heads, d=256, bf16), one decode token per sequence,
harness from the Qwen/TorchTitan generator: `varlen_attn_out` on a 128-token paged cache sized for 64k,
auto splits, CUDA-graph replay, L2 flushed. TRT-LLM is FlashInfer 0.6.13
`trtllm_batch_decode_with_kv_cache` (16-token pages). us per call, lower is better.

|---|---:|---:|---:|---:|
| 1 x 8k | 43.6 | 23.1 | 1.9x | 18.6 |
| 1 x 32k | 129.0 | 47.3 | 2.7x | 41.9 |

Qwen3.5-4B (16 q / 4 kv, TMA path): 16 x 32k 1539.7 -> 459.5 us (3.4x), 64 x 8k 1490.8 -> 529.5 us (2.8x).
Prefill is unchanged: dense `flash_attn_func`, profiler kernel time, 16/2 and 24/4 heads at 4k and 16k are
0.95-1.06x (h_r=6 prefill stays unpacked by the gate above).

Superseded by the stack #2920–#2927, which fixes this whole class of problem instead of patching the dedicated kernel: it runs the hdim-256 forward on the general SM100 kernel (FlashAttentionForwardSm100) and deletes sm100_hd256_2cta_fmha_forward.py (#2925). hdim 256 then gets PackGQA for any head ratio, SplitKV, paged/varlen scheduling, softcap, sinks, local windows, score_mod/mask_mod and block sparsity from the one kernel.

On GB200, Qwen3.5-27B decode (24 q / 4 kv) goes from 1210 to 181 us at 32x8k (this PR: 258 us; TRT-LLM: 162 us), and prefill is 4-28% faster than the dedicated kernel. The stack is based on #2817 (S/P ping-pong).
