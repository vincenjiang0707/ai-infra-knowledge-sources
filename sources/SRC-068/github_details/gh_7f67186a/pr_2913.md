# [PR #2913] [CuTe, SM100] Wait for TMEM allocation at a single aligned barrier site

state: open | updated: 2026-09-24T18:54:46Z

## 正文

## Problem

The SM100 kernels hand the TMEM pointer from the allocator warp to the other warp roles through the
`TmemPtr` named barrier. Each role calls `tmem.wait_for_alloc()` from its own branch, so the first round of
that barrier is joined by 2–3 different `bar.sync` instructions. The thread count adds up, but `bar.sync`
is `.aligned`: PTX requires every thread in a barrier round to execute the same instruction, so this is
undefined behavior. It works today because the hardware only counts arrivals.

`compute-sanitizer --tool=synccheck` flags it on B200 (`Barrier error detected. Divergent thread(s) in
block.`) at the per-role `wait_for_alloc()` lines, e.g. `flash_fwd_sm100.py:1323/1427`, and aborts the kernel.

## Fix

Hoist `tmem.allocate()` and a single `tmem.wait_for_alloc()` above the role dispatch, predicated on the
barrier's participant warps, and drop the per-role waits. `allocate()` already no-ops outside the allocator
warp, so calling it unconditionally keeps the column bookkeeping `free()` relies on. Applied to every kernel
with this pattern: `flash_fwd_sm100`, `flash_bwd_sm100`, `flash_fwd_mla_sm100`, `flash_bwd_mla_sm100`,
`flash_bwd_mla_dk_sm100`, `flash_bwd_mla_dq_dqv_sm100`. The hd256 2-CTA kernels already wait from one site.

## Testing (B200, cutlass-dsl 4.8.0, torch 2.14 cu130)

- synccheck, 14 configs (d64/96/128, causal, GQA, local, softcap, deterministic, DeepSeek 192/128, hd256,
  varlen, SplitKV, paged, paged+SplitKV), fwd+bwd: `main` flagged in 13/14 (hd256 clean), this PR in 0/14.
- synccheck on the MLA + hd256 tests (incl. sparse-MLA bwd) and all of `test_flash_attn_fast.py`: 0 barrier errors.
- pytest on a fixed 1723-ID stratified sample of `test_flash_attn.py`, `test_flash_attn_varlen.py`, and all of
  `test_flash_attn_fast.py`: identical per-test outcomes to `main` (1195 passed, 527 skipped). Two failures
  are pre-existing and identical on `main`: `test_mla_sink_precision_vs_fp64[128-256-True]`, and an illegal
  memory access in `test_flash_attn_mla_absorbed_varlen[0-True-True-False-False-random-1-4096-...]`.

Perf is unchanged: 5 interleaved rounds, median change of this PR vs `main` (negative = faster).
