## 正文

## Problem

The dedicated SM100 hd256 2CTA forward kernel asserted `not is_split_kv`, so every hd256 call ran with one
split. For batch-1 decode and short-chunk shapes, that launches only a few dozen CTAs on a 148/152-SM part.
The kernel then streams all of the KV through a small fraction of the GPU.

## Fix

- **Kernel** (`sm100_hd256_2cta_fmha_forward.py`): writes fp32 O and LSE partials with a leading split dim.
  `_flash_attn_fwd_combine` then merges them, the same path the generic SM100 kernel uses.
  - The static grid folds splits into grid y (`head * num_splits + split`). The varlen scheduler
    (`max_seqlen_q=None`) puts the split on grid y. Both CTAs of a cluster share y/z, so they always agree
    on the split.
  - All four warp roles call the same `decode_work_tile` / `get_kv_block_range` and use one skip predicate.
    `get_kv_block_range` wraps `BlockInfo.get_n_block_min_max` with the split.
  - With ceil-divided ranges and causal tiles, a split can own no KV blocks, and its count can be negative.
    Every role skips that tile, and softmax writes only LSE = -inf, which the combine ignores. The
    non-split path keeps its old behavior: a zero count still runs one fully masked iteration.
- **Heuristic** (`_get_fwd_config`): hd256 counts its real CTAs, `2 * b * h_q * ceil(sq / 256)`. The kernel
  never packs GQA and runs one 2CTA cluster per 256 Q rows. The old `b * h_kv * m_blocks` estimate
  over-split: for b1 sk4k it chose 16 splits, taking 57 us against a best of 34 us.
- **Guards:** a host assert keeps `num_heads * num_splits <= 65535`. SplitKV with the CLC scheduler (unused in
  this kernel) is rejected.
- **Tests:** enables `num_splits=3` for d=dv=256 in `test_flash_attn_output` / `test_flash_attn_varlen_output`.
  These tests are parametrized on `num_splits`:
  - `test_flash_attn_paged_hd256_sm100_tma`, now compared against an unsplit reference
  - `test_flash_attn_paged_hd256_sm100_tma_seqused_k`
  - `test_flash_attn_hd256_varlen_output_alignment`, including auto (`0`) and the varlen-scheduler
    `max_mode="none"` path

## Performance

Setup: GB300 (152 SMs), bf16, 16 Q heads, 8 KV heads, d=256. Timings are the public `flash_attn_func`
including the combine step, CUDA-graph replay median, in us (lower is better).

`num_splits=1` vs `main` (3 interleaved rounds): within ±0.2% on all 11 shapes, including prefill b2 s4k
causal and non-causal. Auto matches the best fixed split on every shape. It picks about 1 split for b >= 4,
where the GPU is already full.

## Testing (GB300, cutlass-dsl 4.6.2, tvm-ffi 0.1.12)

- All 6204 hd256 cases of `test_flash_attn_output` / `test_flash_attn_varlen_output`: 4692 passed, 1512
  skipped for unsupported features (local, softcap, learnable sink, deterministic). The cases were compiled
  with `FLASH_ATTENTION_FAKE_TENSOR=1 -n 48`, then run.
- `pytest tests/cute/test_flash_attn.py -k hd256`: the paged, paged + `seqused_k` and varlen-scheduler cases
  pass with splits. `test_flash_attn_hd256_varlen_output_alignment` fails identically on `main` in this env:
  tvm-ffi rejects the test's nonzero storage offset (`expected byte_offset=0`). With a zero-offset buffer, all
  170 `-k hd256` tests pass.
- Separate checks passed: causal with sq > sk, `num_splits` larger than the KV block count, and varlen with
  zero-length sequences combined with `seqused_k` and with/without `max_seqlen_q`.

## Known limitations

These are heuristic-only; correctness is unaffected.

- Varlen without a host `max_seqlen_q`: the heuristic sees `total_q`, so it under-splits.
- Paged KV: `max_seqlen_k` is the page-table width, so the heuristic can over-split when `seqused_k` is much
  smaller than that width.
