## 正文

**Stacked on the unchanged-upload PR (#20429); only the last commit is this PR. Overlaps #19418, see below.**

Since #18871 commands are submitted only at flush points (sync, readback, host write). For a run of launches such as one LLM decode step the host therefore encodes everything first and the GPU starts afterwards, so encode time and GPU time add up instead of overlapping. On the GPU clock a Llama-3.2-1B decode step showed 2.0 ms of idle time between kernels per 5.4 ms.

Submit the pending commands once `maxDispatchesPerFlush` (default 32) launches have been recorded since the last submission; 0 turns periodic submission off. The field name and default follow #19418, which proposes the same knob for UI responsiveness.

Two differences from #19418:

1. A periodic submission must not restart the uniform pool. Every launch between two flush points keeps its own pool buffer at a stable position, which the bind group cache and the unchanged-upload check rely on; calling `flushCommands()` there took uploads from 13.9k to 50.7k per 256-token generation. So this adds `submitPendingCommands()` (finish + submit, keep the pool position) and has `flushCommands()` restart the pool even when nothing is pending, since a periodic submission may already have sent everything and any later `writeBuffer` is ordered after it.
2. `maxDispatchesPerFlush <= 0` there means "flush after every dispatch"; here `0` turns periodic submission off (the conventional meaning of 0 for an interval) and "after every dispatch" is spelled `1`. Happy to align either way.

Interval sweep on top of the three PRs below (1B, paired): never 1.000, 8: 1.101, 16: 1.107, 32: 1.110, 64: 1.091; uploads unchanged at every interval; text identical. Alone on `main` the mechanism gives 1.18×; the whole stack 1.28× (206.8 → 257.1 tok/s).

One invariant found by an independent review and now pinned by a test: `sync()` must still await the queue after a periodic submission that followed a readback, because the readback is no longer the queue tail (`pendingGPUToCPUCopyIsQueueTail` is cleared by the submission).

Tests: submission every N launches (default > 0) and a flush point restarting the count, `0` disables and the field is read at every launch, pool positions survive periodic submissions so caches still hit, the pool restarts at a flush point even with nothing pending, sync after readback + periodic submission, destroy-after-submit ordering. lint/tsc clean; jest 42 passed.
