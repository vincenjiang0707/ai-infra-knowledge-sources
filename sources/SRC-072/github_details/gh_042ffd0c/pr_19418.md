# [PR #19418] [WebGPU] Fix UI jank caused by compositor starvation in batched dispatch

source: https://github.com/apache/tvm/pull/19418
state: open | updated: 2026-09-24T15:35:58Z
labels: 

## 正文

Batching all dispatches into a single command buffer (introduced in #18871) blocks the browser compositor from interleaving its rendering work, causing visible frame drops and laggy scrolling during LLM inference. This adds a `maxDispatchesPerFlush` field (default 32) to `WebGPUContext` that flushes the encoder periodically, giving the compositor regular breathing room while preserving most of the batching throughput gains. Setting it to 0 restores the old per-dispatch behavior. Fixes #19342

### JCNTH · 2026-09-24

Related: #20430 adds the same `maxDispatchesPerFlush` knob (same name and default of 32), measured for throughput rather than UI responsiveness. On Llama-3.2-1B decode in WebLLM the periodic submission alone is 1.18× (paired, 12 rounds), because the GPU starts on the first dispatches while the host is still encoding the rest.

Two things from that work that may be useful here:

1. The periodic submission should not go through `flushCommands()`, because that restarts the uniform buffer pool. Every launch between two flush points then no longer has a stable pool position, which is what lets a bind-group cache (#20428) and an unchanged-upload check (#20429) hit; with `flushCommands()` uploads went from 13.9k to 50.7k per 256-token generation. #20430 splits out a `submitPendingCommands()` that finishes and submits without restarting the pool, and has `flushCommands()` restart the pool even when nothing is pending.
2. `maxDispatchesPerFlush <= 0` here means "submit after every dispatch"; #20430 spells that as `1` and uses `0` for "off". Happy to align with whichever this PR settles on.

If this one lands first I will rebase #20430 onto it and reduce it to the pool-position fix.
