## Purpose

As requested in (the now-closed) #1107, this minimally adds `openai/mrcr`
as a long-context dataset option to the existing
inference performance evaluation path (`scripts/evaluate/evaluate.py`)
without introducing additional machinery.

MRCR measures speculative decoding acceptance and server performance on
long-context "needle in a haystack"-style prompts.

Because GuideLLM cannot replay a multi-turn conversation without
regenerating the intermediate assistant turns, each MRCR conversation is
**pre-rendered server-side** into a single-turn prompt: every row is sent
through the target server's root `/tokenize` endpoint (with the
conversation's `messages`, applying the server's chat template), then
`/detokenize`, yielding the exact prompt string the server would prefill
plus its token count. Rows are then rebucketed by rendered token count,
and each bucket runs through GuideLLM as a `/v1/completions` workload —
the fixed assistant turns are part of the prompt, so only the final
answer is generated.

The prompt rendering takes ~10 minutes for one needle count (800 prompts),
but the result is cached for subsequent benchmarks with the same target 
model. This initial wait is not ideal, but seems to be required if we want
to tap into the existing GuideLLM benchmark path.

New options (ignored for the standard dataset and SPEED-Bench, just as
`--subsets` is ignored for MRCR):

- `--mrcr-needles` — needle counts to test (default: `2,4,8`)
- `--mrcr-buckets` — context-length buckets, by number 1-8 or label
  (default: all buckets)
- `--mrcr-data-dir` — cache directory for rendered data
  (default: `./mrcr_data`; gitignored, reused across runs, keyed by
  served model)
- `--mrcr-max-samples` — row cap per bucket, for quick debugging runs

The eight buckets span 4,096–1,048,576 rendered tokens. Buckets above
the server's context limit are skipped with a warning. Each
(needle-count, bucket) pair runs as its own subset, labeled
`mrcr/<N>needle/<bucket>` in `acceptance.csv` (and `perf_results.csv`
in sweep mode). Invalid selections (bad needle counts, unknown buckets,
duplicates, max-samples < 1) are rejected at argparse time with
specific messages.

Rendered data is cached per model, so the one-time rendering cost
(~800 rows per needle count, parallelized over 24 workers) is only paid
on first use or when the served model changes.

## Tests

End-to-end against a vLLM server (vLLM 0.30.0, `Qwen/Qwen3.8-27B`,
262,144-token context):

```
vllm serve Qwen/Qwen3.8-27B \
        --speculative-config '{"model":"RedHatAI/Qwen3.8-27B-speculator.dspark","num_speculative_tokens":8,"method":"dspark"}' \
        --tensor-parallel-size 2
```

```
$SPECULATORS_DIR/.venv/bin/python \
     ./scripts/evaluate/evaluate.py \
     --target http://localhost:8000/v1 throughput \
     --dataset openai/mrcr \
     --mrcr-needles 2
```
