## Purpose

Speed up the Mooncake hidden-states backend by removing redundant host-side work on both ends:

- **One object per sample.** Tensor bytes (64-byte aligned) + a JSON manifest trailer are published with a single put instead of `put_tensor` × 2 + manifest put. Publication is atomic, so the "manifest written last" protocol and partial-sample cleanup go away.
- **Zero-copy transfers.** Each thread owns a staging buffer registered with Mooncake once. The producer copies DtoH straight into pinned staging on the connector's copy stream and calls `put_from`; the consumer calls `get_into`. This drops the per-sample pinned allocation, the `get_buffer` bounce buffer, and the GIL-held `new char[]` + memcpy inside `get_tensor`, and lets RDMA read/write registered memory directly.
- **Drop CRC32.** It cost two full CPU passes per sample (~144 ms each for a 587 MB K3 sample). #967 introduced it together with return-code checking; before #967 `setup`/`put_tensor` statuses were ignored, so a failed put could still publish the manifest. The issues caught during the K3 run are most plausibly from that path, since TCP and RDMA are already checksummed on the wire. Integrity now rests on checked status codes, the manifest shape/dtype/bounds checks, and the producer-side finite check. @fynnsu, can you confirm what the K3 run actually tripped on (checksum mismatch vs. non-finite vs. missing tensor)?
- **Check every status code.** `register_buffer`, `put_from`, `put`, `is_exist`, `get_size`, `get_into`, `remove`. Only negative values count as failures, because the size/length APIs return positive counts.
- **Backoff polling.** vLLM answers the HTTP request before the connector's put lands, so the consumer almost always slept one full 50 ms poll. Polling now starts at 1 ms and doubles up to the 50 ms cap.

The manifest version is bumped to 2, so producer and consumer must run the same version.

## Tests

Unit: `pytest tests/unit/hs_connectors tests/unit/train/test_data.py` (62 passed). The fake store now implements the pointer-based API and checks that transfers only touch registered memory. New cases cover negative statuses for every call, short reads, out-of-bounds manifests, staging reuse/growth, and the backoff schedule.

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `e1c12`

The new format and transfer path can improve performance, but mixed-version deployments cannot exchange samples, a failed buffer replacement can disrupt retries, and removing the checksum weakens detection of damaged training data. The available evidence does not establish a new remotely exploitable security path.

**Retained concerns**
- **Medium · architecture · inferred:** Version-1 and version-2 producers and consumers use different object keys and layouts. A mixed-version consumer cannot read the other format, and version-2 deletion does not reclaim version-1 tensor and manifest objects. The impact depends on deployment coordination and whether legacy objects remain.
- **Medium · reliability · observed:** If growing a cached staging buffer successfully unregisters it but registration of its replacement fails, a later retry can reuse the cached, now-unregistered pointer. This breaks the registered-memory precondition for both reads and writes.
- **Medium · reliability · inferred:** Removing the per-tensor CRC permits structurally valid, finite but altered tensor bytes to pass the remaining checks and reach training. This weakens detection of accidental or otherwise independently corrupted stored content; the former CRC did not authenticate content against a writer able to change the manifest too.

**Security Blast Radius**
- _inferred_ — A malformed or altered Mooncake sample can affect its requesting training-data consumer and its recovery attempts. The available source does not establish cross-tenant reachability, Mooncake writer privileges, or deployment-wide exposure.

**Security Findings and Attack Paths**
- _inferred_ — No new authenticated-writer bypass is established. CRC32 detected a mismatch between base-version tensor bytes and its manifest, but a writer able to replace both could recompute it. The head's remaining checks can likewise accept altered finite values that preserve the expected structure and tokens.

**Trust Boundaries and Controls**
- _observed_ — The connector derives the returned handle from a sanitized request ID and uses that key for publication; the training transfer reads and deletes by handle. Store authorization and key isolation are not defined in these paths.

**Resilience and Maintainability Implications**
- _inferred_ — A replacement-registration failure can make subsequent sample retries use an unregistered pointer; an unregister failure is logged while replacement proceeds. Both cases leave registration ownership uncertain on the failure path.

**Hardening Proposals**
- _proposed_ — Coordinate producer and consumer versions during rollout, and define how legacy objects are drained or removed before retiring version-1 cleanup.
- _proposed_ — Make staging-buffer replacement transactional or invalidate its cached entry immediately after successful unregister, so failed registration cannot leave an unregistered pointer reusable.
