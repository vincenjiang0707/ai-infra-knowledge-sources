## Problem

Speculator training data must be on-policy, but the current preparation pipeline mixes several responsibilities:

- loading raw source presets
- loading a local Hugging Face processor
- applying chat templates and tokenization locally
- rendering conversations through the serving endpoint
- accepting pre-tokenized rows
- normalizing conversations and tools
- retaining processor-specific message state
- producing visualization and review-only text

These overlapping paths duplicate logic and make the data contract difficult to explain. More importantly, accepting a raw source preset directly in preparation makes it possible to train on that dataset's assistant responses even though they were not generated by the target model.

The proposed invariant is:

> Every supervised token was generated by the target model. Rendering may encode an on-policy conversation, but it must never turn a source dataset's assistant response into a training target.

## Proposed pipeline

There are three supported inputs:

1. **Raw prompt preset**
   - Accepted by target response regeneration.
   - Existing assistant turns are discarded.
   - The target endpoint generates replacement responses and returns their token IDs.

2. **User-provided on-policy conversation**
   - Accepted by preparation through a local JSON/JSONL file or an explicit `hf:` dataset.
   - The target endpoint's render API applies the serving chat template and identifies assistant boundaries.
   - Rendering does not generate, replace, or validate response provenance; the user is responsible for providing on-policy conversations.

3. **Already prepared data**
   - Contains `input_ids` and `loss_mask`.
   - Skips endpoint rendering and is validated directly.

All paths converge on one internal contract:

```python
class PreparedSample(TypedDict):
    input_ids: list[int]
    loss_mask: list[int]
    messages: NotRequired[list[dict]]
```

One finalizer then validates mask shape and values, truncates, filters, and tensorizes the samples.

## Settled design choices in this prototype

### PreparedSample is the single internal boundary

Response regeneration, rendered conversations, and prepared input all produce the same representation before dataset construction. Optional `messages` exist only for downstream requests that genuinely require multimodal content.

### Conversation failures are reported and skipped

A malformed or unrenderable conversation does not abort an entire dataset. Prepared rows still fail validation for structural errors such as mismatched lengths or non-binary masks.

### Tool results are unsupervised environment observations

Source assistant tool calls are discarded and regenerated by the target model. Cached tool results may be paired with a compatible regenerated call so generation can continue, but tool results are never included in the supervised completion mask. Preparation only renders complete on-policy tool conversations and never executes tools.

### Multimodal remains a placeholder

The generic `messages` field, content adaptation, and downstream multimodal routing remain in the contract. The direct ShareGPT4V/COCO preset path is removed because it does not currently have a supported on-policy regeneration flow. A future focused PR can build that flow without reintroducing source assistant responses as targets.

### Per-assistant-turn fan-out is intentional

Some chat templates rewrite earlier history and therefore do not have a stable append-only boundary. In that case, preparation emits one sample per assistant turn so each target span has a defensible render boundary.

## What the proof of concept removes

- `prepare_data.py --model` and `--trust-remote-code`
- local `AutoProcessor` loading and tokenizer setup during preparation
- processor objects from the preparation API
- duplicate conversation normalization and tool-schema parsing
- review-only detokenized `text` in regeneration output
- local preprocessing visualization and detokenization machinery
- `logging_utils.py` and `torch_utils.py`
- direct raw-preset preparation and its off-policy examples/tests
- the unsupported direct ShareGPT4V/COCO preset path

Relative to #794, the refactor is **610 additions / 1,330 deletions**, a net reduction of **720 lines**, including tests and documentation.

## User-facing migration

- Raw presets such as `sharegpt`, `gsm8k`, and `hermes-fc` must go through response regeneration first.
- User-provided natural-language data must already be on-policy and requires `--render-endpoint`.
- Prepared `input_ids` / `loss_mask` data requires no endpoint.
- Training still loads the verifier tokenizer when it needs model metadata such as `mask_token_id`; only data preparation stops loading a local model processor.



## RFC question for maintainers

If this end state is directionally correct, how should the fresh implementation be divided into reviewable PRs?

One possible sequence is:

1. establish the shared `PreparedSample` contract and finalizer on top of #794
2. share conversation normalization and strict tool parsing
3. make preparation accept only on-policy conversations or prepared rows
4. integrate response regeneration, including cached tool observations
5. remove obsolete processor, visualization, logging, and compatibility paths; migrate docs and examples
6. add true on-policy multimodal source regeneration in a later focused PR
7. integrate into `speculator-cli`

This PR contains (2-5)

The sequence is illustrative; maintainer feedback on dependencies and review boundaries is the purpose of this RFC.
