# [PR #1071] fix(training): Fix regression on DFlash/DFlash2/DSpark: --max-anchors is now per packed document, not per packed sequence

source: https://github.com/vllm-project/speculators/pull/1071
state: open | updated: 2026-09-22T15:50:47Z
labels: documentation

## 正文

## Summary

`--max-anchors` now means anchors **per packed document** instead of per packed sequence. This is the contract `num_anchors` has in SpecForge and TorchSpec, which sample `[B, num_anchors]` with one conversation per row. It applies to DFlash, DFlash2 and DSpark, which share the one `select_anchors` call in `DFlashDraftModel._backbone_forward`. P-EAGLE is untouched.

## Why

Speculators packs several conversations into one `total_seq_len` row. `select_anchors` drew `min(max_anchors, valid)` positions across the whole row and ignored `document_ids`, so the 512 default copied from the reference trainers in #995 gave 2-8x fewer anchors per token than those trainers, and short conversations were starved: one with 187 supervised tokens got about 28 anchors here versus all 187 in SpecForge.

On the tutorial dataset (`windchimeran/speculator-tutorial:tutorial_regen`, mean 3046 tokens, 54% supervised) packed to 8192, per-row 512 covered 14.7% of supervised tokens; per-document 512 covers 30.8%.

## How it works

- Every document in the row gets exactly `max_anchors` slots, filled with a uniform sample of its supervised positions and padded with `anchor_valid == False` when it has fewer (`select_anchors`, `models/dflash/utils.py`). Short documents are fully covered, long ones capped.
- Query length is `num_documents * max_anchors * block_size`, so it depends only on the document count. The family forwards and the block-mask builder compile with `dynamic=False`, giving one static compile per document count. Counts above 8 round up to a power of two, bounding the total at 18 variants.
- Nothing in the compiled forward has a data-dependent shape, so the recompile limits cannot be reached by data. Hitting one means a bug, and dynamo's default reaction (silently running eager) would surface later as an OOM on this memory-heavy path, so `fail_on_recompile_limit_hit` makes it fail immediately instead.
- DSpark derives `num_blocks` from the sampled tensor rather than the flag; its stale 3072 fallback default becomes 512, matching the schema.

## Pitfalls

- **512 is now per document, not per row.** If you tuned `--max-anchors` as a per-row budget, divide it by your typical documents per row. Example recipes move from 3072 to the reference default 512; the Kimi K3 recipe from 1024 to 512.
- **Memory and step time scale with documents per row**, the way they scale with batch size in the reference trainers. Budget from the end-to-end numbers above, not the activation-only microbenchmark.
- **Published results measured under the old semantics shift when rerun**, including the tutorial in #1036.
- **Recipes may now be one epoch too long.** More supervision per step converges faster, so `checkpoint_best` moved from epoch 4 to epoch 3 on the 5-epoch tutorial recipe.

### fynnsu · 2026-09-02

I'm not sold on this change. This will significantly increase the number of padded/non-valid tokens we compute, and although the pr may cap the number of forward compilations, this will still increase it significantly and add another source of failure / slowdown.

We also introduce new rank divergence with this change, and some different ranks will now have batches of varying sizes, which the current reduction logic doesn't account for (not a big deal, mostly affects logged metric correctness but still). 

I also believe the ablation improvement can largely be explained by the increase in average anchors per batch that the pr branch sees. It is being trained on strictly more data and also in turn seeing additional runtime/hardward usage consistent with this. Likely training the main branch with a slightly higher `max-anchors` to match the average `max-anchors` of the pr, would yield a similar result.
