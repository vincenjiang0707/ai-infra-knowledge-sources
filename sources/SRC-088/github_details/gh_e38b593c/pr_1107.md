## 正文

## Summary

Adds a **`long-context`** evaluation mode that measures speculative-decoding acceptance as context length grows, using [OpenAI's MRCR dataset](https://huggingface.co/datasets/openai/mrcr) as a source of long, multi-turn prompts.

The design principle: **a benchmark is just a set of requests to make (in some order, with an optional stop rule); everything is recorded to a table, and reports are pure functions over that table.** So the pieces are decoupled into three layers, none of which is MRCR-specific except the last:

1. **`request_runner.py` — generic runner.** Given an ordered set of requests (chat messages + sampling budget + opaque `metadata`) and an optional per-batch stop predicate, it renders each request through the server's own render endpoint (exact prompt length + context fit-test), generates whatever fits, and streams one flat row per request to a **Parquet table**: request identity, metadata, exact prompt length, response text, and the *raw* server metrics blob — all verbatim. It knows nothing about bins, context length, or spec-decode. Each batch is a separate Parquet part file, so a crash only loses the batch in flight.
2. **`acceptance_report.py` — spec-decode analysis over the table.** Context-length bucket edges live here as *analysis parameters*, not harness constants. Reports acceptance (a) by prompt length at request start and (b) by running token position within each request.
3. **`mrcr.py` — thin MRCR adapter.** Loads the dataset and turns it into a deterministically-selected, length-ordered request set.

Because the raw table is the source of truth, reports can be re-sliced with different bin edges and **no server** via `rebin.py`, and plotted with `plot.py acceptance`.

Correctness is intentionally not graded — MRCR is used only for its long prompts.

### Deterministic superset selection

Records are stratified into MRCR's native power-of-2 token bins and, within each bin, ranked by a stable content hash (`sha256(seed + prompt)`); the lowest-ranked `--samples-per-bin` per bin form the candidate set. Bin assignment uses `n_chars / 4.9` (MRCR carries no token count; the ratio is 4.9 ± 0.1 across the whole dataset, validated offline against o200k) — zero runtime cost, no `tiktoken` dependency. The candidate set is independent of `max_model_len`; the only context-dependent step is the render fit-test, which is monotonic, so `Kept(ctx1) ⊆ Kept(ctx2)` for `ctx1 ≤ ctx2`. Batches run smallest-first and stop once a whole bin renders oversized.

### CLI

```bash
# Server must expose the render endpoint and per-request detailed metrics:
VLLM_ENABLE_SCALE_OUT_ENDPOINTS=1 vllm serve <model> \
    --per-request-spec-decode-metrics detailed \
    --speculative-config '{"model":"<draft>","num_speculative_tokens":N}'

python evaluate.py --target http://localhost:8000/v1 long-context --samples-per-bin 20

# Re-slice results offline with different bins (no server):
python rebin.py --table <out>/raw_table --context-bin-edges 0,8192,32768,131072

# Plot the acceptance figure offline (no server):
python plot.py acceptance --table <out>/raw_table --output <out>/acceptance.png
```

New flags (long-context only): `--samples-per-bin`, `--selection-seed`, `--position-bin-size`. `throughput`/`sweep` are unchanged and don't import the long-context deps.

### Visualization

`plot.py` gains an **`acceptance`** subcommand that renders the recorded table into one figure — another pure slicing of the same source of truth as the CSVs, so it needs no server:

![Long-context acceptance plot](https://raw.githubusercontent.com/reed-meyerson/speculators/pr-assets/acceptance_example.png)

Three panels share one context-length x-axis (example: Qwen3-8B + a DFlash speculator, 7 speculative tokens, MRCR 2-needle):

- **Mean accept len** (line) — mean committed tokens per verify step in each context bin; the headline trend.
- **Tokens generated** (bars) — committed tokens per bin, i.e. how much data backs each column. Deliberately *decoupled* from acceptance (a step-count bar would inflate low-acceptance bins), so it reads cleanly as sample size.
- **Acceptance-length distribution** (heatmap) — within each context bin, the share of verify **steps** that committed exactly *k* tokens (each column sums to ~100%). The integer in a cell is just the precise readout of its color.

The x-axis is the *running* context length at each verify step (prompt length + everything committed so far), not per-request — so it stays meaningful even when generation is long relative to the bin width. Bins default to ~2 log2 bins per octave and can be overridden with `--context-bin-edges`.

Reading the example: acceptance degrades monotonically as context grows — mean length falls 2.73 → 1.68 tokens/step from ~4k to ~26k, and the share of single-token steps climbs 28% → 52%.

### Dependencies

Long-context mode adds `pandas`, `pyarrow`, `huggingface_hub` (dataset loading + Parquet table); requests go straight to the target server's HTTP API, so there's no separate eval harness. Plotting reuses the existing `matplotlib`/`numpy` deps — nothing new.

### Validation

Ran end-to-end against Qwen3-8B + a DFlash speculator at `--max-model-len 40960`: deterministic bounded selection with the bin early-stop firing, a Parquet table written (one part file per bin), both acceptance reports produced, detailed per-step metrics flowing through, `rebin.py` reproducing the reports offline with different bin edges, and `plot.py acceptance` rendering the figure above from the recorded table. Recording is small — a full MRCR run is single-digit MB (the raw prompts are *not* stored, only a reference; the per-step arrays are bounded by the generation cap, not the context length).

### Note

Supersedes #1064 — this replaces the earlier Inspect-AI-based MRCR mode with the recorded-table architecture. Opening fresh rather than force-pushing that branch so the two approaches can be compared. Draft while I gather more validation.

The example image is hosted on the fork's `pr-assets` branch (kept out of this PR's diff), since `gh` can't upload to GitHub's attachment CDN directly.

### reed-meyerson · 2026-09-11

Thanks for the careful repro. This was a real bug, and your two-case (clean control + failing reuse) framing made it easy to confirm. Fixed in `7a86e76`.

On the design question: rather than rejecting a nonempty directory or allocating a unique one, `run_requests` now clears stale `part-*.parquet` files at the start of a run:

```python
table_dir.mkdir(parents=True, exist_ok=True)
for stale in table_dir.glob("part-*.parquet"):
    stale.unlink()
```

The reasoning is consistency with the rest of the harness rather than a new isolation policy. The default output directory is already timestamped and unique per run (`evaluate.py`), so reusing one is an explicit choice; and when a directory *is* reused, the derived CSV reports in it already replace rather than append (a sibling fix in the same commit). The raw table silently merging runs was the odd one out, and clearing stale parts makes the table authoritative for the current run, matching the reports written alongside it. No benchmark in these scripts does resume or checkpointing (runs re-execute wholesale), so there's nothing a part/manifest policy would serve. Your exact reproduction is now a regression check (asserts a shorter rerun yields only the new rows).
