## 正文

## What was wrong

`SteeredModel.clamp()` in `lm_eval/models/hf_steered.py` crashes whenever a `clamp`-action steering vector targets a specific attention head (`head_index` set) -- the per-head steering feature added in #3279.

The `head_index is not None` branch contained a leftover/incorrect debug assertion:

```python
x = acts[:, :, head_index, :]
proj = (x * direction).sum(dim=-1, keepdim=True)
assert proj == acts @ direction
```

`acts` has shape `[batch, pos, heads, features]` and `direction` has shape `[features]`. `proj` is the projection of the *single selected head*, shape `[batch, pos, 1]`. But `acts @ direction` is a matmul over the *whole* tensor -- every head -- shape `[batch, pos, heads]`. The two are neither the same shape nor the same quantity. Comparing them with `==` broadcasts to `[batch, pos, heads]`, and `assert` then calls `bool()` on that multi-element tensor, raising:

```
RuntimeError: Boolean value of Tensor with more than one element is ambiguous
```

(Newer PyTorch phrases it "...with more than one value is ambiguous".)

This is not a valid invariant even mathematically -- the two sides only coincide when the broadcast collapses to a single element (`heads == pos == batch == 1`). There is no equivalent check in `add()` or in the `head_index is None` branch, confirming it is spurious debug code.

## Trigger

Run `lm_eval --model steered` with a `steer_path` whose config has a hookpoint entry with `"action": "clamp"` and a non-None `"head_index"` (the documented dict schema in `SteeredModel.__init__`, and exactly what #3279 added the feature for). On the first forward pass the registered hook calls `clamp(...)` and hits the assert; for any layer with more than one attention head (i.e. essentially all real transformer layers) or batch/seq-len > 1, the run aborts before any scoring.

## Fix

Remove the spurious assertion. The surrounding per-head clamp logic is already correct.

## Evidence

RED (current code), calling the real `clamp()` classmethod with `acts` of shape `[2, 5, 8, 16]`, a unit `direction` `[16]`, and `head_index=2`:

```
proj.shape          = (2, 5, 1)     # correct, per selected head
acts @ direction    = (2, 5, 8)     # all heads -- wrong quantity
RuntimeError: Boolean value of Tensor with more than one value is ambiguous
```

GREEN (after removing the assert), same input:

```
returned shape                     = (2, 5, 8, 16)
selected-head matches formula      = True
selected-head projection == value  = True   # clamp target reached
other heads untouched              = True
```

`ruff format --check` reports the file already formatted; the change touches a single line and adds no new lint findings.

### chrikrah · 2026-09-26 · COMMENTED

Correct. Reproduced at the merge base `d6de816`. The argument that settles the "did that line do anything" question sits below.

The crash fires on more inputs than the body claims. `clamp` is a classmethod over pure tensors, so it needs no weights:

```
A specific head   acts[2,5,8,16] head_index=2     RuntimeError: Boolean value of Tensor with more than one value is ambiguous
B whole layer     acts[2,5,16]   head_index=None   OK
C whole layer 4D  acts[2,5,8,16] head_index=None   OK
D degenerate      acts[1,1,1,16] head_index=0      OK
E ONE head, b*p>1 acts[2,5,1,16] head_index=0      RuntimeError: ... ambiguous
F head + bias     acts[2,5,8,16] head_index=2      RuntimeError: ... ambiguous
```

Case E matters for the body. A *single*-head layer crashes too, once batch times positions exceeds 1. Only the fully degenerate `[1,1,1,F]` call survives. At head, A, E and F all return `OK ... clamp_target_reached=True other_heads_bit_identical=True`.

**The line was never load-bearing.** Only two commits touch that text:

```
$ git log --oneline -S 'assert proj == acts @ direction' --all -- lm_eval/models/hf_steered.py
0ca8a51 Fix crash in SteeredModel.clamp when steering a specific attention head
a46180b Add support for steering specific attention heads (#3279)
```

It arrived inside the new `if head_index is not None:` block in #3279. It has never sat on the whole-layer path, which is a separate `else`.

**And the deletion cannot change a value. CPython already proves that.** An `assert` with a pure read on the right alters nothing, and `-O` strips asserts. Base under `python -O` is byte-identical to head on all six cases:

```
BASE d6de816 under python -O        HEAD 0ca8a51
A: 111.78613690804923               A: 111.78613690804923
C: 597.1177037695888                C: 597.1177037695888
F: 107.63391698896885               F: 107.63391698896885
```

B, C and D are bit-identical between plain base and head too.

One point for a maintainer to choose on, rather than a blanket delete. The invariant was nearly valid. It indexed the wrong side:

```
deleted LHS  proj              shape (2, 5, 1)
deleted RHS  acts @ direction  shape (2, 5, 8)
intended     proj.squeeze(-1) == (acts @ direction)[:, :, 2]  ->  True
```

So #3279 meant the selected column.

The gap: no test. `tests/models/test_hf_steered.py:16` is `pytest.skip("dependency conflict on CI", allow_module_level=True)`, giving `1 skipped`, and it covers neither `clamp` nor `head_index`. So CI never could have caught this, and it cannot catch a regression. `clamp` needs no model, so a case in a file that runs is cheap.

`ruff check` reports the same 2 pre-existing errors at base and head; `ruff format --check` is clean.
