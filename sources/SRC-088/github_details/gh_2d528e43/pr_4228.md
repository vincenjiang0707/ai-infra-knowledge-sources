# [PR #4228] Fix mbpp_plus_instruct: grade against MBPP+ test suite instead of leaked prompt assertion

## 正文

Fixes #4212

## Problem
`mbpp_plus_instruct.yaml` set `doc_to_target` to `{{test_list[0]}}` — the exact same single assertion that `doc_to_text` shows the model in the prompt. This meant a model could score a perfect `pass@1` just by returning a value that satisfies that one assertion, without ever being checked against the real MBPP+ test suite (the dataset's `test` field, which was never referenced anywhere in this config).

Diagnosed by @shaurya416 in #4212.

## Fix
- `doc_to_target`: `{{test_list[0]}}` → `{{test}}` (the full EvalPlus-expanded test suite)
- `doc_to_text`: removed the `"Your code should satisfy the following assertion:\n{{test_list[0]}}"` clause, since showing it to the model was the source of the leak

The grading mechanism itself (`code_eval` / `pass_at_1`) is unchanged — this is purely a data-wiring fix.

## Verification
Using `evalplus/mbppplus`, `mbpp_plus_instruct`, task_id 2 (`similar_elements, at row index 0`):

| Candidate | Target | pass@1 |
|---|---|---|
| Correct reference solution | Old (`test_list[0]`) | 1.0 |
| Correct reference solution | **Fixed (`test`)** | 1.0 |
| Constant-returning cheat (hardcodes the value needed to satisfy only `test_list[0]`) | Old (`test_list[0]`) | **1.0** ❌ |
| Constant-returning cheat | **Fixed (`test`)** | **0.0** ✅ |

This confirms both that the exploit existed before this fix, and that it's closed after it, while a genuinely correct solution is unaffected.

## Environment notes for reviewers
- `code_eval` doesn't run on native Windows at all (`evaluate`'s own check). Verification above was done in WSL.
- On Python 3.14, `code_eval`'s sandbox needs the `fork` multiprocessing start method explicitly (`multiprocessing.set_start_method("fork", force=True)`) — Python 3.14 changed the POSIX default to `forkserver`, which breaks `numpy` imports inside the sandbox's `reliability_guard()`. This is a local verification-environment note only, not a code change.

### shaurya416 · 2026-09-25

Thanks for working on this. One correction that comes from the issue's suggested fix, which I wrote and which was incomplete: removing the assertion clause from `doc_to_text` also removes the only place the prompt names the function that the tests call.

Checked on `evalplus/mbppplus` (test split, 378 rows):

- The function that the `test` text calls is named in `test_list[0]` in all 378 rows. The `prompt` field does not give it as a signature. The name occurs in it in 12 rows (13 by substring), and in those it is a common word that appears in the sentence, for example `sum`, `count` or `split`.
- Running the dataset's own `test` text with the function renamed in the reference solution fails for all 378 rows (`NameError` in 377, `TypeError` in one where the name shadows a builtin). With the original name, the reference solutions for tasks 2, 3 and 4 pass.
- `code_eval` runs the candidate followed by the `test` text, `build_predictions` only extracts the code block, and the task sets `num_fewshot: 0`, so nothing else supplies the name. After this change a correct answer passes only if the model happens to choose the same function name as the dataset.
- EvalPlus builds its MBPP+ prompts the other way: in the v0.2.0 release every one of the 378 prompts is the task text plus one assert, that assert is the dataset's `test_list[0]` in all 378, and the entry point appears in all 378 prompts.

Suggested change: keep `doc_to_text` as it was, and change only `doc_to_target` to `{{test}}`. That still closes the original leak: a constant answer that satisfies only `test_list[0]` passes that assertion and fails the full suite (checked for tasks 2, 3 and 4, where the reference solutions pass the full suite), and the prompt keeps naming the function.

Not run: an end-to-end lm-eval run with a real model.

### chrikrah · 2026-09-26 · COMMENTED

Correct, and it does more than the body claims. Two things to add, one a benefit you have not claimed.

**The old target was itself ungradeable on four rows. So this raises a ceiling, and does not only close a leak.** All 378 reference solutions, run against each target:

```
OLD  doc_to_target: {{test_list[0]}}
  pass@1 of the dataset's own reference solutions = 374/378 = 0.9894
  failing task_ids: [98, 124, 137, 300]
    task_id=98: NameError: name 'math' is not defined
NEW  doc_to_target: {{test}}
  pass@1 = 378/378 = 1.0000
```

Those rows use `math.isclose`. The dataset carries `test_imports: ['import math']`, and lm-eval never applies it:

```
task_id=98  test_list[0] : assert math.isclose(multiply_num((8, 2, 3, -1, 7)), -67.2, rel_tol=0.001)
            test_imports : ['import math']
            `test` uses 'math.' : False
```

So `mbpp_plus_instruct` pass@1 was capped at 0.98942 for every model.

Direction and size of the move:

```
rows passing OLD but failing NEW: 0
rows failing OLD but passing NEW: 4   [98, 124, 137, 300]
```

No correct answer gets harder. The ceiling rises by at most 1.06 points. And any published number falls as far as a model exploited the single leaked assertion:

```
constant cheat vs OLD -> PASS
constant cheat vs NEW -> FAIL  AssertionError: out: {4, 5}, exp: {3, 4}
```

The field itself is safe. `test` is present and non-empty on all 378 rows. It is a self-contained program, it names its own entry point, and it defines an `assertion(out, exp, atol)` helper with float tolerance.

On strictness: 34.6x more cases in total, mean 3.10 against 107.40, and no row has fewer. **Not a literal superset, though.** 353 of 374 rows begin with the exact MBPP inputs. EvalPlus re-normalised the other 21, for instance task 140, where a tuple-of-tuples became a list-of-lists. "Strictly harder" is right and "superset" is not, so the merge commit should avoid the word.

**The sibling task has the same defect and this does not touch it.** Resolving the `include:` chain with the harness loader at the merge base:

```
mbpp_plus           dataset evalplus/mbppplus  num_fewshot 3  doc_to_target {{test_list[0]}}\n{{test_list[1]}}\n{{test_list[2]}}
mbpp_plus_instruct  dataset evalplus/mbppplus  num_fewshot 0  doc_to_target {{test_list[0]}}
```

`mbpp_plus` loads the EvalPlus dataset and grades against base MBPP assertions inherited from `mbpp.yaml`. It keeps the `math.isclose` ungradeability too. After this merges, two tasks named "plus" on one dataset measure different things.
