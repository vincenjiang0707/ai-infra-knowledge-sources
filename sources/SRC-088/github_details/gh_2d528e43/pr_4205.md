## 正文

## What

Fixes the issue in #2552: a model answer that uses display-math formatting — e.g. `Thus the answer is \[ \boxed{42} \]` — is currently scored as wrong because `process_results` only considers content between the first and last `$` delimiters and otherwise falls back to the raw generation string.

This PR adds a lenient extractor and reports it as a second, additive metric, `flexible_match`, alongside the unchanged `exact_match`. With it, the issue's example scores `{exact_match: 0, flexible_match: 1}` instead of a flat 0.

## Why additive

`exact_match` keeps its historical behavior byte-for-byte, so existing runs remain comparable and nothing regresses. The lenient path is exposed as a new metric instead, mirroring how GSM8K already reports both `strict-match` and `flexible-extract` filters. This complements #3741 rather than duplicating it: #3741 changes the single metric's extraction; this PR adds a second metric beside the intact one.

## Changes

- `lm_eval/tasks/hendrycks_math/utils.py`: `process_results` now returns `{"exact_match": ..., "flexible_match": ...}`. The flexible extractor tries, in order:
  1. the content of the last `\boxed{...}` / `\fbox{...}` block anywhere in the generation (inline math, display math, or no math delimiters at all);
  2. the content between the first and last `$` delimiters;
  3. the last number-like token in the generation;
  4. the full generation as a last resort.
- `hendrycks_math_algebra.yaml`: `flexible_match` added to `metric_list` (mean, higher is better); metadata `version` bumped 1.0 → 2.0. All seven sub-tasks inherit via `include` (including `hendrycks_math500`).
- `hendrycks_math.yaml` (group): `flexible_match` added to `aggregate_metric_list` (mean, weight by size) so the group summary reports it too.
- `tests/test_tasks_hendrycks_math.py`: 19 parametrized unit tests covering the extractor priority chain, the unchanged strict behavior (regression guard), and end-to-end metric output for the issue's example.
