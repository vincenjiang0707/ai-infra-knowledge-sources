# [PR #4209] Fix escaped_split: treat separator literally, return list for maxsplit=0

## 正文

## What was wrong

`escaped_split()` in `lm_eval/utils.py` documents `sep_char` as a single separation character, but interpolated it directly into a regex. Regex metacharacters were therefore interpreted as syntax: `escaped_split("a.b.c", ".")` returned `['', '', '', '', '', '']` instead of `["a", "b", "c"]`, and `*` as a separator could raise `re.error`. Separately, `maxsplit=0` returned a bare string rather than a list, contradicting the documented 'split into a list' contract.

## What the fix does

- Escape `sep_char` with `re.escape()` before interpolating it into the negative-lookbehind pattern, so separators are always treated literally.
- `maxsplit=0` now returns `[text]` (one-element list) instead of `text`.
- Adds `TestEscapedSplit` regression tests in `tests/test_utils.py` covering regex metacharacter separators (`.`, `|`, `*`, `+`, `?`), zero splits, escaped separators, positive `maxsplit`, and the original colon-delimited task-path use case.

Fixes #4095

## Test evidence

Ran the 5 new `TestEscapedSplit` tests against the fixed code: **5 passed**. Ran the same tests against pre-fix `upstream/main` code: the metacharacter and zero-split tests fail (2 failed, 3 passed), confirming the tests capture the reported bug. (Full `tests/test_utils.py` requires torch, which could not be installed in this environment; the `escaped_split` tests were run standalone against the repo's actual `lm_eval/utils.py`.)
