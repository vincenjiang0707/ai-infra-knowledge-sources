# [PR #4210] fix(utils): keep per-request timeout across RemoteTokenizer retries

## 正文

Fixes #4201.

## Problem

`RemoteTokenizer._request_with_retries()` resolved its timeout with `kwargs.pop("timeout", self.timeout)` **inside** the retry loop:

```python
for _ in range(self.max_retries):
    resp = self.session.request(
        method, url,
        timeout=kwargs.pop("timeout", self.timeout),
        ...
    )
```

`pop()` removes the key on the first evaluation, so a caller-supplied override only applies to the first attempt. Every retry of the *same* logical request silently falls back to `self.timeout`, which can lengthen a request that asked for a short timeout — or shorten one that asked for a long timeout.

Reproducing the issue's snippet on current `main`:

```
timeouts = [7, 30, 30]   # expected [7, 7, 7]
```

## Fix

Resolve the timeout once, before the loop, and reuse it for every attempt. No behaviour change for callers that don't pass an override — the default path was already correct — and no change to the retry count or exception handling.

## Tests

Two regression tests in `tests/test_utils.py`, using a session stub that records the `timeout` of each attempt and fails the first two:

- `test_remote_tokenizer_keeps_explicit_timeout_across_retries` — asserts `[7, 7, 7]` for an explicit override.
- `test_remote_tokenizer_uses_default_timeout_across_retries` — asserts `[30, 30, 30]` for the default, so the fix can't regress the existing path.

Both fail on `main` (the first with `assert [7, 30, 30] == [7, 7, 7]`) and pass with the change applied.

```
python -m pytest tests/test_utils.py tests/test_requests_caching.py tests/models/test_api.py -q
# 82 passed
```
