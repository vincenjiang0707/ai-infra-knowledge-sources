## 正文

Fixes #4187.

The current get_response chain returns the whole first line, so generations such as B. 4 and Answer: B do not match the one-letter MMLU target. This switches the generative MMLU config to the existing multi-choice filter and keeps the last answer-letter match.

Added a regression test that loads the actual MMLU generative filter configuration and covers bare letters, letters followed by option text, and common answer prefixes.

Validation:

**One regression worth handling before merge: lowercase letters are no longer extracted at all.**

| raw response | current chain | this PR |
|---|---|---|
| `d` | `d` ✓ (metric ignores case) | **`[invalid]` ✗** |
| `b. 4` | `b. 4` ✗ | **`[invalid]` ✗** |

Cause, from the installed tree: `MultiChoiceRegexFilter.__init__` compiles the supplied pattern verbatim — `self.regex = re.compile(regex_pattern)` (`lm_eval/filters/extraction.py:35`) — while `ignore_case` is documented as *"Ignore case during step 1 matching"*, i.e. it applies to the filter's internal choice-matching, not to `regex_pattern`. With `\b([A-D])\b`, lowercase replies never match, and a bare lowercase answer (`d`) goes from **correct** to **wrong**.

One-line fix: `regex_pattern: "(?i)\\b([A-D])\\b"` (or `[A-Da-d]`).

Evidence, the full failure-class write-up and a dependency-free checker for silent zeros: https://github.com/laa1991/silent-zero — happy to re-run this table on an updated revision.

### laa1991 · 2026-09-19

Thanks for the update — `4d57007` fixes the lowercase case, confirmed on my side (`d` → `d`, and the metric's `ignore_case` takes it from there). I re-ran the same 16-row table against the new head pattern and found that **my suggestion is not free either** — reporting it here because it is the same class of failure this PR is about.

Pattern `\b([A-D])\b` vs the adopted `(?i)\b([A-D])\b`, same rows, `group_select: -1`:

| raw response | old pattern | `(?i)` (head `4d57007`) |
|---|---|---|
| `d` | `[invalid]` ✗ | `d` ✓ |
| `b. 4` | `[invalid]` ✗ | `b` ✓ |
| **`The answer is B because a car moves.`** | `B` ✓ | **`a` ✗** |
| **`I would pick B — a safe choice.`** | `B` ✓ | **`a` ✗** |

Totals on my table: 13 wrong → 1 wrong (before), 13 → **2** wrong (after). The two new misses are the same mechanism: case-insensitivity lets the standalone article **`a`** into the match pool, and `group_select: -1` then picks it over the real answer.

Direction I'd suggest (not a patch, just the shape): make the match **answer-anchored** rather than position-anchored, e.g. first try an indicator-then-letter pattern

```yaml
- function: "regex"
  regex_pattern: "(?i)(?:answer|choice|option|select)\\s*[:：]?\\s*\\(?([A-D])\\)?"
  group_select: -1
```

and only fall back to a bare letter when the response *is* essentially a letter (`^\s*\(?([A-Da-d])\)?[.)]?\s*$`). That keeps `d` / `b. 4` / `Answer: B` working while making `…because a car moves` unable to win the last-match race.

Two caveats on my side, so the numbers aren't over-read: this table is a hand-written adversarial set (n=16), not a benchmark — `The answer is B because a car moves.` is my own construction, chosen to probe the last-match rule. I have not measured how often that shape occurs in the wild. If useful I'm happy to run the same table over a real generative-MLU sample set and report the distribution of extracted answers instead of 16 hand-picked rows.

### laa1991 · 2026-09-19

**Retraction — my `(?i)` suggestion is worse on real data, please revert it before merging.**

I said earlier that case-insensitivity was needed because a bare `d` was no longer extracted. That was measured on a hand-written 16-row table, and the cure is worse than the disease on real responses. Here is the measurement, run through the *same* code path the task uses (`MultiChoiceRegexFilter`, `group_select: -1`, `ignore_case: true`, scored with the task's `exact_match` + `ignore_case` + `ignore_punctuation`):

**Corpus:** 600 real generative-MMLU responses from our own runs — 2 models (`deepseek-flash`, `deepseek-v4-pro`) × 10 subjects × 30 items, i.e. the exact generations recorded by the harness (`resps[0]`), scored against `target`.

| extraction | correct / 600 |
|---|---|
| current release (first-line chain) | **0** |
| **`\b([A-D])\b` (this PR as originally written)** | **486** |
| `(?i)\b([A-D])\b` (my suggestion, current head `4d57007`) | **439** |
| start-anchored `(?m)^[\s*_`>\-]*\(?([A-D])\)?[.):]` | 465 |
| indicator-anchored `(?i)(?:answer\|choice\|option\|select)\s*(?:is\|:)?\s*\(?([A-D])\b` | 241 |

Relative to the original pattern, the case-insensitive version changes the extracted value on 76 rows: **49 correct → wrong, 2 wrong → correct.**

**Mechanism.** `group_select: -1` takes the **last** match, and case-insensitivity lets standalone lowercase letters into the match pool. **546 of the 600 responses contain a standalone single-letter word** (overwhelmingly the English article "a"), while **only 1 of 600 is a bare letter**. So the flag massively over-trades: it fixes one shape that barely occurs in real generations and breaks a shape that occurs in 91% of them. Examples of the damage:

| raw response (truncated) | `\b([A-D])\b` | `(?i)\b([A-D])\b` | gold |
|---|---|---|---|
| `C. most organic functional groups absorb in a characteristic region of…` | `C` | `a` | C |
| `D. The number of motorists not wearing seat belts in a random sample of…` | `D` | `a` | D |
| `B. ability of populations to undergo modification as they adapt to a p…` | `B` | `a` | B |

Why my 16-row table missed it: it contained exactly two such rows, **and I wrote both of them myself** to probe the last-match rule; on a hand-picked set they looked like 2 out of 16, not 49 out of 600.

**What I'd do instead:**

1. Keep `\b([A-D])\b` (best of the five measured) — that alone takes the task from 0/600 to 486/600.
2. If bare lowercase letters matter, handle that shape **where it is unambiguous** — a whole-response match — rather than by making single letters match anywhere, e.g. an additional step `^\s*\(?([A-Da-d])\)?[.)]?\s*$` before/after the letter pattern.
3. Start-anchored matching scored 465 and indicator-anchored only 241, so neither is a drop-in replacement here; I would not swap to either without its own measurement.

Caveats so I don't overstate: this is **our** run's response set (600 rows, two DeepSeek models, 10 MMLU subjects), not a random sample of all models; and the counts are *correctness of extraction under the task's metric*, not a statement about how often a case appears in the wild generally. Happy to publish the corpus + the evaluation script (raw response + gold, JSONL) so you can re-run the table yourself — it's a few minutes of work if you want it.

Sorry for the extra round-trip on this; the original report in #4187 stands, and the fix works — it just shouldn't carry `(?i)`.
