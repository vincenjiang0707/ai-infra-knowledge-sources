## 正文

Add defer_download flag to Task and ConfigurableTask so datasets are not downloaded during initialization. Users can call task.download() explicitly when ready. Accessing dataset before download raises a clear RuntimeError.


Closes #1558 (hopefully)

### Architectural Review: Transparent JIT Lazy-Loading vs. Explicit Manual Invalidation

Hi @siddhant-rajhans, thanks for driving the solution for #1558! 

Looking closely at this implementation patch, introducing an explicit `defer_download` flag that throws a `RuntimeError` if `task.dataset` is accessed before an explicit `task.download()` invocation introduces significant downstream integration friction and leaks state-management outside the object. 

#### The Optimization Risk:
1. **API Invalidation / Blast Radius:** Any core evaluator component or downstream third-party module accessing the public `.dataset` attribute will now explicitly crash unless prefixed with a manual setup check.
2. **Encapsulation Failure:** Forcing downstream executors to manage when a dataset is hot/cold violates clean OOP encapsulation.

#### Proposed Refactor (Transparent Property JIT Descriptor):
We can achieve a completely clean, zero-blast-radius alternative by abstracting the dataset instantiation behind a native Python `@property` descriptor handling an implicit Just-In-Time execution closure:

```python
class Task(abc.ABC):
    def __init__(self, ..., defer_download: bool = False):
        self._dataset = None
        self._download_callable = lambda: self.download(...)
        
        if not defer_download:
            self._download_callable()

    @property
    def dataset(self):
        if getattr(self, "_dataset", None) is None:
            if hasattr(self, "_download_callable") and self._download_callable is not None:
                self._download_callable()
        return self._dataset

    @dataset.setter
    def dataset(self, value):
        self._dataset = value

### siddhant-rajhans · 2026-06-19

Thanks @Kesav2k04. Fair point on the encapsulation.

I went with the explicit flag + `task.download()` + hard error because that's what #1558 asks for specifically: a `defer_download` flag, a manual `task.download()` method, and an error if you try to run the task without downloading. So this was implementing the issue as written rather than a design choice I made on my own.

The reason that contract is useful: it lets you construct a bunch of tasks cheaply and then decide when (or whether) to download, e.g. downloading selectively or in parallel. It also means you can inspect a task without triggering a network call. The transparent `@property` version loses that, since any access to `.dataset` would download implicitly.

Where I think you're right: the bare `RuntimeError` is unhelpful. It should say what went wrong and point you at `task.download()`.

@baberabb, do you want the explicit-control contract from #1558, or the transparent lazy-load? Happy to go either way, just don't want to rewrite the API without your call.

Hi **@siddhant-rajhans**, thank you for pointing out the specific wording in #1558. You are completely right that your implementation followed the exact requirements of the issue. I really appreciate you clarifying that context.

Regarding the benefits of explicit control, I actually think the **@property** approach can support those use cases too.

For parallel or explicit downloading, the original **task.download()** method is still fully available. If someone wants to construct tasks cheaply and download them selectively or in parallel, they can still call **task.download()** manually. The property setter will catch the result, and any later access to **task.dataset** will just return the loaded data without triggering a second network call.

For inspecting tasks without triggering a network call, most of the metadata like splits and metrics can be read directly from task.config without ever needing to touch **task.dataset**.

I like that the **JIT approach** gives advanced users the option to use manual control while also preventing unexpected errors for users who rely on the implicit behavior.
