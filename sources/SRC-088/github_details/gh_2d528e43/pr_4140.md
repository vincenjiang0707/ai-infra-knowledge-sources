# [PR #4140] fix(cli): parse signed integers as int instead of float

## 正文

## What

`handle_cli_value_string` used `str.isnumeric()` to detect integers before falling back to `float(arg)`. `isnumeric()` returns `False` for any signed string (`"-1"`, `"+2"`), so signed integer CLI values silently parsed as float instead of int — e.g. `top_k=-1` became `-1.0`. Negative integer sentinels are a common case this affects.

## Fix

Try `int(arg)` first (which correctly handles `+`/`-` signs), falling back to the existing `float()` → `ast.literal_eval()` → string chain only on `ValueError`. Decimal and scientific-notation strings still parse as float; bool/`None`/string-literal handling is unaffected.

## Testing

Added 6 tests to the existing `TestCLIUtils` class in `tests/test_cli_subcommands.py` covering signed int, unsigned int, float, scientific notation, bool/None/string unaffected, and the exact `key_val_to_dict` repro from the issue. Full file: 90 passed, 0 failed. `ruff check` / `ruff format --check` clean on both changed files.

**Note:** `int()` is slightly more permissive than the old `isnumeric()` check (also accepts underscore-grouped literals like `"1_000"` and whitespace-padded strings) — flagging in case maintainers want stricter parsing, but this seemed like a harmless side effect of using the correct primitive rather than something to special-case around.
