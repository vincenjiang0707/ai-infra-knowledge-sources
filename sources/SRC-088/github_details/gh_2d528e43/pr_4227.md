## What changes

Evaluating MXFP4 W4A4 accuracy from an ordinary floating Hugging Face checkpoint currently requires an external quantization integration or a custom evaluation wrapper. This adds `--model hf-mxfp4`, reusing HFLM's standard task/scoring/generation interfaces without a training framework or native FP4 kernel dependency.

- Three comparable modes: `bf16`, `w4a16` (weight QDQ), and `w4a4` (weight and Linear-input QDQ).
- An explicit MXFP4 reference recipe: 32-element last-dimension blocks, E2M1 values, E8M0 floor scales, round-to-nearest/ties-to-even, FP32 QDQ arithmetic followed by the selected floating dtype.
- Quantize weights once in place; dynamically quantize selected Linear inputs. Always preserve the output head, including tied embeddings, and support explicit glob exclusions.
- Record the recipe and exact quantized/excluded module paths in result JSON. Reject unsupported architectures/configurations and empty coverage rather than silently labeling a floating model as W4.
- Document the numerical contract and limitations; add 46 offline tests covering arithmetic, independent-reference logits for Llama/Qwen2/Qwen3/GPT-NeoX, conversion safety, local checkpoint/registry loading, BF16 equivalence, and all three request types.

This is fake quantization for accuracy evaluation: storage and matmuls stay floating point. It does not provide packed FP4 storage or claim native FP4 throughput or kernel equivalence. The first implementation supports stock dense Llama, Qwen2, Qwen3 and GPT-NeoX; model/TP sharding, dispatch/offload, PEFT/delta application and already-quantized checkpoints are outside this scope.

## Validation

Windows CPU, Python 3.12.13, PyTorch 2.9.1+cpu. No veRL installation is needed.

```bash
HF_HUB_OFFLINE=1 HF_DATASETS_OFFLINE=1 python -m pytest tests/models/test_mxfp4.py tests/test_registry.py tests/test_plugins.py -q
```

**110 passed**, separately with Transformers **5.11.0 / PEFT 0.21.0** and **4.57.6 / PEFT 0.18.1**. On this Windows host, `PYTEST_DEBUG_TEMPROOT` pointed to a writable temporary directory inside the virtual environment.

```bash
pre-commit run --files README.md docs/mxfp4.md lm_eval/models/__init__.py lm_eval/models/hf_mxfp4.py lm_eval/models/utils_mxfp4.py tests/models/test_mxfp4.py
git diff --cached --check
```

Both passed.

Public-model task smoke tests used `EleutherAI/pythia-14m` revision `cf967c0a9a04383db6f7b1108d86b2962634b4ac`, Transformers 5.11.0, BF16 floating compute, and `OMP_NUM_THREADS=2 MKL_NUM_THREADS=2`:

```bash
for precision in bf16 w4a16 w4a4; do
  python -m lm_eval --model hf-mxfp4 \
    --model_args pretrained=EleutherAI/pythia-14m,precision=$precision,dtype=bfloat16 \
    --tasks boolq --device cpu --batch_size 1 --limit 8 \
    --output_path results/$precision-boolq --log_samples
done

python -m lm_eval --model hf-mxfp4 \
  --model_args pretrained=EleutherAI/pythia-14m,precision=w4a4,dtype=bfloat16 \
  --tasks gsm8k,wikitext --device cpu --batch_size 2 --limit 2 \
  --num_fewshot 0 --gen_kwargs max_gen_toks=8 \
  --output_path results/w4a4-generation-rolling --log_samples
```

All runs completed and saved results/samples. W4 modes report 24 quantized projections and one excluded output head. BoolQ: 0.375 on the 8 samples in each mode; W4A4 GSM8K exact match: 0/2; W4A4 WikiText word perplexity: 561.1067. These small runs validate the three request paths and result serialization, **not** benchmark quality or the size of accuracy loss. CUDA, Ascend NPU, and distributed execution have not been hardware-tested; the guide states this explicitly. The full repository test suite was not run.

## Related work

Existing quantization integrations serve different runtimes/recipes. #3981 fixes native NVFP4 batch alignment in the Megatron backend, rather than providing a PyTorch MXFP4 fake-quantization reference for floating HF checkpoints.
