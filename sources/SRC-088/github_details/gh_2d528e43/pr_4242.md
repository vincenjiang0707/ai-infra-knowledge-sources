# [PR #4242] Report a task YAML that cannot be loaded instead of skipping it at DEBUG

source: https://github.com/EleutherAI/lm-evaluation-harness/pull/4242
state: open | updated: 2026-09-26T10:18:37Z
labels: 

## 正文

A task YAML that cannot be loaded now disappears from the index without a trace.

`TaskIndex.build` catches every exception from `load_yaml` / `process_cfg` and logs it at `DEBUG`, so a task file with a YAML syntax error, a bad `!function` path or an unresolvable `include:` vanishes at the default log level.

That matters because the index is how a tag and a group learn their members. A group whose member failed to parse still builds, still runs, still exits 0, and still writes a group score — computed over the subtasks that happened to load. The results file records fewer subtasks than the config asks for, and nothing marks it as incomplete:

```
group_subtasks: {'my_group': ['my_ok_task']}   # the config declares two
results: my_group  sample_len=4                # half the documents
```

`lm-eval validate --tasks my_group` on the same directory answers `All tasks found and valid`, and `lm-eval ls subtasks` never lists the broken task, so none of the surfaces a user is likely to check mentions it.

The rest of the function already reports the entries it drops on purpose at `WARNING` — a duplicate task or group name, eight lines below, is a warning. And `_build_tag` warns when a tag names a task that is not in the registry, while the sibling path that expands a tag inside a group has no equivalent check, because by then the member is already missing from the index. This makes the exception path behave like those.

One case is genuinely expected and stays at `DEBUG`: a partial config reached through `include:` has no `task` or `group` key of its own, and `process_cfg` raises `ValueError("Unknown config shape: ...")` for it. Everything else is now a warning.

Running the index over the whole built-in task tree (14685 entries) produces **zero** warnings with this change, so it adds no noise to the tasks that ship with the repo.

Test: `pytest tests/test_task_manager.py -k TestTaskIndex` fails on main with `assert 'broken.yaml' in ''` and passes on this branch. A second test pins that an `include:` fragment still produces no warning, so the split cannot be collapsed into "warn about everything". The whole `tests/test_task_manager.py` is 73 passed. `ruff check` reports the same two findings as on main, both pre-existing.

I checked the group-expanding-tag path in `_factory.py` as well and left it alone: there a missing member is a `KeyError` rather than a silent shrink, so it is a separate fix. Happy to take it separately if you want it.

<details><summary>Reproduction (no network, no model, no API key)</summary>

Put three files in a directory and point `--include_path` at it: a group whose tag lists two tasks, one working task, and one task with a YAML syntax error.

```
$ lm-eval run --model dummy --tasks my_group --include_path ./inc --output_path ./out
... INFO and WARNING output contains no mention of broken.yaml ...
|my_group     |N/A    |none  |     0|exact_match|↑  |    0|±  |     0|
| - my_ok_task|Yaml   |none  |     0|exact_match|↑  |    0|±  |     0|
EXIT=0
```

`results_*.json` then contains `group_subtasks: {'my_group': ['my_ok_task']}`.

</details>
