# [PR #4245] Leave a document with an out-of-range label out of the metrics

source: https://github.com/EleutherAI/lm-evaluation-harness/pull/4245
state: open | updated: 2026-09-27T01:45:17Z
labels: 

## 正文

A document whose label names none of its choices is currently reported as a wrong answer. `ConfigurableTask` maps such a label to a `-100` sentinel, logs a warning, and then scores the document anyway: `acc`, `acc_norm` and `acc_bytes` come out as `0.0`, which after aggregation is indistinguishable from a real miss. A task that declares `multiple_target` raises `TypeError: argument of type 'int' is not iterable` on the sentinel instead, and a task reporting `brier_score` dies at the end of the run with `IndexError: index -100 is out of bounds for axis 0 with size 3`.

Returning no metrics for that document fixes all three. The sentinel is only meaningful as a marker inside the warning: the same block already refuses to use it for `exact_match` (`if gold != -100`), and `brier_score` indexes a one-hot matrix by label, where `-100` is not a class. Leaving the document out of the metrics is a state the aggregation layer already handles — `evaluator_utils.py` documents that "a document whose `process_results` omits a key contributes to some metrics and not others" — and the sample is still written to the log, with an empty `metrics` list, so nothing becomes invisible.

Test: `pytest tests/test_metrics.py` fails on `main` with `assert {'acc': 0.0, 'exact_match': 0} == {}` and `TypeError: argument of type 'int' is not iterable`, and passes on this branch (12 passed). Also ran `pytest tests/test_aggregation_pipeline.py tests/test_evaluator_utils.py` (84 passed).

Lint: `ruff 0.16.3` (the `rev` in `.pre-commit-config.yaml`) reports 20 findings on the two changed files — 17 in `lm_eval/api/task.py`, 3 in `tests/test_metrics.py` — so the `Linters` job will be red. None of them come from this change: running the same command on `main` (`d6de816`) over the same two files gives the same 20, with identical line numbers and codes. The job only sees them because `unit_tests.yml` runs `pre-commit --from-ref <base> --to-ref HEAD`, so a file's pre-existing debt is checked as soon as a PR touches it. The debt is older than the current pin: `.pre-commit-config.yaml` moved to `v0.16.3` in `cc9b6c2a` (2026-08-20), `lm_eval/api/task.py` was last touched on 2026-08-14 (`72d26385`) and `tests/test_metrics.py` on 2026-08-27 (`06e3cb5f`) — both of those commits were merged with `Linters` already failing, as was the current `main` head. I kept the diff to the one `return {}` rather than rewriting nine unrelated places in a core file; happy to split the 20 into a separate `chore:` PR if that is wanted.

<details><summary>Details</summary>

The change is one `return {}` at the point the sentinel is detected, before any metric is computed, so every metric that indexed by label is covered by it.

Raising instead of returning was the other option, but a dataset with a handful of malformed labels would then abort a run that currently completes, and the code already chose to warn and carry on. Skipping only the metrics that cannot be computed was not an option either: with the sentinel, `f1` grows a `-100` class and `acc` cannot be computed at all.

One visible consequence: the document is left out of `sample_len` too, since that is the largest per-metric count. `n_samples.effective` can therefore come out below `original` when a task has unusable labels. That is the honest number — the document was not evaluated — and it is the same thing that already happens for a task that drops a metric key.

`tests/test_tasks.py::test_strip_whitespace_in_target_and_metric` fails in this environment, for all three of its parameters, both on `main` and on this branch: it downloads datasets from HuggingFace and the requests time out. It is unrelated to this change.
