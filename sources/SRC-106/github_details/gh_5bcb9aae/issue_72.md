# [Issue #72] [Issue]: ODR Violation when using both python interface and C interface in same process

## 正文

### Problem Description

ROCm ships with 2 copies of `libamd_smi.so`, in
- `lib`
- `share/amd_smi/amdsmi`

Normal linking (both at `ld` time and with e.g. `dlopen`) loads the copy in `lib`. The python interface loads the other copy-- this is due to [this code](https://github.com/ROCm/amdsmi/blob/amd-staging/py-interface/amdsmi_wrapper.py#L174) which passes an absolute path to the second copy, thus ignoring any previously load copy or copy in `LD_LIBRARY_PATH` or the binary's `rpath`.

A possible solution here is to check for `libamd_smi.so` without an absolute path at first so that any copy available during normal linking is used if available first.

The onus of the caller to setup `LD_LIBRARY_PATH`/`rpath` correctly is standard behavior, and if it breaks a pre-existing usage of the python interface then the caller needs to do the aforementioned proper setup prior to `import amdsmi`.

This issue has presented itself in PyTorch, see e.g. https://github.com/pytorch/pytorch/pull/146324 which addresses the issue for current and older versions of ROCm by hooking `CDLL` to do the `LD_LIBRARY_PATH` / `rpath` lookup first.

### dmitrii-galantsev · 2025-02-06

hey FYI the python_wrapper.py gets generated by [update_wrapper.sh](https://github.com/ROCm/amdsmi/blob/9872083b491c9b136496fd493414aca5c6c144cb/update_wrapper.sh)

Bundling the .so in there is the most obvious solution. Otherwise we have to make assumptions about user ROCm environment. As you said `When you're interacting with amdsmi from only python that's fine, but when you try to interact with libamd_smi.so from native code too this poses a problem, because from native code you'll be linking against the copy of libamd_smi.so from the SDK.`

Reason we did it this way was so python part can be packaged on its own. So the user can install amdsmi _python_ tool alone. Without having to install libamd_smi.so through some magical means.
