# [PR #2246] backend: tolerate a null customParams in nixlBackendEngine

source: https://github.com/ai-dynamo/nixl/pull/2246
state: closed | updated: 2026-09-18T07:16:12Z
labels: external-contribution, size/XS

## 正文

Fixes #2245.

`nixlBackendInitParams::customParams` defaults to `nullptr` and the base constructor dereferences it unconditionally:

```cpp
explicit nixlBackendEngine(const nixlBackendInitParams *init_params)
    : backendType(init_params->type),
      customParams(*init_params->customParams),   // <-- segfault at 0x8
      ...
```

`nixlAgent::createBackend()` always fills the field, so this never fires in normal use. It fires immediately for a directly constructed engine, which is what a backend's own unit tests do. Because the crash happens in the base member-initializer list, before any derived constructor body runs, a backend cannot guard against it itself.

## Verified

Against `main` (e77af99), a storage backend built out of tree:

```cpp
nixlBackendInitParams p{};
p.localAgent = "test";
p.type = "DAOS";
nixlMyEngine eng(&p);   // customParams left at its default
```

Before: `Caught signal 11 (Segmentation fault: address not mapped to object at address 0x8)`, in the base constructor.

After: builds clean and runs —

```
constructed OK, customParams size = 0
```

GCC 14.3.1, C++20, full `ninja` build of the tree.

## Scope

This stops the base class from crashing. It deliberately does **not** make a null `customParams` generally supported — several backends dereference the pointer directly in their own constructors and genuinely require parameters:

- `src/plugins/gpunetio/gpunetio_backend.cpp:52` — `custom_params->count("network_devices")`
- `src/plugins/obj/obj_backend.cpp:37` — `custom_params->find("type")`
- `src/plugins/obj/s3_accel/dell/engine_impl.cpp:318` — `init_params->customParams->emplace(...)`

What an absent-parameters backend should do there is a different question, so those are untouched.

## Note on the other suggestion in the issue

The issue also floated dropping the `= nullptr` default to make the field mandatory. That is wrong and I have retracted it there: with `nixlBackendInitParams p{}` the member is value-initialized either way, so removing the default changes nothing, and it makes `nixlBackendInitParams p;` leave an indeterminate pointer — a reliable segfault turned into an unpredictable one. Making the field mandatory would take a real interface change (a reference, or a constructor parameter), which is a larger decision than this bug needs.
