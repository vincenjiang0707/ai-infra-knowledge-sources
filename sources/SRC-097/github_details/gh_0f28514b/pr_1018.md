## 正文

## What?
Move the AWS EFA validation job to a CUDA 13 base image.

## Why?
The job still runs on `cuda-dl-base:25.06` (CUDA 12.9).

## How?
- Base image: `nvcr.io/nvidia/cuda:13.0.1-devel-ubuntu24.04`, the same CUDA 13.0 base the Jenkins `nixl-ci-non-gpu` ubuntu22 cell builds on.
- `cuda-dl-base` CUDA 13 tags do not work with `.gitlab/build.sh` unchanged: 25.08 to 26.05 bundle DOCA 3.1/3.2, so build.sh skips the RDMA reinstall and the libfabric EFA provider fails to link; 26.06+ are CUDA 13.3/13.4, for which no PyTorch wheel index exists.
- `nvidia/cuda` ships no git, so the job installs it before cloning.
- README, job definition and script defaults aligned to one tag.

🤖 **CI Triage Agent** — `AWS NIXL Validation` · commit `3124ee04`

**TL;DR:** The AWS validation job died in `.gitlab/build.sh` while building libfabric: `./configure --enable-efa` found `infiniband/verbs.h`/`efadv.h` but could not link `-libverbs` or `-lefa` ("configure: error: Cannot continue"), because the RDMA-dev repair step (`apt-get --reinstall libibverbs-dev …`) is nested inside the "base image has no DOCA" branch and was skipped for this image. Move that reinstall out of the conditional so it always runs, as both Dockerfiles already do.

<details><summary>Full analysis</summary>

**Summary:** GHA run 35728012603 ("AWS NIXL Validation", PR #1018 / branch `cuda_update-aws_efa`) failed in the dependency-build step: libfabric 1.21.0 `configure` aborted, and the AWS Batch job then reported `FAILED` after 12s.

**Root cause:** From the run log:

```
configure: *** Configuring efa provider
checking for infiniband/verbs.h... yes
configure: looking for library without search path
checking for ibv_open_device in -libverbs... no
checking for infiniband/efadv.h... yes
configure: looking for library without search path
checking for efadv_query_ah in -lefa... no
configure: WARNING: The EFA provider requires rdma-core v31 or newer.
configure: efa provider: disabled
configure: WARNING: efa provider was requested, but cannot be compiled
configure: error: Cannot continue
```

Headers are present but the link-time libraries (`libibverbs.so`, `libefa.so` dev symlinks) are not resolvable in the default search path, so the mandatory `--enable-efa` provider cannot be built and libfabric's configure hard-fails. This is exactly the broken `libibverbs-dev` state that `.gitlab/build.sh` is supposed to repair with `apt-get -y install --reinstall libibverbs-dev rdma-core ibverbs-utils libibumad-dev libnuma-dev librdmacm-dev ibverbs-providers` — but in `build.sh` that repair sits inside the `else` arm of `if dpkg -s doca-sdk-gpunetio …` (i.e. it is skipped whenever the base image already ships DOCA), while both `contrib/Dockerfile` and `benchmark/nixlbench/contrib/Dockerfile` run the same reinstall **unconditionally**, with the comment "required even when DOCA is from the base image". Since this PR updates the CUDA/EFA image used by the AWS job, the DOCA-present path is taken, the repair never runs, and libfabric's EFA check fails. (The container's `PATH` in the log also contains `/opt/amazon/efa/bin`, so an AWS EFA-installer rdma-core outside the default lib path is a contributing factor — libfabric is given no `--with-verbs=<prefix>`, hence "looking for library without search path".)

**Implicated commit:** The skip was introduced in `9ac7adab` — ovidiusm, "Switch CI base image to pytorch + CUDA 13.3 (#1869)"; triggered by the base-image/EFA change on this PR branch (head `3124ee04`, Mikhail Brinskiy, merge of main into `cuda_update-aws_efa`).

**File:** `.gitlab/build.sh:195-212` (conditional RDMA reinstall) and `.gitlab/build.sh:231-249` (libfabric `--enable-efa` configure); compare `contrib/Dockerfile:145-149`.

**Suggested fix:**
1. In `.gitlab/build.sh`, un-nest the RDMA repair so it runs regardless of whether DOCA came from the base image:
```sh
if dpkg -s doca-sdk-gpunetio >/dev/null 2>&1; then
    echo "DOCA provided by base image; skipping DOCA repo + SDK install"
else
    ... doca-host.deb / SDK install ...
fi
# Always: libfabric --enable-efa needs a working libibverbs-dev/libefa
$SUDO apt-get -qq -y install --reinstall libibverbs-dev rdma-core ibverbs-utils \
    libibumad-dev libnuma-dev librdmacm-dev ibverbs-providers
```
2. If the AWS image intentionally uses the EFA installer's rdma-core under `/opt/amazon/efa`, additionally point libfabric at it instead of relying on the default path, e.g. `./configure … --enable-efa=/opt/amazon/efa` (or `CPPFLAGS=-I/opt/amazon/efa/include LDFLAGS=-L/opt/amazon/efa/lib64`), and add that prefix to `PKG_CONFIG_PATH`/`LD_LIBRARY_PATH`.
3. Cheap guard: before the libfabric build, assert `ls /usr/lib/*/libibverbs.so /usr/lib/*/libefa.so` (or the EFA prefix equivalent) and fail with a clear message — the current failure mode is a 200-line autoconf trace ending in "Cannot continue".

**Related:** #1994 (libfabric EFA/NIC preflight checks), #1555 (EFA installer in the nixlbench container), #1869 (introduced the DOCA-present skip).

</details>

🤖 **CI Triage Agent** — `AWS NIXL Validation` · commit `9ce03014`

**TL;DR:** The AWS EFA job died in the build stage because `.gitlab/build.sh` derived a PyTorch wheel index from `nvcc` (CUDA 13.4 → `https://download.pytorch.org/whl/cu134`), which does not exist, so `pip3 install torch` failed under `set -e`; pin the index to a published one (e.g. `cu130` for CUDA 13.x) or fall back to the default PyPI index.

<details><summary>Full analysis</summary>

**Summary:** AWS Batch job `2ef30c10-2214-4ac1-84d8-[REDACTED:Hex High Entropy String]` (pod `aws-batch.5cc347fa-…`) reached status FAILED ~1 min into the "Build" group; the GHA step then exited 1 with "Failure running NIXL tests".

**Root cause:** The PR's head commit switches the AWS EFA container to `nvcr.io/nvidia/cuda-dl-base:26.08-cuda13.4-devel-ubuntu24.04`. That image does not ship torch, so `.gitlab/build.sh` took the fallback branch:
```
System torch check failed: ModuleNotFoundError: No module named 'torch'
+ cuda_version=134
+ pip3 install ... --index-url https://download.pytorch.org/whl/cu134 torch
ERROR: Could not find a version that satisfies the requirement torch (from versions: none)
ERROR: No matching distribution found for torch
```
PyTorch publishes no `cu134` wheel index (13.x wheels live under `cu130`). `build.sh` runs with `set -e -o pipefail`, so the failed pip install aborted the build, which the wrapper reported as the batch job terminating FAILED. This is not a timeout/hang — the failure is 40 s after the pip install started, with continuous log output throughout. The in-code comment at `.gitlab/build.sh:172-174` confirms the fallback was only ever expected to work on images that already ship torch ("the nvcr.io/nvidia/pytorch base ships torch and has no cu133 wheel index").

**Implicated commit:** [REDACTED:Hex High Entropy String] — "CI: use cuda-dl-base 26.08 for AWS EFA tests", Alexey Rivkin (sets `CONTAINER_IMAGE` at `contrib/aws-efa/aws_test.sh:44`)

**File:** `.gitlab/build.sh:179-185` (index URL construction); trigger at `contrib/aws-efa/aws_test.sh:44`

**Suggested fix:** Stop mapping the full CUDA minor version into the index URL. Either:
1. Map CUDA major → the latest published channel, e.g.
   ```bash
   cuda_major=$(nvcc --version | grep -oP 'release \K[0-9]+')
   case "$cuda_major" in
     13) torch_index="cu130" ;;
     12) torch_index="cu128" ;;
     *)  echo "unsupported CUDA $cuda_major" >&2; exit 1 ;;
   esac
   pip3 install --break-system-packages --index-url "https://download.pytorch.org/whl/${torch_index}" torch
   ```
   (optionally with `|| pip3 install --break-system-packages torch` as a last-resort fallback to the default PyPI index), or
2. keep the AWS EFA job on a base image that ships torch (`nvcr.io/nvidia/pytorch:…`), reverting the `CONTAINER_IMAGE` bump until a `cu134` index exists.

**Related:** PR #1018 (this change); PR #2205 "build: bump CUDA and CI base images, stop restating them across CI" touches the same image/CUDA-version coupling.

</details>

<details><summary>Full analysis</summary>

**Summary:** "Run AWS Tests" step failed: the AWS Batch/EKS job (jobId `2cdc741e-d323-4db2-9542-b9d72979cb92`, pod `aws-batch.296dd777-1442-3913-a4b0-[REDACTED:Hex High Entropy String]`) reached terminal status FAILED 12s after start, with the pod log showing `git: command not found`.

**Root cause:** `contrib/aws-efa/aws_test.sh` builds the in-pod command as `AWS_CMD="set -x && git clone ... && cd nixl && git checkout ... && bash contrib/aws-efa/aws_test_remote.sh"` and passes it as the container's entry command (`aws_vars.template` → `/bin/bash -c "${AWS_CMD}"`). That command runs in the unmodified base image, so `git` must already be present. Commit 799bab3c changed `CONTAINER_IMAGE` to `nvcr.io/nvidia/cuda:13.0.1-devel-ubuntu24.04`; unlike the previously-used `cuda-dl-base` images (see 9ce03014 / [REDACTED:Hex High Entropy String] "Switch from PyTorch to cuda-dl-base images"), the plain CUDA devel image does not include git. **Implicated commit:** [REDACTED:Hex High Entropy String] — Alexey Rivkin, "CI: use nvidia/cuda 13.0.1 for AWS EFA tests" (prior step: 9ce03014, same author)

**File:** contrib/aws-efa/aws_test.sh:44 (image selection) and :58 (`AWS_CMD` starting with `git clone`)

**Suggested fix:** Make the pod bootstrap its own prerequisites instead of assuming them. In `aws_test.sh:58`, prepend a package install to `AWS_CMD`, e.g.:

```sh
export AWS_CMD="set -x && (command -v git >/dev/null || (apt-get -qq update && apt-get -qq install -y git ca-certificates)) && git clone ${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY} && cd nixl && git checkout ${checkout_ref} && $TIMEOUT_CMD bash contrib/aws-efa/aws_test_remote.sh \${NIXL_INSTALL_DIR}"
```

<details><summary>Full analysis</summary>

**Summary:** Stage 156 "Allocate DL EP Environment" failed after 3609 s when the slurm `salloc` for the GB200 test node timed out; the preceding compile stage ("Compiling NIXL EP Docker Image for DL", 1049 s) succeeded and the test image was pushed.

**Root cause:** The pipeline calls `slurm.allocation` with `partition: gb200nvl72_cx8`, `nodes: 1`, `--immediate=3600`, `--account=blackwell`. The log shows:
- `20:27:54` — ssh + `salloc -N 1 -p gb200nvl72_cx8 --job-name=nixl-ci-dl-gpu-ep-1266 --immediate=3600 --time=02:00:00 --no-shell --account=blackwell`
- `21:28:03` — `salloc: Pending job allocation 2271392` / `job 2271392 queued and waiting for resources` / `salloc: error: Unable to allocate resources: Connection timed out`

The single 60-minute gap between those two lines is exactly the `--immediate=3600` window, and the slurm messages show the job was *queued waiting for resources* the whole time — i.e. no free/idle node in `gb200nvl72_cx8` (the lua job submit plugin also forced the job to exclusive mode: "Setting job to exclusive mode as no gpu count was specified", so it needed a whole GB200 node). Nothing in the build hung: the process was blocked in the scheduler queue, and `salloc` reported the expiry of its immediate timeout. Nothing in the commit under test (139244495, branch `cuda_update-aws_efa`) is implicated — the full build, install, nixlbench build and container push all completed cleanly before the allocation attempt.

Secondary observation: cleanup at the end logged `WARNING: No job ID files found in /mnt/pvc/nixl-ci-dl-gpu-ep/`, because the job-ID file (`job_id_ep_1266.txt`) is only written on a successful allocation. If the allocation is ever granted just as the client gives up, the allocation would be orphaned with no ID for `slurm.stopAllForBuild` to cancel.

**Implicated commit:** unknown — no code commit is implicated; the failure is in slurm resource allocation on `dlcluster.nvidia.com`, partition `gb200nvl72_cx8` (slurm job 2271392).

**File:** `.ci/jenkins/pipeline/` job definition for `nixl-ci-dl-gpu-ep` (the `slurm.allocation` step: `partition: gb200nvl72_cx8`, `immediateTimeout: 3600`, `nodes: 1`, `extraArgs: --account=blackwell`) — the "Allocate DL EP Environment" stage, Jenkins stage ID 156.

**Suggested fix:**
1. Re-run the build — this is a transient capacity failure, not a PR regression (verify by checking whether adjacent builds of this job on the same branch pass).
2. Ask the dlcluster admins to check `gb200nvl72_cx8` capacity during the 20:27–21:28 window: whether nodes were DRAIN/DOWN or saturated by other jobs, and whether the `blackwell` account has a QOS/GrpNodes limit blocking the allocation (quote slurm job **2271392**).
3. Make the CI step resilient rather than raising wall-clock limits: wrap the `slurm.allocation` call in a bounded retry (e.g. 2–3 attempts with `immediateTimeout` around 900 s each) so a momentarily full partition doesn't red-flag a PR, and mark this stage's failure as `UNSTABLE`/infra rather than a build failure.
4. Harden cleanup: write the job-ID file as soon as `salloc` returns a pending allocation ID (or parse `Pending job allocation <id>` and record it) so `slurm.stopAllForBuild` can cancel an allocation granted after the client timed out.
5. If the test only needs a subset of GPUs, pass an explicit `--gpus`/`--gres` count so the lua plugin doesn't escalate the request to an exclusive whole-node allocation, which is much harder to schedule on a busy GB200 partition.
