## 正文

## Summary

Fix GPUNetIO transfer-request ownership across preparation, ring reuse, completion polling, reposting, and release.

- Reserve every descriptor-ring entry for its request handle until release. Search the bounded ring for available contiguous entries, and mask every wrapped access.
- Store request-local completion IDs and completion state. Poll all submitted entries and recycle completion slots after observing completion.
- Split descriptor lists across entries with the correct descriptor offset.
- Preserve completed descriptors for reposting. Drain submitted entries after a partial CUDA launch failure, then report the launch error.
- Release prepared and completed handles exactly once. Active handles remain available for polling.
- Preserve the outer request's in-progress state when backend cancellation fails, so polling and a subsequent release continue through the normal request lifecycle.

Related: #2254.

## Validation

- An ASan and UBSan CPU replay compiled the current request methods, the outer request polling and release methods, and the request destructor with CUDA-launch and completion shims. It passed 2,048 lifecycle iterations, 1,025-descriptor splitting, uint32 cursor wrap, read and write reposting, partial completion, completion-capacity pressure, partial-launch recovery, repeated failed release, and retained handles across ring reuse. The original cancellation-state assignment failed the same recovery scenario.
- ClangFormat 19.1.7 checks, repository SPDX checks, and `git diff --check` passed.
- The existing two-process GPUNetIO stream test now exercises ring wrap and retained-handle reposting, validates both received payloads, rejects invalid post and polling statuses, and enforces a 120-second deadline.
- Full CUDA and DOCA compilation and two-process GPUNetIO execution remain pending on compatible hardware. CPU lifecycle replay covers host state transitions.
