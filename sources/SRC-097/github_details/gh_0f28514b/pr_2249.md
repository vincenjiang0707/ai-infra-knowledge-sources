# [PR #2249] build: pin the torch wheel index instead of deriving it from CUDA_VERSION

source: https://github.com/ai-dynamo/nixl/pull/2249
state: closed | updated: 2026-09-16T11:11:05Z
labels: external-contribution, size/S

## 正文

## What?
Replace the derived PyTorch wheel index in `contrib/Dockerfile` and `benchmark/nixlbench/contrib/Dockerfile` with an explicit `ARG TORCH_CUDA_INDEX="cu130"`.

## Why?
`nixl-ci-build-container-pr` fails on every cell at the torch install. Both Dockerfiles compute the index from `$CUDA_VERSION`:

```dockerfile
export UV_INDEX="https://download.pytorch.org/whl/cu$(echo $CUDA_VERSION | cut -d. -f1,2 | tr -d .)"
```

`$CUDA_VERSION` comes from the base image, which exports it as `ENV`:

| base | inherited `CUDA_VERSION` | index | published? |
|---|---|---|---|
| `cuda-dl-base:25.10-cuda13.0` (previous) | `13.0.2.006` | `cu130` | yes |
| `cuda-dl-base:26.08-cuda13.4` (current) | `13.4.1.012` | `cu134` | **no** |

A latent bug the CUDA 13.4 bump made live — PyTorch publishes only some CUDA minors (`cu130` and `cu132` exist; `cu131`, `cu133`, `cu134` all 404).

## How?
The first attempt in this PR declared `ARG CUDA_VERSION="13.2"` and re-exported it as `ENV`. That does **not** work, and CI proved it: the base image's `ENV` of the same name wins when the right-hand side of `ENV CUDA_VERSION=${CUDA_VERSION}` is expanded, making the line a self-assignment of `13.4` and silently shadowing the ARG default. (`Dockerfile.manylinux` uses that same pattern and appears fine only because its base already reports `13.2`, so it resolves to a published index either way — it has never actually been exercised against a conflicting base.)

So this uses a name the base image does not own, set directly to the index component rather than a CUDA version that then has to be mapped onto PyTorch's sparse index set.

`cu130` is the index that carries the full set this build needs, for cp312 on both arches:

| index | torch | torchvision | torchaudio |
|---|---|---|---|
| `cu130` | 2.9.0 … 2.11.0 … 2.14.0 | 0.24.0 … 0.29.0 | 2.9.0 … 2.11.0 |
| `cu132` | 2.12.0 … 2.14.0 | 0.27.0 … 0.29.0 | **none** |

`cu132` was the first choice here and would also have failed: no `torchaudio` cp312 wheel, and it starts at torch 2.12 so it cannot satisfy the `torch==2.11.*` build requirement in `pyproject.toml:17`. PyTorch wheels bundle their own CUDA runtime, so `cu130` wheels run on the 13.4 toolkit in the base.

Scope is deliberately limited to the two Dockerfiles that are broken. The remaining `$CUDA_VERSION` uses in both files only take the major version, which the inherited `13.4` gives correctly, so they are untouched — as are `Dockerfile.manylinux`, `build-container.sh` and `.gitlab/build.sh`.

Still latent, not fixed here: `.gitlab/build.sh` derives the same index from `nvcc`. It is masked because every base it runs on ships torch, so the fallback never executes, but it would break the same way on a torch-less CUDA 13.4 base.
