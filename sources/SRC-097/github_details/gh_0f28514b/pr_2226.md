## 正文

## What?

`nixl::proxyMemViewRegistry`: the table a proxy worker consults on every ring
record it dequeues. It maps the memory-view ids and indices the GPU wrote to the
transport metadata a backend needs, and owns the device-resident
`nixlProxyDeviceMemView` behind every proxy memory-view handle. Nothing constructs
it yet; the runtime in the next PR does.

```
  ring record: src id, index, offset | dst id, index, offset | size, opcode, value
                    |                           |
                    v  one acquire load         v
      local entry -> nixlMetaDesc          remote entry -> nixlMetaDesc + agent name
                    \___________  proxyBackendSubmission      ___________/
```

## Why?

A ring record is frozen at 64 bytes and carries a `uint32` per side, so the GPU
can hand the worker an id, never a pointer. The registry is the one place that
turns an id back into a descriptor, and it sits directly on the submission path,
which dictates its shape.

## How?

- The read side takes no lock and performs no atomic read-modify-write. Entries are
  individually owned and never move. An entry is published by release-storing its
  pointer into a table sized once at construction; a worker resolves an id with one
  acquire load. A growing container could not be indexed unlocked, because it
  rewrites its own bookkeeping as it grows.
- Registration and metadata storage are one step, so an entry is never visible
  before it is complete.
- `unregister` release-stores null so no new submission reaches the entry, keeps
  the host entry alive for a worker that resolved it a moment earlier, and frees
  the device memview immediately. The caller has quiesced the GPU, the same
  condition the direct path relies on when it releases a memory list.
- Application threads serialize on `ctrl_mutex_`; workers never take it.
- Ids are never reused, so `kMaxProxyMemViews` bounds registrations over a
  runtime's lifetime, not live views.
- `StoredDesc::metadata` is a borrowed pointer into the core's remote section, not
  an owning reference. An entry is valid only while the core memory view that
  produced it is alive; owning the section from the core view is a separate core
  change.
- Remote views can carry direct pointers, copied into the device view's trailing
  array for the GPU's direct-access path.
- Five calls: `prepLocal`, `prepRemote`, `unregister`, `resolve`,
  `prepareSubmission`.

## Testing

- `proxy_memview_registry`: local and remote registration and retirement, id
  resolution, bounds and size validation on both sides of a submission,
  direct-pointer storage in the device view, capacity exhaustion, and that a
  retired id stops resolving. Host-only (mock device operations), so it runs
  without a GPU or CUDA.

**Summary:** Stage "Build image" failed in all four parallel matrix legs of `nixl-ci-build-container-pr` #758 during the container image build, at a `git clone` from github.com.

**Root cause:** Evidence from the stage logs:
- x86 leg (stage 233), step 36 (`meson setup build`): the liburing wrap tarball downloaded fine over HTTPS, then
  `Cloning into 'taskflow'... fatal: could not read Username for 'https://github.com': No such device or address` / `fatal: expected flush after ref listing`, followed by
  `ERROR: Subproject taskflow is buildable: NO` and `meson.build:233:16: ERROR: Git command failed: ['/usr/bin/git', …, 'clone', '--depth', '1', '--branch', 'v3.10.0', 'https://github.com/taskflow/taskflow.git', 'taskflow']` → `Error: building at STEP "RUN rm -rf build && … meson setup build …": exit status 1`.
- aarch64 leg (stage 196), step 43: `Cloning into 'ucx'... fatal: could not read Username for 'https://github.com': No such device or address` → `exit status 128`.

"could not read Username" means the GitHub smart-HTTP endpoint answered with a 401 and git had no TTY/credentials to prompt. Both repos are public and other clones in the *same* builds succeeded minutes earlier (`nvidia/gusli` 13:32:44, `Azure/azure-sdk-for-cpp` 13:32:07), and plain HTTPS to github.com still worked (the liburing archive download succeeded seconds before the taskflow failure). That pattern — HTTPS fine, git clone 401, four concurrent builds hammering github.com from the same egress at once — is transient anonymous-clone throttling/blocking of the CI egress IP, not a repository or code problem. There are no large time gaps in the logs; every failure was immediate, so this is not a hang or a timeout.

The reason it is fatal rather than degraded is that the taskflow dependency has no fallback tolerance: `dependency('taskflow', fallback: ['taskflow', 'taskflow_dep'])` is `required` by default, and `subprojects/taskflow.wrap` is a `wrap-git` entry, so a single failed clone aborts `meson setup`.

**Implicated commit:** unknown — no commit in the PR branch (`cpu-proxy-2-device-allocator`, [REDACTED:Hex High Entropy String]) touches the failing clones; the `taskflow` wrap dependency and the UCX clone predate it.

**File:** `meson.build:233` and `subprojects/taskflow.wrap:2` (x86 legs); `contrib/Dockerfile` UCX clone step (`git clone "$UCX_REPO" ucx`, aarch64 legs)

**Suggested fix:**
1. Re-run the build first — this is an intermittent external-fetch failure and will very likely pass on retry.
2. To stop it recurring, remove the reliance on live anonymous GitHub clones in the image build:
   - Convert `subprojects/taskflow.wrap` from `wrap-git` to a `wrap-file` tarball entry (`source_url = https://github.com/taskflow/taskflow/archive/refs/tags/v3.10.0.tar.gz` + `source_hash`), optionally with `source_fallback_url` pointing at an internal mirror. Tarball fetches succeeded in this very build where the git clone did not, and meson will then use `subprojects/packagecache`.
   - Pre-seed `subprojects/packagecache` (or vendor the wrap sources) into the container base layer so `meson setup` never needs network at all.
   - Wrap the `git clone "$UCX_REPO"` in `contrib/Dockerfile` in a bounded retry loop with backoff (e.g. `for i in 1 2 3; do git clone … && break; sleep $((i*15)); done`) and set `GIT_TERMINAL_PROMPT=0` so the failure mode is an explicit error rather than a blocked prompt.
   - Consider serialising/staggering the four matrix legs' external fetches, or routing `github.com` clones through the internal mirror/proxy, to avoid the concurrent-burst throttling.

**Related:** PR #2226 (the PR under test — not the cause); no existing issue tracking this clone failure was found.
