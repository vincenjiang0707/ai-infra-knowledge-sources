## 📌 Description

**This is an alternative to #5520. They fix the same launch problem, and only one of them should be merged.** #5520 changes only host code. This PR changes the kernel's problem search as well, and is faster on large batches. The two are compared side by side below.

With `use_deepseek_fp8_block_scale=True` on SM90, the CUTLASS fused MoE quantizes the BF16 activations of every FC1/FC2 GEMM to FP8 (one scale per 128 columns) with the grouped `scale_1x128_kernel<UseBinarySearch, bf16, fp8_e4m3>`, launched from `fp8_grouped_gemm_run`. The problem, described in more detail in #5520:

1. **The grid is capped at the SM count**, one block (8 warps) per SM, while the other scale kernels in this file launch `kNumDeviceSMs * 8`. On H20, 37,000 rows × K=2560 take 764 µs at 9% of DRAM bandwidth.
2. **The linear/binary search choice is made from `max_shape_m`, which is the runner's high-water mark** (`getWorkspaceSizeBase` keeps the max, and the runner is cached in `MoERunner.runner_dict`). After one large batch, every decode-sized call takes the linear search. There, each warp walks the problem boundaries one by one from problem 0, and again across every problem it skips between two rows. Only raising the grid cap to `* 8` multiplies that walk by 8 and makes small batches up to 1.8x slower than today.

This PR:

- **Replaces the linear walk with a galloping search.** From the current problem it probes +1, +2, +4, ... and then bisects. Stepping into the next problem, which is the common case for dense rows, still costs one probe, as the linear walk did. A long jump (a warp's first row, or a large grid stride over sparse rows) costs O(log distance) instead of O(distance). The problem index, boundaries and padded offset it produces are the same as those of the walk.
- **Drops the host-side search choice and always launches this variant**, since it is cheap for both dense and sparse rows.
- **Launches `kNumDeviceSMs * 8` blocks**, like the other scale kernels here. The non-binary kernel still uses 32 registers per thread (nvcc 13.3, sm_90a, no `__launch_bounds__` needed), so 8 blocks fit per SM.

The binary-search branch is unchanged, and so are the quantization math and scale layout. Outputs are bitwise identical to `main` (see below).

### Correctness

- **Standalone harness** that `#include`s this header and launches the kernel with the host logic reproduced. It covers 477 cases: E ∈ {8, 64, 128, 256}; rows per expert ∈ {0, 1, 31, 32, 33, 127, 128, 1175} plus two random routings (skewed, and with empty experts interleaved); K ∈ {640, 2048, 2560, 7168, 2000, 100}; `max_shape_m` both equal to and far above the actual rows. Each case runs 13 launch configurations, which include the galloping kernel at both 1 and 8 blocks per SM. FP8 bytes and scales are compared bitwise against an independently written reference kernel, including sentinel checks outside the written range. All 477 cases match.
- **`cutlass_fused_moe` end to end**: outputs of this branch and of `main` are bitwise identical on 20/20 (config, batch) pairs. The configs are E/top-k/hidden/inter = 8/2/512/256, 64/8/512/256, 256/8/1024/512 and 128/8/2560/640, each with batches of 2048, 1, 5, 64 and 300 tokens run in that order on the same runner.

<summary>MoE benchmark script</summary>

```python
import statistics
import torch
import torch.nn.functional as F
import flashinfer.fused_moe as fused_moe
from flashinfer.testing import bench_gpu_time


def block_quant(w):
    e, n, k = w.shape
    wv = w.view(e, n // 128, 128, k // 128, 128)
    amax = wv.abs().float().amax(dim=(2, 4), keepdim=True).clamp(1e-4)
    q = (wv * (448.0 / amax)).to(torch.float8_e4m3fn).view(e, n, k).contiguous()
    return q, (amax / 448.0).view(e, n // 128, k // 128).contiguous()


for name, E, topk, H, I in [("E128 H2560 I640", 128, 8, 2560, 640), ("E256 H7168 I2048", 256, 8, 7168, 2048)]:
    g = torch.Generator(device="cuda").manual_seed(0)
    w31_q, w31_s = block_quant(torch.randn(E, 2 * I, H, device="cuda", generator=g, dtype=torch.bfloat16) / 10)
    w2_q, w2_s = block_quant(torch.randn(E, H, I, device="cuda", generator=g, dtype=torch.bfloat16) / 10)
    for T in [8192, 4096, 1024, 256, 64, 16, 1]:  # largest first: the runner keeps the max
        g = torch.Generator(device="cuda").manual_seed(7)
        x = torch.randn(T, H, device="cuda", generator=g, dtype=torch.bfloat16)
        experts = torch.rand(T, E, device="cuda", generator=g).topk(topk, dim=1).indices.to(torch.int)
        weights = F.softmax(torch.randn(T, topk, device="cuda", generator=g), dim=1)
        out = torch.empty_like(x)
        fn = lambda: fused_moe.cutlass_fused_moe(
            x, experts, weights, w31_q, w2_q, torch.bfloat16,
            use_deepseek_fp8_block_scale=True, quant_scales=[w31_s, w2_s], output=out)
        t = bench_gpu_time(fn, enable_cupti=True, dry_run_iters=10, repeat_iters=50, cold_l2_cache=False)
        print(f"{name} tokens={T}: {statistics.median(t) * 1e3:.1f} us")
```

## Reviewer Notes

- **Choosing between this and #5520.** #5520 is host-only and has no measurable regression anywhere in the sweep. This PR changes kernel logic (about 20 lines in the non-binary branch). At 4096–8192 tokens its MoE time is another 1.7–6.5% below #5520 (E=128, 8192 tokens: 3690 vs 3874 µs; E=256: 29702 vs 30209 µs), at the cost of +0.1 to +0.4 µs on 16–64-row calls from a fresh runner. Both PRs carry the same test changes, so after one is merged the other should be closed.
- `scale_1x128_kernel<true, ...>` (binary search) is no longer launched from here. I left it in place so the diff stays confined to the non-binary branch; it can be removed if preferred.
- The galloping loop keeps the walk's invariants: every problem before `lo` has a right boundary ≤ `scales_idx_y`; `hi` never passes `num_problems - 1`, whose boundary is the total row count and therefore > `scales_idx_y`; and `lo - 1 ≥ problem_idx ≥ 0`. Empty problems (equal consecutive boundaries) are skipped as before, and the padded offset is computed from the same `(boundary_left, problem_idx)` pair.
- This file is shared with TensorRT-LLM (`cpp/tensorrt_llm/kernels/cutlass_kernels/fp8_blockscale_gemm/`), so this diverges from upstream TRT-LLM.
- Tested on H20 only. H100/H200 have more SMs (132) but the same per-SM register file, and the 32-register kernel fits 8 blocks per SM there as well.
- AI-assisted change: the analysis, harness and benchmarks were run with an AI coding assistant, and the numbers above are from those runs.
