## 📌 Description

**#5522 is an alternative to this PR. They fix the same problem, and only one of them should be merged.** This PR changes only host code and shows no measurable regression anywhere in the sweep. #5522 replaces the kernel's linear problem walk with a galloping search and launches 8 blocks per SM. At 4096–8192 tokens its MoE time is another 1.7–6.5% lower, but it adds 0.1–0.4 µs to 16–64-row calls from a fresh runner. #5522 has a side-by-side comparison of main, this PR and itself, measured in the same session.

With `use_deepseek_fp8_block_scale=True` on SM90, the CUTLASS fused MoE quantizes the BF16 activations of every FC1/FC2 GEMM to FP8 (one scale per 128 columns) with the grouped `scale_1x128_kernel<UseBinarySearch, bf16, fp8_e4m3>`, launched from `fp8_grouped_gemm_run`. Its launch has two problems:

1. **The grid is capped at the SM count**, i.e. one 256-thread block (8 warps) per SM. The other scale kernels in the same file launch `kNumDeviceSMs * 8` blocks. On H20 (78 SMs), 37,000 rows × K=2560 take 770 µs with 12.5% of warp slots active and 8.9% of DRAM bandwidth used (Nsight Compute).
2. **The linear/binary search choice is made from `max_shape_m`, which is the runner's high-water mark, not this call's row count.** `getWorkspaceSizeBase` keeps `max_shape_m_4_align_ = std::max(...)`, and the runner lives in `MoERunner.runner_dict` for the lifetime of the process. After one large batch, every later call, including decode-sized ones, takes the linear search, in which each warp walks the problem boundaries from problem 0. Only raising the grid cap to `kNumDeviceSMs * 8` multiplies that walk by 8 and makes small batches up to 1.8x *slower* than today. For example, with E=256, K=7168 and 128 rows after a 65,536-row batch, the kernel goes from 14.9 µs to 27.1 µs; Nsight Compute shows 8.96 M instructions instead of 2.42 M.

This PR changes only the host-side launch:

- **Always use the binary-search variant.** Its per-boundary cost is O(log num_problems) and does not grow with the grid.
- **Cap the grid at `kNumDeviceSMs` × the occupancy of that kernel**, queried on each call with `cudaOccupancyMaxActiveBlocksPerMultiprocessor`. The binary-search kernel uses 39 registers per thread (nvcc 13.3, sm_90a), so 6 blocks fit per SM, not 8. A fixed `* 8` would leave a partial second wave.

The kernel is unchanged. FP8 values and scale layout are bitwise identical to before.

### Correctness

- **Standalone harness** that `#include`s this header and launches the upstream kernel with the host logic reproduced. It covers 477 cases: E ∈ {8, 64, 128, 256}; rows per expert ∈ {0, 1, 31, 32, 33, 127, 128, 1175} plus two random routings (skewed, and with empty experts interleaved); K ∈ {640, 2048, 2560, 7168, 2000, 100}; `max_shape_m` both equal to and far above the actual rows. Each case runs 13 launch configurations, including both search variants at both grid sizes and the exact old and new launches. FP8 bytes and scales are compared bitwise against an independently written reference kernel, and sentinel values outside the written range are checked too. All 477 cases match.
- **`cutlass_fused_moe` end to end**: outputs of this branch and of `main` are bitwise identical on 20/20 (config, batch) pairs. The configs are E/top-k/hidden/inter = 8/2/512/256, 64/8/512/256, 256/8/1024/512 and 128/8/2560/640, each with batches of 2048, 1, 5, 64 and 300 tokens run in that order on the same runner.

<summary>MoE benchmark script</summary>

```python
import statistics
import torch
import torch.nn.functional as F
import flashinfer.fused_moe as fused_moe
from flashinfer.testing import bench_gpu_time


def block_quant(w):
    e, n, k = w.shape
    wv = w.view(e, n // 128, 128, k // 128, 128)
    amax = wv.abs().float().amax(dim=(2, 4), keepdim=True).clamp(1e-4)
    q = (wv * (448.0 / amax)).to(torch.float8_e4m3fn).view(e, n, k).contiguous()
    return q, (amax / 448.0).view(e, n // 128, k // 128).contiguous()


for name, E, topk, H, I in [("E128 H2560 I640", 128, 8, 2560, 640), ("E256 H7168 I2048", 256, 8, 7168, 2048)]:
    g = torch.Generator(device="cuda").manual_seed(0)
    w31_q, w31_s = block_quant(torch.randn(E, 2 * I, H, device="cuda", generator=g, dtype=torch.bfloat16) / 10)
    w2_q, w2_s = block_quant(torch.randn(E, H, I, device="cuda", generator=g, dtype=torch.bfloat16) / 10)
    for T in [8192, 4096, 1024, 256, 64, 16, 1]:  # largest first: the runner keeps the max
        g = torch.Generator(device="cuda").manual_seed(7)
        x = torch.randn(T, H, device="cuda", generator=g, dtype=torch.bfloat16)
        experts = torch.rand(T, E, device="cuda", generator=g).topk(topk, dim=1).indices.to(torch.int)
        weights = F.softmax(torch.randn(T, topk, device="cuda", generator=g), dim=1)
        out = torch.empty_like(x)
        fn = lambda: fused_moe.cutlass_fused_moe(
            x, experts, weights, w31_q, w2_q, torch.bfloat16,
            use_deepseek_fp8_block_scale=True, quant_scales=[w31_s, w2_s], output=out)
        t = bench_gpu_time(fn, enable_cupti=True, dry_run_iters=10, repeat_iters=50, cold_l2_cache=False)
        print(f"{name} tokens={T}: {statistics.median(t) * 1e3:.1f} us")
```

## Reviewer Notes

- **Why not just `kNumDeviceSMs * 8`?** That is what the other scale kernels here use, and it is the fastest option for large batches: 209 µs vs 264 µs at 37,000 rows × K=2560, because the linear search keeps 8 blocks per SM. But combined with the high-water-mark `max_shape_m`, it makes decode-sized batches up to 1.8x slower (second table). The kernel-side alternative in #5522 replaces the linear walk with a galloping search and keeps `* 8` without the decode regression.
- The occupancy is queried on every call with that call's `smem_size` (`num_problems * 8` bytes); the query takes about 0.1 µs. For any realistic `num_problems`, registers limit it to 6 blocks per SM, not shared memory; on H20, 32 KB of dynamic shared memory per block (4096 problems) still allows 6 and 40 KB allows 5.
- `scale_1x128_kernel<false, ...>` (linear search) is no longer launched from here. I left the template in place.
- This file is shared with TensorRT-LLM (`cpp/tensorrt_llm/kernels/cutlass_kernels/fp8_blockscale_gemm/`), so this diverges from upstream TRT-LLM.
- Tested on H20 only. H100/H200 have more SMs (132) but the same per-SM limits, so the same occupancy-based grid applies.
- The new test also passes on `main`. It guards the high-water-mark runner state that this launch now depends on; the bitwise comparisons above are what show that the change does not affect results.
- AI-assisted change: the analysis, harness and benchmarks were run with an AI coding assistant, and the numbers above are from those runs.
