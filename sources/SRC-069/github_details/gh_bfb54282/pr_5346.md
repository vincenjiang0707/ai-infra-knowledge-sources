## Scope

Related to https://github.com/flashinfer-ai/flashinfer/issues/3605 — this PR adds the Sampling side of the quality-fuzzing plan (contract layer, independent CPU oracle, deterministic layer, distribution layer, failure ledger). It does not redo the Norm/RoPE work or the Attention fuzzer, and speculative sampling is out of scope for this first version.

In scope: `sampling_from_probs`, `sampling_from_logits`, the individual top-k / top-p / min-p filters, the combined orderings (`top_k_first` vs `joint`), plus two production defects found while building the oracle.

Out of scope: any public API change, `chain_speculative_sampling`, CUDA-graph/compile paths.

## Implementation

Two production fixes, both about per-row filter parameters when `indices` is used:

- `TopKSamplingFromProbKernel` read `top_k_arr[bx]` and `MinPSamplingFromProbKernel` read `min_p_arr[bx]`, while the launcher validates that tensor against `probs.size(0)` (the unique-row count). Whenever `indices` reuses rows (`batch_size > unique_batch_size`) that is an out-of-bounds device read *and* the wrong row's parameter. Both now key on `row_idx`, like the top-p and joint kernels already did.
- The Python shims always materialised the per-row `top_k` tensor as `int32`, while the C++ side reads that buffer as the output `IdType`. With int64 `indices` the int32 buffer was read as int64: garbage `k` (filtering silently disabled) plus an OOB read. The buffer is now materialised in the output dtype.

The test suite is layered the way the issue plan describes:

- **Contract first**, per API, with the source line each fact was read from: retention is value-based (top-k keeps every token equal to the k-th largest value, not k tokens), top-p is strict at the boundary while min-p is inclusive at `max(p) * min_p`, `top_k_first` is *not* `joint`, `valid` differs per API (all-zero rows return `(0, False)` everywhere except `min_p_sampling_from_probs`, whose predicate accepts zeros), and the documented RNG offset advance is `ceil(increment / 4) * 4`.
- **Independent CPU oracle** that implements softmax and the filters itself and never calls the code under test; `top_k_first` and `joint` get separate references.
- **Deterministic layer**: one-hot / unique-candidate inputs must return the only legal token; the same fixed `seed`+`offset` must reproduce the documented behaviour.
- **Distribution layer** with a pre-declared budget: `K = 44` comparisons, `alpha = 0.01`, `N = 200000` trials per case, acceptance `|p_hat - p| <= sqrt(log(2K/alpha) / (2N))` (half width 0.004765). The plan was calibrated against pure reference sampling before being used on the device: 0/30 false positives, power 0.833 at 1.0x half width, 1.000 at 2.0x and at an injected 0.02 bias, 1.000 against a permuted row mapping.
- **Failure ledger**: seed/offset, input rule, filter order, thresholds, indices, reference support, observed frequencies and versions, so a failure is reproducible rather than seed-rolled away.

## Validation

FlashInfer base: `dc04f50c9aa3eabcdaa5feb0934edb3d85e9529a`
Hardware and software: NVIDIA L20 (SM89), driver 595.91.07, CUDA 12.8, torch 2.13.0+cu130, Python 3.10

```
python -m pytest -q tests/sampling/test_sampling_contract_cpu.py
# 12 passed, 0 failed
```

The int64 top-k fix measured on a released runtime, on SM120 (RTX 5090, torch
2.13.0+cu130, `flashinfer-python==0.6.18`), by applying this branch's `sampling.py`
hunk to that install and running a two-property probe on public APIs (k=1 with a
deterministic draw must be the row argmax; with k=3, all 20 draws per row must
stay inside the top-3 support):

```
stock 0.6.18     k=1  32/64 rows produce the argmax (valid=32)   k=3  640/1280 draws inside support
+ branch hunk    k=1  64/64 rows                                 k=3 1280/1280 draws
```

The CPU contract suite passes 12/12 on both sides, so it does not exercise this
path -- without the hunk half the rows sample outside their own support. The
apply/measure/restore harness is `ws/A2/run_int64_top_k_fix_check.py` with
`ws/A2/probe_int64_top_k_fix.py` in the L20 package; it restores the file it
touched and verifies the restore by hash.

GPU layer status (first live run on the L20, single GPU):

```
CUDA_VISIBLE_DEVICES=<n> FLASHINFER_SAMPLING_FUZZ_SHARD=0/4 \
  python -m pytest -q tests/sampling/test_sampling_quality_fuzz.py
# 25 failed, 3 skipped
```

Two failure classes, both stated plainly:

- the harness itself indexes a CUDA tensor with a CPU index tensor in `singular.repeat(case.calls)[rows]` — a test-side device-placement defect, being fixed;
- the first `illegal memory access` occurs in `struct/keying/top_k_int64`, i.e. the int64-indices keying scenario, after which the CUDA context poisons the remaining cases.

Attribution for the second class is now done, and it is **not** this patch: the case was run alone with `CUDA_LAUNCH_BLOCKING=1` on the patched tree and on a clean unpatched worktree of the base commit, and both report the same failure —

```
RuntimeError: Check failed: (status == cudaSuccess) is false:
TopKSamplingFromProbs failed with error code an illegal memory access was encountered
csrc/sampling.cu:225
```

So the out-of-bounds read behind that case is pre-existing upstream behaviour that neither of the two fixes above addresses; it is kept as a known-failing case rather than papered over. It is not SM89-specific: the same case (`struct/keying/top_k_int64`) faults the same way on SM120 (RTX 5090, `flashinfer-python==0.6.18`, log kept as `ws/A2/a2_fuzz_sm120_unpatched.log`), where the harness collects 88 tests and the first `illegal memory access` again surfaces at that case's teardown. Whether a main/SM90 build reproduces it is still open.

This PR is opened as a draft for that reason: the CPU contract/oracle/statistics layer is green and reviewable, the GPU layer is not yet green.

## Results and limitations

Correctness: CPU layer 12/12; the two production fixes have regression cases that fail on the base tree.
Performance: not evaluated; the suite adds no hot-path work.
Memory: not evaluated.
Limitations: GPU layer not green yet (above); per-test timeout / `--forked` isolation and the multi-GPU shard launch are not wired here.




Test and benchmark sources are retained locally; the validation results below refer to those local files.
