## Summary

Round 5 of the Kimi-K3 Stable LatentMoE front / tail projections in `flashinfer/experimental/kimi_k3_latent_moe` (#5575, tracker #4254): the prefill tail's KimiRMSNorm is fused into the persistent 2-CTA tcgen05 tail GEMM on single-wave grids, removing the separate norm launch and the programmatic-dependent hand-off (~2.5 us) on the rows where the norm can be hidden behind the shared-expert K blocks.

- Kernel protocol (generated programs `tail_gemm:tp<1|8>e<0|1>f1`): the epilogue warps of every CTA normalise latent row `bid + (w - 2) x grid` from the routed partials (same arithmetic as the standalone norm kernel, so `y` stays byte-exact), release at GPU scope, and arrive exactly once per launch on a self-wrapping `atom.inc` grid semaphore; the load warp only waits for the semaphore (bounded, then traps) and acquires before its first latent-block TMA load.  The arrival is unconditional per CTA, so trailing-wave stream-K segments without a latent block cannot stall the grid, and the counter needs no reset across eager launches and CUDA-graph replays.
- Host planner (`cake_backend.py`): `fused_norm` plan field = single-wave grid (`grid <= SMs`, `T <= 8 x grid`) and `k2_iters >= 48` shared-expert K blocks before the first latent block; today this selects TP1 `T = 256 / 512`.  Fused rows are one `tail_gemm` launch (no `tail_norm`, no PDL attribute); every other row keeps the round-4 two-launch route.  `tail_gemm_kernel_key(tp, evict, fused)`; the tail workspace gains the semaphore.
- `cake_jit.py` registries and `csrc/cake_kimi_k3_latent_moe/{sm_100a,sm_103a}` regenerated by the Cake export protocol (56 modules per arch; the TP1 weight-eviction tail GEMM `tail_gemm:tp1e1f0` is replaced by the fused-norm single launch `tail_gemm:tp1e1f1`, the other three tail GEMM variants stay `f0`; every module id changes with the producer revision).

### Security Architecture Review

**Security architecture risk:** _🟡 Moderate_ · up to `9136c`

Qualifying tail calls now coordinate normalization and GEMM work within one launch. The synchronization counter is shared by calls with the same plan, but launches are not serialized across streams. Overlapping calls could consume unfinished normalized data. The demonstrated impact is limited to callers sharing a device and plan; no cross-tenant exposure is established.

**Retained concerns**
- **Medium · security · inferred:** Concurrent fused launches with the same device and plan share a grid semaphore without launch identity or stream serialization. Interleaved arrivals can release a loader before its own normalized rows are ready, compromising output integrity and potentially propagating prior buffer contents.
