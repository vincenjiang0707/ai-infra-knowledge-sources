## Scope

Related to https://github.com/flashinfer-ai/flashinfer/issues/3978 — this PR takes the portable red-zone / canary sub-scope only: a reusable test-side helper, safe fault injection, and one real integration. It does not attempt to reproduce the original SM100 issue, and it does not build the asset-snapshot / scattered-sentinel system.

In scope: guarded allocation with an owning storage and a payload view, byte-wise guard verification with region/offset reporting, corruption injection that stays inside the owning allocation, and a real pre-allocated-output call site.
Out of scope: any new public production API, non-contiguous / overlapping-stride layouts, cross-device corruption claims.

## Implementation

- One single owning allocation per buffer: `[alignment pad 0x00][prefix guard 0xA5][payload][suffix guard 0x5A][alignment slack]`, with `payload.data_ptr() % alignment == 0` by construction and the payload a view of that same storage, so the owner cannot outlive nothing and no dangling pointer is handed to a kernel. The prefix guard sits immediately before the payload, so a store at `payload_start - 1` is inside the guard rather than in unreachable padding.
- Guards are compared as **bytes**, never through float equality — a NaN payload cannot produce a false positive — and only the two initialised guard regions are ever read back.
- Fault injection writes through views of the owner, so it can cross the payload's logical boundary but never leaves the owning allocation; `overlap` selects whether the store ends at / starts at the boundary or straddles it, and both the guard size and the payload size are checked before the write.
- Explicit rejections for non-contiguous, nonzero-storage-offset, larger-storage-alias and non-strided templates.
- Real integration: `flashinfer.silu_and_mul(x, out=buffer.payload, enable_pdl=False)` (`flashinfer/activation.py`) — an existing `out=` injection point, no production API change; exercised at `hidden=512` (16-byte vector path) and `hidden=3420` (8-byte aligned y-half, 4-element fallback).
- Stream/graph/lifetime: reset → kernel → verify has an explicit happens-before; the graph case allocates and captures at fixed addresses, resets outside the graph, and never resets after corruption to make verification pass.

## Results and limitations

Correctness: all 12 cases above pass on the L20.
Performance: the helper only exists in tests; `verify_guards()` synchronises the device, so it must never sit in a timing region or a graph capture.
Memory: no device-memory overhead outside the guarded allocations themselves.
Limitations: unchanged guards only prove that *those guarded bytes* were not written. Writes far from the payload, writes of the value already present, and write-then-restore are invisible; the alignment padding in front of the prefix guard is the one region a guarded run does not scan (the byte immediately before the payload is inside the guard); this detects nothing about arbitrary cross-device corruption. It complements, and does not replace, `compute-sanitizer --mode memcheck`.

## Follow-up (review)

- The prefix guard is now the `guard_bytes` immediately before the payload, and `_scan` reports its owner offset from there; previously a store into the alignment padding was neither armed nor compared (`A3-07` covers the byte before the payload).
- The payload offset step is `lcm(alignment, dtype.itemsize)`, so a requested alignment below the element size (`alignment=1` with float32) still yields a legal dtype view instead of an offset the view rejects (`A3-08`). Verified on CPU and CUDA over 7 alignments x 4 dtypes x 5 guard_bytes.
