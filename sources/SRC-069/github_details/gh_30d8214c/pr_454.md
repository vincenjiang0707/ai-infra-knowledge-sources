### v5
本 PR 为 SM90 新增了 NVFP4 权重 + FP8 激活的融合 MegaMoE kernel（dispatch / TMA loader / WGMMA math 三角色、live-ring 计数、interleaved 单 CTA 调度、FP4→FP8 LUT 解码），并补齐了 host 端 heuristics、buffer 布局扩展、Python API、离线量化工具和测试/benchmark。我逐项核对了 host `MegaMoEBuffer`（dispatch_num_mma_elem_bits=8 / sf_gran_k=32 / l2_sf_gran_k=16）与 kernel 手写布局、SF 索引上界、TMA box 尺寸、split-M 双 decoded-B slot 的 hazard、named barrier 配对，这些均一致无误。

但仍有若干合入前必须处理的问题：(1) dispatch warps(0-1) 与 loader warps(2-3) 位于同一 warpgroup，却分别执行 `setmaxnreg` 48 与 64，违反 PTX 对 warpgroup 内立即数一致的要求，属 UB；(2) host 断言 `num_tokens &gt; 0`，导致本地 0 token 的 rank 无法进入 kernel 参与 NVLink barrier，其余 rank 会超时死锁；(3) Python `nvfp4_mega_moe` 未校验 SymmBuffer 的 mma_type/activation/num_shared_experts，与 C++ 无条件按 fp4xfp4/swiglu/0 重切 buffer 不一致，会静默错位读写远端对称内存；(4) 已注明存在 race 的 BM64 配置仍是合法模板实例。另有精度语义（E4M3 预舍入、小 scale 组归零）需在文档中明示、smem 需求未在 host 提前计算、默认关闭 barrier 超时诊断、以 tensor 属性做布局校验易丢失等健壮性问题，以及与本功能无关的 `handle.hpp`/`generate_pyi.py` 改动建议拆分。

### v4

🔴 **critical** `deep_gemm/include/deep_gemm/impls/sm90_nvfp4_mega_moe_fused.cuh:L869`: 线程 0–63 为 dispatch warps，64–127 为两个 loader warps，四个 warp 构成同一个 warpgroup。dispatch 侧执行 `warpgroup_reg_dealloc<kNumDispatchRegisters=48>`，loader 侧（L1147/L1234）执行 `warpgroup_reg_dealloc<kNumNonEpilogueRegisters=64>`。PTX 规定 `setmaxnreg.sync.aligned` 必须由 warpgroup 内所有 warp 以相同立即数执行，否则行为未定义。SM100 版本通过 `kNumDispatchThreads % 128 == 0` / `kNumNonEpilogueThreads == 128` 规避了该问题，这里 64+64 的切分破坏了前提。建议 warp 0–3 统一使用同一寄存器数（如 64，总预算 64*128 + 208*256 = 61440 ≤ 64512 仍满足），并加 static_assert 说明。 <sub>🤖 v5</sub>
