# [PR #456] [Fix] Reject FP32 bmk,bnk->mn einsum without C instead of crashing

## 正文

## Problem

`deep_gemm.einsum('bmk,bnk->mn', a, b, d)` with an FP32 `d` and no `c` crashes the whole Python process with a segmentation fault, instead of raising an error.

For an FP32 D, `bmk_bnk_mn` only supports the accumulated expression, so `c` must be `d` itself. The check that enforces this dereferences the optional `c` without testing it first:

```cpp
// csrc/apis/einsum.hpp
if (d.scalar_type() == torch::kFloat) {
    DG_HOST_ASSERT(c->data_ptr() == d.data_ptr() and ...);   // `c` may be empty here
```

When `c` is `None`, this is undefined behavior on an empty `std::optional`. On an H200 with DeepGEMM `main` (78b6900) the process exits with SIGSEGV:

```
Thread 1 "python" received signal SIGSEGV, Segmentation fault.
#1  c10::TensorImpl::data_impl<...>
#2  c10::TensorImpl::mutable_data
#5  deep_gemm::einsum::bmk_bnk_mn (a=..., b=..., d=..., c=std::optional [no contained value]) at csrc/apis/einsum.hpp:26
```

The check runs before architecture dispatch, so SM100 is affected as well. I found this with a randomized shape fuzzer that calls the public einsum API.

## Fix

Check `c.has_value()` first, so the call fails the host assertion like any other unsupported argument. All other `->` dereferences of optional tensors under `csrc/apis/` are already guarded by a `has_value()` check.

## Test

`tests/test_einsum.py` gets `test_bmk_bnk_mn_fp32_requires_c`, which expects a `RuntimeError` for an FP32 `d` without `c`.

Results on an H200 (CUDA 13.0, PyTorch 2.11.0+cu130):

| Build | `test_bmk_bnk_mn_fp32_requires_c` |
|---|---|
| `main` (78b6900) | process killed by SIGSEGV (exit code 139) |
| this PR | `RuntimeError` from the host assertion, test passes |

The full `python tests/test_einsum.py` passes on this branch.

### v4
The change fixes a real undefined-behavior/SIGSEGV bug: `bmk_bnk_mn` for an FP32 `d` dereferenced the optional `c` before checking that it holds a value. Adding `c.has_value() and` as the first operand of the host assertion makes the condition short-circuit, so a missing `c` now throws a `DGException` (translated by pybind11 into a Python `RuntimeError`) instead of calling `data_ptr()` on an empty `std::optional`. Since `DG_HOST_ASSERT(cond)` expands to `if (not (cond)) throw DGException(...)` (csrc/utils/exception.hpp:31), the guard is effective. The fix is consistent with the existing `has_value()` guards elsewhere in `csrc/apis/`, and safe for the internal recursive FP32 call `bmk_bnk_mn(a, b, workspace, workspace)` where `c` is always set. The new test `test_bmk_bnk_mn_fp32_requires_c` covers exactly the reported public API call (`deep_gemm.einsum('bmk,bnk-&gt;mn', a, b, d)` with FP32 `d` and no `c`) and expects a `RuntimeError`, which is the correct behavior; it is also wired into `__main__`. No correctness, safety, or test-coverage issues were found, so there are no comments requiring author action.
