# [PR #2406] RAS: fix use-after-free in rasMsgHandlePeersUpdate

source: https://github.com/NVIDIA/nccl/pull/2406
state: closed | updated: 2026-09-21T01:34:07Z
labels: bug

## 正文

## Problem

`rasMsgHandlePeersUpdate()` merges a received `RAS_MSG_PEERSUPDATE` into the local peer/dead-peer tables. For every *newly* dead peer in the message, `rasDeadPeersUpdate()` calls `rasConnDisconnect()`, which terminates the connection and frees both the `rasConnection` and **all of its sockets** — including, possibly, the very socket the message is being received on.

If the message's `deadPeers` list contains the address of the peer it was received from, the handler frees its own connection/socket mid-processing and then keeps dereferencing `sock->conn`:

- reads at `src/ras/peers.cc` (`conn->lastSentPeersHash` / `lastRecvPeersHash` etc.),
- writes (`conn->lastSentDeadPeersHash = ...`),
- `rasConnEnqueueMsg()` into the freed connection's send queue.

This is a use-after-free on the RAS thread, which shares the address space of the training process, so a crash takes down the rank. Two properties make this worse than a rare race:

1. **No race is required.** The sender fully controls the `deadPeers` payload; a faulty (or malicious) peer can deterministically trigger the UAF on a neighbor by including its own address.
2. **It can be hit organically at scale.** When a peer is declared dead prematurely (e.g., a keepalive timeout false positive under load), it merges its own "death" and propagates the full `rasDeadPeers` array over its still-live links before exiting — delivering exactly the triggering message to its ring neighbors.

We originally root-caused this after a production training job crashed with a RAS thread segfault whose signature resembled the case-2 report in #1996; with this fix applied, the crash no longer reproduces.

## Root cause

```
rasMsgHandlePeersUpdate            src/ras/peers.cc   (sock->conn used after merge)
  -> rasDeadPeersUpdate            src/ras/peers.cc   (rasConnDisconnect on newly dead)
    -> rasConnDisconnect           src/ras/rasnet.cc
      -> rasConnTerminate          src/ras/rasnet.cc  (frees conn)
        -> rasSocketTerminate(..., finalize=true)     (frees every sock with sock->conn == conn)
```

Note that the event loop caller is already prepared for handlers terminating sockets (`rasSockEventLoop()` re-checks `rasPfds[].revents` after `rasMsgHandle()`), and `rasMsgHandleConnInitAck()` explicitly copies the address "because rasConnDisconnect will terminate the rasSocket" — the peers-update path was simply missing this protection.

## Evidence

AddressSanitizer, harness compiling the real `src/ras/peers.cc` + `src/ras/rasnet.cc` with stubbed socket I/O (no multi-node setup needed):

```
ERROR: AddressSanitizer: heap-use-after-free
READ of size 8 ... rasMsgHandlePeersUpdate      src/ras/peers.cc:609
freed by ... freeSockEntry                       src/ras/rasnet.cc:429
             rasSocketTerminate                  src/ras/rasnet.cc:578
             rasConnTerminate                    src/ras/rasnet.cc:345
             rasConnDisconnect                   src/ras/rasnet.cc:336
             rasDeadPeersUpdate                  src/ras/peers.cc:873
             rasMsgHandlePeersUpdate             src/ras/peers.cc:593
```

## Fix

In `rasMsgHandlePeersUpdate()`:

- save the connection and a copy of its address *before* the dead-peer merge;
- after `rasDeadPeersUpdate()`, if the sender is now in the dead set, drop the connection reference (otherwise re-validate it with `rasConnFind()`), so the freed connection/socket is never touched again;
- newly learned dead peers are still propagated to the remaining RAS links (`rasNetUpdatePeers(..., fromConn=nullptr)`), so dead-peer dissemination is not delayed.

The normal path (sender not in the dead set) is byte-for-byte behaviorally unchanged.

## Testing

- ASan reproducer, "self" mode (dead peer == sender): heap-use-after-free before the fix; clean pass after.
- ASan reproducer, "other" mode (dead peer is a third party): passes before and after — no regression on the normal path.
- File formatted with clang-format 22 per the repo's `.clang-format`; `maint/run-clang-format.sh --diff` reports no changes.
