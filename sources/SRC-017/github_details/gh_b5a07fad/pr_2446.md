# [PR #2446] Avoid ptxas 12.8-13.0 miscompile of add4G on sm_120

source: https://github.com/NVIDIA/nccl/pull/2446
state: open | updated: 2026-09-24T20:06:04Z

## 正文

### Description

fp8 sum AllReduce over symmetric memory crashes with an illegal memory access on sm_120 (RTX 5070 Ti) when NCCL is built with CUDA 12.8, 12.9 or 13.0. compute-sanitizer points at the epoch store in `~ncclLLA2ASession()` (`ll_a2a__funcs.h:33`) inside `ncclSymkDevKernel_AllReduce_AGxLL_R_sum_f8e4m3`. The PTX for that store is fine, but ptxas from those CUDA versions builds the address with its upper 32 bits replaced by zero (a lone 32-bit `ULEA` for the `+ handle*128` step and `URZ` used as the high dword in the following `ULEA.HI.X`). ptxas 13.1 and later assemble the same PTX correctly, and sm_90/sm_100 are fine with 12.9 too. Details are in issue #2445.

It is not only fp8. Scanning the sm_120 SASS of all symmetric kernels for that signature finds 23 kernel functions on master: the fp8 sum AGxLL_R kernels, the `_profile` variants of the half/bf16 AllReduce LL and ReduceScatter LL kernels (so with a profiler plugin active, half sum all_reduce and half/fp8 reduce_scatter crash here too, checked), and the LLMC variants (not reachable on sm_120). With this change the scan finds none.

The address comes from `add4G()` in `nccl_device/utility.h`, which adds a multiple of 4 GB by bumping the upper half of the pointer through a union. This change replaces that type-pun with plain 64-bit integer arithmetic. The front end then emits a normal `shl.b64`/`add.s64` chain and ptxas 12.8-13.0 keep the high dword, so the crashes are gone. The union pun also reads an inactive union member, which is not something C++ guarantees anyway.

To be clear about what this is: it works around a compiler bug by not producing the pattern that triggers it. With those ptxas versions the `+ handle*128` add still has no carry-out, so the result is only right as long as the resource window does not straddle a 4 GB virtual address boundary. That holds for NCCL's own device comm (the resource window is placed first in the LSA reservation and is a few MB), it is not a guarantee for arbitrary window placement. People on CUDA 13.1+ get fully correct code either way.

### Changes & Impact

One function in `src/include/nccl_device/utility.h`. The header is part of the public device API, so user device code that calls the LSA pointer helpers gets the same treatment. The host-only twin in `src/include/bitops.h` is left alone since it is only used from `dev_runtime.cc` on the host.

Tested here with CUDA 12.9.86 on an RTX 5070 Ti with two ranks on the one GPU (`NCCL_MULTI_RANK_GPU_ENABLE=1`, `NCCL_TESTS_DEVICE=0`, nccl-tests `-R 2`), against a build of the same commit without the change: fp8 e4m3/e5m2 sum all_reduce goes from crashing at the first size to passing with 0 wrong values over 8 B to 32 MB; with the example profiler plugin loaded, half all_reduce, half reduce_scatter and fp8 reduce_scatter go from crashing to passing. half/bf16/float/int8 sum, fp8 prod/max, fp8 all_gather and reduce_scatter, `-R 1`, and the regular (non symmetric) `all_reduce_perf -g 2 -c 1` across the 5070 Ti and an RTX 2070 pass before and after. SASS of the fp8 kernel checked for sm_90, sm_100 and sm_120: correct 64-bit address arithmetic with the change; that kernel keeps 128 registers and no stack, other symmetric kernels move by a few registers or spill bytes in both directions. Not tested: real multi-GPU sm_120 hosts, sm_90/sm_100 hardware, CUDA 13.x builds (only the ptxas binaries were checked on the saved PTX), Windows.

### Performance Impact

None expected. The generated code for the address is a 64-bit add either way; register usage of the affected fp8 kernel is unchanged.
