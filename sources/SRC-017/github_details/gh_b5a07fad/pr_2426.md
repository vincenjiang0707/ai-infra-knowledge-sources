# [PR #2426] Reuse empty hunks in ncclMemoryStack

source: https://github.com/NVIDIA/nccl/pull/2426
state: open | updated: 2026-09-21T01:24:07Z
labels: 

## 正文

## Description

`ncclMemoryStack::allocateSpilled()` can lose a hunk. When it has to malloc a new hunk it sets `top1->above = nullptr` and then `top->above = top1`. If an empty hunk from a popped frame is already sitting above the current one, that pointer was the only reference to it, so the hunk is never reused and `ncclMemoryStackDestruct()` never frees it.

You get there when the object is bigger than the hunk above (so it would not fit a new hunk either) and the 16 byte Unhunk proxy does not fit in the current hunk, either because it is full or because the stack was popped back to the stub. A group that repeats the same allocation pattern loses one hunk every time.

With this change the code steps into the hunk that is already waiting above and puts the proxy there. It only mallocs a new hunk when there is none.

## Related Issues

Fixes #2324. #2328 from the issue author does the same thing in behaviour, this one is a smaller diff (no second copy of the code that enters a hunk). I am fine with either going in, I mostly wanted to add a reproducer since the issue had none.

## Changes & Impact

`src/misc/utils.cc` only, the new-hunk branch of `allocateSpilled()`. No API or ABI change.

I wrote a small standalone program that builds against the real `utils.cc` with ASAN. On master it loses a hunk when the stack was popped back to the stub, loses one with a full hunk and an empty one above, and leaks 100 hunks (13 MB) when that second case is repeated 100 times. With the change nothing is lost and the chain stays at 2 hunks. I can attach the program if useful. nccl-tests (all_reduce, alltoall, sendrecv, CUDA graphs, one and two GPUs, mpirun -np 2) pass with the patched library. I did not manage to hit the condition from a real communicator, it needs the current hunk to be full to the last few bytes exactly when a very large object arrives, so in practice this is a rare leak.

## Performance Impact

None. The change is in the slow path that mallocs a new hunk, and it saves a malloc there.
