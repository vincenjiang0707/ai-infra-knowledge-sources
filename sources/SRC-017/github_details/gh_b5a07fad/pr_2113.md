# [PR #2113] Correct crossing multi-sockets bandwith of AMD Zen5/Turin CPUs

## 正文

## Description

This PR adds support for AMD Zen5/Turin CPUs in NCCL topology detection.The latest AMD Turin CPUs are interconnected via XGMI links with bandwidth ranging from 192-256 GB/s. However, the current NCCL codebase defines AMD_BW as only 16.0 GB, which significantly underestimates the actual bandwidth of Turin CPUs. This low bandwidth configuration causes the topology graph search to terminate prematurely, resulting in suboptimal channel configurations that cannot fully utilize the system's capabilities.

## Related Issues

N/A.

## Changes & Impact

Add detection for AMD Zen5/Turin CPUs during topology discovery and configure appropriate inter-CPU interconnect bandwidth.

## Performance Impact

In our test environment, we have 2 servers, each with 2 Zen5/Turin CPUs. Each CPU is connected to 1 NIC and 4 NVIDIA GPUs. Without this patch, the topology discovery could only create 1 channel using a single RDMA device. With this patch, the topology discovery identifies 2 channels, each configured with a different RDMA device, resulting in 2x improvement in allreduce performance.

Hi @marksantesson , thanks for pointing this out.

Sorry, I missed PR #2036 when preparing this PR. I agree that the main intent is the same: both changes try to make NCCL use a more reasonable inter-socket bandwidth on modern AMD platforms, instead of the old flat `AMD_BW` value. I also agree that `NCCL_TOPO_CPU_MODEL_AMD_ZEN5` in #2036 corresponds to what I called `NCCL_TOPO_CPU_MODEL_AMD_TURIN`, so the CPU model detection part is already covered by #2036.


The remaining question is the bandwidth value. From #2036, my understanding is that `AMD_ZEN5_BW = 32.0` was derived from measured cross-socket GPU P2P bandwidth on one Turin platform. I also noticed that the follow-up PR #2127 from the same author changes the Zen5 value again to `40.0`. So this value seems to be a platform-/measurement-dependent effective bandwidth for NCCL topology search, rather than a fixed architectural xGMI bandwidth for all Zen5/Turin systems. @voipmonitor, since you authored both #2036 and #2127, please correct me if I misunderstood the rationale behind those values.

The `192 GB/s` value in my PR came from my understanding of the platform xGMI link capability, not from a direct NCCL P2P benchmark. AMD’s official “AMD EPYC 9005 Processor Architecture Overview”[1] says that in dual-socket configurations, two EPYC 9005 SoCs are connected via xGMI links, and system manufacturers may use either 3 or 4 xGMI/Infinity Fabric links depending on I/O, bandwidth, and system design goals. The same document describes each xGMI/G-link as up to 16 lanes at up to 32 Gbps. Therefore, a 3-link configuration gives `3 * 16 * 32 / 8 = 192 GB/s` nominal aggregate socket-to-socket bandwidth, while a 4-link configuration gives 256 GB/s.

I should clarify that our actual CPU is AMD EPYC 9A75, not one of the public EPYC 9005 SKUs listed in that document. However, it appears to be a Turin/Zen5 part: the CPU is reported as Family 26 / Model 2, which matches the Turin/Zen5 family used by #2036. The public EPYC 9005 document may not describe this exact SKU, but according to the platform information we have, the two CPUs are connected by 3 xGMI links, each at 64 GB/s, for 192 GB/s aggregate CPU-to-CPU bandwidth. So I’m using the EPYC 9005 architecture document as the closest official architectural reference for the Turin xGMI mechanism, and the 3 * 64 GB/s configuration comes from our platform information.

[1] https://docs.amd.com/v/u/en-US/58462_amd-epyc-9005-tg-architecture-overview

> Other than that, I think all the elements of your change have been incorporated. Does that look right?

Yes, that looks right. Since we only had access to our Zen5/Turin platform and did not have enough information for older AMD platforms, my PR only handled the Zen5/Turin case and left older AMD CPUs on the original `AMD_BW` path.

BTW, I tested the changes from #2036 locally, and they do solve the issue I’m currently seeing. The only remaining point that may still need discussion is the appropriate inter-socket bandwidth value for Zen5/Turin platforms.

In any case, the current code on the dev branch already addresses my immediate problem. Could you share when this dev-branch change is expected to be released, and in which NCCL version? I would really appreciate that information.

> @hz-cheng , regarding the appropriate inter-cpu bandwidth, I think the 3-link case is empirically demonstrated to be 32 (as per comment [here](https://github.com/NVIDIA/nccl/pull/2036#issuecomment-4162054390)). (I'm assuming that was 3-link due to some circumstantial evidence.) 


Hi @marksantesson, thanks for the explanation.

One thing I’d like to clarify is that the ~32 GB/s number from #2036 seems to be the effective bandwidth of the full GPU-to-GPU path exercised by the NCCL benchmark, rather than the inter-CPU bus bandwidth itself. That path includes the GPU PCIe links, PCIe host bridges/root complexes, the inter-socket link, and NCCL transport/protocol overhead. So I’m not sure it is rigorous to use that end-to-end GPU P2P/NCCL bandwidth directly as the CPU-to-CPU link bandwidth in the topology model.

To cross-check this, I ran the open-source STREAM benchmark on our machine with NUMA binding. The GPUs on this system are PCIe Gen5 x16, and GPU0/GPU1 NCCL `gather_perf` reaches about 45.8 GB/s busBw, which looks like the GPU/PCIe P2P effective bandwidth range. In contrast, STREAM remote NUMA memory bandwidth is much higher:

```bash
# Built from the official STREAM benchmark source:
# https://www.cs.virginia.edu/stream/FTP/Code/stream.c
gcc -O3 -fopenmp -mcmodel=medium \
  -DSTREAM_ARRAY_SIZE=350000000 -DNTIMES=10 \
  -o /tmp/stream_350m /tmp/stream.c

OMP_NUM_THREADS=64 OMP_PROC_BIND=true \
numactl --cpunodebind=0 --membind=1 /tmp/stream_350m

OMP_NUM_THREADS=64 OMP_PROC_BIND=true \
numactl --cpunodebind=1 --membind=0 /tmp/stream_350m
```
Results:
```
node0 CPUs -> node1 memory:
Copy:   149.2 GB/s
Triad:  110.3 GB/s

node1 CPUs -> node0 memory:
Copy:   148.6 GB/s
Triad:  109.8 GB/s
```
So at least on our platform, the CPU inter-socket effective bandwidth appears to be much higher than the 30-40 GB/s range observed by GPU P2P/NCCL benchmarks. This makes me think the GPU P2P result may be PCIe/P2P-path limited, rather than xGMI-link limited.
