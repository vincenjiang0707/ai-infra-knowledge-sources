# B — Explicit LDMC targets

Fixes #2420. Explicit command-line, environment, or pre-included Makefile `NVCC_GENCODE` now controls LDMC FP8 compilation as well. Capture whether the target was supplied before including `common.mk`, and retain toolkit-dependent architecture-specific defaults only when no target was supplied. No generator or target-list parser changes.

## Send/recv follow-up (2026-09-20)

The earlier -6.02% aggregate is not a reproduced causal regression. Retaining every original sample, the independent quartets disagree:

| Quartet | Baseline geometric mean µs | Patch geometric mean µs | Speed change |
|---|---:|---:|---:|
| APPA | 917.883 | 1039.982 | -11.74% |
| PAAP | 917.479 | 916.860 | +0.07% |

One patch process measured 1185.101 µs; the other seven processes measured 912.634–921.327 µs. The slow process is retained. Two quartets cannot establish stable improvement, equivalence, or a repeatable regression.

The existing baseline and patch `sendrecv.cu.o` SASS dumps are identical. Host `collectives.o` disassembly differs only in the object filename heading. Follow-up disassembly of the final shared libraries also found identical instruction streams for both `ncclDevKernel_SendRecv` and `ncclDevFunc_SendRecv` on SM89. Both library SHA256 values match the original campaign. This rules out changed instructions in those two GPU functions; it does not explain the slow process or prove equivalent end-to-end timing. No speculative production-code change was made.

The common harness now has an opt-in `perf` mode: 20 warmups, 200 measured iterations, one default-configuration measurement per operation, and the existing exact output checks outside timing. Legacy correctness/trace mode is preserved. `tests/run_b_retest.sh` runs eight APPA/PAAP quartets and refuses selected GPUs with resident compute processes. `tests/summarize_b_retest.py` retains every sample and emits per-quartet and aggregate Markdown tables only for a complete campaign. Formula, blocked-campaign and incomplete-operation checks passed locally. The SM89 retest executable compiled successfully. Its GPU-occupancy gate returned `BLOCKED_BUSY` before launching GPU work.

All eight L20 GPUs had other compute processes during this follow-up. No clean performance rerun has completed, and no performance fix or stable speedup is claimed. Git transport failed, but the GitHub API independently confirmed that current upstream remains `12df1a11afad322be5a204a2db890161cbf8131d`; no rebase changes are needed.

## Explicit Makefile target correction (2026-09-20)

The first revision checked `origin NVCC_GENCODE` after including `common.mk`. A caller-supplied Makefile assignment was therefore indistinguishable from a default assignment: requesting SM89 still selected SM100a for LDMC on CUDA 12.8. Capture the origin before including the defaults to respect that explicit target too.

| Check | Before | After |
|---|---|---|
| Pre-included Makefile requests SM89, CUDA 12.8 configuration | LDMC incorrectly selects SM100a | LDMC selects SM89 |
| Default, CLI, environment, Makefile × CUDA 12.6/12.8/12.9/13.0 configuration | Makefile override fails | 16/16 PASS |
| CUDA 12.8 native compilation, Makefile SM89 override, normal/profile LDMC units | — | 2/2 PASS; only SM89 cubins |

The 16-case matrix evaluates Make configuration with explicit version values; it is not compilation with four installed CUDA toolkits. This fixes build-target selection and makes no runtime speedup claim. Previous timing measurements apply to the previous revision; this follow-up changes Makefile-defined target selection.

## Runtime-speed investigation (2026-09-20 10:53–10:57)

No runtime performance fix is claimed. A send/recv-only harness preserves exact correctness checking and runs 20 warmups plus 200 measured iterations. The libraries are the same SHA256-verified runtime artifacts as the earlier experiments; the subsequent Makefile-origin correction does not change their explicit command-line compilation flags.

Nsight recorded 440 SendRecv kernel launches per arm. The baseline launch API median was 4.165 µs and the patch median 4.377 µs. GPU kernel duration medians were 1162.717 and 896.409 µs, but maxima reached 17.706 and 32.837 ms. Stream synchronization dominated CUDA API time. These whole-process profiling aggregates include warmup and initialization; they are not a timed-window speed comparison.

Without profiling, four fresh executions of the identical baseline measured 3145.249, 3134.999, 3142.637, and 3135.624 µs. The following APPA/PAAP pair then crossed from approximately 3.15 ms to approximately 0.91 ms mid-campaign:

| Diagnostic quartet | Baseline µs | Patch µs | Speed change |
|---|---:|---:|---:|
| 0 | 2671.115 | 3150.783 | -15.22% |
| 1 | 914.289 | 908.654 | +0.62% |

Both quartets are shared-host diagnostics, not clean performance validation. All 14 runs (two profiled, four baseline-only, eight alternating) passed send/recv exact correctness. All samples are retained, including the transition. The direction and magnitude of the difference depend on the changing execution conditions, so these results cannot establish a B-specific slowdown, equivalence, or speedup. The measured code does not justify a speculative SendRecv implementation patch. An idle two-GPU allocation is required to continue causal performance validation.

## Contention correlation audit

The saved GPU process snapshots show two additional foreign compute processes (PIDs 2367650 and 2367651 on GPUs 4 and 5) during the slow quartet. Both are absent before the fast quartet, while the other resident processes remain. No foreign processes were stopped by this task. The intermediate baseline run crosses the transition; snapshots are taken before runs, so their exact exit times are not established.

| Run | Arm | Send/recv µs | Extra GPU 4/5 processes present |
|---|---|---:|---|
| 0-0 | base | 3136.916 | Yes |
| 0-1 | patch | 3153.880 | Yes |
| 0-2 | patch | 3147.689 | Yes |
| 0-3 | base | 2274.481 | Yes |

| 1-1 | base | 915.707 | No |

This is evidence of a changed GPU-sharing condition correlated with the timing shift. It strengthens the interference explanation, but is not a controlled causal experiment and does not prove B is performance-neutral. Neither quartet should be used as a clean speedup/regression verdict. The idle-device preflight remains required for formal retesting.
