# [PR #2436] [Fix] dev_runtime: size GIN signal shadows by the allocated context count

state: open | updated: 2026-09-22T03:28:02Z

## 正文

## Problem

`ncclGinDevCommSetup()` rounds the GIN context count up to a multiple of the backend's GIN connection count and publishes the rounded value in `devComm->ginContextCount` (`gin_host.cc`, since 2.31.2). The device indexes the per-context signal shadows with it:

```c
gin->_signalShadows = comm.ginSignalShadows + contextIndex * comm.ginSignalCount;   // gin__funcs.h
```

But `ncclDevrCommCreateInternal()` sizes the shadow region in the resource window before GIN setup runs, using the requested count:

```c
int nGinContexts = reqs->ginContextCount;
...
bufSizeTotal += nGinContexts * ginSignalTotal * sizeof(uint64_t); // include signal shadows
```

Whenever the connection count does not divide the requested context count, contexts in `[requested, rounded)` index past the end of the shadow region. Examples: the default 4 contexts with 3 GIN connections (3 local GIN NICs, `NCCL_GIN_NCONNECTIONS=3`, or `NCCL_GIN_PROXY_NTHREADS=3`) rounds to 6; 1 context with 2 NICs rounds to 2.

NCCL's own device code reaches those contexts:
- `ncclGinBarrierSession` with `ncclGinAllContexts` does `++*shadowPtr` for every context up to `comm.ginContextCount`.
- The symmetric GIN AllGather/ReduceScatter kernels use `blockIdx.x % comm.ginContextCount`.

The overflow is `(rounded - requested) * ginSignalTotal * 8` bytes past the shadow region. It is silent when it lands in the granularity padding of the resource window, and otherwise writes into the next allocation in the symmetric VA space or faults.

## Fix

Compute the shadow size after `ncclGinDevCommSetup()`, using `outDevComm->ginContextCount`. When GIN is not requested, the size is computed exactly as before.

## Testing

I don't have GPUDirect RDMA-capable hardware, so this is verified by code inspection and I could not run it with GIN enabled. Regression testing of the non-GIN paths through the same function, on H200 (both builds from the same tree):
- `docs/examples/06_device_api/01_allreduce_lsa`: PASSED on master and with this PR.
- nccl-tests `all_reduce/all_gather/reduce_scatter_perf -R 2 -c 1` (symmetric kernels, e.g. `AllReduce_RSxLD_AGxST`, which create an internal devComm with a resource window): 0 errors on master and with this PR.

A GIN-enabled run with a context count that the GIN connection count doesn't divide (e.g. `NCCL_GIN_NCONNECTIONS=3`, `ginContextCount=4`, `ncclGinAllContexts` barrier), under compute-sanitizer, would exercise the fixed path directly.
