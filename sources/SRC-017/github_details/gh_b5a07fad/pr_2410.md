# [PR #2410] enqueue: clamp NCCL_CHUNK_SIZE to the P2P step size

source: https://github.com/NVIDIA/nccl/pull/2410
state: closed | updated: 2026-09-24T17:28:25Z
labels: resolved

## 正文

## Description

Fixes wrong ncclSend/ncclRecv data and GPU memory faults when NCCL_CHUNK_SIZE is set larger than the P2P step size.

The P2P kernels move one chunk per step into a buffer slot that is stepSize bytes (comm->p2pChunkSize for the simple protocol, the LL buffer divided by NCCL_STEPS for LL). addP2pToPlan applies NCCL_CHUNK_SIZE to the chunk without checking it against that step, so a larger value makes the kernel write past its slot: it overwrites the neighbouring slots that are still in flight (wrong values) and, from the last slot, runs past the end of the buffer (illegal memory access, or an Xid 31 read fault on a GPUDirect registered network buffer). On a socket network the receiver posts a step sized receive and the sender ships the chunk, so the plugin logs "message truncated" and the kernel waits forever.

This clamps the chunk to the step size and prints a warning once (simple protocol only, the LL clamp never changes anything in practice), saying which variables actually raise the step (NCCL_BUFFSIZE together with NCCL_P2P_NET_CHUNKSIZE / NCCL_P2P_PCI_CHUNKSIZE / NCCL_P2P_NVL_CHUNKSIZE). That is the same thing computeBuffSizes already does silently for p2pChunkSize itself. While at it, values at or below zero are ignored and the chunk gets a 16 byte floor: a negative value used to encode to a huge chunk and NCCL_CHUNK_SIZE=1 crashed with a division by zero on the LL path.

## Related Issues

Fixes #2408. Same symptom as the older #1496.

## Changes & Impact

One block in src/enqueue/enqueue.cc (addP2pToPlan), 12 added lines, 2 changed. Only NCCL_CHUNK_SIZE users are affected. Values up to the step size behave as before. Values above it now get the step size plus one warning per process instead of corrupt data. That includes values that happened to work on PCIe/SHM systems because the physical slot there (buffer / NCCL_STEPS) is bigger than the step; those users will see a smaller chunk than before (about 12% less send/recv bandwidth for 256K on my PCIe host) and the warning tells them how to get a bigger one properly.

Tested on one host with two GPUs (RTX 5070 Ti and RTX 2070, no P2P, SHM transport, and NET/Socket with P2P and SHM disabled) with a small two rank send/recv program that checks every byte: without the patch a 1 MiB chunk over the 128 KiB step gives an illegal memory access on SHM, any chunk above the step hangs on NET/Socket after the "message truncated" warning, and two ranks on one GPU with a 4 MiB chunk get wrong bytes. With the patch all cases pass, and sendrecv_perf / alltoall_perf -g 2 -c 1 with NCCL_CHUNK_SIZE=1M, 256K and unset report 0 wrong values. Built with WERROR=1. I could not test IB/RoCE with GPUDirect (the reporter's setup), NVLink or multi node.

Out of scope: making bigger chunks actually work (bigger buffers / steps, what the reporter really wants for bandwidth) is a design change; and the docs still describe NCCL_CHUNK_SIZE as a bandwidth knob (happy to add a sentence about the clamp to performance_and_tuning.rst if you want it in this PR).

## Performance Impact

None on the data path. One extra comparison per P2P task at plan time. Users who set NCCL_CHUNK_SIZE above the step size get the step sized chunk, which is what the buffers can carry anyway.

### sjeaugey · 2026-09-15

The NCCL_CHUNK_SIZE environment variables is only there to help developers try different tuning when optimizing a new platform. It's not supposed to be set by users, and there was never any guarantee that you could use any value. NCCL_P2P_NET_CHUNKSIZE is documented, but in the "debugging" section, i.e. use at your own risk.

So I'm not sure I'd want to merge this PR, given it makes an already complex piece of code even harder to read and understand, for an unclear benefit.
