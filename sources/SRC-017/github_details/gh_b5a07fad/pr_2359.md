## 正文

## Summary

Adds opt-in ProxyOp/ProxyStep tracking to the NCCL Inspector profiler plugin. Related to #2239.

Rebased the original eight implementation commits onto `dev` (`62d10969`), preserving that breakdown and adding review fixes and a documentation correction.

- Enable JSON-only tracking with `NCCL_INSPECTOR_ENABLE_PROXY=1`; Prometheus/OTLP do not arm Proxy callbacks or allocate Proxy pools.
- Use fixed-capacity active pools and a bounded per-communicator completed ring. Defaults: 1,024 active Ops, 4,096 active Steps, and **1,024 completed Proxy records**.
- Maintain the Op self-reference plus active-child references, snapshot parent correlation at Op start, and emit pointer-free completed records. Preserve first state callbacks and observed-byte aggregation.
- Add `NCCL_INSPECTOR_DUMP_PROXY_STEPS=0` for **Op-only output**. Step callbacks, pools, lifetime references, and Op byte/count aggregation remain active; only completed Step record construction, ring insertion, and output are suppressed.
- Emit **JSON v4.3**: header/metadata appear once in the communicator's `dump_stats` marker, followed by its counted Coll/P2P/Proxy payload records under one output lock. This affects JSON even with Proxy disabled. Both bundled analysis readers are adapted and retain older-format support. Current `dev` already uses v4.2.
- Reuse the ring's `dropped`/`droppedReported` accounting. Report `proxy_records`, `proxy_dropped_total`, and `proxy_dropped_since_last_dump` once per dump, including stats-only windows.
- Count failed Op allocations separately (`proxy_ops_dropped_*`) and reserve sequence numbers before allocation. Emit `n_steps_started` alongside completed/dropped Step counts. Pool warnings are one-shot and include allocation/capacity counts.
- Cache PID at initialization, remove redundant per-record `origin_pid`, and count foreign-PID PXN skips separately without dereferencing the foreign parent **or context**. `proxy_pxn_skipped_process_total` is process-scoped, repeated in communicator markers; aggregate by hostname/PID using max/latest, not a sum across markers.
- Address helper naming, function signature formatting, read-only parent locks, state-dispatch helpers, unreachable stopped checks, and documented/enforced backend → Proxy enablement → pool-sizing order. Preserve `NCCL_INSPECTOR_PROM_DUMP_STATS` parsing from `dev`.

`trans_size_bytes` means bytes observed by tracked Steps. Dropped Steps or missing transfer-size callbacks can undercount; `n_steps * chunk_size_bytes` cannot reconstruct missing bytes. Proxy timestamps are CPU callback timestamps, not GPU execution timing.

## Testing

The following validation was completed on a separate GPU server for the review-fix revision. GPU runs used a single node with four GPUs and `NCCL_INSPECTOR_REQUIRE_KERNEL_TIMING=0`; the default value of `1` has not yet been specifically validated. No macOS compatibility shims, CUDA stubs, or host-only test infrastructure are included in this PR.

### Performance comparison

Forced Socket transport, four GPUs, message sizes from 1 MiB to 16 MiB. Each mode was run three times; values below are medians. All correctness checks passed, with zero dropped records.

| Mode | Bandwidth (GB/s) | Total elapsed time (s) | JSON size (MB) |
| --- | ---: | ---: | ---: |
| Proxy disabled | 4.523 | 2.616 | 0.624 |
| Full Op + Step output | 4.467 | 2.666 | 28.245 |
| Op-only output | 4.569 | 2.717 | 2.985 |

Op-only output reduced JSON volume by approximately **89.4%** relative to full output. Bandwidth differences were small and subject to run-to-run variation; these measurements do **not** establish a consistent performance improvement or regression. This compares output modes on the review-fix revision, not before/after revisions.

### Documentation correction

Clarified that `NCCL_INSPECTOR_DUMP_THREAD_INTERVAL_MICROSECONDS=-1` (the default) disables the internal dump thread entirely and produces no output. There is no teardown/finalization dump path; the earlier README promise was incorrect, and the observed absence of JSON and `dump_stats` records is expected behavior, not a regression from this PR. The usage introduction now explicitly requires a non-negative interval to obtain output. The environment-variable help text and communication-pattern example were corrected as well. No runtime logic was changed.

### Not yet validated / limitations

- Default kernel-timing filtering (`NCCL_INSPECTOR_REQUIRE_KERNEL_TIMING=1`): not specifically validated; these runs used `0`.

### rishdas · 2026-09-08

@LYAccc On the **Known issue — not yet fixed** item: that one is a documentation bug rather than a code bug, so please don't spend time chasing a runtime fix.

`-1` was only ever intended to mean "do not dump periodically". The clause promising output *at communicator teardown/finalization* was documented in error — that path has never existed. The code is behaving exactly as designed:

- `inspectorStartDumpThread()` returns early when `intervalUsecs < 0` and never constructs `dumper`:
  ```c
  static inspectorResult_t inspectorStartDumpThread(int64_t intervalUsecs) {
    if (intervalUsecs < 0) {
      INFO_INSPECTOR("NCCL Inspector: dump thread disabled "
                     "(interval is -1); not starting internal dump thread.");
      return inspectorSuccess;
    }
  ```
- the only two call sites of `inspectorCommInfoListDump()` are inside the dump thread's own dump routine (`inspector.cc:690-691`), so with no thread there is no writer;
- `inspectorGlobalFinalize()` only stops and deletes the dumper — it performs no final flush.

So "zero JSON records and zero `dump_stats` records" with `-1` is correct behavior, and it is not a regression from this PR. What needs fixing is the README sentence that describes the non-existent teardown dump. Something like:

```suggestion
- `NCCL_INSPECTOR_DUMP_THREAD_INTERVAL_MICROSECONDS=<interval>` (default: `-1`)
  Sets the interval (in microseconds) for the internal dump thread to write output. A value of `-1` (default) disables the internal dump thread entirely, so no output is written; set a non-negative value to obtain output. A value of `0` enables continuous dumping (dumps as fast as possible). Set to a positive value to enable periodic dumps at the specified interval (e.g., `500` for every 500 µs). When Prometheus mode is enabled (`NCCL_INSPECTOR_PROM_DUMP=1`), a minimum of `30000000` (30 seconds) is enforced to align with the node exporter polling interval.
```

Two follow-ups worth folding in while you are there:

1. Please drop the "Known issue — not yet fixed" section from the PR description and note the README correction instead, so the fix isn't blocked waiting on a phantom bug.
2. Since `-1` is the default and produces no output at all, the docs should say so plainly up front. Every worked example in the README sets an explicit interval, which is why this has gone unnoticed; a reader taking the default gets silence. Calling that out in the Quick Start would save the next person the same investigation.

Thanks for digging into it and reporting it clearly either way — the write-up is what made it quick to pin down.

### rishdas · 2026-09-04 · CHANGES_REQUESTED

Thanks for this — the ProxyOp/ProxyStep correlation design is sound and the lifetime handling is careful. I built it standalone and ran it on 4x GB200 over a forced Socket NET path to exercise the proxy events, and the core mechanism holds up well:

- Correlation is exact across **3,680 ProxyOps / 35,328 ProxySteps**: zero byte-total mismatches and zero step-count mismatches between op and step records.
- All 10 trace timestamps are populated on 100% of records in both directions, with plausible durations.
- Ring drop accounting is exact on all 4 ranks, and step-pool exhaustion is attributed to the correct op.
- Clean build under `-Wall -Wextra`, and the default-off path is unchanged.
- The JSON-only gate for Prometheus/OTEL works and warns rather than silently misbehaving, and the fact that `NCCL_INSPECTOR_POOL_GROW` does not apply to the proxy pools is already documented. Both appreciated.

My comments fall into three groups.

**1. Please retarget to `dev`.** This is against `master`, but the Inspector has moved on `dev` — #2304 (`ae9733378 profiler/inspector: report ring buffer drops`) landed there and overlaps this PR directly. I rebased all 8 commits onto `dev` to review them and hit exactly three real conflicts, all tractable:

- `inspector_json.cc` — #2304 restructured `inspectorCommInfoDump` around the new `dump_stats` record. Watch the early-return path: as written, a comm with only proxy traffic and no coll/p2p records returns before proxy records are emitted.
- `inspector.cc` — #2304 added `NCCL_INSPECTOR_PROM_DUMP_STATS` parsing at the old Prometheus site, so that parse has to travel with your relocation into `initOutputBackendFromEnv()`.
- `README.md` — trivial.

`inspector.h`, `inspector_event_pool.{cc,h}` and `inspector_plugin.cc` all apply cleanly.

**2. Blocking, and mostly a consequence of that overlap.** The format version is the important one: `dev` already ships `v4.1` meaning "a `dump_stats` record exists", and this PR independently bumps to `v4.1` meaning "proxy records exist". Shipping two incompatible `v4.1` formats leaves consumers no way to tell them apart. Related: the manual drop detection here duplicates the `ring->dropped` accounting `dev` now maintains, and the per-record `proxy_records_dropped` field belongs in `dump_stats` alongside the existing `coll_*`/`p2p_*` counters.

The other blocking item is independent of the rebase: **ProxyOp-pool exhaustion is silent data loss.** When `inspectorEventPoolAllocProxyOp()` returns null the op vanishes with no counter, and because `proxyOpSn` is assigned only after a successful allocation it doesn't even leave a sequence-number gap. With `NCCL_INSPECTOR_PROXY_OP_POOL_SIZE=16` I measured 858 failed allocations against 200 emitted records, with nothing in the JSON indicating loss. Same shape as the cross-process PXN skip. Given #2304 landed specifically to stop the Inspector losing records quietly, these should be counted and surfaced.

**3. Overhead, which is worth a design conversation rather than a fix.** On `all_reduce_perf -b 1M -e 16M -f 2 -g 4 -w 2 -n 20`, enabling proxy tracking took output from 882 KB to 35.7 MB (**40x**) and busbw from 0.621 to 0.524 GB/s (**-15.6%**). 98% of the file is proxy records and 31.4% of those bytes are header/metadata repeated on every record. It's opt-in so it isn't a blocker, but anyone enabling it at scale will notice immediately. Emitting `header`/`metadata` once per dump, and letting op records be enabled without step records, would recover most of it cheaply.

That last point is also why I'd push back gently on my own earlier request for per-step exec time and bandwidth — those add fields to records that are already the dominant cost. If they go in, they should be labelled as CPU proxy-thread timing so nobody compares them against the GPU-derived `coll_exec_time_us`.

Nothing I found is a correctness bug in the proxy state machine itself; I went looking for a use-after-free around the refcount and pool release and there isn't one. The blocking items are all about the `dev` overlap and about loss being observable.

Re-reviewed at `3254c695b`. Thanks for turning this around so thoroughly — every blocking item from the last pass is genuinely fixed, and I verified them in the code rather than taking the replies at face value: `v4.3` clears the version collision, the manual overflow check is gone in favour of the ring's own counters, drop reporting moved into `dump_stats`, `proxy_ops_dropped_*` now makes Op-pool loss visible (with sequence numbers reserved *before* allocation, which closes the gap-analysis hole), and both pool warnings are one-shot. I also re-ran the validation matrix against your revision on a 4xGB200 node, grafting this PR's `plugins/profiler/inspector/` onto our internal `dev` (the PR touches only that directory) and forcing the socket transport so Proxy events actually fire. 14 cells, all pass:

|---|---|
| default off | `v4.3`, zero proxy records |
| full Op+Step | 1,664 Ops / 14,976 Steps, correlation exact, no Op undercounting its observed Steps |
| Op-only (`DUMP_PROXY_STEPS=0`) | 1,664 Ops / 0 Steps, 988 KB vs 8.9 MB |

| Step-pool exhaustion | 12,327 Steps counted dropped, one warning line |

| marker contract | zero payload records carrying `header`/`metadata` |
| p2p path | 825 Ops / 13,145 Steps on `sendrecv` |

Correctness was clean throughout (`#wrong=0`, no hangs in graph-replay stress). Two pre-existing issues showed up that are **not** yours: `sendrecv`/`broadcast` emit no `coll_perf` records under `NCCL_INSPECTOR_REQUIRE_KERNEL_TIMING=1` (the task-relative `KernelCh.channelId` and allgatherv-scheduler cases). Notably `sendrecv` *proxy* records emit fine, since proxy timing is CPU-side and bypasses that gate.

The comments below are all enhancements rather than blockers. Three themes: give the wait timestamps meaning by emitting elapsed time, derive bandwidth from `trans_size_bytes` over that elapsed time, and reconsider nesting Steps inside their Op.

**One thing that needs a profiler-interface change, so it is a follow-up rather than a request here: Proxy records have no notion of which NIC they used.** `ncclProfilerEventDescr_v5_t.proxyOp` carries `pid`, `channelId`, `peer`, `nSteps`, `chunkSize`, `isSend`, and `proxyStep` carries only `step`, so the plugin cannot know or derive the device. `channel_id` correlates with a NIC on multi-rail nodes but does not identify one, and the channel-to-device mapping lives in core's connection resources, invisible to the profiler.

The awkward part is that core has it right at the call site: `resources->netDev` is set at connection setup (`net.cc:764`) and `net.cc` already casts `sub->connection->transportResources` a few lines from where it records the Step states. So exposing it is one field, not a redesign — adding `netDev` (ideally alongside the device name or PCI path from `ncclNetProperties`) to the proxyOp descriptor in the next profiler interface version. Without it, per-NIC attribution -- arguably the main reason to trace proxy activity at scale -- has to be reconstructed from `NCCL_DEBUG=INFO` logs. Worth filing separately; I am happy to raise it if you would rather not expand this PR's scope.
