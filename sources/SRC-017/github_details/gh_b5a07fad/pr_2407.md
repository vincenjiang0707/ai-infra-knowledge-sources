## 正文

## Description

When two ranks talk to each other directly (any 2-rank communicator, or the rank at distance n/2 in a communicator with an even number of ranks), `ncclTransportP2pSetup` exchanges the send-side and recv-side connect infos in a single bootstrap message and assumes the other side's message mirrors its own. If the two programs don't match, for example both ranks do `ncclSend` and then `ncclRecv` without a group, the sizes can still line up and each rank ends up passing the peer's send-side info to its own send connector.

On the SHM transport that makes the kernel write past the peer's small `ncclSendMem` segment and both ranks die with `cudaErrorIllegalAddress`. On NET/Socket it's the error from the issue, `ncclSocketInit: connecting to address with family 1 ...` followed by `internal error - please report this issue`. If only one rank groups its calls the bootstrap layer reports `Message truncated` on one side and reads short on the other. The docs say this pattern should just block, so none of that should happen. The branch where the send and recv peer are different ranks has the same short-read problem.

This change fixes the exchange itself: every connect info message now carries a header with the sender's connect masks toward the receiving rank, the receiver always receives into the full message, checks that the peer's masks mirror its own and takes the layout from the header. A mismatch fails with `ncclInvalidUsage` and a warning that prints both sides' send/recv connection counts. On that error path the connectors that did not get connected are reset, so a correct grouped send/recv afterwards works on the same communicator.

## Changes & Impact

- `src/transport.cc`: new `struct p2pConnectMsg` (masks header plus the connect infos), small helpers to fill, size and check it, and `ncclTransportP2pSetup` uses it for the same-peer message and for both messages of the different-peer branch. Messages are received into the full buffer. `p2pResetUnconnected` runs on the failure path and clears `hasSeen`/`p2pOnly` on the connectors that stayed unconnected.

Each peer slot now holds two message buffers during setup (64 KB instead of 32 KB), freed at the end of the call.

Tested on one node with two GPUs (RTX 5070 Ti + RTX 2070, no P2P, so 2-rank communicators go through SHM; NET/Socket via `NCCL_P2P_DISABLE=1 NCCL_SHM_DISABLE=1`) with a small two-process reproducer: both ranks ungrouped send, and one rank grouped with the other not, now return `ncclInvalidUsage` under SHM, `NCCL_SHM_LOCALITY=1` and NET/Socket instead of the illegal memory access, the hang or the internal error; grouped and correctly ordered send/recv still pass; a mismatched round followed by two grouped send/recv rounds on the same communicator passes with correct data. nccl-tests `all_reduce_perf` (default, `NCCL_ALGO=Ring`, `NCCL_ALGO=Tree`), `sendrecv_perf`, `alltoall_perf`, `broadcast_perf`, `reduce_perf` with `-g 2 -c 1` and on each GPU alone pass, and `mpirun` runs with 2, 4 and 6 ranks (`NCCL_MULTI_RANK_GPU_ENABLE=1`) pass for all_reduce (default, Ring, Tree), sendrecv, alltoall and broadcast, which exercises the different-peer branch. `make src.build WERROR=1` is clean.

Not tested: PAT (the tuner refuses `NCCL_ALGO=PAT` here with 2 and 4 ranks), NVLS tree, CollNet chain and direct, the P2P/IPC and NVLink transports, IB and multi-node. They all go through the same exchange, and for a well-formed program the check is a no-op.

Two things the check does not cover: it only runs while connections are being set up, so a mismatched pattern on a pair that is already connected is not detected and blocks in the kernel like before; and a mismatched pattern between ranks that are not each other's send and recv peer in the same round can still block on the bootstrap receive. Both are what the docs describe.

## Performance Impact

16 bytes of header per connect info message and the larger receive buffer; no extra messages. No change on the data path.

### justus-nv · 2026-09-14

@kodlan Thanks for tracking this down. The diagnosis is right. However, you are addressing the problem with a guard, rather than fixing the root cause. We also want to be cautious about adding overhead to the protocol with extra remote communication.

I'd like to fix the protocol itself rather than guard it with a separate handshake.

I recommend the following change. Prepend a header with the sender's own masks and always receive the message into the max-size buffer. Validate that the peer's masks mirror ours, and derive the layout from the header rather than from local counts.

```c++
struct p2pConnectMsg {
  uint64_t recvMask, sendMask;          // sender's own masks
  struct ncclConnect conn[2 * MAXCHANNELS];
};

// send: fill header, send sizeof(header) + (recvChannels + sendChannels) * sizeof(ncclConnect)
// recv: bootstrapRecv(..., msg, sizeof(*msg))   // max size; framing yields the true length
if (msg->recvMask != sendMask || msg->sendMask != recvMask) {
  WARN(...);
  ret = ncclInvalidUsage;
  goto fail;
}
int peerRecv = countOneBits(msg->recvMask);
sendData[p] = msg->conn;             // peer's recv-side entries feed my send connectors
recvData[p] = msg->conn + peerRecv;  // peer's send-side entries feed my recv connectors
```

Please apply the same header to the two messages in the different-peer branch as well. That path has the same short-read hazard.

*Other items*

- Use `countOneBits()` from `bitops.h` instead of `__builtin_popcountll`.
- Roll back connector state on the error path. When we return `ncclInvalidUsage`, the `hasSeen` and `p2pOnly` bits set during task append stay set, but group teardown only clears `connectSend` and `connectRecv`.
- Reword the warning. The actual constraint is that the connections each side opens in one preconnect round must mirror the peer's. "Must be in the same group" is only one of the possible operating modes.
- Ring, tree, PAT, NVLS tree, CollNet chain, CollNet direct all go through `ncclTransportP2pConnect`. Please consider testing these cases.
