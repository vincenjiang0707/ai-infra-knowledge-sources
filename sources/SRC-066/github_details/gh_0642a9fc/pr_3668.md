# [PR #3668] [CuTeDSL] Explain stride alignment after partitioning

## 正文

A 16-byte-aligned base does not establish alignment for every row when reconstructing a tensor with an unconstrained dynamic stride. Document the FP32 leading-stride divisibility condition, preserve it with `cute.assume`, and distinguish aligned pointers from contiguous copies. Use the actual leading stride `ld` rather than logical width `N`, so padded views are covered correctly.

The host example checks the actual data pointer, unit inner stride, and leading-stride divisibility. An optional 32-bit fallback checks both source and destination views before choosing a copy width; it handles real storage offsets without overstating DLPack alignment. The GPU regression verifies data and unchanged padding around the destination. Related: #3033. These cases do not establish a general `partition_S` alignment-loss bug.

Validation uses the complete PR Python source at `e00ad37439411daf756e03ffb0783aec5aa34102`, matching CuTeDSL/compiler libraries 4.8.0, cuda-python/cuda-bindings 13.0.3, RTX 5090 SM120, CUDA 13.0.88 and driver 580.82.07, in a separate environment.

`test_partition_alignment.py`: 5 methods / 13 subcases pass (10 GPU copies and 3 expected compilation errors); Compute Sanitizer memcheck reports 0 errors. These tests use one thread per row. All five wide cases emit PTX `ld/st.global.v2.b64` and SASS `LDG.E.128/STG.E.128`; all five narrow cases emit PTX `ld/st.global.b32` and scalar SASS memory instructions. A requested atom width alone is not evidence of the emitted memory-access width. The changed RST section builds with Sphinx `-n -W`; the whole documentation site was not built. Earlier 4.6 compiler crashes remain historical observations, not passing tests or an established root-cause diagnosis.
