# [PR #3688] [CuTeDSL] Make dynamic % and float // match Python semantics

source: https://github.com/NVIDIA/cutlass/pull/3688
state: open | updated: 2026-09-27T00:45:59Z
labels: 

## 正文

**Fixes #3687.** Makes dynamic `%` (signed ints and floats) and float `//` match Python, so they agree with each other and with the constant-folded results. The float `//` fix is a closely related bug found while fixing #3687. Verified on a B200 with DSL 4.8.0.

## Cause

- **`%`:** `ArithValue.__floordiv__` floors, but `ArithValue.__mod__` lowered to `arith.remsi` / `arith.remf`, whose result takes the **dividend's** sign. With operands of opposite signs, `(a // b) * b + a % b != a`, and a dynamic `%` disagreed with the same expression on constants (which `Numeric` folds with Python's operators). For example, `(i - 1) % 4` with `i = 0` gave `-1` at runtime and `3` when constant.
- **Float `//`:** it was `floor(a / b)`, and rounding `a / b` to float32 before flooring can give the wrong integer: `-1.0 // inf` gave `-0.0` (Python: `-1.0`) and `1.0 // 0.1f` gave `10.0` (Python: `9.0`, since `0.1f` > 0.1).

## Fix

- **`%`** (commit 1): applies the correction `_WatchedM._binop_ir` in `pyir_core.py` already uses. If the remainder is nonzero and its sign differs from the divisor's, add the divisor. A zero float result also takes the divisor's sign (`-4.0 % 2.0 == 0.0`). Unsigned `%` is unchanged.
- **Float `//`** (commit 2): computed the way Python's `float_divmod` (and NumPy and PyTorch) do it: `r = fmod(a, b)`, `div = (a - r) / b`, step `div` down by one where `%` adds the divisor to `r`, round to the nearest integer, and give a zero quotient the sign of `a / b`. A zero divisor keeps `floor(a / b)` (`±inf` / `nan`). Integer `//` is unchanged.

`Numeric` and `TensorSSA` operators both go through `ArithValue`, so both are covered.

## Cost / open question

Both fixes add instructions to every affected op:

| Op | Added |
|---|---|
| signed int `%` | 3 compares, xor/and, add, select |
| float `%` | the same, plus `copysign` |
| float `//` | `remf`, a second `divf`, several compares/selects |

If `remsi` / `floor(divf)` were kept here intentionally for performance, I'm happy to adjust, for example by exposing the C-style versions under an explicit API.

## Verification

B200, DSL 4.8.0:

| | before (dynamic / constant) | after (dynamic / constant) |
|---|---|---|
| `Int32 -7 % 2` | **`-1`** / `1` | `1` / `1` |
| `Float32 -7.0 % 2.0` | **`-1.0`** / `1.0` | `1.0` / `1.0` |
| `Float32 -1.0 // inf` | **`-0.0`** / `-1.0` | `-1.0` / `-1.0` |
| `Float32 1.0 // 0.1f` | **`10.0`** / `9.0` | `9.0` / `9.0` |

- New `test/python/CuTeDSL/test_floordiv_mod_sign.py` runs `//` and `%` on the GPU for `Int32`, `Int64` and `Float32` (scalars and `TensorSSA`) across all sign combinations plus `±inf` and `0.1` divisors, and compares against Python. It has 61 failures on 4.8.0 and passes with this change. The other tests in `test/python/CuTeDSL` give the same results with and without it.
- A randomized check over 4M float32 pairs: `//` now matches `torch.floor_divide` bit for bit (stock: 160,711 mismatches), and `%` matches Python on every sampled pair.

<details>
<summary>Randomized check details</summary>

Inputs: wide magnitudes (2^-30 to 2^30), `±0`, `±inf`, `nan`, and multiples of 0.1.

- `//` matches Python except where `|a // b| >= 2**23`, where float32 cannot represent the float64 result. There it matches `numpy.floor_divide` on float32.
- `%` differs from `torch.remainder` only in the sign of zero results: torch returns `-67.5 % 2.5 == -0.0`, while Python returns `0.0`. This PR follows Python.

</details>
