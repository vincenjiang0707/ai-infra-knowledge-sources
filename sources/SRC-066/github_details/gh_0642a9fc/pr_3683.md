# [PR #3683] Load runtime libraries before dumping the export object file

## 正文

Fixes #3680

`export_to_c` failed with `Symbols not found` for a function compiled for a `--gpu-arch` this machine
cannot run (#3680). `dump_object_file_pic` resolves the module's runtime symbols from libraries loaded
globally in the process. Those libraries are only loaded as a side effect of building the JIT engine,
and a cross-arch compile builds no engine.

- `base_dsl/jit_executor.py`: before the dump, `dump_to_object` now loads the DSL's shared libraries
  (`get_shared_libs()`, the same list the JIT engine gets) with `RTLD_GLOBAL`. As the engine does, it
  skips a library that fails to load, and logs a warning. This is the same thing as the workaround in
  the issue, applied where the libraries are needed. On the native-arch path the libraries are
  already loaded, so the call is a no-op there.
- `test/python/CuTeDSL/test_export_cross_arch.py` (new): compiles a one-kernel function for an arch
  the runtime arch cannot run (`sm_90a`, or `sm_100a` when running on `sm_90a`) and exports it with
  `export_to_c`. It runs in a subprocess, because any earlier native-arch compile in the same process
  loads the libraries and hides the bug.

### Verification

Environment: an aarch64 Ubuntu VM without a GPU, Python 3.12, `nvidia-cutlass-dsl==4.8.0`. I ran it
twice, once with the cu12.9 libs and once with the `[cu13]` libs (CUDA 13.4, as in the report). The
wheel's `base_dsl/jit_executor.py` is identical to `main`'s before this change, and I replaced it with
the patched file. With no device, the DSL's runtime arch defaults to `sm_100a`, so compiling for
`sm_90a` takes the same no-engine path as `sm_90a` on a B200.

```yaml
Command: `python -m pytest -p no:cacheprovider -q test/python/CuTeDSL`
Result:
```
- Before the change, the new test fails with the issue's error, on both cu12 and cu13:
  `AssertionError: 1 != 0 : JIT session error: Symbols not found: [ _cuKernelGetAttribute, _cudaDeviceGetAttribute, ...`.
  The full cu12 run ends `2 failed, 32 passed, 412 subtests passed`.
- After the change, on both cu12 and cu13: `1 failed, 33 passed, 412 subtests passed`.
- The remaining failure is `test_vector_reduction_fastmath.py::TestVectorReduceFastmath::test_fastmath_flag`
  (`TypeError: Vector.reduce() got an unexpected keyword argument 'fastmath'`). It fails the same way
  without this change, because the 4.8.0 wheel's `_mlir_helpers` predate `main`.

Also checked:
- The issue's repro script fails before the change and prints `exported` after it.
- The exported `noop.o` and `noop.h` for `sm_90a` are byte-identical to the output of the issue's
  `--preload` workaround. The embedded cubin is `EM_CUDA` with the sm_90 flag.
- The native-arch (`sm_100a`) export and a `--host-target linux-aarch64` export are byte-identical
  before and after the change.
- The new test passes with `CUTE_DSL_ARCH` unset, `sm_90a` (so it compiles for `sm_100a`), `sm_90`
  and `sm_120a`. It also fails without the fix on the `sm_100a` branch.
- `CUTE_DSL_LIBS` with an extra unloadable file: the native export still succeeds, as it did before,
  and the cross-arch export now succeeds, with the skipped file logged.
- Two cross-arch exports in one process, with `gc.collect()` between them, both succeed.
- `ruff check` and `ruff format --check` pass on the new test. `jit_executor.py` has the same ruff
  findings before and after (146 with default rules) and stays `ruff format` clean.
