# [PR #3661] [CuTeDSL] Guard SM100 UMMA peer arrival mask on the cluster v-extent

source: https://github.com/NVIDIA/cutlass/pull/3661
state: open | updated: 2026-09-22T21:09:53Z

## 正文

**Fixes #3658.** Verified on hardware: the reported fault reproduces before this change and is gone after.

## Cause

`_compute_mcast_arrival_mask` unconditionally ORs in image masks taken at the v-peer coordinate `(v ^ 1, m, n, k)`. That peer only exists for a 2CTA tcgen05 MMA (v-extent 2). At v-extent 1 the coordinate is outside the layout's domain, and if mode 0 carries a non-zero stride the peer image runs off the end of the cluster — `(1,4,1,1):(1,1,4,4)` yields mask `0b11111`, setting bit 4 of a 4-CTA cluster. The mask feeds `tcgen05.commit(..., multicast::cluster)`, so that is an out-of-range remote mbarrier access.

## Fix

Compute the peer terms only when the v-extent is not 1 — the same guard `PipelineAsyncUmma.create` already applies, and the semantics of the C++ `detail::calculate_multicast_mask`, which never addresses a rank outside the cluster.

## Verification

GB300 (`sm_103a`), CUDA 13.0, DSL 4.8.0 — 4-CTA cluster through `PipelineTmaUmma.consumer_release`:

| `cta_layout_vmnk` | before | after |
|---|---|---|
| `(1,4,1,1):(1,1,4,4)` 1SM | **`cudaErrorLaunchFailure` (719)** | `cudaSuccess` |
| `(1,4,1,1):(0,1,0,0)` 1SM | `cudaSuccess` | `cudaSuccess` |
| `((2),2,1,1):((1),2,0,0)` 2SM | `cudaSuccess` | `cudaSuccess` |
| `((2),1,2,1):((1),0,2,0)` 2SM | `cudaSuccess` | `cudaSuccess` |

No in-tree caller is affected — `make_layout`, `tiled_divide` and `make_ordered_layout` give extent-1 modes stride 0, which makes the peer terms inert. `dense_gemm.py` is identical before and after for cluster shapes 1x1, 2x1, 1x2, 2x2, 4x1, 1x4 and 4x4 in both 1SM and 2CTA modes.
