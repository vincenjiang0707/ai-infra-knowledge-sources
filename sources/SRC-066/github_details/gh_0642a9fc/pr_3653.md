# [PR #3653] [examples/77] Wait for TMEM statistics stores before publishing them to the correction warpgroup

state: open | updated: 2026-09-22T05:24:26Z

## 正文

*Found by an ongoing project that formally verifies GPU kernels by checking their PTX against the PTX memory model.*

> **This is a proposed fix for a suspected bug, not a confirmed one.** We are opening it to ask whether the missing ordering is a real defect or something the code deliberately relies on. If it is the latter, please close this PR.

## Summary

In the softmax path of the SM100 FMHA mainloops, the row statistics are written to TMEM and then published to the correction warpgroup:

```cpp
// softmax warpgroup
copy(tiled_tmem_storev, tTMEM_STOREVrS, tTMEM_STOREVtS);   // tcgen05.st (asynchronous)
pipeline_c.producer_commit(pipeline_c_producer_state);      // mbarrier.arrive

// correction warpgroup
pipeline_s0_c.consumer_wait(pipeline_s0_c_consumer_state);
copy(tiled_tmem_loadv, tTMEM_LOADVtS0, tTMEM_LOADVrS);      // tcgen05.ld of the same columns
```

There is no `tcgen05.wait::st` between the store and the arrive, so the notification is not ordered after the asynchronous TMEM write (PTX ISA §9.7.18.6.4.4). This occurs twice per mainloop:

1. the per-iteration old/new row max, published every KV tile, and
2. the final row max and row sum, published when `final_call` is set.

The same function already uses the correct idiom for the P matrix:

```cpp
copy(tiled_tmem_store, ...);
cutlass::arch::fence_view_async_tmem_store();   // tcgen05.wait::st
pipeline_s.consumer_release(pipeline_s_consumer_state);
```

This PR adds `cutlass::arch::fence_view_async_tmem_store()` after both statistics stores in the fwd, gen and MLA-fwd mainloops, six sites in total. Both call sites are warp-uniform, as the `.sync.aligned` wait requires.

## Where the race is

Time runs downwards, for the final statistics. Line numbers are from `f614dc40`, in `examples/77_blackwell_fmha/collective/sm100_fmha_fwd_mainloop_tma_warpspecialized.hpp`.

| # | Softmax warpgroup | TMEM store, in flight | Correction warpgroup |
|---|---|---|---|
| 1 | `tcgen05.st` of row max and row sum, `:721` | accepted, **not yet visible** | blocked in `consumer_wait` |
| 2 | *(this PR inserts `tcgen05.wait::st` here)* | | |
| 3 | `producer_commit`, an `mbarrier.arrive`, `:780` | still in flight | |
| 4 | | still in flight | wait returns |
| 5 | | still in flight | `tcgen05.ld` of the same columns, `:1079` and `:1124` |
| 6 | | store lands | correction has already used the old values |

Row 5 is the race: the arrive at row 3 carries no guarantee that the store at row 1 is visible. The per-iteration row max has the same shape at `:611` and `:613`.

## Is this a real bug?

**The gap survives compilation.** `tcgen05.wait::st` is a real SASS instruction, `FENCE.VIEW.ASYNC.T`, and ptxas does not insert it on its own. In the fp16 `77_blackwell_fmha` binary built from `main`, every one of the 112 `STTM.x2` statistics stores reaches the following `SYNCS.ARRIVE` with no fence in between. With this PR all 112 are fenced; the `FENCE.VIEW.ASYNC.T` count goes from 120 to 232.

**We could not make it fail on B200.** We rebuilt the pattern in a small kernel: store, arrive, then load from the other warpgroup. It compared about 2.65 trillion loaded values against a stale pattern written beforehand. The detector was calibrated to catch a write landing 50 or more cycles after the arrive. No stale value appeared, including with a 1024-deep store backlog, extra warps streaming TMEM stores, and 4 KB stores. Timing `tcgen05.wait::st` in isolation shows the data becomes visible to another warp's `tcgen05.ld` before the store reports completion. The current code relies on that property, which is not documented.

**The question we would like answered:** is this a real bug? The PTX model appears to require the wait, and ptxas does not close the gap for you, so it is still there in the shipped binary. But we could not make it fail, which suggests the mainloop relies on TMEM stores becoming visible to another warpgroup's `tcgen05.ld` before `tcgen05.wait::st` reports completion. Is that ordering guaranteed by the hardware and intended to be relied on here? If so, we will close this. If not, this patch is the minimal fix and we can adjust it however you prefer.

## Testing

B200 (sm_100a), CUDA 13.2, driver 595.58.03, fp16, the examples' compile flags.

- Upstream CMake test options pass, as on `main`: fmha 8 of 8, fmha_gen 5 of 5, MLA fwd 5 of 5.
