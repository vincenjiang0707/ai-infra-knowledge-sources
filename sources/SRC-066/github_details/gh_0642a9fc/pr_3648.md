## 正文

## Motivation

BF16 is the dominant dtype for LLM training and inference, and SM90 WGMMA supports it natively (`wgmma.mma_async ... .f32.bf16.bf16`). The CuTe DSL primitive already allows it: `warpgroup.MmaF16BF16Op` accepts `BFloat16` A/B with `Float32` accumulation. But the Hopper `dense_gemm.py` and `dense_gemm_persistent.py` examples rejected BF16 in `is_valid_dtypes`, so the most common Hopper GEMM configuration could not be run with the reference examples. The Blackwell dense GEMM examples already support BF16.

## Modifications

- `dense_gemm.py`, `dense_gemm_persistent.py`:
  - Allow `BFloat16` A/B, with `Float32` accumulation only. This matches the WGMMA / `MmaF16BF16Op` constraint. `BFloat16` with `Float16` accumulation is still rejected.
  - Allow `BFloat16` output with `Float32` accumulation.
  - Update the module/class docstrings (supported types, accumulator rules, alignment) and the stale `TypeError` messages.
- New `test/examples/CuTeDSL/hopper/test_dense_gemm.py`. Neither kernel had tests before. It uses the existing L0/L1 structure and covers both kernels × {Float16, BFloat16}:
  - L0 compile: all tile shapes (128x256, 128x128, 128x64, 64x64)
  - L1 correctness against `torch.einsum`: tile shapes, cluster shapes (1x1, 2x1, 1x2, 2x2, including multicast), all 8 A/B/C major combinations (batched, L=2), output dtypes {F16, BF16, F32}, non-tile-aligned sizes (1000x1032x264, 136x72x72x3)
  - Validation: BF16 + F32 acc accepted; BF16 + F16 acc and mixed BF16/F16 rejected

The kernel code itself is not changed. BF16 uses the same code path as FP16, and only the operand type of the MMA/TMA atoms differs.

## Correctness

NVIDIA H200 (SM90a), driver 580.159.03, `nvidia-cutlass-dsl[cu13]==4.8.0.dev0`, torch 2.14.0+cu130:

```
$ cd test/examples/CuTeDSL
$ pytest hopper/test_dense_gemm.py -q --target-cc 90 --test-level L2
102 passed in 127.16s
```

Regression check: FP8 (E4M3FN → F16) and INT8 (→ Int32) still PASS on both modified kernels.

SASS check (`CUTE_DSL_KEEP=cubin`, `cuobjdump -sass`, tile 128x256):

| | PTX | SASS | # MMA | # TMA/SYNCS |
|---|---|---|---|---|
| FP16 | `wgmma.mma_async.sync.aligned.m64n256k16.f32.f16.f16` | `HGMMA.64x256x16.F32` | 8 | 38 |
| BF16 | `wgmma.mma_async.sync.aligned.m64n256k16.f32.bf16.bf16` | `HGMMA.64x256x16.F32.BF16` | 8 | 38 |

## Performance

H200, A/B/C K-major/K-major/N-major, F32 accumulation, tile 128x256, cluster 1x1, hot L2, 10 warmup + 50 timed iterations. cuBLAS is `torch.matmul` (BF16) on the same shape. Units are TFLOP/s.

`dense_gemm_persistent.py`:

| M, N, K | DSL FP16 | DSL BF16 | cuBLAS BF16 | DSL BF16 / cuBLAS |
|---|---|---|---|---|
| 4096, 4096, 4096 | 866.3 | 865.8 | 800.5 | 1.08x |
| 8192, 8192, 8192 | 827.7 | 836.6 | 748.3 | 1.12x |
| 4096, 14336, 4096 | 891.0 | 892.5 | 789.8 | 1.13x |
| 4096, 4096, 14336 | 921.9 | 919.4 | 806.0 | 1.14x |
| 16384, 8192, 1024 | 793.9 | 788.8 | 732.3 | 1.08x |
| 8192, 4096, 512 | 638.0 | 636.8 | 627.7 | 1.01x |

BF16 performance matches FP16 within run-to-run noise (about ±2%), as expected because BF16 and FP16 WGMMA have the same throughput. The non-persistent `dense_gemm.py` reaches 815–905 TFLOP/s on the square/LLM shapes (1.04–1.11x cuBLAS) and 0.96x cuBLAS on the short-K 16384x8192x1024 shape, where per-tile prologue/epilogue is not amortized.

## Testing notes

To run the public example tests outside NVIDIA CI I needed `--target-cc 90`, because `test/utils/test_sharding.py` otherwise imports `device_info`, which is not in the repository. I also needed `pytest<9`, because the plugin imports `_pytest.assertion.util.running_on_ci`. These are unrelated to this PR.
