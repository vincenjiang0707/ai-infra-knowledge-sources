# [PR #3652] [examples/93] Wait for the Acc2 tcgen05.ld before releasing TMEM to the MMA warp

## 正文

*Found by an ongoing project that formally verifies GPU kernels by checking their PTX against the PTX memory model.*

> **This is a proposed fix for a suspected bug, not a confirmed one.** We are opening it to ask whether the missing ordering is a real defect or something the code deliberately relies on. If it is the latter, please close this PR.

## Summary

In `EPILOG_warp` (`examples/93_blackwell_low_latency_gqa/tgv_gqa.cuh`), the final Acc2 read is followed by the notification that lets the MMA warp free TMEM:

```cpp
tmem_load<decltype(bmm2_tmem_load)>(acc2_tmem_addr, tAcc2rAcc2);   // tcgen05.ld (asynchronous)
if (lane_id < (CTA_dH / NumEpilogWarps)) {
  // only these lanes consume tAcc2rAcc2 (st.async to the reduction CTA)
}
arrive_barrier(shared_storage.tmem_allocation_result_barrier);
```

and in the MMA warp:

```cpp
arrive_barrier(shared_storage.tmem_allocation_result_barrier);
wait_barrier(shared_storage.tmem_allocation_result_barrier, 1);
tmem_allocator.free(shared_storage.bmm1_tmem_base_ptr, Acc1_col_max);
tmem_allocator.free(shared_storage.bmm2_tmem_base_ptr, Acc2_col_max);
```

With the example's default `dH = 64` the condition is `lane_id < 16`, so lanes 16–31 of each epilogue warp never use their loaded registers. Nothing orders their `tcgen05.ld` before the arrive that allows the deallocation. PTX ISA §9.7.18.6.4.4 ("Non-pipelined instructions, different thread") requires `tcgen05.wait::ld` before synchronizing with another thread. §9.7.18.6.4.5 notes that a register dependency orders only the dependent instruction in the same thread, so even the consuming lanes are not formally covered.

This PR adds `cutlass::arch::fence_view_async_tmem_load()` (`tcgen05.wait::ld`) right after the load. That is the idiom this kernel already uses for Acc1 before it signals the next BMM1 (`tgv_gqa.cuh:1325`).

## Where the race is

Time runs downwards. Line numbers are from `f614dc40`. Both epilogue lanes below are in the same warp; the MMA warp is the TMEM owner.

| # | Epilogue lanes 0–15 | Epilogue lanes 16–31 | MMA warp (TMEM owner) |
|---|---|---|---|
| 1 | `tcgen05.ld` Acc2 issued, `tgv_gqa.cuh:1514` | `tcgen05.ld` Acc2 issued, `:1514` | blocked in `wait_barrier`, `:882` |
| 2 | read the registers, `:1516`–`:1527` | **never read them**, so no dependency forces the load to finish | |
| 3 | `arrive_barrier`, `:1530` | `arrive_barrier`, `:1530` | |
| 4 | | | wait returns: all 160 arrivals in, `:882` |
| 5 | | **load may still be in flight** | `tmem_allocator.free`, `:885`–`:886` |
| 6 | | load completes against TMEM this CTA has already released | |

Row 5 is the race. This CTA never reuses those columns itself, since the scheduler is non-persistent and the CTA exits just after the free; the columns go back to the SM's allocator, which may hand them to another CTA, and the allocation lock is released early at `:819` precisely so that can happen. Note also that rows 1 to 2 do not save the consuming lanes: PTX ISA §9.7.18.6.4.5 says a register dependency orders only that instruction in that same thread, not another thread's view of the TMEM.

## Is this a real bug?

We could not produce a failure on hardware, and on CUDA 13.2 the change does not alter the generated code:

- ptxas already puts the `LDTM` scoreboard wait on the `lane_id < 16` branch, so the whole warp waits for the load before it diverges. Patched and unpatched `93_blackwell_low_latency_gqa` SASS differ only in `NOP` padding.
- A reduced reproduction of this barrier protocol on B200 ran about 14 billion CTAs, with and without `-Xptxas -g-tmem-access-check` and compute-sanitizer. It produced no guardrail trap, sanitizer error, or wrong value.

So the current code is safe because of how ptxas schedules this particular shape, not because the program orders it. The patch states the PTX-required ordering explicitly, and the generated code does not change.

**The question we would like answered:** is this a real bug? Concretely, is `EPILOG_warp` intended to rely on ptxas placing the `LDTM` scoreboard wait ahead of the `lane_id` branch, so that the non-consuming lanes' loads are complete before the arrive? If that reliance is deliberate and guaranteed, we are happy to close this. If it is incidental, this patch is the minimal fix and we can adjust it however you prefer.

## Testing

B200 (sm_100a), CUDA 13.2, driver 595.58.03, built with `nvcc -O3 -std=c++17 -gencode arch=compute_100a,code=sm_100a`.

- Builds cleanly. SASS is identical to `main` apart from `NOP` padding.
- Performance is identical by construction; measured numbers are below.
