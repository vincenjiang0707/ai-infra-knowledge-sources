## 正文

*Found by an ongoing project that formally verifies GPU kernels by checking their PTX against the PTX memory model.*

> **This is a proposed fix for a suspected bug, not a confirmed one.** We are opening it to ask whether the missing ordering is a real defect or something the code deliberately relies on. If it is the latter, please close this PR.

## Summary

In the SM100 FMHA load collectives, the whole load warp executes `producer_acquire` (an mbarrier parity wait), but only the elected lane issues the TMA:

```cpp
uint32_t lane_predicate = cute::elect_one_sync();
pipeline_q.producer_acquire(pipeline_q_producer_state);   // all 32 lanes: empty_barrier.wait(phase)
if (lane_predicate) {
  copy(params.tma_load_q.with(*tma_barrier, 0), ...);      // elected lane only
}
```

Under PTX's per-thread semantics, nothing orders a non-elected lane's wait before the elected lane's TMA. Suppose a non-elected lane reaches its wait only after the elected lane has issued the load and the consumer has released the buffer. Q is released once per tile, so by then the empty barrier has moved to its next phase. That lane is still waiting for parity 1, which will never come again, so the load warp hangs.

This PR adds a `__syncwarp()` after each `producer_acquire` in `sm100_fmha_load_tma_warpspecialized.hpp` and `sm100_fmha_mla_load_tma_warpspecialized.hpp`, 12 sites in total, with a comment explaining why.

## Where the race is

Time runs downwards. Lanes 0 and k are in the same load warp. Line numbers are from `f614dc40`: `load` is `examples/77_blackwell_fmha/collective/sm100_fmha_load_tma_warpspecialized.hpp`, `mainloop` is `sm100_fmha_fwd_mainloop_tma_warpspecialized.hpp`, `pipeline` is `include/cutlass/pipeline/sm100_pipeline.hpp`.

| # | Load warp, elected lane | Load warp, lane k | Consumer warps |
|---|---|---|---|
| 1 | `producer_acquire` for Q: waits parity 1 and returns, `load:242`, wait at `pipeline:1100` | **has not reached its wait yet** | blocked in `consumer_wait` |
| 2 | issues the TMA for Q, `load:245` | | |
| 3 | | | wait returns, reads Q |
| 4 | | | `consumer_release` for Q, `mainloop:474`, which flips the empty barrier to its next phase |
| 5 | | now reaches `producer_acquire` and waits for parity 1, `load:242` | |
| 6 | | **that phase is already gone, so the wait never returns** | |

Row 5 is the race, and row 6 is the hang. Parity 1 is the producer's initial phase, from `InitialProducerPhase` in `include/cutlass/pipeline/sm90_pipeline.hpp:257`. Q is the dangerous buffer because it is released once per tile; the multi-stage K/V ring gives lanes more slack before the same thing happens.

## Is this a real bug?

This is a hazard in the PTX model that current ptxas does not expose:

- In the compiled fp16 fwd kernel, the elected-lane copy is emitted as an unconditional, uniform `UTMALDG`. There is no divergence between `producer_acquire` and the TMA, so all 32 lanes execute each wait together. In a reduced reproduction of about 200 million CTAs, all 32 lanes passed every wait in the same cycle.
- The failure mechanism itself is real. Forcing one lane to execute its parity-1 wait after the consumer's release hangs that lane every time. When the wait is placed in a genuinely divergent region, the hardware scheduler does let the non-elected lanes fall behind, and they hang on the multi-stage K/V ring.

So the code currently depends on ptxas proving that the warp is converged. The `__syncwarp()` makes that ordering explicit.

**The question we would like answered:** is this a real bug? Concretely, are the load collectives intended to rely on ptxas keeping the load warp converged across `producer_acquire` and the elected-lane TMA, so the lanes can never diverge? If that reliance is deliberate, we are happy to close this, especially given the MLA cost below. If it is incidental, this patch is the minimal fix and we can adjust it however you prefer.

## Cost

- **fwd kernel:** ptxas proves the warp convergent and emits no additional `WARPSYNC`; the binary is in fact slightly smaller.
- **MLA fwd kernel:** 144 additional `WARPSYNC.ALL` instructions across all instantiations.
