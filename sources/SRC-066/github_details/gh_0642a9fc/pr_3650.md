## 正文

## Motivation

#3540 reports that the ColumnMajor-output specializations of `GemmUniversalWithBroadcast` / `GemmUniversalStreamkWithBroadcast` misindex the broadcast vector. I added the missing test coverage for the vector under both output layouts and found two things:

1. **The ColumnMajor behavior is self-consistent, but it was not documented.** The specialization transposes the problem, so the underlying row-major kernel broadcasts `V` along *its* columns, which are the **rows** of the column-major `D`. The vector therefore has **M** elements, and the epilogue bounds-checks against M. With a length-M vector, results are correct and memcheck is clean. The OOB reads described in the issue only happen when a caller assumes a length-N vector. Rejecting `ptr_Vector` or changing the indexing would break callers that already use the length-M convention. A per-column vector for column-major D is also not expressible with this epilogue. So this PR takes the issue's other suggestion and **documents the convention**.
2. **A real bug in `GemmUniversalStreamkWithBroadcast`, independent of layout.** It produces wrong results whenever Stream-K splits the K loop across thread blocks, including plain RowMajor output with the default `LinearCombinationBiasElementwise` op. There was no in-tree test of this class.

## Root cause (Stream-K)

In separate-reduction mode, each block reduces one accumulator fragment `reduce_fragment_idx` of an output tile, and then `EpilogueStreamkWithBroadcast::reduce()` calls `EpilogueWithBroadcast::reduce()`. The single-source overload of that function stored the fragment through `destination_iterator` / `tensor_iterator` without advancing them to `reduce_fragment_idx`:

```cpp
destination_iterator.store(frag_Z);   // always fragment 0
++destination_iterator;
```

As a result, every fragment was written over fragment 0: most of D and T were never written, and fragment 0 got whichever peer wrote last. The source iterator *was* advanced (`source_iterator += reduce_fragment_idx`), so C was read from the right place. The dual-source overload in the same file and `Epilogue::reduce()` both do `iterator += reduce_fragment_idx` before storing. This PR makes the single-source overload match them. The function is only reached through `EpilogueStreamkWithBroadcast`.

## Modifications

- `epilogue_with_broadcast.h`: advance `destination_iterator` / `tensor_iterator` by `reduce_fragment_idx` before storing in the single-source `reduce()`.
- `gemm_universal_with_broadcast.h`, `gemm_universal_streamk_with_broadcast.h`: document how the vector is indexed. It always runs along the contiguous dimension of D: N elements for RowMajor, M elements for ColumnMajor. Also document what `ldr` / `batch_stride_Vector` mean, explain why the ColumnMajor specialization uses M, and complete the truncated "Supports" doc comment.
- New `test/unit/gemm/device/gemm_universal_with_broadcast_vector_sm80.cu` (added to `cutlass_test_unit_gemm_device_broadcast`):
  - Inputs are small integers, so the half-precision results must match the reference **bit-exactly**, and every element of both **D (Z)** and **T** (`ptr_Tensor`) is checked.
  - The vector is allocated with exactly its documented length, so compute-sanitizer flags any overread.
  - Covers `GemmUniversalWithBroadcast` × {RowMajor, ColumnMajor} × {M>N, M<N, batched L=2 with `batch_stride_Vector`}, and `GemmUniversalStreamkWithBroadcast` × {RowMajor, ColumnMajor} × {unsplit K=64, Stream-K split K=512 and 520x392x1024, data-parallel `avail_sms=1`}.

## Correctness

Built with CUDA 12.8, `-DCUTLASS_NVCC_ARCHS="80;90"`; run on NVIDIA H200 (SM90) and A800 (SM80).

Before the fix (new test, unmodified headers):
```
[       OK ] SM80_Device_GemmWithBroadcast_f16t_f16n_f16t_tensor_op_f16.128x128_32x3_64x64x32_16x8x16
[       OK ] SM80_Device_GemmUniversalWithBroadcast_f16t_f16n_f16t_tensor_op_f32.vector_per_column
[       OK ] SM80_Device_GemmUniversalWithBroadcast_f16t_f16n_f16n_tensor_op_f32.vector_per_row
[  FAILED  ] SM80_Device_GemmUniversalStreamkWithBroadcast_f16t_f16n_f16t_tensor_op_f32.vector_per_column
             (32981 / 35904 mismatches at 136x264x512; 197730 / 203840 at 520x392x1024)
[  FAILED  ] SM80_Device_GemmUniversalStreamkWithBroadcast_f16t_f16n_f16n_tensor_op_f32.vector_per_row
```
The Stream-K cases pass with `avail_sms=1` (no peer reduction) and with K=64 (no split), which isolates the failure to the peer-reduction path.

After the fix:

## Performance

No performance impact. The fix adds one iterator offset per reduced fragment in the Stream-K separate-reduction path, and the documentation changes are comments only.

Closes #3540
