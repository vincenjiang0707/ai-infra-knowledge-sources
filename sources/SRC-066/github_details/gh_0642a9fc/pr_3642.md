## 正文

## Summary

`cute.arch.inline_ptx` lowers a compile-time constant read-only operand to the immediate constraint `n` regardless of what the target instruction accepts. Some PTX instructions take only a register in a given operand slot, so such a constant is rejected by ptxas. This adds `force_register_args`, an opt-in that names the read-only operands which must be moved into a register first.

Refs #3640.

## Minimal failure

```python
@cute.kernel
def kernel():
    value = cute.arch.thread_idx()[0]
    zero = Int32(0)
    cute.arch.inline_ptx(
        "max.xorsign.abs.bf16x2 {$w0}, {$r0}, {$r1};",
        write_only_types=[Int32],
        read_only_args=[zero, value],
    )
```

Generated PTX on an L20 (sm_89, `nvidia-cutlass-dsl 4.8.0.dev0`):

```ptx
mov.u32 	%r3, %tid.x;
max.xorsign.abs.bf16x2 %r1, 0, %r2;      // immediate operand
```

```
ptxas application ptx input, line 32; error   : Arguments mismatch for instruction 'max'
ptxas fatal   : Ptx assembly aborted due to errors
```

## Where the constraint is chosen

Not in this repository. `NVVM_InlinePtxOp` carries no per-operand register request (only `readOnlyArgs`, `readWriteArgs`, `ptxCode`, `predicate`, `memoryClobber`). The constraint comes from the NVVM to LLVM conversion, `mlir/lib/Dialect/LLVMIR/IR/BasicPtxBuilderInterface.cpp`:

```cpp
static FailureOr<char> getRegisterType(Value v, Location loc) {
  if (v.getDefiningOp<LLVM::ConstantOp>())
    return 'n';
  return getRegisterType(v.getType(), loc);
}
```

The value-level overload returns `n` for any constant without consulting the instruction, so the generated `llvm.inline_asm` gets the constraint string `"=r,n,r"`.

## What this changes

`inline_ptx(..., force_register_args=(0,))` materializes the named read-only operands with an explicit `mov` before the target instruction runs:

```ptx
mov.b32 %r2, 0;
max.xorsign.abs.bf16x2 %r1, %r2, %r3;
```

which is the output #3640 asks for. The operand the target instruction sees is produced by an instruction rather than by a constant op, so the existing type-based register constraint applies. Nothing else changes: the default is `None`, unnamed operands keep today's behavior, and indices refer to `read_only_args` only — out-of-range, negative, bare-int and non-integer indices raise.

## Why not disable immediates globally

A constant is legal, and preferable, in plenty of operand slots (`add.s32`, `mbarrier.init.b64`, ...). Making `getRegisterType(Value)` return `r` for every constant would be a semantics change well beyond this issue. The opt-in is therefore per call site, and the existing immediate path is untouched — covered by `test_default_path_is_unchanged` and by the `add.s32` cases in the verification below.

## Verification

Hardware: 1× NVIDIA L20, compute capability 8.9, driver 570.86.10, `CUTE_DSL_ARCH=sm_89`.
Environment: `nvidia-cutlass-dsl 4.8.0.dev0` (cu12 libraries), PTX generated by CUDA 13.4.46 / NVVM 23.0.0. Baseline is `f614dc40e17fb3ddb1b7b474318b48a8d5d21a2c`.

End-to-end path (Python DSL → lowering → PTX → ptxas → launch → host readback), 32 lanes of packed bf16 covering ±0, ±1, ±2 and ±0.5, compared as raw bit patterns:

| Variant | Compile | Bit-exact readback |
|---|---|---|
| `Int32(0)` as reported | FAIL — `Arguments mismatch for instruction 'max'` | — |
| constant read from memory (pre-change workaround) | PASS | 32/32 |
| `llvm.inline_asm` with explicit `=r,r,r` | PASS | 32/32 |
| `force_register_args=(0,)` | PASS | 32/32 |

Regression matrix, all executed on the device: literal zero; non-zero and negative finite constants; a constant produced by folding; the constant in the second read-only position; two identical constants with only one opted in; a read-only placeholder repeated twice; dynamic operands with and without the opt-in; an instruction where an immediate is legal, with and without the opt-in; two write-only results with a forced constant; and the argument-validation cases. The new test file covers the same IR shapes on CPU, so it needs neither a GPU nor ptxas.

Timing was measured with CUDA events in an interleaved paired run (60 rounds memory-bound, 40 rounds register-resident) including an A/A arm that recompiles and re-measures the patched variant under a second label. The fixed kernel matches the existing workarounds within the A/A noise band (about ±1.2%); the materialized `mov` is hoisted out of the loop and absorbed by register allocation. This is a correctness change, not a throughput change.

Two failures observed while testing are **not** addressed here, and reproduce without this change: `inline_ptx(predicate=...)` emits `@0` instead of the predicate's operand index, and a float read-only constant fails with `constraint 'n' expects an integer constant expression`. Float operands are therefore rejected by `force_register_args` with an explicit error rather than silently ignored.

## Scope and open questions

This is a CUTLASS-side wrapper. The complete fix belongs in LLVM/MLIR — a per-operand register request on `NVVM_InlinePtxOp` honoured by `BasicPtxBuilderInterface` — which then has to reach a release wheel. This repository has no copy of that C++, and the wheel ships a statically linked compiler, so that path cannot be validated from here.

The parameter name is a proposal. Feedback on the name, on whether the `mov` materialization is the right shape, or on waiting for the compiler-side attribute instead, is welcome.

Not tested: sm_100 (the reported target; this host is sm_89), and NaN/subnormal bit-level semantics.

### Timing

This is a correctness fix, so the point of these numbers is that it costs nothing at runtime — not that it is faster.

Hardware: 1× NVIDIA L20, compute capability 8.9, driver 570.86.10, `CUTE_DSL_ARCH=sm_89`. Workloads:

- `mem` — memory-bound elementwise kernel over 16,777,216 packed-bf16x2 carriers (64 MiB read + 64 MiB write), grid 8192 × block 256, 8 carriers per thread.
- `alu` — register-resident loop, 262,144 threads × 8 accumulators × 2048 iterations = 4.29e9 instructions.

Timing uses CUDA events. Every arm is compiled up front, then measured in **interleaved rounds** — each round visits all arms once in a rotating order — 60 rounds for `mem`, 40 for `alu`. `patched_aa` is the patched variant recompiled and measured under a second label: an A/A control that bounds the noise floor of the harness itself.

| Arm | `mem` median (ms) | `mem` effective BW (GB/s) | `alu` median (ms) | `alu` throughput (Gops/s) |
|---|---|---|---|---|
| constant read from memory (pre-change workaround) | 0.198656 | 675.6 | 0.345568 | 12 428.7 |
| `llvm.inline_asm` with explicit `=r,r,r` | 0.199168 | 673.9 | 0.345088 | 12 446.0 |
| `force_register_args=(0,)` | 0.199680 | 672.2 | 0.345088 | 12 446.0 |
| `patched_aa` — A/A control, same code as the row above | 0.199680 | 672.2 | 0.345088 | 12 446.0 |

Paired per-round ratios against the workaround arm:

| Comparison | `mem` geomean ratio | `alu` geomean ratio |
|---|---|---|
| explicit `=r,r,r` / workaround | 1.00321 | 1.00006 |
| `force_register_args` / workaround | 1.00469 | 0.99687 |
| **A/A control / workaround** | **1.00957** | **1.01157** |

The A/A control deviates from the reference arm by *more* than the patched variant does (+0.96% / +1.16% versus +0.47% / −0.31%), so none of the difference is attributable to this change — everything sits inside roughly a ±1.2% noise band. That matches expectation: the materialized `mov` is loop-invariant and absorbed by register allocation.

The host is shared with other workloads, which is why the arms are paired and interleaved rather than measured in sequence. Outputs were compared as raw bit patterns, not with a tolerance; see the readback table in the description.
