## 正文

## Motivation

#3612: `TiledMMA::get_layoutC_TV()` disagrees with `ThrMMA::partition_C()` when the TiledMMA's thread layout has a K mode (`ThrK > 1`). The disagreement goes beyond wrong offsets: the returned layout maps threads **outside the C tile**. With the issue's example (`UniversalFMA`, thread layout `(2,3,4)`, a 2x3 C tile), `cosize(get_layoutC_TV())` is 24, and 18 of the 24 threads report offsets 6..23.

`get_layoutC_TV()` is also the input of `make_tiled_copy_C` / `make_tiled_copy_C_atom`, so those produce wrong tiled copies for such TiledMMAs as well.

## Root cause

`thrfrg_C` produces a thread mode `(ThrV,(ThrM,ThrN))`, which has no K mode. `get_layoutC_TV()` composes it directly with `thridx_2_thrid`, which maps `thr_idx` to a linear `(ThrV,ThrM,ThrN,ThrK)` index. When `ThrK > 1` that index runs past the thread mode's domain. For threads with K coordinate > 0, the composed layout then either extends beyond the tile or lands on the wrong element.

`get_layoutA_TV()` / `get_layoutB_TV()` avoid this. They first compose their thread mode with a tile that re-inserts the missing thread mode (N for A, M for B) with stride 0 (`atile` / `btile`), so it lines up with `(ThrV,ThrM,ThrN,ThrK)`. `get_layoutC_TV()` has no such step.

## Modifications

- `include/cute/atom/mma_atom.hpp`: add the missing `ctile`, which maps `(ThrV,(ThrM,ThrN))` to `(ThrV,(ThrM,(ThrN,ThrK)))` with stride 0 on `ThrK`, exactly like `atile` / `btile`. Threads that differ only in their K coordinate now map to the same C elements, as in `partition_C()`, which drops `ThrK`.
- New `test/unit/cute/core/tiled_mma.cpp` (host-only, in `cutlass_test_unit_cute_core`). For every thread and every value, it checks that `get_layout{C,A,B}_TV()` match `partition_{C,A,B}()` and stay inside the tile. It covers UniversalFMA with `ThrK` 1/2/4 (including a K-fastest thread order and a permuted tile) and `SM80_16x8x16_F32F16F16F32_TN` with `ThrK` 1/2/4 and permutations.

## Testing

**Correctness for `ThrK > 1`** (host, g++ 13). The check compares `get_layoutC_TV()(t,v)` with `partition_C` for every thread and value:

| TiledMMA | before | after |
|---|---|---|
| UniversalFMA thr (2,3,2) / (2,3,4) | 6 / 18 wrong, all out of tile | 0 |
| UniversalFMA thr (4,4,2) row-major; (2,2,2) K-fastest | 16 / 4 wrong | 0 |
| UniversalFMA thr (4,2,2), perm 16x8x4 | 128 wrong (only 32 out of tile, the other 96 are **silently wrong in-tile**) | 0 |
| SM80 16x8x16 thr (2,2,2) / (1,2,4) / (2,2,2) perm 32x32x32 | 512 / 768 / 1024 wrong | 0 |
| SM80 8x8x4 F64, SM75 16x8x8, SM70 8x8x4, thr (2,2,2) | 256 / 512 / 256 wrong | 0 |

The new unit test fails without the fix (2476 mismatches, 8 layouts reaching outside the tile) and passes with it.

**No change for `ThrK == 1`,** which covers all in-tree uses:
- *Layouts:* I dumped the full mappings of `get_layoutC_TV()`, `make_tiled_copy_C(...)` and `make_tiled_copy_C_atom(...)` (S/D TV layouts and tiler) with and without this change. The configurations were UniversalFMA, SM70/SM75/SM80 atoms with and without permutations, and SM90 GMMA 64x128x16 with 1 and 2 warpgroups, paired with UniversalCopy and `SM90_U32x{2,4}_STSM_N`. Across 14 configurations the 221,615 mapped values are **byte-identical**.
- *SASS:* I compiled four translation units twice, with only `mma_atom.hpp` differing, for `sm_80`, `sm_90a` and `sm_100a` (CUDA 12.8), and compared `cuobjdump -sass`. The dependency files confirm that each build picked up its own header. The SASS is **identical**:

  | `examples/50_hopper_gemm_with_epilogue_swizzle.cu` | SM70/80 vectorized `collective::Epilogue`, `make_tiled_copy_C` | 18 | 18,368 = 18,368 |

  Together these cover every in-tree caller of `make_tiled_copy_C` / `make_tiled_copy_C_atom` (`sm90_epilogue_tma_warpspecialized.hpp`, `sm70_epilogue_vectorized.hpp`, `cooperative_gemm.hpp`). The `_array` epilogue variants use the same calls.

### LiRunGuo · 2026-09-22

Thanks, that makes sense. My change makes the K-slices alias, which is the wrong thing for slice-K partials.

I checked what `get_layoutC_TV()` does on current `main` for `ThrK > 1` (host-side, every thread and value). Each K-slice is slice 0 shifted by a constant `tile_M * atom_N * ThrN`:

- If the tile is not extended along N, the shift equals the tile size, so each K-slice gets its own copy of the C tile. For example, `SM80_16x8x16`, thr `(2,2,2)`: shift 512, tile 512, no overlap.
- If the permutation extends N beyond `atom_N * ThrN`, the shift is smaller than the tile and the slices overlap. For example, `SM80_16x8x16`, thr `(2,2,2)`, `Tile<_32,_32,_16>`: shift 512, tile 1024, so half of slice 1 lands on slice 0. `UniversalFMA`, thr `(2,3,2)`, `Tile<_2,_6,_2>`: shift 6, tile 12.

`partition_C()` drops `ThrK`, so K-twins alias there in every case.

Could you confirm the intended contract? Is `get_layoutC_TV()` meant to map K-slice `k` to its own copy of the `(M,N)` tile, at offset `k * M * N`? If so, I'm happy to rework this PR to fix the N-extended overlap instead. If `ThrK > 1` isn't meant to be supported here, I'll close it.
