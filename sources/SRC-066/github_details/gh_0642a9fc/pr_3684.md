# [PR #3684] [CuTeDSL] Only parse -diagnostic itself from the command line

state: open | updated: 2026-09-26T13:34:21Z

## 正文

Fixes #3142

`python/CuTeDSL/cutlass/base_dsl/dsl.py`, `BaseDSL.diagnostic()`: argparse is no longer given
all of `sys.argv`. It gets only the `-diagnostic` / `-diagnostic=<value>` tokens and the token
right after each `-diagnostic`, in their original order. The parser is unchanged, so every form
of the flag behaves as before:

- `-diagnostic` enables `all`.
- `-diagnostic fail` and `-diagnostic=info` enable that type.
- `-diagnostic bogus` still exits with `invalid choice`.
- The last occurrence still wins.

Flags that belong to the host program never reach the parser, so the fix does not depend on
argparse's abbreviation handling on any Python version. A comment says why `allow_abbrev=False`
alone was not used.

`test/python/CuTeDSL/test_diagnostic_argv.py` (new): a regression test for #3142. It patches
`sys.argv`, runs `cute.compile` on an empty `@cute.jit` function, and records which debug types
the check turned on (it mocks `ir._GlobalDebug`, so no global MLIR debug state leaks). It checks
two things:

- `-d 0` and `-d fail` are ignored.
- `-diagnostic`, `-d 0 -diagnostic fail` and `-diagnostic=info` still work.

`cute.compile` turns the JIT cache off (`compile_only`), so `diagnostic()` runs on every call and
the test is deterministic. It needs no GPU.

### Verification

Setup: Ubuntu aarch64 without a GPU, `nvidia-cutlass-dsl==4.8.0` (cu12) in fresh venvs for
Python 3.10.21 and 3.12.14. The installed `base_dsl/dsl.py` is byte-identical to `main`, and I
replaced it with this branch's file for the "after" runs. `CUTE_DSL_NO_CACHE=1`.

Reproduction: a script with a `@cute.jit` function, compiled with `cute.compile`, run as
`python repro.py -d 0` and `python repro.py -d 0 -a R=64 -a N=256 --stopping-criterion entropy`.

- Before: on both Python versions it prints the same `usage: ... [-diagnostic [{all,fail,success,info,suggestion}]]`
  / `error: argument -diagnostic: invalid choice: '0'` as the issue and exits with code 2.
- After: it compiles and exits 0.
- `-d 0 -diagnostic fail` also compiles.

```yaml
Command: `python -m pytest -p no:cacheprovider -v test/python/CuTeDSL/test_diagnostic_argv.py`
Result:
```
- Before the fix: `2 failed` (both `SystemExit: 2`) on 3.12.14 and on 3.10.21.
- After the fix, on both versions:
  `test_diagnostic_argv.py::TestDiagnosticArgv::test_diagnostic_flag_is_parsed PASSED`,
  `test_diagnostic_argv.py::TestDiagnosticArgv::test_host_program_flags_are_ignored PASSED`,
  `2 passed`.

```yaml
Command: `python -m pytest -p no:cacheprovider -q test/python/CuTeDSL`
Result:
```
- Before the fix: `3 failed, 32 passed, 92 warnings, 412 subtests passed`.
- After the fix: `1 failed, 34 passed, 92 warnings, 412 subtests passed`.

Both results are the same on 3.12.14 and 3.10.21. The one failure left,
`test_vector_reduction_fastmath.py::TestVectorReduceFastmath::test_fastmath_flag`, fails the
same way without this change: `TypeError: Vector.reduce() got an unexpected keyword argument
'fastmath'`. The 4.8.0 wheel's `_mlir_helpers/vector.py` predates that change on `main`.

I also ran the old and new `diagnostic()` bodies with a stub `ir` module on CPython 3.9.6,
3.11.15, 3.12.12, 3.13.15 and 3.14.6, over 15 command lines. The new code gives identical
results on all five versions. Host flags (`-d 0`, `-d fail`, `-dia`, `-h`) no longer exit or
enable anything, and every exact `-diagnostic` form gives the same result as before.
