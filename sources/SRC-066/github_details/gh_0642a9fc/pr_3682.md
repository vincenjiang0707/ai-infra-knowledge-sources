# [PR #3682] [CuTeDSL] Restrict pickle.loads in signature metadata decoding

source: https://github.com/NVIDIA/cutlass/pull/3682
state: open | updated: 2026-09-26T10:47:14Z
labels: 

## 正文

Addresses #3403.

## Problem

`CuteSignatureProcessor.loads()` calls `pickle.loads()` on bytes decoded from an object file's `<prefix>_args_spec` global with no restriction, allowing arbitrary code execution via a crafted `__reduce__` payload when a module/artifact is loaded via `cute.runtime.load_module()` and its function is accessed. Reported in #3403 by @brandon-yujie-sun, with a working PoC.

## Threat model

By the time this path runs, the artifact's native code has already been JIT-linked (and any global constructors executed), so this is defense-in-depth, not the primary mitigation for untrusted artifacts — it removes a second, independent path to code execution reachable by tampering with a single metadata string alone, without needing a valid native payload at all.

## Design

Restricting *which classes can be looked up* (a module-prefix allowlist for `cutlass.`/`cuda.`) is not sufficient on its own: it still permits *calling* any callable in those namespaces via `REDUCE`, including real callables that already exist in this codebase (e.g. `cutlass.runtime.load_module`, which JIT-links an arbitrary path).

The fix separates the two privileges pickle normally conflates:
- **referencing** a class/callable as a plain value (`GLOBAL`/`STACK_GLOBAL`) — allowed for `cutlass.`/`cuda.`, since a referenced-but-uncalled annotation value is inert;
- **constructing or mutating** an object (`REDUCE`/`NEWOBJ`/`NEWOBJ_EX`/`INST`/`BUILD`) — allowed only for a fixed, closed identity set (`inspect.Signature`/`Parameter`/`_ParameterKind`, plus the narrow `operator.getitem`/`type(x)` forms CPython's own `typing.Optional`/`Union` pickling uses), enforced by overriding the pickle VM's own opcode handlers.

This requires subclassing `pickle._Unpickler` (the pure-Python implementation) rather than `pickle.Unpickler` — the C-accelerated `Unpickler` has no overridable per-opcode dispatch table, so overriding `load_reduce`/`load_build`/etc. on a subclass of it silently does nothing.

Custom annotation types are supported via explicit opt-in (`register_signature_type`) for the reference allowlist only — never for construction.

## Tests

`test/python/CuTeDSL/test_signature_processor_security.py`, 16 cases:
- the original report's `os.system` PoC is rejected;
- a realistic in-namespace gadget shaped like `cutlass.runtime.load_module` is rejected via `REDUCE` even though the class itself is a legitimate reference target;
- dotted-name namespace pivoting and dynamic class creation via `type(name, bases, ns)` are rejected;
- plain signatures, `Optional[X]`/`Union[X, Y]` annotations, and opt-in registered types round-trip unchanged.

Verified in a clean environment (no GPU/native `cutlass._mlir` build required for this module) via `pytest`.
