# [Issue #46295] [RFC]: Adaptive Speculation Depth for MoE Models via Per-Iteration Utility Budgeting

source: https://github.com/vllm-project/vllm/issues/46295
state: open | updated: 2026-09-23T04:09:01Z

## 正文

### Motivation.

Speculative decoding with a static `num_speculative_tokens` causes measurable
throughput **regressions** on MoE models (DeepSeek-V3, Qwen3-MoE, Kimi-K2,
Mixtral, etc.). This RFC proposes a lightweight, training-free, per-iteration
utility metric that dynamically adjusts speculation depth to prevent slowdowns
while preserving speedups when they are beneficial.

### The core problem: draft trees over-activate MoE experts

In dense LLMs, speculative decoding is reliably beneficial — the verifier
processes K draft tokens in a single forward pass at near-zero marginal cost.
For MoE models, this assumption breaks down.

A draft tree of K tokens collectively activates **many unique experts** across
the batch — often far more than K × top_k_experts — because different draft
tokens route to different experts. This causes:

1. **Expert weight bandwidth explosion** — each unique expert must be fetched from HBM
2. **EP all-to-all volume increase** — more unique destination ranks per step
3. **Verification time scaling with unique experts**, not just token count

Recent empirical results quantify this regression:

| Static K | Unique experts vs K=0 | Verification overhead | Net throughput |
|---|---|---|---|
| 1 | ~1.3× | 1.1× | +10% |
| 4 | ~3.2× | 1.9× | −15% (slowdown) |
| 8 | ~6.1× | 2.4× | **−35% (severe slowdown)** |

The [Cascade paper (arXiv:2506.20675)](https://arxiv.org/abs/2506.20675)
implements an adaptive K controller in vLLM and shows that static K=4 causes
**up to 1.5× slowdown** on code/math workloads with DeepSeek-V3, while
adaptive K limits slowdown to 5% and yields **7–14% throughput improvement**
over the best static K choice.

This aligns directly with the Q2 2026 roadmap goal of
["composable speculation"](https://github.com/vllm-project/vllm/issues/39749)
and the active tracking issue
[#28947](https://github.com/vllm-project/vllm/issues/28947).

### Proposed Change.


### Core idea: per-iteration speculation utility as a dynamic K controller

Define **speculation utility** U at each decoding step as:

```
U = accepted_tokens_this_step / expert_activation_overhead_this_step
```

where:
- `accepted_tokens_this_step` — already tracked by the rejection sampler
- `expert_activation_overhead_this_step` — ratio of unique expert indices
  activated with speculation vs without; derived cheaply from the existing
  `topk_ids` tensor inside `FusedMoE.forward()` (zero additional compute)

**Control loop (test-and-set, no bandit, no training):**
- **Test phase** (short window, ~20 iterations): measure rolling U at current K
- **Set phase** (long, ~100 iterations): lock in K that maximized U
- If U < 1.0 for N consecutive steps → reduce K (or disable speculation)
- If U > threshold for M consecutive steps → restore K toward the configured max


### Codebase changes

**1. `vllm/model_executor/layers/fused_moe/` — `FusedMoE.forward()`**
Expose `unique_expert_count` as a side-channel output from the existing
`topk_ids` tensor:
```python
unique_expert_count = topk_ids.unique().numel()  # already computed, near-zero cost
```
This requires no new kernels and no change to the forward pass computation.

**2. `vllm/v1/spec_decode/` — new `MoESpecUtilityTracker` class**
```python
class MoESpecUtilityTracker:
    def update(self, accepted: int, unique_experts: int) -> None: ...
    def recommended_k(self, max_k: int) -> int: ...
    def reset(self) -> None: ...
```
Stateless across requests; operates on iteration-level aggregates.

**3. `vllm/v1/spec_decode/` — scheduler integration**
Wire `recommended_k()` into the step that sets `num_speculative_tokens` for
the next iteration. The adapted K is bounded by the user-configured max.

**4. `SpeculativeConfig` — new optional fields**
```python
moe_adaptive_spec: bool = False          # opt-in; no-op on dense models
moe_utility_threshold: float = 1.0      # U < threshold → reduce K
moe_utility_window: int = 20            # rolling window size (iterations)
```

**5. Telemetry (`vllm/v1/spec_decode/metrics.py`)**
Add per-step logging of `spec_utility`, `active_k`, `unique_experts_activated`
for observability via existing Prometheus / W&B integration.

### What does NOT change
- Token acceptance logic (rejection sampler) — unchanged
- Draft model (EAGLE / MTP / n-gram / DFlash) — unchanged  
- Verification pass — unchanged
- Non-MoE models — the tracker is a no-op when no `FusedMoE` layer is present
- Existing `speculative_config` API — fully backward-compatible; new fields are optional

### Example API (no breaking change)
```python
llm = LLM(
    model="deepseek-ai/DeepSeek-V3",
    speculative_config={
        "method": "mtp",
        "num_speculative_tokens": 4,   # upper bound; adapted downward at runtime
        "moe_adaptive_spec": True,
        "moe_utility_threshold": 1.0,
        "moe_utility_window": 20,
    },
)
```

### Open questions for discussion

1. **Where to compute `unique_expert_count`?** Preferred: inside
   `FusedMoE.forward()` from the existing `topk_ids` — zero overhead.
   Alternative: post-hoc from telemetry logs (higher latency, less useful).

2. **Discrete vs continuous K adaptation?** Cascade uses discrete
   K ∈ {0, 1, 2, 4}. Continuous adaptation (probabilistically drop the
   last speculative token) is possible but adds sampler complexity.

3. **Interaction with EPLB?** EPLB already rebalances experts across EP ranks.
   Should the utility metric count unique expert *ranks* rather than indices
   under wide-EP (e.g. 64-way EP for DeepSeek-V3)?

4. **Scheduler vs model-runner level?** The scheduler controls K for the next
   step; the model runner has `topk_ids` from the current step. A one-step
   feedback loop is simplest. Is this the right boundary?

5. **Interaction with MTP > 1 spec token for DeepSeek V3.2**
   (see [#31845](https://github.com/vllm-project/vllm/issues/31845)) —
   should adaptive K take priority over or compose with the MTP-specific
   per-model limits?

The key distinction from the Cascade paper's external implementation is that
this RFC proposes integrating the utility controller **natively into vLLM's
scheduler and model runner**, rather than as a wrapper, making it composable
with async scheduling, EPLB, and all existing draft methods (MTP, EAGLE,
n-gram, DFlash) without modification.

### harshithkantamneni · 2026-09-23

Measurement results for this RFC, as promised in my earlier comment. Short version: on this setup (Qwen3-30B-A3B, CPU ngram, one H200, two synthetic workloads) drafts do add measurable expert reads, but little is left to gain over vLLM's static Dynamic SD table (#32374): knowing each workload's best K beats the best static table by at most 1.8% at any measured batch size, under the 5% bar I set before running. So the data does not support adding an expert-aware controller here. It does not rule out a per-step controller that adapts K within a request, which I did not build or measure. Details below.

**Setup.** Qwen/Qwen3-30B-A3B-Instruct-2507 (bf16, 128 experts, top-8, 48 MoE layers), 1x H200 SXM, vLLM main at ecdd11d0e, V1 runner, PIECEWISE CUDA graphs up to 1024, `method: ngram` (CPU proposer, `prompt_lookup_min=2`, `max=4`). Grid K in {0,1,2,4,8} x batch size in {1,4,16,64}, 1024 input / 256 output tokens, greedy, 3 repeats. Two workloads: sonnet line-copy (ngram-friendly) and plain prose. Distinct experts per verify step counted on device from `topk_ids` via a router `capture_fn`; timing from separate passes with the probe off.

**1. Drafts do route to extra experts, but real routing is far from uniform.**

| B | K=0 distinct/layer (sonnet) | uniform prediction (K=0) | K=8 distinct/layer (sonnet) |
|---|---|---|---|
| 1 | 8.0 | 8.0 | 17.0 |
| 4 | 22.0 | 29.1 | 32.7 |
| 16 | 41.9 | 82.4 | 50.9 |
| 64 | 60.9 | 125.9 | 65.0 |

At B=1 and K=8, on steps where the request drafted all 8 tokens, the verify step touches 3.4x the experts of the committed token alone (370 steps pooled over both workloads; 3.2x on sonnet). At B=64 the batch touches about half of the 128 experts (61 per layer at K=0, 65 at K=8), so the expert axis has range well past where uniform routing says it saturates.

**2. The byte model explains verify time; the expert term is significant.** Fitting verify time on predicted bytes with measured distinct experts: R^2 0.956 at an effective 3.79 TB/s. Token count alone: R^2 0.759. At fixed batch size, routed-expert bytes explain 76% of the remaining variance after token count and non-expert bytes (block-permutation p = 0.001). Side note: vLLM's MFU byte model assumes every routed token hits a distinct expert (`min(T*k, E)`, vllm/v1/metrics/perf.py:1290-1291); fitting with that gives R^2 0.730 at an implied 9.0 TB/s, above the H200's peak, i.e. it overcounts routed-expert reads by up to 3x here (at K=0: 1.5x at B=4, about 3x at B=16, 2.1x at B=64).

**3. But the cost is modest, and a batch-size table captures most of the gain.** Sonnet, verify ms K=0 to K=8: B=1 5.22 to 6.14, B=4 6.01 to 7.63, B=64 13.00 to 15.70. By the bar I set before running (B=1 verify time at K=8 at least 1.5x K=0), the cost result is a miss: 1.12x pooled over both workloads. Throughput, sonnet, vs K=0: B=1 K=2 +15.9%; B=4/16/64 K=1 +3.7% / +3.0% / +2.4% and K=8 -4.9% / -3.7% / -8.8%, where the B=4 gain and both B=16 numbers are within repeat noise. On prose, K=0 is best from B=4 up (K=1 costs 2 to 5%). At B=1 and 4 the best fixed K (0 to 2) is below both the acceptance-maximizing K and the K a flat-cost model picks, so draft cost matters for choosing K. Knowing each workload's best K (a per-workload oracle) beats the best static `num_speculative_tokens_per_batch_size` table by only 0.0% / 1.8% / 1.2% / 1.2% at B = 1 / 4 / 16 / 64, under the 5% bar I set in advance. That measures only what identifying the workload is worth, not what a per-step controller adapting K within a request could get. The distinct-expert count from 2 steps earlier (what a scheduler-side controller would see) does explain per-step tokens/s within a (B, K) cell (partial R^2 0.238, block-permutation p = 0.002), but that regression does not control for draft length or workload, so part of it may be ngram match streaks or workload identity rather than anything MoE-specific. A threshold on it, fitted on two repeats and scored on the third, picked each workload's best K at B=4 and B=16 (+1.8% and +0.8% over the table) but not at B=64.

**4. Dynamic SD works with CPU ngram.** The docs list it as tested with Eagle/Eagle-3/DFlash only. On this pin the fitted table `[[1,1,2],[2,4,0],[5,16,1],[17,64,0]]` with `method: ngram` ran cleanly: the K handed to the proposer matched the table lookup on all 5,868 steps with this table (7,810 counting an earlier test table), and this table's throughput matched the fixed-K cells within noise, except that its K=0 entries cost 0.6 to 1.8% against no speculation. Per #46399 (open), `ngram_gpu` asserts `num_speculative_tokens == self.k` (ngram_proposer_gpu.py:340 at this pin), so a table that picks K below the max crashes it; that PR would disable the table with a warning and fall back to static K. I did not run that combination.

**Caveats.** One model, one drafter with low acceptance (0.36 to 0.52 at K=1, 0.06 to 0.11 at K=8), one GPU, two synthetic workloads at fixed 1024/256 lengths in offline batches; a more varied workload mix could leave more headroom than two workloads can show. With a stronger drafter both accepted length and the expert term grow, so the result may differ; EAGLE3 heads exist for this model and that is the obvious next measurement. Compared with #48202: there, on dense Qwen3-4B up to batch 64, trimming DSpark proposals by confidence did not beat full blocks because verify cost was nearly flat in verified tokens. Here, on MoE, verify cost is not flat at batch 1 to 4 (K=0 to K=8: sonnet +18% at B=1 and +27% at B=4, prose +7% and +16%). Speculation clearly pays only at B=1 on sonnet (+16% at K=2); at B=4 the sonnet gain (K=1, +3.7%) is within noise and prose loses 5% (K=1) to 12% (K=8).

Happy to share the harness and raw per-step data.
