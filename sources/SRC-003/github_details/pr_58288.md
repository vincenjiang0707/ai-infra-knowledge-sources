# [PR #58288] [Bugfix][Core] Hash every multimodal input in a block finished by generation

state: open | updated: 2026-09-23T06:53:41Z

## 正文

## Purpose

`request_block_hasher` starts the multimodal scan at the **last** mm input whenever it is not hashing from token 0:

```python
# vllm/v1/core/kv_cache_utils.py
curr_mm_idx = 0
if start_token_idx > 0:
    # Set curr_mm_idx = -1 to indicate the last mm input.
    # Note that since we reach to this branch only when the block is
    # completed with generated tokens, we only need to consider the
    # last mm input.
    curr_mm_idx = -1
```

The premise in that comment does not hold. The block completed by generated tokens is the same block that held the tail of the prompt, and that block can overlap **more than one** mm input — the end of the second-to-last one, plus a last one shorter than the block. Starting at the last one drops the others from the block's extra keys.

So the block hash depends on *when* it was computed. With `block_size=16` and mm inputs at `(offset=17, length=2)` and `(offset=20, length=2)`, the extra keys for the block spanning tokens 16..31 are:

| how the block was hashed | extra keys |
|---|---|
| in the same pass as block 0 (prompt completed it) | `(('mm_first', 1), ('mm_second', 4))` |
| in a later pass (generation completed it) | `(('mm_second', 4),)` |

Two consequences:

**1. Same prefix, two different hashes.** The block is written to the prefix cache under one key and looked up under another.

**2. Different prefixes, same hash.** Two requests whose only difference is the dropped mm input produce the *same* block hash, so one can be served prefix-cache KV that was computed for a different image:

```
A: mm inputs ["mm_cat",   "mm_shared"]  ->  block 1 hash  X
B: mm inputs ["mm_dog",   "mm_shared"]  ->  block 1 hash  X     # collision
```

The one-shot path keeps these distinct, so this only bites once the block has been completed by generation — i.e. after the first decode steps of a request whose prompt does not end on a block boundary and whose last partial block holds two mm inputs.

`vllm/v1/core/block_pool.py` builds the `BlockStored` event's extra keys for the partial block with the same `-1 if block_start > 0 else 0`, so external KV-cache consumers were handed the same truncated key set.

## Changes

- `kv_cache_utils.py`: scan from the first mm input (`curr_mm_idx = 0`) in `request_block_hasher`.
- `block_pool.py`: same, for the `BlockStored` partial-block event.

**This is not a hot-path cost.** `_gen_mm_extra_hash_keys` already returns immediately when every mm input ends at or before `start_token_idx`:

```python
last_pos = mm_features[-1].mm_position
if last_pos.offset + last_pos.length <= start_token_idx:
    return extra_keys, start_mm_idx
```

which is the steady state during decode. Only the single block that still straddles the prompt tail walks the list, and that walk is bounded by the number of mm inputs on the request.

`_gen_mm_extra_hash_keys` keeps its negative-`start_mm_idx` support; after this change nothing passes a negative value, so it can be dropped too if you would rather not leave the branch around — I left it out of this diff to keep the change to the bug.

### haosenwang1018 · 2026-09-23

One more thing on reachability, since the two tests use a 16-token hash block and short placeholders and that reads like a corner case.

The precondition is "two mm items intersect the final partial block", which needs the **last** item to be shorter than `hash_block_size`. That is only exotic when `hash_block_size` is 16. It often is not:

- `get_kv_cache_block_sizes`, single group: `bs = cache_config.block_size * dcp` — so `hash_block_size` is 128 with `--block-size 16 --decode-context-parallel-size 8`.
- Multiple groups: the LCM of the group block sizes when a mamba group is outside `align` cache mode, i.e. the mamba block size, which is in the hundreds to thousands.

At those sizes an ordinary image, audio segment or video frame placeholder is shorter than one hash block. Concrete run on `main` with `hash_block_size=128`, an image at tokens 700-899 and an audio segment at 920-989, prompt 1000 tokens, decoding past 1024:

```
block 7 (896..1023) extra keys, hashed with the prompt : (('image_0', -196), ('audio_0', 24))
block 7 (896..1023) extra keys, hashed after generation: (('audio_0', 24),)

blocks 7 and 8 both differ from the one-shot hashes
```

`image_0` is dropped and, because the hashes are chained, every later block inherits the wrong key.

### haosenwang1018 · 2026-09-23

Last piece of evidence, then I will stop adding to this.

The two tests in the PR pin two hand-picked layouts. The property behind them is more general, and it is the one that matters for a cache key:

> changing one multimodal input must change the hash of **every** block that covers it.

If that does not hold, two prompts that differ in an image can share a block hash, and the prefix cache can hand one of them the other's KV.

Fuzzing that property directly over random layouts (block size in {1,2,4,8,16}, up to 3 non-overlapping placeholders, prompt ending anywhere at or after the last one, then decoding to the end):

| | trials | violations |
|---|---|---|
| `main` | 3000 | 1 |
| this PR | 3000 | 0 |

The counterexample on `main`:

```
block_size=16  total=67  prompt_len=63
mm = [(offset=10, length=22), (offset=50, length=8), (offset=59, length=3)]
changing mm[1]'s identifier leaves block 3 (tokens 48..63) unchanged
```

Block 3 covers the tail of mm[1] and all of mm[2], the prompt ends inside it at token 63, and generation completes it — so it is hashed on the second pass, which starts at mm[2] and drops mm[1].

The same run also checks that a different `cache_salt` changes every block; that holds on both.

Happy to land the fuzz as a property test instead of, or in addition to, the two fixed cases if you would prefer that shape.
