### jahnclawdmonet · 2026-09-16

The `rtx_pro_6000_4x` override on this recipe's NVFP4 (`default`) variant carries `--moe-backend marlin`, alongside `--max-num-seqs 16`, `--gpu-memory-utilization 0.95`, `--max-num-batched-tokens 8192` and `--enable-prefix-caching`. The FP8 variant's override for the same hardware row has the other four and no `--moe-backend`. The command in the report has no `--moe-backend`, so the backend was auto-selected, and the traceback names `FLASHINFER_CUTLASS`.

On `0.1.dev20073+g8e685d198`, MARLIN is a separate branch of `convert_to_nvfp4_moe_kernel_format` in `fused_moe/oracle/nvfp4.py` and does not call `prepare_nvfp4_moe_layer_for_fi_or_cutlass`. Its own preparation pads the rank-local intermediate at `marlin_utils_fp4.py:374-387`, taking the `K % 128 == 0` branch at `hidden_size` 2560, so `round_up(160, 64) = 192` applied to the gate and up shards separately.

The failure is a row-count mismatch. `text_config.moe_intermediate_size` is 640, so under four-way MoE sharding the stacked gate and up rows of `w13` are `2 * 160 = 320`, while `swizzle_blockscale` rounds the scale rows up to `round_up(320, 128) = 384`. That leaves `pad_size` 64 at `flashinfer_fp4_moe.py:423`, and the non-TRTLLM branch raises at 426 rather than padding when padding is needed and `is_act_and_mul`. I reproduced those two calls with synthetic tensors in `vllm/vllm-openai:qwen38-flash-next`, the arm64 build of the same version where the report is x86_64: pad 0 at two-way and unsharded, 64 at four-way, 96 at eight-way. The divisor is the MoE tensor-parallel size rather than `--tensor-parallel-size` as such, and expert parallelism sets it to 1.

#48624 is open against this raise. #42516 hit it on Gemma-4-26B-A4B at TP 2 on the `cutlass` backend, though it is labelled stale and bundles two unrelated pipeline-parallel items.

`--moe-backend marlin` routes around this particular raise. I have not run this model on four 5090s, so I cannot say the server then starts. That hardware row is four RTX PRO 6000 and the NVFP4 variant lists `vram_minimum_gb` 130 against 4 x 32 GB here, but the weights did reach 21/21 in your log before the raise, and I have not measured how much of that figure still applies with `VLLM_PLE_CPU_OFFLOAD=1`.
