# [PR #58064] [Bugfix][Transformers backend] Fix CUDA graph capture for dynamic-rope models

source: https://github.com/vllm-project/vllm/pull/58064
state: open | updated: 2026-09-23T03:15:14Z
labels: bug, ci/build, nvidia

## 正文

## Purpose

A model with `rope_type: "dynamic"` served through the Transformers modeling backend cannot
start at all under CUDA graph capture. Engine startup dies during `determine_available_memory`:

```
File ".../vllm/v1/worker/gpu/cudagraph_utils.py", line 386, in capture
    with torch.cuda.graph(
...
File ".../transformers/models/hunyuan_v1_dense/modeling_hunyuan_v1_dense.py", line 436, in forward
    position_embeddings = self.rotary_emb(hidden_states, position_ids=position_ids)
File ".../transformers/modeling_rope_utils.py", line 125, in wrapper
    dynamic_frequency_update(self, position_ids, device=x.device, **kwargs)
File ".../transformers/modeling_rope_utils.py", line 100, in dynamic_frequency_update
    if seq_len > max_seq_len_cached:  # growth
       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
torch.AcceleratorError: CUDA error: operation not permitted when stream is capturing
Search for `cudaErrorStreamCaptureUnsupported' ...

RuntimeError: Engine core initialization failed.
```

Transformers wraps every RoPE `forward` with `@dynamic_rope_update`, which computes
`torch.max(position_ids)` and branches on it. Reading that value back to the host is illegal
inside a capturing stream, so the capture is invalidated and the engine never comes up. The
only workaround today is to give up CUDA graphs entirely (`cudagraph_mode=NONE`, or
`--enforce-eager`).

#23738 made `can_enable_torch_compile` return `False` for these models, which stops
`torch.compile` from tripping over the same branch, but CUDA graph capture is wrapped at the
model-runner level independently of whether the model was compiled, so the crash path was left
open. This PR closes it.

The observation that makes a fix possible: the update is frequently dead code. It only
recomputes `inv_freq` once positions grow past `max_seq_len_cached` (initialised to
`max_position_embeddings`), and only restores the original `inv_freq` after such a growth has
happened. vLLM never emits a position beyond `max_model_len`, so whenever the context is capped
at or below `max_position_embeddings` **both branches are unreachable** and the decorator is
pure overhead — overhead that happens to be fatal under capture.

This PR:

1. Adds `dynamic_rope_update_is_noop(vllm_config)`: `max_model_len <= max_position_embeddings`.
2. Removes the decorator from the decoder's RoPE modules when that holds
   (`remove_noop_dynamic_rope_update`), restoring the `@torch.no_grad()` that Transformers
   stacks on top of it.
3. Lets `can_enable_torch_compile` return `True` in exactly that case, since the reason it was
   returning `False` no longer exists once the branch is gone.

Two deliberate exclusions:

- **Encoders.** The sweep is scoped to `model.get_decoder()`, because `max_model_len` bounds
  decoder positions only — it says nothing about what an encoder/vision tower is fed.
- **`longrope`.** It reassigns `inv_freq` at any context length, so its modules keep the
  decorator.

One implementation note for reviewers: the decorator is identified by the *code object* of the
wrapper `dynamic_rope_update` returns, not by `forward.__wrapped__`. Transformers writes
`@torch.no_grad()` **above** `@dynamic_rope_update`, and `no_grad` also uses `functools.wraps`,
so `forward.__wrapped__` is the dynamic wrapper itself — unwrapping one level would silently
drop `no_grad` while leaving the update in place.

### Scope

This only helps when `max_model_len <= max_position_embeddings`. For a dynamic-rope model whose
context is genuinely scaled past the pretrained length, the update is live, the decorator stays,
and behaviour is unchanged — including the capture failure, which is correct, since the sync is
real there.

### Not a duplicate

- No open PR touches `can_enable_torch_compile` or `dynamic_rope_update` (searched
  `can_enable_torch_compile`, `dynamic_rope_update`, `"dynamic rope" in:title`, and open PRs on
  the Transformers backend).
- The only prior work in this area is #23738, which this PR completes rather than reverts:
  dynamic-rope models that *can* still rescale within `max_model_len` remain uncompiled, exactly
  as that PR intended.

## Test Plan

New CPU-only unit tests:

```bash
pytest tests/models/transformers/test_dynamic_rope.py -v
```

They assert observable behaviour through the public forward — whether an over-long
`position_ids` still rewrites `inv_freq` — rather than inspecting how the decorator is attached:

- the no-op predicate at and around the `max_position_embeddings` boundary;
- `can_enable_torch_compile` for default / dynamic / per-layer-type rope;
- the update is gone when it cannot fire, and the remaining forward is numerically identical and
  still runs under `no_grad`;
- the update is kept when rescaling is reachable, and for `longrope`.

### Accuracy

this change) versus the patched server above:

| Metric | n | Baseline (`cudagraph_mode=NONE`) | With this change | Delta |
|---|---|---|---|---|
| prompt_level_strict | 541 | 72.6% | 72.5% | -0.1 |
| inst_level_strict | 834 | 79.3% | 79.1% | -0.2 |
| prompt_level_loose | 541 | 74.1% | 74.3% | +0.2 |
| inst_level_loose | 834 | 80.3% | 80.5% | +0.2 |

All four deltas are within 0.2pp, against a binomial 1-sigma of roughly 1.4-1.9pp at these
sample sizes, and they do not share a sign. The model's `generation_config.json` enables
sampling (`temperature: 0.7`, `top_k: 20`, `top_p: 0.8`), so exact agreement was never expected
once compilation and graph capture change kernel selection.

Note the two runs are not the same server config — they cannot be, since the baseline config
does not start. The comparison is `cudagraph_mode=NONE` without the fix versus `cudagraph_mode=FULL` with it.
Where the numbers can move at all is worth being precise about: removing the decorator is
bit-identical at the RoPE layer, which `test_removal_does_not_change_frequencies` asserts
directly. Any end-to-end difference comes from compilation and capture now being available for
this model, which is the same position every other compiled model is in.

### YongfengX · 2026-09-23

@hmellor I saw your comment in the email but I failed to find it in the PR. 

Apologies for the oversight here. I hit this bug serving a model of our own and used AI assistance to work through the fix, and I clearly didn't think the interaction between the two decisions through carefully enough. Thanks for catching it — the mixed-rope case you led me to is a genuine regression in what I proposed.

The placement can't work as written.

`_decorate_for_torch_compile` decorates the class ` (_pre_trained_model_classes.decoder)`, so there is no model instance at that point to walk. And `enable_if `is evaluated inside the patched `__init__ `(compilation/decorators.py:387), i.e. during `AutoModel.from_config`, which is still earlier than any point where the instance exists. So the compile decision is necessarily made before the stripping can happen.

But that ordering is exactly the problem you're pointing at: `can_enable_torch_compile` is predicting what `remove_noop_dynamic_rope_update` will do, and in the current patch it can predict wrong. The stripping has bail-out branches the config-level check doesn't know about. The one that matters today:

```
rope_parameters = {"full_attention": {"rope_type": "dynamic"},
                   "sliding_attention": {"rope_type": "longrope"}}
```

`can_enable_torch_compile` sees `any(... == "dynamic")` and enables compile; the stripping sees longrope in the module's `rope_type` and bails. Compiled model, decorator still there. Before this PR that config returned `False `and was safe, so this is a regression I introduced.

Proposed fix — move the condition the two need to agree on up into the predicate, and make the remaining bail-outs loud instead of silent:

```
rope_types = {rp["rope_type"] for rp in rope_parameters.values()}
if "dynamic" in rope_types:
    # A layer type on longrope keeps the decorator, and with it the sync
    if "longrope" in rope_types:
        return False
    return dynamic_rope_update_is_noop(vllm_config)
```

and in `remove_noop_dynamic_rope_update`, warn when a dynamic non-longrope module turns out not to be strippable (no `max_seq_len_cached`, or the decorator can't be located — both "shouldn't happen" paths that would otherwise leave a compiled model with the sync in it).

I'll add a test covering the mixed dynamic/longrope config. Does that address what you had in mind?
