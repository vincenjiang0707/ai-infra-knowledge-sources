- One NVIDIA H100 80 GB; Python 3.12.3; CUDA 13.0.

- Runtime environment: `VLLM_USE_FLASHINFER_SAMPLER=0`, `VLLM_USE_DEEP_GEMM=0`, `VLLM_MOE_USE_DEEP_GEMM=0`, `VLLM_DEEP_GEMM_WARMUP=skip`.

### Describe the bug

With streaming, thinking enabled, and `tool_choice="auto"`, a text grammar can admit ordinary vocabulary tokens that spell `</think>`, `<tool_call>`, and `</tool_call>`. The Qwen parser can then retain the entire valid-looking invocation in reasoning and emit no structured call. Replacing only those delimiter token sequences with their dedicated IDs preserves the decoded text exactly but restores the structured call.

This is a grammar/parser boundary-contract issue: requiring delimiter *strings* in EBNF does not necessarily enforce the token IDs the parser recognizes. The provider-side failure reproduced by calling vLLM HTTP directly; no gateway or agent adapter was involved.

Related: #39056 and the parser rewrite #45413. This report isolates the delimiter-token representation, including a tool block textually **after** `</think>`, rather than requiring the model to emit an invocation textually inside reasoning. It also differs from #56658, which concerns quoted markers followed by prose instead of a real invocation.

### Token-level causal control

For the tested tokenizer:

| Boundary | Dedicated ID | Ordinary IDs observed in generated failure |
| --- | --- | --- |
| `</think>` | 248069 | `[27, 14, 26003, 29]` |
| `<tool_call>` | 248058 | `[27, 13766, 13042, 29]` |
| `</tool_call>` | 248059 | `[510, 13766, 13042, 29]` |

We verified identical decoded text before comparing the two token sequences. Both tagged parser implementations returned the expected call after delimiter-only normalization; both lost it with the original ordinary-token boundaries.

### Synthetic parser reproduction

This example contains only synthetic `echo` input. It uses the installed parser imports and needs the tokenizer, but no model weights or inference. Pass a local tokenizer.json path as the optional first argument, or allow the public tokenizer download.

**Validation caveat:** locally we executed this example against unchanged tagged parser implementations through a CPU import shim, which substitutes request/protocol plumbing and omits GPU/server imports. It is not a fresh installed-package test of both versions. The separate v0.23.0 H100 experiment below exercises the actual HTTP server. Please run the example in a normal installed vLLM environment to confirm independently.

```python
import json
import sys
from tokenizers import Tokenizer
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest

# No model weights or inference needed. Optional argument: local tokenizer.json.
core = (Tokenizer.from_file(sys.argv[1]) if len(sys.argv) > 1 else
        Tokenizer.from_pretrained('Qwen/Qwen3.6-35B-A3B-FP8'))

class TokenizerAdapter:
    def get_vocab(self):
        return core.get_vocab()
    def decode(self, ids, **kwargs):
        return core.decode(ids, skip_special_tokens=False)
    def encode(self, text, **kwargs):
        return core.encode(text, add_special_tokens=False).ids

tokenizer = TokenizerAdapter()
try:  # v0.24.0
    from vllm.parser.qwen3 import Qwen3Parser as Parser
except ImportError:  # v0.23.0
    from vllm.parser.abstract_parser import DelegatingParser
    from vllm.reasoning.qwen3_reasoning_parser import Qwen3ReasoningParser
    from vllm.tool_parsers.qwen3coder_tool_parser import Qwen3CoderToolParser
    class Parser(DelegatingParser):
        reasoning_parser_cls = Qwen3ReasoningParser
        tool_parser_cls = Qwen3CoderToolParser

request = ChatCompletionRequest(
    model='qwen', messages=[{'role': 'user', 'content': 'Echo hello.'}],
    tools=[{'type': 'function', 'function': {'name': 'echo', 'parameters': {
        'type': 'object', 'properties': {'text': {'type': 'string'}},
        'required': ['text']}}}],
    tool_choice='auto', stream=True, parallel_tool_calls=True,
    chat_template_kwargs={'enable_thinking': True},
)
raw = ('I will echo.\n</think>\n\n<tool_call>\n<function=echo>\n'
       '<parameter=text>\nhello\n</parameter>\n</function>\n</tool_call>')
dedicated = tokenizer.encode(raw)
replacements = {
    core.token_to_id('</think>'): [27, 14, 26003, 29],
    core.token_to_id('<tool_call>'): [27, 13766, 13042, 29],
    core.token_to_id('</tool_call>'): [510, 13766, 13042, 29],
}
ordinary = [part for token in dedicated for part in replacements.get(token, [token])]
assert tokenizer.decode(dedicated) == tokenizer.decode(ordinary) == raw
for label, ids in [('dedicated', dedicated), ('ordinary', ordinary)]:
    parser = Parser(tokenizer, request.tools, chat_template_kwargs={'enable_thinking': True})
    reasoning, calls = '', {}
    for i, token in enumerate(ids):
        delta = parser.parse_delta(tokenizer.decode([token]), [token], request,
                                   [core.token_to_id('<think>')], finished=i == len(ids)-1)
        if delta is None:
            continue
        reasoning += delta.reasoning or ''
        for call in delta.tool_calls or []:
            item = calls.setdefault(call.index, {'name': '', 'arguments': ''})
            if call.function:
                item['name'] += call.function.name or ''
                item['arguments'] += call.function.arguments or ''
    print(label, json.dumps({'calls': list(calls.values()), 'all_text_in_reasoning': reasoning == raw}))
```

Observed on both v0.23.0 and v0.24.0 in the CPU harness:

```text
dedicated {"calls": [{"name": "echo", "arguments": "{\"text\": \"hello\"}"}], "all_text_in_reasoning": false}
ordinary {"calls": [], "all_text_in_reasoning": true}
```

Expected: the real invocation is exposed consistently, or the incompatible grammar/parser boundary contract is rejected or reported explicitly. An ordinary successful final response with no call silently loses the requested action. This is not a request to execute arbitrary quoted markup from reasoning.

### Actual generation and prevention experiment

We used a private multi-turn request, so its prompt and captures are not included here. The synthetic example above isolates the parser condition without that data.

The first full-server batch had 13/13 ordinary requests return parsed calls. To exercise the alternative encoding, we added this **controlled intervention**, not a production-default setting:

```json
{"logit_bias":{"248069":-100,"248058":-100,"248059":-100},"return_token_ids":true}
```

With the original text EBNF, the server generated ordinary-token boundaries and returned a complete stream with populated reasoning, no structured calls, empty content and `finish_reason="stop"`. All 1,096 generated tokens were captured and matched reported completion usage. The delimiter-only CPU control on those IDs restored the call with decoded text unchanged.

A fresh one-H100 comparison then tested dedicated-token enforcement using XGrammar structural-tag `sequence` elements containing `{"type":"token","token":248069}` and corresponding tool-boundary IDs, retaining the action argument grammar:

| Request constraint | Boundary-token suppression | Parsed structured calls |
| --- | --- | --- |
| Original text EBNF | -100 on the three IDs | 0/1; failure reproduced again |
| Token-aware candidate | None | 3/3 |
| Token-aware candidate | Same -100 intervention | 3/3 |

All seven captures were complete. Each candidate response emitted exactly one structured call with JSON-object arguments, `finish_reason="tool_calls"`, and one occurrence of each dedicated boundary ID. One suppressed candidate generated 7,865 tokens, so these small controlled tests are not a production-ready quality/latency validation.

On XGrammar 0.2.5.post1, CPU mask/matcher checks also found that the original grammar accepts all eight combinations of ordinary/dedicated boundaries, while the token-aware candidate accepts only the all-dedicated combination. A separate synthetic exact-text EBNF check accepts both encodings of the `echo` example above.

### Scope and suggested regression coverage

- These experiments establish the controlled failure mechanism, not a natural production failure rate or the cause of an incident lacking raw token IDs.
- Ordinary `</think>` alone is **not** a sufficient failure detector: a separate generated response with dedicated tool boundaries still parsed successfully.
- Test ordinary/dedicated/mixed boundary encodings, chunk boundaries, valid final text, and quoted protocol examples. Do not blindly promote arbitrary reasoning markup into executable calls.
- Is token-aware boundary enforcement the intended requirement for user-supplied text grammars with these parsers, or should the parser recognize the equivalent text boundaries? A validation error or documented constraint would also help avoid silent loss.

Relevant issues were searched before filing. AI assistance was used to run the experiments and draft this report.

### he-yufeng · 2026-09-22

Independently confirmed on current main (54020c3c3e) with the synthetic harness, through the installed `vllm.parser.qwen3.Qwen3Parser` path (no shim):

```
dedicated {"calls": [{"name": "echo", "arguments": "{\"text\": \"hello\"}"}], "all_text_in_reasoning": false}
ordinary {"calls": [], "all_text_in_reasoning": true}
```

The boundary contract as I read it in the tree: `qwen3_config()` puts the four boundaries in `token_id_terminals`, so the streaming engine keys `</think>`, `<tool_call>` and `</tool_call>` by their dedicated IDs. Nothing in the engine reconciles an ordinary-ID spelling of the same delimiter text with those IDs, and the grammar layer (text EBNF) cannot see IDs at all, so the ordinary-token invocation is indistinguishable from prose and is retained as reasoning with no error. The failure is silent by construction, which is the worst part of it.

On the two candidate directions, the parser-side text fallback is the one with the real cost: the engine moved to ID matching specifically to stop quoted markup from executing, and a text match cannot tell the reporter's ordinary-token invocation from a quoted example. The other two are cheaper invariants: token-aware boundary enforcement on the grammar side where it is offered, and failing loudly (validation error or a documented constraint) when a user-supplied text grammar admits ordinary spellings of the configured parser's dedicated boundary strings. The last one fixes the silence without touching parsing semantics.


### yuchenwang3 · 2026-09-22

A concrete docs-first option is to document the delimiter contract and point users to XGrammar token elements such as `{"type":"token","token":"</think>"}` in a structural-tag sequence. The string form resolves against the configured tokenizer, avoiding model-specific hard-coded IDs. `enable_in_reasoning` changes when constraints apply; it does not make EBNF literals token-aware.

I checked this on current main `ca831d1c5`, using the unmodified Qwen3 parser source, the Qwen3.6-35B-A3B-FP8 tokenizer, and XGrammar 0.2.7: all eight dedicated/ordinary boundary combinations decode identically and pass an exact-text EBNF, while the token-element version accepts only the all-dedicated combination. Parser results were consistent at token chunk sizes 1, 7, and whole input. As the report notes, ordinary `</think>` alone is not a sufficient failure detector.

Would a focused documentation addition covering that contract and `return_token_ids` diagnostics be useful while parser semantics are discussed? This would leave quoted-markup handling unchanged and would not compete with #50986 or #57553.

### he-yufeng · 2026-09-22

One caveat on the fail-loudly direction I sketched earlier, because I think it retires itself on inspection: "this text grammar admits an ordinary spelling of a dedicated boundary" is a language-membership question over the EBNF, not a substring check. A naive text scan false-positives on grammars that legitimately quote the delimiter as an example in prose, and false-negatives on grammars that admit the same spelling through a character class or range. Detecting it at admission time is unsound in both directions, so I would not build that variant.

That leaves the two honest surfaces, and they compose: the docs contract @yuchenwang3 describes (name which delimiters the parser keys by dedicated ID — the four boundaries in `qwen3_config`'s `token_id_terminals` — and show the byte-identical token-element replacement, since a user cannot tell their grammar is broken by reading its decoded output), plus `return_token_ids` diagnostics so the mismatch is inspectable instead of silent. The bigger change, making the grammar layer itself token-aware for these boundaries, is the only one that fixes semantics, and it is also the one most likely to collide with #50986 and #57553, so it wants a maintainer's call first.

@yuchenwang3 if you write the docs PR I will happily review it against the harness numbers above; otherwise I can pick it up next round. Happy to defer to whichever surface the maintainers want first.
