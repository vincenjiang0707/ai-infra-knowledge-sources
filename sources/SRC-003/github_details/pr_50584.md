## Purpose

Fixes #8581

DRY penalizes tokens that would extend a token sequence already present in the context, with a penalty that grows exponentially in the repetition length. It targets loops directly, which `repetition_penalty` (a flat per-token scale) does not. It is a standard sampler in llama.cpp, koboldcpp and text-generation-webui (designed by p-e-w, koboldcpp implementation by pi6am, per llama.cpp's credit line). It complements `RepetitionDetectionParams`, which stops a request once a loop is detected; DRY makes the loop less likely to form.

**A custom logits processor. It changes no existing vLLM file: 4 new paths, +1868/-0** against `5302d1fe40` (#56497, which turned the V2 sampler into a `list[LogitsProcessor]`). The four are `vllm/v1/worker/gpu/sample/dry.py`, `vllm/v1/sample/dry_core.py`, `vllm/v1/sample/dry_utils.py` and `tests/v1/sample/test_dry.py`, per `git diff --stat 5302d1fe40 25a5ec7856`. No entry in `Sampler.logits_processors`, no `SamplingParams` field, no change to the OpenAI request schemas, and no sampler test double edited.

**No gpu<->cpu synchronization is added to the sampler hot path.** A live engine is clean in three modes under `VLLM_GPU_SYNC_CHECK=error`, the strict mode of that check (`envs.py:646-650`: `warn` warns on each sync, `error` raises), and a fourth mode with no engine shows the checker itself armed; the two degenerate parameter regions that do synchronize are declared in the source rather than left to trip it.

It loads by FQCN, online or offline:

```
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --logits-processors vllm.v1.worker.gpu.sample.dry:DryState
```

```python
LLM(model="Qwen/Qwen2.5-7B-Instruct",
    logits_processors=["vllm.v1.worker.gpu.sample.dry:DryState"])
```

`--logits-processors` is `ModelConfig.logits_processors` (`config/model.py:370`, registered at `arg_utils.py:978`). A package may instead register `DryState` under the `vllm.logits_processors` entry-points group (`logits_processor/loader.py:34`), in which case no flag is needed. Neither route forces the V1 runner: custom logits processors are not in `VllmConfig._get_v2_model_runner_unsupported_features` (`config/vllm.py:2880`) at this base.

Parameters arrive in `SamplingParams.extra_args`, which is `vllm_xargs` on the OpenAI-compatible endpoints (`completion/protocol.py:226`, copied to `extra_args` at `:365`; the chat and responses schemas do the same at `chat_completion/protocol.py:482` and `:703`, `responses/protocol.py:290` and `:433`; `docs/features/custom_arguments.md`):

```
curl http://localhost:8000/v1/completions -H 'Content-Type: application/json' -d '{
  "model": "Qwen/Qwen2.5-7B-Instruct",
  "prompt": "Summarize the water cycle.",
  "max_tokens": 256,
  "vllm_xargs": {"dry_multiplier": 0.8, "dry_sequence_breakers": ["\n", ":", "\"", "*"]}
}'
```

The recognized keys are `dry_multiplier`, `dry_base`, `dry_allowed_length`, `dry_penalty_last_n` and `dry_sequence_breakers`, written down once with llama.cpp's defaults in `_DRY_DEFAULTS` (`dry.py:74-80`). `dry_multiplier` defaults to 0.0, so a loaded processor is inert until a request sets it. Any other `dry_*` key fails the request (`dry.py:149-158`) instead of being ignored as a misspelling.

One default deliberately differs from llama.cpp: `dry_penalty_last_n` is `-1` here (scan the whole context) against llama.cpp's `64`. llama.cpp has no equivalent: libllama clamps a negative `dry_penalty_last_n` to 0 (`src/llama-sampler.cpp:3640`) and llama-server rejects one (`server-schema.cpp:153-155`, hard limits `[0, INT32_MAX]`). Every other default matches `common/common.h:243-259` at llama.cpp `ec928150`, the revision every llama.cpp line number here is against. Four validation rules also differ from llama.cpp's, three of them llama-server's and the fourth libllama's:

- A `dry_base` below 1.0. llama-server replaces it with the default (`server-schema.cpp:142-147`); this accepts it and warns, which leaves DRY inert (`dry.py:222-234`).
- An empty breaker array. llama-server rejects it (`server-schema.cpp:242-249`); this accepts it (`dry_utils.py:110-112`).
- Breaker count. llama-server has no cap; this rejects more than 64 (`dry.py:217-221`), since a previously unseen multi-character breaker costs a containment scan over the vocabulary.
- Breaker string length. libllama truncates to 40 bytes (`MAX_CHAR_LEN`, `src/llama-sampler.cpp:3642`, compared against `std::string::size()` at `:3665-3668`); this truncates to 40 code points (`dry_utils.py:110`).

### Implementation

Line numbers are against `25a5ec7856` on this branch, or against `5302d1fe40` for files this PR does not touch.

- `DryState` (`dry.py:98`) subclasses the V2 `LogitsProcessor` and is constructed by `build_custom_logits_processors` with `(vllm_config, LogitsProcRequestState)` (`logits_processor/loader.py:183`). The loader's processors are appended after `logit_bias_state`, `penalties_state` and `bad_words_state` (`sampler.py:69-74`), which is llama.cpp's chain order: `common/common.h:261-263` lists `COMMON_SAMPLER_TYPE_PENALTIES` then `COMMON_SAMPLER_TYPE_DRY`. Bad words ahead of DRY means that mask wins over DRY's edits. DRY only subtracts, so it cannot re-inflate a grammar-masked token, which `interface.py:99-103` requires of a processor.
- `validate_params` (`dry.py:138`) is the admission hook: a classmethod over `SamplingParams` that the frontend runs per request (`loader.py:204-209`, which wraps a `ValueError` into `VLLMValidationError`), so a bad argument fails the request before it reaches the sampler. It type-checks all five keys. `dry_multiplier` and `dry_base` get finiteness and non-negativity; `dry_allowed_length` and `dry_penalty_last_n` get a stricter integer check, a lower bound of 0 and of -1 respectively, and an upper bound, `_DRY_INT_MAX` (`dry.py:63`), which is llama-server's `INT32_MAX` cap, because without one an int64 numpy store raises `OverflowError` inside `execute_model`; `dry_sequence_breakers` gets a list-of-strings check and the 64-entry cap.
- The `dry_base >= 1.0` assert is gone from `apply`. The review named `validate_params()` or `use_dry()`; this is the `use_dry()` one, since `validate_params` only warns for such a base, per the parity note above. The invariant is documented on `use_dry` (`dry.py:389-401`), the predicate `add_request` gates the slot on (`dry.py:246`), which returns False for such a base and keeps it out of `dry_core`. The one assert left in `apply` is the draft-expansion check (`dry.py:300`).
- `add_request` (`dry.py:241`) reads `extra_args` through `_dry_args` (`dry.py:85`), stores the five parameters into per-slot numpy arrays, and gates the slot on `use_dry` (`dry.py:246`). Slots are recycled, so it clears the previous occupant's breaker entry (`dry.py:248`) whether or not the new request enables DRY.
- The tokenizer is loaded once in `__init__` with `cached_tokenizer_from_config` (`dry.py:129`), and llama.cpp's default breaker set is resolved there eagerly (`dry.py:133-135`), because `add_request` runs inside `execute_model`.
- Breaker masks are cached by `frozenset` of token ids, not per request slot: `breaker_ids` maps a slot to its set (`dry.py:119`) and `_breaker_masks` maps a set to one `[vocab]` bool device tensor (`dry.py:120`, built at `dry.py:273-291`). Every request that asked for the same breakers shares one mask and one host-to-device copy.
- `apply` (`dry.py:293`) takes its window widths from `ctx.seq_lens_upper_bound_np` (`dry.py:305`), so it does no device read. The interface supplies that host-side bound and documents it as exact when speculative decoding is not in use (`interface.py:86-89`), which is the condition this processor already requires. The field is not from this PR; it is in `5302d1fe40` at `interface.py:89`.
- Windows are gathered from the GPU-resident `req_states.all_token_ids` (`dry.py:324` and `:336-337`), so there is no per-step host copy of token history.
- Match lengths are computed as diagonal comparisons capped at `allowed_length + max_exponent`, which is exact because the exponent clamp maps every longer match to the same penalty. `_J_BUDGET` (`dry_core.py:117`) caps the j dimension, and is asserted below `2**15` so that the int16 run-length sum stays representable (`dry_core.py:122`); the scan is chunked against a separate byte budget, `_CHUNK_BYTE_BUDGET` (`dry_core.py:130`, used at `:241`). The accumulator holds the penalty rather than the match length, so the charged entries go in with one `index_add_` (`dry_core.py:333`) and no post-scan `nonzero()`.
- Breaker strings resolve by llama.cpp's containment rule: every vocabulary token whose decoded text contains a breaker string is a breaker (`resolve_dry_breakers`, `dry_utils.py:91`). A single-character breaker resolves through a character index built alongside the vocabulary decode (`_VocabIndex`, `dry_utils.py:43`); only a multi-character one scans the decoded texts.

### Two deviations from the review comments

- The `frozenset` mask cache is bounded at `_MAX_CACHED_BREAKER_MASKS = 64` sets with FIFO eviction (`dry.py:69` and `:286-289`). `MAX_DRY_SEQUENCE_BREAKERS` (`dry.py:58`) bounds the length of one request's breaker list, not how many distinct sets clients can ask for, so the unbounded form holds one `[vocab]` bool on device per distinct set for the engine's lifetime. The host-side resolution cache is bounded the same way (`dry_utils.py:27` and `:126-128`).
- The tokenizer comes from `cached_tokenizer_from_config` (`dry.py:129`) rather than a bare `get_tokenizer`. It passes the config's `tokenizer_mode` (`tokenizers/registry.py:316-317`). `ModelConfig.__post_init__` replaces `"auto"` there with one of seven concrete modes for the architectures that need one, and leaves it `"auto"` for every other model, Qwen included (`config/model.py:693-712`); where it did replace it, a bare `get_tokenizer` would re-resolve its own `"auto"` default off the path instead (`registry.py:110-111`) and build the HF tokenizer, which is the wrong class for `deepseek_v32`. It is also the `lru_cache` entry the engine core's structured-output manager uses (`registry.py:305`, `v1/structured_output/__init__.py:79`), so the two share one tokenizer instead of building a second, and it returns `None` under `skip_tokenizer_init` (`registry.py:309-310`), which `_resolve_breakers` handles (`dry.py:237`).

### Known limitations

- No per-request refusal under speculative decoding. `validate_params` sees only `SamplingParams` (`interface.py:118-119`), so it cannot fail a request on the engine's configuration. `__init__` raises at startup instead (`dry.py:100-101`), echoing V1's own `STR_SPEC_DEC_REJECTS_LOGITSPROCS` (`v1/sample/logits_processor/__init__.py:44`, raised at `:204`). The consequence: one engine cannot serve both speculative-decoding and DRY traffic. Loading the processor on a speculative engine fails at startup, and not loading it leaves DRY unavailable there.
- Breaker resolution runs in the worker's `add_request`, inside `execute_model`, where the built-in form ran it in the frontend. `Sampler.add_request` calls it (`sampler.py:96`) from `GPUModelRunner.add_requests` (`gpu/model_runner.py:1156`), which `execute_model` calls at `:1646`. Measured on Qwen2.5-0.5B-Instruct (vocab 151643, 151665 ids scanned), CPU only, rounded to the precision this box supports. The harness reports best-of, not a median: best of five for the init terms and for the scan-against-index comparison, best of fifty for the repeated-call figures, and a single run for each first-request figure. `__init__` decodes the vocabulary and builds the character index in about 555 ms (roughly 480 decode, 70 to 80 index) and resolves the default set there, so the default set costs 0.000 ms in `add_request`. A client's own set of single-character breakers costs under 1 ms on its first request and 0.006 ms after that; a set with two multi-character breakers costs about 10 ms, since it still scans the decoded texts. The character index is what makes the single-character case cheap: the same resolutions against the containment scan are about 20 ms for the default set and about 8 ms for the worst single character in that vocabulary (`" "`, in 53,131 tokens), against 0.31 ms and 1.9 ms through the index. The index costs 12.3 MiB of objects next to the 9.0 MiB of decoded texts already cached per tokenizer.
- Each worker rank loads its own tokenizer (`dry.py:129`). The frontend form needed one copy per engine.
- V2 model runner only. `DryState` subclasses the V2 `LogitsProcessor`, and the V1 loader requires its own (`v1/sample/logits_processor/__init__.py:151-152`), so an engine that has fallen back to the V1 runner fails at startup rather than ignoring DRY.
- llama.cpp additionally expands multi-token restart sequences for breakers; not implemented here. Containment resolution handles single-token breakers only.
- Two parameter regions fall back to a sequential scan in Python, which holds the GIL and has to bring the window to the host: a `dry_base` at or below `1.000001`, where the exponent clamp collapses to zero, and an `allowed_length + max_exponent` above the vectorized path's budget of 2048, which at the default `dry_allowed_length` means a `dry_base` below about `1.044`. That body is wrapped in `gpu_sync_allowed()` (`dry.py:355`), so `VLLM_GPU_SYNC_CHECK` does not fire on it silently.
- There is no early-out for a DRY request whose context never repeats: finding that out needs a device read, so such a request pays the full-width accumulator and `index_add_` on every step.

An earlier revision also ran a differential against the llama.cpp binary with no disagreements, but that harness and its logs no longer exist and it is not offered as evidence.
- A live engine under `VLLM_GPU_SYNC_CHECK=error` on this code, four modes, **each exiting 0**: `eager` (`enforce_eager`, so compilation and capture can neither hide nor invent a sync), `cudagraph` (`cudagraph_mode=FULL_AND_PIECEWISE`; the run captures twice, 51 piecewise and 2 full during CUDA graph memory profiling, then 51 piecewise and 35 full once the KV cache is sized), `resolve` (engine core in the same process) and `detector`. The three engine modes each run the same arms on Qwen2.5-0.5B-Instruct: DRY at llama.cpp's default breaker set (`dry_multiplier=0.8`, `dry_base=1.75`, `dry_allowed_length=2`, `dry_penalty_last_n=64`), an unseen breaker set, a degenerate base, a DRY-off control, and five copies of the prompt in one batch. The harness asserts rather than prints its results: the DRY arm's text must differ from the control's on the same prompt, and all five batch rows must equal the batch-of-1 text. Both held in all three engine modes. Under `error` a detected sync raises, so exit 0 is the finding: no undeclared host-device synchronization on the path DRY adds.
- Two of those arms come with the harness's own qualification. The unseen-breaker arm matches the control byte for byte, since no match survives a sentence boundary, so it is path coverage for the request-time resolve and the mask build rather than evidence that DRY changed anything. The degenerate base, `dry_base=1.000001`, routes to the Python sequential fallback wrapped in `gpu_sync_allowed()` (`dry.py:355`), and that arm produces text with the check silent.
- `detector` is what makes the green result mean anything. With no engine, an undeclared `.item()` and an undeclared non-blocking copy from unpinned host memory both raise, and the same two syncs inside `gpu_sync_allowed()` are silent. **The checker is armed.**
- `resolve` counts the vocabulary pass in the process that makes it: once during engine init, 674.0 ms and 680.5 ms in the two runs, and 0 times while serving requests, one trip into `_vocab_index` and a cache hit. That is the same pass as the 555 ms figure above, measured inside a live engine rather than on its own in a CPU-only process, so this is the number that applies here. Resolving the default breaker set in `__init__` is what puts it there. A first DRY request still costs more than a later one in both runs (410.1 and 419.2 ms against 278.8 and 277.1 ms in eager, 300.7 and 319.4 ms against 106.8 and 106.7 ms in cudagraph), but breaker resolution is not that premium: an unseen set of three single-character breakers, which resolves and builds a new mask inside `execute_model`, came in at +4.5 and +0.6 ms over the later-request figure in eager, +1.7 and +1.9 ms in cudagraph. Two runs bound resolution and the mask build under 5 ms and do not separate them from the run-to-run spread. What the rest of the first-request premium is was not measured.
- Loading the processor does not move traffic that never asks for DRY. Two more modes, `untouched-eager` and `untouched-cudagraph`, build two engines each with identical `LLM` kwargs apart from `logits_processors` and with `seed=0` written out rather than left to the default, then compare token ids rather than text: three prompts with no `dry_*` key, the repetitive one, a prose one, and one carrying every character of the default breaker set, each sent alone, then all three batched, then alone again after a DRY request. **9 of 9 id sequences identical per mode, 18 of 18 across the two, both exiting 0.** The positive control is in the same run: the `dry_*` request diverges in the plugin engine while the same `extra_args` changes nothing in the engine without the processor, so the difference is the processor and not the dict. That second engine is sync-clean under the same armed check, and the only measured cost of loading the plugin is engine build time, +1266 ms eager and +904 ms cudagraph, the order of that 674 to 681 ms vocabulary pass.
- No serving path has been exercised. Every run above drives the offline `LLM` API or pytest, so `/v1/chat/completions`, `vllm_xargs` over the wire, concurrent and mixed batches, and end-to-end throughput are unmeasured.
- Two things are not measured on this code: step cost per batch size and a two-arm control over nine sampler suites against pristine main.

### sashko-zakharchuk · 2026-09-15

@njhill Yes. Under `VLLM_GPU_SYNC_CHECK=error` a live DRY run is clean, sequence breakers included. One commit on top of what is already on the PR.

The one that ran every step was reading `positions` off the device to get each request's context length. The model runner already has that on the host as `InputBatch.seq_lens_cpu_upper_bound`, so `apply_dry` takes it from there and the `positions` argument is gone from the signature. A live engine run asserts the two equal on every sampler row. The bound is exact here because DRY is refused under speculative decoding. `batch_shard` has to localise that field alongside `seq_lens`, or a sharded sampler reads another request's length.

The others were mostly mechanical: the pageable host-to-device copies became `async_tensor_h2d`, `j_budget` was being read back from values the caller already had, and in the scan loop an `any()` branch and the boolean-mask index after it became an unconditional scatter with uncharged entries going to a trash slot. The breaker masks used device-side boolean indexing, and are now built in numpy, transferred once, and stacked into one `[R, vocab]` bool, which costs a byte per entry and takes about a quarter off the step when breakers are set.

The one that needed thought was `nonzero()` after the scan, which synchronises because the host does not know its output size. Applying the penalty densely over the vocabulary removes it at about 4x the step time. The accumulator now holds the penalty instead of the match length, which leaves nothing to recover: amax over penalties picks the same winner as amax over lengths and survives being chunked, so the penalty is applied once with a single `index_add_`. The commit message has the full argument.

A `dry_base` at or below 1.000001, or an `allowed_length + max_exponent` over the vectorized path's budget, still falls back to a Z-algorithm in Python, and that one has to bring the window to the host. It is wrapped in `gpu_sync_allowed()` so it does not trip the check silently.

At vocab 128256, a 2048-token window and no breakers, peak over the penalty path goes from 70.6 to 78.8 MiB at batch 32, and 163.5 to 259.1 at batch 384, because the accumulator is float32 where the match lengths were int16.
