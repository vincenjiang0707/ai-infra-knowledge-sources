Refreshing the references, since the issue quoted v0.27.1 and the file has been
restructured since: on current main both sites are still `out_dtype=torch.float32`,
now inside `DeepseekV4Attention._run_parallel_input_projections` in
`vllm/models/deepseek_v4/attention.py` -- the `compressor_kv_score` and
`indexer_compressor_kv_score` closures (the method was called
`attn_gemm_parallel_execute` when I filed this).

My original post was thin on what would actually settle this, so let me fill
that in. Two things need establishing before the dtype is changed:

1. **Kernel support.** Whether `torch.mm(..., out_dtype=bf16)` has a real
   kernel on this path per arch, or silently falls back -- a "free" win that
   turns out to be a fallback would be worse than leaving it alone.
2. **Selection stability, not just score error.** These scores feed the
   lightning indexer's top-k selection, so lower accumulate precision can
   change *which* tokens get selected, not merely perturb the values. A
   throughput gain with unchanged short-form benchmark scores would not be
   sufficient evidence -- it needs a long-context retrieval check to show the
   selection itself did not drift.

We're standing up exactly that harness (needle-style retrieval now, RULER
16K/128K next) on 8x H20 (SM90) for the IndexCache work in #45350, and can run
a bf16-accumulate variant through the same windows. If nobody is actively on
this in a couple of weeks, I'll send a PR with those numbers attached.
