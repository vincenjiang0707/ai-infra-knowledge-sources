# [Issue #58303] [Bug/Perf]: the dense default chosen for Mamba + EAGLE reverts to 0% prefix reuse under interleaved long conversations

source: https://github.com/vllm-project/vllm/issues/58303
state: open | updated: 2026-09-24T16:07:31Z
labels: speculative-decoding

## 正文

## Summary

#55760 (and its follow-up #55861) resolved #53595 by resolving an **unset** `prefix_cache_retention_interval` to `None` (dense) for Mamba + EAGLE. That does fix the case #53595 measured — sparse retention (`0`) keeps only the replay boundary, EAGLE's tail-block drop makes it unreachable, and the hit is 0.

But dense is the **capacity-worst** arm. It keeps a recurrent-state checkpoint for every block, and on a hybrid model those checkpoints share the pool with the attention KV. Under interleaved long conversations the pool fills, the attention chains get evicted, and prefix reuse returns to a clean **0%** — the same symptom #32802 and #53595 were about, reached through the other end of the same axis.

`0` and `None` are the two ends of the knob and both can produce 0% hits. The middle — a sparse interval that is a multiple of `scheduler_block_size` — keeps EAGLE's hit granularity *and* the capacity, and the engine is the one place that knows the block size when the default is resolved.

## Where the default comes from

| PR | Effect |
|---|---|
| #52216 | Promoted `prefix_cache_retention_interval` to an argument; default changed `None` → `0` |
| #53595 | Reported that this is silent, and that under EAGLE the sparse default never hits |
| **#55760** | Unset + Mamba + EAGLE → `None` (dense). Explicit values still respected |
| **#55861** | Extended the dense resolution to hybrid models |

`vllm/engine/arg_utils.py`, v0.29.0, lines 2393-2407:

```python
if (
    retention_interval_unset
    and model_config.is_hybrid
    and speculative_config is not None
    and speculative_config.use_eagle()
):
    # The default sparse retention (0) keeps only the latest replay
    # boundary, which EAGLE's tail-block drop makes unreachable for
    # Mamba state checkpoints, so prefix caching never hits. Default
    # to dense checkpoints instead.
    cache_config.prefix_cache_retention_interval = None
```

The guard is `retention_interval_unset`, so passing the flag explicitly is respected. Only the default is being decided, and it is being decided in favour of the arm that exhausts the pool.

## Measured cost of that arm

Single RTX 5090 D (32 GB), hybrid GDN model (6 Mamba + 2 full-attention + 1 SWA groups), KVarN 4/2-bit KV, `CTX=huge`, 542,206-token pool, 2176-token attention block, 7 draft tokens. Two independent ~135K conversations advanced in strict alternation, `cached_tokens` on the second turn of each:

| `prefix_cache_retention_interval` | conversation A | conversation B |
|---|---|---|
| **dense (the resolved default)** | **0%** — 55–65 s full re-prefill | **0%** — 55–65 s |
| 13056 (one in six) | 97.0% — 3.4 s | 99.4% — 1.4 s |

The knee moves with the interval, and it also moves with the pool — with `--kv-cache-memory` halved (542,206 → 271,103 tokens) the largest surviving co-tenant halves as well. That is a capacity signature, and it is the reason a fixed structural trigger does not explain it.

Reproduced independently on a 3090 / 0.28.0 pin / 268,169-token pool (same 2176 block): at ~32.6K per conversation, dense gives 0% every turn with a 31.8 s re-prefill, one-in-six gives 93.3–99.5% at 0.4–2.6 s.

## Reproducer

The controls are merged as `bench/prefix_alternation.py`, `bench/interleave_dose.py` and `bench/needle_reuse.py` in hyperqwen (PR syv-ai/HyperQwen#184). The three of them together are what make this legible:

- the alternation arm reports prefix loss as "this turn did not reuse the whole prefix the previous turn established", not as a hit-rate average — the failure is a clean 0%, so an average hides it;
- the dose-response arm finds the knee, and the single-conversation control proves the cache is working before the interleaving is blamed;
- the reuse needle puts the answer *inside* the reused prefix and requires both a high cache percentage and a correct answer, because anything that changes which KV is restored can fail as a silent wrong answer rather than a miss.

Supporting detail, including the raw records and the per-group reconciliation dump showing that **all** groups — both full-attention groups included — return 0 in the failing case, is in syv-ai/HyperQwen#174. The forced-default analysis is syv-ai/HyperQwen#183.

## Suggested fix

Any of the following; I have no stake in which:

```
1. **Resolve the unset default to a small multiple of the block** rather than to dense, for the configurations where dense is currently chosen. The engine knows `scheduler_block_size` at that point; the launcher cannot, because the block moves with the draft count (the Mamba page holds the speculative state slots — on our stack the block is 2176 at 7 draft tokens and 2432 at 15). A wrong value refuses to boot rather than degrading, so a derived default has to come from inside.
2. **Or reword the log line.** #53595's complaint was that this was silent, and the fix did add a line — but `defaulting prefix_cache_retention_interval to dense checkpointing` reads as *"this knob has been considered and set for you"*. The content is *"we are choosing the arm that costs the most capacity"*, and the difference matters: we had this knob in our ruled-out column for a week on the strength of that line.
3. If neither, a documented note that dense is capacity-worst and that interleaved long conversations need an explicit sparse interval.
```

On (1): the value wants to be a multiple of the block, and the useful range is bounded by hit granularity — the hit is `floor(prompt_tokens / retention_interval) * retention_interval`, so the cost is a fixed tail of at most one interval per turn. At 130K that is ~1% of the context, at 50K ~21%, and a conversation shorter than one interval reuses nothing at all. That trade may want to be part of whatever default is chosen.

**On your scope question: your reading is correct, and I think it flips how the issue reads.**

Both merges went to the release branch, not to `main`:

```
#55760  base=releases/v0.29.0  merged=2026-09-08  merge_commit=0c766af7fd
#55861  base=releases/v0.29.0  merged=2026-09-08  merge_commit=74c96922ec
```

I checked `vllm/engine/arg_utils.py` on `main` and there is no `retention_interval_unset` and no `is_hybrid` branch at all. `CacheConfig` there is:

```python
prefix_cache_retention_interval: int | None = Field(default=0, ge=0)
```

So the two branches have **opposite** bugs, and a fix that resolves unset to a small block multiple is better than **both** ends — it is not a backport of the dense default:

| | unset resolves to | under hybrid + EAGLE |
|---|---|---|
| `main` | **`0`** | retains only semantic checkpoints → **never hits**. This is #53595, the bug #55760 was fixing |
| `releases/v0.29.0` | **`None`** (dense, via the override) | hits work short-form, but **wipes under interleaved long conversations** — the report here |

That is the argument for doing it on `main` first: there the change only has to beat "never hits", whereas replacing dense on the branch means beating a default that already works for short conversations. I have put the numbers for that asymmetry on #58549 — short version: `k = 6` is fine as `main`'s default, but I would not carry `6` into a v0.29 backport, because there it turns an ~8K conversation's turns 2-3 from 81% into 0%.

**On "unset-vs-explicit tracking":** you were right that `main` lacks it, and here is the shape. The branch kept a sentinel:

```python
PREFIX_CACHE_RETENTION_INTERVAL_UNSET = _UnsetType()          # arg_utils.py:187
...
add_argument("--prefix-cache-retention-interval",
             **{**cache_kwargs[...], "default": PREFIX_CACHE_RETENTION_INTERVAL_UNSET})
```

while `main` inherits the config default through the field:

```python
prefix_cache_retention_interval: int | None = get_field(      # arg_utils.py:559
    CacheConfig, "prefix_cache_retention_interval"
)
```

so unset and an explicit `0` are indistinguishable at that layer. I see #58549 restores the distinction, which is the part that made this look bigger than a one-liner.

Two details from this side that may save a round, both on #58549:

```
1. **`HYBRID_EAGLE_PREFIX_CACHE_RETENTION_BLOCKS = 1` is dense, not minimum sparsity.** `reachable_block_mask` returns `None` — its "cache every block" contract — as soon as `retention_interval // block_size <= 1`, so a multiple of 1 silently lands back on the arm this issue is about.
2. **Re-applying after `Platform.update_block_size_for_backend` is necessary, not defensive.** The hybrid-aligned block only exists later, it moves with the draft count (2176 at 7 drafts, 2432 at 15, 2048 at 3 or fewer here), and a value that is not a multiple of it refuses to boot rather than degrading.
```

Happy to run any arm on the box here — it is dedicated to this model and restartable, and the harness from the report is in `bench/` now.
