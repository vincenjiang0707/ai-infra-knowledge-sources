## 正文

## What

DSpark pipeline-parallel support, end to end: **aggregated (in-flight-batching) serving with PP targets** and **prefill on a pipeline-parallel producer with KV transfer** (PD-disaggregated serving).

This PR is self-contained: it re-applies #56956 (reverted in #58484 for further streamlining) and builds the PD producer path on top. Happy to iterate on the streamlining with you, @njhill.

Aggregated IFB PP (re-applied #56956):

```
- `PPHandler` broadcasts the last rank's sampled tokens (and draft tokens, for spec decode) to earlier stages on a side stream; earlier stages apply them `pp_size` steps later in a deferred post-update.
- The deferred post-update Triton kernel is pre-compiled during warmup with the exact serving specialization (int32 `idx_mapping`, 16-byte-aligned `num_sampled`/`num_rejected` via a padded combined buffer) — a mid-serving compile there would deadlock on the in-flight broadcast NCCL kernel.
- DSv4 router: pad the top-k buffer so non-last stages can drop EAGLE read-ahead rows.
```

PD prefill-only producer (this PR on top):

```
- `SpeculativeConfig.target_kv_transfer_config` + `is_dspark_prefill_only()`; NIXL is rejected for this mode (it cannot describe packed per-layer KV regions; Mooncake works).
- The scheduler narrows `use_eagle` (and eagle block-drop) for the prefill-only producer so it never does the EAGLE-style read-ahead.
- `DFlashSpeculator.materialize_context_kv()`: precompute and store draft context KV without drafting; the model runner calls it in place of `propose()` on the producer and skips draft-side rejection sampling, drafter graph capture, and EPLB registration there. The preparation half is shared with `propose()` via `_prepare_draft_inputs()`; on the aggregated path the context-K/V store stays graph-aware as introduced by #57632 (merged here), while the producer stores eagerly (it captures no draft graph).
- The DSv4 draft in this mode builds only the attention submodule needed for prefill (`context_kv_only`) — avoiding transient MoE expert allocation — and loads just the context-KV weights (the merged `context_wkv_proj` plus per-layer `kv_norm`).
```

Kimi-K3 DSpark additionally relies on the TritonMLA causal multi-token fix from #51065 (merged; included in this branch's base; verified on SM120).

Split from #53577 (reviewer request).

## Model evaluation

Validated end-to-end on the pre-split stack (#53577 lineage): DeepSeek-V4-Flash-0731 DSpark PD disaggregation with PP on both sides — prefill PP2×TP2 (prefill-only DSpark producer) + decode PP2×TP2 with DSpark, Mooncake KV transfer (TCP transport): GSM8K strict-match **0.9447** (1319 samples, stderr 0.0063). This is exactly the P-PP + D-PP DSpark combination previously reported to produce garbled output.

This rebuild rebases that stack onto current main (including the #57632 context-K/V graph-capture refactor and the #58484 revert of #56956, which this PR re-applies); the rebase keeps the aggregated-path behavior and changes no model numerics. Re-validation of the both-PP PD GSM8K on this exact tree is in progress and will be reported here.
