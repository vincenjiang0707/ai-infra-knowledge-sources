### 🐛 Describe the bug

The watermarking feature was added in v0.30.0 (PR #54053, RFC #53916). This new feature allows per-request opt-out even when the server operator configured `--watermark-config`. A user can send `"watermarking": false` in a request, and the server disables the watermark for that request without any warning or log.

This appears to be a gap in the initial implementation of the v0.30.0 watermarking feature. RFC #53916 states watermarking "is a modification of the sampling process, which cannot be modified by downstream consumers." The current implementation contradicts this — any API caller can modify the watermark behavior per-request.

**Root cause:**

`gpu_sampler.py` L41 reads `sampling_params.watermarking` directly. No code path checks the server's `--watermark-config` to override the per-request value.

```python
# v1/watermarking/gpu_sampler.py:41
def add_request(self, req_idx, sampling_params):
    self.watermarking.np[req_idx] = sampling_params.watermarking
    # ← uses per-request value, no server-level enforcement
```

The `watermarking` field is exposed on all API endpoints:

```
- `ChatCompletionRequest.watermarking` (protocol.py L270)
- `CompletionRequest.watermarking` (protocol.py L78)
- `ResponsesRequest.watermarking` (protocol.py L217)
```

**Steps to reproduce:**

```bash
# Start server with watermark enforced
python -m vllm.entrypoints.openai.api_server \
  --model facebook/opt-125m \
  --max-model-len 512 \
  --watermark-config '{"key": 12345}' \
  --port 8000
```

```python
import requests

MODEL = "facebook/opt-125m"
URL = "http://localhost:8000"

r1 = requests.post(URL + "/v1/completions", json={
    "model": MODEL, "prompt": "Once upon a time",
    "max_tokens": 50, "temperature": 0.7, "seed": 42,
    "watermarking": True
})

r2 = requests.post(URL + "/v1/completions", json={
    "model": MODEL, "prompt": "Once upon a time",
    "max_tokens": 50, "temperature": 0.7, "seed": 42,
    "watermarking": False
})

t1 = r1.json()["choices"][0]["text"]
t2 = r2.json()["choices"][0]["text"]
print(f"watermarking=True:  {t1[:100]!r}")
print(f"watermarking=False: {t2[:100]!r}")
```

```
watermarking=True:  ' for a great nation, it was the world’s greatest country, with a population of approximately 4 milli'
watermarking=False: ', I fell in love with a girl.\nBut when I came to the realization that I had no idea what kind of a g'
```

The outputs differ because watermarking changes the sampling distribution (Gumbel-max). The server accepted `watermarking=False` (HTTP 200) without error, even though `--watermark-config` was set.

**Expected behavior:**

```
When `--watermark-config` is active, one of:
1. Ignore the per-request `watermarking` field and always watermark
2. Reject `watermarking=False` with HTTP 400
3. Add a `--watermark-enforce` flag that prevents per-request opt-out
```

**Why this matters:**

The v0.30.0 watermarking feature was built for regulatory compliance (EU AI Act Article 50(2), California SB 942 — see RFC #53916). Without server-level enforcement, operators who deploy `--watermark-config` for compliance cannot guarantee all outputs are watermarked. Any API user can silently bypass the policy. The server logs no warning when watermarking is disabled per-request.

Since this feature just shipped in v0.30.0, fixing the enforcement gap now avoids breaking changes later.

Related: RFC #53916, PR #54053, PR #56338

### JHC56 · 2026-09-22

Addresses #58191, where a caller can bypass a server's `--watermark-config` by sending `watermarking: false` per request.  The PR adds an opt-in enforce flag that overrides the per-request value at a single point in` GPUWatermarkSampler`, so it covers the OpenAI endpoints, the offline LLM API, and speculative decoding. I verified this on an A100 with` opt-125m`. Without `enforce`, the opt-out still changes the output as expected. With `enforce: true`, the output stays watermarked and a warning gets logged instead.
