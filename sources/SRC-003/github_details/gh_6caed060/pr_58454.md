# [PR #58454] [Bugfix][GLM-5.3-Flash] kpool corruption with speculative decoding

source: https://github.com/vllm-project/vllm/pull/58454
state: open | updated: 2026-09-25T01:42:07Z
labels: bug, ready, glm

## 正文

## Purpose

This patch is the result of hunting down random corruption in long GLM-5.3-Flash traces.

Rejected pool-completing drafts can end up subtly corrupting the pool selection logic: When a pool-completing draft is rejected, the drafts stashed behind it have already overwritten that pool's committed keys. A pool of 4 generated tokens gets an incorrect summary key, so the indexer may skip those tokens or pick a less useful pool.

This affects any speculative method with `num_speculative_tokens >= 2`. 

Only pools built during decode (the model's own output) are affected, and only once the context exceeds `index_topk` (2048), where pools compete for selection.

The most likely place it hurts is long reasoning traces, where later thinking refers back to earlier thinking, as slightly worse long-range self-reference. This _may_ be causing specific failures in re-transcription from memory.

The ring now holds `kpool * cdiv(kpool + num_spec, kpool)` slots, and the seed and decode kernels address it by `pos % RING`. The tail slot mapping already uses the spec's block_size, so it follows. 

Encountered this locally, fix based on work in #55219 by @ivanium. This is only a surgical fix + test for this particular issue.

"""Repro: rejected speculative drafts corrupt the GLM-5.3-Flash kpool indexer.

kpool = 4 (GLM-5.3-Flash). A spec-verify step stashes 1 + num_spec rows into
the per-request tail ring before acceptance is known. Pool W covers positions
4..7; positions 4 and 5 were accepted earlier. Step t verifies 6, 7, 8, 9
(num_spec = 3): 6 is accepted, the pool-completing draft 7 and drafts 8, 9 are
rejected. With a ring of exactly kpool slots, drafts 8 and 9 overwrite ring
slots 0 and 1, which still hold the committed keys of positions 4 and 5. Step
t+1 re-verifies from 7 and recompresses pool W from those slots.

Reference: the accepted tokens fed one per step (no speculation).
Run with RING=4 (before the fix) and RING=8 (kpool * cdiv(kpool + num_spec, kpool)).
"""
import os
import torch
from vllm.models.glm5next.nvidia.ops.kpool_compress import (
    kpool_decode_update_and_maybe_write_cache_batched as update,
)

D, P, PAGE, BLOCK, POOL_LOC = 128, 4, 64, 3, 5
RING = int(os.environ.get("RING", P))
dev = "cuda"
torch.manual_seed(0)
rnd = lambda: torch.randn(D, dtype=torch.bfloat16, device=dev)  # noqa: E731
keys, gates = {p: rnd() for p in range(4, 12)}, {p: rnd() for p in range(4, 12)}
dkeys, dgates = {p: rnd() for p in range(6, 12)}, {p: rnd() for p in range(6, 12)}
ape = torch.randn(P, D, dtype=torch.float32, device=dev)


def fresh():
    return (torch.zeros(4, PAGE, D + 4, dtype=torch.uint8, device=dev),
            torch.zeros(8, 2, RING, D, dtype=torch.bfloat16, device=dev))


def step(kv, tail, positions, K, G):
    n = len(positions)
    t = lambda xs: torch.tensor([xs], dtype=torch.int32, device=dev)  # noqa: E731
    update(kv, tail, t([BLOCK * RING + p % RING for p in positions]),
           torch.stack(K).view(1, n, D), torch.stack(G).view(1, n, D), ape,
           t([POOL_LOC if p == 7 else (99 if p % P == P - 1 else -1) for p in positions]),
           t(positions), pool_size=P, head_dim=D)


def pool(kv):
    return kv.view(-1, D + 4)[POOL_LOC].clone()


kv, tail = fresh()
for p in (4, 5, 6, 7):
    step(kv, tail, [p], [keys[p]], [gates[p]])
ref = pool(kv)

kv, tail = fresh()
for p in (4, 5):
    step(kv, tail, [p], [keys[p]], [gates[p]])
step(kv, tail, [6, 7, 8, 9], [keys[6], dkeys[7], dkeys[8], dkeys[9]],
     [gates[6], dgates[7], dgates[8], dgates[9]])
step(kv, tail, [7, 8, 9, 10], [keys[7], dkeys[8], dkeys[9], dkeys[10]],
     [gates[7], dgates[8], dgates[9], dgates[10]])
spec = pool(kv)
bad = (ref[:D] != spec[:D]).sum().item()
print(f"RING={RING}: pool W matches the no-speculation reference: {torch.equal(ref, spec)}"
      f" ({bad}/{D} fp8 key bytes differ)")
```

### simon-veitner-redhat · 2026-09-24

The ring-sizing fix itself looks correct (kernel addressing and the `kpool + num_spec − 1` bound check out), but the new ring size regresses prefix caching.

**Issue:** `KpoolTailSpec.block_size` is now the ring, and it goes into `scheduler_block_size = math.lcm(...)` in `kv_cache_utils.py`. When the ring doesn't divide the attention block, the scheduler block grows. KDA states are saved on the attention-block grid but kept and matched only on the scheduler-block grid, so reused prefixes get cut down to multiples of the larger block.

**Napkin math (TP8, bf16 KV, MTP 7):**

```
- Ring: `4 · cdiv(4 + 7, 4) = 12`. Before the PR it was always 4.
- Attention block: one KDA state per GPU is `8 heads · 128 · 128 · 4 B` (recurrent) + `(3 + 7) · 3072 · 2 B` (conv) = 585,728 B. One MLA token is 1,024 B, so a state is worth 572 tokens. Rounding up to a multiple of 128 gives **640**.
- Scheduler block: `lcm(640, 4) = 640` before the PR, `lcm(640, 12) = 1920` now. 640 = 5 · 128 has no factor of 3.
- Effect, for a 5000-token prompt: the KDA state is saved at 3840 (4480 minus one 640 block for the EAGLE/MTP back-off). The cache keeps only the state at 1920 (3840 minus one 1920 block). Nothing was saved at 1920, so the first reuse gets 0 hits. Every prompt that fits in one prefill chunk (under ~8K tokens) hits the same mismatch.
```

**Affected:** TP8 bf16 with 5–8 draft tokens (MTP 5–8, DFlash2 7), TP4 bf16 with 8 (1280 → 3840), TP2 bf16 with 8 or 13. MTP with ≤4 draft tokens (ring 8) is unaffected, since 8 divides every attention block.

**Repro:**

1. 30-second check. Start the server on the PR branch and on main, and read the startup log:

   ```bash
   vllm serve zai-org/GLM-5.3-Flash --tensor-parallel-size 8 --trust-remote-code \
     --speculative-config '{"method":"mtp","num_speculative_tokens":7}' \
     --enable-prompt-tokens-details --port 8123
   ```

   ```
   kv cache group sizes [640, 12, 640, 640, 640]   # PR
   kv lcm block sizes 1920
   kv cache group sizes [640, 4, 640, 640, 640]    # main
   kv lcm block sizes 640
   ```

2. Real workload, same server command on both trees (8 × B300, default flags otherwise).

   Build the dataset: 64 ShareGPT conversations with 10–12 messages, converted with the in-tree converter. Prepend the same ~5000-token text to every conversation's first user message, as a stand-in for a shared system prompt or tool definitions. Drop a trailing user message if there is one, because the benchmark asserts that each conversation ends on an assistant turn.

   ```bash
   python benchmarks/multi_turn/convert_sharegpt_to_openai.py sharegpt_raw.json sharegpt_conv.json \
     --max-items 64 --min-turns 10 --max-turns 12 --seed 0 --model zai-org/GLM-5.3-Flash
   ```

   Run the benchmark, scraping `/metrics` before and after:

   ```bash
   curl -s localhost:8123/metrics | grep -E '^vllm:prefix_cache_(queries|hits)_total' > before.txt
   python benchmarks/multi_turn/benchmark_serving_multi_turn.py \
     -i sharegpt_conv_sys5k.json -m zai-org/GLM-5.3-Flash --served-model-name zai-org/GLM-5.3-Flash \
     -u http://127.0.0.1:8123 -p 8 -k 16 --no-early-stop --seed 0 --trust-remote-code
   curl -s localhost:8123/metrics | grep -E '^vllm:prefix_cache_(queries|hits)_total' > after.txt
   # hit rate = delta(hits) / delta(queries)
   ```

   |                          | PR               | main         |
   |--------------------------|------------------|--------------|
   | Prefix-cache hit rate    | 66.6%            | 76.9%        |
   | Prompt tokens recomputed | 646,873 (+45%)   | 446,206      |
   | TTFT p50 / p90           | 212 / 409 ms     | 158 / 316 ms |

   On the PR, every one of the 322 requests' cached counts is a multiple of 1920, and most stop at 3840, which is just the shared prefix. Conversation history is almost never reused: the cached share falls from 72% at turn 1 to 64% at turn 5, while on main it rises from 73% to 80%.

Also: `--prefix-cache-retention-interval 640` now fails at startup (`must be ... a multiple of scheduler_block_size (1920)`). NIXL P/D likely trips `assert block_stride % physical_ratio == 0`: NIXL's own LCM includes the ring, so it splits a 655,360 B KDA page into 1920 / 64 = 30 parts, and 655,360 isn't divisible by 30. This one comes from reading the code and was not run.

**Suggested fix:** round the ring up to a power of two and guard it the way QSA does:

```python
ring = self._index_kpool * next_power_of_2(cdiv(span, self._index_kpool))
assert self.cache_config.block_size % ring == 0
```

With kpool = 4 the ring becomes 4, 8, 16 or 32. Every attention block is a multiple of 128, so a power-of-two ring always divides it, and the scheduler block stays equal to the attention block in all 64 configs checked. No test currently covers `get_kv_cache_spec`'s ring size, so it would be worth adding one.
