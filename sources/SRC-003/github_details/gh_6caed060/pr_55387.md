# [PR #55387] [CI/Build] Move the default CUDA build from 13.0 to 13.2

## 正文

## Purpose

`requirements/cuda.txt` already pins `torch==2.13.0`, and PyTorch publishes cu132 wheels for that release. This moves the default vLLM build from CUDA 13.0 to CUDA 13.2 so the shipped wheels match the CUDA version the pinned torch is built against.

## Changes

- `CUDA_VERSION` `13.0.3` → `13.2.1` in `docker/Dockerfile` (plus the regenerated `docker/versions.json`), `.buildkite/release-pipeline.yaml`, the arm64 / GH200 image builds, and the torch-nightly image build.
- Build base images → `pytorch/manylinux2_28-builder:cuda13.2-9f3983c9d6...` and `pytorch/manylinuxaarch64-builder:cuda13.2-9f3983c9d6...` (same pinned commit for both arches).
- `VLLM_MAIN_CUDA_VERSION` `13.0` → `13.2` and the `setup.py` variant map `cu130` → `cu132`, so precompiled-wheel autodetection and the nightly-index default agree with what is actually built.
- `--torch-backend cu130` → cu132 for `check-ray-compatibility.sh`; `DEFAULT_VARIANT_ALIAS` → `cu132`.
- Regenerated `requirements/test/cuda.txt` against the cu132 index.
- Docs updated.

## Two upstream gaps worked around here

**1. FlashInfer has no cu132 index.** `https://flashinfer.ai/whl/` publishes `cu128`, `cu129`, `cu130` and `cu134` — `cu132` 404s, which would break the `flashinfer-jit-cache` step outright. CUDA minor version compatibility makes the cu130 build usable on a 13.2 runtime, so the Dockerfile now maps `cu131|cu132|cu133` → `cu130`. Happy to drop this in favour of asking FlashInfer to publish a cu132 index if maintainers prefer.

**2. `--torch-backend cu132` is unusable for the test lock.** It restricts every torch-ecosystem package to the cu132 index, and `torchaudio==2.11.0` has no cu132 build — torchaudio is no longer released and its last build predates cu132, so the cu132 index tops out at torchaudio 2.2.0:

```
× No solution found when resolving dependencies:
╰─▶ Because there is no version of torchaudio==2.11.0 and you require
    torchaudio==2.11.0, we can conclude that your requirements are unsatisfiable.
```

torchaudio is imported at module scope by several model processors (`midashenglm`, `cohere_asr`, `funasr`, `minicpmo`), so it cannot simply be dropped. The `pip-compile` hook therefore uses `--extra-index-url https://download.pytorch.org/whl/cu132` instead of `--torch-backend`; `unsafe-best-match` still prefers the `+cu132` local versions for torch/torchvision/torchcodec, and torchaudio resolves to its PyPI wheel (`torchaudio==2.11.0`, no local version).

Side effect: uv does not echo `--extra-index-url` into the lock header, so the header no longer records which CUDA index was used. `.pre-commit-config.yaml` is the source of truth.

## Notes for reviewers

```
- **Lock churn.** `requirements/test/cuda.txt` shows ~677 changed lines, but only ~32 of those come from cu130 → cu132. The rest is ordinary staleness — recompiling with the *same* `--torch-backend cu130` today produces ~649 changed lines on its own.
- **`torchao` in `.buildkite/test_areas/quantization.yaml` is deliberately left on the cu130 index.** `torchao==0.17.0` has no cu132 build (the cu132 index only carries 0.18.0). Bumping torchao is out of scope; the cu130 build runs fine on a 13.2 runtime. Worth a follow-up.
- `--torch-backend=cu132` requires uv ≥ 0.12.0. This PR does not need it (the pre-commit `uv` rev stays at 0.11.1), but the install docs now suggest `cu132` to users, and the surrounding text already tells them to `uv self update` if it fails.
```

## Test Plan

Full CI. The docker build is the real test here — it exercises the CUDA 13.2 base image, the FlashInfer cu130 fallback, and the regenerated lock.

Locally verified: `docker/versions.json` regenerates clean from the Dockerfile ARGs, all touched YAML parses, and the cu132 lock resolves end to end.
