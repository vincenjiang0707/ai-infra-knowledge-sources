### 🐛 Describe the bug

**Summary:** For `zai-org/GLM-5.3-Flash` on H100 the auto-selected sparse-MLA attention backend is `FLASHINFER_MLA_SPARSE_SM90` (log: `Using FLASHINFER_MLA_SPARSE_SM90 attention backend out of potential backends: ['FLASHINFER_MLA_SPARSE_SM90', 'FLASH_ATTN_MLA_SPARSE']`). It is **~36% slower at concurrency 1 and ~70% slower at concurrency 8** than the other candidate, `FLASH_ATTN_MLA_SPARSE`, measured with `vllm bench serve` on the same server flags. MTP draft acceptance is identical across the two, so the gap is per-step attention cost, not speculative-decoding behaviour. Forcing `--attention-backend FLASH_ATTN_MLA_SPARSE` recovers it.

**How we found it:** we had been serving from an image built on 2026-08-26 from the `glm-release` branch (base `487ecf187`, FlashInfer 0.6.17). That build logs `Using FLASH_ATTN_MLA_SPARSE attention backend out of potential backends: ['FLASH_ATTN_MLA_SPARSE', 'FLASHMLA_SPARSE']`. After moving to the current `vllm/vllm-openai:glm53-flash` (nightly `385dce36b`, FlashInfer 0.6.18) with identical flags, the backend line changed to `FLASHINFER_MLA_SPARSE_SM90` and single-stream throughput dropped by roughly a third. The preference appears to come from #53906 (`031c899d` "[Model] Use FlashInfer for GLM-5.3-Flash NoPE MLA", `e34f7f71` "[Kernel] Use FlashInfer rc10 for NoPE MLA") and is gated on the FlashInfer version, so the 0.6.17 -> 0.6.18 bump flipped the kernel without any flag change.

### CarrotSwordsman · 2026-09-18

Root-caused this statically on H20 (sm_90) — the full selection chain reproduces both log behaviors in the report; sharing it since a fix decision needs the mechanism.

**Why the backend flips between your two builds.** The backend choice happens CPU-side in `platforms/cuda.py`, and for GLM-5.3-Flash it lands on the Hopper `else` branch of `_get_backend_priorities` (`use_mla=True`, major==9):

```python
sparse_tail = [FLASH_ATTN_MLA_SPARSE, FLASHMLA_SPARSE]
if head_size == 512:
    sparse_tail.insert(0, FLASHINFER_MLA_SPARSE_SM90)   # ← unconditional top priority
```

`head_size = kv_lora_rank + qk_rope_head_dim = 512 + 0 = 512` (NoPE config), so `insert(0, ...)` puts `FLASHINFER_MLA_SPARSE_SM90` **ahead of** `FLASH_ATTN_MLA_SPARSE`. The first four non-sparse candidates are all rejected (model requires sparse), so the winner is decided inside `sparse_tail`.

The version flip is the feature gate: `flashinfer_mla_sparse_sm90.py::supports_combination` calls `has_flashinfer_sm90_nope_mla()`, which checks for the `ckv_scale_arr` kwarg on `BatchMLAPagedAttentionWrapper.run` — introduced in FlashInfer **0.6.18**.

```
- 0.6.17 (your glm-release build): gate rejects → falls through to **FLASH_ATTN_MLA_SPARSE** (fast path)
- 0.6.18 (your nightly): gate passes, `kv_lora_rank == 512` ✓ and `qk_rope_head_dim in (0, 64)` ✓ → **FLASHINFER_MLA_SPARSE_SM90** (36–70% slower per your numbers)
```

Both of your logs are exactly what this chain predicts. The `insert(0, ...)` was introduced by `98ed0856f3` / #53906 — the same change the issue points at. The intent (FP8 KV in-kernel dequant, half HBM traffic on Hopper) is reasonable, but there is no benchmark backing the priority **inversion** on sm_90, and your data (MTP accept length identical → the gap is purely the per-step attention kernel) says the inversion is backwards at least for this model.

**Possible fix directions:**

```
1. Demote the Hopper FlashInfer sparse backend from `insert(0, ...)` to `append` (behind FLASH_ATTN_MLA_SPARSE);
2. Keep the priority but document `--attention-backend FLASH_ATTN_MLA_SPARSE` for sm_90 recipes;
3. Make it batch-size adaptive — your numbers show the gap widens at low concurrency (36% @ 1 vs 70% @ 8).
```

Also worth handling together with #56563 (the TMA descriptor zero-extent error spam when forcing FLASH_ATTN_MLA_SPARSE — output correct but log-spammy), since option 1 would route more users onto that backend by default.

**Honest scope note:** I could not run the throughput A/B on my side — GLM-5.3-Flash's only published weights are FP8 at 328 GB, which doesn't fit 2×96 GB. The chain above is verified against upstream main `75c71390d` source and the model's config.json; the selection logic is fully CPU-side, so the analysis holds independently of memory. If someone with H100s runs the A/B, the numbers in this issue already cover it.


### jtatum · 2026-09-24

Thanks @CarrotSwordsman, that matches what I see. As of nightly 7f1a539 (FlashInfer 0.6.18.post1) the priority is unchanged: `sparse_tail.insert(0, FLASHINFER_MLA_SPARSE_SM90)` for `head_size == 512`, so GLM-5.3-Flash on H100 still defaults to the slower backend unless you pass `--attention-backend FLASH_ATTN_MLA_SPARSE`.

One update on your caveat: the TMA descriptor spam on `FLASH_ATTN_MLA_SPARSE` (#56563) is fixed by #55385. So option 1 (demote to `append`) no longer routes users onto a log-spamming backend. There is also an open illegal-memory-access report against the FlashInfer SM90 sparse backend for this model (#55626), which is another point in favor of not making it the default on sm_90.
