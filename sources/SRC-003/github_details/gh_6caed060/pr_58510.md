## 正文

## Purpose

DeepSeek V4/V4.1 checkpoints store MXFP8 weight scales in 32x32 blocks. The
ModelOpt loader expands them to one scale row per weight row, and on gfx950
`RocmDotScaledMxfp8LinearKernel` then runs one generic `tl.dot_scaled`
kernel on those per-row scales. On DeepSeek-V4.1-Flash these linears
(`fused_wqa_wkv`, `wq_b`, the indexer `wq_b`, `wo_b`, and the shared-expert
`gate_up` and `down`) make up 11.7% of GPU kernel time per decode step at
TP2 conc32.

This PR keeps the checkpoint's 32x32 scale blocks and adds a GEMM that reads
them directly, tuned per shape for the V4.1-Flash projections. It is 1.49x
faster than the current kernel at the median, and 1.07x faster than the
native group32 GEMM in ROCm/aiter#5750 (latest head). End to end, over a
1-hour InferenceX agentx run (TP2, conc 32, DSpark x5), TPOT is 4.8% lower.

## What changes

- **`rocm_block32_gemm.py` (new):** a `tl.dot_scaled` GEMM for an MXFP8
  activation times an e4m3 weight with `[N/32, K/32]` E8M0 block scales.
  - A tiled kernel for larger M.
  - A packed kernel for small M. It fills the MFMA's rows with K panels
    instead of tokens and keeps only the matching-panel (block-diagonal)
    products, so a handful of tokens still streams the weight at full width.
  - Either kernel can split K. Normally the last program of each output tile
    sums the partials in split order within the same launch, so the result
    is deterministic and needs no second launch. A tile's splits run on one
    XCD, so they meet in its L2. The arrival counters are kept per stream.
    If a stream's first split-K launch happens inside a graph capture, it
    has no counters yet and uses a second reduce launch instead.
  - N and K are `constexpr` and M is runtime (`do_not_specialize`), so
    serving does not recompile per batch size.
  - The tile, split-K, MFMA shape and occupancy come from a table tuned on
    MI355X for the ten V4.1-Flash projections at TP2/TP4. Untuned shapes
    use a generic default.
  - It is registered as a custom op, because the config choice branches on
    M and the linear runs under `torch.compile`.
- **`RocmDotScaledMxfp8LinearKernel`:**
  - `process_weights_after_loading` recovers the `[N/32, K/32]` blocks when
    every 32 rows share their scales, which is exactly what the loader
    produces from a 32x32 checkpoint.
  - `apply_weights` dispatches on the scale shape, so pre-processed
    (IPC-cached) weights work either way.
  - The block-scaled path also runs `K % 32 == 0` natively. DeepSeek-V4.1's
    shared-expert `down` at TP4 (K=576) was dequantized to BF16 at load
    before.
  - Checkpoints with per-row (1x32) scales keep the existing kernel
    unchanged.
- **Grouped MXFP8 `wo_a` GEMM (#58456):** `wo_a` goes through the same
  linear kernel, so its scales are now compact too. The kernel derives the
  scale row block from the scale shape and reads either layout.

## Not a duplicate

- **#57857** (open) edits the same kernel for the same model. It masks the K
  tail of the existing per-row kernel so K=576 runs natively, and it adds
  `input_quant_key()` so `wq_b` and the indexer `wq_b` can share one
  pre-quantized activation. This PR instead keeps the checkpoint's 32x32
  scales and replaces the GEMM for them. It covers K=576 as well, at 4.3 µs
  vs the current 8.7 µs at M=192. The activation sharing is orthogonal and
  composes with this. Both touch `rocm_native.py`, so whichever lands second
  rebases.
- **ROCm/aiter#5750** (open) proposes the same idea as an AITER GEMM. This PR
  keeps the kernel in vLLM, so it does not depend on an AITER release, and
  it measures on par or faster at the V4.1 shapes (table above).
- **#48427 and #57760** re-quantize MXFP8 checkpoints to FP8 PTPC. That is a
  different trade-off: it changes the weights.
