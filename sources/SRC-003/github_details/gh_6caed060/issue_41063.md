# SM 12.x kernel coverage gaps for DeepSeek-V4-Flash on consumer Blackwell (RTX 50 / GB10)

Filed against `jasl/DeepGEMM` and tracked alongside vLLM #40899.

This is a comprehensive map of what's missing to run **DeepSeek-V4-Flash on SM 12.x** end-to-end through DeepGEMM, gathered from a 10-layer end-to-end debugging pass on dual NVIDIA GB10 (DGX Spark, SM 121, aarch64) using `jasl/DeepGEMM@7a7a41a1` + `jasl/vllm:ds4-sm120@8d0ebb76` against vLLM nightly `0.19.2rc1.dev220+g7b1bc0a3e`.

## What works in `jasl/DeepGEMM` today

The fork already includes SM 120-native CuTeDSL kernels for these V4 paths:
- `sm120_tf32_hc_prenorm_gemm` (mHC pre-norm GEMM — V4's hyper-connection layer)
- `sm120_fp8_einsum`
- `sm120_fp8_paged_mqa_logits`
- `MmaMXF4NVF4Op` (with the `cute_dsl/warp/mma.py` `sm_120a` whitelist patch — NOT in fork)

These paths boot end-to-end on RTX Pro 6000 (SM 120) per the PR description.

## What's still missing for V4-Flash on SM 12.x

These dispatch sites in the fork still hard-code `arch_major == 9` (Hopper) or `arch_major == 10` (datacenter Blackwell) and reject SM 120/121, OR route to SM 10 kernels that use `tcgen05.*` instructions which SM 12.x silicon does not implement.

### 1. Dispatch routing — pure dispatch fixes (safe to extend to SM 12.x today)

| File | Line | Site | Suggested fix |
|---|---|---|---|
| `csrc/utils/layout.hpp` | 76 | `get_default_recipe`: SM 10 → `(1, 1, 128)` | accept `arch_major == 12` for the same recipe (verified working on GB10) |
| `csrc/apis/layout.hpp` | 48, 56, 106, 110 | SF transformation for FP4 | accept `arch_major == 12` (verified GB10) |
| `csrc/jit/compiler.hpp` | NVCCCompiler + NVRTCCompiler `include_dirs` | cutlass headers from `third-party/cutlass/include` | both compiler classes need `-I third-party/cutlass/include` added — currently NVCC fails with `fatal error: cutlass/detail/helper_macros.hpp: No such file or directory` |

These **alone** unblock the next layer of failures.

### 2. The hard wall — kernel-source-level gaps (require actual SM 12.x kernel writing)

| File | Site | Symptom on GB10 |
|---|---|---|
| `csrc/apis/gemm.hpp:99` | `fp8_fp4_gemm_nt` dispatch only knows `sm90_fp8_gemm_*` and `sm100_fp8_fp4_gemm_1d1d` | Routing to `sm100_fp8_fp4_gemm_1d1d` produces `ptxas: Instruction 'tcgen05.fence' not supported on .target 'sm_120f'`, `Feature '.block32' not supported on .target 'sm_120f'`. **Needs `sm120_fp8_fp4_gemm_1d1d` kernel implementation** — there is no SM 120 equivalent yet in the fork. |
| `csrc/apis/attention.hpp:67, 177, 367` | FP4 attention dispatch | Same `tcgen05.*` ISA mismatch as above. **Needs SM 120 FP4 attention kernel(s)**. |
| `csrc/apis/einsum.hpp:55` | FP4 einsum dispatch | Same problem. **Needs SM 120 FP4 einsum kernel** (the existing `sm120_fp8_einsum` covers FP8 not FP4). |

### 3. Companion vLLM-side gates that also need to relax

These are independent of DeepGEMM but block the deployment from reaching DeepGEMM in the first place. We've submitted the corresponding vLLM PRs:

| vLLM file | What | PR |
|---|---|---|
| `vllm/platforms/cuda.py support_deep_gemm` | accept `is_device_capability_family(120)` | #41062 |
| `vllm/model_executor/layers/fused_moe/experts/deep_gemm_moe.py` | `DeepGemmFP4Experts._supports_current_device` | #41062 |
| `vllm/model_executor/layers/fused_moe/experts/gpt_oss_triton_kernels_moe.py` | `_supports_current_device` cap range `< (11, 0)` → `< (13, 0)` | #41028 |
| `vllm/.../csrc CMakeLists.txt MARLIN_*_ARCHS` | add `12.0f` family | #40923 (Approved by @Harry-Chen) |

### hazyumps · 2026-05-29

Field report from a debugging session on **2× NVIDIA GB10 (DGX Spark, SM 121, aarch64)**, DeepSeek-V4-Flash, TP=2 + `--enable-expert-parallel` over 200G ConnectX RoCE, MTP n=2, fp8 KV cache, vLLM `v0.1.dev16581+gdda4668b5`. Three findings in case they're useful for the rollup.

### 1. Deployment gotcha: NCCL silently falls back to TCP without RDMA device passthrough

On our container NCCL logged `NET/IB : No device found` → used `NET/Socket` for **all** cross-node collectives (all-reduce + EP all-to-all). `libibverbs`/`libmlx5` were present, but the RDMA device nodes weren't mapped in (`/dev/infiniband` missing inside the container), so it ran every collective over the kernel TCP stack.

Fix was passing the devices into `docker run`:
```
--device=/dev/infiniband --cap-add=IPC_LOCK --ulimit memlock=-1:-1
```
→ NCCL switches to `NET/IB` (RoCE), single-stream throughput **~12 → ~34 tok/s**. Non-obvious because the userspace libs being present makes it look configured. Might be worth a one-line note in the deployment docs.

### 2. `sm12x_deep_gemm_fallbacks.py::_fp8_mqa_logits_topk_torch` is FP32/cuBLAS-bound — a small bf16 tweak is a large win

With `deep_gemm` absent, the sparse-indexer top-k routes to this torch fallback, which dequants Q and K to **FP32** and runs `torch.matmul` (cuBLAS SGEMM on CUDA cores, leaving Blackwell tensor cores idle). Under concurrency this dominated — **4 concurrent requests dropped to ~0.1 tok/s (effectively frozen)**, py-spy pinned in `_fp8_mqa_logits_topk_torch → cublasSgemm`.

```
Two no-kernel changes fixed it on our box:
- Dequant the matmul **inputs to bf16** (tensor cores) and `.float()` the result — relu / accumulate / top-k stay fp32, so selection is unchanged (verified coherent output).
- Bump `_SM120_MQA_LOGITS_MAX_SCORE_BYTES` **64 MiB → 1 GiB** — the 64 MiB cap forces many tiny chunk-loop iterations (launch overhead scales with KV length); GB10 has 128 GB unified memory to spare.
```

Result: **4 concurrent ~0.1 → ~60 tok/s**, single-stream 29 → 34, output verified coherent. Happy to open a PR with the diff if it'd help.

### 3. Next gap: `_forward_sparse_mla_prefill_triton` wedges on heavy-concurrent + long-prompt

Same Python-double-loop-over-Triton-chunks structure as the indexer (`for token_start … for index_start: accumulate_indexed_sparse_mla_attention_chunk`). Under heavy concurrent + long-prompt load it **hangs** — requests don't abort on client disconnect, GPU stays pegged at `running=N` with no prompt/gen progress, py-spy pinned in `_forward_sparse_mla_prefill_triton → _forward_prefill`. Looks like the next SM 12.x kernel-coverage item after the indexer.

Glad to test rebased branches on dual GB10 TP=2 — quick turnaround.

### hazyumps · 2026-05-30

For anyone bringing up **DeepSeek-V4-Flash on dual GB10 / DGX Spark (sm_121)**, I put together an end-to-end reproduction repo: **https://github.com/hazyumps/deepseek-v4-flash-gb10**

It sits on top of @jasl's fork (the SM12x enablement is his work) and captures the GB10-specific tuning + runbook to get from "crashes / wedges / ~12 tok/s" to a stable **384K-context, ~31 tok/s single-stream** config across two Sparks (TP=2 + expert-parallel over RoCE, MTP n=2, fp8 KV). A few GB10-specific findings that may be useful here:

```python
- **NCCL 2.30.4 is the wedge fix.** The `shm_broadcast` / "No available shared memory broadcast block found in 60 seconds" deadlocks under load go away on 2.30.4 — but PyTorch's *bundled* NCCL (2.28.x) shadows the system one, so it needs an explicit `LD_PRELOAD` of the 2.30.4 `libnccl.so.2`. (`torch.cuda.nccl.version()` still reports the compiled/bundled version; trust the NCCL banner in the logs.)
- **RDMA must be made visible to the container** (`--device=/dev/infiniband` + `IPC_LOCK` + `memlock=-1`), or NCCL silently runs every collective over TCP (~12 → ~30+ tok/s once IB engages, `via NET/IB` in the logs).
- **Indexer top-k fallback.** On sm_121 the lightning-indexer top-k has no native kernel and lands in the torch fallback. Two fixes helped: (1) bf16 matmul inputs instead of FP32 — the FP32/cuBLAS path froze concurrency (4-way 0.1 → ~60 tok/s); GB10-specific, @jasl saw no benefit on RTX Pro 6000. (2) Routing the per-chunk logits through the existing fused tf32 Triton MQA-logits kernel instead of the bf16 cuBLAS head-loop — ~+29% prefill at 9k, and it matches an fp32 reference **exactly** on the top-512 (i.e. more accurate than the bf16 fallback, not just faster). Patched fallback file + a correctness gate are in the repo.
```

Happy to fold any of this into #41834 if useful. Thanks @jasl / @tonyliu312 for the SM12x work.


### calvarado2004 · 2026-08-14

GB10 long-context field report: prompts beyond ~100K tokens were effectively unserveable on the sm12x stack, and we traced it to the sparse-attn-indexer prefill path. `_fp8_mqa_logits_sm12x` only routes to the Triton kernel when `clean_logits=True`, but the indexer prefill always passes `clean_logits=False` — so every prefill ran `_fp8_mqa_logits_torch`, which degenerates to `head_chunk_size=1` at large `seq_len_kv` (the 64 MiB score budget divides to zero). py-spy on a 450K-token prompt showed the worker pinned there for 35+ minutes without completing a single 8K chunk.

The Triton kernel cleans unconditionally (writes `-inf` outside `[ks, ke)`), so it satisfies both contracts — the fix is dropping `clean_logits` from the gate. Fix + regression test: https://github.com/jasl/vllm/pull/44 (against the #41834 branch, where the code lives).

Measured on 2× DGX Spark (SM121, CUDA 13.3, dual-node TP2, DeepSeek-V4-Flash-0731, nvfp4_ds_mla KV):

```
- Triton vs torch reference: identical `-inf` masks, max rel diff 6.4e-7, 28× at `[1024 × 131072 × 64h]` (much larger at jumbo shapes).
- 468,540-token needle prompt: completes in 498 s with correct retrieval — previously never finished.
- A high-effort reasoning prompt that reliably degenerated into repetition/language-mixing now solves cleanly (`finish=stop`, ~10K tokens, correct answer).
```

This is distinct from the bf16 rework of `_fp8_mqa_logits_topk_torch` discussed above — that's the decode/topk variant; this is the prefill dispatch. Possibly relevant to the ROCm indexer corruption report in #52109, since the failure mode (silent quality collapse at depth) looks similar from the outside.

Separately, while A/B-testing KV dtypes with CUDA constant we found `fp8_ds_mla` produces stray-token injection escalating to full output collapse beyond ~40K context on SM121, while `nvfp4_ds_mla` is clean at 468K under the same probes — deterministic repro payloads available if useful.

(AI-assisted debugging/validation; all measurements from our own two-node GB10 rig.)


### srinathh · 2026-08-31

**Data point on the DSA indexer varlen gate and SM120 `paged_mqa_logits`**

Hardware: 2x DGX Spark (GB10, sm_121a), TP=2 over ConnectX-7. Model: GLM-5.3-Flash (RedHatAI NVFP4) + DFlash2 drafter. vLLM `0.1.dev20051+g487ecf187` (day-0 glm53 image + community SM121 patches), bundled DeepGEMM **2.6.1**.

Three findings that may help scope this tracking issue:

1. **The SM120 `paged_mqa_logits` kernels are present in DeepGEMM 2.6.1** - `impls/sm120_fp8_paged_mqa_logits.cuh`, `impls/sm120_fp4_paged_mqa_logits.cuh`, `scheduler/sm120_paged_mqa_logits.cuh` - templated on `kIsVarlen` with a multi-atom `kNextN` path. So the *files* from the "missing kernels" era are here now.

```
2. **But `_supports_varlen_paged_mqa_logits()`'s family-100 gate is load-bearing, not conservative.** We patched the two gates in `v1/attention/backends/mla/indexer.py` to include family 120 (bind-mount, two guarded edits). Result: it boots, reports `use_flattening=False supports_varlen=True (next_n=4)`, and is **fully correct single-stream** - tool calls, multi-image vision, and needle recall exact at 32K and 128K. Then it hits `CUDA error: an illegal memory access` (surfacing at `v1/attention/backend.py:539 seq_lens_cpu`) in two separate scenarios:
   - two concurrent requests entering decode together (~50K-token contexts each), and
   - a **single** request carrying 3 images (multimodal encoder batch shapes), max_num_seqs=1.
```

   So the SM120 varlen specialisation appears incorrect on sm_121a for non-trivial batch shapes, and the gate should stay until that's fixed at the kernel level. Happy to provide the full crash logs and an exact reproduction.

3. **Separately - and this one hurts even with the gate respected:** with `use_flattening` *or* the uniform-decode path, **two concurrent long-context decodes collapse** on this hardware. Measured decode-only intervals (no prefill in the step), identical 50K-token prompts, temperature 0:

   | config | 1 running | 2 running (aggregate) |
   |---|---|---|
   | DFlash2 k=3 (`next_n=4`, flattened) | 22-25 tok/s | ~4 tok/s |
   | DFlash2 k=1 (`next_n=2`, uniform-batch kernel, no flattening) | 23-24 tok/s | **2.2 tok/s** |

   At 400-token prompts (the usual benchmark size) batching looks normal - the effect only appears at long context, so it's easy to miss. For now we serve with `--max-num-seqs 1`.

Net: SM12x users currently cannot batch long-context DSA decode at all, with or without spec decode. If there's interest I can file the two items separately (varlen kernel fault; uniform-path scaling) with repro scripts.

(Likely related: #49896 dissects a NaN-logits -> uninitialized-smem-indices -> illegal-memory-access chain in the same kernel family on SM120 prefill; our varlen crashes in decode look like the same failure class, so its proposed kernel hardening / torch.topk fallback may cover this too.)

## What changed, and it was not vLLM

#52035 (merged Aug 12) moved `cmake/external_projects/deepgemm.cmake` from `vllm-project/DeepGEMM@e21c821` to `deepseek-ai/DeepGEMM@8b1392b`. Comparing those two trees against the rows in this issue:

| Row in this tracking issue | `e21c821` | `8b1392b` |
| --- | --- | --- |
| `csrc/apis/layout.hpp` SF transformation | `arch_major == 10` only | `arch_major == 10 or arch_major == 12`, plus an added transpose for the K-major SF layout SM120 accepts |
| `sm120_tf32_hc_prenorm_gemm` | absent; `hyperconnection.hpp` dispatched 9 and 10, else `DG_HOST_UNREACHABLE` | `arch_major == 12 -> sm120_tf32_hc_prenorm_gemm` is the first branch |
| `sm120_fp8_einsum` | `einsum.hpp` dispatched 9 and 10, else `DG_HOST_UNREACHABLE` | includes `sm120_bmk_bnk_mn.hpp`, `sm120_bf16_gemm.hpp` and `sm120_fp8_fp4_gemm_1d1d.hpp`, and dispatches `arch_major == 12` |
| `sm120_fp8_paged_mqa_logits` | no `arch_major == 12` branch in `attention.hpp` | dedicated branch calling `sm120_paged_mqa_logits_metadata` |

Two of these I checked by A/B on hardware rather than by reading, running the identical call under both pins:

| Call | `dev608+g99a10304d` (Aug 11, old pin) | `dev1219+g46638857f` (Aug 26, new pin) |
| --- | --- | --- |
| `transform_sf_into_required_layout` | `Assertion error (layout.hpp:60): Unknown SF transformation` | returns `(1024, 4) int32` |
| `mhc_pre_broadcast_tilelang` | `Assertion error (hyperconnection.hpp:56): Unsupported architecture` | passes |

The first reproduces in seconds on one GB10 with no weights loaded:

```python
import torch, vllm.utils.deep_gemm as d
d.transform_sf_into_required_layout(
    torch.ones(1024 // 128, 2048 // 128, dtype=torch.float32, device="cuda"),
    mn=1024, k=2048, recipe=(1, 128, 128), is_sfa=False)
```

I had filed #52732 for the sm_121 side of this and have now closed it on this basis, including a public correction of my own suggested fix there: I had argued for excluding sm_121 from `support_deep_gemm()`, and that was the wrong shape of fix. The gate was right and the kernels have since caught up.

## What this does not cover

```
- @srinathh's finding above stands and is orthogonal. My run had `use_flattening=False supports_varlen=False (next_n=1)`, that is, the unpatched family-100 gate in `_supports_varlen_paged_mqa_logits()`. I did not enable the varlen path, so I have nothing to say about the illegal memory access that appears once it is.
- The SM120 branch of `get_paged_mqa_logits_metadata` asserts `block_kv == 32 or block_kv == 64`. Nothing in that dispatch accepts 2, so the 2-state compress case in #53635 and #53522 is still live. It is only the error text that changed, from `Unsupported architecture` under the old pin to the `block_kv` assert under the new one.
- On the vLLM side, `CutlassFp8BlockScaledMMKernel.can_implement()` is still `return True, None` and is still ordered ahead of `B12xFp8BlockScaledMMKernel` in `_POSSIBLE_FP8_BLOCK_KERNELS`. That stopped mattering for this model only because `DeepGemmFp8BlockScaledMMKernel` sits ahead of both and now handles ue8m0 itself (`Selected DeepGemmFp8BlockScaledMMKernel for Fp8LinearMethod`). A configuration that lands on the CUTLASS block kernel with ue8m0 scales would still fail.
- Also worth flagging for anyone tracking this: #53680 proposes pinning back to `a6b593d`. That commit still carries the `arch_major == 12` branches, so it would not reintroduce the failures above, but it is the kind of change worth re-testing after.
```
