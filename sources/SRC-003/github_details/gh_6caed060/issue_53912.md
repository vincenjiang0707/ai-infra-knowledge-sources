### 🐛 Describe the bug

**Summary.** `--enable-prefix-caching` together with MTP speculative decoding still corrupts output on hybrid (GDN/Mamba) Qwen3.5-class models in **v0.28.0**. A small fraction of responses degenerate into repeated punctuation (`!!!!…`) or come back empty. This is the same failure as #43559, which was closed as completed on 2026-08-06 — the merged scheduler-side fix (#51113) does not cover it, and the cache-manager-side fixes (#43650, #48375) are still open.

**Model.** Qwen3.5-architecture dense 27B VLM (`Qwen3_5ForConditionalGeneration`, hybrid: Gated DeltaNet linear-attention layers + full attention every 4th layer, vision tower), FP8 W8A8 compressed-tensors (`FP8_DYNAMIC`), with an MTP head present in the checkpoint (`Qwen3_5MTP` resolves at startup). TP=1, single H100.

**Server command** (paths redacted):

```bash
export VLLM_NO_USAGE_STATS=1
export VLLM_USE_FLASHINFER_SAMPLER=0

vllm serve <QWEN3_5_27B_FP8_WITH_MTP_HEAD> \
  --served-model-name path-mini \
  --port 8000 \
  --max-model-len 62768 \
  --max-num-seqs 32 \
  --gpu-memory-utilization 0.95 \
  --enable-chunked-prefill \
  --limit-mm-per-prompt.image 10 \
  --enable-prefix-caching \
  --mamba-cache-mode align \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 2}'
```

Startup confirms the configuration: `Resolved architecture: Qwen3_5MTP`, `enable_prefix_caching=True`, `num_spec_tokens=2`, `GPU KV cache size: 576,637 tokens`, attention block size 800 (forced up to match the mamba page size), async scheduling enabled (default).

**Workload.** Multi-step GUI-agent traces: each request is a conversation of prior steps plus 1–3 screenshots (sliding 2-image history), ~4k–12k prompt tokens, ~20–100 output tokens, `temperature=0`, client concurrency up to 32. Consecutive steps of the same episode share a long prefix, so prefix-cache hit rate climbs through a run.

**Observed.**

| vLLM | prefix caching | MTP | final prefix-cache hit rate | malformed responses |
|---|---|---|---|---|
| 0.26.0 | on | k=2 | 27.5% | 25 / 2,636 (0.95%) |
| **0.28.0** | **on** | **k=2** | **31.7%** | **4 / 495 (0.81%)** |
| 0.28.0 | on | k=2, `--kv-cache-dtype fp8` | ~10% (see note) | 0 / 1,135 |

Malformed = response is a run of repeated `!` characters, or empty content. `finish_reason` is normal; no HTTP 5xx, no crash, no traceback — the engine stays healthy and every other response in the same run is correct.

Two observations that point at the prefix cache rather than at MTP alone:

1. **Rate tracks cache hit rate.** Corruption appears only once the prefix cache starts hitting, and scales with the hit rate.
2. **`--kv-cache-dtype fp8` appears to avoid it, but only by destroying the cache.** With fp8 KV, vLLM raises the attention block size 800 → 1600 (`platforms/interface.py`, so that one attention page covers one mamba page). Our requests share ~1,700 tokens of prefix, so at a 1600-token matching unit almost nothing is reusable: hit rate collapses from 31.7% to ~10%, and malformed responses go to 0/1,135. That is consistent with reduced exposure, not with fp8 fixing the underlying defect. (For the same reason `--block-size 800` cannot be used to compensate: the value is derived and only ever raised.)

**Suspected cause** (already described in #43650 / #48375): `MambaManager.find_longest_cache_hit` in `vllm/v1/core/single_type_kv_cache_manager.py` accepts `drop_eagle_block` and never acts on it, so the final matched block — which can hold recurrent state written over draft positions that verification later rejected — stays reachable through the prefix cache and is reused by subsequent requests sharing that prefix. `FullAttentionManager` drops that block. In v0.28.0 the caller (`kv_cache_coordinator.py`) additionally skips the eagle margin for `MambaSpec` with the comment *"its finder never drops"*, i.e. caller and manager disagree about who is responsible.

Applying **#43650** (6 lines, `max_num_blocks -= 1` when `use_eagle`) on top of v0.28.0 starts cleanly and shows no regression on an unrelated accuracy check (100 grounding requests at concurrency 32: 76% vs 75% unpatched, identical coordinate error, 0 malformed). Other users report it resolving the symptom outright (#43650: 18/39 → 39/39 on a private benchmark; `content: null` at ~1-in-8 fixed completely).

**Expected.** `--enable-prefix-caching` + MTP on a hybrid Mamba/GDN model should be either correct or explicitly rejected at startup, not silently corrupting a fraction of responses.

**Notes / questions**

- Was #43559 closed by #51113 intentionally? #51113 fixes chunk alignment on the write path; the reports above (and this one) are about block dropping on the cache-read path, which neither #51113 nor #46384 appears to cover.
- If #43650 is considered too blunt because a hybrid block can be 1k+ tokens, would a narrower fix be acceptable — e.g. dropping the trailing block only when that block actually contains unverified draft positions?
- Happy to run any specific probe on this configuration; we can reproduce on demand with the workload above.

### johny-jose · 2026-08-26

Same symptom here on Qwen3.8-27B-FP8 and Qwen3.6-35B-A3B-FP8, but a different mechanism, worth ruling out before assuming it's the `drop_eagle_block` path.

**Discriminator:** re-run with `--no-async-scheduling`, nothing else changed. If corruption goes to zero while your hit rate stays put, it isn't the cache-read path, block dropping is unaffected by async scheduling.

Ours: 16/288 with async scheduling, 0/288 without, 0/288 with prefix caching but no MTP. It's a host/device race, the accepted-token counts are copied D2H in step N's row order, `_update_states` permutes that same pinned buffer in step N+1 before anything waits on the event, and the `prev_positions` gather then permutes them again, so a request picks up another request's count. Patch: https://github.com/vllm-project/vllm/pull/53919


### erdholion · 2026-08-28

Your title update says this persists in v0.28.0 — worth knowing that #50729 ("[Bugfix][Mamba] Fix overlapping state copy race", member-authored, merged to main Aug 17) **missed the 0.28.0 branch cut**, so v0.28.0 does not contain it. Neither does v0.27.1.

That fix addresses a speculative-decode **conv-state shift copying within the same physical block with overlapping source/destination ranges** — parallel memcpy-style loads/stores give no memmove ordering, so the shifted window can read partially-overwritten state. That is mechanically very close to the wrong-conv-window / GDN-snapshot corruption this issue tracks, and it would naturally correlate with prefix-cache hit rate (hits are what re-enter conv state mid-stream).

Suggestion: re-run your 288-request repro on a build that contains #50729 (the `v0.28.1rc0` tag or current main), async scheduling ON, everything else identical. If it drops to 0/288, this cluster has a root-cause candidate; if not, that's an important negative that rules the copy race out. Sibling fixes in the same lineage worth having in the build: #53077 (GDN empty-draft-schedule count reset) and #54076 (align-mode chunk splitting uses the Mamba cache group's block size).

### erdholion · 2026-09-01

@karls0r — on whether the `--no-async-scheduling` isolation test is worth running: yes, and it's a cleaner discriminator than it looks, because we're both on v0.27.1 and the gate is static there.

The gather that #51571 identifies as the defect sits inside an `if self.use_async_scheduling` branch. In v0.27.1, `vllm/v1/worker/gpu_model_runner.py:2118`:

```python
    if self.use_async_scheduling and prev_req_id_to_index:
        prev_idx = self.prev_positions.np[:num_reqs]
        ...
    else:
        # Non-async mode: use values directly
```

So `--no-async-scheduling` doesn't merely make the race less likely on your box — it removes the code path that #53919 patches. #51571's own fix plan says as much in its step 5 ("Preserve current upstream InputBatch ownership for non-async scheduling"). That makes @johny-jose's discriminator sound on your exact build: the cache-read block-drop path is scheduler-independent (`MambaManager.find_longest_cache_hit` accepts `drop_eagle_block` but never acts on it in v0.27.1, and `kv_cache_coordinator.py:755` skips the eagle margin entirely for `MambaSpec`), so if corruption survives async-off it is not #53919's mechanism.

Two controls worth keeping when you run it, since a null is only meaningful if the exposure is unchanged:

```
1. Confirm your `vllm:prefix_cache_hits_total` rate is the same in both arms. Async-off changes step timing, and if the hit rate moves you've changed exposure, not mechanism.
2. #53919's own repro only shows the bug under host starvation — its test plan notes that without `--cpus`, an idle box reads 0-1/192 and the bug looks absent. At `--max-num-seqs 4` you may be under the detection floor in *both* arms, so budget enough requests that the async-on arm actually produces a nonzero count before reading anything into an async-off zero.
```

I don't have a useful arm to contribute here: our v0.27.1 hybrid-GDN + MTP k=3 + prefix-caching box runs `--no-async-scheduling` at low concurrency, so per the gate above the #53919 path never executes on it, and a null there is uninformative by construction.

### jschmied · 2026-09-05

One data point that may or may not be your case: on Qwen3.8-Flash-Next we traced "a small fraction of responses degenerate with MTP on" to a strided `state_indices_tensor_p[:, 0]` view (the Mamba block table is `1 + num_speculative_blocks` wide once speculation is configured) read with unit stride by a state-carrying kernel, so every prefill after batch row 0 in a prefill-only scheduler step wrote its state into request 0's checkpoint blocks — #55357 has the reproducer and mechanism, #55375 the fix for the PLE short conv (the merge candidate; my duplicate #55467 is closed). The tell is that the corruption needs two or more prompts prefilled in the same step and disappears when they arrive 150 ms apart, independent of prefix caching. If your fraction tracks concurrent arrivals rather than cache hits, it is worth checking the state-index consumers of the GDN path in your build for the same assumption.
