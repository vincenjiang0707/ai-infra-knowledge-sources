## 正文

### Proposal to improve performance

## Summary

On AMD gfx1201 (Radeon AI PRO R9700), a stream of small kernels picks up about 17 µs per dispatch when two or more other HIP streams hold pending waits on it (default hardware-queue limit, graph mode). The driver/runtime side, with a framework-free HIP reproducer, is reported at https://github.com/ROCm/legacy-rocm-build/issues/6685.

The V2 GPU model runner creates exactly that situation on the last pipeline-parallel stage:

```python
- `PPHandler.broadcast()` (and the draft-token broadcast) in `vllm/v1/worker/gpu/pp_utils.py` runs `broadcast_stream.wait_stream(main_stream)` and then enqueues the sends on `broadcast_stream`.
- The async output path copies results device-to-host on its own copy stream, which also waits on the main stream.
```

So while the next step's graph runs, two side queues are waiting on the main stream. On gfx1201 that roughly doubles the time of the dispatch-heavy decode forward. The gfx1030 (V620) control was unaffected; NVIDIA was not tested.

## Measurements

The setup was PP=3 and TP=1 with ranks on V620, V620 and R9700 (last rank). It used an MoE hybrid model with MTP2 speculative decoding, FULL HIP graphs and ROCm 7.14.

| Configuration | R9700 forward (15 layers), median | Pipeline step period | Decode throughput |
| --- | ---: | ---: | ---: |
| Side streams (default) | ~16.9–17.0 ms | ~56–58 ms | ~33 tok/s |
| Last-rank sends and output copy on the main stream | 7.18–7.23 ms | 41.6–42.2 ms | 45.3–46.6 tok/s |

Across 803 measured R9700 forward intervals with the change, every one was below 10 ms. In a separate serving measurement, median decode rose from 31.0 to 46.5 tok/s. The model, weights, placement, graph mode and receiving ranks were unchanged. We have not isolated the individual contribution of each of the two streams, since both were moved together.

### Why not just `GPU_MAX_HW_QUEUES=2`?

In the ROCm microbenchmark, `GPU_MAX_HW_QUEUES=1` or `2` removed the tiny-kernel penalty without code changes. In serving, it also brought the R9700 forward down to ~7.2 ms with the original side streams (B), but it **did not match the main-stream option end to end**:

| Arm | Last-rank main stream | `GPU_MAX_HW_QUEUES` | R9700 forward median / p90 | Step period median | Three xhigh decode rates | 16K TTFT |
| --- | --- | --- | ---: | ---: | --- | ---: |
| A | On | Unset | 7.216 / 7.683 ms | 41.744 ms | 48.2 / 48.9 / 42.2 tok/s | 9.900 s |
| B | Off | 2 | 7.220 / 7.656 ms | 52.755 ms | 35.9 / 35.8 / 34.3 tok/s | 9.915 s |
| C | On | 2 | 7.261 / 7.729 ms | 52.239 ms | 35.9 / 36.2 / 37.2 tok/s | 9.954 s |

The V620 rank forwards rose from ~10.9 ms in A to ~12.9–13.1 ms in B. The queue cap appears to serialize communication with compute on every GPU, although we have not isolated the exact source of the added time. So the queue limit is a useful diagnostic but not a serving fix.

On output: temperature-0 generations are not run-to-run identical on this stack even with the same configuration (a restarted A1/A2 control diverged on 2 of 3 prompts). So token-level A/B differences between the settings do not indicate an effect on output quality.

## Proposed change

Add an opt-in setting (an environment variable or a `ParallelConfig` field) that makes the last PP rank enqueue its token and draft broadcasts, and the async output copy, on the current (main) stream instead of dedicated side streams. Then either:

- leave it off by default and document it for gfx12 users, or
- turn it on automatically when `current_platform.is_rocm()` and the device is gfx12, until the ROCm issue is resolved.

The cost is that those small sends and copies no longer overlap with the next step's launch on the main stream. On gfx1201 that is far cheaper than the dispatch penalty. We have a local patch and can open a PR if the maintainers prefer one of these two options.

The same mechanism may be relevant to the unexplained bimodal single-GPU R9700 decode reported in ROCm/ROCm#6347, since the async output copy stream also waits on the main stream without PP. We have not tested that.
