## 正文

### Your current environment

Docker image `vllm-openai:v0.24.0 - v0.26.0`

### 🐛 Describe the bug

### Summary

I'm seeing a major output-token throughput regression starting with vLLM v0.24.0 and still present in v0.25.0 and v0.26.0.

With the same model, workload (40 parallel requests / ~1k input), and configuration:

- v0.24.0 / v0.25.0 / v0.26.0: output throughput is dramatically lower, generally below ~1k output tokens/s.
- v0.23.0: throughput is much higher, around ~5k output tokens/s under the same workload.

The attached graph shows the difference between runs using the different vLLM versions.

<img width="974" height="311" alt="Image" src="https://github.com/user-attachments/assets/3d1b1f5f-abff-4501-97e5-58f87bcc0a2e" />

### v0.23.0 behavior

v0.23.0 gives much better throughput, but after running for some time the pod can enter what looks like a deadlocked/stuck state:

- Requests remained reported as in-flight indefinitely.
- GPU utilization stayed at ~100%, but no useful inference progress was made.
- Output-token generation stopped completely.
- No new engine statistics were emitted for 10+ hours.
- The API server remained responsive and /health continued returning HTTP 200.
- New requests routed to that replica consequently hung until the upstream request timeout.
- Restarting the pod was required to recover.

This looked like the API process remained healthy while the underlying EngineCore/CUDA execution was stuck.

We don't have logs from the exact moment the engine stopped progressing, so I can't confirm whether this was a CUDA/MoE issue, scheduler issue, or something else.

This is the main reason I tried upgrading, but the newer versions introduce the large throughput regression described above.

### Configuration

The parameters are unchanged between tests:

```yaml
vllmConfig:
  enablePrefixCaching: true
  tensorParallelSize: 1
  extraArgs:
  - --served-model-name
  - Qwen/Qwen3.6-35B-A3B-FP8
  - --trust-remote-code
  - --load-format
  - runai_streamer
  - --tool-call-parser
  - qwen3_coder
  - --reasoning-parser
  - qwen3
  - --mm-encoder-tp-mode
  - data
  - --max-num-seqs
  - 256
````

I also tested v0.26.0 with the old model runner:

```bash
VLLM_USE_V2_MODEL_RUNNER=0
```

but this did not improve the throughput.

### Question

Has anything changed between v0.23.0 and v0.24.0 that could explain such a large decoding/output-token throughput regression for this model/workload?

Are there any flags, scheduler/model-runner settings, or metrics/profiling options you would recommend trying to narrow down where the regression is coming from? I'm also interested in any suggestions for diagnosing the stuck/"ghost running requests" behavior on v0.23.0, since otherwise that version performs significantly better.
