- vLLM `main`: `76ba32160a501e5e8aadb5e1820c51c765714220`
- Also observed with vLLM 0.28.0: `2cf0a6915ce544dc493a0990f2ea38d81601128a`
- Python 3.12.3, PyTorch 2.13.0+cu130
- Runtime validation: two NVIDIA DGX Spark systems (GB10), driver 580.173.02,
  CUDA 13.0, Ubuntu 24.04.4 aarch64

### Describe the bug

When `CompilationConfig.max_cudagraph_capture_size` is set explicitly but
`cudagraph_capture_sizes` is left unset, `_set_cudagraph_sizes()` builds the
default stepped grid and silently truncates the scalar maximum to the largest
grid entry.

For static speculative decoding with `max_num_seqs=6` and six speculative
tokens, the widest uniform decode batch is:

```text
6 requests * (1 sampled token + 6 speculative tokens) = 42 tokens
```

Setting `max_cudagraph_capture_size=42` currently produces a capture list that
ends at 40 and changes the resolved maximum to 40. The model-runner-v2 CUDA
graph manager rounds the 40-token candidate to the seven-token query width,
gets 42, then rejects it because 42 exceeds the resolved maximum of 40. The C6
verification step therefore dispatches eager.

#### Minimal reproducer

```python
from types import SimpleNamespace
from unittest.mock import MagicMock

from vllm.config import (
    CompilationConfig,
    CUDAGraphMode,
    ParallelConfig,
    SchedulerConfig,
    VllmConfig,
)

compilation_config = CompilationConfig(
    cudagraph_mode=CUDAGraphMode.FULL_AND_PIECEWISE,
    max_cudagraph_capture_size=42,
)
config = MagicMock(spec=VllmConfig)
config.compilation_config = compilation_config
config.scheduler_config = SchedulerConfig.default_factory(
    max_num_seqs=6,
    max_num_batched_tokens=8192,
)
config.parallel_config = ParallelConfig()
config.model_config = MagicMock(enforce_eager=False)
config.performance_mode = None
config.diffusion_config = None
config.speculative_config = SimpleNamespace(
    num_speculative_tokens=6,
    num_speculative_tokens_per_batch_size=None,
    uses_dynamic_speculative_decoding=lambda: False,
)
config.num_speculative_tokens = VllmConfig.num_speculative_tokens.fget(config)
config.uniform_decode_query_len = VllmConfig.uniform_decode_query_len.fget(config)

VllmConfig._set_cudagraph_sizes(config)
print(compilation_config.max_cudagraph_capture_size)
print(compilation_config.cudagraph_capture_sizes)
```

Actual output on current `main`:

```text
WARNING ... Truncating max_cudagraph_capture_size to 40
40
[1, 2, 4, 8, 16, 24, 32, 40]
```

Expected output:

```text
42
[1, 2, 4, 8, 16, 24, 32, 40, 42]
```

The expectation is not that every scalar maximum must necessarily become a
capture size. It is that a schedulable uniform decode shape that fits within an
explicit scalar bound is not discarded merely because it is off the inferred
8/16-token stride. An explicit `cudagraph_capture_sizes` list should remain
authoritative.

### Measured serving impact

We reproduced this with DeepSeek V4 Flash Vision, DSpark static K=6,
`max_num_seqs=6`, and an otherwise matched two-node/two-rank configuration.
Five p256/C6 trials were run in each lane:

| C6 median | Inferred list ending at 40 | Exact 42 included |
|---|---:|---:|
| Decode/request | 30.4 tok/s | 27.0 tok/s |
| Aggregate throughput | 25.3 tok/s | 133.3 tok/s |
| TTFT | 26.016 s | 0.839 s |

Adding the 42-token capture removes the eager verification step, improving
aggregate throughput by 5.27x and reducing TTFT by 96.8%. Startup shape probes
also completed 47/47 in 30 seconds, compared with 85 seconds before the fix.

### Related work and duplicate check

- #50488 added uniform-decode shapes when vLLM computes the default scalar
  ceiling; #54418 subsequently kept those defaults within the platform memory
  ceiling. The explicit scalar branch still does not populate
  `uniform_decode_sizes`.
- Open PR #37865 addresses the same externally visible truncation by appending
  every explicit scalar maximum to the inferred grid. It is currently stale
  and conflicted. A narrower alternative is to append only the widest
  schedulable uniform-decode shape when it fits within the scalar maximum,
  leaving unrelated scalar bounds and explicit capture-size lists unchanged.

Because #37865 overlaps this bug, I am not opening a competing PR without
maintainer/author coordination. I have a rebased two-file patch and regression
test ready if the narrower semantics are preferred.

```
max_cudagraph_capture_size = 40
```

So the requested 42 becomes 40, and the shape that disappears is exactly the one the config implies: `max_num_seqs=6` × `uniform_decode_query_len=7` = **42**. The full-batch uniform-decode shape is the one that isn't capturable.
