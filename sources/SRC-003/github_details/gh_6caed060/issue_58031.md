## 正文

> **EDIT (2026-09-23):** The root-cause attribution below is **withdrawn**. `nm -D` shows the `fp4_block_scale_moe` symbols live in `fused_moe_trtllm_sm100.so` (which carries `sm_103a` cubins), not `trtllm_gemm.so` (the dense GEMM module — the sm_100a-only observation is real but irrelevant to this op). The "candidate can never execute on SM103" mechanism does not hold. The symptom stands (unbounded autotune at boot, 40+ min, zero progress lines, no cache write before termination); it is now considered a probable extreme-slow-crawl rather than a proven hang, since the autotuner logs nothing between start and end and only writes the cache on completion. See [this comment](https://github.com/vllm-project/vllm/issues/58031#issuecomment-5788562400) for the corrected analysis and proposed scoping (exclude SM103 from `FLASHINFER_TRTLLM_MXFP4_MXFP8` auto-selection; add per-bucket progress logging). The workaround below remains valid.

## Describe the bug

On a DGX Station GB300 (SM103, compute capability 10.3), the FlashInfer autotune for `trtllm_fp4_block_scale_moe` runs indefinitely at 100% GPU with zero progress and zero autotune cache writes, wedging engine startup forever. There is no error, no traceback, no timeout — the boot simply never completes.

The root cause appears to be an arch-coverage gap in FlashInfer's prebuilt `trtllm_gemm` cubin, combined with an autotuner that has no timeout for a candidate kernel that never terminates.

## Environment

```
- Image: `vllm/vllm-openai:nightly` pulled 2026-09-21 (vLLM `0.29.1rc1.dev452+g3df4ae153`, FlashInfer `0.6.18.post1`), arm64
- GPU: NVIDIA GB300 (SM103), driver 610.43.02
- Model: DeepSeek-V4.1-Flash (MXFP4 experts / MXFP8 rest), TP1, `--cpu-offload-gb 75`, DSpark speculative k=5
- Flags relevant: `--max-num-batched-tokens 16384`, moe backend auto-selects `FLASHINFER_TRTLLM_MXFP4_MXFP8`
```

## Reproduction

Serve DeepSeek-V4.1-Flash (or any model that routes MoE through `trtllm_fp4_block_scale_moe`) on SM103 **without** skipping the op's autotune. Boot proceeds normally through weight load, CUDA graph capture, and JIT warmup, then reaches:

```
[flashinfer_sparse_mla_warmup.py:267] Warming up DeepSeek V4 sparse MLA attention for mixed tokens=16.
[kernel_warmup.py:436] Using FlashInfer autotune cache file: .../autotune_configs.json
autotuner.py:972 - flashinfer.jit: [Autotuner]: Autotuning process starts ...
[kernel_warmup.py:358] Running FlashInfer autotune with 16384 tokens and token buckets (1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 768, 1024, 1280, 1536, 1792, 2048, 2560, 3072, 3584, 4096, 8192, 16384).
```

… and stays there. Observed: 40+ minutes at 100% GPU utilization, 0 new log lines in any 10-minute window, and the cache directory for the config hash created but left **empty**:

```
drwxr-xr-x 2 root root 4096 Sep 21 15:35 .   # created when autotune started
# (no autotune_configs.json ever written)
```

By contrast, the JIT kernel warmup immediately before it completes with per-batch progress lines (10/10 batches in 47s), so the wedge is specific to this op's autotune, not to warmup in general.

The same behavior existed on the launch-day `deepseekv41-flash-0909` image, which is why this deployment has carried `VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS="trtllm_fp4_block_scale_moe,flashinfer::trtllm_fp4_block_scale_moe"` since September 9. Reproducing it on current nightly shows the gap is not fixed.

## Root cause evidence

Inspecting FlashInfer's prebuilt cubins in the nightly image (`flashinfer_jit_cache`):

```console
# 907 .so files in flashinfer_jit_cache overall — sm_103a coverage exists:
$ for so in $(find . -name "*.so"); do cuobjdump -lelf $so 2>/dev/null | grep -oE "sm_103[a-z]?"; done | sort | uniq -c
   3380 sm_103a

# …but the cubin the fp4 block-scale MoE autotuner benchmarks:
$ cuobjdump -lelf .../jit_cache/trtllm_gemm/trtllm_gemm.so | grep -oE "sm_[0-9]+[a-z]?" | sort | uniq -c
      1 sm_100a

$ cuobjdump -ptx .../jit_cache/trtllm_gemm/trtllm_gemm.so | grep -oE "target sm_[0-9]+" | sort | uniq -c
      (empty — no PTX section at all)
```

`trtllm_gemm.so` ships **only an `sm_100a` cubin and no PTX**. An arch-specific (`a`-suffixed) cubin runs on exactly its target arch and never on a later one (this is the same mechanism as the `cooperative_topk` SM103 gap documented in the DeepSeek-V4.1-Flash SM103 patch work — `sm_100a` cubins are unusable on SM103, and without PTX there is nothing to JIT forward).

So on SM103 the autotuner launches a candidate that either fails its launch silently or spins in a grid-stride loop sized for a different arch, and the `cudaEventSynchronize` in the timing loop blocks forever. The autotuner has no per-candidate timeout, so one non-terminating candidate wedges the whole boot.

## Suggested fixes (either would do; both would be robust)

1. **Ship an `sm_103a` (and ideally `sm_103`-JITable PTX) build of `trtllm_gemm`** — the rest of the JIT cache clearly builds for 103a (3,380 cubins), so this specific module looks like an omission rather than a fundamental limitation.
2. **Add a timeout to the FlashInfer autotuner per candidate/bucket** — a wedged candidate should be skipped and logged, not hang the engine forever. Right now one bad kernel costs an unbounded boot.

## Workaround

```
VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS="trtllm_fp4_block_scale_moe,flashinfer::trtllm_fp4_block_scale_moe"
```

With the skip, the same configuration boots to serving in ~8 minutes; the op then runs on its default (untuned) kernel selection. Measured decode on this deployment is ~91 tok/s single-stream with the skip in place.

Same symptom on a second GB300 (SM103) with a different model, plus timings that may help size the fix.

```
- `--moe-backend marlin` (+ `VLLM_USE_DEEP_GEMM=0`): autotune **9 s** ("Saved 0 configs"), same model, same box, serves correctly. That matches what #57784's launch lines and the public GB10 serves use.
```

So on SM103 the TRT-LLM MXFP4 path is not just slow to tune, it is the default and there is no log line telling the user the arch is unsupported. Excluding SM103 in that backend's `is_supported` (or at minimum a warning at selection) would have saved a full night here. Happy to test a patch on this box.

### jmeadlock · 2026-09-22

Checked the cubin side on my box (same FlashInfer `0.6.18.post1`, image `nightly-d05da62e`). I don't think `trtllm_gemm.so` is the module this op runs from:

```
# op symbol location
nm -D jit_cache/trtllm_gemm/trtllm_gemm.so                       | grep -ci fp4_block_scale_moe  -> 0
nm -D jit_cache/fused_moe_trtllm_sm100/fused_moe_trtllm_sm100.so | grep -ci fp4_block_scale_moe  -> 2

# arch coverage of the module that does export it
cuobjdump -lelf fused_moe_trtllm_sm100.so -> 10 sm_100a, 10 sm_103a, 10 sm_120

# the MoE GEMM kernels themselves (flashinfer_cubin/.../batched_gemm-*)
6,846 cubins; the MxE2m1 ones are sm100f (family, runs on 10.3) plus 90 sm103a-specific
```

So `trtllm_gemm.so` being `sm_100a`-only with no PTX looks real, but it's the dense GEMM module, not the one the fp4 block-scale MoE autotuner benchmarks. The MoE kernels do have SM103 coverage, which fits what I saw: tactics executing at 52–66 ms/call, not failing to launch.

That makes me suspect our two cases are the same failure at different scale rather than two mechanisms. The autotuner prints nothing between "Autotuning process starts" and the end, so a very slow sweep and a true hang look identical in the log. Mine needed ~2 h at `--max-num-batched-tokens 2048` (16 buckets); yours is profiling at 16384 with 22 buckets and a larger shape, so 40 min with no cache write would be expected even if it is progressing. (The cache file is written at the end, so an empty dir doesn't separate the two either.)

A cheap way to tell: two `py-spy dump --locals --pid <EngineCore>` a few minutes apart. If the frame is inside `choose_one` and the tactic/profile locals move, it's a crawl; if the stack is parked on the same tactic, it's a real hang and the root cause is somewhere other than `trtllm_gemm.so`. (`FLASHINFER_LOGGING_LEVEL=DEBUG` also surfaces per-tactic lines; at INFO the autotuner only logs start and end.)

```
Either way the vLLM-side fix is the same and small, so I'd suggest scoping this issue to it:
1. On SM103, don't auto-select `FLASHINFER_TRTLLM_MXFP4_MXFP8` (the check is `is_device_capability_family(100)` in `trtllm_mxfp4_moe.py`, which includes 10.3), or at minimum warn at selection that autotune may take hours and point at `--moe-backend marlin` / the skip env.
2. Log per-bucket progress in the FlashInfer autotune warmup so "slow" and "hung" are distinguishable.
```

A per-candidate timeout is a FlashInfer-side change; worth a separate FlashInfer issue if the py-spy check shows a genuine hang. I can put up (1)+(2) as a PR and validate on this GB300 if that's the direction you want.

### jmeadlock · 2026-09-23

Two corrections to my earlier comments, from our DeepSeek-V4.1-Flash logs on the same GB300.

The autotuner isn't silent. FlashInfer wraps the sweep in tqdm (`[AutoTuner]: Tuning flashinfer::trtllm_fp4_block_scale_moe: N/21`, `\r`-separated on stderr). If your capture shows nothing, it is probably dropping those lines.

SM103 isn't the variable; expert placement is. Same box, same op, same nightly (`dee37d89`), same 21 buckets, MBT 8192: stock `--offload-backend uva --cpu-offload-gb 60` spent 71 min in one tuning pass of this op (~3 min/profile). With our [pin-hot-experts hook](https://github.com/J-M-Recipes/recipes/tree/main/recipes/dgx-station-gb300/deepseek-v4.1-flash-vllm-uva-dspark/results/2026-09-17-e2b-pin-hot-experts-v15/hook) (after load it moves the most-used experts into HBM and leaves the rest in Grace; `--cpu-offload-gb 54`, the only other arg change), the same pass took 8 min. Across all our boots: stock placement 72–77 min total autotune, hook 15–17. Your 75 GB stock offload at 16384 / 22 buckets should be slower than our stock case, so 40 min with no cache written fits a crawl.

Withdrawing the SM103 gating proposal.
