### 🐛 Describe the bug

### Summary

Serving **GLM-5.3-Flash** on **8x NVIDIA H20** with vLLM nightly (`260904`). One engine worker (`Worker_TP2_EP2`) aborted with `torch.AcceleratorError: CUDA error: an illegal memory access was encountered` while building attention metadata inside the **FlashInfer SM90 sparse MLA** backend (`flashinfer_mla_sparse_sm90.py`, called from `mamba_hybrid.py prepare_attn`). The fault is reported at a host-side sync point (`positions[:num_rows].cpu()`), so the actual faulting kernel is likely earlier in the async stream, not necessarily the FlashInfer path itself.

### Serving config (EXTRA_PARAMS)

```
--enable-expert-parallel
--no-enable-flashinfer-autotune
--tool-call-parser glm47
--enable-auto-tool-choice
--reasoning-parser glm45
--speculative-config '{"method":"mtp","num_speculative_tokens":5}'
```

Load: input/output length 65536, batch_size 32 (crash observed mid-serving on a normal chat completion request).

### jdejongcalian · 2026-09-24

Deterministic repro of this on 4x H200 (SM90), TP4, **no EP, no MTP**: the trigger is a single uncached prefill longer than about 132 K tokens.

**Setup.** `vllm/vllm-openai:v0.30.0` (FlashInfer 0.6.18.post1, CUDA 13.0.2, driver 580.173), `zai-org/GLM-5.3-Flash` FP8 at `eb9eb208`, BF16 KV cache, prefix caching on (default), async scheduling on (default), `--max-num-batched-tokens 8192` (default).

```
vllm serve zai-org/GLM-5.3-Flash --tensor-parallel-size 4 --max-model-len 262144 \
  --gpu-memory-utilization 0.90 --enable-auto-tool-choice --tool-call-parser glm47 \
  --reasoning-parser glm47 --no-enable-flashinfer-autotune \
  --limit-mm-per-prompt '{"image":0,"video":0}'
```

Auto-selects `FLASHINFER_MLA_SPARSE_SM90`. Requests are chat completions of random words behind a random prefix (so nothing is served from the prefix cache), `max_tokens: 1`, sized exactly with `/tokenize`:

| prompt tokens (fresh) | result |
|---|---|
| 130,999 (first request on a fresh server) | ok |
| 131,150 / 131,498 / 131,798 / 132,100 | ok |
| 132,400 | illegal memory access |
| ~132.5 K, ~133–134 K, 133,998 (third request, after two ~131 K ones), 134,004 (the **first** request on a fresh server) | illegal memory access |

So it is a length threshold between 132,100 and 132,400 tokens, independent of what the server served before. `2^17 + 1152` (one 1,152-token hybrid KV block past 2^17) falls in that window, which may or may not be a coincidence. Prompts of 139–142 K whose earlier part was a prefix-cache hit did *not* crash, so it looks tied to how much of the long prompt is prefilled fresh.

The fault surfaces exactly as reported here: at the host sync in `FlashInferMLASparseSM90Builder._kv_lens_host` (`positions[:num_rows].cpu()`, line 349), reached from `mamba_hybrid.py prepare_attn`, i.e. from an earlier kernel in the previous step. One rank then never answers, and the EngineCore hangs 5 minutes on the `sample_tokens` RPC before dying.

**Not the indexer's logits chunking:** `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=256`, which halves the context lengths at which a prefill step's query rows are split into more sub-chunks, passes fresh 60 K/70 K/100 K and still crashes at ~133 K.

**Workaround: `--attention-backend FLASH_ATTN_MLA_SPARSE`.** Same image and flags, same probe sequence: fresh prefills of 59.6 K, 69.5 K, 99.3 K, 133.0 K, 168.7 K, 198.9 K and 248.6 K all succeed; on a fresh server, 134,000 as the first request, then 132,396 and 250,000, all succeed; and a three-needle recall at 199 K (10/50/90 % depth) returns all three. It is also faster here, matching #56564:

| | FLASHINFER_MLA_SPARSE_SM90 | FLASH_ATTN_MLA_SPARSE |
|---|---|---|
| decode, 1 stream | 128–130 tok/s | 126 tok/s |
| prefill at 130 K | 16.1 K tok/s | 22.9 K tok/s |
| 16 concurrent, aggregate output | 658 tok/s | 1,207 tok/s |

This is consistent with @cjackal's coredump above, which puts the faulting PC in `flashinfer::mla::hopper::BatchMLAPageAttentionHopperKernel`.

Two side notes from the same session. `FLASH_ATTN_MLA_SPARSE` prints the zero-extent `Failed to initialize the TMA descriptor 1` dumps from #56563 here too, without MTP: about 40 KB of log per 256 generated tokens, output unaffected. And `--enforce-eager` together with `CUDA_LAUNCH_BLOCKING=1` crashed on the *first* ~13 K-token request (illegal memory access surfacing at `_compute_slot_mappings_kernel` in `block_table.py`), so blocking launches were not usable to name the kernel here.

AI assistance was used to run these probes and write this comment.
