## 正文

## Purpose

Add an output-only no-repeat n-gram GPU logits-processor plug-in for Model Runner V2. The implementation scans the existing persistent GPU token history with one batched Triton kernel, avoiding the per-request Python processor's model-runner fallback.

The processor is loaded through the existing custom logits-processor path with the FQCN `vllm.v1.worker.gpu.sample.no_repeat_ngram:NoRepeatNGramState`; it is not registered in the built-in sampler list. It is available offline through `SamplingParams.extra_args` and online through `vllm_xargs`. It accepts:

- `no_repeat_ngram_size`, with `ngram_size` as an OCR-integration compatibility alias;
- `window_size`, which bounds the recent output-token history searched;
- `whitelist_token_ids`, which keeps OCR grounding/control tokens available.

Prompt tokens are deliberately excluded. Reused request slots are reset, invalid or out-of-vocabulary values fail closed, and speculative decoding is rejected when the plug-in is initialized.

The DeepSeek-OCR, DeepSeek-OCR-2, and multi-image OCR examples now load this GPU plug-in instead of registering the legacy per-request processor. For exact compatibility, the `ngram_size=1` alias preserves the legacy processor's no-op behavior, while canonical `no_repeat_ngram_size=1` retains standard unigram blocking semantics.

## Model evaluation

A controlled generative-OCR crossover ran on one H200 with the same 100 rendered pages, prompts, sampling parameters, concurrency 32, 8 warm-up requests, and three measured rounds. Both paths used the same `TRITON_ATTN` decoder backend and `TORCH_SDPA` multimodal-encoder backend on the vLLM 0.29.0 CUDA 13.0 runtime:

```
- official per-request Python processor: **7.9096 layout pages/s**;
- this GPU plug-in: **8.5430 layout pages/s** (**+8.0% throughput**, **-7.4% elapsed time**).
```

All 100 outputs from both paths retained the expected layout structure, with no empty or repeated-punctuation outputs. The plug-in run mounted this PR's Python source over the 0.29.0 runtime because no matching prebuilt PR image was available; incompatible FlashAttention Python/native ABIs were therefore avoided by holding both runs to the same backends above. This is a layout-stage comparison, not a claim of the same end-to-end document throughput gain. The repository includes the reusable HTTP benchmark driver used for the comparison.

Thank you @HuXinjing for working on this! I had a discussion with @njhill and since DeepSeek-OCR is currently the only consumer of this feature, we'd prefer to keep the processor model-scoped instead of adding a generic plugin under `vllm/v1/worker/gpu/sample/`. And as Model Runner V2 supports custom logits processors (#56497), the new implementation should serve as an enhancement implements it with the V2 interface rather than the legacy V1 per-request path. For testing we would need to make sure:

1. This custom LP is supported with MRV2
2. Existing perf comparison

Concretely:

1. **Move the implementation into the model file.** Relocate the V2 logits processor class (including the Triton kernel) from `vllm/v1/worker/gpu/sample/no_repeat_ngram.py` into `vllm/model_executor/models/deepseek_ocr.py`, next to the existing V1 `NGramPerReqLogitsProcessor` (`deepseek_ocr.py:140`). Keep the `triton` import function-scoped (inside `__init__`/`apply`): the frontend process imports this module to run `validate_params` at request admission (`vllm/v1/worker/gpu/sample/logits_processor/loader.py`), so the module must stay importable without model-runner/triton dependencies.

3. **Auto-register it via a model config hook, following the Unlimited-OCR pattern (#46564).** Add a `DeepseekOCRForCausalLMConfig(VerifyAndUpdateConfig)` (and the DeepSeek-OCR-2 arch) to `MODELS_CONFIG_MAP` in `vllm/model_executor/models/config.py`, mirroring `UnlimitedOCRForCausalLMConfig`. In `verify_and_update_config(vllm_config)`, append the processor to `model_config.logits_processors`, selecting the class by runner version: the V2 GPU class when `vllm_config.use_v2_model_runner` is true, otherwise keep registering the existing V1 `NGramPerReqLogitsProcessor` (the V1 and V2 loaders each reject classes of the other interface, so both runner paths need a matching class). Also dedupe against user-supplied entries in `model_config.logits_processors` so explicit registration doesn't apply the processor twice.

4. **Keep activation per-request.** With the class auto-registered, users no longer pass `logits_processors=[...]` in `EngineArgs`; activation stays via `extra_args` (`ngram_size` / `no_repeat_ngram_size`, `window_size`, `whitelist_token_ids`). When `ngram_size` is absent, `add_request()` should return `False` so default sampling behavior is unchanged.

5. **Keep speculative decoding unsupported.** The feature functionally does not support spec decode (the V1 path already rejects custom logits processors with spec decode via `STR_SPEC_DEC_REJECTS_LOGITSPROCS`, and this PR does the same at plugin init), so keep rejecting it outright when the processor is registered. Note the corollary of auto-registration: DeepSeek-OCR + spec decode becomes an unsupported combination entirely, which matches the feature's semantics.

6. **Update examples and docs.** Drop the explicit `logits_processors=[NGramPerReqLogitsProcessor]` from the DeepSeek-OCR / multi-image OCR examples (`examples/generate/multimodal/vision_language_offline.py`, `vision_language_multi_image_offline.py`); keep the `extra_args`. Adjust `docs/features/custom_arguments.md` accordingly.
