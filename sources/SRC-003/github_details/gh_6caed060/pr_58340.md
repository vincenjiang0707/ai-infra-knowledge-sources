## Purpose

Expose the number of draft tokens selected for target verification when adaptive verification is enabled.

Adaptive verification may verify fewer tokens than were originally proposed, so the existing vllm:spec_decode_num_draft_tokens_total metric does not reflect the actual verification budget.

This PR adds:

vllm:spec_decode_num_verified_draft_tokens_total
plumbing from the model runner to speculative decoding stats
documentation and unit tests

The existing draft and acceptance metrics are unchanged.

### seongyun1104 · 2026-09-25

This fills a real gap — with adaptive verification `num_draft_tokens` counts proposals and
nothing counted what the target actually verified. Two notes, one on composition and one on
the shape.

**This and `spec_decode_scheduled_k` are complements, not overlaps.** I have #54748 open
adding the K the schedule *resolved*, including the K=0 steps that currently increment no
counter at all. That is the scheduler's decision; yours is what survived the verifier's
trim. With both, `scheduled_k → draft_tokens → verified → accepted` is a closed chain; with
either alone there is a step where tokens vanish with no accounting line. They touch
different hunks of `update_from_output`, so they compose — I mention it only so the overlap
in files does not read as duplicated work.

**On the shape.** Your doc note is right that the mean is derivable: `observe_draft` is
called per request (`make_spec_decoding_stats` takes a `request_id`,
`scheduler.py:2885-2899`), so `num_drafts` counts drafting requests and
`verified / num_drafts` is mean admitted depth. My concern is not that the denominator is
missing — it is that a mean is the wrong summary for how this budget is actually spent.

`_assign_draft_token_budget` scores every `(request, step)` slot by survival probability and
admits a **global top-k** across the batch, then writes the per-request result back into
`capacities` — its docstring says so directly: `capacities` "enters holding each request's
scheduled draft count ... and leaves holding the admitted count"
(`adaptive_verification.py:61-63`). A global top-k concentrates by construction: confident
requests keep their full depth and unconfident ones are zeroed. So with 40 drafting
requests and 40 verified positions, mean admitted depth is 1.0 whether every request kept
exactly one, or four kept ten and thirty-six kept none. Those are opposite operating
conditions — a uniform shave versus a subset losing speculation entirely — and the mean
reports them identically. `num_verified_draft_tokens` is the sum of `capacities`, so the
distribution is discarded one step before it is exported.

The shape that answers it without unbounded labels already exists in the file you are
editing: `SpecDecodingStats` carries `num_accepted_tokens_per_pos` and
`num_draft_tokens_per_pos` (`spec_decode/metrics.py:30-31`), exported through the
per-position counter machinery at `:247-281`. A `num_verified_draft_tokens_per_pos` completes
that triple — proposed, verified, accepted, all keyed on draft index — at a vector length of
`num_spec_tokens`, cardinality this file already spends twice. "Position 5 is proposed but
never verified" then reads straight off it, and the concentrated case separates from the
uniform one because the tail buckets differ.

The honest cost: `capacities` is an `int32` device tensor (`:162-164`) that currently never
leaves the GPU — it is consumed in place by the `cu_num_logits` and `query_start_loc` cumsums
(`:432-442`). Filling a per-position vector needs it on the host, so this adds a
synchronisation to a per-step path. A device-side `bincount` into `num_spec_tokens + 1`
buckets keeps the transfer to a fixed small vector rather than `num_reqs`, and it may fold
into a sync already happening nearby, but I cannot settle that from outside and it is
reasonable to land the scalar first and treat the vector as a follow-up.

Disclosure: #54748 is mine and the closed chain above is better for it existing. Nothing
here depends on that PR landing and I am not asking you to reference it; the distribution
point stands on its own.
