## 正文

List of planned enhancements and fixes for the `NixlPushModeConnector`, aimed at solidifying the implementation for large-scale operational deployments and for use behind an orchestration layer (llm-d / Dynamo), bringing its reliability and failure-handling to parity with the mature pull-mode connector.
Will track respective PRs here.

**Priority:**
- 🔴 **P0** = blocks primetime
- 🟠 **P1** = high
- 🟡 **P2** = medium
- ⚪ **P3** = low / optional

**Summary:** 🔴 **4× P0**, 🟠 **4× P1**, 🟡 **4× P2**, ⚪ **2× P3**

**P0 blockers:** 🔴 **C3, C1** (silent corruption), 🔴 **L1** (no liveness loop), 🔴 **S2** (head-of-line handshake)

### RyanJHamby · 2026-09-18

Looked into L1. Push mode's watchdog (`push_scheduler.py`, `build_connector_meta`) is a one-shot, non-renewable deadline per D-side registration — it currently defaults `push_registration_timeout` to `decoder_kv_blocks_ttl` (480s), which is really a different knob (the bidirectional multi-turn cache TTL), reused here for lack of a dedicated mechanism. And when it does expire, the code only drops local scheduler bookkeeping (`_push_registration_deadlines`/`_push_pending_registrations`) and logs a warning — it doesn't fail the request itself; the comment there says *"the engine layer will eventually time it out via the lease,"* which as far as I can tell doesn't actually happen for a registration that never got a P-side match.

Pull mode already solved exactly this class of problem — the heartbeat-based lease renewal in `docs/design/nixl_kv_cache_lease.md` (#41383): D sends periodic heartbeats (~5s) that extend a short (~30s) lease on P, so a dead/crashed D gets reclaimed in seconds instead of waiting out a long fixed timeout, while a merely-overloaded D stays alive as long as it keeps heartbeating.

Proposing to port that mechanism to push mode rather than design something new: reuse the existing heartbeat plumbing (push mode already calls `_stop_heartbeat` on request completion, so some of this wiring exists) to keep P-side registrations alive under a renewable lease instead of a static deadline, and make the watchdog's actual expiry path terminate the request through the normal failure path instead of just clearing local state.

Happy to scope this into 2-3 PRs (heartbeat wiring on the D side, watchdog failure-path fix on P, tests) if that direction is right — let me know if I'm missing context on why push mode didn't just reuse the pull-mode mechanism directly.


### Pinoeer-kingxi · 2026-09-24

Hi @NickLucche, I’d like to take **W3 — safe shutdown of in-flight Push WRITEs**, if this item is still available.

On current main, `NixlPushConnectorWorker.shutdown()` calls `join(timeout=2)`, then releases tracked transfer handles and invokes base cleanup without confirming that the writer has exited or draining the submitted WRITEs. I would build on the existing EngineCore/Scheduler request-draining mechanism rather than introduce another one.

My proposed scope is:

```
1. **Make the transition to cleanup race-free.** Coordinate the writer and outstanding handshake callbacks so they cannot submit new work or access resources after final cleanup begins. This also needs to cover WRITEs already submitted but not yet published to `_sending_transfers`.
2. **Drain submitted WRITEs before releasing their resources.** Reuse the existing completion and release-failure handling, preserve completion notifications, and make cleanup idempotent. A timeout or failed release must not be treated as proof that the backend has stopped accessing memory.
3. **Respect the existing shutdown lifecycle.** Keep graceful draining distinct from abort/forced exit, with only the necessary changes to connect the worker cleanup to the existing shutdown budget. I do not plan to add background cleanup threads, a separate timeout option, or new retry/lease protocols.
```

I’ll first add deterministic regressions for submission/teardown races, late callbacks, delayed completion, release failure, and repeated shutdown. I have **8× RTX A6000** for single-host P/D and supported TP validation, checking both resource-release ordering and decode-side completion.

Before implementing the timeout path, could you clarify how W3 should coordinate `--shutdown-timeout` with the worker termination grace period? I’ll post the reproduction and focused design here before opening the implementation PR.
