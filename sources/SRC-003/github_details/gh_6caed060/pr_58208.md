# [PR #58208] [ROCm][Perf] Replace torch.topk in DSA candidate block selection

## 正文

## Summary

`select_candidate_blocks` picks the top-k blocks per row with `torch.topk`, which runs a multi-pass radix select (`computeBlockDigitCounts`, `computeBlockwiseWithinKCounts`, `gatherTopK`). That does two things this caller does not need:

```
- **It orders the results.** The only consumer is `_candidate_flags_kernel`, which does `flags[block] = 1`. Nothing downstream reads the ranking or the scores — only the *set* of selected block ids matters.
- **It scans the whole padded workspace.** The logits workspace is padded to `max_model_len`, so `nblocks` is `max_model_len / block_size` no matter how short the context is. Past a row's end every block scores `-inf` and can never win a slot, but `torch.topk` has no way to express a per-row extent, so it reads all of it.
```

This PR replaces that select on ROCm with a Triton kernel:

- Each score and its index are packed into one order-preserving `int64` key, so `tl.topk` returns both at once and the separate `_store_candidates_kernel` pass disappears. The float bits are sign-transformed so IEEE order becomes unsigned order, and the index rides inverted in the low bits so ties resolve to the smaller index, matching `torch.topk`.
- Each row is bounded by its own `end`, which is the part `torch.topk` cannot do. At 4K context in a 256K workspace this skips ~98% of the columns.
- Decode rows are `batch * next_n`, only 1–640, which is too few to fill the GPU one program per row. Rows are split across programs and merged, with the split size computed **on device** from each row's live extent — a host-side bound would need a sync, and sizing from the padded width instead measured 6.3x → 2.0x at low concurrency.

**The CUDA path is unchanged**; the new kernel is behind `current_platform.is_rocm()`.

## Not a duplicate

Checked open PRs touching this area:

```
- **#57858** is the only other open PR touching `candidate_blocks.py`, but it optimizes **prefill consumer-layer scoring** (`candidate_mqa_logits`, scoring only candidate columns). The producer-side block select this PR rewrites is untouched there. The two are complementary. Note #57858 also flips `_store_candidates_kernel`'s NaN handling (`!=` → `>`); the ROCm path here bypasses that kernel entirely, so the behaviors do not collide.
- **#48726** (LiteTopk) is the indexer's *token* top-k, a different kernel and stage.
- **#50470**, **#46172**, **#56944** touch `rocm_aiter_mla_sparse.py` only (AITER dispatch, indexer optimization, prefill row sharding), not block candidate selection.
```

No open PR optimizes `select_candidate_blocks`.

## Correctness

The new path must select the same block *set* as the existing path. Verified against the unchanged path across 27 configurations — contexts 512 to 262144, rows 1 to 640, ragged per-row ends, non-zero `row_ks` starts, `row_repeat` decode grouping, `topk_blocks > nblocks`, and NaN scores:

```
27 cases, 0 mismatches
```

Two cases this caught during development, both now handled:

- `torch.topk` ranks NaN *highest*, and `_block_scores_kernel` can emit NaN during warmup, so keys force NaN above `+inf`.
- When `nblocks < topk_blocks` the internal `K_PAD` shrinks below the output width, leaving tail columns unwritten; they are now `-1` filled.

## Kernel performance (MI355X)

Full `select_candidate_blocks`, CUDA-graph timed, swept over the decode shape space: concurrency 1–128 x spec-decode depth 1–5, `max_model_len=262144`, `block_size=8`, `k=64`. All 120 points are faster.

| context | median | range |
| --- | --- | --- |
| 4096 | 4.16x | 3.97–5.08x |
| 16384 | 3.99x | 3.27–4.70x |
| 65536 | 2.94x | 1.64–3.15x |

Representative points (microseconds):

| context | conc | next_n | rows | before | after | speedup |
| --- | --- | --- | --- | --- | --- | --- |
| 4096 | 1 | 1 | 1 | 47.55 | 11.20 | 4.24x |
| 4096 | 32 | 1 | 32 | 58.00 | 13.96 | 4.16x |
| 4096 | 128 | 5 | 640 | 293.54 | 67.86 | 4.33x |
| 16384 | 32 | 1 | 32 | 59.19 | 14.31 | 4.14x |
| 16384 | 128 | 5 | 640 | 299.65 | 91.67 | 3.27x |
| 65536 | 32 | 1 | 32 | 60.31 | 19.30 | 3.13x |
| 65536 | 128 | 5 | 640 | 330.51 | 185.83 | 1.78x |

These shapes are TP-independent: the DSA indexer is replicated across ranks (`index_n_heads` is not divided by `tp_size`, unlike the main attention heads), so TP2 and TP4 run identical selections and one sweep covers both.

## Notes

The kernel is still well above the bandwidth roofline (~45x at the largest shapes, more at small ones where it is latency-bound on two launches), so there is headroom left. `TILE=512` is a compromise: 1024 would take 65536-context from 2.36x to 2.79x but drop 4096-context from 23.8x to 14.4x. A context-aware tile choice could get both.

Benchmarks used uniform context per batch; heavily ragged batches are bounded by their longest row.

## End-to-end serving

Measured on MI355X TP4, DeepSeek-V4.1-Flash, dspark MTP (5 speculative tokens, acceptance pinned at 3.51 so acceptance variance cannot contribute). Both arms are the **same build** differing only by an env toggle on the selection path, run concurrently on separate 4-GPU sets, after a warmup pass over every shape so Triton JIT and graph capture are paid before measurement.

**There is no measurable end-to-end difference, and none should be expected.** Output throughput, ISL 4096 / OSL 128:

| concurrency | baseline tok/s | this PR tok/s |
| --- | --- | --- |
| 1 | 259.4 | 257.1 |
| 8 | 1287.7 | 1282.4 |
| 32 | 1068.9 | 1070.3 |
| 128 | 1253.8 | 1254.8 |

Repeating a single configuration three times shows run-to-run spread of 1112–1191 tok/s on baseline and 1142–1166 on this branch, with the sign of the difference flipping between repeats. The noise floor is several percent, while the expected effect is about 0.2%: the selection saves roughly 45 us per step against a 14.6 ms inter-token latency. The kernel win is real but it is a sub-1% slice of step time, so it cannot show up above noise in serving throughput.

Median ITL, the most stable metric here, is unchanged (14.59-14.64 ms baseline vs 14.61-14.73 ms this branch).

This PR should therefore be read as removing a hotspot that is prominent in kernel traces and cutting its cost 2-5x, not as an end-to-end throughput win.
