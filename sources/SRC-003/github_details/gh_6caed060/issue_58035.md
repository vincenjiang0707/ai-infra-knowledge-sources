# [Issue #58035] [Bug]: DiffusionGemma: tensor shape mismatch in post_norm under concurrent decode (inputs_embeds vs silently-clamped sc_embeds)

source: https://github.com/vllm-project/vllm/issues/58035
state: open | updated: 2026-09-22T15:50:19Z
labels: quantization

## 正文

### Summary

Both the NVFP4 and bf16 checkpoints of DiffusionGemma-26B-A4B crash the vLLM engine under concurrent request load, with the identical error:

```
RuntimeError: The size of tensor a (257) must match the size of tensor b (256) at non-singleton dimension 0
```

raised from `self.post_norm(inputs_embeds + sc_signal)` in `DiffusionGemmaSelfConditioning.forward()`. This kills the engine core process (`EngineDeadError` propagates to the API layer). It is **not deterministic at any fixed concurrency level** — across 4 independent runs (2 per checkpoint) it triggered at 4, 6, 6, and 16 concurrent users respectively, and never at 2 concurrent users.

This looks related to #50699 (same file, same "concurrent decode" trigger condition) but is a distinct bug — it reproduces at `--max-num-seqs 4`, well below the concurrency level where that issue's OOM appears, and the failure mode is a shape mismatch, not OOM.

### Root cause (traced to source)

Pulled `vllm/model_executor/models/diffusion_gemma.py` from the `vllm/vllm-openai:v0.25.1` image. The crash site is `DiffusionGemmaModelState._apply_self_conditioning`:

```python
for slot, idx in zip(decode_slots_np.tolist(), decode_idx_np.tolist()):
    start = int(query_start_loc_np[idx])
    end = int(query_start_loc_np[idx + 1])
    canvas = slice(start, end)
    soft = sc_embeds[slot, : end - start]
    inputs_embeds[canvas] = self.model.self_conditioning(
        inputs_embeds[canvas], soft.to(inputs_embeds.dtype)
    )
```

```
- `inputs_embeds[canvas]` slices from `_inputs_embeds_buf`, a large batch-wide buffer — `inputs_embeds[start:end]` with `end - start = 257` legitimately returns 257 rows.
- `soft = sc_embeds[slot, :end - start]` slices from `self.diffusion_states.self_conditioning_embeds`, a **fixed-size per-slot buffer** shaped `[max_num_reqs, canvas_length, hidden_size]` where `canvas_length=256` for this checkpoint. PyTorch tensor slicing past the end of a dimension does not raise — it silently clamps. `sc_embeds[slot, :257]` on a 256-length dim quietly returns 256 rows.
```

Net effect: `inputs_embeds[canvas]` has 257 rows, `soft` is silently clamped to 256, both get passed into `self_conditioning.forward()` → `post_norm(inputs_embeds + sc_signal)` → shape mismatch, every time, with exactly these numbers.

**Open question**: why `end - start` (from `query_start_loc_np`, vLLM's scheduler output) is 257 instead of ≤ `canvas_length` for some request in some batches — that span computation lives in the scheduler, outside this file, and I haven't traced it further. This would explain why it only appears under concurrent/continuous-batched decode and never at single-request concurrency.

### HritickGokul · 2026-09-22

@angeloambrose This looks like the same scheduler issue that was fixed in #47464 and tracked in #49495.

The scheduler could turn a one-token prefix-cache remainder into a 257-token span, while `DiffusionGemma`’s self-conditioning buffer only has room for 256 tokens. That explains the exact shape mismatch you’re seeing.

The fix is already on main, but it wasn’t included in v0.25.1. Could you try a recent build from main or another build containing #47464? It should address both the NVFP4 and BF16 cases.
