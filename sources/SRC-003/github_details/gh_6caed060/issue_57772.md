## 正文

### 🚀 The feature, motivation and pitch

A mega-MoE expert path for SM90 (H100/H20) DeepSeek-V4 / V4.1-Flash.

The RFC #42284 mega-MoE work landed, but both new paths are gated away from Hopper, so DeepSeek-V4/V4.1 on SM90 still falls back to weight-only Marlin — which dequantizes MXFP4 to bf16 and leaves the fp8 tensor cores idle. A SM90 mega-MoE (fp8-only) variant would directly address the main throughput bottleneck on the most common Hopper serving fleet.

What is gated away on SM90:

```
- `deep_gemm_mega_moe` (native): `DeepGEMM MegaMoE requires SM100 GPUs` (`vllm/models/deepseek_v4/nvidia/model.py`, `DeepseekV4MegaMoEExperts`) — the kernel consumes fp4 tensor cores.
- `flashinfer_moe_ep_mega_*`: requires an NVFP4-quantized checkpoint (fp8-e4m3 per-16 block scales + per-tensor `weight_scale_2`); MXFP4 checkpoints are rejected with "deep_gemm consumes the MXFP4 checkpoint instead".
```

So on SM90 there is no fused/quantized-MMA MoE option at all for the V4 family: only the weight-only Marlin/MXFP4 fixed-block kernel.

### Alternatives

1. An SM90 mega-MoE variant (fp8 weights/MMA, no fp4 tensor cores — e.g. via DeepGEMM fp8 grouped GEMM with the same fused dispatch→Linear1→Act→Linear2→combine structure).
2. Extending the flashinfer moe_ep path to accept MXFP4 checkpoints on Hopper.
3. Status quo: stay on Marlin. Config-level tuning is a dead end — `VLLM_TUNED_CONFIG_FOLDER` triton MoE configs are ineffective for this model (it does not go through the triton fused_moe path), so Marlin is the ceiling unless a new kernel path exists.

### Additional context

Measured on 8×H20 (TP8, MXFP4 checkpoint, zero offload): conc64 / mt=256 **2434 tok/s**; conc256 short-output **~3300 tok/s**; 128K cold prefill 17.3 s (0 errors, unique-marker bench). DeepSeek-V4.1-Flash is 510 GB / 48 shards; 8×H20 fits it entirely in VRAM, so the fleet this targets is exactly Hopper.

Happy to benchmark any WIP branch on 8×H20 and share numbers.

Related to #49977 (native SM90 W4AFP8 grouped MoE) and #53709 (opt-in MXFP4→block-FP8 expert dequant, DeepSeek-**V4**, prefill-only numbers).

We deployed the same core idea on **V4.1-Flash** and can add full serving-side data, which #53709 does not cover.

**How ours differs from #53709**

```
- Model: `DeepSeek-V4.1-Flash` (V4.1 path, not V4)
- Conversion is offline + a custom `--load-format` plugin, not in-engine load-time conversion
- Data is full serving throughput plus device counters, not single-request prefill TTFT
```

**Environment**

```json
- 2 nodes × 8× NVIDIA H20 96GB (Hopper / SM90), Alibaba Cloud ACK
- vLLM `0.1.dev20904+g179dd0fa9`, torch 2.13.0+cu130 (CUDA 13.0), driver 595.58.03
- Topology: TP8 + DP2 + EP16 (cross-node)
- `--moe-backend deep_gemm --load-format fp8_overlay --kv-cache-dtype fp8 --block-size 64 --max-model-len 1048576 --max-num-seqs 256 --max-num-batched-tokens 8192 --gpu-memory-utilization 0.93`
- `--speculative-config '{"method":"dspark","num_speculative_tokens":5,...}'`
- `--enable-eplb --eplb-config '{"window_size":1000,"step_interval":1000,"num_redundant_experts":64,...}'`
```

**What we did instead of staying on Marlin**

The MXFP4 routed-expert weights are re-encoded to FP8 (E4M3) offline and loaded through a custom `--load-format` plugin, so the routed-expert GEMMs run on FP8 tensor cores instead of dequantizing to BF16 on every step. This is effectively your alternative 1, weight-side only.

**Measured serving throughput** (text prompts)

| concurrency | 1 | 8 | 32 | 64 | 128 |
|---|---:|---:|---:|---:|---:|
| output tok/s | 73.1 | 337.9 | 923.5 | 1520.1 | 2264.2 |

**Device counters under load — the part I think is most informative**

- `utilization.gpu` saturates at 99%
- `utilization.memory` stays at **14–19%**
- board power only rises **270 → 287 W** against an H20 cap of ~500 W

The device reports "busy" while neither HBM bandwidth nor power is anywhere near saturation. That is consistent with the MoE path being latency/launch-bound rather than MMA-bound — which is exactly the gap your alternative 1 would close.

**Two caveats, so the numbers are not over-read**

```
1. **Not directly comparable to your Marlin baseline.** Our cross-node EP communication is on the NCCL all-gather/reduce-scatter backend (`--all2all-backend allgather_reducescatter`), not DeepEP. DeepEP's low-latency path is unavailable on our fleet: the NICs are Alibaba eRDMA and NVSHMEM's IBGDA transport is mlx5-only (reported separately on the DeepEP repo). The FP8 GEMM gain is therefore partly masked by an unoptimized EP communication path.
2. **This addresses weight format only.** It does not deliver a fused mega-MoE; the dispatch/combine seam is still materialized. On SM90 that seam is exactly what alternative 1 would remove.
```

We can share the conversion script and the weight-layout expectations, and we are happy to benchmark any WIP SM90 fp8 path on this fleet.

### luoyuctl · 2026-09-23

Thanks for asking. The checkpoint used in our serving run is FP8 with `weight_block_size: [128, 128]` and `expert_dtype: fp8`, as declared in its `config.json`.

DeepSeek’s official [`inference/convert.py`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/inference/convert.py) also supports `--expert-dtype fp8`, but it uses 32×32 FP8 blocks with E8M0 scales and emits shards for DeepSeek’s reference inference runtime. That differs from the 128×128 layout used in our vLLM run.

Our throughput results were measured on 2 nodes × 8 H20 with TP8/DP2/EP16, so they aren’t directly comparable to a single-node TP8 setup.
