### 🚀 The feature, motivation and pitch

Hi vLLM team,

First, thanks for the amazing work on vLLM—it's been a game-changer for high-performance LLM serving! I'm writing to request a feature addition that would greatly benefit users with diverse hardware setups: support for INT8 quantization in KV Cache, alongside the existing FP8 implementation.

Current Behavior
As of vLLM version 0.4.0 (and confirmed in latest main branch), KV Cache quantization only supports FP8 (e.g., via quantization="fp8" in LLMEngine). While FP8 offers advantages for newer hardware (like NVIDIA H100), it lacks compatibility with older or mainstream GPUs (e.g., A100, RTX 4090, or cloud instances like AWS g5), which either don't support FP8 natively or incur significant overhead when emulating it.

Why INT8 Support is Needed
Hardware Accessibility:
FP8 requires SM9.0+ GPUs (H100+), but many production environments still use A100 (SM8.0) or consumer-grade cards. INT8 is universally supported across all modern NVIDIA GPUs (since Pascal architecture) and avoids FP8 emulation penalties.
Example: On an A100, forcing FP8 for KV Cache may degrade performance by 10–20% due to software emulation, while INT8 would run natively via Tensor Cores.
Memory Efficiency:
INT8 KV Cache reduces memory footprint by ~50% compared to FP16 (and similar to FP8), enabling larger batch sizes or longer context windows on memory-constrained devices. For instance:
FP16 KV Cache: 2 bytes/element
FP8/INT8 KV Cache: 1 byte/element
Unlike FP8, INT8 quantization is more mature and stable for asymmetric ranges (common in KV Cache activations), with proven results in frameworks like Hugging Face Transformers (quantize_kv_cache=True in model.generate()).
Use Case Demand:
Many users (myself included) deploy vLLM on cost-effective cloud instances (e.g., AWS p4d) where FP8 isn't viable. INT8 support would unlock wider adoption without sacrificing latency/throughput.

### EricccYang · 2026-02-10

@drshvik @Wiziechen @yewentao256  


Hello everyone,

This week I attempted to implement int8 KV cache dtype for the FLASHINFER FI backend and here are my findings:

Performance Consideration on Ampere Architecture
In the FLASHINFER backend, FP8 KV cache is utilized by first converting it to FP16/BF16, then performing FMA operations with the query tensor (typically BF16) in Tensor Cores. This means the computational speed remains the same as using the query dtype for both operands.
Although int8 computation in Tensor Cores is theoretically 2x faster than BF16, this requires both the query and KV cache to be in 8-bit dtype, which is not the scenario we are addressing.
Therefore, on Ampere architecture, int8 KV cache is unlikely to outperform FP8 in terms of performance. Regarding compatibility, FP8 KV cache can still function on Ampere GPUs because we are only storing data in FP8 format, not performing computations in FP8.
Decode stage utilizing  low bits kvcache also include type conversion,  though it is not performed on tensor cores. So  in theory INT8 will not be better than FP8.
(Reference: [FLASHINFER Vector Types and CUDA Primitives](https://deepwiki.com/flashinfer-ai/flashinfer/3.1-vector-types-and-cuda-primitives))
The compute_qk function uses mma_sync_m16n16k16_row_col_f16f16f32 or mma_sync_m16n16k16_row_col_f16f16f16 for matrix multiplication. For FP8 KV cache, it includes type conversion steps.
(Code reference: [FLASHINFER Prefill CUDA Kernel](https://github.com/flashinfer-ai/flashinfer/blob/64094534/include/flashinfer/attention/prefill.cuh#L637-L648))

Benchmark Results with Dequantization
I attempted to use the FI backend by dequantizing int8 KV cache to the query dtype before calling the FLASHINFER API. The performance was similar or slightly worse compared to using the query dtype for KV cache.
Test environment: A100-PCIE-40G
Command:
vllm bench latency --model ../Qwen3-4B/ --batch-size 8 --input-len 512 --output-len 1000 --max_model_len 2000 --num-iters 1 --gpu-memory-utilization 0.95 --num-iters-warmup 1 --attention-backend FLASHINFER --kv-cache-dtype int8
--kv-cache-dtype int8: 120 seconds
--kv-cache-dtype auto: 110 seconds
I used a Triton kernel for dequantization, which may not be optimal, but I believe dequantizing before the actual attention kernel (especially during decoding) is not an efficient approach. This indicates that FLASHINFER and FLASH_ATTN backends are inherently challenging to adapt for int8 KV cache support, as neither library currently natively supports int8 KV cache—dequantization before use is mandatory.
Therefore, it appears that  for vLLM TRITON_ATTN is currently the only backend capable of supporting int8 KV cache dtype (sglang could use different decode and prefill backend in one batch, uses TRITON_ATTN for decoding and a dequantization-before-use approach for prefill).
I am currentlly working on TRITON_ATTN to support int8. 

I not 100% sure about these and  would like to hear some advice before next step.

### jagmarques · 2026-04-07

The hardware accessibility argument is the right framing here. To add some technical context on why INT8 KV cache is genuinely different from FP8 (not just a fallback):

```
**Precision vs. storage format**: For KV cache, what matters is reconstruction accuracy per bit, not floating-point arithmetic compliance. INT8 with per-channel or per-token scaling is a well-understood quantization scheme that can match or beat FP8 in practice because:
- INT8 has a uniform step size (good for normally-distributed activations post-LayerNorm)
- FP8 has non-uniform density (better for log-scale distributions like weights, but KV activations are closer to normal)
```

In terms of quantization error on KV tensors specifically, INT8 with per-token `absmax` scaling is competitive with FP8 E4M3 at the same 8-bit budget. The choice is really about hardware, not accuracy.

**Practical path forward**: The main implementation work is adding an INT8 dequant kernel in the attention CUDA path. The attention kernel reads KV blocks, dequantizes them (scales stored per block), then runs softmax + weighted sum. For INT8, this is simpler to implement than FP8 because there's no exponent bit handling — it's just `float32(int8_val) * scale_factor`.

For A100/A5000/consumer GPU users who can't use FP8 natively, INT8 KV cache gets you 2× memory reduction (vs BF16) on supported hardware with ~0.1–0.3% PPL cost at 8-bit for most 7B–70B models. That's a meaningful improvement for running longer context on fixed VRAM.

If someone wants to implement this, the cleanest entry point is probably modeling it on the existing FP8 KV cache path and replacing the dequant op. The block size and layout can stay identical.

### oladri-renuka · 2026-08-22

Following up on the int8_per_token_head question above — ran a small evaluation comparing auto / fp8 (calibrated) / int8_per_token_head on Qwen2.5-7B-Instruct across 100 math reasoning problems (AIME 2025 + GSM8K), scoring not just accuracy but how the model fails (using a taxonomy from our prior work on quantized reasoning failures).
Summary:
int8_per_token_head: 73% accuracy, closely tracks unquantized baseline (also 73%) on both accuracy and failure patterns
fp8 with calculate_kv_scales=True: 3% accuracy. The vast majority of failures aren't subtle reasoning errors, it's near-total generation collapse (repeated tokens, incoherent output)
For what it's worth, on the reasoning-quality axis specifically, int8_per_token_head held up notably better than FP8 in my tests, relevant to the "int8 has no advantage over fp8" point raised earlier in this thread. @jagmarques's point above about INT8's uniform step size being a better match for KV activation distributions lines up with what I'm seeing empirically here, at least for this model/workload.
Full writeup, raw transcripts, and reproduction scripts here: [https://github.com/oladri-renuka/vllm-kvcache-quant-reasoning-eval](https://github.com/oladri-renuka/vllm-kvcache-quant-reasoning-eval)

Thanks for the flag, good to know. Found a related bug report (#21640) showing calculate_kv_scales=True causing compilation issues on Qwen models, which tracks with what you're describing. My FP8 number may reflect that known issue rather than telling us much about FP8 KV-cache quantization generally, worth treating as unverified for now.  Re-ran `fp8` without the flag (default, uncalibrated scale=1.0) on the same 100-question dataset to isolate the flag from FP8 itself:

| Condition | Accuracy | Reasoning Quality |
|---|---|---|
| Baseline (auto) | 73% | 88% NO_FAILURE, 9% HC, 11% SC |
| **FP8, uncalibrated** | **51%** | 1% NO_FAILURE, **50% HC, 46% SC** |

| int8_per_token_head | 73% | 64% NO_FAILURE, 9% HC, 16% SC |

**Key finding:** The flag causes generation collapse (garbage output). Without it, FP8 still degrades reasoning (51% accuracy, 96% of errors are genuine reasoning failures — Hollow Convergence + Shortcut Collapse), but it's fluent-but-wrong reasoning, not gibberish. `int8_per_token_head` remains unaffected across all conditions.
