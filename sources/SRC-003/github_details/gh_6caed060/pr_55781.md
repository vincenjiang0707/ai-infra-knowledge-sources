## 正文

## Purpose

Add bounded-label telemetry for **logical frontend weight operations** in both frontends.

```text
HTTP request
    -> input validation            (outside the recorder)
    -> 0..N logical weight operations
    -> record: outcome / duration / concurrency
```

One request maps to zero or more operations:

| Endpoint | operation |
| --- | --- |
| `/init_weight_transfer_engine` | `init` |
| `/start_weight_update` | `start` |
| `/start_draft_weight_update` | `start_draft` |
| `/update_weights` | `update` |
| `/finish_weight_update` | `finish` (+ `set_version` when a `weight_version` is supplied) |
| `/update_weight_version` | `set_version` |

## Metrics

| Metric | Type | Labels |
| --- | --- | --- |
| `vllm:rl_weight_update_operations_total` | Counter | `operation`, `status` (`success`/`error`) |
| `vllm:rl_weight_update_operation_duration_seconds` | Histogram | `operation` |
| `vllm:rl_weight_update_operations_in_flight` | Gauge | `operation` |

- Shared buckets: `0.01, 0.1, 1, 10, 30, 60, 120, 300, 600` seconds.
- Names say `operations`, not `requests`: do **not** sum across the `operation` label, since `update` is per weight chunk while the others are lifecycle events.
- Python and Rust expose the same names, labels, status values and buckets. The Rust counter family is registered without a `_total` suffix because `prometheus-client` appends it when encoding.

## Semantics

- **`finish` covers only `engine.finish_weight_update()`.** The weight-version handshake is counted separately as `set_version` on both frontends, so
  ```text
  /finish_weight_update {"weight_version": "B"}
      finish{success} +1
      set_version{error} +1      (version handshake failed)
      HTTP 500
  ```
  is a valid, meaningful outcome; the failure is attributed to the version handshake instead of being flattened into `finish=error`.
- **A clean exit is `success`; anything else is `error`**, including an engine exception, an `HTTPException` and a cancellation/client disconnect (`asyncio.CancelledError` in Python, a dropped future in Rust). The in-flight gauge is released on every path.
- **Invalid input never enters the recorder.** The accepted/rejected *JSON payload shapes* are the same on both frontends:
  ```text
  top-level body : JSON object
  init_info      : JSON object only
  update_info    : JSON object, or list of JSON objects (an empty list is accepted
                   on both sides: all([]) is true, as is iter().all(...))
  ```
  Invalid shapes (including a non-object top-level body) return 400 with the engine untouched and no counter, histogram or gauge movement. Endpoint-level 4xx is already covered by the HTTP metrics.

  Scope note: this is **payload shape** agreement only. The Rust `Json<T>` extractor additionally rejects a mismatched `Content-Type`; Python keeps accepting it exactly as before, deliberately, because changing that would be an API compatibility change outside this PR.

## Implementation notes

- Python: `WeightOperationMetrics.record()` is a context manager; the status starts as `error` and flips to `success` only after a clean exit, and the gauge is released in `finally`.
- Rust: `record_weight_operation()` returns an RAII recorder; `success()` consumes it, `Drop` without success records `error`, and `complete()` is idempotent.
- Collectors are created **lazily, on first use**, on the process default registry. That is the `prometheus_client` contract for multiprocess mode: values become mmap-backed and the `/metrics` scrape registry aggregates them through `MultiProcessCollector`. Lazy creation exists so metric objects are instantiated only after multiprocess Prometheus setup has run (`PROMETHEUS_MULTIPROC_DIR` must be set before a metric object exists).

## Not in scope

- whole transfer-session duration; RL transaction/lifecycle state; weight-version labels; weight correctness verification;
- `PrometheusStatLogger` ownership (separate bugfix, `pr-55781-ownership-fix`);
- HTTP `Content-Type` validation parity;
- `/abort_requests` robustness: it is untouched by this PR and retains its original body parsing.

## Semantics revision pushed: `requests` -> `operations`, and correct multiprocess registry usage

Latest head: `cf3ee740b8`. The PR now describes **logical frontend weight operations** everywhere (names, help text, docstrings, comments) instead of HTTP requests, and the metric creation registry follows the `prometheus_client` multiprocess contract.

### Renames

| Before | After |
| --- | --- |
| `vllm:rl_weight_update_requests_total` | `vllm:rl_weight_update_operations_total` |
| `vllm:rl_weight_update_request_duration_seconds` | `vllm:rl_weight_update_operation_duration_seconds` |
| `vllm:rl_weight_update_requests_in_flight` | `vllm:rl_weight_update_operations_in_flight` |

The names now say `operations` because one HTTP request maps to zero or more of them (`/finish_weight_update` with a version records `finish` **and** `set_version`). The help text states this, and the PR body documents that summing across the `operation` label is not meaningful: `update` is per weight chunk while `finish`/`set_version`/`init`/`start`/`start_draft` are lifecycle events. So `sum(..._operations_total)` is not "number of weight updates" - query per operation instead.

### Registry usage

The recorder is no longer created with `get_prometheus_registry()` as its creation registry. In multiprocess mode that returns a `CollectorRegistry` whose purpose is scrape/aggregation (`MultiProcessCollector`), not metric creation. The collector is now created on the process default registry with no `registry=` argument, which is what `prometheus_client` expects: the values become mmap-backed and the `/metrics` scrape registry aggregates them. The lazy singleton stays, but its stated purpose is now "metric objects are instantiated after multiprocess Prometheus setup has occurred" rather than "bind to the registry returned to `/metrics`".

### New real multiprocess regression test

`tests/entrypoints/unit_tests/test_rl_weight_operation_multiprocess.py` uses real child processes and a real `PROMETHEUS_MULTIPROC_DIR` (skipped on Windows, where the mmap files are locked):

- two processes each completing one operation: `operations_total == 2`, `operation_duration_seconds_count == 2`;
- two processes each holding one operation open: `operations_in_flight == 2`, which is what actually validates `multiprocess_mode="livesum"`;
- different `operation` labels stay separate across processes;
- `mark_process_dead` clears a dead process's stale in-flight gauge while a live process is unaffected;
- a subprocess asserts the module import creates no collectors and that the counter/histogram/livesum mmap files appear only after first use.

The old test that mocked `get_prometheus_registry()` and asserted registration into the mock registry is gone - it did not test multiprocess behaviour, and `test_metrics_are_created_lazily` now covers the lazy contract directly.

### 2. Top-level JSON shape validation

Confirmed the gap: a valid JSON scalar or array parsed fine and then hit `body.get(...)`, i.e. `AttributeError` → 500 instead of 400, whereas Rust rejects it at the `Json<T>` extractor. Fixed with a shared helper used by both routes:

```python
async def _json_object_body(raw_request: Request) -> dict:
    try:
        body = await raw_request.json()
    except json.JSONDecodeError as e:
        raise HTTPException(status_code=400, detail="Invalid JSON format") from e
    if not isinstance(body, dict):
        raise HTTPException(status_code=400,
                            detail=f"Request body must be a JSON object, got {_summarize_type(body)}")
    return body
```

I applied it to `/abort_requests` as well, which had the identical latent bug (`[]` → `AttributeError` → 500) and is not recorder-related, so it is a plain robustness fix.

New matrix (each → 400, engine never called, no counter/gauge/histogram movement): `1`, `[]`, `"x"`, `null`, `true` for both `/init_weight_transfer_engine` and `/update_weights`.
