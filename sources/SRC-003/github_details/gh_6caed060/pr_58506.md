# [PR #58506] [Kernel] Avoid redundant SM100 blockwise FP8 scale padding

## 正文



## Purpose

The SM100 blockwise FP8 GEMM requires the leading dimension of its
column-major activation scales to be divisible by four for TMA scale-factor
copies.

The current implementation handles a non-aligned `M > 64` by allocating a
temporary padded scale tensor and issuing a `cudaMemcpy2DAsync` before every
GEMM. This is correct and significantly faster than falling back to the
`swapAB` kernel, but the allocation and copy are unnecessary when vLLM owns
the activation quantization step.

This PR makes the vLLM CUTLASS block-FP8 path produce TMA-aligned activation
scales directly during quantization. The GEMM then derives the physical scale
extent from `a_scales.stride(1)` and consumes the aligned tensor without an
additional allocation or copy.

The change preserves compatibility with direct custom-op callers:

- TMA-aligned scales use the zero-allocation, zero-copy fast path.
- Packed, non-aligned scales retain the existing temporary-padding fallback.
- The existing `M <= 64` `swapAB` heuristic is unchanged.
- There is no public API change.

The persistent storage overhead is at most three FP32 scale entries per
`K / 128` scale column, while the per-GEMM temporary allocation is removed
from the normal vLLM path.

### Lossless behavior

This is a physical-layout optimization only. It does not change the logical
scale values, FP8 quantization, kernel math, accumulation type, or output
type.

Packed and aligned paths were compared with `torch.equal` for
`M = 13, 64, 65, 66, 67, 125, 511, 1026, 2047`:

| Comparison | Result | Maximum absolute difference |
|---|---:|---:|
| Quantized FP8 activations | Bitwise identical | 0 |
| Logical FP32 scales | Bitwise identical | 0 |
| GEMM-only BF16 output | Bitwise identical | 0 |
| Quantization + GEMM BF16 output | Bitwise identical | 0 |

The separately reported 0.11%-0.15% relative error is the expected error of
the FP8/BF16 result relative to an FP32 dequantized reference. Both the packed
baseline and aligned fast path have the same error and are bitwise identical
to each other.

## Test Plan

1. Rebuild the stable-ABI CUDA extension with the SM100 CUTLASS kernels.
2. Run focused correctness tests for both scale layouts across:
   - the `M = 64/65` dispatch boundary;
   - all non-zero `M % 4` residue classes;
   - tiny, medium, and multi-scale-atom `M` values;
   - a non-128-aligned weight dimension.
3. Compare packed and aligned quantization outputs and GEMM outputs bitwise.
4. Benchmark both paths after five warmup iterations:
   - GEMM-only: reuse the output tensor to isolate scale-padding overhead;
   - end-to-end: include activation quantization, tensor allocation, and GEMM.
5. Run the repository pre-commit hooks on all modified files.

Representative commands:

```bash
pytest -q \
  tests/kernels/quantization/test_block_fp8.py::test_w8a8_block_fp8_cutlass_matmul

pre-commit run --files \
  csrc/libtorch_stable/quantization/w8a8/cutlass/c3x/scaled_mm_blockwise_sm100_fp8_dispatch.cuh \
  tests/kernels/quantization/test_block_fp8.py \
  vllm/model_executor/kernels/linear/scaled_mm/cutlass.py
```

### Performance

Measured on an NVIDIA L20D. Each value is the arithmetic mean across these
five model GEMM shapes:

- `N=5120, K=4096`
```
- `N=4096, K=2048`
- `N=512, K=4096`
- `N=4096, K=256`
- `N=4608, K=4096`
```

`Speedup = packed baseline wall time / aligned fast-path wall time`; higher is
better.

| M | GEMM-only wall-time speedup | Quantization + GEMM wall-time speedup |
|---:|---:|---:|
| 65 | 1.169x | 1.149x |
| 511 | 1.171x | 1.118x |
| 2,047 | 1.128x | 1.058x |
| 8,191 | 1.065x | 1.034x |
| 63,798 | 1.027x | 1.012x |

The benefit is largest for smaller token counts, where the allocation and copy
are a significant fraction of the GEMM latency. For large compute-bound GEMMs,
the improvement converges toward 1%, while narrow `N` or `K` shapes still show
larger gains.

Selected per-shape end-to-end results:

| M | N | K | Packed wall time | Aligned wall time | Speedup |
|---:|---:|---:|---:|---:|---:|
| 65 | 5,120 | 4,096 | 0.0487 ms | 0.0429 ms | 1.136x |
| 65 | 4,096 | 2,048 | 0.0444 ms | 0.0382 ms | 1.161x |
| 65 | 512 | 4,096 | 0.0480 ms | 0.0416 ms | 1.155x |
| 65 | 4,096 | 256 | 0.0435 ms | 0.0375 ms | 1.160x |
| 63,798 | 5,120 | 4,096 | 1.7230 ms | 1.7096 ms | 1.008x |
| 63,798 | 512 | 4,096 | 0.6449 ms | 0.6341 ms | 1.017x |

No documentation update is required because this change does not alter the
public interface or supported model set.
