### 🐛 Describe the bug

With `method: ngram_gpu` + xgrammar structured outputs + `--async-scheduling`, the
target model **verifies and accepts draft tokens that the grammar forbids**. The
authoritative FSM then rejects them at commit time and the request is terminated:

```
ERROR [backend_xgrammar.py:162] Failed to advance FSM for request chatcmpl-... for tokens 2585. Please file an issue.
ERROR [scheduler.py:1654] Unexpected: grammar rejected tokens [2585] for request chatcmpl-... Terminating request.
ERROR [serving.py:173] Request chatcmpl-... failed with an internal error during generation
```

```
Observable behavior is strongly **concurrency-dependent** (single in-flight request is
clean; the async pipeline never overlaps):
```

| symptom | measurement |
|---|---|
| `/v1/chat/completions` (grammar + penalties) | **~88% HTTP 500** at concurrency 4 (bf16: 178/200; NVFP4: 87/100) |
| `/v1/completions` (token-id prompts, grammar) | zero HTTP errors but **silent truncation growing with load**: mean response chars 264 → 174 → 95 → 47 → 24 → 24 at concurrency 1 → 2 → 4 → 8 → 12 → 16; server-side mean generation length collapses ~70 → ~17.5 tokens/request |
| concurrency 1 | outputs intact (~264 chars, normal lengths) |
| drafting itself | healthy: ~67% acceptance, ≈1.9 accepted tokens/step — the speedup potential is real, which is what makes the silent-truncation mode dangerous |

## Root-cause analysis (v0.25.1 source)

```bash
Under async scheduling the engine core and the model runner end up holding **two
divergent views of the draft tokens** for a structured-output request:
```

1. In the deferred-output path, `Scheduler.update_draft_token_ids_in_output`
   (`vllm/v1/core/sched/scheduler.py`) validates drafts against the grammar
   (`grammar.validate_tokens`) and **patches invalid ones to `-1`** in
   `scheduler_output.scheduled_spec_decode_tokens`, recording the count in
   `num_invalid_spec_tokens`.
2. The bitmask builder (`StructuredOutputManager.grammar_bitmask`,
   `vllm/v1/structured_output/__init__.py`) treats a `-1` draft as "skip": it emits an
   **unconstrained bitmask row** for that position and sets `apply_bitmask = False` for
   the remainder of the window.
3. However, when ngram_gpu is used, the model runner **snapshots the *unpatched* dict**
   before the engine core patches it — `gpu_model_runner.py` (~line 4086):

   ```python
   # If ngram_gpu is used, we need to copy the scheduler_output to avoid
   # the modification has influence on the scheduler_output in engine core process.
   ```

   so verification runs against the **original raw draft tokens**, not the
   grammar-filtered ones the bitmask was built for.
4. Nothing closes the gap: `num_invalid_spec_tokens` is consumed **only** by
   `make_spec_decoding_stats` — neither `gpu_model_runner.py` nor
   `rejection_sampler.py` reference it, so grammar-invalid draft positions are **never
   force-rejected**.

```bash
Net effect: a grammar-illegal draft token is verified at an unconstrained position,
accepted by the target model (it is perfectly plausible *text*), and then rejected by
the authoritative FSM in `Scheduler.update_from_output` → `FINISHED_ERROR` (chat) or
truncated output (token-id path).
```

A second, compounding async-only mechanism: the 2-deep pipeline races draft validation
against FSM advancement (drafts can be validated against an FSM that has not yet
consumed the in-flight step's accepted tokens), which matches the observed
concurrency-dependence. This half looks adjacent to PR #44993 (merged 2026-07-23,
not yet in any release) — but #44993 is framed around reasoning parsers, and v0.25.1
already contains #44297 (the bonus-row fix for #44006), so what we hit appears to be an
**unfixed residual specific to the ngram_gpu snapshot path**.

## Reproduction

1. Serve any model with the flags above (any nontrivial EBNF/JSON-schema grammar via
   xgrammar; large prompts are not required, but a grammar whose legal-token set is
   sparse makes it trigger faster).
2. Send ≥4 concurrent `/v1/chat/completions` requests with
   `structured_outputs.grammar` set and sampling enabled.
3. Watch for `Failed to advance FSM` / `grammar rejected tokens` in the engine log;
   HTTP 500s on chat requests; or compare output lengths at concurrency 1 vs 8 on
   `/v1/completions` (silent truncation).

At concurrency 1 everything is clean, so smoke tests will not catch it.

## Workarounds verified

- `{"method": "ngram", ...}` (CPU drafter) **with `--async-scheduling` removed** is
  fully correct in our testing (100/100 requests OK, no truncation, ~65% acceptance,
  and a −31% mean e2e latency win at our production operating point). Note plain
  `ngram` + `--async-scheduling` is already rejected at startup
  ("async scheduling is only supported with EAGLE/MTP/Draft Model/NGram GPU/DSpark"),
  which is what pushes users onto the broken `ngram_gpu` path in the first place.
- Disabling speculative decoding obviously also avoids it.

With 8 concurrent structured-output requests, 100 of 107 were terminated with
"grammar rejected tokens ... Terminating request" or "Failed to advance FSM". With one
request at a time there were no failures.

The cause is the one described in #49738. `apply_grammar_bitmask` locates each request's
rows in the engine core's bitmask using the model runner's trimmed draft counts, but the
bitmask was built with the untrimmed counts (k+1 rows per request). After the first
trimmed request, every later request in the batch reads the wrong rows.

```
Using the pre-trim counts for the source offset fixed it for us: no failures at 8
concurrent, and outputs match non-speculative decoding apart from near-ties.
```
