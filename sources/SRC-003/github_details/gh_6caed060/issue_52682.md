## 正文

### Your current environment

```
- vLLM version: 0.27.1 (`vllm/vllm-openai:latest` container image)
- Model: `Qwen/Qwen3.8-27B-FP8`
- GPU: 4x NVIDIA RTX A5000 (Ampere, compute capability 8.6), `--tensor-parallel-size 4`
- Platform: bare-metal Kubernetes (MicroK8s), NVIDIA driver 595.84
```

### Model Input Dumps

```
vllm serve Qwen/Qwen3.8-27B-FP8 \
  --tensor-parallel-size 4 \
  --max-model-len 262144 \
  --kv-cache-dtype fp8 \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder
```

### 🐛 Describe the bug

Startup hangs indefinitely — no crash, no error, no further log output — shortly after model loading completes, with the above launch command on 4x RTX A5000 (Ampere). Confirmed via multiple independent attempts (30+ minutes each, manually terminated) that this is not simply slow, but a genuine stall:

- Last log lines before the hang:
  ```
  Selected MarlinFP8ScaledMMLinearKernel for Fp8LinearMethod
  Using Triton/FLA GDN prefill kernel (requested=auto, head_k_dim=128).
  Using FLASHINFER attention backend out of potential backends: ['FLASHINFER', 'TRITON_ATTN'].
  ```
  (Then nothing — no further output, ever, across 30+ minute waits.)

- **Ruled out slow Triton autotuning**: re-ran with `VLLM_TRITON_FORCE_FIRST_CONFIG=1` (skips exhaustive autotuning). The process stalled at the *exact same log line* with no measurable difference in behavior, which rules out an autotuning-search-space explanation.

```
- **Ruled out a genuine deadlock/network-handshake wait**: inspected `/proc/<pid>/wchan` for every worker process across two independent attempts:
  - One worker consistently shows sustained ~16% CPU usage, growing linearly over 25+ minutes, blocked on `futex_do_wait` (thread-pool coordination primitive) with 109 threads.
  - The other 3 workers show near-zero CPU, blocked on `hrtimer_nanosleep` (a timed poll-with-backoff loop, i.e. periodically checking a shared flag), not a blocking socket read.
```

  Neither of these is a network I/O wait — this looked initially like a plausible (if very slow) real compile/autotune in progress, but see below.

- **Fix**: adding `--enforce-eager` (disables CUDA-graph capture and `torch.compile`) allows the exact same model/config to complete `init engine (profile, create kv cache, warmup model)` in **10 seconds**, and reach a fully serving state in under 2 minutes total. Confirmed via the engine's own logged `compilation_config={'mode': <CompilationMode.NONE...}` when `--enforce-eager` is set, versus the full CUDA-graph/inductor compilation config (dozens of `cudagraph_capture_sizes`, multiple fusion passes) when it's not.

This strongly suggests the hang is in vLLM's CUDA-graph capture / `torch.compile` pipeline specifically for this model's hybrid Gated DeltaNet attention kernel (`qwen_gdn_linear_attn.py`), on Ampere (compute capability 8.6) specifically — not in the GDN kernel's own Triton JIT compile (which still runs fine under `--enforce-eager`), and not a plain autotuning slowness.

### Possibly related issues

None of these match exactly (different hardware and/or different trigger point — during inference/load rather than at startup before serving any request), but they point at the same general GDN/hybrid-attention hang/livelock problem class recurring across vLLM releases and backends:

```
- #52551 — Qwen3.6-27B (dense Gated-DeltaNet) permanently hard-wedges the V1 engine (NVIDIA, triggered by large images/long multi-turn — not startup)
- #45929 — Qwen3-Next/GDN hangs at Triton compile (ROCm RDNA4/gfx1201, closed)
- #49203 — Qwen3.6-35B-A3B (GDN hybrid) intermittently livelocks under load (NVIDIA GB10/Blackwell, not Ampere)
- #43885 — Qwen3.6-27B-FP8 spin-loop during prefill burst (NVIDIA GB10/Blackwell)
```

Given the pattern across several different Qwen GDN-hybrid models, hardware backends, and vLLM versions, it seems worth asking whether CUDA-graph capture for this kernel family has been validated on Ampere-class (compute capability < 9.0) hardware at all, or whether `--enforce-eager` should be documented as a required flag there for now.

**One silent phase worth knowing about.** On a cold cache, ~3.5 min of init is FlashInfer JIT-compiling two modules for SM8x (`sampling` and `batch_prefill_with_kv_cache_dtype_q_bf16_dtype_kv_e4m3_..._head_dim_qk_256`). Nothing is logged while this happens, and the process state looks like what you described: one rank waiting on the `ninja`/`nvcc` child, the other ranks polling FlashInfer's file lock. However, the JIT also happens with `--enforce-eager` (row 3), and you saw `--enforce-eager` start in 10 s, so I don't think this is your hang. The official image also ships these modules prebuilt in `flashinfer-jit-cache` (they contain `sm_80` SASS, which runs on SM86).

Could you retry with a current image (≥ v0.29.0)? If it still hangs, a `py-spy dump --pid <worker pid>` of each TP worker while it is stuck would pin down where it is.
