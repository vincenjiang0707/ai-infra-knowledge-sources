## Summary

Integrate DeepGEMM Mega-Gate into the DeepSeek V4/V4.1 DeepGEMM MegaMoE path, fusing the gate GEMM and expert selection. Prepare routing metadata once per model forward and reuse it across layers. Preserve hash routing for V4, image routing bias for V4.1, draft-layer expert counts, MTP warmup, and decoder auxiliary-state capture.

Two integration fixes are included:

- Let CMake FetchContent update an existing DeepGEMM checkout when its pinned revision changes. Previously, finding `csrc/python_api.cpp` skipped the update entirely and could rebuild 2.6.1 without `bf16_mega_gate` despite the new pin.

NaN padding can trigger the kernel's finite-score assertion, later surfacing as a CUDA launch failure or NCCL error. `masked_fill_` avoids allocating a separate hidden-state tensor; valid rows are unchanged. Regression cases cover NaN padding for both main/draft and text/image routing.~~ Removed, fixed by https://github.com/vllm-project/DeepGEMM/pull/11

## Kernel benchmark: DeepSeek V4.1 Flash Gate

Measured on a **single NVIDIA GB300 (SM103)** with BF16 inputs `[M, 5120]`, BF16 gate weights `[384, 5120]`, **top-k=6**, `sqrtsoftplus`, normalization, and routed scaling factor **1.5**. **M is the number of token rows processed on one GPU**, not serving request concurrency.

The baseline is `GateLinear + fused_topk_bias`, using its normal shape-dependent dispatch. Mega-Gate fuses the gate GEMM and expert selection. The updated DeepGEMM pin allows non-finite padding scores, eliminating the separate hidden-state padding clear; existing input staging discards padded routes.

**Mega-Gate achieves 1.18–1.31× routing speedup for M ≥ 32, with no meaningful speedup for M ≤ 16.** Speedup is baseline latency divided by Mega-Gate latency.

**Method:** FlashInfer CUPTI timing of CUDA-graph replays with cold L2, 25 warmups, three rounds with alternating implementation order, and 100 samples per round. Values are medians of the round medians. Allocation, compilation, graph capture, input generation, routing metadata preparation, expert input staging, expert execution, and communication are outside the timed region. These measurements do not establish an E2E serving speedup.

**Correctness:** Expert IDs matched exactly at every batch size; routing weights matched with `rtol=1e-3, atol=1e-4`. Synthetic inputs and separated correction biases avoid ambiguous top-k boundaries. An additional 48 CUDA-graph replay cases passed with NaN/Inf padding across text, image, and hash/image routing.

**Versions:** vLLM `ef50fde183`, DeepGEMM `40d109bf`, PyTorch `2.13.0+cu130`, CUDA toolkit `13.1`, FlashInfer `0.6.18`, and CUPTI Python `13.0.1`.

### ywang96 · 2026-09-12

## Review: Mega-Gate integration (correctness + style)

This PR replaces the `fused_topk_bias` router with DeepGEMM's fused `bf16_mega_gate` kernel (gate GEMM + scoring + bias + top-k in one kernel) for all MegaMoE backends, deriving the extra routing metadata (image-token mask, hash-routing masks, safe hash input IDs) once per model forward and threading it through the layers as `MegaGateRoutingMetadata`. Overall this looks correct and carefully wired — **approve with comments**; findings below, with the merge-blocking items called out at the end.

I verified the wrapper against the pinned DeepGEMM commit (`39d8c4c`): positional/keyword argument order, `out=(topk_idx, topk_weights)` tuple order, int64/fp32 output dtypes, and the `image_bias`/`image_token_mask` co-presence assert all match `csrc/apis/mega_gate.hpp`. The kernel always emits normalized weights (`selected_weight / topk_sum * routed_scaling_factor` in the epilogue), so the new `use_mega_moe and not renormalize` init-time guard is correct and necessary. `ep_rank` is only consumed for EPLB duplicate selection / random routing (neither used here), so passing it is benign. SP handling is consistent in all four entry points (metadata derived from the already-sharded `input_ids`; MTP explicitly shards `routing_input_ids`), and draft-layer prefixes (`layers.{num_hidden_layers+i}`) guarantee draft MoEs are never hash-routed, so the hardcoded `has_hash_routing=False` in mtp/dspark is safe.

## Correctness findings

**Major**

1. **DeepGEMM pin bump silently drops SM120 and CUDA<12.9 support** — `cmake/external_projects/deepgemm.cmake:43-69`, `tools/install_deepgemm.sh:75`. The previous pin was explicitly chosen for SM120 ("nv_dev branch (SM120 support)"); the new one removes `12.0f/12.0a/12.1a` from `DEEPGEMM_SUPPORT_ARCHS` and raises the SM90 CUDA floor from 12.3 to 12.9. On SM120 builds the arch intersection is now empty, so DeepGEMM `_C` silently isn't built. This branch carries SM120-specific DSv4 code (`DeepseekV4FlashInferSM120Attention`, `model.py:1158-1160`), so this is a regression on this branch, not just a future-merge concern — currently only acknowledged in a cmake comment. Please call it out in the PR description and/or gate it so SM120 builds fail loudly or fall back instead of shipping without DeepGEMM.

2. **FlashInfer mega-MoE backends now silently require the SM100-only DeepGEMM gate** — `vllm/config/kernel.py:160` (`MEGA_MOE_BACKENDS = {"deep_gemm_mega_moe"} | FLASHINFER_MOE_EP_BACKENDS`), `vllm/models/deepseek_v4/nvidia/model.py:1087`. Because `use_mega_moe` is true for the FI EP backends, their routing now flows through `bf16_mega_gate`, which hard-asserts `arch_major == 10` in C++. The experts-level `_check_runtime_supported` (`model.py:362-365`) covers the DeepGEMM experts path, but a stale DeepGEMM install surfaces only via the wrapper's generic `RuntimeError` at first forward. An explicit SM100 capability check at `DeepseekV4MoE.__init__` when `use_mega_moe` would make this actionable.

**Minor**

3. **No Python-side validation in the `bf16_mega_gate` wrapper** — `vllm/utils/deep_gemm.py:462-510`. DeepGEMM requires bf16 contiguous `x`, `hidden % 256 == 0`, `num_routed_experts % 4 == 0`; violations surface as raw C++ `DG_HOST_ASSERT`s (this is why the test had to bump `hidden_size` 128→256). Note the existing experts guard checks `hidden % 128` (`model.py:366`) while the gate needs `% 256`. A one-line dtype/shape check would turn these into actionable errors.

4. **Vision+hash combined branch untested and fragile to config drift** — the two kernel tests cover (vision, no-hash) and (hash, no-vision) separately; the `torch.where(image_token_mask, 0, input_ids)` + `~image_token_mask` path (`model.py:476-480`) is never exercised. DeepGEMM asserts `image_bias.has_value() == image_token_mask.has_value()`, so any draft/target `vision_n_layers` inconsistency crashes deep in C++. Configs are consistent today (both sides read the same hf_config), but a unit test for this branch would lock that in.

5. **Test reference mask narrower than production** — `tests/models/test_deepseek_v4_mega_moe.py:113` treats only `IMAGE_SENTINEL_BASE_ID` and `IMAGE_PAD_ID` as image tokens; production masks all five sentinel ids. The test inputs only contain those two, so it passes, but `IMAGE`/`IMAGE_NEW_LINE`/`IMAGE_END` sentinels are never exercised.

**Nit**

6. `vllm/utils/deep_gemm.py:476-480` — the docstring sentence "Passing PyTorch-owned outputs to DeepGEMM makes their storage part of CUDA graph capture" is cryptic; the point is that torch-allocated `out` tensors get stable addresses across graph replays.

## Style findings

**Minor**

1. **The same ~7-line metadata block is copy-pasted into five forward methods** — `v4/nvidia/model.py:1511-1519`, `v4/nvidia/dspark.py:211-219`, `v4/nvidia/mtp.py:184-195`, `v4_1/nvidia/model.py:618-626`, `v4_1/nvidia/dspark.py:206-214`. Each repeats the `mega_gate_metadata = None / if self.use_mega_moe: ...` scaffolding plus the vision predicate `IMAGE_SENTINEL_BASE_ID if getattr(self.config, "vision_n_layers", 0) > 0 else None` — a predicate the MoE class already encodes at `model.py:874-876`. Six copies of logic that must stay in sync with `bias_vl` creation; letting `prepare_mega_gate_routing_metadata` take the config (or a `_has_vision(config)` helper) collapses each call site to one line.

2. **`prepare_mega_gate_routing_metadata` re-implements an existing helper with a magic number** — `model.py:471-473` hardcodes `+ 5`; `vllm/models/deepseek_v4/common/mm_preprocess.py:73-77` already provides `image_sentinel_mask()` keyed to `len(IMAGE_SENTINEL_TOKEN_NAMES)`. The `5` will silently drift if the sentinel family changes. Similarly, `torch.where(image_token_mask, 0, input_ids)` (`model.py:477`) uses a magic `0` fallback id with no comment.

3. **No docstrings on the two new module-level helpers** — `MegaGateRoutingMetadata` (`model.py:97-101`) and `prepare_mega_gate_routing_metadata` (`model.py:104-124`). Neighboring helpers carry one-line docstrings (e.g., `image_sentinel_mask`). The non-obvious contract — text models get all-`None` fields; `hash_token_mask` doubles as the kernel's `fix_routing_mask`; image tokens get id 0 as a safe hash-table index — is exactly what should be documented.

**Nit**

4. **Error-type/message inconsistency in the MoE forward** — adjacent pre-existing checks use `ValueError` with a `DeepSeek V4 ...` prefix (`model.py:1057`, `1061`); the new checks use `RuntimeError` without the prefix and without naming the parameter (`model.py:1066-1069`, `1077`, `1079`). Same caller-error category, two conventions.

5. **Function-local import of `bf16_mega_gate` in the per-layer forward** — `model.py:1071`. `vllm/utils/deep_gemm.py` has no circular-import risk; this exists so `monkeypatch.setattr("vllm.utils.deep_gemm.bf16_mega_gate", ...)` works in the test. Defensible, but it looks accidental in a hot path — add a one-line comment, or import at module level and patch `vllm.models.deepseek_v4.nvidia.model.bf16_mega_gate` in the test (patch-where-used).

6. **`vllm/utils/deep_gemm.py` watched only by the DSv4 kernels CI area** — `.buildkite/test_areas/kernels.yaml`. The module is shared infrastructure (fp8 GEMM, MQA-logits wrappers); it's absent from `attention.yaml`/`quantization.yaml`/etc., so future edits to it trigger only DSv4 tests.

7. **cmake comment narrates the previous revision** — `cmake/external_projects/deepgemm.cmake:68-69` ("The previous nv_dev pin also supported 12.0f ..."). Useful as a restore-note, but describes code that no longer exists; will go stale on the next re-pin.

8. **`moe_backend in MEGA_MOE_BACKENDS` open-coded in three more files** — `mtp.py:98`, `dspark.py:81`, `v4_1/dspark.py:83` (model.py already had three copies). The codebase has the named-predicate precedent `is_fi_moe_ep_backend` (`model.py:85`); an `is_mega_moe_backend()` next to `MEGA_MOE_BACKENDS` in `vllm/config/kernel.py` would read better.

9. **Bare "PR 432" reference in a code comment** — `model.py:1080`. Which repo? It's DeepGEMM#432; the permanent comment should link it.

10. **Test-style nits** — new `test_deepseek_v4_mega_gate_hash_routing_correctness` has no docstring while neighbors have one-liners; `tests/kernels/test_mhc_kernels.py:112` absorbs the new kwarg via `**kwargs` instead of naming `mega_gate_metadata=None` (hides future signature drift); the in-body `pytest.skip("DeepGEMM Mega Gate requires SM100")` could be `@pytest.mark.skipif` decorators matching the module's `pytestmark` style.

**Verified clean (no finding):** import ordering satisfies ruff isort (`I`) in all touched files, and the relative-vs-absolute split (`..common.mm_preprocess` in v4.1 vs absolute in v4) matches each file's pre-existing convention. No dead code from the removed `fused_topk_bias` import (`image_sentinel_lo` still feeds `_init_fused_moe_experts`, `hash_indices_dtype` still used for the `tid2eid` parameter). Type annotations complete and in file style; no prints, bare asserts, or commented-out code added; `_lazy_init` global/early-return plumbing follows the file's pattern exactly.

Thanks for the Mega-Gate integration. One SM12x note on the pin change, from 2x DGX Spark (GB10, sm_121), where DeepSeek-V4-Flash currently serves on the `nv_dev` pin.

This PR moves the pin to DeepGEMM `main` and drops `12.0f`, `12.0a` and `12.1a` from `DEEPGEMM_SUPPORT_ARCHS`. DeepGEMM `main` has no SM12x sources, and `nv_dev` (latest commit `572557e`, 09-08) is 108 commits ahead and 1 behind `main`, so it has not been rebased onto the 26/09 release yet.

Unlike #56255, this PR leaves `support_deep_gemm()` returning True for the whole 120 family. So on sm_121 DeepGEMM would still be reported as supported while no SM12x kernels are built. I have not built this PR to see exactly how that fails, but on current `main` several DSv4 paths call DeepGEMM on GB10: `mhc_pre_broadcast_tilelang` (which passes `use_tilelang_fallback=False`), `deep_gemm_fp8_o_proj` via `fp8_einsum` (no platform check), and the DeepGEMM FP8 block linear kernel that auto selects on sm_121.

Both this PR and #56255 rewrite the same pin line, so whichever lands first sets SM12x's fate for the other. Could SM12x keep a working path until `nv_dev` is rebased, for example by holding the arch removal or keeping a separate pin for 12.x, as the cmake comment already anticipates? Happy to test on 2x GB10.
