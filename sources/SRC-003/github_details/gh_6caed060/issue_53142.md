# [Issue #53142] [Bug] Hybrid mamba align precopy: illegal memory access on prefix-cache resume with explicit --block-size (state column seeded with wrong block size)

source: https://github.com/vllm-project/vllm/issues/53142
state: open | updated: 2026-09-22T19:53:47Z
labels: quantization

## 正文

### Your current environment

vLLM 0.27.1, V2 GPU runner, single RTX 3090 (SM86), CUDA 12.x, WSL2 Ubuntu 24.04 (also reproduces the same way on bare metal by code inspection). Model: Qwen3.8-27B (hybrid GDN/mamba + full attention), W4A16.

### 🐛 Describe the bug

`MambaHybridModelState.add_request` (v1/worker/gpu/model_states/mamba_hybrid.py) seeds the running mamba state column with the **CLI/attention block size** instead of the **mamba KV-cache group's block size**:

```python
self._mamba_state_idx_gpu[req_index].fill_(
    (new_req_data.num_computed_tokens - 1) // self.cache_config.block_size
)
```

On hybrid models the mamba group's `block_size` is derived from page matching (e.g. 2176 for a Qwen3-Next-style hybrid) and generally differs from `cache_config.block_size` whenever the user passes `--block-size` explicitly (required e.g. for quantized-KV setups whose tile size dictates the block, in our case 128).

With `--block-size 128 --enable-prefix-caching --mamba-cache-mode align`, the **second** request over a cached prefix crashes: a resume with `num_computed_tokens=100096` seeds `state_idx = (100096-1)//128 = 781` instead of `(100096-1)//2176 = 45`. The fused align precopy (`precopy_mamba_align_fused_kernel`) then reads `block_table[req, 781]` in a table with only ~61 columns, gets a garbage block id, and dies with:

```
RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered
  File "vllm/v1/worker/gpu/model_states/mamba_hybrid.py", line 201, in preprocess_state
  File "vllm/v1/worker/mamba_utils.py", line 826, in run_fused_precopy
```

(confirmed as the faulting kernel with `CUDA_LAUNCH_BLOCKING=1`).

First requests are unaffected (`num_computed == 0` seeds `-1` regardless of divisor), so in practice this looks like a spurious crash that only appears on the second request over a >1-block cached prefix — easy to misattribute.

**Repro:** any hybrid (mamba+attention) model with `--block-size <n>` where n != the mamba group block size, `--enable-prefix-caching`, `--mamba-cache-mode align`; send the same multi-block prompt twice.

### Fix (verified)

Seed with the mamba spec's block size. `_mamba_spec` is populated lazily by the first batch's `preprocess_state`; a resume can only happen after some batch has run, and fresh requests seed `-1` either way, so the fallback is safe:

```python
mamba_bs = (self._mamba_spec.block_size
            if self._mamba_spec is not None
            else self.cache_config.block_size)
self._mamba_state_idx_gpu[req_index].fill_(
    (new_req_data.num_computed_tokens - 1) // mamba_bs
)
```

Verified on the setup above: two-turn 102k-token needle test, turn 2 resumes from 100,096 cached tokens, both answers correct, turn-2 latency 6.3 s vs ~190 s cold. Happy to turn this into a PR if wanted.

Scoping update after downstream discussion (syv-ai/qwen38-27b-rtx3090#13): two preconditions worth naming so this reproduces cleanly.

**1. The buggy code only runs on the V2 GPU runner.** `MambaHybridModelState` lives in `v1/worker/gpu/model_states/` — MTP-style speculative decoding uses the classic runner and never executes `add_request`'s seed, so an MTP setup with the same flags will *not* crash. Repro needs a spec-decode method that forces the V2 runner (e.g. `method: dflash`).

**2. The mamba group's block size must actually diverge from `cache_config.block_size`.** As noted downstream, `models/config.py` sets `mamba_block_size = cache_config.block_size` when prefix caching is enabled, so a plain config keeps the two equal and the wrong divisor is harmless. The divergence appears when page-size matching realigns the mamba spec upward — in our case a hybrid whose uniform page is dictated by the mamba layers while an explicit `--block-size 128` (KV-quant tile) keeps `cache_config.block_size` small, with the drafter's sliding-window group in the mix. Boot log at crash time: mamba spec block 2176, `cache_config.block_size` 128 → resume from a 100,096-token cached prefix seeds column 781 of a ~61-column table.

The one-line fix (seed with `self._mamba_spec.block_size`) is precondition-free and cheap: it is correct whether or not the two block sizes diverge. Happy to send it as a PR.

### fabiopili · 2026-08-28

Independent confirmation of this bug on a different deployment, plus a **second site of the same wrong-divisor family** that PR #53798 does not cover and that silently corrupts output even once the crash is fixed.

**Setup:** Qwen3.8-Flash-Next (`Qwen4ExpForConditionalGeneration`, hybrid GDN + full attention + short-conv), NVFP4 weights, bf16 KV, single GB10 (DGX Spark, SM121), `v0.1.dev20073+g8e685d198` (a vendor branch; base commit is not on mainline, so line numbers below are approximate against main). `--enable-prefix-caching`, `mamba_cache_mode=align` (forced, the model does not declare `SupportsMambaPrefixCaching`), chunked prefill with `--max-num-batched-tokens 8192`, MTP speculative decoding `num_speculative_tokens=2`, `--max-model-len 262144`.

**One data point that widens the issue scope:** we hit this **without an explicit `--block-size`** (`user_specified_block_size=False`). On our build, `EngineCore._initialize_kv_caches` (engine/core.py, right after KV profiling) does `cache_config.block_size = min(g.kv_cache_spec.block_size for g in kv_cache_groups)`. With hybrid page-size unification our attention and mamba groups sit at block_size 1600, but some smaller-block group (we did not identify which) contributes 8, so `cache_config.block_size` ends up **8** while the mamba block is **1600** (`cache_config.mamba_block_size` is also unreliable here; it reads 16 at runtime; the only trustworthy source is the resolved `MambaSpec`). Any code that means "the mamba block" but reads `cache_config.block_size` is then off by 200x. So the divergence precondition is not limited to explicit `--block-size` users.

**Site 1 (this issue, confirmed):** `MambaHybridModelState.add_request` seeds `_mamba_state_idx_gpu` with `(num_computed_tokens - 1) // cache_config.block_size`. With divisor 8, a 60,800-token resume seeds src column 7,599 of a 166-column block table (164 + 2 speculative). `precopy_mamba_align_fused_kernel` then loads an arbitrary int32 from far past the table row and multiplies it by the multi-MiB mamba page stride. Measured boundary on our box: resumes with hits of ~54.4k tokens (34 mamba blocks of 1600) survive (the overshoot lands in benign adjacent allocations, i.e. **silent wrong-state migration**), hits of ~60.8k tokens (38 blocks) and above die with `Triton Error [CUDA]: an illegal memory access was encountered` in `run_fused_precopy`. Fresh requests seed `(0-1)//8 = -1` (the skip sentinel), which is why cold prefill at any depth never crashes and only the resume dies. We can also confirm the async-misattribution trap described here: without `CUDA_LAUNCH_BLOCKING=1` the fault surfaces as `CUBLAS_STATUS_INTERNAL_ERROR` in a downstream bf16 GEMM (the GDN in_proj via `default_unquantized_gemm`), which is how this bug got blamed on cuBLAS in at least one downstream recipe. We backported the PR #53798 approach (seed from the spec captured in `_get_mamba_group_info`, config fallback) and the crash is gone: resumes verified clean at 61k, 67.5k, 80.4k, 132k and 143k tokens.

**Site 2 (confirming PR #54076, which we hit and fixed independently before finding that PR):** `Scheduler._mamba_block_aligned_split` (v1/core/sched/scheduler.py) also does all of its arithmetic in `cache_config.block_size` units: `last_cache_position = request.num_tokens - request.num_tokens % block_size`, `aligned_end = end // block_size * block_size`, `next_block_boundary`, and the shared-prefix junction flooring. The function's own invariant comment says "slot p holds the state after exactly (p + 1) * block_size tokens. State is written at chunk ends, so chunk ends must be block aligned", and that invariant only holds in **mamba** block units. With divisor 8 the "alignment" is a no-op: prefill chunks end at 8192-token multiples, so every align-mode snapshot is cached under a hash that promises the state at a 1600-token boundary while actually holding the state at the nearest chunk end. Cold output stays correct (the running state is continuous), but **every resume continues from a state up to one mamba block stale: coherent, on-topic, wrong tokens, no crash**. With the seed fix alone this becomes the dominant resume error, so a deployment that applies only PR #53798 trades a crash for silent quality damage.

**Evidence for site 2:** with the seed fix only, greedy cold-vs-resume continuations on fresh prompts shared 0-3 leading tokens of the 16-32 generated, and two consecutive identical resumes shared only 2 of 19 (consistent with the two resumes consuming different, differently-stale snapshots; we did not instrument which snapshot each hit). After also fixing site 2 (we route the mamba group's spec block_size into `_mamba_block_aligned_split`; a cleaner upstream fix is to plumb the mamba block size in directly, exactly as #53798 does for the seed), resume-vs-resume and cold-vs-resume divergence profiles became **identical** (18/48 tokens shared in both comparisons; the residual jitter exists between two identical consecutive requests as well and is MTP/near-tie greedy noise, not cache-related), and a dual-passkey retrieval probe (one fact planted at ~4k, one near the end of a fresh ~31k context, with the question at the very end of the prompt) went 6/6 across cold and two resumes with correct final answers. Resume completes in 0.9-1.6 s at 28k-132k and ~2.9 s at 143k including 32 generated tokens, against 15-37 s genuinely cold at 31k-143k, with decode throughput unchanged.

**Suggested audit while someone is in there:** grep align-mode code for `cache_config.block_size`. In our tree the two sites above were the only wrong-unit reads we found on the align path, but the field's post-profiling rewrite to min-over-groups makes it a standing trap for any hybrid model with a small-block auxiliary group. Since drafting this we count at least three members of the family across PRs: the seed (#53798), the chunk split (#54076), and the align-allocator retention path (#53803), which supports treating the geometry source as the systemic fix rather than patching sites one at a time.

Happy to provide the full diagnosis writeup, our hook-style backport of both fixes, or reproduction details.

### Windless84 · 2026-09-09

Root cause from the engine side, reproduced and fixed on a Qwen3.8-Flash-Next NVFP4 deployment (GDN + QSA + MTP, one RTX PRO 6000, branch based on 3b45d053 / PR #54129):

`EngineCore._initialize_kv_caches` sets `cache_config.block_size = min(g.kv_cache_spec.block_size for g in kv_cache_groups)`. The QSA indexer registers a `CircularBufferSpec` ring buffer whose `block_size` is the ring capacity, 4 tokens without spec decode and 8 with MTP-3, so `cache_config.block_size` ends up 4/8 while the Mamba managers run on 1,600-token blocks. Two consumers trust it as the Mamba block size:

```
1. `mamba_hybrid.add_request` seeds the resumed state column with `(num_computed_tokens - 1) // cache_config.block_size` (the mechanism described in this issue). On any request resuming over a cached prefix the index lands far past the Mamba block table, hence the illegal memory access on the second request of a shared-prefix pair and never on a fresh prompt. Using the MambaSpec block size instead fixed it: [fork branch](https://github.com/Windless84/vllm/tree/fix/mamba-state-index-uses-mamba-block-size).
2. `Scheduler._mamba_block_aligned_split` aligns prefill chunk ends to it, so every 2,048-token chunk reaches the align-mode Mamba managers unaligned and each step allocates a fresh state block. Measured with the real 76-layer spec list driven through the scheduler on CPU: 140K tokens took 186 of 240 blocks instead of 113 (footprint 21.7K + 1.695 x tokens pool tokens), so any prompt above ~188K could never fit and re-prefilled forever (#56028 turns that spin into an error).
```

On `main` this is already closed by #53906 (2026-09-04), which excludes non-prefix-cacheable groups from the `min(...)` for exactly this reason ("their small block_size would otherwise drag the global block_size below the real allocator block size and desync it from mamba"). Builds based before that commit, including #54129, still hit it; both fixes above were verified on that base (replay of 8 shared-prefix prompts up to 261,802 tokens, 0 illegal-access lines, 140K = 113 blocks).
