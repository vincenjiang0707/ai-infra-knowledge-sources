# [PR #54514] [Bugfix][XPU] store the pointer raw bit pattern instead of its numeric value

source: https://github.com/vllm-project/vllm/pull/54514
state: open | updated: 2026-09-23T07:04:33Z
labels: bug, intel-gpu, mrv2

## 正文

Fix UT models/language/generation/test_common.py::test_models[True-False-5-32-microsoft/phi-2] meet OverflowError: Python int too large to convert to C long.

Root cause: PromptEmbedsState.add_request() stores GPU data_ptr() values into a signed int64 numpy array, which only holds up to 2^63-1 CUDA pointers are low and fit; XPU device addresses have the high bit set exceeding int64's max, so numpy raises OverflowError.

### aaron-seq · 2026-09-02

Diagnosis checks out. `embeds_ptrs` and `mask_ptrs` are `torch.int64` buffers (lines 41 and 42), XPU addresses have the high bit set, and the kernel bitcasts with `.to(tl.pointer_type(...))` at line 132, so a negative int64 carrying the same bits still loads correctly on the device side.

The thing worth settling before this lands is that the repo now has three spellings for the same problem:

- `vllm/v1/worker/mamba_utils.py:186` has `_reinterpret_u64_as_i64`, whose docstring says exactly this, used at lines 999 and 1090.
- `vllm/v1/worker/gpu/block_table.py:90` and the mamba copy buffers allocate their pointer tables as `torch.uint64` and assign `data_ptr()` straight in, with no conversion at all.
- This PR adds a third, inline at `prompt_embeds.py:59` and `:61`.

Two suggestions:

1. `prompt_embeds.py:59` and `:61` could reuse `_reinterpret_u64_as_i64` rather than a third open-coded spelling. It probably wants promoting to a shared util now that it would have callers in two subtrees.

2. Or, better, could `UvaBackedTensor` take `dtype=torch.uint64` for these two buffers? That is what `block_table.py:90` does, and it removes the need to remember the cast at every future write site. If uint64 is not workable here, the kernel's parameter comments at lines 106 and 107 are worth a clause, since those entries can now be negative while still reading as plain "device pointers".

Non-blocking: the conversion is pure and the failing value is a known constant, so a unit test writing a synthetic high address through `add_request` and asserting the stored bit pattern would guard this without XPU hardware. Right now the only cover is a phi-2 model test on Intel GPU.

On the red check: intel-ci #10099 failed 1 of 66 steps, and the failing one is `XPU W8A8 FP8 Linear Examples`, which does not touch this code path. Looks unrelated and worth a retry rather than a change here, though you would know better than me.

Given the RFC @jikunshang mentions, picking one convention and pointing the others at it may be more useful than a local fix.
