### Repro
```

  --speculative-config '{"model":"/drafter","method":"mtp","num_speculative_tokens":3,
    "num_speculative_tokens_per_batch_size":[[1,64,3],[65,128,1],[129,512,0]]}' \
  --kv-cache-dtype fp8 --async-scheduling --attention-backend TRITON_ATTN
```

The env opt-in follows the hint added in 0.25's downgrade warning: *"Overriding cudagraph_mode from FULL_AND_PIECEWISE to PIECEWISE for reliability. Use VLLM_USE_V2_MODEL_RUNNER=1 if you want to use full CUDA graphs."* Without it, DSD falls back to PIECEWISE and does not reach this capture path.

Startup proceeds through weight load, torch.compile, target-model graph capture (`Capturing CUDA graphs (FULL): 150/150` OK), speculator prefill capture OK, then crashes at speculator **decode** FULL capture:

```
File ".../vllm/v1/worker/gpu/spec_decode/autoregressive/cudagraph_utils.py", line 83, in create_forward_fn
    attn_state = prepare_inputs_to_capture(

    input_batch = InputBatch.make_dummy(num_reqs, num_tokens, input_buffers)

```

### Isolation matrix (3 configurations, same stack otherwise)
| speculative-config | Result |
|---|---|
| DSD table `[[1,64,3],[65,128,1],[129,512,0]]` | crash at ~1% of speculator decode capture |
| DSD table `[[1,64,3],[65,512,1]]` (no K=0 tier) | crash immediately at speculator decode capture |
| static `num_speculative_tokens: 3` (no table) | **capture completes** (`Graph capturing finished`) |

→ The **presence of the batch-size table** is the trigger; K=0 tiers are not required.

```python
### Candidate root cause (hypothesis, file:line trail)
`vllm/v1/worker/gpu/cudagraph_utils.py:205-225` reconstructs per-descriptor decode query lens as
`num_new_sampled_tokens_per_step = decode_query_len − num_speculative_tokens`, an invariant written for the **target** manager (`decode_query_len = K + newly sampled`). The autoregressive speculator's capture manager (`spec_decode/autoregressive/cudagraph_utils.py:59-105`) inherits this base, but MTP drafting has different decode-query semantics (1 token/seq/step), so the derived `num_tokens` collapses to ≈K while `num_reqs` is the capture batch size — matching the observed failure boundary (K=3 table fails from bs=4, K=1 table from bs=2: `num_reqs > num_tokens`). EAGLE presumably passes because its execution shape satisfies the invariant.
```

### Notes
- The DSD docs state the feature is "only tested with Eagle and Eagle-3"; this report adds the MTP data point. MTP + DSD works on v0.24.0 (runtime K switching across tiers verified with spec-decode counters), but v0.24.0 forces `cudagraph_mode=PIECEWISE` for DSD, so #45953's full-CG path is the reason to move to 0.25 — and this capture bug currently blocks that move for MTP.
- Perf context (v0.24.0, informational, related to #47277): at client concurrency 256 we see DSD mode incur a 12–25% throughput penalty vs no-spec (oscillating run-to-run) with TTFT p50 inflating ~6×, **even with an all-K=0 table producing near-zero draft tokens**. We isolated it away from the cudagraph downgrade (forcing `cudagraph_mode=PIECEWISE` on a no-spec config costs ≈0% at the same concurrency) — the overhead appears to live in the DSD/spec-decode path itself at high batch, matching the "per-step overhead erases the benefit" pattern reported in #47277 on a different stack (Qwen3.5 native MTP / L20X). We can post the isolation trace on that thread once this capture blocker is resolved and we can re-run the comparison on 0.25.
- Workaround today: static `num_speculative_tokens` (on 0.25 the full-CG capture passes; note startup then needs extra gpu-memory-utilization margin — we hit a warmup OOM at 0.95 on a 94GB H100), or DSD on 0.24 with the PIECEWISE cost.

### CZT0 · 2026-07-24

I opened draft PR #49652 with a root-cause fix for this path.

Related PR #47737 filters non-positive query lengths for DSpark's dynamic
draft manager when K=0 disables drafting. The MTP autoregressive draft decode
case here has different semantics: every draft step always processes exactly
one token per request, so its CUDA graph shape must not be derived from the DSD
schedule at all. Filtering the derived values can also leave no FULL decode
graph when the runtime schedule does not contain the configured upper-bound K.

The PR keeps DSD query-length derivation enabled for target verification,
autoregressive draft prefill, DFlash, and existing callers, and disables it
only for the fixed-shape autoregressive draft decode manager.

Validation includes the targeted pytest suite (`6 passed`), the applicable
Python pre-commit hooks, a 2x A800 red/green capture reproduction, and a
Qwen3.5 native-MTP real-weight smoke test with K=3/1/0.

### Same failure on ROCm with GLM-5.3-Flash — and the PIECEWISE fallback costs more than DSD gains

Reproduced on a completely different setup: 8x MI350X (gfx950), ROCm 7.2.3, TP8, `zai-org/GLM-5.3-Flash` FP8 with its native MTP head (`num_nextn_predict_layers = 1`), `ROCM_AITER_MLA_SPARSE` backend, vLLM dev branch.

```

  "num_speculative_tokens_per_batch_size":[[1,48,4],[49,1024,1]]}'
```

Startup proceeds through weight load and target-model capture, then the worker dies during speculator capture — 157 `Capturing` lines, then `WorkerProc hit an exception` with an empty error string propagated as `RuntimeError: Worker failed with error ''`. Same phase as your report.

Note that on this build the automatic downgrade you describe ("Overriding cudagraph_mode from FULL_AND_PIECEWISE to PIECEWISE for reliability") **does not happen** — `cudagraph_mode` stays `FULL_AND_PIECEWISE` and it crashes rather than falling back. I had to force it explicitly:

```
--compilation-config '{"cudagraph_mode":"PIECEWISE"}'
```

### With that it works — and the switching is verifiably correct

Acceptance length confirms the tier boundary is honoured:

| concurrency | acceptance length | K in use |
|---|---|---|
| 1 | 3.01 | 4 ✓ |
| 8 | 3.08 | 4 ✓ |
| 96 | 1.84 | 1 ✓ |

### But the workaround is not usable, because PIECEWISE costs more than DSD gains

Same server, same dataset, three warmup passes, `vllm bench serve`, 256-token outputs:

| concurrency | static K + FULL_AND_PIECEWISE | DSD + PIECEWISE | delta |
|---|---|---|---|
| 1 | 201 tok/s (K=4) | 105 | **−48 %** |
| 8 | 926 tok/s (K=4) | 629 | **−32 %** |
| 96 | 3 147 tok/s (K=1) | 2 586 | **−18 %** |

The loss is largest exactly where DSD is most valuable. At low concurrency the step is dominated by per-step host overhead, which is what full CUDA graphs remove; giving them up costs about twice what picking the better K wins.

For context on why we wanted DSD in the first place — on this 288-expert MoE the optimal K inverts with load, which is a much stronger effect than on dense models:

| concurrency | K=4 | K=1 | winner |
|---|---|---|---|
| 1 | **201** | 131 | K=4, +54 % |
| 8 | **926** | 630 | K=4, +47 % |
| 32 | **1 748** | 1 555 | K=4, +12 % |
| 48 | 1 956 | 1 939 | tie |
| 64 | 2 528 | **2 601** | K=1, +3 % |
| 96 | 2 890 | **3 147** | K=1, +9 % |

Acceptance length rises monotonically with K (1.83 at K=1 → 3.05 at K=4 → 3.52 at K=8) while throughput peaks at K=1 once the GPU saturates: on an MoE, verifying 5 tokens instead of 1 means proportionally more expert invocations, and roughly two of every five verified tokens at K=4 are discarded. That is the textbook DSD use case — a clean, measurable crossover at 48 concurrent requests — and it is currently out of reach because the feature and full CUDA graphs cannot be combined with an MTP drafter.

So this bug is not just a startup crash: the documented fallback is a net regression, which makes DSD effectively unavailable for MTP models rather than merely degraded. Happy to test a fix on this hardware — I have the harness and the baselines above.


### seongyun1104 · 2026-08-31

Thanks for this — the vendor spread is what changes the shape of the issue. Everything posted here so far has been NVIDIA/CUDA; a reproduction on gfx950 under ROCm with a different attention backend puts the same failure on the other side of the vendor boundary, which makes a backend-local cause much less likely.

Two parts of your report are worth separating, because one of them is new to this thread and the other touches numbers we have published elsewhere and should not be read as simply agreeing with yours.

### 1. On your build the documented fallback does not fire

You had to set `cudagraph_mode` by hand. On our stack vLLM downgrades on its own and says so:

```
WARNING [vllm.py:865] Dynamic speculative decoding changes the target verification
length at runtime. Overriding cudagraph_mode from FULL_AND_PIECEWISE to PIECEWISE
for reliability. Use VLLM_USE_V2_MODEL_RUNNER=1 if you want to use full CUDA graphs.
```

Ours is v0.27.1 on CUDA, yours is a dev branch on ROCm, so this could be version skew or platform — I can't tell which from here. Either way it matters for whoever writes the fix: a fix that treats the automatic downgrade as the safety net still leaves your configuration crashing rather than degrading.

### 2. Your PIECEWISE cost and ours are not measuring the same thing

Our published measurement is here: https://github.com/seongyun1104/depthchart/blob/a4bc8e5/ctx_tax_mechanism/RESULTS.md — 1× H100 NVL (93.6 GB), vLLM 0.27.1, V1, target `prithivMLmods/gemma-4-31B-it-qat-FP8` with drafter `google/gemma-4-31B-it-qat-q4_0-unquantized-assistant`. The load-bearing difference from your setup is that our speculative arm is a **K≡0 arm**: the schedule is written so the scheduler always picks zero draft tokens, and the counters confirm it (`spec_decode_num_draft_tokens_delta = 0.0` summed over every measured run). That arm isolates the floor — what enabling DSD costs before it drafts anything.

| ctx | concurrency | `no_spec` TPOT | `dsd` K≡0 TPOT | tax |
|---:|---:|---:|---:|---:|
| 400 | 2 | 14.374 ms | 15.317 ms | +6.56 % |
| 38 000 | 2 | 15.945 ms | 16.975 ms | +6.46 % |
| 400 | 189 | 77.164 ms | 93.820 ms | +21.58 % |

So our floor **grows** with concurrency (+6.56 % → +21.58 %) while your delta **shrinks** with it (−48 % → −18 %). I don't think those contradict each other, because your DSD arm changes two things at once relative to your baseline: it gives up full graphs *and* it re-picks K. At c=96 it picks K=1, which by your own table is worth +9 % over K=4 — so the K win offsets part of the graph loss exactly where the graph loss is smallest. Our arm never collects that win, because K is always 0.

Read together the two datasets are consistent with there being (at least) two terms:

```
- A **graph term**, largest where per-step host overhead dominates the step — i.e. low concurrency. Your c=1 row (−48 %) is the strongest measurement of it posted in this thread.
- A **capacity term** that only bites when you are pool-limited. On our box, with the drafter loaded and never drafting, the profiled KV pool falls by 15 025 tokens, about 10.6 % (§4 of the link above; two independent launch-order pairings agree to one token). It does not show up in TPOT at low concurrency; it shows up as concurrency you cannot have, which is why our number grows with batch. The memory profiler puts most of it on the activation peak reserved for the drafter's forward, not on draft KV: +3.93 GiB of a 4.97 GiB loss, against +1.05 GiB of weights.
```

If that decomposition holds, your MoE case is the worst available combination: the graph term is largest at exactly the low concurrency where your table shows K=4 winning by +54 %, and the c=48 crossover you measured is precisely the behaviour the feature exists to exploit.

### 3. What we can and cannot check from here

We have a pre-registered attribution run designed to split those terms: four no-spec arms crossing `cudagraph_mode` (`FULL_AND_PIECEWISE` against a forced `PIECEWISE`) with the KV pool pinned by `--kv-cache-memory-bytes` to either the no-spec size or the drafter-loaded size, plus a K≡0 arm, plus a prefix-caching control pair, all at fixed context (https://github.com/seongyun1104/depthchart/blob/286bcb8/tax_attribution/PREREGISTRATION.md). It has not been run yet, and our hardware cannot reach the long-context × high-batch corner where the unattributed remainder would live.

You offered to test a fix on that hardware. If you would also be willing to run measurement arms rather than only a fix, the two that would settle the decomposition on your stack are:

1. your **static-K baseline forced to `PIECEWISE`** (K held at 4, only the graph mode changed) — the graph term alone, with no K policy mixed in;
2. the **same baseline with the drafter loaded but K forced to 0** — the capacity/floor term, comparable to our arm.

Subtracting those from the numbers you already posted separates the graph term from the K policy on a stack where the fallback does not fire automatically and the model is a 288-expert MoE. We have no way to produce either number on that shape.

Related measurements on the same terms, for cross-reference: #49986 (the baseline tax and the graph-mode factor) and #49548 (the batch axis).

### On your point 2 — silently not drafting

This is the gap I opened #54748 for, before reading your note. `make_spec_decoding_stats` returns early on `not num_draft_tokens`, so a step where the schedule resolved K=0 increments no spec-decode counter at all — "the schedule turned speculation off" and "speculation is not running" are indistinguishable in the metrics, which is exactly the failure mode you describe. That PR adds `vllm:spec_decode_scheduled_steps{num_spec_tokens}` counting K=0 as well. It is open and unreviewed; I mention it only because your report is independent evidence that the hole is real in production, not a hypothetical.

### One thing your schedule does still hit on current main

While reading this path I found a live defect and used your exact configuration as the worked case: `[[1,8,6],[9,32,4],[33,128,3]]`, `max_num_seqs=128`, `num_speculative_tokens=6`, `FULL_AND_PIECEWISE`.

Dynamic SD captures a separate FULL decode graph per scheduled query length, but the dispatch candidate ranges are laddered over all of them together, while compatibility is keyed on `uniform_token_count`. So for many batch sizes the nearest captured size belongs to a *different* tier, the descriptor is rejected, and the batch falls to the mixed PIECEWISE graph — running attention eagerly every decode step even though a FULL graph for its own query length was captured and is wide enough to serve it.

On the default capture ladder for that shape, 27 of 128 batch sizes fall back:

```text
q=5 tier (K=4):  9, 11, 14, 17, 19, 22, 25, 27, 30
q=4 tier (K=3):  33, 35, 45, 47, 49, 55, 59, 61, 63, 65, 73, 77, 85, 89, 101, 105, 117, 125
```

**Your two measured points are not among them** — concurrency 4 (K=6) and concurrency 32 (K=4) both dispatch to a FULL graph, so your acceptance-length table is unaffected and I am not claiming otherwise. The exposure is at serving time, where concurrency moves across the whole range.

Fix is in #56136. It changes no capture sizes and adds no graphs; it only lets dispatch reach the graph that was already captured. I could not measure the recovered graphs — I have no hardware — so it is a dispatch-coverage claim, not a throughput claim. If you still have the MI355X harness up, the two arms that would put a number on it are your same run with `cudagraph_mode=FULL_AND_PIECEWISE` before and after that patch, at a concurrency from the list above (33 or 65 are convenient) rather than at 4 or 32.

Either way, thank you for the retest and for the two observability notes — both are more actionable than the bug they came attached to.
