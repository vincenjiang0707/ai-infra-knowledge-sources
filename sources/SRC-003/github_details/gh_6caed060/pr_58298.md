## 正文

## Purpose

Route **decoder prefill / extend** on the vLLM CPU backend through `zentorch_sdpa` on Zen CPUs, instead of always using the paged `cpu_attention_with_kv_cache` kernel.

Prefill has no need to gather K/V back out of the page table when the tokens for this step (and, for extends, the already-written cache) can be attended densely. Decode is unchanged: `query_len` at or below the reorder threshold still runs `cpu_attention_with_kv_cache`.

Dispatch:

- **Equal-length fresh prefills** (`query_len == seq_len` for every row): one `zentorch_sdpa.out(is_causal=True)` over a dense `[B, H, S, D]` batch.
- **Ragged fresh prefills and chunked extends**: one padded call with a bottom-right causal mask. Extends gather the cached prefix from the paged K/V cache.
- **Mixed batches**: the metadata builder requests a `[decode | extend | fresh prefill]` order, zentorch fills the prefill suffix, and the native kernel runs only the decode prefix with rebuilt scheduler metadata.

The path is used only for plain decoder self-attention in bf16/fp32 when `zentorch_sdpa` is registered. ALiBi, sliding window, logits softcap, attention sinks, FP8 KV cache, KV-sharing, encoder, and cross-attention stay native. The KV cache write is unchanged (`forward_includes_kv_cache_update = False`); this only skips the paged **read** for prefill rows.

This does not duplicate an in-tree CPU prefill SDPA path. It is the decoder-prefill counterpart of the Zen CPU encoder SDPA work. No `supported_models.md` / examples update: no new model, same CPU backend.

AI assistance was used to implement and review the change. The submitting author reviewed every line.
