# [Issue #58241] [Bug]: cutlass_scaled_mm_supports_block_fp8 excludes SM89 (Ada Lovelace) despite native FP8 tensor core support

source: https://github.com/vllm-project/vllm/issues/58241
state: open | updated: 2026-09-23T02:20:11Z
labels: bug, quantization

## 正文

### Your current environment

**Environment:**
- GPU: NVIDIA RTX 6000 Ada Generation (SM 8.9)
- vLLM: 0.29.0
- CUDA: 13.4
- Model: Qwen/Qwen3.8-27B-FP8 (block-quantized FP8, 128×128 blocks)

### 🐛 Describe the bug

**Description:**
cutlass_block_fp8_supported() returns False on Ada Lovelace (SM89), causing block-quantized FP8 checkpoints to fall through the kernel priority list in _POSSIBLE_FP8_BLOCK_KERNELS all the way to MarlinFP8ScaledMMLinearKernel — bypassing CUTLASS entirely, even though:

```
Non-block FP8 CUTLASS is supported on this card: cutlass_fp8_supported() == True
Ada Lovelace has native FP8 tensor core hardware, and vLLM's own docs state FP8 W8A8 is officially supported on "Hopper and Ada Lovelace" (https://docs.vllm.ai/en/stable/features/quantization/fp8/)
```

Bisecting ops.cutlass_scaled_mm_supports_block_fp8() directly shows a hard floor at SM90:
- 80 -> False
- 86 -> False
- 89 -> False
- 90 -> True
- 100 -> True

**Question:** Is this a genuine CUTLASS-library-level limitation (e.g. block-scaled grouped GEMM requiring Hopper-specific TMA multicast at the collective-builder level, similar to the SM_120/SM_121 CUTLASS MoE gap in #43507), or is SM89 support for block-scaled CUTLASS GEMM simply not yet wired up in vLLM's compiled extension?

If it's the latter, this is a meaningful gap for anyone running block-quantized FP8 checkpoints (increasingly common — DeepSeek-style 128×128 block scales) on Ada workstation cards (RTX 6000 Ada, L40S, RTX 4090), since it silently falls back to Marlin's weight-only dequant path rather than using the card's native FP8 compute.

**Repro:**
```
from vllm import _custom_ops as ops
for cap in [80, 86, 89, 90, 100]:
    print(cap, ops.cutlass_scaled_mm_supports_block_fp8(cap))
```

### hclsys · 2026-09-23

It's the former, and the tree shows it fairly directly.

Every block-scaled FP8 GEMM in vLLM lives under `csrc/libtorch_stable/quantization/w8a8/cutlass/c3x/`:

```
c3x/scaled_mm_blockwise_sm90_fp8{.cu,_dispatch.cuh}
c3x/scaled_mm_blockwise_sm100_fp8{.cu,_dispatch.cuh}
c3x/scaled_mm_blockwise_sm120_fp8{.cu,_dispatch.cuh}
```

There is no blockwise source under `c2x/` at all, and `c2x` is the path SM89 uses (`scaled_mm_c2x_sm89_fp8_dispatch.cuh`). So it isn't a missing dispatch entry — there is no non-c3x implementation to point at.

And the c3x ones can't be retargeted at Ada, because they're all TMA kernels:

```
sm90_dispatch.cuh:69    using ArchTag = cutlass::arch::Sm90;
       :215   cutlass::gemm::KernelTmaWarpSpecializedCooperativeFP8BlockScaledAccum
sm120_dispatch.cuh:72   using ArchTag = cutlass::arch::Sm120;
       :153   cutlass::gemm::KernelTmaWarpSpecializedBlockwisePingpongSm120
sm100_dispatch.cuh:71   using ArchTag = cutlass::arch::Sm100;
       :256   cutlass::gemm::KernelTmaWarpSpecializedBlockwise1SmSm100
```

TMA is Hopper-and-later hardware; Ada doesn't have the unit. So SM89 block-scaled CUTLASS would mean writing a non-TMA blockwise kernel, not wiring up an existing one. The `>= 90` floor in `scaled_mm_entry.cu:161` is accurate about what's actually compiled.

For what it's worth, your bisect matches what a current `main` build reports here — GB10, CUDA 13.0, so a different arch but the same predicate, and I added the non-block column since that's the contrast you're pointing at:

```
cap   supports_block_fp8   supports_fp8
89    False                True
90    True                 True
100   True                 True
120   True                 True
121   True                 True
```

The fallback-to-Marlin consequence you describe is real though, and that part is worth keeping open — on Ada the interesting question is whether a per-tensor requant through the c2x FP8 path beats Marlin's weight-only dequant for these checkpoints. That's a different change from "enable block FP8 on SM89".
