# [PR #58142] [Bugfix][Model] MiMo: keep fused fp8 qkv_proj pairing state across weight-loading calls

source: https://github.com/vllm-project/vllm/pull/58142
state: open | updated: 2026-09-23T03:50:57Z

## 正文

## Purpose
`XiaomiMiMo/MiMo-V2.6-Flash-RL` (and V2.5) produce degenerate output when using `--load-format fastsafetensors` or `--safetensors-load-strategy eager` when testing on Mi355x.  This issue should be platform-agnostic. 

## Root cause

MiMo's fused fp8 `qkv_proj` arrives as two checkpoint tensors (`weight` and `weight_scale_inv`) that must be sharded together, so `MiMoV2Model.load_weights` paired them in a dict and flushed only when both members arrived in the *same* call.

`AutoWeightsLoader._groupby_prefix` (`vllm/model_executor/models/utils.py:260-274`) groups the stream with `itertools.groupby` on the first name component and calls a child's `load_weights` **once per contiguous run of `model.*`**. Any pair that straddles a group boundary therefore never flushes and both parameters are left uninitialised — zeros/NaN for the fp8 weight and `-inf` for its scale:

Instrumented load (`mimo_v2.py`), TP=2:

| loader | `layers.0.self_attn.qkv_proj.weight` | `…weight_scale_inv` |
|---|---|---|
| default | correct | correct |
| `--load-format fastsafetensors` | `sum=0` | `sum=-inf` |
| `--safetensors-load-strategy eager` | `sum=0`/`NaN` | `sum=-inf` |

`eager` fragments heavily because `safetensors.torch.load` returns a Rust `HashMap` (not file order). Nothing errored because weights tracking is disabled for quantized models (`default_loader.py:435-438`), hence gibberish tokens instead of a load failure.

## Fix

MiMo's fused fp8 `qkv_proj` arrives as two separate tensors — the weight and its scale — which have to be sharded together, so the loader holds the first one until the second shows up. That holding area was a local variable, and a local variable only lives for one call of `load_weights`; when the loader runs more than once (fastsafetensors, eager), a pair can be split across two calls, both tensors are dropped, and the attention projections are left empty.

Keep the holding area on the model instead (`mimo_v2.py`, and the same spot in `mimo_v2_mtp.py`), so a pair still completes no matter which call each half arrives in. Nothing in the loader itself is changed, so no other model is affected.

### jmeadlock · 2026-09-22

Independent confirmation on different hardware, loader, and model size — this diff fixes it.

**Setup:** DGX Station GB300 (SM103, Blackwell Ultra, driver 595.84), `vllm/vllm-openai:nightly-d05da62e` (0.29.1rc1.dev422), TP1, `--moe-backend marlin`, `--offload-backend uva --cpu-offload-gb 320` on `routed_experts.*`. Model: **`XiaomiMiMo/MiMo-V2.6-Pro-RL`** (1.02T, 70 layers, fused fp8 `qkv_proj` pre-sharded 8 ways). Loader that triggers it here: **`--load-format runai_streamer`** (not in your table) — same mechanism, the streamer also fragments the `model.*` group.

**Method:** in-process `LLM(...)` with `enforce_eager=True` and forward hooks dumping the last token after `qkv_proj`, `self_attn`, `mlp`, and each decoder layer, on a 16-layer truncation (`--hf-overrides '{"num_hidden_layers":16}'`), compared against an independent CPU reference built from the checkpoint's own `modeling_mimo_v2.py` with hand-written fp8/mxfp4 dequant.

| loader | `layers.0.self_attn.qkv_proj` output ‖·‖ | layer-15 residual cos vs reference |
|---|---|---|
| default | 45.7 | 1.0000 |
| `runai_streamer`, stock `mimo_v2.py` | **0.0** (attn output 0.0; MoE output ‖·‖ 1354 vs 9.3 ref) | 0.21 |
| `runai_streamer` + this PR's `mimo_v2.py` hunk only | 45.7 | 1.0000 |

Full 70-layer Pro with the default loader serves correctly on this box (greedy: "Hello there, how are you?", "Paris", tool calls parse); it was garbage for 11 boots with the streamer before this was found. Notes and the hook/reference scripts: https://al-engr.com/gb300-mimo-v26-pro-testing.html

One observation for the reviewers rather than a change request: because weights-tracking is off for quantized models, nothing in the log distinguishes this from a healthy boot. A `logger.warning` when `_pending_fp8_qkv_proj` is non-empty at the end of `load_weights` would have saved a night here.
