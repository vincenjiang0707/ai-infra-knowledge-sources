### 🐛 Describe the bug

The kpool sparse indexer in `vllm/models/glm5next/common/attention.py` is replicated on every TP rank: `wq_b` is a `ReplicatedLinear` and `wk_weights_proj` uses `disable_tp=True`, so each rank computes the same keys and candidate sets from the same inputs. That only works if the ranks compute them **bit-identically**. Nothing enforces this, and one step in the key path does not guarantee it.

The key is normalised by `_fused_indexer_k_norm(kw[:, :head_dim], ...)`, a leaf compiled with `torch.compile(dynamic=True)`. Inductor turns it into a persistent reduction with three candidate configs (`XBLOCK` 1, 8 and 32, `num_warps` 2), and each rank picks one by benchmarking the first time it runs. `XBLOCK=1` computes the row reduction in a different order: on a fixed strided input of 2,048 × 160 → `[:, :128]`, its output differs from `XBLOCK` 8 and 32 in 2 of 2,048 rows (8 and 32 agree; the same classes on both GPUs). The difference is small, but the indexer then selects the top 512 of 540 pools per row. Where pools are close to a tie, a slightly different key selects a different set on one rank. The two ranks' attention outputs then differ, the all-reduce mixes them, and the greedy completion forks.

What we observed on the two-GPU pair, with everything else fixed (weights verified identical across launches by digest, same image and profile):

| rank 0 config / rank 1 config | Launch state | Ranks' keys differ in | Candidate sets differ in |
|---|---|---|---|
| {8, 32} / {8, 32} | state 1 | 0 of 858 indexer calls | 0 |
| {8, 32} / 1 | state 2 | 10 of 792 (8 of 11 MLA layers, from the first) | 2 (layer 19) |
| 1 / {8, 32} | state 3 | 13 of 836 | 2 (layer 19) |

Each state gives its own bit-reproducible set of completions for our fixed prompts; requests repeat exactly within a launch. So "which completion does this server give at temperature 0" depended on which config each rank's benchmark happened to pick at startup. Across the 16 launches we recorded with per-rank benchmarking, we saw state 1 11 times, state 2 3 times and state 3 twice.

Causality was shown by intervention, not only by correlation: we pinned only this kernel's config before the model loaded. `8 / 1` reproduced state 2, with a request trace identical row for row to an earlier naturally occurring state-2 launch. `8 / 8` restored state 1. Between the two arms, the only hash that changed was rank 1's output of this kernel on a fixed input.

### Why the obvious fix does not work today

`TORCHINDUCTOR_DETERMINISTIC=1` should make Inductor select one reduction config without benchmarking, the same on every rank. With a torch 2.13 bug it does not survive the first compiled frame: Dynamo's global-state restore calls `torch.use_deterministic_algorithms(False)`, which also sets `torch._inductor.config.deterministic = False` (reported as pytorch/pytorch#198563). Forcing the entry (`torch._inductor.config._config["deterministic"].env_value_force = True`, set right after the config module is imported) made it work. Both ranks then served the kernel with `XBLOCK=8`, cache state "only 1 config", keys identical on every call, with decode speed within ±3 %. Pointwise leaves still autotune per rank; since each element is computed by the same instructions, their block size should not change the bits (not measured).

### Suggested fixes (for the maintainers to judge)

```
1. Make the replicated key path deterministic by construction. For example, compute the key norm eagerly in fp32 (it is 128 wide and small), or pin its config, so it does not depend on a per-rank benchmark.
2. Or give each selected row a single owner. The prefill and decode row-sharding PRs (#54394, #58536) compute each row on one rank and all-gather the int32 indices, which removes cross-rank disagreement in the selection. Their motivation is performance, and #58536 applies only to uniform decode batches of 8 or more requests, so small-batch serving keeps the replicated path.
3. In general, any computation that is replicated across TP ranks and feeds a discrete choice (top-k, argmax) needs either bit-identical kernels or a single writer. Inductor leaves in model code autotune per rank and give no such guarantee.
```

### hclsys · 2026-09-24

One GB10 here, not two, so I can't speak to the cross-rank half. But the part that blocks the obvious workaround is single-GPU testable, and it's **wider than you framed it**.

You attribute the `TORCHINDUCTOR_DETERMINISTIC=1` failure to a torch 2.13 bug. It reproduces on **2.12.1** as well:

```
torch 2.12.1+cu130  (GB10, sm_121, CUDA 13.0)
TORCHINDUCTOR_DETERMINISTIC=1
  deterministic BEFORE first compiled frame : True
  deterministic AFTER  first compiled frame : False
  torch.are_deterministic_algorithms_enabled() : False
```

And your forced-entry workaround holds there too:

```
torch._inductor.config._config['deterministic'].env_value_force = True
  BEFORE : True
  AFTER  : True
```

So pytorch/pytorch#198563 isn't a 2.13 regression — it's at least two minors deep, which means "upgrade/downgrade torch" is not an escape and the force-entry is the only lever on 2.12 as well. Worth saying because a reader hitting this on 2.12 would otherwise assume they're safe.

The replication premise also checks out on current `main` (`36f94d5fe8a3`-era code, I read `upstream/main`), for anyone triaging:

