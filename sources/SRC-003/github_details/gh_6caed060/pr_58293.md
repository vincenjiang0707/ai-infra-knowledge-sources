# [PR #58293] [Bugfix][KV Connector][Mooncake] Announce residency for every Store write

source: https://github.com/vllm-project/vllm/pull/58293
state: open | updated: 2026-09-23T07:07:12Z
labels: bug, kv-connector

## 正文

## Purpose

`MooncakeStoreConnector` writes to the Store from two places, and only the positional save published the `BlockStored` event for what it committed. The hand-off path that persists mamba `align` boundary states stored its keys with no event at all, and `store_mask` keeps mamba groups out of the positional save, so that path is their only writer. A consumer intersecting the cache groups of a block therefore saw the mamba groups as missing everywhere, including on the rank that had just stored them.

Both paths now go through a single `_write`, which owns dedup, transfer, failure handling, statistics and the residency event, so a block this rank persists is announced by construction. The producers only describe what to write (`StoreBlock` / `StoreObject`), and `StoreResidencyEvents` is the only place a `BlockStored` is built. A block is announced once all of its Store objects are committed.

The events also carry `group_idx` plus the group's `kv_cache_spec_kind` and sliding window — the same metadata the core annotates its own prefix-cache events with — so a consumer can classify the group an event names (#49537 asks for this on hybrid models).

Nothing about what is written or read changes: keys, addresses, dedup, retry accounting and the scheduler side are untouched.

## Test plan

Unit suites:

```
pytest tests/v1/kv_connector/unit/test_mooncake_store_worker.py \
       tests/v1/kv_connector/unit/test_mooncake_store_hma_e2e.py -q    # 186 passed
pytest tests/v1/kv_connector/unit/test_mooncake_store_connector.py \
       tests/v1/kv_connector/unit/test_mooncake_store_scheduler.py -q  # 86 passed
```

`test_handoff_offload_announces_mamba_boundary_state` is the regression test for the reported behavior; it fails on the base commit, where the hand-off published nothing.

End-to-end, Qwen3.5-4B (GDN linear attention plus full attention, 4 cache groups) against a real Mooncake master, TP=2, `--mamba-cache-mode align --enable-prefix-caching --kv-events-config` on a zmq publisher, three ~4.4k-token prompts plus one repeat:

| | base | this change |
| --- | --- | --- |
| Store objects per group (0/1/2/3) | 6/6/6/48 | 6/6/6/48 |
| Store-side events per group | 0/0/0/24 | 3/3/3/24 |
| `kv_cache_spec_kind` on store-side events | absent | `mamba` / `full_attention` |
| block hashes covered by all four groups | 0 of 24 | 3 of 24 |

Every stored block is announced exactly once and the counts match what the master lists. `ruff check` and `ruff format --check` are clean; `mypy` reports the same pre-existing zmq typing errors as the base commit.

No model evaluation: this changes control-plane event metadata only, not stored bytes, transfers, scheduling or outputs.
