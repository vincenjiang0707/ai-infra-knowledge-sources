## 正文

## What
Raise `(H100) Helion Kernels Shard %N` from 2 to 5 hash shards of the whole `kernels/helion/` directory, so each shard stays under the 20-minute target. The MI250 mirror is pinned at its current 2 replicas so the new base count does not multiply it.

## Old
```
kernels-helion-test       parallelism: 2   pytest kernels/helion/ --shard-id/--num-shards
  mirror amd (MI250)      inherits 2
```

## New
```
kernels-helion-test       parallelism: 5   pytest kernels/helion/ --shard-id/--num-shards   (command unchanged)
  mirror amd (MI250)      parallelism: 2   (explicit; unchanged behaviour)
```

## Notes
- No coverage change: same command on the same directory, and no filters before or after. Only the replica count changes.
- The directory has ~1,970 run cases per build. Each of 5 shards gets ~390, so no shard is empty.
- A named semantic split was considered and rejected. `test_rms_norm_per_block_quant.py` is about half of the job's pytest time on its own, so it would need a monolith split before it could fit in one job.
- Legacy `.buildkite/test-amd.yaml` is untouched.

## Expected runtime and overhead
Predictions based on recent `main` builds (e.g. [91049](https://buildkite.com/vllm/ci/builds/91049), [91027](https://buildkite.com/vllm/ci/builds/91027)):

| Job / replica | pytest | running wall | non-pytest overhead | main overhead cause |
|---|---|---|---|---|
| before: shard 1–2 (each) | ~34–40m | ~40–46m | ~1–10m | `pip install helion`, image pull when cold |
| after: shard 1–5 (each, predicted) | ~14–16m | ~15–17m | ~1m warm | same, now paid 5× |

```
- Baseline → new: ~81 → ~86 worker-minutes (predicted). That is about **+5 extra worker-minutes**, within the 20-minute budget, and comes from three extra setups.
- Slowest shard: ~16m pytest (predicted), inside the 20m target.
- Why 5: 4 shards would put each at ~19.6m of pytest with no headroom for hash skew or run-to-run variation.
```
