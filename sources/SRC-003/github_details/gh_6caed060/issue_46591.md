### Your current environment

```
- vllm `0.22.2.dev` (HCF fork at upstream sha `fce03608d`, identical to upstream main on the touched test files — `tests/distributed/test_pipeline_parallel.py` has 0-line diff vs `vllm-project/vllm@main`)
- transformers: verified on both `4.57.1` and `5.12.1` (latest stable, released 2026-06-15) — same failure
- 4 × NVIDIA H20 (sm_90), CUDA 13.0, torch `2.11.0+cu130`
```

### 🐛 Describe the bug

`tests/distributed/test_pipeline_parallel.py::test_tp_language_generation` collected from `meta-llama/Llama-3.2-1B-Instruct: PPTestSettings.detailed()`. Two of the 10 expanded combinations consistently fail on H20:

```
- `parallel_setup9-mp` → `(tp=2, pp=2, eager_mode=True)` × `mp`
- `parallel_setup10-ray` → `(tp=2, pp=2, eager_mode=True)` × `ray`
```

(both are the heaviest detailed setup: tp=2 pp=2 = 4 GPU.)

Stack:
```
tests/utils.py:273: self._wait_for_server(url=self.url_for("health"), timeout=max_wait_seconds)
...
E   RuntimeError: Server failed to start in time.
tests/utils.py:652: RuntimeError
```

### Reproducer

```bash
pytest -v -p no:rerunfailures \
    "tests/distributed/test_pipeline_parallel.py::test_tp_language_generation[meta-llama/Llama-3.2-1B-Instruct-parallel_setup9-mp-auto-test_options9]" \
    "tests/distributed/test_pipeline_parallel.py::test_tp_language_generation[meta-llama/Llama-3.2-1B-Instruct-parallel_setup10-ray-auto-test_options10]"
```

Total wall-clock 16:56s. Both fail with the timeout above.

### Diagnosis: it's a deadline issue, not a server-bring-up bug

The vllm server **is starting** for both setups — verified by inspecting the running pytest pod:

- For `setup10-ray`: `vllm serve meta-llama/Llama-3.2-1B-Instruct --pipeline-parallel-size 2 --tensor-parallel-size 2 --distributed-executor-backend ray ...` was alive for 14+ minutes, all 4 GPUs at 100% utilization, ray gcs and dashboard processes running, model loaded, weights loaded, **CUDA graphs (decode, FULL) finished capturing** (`100%|██████████| 4/4`). At that point the test process gives up because:

```python
# tests/utils.py:271
max_wait_seconds = max_wait_seconds or 480   # 8 minutes
```

`tests/distributed/test_pipeline_parallel.py:_compare_tp` does not override `max_wait_seconds`, so the default 480s applies. Llama-3.2-1B + tp=2 pp=2 + Ray executor on H20 takes longer than 480s to reach `/health` 200 (cold flashinfer autotune + cuda graph capture across 4 workers).

Earlier setups (`setup3` ... `setup8`, `setup11`, `setup12`) finish within 480s on the same node, so the deadline is just barely too tight for the heaviest detailed combos when the cluster is under any contention.

### Suggested directions (no preference, just listing)

1. Bump `_compare_tp`'s call-site timeout (e.g. pass `max_wait_seconds=900` to `compare_two_settings`) for distributed pipeline tests where init dominates.
2. Bump the global `max_wait_seconds or 480` default in `tests/utils.py` to `or 900` (or read from an env var).
3. Skip these specific parametrize cells on Hopper if they can be considered redundant with cheaper setups.

Filing this as a report — happy to put up a PR for whichever direction maintainers prefer.
