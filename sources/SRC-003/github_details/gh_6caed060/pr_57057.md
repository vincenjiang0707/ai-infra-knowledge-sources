# [PR #57057] [Attention] Add UltraQuant 4-bit KV cache backend (FlyDSL D=256)

source: https://github.com/vllm-project/vllm/pull/57057
state: open | updated: 2026-09-25T01:00:23Z

## 正文


## Purpose
Adds an `ultraquant_4bit` KV-cache dtype for long-context / agentic serving, where the KV cache is the limiter. UltraQuant stores the cache at 4 bits, FP4 E2M1 codes with UE8M0 (power-of-two) per-group-32 scales, and Hadamard-rotated keys, giving **~2× KV density over fp8**, so more concurrency fits before eviction and decode stays memory-efficient under load.
Decode runs on a FlyDSL `D=256` kernel for GQA group sizes **{6, 8, 16}**, with a Triton unified-attention fallback and numerical reference paths.

## Design
- New `UltraQuantAttentionImpl`, a standalone subclass of `TurboQuantAttentionImpl`. 
- `TurboQuantAttentionBackend.get_impl_cls()` dispatches to the UQ impl on the `ultraquant_4bit` cache dtype.
- New ops under `vllm/v1/attention/ops/ultraquant/` (FP4/UE8M0 format, Hadamard store, dequant, Triton unified attention, reference) and the FlyDSL D=256 decode kernel/launcher.

## Test Plan
```
- **Unit tests** (`tests/kernels/ultraquant/`): store, dequant, decode, and FlyDSL-vs-reference numerical checks, plus config.
- **Serve smokes**: Qwen3.8 (GQA-16, TP=8) and Qwen3.6-27B (GQA-6, TP=2), confirming FlyDSL dispatch (no Triton fallback) and coherent output.
- **Accuracy** (KV format is the only variable; sampling fixed): GPQA-Diamond.
- **Performance**: SemiAnalysis-style 262K-token agentic replay, throughput/latency and peak KV utilization across concurrency.
```

## Usage
Enable the 4-bit KV cache with `--kv-cache-dtype ultraquant_4bit` (D=256, GQA {6,8,16}):

```bash
vllm serve /path/to/Qwen3.8-2.4T-A95B-MXFP4 \
  --tensor-parallel-size 8 \
  --attention-backend ROCM_AITER_UNIFIED_ATTN \
  --kv-cache-dtype ultraquant_4bit \
  --max-model-len 163840 \
  --reasoning-parser qwen3 \
  --trust-remote-code
```

The 4-bit KV cache composes with MXFP4 weights. Decode auto-dispatches to the FlyDSL D=256 kernel (gfx950), otherwise it falls back to Triton unified attention. All accuracy/perf runs use the sampling settings recommended in the model's Hugging Face card (Qwen3.8: `temperature=1.0, top_p=0.95, top_k=20`).

## Test Results
**Accuracy — GPQA-Diamond, mean over multiple seeds.**
UltraQuant is at parity with the fp8 (KV8) baseline — in fact marginally ahead on the mean. The decode kernel is numerically exact, so per-seed differences are sampling variance (the arms trade places seed to seed).
| Model | UltraQuant 4-bit (mean) | KV8 fp8 (mean) |
|---|---|---|
| Qwen3.8 | **93.27%** | 92.42% |
| Qwen3.6-27B | **86.87%** | 85.61% |

```
**Performance: throughput–latency Pareto (262K-token requests, MI355X):**
Qwen3.8 (GQA-16, TP=8). UQ and KV8 track together at low concurrency; UQ pulls ahead from **C=32** onward. KV8 saturates its cache at **C=38 (100%, evicting)** and throughput collapses, while UQ is still at ~44% cache and keeps scaling.
```

## Notes
- Requires a FlyDSL-capable ROCm build (gfx950) for the D=256 decode kernel; falls back to Triton unified attention otherwise.
- Benchmark figures were measured across differing vLLM / AITER / FlyDSL bases, so absolute throughput/latency (and the 8-bit baseline) are indicative rather than bit-identical across environments; the accuracy and relative UQ-vs-KV8 trends are the takeaway.
