# [PR #57679] [Perf][DSv4.1] Restore the fused query RMSNorm + MXFP8 quantization path

state: closed | updated: 2026-09-25T01:39:04Z

## 正文

## Purpose

`can_fuse_query_quant` decides whether the DeepSeek-V4.1 attention block may hand `wq_b` a pre-quantized query, letting `fused_q_kv_rmsnorm_quant` do the q/kv RMSNorm and the MXFP8 quantization in one kernel. It probed `linear.input_quant_key`. #53793 renamed that attribute to the private `_input_quant_key` and introduced `get_input_quant_key` as its reader, but this call site was not updated, and it is the last one in the tree still reading the old name. The gate has been unconditionally `False` since that rename, so every layer runs a BF16 `fused_q_kv_rmsnorm` followed by a standalone `MXFP8QuantizeSwizzled` over the query — exactly the pair the fused kernel exists to replace.

Read the capability through `get_input_quant_key`, and pass `launch_pdl` to the fused kernel's launch. The kernel already compiles in `gdc_wait()` / `gdc_launch_dependents()` from its `LAUNCH_PDL` constexpr, but without the launch attribute Triton issues an ordinary launch, so the kernel cannot start before its predecessor retires and the wait is inert. Its siblings `fused_q_kv_rmsnorm`, `fused_inv_rope_fp8_quant` and the Qwen4 PLE/HC kernels pass both. The fused path is CUDA-only by construction, since `can_fuse_query_quant` returns `False` off CUDA, so the new kwarg is never reached on ROCm.

This restores a lost fusion; it does not change model output. The fused kernel reproduces the separate-kernel FP8 bytes, swizzled scales and normalized KV bit for bit.

## Duplicate-work check

No issue tracks this, so issue-number checks are not applicable. Open-PR searches covered `can_fuse_query_quant`, `input_quant_key`, `get_input_quant_key`, `query_quant deepseek_v41`, `fused_q_kv_rmsnorm`, `launch_pdl triton` and `deepseek_v41 pdl`. Nothing else touches `vllm/models/deepseek_v41/common/ops/query_quant.py`. #53793 performed the rename that stranded this gate. #55505 extends the same contract with input scales and does not change how the key is read. #48086 also adds a missing `launch_pdl`, but in `deepseek_v4/common/ops/fused_inv_rope_fp8_quant.py`, for a `TypeError` on non-PDL hardware rather than a lost overlap. #54063 and #53151 teach ROCm AITER kernels to consume `QuantizedActivation` instead of fixing a producer gate.

## Test Plan

```bash
PATH=/usr/local/cuda-13.1/bin:$PATH .venv/bin/python -m pytest tests/kernels/core/test_fused_q_kv_rmsnorm.py -q
pre-commit run --files vllm/models/deepseek_v41/common/ops/query_quant.py
```

The existing suite already encodes this gate: `test_shared_query_quant_preserves_projection` asserts `can_fuse_query_quant` is true for the two FlashInfer MXFP8 kernels and that the pre-quantized `wq_b` projection matches the BF16 path at `rtol=0, atol=0`. It needs Blackwell plus a FlashInfer that can JIT, so `nvcc` must be on `PATH` or the whole group skips, which is how the regression went unnoticed.

Two standalone harnesses, not included in the diff, produced the numbers below. One times the isolated production chain `fused_wqa_wkv` GEMM → q/kv RMSNorm (+ query quantization) → `wq_b` GEMM and compares outputs bitwise before timing. The other serves the model and sweeps client concurrency, running both code versions inside one job so they share a node, with the order counterbalanced across two jobs.

## Test Result

Standalone commit `20538d465a`, based on `9d75dd4544`. **73 tests passed** in 107 s on GB200. On `main` the same file reports **24 failed**, all of them `test_shared_query_quant_preserves_projection` cases failing at `assert can_fuse_query_quant([linear, linear])`, so no new test was needed. Changed-file pre-commit hooks passed, including ruff, ruff format, typos and mypy 3.10.

Model output is unchanged. The microbenchmark checked FP8 data, swizzled scales, normalized KV and the downstream `wq_b` GEMM output for bitwise equality against the two-kernel path at all 14 shapes before timing, and the projection test asserts the same at `rtol=0, atol=0`. No accuracy evaluation is claimed, because the change cannot move a logit.

### Performance
Serving: `--tensor-parallel-size 4`, `FLASHINFER_MLA_SPARSE_DSV41` with `indexer_kv_dtype=mxfp4` and `indexer_sparse_logits`, `--kv-cache-dtype fp8`, `--max-num-seqs 128`, `--no-enable-prefix-caching`. Client is `vllm bench serve`, random dataset, 1024 input and 256 output tokens, `--ignore-eos` and `--temperature 0` so every request runs exactly 255 decode steps. Concurrency 1 is repeated 10 times and the others 5 times; each cell is the median of per-run medians. The two columns of raw ITL are the two jobs.

All eight paired measurements favour the patched build and swapping the order flips no sign. Concurrency 8 is the most trustworthy row: the two jobs agree at 1.05% and 0.97%, and 48 tokens per step is the shape where the microbenchmark predicts 69.7 us out of a 6.32 ms step, or 1.10%.
