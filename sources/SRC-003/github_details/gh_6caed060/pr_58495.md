## 正文

## Purpose

Follow-up to #57456. The `sm120` family of `_BATCH_INVARIANT_MATMUL_TUNED_CONFIGS` only covered the TP=1 shapes of Qwen3-1.7B / 4B / 8B, so with `VLLM_BATCH_INVARIANT=1` and `tensor_parallel_size > 1` every linear layer on RTX PRO 6000 / RTX 50 still ran the batch-invariant persistent matmul with the default `128x128x64 / 8 warps / 3 stages` config (the TP=2 rows in #57456's comments show the resulting ~2.9x BI overhead unchanged by the table). Now that #57586 selects the tile config from the runtime M, the table is the remaining lever for TP.

This PR adds the 41 per-rank `(N, K)` shapes of the same three models at TP=2 / 4 / 8 (`qkv_proj`, `o_proj`, `gate_up_proj`, `down_proj` and the vocab-parallel `lm_head`; `(3072, 4096)` is shared by Qwen3-8B TP=2 qkv_proj and TP=8 gate_up_proj), 15 -> 56 entries. Same structure and invariance rule as the existing entries: one `BLOCK_K` per `(N, K)`, `BLOCK_M / BLOCK_N / num_warps / num_stages` per M bucket.

## Method

Identical to #57456 (same sweep tool, same gates), one RTX PRO 6000 Blackwell (sm_120, 188 SMs, driver 580.159.04), vLLM main @ 9ef37771b, torch 2.13.0+cu130, triton 3.7.1: per shape 3 `BLOCK_K` x 4 `BLOCK_M` x 4 `BLOCK_N` x 2 warps x 4 stages = 384 configs x 10 M values (1 ... 2048), CUDA-event timed against the current default config and cuBLAS; `BLOCK_K` chosen shape-wide by a decode-weighted score; gate: `allclose` to an fp32 reference and the M = 1 rows **bitwise identical** to the same rows computed at M = 8 / 32 / 256 / 2048 (sha256). All 41 shapes green.

### hclsys · 2026-09-24

Not an objection to this diff — it adds entries and your TP=2 numbers speak for themselves. This is about the key the table is looked up under, which predates it (#57456), and I have hardware that makes it visible.

`_get_tuned_matmul_arch_family` keys on the major version only:

```python
if capability.major == 12:
    return "sm120"
```

So a DGX Spark / GB10 (cc 12.1, **48 SMs**, LPDDR5X unified with system RAM) picks up the same table tuned on RTX PRO 6000 / RTX 50. Confirmed on mine — `arch_family sm120`, table resolved, 15 entries on `main`.

I benchmarked `matmul_persistent` with the table active vs. forced to the default config, same tensors, bf16, 50 iters after warmup, three shapes already in the table:

```
             (12288,2048)   (2048,6144)   (4096,2048)     tuned/default
M=1              0.80x          0.73x         0.50x
M=8              0.87x          0.77x         0.42x
M=32             0.97x          0.78x         0.63x
M=256            1.67x          1.37x         1.15x
M=1024           1.28x          1.25x         1.43x
```

Consistent across shapes and across re-runs: the tuned configs are a solid **win at small M** (up to ~2.4x) and a **loss from M=256 up** (1.15–1.67x slower than the untuned default). Plausibly the block/stage choices assume a much larger SM count and a discrete memory system than Spark has, but I haven't tried to attribute it further.

Worth keeping in proportion: this only fires under `VLLM_BATCH_INVARIANT=1`, so it isn't a default-path regression, and at decode-shaped M the table is helping GB10 too.

If it's useful I'm happy to tune the same shapes on GB10 and send them as a separate family, or to split the key so 12.1 doesn't inherit 12.0's table — say which you'd prefer, or I can move this to its own issue if you'd rather keep this PR focused.
