# [PR #58058] [Bugfix][ROCm] Drop -1 sentinels when building the ragged sparse-MLA indices

source: https://github.com/vllm-project/vllm/pull/58058
state: open | updated: 2026-09-23T02:52:39Z
labels: bug, rocm

## 正文

## Purpose
The sparse MLA kernel (pa_sparse_prefill_opus) currently seg. faults when -1 sentinels happen within accessed region as there is no check for it.

 `combine_topk_swa_indices` reserves top-k columns from a position-derived count and writes `-1` wherever a candidate fails its validity test, and `build_ragged_indices_from_dense` copies the row prefix verbatim, sentinels included.
 
 ## The fix

Make the ragged index stream sentinel-free at the point it is built, so no consumer can dereference one. `build_ragged_indices_from_dense` now keeps only valid entries per row, and `indptr` counts those. Semantically identical, skipping an index and masking it out give the same attention result.

```
This is layout-agnostic: it does not matter whether the sentinels are leading, interior or trailing. Getting rid of 
"-1" indices should not cause any side-effects as they are supposed to be masked out anyway.
```

## Tests

GSM8K 5-shot shares a few-shot prefix, so with prefix caching on (the default)
it generates partial hits:

### cagrikymk · 2026-09-23

> Why the tot is broken here? Is current v0.1.22.post1 also broken for now?

TLDR:
It got introduced on two PRs from 9/9 and 9/10.

The story based on claude anaysis:

1. [vllm-project/vllm#54855](https://github.com/vllm-project/vllm/pull/54855) (7e9176065, 2026-09-09): "Route large DSV4 sparse prefill to AITER OPUS". This is the trigger.

Before this commit, every prefill went through _sparse_attn_prefill_ragged_kernel, vLLM's own Triton kernel. It masks bad indices itself (valid = in_range & (slot >= 0) & (slot < num_kv)), so -1s in the ragged stream did no harm.
[vllm-project/vllm#54855](https://github.com/vllm-project/vllm/pull/54855) sends prefill to pa_sparse_prefill_opus when it's on gfx950, has an attention sink, and has at least 1024 query tokens. It feeds OPUS the same build_ragged_indices_from_dense output the Triton kernel used.
OPUS has no sign check. Its docstring says: "Every entry in kv_indices_prefix / kv_indices_extend must be a valid row index."
The old packer, _pack_dense_prefix_to_ragged_kernel, made this worse. It copied the first lengths entries of each row as-is, and it actively rewrote out-of-range values to -1. That design only worked because the consumer masked them.
The [vllm-project/vllm#54855](https://github.com/vllm-project/vllm/pull/54855) tests don't cover rows containing -1.

2. [vllm-project/vllm#56228](https://github.com/vllm-project/vllm/pull/56228) (9b959b865, 2026-09-10): V4.1-Flash model definitions. This is where your sentinels are produced.

It added the Torch version of combine_topk_swa_indices in vllm/models/deepseek_v41/amd/rocm.py.
topk_len is computed from the token position (min((pos+1)//compress_ratio, topk)), not from how many valid candidates the indexer actually returned.
Any slot that fails (v >= 0) & (v < N) is written as -1, and the SWA indices start right after it at column topk_len. So the -1s land in the middle of the row, inside combined_lens, and get copied into the ragged stream.
The V4.0 Triton combine kernel follows the same logic, so the V4.0 path is exposed too.
