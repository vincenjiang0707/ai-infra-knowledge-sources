# [Issue #58147] [Bug]: Qwen3 parser turns tool-call markup the model quotes into real tool calls (names outside request.tools, and duplicates of offered ones)

source: https://github.com/vllm-project/vllm/issues/58147
state: open | updated: 2026-09-23T05:27:31Z
labels: tool-calling

## 正文

### Your current environment

- vLLM `v0.28.0` (`vllm/vllm-openai:v0.28.0`), xgrammar 0.2.3
- Qwen3.8-27B, NVFP4 checkpoint; chat template sha256 `0a20a4673d45476ed88dcb4a60b6af35ca202ae470fee6fd2bd419758aabd9ab`
- `--reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder`, `--speculative-config '{"method":"mtp","num_speculative_tokens":2}'` (reproduced with and without speculation)
- RTX 5090 (sm_120), CUDA 13.0, torch 2.13.0+cu130
- `/v1/chat/completions`, streaming and non-streaming

### 🐛 Describe the bug

When the model writes tool-call markup as *text* — quoting the format in its
reasoning, showing the caller an example, echoing the template's own
placeholder block — the `ParserEngine` transitions in `vllm/parser/qwen3.py`
(`(REASONING, TOOL_START)`, `(TOOL_BETWEEN, FUNC_PREFIX)`) fire on it, and the
response carries tool calls the model did not make. Two distinct classes:

1. **Names that are not in `request.tools`** — `function_name`, `...`,
   straight from the chat template's example block.
2. **Duplicates of an offered name** — the model shows a `get_weather` block
   and then makes the real call; the client receives two or three.

Both reach the client as ordinary `tool_calls`, so a harness executes them.

#### Minimal reproduction (parser-level, no server)

```python
from vllm.parser.qwen3 import Qwen3Parser
# tools = [get_weather(city: string)], thinking on
text = ("The format is:\n<tool_call>\n<function=function_name>\n<parameter=parameter_name>\nvalue\n</parameter>\n</function>\n</tool_call>\nNow call it.\n</think>\n\n"
        "<tool_call>\n<function=get_weather>\n<parameter=city>\nParis\n</parameter>\n</function>\n</tool_call>")
# extract_tool_calls(text) ->
#   [('function_name', '{"parameter_name": "value"}'), ('get_weather', '{"city": "Paris"}')]
# streaming path: identical two calls
```

#### Measured on a live server

8 cases x thinking off/on x sync/stream, 100 repeats per cell, concurrency 4,
model-default sampling (T 1.0 / top-p 0.95 / top-k 20), 3,200 requests per
arm, every failure carrying its raw generation. In ordinary cases the defect
is rare — 1-2 out-of-set phantoms per 1,600 thinking-on requests, the same
with speculative decoding on or off (it is the parser, not the drafter).

One prompt makes it the common case: *ask the model to show the tool-call
block it is about to use, then use it.* 100 repeats per cell:

| | unpatched 0.28.0 | with `validate_tool_names=True` (i.e. #50986) |
|---|---|---|
| out-of-set names (`function_name`, `...`) | **8** | **0** |
| duplicates of an offered name | 168 | 168 |
| legitimate calls withheld | — | **0** |
| pass, 800 requests | 393/800 | 421/800 |

Thinking on, 76-84 of every 100 responses to that prompt carry a duplicated
in-set call, in both arms.

### The fix for class 1 is already open: #50986

`ParserEngineConfig.validate_tool_names`
(`vllm/parser/engine/parser_engine_config.py:104`) gates `_emit_name_delta`,
`_handle_tool_end` and `extract_tool_calls` (`parser_engine.py:798, 858,
1033`), so a call whose name is not in `request.tools` is never emitted on
either path. `glm47_moe.py:179` opts in; `qwen3_config` does not. #50986
sets it. Measured on a deployed server, that PR:

- removes the out-of-set class outright (8 -> 0 above);
- **withholds nothing legitimate** — every `no_call` under the patch is a
  generation that emitted only placeholder markup; not one raw contained
  `<function=get_weather>`;
- leaves the #39056 implicit-end path (an offered call inside `<think>` with
  no `</think>`) parsing exactly as before — verified at parser level, sync
  and streaming.

### Class 2 is not covered by #50986, and only partly by #57553

Of 336 duplicate-call failures with raw generations kept:

- **86** contain a ``` fence — the shape [#57553](https://github.com/vllm-project/vllm/pull/57553) / #57541 addresses;
- **93** have a `<tool_call>` before `</think>`, i.e. quoted inside reasoning;
- the rest are unfenced quotations in ordinary content.

So fenced-example handling catches about a quarter of what we see. The
general case — the model showing the markup and then using it — needs the
parser to distinguish a quotation from an emission. Filing this so the two
classes are on the record separately; happy to supply raw generations for
either (fixtures are synthetic weather/file calls, nothing private).

Related: #39056 (opposite direction — calls inside `<think>` must not be
lost), #57541 / #57553 (fenced examples), #58105 (streaming loses calls when
the grammar admits ordinary-token delimiters), #54808 (`tool_choice`
`required`/named not enforced on chat completions for the XML parsers — a
grammar would have refused the out-of-set names).

AI assistance was used to investigate the code paths, build the measurement harness and draft this report; the human submitter reviewed it and ran everything described above on his own hardware.

| | default template | froggeric v22.5 |
|---|---|---|
| spurious extra calls, ordinary cases, thinking on | 5 / 1,400 | 7 / 1,400 |
| same, "show the block then call it" prompt, thinking on | 153 / 200 | 160 / 200 |
| out-of-set phantom names on that prompt (responses) | 90 / 200 | 142 / 200 |
| unbalanced `<tool_call>` markup (responses) | 109 / 3,600 | 178 / 3,600 |
| `tool_choice` named, pass | 190 / 400 | 315 / 400 |
| trailing-newline loss (whitespace case) | 55 / 400 | 31 / 400 |

The template genuinely helps named `tool_choice` and whitespace fidelity. It does not make the issue go away: quoted markup and emitted markup are byte-identical to the parser, so a template changes how often the model quotes, not what the parser does with a quote. The phantom names are each template's own placeholder — `function_name` on the default, `example_function_name` (272 spans) on v22.5 — the model echoes whatever example it is shown.
