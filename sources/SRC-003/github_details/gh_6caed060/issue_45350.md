# [Issue #45350] [Feature]: IndexCache support for DeepSeek V4

source: https://github.com/vllm-project/vllm/issues/45350
state: open | updated: 2026-09-23T01:05:30Z

## 正文

### Summary

Extend the existing IndexCache feature (currently only supported for DeepSeek-V3.2 / GLM-5 DSA models) to DeepSeek V4's c4a attention layers, which also use DSA lightning indexer with top-k token selection.

### Motivation

DeepSeek V4 uses a hybrid compressed attention architecture with two layer types:

```
- **c4a layers** (30 layers): Compressed KV + **DSA lightning indexer** (top-k=1024) + sparse attention
- **c128a layers** (31 layers): Heavily compressed KV, near-full attention (no indexer needed)
- **SWA layer** (1 layer): Pure sliding window, no indexer
```

The 30 c4a layers have the same DSA lightning indexer as V3.2, making them **directly amenable to IndexCache optimization** — skipping redundant top-k computation across layers by reusing cached `topk_indices`.

This is not theoretical — **vllm-ascend has already implemented and validated it**:


### Existing Implementation & Validation

**vllm-ascend PR**: [[Feature] IndexCache: reuse topk_indices across decode steps for DSA models (DeepSeek V4)](https://github.com/vllm-project/vllm-ascend/pull/9390) — **Merged** on 2026-05-25

**Performance (DeepSeek V4-Flash, Ascend 910B4, 32K input / 1K output)**:

| Metric | Baseline | IndexCache (freq=4) | Improvement |
|--------|----------|---------------------|-------------|
| Throughput (tok/s) | 1,423 | 1,554 | **+9.18%** |
| TTFT (ms) | 6,182 | 5,813 | **-5.97%** |
| TPOT (ms) | 186.4 | 171.8 | **-7.83%** |

**Accuracy (GPQA-diamond)**: −0.51 pt (within acceptable range)

### Technical Feasibility

The V4 model config confirms c4a layers have full DSA indexer support:

```json
// DeepSeek-V4-Pro config.json
{
  "index_topk": 1024,
  "index_n_heads": 64,
  "index_head_dim": 128,
  "compress_ratios": [128, 128, 4, 128, 4, 128, 4, ...]  // 30 layers with ratio=4 (c4a)
}
```

Key observations from the vLLM v0.22.0 codebase:

1. **V3.2 IndexCache is already implemented** in `deepseek_v2.py` (lines ~1009-1019), using `use_index_cache` / `index_topk_freq` / `index_topk_pattern` config fields
2. **V4's `DeepseekV4Indexer`** already uses `topk_indices_buffer` (shared across layers) — the buffer infrastructure is in place
3. **V4's `SparseAttnIndexer`** already writes `topk_indices_buffer` in both prefill and decode paths
4. **V4's `DeepseekV4MLAWrapper.forward`** already has the `if self.indexer is not None` check — the hook point for `skip_topk` is natural

**What's missing** (roughly ~65 lines of code):

| File | Change |
|------|--------|
| `deepseek_v4/nvidia/model.py` | Read `use_index_cache` config, compute `skip_topk` per layer, pass to MLA modules (~20 lines) |
| `deepseek_v4/amd/model.py` | Same as above for AMD path (~20 lines) |
| `deepseek_v4/attention.py` | Add `skip_topk` to `DeepseekV4MLAModules` dataclass + conditional skip in `DeepseekV4MLAWrapper.forward` (~15 lines) |
| Tests | E2E test for V4 with `use_index_cache=True` (~50 lines) |

### Layer Index Mapping

V4 has heterogeneous layer types — `index_topk_pattern` should map to the **sequence of c4a layers only** (not all 62 layers), consistent with vllm-ascend's approach:

```python
# From vllm-ascend PR #9390
indexer_seq_idx = sum(1 for r in compress_ratios[:layer_idx] if r == 4)
if pattern is None:
    skip_topk = max(indexer_seq_idx - 1, 0) % freq != 0
else:
    skip_topk = pattern[indexer_seq_idx] == "S"
```

For V4-Pro (30 c4a layers), `index_topk_freq=4` would keep ~8 F-layers and skip ~22 S-layers.

### Proposed API

Consistent with existing V3.2 IndexCache:

```bash
# Using index_topk_freq (uniform)
vllm serve deepseek-ai/DeepSeek-V4-Pro \
  --hf-overrides '{"use_index_cache": true, "index_topk_freq": 4}'

# Using index_topk_pattern (custom, for c4a layers only)
vllm serve deepseek-ai/DeepSeek-V4-Pro \
  --hf-overrides '{"use_index_cache": true, "index_topk_pattern": "FFSFSSSFSSFFF..."}'
```

### hjdongxuxu · 2026-08-23

Adding production data from a long-context deployment, in case it helps prioritise this.

```
**Setup**: DeepSeek-V4-Flash, 8×H20-3e, TP8 + EP, vLLM 0.25.0, DSpark speculative decoding,
`max-model-len 655360`, chunked prefill 8960, prefix caching on.
```

**Workload shape**: interactive agent traffic. Context P50 ≈ 55K, **P90 ≈ 280K, max 504K tokens**;
low concurrency (1 in-flight request 58% of the time, peak 7). This is the regime where the
lightning indexer's O(L²) cost dominates.

```
We locally patched in the cross-layer IndexCache gating for V4 (the mechanism already exists for
V3.2) and ran it in production for a full working day with `index_topk_freq=2`.
```

**Benchmark (182.7K-token corpus, cold prefill):**

| | before | after |
|---|---:|---:|
| TTFT | 25.2 s | **22.0 s (−12.7%)** |
| single-stream decode | 262.7 tok/s | 267.6 tok/s (unchanged/slightly up) |

**Production (2,482 real requests, one full working day, test traffic excluded):**

| | before (08-20) | after (08-21) |
|---|---:|---:|
| cold prefill rate (>150K effective input) | 6,356 tok/s | **8,074 tok/s (+27%)** |
| median TTFT, >150K effective input | 41.1 s | **26.1 s (−36%)** |
| cache hit rate | 95.6% | 96.7% |

**The gap between the two tables is the point**: our benchmark corpus is only 182K, but real
traffic reaches P90 280K. The indexer's share of prefill grows with context length, so
**a short benchmark systematically understates this optimisation**. For reference,
vllm-ascend measured −5.97% on a 6.2 s TTFT baseline (mid-length context); we see −36% at
250K+. If you benchmark this, please use a corpus at least as long as your target workload.

**Quality**: no regression across tool-calling, reasoning, long-form Chinese generation, and a
needle-in-a-haystack retrieval test at 10%/50%/90% depth in a 182K document (all forced cold
prefill so the indexer path is actually exercised). We kept `index_topk_freq=2` rather than 4 —
with the corrected cost model below, freq=4 buys only ~1.6 s more while doubling the quality
surface.

**One correction to the benefit model, in case others estimate this**: we initially predicted
−37%, reasoning that the indexer is ~74% of prefill (back-solved from DP8 vs TP8 timings) and
freq=2 removes half of it. Actual was −12.7% on the benchmark. The 74% figure means *"the part
that does not shrink under TP"*, which is **not** the same as *"time the indexer exclusively
owns"* — it runs on an aux CUDA stream, three-way overlapped with `wq_b + kv_insert` and the MLA
compressor. Skipping it only saves the excess over its parallel partners. **Corrected estimate:
the indexer is net ~25% of prefill recoverable by skipping.**

**Implementation note**: V4 needs one thing V3.2 does not. Only layers with `compress_ratio == 4`
carry an indexer, so the freq pattern must count over the *c4a ordinal*, not the raw `layer_id`:

```python
    def _c4a_ordinal(config, layer_id):
        ratios = getattr(config, "compress_ratios", None)
        if ratios is None or layer_id >= len(ratios) or ratios[layer_id] != 4:
            return None
        return sum(1 for r in ratios[:layer_id] if r == 4)
```

Everything else follows the existing V3.2 pattern. Shared layers keep the indexer module (the
checkpoint weights must still load) and skip only the *call*; they then fall through to the
existing `elif self.compressor is not None:` branch, which is exactly the desired
"everything except the indexer" path — no new branch needed. The gating is static per layer, so
cudagraph capture is unaffected.

Happy to share the full diff, benchmark scripts, or more workload data if useful.

### hjdongxuxu · 2026-09-23

Update since my comment above, and an offer.

**One month in production.** The gating has been running continuously at
`index_topk_freq=2` since Aug 20, and we have carried it forward across
0.25.0 -> 0.28.0 -> 0.29.0 -> 0.30.0rc2. That last part is the reason I am
posting again: we apply it as an out-of-tree patch at startup, and the anchor
points shifted twice during those upgrades. A silently mis-applied patch here
fails closed-ish -- the server starts fine and TTFT quietly returns to
baseline -- which is exactly the kind of thing that belongs upstream instead.

**I would like to turn this into a PR**, unless someone is already working on
it. The change is still small and confined to `deepseek_v4/attention.py`, and
it maps cleanly onto current main (`self.compress_ratio` and the per-layer
`topk_indices_buffer` are both already there, so only the gating is missing).

**New evidence on the freq default.** We later ran freq=3 in production and
rolled it back: the extra speedup was real but modest, while long-document
output quality degraded. freq=2 has been stable for a month. That is
directionally consistent with the accuracy drops reported at freq=4 on the
SGLang side (sgl-project/sglang#26274, and the forward-port in
sgl-project/sglang#32771), so for V4 it may be worth documenting 2 as the
recommended starting point rather than the 4 used for V3.2 / ATOM.

**Public accuracy numbers I plan to bring.** To stay comparable with the
SGLang work I will run the same suite -- CEval, AIME2025, GPQA Diamond -- for
off / freq=2 / freq=3 with speculative decoding disabled, and add **RULER at
16K and 128K**, which nobody has reported for this feature. Long-context
retrieval is the failure mode cross-layer top-k reuse actually risks, and the
short-form suites cannot see it. (Methodology note: AIME2025 is 30 questions,
so the freq=4 delta reported on the SGLang PR is a single question; I will
report avg@8.)

**Two questions before I open the PR**

1. *Config surface.* sglang#26274 adds `index_topk_freq` / `index_topk_pattern`
   to the V4 config, mirroring V3.2. Should vLLM do the same here -- i.e.
   reuse `use_index_cache` / `index_topk_freq` / `index_topk_pattern` exactly
   as V3.2 exposes them?
2. *Test bar.* Reviewers on the SGLang PR asked for a separate forward path
   when top-k is skipped, unit tests for the freq/pattern planning, and a
   registered e2e test mirroring `test_deepseek_v32_indexcache.py`. Happy to
   follow the same shape -- let me know what the equivalent expectation is
   here.

**Scope.** Everything above is SM90 (H20) with fp8 KV cache; production runs
with speculative decoding on, accuracy runs will have it off. No H200 / SM100
access, so validation there would help -- worth noting that sglang#32771 has
two reports of illegal memory access when IndexCache is combined with
HiSparse / CUDA-graph capture, which we have not hit on our stack. The change
is inert on DeepSeek-V4.1-Flash, whose `compress_ratios` contain no c4a layers.
