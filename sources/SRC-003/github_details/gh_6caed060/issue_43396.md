# [Issue #43396] CUDA illegal memory access in FP8 MoE moe_permute with cutlass backend at batch size 8192

## 正文

## Bug Description

vLLM crashes with `CUDA error: an illegal memory access was encountered` during FP8 MoE inference when the scheduled batch hits exactly 8192 tokens. The crash occurs in the CUTLASS MoE permutation kernel.

## Environment

```
- vLLM version: 0.17.1 (via `ghcr.io/llm-d/llm-d-cuda:v0.6.0`)
- GPU: NVIDIA H200 (140GB)
- Model: `RedHatAI/Qwen3-30B-A3B-FP8-dynamic` (128 experts, top-2 routing, compressed-tensors FP8)
- TP=1, single GPU
- `max_model_len=2100`, `enable_prefix_caching=True`
```

## Steps to Reproduce

1. Deploy Qwen3-30B-A3B-FP8-dynamic with vLLM v0.17.1
2. Send ~100 concurrent requests with `prompt_tokens=1000, max_tokens=1`
3. vLLM schedules 9 requests in one batch (8×1001 + 1×184 = 8192 total tokens)
4. Engine crashes on the first model execution step

## Scheduler State at Crash

From the dump:
```
total_num_scheduled_tokens = 8192
num_running_reqs = 17
num_waiting_reqs = 82
step_counter = 0  (first step after startup)
kv_cache_usage = 0.016
```

9 new requests scheduled, 8 with 1001 tokens each, 1 with 184 tokens. The last request got partial block allocation (`block_ids=([146, 147, 148])` = only 3 blocks vs 16 for the others).

## Analysis

The crash happens at `total_num_scheduled_tokens=8192` which is a CUDA graph capture boundary size (visible in the config: `cudagraph_capture_sizes: [1, 2, 4, 8, ..., 512]` with `max_cudagraph_capture_size: 512` and `compile_ranges_split_points: [8192]`).

The `permuted_idx` tensor in `moe_permute` appears to have out-of-bounds indices when processing FP8 quantized weights with the CUTLASS MoE backend at this specific batch size. The issue is in the FP8 scale indexing: `permuted_idx.clamp(max=n_token * topk - 1) // topk` produces indices that exceed `a1q_scale`'s first dimension.

## Workaround

Setting `--max-num-batched-tokens` to a value other than 8192 (e.g., 4096 or 16384) avoids the crash.

## Expected Behavior

vLLM should handle FP8 MoE models at any batch size without CUDA memory access errors.

### jshaofa-ui · 2026-05-22

## Proposed Solution: CUDA Illegal Memory Access in FP8 MoE at Batch Size 8192

### Root Cause
The crash occurs at `moe_permute_unpermute.py:90`:
```python
a1q_scale = a1q_scale[permuted_idx.clamp(max=n_token * topk - 1) // topk]
```

When `total_num_scheduled_tokens = 8192` (CUDA graph capture boundary), the last request gets partial block allocation. `permuted_idx` includes indices for partial block tokens that exceed `a1q_scale`'s first dimension → out-of-bounds CUDA access.

### Proposed Fix
**File**: `vllm/model_executor/layers/fused_moe/moe_permute_unpermute.py`

```python
def moe_permute(...):
    # ... existing code ...
    
    scale_indices = permuted_idx.clamp(max=n_token * topk - 1) // topk
    
    # FIX: Clamp to actual tensor size
    if a1q_scale is not None:
        max_scale_idx = a1q_scale.shape[0] - 1
        scale_indices = scale_indices.clamp(max=max_scale_idx)
        a1q_scale = a1q_scale[scale_indices]
```

### Key Changes
- `vllm/model_executor/layers/fused_moe/moe_permute_unpermute.py`: Add bounds checking for scale tensor indexing
- Add boundary validation with graceful fallback and warning log

Full solution: `solutions/vllm-43396-cuda-illegal-memory-access-fp8-moe-8192-fix.md`


### bbenshab · 2026-05-23

## Update: Crash also occurs in C++ `moe_permute` kernel during inference (not just `a1q_scale` indexing)

### Context

We're running **Qwen3-30B-A3B-FP8-dynamic** on H200 GPUs with PD disaggregation (separate prefill and decode pods). We applied a runtime `sed` patch to work around the Python-level `a1q_scale` OOB issue described above. That patch fixed the **startup crash during `profile_run()`**, but we're now hitting a **different crash path in the same function during actual inference**.

### Workaround applied (fixes startup crash)

We patch `moe_permute_unpermute.py` at pod startup before `vllm serve`:

```bash
_MOE_FILE=$(python3 -c "import vllm; print(vllm.__path__[0])")/model_executor/layers/fused_moe/moe_permute_unpermute.py
sed -i 's|a1q_scale = a1q_scale\[permuted_idx.clamp(max=n_token \* topk - 1) // topk\]|scale_idx = permuted_idx.clamp(max=n_token * topk - 1) // topk; scale_idx = scale_idx.clamp(max=a1q_scale.shape[0] - 1); a1q_scale = a1q_scale[scale_idx]|' "$_MOE_FILE"
```

This clamps `scale_idx` to the actual `a1q_scale` tensor size, preventing the Python-level OOB at line ~181. This fix resolves the crash during `profile_run()` → `_dummy_run()` at startup (large dummy batch for CUDA graph memory estimation).

### New crash: C++ kernel `torch.ops._moe_C.moe_permute` during inference

After applying the above patch, the server starts successfully and serves requests. However, under high concurrency (100 concurrent requests, ISL=1000, OSL=1000), the **prefill pod (TP=1)** crashes with the same illegal memory access, but this time inside the **C++ MoE permute kernel** — not the Python `a1q_scale` indexing:

### Summary

The proposed fix in this issue (clamping `scale_idx`) addresses one of two OOB paths. The second path is in the compiled C++ `_moe_C.moe_permute` kernel which also needs bounds checking for the same partial-block-allocation scenario.
