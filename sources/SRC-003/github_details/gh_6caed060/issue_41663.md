### 🐛 Describe the bug

## Summary

`intel/vllm:0.17.0-xpu` reproduces a `VLLM::Worker` general protection fault followed by `xe` BCS engine resets on a dual Intel Arc Pro B70 system when running Qwen3-30B-A3B with TP=2 and dynamic FP8 on Ubuntu 24.04.4 HWE kernel 6.17.

The same failure pattern also reproduces with our local source-built vLLM XPU image. This suggests the issue is not caused by our source build alone, but likely involves an interaction between the host stack, `xe` driver/firmware, PCIe topology, and vLLM XPU TP=2 worker initialization / ProcessGroupXCCL path.

A standalone XCCL/SYCL collective sweep passes on the same host, so this does not appear to be a generic oneCCL/SYCL collective failure.

## Hardware

- 2× Intel Arc Pro B70 32GB, Battlemage G31, device `8086:e223`
- Z890 motherboard with PCIe switch topology
- No XeLink between GPUs
- `p2p_access:0`
- Each B70 reports PCIe 5.0 x8 host link
- `ZE_AFFINITY_MASK=0,1` used for the two B70 GPUs

## Host stack

- OS: Ubuntu 24.04.4 LTS
- Kernel: `6.17.0-23-generic` HWE
- GPU driver: in-kernel `xe`
- GuC firmware: `70.44.1`
- GuC firmware version 70.49.4 has been mentioned in upstream contexts as a newer candidate; we have not yet tested an upgrade.

## Failure domains observed

We observed three separate failure domains while trying to make the source-built image start with `CCL_ENABLE_SYCL_KERNELS=1`.

### 1. BCS engine reset / Level Zero V2 copy-offload side effect

`UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` avoided the BCS engine reset in one worker-init canary, but did not fix the underlying vLLM/XCCL crash.

### 2. oneCCL topo allreduce / ProcessGroupXCCL path

The source-build crashed in:

```text
c10d::ProcessGroupXCCL::allreduce_impl
c10d::ProcessGroupXCCL::collective
c10d::ops::allreduce_XPU
```

`CCL_ALLREDUCE=ring` got past this stage, but performance collapsed and the next failure occurred later during compile.

oneCCL documents that for GPU buffers, `topo` is the default algorithm, and that algorithms other than `topo` copy GPU-buffer data to host and follow the specified CPU algorithm. That likely explains the large performance drop with `CCL_ALLREDUCE=ring`.

### 3. vLLM compile / XPU graph path

After bypassing the allreduce failure with `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1` and `CCL_ALLREDUCE=ring`, the next failure occurred during Dynamo/Inductor compile.

Adding:

```bash
--enforce-eager
VLLM_XPU_ENABLE_XPU_GRAPH=0
```

allowed vLLM to reach `HEALTH=200` and serve inference, but throughput was only ~0.5 tok/s in our smoke test. This is a debug path, not a usable workaround.

## Stable fallback on our current host

The only stable and usable config we found on this Ubuntu 24.04.4 / HWE 6.17 host is:

```bash
CCL_ENABLE_SYCL_KERNELS=0
CCL_TOPO_FABRIC_VERTEX_CONNECTION_CHECK=0
SYCL_UR_USE_LEVEL_ZERO_V2=0
CCL_ATL_TRANSPORT=ofi
CCL_ZE_IPC_EXCHANGE=pidfd
ZE_FLAT_DEVICE_HIERARCHY=COMPOSITE
ZE_AFFINITY_MASK=0,1
ONEAPI_DEVICE_SELECTOR=level_zero:*
VLLM_WORKER_MULTIPROC_METHOD=spawn
VLLM_XPU_ENABLE_XPU_GRAPH=1
```

Observed performance:

- ~29 tok/s single-stream
- ~240 tok/s at 16 concurrency
- ~362 tok/s at 50 concurrency

## Why this looks host-stack related

We are not claiming the exact root cause is known. However:

1. Intel's pre-built `intel/vllm:0.17.0-xpu` image reproduces the same failure pattern.
2. Adding `CCL_TOPO_FABRIC_VERTEX_CONNECTION_CHECK=0` removes the CCL topology warning but does not prevent the GP fault + BCS reset.
3. Standalone torchrun XCCL/SYCL collective sweeps pass on the same host.
4. The failure requires the vLLM TP=2 worker initialization / ProcessGroupXCCL context.
5. Our host differs from Intel's published `0.17.0-xpu` validation BOM, especially OS/kernel/KMD/firmware.

A public external report claims that a similar 2× Intel Arc Pro B70 + Qwen3-30B-A3B + TP=2 + FP8 setup using `intel/vllm:0.17.0-xpu` on Ubuntu 25.10 reaches high throughput. We have not reproduced that environment yet, so we treat this only as motivation for a host-stack A/B test.

We are preparing a separate Ubuntu 25.10 spare-disk test and will report back.

## Hardware behavior and safety

We observed BCS engine resets across multiple failed test runs. After each:

- The `xe` driver recovered the engine.
- GPU devices remained accessible.
- Temperatures returned to idle.
- No cascading errors were observed.
- A full reboot cleared all state cleanly.

Because BCS engine resets are not normal operation, we stopped repeated default Profile B testing on the current host stack.

## Related upstream / external signals

```
- Intel's `0.17.0-xpu` release notes say the container is validated on Intel Arc Pro B-Series Graphics and list the validation BOM as Ubuntu 25.04 + KMD 6.14.0 + oneAPI 2025.3.2 hotfix + PyTorch 2.10 + `vllm-xpu-kernels 0.1.4` + oneCCL 2021.15.7.8.
- oneCCL docs state that `CCL_ALLREDUCE=topo` is the default for GPU buffers, and that non-topo algorithms copy GPU-buffer data to host and use the CPU algorithm.
- Intel SYCL runtime docs state that the Level Zero V2 adapter is used by default on Xe2/Battlemage, and that `SYCL_UR_USE_LEVEL_ZERO_V2=0` selects the legacy adapter.
- `vllm-xpu-kernels` tracks ongoing work to make `torch.compile` the default execution path for XPU. This may be relevant to the later Dynamo/Inductor failure domain, but the primary C8/C8b failure happens earlier during worker initialization.
- There are similar multi-GPU Intel XPU reports in adjacent projects where single-GPU works but multi-GPU fails in SYCL/Level Zero cross-device paths. This may not be the same bug, but it suggests this class of issue is worth investigating.
```

By elimination, the root cause appears to be in one of:

- **PyTorch XPU memory manager** below the caching allocator layer
- **Level Zero V2 runtime** state corruption after failed XPU allocations
- **intel-compute-runtime** internal bookkeeping after engine reset events
- **xe kernel driver** persistent state after GuC firmware engine resets

The fact that only a full reboot recovers the working state — combined with `dmesg` showing xe engine reset events from `kwin_wayland` even during single-card baseline runs — suggests the issue is in a layer below PyTorch where state cannot be reset from userspace.

### marcorigodanzo · 2026-07-13

## Root cause identified via gdb + a working, low-cost mitigation

We were hitting this on the same hardware (2× Arc Pro B70, BMG G31, `8086:e223`, TP=2). After attaching gdb to the hung TP workers we can pin down the exact chain, and it turns out **the "broken pipe" / KVS errors are a downstream symptom, not the cause** — the real trigger is a **GPU page fault caused by oneCCL reusing a stale cached Level-Zero IPC handle**.

**TL;DR mitigation:** `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0` eliminates the hang at ~3% throughput cost (vs ~39% for disabling the whole ZE cache).

### Setup
```
- 2× Arc Pro B70 (Battlemage G31), TP=2, `p2p_access` present on this host (EPYC/ROMED8-2T)
- `torch 2.12.0+xpu` (native `ProcessGroupXCCL`, no IPEX / no `oneccl_bindings_for_pytorch`), oneCCL **2021.17**, vLLM 0.24, `--enforce-eager`
- Model: Qwen3.6-27B int4 (AutoRound)
- Already running the known env workarounds: `CCL_ENABLE_SYCL_KERNELS=0`, `CCL_ATL_TRANSPORT=ofi`, `CCL_ZE_IPC_EXCHANGE=sockets`, `CCL_TOPO_FABRIC_VERTEX_CONNECTION_CHECK=0`, `SYCL_UR_USE_LEVEL_ZERO_V2=0`
```

### Symptom
Under **concurrent** load with **large prompts** (5+ requests, ~13–26k tokens each) the TP=2 collective wedges: the worker never returns from `execute_model`, the scheduler times out on `shm_broadcast` (`mq.dequeue → TimeoutError`) and the engine dies with `EngineDeadError`. It reproduces in ~15–30s under a concurrent large-context soak.

### gdb backtraces of the hung workers

**Compute thread** (blocked forever in the collective):

```
#0  sched_yield()
```

### dmesg (correlated)
```
xe 0000:xx:00.0: [drm] Tile0: GT0: Engine reset: engine_class=ccs   # also seen: bcs
xe 0000:xx:00.0: [drm] Tile0: GT0:
        Faulted Address: 0x0000........
        FaultType: 0            # not-present
        FaultLevel: 4
        Fault response: Unsuccessful -ENOENT
```

### Root cause
oneCCL **caches opened Level-Zero IPC handles** (peer device pointers) to reuse them across collectives. Under vLLM continuous batching, activation buffers get **reallocated**, so a cached IPC handle ends up pointing at memory that is no longer mapped. The next collective's `copy_entry` runs a GPU copy against that stale address → **not-present GPU page fault** → `xe` engine reset → the Level-Zero event tied to that copy **never signals completion** → oneCCL's progress thread busy-waits in `ze_base_entry::is_event_completed()` forever → `ccl_executor::wait()` never returns → the allreduce (and the vLLM worker) hangs indefinitely.

### Mitigation + measurements
Soak at concurrency 10 with large contexts (same workload that faults in ~3 min with defaults):

| config | stable under load | single-stream throughput |
|---|---|---|
| default (IPC handle cache on) | ❌ page fault + hang in ~3 min | 3.88 tok/s |
| `CCL_ZE_CACHE=0` (whole ZE cache off) | ✅ 0 faults / 11 min | 2.36 tok/s (**−39%**) |
| **`CCL_ZE_CACHE_OPEN_IPC_HANDLES=0`** (only the opened-IPC-handle cache) | ✅ **0 faults / 10 min** | **3.77 tok/s (−3%)** |

Disabling *only* the opened-IPC-handle cache (re-opening the handle each collective, so it's always valid) removes the fault while keeping ~97% of throughput. This has been stable for us since.

### Suggested upstream direction
This looks like an IPC-handle-cache invalidation bug in **oneCCL** (`oneapi-src/oneCCL`): a cached opened IPC handle should be invalidated when the peer allocation backing it changes/frees, otherwise a reused handle faults. From the vLLM/torch-xpu side, an option would be to default `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0` for XPU TP (or document it) until oneCCL invalidates stale handles. Happy to provide full backtraces / repro if useful.

### 3. Critical Operational Rules & Traps

1. **`CCL_ENABLE_SYCL_KERNELS=0` Must Be Scoped to TP ≥ 2:**
   * Disabling fused SYCL collective kernels is mandatory on multi-card B70 to avoid the All-Gather CAT error during `profile_run`.
   * **CRITICAL TRAP:** If `CCL_ENABLE_SYCL_KERNELS=0` is passed when `TP=1` (`world_size=1`), oneCCL immediately **SEGFAULTS** inside `ProcessGroupXCCL::allreduce` during vLLM's startup handshake! Always gate this flag behind `if [ "$TP" -gt 1 ]`.
2. **`--enforce-eager` is Mandatory for TP ≥ 2:**
   * vLLM's XPU graph capture / Inductor compile path currently supports single-card execution only. Multi-GPU TP runs will crash during graph warmup if `--enforce-eager` is omitted.
3. **`TRITON_INTEL_DEVICE_ARCH=bmg` is Required:**
   * Under multiprocessing (`spawn`), Triton's automatic architecture detection frequently fails, returning `unknown` and crashing ZEBIN compilation (`std::invalid_argument: stoul`). Setting this variable forces the Battlemage target.
4. **Quantization Reality: GPTQ & AWQ Work Great — But Run Them on a Single Card (TP=1)!**
   * **Do NOT split a 27B/32B INT4 model across multiple cards (TP=2):**
     * A 27B–32B INT4 model (e.g. `JunHowie/Qwen3-32B-GPTQ-Int4`, `cyankiwi/Qwen3.8-27B-AWQ-INT4`) consumes only ~18–20 GB of VRAM. **It fits entirely onto a SINGLE 32 GB B70 card!**
     * Running GPTQ-Int4 on a single card (TP=1) with XPU graph capture delivers **53–70 tok/s** (with speculative decoding), and batch AWQ yields **~234 tok/s aggregate**.
   * **Why @stolk saw only ~9.3 tok/s on TP=2:**
     * Splitting an INT4 model across 2 cards (TP=2) with `--enforce-eager` and `CCL_ENABLE_SYCL_KERNELS=0` creates the worst possible trade-off: because INT4 compute per layer is already extremely fast, the non-accelerated oneCCL PCIe collective synchronization barrier across all 64 layers completely swamps the decode latency (the PCIe inter-card sync tax).
     * Furthermore, XPU graph capture is currently single-card only; running TP=1 unlocks full graph acceleration, whereas TP=2 forces eager execution.
   * **Rule of Thumb on B70:**
     * **INT4 (GPTQ, AWQ, AutoRound):** Run on **ONE card (TP=1)**! (Fits in 32 GB, zero PCIe sync tax, graph capture enabled, 50–70 tok/s).
     * **Multi-Card (TP=2 / TP=4):** Reserve TP for models that **actually exceed 32 GB VRAM**, such as 30B/32B models in **native FP8** or **BF16**, or for massive KV-cache context pools. (For example, `Qwen3-30B-A3B` FP8 on TP=2 achieves **~20.7 tok/s single-stream** and **145.3 tok/s aggregate decode** @ concurrency 8).
     * **NVFP4** is the only format that is fundamentally blocked, as it is proprietary Nvidia Blackwell hardware logic.
5. **TP=4 Greedy Decoding Sensitivity (Why `temperature > 0` is Required on TP=4):**
   * **The Mechanism:** Floating-point summation across 4 discrete PCIe cards without fused SYCL kernels is non-associative: $(A + B) + (C + D) \neq ((A + C) + B) + D$. In multi-card collective reduction, this introduces minor numerical jitter ($\approx 10^{-4}$) into the logits.
   * **Why Greedy (`temp=0`) Breaks:** Greedy decoding performs a strict `argmax(logits)`. When two top token candidates have near-identical logits, this tiny collective jitter flips the winner, triggering autoregressive drift into repetition loops or corrupted tokens.
   * **Why Sampling (`temp > 0`) is Rock-Solid:** Probabilistic sampling over the softmax distribution naturally absorbs this microscopic variance. In our 60-minute soak test at TP=4 (866 requests, up to 22k context), standard sampling (`temperature=0.6–0.7`, `top_p=0.95`) ran with zero corruption.
   * **Rule:** Always use sampling on **TP=4**; reserve **TP=1** or **TP=2** for strict deterministic/greedy decoding.
6. **Stagger Multi-Instance Starts:**
   * When bringing up multiple instances, start them sequentially and poll `/v1/models` for HTTP 200 before launching the next container to prevent host RSS saturation.
7. **Display Card Reservation (Desktop Workstations):**
   * On workstations where one card drives desktop displays, dedicated multi-card inference should select dedicated headless cards via `ZE_AFFINITY_MASK` (e.g. `ZE_AFFINITY_MASK=1,2,3` or `2,3`).

#### 1. `TRITON_INTEL_DEVICE_ARCH=bmg` is Obsolete on Upstream v0.27+ / v0.28.0

  ```c
    case sycl::ext::oneapi::experimental::architecture::intel_gpu_bmg_g31:
  #endif
  ```

#### 2. The Rationale Behind `MEM_UTIL=0.80` on TP=4 (Display GPU Headroom)
* In our launch template, `--gpu-memory-utilization` was set to `0.90` for TP=2 and `0.80` for TP=4. To clarify the root cause:
  * **Dedicated Headless Servers:** If all cards are pure compute devices (e.g. headless PCIe server or BMC console), **TP=4 can safely run at `0.88–0.90`**.
  * **Developer Workstations (Desktop/Display Headroom):** On workstations where GPU 0 (`card0`) drives monitors via KDE/GNOME/Wayland (~1.2–2.0 GB VRAM baseline), symmetric Tensor Parallelism forces all ranks to match the smallest available allocation. Attempting `0.90` on TP=4 attempts a massive KV allocation that exhausts remaining VRAM on GPU 0, triggering:
    `RuntimeError: level_zero backend failed with error: 40 (UR_RESULT_ERROR_OUT_OF_RESOURCES) at _allocate_kv_cache_tensors`.
  * **Guidance:** Lowering to `0.80` is strictly an accommodation to preserve ~2.5–3.0 GB headroom on the display GPU. For TP=2, selecting headless pairs (`ZE_AFFINITY_MASK=1,2`) bypasses GPU 0 entirely, allowing `0.90–0.94` utilization.
