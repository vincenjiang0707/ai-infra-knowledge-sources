## 正文

### Your current environment

- vLLM: main @ 2026-09-23 (`157bcb7c48`), plus in-flight DSpark pipeline-parallel patches (#56956/#56957 — none of them touch the connector code cited below)
- httpx 0.28.1 (`AsyncClient` default timeout: 5.0s)
- 8 × NVIDIA SM120 GPUs, single node
- Model: DeepSeek-V4-Flash with DSpark speculative decoding
- Deployment: PD disaggregation with `MooncakeConnector` (TCP transport); prefill PP2×TP2 (kv_producer), decode PP2×TP2 (kv_consumer) on the same node

### 🐛 Describe the bug

The decode-side Mooncake bootstrap **query** (`GET /query`) has a hardcoded 5-second timeout — httpx's library default — with no configuration knob and no retry. A single slow response permanently fails the request(s) that triggered engine discovery, and is fatal in the cold-start window.

**Code**: `_connect_to_prefiller_bootstrap` constructs `httpx.AsyncClient()` with no `timeout` argument:

https://github.com/vllm-project/vllm/blob/main/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py#L1883-L1908

No env var or connector config feeds this path. `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT` exists but only covers the abort-request path (`mooncake_connector.py:1324`-ish). Unlike the producer-side registration loop (which at least retries `httpx.ConnectError`), the query path has no retry at all: one timed-out `/query` → `handle_new_engine_id` gives up on the remote engine.

**Reproduction** (reliable on cold start):

1. Start a PD deployment; prefill TP0/PP0 hosts the `MooncakeBootstrapServer` in its process.
2. The first request arrives. The producer's first real prefill step performs extended CPU-side work — in our case Triton JIT compilation of two kernels (cold Triton cache), which holds the GIL for well over 5 seconds. The bootstrap server's event loop, running in the same process, cannot answer HTTP during that window.
3. The decode side's `GET /query` exceeds httpx's 5s default. The log shows the tell-tale empty message after the colon (`str(httpx.TimeoutException)` is empty):

```text
ERROR [mooncake_connector.py] Failed to connect to bootstrap server http://<prefill-host>:8998:
ERROR [mooncake_connector.py] Failed to find remote engine_id <engine-id> from bootstrap server http://<prefill-host>:8998
```

4. The triggering request fails even though the bootstrap server recovers a second later and would have answered a retry.

**Downstream failure semantics** (both bad, version-dependent):

- On our base, the failed query flows into `_handle_failed_recv`, and the scheduler's KV-failure reporting path then crashes the **entire decode EngineCore** on `assert req_id in self.requests` in `_update_from_kv_xfer_finished` ([scheduler.py:2899](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py#L2899)) — already tracked by #49089, #46240, #43226, #53049.
- On current main, `handle_new_engine_id` only logs and returns, so the request is left without terminal failure propagation — the semantics tracked by #55870.

**Why this is not covered by existing issues**: #55114 and #55729 report the same httpx-default-timeout defect on the **producer-side registration** path (`POST /register`); #55870 covers missing error propagation after bootstrap failures on an Ascend deployment snapshot (explicitly not reproduced on clean upstream). This report is about the **decode-side query path**, reproduced on current-main-adjacent code on NVIDIA hardware, with a concrete cold-start trigger. The assert crash itself is *not* re-reported here (see the list above).

### Suggested fix

1. Make the bootstrap query timeout configurable (e.g. `VLLM_MOONCAKE_BOOTSTRAP_QUERY_TIMEOUT`, mirroring `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT`) and/or raise the default well above 5s.
2. Add bounded retry with backoff to `/query` — transient unresponsiveness of the producer's rank-0 process during cold start (JIT compilation, large host-segment registration) is expected and self-recovering.
3. Ensure query failure produces a terminal, scheduler-visible request failure that does not kill the engine (see #55870 and the `_update_from_kv_xfer_finished` assert reports).
4. Consider one shared, configurable HTTP client helper for the registration and query paths so the two sides cannot drift apart again.

Happy to submit a PR for 1+2 (and 3 if the desired propagation semantics are agreed).

AI assistance was used in root-causing this issue and preparing this report.

### lucifer1004 · 2026-09-24

Follow-up root-cause detail on the trigger side. We identified via Triton cache forensics (per-config `TRITON_CACHE_DIR` timeline + TTIR diff of warmup vs serving entries) exactly which compilations stall the producer's rank-0 process in the cold-start window:

```
1. `ComputeGlobalTopkIndicesAndLensKernel` (DSv4 sparse attention): warmup keys pinned `topk_indices_stride == topk`, but C128A prefill passes views of the `c128a_max_compressed`-wide persistent buffer (physical stride ≠ logical width), and `token_to_req_indices`/`is_valid_token` arrive with per-batch pointer alignments from token-offset slicing.
2. `_prepare_dflash_inputs_kernel` (DFlash/DSpark): `BLOCK_SIZE = min(256, next_power_of_2(max_tokens_per_req))` is batch-dependent; warmup's tiny synthetic steps only cover the smallest buckets.
3. `_post_update_kernel` (V2 PP deferred post-update): the warmup added in #56956 passed an int64 `idx_mapping` while serving always builds int32 — fixed in #56957 (88cf3c68ed).
```

#58559 fixes 1 and 2. With those, the producer's first-step compile storm shrinks substantially, which reduces (but does not eliminate) the exposure window for the hardcoded 5s bootstrap query timeout reported here — the timeout/retry fix in this issue is still needed.
