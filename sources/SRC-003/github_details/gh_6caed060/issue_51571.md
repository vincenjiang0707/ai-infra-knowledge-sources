# [Issue #51571] [Bug]: Async MTP align mode reads accepted counts from mutable InputBatch rows

## 正文

### Your current environment

Source audit against the current vLLM `main` HEAD:

```text
commit: 83ad767eed3be3ee7f2df63be693bfaca5c7c922
checked: 2026-08-09
```

A native CUDA runtime reproduction has not yet been run against this commit. The runtime evidence below is from the equivalent vLLM-Ascend path; the latest upstream code-path finding is static and deterministic.

### Describe the bug

With all of the following enabled:

- async scheduling;
- MTP/speculative decoding;
- a hybrid Mamba/GDN model;
- `mamba_cache_mode="align"` (the default for hybrid models when prefix caching is enabled);

accepted-token counts produced by model iteration N are asynchronously copied into `InputBatch.num_accepted_tokens_cpu_tensor`. Before iteration N+1 consumes those counts, `_update_states()` removes/adds requests and runs `InputBatch.condense()`, mutating the same persistent row-indexed storage. `_prepare_inputs()` then synchronizes the copy and gathers previous-iteration counts through `prev_positions`, but it gathers them from the already-mutable `InputBatch` array.

Synchronization guarantees D2H completion; it does not preserve iteration-N request ownership for those rows. A wrong accepted count changes the Mamba/GDN state-copy offset and can produce repeated, dropped, or garbled tokens.

### Current `main` code path

1. The align postprocess passes the mutable InputBatch CPU tensor as the D2H destination:
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/gpu_model_runner.py#L1629-L1648

```
2. `postprocess_mamba_align_gpu()` performs a non-blocking copy into that tensor:
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/mamba_utils.py#L1190-L1243
```

3. On the next execution, `_update_states()` runs before `_prepare_inputs()`:
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/gpu_model_runner.py#L4292-L4343

4. `_update_states()` adds requests and condenses the persistent batch:
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/gpu_model_runner.py#L1550-L1561

```
5. New requests initialize their reused row to accepted count `1`, and `condense()` rewrites current per-row state:
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/gpu_input_batch.py#L485-L486
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/gpu_input_batch.py#L708-L817

6. Only after those mutations, `_prepare_inputs()` synchronizes and gathers old row positions from the mutable InputBatch:
   https://github.com/vllm-project/vllm/blob/83ad767eed3be3ee7f2df63be693bfaca5c7c922/vllm/v1/worker/gpu_model_runner.py#L2148-L2170
```

### Concrete example

Iteration N produced:

```text
previous row 11 -> request A -> accepted = 4
previous row 4  -> request B -> accepted = 3
```

After async remove/add/condense, iteration N+1 has:

```text
current row 0 -> request A -> previous row 11
current row 1 -> request C -> new request
current row 2 -> request B -> previous row 4

prev_positions = [11, -1, 4]
```

If mutable InputBatch row 11 has already been reset/reused to `1`, gathering from InputBatch produces:

```text
buggy:    [1, 1, 3]
expected: [4, 1, 3]
```

Request A then uses a state-copy offset that is three tokens too small.

### Why this is not #45100 or #43559

```
- #45100 fixed the equivalent async accepted-count race for **non-align** mode by keeping that path device-authoritative. Its implementation intentionally leaves align mode on the synchronized CPU path because align preprocessing consumes CPU-side counts. The ownership problem above remains in that excluded branch.
- #43559 and its follow-up fixes address MTP + prefix-cache chunk/block alignment and poisoned cached Mamba state. This issue concerns previous-iteration accepted-count ownership across async InputBatch row mutation; it can corrupt the state-copy offset even when cached chunk boundaries are correct.
```

### Cross-backend runtime evidence

The same state-mapping failure was reproduced on the vLLM-Ascend runner, which follows this vLLM model-runner/InputBatch contract:

```
- issue and controlled reproduction: https://github.com/vllm-project/vllm-ascend/issues/13863
- main fix: https://github.com/vllm-project/vllm-ascend/pull/13864
- release fix: https://github.com/vllm-project/vllm-ascend/pull/13865
```

Observed controlled stress results there:

```text
unfixed accepted-count ownership: intermittent corrupted outputs
independent snapshot/remap:        512/512 correct at 98.82% peak KV usage
```

This is supporting evidence for the shared software-state diagnosis, not a claim that the latest CUDA `main` runtime has already been reproduced on GPU.

### Expected behavior

Previous-iteration accepted counts must remain indexed by the previous iteration until they are remapped through `prev_positions`. Current InputBatch row mutation must not overwrite or race with that historical data.

### Suggested fix

Use the runner-owned `self.num_accepted_tokens.cpu` buffer as the previous-iteration snapshot for async scheduling:

1. For async postprocess, copy accepted counts into the independent runner CPU buffer instead of InputBatch.
2. After the existing event synchronization, gather the snapshot through `prev_positions`.
3. Initialize new requests (`prev_position == -1`) to `1`.
4. Write the remapped current-row values back to InputBatch.
5. Preserve current upstream InputBatch ownership for non-async scheduling, where `condense()` must move accepted counts with current requests.

This reuses the existing `CpuGpuBuffer`, D2H/H2D traffic, and event synchronization; it should not allocate KV cache or require a new synchronization point.

### CubeLander · 2026-09-24

Additional Ascend-side runtime evidence for the previous-row ownership problem described here (not a reproduction on current CUDA main).

### Tested environment

- Qwen3.5-35B-A3B, BF16, Ascend 910B2, native TP2.
- vLLM 0.25.1, commit `752a3a504485790a2e8491cacbb35c137339ad34`.
- vLLM-Ascend 0.25.1rc1, commit `9bf964cb4b87c8cd0d6852c41a55b3c29711fa95`.
- torch-npu 2.10.0.post2; CANN 9.0.1.
- Async scheduling, prefix caching, Mamba `align`, MTP with two speculative tokens, eager execution; max sequences 4, query budget 4096, context limit 262144, explicit 8 GiB KV cache per rank.
- The native control used a compatibility adapter for the pinned vLLM/Ascend Mamba-postprocess ABI. This adapter was identical in the failing and repaired MTP runs; no separated-expert implementation was used in that control.

### Bounded functional results

The test placed `cobalt-seven-42` in the middle of a synthetic chat history and requested only that code, using the native nonthinking chat template, temperature 0 and normal EOS handling. It sent cold/warm requests at 4097 and 8193 prompt tokens, followed by four concurrent requests at 4100, 4131, 4162 and 4193 tokens.

| Configuration | Exact retrievals |
|---|---:|
| Native TP2, MTP disabled | 8/8 |
| Native TP2, MTP2, original feedback ownership | 7/8 |
| Native TP2, MTP2, isolated previous-order feedback | 8/8 |

The failing MTP run returned `cobalt-seven-7-42` on one concurrent request. At the divergence, `7` exceeded `4` by 0.75 logit. With MTP disabled or feedback isolation applied, the corresponding correct digit had approximately 99.999% probability.

The local repair redirected postprocessed D2H feedback into independent host storage, waited on the existing completion event, and preserved previous-row order until remapping. Crucially, an empty previous-request map must initialize counts to 1: our first incomplete repair omitted this boundary, fixed the concurrent cases but caused early EOS on a warm request. Adding that initialization restored all eight results. APC-adjusted state-selection counts were preserved, not replaced with raw sampler progress.

This independently supports the snapshot/remapping approach in #51599. It is a small Ascend regression fixture, not validation of that PR's exact diff, current CUDA main, or general model quality. We also recognize the Ascend fix history in vllm-project/vllm-ascend#13864; these pinned-runtime results should not be interpreted as a regression on current Ascend main.
