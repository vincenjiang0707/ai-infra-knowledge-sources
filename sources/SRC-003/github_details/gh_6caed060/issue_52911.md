## 正文

## Motivation.

> Continue working on phase one: https://github.com/vllm-project/vllm/issues/41820.

DeepSeek-V4 introduces CSA (Compressed Sparse Attention, `compress_ratio=4`), HCA layers, and a large MoE backbone. A side-by-side trace comparison of the vLLM decode path against vLLM-ATOM on ROCm shows that vLLM still leaves measurable performance on the table. The gaps cluster into three areas:

1. **Unfused mHC kernels.** vLLM runs `mhc_post` and `mhc_pre` as separate kernels, and `mhc_pre_big_fuse` + `add_rmsnorm_quant` as two kernels, while ATOM fuses each pair into a single kernel (`mhc_fused_post_pre` and `mhc_pre_big_fuse_rmsnorm`). Every extra kernel launch on the decode critical path costs launch latency and cache/register thrash.
2. **Serial execution where overlap is possible.** ATOM forks auxiliary HIP streams to run compressor GEMMs (CSA pre-attention), SWA KV insertion (HCA), and the MoE router/shared experts concurrently with the main stream. vLLM executes all of these serially.
3. **Slower attention support kernels.** ATOM replaces the vLLM CSA top-k selection kernels and the post-attention batched GEMMs (`torch.mm` + `manual_unroll`) with dedicated optimized kernels (e.g., `batched_gemm_bf16_kernel`).

An earlier attempt at closing gap #2 — PR #51794, which enables three-stream overlap for CSA pre-attention — is currently a draft: the overlapped region itself is faster when there is no bubble, but some ranks see a much slower tail all-reduce due to inter-rank latency jitter. The un-optimized kernels running in the parallel streams contend for hardware resources and desynchronize ranks. This suggests the correct order of work is: **replace the kernels with ATOM's optimized versions first, then enable stream overlap on top of them.**

## Proposed Change.

Port the ATOM-optimized decode path into vLLM's ROCm DeepSeek-V4 implementation, using the ATOM trace as the reference for each change. The work is organized per module:

### CSA:

# DeepSeek-V4 CSA (C4) TP8 All-Reduce Jitter Report

## 1. Setup

| Item | Value |
| --- | --- |
| Host | `gbt350-odcdh1-b10-1` |
| Model / layer | DeepSeek-V4 CSA, compress ratio = 4 (sparse decode path) |
| Parallelism | TP=8 (one Kineto Chrome trace per rank) |
| vLLM | `0.28.1rc1.dev199+g7c5dc571c` |
| GPU | gfx950-class (256 CUs per device in the trace header), HIP timestamps |
| Profiler | PyTorch / Kineto `pt.trace.json`, `displayTimeUnit: ms` (event `ts` / `dur` are **microseconds**) |

Traces:

- `dp0_pp0_tp0_dcp0_ep0_rank0.1788336732216461752.pt.trace.json` … `rank7`

Observed HIP streams on every rank:

- **Stream 4**: main compute stream (fused GEMM, CSA topK, sparse MLA, and the CSA all-reduce)
- **Streams 1 and 3**: CSA side streams (additional GEMM / indexer work)
- **Stream 0**: copies

There is **no RCCL/NCCL `all_reduce` GPU kernel** in these traces. Tensor-parallel reduction is the AITER custom kernel `aiter::cross_device_reduce_2stage<bfloat16, 8, false>`.

## 2. Methodology

Each rank trace contains **six** long `execute_context_0(0)_generation_8(8)` decode windows. This report uses **decode step index 2** (0-based; skip first two as warmup-ish, skip the tail). Rank 0’s CPU annotation for that step is used as a **shared HIP time window** so all eight ranks contribute the same physical step:

```
- Window start `t0 = 5368943993187.777 µs`
- Window duration `30.703 ms` (rank-0 annotation)
```

Inside that window every rank has **57** `_sparse_attn_decode_gfx950_partial_kernel` occurrences. A C4 CSA layer is defined as:

1. Main-stream fused GEMM (`mhc_*sqrsum*` / `_gemm_a8w8_blockscale_*` / CK `kernel_gemm_xdl_*` / `Cijk_*`)
2. CSA indexer topK (`radix_topk_one_block_kernel`, `_compute_topk_lens_kernel`, `_pack_global_topk_ragged_kernel`) — **not** MoE `topkGatingSoftplusSqrt`
3. Sparse MLA (`_fused_kv_compress_norm_rope_insert_sparse_attn`, `_sparse_attn_decode_gfx950_partial_kernel`, `_sparse_attn_decode_reduce_kernel`)
4. The **first** `cross_device_reduce_2stage` whose start is at or after that MLA (attn TP all-reduce, not the later MoE/MLP reduce)

28 of the 57 sparse-attn occurrences include indexer topK in the layer window. The other 29 are treated as incomplete splits at the window edge or layers without the indexer sequence in-range. **Three complete C4 layers** are sampled: **2 (early), 30 (mid), 56 (late)**.

Metric definitions (all values in **µs**):

| Metric | Definition |
| --- | --- |
| AR start | GPU kernel `ts` of `cross_device_reduce_2stage` |
| Arrival gap | `AR_start_rank − min_over_ranks(AR_start)` for that layer |
| AR kernel time | kernel `dur` (includes intra-kernel spin-wait on rank signals) |
| Idle before AR | `AR_start − previous_kernel_end` on the **same stream** as the all-reduce |
| Fused GEMM / topK / MLA (main) | sum of matching kernel durations on stream 4 between the previous CSA all-reduce and this one |
| GEMM all streams | same GEMM sum across streams 1/3/4 (side-stream extra work) |
| Overlap | time overlap of GEMM/topK/MLA on a **different** stream with the all-reduce |

Interpretation used below:

```
- A **large arrival gap** is rank-to-rank **jitter** (compute skew or launch skew).
- An **early rank with a long AR `dur`** is spinning inside the 2-stage reduce waiting for late ranks.
- **Longer main-stream GEMM / topK / MLA** on late ranks is compute-side skew and a CU-contention / work-imbalance signal. Overlap of those kernels with the all-reduce would be direct CU contention during the collective.
```

There is **no GPU bubble** on the all-reduce stream. Overlap of side-stream GEMM/topK/MLA with the all-reduce is **0 µs** in all three layers (side work finishes before the collective starts).

Observed relationships (qualitative, all three layers):

```
1. **Arrival gap ≈ AR_dur_early − AR_dur_late.** Finish times of `cross_device_reduce_2stage` line up across ranks. The extra duration on early ranks is intra-kernel wait for the straggler, not extra reduction work.
2. **Idle before the all-reduce is not the jitter source.** Stream 4 is busy up to the AR launch (previous kernel is fused/CK GEMM).
3. **Late arrival tracks longer main-stream kernels.** On layer 2, rank 4’s main fused GEMM is 22 µs longer than rank 5; MLA is 3.6 µs longer; topK is 9.4 µs longer. That is the same order as the 60 µs gap when summed with other uncategorized kernels in the layer.
4. **Side-stream GEMM adds ~38–42 µs** (`gemm_all − gemm_main`) but does **not** overlap the all-reduce. Direct CU contention *during* the collective is not visible in these three layers. CU contention / imbalance is visible **before** the collective: the same fused GEMM / topK / MLA kernels run longer on straggler ranks, which is consistent with CU (and/or cache/NoC) interference from multi-stream CSA, or with rank-local work variation.
5. **Who is late is not a fixed rank.** Layer 2 straggler is rank 4 (rank 5 earliest). Layers 30 and 56 stragglers are ranks 7/6 (rank 3 earliest). Jitter rotates; it is not a single dead GPU.
```

## 5. Conclusions

For this TP8 decode step, CSA C4 all-reduce behavior is dominated by **arrival jitter from main-stream compute skew**, not by a stream-idle gap and not by kernels overlapping the collective:

- The custom all-reduce payload is about **11–13 µs**.
- Rank arrival spread is **60–68 µs** on the three sampled C4 layers, so most of the visible AR kernel time on early ranks is **wait**.
- Longer fused GEMM, CSA topK, and sparse MLA on the late ranks explain why those ranks arrive late (**CU contention / compute imbalance before the collective**).
- Multi-stream CSA GEMM on streams 1/3 is real, but in these samples it completes before `cross_device_reduce_2stage` and does not stretch the collective via concurrent CU use.

Practical implication: shrinking CSA C4 all-reduce wall time on this trace is less about RCCL/AITER payload tuning and more about **tightening per-rank main-stream GEMM/topK/MLA time and reducing multi-stream CU interference that lengthens those kernels**. Once arrivals match, the collective itself is already in the low-teens of microseconds.

## 6. Caveats

- Only one decode step and three C4 layers are tabulated; other steps can differ.
- Layer index is the N-th sparse-MLA → all-reduce pair inside the shared window, not a Hugging Face layer id.
- HIP clocks are treated as comparable across ranks on one node; gaps of tens of microseconds are large compared to typical timestamp noise and are internally consistent with AR finish alignment.
- MoE topK and the second `cross_device_reduce_2stage` per transformer block are excluded by design.
