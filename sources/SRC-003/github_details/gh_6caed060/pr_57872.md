## 正文

## Purpose

Implement encoder-only Prefill for DeepSeek-V4.1-Flash P/D serving with the direct `MooncakeConnector`. This work builds on the asymmetric P/D proposal in RFC #57383 and the full-prompt, cache-hit-replay design in RFC #57738: P encodes the whole prompt through L0-L19 and produces the L20 Main KV/Indexer K, while D replays the adopted cache-hit tail through the full target and samples the first token. RFC #57738 analyzes NIXL pull as its initial path; this PR contributes a Mooncake-specific handoff and credits both RFCs for the design.

The initial Mooncake implementation adds the execution boundary, zero-token P completion, an explicit transfer profile, and connector readiness and region checks. H20 P/D integration checks and TTFT measurements are reported below. DSpark and CUDA graphs are not yet supported in this path; broader validation are planned.

## Implementation

```
- Add opt-in `KVTransferConfig.dsv41_encoder_only_prefill` on dedicated Mooncake producer and consumer roles. Keep full target weights on P in this first change; weight omission is separate work.
- On P, run L0-L19 normally, execute the L20 pre-mix and canonical compressor/Main-KV/Indexer-K writes, and skip L20 attention/FFN, L21-L39, final norm, LM head, sampling, and DSpark.
- Complete a cache-only P request after its full prompt is consumed, with no generated token. Each P worker returns an event-backed output; its executor synchronizes the GPU event before the scheduler may mark Mooncake blocks sendable. The Mooncake proxy sends `cache_only` and the shared `transfer_id`; incomplete and aborted requests remain non-sendable. D waits for Mooncake's transfer completion before replay.
- Select transferable groups from V4.1's configured Main-KV source and Indexer-K owner layer IDs. Fail if a required group is absent, mixed with D-local state, or duplicated. Bounded-replay SWA, compressor continuation, and draft groups remain local. Mooncake also rejects mismatched producer/consumer registered region sets.
- Restrict the first supported path to direct `MooncakeConnector` (not `MooncakeStoreConnector`), NVIDIA, MRV2, PP=1, no PCP or microbatching, bounded replay with a 128-token window, the 40-layer V4.1-Flash topology ending its global sources at L20, text-only requests, and no prompt logprobs. P currently requires `--no-async-scheduling` because async output placeholders do not yet model zero-token completion. D has a DSpark window check, but DSpark and CUDA graphs are not supported in this initial configuration.
```

Enable the new option in both server roles:

```json
{"kv_connector":"MooncakeConnector","kv_role":"kv_producer","dsv41_encoder_only_prefill":true}
{"kv_connector":"MooncakeConnector","kv_role":"kv_consumer","dsv41_encoder_only_prefill":true}
```

Use the existing Mooncake proxy for these roles and pass `--no-async-scheduling` to P. The proxy's `cache_only` marker does not change conventional Mooncake requests when the option is off.

## Validation

### Environment and A/B setup

- Image: vllm/vllm-openai:nightly-0961bbae2894d574be790d219651824eb199318e.
- Hardware: two nodes with 8 NVIDIA H20 GPUs each; P used one 8-GPU node and D used the other.
- Baseline: the fixed nightly above.
- Candidate: the same fixed nightly with PR head `b576413489` applied as a runtime source overlay.
- Both arms included the same consumer-side release-only Mooncake pull fix now present in `760d90833e`. The baseline therefore was not a completely unmodified nightly. This fix is required because bounded replay can discard a short remote hit while Mooncake still has a release-only pull; an empty pull must release P blocks without reporting a receive completion to a D request that never entered `WAITING_FOR_REMOTE_KVS`.
- Baseline and candidate were deployed in fresh pods with separate caches. Runtime source hashes were checked against the prepared source bundles.

### Server configuration

Both roles used MRV2 (`VLLM_USE_V2_MODEL_RUNNER=1`), TP=1, PP=1, DP=8, expert parallelism, bounded replay, synchronous scheduling, no speculative decoding, and CUDA graphs disabled:

```text
vllm serve /data00/models/DeepSeek-V4.1-Flash
  --served-model-name deepseek-v4.1-flash
  --trust-remote-code
  --tokenizer-mode deepseek_v41
  --dtype bfloat16
  --kv-cache-dtype fp8_ds_mla
  --block-size 64
  --tensor-parallel-size 1
  --pipeline-parallel-size 1
  --data-parallel-size 8
  --enable-expert-parallel
  --all2all-backend deepep_high_throughput
  --moe-backend humming
  --linear-backend humming
  --attention-backend FLASHMLA_SPARSE_DSV41
  --no-async-scheduling
  --enable-prefix-caching
  --swa-bounded-replay
  --no-disable-hybrid-kv-cache-manager
  --max-model-len 33792
  --max-num-seqs 8
  --gpu-memory-utilization 0.90
  --safetensors-load-strategy lazy
  --api-server-count 1
  --compilation-config '{"cudagraph_mode":"NONE"}'
```

P used `--max-num-batched-tokens 8192` and the `kv_producer` Mooncake role. D used `--max-num-batched-tokens 2048` and the `kv_consumer` role. Both used the following role-specific `--kv-transfer-config`; the baseline omitted only `dsv41_encoder_only_prefill`:

```json
{"kv_connector":"MooncakeConnector","kv_role":"kv_producer","kv_load_failure_policy":"fail","kv_buffer_device":"cuda","kv_connector_extra_config":{"mooncake_protocol":"rdma","device_name":"mlx5_1,mlx5_2,mlx5_3,mlx5_4"},"dsv41_encoder_only_prefill":true}
{"kv_connector":"MooncakeConnector","kv_role":"kv_consumer","kv_load_failure_policy":"fail","kv_buffer_device":"cuda","kv_connector_extra_config":{"mooncake_protocol":"rdma","device_name":"mlx5_1,mlx5_2,mlx5_3,mlx5_4"},"dsv41_encoder_only_prefill":true}
```

Candidate P and D both set the new option, and its proxy added `cache_only=true` to P requests. `NCCL_IB_DISABLE=1` was set for node-local DP/EP process groups to avoid this NCCL version's virtual GPU-to-NIC topology failure; Mooncake continued to use RDMA between P and D.

DSpark and CUDA graphs are currently unsupported in this Mooncake encoder-only P/D configuration. DSpark was excluded from the measurements because this nightly's speculative cache-group numbering did not match the non-speculative producer. CUDA graphs were disabled in both arms because the nightly's DeepEP high-throughput dispatch performs a CPU count synchronization during capture. Future work will validate DSpark correctness and draft acceptance, CUDA graph execution, full model quality, and additional TP/PP topologies before expanding the support boundary.

### Correctness and benchmark

The correctness corpus contained 20 fixed, temperature-zero completion requests covering short prompts, 127/128/129-token boundaries, 4K/8K/8K+1/16K/32K prompts, and repeated prefixes. All 20 requests completed in both arms. Output text was exactly equal for 18/20 cases; the two differences were generation wording rather than a candidate semantic regression (both math outputs answered 391, and the candidate answered the Chinese capital prompt correctly where the baseline did not). This is a bounded integration check, not a replacement for a full model evaluation.

Performance used `vllm bench serve` through the same P/D proxy:

```text
--backend vllm
--dataset-name random
--random-input-len {4096,8192,16384,32768}
--random-output-len 1
--random-range-ratio 0
--num-prompts 32
--request-rate 0.2
--max-concurrency 4
--temperature 0
--ignore-eos
```

Each length first received 8 disjoint-seed warmup requests, followed by 32 measured requests. A/B used identical measurement seeds; each length used a different seed. P metrics confirmed zero prefix-cache hits and zero preemptions during all measured intervals.

| Input | Baseline Mean TTFT | Candidate Mean TTFT | Mean reduction | Baseline P99 TTFT | Candidate P99 TTFT | P99 reduction |
|---:|---:|---:|---:|---:|---:|---:|
| 4K | 1,597.54 ms | 970.32 ms | 39.26% | 2,494.57 ms | 1,371.39 ms | 45.02% |
| 8K | 3,246.51 ms | 1,757.22 ms | 45.87% | 5,359.65 ms | 2,815.44 ms | 47.47% |
| 16K | 7,124.47 ms | 3,383.92 ms | 52.50% | 10,856.65 ms | 5,279.80 ms | 51.37% |
| 32K | 20,626.11 ms | 8,391.67 ms | 59.32% | 21,579.17 ms | 11,100.91 ms | 48.56% |

Both arms completed all 128 measured requests and all 32 warmup requests with no failures, engine crashes, tracebacks, preemptions, or pod restarts. P99 has only 32 samples per length and should be treated as an observation from this run. This test measures fixed-rate TTFT, not maximum throughput, and does not cover DSpark or CUDA graphs.

### GSM8K accuracy

EvalScope 1.11.1 ran 200 zero-shot GSM8K samples per arm with batch size 8, temperature 0.2, top_p 0.95, seed 42, max_tokens 65536, and reasoning_effort high. Both arms used fresh pods and separate caches. The accuracy deployment increased max model length to 131072 for the generation limit; all other server settings above were unchanged.

| Arm | Correct | Accuracy | Succeeded | Errored |
|---|---:|---:|---:|---:|
| Baseline | 195/200 | 97.5% | 200 | 0 |
| Candidate | 193/200 | 96.5% | 200 | 0 |
| Delta | -2 | -1.0 pp | 0 | 0 |

Pairing by dataset sample index gave 193 samples correct in both arms, 5 wrong in both, 2 correct only in the baseline, and 0 correct only in the candidate (exact two-sided McNemar p=0.5). The two discordant outputs made alternate choices on ambiguously worded problems: "two times older" and "10 times more." Their responses addressed the correct prompts; no response mix-up, request failure, engine error, traceback, or pod restart was observed. This single stochastic run does not establish a statistically significant accuracy regression, but the observed -1.0 percentage-point delta is reported rather than treated as exact equivalence.

## Relationship to other work

Open PRs were checked by RFC number and by Mooncake/encoder-only/cache-only keywords. No other open PR implements this V4.1 execution boundary on direct Mooncake P/D. #55654 optimizes DSpark context-KV insertion, #56437 validates PP sharing, and #56227 supplies the merged bounded replay foundation; they are complementary, not duplicates.

If an RFC author (#57383/#57738) or maintainer lands a shared or NIXL-first implementation, this Mooncake path can be rebased/stacked on that work, retaining its connector-specific transfer profile, readiness handling, tests, corner cases, and eventual measurements. I am happy to coordinate that split rather than maintain duplicate generic model/scheduler code.
