# [PR #57632] [DSpark] Capture the full draft step as a decode CUDA graph

## 正文

## Purpose

Even when the query forward replays a FULL CUDA graph, the DFlash/DSpark draft step still leaves two pieces of per-step host work on the decode hot path:

1. **Context K/V precompute** (`precompute_and_store_context_kv`) runs eagerly outside the graph, because the context shape varies from step to step.
2. **Attention metadata build** runs eagerly on every step solely to refresh the SWA builder's persistent GPU buffers; on the replay path, the built metadata itself is discarded.

On uniform decode, both operations have fixed shapes and are capture-safe. This PR therefore captures the entire draft step (context K/V precompute, metadata refresh, query forward, and Markov sampling) as a single decode-step CUDA graph.

## Validation

Capturing the draft step must not change the speculator's proposals. The checks below therefore compare acceptance and accuracy against this branch's parent commit (`c723a831a8`), and serving performance against current main, with everything else held fixed.

### Setup

- **Hardware / software:** 4× GB200, FlashInfer 0.6.18.post1, `VLLM_USE_V2_MODEL_RUNNER=1`.
- **Model:** DeepSeek-V4.1-Flash (`dba1be0a40aa45a94ad051997016db3960a90277`).
- **Speculative decoding:** DSpark with 5 speculative tokens and full decode CUDA graphs.
- **Topologies:**
  - **DEP4:** MegaMoE backend with adaptive verification.
  - **TP4:** auto MoE backend with fixed verification.

### Acceptance and GSM8K accuracy

Each pair runs the full GSM8K test set (1,319 identical 5-shot completion prompts) with greedy decoding, concurrency 32, a 1,024-token output cap, and strict answer extraction.

Acceptance length is read from the engine's `vllm:spec_decode_*` counters over the whole run for DEP4. For TP4, it is aggregated from the engine's periodic SpecDecoding log windows over the steady state; the same method is used on both sides of each pair.

| Configuration | Acceptance length, incl. bonus (parent → PR) | GSM8K (parent → PR) |
| --- | ---: | ---: |
| DEP4 | 3.411 → **3.385** | 1234 → 1227 / 1319 (93.56% → 93.03%) |
| TP4 | 3.471 → **3.486** | 1227 → 1223 / 1319 (93.03% → 92.72%) |

- The acceptance deltas are within ±1% and have opposite signs across the two topologies, and the per-position acceptance curves coincide. The captured draft step therefore does not change what the drafter proposes.
- The GSM8K deltas are run-to-run noise: two repeats of the same DEP4 parent configuration scored 0.9219 and 0.9356 (an 18/1319 spread), which is wider than any delta in the table.
- These results establish parity with the parent; they do not claim an accuracy improvement.

### Serving benchmark

TP4, DSpark (5 speculative tokens, synthetic acceptance length 5.5), random dataset with 128 input / 1,024 output tokens. **Base** is `826e300cde` (main) and **PR** is `12b4c35c1b` (the same commit plus this PR's diff). CPU/step is the host time per engine step, measured with an injected per-step probe.

| Concurrency | CPU/step | TPOT | ITL |
| ---: | ---: | ---: | ---: |
| 1 | 6.80 → 4.53 ms  | 1.29 → 1.07 ms (−17.1%) | 7.04 → 5.87 ms (−16.6%) |
| 8 | 6.58 → 4.43 ms  | 1.87 → 1.84 ms (−1.6%) | 9.94 → 9.94 ms (0.0%) |
| 32 | 7.00 → 4.54 ms  | 2.95 → 2.92 ms (−1.0%) | 14.74 → 14.65 ms (−0.6%) |
| 64 | 7.16 → 4.64 ms | 4.05 → 3.93 ms (−3.0%) | 20.21 → 20.25 ms (+0.2%) |

The PR cuts host time per step by about a third at every concurrency. At concurrency 1 the step is host-bound, so this carries through to a ~17% lower TPOT and ITL; at higher concurrency the GPU dominates and latency is roughly unchanged.
