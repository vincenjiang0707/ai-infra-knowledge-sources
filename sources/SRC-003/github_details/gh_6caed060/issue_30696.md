## 正文

### 🚀 The feature, motivation and pitch

(co-authored with @sallyom and Claude)

In replicated vLLM deployments behind a load balancer, the load balancer has no visibility into EPLB (Expert-Parallel Load Balancing) state when making routing decisions. EPLB dynamically replicates heavily-used experts across EP ranks to balance load, and instances experiencing high expert load imbalance or active rebalancing operations have degraded capacity. Without metrics exposing this state, load balancers cannot avoid routing traffic to struggling instances, leading to suboptimal performance and increased tail latencies.

EPLB already tracks and logs this information to stdout when `--eplb-log-balancedness` is enabled:

```
EPLB step: 2500: avg_tokens=1024, max_tokens=2048, balancedness=0.5000
```

But these are obviously not queryable by load balancers. This proposal exports the same data that's currently logged as Prometheus metrics, enabling intelligent load balancing decisions based on instance health.

Note - these stats are EP-group-wide, and should not be reported per-engine (i.e. with the `engine_idx` label), instead they should probably only be recorded on DP rank 0.

## Proposed Metrics

| Metric Name | Type | Description
|-------------|------|-------------|
| `vllm:eplb_avg_tokens_per_rank` | Gauge | Average tokens per EP rank in current interval |
| `vllm:eplb_max_tokens_per_rank` | Gauge | Maximum tokens across EP ranks in current interval |
| `vllm:eplb_rebalancing` | Gauge | Whether EPLB is currently rebalancing (0 or 1) |
| `vllm:eplb_rebalance_events_total` | Counter | Total number of EPLB rebalancing operations |

## Sample PromQL

```promql
# Imbalance ratio - 0.5 means 50% balanced
(vllm:eplb_avg_tokens_per_rank / vllm:eplb_max_tokens_per_rank)

# Relative imbalance: avoid instances where one rank is 2x overloaded
(vllm:eplb_max_tokens_per_rank / vllm:eplb_avg_tokens_per_rank) > 2.0

# Absolute imbalance: avoid instances with severe token gap
(vllm:eplb_max_tokens_per_rank - vllm:eplb_avg_tokens_per_rank) > 5000

# Hybrid: high load AND poor balance (most dangerous)
vllm:eplb_max_tokens_per_rank > 15000
AND (vllm:eplb_max_tokens_per_rank / vllm:eplb_avg_tokens_per_rank) > 1.5

# Alert on thrashing
rate(vllm:eplb_rebalance_events_total[5m]) > 2

# Reduce traffic to instance currently rebalancing
vllm:eplb_rebalancing == 1
```

## TL;DR


There are different ways to measure "balancedness" over time with Prometheus that I can think of:
1. **Gauge** (current value) - simple, but may lose data between scrapes
2. **Counter** (sum of avg / sum of max) - no data loss, but mathematically different from average of per-step balancedness
3. **Counter** (sum of per-step balancedness / sum of steps) - gives true average, but requires computing ratio at source

All three capture some notion of balance. I'd love to hear your thoughts on which approach best fits the RFC's goals.


## Balancedness Definition

**Notation:**
```
- $R$: number of EP ranks (GPUs in the expert parallel group)
- $N$: number of steps in a time window
- $i$: step index ($i = 1, 2, \ldots, N$)
- $r$: rank index ($r = 1, 2, \ldots, R$)
```

Let $t_i^{(r)}$ be the number of tokens processed by EP rank $r$ at step $i$.

The **average tokens per rank** at step $i$ is:

$$\text{avg}_i = \frac{1}{R} \sum_{r=1}^{R} t_i^{(r)}$$

(total tokens divided by number of EP ranks)

The **max tokens** at step $i$ is:

$$\text{max}_i = \max_{r} \, t_i^{(r)}$$

(the load on the busiest rank)

The **balancedness** at step $i$ is:

$$\text{balancedness}_i = \frac{\text{avg}_i}{\text{max}_i}$$

(ratio of average load to max load; 1.0 = perfectly balanced, lower = imbalanced)

## The Problem with Gauges (Scraping Loss)

The RFC proposes `eplb_avg_tokens_per_rank` and `eplb_max_tokens_per_rank` as Gauges.

If we want the **average balancedness over $N$ steps**:

$$\bar{B} = \frac{1}{N} \sum_{i=1}^{N} \frac{\text{avg}_i}{\text{max}_i}$$

(sum up balancedness at each step, divide by number of steps)

But Prometheus is scrape-based (if I remember correctly), so if it scrapes at longer intervals and multiple steps occur between scrapes, **intermediate steps data maybe lost**?

## Potential Problem with Counter Alternative (Ratio of Sums Not Equal Sum of Ratios)

We could use Counters instead:
- `eplb_total_avg_tokens`: cumulative sum of avg tokens across all steps, i.e., $\sum_i \text{avg}_i$
- `eplb_total_max_tokens`: cumulative sum of max tokens across all steps, i.e., $\sum_i \text{max}_i$

Then in PromQL we compute:

$$\frac{\text{rate(total\\_avg)}}{\text{rate(total\\_max)}} = \frac{\sum_i \text{avg}_i}{\sum_i \text{max}_i}$$

(ratio of the sums over a time window)

But this is **not always the same as average balancedness** in general:

$$\frac{\sum_i \text{avg}_i}{\sum_i \text{max}_i} \neq \frac{1}{N} \sum_i \frac{\text{avg}_i}{\text{max}_i}$$

The ratio of sums is NOT equal to the average of ratios. (This is because $\sum(a/b) \neq \sum a / \sum b$ in general.)

## Alternative Way To Get True Average Balancedness

We can compute the ratio at the source and accumulate it:

```
- `eplb_balancedness_sum` (Counter): cumulative sum of per-step balancedness values
- `eplb_step_total` (Counter): total number of steps
```

Then the true average balancedness over a time window is:

$$\bar{B} = \frac{\text{rate(balancedness\\_sum)}}{\text{rate(step\\_total)}}$$

(change in balancedness sum divided by change in step count)

## Discussion

I feel like balancedness is more of a qualitative idea, and all three approaches (Gauge, Counter with ratio of sums, Counter with sum of ratios) should give a reasonable sense of how balanced the system is — they just differ in the exact numerical value and what gets captured between scrapes.

I'm relatively new to EPLB, so I'm curious:

```
1. What metrics do users find most useful when tuning load balancing (both dynamic EPLB and static expert placement)?
2. Is the main goal here real-time routing decisions (favoring Gauges for simplicity), or historical analysis/SLOs (favoring Counters)?
3. Are there other signals beyond balancedness that would be helpful to expose (e.g., per-rank load, rebalance duration, expert popularity)?
```

Would appreciate any feedback. Happy to help with implementation if useful!

### markmc · 2026-02-09

Heya. I did some more digging on this and have some incomplete thoughts below

---

**Objective**

Add a “closer to 1.0 is better” measure of how well load (in terms of tokens) is being spread across EP ranks (i.e. GPUs), so that:
- Users can observe EPLB doing its thing - automatic rebalancing should cause an improvement in the metric
- Users can choose between static and dynamic load balancing
- Users can tweak parameters like num_redundant_experts and observe the effect on balancedness
- Users can compare async vs sync rebalancing
- Users can observe the effect of elastic EP - automatically scaling up and down

---

**Constraints**

```
1. We wish to **avoid additional distributed collectives** (e.g. `allreduce`) to collect these stats across EP ranks - i.e. we want this metric to be available without the performance overhead that caused us to make `--log-balancedness` off by default
  - To do: The comment on `expert_load_view` suggests that we do have access (in all ranks) to the global load and links to [this comment](https://github.com/vllm-project/vllm/pull/22167#pullrequestreview-3086143856) - we need to understand this better
2. Consider the llm-d DeepSeek-R1 wide EP setup - **hybrid load-balancing** (an external load-balancer routing to 2 distinct sets of 8 API server), where all API servers within one of these sets is fully-connected to the 8 local engine cores (DP ranks), with each engine core managing a single (`TP=1`) GPU (EP ranks)
  - In other words - we cannot assume that any given API server has access to stats collected from all EP ranks
```

---

**Interim conclusions**

1. We should record per-engine `avg_tokens` and `max_tokens` counters in Prometheus and using a PromQL query, calculate a measure of load-balancedness across all EP ranks
  - Note - I checked how we avoid double-counting per-engine counters where there are multiple API servers ... we do it by only sending `SchedulerStats` to the first API server, see `Return stats to only one of the front-ends`
2. The “ratio-of-sums does not equal the sum-of-ratios” issue is likely not a concern - the ratio of `avg_tokens` and `max_tokens` counters should be fine for the use cases above
  - The metric is probably only really interesting on a heavily loaded system where the `max_tokens` denominator should be reasonable consistent
  - Even where there is a significant variance in the `max_tokens` denominator, the ratio-of-sums calculation will give more weight to heavily loaded steps … and this actually seems desirable

### Eijnewgnaw · 2026-07-27

I have a tested implementation for the two operation-state metrics from this RFC that are not covered by the existing work:

- `vllm:eplb_rebalancing`
- `vllm:eplb_rebalance_events_total`

The scope is intentionally complementary:

- #39178 owns the balancedness computation fix.
- #43715 owns per-layer/per-rank token-routing counters.
- This change does not modify balancedness or export token-load statistics. It uses the existing CPU-side async EPLB state plus a pending event delta, so it adds no device-to-host copies or distributed collectives.
- The EP-group-wide snapshot is recorded only for engine 0 without an `engine` label. PP > 1 fails closed because the frontend only observes the final pipeline stage.

Local validation covers sync/async/profile/dummy/ROCm-skip event semantics, MRV1/MRV2 transport, msgpack, SchedulerStats, and Prometheus behavior. I will link the focused PR here once it is opened.
