## 正文

## Scope

Adds opt-in AITER FlyDSL paged MXFP4 indexing for DeepSeek V4 on ROCm gfx950.

Select with:

```bash
--attention-config '{"indexer_kv_dtype":"mxfp4"}'
```

FP8 remains the default. If the installed AITER does not expose the required stride-capable FP4 scorer APIs, vLLM warns and falls back to FP8.

Supported ROCm configuration:

- gfx950
- C4 compression
- 64 query heads, head dimension 128
- 64-token compressed cache pages
- DCP=PCP=1

This PR changes only the sparse indexer's Q/K cache precision and scorer path. It does not change model/MoE weights or the main attention KV cache.

## Implementation

- The fused ROCm K producer writes packed E2M1 values and UE8M0 scales directly in the AITER preshuffled page layout.
- The fused Q producer emits packed Q plus AITER's scale swizzle.
- The cache adapter creates zero-copy value/scale views over vLLM's shared allocation.
- Prefill and decode dispatch directly to AITER's paged FP4 scorers.
- Folded index weights are rounded to BF16 for the AITER scorer contract.
- Speculative rows are flattened before C4 length conversion.
- Unsupported architectures, shapes and context-parallel configurations fail explicitly.

The shared-pool page-stride and 64-bit address support is provided by ROCm/aiter#5518.

## Platform isolation

The AITER path is selected only under `current_platform.is_rocm()`.

- NVIDIA retains the existing DeepGEMM/CuTeDSL implementation.
- CUDA FP4 packing and scale layout are unchanged.
- FP8 remains the default on every platform.
- ROCm-only packing uses a separate `_fp32x2_to_fp4x2_rocm` path.

## Decode schedule reuse

The final commit preallocates a graph-stable FP4 CTA schedule buffer in the
indexer metadata builder. The builder refreshes the schedule once per decode
step; all sparse-indexer layers consume the same `cta_info` and `total_ctas`.
The 512-CTA floor is unchanged. This does not change cache format, scorer math,
top-k, BF16 weight handling, or NVIDIA paths.

Validation:

- focused host dispatch/schedule tests: **36 passed**;
- AITER strided decode eager + graph replay: **PASS**;
- historical isolated AgentX ablation: FP4 40.397M -> FP4+schedule 40.793M
  tokens/$, **+0.98% relative to FP4** and +3.66% vs the 39.354M baseline.

The historical schedule result is one full3600 run. The serving matrix below was
re-measured with all three commits (including this one) on the 2026-09-10 ROCm
nightly image, so the reported serving numbers are for the complete PR.

### Decode scheduling analysis

```bash
There is no serving-concurrency or C64 branch in this PR. Cache and table
strides come from the tensors. The only fixed scheduling choice is the same
decode floor used by ATOM: `parallel_unit_num=max(512, rows)` with
`block_k=256`.
```

At 128K maximum context, isolated scorer results with 512 CTA are: B1 0.87x,
B2 1.02x, B4 1.49x, B8 1.73x, B16 1.81x and B64 2.37x (FP8 latency divided by
FP4 latency). This explains the serving crossover: TP1/DP8 service concurrency
64 is roughly local batch 8, while C1/C4 leaves most ranks at local batch 0-1.

A 128/256/512 CTA sweep found 256 CTA can recover B1/128K to parity, but B4+
prefers 512 and short-context low-batch optima differ. Auto-grid is slower at
larger batches. No context/batch heuristic is included: selecting from GPU
lengths must not introduce a host synchronization, and the measured table does
not justify a stable rule across context, batch, MTP and graph buckets.

## AITER [ROCm/aiter#5603](https://github.com/ROCm/aiter/pull/5603) and FP4 prefill-planning follow-up

Runtime: old `DeepSeek-V4-Pro` snapshot `b5968e9190ef611bbf34a7229255be88a0e937c1`,
8x MI355X TP8, ROCm 10 Sep-10 nightly
`vllm/vllm-openai-rocm@sha256:72e90adf360ccffb231a098a15eadfb808719c029c6cd43f6386095064552b7e`
(vLLM `2a02f6efe3`), AITER [ROCm/aiter#5603](https://github.com/ROCm/aiter/pull/5603) split-k plus #5518 stride/rebase APIs.

The additional prefill-planning commit plans direct-paged FP4 chunks by
`rows * max(request context)` rather than the gathered-FP8
`rows * sum(request contexts)` workspace. It also computes ragged windows and
the FP4 CTA schedule once in metadata instead of once per indexer layer.

### Kernel profile

On one 16-request mixed-context prefill (56,064 prompt tokens):

| Metric per TP rank | Existing FP4 | New planner | Change |
|---|---:|---:|---:|
| FP4 scorer launches | 60 | 30 | **-50.0%** |
| FP4 scorer device time, max rank | 2.383 ms | 1.910 ms | **-19.9%** |
| Window + row-plan + CTA-info launches | 180 | 6 | **-96.7%** |
| Window + row-plan + CTA-info time, max rank | 2.230 ms | 0.083 ms | **-96.3%** |
| Combined scorer + planning time | 4.613 ms | 1.993 ms | **-56.8%** |

A first HTTP experiment incorrectly sent 16 separate requests with prefix caching
enabled. Its apparent 18.30% wall-time improvement was a scheduler/cache artifact
and is excluded. The corrected experiment sends one completion request containing
all 16 token-ID prompts, disables prefix caching, and performs a shape-identical
warmup. Median wall times were 2317.98 ms for FP8+#5603, 2320.69 ms for existing
FP4, and 2326.11 ms for the new planner: all within 0.35%, i.e. no measurable
end-to-end difference in this sample.

The traces explain why kernel and wall-time results differ. The scheduler still
split the logical request into 8-9 `execute_context` steps with different token
buckets between arms. FP4 reduces indexer work, but the saved few milliseconds
are diluted by roughly 2.3 seconds of model/MoE/attention execution. Therefore
the kernel result is valid, while the earlier 18.30% wall-time attribution was
not.
