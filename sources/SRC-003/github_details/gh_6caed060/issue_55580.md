# [Issue #55580] [Performance]: GDN hybrid (Qwen3.8-27B, fp8 KV, TP2): c32 aggregate throughput steps -24% when the profiled KV pool is below ~190k tokens (<=116 blocks); c8 and single-stream unaffected

## 正文

### Summary

On a GDN hybrid (Qwen3.8-27B, INT4 weights, fp8 KV, TP=2) the aggregate throughput of 32 concurrent short requests drops by ~24 % when the profiled GPU KV pool is **below ~190k tokens (≤116 unified blocks)**, and is fully recovered when the pool is **≥ ~190k tokens (≥121 blocks)**. Each request needs only one block, `c8` and single-stream numbers are identical in every configuration, and the pool size is the only variable that tracks the step. Because the memory profiler lands the *same* launch at 183,028 or 191,884 tokens on different starts (~5 % variance), the c32 throughput of one production launch is a per-start coin flip.

Is there a per-step cap in the hybrid (Mamba/GDN state) scheduling path that is derived from the number of KV blocks, independent of `--max-num-seqs`? If this is expected, what is the right knob?

### Environment

```
- vLLM 0.28.0, torch 2.13.0+cu130, CUDA 13.0, FlashInfer attention backend, driver 616.56, WSL2 (kernel 6.18.33), 2× RTX 5060 Ti 16 GB
- Model: `RedHatAI/Qwen3.8-27B-INT4`
- Launch (production): `--tensor-parallel-size 2 --kv-cache-dtype fp8 --mamba-cache-mode align --max-model-len 163840 --max-num-seqs 32 --max-num-batched-tokens 3135 --gpu-memory-utilization 0.90` (block size 1568 = the unified hybrid block); one series with the LMCache MP connector, one without — the step is the same either way.
```

### Measurement

Probe: 512-token prompt → 256 output tokens; W1 single stream (3 reps), then c1 / c8 / c32 fired at once; aggregate tok/s over the batch wall.

| arm | max_len | util | connector | pool (tokens) | c32 agg t/s | c32 TTFT p95 | c8 agg | W1 |
|---|---|---|---|---|---|---|---|---|
| A | 65,536 | 0.90 | yes | 169,301 | 230.4 | 26.4 s | 160.9 | 29.3 |
| B | 106,496 | 0.90 | yes | 178,452 | 230.6 | 26.4 s | 160.7 | 29.2 |
| C | 131,072 | 0.90 | yes | 180,588 | 229.3 | 26.6 s | 161.5 | 29.5 |
| D | 131,072 | 0.90 | no | 180,588 | 232.8 | 26.1 s | 162.4 | 29.7 |
| E | 163,840 | 0.90 | no | 183,028 | 232.0 | 26.3 s | 162.3 | 29.7 |
| F | 163,840 | 0.88 | yes | 172,696 | 229.6 | 26.4 s | 161.0 | 29.0 |
| **G** | 163,840 | 0.90 | yes | **191,884** | **300.6 / 302.7** | 11.3 s | 160.9 | 29.0 |
| G, batched 1568 | 163,840 | 0.90 | yes | 191,884 | 301.4 | 11.3 s | 160.4 | 29.2 |
| G, batched 4703 | 163,840 | 0.90 | yes | 191,884 | 301.2 | 11.2 s | 160.7 | 29.2 |
| G, `--max-num-seqs 40` | 163,840 | 0.90 | yes | 187,456 | 232.4 | 11.0 s | 161.7 | 29.4 |

- F vs G is the cleanest control: identical launch except util 0.88 → 0.90, i.e. the pool 172,696 → 191,884; c32 goes 230 → 301.
- In the slow arms c32 TTFT p95 is one full 256-token round (26 s) with per-request tok/s unchanged (9.8 vs 9.5), which looks like ~24 of the 32 streams are admitted and 8 wait for a slot.
- `--max-num-seqs 40` at a 187,456 pool admits all 32 (TTFT p95 11 s) but the aggregate stays at 232 — so the cap may be a per-step batch limit rather than admission.
- Ruled out: `--max-num-batched-tokens` (1568 / 3135 / 4703: no change), the connector's per-step cost (slow without it too), host state (re-runs reproduce), GPU clocks (P0, 2.5 GHz throughout).

### Question

```
1. Is there a per-step limit in the hybrid scheduling path that is derived from the number of KV blocks (rather than from `--max-num-seqs` / `--max-num-batched-tokens`)? The 116 → 121 block edge is very sharp for a workload where each request holds one block.
2. Is pinning the pool with `--kv-cache-memory-bytes` (sized to the fast side) the recommended way to make this deterministic, or is there a scheduler knob for it? Pinning gives us the 190,408-token pool on every start, but skips the profile run, so we would rather not rely on it for production if there is a better handle.
```

### Repro

```
- Same launch, `--gpu-memory-utilization 0.88` vs `0.90`, then 32 concurrent 512→256 requests; the aggregate steps by ~24 %.
- Probe: a small asyncio loop over `/v1/completions` (512-token prompt, `max_tokens=256`, 32 requests fired together, aggregate = total generated tokens / batch wall). Happy to attach it or run further arms on request.
```

### wickist · 2026-09-06

We run the same model class in production (Qwen3.8-27B hybrid GDN, `mamba_cache_mode="align"`, FP8 KV, TP2, W4A16 weights, speculative decoding) and your measurements match a mechanism we can put numbers on.

**Why a KV-token pool threshold can gate concurrency that `--max-num-seqs` does not see.** In align mode the mamba/GDN state pool and the KV pool share one block-ID space. A per-sequence GDN state column does not cost one block ID — it costs many. On our 0.27.x stack we measured the shared pool needing ~22.7× the block IDs a KV-only sizing of the same workload suggests (131K-class contexts; methodology in wickist/qwen3.8-27b-vllm-performance-research). The scheduler-side accounting of that shared budget — especially under speculative decoding, where draft slots also draw from it — is exactly what #53398/#53798 track worker-side and what #55533 is now investigating scheduler-side (ArjunPakhan is in `vllm/v1/core/sched/scheduler.py` on the mamba/GDN cache budget vs draft-token accounting).

So a pool of ≤116 unified blocks plausibly cannot back 32 concurrent state columns; below the threshold the effective per-step concurrency is set by allocator availability, not `max_num_seqs`, and c8 stays healthy because 8 columns fit — consistent with everything you measured, including the pool size being the only variable that tracks the step.

**The per-start coin flip.** We see the same profiled-pool variance boot-to-boot on this class. Two mitigations worth considering upstream:

```
1. A startup log/assert stating how many concurrent mamba state columns the profiled pool can actually back, next to `max_num_seqs` — that turns your silent −24% into a one-line deterministic diagnosis instead of a coin flip.
2. Pinning a floor on the profiled pool (or re-profiling once and caching the result) so ~5% profiler jitter cannot straddle the threshold between launches.
```

For what it is worth operationally: our production pools on this class run ~321K tokens — comfortably above the threshold you identified — and c8/single-stream behavior matches yours exactly (unaffected).

Related correctness work in the same area that this threshold interacts with: #54076 (align-mode chunk splitting must stop on the mamba group's own state grid — heterogeneous block sizes), #55600/#55601 (state slot seeding in wrong units on prefix-cache hits), #54713 (retention below a boundary under EAGLE/MTP). All of these change *when* a state column is materialized or resumed, i.e. they move the same shared-pool pressure your issue is measuring.
