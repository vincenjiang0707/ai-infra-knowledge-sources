# [Issue #58192] [Bug]: --max-num-queued-reqs is checked before the render but only counted after it, so a burst renders requests it then refuses (503 after 4–9 s of multimodal preprocessing)

source: https://github.com/vllm-project/vllm/issues/58192
state: open | updated: 2026-09-22T19:48:51Z
labels: multi-modality

## 正文

### Your current environment

vLLM 0.29.0 (`v0.29.0` tag), V1 engine, one API server (`--api-server-count 1`), served with `vllm serve … --max-num-seqs 16 --max-num-queued-reqs 166 --max-num-queued-tokens 360000`, a multimodal model (a Qwen2.5-VL-class 4B page parser, one image per request, `--limit-mm-per-prompt '{"image":1}'`), B300, CUDA 12.9, Python 3.12, Linux. The behaviour below is in the frontend's Python and does not depend on the model or the GPU.

### 🐛 Describe the bug

`--max-num-queued-reqs` is checked twice per request but nothing is counted until the second check, so under a burst the API server renders (decodes the image, runs the HF processor, tokenizes) many requests it then refuses. A request that ends as a 503 pays the full multimodal render first, and the renderer — single-worker for multimodal by design (`renderers/base.py`, `_mm_executor = ThreadPoolExecutor(max_workers=1)`, "must stay single-worker per #38418") — spends its serial capacity on requests that never reach the engine, delaying the ones that will.

**Where, in `v0.29.0`:**

```python
1. `vllm/entrypoints/generate/base/serving.py` `GenerateBaseServing._preflight()` → `engine_client.check_admission(n)`, called from `render_chat_request` / `render_completion_request` **before** `online_renderer.render_chat(...)`.
2. `vllm/v1/engine/async_llm.py` `AsyncLLM._add_request()` → `check_admission(request_id=...)` again, **after** `input_processor.process_inputs_async` (the render), immediately before `output_processor.add_request(...)` — the first point the request is counted by `get_num_unfinished_requests()`.
```

Both checks read `OutputProcessor.get_num_unfinished_requests()` (and `get_num_queued_tokens()`), which only know about requests already handed over in (2). Between (1) and (2) a request is invisible to admission. A burst that arrives while the count is under the cap passes (1) in full, every request is rendered one at a time on `_mm_executor`, and the surplus is refused at (2) with `QueueOverflowError` → HTTP 503 (`Request queue full - rejecting request chatcmpl-… (current=166, n=1, max=166)` in the log, versus `rejecting request None` for a refusal at (1)).

`main` has the same shape (`check_admission` at `_add_request`, and for `n > 1` before the fan-out in `add_request`; the `admission_stats` shared counter added by #54746 for `--api-server-count > 1` is still only incremented at hand-over).

**Measured, production, 2026-09-22** (one B300 container, `--max-num-queued-reqs 16`, requests are pages sent as `image_url`, ~500 KB p50): during four bursts of 375–589 arrivals in 11–21 s, 54 % of the engine's 503s took **4–9 s p50** to arrive (the request had been fetched and rendered — it carried a `media.fetch` span) instead of **0.35–0.44 s** for the ones refused at preflight; the API server held up to ~85–101 requests in the render pipeline while `vllm:num_requests_running` was 16 and `vllm:num_requests_waiting` was 0. On a dev deployment with `--max-num-queued-reqs 166`, a burst of 300 simultaneous requests had 7 refusals, each costing the client ~15 s. The renderer's serial wait (~45 ms a page) also lands on every request that *is* admitted: pre-engine wait (`time_to_first_token − time_in_model_prefill − time_in_queue`) p50 5.7 s, max 12.5 s at 300.

**Expected:** a request that will be refused is refused at (1), before its render, in the ~0.4 s it takes to parse the body — and the renderer only works on requests that will be admitted.

**Suggested fix — reserve at preflight.** Make (1) count: a per-process counter of "admitted, not yet handed over" requests (`n` slots each) that `check_admission` includes in `current` and increments when it passes with no `request_id` (the preflight), and that `_add_request` / the `n > 1` path in `add_request` decrements at hand-over (so the second check becomes a no-op by construction: `unfinished + reserved <= max` holds at every preflight, and hand-over moves a slot from `reserved` to `unfinished`). A reservation whose request never hands over — the client disconnected during the render (`with_cancellation` cancels the handler), or the render returned an `ErrorResponse` — has to be released at the handler's boundary; a TTL on reservations is a reasonable backstop for anything else. Alternatively, `_preflight` could return a token that `generate()` consumes. Moving the render after `_add_request`'s accounting is not possible without the engine seeing an unrendered request.

We run exactly this as a runtime patch on our deployment (wrapping `AsyncLLM.check_admission` and `OpenAIServingChat.create_chat_completion`, reservation ledger with a 60 s TTL) and will report the before/after numbers here; happy to turn it into a PR if the approach is acceptable.

Before/after numbers from the runtime patch described above (wrapping `AsyncLLM.check_admission` so the preflight call reserves a slot the hand-over call consumes; the handler's boundary releases unconsumed reservations), same server build with the patch off and on, `--max-num-seqs 16 --max-num-queued-reqs 166`, 300 requests fired at once, one 1275×1650 inline image each (2,098 prompt tokens), 1,024-token decodes:

| | 200 | 503 | 503 client latency p50 / p99 | refused requests fetched/rendered? | served client p50 / p99 | pre-engine wait (arrival → hand-over) p50 / max | `num_requests_waiting` peak |
|---|---|---|---|---|---|---|---|
| 0.29.0 as is | 300 | 0 | — | — | 21.2 s / 35.7 s | 12.5 s / 22.9 s | 88 |
| 0.29.0 as is, earlier container | 293 | 7 | 15.2 s / 15.3 s | yes, all 7 (refused at `_add_request`) | 17.6 s / 30.4 s | 5.7 s / 12.5 s | 149 |
| reserve at preflight | 167 | 133 | 4.1 s / 4.4 s (the upload of 300 × 218 KB bodies) | no — none of the 133 has a fetch or `llm_request` span | 14.8 s / 22.5 s | 7.2 s / 12.3 s | 51 |
| reserve at preflight, text-only bodies | 166 (= cap) | 134 | 1.3 s / 1.6 s (connection floor, 300 at once) | no | — | — | 150 |

With the reservation every refusal is `check_admission`'s preflight call (`current=3, reserved=163, n=1, max=166` in the log, zero hand-over refusals), the single-worker multimodal executor only works on requests that will be admitted (served pre-engine wait halves), and `--max-num-queued-reqs` bounds what it says: 300 onto 166 refuses ~134, where the unpatched server admitted all 300 because the renderer acted as an invisible queue in front of the count.
