# [Issue #46596] [ROCm][Perf] ROCM_ATTN selected over ROCM_AITER_FA for MHA decode despite VLLM_ROCM_USE_AITER=1 (CDNA)

source: https://github.com/vllm-project/vllm/issues/46596
state: open | updated: 2026-09-25T01:42:51Z
labels: rocm, stale

## 正文

### Summary

On CDNA (MI300X/MI325X/MI355X), setting `VLLM_ROCM_USE_AITER=1` for an MHA model does **not** result in `ROCM_AITER_FA` being selected for decode attention — vLLM still picks the non-AITER `ROCM_ATTN`. This contradicts the documented behavior and the published benchmarks, and significantly slows attention-heavy paths (notably speculative decoding).

### Root cause

In `vllm/platforms/rocm.py::_get_backend_priorities()`, `ROCM_ATTN` is appended to the candidate list **before** `ROCM_AITER_FA`. Selection picks the lowest-index valid backend, so `ROCM_ATTN` wins whenever it is valid — even when the operator explicitly enabled AITER and `ROCM_AITER_FA` is valid.

Server log (AITER is otherwise active — MoE/FP8/sampler all use AITER):
```
[rocm.py] Found incompatible backend(s) [TURBOQUANT] with AttentionType.DECODER.
Overriding with ROCM_ATTN out of potential backends:
['ROCM_ATTN', 'ROCM_AITER_FA', 'ROCM_AITER_UNIFIED_ATTN', 'TRITON_ATTN'].
```

This is inconsistent with the [vLLM ROCm attention-backend blog](https://blog.vllm.ai/2026/02/27/rocm-attention-backend.html): *"With `VLLM_ROCM_USE_AITER=1`, vLLM automatically selects `ROCM_AITER_FA` for MHA models."* In practice it does not.

### Impact (measured, 8x MI300X)

`Qwen/Qwen3-VL-235B-A22B-Instruct-FP8`, EAGLE3 speculative decoding, real (padded) MMMU prompts, `VLLM_ROCM_USE_AITER=1`. `ROCM_AITER_FA` selected via `--attention-backend ROCM_AITER_FA`; everything else identical to the default-selection run.

**SD decode TPOT (ms) — default selection vs ROCM_AITER_FA:**

| mc | v0.21 default | v0.21 AITER_FA | v0.22 default | v0.22 AITER_FA | v0.23 default | v0.23 AITER_FA |
|----|------|------|------|------|------|------|
| 1  | 11.10 | **5.62** | 10.36 | **5.29** | 10.65 | **5.31** |
| 4  | 14.64 | **7.02** | 14.49 | **6.60** | 13.89 | **6.60** |
| 8  | 18.92 | **8.58** | 18.94 | **8.31** | 18.64 | **8.24** |
| 16 | 24.23 | **11.73** | 22.02 | **11.74** | 24.67 | **11.12** |

**SD throughput (tok/s):**

| mc | v0.21 default | v0.21 AITER_FA | v0.23 default | v0.23 AITER_FA |
|----|------|------|------|------|
| 1  | 87  | **178** | 89  | **197** |
| 8  | 390 | **808** | 393 | **798** |
| 16 | 416 | **1083** | 399 | **1023** |

Non-speculative baseline decode is unchanged within noise (±1–5%), consistent with the blog's finding that `ROCM_ATTN`'s HIP paged-decode kernel falls back to Triton only for unsupported KV head sizes (e.g. Qwen3-VL-235B) — which the SD draft+verify loop hits hardest. The blog reports `ROCM_AITER_FA` is **2.8–4.6× faster TPOT / 2.7–4.4× higher throughput** than `ROCM_ATTN` for MHA on CDNA3 (MI300X).

### Proposed fix

Reorder `_get_backend_priorities()` so `ROCM_AITER_FA` outranks `ROCM_ATTN` **only when `is_mha_enabled()` is true** (env opt-in + gfx9). Radeon/RDNA and `VLLM_ROCM_USE_AITER_MHA=0` are unaffected (`is_mha_enabled()` is False there); `ROCM_AITER_UNIFIED_ATTN` keeps its original position; the KV-connector exclusion of `ROCM_ATTN` is preserved.

PR: fix in progress (linked below). Scope is intentionally narrow — this is **not** "make AITER the global default" (which would regress Radeon and was the scope of the now-closed #21805 / #21366); it only honors an explicit opt-in.

### Independent confirmation + the exact regression-introducing PR

This is corroborated by @hongxiayang / @vllmellm's investigation on MI325 in https://github.com/vllm-project/vllm/issues/43153#issuecomment-4499816385:

> v0.18.0 is using the ROCM_AITER_FA by default for dense model. v0.21.0 was changed to select ROCM_ATTN by default in this PR #36702. So to align with the behaviour of v0.18.0, we have to add `--attention-config '{"backend": "ROCM_AITER_FA"}'`.

So the default flip was introduced by **#36702 "[ROCm] Attention selector reordering"** (merged 2026-03-25), which matches our bisect of the image behavior (v0.18 → ROCM_AITER_FA, v0.21+ → ROCM_ATTN). That report observed it on **dense** models / MI325; this issue adds an independent reproduction on **MI300X** and shows the impact is amplified under **EAGLE3 speculative decoding** (the draft + verify forwards run per decode step, so the per-call attention penalty multiplies — SD TPOT roughly halves with `ROCM_AITER_FA` while non-speculative baseline is within noise).

### Exact configuration

This is specifically an **EAGLE3 speculative decoding** issue. Full model pair:
- Target: `Qwen/Qwen3-VL-235B-A22B-Instruct-FP8`
- Draft: `RedHatAI/Qwen3-VL-235B-A22B-Instruct-speculator.eagle3`
- `--speculative-config '{"method":"eagle3","num_speculative_tokens":4}'`, TP=8, MI300X (gfx942/CDNA3)
- `VLLM_USE_V1=1 VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MHA=1`

Note: the linked comment also mentions `VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1` as an additional ROCM_AITER_FA tuning knob for dense full-attention models — orthogonal to this selection fix, but worth surfacing for affected users.

### Additional evidence: the fix generalizes across CDNA3 GPUs and speculative methods

To clarify scope vs the linked thread: the investigation in #43153 was on **MiniMax (dense model)**. Our data extends the same default `ROCM_ATTN` → `ROCM_AITER_FA` finding across more hardware and model/spec-decode configurations, all on CDNA3 with `VLLM_ROCM_USE_AITER=1`:

- **MI300X — Qwen3-VL-235B + EAGLE3 SD** (tables above): SD decode TPOT roughly halves; throughput ~doubles.
- **MI355X — Qwen3-VL-235B**: **>80% geomean improvement** switching from the default `ROCM_ATTN` to `ROCM_AITER_FA`.
- **MI355X — GLM-4.7 + MTP**: large throughput jump with the same switch.

```
Taken together this shows the default-selection regression is **not** specific to one model, one GPU, or one speculative method:
- spans **both CDNA3 generations** (gfx942 MI300X + gfx950 MI355X),
- spans **dense (MiniMax), EAGLE3 (Qwen3-VL-235B), and MTP (GLM-4.7)**,
- and is amplified for any speculative path (EAGLE3 / MTP) because the draft + verify forwards run per decode step, multiplying the per-call attention penalty.
```

This reinforces that honoring the `VLLM_ROCM_USE_AITER=1` opt-in (preferring `ROCM_AITER_FA` over `ROCM_ATTN`) is the right default behavior on CDNA3, consistent with the published blog benchmarks and with v0.18.0's original selection prior to #36702.
