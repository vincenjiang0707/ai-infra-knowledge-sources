## 正文

## Purpose

```bash
Optimize the active ROCm Kimi-K3 `fused_recurrent_kda_fwd_kernel` for
low-concurrency speculative decoding on MI355X.
```

The shipped gated configuration uses `BV=32`, `num_warps=4`, and
`num_stages=2`. With Kimi-K3 TP8 (`H=12`, `V=128`) at concurrency 1, this
launches only 48 workgroups for a four-token verification step on a 256-CU
MI355X. This change increases grid parallelism and removes recurrent-loop
runtime work when speculative requests have a uniform query length.

## Changes

- Select narrower V tiles from the number of head-sequences (`H * N`):
  - at most 24: `BV=4`, one warp;
  - 25-96: `BV=8`, one warp;
  - larger multi-sequence grids retain the dynamic path.
- Specialize equal-length speculative batches with a constexpr sequence length.
  C=1 additionally avoids sequence/head division and `cu_seqlens` loads.
- Detect uniform speculative query lengths from existing CPU metadata. Ragged
  batches retain the original dynamic loop. Token-padded graph inputs are
  checked against the packed tensor size before specialization.
- Tune pipeline stages by sequence length: 2 for T=1, 4/8 for T<=3, 6 for
  T<=6, 10 for T<=10, and 12 for longer specialized loops.
- Hoist `exp(A_log)` and `dt_bias` loads out of the token loop.
- Normalize Q/K with `tl.rsqrt` instead of division by `tl.sqrt`.
- Extend the existing KDA and metadata tests with C=1/2/4/8 uniform cases and a
  ragged fallback case.
- Keep static-loop eligibility separate from launch-configuration selection so
  the tuned thresholds and fallback behavior are explicit.

## Why this is not duplicate work

Open-PR searches were run for Kimi-K3, KDA, and `fused_recurrent_kda` work.
This does not duplicate:

- #57753, which tunes the shared `fused_sigmoid_gating_delta_rule_update_kernel`;
- #54103, which proposes routing ROCm Kimi-K3 to ATOM kernels;
- #52988, which adds adaptive variable-length decode plumbing but does not
  specialize this AMD Triton kernel;
- #53525, which optimizes the NVIDIA non-speculative C=1 native/CuTe pipeline;
- #52375 and #56974, which fix launch-grid dimension limits.

If #54103 changes the active ROCm route before this lands, this PR should be
reassessed.

No issue is linked.

## Model evaluation

A concurrency-1 GSM8K A/B evaluation was run with the same protocol as
[SemiAnalysisAI/InferenceX run 34332168553 attempt 3](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/34332168553/attempts/3).
Both sides used image
`vllm/vllm-openai-rocm:nightly-rocm100-0961bbae2894d574be790d219651824eb199318e`
and the same model, server configuration, prompts, seeds, and evaluator:

- `lm-evaluation-harness` revision
  `b315ef3b05176acc9732bb7fdec116abe1ecc476`;
- GSM8K v3, 5-shot, `local-chat-completions`, and `--apply_chat_template`;
- `num_concurrent=1`, `max_tokens=12288`, temperature 0;
- TP8, `max_num_seqs=2`, DSpark K=6 with the TRITON_MLA draft backend and
  block rejection, FP8 KV cache, and FULL_AND_PIECEWISE graph capture sizes
  2 through 14.

| Revision | Flexible extract | Strict match |
| --- | ---: | ---: |
| Baseline | 96.97% (1279/1319) | 96.97% (1279/1319) |
| Current PR `2a7b3938b7` | 97.04% (1280/1319) | 97.12% (1281/1319) |
| Difference | +0.08 percentage points | +0.15 percentage points |

All 1319 requests completed on both sides without request failures. For the
strict metric, 16 examples changed from incorrect to correct and 14 changed
from correct to incorrect, for a net gain of two. For flexible extraction, the
net gain was one. These differences are smaller than the approximately 0.47
percentage-point standard error, so this evaluation shows no model-level
accuracy regression.

The earlier custom raw-completions run used a different prompt and a 256-token
output limit, causing truncations and non-comparable aggregate scores; it is
superseded by the evaluation above.
