### 🐛 Describe the bug

On macOS arm64 with the CPU backend, Qwen3.5-0.8B crashes when `mamba_cache_mode="align"` needs to copy Mamba/GDN state across blocks and Triton is unavailable.

The failing line is in `vllm/v1/worker/mamba_utils.py`:

```python
batch_memcpy_kernel[grid](src_ptrs, dst_ptrs, sizes, BLOCK_SIZE=BLOCK_SIZE)
```

When Triton is not installed/available on this CPU setup, `batch_memcpy_kernel` behaves like a normal Python function rather than a Triton launchable object, so the `[...]` launch syntax raises:

```text
TypeError: 'function' object is not subscriptable
```

I hit this while running vLLM with an external KV connector (LMCache), but the crash is in vLLM's Mamba align preprocessing path after scheduling a request that crosses the Mamba/attention block boundary. A short prompt works; a prompt of ~732 tokens triggers the copy path. In this run vLLM logs:


A local workaround was to add a CPU fallback in `batch_memcpy` when `batch_memcpy_kernel` is not launchable, using `ctypes.memmove` for each `(src_ptr, dst_ptr, size)`. With that fallback, the same two 732-token completion requests succeeded on the same host.

```python
if not hasattr(batch_memcpy_kernel, "__getitem__"):
    src_ptrs_cpu = src_ptrs.detach().cpu().tolist()
    dst_ptrs_cpu = dst_ptrs.detach().cpu().tolist()
    sizes_cpu = sizes.detach().cpu().tolist()
    for src, dst, size in zip(src_ptrs_cpu, dst_ptrs_cpu, sizes_cpu):
        ctypes.memmove(int(dst), int(src), int(size))
    return
```

Expected behavior: CPU/macOS execution should either use a CPU copy fallback for Mamba state copies when Triton is unavailable, or fail earlier with a clear unsupported-configuration error instead of crashing the engine at request time.
