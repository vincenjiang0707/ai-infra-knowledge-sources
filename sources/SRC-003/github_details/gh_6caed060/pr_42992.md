## Summary

Fix two crashes that prevent DeepSeek-V4-Flash (and any hybrid-KV model) from starting when OffloadingConnector is configured. https://github.com/vllm-project/vllm/issues/43093

[kv_offload] Fix stale cache_config.block_size used as hash_block_size in OffloadingSpec


### User-facing symptoms

Running DeepSeek-V4-Flash with KV offloading enabled causes the engine to crash immediately at startup with one of these assertion errors:

```
# Error 1 — stale block_size causes divisibility check to fail
AssertionError: gpu_block_size=64 not divisible by hash_block_size=256.

# Error 2 — only visible after fixing Error 1
AssertionError: If 'block_size' is specified in kv_connector_extra_config,
there must be at least one KV cache group, and all groups must have the same block size.
```

A typical failing command looks like:

```bash
vllm serve deepseek-ai/DeepSeek-V4-Flash \
  --block-size 256 \
  --kv-cache-dtype fp8 \
  --no-disable-hybrid-kv-cache-manager \
  --kv-transfer-config '{\"kv_connector\":\"OffloadingConnector\",\"kv_role\":\"kv_both\",\"kv_connector_extra_config\":{\"block_size\":256}}'
```

### Why this happens — hybrid KV cache architecture

DeepSeek-V4-Flash uses two different attention mechanisms, each with its own KV cache block size:

| KV Cache Group | Attention Type | Block Size |
|---|---|---|
| Full-MLA (standard attention) | FlashMLA | 256 (user-specified `--block-size`) |
| SWA-MLA (sliding window) | FlashMLA | 64 (hardcoded — SWA and C4A share physical tensor) |

The `--no-disable-hybrid-kv-cache-manager` flag enables this dual-group mode. When the engine initializes, the scheduler computes per-group block sizes and updates `cache_config.block_size` to the minimum (64). **However, this update only happens in the engine process — worker processes never receive it.**

Workers still see the user-specified `--block-size` of 256. `OffloadingSpec.__init__` uses this stale value to compute `hash_block_size = 256`, but the actual SWA-MLA group has `gpu_block_size = 64`. Since `64 % 256 != 0`, the assertion fires.

Even if you work around Error #1 by setting `--block-size 64`, the second error fires because DeepSeek-V4-Flash **requires** block_size=256 for its Full-MLA group (it enforces this internally). So there's no user-facing workaround that works for both groups simultaneously.

### The fix

**Bug 1 — hash_block_size derived from stale config**

Before:
```python
self.hash_block_size = vllm_config.cache_config.block_size * context_parallel_factor
```

After: derive `hash_block_size` from actual `kv_cache_spec.block_size` values using `math.gcd()`, matching the scheduler's `resolve_kv_cache_block_sizes()` logic. For GCD(256, 64) = 64, the divisibility assertion always holds.

**Bug 2 — block_size_factor incompatible with heterogeneous groups**

Before:
```python
assert len(set(self.gpu_block_size)) == 1  # heterogeneous groups crash here
```

After: when groups have different block sizes, log a warning and fall back to `block_size_factor=1` (one CPU block per GPU block per group). This is always semantically correct — the only trade-off is that offloading I/O is issued at GPU-block granularity rather than batched into larger offloaded blocks.

### Scope — which models are affected?

Any model with multiple KV cache groups that have different block sizes AND that uses KV offloading (OffloadingConnector or MultiConnector containing it):

- DeepSeek-V4-Flash (Full-MLA + SWA-MLA)
- Future models with similar hybrid attention architectures

Single-group models (standard Mamba + Attention combinations, etc.) are unaffected — the GCD of one value equals that value, and `len(set)==1` preserves the original path.
