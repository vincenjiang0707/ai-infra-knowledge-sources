### 🐛 Describe the bug

A server started with `--api-key` refuses unauthenticated requests on `/v1/*`, as documented. The same requests are **served** when posted to `/invocations`, which dispatches to the same handlers and is not covered by the guard. 

Measured with `--api-key SECRET-KEY-123` and **no** `Authorization` header:

| request | 0.27.1 | 0.29.0 |
|---|---|---|
| `POST /v1/chat/completions` | 401 | 401 |
| `POST /v1/completions` | 401 | 401 |
| **`POST /invocations`** (chat body) | **200, full completion** | **200, full completion** |
| **`POST /invocations`** (completions body) | **200, full completion** | **200, full completion** |

No special flags: a plain `vllm serve <model> --api-key <key>` on one GPU. 

**Related to but distinct from CVE-2026-22778. That CVE was the video-processing RCE reachable via this route (fixed in 0.14.1).** 

_The api-key bypass property of /invocations itself was not the subject of that fix and still holds on 0.27.1 and 0.29.0; the SageMaker router is mounted unconditionally (no SageMaker flag, no dev-mode gate), so every --api-key operator gets an unauthenticated inference path they did not opt into._

**Cause**

```
The guard is a path-prefix test
(0.27.1 `entrypoints/serve/utils/server_utils.py:42`, 0.29.0 `entrypoints/serve/middleware/authenticate.py:11`):
```

```python
GUARDED_PREFIX = ("/v1", "/v2", "/inference", "/cohere")
...
if url_path.startswith(GUARDED_PREFIX) and not self.verify_token(headers):
    return JSONResponse(content={"error": "Unauthorized"}, status_code=401)
```

`/invocations` is mounted at the root, and **unconditionally** — there is no SageMaker flag and no dev-mode gate:

```python
register_sagemaker_api_router(app, supported_tasks, model_config)   # api_server.py
```

So on every vLLM deployment the SageMaker entrypoint is present, it forwards a request body to the ordinary chat/completions handlers, and the prefix test never sees it.

### Reproduction
Use this: [repro_api_key_bypass.py](https://gist.github.com/Yunzez/99df19c52a4383e5e328be02baaceddc#file-repro_api_key_bypass-py)

`python3 repro_api_key_bypass.py --base-url http://127.0.0.1:8000 --model <model> --api-key <key>`

Start any model with `--api-key <key>`. The script sends the *same* body to `/v1/chat/completions` and to `/invocations` with no credentials and prints both statuses; it exits non-zero when the guarded route refuses and the unguarded one serves.


An operator who sets `--api-key` has exactly one authentication mechanism, and it does not hold. Anyone who can reach the port gets unrestricted inference:

* compute is consumed without authorisation;
* anything the deployment attaches server-side — a system prompt, a chat template's instructions,
  retrieved context, tools — is reachable by an unauthenticated caller;
* rate limiting or accounting keyed on the API key does not see this traffic at all.

The vLLM security guide's firewall advice is to "block all incoming connections except to the TCP port the API server is [on]", i.e. that port is the intended exposed surface, which is where this route lives.

### iharshlalakiya · 2026-09-22

#58028 already fixes this ("[Frontend] --api-key: authenticate all routes except a liveness allowlist") - it makes the middleware deny-by-default, and its tests show `/invocations` going 200 -> 401.

Two notes for that PR:

```
- `/invocations` isn't the only gap. `/tokenize` and `/detokenize` are also unguarded on every server, plus `/pooling`, `/score`, `/rerank`, `/classify` and `/generative_scoring` depending on the model's task. The prefix-allowlist shape is the real defect every new root-mounted route inherits it.
- The Rust frontend has the same bug: `rust/src/server/src/middleware/auth.rs` uses `GUARDED_PREFIXES = ["/v1", "/v2", "/inference"]` and is missing `/cohere` too. Worth fixing alongside, or `--api-key` behaves differently per frontend.
```

If #58028 stalls or lands without covering these, let me know and I'm happy to pick them up.
