# [RFC] LoRA Adapter Lifecycle for RL Training

## Problem

RL + LoRA workflows have three vLLM-side issues:

```
1. **sleep/wake crash**: Level-2 sleep with `enable_lora=True` crashes with KeyError — LoRA adapter parameters are not in cumem's tag set ([#39934](https://github.com/vllm-project/vllm/issues/39934))
2. **Adapter-only sync missing**: frameworks must merge LoRA → send full weights → unmerge. Adapter-only sync (send only LoRA delta, load via vLLM's LoRA serving) would eliminate the merge round-trip ([trl#5975](https://github.com/huggingface/trl/issues/5975))
3. **LoRA + MoE mismatch**: logprob divergence between training and inference grows with LoRA rank on MoE models (Qwen3.6, GLM-4.7-Flash) ([SkyRL#1776](https://github.com/NovaSky-AI/SkyRL/issues/1776))
```

## Downstream demand

```
- [trl#5975](https://github.com/huggingface/trl/issues/5975): Adapter-only vLLM LoRA sync for GRPO/AsyncGRPO
- [SkyRL#1776](https://github.com/NovaSky-AI/SkyRL/issues/1776): LoRA + MoE inference mismatch investigation
- [verl#6782](https://github.com/verl-project/verl/issues/6782): Qwen3.5-27B LoRA GRPO — vLLM never emits EOS with rank=64
```

## Exit criterion

- sleep/wake + LoRA (#39934) no longer crashes
- Adapter-only sync path available (no full-weight merge required)

### chengcuiping · 2026-08-17

Thanks for opening this RFC. I am interested in contributing to the adapter-only synchronization path, especially for asynchronous and multi-turn RL workloads.

One additional lifecycle requirement that may be worth considering is an immutable adapter revision. In Agentic RL, a trajectory can span multiple generation and tool-interaction turns while the trainer publishes a new LoRA policy. Replacing an adapter in place may introduce two correctness risks:

1. different turns of the same trajectory may use different policy weights;
2. prefix-cache KV produced by the previous adapter revision may be reused after a same-name update, related to #42125 and #48352.

I noticed that #49267 already explored adapter-only tensor transfer, manifest validation, and atomic adapter replacement, while intentionally pausing inference during a single-slot update. A narrow follow-up could add:

* staging `v+1` as a new immutable internal adapter revision;
* atomically publishing it for new requests while active requests continue using `v`;
* including the revision identity in prefix-cache keys;
* reclaiming old revisions only after their active references reach zero, with a bounded number of live revisions.

I would keep the vLLM-facing abstraction generic, such as `adapter_revision_id`, while RL frameworks can map it to their `policy_version` and keep one revision pinned across all turns of a trajectory.

Before implementing this, would maintainers prefer this to be treated as a follow-up to the adapter-only sync path, or proposed in a separate RFC? If the direction is aligned, I can first build a small proof of concept using two preloaded LoRA revisions and report correctness and 4×A100 throughput results before submitting a focused PR.

### chengcuiping · 2026-08-17

Thanks — I agree that retaining the previous adapter is unnecessary for synchronous RL, or for an update path that drains all outstanding rollouts before the swap. In that case, replacing the adapter and resetting the prefix cache should be sufficient.

The narrower case is asynchronous multi-turn rollout with trajectory-level policy pinning. A trajectory may wait on a tool or environment response while the trainer publishes the next adapter revision. Without temporarily retaining the previous revision, the update must either wait for those long-tail trajectories to finish, or the resumed trajectory will continue under a different policy revision.

I’ll first validate whether this creates a meaningful update barrier using two preloaded adapter revisions. If the correctness and performance results justify additional lifecycle support, I’ll post the evidence and open a separate focused proposal. Otherwise, the existing single-slot behavior should remain sufficient.

### chengcuiping · 2026-08-17

Thanks for asking. I do not mean that trajectory-level version pinning is universally preferable; re-prefilling with the latest model and continuing as a partial rollout is also a valid design point. I found at least two recent systems that explicitly choose the single-version-per-trajectory alternative for long-tail asynchronous rollouts:

- [DORA](https://arxiv.org/abs/2604.26256) (§3.2, §3.4, and Appendix D) uses multi-version streaming training. A trajectory is assigned a policy version at dispatch and is generated end-to-end under that version, while newer trajectories can proceed under newer versions. In its asynchronous GRPO formulation, this provides a well-defined per-trajectory behavior policy and allows the standard GRPO objective to be used without the additional corrections required by mixed-version partial rollouts. The same-version property also enables its nearly zero-re-prefill migration through direct cross-instance KV-cache transfer. To be precise, avoiding re-prefill depends on that KV-transfer mechanism, not on version pinning alone.

- [Laminar](https://arxiv.org/abs/2510.12633) (§2.4 and §5) similarly lets each trajectory complete on a single, consistent rollout-model version. Its repack mechanism consolidates incomplete trajectories using the same weight version from multiple underutilized rollout replicas onto fewer destination replicas. The released source replicas can then load the latest actor weights and generate fresher trajectories.

These papers support the workload and policy-consistency motivation, but they do not by themselves imply that vLLM should keep multiple LoRA revisions inside one engine: both primarily manage versions at the rollout-cluster or replica level. I do not have evidence about internal deployment practices, so I would keep the claim limited to these published systems.

My proposed two-adapter experiment is therefore intended to determine whether long tool/environment waits make an orchestrator-only solution or a drain-before-swap barrier expensive enough to justify an optional, bounded revision lifecycle in vLLM. If the measured benefit is small, the existing single-slot behavior should remain the simpler choice.

### hongzhi-gao · 2026-09-20

@aoshen02   Thanks for the suggestion. 

I compared file reload, shared-memory reload, and NCCL using real GRPO training.

### Environment and method

Two A100 40GB GPUs on a single node, one for training and one for vLLM; Qwen2.5-7B-Instruct, TRL 1.13.0, and vLLM 0.29.0, with a custom bridge for LoRA synchronization.

The workload used GSM8K with short-answer prompts and BF16 LoRA targeting all seven linear layer types. Each configuration was run with three seeds, with 5 warmup steps followed by 100 measured steps and one adapter update per step.

The shared-memory path preallocates and reuses a pinned CPU shared buffer, transferring tensors through:

`training GPU → shared memory → inference GPU`

This avoids file serialization and repeated buffer allocation.

Both the shared-memory and NCCL paths use an experimental vLLM worker extension and internal adapter-loading interfaces. No installed vLLM source files were modified, but these are custom experimental integrations, not built-in features.

### Results

The table below shows the median total time for 100 training steps, including generation, training, and synchronization:

| LoRA size | File reload | Shared-memory reload | NCCL |
|---|---:|---:|---:|
| 38.5 MiB (rank 8) | 111.5 s | 97.4 s | 96.3 s |
| 308 MiB (rank 64) | 229.3 s | 103.4 s | 98.8 s |

Compared with shared memory, NCCL saved a median of approximately **0.29 s** and **2.09 s** in the synchronization stage per 100 steps, respectively.

Generated trajectories differed across paths, so the total runtime differences cannot be attributed entirely to transport.
