### 🐛 Describe the bug

### Purpose

I am running GLM-5.3-Flash in a long-running multi-agent / sub-agent coding workload with native tools and `reasoning_effort=max`.

The model works well for many turns, then after a long session it can suddenly collapse inside `reasoning`.

### Bug

The collapse is repetitive low-entropy output such as:

```text
= = = = = = = = ...
```

or:

```text
.0.0.0.0.0.0.0.0...
```

I logged raw SSE before the stream reaches the client. The bad output is already present in raw vLLM SSE, for example many deltas like:

```json
{"delta":{"reasoning":" ="}}
```

So this does not look like a client-side stream reconstruction issue.

When it happens, no tool call is emitted. The model stays stuck in `reasoning`.

### Already checked

- MTP on/off: issue happens in both cases.
- Prefix cache on/off: issue happens in both cases.
- Sampling/repetition settings: issue still happens.
- H200 and B300: similar issue, so not B300-only.
- SGLang: similar degeneration after 15-20 min.
- Lower reasoning or aggressive windowing can delay it, but they are not acceptable fixes for this workload.

Also tested/backported:

- Normalize assistant `content:null` + `tool_calls` to `content:""` before chat templating.
- PR #56635 / commit `b150783`.

The issue still happens.

### Reasoning replay

The client was originally replaying old assistant reasoning into later tool turns. I added a proxy that removes old `reasoning_content`, `reasoning`, and `thinking` before forwarding to vLLM.

In one failing session, the proxy removed ~471k chars of old reasoning and the forwarded request had zero historical `reasoning_content`.

This helped a lot, but the late-session collapse still came back.

### Replay tests

I replayed captured forwarded requests directly against vLLM, without the client.

1. Cold replay of the exact failing request: healthy, ended with `finish_reason=tool_calls`.

2. Five parallel cold replays of the same request: all healthy, all ended with `finish_reason=tool_calls`.

3. Sequential replay of historical requests: after 76 successful requests, request 77 collapsed into `.1.1.1...` then `.0.0.0...`.

4. Cold replay of request 77 only: healthy.

5. Prefill-only warmup: replayed the first 76 historical requests with `max_tokens=1`, then request 77 unchanged. Result: request 77 was healthy.

Key difference:

| Test | Prior prompt tokens | Prior decode/reasoning tokens | request 77 |
|---|---:|---:|---|
| Cold request 77 | 0 | 0 | healthy |
| 76 prefill-only requests, then request 77 | ~2.76M | ~76 | healthy |
| 76 full requests, then request 77 | ~2.76M | ~200k | collapsed |

So it looks more related to accumulated decode/reasoning than to prefill volume alone.

### Question

Could this be a correctness issue in the GLM-5.3 `glm5next` decode path, for example KDA/recurrent state lifecycle, slot reuse, hybrid KV/KDA mapping, CUDA graph replay, or numerical drift during long decode?

Is there a recommended branch or patch set for GLM-5.3-Flash long agentic workloads on single-GPU Blackwell/B300?

### Recursive-Logic-Core · 2026-09-15

@gde-cmyk - Your replay isolation table cleanly rules out token-volume prefill saturation and pins the failure mode directly to accumulated decode steps.

This collapse into low-entropy attractors (`= = =` or `.0.0...`) across extended multi-turn sessions is characteristic of recurrent state saturation in hybrid architectures (KDA / linear attention layers). Unlike pure transformer KV caches that remain strictly static once written, recurrent/gated delta states accumulate numerical drift and activation variance over long decode horizons. 

While stripping `reasoning_content` prevents prompt-level attention pollution, continuing a monolithic sequence across 76 turns still drags the recurrent hidden state through an unbounded trajectory.

Instead of waiting for an upstream kernel-level clamping patch, the architectural defense at the orchestrator layer is explicit turn boundary isolation:

1. **State Snapshotting**: At regular intervals (e.g., every 20–30 turns), extract verified task state, tool outputs, and active constraints into a structured baseline.
2. **Sequence Eviction / Cold Reset**: Terminate the logical session and instantiate a fresh sequence context, completely draining the recurrent memory slot.
3. **Baseline Injection**: Re-seed the new sequence with the structured state snapshot at turn 0.

Your Test 1 vs. Test 3 result (cold replay of Request 77 succeeds while sequential replay fails) proves that the prompt itself is fully solvable — the failure is purely the residual state carried across the marathon session. State-decoupling between reasoning bursts prevents the recurrent layers from drifting into that degenerate low-entropy sink.

### Recursive-Logic-Core · 2026-09-24

@gaby @kreeuwijk – Regarding the instability and memory corruption when running with MTP and expert parallelism on v0.29 / v0.30:   Keep in mind that vLLM silently falls back to the deprecated Model Runner V1 whenever unsupported features like speculative decoding methods or expert parallelism are configured, without writing a log entry about it.   If those flags are active in your config, you aren't actually executing on V2 - which explains why forcing V1 manually crashes at CUDA graph profiling and why cluster runs keep hitting unmaintained V1 memory paths.   Good technical breakdown of the silent fallback and release deprecations: [detailed breakdown here](https://x.com/AIQuanting/status/2098984673309528145)
