# [PR #58194] [Perf][Kernel] Vectorized flat abs-max for dynamic per-tensor FP8 quantization

state: open | updated: 2026-09-25T01:22:54Z

## 正文

## Purpose

This PR speeds up the abs-max pass of `dynamic_scaled_fp8_quant` (per-tensor dynamic FP8 quantization) in `csrc/libtorch_stable/quantization/w8a8/fp8/common.cu`. It is the activation quant on every MoE layer of a model served with `--quantization fp8`, and it had never been performance-tuned.

I went in after reading #44173, which took the same kind of kernel (block-per-row, shared-memory tree reduction, scalar loads) and rewrote it as warp shuffles plus vector loads. This kernel had the same shape of problem, so I applied the same approach and measured what it actually buys.

**What was there before**

`segmented_max_reduction_strided` launched one block per token, did one scalar load per element, reduced through a 256-entry shared-memory tree with a `__syncthreads` per level, and issued one atomic per token. For a decode batch of 32 tokens, that is 32 blocks on a 132-SM GPU. For a 65536-token prefill it is 65536 atomics to one address.

**What this PR does**

- For contiguous input, the abs-max is a flat grid-stride kernel over 16-element vectors (32 B loads for bf16, 64 B for fp32). The reduction is a `__shfl_xor_sync` butterfly within each warp and one shared-memory exchange across warps, so a single barrier. The grid is sized from the vector count and capped at 8 blocks per SM, so a small batch gets exactly the blocks it needs and a large one loops. One atomic per block instead of one per token.
- Strided or unaligned input keeps the one-block-per-token kernel, now with vectorized loads (`vectorize_read_with_alignment`) and the same shuffle reduction in place of the tree.
- The quantize pass that follows is unchanged.

**Numerics**

Output is bit-for-bit identical to `main`. The per-element operations are unchanged (`fmaxf` for the abs-max, the same `scaled_fp8_conversion` for the quantize). `fmaxf` is order-invariant, and dividing by a positive constant is monotonic, so regrouping the max across threads, warps, or blocks cannot change any scale or any output byte. I verified this empirically rather than relying on the argument; see below. No API change. Strided rows and all dtypes behave as before.

**Not a duplicate.** #41115 (open since May, merge conflicts, no review) tunes block sizes on the per-token kernel and does not touch the per-tensor path. #55330 targets the per-token-group kernel and #45428 the fused RMSNorm quant kernel.

**Next work.** Once this is approved and merged, I plan a follow-up PR for the per-token kernel in the same file, which reuses the reduction helpers added here.

## Test Plan

- **Bitwise equivalence.** Built `main` and this branch on the same box. Dumped the quantized bytes and scales on CPU-seeded inputs for bf16 and fp32, M in {1, 7, 64, 512, 4096, 16384}, hidden in {17, 1024, 1025, 2048, 4096, 5137, 7168, 8192, 16384, 32768}, and three row layouts (contiguous, misaligned by 8 elements, aligned but padded by 16). Compared with `torch.equal`.
- **Unit tests.** `tests/kernels/quantization/test_fp8_quant.py`, plus a new strided-input test that forces the fallback kernel at both alignments.
- **Performance.** H100 80 GB HBM3, driver 580, CUDA 13.0.3, torch 2.13.0+cu130. `triton.testing.do_bench_cudagraph`, median of the full op including the memset and both kernels, so this is what a caller sees.
- **End to end.** Qwen3-30B-A3B with `--quantization fp8`, `vllm bench throughput` and `vllm bench latency`, main vs this branch on the same box.

## Test Result

- Bitwise: **1080 cases identical, 0 mismatched**, bytes and scales.
- Tests: **249 passed**.

**Per-tensor, bf16, `main` vs this PR**

| M | hidden | main (us) | PR (us) | speedup |
|---:|---:|---:|---:|---:|
| 16 | 4096 | 8.21 | 5.61 | 1.46x |
| 16 | 8192 | 11.36 | 6.01 | 1.89x |
| 512 | 4096 | 9.58 | 7.39 | 1.30x |
| 512 | 7168 | 12.60 | 8.79 | 1.43x |
| 4096 | 4096 | 48.95 | 30.51 | 1.60x |
| 4096 | 7168 | 85.17 | 55.27 | 1.54x |
| 16384 | 4096 | 187.22 | 115.96 | 1.61x |
| 16384 | 7168 | 312.94 | 196.30 | 1.59x |
| 65536 | 4096 | 715.88 | 436.15 | 1.64x |
| 65536 | 8192 | 1378.42 | 866.10 | 1.59x |

Geomean **1.39x** across bf16 and fp32, M in {16, 512, 4096, 16384, 65536}, hidden in {2048, 4096, 7168, 8192}. Range 1.11x to 1.89x. At large M, the op now moves about 3.0 TB/s of real traffic (two reads and one write), which is where it should sit on this GPU.

**End to end: Qwen3-30B-A3B with online FP8**

`--quantization fp8` quantizes activations per-tensor dynamically, and on a MoE model, the expert input of every layer goes through this kernel. Same H100, `vllm bench throughput`, random dataset, 1024 in / 128 out, 512 prompts, three interleaved runs per build after a warm compile cache:

| build | tokens/s (3 runs) | mean | stdev |
|---|---|---:|---:|
| main | 43793, 43706, 43835 | 43778 | 66 |
| this PR | 45154, 44810, 44965 | 44977 | 172 |

**+2.7% throughput**, with run-to-run spread under 0.4%. Batch latency (`vllm bench latency`, batch 32, 1024 in / 128 out): 1.876 s vs 1.843 s avg, about 1.8% lower.

The gain lands where expected: with the compiler fusing this model's per-token quant sites into RMSNorm, the per-tensor abs-max pass on the MoE expert inputs is the only kernel this PR changes that runs in the trace. Model output is unaffected since the kernel is bitwise identical.
