# [Issue #58520] [RFC]: Publish Mooncake Store residency once per complete block

source: https://github.com/vllm-project/vllm/issues/58520
state: open | updated: 2026-09-24T18:50:35Z
labels: 

## 正文

### Motivation

`MooncakeStoreConnector` publishes Store residency on the same KV event stream as the engine's local prefix cache: one `BlockStored` per block, per rank, currently with `medium="cpu"`. Three things about that stream are wrong or undefined, and they share a cause: the fact being published — the pool holds this block — belongs to the pool, but each rank constructs it on its own and the engine merges the copies by counting events.

```
1. **A block is announced only if the path that wrote it remembers to.** `store_mask` keeps mamba/SSM groups out of the positional save, so their `align` boundary states are written by the hand-off path, which published nothing. A consumer intersecting the cache groups of a block therefore scored every mamba block a miss on the rank that had just stored it. #58293 fixes this (one write path that announces what it committed, plus the group's `kv_cache_spec_kind`), and adds the missing diagnostics for hand-offs that are never persisted.
2. **The same block can be announced twice.** The cross-worker merge counts only the workers that reported in that engine step (`increment_workers` per contributing worker in `kv_connector/utils.py`), so when two ranks finish the same block in different steps, each announcement satisfies the quorum by itself.
3. **Nothing retracts a block.** The connector emits no `BlockRemoved`, and `reset_cache`, which issues `remove_all` on the master, emits no `AllBlocksCleared`, so a consumer's view of the Store only grows. `medium` is a literal, so an object the Store placed on disk is still reported as CPU; the mapping from the written replica tier to the event's wire value is undefined.
```

#### How to reproduce

Start a `mooncake_master`, point `MOONCAKE_CONFIG_PATH` at it, and serve a hybrid model:

```bash
vllm serve Qwen3.5-4B --tensor-parallel-size 2 --max-model-len 8192 \
  --enable-prefix-caching --mamba-cache-mode align \
  --kv-transfer-config '{"kv_connector":"MooncakeStoreConnector","kv_role":"kv_both"}' \
  --kv-events-config '{"enable_kv_cache_events":true,"publisher":"zmq","endpoint":"tcp://*:5557","replay_endpoint":"tcp://*:5558","topic":"kv-events"}'
```

Send three distinct ~4.4k-token prompts, then repeat the first. Compare:

```
- the objects the master lists (`GET /get_all_keys` on the master's metrics port), grouped by the `@group:N@` tag of each key;
- the events received on `tcp://127.0.0.1:5558` (a DEALER that sends `(b"", start_sequence_as_8_bytes)`; a plain SUB subscriber drops the first batches), grouped by `group_idx`.
```

On the base commit the Store holds 33 blocks (groups 0/1/2 are the GDN state groups with 3 each, group 3 is full attention with 24) and 24 are announced; the missing 9 are exactly the mamba groups. The same run shows 8 of the 24 group-3 blocks announced twice with identical payloads, and `kv_cache_spec_kind` absent on every Store-side event.

In one observed run with #58293, all 33 blocks were announced once, with `mamba` / `full_attention` set. This validates the missing-write-path fix in item 1 for that run; it does not establish the lifetime, cross-rank once-only semantics in item 2. #58293 does not change the cross-worker event aggregation or its quorum rule, so duplicate behavior can still depend on rank timing. A repeat run is required to evaluate item 2 independently.

### Proposed Change

1. **Define the event.** A `BlockStored` from this connector means "the Store holds a complete copy of this block for this cache group, on medium M". Complete means every rank namespace `lookup` probes for that group has committed its objects — the same set that decides whether a later request can hit the block.
2. **Publish it once.** Build the scheduler-side accumulator with the number of workers in the engine and keep it for the connector's lifetime, instead of adopting the container of whichever step contributed first. An event then waits until the required coverage is reached and is released exactly once. The quorum rule should be stated over `lookup_key_prefixes` rather than over worker counts, so PCP/PP layouts are covered by construction. This is a follow-up to #58293, which only fixes the missing write-path announcement.
3. **Report the tier that was written.** Derive the event medium from the replica that accepted the write: use `CPU` for a memory-backed replica, `STORAGE` for a disk-backed replica, and `None` when the tier is unavailable or unknown. Do not emit a hard-coded lowercase `cpu` value.
4. **Retract what the connector itself invalidates.** After `reset_cache` has drained pending Store work and `remove_all` succeeds on the master, emit `AllBlocksCleared`. If the reset fails, do not emit a clear event; consumers must retain their last known Store view. Evictions stay with the pool, which the connector cannot observe.
5. Keep the connector as the only publisher on the vLLM event stream, so a router serving vLLM does not also have to consume the Store's own key-level channel.

### Any Other Things

```
- #58293 is the completeness fix this builds on; it intentionally does not implement the lifetime quorum, tier reporting, or reset retraction in items 2–4. Those items can land as independent follow-up PRs.
- #52731 covers the load path reporting the tier it read from, which is the read-side half of item 3.
- The offloading connector settled the same ownership question by letting the tier-owned tracker publish; its `BlockStored` metadata is the schema this connector's events are converging on (#51243, #51614, #54325), and #49413 refactors that connector's event path.
```
