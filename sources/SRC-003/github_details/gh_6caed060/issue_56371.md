### 🐛 Describe the bug


### Describe the bug

The non-streaming `/v1/messages` response has no `stop_sequence` key unless generation stopped
on a matched stop string. `vllm/entrypoints/anthropic/api_router.py` serializes the response
with `generator.model_dump(exclude_none=True)`, and `AnthropicMessagesResponse` declares
`stop_sequence: str | None = None`, so the null value is dropped from the wire. `stop_reason`
is dropped the same way when it is null.

Anthropic's published schema lists both as required, nullable members of `Message`
(https://platform.claude.com/docs/en/api/messages, response fields `stop_reason` and
`stop_sequence`; in the OpenAPI spec the SDKs are generated from, `Message.required` lists
both and `stop_sequence` is `string | null`). Anthropic's own non-streaming examples carry
`"stop_sequence": null`. The official SDKs tolerate the missing key; a schema-validating proxy
does not, which is how this was found (vLLM Semantic Router, vllm-project/semantic-router#3500).

This is the non-streaming twin of #55324. That one was `exclude_unset=True` on the streaming
`message_delta`; this one is `exclude_none=True` on the buffered response, so the streaming fix
does not cover it. `message_start` on the stream already carries both keys explicitly.

Live, vLLM 0.26.0, `Qwen/Qwen3.8-27B-FP8`, `"stream": false`, content elided:

```
{"id":"chatcmpl-b09cf4dae16a22a0","type":"message","role":"assistant","content":[...],"model":"Qwen/Qwen3.8-27B-FP8","stop_reason":"max_tokens","usage":{"input_tokens":57,"output_tokens":16}}
```

Keys present: `content, id, model, role, stop_reason, type, usage`. No `stop_sequence`.

Same on main at `828f4f19` (2026-09-10): `api_router.py` line 82.

### To Reproduce

No GPU needed. Build the route's FastAPI app with a mocked handler that returns an
`AnthropicMessagesResponse(stop_reason="end_turn")`, POST `/v1/messages` with
`"stream": false`, and inspect `response.json()`: `"stop_sequence"` is not a key. Inspecting
the model attribute hides the omission (`stop_sequence is None`); `model_dump(exclude_none=True)`
reproduces it.

With a server:

```
curl -s http://<host>:8000/v1/messages \
  -H 'content-type: application/json' -H 'x-api-key: x' -H 'anthropic-version: 2023-06-01' \
  -d '{"model":"<model>","max_tokens":16,"stream":false,"messages":[{"role":"user","content":"Reply with exactly: OK"}]}'
```

### Expected behavior

`"stop_sequence": null` (and `"stop_reason": null` if ever null) on the non-streaming
response, matching the schema and the streaming `message_delta` after #55325. What
`exclude_none` prunes today should stay pruned: the vLLM extension fields
(`kv_transfer_params`, `ec_transfer_params`) and the members of each content block that do
not apply to its type.
