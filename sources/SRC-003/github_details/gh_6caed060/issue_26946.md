# [Issue #26946] [RFC]: Enable libtorch-ABI-stable vLLM cuda wheels

## 正文

### Motivation.

PyTorch is building out a limited ABI through which custom ops writers can build extensions that build with one torch version and run on another. vLLM is an important part of the ecosystem that depends on torch. We'd like to help enable building vLLM wheels that would not be tied to a specific torch version to promote build system simplicity and general developer experience.

### Proposed Change.

As PyTorch increases our ABI surface, we'd love vLLM's collaboration in testing out our stable APIs. We've gone through the repo and gathered the following torch APIs that we are working to make stable. The hope is that once we have the stable versions of these ops, we can build vLLM cuda wheels in a libtorch stable manner, similar to what we did in FA3 here: https://github.com/Dao-AILab/flash-attention/pull/1791

The libtorch stable C shim APIs that we consider the bedrock of our work, e.g., the APIs in https://github.com/pytorch/pytorch/blob/main/torch/csrc/inductor/aoti_torch/c/shim.h are stable -- they are not changing in the foreseeable future and we will only add to the set. ### zou3519 · 2026-03-16

Also, for the record, @tjtanaa asked me offline “why not use tvm-ffi for abi stability instead of the libtorch stableabi”?

TL;DR: We think the simplest way (less engineering, fewest changes in vLLM code) right now to enable abi stability is to go with libtorch stable ABI.

tvm-ffi does not support all the C++ APIs listed [here](https://github.com/vllm-project/vllm/issues/26946#issue-3519588644) that vLLM needs. The libtorch stableabi has analogues for all of these. In particular, tvm-ffi is designed to be a general purpose stable abi layer (that is framework agnostic), while the libtorch stableabi focuses on making existing PyTorch APIs ABI stable.

```
For example, using tvm-ffi: one cannot register a torch custom operator in C++, one cannot use torch’s scalartype [dispatch macros](https://github.com/vllm-project/vllm/blob/main/csrc/dispatch_utils.h#L14-L17) (which are useful for authoring kernels), and one cannot call torch built-in operators (like at::sum) from C++. A pure tvm-ffi stableabi approach would involve:
- registering the custom operators in Python (instead of C++) 
- re-implementing the dtype dispatch, cuda device and stream guard equivalents in vLLM
vLLM adding its own kernels for built-in torch ops (like at::sum) or refactor the code to call these from Python
- For everything that we moved from C++ to Python, study the overheads of the jumps between python/C++
```

### janeyx99 · 2026-06-12

@Harry-Chen thanks for the question! There are two prongs to this. 

1. By setting the TORCH_TARGET_VERSION flag on each extension built, the files of that extension are protected at build time and will screech if an unstable API is used (or even a stable API that’s introduced in a later version). So this part I feel pretty good about, that we should be getting build time signal that’ll prevent people from using unstable APIs in a migrated file. If waiting til build time is too late, @cleonard530 was considering a simple precommit linter that would simply verify that no unstable headers are added to the files under libtorch_stable, which wouldn’t gate against using a stable API introduced in a too new version but would be fast signal. 

2. The second prong is that, during runtime, the stable vLLM extension functions as expected with the target torch version. One example is the e8m0 float8 dtype wasn’t supported in stable til 2.11, and passing it in as a dtype through the dispatcher in python would not work for any version 2.10 and earlier. For this, test cases should catch and fail, but in general, to ensure all corners are covered we could add a CI job that runs tests on the target torch version (2.11 in the current case). 

Lastly, just a note that the whole CUDA migration will not be complete until the dependencies of the stable wheel are also stabilized (flashmla, deepgemm, fa3, fa2). I have been taking a look at these and feel confident we can do it but it’ll a few more weeks to update the forks of fa2/3 and create stable forks of flashmla and deepgemm. Look out for PRs soon!
