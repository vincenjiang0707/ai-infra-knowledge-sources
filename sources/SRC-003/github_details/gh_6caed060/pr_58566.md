# [PR #58566] [ROCm] Cut 69 wasted contiguous copies per decode step from the skinny GEMM path

state: open | updated: 2026-09-25T01:29:25Z

## 正文

## Summary

`rocm_unquantized_gemm_impl` hoists a contiguous copy above the two branches
that consume it:

```python
if use_skinny:
    x_view = x.reshape(-1, x.size(-1)).contiguous()      # always runs
    if (m == 1 or m > 8) and 0 < n <= 5:
        return wvSplitK(..., x_view, ...)                # uses it
    elif m % 4 == 0 and n == 1 and k <= 8192 and bias is None:
        return LLMM1(..., x_view, ...)                   # uses it
    # neither matched -> fall through

if rocm_aiter_ops.is_tgemm_enabled():
    return tgemm.mm(x, weight, bias)                     # uses ORIGINAL x
return torch.nn.functional.linear(x, weight, bias)       # uses ORIGINAL x
```

The outer `use_skinny` gate is broad — ROCm gfx9/gfx11, fp16/bf16,
`k % 8 == 0` — while the inner conditions are narrow (`0 < n <= 5`, or
`n == 1`). Any shape that passes the gate and matches neither builds `x_view`,
discards it, and falls through to a path that uses the original `x`.

This moves the copy into the two branches that use it. The discarded value is
dead, so every path that consumed `x_view` still receives exactly the same
tensor.

## Results

```bash
Kimi-K3 FP4, 8x MI355X, TP8, concurrency 1, MTP depth 6, 384K-token context.
The layer that hits this is `f_b_proj` at **m=7, n=1536, k=128**: `k % 8 == 0`
passes the gate, `(m == 1 or m > 8)` is false, `m % 4 == 0` is false. Its input
is a 128-column slice of a 6284-wide projection output, so it is row-strided
and the copy is real work rather than a no-op.
```

BF16 `direct_copy_kernel_cuda`, same image and context, 6-step decode window:

| | per step | cost |
|---:|---:|---:|
| before | 73.0 | 0.3609 ms/step |
| after | 4.0 | 0.0218 ms/step |
| **removed** | **69.0** | **0.339 ms/step** |

69 removed per step is exactly one per KDA layer. Each moved 1,792 bytes for
about 4.8 us, so the cost was almost entirely launch overhead rather than
bandwidth. The 4 per step that remain are unrelated int64 index copies.

## How the copy was attributed

```bash
Not by reading the source — two earlier guesses from source were wrong. The
evidence is from profiles:
```

1. The kernel template is `gpu_kernel_impl_nocast<...(c10::BFloat16)>`, i.e. a
   same-dtype layout copy, not a dtype cast.
2. Fingerprinting neighbours in the kernel timeline put 420 of 438 copies
   directly between two Tensile GEMMs.
3. Re-running with CUDA graphs disabled kept all 438 copies, so they are not
   inserted by compilation. Every one then resolves through its `cpu_op`
   parents to:

   ```
   aten::copy_ <- aten::clone <- aten::contiguous <- vllm::rocm_unquantized_gemm
   ```

   414 of 414 attributed, 69 per step.
4. The control-flow arithmetic on the actual shape confirms both inner
   branches are false, so the copy is discarded.

A competing hypothesis — that Inductor inserted the copy because the custom op
carries no layout tag — was tested on GPU by tagging the op
`torch.Tag.flexible_layout`, and rejected: the count stayed at 73.0 per step.

## Correctness

No FLOPs change and no numerics change. The removed value was never read on
the affected path; on the two paths that do read it, the same
`x.reshape(-1, x.size(-1)).contiguous()` is still evaluated before use.

## Who is affected

No flag changes are needed to pick this up. `VLLM_ROCM_USE_SKINNY_GEMM`
defaults to `True`, so a stock ROCm deployment is already on the affected
path; the configuration measured above sets nothing related to it.

The waste occurs when the broad outer gate passes and both narrow inner
conditions miss:

| condition | |
| --- | --- |
| `VLLM_ROCM_USE_SKINNY_GEMM` | default `True` |
| `on_gfx9() or on_gfx1x()` | true on gfx950 (MI355X) |
| `x.dtype in [fp16, bf16]` | true for these activations |
| `k % 8 == 0` | 128 % 8 == 0 |
| `skinny_operands_compatible` | contiguous weight and bias |
| **inner:** `(m == 1 or m > 8) and 0 < n <= 5` | **false** at m=7, n=1536 |
| **inner:** `m % 4 == 0 and n == 1 and ...` | **false** at m=7, n=1536 |

Two consequences worth stating plainly, so the scope is not overread:

- A model whose GEMM shapes *do* match an inner branch was always consuming
  `x_view`, so there is nothing to remove and no change is expected.
- Anyone running with `VLLM_ROCM_USE_SKINNY_GEMM=0` never entered this block
  and is unaffected.

```bash
The copy is only real work when the input is non-contiguous. Here it is: the
`f_b_proj` input is a 128-column slice of a 6284-wide projection output. A
shape that passes the gate with an already-contiguous input pays a cheaper
no-op rather than a full copy.
```

## End-to-end (side note)

Deliberately last, and not the claim being made. 0.339 ms/step is roughly 1.5%
of a 23.5 ms decode step at this operating point, which is close to the
run-to-run spread we measure on this workload (~0.8%), and end-to-end
throughput also depends on the tuning of the surrounding GEMMs and attention
kernels. The removed copy count above is the honest result.

The benefit is not specific to Kimi-K3: any ROCm model whose GEMM shapes pass
the `use_skinny` gate while missing both inner conditions pays this today.
