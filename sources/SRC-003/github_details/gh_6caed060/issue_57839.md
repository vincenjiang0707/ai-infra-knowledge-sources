### 🐛 Describe the bug

Two related gaps after #56122.

### 1. Reference detection server cannot detect `dual_key_gumbel` output

`examples/basic/online_serving/watermark_detection_server.py` always constructs `GumbelWatermarkDetector` (line 60). Its argparse takes only `--tokenizer / --key / --prf / --context-width / --p-value-threshold`. There is no `--algorithm` or `--alpha`, so text generated with `algorithm="dual_key_gumbel"` cannot be detected with the reference server. `docs/features/watermarking.md` points users at this server as the deployment pattern (line 228). It should accept `--algorithm dual_key_gumbel --alpha <value>` and build `DualKeyGumbelWatermarkDetector`.

### 2. Detector `alpha` default disagrees with generation default

- `DualKeyGumbelWatermarkDetector.__init__` defaults `alpha=0.2` (`vllm/v1/watermarking/gumbel.py:220`)
- `WatermarkConfig.alpha` defaults to `0.1` (`vllm/config/watermarking.py:35`), as does `DualKeyGumbelWatermarker` (`gumbel.py:107`)

The detector uses `alpha` in the variance normalization (`gumbel.py:252`: `variance = (1 - self.alpha) ** 2 + self.alpha ** 2`), so a silent default mismatch changes p-values. Suggest aligning the detector default to 0.1, or dropping the default and requiring `alpha` explicitly.

### Docs nit

Worth a one-line note in the constraints section that `deduplicate_contexts` and speculative decoding are mutually exclusive in effect today. It is stated at `docs/features/watermarking.md:80-82`, but under the spec-decode heading where it is easy to miss.

### TQCB · 2026-09-21

Reposting here: we should not expect the reference server to implement all possible watermarking schemes. It is a minimalist example to show how a detection endpoint can be set up, it is not production ready. Downstream users should use it as a reference for creating their own endpoint that also handles key, tokenizer, and watermarking candidate management

### simon-veitner-redhat · 2026-09-21

Adding to @TQCB to stress that the public example can't be used for production at all. 
Adverserial user can query a detection endpoint and either remove the watermark or make a fake watermark stamp without knowing the key. Detection in production should properly guard against that and the example does not do that!
