## Purpose

`(H200 MIG 35GB) Spec Decode AL DFlash Nightly` (`spec-decode-dflash-nightly`) has failed 18 nightlies in a row. Right now the only failure is `test_dflash_correctness[qwen3.8-dflash2-nvfp4-mrv2]` (1 failed, 5 passed). Latest failure: https://buildkite.com/vllm/ci/builds/90771#01a0d019-ffc5-47a3-954a-14cfa549c6e9

The config (target `nvidia/Qwen3.8-27B-NVFP4` + draft `z-lab/Qwen3.8-27B-DFlash2`) was added in #55960. It doesn't fit on a 35GB MIG slice:

- budget: 0.85 × 32.5 GiB = 27.62 GiB
- weights: 22.88 GiB (H200 has no native FP4, so this goes through the Marlin fallback)
- CUDA graphs: 1.11 GiB
- KV cache: **-0.53 GiB**, so `ValueError: No available memory for the cache blocks`

This PR:
```
1. Deselects the dflash2 config on the H200 35GB step with `-k "not dflash2"`. #55960 already did the same for the MI300 mirror. The other 5 params (qwen3 mrv1/mrv2, laguna-nvfp4, reference ALs) still run on H200.
2. Adds `:nvidia: (B200) Spec Decode AL DFlash2 Nightly` (`spec-decode-dflash2-nightly-b200`, `b200-k8s`, optional/nightly, 60 min). It runs only `-k "dflash2"`, with the same source deps as the DFlash nightly step minus the Laguna file. B200 has enough memory for this model and native FP4.
```

### Why not #58250
#58250 reverts #55960 entirely, including the fused DFlash2 kernel and its test. The kernel isn't the problem. The problem is that the test was scheduled on hardware too small for the model. Note that the `6.14 * 0.95` acceptance-length threshold has never passed on any CI hardware, so the first B200 run will be the first real check of that threshold. It may still need tuning.

### Not a duplicate
I ran `gh pr list --repo vllm-project/vllm --state open --search "dflash"`. The only related open PR is the #58250 revert. No open PR moves or deselects this config.
