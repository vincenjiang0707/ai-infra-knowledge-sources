### 🐛 Describe the bug

FP8 block-scaled weights (`compressed-tensors` w8a8) fail to load on sm120 with a DeepGEMM assertion. It happens in `process_weights_after_loading` — during weight loading, before any inference — so the engine never starts:

```
RuntimeError: Assertion error (/workspace/.deps/deepgemm-src/csrc/apis/layout.hpp:60): Unknown SF transformation
```

Full call chain (both TP workers fail identically):

```
compressed_tensors_w8a8_fp8.py:169  process_weights_after_loading
  -> kernels/linear/scaled_mm/deep_gemm.py:96  process_weights_after_loading
    -> quantization/utils/fp8_utils.py:1138  deepgemm_post_process_fp8_weight_block
      -> quantization/utils/fp8_utils.py:1077  deepgemm_post_process_weight_scale_block
        -> utils/deep_gemm.py:494  transform_sf_into_required_layout
          -> _transform_sf_into_required_layout_impl
            -> deepgemm csrc/apis/layout.hpp:60  "Unknown SF transformation"
```

The reason this is reached rather than skipped is that vLLM treats sm120 as a supported DeepGEMM target. `vllm/utils/deep_gemm.py` gates on capability family 100 **or** 120 in two places (lines 42-43 and 79-80), and `is_deep_gemm_supported()` documents "only Hopper and Blackwell GPUs are supported" — so consumer Blackwell selects the DeepGEMM path, and then DeepGEMM's own layout transform rejects the scale-factor layout it is handed.

Either the SF transform needs an sm120 case, or the capability-family-120 gate should exclude this path for block-scaled FP8 weights.

### Reproduction

```bash
docker run --gpus all --ipc=host -e CUDA_VISIBLE_DEVICES=0,1 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:muse-glimmer \
  --model RedHatAI/Muse-Glimmer-30B-FP8-block \
  --tensor-parallel-size 2 --gpu-memory-utilization 0.88 --max-model-len 131072
```

Fails ~75 s in, at weight loading, reproducibly.

### Workaround

`VLLM_USE_DEEP_GEMM=0` (plus `VLLM_MOE_USE_DEEP_GEMM=0`) makes the same command work. With that set the model loads and serves normally on 2x RTX 5090 — 177.6 tok/s decode with DFlash speculative decoding, 663,458-token KV cache — so only the DeepGEMM SF-layout path appears to be affected, not FP8 on sm120 in general.

I have not tested whether NVFP4 or non-block-scaled FP8 checkpoints hit the same transform on this hardware; the NVFP4 variant of the same model loads fine with DeepGEMM left at its default.

### ivanusto · 2026-08-31

This looks fixed upstream, and by something outside vLLM, so it is worth retesting before anyone spends time on it.

The assert you hit comes from DeepGEMM, and the pin moved. #52035 (merged Aug 12) changed `cmake/external_projects/deepgemm.cmake` from `vllm-project/DeepGEMM@e21c821` to `deepseek-ai/DeepGEMM@8b1392b`. In `csrc/apis/layout.hpp`, the SF transformation conditions that were `arch_major == 10` are now `arch_major == 10 or arch_major == 12`, with an added transpose for the K-major SF layout SM120 accepts. Under the old pin nothing in that function matched a capability 12 device, which is what produced `Unknown SF transformation`.

I ran the identical call under both pins on a GB10, changing nothing but the image:

| image | result |
| --- | --- |
| `vllm/vllm-openai:muse-glimmer` (`0.26.1rc1.dev608+g99a10304d`), the one in your report | `RuntimeError: Assertion error (csrc/apis/layout.hpp:60): Unknown SF transformation` |
| `vllm/vllm-openai:nightly-aarch64` (`0.26.1rc1.dev1219+g46638857f`) | returns `(1024, 4) int32` |

Reproducer, seconds, one GPU, no weights:

```python
import torch, vllm.utils.deep_gemm as d
d.transform_sf_into_required_layout(
    torch.ones(1024 // 128, 2048 // 128, dtype=torch.float32, device="cuda"),
    mn=1024, k=2048, recipe=(1, 128, 128), is_sfa=False)
```

One caveat you should weigh: I am on sm_121 (GB10) and you are on sm120 (RTX 5090). The fix is written as `arch_major == 12`, which covers both 12.0 and 12.1, and the failure you saw was the dispatch matching nothing rather than a kernel misbehaving, so I would expect it to clear on your hardware too. I cannot confirm that directly since I do not have a 5090.

Any build after Aug 12 should do. If it still fails for you on a current nightly, that would be a genuinely different problem from the one in the traceback above and worth saying so here.

For context, I hit the same assert through a different model on sm_121 and filed #52732, which is now closed for this reason.

### ivanusto · 2026-09-24

Status refresh, because the pin under this issue moved again and the failure mode changed.

`cmake/external_projects/deepgemm.cmake` went from `vllm-project/DeepGEMM@ad1f1726` to `a6bbb8000161c0dc3a85a0300a905f76898a7913` in #57218 (merged 09-16). That range includes the fork's `fix(sm120): correct ported GEMM and MQA execution paths`, which touches `sm120_dispatch.hpp`, `sm120_bf16_gemm`, `sm120_fp8_fp4_gemm_1d1d`, `sm120_tf32_hc_prenorm_gemm`, `sm120_fp8_mqa_logits`, `sm120_fp8_paged_mqa_logits` and `sm120_split_k_reduce`.

I ran an A/B of the two pins on a GB10 (sm_121), same image and same vLLM commit on both sides, weight free, so DeepGEMM is the only difference.

**UE8M0 scales, which is what the serving path uses: unchanged to the digit.**

| M x N x K | `ad1f1726` | `a6bbb80` |
|---|---|---|
| 1 x 7168 x 4096 | rel 0.0 | rel 0.0 |
| 83 x 4096 x 7168 | rel 1.310e-7 | rel 1.310e-7 |
| 2048 x 7168 x 4096 | rel 1.250e-7 | rel 1.250e-7 |

**Float32 block scales: the silent wrong answer became a loud refusal.**

| M x N x K | `ad1f1726` | `a6bbb80` |
|---|---|---|
| 1 x 128 x 256 | NaN in 0.78% of outputs | host assert |
| 7 x 512 x 4096 | NaN in 22.1% | host assert |
| 83 x 7168 x 4096 | NaN in 11.3% | host assert |
| 4096 x 13824 x 16384 | NaN in 38.7% | host assert |

The new failure is `Assertion error (csrc/apis/sm120_dispatch.hpp:127): sfa.scalar_type() == torch::kInt and sfb.scalar_type() == torch::kInt`, raised before launch. No Xid, no poisoned CUDA context, the process keeps running.

So the original `Unknown SF transformation` remains fixed, and the SM12x pure FP8 1d1d path still cannot take float32 scales, it just says so now. The vLLM-side gate for that selection is #57512, and #58157 warns when a float32-scale checkpoint gets requantized to UE8M0.

One caveat on hardware: my numbers are sm_121 (GB10), this issue is sm_120 (RTX 5090). The dispatch and the assert are shared by the 12.x family, but I cannot speak for 5090 specific behaviour.
