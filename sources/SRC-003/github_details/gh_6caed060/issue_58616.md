# [Issue #58616] vllm serve segfaults deterministically right after weight loading (single L4 GPU, V1 engine) — only avoided by VLLM_TRACE_FUNCTION=1

source: https://github.com/vllm-project/vllm/issues/58616
state: open | updated: 2026-09-24T21:25:37Z
labels: 

## 正文

### Description

`vllm serve` segfaults deterministically right after model weight
loading completes, during the internal profile run (before KV cache
size is computed) — on a single NVIDIA L4 GPU (Ada, SM 8.9), serving
`Qwen/Qwen3-1.7B-Base` in bf16 with `--enforce-eager`.

The crash is 100% reproducible, always at the exact same point, and
survives every targeted configuration change I tried. The only thing
that avoids it is `VLLM_TRACE_FUNCTION=1`, which slows down execution
massively and produces a clean, healthy startup instead — suggesting a
race condition sensitive to real-time execution pacing, not a
configuration error.

### Environment

- vLLM versions tested: **0.20.2** and **0.22.0** (identical crash on
  both)
- GPU: 1x NVIDIA L4 (Ada Lovelace, SM 8.9) — Hugging Face Spaces
  `l4x1` hardware
- Base image: `nvidia/cuda:12.4.1-runtime-ubuntu22.04`
- Python: 3.11
- Torch: 2.11.0 (as resolved for vLLM 0.22.0)
- Model: `Qwen/Qwen3-1.7B-Base`, dtype bf16
- Single GPU, `tensor_parallel_size=1` (no parallelism)

### Reproduction

```bash
vllm serve Qwen/Qwen3-1.7B-Base \
    --enable-lora \
    --lora-modules dpo=<a private LoRA adapter repo> \
    --max-lora-rank 16 \
    --enforce-eager \
    --port 8000
```

```
(The crash also happens with `--enable-lora`/`--lora-modules`/
`--max-lora-rank` entirely removed — see "Ruled out" below.)
```

### What I ruled out (each tested independently, in a real deployment, same crash every time unless noted)

1. **`VLLM_ENABLE_V1_MULTIPROCESSING=0`** — no effect (this variable
   only applies to the offline `LLM()` path, not `vllm serve`,
   confirmed by reading `vllm/v1/engine/core_client.py`:
   `make_async_mp_client` is called unconditionally for the async
   server).
2. **Container running as root vs. explicit non-root UID 1000** —
   fixed a real permissions issue (Triton JIT cache resolution under
   `$HOME`), kept as a real fix, but did **not** affect this crash.
3. **LoRA / Punica** — tested with `--enable-lora` fully removed, on
   *both* 0.20.2 and 0.22.0. Identical crash both times, with no
   `PunicaWrapperGPU`/LoRA-kernel log lines at all. Not the cause.
4. **Attention backend** — `--attention-backend FLASHINFER` instead of
   the default FlashAttention2. Confirmed active via log
   (`Using AttentionBackendEnum.FLASHINFER backend.`). Identical
   crash.
5. **`--no-async-scheduling`** — confirmed active via
   `non-default args` log (`'async_scheduling': False`). Identical
   crash.
6. **Fixed startup delay** — added `sleep 20` before `vllm serve` to
   rule out the GPU/driver context not being fully stabilized right
   after a fresh container/GPU allocation. Identical crash.
7. **vLLM version** — 0.20.2 → 0.22.0, identical crash (0.22.0's
   `torch==2.11.0` pin was verified compatible with Python 3.11 before
   testing). A further jump to 0.28.0 was not reachable: its resolved
   torch dependency requires Python 3.12 (`sys.get_int_max_str_digits`,
   added in 3.12), unrelated to this bug.

### The one thing that "fixes" it (but isn't usable)

Setting `VLLM_TRACE_FUNCTION=1` (traces every Python function call,
documented as a >100x slowdown) results in a **complete, healthy
startup** — model loads, LoRA adapter loads, KV cache is sized, the
OpenAI-compatible server comes up and serves `/health` successfully.
This is not viable for real traffic due to the slowdown, but strongly
suggests a race condition whose outcome depends on real-time execution
pacing, rather than a deterministic logic bug tied to any single flag
above.

### Additional environment note

I could not test a different GPU architecture as an additional data
point: switching this same Space to `a10g-large` hardware left the
container stuck indefinitely at boot (no logs at all beyond the
platform's own startup banner, not even reaching vLLM's own startup
banner), reproduced on two separate restarts. I reverted to `l4x1`
rather than continue debugging what looks like an unrelated
provisioning issue on that hardware class, so I cannot say whether
this bug is Ada-architecture-specific.

Happy to provide the full uncut logs for either vLLM version, or run
further targeted diagnostics, if useful.

### racemartin · 2026-09-24

Follow-up: checked `nvidia-smi` and `torch.version.cuda` right before `vllm serve` starts, to rule out a driver/CUDA-runtime mismatch (our base image is CUDA 12.4.1, while torch 2.11.0 pulls in nvidia-*-cu13 wheels). Driver is 580.178.04, natively supports CUDA 13.0; `torch.version.cuda=13.0`, `torch.cuda.is_available()=True`. GPU/driver is healthy — this rules out that theory too.

### racemartin · 2026-09-24

**Update — found a workaround that resolves this for me.**

Rebuilding the deployment image `FROM vllm/vllm-openai:latest` (instead of installing vLLM manually via pip into a generic `nvidia/cuda` base image) makes the segfault disappear entirely — clean startup, LoRA adapter loads, `/health` returns 200, no crash at any point.

Since the official image is what the vLLM team itself builds/tests, whatever subtle difference existed in my hand-rolled build (exact system package versions, build flags, etc.) isn't present there. I don't have a root cause beyond that, but wanted to share the workaround in case it helps anyone else hitting the same wall. Closing this out on my end — feel free to close, or keep open if it's useful as a known-workaround reference for others.
