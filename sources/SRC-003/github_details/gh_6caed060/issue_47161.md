# [Issue #47161] [RFC]: Streaming Derender for Disaggregated Serving

state: open | updated: 2026-09-24T10:51:59Z

## 正文

### Motivation.

The batch derender endpoints (`/v1/chat/completions/derender`, `/v1/completions/derender`) landed in #43606 (detokenization) and #45919 (non-streaming reasoning/tool parsing). They consume `GenerateResponse` and emit a complete `ChatCompletionResponse`.

Many real world disaggregated consumers cannot use a batch only post processing tier:

- **Interactive serving** (llm-d, Dynamo) returns tokens to end clients as they are generated. Streaming is a **hard gating requirement** (ref: @bbrowning in https://github.com/vllm-project/vllm/issues/42729#issuecomment-4631310758).
- The producer side already streams e2e. `/inference/v1/generate` returns an SSE `StreamingResponse` when `request.stream` is set (`scale_out/token_in_token_out/api_router.py`), emitting `GenerateStreamResponse` chunks whose `GenerateResponseStreamChoice` carries the delta token IDs per step (`scale_out/token_in_token_out/serving.py`). `/render` already forwards `stream` / `stream_options`. **It therefore needs to be implemented on the  derender side.**

This RFC specifies a streaming derender that is the inverse of the streaming render path.

#### Why is this not a flag on the derender batch endpoint?

1. **Different input type.** The batch path (#42729) consumes a complete `GenerateResponse`. Streaming consumes `GenerateStreamResponse` *deltas*. It is therefore a distinct request shape and not a parameter on the existing endpoint.
2. **Incremental detokenization is stateful.** `IncrementalDetokenizer` carries `prefix_offset` / `read_offset` / prior tokens across `update()` calls. A naive per chunk `tokenizer.decode()` produces wrong spacing and can split multi-byte characters (see #44620). The per step delta `token_ids` are the right incremental input. `GenerateStreamResponse` however does **not** carry the detokenizer offsets and that state has to come from somewhere.
3. **Streaming parsers are stateful too.** Reasoning/tool parsers maintain incremental parse state across deltas (the reasoning to content/tool transition, partial tool call JSON). This compounds the state transport question below.

### Proposed Change.

#### New endpoints

| Method | Path | Input | Output |
|--------|------|-------|--------|
| `POST` | `/v1/chat/completions/derender` (`stream: true`) | `DerenderChatStreamRequest` | JSON `{ "chunk": ChatCompletionStreamResponse, "stream_state": DerenderStreamState }` |
| `POST` | `/v1/completions/derender` (`stream: true`) | `DerenderCompletionStreamRequest` | JSON `{ "chunk": CompletionStreamResponse, "stream_state": DerenderStreamState }` |

> [!NOTE]
> Streaming reuses the same `derender/` path with a `stream: true` flag, mirroring the producer (`/inference/v1/generate`). FastAPI validates a typed union discriminated on the `stream` literal and the handler dispatches with `isinstance`. The existing non-streaming types keep `generate_response` required.

Both endpoints run on the existing render server (GPU-free, only the `Renderer`/tokenizer) and are **stateless**.

#### Response format: plain JSON per call, not SSE

The derender is a **stateless per chunk translator**: one request in to one `{ "chunk", "stream_state" }` out. SSE out was rejected because it requires either a long lived connection or buffering all chunks before calling derender. This both conflict with the stateless design (Option A). The SSE protocol lives on the generate side and the final usage chunk are the client's responsibility.

#### Core design decision: incremental state (Option A, stateless)

The server returns updated state in each chunk. The client echoes it back on the next chunk. Server stays stateless and idempotent. There is no `request_id` keyed session and no lifecycle/eviction on the render tier.

Other design decision considered:

```
- **Option B (server-side session keyed by `request_id`)**: rejected because it breaks statelessness and adds session lifecycle + eviction + memory pressure.
- **Option C (shm state transport)**: deferred as a future optimization for large round tripped state on long generations. Only consider after Option A's payload cost is measured.
```

#### Parser state: replay (no opaque serialization)

Tool parsers hold internals we can't cheaply round trip (`prev_tool_call_arr`, `current_tool_id`, `streamed_args_for_tool`, engine lexer buffers). Rather than serialize them, the streaming chat derender **rebuilds a fresh parser each chunk by replaying the output tokens through it**, then feeds the new chunk and emits whatever the parser hands back.

Replay keeps the producer's chunk boundaries. `stream_state` carries `output_chunk_lens` (the token count of each chunk as it arrived) next to `output_token_ids`. Every chunk, replayed or live, goes through one `parse_delta` call. That matches standard serving which calls `parse_delta` once per engine step, so a multi-token step (e.g. speculative decoding) rebuilds the same parser state. Per token replay could diverge because some parser state (e.g. `history_tool_call_cnt`) advances once per `parse_delta` call. Text comes from a throwaway incremental detokenizer with `skip_special_tokens=False`, so the parser sees `</think>` / `<tool_call>` markers exactly as generate emits them.

Here are a few things to be aware of:

```
- **Cost:** transport is O(n) per chunk → O(n²) over a generation. Replay is one `parse_delta` call per prior chunk → O(n²) calls over a generation. `parse_delta` is itself O(n) for parsers that re-scan the accumulated text (Hermes tool call JSON, DeepSeek-R1 reasoning), so compute is O(n³) character work. `prompt_token_ids` is also sent and re-scanned on every chunk, so on long prompts it dominates the payload. Prompt + history + delta is bounded by `max_model_len` and rejected past it. Replay runs off the event loop on the renderer's executor (`renderer_num_workers`, default `1`), so size it for concurrent parser configured streams. Documented in `derenderer.md`.
- **Measured:** @shimib's benchmark (https://github.com/vllm-project/vllm/issues/56851#issuecomment-5685698033) found ~9× the in-process CPU at matched load and +15% E2E p50 on multi-thousand-token reasoning outputs. With the default single worker, the tier saturated under concurrent parsed streams.
- **Tool call ID stability:** IDs (`random_uuid()`, and `kimi_k2` style IDs derived from `history_tool_call_cnt`) are pinned in state and reused, so a replay never changes an ID the client has already seen. This isn't only defensive. Under `tool_choice="required"`, `extract_required_tool_call_streaming` resets `function_name_returned` to `False` whenever the partial JSON transiently fails to parse which makes a from scratch replay re-emit `id`+`name` for an index that already has one.
- **Future:** latency sensitive interactive traffic is better served by #56851, which keeps the parser alive for the request on the decode pool instead of replaying. For stateless consumers, an LRU of live `Parser` instances keyed by `(request_id, choice_index)` would skip replay on a cache hit and get compute back to O(delta) with no protocol change. It needs its own design for eviction, memory bounds and chunks routed to different replicas (#57571). Serializing parser state was tied to #32713 which was closed as not planned.
```

> [!NOTE]
> **This was originally specified as replay + diff** — re-run one-shot `parse()` over the accumulated output each chunk and diff against the last emission. Two reasons for the change in design:
>
> 1. `HarmonyParser.parse()` always calls `flush()` → `process_eos()`. Mid-stream that throws and the recovery path re-emits the in-flight message on the `final` channel. Partial reasoning comes out as content with a warning logged every chunk.
> 2. On partial markup like `<tool_call>{"name": "get_w`, `extract_tool_calls` fails the JSON load and returns the raw markup as content. Once the call completes, `parse()` returns *shorter* content and a diff that only moves forward can't take back what it already sent.
>
> `Parser.parse_delta()` and its `StreamState` landed after this RFC was written and gives the incremental semantics directly. So replay stays since it's still the answer to non-serializable parser state and the diff goes away. This swaps the diff step, not the replay step, so it isn't more expensive than what this RFC already accepted. The O(n³) above is the RFC's own replay cost stated more precisely.

#### Detokenization state: carried offsets

PR #47301 landed this differently than understood initially. Instead of rebuilding the decode window from the full token history each chunk, the state carries the incremental decode offsets directly: `prev_tokens` (the trailing window), `prefix_offset` and `read_offset`. `detokenize_incrementally` only ever reads `prev_tokens[prefix_offset:]`, so we carry just that tail then trim and rebase it after each chunk.

Compute is O(delta) per chunk and transport is O(window) which means the state doesn't grow with generation length. Held back multi-byte sequences still work because `read_offset` tracks the partially read character across the chunk boundary. Guarded by token-by-token CJK/emoji parity tests (`chunked == one-shot`) so #46159 stays fixed.

This only covers the completions path and the chat path with no parser. The parser path never reads these fields. It replays, carrying the output tokens instead (see above) and builds its own throwaway detok window per call. #46159 is guarded on that path too with
CJK/emoji tests across the reasoning→content transition.

#### Protocol additions

`vllm/entrypoints/scale_out/token_in_token_out/protocol.py`:

```python
class DerenderStreamState(BaseModel):
    # Detok state for completions, and chat with no parser. Bounded.
    prev_tokens: list[str] = []
    prefix_offset: int = Field(default=0, ge=0)
    read_offset: int = Field(default=0, ge=0)
    role_sent: bool = False               # emit role:"assistant" once
    # Parser path. Replay buffer, bounded by max_model_len.
    output_token_ids: list[int] = []
    output_chunk_lens: list[int] = []     # tokens per chunk, each > 0, sums to len(output_token_ids)
    tools_streamed: bool = False          # drives the finish_reason rewrite
    last_tool_call_ids: list[str] = []    # pinned IDs, stable across replays


class DerenderChatStreamRequest(BaseModel):
    stream: Literal[True]
    model: str | None = None
    generate_chunk: GenerateStreamResponse
    stream_state: DerenderStreamState | None = None  # absent on first chunk
    prompt_tokens: int | None = None                 # count, for usage
    prompt_token_ids: list[int] | None = None        # parser path
    chat_request: ChatCompletionRequest | None = None

class DerenderCompletionStreamRequest(BaseModel):
    stream: Literal[True]
    model: str | None = None
    generate_chunk: GenerateStreamResponse
    stream_state: DerenderStreamState | None = None
    prompt_tokens: int | None = None
    completion_request: CompletionRequest | None = None
```

The existing non-streaming types gain `stream: Literal[False] = False` (backward compatible).

`last_content` / `last_reasoning` from #47301 are removed as they are not required.

`prompt_token_ids` is added. `parse_delta` needs the prompt IDs to work out whether reasoning is already open when generation starts. Chat templates that end in `<think>` misclassify the first tokens without it. The existing `prompt_tokens` is a usage count and can't stand in. Clients already have the IDs: they come back as `GenerateRequest.token_ids` from `/render`. It stays optional on the model (a caller with no parser configured never sends it) and is enforced server side instead.

`output_chunk_lens` is added so replay can reuse the chunk boundaries the generate stream produced (see Parser state). It grows by one entry per chunk which is one per token without speculative decoding.

Responses are typed too: `DerenderChatStreamResponse` and `DerenderCompletionStreamResponse`, each `{chunk, stream_state}`.

**On state size.** The replay buffer is O(n) and there's no way around that. Rebuilding parser state without serializing it is what replay means. It's bounded by `max_model_len` and rejected past that. Everything else (completions, chat without a parser) keeps the bounded window and pays nothing.

> [!NOTE]
> **Single delta, not a list.** The batch `DerenderCompletionRequest` carries `list[GenerateResponse]`. Streaming is inherently per stream, so each chunk carries one `generate_chunk`. Fan out over multiple completions becomes N independent streams with one `DerenderStreamState` each (keyed by `choice.index`) and not a batched list. The completions path leaves the parser fields (output_token_ids, output_chunk_lens, tools_streamed, last_tool_call_ids) unused.

##### Message validation

`stream_state` is entirely client controlled, so the streaming chat endpoint validates before it touches the tokenizer and returns `400` and never `500`:

- **`chat_request` missing while a parser is configured** → reject. Falling through to plain detok would leak raw harmony/tool markup into `content`. The same check now applies to the **batch** path which silently degraded this way before PR #50550 (same class of bug as #45834).
- **`prompt_token_ids` missing while a parser is configured** → reject, rather than silently misclassifying prompt opened reasoning as content.
- **More than one choice in a chunk** → reject. One `DerenderStreamState` is threaded through the chunk, so multiple choices would corrupt each other's detok/parser state.
- **`len(prompt_token_ids) + len(output_token_ids) + len(delta)` over `max_model_len`** → reject. This bounds the replay buffer and the prompt re-scan every chunk does.
- **Inconsistent `output_chunk_lens`** (doesn't sum to `len(output_token_ids)`, or contains a zero entry) → rejected when the request is validated.

An unexpected parser failure on well typed but malformed state also surfaces as a `400` rather than an unhandled `500`: Hermes swallows its own streaming exceptions but `finalize_generation` and the engine based parsers do not.

#### Streaming flow

```
client                         render tier (stateless)
  │  DerenderChatStreamRequest(generate_chunk Δ_0, stream_state=None)
  ├──────────────────────────────►  fresh parser, feed Δ_0 through parse_delta
  │  { chunk: Δ_0, stream_state: S_0 }
  ◄──────────────────────────────┤
  │  DerenderChatStreamRequest(generate_chunk Δ_1, stream_state=S_0)
  ├──────────────────────────────►  fresh parser, replay S_0 history one
  │                                 parse_delta per original chunk (discarded),
  │                                 then feed Δ_1 in one call
  ◄──────────────────────────────┤
  │              ...
  │  final usage chunk (client driven)
```

#### Streaming parsers

Parsers are driven through `parse_delta()`, one call per chunk as it arrived from generate, on a parser rebuilt from replay. It is not through one-shot `parse()` over an accumulated window. Token based parsers (Harmony `openai_tool_parser`, `is_reasoning_end` boundary logic) work unchanged since `parse_delta` receives both the decoded text and the token IDs for each step. Decoding uses `skip_special_tokens=False` so markers reach the parser intact.

`parse_delta` also needs the **prompt** token IDs to settle whether reasoning is already open when generation starts which is why `prompt_token_ids` is new on the request (see Protocol additions). The U+FFFD reasoning to content/tool transition fix (#46159) must not regress and is covered by chunk boundary tests on the parser path.

### Any Other Things.

#### Out of scope

- gRPC / msgpack transport (JSON/pydantic first, per #22817).
- Torch free / in-process parser library (#38925): orthogonal.
- `token_id:N` logprob shape redesign: tracked separately (#57574). Streaming logprobs themselves are in scope (see PR breakdown).
- Serialized parser state: dropped. #32713 was closed as not planned. Replay cost is handled by #56851 for latency sensitive P/D and optionally by a parser cache (#57571) for stateless consumers.  

#### Resolved questions

- **`parser_state` serialization:** avoided by replaying tokens through `parse_delta` on a fresh parser each chunk. #32713 was closed as not planned.
- **State transport:** **Option A** (stateless, client carried). B rejected. **C (shm) deferred.**
- **Routing:** same path + `stream: true`. FastAPI validates a typed union on the `stream` literal and the handler picks with `isinstance`. No manual JSON peeking.
- **Response format:** plain JSON per call. SSE out rejected as incompatible with Option A.
- **Parser path when the caller omits `chat_request` / `prompt_token_ids`:** fail closed with a 400 and is not a documented degradation. Both are recoverable client side. Silently emitting markup or misfiled reasoning is not.
- **Replay granularity:** one `parse_delta` call per original chunk, recovered from `output_chunk_lens`. Not one per token.
- **Replay cost:** measured (https://github.com/vllm-project/vllm/issues/56851#issuecomment-5685698033). Latency sensitive P/D goes to #56851 rather than adding server side state to the render tier.

#50550 has merged, so streaming chat derender now does reasoning and tool call parsing. Thanks @sagearc, @chaunceyjiang, @NickLucche  and @bongwoobak for the reviews.

### What landed in #50550

- Replay through `parse_delta` on a fresh parser each chunk. It emits the same `reasoning` / `content` / `tool_calls` deltas that `/v1/chat/completions` streams for the same tokens.
- Replay keeps the producer's chunk boundaries. `DerenderStreamState` now carries `output_chunk_lens` alongside `output_token_ids`, so a multi-token step (e.g. spec decode) goes through one `parse_delta` call on replay, just like in serving. 
- `prompt_token_ids` on the request, so the parser knows whether the prompt left reasoning open.
- Tool call ID pinning, the `finish_reason` rewrite to `tool_calls` and parallel tool call filtering.
- Fail closed 400s for:
  - a parser configured without `chat_request` (the batch path now checks this too)
  - missing `prompt_token_ids`
  - more than one choice per chunk
  - prompt + history + delta over `max_model_len`
- `model_config` passed to the batch parser, so it knows the model's `tool_call_id_type`. Batch derender still discards the parser's tool call ID, though. That's tracked under #42729.
- A "Streaming cost" section in `derenderer.md`.

### The replay cost has been measured

@shimib benchmarked the derender tier with #50550 applied (https://github.com/vllm-project/vllm/issues/56851#issuecomment-5685698033), on 1×A100-40G with Qwen3-8B and the hermes + qwen3 parsers. At matched load, detokenizing and parsing on the derender tier cost ~9× the in-process CPU. E2E p50 rose 15% on multi-thousand-token reasoning outputs. With the default `renderer_num_workers=1`, the tier also saturated under concurrent parsed streams until the pool was made bigger.

This RFC deferred a parser cache and parser state serialization "until the cost is shown to matter". For latency sensitive interactive traffic, it matters. Rather than add server side state to the render tier, I propose:

- **Latency sensitive P/D (llm-d):** #56851. Detokenization and parsing move onto the decode pool per request and the parser lives as long as the request does. There's no replay, no echoed state and no extra hop per chunk.
- **Stateless consumers (RL, batch, gateways that own postprocessing):** streaming derender as it is. An LRU of live parsers keyed by `(request_id, choice_index)` stays an optional optimization with no protocol change (#57571).
- Serializing parser state was tied to #32713 which was closed as not planned. I'm therefore  dropping it for now.
