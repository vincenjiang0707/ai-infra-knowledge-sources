## Purpose

**Draft for architectural review, not merge-ready.** Add an opt-in traced checkpoint reload path for FP8 linear and MoE layers through NCCL and CUDA IPC. The default remains the existing layerwise implementation.

Related: #54477 and #48312.

### Lifecycle

1. Register `ReloadState` and backend policies before initial checkpoint loading.
2. Observe ordinary parameter-loader arrivals during cold loading, retaining sharding metadata rather than checkpoint payloads. Routed experts instead derive their expected arrivals from the current expert mapping on each reload round.
3. After cold `process_weights_after_loading` (PWAL), bind runtime tensors and backend state.
4. On the first validated local arrival for a layer, prepare writable checkpoint-layout inputs. Reuse compatible dense runtime storage where the policy permits it; otherwise stage inputs. This restores a loadable layout, not the old checkpoint values.
5. Once a layer's expected slots and dependencies are complete, run its repeatable conversion, refresh bound runtime outputs in place, and release temporary checkpoint storage. Global finish checks completeness.

The FP8 processing plan separates cold-only installation/kernel construction from repeatable weight conversion. Existing model loaders retain checkpoint-name routing and sharding responsibilities. Shared parameters have explicit ownership/dependencies.

Enable explicitly:

```bash
--weight-transfer-config '{"backend":"nccl","reload_mode":"trace","preserve_checkpoint":false}'
```

`backend: "ipc"` is also supported. `preserve_checkpoint: true` opts into retaining checkpoint tensors and disables their runtime-storage reuse.

### Scope and contracts

- FP8 linear and MoE policies, including DeepGEMM, FlashInfer CUTLASS, and processing-plan-backed MoE variants. The latest layout-reuse migration also covers batched variants, AITER, and XPU paths.
- Earlier Marlin/Humming policy work is present on this branch, but their migration to the new preparation scheme is deferred and they are excluded from the latest regression selection.
- Complete checkpoint updates only. Inference must be paused/drained, and expert placement must remain fixed during each round. Rebuilding the expert plan between rounds does not coordinate concurrent EPLB movement.
- No rollback or model-wide atomic publication: runtime storage may be modified before global finish. A failed update must not return the worker to serving.
- No arbitrary shape/dtype/backend changes, general model-level PWAL support, or claim of universal quantization support. Unsupported configurations fail closed.
- Conversion scratch may still allocate. No measured peak-memory improvement is claimed.

### Relationship to existing work

I checked the RFC comments, open PRs referencing #48312/#54477, open reload PR titles, and this exact head branch before creating this draft. There is substantial related work; this is a materially different architecture for review, not a claim that reload has no existing implementation:

| Open work | Difference in this draft |
| --- | --- |
| #55595 selective FP8/CUTLASS reload | Replaces range-based staging accounting with ordinary cold-loader slot observation plus per-round routed-expert plans; introduces reusable loading layouts and multi-backend repeatable processing plans. CUTLASS conversion/storage concerns overlap. |
| #51378 modelwise transactions | Completes and releases staging per layer rather than deferring PWAL/publication to a whole-model transaction. No rollback guarantee. |
| #53438 manifest-driven modelwise streaming | Uses observed cold-load slots and dynamic expert plans with backend-owned conversion policies, rather than that modelwise manifest/arena lifecycle. |
| #50564 dummy-load manifest probing | Observes actual cold loading for ordinary layers; no dummy-load probing. Expert placement is not frozen from the cold trace. |
| #49789 ReloadArena | Focuses on policy-owned checkpoint/runtime conversion and layer completion, not a general graph-visible tensor/object arena. |
| #49459 layout-identical fast path | Also addresses layout-changing FP8 conversion and derived-state refresh. |

The implementation approaches should be reconciled before merge; this draft does not request merging overlapping designs independently. The differences are also recorded on RFC #54477.
