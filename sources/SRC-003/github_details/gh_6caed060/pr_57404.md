# [PR #57404] [Bugfix] Fail closed in is_uva_available() when the UVA alias is not live

source: https://github.com/vllm-project/vllm/pull/57404
state: open | updated: 2026-09-23T04:24:54Z
labels: bug, performance

## 正文

## Purpose

`is_uva_available()` only checks that pinned memory is available. That is necessary but not sufficient: the callers depend on the device view being a live alias of the host tensor, and nothing verifies that.

Under NVIDIA Confidential Computing, `pin_memory=True` silently yields an unpinned tensor. `get_accelerator_view_from_cpu_tensor` is gated on `is_pinned()`, so it takes the non-pinned branch and returns a detached one-time copy instead of a live view. Writes made after the view is created never reach the device. The V2 model runner fills its UVA buffers after creating them, so per-request sampling parameters arrive on the GPU as zeros and generation degenerates. Requests still return 200.

Because the predicate stays `True`, none of the existing fallbacks can engage. `NonUvaBuffer` from #56908 is only selected when it is `False`, `StagedWriteTensor` keeps the large tensors in UVA, and the weight offloader and the Engram models skip their guards.

This probes the contract at runtime: create the view, write to the host tensor afterwards, and confirm the device sees it. The probe needs an initialized accelerator, so callers that run before the worker sets its device get an optimistic answer that is not cached, and the worker-side call decides. It fails closed, since the fallback paths are correct and only slower. `@cache` moves from the predicate to the probe, so the answer is still resolved once per process.

Duplicate-work checks found no open PR that changes `is_uva_available()` itself. #50671 removes the `is_pinned()` gate in `cuda_view.cu` so the mapping is attempted where the hardware supports it; this is the other half, making the predicate honest so vLLM degrades safely where it does not. #54655 and #47579 consume the predicate rather than changing it. #52226 adds `is_confidential_compute()` for decode performance and is MRV1 only.

Hardware measurements are in https://github.com/vllm-project/vllm/pull/50671#issuecomment-5712253233

## Test Result

### Predicate

On the CC box `is_uva_available()` now returns `False` and logs the mismatch:

```
UVA reports available but the device view is not a live alias of host memory:
wrote [1, 2, 3, 4, 5, 6, 7, 8], device read [0, 0, 0, 0, 0, 0, 0, 0].
Falling back to explicit copies. This is expected under GPU Confidential Computing.
```

Unpatched it returned `True`. A driver-level probe confirms zero-copy itself is live on this hardware and only the torch pinned view is detached, so the failure is the alias contract rather than the GPU.

### Serving, before the fix

Predicate reverted, UVA path active:


Greedy is deterministic again and temperature is respected.

### Control on non-CC hardware

Same sequence, one variable changed:

```
                              A100 (no CC)      H100 NVL (CC on)
Tensor.is_pinned()            True              False
cudaHostGetDevicePointer      0 (no error)      0 (no error)
host wrote                    [1..8]            [1..8]
device read                   [1..8]            [0, 0, 0, 0, 0, 0, 0, 0]
coherence                     LIVE              DETACHED
```

The probe passes on ordinary hardware, so the predicate still returns `True` there and UVA stays enabled. Only the CC case flips.

### Unit tests

`test_uva_unavailable_when_view_is_detached` and `test_uva_unavailable_when_probe_raises` pass. `test_uva_available_when_alias_is_live` skips on the CC box, which is correct for that hardware.

The first run on CC also surfaced a problem in the file's existing guards. `@skipif(not is_uva_available())` is evaluated at collection time, before the accelerator is initialized, so it saw the optimistic `True` and the CC-dependent tests ran instead of skipping. The guard now resolves after initializing the device, and the two tests that patch the view no longer carry it since they do not need working UVA.

`benchmarks/benchmark_pin_memory.py` called `cache_clear()` on the predicate, so both call sites now point at the probe.

Lint, format and typos are clean.

## Notes

No throughput measurement for the explicit-copy path. It only engages where UVA is already broken, and the alternative there is incorrect output.

Not exercised: the weight offloader, `model_loader/utils.py`, the Engram models, and TP. They gate on the same predicate and should now fail with a clear error rather than corrupt silently.

The CC build used a 0.29.0 precompiled wheel over `main` sources because no per-commit cu130 wheel exists, so unrelated compiled-path failures in that run are ABI noise. The predicate result is corroborated independently by the driver-level probe.
