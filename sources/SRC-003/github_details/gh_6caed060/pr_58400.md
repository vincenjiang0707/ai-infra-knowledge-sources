# [PR #58400] [Perf][MRV2] Allow FULL decode graphs for one-token prompt tails

source: https://github.com/vllm-project/vllm/pull/58400
state: open | updated: 2026-09-25T01:02:40Z
labels: speculative-decoding, mrv2

## 正文

A one-token prompt tail over existing context runs exactly like a decode. This covers a full prefix-cache hit, a P/D KV import on the decode node, and a final one-token chunk. The scheduler may also pad such a tail with placeholder drafts to the K+1 spec-decode shape. The Mamba, GDN and KDA metadata builders already classify these rows as decodes.

Since #51865, any prefilling row made MRV2 reject the FULL decode graph for the whole batch. In P/D serving, every newly arriving request therefore pushed its step's decode batch down to PIECEWISE.

Classify graph eligibility from request state instead: a batch is eligible if every prefilling row schedules exactly one new prompt token (not counting drafts) over existing context. Fresh prompts and multi-token chunks are still excluded, so #49918 stays fixed. PCP batches keep the old behaviour.

- Add a decode_graph_eligible field on BatchReqState/InputBatch, computed in gather_batch_req_state. get_uniform_decode_token_count now takes decode_graph_eligible in place of has_prefill.
- The autoregressive and multi-module MTP drafters use the same flag, so they match the target model's graph mode.
- Compute the per-request draft counts once in gather_batch_req_state and reuse them in prepare_inputs.

This is an alternative / more general fix to https://github.com/vllm-project/vllm/pull/58374.

Note there is still an issue with hybrid models without this additional fix: https://github.com/vllm-project/vllm/pull/58434.

Used Opus 5.5 to help with this.

### seongyun1104 · 2026-09-25

The mechanism here is clearer than the description suggests, and I think it is worth
stating explicitly because it also marks where the gain stops.

**Why the current behaviour is a hard floor, not a heuristic.** Before this change a batch
with `has_prefill` got `uniform_tok_count = None`, and `_is_compatible` rejects every
descriptor that carries a concrete tier:

```python
# vllm/v1/worker/gpu/cudagraph_utils.py:116-120
    return (
        (
            desc.uniform_token_count is None
            or desc.uniform_token_count == uniform_token_count
        )
```

In the separate-decode-routine, non-varlen configuration (`:312`) every FULL decode
descriptor is built with `uniform_token_count=decode_query_len` (`:328`), so a `None` from
the caller could not match any of them — the batch went to PIECEWISE unconditionally, not
because a graph was missing but because it was unaddressable. Passing the real tier is
what makes those graphs reachable at all. That is a different and stronger claim than
"one-token tails behave like decodes", and it is consistent with the 1.62% → 0.00%
non-FULL share you measured.

For the varlen configuration the situation is the mirror image: those descriptors leave
`uniform_token_count` unset and constrain `max_query_len` instead (`:301-307`), which is
the field #58436 is separately restricting. The two paths are mutually exclusive
(`capture_varlen_decode` vs `separate_decode_routine and not self.varlen_decode`), so the
two PRs do not overlap — I checked, since they look adjacent.

**Where the newly eligible batches land.** `decode_query_lens` is plural only under dynamic
SD, where it is derived from the schedule (`:284-289`); otherwise it is a single value
(`:291`). When it is plural, one descriptor per tier is appended to the same
`descs_by_mode[decode_mode]` list (`:333-334`), and the candidate ladder then consumes the
range once across all of them, grouped only on `num_tokens`:

```python
# :377-385
                current_range_start = 0
                for num_tokens, group in groupby(lora_descs, lambda d: d.num_tokens):
                    matching = list(group)
                    for i in range(current_range_start, num_tokens + 1):
                        key = (i, num_active_loras)
                        self._candidates.setdefault(key, []).extend(matching)
                    current_range_start = num_tokens + 1
```

So for a batch size whose next captured `num_tokens` belongs to a different tier, the
candidates at that key carry the wrong `uniform_token_count`, `_is_compatible` rejects them
on the clause quoted above, and `dispatch` falls through to `CUDAGraphMode.NONE` (`:522`).
This PR does not create that behaviour, but it does route a new class of batches into it:
one-token-tail batches now arrive with a concrete tier where they previously arrived with
`None`.

**Why the existing test does not show this.** `test_dynamic_sd_full_cudagraph_covers_all_uniform_decode_shapes`
sweeps every `num_reqs` in `[1, 512]` and asserts FULL each time, so it reads as though the
ladder is already gapless. It passes because the fixture makes it gapless by construction —
`cudagraph_capture_sizes=list(range(1, max_capture_tokens + 1))`, every integer up to
`max_num_seqs * max_decode_query_len`, with the helper's own docstring saying it "uses an
exact capture-size grid so that every valid uniform decode shape has a directly matching
FULL graph candidate". With no gaps `current_range_start` advances by one per group and
never spans a tier boundary. On the default capture ladder the gaps are where the tiers
interleave, and that case has no coverage in this file.

I am not suggesting the test is wrong — its grid is deliberate, and it is testing the
candidate construction rather than the ladder. But if you want the benchmark shape you
measured to hold under a dynamic-SD schedule with several query lengths, that is the case
worth adding, and it is cheap: the same sweep with the inferred default capture sizes
rather than the exhaustive grid.

**Disclosure.** I opened #56136 for the ladder behaviour above, so I have an interest in it
being real; treat the reasoning rather than the source. It is a dispatch-coverage argument
only — I have no hardware and measured no recovered graphs, so I am claiming reachability,
not throughput. Nothing here blocks this PR and I am not asking you to act on that one; the
part that bears on yours is only that the population entering the ladder grows, so if you
benchmark with a multi-tier schedule and see the non-FULL share stop short of 0.00%, this
is the reason rather than something in your change.
