### 🐛 Describe the bug

## Description

In vLLM 0.29.0's V1 model runner, a completed request can leave its `prompt_embeds` tensor referenced by `InputBatch.req_prompt_embeds`.

After all requests have been removed and the persistent batch is empty, the dictionary still contains one tensor for every slot that previously handled a prompt-embedding request. Reusing those slots with ordinary token-ID requests does not release or overwrite the old tensors. They remain alive until another prompt-embedding request overwrites the same slot, the dictionary is cleared, or the worker exits.

The retention is bounded by persistent-batch capacity, but a worker can keep the peak prompt-embedding footprint of a previous burst even after ordinary text requests replace that workload. The reproducer retains 256 MiB across eight reused slots and releases it only when the stale dictionary is cleared. At a `max_num_seqs` of 256, the same `(4096, 4096)` BF16 shape can retain up to 8 GiB of host memory.

This can increase host-memory pressure, swapping, allocation failures, or container eviction risk. Stale entries can also cause unnecessary prompt-embedding staging work for replacement requests.

## Reproduction

Use the script [repro.py](https://github.com/user-attachments/files/32476544/repro_slot_retention.py), with vLLM 0.29.0 installed, run:

```bash
python repro.py 2>&1 | tee reproducer.log
```

The script reproduces a prompt-embedding burst followed by ordinary text traffic:

1. fills eight slots with `(4096, 4096)` BF16 prompt-embedding tensors, totaling 256 MiB;
2. completes all eight requests and forces garbage collection;
3. reuses every slot with an unrelated token-ID request;
4. verifies that every old tensor is still attached to the reused slot; and
5. clears only `req_prompt_embeds` as a control while the text requests remain active.

The script records both weak-reference liveness and process RSS. It calls `malloc_trim()` only after clearing the dictionary so that the RSS control is visible; the weak references establish tensor lifetime independently of the allocator.

```text
  active request IDs: [text-request-0, ..., text-request-7]

```

The weak-reference control shows that the stale dictionary entries are the remaining owners of the tensors. The text requests remain active when the old tensors are released, so the tensors are not needed by the replacement requests. The complete output is in [reproducer_slot_retention.log](https://github.com/user-attachments/files/32476576/reproducer_slot_retention.log).

## Expected result

Once a request is removed, its slot must no longer own the request's prompt-embedding tensor. With an empty batch, `req_prompt_embeds` should be empty. Reusing the slots with token-ID requests should not keep any tensor from the completed requests alive.

## Root cause

[`InputBatch.add_request()`](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/v1/worker/gpu_input_batch.py#L350-L386)
stores the tensor by slot index:

```python
if request.prompt_embeds is not None:
    self.req_prompt_embeds[req_index] = request.prompt_embeds
```

[`InputBatch.remove_request()`](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/v1/worker/gpu_input_batch.py#L528-L582) clears the other request-scoped state but never removes this entry. The empty-batch branch of [`condense()`](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/v1/worker/gpu_input_batch.py#L706-L727) also leaves the dictionary unchanged.

The missing cleanup can be performed as soon as the request index is known:

```python
self.req_prompt_embeds.pop(req_index, None)
```
