# [PR #58139] [Perf][ROCm] Force Triton MXFP4 for 96-row ASM scale tiles

## 正文

## Purpose

On ROCm gfx950, AITER ASM MXFP4 (`gemm_a4w4`) is selected when weight-scale tiles have `rows % 32 == 0` and `cols % 8 == 0`. Qwen3.8 TP1 GDN `in_proj_ba` uses **96×160** scales, which pass that layout check, but ASM is numerically wrong for **M ≤ 64** (Arete: error ratio ~0.83–0.92; ~22–24 µs broken ASM vs ~7.6–8.9 µs Triton).

This PR forces 96-row scales onto Triton `gemm_afp4wfp4`. Other legal tiles (e.g. 128×160) stay on ASM. TP2/TP4 BA (`N=48/24`) already fail the row-%-32 check and were Triton via #55213.

## Test Plan

- Unit: `tests/kernels/quantization/test_rocm_mxfp4.py::test_asm_fp4_scale_swizzle_supported_shape_rules`
  - `(96, 160) -> False` (Triton)
  - `(128, 160) -> True` (ASM unchanged)
- gfx950 TP1 Qwen3.8-27B MXFP4 serve: GDN `in_proj_ba` should log Triton, not ASM, at decode M≤64.

## Test Result

Dispatch unit cases added. Numerical mismatch for 96-row ASM at M=8/16/32/64 was measured on MI355X (Arete Qwen3.8 MXFP4 campaign). Full e2e accuracy vs Triton path still to be attached from the TP1 patched serve.
