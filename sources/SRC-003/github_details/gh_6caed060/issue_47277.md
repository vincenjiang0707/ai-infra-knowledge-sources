# [Issue #47277] [Performance]: Qwen3.5 native MTP can be slower than no-MTP CUDA graph baseline despite good acceptance

## 正文

## Summary

We are benchmarking a Qwen3.5 OCR checkpoint with native MTP support in vLLM. The model has a lightweight native MTP branch:

```
- `mtp_num_hidden_layers=1`
- `mtp_use_dedicated_embeddings=false`
```

In our OCR workload, MTP acceptance is not terrible. MTP1 reaches around `82%-88%` acceptance, and MTP2 can reach mean accepted length above `2.3`. However, end-to-end throughput in graph mode is still below the best no-MTP vLLM baseline.

The main issue seems to be that the vLLM spec decode execution path adds enough per-step overhead to erase the theoretical benefit from fewer decode steps. This is particularly visible with `num_speculative_tokens=2`, where rejection sampling, metadata preparation, slot mapping, and `num_computed_tokens` updates become large overheads.

We would like to understand whether this is expected for native Qwen MTP today, whether `num_speculative_tokens > 1` currently requires repeated forward/processing through the same MTP layer, and whether there are planned optimizations for the graph-mode spec decode path.

## Environment

- vLLM: `0.23.0`
- PyTorch: `2.11.0+cu130`
- GPU: NVIDIA L20X
- Tensor parallel: `1`
- CUDA graph mode: enabled, `enforce_eager=false`
- Workload: multimodal OCR / document parsing, long outputs
- Decode temperature: `0`

Main generation config:

```text
max_new_tokens=16384
max_model_len=32768
max_num_batched_tokens=32768
gpu_memory_utilization=0.8
max_num_seqs=None
```

We intentionally did not give MTP a larger `max_num_seqs` or give baseline a smaller one. Both paths use the same input subset and batching-related configuration.

## Speculative configs tested

MTP1:

```json
{"method":"mtp","num_speculative_tokens":1,"use_local_argmax_reduction":true}
```

MTP2:

```json
{"method":"mtp","num_speculative_tokens":2,"use_local_argmax_reduction":true}
```

Before our local patch, `prepare_num_computed_gpu` was one of the clearest overheads. In MTP1 n32, we observed:

| item | baseline | MTP1 before patch |
| --- | ---: | ---: |
| `prepare_num_computed_gpu` | 6.4 ms | 626.7 ms |

We locally replaced a `torch.compile(dynamic=True)` style `update_num_computed_tokens_for_batch_change` path with a small fused Triton kernel. This improved MTP1 n32 throughput from `1824.31 tok/s` to `1980.96 tok/s`, but it did not solve the full graph-mode overhead problem, especially for MTP2.

## Local experiments that were not safe enough to use

We also tried more aggressive local fast paths:

- a greedy rejection fast path for `temperature=0`
- packed/allfast variants
- faster attention metadata experiments
- GPU token cache / active request gating variants

Some of these either regressed performance or produced non-clean outputs such as `length:1` in offset tests, so we did not count them as valid benchmark results.

## Questions

1. Is it expected that Qwen native MTP in vLLM graph mode can be slower than no-MTP graph baseline even with MTP1 acceptance around `82%-88%`?
2. For `num_speculative_tokens > 1`, does vLLM currently run the same Qwen MTP layer multiple times / perform repeated per-token processing rather than producing multiple draft tokens in one low-overhead pass?
3. Are there known bottlenecks or planned optimizations for:
   - `reject_sample_kernel`
   - spec decode metadata preparation
   - slot mapping updates
   - `num_computed_tokens` correction/update
   - target/draft metadata reuse under CUDA graph
4. Is there a recommended benchmark setup for fairly comparing no-MTP graph baseline vs native MTP graph mode for long-output multimodal workloads?
5. Would the vLLM team be interested in a minimal repro using a public Qwen3.5 native-MTP checkpoint, if available, or local profiling traces from our private OCR checkpoint?

## Expected behavior

For a native MTP model with `80%+` MTP1 acceptance and graph mode enabled, we would expect MTP1 to at least be competitive with no-MTP graph baseline, or for documentation to clarify that MTP may be slower in graph mode unless the acceptance rate and sequence/batch shape meet specific thresholds.

For MTP2/MTP3, we would expect either:

- a low-overhead multi-token draft path, or
- guidance that `num_speculative_tokens > 1` may be slower for Qwen native MTP because it requires repeated MTP forward/processing.

## Actual behavior

On this workload:

- no-MTP graph baseline is still the fastest stable path.
- MTP1 has good acceptance but is slower end to end.
- MTP2 increases mean accepted length but introduces enough extra overhead that it still does not beat the best no-MTP graph baseline.
- Local profiling points to rejection sampling, metadata preparation, slot mapping, and `num_computed_tokens` updates as major overheads.

## Additional context

This benchmark is from a private OCR/document parsing workload, so some exact data/model paths are not public. We can prepare a smaller reproducer if a public Qwen native-MTP checkpoint is suitable.

The most relevant local observation is that the bottleneck is not just draft quality. Even when acceptance is usable, the spec decode path can be too expensive relative to a strong CUDA graph no-MTP baseline.

### seongyun1104 · 2026-07-13

@ZJY0516 thanks for the quick follow-up.

**"all-K=0 batch-size table"**: In vLLM 0.24 DSD (`num_speculative_tokens_per_batch_size`) we passed the schedule `[[1, 512, 0]]` — for every batch size in 1..512 the runtime picks K=0. Drafter is still loaded and initialized, but DSD chooses K=0 per step. Verified via `vllm:spec_decode_num_drafts_total` delta ≈ 0 across the 120s window. The 12–25% throughput penalty vs no-spec still shows up in this configuration, which is why we suspect the overhead isn't in the drafting itself but in the spec-decode path fabric (drafter sync forward, admission-time drafter prefill, spec bookkeeping) that runs even when K=0 is picked every step.

**"MTP may only help for small batch size"**: agreed in the short-context regime — our crossover matches yours (single-turn ~150tok completion: c=30 gives K=3/K=0 = 1.79×, c=128 collapses to 1.00×). The picture shifts once context grows though. At c=256 fixed, ctx ≈ 460/970/1990 gives K=3/K=0 = 1.17× / 1.25× / **1.38×** monotone, with K=3 TPOT flat at ~78ms while K=0 TPOT climbs 81 → 109 → 120ms — decode stays memory-bound as ctx grows and MTP amortizes the KV-read across drafted tokens. So the "MTP helps only at small batch" rule may be a short-context artifact rather than a general property.

### JumpingRain · 2026-07-23

Thanks @andakai and @ZJY0516 for the investigation. I have now run two additional groups of tests: (1) a public `Qwen/Qwen3.5-0.8B` check on OmniDocBench images, and (2) a larger/fairer sweep on our private OCR Qwen3.5 native-MTP checkpoint.

## Short conclusion

I agree that this is **not a generic issue where Qwen3.5 native MTP is always slower**. The public 0.8B model behaves well and does not reproduce the slowdown. However, our private OCR checkpoint still reproduces it consistently on a 300-page long-output workload, including a clean comparison with nearly identical output-token counts and finish reasons.

The current evidence points to a workload/checkpoint-dependent crossover involving:

```
- MTP draft quality, especially second-token acceptance;
- active batch size and the long-tail decode phase;
- repeated Qwen MTP-layer forwards for `num_speculative_tokens > 1`;
- fixed spec-decode preparation/rejection/metadata overhead.
```

This also seems consistent with the newer batch/context-length discussion in #48627: acceptance alone does not determine whether speculation pays.

## 3. Long-tail acceptance collapse

The aggregate acceptance hides a more severe tail effect. In the 300-page MTP2 run, acceptance was around 65%-67% during healthier mid-run windows, but when only the longest OCR requests remained it dropped to approximately:

- average acceptance `30.9%`, position 2 `15.5%` near 98% progress;
- average acceptance `14.1%`, position 2 `3.8%` in a later tail window.

These long repetitive/table-heavy outputs dominate wall time. During this phase MTP2 still pays drafter-forward, rejection-sampling, input-preparation, slot-mapping, and token-state update costs while accepting very few second draft tokens.

## 4. Concurrency and backend controls

On a smaller fixed n32 subset, MTP2 acceptance stayed almost constant at ~75.9%, while the speed ratio changed substantially with `max_num_seqs`:

| max_num_seqs | MTP2/no-MTP | MTP2 acceptance |
|---:|---:|---:|
| 4 | 0.608x | 75.89% |
| 8 | 1.201x | 75.92% |
| 16 | 1.188x | 75.95% |
| 32 | 1.113x | 75.87% |

This supports the point that acceptance by itself is insufficient: runtime batch shape and per-step overhead can move the result from a large regression to a speedup without changing draft quality.

I also tested the earlier attention-backend suggestion. On this vLLM 0.23/H200 setup, forcing FlashInfer made MTP2 substantially slower while acceptance remained unchanged, because the log reported that spec decode was downgraded from `FULL_AND_PIECEWISE` CUDA graphs to `PIECEWISE`. Forcing Triton was better than FlashInfer but still slower than the default FA3 path. Thus backend selection matters, but FlashInfer was not a fix for this particular stack.

## Updated interpretation / next debugging step

The public-model results narrow the issue considerably:

```
1. Native Qwen MTP can provide a real speedup when per-position acceptance is high.
2. Our reproducible regression is associated with an OCR-adapted MTP checkpoint whose position-2 acceptance collapses on long outputs.
3. Even at ~76% aggregate acceptance, changing only concurrency can flip the speed result, confirming that the spec-decode execution cost matters independently of model quality.
4. The clean 300-page comparison rules out unfair `max_num_seqs` settings and output-length mismatch as the explanation for the private-checkpoint regression.
```

### vedcsolution · 2026-09-22

Same symptom on a very different stack, with a decomposition that may help narrow the cause.

**Setup.** `XiaomiMiMo/MiMo-V2.6-Flash-RL` (MoE, 309B total / 15B active, 256 experts, top-8, 48 layers, MXFP4 weights, fp8 KV) on 2× NVIDIA DGX Spark (GB10), TP=2 over RoCE, vLLM `0.29.1rc1.dev467`. The speculator is DFlash (block-diffusion drafter, 5 dense layers, 2.94 GB bf16, `block_size=8`), not MTP. Draft CUDA graphs are captured FULL (`Capturing dflash CUDA graphs (FULL)`, no eager-fallback warning). Single stream, greedy, median of 3 runs, identical engine otherwise.

| arm | decode | accept-len | step |
|---|---|---|---|
| no spec | **26.51 tok/s** | — | 37.7 ms |
| DFlash `k=1` | 17.73 tok/s | 1.75 | 98.7 ms |
| DFlash `k=7` | 12.20 tok/s | 3.21 | 263 ms |

**Decomposition.** Fitting those three points:

```
step(k) ≈ 37.7 + 35 + 26·k   [ms]
```

That is **~35 ms of fixed cost for using the drafter at all**, paid in full even at `k=1`, plus ~26 ms per draft token. The fixed term is what matches your observation that the overhead is most visible at small `num_speculative_tokens`: there is nothing to amortize it against.

**The part I think is worth stating as a criterion.** At `k=1`, accept-len 1.75 is 87.5% of the theoretical maximum of 2.0. Even a *perfect* drafter (accept-len 2.0) would yield 2.0 / 98.7 ms = 20.3 tok/s — still below the 26.51 tok/s no-spec baseline. So the question here is not "is acceptance good enough": **no achievable acceptance at `k=1` can win**, because the per-step toll exceeds the maximum possible benefit.

A cheap diagnostic for anyone hitting this: compute `accept_len_needed = baseline_tok_s × step_with_spec`. If that exceeds `k+1`, the configuration cannot win regardless of drafter quality. Applied to your MTP1 row (1.828 of a maximum 2.0, at 0.86× baseline), the break-even looks similarly out of reach.

**Where the variable term comes from here** — likely MoE-specific, so probably not your case: with 256 experts and top-8, one decode token touches ~8 experts per layer, while a verify batch of `k+1 = 8` tokens touches ~57 distinct experts per layer (`256·(1−(1−1/256)^64)`). Speculation destroys the sparsity of the MoE. Switching `--moe-backend` (marlin → b12x) moved decode by only ~1% at `k=0`, which suggests the no-spec step is already at the memory-bandwidth roofline (~9.3 GB of active weights / 273 GB/s ≈ 34 ms, vs 37.7 ms measured) — so the extra cost is real weight traffic, not kernel-launch overhead.

**Caveat on the acceptance figures**: per #56101, `mean_acceptance_length` can overcount when EOS falls inside the accepted draft, so 1.75 may be an upper bound. This does not change the conclusion — the tok/s figures are measured end-to-end, and a lower true acceptance only makes speculation look worse.

Happy to run further arms on this hardware if a specific hypothesis would help.
