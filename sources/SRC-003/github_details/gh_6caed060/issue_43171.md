## 正文

### 🚀 The feature, motivation and pitch

## Problem

Currently vLLM OpenAI-compatible chat completion responses expose reasoning separately:

```json
{
  "message": {
    "reasoning": "...",
    "content": "..."
  }
}
```
Some OpenAI-compatible clients, SDKs, and agent frameworks expect all generated text to appear in content only and do not parse the reasoning field.

As a result, users currently need to add custom post-processing logic on the client side to merge reasoning back into content.

## Proposed feature

Add a new optional request parameter:

separate_reasoning: bool = True

Behavior:

separate_reasoning=True (default)
Keep existing behavior
Return reasoning and content separately
```json
{
  "reasoning": "...",
  "content": "..."
}
```
separate_reasoning=False
Merge reasoning into content
Suppress the reasoning field
```json
{
  "content": "<reasoning><content>"
}
```
## Motivation

This improves compatibility with:

Existing OpenAI-compatible APIs
SDKs and client libraries that only consume content
Agent frameworks that do not understand a separate reasoning field
Existing applications migrating to vLLM without additional response transformations

## Why this approach
No breaking changes
Default behavior remains unchanged
Requires minimal changes
Applies consistently to both streaming and non-streaming responses

### F0rtiter · 2026-05-29

Thanks for the clarification.

I understand that disabling --reasoning-parser already causes reasoning tokens to be returned inside content.

However, the motivation of this feature request is slightly different: allowing this behavior to be controlled per request rather than per server instance.

For example, when running a shared vLLM deployment with --reasoning-parser enabled:


Some clients/frameworks can consume the separate reasoning field and prefer the current behavior.



Other OpenAI-compatible clients only read content and cannot be modified easily.


With a request-level parameter such as separate_reasoning, the same deployment could support both behaviors simultaneously:


separate_reasoning=true → return reasoning and content separately.



separate_reasoning=false → merge reasoning into content.


Without this, users need either:


Multiple vLLM deployments with different --reasoning-parser configurations, or



Additional proxy/post-processing logic to transform responses.


So the main goal is runtime compatibility control at the API request level, not replacing the existing --reasoning-parser behavior.

### F0rtiter · 2026-06-26

Thanks for the feedback.

I agree that reasoning and content should remain separated by default, and I don't think that behavior should change. The proposed `separate_reasoning` parameter is intended as an **optional compatibility mode**, not a replacement for the current design.

The main motivation comes from migration of existing systems.

Before vLLM introduced the built-in `--reasoning-parser`, many existing projects (including ours) implemented reasoning parsing entirely on the client side. We are gradually migrating to vLLM's native reasoning parser, but because of historical integrations, not all clients can be migrated at once.

During this transition, we need to support both types of clients against the same vLLM deployment:

* New clients that understand the separate `reasoning` field.
* Legacy clients that only consume `content` and cannot be easily modified.

An optional request-level parameter would allow both behaviors to coexist during migration without requiring multiple vLLM deployments or an additional proxy layer.

Since the default behavior would remain unchanged, existing users would not be affected. This would simply provide a temporary compatibility mechanism for deployments that are incrementally adopting the built-in reasoning parser.
