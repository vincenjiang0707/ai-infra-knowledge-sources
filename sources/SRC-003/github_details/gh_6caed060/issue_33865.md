# [Issue #33865] [Bug]: OpenAI-compatible Embeddings API intermittently crashes with multimodal cache assertion (`Expected a cached item for mm_hash`) on Qwen3-VL-Embedding-8B

## 正文

### 🐛 Describe the bug

Using vLLM `serve` with the OpenAI-compatible **Embeddings API** to run **Qwen3-VL-Embedding-8B**, the server intermittently crashes while pre-processing embedding requests. The crash is an assertion inside the multimodal feature cache:

```
AssertionError: Expected a cached item for mm_hash='...'
```

After that, the API server hits a second assertion:

```
AssertionError: assert req_state.detokenizer is not None
```

This suggests the request fails during `preprocess_add_request()` when the engine tries to retrieve multimodal features from `mm_receiver_cache`, but the cache entry for the computed `mm_hash` is missing; then the output handler processes an incomplete request state.

## Environment / deployment

- API: OpenAI-compatible **Embeddings** endpoint
- Deployment: cloud vendor managed model inference service (default settings; limited ability to tune internal worker settings)
- Model: `Qwen3-VL-Embedding-8B`
- Launch command:

```bash
vllm serve /mnt/data \
  --runner pooling \
  --dtype bfloat16 \
  --tensor-parallel-size 2 \
  --max-model-len 65536 \
  --trust-remote-code
```

## Steps to reproduce

This occurs intermittently under real traffic. We don’t have a 100% minimal repro yet, but it happens when sending embedding requests with multimodal inputs to the OpenAI-compatible embeddings endpoint.

## Expected behavior

- The embeddings request should either succeed, or fail gracefully with a clear error response.
- vLLM should not `assert` and crash due to a missing multimodal cache item; if the cache misses, it should recompute the multimodal features or safely reject the request and clean up request state so the output handler does not assert.

## Additional notes / hypotheses

```
- Since we are using a cloud vendor inference service, the internal runtime might use multiple processes/workers or request routing patterns that could make multimodal caches non-sticky across workers.
- The error strongly looks like a multimodal cache inconsistency / race / eviction, or cross-process cache visibility issue: the engine expects a cached `mm_hash` item but cannot find it.
```

### lzgkeegan · 2026-09-23

Reproduced on **v0.30.0** — the mm-cache assertion is now handled gracefully, but the server still crashes one layer down. Sharing our findings since we have a deterministic trigger.

**What changed in v0.30.0**: the `AssertionError: Expected a cached item for mm_hash` is gone. The engine now logs:

```
WARNING [core.py:1868] Multi-modal cache miss for request embd-... (mm_hashes=['a9a6596b...']): P0/P1 cache drift; returning a retryable response so the items are resent with data.
```

**What still crashes**: when the aborted request is a **pooling (embeddings)** request, `output_processor` kills the server:

```
AssertionError: assert req_state.detokenizer is not None
  File ".../vllm/v1/engine/output_processor.py", line 696, in process_outputs
```

This looks like a sibling of #25568 — that fix covered the client-abort path, but not the newer "retryable mm-cache-miss" abort path.

**Deterministic trigger** (matches @Afanmin's repro above):

1. Client sends malformed embedding requests **containing an image** → `400 Bad Request` (in our case 31 validation errors on `body.input`), but P0 has already preprocessed and cached the image features.
2. Client resends a valid request with **the same image** → P0/P1 cache drift → retryable abort → `detokenizer` assert → full server shutdown.

It reproduces even on a freshly started server, so the drift is created by the 400-then-retry pattern itself, not residual state.

**Environment**: `vllm-openai:v0.30.0`, `Qwen3-VL-Embedding-8B`, `--runner pooling --tensor-parallel-size 2 --max-model-len 32768 --dtype bfloat16 --trust-remote-code`, Kubernetes.

**Impact**: one misbehaving client repeatedly crashes a shared embeddings service, taking down all tenants including text-only traffic.

**Workaround**: `--disable-mm-preprocessor-cache` — with the cache disabled the drift never happens; bad requests fail individually and the service stays up.
