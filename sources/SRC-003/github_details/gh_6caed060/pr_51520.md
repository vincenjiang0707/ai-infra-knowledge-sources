# [PR #51520] [RL] Add sharding-aware NCCL M2N weight transfer

## 正文

## Purpose

Adds a complete, sharding-aware `nccl_m2n` weight-transfer backend built on [NCCL M2N](https://github.com/NVIDIA/nccl-extensions), following [RFC #46439](https://github.com/vllm-project/vllm/issues/46439).

The broadcast NCCL backend assumes both sides hold the same layout, so a trainer using FSDP or another sharded layout must materialize full parameters before sending them. `nccl_m2n` instead performs one `reshard` between two disjoint meshes in a shared communicator: trainer ranks `[0, T)` and inference-worker ranks `[T, T + N)`.

This PR now includes the full path:

```
- inference-side engine and wire protocol;
- trainer-side `M2NWeightSource`, `DTensorModuleSource`, and `M2NTrainerWeightTransferEngine`;
- per-parameter destination planning so each inference worker receives only its own shard when layouts permit it;
- strict layout, placement, dtype, and parameter-name validation before transfer or model mutation;
- a runnable FSDP-to-TP example, documentation, unit tests, and multi-GPU E2E coverage.
```

The backend is selected with `--weight-transfer-config '{"backend": "nccl_m2n"}'`. Its optional runtime is imported lazily, so default vLLM behavior is unchanged.

## Not a duplicate

Checked per `AGENTS.md`:

```bash
gh issue view 46439 --repo vllm-project/vllm --comments
gh pr list --repo vllm-project/vllm --state open --search "46439 in:body"
gh pr list --repo vllm-project/vllm --state open --search "NCCL M2N weight transfer"
```

No other open PR implements the RFC's NCCL M2N backend. Adjacent WPI and RDT work uses different transports and does not provide this trainer-to-inference resharding path.

## Test plan

```bash
.venv/bin/python -m pytest tests/distributed/test_weight_transfer_m2n.py -v
uvx ruff check <touched Python files>
```

The suite covers layout and wire validation, registry dispatch, trainer planning, atomic name preflight, direct and fallback destinations, replicated E2E transfer, and a real 1-trainer + 2-worker TP=2 sharded transfer.

## Test results

- Ruff check and format check: passed.
- `git diff --check`: passed.
- **CPU or single-GPU environment:** **31 passed, 2 skipped**. The two skipped tests require the `nccl.m2n` runtime and multiple GPUs.
- **Multi-GPU environment** (H100, CUDA 12.9, NCCL 2.30.7): both M2N E2Es passed — the replicated 1-trainer + 1-worker transfer and the sharded 1-trainer + 2-worker TP=2 transfer. The 4-GPU FSDP-to-TP example also passed with `gpu_memory_utilization=0.8`.

No model-quality evaluation is required: this changes transport and placement, not model computation or generated output. The E2E tests verify exact transferred tensor values.

## Known limitations

Documented in `docs/training/weight_transfer/m2n.md`:

- requires `nccl-extensions` and NCCL >= 2.30.5;
- `VLLM_NCCL_SO_PATH` must identify the same NCCL used by `libnccl_m2n.so`;
- parameter tensors may have 1 to 3 dimensions (independent of TP world size); 4-D parameters, FP4, and `Partial` placements are unsupported;
- trainer meshes must be contiguous from rank zero and one- or two-dimensional;
- each destination shard supports at most 16 source shards (`MAX_SOURCES`, an NCCL M2N compile-time limit).

### aoshen02 · 2026-09-24

Two weight-loading correctness concerns from an AI-assisted review of `397ade252b312a58daf24a7ecc091631867b420e`. Both were reproduced with actual model-loader code and the new M2N Python logic; transport/CUDA stream operations were mocked on CPU, so these are not GPU/NCCL E2E results.

### 1. [P1] Preserve coupled tensors in the same `load_weights` invocation

Location: [`m2n_engine.py:385–389`](https://github.com/vllm-project/vllm/blob/397ade252b312a58daf24a7ecc091631867b420e/vllm/distributed/weight_transfer/m2n_engine.py#L385-L389).

The fallback calls `self.model.load_weights([(name, buffer)])` separately for every tensor. Native model loaders are not necessarily stateless per-tensor callbacks.

For example, `MiMoV2Model.load_weights` creates a local `pending_fp8_qkv_proj` dictionary and waits for both `qkv_proj.weight` and `qkv_proj.weight_scale_inv` before loading them together. With two singleton calls, the first call discards its pending weight when it returns; the second starts with a fresh dictionary containing only the scale. Neither parameter is updated, despite the receive path returning successfully.

A minimal CPU parameter tree using the actual MiMo loader and actual M2N `receive_weights` produced:

```text
One load_weights invocation containing weight + scale:
  loaded names = [attn.qkv_proj.weight, attn.qkv_proj.weight_scale_inv]
  weight sum = 65536.0

M2N receive_weights, with transport replaced by tensor copies:
  weight sum = 0.0
  scale sum = 0.0
```

This concerns MiMo's Pro-format fused FP8 QKV input, not the ordinary BF16 Qwen example. Both tensors have supported wire dtypes and rank-2 shapes. The same invocation-boundary issue also reproduces without quantized tensors: JinaRobertaModel's native LoRA merge needs `.original`, `.0.lora_A`, and `.0.lora_B` together. All probe tensors pass `check_transferable`; the grouped merge succeeds, whereas actual M2N `receive_weights` raises `KeyError(...lora_B)` when it delivers only `.original` first.

Please preserve the native loader's iterable scope, or group the tensors it must process together. This singleton pattern also exists in the older unpacked NCCL path, but that does not make it equivalent to the native loader contract for these inputs.

### 2. [P2] Parameter-loader identity does not establish that model-level loading is a plain copy

Location: [`m2n_layout.py:171–185`](https://github.com/vllm-project/vllm/blob/397ade252b312a58daf24a7ecc091631867b420e/vllm/distributed/weight_transfer/m2n_layout.py#L171-L185).

The direct-path check recognizes the parameter's final loader, but the enclosing model's `load_weights` can transform the checkpoint tensor before invoking that loader. GPT2Model, for example, transposes Conv1D weights before passing them to the ordinary RowParallelLinear loader. A square attention `c_proj.weight` passes the name/shape/loader checks even though this transpose is still required.

The concrete remaining case is a custom, static weight-only source plan that includes `h.0.attn.c_proj.weight` but omits its unchanged bias. **A full GPT-2 parameter plan containing that bias is protected by the latest sibling-demotion fix; I am not claiming that full-plan case remains broken.**

Using a minimal GPT2Model parameter tree, its actual `load_weights`, the actual destination planner, and M2N `receive_weights` with mocked byte transport:

```text
source = arange(16).reshape(4, 4)
native GPT2Model.load_weights result = source.T
M2N planner selects direct = True
M2N receive_weights result = source
matches native loader = False
```

The shape stays 4×4, so shape validation cannot detect the missing transpose. Please require a model-level guarantee/opt-in that bypassing `load_weights` preserves the checkpoint interpretation, or fall back for models with such transformations. Recognizing a parameter-level copy/sharding loader alone is insufficient.

### aoshen02 · 2026-09-24

Two weight-loading correctness concerns from an AI-assisted review of `397ade252b312a58daf24a7ecc091631867b420e`. Both were reproduced with actual model-loader code and the new M2N Python logic; transport/CUDA stream operations were mocked on CPU, so these are not GPU/NCCL E2E results.

### 1. [P1] Preserve coupled tensors in the same `load_weights` invocation

Location: [`m2n_engine.py:385–389`](https://github.com/vllm-project/vllm/blob/397ade252b312a58daf24a7ecc091631867b420e/vllm/distributed/weight_transfer/m2n_engine.py#L385-L389).

The fallback calls `self.model.load_weights([(name, buffer)])` separately for every tensor. Native model loaders are not necessarily stateless per-tensor callbacks.

For example, `MiMoV2Model.load_weights` creates a local `pending_fp8_qkv_proj` dictionary and waits for both `qkv_proj.weight` and `qkv_proj.weight_scale_inv` before loading them together. With two singleton calls, the first call discards its pending weight when it returns; the second starts with a fresh dictionary containing only the scale. Neither parameter is updated, despite the receive path returning successfully.

A minimal CPU parameter tree using the actual MiMo loader and actual M2N `receive_weights` produced:

```text
One load_weights invocation containing weight + scale:
  loaded names = [attn.qkv_proj.weight, attn.qkv_proj.weight_scale_inv]
  weight sum = 65536.0

M2N receive_weights, with transport replaced by tensor copies:
  weight sum = 0.0
  scale sum = 0.0
```

This concerns MiMo's Pro-format fused FP8 QKV input, not the ordinary BF16 Qwen example. Both tensors have supported wire dtypes and rank-2 shapes. The same invocation-boundary issue also reproduces without quantized tensors: JinaRobertaModel's native LoRA merge needs `.original`, `.0.lora_A`, and `.0.lora_B` together. All probe tensors pass `check_transferable`; the grouped merge succeeds, whereas actual M2N `receive_weights` raises `KeyError(...lora_B)` when it delivers only `.original` first.

Please preserve the native loader's iterable scope, or group the tensors it must process together. This singleton pattern also exists in the older unpacked NCCL path, but that does not make it equivalent to the native loader contract for these inputs.

### 2. [P2] Parameter-loader identity does not establish that model-level loading is a plain copy

Location: [`m2n_layout.py:171–185`](https://github.com/vllm-project/vllm/blob/397ade252b312a58daf24a7ecc091631867b420e/vllm/distributed/weight_transfer/m2n_layout.py#L171-L185).

The direct-path check recognizes the parameter's final loader, but the enclosing model's `load_weights` can transform the checkpoint tensor before invoking that loader. GPT2Model, for example, transposes Conv1D weights before passing them to the ordinary RowParallelLinear loader. A square attention `c_proj.weight` passes the name/shape/loader checks even though this transpose is still required.

The concrete remaining case is a custom, static weight-only source plan that includes `h.0.attn.c_proj.weight` but omits its unchanged bias. **A full GPT-2 parameter plan containing that bias is protected by the latest sibling-demotion fix; I am not claiming that full-plan case remains broken.**

Using a minimal GPT2Model parameter tree, its actual `load_weights`, the actual destination planner, and M2N `receive_weights` with mocked byte transport:

```text
source = arange(16).reshape(4, 4)
native GPT2Model.load_weights result = source.T
M2N planner selects direct = True
M2N receive_weights result = source
matches native loader = False
```

The shape stays 4×4, so shape validation cannot detect the missing transpose. Please require a model-level guarantee/opt-in that bypassing `load_weights` preserves the checkpoint interpretation, or fall back for models with such transformations. Recognizing a parameter-level copy/sharding loader alone is insufficient.
