# [Issue #46502] [Bug]: persistent KV Cache memory not released after benchmark completion

## 正文

### Your current environment

vllm 0.22.0 +  mooncakestore connector

Observed Behavior:
After the benchmark completes, ~40% of the HBM (KV cache) remains allocated and is not immediately released. This persists for at least 20 minutes with no active requests. However, when I start a new benchmark, the memory begins to be released (evicted) to accommodate incoming requests.

<img width="467" height="185" alt="Image" src="https://github.com/user-attachments/assets/4dd08dab-5846-4ddb-a21a-9a8077455f8d" />

Expected Behavior:
I expected the KV cache to be released promptly after the benchmark finishes, or at least to see a more aggressive eviction policy, especially when there are no pending requests.

Questions:

Is this behavior expected for MooncakeStoreConnector, or does it indicate a configuration issue?

If this is by design, could you explain the rationale behind keeping the cache warm for such a long duration even when no requests are being served?

Are there any configuration parameters (e.g., max_num_seqs, gpu_memory_utilization, or connector-specific flags) that can be tuned to achieve more proactive memory release after workload completion?

I would appreciate any guidance or clarification on whether this is a known behavior or a potential bug. The fact that memory only starts releasing during the next benchmark suggests a lazy eviction policy, but I want to confirm if this is the intended design.

Thank you for your time!

### ivanium · 2026-06-24

Thanks for the detailed writeup! This is expected behavior rather than a bug.

With the Mooncake store connector, KV blocks that are still being offloaded stay pinned until the worker sees their offload-completion signal, and that signal only gets polled while the engine is actively stepping the model. Once all your requests finish and the engine goes idle, those completions don't get polled, so the blocks just sit there until a new request wakes the loop back up. That's why the memory starts clearing the moment a new benchmark begins.

So the retained HBM isn't leaked. It's completed offload work waiting for the next step to reap it. Tuning `max_num_seqs` or `gpu_memory_utilization` won't help, since it's about the polling lifecycle, not allocation sizing.

We're planning scheduler-side changes so the engine keeps polling for outstanding offloads even when idle, which should make this window go away. For now it's safe to treat that memory as transient.

Thanks again for flagging it.
