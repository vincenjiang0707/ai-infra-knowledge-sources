## Purpose

On SM100, the DSv4.1 O-projection runs four kernels per layer: Triton inverse RoPE with per-32 FP8 quant, DeepGEMM `fp8_einsum` for the grouped `wo_a`, a FlashInfer MXFP8 quantize, and the FlashInfer CuTe-DSL `wo_b` GEMM. At decode batch sizes the first three are latency-bound and together take 11-12 µs on GB200 (DSv4.1-Flash, TP=4).

This PR adds `FusedWoAKernel`, a CuTe-DSL kernel that replaces those three and hands `wo_b` a pre-quantized `QuantizedActivation`:

```
- 128 CTAs in clusters of 8. Each cluster owns 128 `wo_a` output rows, and each CTA owns one head (512 of K = 4096) and TMA-prefetches its 64 KiB weight slice before `griddepcontrol.wait`, overlapping the previous kernel under PDL.
- Inverse RoPE and per-32 UE8M0 quantization of the attention output go straight into the swizzled SMEM operand; `tcgen05` block-scaled MMA accumulates in TMEM.
- Split-K partials are reduced over DSMEM, rounded to BF16 like the unfused path, and quantized to MXFP8 in FlashInfer's F8_128x4 scale layout, including the zero padding FlashInfer's quantizer writes.
```

`dsv41_o_proj(layer, attn_out, positions)`, which the FlashMLA and FlashInfer backends now call directly, takes the fused path for 1-32 tokens (the kernel's limit) on SM100 with 16 local heads in 2 groups (DSv4.1-Flash at TP=4), a per-32 FP8 `wo_a` with TMA-aligned scales, and a FlashInfer CuTe-DSL MXFP8 `wo_b`. Everything else stays on `deep_gemm_fp8_o_proj`.

The kernel follows the `VllmCuTeDSLJitKernel` warmup contract. The FlashMLA and FlashInfer SM100 backends register it at construction, and warmup compiles all 32 token counts (13.5 s on GB200): target graphs, DSpark draft graphs and eager batches land on different counts, so covering the whole range keeps runtime compile-free. `_wo_b_proj` keeps pre-quantized activations off GEMM-RS, which only runs from 128 tokens.

Duplicate check: searched open PRs for `wo_a`, `fused wo_a`, `DSv4.1 o_proj`, `inverse RoPE MXFP8`, `fused_inv_rope` and `o_proj cutedsl`. #57977 (draft) also targets the `wo_a` to `wo_b` handoff, but keeps `fp8_einsum`, has it emit MXFP8, and moves `wo_b` to DeepGEMM; this PR instead collapses the whole pre-`wo_b` chain into one kernel for small batches. Both touch the same call sites; if #57977 lands first, the fused kernel could emit DeepGEMM's packed scale layout for that `wo_b` instead. #58621 changes DSv4, not DSv4.1.

The new test checks the kernel against the unfused Triton + DeepGEMM + FlashInfer reference at T in {1, 3, 6, 8, 12, 16, 18, 32} (every guard and tile size), with padded and unpadded attention output and all-zero input, under CUDA graph replay, including the scale padding.

Both paths run through their production entry points with the libraries' default PDL settings, which enable PDL for every kernel in both chains. Timing is the CUPTI span from first kernel start to last kernel end, with CUDA graphs and cold L2, median of 7 rotated rounds x 500 iterations.

## Test Result

`tests/kernels/test_fused_inv_rope_fp8_quant.py`: 106 passed. The fused FP8 data and scales are bit-identical to the unfused path in most cases; otherwise split-K accumulation order flips rare values (relative L2 up to 6.7e-4 after `wo_b`).
