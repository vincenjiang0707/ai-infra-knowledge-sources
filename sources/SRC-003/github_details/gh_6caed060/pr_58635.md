## Purpose

#53152 lets the monolithic TRTLLM-Gen experts stop after GEMM2 (`do_finalize=False`) and hand an `UnfinalizedMoEOutput` to a consumer that fuses the top-k reduction into its own kernel. On `main`, a layer asks for this by setting `FusedMoEConfig.defer_moe_finalize`, optionally capped by `defer_moe_finalize_max_num_tokens`. This PR brings the same mechanism to the modular path, which models with their own router use (DeepSeek-V4.1's MXFP4 MoE, for one).

- **Experts.** `TrtLlmMxfp4ExpertsModular`, `TrtLlmNvFp4ExpertsModular` and `TrtLlmFp8ExpertsModular` (block FP8 and MXFP8) return the unfinalized output when `moe_config.should_defer_moe_finalize(M)` holds. `TrtLlmBf16ExpertsModular` is left out: it only runs with all2all kernels, which never defer.
- **Requested through a method.** Layers call `moe_config.defer_moe_finalize(max_num_tokens=-1)` instead of assigning the flag and the cap; the flag becomes private. Kimi-K3's runner moves to it, with the same behavior.
- **The request is a hint; `should_defer_moe_finalize(M)` is the answer.** Each launch permutes into its own buffer, so a call the MXFP4 or NVFP4 experts would split across launches can't be deferred. When built, those experts lower `defer_moe_finalize_max_num_tokens` to their single-launch size. A call above it finalizes as before, and `should_defer_moe_finalize(M)` returns `False` for it. The model asks before calling and takes the matching path, so it never gets an output form it didn't expect. For DeepSeek-V4.1-Flash's MXFP4 experts (384 experts, top-k 6), that single-launch size is 86,868 tokens.
- **Modular kernel.** `FusedMoEKernelModularImpl` passes the unfinalized output through and skips `finalize`, but only when `prepare_finalize.supports_deferred_moe_finalize()` holds. That method moves up from the monolithic prepare/finalize base to `FusedMoEPrepareAndFinalize`. `MoEPrepareAndFinalizeNoDPEPModular` opts in, since its `finalize` is only the top-k weight-and-reduce.
- **Standalone finalize.** `finalize_moe_output()` runs the top-k reduction for the calls a fused consumer can't take. It uses vLLM's `moe_unpermute`, the TRT-LLM finalize as a standalone kernel, and gives the experts' own finalized output bit for bit.
- **Types.** `FusedMoEKernel.apply` now returns `torch.Tensor | UnfinalizedMoEOutput`, like `apply_monolithic`. So do `FusedMoEMethodBase.apply`, `RoutedExperts.forward_modular`, and the `apply` of each quant method whose oracle can pick one of these experts.

No layer requests deferral for modular experts yet, and Kimi-K3 behaves as before, so this changes no behavior on its own. The first consumer is #58586 (DSV4.1: MoE finalize fused into the TP all-reduce + mHC boundary), which will be restacked on this PR.

**Duplicate check.** #52601 (MiniMax-M3 MoE tail all-reduce fusion; last updated 2026-09-02) carries the same modular-kernel pass-through, NoDPEP opt-in and NVFP4 modular deferral, next to its model-specific tail. This PR splits out the shared part and adds the MXFP4 and FP8 experts, the standalone finalize and the `FusedMoEKernel.apply` return type, with no consumer, so #52601 and #58586 can both rebase onto it. No other open PR touches modular-path deferral.

## Test Plan

On GB300 (SM103), FlashInfer 0.7.0 (`main`'s pin), torch 2.13.0+cu130:

- New tests share `check_deferred_moe_finalize` in `tests/kernels/moe/utils.py`. Each builds the kernel for one rank of a TP group, as production does, and runs it. It then calls `defer_moe_finalize()` with no token cap and runs it again, checking three things:
  - `finalize_moe_output` on the deferred output equals the first run's output bit for bit;
  - modular experts hand back the router's FP32 weights unchanged;
  - for MXFP4 and NVFP4, a forced chunked run finalizes, bit-identical to the non-deferred run, and `should_defer_moe_finalize` reports it.
  - `tests/kernels/moe/test_ocp_mx_moe.py::test_trtllm_mxfp4_deferred_finalize` (modular, plus one monolithic case for the standalone finalize)
  - `tests/kernels/moe/test_trtllm_nvfp4_moe.py::test_trtllm_fp4_moe_deferred_finalize`
  - `tests/kernels/moe/test_flashinfer.py::test_trtllm_fp8_block_moe_deferred_finalize`
- Regression: `tests/kernels/moe/test_trtllm_nvfp4_moe.py`, `test_flashinfer.py`, `test_trtllm_bf16_moe.py`, `test_modular_oai_triton_moe.py` and `test_ocp_mx_moe.py`, minus the two kernel sweeps that call FlashInfer directly. Also `tests/model_executor/test_flashinfer_autotune_warmup.py` and `tests/models/kimi_k3/test_latent_moe_tail.py::test_deferred_finalize_enabled_before_moe_kernel_setup`.
- `pre-commit run` on the changed files (ruff, typos, SPDX, forbidden imports, test tethering, mypy 3.10), and `pre-commit run mypy-3.12 --hook-stage manual`.

## Test Result

- New tests: 9/9 passed (MXFP4 modular ×3 and monolithic ×1, NVFP4 ×3, FP8 ×2). `finalize_moe_output` is bit-identical to FlashInfer's finalize in every case, and forced chunked runs finalize as `should_defer_moe_finalize` reports.
- Regression: all passed except failures that also occur on `main` (36f94d5fe8) on the same stack:
