# [Issue #58523] [Bug]: explicit off-grid max_cudagraph_capture_size is silently truncated, largest decode batches run eager

source: https://github.com/vllm-project/vllm/issues/58523
state: closed | updated: 2026-09-24T12:57:20Z
labels: 

## 正文

### Your current environment

The configuration-level reproducer below does not require a GPU.

### Describe the bug

When `CompilationConfig.max_cudagraph_capture_size` is set explicitly and
`cudagraph_capture_sizes` is left unset, `_set_cudagraph_sizes()` builds the
stepped 8/16 grid and then truncates the scalar maximum down to the last grid
entry. Decode batches between that entry and the configured maximum have no
captured graph and fall back to eager execution.

This is the non-speculative counterpart of #54933. That issue, and #55004 which
fixes it, concern `uniform_decode_sizes`, which are only computed when
`decode_query_len > 1`. With plain decode the list still ends on the grid, so
the truncation remains.

| `max_cudagraph_capture_size` | resolved to | honored | capture sizes |
|--:|--:|:--|---|
| 12 | 8 | no | `[1, 2, 4, 8]` |
| 20 | 16 | no | `[1, 2, 4, 8, 16]` |
| 42 | 40 | no | `[1, 2, 4, ..., 32, 40]` |
| 50 | 48 | no | `[1, 2, 4, ..., 40, 48]` |
| 100 | 96 | no | `[1, 2, 4, ..., 88, 96]` |
| 200 | 200 | yes | `[1, 2, 4, ..., 192, 200]` |

The only signal is a `Truncating max_cudagraph_capture_size to 96` warning,
which does not say that the largest decode batches will run eager.

### Reproducer

```python
from vllm.config import CompilationConfig, SchedulerConfig, VllmConfig
from vllm.config.compilation import CUDAGraphMode


def resolve(explicit_max):
    cc = CompilationConfig()
    cc.cudagraph_mode = CUDAGraphMode.FULL_DECODE_ONLY
    cc.max_cudagraph_capture_size = explicit_max
    cc.cudagraph_capture_sizes = None
    cc.pass_config.enable_sp = False

    config = type("C", (), {})()
    config.compilation_config = cc
    config.scheduler_config = SchedulerConfig(
        max_num_seqs=256, max_num_batched_tokens=32768,
        max_model_len=2048, is_encoder_decoder=False,
    )
    config.model_config = type("M", (), {"enforce_eager": False})()
    config.parallel_config = type("P", (), {"tensor_parallel_size": 1})()
    config.speculative_config = None
    config.num_speculative_tokens = 0
    config.performance_mode = None
    config.uniform_decode_query_len = 1
    config.update_sizes_for_sequence_parallelism = lambda s: s

    VllmConfig._set_cudagraph_sizes(config)
    return cc.max_cudagraph_capture_size, cc.cudagraph_capture_sizes


for want in (12, 20, 42, 50, 100, 200):
    got, sizes = resolve(want)
    print(f"asked {want:>3} -> got {got:>3}  {'ok' if got == want else 'TRUNCATED'}  {sizes}")
```

### Suggested fix

`_set_cudagraph_sizes()` already appends `max_num_batched_tokens` off-grid for
exactly this reason, and the docstring states the property it is preserving:
"`max_num_batched_tokens` is also appended to the list if it fits within
`max_cudagraph_capture_size`, so the max batch size is captured even when
off-stride."

Applying the same treatment to `max_cudagraph_capture_size` itself costs one
extra captured graph. The value is already clipped to `max_num_batched_tokens`
at that point, so it cannot exceed the token budget.

Following the discussion in #54933: #37865, open since March, already implements exactly the fix suggested here — appending `max_cudagraph_capture_size` to the list when the grid did not reach it. It covers this reproducer and #54933's alike, since the append is independent of `decode_query_len`.

So this is the same root cause as #54933, reached through a non-speculative trigger rather than a speculative one, and it is not a separate bug. The three overlapping PRs are being sorted out in that thread.
