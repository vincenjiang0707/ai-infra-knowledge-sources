# [PR #56914] [Frontend][Metrics] Add per-request reasoning and content token metrics

## 正文

## Purpose

Closes #54829.

Add experimental reasoning-aware output-token metrics for reasoning models while preserving the existing aggregate per-request metrics:

- Reasoning and final-content token counts.
- Time to first token for each output category from a common scheduled-time origin.
- Per-category generation time, mean ITL, and throughput.
- An explicit unclassified token count for remaining parser control and boundary tokens.
- Streaming and non-streaming support for `/v1/responses` and `/v1/chat/completions`.
- Parser APIs for output-token classification, including ParserEngine and the built-in GPT-OSS Harmony parser.

This builds on the aggregate Responses API per-request metrics merged in #55084.

## Opt-in and compatibility

The feature is independently enabled with:

```bash
vllm serve openai/gpt-oss-20b \
  --enable-per-request-output-token-metrics
```

GPT-OSS automatically configures the `openai_gptoss` reasoning parser and uses vLLM's built-in Harmony parser, so it does not require an explicit `--reasoning-parser` argument. Other models require a compatible parser such as `--reasoning-parser gemma4` or `--reasoning-parser nemotron_v3`.

`--enable-per-request-output-token-metrics` does not require `--enable-per-request-metrics`; it includes the aggregate timing fields plus the category breakdown. The option is disabled by default. When enabled, vLLM verifies at startup that the resolved parser supports output-token classification and rejects unsupported parser configurations.

Existing `--enable-per-request-metrics` behavior remains aggregate-only. When the new option is disabled, `output_token_metrics` is omitted completely rather than serialized as `null`, preserving the existing response shape.

The nested object is marked experimental and subject to change, following the existing nested per-request submetrics pattern.

## Metrics semantics

The existing aggregate fields remain at their current locations. The optional category breakdown is nested under `metrics.output_token_metrics`:

```json
{
  "metrics": {
    "time_to_first_token_ms": 85.2,
    "generation_time_ms": 1240.5,
    "queue_time_ms": 12.3,
    "mean_itl_ms": 9.1,
    "tokens_per_second": 103.2,
    "output_token_metrics": {
      "reasoning": {
        "token_count": 36,
        "time_to_first_token_ms": 108.22,
        "generation_time_ms": 160.0,
        "mean_itl_ms": 4.57,
        "tokens_per_second": 218.75
      },
      "content": {
        "token_count": 20,
        "time_to_first_token_ms": 268.22,
        "generation_time_ms": 210.0,
        "mean_itl_ms": 11.05,
        "tokens_per_second": 90.5
      },
      "unclassified_token_count": 2
    }
  }
}
```

Category TTFT uses the request's scheduled time as a common origin. Timing has engine output-batch resolution. Category mean ITL and throughput are averaged over the interval between the first and last observed batches; individual timestamps are not inferred for tokens within a batch. They remain `null` when there are fewer than two category tokens or no measurable interval. Unsupported classification is represented by an omitted `output_token_metrics` object, while supported zero-token categories remain explicit objects with `token_count: 0`.

The category reasoning count reuses the parser's established usage reasoning count. It therefore equals `usage.output_tokens_details.reasoning_tokens` for Responses and `usage.completion_tokens_details.reasoning_tokens` for Chat Completions when that existing usage detail is enabled. For Harmony, the count follows the existing usage convention in which analysis and addressed commentary or tool-call tokens count as reasoning. Content counts final-answer payload tokens; unclassified contains the remaining boundary, framing, and parser-control tokens. Reasoning, content, and unclassified counts sum to the endpoint's total generated-token count.

Multi-generation Responses workflows continue to omit request metrics because one generation's timestamps cannot represent the full request.

## Why this is not a duplicate

I searched open PRs for #54829, reasoning per-request metrics, and output-token metrics. No open PR implements this feature. #55084 added aggregate Responses metrics but does not split reasoning and content output. #46768 added aggregate metrics to Chat Completions and Completions and identified reasoning-aware metrics as future work.

## A100 model validation

Validation used one NVIDIA A100X 80 GB GPU. For each supported reasoning parser, both Chat Completions and Responses were exercised in streaming and non-streaming modes with `--enable-per-request-output-token-metrics` and without `--enable-per-request-metrics`.

| Model | Parser/configuration | Result |
| --- | --- | --- |
| `google/gemma-4-E2B-it` | `--reasoning-parser gemma4` | Passed all four endpoint/mode combinations. A 96-token reasoning stream reconciled as 95 reasoning + 0 content + 1 control token. Reasoning matched the existing usage field, and metrics appeared only in the final streaming event. |
| `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-FP8` | `--reasoning-parser nemotron_v3` | Passed all four endpoint/mode combinations. Every run reconciled as 40 reasoning + 60 content + 1 control token = 101 output tokens; reasoning matched usage exactly. |
| `openai/gpt-oss-20b` | `openai_gptoss` + built-in Harmony parser (automatically selected) | Passed all four endpoint/mode combinations. A completed low-effort run reconciled as 5 reasoning + 1 content + 9 Harmony framing/control tokens = 15 output tokens. A 128-token streaming stress run also reconciled exactly; reasoning matched usage in both cases. |
| `meta-llama/Llama-3.2-1B-Instruct` | No reasoning parser | Correctly rejected the output-token-metrics option with a clear unsupported-classifier error. Baseline Chat and Responses requests with ordinary `--enable-per-request-metrics` passed, retained aggregate metrics, and omitted `output_token_metrics`. |

For all supported models:

- `reasoning.token_count + content.token_count + unclassified_token_count` equaled the endpoint's total output-token usage.
- The reasoning count equaled the endpoint's existing reasoning-token usage field.
- Chat streaming emitted metrics exactly once in the final usage chunk.
- Responses streaming emitted metrics exactly once in `response.completed`.
- Category mean ITL and throughput were computed from first-to-last observed batch intervals, including multi-token engine updates. A post-change Gemma Responses stream returned non-null reasoning ITL and throughput while preserving token reconciliation.

This change affects response accounting and serialization only; it does not change generated content or the classification used by the existing reasoning output APIs.
