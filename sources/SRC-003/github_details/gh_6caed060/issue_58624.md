# [Issue #58624] [Performance]: MoE decode ~15% slower on SM12x since #56876 (DeepGEMM contiguous-layout alignment 128 instead of 64)

source: https://github.com/vllm-project/vllm/issues/58624
state: open | updated: 2026-09-24T21:27:20Z

## 正文

### Report of performance regression

Since #56876 moved DeepGEMM to vllm-project/DeepGEMM `e1f418c2`, `get_theoretical_mk_alignment_for_contiguous_layout` returns 128 on SM12x. DeepGEMM 2.6.1 (`8b1392b9`) returned 64 when each expert gets at most 64 rows. The fork's SM120 port (vllm-project/DeepGEMM#4) left that rule unwired. vLLM pads the contiguous MoE layout with this alignment, so decode pads twice as many rows and the grouped GEMMs run with `BLOCK_M=128`.

DGX Spark (GB10, SM121), Qwen3.6-35B-A3B-FP8, DFlash (7 speculative tokens), TP1, vLLM main 70fc359d (official cu130 aarch64 wheel). Server-side time per decode step:

| | 1 request | 16 requests |
|---|---|---|
| main | 56.6 ms | 173.7 ms |
| main + diff below | 50.2 ms | 146.5 ms |
| c81ace18 build (before #56876) | 50.5 ms | 149.0 ms |

With nsys at 16 requests, the MoE grouped GEMMs and the SiLU-mul/quant kernels account for 23.5 of the 23.7 ms difference. Greedy output is identical with and without the diff.

### Proposal to improve performance

Port the SM12x rule from deepseek-ai/DeepGEMM#447 into vllm-project/DeepGEMM and bump the pin, or restore it in vLLM's wrapper. This is equivalent to the patch measured above:

```diff
--- a/vllm/utils/deep_gemm.py
+++ b/vllm/utils/deep_gemm.py
@@ -382,6 +382,13 @@ def get_theoretical_mk_alignment_for_contiguous_layout(
     _lazy_init()
     if _get_theoretical_mk_alignment_for_contiguous_layout_impl is None:
         return _missing()
+    if current_platform.is_device_capability_family(120):
+        # vllm-project/DeepGEMM returns 128 on SM12x; 2.6.1 used 64 when each
+        # expert gets at most 64 rows.
+        per_group_m = expected_m
+        if expected_m is not None and num_groups:
+            per_group_m = cdiv(expected_m, num_groups)
+        return 64 if per_group_m is not None and per_group_m <= 64 else 128
     if num_groups is None:
         return _get_theoretical_mk_alignment_for_contiguous_layout_impl(expected_m)
     if num_groups <= 0:
```

From reading the code only (not measured): on SM10x the fork returns a fixed 256 regardless of `expected_m`, so the alignment no longer shrinks below 128, where 2.6.1 went down to 32 for small per-expert M. Small-batch decode on B200/GB200 may be affected the same way.

I'm not planning to open a PR for this, so it's free for anyone to pick up.


## 评论 (1)

### hclsys · 2026-09-24

Second GB10 (sm_121) here. I can corroborate the *before* side but not the regression itself, and the reason is worth stating so nobody reads this as a failed repro.

My tree still vendors DeepGEMM **2.5.0**, i.e. older than both the 2.6.1 you cite and the `e1f418c2` pin from #56876. On it, the alignment is 64 across the whole decode-shaped range:

```
num_groups  expected_m  per-expert_m  alignment
         8          64             8         64
         8         512            64         64
        16        1024            64         64
        32        2048            64         64
```

So the pre-#56876 behaviour you describe reproduces on independent sm_121 hardware. I can't produce the 128 without moving to the new pin, so treat this as supporting your baseline, not as a second measurement of the slowdown.

On the proposed diff — the direction looks right to me and it needs no new imports (`current_platform` and `cdiv` are both already imported in that module). One thing to fix before it lands: the new block returns *before* the existing `num_groups` validation, so on SM12x the degenerate cases stop raising.

```
num_groups =  0  -> returns 128, and per_group_m silently falls back to the TOTAL expected_m
num_groups = -3  -> cdiv(512, -3) = -170, so -170 <= 64 -> returns 64
                    (both raise ValueError on every non-SM12x path today)
```

Moving the block below the `if num_groups is None` / `if num_groups <= 0` guards keeps the validation uniform across architectures and makes the `num_groups` truthiness check unnecessary.

Happy to run the alignment probe again once the pin moves, if a second sm_121 confirmation of the 128 is useful.
