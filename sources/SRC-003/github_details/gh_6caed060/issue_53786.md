# [Issue #53786] [Feature][KV cache] Support fine-grained prefix hits for sliding-window groups

source: https://github.com/vllm-project/vllm/issues/53786
state: open | updated: 2026-09-22T10:58:51Z
labels: quantization

## 正文

## Motivation

Multi-turn agent workloads re-send a large stable prefix every turn, so prefix-cache quality dominates TTFT. We run a Qwen3.5-class hybrid (16 full-attention + 48 linear/GDN layers) with a DFlash2 speculative draft whose 5 layers are all `sliding_attention` (`sliding_window=2048`), and measured reuse capped far below what the fine-grained path would allow — because the sliding-window manager disables fine-grained hits for the shared lookup boundary.

## Precise behavior (source of both `0.26.1rc1.dev926+gb05ae5dc0` and current `main`, verified 2026-08-25)

In a hybrid coordinator using fine-grained align-mode Mamba hits, any coarser cache group whose manager lacks fine-grained lookup disables fine-grained hits for the shared lookup boundary ([`kv_cache_coordinator.py`](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/kv_cache_coordinator.py), the `enable_partial_hash_hits` gating): `SlidingWindowManager` sets `supports_fine_grained_hash_lookup = False` and its block size differs from the hash unit, so `--prefix-match-unit 16` is accepted and then disabled with a single boot warning —

```
WARNING [kv_cache_coordinator.py] Disabling fine-grained prefix-cache hits
because these KV cache managers require block-aligned lookups:
SlidingWindowManager.
```

— a warning-only fallback that is easy to miss. The SWA lookup itself asserts *"Fine-grained partial hits are not supported for sliding window now"*, which reads as an acknowledged TODO.

In our layout the sliding-window group exists **only because of the spec-decode draft**; the target has zero windowed layers, and its full-attention and Mamba managers both support fine-grained lookup.

Usable replay = `(floor((N-1)/1648) - 1) * 1648` **on this specific configuration** (model, quantization, block-size resolution, sparse-retention default, EAGLE/dflash config — a different quant resolved the mamba-page block bump to 1600 instead of 1648). Real two-turn agent sessions reproduce the law exactly (6/6 reps matching the prediction to 4 decimals). Prefix caching works and helps (TTFT 2.24 s → 0.81 s warm at 9.8k tokens) — it is capped well below what fine-grained hits should allow. We have not tested whether SWA fine-grained support alone lifts the cap under EAGLE: per #52371, FA fine hits + Mamba + EAGLE can still reconcile down a whole physical Mamba block, so Mamba boundary checkpoints (#53614) may also be required.

## Ask

1. Implement fine-grained (partial) prefix hits for sliding-window groups — completing the acknowledged TODO. We're happy to contribute; the design questions below are exactly where we'd want maintainer direction first:
   - mapping fine candidate boundaries to the physical block run covering the window (null padding that preserves physical block-table indices);
   - EAGLE drop semantics when the block list is physical;
   - retention: keeping every physical block needed to reconstruct a registered fine boundary's window.
2. Related: under interleaved-session memory pressure, one evicted tail block invalidates an entire SWA hit (#48435). Fine-grained SWA retention should be designed with that failure mode in mind.

## Alternatives considered

```
- Disabling speculative decoding removes the windowed draft group and lifts the veto (trade-off: decode throughput).
- A non-windowed draft, if compatible, same effect.
- Accepting the coarse ceiling (current state; documented in our ops notes).
- We looked for a coordinator-level bypass (excluding the draft group from the veto or from lookup) and concluded it is unsound without per-group computed-token boundaries — the coordinator's single shared `num_local_computed_tokens` would claim draft KV that does not exist.
```

### Suppressor72 · 2026-08-25

Following up with a **proposed design direction** for the three open points above, so maintainers have something concrete to confirm or correct rather than open questions. Everything below is desk-checked against the `0.26.1rc1.dev926` source and our measured behavior; we're happy to adjust to maintainer preferences and start on the CPU test matrix + implementation.

### 1. Lookup: fine endpoint, physical block-table geometry

Keep block tables in physical-block units. Define `p` as the exclusive cached-prefix length. For each candidate `p` at `hash_block_size` granularity, look up the endpoint hash and then independently resolve every physical block intersecting

`[max(0, p - (sliding_window - 1)), p)`

Return the exact hit length `p` plus one physical-block list per KV group. Each list has `ceil(p / physical_block_size)` slots, with null *block slots* before the retained window so global block-table indices are preserved. Partial left/right edges remain real physical blocks; there is no token-level null padding inside a block.

This uses the existing chained request hashes and the BlockPool partial-entry mechanism, but SWA still needs producer-side partial-tail registration. A lookup must reject an endpoint if any physical block in its required window has been evicted.

We do not assume the current physical-block miss-skipping TODO transfers to fine endpoint misses: absence of the hash for `p` does not imply absence of `p - hash_block_size` under sparse SWA retention. Without an additional endpoint index, worst-case endpoint probing remains `O(prompt / hash_block_size)`. We would benchmark that cost and separately optimize physical-run validation, rather than claim a stronger bound up front.

### 2. EAGLE: exact drop, followed by independent window validation

Let `e` be the matched EAGLE lookahead endpoint and let `q` be the returned prefix after dropping the required speculative tail. In the common case the drop is one hash unit (`q = e - hash_block_size`), provided that unit covers the complete speculative-prefill lookahead; otherwise the drop must be rounded up to a whole number of hash units or the configuration rejected.

After computing `q`, independently validate every physical block required by the SWA window at `q`. If that validation fails, reject the candidate and continue the ordinary right-to-left search. An earlier physical-aligned endpoint is acceptable only if its own EAGLE lookahead and complete window both match; it is not inferred to be safe from the failed candidate.

The coordinator already accepts exact token-length reductions from capable managers and reconciles them monotonically. Tests must cover repeated fixed-point reductions, multiple EAGLE groups, and retention of the post-drop boundary.

### 3. Retention and eviction: complete on publication, revalidated on use

Insert a fine SWA endpoint key only after every physical block needed for that endpoint's window has been cached, including a partial physical tail when the endpoint is inside a block. Plumb the fine hit alignment into the SWA retention mask so it can select the physical run for the exact replay boundary.

BlockPool's current multi-hash support removes multiple keys owned by one physical block; it does not model an endpoint depending on several blocks. Therefore an interior eviction will not automatically deregister a key owned by the endpoint block. The correctness rule is that lookup always revalidates the full physical window and treats a stale endpoint as a miss.

We would not pin a complete window per registered fine boundary: at small `prefix_match_unit` values that can amplify dependencies and interfere with cache admission under pressure. Atomic boundary invalidation or SWA-aware eviction would require separate dependency metadata and should be evaluated as follow-up work. This change makes fine hits safe under #48435-style pressure, but does not by itself claim to fix that issue's reuse cliff.

### Sequencing and validation

Gate the capability on the complete local path, including fine lookup, partial-tail registration, CoW, retention alignment, EAGLE, and either support for or explicit exclusion of KV connectors/events.

Start with CPU tests for every fine offset, short/equal/non-divisible windows, both partial window edges, exact EAGLE lengths, incomplete-window fallback, interior eviction, shared physical tails, and coordinator fixed-point convergence. Then run #48435-style multi-session pressure and measure lookup CPU, hash-map metadata, scheduler latency, memory, and throughput across several `prefix_match_unit` values.

For corruption detection, compare repeated deterministic no-hit and warm-hit runs under the same speculative configuration, including target-logit checks at adversarial boundaries and exact greedy-token comparison. A no-spec greedy run can be an additional oracle, but nospec-vs-nospec does not exercise the draft SWA path.

SWA support can be developed independently, but end-to-end benefit on this hybrid remains gated on exact-boundary Mamba checkpoint materialization and coordinator reconciliation (#52371/#53614 or equivalent). We would not claim the two paths are composable until their joint EAGLE, CoW, retention, and pressure tests pass.

Does this direction look right? If it does (or with corrections), we'll start with the CPU-level tests and the SWA lookup path.

### Suppressor72 · 2026-08-29


Thanks for picking this up — the plan is aligned with the design sketch above, and reusing `BlockPool.cache_partial_block()` looks like the right primitive: the existing fine-grained implementations in `FullAttentionManager` and `MambaManager` both use it for producer-side partial-tail registration.

A few correctness invariants from the design comment that may be useful in the test plan:

```
1. **Block-table geometry.** Keep block tables in physical-block units: null *block slots* before the retained window so global block-table indices are preserved; partial edges stay real physical blocks, no token-level padding inside a block.
2. **Publish-complete.** Insert a fine endpoint key only after every physical block needed for that endpoint's window `[max(0, p − (W−1)), p)` (with `W` = `sliding_window`) is cached, including a partial physical tail.
3. **Revalidate on use.** `cache_partial_block()` removes all hash keys owned by an evicted physical block, but it has no reverse dependency from an endpoint key to every block in that endpoint's SWA window. If an interior window block is evicted while the endpoint-owning block survives, the endpoint key can remain live; lookup therefore needs to revalidate the full physical window and treat an incomplete endpoint as a miss. This is the pressure case the design needs to handle around #48435, without pinning a full window per boundary. Also, the coarse manager's miss-skipping optimization is currently only a TODO; its inference does not transfer automatically to fine endpoints, because under sparse SWA retention a miss at `p` says nothing about the independently registered endpoint at `p - hash_block_size`.
4. **EAGLE/MTP drop exactness.** For the new fine path, the dropped suffix should be a whole number of hash units covering the complete speculative-prefill lookahead; one hash unit is enough only when it covers that span, otherwise round up or reject an unsupported configuration. After computing the reduced endpoint `q`, independently validate its complete SWA window — do not infer that an earlier endpoint is safe from the failed candidate. #52070 is a useful warning here: it was withdrawn after skipping an EAGLE cache-hit drop changed greedy tokens, so I'd include adversarial-boundary warm-hit vs no-hit greedy identity under the same speculative configuration as a correctness test.
5. **Endpoint probe cost.** Without an endpoint index, a fine miss can probe `O(prompt / hash_block_size)` endpoints (endpoint probes specifically — each then validates its own physical window, so total validation work can be a multiple). Fine to ship without one, but worth benchmarking lookup CPU / scheduler latency across several `prefix_match_unit` values.
6. **Connectors/events.** Please include connector and KV-cache-event behavior in the capability gate, either supporting them or rejecting unsupported combinations explicitly. The Mamba-align fine path illustrates the extra lifecycle involved: `_producer_partial_tail_reqs` connects producer-side partial registration to CoW and connector offload. SWA may not need identical bookkeeping, but its partial entries, CoW, event publication/removal, and connector-visible boundaries should be tested or gated deliberately.
```

On the H20 end-to-end, a model whose target has SWA layers is a useful SWA control, but it does not by itself prove that the new fine path ran: today `enable_partial_hash_hits` is activated by a partial align-mode Mamba group, so the activation condition will need extending (or the run needs a hybrid layout that already enables partial lookup) — worth recording the resolved hash/physical block sizes and `enable_partial_hash_hits` from the boot to confirm the fine mode is actually on. A draft-with-SWA run — EAGLE/MTP over a full-attention target, ideally with the motivating hybrid target as a second case — is the most direct validation of this issue. On hybrid Mamba-align stacks, the PR should also avoid claiming that SWA support alone lifts the separate Mamba/coordinator ceiling tracked by #52371/#53614.

Happy to review an early diff or the PR once it's open. And since the motivating workload (a spec-decode draft inducing the only SWA group, over a hybrid GDN target) may be hard to reproduce elsewhere, I can also run your PR on that stack and share the measured cache-hit numbers against the table in the issue.
