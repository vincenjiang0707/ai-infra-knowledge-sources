### 🐛 Describe the bug
Since upgrading from `vllm-openai-cpu:v0.28.0-x86_64` to `vllm-openai-cpu:v0.29.0-x86_64`, I've been hitting a crash on the very first request. The OpenAI-compatible server for an embedding model (bge-m3) on CPU boots successfully — engine init, warmup, and /v1/models all work, and check_health polls succeed for about a minute. However, on the first real /v1/embeddings request, the EngineCore worker process dies unexpectedly and the engine becomes permanently dead (EngineDeadError), returning a 500 to the client. I tried upgrading to `vllm-openai-cpu:v0.30.0-x86_64`, but this did not resolve the issue.

### sjsreehari · 2026-09-24

Hi @niekvleeuwen, thanks for the detailed report and logs.

### Root Cause
We traced the exact regression between `v0.28.0` and `v0.29.0`/`v0.30.0`:
1. In `v0.28.0`, the CPU image did not bundle `triton-cpu`, so `HAS_TRITON` was `False`. In `vllm/config/vllm.py`, `VllmConfig.use_v2_model_runner` checked `if not HAS_TRITON: return False`, causing CPU to default to the stable V1 `CPUModelRunner`.
2. In `v0.29.0`, commit `373592ef57` ("Ship triton-cpu wheel") bundled `triton-cpu` into `docker/Dockerfile.cpu`. As a result, `HAS_TRITON` became `True` on CPU.
3. Because `use_v2_model_runner` had no platform guard for CPU, it unintentionally started returning `True` by default on CPU.
