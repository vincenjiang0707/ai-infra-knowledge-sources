## 正文

## Summary

Since v0.26.0, `profile_cudagraph_memory()` reports ~4.2 GiB of "CUDA graph
memory" on a hybrid-GDN model (Qwen3.5-122B-A10B, int4 AutoRound, SM120) where
0.23.x reported 0.56 GiB for the *same graph set* (PIECEWISE=7, FULL=5). The
KV cache pool shrinks by the difference: **1,489,281 → 1,135,957 tokens
(−23.7%)** on 0.26.1 nightly, −17.9% on v0.26.0, with identical config.

Root cause (evidenced below): **~96% of the reported number is not graph
memory.** It is the allocator high-water mark of the estimator's *first FULL
sample*, the only sample that runs `profile_seq_lens =
min(max_model_len, max_num_batched_tokens // num_tokens)` — a warmup+capture
whose total profiled context across the batch equals `max_num_batched_tokens`.
That forward transiently allocates **~128 KiB per batched context token** on
0.26.x (it did not on 0.23.x), and the measurement — a free-memory delta with
no `empty_cache()` between samples — charges the whole transient as CUDA
graph memory and sizes the KV pool down by it.

The real captures are innocent: with the new
`--profiler-config '{"capture_torch_profiler": true, ...}'` tracing, the
largest single allocation in any of the 12 real graph captures is **11.8
MiB**, and the estimator's own per-graph increments are 14–26 MiB.

⚠️ **A one-sided fix is dangerous** — see "Why this must be fixed as a pair"
below. On this model the mischarged 4 GiB currently doubles as activation
headroom that the memory profiler fails to attribute to the GDN long-prefill
path; releasing it to the KV pool (e.g. `cudagraph_mode: PIECEWISE`, or
`VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0`) produces a reproducible OOM
crash in `chunk_gated_delta_rule` on a single 32k prefill.

## Symptom

Identical config, boot logs:

| | 0.23.1 dev714 | v0.26.0 | 0.26.1rc1.dev245 |
|---|---|---|---|
| Model loading | 62.61 GiB | 62.61 GiB | 62.82 GiB |
| CUDA graph memory (actual) | 0.56 GiB | 4.18 GiB | 4.19–4.21 GiB |
| Available KV cache memory | 18.74 GiB | 15.43 GiB | 14.31 GiB |
| GPU KV cache size | 1,489,281 tok | 1,223,338 (−17.9%) | **1,135,957 (−23.7%)** |
| Max concurrency @262,144 | 5.68x | 4.67x | 4.33x |

Graph set is identical in all three: PIECEWISE=7 (sizes 1–32), FULL=5
(sizes 1–16; capped by `max_num_seqs=16`). KV efficiency per GiB is unchanged
(≈79.3–79.5k tok/GiB) — the loss is purely "less memory handed to the pool".

## Evidence 1 — the estimator's own breakdown: it's one sample, not the graphs

`VLLM_LOGGING_LEVEL=DEBUG` on 0.26.1rc1.dev245:

```
Profiling CUDA graph memory: PIECEWISE=7 (largest=32), FULL=5 (largest=16)
Estimated PIECEWISE CUDA graph memory:  120.00 MiB first-capture + (7-1) × 14.00 MiB per-graph
Estimated FULL      CUDA graph memory: 4108.00 MiB first-capture + (5-1) × 24.00 MiB per-graph
Estimated CUDA graph memory: 4.19 GiB total
```

4,108 of 4,290 MiB is the FULL "first-capture" — the only sample where
`_warmup_and_capture` receives `profile_seq_lens` (gpu_model_runner.py, the
`mode == CUDAGraphMode.FULL and i == 0` branch in `profile_cudagraph_memory`).
The FULL graphs themselves cost ~24 MiB each — same order as 0.23.x.

## Evidence 2 — it scales with max_num_batched_tokens, not max_model_len

Three boots of the same image, only the flagged knob changed:

| max-model-len | mnbt | FULL first-capture | total estimate | KV pool |
|---|---|---|---|---|
| 262144 | 32768 | 4,108 MiB | 4.19 GiB | 1,135,957 |
| 131072 | 32768 | 4,108 MiB | 4.20 GiB | 1,031,329 |
| 131072 | 16384 | **2,070 MiB** | 2.12 GiB | 1,490,081 |

Exactly linear in mnbt (~128 KiB per batched context token), independent of
max_model_len. Consistent with `profile_seq_lens = mnbt // num_tokens` making
**total profiled context = num_reqs × (mnbt / num_reqs) = mnbt**. A separate
config on the same GPU with mnbt=2048 (NVFP4 sibling model) reports 0.61 GiB.

## Evidence 3 — capture traces: real captures allocate nothing big

`--profiler-config '{"profiler":"torch","torch_profiler_dir":"/traces","capture_torch_profiler":true}'`
traced all 12 real captures (trace for `capture_16_FULL` attached in a comment below; the other
11 available on request). Largest single allocation in ANY capture:
**11.8 MiB** (`aten::empty`); per-capture allocation totals 0.5–2.0 GiB of
small transients that the shared pool overlays across graphs. The real
capture path (`capture_model` → `_capture_cudagraphs`) never passes
`profile_seq_lens`.

The runtime "actual" figure is `start_free − end_free` spanning **all
warmups + captures + vision-encoder graph capture, measured before the
post-capture `empty_cache()`** — so warmup transients cached in the allocator
are counted as graph residency. Estimate and "actual" agree (0.4% diff)
because they mismeasure the same way, not because the graphs hold 4 GiB.

## Evidence 4 — the estimator didn't change; the model-side forward did

I diffed the two images file-by-file: `profile_cudagraph_memory`,
`_warmup_and_capture`, `profile_seq_lens` plumbing, `cuda_graph.py`
(pool sharing), `cudagraph_dispatcher.py`, and the GDN
`build_for_cudagraph_capture` are **byte-identical** between 0.23.1 dev714
and 0.26.1rc1.dev245 (modulo a ROCm stream fix and the new profiler hooks).
dev714 runs the same profile-seq-lens sample and reports 0.5 GiB.

So the ~128 KiB/context-token transient is a 0.23→0.26 regression in the
model-side decode-with-context path executed by that sample (the window
includes the FLA move to `vllm/third_party/flash_linear_attention`, the
`mamba/gdn/` package refactor, and new ops like `gather_initial_states`). I
did not pin the exact op: the capture profiler doesn't cover the estimator
phase. Wrapping `profile_cudagraph_memory()` with
`torch.cuda.memory._record_memory_history()` should name it in one run.

## Why this must be fixed as a pair (data from the v0.26.0 evaluation)

On v0.26.0 I tested the obvious mitigations:

- `cudagraph_capture_sizes: [1,2,4,8,16]`: 4.15 GiB — trimming graphs is not
  the lever (consistent with per-graph ≈ 24 MiB).
- `cudagraph_mode: PIECEWISE`: reports 0.11 GiB, KV pool grows to 1,546,269 —
  and then the engine **OOM-crashes on a single 32k-token prefill**:

  ```
  vllm/third_party/flash_linear_attention/ops/wy_fast.py, recompute_w_u_fwd
      w = k.new_empty(B, T, H, K)
  torch.OutOfMemoryError: Tried to allocate 458.00 MiB. GPU 0 ... 121.00 MiB free
  ```

- `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0`: same failure mode, silently.

The memory profiler measures peak activation at 8.29 GiB for this config, but
the real GDN chunked-prefill peak is ~4 GiB higher. The mischarged
"cudagraph" reservation currently absorbs that gap by accident. Therefore:

1. **Accounting fix** — don't charge profiling/warmup transients as CUDA
   graph memory (measure retained pool after `empty_cache()`, or isolate the
   profile-seq-lens sample from the graph-memory figure); **and**
2. **Profiling fix** — make the activation-peak profiling actually cover the
   hybrid (GDN) chunked-prefill worst case, so the freed memory is reserved
   for the reason it is actually needed.

Fixing (1) alone converts this from a −24% KV pool regression into an OOM
crash for GDN hybrids at long prefill. (3) Optionally, finding and removing
the new ~128 KiB/token allocation fixes the estimate at the source and
probably improves real decode-with-long-context memory behavior too.

## Reproduction

Any GDN hybrid at a non-trivial mnbt shows it; no load needed:

```bash
# boot with VLLM_LOGGING_LEVEL=DEBUG and read the two
# "Estimated {PIECEWISE,FULL} CUDA graph memory" lines:
#   FULL first-capture ≈ 128 KiB × max_num_batched_tokens, per-graph ~24 MiB
# halve --max-num-batched-tokens → FULL first-capture halves, KV pool jumps
```

### Burlesque1 · 2026-09-23

Cross-model reproduction on **GLM-5.3-Flash (4×H20, TP=4, CUDA)** — same over-count, and confirms the "one-sided fix is dangerous" warning here too.

| config | graph charged | KV pool | long-prefill |
|---|---|---|---|
| old vLLM (no profiler) | 2.30 GiB | 5.30 GiB / 416,630 tok | stable |
| v0.29.1rc1 `profiling=1` | 4.5 GiB | 3.42 GiB / 268k tok | can't fit `max_model_len=335232` |
| v0.29.1rc1 `profiling=0` | 0 | 7.28 GiB / 571,929 tok | **50k-token prefill CUDA OOM** |

The `profiling=0` OOM (`expandable_segments: memory mapping failed with OOM ... free: 4063232`) happened at 98% GPU usage while idle (util target 0.95), so the long-prefill activation peak — the chunked-scan buffers that are the profiling blind spot described in #54775 — had no headroom left.

Safe workaround that reproduces the old pool without the OOM: `profiling=1 + --gpu-memory-utilization 0.97` → 5.32 GiB / 418,772 tok, 50k/100k prefill stable. Per-token KV 13.67 KB (7.28 GiB / 571,929 tok).
