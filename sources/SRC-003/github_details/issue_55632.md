# [Issue #55632] [Bug][ROCm] 15s EngineCore cleanup grace is defeated by MultiprocExecutor's 9s worker-kill budget; workers SIGKILLed mid-teardown

## 正文

```text
GPU      : 8x AMD Instinct MI355X, single node
Parallel : TP=8, DCP=1, PP=1, EP=1
Platform : Linux 5.15.0-70-generic, Python 3.12
```

`collect_env.py` was not run because a long benchmark occupies the GPUs; the
versions above were read from the installed `vllm-*.dist-info`, the torch
dist-info, and `/opt/rocm/.info/version`.

### 🐛 Describe the bug

On ROCm, two nested shutdown timers disagree, and the inner one force-kills the
processes that the outer one exists to protect.

`get_engine_process_shutdown_timeout()` returns
`ROCM_ENGINE_PROCESS_SHUTDOWN_TIMEOUT_S = 15.0` on the zero/zero path
(`vllm/v1/engine/utils.py`). Its docstring states the purpose:

> The parent process manager still needs a separate window in which the
> EngineCore can release device resources before it is force-killed. ROCm
> teardown can take longer than the generic best-effort window, and
> force-killing during teardown can leave VRAM resident.

That 15s grace applies to the **EngineCore process**. But inside EngineCore,
`MultiprocExecutor.shutdown()` (`vllm/v1/executor/multiproc_executor.py`) is
platform-agnostic and runs its own, shorter escalation against the **worker
processes**:

1. wait `envs.VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS` — default `5`
2. `proc.terminate()` (SIGTERM)
3. wait a hardcoded `4` seconds — `wait_for_termination(active_procs(), 4)`
4. `proc.kill()` (SIGKILL)

That inner budget totals 9s and therefore always expires inside the outer 15s
window. The workers are the processes holding device memory, so on ROCm they are
SIGKILLed mid-teardown — which is exactly the outcome the 15s grace was added to
prevent. The outer grace never gets a chance to matter: in our runs
`Process manager: force killing remaining processes` never fires, because the
inner escalation has already finished by +9s.

SIGTERM does not help either. The worker's handler raises `SystemExit`, but a
signal handler only propagates once the interpreter regains control, and at that
point the worker main thread is blocked in native teardown —
`worker.shutdown()`, `destroy_model_parallel()`,
`destroy_distributed_environment()` — i.e. RCCL communicator destruction and
release of a multi-million-token KV pool. So step 3 elapses and step 4 kills it.

### Evidence

Five independent 1-hour runs (8-way TP, MI355X, `VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS`
unset, offsets relative to `Executor: waiting for worker exit`):

| run | workers | SIGTERM | SIGKILL | `all workers exited gracefully` | outer force-kill | leaked-resource warnings |
|---|---|---|---|---|---|---|
| 1 | 8 | +5s | +9s | never | no | 1 |
| 2 | 8 | +5s | +9s | never | no | 2 |
| 3 | 8 | +5s | +9s | never | no | 2 |
| 4 | 8 | +5s | +9s | never | no | 2 |
| 5 | 8 | +5s | +9s | never | no | 2 |

Deterministic: 5/5, identical to the second, and the graceful-exit path is never
taken. Representative log excerpt:

```
(EngineCore pid=3070) INFO  [core.py:1501] [shutdown] EngineCore: start mode=abort timeout=0s
(APIServer  pid=2246) INFO  [utils.py:249] [shutdown] EngineCore process manager: using 15.0s ROCm cleanup grace after immediate request abort
(EngineCore pid=3070) INFO  [multiproc_executor.py:472] [shutdown] Executor: waiting for worker exit count=8
(EngineCore pid=3070) WARN  [multiproc_executor.py:484] [shutdown] Executor: workers still running after grace period; sending SIGTERM count=8
(EngineCore pid=3070) WARN  [multiproc_executor.py:494] [shutdown] Executor: workers still running after SIGTERM; sending SIGKILL count=8
/usr/lib/python3.12/multiprocessing/resource_tracker.py:279: UserWarning: resource_tracker: There appear to be 8 leaked semaphore objects to clean up at shutdown
/usr/lib/python3.12/multiprocessing/resource_tracker.py:279: UserWarning: resource_tracker: There appear to be 1 leaked shared_memory objects to clean up at shutdown
```

The leaked semaphores (one per worker) and shared-memory segment are the
expected debris of killing 8 workers mid-cleanup, and are absent from the
graceful path by construction.

### Why this matters

#52281, which added the ROCm grace, was motivated by an AMD CI run where "GPU
memory then remained at 11.72 GB for the full 120-second release wait." That
symptom is still reachable on this path, because the memory is held by the
worker processes and the fix only protects their parent.

### What we have not established

How long ROCm worker teardown actually needs. It has never been allowed to
finish in our runs — everything past 5s was cut short — so `> 5s` is the only
claim the data supports. It could be 6s or well past 15s. We are measuring it
next and will report the number here.

That measurement matters for the fix: if workers need more than ~15s, simply
raising `VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS` moves the force-kill up one level
to the outer manager rather than eliminating it, and both constants need to move
together.

### Suggested direction

Deliberately not sending a patch until the number above is known, but the shape
seems to be one of:

- Make the worker-exit budget ROCm-aware from the same constant that governs the
  outer grace, so the inner escalation cannot undercut the outer allowance; or
- Have `MultiprocExecutor.shutdown()` respect the remaining outer budget instead
  of applying an independent 5+4s schedule.

Happy to send a PR once we can justify the constant with a measurement.

### Note on a related but separate report

The same teardown also intermittently logs a spurious `EngineDeadError`
(4 of our 5 runs). That is #48745, already open and reported from CUDA hardware,
with a fix in flight in #49000 — so it is not part of this report. Our logs are consistent
with the poison-pill root cause described in that issue rather than with the
worker kill described here: the `EngineDeadError` lands immediately after
`MPClient: cleaning up background resources` / `MPClient: complete`, and the one
run that did not log it still SIGKILLed its workers identically. The two look
independent.

Fix proposed in #55646: derive the ROCm worker grace from `ROCM_ENGINE_PROCESS_SHUTDOWN_TIMEOUT_S` minus the SIGTERM step, so the executor's schedule can no longer expire inside the window the process manager grants for device teardown.

Deliberately not inventing a constant, since the real teardown duration is still unmeasured — the PR reuses the budget the outer manager already allows, which holds regardless.
