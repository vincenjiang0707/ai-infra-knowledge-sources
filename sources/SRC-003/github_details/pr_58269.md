## Purpose
The test requests `block_size=560`, but Qwen3-Next's linear-attention layers use the GDN backend, and on XPU those kernels only support block sizes divisible by 64, so `XPUPlatform.update_block_size_for_backend` rounds the request up to `cdiv(560, 64) * 64 = 576`:

```bash
INFO [kv_cache_utils.py:763] kv lcm block sizes 576
```
The step-action tables in the test are written as absolute token counts around a 560-token boundary (554, 557, 560*2, ...), so every case that depends on where a block boundary falls breaks. 

Since `BLOCK_SIZE` is an arbitrary hard-coded value here and the test is about where block boundaries fall relative to the in-flight speculative tokens, not about any particular block size. This PR sets it to a multiple of 64 and expresses the step-action tables relative to it.
