# [Issue #13686] [BUG]: Standalone Rust EPP fails with agentgateway because ProtocolConfiguration misses send_body_without_waiting

source: https://github.com/ai-dynamo/dynamo/issues/13686
state: open | updated: 2026-09-21T08:48:57Z
labels: bug, language::rust, backend::vllm, deployment::k8s, epp

## 正文

### Describe the Bug

When running the Dynamo Rust EPP (dynamo-ext-proc) in standalone mode behind agentgateway v1.4.1 with `inferenceExtension.enabled=true`, every inference request fails at the ext_proc boundary with:
```SH
ProtocolConfiguration mismatch — failing stream
request_body_mode=4 response_body_mode=4 send_body_without_waiting=false
```

The Rust EPP strictly requires `send_body_without_waiting_for_header_response=true`, but agentgateway sends false even though its own ext_proc implementation actually streams the body before waiting for the header response.

### Steps to Reproduce

1. Install Gateway API + GAIE CRDs + agentgateway v1.4.1 with `inferenceExtension.enabled=true`.
2. Deploy a vLLM worker and a standalone Rust EPP and EPP Service.
3. Create an `InferencePool` relate to the Rust EPP Service.
4. Create an `HTTPRoute` attached to the agentgateway pointing to the `InferencePool`.
5. Send any request, e.g. `curl http://<gateway>/v1/models`.

### Expected Behavior

The request reaches the Rust EPP, which tokenizes the body, selects a worker, and returns a routing decision.

### Actual Behavior

The ext_proc stream is rejected immediately. The client receives an HTTP 500 or timeout.

**Rust EPP logs:**
`2026-08-22T14:08:21.187963Z ERROR dynamo_ext_proc::server: ProtocolConfiguration mismatch — failing stream request_body_mode=4 response_body_mode=4 send_body_without_waiting=false`

### Environment

Dynamo commit: `d023c6af5465bc08f663fed366c89bb56398365c`
agentgateway chart version: v1.4.1
Rust EPP env: DYN_EPP_MODE=standalone, TLS enabled (DYN_SECURE_SERVING=true)
InferencePool: inference.networking.k8s.io/v1


### Additional Context

**Root cause**

In agentgateway main (https://github.com/agentgateway/agentgateway/blob/75b4e6ce6e0e1ac7959d5548ebe8dbeaede4f180/crates/agentgateway/src/http/ext_proc.rs#L813)
```rust
fn protocol_config(&self) -> ProtocolConfiguration {
    ProtocolConfiguration {
        request_body_mode: self.mode_state.request_body_mode.into(),
        response_body_mode: self.mode_state.response_body_mode.into(),
        ..Default::default()
    }
}
```

It seems like the `send_body_without_waiting_for_header_response` is left at its default (false). 

**Suggested fix**

Either:

- Fix agentgateway: set `send_body_without_waiting_for_header_response`: true in `protocol_config()` whenever request/response body mode is `FULL_DUPLEX_STREAMED`.

- Or relax Rust EPP validation: allow the stream to proceed when both directions are `FULL_DUPLEX_STREAMED` but the flag is false, since agentgateway's behavior is already correct.

**Temporary workaround used**

I locally patched `deploy/inference-gateway/ext-proc/src/server.rs::validate_protocol_config` to log a warning instead of returning `Status::failed_precondition` when both body modes are `FULL_DUPLEX_STREAMED`. After this patch, agentgateway and Rust EPP communicate successfully.

**Question**

Should Dynamo wait for an agentgateway upstream fix, or should the Rust EPP add a compatibility mode for gateways that stream full-duplex but omit this flag?

### ayaangazali · 2026-08-23

Not picking this up, because the issue ends with a design question that is the maintainers' to answer. But I read what the strict check is actually protecting, and it bears on which of your two options is safe, so passing it on.

`validate_protocol_config` in `deploy/inference-gateway/ext-proc/src/server.rs` documents the flag as guarding a **deadlock**, not a preference:

> That ordering, header response after body, is only legal under `BodySendMode::FULL_DUPLEX_STREAMED` with `send_body_without_waiting_for_header_response = true`. Under any other mode Envoy waits for our header response before sending body chunks while we wait for body chunks before producing the header response, which silently deadlocks until the ext_proc timeout fires.

The EPP has to defer its `RequestHeaders` response until it has the body, because the body carries the prompt it tokenizes to pick a worker, and the chosen worker is what goes into `x-gateway-destination-endpoint`. So the flag is the gateway promising it will not wait.

That is why I think the two options are not symmetric, and why your local patch is a good workaround but a risky default:

Your diagnosis of agentgateway looks right, and for agentgateway specifically the deadlock cannot happen since it streams the body regardless of the flag. But the check does not only see agentgateway. A real Envoy that reports `send_body_without_waiting_for_header_response=false` genuinely does wait, and that combination is reachable, since the flag is exactly the knob controlling it. Downgrading the failure to a warning whenever both modes are `FULL_DUPLEX_STREAMED` would hand that configuration back the silent multi-second timeout this check exists to convert into an immediate, self-explaining error.

So a blanket relaxation trades a clear failure for a hidden one in a case the check was written for. Fixing `protocol_config()` upstream, or an opt-in escape hatch that an operator sets deliberately for a known-good gateway, both keep the fast failure for the case that actually deadlocks. Which of those is right is your and the maintainers' call.

To be clear about what I did and did not check: I read the validation path and its rationale in this repository, I did not run agentgateway, so the claim that it streams the body regardless of the flag is yours and I have taken it at face value.

### thuanpham582002 · 2026-09-21

This also affects official Envoy, not only agentgateway.

With Dynamo Rust EPP based on `6744faa5284de95351994aebc4f2de6323ea7062`, we reproduced the immediate `ProtocolConfiguration mismatch` rejection behind Envoy **1.38.1** using:

```yaml
processing_mode:
  request_header_mode: SEND
  response_header_mode: SEND
  request_body_mode: FULL_DUPLEX_STREAMED
  response_body_mode: FULL_DUPLEX_STREAMED
  request_trailer_mode: SEND
  response_trailer_mode: SEND
# send_body_without_waiting_for_header_response omitted (defaults to false)
```

Envoy's definition says the boolean only applies to `STREAMED` and is ignored for other body modes:
https://github.com/envoyproxy/envoy/blob/v1.38.1/api/envoy/extensions/filters/http/ext_proc/v3/ext_proc.proto#L287-L302

The implementation explicitly sends body data while header processing is pending when the mode is `FULL_DUPLEX_STREAMED`, independently of this boolean:
https://github.com/envoyproxy/envoy/blob/v1.38.1/source/extensions/filters/http/ext_proc/ext_proc.cc#L1015-L1024

`encodeProtocolConfig` still copies the raw configured boolean, explaining the valid `4/4/false` metadata:
https://github.com/envoyproxy/envoy/blob/v1.38.1/source/extensions/filters/http/ext_proc/ext_proc.cc#L1063-L1071

Our focused patch preserves the strict checks for both full-duplex body modes and removes only the additional boolean requirement. It also updates the explanation/error text and changes regression coverage to accept both `4/4/true` and `4/4/false` while retaining incompatible-mode rejection.

Validation completed after replacing only the EPP image, with the Envoy image and the configuration above unchanged:

- 5 focused protocol tests passed, including `4/4/false` acceptance and incompatible-mode rejection.
- All 161 `dynamo-ext-proc` library tests passed (`cargo test --release --offline --locked -p dynamo-ext-proc --lib`).
- Live text completion, SSE completion, forced tool call, matching tool-result followup, and image request all returned HTTP 200 and passed response validation. The tool response contained structured `tool_calls`; SSE terminated with `[DONE]`; no raw DSML markers leaked in these probes.
- Post-change EPP logs recorded request/response modes `4/4` and `send_body_without_waiting=false`, with no protocol mismatch in the captured smoke window.

This verifies successful end-to-end operation under the unchanged false flag. It is not a packet-level capture or a long-context load benchmark.

Given this protocol contract, could #13700 accept full-duplex modes without requiring an opt-in for the ignored boolean? A gateway that advertises full-duplex but actually waits for the header response would be a separate protocol-conformance problem. We are posting here to avoid duplicating the existing issue and PR.
