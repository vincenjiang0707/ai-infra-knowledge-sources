# [Issue #13239] [BUG]: DGDR hardware auto-discovery writes the raw nvidia.com/gpu.product string into spec.hardware.gpuSku, which its own CRD enum then rejects

source: https://github.com/ai-dynamo/dynamo/issues/13239
state: open | updated: 2026-09-22T16:20:01Z
labels: bug, dynamo-deploy, backend::vllm, deployment::k8s, QA Bug, DGDR, operator

## 正文

## Describe the Bug

DGDR hardware auto-discovery can write a value into `spec.hardware.gpuSku` that its own CRD
enum rejects, so the reconcile fails and the DGDR never progresses.

`InferHardwareSystem` in `deploy/operator/internal/gpu/discovery.go` is careful here — its
doc comment states that unknown GPUs "gracefully return empty string", and it does:

```go
// Matching is based on substring checks and is tolerant of variations
// in formatting (case, spaces, dashes). If no known GPU is detected,
// an empty SKU type is returned.
```

But the caller in `enrichHardwareFromDiscovery`
(`deploy/operator/internal/controller/dynamographdeploymentrequest_controller.go`) discards
that guarantee and falls back to the raw product string:

```go
	if hw.GPUSKU == "" {
		inferred := gpu.InferHardwareSystem(gpuInfo.Model)
		switch {
		case gpuInfo.System != "":
			hw.GPUSKU = gpuInfo.System
		case inferred != "":
			hw.GPUSKU = inferred
		default:
			hw.GPUSKU = nvidiacomv1beta1.GPUSKUType(gpuInfo.Model)   // <-- raw label value
		}
		changed = true
	}
```

`gpuInfo.Model` comes from the `nvidia.com/gpu.product` node label
(`LabelGPUProduct` in the same discovery package). That string is free-form and is
**guaranteed not to be a member of the enum** whenever `InferHardwareSystem` returned empty —
because "returned empty" means precisely "this product string matched none of the known
tokens".

`HardwareSpec.GPUSKU` is validated by:

```go
	// +kubebuilder:validation:Enum=gb200_sxm;gb10;b200_sxm;h200_sxm;h100_sxm;h100_pcie;a100_sxm;a100_pcie;a30;l40s;l40;l4;v100_sxm;v100_pcie;t4;mi200;mi300
	GPUSKU GPUSKUType `json:"gpuSku,omitempty"`
```

So the subsequent `r.Update(ctx, dgdr)` in `createProfilingJob` is rejected by the API server
and the reconcile returns `failed to update DGDR with auto-discovered hardware`.

The net effect: **on any GPU model the enum does not list, DGDR auto-discovery fails with a
validation error rather than degrading gracefully** — even though the discovery helper was
written to degrade gracefully.

This code is identical on `v1.3.1` and on `main` as of 2026-08-14.

**Update (2026-08-14): the enum is not derived from AIConfigurator's system list, and the perf
data for this GPU already exists upstream.** `aiconfigurator` ships a system definition and a
full kernel database for this exact part:

- `aic-core/src/aiconfigurator_core/systems/rtx_pro_6000_server.yaml` — measured on a real
  node (`mem_capacity: 102641958912` = 97887 MiB, `sm_version: 120`, `power: 600`,
  `num_gpus_per_node: 8`, comment notes collection on 2026-07-25)
- `systems/data/rtx_pro_6000_server/` — attention, gemm, moe, mla, mla_bmm, comm,
  linear_attention, encoder_attention, kda, mhc
- `systems/support_matrix/rtx_pro_6000_server.csv` — 1013 rows of validated
  model x backend x version x mode combinations, e.g. `vllm 0.19.0 agg -> PASS (silicon)`
  and `trtllm 1.3.0rc20 disagg -> PASS (silicon)`

Comparing the CRD enum (17 values) against `aiconfigurator`'s systems directory (14 systems),
the two diverge in **both** directions:

| | values |
|---|---|
| In AIC, missing from the enum | `rtx_pro_6000_server`, `b300_sxm`, `b60`, `gb300` (plus `gb200`, which the enum spells `gb200_sxm`) |
| In the enum, no AIC system | `gb10`, `l40`, `t4`, `v100_sxm`, `v100_pcie`, `mi200`, `mi300` |
| Present in both | `a100_pcie`, `a100_sxm`, `a30`, `b200_sxm`, `h100_pcie`, `h100_sxm`, `h200_sxm`, `l4`, `l40s` |

So only 9 of the 17 accepted values correspond to a system the profiler actually has data for.
That suggests the enum should be generated from (or validated against) AIC's systems list
rather than maintained separately.

## Steps to Reproduce

1. Run on a cluster whose GPU nodes carry a `nvidia.com/gpu.product` label that
   `InferHardwareSystem` does not match. Ours is:

   ```
   nvidia.com/gpu.product: NVIDIA-RTX-PRO-6000-Blackwell-Server-Edition
   ```

2. Apply a `DynamoGraphDeploymentRequest` **without** `spec.hardware` (or with any of
   `gpuSku`/`vramMb`/`numGpusPerNode`/`totalGpus` omitted, which triggers discovery).

3. Watch the operator log / DGDR status.

## Expected Behavior

Auto-discovery either leaves `gpuSku` empty and reports a clear, actionable message naming the
unrecognised product string and the accepted values, or the enum covers the GPU. In no case
should the operator write a value it will then reject itself.

A minimal fix would be to drop the `default:` branch — leaving `hw.GPUSKU` empty and surfacing
"could not infer gpuSku from node label %q; set spec.hardware.gpuSku explicitly" — so the
failure names the actual problem.

## Actual Behavior

```
failed to update DGDR with auto-discovered hardware:
  spec.hardware.gpuSku: Unsupported value: "NVIDIA RTX PRO 6000 Blackwell Server Edition"
  supported values: gb200_sxm, gb10, b200_sxm, h200_sxm, h100_sxm, h100_pcie,
                    a100_sxm, a100_pcie, a30, l40s, l40, l4, v100_sxm, v100_pcie,
                    t4, mi200, mi300
```

The message reads as "you supplied a bad value", but we supplied nothing — the operator
discovered it, wrote it, and rejected it. That made this take longer to diagnose than it
should have.

## Environment

- Dynamo operator **1.3.1**; DGDR CRD storage version `nvidia.com/v1beta1`
  (code re-checked against `main` on 2026-08-14)
- `dynamo env` output is not applicable here: there is no local Dynamo install involved. The
  defect is in the operator's reconcile loop, reached by applying a DGDR to the cluster.
- Kubernetes **v1.35.6** (vanilla), managed by NVIDIA Run:ai 2.26.27
- GPUs: NVIDIA RTX PRO 6000 Blackwell Server Edition (SM120), 96 GiB, 8 per node
- `nvidia.com/gpu.product` = `NVIDIA-RTX-PRO-6000-Blackwell-Server-Edition`

## Additional Context

- **Workaround**: set all four `spec.hardware` fields explicitly, which skips discovery
  entirely (the `HardwareSpec` doc comment documents this: "If all four fields are set,
  discovery is skipped"). We use `gpuSku: l40s` as the nearest listed GDDR part so the
  operator accepts the DGDR.

- **The workaround has a real cost, which is why this matters beyond the error message.**
  `gpuSku` is what the profiler keys its performance data on, and the value we are forced to
  pick is a different GPU. Observed on 2026-08-14 with `gpuSku: l40s`, `searchStrategy: rapid`
  and `features.mocker`:

  ```
  perf_database.get_database: Loading database for system='l40s', backend='vllm',
                              version='0.14.0'
  task.run: Starting Pareto Analysis for
            disagg_Qwen/Qwen3-0.6B_l40s_None_vllm_0.14.0_512_256_0_200.0_10.0
  profile_sla._execute_strategy: Selected prefill: tp1 (1 GPUs), decode: tp2 (2 GPUs)
  profile_sla.run_profile: Final cleanup completed.
  ```

  Profiling **succeeds silently** against L40S data (48 GB GDDR6, Ada) for a 96 GB GDDR7
  SM120 part, and the resulting parallelism plan is not meaningful for this hardware. No
  warning is emitted that the requested hardware is not the hardware being modelled. An
  earlier run of ours recorded `profiling_results/H200_TP1P_TP1D` in the generated worker
  args; we could not re-verify that specific path on 2026-08-14, but the substance is the
  same either way — the plan comes from a substituted GPU.

- **Suggested fix is cheaper than adding support for new hardware.** The perf database,
  the system definition and the support matrix all already exist upstream for this part; only
  the CRD enum rejects the name. Syncing the enum with `aiconfigurator`'s systems directory
  would close this for `rtx_pro_6000_server` and for `b300_sxm` / `b60` / `gb300` at the same
  time.

- **A note on an earlier version of this report**: it stated that `l40s` is not in AIC's
  supported systems and that `features.mocker` fails with
  `unsupported model for Rust core estimator`. Both were wrong — `l40s` is present in AIC
  (`systems/l40s.yaml`, `support_matrix/l40s.csv`) and the profiling run above completed with
  no AIC error. Corrected here rather than left in place.

### vvagias · 2026-08-31

I reproduced the same contract failure specifically for GB300 while following the published Kubernetes path against a v1.2.1 platform.

A server-side dry-run of a DGDR with `spec.hardware.gpuSku: NVIDIA-GB300` is rejected by the installed CRD:

```text
spec.hardware.gpuSku: Unsupported value: "NVIDIA-GB300": supported values: "gb200_sxm", "b200_sxm", "h200_sxm", "h100_sxm", "h100_pcie", "a100_sxm", "a100_pcie", "a30", "l40s", "l40", "l4", "v100_sxm", "v100_pcie", "t4", "mi200", "mi300"
```

This was `kubectl apply --dry-run=server`; no resource was persisted. Omitting `spec.hardware` passes admission, but the v1.2.1 controller has the same raw-label fallback described in this issue, so discovery of the node label `NVIDIA-GB300` reaches the rejected update path during reconciliation.

I also rechecked current `main`: the Go CRD enum and generated Python DGDR type still omit `gb300`, and `InferHardwareSystem` has no GB300 normalization rule. This makes the issue relevant to both the old platform path and the current public-source path, not just the RTX PRO example.

This is useful to document because an explicit alias such as `b200_sxm` can pass admission but silently selects performance data for different hardware. A supported GB300 name/mapping or an actionable discovery error is needed before a new user can safely proceed with DGDR on GB300.

There is also a coupled v1.2.1 artifact-selection problem once discovery is bypassed. The v1.2.1 installation requirements say B300/GB300 require CUDA 13, and NGC publishes distinct `vllm-runtime:1.2.1-cuda13` and `sglang-runtime:1.2.1-cuda13` tags. The DGDR default is `dynamo-planner:1.2.1`, while `derive_backend_image()` preserves the planner tag and changes only the image name, so the generated worker image is `vllm-runtime:1.2.1` or `sglang-runtime:1.2.1` rather than the required `-cuda13` variant. NGC's planner repository lists only the bare `1.2.1` tag, so setting `spec.image` to an analogous planner CUDA suffix is not a valid workaround. The advanced `overrides.dgd` path can replace worker images, but the public minimal DGDR path does not select the required runtime variant automatically.
