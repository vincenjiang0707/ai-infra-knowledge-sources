# [PR #15143] feat(runtime): start every discovery watch with one resync snapshot

## 正文

Fixes #15066. Follow-up to #14769.

## Summary

Every `Discovery::list_and_watch` stream now starts with the state at establishment as one
`Added` event per matching instance and then exactly one `DiscoveryEvent::Resync` of the same
set, empty when nothing matches. A consumer that reopens a watch after losing one replaces its
state with that `Resync` and needs no `list()` call; an instance that left during the gap is
absent from the snapshot.

Design decision: the initial `Added` events stay, and the `Resync` follows them. Every existing
consumer either replaces its state on `Resync` with a set it already holds (no double-count, no
republish) or ignores `Resync`.

Per backend:

- **KV stores (etcd, file, memory):** `Bucket::watch` sends the existing entries as one
  `WatchEvent::Resync` instead of a `Put` burst, so the discovery layer's existing resync
  translation ends the startup burst with the snapshot. The discovery stream,
  `TypedPrefixWatcher`, and `KvCache` log the first resync at debug and a later one at warn. The
  NATS store is not a discovery backend and keeps its `Put` replay.
- **Kubernetes:** the daemon reports `Pending`/`Ready`/`Stopped`/`Failed` on a watch channel and
  sends `Ready` only after both reflectors completed their initial list and the result is in
  `list_state`. `list_and_watch` and `list` wait for `Ready` and fail when the daemon stopped or
  failed first, instead of returning an empty set the caller cannot tell from an empty cluster.
  The wait is unbounded while a reflector retries its initial list (unreachable API server, RBAC
  denial); the trait doc states this. `list_and_watch` stops waiting when the caller's
  cancellation token fires. `list()` waiting for readiness is a deliberate change to a second
  method, for consistency with the watch.
- **Mock:** one `Resync` after the `Added` burst.

Consumer audit (every `list_and_watch` caller in `lib/` and `lib/bindings/python`):

- Replace-on-`Resync`, unchanged set: `component/client.rs` (`EndpointDiscoverySource`),
  `llm/discovery/controller.rs` (revision-guarded), `llm/kv_dc_relay/discovery.rs`
  (`replace_all` reports no change), `llm/discovery/runtime_configs.rs` (no republish).
- Ignore `Resync`: `llm/discovery/{endpoint_card,kv_source_watch,watcher}.rs`,
  `llm/direct_zmq_fan_in.rs`, `llm/kv_router/indexer/recovery/{direct_zmq,state_agent}.rs`,
  `llm/kv_router/publisher/state_agent_host.rs`, `runtime/discovery/utils.rs`,
  `runtime/pipeline/network/egress/push_router.rs`,
  `runtime/transports/event_plane/dynamic_subscriber.rs`, `bindings/python/rust/llm/fpm.rs`.
- Re-list on every event: `llm/kv_router/publisher/attachment_owner.rs` and
  `llm/kv_dc_relay/membership_watch.rs` do one extra `list()` per new watch at startup. Benign.

Out of scope, for follow-up issues: `push_router.rs` watchers reconnect on stream end but keep
their dispatch and indexer state and ignore `Resync`, so the new snapshot does not yet remove an
instance that left during their gap; a Kubernetes watch opened before a post-`Ready` daemon
failure keeps serving and never errors (pre-existing, now observable through `DaemonState`).
