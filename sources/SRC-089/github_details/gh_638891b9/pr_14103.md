## 正文

## Summary

Adds always-on cache-reuse counters for each KV-routing attempt. The router records the raw cached prefix on the best eligible worker and on the selected worker/rank. The worker reports its cache-hit counts when the request completes. Routing decisions and tier weights are unchanged; reported token values are raw and uncapped.

The counters use the existing `RouterRequestMetrics` and request-guard lifecycle, with one once-only flag for completion, errors, cancellation, and dropped streams. This incorporates Neelay's reference cleanup from #15173, retaining counters rather than introducing histograms.

## Metrics and compatibility

All names below have the `dynamo_component_router_` prefix and carry `phase` (`aggregated`, `prefill`, or `decode`) and `model` labels.

| Measurement | Metric |
| --- | --- |
| Received input tokens (F0) | `input_sequence_tokens_sum` (existing histogram sum) |
| Best eligible cached prefix (F2) | `kv_best_eligible_cached_prefix_tokens_total` |
| Selected worker/rank cached prefix (F3) | `kv_selected_cached_prefix_tokens_total` |
| Worker lookup hits, when available (F4) | `kv_worker_lookup_tokens_total` |
| Backend-reported cache-hit tokens (F5) | `kv_worker_reused_tokens_total` |
| Worker reporting coverage | `kv_worker_outcomes_total{result}` |

- F0's existing histogram now excludes query-only selections and carries matching phase/model labels. Queries needing process-wide totals must sum across those labels.
- F2/F3 are recorded at selection. Worker values require successful completion and a valid prompt-matched report. The guard retains the attempt's original phase.
- Missing external lookup data does not fall back to successful hits or zero. F5 is still recorded, F4 is not incremented, and the outcome is `lookup_unavailable`. A valid lookup report is `complete`; missing, invalid, overflowing, or failed reports are `incomplete`.
- Both the vLLM worker and router now use `engine_data.kv_cache_hit`. No compatibility reader for the old key is included; upgrade frontends and workers together.
- F2–F5 need no enable flag. F1 history tracking remains separate and opt-in in #14889.

## Interpretation and limitations

- Compare the same model and phase. Prefill and decode are separate routing attempts; migration adds attempts that may include already-generated tokens. Selection and completion happen at different times.
- Multimodal routing tokens can differ from the input token IDs counted by F0.
- Existing `router_kv_hit_rate` is tier-weighted; these counters are not.
- Worker reporting is currently vLLM-only. SGLang and TensorRT-LLM KV attempts record router estimates and incomplete worker outcomes. Extending worker reporting to non-KV routing is deferred.
- Stock vLLM does not expose a separate external lookup count. Its cached-token statistics may also retain initial matches after transfer failures. F5 is a backend report, not independently verified successful reuse; backend failure-accounting work is separate.
- Check outcome coverage before interpreting F4: once a lookup series exists, later unavailable reports leave it flat rather than remove it.
- The frontend cached-token metric and its estimate fallback are unchanged.

### tmonty12 · 2026-09-16

Several of these stages overlap with metrics already on `main` — F5 is arithmetically the same number as `dynamo_frontend_cached_tokens`, and F3/F0 is `router_kv_hit_rate` up to block rounding. I'm concerned that shipping both leaves users with two series answering the same question and no way to tell which is authoritative.

| Stage | Definition | Existing metric | Verdict |
|---|---|---|---|
| **F0** | Prompt tokens sent into worker selection | `dynamo_frontend_input_sequence_tokens_sum` | Same value, different population [^1] |
| **F0** | (same) | `dynamo_component_router_input_sequence_tokens_sum` | Same value, same population [^2] |
| **F1** | Prompt-prefix tokens the router has seen before | — | **New** [^3] |
| **F2** | Weighted cached tokens on the best-cached eligible worker | `router_overlap_blocks_lost` | Same quantity, published only as a difference [^4] |
| **F3** | Weighted cached tokens on the selected worker, as the router estimated them | `router_kv_hit_rate` | Same quantity, different granularity [^5] |
| **F3** | (same) | `dynamo_frontend_cached_tokens`, no-usage path | **Identical** [^6] |
| **F4** | Tokens the worker's lookup located: GPU hits plus external attempts | `router_shared_cache_beyond_blocks` | Different cache; no equivalent exists [^7] |
| **F5** | Tokens the engine actually skipped recomputing | `dynamo_frontend_cached_tokens`, usage path | **Identical** [^8] |

Two things worth calling out from this:

- `dynamo_frontend_cached_tokens` is effectively two metrics under one name — it reports F5 when the backend sends usage and F3 when it doesn't, a worker measurement and a router prediction in the same unlabeled series. That is a real problem this PR identifies, and splitting that series by source would deliver much of what the funnel is for.
- The stages don't share a measurement basis. F2 and F3 are tier-weighted routing scores expressed in token units (device 1.0, host-pinned 0.75, disk/external 0.25); F4 and F5 are exact unweighted worker counts. An F5/F3 ratio will move with `host_cache_hit_weight` rather than with any real effect, while the dashboard labels ("Tokens Resident on ...") read as residency counts for all four.

[^1]: The frontend histogram counts one client request that produced at least one output token; F0 counts one routing attempt — 2+ per request under disaggregation, +1 per migration. The histogram also retains a distribution; F0 is a total only, and a histogram's `_sum` is already a cumulative token counter.

[^2]: Same call site (`track_selection_with_cleanup`), same value for text-only requests. Diverges only on multimodal, where the histogram reads `request.token_ids` and F0 reads the routing sequence — and those requests are then dropped as `incomplete` by the prompt-length equality check.

[^3]: Nothing existing measures prompt novelty independent of whether a worker still holds the KV.

[^4]: The histogram's `highest_overlap_blocks` term *is* F2 in effective blocks, but it is only published as `highest - selected`, only when that difference is positive, only for `worker_type == prefill`, and only for admitted requests.

[^5]: `kv_hit_rate = effective_overlap_blocks[sel] / ceil(isl/block_size)`; `F3/F0 = round(effective_overlap_blocks[sel] * block_size) / isl`. Identical up to block rounding on both numerator and denominator.

[^6]: With no backend usage to latch, the frontend falls back on request drop to `tracker.cached_tokens()`, set from `selection.cached_tokens` at `kv.rs:422` — that is F3. Latched once per request via `OnceLock`, so under disaggregation it holds the prefill leg's value.

[^7]: `beyond_blocks` is the router's view of the cluster-wide shared store past the selected worker's device prefix; F4 is the worker's own hierarchy as the engine saw it. On stock vLLM the missing `num_external_lookup_tokens` field forces `cpu_lookup_tokens = external_hits`, collapsing F4 onto F5 and making the lookup-miss gap unobservable.

[^8]: The frontend metric reads vLLM `num_cached_tokens` directly (`handlers.py:3180`); F5 computes `local + external`, and this PR's own fallback (`local = aggregate - external`) asserts those are the same number.

**Suggestion, not a blocker: consider histograms for the four stage series.** Every other per-attempt router metric (`input_sequence_tokens`, `output_sequence_tokens`, `kv_hit_rate`, TTFT, ITL) is a histogram on `RouterRequestMetrics`. A histogram's `_sum` carries exactly the totals the counters carry today (checked: the same 96/64/80/72 come out), and `_count` plus the buckets add the per-attempt distribution — for example "what share of attempts had no resident prefix at all", which totals alone cannot answer.

Counters on the same struct are an equally acceptable outcome — the structural suggestion further down does not depend on the metric type. @jh-nv — your call on type and series count for the observability catalog.

### nnshah1 · 2026-09-22

**Two labels these series need: `phase` and `model`.** `RouterRequestMetrics::from_component` creates one shared instance per process (a `static OnceLock`), and `router_id` is the DRT `instance_id` of whichever component initialised first. Routing hosts are created per model and per pool, but they all share that one instance — so a frontend hosting the prefill and decode routers, or several models, records all of their attempts into the same series. The catalog's "compare within a pool" is therefore only true across processes today.

- `phase = aggregated | prefill | decode`, from `tracker.phase()` — the same label and values the frontend already exports on `stage_duration_seconds{stage,phase}`. Not `worker_type`: an aggregated router reports `"decode"` (`routing_load.rs:36`), which would mislabel a prefill-reuse metric in the most common deployment, and widening that vocabulary changes what existing per-worker gauges mean.
- `model`, from `PreprocessedRequest.model` — a closed set (the served models), with router-side precedent in the queue-pending and selection-policy gauges.

Number of series: × phases present (1 aggregated, 2 disaggregated) × served models — the same shape as the existing `overlap_blocks_lost{worker_type}`. @jh-nv — flagging for a series-count check.
