## Design boundary

vLLM remains authoritative for scheduling, block tables, block hashes, prefix caching, and eviction. GMS owns daemon-lifetime CUDA VMM allocations plus generation-fenced recovery facts. GMS does not mirror vLLM's prefix tree.

This vLLM checkpoint demonstrates the integration and controlled failover loop. The cumulative arbitrary-crash safety model—including quarantine of ambiguous predecessor accesses and classify-before-admission—continues through the hardening tracker #15035. Do not infer the final hardening guarantees from this checkpoint alone.

Those results are retained as historical evidence, not as fresh qualification of the rewritten commit graph.

### Minimal Changes

**Persist underlying KV Cache bytes**: GMS owns the KV pool keyed by stable names; on failover the shadow reattaches the same physical pages at its own VAs. No reload, no realloc.

**Persist the prefix index:** As the primary serves, mirror its prefix-index changes into a small shared-memory log, published only after each step's KV writes are durable (so a crash never records bytes that weren't written). On takeover the shadow replays the log into its own prefix index.

**Reattach safely**: On failure, kill the whole primary process tree and verify it's gone (proc/NVML + GMS reports no other holder on the key) before the shadow touches the pool, so there's never a second live writer. A file lock does the leader election.

**Compatibility: Ensure identical KV cache config**: The shadow adopts records only if model, geometry, layout, and hash seed match; otherwise it cold-starts (correct, just slower). In particular the shadow inherits the primary's num_blocks rather than re-profiling.

### Re-use of existing PRs

Bytes: reuse as-is (#12056, #8, #11).

Index: same as your content directory (#10), realized as a shm log off vLLM's native block events.

Safety: reuse your teardown (#12032); drop the lease ring (#12057) from the write path.

Compatibility: reuse your check, plus a tag-plan and geometry fingerprint.

Election / validation: already on main, plus your exact-output gate (#13).

### Explicit Simplifications

Extinction, not arbitration: kill + a verified fence make the old writer provably dead, so no lease-based per-block write coordination is needed.

Index presence = finality: a block is reusable exactly when it's in the post-barrier index, so there's no separate seal/generation state for reuse.

Native events, not a service: the survivable record is just vLLM's own block events drained to shm, so no separate content-directory or publish path.

Benign crash or cold-start: reuse is trusted only for a clean crash; corruption or any layout/hash mismatch fails closed to cold-start, so no integrity machinery beyond the barrier + fingerprint.

# KV cache failover MVP: retained invariants and deferred machinery

Status: discussion draft  
Scope: Dynamo Snapshot, GMS V1, vLLM, single node, multi-TP

## The simplification in one sentence

The current [#12053 PR train](https://github.com/ai-dynamo/dynamo/issues/12053) supports fine-grained KV ownership and recovery between potentially overlapping participants. Our first Snapshot-based version does not need that generality: it has one active engine, one sleeping standby, and one whole KV pool that changes owners only after the old engine is fenced.

This lets us keep a small set of strong safety rules and remove most of the per-block coordination machinery.

The KV bytes are not copied during failover. GMS keeps the same GPU pages alive. The only host state we preserve is the prefix index that tells vLLM which completed prefix is stored in each physical block.

## The MVP model

```text
primary owns the whole pool
           |
           | crash + external fencing
           v
standby becomes the new whole-pool owner
           |
           | attach every TP rank
           | verify identical layout
           v
bulk restore the prefix index
           |
           +---- valid recovery ----> serve warm
           |
           `---- anything uncertain -> clear index and serve cold
```

There is no period in which the primary and standby are both allowed to allocate, overwrite, or publish KV blocks.

That assumption is the main reason the reduced design is safe. If we later allow active/active engines, a shadow that executes requests, live migration, or multiple competing adopters, we will need to reconsider the machinery removed below.

## What we retain

### 1. Persistent GPU pages

**Purpose:** The actual KV tensors must outlive the engine process that created them.

**MVP:** GMS V1 owns the allocation rather than the vLLM process. When vLLM dies, GMS preserves the pages and allows the replacement to attach them.

This is the physical foundation of warm recovery. Without it, there are no KV bytes to recover.

### 2. Whole-pool writer ownership

**Purpose:** Prevent two engines from modifying the same physical KV memory or its metadata at the same time.

**MVP:** Ownership is granted for the entire pool, not block by block. The active engine owns:

- The read/write GMS attachment to all KV pages.
- The right to modify the associated prefix index.

Dynamo Snapshot provides the process-level election and fencing. GMS enforces one read/write attachment. The prefix-index store enforces one metadata writer.

This is the key trade: a stronger, simpler whole-pool rule replaces a large per-block ownership protocol.

### 3. One writer epoch

**Purpose:** Reject late metadata operations from the old engine after the standby has taken over.

**MVP:** Promotion atomically advances one epoch for the entire prefix index. Every publish, invalidate, or clear operation carries that epoch. An operation from an older epoch is rejected.

The epoch protects host metadata. It does not replace the requirement to fence the old engine from writing GPU memory.

### 4. Layout identity

**Purpose:** A prefix entry is useful only if block ID `N` still refers to the same physical location and tensor layout.

**MVP:** The saved index is bound to the GMS allocation identity and the exact vLLM KV layout. At minimum, this includes all TP ranks, device identity, pool identity, model/KV shape, block count, block size, dtype, KV groups, hash format, and relevant vLLM integration version.

The replacement must prove an exact match before it trusts any saved entry.

### 5. Invalidate before overwrite

**Purpose:** Prevent a prefix hash from pointing at a block while that block is being reused for different KV data.

**MVP:** When vLLM chooses blocks for reuse, the BlockPool integration synchronously invalidates those block IDs before the scheduler may overwrite their GPU pages.

If invalidation fails, the engine must stop before reuse. Continuing would make a stale cache hit possible after failover.

### 6. Publish after completion

**Purpose:** Prevent the prefix index from advertising KV bytes that are only partially written.

**MVP:** A block is published only after the GPU work that produced it has completed. The record payload is written first; its valid marker is written last.

A failed or interrupted publish becomes a cache miss. It must never become a valid partial entry.

Together, invalidate-before-overwrite and publish-after-completion give us the core crash guarantee:

| Crash point | Result after recovery |
| --- | --- |
| Before invalidation | Old entry and old bytes are still valid |
| After invalidation, before or during overwrite | Entry is absent; safe miss |
| After completion, before publication | Entry is absent; safe miss |
| After publication | New entry points at complete new bytes |

### 7. Bulk BlockPool restore

**Purpose:** Rebuild vLLM's in-process prefix lookup after a replacement EngineCore starts.

**MVP:** After all validation succeeds, read the prefix index once and insert all valid entries through vLLM's native BlockPool insertion path.

This is intentionally eager and simple. We do not intercept individual cache misses and hydrate entries on demand.

### 8. Free-queue reordering

**Purpose:** Restored cache entries must participate correctly in vLLM's eviction order.

**MVP:** After insertion, place recovered blocks at the protected end of the native free/eviction queue. Otherwise, vLLM may immediately select and overwrite the blocks we just restored.

This is part of restore correctness, not only a performance optimization.

### 9. All-rank adoption gate

**Purpose:** A logical KV block spans every tensor-parallel rank. Reusing it on only some ranks is invalid.

**MVP:** Every TP worker must attach its expected GMS allocation and report a matching layout. The EngineCore restores the prefix index only after all ranks succeed.

There is no partial warm recovery. One missing or mismatched rank makes the entire engine start cold.

### 10. Fail-cold behavior

**Purpose:** Never turn uncertain state into a cache hit.

**MVP:** Missing metadata, corrupt records, layout mismatch, a failed rank attachment, or failed restore causes the new owner to clear the prefix index and use the pool as an empty cache.

This favors lost cache value over incorrect model output.

### 11. Version and hook verification

**Purpose:** The vLLM integration depends on private construction, allocation, completion, and restore seams. A vLLM change could silently break our ordering guarantees.

**MVP:** Pin or explicitly support known vLLM versions and verify the expected hooks before serving. If the feature is enabled and the integration seam is missing, startup fails visibly.

This differs from runtime fail-cold behavior. An incompatible integration cannot safely run because we may no longer intercept every overwrite or know when GPU work is complete.

## What we remove from the first version

### Fine-grained ownership machinery

We initially remove:

- Per-block leases.
- Per-block generations.
- Claim tokens.
- READY/ACTIVE adoption states.
- Successor-generation staging.
- Lease allocation backpressure.

These mechanisms primarily support blocks changing hands independently while multiple participants may still be alive, performing lookups, or competing for capacity.

Our MVP has no such competition. One fenced promotion transfers the whole pool to one replacement. One global epoch fences prefix metadata, while invalidate-before-overwrite protects block reuse during normal operation.

The simplified ownership model is:

```text
OLD OWNER(epoch 7) --fenced--> NEW OWNER(epoch 8)

All blocks follow the owner of the pool.
There is no independent per-block owner or adoption state.
```

The non-negotiable condition is that the old engine cannot continue GPU writes after promotion. If that cannot be guaranteed, removing per-block fencing is unsafe.

### Distributed and incremental metadata recovery

We initially remove:

- Async directory replication.
- Lazy/on-demand hydration.

The prototype handles an engine-process crash on the same node. A local mmap-backed prefix index can survive that process failure. Node loss and remote recovery are out of scope, so there is no second directory replica.

The replacement reads and restores the whole index once. That is easier to reason about and test than performing claims and hydration during live cache lookups. We can revisit lazy restore only if bulk restore becomes a measured startup problem.

### Concurrent-capacity management

We initially remove:

- Capacity/headroom management for a shadow.
- Lease allocation backpressure.

The standby does not execute inference while the primary owns the pool. It therefore does not need reserved blocks or a policy for competing allocations. Once promoted, it uses normal vLLM allocation and eviction policy over the same pool.

### Broader product modes

We initially remove or defer:

- Host and storage tiers.
- Shadow comparison mode.
- Generic inference-engine support.

The first deliverable recovers only KV that remains in local GPU memory, and it integrates only with vLLM. The standby sleeps instead of running requests for output comparison.

These are useful later directions, but none is needed to prove the central mechanism: surviving HBM plus a safely restored vLLM prefix index.

## Resulting safety contract

The reduced design is safe only if all five statements remain true:

1. Dynamo fences the old engine before promotion completes.
2. GMS permits only the current owner to attach the KV allocation read/write.
3. Every vLLM block overwrite passes through synchronous invalidation.
4. A prefix entry becomes valid only after the corresponding GPU write completes.
5. Warm restore is all-or-nothing across TP ranks and exact layout identity.

Everything else can fail as a cache miss. These five conditions cannot.

## Effect on the existing PR train

This simplification changes the train in four main ways:

1. **Keep the persistent-allocation work.** Preserve the GMS-owned GPU allocation, reattachment path, and stable allocation identity, expressed through GMS V1.
2. **Remove the block lease ring.** Whole-pool election, exclusive attachment, and one metadata epoch replace per-block ownership.
3. **Replace the GMS content directory with a small external prefix index.** Keep layout binding, writer fencing, publish, invalidate, read, and clear. Do not put vLLM prefix metadata or host-state management in GMS.
4. **Reduce the vLLM adoption path.** Keep completion-aware publication, overwrite invalidation, bulk BlockPool restore, free-queue ordering, and all-rank validation. Remove claims, staged state transitions, lazy hydration, and lease pressure handling.

The end-to-end test should target the actual first deliverable: single-node multi-TP Snapshot failover where the first successful standby response reports a recovered prefix-cache hit and produces byte-identical output.

## Explicit non-goals

- Active/active KV writers.
- A shadow that performs inference before promotion.
- Multiple standby candidates racing to adopt individual blocks.
- Cross-node or post-reboot KV recovery.
- Recovery after GPU reset or allocation loss.
- Live KV migration.
- CPU or storage-backed KV recovery.
- Other inference engines.

These boundaries should appear in the issue and user documentation so the simple implementation is not mistaken for a general KV mobility system.

## Intended sequencing for KV recovery

We intend the new design work to proceed in two layers:

```text
#14888 — foundation
    minimal KVRecoveryManager protocol
    shared vLLM adapter and BlockPool integration
    whole-pool recovery backend
    Snapshot + GMS end-to-end proof
            |
            v
#14828 — follow-on
    block-lease recovery backend
    reuse the same manager protocol and vLLM adapter
    expand the protocol only where lease semantics require it
```

#14888 is the first deliverable because Snapshot already gives us a simpler ownership model: one active engine, one sleeping standby, and a whole pool transferred only after the previous engine is fenced.

#14828 should build on that foundation. `BlockLeaseRecovery` becomes another implementation behind `KVRecoveryManager`, rather than introducing a separate recovery stack above it. Existing lease-table and adoption work remains useful input for that backend.

The shared engine-facing flow remains:

```text
recover before serving
invalidate before overwrite
publish after GPU completion
```

The first acceptance target remains a single-node, multi-TP failover where the replacement remaps the same GMS allocations, restores the prefix index, records a real cache hit on its first successful request, and produces identical output.
