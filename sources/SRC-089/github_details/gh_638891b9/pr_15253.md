# [PR #15253] perf(frontend): auto-size SGLang preprocess workers

## 正文

## Overview:

With the SGLang chat processor, the current default of `DYN_PREPROCESS_WORKERS=0` runs request preprocessing on the frontend's main Python event loop. An earlier deployment showed substantially lower frontend ITL p99 after enabling two preprocessing workers, with no drop in request or output-token rate.

This PR selects a bounded worker count automatically when the setting is omitted. The automatic default applies only to SGLang; explicit values, including `0`, remain unchanged. Other chat processors continue to default to `0`.

## Details:

### Default behavior

For SGLang, an unset worker count resolves to `min(2, max(0, available CPUs - 1))`. CPU availability uses process affinity and the cgroup CPU quota, taking the tighter detected limit.

| Available CPUs | Automatic SGLang workers |
|---:|---:|
| 1 | 0 |
| 2 | 1 |
| 3 or more | 2 |

The two-worker cap applies only to the automatic value. Users can still set a different count explicitly through `--dyn-preprocess-workers` or `DYN_PREPROCESS_WORKERS`; setting `0` keeps preprocessing on the main event loop. Dynamo and vLLM processor defaults remain `0`. Negative counts are rejected.

Each model creates its own preprocessing worker pool. The cap limits the additional process and tokenizer-memory cost per model. CLI help and the frontend configuration reference have been updated accordingly.

### Observed frontend and SGLang ITL

The frontend comparison uses two approximately five-minute windows before and after setting `DYN_PREPROCESS_WORKERS=2`. Each frontend ITL window contains approximately 570,000–590,000 samples.

| Metric | Before: `0` workers | After: explicit `2` workers |
|---|---:|---:|
| Frontend ITL p99 | 29.21 ms | Approximately 22 ms |
| `routed_rust_received` ITL p99 | 22.18 ms | 21.98 ms |
| `routed_received` ITL p99 | Approximately 29 ms | Approximately 22 ms |
| Output rate | Approximately 1,931 tokens/s | Approximately 2,012 tokens/s |
| Request rate | Approximately 4.56 requests/s | Approximately 6.18 requests/s |
| SGLang decode ITL p99, nearby dashboard observations* | Approximately 20.6 ms | Approximately 20 ms |

*The SGLang values came from nearby dashboard observations, not queries preserved for the exact same two five-minute windows. They indicate that SGLang decode ITL remained around 20 ms, but should not be presented as a paired measurement.

Frontend ITL p99 fell by approximately 7.2 ms (24.7%) after enabling two preprocessing workers, despite higher request and output-token rates. The Rust receive checkpoint stayed near 22 ms, while the Python receive checkpoint fell from approximately 29 ms to 22 ms. The frontend's observed token interval therefore moved closer to the approximately 20 ms SGLang decode ITL. This supports the hypothesis that synchronous preprocessing on the main Python event loop contributes to frontend ITL tail latency, and that moving it to worker processes can reduce **frontend ITL p99**.
