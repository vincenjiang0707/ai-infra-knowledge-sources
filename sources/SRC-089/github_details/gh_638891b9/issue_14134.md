# [Issue #14134] fix(llm): request-payload audit record loses response and misreports payload_complete on mid-stream/admission error

source: https://github.com/ai-dynamo/dynamo/issues/14134
state: closed | updated: 2026-09-18T20:16:09Z
labels: bug, language::rust, dynamo-llm, observability

## 正文

## Summary

When a streaming chat-completion request ends in an error — a mid-stream backend failure, a guided-decoding/grammar rejection, a client cancel, or an immediate admission-time rejection (e.g. a worker-capacity 503) — the request-payload audit record written for compliance/logging purposes omits the `response` field entirely, **but still reports `payload_complete: true` and `payload_drop_reason: null`**, as if nothing were missing.

## Why this is a problem

`RequestPayloadHandle::emit()` hardcodes both fields regardless of whether a response was actually produced:

https://github.com/ai-dynamo/dynamo/blob/ce48476ff9b95a6de7dbe64c952e1b2049e1cc72/lib/llm/src/request_trace/payload.rs#L76-L94

```rust
/// Publish one request trace payload record. Consumes the handle to enforce
/// exactly one payload record per request. `response` is `None` on client
/// cancel / gateway timeout / aggregation failure; the record still carries
/// the request so those cases remain inspectable.
pub fn emit(self, response: Option<Arc<NvCreateChatCompletionResponse>>) {
    super::record::emit_request_payload(
        super::RequestTracePayload {
            request_id: self.request_id,
            endpoint: "openai.chat_completion".to_string(),
            model: self.model,
            request: Some(self.request),
            response,
            http_request_headers: self.http_request_headers,
            payload_complete: true,
            payload_drop_reason: None,
        },
        unix_time_ms(self.event_time),
    );
}
```

The doc comment already acknowledges `response` can legitimately be `None` — but `payload_complete`/`payload_drop_reason` were never wired to reflect that.

`response` gets `None` whenever `DeltaAggregator::apply` fails to aggregate the collected stream chunks:

https://github.com/ai-dynamo/dynamo/blob/ce48476ff9b95a6de7dbe64c952e1b2049e1cc72/lib/llm/src/request_trace/payload_stream.rs#L59-L114

`DeltaAggregator::apply` uses `try_fold` over `Annotated::into_data()`, which returns `Err` for any chunk flagged as an error event:

https://github.com/ai-dynamo/dynamo/blob/ce48476ff9b95a6de7dbe64c952e1b2049e1cc72/lib/llm/src/protocols/openai/chat_completions/aggregator.rs#L331-L337

https://github.com/ai-dynamo/dynamo/blob/ce48476ff9b95a6de7dbe64c952e1b2049e1cc72/lib/runtime/src/protocols/annotated.rs#L99-L104

`try_fold` short-circuits on the first `Err`, discarding all previously-accumulated content — proven intentional-but-narrow by the aggregator's own test:

https://github.com/ai-dynamo/dynamo/blob/ce48476ff9b95a6de7dbe64c952e1b2049e1cc72/lib/llm/src/protocols/openai/chat_completions/aggregator.rs#L2609-L2644 (`preserves_typed_error_after_partial_output` — feeds a partial-content chunk followed by an error chunk and asserts the whole call returns `Err`, losing the partial text)

`RequestPayloadHandle` is created from the pristine inbound request the moment it arrives at the frontend, before dispatch to any worker — so this isn't limited to mid-generation failures; an immediate admission-time rejection (e.g. a worker returning 503 before any token is generated) goes through the identical path and produces the identical misleadingly-"complete" record.

`response` and `payload_drop_reason` are both `skip_serializing_if = "Option::is_none"`, while `payload_complete` is not optional:

https://github.com/ai-dynamo/dynamo/blob/ce48476ff9b95a6de7dbe64c952e1b2049e1cc72/lib/llm/src/request_trace/types.rs#L57-L72

So the emitted JSONL/NATS/OTEL record for a failed request simply omits the `response` key while asserting `"payload_complete": true` — indistinguishable from a genuinely complete record to any downstream consumer that checks the flag rather than key presence. This directly undermines the audit/compliance use case the payload-capture feature exists for: a request whose response the client actually received over SSE can end up with **no recorded response at all**, silently, with no truncation or drop-reason marker.

This was found while investigating NVBugs 6705092 (sporadic multi-hour gaps in Kratos-ingested request/response payload logs for a production NVCF-hosted Dynamo deployment). No customer/deployment detail from that investigation is included here.

## Proposed fix

- Set `payload_complete: false` and populate `payload_drop_reason` (e.g. `"aggregation_failed"`, `"client_cancelled"`, or the underlying error message) in `RequestPayloadHandle::emit` whenever `response` is `None`, instead of hardcoding `true`/`None`.
- Consider giving `DeltaAggregator::apply` (or a payload-capture-specific variant) a mode that returns whatever partial content was accumulated before the error, alongside the error, rather than discarding it via `try_fold`'s short-circuit — so a request that streamed real content before failing doesn't lose that content from the audit trail.
- Add a test in `payload_stream.rs`/`request_trace/` that feeds a partial-content chunk followed by an error chunk (mirroring `preserves_typed_error_after_partial_output`) and asserts the emitted `RequestTracePayload` has `payload_complete: false` with a populated `payload_drop_reason` — there's currently no coverage of this path in that module.
- Separately worth checking: audit-payload capture appears wired only for the chat-completions endpoint (`create_handle`/`emit` call sites); the legacy `/v1/completions` path may have no equivalent capture at all, which would be a related but distinct gap.
