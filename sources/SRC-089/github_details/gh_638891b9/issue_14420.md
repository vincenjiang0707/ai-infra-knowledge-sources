# [Issue #14420] DEP: North Star: Make DGD workload materialization and logical wiring orthogonal

source: https://github.com/ai-dynamo/dynamo/issues/14420
state: open | updated: 2026-09-23T10:57:29Z
labels: enhancement, dynamo-deploy, deployment::k8s, dep:draft, operator

## 正文

## Summary

Define two orthogonal composition axes as the architectural north star for `DynamoGraphDeployment` reconciliation:

1. **Workload materialization** decides which controller and Kubernetes resource realize each component, for example a `DynamoComponentDeployment`, direct Grove lowering, a `DisaggregatedSet`, a future Elastic EP `EnginePool`, or an `LPXGraphDeployment`.
2. **Logical wiring** decides how components and their internal roles communicate, for example request routing, KV exchange, speculative decoding, or leader/worker rendezvous for tensor and expert parallelism.

One selected graph-level workload program continues to own the complete DGD reconciliation state machine. Inside that program, focused reconcilers may claim disjoint component subsets and materialize them through different workload resources. Wiring is compiled from semantic component identities, capabilities, roles, and stable endpoint declarations rather than from the concrete resource kind that happened to deploy a component.

This separation allows either axis to evolve independently: a component can move from direct Grove lowering to an independently reconciled workload resource without redesigning its communication contract, and a new wiring pattern can connect components without teaching it whether they are backed by a DCD, EnginePool, LPXGraphDeployment, or another provider object.

![DGD north star: workload materialization and logical wiring as orthogonal axes](https://github.com/user-attachments/assets/3b1d2cf2-3d95-4d0a-ab68-8b128fea23bc)

## Motivation

Dynamo already has heterogeneous workload materialization at several levels:

- A multinode worker component lowers to distinct Leader and Worker Pods.
- The component pathway creates one `DynamoComponentDeployment` per DGD component, and each DCD may lower to a `Deployment` or `LeaderWorkerSet`.
- The Grove pathway lowers one DGD into PodCliqueSet resources, including PodCliqueScalingGroups for compound components.
- The DisaggregatedSet pathway selects several eligible worker components as roles of one `DisaggregatedSet` while lowering the remaining components to DCDs.

These shapes demonstrate that one DGD program may already own several child kinds. Future integrations increase that pressure: Elastic EP may justify an `EnginePool` lifecycle boundary, while a compiled multi-role engine may justify an `LPXGraphDeployment`. [nvidia-lpu/lpu-dynamo#414](https://github.com/nvidia-lpu/lpu-dynamo/pull/414) explores the latter persisted boundary and currently aggregates the selected LPX components into one private child. This DEP does not standardize that cardinality: a materializer must explicitly claim its component set, and the program must support multiple child instances when the semantic and lifecycle boundaries require them. These objects can be correct retry, ownership, compilation, rollout, or observability boundaries without becoming new graph programs.

First, a graph program may need more than one kind of persisted child resource. A specialized controller can own one component's internal lifecycle while ordinary components continue through the existing DCD or Grove lowering. A single DGD may contain multiple such specialized components. Creating a new graph program for every specialized component type is not sufficient: mixed graphs still need one owner for finalization, ordering, restart, rollout, stable resources, readiness aggregation, and DGD status.

The physical decomposition must not determine logical communication. A prefill and decode pair still needs the same KV-transfer intent whether one side is a DCD, a direct Grove contribution, or a specialized child CR. A multinode leader and its workers still need rendezvous and rank identity whether they become a LeaderWorkerSet, Grove PodCliques, or an EnginePool. The implementation may differ in how a stable endpoint becomes a Service name, headless DNS name, Pod ordinal, or runtime environment variable, but those addressing adapters must not redefine the semantic edge.

Conversely, communication must not determine materialization. A speculative-decoding drafter and verifier may both use one materializer, different materializers, or two instances of the same specialized child type. That should not require a new graph-level program for each combination.

Issue #12035 established composition-first reconciliation programs: one complete program owns control flow and reuses smaller building blocks with genuinely shared invariants. PR #12625 demonstrates that one such program can own heterogeneous child kinds without invoking another complete program. DEP #14417 defines inward component roles for compound components. This DEP defines the larger DGD structure in which materializers, role-aware renderers, and logical wiring are composed.

## Goals

- Keep exactly one graph-level workload program selected for a DGD.
- Allow a program to compose concrete reconcilers for disjoint component subsets.
- Establish workload materialization and logical wiring as independent DGD architecture axes.
- Support zero, one, or multiple specialized child deployments of each kind in one DGD.
- Allow future materialization boundaries such as `EnginePool` and `LPXGraphDeployment` without creating a graph program per component kind.
- Compile inter-component and intra-component communication from semantic identities and endpoint contracts rather than concrete workload kinds.
- Make the unavoidable address-formation adapter explicit and narrow.
- Keep the selected program as the sole writer of aggregate DGD workload status.
- Preserve the component as the inference-aware lifecycle and scaling unit, as defined further by DEP #14417.
- Reuse normalization, PodTemplate rendering, stable-resource reconciliation, and status helpers where their invariants are shared.
- Keep provider-specific object models, naming, watches, readiness, rollout, and cleanup semantics in focused reconcilers.
- Make duplicate, missing, or stale component ownership detectable and testable.
- Permit a future joint Grove PodCliqueSet to be assembled from independently reconciled component contributions without making every child controller understand the whole graph.

## Non-goals

- A universal provider callback framework or common provider state machine.
- Calling one complete workload program from another workload program.
- Redefining the component-role API proposed by DEP #14417.
- Treating component roles as arbitrary user-defined graph topology.
- Exposing Grove PodClique, PodCliqueScalingGroup, or object-naming concepts in semantic DGD APIs.
- Replacing `DynamoComponentDeployment`, Grove, LeaderWorkerSet, or DisaggregatedSet.
- Selecting server-side apply or a Grove render collector as the final joint-PCS assembly mechanism in the initial refactor.
- Promising cross-child atomic rollout or colocation merely because contributions can be assembled into one object.
- Changing the durable workload-provider selection mechanism.
- Migrating existing DGDs between workload providers.

## Proposal

### 1. DGD north star: two orthogonal axes

The DGD architecture treats physical materialization and logical communication as independent dimensions:

| Workload materializer | Standalone request | KV exchange | Speculative decoding | TP/EP rendezvous |
| --- | ---: | ---: | ---: | ---: |
| DCD / Deployment / LWS | possible | possible | possible | possible |
| Direct Grove lowering | possible | possible | possible | possible |
| DisaggregatedSet | possible | possible | possible | possible |
| EnginePool | future | future | future | primary use case |
| LPXGraphDeployment | future | future | primary use case | primary use case |

Not every cell must be implemented, but neither axis defines the other. A materializer realizes its claimed set of one or more components; a wiring compiler connects semantic endpoints. The narrow bridge between them is an explicit endpoint and runtime-binding contract.

```text
DynamoGraphDeployment
    |
    +- semantic components, roles, capabilities and graph relationships
    |
    +- MATERIALIZATION
    |    |- direct Grove contributor
    |    |- DynamoComponentDeployment
    |    |- DisaggregatedSet
    |    |- EnginePool                         (future)
    |    `- LPXGraphDeployment                 (future)
    |
    `- WIRING
         |- request/service edge
         |- KV-transfer edge
         |- speculative draft/verify edge
         `- leader/worker or agent rendezvous
```

One selected `workloadProgram` owns the complete graph reconcile and orders both axes. A graph program may contain many focused reconcilers. "Complete program" means that the program owns graph-level control flow and status; it does not mean that the implementation is monolithic or that every component uses the same child resource.

Programs do not invoke other complete programs:

```text
incorrect: groveProgram -> componentProgram -> anotherProgram

correct:   groveProgram
             |- componentClassifier
             |- endpointDeclarationReconciler
             |- logicalWiringCompiler
             |- ordinaryGroveMaterializer
             |- enginePoolChildrenReconciler
             |- lpxGraphDeploymentChildrenReconciler
             |- groveAssemblyReconciler
             |- scalingAdaptersReconciler
             `- aggregate status projection
```

These are concrete collaborators inside one program, not provider callbacks in a universal lifecycle framework.

### 2. Declare, wire, then materialize

Wiring cannot be an afterthought applied only after Pods exist: workload commands, environment variables and ConfigMaps may require peer addresses during rendering. Materialization also cannot own all wiring, because the peer may be realized by another controller and resource kind.

The program therefore uses a staged contract:

```text
1. normalize DGD component and role intent
2. classify each component and assign exactly one materializer
3. declare stable logical endpoints and workload identities
4. compile graph and role relationships into runtime bindings
5. reconcile stable Services, ConfigMaps and other binding resources
6. pass bindings into each materializer or its child CR
7. obtain direct resources or asynchronously published render contributions
8. assemble and reconcile provider-native workloads
9. observe child/provider status and project aggregate DGD status
```

Endpoint declaration precedes physical workload creation. A declaration can resolve deterministically to a Service reference, role identity or provider-neutral endpoint handle without requiring a live Pod. If an external controller determines an endpoint dynamically, it publishes an observed-generation-guarded endpoint result and the graph program requeues until it is available.

The order is a program concern. It is not a requirement that every collaborator implement one common `Render/Ready/Rollout` interface.

### 3. Component claiming inside a program

Component normalization occurs once per graph reconcile. The selected program then assigns every normalized component to exactly one workload contributor.

The initial implementation should use concrete reconcilers rather than a universal provider interface. A small internal value may make ownership and aggregation explicit:

```go
type ComponentClaim struct {
    ComponentName string
    Contributor   string
}

type WorkloadContribution struct {
    Resources  []Resource
    Components map[string]v1beta1.ComponentReplicaStatus
    Conditions []metav1.Condition
}
```

The program is responsible for validating that:

- every component is claimed exactly once;
- two contributors do not claim the same component;
- returned component status belongs to a claimed component;
- stale children from an earlier set of claims are removed safely; and
- a contributor failure is projected through the program's native error and status policy.

This is a mechanical composition contract, not a claim that contributors share rollout, readiness, revision, or scaling semantics.

### 4. Concrete program composition

The existing graph programs retain their complete state machines and compose focused workload reconcilers.

#### ComponentProgram

```text
componentProgram
    |- common graph resources
    |- component workload reconciliation
    |    `- zero or more DynamoComponentDeployments
    |- rollout and scaling adapters
    `- DCD status aggregation
```

The DCD controller remains the persisted retry and ownership boundary that lowers one component to a `Deployment` or `LeaderWorkerSet`.

#### GroveProgram

```text
groveProgram
    |- common graph resources
    |- ordinary Grove workload reconciler
    |    `- components handled directly by Grove lowering
    |- specialized child-deployment reconciler
    |    `- zero or more child CRs for claimed materialization units
    |- Grove-specific rollout, scaling, topology, and readiness
    `- aggregate component status
```

The specialized child reconciler is set-oriented. It deterministically reconciles one child per claimed materialization unit, which may contain one or several components, deletes stale owned children, and returns current status for every claimed component. Each child controller owns its provider-specific compilation and workload lifecycle.

This supports graphs containing two or more specialized components without selecting multiple graph programs.

#### DisaggregatedProgram

```text
disaggregatedSetProgram
    |- common graph resources
    |- selected eligible worker components
    |    `- one DisaggregatedSet with embedded role LeaderWorkerSetSpecs
    |- remaining components
    |    `- zero or more DynamoComponentDeployments
    `- aggregate DisaggregatedSet and DCD readiness
```

DisaggregatedSet roles are graph-level roles whose members are complete DGD components. They are distinct from the component-internal roles defined by DEP #14417.

### 5. Component-internal roles

[DEP #14417](https://github.com/ai-dynamo/dynamo/issues/14417) defines the public component-role API. This DEP consumes its result rather than reopening its API decisions.

A role refines the inside of one semantic component. It does not become a DGD graph node or an independently owned workload component. The graph program resolves the component and its roles into a provider-neutral model before either materialization or wiring:

```go
type ResolvedComponent struct {
    Name     string
    Type     v1beta1.ComponentType
    Replicas int32
    Roles    []ResolvedRole
}

type ResolvedRole struct {
    Name        string
    Replicas    int32
    PodTemplate corev1.PodTemplateSpec
    Endpoints   []EndpointDeclaration
}
```

`ResolvedRole` contains semantic role information, effective PodTemplates and semantic endpoint declarations. It must not contain Grove, LeaderWorkerSet, DisaggregatedSet, scheduler, or provider-generated object names.

For example, the resolved `leader` and `worker` roles of a multinode engine can participate in a rendezvous binding while still materializing through either LeaderWorkerSet or Grove. A specialized compiled engine can resolve coordinator and agent roles and then delegate their physical realization to an `LPXGraphDeployment`.

### 6. Workload materializers

Each workload implementation translates the same resolved component roles into its native objects:

| Semantic component shape | Possible materialization |
| --- | --- |
| Single-Pod engine or frontend | DCD -> Deployment, or direct Grove PodClique |
| Multinode leader + workers | DCD -> LeaderWorkerSet, direct Grove PCSG, or future EnginePool |
| Disaggregated component set | DisaggregatedSet plus DCDs for the remaining graph |
| Elastic expert-parallel engine | direct Grove initially; future EnginePool child boundary |
| Specialized compiled multi-role engine | LPXGraphDeployment -> provider-native workloads |

The table is deliberately many-to-many. A semantic shape does not permanently select a Kubernetes resource kind, and a materializer is not a communication mode.

Concrete materializers remain responsible for their child API, watches, compilation, rollout interpretation, readiness, cleanup and native resource naming. They consume resolved components and runtime bindings. They must not rediscover DGD relationships by inspecting sibling workload object names.

The initial implementation can keep direct Grove lowering in-process. A persisted child such as `EnginePool` or `LPXGraphDeployment` is introduced only when it provides an independent retry, ownership, compilation, rollout, scaling or observability boundary.

### 7. Multiple specialized components

A specialized child deployment is scoped to a materialization unit rather than necessarily to one component. A unit may claim one component or several complete components when its materializer supports their shared lifecycle. Its identity is derived from the owning DGD and a stable unit key; source identity includes the exact DGD UID. The claimed component set may be explicit or, for the initial LPX singleton, implicit in the DGD-scoped handoff. The graph program must still assign each component to exactly one active materializer claim.

```text
DGD
    |- ordinary component A -> ordinary provider workload
    |- specialized component B -+
    `- specialized component C -+-> one shared child deployment
```

The graph program owns the collection of children. Each child controller owns only its claimed components' materialization and native workload resources. The graph program aggregates status for each claimed component together with ordinary component status.

Relationships between specialized components, such as speculative draft and verifier request flow, remain semantic wiring. They do not by themselves determine child cardinality. Two components may be claimed by one child when the materializer supports a shared unit, or by separate children when their lifecycle boundaries are independent. In the initial LPX integration, one DGD-scoped LGD claims all LPX components, including multiple independent engines; #14473 defines that compatibility boundary and its future partitioning.

### 8. Logical wiring

Logical wiring describes why two semantic endpoints communicate, not which Kubernetes resources contain their Pods. It includes both inter-component and intra-component relationships:

| Wiring intent | Example producer and consumer | Materialization-independent meaning |
| --- | --- | --- |
| Request/service | frontend -> engine | Send inference requests to a ready component endpoint |
| KV transfer | prefill -> decode | Transfer KV state using the selected transport and endpoint capabilities |
| Speculative decoding | verifier/target -> drafter | Bind the verifier to one or more draft endpoints |
| Rendezvous | leader -> workers | Form one distributed engine instance with rank and leader identity |
| Expert-parallel membership | coordinator -> ranks | Join the same EP control and data plane |

Some relationships are inferred today from component types and backend configuration rather than expressed as explicit DGD edges. This DEP does not require a new graph-edge API. It requires the reconciler to normalize those existing semantics into a wiring model before provider-specific rendering.

Conceptually:

```go
type EndpointRef struct {
    ComponentName string
    RoleName      string // optional
    Port          string
    Protocol      string
}

type WiringIntent struct {
    Kind     WiringKind
    Consumer EndpointRef
    Producer EndpointRef
    Policy   WiringPolicy
}

type RuntimeBinding struct {
    Consumer EndpointRef
    Values   []BindingValue // service refs, env, args, config or typed handles
}
```

These are illustrative internal values, not a proposed public API. `WiringIntent` must not contain DCD, EnginePool, LPXGraphDeployment, PodClique or PodCliqueScalingGroup names.

The wiring compiler consumes semantic relationships and endpoint declarations. A materialization adapter translates the resulting binding into the concrete form required by its workload: a stable Service DNS name, a headless Service, an ordinal-aware hostname, environment variables, command arguments, a ConfigMap entry, or a child-CR reference.

The invariant is:

```text
wire(A, B, kind) depends on A/B capabilities and EndpointRefs,
not on whether A or B is deployed by DCD, Grove, EnginePool or LPXGraphDeployment.
```

Address formation is the explicit exception. The adapter may need to know how the selected materializer publishes or derives an endpoint, but that knowledge is confined to endpoint resolution and does not leak into graph semantics.

### 9. Endpoint and binding contract

Every materializer declares the endpoints and identities it can provide before workload rendering. A declaration uses stable semantic keys:

```go
type EndpointDeclaration struct {
    Ref          EndpointRef
    Scope        EndpointScope // component, role, replica or rank
    AddressClass AddressClass  // service, headless, ordinal, runtime-published
    Capabilities []Capability
}

type ComponentMaterialization struct {
    ComponentName string
    Materializer  string
    ChildRef      *corev1.ObjectReference
    Endpoints     []EndpointDeclaration
}
```

The concrete representation may be an ephemeral program value, a child spec, or observed child status depending on the ownership boundary. The contract must preserve these properties:

- endpoint identity is stable across rollout revisions;
- the producer of an endpoint owns its address realization;
- consumers refer to semantic endpoint identity, not inferred object names;
- status-derived endpoints carry source generation and freshness;
- a child can publish explicit references without exposing how it factors its internal Grove resources;
- missing or stale endpoint information blocks only the dependent binding and is reported through the program's status policy.

Internal role wiring follows the same rule. A multinode renderer may resolve the leader endpoint into LWS-specific or Grove-specific DNS, while an EnginePool may publish its own rendezvous handle. The engine's leader/worker relationship remains the same semantic input.

### 10. Composing one Grove graph from decomposed workloads

![Three ways to assemble one Grove PodCliqueSet from decomposed workload controllers](https://github.com/user-attachments/assets/725465bb-c2e4-4213-9988-20ae71f1ab14)

Independent child resources create a separate physical question: must their workloads live in separate PodCliqueSets, or must the selected Grove program eventually produce one joint PodCliqueSet?

Separate PCSs are sufficient when components only require network wiring and independently scalable lifecycles. A joint PCS may be required when the desired contract needs Grove-native colocation, one topology scope, cross-role startup ordering, or one shared scaling-group/index space. Sharing a PCS must not be inferred merely from the existence of a logical edge.

Three assembly models are possible:

#### In-process composition

Focused reconcilers return render contributions during the DGD reconcile, and `groveProgram` assembles one complete PCS in memory. This preserves a single writer and is the simplest model while all lowering remains in the Dynamo operator process. It does not provide an independent persisted controller boundary for EnginePool or LPXGraphDeployment.

#### Multi-writer server-side apply

The DGD Grove reconciler and specialized child controllers apply disjoint, map-keyed fragments to one PCS using distinct field managers:

```text
DGD Grove reconciler  --SSA manager:dgd-->  PCS frontend/prefill entries
EnginePool controller --SSA manager:ep----> PCS elastic-EP entries
LPX controller        --SSA manager:lpx---> PCS compiled-engine entries
```

This keeps compilation and controller code independent while sharing one native object. It is viable only with a deliberately designed ownership protocol:

- every jointly written list has stable map keys and compatible CRD list semantics;
- one controller owns root metadata, owner references and root policy;
- field-manager names and owned paths are stable API contracts;
- key collisions are rejected deterministically;
- removal, stale-manager cleanup and child deletion are defined;
- no controller force-applies over another manager's fields;
- readiness, revision and failure ownership are explicit;
- controllers cannot observe a transient partial object and misinterpret it as a complete graph.

SSA prevents accidental field overwrites; it does not by itself create a graph transaction, coordinate rollout, or define when the joint PCS is complete.

#### Grove render collector

Each independently reconciled workload object publishes an observed-generation-guarded Grove render contribution, for example in child status. A DGD-scoped Grove assembly reconciler is the sole writer of the complete PCS:

```text
DGD/direct components --------> Grove fragment --+
EnginePool.status ------------> Grove fragment ---+--> Grove assembly --> one PCS
LPXGraphDeployment.status ----> Grove fragment --+
```

A contribution contains exact desired Grove entries and explicit exported endpoint references. The collector never reverse-engineers child naming. It validates ownership, source generation, unique keys, references and compatibility, then renders the complete desired PCS through the ordinary single-writer path.

This preserves strong write ownership and makes the assembled graph observable, but adds an asynchronous handshake. The design must specify whether an unavailable or stale fragment blocks a new revision, retains the last complete PCS, or removes the component contribution. It must also prevent fragments from different DGD generations or rollout revisions from being combined.

The initial composition refactor does not choose between SSA and a collector. It must avoid assumptions that make either impossible. In particular, contributors must have stable identities, explicit references, collision-free keys and generation-aware results.

### 11. Status, scaling, and rollout

- The selected graph program is the sole owner of aggregate DGD workload status.
- Each contributor reports status only for the components it claimed.
- A child controller publishes observed-generation-guarded component status on its child CR.
- The graph program projects that status without interpreting private child object names.
- Component scaling changes logical component replicas. Role scaling is internal to one component replica and follows component-type rules.
- Multiple specialized components may scale independently unless the DGD API requests an explicitly supported coordination scope.
- Combining status does not imply an atomic transaction across DCDs, child CRs, DisaggregatedSets, or PodCliqueSets.
- Logical wiring readiness and workload readiness are separate observations. The program combines them into component and DGD conditions without pretending they are one provider-neutral state machine.
- Scaling changes materializer-owned capacity. Wiring consumes ready endpoint sets and must tolerate the convergence interval without owning the scaling mechanism.
- A joint PCS may share a rollout envelope, but neither SSA nor fragment collection alone defines atomic scale or rollout semantics.

### 12. Resource ownership and watches

- The DGD owns graph-stable resources and its direct workload children.
- A specialized child CR owns the compiled or provider-native workload resources for its claimed materialization unit.
- Controller watches are registered statically for typed child APIs and map events through verified owner references and source identity.
- Child cleanup is set-based: reconcile desired children, retain current matching children, and delete only stale children with an exact owner chain.
- Provider-generated object names are encapsulated by the controller that owns those objects. Parent controllers consume explicit references or child status, not inferred names.
- If several controllers contribute to one PCS, the owner and deletion authority of that PCS are singular even when field ownership is distributed.
- A Grove collector, if selected, owns the complete PCS write; child controllers own only their contribution publication and child status.

## Alternate Solutions

### Promote runtime roles to sibling DGD components and reconstruct them with component groups

This makes the group the real lifecycle unit and turns its members into fragments that may not be deployable independently. It changes component-type semantics and exposes provider topology in the inference-aware DGD API. It also creates two ways to produce similar provider objects: implicit lowering for existing compound components and explicit grouping for new ones.

Component groups may still be useful where complete, independently meaningful components require an explicit graph-level coordination boundary. They should not be required merely to describe the internal roles of one engine.

### Add one graph program per specialized component type

This does not compose mixed graphs naturally. A graph containing ordinary components and multiple specialized components would either require nested programs or make one provider name misleadingly represent the whole graph.

### Let programs invoke other complete programs

Nested programs create competing owners for ordering, finalization, events, rollout, and aggregate status. Shared behavior should instead be extracted into focused reconcilers and libraries.

### Use a universal workload-provider interface

As described in #12035, structurally similar provider operations do not imply equivalent readiness, revision, rollout, or failure semantics. This DEP uses concrete program composition and a narrow contribution value, not a universal lifecycle interface.

### Couple wiring directly to each materializer

Teaching DCD, Grove, DisaggregatedSet, EnginePool and LPXGraphDeployment paths independently how to discover and connect every peer duplicates semantic logic and produces a cross-product of materializer and communication modes. It also makes changing a component's workload resource an API-visible communication change. Materializers should consume bindings through a narrow adapter instead.

### Encode workload resources in graph edges

An edge such as `prefillDCD -> decodeLPXGraphDeployment` may appear concrete, but it confuses a current deployment decision with the semantic KV-transfer relationship. Graph relationships refer to components, roles and capabilities. Object references belong in the materialization and endpoint layers.

### Require every contributor to mutate one shared provider object immediately

Forcing every integration into one in-process Grove renderer prevents independently owned child CRs and controllers. Forcing every controller to write one PCS without a protocol creates ambiguous ownership. Multi-writer SSA and a render collector remain possible assembly mechanisms, but both require explicit generation, ownership, collision, deletion, readiness and rollout contracts.

### Always create one PCS per child workload

Separate PCSs provide clean ownership and are sufficient for ordinary network wiring. They cannot express every possible Grove-native relation across the boundary, including joint colocation, startup dependencies or one shared scaling-group/index space. The architecture should permit separate PCSs without making them the only future answer.

### Always create one joint PCS

A joint PCS can preserve one Grove topology and rollout envelope, but requiring it for every logical edge falsely couples communication with placement. It also makes independent materializers participate in shared-object ownership even when no cross-component Grove constraint exists.

## Requirements and Invariants

1. Exactly one workload program is selected for a DGD.
2. Programs may compose reconcilers and libraries but never invoke another complete program.
3. Workload materialization and logical wiring are independent DGD architecture axes.
4. Every normalized component is claimed by exactly one materializer during workload reconciliation.
5. The selected program remains the sole aggregate DGD status writer.
6. One DGD may contain components realized by different workload resource kinds inside the selected program.
7. A DGD may own zero, one or multiple child resources of each supported specialized kind.
8. Adding a materializer does not require adding a new graph-level program when it composes within an existing program.
9. A wiring intent references semantic components, roles and capabilities, not DCD, PCS, EnginePool, LPXGraphDeployment or generated object names.
10. Materializers declare stable endpoint identities before rendering and own their concrete address realization.
11. The address-formation adapter is the only layer allowed to translate semantic EndpointRefs into provider- or resource-specific addresses.
12. A component's communication semantics remain stable when its materializer changes, unless the replacement cannot provide a required endpoint capability.
13. A materializer consumes resolved runtime bindings instead of rediscovering graph relationships from sibling resources.
14. Component roles do not become sibling DGD components; their API and invariants are owned by DEP #14417.
15. DisaggregatedSet graph roles and component-internal roles remain distinct concepts in APIs, code and documentation.
16. Provider-generated object names are encapsulated by the controller that owns or renders those objects.
17. Status-derived contributions and endpoints carry observed generation and cannot be combined across incompatible graph revisions.
18. Separate PCSs are valid for independently placed and scaled components; a joint PCS is required only by an explicit Grove-level coordination need.
19. SSA field separation prevents overwrite conflicts but does not imply graph completeness, atomic scaling or rollout.
20. A Grove collector, if used, is the sole writer of the complete PCS and never infers child resource factoring or names.
21. Cross-child atomicity, colocation and one-object materialization must be requested and implemented explicitly; status aggregation or logical wiring alone does not imply them.
22. Existing DGD and DCD manifests preserve their current rendered behavior during the initial composition refactor.

## Implementation Plan

### Phase 1: Characterize and factor the existing programs

- Characterize existing Component, Grove, and DisaggregatedSet outputs before changing reconciliation structure.
- Keep the existing complete programs and extract concrete collaborators for ordinary component reconciliation, stable Services, normalization, and status aggregation.
- Ensure each collaborator documents its consumed facts, returned contribution, side effects, and ownership invariants.
- Remove any program-to-program calls or provider-specific naming dependencies discovered during extraction.
- Add exactly-once component-claim validation and contribution aggregation.

### Phase 2: Establish the two-axis internal model

- Introduce provider-neutral `ResolvedComponent` and `ResolvedRole` values without copying provider API objects.
- Introduce semantic `EndpointRef`, `EndpointDeclaration`, `WiringIntent` and `RuntimeBinding` values.
- Normalize existing service discovery, KV transfer and multinode rendezvous behavior into these values without changing rendered output.
- Separate endpoint declaration, binding compilation and materializer-specific address formation.
- Add tests proving that the same semantic wiring can target at least the existing DCD and Grove materializers.

### Phase 3: Support plural specialized workload resources

- Reconcile one deterministic child CR per selected materialization unit, including units that claim multiple components and multiple children of the same kind.
- Add exact-owner adoption rejection, stale-child deletion, finalization, indexed watches, and per-component status projection.
- Pass resolved component intent and bindings into child specs without embedding sibling workload names.
- Accept explicit, generation-aware endpoints and render contributions from child status where required.
- Test zero, one, two, removal, rename, failed child, stale generation, and partial readiness cases.

Candidate future children include an Elastic EP `EnginePool` and `LPXGraphDeployment`; introducing either resource remains a separate API decision.

### Phase 4: Generalize Grove assembly

- Define a versioned internal Grove contribution schema with stable keys and explicit references.
- Preserve current in-process one-PCS rendering as the baseline.
- Prototype SSA and render-collector assembly against the same multi-contributor scenarios.
- Test addition, update, removal, stale generation, key collision, partial contribution, controller restart and failed child behavior.

## Testing Strategy

- Golden rendering tests for existing DGD and DCD manifests with no role fields.
- Unit tests for component claiming and contribution aggregation.
- Envtest coverage for zero, one, and multiple specialized child CRs.
- Status tests covering mixed ordinary and specialized components, stale child generations, and partial failures.
- Cleanup and finalizer tests proving that only exact owned children are deleted.
- Wiring golden tests proving that DCD and Grove materializers receive equivalent semantic bindings for the same component graph.
- Endpoint tests for stable Service, headless, role, replica and runtime-published address classes.
- Provider-specific tests proving that wiring and role lowering do not depend on generated object names outside the owning renderer.
- DisaggregatedSet tests proving that graph-level DS roles remain complete component selections rather than component-internal roles.
- Multi-materializer tests such as ordinary frontend plus specialized engine, ordinary verifier plus specialized drafter, and two specialized components of the same type.
- Scaling tests proving that endpoint sets may converge independently while logical wiring intent remains stable.
- Joint-PCS tests for in-process composition and any selected SSA or collector prototype, including key conflicts, removal, stale generations and incomplete contributions.
