# [Issue #14310] DEP: One SelectionCore behind the frontend, the standalone selection service, and the EPP

source: https://github.com/ai-dynamo/dynamo/issues/14310
state: closed | updated: 2026-09-18T05:06:38Z
labels: enhancement, language::rust, dynamo-runtime, dynamo-llm, router, dep:draft, epp

## 正文

## Summary

Make `SelectionCore` in `lib/kv-router` the only implementation of worker selection, booking and load accounting, worker-record reconciliation, KV indexing, and session affinity. The frontend's `KvRouter` and the standalone EPP embed the core; `SelectionService` is the standalone deployment of the same core (HTTP API, peer mesh, workers file, lease sweeper). Every runtime-dependent piece (discovery watch, event plane, request contexts) becomes an implementation of a `lib/kv-router` trait that lives in `lib/llm`. `lib/kv-router` never imports `dynamo-runtime`. The frontend keeps using the Dynamo runtime for discovery, the request plane, and the event plane; only the implementation behind those signals moves.

This is a refactor with one addition: no change in routing decisions, wire formats, or configuration for existing deployments, plus session affinity for the standalone EPP. A complete prototype exists as a stacked series on a fork (references below) and is proposed here as nine stacked PRs.

## Terminology

- **`SelectionCore`** (`lib/kv-router/src/services/selection/core/`): the engine. Worker catalog and record reconciliation (a record becomes schedulable only when it carries endpoint, block size, DP layout, and, when events are required, KV-event endpoints), per-partition scheduler and sequence tracker, `select` / `select_and_reserve` / `prefill_complete` / `free`, reservation index, indexer listeners per worker rank. This is what the DEP unifies and what every host embeds.
- **`SelectionService`** (`service.rs`): the standalone process around the core: builder, HTTP router, replica peer mesh, indexer recovery from peer `/dump`, initial workers file, lease sweeper, shutdown. Used by the standalone binary and the EPP standalone mode. Peer-dump recovery is a service feature, not a core one, and is not what the frontend runs.
- **Host**: whoever embeds the core. Today the frontend `KvRouter` (over the Dynamo runtime) and the standalone service / EPP (over ZMQ and a pod reflector).

## Motivation

Today the frontend and the EPP each carry their own copy of the routing brain, and the frontend's is ahead:

| Capability | Frontend | Standalone `SelectionService` (EPP) |
|---|---|---|
| Scheduler and load bookkeeping | `KvScheduler`, bound to the runtime event plane | `SelectionCore` |
| KV index | `lib/llm` `Indexer` enum with recovery (event plane or direct ZMQ, replay, worker tree dump, state agent, source health) | a separate `Indexer` enum in `lib/kv-router`, direct ZMQ listeners, peer `/dump` on cold start |
| Session affinity | `AffinityCoordinator`: hard and soft modes, TTL, replica-aware bindings over the event plane | none |
| Worker membership | runtime-config watch with a router-local feeder | pod reflector with an EPP-local reconcile loop |
| Custom selection policies | a `Sel` type parameter threaded through `KvRouter`, `RoutingHost`, `PrefillRouter`, `ModelWatcher` | policy factory on the service builder |

Every bookkeeping or indexing change is made twice or lands only in the frontend. The EPP lags on shared-cache hits, LoRA narrowing, structured session context, router hints, busy evaluation, and recovery diagnostics, and has no session affinity at all. Membership bugs are record-shape drift between two feeders that should be one.

## Proposal

One boundary with two directions. Below it, `SelectionCore` owns selection, booking, load accounting, record reconciliation, KV indexing, affinity, and replication state. Above it, the host owns transport, discovery, retry, and telemetry consumption. The host and the core meet at two objects.

**`SelectionHost`**: what a host supplies to every partition the core creates, grouped by purpose, each group defaulting to the standalone service's behavior.

- `load`: prefill-load estimator; overloaded and available worker providers (the frontend feeds these from its request client).
- `cache`: `shared` (a cross-worker KV cache) and `index: KvIndexSource`.
- `eligibility`: LoRA worker filter.
- `telemetry`: scheduler-load sink (per-worker snapshots for metrics and overload rejection).
- `replication`: host-carried channels for active-sequence replica events.

**`KvIndexSource`**: `Owned(Arc<dyn KvEventIngress>)` or `Remote(url)`. An ingress builds the partition's index (`open`) and feeds it. Runtime-free traits in `lib/kv-router`, implemented per host:

| Trait | Frontend implementation (`lib/llm`) | Standalone / EPP implementation (`lib/kv-router`) |
|---|---|---|
| `KvEventIngress` | `RuntimeIngress`: event plane (ZMQ or NATS), per-rank recovery, served-indexer endpoint | `ZmqDirectIngress`: one SUB socket per rank, replay socket, decides which metadata makes a worker schedulable |
| `WorkerCatalogSource` | `RuntimeDiscoverySource`: runtime-config watch | `PodReflectorSource`: the EPP's pod reflector |
| `AffinityReplicaSink` | runtime event plane | ZMQ peer mesh, second topic |

Both hosts share one `Indexer` type (`services::indexer::{backend, lookup, recording}`), including the lookup pipeline, routing-decision recording, and the approximate-LRU lease. The frontend's `Indexer` enum is deleted.

**Membership**: `WorkerCatalogSource` yields complete desired snapshots; `CatalogReconciler` applies them to the catalog (upsert new or changed, retry not-yet-schedulable, delete departed, reject duplicate ids). One reconcile loop replaces the router-local and EPP-local ones.

**Policies**: `SelectionPolicySource { Registry, Factory }` replaces the `Sel` type parameter. The partition resolves the policy once; custom policies use the public filter/scorer/picker API.

**Session affinity**: `SessionAffinity` (versioned bindings, TTL reaper, initialization and lease lifecycle, hard and soft validation, replica apply) becomes the one table. The frontend wraps it for pipeline streams and request-context cancellation and replicates bindings over the runtime event plane. The standalone service owns a table when given a TTL, holds the lease with the booking, and replicates bindings over its ZMQ peer mesh. This is the one capability the EPP gains.

**`SelectionService`** stays the thin standalone host: builder, HTTP API, peer mesh, workers file, lease sweeper.

```
frontend KvRouter ──┐                              ┌── standalone service / EPP
  RuntimeIngress    │      SelectionHost           │   ZmqDirectIngress
  RuntimeDiscovery  ├──▶  SelectionCore (partition) ◀──┤  PodReflectorSource
  AffinityCoordinator│     Indexer, SessionAffinity  │   SessionAffinity (owned)
  runtime event plane┘                              └── ZMQ peer mesh
```

### Delivery

Nine stacked PRs, each independently reviewable and green:

| Step | Scope |
|---|---|
| 1, 2 | Core parity in `lib/kv-router`: `SelectionHost`, shared-cache hits and session context, LoRA narrowing, reservation index, advisory select with busy evaluation, approximate and remote indexers, router hints |
| 3 | `KvRouter` re-hosted on an embedded core partition; embedded made the only path |
| 4 | Delete `KvScheduler` and its runtime-bound bookkeeping |
| 5 | `SelectionPolicySource`; remove the `Sel` type parameter |
| 6 | `WorkerCatalogSource` + `CatalogReconciler`; `RuntimeDiscoverySource`, `PodReflectorSource` |
| 7 | `KvIndexSource`, one `Indexer` type, `KvEventIngress` with `ZmqDirectIngress` and `RuntimeIngress` |
| 8 | `SessionAffinity` table in `lib/kv-router`; frontend `AffinityCoordinator` becomes a wrapper |
| 9 | Core-owned session affinity for the standalone service and EPP (`--session-affinity-ttl-secs`, `DYN_EPP_SESSION_AFFINITY_TTL_SECS`) |

## Behavior and compatibility

- No observable change for runtime-backed frontends: same discovery, request plane, event plane, replica sync, session affinity, overload rejection (529), migration. The frontend's recovery machinery is unchanged and reached through `RuntimeIngress`.
- Worker records, discovery records, KV-event formats, and the active-sequence replica wire format are unchanged. The one new wire is a second ZMQ topic on the standalone peer mesh that older peers never subscribe to.
- No new configuration for existing deployments. The two new knobs are opt-in for standalone hosts.

## Alternate solutions

- **Keep two schedulers and port features across.** Rejected: the drift above is the cost of that approach; every routing change keeps landing twice.
- **Make the frontend embed `SelectionService` with standalone concerns disabled.** Rejected after prototyping: the service wrapper carries process-level choices (peer mesh, workers file, dump recovery) the frontend must switch off one by one. Embedding the core through `SelectionHost` keeps the wrapper thin and the frontend honest about what it provides.
- **Move the frontend's recovery state machine into the core now.** Deferred: it is transport-bound, and `RuntimeIngress` is a clean seam for it. Follow-up below.

## Validation

Per PR: kv-router, llm, and ext-proc unit suites; clippy; Python bindings check. At the tip of the series: `tests/router/test_router_e2e_with_mockers.py`, offline KV replay byte parity on four rows (vLLM and SGLang, aggregated and disaggregated) against the pre-series baseline, and a frontend A/B benchmark for the embedded partition. On the fork prototype: e2e 45 passed and 6 skipped with 5 environment-only failures for build features not enabled locally, replay parity byte-identical on all four rows, and +6% requests/s with lower p50 and p99 at concurrency 128. The upstream PRs will carry rebased numbers.

## Out of scope, tracked as follow-ups

- **Moving the frontend's per-rank recovery state machine into the core.** Today, when a worker's KV events arrive over the runtime event plane, the frontend tracks a small state machine per data-parallel rank: is the rank healthy, did events go missing (sequence gap), should it ask the engine to replay them, should it drop what it knows about the rank and rebuild from the engine's authoritative dump, and how does it report source health. That logic lives in `lib/llm` behind `RuntimeIngress`. `ZmqDirectIngress` has a simpler version: one subscriber per rank plus gap replay. The follow-up moves the richer recovery logic into `lib/kv-router` so both ingresses share it and the frontend copy is deleted; transport stays per host. It is not in this DEP because the logic is tangled with runtime types (endpoints, subscriptions, worker query RPCs) and pulling it apart risks changing routing behavior, which this DEP promises not to do. Gate: offline replay byte parity on the four rows and the router e2e suite must pass unchanged before the frontend copy is removed.
- **Peer `/dump` cold-start recovery in the standalone service.** When a standalone replica starts with an empty index, it asks a peer replica for a full copy of its index over HTTP (`/dump`) and loads it, then follows live events. This is a `SelectionService` feature, not a core one, and the frontend never uses it: the frontend rebuilds from the engine itself, which is the only source that is actually correct. A peer copy can be stale or can have been built from a peer that was itself recovering. The follow-up gives `ZmqDirectIngress` an engine-authoritative full dump (the engine's own block tree, the same thing the frontend's worker query reads today) so a cold replica rebuilds from the engine instead of a neighbor. Until then peer `/dump` stays as-is. Gate: a cold standalone replica converges to the same index as a warm one on the replay parity rows.
- One disaggregation coordinator (`DisaggCoordinator`, prefill-anchored and decode-anchored orders) shared by the frontend `PrefillRouter` and the EPP. A separate DEP: the frontend fuses select, book, and dispatch with migration retries inside, and moving it is not a refactor.

### tmonty12 · 2026-09-09

Two notes on LoRA, one for this stack and one as a follow-up.

**For this stack:** `SelectionHost.eligibility` (the `LoraWorkerFilter` hook) feels like it belongs in the catalog rather than as a host-supplied interface. Workers already publish their loaded adapters and capacity through MDC events — that information should live in the worker record in `WorkerCatalogSource`. When the catalog carries LoRA state, `SelectionCore` can handle narrowing natively given a `lora_name` in the selection input, and the host doesn't need to know about LoRA routing at all. `eligibility` would go away.

**As a follow-up:** the current LoRA filtering runs before the scheduler or KV scorer sees any candidates — `narrow_allowed_by_lora` prunes the candidate set before `ScheduleRequest` is built, and the builtin path can bypass the selector entirely. This means LoRA warmth and KV cache overlap never interact: a worker with good KV overlap and the right adapter loaded can lose to one with poor overlap just because the filter ran first. The right model is to express LoRA logic through the existing plugin interface (`WorkerFilter` or `WorkerScorer`) with the current warm-worker preference and HRW cold-start pinning as the default implementation. Custom policies could then weight LoRA warmth against KV overlap rather than hard-filtering before scoring. Out of scope for this DEP but worth tracking.

### tmonty12 · 2026-09-09

One more note on `SelectionHost.cache`.

`HicacheSharedKvCache` bundles two things: config discovery (reading `SglangHicacheMooncakeConfig` — page size, TP/PP layout, KV event endpoint — from worker metadata) and the ZMQ subscription to Mooncake events. Only the first is host-specific. The natural split, consistent with the `KvIndexSource` / `KvEventIngress` pattern already in the DEP: the host provides a stream of Mooncake config updates through a trait (call it `SharedCacheConfigSource`), and `SelectionCore` owns the ZMQ connection and the `present_keys` index. ### tmonty12 · 2026-09-09

A note on `SelectionHost.load` — all three inputs belong inside the core rather than as host-supplied hooks.

**`WorkerAvailabilityProvider`** is redundant with `WorkerCatalogSource`. Under `CatalogReconciler`, a worker only becomes schedulable once its record is complete, so a worker in the catalog is by definition available.

**`OverloadedWorkerProvider`** is derivable from the slot tracker. The `SchedulerLoadSnapshot` values `KvWorkerMonitor` receives come from the frontend's own `ActiveSequences` tracking — the same data the slot tracker in `lib/kv-router` already owns. The core has per-worker load from the slot tracker and thresholds from config; it can evaluate overload inline during selection without an external monitor or provider callback.

**`PrefillLoadEstimator`** is not host-specific. The only production implementation (`RustAicCallback` / `AicEngine`) is a pure perf model with no dependency on the runtime or transport. The EPP could initialize the same model from the same config at startup. This is a construction-time parameter to the partition, not a host hook.

`SelectionHost.load` goes away entirely.

### Follow-up: one routing configuration contract across entrypoints

After #14570, simplify routing configuration across the frontend, worker advertisements, standalone Dynamo router, SelectionService CLI/Python API, and EPP. The target is one set of routing semantics with thin input adapters. Transport, discovery, HTTP serving, and backend-engine configuration stay with their respective hosts; this is not a rewrite of all Dynamo configuration.

[Fork PR #57](https://github.com/ishandhanani/dynamo/pull/57) is related work: it separates affinity from KV tuning and shares affinity parsing across Rust entrypoints. Current #14570 already restores non-KV affinity through the #56 revert; #57 is a candidate refinement of that configuration path. It does not complete the [affinity-policy follow-up](https://github.com/ai-dynamo/dynamo/issues/14310#issuecomment-5689849345) for retries, table exhaustion, competing bindings, and dispatch ownership. Its `44de44f332` head is based on the older `39da83d7c1` branch state; any integration must reconcile the subsequent #56 revert, restored configuration compatibility, and HTTP-indexer deferral. This comment does not approve or merge #57.

**Problem.** Settings pass through Python argument groups, kwargs lists, PyO3 constructors, Rust config types, environment loaders, builders, and discovery overlays. Defaults and validation are repeated across these boundaries, and a field can be accepted without reaching the routing mode that consumes it. The non-KV affinity regression is a concrete example. Configuration sources also have different scopes: frontend defaults, worker-set advertisements, and prefill-hop configuration cannot safely be flattened into one generic merge.

**Proposed design**

1. **Give shared routing settings one owner.** Use runtime-free Rust domain types with authoritative defaults (including documented host-specific defaults) and semantic validation, exposed through existing bindings. Compose independent affinity, selection/scheduling, admission, and KV/index/cache settings; affinity must remain usable without KV routing. Host adapters supply capabilities and host settings. Reuse existing types where possible; avoid a single object containing every process option or a new configuration framework.
2. **Separate supplied values from resolved values.** Normalize legacy names into sparse inputs that distinguish omitted, explicitly disabled, and explicitly set. Resolve process inputs once at the host boundary, then resolve a configuration snapshot for each worker set/routing hop when its admitted configuration or selected generation changes, preserving incumbent/cohort admission rules. Rejected advertisements must not reconfigure a serving worker set. Constructors consume resolved typed values and do not independently read environment variables, reopen configuration files, or reinterpret defaults. Requests continue to use their existing request-level constraints/overrides without configuration I/O in the hot path.
3. **Specify precedence by scope.** Within a host's process inputs, document CLI/API versus environment versus defaults, including aliases and the treatment of malformed shadowed values. Preserve existing policy-file replacement rules, preset/expansion order, and worker-advertisement behavior in the first migration. For example, Python currently applies the load-aware preset before conditional-disaggregation expansion and its queue-threshold fallback. Today a worker advertisement supplies the routing group, with explicit frontend overlays for prefill/decode policy and affinity mode; prefill advertisements can replace the hop's affinity TTL with disabled. A worker without an explicit router mode must keep advertising no router configuration. Encode these rules in one resolver instead of introducing a blanket CLI-over-worker or recursive field-merge rule. Any intended precedence change must be separately identified and tested.
4. **Make the result inspectable.** Provide a stable effective-routing-config view showing values, their sources, and the relevant model/worker-set/hop. Support startup inspection and inspection after discovery resolves a worker set, with an identifiable snapshot revision. Report unsupported requested behavior explicitly; keep legitimate host defaults and capabilities visible. Do not expose credentials or arbitrary environment contents.
5. **Keep compatibility adapters narrow.** Preserve valid existing CLI/environment names, Python kwargs, and N-2 worker/frontend wire behavior while routing them through the shared contract. In particular, cover `DYN_EPP_SESSION_AFFINITY_TTL_SECS`, the common affinity names where supported, integer-second frontend TTLs versus fractional-second SelectionService/EPP TTLs and their shared range, omitted versus disabled values, and current EPP affinity capabilities. Strictness changes for malformed inputs or previously ignored settings, additional EPP modes, and any removal of aliases are explicit behavioral changes, not incidental cleanup. Preserve worker-card normalization and admission/checksum rules.

**Delivery and acceptance**

- First, inventory the routing fields and record each owner, input names, units, default, scope, precedence, supported hosts/modes, and wire representation. Add characterization tests before replacing a path. Use #57 as the affinity starting point after reconciling it with the current branch.
- Next, move adapters to the shared types/resolver in small PRs. Cover frontend KV and non-KV modes, worker advertisement on/off, prefill/decode combinations, standalone router, SelectionService CLI/API, and EPP. Exercise explicit overrides, preset/conditional-disaggregation ordering, legacy aliases, invalid values, disabled affinity, independent config instances in one process, and mixed-version cards. Equivalent supported inputs must yield equivalent resolved settings and routing behavior; intentional differences must be named.
- Finally, publish the effective-config view and one field reference. Remove duplicate defaults, validators, kwargs forwarding lists, and redundant config wrappers as each migrated path passes its checks. Derive CLI/binding/docs metadata from the shared field definitions where practical, with CI drift checks; this does not require a code-generation project before the first migration. Preserve lightweight argument/help imports that do not require loading the native extension.

No new universal YAML format, precedence change, affinity-policy change, or delivery date is committed by this proposal. The configuration cleanup and the existing runtime-affinity follow-up are separate workstreams with shared compatibility tests.
