## Describe the bug

Case-level follow-up to #13383 and its [earlier validation report](https://github.com/ai-dynamo/dynamo/issues/13383#issuecomment-5594559029). This issue tracks **`vllm-omni-video-agg`** specifically so the corresponding local workflow and Kubernetes translation can have explicit pass/fail acceptance criteria.

On matched public Dynamo **1.4.2** images, startup/model discovery succeed, but generation has two independently observed defects:

1. `response_format=b64_json` is dropped; the completed response contains only a pod-local `file://` URL.
2. The recovered video has severe color corruption from the bundled FFmpeg path.

These are not worker-startup failures and are not cured by aligning the operator to the same release.

## Expected behavior

HTTP 200 with `status=completed`, a nonempty `data[0].b64_json` containing the MP4, and decodable video without encoder-introduced magenta/banding. A pod-local filesystem URL is not a remotely usable substitute for explicitly requested base64.

## Actual behavior

HTTP 200 and completed generation, but no `b64_json`. Sanitized response excerpt:

```json
{
  "status": "completed",
  "progress": 100,
  "data": [
    {
      "output_format": "mp4",
      "url": "file:///tmp/dynamo_media/videos/<request-id>.mp4"
    }
  ]
}
```

The forensically recovered MP4 is **27,497 bytes**, decodes to 832×480 video (nine frames, 16 fps), and has severe magenta/banding. The four inference steps are a plumbing smoke test, not a comprehensive model-quality evaluation.

## Diagnosis and suggested scope

### A. Missing per-request field propagation

[`_engine_inputs_from_video()` in the tested release](https://github.com/ai-dynamo/dynamo/blob/v1.4.2/components/src/dynamo/vllm/omni/omni_handler.py) constructs `EngineInputs` without `response_format=req.response_format`. The [formatter](https://github.com/ai-dynamo/dynamo/blob/v1.4.2/components/src/dynamo/vllm/omni/output_formatter.py) consequently defaults to `url`.

Static inspection of [current upstream main at `0873e6c52d13`](https://github.com/ai-dynamo/dynamo/blob/0873e6c52d13ebb571b7205b1eda7d523b2d5335/components/src/dynamo/vllm/omni/omni_handler.py) also finds this assignment missing. Current-main serving was not deployed in this rerun.

The direct fix is small:

```diff
 return EngineInputs(
     ...
     request_type=RequestType.VIDEO_GENERATION,
     fps=fps,
+    response_format=req.response_format,
     ...
 )
```

This is an **HTTP request field**, not a launcher CLI flag. The launcher's example `response_format=url` and our intentional Kubernetes `b64_json` request are different delivery choices, not incompatible worker launch flags. A one-line patch was applicability-checked locally, but not deployed as a rebuilt image.

### B. Independent bundled-FFmpeg color defect

The forensically recovered generated MP4 has severe magenta discoloration and horizontal bands. That copy was recovered inside the worker pod; it was **not** successfully delivered to the client as requested base64.

This is not explained by the low inference-step count: a **model-free** synthetic RGB quadrant test reproduces the corruption through both `encode_to_video_bytes()` and `/usr/local/bin/ffmpeg` directly. An independent local FFmpeg decoder reproduces the bad colors.

| Controlled encode path | Result after independent decode |
|---|---|
| Known RGB24 → installed default YUV420p/VP9 path | Magenta/banding |
| Known-good YUV420p → same installed VP9 encoder | Correct colors |
| RGB24 with `-cpuflags mmx+mmxext` | Corruption |
| RGB24 with `-cpuflags mmx` | Correct colors |
| RGB24 with `-cpuflags -mmxext` | Correct colors |
| RGB24 with `-cpuflags 0` | Correct colors |
| RGB24 → YUV444p/VP9 | Correct colors |

The installed FFmpeg reports **8.1.2**, built with `--disable-x86asm`. Its packaged source still unconditionally sets `use_mmx_vfilter=1` in `libswscale/x86/swscale_template.c`; the corresponding external plane writers are gated out. This matches the MMX-filter-layout issue discussed in [FFmpeg's upstream corruption report](https://ffmpeg.org/pipermail/ffmpeg-devel/2024-May/326675.html) and [the upstream guard-fix proposal](https://www.mail-archive.com/ffmpeg-devel@ffmpeg.org/msg184947.html). This report does not assert that the proposal has merged or shipped in a particular FFmpeg release.

<details>
<summary>Model-free codec reproduction used to isolate this defect</summary>

Run in the stock runtime; no GPU model is needed. Decode/inspect the resulting files using an independent, known-good decoder, not just the producer's exit status.

```python
import pathlib
import subprocess
import numpy as np
from dynamo.common.utils.video_utils import encode_to_video_bytes

out = pathlib.Path('/tmp/dynamo-codec-repro')
out.mkdir(exist_ok=True)
frame = np.zeros((480, 832, 3), dtype=np.uint8)
frame[:240, :416] = [255, 0, 0]
frame[:240, 416:] = [0, 255, 0]
frame[240:, :416] = [0, 0, 255]
frame[240:, 416:] = [255, 255, 255]
frames = np.stack([frame] * 9)
(out / 'dynamo.mp4').write_bytes(
    encode_to_video_bytes(frames, fps=16, output_format='mp4')
)
for label, flags in [('default', []), ('no-mmxext', ['-cpuflags', '-mmxext'])]:
    subprocess.run([
        '/usr/local/bin/ffmpeg', '-y', '-hide_banner', '-loglevel', 'error',
        *flags, '-f', 'rawvideo', '-pix_fmt', 'rgb24', '-s', '832x480',
        '-r', '16', '-i', 'pipe:0', '-an', '-c:v', 'libvpx-vp9',
        '-pix_fmt', 'yuv420p', str(out / f'{label}.mp4'),
    ], input=frames.tobytes(), check=True)
```

The default red quadrant decodes approximately magenta (`255,0,255`); the MMXEXT-disabled control decodes approximately red (`252,0,0`). The exact corrupted bytes vary; pixel correctness is the assertion.
</details>

Disabling MMXEXT is a **diagnostic workaround**, not a performance-qualified deployment fix. Backport/validate the FFmpeg guard fix (or another correct build configuration) in a rebuilt runtime and add an RGB→video→RGB regression. No patched end-to-end model run was performed in this investigation.
