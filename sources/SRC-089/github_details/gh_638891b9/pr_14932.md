# [PR #14932] fix(backends): report cached-token usage during vLLM and SGLang streaming

## 正文

## Summary

Expose engine-reported cached-token usage before generation finishes in the vLLM and SGLang token-streaming adapters, without repeating unchanged usage metadata on every backend chunk.

Previously, both adapters attached `completion_usage` only at completion. Continuous-usage clients could receive generated-token totals but no cache details before then, including when they disconnected early.

Closes #14850 (vLLM) and #14938 (SGLang).

## Implementation

- Both adapters emit usage on the first usable report per choice, when prompt/cache metadata changes, and at completion. Explicit zero and unavailable cache counts remain distinct.
- vLLM maintains an O(1) request-wide cumulative completion total, advancing it as each choice is emitted so snapshots do not include later, un-emitted choices.
- SGLang captures usage before metadata-upload cleanup clears engine metadata and continues treating incomplete usage as optional.
- The Rust frontend already retains prompt/cache metadata and counts generated token IDs. A regression test verifies persistence and counting across sparse reports and interleaved choices.
- The optional Python vLLM and SGLang chat processors now retain sparse usage metadata and count generated tokens locally. Intermediate usage requires both `include_usage` and `continuous_usage_stats`; existing terminal/non-streaming usage behavior is retained. Metadata survives suppressed deltas and SGLang batched flushes.

For the synthetic 1,024-chunk, stable-cache example discussed in review, additional non-final MessagePack usage payload decreases from 114,194 bytes to 110 bytes (99.9%). This is an encoded-payload calculation, not a throughput or CPU benchmark.

Follow-up on the default-stream overhead questions:

The concern is valid: the current adapters construct usage even when the frontend will not expose intermediate usage. I calculated the incremental encoded payload size using synthetic values only: prompt_tokens=4096, cached_tokens=2048, and completion_tokens=128. This compares a minimal token chunk with and without the new completion_usage field.

| Scenario | Additional MessagePack bytes/chunk | Additional compact JSON bytes/chunk |
|---|---:|---:|
| Cache count available | 111 | 133 |
| Cache count unavailable, vLLM (details=null) | 94 | 115 |
| Cache count unavailable, SGLang (details omitted) | 71 | 86 |

For a synthetic 1024-output-token request with one token per chunk and stable positive cache details, summing the extra payload over the 1023 non-final chunks gives 114194 MessagePack bytes or 135975 compact JSON bytes. Final-chunk usage was already present before this PR. At a hypothetical 10000 chunks/s, the representative cache-hit payload delta is about 1.06 MiB/s (MessagePack) or 1.27 MiB/s (JSON).

These are payload-size calculations using Python msgpack and compact JSON encoders, not measurements of the Rust transport, CPU, model throughput, framing, or allocator behavior. Exact sizes depend on values and the surrounding message. The source codec supports both formats and defaults configured request-plane payloads to MessagePack. The Python path also adds a usage dictionary and, when cache details are present, a nested dictionary per emitted chunk.

A potential improvement is to emit usage on the first usable engine report, again when prompt/cache metadata changes, and at completion. The standard Rust frontend already retains prompt/cache details and counts output tokens itself. Comparing stable prompt/cache metadata rather than the ever-changing completion count would avoid repeating unchanged metadata while preserving late-arriving cache counts. This needs regression coverage for persistence and per-choice/disaggregated behavior before changing the emission policy.
