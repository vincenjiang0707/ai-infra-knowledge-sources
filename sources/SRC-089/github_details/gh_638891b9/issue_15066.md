# [Issue #15066] Emit an authoritative initial snapshot from discovery watches

source: https://github.com/ai-dynamo/dynamo/issues/15066
state: open | updated: 2026-09-21T16:10:26Z
labels: enhancement, language::rust, dynamo-runtime, discovery, runtime

## 正文

## Summary

Emit an authoritative initial snapshot from `Discovery::list_and_watch()` so a consumer opening or reopening a watch can reconstruct the complete current instance set without a separate `list()` call.

Follow-up to #14769, which explicitly leaves an initial `DiscoveryEvent::Resync` out of scope. That PR establishes the watch before returning and exposes backend resynchronization through `Resync`; initial state is still reported as individual `Added` events.

This is a discovery-contract enhancement, not a confirmed remaining production bug. #14769 notes that the earlier problematic consumer did not merge and that the stream-only watcher in main did not leak instances.

## Motivation

A reconnecting consumer may retain instances from an earlier connection:

1. The consumer knows about workers A and B.
2. Its discovery connection drops, and B disappears during the gap.
3. The consumer opens a new watch and receives `Added(A)`.
4. That event alone does not establish that B is absent. An authoritative initial `Resync([A])` lets the consumer replace its remembered membership.

An explicit empty snapshot is equally important: silence does not distinguish an empty registry from initial discovery that has not completed.

## Proposed scope

- Expose the storage/backend initial snapshot as a complete event and propagate it through discovery as an initial `DiscoveryEvent::Resync`.
- Define a consistent startup contract across the supported discovery backends, including KV-backed, Kubernetes, and mock discovery.
- Preserve snapshot/change ordering: a mutation during establishment must be reflected in the initial snapshot or a subsequent event, without a stale snapshot overwriting newer state.
- Audit existing discovery consumers for compatibility with an initial `Resync`, including consumers that currently rely on initial `Added` events or ignore `Resync`.
- Document how a reconnecting consumer replaces its state and how initialization failure differs from an authoritative empty snapshot.

## Design decision

Decide whether initial `Added` events remain alongside the initial `Resync` or are replaced by it. Document the event ordering and consumer migration requirements before changing the sequence. Retaining `Added` events must not cause consumers to double-count membership or perform duplicate registration work.

## Acceptance criteria

- [ ] Every successfully initialized watch emits an authoritative initial snapshot, including when the instance set is empty.
- [ ] A reconnecting consumer retaining A and B converges to A when B disappeared during the connection gap, without calling `list()` separately.
- [ ] Deterministic tests cover registration, removal, and updates during watch establishment; subsequent events cannot be overwritten by older initial state.
- [ ] Initialization failures are surfaced as failures rather than empty membership.
- [ ] Tests cover the startup contract across supported discovery backends and preserve existing resynchronization behavior.
- [ ] Existing consumers remain correct under the chosen initial `Added`/`Resync` ordering, with regression coverage for affected consumers.
- [ ] The `list_and_watch` documentation describes startup completion, ordering, and reconnect behavior.

Unrelated discovery cleanup, including removal of unused helpers, is outside this issue.
