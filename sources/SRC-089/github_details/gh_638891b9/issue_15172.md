# [Issue #15172] [BUG]: Grammar compile failures on worker return HTTP 500 due to request-plane msgpack deserialization errors

source: https://github.com/ai-dynamo/dynamo/issues/15172
state: open | updated: 2026-09-22T22:01:45Z
labels: bug, backend::vllm, frontend, router

## 正文

### Describe the Bug

When a `chat/completions` request carries a `response_format: json_schema` that xgrammar rejects on the **worker** (after passing frontend validation), the worker's error is not propagated cleanly to the frontend. The frontend fails to deserialize the worker's request-plane response and surfaces an opaque **HTTP 500** instead of a **400** with the grammar error.

This is a client-side schema error and should not be classified as a server failure.

We observe **two failure points on the same request**:

1. **Worker (grammar compile failure):** xgrammar rejects the schema during grammar compilation.
2. **Frontend (request-plane deserialization failure):** the frontend cannot msgpack-decode the worker's error response and returns a generic 500.

The exact frontend deserialization error varies by image/version:
- `invalid type: unit variant, expected newtype variant` (`response_bytes_len=175`)
- `Invalid FinishReason variant: 'error'` (`response_bytes_len=171`)

Both paths yield the same customer-visible **500**.

Related prior work that does **not** cover this case:
- #11377 / #11453 — fixed some xgrammar invalid-schema paths to return 400, but `oneOf` + empty `enum` still slips through
- #8549 / #13984 — fixed bare `finish_reason="error"` deserialization, but client still gets 500; different wire shape than the `unit variant` case
- #14467 — typed pre-stream errors on TCP; grammar compile failures on the worker still hit this gap

### Steps to Reproduce

**Prerequisites:** Dynamo vLLM deployment with `response_format: json_schema` on the xgrammar backend.

**Minimal repro payload** (invalid schema: empty `enum` nested inside `oneOf`, which bypasses frontend validation that catches top-level `enum: []`):

```bash
curl -sS -X POST "${ENDPOINT}/v1/chat/completions" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "<model>",
    "messages": [{"role": "user", "content": "x"}],
    "max_tokens": 16,
    "stream": true,
    "response_format": {
      "type": "json_schema",
      "json_schema": {
        "name": "bad",
        "strict": true,
        "schema": {
          "type": "object",
          "properties": {
            "value": {
              "oneOf": [
                {"type": "string", "enum": []},
                {"type": "null"}
              ]
            }
          },
          "required": ["value"],
          "additionalProperties": false
        }
      }
    }
  }'
```

Reproduced on multiple `dynamo-vllm` models (e.g. `deepseek-ai/DeepSeek-V4-Pro-0813`, `Qwen/Qwen3.8-27B`).

**Control** (same empty-enum bug class, caught early — does **not** trigger the worker/msgpack path):

```bash
# Replace the "value" property with a top-level empty enum:
"properties": {
  "status": {"type": "string", "enum": []}
},
"required": ["status"]
```

Control result: **HTTP 400** — `Grammar error: Unsatisfiable schema: required property 'status' is unsatisfiable`

### How to observe the two issues on one request

Use the minimal repro above and correlate logs by `request_id`.

#### Issue 1 — Worker grammar compile failure

Query worker pods (`*-w-*`):

```logql
{namespace="inference", pod=~".*-w-.*"} |= "Failed to compile grammar"
```

Expected worker log:
```
Failed to compile grammar for request <internal-id>
RuntimeError: enum array must not be empty
  at xgrammar/compiler.py compile_json_schema
  at vllm/v1/structured_output/backend_xgrammar.py compile_grammar
```

#### Issue 2 — Frontend request-plane deserialization failure

Query frontend pods (`*-f-*`):

```logql
{namespace="inference", pod=~".*-f-.*"}
  |~ "failed deserializing request-plane response|unit variant|Invalid FinishReason variant"
```

Expected frontend log (variant A):
```
failed deserializing request-plane response
  err=invalid type: unit variant, expected newtype variant
  codec="msgpack" response_bytes_len=175
```

Expected frontend log (variant B):
```
failed deserializing request-plane response
  err=Invalid FinishReason variant: 'error'
  codec="msgpack" response_bytes_len=171
```

### Expected Behavior

- **HTTP 400 Bad Request** with the xgrammar/grammar-compile error message (matching stock vLLM OpenAI server behavior for invalid schemas).
- No frontend msgpack deserialization failure.
- No impact on model success-rate SLOs for healthy traffic.

### Actual Behavior

| Mode | HTTP status | Body |
|---|---|---|
| `stream: true` | 200 then error frame, or 500 depending on path | `{"error":{"message":"Internal server error","code":500}}` or plain 500 JSON |
| `stream: false` | **500** | `{"message":"Internal server error","type":"Internal Server Error","code":500}` |

The worker correctly rejects the schema, but the error is lost on the request plane.

### Environment

- Dynamo stack: frontend (`*-f-*`) + worker (`*-w-*`) pods
- Worker orchestration: **Grove** (not LWS)
- Engine: `dynamo-vllm`
- Structured-output backend: `auto` (xgrammar)

### Suggested fix direction

1. Reject `oneOf` + empty `enum` (and similar) at the frontend before dispatch, consistent with top-level `enum: []` handling.
2. Ensure worker grammar-compile failures serialize as typed pre-stream errors that the frontend can decode on the request plane (msgpack), returning 400 with the worker's message.
3. Align error wire formats so `FinishReason`, `DynamoError`, and typed refusal variants do not regress across engine/image versions.

### Impact

- Invalid client schemas are misclassified as retryable **5xx**, inflating model success-rate alerts.
- SDKs/gateways retry doomed requests.
- Debuggability: bare 500 hides the actual grammar error from the caller.
