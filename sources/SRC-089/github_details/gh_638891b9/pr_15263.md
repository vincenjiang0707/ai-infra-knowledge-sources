# [PR #15263] fix(runtime): detect hung etcd members with channel keepalive; never abandon discovery watches

## 正文

## Overview:

A discovery watch on an etcd member that **hangs without closing its TCP connection** stays open but silent forever. No error or EOF arrives, so `monitor_watch_stream` never returns and the resync-after-reconnect path from #11146 never runs. Every instance removed after the hang stays in the consumer's view, so a frontend keeps routing to dead workers and routers and never learns about their replacements. Full description and a standalone repro are in #15262.

The cause is that `ClientOptions::default()` sets no HTTP/2 keepalive on the etcd channel, so a peer that stops answering is never detected. That is common in Kubernetes, where clients dial a headless service and a hung member is a live TCP connection to a pod IP.

## Details:

- **Channel keepalive by default** (`lib/runtime/src/transports/etcd.rs`): `ClientOptions::default()` adds `ConnectOptions::with_keep_alive(10s, 5s)`, merged with any auth or TLS options. A hung peer now fails the channel within about 15 s, the watch errors, and the existing reconnect + resync runs.
  - `ETCD_KEEPALIVE_INTERVAL_SECONDS` (`0` disables, which gives back today's behaviour) and `ETCD_KEEPALIVE_TIMEOUT_SECONDS` override the defaults. Parsing follows `ETCD_STARTUP_CONNECT_TIMEOUT_SECONDS`: a pure `keep_alive_from_values` helper that warns and falls back on invalid input, covered by the unit test `parses_keep_alive`.
  - An interval below etcd's default `--grpc-keepalive-min-time` (5 s) logs a warning, since the server answers it with GOAWAY `too_many_pings`.
- **Watch task never exits on stream-creation failure**: `Err(_) => return` after `new_watch_stream` becomes a retry loop using the existing `watch_retry_backoff`. It stops only when the receiver is dropped or the runtime is cancelled. Without this, a keepalive-detected failure lasting longer than `new_watch_stream`'s 10 s reconnect deadline would turn a stale watch into a dead one.
- `config/environment_names.rs`: the two new variables, added to the registry list so `test_no_duplicate_env_var_names` / `test_naming_conventions` cover them.

**Validation** (3-member etcd v3.5.21 in Docker, `docker pause` on the member serving the watch, harness in #15262):

| build | after the freeze |
|---|---|
| `main` @ `a76e12e65` | view keeps deleted keys and misses the new one for the whole freeze; nothing logged; catches up only on unpause |
| this PR, `ETCD_KEEPALIVE_INTERVAL_SECONDS=0` | same as `main` |

- `cargo test -p dynamo-runtime --lib -- transports::etcd::unit_tests config::environment_names`: 7 passed.
- `cargo fmt --check` clean. `cargo clippy -p dynamo-runtime -- -D warnings` shows no findings in the changed files. Its only error is the existing unused `join_reuseport` in `pipeline/network/quic_response.rs`, which also fails on unmodified `main` on macOS.
