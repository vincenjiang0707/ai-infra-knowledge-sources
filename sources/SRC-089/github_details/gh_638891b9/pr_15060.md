## Overview:

Automated dependency upgrade to TensorRT-LLM `1.3.0rc27`, plus the changes the upgrade turned out to need: a fix in the dpkg license generator, a correction to the DALI block and its note, an ignore list for new deprecation warnings, and a per-architecture Open MPI selection with its settings and login-profile fixes, a hostname workaround so Open MPI 5 can start workers on arm64, and tests that guard the MPI setup.

## Details:

### The upgrade (`72028898`, `a3bda421`)

`container/context.yaml` runtime tag, the `pyproject.toml` pin, both per-arch baseline SBOMs re-captured against `1.3.0rc27`, the DALI pin moved from 2.1.1 to 2.2.0 to match the base image, and the release and compatibility pages. The manifest also closes a gap on `main`, where the baseline SBOM recorded `1.3.0rc25` while `container/context.yaml` recorded `1.3.0rc26`.

### The licenses stage (`a95a2263`, `c4e8e573`, `a9c56d28`)

`trtllm-runtime` and `trtllm-runtime-efa` both stopped at:

```
[dpkg] dpdk-community@26.03.0.5-1: license is UNKNOWN and policy.licenses.unknown = 'deny' (SPDX: 'UNKNOWN')
```

The rc27 base image installs `dpdk-community` and `doca-sdk-common` while it is built, and removes them again without purging them. dpkg keeps both entries in the `config-files` state: it deleted the packages' files and kept their conffiles, and those still ship. `doca-sdk-common` leaves `/etc/ld.so.conf.d/doca-runtime-<arch>-linux-gnu.conf` and `/etc/profile.d/doca-runtime.sh`, and `dpdk-community` leaves `/etc/ld.so.conf.d/dpdk-<arch>-linux-gnu.conf`. syft, which captures the baseline SBOMs, catalogs installed packages only, so both entries survive baseline subtraction and reach the policy gate. rc25 and rc26 carried the same pair as `doca-sdk-common` and `mlnx-dpdk`, and both have a `license_overrides.yaml` entry, which is why the gate passed until upstream renamed the DPDK package.

`dpdk-community` has no license the generator can read: the package ships no copyright file at all. The `dpdk-community_26.03.0.5-1_amd64.deb` from the public DOCA 3.5.0 repository has none, and its only SPDX tags are seven `BSD-3-Clause` tags. `a9c56d28` adds a `BSD-3-Clause` override, like the existing `mlnx-dpdk` entry.

The generator now reads each entry's dpkg state (`${db:Status-Status}`). It skips a `config-files` entry only when dpkg lists its conffiles and none of them is on disk, and it logs every kept entry with its surviving conffiles. An earlier version on this branch (`a95a2263`) skipped every `config-files` entry. Review showed that their conffiles ship, so `a9c56d28` narrowed the skip.

### The DALI block (`eed14723`)

rc27 ships DALI 2.2.0 in the base image, so the pinned install is a no-op and three statements in the note above the block described the old base. The note is corrected, and one hole in the code is closed: the decoder enumeration finds its library with `find ... -name 'libavcodec*.so*'` and loops over the result, so an empty match checked nothing and exited 0. A release that links the codec into a differently named library, which is what PyNvVideoCodec 2.2.0 does three blocks below, passed that guard while shipping decoders. Both the `runtime_full` block and the post-overlay guard now fail on an empty match.

### The codec waiver (`24344f20`)

Text only. The DALI waiver in `container/compliance/policy/codec_policy.yaml` ends with "Re-measure when the vendored version moves." It moved, so the rc27 measurement is recorded there. Two statements in the same note needed the same pass: it said the Dockerfile pins `nvidia-dali-cuda130>=2.1.1`, where the pin is exact and now reads `==2.2.0`, and it said one guard runs "after the upgrade", where that install is a no-op.

### The rc27 deprecations (`04cdba0b`)

Three trtllm tests failed at import time, not on an assertion: `cutlass.utils.LayoutEnum is deprecated`. The rc27 base ships nvidia-cutlass-dsl `4.8.0.dev0` where rc26 shipped `4.6.2`, and it moves names out of `cutlass.utils` and `cutlass.arch` behind a module `__getattr__` that warns. flashinfer is `0.6.18` in both images and still reads the old locations, some in class-body annotations that run at import time, as does TensorRT-LLM's own `cute_dsl_kernels`. Under `filterwarnings = ["error", ...]` the import raises. Two ignore entries cover all four warnings the import gains between the two images.

### The fourth glob loop (`f502244d`)

This file has four loops that enumerate a vendored FFmpeg library. The DALI commit above closed three. This closes the post-overlay PyNvVideoCodec one, with the counter its own sibling in `runtime_full` already uses.

### The MPI path (`1ff5387a`, `f04ff8d1`, `69d62c63`, `2111e3f2`, `fc14cb34`, `7b05507e`)

rc27 repointed `/opt/hpcx/ompi` and `/usr/local/mpi` from `ompi4` to `ompi5`, so the image defaults to Open MPI `5.0.10rc2` where rc26 defaulted to `4.1.9a1`. TensorRT-LLM spawns its executor ranks with `MPI.COMM_SELF.Spawn`. On amd64 that spawn fails on `ompi5` with `ucp_ep_create(proc=0) failed: Destination is unreachable`, the worker never binds its gRPC port, and the serving tests wait out their deadlines. On arm64 `ompi4` is not an option: the base image's `libtorch_cpu.so` needs `ompi_mpi_short_float`, which only `ompi5` defines.

`1ff5387a` links `/opt/dynamo/mpi` to `ompi4` on amd64 and to `ompi5` on arm64. The `PATH`, `LD_LIBRARY_PATH` and `OPAL_PREFIX` entries name that link, in `runtime_full` and in `pre_runtime`, which the shipped image builds on. Transitional: delete the link and the entries when upstream's `ompi5` can spawn.

`f04ff8d1` completes the switch to `ompi4`. The base image edits `etc/openmpi-mca-params.conf` only in the Open MPI it selects itself, so `ompi4` kept `hwloc_base_binding_policy = core` and `btl = self`. With `core`, `import tensorrt_llm` pins the process and every child to CPUs 0-1. With `btl = self`, `mpirun --mca pml ob1`, which the operator's multi-node launch uses, cannot connect two ranks. The commit applies the base image's two edits to the selected MPI and fails the build if either setting survives.

`69d62c63` makes the dev images' login profile, `container/dev/50-framework-paths.sh`, prefer `/opt/dynamo/mpi`. It used to reset login shells, SSH sessions and later dev-image RUN steps to `/opt/hpcx/ompi`, which is ompi5 in rc27.

`2111e3f2` replaces the affinity test with `tests/dependencies/test_trtllm_mpi.py`, which checks the whole selection in the built image: the link's target per architecture, the library mpi4py loads, a `MPI.COMM_SELF.Spawn`, a two-rank `ob1` launch, and the CPU affinity.

`fc14cb34` fixes what that spawn check found on arm64. Open MPI 5 cannot spawn from a singleton when the hostname length plus the digits of its pid exceeds 37, and TRT-LLM starts its workers that way. CI's pod names are 46 (arm64) and 50 (amd64) characters long. amd64 avoids the defect by running ompi4, which is likely the real reason the serving tests failed on ompi5 there. arm64 cannot, so where the image selects ompi5, a `.pth` line imports `_dynamo_pmix_hostname` when Python starts. It sets `PMIX_HOSTNAME` to a short name only in processes that no MPI launcher started, on hosts whose names are longer than 30 characters. Ranks that mpirun or prte start get `PMIX_HOSTNAME` from the launcher and keep the real hostname. A real multi-node launch is not verified: a Python process that runs a multi-node `mpirun` itself would pass the short name on to it. The operator's multi-node launch starts `mpirun` from `/bin/sh`, so the hook does not run there.

The cause is in Open MPI itself: it passes the singleton's name to `prte` through a 50-byte print buffer, so a long name is cut short and `prte` registers the wrong one. It is fixed upstream in open-mpi/ompi#14398 (v5.0.x backport: open-mpi/ompi#14409), and Mellanox/ompi's `v5.0.x_hpcx` branch has had the fix since Mellanox/ompi#61. No release has it yet: Open MPI 5.0.11 does not, and TRT-LLM 1.3.0rc28 still ships HPC-X v2.50 with Open MPI 5.0.10rc2 and fails the same spawn. `7b05507e` records when to remove each part of the workaround. Delete the hook once a base image's HPC-X passes a spawn with a 46-character hostname without it. Delete the amd64 Open MPI 4 selection only when Open MPI 5 also spawns on amd64 without the hook, in CI and on a host with extra network interfaces. Tracked in NVIDIA/TensorRT-LLM#19607.

### The CUDA IPC test (`7a57fd6a`, `d8b48f54`)

`7a57fd6a` passes the consumer's result through the queue as a numpy array, reports child errors, and always cleans up its processes. It also built the expected tensor with a CPU float16 `arange`. Past 2048 that rounds differently from the producer's CUDA `arange`, so the assertion failed whenever the transfer worked. `d8b48f54` builds `expected` on the GPU again.

### The LD_PRELOAD order (`d4bfa7d9`)

The ENV block named `/opt/dynamo/libstdc++.so.6` in `LD_PRELOAD` before the RUN that creates it. Every command in between printed `ERROR: ld.so: object '/opt/dynamo/libstdc++.so.6' from LD_PRELOAD cannot be preloaded`. The RUN now comes first.

### The merge of main

main cut v1.5.0, which rewrote the three release tables this branch touches. `docs/fern/components/releases.data.ts` is the source of truth and merged cleanly with both sides. The two conflicted pages are generated from it, so they were taken from main and regenerated rather than hand-resolved, and `gen_llms_tables.py --check` reports every marker-spliced page unchanged.

## Where should the reviewer start?
