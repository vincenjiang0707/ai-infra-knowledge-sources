# [Issue #10171] DGD lacks NUMA/PCI-root topology awareness for prefill/decode placement (~50% throughput loss, ~30x latency)

source: https://github.com/ai-dynamo/dynamo/issues/10171
state: open | updated: 2026-09-23T05:17:42Z
labels: enhancement, deployment::k8s, performance, router, operator

## 正文

## Summary

`DynamoGraphDeployment` has no NUMA / PCI-root topology awareness when placing `vllmPrefillWorker` and `vllmDecodeWorker` replicas on multi-root GPU nodes. Because the k8s device plugin allocates GPUs lowest-index-first, both prefill replicas can land on GPUs sharing a single PCI root, forcing decode workers on the opposite root to traverse `PCIe -> CPU -> PCIe` for every NIXL transfer. This produces a ~50% throughput regression and ~30x higher per-batch latency vs. a baseline where prefill is split one-per-root.

## Environment

- Dynamo runtime: 1.0.1
- Deployment: `DynamoGraphDeployment vllm-32b`
- Topology: 2 prefill (TP=1) + 4 decode (TP=1) on one `a3-highgpu-8g` node (8x H100 SXM5)
- PCI layout:
  - GPUs 0-3 on root 0 (bus `04/05/0A/0B`)
  - GPUs 4-7 on root 1 (bus `84/85/8A/8B`)
  - Cross-root NIXL traverses CPU/QPI; same-root uses intra-NUMA PCIe.
- Workload: Locust `u=64`, `OSL=1024`, `ignore_eos=true`, FP8 weights, `--no-enable-prefix-caching`, `DYN_ROUTER_MODE=kv`

## Repro / Observation

Same workload, same code, same node - the only variable is which PCI roots the prefill pods land on.

- **Bad placement** (both prefill on root 0, decode split across roots): `kv_consumers` on the *opposite* root from both `kv_producers` become the bottleneck. Their NIXL `cudaIpcOpenMemHandle` + `cudaMemcpyAsync` path goes `PCIe -> CPU -> PCIe`.
  - ~50% throughput loss
  - ~30x higher per-batch latency
- **Good placement** (one prefill per PCI root): baseline throughput / latency.

Placement is non-deterministic from the user's perspective - it depends on the device plugin's lowest-index-first allocation order.

## Root cause

1. The underlying NIXL transfer cost is dominated by IOMMU / cross-root PCIe traversal on this hardware.
2. DGD has no scheduling hint / affinity policy to keep `kv_producer` and `kv_consumer` workers on the same PCI root (or at least balanced one-per-root for the prefill side).

## Ask

Add NUMA / PCI-root affinity awareness to `DynamoGraphDeployment` placement, e.g.:

- A topology policy on the worker spec (`spread-across-pci-roots`, `pack-within-pci-root`, or explicit affinity between producer/consumer roles).
- Integration with the k8s device plugin's topology hints (or NFD labels for GPU<->PCI-root mapping) so the scheduler can place prefill/decode pairs intra-root when possible.
- At minimum, documentation of the failure mode and a manual workaround (e.g. `nodeAffinity` + per-root extended resources) until the scheduler is topology-aware.

### yankay · 2026-06-02

Just for discussion / to throw out an initial idea.

I’m trying to better understand how the Dynamo project currently thinks about NUMA-aware placement.

One possible direction is to treat this as a DRA-backed device-topology placement issue, not just a NIXL issue. This seems related to [Grove GREP-244 Story 3: NUMA-Aware GPU Benchmarking](https://github.com/ai-dynamo/grove/tree/main/docs/proposals/244-topology-aware-scheduling#story-3-numa-aware-gpu-benchmarking), which calls out NUMA-aware GPU allocation when selecting a subset of GPUs from an 8-GPU node. Here we have the disaggregated inference version of the same problem: prefill/decode workers need PCIe-root / NUMA-aware placement to avoid cross-root KV transfers.

Node-level topology constraints alone may not be enough because the bad placement can happen inside one node. If the GPU DRA driver exposes a standard attribute like [`resource.kubernetes.io/pcieRoot`](https://github.com/kubernetes/kubernetes/pull/132296), DGD/Grove could potentially translate a role-aware policy into ResourceClaims, e.g.:

- spread prefill workers across PCIe roots;
- prefer/require decode workers on the same PCIe root as their prefill producer;
- publish the allocated PCIe-root as worker topology metadata for KV routing.

So DRA `pcieRoot` would not fix this automatically, but it might be a useful lower-level primitive. Curious how the Dynamo maintainers currently view NUMA-aware / PCIe-root-aware placement, and whether this is expected to live in DGD, Grove, DRA integration, or some combination of these layers.
