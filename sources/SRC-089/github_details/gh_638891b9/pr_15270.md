# [PR #15270] fix(frontend): unblock the request path — render chat templates off the runtime, make the CallHome listen backlog configurable

## 正文

## Overview:

Two independent frontend fixes, both found while investigating an intermittent warmup failure on a 2,934-concurrency agentic workload. They are separable and can be split on request, but they are the two halves of one story: a starved tokio runtime, and the accept queue that starved alongside it.

1. **`fix(runtime)`** — a listen-backlog regression. On 2026-08-24 commit `138668ba94` ("feat(mm-routing): add Kimi K3 support", #13371) bumped the workspace pin from `mio = "=1.1.1"` to `"=1.2.2"` as an incidental lockfile refresh. mio 1.1.1 passed `-1` on Linux (`sys/mod.rs:132`, *"Silently capped to /proc/sys/net/core/somaxconn"*); mio 1.2.2 hardcodes `128` (`net/tcp/listener.rs:92`). Every `dynamo-runtime` listener silently lost **32x** of accept-queue depth on hosts with `somaxconn = 4096`. #15080 restored this for the HTTP listener; this does the same for the CallHome listener.

2. **`fix(frontend)`** — restores the closed PR #15092. `apply_template` renders the chat template **synchronously on a tokio worker thread**. Tokenization was already moved to the blocking pool for exactly this reason; the render was not.

## Details:

### Why these two are related

`encode_with_timing` already carries the diagnosis in a comment:

> *"Offload the CPU-heavy BPE encode to the bounded blocking pool instead of running it on the async event loop. For long prompts at high concurrency, a synchronous encode here stalls the frontend tokio runtime for seconds, **starving the I/O tasks that share the runtime**."*

The template render sits on the same request path and was never offloaded. When a few thousand long conversations arrive together, the renders saturate the worker pool and hyper's I/O tasks stop being scheduled. Two things follow:

- the **accept loop** starves, so the accept queue fills — which is why the shallow backlog became visible at all
- the **body-read tasks** starve, so request bodies sit unread, receive windows close, and clients with a TCP user timeout abort mid-upload

The backlog change makes the queue deep enough to survive a burst; the render change stops the burst from stalling the runtime in the first place.

### Every production listener, and why only one changes

I enumerated every production `TcpListener::bind` on `main` and measured accept-queue depth (`sk_ack_backlog` from `/proc/net/tcp`, sampled every 500 ms) on a 2,934-concurrency disaggregated run. Across **160** and **407** distinct listening ports on the frontend node, only three ever held a non-empty accept queue — and one of those was `slurmd`.

| # | site | role | measured peak depth | needs raising? |
|---|---|---|--:|---|
| — | `llm/http/service/service_v2.rs` (HTTP) | client -> frontend | **2,569 / 2,247 / 1,976 / 1,081** | already fixed by #15080 |
| **1** | `runtime/pipeline/network/tcp/server.rs` | **CallHome; one connection per response stream** | **404, 669, 21** | **yes — this PR** |
| 2 | `runtime/pipeline/network/ingress/shared_tcp_endpoint.rs` | request plane, worker-side; client pooled at 100/host | not measured (worker-side); O(workers) | no |
| 3 | `runtime/system_status_server.rs` | status/metadata HTTP | **0 for the entire run** | no |
| 4 | `llm/http/service/service_v2.rs:1082` | RL worker discovery; opt-in, `rl_router` is `None` unless configured | absent from the deployment | no |
| 5 | `llm/block_manager/metrics_kvbm.rs` | standalone KVBM Prometheus `/metrics` | absent; scrape rate | no |
| 6 | `llm/kv_dc_relay/wan/grpc/server.rs` | KV DC relay gRPC; HTTP/2 multiplexes many streams per connection | absent; O(peers) | no |

Sites 2-6 regressed identically, but none has a load-proportional accept rate and none was observed to queue at all. This PR stays minimal rather than converting them speculatively; they can be revisited if a workload is shown to exercise them.

CallHome is the exposed one because every response stream is its own connection — `tcp/client.rs` `create_response_stream` -> `TcpStream::connect`, no pooling, called once per request from `ingress/push_handler.rs`. The request plane, by contrast, is pooled client-side (`egress/tcp_client.rs`, `DEFAULT_POOL_SIZE = 100` per host).

### Field measurement

Same workload, same topology, same hardware; only the frontend build differs. The backlog was raised via an `LD_PRELOAD` `listen(2)` shim so it could be held constant across arms.

| arm | HTTP + CallHome backlog | build | runs passed |
|---|---|---|---|
| A | 128 (stock mio) | stock | **0 / 3** |
| B | 4096 | stock | **3 / 9** (33%) |
| C | 4096 | **+ the render fix** | **5 / 6** (83%) |

| comparison | Fisher one-tailed |
|---|---|
| A -> B — backlog alone | **p = 0.38** (no detectable effect) |
| B -> C — adding the render fix | **p = 0.084** |

**The backlog change alone did not measurably reduce failures.** That is expected under the mechanism above: a deeper queue does not help when the accept loop is not draining it. It is included here as regression restoration, not as a fix for this failure.

Caveat, stated plainly: arm C's build also carried #15080 and an unrelated fix, and its base was newer than arm B's, so it implicates the render change without isolating it. n = 6, and p = 0.084 is suggestive rather than conclusive.

### Why #15092 was closed, and why this revisits it

#15092 was closed on the assessment "no measurable effect", from a throughput comparison (191,689.0 vs 191,682.3 tok/s/GPU) between two runs that **both already passed**. Throughput on passing runs cannot detect a change in how often runs *fail*. Measured against the failure rate it was written to address, the effect is the 33% -> 83% above.

## Where should the reviewer start?

- `lib/llm/src/preprocessor.rs` — `off_runtime` and its single call site in `preprocess_request_with_options`
- `lib/runtime/src/pipeline/network/tcp.rs` — `DEFAULT_TCP_LISTEN_BACKLOG`, `parse_tcp_listen_backlog`, `bind_listener`
- `lib/runtime/src/pipeline/network/tcp/server.rs:763` — the single call-site change
- `lib/runtime/src/config/environment_names.rs`, `components/src/dynamo/common/snapshot/constants.py`, `deploy/operator/internal/checkpoint/compatibility.go` — `DYN_TCP_LISTEN_BACKLOG` registration and snapshot-restore allowlists

A note on TCP semantics, because it is easy to state backwards: with the default `net.ipv4.tcp_abort_on_overflow=0`, an overflowing accept queue causes the kernel to **drop the client's final ACK and fall back to SYN-ACK retransmission** (1s/3s/7s), so the symptom is added connection latency and, once `tcp_synack_retries` is exhausted, connection failure. A prompt RST is sent only with `tcp_abort_on_overflow=1`. Verified directly: 3,000 dials at backlog 128 with no acceptor produced `ListenOverflows +11484` and **zero** client-side RSTs.

`block_in_place` is used rather than `spawn_blocking` because `apply_template` borrows the request generically (`&R`), so there is no `'static` value to move into a spawned closure.
