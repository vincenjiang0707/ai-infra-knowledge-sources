# [Issue #15187] DEP: Cross-replica PolicyClass fairness contract

## 正文

## Summary

PolicyClass queue and deficit-round-robin (DRR) state is local to each router. In a two-frontend reproducer, a configured 4:1 `premium:regular` share remained near 4:1 when each replica received demand from both classes, but fell near 1:1 when each class reached a different replica.

This DEP has two phases. Phase 1 documents the current router-local contract so deployments do not infer an aggregate guarantee Dynamo does not provide. Phase 2 pursues an ingress-independent aggregate weighted-share guarantee. This DEP recommends one logical PolicyClass scheduler owner per scheduling domain as the first implementation.

## Current behavior

Each router maintains its own PolicyClass queues, DRR deficits, ring position, and counters. Replica synchronization does not provide a shared PolicyClass queue or DRR budget.

For this discussion, a *scheduling domain* is the contention scope formed by PolicyClasses competing for the same eligible worker capacity. The eligible worker set defines the capacity boundary. The PolicyClasses are the participants.

## Evidence

The reproducer used one shared CPU Mocker worker, identical worker eligibility, equal-cost 512-token prompts, replica synchronization, and a 4:1 `premium:regular` policy.

| Topology and ingress              | Premium booked cost | Regular booked cost | Equivalent requests |
| --------------------------------- | ------------------: | ------------------: | ------------------: |
| One frontend                      |              130560 |               33280 |              255:65 |
| Two frontends, balanced per class |              133120 |               34304 |              260:67 |
| Two frontends, direct skew        |               83456 |               82944 |             163:162 |
| Two frontends, swapped skew       |               82944 |               83456 |             162:163 |

Direct skew sends `premium` only to frontend A and `regular` only to frontend B. Swapped skew reverses the placement. Both skewed cases remain near 1:1.

These are successful-booking scheduling-cost counters from a bounded observation window. Prometheus polling can include bookings beyond the sampler’s 320-booking target. The result establishes topology-dependent behavior in this setup. It does not establish a general fairness bound under balanced ingress.

## Proposed current contract

PolicyClass scheduling state and its weighted scheduling decisions are local to each router. Dynamo makes no ingress-independent aggregate PolicyClass share guarantee across router replicas today.

Aggregate behavior depends on how each class’s scheduling-cost demand and backlog reach those replicas. Balancing total HTTP request counts is not enough to ensure that competing classes reach each local scheduler. Dynamo does not enforce per-class ingress distribution.

## Phase 1: Document Current Semantics

Document this behavior and its deployment assumption. A documentation PR carries the wording and focused validation. The booked scheduling-cost metric remains a separate, reviewable change if router owners find it useful.

Phase 1 does not change scheduling behavior. It makes the present limitation explicit and establishes the contract that Phase 2 replaces.

## Phase 2: Cross-Replica Fairness

Phase 2 aims to provide ingress-independent aggregate PolicyClass fairness for each scheduling domain. Its initial scope is an isolated eligible worker set and every PolicyClass that can book work on it. No PolicyClass outside the domain may book a worker in that set. A participating PolicyClass may not book outside it. Classes with overlapping eligibility sets require a later design.

For continuously backlogged classes in one Phase 2 domain, the configured weighted share must hold in successful-booking scheduling-cost units over an exact fixed window, within a documented DRR deviation bound. The bound must account for the maximum request cost and outstanding reservations.

This DEP recommends one logical scheduler owner per domain as the first implementation. Phase 2 is not ready for implementation approval until the domain eligibility rule and the measurable share bound are specified.

The recommended implementation uses one logical scheduler owner per domain:

1. A forwarding router classifies a request and sends its admission intent to the domain owner.
2. The owner is authoritative for the domain's PolicyClass queues, DRR deficits, ring position, and reservations.
3. The owner selects and books work. The forwarding router sends the selected request to the worker.
4. If the owner is unavailable, admission returns an explicit retriable error rather than falling back to independent local scheduling and weakening the guarantee.

Phase 2 deliberately excludes replicated DRR budgets, automatic owner election, and splitting one scheduling domain across multiple owners. Those are scale and availability extensions. Revisit them after the initial single-owner implementation establishes the fairness contract.

The Phase 2 PR must establish the guarantee with an exact successful-booking scheduling-cost window across the existing one-frontend, balanced, direct-skew, and swapped-skew cases. The test placement and harness mechanics belong in that PR.

## Requested decision

**Do you agree with this phased direction: document the router-local contract and ingress assumption in Phase 1, then specify and pursue ingress-independent aggregate PolicyClass fairness in Phase 2?** I recommend yes.

This decision approves the product direction and sequencing. It does not approve a Phase 2 implementation and only recommends the single-owner design.
