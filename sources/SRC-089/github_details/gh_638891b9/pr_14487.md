# [PR #14487] fix(vllm): advertise reachable Mooncake bootstrap address

## 正文

## Overview

Fix cross-node vLLM prefill/decode disaggregation with `MooncakeConnector` by ensuring Dynamo advertises a prefill bootstrap address that the decode worker can reach.

Previously, Dynamo reused vLLM’s local Mooncake bootstrap address. In external or hybrid load-balancing mode, that address can be `127.0.0.1`, causing a decode worker in another pod to contact its own loopback interface instead of the prefill worker.

## Details

- Separate the Mooncake bootstrap address advertised to remote decode workers from the address used locally by the prefill worker.
- Use the configured reachable prefill host when constructing `remote_bootstrap_addr`.
- Preserve the Mooncake bootstrap port and existing transfer metadata, including `transfer_id` and `remote_engine_id`.
- Add regression coverage confirming that a reachable address is advertised instead of `127.0.0.1`.
- Preserve existing behavior when no advertised-host override is configured.

## Where should the reviewer start?

- `components/src/dynamo/vllm/kv_connector_protocols.py`
  - Review how `MooncakeConnectorProtocol` selects the host used in `remote_bootstrap_addr`.
- `components/src/dynamo/vllm/tests/test_vllm_kv_connector_protocols.py`
  - Review the regression cases for loopback and explicitly configured advertised addresses.
- `deploy/operator/internal/dynamo/backend_vllm.go`
  - If included in this PR, review how the reachable pod address is supplied to the vLLM prefill container.

### P1 — avoid rolling unrelated workloads on an operator-only upgrade

The [unconditional prefill env default](https://github.com/ai-dynamo/dynamo/blob/6d2a62c57d502fd55ea74bf4f2d5cf00edbbd826/deploy/operator/internal/dynamo/backend_vllm.go#L54-L62) also applies to existing NIXL/non-Mooncake vLLM prefill Deployments. On reconciliation, the new env entry changes the rendered pod template; the Deployment controller applies that spec change and Kubernetes rolls the pods even when the DGD and runtime image are unchanged. This conflicts with the operator upgrade contract.

Please narrow the default to the relevant connector and preserve existing workloads through origin-version/explicit opt-in compatibility behavior, or an explicit documented migration. Connector filtering alone still leaves existing Mooncake workloads subject to operator-only rollout. Add an old-render → new-reconcile regression; calling the new renderer twice proves idempotence, not upgrade preservation.

### P2 — serialize or reject IPv6 advertised hosts correctly

The operator supplies a raw `status.podIP`, but [URL construction](https://github.com/ai-dynamo/dynamo/blob/6d2a62c57d502fd55ea74bf4f2d5cf00edbbd826/components/src/dynamo/vllm/kv_connector_protocols.py#L104-L115) simply interpolates it. With `fd00::17`, the result is `http://fd00::17:8998`, not `http://[fd00::17]:8998`; port parsing fails. Please add IPv6-safe host serialization/validation and a regression for raw IPv6 input. If IPv6 is outside the supported connector contract, reject it clearly rather than publish a malformed URL. This is a URL-construction finding, not a claim that end-to-end Mooncake IPv6 is supported.
