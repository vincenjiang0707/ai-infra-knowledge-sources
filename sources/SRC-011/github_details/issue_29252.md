# [Issue #29252] Misc. bug: CPU f32 GELU uses GGML_GELU_FP16, loses precision

source: https://github.com/ggml-org/llama.cpp/issues/29252
state: open | updated: 2026-09-22T04:10:09Z
labels: 

## 正文

### Name and Version

ggml v0.24.0, commit 456172e.

### Abstract

I was porting laya-vision to ggml, and found the network lose precision compared to the PyTorch version. (the project: https://git.sr.ht/~iacore/ggml-question)

It turns out that f32 GELU on CPU converts input to FP16 first, which loses precision over actual f32 GLEU.

### Reproduction repo

Here is a standalone program linked directly against ggml, CPU backend, no model or server
involved.

https://github.com/iacore/ggml-gelu-f16-repro

### Operating systems

Linux

### Which llama.cpp modules do you know to be affected?

libllama (core library)

### Command line

```sh
cc -O2 -I <ggml>/include repro.c -o repro \
   -L <ggml-build>/ggml/src -lggml -lggml-base -lggml-cpu -lm
LD_LIBRARY_PATH=<ggml-build>/ggml/src ./repro
```

The program builds one `GGML_OP_GELU` and one `GGML_OP_GELU_ERF` over the same f32 input tensor,
runs the graph on the CPU backend, and compares both against the exact float32 formula.

### Problem description & steps to reproduce

`src/ggml-cpu/vec.h:46` defines `GGML_GELU_FP16` unconditionally, and under it the **f32** GELU
does not evaluate its formula. It rounds the input to half precision, indexes a table, and converts
the result back:

```c
#ifdef GGML_GELU_FP16
inline static void ggml_vec_gelu_f32(const int n, float * y, const float * x) {
    uint16_t t;
    for (int i = 0; i < n; ++i) {
        if (x[i] <= -10.0f) {
            y[i] = 0.0f;
        } else if (x[i] >= 10.0f) {
            y[i] = x[i];
        } else {
            ggml_fp16_t fp16 = GGML_CPU_FP32_TO_FP16(x[i]);
            memcpy(&t, &fp16, sizeof(uint16_t));
            y[i] = GGML_CPU_FP16_TO_FP32(ggml_table_gelu_f16[t]);
        }
    }
}
```

The table is filled at `src/ggml-cpu/ggml-cpu.c:3883` with
`GGML_CPU_FP32_TO_FP16(ggml_gelu_f32(f))`. So one element takes x -> f16 -> gelu -> f16 -> f32:
rounded to half precision twice, once on the way in and once on the way out.

`GGML_GELU_QUICK_FP16`, defined on the line below, means `ggml_gelu_quick` gets the same treatment.
`GGML_OP_GELU_ERF` is not affected: `ggml_vec_gelu_erf_f32` has no table path.

Measured against the exact float32 form of the same formula, 4096 values over the stated range:

| input range | max abs | max rel | elements over 1.2e-4 rel |
| --- | ---: | ---: | ---: |
| [-12, 12] | 3.9024e-3 | 3.6916e-3 | 1611 / 4096 |
| [-10, 10] | 3.90e-3 | 2.70e-3 | 1917 / 4096 |
| [-5, 5] | 1.95e-3 | 3.65e-3 | 2548 / 4096 |
| [-1, 1] | 3.20e-4 | 7.52e-4 | 2833 / 4096 |

Control on the same inputs: `GGML_OP_GELU_ERF` against the erf formula gives **0.0000e+00** rms
relative error, bit-exact.

The error is broad rather than localized -- roughly 4e-4 relative on nearly every element, which is
f16 epsilon (2^-11 = 4.9e-4). It is not one or two bad elements.

I have not traced which models in this repository route through `GGML_OP_GELU` in f32 on CPU, or by
how much their output changes. The error is on the order of the activation's own precision, so it
may well be an acceptable trade for avoiding a `tanhf` per element. I am reporting the behavior and
the test's blind spot, not claiming model output is visibly wrong.

### Why test-backend-ops does not catch it

`tests/test-backend-ops.cpp:3940` sets the GELU tolerance and states an assumption the code does not
satisfy:

```c
// gelu shader uses exp form, CPU uses tanhf
default:            return op == GGML_UNARY_OP_GELU ? 5e-7 : 1e-7;
```

"CPU uses tanhf" is not true under `GGML_GELU_FP16`.

Separately, `test_unary_mul` compares with `err()`, which is `nmse(...)`
(`test-backend-ops.cpp:298`, `:1191`) -- a signal-to-noise ratio, not a max error. The measured NMSE
is 2.9e-8, seventeen times under the 5e-7 tolerance, so the test passes.

That is the wrong metric for this shape of error rather than a tolerance that is merely loose. NMSE
catches one large absolute error loudly; a broad, small *relative* error contributes about
(relative error)^2 and disappears. This is the second shape.

A max-relative-error check, or an NMSE bound chosen for f32 rather than f16, would have caught it.

### First Bad Commit

Not bisected. `GGML_GELU_FP16` has been unconditional for a long time and this is not a recent
regression.

### Relevant log output

```

```
