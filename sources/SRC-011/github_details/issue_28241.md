### Problem description & steps to reproduce

### Summary

With `-cmoe` (CPU MoE offload) on a Turing GPU, `llama-server` reliably crashes with
`illegal memory access` when the prompt is **exactly 94 tokens** (`prompt_n` as reported by the
server, which is 86 tokens as returned by `/tokenize` plus 8 for the chat template).
93 tokens is fine, 95 tokens is fine. Content, language and topic are irrelevant — only the
exact length matters.

The crash always happens during prompt processing, 100–600 ms after `launch_slot_`, and never
during generation. The CPU-only build handles the same prompt without any problem.

### Steps to reproduce

1. Start the server:

```
llama-server.exe -m Qwen3-Coder-Next-UD-Q4_K_S.gguf \
  -c 32768 -t 6 -lm none -np 1 -ngl 99 -cmoe \
  --host 127.0.0.1 --port 61129
```

2. Send this prompt as a single user message with `"cache_prompt": false`
   (86 tokens per `/tokenize`, 438 characters):

```
Write a short PHP function that reads a list of numeric values from a text file and returns the average, the minimum and the maximum of those values. Explain briefly what to watch out for when the input file is empty, when it contains invalid or non numeric rows, and how to keep the resulting code readable and easy to test later on. Please also mention how you would report errors back to the caller without throwing any exceptions, and
```

3. The server dies immediately. Any prompt of that exact token length does the same.

### Token-length sweep

Neutral English prompts built word by word and verified via `/tokenize`, each sent 3× with
`cache_prompt: false`, server restarted after every crash — 27 requests total:

| `/tokenize` tokens | server `prompt_n` | result |
|---|---|---|
| 82 | 90 | 3× OK |
| 83 | 91 | 3× OK |
| 84 | 92 | 3× OK |
| 85 | 93 | 3× OK |
| **86** | **94** | **3× CRASH** |
| 87 | 95 | 3× OK |
| 88 | 96 | 3× OK |
| 89 | 97 | 3× OK |
| 90 | 98 | 3× OK |

We originally hit this with an unrelated Czech prompt that happened to have the same
`prompt_n = 94` — also 3/3 crashes. Changing any single word that shifted the length by one
token made it disappear, which is why it looked nondeterministic at first.

### What we ruled out

| Hypothesis | Test | Result |
|---|---|---|
| Corrupted model file | sha256 vs HF `lfs.oid` | matches |
| Model or prompt itself | same prompt on **CPU-only build** | runs fine (5.5 t/s) |
| Quantization-specific | `UD-Q3_K_XL` and `UD-Q4_K_S` | both crash |
| Driver version | 596.36 → 597.06 | identical behaviour |
| KV cache in VRAM | `--no-kv-offload` | still crashes, and ~40 % slower |
| Language / diacritics | English, Czech, Czech without diacritics | only length matters |
| Specific words or topic | 7 single-word variants, 4 unrelated topics | only length matters |
| Prompt length in characters | 210–217 chars crash *and* pass | only token count matters |

### Possibly relevant

- **A cached prompt does not crash.** With `cache_prompt: true` a repeated identical request
  reports `prompt 4 tok` and completes normally — consistent with the fault being in prompt
  processing rather than in the graph itself.
- `prompt_n = 94` is two tokens below 96 = 3×32, so a tile/block boundary in one of the `-cmoe`
  kernels looks like a plausible place to look. Not verified.
- Without `-cmoe` we have never seen this crash.
- Reproduced on both `b10639` and `b10742`, so it is not a recent regression.

### Workaround

Make sure the prompt is not exactly 94 tokens — adding or removing a single token avoids it
entirely.

### First Bad Commit

Not identified. Reproduced on b10639 (2026-08-26) and b10742 (2026-09-01) alike,
so it predates b10639.
