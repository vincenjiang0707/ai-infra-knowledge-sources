### Yoshi4470 · 2026-06-07

I believe this is the same underlying issue addressed in this commit:

https://github.com/Yoshi4470/llama.cpp/commit/09c1af8dd1586f9743f6e637bf3fdd517e671399

What happens

On the first draft-mtp speculative decode, the server may save the MTP draft context via spec_ckpt.update_dft(..., LLAMA_STATE_SEQ_FLAGS_PARTIAL_ONLY). That goes through llama_state_seq_get_data_ext → llama_io_write_host.

KV serialization writes per-stream views (layer.k_stream[...]) in llama_kv_cache::state_write_data(). In ggml, those views normally have tensor->data == NULL; storage lives on view_src.

When llama_io_write_host is destroyed, it calls ggml_backend_tensor_get() on those views. On upstream b9542, that path still asserts:

GGML_ASSERT(tensor->data != NULL && "tensor not allocated");
which matches the crash at ggml-backend.cpp:348.

What the commit changes

It resolves the backing buffer via view_src in ggml_backend_tensor_get/set (and related checkpoint IO paths), instead of asserting on the view’s own data pointer.

Note on the bisect result

6c4cbdc70 (#23646) likely changed when/how the MTP draft context is set up, which makes this checkpoint path easier to hit. The direct cause of the assert itself is the view-tensor handling in checkpoint IO, not the cache-type change alone.

If you can try a build that includes 09c1af8dd, it would be useful to confirm whether this resolves the crash on your side.
