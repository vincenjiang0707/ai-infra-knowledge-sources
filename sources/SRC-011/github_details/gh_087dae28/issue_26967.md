## DFlash `predicted_ms` becomes impossible on some Q4/Metal requests

On the current upstream commit `9ba73fd1f5bc882d4cb58101a99e99f4f326506c`, I see corrupted server decode timing fields for DFlash on Apple Metal.

Configuration:

- MacBook Air M4, 24 GB unified memory; Metal build.
- Target: `Qwen/Qwen3-4B` converted to `Q4_K_M`.
- Draft: `z-lab/Qwen3-4B-DFlash-b16` converted to BF16 GGUF.
- `--spec-type draft-dflash --spec-draft-n-max 15 --temp 0 --top-k 1 -np 1 -c 4096 --jinja --metrics`.
- No-thinking greedy requests (`temperature=0`, `top_k=1`).

In a 33-sample / 39-turn SPEED-Bench qualitative run, all requests returned HTTP 200. For three math requests, client wall-clock latency was about 36 seconds with a 256-token completion, but the response timing fields were implausibly large:

| question ID | client latency | completion tokens | `timings.predicted_ms` | reported `predicted_per_second` |
| --- | ---: | ---: | ---: | ---: |
| `47534ec0377943708c55cb1bfad6c83d` | 35.707 s | 256 | 2,198,466.543 ms | 0.1164 tok/s |
| `f73440d5701f4feeaeffcacf282d5607` | 35.832 s | 256 | 206,481.456 ms | 1.2398 tok/s |
| `10983429e00549a3bf63b7ea733195af` | 37.950 s | 256 | 2,675,502.216 ms | 0.0957 tok/s |

The same prompt IDs under the no-speculation Q4 baseline reported 19.9–22.3 s client latency and 19,813–22,259 ms `predicted_ms`, which is internally consistent. Other DFlash requests in the same run also had `predicted_ms` close to client elapsed time.

This contaminates `tools/server/bench/speed-bench`'s averaged decode tok/s (DFlash math becomes 0.48 tok/s) even though the client latency is normal. Raw result file SHA-256:
`4530ecd200566253582d430beb7dfaf588d49420c1a1567cbd8ba94a2fd0d412`.

I can provide the full raw JSON or rerun a minimal one-prompt repro if helpful.
