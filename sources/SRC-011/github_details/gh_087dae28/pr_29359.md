# [PR #29359] ggml-cpu x86: exact -128 handling in int8 dot-product helpers (fix #29351; excludes q1_0, iq2_*, iq3_*, sgemm, repack)

state: open | updated: 2026-09-26T17:59:00Z

## 正文

Fixes #29351

## Overview

The `sign_epi8` + `maddubs` trick in the x86 helpers cannot negate `-128` (negating -128 in int8 stays -128), and `(-128) * (-128) = 16384` has no `u8 x s8` factorization at all, so any block whose y-side contains -128 is silently wrong on non-VNNI builds. llama.cpp's own quantizers clamp to [-127, 127], but -128 is reachable via the public API and hand-built/third-party GGUFs, and it makes generic-C and SIMD builds diverge. This PR guards the affected fast paths and widens both operands to int16/int32 for those rare blocks.

## Changes (185+/14-, `ggml/src/ggml-cpu/arch/x86/quants.c` + `tests/test-quantize-fns.cpp`)

- `mul_sum_i8_pairs` (SSSE3/AVX/AVX2): guard on `y == -128` -> widen both operands to int16, `madd_epi16` -> int32, compact back to the maddubs lane layout
- `mul_sum_i8_pairs_float` AVX2 (non-`__AVXVNNIINT8__` path) and AVX: same guard -> widening path
- `mul_add_epi8` (AVX2) / `mul_add_epi8_sse` (AVX): guard + int16 widening, repacked via `packs_epi32`. The repack is exact for every remaining caller: the guard only fires for `y == -128`, only q8_0 can carry `x == -128`, and q8_0's AVX-only path no longer reaches this pack (next bullet), so `|pair sum| <= 2 * 127 * 128 < 2^15` there
- `mul_sum_i8_quad_float` (AVX-only): now accumulates via `mul_sum_i8_pairs` instead of `mul_add_epi8_sse` + `madd(ones, ...)`. Two `(-128) * (-128)` products sum to `2^15 = 32768`, which does not fit the int16 lanes of that path - `packs_epi32` saturates it to `32767` (reachable because q8_0 has full-range x). Same lane layout, per-half `-128` scan, perf-neutral
- `ggml_vec_dot_iq1_m_q8_K`: inline `sign_epi8(q8b, delta)` dot3/dot4 have the same flaw - guarded, slow path `mul_sign_delta_i8`
- VNNI `dpbssd` paths untouched (already exact)

## Tests

**In-tree regression test** (`tests/test-quantize-fns.cpp`, `test_vec_dot_q8_0_i8_min`), ported from #29356 with attribution and extended to 12 cases: byte offsets 0/8/16/30 within a block, both blocks (the inactive block gets a distinct scale, so a dropped range, a missing block or a wrong block/scale association changes the result), `x == -128` with `y == +127` (and vice versa), and the `2^15` saturation corner.

- without the `mul_sum_i8_quad_float` fix: **7/12 fail on the AVX-only build** (`32768 -> 32767`); native already passed there (the AVX2 path accumulates those products in int32)

Custom harnesses; restricted-y (no -128) control rounds are 0 wrong on every build including unpatched, so the references are sound.

Thanks for picking this up at the helper level. I tested it locally, and it's correct for everything it touches, but I think the overhead is higher than the description says and there's a cheaper way to get most of the coverage.

**What I ran** (i9-14900KF, clang-22, `GGML_NATIVE=OFF`, AVX512/AVX_VNNI/AMX off, `GGML_LLAMAFILE=OFF`, one AVX2 and one AVX-only build each of base `53ed051ce`, #29356 and this PR):

- A standalone test that pulls the helper block straight out of each tree's `arch/x86/quants.c` and checks it against a scalar reference. For each helper it runs all int8 (x, y) pairs at every byte position, all pair corners from {-128, -127, -1, 0, 1, 127}, and random vectors at several -128 injection rates. I ran it with SSSE3, AVX, AVX2 and AVX2+AVX-VNNI (the dpbusd path). The PR goes from 700k to 1.4M mismatches per helper on base to 0 in `mul_sum_i8_pairs`, both `mul_sum_i8_pairs_float` variants, `mul_add_epi8`, `mul_add_epi8_sse`, `mul_sum_i8_quad_float` and the new `mul_sign_delta_i8`. The control rounds (x full range, y without -128) are 0 on base as well, so x = -128 on its own is harmless as expected.
- A kernel-level comparison of `vec_dot` against `ggml_vec_dot_*_generic` for all 24 x86 types, with -128 injected into y (bsums and `s` recomputed). Per type, out of 1200 injected rows: q8_0, q4_0, q5_0, mxfp4, nvfp4, iq1_s, iq1_m, iq4_nl and iq4_xs go from about 800 to 1100 wrong rows to 0 on both builds. #29356 fixes only q8_0.
- Your `test-quantize-fns.cpp` built against base libs: 9/12 i8_min cases fail on both AVX2 and AVX-only. Against this PR and against #29356 it's 12/12. `test-backend-ops -b CPU -o MUL_MAT,MUL_MAT_ID` passes 2266/2266 on all three trees. That's only a regression check, since ggml-quantized inputs never contain -128.
- #29359's `quants.c` also compiles cleanly (gcc-13 and clang-22) with AVX512F/VL/VNNI and AVX-VNNI-INT8 flags. I couldn't execute those paths here.

**Performance.** `test-quantize-perf --op vec_dot_q`, pinned to one P-core, 7 interleaved rounds, median of min cycles. The machine was shared and loaded, so treat these as ±5% (q4_K, which neither PR touches, moved -5%..+4%). AVX2 L1/L2: q8_0 +11%/+13%, q4_0 +5%/+12%, q5_0 +11%/+12%, iq4_nl +19%/+19%, mxfp4 +28%/+24%, nvfp4 +10%/+13%, iq4_xs +20%/+26%. AVX-only: q8_0 +26%, q4_0 +17..25%, iq4_nl +21..30%, mxfp4 +21..25%, iq4_xs +21..28%. That's noticeably more than the +3 to 13% in the description. My `test-backend-ops perf` MUL_MAT runs (16 threads on a busy box) were too noisy (±30%) to say whether any of this survives in a memory-bound mat-vec, so I'm not claiming a model-level number.

That cost matters here because ggml can't produce this input itself. `quantize_row_q8_0`/`q8_1` scale by 127/amax, and `quantize_row_q8_K_ref` deliberately uses `-127.f/max` with the comment "We need this change for IQ2_XXS, else the AVX implementation becomes very awkward" (`ggml/src/ggml-quants.c:2788-2790`). So [-127, 127] for the activation side is an existing, intentional invariant. Every normal matmul pays the check in the inner loop for a case only direct `vec_dot` callers with foreign data can hit.

**Suggestion: swap operands instead of guarding, for every type except q8_0 x q8_0.** The sign trick is only wrong when the *signed* operand is -128. For all of these types the weight side is bounded (q4_0 [-8,7], q5_0 [-16,15], iq4_nl/iq4_xs >= -127, mxfp4/nvfp4 small, iq1 ±1), so calling the existing helpers as `mul_sum_i8_pairs_float(qy, qx)` / `mul_add_epi8(q8b, q4b)` puts `abs()` on y (|-128| = 128 is a valid u8) and the sign on x. Pair sums stay within 2·128·127 = 32512. I checked this with the unchanged base helpers: with x clamped to [-127, 127] and y full range, all five helpers give 0 mismatches over the same exhaustive/random set on SSSE3, AVX, AVX2 and AVX2+VNNI. It costs no extra instructions. Only q8_0 x q8_0, where both sides are full range, needs an exact slow path. That could be a q8_0-local guarded helper (your widening code is fine there) rather than a branch in helpers shared by everything. For iq1_m, `maddubs(abs(q8b), sign(delta, q8b))` should likewise be exact without a branch, though I haven't tested that one.

**Coverage gaps.** The description lists iq2_xxs/iq2_xs/iq3_xxs as follow-up, but the same negation overflow is also in the `sub(xor(q8, m), m)` form. After this PR my kernel harness still shows ~890 of 1200 injected rows wrong for each of these:

- q1_0: `quants.c:686`, `:694` (AVX2) and `:720`, `:737`, `:773` (AVX)
- iq2_s: `:3231`, `:3236`, `:3312-3322`
- iq3_s: `:3550`, `:3555`, `:3645-3655`

Outside this file, `llamafile/sgemm.cpp:1552-1665` (`updot(sign(a,a), sign(b,a))`) and `arch/x86/repack.cpp:170-172` use the same trick. With default builds, q8_0/q4_0 matmuls go through those instead of `vec_dot`. If the goal is "SIMD matches generic for any int8 input", those need the same treatment. Otherwise the title should say which kernels are covered.

**Smaller things:**

- `quants.c:106-107` and `:132-133` use `_mm256_set_m128i`. The file defines `MM256_SET_M128I` at `:25-26` because some compilers don't provide it (gcc 7), so please use the macro.
- `quants.c:197-206`: the AVX2 widening path returns a different lane layout from the fast path (lane i = bytes 2i, 2i+1, 16+2i, 17+2i). That's fine for the current callers (q4_0 `:830`, q5_0 `:1270`, q8_0 `:1431` all broadcast one scale and hsum), but the comment should say the layout differs explicitly so nobody adds a per-lane-scale caller later.
- `quants.c:100-107` / `:256-262`: the saturating `packs_epi32` repack is only exact because no current caller has x = -128. It's documented, but a debug-only check on x in the slow path would catch a future caller that breaks that. The swap approach above avoids the question entirely.
- The in-tree test only exercises q8_0. The helper changes for q4_0, q5_0, mxfp4, nvfp4, iq1_s, iq1_m, iq4_nl and iq4_xs have no in-tree coverage. A loop in `test-quantize-fns.cpp` that builds a q8_0/q8_K y with a -128 byte (fixing up bsums) and compares `vec_dot` against dequantize+float dot for each type would cover them.

**Compared with #29356:** that PR falls back to `ggml_vec_dot_q8_0_q8_0_generic` for the whole row when a block contains -128. It's correct for q8_0 (0 wrong in my harness), but it leaves the other 14 affected types broken (13193 wrong rows vs 5362 here). On q8_0 it costs about the same as this PR (+13% AVX2, +18% AVX-only in the same microbenchmark), since the check is per block either way. I prefer the helper-level fix here over the call-site fallback because it has the broader scope. I'd still like to see it restructured so the bounded-operand types pay nothing, and either the remaining inline patterns fixed or the scope stated in the title.
