# [Issue #26293] server: prompt cache is populated by rerank tasks that can never read it back (cache_idle_slots missing the SERVER_TASK_TYPE_COMPLETION guard)

source: https://github.com/ggml-org/llama.cpp/issues/26293
state: open | updated: 2026-09-26T01:11:14Z
labels: 

## 正文

### Summary

On a rerank-only server, host RAM grows by ~23 MB per `/v1/rerank` call until it reaches the `--cache-ram` limit (8192 MiB by default), and is never released while the process lives. The growth is the **prompt cache being populated by rerank tasks that can never read it back** - for `SERVER_TASK_TYPE_RERANK` the cache is write-only.

This is not the same as #25740 (closed as not-planned). There the cache was doing its job on the completion path and the reporter simply hadn't set `-cram 0`. Here the entries are provably never read, so the memory is pure waste plus a per-request serialisation cost.

### Version / environment

- `b4d6c7d8ff69c2e05e4e8ee7e6e710a08abd7b45` (b10091), also present on master at time of writing
- CUDA, aarch64 (NVIDIA GB10), driver 580.173.02
- Model: Qwen3-Reranker-0.6B Q8_0 GGUF
- Server: `llama-server --reranking --pooling rank -c 8192 -np 2 -ngl 999 -fa on --no-mmap`
- Reproduced identically on two hosts

### The path

1. `POST /v1/rerank` creates independent `SERVER_TASK_TYPE_RERANK` tasks with no parent.
2. `server_slot::release()` clears the prompt only for child tasks (`server-context.cpp:488-491`):
   ```cpp
   // do not keep context of the child slots - the parent's context is enough
   if (task->is_child()) {
       prompt_clear();
   }
   ```
   Rerank tasks are not children, so `slot.prompt` and its KV state survive release.
3. On the next task launch, the idle-slot pass saves every idle slot to the prompt cache (`server-context.cpp:2398-2414`) - **with no task-type guard**:
   ```cpp
   if (params_base.cache_idle_slots) {
       for (auto & slot : slots) {
           if (!slot.is_processing()) {
               if (slot.prompt_save(*prompt_cache)) {
   ```
4. The other call site does have the guard it needs (`server-context.cpp:1617-1618`):
   ```cpp
   // cache prompts only for completion tasks
   update_cache = update_cache && task.type == SERVER_TASK_TYPE_COMPLETION;
   ```
5. `prompt_load` is only reached from inside that completion-gated branch, so nothing ever reads a rerank entry back.

With `-np 2`, `kv_unified` is false, so the `[TAG_IDLE_SLOT_CLEAR]` path does not run and the slot keeps its prompt after the save as well.

### Measurements

Fresh restart each arm, 40 calls, resident memory of the service:

| workload | growth |
|---|---|
| 40 calls, **identical** query+docs | +68 MB, then flat from call ~10 |
| 40 calls, 20 docs, **40 distinct** doc lengths | +3032 MB by call 20, climbing until capped |
| same, with `--cache-ram 0` | +626 MB |
| same, `--cache-ram 0` + `GGML_CUDA_DISABLE_GRAPHS=1` | +620 MB (graph cache not involved) |
| same 40 lengths **descending** | +620 MB immediately, then flat |

Two separate effects: the cache (dominant, content-keyed, deduped only on full prefix match, so every distinct query+document pair is a new entry) and a benign high-water-mark buffer allocation of ~620 MB that stops growing once the largest request has been seen.

The arithmetic matches: Qwen3-0.6B is 28 layers x 8 KV heads x 128 head_dim, f16 → 112 KiB/token, so ~23 MB/call ≈ 210 tokens of KV state - a query plus a few short documents. In production the process sat at 9137 MB with **zero busy slots**, consistent with ~1.1 GB baseline plus the 8 GiB cap.

### Reproduce

```bash
llama-server -m Qwen3-Reranker-0.6B-Q8_0.gguf --reranking --pooling rank -c 8192 -np 2
# then POST /v1/rerank repeatedly with DIFFERENT documents each time and watch RSS.
# Identical documents will not reproduce it - the cache dedups on full prefix match.
```

### Suggested fix

Apply the same guard the completion path already uses, so idle slots are only saved for task types that can read the cache back:

```cpp
if (params_base.cache_idle_slots) {
    for (auto & slot : slots) {
        if (!slot.is_processing() && slot.task && slot.task->type == SERVER_TASK_TYPE_COMPLETION) {
```

Alternatively (or additionally) clear the prompt on release for task types that never reuse it.

### Workaround

`--cache-ram 0` (which also auto-disables `cache_idle_slots`), or `--no-cache-idle-slots`. For a rerank/embedding-only server this costs nothing, since those entries are never read. Confirmed: 9137 MB → ~1.1 GB steady state on our fleet.

### Note on scope

`/v1/embeddings` builds non-child `SERVER_TASK_TYPE_EMBEDDING` tasks through the same `send_embedding` → `release()` path, so it looks structurally exposed. I could **not** reproduce growth on an embedding-only server (Qwen3-Embedding-0.6B, 30 distinct input lengths, +20 MB and flat), so I am reporting only what I measured rather than assuming.

### zanphear · 2026-08-21

Adding the measurements behind this, since the report above was mostly a code-reading and the numbers make the cost concrete.

Setup: `llama-server` as a reranker (`--reranking`), `qwen3-reranker-0.6b` Q8_0, GB10 / CUDA 13 / aarch64. Fresh restart per arm, 40 rerank calls per arm, RSS sampled with zero busy slots.

## Measured decomposition

| workload | RSS growth |
|---|---|
| 40 calls, **identical** content | +68 MB, then flat from call ~10 |
| 40 calls, **distinct** content | **+3,032 MB by call 20**, still climbing until the cap |
| distinct content, `--cache-ram 0` | **+626 MB** |
| distinct content, `GGML_CUDA_DISABLE_GRAPHS=1` | +620 MB |
| same lengths, **descending** | +620 MB immediately, then flat |

Three things fall out of that:

1. **Identical content is flat, distinct content grows.** That is the signature of a cache keyed on prompt content that nothing ever reads back, rather than an allocator leak.
2. **`GGML_CUDA_DISABLE_GRAPHS=1` changes nothing** (+620 vs +626 MB), so the CUDA graph cache is ruled out as the source.
3. **Descending lengths grow once and then stay flat**, so the ~620 MB residual is a benign high-water mark, not an ongoing leak.

The arithmetic matches the KV interpretation: Qwen3-0.6B is 28 layers x 8 KV heads x 128 head_dim at f16 = **112 KiB/token**, so ~23 MB/call is about 210 tokens of KV state per rerank call.

## What it cost in production

The unit had been running for weeks and sat at **9,137 MB RSS with zero busy slots**, which is consistent with roughly 1.1 GB of baseline plus the full 8 GiB `--cache-ram` default being filled with entries that can never be hit.

Adding `--cache-ram 0`:

| host | before | after |
|---|---|---|
| A | 9,137 MB | **1,194 MB** |
| B | 9,137 MB | **561 MB** |

Those readings have held since. Sampling the same units today, weeks later, gives 1,094 MB and 199 MB, so the fixed state is stable and the residual really is the high-water mark rather than a slower leak.

## Negative control

**The embedder does not share the defect**, and this was measured rather than assumed: `Qwen3-Embedding-0.6B` over 30 distinct input lengths grew **+20 MB and stayed flat**. `/v1/embeddings` looks structurally exposed through the same non-completion path, but it did not reproduce, so whatever guards it in practice may be worth comparing against the rerank path.

## One implementation note

`--cache-ram 0` is a complete workaround rather than a partial one, because it also turns off the idle-slot publish. In `server-context.cpp`:

```
if (params_base.cache_idle_slots) {
    if (params_base.cache_ram_mib == 0) {
        SRV_WRN("%s", "--cache-idle-slots requires --cache-ram, disabling\n");
        params_base.cache_idle_slots = false;
```

So a reranker deployment can mitigate today with the single flag, at no cost, since the cache was never readable for these tasks anyway. That said, the default is on, and a rerank-only server silently giving up 8 GiB of RAM to unreachable entries is a poor default.

`#26893` ("server: avoid caching non-completion idle slots in RAM") looks like it addresses this. Happy to test a patch on the workload above, the distinct-content arm reproduces in well under a minute.


### Tyberious · 2026-09-25

This also affects embedding-only servers. There it shows up as falling throughput rather than memory growth (~2 KB per input), which may be why the 30-input test above looked flat.

**Setup:** build 11026 (`b49650adb`; the same code is on master at `4b1a27fa0`), Vulkan on an AMD Radeon 8060S (RADV), bge-m3 FP16 (an encoder, no KV memory).
`llama-server --embeddings --pooling cls -ngl 99 -c 8192 -b 8192 -ub 8192 --parallel 8`
One client posts `/v1/embeddings` with 32 distinct inputs at a time, back to back (~50 inputs/s).

| uptime | inputs/min |
|---|---|
| 0 | ~2,950 |
| 30 min | ~2,200 |
| 6 h 47 min | ~400 (GPU ~22% busy at ~1 GHz) |

A restart restores the full rate immediately. RSS grows ~5 MB/min.

**Why the limits never evict:** each entry's state (`llama_state_seq_get_size_ext`) is ~0 bytes, so `size()` never approaches `--cache-ram`. In `update()`, `size_per_token = max(1.0f, size()/n_tokens())` is then 1, so `limit_tokens_cur = limit_size / 1`, about 8.6e9 tokens. `states` gains one entry per distinct input for the life of the process.

Each launch offers every idle slot to the cache (non-unified KV with `--parallel 8`, so slots keep their prompt). Each offer walks the whole list: in `alloc()` twice (the duplicate check, then contained-prompt removal), and again in `update()` (`size()` and `n_tokens()`). The cost per input grows linearly with the inputs served, on the thread that feeds the GPU.

**Workaround:** `--cache-ram 0`, which also disables `cache_idle_slots`. With it, over 45 min of uptime: ~3,040 inputs/min at 0-10 min, ~3,040 at 30 min, ~2,930 at 45 min (every minute fell between 2,912 and 3,072). RSS growth dropped from ~5 MB/min to ~1.2 MB/min; I haven't identified the rest.

**Fix:** the task-type guard proposed above covers this. Separately, the byte-derived token limit in `update()` shouldn't apply when the saved state is ~0 bytes.
