```shell
  "messages":[{"role":"user","content":"What is the capital of France? One word."}],
  "chat_template_kwargs":{"enable_thinking":false},
  "tools":[{"type":"function","function":{"name":"assist","description":"web research","parameters":{"type":"object","properties":{"query":{"type":"string"}},"required":["query"]}}}],
  "tool_choice":"required","temperature":0,"max_tokens":600}'
```

### Problem description & steps to reproduce

With a Qwen3-family chat template (Qwen3.5/3.6 MoE, embedded GGUF template, handled by the auto-parser path) and `chat_template_kwargs: {"enable_thinking": false}`, the `tool_choice: "required"` constraint (and likewise a named function `tool_choice`) is **not enforced**: the model free-runs plain prose until `max_tokens` (`finish_reason: "length"`), returns no `tool_calls`, and `content` stays empty when the run ends inside what the parser treats as reasoning.

Control experiments on the same build and GGUF, changing exactly one variable each:

| Variant | Result |
|---|---|
| same request, thinking **enabled** (omit the kwarg) | tool call correctly forced ✓ |
| same request, **Gemma-3-family** GGUF/template | tool call correctly forced ✓ |
| same schema via `response_format: json_schema` instead of tools | grammar correctly enforced ✓ |
| `tool_choice: "auto"` | behaves as expected (model may answer) ✓ |

So the grammar machinery itself is fine — the combination *Qwen3 template + `enable_thinking: false` + forced tool choice* is what loses the constraint. `stop` sequences are unrelated (reproduced with and without).

At temperature 0 the failure is fully deterministic. Practical impact: OpenAI-compatible agent frameworks that force the selected tool via named `tool_choice` (to generate its arguments) silently break on these very common Qwen3 no-think setups — the doomed generation runs to the token cap on every decision.

Happy to provide full server logs or test other template families if useful.

*Disclosure: this report was prepared with AI assistance (Claude); the bisection across the three builds and all control experiments were run and verified by hand on real hardware.*

### walcz-de · 2026-08-26

Additional cross-checks to rule out a quantizer/template artifact (same build `f280b26983`, same request, CPU):

| GGUF | Source | Result with `enable_thinking:false` + `tool_choice:"required"` |
|---|---|---|
| Qwen3.6-35B-A3B (MoE) | quantizer A | not enforced — free-run to `length`, no tool_calls |
| Qwen3.6-27B (dense, UD-Q5_K_XL) | Unsloth | not enforced — free-run to `length`, no tool_calls |
| Qwen3.5-4B (Q4_K_M) | official Qwen GGUF | **enforced correctly** — `finish_reason: tool_calls` ✓ |

So this reproduces with the embedded template of **Qwen3.6** models from two independent quantizers (both MoE and dense), while the official Qwen3.5-4B GGUF is fine — narrowing the affected scope from "Qwen3-family" (as I wrote initially) to the **Qwen3.6 chat template** specifically. Sorry for the imprecision in the original title; happy to retest with any template override if that helps bisect the template block responsible.
