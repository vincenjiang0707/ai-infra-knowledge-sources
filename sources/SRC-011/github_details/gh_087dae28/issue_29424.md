### Feature Description

We'd like to add K2 Horizon to llama.cpp. It's our model family at IFM (MBZUAI), and there are five sizes: 0.9B, 3.7B, 7B, 32B and a 36B MoE that uses MoVA. They all use the same architecture, so it's one `k2-horizon` arch and one converter for all of them.

We already have it working on our fork: https://github.com/ifm-ai/llama.cpp/tree/model/K2Horizon

GGUFs for all sizes are on Hugging Face: (https://huggingface.co/collections/IFM/k2-horizon-quantization)


### Motivation

Quite a few people are already using the fork, but that means building a separate llama.cpp and waiting on us every time upstream moves. We'd much rather have it in main so it works everywhere llama.cpp does, and we can stop maintaining a fork.

The good news is it's not a big change. The base is a regular Llama-style decoder. The dense models add two small things: RMSNorm is applied in groups over the hidden dim (with one full-length weight), and there's an optional softplus gate on the attention output before `o_proj`. Both are a few existing ops in the graph. The 36B also has a DeepSeek-V3-style MoE FFN, which goes straight through `build_moe_ffn`, plus MoVA, which is the one part that's actually new.

### MoVA

MoVA is "mixture of value experts". In the sparse layers of the 36B, instead of a single V projection, each token picks 4 out of 64 value projections through a small router. It then mixes them: `V = Σ w_k · silu(W_k x)`. Q and K are untouched.

We tried to make it look as much like the existing MoE code as possible:

- All 64 expert matrices are stacked into one 3D tensor at conversion time, so in the graph it's a single `ggml_mul_mat_id` that only computes the 4 selected experts per token. It's the same trick `build_moe_ffn` uses, so it runs on every backend with no new ops.
- The router follows the MoE FFN's conventions: sigmoid scores, a bias that only affects which experts get selected, and the mixing weights taken from the unbiased scores, then normalized and scaled. Because of that we reuse the existing gating/norm/scale keys. The only new keys are `attention.value_expert_count` and `attention.value_expert_used_count`.
- The mixed V is what goes into attention, so the KV cache doesn't change at all. It's the same size and layout as any other model. The extra cost is only in the V projection.

It lives in one helper, `build_routed_value`, in `src/models/k2-horizon.cpp`. The tensors are currently named `attn_v_gate` (router) and `attn_v_exps` (experts). We're happy to switch to names that mirror the FFN MoE ones (`attn_v_gate_inp`, `attn_v_exp_probs_b`, ...) if you prefer, since we'd rather get that right before merging.

### Possible Implementation

Everything is on the fork: the converter (`conversion/k2_horizon.py` + gguf-py), the model (`src/models/k2-horizon.cpp`, built on the usual `build_*` helpers), the tokenizer, and the chat template with reasoning/tool call parsing for `llama-server --jinja`.

One thing worth mentioning about the tokenizer: the HF pre-tokenizer regex uses `\p{...}` classes, which `std::regex` can't handle on MSVC. So we wrote the splitter by hand in `unicode.cpp`, the same way the llama3 one is done, and added cases to `test-unicode`.

We've tested on CPU and CUDA.

If it's easier to review, we can split this into a few smaller PRs (the jinja fix, the tokenizer, the model, then chat parsing). Just let us know what works best.
