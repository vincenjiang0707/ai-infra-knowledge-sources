## 正文

## Overview

For every new prompt the server creates context checkpoints (by default: start of the last user message, `4 + n_ubatch` tokens before the end, and 4 tokens before the end). For recurrent / hybrid models each checkpoint copies the full recurrent state, and over RPC that copy crosses the network. On a two-node cluster serving Qwen3.8-27B (recurrent hybrid, ~21 recurrent layers on the RPC worker) each checkpoint costs ~66-69 MB over 1GbE (~0.6 s), and in multi-turn serving most of the default checkpoints are never used for reuse - so the traffic is mostly wasted.

This makes the checkpoint layout configurable:

- `LLAMA_CKPT_OFFSETS` - list of offsets from the end of the prompt (`"u"` = `4 + n_ubatch`), e.g. `LLAMA_CKPT_OFFSETS=4` keeps a single checkpoint
- `LLAMA_CKPT_LAST_USER=0` - drops the checkpoint at the start of the last user message

Unset = current behavior, byte for byte.

## Changes

- `common/speculative`: pass the target context to the draft contexts as `ctx_other`, so speculative (MTP) state is checkpointed/restored consistently with the target
- `server`: parse the two env vars and build the checkpoint offset list from them; default list unchanged

## Perf check

Two-node RPC cluster (RTX 4070 12GB controller + worker over 1GbE), Qwen3.8-27B UD-IQ3_S, KV q4_0, 64K context, 3 slots, MTP draft:

| | before | after |
|---|---|---|
| network traffic per turn | ~287 MB | ~150 MB |
| short turn latency | 3.72 s | 2.47 s |
| new prompt latency | 5.23 s | 3.89 s |
| new session sharing a ~10.5K system prompt | 10466 tokens reprocessed, 17.1 s | 15 tokens reprocessed, 2.5 s |

Checkpoint reuse behavior unchanged (reprocessed-token counts identical to upstream). Solo decode unchanged (~48 tok/s).

## Additional information

Tested in production on the two-node cluster above: 3 concurrent sessions, multi-turn, MTP acceptance 35-71% after turn 1, no errors.
