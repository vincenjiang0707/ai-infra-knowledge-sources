# [Issue #25859] Offloaded-MoE prefill leaves the GPU idle waiting on serial expert H2D copies (single-GPU -ncmoe)

source: https://github.com/ggml-org/llama.cpp/issues/25859
state: open | updated: 2026-09-27T01:21:21Z
labels: stale

## 正文

Sharing a performance finding from profiling the offloaded-MoE path (`--n-cpu-moe` / `-ncmoe`) — the setup where a big MoE model runs on a small GPU with the experts kept in system RAM and streamed in per layer.

My box: RTX 3060 12GB, Ryzen 5600X, 32GB DDR4, PCIe 4.0, Ubuntu 24.04. Model: Qwen3.6-35B-A3B (Q4_K_M), `-ncmoe 26`, prefill at pp2048 / ub2048. Everything below is single-box and gen4-specific, so numbers will move on other hardware.

On this setup prefill is bottlenecked by PCIe transfers, not GPU compute. Profiling with Nsight, the GPU sits idle a large fraction of each prefill pass waiting on expert-weight H2D copies, and those copies run serially with the matmul that consumes them — layer N's weights finish uploading, then layer N computes, then N+1's weights start uploading. The upload and the compute don't overlap on the offload path.

Two changes helped a lot, both prefill-only and both producing token-identical output at temp 0:

1. Page-locking the mmap-backed CPU expert weights so the H2D transfers DMA directly instead of going through a pageable bounce buffer. ~+21% on its own.
2. Overlapping the expert uploads with compute on a second stream with a few staging slots, so layer N+1's weights upload while layer N is still computing. This is where most of the win is.

Together that took prefill from ~1143 to ~1880 tok/s at identical settings — roughly +64%, pure code, no config change. GPU idle during prefill dropped from ~42% to a few percent.

I prototyped both behind env flags on a fork so I could A/B them on the same binary and confirm the output stayed identical: https://github.com/thecodacus/llama.cpp/tree/fable5/prefetch-experts (there's a benchmark writeup in the branch with the exact commands and the full before/after log). I'm raising this as a finding rather than a PR — partly because AGENTS.md asks for that, and partly because the right way to expose something like this upstream is probably whoever owns the CUDA scheduler deciding on the shape, not me dropping a patch on you.

Two honest caveats: this was measured a few weeks back at around the b6xxx era, and the CUDA backend has moved since, so the exact idle percentage may be stale — I haven't re-run against current master. And I know pipeline copies are already a thing for the multi-device case; the gap I'm describing is specifically the single-GPU offload path, which always gets `n_copies = 1`.

Main question for maintainers: is reducing GPU idle on the offload path something you'd want addressed, and if so, is overlap-on-a-second-stream the right approach — or is there a reason the offload copies are serial today that I'm not seeing? Happy to share nsys timelines or run other configs if that's useful.

### thecodacus · 2026-07-18

One more detail that belongs here, because it changes how you'd approach a fix.

The offload path's selective expert copy needs the routing ids on the host to know which experts to upload, so each layer does a D2H readback of the ids before the copies start. That readback is a hard sync point: compute has to finish producing the ids, then the pipeline stalls while they come back, then uploads begin. Even with pinned memory and a second stream, that sync alone keeps upload and compute from overlapping cleanly.

The thing is, at prefill batch sizes the selection isn't buying anything. I instrumented the router: at pp2048 the union of experts selected across the batch is essentially all of them (256/256 for Qwen3.6-35B-A3B on nearly every layer). You pay the sync to learn "upload everything."

So the overlap change in my branch does the obvious thing: past a batch-size threshold it skips the ids readback entirely and streams each layer's full expert tensors. That's what lets the second-stream prefetch run ahead of compute with no sync in the loop. At decode-size batches the selection still wins (only a handful of experts per token) and that path is untouched.

Worth knowing if anyone picks this up upstream: the fix isn't "make the readback async," it's "notice when selection is pointless and don't do it."

### yalun753 · 2026-08-08

Great writeup — we've been working the same direction (experts resident in host RAM, computed on GPU) and can add a decode-side data point that complements your prefill numbers.

Setup: RTX 4090, experts mmap'd in system RAM, computed via cuBLAS on GPU. Model Qwen3.6-35B-A3B (IQ2_M), 256 experts/layer.

On the decode path:
- Page-locking the mmap'd expert tensors (cudaHostRegister, whole-tensor merged registration) — same trick as your point 1 — helps here too: generation 46.8 -> **50.2 t/s** at 2.9 GB VRAM. The DMA fast path removes the pageable bounce buffer on every per-token transfer.
- Your point 2 (double-buffered H2D pipeline on a second stream) we measured as **no gain on decode**: 5.0 vs 5.5 t/s. Root cause: at batch size 1 a single expert is ~1 MB — Gen4 copy ~60 us vs MMVQ kernel <10 us, nothing to overlap. That's consistent with your prefill result: at pp2048 there's real overlap headroom, at decode there isn't.

We also cap resident memory with madvise(DONTNEED) expert-page eviction so RSS stays bounded on long conversations (V4-Flash 157B: 84 GB -> 17-24 GB on 16 GB-RAM machines, in low-memory mode).

Shipped open-source: https://github.com/yalun753/moe-l2 (`pip install moe-l2`) — benchmark table includes Qwen3.6-35B-A3B, DS-V2-Lite and DeepSeek-V4-Flash 157B (10.1 t/s @ 17.4 GB VRAM on 4090). Happy to share exact repro commands if useful.


### mobilinkd · 2026-08-14

> This is the same as #21067

@am17an @thecodacus These overlap but target different cases; they have very different performance profiles when prefetching expert tensors. With DS4F_IQ2_XXS, #21067 reserves about 1.7GB of extra memory, and with a single copy slot (n_copies=1) it rarely keeps the pipeline from stalling. #25859 lets you tune the ring buffer as a multiple of the largest expert tensor. In practice 21067 is worse for me with pw=1: it pays to fetch the full weight tensors for every offloaded layer (dense and MoE alike), but the pipeline is mostly stalled. The tunable ring in this PR is the part that matters. With GGML_SCHED_PREFETCH_EXPERTS=4 using this code I can keep the pipeline from stalling and get a 17-20% prefill throughput improvement, at a cost of 2.4GB. I am curious whether this was made adjustable and defaulted to 3 slots because the same issue was encountered during its development. The problem with doing this in 21067 is that its reservation unit is a whole fused split (all of a layer's offloaded weights) rather than a single expert tensor, so adding ring slots there is several times more expensive per slot than the expert-tensor-sized ring here.

There is real value in distinguishing prefetching expert weights from prefetching any model graph.

Note: I had to adapt the prefetch to work around SYCL, and what has worked is an expert-only prefetch modeled on this code -- in part because the ring size is tunable. This comes out of SYCL work I've been contributing via @arthw.

### yalun753 · 2026-08-14

This matches what we measured independently on our expert-offload path (experts mmap'd in host RAM, GPU reads them via PCIe DMA). Point 1 (page-locking) is confirmed as the real win: we already pin expert tensors with cudaHostRegister — selectively, only the top-K experts per layer from a router map, with on-demand pinning as fallback for the rest — and measured ~0.43 ms page-lock on first touch.

On point 2 (overlapping H2D upload with compute on a second stream): we tried exactly that (double-buffered multi-stream pipeline) and it measured no benefit, or a regression, on our setups. Single expert tensors are small (e.g. 1.55 MB ≈ 60 µs over PCIe Gen4 vs <10 µs kernel time), so there's nothing for the overlap to hide; on DeepSeek-V4-Flash (43 layers × 256 experts, very scattered routing) staged copy was actually slower. Instead of overlapping the copy we remove it: hot experts stay resident in a VRAM LRU cache, cold ones stream in once through the DMA path. That also sidesteps the TTFT regression and the permanent double-buffer VRAM reservation that whole-tensor prefetch (#21067) pays on MoE.

Measured end-to-end (moe-l2, llama.cpp fork): Qwen3.6-35B-A3B 30.9-48 t/s, DS-V2-Lite 85-133 t/s, DeepSeek-V4-Flash 157B 10.1 t/s @ 17.4 GB VRAM (85 GB file, 2080 Ti/4090). Details in our issue #26448.

### Castoff995 · 2026-08-27

Additional Windows / AMD RDNA4 / Vulkan datapoint for the stock single-GPU `-ncmoe` path.

I spent some time tuning Qwen3.6-35B-A3B on an RX 9070 XT 16 GB and found a fairly sharp interaction between `-ncmoe`, batch/ubatch size, and KV quantization. No code changes or custom fork were used.

### Environment

- GPU: AMD Radeon RX 9070 XT 16 GB (gfx1201 / RDNA4)
- CPU: AMD Ryzen 5 7500F
- RAM: 32 GB DDR5-5600
- OS: Windows 11 Pro
- Backend: Vulkan, single GPU
- llama.cpp: official Windows Vulkan build `b10644`
- version: `0.3.0-dev`
- commit: `d7a207411`
- Model: `Qwen3.6-35B-A3B-UD-Q4_K_M.gguf` (Unsloth, ~22.1 GB)
- `--parallel 1`
- Flash Attention enabled
- Tests below use `llama-server` timing output, not `llama-bench`

### Final configuration

```powershell
.\llama-server.exe -m "Qwen3.6-35B-A3B-UD-Q4_K_M.gguf" --no-mmproj -dev Vulkan0 -ngl all -ncmoe 20 --fit off -c 131072 -ub 2048 -b 8192 -ctk q4_0 -ctv q4_0 --kv-unified --parallel 1 --load-mode none --cache-ram 0 -fa on --jinja --reasoning auto --host 127.0.0.1 --port 8080
```

### 48.5k real-context result

The synthetic prompt contained 48,531 input tokens and generated 256 tokens.

| Configuration | Prompt processing | Token generation | Total |
|---|---:|---:|---:|
| Initial: `ncmoe=22`, `b=1024`, `ub=512`, Q8/Q8 KV | 704.99 t/s | 30.58 t/s | 77.18 s |
| Tuned: `ncmoe=20`, `b=8192`, `ub=2048`, Q4/Q4 KV | **1565.65 t/s** | **42.18 t/s** | **37.04 s** |

So configuration tuning alone changed:

- prompt processing: ~705 -> ~1566 t/s (**2.22x**)
- generation: 30.58 -> 42.18 t/s (**+38%**)
- complete 48.5k + 256-token request: 77.18 -> 37.04 s (**~2.08x faster**)

### `-ncmoe` has a sharp performance boundary

With the final `b=8192`, `ub=2048` and Q4/Q4 KV:

| `-ncmoe` | Prompt processing | TG |
|---:|---:|---:|
| 22 | 1527.56 t/s | 36.75 t/s |
| 21 | 1526.42 t/s | 36.66 t/s |
| **20** | **1565.65 t/s** | **42.18 t/s** |
| 19 | 1544.73 t/s | **35.33 t/s** |

The `20 -> 19` step alone drops generation by about 16%.

I am not claiming a cause for this boundary; I did not profile PCIe transfers or GPU idle time. I am only reporting the reproducible behavior.

A repeated fresh-server run at `ncmoe=20` reproduced the same prompt-processing progression and exactly 42.01 t/s at the 128-generated-token checkpoint, so the jump at 20 was not a one-off.

### Batch / ubatch sweep

At 48.5k input tokens, before switching to Q4 KV, `ncmoe=22` showed a strong batch-size effect:

| `b / ub` | Prompt processing | TG |
|---|---:|---:|
| 1024 / 512 | 704.99 t/s | 30.58 t/s |
| 2048 / 1024 | 1008.24 t/s | 31.19 t/s |
| 4096 / 2048 | 1104.15 t/s | 30.92 t/s |
| **8192 / 2048** | **1524.28 t/s** | **35.63 t/s** |
| 16384 / 2048 | 1510.35 t/s | 34.28 t/s |
| 4096 / 4096 | 808.45 t/s | 28.40 t/s |

On this particular 16 GB RDNA4 setup, increasing logical batch helped substantially up to around `b=8192`, while making the physical ubatch too large was actively harmful.

`ub=3072` was also tested. After the final `ncmoe=20 + Q4 KV` configuration it regressed to 1466.00 PP / 38.98 TG versus 1565.65 / 42.18 at `ub=2048`.

### KV-cache interaction

At `ncmoe=20`, `b=8192`, `ub=2048`, with 48.5k input tokens:

| K / V | Prompt processing | TG |
|---|---:|---:|
| **q4_0 / q4_0** | **1565.65 t/s** | **42.18 t/s** |
| q8_0 / q4_0 | 1528.60 t/s | 38.72 t/s |
| q4_0 / q8_0 | 1530.94 t/s | 32.38 t/s |

The interaction between KV type and the useful `-ncmoe` placement was large enough that tuning `-ncmoe` in isolation would have missed the best configuration on this system.

Again, I don't want to speculate about the exact mechanism without profiling.

### Near-full 128k context

I also tested a 121,269-token prompt, close to the configured 131,072-token context.

With Q4/Q4 KV:

```text
prompt eval time = 120543.40 ms / 121269 tokens
                 = 1006.02 tokens/s

eval time        = 46716.04 ms / 1718 tokens
                 = 36.75 tokens/s
```

With the identical prompt using Q8/Q8 KV:

```text
prompt eval time = 157568.05 ms / 121269 tokens
                 = 769.63 tokens/s

eval time        = 51845.12 ms / 1876 tokens
                 = 36.17 tokens/s
```

Generation lengths differ because the model's reasoning ended at different points, so I would not compare total request time directly.

### Q4 vs Q8 long-context retrieval check

Because Q4/Q4 was faster, I also checked whether the lower-precision KV cache caused an obvious retrieval failure.

The 121,269-token synthetic test contained:

- four direct records distributed from near the beginning to near the end of the context;
- four two-hop relations of the form `PROJECT -> TAG -> secret`, with the two records placed far apart;
- similar obsolete/decoy values next to the correct values.

Results:

| KV | Direct records | Two-hop relations | Total |
|---|---:|---:|---:|
| Q4/Q4 | 4/4 | 4/4 | **8/8** |
| Q8/Q8 | 4/4 | 4/4 | **8/8** |

Both configurations returned every requested value exactly and rejected all of the decoys.

This obviously does **not** prove that Q4 KV is quality-equivalent to Q8 KV in general. It only shows that I could not measure a recall/association loss in this particular ~121k synthetic retrieval test.

### `--load-mode none`

Earlier in the tuning process, using CPU tensor overrides with mmap produced:

```text
tensor overrides to CPU are used with mmap enabled - consider using --load-mode none for better performance
```

Following that recommendation mattered on this machine.

In an early 32k-context test at `ncmoe=20`, the same short generation improved from about 27.6 t/s with mmap to about 31.4 t/s with `--load-mode none`, with a much larger improvement in prompt processing.

### Why I'm posting this here

This is not a diagnosis of the serial-H2D behavior discussed in this issue; I did not capture a Vulkan transfer timeline.

I thought the numbers might nevertheless be useful as a current stock-llama.cpp baseline for the same Qwen3.6-35B-A3B Q4_K_M offloaded-MoE workload on:

- AMD RDNA4
- Windows
- Vulkan
- 16 GB VRAM
- 32 GB system RAM
- single-GPU `-ncmoe`

The large sensitivity to `b/ub`, KV type, and especially the sharp `ncmoe=20 -> 19` cliff may also be useful when evaluating future pinned-memory / transfer-overlap changes: a default-ish configuration can leave a substantial amount of performance on the table before any code-level optimization is measured.

Happy to rerun exact configurations or test a patch on the RX 9070 XT if useful.

AI assistance was used to organize this benchmark write-up; all performance numbers above are copied from tests I ran locally and checked against the console logs.
