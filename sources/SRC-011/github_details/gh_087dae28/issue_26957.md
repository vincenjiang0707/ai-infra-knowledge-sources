# [Issue #26957] Performance regressions on Android arm64 CPU (Snapdragon 8 Gen 2): text generation ~8% slower since b10333, prompt processing ~13% slower since b10369

## 正文

### Summary

Two separate CPU performance regressions on Android arm64 (Snapdragon 8 Gen 2), measured with the official `llama-bXXXXX-bin-android-arm64.tar.gz` release binaries, CPU backend only:

1. **Text generation is ~8 % slower in b10333 than in b10092**, and slightly worse again by b10369.
2. **Prompt processing regressed a further ~13 % between b10333 and b10369** (it was at parity between b10092 and b10333).

| Median | b10092 | b10333 | b10369 |
|---|---:|---:|---:|
| Decode tok/s (192-token generations) | **15.48** | 14.26 (0.921×) | 13.92 (0.899×) |
| Prompt tok/s (~2k-token prompt) | 72.7 | **73.9** (1.017×) | 64.5 (0.887×) |

### Environment

- Device: Samsung Galaxy S23 Ultra (SM-S918B), Snapdragon 8 Gen 2, Android 16 / API 36
- Binaries: unmodified official release archives, e.g. `llama-b10369-bin-android-arm64.tar.gz`; the runtime auto-selects the armv9.2 CPU variant
- Model: Qwen3.5-2B `Q4_K_M` (bartowski conversion), 1.30 GiB, fully resident, no swap activity

### Method

`llama-server` run under the shell UID with:

```
llama-server -m Qwen_Qwen3.5-2B-Q4_K_M.gguf --host 127.0.0.1 --port 18080 \
  -c 10240 -np 1 -t 5 -tb 8 -Cr 3-7 --cpu-strict 1 -Crb 0-7 --cpu-strict-batch 1 \
  --jinja --no-webui
```

Non-streaming `/v1/chat/completions` requests with `temperature 0`; decode and prompt rates read back from the response `timings` object, so the numbers are the server's own.

Thermal control, since this class of device throttles enough to reorder any comparison:

- every series starts only after battery temperature ≤ 30.0 °C and with charging disabled;
- big-core `scaling_max_freq / cpuinfo_max_freq` headroom is recorded next to every sample;
- the first (page-cache warm-up) sample of every series is discarded;
- decode = 7 samples × 192 tokens; prompt = 4 samples of a ~2,000-token prompt with `cache_prompt: false`.

The regressions are not thermal artifacts: the losing builds ran at **equal or higher** clock headroom than the winning ones (e.g. the b10333 decode series ran entirely at 0.95–1.0 headroom and still lost to a b10092 series that dipped to 0.70).

One observation in the newer builds' favor: server RSS was ~290 MB lower on b10369 (2.66 GB vs 2.95 GB at the same context size).

### Fritz1729 · 2026-08-13

The issue seems to be ARM specific, since I detect no regression on my CPU.

Here are some AI based ideas on finding the root cause (found by Qwen 3.6 27B):

## Decode regression

In commit cb26014d9, the FP16 support detection was updated.
To see whether this is related, you could build b10333 with "-DLLAMA_ARM_ARCH=armv8-a" (no FP16) or "-DLLAMA_ARM_ARCH=armv8.2-a+fp16" (force FP16).
If the build with FP16 is faster than the one without, this would be a workaround and indicate a relation to this commit.

## Prompt regression

CPU affinity options were silently ignored before; that was fixed in d2f83055d.
To see whether this is the cause, you could test with b10369 and skip the affinity options "-Cr 3-7 --cpu-strict 1 -Crb 0-7 --cpu-strict-batch 1".
If this improves speed, there is no regression, and the affinity enforcement was just counterproductive.
