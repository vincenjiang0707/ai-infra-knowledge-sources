### Feature Description

llama-server knows exactly how much memory it allocated on every device - model weights, context/KV cache, compute buffers, per GPU - plus each device's total and free memory. All of that only shows up as log lines. No API exposes it anywhere.

I want it reported per device, plus the model's layer count (the unit you split by). On `/metrics` (real output, M1 Pro):

```
llamacpp:memory_model_bytes{device="MTL0"} 83349984
llamacpp:memory_model_bytes{device="Host"} 13191648
llamacpp:memory_context_bytes{device="MTL0"} 0
llamacpp:memory_compute_bytes{device="MTL0"} 22559744
llamacpp:memory_total_bytes{device="MTL0"} 22906503168
llamacpp:memory_free_bytes{device="MTL0"} 22800187392
llamacpp:model_n_layer 12
```

And as JSON, since every other server endpoint speaks JSON:

```json
{
  "n_layer": 12,
  "data": [
    {"name": "MTL0", "model": 83349984, "context": 0, "compute": 22559744, "total": 22906503168, "free": 22800187392},
    {"name": "Host", "model": 13191648, "context": 0, "compute": 3684352}
  ]
}
```

`/metrics` serves Prometheus/Grafana; `GET /memory` serves programs. With a multimodal projector loaded, its per-device memory is reported too.

### Motivation

**My use case.** I run several llama-server instances sharing a set of GPUs. Before each launch I estimate how much memory it needs on each card, to pick a GPU and a context size. I have no way to check that estimate against what the server actually allocated - a bad estimate does not fail at launch, it fails later as a dead request.

**Today I parse the log.** A regex over the server log, environment variables to raise verbosity (the default level omits the report) and route the log to a file, and checked-in log fixtures to catch format drift between builds. It works. It is brittle and not a contract I want to rely on.

**Other people want this too.** In #23926 one user ships llama-server logs to Loki just to track per-GPU offloading and finds `-lv 4` far too noisy to store; another calls multi-GPU packing "guess work" while "completely blind".

**Nothing exposes it:**

| Surface | Per-device memory? | Reference |
| --- | --- | --- |
| `include/llama.h` | No. `llama_model_size()` is the whole model with no split. `llama_max_devices()` is a compile-time cap. | grep of all `LLAMA_API` |
| `llama_memory_*` in `llama.h` | No. That is the KV-cache sequence API (`seq_rm`, `seq_cp`, `pos_max`). | `llama.h:724-785` |
| `src/llama-ext.h` | Partly. `llama_get_memory_breakdown()` returns per buffer type, not per device. Header says staging, WIP, do not include elsewhere. | `llama-ext.h:1-5, 91` |
| HTTP | No. 50 registered method+path pairs, none carry memory. | `tools/server/server.cpp` route table |

Checked against a running server: `/props` is model and template metadata, `/metrics` is token counters, `/slots` has no memory field.

**The OS is not a substitute:**

- Apple Silicon: unified memory, so there is no per-process VRAM number to read at all. llama.cpp's own Metal backend reports `recommendedMaxWorkingSetSize` as the device total (`ggml/src/ggml-metal/ggml-metal-device.m:1043`) - 21845 MiB on this 32 GiB machine. A share of system RAM, not a pool you can attribute to a PID.
- Linux: the kernel's per-process counters (`drm-total-*`, `drm-resident-*`) are [optional per driver](https://docs.kernel.org/gpu/drm-usage-stats.html). Vendor tools fill the gap at one dependency and one output format per vendor.
- It is one number. No weights/context/compute split, so a wrong device split and an over-sized context look identical.
- `llama-bench` (#23208) and the router (#21231) need this in-process. They cannot shell out to `nvidia-smi`.

**The same aggregation is copy-pasted four times inside llama.cpp:**

| Location | What it is | Difference |
| --- | --- | --- |
| `common/fit.cpp:843-870` | inside `common_memory_breakdown_print` | counts only devices the model uses, buckets the rest into a separate row |
| `common/fit.cpp:77-97` | inside `common_get_device_memory_data_impl` | no separate bucket for unmatched buffer types |
| PR #23208 (`llama-bench`) | its own `std::map<ggml_backend_dev_t, size_t>` fold | sums into any device a buffer type resolves to, so it can disagree with the printed table for the same model |
| PR #21231 (router) | new `llama_context_device_memory()` plus its own `ggml_backend_dev_memory()` + margin logic | a third mechanism for the same question |

All of this is already computed, correctly - the server even prints it on exit (`tools/server/server.cpp:504`, only at trace verbosity). It is just logged. No API exposes it.

### Proposed Implementation https://github.com/ggml-org/llama.cpp/pull/26130

1. Move the aggregation out of the print function into a `common/` function that returns the rows. The print renders those rows, and `--fit`'s copy folds into it; `llama-bench` and the router can use it instead of theirs.
2. Report the rows on `/metrics` with a `device` label, and as JSON on `GET /memory` behind its own `--memory` flag (the `--slots` pattern: one flag per endpoint). Same internal task path.

Why `/metrics` for the Prometheus surface: it already exists, already gated, already works in router mode - and VRAM in Grafana is useful to more people than me. Why not `/props`: it is built to answer while the model is unloaded (`server-context.cpp:4526` makes touching the context a compile error), and free memory changes at runtime.

The `device` label is the backend's own name (`CUDA0`, `MTL0`, `Vulkan1`) - the same one `--list-devices` prints and `--device` accepts - so a caller can attribute memory to a specific card.

Flagging up front:

- `memory_total_bytes` / `memory_free_bytes` come straight from `ggml_backend_dev_memory()`, which has known bugs on some backends (#20858 Vulkan underflow, #24906 ROCm). Report as-is; fix those at the source.
- The `/metrics` writer formats every value as a `double`, which rounds past 6 significant digits. Byte counts need that fixed, and `prompt_tokens_total` is already affected past a million tokens.

I have both surfaces working, each behind its own flag - PR follows this issue.
