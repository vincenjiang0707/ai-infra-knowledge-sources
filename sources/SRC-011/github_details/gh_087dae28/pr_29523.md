# [PR #29523] speculative : lag the MTP catch-up decode to restore multi-GPU prefill

source: https://github.com/ggml-org/llama.cpp/pull/29523
state: closed | updated: 2026-09-27T09:24:29Z
labels: model

## 正文

Fixes #27428.

The MTP catch-up reads the target's hidden rows through `llama_get_embeddings_nextn(ctx_tgt)`. That read forces the target's ubatch to complete before the MTP batch can be built, so on a `--split-mode layer` setup the next device cannot start the following ubatch and the pipeline overlap is lost. A single GPU has no overlap to lose, which is the asymmetry reported in the issue. Generation is unaffected: a generation step is one small batch with no next ubatch to overlap with.

This lets the catch-up lag one logical batch behind the target:

- the target context keeps two pinned host views of the nextn rows, each with a backend event recorded after its async D2H copy. MTP consumes the previous view and waits only on that view's event, never on the decode in flight
- `process()` parks the batch instead of decoding it immediately. Intermediate prompt chunks request no logits, so nothing reads them that turn and they can lag safely. The final prompt chunk and every generation batch do request logits and stay on the synchronous path that sampling correctness needs
- `begin()` and `draft()` flush whatever is parked against the current view before they read

Two supporting changes, both needed for the above to pay off:

- **the MTP context is excluded from pipeline parallelism.** Its single block gains nothing from it, and since the scheduler hands each newly allocated graph the next of its input copies, MTP alternating the catch-up and draft graphs made every draft graph see a new input address and re-record its CUDA graph instead of replaying it
- **the MTP context reserves a K/V-only graph**, since it consumes prompt batches only to populate its K/V and never runs the full-output pass the generic reserve sizes for

One more change rides along, because it is the same scheduler problem seen from the other side: an external mtmd decode moves the output-ring phase and leaves the scheduler in the embedding topology, so `llama_reset_after_external_decode()` forces a re-reserve before the next text batch. Without it, prompt processing in the same process drops by about a third after a few images and stays there until restart.

## Measurements

Two builds of `b29c606` (v0.4.1) differing only by this branch, same machine (2x RTX 3090, `--split-mode layer`, `--tensor-split 0.525,0.475`), Qwen3.8-27B hybrid (arch `qwen35`), `--spec-type draft-mtp`, `--ctx-size 262144`. Identical 10464-token prompt, greedy sampling, `cache_prompt: false` so every round pays the full prefill, 200 tokens generated, 3 rounds per arm.

| | prompt processing | generation |
|---|---|---|
| `b29c606` as released | 1132.0 t/s | 57.98 t/s |
| this branch | **1848.8 t/s** | 59.98 t/s |

Prompt processing is the warm rounds (2 and 3); including the cold first round the figures are 1111.5 and 1779.1 t/s, so +60% rather than +63%. Generation is the mean of all three rounds, with a round-to-round spread of 2.7% and 2.2% respectively — the small gain there is inside that spread, and draft acceptance was 71.4% in both arms, so nothing about generation is being traded away.

A note on measurement, in case it saves someone time: this cannot be benchmarked at a normal sampling temperature. MTP acceptance tracks how predictable the generated text is far more than it tracks any flag, and at `temperature 0.7` the spread *within* one configuration was as wide as the difference between configurations.

## Also fixes a silent startup fallback

On this configuration the released build fails to allocate the MTP draft context's compute buffer on the second device and quietly continues without pipeline parallelism for the rest of the run:

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 1226.06 MiB on device 1: cudaMalloc failed: out of memory
ggml_gallocr_reserve_n_impl: failed to allocate CUDA1 buffer of size 1285620224
graph_reserve: failed to allocate compute buffers
sched_reserve: compute buffer allocation failed, retrying without pipeline parallelism
```

Excluding the MTP context from pipeline parallelism removes this; the startup log is clean on the branch.

## Notes for reviewers

- The K/V-only graph path is implemented for `qwen35` only; other MTP architectures keep the existing behaviour. The lag itself is architecture-independent.
- A branch with this and the graph-reuse change together, for anyone who wants to build both at once: https://github.com/Nilline/llama.cpp/tree/issue-27428-mtp-prefill
