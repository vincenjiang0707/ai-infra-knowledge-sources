# [Issue #26912] [RPC] SET_ROWS can write past an output tensor buffer in release builds

source: https://github.com/ggml-org/llama.cpp/issues/26912
state: closed | updated: 2026-09-27T01:21:07Z
labels: stale

## 正文

### Name and Version

`ggml-rpc-server` at commit `15586e2d7165` (tag `b10298`), tested on Linux with ASan and plain RelWithDebInfo builds.

### Affected Module

The ggml RPC backend (`ggml/src/ggml-rpc`) and the CPU `SET_ROWS` kernel.

### Problem description

I found the write-side counterpart to the GET_ROWS out-of-bounds read reported in #26825. An RPC client can send a GRAPH_COMPUTE request with mismatched SET_ROWS tensor shapes, causing the worker to write attacker-controlled data past the output buffer.

ggml_set_rows() requires dst.ne[2] == src0.ne[2] and dst.ne[3] == src0.ne[3], but RPC graph reconstruction bypasses these checks. The CPU kernel only checks them with plain assert(), which is removed when NDEBUG is enabled.

The output offset is also controllable. ggml_nbytes() does not include a dimension's stride when its size is 1, so setting dst.ne[2] = 1 leaves dst.nb[2] out of the RPC buffer-size check. With src0.ne[2] = 2, the kernel reaches i02 = 1 and writes at dst.data + dst.nb[2]. This gives the client a controlled overwrite at a chosen offset relative to dst; it is not an arbitrary write to any process address.

The victim buffer’s sentinel values (100, 200, 300, 400) were replaced with the src0 payload (41, 42, 43, 44). This is a direct overwrite rather than an accumulation, even though the SET_ROWS graph never referenced the victim buffer.

### Expected behavior

The RPC server should reject a SET_ROWS graph with incompatible tensor shapes before running the kernel.

Replacing assert(ne2 == ne02) and assert(ne3 == ne03) with GGML_ASSERT prevented the write in both builds. A valid SET_ROWS request still produced the expected output. Rejecting the malformed graph at the RPC layer would be preferable to aborting the process.

### Scope and AI use

This uses the same RPC graph-reconstruction path as #26825. I am reporting it as a regular issue because `SECURITY.md` says the RPC backend should not be exposed to an untrusted network and the private disclosure program is currently disabled.

I used Claude Code for static analysis and to draft the PoC. I reviewed the relevant code and verified the PoC and test results myself.

### Omar0Gamal · 2026-08-11

Thanks for discovering and reporting this!

I've opened a [PR](https://github.com/ggml-org/llama.cpp/pull/26933) with a patch

The fix adds a pre-execution validation loop inside rpc_server::graph_compute. It strictly verifies that the ne[2] and ne[3] dimensions of dst and src0 match for GGML_OP_SET_ROWS before passing the graph to ggml_backend_graph_compute. If a dimension mismatch is detected, the server cleanly aborts the request, preventing the OOB write.
