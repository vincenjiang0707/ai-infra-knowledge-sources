# [Issue #29411] Misc. bug: Hexagon ADD reads wrong rows when dim 1 broadcasts across dim 2 slices

state: open | updated: 2026-09-26T23:24:17Z

## 正文

### Name and Version

Current upstream `master` at `f805c57a2d0b7cc171e599303ce2040f6e1bfe15` (the same path is present in `6e0962b6f60b73ec9e6c0d428d4503151a8ee3d3`).

### Backend

Hexagon HTP, `GGML_OP_ADD` with F32 or F16 operands.

### Problem description and steps to reproduce

Use `src0` with GGML dimensions `[N, R, B, 1]` and `src1` with dimensions `[N, 1, B, 1]`, where `N > 1`, `R > 1`, and `B > 1`. For example, `[128, 4, 8, 1]` plus `[128, 1, 8, 1]`. Fill each dim-2 slice of `src1` with a distinct finite value and compare `ggml_add(src0, src1)` on HTP with CPU. Every row in a dim-2 slice should use the same `src1` row. The reported symptom is `FLT_MAX` / `inf` output.

Static code-path analysis shows a mismatch:

1. [Host dispatch](https://github.com/ggml-org/llama.cpp/blob/f805c57a2d0b7cc171e599303ce2040f6e1bfe15/ggml/src/ggml-hexagon/ggml-hexagon.cpp#L5001-L5006) classifies this as `HTP_BINARY_KERNEL_SAME_SHAPE`: `ne11 == 1` satisfies `is_same_shape`, but `ne12 > 1` excludes `HTP_BINARY_KERNEL_ROW_BCAST`.
2. [The same-shape HTP worker](https://github.com/ggml-org/llama.cpp/blob/f805c57a2d0b7cc171e599303ce2040f6e1bfe15/ggml/src/ggml-hexagon/htp/binary-ops.c#L502-L516) starts at `i11 = 0` but copies `current_block_size` `src1` rows with source stride `nb11`. When a block contains at least two rows, the second copy reads the next dim-2 slice instead of repeating the current row. The last slice can read past `src1`.

The existing [binary broadcast test cases](https://github.com/ggml-org/llama.cpp/blob/f805c57a2d0b7cc171e599303ce2040f6e1bfe15/tests/test-backend-ops.cpp#L9700-L9730) do not appear to include this exact shape pattern.

This report is based on source analysis and the reported output symptom; I do not have an on-device log to attach.
