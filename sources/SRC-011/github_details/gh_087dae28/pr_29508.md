## 正文

## Overview

As discussed in https://github.com/ggml-org/llama.cpp/pull/29292#issuecomment-5794058932, this is the separate PR that aligns `__CUDA_ARCH__` with the HIP approach.

`__CUDA_ARCH__` is defined in `vendors/hip.h`, but it was never defined for MUSA. Every architecture test in the shared `ggml-cuda` sources therefore evaluated to 0, and the kernels guarded by them were compiled with an empty body and still launched. `dequantize_block_q8_0_f16`, guarded by `__CUDA_ARCH__ >= GGML_CUDA_CC_PASCAL`, was one of them: every `q8_0` dequantization produced garbage.

Two changes in this PR:

- `vendors/musa.h`: define `__CUDA_ARCH__` as `GGML_CUDA_CC_RUBIN` (1300), the way HIP does, and explicitly exclude the NVIDIA-only features that this value would otherwise enable — `TURING_MMA_AVAILABLE`, `AMPERE_MMA_AVAILABLE`, `CP_ASYNC_AVAILABLE`, `__reduce_add_sync`, the Ampere/Pascal-DP4A MMQ and MMVQ configurations and `__bfloat1622float2`. The definition is scoped to the device pass (`#ifdef __MUSA_ARCH__`): CUB tells host from device code with `defined(__CUDA_ARCH__) || defined(__MUSA_ARCH__)` in `cub/util_debug.cuh`, which is also how nvcc behaves.
- `convert.cu`: carry over the `dequantize_block_iq4_nl` short-row guard from #29292 (cherry-picked with `-x`), so that this PR can replace it.

NVIDIA and HIP builds are unaffected: `defined(__MUSA_ARCH__)` is false there, and the added `!defined(GGML_USE_MUSA)` conditions are no-ops. The host pass is unchanged as well — with the definition scoped to the device pass, the feature macros stay undefined for MUSA exactly as before.

## Additional information

Measured with `test-backend-ops` on an MTT S5000 (MUSA SDK 5.2, MUSA architecture `31`, driver 5.2.0-server), single card, built with `-DGGML_MUSA=ON -DGGML_BACKEND_DL=ON -DLLAMA_BUILD_TESTS=ON`:

| build | `test-backend-ops` |
| --- | --- |
| master | 12458/12507 — 49 failures: 31x `MUL_MAT_ID` and 18x `MUL_MAT`, all `type_a=q8_0`, `NaN` or error above tolerance |
| this PR | 12507/12507 |

`MUL_MAT_ID` alone: 899/929 on master, 929/929 here. The failing case is exactly the one that reaches `batched_mul_mat_traits<GGML_TYPE_F16>::convert` for quantized `src0`. CUB-based ops (`ARGSORT`, `TOP_K`, `SUM`, `CUMSUM`, `MEAN`, `SSM_SCAN`) are 682/682, and the same tree also builds for `MUSA_ARCHITECTURES=21;22;31` (only `31` was run on hardware). Model smokes (Qwen3-0.6B-Q4_K_M with `-fa on -ctk q8_0 -ctv q8_0`, and `llama-bench`) are unchanged to within noise, and the backend capability list for MUSA is byte-identical to master.

The first commit fixes the `q8_0` case; the second one is #29292's other fix, which is backend independent.
