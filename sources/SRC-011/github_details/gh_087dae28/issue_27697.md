### Problem description & steps to reproduce

When the audio duration is an exact multiple of 30 seconds (or falls within approximately 20ms of the end of a 30-second cycle), the Whisper audio preprocessor generates an extra audio chunk and encodes it separately. This additional chunk consists entirely of trailing padding (silence) and contains no actual audio. In the logs, this manifests as `total = 4` instead of `total = 3` (or `5` instead of `4` for 60-second audio), resulting in an extra encoding operation taking about 550ms.

The Mel spectrogram has approximately 3,001 frames of padding appended to the end. The chunking logic slices the audio every 3,000 frames. When the number of actual audio frames is a multiple of 3,000 (or exactly one less), this padding fills a complete 3,000-frame window; consequently, it is encoded as a normal chunk rather than being discarded. The "skip last incomplete chunk" check in the code (`if (n_len < frames_per_chunk) break;`) only catches incomplete padding chunks; it fails to catch padding chunks that fill a complete window. (Location: `mtmd_audio_preprocessor_whisper::preprocess` in `tools/mtmd/mtmd-audio.cpp`, lines ~597–601.)

The transcription output is unaffected—I compared the output before and after the fix, and it is byte-identical. Therefore, this is a performance and context-usage issue, not a correctness one.The cost is an extra ~187 context tokens (all silence) and ~550ms of encoding time per instance. While the hit rate might appear low (random durations have a ~0.067% chance), slicing long audio into fixed 30-second segments is a common practice in speech processing pipelines, meaning such callers would trigger this issue for every segment.

Based on the code, the `qwen3a` and `gemma4a` preprocessors in the same file already use the "number of valid frames" as the upper bound for the loop and do not suffer from this issue; only the Whisper preprocessor uses the "total length including padding."

I believe the fix is ​​to have the chunking loop terminate when the remaining frames consist entirely of padding (by using the number of valid audio frames as the upper bound). The change is minimal, and I am willing to submit a PR, but I would like to confirm first if the maintainers agree with this approach.

Steps to reproduce:
1. Create a 16 kHz mono WAV whose length is exactly 480000 samples (30.00 s).
2. Run: llama-mtmd-cli -hf ggml-org/Voxtral-Mini-3B-2507-GGUF --audio 30s.wav -p "T." -n 1 --no-warmup
3. The log shows the audio encoded twice (total = 4) instead of once (total = 3).

|--------------|---------|----------------|----------|

Hi @hera2019 , thanks for the detailed report!

I just independently reproduced this issue on _Windows x64 (MSVC Debug, CPU-only)_ using llama-mtmd-cli with Voxtral Mini 3B. I can confirm your findings regarding the phantom chunk.

I also tested the exact boundaries, and the extra chunk actually triggers slightly before 30 seconds due to the hop length and padding math. Here are my observations based on the emitted audio_tokens->n_tokens (187 per chunk):

By tracking audio_tokens->n_tokens (187 per chunk) in the verbose log, I found that the phantom chunk actually triggers slightly before 30 seconds due to the hop length and padding math:
- 29.989625s (479,834 samples): Emits 1 chunk as expected
- 29.990000s (479,840 samples): Emits 2 chunks (triggers phantom chunk)
- 30.000000s (480,000 samples): Emits 2 chunks instead of 1
- 60.000000s (960,000 samples): Emits 3 chunks instead of 2

I fully agree with your analysis. In mtmd_audio_preprocessor_whisper::preprocess(), the padding algorithm appends 480,000 zero samples to fill the encoder window. For a 30s input (480,000 samples), this produces floor((480000 + 480000) / 160) + 1 = 6001 mel frames. The split loop then chunks this into two 3000-frame blocks, where the second block is 100% padding phantom chunk.

The padding itself cannot be removed, but we should restrict the total valid chunks using the original PCM sample count (e.g., ceil(original_samples / 480000)). Also worth noting: this shared preprocessor path affects other models as well.
