# [Issue #28778] SYCL: DFlash2 draft model triggers GPU driver TDR reset (VIDEO_TDR_TIMEOUT_DETECTED) on dual Arc Pro B70

source: https://github.com/ggml-org/llama.cpp/issues/28778
state: open | updated: 2026-09-26T02:46:07Z
labels: 

## 正文

## Summary

Loading a DFlash2 draft model (`--model-draft`) on the SYCL backend against dual Intel Arc Pro B70 GPUs causes a GPU driver TDR (Timeout Detection and Recovery) event — Windows force-resets the GPU driver — rather than a normal crash or clean load. The process disappears with no application-level error logged; the only trace is a `LiveKernelEvent` (Bug Check `0x141` = `VIDEO_TDR_TIMEOUT_DETECTED`) in the Windows Application event log, occurring on both GPUs across repeated attempts. GPU driver status recovers to `OK` afterward, but the server never comes up.

## Environment

- Build: `b10883` (commit `91f6a6cf3`), official Windows SYCL x64 binary, `version: 0.4.0-dev (build 10883, commit 91f6a6cf3)`
- Hardware: 2x Intel Arc Pro B70 (32GB each)
- OS: Windows (native), Level-Zero runtime, driver `32.0.101.8805`
- Target: Qwen3.8-27B UD-Q6_K_XL GGUF (unsloth)
- Draft: Qwen3.8-27B-DFlash2 Q8_0 GGUF (z-lab/Qwen3.8-27B-DFlash2-GGUF)
- `--spec-type` not passed; auto-detected as `draft-dflash` from draft model metadata (confirmed in logs before the hang)

## Repro

```
set UR_L0_ENABLE_RELAXED_ALLOCATION_LIMITS=1
set ZES_ENABLE_SYSMAN=1
set GGML_SYCL_ENABLE_VMM=0

llama-server.exe ^
  -m Qwen3.8-27B-UD-Q6_K_XL.gguf ^
  --model-draft Qwen3.8-27B-DFlash2-Q8_0.gguf ^
  -ngl 99 -np 1 -c 131072 -t 8 ^
  --load-mode dio -ctk q4_0 -ctv q4_0 ^
  -b 2048 -ub 2048 -fa on --jinja --reasoning off ^
  --metrics --host 127.0.0.1 --port 9019
```

No `--split-mode` flag is passed (default layer/pipeline split across the two GPUs) — this is not the tensor-parallel-specific issue reported separately for the CUDA backend (see linked issue).

## Observed

Console output reaches this point and then the process silently disappears (varies run-to-run exactly how far it gets before vanishing — sometimes right after tensor-warning lines, sometimes after the speculative implementation is registered):

```
I spec common_specu: auto-detected speculative type 'draft-dflash' from the draft model metadata
I srv    load_model: loading model '...Qwen3.8-27B-UD-Q6_K_XL.gguf'
E llama_init_from_model: failed to initialize the context: dflash requires ctx_other to be set (this warning is normal during memory fitting)
W operator(): failed to measure the memory of the extra model, fitting without it: failed to create llama_context from model
... (unused-tensor warnings for blk.64.* — expected, same as non-crashing loads)
I cmn          init: llama threadpool init, n_threads = 8
I common_speculative_init_result: loading draft model '...Qwen3.8-27B-DFlash2-Q8_0.gguf'
I srv    load_model: initializing, n_slots = 1, n_ctx_slot = 131072, kv_unified = 'false'
I common_speculative_impl_draft_dflash: adding speculative implementation 'draft-dflash'
I common_speculative_impl_draft_dflash: - n_max=3, n_min=0, p_min=0.00
I common_speculative_impl_draft_dflash: - block_size=8, mask_token_id=248070, n_extract=5, sample_from_anchor=true
```
— then nothing. No further stdout/stderr, no application-error event (Event ID 1000), process no longer present in `tasklist`.

Windows Application event log (via `Get-WinEvent`), timestamped to match the hang, on every attempt (reproduced 3x with different process-launch methods — direct WSL exec, detached WSL background, and native PowerShell `Start-Process` — ruling out a launcher artifact):

```
Provider: Windows Error Reporting
Event ID: 1001
Event Name: LiveKernelEvent
Problem signature: P1: 141   (Bug Check 0x141 = VIDEO_TDR_TIMEOUT_DETECTED)
```

Multiple such events fired per attempt (both GPU device contexts affected, based on distinct P3 addresses corresponding to the two cards). `Get-WmiObject Win32_VideoController` reports `Status: OK` on both GPUs after each hang — the driver recovers, but the model never loads.

For comparison, the same target model with native MTP drafting (`--spec-type draft-mtp`) loads and serves normally on this exact hardware/build family (production config, no TDR events).

## Expected

DFlash2 should load and serve without hanging the GPU driver, matching the behavior of native MTP speculative decoding on the same hardware.

## Notes

- Not reproducible as a normal segfault/exception — no Application Error (Event ID 1000) is ever logged, only the driver-level TDR event, suggesting whatever DFlash2-specific kernel/operation is dispatched here enters a state the Level-Zero/SYCL driver cannot recover from within the timeout, rather than crashing outright.
- Happy to test a patched build or provide `sycl-ls` output / additional driver diagnostics if useful.
