## Overview

As per discussion in #25863 , implement the ring buffer mechanism for input tensors, on top of @am17an 's sanitizer (#26167), plus additional hardening for the sanitizer and extra scheduler fixes (there was an error with duplicating pinned memory that was a view's base).

## Additional information

Makes host buffers viable again, ping @ORippler for feedback / tests on CUDA integrated boxes. No measurable efficiency losses.

Supersedes #25863 , #26167 , #26225

Moved all scheduler documentation to a dedicated doc.

@nabe2030 asked whether the ring buffer fixes the MTP collapse from #27572, so I ran the comparison directly on the affected hardware before anything else got built on top of it. Three builds were tested under identical conditions on AMD Strix Halo (gfx1151, 128GB unified, ROCm 7.2.2, Qwen3.8-27B-UD-Q4_K_XL + mmproj-F16): variant A is current master `d222767c7` plus the six-line fix from #27572 (a `ggml_backend_sched_synchronize(sched.get())` immediately before `res->set_inputs(&ubatch)` in `llama_context::process_ubatch()`), variant B is this PR at `b3823d816`, and variant C is stock master `d222767c7` as the control. All three were built with `-DGGML_HIP=ON -DAMDGPU_TARGETS=gfx1151 -DCMAKE_BUILD_TYPE=Release` and launched with the same flags as the original issue (`-np 4 -c 1048576 -b 1024 -ub 256 -fa on -ctk q4_0 -ctv q4_0 --spec-type draft-mtp --spec-draft-n-max 4 --metrics`), and each variant ran the same three tests in order: a sequential sanity check of one request with a ~19k-token prompt, the concurrent reproducer from #27572 (4 threads × ~19k prompts × 2 rounds, the script already attached to that issue), and a throughput benchmark at temp 0 with 3-run medians across four prompt sizes.

All three variants pass the sequential test, confirming the race requires concurrency as described in #27572. The stock-master round-1 failures produced completions of 7, 33, and 5 tokens with empty content after short reasoning — the exact symptom from the original report.

**Throughput parity (temp 0, 3-run median):**

| Prompt tokens | A pp t/s | B pp t/s | A tg t/s | B tg t/s |

The stock-master benchmark is omitted since the server is racing and the numbers are meaningless. A and B are within 1–4% on prefill and 0–1% on generation, which is within run-to-run noise on this rig — the ring buffer costs nothing measurable on a single-GPU spec-decode workload.

**Conclusion:** this PR resolves #27572 in addition to the multi-slot corruption and the #27579 tool-array corruption that @nabe2030 already verified against it, making it the fourth issue closed by the input ring buffer. The sched-synchronize variant remains a valid minimal backport for release branches, but the ring buffer is the better fix architecturally since it removes the host stall entirely rather than extending it to single-GPU setups, and it enables host/GPU overlap that the synchronize approach structurally cannot provide. ### 1. Sanitizer race counts under realistic load

`GGML_SCHED_SANITIZE=1` + `GGML_SCHED_SANITIZE_NONFATAL=1`, `--parallel 8`, MTP off,
n=20 completions:

| | races detected |
|---|---:|
| ring on | **0** |
| ring off | **3597** — all `RACE (write-after-read) on ROCm_Host[...]` |

@frizikk reported 18 races over 4 prompts × 3 rounds earlier in this thread. Different
workload, so not a ratio to read literally, but the point is that what shows up as a
handful of races on a light probe is two orders of magnitude more frequent under a
ShareGPT-style server load — and every one of them lands in the HIP host buffer, which
is exactly what this PR is protecting.

### 2. Multi-slot output corruption, concurrency sweep (MTP off)

Generated text captured and checked, n=20 per cell:

| | c=8 | c=16 | c=32 |
|---|---|---|---|
| ring on | 0/20 flagged | 0/20 | 0/20 |
| ring off | 20/20 flagged | — | — |

Ring off reproduces the known signature (repeated `/`) at 100%. This is independent of
speculative decoding — MTP is off in all of these.

### 3. Tool-array corruption (#27579), single slot

29,355-token prompt, 17 tools, `--parallel 1`, n=16, model asked to name its own tools:

| | correct |
|---|---|
| ring on | **16/16** |
| ring off | 4/16 |
| stock master `d222767c7`, no PR | 3/16 |

The stock-master row is the control for the caveat above: ring off and stock master sit at
the same level, so the improvement is the ring and not the PR's other changes.

This failure mode is worth separating from the degenerate-text one. The output stays
completely fluent and the model confidently mis-states its own tool list — the head of the
array is gone and nothing in the response says so. It passes every "does this look sane"
check, which is why we scored an earlier single-slot run as clean when it was not.

### 4. MTP acceptance (#27572) — independent confirmation

@ByungHyun21 already settled this above with a cleaner three-way comparison. Ours agrees,
from a different harness (`--parallel 8`, 200 tasks, our own load generator rather than his
reproducer):

| | acceptance | output |
|---|---:|---|
| ring on | 0.5083 | 0/200 flagged |

### 5. vLLM control on the same silicon

Worth stating since "gfx1151 is just broken" comes up whenever these reports appear: on
this same machine, vLLM through ROCm/HIP is clean at concurrency 1 through 32 (0/20 flagged,
every cell), as is Vulkan. Those are earlier measurements from our own investigation, not
re-run against this PR — vLLM is unaffected by a llama.cpp scheduler change — but they do
place the defect in the llama.cpp HIP path rather than in ROCm or the hardware.

One environment note that may be useful to others reporting here: our "ROCm 7.14" builds
turned out to be linking the 7.2.2 runtime at execution time, because no RUNPATH was set
and the SONAME resolved to the system default. Compiler version and runtime version are
easy to conflate on a machine with both installed. Everything above is 7.2.2 runtime
throughout, so the comparisons are internally consistent — but it means this thread now has
the same defect reproduced across 7.2.2, 7.2.4 (@DeMaulwurfn) and TheRock 10.1.0
(@Superfish1000).

quite right — there is a small, reproducible cost, and it is not in the ring.

Okay, this is the mechanism:
