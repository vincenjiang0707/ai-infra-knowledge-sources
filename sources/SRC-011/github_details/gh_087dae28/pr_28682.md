# [PR #28682] chat: add dedicated Ling 3.0 (Bailing V3) parser

state: closed | updated: 2026-09-26T21:13:34Z

## 正文

## Overview

Ling 3.0 templates pre-open <think> in the generation prompt, so the model never emits an opening tag and tool calls can appear before `</think>`. The generated parser classified that output entirely as `reasoning_content` and clients received `content=""` with no `tool_calls`.

This adds a dedicated Ling parser (modeled on the hand-written Qwen3-Coder and Kimi parsers) that terminates reasoning at `</think>` or a tool-call marker, prefers the close tag when both are present, defers the streaming split to the final parse so delivered deltas are never reclassified, and keeps trailing prose after the last tool call as content. Adds the Ling 3.0 Flash chat template (byte-identical to the GGUF-embedded template) and tests covering the unclosed-think tool call (full and streaming), closed-think paths, trailing prose, parallel calls, marker-like strings in argument values, and `reasoning_format=none`.

## Additional information

This builds upon the initial work that added BailingMoE 3 support #26608.  Ling 3.0 also emits stray byte-level tokenizer pieces that decode to invalid UTF-8, which hard-fails the parse layer with a 500.  That is fixed separately in #28724.  Please note that both changes are needed for reliable usage of Ling 3.0 Flash in llama.cpp.

Validated against Ling 3.0 Flash GGUF on llama-server with `--jinja --reasoning-format deepseek`. With this parser and #28724 applied, a 29-task agentic benchmark went from 5 reasoning-only tool-call stops and 1 parse `500` to 0 of both.

### pwilkin · 2026-09-10

Models doing tool calls inside reasoning is generally a model bug. We don't want to adjust the parser behavior to support model bugs because fundamentally it usually results in reduced quality anyway. The only exceptions are when the behavior is so common (and present in high quantization versions) that it can be justifiably explained as actual trained model behavior, but we certainly don't want this to become the standard.

### aetherbird · 2026-09-10

> Models doing tool calls inside reasoning is generally a model bug. We don't want to adjust the parser behavior to support model bugs because fundamentally it usually results in reduced quality anyway. The only exceptions are when the behavior is so common (and present in high quantization versions) that it can be justifiably explained as actual trained model behavior, but we certainly don't want this to become the standard.

A tool call emitted before `</think>` is not model misbehavior in Ling 3.0 Flash: the template's generation prompt pre-opens `<think>` (the model never emits an opening tag), so tool calls in an unclosed think block are the template's defined output format.  InclusionAI's reference stack parses the same shape (vLLM/SGLang, `--tool-call-parser ling3`).

Master's hand-written parsers already terminate reasoning at non-think boundaries: `common/parsers/qwen3-coder.cpp` and `common/parsers/deepseek.cpp` at tool-call markers, `common/parsers/kimi-k3.cpp` at a response boundary. The change puts the generated parsers on the same behavior.

The close tag in this change is preferred.  A `<tool_call>` appearing inside reasoning text does not end the reasoning block when a real `</think>` follows (Reka-Edge template test). Streaming defers the split to the final parse, so delivered deltas are never reclassified.

The UTF-8 tolerance commit changes no parsing rules. Invalid bytes are skipped and rendered as U+FFFD.  Everything around them parses by the unchanged rules.  This can be split into its own PR if needed.

### aetherbird · 2026-09-11

72ddff5c0 adds handling for Ling's end-of-turn token.

`<|role_end|>` is the registered EOS for this tokenizer. The model sometimes spells it out as text tokens instead of emitting the control token, which does not stop generation, so it leaks into content. This is the same failure class the autoparser handles for Laguna's `</assistant>` with a literal stop string.  

This registers `<|role_end|>` as an additional stop and consumes it in the parser if it still reaches the text. Tests cover both paths.
