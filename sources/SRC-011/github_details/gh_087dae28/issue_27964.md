### Problem description & steps to reproduce

Qwen3.8-Flash-Next aborts before server readiness when using `--split-mode tensor` on 2x RTX 5090 / CUDA.

The same model and hardware work correctly with `--split-mode layer`.

The failure is:

```text
ggml/src/ggml-backend-meta.cpp:537:
GGML_ASSERT(ret.axis != GGML_BACKEND_SPLIT_AXIS_UNKNOWN) failed
```

I reproduced the tensor-split failure with both KV cache configurations:

```text
layer  1,1 + Q8_0 K / Q8_0 V -> OK
tensor 1,1 + Q8_0 K / Q8_0 V -> ASSERT

tensor 1,1 + Q8_0 K / Q5_1 V -> ASSERT
```

A later `layer` split test with the same `-ts 1,1` ratio also started and served requests successfully, so the `1,1` tensor split ratio itself does not appear to be sufficient to trigger the failure.

There is no DFlash2 drafter, MTP drafter, or speculative decoding involved in this reproduction.

One preserved reproduction used Q8_0 K / Q5_1 V with CUDA graphs disabled:

```shell
GGML_CUDA_DISABLE_GRAPHS=1 \
./llama.cpp/build/bin/llama-server \
  -m /path/to/Qwen3.8-Flash-Next-AD-4.27bpw-Q4_K_M-M64-00001-of-00033.gguf \
  -lm mmap \
  -dev CUDA0,CUDA1 \
  -ngl all \
  -sm tensor \
  -ts 1,1 \
  -fit off \
  -ctk q8_0 \
  -ctv q5_1 \
  -c 261888 \
  -np 1 \
  -b 1024 \
  -ub 128 \
  -fa on \
  --jinja
```

The process aborts with exit code 134 before `/health` becomes ready. GPU memory is reclaimed after the abort, and no CUDA OOM is involved in this failure.

I also reproduced the same `SPLIT_AXIS_UNKNOWN` assertion using Q8_0 K / Q8_0 V.

Possibly related to #27829 and #26902.

#27829 reports the same assertion with Qwen3.8-27B + DFlash2 on ROCm. This reproduction is different because it uses Qwen3.8-Flash-Next on CUDA without DFlash2, MTP, or any speculative drafter.

#26902 reports the same assertion with CUDA tensor split, but with a different model architecture and 4x Tesla T10 GPUs.

This may indicate that the tensor split metadata issue is not specific to DFlash2.
