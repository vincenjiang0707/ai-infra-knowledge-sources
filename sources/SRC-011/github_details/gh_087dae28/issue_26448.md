# [Issue #26448] Feature request: run MoE expert weights from host RAM via PCIe DMA (no H2D copy) — 23GB MoE on 1.6GB VRAM, 81GB Qwen3-235B on 8GB cards

source: https://github.com/ggml-org/llama.cpp/issues/26448
state: open | updated: 2026-09-27T01:21:12Z
labels: stale

## 正文


## TL;DR

For MoE models, keep expert weights in host memory (pinned buffer) and let cuBLAS read them **directly over PCIe DMA** — never copy experts into VRAM. Non-expert layers stay in VRAM as usual. Result (RTX 4090, real measurements):

| Model | Standard (all-in-VRAM) | This approach | VRAM saved | Speed |
|---|---|---|---|---|
| DeepSeek-V2-Lite Q2_K (23.3GB) | 23.3GB VRAM, 65 t/s | **1.6GB VRAM, 37.5 t/s** | −93% | 58% retained |
| Qwen3.6-35B-A3B (11GB) | OOM on 8GB cards | **2.1GB VRAM, 46.8 t/s** | — | ≈ parity |
| Qwen3-235B-A22B Q2_K (81.7GB) | impossible on consumer GPUs | **8GB VRAM (verification in progress)** | — | TBD |

## Motivation

The biggest real-world MoE use case is running a large model on a small GPU. With all experts in VRAM, an 8GB card tops out around a 7-8B dense or a ~11GB MoE. But MoE experts are only *activated* sparsely (2-8 of 256 per token) — the full weight set doesn't need to live on the GPU. The bottleneck is that llama.cpp's offload path copies expert weights H2D per layer (see #25859), and the `--n-cpu-moe` path computes experts on CPU (slow).

## Proposed approach (high level)

1. Load expert weights into a **host pinned buffer** (not GPU VRAM, not anonymous mmap that gets evicted).
2. Run the expert matmuls on GPU via **cuBLAS operating directly on host pointers** — the CUDA driver DMA-reads the expert weights from host RAM over PCIe on demand, per activated expert. No H2D staging copy, no per-layer streaming.
3. VRAM holds only non-expert layers + KV cache. For DS-V2-Lite that's ~1.6GB total.
4. Optional: a small expert cache (a few slots, LRU) that D2D-copies the *hot* experts into VRAM once and reuses them — helps when the same experts fire repeatedly (e.g. long prompts / codegen patterns).

## Measured results (RTX 4090, 2026-08-02)

- **DeepSeek-V2-Lite Q2_K**: VRAM 23.3GB → **1.6GB**; speed 37.5 t/s (vs 65 t/s fully offloaded — reasonable PCIe price for −93% VRAM). Expert cache at 0.25: prompt throughput 99 → **308 t/s (+211%)**, gen +5%.
- **Qwen3.6-35B-A3B**: VRAM **2.1GB**, 46.8 t/s — an 11GB MoE that OOMs an 8GB card normally, now runs on ~2GB with near-full speed.
- **Qwen3-235B-A22B Q2_K (81.7GB)**: download in progress; target: run on 8GB VRAM (experts ~80GB in host RAM + PCIe DMA).

## Why this is different from existing work

- #26414 (pin hot experts in RAM via mlock): keeps experts in *system RAM* but still computes them on CPU (or pages them back) — this keeps expert compute on **GPU** with DMA reads.
- #25859 (-ncmoe H2D copies serial): that path still copies weights into VRAM per layer; this approach reads them **in place from host memory** — the copy disappears entirely.
- #23855 (spill-over / MoE GPUs): multi-GPU layout question; orthogonal.

This also composes with existing features: `--n-cpu-moe`-style flag to select the expert storage mode, GGML_OP_OFFLOAD_MIN_BATCH to control when offload kicks in, and the expert cache as an optional accelerator.

## Update 2026-08-07: on-demand pin main path — V4-Flash 5× faster on 4090

We shipped the "lazy mmap + pin-on-first-touch" approach this issue is about, as the new default path (v0.7.1 / bins-v0.3.1).

**New numbers (RTX 4090, multi-arch build, CUDA 12.8):**

| model | before (lazy, no pin) | now (on-demand pin) |
|---|---|---|
| Qwen3.6-35B-A3B (32B MoE) | 11.6 t/s | **50.2 t/s** |
| DeepSeek-V2-Lite (16B MoE) | 11.6 t/s | **37.9 t/s** |
| DeepSeek-V4-Flash (157B MoE, 85 GB) | 1.7-2.0 t/s | **10.1 t/s** (5×) |

**How:** experts stay in lazy mmap (zero VRAM, no load-time RAM spike — the 85 GB V4 loads in seconds). On first GPU touch, the page range is mprotect + cudaHostRegister'd (merge-registration so every copy source stays inside a single registered range).

**A CUDA gotcha worth knowing (CUDA 11.8):** `cudaMemcpyAsync` fails with `invalid argument` when the source spans **multiple** `cudaHostRegister` ranges — even adjacent ones. Registering only the uncovered segments (which fragments the range) crashes; the fix is to unregister the neighbouring ranges and re-register them as one merged range. We hit this hard during bring-up; the pintest repro + fix are documented in our repo.

Binaries: one multi-arch build (sm_61 → sm_120a, CUDA 12.8) via https://github.com/yalun753/moe-l2/releases/tag/bins-v0.3.1 · `pip install moe-l2` (0.7.1)


### PmNz8 · 2026-08-07

The results seems to be very good. But is this scenario so performant only when model size + context size < VRAM + RAM size? Or does it help in case of disk streaming as well?

### yalun753 · 2026-08-07

Good question — the design covers both, with a performance gradient.

**Our stack is 3-tier by intent:** L1 GPU VRAM (hot experts, A3 cache) → L2 host RAM (lazy mmap + on-demand pin) → L3 SSD (cold experts, page-fault on first touch). Disk streaming is part of the design, not an afterthought.

**Case A — model fits in RAM (your premise):** whole-tensor pin keeps everything resident → fastest. That's the 10.1 t/s on 4090 (V4 85 GB on a 1 TB-RAM box, RSS ~81 GB).

**Case B — model exceeds RAM (disk streaming):** experts stay in lazy mmap; first GPU touch faults the page in from SSD, and our expert-page eviction (v3.1: fixed-expert-count LRU + madvise(DONTNEED)) drops cold pages so RSS stays capped. Measured with V4 on 2080 Ti / RTX 3080: full pipeline 0.89–2.22 t/s, RSS capped at 11–12 GB (vs 29 GB without eviction) — that run effectively used RAM as a hot cache with the SSD as backing store.

**The gradient:** all-RAM (10 t/s) > hot-in-RAM + eviction (1–2 t/s on 11 GB cards) > pure disk streaming (not yet benchmarked with model > RAM on a small box, e.g. 85 GB on 32 GB RAM — architecturally supported, but repeated SSD faults dominate and we haven't measured that corner yet).

So yes, it helps in disk-streaming mode — that's exactly what the eviction tier targets; numbers degrade gracefully as you move down the memory hierarchy.

### yalun753 · 2026-08-08

Following up on the Guanaco discussion — we shipped **dynamic pin set (low-memory mode)** in v0.7.2 / bins-v0.3.2. Instead of registering the whole expert tensor on first touch, only the actually activated experts are registered (per-expert group registration), and the LRU evictor unregisters + madvises cold experts.

Measured on RTX 4090 / DeepSeek-V4-Flash (85 GB): **RSS 84 GB → 17-24 GB** (`MOE_L2_LRU_MAX_EXPERTS`), speed 4-5 t/s. V4 routes extremely wide — new experts pay a ~2.1 ms first-touch page-fault (0.43 ms page-lock + 1.7 ms read); WILLNEED prefetch, group batching and staged copies were all verified ineffective (physical limit for this access pattern). Default remains whole-pin at full speed (**10.1 t/s @ 82 GB**).

Bonus: dynamic pin also cuts model load time from ~52 s to ~10 s (no whole-file fault on startup).

Install: `pip install moe-l2` (v0.7.2); binaries: bins-v0.3.2 (sm_61-120a, CUDA 12.8, no NCCL).
