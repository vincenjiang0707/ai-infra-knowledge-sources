# [PR #29461] rpc: optional GGML_RPC_MAX_ALLOC_MB cap on device memory handed out by rpc-server

## 正文

## Overview

An `rpc-server` on a GPU that is shared with other consumers (desktop session, other apps) will keep allocating device memory for the client's buffers as long as the GPU has free memory: a big model load or KV growth can starve the rest of the machine.

This adds an optional hard cap. With `GGML_RPC_MAX_ALLOC_MB=<MiB>`, the server refuses any buffer allocation that would push the total device memory handed out past the cap, and `GET_DEVICE_MEMORY` reports the cap as the device total, so the client's memory planner sees the reduced budget and the model load fails cleanly on the client instead of the server silently draining the GPU. Unset or 0 = no cap; default behavior is unchanged.

## Changes

- `rpc_server`: new optional env `GGML_RPC_MAX_ALLOC_MB` (MiB)
  - `alloc_buffer`: refuses allocations that would exceed the cap and logs the request size and the in-use/limit values
  - `free_buffer`: returns the freed bytes to the budget
  - `get_device_memory`: clamps `total_mem`/`free_mem` to the cap
- no protocol change, no new API; 19 lines in `ggml-rpc.cpp`

## Perf check

None expected: the cap is one addition and one comparison per buffer allocation (model-load time); nothing in the compute path. With the env unset the behavior is unchanged.

## Additional information

Tested on a two-node RPC cluster (RTX 4070 12GB controller + RTX 5070 worker over 1GbE, Qwen3.8-27B recurrent hybrid, ~60% of the layers on the worker): with the cap set below the model's requirement the load fails fast with a clear log line on the server instead of allocating until the worker OOMs; with the cap set above it, serving is unaffected.
