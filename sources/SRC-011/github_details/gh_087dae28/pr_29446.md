## 正文

## Overview

This PR adds support for the `GraniteSpeech5ForCTC` model architecture to support https://huggingface.co/ibm-granite/granite-speech-5.0-470m-turboctc. The model is non-autoregressive (encoder-only) and therefore introduces some net-new code paths discussed below.

## Additional information

`llama.cpp` has had support for `/v1/audio/transcriptions` for a while, but the implementation has only served to send audio to a full multimodal audio-llm with a prompt requesting transcription. This PR extends that entrypoint to support STT-only models like `granite-speech-5.0-470m-turboctc`, along with implementing support for that model architecture.

Along with this additional path through `tools/server` and `tools/common`, this model poses a challenge in both `tools/mtmd` and `libllama` itself: The core model is itself just an audio projector (nearly equivalent to the encoder in the `mmproj` for `granite-speech-4.x`), but rather than projecting this into text-token space and running it through an LLM backbone, the encoded audio is simply sent through an output layer and converted directly into `logits`. This makes the model extremely fast, but breaks a lot of assumptions in both `mtmd` and `libllama`.

To work through these issues, this PR introduces the following changes:

- Since all model-outputs are expected to derive from `libllama`, we couldn't directly pull from an `mtmd` model and skip `libllama` entirely for these models. This meant needing to split the logic between `mtmd` in a degenerate `mmproj` and `libllama` for the main encoder-only CTC-encoder model.
- New public method in `common.h`: `common_ctc_greedy_decode`. This implements the non-generative encode + greedy sampling needed by this model. It should generalize well to other models with similar encoder-only non-sampling styles, though the naming may be something we want to make more general to include future uses.
- New public method in `llama.h`: `llama_n_outputs`. This exposes the internal `n_outputs` from `llama_context` so that the greedy decoding can get the correct number of non-blank logits.
- Auto-expand `cparams.n_batch` / `cparams.n_ubatch` for non-decoder models in `llama_context`. These batching values are needed to support processing input sequences in batches for autoregressive models, but this model is single-shot, so needs to process the entire input in a single batch. This is _likely_ to be true of any such non-autoregressive model, but certainly up for discussion here.
- In `tools/server`, we need a fully new route for running `transcriptions` tasks using this kind of encoder-only model. We do this by checking whether the model needs logits, sampling, and memory, and if it is memory-free, requires logits, and doesn't require sampling, we use the new path that forwards through to `common_ctc_greedy_decode`, otherwise we use the old audio-LLM path.

## Open Questions

Given the number of new code-paths, there are a bunch of open questions here:

1. Does this kind of model even belong in `llama.cpp` instead of `whisper.cpp`? My main argument in favor of having the model here is one of distribution. `llama-server` (and https://llama.app) have become a user-facing distribution point and having these models supported here gives them reach both through the single server with `llama serve` and through downstream platforms that use `llama-server` directly (Ollama, LM Studio, AnythingLLM, etc).
2. Should we consider having this kind of model skip `libllama` _entirely_ and only live in `mtmd`? This would allow more code reuse between this architecture and `granite-speech`, but would require some more significant path changes in `common` and `server` to allow request handling to call pure-`mtmd` models.
