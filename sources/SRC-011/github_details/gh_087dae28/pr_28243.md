**Arm 1 — shared Q4_K_M sidecar, `-ngld 99 --spec-type draft-mtp --spec-draft-n-max 3`:** loads and drafts, but acceptance is only **0.32–0.38** (mean len ≈ 2.1), even with `temp 0 / top_k 1`. Decode 23–24 t/s @ temp 0.6, best greedy run 39.6 t/s — never beats baseline.

**Arm 2 — same but without `-ot per_layer_token_embd.weight=CPU`:** draft load crashes: `invalid vector subscript` immediately after `loading draft model`. So on this setup the shared-embed borrow path only works when the target's embed tensor is CPU-resident; GPU-resident embed breaks the load entirely. (Possibly related: arm 1's low acceptance could also be a symptom of the borrow path misbehaving with the UD-Q3_K_XL embed.)

**Arm 3 — standalone Q8_0 grafted head** (the drluoto file that gave **82–95% acceptance on #27836 @ `1d8de7c1`**, same target, same box): first OOM'd at 512K (draft KV cache wants 1 GiB on device 1; the 90 GB target leaves ~6–9 GiB free). Re-tested at `-c 65536`: loads, drafts, but acceptance is again **0.36–0.39 even greedy** — same collapse as the shared head. Greedy decode 40–42 t/s ≈ baseline, temp 0.6 drops to 25–28 t/s.

Same draft file, same target, same prompts: 0.82–0.95 acceptance on #27836 vs ~0.37 on this branch — so something between `1d8de7c1` and `2857e5114` (this PR's changes or the newer post-#27941 master base) appears to regress draft-mtp acceptance on this hardware/quant combo. Happy to rerun any fix quickly; the box rebuilds in ~6 min.

Side note: draft compute buffer (2253 MiB) initially OOMs on device 1 next to the 90 GB target, recovered by `retrying without pipeline parallelism` — harmless here, but worth knowing for tight-VRAM multi-GPU setups.

### ovidiu-morar · 2026-09-04

## Follow-up on my Metal report: the divergence is a MUL_MAT batch-invariance issue, not flash attention, and my "n-max 2 is the safe default" suggestion was premature

Two corrections to my earlier comment, then the mechanism, then a repro that needs no model.

### 1. Withdrawing my n-max 2 recommendation

I suggested n-max 2 as a safe default on Metal because its token stream was identical at temp 0. That was measured at `-n 200`. At `-n 400` on a longer prompt, n-max 2 diverges. Greedy identity is not a property of a batch width on its own: it is a threshold on accumulated rounding, so a single generation length is a weak instrument. Any claim of the form "width N is safe" needs the length it was measured at attached. Mine did not have one.

### 2. The cause is not flash attention

I was about to attribute this to the Metal flash-attention path, because `-fa off` makes the speculative stream byte-identical while `-fa on` does not. That correlation is real and reproducible, but it is not the mechanism. I tested the op directly.

Batch-invariance probe: same K, V and mask, all-zero mask so row 0 attends to the same keys in both cases, compare the output row for query 0 computed alone (`nb=1`) against the same row computed together with other rows (`nb` in 2, 3, 4, 6, 9), bitwise. A positive control runs first, comparing row 0 against row 1 in the same call, so a "no differences" result only counts once the probe is shown to see differences at all.

Result: `GGML_OP_FLASH_ATTN_EXT` is bitwise batch-invariant on Metal at every shape I tried, `hs` in {128, 256}, `kv` in {256, 300, 512, 768, 1536}, `nh` in {8, 12}, F16 K and V. That includes `kv=300`, which goes through the KV padding path, and `kv=1536`, which is above the 1024 bucket where the `fa_vec` tuning table is actually consulted and where `ne01=1` and `ne01=3` fall into different `ne01` buckets. Zero differing values in all of them.

So flash attention is not the source of the batch dependence here. My earlier framing would have sent this in the wrong direction.

### 3. The cause is `MUL_MAT`, with thresholds that match the source

The same probe applied to `GGML_OP_MUL_MAT`, comparing the result column for the same activation vector computed alone against computed alongside others:

| weight type | first width that breaks bitwise identity | gate in `ggml-metal-ops.cpp:2381-2410` |
|---|---|---|
| `q6_K` | `ne11 = 4` (identical at 2 and 3) | K-quants: `ne11 >= 4` |
| `q8_0` | `ne11 = 2` | first list: `ne11 >= 2` |
| `iq4_nl` | `ne11 = 2` | first list: `ne11 >= 2` |
| `f16` | `ne11 = 2` | first list: `ne11 >= 2` |

The thresholds were predicted from the source before running, and each one lands exactly where the small-batch mat-mv path admits that type. Inside the path, `nxpsg` switches at `ne11 >= 3` and `r1ptg` varies non-monotonically with `ne11` (2, 3, 4, 5, then 3 for 6, 4 for 7 and 8), so the reduction width changes with batch width.

At `ne11 = 9` the behaviour changes character rather than degree: the gate closes at `ne11 > 8`, execution falls back to `mul_mm`, and the difference goes from around 5e-6 on a few hundred values to around 1.5e-2 on all of them.

### 4. Why this shows up as an MTP divergence

Speculative verification evaluates `n_max + 1` tokens in one matmul instead of one. The target here, `Qwen3.8-Flash-Next-UD-IQ3_XXS`, is 250 `q6_K` tensors, 248 `q8_0`, 49 `iq4_nl`, 24 `bf16`, and 96 tensors in types that never take this path. The `q8_0` group starts perturbing at width 2, but at around 4e-6 that is not enough to move a token. The `q6_K` group joins at width 4, which is `n-max 3`, and that is exactly the width where the greedy stream first breaks on this box with `-fa off`, consistently across runs.

The op-level threshold is where the perturbation starts, not where it becomes visible. That gap is why the text-level answer depends on generation length and on which numeric path the rest of the graph takes, and it is why the `-fa on` versus `-fa off` difference looked like a cause when it is a difference in sensitivity.

### 5. Speed, corrected

I still do not have a setting that is both greedy-exact and faster on this box, and the margin is much smaller than I previously reported.

27 runs, 3 configurations x 3 arms x 3 rounds, `-n 400`, each arm as a ratio to the baseline of its own round and configuration. All 27 rows recorded a free GPU, mains power and flat wired memory, and the slow-round guard flagged nothing, so all three rounds count.

| fa | KV | arm | r1, r2, r3 | mean | greedy-exact |
|---|---|---|---|---:|---|
| off | f16 | n-max 2 | 0.906, 0.926, 0.926 | 0.919 | yes, 3/3 |
| off | f16 | n-max 3 + p-min 0.7 + backend sampling | 1.022, 1.026, 1.024 | **1.024** | no |
| on | f16 | n-max 2 | 0.933, 0.923, 0.932 | 0.929 | no |
| on | f16 | n-max 3 + gating | 0.965, 0.977, 0.984 | 0.975 | no |
| on | q8_0 | n-max 2 | 0.881, 0.895, 0.894 | 0.890 | no |
| on | q8_0 | n-max 3 + gating | 0.968, 0.995, 0.995 | 0.986 | no |

So one cell is faster, by 2.4 percent, tightly reproducible across rounds, and it is not greedy-exact. The only greedy-exact cell costs 8 percent.

I had previously put the best cell at about +15 percent. That figure was wrong in both size and location: it came from a matrix where the baseline itself had degraded between rounds, and it named `-fa on` f16, which measures 0.975x here. I withdraw it. An earlier attempt to correct it went too far the other way, concluding from a single clean round that nothing was faster at all, which this run also contradicts.

The measurement lesson, for anyone repeating this on a laptop: compare arms within a round, discard rounds where the baseline moves, and do not conclude from one surviving round. Watch the prefill number as a cross-check, since it is compute-bound and stays flat under memory-bandwidth contention while decode falls, which distinguishes contention from thermal throttling.

### 6. Why this may be worth acting on

#28108 fixed a comparable batch-invariance issue on CUDA and added an invariance test with it. Metal has no equivalent test, and `MUL_MAT` here is not batch-invariant by construction, since the kernel variant and its reduction width are selected from the batch width. That is fine for throughput, but it means any feature that changes batch width at runtime, speculative decoding being the obvious one, silently changes greedy output. The bug, if it is one, is not in the MTP head.

The probe is about 120 lines against the ggml backend API, no model and no draft head required, and it runs in a couple of seconds. Happy to clean it up and post it, or to open it as a separate issue against the Metal backend if that is a better fit than this PR thread. I can also run it on other shapes or types on request.

- RTX 5080: 15.3 GB

### Abort in `ggml_backend_sched_split_graph` when a `shared-` MTP head is combined with `--spec-draft-device` (surfaced alongside `--n-cpu-moe`)

> **Disclosure:** this report was generated end-to-end by Claude (Fable 5, Anthropic) operating this account's homelab; the human account owner directed the filing but the investigation, repro, and text are the model's. Details below were machine-verified against the running system before posting.

**Build:** this PR's head at `6fcaa16f4b360649933a54d1f91ad40ed35c0e11`, HIP backend, `-DAMDGPU_TARGETS=gfx1201`, Clang 23 (ROCm from kyuz0/vllm-therock base). One local patch is applied to `ggml_backend_cuda_buffer_set_tensor` (bounded pinned staging for H2D uploads on small-RAM hosts) — upload path only, no scheduler involvement.

**Hardware:** 2× AMD Radeon AI PRO R9700 (32 GB each), host RAM 16 GB (LXC).

**Models:** main = AtomicChat `Qwen3.8-Flash-Next-AD-4.27bpw-Q4_K_M-M64` (33 shards); draft = Unsloth `MTP/mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf` (the `shared-` variant that borrows `token_embd`/`output` from the main model).

**Repro:**

```
llama-server \
  -m /models/Qwen3.8-Flash-Next-AD-4.27bpw-Q4_K_M-M64/...-00001-of-00033.gguf \
  -md /models/MTP/mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf \
  --spec-type draft-mtp --spec-draft-n-max 2 \
  -ctkd q8_0 -ctvd q8_0 -ngld 999 \
  -devd ROCm0 \
  --n-cpu-moe 12 \
  -ngl 99 -c 262144 -ub 256 -fit off -ctk q8_0 -ctv q8_0
```

**Result** (during the draft model's context init, right after the main model loads):

```
/opt/llama.cpp/ggml/src/ggml-backend.cpp:941: pre-allocated tensor (output.weight) in a buffer (ROCm1) that cannot run the operation (NONE)
ggml_abort
ggml_backend_sched_split_graph
llama_context::graph_reserve
llama_context::resolve_fused_ops
llama_context::sched_reserve
llama_context::llama_context
llama_init_from_model
common_speculative_init_result::common_speculative_init_result
common_speculative_init_from_params
server_context_impl::load_model
```

**What it looks like:** the `shared-` head borrows `output.weight` from the main model, whose copy lives on ROCm1 under the default tensor split — but `-devd ROCm0` gives the draft context a scheduler whose device set doesn't include ROCm1, so the split-graph pass finds the borrowed pre-allocated tensor in a buffer none of the draft's backends can run and aborts.

**Observations that bracket the trigger:**

- Same command **without `--n-cpu-moe`**: no abort — the draft fails earlier with a plain cudaMalloc OOM (VRAM genuinely exhausted at these settings), so it never reaches `graph_reserve`. `--n-cpu-moe` seems to matter only by freeing enough VRAM for the draft to get that far; the abort itself smells like `-devd` + borrowed tensors.
- Same command **without `-devd ROCm0`** (keeping `--n-cpu-moe`): no abort; loads or OOMs cleanly depending on headroom, and with `--n-cpu-moe 3 -ts 28,20` it runs fine (serving now, draft acceptance ~0.75).
- `--spec-draft-n-cpu-moe 0` added to the aborting command: still aborts — the draft's own MoE-offload setting is not the trigger.

So the actionable combination appears to be **`shared-` head + `-devd <subset of the main model's devices that excludes the borrowed tensors' device>`**. A self-contained head presumably avoids it (borrowing is the only cross-model tensor reference), though I have not re-run that permutation on this box.

Happy to run further permutations on this hardware if useful.
