## Command line

llama-cli -m Qwen3.8-27B-UD-Q4_K_XL.gguf -ngl 99 -c 4096 -n 32 -no-cnv --no-warmup -p "1+1="
```

## Problem description & steps to reproduce

`-no-cnv` / `--no-conversation` is listed in `llama-cli --help` and documented in `tools/cli/README.md` as disabling conversation mode. On the new `llama-cli` it has no effect: conversation mode starts regardless, the prompt is consumed as the first user turn, and after generating the answer the process blocks at `>` waiting for input until it is killed.

Steps:

1. Run the command above.
2. Observe the banner, the `/exit /regen /clear` command list, and `> 1+1=` — i.e. conversation mode, despite `-no-cnv`.
3. The answer is generated and the perf line is printed.
4. The process never exits.

Controls — same machine, same model, only the marked change:

| change | result |
|---|---|
| as above | never exits (killed at 150 s) |
| `-st` instead of `-no-cnv` | exits cleanly, code 0, 14.6 s |
| `llama-completion`, same args including `-no-cnv` | exits cleanly, code 0, 14.2 s |
| stdin redirected from an empty file | exits on its own, code 130 |

The `-st` row isolates the flag: same binary, same model, same environment, only `-no-cnv` → `-st` changes, and the process exits in 14.6 s. The stdin-EOF row shows the process is genuinely blocked on console input rather than looping.

This is not tty-dependent — the result is identical with stdout redirected to a file and with a real console attached — and it is not new in `b10453`; `b10448` behaves the same way.

Either the flag should do what it says, or it should be removed from `llama-cli --help` and from `tools/cli/README.md`. As it stands it is accepted silently and does nothing, which sends scripted and non-interactive callers into what looks like an unexplained hang: no output, no error, no exit code. `-st` works, and `llama-completion` is the documented path for deterministic pipelines (#17618), but nothing at the point of use points there.

Possibly related: #18200 proposes disabling conversation mode when stdin or stdout is not a tty, which would also have avoided this in the scripted case.

On scope: I have only tested on Windows. Nothing in the observed behaviour looks platform-specific — the flag simply does not disable conversation mode — but I have not verified on Linux or macOS and would be happy to if that helps. My guess as to why this seems under-reported is that it only bites when `llama-cli` is driven non-interactively (scripts, CI, coding agents). Interactive users never pass `-no-cnv`, and a blocked non-interactive process emits nothing to diagnose, so it tends to be misattributed to whatever is driving it.

### Alex5418 · 2026-08-17

Reproduced on Linux as well, with a 0.6B model so the whole repro runs in ~2 s.

**Environment:** WSL2 Ubuntu 24.04, kernel 6.6.87.2, official `llama-b10453-bin-ubuntu-x64` CPU build — `version: 0.1.0-dev (build 10453, commit 3cb7ffb1a)`, `built with GNU 11.4.0 for Linux x86_64`.

**Repro** (`script` is only there to allocate a pty):

```
script -qec "llama-cli -hf ggml-org/Qwen3-0.6B-GGUF -ngl 0 -c 512 -n 8 --no-warmup -no-cnv -p '1+1='" /tmp/ts.txt
```

Conversation mode starts despite `-no-cnv` — banner, the `/exit /regen /clear` list, and `> 1+1=` as a user turn. The answer is generated, then the process blocks at `>` and is killed by `timeout` at 90 s (exit 124).

Changing **only** `-no-cnv` → `-st`, everything else identical:

```
script -qec "llama-cli -hf ggml-org/Qwen3-0.6B-GGUF -ngl 0 -c 512 -n 8 --no-warmup -st -p '1+1='" /tmp/ts.txt

exits cleanly in **2 s** with `Exiting...`, code 0.

So the flag is inert on Linux too — this is not Windows-specific.

**One platform difference worth flagging separately.** With stdout/stderr redirected (no tty), the Linux `llama-cli` writes **0 bytes to both and exits 0**, having done nothing at all — no model load, no generation, no error:

| command (stdout → file, stderr → file) | stdout | stderr | exit |
|---|---|---|---|
| `llama-cli -hf ggml-org/Qwen3-0.6B-GGUF -ngl 0 -c 512 -n 8 -st --no-warmup -p "hi"` | 0 B | 0 B | 0 |
| `llama-completion -hf ggml-org/Qwen3-0.6B-GGUF -ngl 0 -c 512 -n 8 -no-cnv --no-warmup -p "1+1="` | 14 B | 2087 B | 0 |

Either way the caller gets nothing useful, but the Linux behaviour seems worth a look on its own: a script that redirects or pipes `llama-cli` output today gets exit code 0 and an empty result, with no indication that no work was done.


### Souravrajvi0 · 2026-08-22

Reproduced on Linux (CPU-only, 2-core VM) with a small local GGUF model.

**Root cause:** the new `llama-cli` (`tools/cli/`) parses `-no-cnv` into `params.conversation_mode` but never reads it. The interactive loop in `cli-context.cpp` only checks `params.single_turn`, so scripted runs with `-p` generate once and then block at `>`.

**Fix:** when `-no-cnv` is set and a prompt is provided, treat it like single-turn mode and exit after generation; if `-no-cnv` is used without `-p`, return a clear error instead of entering interactive chat. Also hide the `/exit /regen /clear` banner in non-conversation mode.

Tested locally:
```bash
llama-cli -m <tiny.gguf> -ngl 0 -no-cnv -p 'hello'
# exits 0 with "Exiting..." (no hang)

llama-cli -m <tiny.gguf> -no-cnv
# exits 1: non-conversation mode requires a prompt (-p)
```
