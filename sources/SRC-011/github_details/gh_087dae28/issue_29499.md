## 正文

## Environment

- Board: NVIDIA Jetson Orin NX 16GB (sm87, unified memory, VMM: yes)
- L4T / JetPack 36.4.7, kernel 5.15.148-tegra, driver 540.4.0, CUDA 12.6
- llama.cpp tags `b9016` (846262d78) and `b11199` (86a24a182), both built via jetson-containers with `GGML_CUDA=ON -DGGML_CUDA_F16=ON -DGGML_CUDA_FA_ALL_QUANTS=ON` for sm87
- Run inside `docker run --runtime=nvidia --network=host` (and same behavior outside docker)

## Repro

```
llama-server -m <any GGUF> --host 0.0.0.0 --port 11434 -ngl 99 -c 2048 --parallel 1 --jinja
```

Last output line:

```
0.37.437.187 I srv  llama_server: listening on http://0.0.0.0:11434
```

After that, never anything: `/health` and `/v1/chat/completions` hang (curl timeout), no request is ever logged, no error, no crash. The process sits in state S with ~0% CPU; `gdb -p <pid> -ex "thread apply all bt"` shows every thread parked in futex/lock waits.

## What we verified (all hang identically)

- Model-independent: tested Qwen3.5-9B, Qwen3.6-27B, and several
- `-ngl` 0..99, `-c` 1024..8192, `--parallel 1` and default 4
- `--no-warmup` on and off
- CPU-only (`-ngl 0`) and CUDA
- `--shm-size=8g` and default (64 MB)
- `GGML_CUDA_ENABLE_UNIFIED_MEMORY` set and unset
- `dmesg` clean - no driver/nvmap errors on any run

## Differential

- Older llama.cpp **b8638** (same board, same `docker run --runtime=nvidia --network=host`, same model file): serves fine. Its log shows the old server entry point:
  - `main: server is listening on http://0.0.0.0:11434`
  - `main: starting the main loop...`
  - `srv  update_slots: all slots are idle`
- New-style server (`srv llama_server: listening`, operator-based rewrite): binds the port, prints listening, then never enters the request loop.

Regression window: b8638 -> b9016 (378 commits; heavy server/kv-cache/checkpoint churn in that window, e.g. #22114 "refactor use checkpoint logic", #19493 "server: speculative checkpointing", #22155 "ggml-cuda: flush legacy pool on OOM").

## Ask

The post-b8638 server implementation hangs during startup (before serving any request) on Jetson/aarch64 with this driver generation. Is a tegra/aarch64 startup hang known in the server rewrite era? Happy to provide full gdb backtraces from the wedged process or test specific commits on this board within the b8638..b9016 window.
