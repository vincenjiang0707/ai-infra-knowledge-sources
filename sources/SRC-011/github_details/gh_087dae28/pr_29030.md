# [PR #29030] qwen4exp/gemma4: gather lazy tensor rows with direct reads

source: https://github.com/ggml-org/llama.cpp/pull/29030
state: open | updated: 2026-09-27T08:48:24Z
labels: documentation, model, examples, server

## 正文

A reimplementation of #28136 replacing the mmap-backed `on` mode with direct reads.

Supersedes #28136.

The key mechanism here is `llm_graph_lazy_rows` (introduced in `llama-graph.cpp/h`), an input builder that builds readers (`llama-lazy-reader.cpp/h`) for lazy tensors per-context. The reader prototypes are stored in the model object, when a context gets constructed, they get cloned into the context, one per future gather thread. Whenever an ubatch is created and `set_inputs` is called, the lazy reader's `gather()` method is called and populates the input tensor.

This is pretty critical because the performance overhead especially on integrated platforms (esp. on Strix Halo) is huge:

| test | `-lzm on` | `-lzm on-direct` | |
|---|---|---|---|
| pp512 | 181.0 | 400.8 | +121% |
| pp2048 | 191.7 | 421.1 | +120% |
| pp8192 | 273.8 | 451.4 | +65% |

Instead, there are 2 cleaner designs but both requires thoroughly discussion with ggml maintainers:
- Add a new backend called CPU-lazy, that extends from ggml-cpu but only support one single op `GET_ROWS`
- Or, add a new flag `GGML_TENSOR_FLAG_LAZY` and let ggml decide on its own, whether to use mmap or `read()`

### pwilkin · 2026-09-21

@ggerganov When you read the lazy ngrams, the core issue is that it's a completely different read type from the typical expert read. Experts are large contiguous tensors, ngrams are random bits and pieces from different places of the cache. But by default, the lazy read mode uses mmap, which will try to fetch entire pages into the page cache on page faults. So basically we need a mode for lazily reading small random snippets such as ngrams that doesn't utilize the page cache, similar to how `direct-io` works for load-mode already.

### ngxson · 2026-09-21

@ggerganov agree, mmap is indeed not the optimal way for this use case since it's transparent how the reads are handled at OS level

lazy mode currently relies on mmap as it doesn't require too many changes in the code base. but we should eventually use plain `seek/read` for that

one important thing to note though, this should be done inside ggml to prevent any circumstances where 2 threads calling the `seek/read` on the same file descriptor, that's not thread-safe

@pwilkin regarding why I proposed 2 solutions:
- the first solution address the problem where CPU backend currently assume tensor data to already be available on RAM. we could, ofc, change that logic, but will make quite many branching in ggml-cpu code. that will be quite spaghetti
- second solution is more future-proof, basically other backends can impl lazy loading/reading tensor on-demand (for example, expert streaming). but important to note that this one flag is not enough, the backend interface will need to be extended, and then backends will also need to impl those. and more annoying of all, whatever to be designed, they need to be able to do overlapping in the future (i.e. case where we want to pre-fetch experts at layer N, while currently at N-1 layer)
