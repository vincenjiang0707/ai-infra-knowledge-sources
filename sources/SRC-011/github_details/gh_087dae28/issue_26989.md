### Feature Description

### Is your feature request related to a problem? Please describe.

Currently, `llama.cpp` supports several quantized formats for KV cache compression (such as `q8_0`, `q4_0`, `f16`, `f8_e5m2`, etc.). While integer 4-bit options like `q4_0` significantly reduce VRAM consumption during long-context inference, floating-point formats generally offer better dynamic range and lower accuracy degradation for attention key/value representations.

With the growing adoption of NVFP4 (NVIDIA FP4) in modern model weights and hardware, having native NVFP4 support for the KV cache would be a huge enhancement for memory-constrained, long-context scenarios.

---

### Describe the solution you'd like

1. Add support for `nvfp4` / `fp4` as valid options for `--cache-type-k` and `--cache-type-v` in `llama-cli`, `llama-server`, and the C++ API.
2. Implement GGML conversion/quantization kernels for NVFP4 KV cache storage and attention computation (leveraging hardware FP4 Tensor Cores where available, with software fallback for unsupported architectures).

---

### Describe alternatives you've considered

- **`q4_0` / `q8_0` KV Cache**: While `q8_0` retains near-lossless precision, it takes 8 bits per element. `q4_0` reduces memory to 4 bits but can suffer from accuracy degradation in complex reasoning or coding tasks compared to 4-bit floating-point formats (E2M1 scaling).
- **`fp8` (E4M3 / E5M2)**: Excellent quality, but still requires ~8 bits per element.

---

### Additional context

- **VRAM Savings**: FP4 KV cache cuts KV memory usage by up to 75% compared to FP16, allowing much larger context windows (e.g., 32k–128k+) on consumer GPUs (16GB–24GB VRAM).
- **Target Use Case**: Long-context local agentic workflows (e.g., coding, multi-turn tool calling) where KV cache dominates VRAM footprint.
- **Ecosystem Alignment**: NVFP4 is increasingly becoming a standard FP4 format supported across recent NVIDIA architectures and LLM ecosystems.

### Motivation

As local LLMs (like Qwen3.6-27B and DeepSeek models) rapidly expand their context windows to 32k–128k+, the VRAM consumption of the KV cache frequently exceeds the memory footprint of the model weights themselves. 

While integer 4-bit options (`q4_0`, `q4_1`) are supported in `llama.cpp`, integer quantization often struggles to preserve fine-grained attention weights in long-context reasoning and code generation tasks. FP4 formats (specifically NVFP4 / E2M1 scaling) offer a significantly better dynamic range for attention keys and values at 4-bit precision. 

Adding NVFP4 KV cache support would allow developers running local coding assistants and agentic workflows to handle massive contexts (64k–128k) on consumer GPUs (16GB/24GB VRAM) with minimal accuracy degradation and drastically reduced memory pressure.

### Possible Implementation

1. **GGML Type Definition**:
   - Introduce `GGML_TYPE_NVFP4` (or `GGML_TYPE_FP4`) in `ggml.h` with appropriate block size (e.g., 32 elements per block with FP16/E8M0 scales).

2. **Quantization & CUDA Kernels**:
   - Add FP4 quantization/dequantization routines in `ggml-quants.c` and CUDA backend (`ggml-cuda/`).
   - Implement FP4 unpack/dequantize inline within flash attention / K-V cache lookup kernels (or leverage native FP4 Tensor Core instructions on supported NVIDIA architectures).

3. **CLI & Argument Parsing**:
   - Register `nvfp4` / `fp4` in `common/arg.cpp` for `--cache-type-k` (`-ctk`) and `--cache-type-v` (`-ctv`).
