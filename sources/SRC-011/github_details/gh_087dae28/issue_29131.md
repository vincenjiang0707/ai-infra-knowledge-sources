### Problem description & steps to reproduce

## Description

The issue is in the RVV implementations in `ggml/src/ggml-cpu/arch/riscv/quants.c`. The line references below are based on commit `b23701f77d47dad9de834d59ebfcbe25c9e8b46f`.

| Function                         | Loop location                                                                                                                                        |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ggml_vec_dot_iq4_nl_q8_0_vl128` | [L5501-L5532](https://github.com/ggml-org/llama.cpp/blob/b23701f77d47dad9de834d59ebfcbe25c9e8b46f/ggml/src/ggml-cpu/arch/riscv/quants.c#L5501-L5532) |
| `ggml_vec_dot_iq4_nl_q8_0_vl256` | [L5556-L5589](https://github.com/ggml-org/llama.cpp/blob/b23701f77d47dad9de834d59ebfcbe25c9e8b46f/ggml/src/ggml-cpu/arch/riscv/quants.c#L5556-L5589) |
| `ggml_vec_dot_mxfp4_q8_0_vl128`  | [L6492-L6523](https://github.com/ggml-org/llama.cpp/blob/b23701f77d47dad9de834d59ebfcbe25c9e8b46f/ggml/src/ggml-cpu/arch/riscv/quants.c#L6492-L6523) |
| `ggml_vec_dot_mxfp4_q8_0_vl256`  | [L6547-L6580](https://github.com/ggml-org/llama.cpp/blob/b23701f77d47dad9de834d59ebfcbe25c9e8b46f/ggml/src/ggml-cpu/arch/riscv/quants.c#L6547-L6580) |

These four functions process two quantization blocks per loop iteration. However, there is no tail handling when the number of blocks is odd.

As a result, the final block is skipped and its contribution is not accumulated into the dot-product result, producing an incorrect numerical result.

The behavior is especially clear when `nb = 1`. In that case, the loop condition

```cpp
ib + 1 < nb
```

is false at the initial condition check, so the loop body is never executed and the initially zero-valued `sumf` is returned directly.

I reproduced the issue on a native RISC-V system using a SpacemiT X60 CPU with VLEN=256 and GCC/G++ 14.2.

Codex was used during the initial code analysis and to run the first build and validation workflow on the board over SSH. I subsequently reran the validation programs manually on the same system and confirmed the same results.

On this machine, the directly executed kernels are the `vl256` implementations. The corresponding `vl128` functions have the same two-block loop structure and missing odd-block tail handling, but they were not directly executed on the X60 system used for this reproduction.

The attached reproduction package contains two validation programs:

* a kernel-level differential test comparing the RVV implementation against the generic implementation;
* a `GGML_OP_MUL_MAT` test exercising the issue through the actual CPU execution path.

### Related prior work

#8549 fixed a similar odd-block handling issue in earlier `IQ4_NL` CPU implementations. The affected RVV `IQ4_NL` and `MXFP4` kernels were added later in #18859.

The RVV implementations reported here use a two-block loop guarded by `ib + 1 < nb`, so an odd final block is skipped unless it is handled separately. This appears to be an RVV counterpart of the previously identified odd-block handling issue, rather than a duplicate of the same implementation.

## Expected behavior

All input blocks should contribute to the dot-product computation, regardless of whether the number of blocks is odd or even.

For equivalent inputs, the RVV implementation should therefore agree with the generic implementation within the expected numerical tolerance, and the `GGML_OP_MUL_MAT` results should remain correct for odd-block inputs as well.

### Exit status

The reproduction records:

```text

arch_diff_exit=1
```

Both validation programs intentionally return `1` when they detect numerical mismatches.

The non-zero exit status alone is not sufficient to identify this issue; a successful reproduction should also show the `IQ4_NL` / `MXFP4` odd-block mismatch pattern described above.

`run-reproduction.sh` records the exit status of the validation programs but does not treat their non-zero status as a failure of the wrapper script. Therefore, the wrapper script may still exit with status `0` even when the validation programs return non-zero. The reproduction result should be determined from the recorded logs and the specific mismatch pattern described above.

Confirmed this in the current source. All four RVV dot-product kernels for IQ4_NL and MXFP4 (vl128/vl256 variants) in ggml/src/ggml-cpu/arch/riscv/quants.c use for (; ib + 1 < nb; ib += 2), which silently skips the final block whenever nb is odd, no crash, just a wrong result. I'd like to take this on. adding a scalar tail loop after each paired loop, reusing the same per-block math already used by the generic fallback, to handle the odd leftover block. Will open a PR shortly.
