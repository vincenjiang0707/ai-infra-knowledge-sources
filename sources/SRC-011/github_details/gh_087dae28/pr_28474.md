## 正文

## Overview

An opt-in `--no-fallback` flag for llama-quantize that will exit with an error when tensor shapes would otherwise force a
fallback quant - before any tensor data is read. More information can be found in the issue #26616 with related
discussion.

_This PR contains_:

- Opt-in flag on `llama-quantize`. When any tensor shape would force a type substitution, it errors out before any
  tensor data is read, through the same error path the `imatrix` check uses, so the tool exits non-zero
- Why a flag: dry run reports the substitutions but cannot gate on them. `--dry-run --no-fallback` is a preflight check
  that finishes in seconds
- The existing end-of-run fallback warning now carries a summary in both modes:
    - count
    - parameter share
    - byte share
    - nominal versus actual bpw
    - the recipe's own no-substitution bpw
    - the substitutions grouped by column count and type pair, largest first, capped at eight lines. Per-tensor warning
      lines are unchanged
- New field in the public params struct, default off, inserted after dry_run the same way dry_run was added. Pointer
  members after it shift so any code built with the old struct layout must rebuild; identical trade to
  the [dry-run PR](https://github.com/ggml-org/llama.cpp/pull/19526)
- Help text and README bullet

## Additional information

- Ref: #26616
- Ref: PR #3747 as the PR that introduced the fallback behavior
- Parity with [ggufaudit](https://github.com/JoshBolding/ggufaudit):
    * same units and denominators as ggufaudit: tensor count, % of params, % of bytes, bpw; projected bpw exact on
      lmstudio's Q4_K_M, within 0.01 bpw on bartowski's imatrix quant
    * the ggufaudit census count runs n+1 per affected model: output.weight. The recipe itself sends it to Q8_0
      when its width is not a multiple of 256 so it never reaches `tensor_type_fallback()` and is not a substitution;
      ggufaudit cannot tell a recipe choice from a fallback. Nemotron below: 141 in the banner, 142 in the ggufaudit
      census row for the same 417-tensor model
    * i-quant rungs: without the maker's imatrix the recipe requests different types (q2_K where the ggufaudit census
      file has IQ2_XXS), so counts and bpw agree but type names differ
    * non-256 labels (Q4_0 etc.): ggufaudit does not apply its test; the flag still catches the substitution
- Testing details:
    * macOS arm64, Debug, LLAMA_FATAL_WARNINGS=ON, GGML_OPENMP=OFF
    * full build of all targets clean; ctest -L main subset (ci/run.sh's Debug set) 50/50; test-quant-type-selection
      pass
    * both no-fallback modes on the 61 GiB BF16 return in <1s and write nothing to disk
    * full ci/run.sh run locally, 100% tests pass

**Your 141 is right and my 142 is wrong.** The difference is `output.weight`. `llama-quant.cpp:530` picks `Q8_0` for the output tensor whenever `nx % qk_k != 0`, on purpose, before `tensor_type_fallback()` is reached. Nothing is substituted, so there's nothing to record. `ggufaudit` saw `Q8_0` at a 256-indivisible width and inferred a forced `Q6_K -> Q8_0`. It can't see the requested type; your branch can. Fixing the over-count on my end.

That asymmetry is a decent argument for this PR on its own. An auditor reading a finished file has to guess what was asked for; only the quantizer knows.

Also confirmed: `--dry-run --no-fallback` exits 1 on all three affected models and 0 on all five clean ones; the summary prints in warn mode too; the `n_show = 8` cap works (forced 12 groups, got 8 rows plus `... and 4 more groups`).

### JoshBolding · 2026-09-17

Separate from the parity results: `--output-tensor-type` and `--token-embedding-type` bypass the shape check, so `--no-fallback` can't see them.

`llama_tensor_get_type` returns early at line 768 for `output_tensor_type` and line 765 for `token_embedding_type`. Both sit above the only `tensor_type_fallback()` call, at line 799.

The result is that the preflight passes a config that then hard-fails. Same model, same flags, only `--dry-run` differs:

```
$ llama-quantize --dry-run --no-fallback --output-tensor-type Q6_K <lightning-bf16> Q8_0
  exit 0, no warnings, no banner, "quant size = 33294.12 MiB (8.49 BPW)"

$ llama-quantize --no-fallback --output-tensor-type Q6_K <lightning-bf16> out.gguf Q8_0
  [   1/ 417] output.weight - [2688, 131072], converting to q6_K ..
  ggml_validate_row_data: invalid size 15435 for type q6_K (type size = 210)
  exit 1
```

`--token-embedding-type Q6_K` does the same, failing at tensor 3 of 417. Any model whose output or embedding width isn't divisible by 256 reproduces it. Nemotron-3.5-Lightning's is 2688.

Two things in fairness: that early return is pre-existing upstream behaviour, not something you added, and it fails loudly rather than writing a corrupt file. But the README line here is "Combine with `--dry-run` to validate a quantization before running it", so I think it lands in scope. Routing those two returns through `tensor_type_fallback()` looks like it would close it.

Happy to test a fix if you push one.
