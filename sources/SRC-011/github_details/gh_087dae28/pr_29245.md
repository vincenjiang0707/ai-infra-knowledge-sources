## Overview

<!-- Describe what this PR does and why. Be concise but complete -->
The current approach to handling experts in MoE models use one GEMM per expert. These activations are relatively narrow, and cannot use the compute hardware effectively (neither ALU0/1 nor the XMX tiles). Additionally, the small inputs result in particularly inefficient dequantization. 
This can be fixed by grouping many small experts into one kernel, and handling them in one operation.

This patch proposes grouped and optionally fused GEMM kernels tuned on XMX (`joint_matrix`).
Approach:
- Build a host-side schedule of active expert tiles and launch as one grouped kernel instead of one GEMM per expert
- Dequantizes IQ4_NL or IQ3_S weights into f16 tiles in local memory
- Packs routed f32 activations into the VNNI f16 layout consumed by XMX.

## Additional information
Model: `unsloth/Qwen3.8-Flash-Next-GGUF:UD-IQ4_XS`.
The boost happens during pp.

| Mode | Prompt tok/s | Decode tok/s |
|---|---:|---:|
| Grouped off | 274.101 | 18.567 |
| Grouped on | 368.298 | 18.743 |
| Change | +34.37% | +0.95% |

### cwriter · 2026-09-23

> Hm, I see that you have cases for IQ4_NL + IQ3_S weights. Is there some way to generalize the kernel to accept more quant types?

There is, I have implemented some more types (including Q8_0), although the effects are much more limited there.
The key issue of IQ4_NL (and IQ3_S, much more) is that the dequantization overloads the scatter/gather units, because no alignment of each weight can be assumed. This makes it particularly expensive to dispatch in single units (because the memory unit needs to deal with many small unaligned accesses, and then the compute is underfed). Building the schedule on the host avoids these limits.
In terms of code parameterization, I did not yet find a very good way of parameterizing the stages. 

I thought it more useful to add the biggest gains now without blowing up the commit. If you prefer, I can update the commit with more types, but we're talking about ~2% for the remaining types for the IQ model I'm tuning. The trade-off will be the size of the commit.
