# [Issue #24946] [SYCL/xe] -cb pins GPU at gt-c0 on Battlemage, prevents idle power savings

source: https://github.com/ggml-org/llama.cpp/issues/24946
state: closed | updated: 2026-09-26T01:11:32Z
labels: stale

## 正文

### What happened

When running `llama-server` with the SYCL backend on an Intel Arc Pro B70 (Battlemage / `xe` driver), the `-cb` (continuous batching) flag keeps the GPU pinned in the active `gt-c0` power state with the clock at boost (2800 MHz) **continuously between requests**. The card never transitions to `gt-c6` deep sleep.

Over 8 days of uptime with the model loaded and serving sporadic requests, total GT idle residency was **197 seconds out of ~691,200** — 0.03% of the time. The card sustained ~50W idle draw, kept the fan audibly spinning, and held VRAM at ~72°C continuously.

`/slots` correctly reported `is_processing: false` between requests. CPU was at 0%. No actual inference was happening — the GPU's power state was simply stuck.

Dropping `-cb` (everything else identical) fixes it: the GT transitions to `gt-c6` within ~2 seconds of request completion. Wake latency on the next request is ~600ms (un-noticeable for inference workloads). VRAM cools from 72°C → 42°C, fan goes silent, power drops to <15W idle.

### Reproduction

```bash
source /opt/intel/oneapi/setvars.sh

./build-sycl/bin/llama-server \
  -m Qwen3.6-35B-A3B-UD-Q4_K_M.gguf \
  -ngl 99 --host 0.0.0.0 --port 8080 \
  -c 524288 --parallel 2 -cb \
  --mlock --no-warmup \
  -ctk q4_0 -ctv q4_0
```

Make one chat completion request. Wait 30 seconds. Then check:

```bash
# Expected (without -cb): gt-c6 / 0 MHz / fan stops
# Observed (with -cb): gt-c0 / 2800 MHz / fan running
cat /sys/class/drm/card0/device/tile0/gt0/gtidle/idle_status
cat /sys/class/drm/card0/device/tile0/gt0/freq0/act_freq
sensors xe-pci-0300 | grep -E '^(pkg|vram|fan)'
```

`idle_residency_ms` under `/sys/.../gtidle/` confirms: barely advances with `-cb`, accumulates seconds-per-second without `-cb`.

### Root cause (best guess)

`-cb` keeps the SYCL command queue armed between requests so a new request can fuse into the in-flight batch with zero allocation overhead — that's its purpose. On the older `i915` driver, this was harmless because power-state transitions were gated on actual kernel execution, not queue residency. On the new `xe` driver, GT-c-state transitions are gated on the queue being drained, so an armed-but-idle queue holds the GT in `gt-c0` indefinitely.

The `-cb` behavior is correct in isolation. The `xe` driver behavior is also defensible in isolation. The interaction is what's broken — and it's not detectable from llama.cpp's perspective without sysfs inspection.

### Suggested resolution (any of these would help)

In increasing order of effort:

1. **Documentation note in the SYCL backend README:** add a line that `-cb` on the `xe` driver (Battlemage and later) currently prevents idle power savings. Recommend dropping `-cb` for low-throughput single-tenant deployments on those GPUs.
2. **Runtime warning:** if `/sys/bus/pci/drivers/xe` exists and `-cb` is enabled, log a one-line warning at startup. Users on `i915` would not see it.
3. **Idle-queue-drain:** after N seconds of no new requests, explicitly drain/destroy the SYCL queue and re-establish it on the next request. Wake cost is ~600ms in my testing — acceptable for the idle-power win on this driver path.

Option 1 alone would have saved me ~3 hours of diagnostics yesterday. The symptoms (nvtop showing 100% but `/slots` showing idle; high thermals but zero CPU) sent me down several wrong paths before I dropped to `/sys/class/drm` and found the GT-c-state evidence.

### Workaround

Drop `-cb`. `--parallel 2` (or higher) still allows concurrent request handling, just without cross-request decode-step fusion. The throughput cost is real only under sustained 10+ concurrent requests; for single-tenant or low-concurrency deployments on `xe`, dropping `-cb` is strictly better.

### Related — upstream `xe` driver

The deeper fix belongs in the `xe` kernel driver — it should drop the GT to a low-power state when no kernel is actively executing, regardless of queue residency. This matches `i915` behavior. I'll be filing a separate report against the `xe` driver tracker. This issue is filed here in the meantime because the documentation/warning fix is much faster and helps users immediately.
