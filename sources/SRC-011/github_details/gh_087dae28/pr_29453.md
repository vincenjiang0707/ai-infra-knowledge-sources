# [PR #29453] CUDA: fix CCCL version guard breaking on major version rollover

source: https://github.com/ggml-org/llama.cpp/pull/29453
state: open | updated: 2026-09-26T03:43:11Z
labels: ggml, CUDA

## 正文

## Summary

`ggml/src/ggml-cuda/argsort.cu` gates `STRIDED_ITERATOR_AVAILABLE` on a
CCCL version check that compares the major and minor components
independently:

```c
#if (CCCL_MAJOR_VERSION >= 3 && CCCL_MINOR_VERSION >= 1)
```

The minor component resets to 0 whenever a new major series is cut. On
CCCL 4.x the condition therefore evaluates as `4 >= 3 && 0 >= 1`, which
is false. The macro goes undefined and argsort silently falls back to
the `init_offsets` path. The build still succeeds and nothing warns, so
this lands as a quiet performance regression rather than a build break.

## Root cause

Comparing version components separately is only correct within the
current major series. It implicitly assumes the minor component keeps
increasing, which stops being true at every major-version boundary.

CCCL already publishes the version as a single packed integer in
`MMMmmmpp` form, which is what its own version header defines:

```c
#define CCCL_VERSION 3004003
#define CCCL_MAJOR_VERSION (CCCL_VERSION / 1000000)
#define CCCL_MINOR_VERSION (((CCCL_VERSION / 1000) % 1000))
#define CCCL_PATCH_VERSION (CCCL_VERSION % 1000)
```

so 3.4.3 is 3004003, and "at least 3.1" is a plain `>= 3001000`. That
leaves a single comparison with no component arithmetic to get wrong.

## The fix

```diff
-#    if (CCCL_MAJOR_VERSION >= 3 && CCCL_MINOR_VERSION >= 1)
+    // CCCL_VERSION is packed MMMmmmpp: 3.4.3 -> 3004003
+#    if (CCCL_VERSION >= 3001000)
```

## Testing

RTX 4070 (sm_89), CUDA 13.4.92, CCCL 3.4.3, Ubuntu 26.04.

- `cmake --build build --config Release` - exit 0
- `test-backend-ops test -o ARGSORT -b CUDA0` - 98/98 passed, CUDA0 OK

The new guard was checked against a hand-written "version >= 3.1"
reference across 2.9.9, 3.0.0, 3.1.0, 3.1.99, 3.2.0, 3.4.3, 3.9.9,
3.99.99, 4.0.0, 4.2.7 and 5.0.0, with no divergences. The previous
guard disagreed at 4.0.0 and 5.0.0.

Worth noting that a green `test-backend-ops` run does not by itself show
the guard is still taken, because the fallback path passes those tests
as well. Preprocessing the real translation unit confirms the
strided-iterator branch is the one being compiled in: `counting_iterator`
is present and `init_offsets` is not.

## Note

`ggml/src/ggml-cuda/top-k.cu` carries the same defect with a `>= 3.2`
threshold. It is left untouched here to keep this change reviewable on
its own; a follow-up PR for it would be welcome.
