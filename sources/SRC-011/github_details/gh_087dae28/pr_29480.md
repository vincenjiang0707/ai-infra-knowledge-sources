## Overview

`llama_kv_cache_iswa::seq_pos_max` answered from the SWA cache alone. After a partial `seq_rm` below the sliding window (e.g. keeping only the last few tokens of a long prompt), the SWA cache becomes empty while the base cache still holds cells, so `seq_pos_max` returned `-1` for a sequence that is not empty. Callers that derive positions from it (`llama_batch_get_one` via `llama_batch_allocr`) then restart at position 0 and silently overwrite live base-cache cells - the KV corruption reported in #29045.

The base cache is a superset of the SWA cache, so the fix reports the maximum across both caches:

```cpp
return std::max(kv_base->seq_pos_max(seq_id), kv_swa->seq_pos_max(seq_id));
```

This restores the documented contract that `-1` means "the sequence is empty". `seq_pos_min` already reports the minimum across both caches and is unchanged.

## Additional information

Fixes #29045. The fix direction matches what @juliusbangert proposed in the issue thread; the repro was confirmed on current master by @mitoyosh.

Validation: CPU-only build (`-DLLAMA_CURL=OFF`); `test-batch-alloc` (the `llama_batch_allocr` consumer of `seq_pos_max`) passes - 50 tests, 327 assertions, 0 failures. The repo has no dedicated iSWA unit-test harness, so no new regression test is included; the issue body has the minimal runtime repro. Happy to add a targeted test if a maintainer points at the preferred harness.
