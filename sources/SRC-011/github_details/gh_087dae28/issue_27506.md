### Problem description & steps to reproduce

### Summary
When built with the ROCm backend, model output quality drastically degrades starting from commit `b10040` (and remains broken on the latest master), resulting in a severe perplexity (PPL) explosion.

### Details
When using the ROCm build, context comprehension significantly degrades, and tool calling frequently fails. 
Using the exact same model and arguments with a Vulkan build runs without any issues (completing tool calls perfectly), indicating that this issue is specific to the ROCm implementation.

### Reproduction Command
```bash
llama-perplexity -m /models/llama-3.2-3b-q4_0.gguf -f /wikitext-2-raw/wiki.test.raw -c 32768 -ngl 999 --chunks 1

```

### sjvrensburg · 2026-08-22

Confirming this on a second gfx1151 machine, and I can add three data points that narrow it down: it is **not quant-specific, not model-specific, and `rocWMMA` is not an escape hatch**.

### Environment

- AMD Ryzen AI Max+ 395 w/ Radeon 8060S (gfx1151), 128 GB, GTT 112 GiB
- Fedora 44, kernel 7.1.8-200.fc44
- ROCm 7.1.1 (`rocm-core-7.1.1-4.fc44`), built with `GGML_HIP_NO_VMM=ON`
- Vulkan control: RADV, `mesa-vulkan-drivers-26.1.7-1.fc44`
- llama.cpp **b10469** (`666f8898a`)

### Results

Same machine, same model files, same corpus (`wikitext-2-raw/wiki.test.raw`), `-ngl 999`:

| Build | MiLMMT-46-1B **Q8_0** (20 chunks) | gemma-2b-it **Q4_K_M** (12 chunks) |
|---|---:|---:|
| `build-vulkan` | **18.3318** +/- 0.79941 | **37.2509** +/- 2.46808 |
| `build-rocm` | 3921.1830 +/- 318.86146 | 14468.7844 +/- 1363.40089 |
| `build-rocm-wmma` | -- | 14520.9417 +/- 1368.81232 |

That is 214x and 388x. Vulkan on the same machine is clean.

```
llama-perplexity -m <model.gguf> -f wikitext-2-raw/wiki.test.raw --chunks 20 -ngl 999
```

### What this adds to the original report

1. **Not quant-specific.** The original report tested Q4_0; this reproduces on **Q8_0** and **Q4_K_M** alike. Q8_0 blowing up is notable -- it argues against a K-quant dequant path being the sole cause.
2. **Not model-specific.** MiLMMT-46 and gemma-2b are unrelated architectures, consistent with the original report's spread across Llama-3.2-3B / Qwen 3.6-35B / Laguna S 2.1.
3. **`GGML_HIP_ROCWMMA_FATTN` builds are equally affected.** `build-rocm-wmma` gives 14520.94 against `build-rocm`'s 14468.78 -- statistically indistinguishable, so rocWMMA flash attention neither causes nor avoids it.
4. `NO_VMM = 1` is present in `system_info` on the affected runs, so `GGML_HIP_NO_VMM=ON` does not avoid it either.

Degradation is immediate -- chunk `[1]` is already 3705.7453 on the Q8_0 run against 10.5117 on Vulkan -- so this is not an accumulating drift, and it should be cheap to bisect against b10038/b10040 with a small model and a handful of chunks.

Happy to run further tests on this hardware if it would help narrow the commit.

### nabe2030 · 2026-08-25

Wanted to close the loop here — thanks for pinning this to b10040 and later, and especially to
@Rcat999 for independently identifying the exact same commit (c7d8722922a2, #24233) from your
own bisection days before we got there from a different symptom (multi-slot output corruption,
not PPL). Our automated `git bisect` between b10039 and b10588 converged on the identical commit
and `#ifdef` block you found manually — good independent confirmation from two different angles.

Since then we've gone further: the corruption we were chasing (and, we now think, yours too)
traces to a race in `llama_context::process_ubatch()` — an H2D input-write racing a still-running
graph compute, ungated on single-GPU setups. c7d8722's `integrated=true` restoration on HIP
enables a host-buffer code path that appears to widen that race window enough to hit routinely
on APU/UMA hardware. We tested the actual sync fix (not just the `integrated=false` workaround
you and we both independently landed on) and it resolves the corruption too. Full writeup and
test matrix: https://github.com/ggml-org/llama.cpp/issues/27579#issuecomment-5409248004 and
https://github.com/ggml-org/llama.cpp/issues/27579#issuecomment-5411206667.

If your PPL runs batch multiple sequences/chunks per pass on HIP, that would line up with what
we're seeing — the `integrated=false` revert you verified is the same workaround we converged on
independently, and should keep working as a stopgap; the durable fix is the sync correction
described above.

### nabe2030 · 2026-08-26

@thedelph — thank you, the Vulkan-controlled numbers are what this thread needed. And
the point about the greedy canary running clean for forty minutes while the backend was
numerically broken throughout deserves more attention than it will get: we hit the same
trap from the other side, and reported HIP throughput figures (`-np 16`, 42 t/s) for a
day before output verification showed the generations were degenerate. tok/s and HTTP 200
are not evidence of correctness on this backend.

On your "wrong from the first token, not triggered by prompt size, by concurrency, or by
generation length" — that now has an explanation, and you're right that it isn't depth.
@Superfish1000 established the rule in #27311 (Aug 25) on the same hardware class:
**corruption tracks `n_ubatch < n_batch`, 8/8.** Holding `-b 4096` and varying `-ub`:

| `-c` | `-b` | `-ub` | PPL |
|---:|---:|---:|---:|
| 4096 | 4096 | 4096 | 56.55 |
| 4096 | 4096 | 2048 | 757.85 |
| 4096 | 4096 | 1024 | NaN |
| 4096 | 4096 | 512 | 6.97e9 |

and with `ub == b` it is clean at 512, 1024 and 2048 alike. The only passing configuration
is the one where the whole prompt lands in a single ubatch. So it is wrong from chunk 1
because a single chunk larger than `n_ubatch` is already two graph executions — nothing
has to accumulate across chunks.

That also puts @Rcat999's `-c 512` clean / `-c 2048` broken boundary earlier in this
thread exactly on the rule, with `--chunks 1` and the default `-ub 512`. And
@sjvrensburg's runs, which used default flags, would have had `ub < b` throughout.

Superfish1000 also confirmed the mechanism directly rather than by bisect: making
`integrated` runtime-switchable on an otherwise unmodified tree gives PPL 850,121 with it
on and 72.80 with it off, from the same binary. That closes the loop on the `#ifdef` block
@Rcat999 identified manually and we hit independently by bisect.

@Rcat999 — on closing this. The durable fix is **#27311**, which measures PPL 63.59
against a Vulkan reference of 64.10 where the base gives 872,006, at no measurable
throughput cost. **#25863** fixes both symptoms equally well (63.67) and is far smaller,
if a targeted mitigation is preferred over the general scheduler change. Neither is merged
— #27311 needs two approving reviews and has four pending. Your `integrated = false`
revert stays correct as a stopgap in the meantime, but I'd suggest leaving this issue open
until one of them lands: the revert removes a path that #27311 is trying to make correct
rather than delete, so "fixed by reverting" and "fixed" are different outcomes here.

One thing your report adds that the #27311 thread does not have, @thedelph: your Vulkan
switch cost 5–9% on prefill and **gained 24% on decode** (49.5 → 61.5 t/s). Worth stating
plainly for anyone still weighing whether to wait — on this chip there is currently no
throughput argument for staying on the ROCm build.

We're testing #27311 on our Strix Halo now against the multi-slot and tool-array failure
modes we reported, and will post results to that PR.
