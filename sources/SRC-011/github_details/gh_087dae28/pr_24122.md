# [PR #24122] rpc: reduce small-message overhead and tune cache probing

## 正文

## Summary

- coalesce small RPC command/header writes to reduce TCP message overhead
- make the RPC tensor cache probe/save threshold configurable via `GGML_RPC_CACHE_MIN_SIZE`
- avoid client hash probes when the server reports that it has no cache
- add local and remote RPC benchmark helpers, including per-case env overrides for one-sided experiments
- document TCP buffer tuning and separate client-side cache probing from per-node server-side cache saving

## Validation

- `python -m py_compile tools/rpc/bench_rpc_remote.py`
- `tools/rpc/bench_rpc_remote.py --dry-run ... --env GGML_RPC_TCP_BUFFER_SIZE=4194304 --patch-env GGML_RPC_CACHE_MIN_SIZE=1048576` confirmed the patch-only env is recorded only for the patch case
- CPU/RPC build: `cmake -S . -B build-rpc-cpu-check -DGGML_RPC=ON -DGGML_CUDA=OFF -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF -DCMAKE_BUILD_TYPE=Release && cmake --build build-rpc-cpu-check --target rpc-server llama-bench`
- Representative heterogeneous RPC run, `p16/n16/r1`, all caches warm: prompt throughput improved from `2.908077` to `3.430841` tok/s (`+17.98%`), decode improved from `0.411090` to `0.416935` tok/s (`+1.42%`), wall time was unchanged (`436.15s` to `436.17s`)
- Earlier warm run: wall time improved `-9.32%`, decode throughput improved `+30.40%`, prompt throughput changed `-5.69%`

## Notes

Lowering the server-side cache threshold on every node is not always safe or useful on mixed hardware. The docs now describe client-side probing separately from server-side saving, and the remote benchmark helper can record patch-only client env such as `GGML_RPC_CACHE_MIN_SIZE=1048576`.

### marknx · 2026-08-24

Independent validation on a heterogeneous two-box setup — this PR delivers a solid decode speedup for MoE expert-offload over RPC.

**Setup:** DeepSeek-V4-Flash-0731 (284B MoE, expert-pruned to 216 experts, UD-IQ4_XS, 108.5 GiB). Master: llama-server on Windows, RTX 5090 (attention + KV). Worker: ggml-rpc-server on DGX Spark GB10 (sm_121), holding **all** routed-expert FFN tensors via `-ot "blk\.[0-9]+\.ffn_(gate|down|up)_exps\.weight=RPC0[...]"`. Link: 10 GbE, ~0.3 ms RTT. This layout does 43 layers × 2 round-trips per token, so it is very sensitive to per-message overhead.

**Method:** rebased the RPC core of this PR (ggml-rpc.cpp, transport.*, headers) onto b10590. To keep wire compatibility with a stock peer during partial rollout, the new RPC commands were appended **after** `RPC_CMD_MEMSET_TENSOR` (which b10590 added at that slot) and the b10590 protocol version was kept. `llama-bench -p 0 -n 128 -r 3`, identical flags across runs, env vars at defaults:

| Config | tg128 |
|---|---|
| stock b10590 both sides | 17.68 ± 0.97 t/s |
| PR worker + stock master | 19.30 ± 0.31 t/s (+9.2%) |
| PR both sides | **20.45 ± 1.34 t/s (+15.7%)** |

Notes:
- Worker-only deployment already captures more than half of the gain (and reduced run-to-run variance to a third) — nice property for mixed-version fleets.
- Stable across model loads, long-context runs (192k prompt) and multi-hour operation; outputs verified unchanged at temperature 0.
- Happy to run further A/Bs on this setup (Windows master + aarch64/sm_121 worker) if useful, e.g. the `GGML_RPC_*` tuning knobs.


### danilofalcao · 2026-09-26

Measured on a two-node 1GbE RPC cluster serving Qwen3.8-27B (recurrent hybrid, ~60% of layers on the worker): total per-turn RPC traffic dropped from ~287 MB to ~150 MB after (a) run-length encoding the attention mask before sending it, (b) keeping saved KV regions on the rpc-server and passing them by reference, and (c) reducing the number of prompt checkpoints. At long context the attention mask is one long run of 1s, so RLE shrinks it from O(n) to O(runs) bytes. Happy to provide a per-item breakdown if it helps the discussion.
