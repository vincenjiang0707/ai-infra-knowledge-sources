# [Issue #27796] ggml-hip: quantized KV cache decodes slower than f16 on RDNA4 (gfx1201), worse the more unpacking the type needs

source: https://github.com/ggml-org/llama.cpp/issues/27796
state: closed | updated: 2026-09-22T19:35:03Z
labels: 

## 正文

### Summary

On RDNA4 (gfx1201, Radeon AI PRO R9700), every quantized KV cache type decodes **slower** than `f16`, and the deficit grows with the amount of unpacking the type requires. This is the opposite of the expected memory-bandwidth tradeoff.

### Measurements

`llama-bench`, single GPU, ROCm backend, `-ngl 99 -p 0 -n 64 -r 1`.
Model: `Qwen3.6-27B-UD-Q5_K_XL.gguf` (26.9B, 18.65 GiB, head dim 256).

| KV type | tg64 @ d16384 | vs f16 |
|---|---|---|
| `f16`  | 23.44 t/s | — |
| `q8_0` | 22.43 t/s | −4% |
| `q4_0` | **18.56 t/s** | **−21%** |

The ordering tracks per-element unpacking work: `q4_0`, which needs the most bit manipulation, is by far the worst, despite touching the *fewest* KV bytes.

I also see the deficit widen with context depth on another model here (`q8_0`: −7% at d0, −11% at d32768, −21% at d131072). I'm deliberately not putting those numbers in the table above because that model uses a downstream quant type you can't load — but the trend is worth flagging, because a *fixed* per-token dequant overhead should shrink as a fraction once KV dominates traffic. It grows, which suggests the cost scales with KV bytes touched.

### Flash attention is not the cause

`-fa auto` and `-fa on` give identical results (`f16` 41.63 vs 41.61; `q8_0` 38.06 vs 37.50 at d32768), so this is not the "quantized KV falls off the fused FA path" failure mode.

### Suspected cause

`ggml/src/ggml-cuda/fattn-vec.cuh` uses a flat tuning for all quantized KV types under `RDNA`:

```c
constexpr int nthreads_KQ_q = 2;
```

At head dim 256 with a large KV cache, this looks like it leaves the quantized path badly under-parallelized — the dequant work per thread grows with KV size while the thread count stays fixed at 2. That would explain both the ordering (more unpacking = worse) and the depth scaling.

I haven't confirmed this by profiling yet; it's a hypothesis from reading the code and the measurement shape.

### Environment

- AMD Radeon AI PRO R9700 (gfx1201, RDNA4), 32 GiB, wave32
- ROCm 7.x, HIP backend
- Head dim 256, 4 KV heads, hybrid attention (16 of 64 layers full-attention)

### Offer

I have a dual-R9700 gfx1201 box and am happy to run sweeps or test patches — including a `nthreads_KQ_q` sweep across the quantized types if that's the right direction. RDNA4 data points seem scarce, so tell me what would be useful.

If that interpretation is correct, the main issue seems to be that the RDNA4 quantized decode path scales much worse with context than the F16 path for this D=256 geometry.

### The-Monk · 2026-09-13

Confirming the kernel-selection mechanism and adding a second gfx1201 data point.

**The dispatch asymmetry is real** and matches the earlier analysis. In `ggml_cuda_get_best_fattn_kernel`, for D=256 batch-1 decode with GQA (Qwen3.8-27B is 24 Q / 4 KV heads, so gqa_ratio 6 → gqa_ratio_eff 2):

- the AMD-WMMA → `MMA_F16` branch requires `Q->ne[1] * gqa_ratio_eff > 16`, i.e. `1*2 = 2`, which is never satisfied at batch-1 — so it is skipped for **both** f16 and quantized KV;
- in the fallback `can_use_vector_kernel` block, **quantized KV takes VEC** (`if (Q->ne[1] <= 2) return BEST_FATTN_KERNEL_VEC;`), while **f16 KV honors `gqa_opt_applies` and falls through to TILE** (it returns VEC only `if (!gqa_opt_applies)`).

So at D=256 batch-1 decode, f16 and quantized KV run **different** kernels (f16 → TILE, quantized → VEC), and it's the D=256 quantized VEC path that scales poorly with context depth.

**Second data point (gfx1201 / R9700, ROCm), same geometry (Qwen3.8-27B, D=256), tg128 t/s vs depth:**

| depth | q4_1 | q8_0 | f16 |
|---:|---:|---:|---:|
| 0 | 29.0 | 28.9 | 29.2 |
| 16384 | 26.2 | 27.2 | 28.2 |
| 32768 | 23.0 | 26.2 | 26.8 |

The q4_1 slope is gentler here than the original repro (−21% at 32K vs ~−33% reported), and **q8_0 tracks f16 within ~2–3% at 32K** — i.e. a D=256 quantized decode kernel *can* scale about as well as f16, which suggests this is a tunable property of the D=256 quantized VEC kernel rather than something fundamental. These numbers are from a downstream fork that carries RDNA4-specific FA tuning, so treat the absolute values as indicative rather than stock; the dispatch analysis above is the stock path.

One caution on the obvious fix: rerouting D=256 batch-1 quantized KV to the TILE kernel (which dequantizes K/V to f16 in SRAM) was **not** a clean win in my testing — roughly neutral for q4_1 and slightly negative for q8_0 — so the lever looks like the VEC kernel's depth-scaling at D=256, not the routing.

Happy to run the full depth curve on any candidate patch.
