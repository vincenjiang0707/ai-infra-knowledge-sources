### Which llama.cpp modules do you know to be affected?

libllama (core library), llama-cli, llama-server

### Command line

```shell
llama-server -hf ggml-org/Voxtral-Mini-3B-2507-GGUF --port 18080 -c 4096
# Then send a request to /v1/chat/completions with a single-sample WAV file provided as input_audio.
```

### Problem description & steps to reproduce

When a WAV file containing is exactly one sample, the process aborts at mtmd.cpp:1553 GGML_ASSERT(buf.size() > sizeof(float)). Because one float occupies 4 bytes, the buffer size is also 4 bytes, the condition evaluates to false (4 > 4 is false). 
I verified the crash on Voxtral; the assertion sits on the shared path before the per-model preprocessor is selected, so it should affect all audio models.
The Whisper preprocessor is designed to zero-pad very short audio clips. Therefore, regardless of whether such extremely short input should ultimately be accepted or result in an error, a single request should not trigger an assertion that kills the entire server process. The erroneous assertion causes the entire server process to abort instead of returning an error for the request.

Steps to reproduce:
1. Build any recent master with audio-capable mtmd.
2. Create a 1-sample 16 kHz mono WAV (see attached script).
3. Feed it to llama-mtmd-cli, or POST it to llama-server as input_audio.
4. CLI aborts with exit code 134; the server process dies and /health stops responding.

AI usage disclosure: I used an AI assistant to help troubleshoot this bug and draft this report. I personally reproduced and verified the crash and also understand the relevant code.

### First Bad Commit

Not bisected. The assertion is long-standing and was not touched by the recent
short-input fix (#26536), which changed min_samples inside the preprocessor but
not this buffer-size guard at the tokenizer entry.

You're right that my dynamic evidence so far is limited to the Whisper-based path, specifically Voxtral. I tried to find models using other audio preprocessors for testing, but the small audio-capable models I could readily use from ggml-org, including Voxtral, Qwen2.5-Omni, and Ultravox, all appear to use the Whisper preprocessor. So I haven't yet been able to dynamically cover the qwen3a, gemma4a, or conformer paths.

My current understanding is that these two checks have different responsibilities. The guard at mtmd.cpp:1553 checks whether the input buffer is structurally large enough to contain at least one float. Whether a particular model can semantically handle such a short audio input seems to belong to the model-specific preprocess() implementation. The individual preprocessors already have their own validation logic, for example checks such as n_samples == 0 returning false. Whisper does more than simply reject invalid inputs; it features an explicit zero-padding path (`min_samples = n_fft/2 + 1`), indicating that accepting extremely short audio clips was part of the original design. If preprocess() returns false, the caller reaches the LOG_ERR(...) / return 2 path instead of aborting the process. So changing > to >= would at least remove this unconditional abort at the tokenizer entry and allow the model-specific preprocessor to decide whether the input can be handled. For Voxtral/Whisper, I've verified that the 1-sample input is then padded and processed successfully. For the other preprocessors, I agree that this still needs dynamic verification.
```
mtmd.cpp:1553  GGML_ASSERT(buf.size() > sizeof(float));     // structural check on the buffer
mtmd.cpp:1559  bool ok = ctx->audio_preproc->preprocess(...); // per-model semantic check
mtmd.cpp:1560  if (!ok) { LOG_ERR("Unable to preprocess audio\n"); return 2; }  // graceful
```

If you can run a model using a different preprocessor on Windows, that would be especially helpful. For example, something using the qwen3a, gemma4a, or conformer path would cover exactly the gap in my current testing. That would give us much better evidence for whether >= is appropriate as the shared-path fix.
