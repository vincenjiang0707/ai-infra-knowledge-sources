### Problem description & steps to reproduce

ggml_backend_cpu_x86_score() in ggml/src/ggml-cpu/arch/x86/cpu-feats.cpp checks CPUID feature bits but not the OS-enabled XSAVE state (XCR0). Under GGML_BACKEND_DL, the loader can select an AVX/AVX512 variant on a system where the OS/hypervisor has not enabled that state, causing a SIGILL. The existing FIXME in the score function documents this gap.

## Reproduction

Environment:
- Host: QEMU/KVM x86_64, launched with -cpu host
- Guest: Debian stable, kernel booted with clearcpuid=xsave
- llama.cpp build flags:
    -DGGML_BACKEND_DL=ON -DBUILD_SHARED_LIBS=ON \
    -DGGML_CPU_ALL_VARIANTS=ON -DCMAKE_BUILD_TYPE=Debug

### teja2789 · 2026-09-26

Hi, I dug into this and confirmed it directly in the current source. ggml_backend_cpu_x86_score() in ggml/src/ggml-cpu/arch/x86/cpu-feats.cpp has a // FIXME: this does not check for OS support comment right above the exact code path this issue describes. is.AVX() only checks the CPUID feature bit, it never checks is.OSXSAVE() (which is already detected but unused) or verifies via XGETBV that the OS has actually enabled AVX/AVX512 state saving in XCR0. I'd like to take this on, I'll add an XGETBV-based OS-support check gated behind the existing OSXSAVE() detection, following the standard pattern most compilers and libc implementations use for exactly this check. Opening a PR shortly with the fix and a clear writeup of the reasoning.
