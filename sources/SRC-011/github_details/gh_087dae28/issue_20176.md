### DByte308 · 2026-07-26

Reproducing this on 2× MI50 (gfx906) with a Qwen3.5-35B-A3B derivative, plus some data on what the workaround costs and several hypotheses I was able to rule out.

### Setup

- 2× AMD Radeon Instinct MI50 32GB (gfx906), PCIe, `--split-mode layer`
- ROCm 7.2.4 (community gfx906 build, `mixa3607/rocm-gfx906:7.2.4-complete`)
- llama.cpp b10088 (via the gfx906 fork `mxxm-t/mx-llama.cpp` @4daf555)
- Model: Ornith-1.0-35B-AEON — `qwen35moe` (Qwen3.5-35B-A3B lineage, 30 GatedDeltaNet + 10 full-attention layers), Q8_0, with the MTP head in-GGUF
- `--spec-type draft-mtp --spec-draft-n-max 2 -c 262144 -b 2048 -ub 2048 --parallel 1 --cache-ram 0`

### Symptom

```
Memory access fault by GPU node-1 (Agent handle: 0x...) on address 0x... Reason: Page not present or supervisor privilege.
```

Occurs a few requests into normal multi-turn chat serving. Setting `--ctx-checkpoints 0` avoids it completely — we have run that configuration for weeks without a single fault.

### The workaround has a large cost

On this build, context checkpoints appear to be the **only** prompt-reuse mechanism that works for hybrid recurrent models. Measured with a strict-extension follow-up (8442 → 8954 token prompt, i.e. the same prompt plus 512 new tokens), no slot erase, `cache_prompt: true`:

| flags | `prompt_n` reprocessed | prefill |
|---|---|---|
| `--cache-ram 0 --ctx-checkpoints 0` | 8954 (all) | 7.44 s |
| `--ctx-checkpoints 0` | 8954 (all) | 7.44 s |
| `--cache-ram 0` | **516** | **0.75 s** |
| (neither) | **516** | **0.75 s** |

So `--ctx-checkpoints 0` is the difference between reusing the prompt and reprocessing it in full — roughly 10× on follow-up turns. `--cache-ram` makes no difference either way. At 30k context this is ~37 s of avoidable prefill per turn.

### Ruled out

- **PR #21170's `ggml_cuda_set_device()` patch** — applied on top of b10088 (the `#ifndef GGML_USE_HIP` guard in `ggml_cuda_set_device` plus the call in `ggml_backend_cuda_set_tensor_async`). Fault still occurs.
- **Remaining uncovered async copy sites.** In b10088 `ggml-cuda.cu`, the buffer-interface copies (`ggml_backend_cuda_buffer_set_tensor` and friends) already call `ggml_cuda_set_device()`, but four backend-async sites do not: `ggml_backend_cuda_get_tensor_async`, `ggml_backend_cuda_set_tensor_2d_async` (both the chunked and the `cudaMemcpy2DAsync` path), and `ggml_backend_cuda_get_tensor_2d_async`. I added `ggml_cuda_set_device(cuda_ctx->device)` to all four and rebuilt — **fault still occurs**. So the missing-device-context theory from #21140 does not appear to explain this one, at least not at those sites.
- **`--cache-ram 0`** — no effect on the fault either way.

### Reproduction is shape-sensitive

Worth flagging for anyone trying to reproduce: I could **not** trigger it with synthetic traffic.

- 16 sequential `/completion` requests with raw token arrays, including deliberately divergent prompts sharing a long prefix — 0 faults.
- 6 sequential `/v1/chat/completions` turns with growing history, up to 2797 prompt tokens — 0 faults, on both the patched and unpatched builds.

It reproduces reliably on **real** chat traffic (large system prompt + tool schemas, conversations growing into the 10k+ token range) within a handful of requests. This matches the note in #21140 about the crash appearing on the 4th–5th sequential agent request via the prompt-cache restore + LCP-similarity path.

Happy to run diagnostics or test a patch on this hardware — it reproduces readily here and I have a stable `--ctx-checkpoints 0` baseline to compare against.

### lbbit · 2026-09-22

### Additional data: deterministic reproductions, and evidence that the `-1` device hint is post-mortem (not the root cause)

We hit this on a 2× RX 7900 XTX (gfx1100) ROCm box and collected ~14 crashes over several days. Two findings may be useful here, plus a negative result on the #21170 patch.

---

## Environment

| | |
|---|---|
| GPUs | 2× Radeon RX 7900 XTX (gfx1100, RDNA3), 24 GB each, PCIe 4.0 x16 |
| CPU / RAM | 2× Xeon E5-2680 v4, 64 GB |
| ROCm | 7.2.4 |
| Kernel | 6.8.0-138 |
| Build | `-DGGML_HIP=ON -DAMDGPU_TARGETS=gfx1100 -DCMAKE_BUILD_TYPE=Release`, commit `b96806d` |
| Model | Qwen3.6-35B-A3B (arch `qwen35moe`, hybrid/recurrent: `full_attention_interval=4`, has `ssm.*` keys) |
| Server flags | `-ngl 99 -fa on -c 262144 --cache-type-k f16 --cache-type-v f16 -b 4096 -ub 1024 --parallel 1` |

Note the architecture: `qwen35moe` is a **hybrid recurrent** model (30 of 40 layers linear attention). Per the discussion in #21140, that's the class that goes through `llama_memory_hybrid` / `llama_memory_recurrent`.

---

## Finding 1: the `current device: -1` is a *post-mortem* artifact, not the cause

`ggml_cuda_error()` initializes its device variable to `-1` and only fails to overwrite it if `cudaGetDevice()` itself fails:

```cpp
void ggml_cuda_error(const char * stmt, const char * func, const char * file, int line, const char * msg) {
    int id = -1; // in case cudaGetDevice fails
    (void)cudaGetDevice(&id);
    GGML_LOG_ERROR("  current device: %d, in function %s at %s:%d\n", id, func, file, line);
```

So `-1` means *"`cudaGetDevice()` failed while we were already reporting an error"*, i.e. the context was already broken. It is a symptom of the failure being reported, not evidence of which device the failing call targeted.

This matters because #21140 / #21170 interpreted `-1` as *"the device context was never set"* and fixed it by forcing `hipSetDevice()`. We think that reading is wrong — see Finding 3.

---

## Finding 2: the failing transfers are **exactly 10 contiguous 4 KiB pages**, every time

This is the part we haven't seen reported and it may point at the real mechanism.

On each crash the kernel logs **exactly 10** `[gfxhub] page fault` entries, and the addresses are 10 consecutive 4 KiB pages:

```
amdgpu 0000:07:00.0: amdgpu: [gfxhub] page fault (src_id:0 ring:24 vmid:9 pasid:32778, ...)
amdgpu 0000:07:00.0: amdgpu:   in page starting at address 0x0000752066200000 from client 10
                                                        ... 0x0000752066201000 ...
                                                        ... 0x0000752066202000 ...
                                                        ... 0x0000752066203000 ...
                                                        ... 0x0000752066204000 ...
                                                        ... 0x0000752066205000 ...
                                                        ... 0x0000752066206000 ...
                                                        ... 0x0000752066207000 ...
                                                        ... 0x0000752066208000 ...
                                                        ... 0x0000752066209000 ...
amdgpu 0000:07:00.0: amdgpu: GCVM_L2_PROTECTION_FAULT_STATUS:0x00901A31
amdgpu 0000:07:00.0: amdgpu:          Faulty UTCL2 client ID: SDMA0 (0xd)
```

Count per crash, across 5 crashes in one boot:

| crash | faults |
|---|---|
| 01:14:58 | 10 |
| 01:19:32 | 10 |
| 02:19:23 | 10 |
| 10:25:40 | 10 |
| 12:56:17 | 10 |

**Exactly 10, and strictly contiguous 40 KiB, on every single crash.** That is the signature of a *single* batched copy walking past the end of a buffer, not of memory corruption or a randomly bad address. (For comparison, unrelated page faults elsewhere in the same boot are single events.)

All faults report `SDMA0` and land on the GPU at `0000:07:00.0`.

---

## Finding 3: applying the #21170 change does **not** stop the crash

We patched our build with exactly what #21170 proposes (HIP-only removal of the `ggml_cuda_set_device()` early-return, plus the added `ggml_cuda_set_device()` in `ggml_backend_cuda_set_tensor_async()`), verified the change is present in the built `libggml-hip.so` (`hipSetDevice` called, `hipGetDevice` no longer called in `ggml_cuda_set_device`), and confirmed the running process had loaded that patched library:

```
$ objdump -d build-hip/bin/libggml-hip.so.0.22.0 | sed -n '/<ggml_cuda_set_device>:/,/ret/p'
  ... call hipSetDevice@plt        <- no hipGetDevice@plt
$ grep -o '/[^ ]*libggml-hip[^ ]*' /proc/<pid>/maps | sort -u
  /home/.../llama.cpp/build-hipfix/bin/libggml-hip.so.0.22.0
```

With that build loaded we still crashed, with the same stack:

```
$ journalctl -u <svc> | grep -E 'ROCm error|current device|hipMemcpyAsync'
... ROCm error: an illegal memory access was encountered
... current device: -1, in function ggml_backend_cuda_buffer_set_tensor at ggml-cuda.cu:805
... hipMemcpyAsync((char *) tensor->data + offset, data, size, hipMemcpyHostToDevice, ((hipStream_t)2))
```

So this is consistent with @IMbackK's comment that the patch "doesn't really solve anything". It may shift timing, but it does not remove the fault.

---

## Finding 4: a deterministic reproducer

Synthetic load was surprisingly hard to use: 600 consecutive short requests (~450–720 tokens, shared prefix, LCP hits every time, 602 checkpoint evictions) ran **0 crashes**. What does reproduce it reliably is alternating **two different long prompts**:

```
A (16K tokens) → B (16K tokens, different content) → A → B → ...
```

- First attempt at this: crash within ~700 ms of the alternation starting.
- Afterwards 8 consecutive attempts: 0 crashes — it needs the accumulated state/prompt-cache to build up again first.

The crash lands in the checkpoint/prompt-cache restore path:

```
#4  ggml_backend_cuda_buffer_set_tensor  /  ggml_backend_cuda_synchronize
#5  llama_io_read_host::~llama_io_read_host
#6  llama_context::state_seq_set_data
#7  common_prompt_checkpoint::load_tgt   /  server_prompt_cache::load
#8  server_context_impl::pre_decode()::{lambda(server_slot&)#6}
```

8 of 12 observed crashes are `load_tgt`; the others are `update_tgt` (via `llama_context::synchronize`) and one straight from `llama_decode`.

---

## Finding 5: disabling `--ctx-checkpoints` alone is not sufficient

We initially worked around it with `--ctx-checkpoints 0`. That removes the checkpoint path, but we then crashed via the **prompt cache** path instead, which uses the same serialization entry point with `flags = 0`:

```
#7  server_prompt_cache::load      <- not a checkpoint
#6  llama_context::state_seq_set_data
#5  llama_io_read_host::~llama_io_read_host
```

Both call sites go through `llama_state_seq_set_data_ext()` and end in the same `hipMemcpyAsync(..., hipStreamPerThread)` on the server's main thread. To actually stop it we had to disable both (`--ctx-checkpoints 0 --cache-ram 0`).

That workaround costs real performance: alternating two different long prompts goes from **0.71 s to 4.71 s** (every turn re-prefills instead of restoring). So it's not something we want to keep.

---

## Summary / questions

1. `current device: -1` looks like a red herring — it's set when `cudaGetDevice()` fails *after* the error. The actual reported error is a plain illegal memory access.
2. The fault pattern (exactly 10 contiguous 4 KiB pages, `SDMA0`, always the same GPU) looks like a single batched transfer overrunning a buffer, rather than a missing device context.
3. The #21170 workaround does not prevent it — reproduced with that patch built and loaded.
4. Reliable trigger: alternating two long prompts with a hybrid-recurrent model, which exercises repeated save/restore.

Is there a known-length/off-by-one issue in the state (de)serialization path for hybrid recurrent memory, specifically in how `llama_memory_recurrent::state_read_data()` maps `cell_count` onto the `r_l` / `s_l` row offsets? We'd be glad to test any patch or gather more targeted instrumentation (e.g. dumping `offset`/`size` per `read_tensor`) if that would help.

We're happy to provide full logs, the exact reproducer script, or to run a debug build with extra assertions on request.
