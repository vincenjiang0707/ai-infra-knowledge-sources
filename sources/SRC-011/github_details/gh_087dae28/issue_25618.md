# [Issue #25618] Eval bug: Speculative decoding (draft-mtp / draft-dspark): greedy output diverges from vanilla on quantized targets

source: https://github.com/ggml-org/llama.cpp/issues/25618
state: open | updated: 2026-09-22T17:11:42Z
labels: bug-unconfirmed

## 正文

## Summary

Under greedy sampling (`temperature=0`, `top_k=1`), **draft-model** speculative decoding can produce different text than a non-speculative run when the **target is quantized** (e.g. Q4_K_M). The same setups match on a **bf16 target**. **Ngram** speculation on the same quantized target stays lossless even when drafts are accepted.

This contradicts the expected property that speculative decoding is lossless for greedy decode (draft proposes; target verifies).

Related: https://github.com/ggml-org/llama.cpp/pull/25173 (`draft-dspark`), but the issue is **not DSpark-only**.

## Environment (local repro)

- Hardware: AMD Strix Halo iGPU
- Backend: Vulkan (`-DGGML_VULKAN=ON`)
- Branch: PR #25173
- Others have also reported similar mismatches on **CUDA** (not re-run here)

## Expected

Greedy speculative output == greedy vanilla output for the same target weights / seed / prompt.

## What this is / is not

- **Is quantization-related:** yes (Q4 breaks; bf16 OK for DSpark).
- **Is not “all speculative”:** ngram paths match on the same Q4 target, including with accepts.
- **Is not DSpark/DFlash-only:** Gemma **MTP** also diverges on Q4.
- **Is not Qwen-only:** Gemma-4 + MTP also fails.
- **Is not vanilla Q4 nondeterminism:** two vanilla Q4 runs match.
- **Is not FA-only:** DSpark still mismatches with `-fa off`.
- **Target weights likely fine:** ngram uses the same greedy accept/verify sampler path (`common_sampler_sample_and_accept_n` in server) and stays lossless → points to **draft-model speculative paths** (MTP / DSpark: draft ctx, KV, embd/injection, multi-token target batching) interacting badly with **quantized** target compute—not permanent weight corruption.
- **Type-cast root cause:** not isolated; path-dependent Q4 numerics remain a plausible contributor.

### Ankk98 · 2026-07-13

**Issue 1 - FA GQA packed path for multi-token queries.** Speculative verify runs flash attention with `neq1 > 1` (several query tokens at once). Vulkan’s GQA-packed FA path treated `N <= 8` as “use GQA packing,” then overwrote `N` with `gqa_ratio` and remapped workgroups as if there were a single query token. That is only valid for single-token decode, so multi-token parallel verify disagreed with sequential FA and drifted logits (e.g. wrong-draft windows with `n_win >= 4`). Fix: only enable that packing when `neq1 == 1`.

**Issue 2 - FA-off KxQ used GEMM instead of p021.** With flash attention off, scores are `mul_mat` of permuted F16 K (cache view) and F32 Q. The correct Vulkan path is `mul_mat_vec_p021`, but the dispatch required `dst->ne[1] == 1`, so multi-token verify fell through to general `mul_mat_q_f16` GEMM. That path is not bitexact with single-token p021 on strided/permuted KV, so parallel vs sequential argmax flipped (classic `279` vs `432` at cut=4). Fix: extend p021 to `ncols_y > 1` with token-major Q indexing.

**Issue 3 - FA packed vs generic path mismatch after rejects.** Even after Issue 1’s gate, single-token decode still used the GQA-packed FA kernel while multi-token verify used the generic FA kernel. Those two paths are not bitexact, so K/V written for accepted token S during parallel verify disagreed with what sequential decode would have written; after reject + `seq_rm`, greedy continuation could still diverge. Fix: disable the packed path so single- and multi-token decode share one FA implementation.

**Issue 4 - FA tile sizes and split_k depended on N.** Scalar flash-attn tuning chose different block shapes / AMD subgroup sizes for `n_rows == 1` vs `n_rows > 1`, and `split_k` scaled with token count. Parallel verify (N>1) and sequential decode (N=1) therefore computed different values for the same logical query (and for S’s K/V). Fix: for speculative-sized batches (`N <= 8`), force the N=1 tile configuration and `split_k = 1`.

**Issue 5 - FA-off Vxkq could not batch tokens and heads together.** Value multiply `mul_mat(V, kq)` has `ne11 = n_tokens` and `ne12 = n_head`. DMMV only supported either multi-column (`NUM_COLS`) *or* multi-head batching on `WorkGroupID.y`, both overloading the same `batch_stride_*` fields. Speculative FA-off hit both axes and fell through to GEMM, which diverged from single-token DMMV. Fix: dual strides - columns use `stride_b`/`stride_d`, heads keep `batch_stride_*`.

**Issue 5b - DMMV host used logical `ne` strides on holey views.** After dual-stride landed, some probes still looked wrong because the host computed Y/D batch strides from `ne10*ne11`. A view with `ne11 == 1` into a multi-token parent has physical `nb[2] = n_kv * n_tok`, not `n_kv`, so head `> 0` read the wrong B/D slices. Dense parallel DMMV was already fine; the bug was view/hole indexing. Fix: use physical `nb[1]`/`nb[2]` when Y is not staged contiguous.

**Issue 6 - MMVQ DMMV not bitexact across batch size (FA-off residual).** After 1-5b, FA-on was clean but FA-off full matrix still had many BUGs. `COMPARE_SEQ` showed endemic soft logit drift (LINF ~0.1-0.3) and sparse argmax flips because parallel verify used integer-dot MMVQ (`Q8_1` staged Y, `NUM_COLS > 1`) while sequential recheck used `NUM_COLS == 1` (often also MMVQ). Those paths disagree, so greedy accept/reject diverged from vanilla. Disabling MMVQ only for `n > 1` was not enough (F32 parallel vs MMVQ seq still drifted). Fix: disable auto MMVQ for DMMV entirely so both N=1 and N>1 use F32 DMMV (prefill GEMM MMQ unchanged; force-reenable via `GGML_VK_FORCE_MMVQ`).

### dbsanfte · 2026-08-08

Hi, I'm the developer of Llaminar and I've been working on MTP myself.

https://github.com/Llaminar/llaminar

The key to MTP working is a property called *batch invariance*. The DeepSeek DSpark paper is quite clear about this. Here's also the vLLM doc on the topic: 

https://docs.vllm.ai/en/latest/features/batch_invariance/

A kernel that does a batched/grouped decode for e.g. M=3 must be bitwise identical to the serial decode result (unbatched) for rows 1,2,3. This is an obligatory invariant and it touches every kernel in the codebase. Cosine/KL is not enough. 0.999999999 is not enough. It must be *bitwise identical*.

All GEMM/GEMV kernels need to be batch invariant, and proven to be so. Floating point reduction orders need to be identical. 

That's how you fix this. Even one ULP difference is enough to cause MTP to diverge. 

I speak from experience here, I had to rewrite most of my math kernels in order to stop this drift, absolute pain 😅

## Interpretation / scope

- The Q8_0 draft is not inevitably associated with different output here: with FA on and F16 V cache, MTP was byte-exact and descriptively about 30% faster for this prompt in two launches per mode.
- With FA on, the F16-V variant is exact while the Q8_0-V variant diverges on this probe. This is consistent with a quantized-V/batched-verification interaction, but it does not prove one: an ordinary batch-dependent numerical shift could cross a near-tied greedy argmax only in the Q8_0-V run.
- With FA off and F16 V, MTP also diverges. That is consistent with the separate non-FA path discussed above, but again is association rather than causal isolation.
- `--no-spec-draft-backend-sampling` did not affect the divergence.
- The wall-time percentages are descriptive for this single 384-token prompt and two launches per mode, not statistical performance estimates.
- I did not run the 27B target in BF16 under comparable conditions.

- operation: `linear_attn_out-0`, `MUL_MAT`
- weight: Q8_0 `[6144, 5120]`

- baseline path (`N=1`): `mul_mat_vec_q8_0_f32_f32`

This confirms the path switch and F32-to-Q8_1 staging as the cause of this boundary, not sampling or the drafter.

A narrow local diagnostic gate removed this boundary in a fresh `n_predict=2` baseline/MTP run: generation 0 remained exact, the layer-0 predecessor and output were exact, and one draft token was generated and accepted. Full generation-1 logits still differed (`248040/248320`), however, so this is not a complete fix.

### 2. Next confirmed boundary: ADD -> RMS reduction path

With the Q8_0 boundary removed, bounded layer bisection preserved the reference full-logit hashes and located the next earliest difference in layer 2:

- exact predecessor: `attn_residual-2`, ADD F32
- first different result: `norm-2` RMS_NORM fused with the following MUL
- `3417/5120` values differ, max 2 ULP, RMS `1.09370787e-08`
- `N=1`: fused ADD/RMS partial reduction (`rms_norm_mul_partials_f32`)
- `N=2`: ordinary ADD followed by regular `rms_norm_mul_f32`

Standalone CPU/Vulkan replay reproduced the captured `N=1` and `N=2` row-0 outputs bit-for-bit. Forcing the regular reduction for `N=1` produced exactly the captured `N=2` row-0 hash. CPU `N=1`/`N=2` remained exact.

This second finding is operator-level evidence only. The local ADD/RMS diagnostic candidate has not yet passed its final test-harness quality review or a combined model-level generation-1 gate, so I am not presenting it as a fix.

A separate real generation-1 capture showed that row-0 Q and the current-position K/V already differed before `FLASH_ATTN_EXT`; the causal mask and the earlier K/V prefix were exact.
```
ncols_dst 1..4  ->  4 warps
ncols_dst 5..8  ->  2 warps
ncols_dst > 8   ->  1 warp
```

`ncols_dst` is the verification width, and the warp count feeds two things in `mmvq.cu` that change the arithmetic rather than only the occupancy. `blocks_per_iter` is `vdr * nwarps * warp_size / qi`, so each thread walks a different subset of the K dimension in a different order. The standing explanation for this class of divergence is that different batch sizes take different kernels ([#23335](https://github.com/ggml-org/llama.cpp/issues/23335#issuecomment-4488338528)). I ran the missing `--spec-draft-n-max 1` cases to put numbers on that: where it starts, whether the rates track the dispatch boundaries, and whether the boundary itself is causal.

**Divergence starts immediately at width 2** (`--spec-draft-n-max 1`), the smallest speculative width there is. There is no non-divergent onset threshold; it is present as soon as anything is verified in a batch at all. At width 2, 57 of 75 requests differed from the non-speculative baseline. That is consistent with the batch-invariance framing raised earlier in this thread: the invariant is already violated at M=2.

The rates group, and the groups coincide with the dispatch boundaries in `ggml/src/ggml-cuda/mmvq.cu`:

| Widths (`n-max` + 1) | `mmvq.cu` dispatch (`ncols_dst`) | Identical | Median shared prefix |
| --- | --- | ---: | ---: |
| 2, 3, 4 | 2..4 (4 warps) | 24.0% | 0.240 |
| 5, 6, 7, 8 | 5..8 (2 warps) | 20.0% | 0.228 |
| 9 | above `MMVQ_MAX_BATCH_SIZE 8`, leaves the kernel | 12.0% | 0.172 |

So the rate groups do follow the dispatch table. But the table is not the cause.

**Important negative result: the warp count is not the mechanism.** I ran a forced-warp intervention using four builds from one configure, with the `MMVQ_PARAMETERS_GENERIC` table edited up at widths 5 to 8 and down at 3 and 4. SASS confirms the edit reached the machine code and only there: 92 and 46 `mul_mat_vec_q` kernels at exactly those `ncols_dst`, and Ampere dispatches every quantized type through MMVQ at ne11 1 to 8, so the edited kernels are the ones that run.

The forced builds moved the kernel's runtime by up to **26.68%** and changed **not one output byte** in 150 records each. A change that moves no output cannot move a fork position, which is a property of the text. The table coincides with the boundary, but it is not what puts the widths into two groups.

### skoulik-claude · 2026-09-16

**Metal: the two places where a verify batch stops matching a single-token decode**

Adding a Metal data point, with the kernels isolated. The setup differs from the reports above: the target is **Q8_0 with an f16 KV cache** (`-fa on --swa-full`, Apple M1 Max, Gemma 4 26B-A4B with its in-checkpoint MTP drafter, n-max 2). So neither a quantized KV cache nor a K-quant target is needed.

**What breaks.** Speculative decoding only works if the target model computes the same thing for a token whether that token is decoded on its own or verified as one row of a batch. On Metal it computes something slightly different, in two places:

1. **`mul_mv` against `mul_mv_ext`.** One token goes to `kernel_mul_mv_<type>_f32`, which multiplies int8 by float and applies the block scale once at the end, with a threadgroup per token. Two to eight tokens go to `kernel_mul_mv_ext_*`, which dequantizes to float4 first, accumulates float4 dot products over a strided set of chunks, and reduces across lanes with halving shuffles. Different scaling point, different assignment of values to threads, different reduction tree. `nxpsg` also depends on the token count itself (16 when the row length divides by 256 and there are fewer than 3 tokens, else 8), so batches of 2 and of 3 disagree with each other too — which is why every `--spec-draft-n-max` value produces its own outputs.
2. **`flash_attn_ext_vec`'s simdgroup count.** `nsg` doubles while `2*nwg*nsg*ncpsg < ne11`, i.e. past a padded KV length of 2048 and again past 4096, and the KV length is padded in steps of 256. A verify batch reaches the boundary one or two positions before plain decoding does, so at exactly those positions the same query is reduced by a different number of workers.

**Measured.** Comparing a 1-token decode against row 0 of a 2- or 3-token batch at the same position: unmodified, row 0 differs at every position, the first differing tensor being layer 0's Q projection, with logits up to 7e-3 apart. Sending 2–8 rows to `mul_mv` leaves every position bit-identical **except** 2046/2047 and 4094/4095, which is what pointed at the attention threshold; pinning `nsg` as well makes all positions bit-identical, along with all 2074 intermediate F32 tensors.

Every divergence we traced was a near-tie: at the first split the top two tokens were 0.0027 nats apart, at the second 0.0004. So the output changes but the quality does not, which matches the small macro-score deltas reported elsewhere in this thread. On a 62-request workload, MTP on and MTP off agreed on 24 of 62 requests unmodified, and on **62 of 62** once both causes were addressed.

Happy to share the probe and the diff if useful.

1. In every case the token the speculative arm emitted is the target's **runner-up** (once third) under
