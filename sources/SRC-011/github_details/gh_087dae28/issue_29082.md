### Problem description & steps to reproduce

## What happened

`llama-server` with the Vulkan backend crash-aborts while loading sliding-window-attention
decoder models when the KV cache is offloaded to the GPU. The process dies with
`exitCode=3221226505` (`0xC0000409`, fail-fast) before becoming healthy.

Exact abort line (stderr):

```text
llm-engine\llama.cpp\ggml\src\ggml-backend.cpp:941: pre-allocated tensor (cache_k_l0) in a buffer (Vulkan1) that cannot run the operation (NONE)
```

## Regression info

- ✅ `llama.cpp ... 2.39.0` (Vulkan, AVX2) — same model, `-ngl 99` — **loads in ~5s, serves fine**
- ❌ `llama.cpp ... 2.40.0` (Vulkan, AVX2) — same model, `-ngl 99` — **aborts as above**
- ❌ `llama.cpp ... 2.41.0` (Vulkan, AVX2) — same model, `-ngl 99` — **aborts as above**
- ✅ `2.41.0` Vulkan with `--no-kv-offload` — **loads and serves** (KV cache on CPU)
- ✅ `2.41.0` Vulkan with full offload + embedding model (`nomic-embed-text-v1.5.Q4_K_M`,
  full attention, `--embedding`) — **loads and serves**

So it is not a globally broken Vulkan backend: it is the
`Vulkan + KV-cache GPU offload + SWA/hybrid-attention decoder` path that regressed
between 2.39 and 2.40.

## Repro

```bat
llama-server.exe -m mistralai_Voxtral-Mini-3B-2507-Q4_K_S.gguf -ngl 99 --port 18081
```

- Model: `bartowski/mistralai_Voxtral-Mini-3B-2507-GGUF`, `Q4_K_S` (~2.4 GB)
- No other flags (all defaults). Crash happens during `load_model`, before listening.

Notable log lines on the crashing 2.41 run (before the abort):

```text
W resolve_fused_ops: layer 0 is assigned to device Vulkan1 but Flash Attention is assigned to device CPU (usually due to missing support)
W resolve_fused_ops: Flash Attention not supported, set to disabled
W ggml_vulkan: Failed to allocate pinned memory (Requested buffer size exceeds device buffer size limit: ErrorOutOfDeviceMemory)
```

On the working `--no-kv-offload` run the server reports `kv_unified = 'true'`,
`n_slots = 4`, then `model loaded` / `listening`.

## Environment

- OS: Windows 11 x64 (build 10.0.26200)
- GPU: Intel Arc Pro B50 (discrete) + Intel integrated Graphics
- Driver: Intel `32.0.101.8805` (06.07.2026), `vulkan-1.dll` present (system + app dir)
- Builds: LM Studio / Bionic bundled `llama.cpp-win-x86_64-vulkan-avx2` packs
  `2.39.0` (working) vs `2.40.0` / `2.41.0` (crashing), CPU 14 threads
- The same setup serves the models fine on engine 2.39, so driver / loader / model
  file are ruled out

## Suspected area

New fused-ops / unified-KV graph building for SWA models (`cache_k` pre-allocation
landing in a Vulkan buffer that reports no supported op) introduced between 2.39
and 2.40. Happy to test any debug build / extra logging on this machine
(Arc Pro B50 available).

### First Bad Commit

Regressed between bundled builds 2.39.0 (works) and 2.40.0 (broken). Exact upstream commit unknown — these are third-party Bionic/LM Studio bundles, not direct llama.cpp builds. Happy to bisect if given build instructions for Windows Vulkan.

### allutkin-stack · 2026-09-18

Update: 2x Intel Arc Pro B50 here. Forced single-device runs (GGML_VULKAN_DEVICE=0/1/2) all abort identically with the same cache_k_l0 line, so this is not a multi-GPU split issue.

### allutkin-stack · 2026-09-23

Still reproducible on the newest Vulkan runtime (2.44.0), and after bisecting it the trigger looks narrower than this issue's title suggests.

TL;DR: the abort needs `n_slots = 4` (`--parallel 4`) **together with** KV-cache GPU offload. It is not SWA-specific (a plain Llama-arch model reproduces it), not VRAM pressure (a 3.2 GB model that fits entirely in one 16 GB card still aborts), and not a multi-device split problem (`-dev Vulkan1` aborts as well).

### Versions

- broken: `llama.cpp-win-x86_64-vulkan-avx2` 2.44.0 - `llama-server --version` reports `0.4.1-dev (build 1, commit 42916d8)`
- works: same runtime, 2.39.0 - `0.4.1-dev (build 1, commit d1d3c33)`
- both are the LM Studio Bionic bundled builds (app 1.1.6+3), Windows 10.0.26200

Hardware: 2x Intel(R) Arc(TM) Pro B50 (16 GB each) + Intel(R) Graphics iGPU, driver 32.0.101.8805, 68 GB RAM, models on NVMe.

### Repro (small model, aborts in about 1 s)

```console
llama-server.exe --model Voxtral-Mini-3B-2507-Q4_K_M.gguf --no-webui --jinja ^
  --fit on --fit-ctx 32768 -b 2048 -ub 512 -t 5 -np 4 ^
  -ctk f16 -ctv f16 -fa on -kvo -kvu
```

```console
llm-engine\llama.cpp\ggml\src\ggml-backend.cpp:941: pre-allocated tensor (cache_k_l0) in a buffer (Vulkan1) that cannot run the operation (NONE)
```

The process exits with `3221226505` (`0xC0000409`). `-kvo` / `-kvu` are the defaults and are only listed here because the app passes them explicitly.

### What changes the outcome (2.44.0, same command line otherwise)

- `-np 1`, `-np 2`, `-np 3` - loads and serves normally
- `-np 4` - aborts, deterministic (3 out of 3 runs)
- `-np 4` with `-nkvo` (KV cache left on the host) - loads normally
- `-np 4` with `-dev Vulkan1` (single GPU, no iGPU) - aborts with the same line
- `-np 4` with a smaller context (`--fit-ctx 8192`) - aborts
- `-np 4` with `-fa auto` instead of `-fa on` - aborts
- `-np 4` without the mmproj or without `--spec-type draft-mtp` - aborts (both irrelevant)
- a 35B MoE model (Qwen3.8-35B-A3B Q4_K_M + mmproj + draft-mtp) - same abort, tensor `cache_k_l3`
- either model on 2.39.0 with `-np 4` and KV offload enabled - loads normally

LM Studio always launches the engine with `--parallel 4`, which is why every model load in the app hits this path. On 2.44.0 the only escape hatches found are disabling KV-cache GPU offload or rolling the runtime back to 2.39.0.

### App-side evidence

### SG-Amadeus · 2026-09-26

This looks related to #28849 and #29437.

In my Vulkan reproduction on Windows 11 with an RTX 5070 Ti 16 GB, I could trigger the same `cache_k_l0 ... operation (NONE)` failure path by forcing the buffer-size boundary across the transient KV tensor. With 4 slots, auto-fit briefly probes `n_ctx = 524288` (`131072 × 4`), making `cache_k_l0` reach 1 GiB.

After applying #29437, which reverts #28849, that `524288` probe disappears and the same limit no longer reproduces the failure.

It may be worth checking #28849, #29270, and #29437 against this issue.
