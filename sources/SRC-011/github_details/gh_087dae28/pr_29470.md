# [PR #29470] server: roll back batch state after slot exceptions

## 正文

## Overview

Fixes a `llama-server` exception-safety issue where a failed slot could leave partial state in the shared batch and later trigger a process-level abort.

During `pre_decode()`, a slot may append tokens or embeddings and update related state before a later operation throws. Previously, `iterate()` released the failed slot without rolling back those partial changes, which could leave inconsistent state such as:

```cpp
batch.size() > 0 && batch.slot_batched == nullptr
```

and later trigger:

```cpp
GGML_ASSERT(batch.slot_batched || batch.size() == 0);
```

This PR adds per-slot rollback for unrendered batch state. On exception, it restores the previous batch sizes and metadata, resets temporary speculative / aLoRA state, clears the failed slot's prompt state, and preserves work already added by healthy slots.

It also moves `batch.clear()` to the start of `pre_decode()` so the batch-building phase is consistently rollback-safe, and skips slot pointers that have already been released.

## Additional information

Related issue: #29391

This does not fix the underlying cause of the reported `std::bad_alloc`. It prevents a slot-local exception from corrupting shared batch state and escalating into a server-wide failure.

Regression tests use deterministic fault injection to throw `std::bad_alloc` after a slot has already modified the batch.

The tests cover:

- prompt and generation phases;
- single-slot and multi-slot continuous batching;
- failures in different slot positions;
- preservation of healthy requests and their generated tokens;
- server health after the failed request;
- cleanup of the failed slot's prompt/cache state;
- successful retry after rollback;
- normal prompt-cache reuse after recovery.

The rollback only stores vector sizes and a small amount of metadata; it does not copy the full batch.
