### Problem description & steps to reproduce

The crash occurred during speculative decoding (`common_speculative_draft`) while running Gemma 4 with draft-mtp, KV unified cache, and multi-GPU tensor split (`-sm tensor -dev Vulkan1,Vulkan2`).

### To Reproduce

Run `llama-server` with the following parameters:

/usr/bin/llama-server \
  --kv-unified --reasoning on \
  --jinja --tools all -np 1 \
  -hf unsloth/gemma-4-31B-it-qat-GGUF:UD-Q4_K_XL \
  -ctk bf16 -ctv bf16 -c 65536 -b 256 -ub 256 \
  -ngl 60 --no-mmproj-offload -sm tensor --spec-type draft-mtp --spec-draft-n-max 4 \
  -dev Vulkan1,Vulkan2 \
  --port 8081 \
  --host 0.0.0.0

Server loads the model, vision projector (mmproj-BF16.gguf), and MTP draft model (mtp-gemma-4-31B-it.gguf).

Run multiple conversational tasks (in this instance, context grew across tasks 0, 252, 696).

Task 696 was canceled / stopped.

### tczank · 2026-09-26

**Not reproducible on AMD under structurally identical conditions — plus two pointers from the assert's neighborhood.**

Ran your condition class (`-sm tensor` dual-device + `--kv-unified` + `--spec-type draft-mtp` + `-fa on`) on RX 7900 XTX + 7800X3D iGPU (RADV Mesa 26.2.3, `-dev Vulkan0,Vulkan1`), build `a02c7f58c`. Your `4de092659` and `a02c7f58c` have **identical `ggml-vulkan` sources** — `git log a02c7f58c..4de092659 -- ggml/src/ggml-vulkan/` is empty.

- 3 boots, 6 greedy completions (5 x 100 tok + 1 x 400 tok), embedded-MTP model, ctx 4096, q4_0 KV, n-max 2: **0 `GGML_ASSERT`**, all outputs valid, MTP active (acceptance 0.6418-0.68675, mean verify 2.28-2.36)
- both devices proven computing mid-generation: iGPU 100/100/100 %, XTX 13/29/9 % busy sampled at 45/53/61 s (decode 2.22-2.47 t/s — iGPU-bound, as expected for tensor split with a 2-CU iGPU)
- log confirms `kv_unified = 'true'`, `offloaded 66/66 layers to GPU`, `flash_attn = enabled` on both target and draft contexts
- with n-max 2 the verify batch is N = 3, i.e. inside the same `N <= 8` multi-token window as your n-max 4 (N = 5)

Reading the assert (line numbers in `a02c7f58c`, which is your source): `:8025` sits at the entry of `ggml_vk_flash_attn()` (`:7988`), with `HSK = nek0` (`:8012`) — it checks Q's dim0 against K's dim0, both static head-size properties of a model's layout. Since you crashed first at task 877 (after the LCP reuse + prompt-state-skip warning, mid-generation), a *dynamic* mismatch implies some graph variant handed FA a non-canonical Q or K shape rather than a static model property.

Two pointers from the same region:

1. The GQA-packing gate for multi-token queries is right below the assert: `:8075` (`N <= 8 && qk_ratio > 1 && ...`), and the Xe-specific dual-phase pipeline is keyed at `:8231` (`xe_fa_pipeline_dual_phases`, `pipelines[{neq0, nev0, qk_ratio, neq1}]`). Your B580s (Xe2) take that path, RDNA3 does not — which fits both your repro and my non-repro. This is also the territory of #26358 ("vulkan: disable FA GQA packing for multi-token queries", closed unmerged, @0cc4m: "probably valid, but the code needs to be cleaned up"). Worth noting the packing gate is engaged during MTP verify on my side too (verified earlier in the #25618 discussion for this model), so RDNA3 exercises that code without hitting `:8025`.

2. Cheap isolations that would narrow it fast: print the actual `neq0` / `nek0` values at `:8025` (one-line patch — the values immediately say model-wrong vs graph-variant-wrong); `-fa off` control through your 877-task sequence (if it survives, the fault is in FA input construction); single-device control (`-dev Vulkan1` alone, `-sm none`) to confirm tensor-split dependence.

I do not hit the LCP-churn / 9.3 GB prompt-state precondition (short prompts here), so the reuse-triggered variant specifically remains untested on my side — happy to run a scripted churn sequence if someone can confirm the single-device control first.
