### Hardware

Linux / CUDA / 4× Tesla P100-PCIE-16GB (sm_60), dual Xeon, driver 580.159.03, CUDA 12.4. Tested on Ubuntu Server 26.04.

### Models

Qwen3.6-27B Q6_K (22,523,238,624 bytes) for the quality panel; Qwen3.6-4B dense and Darwin-36B-A3B (Qwen3.5-MoE arch) Q6_K for the speed legs.

### Problem description & steps to reproduce

SM_60 currently gets put into a hardware accelerated fast-path by default, which uses a FP16 hardware accelerator. The problem is that some FP32 math is silently getting truncated to FP16 that shouldn't be, causing significant accuracy deviations from baseline (0.002298 median KL divergence vs FP32 reference/1-in-29 flipped top tokens).

The fix for this is to carve out SM_60 the same way SM_61 already is, bypassing the Fast Path gate, and keeping FP32 math at 32 bits as it should be.

1. Build stock llama.cpp using  `-DCMAKE_CUDA_ARCHITECTURES=60`.
2. Generate the truth base, run `llama-perplexity --kl-divergence-base out.kld` with fp32 KV, FA off,
   on a patched build (fp32 arithmetic) — this is the step everyone skips.
3. Compare the stock vs patched runs against that base with `--kl-divergence`, 2048 ctx, 32 chunks.
4. Speed: `llama-bench` pp8192/tg32 @ d8192, patched vs unpatched, same host, nothing else
   on the GPUs.



### First Bad Commit

We followed the 610-only exemptions in their present form back through the 2024-era commits dc685be46 (#7188, FP32 FA vec kernel), 9b596417a (#7527, quantized KV for FA vec), and a818f3028 (#8075, MMQ-by-default) — sm_60 has been on the fast path the whole time,  no bisect needed.

rankaiyx is right.

Our testing captured circumstances where attention dominates and the GEMM share is diluted. 
Their test is the opposite shape. Nearly pure GEMM. The fp16→fp32 GEMM cost shows prefill −26.8%(1),

Importantly, decode remains flat to slightly improved post patch(2).

I'd suggest an opt-in for Fast_Path so it remains optional if needed, e.g. an env var or build flag (say, GGML_CUDA_FORCE_FAST_FP16) on the three gates. 

1. (row-split, 532.5→389.7 t/s) and −26.7% (layer-split, 199.6→146.2 t/s) end-to-end, roughly flat with depth.
Also informative, their workload is GEMM-bound the whole way through, exactly the shape our attention-heavy benches didn't sample.

2. their logs: 31.76 vs 30.40 t/s row-split (+4.5% patched), 12.54 vs 12.64 layer-split (tie); consistent with the +1.4–1.5% decode improvement we measured on our own rig.

### apollo-mg · 2026-07-16

We ran a V3 test last night on our 4×P100 at their workload shape(1). We applied the same carve-out change to upstream master 505b1ed1 — rankaiyx's branch is line-for-line identical to the patch merged in the two forks, so the built source is byte-equivalent.

Interestingly, the regression does not reproduce here — it inverts. Decode is a wash within noise here (±1–2% across our runs, sign varies by workload). Here's what we saw: 

| build | prefill | decode |
|---|---|---|
| master (fp16 fast path) | 261.7 t/s | 13.85 t/s |
| + carve-out (fp32) | 286.1 t/s (+9.3%) | 13.76 t/s |

V1's env-toggle on our old lineage gave nearly identical numbers. So it would seem that on this rig, fp32 beats fp16 across two code generations, repeatably. rankaiyx measured −27% on their 4×P100; we measure +9% on ours, same code. In other words, it looks like fp16 fast path on sm_60 isn't a speed feature with a cost — it's a coin-flip whose sign depends on environment (prime suspect: cuBLAS HGEMM kernel selection varies by CUDA version — we're CUDA 12.4 / driver 580.159.03; theirs unknown). 

Given the data so far, it would appear neither default is right for everyone. Hardcoding either direction would guarantee someone a 9–27% regression. I cannot test row-split (no P2P on our board — "does not support split buffers").

### apollo-mg · 2026-07-17

Mystery solved. Microbatching was the whole discrepancy. We reproduced both directions of the sign flip on one machine by changing only the ubatch flag. At ub 512 the builds' weight paths are effectively identical and the delta is FA kernel choice between builds; with -fa off the gap collapses to noise (249.5 vs 247.0, −1.0%). The weight GEMMs run through cuBLAS at both sizes; but at ub 4096 they're large enough that sm_60's roughly 2× HGEMM-over-SGEMM throughput dominates, while at ub 512 the precision choice is immaterial (fa-off cells).

| cell (v7, e8f19cc0, clean builds) | master | carve-out | delta 
|---|---|---|---|
|ub 512, fa on | 261.6 | 285.9 | carve +9.3% |
|ub 4096, fa on | 266.8 | 215.6 | master +23.7% |
|ub 512, fa off|249.5|247.0|−1.0% (gap gone) |
| ub 4096, fa off |OOM |OOM |untestable, ~13.3GB buffer on 16GB |

All prefill t/s, 27,123-token prompt, driver 580.159.03, CUDA 12.4, Qwen3.6-27B Q4_0, quad P100 layer-split, temp 0. Decode is a wash in every cell (13.86 vs 13.75 @512; 12.95 vs 12.84 @4096 — both −0.8%). v7 cells are 1 rep; the fa-on cells match the earlier 2-rep runs within 0.2 t/s (v3 means 261.7/286.1, v4 means 266.9/215.8). Commit e8f19cc0, pulled July 16.

Proposal: correct-by-default with GGML_CUDA_FORCE_FAST_FP16 as a compile-time opt-in — probably a CMake define, which would be consistent with the existing FORCE_MMQ/FORCE_CUBLAS family. Net effect: default-ubatch users get the correctness fix plus a free speedup; large-ubatch users lose prefill performance that's recoverable by tuning on this workload — the correct build at default ubatch (285.9) is in fact faster than the fast-fp16 build at ub 4096 (266.8).
