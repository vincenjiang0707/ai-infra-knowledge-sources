### Problem description & steps to reproduce

Originally from #25214.
After about 70 seconds of idle time, the secondary (no display connected) dGPU's dedicated memory usage starts to drop while the primary dGPU dedicated memory usage show no change.

Confirmed that VRAM unloading to RAM when idle. This VRAM unloading issue causes following 3 problems:
1. Performance degradation
2. Model weights use double memory (one from llama.cpp, one from VRAM unload).
3. Related to problem 2: with --load-mode dio, llama would not normally keep model weights in RAM. However, if VRAM is offloaded, llama will abnormally keep model weights in RAM, causing model weights to still use double memory even when using dio.

I believe this PR https://github.com/ggml-org/llama.cpp/pull/25214 is necessary, many users reported similar issue.

### ac-mmi · 2026-09-21

I did some digging into the current Vulkan backend and the behavior in this issue.

One thing that seems clear from the code is that this isn't llama.cpp actually unloading the model.

With `--sleep-idle-seconds -1`, the idle server path does not destroy the model/context or Vulkan buffers. `/models` can therefore remain `loaded` while the underlying Vulkan allocations still exist. The observed drop in dedicated VRAM appears to be a separate memory-residency/demotion event.

I also looked at #25214. There seems to be a multi-GPU coverage issue with the Vulkan heartbeat proposed there: the heartbeat is gated on `ctx->sync_staging`, which is owned by an individual `ggml_backend_vk_context`. Normal device staging is instead `device->sync_staging`, and multiple backend contexts/devices can exist.

This means a heartbeat attached to a particular backend context isn't necessarily equivalent to keeping every Vulkan device containing model weights active.

A possible alternative would be a Vulkan-backend-local, device-level keep-alive:

    vk_device
        -> device-owned small staging buffer
        -> periodic vkCmdFillBuffer
        -> device queue/fence

with one keep-alive per Vulkan device rather than relying on `ctx->sync_staging`.

This would be similar in spirit to the existing Metal residency/keep-alive handling, while avoiding a server-level heartbeat or modifying the general synchronize path.

I haven't implemented this because I don't want to assume this is the desired direction.

Would maintainers prefer:
1. waiting for the relevant Windows/Intel driver-side fix,
2. a backend-local Vulkan workaround,
3. or specifically a device-level keep-alive along these lines?

If useful, I can prototype the Vulkan-only device-level approach separately.

### rusifele · 2026-09-27

### Similar behavior on AMD Strix Halo (APU) + Windows 11 + AMD Vulkan driver — eviction starts within ~1.5 s of idle, and appears to depend on commit headroom

Unlike the original report (an Intel dGPU used as a secondary, display-less GPU, evicted after ~70 s of idle), this is an AMD APU (integrated Radeon 8060S with a UMA carve-out) where eviction starts within ~1.5 s, and it shows a fairly clear dependence on the UMA carve-out size and page-file configuration. Sharing the data in case it helps.

#### Environment
- Machine: GMKtec EVO-X2 — Ryzen AI Max+ 395, Radeon 8060S (gfx1151), 128 GiB unified memory (SMBIOS type LPDDR5, configured 8000 MT/s)
- OS: Windows 11 Pro 25H2, OS build 26200.9550
- Driver: AMD Software (Adrenalin) 26.8.1, driver 32.0.31041.1004, Vulkan driver 2.0.395
- llama.cpp: b10909 (a2878d30d), official Windows Vulkan x64 release
- Model: Qwen3.6-35B-A3B UD-Q5_K_S (unsloth MTP GGUF) + mmproj-BF16
- Server args: `-n 8192 --mmproj mmproj-BF16.gguf -c 262144 --parallel 4 --slot-prompt-similarity 0.9 --spec-type draft-mtp --kv-unified -ngl 999 --load-mode none -fa on --jinja -fit off --reasoning-budget 2048 -b 2048 -ub 1024 -dev Vulkan0 --cache-type-k q8_0 --cache-type-v q8_0` (some runs added `-lv 4`)
- Device-local allocations reported by the log (`-lv 4`): weights 23,829 MiB, KV 2,720 MiB, recurrent state 1,005 MiB, MTP KV 512 MiB, compute buffers 675 + 596 + 248 MiB — about 29.6k MiB in total; mmproj (CLIP) also on Vulkan0 (~0.84 GiB file, buffer size not logged). Peak dedicated usage of `llama-server` measured by the GPU Process Memory counter: 30.3 GiB.

All memory values below are from Windows performance counters and are in GiB.

#### Observation 1 — eviction appears to depend on commit headroom, not on VRAM budget
Dedicated GPU memory of `llama-server` was sampled with the `GPU Process Memory` counter (effective interval ~1.4 s).

| UMA carve-out | Page file | OS-visible RAM / commit limit | Idle behavior |
|---|---|---|---|
| 64 GB | system-managed | 63.65 / 72.65 | Evicted: 30.3 → ~0.1, starting within one sample (~1.4 s) after the model became fully resident, complete in ~7 s. Reload on next request ~7 s. Right after model load it was not resident at all (0.04). |
| 96 GB | system-managed | 31.65 / 36.65 | **Stayed resident** while idle: 30.11 for 60 s after load, 30.18 for 60 s after a request. With a `/completion` ping every 2 s, pings 2–43 (~1.5 min) stayed at 37–52 ms (the first one took 0.6 s), then eviction/reload cycles began. At the end of that test commit was 41.5 / 43.8 and the page file had grown to 12.4 GB (the exact timing of the page-file growth vs. the eviction onset was not recorded). |
| 96 GB | fixed 48 GB | 31.65 / 79.65 | Evicted again while idle: avg 0.33 over 60 s after load, avg 1.79 over 60 s after a request; all 20 pings (every 2 s) took > 1 s, median 21.7 s. Available memory ~0.1 while idle. Same result with the default `--cache-ram` and with `--cache-ram 1024`. |

At UMA 64 GB, `vulkaninfo` reports a device-local heap of 74.43 GiB with a budget of 70.71 GiB, so ~30 GiB is well within budget. Our working hypothesis is that WDDM / the driver demotes idle device-local allocations to system memory whenever there is enough commit headroom to do so. This is inferred from the measurements above, not confirmed from driver documentation.

Related: at UMA 64 GB, `llama-server` private bytes were ~33.7 GiB while its working set stayed below ~3 GiB, i.e. roughly the size of the device-local allocations; commit dropped by ~34 GiB when the server was stopped (UMA 96 GB). It looks like the driver charges commit for device-local allocations as well (again an inference).

#### Observation 2 — impact on latency
- `llama-bench` itself is unaffected: pp4096 1,358 t/s at UMA 96 GB and 1,355 t/s at UMA 64 GB (ub 1024), tg128 59.0–59.1 t/s. pp4096 repeated 40 times at UMA 64 GB stayed at 1,339–1,368 t/s.
- 4 concurrent requests × ~6k tokens, time to first token (median / max):
  - UMA 96 GB, system-managed page file: 22.0 s / 27.5 s, second run 22.7 s / 28.3 s (residency was not sampled in these runs)
  - UMA 64 GB: 35.2 s / 46.2 s on the first run, then 50.2 s / 61.1 s on the following two runs (20 s gaps between runs; dedicated memory dropped to ~0.1 in the gaps)
- A 62.8 MiB context checkpoint (recurrent state) takes ~2,050 ms at UMA 64 GB vs ~490 ms at UMA 96 GB. For comparison, #28118 mentions ~600 ms per round on Linux/RADV on the same APU (gfx1151), with a different model.

#### Observation 3 — keep-alive does not reliably help here
- A lightweight `/completion` ping (`n_predict: 1`, `cache_prompt: false`, fixed `id_slot`; 36–51 ms client wall time when resident) sent every 1, 2 or 5 s did **not** prevent eviction at UMA 64 GB. Eviction started again right after each reload completed, so every ping ended up waiting ~9–13 s for a reload. This made things worse.
- A heavier chat-completion ping every 2.5 s (~2.1 s each, dominated by checkpoint creation) did keep the model resident, but only because the GPU was busy most of the time (~2.1 s out of every 2.5 s), which in turn slowed down real requests (a single request's generation dropped to 9.4 t/s; measured with memory compression disabled).

So an idle-time keep-alive like the one proposed in #25214 may not be sufficient on this platform if the eviction window is this short.

#### Things that had no effect (UMA 64 GB)
- `GGML_VK_ENABLE_MEMORY_PRIORITY=1` (driver reports `VK_EXT_memory_priority` / `memoryPriority = true`; whether b10909 actually enabled it was not visible in the default log)
- `--no-kv-unified`
- `--no-cache-idle-slots`
- Disabling Windows memory compression (`Disable-MMAgent -MemoryCompression`)

For reference, the driver also reports `VK_EXT_pageable_device_local_memory` (`pageableDeviceLocalMemory = true`), which b10909 does not enable. I haven't tested whether enabling it together with explicit priorities would change anything.

#### Not yet tested
- Toggling Hardware-accelerated GPU scheduling (HAGS; currently enabled)
- The same measurements on Linux (RADV) on this machine. We previously ran this model there, but idle residency was not measured.

Happy to run additional tests or provide logs if useful.
