### Problem description & steps to reproduce

Running MTP speculative decoding on the OpenVINO backend fails in every configuration I tried. Plain decode (same build, same model, no -md) works fine.

```bash
GGML_OPENVINO_DEVICE=GPU llama-cli -m gemma-4-12b-it.gguf
-md gemma-4-12b-mtp-q8.gguf --spec-type draft-mtp
-ngl 99 -ngld 99 -fa on -c 4096 -n 128 --temp 0 -p "test prompt"
```

What I tried:

1. Target and draft both on OpenVINO (command above): crashes during graph compute with a MatMul shape error, then dumps core. See first log block. Looks like the draft graph's raw hidden-state input (3840-dim, fed from the target) doesn't get a dynamic token dimension, so the post-concat MatMul shape-infers wrong.
2. Draft on CPU (-ngld 0): runs and produces correct-looking output, but logs ~505 graph-compute failures over a 128-token generation and decodes at 6.1 t/s — slower than plain decode (8.1 t/s), so speculation makes things worse.
3. Target on OPENVINO0, draft on Vulkan0 (build with both backends): aborts at ggml-backend.cpp:898 (second log block). The Gemma-4 MTP head reads the target's KV cache, which is pre-allocated in the OpenVINO buffer and can't be used from Vulkan.
4. Same as 3 with GGML_OPENVINO_STATEFUL_EXECUTION=1: throws ov::Exception from graph_rewrite.cpp:298 during compile.

This matters: on this iGPU the OpenVINO backend prefills ~6.5x faster than Vulkan (917 vs 142 t/s, pp512, Gemma-4-12B Q4_0), but Vulkan+MTP decodes ~3x faster than OpenVINO (23.5 vs 8.1 t/s). Spec-decode support is the only thing preventing the OpenVINO backend from being strictly better on Intel iGPUs.

Possibly useful data point: OpenVINO GenAI's native Gemma-4 MTP implementation works on this same GPU (measured 18.9 -> 54 t/s on Gemma-4-E2B via the optimum-intel MTP export), so the runtime handles this workload fine: the gap is in the ggml->OV translation layer.
