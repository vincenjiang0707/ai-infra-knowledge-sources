# [Issue #27505] server: deadlock under sustained chat workload on Gemma 4 26B-A4B + Vulkan (regression between v194 and v0.2.0-dev)

state: open | updated: 2026-09-22T01:11:14Z

## 正文

**last known good:** v194 (69bf643) — 24h+ soak clean
**first known bad:** 0.2.0-dev build 433 (bb4caa754)

## Symptom

llama-server deadlocks after serving several hundred sequential chat requests. The log stops mid-request at a `slot get_availabl` line; no further activity for minutes until the client times out and the server logs `srv stop: cancel task`. After that the server is fully wedged: `/health` does not respond, new requests are not even logged, but the process stays alive. No errors or warnings in the log around the stall, no GPU driver faults in dmesg, GTT memory usage normal (21.9/48 GiB). Decode throughput degrades noticeably before the stall (~74 -> ~62 t/s on the last tasks).

## Repro

- Model: `unsloth/gemma-4-26B-A4B-it-GGUF` QAT UD-Q4_K_XL (~13.3 GiB)
- Hardware: AMD Strix Halo APU (Ryzen AI MAX+ 395, Radeon 8060S iGPU, gfx1151, unified memory), Mesa RADV 26.0.3, kernel 7.0
- Launch flags: `-ngl 99 --load-mode mlock --ctx-size 262144 --kv-unified --cache-type-k f16 --cache-type-v f16 --flash-attn on --jinja --reasoning on --reasoning-format auto -b 2048 -ub 512 -t 16 -tb 16 -np 4` (env `GGML_VK_DISABLE_MMVQ=1`)
- Workload: sequential OpenAI-compatible chat completions with tool definitions, shared long system prompt (heavy prefix reuse across slots), temp 1.0, several hundred requests. Stall reproduced twice: after ~1300 and after ~650 tasks.

The same workload on the same machine/driver with v194 (69bf643) runs indefinitely without issue. A bisect over the ~600 commits between 69bf643 and bb4caa754 was not performed.
