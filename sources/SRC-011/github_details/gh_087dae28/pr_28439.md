## 正文

## Overview

The current flash-attention kernel processes 8 query rows for each K/V tile it loads. The main idea in this PR is to reuse that same K/V data for 16 query rows instead, so each K/V load does twice as much query work.

`kernel_flash_attn_ext` already takes the number of queries per threadgroup `Q` as a template parameter, but the QK^T and P*V simdgroup-matrix blocks only process the first 8 query rows, and only `Q = 8` is instantiated. This PR makes those blocks iterate over all `Q/8` query blocks and adds `Q = 16` with `nsg = 4` and `nsg = 8`.

Whether the 16-row tile is faster depends on the device and shape, so it is selected through the tuning table, like `fa_vec_pick`. Only `GGML_METAL_DEVICE_M5` has rows in this PR, and M5 is not a family representative, so other devices keep the existing dispatch.

The first version of this PR used a shape-only gate and always ran the 16-row tile with `nsg = 8`. That regressed on M4 Max (see @forforever73's table below), so the gate was replaced by the tuning table as suggested.

---

### Dispatch

`ggml_metal_tuning::fa_pick` maps `(device, DK, DV, ne11 bucket)` to `(Q, NSG)`. It first looks for an exact `ne11` bucket, then a `FA_NE11_DEFAULT` row, first for the device and then for its family representative.

If nothing matches, the existing dispatch is used. M5 is not the representative of any family, so its 25 rows are not used by another device.

The 8-row tile is always used when:

* `ne01 < 64`
* `ne01 < 256` and the last wide tile would hold only 1..8 rows. It would pad 8 more rows than the 8-row tile, which costs 2–4% at KV 4096 on M5 (`ne01 = 68`: 0.96x).
* K/V are not F16 and are not dequantized to F16 up front through `use_kv_f16`. BF16/F32 K/V and the in-kernel dequantization branches are unchanged.
* `GGML_PAD(DV, 64) % (16*NSG) != 0`
* The threadgroup memory would exceed the device limit (320/256 and 576/512 at 32 KiB).

The wide tile is only instantiated for the F16 kernels, which keeps library load time close to master. A cold compile of the `fa` library with an empty shader cache goes from 13.6 s to 14.2 s on M5. The `blk` buffer stays sized for the 8-row tile, which is an upper bound for the 16-row one.

### Tuning

`ggml-metal-tuning fa` generates the table rows. The sweep took about 20 minutes on M5.

The tuner compares the 8-row tile against `Q = 16` with `nsg = 4` and `nsg = 8`, using F16 K/V and GQA 8. GQA 8 had the smallest gains in the measurements below. The sweep covers 13 head sizes, 8 KV lengths from 512 to 65536, and up to 4 batch sizes, including a partial last tile.

A bucket gets a row only if the candidate is no slower than the 8-row tile at every sampled point and at least 2% faster overall. `nsg = 8` is selected over `nsg = 4` only when it is at least 3% faster. On M5, hs 96, 192, and 256 lose at some point with KV < 4096 and get no row there.

`nsg` is part of the table because no single value works for every head size. `Q = 8` with `nsg = 8` is slower than master's `Q = 8, nsg = 4` in every case measured on M5 (0.77–0.99x).

For `Q = 16`, geometric mean speedup vs master over the tuner's 30 sample points per head size is:

| Head | `Q = 16, nsg = 4` | `Q = 16, nsg = 8` |
| --- | --- | --- |
| 64/64 | 1.166 (0) | 1.007 (2) |
| 128/128 | 1.166 (0) | 1.147 (0) |
| 256/256 | 1.035 (13) | 1.099 (3) |

> *The number in parentheses denotes the count of sampled points slower than master.*

With `nsg = 4`, hs 256 loses at almost every point with KV $\le$ 4096 (0.89–1.00x). With `nsg = 8`, hs 64 gains almost nothing. The three hs 256 points where `nsg = 8` loses are at KV < 4096, where hs 256 gets no row. Master's `nsg = ne00 >= 512 ? 8 : 4` still applies to the 8-row tile.

Whether `Q = 16` helps on M4 Max requires running the tuner on that hardware. A device only uses the wide tile once it has rows in `fa_tuned_table`, and a run that emits nothing indicates it should stay on the 8-row tile. Rows for other devices can be added once profiled.

### Adding a Device

To generate rows for another Metal device:

1. **Build the tuner and test targets:**
```sh
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j --target ggml-metal-tuning test-backend-ops llama-bench

```


2. **Run the tuner:**
```sh
./build/bin/ggml-metal-tuning fa > fa_rows.txt 2> fa_sweep.log

```


* Takes ~20 minutes on M5.
* `fa_rows.txt` contains rows ready to add to `fa_tuned_table`. An empty file indicates the wide tile did not outperform the baseline.
* `fa_sweep.log` contains detailed per-point measurements.


3. **Verify correctness and benchmark:**
```sh
# Correctness check
./build/bin/test-backend-ops test -b MTL0 -o FLASH_ATTN_EXT

# Microbenchmarks
./build/bin/test-backend-ops perf -b MTL0 -o FLASH_ATTN_EXT -p 'nb=4096,'

# End-to-end performance
./build/bin/llama-bench -m <model> -fa 1 -ub 2048 -p 2048 \
  -d 0,2048,4096,8192,16384,32768 -r 1 -n 32 -t 1

```



> **Note:** The tuner prints the device token near the start of `fa_sweep.log`. If the device reports `GGML_METAL_DEVICE_GENERIC`, it must be explicitly defined in `ggml_metal_device_id` first to prevent generic rows from matching unspecified hardware.

**Hardware:** Apple M5 (10-core GPU, 24 GB)

### forforever73 · 2026-09-10

Ran test-backend-ops perf -b MTL0 -o FLASH_ATTN_EXT on an M4 Max (the built-in f16 sweep, nb=4096). The wide tile isn't a uniform win here — it regresses over a good part of the shape space (speedup %, positive = this PR faster):

| hs / GQA   | kv=4096 | 8192  | 16384 | 32768 | 65536 |
|------------|--------:|------:|------:|------:|------:|
| hs128 / g1 |    -8.7 |  -6.0 |  +6.0 | +25.1 | +34.8 |
| hs128 / g4 |    -8.8 |  -8.0 |  -7.5 |  +3.5 | +19.7 |
| hs128 / g8 |    -9.2 |  -8.4 |  -8.2 |  -4.1 |  +2.7 |
| hs256 / g1 |   -15.5 |  -7.6 | +15.4 | +29.4 | +37.6 |
| hs256 / g4 |   -16.8 | -17.0 | -11.3 | +19.6 | +27.4 |
| hs256 / g8 |   -17.8 | -17.0 | -16.5 |  -6.7 |  +8.6 |

It only pays off in the memory-bound corner (long KV + low GQA), and the break-even KV moves right as the GQA ratio grows (~16K at g1, ~32K at g4, ~64K at g8). So a typical GQA-8 model (e.g. Qwen3-30B-A3B) sees an regression. 

This is the same idea as #23114  (widen Q to amortize K/V loads), which turned out to be device-dependent. I don't think a shape-only gate has a global optimum across GPU families. Since we already have fa_vec_pick for exactly this, I'd prefer routing the non-vec nqptg selection through the tuning table instead of a hardcoded gate.

(Deleted my comment from earlier today, it described the branch before the last push. I replaced it now, and sorry for the edit comment spam from earlier.)

@forforever73 Found it and fixed it!
The small-launch regression is an occupancy problem: under ~64 wide tiles the GPU is not full and Q16 loses. The old tuner always ran 32 heads, so it never hit that case, which is now fixed and it now removes every regression the probe found and we keep the long-context gains, hopefully the same would apply to the M4 max (fingers crossed).

The tuner now works like this:

```
1. Need at least 2% total gain on launches of 1024+ tiles.
2. Sample 8-head launches from 32 to 1024 tiles.
3. A result within +-1.5% of baseline is measured two more times, median of three.
4. tiles_min = the smallest small full-tile launch that gains at least 1.5%, and every larger one does too.
5. A large or partial-tile launch drops the row only if it loses more than 1.5%. Otherwise it just counts in the total.
```

The dispatch counts a launch as `ceil(ne01/16) x ne02 x ne03` and keeps the 8-row tile below the row's `tiles_min`. The other checks are unchanged.

I also checked if one threshold works for other layouts, since the tuner only samples GQA 8. At the same tile count, MHA, GQA 4, 32-head MQA and two-stream launches all win where the GQA 8 shape wins, and GQA 8 gains the least of them. So one tiles_min per row is the safe choice.

`tiles_min` works as intended here: the sweep now emits 8 rows instead of 0, and the break-even is clearly row- and device-dependent (roughly 512–2048 tiles on M4 Max against 16–128 on M5). The rows are all at `dk/dv` of 32/32, 40/40 and 96/64 though, with hs 64, 128 and 256 all getting nothing.

The main issue I found is the `ne01=264` sample. It is the only partial-tile point in `{64, 264, 512, 2048}`, and for the wide tile it introduces ~3% extra padded work (`16*ceil(264/16) = 272` rows against `8*ceil(264/8) = 264`), unrelated to occupancy. Because `264 % 16 != 0` it also isn't `small`, so it takes the `else if (loss)` branch instead of raising `tiles_bad`. On M4 Max the wide tile only gains about 1.02–1.07x at that launch size — the adjacent full-tile samples at 512 and 1024 tiles are 1.018 and 1.068 for `dk=dv=64` — so 3% of padding is enough to turn it into a loss. `dk=dv=64` measures 0.963x at 544 tiles while winning at every sampled point ≥1024 tiles (1.033–1.093x), and that single point drops the row.

The veto isn't wrong, to be fair: without that point the threshold would come out at 512, and 544 > 512, so a row at 512 really would pick the wide tile for a 264-token ubatch and lose ~4%. It's that the same measurement already says the row should start at 1024, and the rule discards the row instead of recording that.

If partial-tile losses raise `tiles_min` instead of dropping the candidate, it produces 33/78(tuner collapse those as 13 table rows rather than 33,); all 25 additional rows get `tiles_min=1024` — which is `upper_bound(544)`, so the losing launch stays on the baseline — at 1.02–1.13x, and none of their sampled points at ≥1024 tiles loses by more than 1.5%.

So I think partial tiles should constrain the threshold rather than veto the row. I would also make the padding guard analytic instead of relying on `FA_NE01_MIN_PARTIAL=256`: when `ne01 % 16 ∈ [1,8]` the overhead is exactly `1/ceil(ne01/8)`, so tying the cutoff to `TUNE_THETA` puts it at `ne01 ≈ 400` with no magic number.

One correction to the GQA assumption: on M4 Max, GQA 8 is not the conservative case.

With the launch size fixed at 1024 tiles, speedup generally increases with the number of K/V heads, and it can flip a GQA-8 win into a loss. I think I can see why your M5 run reads the other way: in `m5_fa_sweep_v11.log`, at the same point, the 4-KV-head and 1-KV-head numbers are 1.353x and 1.360x — indistinguishable. At a 35% gain this axis is invisible; at 2–7% it decides. Since the tuning table has no GQA dimension, the cheaper fix looks like a runtime guard that avoids applying a row above the GQA ratio it was calibrated for.

Finally, TUNE_EPS=0.015 currently acts as both the retry band and the loss threshold. Near the cutoff, that means a 1.4% loss gets median-filtered while a 1.7% loss may be measured once and veto the row.

I hit this with two --dk 32 runs on the same binary ~20 minutes apart: two buckets moved from 0.987→0.983 and 0.988→0.983, crossing the 0.98522 cutoff and flipping both rows from emitted to dropped.

I'd consider widening only the retry band while keeping the actual loss threshold unchanged.
