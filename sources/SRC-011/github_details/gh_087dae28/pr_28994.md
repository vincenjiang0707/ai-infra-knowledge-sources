### gat45 · 2026-09-18

Following up with real-device data (OnePlus 15 / SM8850, HTP v81, HMX active, self-build 18ea685b):

**Measured cost of the K-quant repack path (Marco-Nano MoE, wikitext 584x512, llama-perplexity):**

| Model | PPL | tg16 (llama-bench) |
|---|---|---|
| Q4_0 direct | 6892.6 +/- 66.6 | 29.97-33.5 t/s |
| Q4_K_M (requant Q8_0, repacked to Q4_0 on DSP) | 8741.2 +/- 92.3 (**+26.8%**) | 31.6 t/s |

So the repack erases the K-quant benefit on the DSP side, as expected from the storage type - the real value of #28994 is **loading community GGUFs without conversion**.

**Feature request flowing from this:** extend the same mechanism to **Q3_K** (and optionally Q2_K) in `ggml_hexagon_is_repack_type` / `ggml_hexagon_weight_dsp_type` / `repack_q4k_as_q4_0_tiled` (fastrpc.cpp, l.1194/1205/2327 @ b11644). Many community MoE GGUFs (Gemma 26B-class, experts = 92% of weights) are Q3_K_M, and today they fall back to CPU - which is not viable on 16 GB phones: our Q3_K-experts GGUF (12.0 GiB, `-ot ffn_*_exps=CPU`) hard-reboots the device 2/2 during load (RAM stress).

Happy to benchmark a patch same-day on SM8850 (bench + PPL harness with md5-ed logs).

### gat45 · 2026-09-18

**Addendum (Sep 18) — new device data strengthening the request above** (OnePlus 15 / 16 GB, HTP, self-build ≥ b11644):

- **CPU fallback for big-MoE experts is not just slow — it is fatal at realistic sizes.** Two different mixed recipes (Q3_K experts → 12.0 GiB file / ~10.7 GiB CPU payload; Q2_K+Q4_0 experts → 11.9 GiB file / ~9.0 GiB CPU payload) both **hard-reboot the phone during model load**, 2/2 attempts each. MemAvailable telemetry: 11.6 GB → **29 MB in 8 s** at load, then watchdog reboot. The working point is ≈ ≤11.3 GB of committed weights+driver; anything above reboots.
- Meanwhile the all-HTP Q4_0/Q8_0 working point (5 GiB file) runs 30–33 t/s with multi-GB headroom.
- For context, the measured double-quant cost: Q4_K_M requantized from Q8_0 → PPL 8741 vs 6893 for direct Q4_0 (+26.8%, wikitext/512). A Q3_K GGUF quantized from source and repacked once to Q4_0 would avoid chained requant steps entirely.

So a Q3_K/Q2_K → Q4_0 repack (same dequantize_row_q3_K → quantize_row_q4_0_ref mechanism, plus the two type-map entries) would let the large ecosystem of community Q3_K/Q2_K MoE GGUFs run fully on HTP. Today those models either need a PC-side requant or hit the fatal CPU-fallback path.
