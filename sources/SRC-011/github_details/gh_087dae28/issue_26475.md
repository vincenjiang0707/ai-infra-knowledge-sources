### zack969969 · 2026-08-03

Following up on #26475 — I hit the same crash class (`GGML_ASSERT(n_graph_inputs < GGML_SCHED_MAX_SPLIT_INPUTS)` in `ggml_backend_sched_split_graph`, via `resolve_fused_ops` -> `graph_reserve` -> `sched_reserve`), but on an **8-GPU** tensor-split setup rather than 2. I tried the workaround from @FlareP1's comment (giving the draft's device a slice of the main model instead of isolating it) plus a few other combinations, and none of them avoided the crash — wanted to share the data points in case it helps narrow down the root cause (possibly related to the graph-node-count instability @ggerganov mentioned in #26369).

### Environment
- 8x Tesla V100-SXM2-32GB, no NVLink (PCIe only)
- CUDA 11.5 (nvcc), driver 580.173.02
- llama.cpp commit `221f0f6356efe2260023208365705ec5d5a7c8f5` (2026-08-02), build: `version: 363 (221f0f6)`, CUDA backend, `CMAKE_CUDA_ARCHITECTURES=70`
- Target model: DeepSeek-V4-Flash-0731, unsloth UD-Q8_K_XL GGUF (~162GB, 8-shard tensor-split)
- Draft model: DSpark support GGUF converted locally via `convert_hf_to_gguf.py --remote --dspark` from `deepseek-ai/DeepSeek-V4-Flash-DSpark` (verified byte-identical to `am17an/DeepseekV4-Flash-20260731-DSpark`, so not a conversion issue)

### What I tried (all crash identically)

1. Baseline: main model split across all 8 GPUs, draft with `--spec-draft-ngl 999` and no explicit `--spec-draft-device`
   ```
   -ngl 999 --tensor-split 1,1,1,1,1,1,1,1 --spec-draft-ngl 999
   ```
2. Draft pinned to a device that **already holds a full share of the main model** (mirroring the "shared device" workaround from #26475)
   ```
   -ngl 999 --tensor-split 1,1,1,1,1,1,1,1 --spec-draft-ngl 999 --spec-draft-device CUDA7
   ```
3. Main model restricted to CUDA1-7 (7-way split), draft isolated on CUDA0, smaller context
   ```
   -dev CUDA1,CUDA2,CUDA3,CUDA4,CUDA5,CUDA6,CUDA7 -ngl 999 --tensor-split 1,1,1,1,1,1,1 \
   --spec-draft-ngl 999 --spec-draft-device CUDA0 -c 65536
   ```
4. Baseline + `--fit off` (to rule out the auto-fit probing pass — this did remove the `common_fit_params`/`common_get_device_memory_data_impl` frames from the backtrace, confirming `--fit off` skips that pass, but the crash still occurs in the real (non-probing) context init)
   ```
   -ngl 999 --tensor-split 1,1,1,1,1,1,1,1 --spec-draft-ngl 999 --spec-draft-device CUDA0 \
   --fit off --batch-size 2048 --ubatch-size 512 --parallel 1
   ```
5. Small deliberate overlap, mirroring @FlareP1's exact "give the draft's device a small slice" pattern (`-ts 24,1` style) scaled to 8 devices
   ```
   -ngl 999 --tensor-split 1,8,8,8,8,8,8,8 --spec-draft-ngl 999 --spec-draft-device CUDA0 \
   --fit off --batch-size 2048 --ubatch-size 512 --parallel 1
   ```

All five produce the identical stack:
```
ggml/src/ggml-backend.cpp: GGML_ASSERT(n_graph_inputs < GGML_SCHED_MAX_SPLIT_INPUTS) failed
#3  ggml_backend_sched_split_graph ()
#4  llama_context::graph_reserve(...)
#5  llama_context::resolve_fused_ops(...)
#6  llama_context::sched_reserve()
#7  llama_context::llama_context(...)
```

### Takeaway
The device-overlap workaround that helped @FlareP1 on a 2-GPU setup doesn't scale to 8 GPUs — the crash reproduces regardless of overlap ratio or `--fit` state. This is consistent with @ggerganov's note in #26369 about the DSpark graph having a variable node count across batch sizes (397 @ bs=512 vs 417 @ bs=1) — more devices likely means more graph splits, making it easier to exceed `GGML_SCHED_MAX_SPLIT_INPUTS` even with the overlap trick. Happy to test patches or provide more logs if useful.

### yoller · 2026-08-11

I can reproduce what looks like the same original scheduler/backend issue with **Qwen3.6-27B + DFlash** on a dual-GPU CUDA setup.

### Environment

* llama.cpp commit: `f95de9776` (`master`)
* OS: CachyOS / Linux
* CUDA UMD: 13.3
* NVIDIA driver/KMD: 610.43.03
* GPUs: 2× RTX 3060 12 GB
* Target model: `Qwen3.6-27B-IQ4_NL_MTP.gguf`
* Draft model: `Qwen3.6-27B-DFlash-Q4_K_M.gguf`
* Speculative mode: `draft-dflash`

The target model works normally across both GPUs with MTP.

### Reproduction

Relevant parameters:

```text
--model Qwen3.6-27B-IQ4_NL_MTP.gguf
--model-draft Qwen3.6-27B-DFlash-Q4_K_M.gguf
--spec-type draft-dflash
--spec-draft-n-max 15
--device-draft CUDA0
--n-gpu-layers-draft all
--split-mode tensor
--tensor-split 950,1050
```

The DFlash model is recognized and reaches 100% loading, but context initialization aborts with:

```text
ggml/src/ggml-backend.cpp:898:
pre-allocated tensor (output.weight) in a buffer (CUDA1)
that cannot run the operation (NONE)
```

The stack follows the same path as the original report:

```text
ggml_backend_sched_backend_id_from_cur()
ggml_backend_sched_split_graph()
llama_context::graph_reserve()
llama_context::sched_reserve()
llama_context::llama_context()
common_speculative_init_result()
```

I also tried several configurations to rule out a straightforward VRAM or draft-placement issue.

### Additional tests

Forcing the entire draft model onto CUDA0:

```text
--device-draft CUDA0
--n-gpu-layers-draft all
--override-tensor-draft .*=CUDA0
```

changes the failing tensor, but the same scheduler/backend error remains:

```text
pre-allocated tensor (blk.0.attn_q.weight) in a buffer (CUDA0)
that cannot run the operation (NONE)
```

I also reproduced the same class of failure with `--split-mode layer` instead of `tensor`.

With deliberately less balanced layer splits I can trigger ordinary CUDA OOM errors (`cudaMalloc failed: out of memory`), which are clearly distinct from this failure. When VRAM is sufficient, initialization instead proceeds until the same `ggml_backend_sched_split_graph()` / `operation (NONE)` abort.

This appears to be the same original issue reported here, rather than the separate `GGML_SCHED_MAX_SPLIT_INPUTS` assert discussed in the comments.

Since this reproduces with **DFlash/Qwen3.6** rather than DSpARK/DeepSeek, it may indicate that the issue is not specific to DSpARK and can affect speculative draft models with a multi-GPU target more generally.
