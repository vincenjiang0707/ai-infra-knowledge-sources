### Feature Description

Description:
The llama.cpp OpenAI-compatible server currently supports endpoints like /v1/chat/completions, but does not support the newer OpenAI Responses API (/v1/responses).

Many OpenAI client SDKs and tools are moving toward the unified Responses API, which supports structured outputs, tool calls, and multimodal responses in a single endpoint. Lack of /v1/responses support makes it harder to use llama.cpp as a drop-in replacement for OpenAI backends without an additional proxy or translation layer.

Requested feature:
Add native support for the /v1/responses endpoint in llama-server, aligned as closely as possible with OpenAI’s Responses API request/response format.

Benefits:

Improved compatibility with modern OpenAI SDKs

Easier migration from OpenAI APIs to llama.cpp

Reduced need for custom proxy or request rewriting layers

Thanks for the great work on llama.cpp!

### Motivation

I want to use ClaudeCode with llama-server offline, but it currently don't support necessary endpoints.

### bdellaterra · 2026-06-09

In case it's helpful to anyone, here's a JSON transform I came up with. I've had some luck applying this to the partially supported `/responses` endpoint, as a temporary workaround until PR #[21174](https://github.com/ggml-org/llama.cpp/pull/21174) lands.

```typescript
type Json = { [key: string]: unknown };
type NestedJson = Json & { [key: string]: NestedJson };

export const patchOpenAIResponseJson = ({
  usage,
  usage: { output_tokens_details = {} } = {},
  ...json
}: NestedJson) => ({
  error: null,
  incomplete_details: null,
  instructions: null,
  metadata: null,
  temperature: null,
  top_p: null,
  parallel_tool_calls: false,
  tools: [],
  tool_choice: 'auto',
  usage: {
    ...usage,
    output_tokens_details: {
      reasoning_tokens: 0,
      ...output_tokens_details,
    },
  },
  ...json,
});
```

### colout · 2026-08-13

I also ran into a pretty bad issue. I'm using Terminal Bench's harbor for some custom evals using opencode as a harness. It works flawlessly on the deprecated completions endpoint, but I need to add some nasty args to the CLI to get that working:

uv run harbor run
  -p tasks/fix-calculator
  -a opencode
  -m "llamacpp/Qwen3.6-35B-A3B-GGUF:UD-Q8_K_XL"
  --ak 'opencode_config={"provider":{"llamacpp":{"npm":"@ai-sdk/openai-compatible","name":"llama.cpp","options":{"baseURL":".../v1","apiKey":"sk-1234"},"models":{"...":{}}}}}'

Ideally i can drop the whole `--ak` argument once responses follow the spec.

For anyone wanting to reproduce: opencode v1.18.18 against llama-server b10298 with a Qwen thinking model. Pointing opencode's `openai` provider at `/v1/responses` errors with `"text part msg_... not found"` in the TUI, and in headless mode it fails silently — tokens get consumed, finish reason is `stop`, but no text or tool calls ever come back. opencode talks through @ai-sdk/openai (3.0.84), which schema-validates every SSE event and quietly drops the ones that don't match.

Comparing llama-server's actual SSE stream against the spec: events are missing `output_index`, `content_index`, and `sequence_number`, the `response.created`/`in_progress` payloads lack `created_at` and `model`, and reasoning comes out as `response.reasoning_text.delta`, which the SDK doesn't recognize at all. I confirmed the cause with a small proxy between opencode and llama-server that only injects the three missing index fields — same versions, and everything works.

#24957 and #21174 both add these fields already.
