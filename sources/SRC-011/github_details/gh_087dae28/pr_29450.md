## Overview

The CPU and GPU in APUs share memory. When llama.cpp knows the device is an iGPU, it lets GPU read the model's inputs directly from the CPU instead of copying those inputs to the GPU's memory first. The problem with this is that the GPU's work is queued asynchronously, so when llama.cpp starts writing the next chunk's worth of inputs, it overwrites the previous inputs. This can happen while the GPU is in the process of reading those previous inputs, which produces very bad outputs, leading the PPL to be pretty high. 

We suspected AMD's backend to be the issue because the HIP_LAUNCH_BLOCKING=1 flag makes the CPU wait after each GPU launch, forcing the CPU to wait and thereby preventing the overwrite. The HIP runtime, amdgpu driver and firmware weren't at fault, and this issue wasn't just showing up in APUs. It showed up in a gfx1036(iGPU)+gfx1100(dGPU) setup too.

The fix I have is that, first, we turn the integrated flag back on for HIP. Second, when llama.cpp sets up, check whether any GPU can read the CPU input buffer directly. Only in that case, wait for the previous GPU step to finish before writing new inputs. This concept already exists in llama.cpp as it is used in multi-GPU pipelines. This will also significantly speed up things compared to just setting the blocking flag.
