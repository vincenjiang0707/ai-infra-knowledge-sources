### Problem description & steps to reproduce


Hit this while running DeepSeek V4 Flash 0731 through `llama-server`.

A large tool result containing one long run of ASCII letters crashes the server during tokenization, before inference gets a turn.

### Steps to reproduce

1. Check out llama.cpp commit `a1f96d4fc2c9e4101a6666a9d87f547e7e880df6`.

2. Build with CUDA and start the server:

```console
llama-server \
  -m DeepSeek-V4-Flash-0731-UD-IQ1_S-00001-of-00003.gguf \
  -c 16384 \
  -b 2048 \
  -ub 512 \
  -np 1 \
  --swa-full \
  -fa on \
  -ctk f16 \
  -ctv f16 \
  -ngl 999 \
  --host 127.0.0.1 \
  --port 18082 \
  --jinja \
  --reasoning-format deepseek \
  --reasoning on \
  --reasoning-budget -1
```

3. Run an OpenAI-compatible tool-use conversation against `/v1/chat/completions`.

4. Have one tool produce a long letter run:

```console
python3 -c "print('Z' * 131072)"
```

5. Send the tool result back to the model. In the tested run, Pi 0.84.0 clipped it to 51,294 bytes.

Server falls over with `SIGSEGV` while tokenizing that request.

### What should happen

If the request is too large, return a normal context limit error and keep the server alive.

### What actually happens

libstdc++ piles up roughly 76,000 recursive `std::regex` frames and exhausts the worker thread stack. Backtrace ends up here:

```text
std::__detail::__regex_algo_impl
unicode_regex_split
llm_tokenizer_bpe_session::tokenize
llama_vocab::tokenize
common_tokenize
tokenize_input_prompts
server_routes::handle_completions_impl
```

GGUF has `tokenizer.ggml.pre` set to `joyai-llm`. That is just the pre-tokenizer compatibility tag. Its regex is also used by DeepSeek V3 and Hunyuan Dense.

No custom splitter handles this exact regex, so `unicode_regex_split()` punts it to `std::regex`. Long letter runs then chew through the thread stack.

A non-recursive splitter fixes the crash. Replaying the original request returns the expected `27940 tokens exceeds 16384 tokens` error, and `/health` stays `ok`.
