### Problem description & steps to reproduce

This is prob an obvious and apparent issue, but you can try reproduce it with [repro_llamacpp_unbounded_logprobs.py](https://gist.github.com/Yunzez/d8402faa6c6814ab14ec6b6d4d7c0f9d#file-repro_llamacpp_unbounded_logprobs-py)

The number of per-token probabilities returned for `logprobs` / `top_logprobs` (internally `n_probs`) is bounded **only by the vocabulary size**, not by any small cap. A single `/v1/completions` request can therefore be amplified into an enormous response and a correspondingly large amount of CPU (a full-vocabulary sort + JSON serialization per generated token) and memory.

Measured on the CPU build, `Qwen2.5-0.5B` (vocab 151,936), `max_tokens: 8`:

| `logprobs` | response size | wall time | `top_logprobs` per token |
|---|---|---|---|
| 5 | 4.7 KB | 0.12 s | 5 |
| 1,000 | 728 KB | 0.31 s | 1,000 |
| 100,000 | **75 MB** | **5.6 s** | 100,000 |
| 200,000 | **115 MB** | **8.1 s** | 151,936 (clamped to vocab) |

So `logprobs: 200000` on an 8-token completion returns a **115 MB** JSON in **8 s**. The amount scales linearly with `max_tokens` as well: `max_tokens: 512, logprobs: 200000` would produce a response on the order of **7 GB** and minutes of CPU, from one request whose own body is a few hundred bytes. There is no authentication requirement and the OpenAI-compatible route accepts it.

For comparison, the OpenAI API caps `top_logprobs` at 20, and vLLM caps it (`max_logprobs`, default 20), refusing larger values with a 400.
