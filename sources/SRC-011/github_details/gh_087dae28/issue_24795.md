### Problem description & steps to reproduce

 Loading a gemma4-assistant MTP draft model for speculative decoding (--spec-type draft-mtp) crashes
  during model load with "invalid vector subscript". The main/target model loads fine — only the draft
  load crashes, so generation never starts.

  This is a REGRESSION. The exact same models + command load cleanly and work on b9553 (~2.5x speedup,
  lossless), but crash on b9702 and b9717. Something in the gemma4-assistant loader / context-init path
  regressed between b9553 and b9702.

  Command used (crashes on b9702/b9717, works on b9553 with the older flag names):

  b9702/b9717 (new flag names):
    llama-server -m gemma4-v2-Q8_0.gguf \
      --spec-type draft-mtp --spec-draft-model gemma-4-12B-it-MTP-Q8_0.gguf \
      --spec-draft-ngl 99 --ctx-size 65536 -ngl 99 --flash-attn on --jinja

  b9553 (old flag names, WORKS):
    llama-server -m gemma4-v2-Q8_0.gguf \
      --model-draft gemma-4-12B-it-MTP-Q8_0.gguf --spec-type draft-mtp \
      --spec-draft-n-max 4 -ngl 99 -ngld 99 -fa on --jinja

  Key detail: the "invalid vector subscript" fires the instant `load_tensors: loading model tensors...`
  begins for the draft — before any tensor data is read. So the out-of-bounds is in the gemma4-assistant
  tensor-layout / model-build code, not in reading tensor data. Likely an out-of-range index over a
  per-layer array (block_count=4), e.g. attention.head_count_kv=[8,8,8,1] or
  sliding_window_pattern=[true,true,true,false], or nextn_predict_layers / embedding_length_out=3840 handling.

  The crash occurs AFTER the memory-fitting step (which harmlessly aborts with "n_gpu_layers already set
  by user to 99, abort"), at the actual draft load — so -fit off does not change it. The
  "Gemma4Assistant requires ctx_other to be set (this warning is normal during memory fitting)" line also
  appears on the working b9553 build and is harmless; the fatal regression is the "invalid vector subscript".

  Tried — all crash identically on b9702/b9717, both quants:
    b9702 + Q8_0 -> crash
    b9717 + Q8_0 -> crash
    b9717 + BF16 -> crash
    b9553 + Q8_0 -> WORKS

  So it is neither a file/quant issue nor a user-config issue. It is in the model loader and reproduces
  with any binary that loads this draft.

`free` is 0, but `total` is reported. `splits[0]` is set to 0:

I guess it's due to lack of MTP memory fitting implementation: `Gemma4Assistant requires ctx_other to be set (this warning is normal during memory fitting`. MTP gets moved without any fit check to GPU if main model was fully offloaded. 

Since MTP is fairly small (1 GB at 131K?), that works okay. But if you have just enough memory for the model, but not MTP -- you get this bug.

On Windows WDDM free-memory shenanigans don't help and this issue easier to stumble into:
```
# no matter the actual VRAM usage, llama.cpp sees the same amount of free VRAM at startup:
llama_prepare_model_devices: using device CUDA0 (NVIDIA GeForce RTX 3090) (0000:01:00.0) - 23300 MiB free

# on the second free memory query / log (after the main model is loaded, right before loading MTP .gguf):
llama_prepare_model_devices: using device CUDA0 (NVIDIA GeForce RTX 3090) (0000:01:00.0) - 1412 MiB free
# 1412 MB is more than enough for MTP, so it'll succeed

# but if there's VRAM used by other processes, you could randomly get this
# (despite the same 23300 MB always being reported as free at startup):
llama_prepare_model_devices: using device CUDA0 (NVIDIA GeForce RTX 3090) (0000:01:00.0) - 0 MiB free
```
So it seems that even if MTP memory fitting was fixed, the issue would remain (on Windows), as WDDM lies about free memory at process startup and then dynamically walks back on available free memory.
So, to trigger this on Windows, you could have nowhere near enough free GPU memory for the model itself. First allocation for the model itself would succeed. But whent it's time to load MTP, WDDM would report 0 free.

I guess it's not worth fixing. But adding clear error about 0 VRAM would be great. Right now it's only an info log, which you wouldn't see without `-lv 4`.

### jebbadee · 2026-08-24

Root cause found, with an experimentally verified workaround.

**TL;DR:** the crash is a NaN in the default tensor-split computation in `llama_model_base::load_tensors` (`src/llama-model.cpp`), not in any MTP/arch loader. Workaround today: pass an explicit `--tensor-split` (e.g. `--tensor-split 1` on a single GPU) — loads clean on b10581/b10603.

**Mechanism.** With no user tensor_split, `load_tensors` sizes the split points by free device memory:

```cpp
splits[i] = free;                       // per device
...
split_sum += splits[i]; splits[i] = split_sum;
splits[i] /= split_sum;                 // 0/0 = NaN when every device reports free == 0
...
const int layer_gpu = std::upper_bound(splits.begin(), splits.begin() + n_devices(), ...) - splits.begin();
auto * dev = devices.at(layer_gpu).dev; // NaN comparisons -> past-the-end -> out_of_range
```

When `free == 0` but `total != 0`, the existing `free==0 && total==0` host-memory fallback does not apply, `split_sum` is 0, every split point becomes `0/0 = NaN`, `upper_bound` over NaNs returns past-the-end, and `devices.at(n_devices())` throws MSVC's `out_of_range("invalid vector subscript")`, which `llama_model_load` reports as "error loading model: invalid vector subscript".

**Why it looks like an MTP-draft bug:** the draft model is simply the model you load *second* — by then the target model + KV cache have filled VRAM, and on Windows/WDDM CUDA then reports 0 bytes free. The target loads first with plenty of free memory, so it never hits the path. Architecture is irrelevant (reproduced with qwen35 here; gemma4-assistant in the OP).

**Supporting experiments** (RTX 4090 Laptop 16 GB, Windows 11, official b10581 + b10603 CUDA 12.4 builds, Qwen3.8-27B target + a4lg MTP-ONLY-Q4_K_M draft):

| condition | result |
|---|---|
| `--ctx-size 512` (VRAM headroom left at draft load) | loads |
| `--ctx-size 8192` / `65536` | crashes |
| `--ctx-size 8192/65536` + `--fit off` | still crashes (matches OP) |
| `--ctx-size 8192/65536` + `--tensor-split 1` (skips the free-memory branch) | **loads** |
| same source, CPU-only build (no devices → branch never runs) | loads |

**Fix** (guard the zero sum; falls back to an even split):

```cpp
    if (split_sum <= 0.0f) {
        // all devices reported zero free memory (e.g. Windows/WDDM after another model
        // filled VRAM, common when loading a speculative draft model second).
        // normalizing would produce NaN split points and send the upper_bound search in
        // get_layer_buft_list past the end of `devices`.
        LLAMA_LOG_WARN("%s: all devices report zero free memory, falling back to an even tensor split\n", __func__);
        for (size_t i = 0; i < n_devices(); ++i) {
            splits[i] = float(i + 1) / n_devices();
        }
    } else {
        for (size_t i = 0; i < n_devices(); ++i) {
            splits[i] /= split_sum;
        }
    }
```

Compiles and passes a load test here. Happy to open a PR if useful.

The regression window fits: the split-by-free-memory default (with the `free==0 && total==0` host fallback from #18577) landed between b9553 and b9702, which is exactly when the OP's setup broke.
