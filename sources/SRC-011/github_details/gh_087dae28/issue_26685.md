### ggerganov · 2026-08-06

The memset that was introduced in the DSv4 cache in 13f2b28 is not synchronized with the computation of the context, so there is a data race that is likely causing this.

### matt23654 · 2026-08-07

@ggerganov I don't think it is 13f2b28 causing this, at least not directly. I asked Kimi to backport the RPC fix from f5b9bd3 to a patch and bisected it to 0dc74e332edee2616e4d8d9ab3b68dfc340fc14a . 

I did also try a few simple fixes like ``GGML_VK_DISABLE_ASYNC=1`` and ``device.waitIdle()`` in Vulkan's memset function, in an attempt to prove your hypothesis. Neither of those attempts fixed the garbled output.

### matt23654 · 2026-08-07

Ok, I have figured it out with Kimi's help. The fused ops are all enabled on the CUDA Host and scheduled onto RPC Vulkan which currently does not have those ops. The Vulkan graph computation then skips them without erroring.

This also explains why this error is uncommon, running Vulkan/Vulkan across 2 Strix Halos or similar will not have this bug. This bug requires mismatched underlying GGML backends and RPC, with the host having more implemented ops.
