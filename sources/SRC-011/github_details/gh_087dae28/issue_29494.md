### Problem description & steps to reproduce

Repro script:[repro_llamacpp_sampler_penalty_oom.py](https://gist.github.com/Yunzez/17be5c4729c0654d54f7406e6b3bb74b#file-repro_llamacpp_sampler_penalty_oom-py)

The repetition-penalty sampler and the DRY sampler each pre-size a ring buffer to the **raw client-supplied count**, with no clamp to the context size or any other cap. The request schema hard-limits `repeat_last_n` and `dry_penalty_last_n` only to `0 .. INT32_MAX` (`tools/server/server-schema.cpp:126` and `:153`), and the value flows unclamped into sampler initialization. The buffer is **value-initialized (zero-filled)**, so every page is actually committed.

A single unauthenticated request therefore forces a huge allocation at slot launch (sampler init), **before any token is generated** (so `n_predict: 1` is enough): Claude results

| trigger (fields in the request body) | buffer(s) allocated | size at `INT32_MAX` |
|---|---|---|
| `repeat_penalty:1.1, repeat_last_n:2147483647` | `prev` ring buffer (`llama_token`, 4 B) | **~8.6 GB** |
| `dry_multiplier:1.0, dry_base:1.1, dry_penalty_last_n:2147483647` | `dry_repeat_count` (`int`) **+** `last_tokens` ring buffer | **~17 GB** |

On a default deployment (Linux memory overcommit on, no cap) the zero-fill commits the pages and the OOM-killer `SIGKILL`s the server: a single request kills a typical 2–16 GB container/VM, and a handful of concurrent requests exhausts any host. Under a memory cap (`ulimit -v` / cgroup) the allocation throws `std::bad_alloc`, which the server catches (`server-context.cpp:1782`) and turns into a `400`, so the server survives — but that is a fragile, deployment-dependent mitigation, not a bound.

Measured (CPU build, `ulimit -v 5000000` so the blow-up fails safely; `VmHWM` = peak resident):

```
baseline                                             VmHWM  598 MB
repeat_penalty=1.0, repeat_last_n=2e9  (DISABLED)     200,   Δ +0 MB     <- ablation: no alloc
repeat_penalty=1.1, repeat_last_n=1e8  (enabled)      200,   Δ +382 MB   <- committed ~= 1e8 * 4 B
repeat_penalty=1.1, repeat_last_n=2e9  (enabled)      400 "Failed to initialize samplers: std::bad_alloc"
dry_multiplier=0.0, dry_penalty_last_n=2e9 (DISABLED) 200,   Δ +0 MB     <- ablation: no alloc
dry_multiplier=1.0, dry_penalty_last_n=1e8 (enabled)  200,   Δ +384 MB   <- committed, proportional
dry_multiplier=1.0, dry_penalty_last_n=2e9 (enabled)  400 "Failed to initialize samplers: std::bad_alloc"
```

The physical commit grows linearly with the count (ablation: with the sampler disabled the same `2e9` count allocates nothing, proving the ring-buffer size is the cause). The fields are also accepted on the OpenAI-compatible `/v1/chat/completions` and `/v1/completions` routes (llama.cpp passes its sampler-specific fields through them).
