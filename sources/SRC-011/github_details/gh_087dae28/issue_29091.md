### Problem description & steps to reproduce

In llama.cpp version 0.4.1, calling the GET /v1/models endpoint returns "vocab_type": true inside the model's meta object. In earlier releases (e.g., 0.3.0), this field correctly serialized the integer value corresponding to the llama_vocab_type enum (2 for BPE).

Per tools/server/README.md and the internal vocabulary enum, vocab_type should be an integer:

0: LLAMA_VOCAB_TYPE_NONE
1: LLAMA_VOCAB_TYPE_SPM
2: LLAMA_VOCAB_TYPE_BPE
3: LLAMA_VOCAB_TYPE_WPM

Returning a boolean breaks API client verification systems that expect the documented integer enum type.

Steps to Reproduce

1. Start llama-server with any standard GGUF model

llama-server -m models/sakura-14b-qwen2.5-v1.0-iq4xs.gguf -ngl 999 -c 32768 -a sakura-14b-qwen2.5-v1.0-iq4xs --host 127.0.0.1 

2. Send a GET request to /v1/models:

GET http://127.0.0.1:8080/v1/models

3. Inspect the returned JSON payload under data[0].meta.vocab_type.

### ZitouniNidhal · 2026-09-19

### Cause Analysis
In `tools/server/server.cpp`, during the construction of the metadata JSON object for the `/v1/models` endpoint, `vocab_type` is implicitly evaluated as a boolean check `(bool) llama_vocab_type(...)` rather than being serialized as an integer enum value (`LLAMA_VOCAB_TYPE_NONE = 0`, `LLAMA_VOCAB_TYPE_SPM = 1`, `LLAMA_VOCAB_TYPE_BPE = 2`, `LLAMA_VOCAB_TYPE_WPM = 3`).

### Proposed Fix
Explicitly casting `llama_vocab_type(model)` to an integer or `int32_t` ensures the JSON builder serializes the numeric enum identifier as documented in `tools/server/README.md`:

```cpp
meta["vocab_type"] = static_cast<int>(llama_vocab_type(model));
