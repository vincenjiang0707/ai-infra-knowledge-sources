# [PR #29360] [Security]: prevent out-of-bounds accesses from malformed mmproj files

source: https://github.com/ggml-org/llama.cpp/pull/29360
state: open | updated: 2026-09-27T02:41:28Z
labels: mtmd

## 正文

The allocation used the declared slot sizes while the copy used the tensors from the graph. Use the graph tensors for both so the size cannot disagree.

## Security context

**`state_out` heap out-of-bounds write (gen-audio / pocket-tts path).** The graph of a gen-audio mmproj exposes `state_out_<slot>` tensors whose shapes are fully determined by the projector's weights and metadata. `list_gen_state_slots()` reports the *declared* slot sizes, and the `state_out` buffer was sized from those, while the copy loop pulls `ggml_nbytes(t)` bytes out of the *graph* tensors. Nothing makes the two agree: a crafted mmproj can declare small state slots while making the graph's state tensors larger, and each encode then writes past the end of `state_out` - a heap out-of-bounds write whose length and contents are chosen by the projector file, repeated on every generation flush. Depending on the layout this is silent corruption or a crash (heap-buffer-overflow under ASan).

The only attacker-controlled input is the mmproj passed to `--mmproj`; the text model and the CLI invocation are the victim's own.

With this change the graph tensors are resolved first and `state_out` is sized from `ggml_nbytes()` of exactly those tensors, then exactly that many bytes are copied per tensor, so the allocation and the copy cannot disagree by construction.

**`feature_layer` hardening.** Master already rejects indices above `n_layer` (#29276); this additionally rejects negative indices (conversions are expected to standardize on non-negative values) and includes the key name and the valid range in the error message.

## Testing

- crafted mmproj declaring small state slots with oversized graph state tensors: before, ASan reports a heap-buffer-overflow in the `state_out` copy path; after, the encode completes with `state_out` sized to the graph tensors
- well-formed gen-audio projectors: the graph tensors match the declared slots, so `state_out` layout is unchanged and generation is unaffected

## 1. `clip.vision.feature_layer` — heap out-of-bounds read

**Trigger:** an mmproj declaring `clip.vision.block_count = 2` together with `clip.vision.feature_layer = [4096]`.

The two keys are read as plain data and then take on uncoordinated roles:

- **Parse** — `clip.vision.feature_layer` is read at `clip.cpp:1413` via `get_arr_int()` (`clip.cpp:3894-3917`). That helper validates that the key is an array, that its element type is `GGUF_TYPE_INT32`, and that the element count matches. It performs no range check on the values, so `[4096]` comes back as ordinary data.
- **Allocate** — `model.layers` is sized from a *different* key at `clip.cpp:2245-2246`: `model.layers.resize(hparams.n_layer)`, where `n_layer` is `clip.vision.block_count`. With `block_count = 2` and `sizeof(clip_layer) == 720`, that is a 1440-byte allocation.
- **Change of role** — in `models/llava.cpp:24-29`, `max_feature_layer` is initialised to `hparams.n_layer` (which would be safe), but line 29 overwrites that as soon as any declared value is `>= 0`, with no clamp back. The field stops meaning "which layer's features do I want" and becomes "how many layers does the model have".
- **Sink** — `models/llava.cpp:56-57` loops `for (int il = 0; il < max_feature_layer; il++)` and takes `auto & layer = model.layers[il]`, dereferenced at line 67 by `build_norm(cur, layer.ln_1_w, ...)`. At `il == 2` the read is past the end of the 1440-byte region.

This fires during **model load**, inside `clip_init`'s warmup (`clip.cpp:3975` → `:3692` → `:3701` → `:3764`) — before any image is encoded. The `--image` argument only exists to satisfy the CLI's single-turn mode.

```
./build/bin/llama-mtmd-cli -m victim_text_model.gguf --mmproj mmproj_evil.gguf --image photo.png -p "describe this image"
```

```

READ of size 8 ... 0 bytes to the right of a 1440-byte region
    #0 clip_graph_llava::build()                     tools/mtmd/models/llava.cpp:67:37
    #1 clip_model_loader::reserve_compute_meta(...)  tools/mtmd/clip.cpp:3764:70
    #2 clip_model_loader::warmup(...)                tools/mtmd/clip.cpp:3701:20
    #3 clip_model_loader::warmup(clip_ctx&)          tools/mtmd/clip.cpp:3692:9
    #4 clip_init(char const*, clip_context_params)   tools/mtmd/clip.cpp:3975:17
    #5 mtmd_context::mtmd_context(...)               tools/mtmd/mtmd.cpp:582:20
    #6 mtmd_init_from_file                           tools/mtmd/mtmd.cpp:1089:20
    #7 mtmd_cli_context::init_vision_context(...)    tools/mtmd/mtmd-cli.cpp:170:26
    #8 mtmd_cli_context::mtmd_cli_context(...)       tools/mtmd/mtmd-cli.cpp:121:9
    #9 main                                          tools/mtmd/mtmd-cli.cpp:437:22

    #1 std::vector<clip_layer>::_M_default_append(unsigned long)
    #2 clip_model_loader::load_tensors(clip_ctx&)    tools/mtmd/clip.cpp:2246:22
```

1440 bytes is exactly 2 × `sizeof(clip_layer)`, i.e. the `block_count` the file declared, and the allocation frame points straight back at the `resize()`. The stack runs unbroken from `main()`.

**Negative control:** `mmproj_benign.gguf` is byte-identical except `feature_layer = [1]`. It produces **0** ASan reports and gets *further*, not less far — the mmproj tensor loader runs and the CLI reaches `mtmd-cli.cpp:130`, which is only reachable once `init_vision_context()` has returned. It then exits 1 because the tiny text model has no chat template, which is unrelated. The only difference between the two runs is the `--mmproj` file.

On a stock release build this is a deterministic process kill rather than a silent read: because `sizeof(clip_layer) = 720` is a multiple of 16, the first out-of-bounds layer begins exactly on the next glibc chunk header, so `ln_1_b` reads the `size | PREV_INUSE` word, which `ggml_add` then dereferences at an unmapped low address on PIE (SIGSEGV, exit 139).

The `[0, n_layer]` check this PR adds at the parse site covers every consumer of the key at once, which is the right place for it. Worth noting the ordering constraint: `hparams.n_layer` comes from `clip.vision.block_count`, so the bound has to be applied after that key is parsed.

## 2. pocket-tts `state_out` — heap out-of-bounds write

**Trigger:** an mmproj with crafted F32 upsample weights, so that the graph's actual state tensor is `[48, 512]` (98304 bytes) while `state_out` was only given the slot reserved for the declared `[48, 1]`.

```
llama-tts -m pocket-tts.gguf --mmproj <evil>.gguf -p "..." -n 64 -t 4 --seed 42 --no-mmproj-offload -o out.wav
```

```
ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 98304 at 0x7fffbaf62ec4 thread T0
    #0 memcpy
    #1 clip_encode(clip_ctx*, clip_encode_params*)              tools/mtmd/clip.cpp:5849:13
    #2 mtmd_gen_audio_process_impl(...)                         tools/mtmd/mtmd.cpp:2020:10
    #3 mtmd_gen_audio_process                                   tools/mtmd/mtmd.cpp:2035:16
    #4 pockettts_gen_audio_pipeline::flush_gen_wav()            tools/mtmd/mtmd-helper-gen.cpp:952:13
    #5 pockettts_gen_audio_pipeline::step_gen(...)              tools/mtmd/mtmd-helper-gen.cpp:644:18
    #6 mtmd_helper_gen_audio_step_gen                           tools/mtmd/mtmd-helper-gen.cpp:1049:40
    #8 main                                                     tools/tts/tts.cpp:169:17

0x7fffbaf62ec4 is located 0 bytes after 2066116-byte region
allocated by thread T0 here:
    #5 std::vector<unsigned char>::resize(unsigned long)
    #6 clip_encode(clip_ctx*, clip_encode_params*)              tools/mtmd/clip.cpp:5841:19
```

The allocation at `clip.cpp:5841` and the `memcpy` at `clip.cpp:5849` disagree about the size — the vector is sized from the declared slot sizes while the copy uses the tensors from the graph. That is exactly the disagreement this PR removes by sizing from `ggml_nbytes(t)` on the graph tensors, with the `nullptr` check ahead of it.

Two things make this more than a crash: the write repeats once per `GEN_WAV` flush (7–8 times over a generation rather than once), and its contents are derived from attacker-supplied weights, so it behaves as a write primitive into the heap past `state_out`. I have not attached that follow-on work and don't think it belongs in a public thread before this lands.

The artifact for this one is ~58 MB so it isn't attached; I can provide it or the generator script if that's useful for review.

## What I did not test

- Only `llama-mtmd-cli` (issue 1) and `llama-tts` (issue 2) were run. `--mmproj` is also accepted by `llama-server` and `llama-cli` (`common/arg.cpp:60-65`); **`llama-server` would be the materially more serious case** for issue 1 and I'd suggest someone check it there.
- Issue 1 covers the `mlp` projector type and the `clip_graph_llava` path. Four other projector types route to the same graph builder (`clip.cpp:1052-1059`); I verified one of them, and did not examine the other graph builders.
- With `--no-warmup`, the issue-1 read moves to `clip_image_encode` and a real image is then required. I ran the default.
- ASLR was disabled in the container (`setarch -R`, the standard ASan workaround on kernels with high `vm.mmap_rnd_bits`). It does not affect parsing or validation.
- I did not enumerate the full affected commit range; `3d82ef62d47f` is what I reproduced on.
