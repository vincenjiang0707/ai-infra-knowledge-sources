### Problem description & steps to reproduce

First, run the model like this (likely will be reproducible with very small vision-enabled models too, but for larger ones it is much more noticeable issue since when the model is big, prefilling 100K-200K tokens from scratch to return to a dialog or Roo Code project takes long time if cannot restore saved cache):

```
numactl --cpunodebind=0 --interleave=all /home/lissanro/pkgs/llama.cpp/build/bin/llama-server \
--model /mnt/neuro/models/Kimi-K2.5-Q4_X-VL.gguf \
--mmproj /mnt/neuro/models/Kimi-K2.5/mmproj-Kimi-K2.5-F16.gguf \
--fit on --fit-ctx 262144 -b 4096 -ub 4096 -fa on \
--threads 64 --host 0.0.0.0 --port 5000 \
--jinja \
--slot-save-path /var/cache/llama.cpp/k2.5 --cache-ram 131072 --fit-target 512 \
--min-p 0.01 --top-p 0.95 --temp 1.0 --top-k 100
```

Then try to save the cache:

```
curl --header "Content-Type: application/json" --request POST --data '{"filename":"cache.bin"}' "http://localhost:5000/slots/3?action=save"
```

It fails to save the cache. Please refer to the "Relevant log output" section for the exact error message. For K2.5 support I used https://github.com/ggml-org/llama.cpp/issues/19127 but I think this issue is reproducible with any vision model, based on the error message.

    if (!check_no_mtmd(task.id)) {

### F3zz1k · 2026-07-17

@Lissanro I'm taking a look at --slot-save-flush-interval and wondering if it would be better to have an idle delay instead or on top of it.  With the interval it ensures we save every so long even when under continuous load where the cache is being extended continuously.  The catch is that under continuous single agent load you probably want to wait until the end of the message burst before saving to disk.  If we go with a delay then you'd only save to disk if the instance is idle for some time, where your GBs write aren't an inconvenience.  You'd still get caching if non-matching message comes in and you'd get the protection from long-running single agent being lost in most cases.  A single agent thread can't keep running forever anyways, the max cache size is a hard limit so we know at some point the session must go idle or move to a new thread and that's when I think we'd want to save.

Thinking about this has made me realize how much space we waste.  I want to look into saving deltas instead of the entire cache.  For attention layer kv this should be easy though it won't work for recurrent layers which we would need to snapshot at each delta chunk.  Flash-attention is also a bit problematic.  But this would make branches (shared context for subagents) relatively cheap though a bit more complex to handle and clean up.  That combined with a save on idle delay and image hash I think would cover all of our bases and save even more disk space.

This is just a thought.  I'm almost done working in your ideas to my branch and will test it overnight.  If I have time this weekend I might take a look at delta saving.  It's a whole other beast though so I might not be able to get to it until next weekend.

For the initial report though...  What would it take for us to get an official green light to implement mmproj aware caching into the official release?  I still think this is very important for anyone seriously using llama.cpp for agentic work.  In SimVX my agentic loops include having verifier agents doing visual checks and these need to be cached while the implementer agent is doing it's thing.

### F3zz1k · 2026-07-18

@gordan-bobic Technically you should be able to:
1. Prefill only, no generation — hit /completion (raw, not chat, so nothing gets appended) with the system prompt as the exact prompt and zero tokens out:
POST /completion
{"prompt": "<system prompt text>", "n_predict": 0, "cache_prompt": true}
      - n_predict: 0 evaluates the prompt into the slot's KV and stops — no sampling.
2. Save that slot to disk:
POST /slots/0?action=save
{"filename": "sysprompt.bin"}

Later, POST /slots/0?action=restore {"filename":"sysprompt.bin"} reloads it, and the next request continues from the system prefix.

Note this only works for non-recurrent on vanilla llama.cpp, I've got a fix for recurrent on my fork (I use it with gemma4 and qwen3.6) where I had to add handling to reuse a disk-restored recurrent state for the continuation (and regenerate the next-token logits for the exact-prefix case), and also add auto-saving to disk.
