## Overview

<!-- TODO(author): describe what this PR does and why. Be concise but complete -->
Two fixes to the `ggml-cuda` dequantization kernels:
- `dequantize_block_q8_0_f16` is guarded by `__CUDA_ARCH__ >= GGML_CUDA_CC_PASCAL`. MUSA's `mcc` defines `__MUSA_ARCH__` in the device pass and not `__CUDA_ARCH__`, so the condition is false, the body is dropped and the kernel is launched empty — every `q8_0` dequantization produces garbage. Also guard on `__MUSA_ARCH__`; NVIDIA builds are unaffected because `defined(__MUSA_ARCH__)` is false there.
- `dequantize_block_iq4_nl` writes `QK_K` values per block, but an `IQ4_NL` row is only guaranteed to be a multiple of `QK4_NL`, and ops such as `MUL_MAT` do use shorter rows. Threads whose 32-value sub-block starts at or past the end of the row were reading and writing past the end of the output. Skip those sub-blocks. For rows that are a multiple of `QK_K` the check never fires.
Both were found with `test-backend-ops` on an MTT S5000 (MUSA architecture `31`); the `q8_0` case is MUSA specific, the `iq4_nl` case is backend independent.
