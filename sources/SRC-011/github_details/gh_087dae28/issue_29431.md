### Problem description & steps to reproduce

- On Adreno A750
  - `maxComputeWorkGroupInvocations` is `2048`
  -  `maxComputeWorkGroupSize`: `[1024, 1024, 1024]`
- `use_small` is `true` in  `ggml_vk_argsort()`
- `pipeline_argsort_f32[10]` is used, which has `BLOCK_SIZE` of `1024`
- 2 workgroups are dispatched
- Only half of the array is sorted
- Test fails

I think the 2 workgroups end up sorting the first 1024 elements (so those end up being sorted twice while the other 1024 half remains unsorted).

### tczank · 2026-09-26

Confirmed on desktop RDNA3 against master (`a02c7f58c`) — the exact repro passes on both my devices:

- RX 7900 XTX (RADV NAVI31, `maxComputeWorkGroupInvocations = 1024`): OK
- Ryzen 7 7800X3D iGPU (RADV RAPHAEL_MENDOCINO, 1024): OK — also `ne=[4096,1,1,1]` OK

Root cause looks like the `pipeline_idx` clamp in `ggml_vk_argsort`:

```cpp
uint32_t pipeline_idx = std::min(ncols_pad_log2, num_argsort_pipelines - 1); // num_argsort_pipelines = 11
bool use_small = ncols_pad_log2 <= ctx->device->max_workgroup_size_log2 &&
                 ctx->device->pipeline_argsort_f32[pipeline_idx] != nullptr;
```

With `ne0 = 2048` (log2 = 11) on a device whose `max_workgroup_size_log2` is 11, `pipeline_idx` clamps to 10 (BLOCK_SIZE 1024), `pipeline[10]` exists, so `use_small` becomes true although that pipeline only covers 1024 columns — the cross-workgroup merge loop sits behind `if (!use_small)` and is skipped, and the dispatch runs 2 x 1024-wide workgroups over one row.

Broken window: `ne0` in (1024, 2048] on devices advertising 2048 invocations. Devices with 1024 limits (desktop RDNA) fall to the large path, hence PASS here.

Suggested fix: gate `use_small` on the unclamped index (require `ncols_pad_log2 == pipeline_idx`) so a clamped pipeline can never select the small path.
