### Problem description & steps to reproduce

Build llama.cpp on ROCm 7.14.0. The build succeeds. Running any resulting binary fails with:
`./llama-fit-params: error while loading shared libraries: libhipblas.so.3: cannot open shared object file: No such file or directory`

The libraries are located at /opt/rocm/core-7.14/lib/.  Setting LD_LIBRARY_PATH=/opt/rocm/core-7.14/lib works around the issue.

Build: 
`cmake -S . -B build   -DGGML_HIP=ON  -DGGML_CUDA_FORCE_MMQ=OFF   -DGGML_HIP_UMA=OFF   -DGGML_HIP_ROCWMMA_FATTN=OFF   -DGPU_TARGETS="gfx1151"   -DGGML_HIP_GRAPHS=OFF   -DLLAMA_CURL=OFF   -DGGML_CUDA_FORCE_CUBLAS=OFF   -DCMAKE_BUILD_TYPE=Release`

I have to use: `export LD_LIBRARY_PATH=/opt/rocm/core-7.14/lib:$LD_LIBRARY_PATH`

### liminfei-amd · 2026-07-19

PR: https://github.com/ggml-org/llama.cpp/pull/25899

Reproduced the loader failure in the official ROCm 7.14 image. The patch adds target-derived build and install RUNPATH entries for rocBLAS, hipBLAS, and the HIP runtime; patched build/install launches and a ROCm 7.2 control pass without a ROCm `LD_LIBRARY_PATH`.
The later `ggml_cuda_op_rms_norm_fused` abort is a separate runtime issue after loading succeeds.


### liminfei-amd · 2026-07-21

Update: we confirmed that the missing-library failure is caused by TheRock's Linux native packages not registering `/opt/rocm/lib` with the system dynamic loader.

We opened ROCm/TheRock#6716 and proposed the package-level fix in ROCm/TheRock#6718. llama.cpp PR #25899 has been closed in favor of fixing the root cause there.

### liminfei-amd · 2026-08-06

Update: the product-owner review on ROCm/TheRock#6718 clarified that global `ldconfig` or `LD_LIBRARY_PATH` selection should remain with system administrators, particularly for side-by-side ROCm installations, so I am no longer pursuing a TheRock package change. The revised llama.cpp design adds target-derived `BUILD_RPATH` only to `libggml-hip.so` and leaves installed ROCm selection explicit through standard `CMAKE_INSTALL_RPATH`, without adding a HIP-specific option. On current `master` in the official ROCm 7.14 image, the baseline clean launch exits 127 on `libhipblas.so.3`, while the patched build, install, and relocated install all exit 0 without a loader environment override. I would appreciate feedback on whether this application-side boundary is the preferred direction: https://github.com/ggml-org/llama.cpp/pull/26671

Hey there! Yes, I was finally able to figure out what was causing this, with some help from GPT.

The issue is that installing ROCm 7.14 on Windows can leave you with multiple ROCm runtime installations. In my case, llama.cpp was picking up the wrong `amdhip64_7.dll` from `C:\Windows\System32` instead of the one from my TheRock installation.

## The fix

After building llama.cpp, copy the TheRock version of `amdhip64_7.dll` into the same directory as `llama-server.exe`:

```ps
cd .\llama.cpp\build\bin
Copy-Item C:\TheRock\build\bin\amdhip64_7.dll .\
```

If you're using a prebuilt llama.cpp binary, simply copy it to the directory containing `llama-server.exe`.

This forces Windows to load the **TheRock ROCm** runtime instead of the older `C:\Windows\System32\amdhip64_7.dll`.
