# [Issue #28158] bug: Qwen3.8 DFlash/MTP speculative emits OOB token id == n_vocab (248320) on Vulkan

## 正文

## Summary
On AMD Strix Point (`gfx1150`) Vulkan with llama.cpp **b10724**, Qwen3.8-27B + z-lab DFlash2 (or ggml MTP draft) fails decode with:

```
init: invalid token[1] = 248320
decode: failed to initialize batch
```

**248320 equals `tokenizer.ggml.tokens` array length** — valid token ids are `0..248319`. This looks like a classic off-by-one in draft sampling / logits indexing.

## Environment
- GPU: AMD Strix Point `gfx1150`, Vulkan/RADV
- Runtime: llama.cpp **b10724** (also reproduced earlier on b10666)
- Target: `Qwen3.8-27B-UD-Q4_K_XL.gguf` (architecture `qwen35`)
- Draft A: `z-lab/Qwen3.8-27B-DFlash2-GGUF` → `Qwen3.8-27B-DFlash2-Q4_K_M.gguf` (`dflash`)
- Draft B: Unsloth `mtp-Qwen3.8-27B-Q4_0.gguf` (`qwen35`) — same `248320` with ggml MTP
- Flags: `--spec-type draft-dflash --spec-draft-n-max 2` (or `draft-mtp`)

Note: Muse-Glimmer + DFlash on the same binary/hardware **works** (different vocab/arch ~200k). Vanilla Qwen3.8 without speculation is fine (~4.3 t/s).

## GGUF metadata (streaming count of `tokenizer.ggml.tokens`)
| Field | Value |
|---|---|
| n_vocab (`tokenizer.ggml.tokens` len) | **248320** |
| bos_token_id | 248044 |
| eos_token_id | 248046 |

Same n_vocab / bos / eos on target, DFlash draft, and MTP draft.

## Expected
Draft sampling never emits token id `>= n_vocab`.

## Actual
First decode step emits token **248320** (exactly `n_vocab`). Server returns HTTP 500 / "Invalid input batch."

## Suggested fix
1. Clamp draft token ids to `[0, n_vocab - 1]` after sampling in the DFlash/MTP verify path.
2. Audit `qwen35` / `dflash` draft-head logits indexing for `< n_vocab` vs `<= last index` (or `argmax` over `n_vocab+1` slots).

## Repro
```bash
llama-server \
  --model Qwen3.8-27B-UD-Q4_K_XL.gguf \
  --model-draft Qwen3.8-27B-DFlash2-Q4_K_M.gguf \
  --spec-type draft-dflash --spec-draft-n-max 2 \
  --device Vulkan0 -ngl 999 --ctx-size 8192 \
  --cache-type-k f16 --cache-type-v f16 --flash-attn on \
  --host 127.0.0.1 --port 8080 --no-webui
# POST /v1/chat/completions → 500; log shows invalid token 248320
```

## Related
- #27812 fixed Vulkan graph-optimizer wrong tokens for speculative acceptance (merged); this is a separate hard OOB failure that remains on tip after that fix.
- Unsloth Qwen3.8 MTP on the same stack loads without `248320` in one layout but reports **accept rate 0.0** (possible related draft-head issue; see also #28097).

Happy to provide full server logs / GGUF SHA if useful.

### tczank · 2026-09-22

Controlled datapoint on the `248320` signature: on our side the garbage-logits source is known and removable, and the id comes out **always exactly `n_vocab`** — which reads like a sentinel, not an OOB index read.

- GPU: AMD Radeon RX 7900 XTX (gfx1100, RADV, wave64)
- Model: Qwen3.8-27B GSQ-RCO IQ3_XXS, embedded draft-mtp (`--spec-draft-n-max 2`)
- Build: llama.cpp ce8caa6 (b11065-era), Vulkan0, `-ngl 99 -t 16 -ctk q4_0 -ctv q4_0 -fa on`, n_ctx 131072
- Trigger: a local, uncommitted `GGML_VK_TILE_L=256:128:32` override in `ggml-vulkan.cpp` that violates the mul_mm warp-layout invariant `(BM/WM)*(BN/WN) == BLOCK_SIZE/WARP`: on wave64 (BLOCK=256, WARP=64, WM=WN=64) `warp_c = warp_i / (BM/WM)` collapses to 0, so every prefill workgroup (the "l" tile, m>64) writes only columns `[0,64)` of its 128-wide destination tile — the other half is never written → poisoned KV/hidden states → garbage draft-head logits.

Signature, byte-identical to this thread:

```
E init: invalid token[2] = 248320
E decode: failed to initialize batch
E srv decode: Invalid input batch. off = 0, n_batch = 2048, ret = -1
```

Anatomy of all six of our occurrences:

1. Every failure is the **first decode step**, draft-token position in the target verify batch (`token[2]` for us, `token[1]` for maciejdzialo — differs only by how many tail tokens enter the batch). Prefill never rejects: a full 29,213-token prefill completed first; prompt tokens are tokenizer-valid.
2. It also fires on fully KV-cached requests (failure ~1.2 s after launch, zero prefill) — the poisoned cache persists across requests.
3. **6/6 are exactly 248320, deterministic** — never a scattered id. With the override removed: 0 `invalid token` occurrences across all our retained logs on the identical launcher/model/flags.
4. Some requests inside the corrupted window *completed* without tripping validation (text unaudited) — i.e. only the sentinel manifestation fails loudly, which would fit the sporadic vanilla reports if the NaN source is intermittent.

Reading: a constant `n_vocab` emitted from fully-garbage score rows matches maciejdzialo's observation (all 16 DFlash top-k slots at 248320, NaN scores) better than an `argmax over n_vocab+1` / off-by-one *read* — an OOB read past a padded logits row would return varying ids, not a constant, across models/contexts/quants.

If that holds, there are two separate defects upstream: (a) whatever makes draft logits NaN on Vulkan (the actual bug), and (b) a selection/sampling path that silently yields `n_vocab` instead of failing at the source. Two concrete suggestions:

1. Grep the draft sampling/selector paths (DFlash selector, MTP draft sampling, top-k fill) for an `n_vocab` sentinel initialization or an `n_vocab_padded` row length — that is where 248320 is born.
2. Validate sampled draft ids `< n_vocab` at the sampling boundary with a *loud* error, rather than letting them reach `llama_decode`'s batch init. Caveat on the clamp in the OP: a silent clamp would convert this crash into silent garbage — our corrupted window already demonstrated the failure mode that produces (generations "succeeding" on garbage logits).

Not a vanilla repro — ours required the local tile patch — but the signature is byte-identical and the garbage source is controlled, so the constant-id datapoint may help choose between the OP's off-by-one hypothesis and the sentinel-on-NaN one.
