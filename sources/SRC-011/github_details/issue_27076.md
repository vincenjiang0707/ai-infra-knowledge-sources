### FabioLeitao · 2026-08-18

### Data point: `GGML_VK_MAX_NODES_PER_SUBMIT` (#24872) fixes device-lost at 32k context, but fails *worse* at 64k

Hit this on **Intel Iris Xe (Raptor Lake-U, Gen12)**, Mesa ANV 25.0.7, kernel 6.12.101, via Ollama 0.32.9 (which vendors ggml-vulkan with the #24872 fix present — verified with `strings libggml-vulkan.so`). Workload is [Strix](https://github.com/usestrix/strix) (autonomous AI pentesting agent) — its system prompt plus 30 tool schemas makes context genuinely big (~30k tokens), not synthetic.

Three runs, same hardware, same day — the failure mode changed each time:

| Run | Config | Context | Result |
|---|---|---|---|
| 1 | iGPU on, **no** batch limit | 30,795 tok | `ggml_vulkan: device lost on Vulkan0` / `vk::Queue::submit: ErrorDeviceLost`. Kernel: 9× `Fence expiration time out`, then `i915 GPU HANG: ecode 12:1:8ed9fff3` + `context reset due to GPU hang`. **Ollama recovered on its own** — subsequent requests worked without restart. |
| 2 | `GGML_VK_MAX_NODES_PER_SUBMIT=8` | 30,275 tok | **No device-lost, no GPU hang.** 39 `Fence expiration time out` absorbed over ~8min without ever escalating. Request completed: `POST /v1/chat/completions 200, 6m20s`. So the fix genuinely works at this size. ⚠️ But output was garbage (walls of `?????`), deterministic across 8 retries including fast cache-hit ones — separate correctness issue, possibly same class as #21888. |
| 3 | `GGML_VK_MAX_NODES_PER_SUBMIT=8`, larger-context model | `num_ctx=65536` | **Full system hard-lock.** 2 fence timeouts, then total silence — no GPU HANG ever declared, no context reset logged. Keyboard interrupts dead (Caps Lock LED unresponsive), **SysRq/REISUB did not work**, required physical power-off. Logs persisted up to the freeze and simply stop. |

**The relevant delta for run 3** is likely memory pressure, not just dispatch size. That model is 4.7B/Q4_K_M with `num_ctx=65536`; rough KV-cache estimate lands around ~9.6 GB, plus ~3.4 GB weights, against `available="14.0 GiB"` reported by the runtime for this shared-memory iGPU. Run 2's model was 32k context — roughly half the KV footprint, comfortable headroom. (Layer/kv-head counts inferred from embedding size, so treat the estimate as order-of-magnitude.)

Two things that may be useful to others:

1. **#24872 is effective** — it turned a reproducible device-lost into 39 cleanly-absorbed fence timeouts. Worth knowing it exists; it is not obvious from the error message that a knob helps.
2. **It has a ceiling, and past that ceiling the failure gets more severe, not less.** Going from "GPU context reset, driver recovers" to "kernel deadlock, SysRq dead, power-off required" is a meaningful escalation. Anyone testing this on a machine they care about should treat large-context Vulkan runs on shared-memory iGPUs as potentially machine-fatal, not just job-fatal.

Hardware was verified undamaged afterwards (Vulkan + OpenGL functional, normal temps, no thermal throttling in the pre-freeze boot log) — this is a logical deadlock, not a physical/thermal failure.

Happy to provide full `journalctl -k` excerpts or the runtime detection logs if useful. Not re-running the 64k case on this machine.


### cjohnston1158 · 2026-09-02

I have a reproducible Strix Halo case that now strongly points to the Linux AMDGPU compute watchdog as the trigger for at least one Qwen3.8-27B Vulkan `DeviceLost` path.

## Hardware / OS

- AMD Ryzen AI Max+ 395 / Radeon 8060S (`gfx1151`, Strix Halo)
- 128 GB unified memory
- Ubuntu 26.04
- kernel `7.0.0-31-generic`
- RADV / Vulkan

## llama.cpp

- commit `458681e1d5d4a29a1463c4732e03226cf384b997`
- build `10729`
- verified at runtime from result JSON:
  - `build_commit = 458681e1d`
  - `build_number = 10729`
- verified with `ldd` that `libllama*` / `libggml*` resolve from the b10729 build directory, not an older runtime/toolbox copy

## Model

- `Qwen3.8-27B-Q4_K_M.gguf`

## Minimal benchmark configuration

```text
-dev Vulkan0
-ngl 999
-fa on
--load-mode none
-t 16
-b 2048
-ub 512
-ctk f16
-ctv f16
-d 131072
-p 512
-n 128
-r 3
```

With the normal Linux 7.x AMDGPU watchdog behavior, this configuration reproducibly fails with:

```text
radv/amdgpu: The CS has been cancelled because the context is lost
vk::Queue::submit: ErrorDeviceLost
```

and the kernel reports the corresponding compute-ring timeout/reset, for example:

```text
ring comp_1.1.0 timeout
...
compute queue reset
...
device wedged, but recovered through reset
```

The failure does not appear to be caused by memory pressure:

- memory remains healthy
- swap does not grow materially

## Other observations

- `GGML_VK_MAX_NODES_PER_SUBMIT=1` did not fix it
- FA off did not fix it
- Q8/Q8 KV at 128K passes
- Q8 K / F16 V passes
- F16 K / Q8 V passes
- F16/F16:
  - `ub512` fails
  - `ub256` passes
  - `ub128` passes

## Controlled watchdog experiment

I then ran a controlled watchdog experiment using the exact same b10729 binary/libraries and the exact same benchmark parameters.

The only relevant boot-time change was:

```text
amdgpu.lockup_timeout=10000,60000,10000,10000
```

while preserving:

```text
ttm.pages_limit=31457280
amdgpu.cwsr_enable=0
```

Under the extended compute timeout, the previously failing `128K / F16-F16 / ub512` run passes cleanly:

```text
rc=0
classification=PASS
```

No userspace `DeviceLost` signature and no kernel GPU timeout/reset were recorded.

## Result rows

```text
pp512 @ depth 131072:
16.116 t/s average

tg128 @ depth 131072:
7.853 t/s average
```

Minimum `MemAvailable` during the run was approximately 86 GiB and final swap usage was 0.

## Interpretation

This looks like strong evidence that, on Strix Halo, this particular Qwen3.8-27B / 128K / F16-F16 / ub512 Vulkan path can generate a compute submission or work unit long enough to cross the default AMDGPU compute watchdog.

Reducing ubatch to 256 or 128 also avoids the failure, which is consistent with the same hypothesis.

Related: #27306 appears to be another RADV/AMDGPU timeout-driven `DeviceLost` path on Strix Halo, although that reproducer is MTP/prefill-specific.

I have a full evidence bundle with provenance, `ldd`, stderr, kernel logs, telemetry, and result JSON if useful.

### joleuger · 2026-09-02

I have a Radeon 780M. I have also added the amdgpu.lockup_timeout to my grub and it works now without issues with Qwen 3.8 27B.

```
sudo mkdir -p /etc/default/grub.d
sudo tee /etc/default/grub.d/amdgpu-latency.cfg <<'EOF'
GRUB_CMDLINE_LINUX_DEFAULT="${GRUB_CMDLINE_LINUX_DEFAULT} amdgpu.lockup_timeout=2000,60000,2000,2000"
EOF
sudo update-grub
```
