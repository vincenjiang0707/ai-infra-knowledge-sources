**Problem description**

Running `llama-server` with:
```
-ngl 99 -ncmoe 35 -fa on -np 1 -kvu -ub 2048 -c 65536 -ctk q8_0 -ctv q8_0 \
--spec-type draft-mtp --spec-draft-n-max 2 \
--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0.0
```
plain `/v1/chat/completions` requests (no tools, no grammar/schema constraint from the client side) with long Korean-language generations (2000-3000+ tokens) intermittently:

1. Produce stray foreign-script tokens mid-sentence unrelated to the requested language (e.g. random Chinese/Japanese/Arabic/Devanagari characters spliced into Korean words), roughly 2 of 5 long-generation test prompts.
2. Occasionally (~1 of 10-15 requests across quants/sampler settings) hard-fail mid-stream with:
   ```
   {"error":{"code":500,"message":"The model produced output that does not match the expected peg-native format","type":"server_error"}}
   ```

Tried to isolate the cause and ruled out:
- MTP speculative decoding (`--spec-type draft-mtp`) — disabling it entirely did not change frequency of either symptom.
- Quantization level — going from Q4_K_M to Q5_K_M made both symptoms *more* frequent (5/5 test prompts showed foreign-script splicing at Q5 vs 2/5 at Q4), which points away from a quant-precision explanation.
- Sampler settings — lowering `--temp` to 0.7, `--top-p` to 0.9, and raising `--min-p` to 0.05 (to cut the low-probability tail) did not help; the 500 error still reproduced on a different prompt.

No tool-calling involved in any of these reproductions, so this looks like the same underlying generation-corruption issue as the OP rather than a grammar/tool-schema-specific one. Happy to share fuller logs/prompts if useful for narrowing this down.

### What we measured

| condition | calls | 500s | rate |
|---|---|---|---|
| sequential, b10066 | 35 | 0 | 0% |
| sequential, b11109 | 35 | 0 | 0% |
| overlapping client requests, b10066 | 176 | 6 | 3.4% |
| overlapping client requests, b11109 | 208 | 3 | 1.4% |

b10066 vs b11109: Fisher exact two-sided **p = 0.31**. We cannot distinguish the two builds at this sample size — the newer build did not fix it here.

Notes that may narrow it down:

- **Only under overlapping requests.** 70 sequential calls across both builds produced none. The server is `--parallel 1`, so the overlap is queued client requests, not concurrent decoding.
- **`response_format`/`json_schema` is not required.** 48 calls on the JSON-schema path under the same load: **0 failures**. So for this model it is not #27279's path — the failures are on the plain text path.
- **Not truncation.** In the server log the failing requests' completions are full length (1,927–1,938 tokens) and `truncated` is 0 for the window. The generation finishes and is then rejected.
- **Retrying the identical request works.** 4/48 failed when called directly; 0/48 failed when a single retry was allowed on a 500 (p = 0.12, so suggestive rather than established, but we have not yet seen a retry fail).
- **Prompt-prefix reuse: suggestive, not isolated.** Prompts sharing a long prefix failed 6/240 (2.5%); prompts with a randomized 400-char prefix failed 0/144 (p = 0.088). We tried to knock this out with `--slot-prompt-similarity 1.0` and still saw 1/96 — but that flag only gates slot *selection*, so it does not disable intra-slot prefix cache reuse. Treat this as an untested lead, not a result.

Re: the earlier "reads more like a generation issue than a parsing one" — we cannot confirm or deny that here, because the server discards the text it rejects. If it is useful, we can re-run the failing shape with the parser bypassed and report whether the raw generation is malformed or clean. Say the word and we will capture it.

Full method and raw per-call data available on request.
