### Problem description & steps to reproduce

`llama_kv_cache_dsv4::state_read()` clears the **entire** CSA/HCA/LID compressed caches — i.e. all sequences — before reading back the state of a **single** sequence:

```cpp
// src/llama-kv-cache-dsv4.cpp:1594-1604 (master cd0fa60)
    kv_raw->state_read(io, seq_id, flags);          // <-- correctly scoped to seq_id

    if (!partial_only) {
        kv_csa->clear(true);                        // <-- cache-wide: ALL sequences
        kv_hca->clear(true);
        kv_lid->clear(true);

        dsv4_state_read_k_cache(io, kv_csa.get(), seq_id, flags);
        dsv4_state_read_k_cache(io, kv_hca.get(), seq_id, flags);
        dsv4_state_read_k_cache(io, kv_lid.get(), seq_id, flags);
    }
```

`llama_kv_cache::clear(bool)` is cache-wide, while the restore of the raw cache immediately above it is scoped to `seq_id`. The class already provides a sequence-scoped helper for exactly this:

```cpp
// src/llama-kv-cache-dsv4.cpp:1671
void llama_kv_cache_dsv4::clear_compressed(llama_seq_id seq_id, bool data);
```

That helper was introduced by #25521 ("DeepseekV4: clear cache only for seq rather than full", `13f2b28b0`) specifically so that per-sequence operations stop wiping the whole compressed cache, and `seq_rm()` (line 1447) and `seq_keep()` (line 1481) both use it correctly. `state_read()` is the one path that still does a full clear.

**Consequence.** With `--parallel N` (N > 1, which is also the server's auto default of 4), restoring the state of one sequence destroys the compressed KV of every *other* sequence while leaving their raw KV intact. Those sequences are left silently desynced — no error and no crash, they simply continue decoding against zeroed compressed caches. The user-visible symptom is one slot abruptly losing its context while other slots are being restored.

Affected paths are any single-sequence `state_read`: `POST /slots/{id}?action=restore`, `--prompt-cache`/checkpoint reload, and `llama_state_seq_set_data()` in the public API.

**Steps to reproduce**

1. `llama-server` with DeepSeek-V4-Flash, `--parallel 2` (or the auto default of 4) and `--slot-save-path <dir>`.
2. Build up a conversation on slot 0 and a second, different conversation on slot 1.
3. `POST /slots/0?action=save`, then `POST /slots/0?action=restore`.
4. Continue the conversation on **slot 1** — its continuation no longer reflects its own history.

**Suggested fix** — use the existing seq-scoped helper, which already treats `seq_id < 0` as "all":

```cpp
    if (!partial_only) {
        clear_compressed(seq_id, true);

        dsv4_state_read_k_cache(io, kv_csa.get(), seq_id, flags);
        dsv4_state_read_k_cache(io, kv_hca.get(), seq_id, flags);
        dsv4_state_read_k_cache(io, kv_lid.get(), seq_id, flags);
    }
```

**Disclosure about how this was found.** This is from code inspection while investigating unrelated context-corruption on our rig, not from a captured reproduction — we run `--cache-ram 0` and avoid the restore path, so I do not have a log of the failure itself. The control flow above is unambiguous, but I have not bisected a live repro, hence no log section below. Happy to run the reproduction above and report back if that would help.

**Note on similar-looking reports.** #25171 ("forgets everything") and #25259 ("forgot context when hit cache or use checkpoint in long context") describe the same user-visible symptom, but both were opened (2026-06-30 and 2026-07-03) *before* the commit below landed, so this is not their original cause. Mentioning them only because the symptom class is identical and multi-slot users hitting it today may now be running into this instead.
