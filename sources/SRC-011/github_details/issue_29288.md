After **255 successful `zeCommandQueueCreate` calls in one context**, the next one fails with

```
L0 zeCommandQueueCreate result: ZE_RESULT_ERROR_UNINITIALIZED, code 0x78000001 - driver is not initialized
```

while the device and driver are perfectly healthy. The kernel logs the real reason at the same time:

```
intel_vpu 0000:00:0b.0: [drm] *ERROR* ivpu_cmdq_create(): Failed to allocate command queue ID: -16
```

`-16` is `-EBUSY` from the command queue ID allocation (`IVPU_CMDQ_MIN_ID 1` .. `IVPU_CMDQ_MAX_ID 255`,
`drivers/accel/ivpu/ivpu_drv.h`), i.e. the per-context pool of 255 command queue IDs is full. The
reported `ZE_RESULT_ERROR_UNINITIALIZED` / "driver is not initialized" is misleading: nothing is
uninitialised, the queue budget is exhausted.

This is easy to hit with LLM workloads: the OpenVINO NPU plugin creates **one command queue per
compiled model** (`ZeroCommandQueue::create` from `Plugin::compile_model`,
`src/plugins/intel_npu/src/plugin/src/plugin.cpp`), and pipelines that compile per-layer or
per-subgraph models hold hundreds of them at once. Concretely, llama.cpp's OpenVINO backend
compiles one OpenVINO model per graph fragment and keeps them alive, so a gemma-3-1b run reaches
~419 compilations for the prefill graph alone and dies on the 256th, after which the backend logs
`device NPU is not available, fallback to CPU` and silently runs on the CPU.

## Minimal reproduction (no llama.cpp needed)

```python
import numpy as np
import openvino as ov

core = ov.Core()
p = ov.opset13.parameter([1, 4], ov.Type.f32, name="x")
model = ov.Model([ov.opset13.relu(p)], [p], "relu_test")
cfg = {"NPU_USE_NPUW": "YES", "NPUW_DEVICES": "NPU", "NPUW_WEIGHTS_BANK": "shared"}

kept = []                                  # hold them alive: one queue each
for i in range(300):
    kept.append(core.compile_model(model, "NPU", cfg))
```

```
$ LD_LIBRARY_PATH=<umd-1.38.0>:<openvino-runtime> python npu_hold_test.py
compile 255 FAILED while holding 255 compiled models:
  L0 zeCommandQueueCreate result: ZE_RESULT_ERROR_UNINITIALIZED, code 0x78000001 - driver is not initialized
```

Failure at exactly 255, every time. Controls, same driver/loader/device:

- one `compile_model` + one `infer` on the NPU: **OK** (`relu([-1,2,-3,4]) == [0,2,0,4]`)
- 300 `compile_model` calls **without** holding them alive (each released before the next): **OK**
- 64 infer requests created from one compiled model: **OK**

So the limit is the number of *simultaneously live* compiled models in one process.

## Expected

- A queue-budget exhaustion should not be reported as `ZE_RESULT_ERROR_UNINITIALIZED` /
  "driver is not initialized". `ZE_RESULT_ERROR_NOT_AVAILABLE` (or
  `ZE_RESULT_ERROR_OUT_OF_HOST_MEMORY`) plus a message naming the limit would let consumers react
  (retry later, release compiled models, fall back to another device) instead of debugging a
  phantom initialisation failure.
- Please confirm whether 255 command queues per context is the intended budget for the HW-scheduler
  path (`Scheduler mode: HW`) on NPU37XX, and whether it can be raised or made dynamic. If it is a
  hard limit, it needs documenting: with one queue per compiled model it caps the number of
  concurrently live compiled models, which is a normal pattern for LLM pipelines.
- The `ivpu_cmdq_create()` line is logged as `*ERROR*` but the failure is a resource limit, not a
  driver error; it would help to log the current/max queue count with it.

## Notes / caveats

- Not a wedged device: the queue IDs belong to the context and are released when the process exits.
  A trivial compile works again immediately after a failing run. Reports of an NPU that "needs a
  reboot" after such a failure are this same per-process exhaustion: the failing process is the one
  that needs more queues than exist.
- A module reload (`modprobe -r intel_vpu && modprobe intel_vpu`) and a PCI function-level reset
  (`echo 1 > /sys/bus/pci/devices/0000:00:0b.0/reset`, then unbind/bind) both re-initialise the
  device cleanly; neither changes the outcome, which is consistent with a per-context budget.
- The 255 model compilations in the python reproducer are tiny (`Relu` on `[1,4]`) and take under a
  second in total, so the limit is reached long before any memory or time pressure.
- Cross-reference for the OpenVINO side: creating one command queue per compiled model makes any
  pipeline that keeps many compiled models alive fail here; a shared/pooled command queue per
  context, or releasing the queue when the model is released, would avoid the cliff.

## Issue description

A Qwen3.5-class hybrid model that contains **GatedDeltaNet** (linear-attention) layers compiles on the NPU, but the **first inference hangs the NPU** and the device is reset by the watchdog (TDR):

```
L0 zeFenceHostSynchronize result: ZE_RESULT_ERROR_DEVICE_LOST, code 0x70000001 - device hung, reset, was removed, or driver update occurred
```

The failure is not a size/CMX issue and not a compiler-version issue:

- It reproduces with a **minimal** sequence: prefill chunk = 1, `-c 8`, prompt "Hi".
- It reproduces with two GatedDeltaNet-capable compilers: OpenVINO 2026.4.0's Compiler-in-Plugin, and the driver compiler from `linux-npu-driver` v1.38.0 (both contain `IE.GatedDeltaNet`).
- The same model runs correctly on the **CPU** plugin, so the graph/IR is valid.
- A plain-attention model (`Qwen/Qwen3-0.6B-GGUF`) runs on the same NPU, so the NPU stack works in general.
- With the older `intel-npu-driver` v1.35.0 compiler (no GatedDeltaNet) it fails earlier, at compile time: `Cannot create GatedDeltaNet layer ... unsupported opset: extension`.
- Size is ruled out: `Qwen3.5-0.8B-Q4_K_M` (532 MB GGUF, same `qwen35` GatedDeltaNet tensors `ssm_a` / `ssm_alpha` / `ssm_beta` / `ssm_conv1d` / `ssm_dt` / `ssm_norm` / `ssm_out`) hangs the NPU the same way, while the plain-attention positive control passes in the same session. The 0.8B blob is far below the 2 GB shave-memory window, so this is not a CMX/size limit. The same 0.8B GGUF runs on the CPU plugin (Prompt 101.8 t/s, Generation 18.6 t/s), so the file and graph are valid.

Expected: run correctly on NPU37XX, or fail with a clear "not supported on this platform" error. A device reset is not an acceptable failure mode. GatedDeltaNet / linear-attention hybrid models therefore cannot be used on Meteor Lake NPUs.

## Update 2026-09-20: failure mode changed, rank fix applied, NPU test blocked

After fixing the surrounding gemma issues and installing the NPU plugin **built from the
OpenVINO 2026.4.0 source** (the runtime-archive plugin fails gemma with a Reshape error), the
GatedDeltaNet failure changed completely: there is no hang and no TDR any more:

    While validating node 'extension::GatedDeltaNet GatedDeltaNet_2069 (...)':
    Rank of `query` input should be in [4] list, but it is 3.

Measured inputs: query/key `[1, ?, 2048]` (rank 3, flattened), value `[?, ?, 16, 128]` (rank 4),
gate/beta `[1, ?, 16]` (rank 3). OpenVINO's op requires query/key/value/state at rank 4
(`[B, S, H, D]`) and gate/beta at rank 3 (`[B, S, H]`).

Fix applied in `ggml-openvino/openvino/op/gated_delta_net.cpp`: reshape rank-3 query/key to
`[B, S, H_k, D]` (`{0, 0, H_k, -1}`, special_zero) before building the op, using the head count
already read from the ggml shape. With that, validation proceeds past the GatedDeltaNet op.

With the NPU healthy again (prebuilt plugin, which enumerates the device reliably), the rank
error is gone and the next validation fails on the head-size check:

    Check 'state_hidden_size_0.compatible(k_head_size)' failed
    GatedDeltaNet: query [1,1,1,6144], key [1,1,1,6144], value [1,1,16,128],
                   state [1,16,128,128], gate/beta [1,1,16]

ggml provides q/k/v as `[1, T, 16, 128]` (2048 elements each; state `[1, 16, 128, 128]`), so the
op needs `k_head_size = 128`. The OV tensors reaching the op carry **6144 elements (3x)** for
q/k (value is correct at 2048), i.e. q/k arrive packed/unsliced. Naively splitting 6144 into
heads gives 48, which then violates the GQA check (value heads 16 must be a multiple of q/k
heads). Next step: find why the q/k translators (`q_conv_predelta`, `k_conv_predelta`) emit a
3x tensor (likely a packed qkv) and slice them to `[B, T, H, D]` before building the op.

Also worth reporting upstream: for this fork the NPU plugin built from the 2026.4.0 source makes
gemma work but leaks command queues (`ivpu_cmdq_create(): -EBUSY`) and eventually wedges the
device, while the runtime-archive plugin enumerates fine but fails gemma with a Reshape error.

## Update 2026-09-22: graph now validates end-to-end, execution fails on the platform

Two llama.cpp-side bugs found while reproducing this were fixed (they only hid the platform
failure):

1. rank: `gated_delta_net.cpp` reshapes rank-3 query/key to `[B, S, H_k, D]` before building
   the op.
2. packed views: the GatedDeltaNet q/k inputs run through `RMS_NORM -> SCALE` chains whose
   sources are views of a packed qkv conv output (3 x 2048 features). The generic view handling
   returned such views unchanged (it only expressed a single differing dim, and a packed view
   shrinks the source's last dim), so q/k reached the op with 6144 elements instead of 2048.
   `process_view_input_new` in `openvino/utils.cpp` now slices those views at the view offset for
   the view's element count and reshapes to the view's OV shape.

With both fixes the whole Qwen3.5-0.8B graph translates and compiles with **zero shape-inference
failures** and the failure moves to execution:

    L0 zeFenceHostSynchronize result: ZE_RESULT_ERROR_UNKNOWN, code 0x7ffffffe

The same graph previously hung the NPU (TDR / `ZE_RESULT_ERROR_DEVICE_LOST`); now the graph is
valid and the NPU returns a plain execution error. `IE.GatedDeltaNet` is present in both
compilers used, the graph has no rank/shape problem left, and 0.8B is far inside the 2 GB shave
window, so this is the platform's GatedDeltaNet execution on NPU37XX. The bug report itself is
unchanged: a GatedDeltaNet (linear-attention hybrid) model cannot execute on the Meteor Lake NPU,
and the failure mode should be a clear "not supported on this platform" error rather than a
device reset.

Reproduction note (not an OpenVINO bug): a plugin built from the 2026.4.0 source tree embeds a
RUNPATH pointing into its build tree, so `dlopen("libze_loader.so.1")` resolves the Level Zero
loader built next to it. With that loader the plugin cannot initialise the device, llama.cpp logs
`device NPU is not available, fallback to CPU` (and still generates text). Any result claimed to
be from the NPU has to be checked with `grep -c "not available" <log>`; 0 means the NPU ran.
Build the plugin with `-DCMAKE_SKIP_BUILD_RPATH=ON -DCMAKE_SKIP_INSTALL_RPATH=ON`, or use the
released plugin.

The command-queue errors noted above (`ivpu_cmdq_create(): -EBUSY`) are now understood and are
**not** a leak: the driver allows 255 command queue IDs per context and the NPU plugin creates one
command queue per compiled model, so a process that keeps more than 255 compiled models alive fails
on the 256th with `zeCommandQueueCreate -> ZE_RESULT_ERROR_UNINITIALIZED` (misleading; the queue
budget is exhausted). The IDs are released when the process exits, so the device is not wedged and
no reboot is needed. See the separate report `openvino-bug-gemma-npu-queue-limit.md`; it does not
change the GatedDeltaNet issue below, but it does bound what can be verified on the NPU.

## Update 2026-09-22 (2): the "executes on the NPU" line above needs re-verification

Two things found today affect how the section above should be read:

1. The RUNPATH/loader problem means the earlier "compiles and executes on the NPU" observations
   were very likely **CPU fallbacks** (they predate the `grep -c "not available"` check). What is
   solid from that work: two real llama.cpp-side bugs were fixed (rank-3 query/key, packed q/k
   views), and with them the whole Qwen3.5 graph translates and compiles with zero shape-inference
   failures.
2. Any NPU run of this model must fit in the driver's 255 command queues per context, i.e. under
   255 live compiled models (see `openvino-bug-gemma-npu-queue-limit.md`). Whether Qwen3.5-0.8B's
   graph fits was not measured, so "compiles and executes on the NPU" is unverified.

To re-check properly: build the plugin without a build-tree RUNPATH (or use the released/wheel
plugin), run with `GGML_OPENVINO_DEVICE=NPU`, and require `grep -c "not available" <log>` == 0 and
no `zeCommandQueueCreate` failure in the log. Until then, the GatedDeltaNet bug report stands on
the original evidence (hang / device reset with the minimal reproducer, `IE.GatedDeltaNet` present
in both compilers, plain-attention control model running on the same NPU).
