# [PR #170] Skip untimed correct samples in geometric mean speedup

source: https://github.com/ScalingIntelligence/KernelBench/pull/170
state: open | updated: 2026-09-25T17:50:55Z
labels: 

## 正文

Fixes #169

## Cause

`KernelExecResult.runtime` defaults to `-1.0`. A correct kernel keeps that value when `measure_performance=False`, or when timing raises (eval.py stores the exception in `metadata["error_during_performance"]` and the row stays correct). `scripts/benchmark_eval_analysis.py` passes the runtime straight to `geometric_mean_speed_ratio_correct_only`, which divides the baseline by `-1.0`:

- one such row makes the product negative, and the root is NaN;
- two such rows cancel, giving a finite wrong value (baselines `[2, 3, 5]`, runtimes `[1, -1, -1]` give 3.107 instead of 2.0);
- a `measure_performance=False` run with an even number of correct rows reports a positive "speedup" built only from baseline times.

## Change

In `src/kernelbench/score.py`, `geometric_mean_speed_ratio_correct_only` now averages only correct samples that have a positive runtime, takes the root over that count, and raises a `UserWarning` that says how many correct samples were left out. If no correct sample was timed it returns 0, which is what it already returns when no sample is correct. Results for runs where every correct sample was timed are unchanged.

`fastp` and `geometric_mean_speed_ratio_correct_and_faster_only` are not changed. A `-1.0` runtime gives a negative speedup, which never passes `> p` for `p >= 0` or the `> 1` filter, so their values were already unaffected. When untimed rows are present, the warning is printed during the analysis run and accounts for `fast_0` being below the correctness rate.

## Validation

New tests are in `src/kernelbench/unit_tests/test_score.py`. The existing tests were run as well.

| Test | Kind | Before | After |
|---|---|---|---|
| `..._one_untimed_correct_sample` | bug | FAIL: NaN, no warning | PASS |
| `..._two_untimed_correct_samples` | bug | FAIL: 3.1072 instead of 2.0 | PASS |
| `..._no_timed_correct_sample` | bug | FAIL: 0.2449 instead of 0 | PASS |
| `..._untimed_incorrect_samples` | control: `-1.0` only on incorrect rows, must not warn | PASS | PASS |
| `..._slower_and_incorrect_timed_samples` | control: a correct sample slower than baseline, and an incorrect sample with a positive runtime | PASS | PASS |
| `test_geometric_mean_speed_ratio_correct_only` (existing) | control | PASS | PASS |
| `test_geometric_mean_speed_ratio_correct_and_faster_only` (existing) | control | PASS | PASS |
| `test_fastp` (existing) | control | PASS | PASS |

Totals: before, 3 failed and 5 passed. After, 8 passed, run with `-W error::RuntimeWarning`.

The two new controls are there to catch plausible wrong fixes. A separate script tried three of them against those controls:

- Counting every positive runtime for the root, including incorrect rows, gives 1.414 instead of 1.587.
- Dropping speedups below 1 gives 2.828.
- Warning on any `-1.0`, including incorrect rows, fails the no-warning control.

The same script also passed numpy arrays like the ones the analysis script builds (bool correctness, float runtimes) to the before and after code:

| Scenario | geo mean before | geo mean after | fast_p at p = 0, 0.5, 1, 2 |
|---|---|---|---|
| all correct rows untimed (3 of 4 correct) | NaN | 0, warns "3 correct sample(s)" | 0, 0, 0, 0 both before and after |
| one correct row failed only during timing | NaN | 1.414, warns "1 correct sample(s)" | 0.5, 0.5, 0.25, 0 both before and after |
| all correct rows timed | 1.0 | 1.0, no warning | 0.75, 0.5, 0.25, 0 both before and after |

How it was run: the package was not installed or imported from the clone. The three functions in `score.py` were extracted with `ast.get_source_segment` from the file before and after the change. Each version was written, with its own import lines, into a stub `kernelbench/score.py` in a directory outside the repository. The updated `test_score.py` was then run against each stub with pytest 9.1.1 on Python 3.12.4 and numpy 2.3.1. No stand-ins were needed: `score.py` imports only `numpy` and `warnings`, and real numpy was used.

Lint: `pyproject.toml` lists `ruff` as a dev dependency with no version or config. `ruff check --isolated` (ruff 0.16.9) on the two files found 3 issues before the change: I001 in both files, plus F401 for the unused `pytest` import in the test file. After the change it finds 2: the same two I001 import-layout issues, which were already there. The F401 is gone because the tests now use `pytest.warns`. `ruff format --check` wants to reformat both files both before and after the change, so the files were not reformatted.

Not run: the rest of the test suite, `scripts/benchmark_eval_analysis.py` end to end, Python 3.10 (the version `pyproject.toml` requires), numpy 2.4.0 (pinned in the archived `requirements.txt`), and any GPU evaluation.

## Notes

- This PR does not change the eval.py part of the issue (the excessive-speedup check divides by `-1.0` when timing failed).
- `fast_p` keeps its current definition: untimed correct rows count toward `n` and never toward the numerator.
