### Feature Description

Decouple graph shapes from the number of *active* slots: always prepare decode ubatches
padded to a fixed number of token positions B (B = `n_parallel`, or a small bucket set
{1,2,4,8}):

- inactive positions get a dummy token id;
- attention mask: padding **key** columns are −inf for all queries; padding **query** rows
  produce outputs that are never consumed (logit consumption reads only real slots);
- KV cache: padding K/V is written to a reserved dummy row (unified/ring KV), so real
  entries are never overwritten;
- `out_ids` fixed; content changes per step, shapes do not.

Then galloc reserves once, cgraph captures once per bucket, and steady state is
`set_inputs` + `cudaGraphLaunch`. Prefill stays unpadded: it is compute-bound, a separate
graph family, and rebuilding there is amortized by arithmetic.

This implies relaxing the batch>1 cgraph disable for shape-stable graphs: the restriction
exists because the update/patch path cannot track structural changes — with padding there
is nothing to track.

### Motivation

The practical consequence: `llama-server --parallel N` loses CUDA graphs entirely as soon
as ≥2 slots decode together. Every step falls back to the full pipeline: graph build,
`ggml_gallocr_alloc_graph`, per-kernel `cudaLaunchKernel`, input copies, sync. I have CPU
profiles showing exactly this: with 1 active slot the step is a cgraph replay; with 2
active slots every step is build+alloc+launch. Repro: run server with `-np 2`, send two
concurrent decodes, observe the disable message and per-step launch overhead in a profile.

Decode is the latency-critical steady state, and at small batches launch overhead is a
large fraction of step time — i.e. multi-slot serving pays exactly the tax cgraph was
built to remove.

### Cost model

Decode is memory-bandwidth bound: weights are streamed once per step regardless of
n_tokens. Padding 1→B active tokens adds negligible compute and trades it for removing
all launch/allocation overhead.

### Prior art

- vLLM: CUDA graph cache keyed by (padded) batch — core design.
- TensorRT-LLM: CUDA graph padding (e.g. "MTP with CUDA graph padding" in release notes).
- NVIDIA CUDA Graph best practices: "Solution 1 — Padding to fixed size".
- SGLang: fixed-batch capture for decode.

### Related

- #6763 (original cgraph integration), #7302 (avoid unnecessary cgraph disabling);
- #16548 (cgraph plans for split graphs — complementary: padding keeps shapes stable so
  reuse heuristics trivially hit);
- #20315, #25082 (cgraph cache growth from per-step shape/offset changes — padding
  collapses the cache key space and mitigates both);
- #3479 (batched decode performance), #11614 (cgraph disabled at batch > 1).

### Open questions

- Flash attention: with an explicit `kq_mask`, −inf columns suffice; with FA, padding keys
  need out-of-window positions or a kernel-side ignore flag. Which path first?
- B = `n_parallel` vs bucketing (capture count vs wasted compute).
- SWA models: ring size is already constant, so `n_kv` dim is stable; mask is window×B.
- Interaction with speculative decoding / MTP (per-layer residual outputs).
