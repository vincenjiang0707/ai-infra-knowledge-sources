### Problem description & steps to reproduce

I found a fix for part of the Flash attention causing errors in the numbers when taking HMX path. I traced the issue to a race condition in the HMX queue mechanism. I tested it on qdc :

```
ggml-hex: Hexagon Arch version v75
ggml-hex: HTP0 hwinfo: threads 4, hvx 4, hmx 1, vtcm 8 MB
adb: product:pineapple  model:Pineapple_for_arm64
QDC chipsetAlias: QRD8650
```


### **Dry run of the HMX queue:**
QKn = QK dot for block n. Example QK1 is the QK dot of block 1
OUn = O update for block n. Example OU2 is the O update for block 2


```
ITR 0
  queue: [QK0]    		     # QK0 pushed ahead of loop start
  push QK1          -> [QK0, QK1]
  pop                    -> [QK1]         # got QK0   OK, this is what the code wanted
  (no O update yet, kv_blk == 0)
  (no second pop)
  END OF ITERATION: [QK1] still waiting

ITR 1
  queue: [QK1]
  push QK2        -> [QK1, QK2]
  pop                 -> [QK2]          # got QK1   OK
  push OU0        -> [QK2, OU0]
  softmax
  pop                  -> [OU0]          # got QK2   -- the code believed it waited for OU0
  END OF ITERATION: [OU0] still waiting        <-- an O update leaks into the next iteration

ITR2 2
  queue: [OU0]                                 <-- left over
  push QK3        -> [OU0, QK3]
  pop                -> [QK3]          # got OU0   -- the code believed it waited for QK2
  push OU1        -> [QK3, OU1]
  softmax
  pop             -> [OU1]          # got QK3   -- the code believed it waited for OU1
  END OF ITERATION: [OU1] still waiting

ITR 3   (same shape as iteration 2, forever after)
  queue: [OU1]
  push QK4        -> [OU1, QK4]
  pop                 -> [QK4]          # got OU1
  push OU2        -> [QK4, OU2]
  softmax
  pop                 -> [OU2]          # got QK4
  END OF ITERATION: [OU2] still waiting
```



so from itr2 neither pop waits for what is actually wants. Every update itr ends with an O update still running. 
OU0 reads vtcm_v_tiles[prev_buf] and vtcm_p_tiles[prev_buf]. Its pushed in at itr1 when the buf_idx=1 so prev_buf=0
at step 1 fa_phase_v_interleave(..., vtcm_v_tiles[buf_idx], ...);   // buf_idx == 0
itr2 overwrites v_tiles[0] and its the buffer OU0 is still reading. This is the race condition. 


I did a bunch of testing:
1. Run with GGML_HEXAGON_USE_HMX=0
   102 failures went down to 2. This tell us HMX path is the problem in flash attention.

2. can_pipeline = false hardcoded
   102 failures went down to 32. so the pipeline causes most of them
3. ran same binary twice 
   52 vs 57 failures, different failing sets. 

4. is HMX engine inaccurate? wrote standalone harness in the hexagon sim multiplying matrices with k from 128 to 576 and compared with float32 refs. Matches to the last bit at all depths(found occasional deviations they are negligible). So the athematic is fine

5.  Started testing the queue.
    tried draining the queue before the V interleave across two different jobs two runs each [THE FIX]
    
```
    job         run          unmodified          drain fix
   743500        1            115 fail              49 fail
   743500        2            140 fail              59 fail
   743551        1            112 fail              47 fail
   743551        2            103 fail              53 fail
```


6. Why not just pop once more rather than drain? 
   I tested this first single pop gave 106 and 98 in the back to back runs. 

> Performace cost is +0.1% across 15 cases measured on the same device back to back.

I believe this race condition only caused part of the problem. The fix takes 103-140 down to 47-59, disabling HMX entirely gives 2. The other issue which is causing the errors is still unknown. I have the patch ready its a small change in the beginning of the loop to fix the race.
