### Problem description & steps to reproduce

Just spent the last two days knees deep in benchmark after benchmark with a bench harness I built out as I tried to optimize my setup. Essentialy a llama-bench-replica for all the flags.

I found some anomolies with MTP. After doing my best to track them down, I'm convinced these are unnexpected behavior. tldr: MTP is still a net gain, but my pp drops from ~1k to ~500 t/s. Wins back on my workloads to pay itself off in the benefits on tg, but... I'm pretty confident that hit hints at a bigger issue. I do think tb4 is probably exacerbating the issue, but my suspicion is this is an issue for others with more standard setups as well.

To be clear, on single gpu, it's like a 3% penalty to use MTP. When I split across my two gpus, it's like a 100% penalty. something is off. and settings the `draft mtp device` flag to set it to one gpu gets me back only 8% of that loss.

whenever the model is split across two GPUs with `--split-mode layer`. On a single GPU
the overhead is small. Same model file, same flags, only the device assignment changes.

I went down a few wrong paths on this (thought it was my eGPU, then thought it was
CUDA-specific) so I ended up with a fairly complete matrix. 22k token cold prompt (huge code file + give me a code review of this),
prompt eval t/s from server timings:

## Why I think this happens (or I should say, why AI tells me this is possibly happening--this is above my paygrade)

> In common/speculative.cpp the MTP process() hook runs a synchronous catch-up decode in
the draft context for every prefill ubatch (unless the model is mem-shared; the
"e.g Gemma4" comment). On a layer split that means every ubatch the pipeline between
the two GPUs gets broken by a decode on another context, so the ubatch overlap
(GGML_SCHED_MAX_COPIES) never gets going. That would explain why single GPU is nearly
free but any split pays ~2x regardless of backend.

### Nilline · 2026-09-16

I think I have the mechanism for this, and a patch that recovers the lost prompt processing.
Everything below is measured on b10964 (v0.4.1), on a two-GPU `--split-mode layer` setup with a
27B hybrid model (arch `qwen35`) and `--spec-type draft-mtp`.

## Mechanism

The MTP catch-up decode reads the target's hidden rows via `llama_get_embeddings_nextn(ctx_tgt)`.
That read forces the target's ubatch to complete before the MTP batch can be built.

On a layer split this is exactly the wrong place to block: while the host waits on the target's
output, the next GPU in the pipeline cannot start the following ubatch, so the overlap that makes
multi-GPU prefill fast is lost. On a single GPU there is no overlap to lose — which is the
asymmetry reported here.

Generation is unaffected because a generation step is one small batch; there is no next ubatch to
overlap with.

## Fix

Let the MTP catch-up lag one logical batch behind the target:

1. The target context keeps **two pinned-host buffers** for the nextn rows, each with a backend
   event recorded after its async D2H copy. MTP consumes the *previous* buffer and waits only on
   that buffer's event, so it never synchronizes the decode currently in flight.
2. `process()` **parks** the batch instead of decoding it immediately. Intermediate prompt chunks
   request no logits, so nothing reads them that turn and they can lag safely. The final prompt
   chunk and every generation batch do request logits, so they stay on the synchronous path that
   sampling correctness needs.
3. Consumers (`begin()`, `draft()`) flush the parked batch against the current buffer before they
   read.

Two supporting changes were needed:

- **The MTP context is excluded from pipeline parallelism.** Its single block gains nothing from
  it, and since the scheduler hands each newly allocated graph the next of its input copies, MTP
  alternating the catch-up and draft graphs made every draft graph see a new input address and
  re-record its CUDA graph instead of replaying it.
- **The MTP context reserves a K/V-only graph.** It consumes prompt batches only to populate its
  K/V, so reserving the generic full-output graph sizes the scheduler for an MTP logits pass that
  never happens.

## Results

Same prompt, greedy sampling, `cache_prompt: false` so every round pays the full prefill, three
rounds per arm:

| | prompt processing | generation |
|---|---|---|
| b10964 as released | baseline | baseline |
| with the patch | **+57%** | **+1%** (unchanged) |

Round-to-round spread on generation was under 1.5%, so the prompt-processing gain is well clear of
noise. A ~75k-token prompt behaves the same way, and stays stable across long runs.

A note on measurement, in case it saves someone time: this cannot be benchmarked at a normal
sampling temperature. MTP acceptance tracks how predictable the generated text is far more than it
tracks any flag, and at `temperature 0.7` the spread *within* one configuration was as large as the
difference between configurations (roughly ±20%). Greedy sampling brought that down to under 1.5%.

## Also worth noting

On this configuration b10964 does not start cleanly with MTP at a large context:

```
creating MTP draft context against the target model ...
ggml_backend_cuda_buffer_type_alloc_buffer: allocating ... on device 1: cudaMalloc failed: out of memory
graph_reserve: failed to allocate compute buffers
sched_reserve: compute buffer allocation failed, retrying without pipeline parallelism
```

It silently falls back to running without pipeline parallelism and continues, so the only symptom
is that everything is slower than it should be. Excluding the MTP context from pipeline
parallelism (above) removes this as well — the startup log is clean afterwards.

## Happy to open a PR

I would prefer to split it, since one piece is independent of MTP:

- **Graph reuse keyed on tensor shape alone.** `llm_graph_input_embd{,_h}` can currently reuse an
  mtmd embedding graph as a token graph: `can_reuse()` compares shapes, and an embedding batch and
  a token batch of the same length are indistinguishable to it. The fix carries which branch the
  graph was built for and refuses a cross-modality reuse — strictly more conservative than the
  `true` it replaces, since it can only refuse a reuse, never enable a wrong one.
- **The MTP prefill lag**, as described above.

Related, and part of the second piece: an external mtmd decode also leaves the scheduler in the
embedding topology, so it needs a re-reserve before the next text batch. Without that, prompt
processing in the same process dropped by about a third after a few images and stayed there until
restart; with it, it returns to full speed.

Let me know if the split makes sense, or if you would rather see it as one change.
