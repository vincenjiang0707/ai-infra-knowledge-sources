# qwen4exp decode depth-decay — LLM generated "fix" summary

**Arch:** `qwen4exp` (Qwen3.8-Flash-Next, 125B-A6B; 12 QSA sparse-attn + 36 Gated-DeltaNet layers, `indexer.top_k=2048`, `compress_ratio=4`).
**Problem:** single-stream decode slows ~linearly with context depth even though QSA is supposed to bound attention to a fixed top-k budget. Root cause (nsys-profiled): the top-k path was running as a **dense** attention scan over all `n_kv`, plus per-token re-pooling of the whole cache and MBs of host→device + P2P input traffic.
**Base:** llama.cpp master `df03399b8`, branch `levers`. **Build/run:** CUDA 12.4.1, `sm_86`, image `llama.cpp:lever2b-cuda124`; **`KV_TYPE=f16` is mandatory** (quantized KV can't reach the sparse MMA kernel at batch 1 on Ampere).

37.2tok/s to 50.8tok/s at 42k ctx (+37%)
22.5tok/s to 48.0tok/s at 111k (+113%)
11tok/s to 41.8tok/s at 250k (+280%)

## Changes (7 patches, `llama-levers/000*.patch`)

```
 lever1     src/models/qwen4exp.cpp                 |  9 +++++----   (+ incidental Dockerfile pip fix)
 lever3     src/llama-memory-hybrid-idx.{cpp,h}     |  99 ++++++      block-granular top-k
            src/models/qwen4exp.cpp                 |  72 ++++
 sparse256  ggml/src/ggml-cuda/fattn-mma-f16.cuh    |  3 +           whitelist DKQ=DV=256 MMA
 lever2     src/llama-memory-hybrid-idx.{cpp,h}     | 590 ++++++     persistent pooled block-key cache
            src/llama-kv-cache.{cpp,h}, qwen4exp.cpp
 lever2b    src/llama-memory-hybrid-idx.{cpp,h}     |  59 ++++       device-resident block-member cells
            src/llama-kv-cache.{cpp,h}, qwen4exp.cpp
```

**lever1 — enable the sparse-FA path (the big one).** The enablement PR #27742 shipped top-k as a dense mask with a `// TODO: enable sparse attention`. Un-TODO it: pass `top_k->ne[0]` as `n_kv_max` so flash-attn treats the finite mask entries as a sparse K/V set — O(top_k) instead of O(n_kv). Drops attention from ~11 ms to **0.22 ms/token @250k**.

```c
-    // TODO: enable sparse attention when we are ready
-    ggml_tensor * cur = build_attn_mha(q, k, v, nullptr, kq_mask_top_k, nullptr, nullptr, 0, kq_scale, il);
+    // LEVER1: passing top_k->ne[0] as n_kv_max -> sparse K/V set (deepseek4/GLM-DSA pattern, #27970)
+    ggml_tensor * cur = build_attn_mha(q, k, v, nullptr, kq_mask_top_k, nullptr, nullptr, top_k->ne[0], kq_scale, il);
```

**sparse256 — instantiate the kernel for this head shape.** `may_use_sparse` only whitelisted the MLA shapes; qwen4exp is `DKQ=DV=256, ncols2=8` and that MMA template instance already exists. One clause:

```c
-    return (DKQ == 512 && DV == 512 && ncols1 == 1 && ncols2 == 8) ||
+    return (DKQ == 256 && DV == 256 && ncols1 == 1 && ncols2 == 8) ||
+           (DKQ == 512 && DV == 512 && ncols1 == 1 && ncols2 == 8) ||
            (DKQ == 576 && DV == 512 && ncols1 == 1 && ncols2 == 16);
```

**lever3 — block-granular top-k.** Scores are block-constant and the budget is whole blocks, so select blocks first and expand only the ~513 selected blocks to cell indices (via `blk_cells`), instead of expanding block scores to all `n_kv` cells and sorting those. Removes the O(n_kv) expansion `get_rows` + one O(n_kv) mask add and shrinks the sort by `compress_ratio`. Fully-future blocks get −inf bias; the incomplete tail block's cells ride a small per-token side input.

**lever2 — persistent pooled block-key cache.** The indexer re-gathered, mean-pooled, RMS-normed and re-RoPEd **all** cached blocks every token though only the newest changed. Add a third per-QSA-layer buffer of pooled+normed+roped block keys; each ubatch recomputes only blocks it dirtied (host-side structural compare of member cells — also catches defrag/rollback/seq-ops with no invalidation hooks) and `ggml_set_rows` them in. Dirty count is pow2-bucketed (≥4) for CUDA-graph topology stability.

**lever2b — device-resident block-member cells.** After 1–3 the residual depth cost was input traffic (~3.1 MB/token HtoD + ~13.2 MB/token P2P for `blk_cells`/mask). Store each block's member cells in the block cache's V tensor (f32; `ggml_set_rows` takes no i32) and gather the top-k expansion on-device — removes the `blk_cells` term entirely.

## Validity

Every patch was A/B'd against the immediately-prior build and **kept only if it passed all gates**, all at temperature 0:
- **Exact needle-in-haystack retrieval** at 63k and 111k (a random code string embedded mid-context must be reproduced verbatim) — guards against the sparse path silently dropping the right K/V.
- **Multi-turn prefix reuse + rewind** and **2 concurrent slots** — guards against the persistent block-key cache going stale across defrag/rollback/seq ops.
- Throughput read from `timings.predicted_per_second` on `POST /completion`, `cache_prompt:false`, `n_predict:48`, `ignore_eos:true`.

A comparable dense model on the same rig (`arch=qwen35`, plain GQA, no indexer) stays flat at these depths, confirming the decay was QSA/indexer-specific, not KV bandwidth.

## Status / upstream

Upstream #28012 (this exact CUDA decay) is closed. Patches are self-contained and PR-able in order: lever1+sparse256 (smallest), then lever3, then lever2+lever2b (shared machinery). Remaining depth losses: host-side O(n_kv) grouping scan in `set_input_qsa`; per-GPU f16 mask fan-out; `flash_attn_mask_to_sparse_indices` re-scanning the mask per layer (an indices-in FA API would remove both). Full detail + nsys attribution in `new-issue.md` / `issue-speed.md §9`.

### goodbadwolf · 2026-09-22

### With speculative decoding on, the merged sparse path helps prefill and costs decode, and one clause separates them

Rig: one RTX PRO 6000 Blackwell (sm_120), `unsloth/Qwen3.8-Flash-Next-GGUF` UD-Q4_K_XL snapshot `38bb39ee`, `-ngl 999 -ot per_layer_token_embd=CPU -fa on -np 1 -c 524288 --rope-scaling yarn --rope-scale 2 --yarn-orig-ctx 262144 -ctk q8_0 -ctv q8_0`, default `-b 2048 -ub 512`, MTP speculative decoding at `--spec-draft-n-max 4`. Baseline is `53b1389d0b`; candidate is master `0c3626ec06` (b11070, which carries #28770 and not #28536) with PR#28243's MTP commits merged on top, clean merge. I reached `lever1` and `sparse256` independently before finding this thread, so first: both reproduce exactly as @lukolszewski and @wussh describe. Everything below is about speculation, which nobody here appears to be running.

**Read decode as steps per second, from the log rather than from acceptance.** With MTP, tok/s is the step rate times the tokens a step returns, and the second factor is draft acceptance, which is not controlled. The server already prints what is needed: `mean len` on its `draft acceptance` line is tokens per step, so a request's step rate is its own tok/s divided by its own `mean len`. One example from the runs below, three repetitions of one prompt at one depth: 41.80, 53.44 and 42.86 tok/s, a 28 percent spread, and 16.85, 16.91 and 16.74 steps per second, a 1.0 percent spread. Across eleven server starts the within-configuration step-rate spread stayed between 0.2 and 3.1 percent. `1 + n_max x acceptance` agrees with `mean len` to under 1.5 percent and works as a fallback, but `n_max` is the maximum draft length rather than the length drafted, so the logged value is the one to trust.

**The merged sparse path splits by phase.** Prefill tok/s and decode steps/s, three depths, fresh server per configuration, three repetitions, same prompts in the same order, decode taken per request from `mean len`.

| Depth   | baseline `53b1389d0b` | master, sparse disabled | master as merged | master, with the `Q->ne[1]` guard |
| ------- | --------------------- | ----------------------- | ---------------- | --------------------------------- |
| 9,411   | 1962.3 / 45.20        | 1978.4 / 45.82          | 1982.9 / 46.17   | 1977.6 / 45.90                    |
| 106,572 | 1586.9 / 32.35        | 1590.0 / 31.63          | 1683.8 / 30.88   | 1677.6 / 31.78                    |
| 350,734 |  989.7 / 17.01        |  994.3 / 16.97          | 1201.4 / 16.40   | 1194.0 / 16.85                    |

Column 2 is the control: with the sparse path disabled inside `shall_use_sparse`, the candidate binary lands within 2.3 percent of the old baseline on decode at every depth and within 0.5 percent on prefill. So the effect in column 3 is the sparse path and not the 34 intervening commits: **+5.9 and +20.8 percent of prefill, against -2.4 and -3.4 percent of decode.** The decode cost grows with depth, which the phase argument below predicts.

**Why the two phases disagree.** `shall_use_sparse` computes `n_gather = (ncols1 == 1 ? Q->ne[1] : ncols1) * n_kv_max` and engages at `K->ne[1] >= max(4096, 2*n_gather)`, and `switch_ncols1` tries the `ncols1 == 1` variant first. `n_kv_max` here is 2051, from `min(n_kv, indexer_top_k + r - 1)` with `top_k` 2048 and `compress_ratio` 4. A prefill flash-attention node sees one physical ubatch, 512 by default, so its `n_gather` is 1,050,112 and that branch cannot fire at any depth this model reaches. Prefill falls through to `ncols1 = 8, ncols2 = 8` and the union kernel, whose own sparse check needs `2*8*2051` = 32,816. An MTP verify batch has `Q->ne[1]` = 5, so `n_gather` is 10,255 and the threshold is 20,510: decode takes the one-column path from 20k of context onward. The 9,411 row sits below that and does not move.

That row is a weaker control than it looks. It shows the 34 commits cost nothing *at a depth where the sparse path is inactive on both axes*, which is not the same as showing they cost nothing at depth. The `QSA_SPARSE_MODE=0` column is the control that carries the argument.

**The cost looks like the index build rather than the attention.** I filed [#29281](https://github.com/ggml-org/llama.cpp/issues/29281) separately with `test-backend-ops` numbers. On the 11 sparse configurations it generates, all of them at `nb=1`, #28770 costs 64 percent median and 113 percent worst. Dividing the added time by the mask width gives a constant, 0.589 to 0.594 ns per column across a twelve-fold range of `kv` and across `n_kv_max` 512 and 2048, which points at `flash_attn_mask_to_sparse_indices` rather than at the attention kernel. Its new inner loop has a runtime trip count and a data dependent exit, so the `#pragma unroll` around it no longer yields straight line code, and at `ncols1 == 1` the body always runs once.

**If that is right, the scan fix belongs before the guard.** A per-column cost is paid whatever the batch width, so a 5-token verify batch spreads it over five queries and a 1-token decode over one, which would make 3 percent here and 64 percent there the same mechanism. Specialising `ncols1 == 1` might remove enough of it that the guard is unnecessary. I cannot say that it would, because the f16 conversion below is a second cost with the same shape and I have not measured it. I would fix the scan and re-measure the guard against that, rather than take both.

**Forcing the verify batch onto the union kernel instead is much worse**, so the current dispatch choice is right. Skipping the `ncols1 == 1` branch so a 5-token batch reaches `ncols1 = 8` gives 45.70 / 24.88 / 11.59 steps/s at the three depths, against 46.17 / 30.88 / 16.40 as merged. Prefill was unchanged at 1984.9 / 1686.4 / 1199.5, confirming only the decode path moved. The loss grows with depth.

**What does work is refusing the sparse path for narrow batches.** Column 4 adds one clause to `shall_use_sparse`, `if (Q->ne[1] < 64) return false;`, which covers both call sites. That clause has been serving this unit since 2026-09-21, behind an environment lever so the three states can be compared from one binary. Against the dense control it keeps +5.5 and +20.1 percent of prefill and returns decode to within +0.5 and -0.7 percent, inside the repeat spread at every depth.

**For continuations at depth the benefit depends on the append size, and small appends lose.** Production prefill on this unit is overwhelmingly short continuations rather than cold prompts, so this is the case that decides whether the guard is worth having. Two append sizes at the same 349k depth, same build pair, deployed against guarded: 893-token appends take 2053 and 1765 ms, so **+16.3 percent**, while 119-token appends take 885 and 912 ms, so **-2.9 percent**. Reading those four points as a fixed cost plus a per-token cost, the guard cuts the per-token cost 27 percent, from 1.51 to 1.10 ms, and adds about 75 ms of fixed cost, with break-even near 184 tokens. Two points per line is a weak fit and I would not defend the coefficients, but the sign change is measured rather than modelled. My best statistic for this unit's real traffic is a median of 287 newly evaluated tokens per call, which the model puts at about +4 percent. So the honest summary is a large win on cold deep prefill, a few percent on a median continuation, and a small loss on very short ones.

I would guess the added fixed cost is the top-k index build over the whole cache, which runs whatever the append size, but I have not measured that.

**The q8_0 restriction may be deeper than kernel reachability.** The batch-1 story is that quantized KV selects the VEC kernel, which has no sparse path. Speculation removes that: `Q->ne[1]` = 5 is above the VEC condition, so `MMA_F16` is selected and the sparse path is reachable at q8_0. It is reachable and it still loses for decode, because `MMA_F16` sets `need_f16_K`/`need_f16_V` and `fattn-common.cuh` converts the whole cache with `to_fp16(K_data, K_f16, ggml_nelements(K), ...)` before any index is read. That conversion is O(n_kv) and unconditional, so it caps what the sparse path can win, and a 5-token batch is too narrow to amortise it. I want to be careful about how far that goes: the dense `MMA_F16` path pays the same conversion, so this limits what the sparse path can win without demonstrating why it loses, and moving the conversion after the gather would not on its own prove the guard unnecessary. But if the reading is right, `q8-compact` and a `Q->ne[1]` guard are pushing on the same constraint from two ends.

**Separately, [PR#28213](https://github.com/ggml-org/llama.cpp/pull/28213)'s gather cannot fire alongside MTP at all.** Its condition requires `n_tokens` to equal `n_stream`, and a five-token verify batch against one stream never matches. Measured: decode steps/s of 45.30 / 32.00 / 17.05 with it enabled against 45.61 / 31.62 / 17.22 disabled, identical within the repeat spread at all three depths. With #28770 merged it looks redundant anyway.

**What I have not shown.** Retrieval of three planted constants at 10/50/90 percent depth scored 6/6 at 106,630 and 6/6 at 350,792 as merged, and the guarded configuration scored 6/6 at 350,792 against the running server. Six trials against one planted set is a smoke test, not a qualification of either path. I also had a weighted "percent of total serving time" figure here and have removed it: the journal window it rested on does not reproduce, so the honest claim is the per-phase numbers above and the continuation measurement, not a single blended number.

Happy to re-run any of this against a scan fix, to test `server-seq-compact`, or to open the guard as a PR if it still earns its place afterwards.
