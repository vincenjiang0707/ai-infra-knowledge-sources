### kwilliams90 · 2026-09-13

Reproduced on a different RDNA3 card (Radeon PRO W7800, gfx1100), Windows 11 Pro 26200, Adrenalin driver 32.0.21041.1000 (2026-01-07), official Windows Vulkan release zips, no rebuild.

Model: Qwen3.8-27B Q6_K GGUF (27.3B params, `qwen35` arch), MTP draft enabled (`--spec-type draft-mtp --spec-draft-n-max 2`). Same flags on both builds:

```
llama-server --ctx-size 65536 --parallel 1 --gpu-layers all --flash-attn on \
  --cache-type-k q8_0 --cache-type-v q8_0 --jinja --reasoning-format deepseek \
  --no-context-shift --batch-size 2048   # -ub left at the default 512
```

Measurement: one cold `/v1/chat/completions` request with a 63,432-token prompt (`cache_prompt` off), reading `timings.prompt_ms` / `timings.prompt_per_second` from the response.

| build | prompt tokens | prompt_ms | prompt tok/s | decode tok/s (after the long prompt) | VRAM |
| --- | ---: | ---: | ---: | ---: | ---: |
| b10780 | 63,432 | 266,643 | **237.9** | 31.9 | 24.3 GB |
| b10809 | 63,432 | 412,742 | **153.7** | 31.9 | 24.1 GB |

b10809 is 1.55x slower on prompt processing for the same request; token generation and VRAM are unchanged. On b10809, `-ub 1024` (425 s) and `-ub 2048` (432 s) did not help, and switching the KV cache to f16/f16 only brought it to 354 s (179 tok/s), so neither batch size nor KV quantization explains the gap.

One caveat: the 31-token warm-up prompt took 845 ms on b10780 versus 265 ms on b10809 in a single sample, so very short prompts may have gone the other way; I did not repeat that case.

One more observation that may or may not belong here: f16 KV is also slow on b10956 on this device (1896 at depth 0), even though the f16 scratch path is not merged as far as I can tell. And on this driver a 512-token prefill batch runs about 6 times slower than 1024 on every build back to b9637 (pp512 548, pp1024 3644, pp2048 3380, pp4096 2978 on b9637), which looks like a driver shader choice for that one shape and is independent of these PRs.
