### dmae97 · 2026-09-16

### Independent reproduction on RTX 5060 Ti 16GB (sm_120) + CUDA 13.2 — the discriminator looks like **IQ3_S tensor presence**, not "this model fails"

Different machine, different publisher set, and a cleaner split than the original report.

**Hardware / toolchain**
- RTX 5060 Ti 16GB (sm_120, Blackwell consumer), driver 610.88, WSL2 / Ubuntu 24.04
- CUDA toolkit **13.2** (nvcc V13.2.78), `libcudart.so.13`
- llama.cpp master `e13469a` (build 613), `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=native`
- Qwen3.8-27B (`qwen35` hybrid: 64 layers = 48 Gated DeltaNet + 16 gated attention), full offload `-ngl 99`
- Flags held constant: `-c 4096 -ctk q8_0 -ctv q8_0 -fa on`, greedy, prompt `The capital of France is`

**Result matrix**

| GGUF | `general.file_type` | IQ3_S | IQ4_XS | `blk.0.ssm_alpha.weight` | output |
|---|---|---|---|---|---|
| mradermacher heretic-ara IQ4_XS (866 tensors, embedded MTP) | 30 | **0** | 432 | IQ4_XS | coherent |
| RVN-IQ4_XS (851 tensors, no MTP) | 30 | **0** | 425 | IQ4_XS | coherent |
| unsloth UD-Q3_K_XL | 13 | 111 | 156 | Q8_0 | garbage |
| hauhau IQ3_M | 27 | 411 | 5 | IQ3_S | garbage |
| ISTA-DASLab GSQ-RCO IQ2_XS | 19 | 47 | 11 | BF16 | garbage |
| Bucoid Heretic-Ara iq4_xs-3.0 | 15 | 46 | 204 | F32 | garbage |

Two GGUFs pass, four fail. The two that pass are the only ones with **zero IQ3_S tensors**. Tensor count, embedded MTP, and file size do not separate them — one passing file carries the embedded MTP head at `block_count=65` and one does not.

**Controlled A/B that removes MTP as a variable:** ISTA-DASLab publishes the same quant with and without the embedded MTP head (`IQ2_XS` 851 tensors vs `IQ2_XS-mtp` 866 tensors). Both produce **byte-identical** garbage on this box, so the MTP head is neither necessary nor sufficient.

**Partial-offload threshold:** `-ngl 8` and `-ngl 16` are coherent, `-ngl 32` and above are garbage. Same shape as the "silently breaks past a certain offload size" behaviour in #27763.

**Excluded on this box (all still garbage at `-ngl 99`)**
- flash attention on/off, and f16 vs q8_0 KV cache
- `GGML_CUDA_DISABLE_FUSION=1`
- `--fit off`
- stale shared libraries — verified with `ldd`; every `libggml*`/`libllama*` resolves inside the fresh build dir, no duplicates on disk, `LD_LIBRARY_PATH` unset
- small models are unaffected: Qwen3-0.6B (232 tok/s) and Qwen3.5-0.8B (207 tok/s, same `qwen35` arch and same `head_dim=256`) are correct at `-ngl 99`; a 30B model (Qwen3-Coder-30B-A3B Q3_K_M) is also correct at `-ngl 99`, 67 tok/s

This matches PR #28784's diagnosis (byte extraction from the packed 32-bit quant word miscompiled by nvcc 13.2 for sm_120). I'm adding the per-file IQ-type census because "this model fails" and "this file contains IQ3_S tensors" are different statements, and only the second one reproduces across publishers.

Related: #27763 (toolkit 13.2 vs 13.0/13.3), #27329.

Happy to rerun this exact six-row matrix after rebuilding with CUDA 13.3 and report back whether the fix closes all of them.


### dmae97 · 2026-09-16

### Follow-up: CUDA 13.3 closes it — same machine, same GGUFs, only the toolkit changed

Rebuilt with `cuda-toolkit-13-3` (nvcc **13.3.73**) alongside the existing 13.2 build, into a separate build dir so both binaries exist side by side and nothing else moved.

```
cmake -S . -B build-cuda133 -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CUDA_COMPILER=/usr/local/cuda-13.3/bin/nvcc \
      -DCMAKE_CUDA_ARCHITECTURES=120
```

**`test-backend-ops -b CUDA0 test -o MUL_MAT`**, counting only `type_a=iq{1,2,3}_s` cases:

| build | iq1_s / iq2_s / iq3_s | iq4_xs |
|---|---|---|
| CUDA 13.2 (nvcc 13.2.78) | **FAIL 34, OK 0** | OK 11 |
| CUDA 13.3 (nvcc 13.3.73) | **FAIL 0, OK 31** | OK 12 |

Failing cases on 13.2 reported `ERR` between 0.63 and 0.82 against a 0.0005 threshold, matching the original report.

**End-to-end, the same GGUF through both binaries back to back** (Qwen3.8-27B IQ3_M, 411 IQ3_S tensors, `-ngl 99 -c 4096 -ctk q8_0 -ctv q8_0 -fa on`, greedy, prompt `The capital of France is`):

```
build/bin/llama-cli           (13.2) -> reatoroge道上mong.Util…      garbage
build-cuda133/bin/llama-cli   (13.3) -> [thinking] … The answer is Paris. / Paris
```

Nothing else differs between those two lines — same file, same flags, same driver (610.88), same llama.cpp tree (`e13469a`), minutes apart.

**Rows I could retest.** I had deleted three of the six GGUFs from the earlier matrix during disk cleanup before rebuilding, so this covers three:

| GGUF | IQ3_S tensors | CUDA 13.2 | CUDA 13.3 |
|---|---|---|---|
| hauhau Aggressive IQ3_M | 411 | garbage | **coherent** |
| mradermacher heretic-ara IQ4_XS | 0 | coherent | coherent (no regression) |
| RVN-IQ4_XS | 0 | coherent | coherent (no regression) |

So on this box the split is exactly as PR #28784 describes: files carrying IQ1_S/IQ2_S/IQ3_S tensors are the ones that break, the breakage is in the kernels nvcc 13.2 emits for sm_120, and a 13.3 toolchain fixes both the op-level test and real generation. The IQ4_XS files never depended on the miscompiled path and are unchanged in both directions.

Environment: RTX 5060 Ti 16GB (sm_120), driver 610.88, WSL2 / Ubuntu 24.04, llama.cpp `e13469a`.

one thing though: you don't need 13.3. built the same tree against four toolkits, nothing else changed:

| 13.2.86 | 13.2.2 | 0 / 0 |
