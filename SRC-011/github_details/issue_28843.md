### Feature Description

Add a Strix Halo (gfx1151 / RDNA3.5) specific tuning for the Vulkan KHR_cooperative_matrix (coopmat) matrix-multiply tiles, to make prompt processing (prefill) faster on models like Qwen3.8-27B.

Today the AMD coopmat path uses one generic large tile for all AMD cards; Strix Halo is an integrated GPU with its own cache sizes and wavefront behavior, so it should get its own tile sizes, picked by measuring.

## Measurements / observations

`UD-Q4_K_S`, `-p 128 -n 32 -b 128 -ub 128 -r 3 -fa on -ngl 99`:

- `pp128: 194.13 ± 1.45 t/s`, `tg32: 12.86 ± 0.10 t/s`

|---|---|---|---|
| m=17408, k=5120 (FFN up/gate) | 69x 2087us (10.9 TFLOPS) | 17x 2084us (11.0 TFLOPS) | 14x 2045us (11.2 TFLOPS) |

Path checks (same flags, prove which code runs):

- `GGML_VK_DISABLE_COOPMAT=1` → pp128 falls to 106.21 (-45%), tg32
  unchanged. So prefill runs on coopmat, decode does not.
- `GGML_VK_DISABLE_INTEGER_DOT_PRODUCT=1` → pp128 falls to 174.53

History: PR #18749 (generic AMD large tile `{256,128,128}`) gave

was never specialized for gfx1151. The card reports only `16x16x16`

room left in workgroup geometry, subgroup size, and LDS traffic.

## Proposed behavior

1. Detect gfx1151 narrowly (AMD + coopmat + not proprietary driver +
   `uma` + 64 KiB shared memory + `STRIX_HALO` device name) and give it
   its own `l/m_warptile_mmq*` values, found by measurement: first
   BM/BN/BK geometry (including non-square), then subgroup 32 vs 64,
   then `LOAD_VEC_A` / LDS bank padding per quant type.
2. Generic AMD path and all other vendors/drivers stay exactly as now.
3. Longer term: rebase and evaluate the int8-coopmat prototype branch,
   starting with NVFP4 (simple dequant, already in the upstream MMQ
   type lists) before attempting `iq4_xs`.

### Motivation

Prefill at `n=128` is compute-bound (about 380 FLOP/byte vs a machine balance of about 325), while decode (`n=1`) is memory-bandwidth-bound near the ~200 GB/s wall. So tile tuning moves prefill/TTFT without being able to hurt decode much and the per-shape table above shows prefill GEMM at ~9-11 TFLOPS against a ~65 TFLOPS WMMA roof, i.e. mostly headroom. Prior art (#18749) already proved tiles alone can move Strix Halo prefill by tens of percent.

### Possible Implementation

- Step 1: sweep `l_mmq` BM/BN/BK (`{256,128,128}` vs `{256,64,128}`
  vs `{128,128,128}` vs `{256,128,64}`) and `m_mmq` at `n=128`;
  keep `s` tiles stable; verify each candidate survives the
  `matmul_shmem_support` guard via `GGML_VK_PERF_LOGGER=1`.
- Step 2: clone the winner with `WARP 64 -> 32` (RDNA3 is natively
  wave32; current tiles use 64).
- Step 3: `LOAD_VEC_A` 4 -> 8 for `q4_K`/`q5_K`/`iq4_xs` int paths,
  `SHMEM_STRIDE_PAD` 8 vs 4/16 on the winning tile.
- Step 4: measure (do not assume) B-operand layout per dtype; expect
  ~0% on fp16.
- Step 5: rebase `0cc4m/vulkan-coopmat-int8`, `test-backend-ops` all
  covered quants, measure pp128/512/2048 + tg32; NVFP4 first, then
  consider `iq4_xs` (43.8% of prefill, covered nowhere today).
- Bench rule: matched `-b/-ub` flags, cool-downs, tg32 guard on every
  step, `test-backend-ops` on every tile change. Tiles must stay
  bit-identical (same accumulation order) or pass greedy exact-match
  (`--temp 0 --top-k 1 --seed 42`).

### tczank · 2026-09-22

Follow-up to my gfx1100 datapoint above — the retune is now **measured with a correctness check**, and I found a hard invariant the tile must satisfy. A naive "bigger tile" retune silently corrupts.

**Setup:** RX 7900 XTX (gfx1100, RADV NAVI31), llama.cpp b11065 (`ce8caa6`) + a local env-var override for the l-tile (`GGML_VK_TILE_L=BM:BN:BK`, rewrites `l_warptile_mmq` and `l_mmq_wg_denoms` in lockstep), Qwen3.8-27B IQ3_XXS (MTP), q4_0 KV, 16 threads, `llama-bench -p 512 -n 512 -r 2`; gaming env vars (MANGOHUD/RADV_PERFTEST/AMD_VULKAN_ICD/DXVK_ASYNC) cleared for all runs.

**The invariant** (coopmat D-write in `mul_mm.comp`): warps map onto the tile with `warp_r = warp_i % (BM/WM)`, `warp_c = warp_i / (BM/WM)`. Full coverage requires `(BM/WM)·(BN/WN) == BLOCK/WARP`. On gfx1100: `subgroupSize = 64` → WARP = WM = WN = 64, BLOCK = 256 → **4 warps**, so `(BM/64)·(BN/64) == 4`:

| tile | (BM/64)·(BN/64) | result |
|---|---|---|
| 128:128 (AMD default) | 2×2 | valid |
| 64:256 | 1×4 | valid |
| 256:64 | 4×1 | valid |
| 256:128 | 4×2 | **invalid — only cols 0..63 of each 128-wide D tile are written; cols 64..127 are never written (D has no init, no fallback) → stale data** |

The 256:128 case is not just slow, it is **corrupting**: stale D → garbage hidden states → garbage logits → sampled token == n_vocab exactly (248320 for Qwen3.8) → rejected at the next batch init (`init: invalid token[k] = 248320`). That signature is byte-identical to #28158 — my case is a controlled, known bad-logits source that reproduces it. `llama-bench` cannot catch any of this (no correctness check): my first 256:128 bench reported +42.5% pp, which was just "half the matmul computed on garbage."

**Measured results (valid tiles; correctness = token-identical vs baseline on a ~634-token prompt, temp 0 greedy):**

| config | pp512 | tg512 | correctness |
|---|---|---|---|
| baseline (128:128) | 914.90 | 50.25 | ref |
| tile 64:256:32 | 933.33 (+2.0%) | 50.00 (−0.5%) | byte-identical |
| `GGML_VK_ALLOW_GRAPHICS_QUEUE=1` | 919.13 (+0.5%) | 53.32 (+6.1%) | — |
| **tile 64:256:32 + gfx queue** | **962.73 (+5.8%)** | **53.56 (+6.8%)** | byte-identical |

256:64:32 is also byte-identical but slower (−14.5% pp). Decode is unaffected by the tile (the override only touches the l-tile; decode uses the s-tile) — the tg gain comes from the graphics-queue flag, not the tile.

**Takeaways for the RDNA3 retune:**
1. The only valid non-default l-tiles for this warptile layout are 64:256 and 256:64 — same total FLOPs as the default; expect single-digit % from tile shape, not double-digit.
2. `GGML_VK_ALLOW_GRAPHICS_QUEUE=1` is the biggest single lever on this card (+6% decode).
3. If the warptile tables get retuned, add a sanity check `(BM/WM)·(BN/WN) == BLOCK/WARP` — a bad tile silently produces stale D columns and no benchmark can detect it. (The Intel Xe1 branch already satisfies the invariant by raising BLOCK to 512, so the pattern is in-tree; the AMD table just was never validated against it.)

Happy to share the exact benchmark/verify scripts.
