### Problem Description

After updating to the July 17 version (b10059 and b10043),  VRAM usage keeps increasing with each conversation turn and eventually causes OOM . After setting the environment variable `GGML_CUDA_DISABLE_GRAPHS=1` to disable CUDA Graphs, VRAM usage becomes stable and the problem disappears.

### Steps to Reproduce

1. Start `llama-server` with the parameters below.
2. Have 5-10 rounds of conversation.
3. Monitor VRAM usage - it keeps growing until OOM.

### laidick · 2026-08-22

Confirming this on different hardware, OS and driver, with per-request measurements. Our data does not support "it should stabilize after a point" — we ran it to exhaustion and it grows linearly until the server dies.

### Environment

- RTX 4090 24 GB, driver 580.126.09, CUDA 12.0.140, Linux
- llama.cpp fork, `version: 10469 (5ecb3c44c)`. **Caveat:** this is not a stock upstream build — DFlash2 is a local drafter, and MTP (`--spec-type draft-mtp`) is the configuration directly comparable to this report.
- Qwen3.8-27B IQ4_XS, `-c 262144 -fa on -ngl 99 -np 1 -b 1024 -ub 256 --threads 8`, quantized KV
- Fixed request stream, greedy decoding (`temp 0`, fixed seed), VRAM sampled per request

### The trigger is speculative decoding + CUDA graphs

| configuration | requests | VRAM growth |
|---|---:|---:|
| no speculation, graphs **on** | 50 | **+0.04 MiB/req** |
| MTP n=3, graphs **on** | 50 | **+7.96 MiB/req** |
| DFlash2 n=3, graphs **on** | 60 | **+7.97 MiB/req** |
| MTP n=3, `GGML_CUDA_DISABLE_GRAPHS=1` | 50 | +0.12 MiB/req |
| DFlash2 n=3, `GGML_CUDA_DISABLE_GRAPHS=1` | 60 | +0.033 MiB/req |

Plain inference with graphs enabled is clean on the same binary and the same traffic. Both drafters leak at effectively the same rate.

### It does not stabilize

Graphs **off**, fixed 32k context, 150 requests: `20955 -> 20957 MiB`. Steady state is reached after ~16 requests and VRAM is then bit-identical for the remaining 134 requests.

Graphs **off**, fixed 232k context, 50 requests: `21773 -> 21775 MiB`.

Graphs **on**, same 32k traffic, 80 requests: `20979 -> 21617 MiB`, i.e. +7.975 MiB/req with no sign of a plateau.

Under a longer mixed-workload run with graphs on, VRAM climbed monotonically from 20893 MiB to the 24081 MiB ceiling by request ~120 and the server stopped responding at request ~142. Same workload with graphs disabled: plateau reached at request 59, then bit-identical VRAM for the next 400 requests (0 restarts, 0 HTTP 500).

### Two hypotheses we tested and disproved

Posting these so nobody re-treads them:

1. **Unbounded `cuda_graphs` map.** It is keyed on `cgraph->nodes[0]` and only evicts after 10 s idle, so we expected a busy server to accumulate entries. Instrumenting it showed the population never exceeds **3–4 entries**. We also implemented an LRU cap and measured cap=64 against unlimited: **+7.967 MiB/req in both cases**, identical to three decimals. Cache population is not the cause.
2. **Proportional to graph captures.** Also wrong: DFlash2 recorded **116 captures** and MTP **1602 captures** over comparable runs, yet both leaked ~8 MiB/req. The growth tracks requests, not captures.

Additionally, `ggml_cuda_pool_vmm::pool_size` stayed stable (148 MiB / 20 MiB for the two contexts), `cudaDeviceGetGraphMemAttribute` reported `0/0 MiB`, and no `cudaMallocAsync` is used — while `cudaMemGetInfo` free memory decreased steadily. So the memory is not visible in anything ggml tracks.

**We are not claiming to have identified the exact driver-side allocation.** What the measurements establish is the trigger (speculative decoding + CUDA graphs), the rate, and that it does not converge.

### Workaround and its cost

`GGML_CUDA_DISABLE_GRAPHS=1` when using speculative decoding. Measured cost on our workload:

| metric | graphs on | graphs off | delta |
|---|---:|---:|---:|
| DFlash2 32k generation tok/s | 105.53 | 103.75 | **−1.7%** |
| DFlash2 232k generation tok/s | 59.55 | 58.22 | **−2.2%** |
| DFlash2 232k prompt tok/s | 701.75 | 681.4 | **−2.9%** |
| MTP 32k generation tok/s | 103.38 | 102.93 | **−0.4%** |
| draft acceptance rate | 0.85 / 0.81 | 0.85 / 0.81 | unchanged |

Cheap insurance against an OOM that is otherwise inevitable under sustained traffic.

### Not tested

We did not test upstream's vanilla draft-model speculative decoding (`--model-draft` / `draft-simple`) because we had no suitable small draft model on hand, so we cannot say whether it is affected. Given that two independent drafter implementations behave identically, we would expect it to be, but that is inference and not measured.

Happy to run further experiments on this hardware if it would help narrow it down.
