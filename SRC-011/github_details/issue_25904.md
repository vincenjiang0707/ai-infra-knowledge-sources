## Problem description
Running llama.cpp with OpenVINO NPU backend on Intel Core Ultra 7 255H (Arrow Lake-P) results in two failure modes depending on NPUW configuration:

**Mode 1: Without NPUW** — SIGSEGV in `pthread_once` inside `libopenvino_intel_npu_plugin.so`. Appears to be a TBB race condition during NPU plugin initialization.

Backtrace:
```
#0  std::once_flag::_Prepare_execution (libllama-server-impl.so)
#1  pthread_once (libc.so.6)
#2  libopenvino_intel_npu_plugin.so
```

Minimal C++ test (`ov::Core` + `get_available_devices()`) works fine. Python bindings work fine. Crash only occurs during model compilation within llama.cpp context.

**Mode 2: With NPUW** (`NPU_USE_NPUW=YES`, `NPUW_WEIGHTS_BANK=shared`, etc.) — avoids SIGSEGV but fails with:
```
No "WeightlessCacheAttribute" has been found in any of the model's Constant nodes.
This attribute is required for running the "weights separation" flow.
```

The `ov::WeightlessCacheAttribute` class exists in `libopenvino.so` but its header is not installed in the distro package, so it cannot be added to weight `Constant` nodes from the OpenVINO backend.

Without `NPUW_WEIGHTS_BANK=shared`, falls back to Mode 1 (SIGSEGV).

## Related issues
Similar NPU-related issues exist, but our case is distinct:
- #25809 — first-run RoPE shape mismatch on Windows; second run succeeds via NPUW cache. Our crash is a SIGSEGV in driver init, not a shape error, and no second-run workaround.
- #25324 — same CPU (255H) on Windows, but crashes with `GGML_ASSERT` in CPU ops, not in NPU plugin.
- #23984 — f32/f16 type mismatch on NPU compilation, not a driver-level crash.

## Steps to reproduce
1. Build with `cmake -DGGML_OPENVINO=ON ..`
2. Download any small Llama GGUF (e.g., Llama-3.2-1B-Instruct-Q4_K_M)
3. Run:
   ```
   GGML_OPENVINO_DEVICE=NPU ./build/bin/llama-simple -m model.gguf -p "Hello" -n 10
   ```
   Result: SIGSEGV
4. Run with NPUW config (current code sets `NPUW_WEIGHTS_BANK=shared`):
   Result: `WeightlessCacheAttribute` error

## Expected behavior
NPU inference works, similar to CPU-only build which produces 39 t/s on 1B model.
