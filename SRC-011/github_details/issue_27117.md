# [Issue #27117] speculative: draft-dflash draft acceptance collapses under concurrent sequences (-np 16 pathological, -np 4 healthy, --spec-draft-n-max 1 recovers)

## 正文

### Summary

`--spec-type draft-dflash` works well at low concurrency, but under concurrent slots the **draft model's predictions get corrupted**, draft acceptance collapses, and throughput goes into reverse (slower than no speculation). We traced this on an AMD gfx1151 APU across two ROCm versions and pinned down that the corruption **scales with the number of concurrently-drafting sequences, not with batch token count, server slot count, or draft length alone**:

| server `-np` | active requests | `--spec-draft-n-max` | noise-block batch | per-slot draft acceptance | aggregate throughput |
|---|---|---|---|---|---|
| 4 | 4 | 15 | 64 tok | **0.51 – 0.66** (healthy) | healthy |
| **16** | **4** | 15 | 64 tok | **0.51 – 0.66** (bit-identical to the row above, same seed) | healthy |
| 8 | 8 | 15 | 128 tok | 0.11 – 0.46 (degraded) | degraded |
| 16 | 16 | 7 | 128 tok | 0.22 – 0.74 (bimodal) | bad |
| 16 | 16 | 15 | 256 tok | **0.06 – 0.49** (bimodal; sustained load collapses to **0.0018**) | ~17–21 tok/s vs **37 tok/s** no-spec baseline |
| 16 | 16 | **1** | 32 tok | **0.83 – 0.92** | **~80 tok/s (2.2× the no-spec baseline)** |

Key observations that localize the defect:

1. **Per-slot corruption is established during prefill and persists for the request's lifetime.** 16 *identical* requests (same prompt, seed, temperature) produce an ~8× spread in acceptance across slots, visible from the very first speculative tick. The draft model's top-1 confidence is bimodal per slot: median 0.25 on "broken" slots vs 0.92–0.98 on "healthy" ones.
2. **It is not the server's slot configuration** — a `-np 16` server with only 4 in-flight requests produces bit-identical results to a `-np 4` server.
3. **It is not the drafter's intrinsic quality** — with `--spec-draft-n-max 1` the same 16-way load accepts 83–92 % of drafts and beats the no-spec baseline by 2.2×.
4. **It is not a ROCm-version regression** — identical pathology on ROCm 7.2.1 and 7.14.0 (we cannot test CUDA here; see "ask" at the end).

Controls (each on a fresh server):

- `-P4` instead of `-P16` (same `-np 16` server) → acceptance recovers to ~0.5–0.66.
- `--spec-draft-n-max 1` with `-P16` → acceptance 0.83–0.92, ~2.2× no-spec throughput.
- `-np 4` server, `-P4` → bit-identical to the `-np 16`/`-P4` run (same seed).

### Problem description & logs

Expected: draft acceptance roughly constant w.r.t. concurrency (speculative decoding is lossless; batching drafts from many sequences should not change per-sequence predictions), and DFlash at `-np 16` to at least not be slower than no speculation.

Actual (16 identical concurrent requests, fresh server, `0b1bad1`):

```
slot print_timing: id  1 | draft acceptance = 0.05333 (    4 accepted /    75 generated), mean len =  1.80
slot print_timing: id  7 | draft acceptance = 0.25424 (   45 accepted /   177 generated), mean len =  3.50
slot print_timing: id 10 | draft acceptance = 0.49074 (   53 accepted /   108 generated), mean len =  6.89
slot print_timing: id 12 | draft acceptance = 0.19048 (   44 accepted /   231 generated), mean len =  3.44
slot print_timing: id  0 | draft acceptance = 0.07289 (   32 accepted /   439 generated), mean len =  2.03
...
spec statistics: draft-dflash: #calls(b,g,a) = 16 31 294, #gen tokens = 3758, #acc tokens = 509,
                #mean acc len = 2.73, dur(b,g,a) = 0.020, 4133.404, 0.072 ms
```

Under sustained long-generation load this collapses completely — a 16×512, 5-rep run on ROCm 7.2.1 was aborted after 5 h 16 min with **3,270,000 drafted / 6,060 accepted (0.18 %)**.

Secondary symptoms at `-np 16` (measured on the same runs):

- Prompt processing with DFlash injection runs at ~57 ms/token (~17.5 tok/s) vs ~23 ms/token (~43 tok/s) without DFlash at the same `-np` — the per-sequence sequential `llama_encode` + inject `llama_decode` in `process()` is paid once per sequence per batch.
- Steady-state speculative tick is 1.15–1.5 s; `draft()` alone averages 133 ms per call (256-token noise block); per-token time grows ~3× over a 320-token request (207 → 570 ms/token), i.e. it decays as generations lengthen.
- The HIP backend logs `CUDA graph warmup reset` 1–2× per tick (54–194 per run) as batch composition changes, adding graph re-capture churn.

### Analysis (pointers, not conclusions)

- The corruption tracks **how many sequences share the batched non-causal noise-block decode** (`common_speculative_impl_draft_dflash::draft()`, one `llama_decode` with `n_seq × (n_max+1)` tokens): 4 seqs → clean, 8 → degraded, 16 → collapsed; same total token count with 16 seqs (`n_max=7`) is still corrupted, which is why we suspect per-sequence state (KV injection / attention mask / sampler alignment) rather than raw batch size.
- `common_speculative_process()` is invoked after **every** target decode ([tools/server/server-context.cpp](https://github.com/ggml-org/llama.cpp/blob/0b1bad14ff204627636aeb1de22ddcd5acb859d4/tools/server/server-context.cpp) `decode()`), including verification batches, and processes sequences sequentially — under a mixed 16-slot prefill this interleaves 16 encode+inject rounds with concurrent drafting.
- Ruled out: slot reuse / prompt-cache state (fresh server, cold slots); the "Drafts may degrade" prefill-ubatch path (no such warnings); drafter quality (n_max=1 accepts 0.87+); ROCm version (7.2.1 ≡ 7.14.0).
- **Ask:** could someone reproduce on CUDA? If it reproduces there, the defect is in the core spec-decode/masking path; if not, it points at the HIP path (and we can help bisect kernels).

### Workaround

At high concurrency either cap active requests (≤4) or use `--spec-draft-n-max 1` — measured **~80 tok/s aggregate vs 37 tok/s** no-spec baseline at `-np 16` (acceptance 0.83–0.92). Documenting this knob next to DFlash multi-slot guidance would already help users.

Unrelated observation while testing: at `temperature 1.0` the server sometimes terminates completed streams with HTTP 500 `"The model produced output that does not match the expected peg-native format"` — happy to file that separately with logs.

### Zeldatales · 2026-08-23

Adding three data points from the same gfx1151 family (Ryzen AI MAX+ 395 / Radeon 8060S), Vulkan/RADV rather than ROCm. Two of them may widen the scope of this issue.

### 1. The same pathology appears with `draft-mtp`, not just `draft-dflash`

Target `Qwen3.8-27B-Q4_K_M`, `-np N` with `--ctx-size 4096*N`, 3 rounds of N simultaneous requests, code-generation prompt, `max_tokens=300`, `temperature=0`, llama.cpp PR #27342 @ `5ecbe1ac1`:

| drafter | np=1 | np=2 | np=4 |
|---|---|---|---|
| DFlash2 Q8_0 | 21.22 | 15.87 | 25.32 |
| MTP Q4_0 | 22.10 | 16.52 | 26.35 |
| **none** | 11.11 | **20.14** | **34.14** |

(aggregate tok/s; per-request was 21.23 / 8.13 / 6.53, 22.10 / 8.33 / 6.80, 11.11 / 10.07 / 8.54 respectively)

MTP tracks DFlash2 within noise at every level. Whatever this is, it is not specific to the dflash drafter — which the issue title currently implies.

### 2. No-drafter control: the server's batching path is fine

The third row is the control I did not see elsewhere in the thread. Without a drafter, aggregate throughput scales close to linearly (11.11 → 20.14 → 34.14, 3.07× at np=4). With either drafter, aggregate throughput *falls below the single-stream figure* at np=2 and only recovers past it at np=4.

So the regression sits in the speculative layer, not in slot scheduling or continuous batching. That should narrow where to look.

### 3. Different signature at low np, and a MoE model that does not show it

My worst point is np=2, not np≥8 — aggregate drops ~25% below single-stream there, then recovers. That is a different shape from the acceptance collapse you measured at np=8/16, so there may be two distinct effects, or one effect whose onset depends on the target model.

Relevant here: a MoE target on the same machine scaled cleanly.

| target | drafter | np=1 | np=2 | np=4 | np=8 |
|---|---|---|---|---|---|
| gpt-oss-20b (MoE, ~3.6B active) | eagle3 | 74.89 | 104.91 | 125.24 | 154.49 |

Monotonic all the way to np=8, no dip. **Caveat: this is not a controlled comparison** — both the target architecture (MoE vs dense) and the drafter type (eagle3 vs dflash/mtp) differ from the rows above, so I cannot say which of the two explains it. If it is the target architecture, that would be worth knowing; if it is the drafter type, eagle3 might be a useful control for isolating the defect.

I have not reproduced your `--spec-draft-n-max 1` recovery yet — happy to run it, and to extend the np sweep to 16 on either target, if that would help separate the two signatures.
