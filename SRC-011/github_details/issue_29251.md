## Environment
- Models: Qwen3-VL-8B dense fine-tune (LoRA merged, bf16), converted with current `convert_hf_to_gguf.py` (mmproj: f16, also tested f32).
- Runtimes tested: b10707 (Vulkan, 0.7 box), b10909 (CUDA, 52 box), and a build of PR #21103 head on its merge-base (March 2026).
- Test set: 58 real canteen tray photos, verified human GT; metric = exact set match per tray (all dishes correct), soft-menu-prefilled prompts, temperature 0, max_tokens 384, client image side 1024 (and native 1920×1080 for the "original" configs).

## Symptom
| stack | set-exact (58) |
|---|---|
| HF transformers (bf16, training-identical stack) | **31** |
| llama.cpp, original image size (no client resize, ~2025 img tokens) | 28 |
| llama.cpp, 1024-side input (~576 tokens), f16 or f32 mmproj, Q8 or bf16 LM, Vulkan or CPU, b10707/b10909/PR#21103-head | **22–24** |
| llama.cpp, image preprocessed to HF-identical 832×448 (~364 tokens) | 16 |

Reproduction is deterministic. Note the monotone pixel-count effect on llama.cpp (352→16, 576→23, 2025→28) — consistent with per-token feature noise being compensated by redundancy.

## Exclusions (all tested)
- **Quantization**: Q4_K_M 19 / Q8_0 23 / bf16 24 — not the driver.
- **Client preprocessing**: feeding HF-processor-identical pixels (832×448 bicubic) makes it worse, not better.
- **Runtime version**: b10707 ≈ b10909 ≈ March base ≈ PR #21103 head (22–24).
- **Backend**: Vulkan 23 ≈ CPU 22 in the same build.
- **mmproj weight precision**: f32 mmproj = f16 mmproj = 23.
- **Chat template / empty-think prefill**: adding the training-time `<think>\n\n</think>\n\n` assistant prefill: 21–23, no change.
- **mrope**: sections [24,20,20,0] match HF; LLAMA_ROPE_TYPE_IMROPE is selected for QWEN3VL; image position advancement max(nx,ny)=26 matches HF's `max(h,w)//merge`; verified by reading both implementations.
- **Deepstack wiring**: GGUF has `n_deepstack_layers=3`; the 16384-wide input split order [main|ds0|ds1|ds2] verified; injection loop (view at (il+1)*n_embd, added for il<3) reviewed.
- **Vision embedding values**: concat order and per-chunk means/stds match HF to 4 decimal digits.

## Key quantitative evidence (the smoking gun)
Using `MTMD_DEBUG_EMBEDDINGS=1` on the same image (832×448, same pixels both stacks):

- HF *internal* precision floor (same model, f32 vs bf16, vision tower output): `|Δ|mean = 0.0147` (main merger output), 0.0016 / 0.0056 (deepstack outputs).
- HF(bf16) vs mtmd token-0 values: `|Δ| ≈ 0.05–0.15` per element — **≈5× the internal floor** — while global stats (mean/std/min/max/sum over the full [16384×364] tensor) agree to 4 decimal places, i.e. the divergence is zero-mean per-element noise rather than a structural/permutation error.

Conclusion: the mtmd vision path introduces per-element noise ~5× above what the same computation shows internally in HF. Downstream the LLM is sensitive to it (fine-tuned model; accuracy −8/58 @1024), and extra input resolution partially compensates.

## 评论 (1)

### DobsonDong · 2026-09-22

**Correction / updated findings** — after isolating a confound in our own evaluation harness. Two updates:

1) **The numeric finding stands unchanged.** The flash-attn path in `mtmd` casts K/V to F16 (`build_attn`, `CLIP_FLASH_ATTN_TYPE_ENABLED`); the non-flash path runs full f32. Measured per-element vs an HF-f32 reference on identical pixels (same model, current convert scripts, real 832x448 photo):
- attn_out-0: flash-on |d|mean 4.9e-3 -> flash-off 1.07e-4 (46x; the non-flash path sits ~5x *below* HF's own bf16-vs-f32 floor of 5.5e-4)
- final tower output: 4.5e-2 -> 3.0e-3

So `-fa off` (or making the cast optional) remains worthwhile for vision-path fidelity, and the non-flash path is measurably the more faithful one.

2) **The accuracy attribution in the original report was a confound — retracted.** Our llama.cpp eval harness and our transformers baseline disagreed on message content order ([text,image] vs [image,text] — harness bug on our side, mirroring an unused proxy script). After aligning the protocol (same model, same pixels, only the order flipped), our benchmark scores move by ~30 points; with the protocol aligned, `-fa on` vs `-fa off` differ by <=1/58, i.e. the f16-cast noise measured here is below the finetuned model's tolerance on our workload. The "accuracy -8/58" figure in the original post should be disregarded; the precision measurements above are unaffected.

Apologies for the noise in part 2, and thanks for maintaining mtmd — the debug callback infra (`llama-mtmd-debug`, `cb()` graph annotations) is what made the bisection possible.
