### Problem description & steps to reproduce

Problem: when running llama-server with Deepseek-v4-Flash on Intel B70 (after #26462 is addressed), the following warnings are observed.

Refer to #26462 for hardware and model used.

```
resolve_fused_ops: Lightning Indexer not supported, set to disabled
resolve_fused_ops: fused DeepSeek V4 HC pre not supported, set to disabled
resolve_fused_ops: fused DeepSeek V4 HC comb not supported, set to disabled
resolve_fused_ops: fused DeepSeek V4 HC post not supported, set to disabled
```

ggml-sycl supports_op gates lacking cases for these four ops. The scheduler falls back to unfused ggml primitives on CPU — correct, but slower and (for the Lightning Indexer) at significantly higher VRAM usage (the unfused indexer materializes a [n_kv x ubatch] score tensor per layer).

Once the Lightning Indexer is implemented, 1M context is easily achieved on B70.

@arthw -- two patches to address missing Lightning Indexer and HC fused ops. 

- PR #26515 (set_rows F16 fix, by arthw): OPEN, not merged. These patches
  do not depend on #26515 for compilation; #26515 is needed for
  end-to-end verification (DSv4F on SYCL crashes at first decode on master
  without the set_rows F16 fix).
- HC ops (DSV4_HC_PRE/COMB/POST): CUDA port (CUDA ref: dsv4-hc.cu, 294
  lines). Mechanical: element-wise and small-matrix math. No tensor cores.
- Lightning Indexer: CUDA port (lightning-indexer.cu, 588 lines, uses
  NVIDIA WMMA). Our kernel uses plain SYCL (no DPAS/WMMA). Deliberate
  16-lane subgroup adaptation (CUDA/Metal hard-assume WARP_SIZE=32 with
  explicit TODOs). Flat-index store with an explanatory comment addresses a
  known IGC Xe2 miscompile (strided stores via computed base pointers);
  AMD/Metal reviewers should not "tidy" it.

### cfsill · 2026-08-22

**Confirmed working on Arc Pro B65 (BMG-G31, 32GB)** — official `ghcr.io/ggml-org/llama.cpp:server-intel` image (build `b10573-d775b8967`, oneAPI 2025.3 userspace), Unraid, kernel 6.18.38, xe KMD, single device via `ONEAPI_DEVICE_SELECTOR=level_zero:0`.

All four `resolve_fused_ops ... not supported` warnings gone, no SIGSEGV at first decode, coherent output. DSv4F-0731 UD-IQ3_XXS (~104 GB) hybrid: `-ngl 99 --n-cpu-moe 35 -c 65536 -ub 1024 -sm none` on 32 GB VRAM + 96 GB DDR4 → **7.2–7.4 t/s sustained** over a 14.7k-token generation.

**Gotcha for anyone still seeing a silent first-decode crash with these fixes applied: check `SYCL_CACHE_PERSISTENT`.** With `SYCL_CACHE_PERSISTENT=1` set, we get a SIGSEGV at first decode that presents identically to the pre-#26515 crash — silent death right after `llama threadpool init`, dmesg showing a GPF in libc followed by an xe `bcs` engine reset (the reset is cleanup fallout, not the cause). gdb:

```
#0  __strcmp_avx2
#1  sycl::_V1::detail::getSortedImages(...)
#2  sycl::_V1::detail::PersistentDeviceCodeCache::getItemFromDisc(...)
#3  sycl::_V1::detail::ProgramManager::getOrCreateURProgram(...)
...
#17 ggml_sycl_op_bin_bcast<op_repeat>   ('hc_init' — first op of the DSv4F graph)
#18 ggml_sycl_repeat
```

Reproduces even with a freshly created empty cache directory, so it's the disk-read path itself, not cache corruption. Unsetting the variable (in-memory JIT only) makes the identical command run. Looks like an oneAPI 2025.3 runtime bug (will file against intel/llvm) rather than llama.cpp, but since this issue is where people land when DSv4F dies at first decode on SYCL, noting it here. None of the usual mitigations touch it (`GGML_SYCL_DISABLE_OPT/GRAPH`, `UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1`, legacy L0 adapter, NEO `EnableBlitterOperationsSupport=0` — all confirmed applied, crash unchanged).

Two smaller datapoints for hybrid (CPU-expert) configs:
- DSpark spec decode (`draft-dspark`, Q2K-Q8 drafter, n_max clamps to 5) measured **net-negative** here: 5.3–5.6 t/s @ 0.35 acceptance vs 6.4 t/s drafterless, same config at 32k. Batched verification multiplies DDR4 expert reads; with the fused ops the backend is faster without the drafter.
- Dual-GPU (B65 + A770) on pre-7.1 kernels fails with `UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY` whenever the L0 context spans both devices, any model — that's intel/compute-runtime#916 (drm/xe `XE_VM_BIND` bug, kernel fix in 7.1-rc1), unrelated to these ops. Selector-pinning one device per process avoids it.
