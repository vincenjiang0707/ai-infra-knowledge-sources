### mitoyosh · 2026-09-21

Two things that may help narrow this down: a negative result on CPU, and what your own log says about where the instance stopped.

**Not reproducible on CPU without speculative decoding** (master `930e2fa`, Debian 13 in an LXC, 6 threads, `gemma-3-1b-it-Q4_K_M`, `--metrics`, a 1 s `curl /metrics` loop, one 6002-token `/completion` that takes ~41 s of prompt processing):

| mode | scrape target | scrapes during the request | result |
|---|---|---|---|
| single model | `GET /metrics` | 42 × 200 | 200 after 43 s, `prompt_ms` 41787 |
| router (`--models-preset`, `--models-max 1`) | `GET /metrics` | 41 × 400 (router rejects it without `?model=`) | 200 after 41 s |
| router | `GET /metrics?model=…` (forwarded to the instance) | 41 × 200 | 200 after 42 s |

So the scrape being answered *during* prompt processing is fine on its own; the worker thread serving `METRICS` tasks while the main thread is inside `yield_to_queue()` works as designed here.

**Your log (`llama-router.log`) shows the stall is not during prompt processing, and not in the server queue.** Instance `[59181]`, task 25:

```
1.10.015  prompt processing, n_tokens = 70565, progress = 1.00, t = 39.30 s     ← prompt done
1.14.855  process_toke: n_gen = 107 … accepted 3/3 draft tokens, new n_tokens = 70675
1.14.861  decode: n_batch (effective) = 1024 → yield_to_que: yielding to queue   ← target decode of the 3 drafted tokens
1.14.861  process_new_: task 179 declined (NEXT_RESPONSE, normal while decoding)
1.14.861–1.15.101   162 × "CUDA Graph id … reused"
                    (every previous target decode in the log replays 258 graphs and finishes in ~25 ms)
1.15.499 … 1.44.501   /metrics tasks 180–209 served once per second by the worker thread;
                      llamacpp:n_decode_total stays at 109 in all 30 of them
                      no "done yielding to queue" ever follows the 1.14.861 yield
```

So generation had been running for ~5 s after the prompt finished, and the decode thread stopped mid-way through a CUDA graph replay (162 of 258) and never returned. The queue and HTTP side kept working — which is exactly why `/metrics` keeps answering and why there is nothing suspicious in the log: the thread that is stuck is the one that would have written the next line. GPU load at 0 is consistent with a thread waiting on the driver rather than computing.

That pattern — sm_120 (your 5070 Ti is compute capability 12.0), tensor split across two GPUs, hang inside CUDA graph replay with no error — is what #27330 describes (RTX 5090 Laptop, RC watchdog / Xid 8, `GGML_CUDA_DISABLE_GRAPHS=1` a complete workaround). Worth ruling in or out before treating `/metrics` as the cause:

1. `GGML_CUDA_DISABLE_GRAPHS=1` with the scraper still running — if the stall disappears, this is #27330 and the scrape is a bystander (it is the only other activity in the process, so it is what a "what changed" look lands on).
2. Same run with the scraper stopped, several requests long enough to reach generation — the log suggests the stall is a generation-time event, so it should reproduce without `/metrics` if it is a CUDA hang.
3. `dmesg`/Event Viewer for an Xid at the time of the stall.

If the scrape *is* required to trigger it, the interesting fact would be that the only concurrent activity is a second thread copying the `metrics` struct while the graph replay is in flight — but the log above does not show that thread doing anything else.

### mitoyosh · 2026-09-22

Thanks — the CPU-only result matches what the log showed (the stuck thread is the one issuing GPU work), and the fact that `GGML_CUDA_DISABLE_GRAPHS=1` only delays it rules out #27330 as the whole story.

One thing about `disable_compression`: on the server side it cannot change anything. `llama-server` does not compress API responses at all — the only gzip code in `tools/server/server-http.cpp` (`handle_gzip_header`) serves the pre-gzipped web UI assets. `disable_compression: true` only removes VictoriaMetrics' `Accept-Encoding: gzip` request header, which the `/metrics` handler never reads. So the "both settings together" run was really just `GGML_CUDA_DISABLE_GRAPHS=1` plus timing noise, consistent with it stalling at 188 s.

That leaves the PowerShell-vs-VictoriaMetrics difference as the real lead, and it is probably not the payload but the connection pattern. A scraper holds a persistent connection and, in router mode, every scrape goes through a `start proxy thread GET /metrics?…` on the router, which streams the child's response chunk by chunk (`http: streamed chunk` / `http: stream ended` lines in your log). Two cheap ways to pin it down without VictoriaMetrics:

1. From the same machine, in a loop: `curl -s -o NUL --http1.1 -H "Accept-Encoding: gzip" "http://127.0.0.1:9931/metrics?autoload=false&model=qwen38-27b"` once per second, and separately with `--keepalive-time 60` on one long-lived connection (or a tiny Python loop that reuses a `http.client.HTTPConnection`). If the persistent-connection loop stalls and the per-request one does not, it is the router's proxy thread + keep-alive, not the metrics content.
2. Scrape the child instance's port directly (the `on port 59181` in the log) instead of the router. If the stall disappears, the router proxy is in the path; if it stays, it is inside the instance.

And when it is frozen, a stack of the child process would say more than any log: Process Explorer → the `llama-server` child → Threads → the thread with the highest cycles stopped in `cudart`/`nvcuda` vs. one waiting on a mutex in the http/queue code are different bugs.
